Subject: [PATCH v3] advice: add scope hint for disabling advice messages
Series version: v4 (three patches)
Originating author: Vsevolod Myalitsin
Thread type: patch series

Core problem or goal
Add a `scope_hint` field to Git’s advice settings so that when users are told how to disable an advice message (e.g., `git config --global advice.detachedHead false`), the command includes the correct config scope (`--global`, `--local`, `--worktree`, or `--system`). The patch touches only `advice.c` and does not change any user-visible behavior beyond making the advice messages more accurate.

Current status
v4 is posted as a three-patch series: (1) refactor `vadvise()` to accept the full `advice_setting` struct, (2) introduce the scope-hint mechanism, and (3) assign `ADVICE_SCOPE_GLOBAL` to the `defaultBranchName` advice. Junio’s mechanical feedback from v3 (commit-message motivation, `vadvise()` documentation, indentation) is addressed. Junio’s review of v4 identified a build failure under `DEVELOPER=YesPlease` mode: the `switch` statement in `vadvise()` does not handle all values of the `CONFIG_SCOPE` enum (`CONFIG_SCOPE_WORKTREE`, `CONFIG_SCOPE_COMMAND`, and `CONFIG_SCOPE_SUBMODULE`), causing a compilation error. Jeff King (Peff) has now proposed an alternative to Junio’s suggested `BUG()`: treat all unhandled scopes as equivalent to the default (unadorned `git config` command), arguing that these scopes are either irrelevant to advice settings or would never be passed in practice. The series remains under review; no evidence of Junio picking it up for integration.

Key technical details
- Files touched: `advice.c`
- New field: `scope_hint` in the `advice_setting` struct
- Enum: reuse of `CONFIG_SCOPE` (local, global, worktree, system, command, submodule, unknown); `CONFIG_SCOPE_UNKNOWN` (value `0`) is interpreted as "use the default location for writing config" (currently local scope)
- Translatable string: rewritten to avoid string interpolation; no longer uses `"git config %s advice.%s false"`
- Symbols: `advice_setting`, `scope_hint`, `CONFIG_SCOPE_*`, `advice_config[]`, `vadvise()` interface (now takes `const struct advice_setting *`), `ADVICE_DEFAULT_BRANCH_NAME` with `ADVICE_SCOPE_GLOBAL` hint
- Helper function: `config_scope_name()` (existing) constructs the scope flag programmatically
- Refactoring: `vadvise()` now accepts the entire `advice_setting` struct instead of separate key and level arguments; call sites in `advise()` and `advise_if_enabled()` updated accordingly
- Build-failure resolution: two competing approaches: (a) Junio’s `default: BUG("unexpected scope value");` or (b) Peff’s `default:` case that treats unhandled scopes as equivalent to the default (local) scope

Open questions and loose ends
1. Build failure: the `switch` statement in `vadvise()` must handle all `CONFIG_SCOPE` enum values under `DEVELOPER=YesPlease` mode. The resolution is now between Junio’s `BUG()` and Peff’s default-scope fallback. No consensus yet.
2. Scope hint criteria for other advice settings: resolved only for `defaultBranchName`; whether other settings should default to `--global` or `--local` is left to future work or maintainer discretion.
3. Practical need for `--system` scope: Peff questions its relevance for advice settings but acknowledges the debate may not be productive at this stage.

Participant positions

Thread identity: Discussion on adopting an automatic code formatter for the Git project. Originating author: brian m. carlson. Thread type: design discussion (RFC).

Core problem or goal: Reduce contributor friction by automating code formatting, eliminating manual style nitpicks in reviews, and freeing time for substantive work. The discussion now explores two competing approaches: (1) adopting `clang-format` as an external tool (brian m. carlson's original proposal), and (2) building a pluggable, language-specific formatting system directly into Git (Randall S. Becker's counterproposal). The goal remains to automate formatting while addressing platform compatibility and inclusivity concerns.

Current status: Early-stage discussion; no patches or implementation plan yet. Junio C Hamano has signaled cautious openness to exploring the `clang-format` proposal, contingent on its ability to reformat the existing codebase without excessive disruption. Randall's counterproposal introduces a new architectural direction but has not yet been addressed by other participants. No decisions or agreements reached.

Key technical details: The original proposal centers on using `clang-format`, which is cross-platform but unavailable on some platforms (e.g., NonStop). Git already has a `.clang-format` file, but it does not fully match Git's current style. Randall's counterproposal suggests implementing a pluggable clean filter system within Git, written in a portable language (e.g., Perl) and invoked automatically on `git add` or `git commit`. This system would support multiple languages (C, Java, PHP, Perl, COBOL, TAL) and could delegate to platform-specific formatters (e.g., `clang-format`) where available. No new files, symbols, or on-disk changes are introduced at this stage.

Open questions and loose ends:
- Whether `clang-format` can be configured to produce output sufficiently close to Git's current style without requiring major compromises (original proposal).
- How to handle edge cases where `clang-format` output diverges from Git's style (e.g., minor suboptimal formatting).
- Who would drive the implementation (e.g., updating the `.clang-format` file, testing, and integration for the original proposal; designing and implementing the pluggable system for the counterproposal).
- Potential impact on existing patches and in-flight work (e.g., merge conflicts due to reformatting).
- Whether the trade-off (automation vs. style deviations) is acceptable to the community (original proposal).
- Whether the counterproposal's pluggable system can be implemented portably and efficiently, and how it would integrate with Git's workflow.
- How the counterproposal would handle language-specific formatting rules (e.g., C vs. Perl vs. COBOL).
- Next steps: refining the `.clang-format` configuration (original proposal), assessing the impact of the pluggable system (counterproposal), and determining workflow integration for either approach.

Participant positions:
- **brian m. carlson**: Advocates for adopting `clang-format`, emphasizing efficiency gains and reduced contributor friction. Positions the proposal as a pragmatic trade-off (minor style deviations for automation). Notes that even experienced contributors spend significant time on formatting.
- **Junio C Hamano**: Cautiously open to the `clang-format` proposal, provided it can reformat the existing codebase without excessive disruption. Focuses on practical alignment with Git's style rather than debating automation's merits.
- **Randall S. Becker**: Opposes the `clang-format` proposal due to platform compatibility concerns (NonStop lacks `clang-format`). Proposes an alternative: a pluggable, language-specific formatting system built into Git, written in a portable language (e.g., Perl) and invoked automatically on `git add` or `git commit`. Argues this approach is more inclusive and supports multiple languages beyond C.

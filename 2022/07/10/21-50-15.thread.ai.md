Thread identity: Discussion on adopting an automatic code formatter for the Git project. Originating author: brian m. carlson. Thread type: design discussion (RFC) with incremental patch series.

Core problem or goal: Reduce contributor friction by automating code formatting, eliminating manual style nitpicks in reviews, and freeing time for substantive work. The discussion explores two competing approaches: (1) adopting `clang-format` as an external tool (brian m. carlson's original proposal), and (2) building a pluggable, language-specific formatting system directly into Git (Randall S. Becker's counterproposal). The goal remains to automate formatting while addressing platform compatibility and inclusivity concerns, with NonStop platform constraints as a hard blocker for `clang-format`. The thread includes a concrete patch series aimed at reducing the delta between `clang-format` output and Git's current style, with tooling to measure and refine progress.

Current status: Early-stage discussion with an incremental patch series advancing the `clang-format` proposal. No implementation plan or enforcement mechanism has been agreed upon. Junio C Hamano has signaled cautious openness to exploring the `clang-format` proposal, contingent on its ability to reformat the existing codebase without excessive disruption. Randall's counterproposal—framed as a pluggable, language-agnostic infrastructure built into Git—remains unaddressed by other participants. Ævar Arnfjörð Bjarmason's RFC patch series introduces and refines Makefile targets (`style-all`, `style-all-diff-ok`, `style-all-diff-apply`) to test `.clang-format` formatting across the entire codebase, enabling iterative refinement of the configuration. The series has now reduced the formatting delta by ~60% (from ~32k to ~12,742 lines of diff) through successive rule tweaks: disabling column limits, relaxing bit-field colon spacing, preventing indentation of `goto` labels, disabling alignment of backslashes in multi-line macros, and enforcing no spacing around bit-field colons. The latest patch (fourth in the series) disables indentation of `goto` labels (`IndentGotoLabels: false`), trimming the diff by ~3 lines across 510 files. Phillip Wood's review raises concerns about `clang-format`'s inconsistent struct formatting, which may not align with Git's manual style and could cause excessive churn if adopted as-is. Ævar's follow-up rebuts this concern by demonstrating that the specific example Phillip raised (struct initialization in Han-Wen Nienhuys' refs backend work) has already been resolved via designated initializers, a change Ævar introduced in a prior patch (`32bff617c6a`). This shifts the framing of the struct-formatting issue from a fundamental incompatibility to a solvable problem, either by accepting `clang-format`'s consistent output or by using `/* clang-format off */` directives for alignment-sensitive code. The tooling allows the community to assess whether remaining deviations are acceptable or fundamental. The series also surfaces a version-compatibility constraint: `BitFieldColonSpacing: None` requires clang-format v12 or newer (released April 2021), raising questions about whether to dynamically detect versions or standardize on a "blessed" version for CI enforcement. Elijah Newren's reply reframes the `clang-format` proposal as a net win for the project, arguing that even contributors who cannot use the tool directly (e.g., due to platform constraints) are not harmed by its adoption, since the formatter merely automates existing style requirements rather than imposing new ones. This position reinforces the pragmatic trade-off of the original proposal: minor style deviations are acceptable if they reduce reviewer burden and contributor friction, and platform-specific workarounds (e.g., VMs, cross-platform development) are a reasonable expectation for contributors on less common platforms. No decisions or agreements reached; the discussion remains polarized between the two approaches, with measurable progress toward `clang-format` compatibility but no movement on the pluggable system counterproposal.

Key technical details: The original proposal centers on using `clang-format`, which is unavailable on NonStop and likely to remain so for at least five years. Git already has a `.clang-format` file, but it does not fully match Git's current style. Randall's counterproposal envisions a pluggable clean filter system within Git, written in a portable language (e.g., Perl) and invoked automatically on `git add` or `git commit`. This system would support multiple languages (C, Java, PHP, Perl, COBOL, TAL) and could delegate to platform-specific formatters (e.g., `clang-format`) where available. Ævar's patch series tweaks five `.clang-format` rules: disabling column limits (`ColumnLimit: 0`), relaxing bit-field colon spacing (`BitFieldColonSpacing: None`), preventing indentation of `goto` labels (`IndentGotoLabels: false`), disabling alignment of backslashes in multi-line macros (`AlignEscapedNewlines: DontAlign`), and enforcing no spacing around bit-field colons. It adds Makefile targets to test formatting across all tracked `.c` and `.h` files, generating formatted versions, comparing them to the current state, and optionally applying changes. The `style-all-diff-ok` target fails if any file would be reformatted, providing a mechanism for future CI enforcement. No new files, symbols, or on-disk changes are introduced. The series provides tooling to measure the impact of `.clang-format` rule changes, enabling further refinement of the configuration. The latest patch disables `IndentGotoLabels`, which aligns `clang-format` with Git's convention of flushing `goto` labels to the left margin. Phillip Wood's review highlighted a specific incompatibility: `clang-format`'s inconsistent struct formatting, which may place one field per line or pack multiple fields per line with irregular indentation, diverging from Git's manual style. Ævar's rebuttal demonstrates that the specific example Phillip raised has been resolved via designated initializers, and suggests `/* clang-format off */` directives as a fallback for alignment-sensitive code (e.g., `tar.h`). The version-compatibility constraint for `BitFieldColonSpacing: None` (clang-format v12+) underscores the trade-off between incremental progress and platform inclusivity.

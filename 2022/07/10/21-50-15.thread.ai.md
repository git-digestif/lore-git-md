Thread identity: Discussion on adopting an automatic code formatter for the Git project. Originating author: brian m. carlson. Thread type: design discussion (RFC) with incremental patch series.

Core problem or goal: Reduce contributor friction by automating code formatting, eliminating manual style nitpicks in reviews, and freeing time for substantive work. The discussion explores two competing approaches: (1) adopting `clang-format` as an external tool (brian m. carlson's original proposal), and (2) building a pluggable, language-specific formatting system directly into Git (Randall S. Becker's counterproposal). The goal remains to automate formatting while addressing platform compatibility, line-wrapping conventions, and inclusivity concerns, with NonStop platform constraints as a hard blocker for `clang-format`. The thread includes a concrete patch series aimed at reducing the delta between `clang-format` output and Git's current style, with tooling to measure and refine progress. Recent replies introduce nuanced perspectives: advocating for incremental experimentation (e.g., limited-scope formatting rules or alternative tools like GNU `indent` or `checkpatch`) to mitigate friction points such as delayed CI feedback, enforcement gates, and contentious edge cases (e.g., struct alignment, bit-field spacing, line-wrapping reflow), while others reaffirm the long-term benefits of `clang-format` despite the transition challenges. Junio's latest replies raise targeted concerns about `clang-format`'s ability to replicate Git's nuanced line-wrapping conventions, the trade-offs between rigid line-length limits (80 or 132 characters) and human judgment in line breaks, the empirical prevalence of bit-field spacing styles in the existing codebase, and the tool's reflow behavior, which actively rewraps code to fill the available width even if the original code was manually wrapped to a narrower limit. These concerns highlight a fundamental tension: while `clang-format` can enforce consistency, it may not respect the flexibility that Git's contributors rely on when wrapping lines for readability.

Key technical details: The original proposal centers on using `clang-format`, which is unavailable on NonStop and likely to remain so for at least five years. Git already has a `.clang-format` file, but it does not fully match Git's current style. Randall's counterproposal envisions a pluggable clean filter system within Git, written in a portable language (e.g., Perl) and invoked automatically on `git add` or `git commit`. It adds Makefile targets to test formatting across all tracked `.c` and `.h` files, generating formatted versions, comparing them to the current state, and optionally applying changes. The `style-all-diff-ok` target fails if any file would be reformatted, providing a mechanism for future CI enforcement. No new files, symbols, or on-disk changes are introduced. The series provides tooling to measure the impact of `.clang-format` rule changes, enabling further refinement of the configuration.

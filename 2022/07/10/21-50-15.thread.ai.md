Thread identity: Discussion on adopting an automatic code formatter for the Git project. Originating author: brian m. carlson. Thread type: design discussion (RFC) with incremental patch series.

Core problem or goal: Reduce contributor friction by automating code formatting, eliminating manual style nitpicks in reviews, and freeing time for substantive work. The discussion explores two competing approaches: (1) adopting `clang-format` as an external tool (brian m. carlson's original proposal), and (2) building a pluggable, language-specific formatting system directly into Git (Randall S. Becker's counterproposal). The goal remains to automate formatting while addressing platform compatibility and inclusivity concerns, with NonStop platform constraints as a hard blocker for `clang-format`. The thread now includes a concrete patch series aimed at reducing the delta between `clang-format` output and Git's current style, with new tooling to measure and refine progress.

Current status: Early-stage discussion with an incremental patch series advancing the `clang-format` proposal. No implementation plan or enforcement mechanism has been agreed upon. Junio C Hamano has signaled cautious openness to exploring the `clang-format` proposal, contingent on its ability to reformat the existing codebase without excessive disruption. Randall's counterproposal—framed as a pluggable, language-agnostic infrastructure built into Git—remains unaddressed by other participants. Ævar Arnfjörð Bjarmason's RFC patch series introduces and refines Makefile targets (`style-all`, `style-all-diff-ok`, `style-all-diff-apply`) to test `.clang-format` formatting across the entire codebase, enabling iterative refinement of the configuration. The series has now reduced the formatting delta by ~60% (from ~32k to ~12,993 lines of diff) through successive rule tweaks: disabling column limits, relaxing bit-field colon spacing, preventing indentation of `goto` labels, disabling alignment of backslashes in multi-line macros, and now enforcing no spacing around bit-field colons. The tooling allows the community to assess whether remaining deviations are acceptable or fundamental. The latest patch also surfaces a version-compatibility constraint: `BitFieldColonSpacing: None` requires clang-format v12 or newer (released April 2021), raising questions about whether to dynamically detect versions or standardize on a "blessed" version for CI enforcement. No decisions or agreements reached; the discussion remains polarized between the two approaches, with measurable progress toward `clang-format` compatibility but no movement on the pluggable system counterproposal.

Key technical details: The original proposal centers on using `clang-format`, which is unavailable on NonStop and likely to remain so for at least five years. Git already has a `.clang-format` file, but it does not fully match Git's current style. Randall's counterproposal envisions a pluggable clean filter system within Git, written in a portable language (e.g., Perl) and invoked automatically on `git add` or `git commit`. This system would support multiple languages (C, Java, PHP, Perl, COBOL, TAL) and could delegate to platform-specific formatters (e.g., `clang-format`) where available. Ævar's patch series tweaks five `.clang-format` rules: disabling column limits (`ColumnLimit: 0`), relaxing bit-field colon spacing (`BitFieldColonSpacing: None`), preventing indentation of `goto` labels (`IndentGotoLabels: false`), disabling alignment of backslashes in multi-line macros (`AlignEscapedNewlines: DontAlign`), and now enforcing no spacing around bit-field colons. It adds Makefile targets to test formatting across all tracked `.c` and `.h` files, generating formatted versions, comparing them to the current state, and optionally applying changes. The `style-all-diff-ok` target fails if any file would be reformatted, providing a mechanism for future CI enforcement. No new files, symbols, or on-disk changes are introduced. The series provides tooling to measure the impact of `.clang-format` rule changes, enabling further refinement of the configuration. The latest patch introduces a version-compatibility constraint (clang-format v12+) for the bit-field colon spacing rule, underscoring the trade-off between incremental progress and platform inclusivity.

Open questions and loose ends:

- How to handle "landmine checks"—CI or pre-commit hooks that fail patches due to pre-existing formatting violations—and whether enforcement should proceed in parallel with a cleanup plan.
- Who would drive the implementation (e.g., updating the `.clang-format` file, testing, and integration for the original proposal; designing and implementing the pluggable system for the counterproposal).
- Potential impact on existing patches and in-flight work (e.g., merge conflicts due to reformatting).
- Whether the trade-off (automation vs. style deviations) is acceptable to the community (original proposal).
- Whether the counterproposal's pluggable system can be implemented portably and efficiently, and how it would integrate with Git's workflow.
- How the pluggable system would handle language-specific formatting rules (e.g., C vs. Perl vs. COBOL) and whether it could realistically be adopted by other projects (as Randall suggests) or would remain Git-specific.
- Next steps: refining the `.clang-format` configuration (original proposal), assessing the feasibility of the pluggable system (counterproposal), and determining workflow integration for either approach—now with the added constraint that NonStop's lack of `clang-format` support is a permanent blocker.
- Whether the tooling introduced by Ævar's patch series will be sufficient to resolve the remaining formatting delta or if fundamental incompatibilities between `clang-format` and Git's style will persist.
- How to address version-compatibility constraints introduced by `.clang-format` rule tweaks (e.g., `BitFieldColonSpacing: None` requiring clang-format v12+), including whether to dynamically detect versions or standardize on a "blessed" version for CI enforcement.

The Git project is discussing whether to adopt an automatic code formatter to reduce contributor friction and eliminate manual style nitpicks in reviews. The conversation has centered on two competing approaches: using `clang-format` (proposed by brian m. carlson) and building a pluggable, language-agnostic formatting system directly into Git (suggested by Randall S. Becker). The discussion remains in the design phase, with no implementation plan or enforcement mechanism agreed upon yet.

Progress has been made on the `clang-format` front through Ævar Arnfjörð Bjarmason’s patch series, which has reduced the formatting delta between `clang-format` output and Git’s current style by about 60%. The latest patch disables indentation of `goto` labels to better match Git’s conventions. However, key challenges remain, including struct formatting inconsistencies, line-wrapping conventions, and platform compatibility—particularly for NonStop, which lacks `clang-format` support. Junio C Hamano has expressed cautious openness to the `clang-format` proposal but raised concerns about its ability to replicate Git’s nuanced line-wrapping rules. brian m. carlson’s latest reply reaffirms the importance of enforcing an 80-character line limit, suggesting either sticking with the traditional limit or adopting a longer one (e.g., 132 characters) to reduce churn. This adds a new constraint: if line-length enforcement is part of the automated formatter, the project must pick a specific limit.

The discussion remains polarized, with participants divided over the trade-offs between automation, style consistency, and platform inclusivity. Randall’s counterproposal for a pluggable system has not gained traction, while Ævar’s incremental approach and Elijah Newren’s advocacy for `clang-format` continue to shape the debate. Open questions include how to handle remaining formatting inconsistencies, whether to reintroduce a line-length rule, and how to address platform-specific constraints. The next steps will likely involve further refinement of the `.clang-format` configuration or exploration of alternative tools, but no clear path forward has emerged yet.

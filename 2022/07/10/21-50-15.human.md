This is a proposal to adopt an automatic code formatter for the Git project.

Brian m. carlson reopens the long-standing discussion about introducing an automatic code formatter, arguing that it would reduce friction for contributors by eliminating manual code style nitpicking. He notes that many contributors—including experienced ones—spend significant time addressing formatting feedback, which delays patch series and can discourage newcomers. An automated tool would allow contributors to format code with minimal effort, potentially even verifying compliance in CI.

The proposal suggests using `clang-format`, which is widely available and highly configurable, though Brian is open to alternatives as long as they are packaged in Debian. Git already has a `.clang-format` file, but it does not perfectly match the project’s current style. The key idea is to redefine Git’s style in terms of the formatter’s output rather than trying to make the formatter match the existing style.

Brian frames this as a productivity issue, citing his own experience rebasing the SHA-1/SHA-256 interop work, where formatting cleanup competes with more meaningful development tasks. He acknowledges that the resulting style might not be perfect but argues that the efficiency gains outweigh minor stylistic trade-offs.

This is not a patch or technical change—it’s a call for discussion. The proposal is likely to be contentious, as past debates on this topic have shown. Some contributors may see it as a worthwhile trade-off for reduced maintenance burden, while others may resist changing long-standing conventions or worry about unintended consequences (e.g., churn in existing code). The thread is worth following for anyone interested in Git’s development process or contributor experience.

This is a reply in the ongoing discussion about adopting `clang-format` for Git’s codebase, specifically addressing Junio’s concern about line-wrapping behavior. Eric Sunshine chimes in to clarify how `clang-format` handles line length in practice.

Eric points out that `clang-format` doesn’t just enforce a maximum line length—it actively *reflows* code to fill the available space up to the configured limit. For example, if a developer manually wraps code to fit neatly in 80 columns but `clang-format` is set to 132 columns, the tool will automatically expand those lines to 132 columns, potentially creating "unreadable mess" (as Junio warned). This behavior would undermine Git’s flexible, context-aware line-wrapping conventions, where developers are encouraged to break lines at logical points even if it slightly exceeds 80 columns. Eric’s observation suggests that `clang-format`’s rigid reflowing could conflict with Git’s style, regardless of whether the limit is set to 80 or 132 characters.

Eric then asks whether there’s a configuration option to disable this "reflow-to-occupy-full-width" behavior, tagging brian m. carlson for input. This question is critical: if such a knob exists, it might address Junio’s concern about preserving human judgment in line breaks. If not, the project may need to accept `clang-format`’s rigid line-breaking or abandon line-length enforcement altogether in the automated formatter. The reply doesn’t propose a solution but highlights a concrete technical hurdle that wasn’t previously addressed in the thread. It also underscores the tension between automation and the nuanced, subjective aspects of code readability.

This is a brief but substantive review comment from Junio C Hamano on Ævar Arnfjörð Bjarmason’s RFC patch series about adopting `clang-format` for Git. Junio questions whether any automated formatter—including `clang-format`—can handle the nuanced, context-dependent line-wrapping decisions that Git’s style guidelines allow. Git’s documented 80-column limit is not a hard rule; it permits exceptions when breaking earlier would harm readability or when the next natural break falls slightly beyond 80 columns. Junio wonders if `clang-format` (or any tool) can encode this kind of judgment, or if automated formatting will inevitably produce rigid, suboptimal line breaks that clash with human preferences.

The comment does not oppose the patch series or the broader `clang-format` proposal, but it introduces a new technical hurdle: whether the tool can be configured to respect Git’s flexible line-wrapping conventions. This is a deeper challenge than the mechanical rule tweaks in Ævar’s patches, as it touches on the fundamental limitations of automated formatting. If `clang-format` cannot handle these shades of gray, the project may need to accept either manual overrides (e.g., `/* clang-format off */`) or a permanent gap between automated output and Git’s ideal style. The comment leaves the question open, inviting further discussion or experimentation.

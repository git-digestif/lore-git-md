This is a substantive review comment in the ongoing discussion about adopting an automatic code formatter for Git. Phillip Wood responds to brian m. carlson’s proposal to use `clang-format` by highlighting a concrete, unresolved issue: `clang-format`’s inconsistent and disruptive struct formatting.

Phillip agrees with the goal of automating style enforcement—calling it “lovely not to have to think about style rules”—but demonstrates that `clang-format` currently produces output that diverges significantly from Git’s existing conventions. The example he provides shows two structs reformatted in wildly different ways: one with each field on its own line (closer to Git’s current style), and another crammed onto a few lines with arbitrary indentation. This inconsistency, he argues, would introduce unnecessary churn and make the code harder to read, especially when adding new fields.

The review is grounded in a real-world example from a past patch (Han-Wen Nienhuys’s ref backend work), and Phillip notes that he tried (and failed) to tweak `.clang-format` rules to fix the issue. His concern isn’t just theoretical; it’s a practical obstacle to adopting `clang-format` as-is. The message doesn’t reject automation outright but underscores that the tool’s current behavior is not yet fit for purpose.

This comment adds weight to the thread’s open question: whether further rule tweaks can close the gap between `clang-format` output and Git’s style, or whether fundamental incompatibilities will persist. It’s a measured, evidence-based contribution that advances the discussion beyond abstract trade-offs.

This thread concerns a bug in the new `git history fixup` command where running it in one worktree leaves spurious staged changes in other worktrees that share the same repository. Toon Claes reported the issue with a clear reproduction case, and Phillip Wood diagnosed the root cause: the command rewrites branches checked out in other worktrees without updating their index or working copy. After weighing alternatives, the group settled on a conservative fix that mirrors `git rebase --update-refs`: `git history fixup` will refuse to rewrite any branch that is checked out in another worktree. Patrick Steinhardt, the original author of `git history`, endorsed this safer approach and opened GitLab issue #772 to track the work.

The design is now finalized, but no patch has been posted yet. Aniket Gupta has recently volunteered to implement the fix, committing to add the safety check in `builtin/history.c` and the associated worktree detection logic, along with regression tests in both the history and worktree test suites. Until that patch arrives, the exact implementation details and any edge cases around concurrent rebases remain open.

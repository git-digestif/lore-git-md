Thread identity: Subject `git history fixup` corrupts index in other worktrees; not a patch series (bug report); originating author Toon Claes; thread type bug report.

Core problem or goal: The `git history fixup` command (introduced in Git 2.46, 2026) does not isolate index modifications to the current worktree. When run in one worktree it leaves spurious staged changes in other worktrees sharing the repository, corrupting their index state without user action there. Root cause: `git history fixup` rewrites commits pointed to by branches checked out in other worktrees without updating their index or working copy.

Current status: Design decision settled: `git history fixup` will refuse to rewrite branches checked out in other worktrees, mirroring `git rebase --update-refs` behavior. Aniket Gupta has volunteered to implement this fix (responding to GitLab issue #772 opened by Patrick Steinhardt) but no patch has been posted yet. Implementation remains pending. Issue tracked in GitLab issue #772 for the next release cycle.

Key technical details: Command `git history fixup`; subsystems worktree handling, index management, commit rewriting; files likely involved `builtin/history.c`, `worktree.c`, `read-cache.c`. Behavior: staged changes leak across worktrees after fixup; commit history remains correct. Safety mechanism: will adopt `git rebase`'s protection against rewriting branches checked out in other worktrees, plus detection of in-progress rebases when the update would change the branch tree. On-disk format: no changes. Test coverage: none yet; regression tests planned for both `git history` and worktree test suites.

Open questions and loose ends: Exact mechanism for detecting an in-progress rebase on a branch; whether to reuse `git rebase` safety-check logic verbatim or adapt it for `git history` context; test scenarios for concurrent rewrite scenarios beyond basic regression; backward compatibility impact on user workflows.

Participant positions: Toon Claes reported the bug with reproduction case and initially leaned toward best-effort updates but aligned with the settled conservative approach. Phillip Wood provided root cause analysis and proposed the solution path drawing on `git rebase --update-refs` behavior, identifying the missing safety mechanism for concurrent rewrites. Patrick Steinhardt, author of the original `git history` command, endorsed the safer refuse-to-rewrite approach and opened GitLab issue #772. Aniket Gupta volunteered to send a patch implementing the settled design, referring to the original report as "Nikita's report", and specified the check should also cover branches currently being rebased.

Subject: [PATCH 0/4] last-modified: reuse Bloom filters for speed

Thread type: patch series (performance optimization)

Core problem or goal
Make the experimental `git last-modified` command as fast as `git log` when querying the last commit that modified files matching a pathspec (including wildcards like `*.c`), by reusing Git’s Bloom filter machinery more effectively. The v4 series achieves a 3.7× speedup without `--show-trees` (60.7 ms → 16.2 ms) and a 1.95× speedup with `--show-trees` (61.9 ms → 31.8 ms) on the ziglang/zig repository, bringing performance nearly to parity with `git log`. The series now fully supports wildcard pathspecs (e.g., `*.c`) without performance regressions, includes trace2 instrumentation to verify the Bloom filter fast-path is correctly triggered, and resolves the test environment interaction that blocked v3.

Current status
Under review; v4 posted and complete. The series is ready for integration pending resolution of Patrick Steinhardt’s review comments across multiple patches: (1) a correctness issue in `bloom_filter_contains_any_vec()` (patch 3/4) where the helper can return `-1` (from `bloom_filter_contains()`) when the Bloom filter is empty, but its usage context assumes only `0` or `1`, (2) a naming and documentation clarity issue in `revs_maybe_changed_in_bloom_with_leading_dirs()` (patch 4/4; renamed from `revs_maybe_changed_in_bloom_with_parents()`), where "parents" could be misinterpreted as referring to commit parents rather than parent directories, and (3) two points in patch 5/4 regarding the pre-filter’s rationale and performance trade-offs—specifically, whether the pre-filter might sometimes do redundant work (since the same Bloom filter checks could be repeated later for individual paths) and the need for a benchmark demonstrating the pre-filter’s benefit. The fixes for the first two issues are to normalize the return value of `bloom_filter_contains_any_vec()` to `0`/`1` (boolean) and rename `revs_maybe_changed_in_bloom_with_parents()` to `revs_maybe_changed_in_bloom_with_leading_dirs()` to align with its documented behavior. Key technical details
- Files touched: `revision.c`, `revision.h`, `bloom.c`, `bloom.h`, `builtin/last-modified.c`, test suite (`t/t8020-last-modified.sh`)
- New symbols: `revs_maybe_changed_in_bloom` (public, boolean return), `revs_maybe_changed_in_bloom_with_leading_dirs` (public, boolean return; renamed from `revs_maybe_changed_in_bloom_with_parents`), `bloom_filter_contains_path` (private helper in `bloom.c`), `bloom_filter_contains_any_vec` (private helper in `bloom.c`)
- Behavior change: `git last-modified` reuses Bloom filters instead of re-fetching them, reducing runtime by up to 3.7×. The optimization now covers all pathspec types, including wildcards (e.g., `*.c`), with per-path Bloom-filter lookups. The `--show-trees` correctness bug is fixed by filtering out ancestor tree entries not covered by the original pathspec in `add_path_from_diff()` using `match_pathspec()`, preserving performance while avoiding misleading results. The fix handles the minor edge case of directory queries (e.g., `Documentation/technical/`) by retaining the queried directory while removing its parent (`Documentation/`), which is considered non-critical given the command's experimental status. The new `revs_maybe_changed_in_bloom_with_leading_dirs()` function enables `--show-trees` to report changes to parent directories by checking all keys in the path’s key vector (e.g., for `a/b/c/`, it checks `a/`, `a/b/`, and `a/b/c/`). Patch 3/4 adds `bloom_filter_contains_any_vec()` to answer whether *any* key in a vector is present in the Bloom filter (proving the path *or any of its parent directories* might have changed), which is exactly what `--show-trees` needs to avoid false negatives for directory queries. The helper is a 12-line loop over the key vector that returns `1` as soon as any key is found in the filter, and `0` only if none are present. **Patrick Steinhardt identified a correctness issue in `bloom_filter_contains_any_vec()`: it can return `-1` (from `bloom_filter_contains()`) when the Bloom filter is empty, but its usage context assumes only `0` or `1`. This mismatch could cause subtle bugs in `revs_maybe_changed_in_bloom_with_leading_dirs()` (patch 4/4), which relies on the helper to determine whether a path or its parent directories *might* have changed.** The fix is to normalize the return value to `0`/`1` (boolean), avoiding exposure of Bloom filter internals to callers. Patch 4/4 introduces `revs_maybe_changed_in_bloom_with_leading_dirs()`, a 15-line helper that loops over the key vectors and calls `bloom_filter_contains_any_vec()` to determine if any key in the vector is present, returning `true` if the Bloom filter indicates a possible change to the path or any of its parent directories. Patch 5/4 adds a 12-line pre-filter in `maybe_changed_path()` that calls the appropriate Bloom filter helper before starting the per-path diff machinery, discarding commits that definitely did not touch any relevant path early. The pre-filter uses `revs_maybe_changed_in_bloom()` for the default case and `revs_maybe_changed_in_bloom_with_leading_dirs()` for `--show-trees`, ensuring correctness for directory queries. The pre-filter’s design favors fewer pathspecs over expanded paths, but this trade-off should be explicitly documented in the commit message along with a benchmark demonstrating its benefit. **Patch 6/4 in v4 restores `bloom_filter_settings` after `prepare_revision_walk()` clears it, but Patrick Steinhardt’s latest review proposes an alternative: store the settings in `struct last_modified` instead of the revision machinery, removing the post-walk restoration and isolating the Bloom filter state. The change is 12 lines and does not alter behavior, but the author must confirm whether the revision machinery *requires* the settings for other callbacks.** The v4 reroll incorporates Junio’s fix for the test environment interaction in `t8020-last-modified.sh`: the test now explicitly controls `GIT_TEST_COMMIT_GRAPH` for both the commit-graph-disabled baseline (`GIT_TEST_COMMIT_GRAPH=0`) and the commit-graph-enabled case (`GIT_TEST_COMMIT_GRAPH=1`). Patch 1/4 in v4 refactors `revision.c` to move the `revs->bloom_keyvecs_nr` check into `check_maybe_different_in_bloom_filter`, making `bloom_ret` return `-1` when no Bloom key vectors are present, which prevents `count_bloom_filter_false_positive` from being incremented in that case. Patch 2/4 exposes `revs_maybe_changed_in_bloom()` as a public helper, preserving the original function’s tristate return for statistics while providing a boolean API for filtering.

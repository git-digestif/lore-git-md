Thread identity
Subject: [PATCH 0/3] teach `git history` to sign rewritten commits
Series version: v5 (v1–v4 previously, plus follow-up completion fix)
Originating author: Souma
Thread type: patch series

Core problem or goal
Teach `git history` to sign rewritten commits (`drop`, `fixup`, `reword`, `split`, `squash`) using the same configuration (`commit.gpgsign`) and command-line options (`-S/--gpg-sign`, `--no-gpg-sign`) already supported by `git commit`, `git rebase`, and `git cherry-pick`.

Current status
Series is at v5; **cooking in `seen`**. All substantive review feedback from Patrick Steinhardt (v1–v3) and Junio C Hamano’s DCO query have been addressed. The replay API plumbing (patch 1/3) is unchanged from v3 and now explicitly split into a preparatory follow-up patch. The main feature patch (originally 2/3, now effectively 3/5 after follow-ups) covers all five subcommands with documentation, synopsis, and test coverage. Junio merged the series to `seen` for integration testing, where two issues surfaced: (1) a mechanical regression in `t9902-completion.sh` (completion script did not handle the new `--gpg-sign`/`--no-gpg-sign` options for `git history`), and (2) a clarification question about the literal use of `...` in the test script. Souma’s follow-up confirmed that `...` is a literal placeholder for dynamically generated `--no-*` options (e.g., `--no-gpg-sign`) appearing after the `--` separator in the completion helper output, matching `git rebase` and `git commit` behavior. The follow-up patches (1/2 and 2/2) addressed the `t9902-completion.sh` regression by adding `--gpg-sign` and `--no-...` to the expected completion output for `git history split`. The series is now unblocked and ready to graduate to `next`.

Key technical details
- Files touched: `builtin/history.c`, `replay.c`, `replay.h`, `Documentation/git-history.adoc`, `t/t3451-history-reword.sh`, `t/t3452-history-split.sh`, `t/t3453-history-fixup.sh`, `t/t3454-history-drop.sh`, `t/t3455-history-squash.sh`, `t/t9902-completion.sh`
- New behavior: all five subcommands respect `commit.gpgsign`, `-S[=<key-id>]`, `--gpg-sign[=<key-id>]`, and `--no-gpg-sign`; command-line options override configuration, and the last option wins
- New symbols: `sign_commit` field in `replay_revisions_options` struct, plumbing through `pick_regular_commit`, `create_commit`, `commit_tree_ext`, `commit_tree_with_edited_message`, `split_commit`; custom `history_config` callback to read `commit.gpgsign`; `OPT_HISTORY_GPG_SIGN` macro for command-line parsing
- On-disk format: unchanged; only the commit object’s signature trailer is added when signing is enabled
- Test coverage: GPG-gated tests in `t3451`–`t3455` verify config-driven signing, command-line overrides, explicit key selection, and the no-new-commit case for `drop`; all flag/config combinations are covered. The follow-up patch adds completion test coverage for `--gpg-sign` and `--no-...` in `t9902-completion.sh`, where `...` is a literal placeholder for the dynamically generated `--no-gpg-sign` option.
- Completion protocol: `--git-completion-helper` for `git history split` lists all static options before `--` and generated negated options after it, matching `git rebase` and `git commit` behavior

Open questions and loose ends
- **Conceptual trade-off**: whether signing rewritten commits that were originally authored by someone else is desirable or misleading; documented in the commit message but unresolved.

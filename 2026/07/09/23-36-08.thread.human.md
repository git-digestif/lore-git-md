This thread is about a patch series proposing a unified `post-worktree` hook to notify external tools (like IDEs or AI agents) when worktrees are created, removed, or moved—even when those actions are triggered by uncontrolled callers (e.g., an IDE or a user running `git worktree remove` directly). Domen Kožar, the author, argues that hooks are necessary for observability in cases where wrappers can’t be used, while Kristoffer Haugsbakk has proposed an alternative `--id=<string>` option to enforce ownership of worktrees. The two approaches are now seen as potentially complementary, though no concrete integration has been proposed yet.

The discussion is still in the design phase, with no merge status change. Domen’s latest version (v2) remains in Junio C Hamano’s `seen` branch, pending resolution of Junio’s fundamental objection to hooks. Maciej Ciemborowicz’s recent report adds real-world weight to Domen’s argument: IDEs like VS Code create worktrees directly, bypassing wrappers, leaving tools like his unable to reliably detect creation or removal events. This use case—provisioning isolated container environments for AI agents—highlights the need for observability when the caller is uncontrolled, regardless of ownership.

Key unresolved questions include whether Junio will accept the observability argument, how hooks and IDs might coexist, and whether the unified hook’s interface (subcommand-style: `post-worktree add`, `post-worktree remove`, etc.) is the right approach. Domen has clarified that hooks and IDs serve different purposes (observability vs. ownership), but feedback from Junio and others on this framing is still pending. Phillip Wood’s earlier concerns about hook execution order and unconditional execution remain unaddressed, and Kristoffer’s counterproposal hasn’t yet been evaluated in light of Domen’s complementary framing. The thread is evolving into a broader discussion about how to balance observability and ownership in Git’s worktree lifecycle.

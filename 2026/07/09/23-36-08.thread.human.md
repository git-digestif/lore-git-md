This thread is about a proposed unified `post-worktree` hook to notify external tools (like IDEs or development environments) when worktrees are added, removed, or moved—even if the action wasn’t triggered by the tool itself. Domen Kožar initially proposed a single hook with subcommands (`add`, `remove`, `move`) as a compromise after earlier feedback, but Kristoffer Haugsbakk countered with an alternative: an `--id=<string>` option for `git worktree add` to enforce ownership, eliminating the need for hooks entirely.

Domen has now clarified that the two proposals address different problems. Ownership IDs (Kristoffer’s approach) help tools avoid stepping on each other’s worktrees, but they don’t solve the core issue of *observability*—letting tools like devenv react to worktree changes they didn’t initiate, such as a user running `git worktree prune` or manually deleting a worktree. Domen argues that hooks remain the only reliable way to handle these uncontrolled events, as Git itself knows exactly what’s happening (including damaged or partially deleted worktrees). He suggests the two ideas could coexist, though no concrete integration has been proposed yet.

The thread is still in active design discussion, with no clear resolution. Junio C Hamano, the maintainer, hasn’t weighed in on Domen’s latest framing or the counterproposal. Phillip Wood’s earlier feedback (about hook execution order and documentation) remains unaddressed, and no other participants have engaged with the latest arguments. The series is still in the `seen` branch (proposed updates), with no indication of when—or if—it might move forward. For now, the debate hinges on whether Git should provide native observability for worktree lifecycle events, or if tools should handle it themselves.

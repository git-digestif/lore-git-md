# Thread deltas

## 2026/08/30

- [2026/08/30/17-21-41 by Domen Kožar <domen@cachix.org>] Domen Kožar argued that a wrapper is insufficient for worktree lifecycle notification because the component needing the notification (e.g., devenv) does not control the callers invoking Git (IDEs, coding agents, other worktree tools, scripts, or the user directly), making wrapper-based notification optional in practice.
- [2026/08/30/17-21-41 by Domen Kožar <domen@cachix.org>] He explained that "git worktree prune" cannot be reliably reproduced in a wrapper: one invocation may remove zero or many administrative entries, only Git knows exactly which entries it actually removes, and comparing "git worktree list" before and after is not an authoritative event stream, can race another worktree operation, and has limited information when an entry is already damaged.
- [2026/08/30/17-21-41 by Domen Kožar <domen@cachix.org>] He cited earlier thread examples—Alexander's point that Xcode and related tools keep substantial path-keyed state outside the worktree so agents invoking "git worktree remove" or "git worktree prune" directly leave many gigabytes of state behind even though a cleanup wrapper exists, and Phillip's unpublished add-hook patch for copying per-worktree files such as config.mak.
- [2026/08/30/17-21-41 by Domen Kožar <domen@cachix.org>] To address the concern about hook proliferation, he proposed consolidating the three separate hooks into a single "post-worktree" hook with a fixed interface: "post-worktree add <id> "" <new-path>", "post-worktree move <id> <old-path> <new-path>", and "post-worktree remove <id> <old-path> """, using absolute paths, issuing one "remove" event for each entry actually pruned (and none under --dry-run), and reporting only operations that have taken effect and cannot be undone.
- [2026/08/30/17-21-41 by Domen Kožar <domen@cachix.org>] He stated that this narrower interface would pass information Git already has (addressing Caleb's earlier comment) and avoid using argument count to distinguish events, and asked whether this, together with the need to observe operations from callers that cannot be required to use a wrapper, meets the bar for a native hook or if he should seek guidance before spending time on a reroll.

## 2026/09/07

- [2026/09/07/14-30-13 by Domen Kožar <domen@cachix.org>] Domen Kožar pinged the list on the single "post-worktree" hook proposal, arguing that as coding agents increasingly create and discard worktrees, reliable lifecycle notifications matter more because tools managing environments and cleanup cannot control every caller invoking Git; he asked whether the interface would address the concerns and offered to prepare v3 if the direction could be agreed.
- [2026/09/07/18-18-47 by Kristoffer Haugsbakk <kristofferhaugsbakk@fastmail.com>] Kristoffer Haugsbakk proposed an alternative to hooks: a `--id=<string>` option on `git worktree add` stored in the worktree to communicate ownership, with git-worktree commands lacking that ID doing nothing to owned worktrees, so hooks would not be needed for adding, removing, or pruning; he suggested agent tools could use their own ID to manage a pool of worktrees and that extra metadata like an expiry timestamp could be left to tools rather than git-worktree itself.
- [2026/09/07/19-34-43 by Domen Kožar <domen@cachix.org>] Domen Kožar replied that an ownership ID could help tools avoid interfering with each other's worktrees, but his case involves two separate participants — an IDE or agent creating/removing worktrees while devenv provisions and cleans up each environment — and since devenv neither owns the worktrees nor controls the commands, it needs to observe the lifecycle regardless of which tool invokes Git, asking how devenv would learn of an add or remove even with an ownership ID; he also noted that for pruning, Git knows which administrative entries it actually removes (including entries whose directories are already gone) and a hook could report each removal, and asked whether ownership IDs and lifecycle notifications could serve complementary purposes.

This thread is about a Google Summer of Code contributor’s eighth patch series (`[PATCH v7]`) adding eight new path-related keys to `git repo info`, exposing filesystem locations like the hooks directory, index file, superproject root, and relative paths between the current directory and the top-level working tree. The series is now mechanically complete and correctness-fixed after seven revisions, but it faces a critical risk of being dropped from Junio C Hamano’s integration branch unless reviewers engage within the next few weeks.

The core goal is to make internal Git paths scriptable without requiring direct access to Git’s internals. The new keys—such as `path.toplevel`, `path.superproject-root`, `path.hooks`, and `path.cdup`—mirror existing struct fields and support suffix-based formatting (e.g., absolute vs. relative paths). The series also introduces `path.cdup`, the inverse of `path.git-prefix`, to address a prior design objection from Junio and achieve symmetry with `git rev-parse --show-cdup`. All high-weight issues from earlier versions have been resolved, including a correctness bug in `get_superproject_working_tree()` and edge-case discrepancies in `path.cdup`.

However, a new test correctness issue has surfaced in patch 2/8: a test in `t/t7400-submodule-basic.sh` exercises `path.superproject-root.absolute`, a key introduced in patch 3/8, breaking bisectability. The fix is straightforward—move the test to patch 3/8 or rewrite it to use `git rev-parse --show-superproject-working-tree`—but it must be addressed before the series can progress. Justin Tobler, who committed to reviewing the series, identified this issue but has not yet provided further substantive feedback. Junio has reiterated that the series will be abandoned unless reviewers step up, and no other contributors have engaged beyond surface-level comments.

The series touches `builtin/repo.c`, `submodule.c`, `builtin/rev-parse.c`, and test files, introducing 24 new keys with consistent behavior: returning empty strings for inapplicable contexts (e.g., bare repositories) and paths unconditionally for `path.index`, `path.grafts`, and `path.hooks`, even when the file doesn’t exist. The implementation aligns with `git rev-parse --git-path` precedent, though this design choice may still draw scrutiny. A deferred refactoring series is planned to deduplicate shared logic between `git repo info` and `git rev-parse`, but this work is contingent on the current series being merged. For now, the focus is on resolving the test correctness issue and securing substantive review to avoid abandonment.

Thread identity: RFC patch series proposing a breaking change for Git 3.0: restricting hex object IDs to lowercase only. Originating author: brian m. carlson. Thread type: design discussion / RFC, now at v2.

Core problem or goal: Git currently emits lowercase hex object IDs but accepts both uppercase and lowercase in parsing, creating potential compatibility and security issues for external tools that assume hex uniqueness. The series enforces lowercase-only parsing in Git 3.0 to make behavior consistent and predictable, addressing real-world security vulnerabilities where external tools failed to properly sanitize or filter object IDs due to case insensitivity. The first four patches introduce infrastructure (new `hex_kind` enum, `hexval_lc_table`, updated `hexval()`, `hex2chr()`, and `hex_to_bytes()` functions) and refactor existing hex-parsing code to use these helpers without altering runtime behavior. The fifth patch replaces an open-coded hex-parsing loop in `object-name.c` with the new `hexval()` helper, preserving the existing behavior (forcing hex digits to lowercase) while paving the way for the final patch’s enforcement. The sixth patch adjusts `t5324-split-commit-graph.sh` to avoid false positives in SHA-256 mode by changing the corruption character from "A" to "b" at position 70 (ensuring failure is due to corruption, not uppercase rejection) and from "A" to "a" at position 30 (for consistency with lowercase-only requirement). The seventh patch activates enforcement by defining `HEX_KIND_OID` as `HEX_KIND_LOWER` when `WITH_BREAKING_CHANGES` is enabled, documents the change in `Documentation/BreakingChanges.adoc`, and adds test coverage in `t1503-rev-parse-verify.sh` to verify rejection of uppercase object IDs.

Current status: v2 of the RFC series is complete and addresses all feedback from the initial RFC. The series remains in RFC limbo, with no final decision on whether the project will accept the breaking change. Junio C Hamano’s tentative "Will queue" from the RFC stage still holds, but the discussion around Phillip Wood’s adjacent proposal—whether Git should also forbid ref names that *look like* object IDs—could broaden the scope if others engage. The breaking change is gated behind `WITH_BREAKING_CHANGES` and targets Git 3.0. The preparatory patches (1-4) do not change behavior; the fifth patch introduces no behavioral change (it preserves the existing lowercase-forcing behavior while replacing the open-coded loop with `hexval()`); the sixth patch adjusts tests; and the seventh patch introduces the breaking change. The fourth patch specifically updates `diagnose.c`, `hex.c`, `http-push.c`, `notes.c`, and `object-file.c` to use `HEX_KIND_OID` instead of `HEX_KIND_MIXED` for object ID parsing, addressing Junio’s review feedback. The fifth patch replaces the open-coded hex-parsing loop in `object-name.c` with `hexval(c, HEX_KIND_OID)`, preserving the existing lowercase-forcing behavior while adopting the defensive pattern (`val & ~0xff`) to safely check for invalid hex digits. The sixth patch updates `t/t5324-split-commit-graph.sh` to replace corruption characters "A" with "b" at position 70 and "A" with "a" at position 30, ensuring the test remains valid under the lowercase-only enforcement. The seventh patch activates enforcement in `hex-ll.h`, documents the change in `Documentation/BreakingChanges.adoc`, and adds a test in `t1503-rev-parse-verify.sh` to verify rejection of uppercase object IDs.

Open questions and loose ends:
- Whether the project will accept the breaking change. Junio’s "Will queue" signals tentative movement toward integration, but the thread remains open pending broader community feedback. The security rationale has been strengthened by brian m. carlson’s responses and Michael Montalbo’s demonstration, but Phillip Wood’s latest reply expands the discussion to adjacent policy questions, challenging the premise that restricting hex case alone is sufficient. The thread’s focus remains on the lowercase-only hex change, but the scope may broaden if others engage with Phillip’s ref-name proposal.
- Whether `HEX_KIND_OID` should cover derived hashes (e.g., packfile names, rerere database keys). Junio raised this question earlier, and it remains unaddressed.
- Junio’s micro-optimization suggestion for the third patch (hoisting `hexval` table selection outside the loop in `hex_to_bytes()`) remains unresolved. Jeff King’s review suggests the optimization is not urgent, but it is unclear whether brian m. carlson will adopt it.
- The edge case of uppercase hex in object payloads (commits and tags) creating parallel histories, acknowledged by brian m. carlson as a real issue complicating hash-algorithm compatibility. This edge case is not addressed by the current proposal and may weaken the justification for the breaking change.
- The feasibility of Junio’s proposed compromise: normalizing mixed-case inputs to lowercase internally while accepting them from external sources. The discussion remains open, with no clear resolution on whether the project is willing to invest in the necessary auditing and normalization work.
- Phillip Wood’s new proposal: whether Git should forbid ref names that *look like* object IDs (e.g., `refs/heads/abcdef1234...`). This idea is new to the thread and could evolve into a separate (or complementary) effort if others find it compelling. For now, it remains a loose end, with no indication of whether the project will pursue it.

Participant positions:
- brian m. carlson (author): argues for the change on grounds of consistency, security, and ecosystem compatibility. Provides concrete evidence of real-world security vulnerabilities caused by Git's current case-insensitive parsing, cites ecosystem tools (Gitolite, GitHub-hosted tools) that reject or mishandle uppercase hex, and notes Git's own documentation (hook examples) reinforces lowercase-only expectations. The first four patches are infrastructure-only and do not alter behavior; the fifth patch replaces the open-coded hex-parsing loop in `object-name.c` with `hexval()`, preserving the existing lowercase-forcing behavior while adopting the defensive pattern (`val & ~0xff`) to safely check for invalid hex digits; the sixth patch adjusts `t5324-split-commit-graph.sh` to replace corruption characters "A" with "b" (position 70) and "a" (position 30), addressing Elijah Newren’s review feedback; the seventh patch introduces the breaking change. In earlier responses, Brian pushed back against Junio’s invocation of the Robustness Principle, citing modern security practices to argue that lenient parsing is now a security anti-pattern. He rejected Junio’s proposed compromise—enforcing lowercase internally while accepting uppercase from external sources—as impractical, noting it would require auditing every `oid_to_hex` call for only a partial fix. He acknowledges the edge case of uppercase hex in object payloads as a real issue complicating hash-algorithm compatibility, noting that such objects cannot be round-tripped through Git's interoperability code (which only emits lowercase object IDs), effectively making them SHA-1-only. His v2 addresses all review feedback, including Junio’s omissions, Elijah Newren’s correctness concerns, and test adjustments. He remains conciliatory, deferring to project consensus and leaving the door open for the series to be dropped if the community disagrees.
- Junio C Hamano (maintainer): initially pushed back on the motivation but has since engaged deeply with both the implementation and the philosophical premise. He approved the use of `HEX_KIND_OID` in the fourth patch and raised technical questions about derived hashes, micro-optimizations, behavioral subtleties, and test adjustments. In later reviews, he invoked the Robustness Principle to question whether Git should ever reject uppercase hex digits, even in a breaking-change release, and distinguished between internal enforcement and external inputs. His latest replies signal tentative acceptance ("Will queue") while expressing discomfort with the idea of offloading compatibility fallout onto reimplementations like libgit2 or JGit. He revives the idea of normalizing mixed-case inputs to lowercase internally while accepting them from external sources, suggesting this could address both security and compatibility concerns. His position remains ambivalent but leans toward accepting the series as-is, pending further community input. His reviews of v2 flagged no new issues, indicating the implementation is technically sound.
- Jeff King (Peff): provides substantive reviews focused on implementation details and edge cases. He confirmed that gcc-15 does not hoist the `hexval` table selection out of the loop in `hex_to_bytes()`, but noted that branch prediction may mitigate the performance cost, making Junio’s micro-optimization suggestion less urgent. He also identified the edge case of uppercase hex within object payloads creating parallel histories, which brian m. carlson later acknowledged as a real issue complicating hash-algorithm compatibility. His reviews are narrowly scoped to technical details and do not address the broader design or motivation of the series.
- Michael Montalbo: contributed a concrete demonstration of how mixed-case object IDs can create ambiguity and potential security issues. His script shows that Git currently allows commits to reference the same parent object using different case spellings, producing distinct commit objects that differ only in the case of the parent OID field. While both spellings resolve to the same underlying object, Git's output paths handle them inconsistently: raw output preserves the mixed-case form, while formatted output (e.g., `%P`) normalizes to lowercase. This inconsistency could confuse downstream tools that parse Git output, creating opportunities for malicious manipulation or unintended behavior. The demonstration strengthens brian m. carlson's argument that Git's current case-insensitive parsing is problematic.
- Phillip Wood: raises pivotal questions about the security rationale and scope of the proposed change. His initial review asked why `ABCDEF` is a security risk when `abcdef^0` (the same object) is not, challenging the core justification for the series. Brian’s response provided concrete scenarios where case-insensitive parsing enables security bypasses, which Phillip acknowledges in his latest reply. However, he expands the discussion to adjacent policy questions: if uppercase hex can defeat a security check, why can’t a ref name pointing to the same commit do the same? This challenges the premise that restricting hex case alone is sufficient and introduces the idea of forbidding ref names that *look like* object IDs (e.g., `refs/heads/abcdef1234...`). His tone is constructive and exploratory, and his questions are not objections but invitations to clarify the scope of the problem. His position remains open-ended, with no clear endorsement or opposition to the series, but his latest reply may shift the thread toward broader input validation discussions if others engage with his ref-name proposal.
- Elijah Newren: provided **substantive, narrowly scoped reviews** of the fifth and sixth patches in v1. His review of the fifth patch flagged a behavioral change (the new `hexval()` call preserving original case, whereas the old code lower-cased it) and a correctness risk (storing `hexval()`’s `unsigned int` result in an `int`, making the `if (val < 0)` check fragile). His concerns were addressed in v2 by documenting the behavioral change (the fifth patch preserves the existing lowercase-forcing behavior) and adopting the defensive pattern (`val & ~0xf`). His review of the sixth patch was **surface-level**, addressing only minor issues: the commit message’s ambiguity about which "A" is changed to "b" in `t5324-split-commit-graph.sh` (position 70, not 30) and the indentation inconsistency in `Documentation/BreakingChanges.adoc` (tabs vs. spaces). Neither review engages with the series’ broader design or motivation, but the fifth patch’s feedback was actionable and critical for correctness. No new reviews from Elijah on v2.

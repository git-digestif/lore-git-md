Thread identity: RFC patch series proposing a breaking change for Git 3.0: restricting hex object IDs to lowercase only. Originating author: brian m. carlson. Thread type: design discussion / RFC.

Core problem or goal: Git currently emits lowercase hex object IDs but accepts both uppercase and lowercase in parsing, creating potential compatibility and security issues for external tools that assume hex uniqueness. The series aims to enforce lowercase-only parsing in Git 3.0 to make behavior consistent and predictable, addressing real-world security vulnerabilities where external tools failed to properly sanitize or filter object IDs due to case insensitivity. The first five patches introduce infrastructure (new `hex_kind` enum, `hexval_lc_table`, updated `hexval()`, `hex2chr()`, and `hex_to_bytes()` functions, and `HEX_KIND_OID` constant) and refactor existing hex-parsing code to use these helpers without altering runtime behavior yet. The final patch activates enforcement by defining `HEX_KIND_OID` as `HEX_KIND_LOWER` when `WITH_BREAKING_CHANGES` is enabled, documents the change in `Documentation/BreakingChanges.adoc`, and adds test coverage to verify rejection of uppercase object IDs.

Current status: RFC stage; no prior versions. The series is complete in implementation but explicitly seeks feedback on whether the project wants this breaking change. Junio C Hamano has signaled tentative acceptance ("Will queue") but remains ambivalent, distinguishing between *careless* leniency (storing mixed-case inputs verbatim) and *deliberate* leniency (normalizing inputs to lowercase internally) as a potential compromise. The thread remains in RFC limbo, with no final decision made. The first five patches are preparatory and do not change behavior; the sixth patch introduces the breaking change but remains gated behind `WITH_BREAKING_CHANGES`. Junio’s latest reviews identify technical omissions and behavioral subtleties: in the fourth patch, two sites (`builtin/index-pack.c` and `notes.c`) should use `HEX_KIND_OID` instead of `HEX_KIND_MIXED`; in the fifth patch, the new `hexval()` call in `object-name.c` preserves original case during the transition period, whereas the old code lower-cased it, a behavioral change that will be documented in the commit message for the next version (`v2`). Elijah Newren’s review of the fifth patch flags the same behavioral change and raises a correctness risk: `hexval()` returns an `unsigned int`, but the patch stores its result in an `int`, making the subsequent `if (val < 0)` check fragile if the variable type is later changed to `unsigned int`. This will be addressed by adopting the defensive pattern used in patch 1 (`val & ~0xf`). Junio’s review of the sixth patch questions the rationale behind test adjustments in `t5324-split-commit-graph.sh`, noting the corruption character changes from "A" to "b" in one case and to "a" in another. The change to "b" ensures the test fails due to corruption (not uppercase rejection) in SHA-256 mode, where the correct character at position 70 is "a"; the change to "a" is a no-op but aligns the test with the series’ lowercase-only requirement. The commit message will clarify these choices in `v2`. Phillip Wood’s question about the security rationale—why `ABCDEF` is a risk when `abcdef^0` is not—has been addressed by brian m. carlson, who provided concrete scenarios where case-insensitive parsing enables security bypasses (e.g., tools checking only lowercase forms, regex misclassification). Phillip’s latest reply acknowledges these examples but expands the discussion to adjacent policy questions: if uppercase hex can defeat a security check, why can’t a ref name pointing to the same commit do the same? This challenges the premise that restricting hex case alone is sufficient and introduces the idea of forbidding ref names that *look like* object IDs (e.g., `refs/heads/abcdef1234...`). The thread’s focus remains on the lowercase-only hex change, but Phillip’s reply hints at a possible next step if the current series is accepted. Junio’s proposed compromise—normalizing mixed-case inputs to lowercase internally while accepting them from external sources—remains unresolved, with no clear indication of whether the project is willing to invest in the necessary auditing and normalization work.

Key technical details:
- New files: `hex-ll.c`/`hex-ll.h` (lower-level hex parsing utilities).
- New symbols: `hex_kind` enum (`HEX_KIND_MIXED`, `HEX_KIND_LOWER`, `HEX_KIND_OID`), `hexval_lc_table`, updated `hexval()`, `hex2chr()`, and `hex_to_bytes()` functions (all take `enum hex_kind` parameter).
- Modified subsystems: `hex.c`, `pkt-line.c`, `color.c`, `mailinfo.c`, `ref-filter.c`, `strbuf.c`, `url.c`, `urlmatch.c`, `index-pack.c`, `diagnose.c`, `http-push.c`, `notes.c`, `object-file.c`, `object-name.c` (hex parsing in packet-length parsing, quoted-printable decoding, percent-encoding, ref formatting, URL handling, object ID parsing from disk/network/diagnostics, and object name resolution), plus `Documentation/BreakingChanges.adoc` (documentation).
- On-disk format: no changes; this is a parser behavior change only.
- Test coverage: new test in `t1503-rev-parse-verify.sh` verifies rejection of uppercase object IDs; existing test in `t5324-split-commit-graph.sh` adjusted to avoid false positives in SHA-256 mode (corruption character changed from "A" to "b" at position 70 to ensure failure is due to corruption, not uppercase rejection; "A" changed to "a" at position 30 for consistency with lowercase-only requirement).
- Breaking change gated behind "breaking changes mode" (target: Git 3.0).
- Junio’s review of the third patch suggested a micro-optimization: hoisting the `hexval` table selection outside the loop in `hex_to_bytes()` to avoid repeated conditional checks. Jeff King’s review confirms that gcc-15 does not perform this hoisting automatically, but notes that branch prediction may reduce the performance impact, making the optimization less urgent.
- Junio’s latest review of the fourth patch flags two omissions: `builtin/index-pack.c` and `notes.c` should use `HEX_KIND_OID` instead of `HEX_KIND_MIXED` for object ID parsing.
- Junio’s and Elijah Newren’s reviews of the fifth patch note a behavioral change: the new `hexval()` call in `object-name.c` preserves original case during the transition period, whereas the old code lower-cased it. This change will be documented in the commit message for `v2`. The correctness risk flagged by Elijah—`hexval()` returning `unsigned int` but the result being stored in an `int`, making the `if (val < 0)` check fragile—will be resolved by adopting the defensive pattern from patch 1 (`val & ~0xf`).
- Jeff King’s observation: uppercase hex within object payloads (commit and tag objects) can create parallel histories, as Git does not normalize case when hashing object contents. Junio later dismissed this as unlikely to occur accidentally and not a meaningful problem, but Brian's latest response acknowledges it as a real issue complicating hash-algorithm compatibility, as objects containing uppercase hex cannot be round-tripped through Git's interoperability code (which only emits lowercase object IDs), effectively making them SHA-1-only.
- Michael Montalbo’s demonstration: a script showing that Git allows commits to reference the same parent object using different case spellings, producing distinct commit objects that differ only in the case of the parent OID field. While both spellings resolve to the same underlying object, Git's output paths handle them inconsistently: raw output preserves the mixed-case form, while formatted output (e.g., `%P`) normalizes to lowercase. This inconsistency could confuse downstream tools that parse Git output, creating opportunities for malicious manipulation or unintended behavior.

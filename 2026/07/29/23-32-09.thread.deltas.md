- [2026/07/31/07-38-17 by Junio C Hamano <gitster@pobox.com>] On making hex_to_bytes accept a hex kind, Junio C Hamano suggested that for long loops it may be more performant to select the hexval table once outside the loop, sketched a restructured API using `void *hextable = hex_table(HEX_KIND_MIXED);` passed into hexval(), and said it does not look too bad.
- [2026/07/31/07-48-14 by Junio C Hamano <gitster@pobox.com>] On restricting object IDs to lowercase in breaking changes mode, Junio C Hamano said others' violation of Postel's Law does not oblige Git to follow suit, and proposed treating locally used object names and names exchanged with others over the network separately: stay strict and lowercase in what we produce while still accepting uppercase from third-party reimplementations.
- [2026/07/31/12-33-47 by Junio C Hamano <gitster@pobox.com>] On the same patch, Junio C Hamano laid out a hypothetical dumb-HTTP scenario where liberally accepting an uppercase loose object AB/012345...EF alongside an existing lowercase ab/012345...ef could trigger bad behavior, argued the RFC's rejection of uppercase avoids that state but that the solution honoring the robustness principle is to recognize the uppercase file as the same object already present locally, and stated that tightening the rule after twenty years is the part he is most hesitant to accept ("So, I dunno.").

## 2026/08/01

- [2026/08/01/14-35-13 by Jeff King <peff@peff.net>] Jeff King reported that, testing with gcc-15, the compiler does not hoist the hex-table comparison out of the `hex_to_bytes` loop (it loads both table addresses but keeps a branch in the loop), so manual hoisting of the table selection could theoretically help performance, though it might not matter much given branch prediction.
- [2026/08/01/14-45-27 by Jeff King <peff@peff.net>] Jeff King raised the additional case of uppercase hex inside objects: uppercasing a commit's `parent` line and re-hashing produces a parallel history of otherwise identical commits, which Git generally tries to avoid as multiple representations of the same data; he noted only commits and tags are subject to this (tree hashes are binary) and that most code incidentally normalizes case by round-tripping through a binary hash.
- [2026/08/01/18-22-49 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano agreed the uppercase parallel-history concern is not a huge issue since parallel histories already exist (e.g., an empty rebase delaying the clock by one second), clarified that tree hierarchies are fully binary and only the top-level object name in a commit/tag can have multiple representations, and noted that `git diff` between such commits still detects the same tree because `diff_tree()` receives binary tree names, with case normalization happening incidentally wherever values pass through binary form.

## 2026/08/02

- [2026/08/02/21-55-10 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson agreed with Jeff King that uppercase hex within objects creates multiple representations of the same data (a parallel history), and added that such objects cannot be round-tripped through the interoperability code (which only writes lowercase object IDs), effectively locking them to SHA-1 only.
- [2026/08/02/22-09-52 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson argued that Postel's Law is no longer a good idea because being liberal in what is accepted now usually has security implications (citing TLS, HTTP request smuggling, and CR issues on Windows), and rejected Junio C Hamano's suggestion to treat local and network object names separately, saying it does not fix most security problems involving object IDs passed on the command line (though it would fix round-tripping between hash algorithms), and that he does not want to audit every use of `oid_to_hex` to half-fix the situation.

## 2026/08/05

- [2026/08/05/03-09-53 by Michael Montalbo <mmontalbo@gmail.com>] Michael Montalbo agreed with restricting hex object IDs to lowercase and reported that mixed upper/lowercase OIDs are currently possible, with Git normalizing the casing on some output paths while preserving the raw stored form on others; he noted this ambiguity could cause confusion or be maliciously exploited by downstream consumers with differing parsers, and provided a reproduction demonstrating two distinct commit objects differing only by case in the parent field that resolve to the same parent object but display differently depending on the Git command used.

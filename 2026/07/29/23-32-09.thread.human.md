The Git mailing list thread proposing a breaking change for Git 3.0—restricting hex object IDs to lowercase only—has reached a pivotal moment. The series, now in its second iteration (v2) with seven patches, addresses all prior feedback and is ready for broader review. Authored by brian m. carlson, the change aims to eliminate Git’s current case-insensitive parsing of object IDs, a behavior that has caused real-world security vulnerabilities and ecosystem compatibility issues. The first four patches introduce infrastructure (new hex-parsing utilities) without altering runtime behavior, while the fifth preserves existing lowercase-forcing logic in `object-name.c`. The sixth adjusts a test to avoid false positives under SHA-256, and the seventh activates enforcement, gated behind the `WITH_BREAKING_CHANGES` flag for Git 3.0.

Junio C Hamano, the maintainer, has signaled tentative acceptance by asking the list to verify that v2 aligns with the earlier consensus and, if so, to approve its integration into the `next` branch. His call-to-action is procedural, not a reopening of the design debate: he wants confirmation that the implementation matches the agreed-upon direction, not a re-litigation of the security rationale or philosophical trade-offs. The series has drawn substantive feedback from key contributors—Jeff King (Peff) flagged edge cases like uppercase hex in object payloads, Michael Montalbo demonstrated how mixed-case IDs can create ambiguity, and Phillip Wood expanded the discussion to adjacent policies (e.g., forbidding ref names that *look like* object IDs). However, no new technical objections have emerged since v2, and Junio’s silence on unresolved questions (e.g., derived hashes, micro-optimizations) suggests they are not blockers.

The thread’s core tension remains unresolved: whether the project will accept a breaking change that improves consistency and security at the cost of ecosystem disruption. Junio’s ambivalence—his invocation of the Robustness Principle and discomfort with offloading compatibility work onto reimplementations like libgit2—has not derailed the series, but neither has it been fully assuaged. For now, the path forward hinges on community engagement: if reviewers confirm v2’s technical soundness, Junio appears prepared to queue it for integration testing. The open questions (e.g., Phillip Wood’s ref-name proposal) may yet broaden the scope, but the current focus is on landing the hex-case restriction as a standalone change. The next step is clear: the list must either endorse v2 or raise new concerns before the series can advance.

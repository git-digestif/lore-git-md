This thread is about an RFC patch series proposing a breaking change for Git 3.0: restricting hex object IDs to lowercase only. The series, authored by brian m. carlson, aims to address security and compatibility issues caused by Git's current case-insensitive parsing of object IDs, which has led to real-world vulnerabilities in external tools.

The series is now at v2, with the third patch being a preparatory step that extends the `hex_to_bytes()` function to accept an `enum hex_kind` parameter, allowing callers to specify the expected hex format. This patch updates several low-level utilities and subsystems to use the new parameter while preserving current behavior. The actual enforcement of lowercase-only parsing will come in a later patch, gated behind the `WITH_BREAKING_CHANGES` flag for Git 3.0.

Key participants include Junio C Hamano, the maintainer, who has tentatively signaled acceptance ("Will queue") but remains ambivalent about the broader implications. Jeff King and Elijah Newren have provided technical reviews, focusing on implementation details and correctness. Michael Montalbo contributed a concrete demonstration of how mixed-case object IDs can create ambiguity and security risks. Phillip Wood has raised pivotal questions about the scope of the change, suggesting that Git should also forbid ref names that look like object IDs, which could broaden the discussion if others engage.

The series addresses all feedback from the initial RFC, including Junio’s omissions and Elijah’s correctness concerns. However, unresolved questions remain, such as whether the project will accept the breaking change, whether `HEX_KIND_OID` should cover derived hashes, and the edge case of uppercase hex in object payloads. The thread is still open, and the community’s response to Phillip Wood’s latest proposal could shift its focus toward broader input validation discussions. For now, the series is technically sound and ready for deeper review if the project decides to proceed.

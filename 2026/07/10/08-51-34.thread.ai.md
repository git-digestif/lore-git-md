Thread identity: Patch series replacing the `GIT_NO_LAZY_FETCH=fromAccepted` proposal with `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable to mark repositories as trusted for lazy fetching. Series version: v3. Originating author: Christian Couder.

Core problem or goal: Provide a server-side mechanism for operators to explicitly declare which repositories are safe to lazy-fetch from, addressing the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration. The new approach shifts trust decisions entirely to the server operator, modeled after Git’s `safe.directory` configuration, and replaces the earlier client-side `fromAccepted` proposal.

The `GIT_INTERNAL_LAZY_FETCH_DEPTH` environment variable (introduced in 4/5) limits recursion depth to `MAX_LAZY_FETCH_DEPTH` (5), chosen to balance safety and legitimate nesting (e.g., `git fetch` invoking `index-pack` to lazily fetch REF_DELTA bases). The final patch (5/5) activates the mechanism by setting `GIT_NO_LAZY_FETCH=0` in `builtin/upload-pack.c` when serving a trusted repository.
- New behavior: `uploadpack.lazyFetchTrusted` (protected configuration variable) allows server operators to mark repositories as trusted for lazy fetching, with recursion safeguards preventing infinite loops when a repository is configured as its own promisor remote. The configuration is read from protected files only, and only absolute paths are accepted (rejecting `.` and relative paths). Non-bare repositories must be allowlisted by their `.git` directory (e.g., `/srv/repo/.git` for `/srv/repo`). The callback-based allowlist design enables caller-specific validation rules: `uploadpack.lazyFetchTrusted` requires absolute paths, while `safe.directory` retains its existing behavior. Documentation clarifies that the configuration is multi-valued, specifies repository paths as git directories, warns against self-referential promisor remotes, and supports `~` and `%(prefix)` expansions. Tests verify recursion limits, path validation, and the server-side trust model’s security properties.

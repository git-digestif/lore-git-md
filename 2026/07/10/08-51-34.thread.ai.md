Thread identity: Patch series replacing the `GIT_NO_LAZY_FETCH=fromAccepted` proposal with `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable to mark repositories as trusted for lazy fetching. Series version: v4. Originating author: Christian Couder.

Core problem or goal: Provide a server-side mechanism for operators to explicitly declare which repositories are safe to lazy-fetch from, addressing the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration. The new approach shifts trust decisions entirely to the server operator, modeled after Git’s `safe.directory` configuration, and replaces the earlier client-side `fromAccepted` proposal.

Current status: Under review, with all v3 feedback addressed in v4. The series is rebased on a recent `master` commit and passes CI tests. Junio’s final review of 5/5 is surface-level and entirely positive, with no substantive concerns raised. The series remains under review, not in `seen`, `next`, or `master`.

Key technical details:
- Files touched: `promisor-remote.c` (refactoring in 1/5, recursion safeguard in 4/5), `setup.c` (callback-based allowlist logic in 2/5 and 3/5, configuration reading in 4/5), `setup.h` (new helpers in 2/5 and 3/5), `upload-pack.c` (configuration integration and recursion safeguard in 3/5, 4/5), `builtin/upload-pack.c` (behavior activation in 5/5 with revised environment-handling logic), `git-upload-pack.adoc`, `git.adoc`, `Documentation/config/uploadpack.adoc` (documentation in 5/5), `environment.h` (new `GIT_INTERNAL_LAZY_FETCH_DEPTH` constant in 4/5), test scripts `t/t5710-promisor-remote-capability.sh` (expanded in 5/5) and `t/t0410-partial-clone.sh` (new recursion test in 4/5).
- New or modified symbols: `lazy_fetch_objects()`, `try_promisor_remotes()`, `path_allowlist_apply()`, `path_allowlist_config_apply()`, `allow_safe_dir()`, `allow_trusted_path()`, `upload_pack_lazy_fetch_trusted()`, `upload_pack_protected_lazy_fetch_config()`, `lazy_fetch_trusted` struct, `fetch_objects()`. The `GIT_INTERNAL_LAZY_FETCH_DEPTH` environment variable limits recursion depth to 5. The final patch (5/5) activates the mechanism by conditionally setting `GIT_NO_LAZY_FETCH=1` only if the environment variable is unset and the repository is not in the allowlist.
- New behavior: `uploadpack.lazyFetchTrusted` (protected configuration variable) allows server operators to mark repositories as trusted for lazy fetching, with recursion safeguards preventing infinite loops. The configuration is read from protected files only, accepts only absolute paths, and requires non-bare repositories to be allowlisted by their `.git` directory. Documentation specifies repository paths as git directories, warns against self-referential promisor remotes, and supports `~` and `%(prefix)` expansions. Tests verify recursion limits, path validation, and security properties.

Open questions and loose ends: Junio’s scalability critique about memory overhead in `lazy_fetch_objects()` and conceptual doubt about using a configuration variable remain unresolved, though mitigated by the server-side trust model. A latent design issue in the existing `safe.directory` logic—silent ignoring of non-existent paths—risks propagating to `uploadpack.lazyFetchTrusted`. Junio’s latest review of 2/5 proposes an enhancement to the configuration syntax (e.g., `:(optional)foo/bar`) to allow explicit marking of optional paths, along with a warning message to guide users. While this is outside the scope of the current series, he recommends adding a `NEEDSWORK` comment to flag the issue for future work. Christian has acknowledged the concern and proposed addressing it in a follow-up patch. The depth limit of 5 in the recursion safeguard may require adjustment based on real-world use cases.

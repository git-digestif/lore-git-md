Thread identity: Patch series replacing the `GIT_NO_LAZY_FETCH=fromAccepted` proposal with `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable to mark repositories as trusted for lazy fetching. Series version: v5. Originating author: Christian Couder.

Core problem or goal: Provide a server-side mechanism for operators to explicitly declare which repositories are safe to lazy-fetch from, addressing the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration. The new approach shifts trust decisions entirely to the server operator, modeled after Git’s `safe.directory` configuration, and replaces the earlier client-side `fromAccepted` proposal.

The `GIT_INTERNAL_LAZY_FETCH_DEPTH` environment variable limits recursion depth to 5. The final patch (5/5) activates the mechanism by conditionally setting `GIT_NO_LAZY_FETCH=1` only if the environment variable is unset and the repository is not in the allowlist.
- New behavior: `uploadpack.lazyFetchTrusted` (protected configuration variable) allows server operators to mark repositories as trusted for lazy fetching, with recursion safeguards preventing infinite loops. The configuration is read from protected files only, accepts only absolute paths, and requires non-bare repositories to be allowlisted by their `.git` directory. Documentation clarifies repository identification for `--separate-git-dir` and linked worktrees, and explicitly states that trust does *not* propagate to promisor remotes. Tests verify recursion limits, path validation, and security properties.
- Refactoring details (1/5 and 2/5): The new `lazy_fetch_objects()` helper consolidates the `GIT_NO_LAZY_FETCH` environment check into a single up-front call. Patch 2/5 extracts reusable path-allowlist logic from `safe.directory` into `path_allowlist_apply()` and `path_allowlist_config_apply()`, introducing 143 lines of new code while removing 49 lines of duplication. The refactoring is observably equivalent, with no behavioral changes. Documentation for `try_promisor_remotes()` and `lazy_fetch_objects()` clarifies ownership rules for arguments. Patch 2/5 also flags a latent design issue in `safe.directory`—silent ignoring of non-existent paths—with a `NEEDSWORK` comment, proposing a follow-up patch to explore alternatives (e.g., `:(optional)` prefix syntax).
- Patch 3/5 details: Registers a protected-config callback (`upload_pack_protected_lazy_fetch_config`) that invokes `path_allowlist_config_apply()` with a custom `allow_trusted_path()` validator. The validator enforces absolute paths (rejecting `.` shorthand). The public `upload_pack_lazy_fetch_trusted()` function resolves the repository’s real git-dir, consults the allowlist, and returns a boolean.
- Patch 4/5 details: Introduces a recursion depth counter via `GIT_INTERNAL_LAZY_FETCH_DEPTH`, incremented each time `fetch_objects()` spawns a child process. If the depth exceeds `MAX_LAZY_FETCH_DEPTH` (5), the code emits a warning and aborts further lazy fetching. The safeguard is implemented in `promisor-remote.c`, with tests verifying the limit.
- Patch 5/5 details: Activates the mechanism by conditionally setting `GIT_NO_LAZY_FETCH=1` only if the repository is untrusted *and* no explicit override exists. Documentation updates clarify repository identification and non-propagation of trust to promisor remotes.

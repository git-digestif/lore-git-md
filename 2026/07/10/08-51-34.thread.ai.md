Thread identity: Patch series replacing the `GIT_NO_LAZY_FETCH=fromAccepted` proposal with `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable to mark repositories as trusted for lazy fetching. Series version: v5. Originating author: Christian Couder.

Core problem or goal: Provide a server-side mechanism for operators to explicitly declare which repositories are safe to lazy-fetch from, addressing the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration. The new approach shifts trust decisions entirely to the server operator, modeled after Git’s `safe.directory` configuration, and replaces the earlier client-side `fromAccepted` proposal.

Current status: Under review, with all feedback from Junio’s v4 review now addressed in v5. The series is rebased on Git 2.56 (a018953688) and passes CI tests. No substantive concerns remain; Junio’s final review was entirely surface-level (documentation wording and grammar). The series remains under review, not in `seen`, `next`, or `master`.

Key technical details:

- New or modified symbols: `lazy_fetch_objects()` (extracted from `fetch_objects()` and `promisor_remote_get_direct()` in 1/5), `try_promisor_remotes()`, `path_allowlist_apply()`, `path_allowlist_config_apply()`, `allow_safe_dir()`, `allow_trusted_path()`, `upload_pack_lazy_fetch_trusted()`, `upload_pack_protected_lazy_fetch_config()`, `lazy_fetch_trusted` struct, `fetch_objects()`. The `GIT_INTERNAL_LAZY_FETCH_DEPTH` environment variable limits recursion depth to 5. The final patch (5/5) activates the mechanism by conditionally setting `GIT_NO_LAZY_FETCH=1` only if the environment variable is unset and the repository is not in the allowlist.
- New behavior: `uploadpack.lazyFetchTrusted` (protected configuration variable) allows server operators to mark repositories as trusted for lazy fetching, with recursion safeguards preventing infinite loops. The configuration is read from protected files only, accepts only absolute paths, and requires non-bare repositories to be allowlisted by their `.git` directory. Documentation now clarifies repository identification for `--separate-git-dir` and linked worktrees, and explicitly states that trust does *not* propagate to promisor remotes. Tests verify recursion limits, path validation, and security properties, including cases where a repository’s `.git` file points to a separate git directory and where a trusted repository’s promisor remote is *not* automatically trusted. The activation logic in 5/5 ensures `GIT_NO_LAZY_FETCH` is set only when the repository is untrusted *and* no explicit override exists, preserving operator control.
- Refactoring details (1/5 and 2/5): The new `lazy_fetch_objects()` helper (1/5) consolidates the `GIT_NO_LAZY_FETCH` environment check into a single up-front call, eliminating redundant checks (one per promisor remote in the old code). Patch 2/5 extracts reusable path-allowlist logic from `safe.directory` into `path_allowlist_apply()` and `path_allowlist_config_apply()`, introducing 143 lines of new code while removing 49 lines of duplication. The refactoring is observably equivalent: the only behavioral differences are reduced environment checks (1/5) and deferred initialization (1/5), neither of which changes outcomes. Documentation for `try_promisor_remotes()` and `lazy_fetch_objects()` clarifies ownership rules for the `remaining_oids` and `to_free` arguments. Patch 2/5 also flags a latent design issue in `safe.directory`—silent ignoring of non-existent paths—with a `NEEDSWORK` comment, proposing a follow-up patch to explore alternatives (e.g., `:(optional)` prefix syntax to mark intentionally missing paths, with a warning message hinting at this syntax).
- Patch 3/5 details: Adds 62 lines to `upload-pack.c` and 3 lines to `upload-pack.h`, registering a protected-config callback (`upload_pack_protected_lazy_fetch_config`) that invokes `path_allowlist_config_apply()` with a custom `allow_trusted_path()` validator. The validator enforces absolute paths (rejecting the `.` shorthand accepted by `safe.directory`) because `upload-pack` always serves repositories by absolute git-dir path. The public `upload_pack_lazy_fetch_trusted()` function resolves the repository’s real git-dir, consults the allowlist, and returns a boolean. Memory management is clean: `real_pathdup()` is paired with a `free()` in the same function.
- Patch 4/5 details: Introduces a recursion depth counter via the `GIT_INTERNAL_LAZY_FETCH_DEPTH` environment variable, incremented each time `fetch_objects()` spawns a child process. If the depth exceeds `MAX_LAZY_FETCH_DEPTH` (5), the code emits a warning and aborts further lazy fetching. The limit is chosen to allow legitimate nesting (e.g., `index-pack` fetching REF_DELTA bases) while preventing infinite loops. The safeguard is implemented in `promisor-remote.c`, with the depth check added to `lazy_fetch_objects()` and propagated through `try_promisor_remotes()` and `fetch_objects()`. The test in `t/t0410-partial-clone.sh` verifies the safeguard by configuring two partial clones as each other’s promisor remotes and confirming that lazy fetching fails with the expected warning after exactly 5 nested fetches, counting the number of `git fetch` subprocesses spawned.
- Patch 5/5 details: Activates the mechanism by conditionally setting `GIT_NO_LAZY_FETCH=1` in `builtin/upload-pack.c` only if the repository is untrusted *and* the environment variable is unset. The logic is structured as three cases: (1) explicit operator override via `GIT_NO_LAZY_FETCH` (takes precedence), (2) server-side trust via `uploadpack.lazyFetchTrusted` (enables lazy fetching if the repository is allowlisted), and (3) default behavior (disables lazy fetching). Documentation updates clarify repository identification (including `--separate-git-dir` and linked worktrees), emphasize non-propagation of trust to promisor remotes, and distinguish server-side trust from client-side `GIT_NO_LAZY_FETCH=0`. The phrasing in the documentation now uses "each value of which specifies" (per Junio’s suggestion) while retaining the rest of the sentence to avoid ambiguity about whether the server fetches *from* or *for* the configured repository. Tests cover path validation (worktree vs. git-dir), recursion safeguards (a trusted repository serving itself), explicit environment variable override, and non-propagation of trust to promisor remotes.

Open questions and loose ends: Junio’s scalability critique about memory overhead in `lazy_fetch_objects()` and conceptual doubt about using a configuration variable remain unresolved, though mitigated by the server-side trust model. The latent design issue in `safe.directory`—silent ignoring of non-existent paths—is now explicitly flagged with a `NEEDSWORK` comment in patch 2/5, with Christian proposing to address it in a follow-up patch by adopting Git’s existing `:(optional)` prefix syntax (already supported for pathname-typed configuration variables) to mark intentionally missing paths, accompanied by a warning message hinting at this syntax. The depth limit of 5 in the recursion safeguard may require adjustment based on real-world use cases. Junio’s v4 suggestion to enhance configuration syntax (e.g., `:(optional)foo/bar`) remains outside the scope of the current series but is now documented as a potential follow-up.

Thread identity: Patch series replacing the `GIT_NO_LAZY_FETCH=fromAccepted` proposal with `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable to mark repositories as trusted for lazy fetching. Series version: v4. Originating author: Christian Couder.

Core problem or goal: Provide a server-side mechanism for operators to explicitly declare which repositories are safe to lazy-fetch from, addressing the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration. The new approach shifts trust decisions entirely to the server operator, modeled after Git’s `safe.directory` configuration, and replaces the earlier client-side `fromAccepted` proposal.

Current status: Under review, with all v3 feedback addressed in v4. The series is rebased on a recent `master` commit and passes CI tests. The final patch (5/5) now fully addresses Junio’s environment-handling critique: instead of unconditionally setting `GIT_NO_LAZY_FETCH=1` early and later relaxing it, the code checks the environment first (`no_lazy_fetch_set = !!getenv(NO_LAZY_FETCH_ENVIRONMENT)`) and only sets `GIT_NO_LAZY_FETCH` if it wasn’t already set by the operator. This preserves operator control while defaulting to safe behavior for untrusted repositories. The commit message is updated to explicitly list the three possible states (operator-set environment, allowlisted repository, default behavior) and clarify what the operator vouches for when listing a repository (trustworthiness of its promisor remotes, configuration, and hooks). The series remains under review, not in `seen`, `next`, or `master`.

Key technical details:
- Files touched: `promisor-remote.c` (refactoring in 1/5, recursion safeguard in 4/5), `setup.c` (callback-based allowlist logic in 2/5 and 3/5, configuration reading in 4/5), `setup.h` (new helpers in 2/5 and 3/5), `upload-pack.c` (configuration integration and recursion safeguard in 3/5, 4/5), `builtin/upload-pack.c` (behavior activation in 5/5, now with revised environment-handling logic), `git-upload-pack.adoc`, `git.adoc`, `Documentation/config/uploadpack.adoc` (documentation in 5/5), `environment.h` (new `GIT_INTERNAL_LAZY_FETCH_DEPTH` constant in 4/5), test scripts `t/t5710-promisor-remote-capability.sh` (expanded in 5/5 with six new test cases covering allowlist mechanism, operator override, protected-config enforcement, recursion safeguards, and path validation) and `t/t0410-partial-clone.sh` (new recursion test in 4/5).
- New or modified symbols: `lazy_fetch_objects()` (new helper in 1/5 consolidating lazy-fetching logic, modified in 4/5 to check recursion depth; includes detailed documentation for parameter ownership rules and the up-front `GIT_NO_LAZY_FETCH` check), `try_promisor_remotes()` (converted from `int` to `bool` in v3, reverted to `int` in v4 for consistency; documentation explicitly describes behavior, parameter semantics, and ownership rules), `path_allowlist_apply()` and `path_allowlist_config_apply()` (new generic helpers in 2/5 for path validation, flagged for silent-ignoring behavior on non-existent paths), `allow_safe_dir()` (new callback in 2/5 for `safe.directory` rules), `allow_trusted_path()` (new callback in 3/5 for `uploadpack.lazyFetchTrusted` validation, enforcing stricter path requirements than `safe.directory`), `upload_pack_lazy_fetch_trusted()` (new function in 3/5 to check configuration), `upload_pack_protected_lazy_fetch_config()` (new helper in 3/5 to process configuration), `lazy_fetch_trusted` struct (new in 3/5 to track repository path and trust status), `fetch_objects()` (modified in 4/5 to pass recursion depth to child processes). The `GIT_INTERNAL_LAZY_FETCH_DEPTH` environment variable (introduced in 4/5) limits recursion depth to `MAX_LAZY_FETCH_DEPTH` (5), chosen to balance safety and legitimate nesting (e.g., `git fetch` invoking `index-pack` to lazily fetch REF_DELTA bases). The depth counter’s type is `int`, cast from `git_env_ulong()`, following Junio’s acceptance of this approach. The final patch (5/5) activates the mechanism by conditionally setting `GIT_NO_LAZY_FETCH=1` in `cmd_upload_pack()` only if the environment variable is unset and the repository is not in the allowlist, preserving operator control. Patch 1/5 introduces two observable behavioral changes: the `GIT_NO_LAZY_FETCH` check is now performed once up front (instead of once per promisor remote), and `promisor_remote_init()` is no longer called when lazy fetching is disabled, which is safe because downstream functions like `is_promisor_object()` do not need it in that case.
- New behavior: `uploadpack.lazyFetchTrusted` (protected configuration variable) allows server operators to mark repositories as trusted for lazy fetching, with recursion safeguards preventing infinite loops when a repository is configured as its own promisor remote. The configuration is read from protected files only, and only absolute paths are accepted (rejecting `.` and relative paths). Non-bare repositories must be allowlisted by their `.git` directory (e.g., `/srv/repo/.git` for `/srv/repo`). The callback-based allowlist design enables caller-specific validation rules: `uploadpack.lazyFetchTrusted` requires absolute paths, while `safe.directory` retains its existing behavior. Documentation now explicitly states that the configuration is multi-valued, specifies repository paths as git directories, warns against self-referential promisor remotes, and supports `~` and `%(prefix)` expansions. Tests verify recursion limits, path validation, and the server-side trust model’s security properties. Patch 4/5 adds the recursion depth counter (`GIT_INTERNAL_LAZY_FETCH_DEPTH`) to cap recursion at 5, addressing Junio’s v2 concern about recursion risks. The safeguard is internal and not user-configurable, with the depth counter incremented in `fetch_objects()` and checked in `lazy_fetch_objects()`. A new test in `t/t0410-partial-clone.sh` verifies the recursion safeguard by configuring mutual promisor remotes and confirming the fetch fails after 5 nested attempts.

Open questions and loose ends: The unresolved high-weight concerns remain: Junio’s scalability critique about memory overhead in `lazy_fetch_objects()` (holding missing object names in memory) and conceptual doubt about using a configuration variable for this purpose, along with brian m. carlson’s security objection, though both are mitigated by the server-side trust model. Junio’s review of 2/5 in v3 highlights a latent design issue in the existing `safe.directory` logic: the silent-ignoring of non-existent paths, which could mask configuration errors (e.g., unmounted filesystems) and lead to unintended trust decisions. This issue is inherited and not blocking, but it now risks propagating to `uploadpack.lazyFetchTrusted` if unaddressed. Christian acknowledges the concern but defers addressing it, citing the existing justification in commit dc0edbb01c, and proposes adding a `NEEDSWORK` comment in a follow-up patch to explore alternatives such as a warning (with a config option to suppress it) or deferred reporting (mentioning unresolvable entries only when the overall check fails). The depth limit of 5 in the recursion safeguard may require adjustment based on real-world use cases. No new substantive reviews have been posted since v4.

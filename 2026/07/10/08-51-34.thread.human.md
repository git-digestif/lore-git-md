This thread is about a patch series (v4) that replaces an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`) with a server-side mechanism, `uploadpack.lazyFetchTrusted`, allowing Git operators to explicitly mark repositories as safe for lazy fetching. The goal is to address security concerns—such as arbitrary code execution via lazy-fetch hooks—by shifting trust decisions to the server, modeled after Git’s `safe.directory` configuration.

The series is now technically complete, with all feedback from v3 addressed. The final patch (5/5) resolves Junio’s key critique about environment handling: instead of unconditionally setting `GIT_NO_LAZY_FETCH=1`, it now checks the environment first and only sets the variable if the operator hasn’t already done so, preserving their control. Other changes include reverting function return types to `int` for consistency, adjusting the recursion depth counter to `int`, and adding detailed documentation. Tests verify the allowlist mechanism, recursion safeguards, and path validation.

Junio’s lingering concerns—scalability (memory overhead in `lazy_fetch_objects()`) and the conceptual fit of using a configuration variable for this purpose—remain unresolved, as does brian m. carlson’s security objection. However, these are mitigated by the server-side trust model. Christian also acknowledges a latent issue in the existing `safe.directory` logic (silent-ignoring of non-existent paths) but defers addressing it, proposing a `NEEDSWORK` comment in a follow-up patch. The series is under review and not yet in `seen`, `next`, or `master`. No new substantive reviews have been posted since v4.

This thread is about a patch series (v4) by Christian Couder that replaces an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`) with a server-side mechanism, `uploadpack.lazyFetchTrusted`, to let operators mark repositories as trusted for lazy fetching. The goal is to address security concerns about untrusted repositories triggering arbitrary code execution via lazy-fetch hooks or configuration, shifting trust decisions entirely to the server operator.

The series is now in its fourth iteration, with all feedback from v3 addressed. The key change in v4 is the revised environment-handling logic in the final patch (5/5), which now checks the environment first and only sets `GIT_NO_LAZY_FETCH` if it isn’t already set by the operator, preserving operator control. Other v4 adjustments include reverting function return types from `bool` to `int` for consistency and switching the recursion depth counter from `unsigned long` to `int` (with a cast from `git_env_ulong()`), as Junio confirmed this was acceptable. Junio’s earlier critiques—API rigidity, recursion risks, and documentation ambiguities—are fully resolved in this version. The series remains under review, not yet in `seen`, `next`, or `master`, with CI tests passing.

The first patch in the series (1/5) is a pure refactoring of the promisor-remote subsystem, extracting lazy-fetching logic into a new helper function, `lazy_fetch_objects()`. This consolidates redundant environment checks and defers initialization until lazy fetching is actually attempted. The patch also adds detailed documentation for the new helper and the existing `try_promisor_remotes()`, addressing Junio’s request for clearer parameter semantics, though he may still want further precision. No behavior change is intended, and this patch is a clean candidate for early integration if the series stalls.

The unresolved high-weight concerns are Junio’s scalability critique (memory overhead in `lazy_fetch_objects()`) and conceptual doubt about using a configuration variable for this purpose, along with brian m. carlson’s security objection, though both are mitigated by the server-side trust model. Junio’s review of patch 2/5 also highlighted a latent design issue in the existing `safe.directory` logic (silent-ignoring of non-existent paths), which could propagate to `uploadpack.lazyFetchTrusted` if unaddressed. No new substantive reviews have been posted for v4.

This thread is about a patch series that replaces an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`) with a server-side mechanism, `uploadpack.lazyFetchTrusted`, allowing operators to explicitly mark repositories as trusted for lazy fetching. The goal is to address security concerns about untrusted repositories triggering arbitrary code execution via lazy-fetch hooks or configuration, shifting trust decisions entirely to the server operator.

The series is now at version 4, with all feedback from v3 addressed. The first patch in this version is a pure refactoring of `promisor-remote.c`, extracting lazy-fetching logic into a new helper function, `lazy_fetch_objects()`, while preserving existing behavior. Christian Couder has fully addressed Junio’s documentation feedback from v3 by rewriting the comment for `try_promisor_remotes()` to clarify its behavior, parameter semantics, and ownership rules. The patch also reverts to using `int` return types for consistency with existing conventions, aligning with Junio’s preferences. No functional changes are introduced, and the refactoring is uncontroversial, making it a candidate for early integration if the series stalls.

The series remains under review, with the key unresolved concerns being Junio’s scalability critique (memory overhead in `lazy_fetch_objects()`) and conceptual doubt about using a configuration variable for this purpose, along with brian m. carlson’s security objection. However, these are mitigated by the server-side trust model. The final patch activates the mechanism by conditionally setting `GIT_NO_LAZY_FETCH=1` in `builtin/upload-pack.c` only if the environment variable is unset and the repository is not in the allowlist, preserving operator control. The series includes recursion safeguards, path validation, and detailed documentation, with tests verifying the new behavior. No new substantive reviews have been posted since v4.

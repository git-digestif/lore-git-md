This thread is about Christian Couder’s patch series introducing `uploadpack.lazyFetchTrusted`, a server-side configuration to mark repositories as safe for lazy fetching. The series is now at v3, with v4 pending minor adjustments to patches 4/5 and 5/5. The core idea replaces an earlier client-side proposal with a server-controlled mechanism modeled after Git’s `safe.directory`, addressing security concerns about untrusted repositories triggering arbitrary code execution via lazy-fetch hooks.

All substantive feedback from Junio’s v2 review has been addressed: the API rigidity is resolved by a callback-based allowlist, stricter path validation in patch 3/5 enforces caller-specific rules, recursion risks are mitigated in 4/5 via an environment variable limiting depth, and documentation ambiguities in 5/5 are fixed. Junio’s latest reviews of v3 focus on mechanical details: he suggests using `int` instead of `unsigned long` for the recursion depth counter in 4/5, and Christian proposed a cast as a workaround, citing precedent. In this latest exchange, Junio confirms the cast is acceptable, noting Git already has many callers of `git_env_ulong()` that cast to smaller types without issue. This resolves the last open nit for 4/5, leaving only the environment-handling logic in 5/5 to tweak for v4. The series remains under review, not yet in Junio’s integration branches, with no new substantive objections since v3. The unresolved high-weight concerns—Junio’s scalability critique and conceptual doubt about using a configuration variable, along with brian m. carlson’s security objection—are mitigated by the server-side design but not fully resolved.

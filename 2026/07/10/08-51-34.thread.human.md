This thread is about a patch series (v4) by Christian Couder that introduces `uploadpack.lazyFetchTrusted`, a server-side configuration variable to mark repositories as trusted for lazy fetching. The goal is to address security concerns around untrusted repositories triggering arbitrary code execution via lazy-fetch hooks or configuration, shifting trust decisions entirely to server operators. The series replaces an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`) and is modeled after Git’s `safe.directory` mechanism.

All feedback from the v3 review has been addressed in v4, including Junio’s critiques about API rigidity, path validation, recursion safeguards, and documentation clarity. The final patch (5/5) resolves Junio’s environment-handling concern by preserving operator control while defaulting to safe behavior for untrusted repositories. Junio’s latest review of the final patch is positive, noting only minor documentation wording tweaks and praising the code’s clarity. The series is now technically complete and under review, though it remains in neither `seen`, `next`, nor `master`.

Two open questions linger: Junio’s unresolved scalability critique about memory overhead in `lazy_fetch_objects()` and a latent design issue in `safe.directory` (silent ignoring of non-existent paths), which risks propagating to `uploadpack.lazyFetchTrusted`. Christian has acknowledged the latter and proposed addressing it in a follow-up patch. The recursion depth limit (5) may also need adjustment based on real-world use. No other substantive reviews have been posted for v4, and the series awaits Junio’s integration decision.

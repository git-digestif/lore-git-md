This thread is about a patch series (v3) by Christian Couder that replaces an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`) with a server-side mechanism, `uploadpack.lazyFetchTrusted`, to let operators explicitly mark repositories as trusted for lazy fetching. The goal is to address security concerns about untrusted repositories triggering arbitrary code execution via lazy-fetch hooks or configuration, shifting trust decisions entirely to the server operator.

The series is now complete with this final patch, which activates the mechanism by setting `GIT_NO_LAZY_FETCH=0` when `upload-pack` serves a repository listed in the protected `uploadpack.lazyFetchTrusted` configuration. The patch includes thorough documentation and expands test coverage to verify the security model, recursion safeguards, and edge cases like self-referential promisor remotes. Earlier critiques from Junio—about API rigidity, recursion risks, and documentation ambiguities—have been addressed in this version, though his scalability concern (memory overhead in `lazy_fetch_objects()`) and conceptual doubt about using a configuration variable for this purpose remain unresolved, as does brian m. carlson’s security objection. Both are mitigated by the server-side trust model.

The series is under review and not yet in Junio’s integration branches (`seen`, `next`, or `master`). No new substantive reviews have been posted since v3, though the tests pass (except for an unrelated Debian 11 environment issue). The implementation leverages Git’s existing `safe.directory` mechanism and protected configuration infrastructure, and the recursion safeguards (via `GIT_INTERNAL_LAZY_FETCH_DEPTH`) prevent infinite loops when a repository is configured as its own promisor remote. The documentation clarifies that the configuration is multi-valued, requires absolute paths, and identifies repositories by their `.git` directory.

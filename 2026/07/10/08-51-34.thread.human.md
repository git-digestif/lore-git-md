This thread is about a patch series (v5) by Christian Couder that replaces the earlier `GIT_NO_LAZY_FETCH=fromAccepted` proposal with `uploadpack.lazyFetchTrusted`, a server-side configuration variable to mark repositories as trusted for lazy fetching. The goal is to address security concerns by shifting trust decisions to server operators, modeled after Git’s `safe.directory` mechanism.

The series is now fully reviewed, with all feedback from Junio’s prior critiques addressed. The latest exchange was a minor documentation clarification: Junio suggested phrasing to emphasize that the configuration specifies repositories *from which* lazy fetching is allowed, but Christian noted this could be misleading, as the server fetches objects *for* the configured repository via its promisor remotes. The v5 patch retains Junio’s preferred structure while avoiding the ambiguity. No substantive concerns remain, and the series is rebased on Git 2.56, passing CI tests. It remains under review, not yet in `seen`, `next`, or `master`.

Key technical aspects include a callback-based allowlist for trusted paths, recursion safeguards (limited to 5 nested fetches), and strict path validation. The series also refactors promisor-remote logic and consolidates environment checks. Open questions include a latent design issue in `safe.directory` (silent ignoring of non-existent paths) and the recursion depth limit, both flagged for follow-up. The only unresolved critique is Junio’s conceptual doubt about using a configuration variable, though this is mitigated by the server-side trust model. No other reviewers have raised objections in v4 or v5.

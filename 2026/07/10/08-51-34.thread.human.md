This thread is about a patch series (v5) by Christian Couder that replaces an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`) with a server-side mechanism, `uploadpack.lazyFetchTrusted`, to let operators mark repositories as trusted for lazy fetching. The goal is to address security concerns about untrusted repositories triggering arbitrary code execution via lazy-fetch hooks or configuration, shifting trust decisions entirely to the server operator.

The series is now under review, with all feedback from v4 addressed in v5. Junio’s final v4 review was entirely surface-level (documentation wording), and no substantive concerns remain. The series is rebased on Git 2.56 and passes CI tests but is not yet in Junio’s integration branches (`seen`, `next`, or `master`). The latest patch (4/5) adds a recursion safeguard to prevent infinite loops when a repository and its promisor remote are configured to lazy-fetch from each other. This is implemented via a depth counter (`GIT_INTERNAL_LAZY_FETCH_DEPTH`) capped at 5, with tests verifying the safeguard works as intended. The patch is clean and ready for integration if the series is accepted.

Key unresolved points include Junio’s lingering scalability critique about memory overhead in `lazy_fetch_objects()` and his conceptual doubt about using a configuration variable, though both are mitigated by the server-side trust model. A latent design issue in Git’s `safe.directory` mechanism—silent ignoring of non-existent paths—is now flagged with a `NEEDSWORK` comment and may be addressed in a follow-up. The series also builds on Git’s existing protected configuration infrastructure and is a candidate for early integration if the broader effort stalls. No other substantive reviews have been posted for v5.

This thread is about a patch series (v3) by Christian Couder that replaces an earlier client-side proposal (`GIT_NO_LAZY_FETCH=fromAccepted`) with a server-side configuration variable, `uploadpack.lazyFetchTrusted`. The goal is to let server operators explicitly mark repositories as safe for lazy fetching, addressing security concerns about untrusted repositories triggering arbitrary code execution via hooks or configuration. The series is under review and not yet merged.

The v3 patches fully address Junio’s earlier critiques on design, API rigidity, recursion risks, and documentation ambiguities. The current version introduces a callback-based allowlist for path validation, stricter path checks for the new configuration, recursion safeguards, and clearer documentation. However, Junio’s concerns about scalability (memory overhead in `lazy_fetch_objects()`) and the conceptual fit of using a configuration variable for this purpose remain unresolved, as does brian m. carlson’s security objection—though both are mitigated by the server-side trust model.

In the latest email, Junio reviews the first patch of the v3 series, focusing on documentation clarity. He flags a confusing phrase in the comment for `try_promisor_remotes()` and notes that the parameters (`remaining_oids` and `to_free`) have subtle, undocumented semantics. While he approves of the refactoring itself (removing redundant checks and unnecessary initialization), he asks for clearer documentation to avoid future confusion. This is a surface-level but substantive request—no design or correctness issues were raised, and the patch is otherwise ready for integration once the wording is fixed. No other reviews have been posted since v3.

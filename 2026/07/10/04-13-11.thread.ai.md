Thread identity: Patch series (single patch) introducing a bugfix for `--autosquash` behavior in `git rebase` when `fixup!`/`squash!` commits cancel out their target, resulting in empty commits. Originating author: Farid Zakaria. Thread type: bug report and fix.

Core problem or goal: Fix a long-standing edge case in the sequencer subsystem where `fixup!` or `squash!` commits that cancel out all changes in their target commit are not handled according to the `--empty` option (`drop`, `keep`, or `stop`). Currently, Git halts the rebase with an error instead of respecting the user's `--empty` configuration.

Current status: **Ready for merging** as of `v5`. The patch has evolved through five iterations, incorporating all substantive feedback from Phillip Wood. The `v5` addresses the final review concerns, including correctness fixes (e.g., `rewritten-pending` file handling), performance optimizations (e.g., unconditional `ALLOW_EMPTY` for non-final fixups), and additional test coverage. Phillip Wood's latest review (implied by the `v5` changes) confirms the patch is technically sound. No merge event to `master` or other integration branches has been reported; the series remains under review pending Junio's final approval.

Key technical details:
- **Files touched**: `sequencer.c` (core logic), `Documentation/git-rebase.adoc` (user-facing documentation), `t/t3415-rebase-autosquash.sh` (new test coverage), `t/t5407-post-rewrite-hook.sh` (additional test coverage).
- **Subsystems**: Sequencer (`--autosquash` logic), rebase.
- **New/renamed symbols**: `is_amended_head_empty()` (detects when applying a `fixup!`/`squash!` empties the target commit), `enum fixup_target` (tracks whether the target commit was originally picked with changes), `PICK_RESULT_DROPPED_HEAD` (signals when a commit is dropped due to being emptied), `rebase_path_fixup_target()` (persists state across rebase restarts).
- **Behavior changes**:
  - Introduces `is_amended_head_empty()` to detect when applying a `fixup!` or `squash!` empties the target commit, ensuring `--empty` is honored for such commits.
  - Only commits that *become* empty (not those picked empty to begin with) are subject to `--empty` handling, preserving existing behavior for workflows that rely on empty commits as placeholders.
  - When `--empty=drop` applies, the patch ensures the emptied commit is dropped by updating `HEAD` to its parent and cleaning up the `rewritten-pending` file, preserving mappings for `--update-refs` and other consumers.
  - Supports conflict resolution: if a user resolves a conflicted `fixup!` by undoing its target, the patch honors `--empty` for the resulting empty commit.
  - Only the final `fixup!` in a chain may drop the target commit, as dropping it earlier would cause subsequent fixups to be squashed into the wrong commit.
  - The last fixup in a chain now checks whether `HEAD` was emptied even if the fixup itself is dropped as already upstream.
  - `ALLOW_EMPTY` is set unconditionally for non-final fixups or under `--empty=keep`, reducing redundant checks.
  - `set_fixup_target_picked()` is shared with `skip_unnecessary_picks()` to avoid redundant lookups.
- **On-disk format changes**: Introduces a new on-disk state file (`$GIT_DIR/rebase-merge/fixup-target`) to track whether the target commit was originally picked with changes.
- **Test coverage**: Comprehensive tests in `t/t3415-rebase-autosquash.sh` cover all three `--empty` modes (`drop`, `keep`, `stop`) for `fixup!` and `squash!` scenarios, including edge cases like mid-chain fixups, root commits, conflict resolution, and already-empty targets. Additional coverage in `t/t5407-post-rewrite-hook.sh` ensures hooks are triggered correctly. Tests now use `test_commit` and `test_cmp` for clearer diagnostics.

Open questions and loose ends:
- The follow-up discussion about a potential `revert!` (or `drop!`) autosquash directive remains unresolved. Three competing designs are proposed:
  1. **Phillip Wood (original)**: Use an empty marker commit to represent the `revert!` directive, avoiding conflicts during rebase.
  2. **Yuxuan Chen**: Use an inverse patch (like `git revert`) to represent the `revert!` directive, prioritizing semantic clarity and consistency with existing Git commands. Conflicts during rebase would signal real difficulties in undoing the change.
  3. **Phillip Wood (new)**: A middle-ground proposal: a new `git revert --drop` option (or similar) that creates a commit containing the inverse patch *and* a `drop!` message. During `git rebase --autosquash`, the sequencer would replace the target commit’s `pick` with `drop` and discard the `drop!` commit itself. This avoids conflicts during rebase while reflecting the intended removal in the repository state before the rebase runs. Cites an open GitGitGadget issue as prior art for this idea.
- The trade-off between conflict avoidance (Phillip) and semantic consistency (Yuxuan) is the central point of contention, with no consensus reached.
- Phillip Wood notes two **unrelated but worth-fixing** inconsistencies in the existing codebase:
  - The behavior of `--empty=stop` differs depending on whether the target commit was originally empty or became empty via fixup. This is not a regression (the patch preserves existing behavior) but may warrant a separate cleanup.
  - The current code drops a `pick` even if it’s followed by fixups, which is a bug. The patch fixes this by deferring the drop decision until the end of the fixup chain.

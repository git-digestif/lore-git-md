This thread is about a regression in `git rebase` (and related operations) that causes fatal errors when commit graphs are enabled and submodule pointers are involved. The issue was bisected to commit `bb5da75d61`, which made `lookup_commit_reference_gently()` consult the commit graph but failed to account for submodule boundaries, leading to cross-repository object lookups.

Orestis Floros has posted a patch that fixes the issue by ensuring reachability functions like `can_all_from_reach()` parse commits in the correct repository. The patch propagates the `struct repository *` parameter through the call chain, preventing misinterpretation of commit-graph positions across repository boundaries. It includes a new test case in `t/t6437-submodule-merge.sh` that verifies the fix by merging branches with updated submodule pointers in a setup with separate commit-graphs for the superproject and submodule.

The patch is narrowly scoped and well-motivated, addressing the root cause without altering the core logic of the reachability functions. It aligns with the ongoing effort to eliminate implicit reliance on `the_repository` and should be uncontroversial for reviewers familiar with the commit-graph and submodule subsystems. No objections or open questions have been raised yet, and the fix appears to resolve the regression reported by Florian Schmidt. The next steps are likely review and integration into Junio’s queue. The workaround of disabling commit graphs (`core.commitGraph=false`) remains available for affected users until the fix is merged.

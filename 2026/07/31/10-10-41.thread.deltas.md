## 2026/08/26

- [2026/08/26/19-54-10 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano analyzed the proposed concurrency change, explaining that pull-request events would now use group `<workflow>-<pull-request-number>` (e.g., "main-workflow-42") so an updated PR shares a group with its predecessor, while other events would use `<workflow>-<commit-object-name>`, which differs from the original commit-hash-only grouping.
- [2026/08/26/19-54-10 by Junio C Hamano <gitster@pobox.com>] He flagged an unverified concern that if three or more workflows sharing the same concurrency group are triggered simultaneously for the same commit, there may be at most one active and one pending run in the group, potentially causing some workflows to fail to run on that commit; he noted this needs verification and should be added to the commit log if correct, or a revised description should explain why non-PR events are not negatively affected.
- [2026/08/26/19-54-10 by Junio C Hamano <gitster@pobox.com>] He noted that the original configuration did not specify `cancel-in-progress` so jobs did not cancel each other, whereas now pull-request events cancel an earlier run in the same group when a new one is triggered, while non-pull-request events default to false and thus have no regression.
- [2026/08/26/19-54-10 by Junio C Hamano <gitster@pobox.com>] He suggested that they might want two back-to-back pushes to cause CI to drop one of the runs on the same commit, but that this can be left as an independent issue.

## 2026/08/30

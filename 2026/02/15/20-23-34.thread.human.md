Orgad Shaneh has posted version 2 of a two-patch series fixing an inconsistency where `git fetch --prune-tags` prunes local tags missing from the remote but rejects changed tags with "would clobber existing tag", contrary to what the documentation promises. The series traces the problem to an oversight: the `--prune-tags` flag was added in 2018 before tag-clobbering protection landed later that year in Git 2.20, and the protection code never updated the prune-tags path. Patch 1/2 strengthens the test suite in `t/t5516-fetch-push.sh` to verify actual tag object updates via a new `check_child1_tag` helper and to cover `git fetch --force`; patch 2/2 modifies `builtin/fetch.c` to prepend a "+" force prefix to the implied `refs/tags/*:refs/tags/*` refspec when `--prune-tags` is active, so changed tags are updated rather than rejected. Version 2 specifically scopes the force behavior to the auto-following tag refspec only, avoiding a v1 bug where explicit refspecs were inadvertently forced when `fetch.pruneTags` was configured.

Junio C Hamano has questioned the historical intent behind the original behavior and whether the test coverage is sufficient, but has not yet issued a substantive ruling on whether the code should change to match the docs or vice versa. Ævar Arnfjörð Bjarmason, who originally implemented `--prune-tags`, has not yet weighed in to clarify whether the current no-force behavior was deliberate. The series remains under review with no integration status; it is awaiting either Junio's decision or input from Ævar or other fetch/tag experts before it can proceed.

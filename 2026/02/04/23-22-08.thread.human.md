This thread is about reorganizing Git’s experimental Rust code into a dedicated `rust/` subdirectory. Mike Hommey has posted the fourth version of his patch series, addressing all the mechanical feedback from the previous round: duplicate `.gitignore` and `Makefile` entries are fixed, the `Makefile clean` target now matches the relocated `Cargo.lock`, and the `meson.build` path error that broke the build has been corrected. The changes are purely structural—moving files and updating paths—with no functional impact, and the patch now appears ready for acceptance.

The broader goal is to improve project hygiene by avoiding a misleading top-level `Cargo.toml` and preventing Cargo from treating the entire Git repository as a single crate. This reorganization also supports downstream projects that vendor Git’s C code while excluding its Rust components, though the long-term solution for handling Git 3.0’s mandatory Rust components remains unresolved. Mike has proposed publishing the `gitcore` crate to crates.io as a way to manage mixed C/Rust dependencies post-Git 3.0, but this discussion is still open.

Junio C Hamano and Tuomas Ahola provided surface-level review feedback in earlier rounds, all of which has now been addressed. Brian M. Carlson raised concerns about forward-compatibility for downstream projects, but hasn’t yet responded to Mike’s crate-publishing proposal. With the mechanical issues resolved, the series is now technically sound, though the broader compatibility question will likely continue in parallel.

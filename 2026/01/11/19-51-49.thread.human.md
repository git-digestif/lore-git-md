This thread tackles two macOS-specific compatibility issues in Git, both now technically ready but with one facing unresolved architectural debate. The first, a two-patch series fixing an ISO-2022-JP iconv bug in utf8.c, is complete and awaits merging after addressing minor feedback. The second, Curtis Allen Smith's v4 patch series for a CRLF conversion size-trusting bug in read-cache.c, has drawn fresh scrutiny from Phillip Wood.

Curtis's series aims to prevent `git status` from incorrectly reporting modifications when clean filters or CRLF conversion alter file sizes without changing content. The v4 patch inlines the fix into `ie_modified()`, avoiding a helper function but maintaining the core logic: when a file's size changes and conversion is active, Git verifies whether the change reflects actual modification. While Curtis's benchmarks show negligible overhead in most cases, Phillip Wood's review raises two critical points. First, the fix affects more than `git status`—it impacts `git diff-files` and `git diff-index` too, and the commit message should clarify whether these commands benefit from avoiding unnecessary blob comparisons. Second, Curtis's proposed optimization to skip conversion and hashing when length mismatches already rule out a match may not work for files with blank lines, where CRLF conversion can dramatically alter size without meaningful content changes.

The architectural debate remains the series' biggest hurdle. Johannes Sixt argues the fix should target `git add` to ensure the index records the correct post-conversion size, while Curtis maintains the issue is a false positive in `git status`'s detection logic. Junio Hamano has no objections to the approach but remains concerned about performance trade-offs. With Phillip's review adding practical concerns about the optimization's correctness and the patch's broader implications, the series may need another iteration to address these questions before the community can settle the architectural direction.

This thread tackles two related macOS compatibility issues in Git, both now at critical review stages. The first, a two-patch fix for an ISO-2022-JP iconv bug in utf8.c, is technically complete and ready for merging after incorporating feedback from René Scharfe and Junio C Hamano. The second, Curtis Allen Smith’s five-iteration patch series addressing a CRLF conversion size-trusting bug in read-cache.c, has drawn fresh scrutiny from Junio, who flags potential performance risks in its unconditional approach.

Curtis’s v5 patch refines the fix to handle cases where external tools rewrite files with CRLF line endings after checkout, preventing false modification reports in commands like `git status` or `git rebase`. While earlier feedback from Phillip Wood and Torsten Bögershausen has been addressed—clarifying scope, simplifying tests, and quantifying performance impact—Junio’s latest review raises two new concerns. First, the patch might interfere with Git’s racy Git logic, which tolerates false positives for performance, particularly when `CE_MATCH_RACY_IS_DIRTY` is set. Second, the tests could inadvertently mask the bug by running too quickly, triggering racy conditions. The architectural debate remains unresolved: Johannes Sixt argues the fix should target `git add` to ensure correct size recording, while Curtis maintains it belongs in index refresh operations to correct false positives in `ie_modified()`.

The series is technically sound and well-tested, with negligible overhead in typical use cases, but Junio’s feedback suggests further refinement is needed to avoid disrupting Git’s performance trade-offs. Curtis will likely need to adjust the patch to respect racy Git conditions and justify its unconditional nature before the series can advance. Meanwhile, the utf8.c fix awaits final integration, having cleared all technical hurdles.

This thread tackles two related macOS compatibility issues in Git, both now at critical juncture. The first—a two-patch fix for an ISO-2022-JP iconv bug in utf8.c—is technically complete and ready for merging, with only platform-specific build-system detection remaining.

The second, more contentious effort addresses a CRLF conversion bug in read-cache.c that causes Git to misreport file modifications when clean filters or line-ending conversion alter file size without changing content. Curtis Allen Smith’s v5 patch series, incorporating feedback from Phillip Wood, Junio, Torsten Bögershausen, and Johannes Sixt, is well-tested and correct but remains stalled over where to place the conversion check. Four competing approaches are in play: Curtis’s v5 placement in `ie_modified()`, Johannes Sixt’s preference for fixing size recording during `git add`, Torsten’s proposal to move the check to `ie_match_stat()` to avoid racy Git interference, and Junio’s insistence that any solution must preserve the lstat()-based optimization that skips content comparisons for files whose sizes haven’t changed.

Torsten’s latest email proposes a follow-up optimization to Curtis’s v5, consolidating the conversion check within `ie_match_stat()` to eliminate redundant attribute lookups and avoid the double `would_convert_to_git()` call. This refinement reduces code size and improves efficiency but leaves the core architectural debate unresolved. Johannes Sixt’s objection—that the index’s recorded size is a cache of stat information, not a reflection of the blob’s size—remains unaddressed, as does Junio’s concern about the lstat() optimization. The series is now at a crossroads: the technical fix is sound, but the project’s performance and design priorities are in tension, and no hybrid approach has yet emerged that satisfies all reviewers.

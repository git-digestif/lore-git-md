This thread is about a platform-specific bugfix for Git’s CRLF conversion logic, specifically targeting a macOS issue where Git could miscalculate file sizes after character encoding conversions. The problem was originally identified by Curtis Allen Smith, and Torsten Bögershausen has now refined the patch to address it more robustly.

The core issue occurs in `read-cache.c` when Git performs encoding conversions during index operations. If the conversion alters the file size (e.g., due to encoding differences), Git currently trusts the new size without verifying whether the conversion succeeded. On macOS, this can lead to data corruption if the conversion buffer needs to grow, as the platform’s `iconv` implementation may lose state during resizing. The patch adds a 25-line change to `read-cache.c` that makes Git more cautious: it now checks whether conversion was active and, if so, avoids blindly trusting the post-conversion size. The fix is simpler than earlier iterations, removing a configuration switch in favor of an always-on approach, which the author believes is safe for all platforms.

The patch is still in RFC status, meaning it’s under active development and seeking feedback. While the technical approach appears sound—with thorough test coverage added to `t/t0020-crlf.sh`—the commit message is still rough ("bumpy," in the author’s words). The mailing list will likely focus on refining the message and possibly the exact conditions for the size check. This fix is related to, but distinct from, the earlier macOS `iconv` workaround series (which targeted `utf8.c` and build system detection), as it addresses a separate but adjacent issue in character encoding conversion. The patch is narrowly scoped and well-motivated, but its RFC status means it’s not yet ready for merging.

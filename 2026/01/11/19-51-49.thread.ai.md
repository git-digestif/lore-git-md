Thread identity: Two distinct but related platform compatibility efforts targeting macOS character encoding and line-ending conversion issues. The first is a completed two-patch series addressing an ISO-2022-JP iconv bug in utf8.c. The second is a patch series from Curtis Allen Smith (curtis.allen.smith@gmail.com) refining work on a CRLF conversion size-trusting bug in read-cache.c, affecting macOS and other environments where tools rewrite files with CRLF line endings. The series is now at v5, with Curtis incorporating feedback from Phillip Wood, Junio C Hamano, Torsten Bögershausen, Johannes Sixt, and the latest substantive review from Junio on v5.

Core problem: macOS's ecosystem exhibits two distinct flaws during file processing:
1. In ISO-2022-JP to UTF-8 conversion (utf8.c), buffer growth during conversion loses internal state, corrupting output.
2. In CRLF conversion (read-cache.c), Git blindly trusts the reported post-conversion file size without verifying conversion success, causing commands that refresh the index (e.g., `git status`, `git rebase`, `git pull --rebase`, `git update-index --refresh`) to incorrectly report modifications when clean filters or CRLF conversion alter file size without changing content. The architectural debate centers on whether the index's recorded size is a cache of stat information (and thus should be corrected during `git add`) or whether the fix should target index refresh operations to handle cases where external tools rewrite files after checkout.

Key technical details:
- utf8.c series: State preservation during buffer growth when ICONV_RESTART_RESET enabled; Makefile macros HAS_GOOD_LIBICONV/NEEDS_GOOD_LIBICONV for automatic detection.
- read-cache.c series: v5 adds 4 lines to `ie_modified()` (introducing `ce_modified_check_fs()` and calling `would_convert_to_git()` when size changes occur) and 45 lines of new tests in `t/t0020-crlf.sh` covering CRLF rewrites, lone-CR edge cases, and commands that refresh the index. The fix is unconditional (no configuration switch), preserves existing behavior for non-converted files, and handles edge cases like lone-CR rewrites. Benchmark data shows negligible overhead in realistic scenarios (12 microseconds per modified 2.6 KB file) but measurable costs in extreme cases (e.g., 138ms for 10,000 modified files). The patch affects all commands that refresh the index (e.g., `git status`, `git rebase`, `git pull --rebase`, `git update-index --refresh`) but does not directly change `git diff-files` or `git diff-index` (which use `ie_match_stat()`). Test design simplified in v5 to avoid separate repositories, aligning with existing `t/t0020-crlf.sh` patterns. Junio's review highlights two new risks: (1) the patch may interfere with code paths that tolerate false positives for performance (e.g., where `CE_MATCH_RACY_IS_DIRTY` is set), and (2) the tests may inadvertently trigger racy Git conditions, masking the bug they aim to catch.

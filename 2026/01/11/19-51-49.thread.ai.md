Core problem: macOS's ecosystem exhibits two distinct flaws during file processing:
1. In ISO-2022-JP to UTF-8 conversion (utf8.c), buffer growth during conversion loses internal state, corrupting output.
2. In CRLF conversion (read-cache.c), Git blindly trusts the reported post-conversion file size without verifying conversion success, causing commands that refresh the index (e.g., `git status`, `git rebase`, `git pull --rebase`, `git update-index --refresh`) to incorrectly report modifications when clean filters or CRLF conversion alter file size without changing content. The architectural debate now revolves around reconciling correctness, performance, and racy Git avoidance.

The fix is unconditional (no configuration switch), preserves existing behavior for non-converted files, and handles edge cases like lone-CR rewrites. Benchmark data shows negligible overhead in realistic scenarios (12 microseconds per modified 2.6 KB file) but measurable costs in extreme cases (e.g., 138ms for 10,000 modified files). Junio's latest review highlights that the current approach risks eliminating the lstat()-based optimization, which skips content comparisons for files whose sizes haven't changed—a long-standing performance trade-off that the project is reluctant to regress.

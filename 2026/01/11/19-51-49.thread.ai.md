Core problem: macOS's ecosystem exhibits two distinct flaws during file processing:
1. In ISO-2022-JP to UTF-8 conversion (utf8.c), buffer growth during conversion loses internal state, corrupting output.
2. In CRLF conversion (read-cache.c), Git blindly trusts the reported post-conversion file size without verifying conversion success, causing commands that refresh the index (e.g., `git status`, `git rebase`, `git pull --rebase`, `git update-index --refresh`) to incorrectly report modifications when clean filters or CRLF conversion alter file size without changing content. The architectural debate now revolves around three competing approaches: (a) Curtis's original placement in `ie_modified()`, (b) Johannes Sixt's preference for fixing the size recording during `git add`, and (c) Torsten's proposal to move the check to `ie_match_stat()` to avoid racy Git interference. Junio's latest review introduces a fourth dimension: the performance cost of unconditionally triggering content comparisons, which risks regressing the lstat()-based optimization that avoids unnecessary work for unchanged files.

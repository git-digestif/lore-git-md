Thread identity: Two distinct but related platform compatibility efforts targeting macOS character encoding and line-ending conversion issues. The first is a completed two-patch series addressing an ISO-2022-JP iconv bug in utf8.c. The second is a patch series from Curtis Allen Smith (curtis.allen.smith@gmail.com) refining work on a CRLF conversion size-trusting bug in read-cache.c, affecting macOS and other environments where tools rewrite files with CRLF line endings. The series is now at v4, with Curtis reasserting ownership after Torsten Bögershausen's v3.

Core problem: macOS's ecosystem exhibits two distinct flaws during file processing:
1. In ISO-2022-JP to UTF-8 conversion (utf8.c), buffer growth during conversion loses internal state, corrupting output.
2. In CRLF conversion (read-cache.c), Git blindly trusts the reported post-conversion file size without verifying conversion success, causing `git status` to incorrectly report modifications when clean filters or CRLF conversion alter file size without changing content. The architectural debate centers on whether the index's recorded size is a cache of stat information (and thus should be corrected during `git add`) or whether the fix should target `git status` to handle cases where external tools rewrite files after checkout.

Current status:
- First series (utf8.c): v2 complete, technically ready for merging. Implements ICONV_RESTART_RESET workaround with build system detection for Homebrew/MacPorts/Fink libiconv.
- Second series (read-cache.c): v4 posted by Curtis. The patch inlines the fix directly into `ie_modified()`, removing the helper function introduced in v3. The core logic remains unchanged: when a file's size changes and conversion is active, Git falls through to `ce_modified_check_fs()` to verify whether the size change reflects actual modification. The series is technically clean and ready for review, though its architectural premise remains contested.

Key technical details:
- utf8.c series: State preservation during buffer growth when ICONV_RESTART_RESET enabled; Makefile macros HAS_GOOD_LIBICONV/NEEDS_GOOD_LIBICONV for automatic detection.
- read-cache.c series: v4 adds 4 lines to `ie_modified()` and 45 lines of new tests in `t/t0020-crlf.sh` covering CRLF rewrites and lone-CR edge cases. The fix is unconditional (no configuration switch), preserves existing behavior for non-converted files, and handles edge cases like lone-CR rewrites. Benchmark data shows negligible overhead in most cases: a clean tree pays nothing, and a tree without conversion pays only one attribute lookup per size-changed file. Overhead becomes noticeable only when conversion is active *and* the file is genuinely modified or rewritten (e.g., 25ms → 137ms for 10,000 files), with a follow-up optimization reducing this to 57ms by skipping conversion and hashing when the length already rules out a match.

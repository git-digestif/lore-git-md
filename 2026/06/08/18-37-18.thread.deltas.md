## 2026/07/27

- [2026/07/27/13-07-24 by Toon Claes <toon@iotcl.com>] Toon Claes responded to Elijah Newren's proposal to error on multiple positive refs as an interim step, stating he appreciates the openness but wants to understand the end goal better before continuing.
- [2026/07/27/13-07-24 by Toon Claes <toon@iotcl.com>] Toon Claes explained that he is adding `--linearize` mostly to scratch his own itch: performing a server-side non-interactive rebase identical to `git-rebase(1)`'s `--no-rebase-merges`, and guessed that properly replaying merges would be far more useful to most people than `--linearize`.
- [2026/07/27/13-07-24 by Toon Claes <toon@iotcl.com>] Toon Claes argued that v7's `--linearize` can make commits reachable from a branch where they were not before, giving a concrete example where `git replay --linearize --onto master branchA branchB branchC` would cause branchC to reach branchB's commits and branchA to contain both branchB and branchC, which he identified as an ordering problem he personally considers more significant than Elijah did.
- [2026/07/27/13-07-24 by Toon Claes <toon@iotcl.com>] Toon Claes noted that while `git-replay(1)` only accepts a single revision range, v7's `--linearize` effectively converts distinct ranges into a single connected set of commits, which makes the option name "linearize" not very good.
- [2026/07/27/13-07-24 by Toon Claes <toon@iotcl.com>] Toon Claes agreed with Elijah Newren's reasoning that erroring out now is preferable because turning an error into working behavior later never breaks anyone, whereas merging the current concatenation semantics risks users depending on them.
- [2026/07/27/13-07-24 by Toon Claes <toon@iotcl.com>] Toon Claes raised the same reachability issue for `--contained`, showing that it would cause branchC to suddenly contain branchB's commits, and proposed that `--contained` should not be allowed with `--linearize`.
- [2026/07/27/13-07-24 by Toon Claes <toon@iotcl.com>] Toon Claes proposed that `--ref` should perhaps be required when `--linearize` is given, so that a command like `git replay --onto master branchA branchB branchC --ref branchA` produces an unambiguous result: all commits reachable from the three branches are replayed linearly onto master and only ref `branchA` is updated.

Here’s the human-readable summary for a developer catching up on the thread:

This thread proposes two worktree improvements by Jason Newton: copy-on-write (reflink) support for faster worktree creation, and automatic cleanup of ephemeral branches when worktrees are removed. The series is now at v3, with four patches under active review.

The reflink feature allows worktrees to be created using filesystem-level copy-on-write on supported platforms (Linux btrfs/XFS/bcachefs, macOS APFS), avoiding the overhead of full checkouts. Windows ReFS support was permanently disabled in v3 due to a known silent corruption bug (Git LFS #6312, build 26200). The implementation is opt-in via `--reflink` or `worktree.reflink` config, a design choice contested by Eric Sunshine, who argues it should default to automatic for tracked files (where the untracked-file copying concern doesn’t apply). The feature degrades gracefully on unsupported filesystems and handles edge cases like dirty worktrees and untracked files.

The second feature, ephemeral branch reaping, automatically deletes branches created by `git worktree add` when the worktree is removed. This addresses a long-standing cleanup nuisance but remains controversial. Eric Sunshine objects that the feature is redundant given the existing `--detach` flag and risks disrupting workflows. Jason counters that ephemeral branches are more ergonomic than detached HEADs, as they behave like normal branches (supporting `git status`, `git push`, etc.) while the worktree exists. The reaping mechanism is narrowly scoped: it only applies to branches auto-created by DWIM (the final component of `<path>`), and only when the worktree was created by the same Git version. Explicitly named branches (`-b/-B`), pre-existing branches, and detached HEADs are never reaped. Users can preserve commits by creating a normal branch or using `--keep-branch`.

The v3 revision also includes a build-system fix for Windows compatibility and adds warnings for `--reflink` usage on Windows. The series has extensive test coverage and documentation updates, but key questions remain: whether reflink should default to automatic for tracked files, whether ephemeral branch reaping should be opt-in or removed, and how the features interact with existing tooling. The thread is still under review, with no maintainer decision yet.

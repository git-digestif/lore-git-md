This thread is about a proposed feature to improve `git worktree` with two main enhancements: copy-on-write (CoW) worktree creation via `--reflink` and automatic cleanup of ephemeral branches. The series is now at version 3, consisting of four patches, and is under active review.

The first major feature, `--reflink`, allows worktrees to be created using filesystem-level CoW links on supported platforms (Linux btrfs/XFS/bcachefs, macOS APFS), avoiding the overhead of full checkouts. This is implemented via cross-platform primitives in `copy.[ch]` and is configurable via a new `--reflink` flag or `worktree.reflink` config option. However, Windows ReFS support has been permanently disabled due to a known silent corruption bug (Git LFS #6312), and the feature remains contested: Eric Sunshine argues that CoW should be the default for tracked files, where the untracked-file copying concern doesn’t apply, rather than requiring explicit opt-in.

The second feature, ephemeral branch reaping, automatically deletes branches created by `git worktree add` when the worktree is removed. This addresses a long-standing cleanup nuisance but is also disputed by Eric Sunshine as redundant (given the existing `--detach` flag) and disruptive to workflows that rely on auto-created branches. The feature unconditionally deletes ephemeral branches, even if they contain unmerged commits, which remains a sticking point.

Key participants include Jason Newton (the author), who has implemented the cross-platform reflink support and ephemeral branch reaping, and Eric Sunshine, who has raised substantive objections to both features. Junio Hamano and brian m. carlson have also weighed in, with Junio questioning the opt-in design in earlier versions and brian highlighting the Windows ReFS corruption risk, which has since been addressed by disabling reflink on Windows. The macOS `clonefile()` path has been validated in CI, resolving earlier testability concerns.

The series is still under review, with open questions about whether reflink should be the default for tracked files, whether ephemeral branch reaping should be opt-in or removed entirely, and how to document the limitations (e.g., overlayfs incompatibility, Windows ReFS corruption risk). The v3 revision has addressed the immediate technical blockers but leaves the broader design debates unresolved.

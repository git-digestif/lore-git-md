## 2026/06/05

- [2026/06/05/18-49-26 by Jason Newton via GitGitGadget <gitgitgadget@gmail.com>] Jason Newton posted a two-patch series proposing `git worktree add --reflink` for copy-on-write worktree creation and allowing a branch to be checked out in multiple worktrees, reporting a benchmark on a Linux-kernel fork (btrfs) where normal adds allocate ~0.9 GB real disk per worktree while --reflink allocates ~0.
- [2026/06/05/18-49-27 by Jason Newton via GitGitGadget <gitgitgadget@gmail.com>] Jason Newton added the `--reflink` option to `git worktree add`, which on copy-on-write filesystems populates the new worktree by reflinking the current worktree's files and index via a new `reflink_file()` helper (FICLONE on Linux, clonefile() on macOS), falling back to a normal checkout when unsupported, with `worktree.reflink` config (true/false/auto) and `--no-reflink` override.
- [2026/06/05/18-49-28 by Jason Newton via GitGitGadget <gitgitgadget@gmail.com>] Jason Newton changed `git worktree add` to permit checking out a branch already checked out in another worktree, replacing the blanket `die_if_checked_out()` check with `die_if_branch_busy()` which still refuses branches mid-rebase or mid-bisect.
- [2026/06/05/19-59-41 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson noted that Windows ReFS supports CoW (referencing Git LFS code), asked how `--reflink` handles a dirty source worktree (whether the destination would have stale files) and requested this be explained in the commit message, asked how two worktrees sharing a branch avoid one reverting the other's commits, and suggested an alternative of creating many refs pointing to the same object ID, proposing a FAQ entry or manual edit if that approach is valuable.

## 2026/10/20

- [2026/10/20/16-04-07 by Jason Newton via GitGitGadget <gitgitgadget@gmail.com>] Jason Newton posted v2 of the two-patch series "worktree: copy-on-write creation and ephemeral branches", adding `git worktree add --reflink` and ephemeral-branch reaping by `git worktree remove`, including a ReFS block-cloning arm for Windows and a `worktree.reflink` configuration.
- [2026/10/20/16-04-08 by Jason Newton via GitGitGadget <gitgitgadget@gmail.com>] Jason Newton submitted patch 1/2 implementing `--reflink`: on copy-on-write filesystems it reflinks the source worktree's files and index then runs `git reset --hard` so only paths differing from `<commit-ish>` are rewritten; uncommitted tracked changes do not leak because the index refresh re-validates by content; unsupported filesystems fall back to a normal checkout.
- [2026/10/20/16-04-09 by Jason Newton via GitGitGadget <gitgitgadget@gmail.com>] Jason Newton submitted patch 2/2 implementing ephemeral-branch reaping: a branch auto-created by `worktree add` is recorded in `worktrees/<id>/owned-branch` and deleted by `worktree remove` (even with unmerged commits); branches named with `-b`/`-B` or pre-existing are never owned; `--keep-branch` preserves an owned branch; `git branch -m` updates the ownership marker.
- [2026/10/20/21-20-14 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson stated the Windows ReFS implementation is defective due to a known corruption bug in Git LFS (issue #6312) and should be skipped on Windows unless a fixed Windows version can be guaranteed; he also asked whether macOS `cp` supports `--reflink=always` so the APFS path would be exercised in CI.

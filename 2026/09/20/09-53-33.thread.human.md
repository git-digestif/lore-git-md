This thread is about a user-experience improvement for shallow clones: when a user tries to access an ancestor not present locally via `<rev>~N` or `<rev>^N` syntax, Git currently emits a generic error with no hint that the operation was limited by the shallow boundary. Harald Nordgren’s patch (v3) adds an advice message that explains the shallow boundary, why the operation failed, and suggests the exact `git fetch --deepen=<n>` command needed to resolve it. The patch is technically ready—it addresses all prior feedback, touches the right files, and includes thorough test coverage—but it has been stalled for weeks due to a lack of reviewers.

Junio has explicitly warned that unless someone steps forward to review it in the next few weeks, he will drop the patch from his integration branches. The advice for failing syntax is uncontroversial, and no substantive objections remain, but the thread has become a microcosm of the project’s broader review bottleneck. Harald’s latest email shifts the discussion to process, proposing two concrete ideas: loosening review requirements for non-critical code (letting CI handle tests, leaks, and linting) and offering to trade reviews with other contributors. Kristoffer Haugsbakk had earlier framed the bottleneck as a structural issue, and Harald’s reply leans into that framing with a pragmatic, collaborative tone—but so far, no reviewer has taken the bait, and the patch’s fate remains uncertain.

The patch itself is narrow and focused: it only advises on explicit `<rev>~N`/`<rev>^N` syntax that fails to resolve, avoiding the flawed `git log` integration that was dropped in v2. The advice is context-aware, auto-detects the remote and branch, and suppresses itself in non-shallow repos or when Git is running quietly. A small edge case—whether the advice for `<rev>^N` should suggest `--deepen=1` when all parents share the same depth—remains unresolved, but Junio’s feedback on this point was more of a question than an objection. For now, the patch is in limbo, caught between technical readiness and the project’s chronic shortage of review bandwidth.

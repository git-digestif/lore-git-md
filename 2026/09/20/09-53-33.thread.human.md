This thread began with Harald Nordgren’s patch to add helpful advice when users in shallow clones hit history limits—either via explicit `<rev>~N`/`<rev>^N` syntax that fails, or commands like `git log -20` that silently truncate output. The v2 patch expanded the scope to cover both cases, but Junio C Hamano’s latest review has thrown a wrench into the plan.

Junio identified a critical flaw in how the patch detects shallow boundaries: it only triggers advice when the *last commit shown* is itself shallow, missing cases where the walk stops because a *parent* of a shown commit is missing. In his example, a shallow clone might show commits `g` through `a` but stop at `b` because its parents are hidden—yet the advice never appears because `a` is a genuine root. This makes the advice unreliable, sometimes appearing and sometimes not for the same underlying problem. As a result, Junio has retracted his earlier suggestion to cover silent truncation in `git log` and now considers the current implementation counter-productive.

The `<rev>~N`/`<rev>^N` advice for failing syntax remains uncontroversial and may still be viable, but the `git log` integration needs a rethink. Harald will need to devise a way to reliably detect when a walk stops *because of* a shallow boundary, not just when it stops *at* one. Until then, the patch’s future is uncertain—though the core idea of helping users understand shallow history limits still has support. D. Ben Knoble’s earlier feedback about documentation clarity (using `<rev>` instead of `<ref>`) and Junio’s lingering questions about `<rev>^N` coverage also remain unresolved.

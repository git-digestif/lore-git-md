This is the third and final patch in Maciej Ciemborowicz’s v2 series fixing the regression in the `reference-transaction` hook when branches, tags, or remote refs are deleted. The patch updates `git fetch --prune` and `git remote prune` to retain and pass the resolved old OIDs to the deletion transaction, ensuring the hook receives meaningful values (the old OID followed by all-zeros) instead of all-zero OIDs. This restores the pre-regression behavior from Git 2.28–2.30 while preserving the performance gains of the original optimization.

The change is straightforward: `get_stale_heads()` already records the current OID of each stale ref in its `new_oid` field, but the pruning code previously discarded this value and requested unconditional deletion. The patch carries these OIDs into the deletion transaction, making deletions conditional (compare-and-delete) and preventing the prune operation from silently overwriting refs updated by another process after the stale scan. This safety check is the same trade-off documented in the earlier patches: it may cause prune failures in the presence of concurrent updates, but the author argues this is the desirable behavior to avoid data loss. The patch also suppresses the "[pruned]" status message when a non-atomic prune fails its old-OID check, fixing a UI inconsistency.

The implementation is clean and efficient, reusing data already collected during the stale ref scan without additional ref reads. It introduces a new `stale_ref` struct in `builtin/remote.c` to carry both the ref name and old OID, and updates the pruning logic in both `builtin/fetch.c` and `builtin/remote.c` to pass the OIDs to `refs_delete_refs()`. The patch includes comprehensive test coverage in `t/t1416-ref-transaction-hooks.sh`, verifying that the hook receives the correct old OIDs for remote ref deletions, that concurrent updates are preserved, and that the UI behaves consistently (no "[pruned]" output on failure).

This patch completes the series, addressing all known affected commands (`git branch -d`, `git tag -d`, `git remote prune`, and `git fetch --prune`). The series is well-motivated, with clear commit messages, thorough test coverage, and no performance regression. The only remaining open question is whether the project accepts the intentional race condition trade-off (safety via conditional deletion) or prefers unconditional deletion, but the v2 series frames this as a deliberate choice to restore the pre-regression safety check. The patches look ready for merging pending resolution of that discussion.

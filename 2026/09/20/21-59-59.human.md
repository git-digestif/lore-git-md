This is a **surface-level review** of Harald Nordgren’s patch that adds advice for shallow history in `<ref>~N` and `<ref>^N` lookups. The reviewer, D. Ben Knoble, raises a narrow but important point about clarity in the documentation and commit message.

The patch itself is a well-motivated usability fix: when a user in a shallow clone tries to access an ancestor that isn’t present locally, Git currently emits a generic “is not a commit” error. The new advice (`advice.shallowHistory`) explains that the repository is shallow, why the operation failed, and suggests the exact `git fetch --deepen=<n>` command needed to resolve it. The implementation is careful—it only triggers when the walk stops exactly at a recorded shallow boundary, avoiding false positives, and provides context-aware suggestions (e.g., accounting for existing depth when calculating `--deepen` values).

Knoble’s feedback focuses on wording precision. The commit message and documentation use “ref” and “~N”/“^N” loosely, which could confuse readers. The `~N` and `^N` syntax works with any *commit-ish* (e.g., commit hashes, tags, or refs), not just refs, and the documentation should reflect that by using the standard `<rev>~<n>` and `<rev>^[<n>]` notation from `gitrevisions(7)`. Knoble also questions whether the feature should be restricted to refs (since unshallowing via `fetch` requires a ref to target), though this is more of an observation than a demand for change.

The review is surface-level—it doesn’t engage with the code’s correctness, edge cases, or broader design—but it’s a valid nit. The patch is otherwise complete, with thorough test coverage and a clear rationale, and this feedback is unlikely to derail it. If addressed, it would make the documentation and commit message more precise without altering the patch’s behavior.

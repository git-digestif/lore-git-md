# Git mailing list daily digest for 2026/09/20

## The day in brief
Maciej Ciemborowicz posted a v2 series teaching `refs_delete_refs()` to carry old OIDs into batched ref deletions so branch, tag, and fetch prune operations become compare-and-delete, plus a separate patch routing reference copy and rename through the transaction API so the `reference-transaction` hook observes them. Haokai Ding's `diff --no-index -R` file/directory conflict fix collected two reviews.

## Notable threads

### refs: report old OIDs for batched deletions
This is a change to the refs core code: `refs_delete_refs()` currently passes zero as both the old and new OID to the reference-transaction hook when branch, tag, fetch, and remote delete refs in batches, even though those callers already know the values they selected for deletion. Maciej Ciemborowicz's v2 series adds an optional `oid_array` parameter to `refs_delete_refs()` and passes each non-null OID to `ref_transaction_delete()`, which makes the deletion conditional and fails the transaction if the ref changed after the caller resolved it. For branch and tag this restores the compare-and-delete race protection that existed before 8198907795 converted them to batched deletion; for pruning it prevents a stale scan from deleting a ref updated by another process. The v2 cover letter states the changes since v1: documenting the conditional deletion behavior and its race protection, adding tests that update refs from the hook's preparing phase and verify branch deletion and remote pruning preserve the concurrent update, avoiding printing deletion status when a non-atomic prune fails, and using a local `string_list_item` in `refs_delete_refs()`. The series adds no ref reads and retains batched performance.

### refs: run copy and rename through transactions
This patch changes the refs code so that reference copy and rename operations go through the transaction API instead of bypassing it, which today leaves the reference-transaction hook seeing only the source deletion with the files backend and no useful update with the reftable backend. Maciej Ciemborowicz represents a rename as a deletion of the old reference plus creation of the new reference in the same transaction, retains backend-specific reflog handling, suppresses hooks for the files backend's nested deletion transactions so callers observe one logical transaction, and records and verifies source and destination values after taking backend locks so concurrent changes are rejected rather than applied. It also preserves D/F renames, restores overwritten references and reflogs when a prepared hook rejects the operation, and adds tests covering rename, copy, forced updates, both directions of D/F conflicts, concurrent updates, and prepared-hook rollback.

### diff --no-index: fix -R with file/directory conflicts
This is a bugfix in the diff machinery: when a path is a file on one side and a directory on the other, `queue_diff()` queues the file separately before recursing into the directory, and that early queue entry bypasses the `reverse_diff` handling used for ordinary files, so `git diff --no-index -R` reports both paths as deleted, or both as added when the operands are reversed. Haokai Ding's patch swaps the filespecs of the early queue entry when `reverse_diff` is set and adds regression tests for both directions. René Scharfe reviewed it with "Good find!" and "Looks good. I like the explicit exit code expectation.", and Jacob Keller added a Reviewed-by trailer.

## In brief
- Harald Nordgren posted a patch adding a `shallowHistory` advice that fires when `<ref>~N` or `<ref>^N` resolution stops at a shallow boundary, suggesting `git fetch --deepen=<n>` (the exact remaining depth for `~N`, always 1 for `^N`) and naming the remote and branch when the ref looks like `<remote>/<branch>`; D. Ben Knoble suggested restricting the feature to refs only and documenting the syntax as `<rev>~<n>` and `<rev>^[<n>]`.
- Maciej Ciemborowicz proposed an RFC adding native hooks for worktree lifecycle events (add, remove, move, lock, unlock, prune), since tools such as git-hooks-ext currently must wrap `git worktree` or compare `git worktree list --porcelain` output before and after; he asked whether a single hook like `reference-transaction` or separate post-operation hooks fit better, and whether a stable worktree identifier should be exposed in addition to the path. Kristoffer Haugsbakk pointed to an existing discussion on the topic.
- Johannes Schindelin's four-patch series fixing the cargo invocation in the GitLab CI Windows jobs saw the `build:mingw64` job succeed, though he noted it should probably be renamed `build:ucrt64`, while `build:msvc-meson` timed out on a credentials step.

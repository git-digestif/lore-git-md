This is a **bugfix follow-up** addressing a **substantive review concern** in the reference-transaction hook regression series. The author, Maciej Ciemborowicz, acknowledges Karthik Nayak’s race condition feedback and clarifies the intended behavior: the patch deliberately changes deletions from unconditional to compare-and-delete to prevent deleting refs that were never examined by the caller. This restores the pre-regression safety check (from Git 2.28–2.30) where `delete_ref()` was passed the resolved OID. Maciej argues the failure mode is desirable—it prevents concurrent updates from being silently overwritten—and provides a reproduction case: a hook that modifies the branch during the "preparing" phase causes the current Git to succeed (deleting the updated ref), while the patched version fails the old-OID check, preserving the new value. The same check also prevents `git fetch --prune` from deleting refs updated after the stale scan. For v2, Maciej plans to document this behavior change in commit messages, add a regression test for concurrent updates, and fix a UI inconsistency where `git remote prune` prints "[pruned]" even after a deletion failure. The response also accepts Karthik’s minor readability suggestion (using a local loop variable). The core technical trade-off—safety via conditional deletion versus unconditional deletion—remains unresolved but is now explicitly framed for discussion. Key details for follow-up: the race condition is reproducible, the failure mode is intentional, and the v2 series will include tests and documentation clarifying the new behavior.

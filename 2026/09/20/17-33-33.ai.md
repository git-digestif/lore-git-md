This is an RFC proposing new worktree lifecycle hooks. The author, Maciej Ciemborowicz, suggests adding native Git hooks for worktree operations (`add`, `remove`, `move`, `lock`, `unlock`, `prune`) to replace the current indirect detection via `post-checkout` or external wrappers. The motivation is to enable tools like `git-hooks-ext` to observe worktree changes without wrapping `git worktree` or diffing `git worktree list --porcelain` output.

Two design options are presented: separate post-operation hooks (e.g., `post-worktree-add`) or a unified `worktree-lifecycle` hook (similar to `reference-transaction`) that reports events like `add <path>`, `remove <path>`, etc. The author leans toward the latter for operations like `prune` that affect multiple worktrees at once and notes that veto hooks are unnecessary for their use case. The email also asks whether a stable worktree identifier (beyond the path) should be exposed.

The proposal is well-motivated with a clear use case and avoids over-engineering (e.g., veto hooks). The unified hook design seems more flexible and aligns with Git’s existing `reference-transaction` pattern. The question of a stable identifier is relevant, as paths can change (e.g., during `move` or `repair`). No prior work or ongoing efforts are mentioned, but this would complement the broader hook subsystem improvements (e.g., Adrian Ratiu’s config-based hooks).

This is likely to generate discussion about hook design, backward compatibility, and whether the feature belongs in core Git or should remain a wrapper concern. The author’s focus on post-operation hooks (rather than pre-operation or veto hooks) may reduce controversy. Key files touched would include `builtin/worktree.c`, `hook.c`, and documentation. Test coverage would need to verify hook invocation for all worktree commands, including edge cases like `prune`.

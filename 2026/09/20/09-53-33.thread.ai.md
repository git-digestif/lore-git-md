Thread identity
Subject: [PATCH] rev-parse: add advice for shallow history in <rev>~N and <rev>^N
Series version: single patch (v1 under review; v2 likely)
Originating author: Harald Nordgren
Thread type: bugfix / user-experience improvement

Core problem or goal
When a user in a shallow clone attempts to use `<rev>~N` or `<rev>^N` to access an ancestor not present locally, Git emits a generic “is not a commit” error. The patch adds a new advice (`advice.shallowHistory`) that explains the shallow boundary, why the operation failed, and suggests the exact `git fetch --deepen=<n>` command needed to resolve it.

Current status
Under review; no prior versions. Junio C Hamano’s review accepts the technical implementation but raises two substantive refinements: (1) whether `<rev>^N` should be included in the advice, given that all merge parents share the same depth and the suggested `--deepen` value is less meaningful for them, and (2) documentation clarity—using `<rev>` instead of `<ref>` to accurately reflect that the feature applies to any commit-ish, not just references. Harald’s latest reply clarifies that the advice is **only** triggered by explicit `<rev>~N` or `<rev>^N` syntax in commands that fail to resolve (e.g., `git show HEAD~20`), not by internal resolution failures in commands like `git log -20` or `git log --since=2.months` that stop gracefully at the shallow boundary. A v2 is still likely to address the remaining open questions.

Key technical details
- Files touched: `advice.c`, `advice.h`, `sha1-name.c`, `t/t1506-rev-parse-diagnosis.sh`
- New enum value: `ADVICE_SHALLOW_HISTORY`
- New CLI behavior: advice appears only when the revision walk stops exactly at a recorded shallow boundary **and** the user explicitly used `<rev>~N` or `<rev>^N` syntax in a command that fails to resolve
- Suggested `--deepen` value is context-aware:
  • `<rev>~N` → `--deepen=<N - current_depth>`
  • `<rev>^N` → `--deepen=1` (because a shallow boundary commit has no parents recorded locally)
- Remote and branch are auto-detected if `<rev>` looks like `<remote>/<branch>`
- Advice is suppressed during internal re-resolution via `GET_OID_QUIETLY`
- Test coverage is straightforward and approved by Junio

Open questions and loose ends
- **Scope of advice**: Should the feature cover `<rev>^N` (merge parents), given that all parents share the same depth and the suggested `--deepen` value is less meaningful for them?
- **Documentation clarity**: Use `<rev>` instead of `<ref>` to accurately reflect that the feature applies to any commit-ish, not just references. The commit message and advice text should also use the correct syntax (`<rev>~<n>`/`<rev>^[<n>]`) per `gitrevisions(7)`.

Participant positions

Clarified that the advice is **only** triggered by explicit `<rev>~N` or `<rev>^N` syntax in commands that fail to resolve, not by internal resolution failures in commands that stop gracefully at the shallow boundary.
- **Junio C Hamano**: Substantive review. Praises the technical implementation (auto-detection, suppression of double-printing) and test coverage, but questions the inclusion of `<rev>^N` and flags the `<ref>` vs. `<rev>` documentation inconsistency. Position implies a v2 is needed.
- **D. Ben Knoble**: Surface-level review identifying the `<ref>` vs. `<rev>` documentation inconsistency. No objection to the patch’s core logic or usefulness.

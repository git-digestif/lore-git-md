Subject: [PATCH] rev-parse: add advice for shallow history in <ref>~N and <ref>^N
Series version: single patch (no series)
Originating author: Harald Nordgren
Thread type: bugfix / user-experience improvement

Core problem or goal
When a user in a shallow clone attempts to use `<ref>~N` or `<ref>^N` to access an ancestor that is not present locally, Git emits a generic “is not a commit” error. The new advice (`advice.shallowHistory`) explains that the repository is shallow, why the operation failed, and suggests the exact `git fetch --deepen=<n>` command needed to resolve it.

Current status
Under review; no prior versions. The patch is self-contained and targets the rev-parse and object-name subsystem.

Key technical details
- Files touched: `advice.c`, `advice.h`, `sha1-name.c`, `t/t1506-rev-parse-diagnosis.sh`
- New enum value: `ADVICE_SHALLOW_HISTORY`
- New CLI behavior: advice message appears only when the revision walk stops exactly at a recorded shallow boundary
- Suggested `--deepen` value is context-aware:
  • `<ref>~N` → `--deepen=<N - current_depth>`
  • `<ref>^N` → `--deepen=1` (because a shallow boundary commit has no parents recorded locally)
- Remote and branch are auto-detected if `<ref>` looks like `<remote>/<branch>`
- Advice is suppressed during internal re-resolution via `GET_OID_QUIETLY`
- Documentation and commit message inconsistently use “ref” and “commit-ish”, and show bare `~N`/`^N` syntax instead of `<rev>~<n>`/`<rev>^[<n>]` as per `gitrevisions(7)`

Open questions and loose ends
- **Documentation clarity**: The commit message and advice documentation use inconsistent terminology (“ref” vs. “commit-ish”) and incorrect syntax (`~N`/`^N` instead of `<rev>~<n>`/`<rev>^[<n>]`). This could confuse users about the feature’s scope (refs only vs. any commit-ish).

Participant positions

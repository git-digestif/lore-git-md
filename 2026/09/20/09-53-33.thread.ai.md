Thread identity
Subject: [PATCH] rev-parse: add advice for shallow history in <rev>~N and <rev>^N
Series version: v2 (under review; scope narrowed after Junio’s review)
Originating author: Harald Nordgren
Thread type: bugfix / user-experience improvement

Core problem or goal
When a user in a shallow clone attempts to access an ancestor not present locally—via explicit `<rev>~N`/`<rev>^N` syntax (which fails) or via commands like `git log -20` (which silently truncates)—Git provides no indication that the operation was limited by the shallow boundary. The original goal was to add a new advice (`advice.shallowHistory`) that explains the shallow boundary, why the operation failed or was truncated, and suggests the exact `git fetch --deepen=<n>` command needed to resolve it. The v2 patch initially expanded the scope to cover both failing syntax and silent truncation in `git log -<n>`/`git log --since=<date>`, but Junio’s latest review identifies a fundamental flaw in the detection logic for silent truncation, making that part of the patch unreliable.

Current status
Under review; v2 posted but now effectively split. The `<rev>~N`/`<rev>^N` advice for failing syntax remains viable and uncontroversial. The `git log` integration for silent truncation is blocked by Junio’s review: the current implementation triggers advice only when the *last commit shown* is itself a shallow boundary, missing cases where the walk stops because a *parent* of a shown commit is shallow. Junio retracts his earlier suggestion to cover silent truncation and suggests that a better solution might involve enriching `git log --graph` output, but that is outside the scope of this patch. No new version has been posted yet.

Key technical details
- Files touched: `advice.c`, `advice.h`, `object-name.c`, `shallow.c`, `shallow.h`, `builtin/log.c`, plus new tests in `t/t1500-rev-parse.sh` and `t/t4202-log.sh`.
- New enum value: `ADVICE_SHALLOW_HISTORY`.
- New CLI behavior (viable part): advice appears when a user explicitly uses `<rev>~N` or `<rev>^N` syntax in a command that fails to resolve (e.g., `git show HEAD~20`). The suggested `--deepen` value is context-aware:
  - `<rev>~N` → `--deepen=<N - current_depth>`
  - `<rev>^N` → `--deepen=1` (because a shallow boundary commit has no parents recorded locally).
- Remote and branch are auto-detected via `remote_find_tracking` instead of assuming `refs/remotes/<remote>/<branch>`.
- Advice is suppressed during internal re-resolution via `GET_OID_QUIETLY` and in non-shallow repos.
- Paging awareness: the advice waits for the pager to close so it isn’t wiped from the terminal.
- Test coverage: 14 new test cases verify the advice appears (or doesn’t) in all expected scenarios, including merge parents, partial depths, disabled advice, and non-shallow repos.
- Flawed integration (blocked part): the v2 patch attempted to detect silent truncation in `git log -<n>`/`git log --since=<date>` by checking if the last commit shown is a shallow boundary. Junio’s review demonstrates that this misses cases where the walk stops because a *parent* of a shown commit is shallow, making the advice unreliable.

Open questions and loose ends
- **Scope of advice for `<rev>^N`**: The v2 patch retains `<rev>^N` coverage, but the `--deepen=1` suggestion may still be less meaningful for merge parents (all parents share the same depth). Junio’s v1 feedback questioned whether this case should be included; no explicit resolution yet.
- **Documentation clarity**: The commit message and advice text must use `<rev>` instead of `<ref>` to accurately reflect that the feature applies to any commit-ish (not just references) and must use correct syntax (`<rev>~<n>`/`<rev>^[<n>]`) per `gitrevisions(7)`. This was flagged in v1 but not yet confirmed as addressed in v2.
- **Implementation robustness for `<rev>~N`/`<rev>^N`**: Junio’s review of the test case (`shallowHistory advice accounts for depth already present`) asks whether the advice would behave the same for `origin/main^^^^^` as it does for `origin/main~5`, hinting at potential edge cases in the `--deepen` calculation.
- **Future of silent truncation detection**: The current approach for `git log` integration is fundamentally flawed. A reliable solution would need to detect when a walk stops *because of* a shallow boundary, not just when it stops *at* one. This may require changes to the revision walker itself, which is beyond the scope of this patch.

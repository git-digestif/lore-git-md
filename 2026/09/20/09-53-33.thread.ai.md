Thread identity
Subject: [PATCH] rev-parse: add advice for shallow history in <rev>~N and <rev>^N
Series version: v2 (expanded scope; under review)
Originating author: Harald Nordgren
Thread type: bugfix / user-experience improvement

Core problem or goal
When a user in a shallow clone attempts to access an ancestor not present locally—whether via explicit `<rev>~N`/`<rev>^N` syntax (which fails) or via commands like `git log -20` (which silently truncates)—Git provides no indication that the operation was limited by the shallow boundary. The patch adds a new advice (`advice.shallowHistory`) that explains the shallow boundary, why the operation failed or was truncated, and suggests the exact `git fetch --deepen=<n>` command needed to resolve it. The v2 patch expands the scope to cover both failing syntax and silent truncation in `git log -<n>`/`git log --since=<date>`.

Current status
Under review; v2 posted. Junio C Hamano’s review of v1 accepted the technical implementation but raised two substantive refinements: (1) whether `<rev>^N` should be included, given that all merge parents share the same depth and the suggested `--deepen` value is less meaningful for them, and (2) documentation clarity—using `<rev>` instead of `<ref>` to accurately reflect that the feature applies to any commit-ish. Harald’s reply clarified that the advice was **only** triggered by explicit `<rev>~N` or `<rev>^N` syntax in commands that fail to resolve, not by internal resolution failures in commands like `git log -20`. Junio’s subsequent email argued that the silent truncation in these graceful-stop commands is *more* confusing to users and that the advice should also appear there, prompting the v2 patch. The v2 implementation now covers both failing syntax and silent truncation in `git log -<n>`/`git log --since=<date>`, with careful suppression logic to avoid false positives (e.g., a plain `git log` running out of history stays silent).

Key technical details
- Files touched: `advice.c`, `advice.h`, `object-name.c`, `shallow.c`, `shallow.h`, `builtin/log.c`, plus new tests in `t/t1500-rev-parse.sh` and `t/t4202-log.sh`.
- New enum value: `ADVICE_SHALLOW_HISTORY`.
- New CLI behavior: advice appears when a revision walk stops exactly at a recorded shallow boundary, either because:
  - The user explicitly used `<rev>~N` or `<rev>^N` syntax in a command that fails to resolve (e.g., `git show HEAD~20`), or
  - A command like `git log -20` or `git log --since=2.months` silently truncates history at the boundary (but only if the command would have printed more commits had history been deeper).
- Suggested `--deepen` value is context-aware:
  - `<rev>~N` → `--deepen=<N - current_depth>`
  - `<rev>^N` → `--deepen=1` (because a shallow boundary commit has no parents recorded locally).
- Remote and branch are auto-detected via `remote_find_tracking` instead of assuming `refs/remotes/<remote>/<branch>`.
- Advice is suppressed during internal re-resolution via `GET_OID_QUIETLY` and in non-shallow repos.
- Paging awareness: the advice waits for the pager to close so it isn’t wiped from the terminal.
- Test coverage: 14 new test cases verify the advice appears (or doesn’t) in all expected scenarios, including merge parents, partial depths, disabled advice, and non-shallow repos.

Open questions and loose ends
- **Scope of advice for `<rev>^N`**: The v2 patch retains `<rev>^N` coverage, but the `--deepen=1` suggestion may still be less meaningful for merge parents (all parents share the same depth). Junio’s v1 feedback questioned whether this case should be included; no explicit resolution yet.
- **Documentation clarity**: The commit message and advice text must use `<rev>` instead of `<ref>` to accurately reflect that the feature applies to any commit-ish (not just references) and must use correct syntax (`<rev>~<n>`/`<rev>^[<n>]`) per `gitrevisions(7)`. This was flagged in v1 but not yet confirmed as addressed in v2.
- **Implementation robustness**: The v2 patch introduces logic in `builtin/log.c` to detect silent truncation at shallow boundaries. This is a new integration point; its correctness and potential edge cases (e.g., interactions with `--skip`, `--max-count`, or custom revision walkers) may need further scrutiny.

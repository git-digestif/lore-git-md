This is the first patch in a three-patch **bugfix series** targeting the refs subsystem. It restores the correct behavior of the `reference-transaction` hook when branches or tags are deleted by allowing callers to supply the old OIDs that were resolved before deletion.

The patch modifies `refs_delete_refs()` to accept an optional `oid_array` of old OIDs, one per refname. If an OID is provided, the deletion becomes conditional: the transaction will fail if the ref’s current value does not match the supplied OID, preventing concurrent updates from being silently overwritten. This restores the pre-regression safety check that was lost in Git 2.31 when `delete_ref()` was replaced with `delete_refs()`. Callers that pass `NULL` retain the unconditional behavior.

The change touches the core refs API (`refs.c`, `refs.h`) and updates all existing callers (`bisect.c`, `builtin/branch.c`, `builtin/fetch.c`, `builtin/remote.c`, `builtin/tag.c`, and `t/helper/test-ref-store.c`) to pass `NULL` for the new parameter, preserving their current behavior. The patch includes input validation to ensure the `oid_array` size matches the refname count and skips null OIDs (treating them as no verification).

This is a well-motivated, low-risk plumbing change that directly addresses the regression while preserving the performance gains of the original optimization. The conditional deletion trade-off (safety vs. unconditional deletion) is now explicitly documented and tested in the series, leaving the project’s acceptance of this trade-off as the remaining open question. The patch is ready for review and appears uncontroversial in its implementation.

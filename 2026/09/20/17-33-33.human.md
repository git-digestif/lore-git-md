This is an RFC proposing new worktree lifecycle hooks. The author, Maciej Ciemborowicz, suggests adding native Git hooks for operations like `git worktree add`, `remove`, `move`, `lock`, `unlock`, and `prune`. Currently, tools like `git-hooks-ext` must wrap `git worktree` or compare worktree states to detect these events, which is indirect and unreliable.

The proposal outlines two approaches: separate post-operation hooks (e.g., `post-worktree-add`) or a single unified hook (similar to `reference-transaction`) that reports all lifecycle changes in a structured payload. The latter could handle batch operations like `prune` more elegantly and might accommodate future commands like `repair`. The author clarifies that these hooks would be informational only, without veto power.

The motivation is clear—external tools need a reliable way to observe worktree changes without wrapping Git commands. The RFC seeks feedback on whether this fits Git’s hook model and whether a single hook or individual hooks would be preferable. It also asks whether a stable worktree identifier (beyond just the path) should be exposed.

This is a well-scoped feature request with a concrete use case. The discussion will likely focus on the hook design (single vs. multiple) and whether the payload should include additional metadata. If you care about worktree tooling or hook extensibility, this thread is worth following.

This is the first patch in a three-patch **bugfix series** targeting a regression in the `reference-transaction` hook. The regression, introduced in Git 2.31, causes the hook to receive all-zero OIDs when branches or tags are deleted via high-level commands like `git branch -d` or `git tag -d`, breaking external tools that rely on the old OID for monitoring ref changes.

The patch modifies `refs_delete_refs()` to accept an optional `oid_array` of old OIDs, allowing callers to make deletions conditional. If an OID is provided, the deletion fails if the ref’s value changes after the caller resolved it, restoring the pre-regression safety check (compare-and-delete) that prevents overwriting concurrent updates. This is a deliberate trade-off: the patch prioritizes safety over unconditional deletion, but the project has not yet settled whether this is the preferred approach. The change is well-documented in the commit message and code comments, and the patch includes a `BUG()` check to ensure the `oid_array` size matches the number of refs.

The patch touches core ref plumbing (`refs.c`, `refs.h`) and updates several built-in commands (`bisect.c`, `builtin/branch.c`, `builtin/fetch.c`, `builtin/remote.c`, `builtin/tag.c`) to pass `NULL` for the new parameter, preserving their existing unconditional behavior for now. The next two patches in the series will update these callers to pass resolved old OIDs, ensuring the hook receives meaningful values. The patch is clean, with no performance regression, and the added safety check is explicitly tested in the series’ regression tests (added in patch 3). The open question remains whether the project accepts the race condition trade-off—conditional deletion to prevent overwriting concurrent updates—or prefers unconditional deletion.

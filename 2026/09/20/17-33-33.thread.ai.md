Thread identity
Subject: RFC: Native worktree lifecycle hooks
Series version: RFC (no patch version yet)
Originating author: Maciej Ciemborowicz
Thread type: design discussion (RFC)

Core problem or goal
Add native Git hooks for worktree operations (`add`, `remove`, `move`, `lock`, `unlock`, `prune`) to replace indirect detection via `post-checkout` or external wrappers. The goal is to enable tools like `git-hooks-ext` to observe worktree changes without wrapping `git worktree` or diffing `git worktree list --porcelain` output.

Current status
Proposal stage; no patches yet. Two design options presented: separate post-operation hooks (e.g., `post-worktree-add`) or a unified `worktree-lifecycle` hook (similar to `reference-transaction`) that reports events like `add <path>`, `remove <path>`, etc. Author leans toward the unified hook design, citing flexibility for operations like `prune` that affect multiple worktrees. Veto hooks deemed unnecessary. Open question: whether to expose a stable worktree identifier (beyond the path). Historical context: the mailing list previously discussed worktree hooks in 2024 during Adrian Ratiu’s `git hook list` series, but the idea was not pursued at that time.

Key technical details
Files/subsystems: `builtin/worktree.c`, `hook.c`, documentation.
New symbols: proposed hook names (`post-worktree-add` or `worktree-lifecycle`), event types (`add`, `remove`, `move`, etc.).
Behavior: hooks would fire after worktree operations; no pre-operation or veto hooks.
On-disk format: none (hooks are configuration-based).
Test coverage: would need to verify hook invocation for all worktree commands, including edge cases like `prune`.

Open questions and loose ends
1. Unified hook vs. separate hooks: which design is preferred?
2. Stable worktree identifier: should one be exposed, given paths can change (e.g., during `move` or `repair`)?
3. Backward compatibility: how to handle existing tools that rely on `post-checkout` or external wrappers?
4. Scope: should this be in core Git, or remain a wrapper concern?
5. Prior art: the 2024 discussion in Adrian Ratiu’s `git hook list` series may contain relevant arguments or objections that should be addressed.

Participant positions
Maciej Ciemborowicz (author): proposes unified `worktree-lifecycle` hook; no need for veto hooks; stable identifier desirable but not required for initial implementation.
Kristoffer Haugsbakk: **surface-level** -- points to prior 2024 discussion on worktree hooks but does not engage with technical merits of the current proposal.

Related work

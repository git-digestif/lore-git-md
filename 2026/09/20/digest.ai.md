# Git mailing list daily digest for 2026/09/20

## The day in brief
Maciej Ciemborowicz advanced two related series hardening the refs API against concurrent modifications: a v2 of the batched-deletion old-OID series that makes branch, tag, and remote prune deletions compare-and-delete, and a new patch routing reference copy and rename through the transaction API so hooks observe them as single logical operations. Harald Nordgren added a `shallowHistory` advice explaining failed `<ref>~N` resolution in shallow clones, while reviewers blessed a `diff --no-index -R` fix for file/directory conflicts.

## Notable threads

### refs: report old OIDs for batched deletions
The reference-transaction hook currently receives zero as both old and new OID when branch, tag, fetch, and remote delete refs through `refs_delete_refs()`, even though those callers already know the values they selected for deletion. Maciej Ciemborowicz posted the v2 of a three-patch series teaching `refs_delete_refs()` to accept an optional `oid_array` of aligned old OIDs and pass each non-null OID to `ref_transaction_delete()`. Supplying an OID makes the deletion conditional and fails the transaction if the ref changed after the caller resolved it, which restores the compare-and-delete race protection for branch and tag that existed before commit 8198907795 converted them to batched deletion, and prevents a stale prune scan from deleting a ref updated by another process. The first patch adds the parameter, the second passes old OIDs for branch and tag so hooks receive useful old values, and the third carries `get_stale_heads()` values into prune deletion transactions so a concurrent change makes the prune fail and preserves the new value without printing "[pruned]" after a deletion failure. The series documents the conditional deletion behavior, adds tests that update refs from the hook's preparing phase to verify branch deletion and remote pruning preserve concurrent updates, and uses a local `string_list_item` in `refs_delete_refs()`.

### refs: run copy and rename through transactions
Reference copy and rename operations currently bypass the transaction API, so the reference-transaction hook sees only the source deletion with the files backend and no useful update with the reftable backend. Maciej Ciemborowicz posted a patch representing both operations as reference transactions containing their logical updates: a rename becomes a deletion of the old reference plus creation of the new reference in the same transaction. The patch retains backend-specific reflog handling, with the files backend staging its existing rename procedure across prepare, finish, and abort while reftable stages an addition while holding the stack lock, suppresses hooks for the files backend's nested deletion transactions so callers observe one logical transaction, and records and verifies source and destination values after taking backend locks to reject concurrent changes instead of applying a rename that differs from the payload shown to the preparing hook. It preserves D/F renames, restores overwritten references and reflogs when a prepared hook rejects the operation, and adds test coverage for rename, copy, forced updates, both directions of D/F conflicts, concurrent updates detected during the preparing hook, and prepared-hook rollback.

### diff --no-index: fix -R with file/directory conflicts
When a path is a file on one side and a directory on the other, `queue_diff()` queues the file separately before recursing into the directory, bypassing the `reverse_diff` handling used for ordinary files, so `diff --no-index -R` reports both paths as deleted or added incorrectly. Haokai Ding's patch swaps the filespecs of the early queue entry when `reverse_diff` is set, with regression tests for both directions. René Scharfe reviewed the fix, writing "Good find!" and "Looks good. I like the explicit exit code expectation," and Jacob Keller added a `Reviewed-by` tag.

### object-name: explain why <ref>~N fails in a shallow clone
Asking for a commit's ancestor with `<ref>~N` or `<ref>^N` in a shallow clone that lacks N commits of history locally fails with a bare "is not a commit" error, with no indication that the repository being shallow is the reason. Harald Nordgren posted a patch adding a `shallowHistory` advice that triggers when the walk runs out of parents exactly at a recorded shallow boundary, explaining that history was intentionally truncated there. When `<ref>` looks like `<remote>/<branch>` and `<remote>` is configured, the suggested command names that remote and branch directly; for `<ref>~N` it suggests the exact `--deepen` needed accounting for history already present, while for `<ref>^N` the suggestion is always `--deepen=1` because a shallow boundary commit has no parents recorded locally. The hint is suppressed under `GET_OID_QUIETLY` to avoid duplicate output and does not fire for non-shallow repositories or when resolution succeeds. D. Ben Knoble suggested restricting the feature to refs only since a ref may be needed to unshallow via fetch, noted that the documentation is unclear about triggers because `~N`/`^N` work with any commit-ish, recommended documenting the syntax as `<rev>~<n>` and `<rev>^[<n>]` rather than bare `~N`/`^N`, and questioned whether "rev" was intended instead of "ref" in the commit message.

### worktree: add lifecycle hooks
Git currently invokes `post-checkout` after `git worktree add` but has no native hooks for other worktree lifecycle operations such as remove, move, lock, unlock, or prune, forcing tools like git-hooks-ext to wrap `git worktree` or compare `git worktree list --porcelain` output before and after. Maciej Ciemborowicz proposed an RFC adding native hooks for these events, suggesting either separate post-operation hooks or a single hook similar to `reference-transaction` with a payload listing the operation and path(s), stating the hooks would only need to notify observers after a successful operation without veto power, and asking whether a stable worktree identifier should be exposed in addition to the path. Kristoffer Haugsbakk pointed to an existing discussion on the topic.

This is a reply in the ongoing thread about hardening fixes for Git for Windows, specifically a discussion of the second patch in the series (GPG signature-prefix matching). Johannes Schindelin pushes back against Junio C Hamano’s proposed simplification, arguing that the current patch’s approach is necessary for correctness and safety.

The exchange centers on whether to propagate a new `slen` (signature length) parameter through `get_format_by_sig()` and its callers, or to confine the length-aware check to `get_format_by_sig()` and avoid changing `check_signature()`’s public interface. Johannes makes two key points: first, `check_signature()` has included a `slen` parameter since 2021, so dropping it now would introduce an unrelated API change into a bugfix; second, and more critically, `slen` is used not only for prefix matching but also to determine the exact byte count passed to external verifiers (`gpg`/`ssh-keygen`), meaning that relying on `strlen(signature)` could truncate signatures with embedded NULs and break cryptographic verification.

The discussion also highlights a prior incident: in 2024, Jeff King (Peff) concluded that `parse_signed_buffer()` was safe from buffer overreads because it was always called with a `strbuf`, but that assumption was invalidated months earlier by a new caller (`convert_tag_object()`) that does not use a `strbuf`. Johannes argues that repeating this pattern in `check_signature()` would risk reintroducing the same class of defect.

This reply advances the thread by clarifying the technical stakes: the patch is not just about defensive prefix matching, but about maintaining a consistent, length-aware interface throughout the GPG verification path. The disagreement is narrow but substantive, touching on API design, security assumptions, and the trade-off between minimalism and robustness. Future discussion is likely to focus on whether Johannes’s concerns about embedded NULs and verification correctness outweigh the desire for a simpler patch.

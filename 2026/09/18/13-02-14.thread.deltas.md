## 2026/09/19

- [2026/09/19/15-23-41 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood endorsed the general direction of APIs that return errors rather than dying on allocation failures or overflow, noting that the xdiff and reftable code already have something similar, but objected to the name "safe" as not describing how the APIs differ from existing ones, preferring documentation and naming that reflect returning errors on failure.
- [2026/09/19/15-23-41 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood proposed that for the strbuf API, checking for failure on every function call would not be attractive, and instead suggested a sticky error bit like the stdio functions so a string can be built and checked for failures once just before use.
- [2026/09/19/15-23-41 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood identified a flaw in the RFC's CodeQL verification: the implementation of sstrbuf_grow() in patch 4 calls st_add3(), which dies on overflow, rather than st_add_overflows(), indicating the checks are not working as intended.

## 2026/09/21

- [2026/09/21/21-18-48 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano argued that the longer-term goal should be to make service routines like strbuf, string_list, and csum_file free of die() and "safe", suggesting that expanding the "safe" API surface so callers take responsibility for errors would be as useful as the "libification" trend of passing "struct repository *" explicitly; he agreed that picking strbuf as the first instance is a good idea and suggested renaming functions that merely use a strbuf to return results but are not strbuf-specific (such as strbuf_realpath() in abspath.h) away from the strbuf_ prefix.
- [2026/09/21/21-24-28 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano noted that safe_memory_limit_check() produces a confusing error message when git_alloc_limit is 0 (the code uses SIZE_MAX as a stand-in limit but the message reports the limit as git_alloc_limit, i.e., zero), and suggested the message should report the local "limit" value instead.
- [2026/09/21/21-29-57 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano identified a memory leak in srealloc(): the code overwrites *ptr with realloc()'s return value before checking for failure, so when realloc() fails the original pointer is clobbered and the allocated memory is leaked.
- [2026/09/21/21-44-49 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano questioned whether "enum safe_result" is meant as an enumeration of distinct error kinds or as bitmasks, and provided two alternative implementations for jw_release(): if it is an enumeration of kinds, report only the first error encountered using an explicit if-check pattern; if it is bitmasks, accumulate errors with |=.
- [2026/09/21/22-34-43 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano added a third possibility for jw_release(): if the function is designed to return 0 for success and non-zero for failure, declaring "result" as a plain "int" and using the "|| result" construct as written would make sense.

## 2026/09/23

- [2026/09/23/19-25-23 by Mark C. Chu-Carroll <markchucarroll@fastmail.com>] Mark C. Chu-Carroll endorsed the safe-strbuf idea in general (having hit similar cascading-error problems in other systems), and offered a series of optional writing-style nitpicks on PATCH 1/6's commit message and strbuf-safe.h comments: avoid "we" in comments, drop quotation marks used as emphasis around words like "safe" and "private", rephrase "In the future, we will hope..." as "Future changes will include...", strengthen invariant wording to "must", and replace "play" with "manipulate" — explicitly inviting the author to ignore them if he disagrees.
- [2026/09/23/19-46-28 by Jeff King <peff@peff.net>] Jeff King objected to the term "safe" for the proposed API on two grounds: it implies the normal strbuf functions are unsafe (whereas the "malloc failure is fatal" scheme is shared with most of the codebase), and it covers only one kind of safety — the new code would still call malloc() and thus would not be safe from a signal handler. He said he had instead imagined strbuf-like functions operating on a fixed-size buffer (static max like 4k or a per-variable max in the struct), whose out-of-room errors would be deterministic for a given input rather than dependent on malloc races; he also agreed with the earlier quoted suggestion (Phillip Wood) that a sticky error bit checked once before use would be a nicer approach.
- [2026/09/23/20-14-34 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano pushed back on Mark C. Chu-Carroll's framing that the safe API avoids "loss of error details", noting the details are lost either way — whether strbuf dies on allocation failure or the memory to format the details cannot be allocated; he also joked that the third word of Mark's comment should be "I" rather than "we" if it was meant to include the commit-log writers.

This is a reply in the ongoing discussion about the second patch in Johannes Schindelin’s seven-patch series fixing Coverity-reported issues in Git for Windows. The patch makes GPG signature-prefix matching length-aware to prevent buffer overreads, but Junio C Hamano suggested a simpler alternative: drop the new `slen` parameter from `check_signature()` entirely, since all existing callers already pass a NUL-terminated buffer from a `strbuf`.

Johannes pushes back firmly, arguing that the parameter should stay. He points out two key reasons: first, `check_signature()` has included `slen` since 2021, so removing it now would mix an unrelated API change into a bugfix; second, and more critically, `slen` is used not just for prefix matching but also to determine how many bytes to write to the temporary file for cryptographic verification. If the parameter were dropped, a signature containing an embedded NUL would be truncated before reaching the external verifier, creating a correctness regression in the actual verification path. He also notes that relying on NUL-termination has already bitten the project once—earlier reasoning that `parse_signed_buffer()` was safe because it fed from a `strbuf` became invalid after a new caller was added, and the same risk applies here.

The exchange is substantive: Johannes’s response clarifies the technical stakes and justifies the patch’s current design. No new code is proposed, but the thread is now clearly at a decision point—whether to accept the patch as-is or revisit the interface. For a reader scanning the digest, this is the kind of detail that signals the patch is not purely mechanical and may need wider attention before merging.

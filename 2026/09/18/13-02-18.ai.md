This is the fourth patch in Derrick Stolee’s six-patch RFC series introducing a "safe" `strbuf` API that cannot transitively call `die()` or `exit()`. The patch implements the first safe method, `sstrbuf_grow()`, which is a safe version of `strbuf_grow()`.

The patch is **technically focused and incremental**, building on the preparatory work in earlier patches (moving `strbuf` struct definitions to `strbuf-safe.h` and refactoring `GIT_ALLOC_LIMIT` initialization). The implementation is straightforward: `sstrbuf_grow()` replaces the `ALLOC_GROW` macro with a new `SAFE_ALLOC_GROW` macro that uses `srealloc()` (a safe version of `xrealloc()`) and returns an error code instead of dying. The existing `strbuf_grow()` is updated to call `sstrbuf_grow()` and die on failure, preserving backward compatibility.

**Key changes**:
- Introduces `strbuf-safe.c`, the new source file for the safe API, containing `sstrbuf_grow()` and the `SAFE_ALLOC_GROW` macro.
- Adds `srealloc()` to `wrapper.c` and `wrapper.h`, a safe version of `xrealloc()` that returns an error code instead of dying.
- Defines `enum safe_result` in `strbuf-safe.h` to standardize error codes (`SUCCESS` and `MEMORY_ERROR`).
- Updates `strbuf.c` to delegate `strbuf_grow()` to `sstrbuf_grow()` and die on failure.
- Updates the build system (`Makefile` and `meson.build`) to include `strbuf-safe.c`.

**Behavior changes**: None for existing callers. The safe API is opt-in, and the patch does not yet update any callers to use `sstrbuf_grow()`. The `strbuf_grow()` function remains unchanged in its behavior (it still dies on failure), but its implementation now relies on the safe API.

**Motivation**: The patch is a necessary step toward making `json-writer` (and by extension, trace2) safe from recursive `die()` loops. By implementing `sstrbuf_grow()` first, Stolee ensures that other safe methods (e.g., `sstrbuf_init()`, `sstrbuf_release()`) can reuse it without introducing `die()` calls.

**Likely discussion points**:
- The `sstrbuf_*` naming convention (vs. `strbuf_*_gently` or another scheme).
- The trade-off between safety and performance (e.g., the overhead of error-code returns vs. the simplicity of `die()`).
- Whether `srealloc()` should be exposed in `wrapper.h` or kept internal to the safe API.
- The choice of `enum safe_result` values (e.g., whether `MEMORY_ERROR` is sufficient or more granular error codes are needed).

The patch is **well-structured and minimal**, focusing on a single method while laying the groundwork for the rest of the safe API. It is **not yet ready for merging** (as part of an RFC series), but the implementation is clean and aligns with the series’ goal of eliminating `die()` calls in critical code paths. The use of `srealloc()` and the `SAFE_ALLOC_GROW` macro demonstrates a clear pattern for future safe methods.

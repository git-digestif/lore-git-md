This is the second patch in Derrick Stolee’s six-part RFC series introducing a "safe" `strbuf` API that cannot call `die()`. The series aims to prevent recursive `die()` loops in low-level libraries like trace2, where crashing is unacceptable.

This patch **proactively initializes the `GIT_ALLOC_LIMIT` environment variable** during Git’s startup (`setup_environment()`), rather than lazily during the first memory allocation. The change is a prerequisite for later patches that will introduce a version of `memory_limit_check()` that doesn’t call `die()` at all. By moving initialization to startup, the safe API can assume the limit is already set, avoiding the need to call `git_env_ulong()` (which could itself trigger a `die()`).

The patch also **documents `GIT_ALLOC_LIMIT`** in `git.adoc`, acknowledging its long-standing but previously undocumented use in tests. Stolee opts not to rename it to `GIT_TEST_ALLOC_LIMIT` (despite its test-only purpose) due to Hyrum’s Law, noting that someone might depend on it in the wild. The commit message explains this trade-off clearly.

The implementation is straightforward: `initialize_git_alloc_limit()` is added to `wrapper.h`, and the static `limit` variable in `memory_limit_check()` is replaced with a global `git_alloc_limit`. The change is minimal and doesn’t alter behavior—it just shifts when the limit is read.

This patch is **well-motivated and uncontroversial** as a stepping stone for the safe API. The only open question is whether the `GIT_ALLOC_LIMIT` name should be preserved (as done here) or renamed, but Stolee’s reasoning is sound. The patch looks ready for merging once the RFC is accepted.

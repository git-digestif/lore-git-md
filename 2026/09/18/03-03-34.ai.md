This is the fourth patch in a five-patch bugfix series (v2) addressing a data-loss race in `git repack -d` where concurrent pushes can cause objects to vanish despite `.keep` files. The series replaces the `--honor-pack-keep` mechanism with a snapshot-based approach to ensure `.keep` files are managed consistently.

This patch adds `--keep-pack-from-file=<file>` to `git pack-objects`, allowing callers to pass a file containing one pack name per line (empty lines ignored). The names are treated identically to those passed via `--keep-pack`: matched against local packs, ignored if they don’t exist, and kept open under `--stdin-packs=follow`. Relative paths are resolved against the working directory, matching the behavior of `git multi-pack-index write --refs-snapshot`. The `keep_pack_list` now owns its strings (`strdup_strings = 1`) to accommodate strings from both command-line arguments and the file.

The motivation is practical: command-line length limits (e.g., 32K characters on Windows) prevent passing hundreds of pack names via `--keep-pack`. This is a scalability enabler for the series’ main fix (patch 5/5), where `repack` will pass `pack-objects` its snapshot of `.keep` packs via this option. The implementation is straightforward: the new `read_keep_pack_list()` helper reads the file line-by-line, appends non-empty lines to the existing `keep_pack_list`, and dies on I/O errors. The file format (one pack name per line) is consistent with other Git tools and sufficient for the use case.

The patch includes two new tests in `t/t5331-pack-objects-stdin.sh`. The first verifies that `--keep-pack-from-file` behaves identically to `--keep-pack`, including ignoring empty lines and non-existent packs. The second ensures the command fails cleanly when the file is missing, with a descriptive error message. The tests are minimal but cover the critical behaviors.

This is a well-motivated, narrowly scoped addition that addresses a real-world limitation. The implementation is clean, the documentation is clear, and the tests are sufficient. The patch is unlikely to be controversial, though reviewers may discuss whether the file format should be more structured (e.g., NUL-terminated) or whether the error handling could be more graceful (e.g., skipping unreadable files). The current design is pragmatic and aligns with existing Git conventions.

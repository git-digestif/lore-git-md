This is the fourth patch in Derrick Stolee’s six-part RFC series introducing a "safe" `strbuf` API that cannot call `die()` or `exit()`. The series targets a real problem: the trace2 subsystem (via `json-writer`) can trigger recursive `die()` loops if memory allocation fails, which is unacceptable for low-level libraries.

This patch implements the first safe method, `sstrbuf_grow()`, a safe version of `strbuf_grow()`. The naming convention (`sstrbuf_*` instead of `strbuf_*_gently`) is intentional, signaling that these methods are even safer than "gentle" variants, which still `die()` on system-level errors. The patch also introduces `SAFE_ALLOC_GROW`, a macro that mirrors `ALLOC_GROW` but returns a `MEMORY_ERROR` enum instead of calling `die()`. The existing `strbuf_grow()` is refactored to use `sstrbuf_grow()` internally, preserving backward compatibility while paving the way for future safe methods.

The patch touches `strbuf-safe.c` (new file), `strbuf-safe.h` (adds the `safe_result` enum and `sstrbuf_grow()` declaration), `strbuf.c` (refactors `strbuf_grow()` to use the safe version), and `wrapper.c`/`wrapper.h` (introduces `srealloc()`, a safe version of `xrealloc()` that returns an error instead of dying). Build system files (`Makefile`, `meson.build`) are updated to include the new `strbuf-safe.c`.

The implementation is clean and logically structured, with clear separation between safe and unsafe code paths. The `sstrbuf_grow()` method is chosen as the first safe method because it’s a low-level helper used by many other `strbuf` APIs, making it a natural foundation for the rest of the safe API. The patch does not yet introduce callers for `sstrbuf_grow()`, but it sets the stage for future patches that will integrate the safe API into `json-writer.c` and other critical paths.

This patch is a well-executed step in the series, addressing a specific technical need without disrupting existing behavior. The use of `enum safe_result` and the `srealloc()` helper demonstrates a thoughtful approach to error handling. The only open question is whether the `sstrbuf_*` naming convention will gain traction, but the justification (avoiding confusion with "gentle" methods) is reasonable. The patch is not yet ready for merging (it’s part of an RFC), but it’s a solid building block for the larger goal of making Git’s low-level APIs more robust.

This is the **second patch in the v2 series** fixing a data-loss race in `git repack -d`. It addresses a **latent bug in the cruft-pack walk** that becomes critical once the series removes `--honor-pack-keep`.

The patch fixes a stale kept-pack cache in `pack-objects` that causes the cruft-pack walk to stop prematurely at packs marked as kept during the initial object collection phase. The bug surfaces when an unreachable object chain spans multiple packs, with the middle commit sitting in a pack that `pack-objects` was not explicitly told about. Without the fix, the walk fails to traverse through that pack, leaving expired objects unreachable and thus lost.

The fix is minimal: expose `packfile_store_invalidate_kept_pack_cache()` (already present in `packfile.c`) and call it after re-marking the fresh packs as kept. This ensures the cache reflects the current kept-pack state before the walk begins. The patch also updates the comment in `odb/source-packed.h` to document the new explicit invalidation path.

The test in `t/t5329-pack-objects-cruft.sh` reproduces the bug by creating an unreachable chain where the middle commit sits in an untold pack. Without the fix, the cruft pack contains only the recent tip; with the fix, it includes all reachable objects, including the expired ones.

This is a **correctness fix** with no performance impact. The change is internal to `pack-objects` and does not alter user-visible behavior—until the series removes `--honor-pack-keep`, at which point the bug would cause data loss. The patch is a prerequisite for the series’ main fix (patch 5/5) and is unlikely to be controversial, though reviewers may seek confirmation that the cache invalidation is sufficient and does not introduce edge cases. Key files touched: `builtin/pack-objects.c`, `packfile.c`, `packfile.h`, and `odb/source-packed.h`.

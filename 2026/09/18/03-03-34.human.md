This is the fourth patch in a five-patch bugfix series targeting a data-loss race in `git repack -d` when concurrent pushes create `.keep` files mid-repack. The series replaces the racy `--honor-pack-keep` mechanism with a snapshot-based approach, and this patch adds the plumbing needed to scale it.

The patch introduces `--keep-pack-from-file=<file>` to `git pack-objects`, which reads one pack name per line from a file and treats them exactly like `--keep-pack` arguments. Empty lines are ignored, and relative paths are resolved against the working directory. The implementation is straightforward: the file is read line-by-line, and each non-empty line is appended to the same `string_list` that holds `--keep-pack` names. The list now owns its strings (`strdup_strings = 1`) to handle the two sources cleanly.

This is a scalability enabler for the series' main fix (patch 5/5), which will pass `repack`’s snapshot of `.keep` packs to `pack-objects` via this new option. Without it, repositories with many kept packs would hit command-line length limits (32K characters on Windows). The file format—one pack name per line—matches other Git tools and is sufficient for the use case; the commit message notes that more structured formats (e.g., NUL-terminated) were considered unnecessary.

The patch includes two new tests in `t/t5331-pack-objects-stdin.sh`. The first verifies that `--keep-pack-from-file` behaves identically to `--keep-pack`, including ignoring empty lines and non-existent packs. The second confirms the command fails cleanly when the file is missing. The tests are minimal but cover the critical cases.

This is a well-crafted, narrowly scoped addition that addresses a real problem. The implementation is clean, the documentation is clear, and the tests are sufficient. It’s unlikely to be controversial, though reviewers may discuss whether the file format should be more rigid (e.g., rejecting malformed lines).

This is the second patch in Derrick Stolee’s six-patch RFC series introducing a "safe" `strbuf` API that cannot call `die()`. It **proactively initializes the `GIT_ALLOC_LIMIT` environment variable** during Git’s early startup (`setup_environment()`), moving the logic out of the `memory_limit_check()` function. The goal is to **decouple the limit-checking logic from `die()`-prone environment parsing**, which is necessary for the safe API’s error-returning behavior in later patches.

The patch **documents `GIT_ALLOC_LIMIT`** (previously undocumented) in `Documentation/git.adoc`, noting its purpose as a per-allocation memory cap. It also **resists renaming it to `GIT_TEST_ALLOC_LIMIT`** despite the variable’s test-oriented origin, citing Hyrum’s Law and the possibility of external usage. The change is **minimal and focused**: it extracts the static `limit` variable into a global `git_alloc_limit`, adds an initialization function (`initialize_git_alloc_limit()`), and updates `memory_limit_check()` to use the pre-initialized value. The build system is untouched here (unlike the first patch), but the new function is declared in `wrapper.h` and called from `common-init.c`.

This patch is **a prerequisite for the safe API** because it ensures the allocation limit is set before any safe methods (e.g., `sstrbuf_grow()`) are called, avoiding implicit `die()` calls from `git_env_ulong()`. The commit message is clear about the trade-off: while the initialization is now explicit, the safe API will still make "reasonable assumptions" about timing. The patch is **well-motivated and technically sound**, with no behavior changes—just a refactoring to enable future safety improvements. The only open question is whether the decision to keep `GIT_ALLOC_LIMIT` (rather than rename it) will draw pushback, but the commit message preemptively justifies the choice.

This thread is an RFC patch series by Derrick Stolee introducing a "safe" subset of the `strbuf` API that cannot call `die()` or `exit()`, aimed at critical code paths like the trace2 subsystem. The series is now complete at 6 patches, but key design and implementation issues remain unresolved.

The core debate centers on whether the proposed "safe" API is the right approach. Junio C Hamano supports the goal of making core routines safer as part of Git's libification trend but questions whether carving out a niche subset is the best long-term strategy. Jeff King (Peff) critiques the "safe" framing as misleading, arguing the API doesn't address signal-safety (due to `malloc()` locks) and proposes an alternative: fixed-size, stack-allocated buffers (e.g., `static_strbuf`) that avoid dynamic allocation entirely. Phillip Wood raises concerns about the API's usability, suggesting a sticky error bit to simplify error handling, and identifies bugs in `sstrbuf_grow()` and `srealloc()`.

Key unresolved issues include a memory leak in `srealloc()`, a safety violation in `sstrbuf_grow()`, and the incomplete transition in `json-writer.c`, where callers aren't yet updated to handle errors. The naming convention (`sstrbuf_*`) and error aggregation logic in `jw_release()` are also contested. The discussion now revolves around whether to harden the existing `strbuf` API, adopt Peff's fixed-size buffers, or pursue another strategy. While the series documents `GIT_ALLOC_LIMIT` and initializes it during startup, its resistance to renaming it may draw pushback.

Participants include Stolee (author), Junio (maintainer), Peff, Phillip Wood, and Mark C. Chu-Carroll (surface-level review).

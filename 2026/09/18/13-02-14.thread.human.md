This thread is an RFC patch series from Derrick Stolee proposing a "safe" subset of the `strbuf` API that cannot call `die()` or `exit()`, motivated by a real-world problem in the trace2 subsystem. The trace2 code (via `json-writer`) can trigger recursive `die()` loops if memory allocation fails, which is unacceptable for low-level libraries that must not crash. The series is structured incrementally: earlier patches split `strbuf` definitions into a new header and refactored `GIT_ALLOC_LIMIT` initialization to avoid `die()`-prone environment parsing, while this latest patch introduces a safe memory limit check that never calls `die()`.

The current patch (3/6) refactors the memory limit checking logic in `wrapper.c` to create `safe_memory_limit_check()`, which assumes `SIZE_MAX` as the limit if `git_alloc_limit` is unset—avoiding the `die()`-prone environment parsing that the old logic relied on. This is safe because an earlier patch in the series proactively initializes `GIT_ALLOC_LIMIT` during Git’s startup, ensuring the limit is set before any safe API calls occur. The existing `memory_limit_check()` is preserved for backward compatibility but now delegates to the safe version, calling `die()` only when not in "gentle" mode. The trade-off is that safe APIs might fail to allocate memory that would have succeeded under the old logic if called *very* early in startup, but this is deemed acceptable given the narrow window and the safety guarantee.

The series remains under review at the RFC stage, with no major objections raised so far. Key open questions include whether the "safe" API is the right solution (vs. hardening the existing API), the naming convention (`sstrbuf_*` vs. `strbuf_*_gently`), and the transition plan for handling errors in `json-writer` callers. The series is technically sound, with CodeQL used to verify the safety property in later patches, and the refactoring in this patch is low-risk with no behavior changes for existing callers. The next steps will likely focus on integrating the safe API into `json-writer` and addressing any feedback on the approach.

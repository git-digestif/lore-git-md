The thread is about Derrick Stolee’s RFC patch series introducing a "safe" subset of the `strbuf` API that cannot call `die()` or `exit()`, motivated by the trace2 subsystem’s need for crash-free operation. The series is now complete at six patches, with the goal of providing a safe alternative for critical code paths like trace2 while preserving backward compatibility for existing callers.

Key participants include Stolee (the author), Junio C Hamano (the maintainer), and Phillip Wood. Junio has endorsed the direction of making core service routines safer as part of Git’s libification trend but questions whether the current approach—carving out a niche "safe" subset—is the right long-term strategy. He suggests the entire `strbuf` API should eventually be hardened, not duplicated, and has identified several bugs in the series, including a misleading error message in `safe_memory_limit_check()` (now fixed) and a memory leak in `srealloc()`. His latest feedback focuses on a design flaw in `jw_release()`’s error aggregation logic, arguing that the current use of `||` to coalesce errors is inflexible and future-hostile. He proposes either preserving distinct error types or using a bitmask to combine flags, depending on whether callers need to distinguish between error types.

Phillip Wood’s substantive review raises three main concerns: the "safe" framing is vague and should instead describe the API as error-returning (with naming aligned to existing patterns like `strbuf_*_gently`), the usability of the API is poor due to the need to check errors on every call (he proposes a sticky error bit to simplify handling), and a bug in `sstrbuf_grow()` (using `st_add3()`, which calls `die()` on overflow) that violates the safety guarantee. The series has also introduced new files (`strbuf-safe.h`, `strbuf-safe.c`) and symbols (`sstrbuf_init()`, `sstrbuf_release()`, `sstrbuf_grow()`, `SAFE_ALLOC_GROW`), and has begun converting `json-writer.c` to use the safe API, though callers are not yet updated to handle errors.

The series is still under review, with open questions about the API’s long-term scope (niche alternative vs. broader hardening), naming conventions, usability, and error-handling philosophy. The bugs identified by Junio and Phillip must be addressed before the series can progress beyond the RFC stage.

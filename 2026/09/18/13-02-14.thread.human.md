This thread introduces a "safe" `strbuf` API designed to avoid `die()` calls, motivated by the trace2 subsystem's need to avoid crashes. Derrick Stolee's RFC series (now complete at 6 patches) proposes splitting the `strbuf` API into a subset that returns errors instead of dying, with `json-writer.c` as the initial adopter. The series is technically sound but remains in the RFC stage, with key design questions unresolved.

Phillip Wood's recent review raises three major concerns. First, he finds the "safe" framing unclear and suggests the API should instead be named to reflect its error-returning behavior (e.g., `strbuf_*_gently`), aligning with existing patterns in `xdiff` and `reftable`. Second, he critiques the API's usability, arguing that checking errors on every call would be cumbersome and proposes a sticky error bit (like C's `stdio`) to defer error handling. Third, he identifies a critical bug: `sstrbuf_grow()` uses `st_add3()`, which can `die()` on overflow, violating the safety guarantee and undermining the CodeQL verification in the series. He recommends using `st_add_overflows()` instead.

The series is under active discussion, with no decisions yet on naming, usability improvements, or the bug fix. The transition plan—land the API first, then refactor callers—remains uncontested, but the unresolved issues may delay progress. The safe API is functionally complete, but its adoption in `json-writer.c` is partial, and callers are not yet error-aware, leaving a gap where consumers might continue running after failures. The conversation is collaborative, treating the RFC as a starting point rather than a finished proposal.

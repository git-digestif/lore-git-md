This thread is an RFC patch series by Derrick Stolee introducing a "safe" subset of the `strbuf` API that cannot call `die()` or `exit()`, addressing a critical issue where the trace2 subsystem (via `json-writer`) can trigger recursive `die()` loops during memory allocation failures. The series is now complete with the sixth patch, which adds the remaining core methods (`sstrbuf_init()` and `sstrbuf_release()`) and begins converting `json-writer.c` to use them.

The motivation remains clear: low-level libraries like trace2 must not crash, and the safe API provides an opt-in alternative for such code paths. The series has progressed incrementally, with earlier patches splitting `strbuf` definitions into a new `strbuf-safe.h` header, refactoring `GIT_ALLOC_LIMIT` initialization to avoid `die()`-prone environment parsing, and implementing the first safe method (`sstrbuf_grow()`). The latest patch completes the API by adding initialization and release methods, and updates `json-writer.c` to propagate errors from the safe API, though the transition is intentionally incomplete—callers like trace2 are not yet adapted to handle these errors, leaving that work for future patches.

Key technical details include the new `sstrbuf_init()` and `sstrbuf_release()` functions, the conversion of `jw_release()` to return an error code, and the use of `banned-die.h` in `json-writer.c` to enforce the no-`die()` rule. The patch preserves backward compatibility by keeping the existing `strbuf_init()` and `strbuf_release()` functions unchanged (they still die on failure). Open questions remain about the naming convention (`sstrbuf_*` vs. alternatives), the scope of the safe API (whether it should eventually replace the existing API in more places), and the deferred adaptation of `json-writer` callers. The series is technically sound but leaves room for discussion on these points.

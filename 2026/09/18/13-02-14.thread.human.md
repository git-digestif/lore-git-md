This thread is an RFC patch series by Derrick Stolee proposing a "safe" subset of the `strbuf` API that cannot call `die()` or `exit()`, motivated by the trace2 subsystem's need to avoid crashes even under memory pressure. The series introduces new functions like `sstrbuf_init()`, `sstrbuf_release()`, and `sstrbuf_grow()`, refactors `GIT_ALLOC_LIMIT` initialization to avoid `die()`-prone environment parsing, and begins converting `json-writer.c` to use the safe API. Junio C Hamano has endorsed the direction of making core routines safer but questions whether carving out a niche "safe" subset is the right long-term strategy, suggesting the entire `strbuf` API should eventually be hardened instead.

The series has drawn substantive feedback from Phillip Wood and Jeff King (Peff), both of whom critique the "safe" framing as misleading. Phillip argues the API should be described as error-returning and aligned with existing patterns (e.g., `strbuf_*_gently`), while Peff proposes an entirely different approach: fixed-size, stack-allocated buffers to avoid `malloc()` entirely, which he argues would better serve trace2's crash-resilience needs. Both reviewers also highlight usability concerns, with Phillip and Peff independently proposing a sticky error bit (like C’s `stdio` functions) to simplify error handling. Junio’s feedback has identified bugs in the implementation (e.g., a memory leak in `srealloc()` and a `die()`-calling overflow check in `sstrbuf_grow()`), while Phillip and Peff’s critiques focus on the API’s design and long-term viability.

The series is still in the RFC stage, with key questions unresolved: whether the safe API should be a niche subset or a broader hardening effort, how to handle error checking ergonomically, and whether the current approach (error-returning functions) is the right solution for trace2’s requirements. The discussion has shifted toward more radical alternatives, such as Peff’s fixed-size buffers, which could redefine the scope of the work. No decisions have been made, and the thread remains open for further input on the best path forward.

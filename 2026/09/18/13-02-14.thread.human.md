This thread is an RFC patch series from Derrick Stolee introducing a "safe" subset of Git's `strbuf` API that cannot call `die()` or `exit()`, motivated by the trace2 subsystem's need to avoid crashes even under memory pressure. The series is now complete at six patches, with the core goal of providing safe alternatives for critical code paths like trace2's JSON writer.

Key participants include Derrick Stolee (author), Junio C Hamano (maintainer), and Phillip Wood (reviewer). Junio has been broadly supportive of the direction—making core routines safer as part of Git's libification trend—but has raised several technical concerns. His latest feedback refines the error-handling design in `jw_release()`, suggesting the return type should be a simple `int` (0 for success, non-zero for failure) rather than an `enum safe_result`, as the aggregation logic only needs to report whether *any* error occurred. This simplifies the implementation while preserving correctness. Earlier, Junio identified a memory leak in `srealloc()` and a misleading error message in `safe_memory_limit_check()`, both of which have straightforward fixes. Phillip Wood's review has been substantive, critiquing the "safe" framing as vague, proposing a sticky error bit for usability, and flagging a bug in `sstrbuf_grow()` where `st_add3()` violates the no-`die()` guarantee.

The series is still under review, with open questions about the API's long-term scope (whether to harden the entire `strbuf` API or keep this as a niche subset), naming conventions (`sstrbuf_*` vs. `strbuf_*_gently`), and error-handling ergonomics. The current implementation leaves trace2 callers unprepared to handle errors, creating a gap where consumers might continue running after a failure. While the RFC is a functional starting point, Junio and Phillip's feedback suggests the series would benefit from broader hardening and clearer alignment with existing error-returning patterns in Git.

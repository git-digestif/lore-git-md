This is the second patch in a five-patch bugfix series addressing a data-loss race in `git repack -d` when concurrent pushes create `.keep` files mid-repack. The series is well-motivated, production-tested, and targets a real issue that can cause objects to vanish despite `.keep` protections.

This specific patch fixes a latent bug in the cruft-pack walk that becomes critical once the series removes `--honor-pack-keep`. The issue: when `pack-objects` writes a cruft pack, it first collects recent objects, marks untold packs as kept (so their objects aren’t copied), then unmarks them before walking reachability. However, the kept-pack cache isn’t invalidated after unmarking, so the walk still sees the stale cache and stops at untold packs, omitting objects that should be rescued. The fix exposes and calls `packfile_store_invalidate_kept_pack_cache()` to clear the cache after re-marking, ensuring the walk sees the current state.

The patch is minimal and surgical: it adds a single call to invalidate the cache in `enumerate_and_traverse_cruft_objects()`, updates a comment in `odb/source-packed.h`, and exposes the existing invalidation helper in `packfile.h`. The test reproduces the bug by building an unreachable chain where the middle commit sits in an untold pack; without the fix, only the recent tip is included in the cruft pack. The test is clear and fails without the patch, confirming the fix works.

This is a **correctness fix** with no behavior change under current usage (the bug is masked by `--honor-pack-keep`), but it’s essential for the series’ main goal. The commit message is excellent: it explains the bug, why it went unnoticed, and how the fix works. The patch is unlikely to be controversial, though reviewers may verify the cache invalidation is sufficient and doesn’t introduce performance regressions. It’s a prerequisite for patch 5/5, which removes `--honor-pack-keep` entirely.

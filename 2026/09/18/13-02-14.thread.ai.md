Thread identity
Subject: [RFC PATCH 0/6] Introduce a "safe" strbuf API that cannot die()
Series version: RFC (first iteration)
Originating author: Derrick Stolee
Thread type: RFC patch series

Core problem or goal
Introduce a subset of the `strbuf` API that cannot transitively call `die()` or `exit()`, motivated by a real-world problem: the trace2 subsystem (via `json-writer`) can trigger recursive `die()` loops if memory allocation fails, which is unacceptable for low-level libraries. The goal is to provide a safe alternative for code paths that must not crash, such as trace2. The series is structured in phases: (1) split `strbuf` definitions into a new header to enable the safe API, (2) refactor `GIT_ALLOC_LIMIT` initialization to avoid `die()`-prone environment parsing, (3) implement the first safe methods, including memory limit checking, and (4) integrate them into `json-writer.c`.

Current status
Under review (RFC stage). The series is progressing incrementally. Patch 1/6 moved `strbuf` struct definitions and constants to `strbuf-safe.h` (included by `strbuf.h`) to enable the safe API while preserving backward compatibility. Patch 2/6 proactively initializes `GIT_ALLOC_LIMIT` during Git’s early startup (`setup_environment()`), decoupling the limit-checking logic from `die()`-prone environment parsing. Patch 3/6 refactors the memory limit checking logic in `wrapper.c` to introduce `safe_memory_limit_check()`, which never calls `die()` and assumes `SIZE_MAX` as the limit if `git_alloc_limit` is unset. This is a prerequisite for the safe API, as it ensures allocation checks can be performed without risking fatal errors. The series remains technically sound, with CodeQL used to verify the safety property in later patches. The transition is acknowledged as incomplete: `json-writer` methods become "safe" in later patches, but their callers are not yet updated to handle errors.

Key technical details
- **New files**: `strbuf-safe.h` (defines `struct strbuf`, `strbuf_slopbuf`, `STRBUF_INIT`; included by `strbuf.h`).
- **Files touched**: `strbuf.h` (reduced to a thin wrapper including `strbuf-safe.h`), `Makefile`, `meson.build` (build system updates for `strbuf-safe.h`), `wrapper.h` (declarations of `initialize_git_alloc_limit()` and `safe_memory_limit_check()`), `wrapper.c` (implementation of `safe_memory_limit_check()`), `common-init.c` (call to `initialize_git_alloc_limit()`), and `Documentation/git.adoc` (documentation for `GIT_ALLOC_LIMIT`).
- **New symbols**: `git_alloc_limit` (global variable replacing the static `limit` in `memory_limit_check()`), `initialize_git_alloc_limit()` (initialization function), `safe_memory_limit_check()` (new function that never calls `die()`).
- **Behavior changes**: None for existing callers in this patch series. The safe API’s error-returning behavior will be introduced in later patches. The `GIT_ALLOC_LIMIT` initialization is now explicit and occurs during startup, avoiding implicit `die()` calls from `git_env_ulong()`. The `safe_memory_limit_check()` function assumes `SIZE_MAX` as the limit if `git_alloc_limit` is unset, which may result in slightly more permissive allocation checks if called *very* early in Git’s startup (before `GIT_ALLOC_LIMIT` is initialized), but this is deemed an acceptable trade-off for safety.
- **Naming convention**: `sstrbuf_*` (instead of `strbuf_*_gently`), justified in the series as clearer for the intended use case.
- **Test coverage**: No new tests introduced in this RFC; the focus is on API design and safety verification via CodeQL. The `GIT_ALLOC_LIMIT` documentation is now present in `Documentation/git.adoc`.

Open questions and loose ends
- **Approach**: Whether the "safe" API is the right solution (vs. hardening the existing API or using a different error-handling strategy).
- **Naming**: Whether `sstrbuf_*` is preferable to `strbuf_*_gently`.
- **`GIT_ALLOC_LIMIT`**: The series documents the variable and resists renaming it to `GIT_TEST_ALLOC_LIMIT` (despite its test-oriented origin), citing Hyrum’s Law and the possibility of external usage. This decision may draw pushback.
- **Transition plan**: How to handle errors in `json-writer` callers (currently unaddressed in this series).
- **Scope**: Whether the safe API should eventually replace the existing API in more places or remain a niche alternative.
- **Timing assumptions**: The safe API assumes `GIT_ALLOC_LIMIT` is initialized before any safe methods are called. While the series proactively initializes it during startup, the assumption may need validation for edge cases (e.g., very early calls).
- **Fallback behavior**: Whether assuming `SIZE_MAX` as the limit when `git_alloc_limit` is unset is sufficiently robust for all edge cases.

Participant positions
- **Derrick Stolee (author)**: Proposes the safe API as a solution to the trace2 recursion problem, with a two-phase transition plan (land the API first, then refactor callers). Justifies the `sstrbuf_*` naming convention and the decision to retain `GIT_ALLOC_LIMIT` (rather than rename it). Acknowledges the incomplete transition but argues for incremental progress. The refactoring of `GIT_ALLOC_LIMIT` initialization and the introduction of `safe_memory_limit_check()` are presented as necessary steps to avoid `die()` calls in the safe API.

Related work
- **Trace2 subsystem**: The primary motivator for this series, as it must not crash.
- **`json-writer.c`**: Early adopter of the safe API (in later patches), though callers are not yet updated to handle errors.
- **`GIT_ALLOC_LIMIT`**: Previously undocumented; this series documents it and moves its initialization to process startup.
- **CodeQL**: Used to verify the safety property of the new API (in later patches).

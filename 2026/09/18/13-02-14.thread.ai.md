Thread identity
Subject: [RFC PATCH 0/6] Introduce a "safe" strbuf API that cannot die()
Series version: RFC (first iteration, now abandoned)
Originating author: Derrick Stolee
Thread type: RFC patch series (now closed)

Core problem or goal
Introduce a subset of the `strbuf` API that cannot transitively call `die()` or `exit()`, motivated by the trace2 subsystem (via `json-writer`) requiring crash-free operation even under memory pressure. The goal was to provide a safe alternative for critical code paths like trace2. Junio C Hamano endorsed the direction of making core service routines "safe" as part of the broader libification trend but questioned whether carving out a niche "safe" subset was the right long-term strategy. Jeff King (Peff) proposed an alternative: **fixed-size, stack-allocated `strbuf`-like buffers** (e.g., `static_strbuf`) that avoid `malloc()` entirely, arguing this would better serve the trace2 use case by eliminating dynamic allocation failures rather than handling them. Peff also critiqued the "safe" framing as misleading, noting the API would still not be safe for signal handlers (due to `malloc()` locks) and would only address a narrow aspect of safety (malloc failures).

Current status
**Abandoned.** Derrick Stolee has set the RFC series aside indefinitely after substantive critiques from Peff and Phillip Wood. The series reached patch 6/6 but will not be revised or resubmitted in the near term. Key unresolved issues remain:
- The **memory leak bug** in `srealloc()` (identified by Junio), where `realloc()` failure clobbers the caller’s pointer.
- The **safety violation** in `sstrbuf_grow()` (identified by Phillip Wood), which uses `st_add3()` and thus calls `die()` on overflow.
- The **incomplete transition** in `json-writer.c`, where callers are not updated to handle errors, leaving a window where consumers may continue running after an error occurs.
- The **naming and usability concerns** (e.g., `sstrbuf_*` vs. `strbuf_*_gently`, error checking on every call vs. a sticky error bit).
- The **architectural debate** between hardening the existing `strbuf` API (RFC approach) and replacing dynamic allocation with fixed-size buffers (Peff’s proposal).

Peff’s alternative design—fixed-size buffers with a sticky error bit—remains the most viable path forward for addressing the trace2 use case, but no active work is underway. The broader question of how to make `strbuf` operations safe for critical code paths is unresolved.

Key technical details
- **New files (proposed)**: `strbuf-safe.h` (defines `struct strbuf`, `strbuf_slopbuf`, `STRBUF_INIT`, `enum safe_result` with values `SUCCESS` and `MEMORY_ERROR`, and declarations for `sstrbuf_init()`, `sstrbuf_release()`, `sstrbuf_grow()`), `strbuf-safe.c` (implementation of `sstrbuf_init()`, `sstrbuf_release()`, `sstrbuf_grow()`, and the `SAFE_ALLOC_GROW` macro).
- **Files touched (proposed)**: `strbuf.h` (reduced to a thin wrapper including `strbuf-safe.h`), `strbuf.c` (delegates `strbuf_init()`, `strbuf_release()`, and `strbuf_grow()` to their safe counterparts and dies on failure), `wrapper.h`/`wrapper.c` (declarations/implementation of `initialize_git_alloc_limit()`, `safe_memory_limit_check()`, and `srealloc()`), `Makefile`, `meson.build`, `common-init.c`, `Documentation/git.adoc`, `json-writer.c`/`json-writer.h`, `tr2_tgt_event.c`, `tr2_tgt_perf.c`.
- **New symbols (proposed)**: `sstrbuf_init()`, `sstrbuf_release()`, `sstrbuf_grow()`, `SAFE_ALLOC_GROW`, `srealloc()`, `enum safe_result`.
- **Behavior changes (proposed)**: `jw_release()` would return an error code (nonzero on failure), and `fmt_double()`/`append_sub_jw()` would propagate errors from the safe API. The existing `strbuf` API would remain unchanged (still dies on failure). The safe API would be opt-in, and the transition in `json-writer.c` was partial.
- **Bugs (unresolved)**:
  - `sstrbuf_grow()` uses `st_add3()`, which calls `die()` on overflow (violating the safety guarantee).
  - `srealloc()` clobbers the caller’s pointer on failure, leaking memory.
  - The error message in `safe_memory_limit_check()` was corrected to report the effective limit (`SIZE_MAX`) instead of the original `git_alloc_limit` value, but this was not part of the abandoned series.
- **Assumptions (proposed)**: The safe API assumed `GIT_ALLOC_LIMIT` was initialized before use. The series proactively initialized it during startup, but edge cases (e.g., very early calls) may need validation.
- **Peff’s alternative design**: Fixed-size, stack-allocated buffers (e.g., `static_strbuf`) with a pre-allocated size (e.g., 4KB or per-struct max size). These would avoid `malloc()` entirely, eliminating dynamic allocation failures but introducing deterministic failure modes (e.g., buffer overflow). Peff suggested a **sticky error bit** (like C’s `stdio` functions) to simplify error handling, allowing deferred error checking until the final result is needed.
- **Error detail limitation**: Junio clarified that the "safe" API would not preserve error details (it cannot allocate memory to format them), reinforcing the distinction between crash avoidance and full error handling.

Open questions and loose ends
- **Approach**: Whether the "safe" API should harden the existing `strbuf` API (abandoned RFC), replace dynamic allocation with fixed-size buffers (Peff’s proposal), or pursue another strategy. Peff’s critique suggests the abandoned approach may have been solving the wrong problem, as it did not address signal-safety or other aspects of "safety."
- **Naming**: Whether `sstrbuf_*` or `strbuf_*_gently` (or another scheme) would be preferable. Phillip Wood and Peff argued for alignment with existing error-returning APIs (e.g., `xdiff`, `reftable`).
- **Usability**: Whether error checking on every `strbuf` call is acceptable, or if a sticky error bit (proposed by Phillip Wood and endorsed by Peff) would be more ergonomic. Junio’s feedback on `jw_release()`’s error aggregation logic also touched on this, suggesting a plain `int` return type for simplicity.
- **`GIT_ALLOC_LIMIT`**: The series documented the variable and resisted renaming it to `GIT_TEST_ALLOC_LIMIT`, citing Hyrum’s Law. This decision may draw pushback if the topic is revisited.
- **Transition plan**: How to handle errors in `json-writer` callers (e.g., in trace2). The safe API would return errors, but existing callers are not prepared to handle them. The abandoned series deferred this work, leaving a window where consumers may continue running after an error occurs.
- **Scope**: Whether the safe API should eventually replace the existing API in more places or remain a niche alternative for critical code paths. Junio’s feedback suggested the former, while the abandoned series implemented the latter.
- **Error granularity**: Whether `enum safe_result` (currently `SUCCESS`/`MEMORY_ERROR`) is sufficient or more granular codes are needed (e.g., `LIMIT_ERROR`). Junio’s feedback on `jw_release()` suggested the API should accommodate future expansion, but Peff’s alternative design may obviate this need.
- **`srealloc()` visibility**: Whether `srealloc()` should be exposed in `wrapper.h` or kept internal to the safe API.
- **Performance overhead**: The trade-off between safety (error-code returns) and performance (the overhead of checking return values vs. the simplicity of `die()`).
- **Fallback behavior**: Whether assuming `SIZE_MAX` as the limit when `git_alloc_limit` is unset is robust for all edge cases.
- **Header hygiene**: Patch 5/6 addressed known cases where `json-writer.h` transitively included `strbuf.h`, but other implicit dependencies may exist.
- **Error propagation**: Whether the deferred adaptation of `json-writer` callers is acceptable, or if the series should have included those changes.
- **Safety guarantees**: The use of `banned-die.h` in `json-writer.c` enforces the no-`die()` rule, but the bugs in `sstrbuf_grow()` and `srealloc()`, and the incomplete transition to error-aware callers, would have limited its effectiveness.
- **API surface clarity**: Junio suggested renaming higher-level utilities like `strbuf_realpath()` to avoid the `strbuf_` prefix, as they are not fundamental `strbuf` operations.
- **Signal safety**: Peff noted that the "safe" API would still not be safe for signal handlers due to `malloc()` locks, undermining the trace2 use case. This raises the question of whether the API’s guarantees would have been sufficient for its intended purpose.
- **Error detail preservation**: Junio clarified that the "safe" API would not preserve error details (it cannot allocate memory to format them), reinforcing the distinction between crash avoidance and full error handling.

Thread identity
Subject: [RFC PATCH 0/6] Introduce a "safe" strbuf API that cannot die()
Series version: RFC (first iteration, now complete at patch 6/6)
Originating author: Derrick Stolee
Thread type: RFC patch series

Core problem or goal
Introduce a subset of the `strbuf` API that cannot transitively call `die()` or `exit()`, motivated by a real-world problem: the trace2 subsystem (via `json-writer`) can trigger recursive `die()` loops if memory allocation fails, which is unacceptable for low-level libraries. The goal is to provide a safe alternative for code paths that must not crash, such as trace2. The series is structured in phases: (1) split `strbuf` definitions into a new header to enable the safe API, (2) refactor `GIT_ALLOC_LIMIT` initialization to avoid `die()`-prone environment parsing, (3) implement the first safe methods (including `sstrbuf_grow()`), (4) integrate them into `json-writer.c`, (5) prepare `json-writer.c` for safe API adoption by switching its header inclusion to `strbuf-safe.h`, and (6) add the remaining core methods (`sstrbuf_init()`, `sstrbuf_release()`) and begin converting `json-writer.c` to use them.

Current status
Under review (RFC stage). The series is now complete at patch 6/6. Patch 1/6 moved `strbuf` struct definitions and constants to `strbuf-safe.h` (included by `strbuf.h`) to enable the safe API while preserving backward compatibility. Patch 2/6 proactively initializes `GIT_ALLOC_LIMIT` during Git’s early startup (`setup_environment()`), decoupling the limit-checking logic from `die()`-prone environment parsing. Patch 3/6 refactored the memory limit checking logic in `wrapper.c` to introduce `safe_memory_limit_check()`, which never calls `die()` and assumes `SIZE_MAX` as the limit if `git_alloc_limit` is unset. Patch 4/6 implements the first safe method, `sstrbuf_grow()`, which replaces the `ALLOC_GROW` macro with a new `SAFE_ALLOC_GROW` macro that uses `srealloc()` (a safe version of `xrealloc()`) and returns an error code instead of dying. The existing `strbuf_grow()` is updated to call `sstrbuf_grow()` and die on failure, preserving backward compatibility. Patch 5/6 switches `json-writer.c` to include `strbuf-safe.h` instead of `strbuf.h`, a mechanical change that prepares the file for safe API adoption in later patches. Patch 6/6 adds the remaining core methods (`sstrbuf_init()`, `sstrbuf_release()`) to the safe API and begins converting `json-writer.c` to use them. The `jw_release()` function now returns an error code (aggregating the results of both `sstrbuf_release()` calls), and two helper functions (`fmt_double()`, `append_sub_jw()`) are updated to propagate errors from the safe API. The `json-writer` methods are now "safe" in the sense that they cannot call `die()`, but their callers (e.g., in trace2) are not yet updated to handle errors, leaving a window where consumers may continue running after an error occurs. The series remains technically sound, with CodeQL used to verify the safety property in later patches. The transition is acknowledged as incomplete: the safe API is now functionally complete, but its adoption in `json-writer` is partial, and callers are not yet error-aware.

Key technical details
- **New files**: `strbuf-safe.h` (defines `struct strbuf`, `strbuf_slopbuf`, `STRBUF_INIT`, `enum safe_result` with values `SUCCESS` and `MEMORY_ERROR`, and declarations for `sstrbuf_init()`, `sstrbuf_release()`, `sstrbuf_grow()`), `strbuf-safe.c` (implementation of `sstrbuf_init()`, `sstrbuf_release()`, `sstrbuf_grow()`, and the `SAFE_ALLOC_GROW` macro).
- **Files touched**: `strbuf.h` (reduced to a thin wrapper including `strbuf-safe.h`), `strbuf.c` (delegates `strbuf_init()`, `strbuf_release()`, and `strbuf_grow()` to their safe counterparts and dies on failure), `wrapper.h` (declarations of `initialize_git_alloc_limit()`, `safe_memory_limit_check()`, and `srealloc()`), `wrapper.c` (implementation of `srealloc()`), `Makefile`, `meson.build` (build system updates for `strbuf-safe.c` and `strbuf-safe.h`), `common-init.c` (call to `initialize_git_alloc_limit()`), `Documentation/git.adoc` (documentation for `GIT_ALLOC_LIMIT`), `json-writer.c` (converted to use `sstrbuf_init()` and `sstrbuf_release()`, with `jw_release()` now returning an error code and helper functions propagating errors), `json-writer.h` (signature of `jw_release()` updated to return `int`), `tr2_tgt_event.c` and `tr2_tgt_perf.c` (now explicitly include `strbuf.h`).
- **New symbols**: `sstrbuf_init()` (safe version of `strbuf_init()`), `sstrbuf_release()` (safe version of `strbuf_release()`), `sstrbuf_grow()` (safe version of `strbuf_grow()`), `SAFE_ALLOC_GROW` (macro replacing `ALLOC_GROW` for safe allocations), `srealloc()` (safe version of `xrealloc()`), `enum safe_result` (standardized error codes for the safe API).
- **Behavior changes**: `jw_release()` now returns an error code (nonzero on failure), and `fmt_double()`/`append_sub_jw()` propagate errors from the safe API. The existing `strbuf_init()`, `strbuf_release()`, and `strbuf_grow()` still die on failure, so no behavior change for existing callers. The safe API is opt-in, and the transition in `json-writer.c` is partial: `jw_init()` remains unchanged (as it does not allocate memory), while `jw_release()` and helpers are updated. The patch adds `#include "banned-die.h"` to `json-writer.c` to enforce the no-`die()` rule.
- **Naming convention**: `sstrbuf_*` (e.g., `sstrbuf_init()`, `sstrbuf_release()`, `sstrbuf_grow()`) for safe methods, justified in the series as clearer for the intended use case than `strbuf_*_gently`.
- **Test coverage**: No new tests introduced in this RFC; the focus is on API design and safety verification via CodeQL. The `GIT_ALLOC_LIMIT` documentation is now present in `Documentation/git.adoc`.
- **Error handling**: The safe API uses `enum safe_result` (`SUCCESS`/`MEMORY_ERROR`) for consistency. `jw_release()` aggregates errors without short-circuiting (both buffers are released even if one fails). The `srealloc()` function returns `NULL` on failure (like `realloc()`), unlike `xrealloc()` which dies.

Open questions and loose ends
- **Approach**: Whether the "safe" API is the right solution (vs. hardening the existing API or using a different error-handling strategy).
- **Naming**: Whether `sstrbuf_*` is preferable to `strbuf_*_gently` or another naming scheme.
- **`GIT_ALLOC_LIMIT`**: The series documents the variable and resists renaming it to `GIT_TEST_ALLOC_LIMIT` (despite its test-oriented origin), citing Hyrum’s Law and the possibility of external usage. This decision may draw pushback.
- **Transition plan**: How to handle errors in `json-writer` callers (e.g., in trace2). The safe API returns errors, but existing callers may not be prepared to handle them. The series defers this work to future patches, leaving a window where consumers may continue running after an error occurs.
- **Scope**: Whether the safe API should eventually replace the existing API in more places or remain a niche alternative for critical code paths like trace2.
- **Error granularity**: Whether `enum safe_result` (currently `SUCCESS` and `MEMORY_ERROR`) is sufficient or more granular error codes are needed (e.g., for limit violations vs. allocation failures).
- **`srealloc()` visibility**: Whether `srealloc()` should be exposed in `wrapper.h` or kept internal to the safe API.
- **Performance overhead**: The trade-off between safety (error-code returns) and performance (the overhead of checking return values vs. the simplicity of `die()`).
- **Timing assumptions**: The safe API assumes `GIT_ALLOC_LIMIT` is initialized before any safe methods are called. While the series proactively initializes it during startup, the assumption may need validation for edge cases (e.g., very early calls).
- **Fallback behavior**: Whether assuming `SIZE_MAX` as the limit when `git_alloc_limit` is unset is sufficiently robust for all edge cases.
- **Header hygiene**: Patch 5/6 addressed the two known cases where `json-writer.h` transitively included `strbuf.h` (trace2 targets), but there may be other implicit dependencies elsewhere in the codebase.
- **Error propagation**: Whether the deferred adaptation of `json-writer` callers is acceptable, or if the series should include those changes now. The patch adds `#include "banned-die.h"` to `json-writer.c`, but callers are not yet error-aware.
- **Safety guarantees**: The use of `banned-die.h` in `json-writer.c` enforces the no-`die()` rule, but the incomplete transition to error-aware callers may limit its effectiveness in practice.

Participant positions
- **Derrick Stolee (author)**: Proposes the safe API as a solution to the trace2 recursion problem, with a two-phase transition plan (land the API first, then refactor callers). Justifies the `sstrbuf_*` naming convention and the decision to retain `GIT_ALLOC_LIMIT` (rather than rename it). Acknowledges the incomplete transition but argues for incremental progress. The refactoring of `GIT_ALLOC_LIMIT` initialization and the introduction of the safe API are presented as necessary steps to avoid `die()` calls in critical code paths. The final patch completes the safe API’s core functionality and begins converting `json-writer.c` to use it, while deferring caller adaptation to future work.

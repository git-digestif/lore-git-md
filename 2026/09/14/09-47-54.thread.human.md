This thread introduces an opt-in incremental connectivity check for Git fetches and pushes, aimed at reducing the performance cost of verifying object connectivity in large repositories. The feature, proposed by Kristofer Karlsson, adds a new configuration option `transfer.connectivityCheck=incremental` that processes incoming commits incrementally against their parents rather than walking the full object closure of boundary commits. This shifts the cost from repository size to the size of incoming changes, offering dramatic speedups—up to 190x faster with significantly lower memory usage—for small pushes to large repos, while introducing only a modest slowdown for very long incoming histories.

The implementation, now at version 2, addresses all prior feedback from Junio C Hamano, including hardening lazy-fetch protection and adding explicit NULL checks in the verifier logic. The core of the feature is a new `tree-verify.c` file that implements the incremental algorithm, which processes commits in topological order, skips unchanged subtrees, and verifies only new or modified objects. The patch integrates seamlessly with the existing `check_connected()` machinery and preserves partial-clone semantics, ensuring promised objects are handled correctly. Extensive test coverage verifies semantic equivalence with the full check, corruption detection, and edge cases like shallow boundaries and submodule handling.

The series is under active review, with no unresolved objections. The first patch (documentation) has been posted, and this second patch (implementation) is now available for further scrutiny. While the feature is opt-in and falls back to the full check for edge cases, one lingering question is whether the commit boundary-finding step could be optimized further for repositories with many refs. The series appears ready for broader review, with a strong foundation of testing and performance benchmarks to support its adoption.

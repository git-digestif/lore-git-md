This thread introduces an opt-in incremental connectivity check for Git fetches and pushes, aiming to reduce the performance cost of verifying object connectivity in large repositories. The feature, proposed by Kristofer Karlsson, is now in its third version and has gained strong interest from maintainer Junio C Hamano, who called it "exciting" and accepted its performance trade-offs (a 1.5x slowdown for very long incoming histories) as reasonable for an opt-in feature.

The series is split into four patches: documentation, baseline performance tests, config plumbing, and the core implementation. All prior feedback has been addressed, including concerns about NULL-dereference risks, lazy-fetch handling, and documentation clarity. The implementation reuses Git’s existing boundary-detection mechanism but processes incoming commits incrementally, verifying only changed subtrees against trusted parent trees. Benchmarks show up to 190x speedup for small pushes to large repositories, with memory usage reduced from gigabytes to megabytes.

Two open questions remain. First, whether to add a dynamic fallback mechanism for very long incoming histories (10,000+ commits), which Kristofer framed as a trade-off between safety and code simplicity. Second, a refactoring suggestion from Junio to reduce reliance on Git’s global `the_repository` variable—this has now been settled, with Junio deferring a broader cleanup to avoid scope creep. The next reroll will focus on a narrow change to `check_connected_options`, while the larger architectural work remains a potential follow-up.

The series is effectively cleared from a maintainer perspective and is now awaiting further feedback from other reviewers. Key participants include Kristofer (author), Junio (maintainer), and Patrick Steinhardt (reviewer), with no unresolved objections. The feature is opt-in via `transfer.connectivityCheck=incremental` and falls back to the full check for edge cases like deepening fetches or promisor objects.

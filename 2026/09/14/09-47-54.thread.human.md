This thread introduces an opt-in incremental connectivity check for Git fetches and pushes, aiming to reduce the performance cost of verifying object connectivity. The feature, proposed by Kristofer Karlsson, is now in its third version (v3) as a four-patch series and is under active review.

The core idea is to shift the cost of connectivity checks from repository size to the size of incoming changes. Instead of walking the full object closure of boundary commits, the new `transfer.connectivityCheck=incremental` mode processes incoming commits in topological order, verifying trees only where they differ from trusted parent trees. This approach reuses Git’s existing `--not --all` boundary-detection mechanism and falls back to the full check for edge cases like deepening fetches, very long histories (10,000+ commits), shallow boundaries, and promisor objects. The implementation is split into four patches: documentation, baseline performance tests, config plumbing, and the core logic in `tree-verify.c`.

Key participants include Junio C Hamano, who raised initial concerns about edge-case robustness (now addressed), and Patrick Steinhardt, who provided detailed feedback on documentation clarity, trust boundary detection, and performance trade-offs. All prior feedback has been resolved, and the series is rebased onto the latest master. Benchmarks show dramatic speedups (up to 190x faster, with significantly lower memory usage) for small pushes to large repositories, though very long incoming histories may see modest regressions. The feature is production-ready behind its opt-in config, with future scalability improvements (like MIDX-based connectivity closure) explicitly out of scope for now.

The series is still awaiting further review, with no merge status reported. The implementation is thoroughly tested, including semantic equivalence with the full check, corruption detection, and integration with fetch/push/clone workflows.

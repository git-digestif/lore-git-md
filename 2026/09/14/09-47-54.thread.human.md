This thread is about an opt-in performance feature for Git’s fetch and push operations: an incremental connectivity check that reduces the cost of verifying object connectivity by processing only incoming commits and their changed subtrees, rather than scanning the entire repository. The feature is controlled by a new configuration option, `transfer.connectivityCheck`, which supports three modes—`full` (the default), `incremental`, and `auto[=<n>]`—with a configurable 1,000-commit cutoff for the auto mode to balance performance and safety.

The series, now in its fourth iteration, is complete and ready for integration. It consists of six patches covering documentation, baseline performance tests, refactoring to remove reliance on the global `the_repository` variable, config plumbing, the core implementation, and the auto mode with dynamic fallback. All prior feedback has been addressed, and the maintainer, Junio C Hamano, has signaled strong interest. The implementation introduces a new `tree-verify.c` subsystem that inductively trusts parent trees and verifies only new or modified subtrees, using a merge-walk to collect same-path parent subtrees and skipping gitlinks and promisor objects. Performance benchmarks show up to 190x speedups for small pushes to large repositories, with negligible overhead for small repos.

The latest exchange in the thread addresses two forward-looking maintainability concerns raised by Junio: the implicit lazy-fetching assumption in the config parser and the handling of promisor objects in the blob verifier. Kristofer Karlsson, the author, agrees with both points and proposes adjustments—simplifying the lazy-fetching logic to always disable fetches during connectivity checks, and deferring a more explicit promisor-object refactoring to a follow-up patch. These changes are uncontroversial and will likely appear in a v5 revision, but they do not block integration. The series remains on track for inclusion, with no outstanding technical objections.

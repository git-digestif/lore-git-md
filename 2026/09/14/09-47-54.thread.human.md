This thread introduces an opt-in incremental connectivity check for Git fetches and pushes, aiming to reduce the cost of verifying object connectivity. The feature, now in its third version, is implemented as a four-patch series that adds documentation, baseline performance tests, config plumbing, and the core implementation. Kristofer Karlsson is the author, and the series has drawn strong interest from Junio C Hamano, who called it "exciting" and accepted its performance trade-offs—specifically, a 1.5x slowdown for very long incoming histories and a fallback to the full check for deepening fetches—as reasonable for an opt-in feature.

The series is effectively cleared from a maintainer perspective, with all prior feedback addressed. The only remaining technical point is a refactoring suggestion from Junio to reduce reliance on the `the_repository` global variable, which Kristofer plans to address in the next reroll. The implementation introduces a new config key (`transfer.connectivityCheck=incremental`), a new internal `rev-list` flag (`--verify-trees-incremental`), and a new source file (`tree-verify.c`) that implements the incremental verification logic. Performance benchmarks show up to a 190x speedup for small pushes to large repositories, though the feature falls back to the full check for edge cases like deepening fetches or very long histories.

The latest email from Kristofer raises a new design question: whether to add a dynamic fallback mechanism that disables incremental mode when the number of incoming commits exceeds a threshold. He seeks explicit guidance on whether to hardcode a limit, make it configurable, or leave the current implementation unchanged. The trade-off is between immediate safety and long-term code simplicity, and Kristofer leans toward a single, universally performant implementation but acknowledges the uncertainty. The question is now open for discussion, with no technical changes proposed yet.

This thread introduces an opt-in incremental connectivity check for Git fetches and pushes, aiming to reduce the performance cost of verifying object connectivity in large repositories. The feature, proposed by Kristofer Karlsson, is now in its third version (v3) and has gained strong support from Junio C Hamano, the project maintainer.

The series adds a new configuration option, `transfer.connectivityCheck=incremental`, which processes incoming commits in topological order, verifying only the changes against trusted parent trees. This shifts the cost from repository size to the size of incoming changes, offering up to a 190x speedup for small pushes to large repos while introducing a modest 1.5x slowdown for very long incoming histories (10,000+ commits). The implementation falls back to the full check for edge cases like deepening fetches, shallow boundaries, and promisor objects, ensuring robustness. All prior feedback—including concerns about NULL-dereference risks, lazy-fetch handling, and documentation clarity—has been addressed, and the series is rebased onto the latest master.

Junio’s latest response signals enthusiasm for the feature, calling it "exciting" and accepting the trade-offs as reasonable for an opt-in mode. No new technical concerns were raised, and the series appears technically sound from the maintainer’s perspective. The only remaining loose end is a minor refactoring suggestion to reduce reliance on the `the_repository` global variable, which aligns with the project’s ongoing architectural goals but is not a blocker. With Junio’s endorsement, the series is now poised for integration, pending any further review from other contributors.

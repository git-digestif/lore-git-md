This is **patch 3/6 in a six-patch bugfix series** targeting a data-loss race in `git repack -d` when concurrent pushes are active. The series as a whole is production-tested, well-motivated, and under active review; this patch fixes a pre-existing bug in the cruft-pack walk that was masked by `--honor-pack-keep` but will become critical once the series removes that flag.

The bug: when `git pack-objects` writes a cruft pack with an expiration, it first collects recent objects (marking any pack it wasn’t told about as “kept” so their objects aren’t copied), then unmarks those packs so the subsequent reachability walk can traverse them. However, the walk consults a cache that was built during collection and never invalidated, so it still sees the packs as kept, halting the walk prematurely. Objects beyond those packs—even if they are reachable from the recent objects—are silently omitted from the cruft pack, leading to data loss.

The fix: after re-marking only the fresh packs as kept, the patch explicitly invalidates the kept-pack cache for every ODB source. This ensures the walk rebuilds the cache with the current in-core marks and can traverse the previously unknown packs. The change is minimal—exposing and calling an existing invalidation helper—and is exercised by a new test that builds an unreachable chain whose middle commit sits in an untold pack; without the fix, only the recent tip is rescued.

Files touched: `builtin/pack-objects.c` (adds the invalidation call), `odb/source-packed.h` (doc update), `packfile.c`/`packfile.h` (exposes the helper), and `t/t5329-pack-objects-cruft.sh` (adds the test). The patch is a prerequisite for patch 6/6, which removes `--honor-pack-keep` entirely, making this bug unmasked and therefore critical.

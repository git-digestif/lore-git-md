This is a two-patch **performance feature** introducing an incremental connectivity check for Git, gated behind the `transfer.connectivityCheck=incremental` configuration. The goal is to reduce the cost of verifying object connectivity during fetches and pushes, particularly in large repositories where the existing full check scales poorly with repository size.

The patch series adds a new internal `rev-list` flag (`--verify-trees-incremental`) that runs the verifier inside the same subprocess already used by `check_connected()`. Instead of walking the entire reachable object closure, the incremental mode processes incoming commits in topological order, tracking a growing set of "trusted" objects (derived from parent commits) to skip unchanged subtrees. This shifts the cost from being proportional to the repository size to being proportional to the size of the incoming changes.

Benchmark results show dramatic speedups for small pushes to large repositories (up to 190x faster for a single commit in a 3.4 GB boundary closure), with memory usage also significantly reduced (14 MB vs. 3.4 GB in the same case). The incremental mode does introduce a modest regression (1.5x slower) for very long incoming histories (10,000+ commits), but the author argues this is an acceptable tradeoff for an opt-in feature targeting the common case of small pushes. Deepening fetches currently fall back to the full check, as the incremental approach would require separate work.

The implementation adds a new `tree-verify.c` file (306 lines) and updates `builtin/rev-list.c` and `connected.c` to wire up the feature. Documentation is thorough, including a new technical document (`Documentation/technical/connectivity-check.adoc`) explaining the algorithm and tradeoffs. Test coverage is extensive, with correctness tests in `t5412-connectivity-check.sh` (655 lines) and performance tests in `t/perf/p5412-connectivity-check.sh`. The tests verify semantic equivalence with the full check, corruption detection, partial clone handling, and integration with real fetch/push/clone operations.

The series builds on an earlier RFC by the same author and addresses feedback by moving the verifier into the `rev-list` subprocess (rather than running it in-process), which simplified error handling and avoided issues with lazy fetches in partial clones. The author notes that future work could optimize the commit boundary-finding step, which remains a bottleneck for repositories with many refs. The patch is well-motivated, with clear benchmarks and a conservative design (opt-in, fallback to full check for edge cases). The implementation looks clean and self-contained, touching only the necessary subsystems.

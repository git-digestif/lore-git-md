This is the v4 cover letter for a two-patch bugfix series targeting the `rerere` subsystem. The series addresses a long-standing race condition in Git’s conflict-resolution cache (`rr-cache`) where background maintenance tasks (like `git rerere gc`) can deadlock or kill an in-progress rebase when both try to acquire the `MERGE_RR.lock` simultaneously. The issue became more noticeable after Git 2.54 introduced geometric maintenance, which triggers `rerere gc` more aggressively, but the race itself is inherent to the locking design.

The first patch makes all `rerere` operations wait for the lock (configurable via `rerere.lockTimeout`, defaulting to 1000 milliseconds) instead of failing immediately, while letting background maintenance skip its run entirely if the lock is held. This ensures that a rebase can proceed even if maintenance is running concurrently, avoiding the "you have staged changes" error that previously blocked `--continue`. The second patch refines this behavior: commands that stop at a conflict (like `git rebase`, `git merge`, or `git am`) now warn and proceed if the lock remains held after the timeout, while post-resolution recording and explicit `git rerere` commands still fail. This compromise preserves the user’s ability to recover conflict preimages manually while preventing silent corruption of the `MERGE_RR` file.

The series is well-structured, with clear test coverage for edge cases (e.g., 20,000-entry `rr-cache` to trigger the race, lock-timeout scenarios, and behavior under held locks). The commit messages are detailed and address feedback from Junio, Patrick Steinhardt, and Phillip Wood, who have all reviewed earlier versions. The patches are based on `master` and merge cleanly with ongoing work like `ps/tune-rerere-gc` (which reduces maintenance frequency) and `tb/rerere-lock-grace` (a related effort to prevent maintenance from starting during rebase).

This is a pragmatic fix for a real-world problem that has disrupted workflows since Git 2.54. The solution balances robustness (allowing rebases to proceed) with correctness (failing loudly where silent skips could cause data loss). The split into two patches allows the locking changes to be evaluated separately from the behavioral compromise, which remains the most contentious part. If you use `rerere` or rely on background maintenance, this series is worth reviewing.

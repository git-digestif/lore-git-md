This is the fourth patch in a six-part **bugfix series** addressing a data-loss race in `git repack -d` when concurrent pushes are active. The series as a whole is well-motivated and production-tested, with clear commit messages and thorough test coverage.

This specific patch is a **performance optimization** for `git pack-objects`. It sorts the list of `--keep-pack` names once, then uses binary search (`string_list_has_string`) to check whether each pack in the repository is kept. The current implementation scans the entire list for every pack, which becomes prohibitively slow when the list grows large — for example, matching 20,000 kept packs against 20,000 names takes 11 seconds, compared to under a second with `--honor-pack-keep`. The optimization is a prerequisite for patch 6/6, which will allow `repack` to pass the full list of kept packs to `pack-objects` (rather than relying on `--honor-pack-keep`), eliminating the race window.

The change is mechanical and safe: the comparison function (`fspathcmp`) remains the same, so what matches does not change. The patch touches only `builtin/pack-objects.c` and is narrowly scoped to the `add_extra_kept_packs` helper. No behavior changes are introduced, and the optimization is invisible to users. The commit message clearly explains the motivation and the performance impact, making it easy for reviewers to assess.

This is a **low-risk, high-value patch** that directly enables the series' main fix. It is likely to be uncontroversial, though reviewers familiar with the ODB and repack machinery (e.g., Patrick Steinhardt, Taylor Blau) may want to confirm the sorting logic does not interact poorly with other parts of the system.

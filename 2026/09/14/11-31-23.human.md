This is the final patch in a **well-crafted, production-tested bugfix series** that closes a data-loss race in `git repack -d` when concurrent pushes are happening. The series as a whole is a **serious contribution**—the race is subtle, the fix is careful, and the tests are thorough.

This patch (6/6) is the **core fix**: it eliminates the race by ensuring `repack` and `pack-objects` work from the same snapshot of which packs are kept. Instead of letting `pack-objects` rescan the `.keep` files (which can change while it runs), `repack` now hands it the exact list it collected at startup via a new `--keep-pack-from-file` option (introduced in patch 5/6). The result is that a `.keep` appearing or disappearing mid-repack cannot make the two processes disagree about which packs are safe to delete.

The implementation is clean: the kept-pack list is written to a tempfile next to the refs snapshot already used for `multi-pack-index`, and the file is passed to every `pack-objects` invocation when `--pack-kept-objects` is not in effect. The patch also removes a redundant loop in `write_filtered_pack()` that was passing kept packs without the `.pack` suffix, which `pack-objects` would not match against. A small but important edge case is handled: pack names containing newlines are rejected up front, since they would split into two lines in the file and cause `pack-objects` to misinterpret them.

The tests added here are **strong**: one reproduces the race itself (a `.keep` appearing mid-repack), and another verifies that a kept pack does not block the traversal from rescuing objects that are only reachable through it. Both tests fail without the fix and pass with it.

This patch is **ready for serious review**—it touches the repack machinery, ODB, and tempfile handling, so it will likely attract attention from Patrick Steinhardt, Taylor Blau, and Jeff King.

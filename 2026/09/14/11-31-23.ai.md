This is the **final patch (6/6)** in a well-crafted bugfix series targeting a data-loss race in `git repack -d`. The series as a whole is production-tested, thoroughly motivated, and already summarized in the thread context; this patch is the capstone that eliminates the race by ensuring `repack` and `pack-objects` work from a single, consistent snapshot of which packs are kept.

The patch replaces the `--honor-pack-keep` mechanism (which rescans the `.keep` directory mid-repack) with a snapshot file written at startup. `repack` now passes this file to every `pack-objects` invocation via the new `--keep-pack-from-file` option (introduced in patch 5/6). The snapshot contains one `<name>.pack` per line, matching the exact set of kept packs `repack` observed when it began. This guarantees both processes agree on which packs to leave untouched, closing the window where a concurrent push could drop a `.keep` after `repack`’s scan but before `pack-objects`’s, causing objects to be lost.

Key technical details:
- The snapshot is written to a tempfile next to the refs snapshot already used for `multi-pack-index write`.
- The file is passed to all `pack-objects` invocations except the cruft pack (which already has the kept packs on stdin).
- Names with newlines are rejected up front to avoid splitting them into multiple packs.
- The patch removes a redundant loop in `write_filtered_pack()` that was passing kept packs without the `.pack` suffix.
- Alternate ODB packs are no longer skipped; they are now packed (not deleted), which trades disk space for safety.

The patch adds two tests:
1. `t7700-repack.sh` verifies `--keep-pack` with `--pack-kept-objects` still excludes the kept pack’s objects.
2. `t7703-repack-geometric.sh` reproduces the race (a `.keep` appearing mid-repack) and confirms objects are not lost. A second test ensures kept packs do not block traversal of objects reachable through them.

This is a **clean, minimal fix** for a subtle but serious bug. The design avoids introducing new races, and the tests cover both the happy path and the edge case that triggered the original data loss. The patch is likely to be uncontroversial, though reviewers may scrutinize the tempfile ownership and signal-safety guarantees (already addressed in patch 1/6). Expect attention from Patrick Steinhardt and Taylor Blau (repack/ODB maintainers).

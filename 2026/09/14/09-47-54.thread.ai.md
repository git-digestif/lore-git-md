Core problem or goal
Introduce an opt-in incremental connectivity check (`transfer.connectivityCheck=incremental` or `auto`) to reduce the cost of verifying object connectivity during fetches and pushes. The existing full check scales poorly with repository size; the new mode processes incoming commits in topological order, tracking trusted objects from parent commits to skip unchanged subtrees, shifting cost from repository size to incoming change size.

The latest update (v4) introduces a **three-mode config design** (`full`/`incremental`/`auto`) with a **configurable 1,000-commit cutoff** (via `transfer.connectivityCheckIncrementalMaxCommits` or `auto[=<n>]`, default: 1,000) for dynamic fallback to the full check, based on new benchmark data showing this threshold balances performance and safety. The `auto` mode allows safe rollout and future default changes without breaking workflows. Error handling has been refined to **avoid new `die()` calls** in library code, centralizing them at the subprocess boundary to align with Git’s libification goals. The patch now uses `size_t` for counters (`trees_loaded`, `blobs_checked`) and includes additional explanatory comments around merge-walk logic and trust boundaries. The **stack overflow risk** in recursive tree verification remains unresolved but is acknowledged as a potential follow-up.

Key technical details
- New config keys: `transfer.connectivityCheck=full|incremental|auto[=<n>]` (default: `full`), `transfer.connectivityCheckIncrementalMaxCommits=<n>` (default: 1,000)
- New internal `rev-list` flag: `--verify-trees-incremental`
- New source file: `tree-verify.c` (316 lines, implements incremental verifier with inductive trust algorithm: parent trees trusted, new trees verified only where differing from parents; tracks tree OIDs in three states: untrusted, trusted, expanded; uses merge-walk to collect same-path parent subtrees as comparison bases; skips gitlinks entirely)
- Updated files: `builtin/rev-list.c` (wires up new mode), `connected.c` (integrates verifier into `check_connected()` subprocess; reduced reliance on `the_repository`), `Documentation/config/transfer.adoc` (20 lines documenting the new config keys), `Documentation/rev-list-options.adoc` (6 lines marking the flag as internal), `Documentation/technical/connectivity-check.adoc` (109 lines, explains connectivity invariant, full check mechanics, exceptions like submodules and promisor objects, and includes example graph illustrating boundary between incoming and already-connected commits; confirmed for build system integration)
- New test files: `t5413-connectivity-check.sh` (renumbered from `t5412`, 680 lines, verifies semantic equivalence with full check, corruption detection, promisor object handling, and integration with fetch/push/clone), `t/perf/p5413-connectivity-check.sh` (renumbered from `p5412`, 92 lines, benchmarks incremental vs. full check across repository size, incoming commit count, and files changed per commit; uses synthetic repositories with flat directory structure and Perl generator to isolate connectivity-check overhead; includes `PERL` prerequisite and corrected usage comment)
- Behavior: incremental mode runs inside the existing `check_connected()` subprocess; falls back to full check for deepening fetches, shallow boundaries, promisor objects, and incoming histories exceeding the configured cutoff. Detects corruption (missing objects, malformed trees, type mismatches). The `auto` mode dynamically switches at the configured threshold.
- Trust boundary detection: relies on `git rev-list --not --all` to identify already-connected commits (old tips), then processes incoming commits in reverse topological order; each commit’s tree is verified only against its parents’ trusted trees, with memoization skipping objects seen in trusted trees.
- Error handling: `die()` calls centralized at subprocess boundary (no new `die()` calls in library code); error messages improved for missing/corrupt objects; partial-clone compatibility tested.
- Performance: up to 190x faster for small pushes to large repos (14 MB vs. 3.4 GB memory), 2.6–2.8x faster for large/medium repos at 1,000 commits, ~30% slowdown for small repos (e.g., `git.git`) but absolute times negligible (0.1–0.3s). Trace2 instrumentation measures trees loaded and blobs checked.
- On-disk format: unchanged
- Future scalability ideas (not part of current series): MIDX-based connectivity closure (precompute closed pack sets) and parallel ref loading (balance ref-loading overhead against object-checking cost)

Open questions and loose ends
- Stack overflow risk: Patrick Steinhardt questions whether the recursive tree verification could risk stack overflow for very deep trees (up to 2048 layers) and suggests using a work queue instead. Kristofer Karlsson will explore this in a follow-up but notes similar recursion exists elsewhere in Git.
- Long-term viability of subprocess architecture: whether `die()` is appropriate for server-side operations (e.g., `git-receive-pack`), where it may disrupt client communication; acknowledged as a worthwhile long-term improvement but out of scope for this series.
- Generalization of the 1,000-commit cutoff: Kristofer Karlsson notes the threshold may not generalize across all repository shapes, but benchmarks show it works well for small/medium/large repos. The configurable `auto[=<n>]` syntax allows future adjustments without breaking changes.

Core problem or goal
Introduce an opt-in incremental connectivity check (`transfer.connectivityCheck=incremental` or `auto`) to reduce the cost of verifying object connectivity during fetches and pushes. The existing full check scales poorly with repository size; the new mode processes incoming commits in topological order, tracking trusted objects from parent commits to skip unchanged subtrees, shifting cost from repository size to incoming change size.

**Series is now complete and ready for integration.** All six patches are submitted: 1/6 (technical documentation), 2/6 (baseline performance tests), 3/6 (refactoring to drop `the_repository` dependency in `connected.c`), 4/6 (config key and `rev-list` flag plumbing), 5/6 (core implementation in `tree-verify.c`), and **6/6 (auto mode with configurable cutoff)**. The **auto mode (patch 6/6)** implements the **three-mode config design** (`full`/`incremental`/`auto[=<n>]`) with a **configurable 1,000-commit cutoff** (default), dynamically switching to incremental mode for incoming histories up to the threshold and falling back to full checks above it. The heuristic reuses the existing `revs.commits` list to avoid overhead, preserves all prior fallback logic (deepening fetches, promisor objects, etc.), and is thoroughly tested with new cases in `t/t5413-connectivity-check.sh`. The cutoff is conservative but effective across repository sizes, including large monorepos.

Key technical details
- New config keys: `transfer.connectivityCheck=full|incremental|auto[=<n>]` (default: `full`), `transfer.connectivityCheckIncrementalMaxCommits=<n>` (default: 1,000)
- New internal `rev-list` flag: `--connectivity-check=full|incremental` (documented as internal in `Documentation/rev-list-options.adoc`)
- New source files: `tree-verify.c` (427 lines, implements incremental verifier with inductive trust algorithm: parent trees trusted, new trees verified only where differing from parents; tracks tree OIDs in three states: untrusted/trusted/expanded; uses merge-walk to collect same-path parent subtrees; skips gitlinks and promisor objects), `tree-verify.h` (header)
- Updated files:
  - `builtin/rev-list.c` (wires up new flag, stores mode in `struct connectivity_check`, invokes `tree_verify()` for incremental mode; **patch 6/6 adds auto-mode logic**)
  - `connected.c` (reads config, passes mode to `rev-list`; now accepts explicit `struct repository *` parameter; **patch 6/6 adds auto-mode fallback logic**)
  - `Documentation/config/transfer.adoc` (documents new config keys)
  - `Documentation/rev-list-options.adoc` (marks flag as internal)
  - `Documentation/technical/connectivity-check.adoc` (259 lines, explains connectivity invariant, full check mechanics, exceptions like submodules and promisor objects, and includes example graph illustrating boundary between incoming and already-connected commits; confirmed for build system integration in both `Makefile` and `meson.build`)
- **New test files:**
  - `t/t5413-connectivity-check.sh` (795 lines, verifies semantic equivalence with full check, corruption detection, promisor object handling, integration with fetch/push/clone, and **auto-mode fallback behavior**; covers correctness and performance via Trace2 counts)
  - `t/perf/p5413-connectivity-check.sh` (92 lines, benchmarks incremental vs. full check across repository size, incoming commit count, and files changed per commit; uses synthetic repositories with flat directory structure and Perl generator to isolate connectivity-check overhead; includes `PERL` prerequisite and corrected usage comment)
- Behavior: incremental mode runs inside the existing `check_connected()` subprocess; falls back to full check for deepening fetches, shallow boundaries, promisor objects, and incoming histories exceeding the configured cutoff. The `auto` mode dynamically switches at the threshold. Detects corruption (missing objects, malformed trees, type mismatches). Trust boundary detection relies on `git rev-list --not --all` to identify already-connected commits, then processes incoming commits in reverse topological order.
- Data structures: `kh_oid_tree_t` map tracks tree OIDs in three states (untrusted/trusted/expanded); `oidset` tracks trusted blobs; `work_list` queues untrusted entries for verification.
- Performance instrumentation: Trace2 events (`trees_loaded`, `blobs_checked`) measure overhead.
- Error handling: `die()` calls centralized at subprocess boundary (no new `die()` in library code); error messages improved for missing/corrupt objects; partial-clone compatibility tested.
- Performance: up to 190x faster for small pushes to large repos (14 MB vs. 3.4 GB memory), 2.6–2.8x faster for large/medium repos at 1,000 commits, ~30% slowdown for small repos (e.g., `git.git`) but absolute times negligible (0.1–0.3s). Trace2 instrumentation measures trees loaded and blobs checked.
- On-disk format: unchanged
- Future scalability ideas (not part of current series): MIDX-based connectivity closure (precompute closed pack sets) and parallel ref loading (balance ref-loading overhead against object-checking cost)

Open questions and loose ends
- **Stack overflow risk**: Patrick Steinhardt questions whether the recursive tree verification in `tree-verify.c` could risk stack overflow for very deep trees (up to 2048 layers) and suggests using a work queue instead. Kristofer Karlsson will explore this in a follow-up but notes similar recursion exists elsewhere in Git. The risk is acknowledged in the commit message and documentation.
- **Lazy-fetching assumption in `parse_connectivity_check()`**: Junio C Hamano flags the unconditional `repo->fetch_if_missing = 0` for non-`full` modes as a potential trap for future developers. The code assumes that any mode other than `full` should avoid lazy fetching, but this is not explicitly documented or enforced. Kristofer Karlsson proposes simplifying the logic by **always setting `fetch_if_missing = 0` for any connectivity check**, regardless of mode, to avoid the trap. This adjustment will be included in v5.
- **Explicit promisor-object handling in `verify_blob()`**: Junio questions whether `odb_read_object_info()` should use an explicit flag (e.g., `_extended()`) to avoid promisor fetches, rather than relying on `repo->fetch_if_missing`. Kristofer Karlsson acknowledges the merit of this approach but suggests deferring it to a **follow-up patch**, as it would require broader refactoring (e.g., adding a no-fetch flag to `repo_parse_commit_gently()` and the revision walk). The current `fetch_if_missing = 0` approach is deemed sufficient for the current series.
- **Long-term viability of subprocess architecture**: whether `die()` is appropriate for server-side operations (e.g., `git-receive-pack`), where it may disrupt client communication; acknowledged as a worthwhile long-term improvement but out of scope for this series.
- **Generalization of the 1,000-commit cutoff**: Kristofer Karlsson notes the threshold may not generalize across all repository shapes, but benchmarks show it works well for small/medium/large repos. The configurable `auto[=<n>]` syntax allows future adjustments without breaking changes.

Core problem or goal
Introduce an opt-in incremental connectivity check (`transfer.connectivityCheck=incremental` or `auto`) to reduce the cost of verifying object connectivity during fetches and pushes. The existing full check scales poorly with repository size; the new mode processes incoming commits in topological order, tracking trusted objects from parent commits to skip unchanged subtrees, shifting cost from repository size to incoming change size.

The **auto mode (patch 6/6)** implements the **three-mode config design** (`full`/`incremental`/`auto[=<n>]`) with a **configurable 1,000-commit cutoff** (default), dynamically switching to incremental mode for incoming histories up to the threshold and falling back to full checks above it. The heuristic reuses the existing `revs.commits` list to avoid overhead, preserves all prior fallback logic (deepening fetches, promisor objects, etc.), and is thoroughly tested with new cases in `t/t5413-connectivity-check.sh`. Benchmarks show the incremental mode is up to 190x faster for small pushes to large repositories (14 MB vs. 3.4 GB memory usage), with a modest 1.5x slowdown for very long incoming histories (10,000+ commits), mitigated by the auto mode fallback. The auto mode is now **fully integrated and stable**.

**Patch 4/6 (config plumbing)** adds the `transfer.connectivityCheck` configuration option (supporting `full`, `incremental`, and `auto`) and wires it through `connected.c` to `git rev-list` via the new internal flag `--connectivity-check=<mode>`. The config key is documented in `Documentation/config/transfer.adoc`, and the flag is marked as internal in `Documentation/rev-list-options.adoc`. The implementation is minimal, conservative (falling back to `full` for unknown values), and explicitly passes the mode to `rev-list` for future optimizations.

**Patch 5/6 (core implementation)** introduces the incremental verifier in `tree-verify.c` (433 lines) and `tree-verify.h` (15 lines). The verifier processes incoming commits in reverse topological order, using an inductive trust model: parent trees are trusted, and new trees are verified only where they differ from parents. It tracks tree OIDs in three states (untrusted/trusted/expanded) using `kh_oid_tree_t`, skips gitlinks and promisor objects, and avoids lazy fetches via `odb_read_object_info_extended()` with `OBJECT_INFO_SKIP_FETCH_OBJECT`. Error handling is centralized at the subprocess boundary, with detailed messages for missing/corrupt objects. The implementation is self-contained, with minimal changes to existing files (`builtin/rev-list.c`, `connected.c`) and thorough test coverage in `t/t5413-connectivity-check.sh` (795 lines). The patch also updates `t/t6700-tree-depth.sh` to enforce the same recursion limit as the full check, ensuring consistent behavior.

- Behavior: incremental mode runs inside the existing `check_connected()` subprocess; falls back to full check for deepening fetches, shallow boundaries, promisor objects, and incoming histories exceeding the configured cutoff. The `auto` mode dynamically switches at the threshold. Detects corruption (missing objects, malformed trees, type mismatches). Trust boundary detection relies on `git rev-list --not --all` to identify already-connected commits, then processes incoming commits in reverse topological order.
- Data structures: `kh_oid_tree_t` map tracks tree OIDs in three states (untrusted/trusted/expanded); `oidset` tracks trusted blobs; `work_list` queues untrusted entries for verification.
- Performance instrumentation: Trace2 events (`trees_loaded`, `blobs_checked`) measure overhead.
- Error handling: `die()` calls centralized at subprocess boundary (no new `die()` in library code); error messages improved for missing/corrupt objects; partial-clone compatibility tested.
- Performance: up to 190x faster for small pushes to large repos (14 MB vs. 3.4 GB memory), 2.6–2.8x faster for large/medium repos at 1,000 commits, ~30% slowdown for small repos (e.g., `git.git`) but absolute times negligible (0.1–0.3s). Trace2 instrumentation measures trees loaded and blobs checked.
- On-disk format: unchanged
- Future scalability ideas (not part of current series): MIDX-based connectivity closure (precompute closed pack sets) and parallel ref loading (balance ref-loading overhead against object-checking cost)

Open questions and loose ends
- **Stack overflow risk**: Patrick Steinhardt questions whether the recursive tree verification in `tree-verify.c` could risk stack overflow for very deep trees (up to 2048 layers) and suggests using a work queue instead. Kristofer Karlsson will explore this in a follow-up but notes similar recursion exists elsewhere in Git. The risk is acknowledged in the commit message and documentation.
- **Long-term viability of subprocess architecture**: whether `die()` is appropriate for server-side operations (e.g., `git-receive-pack`), where it may disrupt client communication; acknowledged as a worthwhile long-term improvement but out of scope for this series.
- **Generalization of the 1,000-commit cutoff**: Kristofer Karlsson notes the threshold may not generalize across all repository shapes, but benchmarks show it works well for small/medium/large repos. The configurable `auto[=<n>]` syntax allows future adjustments without breaking changes. The auto mode's effectiveness is now **demonstrated in benchmarks** and **thoroughly tested**.

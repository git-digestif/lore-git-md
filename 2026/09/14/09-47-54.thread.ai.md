Subject: [PATCH 0/2] Add incremental connectivity check for fetch/push

Core problem or goal
Introduce an opt-in incremental connectivity check (`transfer.connectivityCheck=incremental`) to reduce the cost of verifying object connectivity during fetches and pushes. The existing full check scales poorly with repository size; the new mode processes incoming commits in topological order, tracking trusted objects from parent commits to skip unchanged subtrees, shifting cost from repository size to incoming change size.

Key technical details
- New config keys: `transfer.connectivityCheck=incremental`, `transfer.connectivityCheckIncrementalMaxCommits=<n>` (proposed, default: 1,000)
- New internal `rev-list` flag: `--verify-trees-incremental`
- New source file: `tree-verify.c` (316 lines, implements incremental verifier with inductive trust algorithm: parent trees trusted, new trees verified only where differing from parents; tracks tree OIDs in three states: untrusted, trusted, expanded; uses merge-walk to collect same-path parent subtrees as comparison bases; skips gitlinks entirely)
- Updated files: `builtin/rev-list.c` (wires up new mode), `connected.c` (integrates verifier into `check_connected()` subprocess; will be reduced to rely less on `the_repository` in v4), `Documentation/config/transfer.adoc` (20 lines documenting the new config keys), `Documentation/rev-list-options.adoc` (6 lines marking the flag as internal), `Documentation/technical/connectivity-check.adoc` (109 lines, explains connectivity invariant, full check mechanics, exceptions like submodules and promisor objects, and includes example graph illustrating boundary between incoming and already-connected commits; now confirmed for build system integration)
- New test files: `t5413-connectivity-check.sh` (renumbered from `t5412`, 680 lines, verifies semantic equivalence with full check, corruption detection, promisor object handling, and integration with fetch/push/clone), `t/perf/p5413-connectivity-check.sh` (renumbered from `p5412`, 92 lines, benchmarks incremental vs. full check across repository size, incoming commit count, and files changed per commit; uses synthetic repositories with flat directory structure and Perl generator to isolate connectivity-check overhead; now includes `PERL` prerequisite and corrected usage comment)
- Behavior: incremental mode runs inside the existing `check_connected()` subprocess; falls back to full check for deepening fetches, shallow boundaries, promisor objects, and (if implemented) incoming histories exceeding `transfer.connectivityCheckIncrementalMaxCommits`. Detects corruption (missing objects, malformed trees, type mismatches). The fallback for very long incoming histories is now proposed as a configurable threshold rather than an implicit trade-off.
- Trust boundary detection: relies on `git rev-list --not --all` to identify already-connected commits (old tips), then processes incoming commits in reverse topological order; each commit’s tree is verified only against its parents’ trusted trees, with memoization skipping objects seen in trusted trees. The boundary detection mechanism is identical to the full check, though the incremental mode avoids the full tree walk of boundary commits.
- Error handling: currently uses `die()` for cycles in the incoming commit graph and missing objects (consistent with existing `rev-list` patterns); subprocess architecture ensures clean error propagation to parent process (e.g., `git-receive-pack`). Patrick Steinhardt’s review suggests replacing `die()` with error returns to align with libification efforts, improving error messages for missing/corrupt objects, and addressing potential issues with `parse_commit_or_die()` in partial clones. Kristofer Karlsson plans to centralize `die()` calls at the subprocess boundary and add a test for partial-clone edge cases in v4, but does not treat this as a blocker.
- Performance: up to 190x faster for small pushes to large repos (14 MB vs. 3.4 GB memory), 1.5x slower for very long incoming histories (10,000+ commits); Trace2 instrumentation measures trees loaded and blobs checked. The performance test suite benchmarks three dimensions: repository size (5,000–800,000 files), incoming commit count (1–10,000), and files changed per commit (1–2,000), using synthetic repositories with minimal overhead to isolate connectivity-check cost.
- On-disk format: unchanged
- Future scalability ideas (not part of current series): MIDX-based connectivity closure (precompute closed pack sets) and parallel ref loading (balance ref-loading overhead against object-checking cost)

Open questions and loose ends
- Dynamic fallback mechanism: whether to implement the proposed `transfer.connectivityCheckIncrementalMaxCommits` config key (default: 1,000 commits) to dynamically fallback to the full check for very long incoming histories. Kristofer Karlsson has tentatively agreed to add this if consensus forms, noting that a single threshold may not generalize across repository shapes. The question remains open but is no longer a blocker.
- Error handling: Patrick Steinhardt’s review suggests replacing `die()` with error returns to align with libification efforts, improving error messages for missing/corrupt objects, and addressing potential issues with `parse_commit_or_die()` in partial clones. Kristofer Karlsson plans to centralize `die()` calls at the subprocess boundary and add a test for partial-clone edge cases in v4, but does not treat this as a blocker.
- Stack overflow risk: Patrick Steinhardt questions whether the recursive tree verification could risk stack overflow for very deep trees (up to 2048 layers) and suggests using a work queue instead. Kristofer Karlsson will explore this in v4, though he notes similar recursion exists elsewhere in Git.
- Long-term viability of subprocess architecture: whether `die()` is appropriate for server-side operations (e.g., `git-receive-pack`), where it may disrupt client communication; acknowledged as a worthwhile long-term improvement but out of scope for this series.

Subject: [PATCH 0/2] Add incremental connectivity check for fetch/push
Series version: v1 (initial submission)
Originating author: Kristofer Karlsson (via GitGitGadget)
Thread type: patch series (performance feature)

Core problem or goal
Introduce an opt-in incremental connectivity check (`transfer.connectivityCheck=incremental`) to reduce the cost of verifying object connectivity during fetches and pushes. The existing full check scales poorly with repository size; the new mode processes incoming commits in topological order, tracking trusted objects from parent commits to skip unchanged subtrees, shifting cost from repository size to incoming change size.

Current status
Under review (v1 posted). No prior versions. Junio C Hamano has provided initial substantive review, raising two technical concerns about edge-case handling in `tree-verify.c` (promisor object checks and NULL-dereference risks). The series remains in early review with no merge status or version updates yet.

Key technical details
- New config key: `transfer.connectivityCheck=incremental`
- New internal `rev-list` flag: `--verify-trees-incremental`
- New source file: `tree-verify.c` (306 lines, implements incremental verifier)
- Updated files: `builtin/rev-list.c` (wires up new mode), `connected.c` (integrates verifier)
- New documentation: `Documentation/technical/connectivity-check.adoc` (explains connectivity invariant, full check mechanics, exceptions like submodules and promisor objects, and includes example graph illustrating boundary between incoming and already-connected commits)
- New test files: `t5412-connectivity-check.sh` (655 lines, verifies semantic equivalence with full check, corruption detection, and integration with fetch/push/clone), `t/perf/p5412-connectivity-check.sh` (benchmarks incremental vs. full check across repository size, incoming commit count, and files changed per commit)
- Behavior: incremental mode runs inside the existing `check_connected()` subprocess; falls back to full check for deepening fetches, very long incoming histories (10,000+ commits), shallow boundaries, and promisor objects; detects corruption (missing objects, malformed trees, type mismatches)
- Performance: up to 190x faster for small pushes to large repos (14 MB vs. 3.4 GB memory), 1.5x slower for very long incoming histories (10,000+ commits)
- Trace2 instrumentation: measures trees loaded and blobs checked
- On-disk format: unchanged

Open questions and loose ends
- **Promisor object handling**: Junio questions whether the `is_promisor_object()` check in `verify_blob()` occurs too late, after `odb_read_object_info()` may have already triggered a lazy fetch, potentially violating the incremental check's goal of avoiding network round-trips.
- **NULL-dereference risks**: Junio identifies potential crashes in `verify_commit_tree()` if `parse_commit_or_die()` succeeds but the commit's tree is missing or corrupted, leading to NULL returns from `get_commit_tree_oid()` passed to `tree_map_add()`.
- Future optimization: commit boundary-finding step remains a bottleneck for repos with many refs.

Subject: [PATCH 0/2] Add incremental connectivity check for fetch/push
Series version: v2 (addresses Junio's review; documentation and implementation patches under substantive review by Patrick Steinhardt; v3 planned to split implementation patch and address documentation feedback)

Core problem or goal
Introduce an opt-in incremental connectivity check (`transfer.connectivityCheck=incremental`) to reduce the cost of verifying object connectivity during fetches and pushes. The existing full check scales poorly with repository size; the new mode processes incoming commits in topological order, tracking trusted objects from parent commits to skip unchanged subtrees, shifting cost from repository size to incoming change size.

Key technical details
- New config key: `transfer.connectivityCheck=incremental`
- New internal `rev-list` flag: `--verify-trees-incremental`
- New source file: `tree-verify.c` (316 lines, implements incremental verifier with inductive trust algorithm: parent trees trusted, new trees verified only where differing from parents; tracks tree OIDs in three states: untrusted, trusted, expanded; uses merge-walk to collect same-path parent subtrees as comparison bases; skips gitlinks entirely)
- Updated files: `builtin/rev-list.c` (wires up new mode), `connected.c` (integrates verifier into `check_connected()` subprocess)
- New documentation: `Documentation/technical/connectivity-check.adoc` (109 lines, explains connectivity invariant, full check mechanics, exceptions like submodules and promisor objects, and includes example graph illustrating boundary between incoming and already-connected commits; under revision to address Patrick Steinhardt's feedback)
- New test files: `t5412-connectivity-check.sh` (680 lines, verifies semantic equivalence with full check, corruption detection, promisor object handling, and integration with fetch/push/clone), `t/perf/p5412-connectivity-check.sh` (92 lines, benchmarks incremental vs. full check across repository size, incoming commit count, and files changed per commit)
- Behavior: incremental mode runs inside the existing `check_connected()` subprocess; falls back to full check for deepening fetches, very long incoming histories (10,000+ commits), shallow boundaries, and promisor objects; detects corruption (missing objects, malformed trees, type mismatches)
- Trust boundary detection: relies on `git rev-list --not --all` to identify already-connected commits (old tips), then processes incoming commits in reverse topological order; each commit’s tree is verified only against its parents’ trusted trees, with memoization skipping objects seen in trusted trees. The boundary detection mechanism is identical to the full check, though the incremental mode avoids the full tree walk of boundary commits.
- Error handling: uses `die()` for cycles in the incoming commit graph (consistent with existing `rev-list` patterns); subprocess architecture ensures clean error propagation to parent process (e.g., `git-receive-pack`)
- Performance: up to 190x faster for small pushes to large repos (14 MB vs. 3.4 GB memory), 1.5x slower for very long incoming histories (10,000+ commits); Trace2 instrumentation measures trees loaded and blobs checked
- On-disk format: unchanged
- Future scalability ideas (not part of current series): MIDX-based connectivity closure (precompute closed pack sets) and parallel ref loading (balance ref-loading overhead against object-checking cost)

Open questions and loose ends
- Long-term viability of subprocess architecture: whether `die()` is appropriate for server-side operations (e.g., `git-receive-pack`), where it may disrupt client communication; acknowledged as a worthwhile long-term improvement but out of scope for this series.
- Scalability of ref-parsing overhead: remains a separate challenge (out of scope), though the current implementation avoids parsing all refs upfront.
- Documentation patch (1/2): will address all three of Patrick Steinhardt's points: (1) explicitly state the reverse of the connectivity invariant (unreachable objects are untrusted), (2) remove or relocate code references to avoid staleness, and (3) clarify or remove the three-phase breakdown of the full check and the "subsequent object traversal" for non-commit tips.
- Patch organization: implementation patch (2/2) will be split into smaller commits (option introduction, benchmark, `rev-list` flag, and strategy implementation) for better reviewability.
- Future directions: MIDX-based connectivity closure and parallel ref loading are acknowledged as potential scalability improvements but are explicitly out of scope for this series.

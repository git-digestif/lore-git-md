Subject: [PATCH 0/2] Add incremental connectivity check for fetch/push

Originating author: Kristofer Karlsson (via GitGitGadget)
Thread type: patch series (performance feature)

Core problem or goal
Introduce an opt-in incremental connectivity check (`transfer.connectivityCheck=incremental`) to reduce the cost of verifying object connectivity during fetches and pushes. The existing full check scales poorly with repository size; the new mode processes incoming commits in topological order, tracking trusted objects from parent commits to skip unchanged subtrees, shifting cost from repository size to incoming change size.

Under review (v2 posted). Both patches (1/2 documentation and 2/2 implementation) are available. Key technical details
- New config key: `transfer.connectivityCheck=incremental`
- New internal `rev-list` flag: `--verify-trees-incremental`
- New source file: `tree-verify.c` (316 lines, implements incremental verifier with inductive trust algorithm: parent trees trusted, new trees verified only where differing from parents; tracks tree OIDs in three states: untrusted, trusted, expanded; uses merge-walk to collect same-path parent subtrees as comparison bases; skips gitlinks entirely)
- Updated files: `builtin/rev-list.c` (wires up new mode), `connected.c` (integrates verifier into `check_connected()` subprocess)
- New documentation: `Documentation/technical/connectivity-check.adoc` (109 lines, explains connectivity invariant, full check mechanics, exceptions like submodules and promisor objects, and includes example graph illustrating boundary between incoming and already-connected commits; under review for precision and maintainability)
- New test files: `t5412-connectivity-check.sh` (680 lines, verifies semantic equivalence with full check, corruption detection, promisor object handling, and integration with fetch/push/clone), `t/perf/p5412-connectivity-check.sh` (92 lines, benchmarks incremental vs. full check across repository size, incoming commit count, and files changed per commit)
- Behavior: incremental mode runs inside the existing `check_connected()` subprocess; falls back to full check for deepening fetches, very long incoming histories (10,000+ commits), shallow boundaries, and promisor objects; detects corruption (missing objects, malformed trees, type mismatches)
- Performance: up to 190x faster for small pushes to large repos (14 MB vs. 3.4 GB memory), 1.5x slower for very long incoming histories (10,000+ commits)
- Trace2 instrumentation: measures trees loaded and blobs checked
- On-disk format: unchanged

Open questions and loose ends
- Trust boundary detection: how the verifier identifies trusted trees without parsing all refs—a potential bottleneck for repos with many refs.
- Error handling: whether `die()` is appropriate for server-side operations like `git-receive-pack`, where it may disrupt client communication.
- Performance trade-offs: incremental mode may verify more objects in scenarios with many refs or large boundary trees.
- Documentation patch (1/2) has three open points from Patrick Steinhardt: (1) explicitly state the reverse of the connectivity invariant (unreachable objects are untrusted), (2) remove or relocate code references to avoid staleness, and (3) clarify or remove the three-phase breakdown of the full check and the "subsequent object traversal" for non-commit tips.
- Patch organization: suggestion to split the implementation patch (2/2) into smaller, focused commits (option introduction, benchmark, `rev-list` flag, and strategy implementation) to improve reviewability.
- Junio's tangential observation about non-ref roots (e.g., index entries) in connectivity checks for `fsck` remains speculative and is not tied to a specific request for changes in this series.

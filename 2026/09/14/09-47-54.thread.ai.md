Subject: [PATCH 0/2] Add incremental connectivity check for fetch/push
Series version: v4 (four-patch series: documentation, baseline performance tests, config plumbing, implementation; rebased onto master; addresses all prior feedback)

Thread type: patch series (performance feature)

Core problem or goal
Introduce an opt-in incremental connectivity check (`transfer.connectivityCheck=incremental`) to reduce the cost of verifying object connectivity during fetches and pushes. The existing full check scales poorly with repository size; the new mode processes incoming commits in topological order, tracking trusted objects from parent commits to skip unchanged subtrees, shifting cost from repository size to incoming change size.

Key technical details
- New config key: `transfer.connectivityCheck=incremental`
- New internal `rev-list` flag: `--verify-trees-incremental`
- New source file: `tree-verify.c` (316 lines, implements incremental verifier with inductive trust algorithm: parent trees trusted, new trees verified only where differing from parents; tracks tree OIDs in three states: untrusted, trusted, expanded; uses merge-walk to collect same-path parent subtrees as comparison bases; skips gitlinks entirely)
- Updated files: `builtin/rev-list.c` (wires up new mode), `connected.c` (integrates verifier into `check_connected()` subprocess; will be reduced to rely less on `the_repository` in v4), `Documentation/config/transfer.adoc` (20 lines documenting the new config key), `Documentation/rev-list-options.adoc` (6 lines marking the flag as internal), `Documentation/technical/connectivity-check.adoc` (109 lines, explains connectivity invariant, full check mechanics, exceptions like submodules and promisor objects, and includes example graph illustrating boundary between incoming and already-connected commits; now confirmed for build system integration)
- New test files: `t5413-connectivity-check.sh` (renumbered from `t5412`, 680 lines, verifies semantic equivalence with full check, corruption detection, promisor object handling, and integration with fetch/push/clone), `t/perf/p5413-connectivity-check.sh` (renumbered from `p5412`, 92 lines, benchmarks incremental vs. full check across repository size, incoming commit count, and files changed per commit; uses synthetic repositories with flat directory structure and Perl generator to isolate connectivity-check overhead; now includes `PERL` prerequisite and corrected usage comment)
- Behavior: incremental mode runs inside the existing `check_connected()` subprocess; falls back to full check for deepening fetches, shallow boundaries, and promisor objects; detects corruption (missing objects, malformed trees, type mismatches). The fallback for very long incoming histories (10,000+ commits) is currently implicit (the 1.5x slowdown is accepted as a trade-off), but the question of whether to make it explicit via a dynamic fallback mechanism remains open.
- Trust boundary detection: relies on `git rev-list --not --all` to identify already-connected commits (old tips), then processes incoming commits in reverse topological order; each commit’s tree is verified only against its parents’ trusted trees, with memoization skipping objects seen in trusted trees. The boundary detection mechanism is identical to the full check, though the incremental mode avoids the full tree walk of boundary commits.
- Error handling: currently uses `die()` for cycles in the incoming commit graph and missing objects (consistent with existing `rev-list` patterns); subprocess architecture ensures clean error propagation to parent process (e.g., `git-receive-pack`). Patrick Steinhardt’s review suggests replacing `die()` with error returns to align with libification efforts, improving error messages for missing/corrupt objects, and addressing potential issues with `parse_commit_or_die()` in partial clones. These changes are expected in v4.
- Performance: up to 190x faster for small pushes to large repos (14 MB vs. 3.4 GB memory), 1.5x slower for very long incoming histories (10,000+ commits); Trace2 instrumentation measures trees loaded and blobs checked. The performance test suite benchmarks three dimensions: repository size (5,000–800,000 files), incoming commit count (1–10,000), and files changed per commit (1–2,000), using synthetic repositories with minimal overhead to isolate connectivity-check cost.
- On-disk format: unchanged
- Future scalability ideas (not part of current series): MIDX-based connectivity closure (precompute closed pack sets) and parallel ref loading (balance ref-loading overhead against object-checking cost)

Open questions and loose ends
- Dynamic fallback mechanism: whether to add an explicit fallback to the full check when the number of incoming commits exceeds a threshold (e.g., 10,000 commits). Kristofer Karlsson has raised this as a design question, noting that the current implementation accepts the 1.5x slowdown for very long histories as a trade-off but that a fallback could provide additional safety. Patrick Steinhardt has also suggested this as a potential improvement, noting that the algorithm already knows the number of commits upfront. The question is whether to hardcode a limit, make it configurable, or leave the current behavior unchanged. No consensus has been reached yet, but the discussion is now framed as a trade-off rather than a blocker.
- Error handling: Patrick Steinhardt’s review suggests replacing `die()` with error returns to align with libification efforts, improving error messages for missing/corrupt objects, and addressing potential issues with `parse_commit_or_die()` in partial clones. These changes are expected in v4.
- Stack overflow risk: Patrick Steinhardt questions whether the recursive tree verification could risk stack overflow for very deep trees (up to 2048 layers) and suggests using a work queue instead. This is a new concern and is expected to be addressed in v4.
- Long-term viability of subprocess architecture: whether `die()` is appropriate for server-side operations (e.g., `git-receive-pack`), where it may disrupt client communication; acknowledged as a worthwhile long-term improvement but out of scope for this series.
- Patch structure: Patrick Steinhardt’s review of patch 3/4 (plumbing) suggests splitting the plumbing patch into three logical steps to make each patch self-contained and easier to review. The proposed sequence is (1) introduce the config option but only accept `"full"` (the default), (2) implement the `rev-list` flag in the next patch, and (3) enable the `"incremental"` config value in the final patch. This adjustment is purely organizational and does not affect functionality or performance. The author has accepted this suggestion and will incorporate it in v4.

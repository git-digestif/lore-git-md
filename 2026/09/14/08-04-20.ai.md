This is the first patch in Thomas Bachem’s v4 two-patch series fixing a long-standing race condition in Git’s `rerere` subsystem. The patch introduces a configurable timeout (`rerere.lockTimeout`, defaulting to 1000 milliseconds) for acquiring the `MERGE_RR.lock`, replacing the previous behavior where a second process would die immediately if the lock was held. Background maintenance tasks (`git rerere gc`) now skip their run entirely if the lock is held, while other commands (e.g., `git merge`, `git rebase`) wait up to the timeout before failing. The patch also updates documentation to clarify the new behavior and adds comprehensive test coverage for edge cases, including held locks during `git rerere`, `git rerere forget`, `git rerere clear`, and `git rebase --abort`.

The implementation touches `rerere.c` (locking logic and error handling), `rerere.h` (new `RERERE_NOWAIT` flag), and documentation files, with tests in `t/t4200-rerere.sh` and `t/t7900-maintenance.sh`. The patch is well-motivated, addressing a real-world issue exacerbated by Git 2.54’s geometric maintenance strategy, and the changes are narrowly scoped to the locking mechanism. The test suite now verifies that error messages are accurate and that the timeout allows foreground operations to proceed after background maintenance completes. No objections to this patch remain after incorporating feedback from Junio, Patrick Steinhardt, and Phillip Wood, though the second patch in the series (handling conflict-stop recovery) is still under discussion. Key technical details include the use of `hold_lock_file_for_update_timeout()` with a configurable timeout, a `BUG()` assertion to catch incompatible flag combinations, and the distinction between maintenance tasks (which skip the lock) and other commands (which wait). The patch is based on `master` and resolves a trivial conflict with recent lockfile helper refactoring.

This is the fifth patch in a six-patch **bugfix series** targeting a data-loss race in `git repack -d` when concurrent pushes are active. The series is well-motivated, production-tested, and under active review; this patch specifically addresses a command-line length limitation that would otherwise block the full fix.

The patch adds `--keep-pack-from-file=<file>` to `git pack-objects`, allowing callers to specify a file containing a list of pack names (one per line) to treat as if they had been passed via `--keep-pack`. Empty lines are skipped, and relative paths are resolved against the user’s working directory. The implementation is straightforward: the file is read into the same `string_list` that holds `--keep-pack` names, and the list is configured to own its strings (`strdup_strings = 1`). The new option is documented in `git-pack-objects.adoc` and tested in `t/t5331-pack-objects-stdin.sh`, where it is verified to behave identically to `--keep-pack` (including ignoring empty lines and non-existent packs) and to fail cleanly when the file is missing.

This is a **scalability enabler** for the series’ final patch (6/6), which passes `repack`’s snapshot of `.keep` packs to `pack-objects` to close the race window. Without this plumbing, repositories with hundreds of kept packs would hit ARG_MAX or Windows’ 32K-character command-line limit, causing the spawn to fail before `pack-objects` even starts. The design is conservative: it reuses the existing `--keep-pack` machinery, avoids introducing new state, and maintains backward compatibility. The only behavioral change is that the `string_list` now owns its strings, which is necessary because it now holds entries from two sources.

The patch is **unlikely to be controversial**; it follows the established pattern of `--stdin` options in `fetch-pack` and `multi-pack-index`, and the implementation is minimal and well-tested. The only potential point of discussion is whether the file format should be more structured (e.g., NUL-terminated), but the one-per-line convention is consistent with other Git tools and sufficient for the use case. The test coverage is thorough, including edge cases like empty lines and missing files.

Key technical details for follow-up discussion:
- **New option**: `--keep-pack-from-file=<file>`
- **File format**: one pack name per line, empty lines ignored
- **Path resolution**: relative paths resolved against the working directory
- **String ownership**: `keep_pack_list` now owns its strings (`strdup_strings = 1`)
- **Error handling**: fails with `die_errno` if the file cannot be read
- **Test file**: `t/t5331-pack-objects-stdin.sh` (two new tests)

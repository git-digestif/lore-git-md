This is the second patch in Thomas Bachem’s two-part bugfix series for the `rerere` subsystem, addressing a long-standing race condition where concurrent `rerere` operations (e.g., a rebase and a background `rerere gc`) contend for the shared `MERGE_RR.lock`. The first patch, already accepted, introduced a configurable timeout for acquiring the lock and unified error reporting. This patch builds on that foundation by allowing commands that stop at a conflict (e.g., `git rebase`, `git merge`, `git am --3way`) to proceed with a warning if the lock remains held after the timeout, while post-resolution recording and explicit `git rerere` commands still fail.

The core change is pragmatic: when a conflict-stopping command (like `git rebase`) hits the lock timeout, it emits a warning advising the user to run `git rerere` manually before resolving the conflict, then continues. This preserves the user’s ability to recover the conflict preimage without leaving the rebase in an unrecoverable state. The patch updates all relevant callers (`apply.c`, `builtin/am.c`, `builtin/merge.c`, `builtin/stash.c`, `sequencer.c`) to pass the new `RERERE_SKIP_LOCKED` flag, which triggers the warning-and-continue behavior. Documentation is updated to clarify the new behavior, and the test suite is expanded with 105 new lines covering edge cases like manual recovery via `git rerere` and the distinction between conflict stops and post-resolution recording.

The implementation is well-motivated and thorough, with clear test coverage for both the warning behavior and the recovery path. The trade-off—resilience over strict correctness—has been debated in the thread, but the v4 compromise (warning at conflict stops, failure elsewhere) addresses the most disruptive aspect of the race while preventing silent corruption. The patch is ready for review, with no unresolved technical objections to the approach. If accepted, it will complete the series and resolve a long-standing usability issue in `rerere`.

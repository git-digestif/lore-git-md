This is a reply in the ongoing `imap-send` OpenSSL compatibility series, specifically addressing Patrick Steinhardt’s question about the necessity of the OpenSSL 4.1 compatibility macro in patch 1. Beat Bolli clarifies that while the OpenSSL documentation does not explicitly mark `ASN1_STRING_length()` as deprecated, it *is* listed among functions that will be hidden when `OPENSSL_API_COMPAT` is defined for OpenSSL 4.1 or later. The patch is motivated by a practical build failure: under `DEVELOPER=1`, the deprecation warning is treated as an error, breaking the build. This is a forward-compatibility fix, not a response to an immediate deprecation, and the change aligns with Git’s practice of avoiding deprecated APIs where possible.

The reply does not resolve the larger unresolved issues in the series (the memory-safety bug in patch 2, incomplete RFC 6125 compliance in patch 3, or the architectural question about manual vs. OpenSSL-native verification), but it provides a clear justification for the compatibility shim. The justification is technical and specific: the function is not yet deprecated, but it will be hidden in future OpenSSL versions, and Git’s build configuration already treats deprecation warnings as errors. This makes the patch a preemptive correctness fix rather than a premature abstraction.

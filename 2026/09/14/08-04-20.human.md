This is the first patch in a two-part bugfix series targeting the `rerere` subsystem. It addresses a long-standing race condition where concurrent `rerere` operations (e.g., a rebase and a background `git rerere gc` from maintenance) contend for the shared `MERGE_RR.lock`, causing the second process to die and leaving the rebase in an unrecoverable state. The issue became more pronounced after Git 2.54’s geometric maintenance strategy made background `rerere gc` runs more frequent.

The patch introduces a configurable timeout (`rerere.lockTimeout`, defaulting to 1000 milliseconds) for acquiring the `MERGE_RR.lock`. Non-maintenance callers (e.g., `git merge`, `git rebase`) now wait up to the timeout before failing, while background maintenance (`git rerere gc`) skips its run entirely if the lock is held. This ensures that a rebase can proceed even if a concurrent `rerere gc` is running, avoiding the previous deadlock. The implementation is clean: it replaces the `LOCK_DIE_ON_ERROR` flag with `hold_lock_file_for_update_timeout()`, adds a new `RERERE_NOWAIT` flag for maintenance tasks, and updates the documentation to reflect the new behavior.

The patch touches `rerere.c` (locking logic and error handling), `rerere.h` (new flags), documentation, and test files. The test suite has been expanded to cover edge cases, including verifying that `git rerere gc` skips its run when the lock is held, that commands wait for the lock within the timeout, and that explicit `git rerere` commands fail if the lock remains held. The implementation is well-motivated and addresses the core issue without introducing new complexity.

This patch is a clear improvement over the status quo. The race condition is a real problem, and the timeout-based approach is a pragmatic solution that balances robustness with minimal disruption. The configurable timeout and clear documentation make the behavior predictable for users. The patch is ready for review, with no obvious flaws or missing pieces. The second patch in the series (which allows conflict-stopping commands to proceed with a warning if the lock remains held) will build on this foundation.

This thread is a five-patch bugfix series (v2) addressing a data-loss race in `git repack -d` where concurrent pushes can delete packs whose objects were never copied elsewhere, leaving dangling refs. The series, authored by Qin ShiCheng (qeesung), replaces the `--honor-pack-keep` mechanism with a snapshot-based approach to ensure `.keep` files are managed consistently. The first version of the series included six patches, but patch 1/6 was withdrawn in favor of Justin Tobler’s separate ODB-focused series, which will handle `.keep` file ownership logic more cleanly.

The series is now at v2, with patches 1/5–5/5 under review. Key changes include fixing a long-standing traversal inconsistency in `pack-objects --stdin-packs=follow` (patch 1/5), addressing a latent cruft-pack walk bug (patch 2/5), optimizing `--keep-pack` lookups for scalability (patch 3/5), and introducing `--keep-pack-from-file` to `git pack-objects` (patch 4/5). The final patch (5/5) replaces `--honor-pack-keep` with a snapshot-based approach, ensuring `.keep` packs observed at repack startup are consistently respected. The series touches multiple subsystems, including `pack-objects`, `repack`, and ODB, and includes comprehensive test coverage.

The latest email covers patch 4/5, which adds `--keep-pack-from-file=<file>` to `git pack-objects`. This option reads a file containing one pack name per line (empty lines ignored) and treats them identically to `--keep-pack` arguments. The motivation is practical: command-line length limits (e.g., 32K characters on Windows) prevent passing hundreds of pack names via `--keep-pack`, making this a scalability enabler for the series’ main fix. The implementation is straightforward, with a new helper function reading the file line-by-line and appending non-empty lines to the `keep_pack_list`. The patch includes two new tests in `t/t5331-pack-objects-stdin.sh` to verify behavior and error handling.

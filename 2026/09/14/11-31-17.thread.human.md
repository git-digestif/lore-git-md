This thread is about a v2 patch series from Qin ShiCheng (qeesung) that fixes a race condition in `git repack -d` where concurrent pushes could cause data loss by deleting packs whose objects weren’t safely copied elsewhere. The series replaces the `--honor-pack-keep` mechanism with a snapshot-based approach to manage `.keep` files consistently, and also fixes a latent cruft-pack walk bug that would become critical once the old mechanism is removed.

The series is now at v2, with five patches (the original first patch was withdrawn in favor of Justin Tobler’s separate ODB-focused series, which will handle `.keep` file ownership). The key change in the final patch (5/5) eliminates the race by passing `pack-objects` a snapshot of `.keep` packs observed at repack startup, replacing the mid-repack directory scan that could miss concurrent `.keep` file creation. The series has been under review, with no Reviewed-by or Acked-by tags yet, but Junio C Hamano just weighed in on the second patch with a substantive architectural concern.

Junio’s review focuses on a layering issue in the cruft-pack walk fix: the patch exposes and calls `packfile_store_invalidate_kept_pack_cache()` to reset the kept-pack cache after re-marking fresh packs as kept, but it assumes every ODB source is a `files`-backend source without checking the source type. This could trigger a `BUG()` if a future pluggable ODB backend is introduced. Junio suggests either checking the source type (a layering violation) or re-architecting the code to push packfile management details down to the files backend layer entirely. He acknowledges the latter is beyond the scope of this patch but flags the unchecked downcast as technical debt. The thread is now open for discussion on whether to accept the patch as-is or address the layering concern first. Likely respondents include Patrick Steinhardt (ODB abstraction lead), Justin Tobler, and Qin ShiCheng.

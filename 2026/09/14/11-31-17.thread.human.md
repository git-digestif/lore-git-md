This thread addresses a data-loss race in `git repack -d` where a `.keep` file appearing on a pack after `repack` has decided to delete it but before `pack-objects` scans causes objects to be lost, leaving refs dangling. Qin ShiCheng (qeesung) has posted the fifth iteration (v5) of a three-patch series that fixes this by replacing the `--honor-pack-keep` mechanism with a snapshot-based approach: `repack` now records which non-kept packs it observed at startup and passes this list to `pack-objects` via a new `--ignore-pack-keep-from` option, ensuring `.keep` files created mid-run cannot trigger deletion of packs whose objects were not copied elsewhere.

The v5 series is essentially v4 rebased onto current `master` to resolve a test conflict with the `ds/path-walk-tagged-tree-revisit` topic, with the only code change being that the kept-pack list is now sorted before collection. Jeff King provided a Reviewed-by for the cruft-walk cache fix in patch 1/3, and Taylor Blau reviewed patch 3/3, which implements the snapshot mechanism; with these reviews and Junio C Hamano's earlier ack of the underlying fix, the series is considered ready for integration.

The patches touch `builtin/repack.c`, `builtin/pack-objects.c`, and the packfile layer, introducing `repo_invalidate_kept_pack_caches()` and the `--ignore-pack-keep-from` plumbing, with tests covering all repack modes including `--cruft` and `--geometric`. One intentional trade-off is that the cruft walk now traverses alternate object database packs for safety, which can slow `repack -d -l --cruft` in shared clones, but this is accepted as necessary to prevent data loss.

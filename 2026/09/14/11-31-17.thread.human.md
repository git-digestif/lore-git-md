This thread is a bugfix series from qeesung (Qin ShiCheng) addressing a data-loss race in `git repack -d`: if a `.keep` file appears on a pack after repack's initial scan but before `pack-objects` runs, the old code could delete a pack whose objects were never copied elsewhere, leaving dangling refs. The current v5 series replaces the old `--honor-pack-keep` mechanism with a snapshot-based approach: repack writes the basenames of all packs it may delete to a tempfile and passes it to `pack-objects` via a new `--ignore-pack-keep-from=<file>` option, forcing those packs to be treated as deletable regardless of any `.keep` files that appear mid-run. The series also fixes a latent cruft-walk bug where the kept-pack cache could stop the reachability walk too early.

The series is at v5, which is simply v4 rebased onto current `master` to resolve a test conflict; the only code change is sorting the keep-pack list before collection. It has received Reviewed-by tags from Jeff King on the cruft-walk fix (patch 1/3) and Taylor Blau on the snapshot mechanism (patch 3/3), and Junio C Hamano has acked the cruft-walk fix, so the series is considered ready for integration. Tests in `t/t7700-repack.sh` and `t/t7703-repack-geometric.sh` reproduce the race across `-a -d`, `-A -d`, `--cruft`, `--geometric`, and `--filter` modes using a shim that creates a `.keep` file at the moment `pack-objects` starts, verifying with `git fsck` that no objects are lost.

One open trade-off noted in review is performance: the fix causes the cruft walk to traverse alternate ODB packs (trading disk space for safety), which can noticeably slow `repack -d -l --cruft` in shared clones. Both Jeff King and the author consider this acceptable for correctness, but it may draw discussion. Otherwise the series has no outstanding objections and is expected to land in `next`.

This thread is about a critical bugfix series that addresses a data-loss race condition in `git repack -d` when concurrent pushes occur. The series, authored by qeesung (via GitGitGadget), is currently at version 1 and under review.

The bug manifests when two pushes of identical content create identical thin packs, leading `index-pack` to target the same `.keep` file in the object database. If the first push’s `.keep` file is still present when the second push’s quarantine is migrated, `receive-pack` could previously remove it unconditionally—even if the push was rejected or the `.keep` belonged to another pack. This could orphan packs, resulting in dangling refs pointing to nonexistent commits. The issue has been observed in production and reproduces on Git 2.43 and `master`.

The first patch in the series, just posted, focuses on preventing `receive-pack` from removing `.keep` files it didn’t create. This is a prerequisite for the full race fix in the final patch. The fix changes the timing of `.keep` file registration, ensuring only `.keep` files created by the current push are removed. It introduces a new `unregister_tempfile()` helper and refactors `.keep` file management using `string_list` for cleaner ownership tracking. The patch includes two new tests to verify that rejected pushes don’t remove foreign `.keep` files and that `.keep` files installed during failed migrations are still cleaned up.

The series touches several key files (`builtin/pack-objects.c`, `builtin/repack.c`, `object-file.c`, `packfile.h`, `tempfile.h`) and introduces new plumbing options (`--stdin-packs=follow` and `--keep-pack-from-file`) to handle repositories with many kept packs. While the series is self-contained and all tests pass, no reviews have been posted yet. Key reviewers likely include Patrick Steinhardt and Taylor Blau, given their expertise in the repack and ODB subsystems. The fix is described as well-scoped and low-risk, with clear commit messages and comprehensive test coverage.

# Thread deltas

## 2026/09/14

- [2026/09/14/11-31-17 by qeesung via GitGitGadget <gitgitgadget@gmail.com>] Qin ShiCheng posted a 6-patch series fixing a race where "git repack -d" deletes a pack whose objects were never copied because a ".keep" file appeared mid-run between repack's initial scan and pack-objects' rescan; the series makes receive-pack remove only ".keep" files it installed (1/6) and has repack hand pack-objects its startup snapshot of kept packs instead of using "--honor-pack-keep" (6/6), with supporting changes to pack-objects traversal, cruft handling, and list handling (2-5).
- [2026/09/14/11-31-18 by Qin ShiCheng via GitGitGadget <gitgitgadget@gmail.com>] receive-pack now registers ".keep" paths immediately before quarantine migration and reads the files back afterward, deleting only those carrying its own message via the new unregister_tempfile(), so a rejected push or a push of duplicate content no longer removes a foreign ".keep" file.
- [2026/09/14/11-31-19 by Qin ShiCheng via GitGitGadget <gitgitgadget@gmail.com>] Under "--stdin-packs=follow", a pack named with "--keep-pack" is now marked kept-open ("!") instead of closed ("^"), allowing the reachability traversal to pass through it and rescue dependent objects that would otherwise be lost.
- [2026/09/14/11-31-20 by Qin ShiCheng via GitGitGadget <gitgitgadget@gmail.com>] The cruft walk now invalidates the kept-pack cache after re-marking fresh packs via packfile_store_invalidate_kept_pack_cache(), fixing a pre-existing bug where expired objects beyond an unlisted kept pack were dropped because the walk consulted a stale cache.
- [2026/09/14/11-31-21 by Qin ShiCheng via GitGitGadget <gitgitgadget@gmail.com>] add_extra_kept_packs() now sorts the "--keep-pack" list once and performs a binary lookup per pack, reducing the cost of matching thousands of kept packs from a linear scan.
- [2026/09/14/11-31-22 by Qin ShiCheng via GitGitGadget <gitgitgadget@gmail.com>] pack-objects gains "--keep-pack-from-file=<file>" to read kept pack names from a file (one per line, skipping empty lines), avoiding command-line length limits such as the 32,767-character cap on Windows.
- [2026/09/14/11-31-23 by Qin ShiCheng via GitGitGadget <gitgitgadget@gmail.com>] repack now writes its startup snapshot of kept packs to a tempfile and passes it to every spawned pack-objects via "--keep-pack-from-file" instead of "--honor-pack-keep", so both processes work from one snapshot and a ".keep" appearing or disappearing mid-run cannot cause object loss; pack names containing newlines are refused up front.

## 2026/09/15

- [2026/09/15/18-25-19 by Justin Tobler <jltobler@gmail.com>] Justin Tobler agreed that a ".keep" registered as a tempfile must know its post-migration path so it can be deleted after refs are updated or on early exit, noting the awkwardness results from relying on git-index-pack(1) to create the ".keep" in the quarantine directory.
- [2026/09/15/18-25-19 by Justin Tobler <jltobler@gmail.com>] He observed that with concurrent identical pushes, a process exiting early could delete another process's packfile, and that a process should probably only delete a ".keep" file it created itself.
- [2026/09/15/18-25-19 by Justin Tobler <jltobler@gmail.com>] He noted that two concurrent identical pushes generate the same ".keep" name but different keep messages; the first migrated "wins" and the competing push fails the collision check, so encountering an already existing ".keep" in the main ODB may be sufficient reason to abort early.
- [2026/09/15/18-25-19 by Justin Tobler <jltobler@gmail.com>] He suggested not registering ".keep" tempfiles before the ODB transaction commit and instead stopping the use of git-index-pack(1) to prematurely create ".keep" files, letting the ODB transaction commit phase create it explicitly to avoid awkward pre-commit tracking and to simplify the fix by attempting to create the ".keep" and aborting if it already exists.
- [2026/09/15/18-25-19 by Justin Tobler <jltobler@gmail.com>] He offered to send upstream local patches from another series that create ".keep" files explicitly during the ODB commit phase in the "files" backend, adjusted to also fix the issue in the first patch, pending the author's preference.

## 2026/09/16

- [2026/09/16/06-01-14 by Qin ShiCheng <qeesung@live.com>] Qin ShiCheng agreed that aborting on an existing ".keep" is fine for concurrent identical pushes, but clarified the production failure involved pushes seconds apart rather than concurrent: the first had already finished and removed its ".keep", so the second found nothing at that path and linked its own ".keep" onto the first push's pack.
- [2026/09/16/06-01-14 by Qin ShiCheng <qeesung@live.com>] He stated the patch's aim is narrower than collision handling: only remove a ".keep" the process created itself, noting that finalize currently unlinks the path unconditionally even when pre-receive rejected the push and nothing was migrated (pinned by the first t5547 test).
- [2026/09/16/06-01-14 by Qin ShiCheng <qeesung@live.com>] He endorsed creating the ".keep" at ODB commit time and registering it there as the better shape, because it gives the two guarantees the patch currently gets by reading files back: nothing foreign is removed, and a signal after the ".keep" is in place still cleans it up.
- [2026/09/16/06-01-14 by Qin ShiCheng <qeesung@live.com>] He flagged a case to keep in mind: a migration that fails partway with the ".keep" already installed, e.g. the ".idx" colliding because pack.indexVersion changed between the two pushes, which the second t5547 test covers.
- [2026/09/16/06-01-14 by Qin ShiCheng <qeesung@live.com>] He announced he will drop 1/6 from v2 so the series covers only the repack side (2/6-6/6 do not depend on it), and offered the two t5547 tests to Justin Tobler's series.

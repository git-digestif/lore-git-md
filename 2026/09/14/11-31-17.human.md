This is a six-patch bugfix series targeting the `git repack` command. The core issue is a race condition where a concurrent push can cause `git repack -d` to delete a packfile whose objects were never copied elsewhere, leaving dangling refs. The problem occurs when a `.keep` file appears between the time `repack` scans for kept packs and when `pack-objects` runs, leading to objects being omitted from the new pack but the old pack being deleted anyway.

The series fixes two distinct problems: first, `receive-pack` now only removes `.keep` files it actually installed (patch 1/6), preventing it from cleaning up foreign `.keep` files that might protect unrelated packs. Second, `repack` now passes its initial snapshot of kept packs directly to `pack-objects` (patch 6/6), eliminating the window where a new `.keep` could appear mid-run. The intermediate patches (2-5/6) prepare the groundwork by improving how `pack-objects` handles kept packs, including performance optimizations for large repositories.

The motivation is clear and production-tested: the author reports hitting this issue in Git 2.43, and the race reproduces on `master`. Each patch includes a test that fails without the fix, and the series as a whole passes the full test suite. The changes touch core repack logic (`builtin/repack.c`, `builtin/pack-objects.c`) and object database handling (`object-file.c`), with new options like `--keep-pack-from-file` to handle edge cases like Windows' command-line length limits.

This looks like a well-crafted fix for a real problem. The commit messages are detailed, the test coverage is thorough, and the series merges cleanly into `next` and `seen`. If you work with large repositories or care about repack safety, this is worth reviewing.

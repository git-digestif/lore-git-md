This is the fourth patch in a six-patch **bugfix series** addressing a data-loss race in `git repack -d` when concurrent pushes are active. The series as a whole is well-motivated, production-tested, and under active review; this specific patch is a **performance optimization** that becomes critical once the series’ later patches allow `repack` to pass thousands of kept-pack names to `pack-objects`.

The patch sorts the `--keep-pack` list once and switches from a linear scan to a binary search (`string_list_has_string`). The commit message reports an 11× speed-up (11 s → 1 s) when matching 20 000 kept packs against 20 000 repository packs. The change is purely internal: the comparison function (`fspathcmp`) and the set of packs that match remain unchanged. The only code touched is `builtin/pack-objects.c`, where `add_extra_kept_packs` is updated to sort its input list and use the sorted lookup helper.

This is a **clean, minimal optimization** that directly enables the scalability of patch 6/6, which passes the full list of `.keep` packs observed at `repack` startup. No new edge cases or behaviors are introduced; the patch simply makes an existing operation efficient enough to handle the larger inputs that the series will soon require. Reviewers are unlikely to object to the approach, although they may check that the sorted list does not interact poorly with any future callers that might expect insertion order.

This is the fifth patch in a six-patch **bugfix series** targeting a data-loss race in `git repack -d` during concurrent pushes. The series is well-motivated, production-tested, and under active review.

This patch adds `--keep-pack-from-file` to `git pack-objects`, allowing callers to specify a file containing a list of pack names to keep (one per line). This is a practical necessity for `git repack`, which in the final patch (6/6) will pass `pack-objects` its own snapshot of `.keep` packs—potentially hundreds or thousands of names that would exceed command-line length limits (especially on Windows, where the entire line is capped at 32K characters). The implementation is straightforward: the file is read line-by-line, empty lines are skipped, and the names are appended to the same `string_list` used by `--keep-pack`. The list now owns its strings (`strdup_strings = 1`) to accommodate both command-line and file-sourced names.

The patch includes two new tests in `t/t5331-pack-objects-stdin.sh`. The first verifies that `--keep-pack-from-file` behaves identically to `--keep-pack`: it ignores empty lines and nonexistent pack names, and the resulting pack contains the same objects. The second test confirms the expected error when the file is missing. The tests are minimal but sufficient to validate the plumbing.

This is a **clean, low-risk addition** that enables the scalability of the final patch. There are no behavior changes—only a new input channel for an existing feature. The commit message clearly explains the motivation (command-line length limits) and the design choice (file-based input). The patch is unlikely to draw controversy, though reviewers may check that the file path resolution (relative to the user’s working directory) is consistent with other Git file-based options.

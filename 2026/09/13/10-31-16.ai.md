This is the second patch in the v3 series enabling Rust compilation in Git’s GitHub Actions Windows CI jobs. It removes the `NO_RUST` opt-out in `ci/lib.sh` and adds a new step to the CI workflow that installs the precompiled Rust `std` library for the GCC-compatible target triple matching the `MSYSTEM` environment variable.

The patch is narrowly scoped to CI infrastructure, touching only `.github/workflows/main.yml` and `ci/lib.sh`. The new step maps `MSYSTEM` to the correct Rust target triple (e.g., `x86_64-pc-windows-gnu` for `MINGW64` or `UCRT64`, `aarch64-pc-windows-gnullvm` for `CLANGARM64`) and runs `rustup target add` to install the required `std` library. This ensures `cargo build` can produce a static library (`libgitcore.a`) compatible with MinGW’s `ld.exe`, addressing the core problem introduced by Git 2.55.0’s default Rust requirement. The mapping is explicit and mirrors the logic in `config.mak.uname`, but is enumerated here for clarity and to document the expected behavior for each `MSYSTEM` value.

The commit message explains why this step is necessary: GitHub’s Windows runners ship a Rust toolchain targeting the MSVC ABI by default, but Git for Windows uses the GCC ABI, so the precompiled `std` for the GCC-compatible target must be installed separately. The message also clarifies that no additional toolchain components (e.g., the `gnullvm` linker) are needed, as `cargo build` for a `staticlib` crate does not invoke an external linker.

Feedback from earlier iterations has been fully addressed. The v3 revision aligns with the recently merged `jc/rust-cargo-build-target` topic and omits the `--target` flag for native builds, as advised by James Le Cuirot. The series is now ready for final review, with no outstanding objections. The only open question is whether GitLab’s Windows runners (`saas-windows-medium-amd64`) have Rust available and are compatible with this setup, but this is not a blocker for merging.

This patch is a clean, well-motivated solution to a real CI gap. It is CI/build-system-only, with no changes to core Git functionality or user-facing features. The series is a prerequisite for the broader Rustification effort, unblocking the eventual removal of the Rust opt-out in Git’s CI. The implementation is straightforward and unlikely to be controversial.

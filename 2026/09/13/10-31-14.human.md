This is a CI/build system patch series (v3) from Johannes Schindelin, enabling Rust compilation in Git’s Windows CI jobs on GitHub Actions. The series is now ready for review after addressing all feedback from v2.

The goal is straightforward: since Git 2.55.0 requires Rust by default, the Windows CI jobs (which use a minimal Git for Windows SDK without Rust) must now use the Rust toolchain pre-installed on GitHub’s runners. The patches configure Cargo to target the GCC ABI (used by Git for Windows) instead of the default MSVC ABI, ensuring the build produces a static library (`libgitcore.a`) compatible with MinGW’s linker. The series also removes the `NO_RUST` opt-out in the CI workflow and adds steps to install the required Rust components.

Key changes in v3 include mechanical adjustments to align with the recently merged `jc/rust-cargo-build-target` topic: renaming `CARGO_TARGET` to `CARGO_BUILD_TARGET` and omitting the `--target` flag (and `CARGO_BUILD_TARGET`) for native builds. This avoids breaking Cargo’s internal assumptions, such as `RUSTFLAGS` not applying to build-time tools. The target triple mapping now correctly uses `x86_64-pc-windows-gnu` for UCRT64 (GCC ABI) and `aarch64-pc-windows-gnullvm` for CLANGARM64 (Clang ABI), resolving an inconsistency pointed out by Junio in v1.

The series touches `.github/workflows/main.yml`, `ci/lib.sh`, `config.mak.uname`, and the `Makefile`, but does not affect core Git functionality or user-facing features. It is narrowly scoped to GitHub Actions; the cover letter still requests testing on GitLab’s Windows runners (`saas-windows-medium-amd64`), as Rust availability there remains unconfirmed. The patches look well-crafted and address a clear gap in the CI setup without introducing unnecessary complexity. If the GitLab runners behave as expected, this series should unblock the eventual removal of the Rust opt-out in Git’s CI.

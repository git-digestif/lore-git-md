This thread is a two-patch bugfix series from Justin Tobler addressing a race condition in Git’s ODB transaction layer, where large blobs could trigger a "No such file or directory" error during commit when `core.fsync` batching is enabled. The series is now in its initial review phase, with both patches receiving substantive feedback.

The first patch refactors `odb_maybe_flush_packfile()` to separate ODB reprepare logic from packfile flushing, a preparatory step for the second patch. While Karthik Nayak suggested a minor optimization (conditional flushing), Justin declined it. Patrick Steinhardt later raised a correctness concern: the refactoring now calls `odb_reprepare()` unconditionally after `flush_packfile_transaction()`, even if the flush fails, which could mask errors in edge cases like filesystem failures. This remains unresolved.

The second patch moves the `flush_packfile_transaction()` call earlier in `odb_transaction_files_commit()` to flush pending packfiles before transaction migration, eliminating the race. Karthik confirmed the logic is sound, and Patrick previously agreed. However, in the latest email, Patrick flags two issues: the commit message inaccurately claims that repreparation is "slightly deferred" (only the flush is moved, not the reprepare), and the test’s comment doesn’t match its implementation. The test checks object readability post-commit but doesn’t directly verify that temporary files are absent. Patrick suggests a subshell for cleaner test setup, though Justin may prefer the current approach for performance.

The series is close to being ready, pending a v2 to address Patrick’s feedback on the commit message and test clarity. No fundamental objections exist, and the fix is critical for stabilizing the ODB transaction API, which underpins Patrick’s ongoing ODB abstraction work. The unresolved question about error handling in patch 1/2 is unlikely to block progress but may warrant a follow-up. Key participants include Justin (author), Karthik (reviewer), and Patrick (reviewer and ODB subsystem lead).

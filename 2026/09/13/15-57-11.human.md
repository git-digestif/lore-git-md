This is the first patch in a two-part CI/build system series (v4) that enables Rust compilation in Git’s GitHub Actions Windows CI jobs. The patch ensures that when Git is built under MSYS2/MinGW with Rust support, the Rust toolchain targets the GCC-compatible ABI (used by Git for Windows) rather than the default MSVC ABI. Without this change, Cargo produces a `.lib` file that MinGW’s `ld.exe` cannot link, causing build failures in CI.

The patch reuses and fixes the `HOST_CPU` variable to derive the correct Rust target triple (e.g., `x86_64-pc-windows-gnu` for `UCRT64`, `aarch64-pc-windows-gnullvm` for `CLANGARM64`) based on the `MSYSTEM` environment variable. It then sets `CARGO_BUILD_TARGET` to this triple, ensuring Cargo generates a static library (`libgitcore.a`) in the correct location. The `RUST_LIB` path is updated to include the target triple, and the logic is explicitly enumerated for each `MSYSTEM` value to avoid ambiguity. The patch touches `Makefile` and `config.mak.uname` but does not affect core Git functionality or user-facing features.

This revision (v4) incorporates all prior feedback, including removing the `--target` flag for native builds (now handled by the recently merged `jc/rust-cargo-build-target` topic) and aligning the variable naming with established conventions. The patch is narrowly scoped to Windows CI and is a prerequisite for the broader Rustification effort, as it unblocks the eventual removal of the `NO_RUST` opt-out in CI. The commit message is clear and well-motivated, linking to a failed CI run that demonstrates the original problem.

The patch looks ready for merging, assuming no further issues arise in testing on GitLab’s Windows runners (which remain unconfirmed). It is unlikely to be controversial, as it addresses a clear technical gap without introducing unnecessary complexity. The second patch in the series will remove the `NO_RUST` opt-out and add the `rustup target add` step to install the required Rust components.

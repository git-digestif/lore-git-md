This is the v3 cover letter for a CI/build system patch series that enables Rust compilation in Git’s GitHub Actions Windows CI jobs. The series is now ready for review after incorporating feedback from v2, with two key adjustments: (1) renaming `CARGO_TARGET` to `CARGO_BUILD_TARGET` to align with the recently merged `jc/rust-cargo-build-target` topic, and (2) omitting the `--target` flag (and `CARGO_BUILD_TARGET`) entirely for native builds, as explicitly targeting the native host changes Cargo’s internal behavior and can break assumptions (e.g., `RUSTFLAGS` not applying to build-time tools). The series remains narrowly scoped to Windows CI, touching `.github/workflows/main.yml`, `ci/lib.sh`, `config.mak.uname`, and the `Makefile`.

The motivation is clear: since Git 2.55.0, Rust is required by default, but Windows CI jobs currently opt out because the minimal Git for Windows SDK lacks Rust. This series leverages the pre-installed Rust toolchain on GitHub’s Windows runners, configuring it to target the GCC ABI (used by Git for Windows) instead of the default MSVC ABI. The first patch maps the `MSYSTEM` environment variable to the correct Rust target triple (e.g., `x86_64-pc-windows-gnu` for `UCRT64`), while the second removes the `NO_RUST` opt-out and installs the precompiled Rust `std` library for the GCC-compatible target. The series is well-motivated and practical, addressing a concrete gap in the CI setup without introducing unnecessary complexity.

Feedback from v2 has been fully addressed. Junio C Hamano’s review identified a naming inconsistency (`CARGO_TARGET` vs. `CARGO_BUILD_TARGET`), and James Le Cuirot clarified that `--target` should not be set for native builds, as it alters Cargo’s behavior in ways that can break the build. Both points are now resolved in v3. The series is unlikely to be controversial, though the author still requests testing on GitLab’s Windows runners (`saas-windows-medium-amd64`) to confirm Rust availability and toolchain compatibility there. This is not a blocker for merging, but it’s a sensible caveat.

The patches are CI/build-system-only, with no changes to core Git functionality, on-disk formats, or user-facing features. Test coverage is limited to CI validation, as the changes are infrastructure-focused. The series is a prerequisite for the broader Rustification effort in Git, unblocking the eventual removal of the Rust opt-out in Git’s CI. It does not interact with other in-flight efforts (e.g., ODB abstraction, reftable backend) and is self-contained.

Overall, this looks like a clean, well-scoped solution to a real problem. The adjustments in v3 reflect thoughtful engagement with feedback, and the series is now ready for final review. If the GitLab runners behave as expected, this should be a straightforward merge.

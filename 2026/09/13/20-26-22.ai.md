This is the second and final patch in a two-patch bugfix series targeting a race condition in Git's object database (ODB) transaction layer. The series addresses a specific failure scenario during commit when loose objects and large blobs are present with `core.fsync` batching enabled.

The patch ensures that any pending packfile in an ODB transaction is flushed *before* the transaction migrates its objects to the main ODB, rather than after. This fixes a race where a large blob (exceeding `core.bigFileThreshold`) is written to a packfile in the transaction's temporary directory, but the transaction migrates before the packfile is finalized, leaving it unflushed and causing a "No such file or directory" error during the subsequent rename operation. The fix is minimal: moving the call to `flush_packfile_transaction()` earlier in `odb_transaction_files_commit()`.

The patch also adds a new test in `t/t1050-large.sh` that reproduces the bug with a minimal repository setup: two files (one small, one large), `core.fsync` enabled, and `core.fsyncMethod` set to `batch`. The test verifies that neither object is left behind in a temporary location after the transaction commits.

This is a narrowly scoped, well-motivated fix that directly addresses the root cause of the race. The first patch in the series (already summarized) refactored `odb_maybe_flush_packfile()` to separate ODB reprepare logic from packfile flushing, making this change possible. The series is part of the ongoing ODB abstraction effort led by Patrick Steinhardt, and Justin Tobler (the author) is a frequent contributor to that work. The patch touches only `object-file.c` and adds a targeted test, with no on-disk format changes or new CLI/config options.

The fix appears correct and uncontroversial, but no reviews have been posted yet. The test coverage is appropriate, and the commit message clearly explains the problem and solution. This patch is likely to be merged once reviewed, as it resolves a real bug without introducing broader changes.

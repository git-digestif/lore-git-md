This is a CI/build system patch series (v4) that enables Rust compilation in Git’s GitHub Actions Windows CI jobs. It is the fourth iteration of a two-patch series originally posted by Johannes Schindelin to address the Rust requirement introduced in Git 2.55.0. The series is narrowly scoped to Windows CI and does not affect core Git functionality, on-disk formats, or user-facing features.

The core goal is to configure GitHub’s pre-installed Rust toolchain to target the GCC ABI (used by Git for Windows) instead of the default MSVC ABI, ensuring Cargo produces a static library (`libgitcore.a`) compatible with MinGW’s linker. This avoids the need to include Rust in the minimal Git for Windows SDK, which would more than double its size. The v4 revision removes the now-unnecessary `--target` flag for native builds, aligning with feedback from James Le Cuirot and the recently merged `jc/rust-cargo-build-target` topic. The `CARGO_BUILD_TARGET` variable is now set only for cross-compilation cases (e.g., `aarch64` builds on `x86_64` runners), while native builds omit it entirely to avoid breaking Cargo’s internal assumptions.

Key changes since v3 include removing outdated references to `--target` in the commit message and dropping the flag from the build configuration. The series remains split into two patches: the first maps the `MSYSTEM` environment variable to the correct Rust target triple (e.g., `x86_64-pc-windows-gnu` for `UCRT64`, `aarch64-pc-windows-gnullvm` for `CLANGARM64`) and adjusts the `RUST_LIB` path accordingly, while the second removes the `NO_RUST` opt-out in `ci/lib.sh` and adds a step to install the precompiled Rust `std` library via `rustup target add`. The patches touch `.github/workflows/main.yml`, `ci/lib.sh`, `config.mak.uname`, and the `Makefile`, with no new test files or test cases.

The series is now considered ready for final review, with all prior feedback addressed. Junio C Hamano and James Le Cuirot raised no further objections in the v3 discussion, and the v4 changes are mechanical cleanups rather than substantive rework. The only open question is whether the patches work on GitLab’s Windows runners (`saas-windows-medium-amd64`), as Rust availability and toolchain compatibility there remain unconfirmed. Johannes explicitly requests testing from GitLab contributors (e.g., Patrick Steinhardt) but does not treat this as a blocker for merging.

This series is a prerequisite for the broader Rustification effort in Git, as it unblocks the eventual removal of the Rust opt-out in CI. It is unlikely to be controversial, assuming the GitLab runners behave as expected. The patches are well-motivated, narrowly scoped, and address a clear gap in the CI setup without introducing unnecessary complexity.

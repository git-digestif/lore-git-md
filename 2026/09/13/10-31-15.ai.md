This is the first patch in a two-part CI/build system series (v3 1/2) that configures Git’s Windows CI jobs to compile Rust code with a GCC-compatible ABI, ensuring the resulting static library (`libgitcore.a`) can be linked by MinGW’s `ld.exe`. The patch touches `Makefile` and `config.mak.uname` to map the `MSYSTEM` environment variable (e.g., `UCRT64`, `CLANGARM64`) to the correct Rust target triple (`x86_64-pc-windows-gnu` or `aarch64-pc-windows-gnullvm`) via the `CARGO_BUILD_TARGET` variable. The `HOST_CPU` variable is repurposed to derive the CPU architecture (`i686`, `x86_64`, or `aarch64`), and the `RUST_LIB` path is adjusted to include the target triple, ensuring the build process picks up the correct `.a` file.

The motivation is clear: Git’s Windows CI jobs use a minimal Git for Windows SDK that lacks Rust, and the default Rust toolchain on GitHub’s Windows runners targets the MSVC ABI, producing a `.lib` file incompatible with MinGW. This patch ensures Cargo generates a `.a` file that MinGW’s linker can consume, unblocking the default Rust requirement introduced in Git 2.55.0. The changes are narrowly scoped to the build system and do not affect core Git functionality or user-facing features.

Key technical details include the conditional logic in `config.mak.uname` that maps `MSYSTEM` to the appropriate Rust target triple, and the adjustment to `RUST_LIB` in the `Makefile` to include the target triple in the path. The patch also repurposes `HOST_CPU` to avoid relying on environment variables not present in the minimal SDK. The commit message notes that `rustup target add` is sufficient for installing the required Rust components, as Cargo’s `staticlib` crate type does not invoke an external linker.

Feedback from prior versions has been addressed: the `CARGO_TARGET` variable was renamed to `CARGO_BUILD_TARGET` to align with the recently merged `jc/rust-cargo-build-target` topic, and the logic for deriving `HOST_CPU` was fixed to correctly handle ARM64 builds. The patch is well-motivated and practical, with a clear link to a failed CI run demonstrating the original problem. No new test files or test cases are introduced, as the changes are CI/build-system-only.

This patch is a prerequisite for the broader Rustification effort in Git, as it removes a key blocker in the Windows CI setup. It is unlikely to be controversial, though the author has requested testing on GitLab’s Windows runners to confirm Rust availability and toolchain compatibility there. The series is now ready for final review, with the second patch removing the `NO_RUST` opt-out and installing the precompiled Rust `std` library.

This is the second patch in a two-part CI/build system series (v4) that enables Rust compilation in Git’s GitHub Actions Windows CI jobs. It directly addresses the gap identified in the first patch by installing the precompiled Rust `std` library for the GCC-compatible target triple (e.g., `x86_64-pc-windows-gnu` for `MINGW64`/`UCRT64`, `aarch64-pc-windows-gnullvm` for `CLANGARM64`) via `rustup target add`. The patch removes the `NO_RUST` opt-out in `ci/lib.sh` and adds a new step in `.github/workflows/main.yml` that maps the `MSYSTEM` environment variable to the correct Rust target triple, ensuring Cargo can produce a static library (`libgitcore.a`) compatible with MinGW’s linker.

The implementation is straightforward and mirrors the logic already present in `config.mak.uname`, but enumerates the expected `MSYSTEM` values explicitly for clarity and documentation. The new step runs `rustup target add` for the derived target triple, which is sufficient because Cargo’s `staticlib` crate type does not invoke an external linker. The patch also adjusts the `PATH` to ensure `cargo.exe` is found in the minimal Git for Windows SDK environment. No additional toolchain components (e.g., the `gnullvm` linker) are needed.

This patch is a mechanical follow-up to the first patch in the series and completes the CI setup required to unblock the Rustification effort in Git. All prior feedback has been addressed, including the removal of the `--target` flag for native builds (aligned with the recently merged `jc/rust-cargo-build-target` topic) and the explicit mapping of `MSYSTEM` to Rust target triples. The series is now ready for final review, with the only open question being whether the patches work on GitLab’s Windows runners (`saas-windows-medium-amd64`), though this is not treated as a blocker.

The patch touches `.github/workflows/main.yml` and `ci/lib.sh`, with no changes to core Git functionality, on-disk formats, or user-facing features. It is narrowly scoped to Windows CI and is unlikely to be controversial, assuming the GitLab runners behave as expected. The commit message is clear and well-motivated, and the implementation is clean and minimal.

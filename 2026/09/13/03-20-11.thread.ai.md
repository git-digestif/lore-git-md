Subject: [PATCH 0/2] worktree repair: fix incorrect repair of unrelated worktrees

Core problem or goal
The `git worktree repair` command can incorrectly modify `.git` files or gitdirs belonging to unrelated worktrees when cross-references between a linked worktree and its administrative data are not validated before repair. The goal is to add validation that ensures the repair target is correct before making changes, preventing accidental corruption of unrelated worktrees. The issue manifests in edge cases such as manually swapped worktree directories or copied linked worktrees, where `git worktree repair` would previously operate on the wrong administrative files without checks.

Key technical details
- Files touched: `worktree.c`, `t/t2406-worktree-repair.sh` (patches 1–5)
- New/renamed symbols: `read_gitfile_raw()` (new helper function for stricter `.git` file parsing, introduced in patch 2), `get_worktree_id()` (new helper function, internal use only, introduced in patch 3)
- Behavior change: `git worktree repair` now validates the worktree ID and gitdir path before making changes, skipping repairs if the target is unrelated. The refactoring in patches 1–4 also adjusts error handling for malformed `.git` files:
  - Rejects `.git` files with `gitdir:` prefixes missing a trailing space (e.g., `gitdir:foo/bar`), which the original code accepted.
  - Treats trailing whitespace in `.git` files as part of the path (e.g., `gitdir: foo/bar/   ` resolves to `worktrees/   `), whereas the original code trimmed it.
  - Behavior for completely invalid `.git` files (e.g., missing `gitdir:` prefix) remains unchanged, as `read_gitfile_gently()` is still used for initial validation.
- Patch 1:
  - Replaces `read_gitfile_gently()` with `read_gitfile_raw()` in `repair_worktree_at_path()`, moving path resolution and repository validation to the caller.
  - Uses `strbuf` for `.git` file content, avoiding memory leaks and aligning with `repair_gitfile()`.
  - Explicitly handles absolute and relative paths in `.git` files, stripping the `.git` suffix and appending relative paths when necessary.
  - Preserves existing fallback to inferred backlinks when the `.git` file is invalid but an inferred path exists.
- Patch 2:
  - Refactors `repair_worktree_at_path()` to centralize inferred backlink selection logic, reordering steps so the inferred backlink is computed after reading the `.git` file but before validating the backlink’s gitdir.
  - Ensures the inferred backlink is preferred when both a valid gitdir and an inferred path exist, addressing edge cases where a worktree was copied (rather than moved) alongside its main repository.
  - No new functions or behavior changes; the logic is now clearer and easier to follow.
- Patch 3:
  - Refactors `infer_backlink()` to use `read_gitfile_raw()`, ensuring consistent parsing of `.git` files (e.g., trailing whitespace handling, `gitdir:` prefix validation) with `repair_gitfile()` and `repair_worktree_at_path()`.
  - Extracts `get_worktree_id()` as a helper function to simplify worktree ID extraction, replacing manual pointer arithmetic with a cleaner abstraction. This function is reused in patch 5 for validation logic.
  - No behavior changes; the patch is purely internal refactoring to align parsing rules and reduce code duplication.
- Patch 4:
  - Eliminates a redundant `read_gitfile_raw()` call in `infer_backlink()` by passing the already-loaded `.git` file contents from `repair_worktree_at_path()`.
  - Removes the now-unused `gitfile` parameter from `infer_backlink()` and drops the local `strbuf`, relying on the caller’s buffer.
  - No behavior changes; the patch is purely internal refactoring to reduce redundant file I/O.
- Patch 5:
  - Adds validation logic to `repair_gitfile()` and `repair_worktree_at_path()` to prevent repairs on unrelated worktrees.
  - `repair_gitfile()` now checks whether the worktree ID extracted from the `.git` file matches the expected `wt->id`; if not, it aborts with an "unrelated .git file" error.
  - `repair_worktree_at_path()` now fails early if the inferred gitdir path is empty, avoiding repairs that could overwrite unrelated gitdirs.
  - Refactors `get_worktree_id()` to validate the `/worktrees` prefix before extracting the ID, improving robustness. Junio’s review highlights that this validation does not account for backslashes (e.g., `\worktrees`) or duplicate slashes (e.g., `//worktrees`), which could occur in malformed or manually edited `.git` files on Windows.
  - No changes to on-disk format.
- Test coverage: Updated `t/t2406-worktree-repair.sh` in patches 2–5 with test cases for skipping unrelated `.git` files, handling `.git` files that do not belong to a linked worktree, verifying the new error-handling behavior (e.g., rejection of malformed `gitdir:` prefixes), and validating the worktree ID and gitdir inference checks introduced in patch 5. The v2 series expands coverage to include the stricter parsing rules introduced in patches 1–4 and the validation logic in patch 5.

Open questions and loose ends
- **Robustness of `get_worktree_id()`**: Junio’s review questions whether the function is sufficiently defensive in handling non-canonical path separators (backslashes, duplicate slashes) in `.git` file contents. The current implementation assumes forward slashes and does not account for Windows-style paths or malformed inputs with duplicate slashes. This could lead to false negatives in validation, allowing repairs on unrelated worktrees in edge cases. The author may need to address this either by hardening the function or documenting its limitations.
- The potential for unintended side effects from the stricter `.git` file parsing (e.g., breaking manually edited `.git` files) remains untested in broader review. The validation logic in patch 5 could interact unexpectedly with these rules, though the separation of concerns in v2 mitigates this risk.
- The inferred backlink selection logic in patch 2, while clearer, could introduce subtle breakage if the reordering interacts unexpectedly with the stricter `.git` file parsing in patch 1. This risk is mitigated by the patch’s simplicity, but it remains untested in broader review.
- No feedback from other contributors; the series has not yet attracted broader review. The validation logic in patch 5 is straightforward and well-motivated, but its edge-case handling (e.g., interaction with the stricter `.git` file parsing and the `get_worktree_id()` robustness question) remains untested.

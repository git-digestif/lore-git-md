# Git mailing list daily digest for 2026/09/13

## The day in brief
Junio C Hamano approved and fast-tracked a CI/build system series enabling Rust compilation in Git’s GitHub Actions Windows jobs. A Coccinelle rule discussion shifted toward accepting compiler warnings for correctness, while a documentation series dropped its lint script patch. New bugfix series addressed worktree repair validation, ODB transaction races, and Windows test compatibility.

## Notable threads

### Rust compilation in GitHub Actions Windows CI
Johannes Schindelin’s two-patch series enabling Rust compilation in Git’s GitHub Actions Windows CI jobs reached final approval. Junio C Hamano [2026/09/13/22-52-34] agreed to merge the v4 iteration directly into `next` and fast-track it to `master`, bypassing the usual one-week cooking period. The series configures the Rust toolchain to target the GCC ABI (MinGW) instead of the default MSVC ABI, ensuring Cargo produces a static library (`libgitcore.a`) compatible with Git for Windows’ linker. All prior feedback from Junio and James Le Cuirot has been addressed, including the removal of the `--target` flag for native builds to align with Cargo’s expected behavior. The patches touch `.github/workflows/main.yml`, `ci/lib.sh`, `config.mak.uname`, and the `Makefile`, but do not affect core Git functionality or user-facing features. The series is a prerequisite for the broader Rustification effort, as it removes the `NO_RUST` opt-out in CI.

### Coccinelle rule removal and compiler warning trade-offs
The discussion around removing a risky Coccinelle rule (`tools/coccinelle/free.cocci`) that converted `if (!E) free(E);` into an unconditional `free(E)` took a substantive turn. René Scharfe [2026/09/13/10-45-48] argued that the project should tolerate compiler warnings for the sake of correctness, noting that GCC accepts `if (!E);` without warning while Clang warns (though both accept `if (!E) {}`). He acknowledged the risk of removing the guarded `free(E)` call entirely—specifically, losing side effects from evaluating `E`—but argued that the bluntness of simply deleting the line is preferable to preserving flawed code for the sake of politeness. The thread remains unresolved, with no consensus on whether to adopt René’s approach, Junio’s original rule removal, or another alternative. The discussion now hinges on the project’s tolerance for compiler warnings and the perceived risk of side effects.

### Documentation backtick-quoting consistency
Todd Zullinger’s v1 patch series fixing backtick-quoting inconsistencies in `git-refs` and `git-pack-refs` man pages will drop its lint script patch in v2. Todd [2026/09/13/14-14-05] acknowledged Jean-Noël Avila’s substantive review objection to the lint script change in patch 1, which identified false positives in five unrelated man pages (`git-add.adoc`, `git-push.adoc`, `git-difftool.adoc`, `git-daemon.adoc`, `git-fetch.adoc`). The objection did not question the goal of consistent backtick-quoting for commands and options, only the mechanical means of enforcing it. Todd plans to resubmit v2 with only the mechanical backtick-quoting conversions in patches 2 and 3, which remain uncontested. The series is part of the ongoing synopsis-style documentation conversion effort led by Jean-Noël Avila.

### Worktree repair validation
Yoichi NAKAYAMA [2026/09/13/03-20-11] posted a two-patch bugfix series to prevent `git worktree repair` from incorrectly modifying unrelated worktrees. The issue arises when cross-references between a linked worktree and its administrative data are not validated before repair, risking corruption of unrelated worktrees in edge cases like manually swapped directories. Patch 1/2 refactors the code to reduce redundant `.git` file reads and extract the worktree ID, while patch 2/2 adds validation logic using that ID to ensure the repair target is correct. The series includes test coverage for the new behavior in `t/t2406-worktree-repair.sh`. The changes are confined to `worktree.c` and the test script, addressing a subtle but important correctness issue in the worktree subsystem.

### ODB transaction race fix
Justin Tobler [2026/09/13/20-26-20] posted a two-patch series to fix a race condition in the ODB transaction layer during commit when loose objects and large blobs are present with `core.fsync` batching enabled. The bug occurs when a "large" blob (exceeding `core.bigFileThreshold`) is written to a packfile in a transaction’s temporary directory, but the transaction migrates to the main ODB before the packfile is finalized, leaving it unflushed and causing a "No such file or directory" error. Patch 1/2 refactors `odb_maybe_flush_packfile()` to separate ODB reprepare logic from packfile flushing, while patch 2/2 adds a call to flush pending transaction packfiles before migration. The series includes a new test in `t/t1050-large.sh` that reproduces the bug with a minimal repository setup. The fix is narrowly scoped to the ODB transaction layer and aligns with the ongoing ODB abstraction effort led by Patrick Steinhardt.

### Windows test compatibility fixes
Johannes Schindelin [2026/09/13/19-11-05] posted a two-patch series to fix Windows-specific test failures encountered during full Windows/ARM64 test runs in preparation for Git for Windows v2.56.0-rc0. The first patch adjusts Perl environment detection in `t/t9700/test.pl` to accommodate MSYS2 Perl now reporting itself as `cygwin`, while the second patch unconditionally skips UTF-8 tests in `t/t9129` on Windows due to fundamental encoding incompatibilities. The changes are minimal (3 insertions/deletions total) and confined to the test suite, addressing platform-specific quirks without affecting core Git functionality.

### CMake build system update for UCRT64
Johannes Schindelin [2026/09/13/20-41-12] posted a patch to update the CMake build system for Git for Windows’ migration from the MINGW64 toolchain to UCRT64. The change updates the Unix tools prefix in `contrib/buildsystems/CMakeLists.txt` from `/mingw64/` to `/ucrt64/`, ensuring `git.exe` correctly locates its dependencies. The patch is a follow-up to the recently merged `js/mingw-build-updates` series and is required for Git for Windows but optional for core Git. The commit message explains the technical necessity and timing clearly, aligning the build system with an already-completed migration.

### Advice scope hint simplification
The discussion around Vsevolod Myalitsin’s patch series adding scope hints to Git’s advice settings took a new turn. Junio C Hamano [2026/09/13/16-32-37] proposed an even simpler approach: the hint could *always* recommend `--global` without needing to mark individual advice settings for their intended scope, eliminating the need for the `is_global_hint` field entirely. This conflicts with Jeff King’s argument that some settings (like `defaultBranchName`) are inherently global and should be marked as such. Junio clarified that the original 2009 design of the `advice.*` config system never intended the scope-less hint to be a literal cut-and-paste command, and that adding scope hints now is a deliberate enhancement. The thread remains unresolved, with no indication yet of whether Junio will pick up the series for integration.

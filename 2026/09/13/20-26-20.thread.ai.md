Thread identity: Bugfix series addressing a race in the ODB transaction layer during commit when loose objects and large blobs are present with `core.fsync` batching enabled. Series version: v1 (initial submission, pending v2 update). Originating author: Justin Tobler. Thread type: patch series (bugfix).

Core problem or goal: Fix a race condition where a "large" blob (exceeding `core.bigFileThreshold`) is written to a packfile in a transaction's temporary directory, but the transaction migrates to the main ODB before the packfile is finalized. This leaves the packfile unflushed, causing a "No such file or directory" error during the subsequent rename operation. The fix ensures pending packfiles are flushed before transaction migration by refactoring `odb_maybe_flush_packfile()` (patch 1/2) and adding a call to flush pending transaction packfiles earlier in `odb_transaction_files_commit()` (patch 2/2).

Current status: Under review, with feedback incorporated for a planned v2 update. The series consists of two patches:
1. Refactored `odb_maybe_flush_packfile()` to separate ODB reprepare logic from packfile flushing (preparatory for patch 2/2). Karthik Nayak suggested a minor optimization (conditional flush when `have_packfile` is true), which Justin Tobler declined. Patrick Steinhardt initially noted a potential behavior change: `odb_reprepare()` was now called unconditionally after `flush_packfile_transaction()`, even if the flush failed. Justin later clarified that this was a misunderstanding—`odb_reprepare()` is only invoked when there is a packfile to flush, matching the original behavior. The broader issue of missing error handling in `flush_packfile_transaction()` (which swallows errors by calling `die()` internally) remains unresolved but is deferred to a future series. No changes to the patch are planned for this.
2. Adds a call to `flush_packfile_transaction()` earlier in `odb_transaction_files_commit()` to flush pending packfiles before transaction migration, resolving the race. Includes a new test (`t/t1050-large.sh`) that reproduces the bug. Karthik Nayak confirmed the logic is correct and necessary. Patrick Steinhardt provided feedback on the commit message and test: (a) the commit message incorrectly claims that repreparation is "slightly deferred" (only the flush is moved, not the reprepare), and (b) the test’s comment ("Neither object may be left behind in a temporary location") does not match its implementation (it checks object readability, not temporary directory contents). Justin Tobler has now accepted this feedback and will correct the commit message to remove the misleading claim about repreparation, adopt Patrick’s subshell suggestion for test setup to improve readability, and drop the inaccurate comment in the test. The test will continue to verify object readability, not directory contents.

Key technical details:
- Files touched: `object-file.c` (ODB transaction layer), `t/t1050-large.sh` (new test).
- Symbols: `odb_maybe_flush_packfile()` (refactored to separate reprepare logic), `flush_packfile_transaction()` (now called earlier in `odb_transaction_files_commit()`), `odb_transaction_files_write_object_stream()` and `odb_transaction_files_commit()` (callers updated to handle reprepare logic).
- Behavior change: Patch 2/2 ensures packfiles are flushed before transaction migration, eliminating the race. Patch 1/2’s refactoring does not alter the original behavior regarding `odb_reprepare()` calls (it is only invoked when there is a packfile to flush). No on-disk format changes or new CLI/config options introduced.
- Test coverage: The race is reproduced and fixed in `t/t1050-large.sh`, which verifies object readability after commit. The test’s comment about temporary directory contents will be removed in v2.

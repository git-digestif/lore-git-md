This is a CI/build system patch series (v2) targeting Git’s GitHub Actions Windows CI jobs. It enables Rust compilation by configuring the pre-installed Rust toolchain on GitHub’s Windows runners to target the GCC ABI (used by Git for Windows) instead of the default MSVC ABI, unblocking the default Rust requirement introduced in Git 2.55.0.

The series consists of two patches. The first ensures Cargo picks a GCC-compatible target under MSYS2/MinGW by mapping the `MSYSTEM` environment variable to the correct Rust target triple (e.g., `x86_64-pc-windows-gnu` for UCRT64 and MINGW64). The second patch removes the `NO_RUST=UnfortunatelyYes` opt-out in the CI workflow, installs the Rust standard library for the GCC-compatible target, and adjusts the `PATH` to ensure `cargo.exe` is found in the minimal Git for Windows SDK environment. The changes touch `.github/workflows/main.yml`, `ci/lib.sh`, `config.mak.uname`, and the `Makefile`, but do not affect core Git functionality or user-facing features.

Since v1, the series addresses Junio C Hamano’s feedback by correcting an inconsistency in the UCRT64 target triple mapping: UCRT64 now consistently maps to `x86_64-pc-windows-gnu` (GCC ABI) instead of `x86_64-pc-windows-gnullvm` (Clang ABI), aligning with the MinGW toolchain used by Git for Windows. The commit message also clarifies that `rustup target add` is sufficient to install the required Rust bits, as the linker is already provided by the SDK.

The series is narrowly scoped to GitHub Actions and does not attempt to address GitLab’s Windows runners, where Rust availability remains unconfirmed. The author explicitly requests testing on GitLab’s `saas-windows-medium-amd64` runners to determine whether additional changes are needed. The patches are well-motivated and practical, addressing a clear gap in the CI setup without introducing unnecessary complexity. The request for GitLab testing is a sensible caveat, and the series is unlikely to be controversial if the GitLab runners behave as expected.

This work is a prerequisite for the broader Rustification effort in Git, as it removes the CI opt-out that currently blocks Rust code from being compiled in Windows CI jobs. The changes are minimal and focused, with no new test files or test cases—coverage is limited to CI validation. The series looks ready to merge once the GitLab testing question is resolved.

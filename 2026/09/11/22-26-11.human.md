This is a CI/build system discussion about the Rust toolchain configuration in Git’s Windows CI workflows. The email is a reply in the thread reviewing Johannes Schindelin’s v2 patch series that enables Rust compilation in GitHub Actions Windows jobs by targeting the GCC ABI (MinGW) instead of the default MSVC ABI.

James Le Cuirot, the author of the recently merged `jc/rust-cargo-build-target` topic, weighs in to clarify how Cargo’s target handling works. He confirms Junio C Hamano’s suggestion that `CARGO_BUILD_TARGET` is the correct variable to use (not `CARGO_TARGET`) but adds an important caveat: the variable should *not* be set at all when not cross-compiling. Setting it explicitly—even to the native target triple—changes Cargo’s behavior in ways that can break builds, such as restricting `RUSTFLAGS` to target binaries only. His example from Gentoo Linux’s Rust packaging shows that omitting `--target` (and thus `CARGO_BUILD_TARGET`) is the standard practice for native builds.

The email includes the relevant diff from his merged patch, which already adjusts the build logic to respect `CARGO_BUILD_TARGET` when locating the compiled Rust library (`libgitcore.a`). This reinforces the need for consistency: Schindelin’s patch should align with the existing pattern rather than introducing a parallel `CARGO_TARGET` variable. The feedback is technical but narrow, focusing solely on Cargo’s expected behavior and avoiding broader discussion of the series’ goals.

This exchange is unlikely to derail the series—it’s a straightforward naming and behavior alignment issue—but it does highlight a subtle gotcha in Rust’s build system. The author will need to adjust the patch to either omit `CARGO_BUILD_TARGET` for native builds or ensure it’s only set when genuinely cross-compiling.

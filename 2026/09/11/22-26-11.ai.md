This is a **CI/build system** follow-up in the ongoing thread to enable Rust compilation in Git’s GitHub Actions Windows CI jobs. The email is a **substantive review reply** from James Le Cuirot (the author of the recently merged `jc/rust-cargo-build-target` topic) that clarifies how Cargo’s target handling works and reinforces Junio C Hamano’s naming feedback on Johannes Schindelin’s patch.

James explains that the correct approach is to **avoid setting `--target` (or `CARGO_BUILD_TARGET`) entirely when not cross-compiling**, rather than introducing a new `CARGO_TARGET` variable. Cargo’s default behavior is to build for the native host, and explicitly setting the target triple—even if it matches the native host—changes Cargo’s internal behavior in ways that can break assumptions (e.g., `RUSTFLAGS` being applied only to the target, not to build-time tools). His recommendation aligns with Gentoo Linux’s Rust cross-compilation practices, where the native build is left untargeted and only cross-builds specify a target.

The email includes the full commit message and diff from `jc/rust-cargo-build-target` to illustrate how `CARGO_BUILD_TARGET` is already used in Git’s build system to locate build artifacts in the correct target-specific subdirectory. This reinforces Junio’s earlier point that the new `CARGO_TARGET` variable should be renamed to `CARGO_BUILD_TARGET` for consistency.

No new technical objections are raised; the feedback is narrowly focused on Cargo’s expected behavior and variable naming. The author of the original patch (Johannes Schindelin) will likely revise the series to drop the explicit `--target` flag for native builds and adopt `CARGO_BUILD_TARGET` for cross-compilation cases. The change is mechanical and should not affect the series’ core goal of enabling Rust compilation in Windows CI.

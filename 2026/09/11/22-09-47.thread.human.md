This thread is about a small but consequential change to Git’s Coccinelle rules, specifically removing a rule that automatically converted guarded `free(E)` calls into unconditional ones—a transformation that could introduce bugs. Junio Hamano kicked off the discussion by removing the risky rule from `tools/coccinelle/free.cocci`, arguing it was too dangerous. A follow-up patch then explicitly allowed unconditional `FREE_AND_NULL(E)` calls, aligning the tool’s behavior with safer practices.

The debate has since centered on whether the guarded `free(E)` call should be removed entirely (René Scharfe’s preference) or left as-is (Junio’s original approach). René has pushed back, questioning the rule’s original utility and advocating for a more aggressive cleanup—even if it risks compiler warnings for empty `if` blocks. His latest email provides concrete evidence that GCC accepts `if (!E);` without complaint, while Clang warns (though both accept `if (!E) {}`). He acknowledges the risk of losing side effects from evaluating `E` but argues that the bluntness of simply deleting the line is preferable to preserving flawed code for the sake of build hygiene.

No consensus has emerged yet. The thread remains under review, with the discussion now pivoting to whether the project should tolerate compiler warnings as a trade-off for correctness. The current patch (removing the Coccinelle rule) is the safest middle ground, but René’s questions about the rule’s value and the project’s tolerance for warnings could prompt further changes. For now, the only file touched is `free.cocci`, and no runtime code or tests are affected.

Thread identity: patch series introducing `--matched-only` option to `git range-diff`; originating author Harald Nordgren; thread type: feature patch; series version v3 (final, mechanically complete).

Core problem or goal: add a `--matched-only` flag to `git range-diff` that filters output to show only commits present in both input ranges, addressing the workflow pain point of reviewing rebases or range-diffs where users want to focus on how surviving commits changed rather than seeing added or dropped commits. The feature’s motivation is concretely illustrated: when rebasing a long-lived branch against `master`, the default output buries relevant changes under hundreds of unrelated commits, while `--matched-only` filters to show only the commits present in both ranges, eliminating irrelevant entries. The distinction from `--left-only` is clarified: while `--left-only` can filter out dropped commits, it cannot simultaneously suppress added commits, making `--matched-only` the only solution for the core use case. Junio’s clarification confirms that the three-revision form of `git range-diff` (e.g., `git range-diff <base>..<rev1> <base>..<rev2>`) cannot replace `--matched-only` in the rebasing scenario, as there is no single `<base>` revision that can be used when comparing two ranges that share no common base (e.g., a topic branch before and after rebasing onto an updated `origin/master`). Ben Knoble and Matt Hunter’s replies suggest that careful input selection (e.g., `origin..old-topic` and `origin..new-topic`) or symmetric difference syntax (`<A>...<B>`) can achieve similar filtering in *some* cases, but these do not cover the full scope of the rebasing scenario—particularly when the base has advanced since the previous round—leaving the feature’s necessity intact for the workflow it targets.

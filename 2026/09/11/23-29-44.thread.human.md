This thread proposes a small but impactful usability improvement for `git blame`: automatically using `HEAD:.git-blame-ignore-revs` as the default ignore-revs file when none is explicitly configured. The goal is to align Git's local behavior with hosting platforms like GitHub and GitLab, which already respect this file by convention. The series has evolved significantly since its first iteration, now split into two carefully structured patches after maintainer feedback.

The first patch (already posted) focuses on security hardening—critical because the ignore-revs parser will now process upstream-controlled content. It rejects malformed input like embedded NUL bytes and prevents promisor fetches in partial clones, ensuring the parser is robust before being exposed to untrusted data. The second patch, just posted, implements the core feature: checking for the `.git-blame-ignore-revs` blob in the `HEAD` tree and parsing it in memory if found. The design intentionally skips untracked working-tree files to avoid surprises, favoring the committed version instead. Edge cases like subdirectory invocations, bare repositories, and CLI/config overrides are all handled, and the documentation has been updated to clarify the new behavior.

Junio Hamano, the maintainer, initially opposed the implementation due to security and consistency concerns but later proposed the `HEAD:.git-blame-ignore-revs` approach, which the author adopted. The series is now under broader review, with the security improvements needing validation from security-interested contributors like Jeff King or brian m. carlson before integration. While the design is technically sound and well-motivated, the hardening work remains the key hurdle—its adequacy will determine whether the feature can proceed. For developers who rely on `git blame` or work with hosting platforms, this is a thread worth following.

This thread is about a patch series that makes `git blame` and `git annotate` automatically use `HEAD:.git-blame-ignore-revs` as the default ignore-revs file when no explicit file is configured. The goal is to align Git's local behavior with hosting platforms like GitHub and GitLab, which already respect this file by default. The series is now in its third version (v3), authored by Ravi Mistry, and has been approved by Junio C Hamano for integration into the `next` branch, pending minor refinements.

The series consists of two patches: the first hardens the ignore-revs parser and tag-peeling logic to reject malformed input and prevent promisor fetches in partial clones, while the second implements the default file lookup. Key technical details include security refinements like optional NUL-byte rejection and promisor fetch prevention, as well as the default file lookup logic, which resolves `HEAD:.git-blame-ignore-revs` and ensures user-configured files take precedence. The series is well-tested and feature-complete, with no new technical objections raised since v3 was posted.

Two open questions remain. First, Junio has explicitly endorsed Phillip Wood’s concern about the lack of a size limit on the ignore-revs file, flagging it as a valid scalability issue that could theoretically allow memory exhaustion from maliciously large blobs. Second, the handling of uncommitted changes to `.git-blame-ignore-revs` is still unresolved. The current implementation ignores uncommitted changes, which Phillip Wood considers a user-experience regression and inconsistency with `.gitattributes` behavior. Junio acknowledges this but remains neutral, noting that the current approach matches hosting site behavior while conceding that consulting the working-tree file "feels more intuitive." Ravi Mistry has signaled flexibility on both points and may address them in a future revision. The series’ approval for `next` remains unaffected, but these unresolved issues could prompt further discussion or a v4 patch.

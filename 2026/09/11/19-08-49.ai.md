This is the first patch in a two-part CI/build system series (v2) that enables Rust compilation in Git’s GitHub Actions Windows CI jobs. The patch ensures Cargo produces a static library (`libgitcore.a`) compatible with MinGW’s `ld.exe` by configuring the Rust toolchain to target the GCC ABI (used by Git for Windows) instead of the default MSVC ABI.

The change modifies the `Makefile` and `config.mak.uname` to introduce a `CARGO_TARGET` variable that maps the `MSYSTEM` environment variable to the correct Rust target triple. For Clang/LLVM-based subsystems (e.g., `CLANGARM64`), it uses `*-pc-windows-gnullvm`; for MSVCRT-based MinGW subsystems (e.g., `UCRT64`, `MINGW64`), it uses `*-pc-windows-gnu`. The `HOST_CPU` variable is repurposed to derive the CPU architecture (`i686`, `x86_64`, or `aarch64`). The `RUST_LIB` path is updated to include the target triple, ensuring the correct `.a` file is linked. The patch also appends `--target $(CARGO_TARGET)` to `CARGO_ARGS` to ensure Cargo builds for the correct ABI.

This patch addresses the immediate build failure in GitHub’s Windows CI runners, where the default MSVC-targeted Rust toolchain produces a `.lib` file incompatible with MinGW’s linker. The fix is minimal and narrowly scoped to the build system, with no changes to core Git functionality or user-facing features. The commit message provides clear motivation and links to a failed CI run demonstrating the original problem. The logic is well-explained and aligns with the toolchain setup used by Git for Windows.

The patch is a prerequisite for the second patch in the series, which removes the `NO_RUST` opt-out in the CI workflow. It is unlikely to be controversial, as it directly resolves a blocking issue for Rust support in Windows CI. The only open question is whether the same logic will work on GitLab’s Windows runners, which the author has explicitly flagged for testing. The patch is well-crafted, with thorough commit message documentation and a clean implementation.

This is the **final patch (3/3)** in the `dk/use-nsec-runtime` series, which has already graduated to `next` and is effectively complete. It converts the build-time `USE_NSEC` macro into a runtime configuration option (`core.useNanosec`), allowing users to enable nanosecond precision for file timestamps without recompiling Git. This addresses long-standing "racy Git" problems that degrade performance in commands like `git diff` in new worktrees.

The patch touches 10 files, including `read-cache.c`, `environment.c`, and `Documentation/config/core.adoc`. Key changes:
- Introduces the `core.useNanosec` config key (defaults to false), documented with warnings about platform/filesystem limitations.
- Replaces `#ifdef USE_NSEC` guards in `is_racy_stat()` and `match_stat_data()` with runtime checks against `repo_config_values(istate->repo)->use_nanosec`.
- Removes `USE_NSEC` from `Makefile` and `configure.ac`, eliminating the build-time knob.
- Updates `Documentation/technical/racy-git.adoc` to reflect the runtime switch and clarify platform support (e.g., ext4, XFS, and FAT are now known to work).

The patch retains a preprocessor guard (`#ifndef NO_NSEC`) around the config handler in `environment.c` to prevent reading nanosecond values on unsupported platforms, avoiding false negatives in racy checks. This guard also means users on `NO_NSEC` builds cannot enable `core.useNanosec` without recompiling, even if their platform supports it—a trade-off accepted by the author and Jeff King (Peff) as reasonable given the complexity of eliminating `NO_NSEC` entirely.

A latent bug remains: `is_racy_stat()` now calls `repo_config_values()`, which only works for `the_repository`. For other repositories (e.g., submodules), the code defaults to treating `core.useNanosec` as false. This is documented as a forward-looking constraint and a blocker for future recursive submodule operations, but no deeper refactoring was attempted due to complexity. The author’s partial analysis of 214 call paths to `repo_config_values()` confirmed all terminate at `the_repository`, but the limitation persists.

The patch is well-crafted, with thorough documentation and backward compatibility preserved. The performance regression from earlier versions (~41× slowdown) is resolved by caching the config value in `repo_config_values`. While the architectural constraint is a notable loose end, the series is ready for integration, pending routine conflict resolution with `ty/repo-config-cleanups` in `seen`. No further changes are expected.

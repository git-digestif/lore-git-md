This is the second patch in a two-part CI/build system series enabling Rust compilation in Git’s GitHub Actions Windows CI jobs. It removes the `NO_RUST=UnfortunatelyYes` opt-out and installs the precompiled Rust `std` library for the GCC-compatible target triple matching the MSYS2 subsystem (`MSYSTEM`), ensuring Cargo can build a static library (`libgitcore.a`) compatible with MinGW’s `ld.exe`.

The patch adds a new step in `.github/workflows/main.yml` that runs `rustup target add` for the correct target triple (`x86_64-pc-windows-gnu` for UCRT64/MINGW64, `aarch64-pc-windows-gnullvm` for CLANGARM64, etc.), mirroring the logic already present in `config.mak.uname`. The step also adjusts the `PATH` to ensure `cargo.exe` is found in the minimal Git for Windows SDK environment. The `ci/lib.sh` hunk removes the `NO_RUST` opt-out, which was previously necessary because the CI environment lacked the precompiled `std` for the GCC-compatible target.

The patch is narrowly scoped to GitHub Actions and does not attempt to address GitLab’s Windows runners, where Rust availability remains unconfirmed. The author explicitly documents the mapping between `MSYSTEM` values and Rust target triples, making the logic self-documenting and future-proof for upcoming MSYS2 subsystem changes (e.g., UCRT64). The commit message clarifies that `rustup target add` is sufficient because Cargo does not invoke an external linker for a `staticlib` crate-type.

This patch directly unblocks the broader Rustification effort in Git by removing the CI opt-out that previously prevented Rust code from being compiled in Windows CI jobs. The changes are minimal, well-motivated, and unlikely to be controversial, assuming the GitLab runners behave as expected. The series as a whole looks ready to merge once the GitLab testing question is resolved.

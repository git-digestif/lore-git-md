Subject: [PATCH] coccinelle: remove risky "if (!E) free(E)" rule
Series version: standalone patch (now with follow-up discussion on compiler warnings and trade-offs)
Originating author: Junio C Hamano
Thread type: patch (CI/build system)

Core problem or goal
Remove a Coccinelle semantic patch rule (`tools/coccinelle/free.cocci`) that converted `if (!E) free(E);` into an unconditional `free(E)`, as it risked introducing bugs by freeing pointers that were conditionally guarded for a reason. The discussion has expanded to explore whether the guarded `free(E)` call should be removed entirely (René Scharfe’s preference) or left unconditional (Junio’s original approach), with the trade-off now explicitly framed around compiler warnings, side effects, and the project’s tolerance for build hygiene vs. correctness.

Current status
Under review. The original patch deleted 10 lines from `tools/coccinelle/free.cocci`, removing the risky rule for `free(E)` and `commit_list_free(E)`. A follow-up patch added 2 lines to explicitly allow unconditional `FREE_AND_NULL(E)` calls. No consensus yet on whether to adopt René’s alternative (removing the guarded `free(E)` call entirely) or retain the current approach. The discussion has shifted to whether compiler warnings for empty `if` blocks (a consequence of René’s approach) are an acceptable trade-off for safety, or whether the project should prioritize build hygiene. No other files or subsystems are touched.

Key technical details
- File touched: `tools/coccinelle/free.cocci`
- Symbols affected: `free(E)`, `commit_list_free(E)`, `FREE_AND_NULL(E)`
- Old behavior: Coccinelle rule generated patches to remove the `if (!E)` guard for `free(E)` and `commit_list_free(E)`; `FREE_AND_NULL(E)` was not explicitly allowed.
- New behavior: Risky rule is deleted; unconditional `free(E)`, `commit_list_free(E)`, and `FREE_AND_NULL(E)` are explicitly allowed. No automatic transformation occurs for guarded calls.
- Compiler behavior: GCC accepts `if (!E);` without warning, while Clang warns (though both accept `if (!E) {}`). This difference informs the trade-off between safety and build hygiene.
- Side-effect risk: Evaluating `E` in `if (!E)` may have unintended consequences if the guarded `free(E)` is removed entirely (e.g., `if (!get_pointer()) free(get_pointer());` would lose the side effect of the second call).
- On-disk format: N/A
- Test coverage: N/A (CI rule, not runtime code)

Open questions and loose ends
- Whether the original rule was ever useful in practice (i.e., caught real bugs). René Scharfe questions its value, suggesting alternatives like replacing guarded `free(E)` with `BUG()` or removing it entirely, and notes that runtime tools (e.g., LeakSanitizer) might be equally effective.
- Whether removing the rule might miss opportunities to clean up genuinely redundant free calls.
- Broader question of how aggressive Coccinelle rules should be in Git’s CI pipeline: whether they should enforce correctness (e.g., via `BUG()`) or merely suggest cleanups.
- Whether other custom free-like macros (e.g., in third-party code or future additions) should also be explicitly allowed.
- Whether the compiler warning risk for empty `if` blocks is real or hypothetical, and if real, whether it can be mitigated (e.g., with comments or pragmas) or should be accepted as a trade-off for safety.
- **New**: Whether the project should tolerate compiler warnings (e.g., from Clang) for the sake of correctness, or prioritize build hygiene by avoiding them. This hinges on the perceived risk of side effects from evaluating `E` in `if (!E)` and the practical impact of warnings on CI.

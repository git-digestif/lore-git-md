This thread is about Harald Nordgren’s patch series adding a `--matched-only` option to `git range-diff`, now at its third and final version. The feature filters range-diff output to show only commits present in both input ranges, addressing a common pain point when reviewing rebases: the default output buries meaningful changes under hundreds of unrelated commits, while `--matched-only` lets users focus on how surviving commits changed. The patch is technically complete, with no open objections, and has been queued in Junio’s `seen` branch, though it risks being dropped soon for lack of review.

The discussion has centered on whether the feature is truly necessary. Junio initially questioned its conceptual fit but later clarified that the existing three-revision syntax (`git range-diff <base>..<rev1> <base>..<rev2>`) cannot replace `--matched-only` in the rebasing scenario, where the two ranges share no common base. Ben Knoble’s recent reply suggests that if both topic branches are reachable from a common `origin`, the three-revision form could achieve similar filtering—but this doesn’t cover the case Harald described, where the topic is rebased onto an updated `origin/master`. The patch’s value thus depends on the specific workflow, and while its necessity is reaffirmed, it still needs a reviewer to validate its fit for `range-diff`.

The implementation is low-risk and additive, touching only the CLI and library layers to add the new option, enforce mutual exclusion with `--left-only` and `--right-only`, and filter output. Tests verify the behavior, and the man page is updated. The patch is ready for merging but remains in limbo pending review. If no one steps in soon, Junio will likely drop it from `seen`.

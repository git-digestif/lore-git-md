This thread is about adding a `--matched-only` option to `git range-diff`, allowing users to filter output to show only commits present in both input ranges. The feature addresses a common pain point when reviewing rebases or range-diffs: the default output can bury relevant changes under hundreds of unrelated commits, while `--matched-only` filters to show only the commits that survived, making the review more focused.

The patch series is now in its third and final version (v3), authored by Harald Nordgren. It’s a low-risk, additive change that reuses existing suppression logic by internally setting both `--left-only` and `--right-only` when `--matched-only` is specified. The implementation touches `builtin/range-diff.c`, `range-diff.c`, `range-diff.h`, the documentation, and adds test coverage in `t/t3206-range-diff.sh`. The only remaining architectural concern—an error-handling layering violation—was resolved in v3 by reverting to `error()` in the library layer and delegating `die()` to the CLI front-end.

The patch is technically complete and ready for merging, currently queued in Junio’s `seen` branch. However, it has stalled due to lack of review rather than any technical objections. Harald suggests the lack of feedback may stem from the patch’s simplicity, but Junio gently reminds that even simple patches require justification: the key question is whether enabling both `--left-only` and `--right-only` simultaneously is a meaningful and coherent user-facing behavior.

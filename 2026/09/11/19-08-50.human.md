This is the second patch in a two-part CI/build system series that enables Rust compilation in Git’s GitHub Actions Windows CI jobs. It removes the `NO_RUST=UnfortunatelyYes` opt-out and installs the precompiled Rust standard library for the GCC-compatible target triple matching the MSYS2 subsystem (`MSYSTEM`).

The patch adds a new step to the `windows-build` job in `.github/workflows/main.yml` that runs `rustup target add` for the correct target triple (`x86_64-pc-windows-gnu` for UCRT64 and MINGW64, `aarch64-pc-windows-gnullvm` for CLANGARM64, etc.). This ensures Cargo can build a static library (`libgitcore.a`) compatible with MinGW’s `ld.exe`. The step also adjusts the `PATH` to ensure `cargo.exe` is found in the minimal Git for Windows SDK environment. The mapping from `MSYSTEM` to target triple mirrors the logic already present in `config.mak.uname`, but is spelled out explicitly here for clarity and to document the expected behavior for future MSYS2 subsystems.

The commit message explains why this step is necessary: GitHub’s Windows runners ship a default Rust toolchain targeting the MSVC ABI, but Git for Windows uses MinGW, so the precompiled `std` for the GCC-compatible target must be installed separately. The message also clarifies that no additional toolchain components (e.g., the `gnullvm` linker) are needed because `cargo build` for a `staticlib` crate does not invoke an external linker.

This patch is well-motivated and practical, addressing a clear gap in the CI setup without introducing unnecessary complexity. The changes are minimal and focused, touching only the CI workflow and `ci/lib.sh`. The series as a whole looks ready to merge once the author’s request for testing on GitLab’s Windows runners is addressed, though that is not a blocker for this patch. The removal of the `NO_RUST` opt-out directly unblocks the broader Rustification effort in Git, making this a prerequisite for future Rust code contributions.

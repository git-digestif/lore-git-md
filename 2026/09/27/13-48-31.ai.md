This is a design proposal in the ongoing Git version numbering thread, specifically a follow-up to Harald Nordgren’s rejected suggestion to include user-facing breaking changes in Git 3.0. Phillip Wood responds to Junio’s firm rejection of Harald’s proposal by shifting the discussion from *whether* to change defaults to *how* Git might responsibly evolve them in the future. The email introduces two ideas: (1) adopting a consequentialist approach to default changes for cosmetic or low-impact settings (e.g., `diff.algorithm`, `merge.conflictStyle`), and (2) introducing a meta-config variable (`core.defaults`) that would allow users to opt into "modern defaults" without requiring disruptive breaking changes for everyone.

Phillip’s consequentialist framing is a direct challenge to the project’s current deontological stance, which treats any negative impact on even a small number of users as unacceptable. He argues that for settings where the downsides are limited (e.g., visual changes rather than data corruption), the net benefit of a default change could justify the disruption. This is a substantive reframing of the problem, though it leaves open the question of how to measure costs and benefits in practice. The proposal is not tied to Git 3.0 but is clearly motivated by the thread’s broader discussion about when and how to introduce breaking changes.

The `core.defaults` idea is more concrete: a single config variable that would override the defaults for a curated set of settings, effectively creating a "modern defaults" profile. Phillip suggests this could evolve over time and even be tuned for specific workflows (e.g., triangular workflows). This approach would allow the project to ship progressive defaults without forcing them on all users, addressing Junio’s concern about last-minute disruptive changes while still enabling gradual modernization. The proposal is well-scoped to cosmetic or workflow-related settings, avoiding the more contentious changes Harald proposed (e.g., autostash, `git status` behavior).

Phillip’s email is a thoughtful, substantive contribution that advances the thread beyond Junio’s rejection of Harald’s proposal. It introduces a new technical mechanism (`core.defaults`) and a philosophical shift (consequentialism) that could shape how Git handles default changes in the future. The ideas are still conceptual, with no code or implementation details, but they provide a clear path forward for revisiting this topic post-3.0. The proposal is likely to generate discussion, particularly around how to define "modern defaults" and whether a meta-config variable would add unnecessary complexity.

Key technical details introduced: the `core.defaults` config variable, the idea of workflow-specific default profiles, and the distinction between cosmetic and high-impact settings. The email does not reference specific subsystems or code changes, but it implies future work in the config system and documentation. The proposal is orthogonal to the version numbering discussion but directly addresses the underlying tension between stability and progress that has driven the thread.

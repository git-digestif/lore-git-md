This is the seventh iteration of a **feature patch series** adding seven new path-related keys to the `git repo info` command. The series is now **mechanically complete and correctness-bug-fixed**, addressing all prior review feedback. The author, a Google Summer of Code contributor, has split the previously monolithic second patch into two distinct commits: one to fix the `get_superproject_working_tree()` function (now respecting the `repo` parameter) and another to introduce the `path.superproject-root` keys. The `path.index` implementation no longer includes dead code, and the `path.cdup` key now correctly handles the edge case where the current working directory is outside the repository’s working tree by returning the absolute path to the working tree root.

The series touches `builtin/repo.c` (implementation), `Documentation/git-repo.adoc` (documentation), `t/t1900-repo-info.sh` (tests), and `submodule.c`/`submodule.h` (refactoring `get_superproject_working_tree()`). The new keys (`path.toplevel`, `path.superproject-root`, `path.hooks`, `path.index`, `path.grafts`, `path.git-prefix`, and `path.cdup`) expose filesystem locations of repository components in a scriptable format, supporting both absolute and relative paths via suffix-based formatting (e.g., `path.toplevel.absolute`). The implementation aligns with existing Git conventions, such as returning empty strings for inapplicable contexts (e.g., bare repositories or non-submodule setups) and respecting environment overrides like `GIT_INDEX_FILE`.

The most significant changes since v6 are the **split of the second patch** (as requested by Junio C Hamano) and the **fix for `path.cdup`** to handle the outside-working-tree scenario. The latter now checks `is_inside_work_tree(repo)` and falls back to `repo_get_work_tree(repo)` when outside the working tree, ensuring consistency with `git rev-parse --show-cdup`. Tests for this edge case have been added to `t/t1900-repo-info.sh`. The series is now **feature-complete**, with all design objections resolved and no known correctness issues remaining. The only unresolved question is whether the follow-up refactoring to deduplicate shared logic between `git repo info` and `git rev-parse` will proceed as a separate series, but this does not block merging.

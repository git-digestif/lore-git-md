This is a meta-discussion reply in the ongoing thread about version numbering and breaking changes for the next major Git release. Phillip Wood weighs in on Harald Nordgren’s proposal to change default configuration values, which Junio already ruled out for Git 3.0.

Phillip suggests rethinking the project’s traditional reluctance to change defaults, especially for UI-related settings like `diff.algorithm`, `diff.colorWords`, or `merge.conflictStyle`. He argues that Git’s current "deontological" approach—avoiding any negative impact on even a small number of users—is too rigid. Instead, he proposes a "consequentialist" framework: if the net benefit of a change outweighs the downsides, it should be allowed. This would give the project more flexibility to modernize defaults, though it would require a way to measure costs and benefits.

To make such changes less disruptive, Phillip floats the idea of a new `core.defaults` configuration variable. This would act like a "modern defaults" toggle, letting users opt into updated behavior (similar to `feature.experimental`). The concept could even be extended to tailor defaults for specific workflows—for example, a setting that implies `push.default=current` and `status.compareBranches=@{upstream} @{push}` for triangular workflows. If adopted, the modern defaults could be enabled by default, with users able to opt out by setting a single config variable.

The proposal is thoughtful and pragmatic, offering a middle ground between Harald’s call for immediate breaking changes and Junio’s firm rejection of them for 3.0. It doesn’t challenge the timeline for 3.0 but suggests a path for future changes without waiting for another major version. The idea of workflow-specific defaults is particularly interesting, though it would require careful design to avoid complexity. This reply adds a fresh perspective to the thread and could shape how Git approaches default changes in the long term.

This is the third and final patch in a well-crafted bugfix series targeting a regression in Git's reference-transaction hook. The regression, introduced in Git 2.31, causes the hook to receive all-zero object IDs when branches or tags are deleted via high-level commands like `git remote prune` or `git fetch --prune`, breaking external tools that rely on the hook to monitor ref changes.

This patch updates the pruning logic in `builtin/fetch.c` and `builtin/remote.c` to pass the resolved old OIDs (collected during the stale ref scan) into the deletion transaction. If a ref changes after the scan, the deletion is rejected, preserving the new value. The change avoids additional ref reads by reusing the OIDs already collected by `get_stale_heads()`. It also suppresses "[pruned]" output when a deletion fails, ensuring UI consistency. The patch includes thorough test coverage in `t/t1416-ref-transaction-hooks.sh`, verifying that the hook receives the correct old OIDs for batched deletions and that concurrent updates are properly rejected.

The series as a whole is a high-priority fix for a real-world regression affecting external tools like Gerrit and GitLab. The v3 iteration addresses all feedback from Junio and Karthik, resolving the core design conflict (all-or-nothing transactions vs. unconditional deletion) by adopting `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures while preserving backward compatibility. The patch is clean, well-motivated, and ready for merging. If you care about reference-transaction hooks or use tools that depend on them, this is worth reviewing.

This is a design discussion reply in the ongoing thread about improving `git fetch` behavior in shallow repositories. Harald Nordgren responds to Junio C Hamano’s proposal for a "matching-inspired" fetch mode by suggesting a refinement: the remote’s default branch should always be fetched, even if no local branch tracks it yet. This addresses a practical pain point—users often set the upstream of their current branch to the remote’s default branch (e.g., `main` or `master`), but in shallow repositories, this fails unless the remote’s `HEAD` is explicitly fetched first.

Harald’s suggestion is motivated by real-world workflow friction: he routinely runs `git branch --set-upstream-to=upstream` (where `upstream` is the remote name) to track the remote’s default branch, but this fails in shallow repositories unless `git remote set-head upstream --auto` is run first. His proposal would eliminate this extra step by ensuring the default branch is always included in the fetch, regardless of tracking relationships. The change is small but meaningful—it preserves the dynamic, tracking-based approach Junio proposed while smoothing a common edge case.

No code has been written for either the matching-inspired fetch mode or Harald’s refinement. The discussion remains conceptual, focusing on how to balance flexibility (fetching only what’s needed) with usability (avoiding manual workarounds). Harald’s input is practical and user-centric, but it also raises an implementation question: how should the remote’s default branch be determined without a network call? The thread has previously considered using the remote’s `HEAD` (which may be stale) or the local repository’s current branch as proxies, but neither is foolproof. This detail will need resolution before any patch can land.

The thread has already abandoned the original `fetch.shallow` config patch in favor of addressing the root cause—wildcard fetch refspecs in shallow repositories. Junio’s proposal and Harald’s refinement are now the leading contenders, but they are not mutually exclusive. The matching-inspired fetch mode could coexist with Phillip Wood’s narrower refspec idea for `git remote add`, though the thread has not yet clarified how they would interact or which would take precedence in shallow repositories. Harald’s suggestion does not directly engage with that question, focusing instead on improving the fetch mode’s usability.

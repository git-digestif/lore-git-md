This is the third and final patch in Maciej Ciemborowicz’s **v3 bugfix series** for the reference-transaction hook regression, now under final review by Junio C Hamano. The patch restores the pre-2.31 behavior for `git fetch --prune` and `git remote prune` by ensuring the hook receives the resolved old OIDs when pruning stale remote refs, while preserving the performance gains of the original optimization.

Junio’s review identifies a **user-visible reporting issue**: when pruning multiple refs, if one deletion fails, the current patch suppresses the "[deleted]" output for *all* refs, including the successful ones. This deviates from the existing behavior, where `git fetch --prune` and `git remote prune` report each deletion individually, even if some fail. The regression would make it harder for users to diagnose partial failures, as they would no longer see which refs were successfully pruned. The fix is straightforward—continue reporting deletions even after a failure—but it requires careful handling of the `refnames` list in the error path.

The patch is otherwise technically sound, addressing all prior feedback (including Junio’s earlier design concerns about all-or-nothing transactions and Karthik Nayak’s code cleanup suggestions). The series is now one small tweak away from being ready for merging. This is a **high-priority bugfix** for a regression affecting external tools like Gerrit and GitLab, and the remaining issue is purely about UI consistency, not correctness.

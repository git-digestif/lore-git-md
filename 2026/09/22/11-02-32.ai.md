This is a feature request proposing a mechanism for fast, low-disruption removal of personal information from Git history.

The email describes a common pain point: a public repository accidentally commits sensitive data (e.g., passwords, PII), and the cleanup process today is disruptive—typically requiring a full history rewrite (`git filter-repo`, `git filter-branch`, or BFG), which forces every developer to rebase, reconcile branches, and pause work. The author argues that Git should provide a built-in way to purge specific content from history *without* rewriting commit hashes, so that existing clones remain functional and development can continue uninterrupted.

The proposal is intentionally high-level: no implementation sketch, no reference to existing tools (`filter-repo`, `git replace`, `git notes`), and no discussion of trade-offs (e.g., whether the purged data could still be recovered from reflog or alternate object stores). It is framed as a user-experience wish rather than a technical design.

Key technical details that are *not* provided but would likely surface in follow-up discussion: how the purged data is identified (by path, by regex, by object ID), how the repository state is updated (whether objects are physically deleted or merely hidden), and how clients discover the purge (a new ref, a server-side hook, or a client-side fetch filter). The email also does not address whether the mechanism would be server-side only or require client support.

The tone is polite and enthusiastic but does not engage with the project’s norms (no Signed-off-by, no patch, no prior art research). This is clearly a first-time contributor expressing a need rather than a seasoned participant proposing a solution.

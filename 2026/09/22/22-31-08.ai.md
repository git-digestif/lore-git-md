This is the first patch in the v4 series fixing the reference-transaction hook regression. It modifies the `refs_delete_refs()` API to allow callers to supply old OIDs for batch deletion, enabling the hook to receive meaningful old OID values instead of all-zeros. The patch also enforces best-effort deletion by always using `REF_TRANSACTION_ALLOW_FAILURE` and adds granular error reporting via an optional `string_list` parameter for failed refs.

The core change is in `refs.c`, where `refs_delete_refs()` now accepts an optional `old_oids` array (parallel to the refname list) and a `failed_refs` output parameter. Each ref is deleted only if it still points to the expected OID, with null OIDs treated as unconditional deletions. The transaction now uses `REF_TRANSACTION_ALLOW_FAILURE` to ensure partial failures don’t block independent refs, and a rejection handler populates the `failed_refs` list. The patch also updates `ref_transaction_delete()` to handle null OIDs internally, simplifying the API.

Callers in `bisect.c`, `builtin/branch.c`, `builtin/fetch.c`, `builtin/remote.c`, and `builtin/tag.c` are updated to pass `NULL` for the new parameters, preserving their current behavior. The changes are mechanical and low-risk, touching only the refs subsystem. Test coverage is handled in subsequent patches, but the patch includes a new rejection handler and updates to the `refs.h` API documentation.

This patch directly addresses the core design conflict identified in earlier reviews by adopting `REF_TRANSACTION_ALLOW_FAILURE` and granular error reporting, while maintaining backward compatibility. The changes are well-motivated and align with the series’ goal of restoring pre-2.31 hook behavior without sacrificing performance. The patch is ready for review and likely to proceed to `next`.

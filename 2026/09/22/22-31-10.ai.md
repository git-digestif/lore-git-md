This is the **third and final patch in the v4 bugfix series** addressing the reference-transaction hook regression introduced in Git 2.31. The patch restores the pre-regression behavior for `git fetch --prune` and `git remote prune`, ensuring the hook receives the resolved old OID (instead of all-zeros) when remote refs are deleted, while preserving the performance gains of the original optimization and addressing all prior feedback.

The patch updates `prune_refs()` (used by `git fetch --prune`) and `prune_remote()` (used by `git remote prune`) to pass the old OIDs recorded by `get_stale_heads()` into the deletion transaction. If a ref changes after the stale scan (e.g., due to a concurrent update), the deletion is rejected for that ref, but non-atomic pruning continues for the remaining refs. The UI now reports successful deletions granularly ("[deleted]" or "[pruned]") while omitting failed refs from dangling symref checks, matching existing user expectations. Atomic fetches remain all-or-nothing, as before.

Key changes:
- **`builtin/fetch.c`**: `prune_refs()` now collects old OIDs from `stale_refs->new_oid` and passes them to `refs_delete_refs()`, which returns failed refs via a `string_list`. The UI skips reporting failed refs and excludes them from dangling symref checks.
- **`builtin/remote.c`**: `prune_remote()` similarly collects old OIDs and handles partial failures, with UI updates to match `git fetch --prune`.
- **Tests**: Adds three new tests to `t/t1416-ref-transaction-hooks.sh` covering:
  1. Hook payloads for pruned remote refs (files and reftable backends, SHA-1/SHA-256).
  2. UI behavior for `git remote prune` when a concurrent update rejects one ref but others succeed.
  3. UI behavior for `git fetch --prune` under the same conditions.

The patch is technically complete, with all feedback from Junio and Karthik addressed. It integrates cleanly with the earlier patches in the series, which already modified `refs_delete_refs()` to support partial failures and granular error reporting. The full test suite passes with `DEVELOPER=1`, and the rebase onto `master` (3bc0341127) is clean. This is a low-risk, high-priority fix for a regression affecting external tools (Gerrit, GitLab, CI systems) and is ready for merging to `next`.

This is a **user-experience bugfix** for shallow clones, part of Harald Nordgren’s ongoing effort to improve Git’s handling of shallow history boundaries. The thread is now focused on a fundamental design question raised by Junio C Hamano about the v2 patch’s approach to detecting and advising on silent truncation in `git log`.

The core issue is that the current implementation only advises when the *last commit shown* is a shallow boundary, but this misses cases where the traversal stops at a non-boundary commit (like a genuine root commit) while still hiding significant history behind a shallow boundary elsewhere. Junio illustrates this with a history where a side branch is truncated, but the last commit shown (`a`) is a genuine root, so no advice appears—even though the user is missing hundreds of commits behind `b`. This inconsistency makes the advice unreliable and potentially misleading.

Junio now regrets expanding the scope to cover silent truncation in `git log`, calling it a "can of worms" and suggesting that the feature may be counterproductive in its current form. He proposes abandoning the `git log` integration entirely, leaving the advice only for explicit `<rev>~N`/`<rev>^N` syntax failures (the v1 scope). He hints that a better solution might involve enriching `git log --graph` output, but that would be a separate effort.

The patch itself is well-crafted, with careful suppression logic, context-aware `--deepen` suggestions, and thorough test coverage. However, the design flaw Junio identifies is serious enough that it may require a rethink. If the advice only appears in some cases but not others—despite similar user confusion—it could do more harm than good. The thread is now at a crossroads: either refine the detection logic to cover all truncation cases (a non-trivial challenge) or revert to the narrower v1 scope. Either way, this is a substantive discussion about how Git should communicate shallow boundaries to users.

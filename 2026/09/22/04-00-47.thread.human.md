This thread is about a refactoring of how Git handles the `fetch.followRemoteHEAD` configuration setting. The goal is to stop Git from issuing warnings about this setting during configuration parsing when the setting isn’t even used in the current fetch operation. Colin Hinton’s latest patch (v3) defers validation for the global `fetch.followRemoteHEAD` setting until it’s actually needed, which fixes the spurious warnings for that case—but the remote-side parser (for `remote.<name>.followRemoteHEAD`) still triggers warnings prematurely, leaving the problem only partially solved.

Junio C Hamano, the maintainer, has confirmed that the lazy-validation pattern should eventually be applied to the remote-side parser as well, but Colin’s current patch keeps that work separate to avoid complicating the review. Colin plans to update the patch’s comments in v4 to make it clearer that the remote-side refactoring is still needed, moving the `NEEDSWORK` note to `remote.c` while leaving a brief explanation in `fetch.c`. Matt Hunter has already posted a follow-up patch that extends the lazy validation to the remote side, but it hasn’t been merged yet. The discussion remains constructive, with no major disagreements—just a shared understanding that the full fix will require two steps. For now, the patch is still under review, and the user-facing issue (unnecessary warnings) won’t be fully resolved until both parsers are updated.

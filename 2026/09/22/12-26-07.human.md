This is the first patch in a three-part bugfix series targeting a regression in Git's reference-transaction hook. The regression, introduced in Git 2.31, causes the hook to receive all-zero OIDs when branches or tags are deleted via high-level commands like `git branch -d` or `git tag -d`, breaking external tools that rely on the old OID (e.g., Gerrit, GitLab, CI systems). This patch modifies `refs_delete_refs()` to accept an optional array of old OIDs from callers, allowing deletions to be conditional on the ref still pointing to the expected OID. When old OIDs are provided, the function uses `REF_TRANSACTION_ALLOW_FAILURE` to preserve best-effort behavior—individual deletions can fail (e.g., due to concurrent updates) while others proceed, addressing the core design conflict raised in earlier reviews.

The change is well-motivated and technically sound. The commit message clearly explains the problem, the solution, and the trade-offs (e.g., preserving unconditional deletion for `git fetch --prune`). The implementation is clean: input validation ensures the `oid_array` size matches the refname count, and null OIDs are explicitly handled to avoid masking bugs. The patch touches core ref-handling code (`refs.c`, `refs.h`) and updates callers in `bisect.c`, `builtin/branch.c`, `builtin/fetch.c`, `builtin/remote.c`, and `builtin/tag.c` to pass `NULL` for now (later patches will supply the resolved OIDs). Test coverage is thorough, with regression tests added in patch 3.

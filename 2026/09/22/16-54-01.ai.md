This is a follow-up discussion in the thread about adding lifecycle hooks to Git worktrees, specifically advocating for a **pre-worktree-remove** hook.

The email argues that a pre-removal hook is essential for cases where external resources (e.g., Docker containers, databases, sockets, volumes) are tied to a worktree. Currently, post-removal hooks fire too late—after the worktree is deleted—leaving no reliable way to map external resources to their worktrees. The author describes a real-world scenario where AI-generated worktrees (created and discarded rapidly) led to orphaned resources consuming significant disk space, requiring manual cleanup scripts to reverse-engineer associations. A pre-removal hook would allow deterministic teardown while the worktree’s configuration is still accessible.

The email clarifies that the pre-removal hook is not intended to veto removal but to enable informed cleanup. It also acknowledges a limitation: the hook would only apply to `git worktree remove`, not manual deletion followed by `git worktree prune`, making post-removal hooks still necessary for those cases. The tone is pragmatic, focusing on a specific gap in the proposed lifecycle hooks rather than revisiting the broader design.

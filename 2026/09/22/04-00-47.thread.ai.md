Subject: [PATCH] fetch: defer validation of fetch.followRemoteHEAD until needed
Series version: v5 posted (single patch), follow-up direction aligned but not yet merged
Originating author: Colin Hinton
Thread type: patch (refactoring)

Core problem or goal
Refactor the handling of the `fetch.followRemoteHEAD` configuration setting to defer validation until the setting is actually used in `do_fetch()`. The current implementation issues warnings during config parsing even when the fetch operation never consults the setting, which is unnecessary and potentially confusing. The patch must address premature validation in both the local (`builtin/fetch.c`) and remote-side (`remote.c::handle_config()`) parsers, and unify parsing logic for `fetch.followRemoteHEAD` and `remote.<name>.followRemoteHEAD`.

Current status
Under review; v5 posted. Colin Hinton’s v5 defers validation in `builtin/fetch.c` by introducing a `char *follow_remote_head_raw` field and a `follow_remote_head_seen` flag in `struct fetch_config`, along with a helper function `get_follow_remote_head()` that parses the raw string into the appropriate enum value when called in `do_fetch()`. This eliminates spurious warnings for fetches that never consult the setting and preserves existing precedence rules (remote override vs. config fallback vs. default). The patch now uses `xstrdup_or_null(v)` to safely handle valueless truth settings (e.g., `fetch.followRemoteHEAD` with no value), treating both valueless and empty-string settings as errors that `die()` at lazy-validation time, replacing the historical warn-and-ignore behavior. Junio C Hamano’s review of v4 suggested using `xstrdup_or_null(v)` unconditionally in `git_fetch_config()` to preserve the distinction between a valueless setting and an explicitly empty string, and Colin’s v5 implements this by introducing the `follow_remote_head_seen` flag to track whether the setting was encountered during config parsing, regardless of its value. Junio’s latest reply endorses tightening the rules to `die()` for both cases, calling the historical warn-and-ignore behavior a "weak excuse" for premature validation. Matt Hunter’s substantive review of v5 confirms the `follow_remote_head_seen` flag correctly distinguishes between valueless, empty-string, and normal values, allowing the lazy-validation helper to handle all cases safely. Junio’s final review of v5 identifies two minor issues: the commit message’s phrasing about `NEEDSWORK` comments is misleading (there is only one such comment, relocated to `remote.c`), and the patch introduces a memory leak in `follow_remote_head_raw` (allocated via `xstrdup_or_null()` but never freed). Junio calls the patch “very good” and implies it is otherwise ready for integration, pending these fixes. The remote-side parser in `remote.c` remains unchanged in v5, but the `NEEDSWORK` comment has been relocated from `fetch.c` to `remote.c` near the remaining defect in `handle_config()`, with a brief explanatory note added in `fetch.c` for context. Junio’s feedback confirms that the lazy-validation pattern should eventually be applied to the remote-side parser for consistency, making the current patch only a partial fix. The user-facing problem (spurious warnings from unused config settings) is resolved for the local parser in v5, but remains unresolved for the remote-side parser until follow-up work is completed.

Key technical details
- Files touched: `builtin/fetch.c` (v5), `remote.c` (`NEEDSWORK` comment relocated in v5)
- New symbols: `follow_remote_head_raw` (field in `struct fetch_config`), `follow_remote_head_seen` (field in `struct fetch_config`), `get_follow_remote_head()` (helper function in `builtin/fetch.c`), `xstrdup_or_null()` (used for safe NULL handling)
- Old behavior: config validation and warnings during parsing in `git_fetch_config()` (local) and `remote.c::handle_config()` (remote); segfault on valueless truth settings; warn-and-ignore for invalid values
- New behavior: validation deferred until `do_fetch()` consults the setting; both valueless and empty-string settings now `die()` with a complaint about not being a boolean (Junio’s preference), replacing the historical warn-and-ignore behavior. The `follow_remote_head_seen` flag tracks whether the setting was encountered during config parsing, regardless of its value, allowing the lazy-validation helper to enforce the tightened rules. Remote-side config parsing remains unchanged in v5; `NEEDSWORK` comment relocated to `remote.c` to signal remaining work. Junio’s review of v4 suggested using `xstrdup_or_null(v)` unconditionally in `git_fetch_config()` to preserve the distinction between a valueless setting and an explicitly empty string, and v5 implements this. Matt Hunter’s review confirms the `follow_remote_head_seen` flag is correctly initialized to `0` in the `fetch_config` struct and that the `NULL` case in `get_follow_remote_head()` is now meaningful (previously unreachable). The empty-string case is handled naturally by the existing string-comparison logic. The warning message in `get_follow_remote_head()` still refers to `fetch.followRemoteHEAD` even when parsing `remote.<name>.followRemoteHEAD` (follow-up concern). Junio’s final review identifies a memory leak in `follow_remote_head_raw` (allocated via `xstrdup_or_null()` but never freed when `cmd_fetch()` exits). The leak is technical, not functional, but must be fixed before merging.
- No on-disk format changes; no test coverage changes
- Control flow: `do_fetch()` -> `get_follow_remote_head()` -> parse `follow_remote_head_raw` (local only in v5); `xstrdup_or_null(v)` ensures safe handling of NULL inputs
- Edge cases: valueless and empty-string settings now handled uniformly (both `die()`), with the `follow_remote_head_seen` flag ensuring the setting was encountered during config parsing; unrecognized values like `"f@KeValue"` still warn (not `die()`), preserving v4 behavior but diverging from Junio’s preference for `die()` in all error cases

Open questions and loose ends
- Whether to escalate warnings to `die()` for all invalid values (unrecognized strings like `"f@KeValue"`), aligning with Junio’s preference for tightening the rules. The current v5 implementation preserves the v4 behavior of warning (not dying) on unrecognized values, while dying on `NULL` or empty strings. Matt Hunter’s review flags this as a point where opinions might differ but does not push for a change.
- Whether to merge the remote-side parser refactoring into Colin’s next patch or handle it as a follow-up. Junio’s feedback confirms that the lazy-validation pattern should eventually be applied to the remote-side parser for consistency, making the current patch only a partial fix. Colin and Matt agree the only substantive difference between local and remote parsers is the `warn-if-not-$branch` setting, which is remote-specific and not supported for `fetch.followRemoteHEAD`, suggesting the remote-side unification can proceed as a follow-up without complicating the current patch.
- Memory management for `follow_remote_head_raw`: Junio’s final review identifies a leak (allocated via `xstrdup_or_null()` but never freed when `cmd_fetch()` exits). This must be fixed before merging.
- Awkward points in Matt’s follow-up: warning message in `get_follow_remote_head()` still refers to `fetch.followRemoteHEAD` even when parsing `remote.<name>.followRemoteHEAD`, and the enum definition might belong in `fetch.c` rather than `remote.h`. Matt’s review also suggests adding a `NEEDSWORK` label to the explanatory comment in `fetch.c` for consistency with the relocated comment in `remote.c`.
- Performance optimization: should Git skip the `ls-refs` query when `FOLLOW_REMOTE_CREATE` is set and the local repository already has a symref for the remote’s HEAD? This is a separate feature request that would complicate control flow and is not tied to the current refactoring goal.

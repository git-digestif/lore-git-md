Thread identity
Subject: [PATCH] fetch: defer validation of fetch.followRemoteHEAD until needed
Series version: v6 (single patch), now signed off and ready for integration into `next`
Originating author: Colin Hinton
Thread type: patch (refactoring)

Core problem or goal
Refactor the handling of the `fetch.followRemoteHEAD` configuration setting to defer validation until the setting is actually used in `do_fetch()`. The current implementation issues warnings during config parsing even when the fetch operation never consults the setting, which is unnecessary and potentially confusing. The patch addresses premature validation in the local parser (`builtin/fetch.c`) while leaving the remote-side parser (`remote.c::handle_config()`) for a follow-up, and unifies parsing logic for `fetch.followRemoteHEAD` and `remote.<name>.followRemoteHEAD`.

Current status
**Signed off by Junio C Hamano and queued for `next`**. Colin Hinton’s v6 addresses all feedback from Junio’s review of v5: it fixes the memory leak in `follow_remote_head_raw` (now freed in `cmd_fetch()`’s cleanup block), clarifies the commit message to accurately reflect that only one `NEEDSWORK` comment was relocated (to `remote.c`), and tightens validation rules to `die()` for both valueless and empty-string settings at lazy-validation time. Junio’s final review calls the patch “good enough” and implies no further changes are needed before integration. The patch defers validation in `builtin/fetch.c` by introducing a `char *follow_remote_head_raw` field and a `follow_remote_head_seen` flag in `struct fetch_config`, along with a helper function `get_follow_remote_head()` that parses the raw string into the appropriate enum value when called in `do_fetch()`. This eliminates spurious warnings for fetches that never consult the setting and preserves existing precedence rules (remote override vs. config fallback vs. default). The remote-side parser remains unchanged, but the relocated `NEEDSWORK` comment in `remote.c` signals the remaining work for consistency. The patch uses `xstrdup_or_null(v)` to safely handle valueless truth settings (e.g., `fetch.followRemoteHEAD` with no value), treating both valueless and empty-string settings as errors that `die()` at lazy-validation time, replacing the historical warn-and-ignore behavior. Unrecognized values (e.g., `"f@KeValue"`) still warn but do not `die()`, preserving the v5 behavior despite Junio’s preference for escalating all errors to `die()`.

Key technical details
- Files touched: `builtin/fetch.c` (v6), `remote.c` (`NEEDSWORK` comment relocated in v6)
- New symbols: `follow_remote_head_raw` (field in `struct fetch_config`), `follow_remote_head_seen` (field in `struct fetch_config`), `get_follow_remote_head()` (helper function in `builtin/fetch.c`), `xstrdup_or_null()` (used for safe NULL handling)
- Old behavior: config validation and warnings during parsing in `git_fetch_config()` (local) and `remote.c::handle_config()` (remote); segfault on valueless truth settings; warn-and-ignore for invalid values
- New behavior: validation deferred until `do_fetch()` consults the setting; both valueless and empty-string settings now `die()` with a complaint about not being a boolean, replacing the historical warn-and-ignore behavior. The `follow_remote_head_seen` flag tracks whether the setting was encountered during config parsing, regardless of its value, allowing the lazy-validation helper to enforce the tightened rules. Remote-side config parsing remains unchanged; the relocated `NEEDSWORK` comment in `remote.c` signals the remaining work. Junio’s review confirms the loss of source-line information in error messages (a side effect of lazy validation) is not a significant usability regression. The warning message in `get_follow_remote_head()` still refers to `fetch.followRemoteHEAD` even when parsing `remote.<name>.followRemoteHEAD` (follow-up concern noted by Matt Hunter).
- No on-disk format changes; no test coverage changes
- Control flow: `do_fetch()` -> `get_follow_remote_head()` -> parse `follow_remote_head_raw` (local only in v6); `xstrdup_or_null(v)` ensures safe handling of NULL inputs
- Edge cases: valueless and empty-string settings now handled uniformly (both `die()`), with the `follow_remote_head_seen` flag ensuring the setting was encountered during config parsing; unrecognized values like `"f@KeValue"` still warn (not `die()`), preserving v5 behavior

Open questions and loose ends
- Whether to escalate warnings to `die()` for all invalid values (including unrecognized strings like `"f@KeValue"`), aligning with Junio’s preference. The current implementation preserves the v5 behavior of warning on unrecognized values, while dying on `NULL` or empty strings. This divergence from Junio’s stated preference remains unresolved but is not blocking integration.
- Follow-up work: apply the lazy-validation pattern to the remote-side parser (`remote.c::handle_config()`) for consistency. Junio’s feedback confirms this should be handled as a separate patch, noting the only substantive difference between local and remote parsers is the `warn-if-not-$branch` setting, which is remote-specific and not supported for `fetch.followRemoteHEAD`.
- Awkward points noted by Matt Hunter: the warning message in `get_follow_remote_head()` still refers to `fetch.followRemoteHEAD` even when parsing `remote.<name>.followRemoteHEAD`, and the enum definition might belong in `fetch.c` rather than `remote.h`. Matt also suggests adding a `NEEDSWORK` label to the explanatory comment in `fetch.c` for consistency with the relocated comment in `remote.c`.
- Performance optimization: whether to skip the `ls-refs` query when `FOLLOW_REMOTE_CREATE` is set and the local repository already has a symref for the remote’s HEAD. This is a separate feature request not tied to the current refactoring goal.

Thread identity
Subject: [PATCH] fetch: defer validation of fetch.followRemoteHEAD until needed
Series version: single patch (no series), now with proposed follow-up patch
Originating author: Colin Hinton
Thread type: patch (refactoring)

Core problem or goal
Refactor the handling of the `fetch.followRemoteHEAD` configuration setting in `builtin/fetch.c`, `remote.c`, and `builtin/remote.c` to defer validation until the setting is actually used in `do_fetch()`. Currently, the config parser issues warnings for unrecognized values even when the fetch operation never consults the setting, which is unnecessary and potentially confusing. The patch must address premature validation in both the local (`builtin/fetch.c`) and remote-side (`remote.c::handle_config()`) parsers, and unify parsing logic for `fetch.followRemoteHEAD` and `remote.<name>.followRemoteHEAD`.

Current status
Under review; no prior versions. Colin Hinton’s v1 introduced a new `char *follow_remote_head_raw` field in `builtin/fetch.c` and a helper function `get_follow_remote_head()` to parse it lazily in `do_fetch()`. Junio C Hamano’s review identified two gaps: (1) the patch still fails during config parsing for valueless truth settings (e.g., `fetch.followRemoteHEAD` with no value), and (2) the remote-side parser in `remote.c` shares the same problem and must be refactored in tandem. Colin agreed with Junio’s feedback and plans to revise the patch. Matt Hunter has now posted a concrete follow-up patch that extends lazy validation to the remote-side parser, introduces a new `struct follow_remote_head_target` to unify parsing logic, and replaces the `follow_remote_head` enum field in `struct remote` with a `char *follow_remote_head_raw` field. The follow-up patch does not address the valueless-truth-setting edge case; that remains an open item for Colin’s next revision. Junio’s suggested simplification (initializing `follow_remote_head` to `FOLLOW_REMOTE_NEVER` and testing it directly) has not been adopted in the follow-up patch.

Key technical details
- Files touched: `builtin/fetch.c`, `remote.c`, `builtin/remote.c`, `remote.h`
- New symbols: `follow_remote_head_raw` (field in `struct remote`), `struct follow_remote_head_target` (unifies parsing logic), updated `get_follow_remote_head()` (handles both config sources and returns parsed enum value *and* `no_warn_branch` string)
- Old behavior: config validation and warnings during parsing in `builtin/fetch.c`, `remote.c::handle_config()`, and `builtin/remote.c::set_head()`
- New behavior: validation deferred until `do_fetch()` consults the setting; remote-side config parsing in `handle_config()` and `set_head()` is similarly deferred
- No on-disk format changes; no test coverage changes
- Control flow: `do_fetch()` -> `get_follow_remote_head()` -> parse `follow_remote_head_raw` (local or remote); remote-side parsing in `handle_config()` and `set_head()` now stores raw string and defers validation
- Edge cases: valueless truth settings (still not addressed; `die(...)` must be deferred to lazy-validation point), multiple config definitions (existing code handles this; patch preserves), warning message in `get_follow_remote_head()` still refers to `fetch.followRemoteHEAD` even when parsing `remote.<name>.followRemoteHEAD`, enum definition might belong in `fetch.c` rather than `remote.h`
- Additional considerations: default value for unrecognized config values (`FOLLOW_REMOTE_NEVER` vs. `FOLLOW_REMOTE_UNCONFIGURED`), potential optimization to skip `ls-refs` queries when local symref already exists, special case in `set_head()` where a remote’s `always` setting is overridden if the user manually modified HEAD

Open questions and loose ends
- Whether to include the remote-side parser refactoring in Colin’s next patch or defer it to a follow-up. Matt’s patch now provides a concrete implementation, but Colin has not yet indicated whether he will adopt it.
- Memory management for `follow_remote_head_raw` if multiple config definitions are encountered during lazy validation (both local and remote).
- Default behavior for unrecognized `fetch.followRemoteHEAD` values: should they default to `FOLLOW_REMOTE_NEVER` (Matt Hunter’s preference) or `FOLLOW_REMOTE_UNCONFIGURED` (current behavior)? This is a behavioral change that could affect both local and remote-side parsers.
- Performance optimization: should Git skip the `ls-refs` query when `FOLLOW_REMOTE_CREATE` is set and the local repository already has a symref for the remote’s HEAD? This is a separate feature request that would complicate control flow.
- Valueless truth settings: the `die(...)` call for valueless settings (e.g., `fetch.followRemoteHEAD` with no value) must be deferred to the lazy-validation point. This is not addressed in Matt’s follow-up patch and remains an open item for Colin’s next revision.
- Awkward points in Matt’s patch: warning message in `get_follow_remote_head()` still refers to `fetch.followRemoteHEAD` even when parsing `remote.<name>.followRemoteHEAD`, and the enum definition might now belong in `fetch.c` rather than `remote.h`.

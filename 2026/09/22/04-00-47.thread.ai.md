Thread identity
Subject: [PATCH] fetch: defer validation of fetch.followRemoteHEAD until needed
Series version: single patch (no series)
Originating author: Colin Hinton
Thread type: patch (refactoring)

Core problem or goal
Refactor the handling of the `fetch.followRemoteHEAD` configuration setting in `builtin/fetch.c` to defer validation until the setting is actually used in `do_fetch()`. Currently, the config parser issues warnings for unrecognized values even when the fetch operation never consults the setting, which is unnecessary and potentially confusing. The patch must also address the same premature-validation issue in the remote-side config parser (`remote.c::handle_config()`) to fully achieve lazy validation.

Current status
Under review; no prior versions. Patch introduces a new `char *follow_remote_head_raw` field in `builtin/fetch.c` to store the raw config string and a helper function `get_follow_remote_head()` to parse it lazily in `do_fetch()`. Junio C Hamano’s review identifies two gaps: (1) the patch still fails during config parsing for valueless truth settings (e.g., `fetch.followRemoteHEAD` with no value), and (2) the remote-side parser in `remote.c` shares the same problem and must be refactored in tandem. Junio suggests simplifying the logic by initializing `follow_remote_head` to `FOLLOW_REMOTE_NEVER` and testing it directly, eliminating the redundant `do_set_head` state.

Key technical details
- Files touched: `builtin/fetch.c`, `remote.c`
- New symbols: `follow_remote_head_raw` (field), `get_follow_remote_head()` (function)
- Old behavior: config validation and warnings during parsing in both `builtin/fetch.c` and `remote.c`
- New behavior: validation deferred until `do_fetch()` consults the setting; remote-side config parsing must also be deferred
- No on-disk format changes; no test coverage changes
- Control flow: `do_fetch()` -> `get_follow_remote_head()` -> parse `follow_remote_head_raw`; remote-side parsing in `handle_config()` must be similarly deferred
- Edge cases: valueless truth settings, multiple config definitions (existing code handles this; patch must preserve)

Open questions and loose ends
- How to handle valueless truth settings (`fetch.followRemoteHEAD` with no value) during lazy validation.
- Whether to retain the `do_set_head` state or simplify by initializing `follow_remote_head` to `FOLLOW_REMOTE_NEVER` and testing directly.
- Potential memory leak if multiple config definitions are not handled correctly in the lazy-validation path.

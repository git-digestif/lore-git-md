Thread identity
Subject: [PATCH] fetch: defer validation of fetch.followRemoteHEAD until needed
Series version: v4 (single patch), follow-up direction aligned but not yet merged
Originating author: Colin Hinton
Thread type: patch (refactoring)

Core problem or goal
Refactor the handling of the `fetch.followRemoteHEAD` configuration setting to defer validation until the setting is actually used in `do_fetch()`. The current implementation issues warnings during config parsing even when the fetch operation never consults the setting, which is unnecessary and potentially confusing. The patch must address premature validation in both the local (`builtin/fetch.c`) and remote-side (`remote.c::handle_config()`) parsers, and unify parsing logic for `fetch.followRemoteHEAD` and `remote.<name>.followRemoteHEAD`.

Current status
Under review; v4 posted. Colin Hinton’s v4 defers validation in `builtin/fetch.c` by introducing a `char *follow_remote_head_raw` field and a helper function `get_follow_remote_head()` that parses the raw string into the appropriate enum value when called in `do_fetch()`. This eliminates spurious warnings for fetches that never consult the setting and preserves existing precedence rules (remote override vs. config fallback vs. default). The patch now uses `xstrdup_or_null(v)` to safely handle valueless truth settings (e.g., `fetch.followRemoteHEAD` with no value), treating them as `FOLLOW_REMOTE_NEVER` with a warning at lazy-validation time. The remote-side parser in `remote.c` remains unchanged in v4, but the `NEEDSWORK` comment has been relocated from `fetch.c` to `remote.c` near the remaining defect in `handle_config()`, with a brief explanatory note added in `fetch.c` for context. Junio C Hamano’s feedback confirms that the lazy-validation pattern should eventually be applied to the remote-side parser for consistency, making the current patch only a partial fix. The user-facing problem (spurious warnings from unused config settings) remains unresolved until both parsers are refactored.

Key technical details
- Files touched: `builtin/fetch.c` (v4), `remote.c` (follow-up, not yet included), `remote.h` (follow-up, not yet included)
- New symbols: `follow_remote_head_raw` (field in `struct fetch_config`), `get_follow_remote_head()` (helper function in `builtin/fetch.c`), `xstrdup_or_null()` (used for safe NULL handling)
- Old behavior: config validation and warnings during parsing in `git_fetch_config()` (local) and `remote.c::handle_config()` (remote); segfault on valueless truth settings
- New behavior: validation deferred until `do_fetch()` consults the setting; valueless truth settings treated as `FOLLOW_REMOTE_NEVER` with a warning at lazy-validation time; remote-side config parsing remains unchanged in v4; `NEEDSWORK` comment relocated to `remote.c` to signal remaining work
- No on-disk format changes; no test coverage changes
- Control flow: `do_fetch()` -> `get_follow_remote_head()` -> parse `follow_remote_head_raw` (local only in v4); `xstrdup_or_null(v)` ensures safe handling of NULL inputs
- Edge cases: valueless truth settings now handled safely (no segfault), but warning message in `get_follow_remote_head()` still refers to `fetch.followRemoteHEAD` even when parsing `remote.<name>.followRemoteHEAD` (follow-up concern)
- Additional considerations: default value for unrecognized config values (Colin aligns with Matt’s preference for `FOLLOW_REMOTE_NEVER` with a warning), potential optimization to skip `ls-refs` queries when local symref exists (separate feature request)

Open questions and loose ends
- Whether to merge the remote-side parser refactoring into Colin’s next patch or handle it as a follow-up. Junio’s feedback confirms that the lazy-validation pattern should eventually be applied to the remote-side parser for consistency, making the current patch only a partial fix. Colin and Matt agree the only substantive difference between local and remote parsers is the `warn-if-not-$branch` setting, which is remote-specific and not supported for `fetch.followRemoteHEAD`, suggesting the remote-side unification can proceed as a follow-up without complicating the current patch.
- Memory management for `follow_remote_head_raw` if multiple config definitions are encountered during lazy validation (both local and remote).
- Awkward points in Matt’s follow-up: warning message in `get_follow_remote_head()` still refers to `fetch.followRemoteHEAD` even when parsing `remote.<name>.followRemoteHEAD`, and the enum definition might belong in `fetch.c` rather than `remote.h`.
- Performance optimization: should Git skip the `ls-refs` query when `FOLLOW_REMOTE_CREATE` is set and the local repository already has a symref for the remote’s HEAD? This is a separate feature request that would complicate control flow and is not tied to the current refactoring goal.

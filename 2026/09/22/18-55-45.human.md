This is the first patch in a **v3 bugfix series** addressing a regression in the reference-transaction hook, where deleting branches or tags via high-level commands (e.g., `git branch -d`, `git tag -d`) now passes all-zero OIDs to the hook instead of the resolved old OID. The regression, introduced in Git 2.31, breaks external tools like Gerrit and GitLab that rely on the hook to monitor ref changes.

Junio’s review of this patch is **substantive** and focuses on two key areas: (1) whether `REF_TRANSACTION_ALLOW_FAILURE` should always be used in `refs_delete_refs()`, and (2) the handling of rejection data and null OIDs. He suggests that `REF_TRANSACTION_ALLOW_FAILURE` should be the default for `refs_delete_refs()`, as the function’s documented behavior is "best-effort" deletion, and the flag was introduced precisely to support this use case. This would simplify the logic and avoid the conditional flag passing in the current patch.

On the rejection handler, Junio notes that the current implementation treats `rejection_data.failures` as a boolean (0 or 1) rather than a counter, which is misleading. He proposes either renaming it to `failed` (if it remains a boolean) or actually counting failures (if the caller expects to know how many deletions failed). He also questions the need to treat null OIDs specially in the caller, suggesting that `ref_transaction_delete()` should handle null OIDs internally instead of forcing callers to do so.

The patch itself is well-motivated and technically sound, but Junio’s feedback highlights opportunities to simplify the design and improve clarity. The discussion is constructive and focuses on aligning the implementation with the intended behavior of the refs API. This patch is a critical piece of the series, as it introduces the mechanism for passing old OIDs to the hook, and the feedback is likely to result in a minor revision before merging. The series as a whole remains a high-priority bugfix for a regression affecting real-world workflows.

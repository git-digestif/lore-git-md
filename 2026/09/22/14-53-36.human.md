This is a design-discussion follow-up in the ongoing `fetch.shallow` thread. The conversation has now firmly settled on an alternative solution: modifying `git remote add` to avoid wildcard fetch refspecs in shallow repositories, rather than introducing the originally proposed `fetch.shallow` configuration option.

Phillip Wood and Harald Nordgren agree that the root cause of the performance issue lies in `git remote add` defaulting to a wildcard refspec (`+refs/heads/*:refs/remotes/<name>/*`) even in shallow repositories. This causes refspec-less fetches to negotiate history for all remote branches, leading to slow or hanging operations. The proposed fix is to change `git remote add` so that, in shallow repositories, it defaults to a narrower refspec (e.g., `+refs/heads/<default-branch>:refs/remotes/<name>/<default-branch>`), restricting fetches to the current branch’s upstream by default.

The discussion is now focused on implementation details for this alternative approach, with no objections raised to the pivot away from `fetch.shallow`. The original patch remains unmodified and unmerged, and no new code has been written yet. This looks like a well-motivated and uncontroversial design shift, targeting a real usability pain point for shallow repository users. The next step will likely be a patch implementing the `git remote add` behavior change.

This is the first patch in a three-patch **bugfix series** targeting a regression in the reference-transaction hook. The regression, introduced in Git 2.31, causes the hook to receive all-zero OIDs when branches or tags are deleted, breaking external tools like Gerrit and GitLab that rely on the old OID to track ref changes.

This patch modifies `refs_delete_refs()` to accept an optional array of old OIDs, allowing callers to preserve the resolved values for the hook. It also switches the function to always use `REF_TRANSACTION_ALLOW_FAILURE`, enabling granular error reporting for partial failures—one rejected ref no longer blocks the entire batch. The patch introduces a new `string_list` parameter to return failed refs, which callers can use to report partial results. The change is backward-compatible: existing callers pass `NULL` for the new parameters, preserving the current behavior.

The patch touches eight files, primarily updating callers (`git branch`, `git tag`, `git fetch`, `git remote`) to pass `NULL` for the new parameters. The core logic in `refs.c` is expanded to handle the old OID array, treat null OIDs as unconditional deletions, and report rejected updates via a callback. The API change is well-documented in `refs.h`, and the commit message clearly explains the motivation and design choices.

This is a **high-quality bugfix** with a clear regression target, thorough test coverage (added in later patches), and careful attention to backward compatibility. The use of `REF_TRANSACTION_ALLOW_FAILURE` resolves the core design conflict noted in earlier reviews, and the granular error reporting addresses Junio’s concern about user-facing consistency. The patch is ready for merging and is a strong candidate for `next`.

This thread is Junio’s "What’s cooking" report for September 2026, summarizing the state of in-flight patches as Git 2.56-rc1 was tagged, followed by a community discussion about the Git 3.0 release timeline, scope, and outcomes from the recent Contributor’s Summit. The key participants are Junio (maintainer), Johannes Schindelin (Git for Windows), Daniele Sassoli (JGit), Toon Claes (GitLab), and D. Ben Knoble, among others.

The core focus is aligning the project on Git 3.0’s timeline and breaking changes. Junio has proposed a provisional three-phase plan: Git 2.98 (December 2026) as the final 2.x feature release, Git 2.99 (March 2027) as a transitional release with breaking changes disabled via a `WITH_BREAKING_CHANGES` Makefile knob, and Git 3.0 (April 2027) enabling those changes. The month-long gap between 2.99 and 3.0 is meant to give downstream projects time to prepare, not for new development. Git 2.99.1 (April 2027) will be a bugfix-only release identical to 3.0 but with breaking changes disabled, minimizing maintenance overhead. Volunteers may maintain 2.99.x for LTS distributions, but there’s no formal commitment.

The summit also addressed ecosystem readiness for Git 3.0’s goals. JGit’s pluggable backend infrastructure is confirmed as technically viable (dating back 16 years), but production adoption has been limited. SHA-256 interoperability is feasible in JGit but lacks active development due to resource constraints, not technical barriers. Rust support remains a goal for Git 3.0 but isn’t guaranteed due to portability concerns (e.g., the NonStop platform). Security process improvements—like documenting Git’s security model and increasing GitLab’s triage staffing—are now actionable, though under-resourced. Documentation efforts are split between incremental updates (e.g., man pages) and complete rewrites (e.g., tutorials), with Julia Evans’ Sovereign Tech Fund grant providing some continuity.

Open questions include the final scope of breaking changes (e.g., Rust, SHA-256), downstream coordination (e.g., Gentoo’s LTS needs), and unresolved technical tradeoffs (e.g., pluggable ODBs, push protocol v2). Junio’s latest email clarifies the timeline and technical strategy but doesn’t resolve these uncertainties. The next steps will likely involve community feedback on the proposal, with refinements expected in Junio’s next "What’s cooking" report. For now, the plan is flexible, and the focus is on pragmatic coordination rather than rigid commitments.

This thread is Junio’s September 2026 “What’s cooking” report, summarizing the state of all in-flight topics as Git 2.56-rc1 has been tagged and the community begins planning for Git 3.0. The discussion has since focused on three main areas: the provisional timeline for Git 3.0, the readiness of downstream projects (especially JGit), and operational improvements to security processes and documentation.

Junio initially proposed a three-phase timeline—Git 2.98 in December 2026, Git 2.99 (with breaking changes disabled) in March 2027, and Git 3.0 (identical code but with breaking changes enabled) in April 2027. He has since clarified that the April 2027 target is tentative; the stabilization period for Git 2.99 may require additional maintenance releases (e.g., 2.99.2 or 2.99.3) before Git 3.0 is finalized. The technical strategy remains unchanged: a `WITH_BREAKING_CHANGES` Makefile knob will minimize divergence between 2.99.x and 3.0, and Rust support is a goal but not guaranteed due to portability concerns (e.g., NonStop, Cygwin). Johannes Schindelin confirmed that the timeline provides sufficient clarity for Git for Windows’ roadmap, which now includes Rust-based builds and Git Credential Manager v3.0 integration.

The biggest update concerns JGit’s readiness. Earlier in the thread, Schindelin had framed JGit as a “gap” for SHA-256 interoperability, but Daniele Sassoli and Luca Milanesio have since provided concrete evidence that JGit’s pluggable backend infrastructure is production-ready. Milanesio’s email cites Google’s internal Git servers (using a proprietary JGit backend for over a decade) and GerritForge’s open-source global refdb backend as proof of the architecture’s maturity and scalability. This shifts the narrative: JGit is technically capable of supporting Git 3.0’s ODB goals, but resource constraints—not technical barriers—are the primary obstacle for SHA-256 support. A forthcoming talk at the Gerrit User Summit (October 24–25, 2026) may provide further clarity on JGit’s SHA-256 plans.

On the operational side, Toon Claes has committed to documenting Git’s security model and reviving stalled discussions about the security boundary, while GitLab will increase staffing for report triage. Schindelin has endorsed Toon’s proposal to collaborate on the next security release, signaling tangible progress toward addressing long-standing bottlenecks. Documentation improvements are also in focus: a two-pronged strategy (incremental updates for reference material, complete rewrites for tutorials) is now explicit, though resourcing remains unclear. The `git-scm.com` website, including its “UI list,” is acknowledged as a critical but under-maintained resource.

Open questions include the final scope of Git 3.0’s breaking changes, the fate of stalled topics (e.g., `mm/diff-process-hunks`, `tb/midx-incremental-custom-base`), and whether Rust support will make it into the release. Downstream coordination remains a work in progress, with D. Ben Knoble volunteering to engage Gentoo maintainers about a potential Git 2.x LTS branch. The thread is now in a holding pattern, awaiting Junio’s next “What’s cooking” report and further feedback from the community.

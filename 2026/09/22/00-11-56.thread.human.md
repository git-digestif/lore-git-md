This thread is Junio’s "What’s cooking in git.git" report for September 2026, summarizing the state of in-flight patches as Git 2.56-rc1 was tagged, but it’s mostly about planning for Git 3.0. The key participants are Junio (maintainer), Johannes Schindelin (Git for Windows), and a handful of others like Toon Claes (GitLab) and Daniele Sassoli (JGit). The goal is to align the community on a timeline and scope for Git 3.0, which is tentatively set for April 2027, with a transitional 2.99 release in March 2027.

The current plan is a three-phase rollout: Git 2.98 in December 2026 (final 2.x feature release), Git 2.99 in March 2027 (with breaking changes disabled via a `WITH_BREAKING_CHANGES` Makefile knob), and Git 3.0 in April 2027 (identical to 2.99.1 but with breaking changes enabled). The month between 2.99 and 3.0 is meant as an "advertisement" period for downstream projects to prepare, not a full development cycle. Junio has repeatedly stressed that this timeline is provisional and subject to change—most recently clarifying that the stabilization period for 2.99 might extend beyond the current plan, potentially requiring additional maintenance releases (e.g., 2.99.2 or 2.99.3) before 3.0 ships. Git for Windows has already tied its roadmap to this timeline, planning Rust-based builds and Git Credential Manager v3.0 integration, but Junio’s latest note tempers expectations by emphasizing that the April 2027 date isn’t set in stone.

On the technical side, Git 3.0 aims to include Rust support (though portability concerns, like the NonStop platform, remain unresolved) and other breaking changes, but the exact scope is still fluid. JGit’s pluggable backend infrastructure is technically ready for Git 3.0’s goals, but resource constraints—not technical barriers—are the main obstacle for SHA-256 interoperability and production adoption. Security process improvements are also in progress, with Toon Claes committing to document Git’s security model and collaborate with Schindelin on the next security release. Documentation is another focus, with a two-pronged strategy: incremental updates for reference material and complete rewrites for tutorials (like Julia Evans’ work on `git reset`), though resourcing remains a challenge.

What’s still open? The scope of breaking changes (e.g., Rust, SHA-256, pluggable ODBs) needs broader community feedback, and downstream coordination—especially with distributions like Gentoo—is still informal. The security process is making progress, but details like release cadence and staffing are unresolved. Documentation tooling (e.g., Open Blocks for diagrams) and maintenance of `git-scm.com` are also works in progress. Junio’s next "What’s cooking" report will likely refine the Git 3.0 plan further, but for now, the key takeaway is that the timeline is a working proposal, not a guarantee.

Here’s the human-mode summary for a developer catching up on this thread:

This thread is Junio’s September 2026 “What’s cooking” report, summarizing all in-flight patch series and kicking off the Git 3.0 planning cycle. The big picture: Git 2.56-rc1 has been tagged, so no new features will land in 2.x. The community is now aligning on a provisional three-phase timeline for Git 3.0—December 2026 for the final 2.x feature release (2.98), March 2027 for a transitional 2.99 release with breaking changes disabled, and April 2027 for Git 3.0 itself, which will be identical to 2.99.1 except that the breaking changes are enabled. The month between 2.99 and 3.0 is meant as an “advertisement” period for downstream projects to prepare, not a full development cycle.

Key participants are Junio (maintainer), Johannes Schindelin (Git for Windows), Toon Claes (GitLab), and a handful of others who chimed in on specific topics. The thread has clarified several Git 3.0 prerequisites: Git for Windows is on board with the timeline, tying it to their own Rust-based builds and Git Credential Manager v3.0 integration. JGit’s pluggable backend infrastructure is technically ready—it’s been viable for years—but lacks active development due to resource constraints, not technical barriers. SHA-256 interoperability in JGit is also technically feasible but not currently prioritized. Rust support remains a goal for Git 3.0, though portability concerns (e.g., the NonStop platform) could still derail it.

Security process improvements are now moving from discussion to action. Toon Claes has committed to documenting Git’s security model, increasing GitLab staffing for report triage, and adopting a more predictable release cadence. Schindelin just followed up to say he’s ready to collaborate on the next security release, signaling that the long-standing bottlenecks—lack of documented procedures and over-reliance on a few individuals—are finally being addressed. Documentation is another focus: the plan is to split efforts between incremental updates for reference material and complete rewrites for tutorials and conceptual guides, with Julia Evans’ Sovereign Tech Fund grant providing some funding. The `git-scm.com` website, however, remains a maintenance headache due to stagnation and lack of review activity.

What’s still open: the exact scope of Git 3.0’s breaking changes hasn’t been nailed down, and downstream coordination beyond Git for Windows (e.g., JGit, distributions) is still ad-hoc. The proposed Git 2.x LTS branch needs volunteers to engage with distributions like Gentoo. Stalled patch series (`mm/diff-process-hunks`, `tb/midx-incremental-custom-base`, etc.) are still waiting for review or rerolls. Kristoffer Haugsbakk has promised a reroll of his `kh/format-patch-range-diff-notes` series by the weekend. AI policy and push protocol v2 are still under discussion, with no consensus yet. Overall, the thread has shifted from high-level planning to concrete next steps, but the final shape of Git 3.0—and whether it will include Rust or SHA-256 interoperability—remains fluid until Junio’s next “What’s cooking” report.

This is a feature request discussion about adding **pre-worktree-remove hooks** to Git’s worktree subsystem.

Michał Papis argues that the existing post-worktree-remove hooks are insufficient for tools that manage external resources (containers, databases, sockets) tied to a worktree. Once the worktree is deleted, its configuration — the only reliable mapping between the worktree and those external resources — is lost, forcing cleanup scripts to guess which resources belong to which deleted worktree. A pre-worktree-remove hook would run while the worktree’s configuration is still available, allowing deterministic teardown of external state. Papis notes this isn’t about vetoing removal, just about performing cleanup with full information.

He also clarifies that pre-remove hooks would only fire for `git worktree remove`, not for manual deletion followed by `git worktree prune`, so post-remove hooks remain necessary for those cases. The two types of hooks are complementary rather than redundant.

The email is part of an ongoing thread (context provided) but does not include the original RFC patch itself. It focuses on motivating the need for pre-remove hooks rather than proposing a specific implementation. The use case — AI-generated worktrees that exhaust disk space without proper cleanup — is concrete and likely to resonate with users managing ephemeral worktrees at scale.

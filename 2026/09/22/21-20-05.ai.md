This is a **substantive review** of Harald Nordgren’s v2 patch adding shallow-history advice. Junio C Hamano’s reply identifies a fundamental flaw in the patch’s approach to detecting when a revision walk stops at a shallow boundary.

The core issue: the patch triggers advice only when the *last commit shown* is itself a shallow boundary. Junio points out that this misses cases where the walk stops because a *parent* of a shown commit is shallow, not the commit itself. In his example history—where a side branch is denser than the trunk—a shallow clone might show commits `g, f, e, d, c, b, a` but stop at `b` because its parents are hidden. The last commit shown (`a`) is a genuine root, so the advice never fires, even though the user is missing history behind `b`. This makes the advice unreliable: sometimes it appears, sometimes it doesn’t, for the same underlying problem.

Junio concludes that the current implementation is counter-productive and retracts his earlier suggestion to cover silent truncation in `git log`. He suggests that a better solution might involve enriching `git log --graph` output, but that’s outside the scope of this patch. The review effectively kills the v2 approach for `git log` integration, though the `<rev>~N`/`<rev>^N` advice in `rev-parse` may still be viable.

Harald’s test case (`shallowHistory advice accounts for depth already present`) is also scrutinized: Junio asks whether the advice would behave the same for `origin/main^^^^^` as it does for `origin/main~5`, hinting at potential edge cases in the `--deepen` calculation.

The thread is now at a crossroads: the `<rev>~N`/`<rev>^N` advice for failing syntax remains uncontroversial, but the `git log` integration needs a rethink. The patch’s future likely depends on whether Harald can devise a way to reliably detect when a walk stops *because of* a shallow boundary, not just when it stops *at* one.

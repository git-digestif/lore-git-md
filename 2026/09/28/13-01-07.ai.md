This is a **substantive review** of Jeff King's bugfix patch for the HTTP transport layer, focusing on the redirect detection logic in light of libcurl 8.23.0's credential-stripping behavior.

Patrick Steinhardt engages directly with the core problem: Git's current redirect detection relies on a simple string comparison between the requested URL and the effective URL returned by libcurl. With libcurl 8.23.0 stripping credentials from the effective URL, this comparison fails even when no redirect occurred, causing Git to unnecessarily flush cached credentials. Patrick restates the issue clearly and questions whether the proposed solution—adding a helper function to strip credentials and re-compare—is the most direct approach.

The key new suggestion in this email is to use `CURLINFO_REDIRECT_COUNT` instead of URL comparison to detect redirects. This interface, available since libcurl 7.9.7 (2001), directly reports the number of redirects encountered during the request, which Patrick argues is a more straightforward way to determine whether a redirect happened. This alternative would avoid the need for URL parsing or string manipulation entirely, potentially simplifying the fix and reducing the risk of edge cases in URL handling.

The review is substantive: it identifies a specific libcurl API that could address the problem more directly, questions the algorithmic choice in the patch, and suggests an alternative with a technical rationale. No testing or implementation is reported, but the feedback is clearly grounded in libcurl's documented behavior and Git's existing use of its APIs. This is likely to spark further discussion about the best way to handle the regression, and the outcome may influence whether the patch is revised or replaced.

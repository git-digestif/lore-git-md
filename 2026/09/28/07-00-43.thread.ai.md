Subject: reftable reflog timezone encoding discrepancy
Series version: none (standalone bug report)
Originating author: Josh McKinney
Thread type: bug report / design discussion

Core problem or goal
Git 2.55.0’s reftable backend writes reflog timezone offsets as signed HHMM integers (e.g., +05:30 → 0530), but the published reftable specification requires signed minutes (e.g., +05:30 → 330). The mismatch is internally consistent (Git’s writer and reader agree) but breaks interoperability with other implementations and violates the documented format. The goal is to decide which representation to standardize on and how to handle existing on-disk tables.

Current status
Under review. The report includes a self-contained reproducer (temporary SHA-1 reftable repository + Python script) and a minimal test case that confirms the discrepancy without external tools. No patch has been posted; the author is seeking guidance on whether to update the specification to match Git’s behavior or to change Git to match the specification.

Key technical details
- Subsystem: reftable backend (refs/reftable/)
- On-disk format: reflog timezone offset encoding
- Old behavior: signed HHMM (e.g., +05:30 → 0530)
- New behavior: undecided (either HHMM or signed minutes)
- Test coverage: minimal test case added to demonstrate the issue
- Interoperability risk: JGit and other reftable consumers

Open questions and loose ends
1. Is this discrepancy already known?
2. Which representation should be adopted (Git’s HHMM or the spec’s signed minutes)?
3. How should existing tables be interpreted if the format changes?
4. Coordination with JGit and other reftable implementations to avoid interoperability breakage.

Thread identity
Subject: reftable reflog timezone encoding discrepancy
Series version: none (standalone bug report)
Originating author: Josh McKinney
Thread type: bug report / design discussion

Core problem or goal
Git 2.55.0’s reftable backend writes reflog timezone offsets as signed HHMM integers (e.g., +05:30 → 0530), but the published reftable specification requires signed minutes (e.g., +05:30 → 330). The mismatch is internally consistent (Git’s writer and reader agree) but breaks interoperability with other implementations (notably JGit) and violates the documented format. The goal is to decide which representation to standardize on and how to handle any existing on-disk tables.

Current status
Under review. The report includes a self-contained reproducer (temporary SHA-1 reftable repository + Python script) and a minimal test case in `t/t0610-reftable-basics.sh` that confirms the discrepancy without external tools. Consensus is forming to align Git with the specification (signed minutes). Junio C Hamano and Patrick Steinhardt agree the practical impact is limited (timezone offsets misinterpreted by at most 10 hours, and only in reflogs, which are typically garbage-collected within 30 days). No patch has been posted; discussion is now focused on migration strategy, with a one-time offline conversion suggested but considered potentially unnecessary due to the limited scope of the issue.

Key technical details
- Subsystem: reftable backend (`refs/reftable/`)
- On-disk format: reflog timezone offset encoding
- Old behavior: signed HHMM (e.g., +05:30 → 0530)
- Proposed behavior: signed minutes (e.g., +05:30 → 330)
- Test coverage: minimal test case added to `t/t0610-reftable-basics.sh`; reproducer uses a temporary SHA-1 reftable repository
- Interoperability risk: JGit and other reftable consumers (JGit already implements the specification correctly)
- Format version: SHA-1 repositories use version 1; a version bump is considered unhelpful for this issue

Open questions and loose ends
1. Is the consensus to align Git with the specification (signed minutes) now settled? (Junio and Patrick agree; no dissent voiced.)
2. Is a migration strategy (e.g., one-time offline conversion) needed, or can the fix be applied without special handling? (Junio suggests it might be simplest, but questions whether it’s worth the effort given the limited practical impact.)
3. Should coordination with JGit and other reftable implementations occur before landing the fix? (No new input on this point.)

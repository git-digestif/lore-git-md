This is the third and final patch in Thomas Bachem’s v5 series fixing a long-standing race condition in Git’s `rerere` subsystem. The patch allows conflict-stopping commands (`git merge`, `git rebase`, `git am --3way`, `git stash pop`, `git apply --3way`) to proceed with a warning if the `MERGE_RR.lock` remains held after the timeout, while post-resolution recording (`git commit`, `git am --continue`) and explicit `git rerere` commands still fail immediately.

The change is surgical: it introduces a new `RERERE_SKIP_LOCKED` flag that, when passed to `repo_rerere()`, causes the command to emit a warning (via `advise_if_enabled()` under `advice.mergeConflict`) and continue without recording the conflict preimage. The warning instructs the user to run `git rerere` manually before resolving the conflict, ensuring the preimage is recorded or a known resolution is replayed. The flag is added to all conflict-stopping call sites (`apply.c`, `builtin/am.c`, `builtin/merge.c`, `builtin/stash.c`, `sequencer.c`), while post-resolution and explicit `rerere` commands retain the original behavior of failing loudly. Documentation is updated to clarify the distinction, and the test suite now covers the new behavior across all affected commands, including manual recovery via `git rerere` and the restoration of upstream signatures for `rerere_clear()` and `rerere_forget()`.

The patch addresses the last piece of feedback from Junio C Hamano and Phillip Wood, who had insisted on a clear distinction between conflict stops (where resilience is prioritized) and post-resolution recording (where correctness is non-negotiable). The use of `advise_if_enabled()` aligns with Git’s existing advice system, and the warning message is actionable and specific. The test coverage is thorough, verifying that the lock timeout does not break the rebase state file (`.git/rebase-merge/stopped-sha`) and that manual recovery works as expected. No open questions remain for this patch; it is ready for final review.

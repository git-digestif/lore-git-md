This is a **bugfix report** targeting the reftable backend, specifically a discrepancy between Git's reflog timezone encoding and the published reftable specification.

Josh McKinney identifies a mismatch in how Git 2.55.0 stores timezone offsets in reftable reflogs: the code writes signed HHMM integers (e.g., +05:30 becomes 0530), but the specification requires signed minutes (e.g., +05:30 becomes 330). The commit message provides a clear reproducer using a temporary SHA-1 reftable repository and a Python script to inspect the raw bytes, demonstrating that Git's internal consistency (writer and reader agree) does not align with the documented format. The patch includes a minimal test case that confirms the issue without requiring external tools beyond Git and Python's standard library.

The email raises three practical questions: whether this discrepancy is already known, which representation interoperable implementations should adopt, and how existing tables should be interpreted if the format changes. The author suggests updating the specification to match Git's behavior, but notes the need to consider other implementations (e.g., JGit) and backwards compatibility. No patch is proposed yet—this is a diagnostic report and request for guidance.

The reftable backend is a critical subsystem, and this issue touches on-disk format compatibility. The reproducer is thorough and self-contained, making it easy for reviewers to verify the problem. If the specification is updated, it would likely require coordination with other reftable consumers (notably JGit) to avoid interoperability breakage.

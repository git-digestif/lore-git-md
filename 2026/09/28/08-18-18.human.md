This is a surface-level review comment on the second patch of Thomas Bachem’s two-part bugfix series for the `rerere` subsystem. The series addresses a long-standing race condition where concurrent `rerere` operations contend for the shared `rr-cache` directory lock, exacerbated by the geometric maintenance strategy introduced in Git 2.54.

Patrick Steinhardt points out a minor implementation detail in the warning logic: the patch currently uses `advise()` to suggest running `git rerere` manually when the lock remains held, but it should use `advise_if_enabled()` instead. This ensures the advice respects the user’s `advice.*` configuration settings (e.g., `advice.skipRerereLocked`), aligning with Git’s standard practice for optional guidance. The change is trivial and does not affect the patch’s core functionality—it’s purely about consistency with Git’s advice framework.

The patch itself remains well-motivated and ready for review. It introduces a pragmatic compromise: commands that stop at conflicts (e.g., `git rebase`, `git merge`) proceed with a warning if the lock is held, while post-resolution recording and explicit `git rerere` commands still fail. This preserves the user’s ability to recover conflict preimages manually while preventing silent corruption of the `MERGE_RR` file. The implementation is clean, and the test coverage is thorough. No substantive objections to the approach remain.

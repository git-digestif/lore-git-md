This is a **bugfix series follow-up** from Thomas Bachem, the author of the `tb/rerere-lock-grace` topic, clarifying the root cause of the `t5520-pull.sh` test breakage that ejected D. Ben Knoble’s stash autostash series from Junio’s `seen` branch.

Thomas confirms Phillip Wood’s earlier diagnosis: the breakage stems from an interaction between auto-maintenance (introduced in `tb/rerere-lock-grace`) and reflog expiration under the test’s fixed `GIT_COMMITTER_DATE` (2005). The key detail is that `git merge`—when restoring a dirty tree via `stash apply --index`—spawns `git reset --quiet --refresh`, which writes a reflog entry. In `t5520`, this happens eight times before the critical fetch in test 68. Auto-maintenance expires reflogs once HEAD’s reflog reaches 100 entries (the default `maintenance.reflog-expire.auto` threshold), and with the test’s 2005 timestamp, every entry is eligible for expiration. The extra maintenance run added by `tb/rerere-lock-grace` shifts the expiration point just enough to wipe the reflog entry that `git pull --rebase` needs for fork-point detection, causing the rebase to misidentify the upstream commit.

Thomas proposes a targeted fix: pinning reflog expiration to `never` in the test setup, mirroring an earlier patch (`ea7d894f44`) that did the same for rebase tests. He has already sent this as a standalone patch (`pull.2243.git.1790606282769.gitgitgadget@gmail.com`) to `master`. The fix is narrow—it only affects `t5520`—but Thomas notes that any test script reading reflogs after 100 HEAD updates could hit the same issue, suggesting this might be a broader test-suite fragility.

For the stash series, this means the `t5520` breakage is not a flaw in the in-core merge logic but a test-environment quirk. The series can likely re-enter `seen` once Thomas’s patch lands, assuming the NULL-dereference risk in Patch 5/5 is also addressed. The interaction highlights a real-world edge case: auto-maintenance could disrupt workflows that rely on recent reflog entries (e.g., `git pull --rebase`), but the fix belongs in the maintenance subsystem, not the stash code.

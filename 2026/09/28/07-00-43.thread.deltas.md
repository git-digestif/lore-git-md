# Thread deltas

## 2026/09/28

- [2026/09/28/07-00-43 by Josh McKinney <git-bugs@lists.joshka.net>] Josh McKinney reported that Git 2.55.0 stores reftable reflog timezone offsets as signed HHMM integers (e.g., 530 for +05:30) rather than the signed minutes (330) the reftable specification requires, reproduced on macOS arm64 with both HEAD and refs/heads/main reflog entries affected; Git reads its own entries back consistently, and he asked whether the discrepancy is known, which representation interoperable implementations should use, how existing tables should be interpreted, and suggested updating the specification to match Git's behavior.
- [2026/09/28/12-13-27 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt confirmed he reproduced the issue and called the current storage "plain wrong"; supplied a Git reproducer (a test-helper fix for unsupported hash algorithms plus a t0610 test asserting the stored "0530" value); stated the issue was not known to him; argued the specification's minutes representation should be used and Git fixed, since JGit's reftable implementation reads the int16 as minutes per the spec; assessed backwards-compatibility impact as limited (divergence under 10 hours, reflogs only, 30-day default reflog GC grace period) and said he is inclined to treat it as a bug and fix it without backwards-compatibility handling, while inviting alternative takes.
- [2026/09/28/14-42-01 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano agreed with the conclusion to fix Git, noting reftable files are not shipped over networks and reflogs are not shared across repositories, so the remaining question is migrating local reftable repositories, where a one-time offline conversion may be simplest but may not be worth it given the limited divergence.
- [2026/09/28/16-02-36 by Josh McKinney <git-bugs@lists.joshka.net>] Josh McKinney said his main concern is multiple tools interpreting the same on-disk format (his tooling caught the mismatch comparing Git's output with a library it is writing), and that nothing is urgent from his side.

## 2026/09/29

- [2026/09/29/07-10-14 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt agreed that sticking to the specification is the best way to resolve interoperability issues when multiple tools use the same repository, stated that fixing the inconsistency is somewhat urgent because it causes more problems the longer it persists, and said he would aim to have a fix ready later this week.

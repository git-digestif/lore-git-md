This is a refactoring patch in Christian Couder’s five-part series introducing `uploadpack.lazyFetchTrusted`, a server-side configuration to mark repositories as trusted for lazy fetching. This patch (2/5) extracts and generalizes the path-allowlist logic from Git’s existing `safe.directory` mechanism into reusable helpers, preparing the ground for the new `uploadpack.lazyFetchTrusted` feature in later patches.

The patch splits the existing `safe_directory_cb()` function into two new helpers: `path_allowlist_apply()` and `path_allowlist_config_apply()`. The first handles the core logic of checking whether a target path matches an allowlist entry (supporting wildcards like `*` and trailing `/*`), while the second wraps it to handle config-variable expansion via `git_config_pathname()`. Both helpers take a callback function (`allow_path`) that lets callers enforce their own path-validation rules—here, `allow_safe_dir()` replicates the existing `safe.directory` behavior (accepting only absolute paths or `.`). The patch also changes the `is_safe` field in `struct safe_directory_data` from `int` to `bool` to align with the new helpers’ return convention.

This is a clean, behavior-preserving refactoring with no functional changes. The extracted helpers are well-documented, and the commit message clearly explains the motivation: avoiding code duplication when adding the new `uploadpack.lazyFetchTrusted` configuration in patch 3/5. Junio’s earlier review of this patch in v3 noted a latent design issue in the existing `safe.directory` logic (silent-ignoring of non-existent paths), but this is inherited and not addressed here. The patch is a logical prerequisite for the series and could be merged independently if the larger effort stalls. No substantive objections remain.

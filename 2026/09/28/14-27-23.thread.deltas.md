## 2026/10/05

- [2026/10/05/05-53-37 by Hanan Arshad <hananarshad619@gmail.com>] Hanan Arshad revised the RFC proposal to drop any fixed remote namespace (e.g. refs/stashes/<author>/<name>) in favor of a user-selected remote ref, and laid out a four-operation porcelain interface: `git stash publish <remote> <remote-ref> [<stash>]` (defaulting to stash@{0}), `git stash list --remote <remote> [<ref-pattern>]` (listing refs only, without downloading stash objects), `git stash get <remote> <remote-ref-or-pattern>` (fetching and importing via existing stash import, with explicit wildcards and no tracking relationship), and `git stash remove <remote> <remote-ref-or-pattern>` (deleting remote refs, leaving local copies unaffected); he asked whether all four operations should be pursued or only publish.
- [2026/10/05/07-47-20 by Johannes Sixt <j6t@kdbg.org>] Johannes Sixt objected to the publish interface, arguing stashes are strictly personal, short-lived WIP states and that shareable work belongs on branches; he noted the same result is already achievable with `git push origin stash@{0}:refs/stashes/hanan/fix-login`, so no magic support is needed or desired.
- [2026/10/05/08-03-44 by Hanan Arshad <hananarshad619@gmail.com>] Hanan Arshad agreed stashes should remain short-lived WIP, narrowed the use case to temporarily handing an unfinished state to another clone or developer (Perforce-shelf-like, without converting it to a branch workflow), and asked whether Johannes Sixt would still object to a narrowly scoped porcelain wrapper or only to the broader "shared stashes" concept.
- [2026/10/05/08-21-03 by Johannes Sixt <j6t@kdbg.org>] Johannes Sixt acknowledged the narrower use case but questioned the need for convenience since a single push already suffices, stating there is zero reason to upgrade stashes to do what branches already do, and advising branches for frequently shared half-finished work.
- [2026/10/05/09-06-36 by Hanan Arshad <hananarshad619@gmail.com>] Hanan Arshad retracted the publish proposal, agreeing that `git push origin stash@{0}:refs/stashes/hanan/fix-login` already covers it and that he does not plan to pursue `git stash publish`; he narrowed the remaining proposal to porcelain only for `git stash list --remote`, `git stash get`, and `git stash remove` (around existing ls-remote, fetch/stash-store, and remote ref deletion), with publishing left as ordinary git push and no new stash representation, server-side mechanism, tracking, or mandatory namespace.
- [2026/10/05/15-25-38 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano agreed with Johannes Sixt, noting that discovery, transfer, and clean-up are all easier with branches, which have always supported these operations, and saw no good reason to add parallel stash support; he also reminded Hanan Arshad not to top-post on the list.

## 2026/10/07

- [2026/10/07/06-31-55 by Hanan Arshad <hananarshad619@gmail.com>] Hanan Arshad clarified the RFC's motivation as a concrete configuration-overlay use case (inspired by Perforce shelves): a tester needs to apply the same temporary local configuration across different branches or revisions without it becoming a line of history that must be merged, rebased, or cherry-picked as the code changes. He conceded that, since a stash can already be pushed as a ref, adding a separate "publish" command would not be justified, and reframed the RFC as seeking a more coherent UX over the existing stash/ref/push/fetch functionality rather than any new transport or storage mechanism.
- [2026/10/07/10-36-32 by Johannes Sixt <j6t@kdbg.org>] Johannes Sixt replied that the required workflow is being overthought: commit configuration X once on a single branch (e.g. "configuration-X"), push it, and in each clone that needs it run `git fetch origin` followed once by `git show origin/configuration-X | git apply -3`, which leaves the modifications uncommitted; from there the local stash can carry the changes to other branches just as a transferred stash would.

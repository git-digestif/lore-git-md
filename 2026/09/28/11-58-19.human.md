This is a bugfix patch series (v5) targeting the `rerere` subsystem, addressing a long-standing race condition where concurrent `rerere` operations contend for the shared `MERGE_RR.lock`. The series is now split into three focused patches, reflecting feedback from earlier iterations.

The core issue is that `setup_rerere()` fails immediately if the lock is held, which became more problematic after Git 2.54's geometric maintenance strategy made `git rerere gc` runs more frequent. The v5 series resolves this with three changes: (1) all `rerere` writers now wait for the lock (configurable via `rerere.lockTimeout`, defaulting to 1 second), (2) only `git rerere gc --auto` (triggered by background maintenance) skips the lock silently, while manual `git rerere gc` fails if the lock is held, and (3) commands that stop at conflicts (e.g., `git rebase`, `git merge`) warn and proceed if the lock remains held after the timeout, advising the user to run `git rerere` manually before resolving.

The series touches `rerere.c`, `rerere.h`, and callers in `apply.c`, `builtin/am.c`, `builtin/merge.c`, `builtin/stash.c`, and `sequencer.c`, along with documentation and test updates. The changes are well-motivated and address earlier concerns about silent failures and modularity. The test coverage is thorough, verifying both the new timeout behavior and the distinction between conflict-stopping commands and post-resolution recording.

This looks like a clean, pragmatic fix for a real-world problem. The split into three patches makes the changes easier to review, and the compromise between resilience (allowing conflict stops to proceed) and correctness (failing post-resolution recording) appears settled. The series is ready for final review.

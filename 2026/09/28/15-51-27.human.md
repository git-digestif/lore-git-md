This is a performance-focused patch series introducing a compile-time option to use a new Rust-based SHA-1 implementation (`sha1dc` crate) as an alternative to Git's existing C-based SHA-1 backend. The series is authored by Johannes Schindelin, who reports significant speedups—up to 3x faster `git index-pack` operations—on Windows, particularly beneficial for monorepos.

The series adds the Rust crate as an optional feature in `libgitcore`, introduces a new config option (`core.sha1dcBackend=c`) to fall back to the C backend without recompiling, and includes thread-safety fixes (e.g., `pthread_once()` shims for Windows and `NO_PTHREADS` builds). The Rust implementation is enabled by default if the feature is compiled in, but the escape hatch ensures users can revert to the C backend if needed.

The motivation is clear: measurable performance gains on Windows, where SHA-1 computation can be a bottleneck. The patches touch core hashing infrastructure (`hash.h`, `sha1dc_git.c`), build system (`Makefile`, `Cargo.toml`), and platform compatibility (`compat/win32/pthread.*`). The thread-safety work in patches 3 and 4 suggests the Rust crate may have different initialization requirements than the C backend.

This is a well-scoped but potentially controversial change. The performance claims are compelling, but the reliance on a new, unproven Rust crate could raise concerns about long-term maintenance or platform support (e.g., Randall S. Becker’s NonStop port). The series is under review; whether it lands may hinge on broader Rustification debates and the project’s appetite for experimental backends. For now, it’s a Windows-centric optimization with a safety net.

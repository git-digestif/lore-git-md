This is the implementation patch (2/2) of Kristofer Karlsson’s **performance feature** introducing an incremental connectivity check for Git fetches and pushes. The patch adds the core logic behind the new `transfer.connectivityCheck=incremental` configuration, which dramatically reduces the cost of verifying object connectivity in large repositories by processing incoming commits incrementally rather than walking the entire object closure of boundary commits.

The implementation centers on a new `tree-verify.c` file (316 lines), which contains the incremental verifier. The verifier processes incoming commits in topological order, comparing each commit’s tree against its parents’ trees to avoid re-checking unchanged subtrees. This shifts the cost from repository size to the size of the incoming change, delivering up to 190x speedups for small pushes to large repositories while using far less memory (14 MB vs. 3.4 GB in the best case). The patch also wires up the new mode in `builtin/rev-list.c` and `connected.c`, and includes thorough test coverage in `t5412-connectivity-check.sh` (680 lines) and performance benchmarks in `t/perf/p5412-connectivity-check.sh`.

The design is conservative: it falls back to the full check for edge cases like deepening fetches, shallow boundaries, and promisor objects, and preserves partial-clone semantics by preventing lazy-fetching during incremental checks. The patch addresses the two technical concerns raised by Junio in the v1 review—explicit NULL checks after `get_commit_tree_oid()` and hardened lazy-fetch protection—making the implementation robust against edge cases. The new `Documentation/technical/connectivity-check.adoc` (included in patch 1/2) provides a detailed explanation of the algorithm, trust model, and invariants, which this patch implements faithfully.

The test suite is exhaustive, covering corruption detection (missing objects, malformed trees, type mismatches), tree-diff optimizations (moves, merges, file-to-directory transitions), replacement objects, and promisor object handling. The performance benchmarks demonstrate the feature’s strengths and tradeoffs: it is up to 20x faster for large repositories with small incoming changes, but becomes 1.5x slower for very long incoming histories (10,000+ commits), a tradeoff the author argues is acceptable for an opt-in feature targeting the common case.

This patch looks production-ready. The prior technical concerns have been addressed, the design is well-motivated and conservative, and the test coverage is thorough. The incremental mode is opt-in, so there is no risk of regressing existing workflows. For large repositories where connectivity checks are a bottleneck, this feature could be a significant quality-of-life improvement.

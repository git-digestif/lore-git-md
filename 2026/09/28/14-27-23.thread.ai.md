Thread identity
Subject: [RFC] Share Git stashes through remotes
Series version: RFC (no patch series yet)
Originating author: Hanan Arshad
Thread type: feature proposal (porcelain workflow)

Core problem or goal
Enable lightweight sharing of Git stashes across repositories by composing the existing `git stash export` and `git stash import` plumbing with standard push/fetch operations. The goal is to provide a porcelain interface for publishing, listing, importing, and removing shared stashes without introducing new object formats or server-side services.

Current status
Early-stage RFC; no implementation exists. The author has tested the underlying mechanism (export + push / fetch + import) and is soliciting feedback on four design questions before writing code:
- Remote ref namespace (proposed: `refs/stashes/`)
- Shared stash identifiers (user-provided names vs. object-derived hashes)
- Whether `git stash list-shared` should fetch export commits to display stash messages
- Command naming that aligns with the existing `git stash` interface

Key technical details
- Subsystem: `git stash` (porcelain)
- No new object formats; relies on existing export/import plumbing
- Proposed ref namespace: `refs/stashes/<identifier>`
- No on-disk format changes; uses standard Git objects (commits from `git stash export`)
- No test coverage yet

Open questions and loose ends
1. Remote ref namespace: Is `refs/stashes/` the right choice, or should it be under `refs/remotes/` or another hierarchy?
2. Shared stash identifiers: Should they be user-provided names (e.g., `refs/stashes/feature-branch`) or derived from the stash object (e.g., `refs/stashes/<hash>`)?
3. Listing behavior: Should `git stash list-shared` fetch export commits to display stash messages, or should it only show refs without fetching?
4. Command naming: Are the proposed commands (`git stash publish`, `git stash list-shared`, `git stash import-shared`, `git stash remove-shared`) intuitive and consistent with the existing `git stash` interface?

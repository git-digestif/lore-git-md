Thread identity
Subject: [RFC] Share Git stashes through remotes
Series version: RFC (no patch series yet)
Originating author: Hanan Arshad
Thread type: feature proposal (porcelain workflow)

Core problem or goal
Enable lightweight, temporary sharing of Git stashes across repositories by composing existing Git plumbing (`git stash export`, `git stash import`, `git ls-remote`, `git fetch`, `git push --delete`) into porcelain wrappers for discovery, fetching, and removal of remote stash refs. The proposal frames the use case as a Perforce-shelf-like handoff of unfinished work—temporary, ephemeral, and not a replacement for branches—rather than a persistent or collaborative workflow. The goal is to reduce friction for a niche workflow without introducing new object formats, server-side services, or fixed ref namespaces.

Current status
Early-stage RFC with no implementation. The author has revised the design three times: first to address **brian m. carlson**'s feedback by abandoning a standardized remote ref namespace, then to address **Johannes Sixt (Hannes)**'s opposition by abandoning the `git stash publish` porcelain wrapper, and now to propose a strictly limited set of porcelain commands (`git stash list --remote`, `git stash get`, `git stash remove`) for discovery, fetching, and removal of remote stash refs. The design reuses existing Git plumbing and push/fetch machinery, requiring no new object formats or server-side changes. **Hannes** and **Junio C Hamano** (the maintainer) are now both strongly opposed, arguing that branches are the "right tool" for shareable work and that the existing workflow (`git stash export` + `git push`/`git ls-remote`/`git fetch`) is already sufficient. Junio's response is brief but decisive, signaling that the proposal in its current form is unlikely to gain traction without a compelling counterargument to the "use branches" position. The thread now hinges on whether the author or other participants can articulate a use case that branches cannot satisfy or whether the proposal will be abandoned.

Key technical details
- Subsystem: `git stash` (porcelain)
- No new object formats; relies on existing `git stash export`/`import` plumbing (commits)
- Remote refs are user-configurable (e.g., `refs/heads/stash/fix-login`)
- Proposed commands:
  - `git stash list --remote` (wraps `git ls-remote`)
  - `git stash get <remote> <ref>` (wraps `git fetch` + `git stash import`)
  - `git stash remove <remote> <ref>` (wraps `git push --delete`)
- No on-disk format changes; uses standard Git objects
- No test coverage yet

Open questions and loose ends
1. **Feature necessity**: Is even this narrowed convenience layer justified, or is the existing plumbing (`git ls-remote`, `git fetch`, `git push --delete`) sufficient? Hannes and Junio argue the latter is adequate and that the feature encourages misuse of stashes.
2. **Philosophical alignment**: Does the narrowed use case (temporary handoff of unfinished work) sufficiently address Hannes’s and Junio’s objection that stashes are inherently personal and ephemeral, or is the feature fundamentally misaligned with Git’s design principles?
3. **Command scope**: Are the proposed commands (`list --remote`, `get`, `remove`) appropriately scoped, or should they be further narrowed or expanded (e.g., wildcard support, `--fetch` flag for `list`)?
4. **Backwards compatibility**: How should the porcelain handle conflicts with existing refs (e.g., fetching a stash that collides with a local branch)? No error handling or collision avoidance is yet proposed.
5. **Wildcard behavior**: Should wildcard patterns (e.g., `refs/stashes/*`) be supported in `git stash get` or `git stash remove`, or should users explicitly specify refs?
6. **Metadata trade-offs**: Is the reliance on existing commands for listing/fetching acceptable, or should the porcelain provide more flexibility (e.g., filtering by author, date, or message)?

Participant positions
- **Hanan Arshad** (author): Proposes a narrowed design, emphasizing porcelain wrappers for discovery, fetching, and removal of remote stash refs. Directly addresses Hannes’s concerns by abandoning the `publish` command and framing the use case as a temporary handoff of unfinished work. Review is substantive (engages with behavior, edge cases, and usability).
- **brian m. carlson**: Supported the original goal but raised concerns about (1) lack of a universal ref namespace, (2) incomplete metadata without fetching, and (3) command naming (`publish` vs. `push`). The revised proposal aligns with his emphasis on flexibility, but no explicit response to the narrowed scope yet.
- **Johannes Sixt (Hannes)**: Strongly opposes the feature, arguing stashes are inherently personal and ephemeral. Advocates using branches for shareable work and existing plumbing for edge cases. Review is substantive (engages with core motivation and design principles). Position remains firm: the existing workflow (`git stash export` + `git push`/`git ls-remote`/`git fetch`) is already sufficient, so no convenience wrapper is justified. No compromise offered.
- **Junio C Hamano** (maintainer): Aligns with Hannes’s opposition, stating that branches already provide robust support for discovery, transfer, and cleanup of shared work. Sees no justification for adding parallel functionality to stashes, reinforcing the view that stashes should remain personal and ephemeral. No technical objections to the implementation; the rejection is purely philosophical. Position is decisive, signaling the proposal is unlikely to proceed without a compelling counterargument.

Thread identity
Subject: [RFC] Share Git stashes through remotes
Series version: RFC (no patch series yet)
Originating author: Hanan Arshad
Thread type: feature proposal (porcelain workflow)

Core problem or goal
Enable lightweight sharing of Git stashes across repositories by composing the existing `git stash export` and `git stash import` plumbing with standard push/fetch operations. The goal is to provide a porcelain interface for publishing, listing, importing, and removing shared stashes without introducing new object formats, server-side services, or fixed ref namespaces.

Current status
Early-stage RFC; no implementation exists. The author has revised the design to address **brian m. carlson**'s feedback, abandoning the idea of a standardized remote ref namespace (e.g., `refs/stashes/`) in favor of user-specified refs. The proposed interface now consists of four porcelain commands: `git stash publish <remote> <remote-ref> [<stash>]`, `git stash list --remote <remote> [<ref-pattern>]`, `git stash get <remote> <remote-ref-or-pattern>`, and `git stash remove <remote> <remote-ref-or-pattern>`. The design reuses existing `git stash export`/`import` plumbing and Git’s push/fetch machinery, ensuring no new object formats or server-side changes are required.

Key technical details
- Subsystem: `git stash` (porcelain)
- No new object formats; relies on existing export/import plumbing (commits from `git stash export`)
- Remote refs are fully user-configurable (e.g., `refs/heads/stash/fix-login`, `refs/stashes/<author>/<name>`), addressing Carlson’s concern about inflexible namespaces
- `git stash list --remote` does not fetch objects, prioritizing performance over complete metadata (e.g., stash messages, sizes)
- `git stash get` fetches and imports stashes, providing full metadata when needed
- Wildcard matching is explicit (e.g., `refs/stashes/hanan/*`), requiring users to specify patterns rather than treating prefixes as implicit namespaces
- No on-disk format changes; uses standard Git objects
- No test coverage yet

Open questions and loose ends
1. **Command necessity**: Are all four proposed porcelain commands (`publish`, `list --remote`, `get`, `remove`) necessary, or could some operations (e.g., `remove`) be deferred to existing Git commands like `git push --delete` or `git fetch --prune`?
2. **Wildcard behavior**: Should wildcard patterns (e.g., `refs/stashes/*`) be supported in `git stash get` and `git stash remove`, or should users be required to explicitly specify refs? Carlson’s feedback did not address this, but the current proposal leans toward explicit patterns.
3. **Metadata trade-offs**: The design prioritizes lightweight listing (`list --remote`) over complete metadata, but users can still retrieve full details via `git stash get`. Is this trade-off acceptable, or should the porcelain provide more flexibility (e.g., a `--fetch` flag for `list --remote`)?
4. **Backwards compatibility**: How should the porcelain handle conflicts with existing refs (e.g., if a user publishes to `refs/heads/main`)? The proposal does not yet address error handling or collision avoidance.

Participant positions
- **Hanan Arshad** (author): Proposes the revised design, emphasizing flexibility in remote ref naming and lightweight listing. Directly addresses Carlson’s concerns about namespace rigidity and metadata trade-offs. Review is substantive (engages with behavior, edge cases, and usability).
- **brian m. carlson**: Supported the original goal but raised concerns about (1) lack of a universal ref namespace, (2) incomplete metadata without fetching, and (3) command naming. Suggested `git stash push` over `publish`. Review was substantive (engaged with behavior, edge cases, and usability). No explicit response to the revised design yet, but the new proposal aligns with his emphasis on flexibility.

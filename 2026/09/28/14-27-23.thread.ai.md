Thread identity
Subject: [RFC] Share Git stashes through remotes
Series version: RFC (no patch series yet)
Originating author: Hanan Arshad
Thread type: feature proposal (porcelain workflow)

Core problem or goal
Enable lightweight, temporary sharing of Git stashes across repositories by composing existing `git stash export` and `git stash import` plumbing with standard push/fetch operations. The proposal now frames the use case as a Perforce-shelf-like handoff of unfinished work—temporary, ephemeral, and not a replacement for branches—rather than a persistent or collaborative workflow. The goal is to provide a porcelain interface for publishing stashes without introducing new object formats, server-side services, or fixed ref namespaces.

Current status
Early-stage RFC with no implementation. The author has revised the design twice: first to address **brian m. carlson**'s feedback by abandoning a standardized remote ref namespace in favor of user-specified refs, and now to address **Johannes Sixt (Hannes)**'s opposition by narrowing the scope to a minimal porcelain wrapper around existing plumbing. The proposed interface is now reduced to a single command (`git stash publish`), with listing, fetching, and deletion left to existing Git commands (`git ls-remote`, `git fetch`, `git stash import`, `git push --delete`). The design reuses existing plumbing and Git’s push/fetch machinery, requiring no new object formats or server-side changes. **Hannes** remains strongly opposed, arguing that stashes are inherently personal and that branches should be used instead for shareable work. The proposal remains under active discussion with no consensus on whether to proceed.

Key technical details
- Subsystem: `git stash` (porcelain)
- No new object formats; relies on existing `git stash export`/`import` plumbing (commits)
- Remote refs are user-configurable (e.g., `refs/heads/stash/fix-login`)
- `git stash publish` would wrap `git stash export` + `git push` into a single porcelain command
- Listing, fetching, and deletion would use existing Git commands (`git ls-remote`, `git fetch`, `git stash import`, `git push --delete`)
- No on-disk format changes; uses standard Git objects
- No test coverage yet

Open questions and loose ends
1. **Feature necessity**: Is even a minimal porcelain wrapper (`git stash publish`) justified, or is the existing plumbing (`git stash export` + `git push`) sufficient? Hannes argues the latter is adequate and that the feature encourages misuse of stashes.
2. **Command scope**: Would a single `publish` command address concerns about complexity, or is the feature still unnecessary?
3. **Philosophical alignment**: Does the narrowed use case (temporary handoff of unfinished work) sufficiently address Hannes’s objection that stashes are inherently personal and ephemeral?
4. **Backwards compatibility**: How should the porcelain handle conflicts with existing refs (e.g., publishing to `refs/heads/main`)? No error handling or collision avoidance is yet proposed.
5. **Wildcard behavior**: Should wildcard patterns (e.g., `refs/stashes/*`) be supported in `git stash publish`, or should users explicitly specify refs?
6. **Metadata trade-offs**: Is the reliance on existing commands for listing/fetching acceptable, or should the porcelain provide more flexibility (e.g., a `--fetch` flag for `list`)?

Participant positions
- **Hanan Arshad** (author): Proposes a narrowed design, emphasizing a minimal porcelain wrapper (`git stash publish`) for temporary handoff of unfinished work. Directly addresses Hannes’s concerns by framing the use case as analogous to Perforce shelves and explicitly excluding persistent or collaborative workflows. Review is substantive (engages with behavior, edge cases, and usability).
- **brian m. carlson**: Supported the original goal but raised concerns about (1) lack of a universal ref namespace, (2) incomplete metadata without fetching, and (3) command naming (`publish` vs. `push`). The revised proposal aligns with his emphasis on flexibility, but no explicit response to the narrowed scope yet.
- **Johannes Sixt (Hannes)**: Strongly opposes the feature, arguing stashes are inherently personal and ephemeral. Advocates using branches for shareable work and existing plumbing for edge cases. Review is substantive (engages with core motivation and design principles). No compromise offered; tone remains firm.

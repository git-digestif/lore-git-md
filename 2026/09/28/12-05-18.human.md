This is a bugfix series targeting a subtle but serious issue in `git stash` where autostashing fails to preserve staged index entries when `stash.index=true` is set, particularly during merge operations. The root cause is a race condition in the subprocess-based logic (`git diff-tree` and `git apply`) that the series replaces with in-core merging via `merge-ort.c`. The fix is now in its third iteration (v3), structured as a five-patch series.

The first patch—a minor cleanup—has already been merged to `master`. The remaining four patches (2–5) were previously ready for integration but have been temporarily ejected from Junio’s `seen` branch due to three independent issues. The most pressing is a test breakage in `t5520-pull.sh` (test 69), which Phillip Wood has traced to an unexpected change in `git pull --rebase`'s fork-point detection. The upstream commit argument shifts from `f29aa667ce` to `ae9857430e` when the series is applied, even though the test does not involve stashing. This suggests the series inadvertently alters rebase’s fork-point logic, likely through a side effect in index or ref-handling code paths. The author, D. Ben Knoble, plans to bisect `seen` to isolate the cause and coordinate with Phillip or other rebase experts if needed.

Two other issues have been identified: a NULL-dereference risk in Patch 5/5 (where `merge_incore_nonrecursive()` may return with `result.tree` uninitialized on catastrophic failure) and a verbosity regression in the same patch (now resolved by preserving the original verbosity setting). The author has confirmed the NULL-dereference issue and will address it by checking `result.clean` before dereferencing `result.tree`, possibly combined with a fallback to the original subprocess-based logic.

The series is technically sound and addresses a real problem—autostash with staged index entries is currently broken—but the `t5520` breakage and NULL-dereference risk must be resolved before it can proceed. The author’s responsiveness to feedback and the thoroughness of the test coverage (including new tests for edge cases) suggest this is a well-crafted fix, but the fork-point detection issue introduces an unexpected dependency on rebase logic that may require broader coordination. Worth watching if you care about stash, merge, or rebase behavior.

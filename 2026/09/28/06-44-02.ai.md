This is a **substantive review reply** from Patrick Steinhardt in the ongoing discussion about the reference-transaction hook regression fix. Patrick endorses Maciej Ciemborowicz’s pivot to resolving missing old OIDs in the transaction hook layer itself, calling it "a sensible change to make." His brief reply confirms the architectural direction for the upcoming v6 series: the fix will ensure the hook always receives both old and new OIDs for every ref modification, without requiring changes to callers of `refs_delete_refs()` or other ref-modifying APIs.

The key implication is that the v6 approach will sidestep the API semantics debate entirely by moving the logic into the transaction layer, where it can resolve old OIDs on demand. This design preserves the unconditional deletion semantics of `refs_delete_refs()` while restoring the pre-regression hook behavior for *all* ref-modifying commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, etc.). The trade-off—potential latency from on-demand OID resolution—remains unquantified but is now explicitly endorsed by the refs subsystem maintainer. The thread is now awaiting the v6 patch, which will touch `refs.c`, the transaction hook layer, and regression tests.

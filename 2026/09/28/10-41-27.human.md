This is the third patch in Kristoffer Haugsbakk’s four-part RFC series converting Git’s `BreakingChanges` document into a proper manpage (`gitbreaking-changes(7)`). The series aims to make upcoming breaking changes more visible to end users by integrating the information into Git’s documentation system.

This patch adds a short note (formatted as an AsciiDoc admonition) immediately after the existing “living document” paragraph. The note reminds readers that the document evolves over time and that if they are reading a released version, they might want to check the current development version before posting feedback. The motivation is clear: prevent users on older releases from reacting to decisions that have already been revised in the mainline document. The example in the commit message (a Debian Stable user complaining about Git 3.0 changes when Git 4.0 is already in development) illustrates the real-world scenario the patch addresses.

The change is minimal and focused: ten lines added to `Documentation/gitbreaking-changes.adoc`, with no build-system or cross-reference updates. The wording is concise and avoids prescribing how users should fetch the latest source, keeping the note simple and actionable. The patch is well-motivated and fits cleanly into the series’ goal of improving usability without altering the underlying content. If the RFC receives no objections, this is a sensible, low-risk addition.

This is the third patch in Christian Couder’s five-part v4 series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators explicitly mark repositories as trusted for lazy fetching. The patch teaches `upload-pack` to read the new configuration and expose the result through a new helper, `upload_pack_lazy_fetch_trusted()`.

The implementation reuses the generic `path_allowlist_config_apply()` helper introduced in patch 2/5, passing it a new `allow_trusted_path()` callback that enforces stricter rules than the existing `safe.directory` logic: only absolute paths are accepted, and the special `.` value (meaning “current repository”) is rejected because `upload-pack` always serves repositories identified by absolute paths. The callback also warns about non-absolute paths, making configuration errors visible rather than silently ignored. The repository is identified by its `.git` directory, so a non-bare repository served as `/srv/repo` must be allowlisted as `/srv/repo/.git`.

The new `upload_pack_lazy_fetch_trusted()` function is the public API: it takes a `struct repository *`, resolves the repository’s git directory to an absolute path, and consults the protected configuration to determine whether the repository is trusted. The function returns a boolean, but the underlying logic is careful about memory management (using `real_pathdup()` and freeing the result) and respects the protected configuration infrastructure, ensuring the setting can only be read from trusted files.

This patch is a clean, focused addition with no behavioral impact on its own; the actual lazy-fetching behavior change comes in patch 5/5. The commit message is thorough, explaining the design choices (absolute paths, `.git` directory identification) and the rationale for rejecting `.`. The code is well-structured, with clear separation between the callback, the configuration reader, and the public API. No substantive review comments have surfaced on this patch in the v4 iteration, suggesting it is uncontroversial and ready for integration if the series as a whole moves forward.

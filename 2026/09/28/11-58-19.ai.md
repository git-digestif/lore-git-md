This is the v5 cover letter for a three-patch series that fixes a race condition in Git’s `rerere` subsystem, where concurrent writers contend for the shared `MERGE_RR.lock`. The series is now split into three logical parts: (1) making all `rerere` writers wait for the lock (configurable via `rerere.lockTimeout`), (2) introducing a `--auto` mode for `git rerere gc` that skips a held lock silently (matching the behavior of other auto-maintenance tasks), and (3) allowing conflict-stopping commands (e.g., `git rebase`, `git merge`, `git am --3way`) to proceed with a warning if the lock remains held after the timeout, while post-resolution recording and explicit `git rerere` commands still fail immediately.

The key changes since v4 are the separation of the `gc` behavior into its own patch (patch 2), which now distinguishes between manual and auto-maintenance invocations: only `git rerere gc --auto` (triggered by `git maintenance run --auto` or `git gc --auto`) skips a held lock silently, while manual invocations of `git rerere gc` wait and then fail like other `rerere` commands. The advisory message for conflict-stopping commands now uses `advise_if_enabled()` under `advice.mergeConflict`, allowing users to silence it via configuration. The test suite has been updated to cover these distinctions, including verifying that scheduled maintenance runs (which are treated like manual runs) fail on a held lock.

The series is well-structured and addresses the feedback from Patrick Steinhardt and Phillip Wood, who had raised concerns about the previous version’s handling of manual vs. auto-maintenance and the clarity of the advisory message. The core logic remains unchanged: the race is a long-standing issue in `rerere` locking, exacerbated by the geometric maintenance strategy introduced in Git 2.54, and the solution balances resilience (allowing conflict stops to proceed) with correctness (failing post-resolution recording to avoid silent corruption). The patches touch `rerere.c`, `rerere.h`, and several caller sites (`apply.c`, `builtin/am.c`, `builtin/merge.c`, `builtin/stash.c`, `sequencer.c`), along with documentation and test updates.

This version looks ready for final review. The separation of concerns (wait logic, `gc` behavior, conflict-stop handling) makes the changes easier to assess, and the use of `advise_if_enabled()` aligns with Git’s existing advice system. The test coverage is thorough, including edge cases for manual recovery via `git rerere` and the distinction between auto and manual maintenance. No major objections remain, and the series appears to be a clean, targeted fix for a real-world problem.

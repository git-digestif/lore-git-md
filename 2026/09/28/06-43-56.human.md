This is a **substantive architectural discussion** in the ongoing thread about restoring old-OID reporting in the reference-transaction hook for branch and tag deletions. Patrick Steinhardt responds to Junio C Hamano’s request for clarification on the commit message’s wording and proposes a **fundamental redesign** of the fix.

Patrick acknowledges that the current phrasing—"callers cannot preserve old values that they have already resolved"—is misleading. The real issue is not a technical limitation but a **design choice**: callers *do not* preserve old OIDs because `refs_delete_refs()` is intentionally a simple wrapper for unconditional deletions. He argues that the fix should not extend this function’s interface (as the v5 series does) but instead move the logic into the **transaction layer itself**, where it can resolve and cache old OIDs for *all* ref updates, regardless of whether the caller provided them. This would eliminate the need to modify `refs_delete_refs()` or its callers, preserving the function’s simplicity while ensuring the hook always receives correct old OIDs.

The proposal aligns with Patrick’s earlier feedback but is now framed as a **clear alternative** to the v5 approach. It addresses Junio’s concern about API consistency and avoids the semantic overloading of null-OID values that Patrick previously criticized. However, it introduces a potential **performance trade-off**: resolving old OIDs on demand in the transaction layer could add latency for large batch deletions, though this remains unquantified. The thread is now at a crossroads—Maciej’s next revision will likely adopt this transaction-layer approach, but the performance implications may prompt further discussion. This is a **high-stakes design decision** with implications for the refs subsystem’s API and the reliability of the reference-transaction hook.

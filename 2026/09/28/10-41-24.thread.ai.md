Thread identity: RFC patch series introducing `gitbreaking-changes(7)` manpage, converting the existing `BreakingChanges` document into a proper manpage for better user visibility. Originating author: Kristoffer Haugsbakk.

Core problem or goal: Make Git’s upcoming breaking changes more discoverable to end users by moving the existing plain-text `BreakingChanges` document into a manpage (`gitbreaking-changes(7)`), ensuring it is accessible via `git help` and `man`, and integrating it into the documentation build system. The series also aims to clarify the document's living-draft nature to prevent user confusion about outdated information.

Current status: Under initial review as an RFC. The series consists of four patches, now complete. Patrick Steinhardt has provided substantive review across multiple patches, engaging with both the motivation and implementation approach. No new patch version has been posted yet.

Key technical details:
- Files touched: `Documentation/BreakingChanges` (retained as a pointer), `Documentation/gitbreaking-changes.txt` (added as `gitbreaking-changes.adoc`), `Documentation/git.txt` (updated), `command-list.txt` (updated), `Makefile` (updated), `meson.build` (updated).
- New manpage: `gitbreaking-changes(7)`.
- Changes in this patch: Replaced all message-ID references (e.g., `<xmqqa59i45wc.fsf@gitster.g>`) with clickable URLs pointing to `lore.kernel.org` threads. Two message-IDs required URL encoding to avoid breaking AsciiDoc parsing. Updated explanatory text to clarify the purpose of the links.
- No new symbols, CLI options, or on-disk format changes.
- Test coverage: None added; the series is documentation-only.

Open questions and loose ends:
- The RFC tag indicates the author is seeking feedback on the overall approach (moving to a manpage and usability improvements like clickable URLs) before finalizing.
- The living-draft note addresses a specific usability concern but may still draw feedback as part of the broader RFC discussion.
- Patrick Steinhardt raised a forward-looking question about the document’s lifecycle post-Git 3.0: whether to retain it and add a new section for Git 4.0, or to archive it. He suggests retaining it, noting that major releases should remain infrequent.
- Patrick critiqued the mechanical approach of the initial patch (conversion and renaming of `BreakingChanges` to the new AsciiDoc manpage format in a single step), making it harder to review the actual formatting changes. This critique does not apply to the current patch, which is narrowly focused on URL usability.
- Patrick suggested moving the "how to add new entries" section to the end of the document, arguing that most readers—now that the document is more public-facing—won’t care about the internal process. This is a usability suggestion, not a blocker.

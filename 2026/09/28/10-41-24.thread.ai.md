Thread identity: RFC patch series introducing `gitbreaking-changes(7)` manpage, converting the existing `BreakingChanges` document into a proper manpage for better user visibility. Originating author: Kristoffer Haugsbakk.

Core problem or goal: Make Git’s upcoming breaking changes more discoverable to end users by moving the existing plain-text `BreakingChanges` document into a manpage (`gitbreaking-changes(7)`), ensuring it is accessible via `git help` and `man`, and integrating it into the documentation build system. The series also aims to clarify the document's living-draft nature to prevent user confusion about outdated information.

Current status: Under initial review as an RFC. The series consists of four patches, now complete:
1. Converts `BreakingChanges` to a manpage template, preserving content while adapting to manpage conventions (e.g., adding `NAME` and `SYNOPSIS` sections, demoting the "Introduction" section to second-level). The old `BreakingChanges` file is retained as a single-line pointer to the new manpage to avoid breaking existing links.
2. Replaces commit-message-style message-ID references (e.g., `<abc1234@mail.gmail.com>`) with clickable URLs to `lore.kernel.org`, including URL-encoding two message-IDs to avoid AsciiDoc parsing issues. The surrounding text is adjusted to clarify the links point to the original email threads.
3. Adds a note (formatted as an AsciiDoc admonition) clarifying the document is a *living draft* and may change between releases. The note is inserted after the existing "living document" paragraph and uses Git’s standard admonition style. The motivation is to preempt confusion from users reading outdated versions (e.g., someone on Debian Stable reading about Git 3.0 changes when the document now reflects Git 4.0 plans).
4. Updates `git(1)`’s "SEE ALSO" section to reference the new `gitbreaking-changes(7)` manpage, placing it alongside other user-facing guides. The change follows the established convention of double-spacing sentences in the `git(1)` manpage, matching the style used in a recent similar addition (the `gitdatamodel(7)` tutorial).

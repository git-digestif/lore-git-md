Thread identity: RFC patch series introducing `gitbreaking-changes(7)` manpage, converting the existing `BreakingChanges` document into a proper manpage for better user visibility. Originating author: Kristoffer Haugsbakk. Series version: four patches, currently under review as an RFC.

Core problem or goal: Make Git’s upcoming breaking changes more discoverable to end users by moving the existing plain-text `BreakingChanges` document into a manpage (`gitbreaking-changes(7)`), ensuring it is accessible via `git help` and `man`, and integrating it into the documentation build system. The series also clarifies the document's living-draft nature to prevent user confusion about outdated information.

Current status: Under review as an RFC. The series is technically aligned on all feedback except for a narrow disagreement about how to format message-ID references in the manpage. All other substantive review comments have been addressed: the "how to add new entries" section was moved to the end of the document, and a minor formatting nit (two spaces after a URL) was fixed. Patrick Steinhardt endorsed the proposed three-step restructuring plan (convert `BreakingChanges` to AsciiDoc in-place, rename to `gitbreaking-changes.txt`, and resurrect `BreakingChanges` as a one-line pointer), and the forward-looking question about the document’s lifecycle post-Git 3.0 was resolved (retain a historical section for Git 3.0, defer Git 4.0 discussion). The only remaining open question is whether to adopt Junio C Hamano’s proposed hybrid URL+message-ID format (e.g., `cf. https://lore.kernel.org/git/xmqqa59i45wc.fsf@gitster.g/[<xmqqa59i45wc.fsf@gitster.g>^]`) or stick with plain URLs (e.g., `cf. https://lore.kernel.org/git/xmqqa59i45wc.fsf@gitster.g/`). Kristoffer Haugsbakk has not yet posted a revised version of patch 2/4.

Key technical details:
- Files touched: `Documentation/BreakingChanges` (retained as a pointer), `Documentation/gitbreaking-changes.txt` (added as `gitbreaking-changes.adoc`), `Documentation/git.txt` (updated), `command-list.txt` (updated), `Makefile` (updated), `meson.build` (updated).

The discussion is about whether to adopt the hybrid format or revert to plain URLs. Two message-IDs required URL encoding to avoid breaking AsciiDoc parsing. No new symbols, CLI options, or on-disk format changes.
- Test coverage: None added; the series is documentation-only.

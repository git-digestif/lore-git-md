This is a refactoring series targeting the repository setup subsystem, specifically the `create_repository()` interface. The v2 update from Patrick Steinhardt addresses feedback on documentation clarity and commit message precision but makes no functional changes to the code.

The goal remains the same: enforce that the `struct repository` passed to `create_repository()` is stateless, removing the last in/out usage (propagation of `core.sharedRepository`). The series now clears the repository at the start of the function, ensuring no caller can rely on undocumented state persistence. The updated commit message for patch 6/7 better explains the rationale for replacing `FREE_AND_NULL()` with `free()` followed by `memset()`, avoiding redundant zeroing while fully resetting the struct.

The documentation in `path.h` has been streamlined, grouping the four `safe_create_leading_directories_*()` variants under a single explanatory paragraph that clarifies their intended use cases (git-dir vs. working-tree files), behavior regarding `core.sharedRepository`, and whether the input path is modified. This addresses Kaartic Sivaraam’s feedback from v1 without altering functionality.

The series touches `builtin/init-db.c`, `builtin/clone.c`, `path.c`, `repository.c`, and `setup.c`, with a new test in `t/t1301-shared-repo.sh` verifying leading directory permissions for both `git init` and `git clone`. The changes are incremental and well-scoped, with patches 1-6 serving as mechanical prerequisites for the capstone patch 7/7, which enforces statelessness. The follow-up unification of repository initialization mentioned in the cover letter remains unspecified but appears to be the logical next step.

No substantive technical review has yet engaged with the core interface change (patch 7/7), but the series looks uncontroversial. The test coverage and careful refactoring suggest Patrick has anticipated edge cases, though undocumented caller reliance on the old behavior could surface during wider review.

This is the second patch in Johannes Schindelin’s four-patch series introducing an optional Rust-based SHA-1 backend for Git. It implements the runtime escape hatch (`core.sha1dcBackend`) that lets users switch between the Rust and C implementations without recompiling, addressing a key concern about adopting new, unproven code in a critical path.

The patch wires up a set of function pointers in `sha1dc_git.c` that are initialized on the first call to `git_hash_init()`. The config key `core.sha1dcBackend` accepts `rust` (the default when `DC_SHA1_RS` is defined) or `c` (the fallback). The implementation is careful: it avoids redefining platform constants by reordering includes, and it adds proper resource cleanup for both backends. Tests in `t/t0013-sha1dc.sh` verify that the config knob works and that collision detection still triggers correctly in both modes.

The escape hatch is a pragmatic concession to the broader Rust-in-Git debate. By making the Rust backend optional and providing a runtime fallback, the patch reduces the risk of regressions while still delivering the performance gains claimed in the series. The build system (`Makefile`, `Cargo.toml`) remains unchanged from patch 1, so the Rust backend is still compile-time optional and not a hard dependency.

This patch is likely uncontroversial on its own—it’s a clean, well-motivated addition that doesn’t force anyone to use Rust. The real discussion will probably center on whether the escape hatch is necessary (some may argue it’s over-engineering) or whether the performance gains justify the added complexity. The thread-safety fixes in patches 3–4 may also draw attention, but this patch stands alone as a straightforward feature.

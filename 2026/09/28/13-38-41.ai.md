This is the v4 cover letter for Christian Couder’s five-patch series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators explicitly mark repositories as trusted for lazy fetching. The series replaces the earlier client-side `GIT_NO_LAZY_FETCH=fromAccepted` proposal with a server-controlled trust model, addressing security concerns about untrusted repositories triggering arbitrary code execution via lazy-fetch hooks or configuration.

The v4 iteration incorporates Junio’s feedback from v3, primarily refining the environment-handling logic in the final patch (5/5). Instead of unconditionally setting `GIT_NO_LAZY_FETCH=1` and later relaxing it to `0` for trusted repositories, the new implementation checks the environment first and only sets the variable if it isn’t already set by the operator, preserving operator control. This resolves Junio’s design nit about operator precedence. The commit message for 5/5 is also reframed to clarify that the configuration variable teaches the code to consult the allowlist rather than overriding the environment. Other changes include reverting function return types from `bool` to `int` in patches 1/5 and 2/5 for consistency with existing conventions, and switching the recursion depth counter in patch 4/5 from `unsigned long` to `int` (with a cast from `git_env_ulong()`), as Junio confirmed this is acceptable following existing precedent in Git.

The series remains a clean, incremental implementation: patches 1/5 and 2/5 are refactorings with no behavioral impact, making them candidates for early integration if the series stalls. The core functionality—allowing lazy fetching only for repositories explicitly allowlisted by the server operator—is introduced in patches 3/5 and 5/5, with patch 4/5 adding a recursion safeguard to prevent infinite loops when a repository is configured as its own promisor remote. The implementation touches the promisor-remote subsystem, `setup.c`, `upload-pack.c`, and adds new tests covering recursion limits and path validation. Key symbols include `upload_pack_lazy_fetch_trusted()` (checks if a repository is trusted), `GIT_INTERNAL_LAZY_FETCH_DEPTH` (limits recursion depth to 5), and `path_allowlist_config_apply()` (a generic helper for path validation). Documentation updates in 5/5 clarify that the configuration is multi-valued, specifies repository paths as git directories (e.g., `/srv/repo/.git`), and warns against self-referential promisor remotes.

The unresolved high-weight concerns from earlier iterations—Junio’s scalability critique about memory overhead in `lazy_fetch_objects()` and conceptual doubt about using a configuration variable for this purpose, along with brian m. carlson’s security objection—remain but are mitigated by the server-side trust model. Junio’s review of 2/5 in v3 also highlighted a latent design issue in the existing `safe.directory` logic (silent-ignoring of non-existent paths), which could propagate to `uploadpack.lazyFetchTrusted` if unaddressed, though this is not blocking. CI tests pass, and the series is rebased on a recent `master` commit to avoid merge conflicts. No new substantive reviews have been posted since v3.

This thread introduces a Rust-based SHA-1 backend for Git, aiming to deliver a 3× performance boost in `git index-pack` on Windows and large repositories. Johannes Schindelin, the author, has submitted a four-patch series (v1) that makes the Rust implementation optional at compile time, adds a runtime escape hatch (`core.sha1dcBackend`) to fall back to the C version, and includes thread-safety fixes for Windows and non-PTHREADS builds. The series touches critical files like `hash.h`, `sha1dc_git.c`, and `Makefile`, and introduces a new Rust crate (`sha1dc`) via FFI.

Junio C Hamano, the maintainer, raised a key concern about whether the Rust and C backends are functionally equivalent, particularly for collision detection—a critical security feature. Schindelin has since clarified that while the two implementations take different approaches (SIMD optimizations in Rust vs. the original C logic), they cover the same collision space and produce identical SHA-1 outputs for the same inputs. However, full cross-architecture testing is still pending, leaving some uncertainty about edge cases. The runtime escape hatch remains a pragmatic fallback, but its utility depends on the backends being truly interchangeable.

The series is still under review, with no merge to Junio’s integration branches yet. Open questions include the need for independent performance validation, the build system’s complexity (e.g., Rust version requirements, `Cargo.toml` maintenance), and long-term ownership of the Rust crate. The broader Rustification debate—including concerns from Randall S. Becker about platform support—looms in the background, though the optional nature of this feature may mitigate resistance. For now, the thread’s focus is on verifying the Rust backend’s correctness and ensuring the escape hatch works as intended.

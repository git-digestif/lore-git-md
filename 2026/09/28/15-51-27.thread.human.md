This thread introduces an optional Rust-based SHA-1 backend for Git, aiming to deliver a ~3× performance improvement in `git index-pack` on Windows and large repositories. The series, now at its first version, is authored by Johannes Schindelin and consists of four patches. The first patch (previously summarized) laid the groundwork by integrating the Rust crate via FFI, while the latest email covers the second patch, which implements a runtime escape hatch (`core.sha1dcBackend`) to switch between the Rust and C implementations without recompiling.

The escape hatch is a pragmatic addition, addressing concerns about adopting new code in a critical path. It allows users to fall back to the C implementation (`core.sha1dcBackend=c`) if issues arise, while the Rust backend remains the default when enabled at compile time. The patch is technically straightforward, wiring up function pointers in `sha1dc_git.c` and adding tests to verify the config knob works as expected. While the escape hatch itself is unlikely to be controversial, it reflects broader questions about the series: whether the performance gains justify the added complexity, whether the Rust backend’s optional nature sufficiently mitigates platform support concerns (e.g., NonStop), and whether the build system changes (e.g., Rust version requirements) introduce unacceptable overhead.

The thread is still under review, with no merge to Junio’s integration branches yet. Key participants so far include Schindelin, who frames the series as a collaborative optimization rather than a mandatory dependency. The remaining patches (3–4) will address thread-safety fixes for Windows and non-PTHREADS builds, which may draw further scrutiny. The series also intersects with ongoing debates about Rust’s role in Git, though its optional design may help sidestep some resistance. For now, the focus remains on validating the performance claims and ensuring the escape hatch and build system changes are robust.

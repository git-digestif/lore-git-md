This thread introduces a Rust-based SHA-1 backend for Git, aiming to deliver a ~3× performance improvement in `git index-pack` on Windows and large repositories. The series, authored by Johannes Schindelin via GitGitGadget, consists of four patches that wire up a Rust crate (`sha1dc`) via FFI, implement a runtime escape hatch (`core.sha1dcBackend`) to fall back to the C implementation, and address thread-safety for Windows and non-PTHREADS builds. The Rust backend is optional at compile time (`DC_SHA1_RS` flag) and defaults to "rust" when enabled, though users can switch back to the C implementation at runtime.

Junio C Hamano’s review highlights a key clarification: while the series is often framed as a compile-time feature, its real value lies in the runtime escape hatch, which allows users to toggle backends without recompiling. This makes the feature more practical but also raises a critical question about functional equivalence—whether the Rust and C implementations behave identically, particularly for collision detection. If they diverge, users could encounter inconsistent behavior, undermining the escape hatch’s purpose. Junio’s feedback also notes that the series title ("compile-time option") is misleading, as it downplays the runtime flexibility.

The series remains under review at v1, with no merge to any integration branch yet. Open questions include the need for independent performance validation, the build system’s complexity (e.g., `Cargo.toml` maintenance), platform support (e.g., NonStop’s lack of Rust toolchain), and the long-term maintenance burden of the Rust crate. Johannes Schindelin has positioned the series as a pragmatic performance win, emphasizing its optional nature and thread-safety fixes, but Junio’s review suggests that correctness and consistency will be focal points for further discussion. The broader Rustification debate (e.g., Randall S. Becker’s concerns about platform support) may also surface in reviews.

This is a **bugfix for the HTTP transport layer**, addressing a regression caused by libcurl 8.23.0’s new behavior of stripping credentials from the effective URL. The patch is under active review, with Jeff King (Peff) responding to Patrick Steinhardt’s suggestion to use `CURLINFO_REDIRECT_COUNT` instead of URL comparison for redirect detection.

Peff clarifies the distinction between *stripping* (removing credentials from the URL) and *flushing* (discarding cached credentials), noting that the latter is the real goal—preventing credentials from being sent to unintended destinations after a redirect. He explains why an earlier approach (stripping credentials immediately after extraction) failed: credentials extracted from the URL aren’t passed across process boundaries (e.g., to `http-push`), breaking existing tests.

On Patrick’s alternative, Peff acknowledges its elegance but reports it doesn’t work in practice. `CURLINFO_REDIRECT_COUNT` incorrectly reports a redirect for the initial authentication request (401 → 200), making it unreliable for detecting *meaningful* redirects. The thread now confirms that the original approach—comparing URLs while accounting for credential stripping—is the only viable solution. The patch remains well-motivated, with a clear regression scenario (libcurl 8.23.0+), thorough testing (existing test `t5550.15` now passes), and no unresolved technical objections.

Junio’s earlier endorsement ("very sensible") suggests this is on track for merging, though the discussion highlights that the fix is more nuanced than initially apparent. The patch touches `http.c` and adds a new field to `http_get_options`, but the on-disk format is unaffected. For readers following Git’s HTTP layer, this is a targeted fix worth noting—especially if you’re using libcurl 8.23.0 or later.

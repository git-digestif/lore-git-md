This is the v4 cover letter for Christian Couder’s five-patch series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators explicitly mark repositories as trusted for lazy fetching. The series replaces the earlier client-side `GIT_NO_LAZY_FETCH=fromAccepted` proposal with a server-controlled trust model, addressing the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration.

The v4 iteration is a direct response to Junio’s v3 review. The most significant change is in patch 5/5, which now reframes the environment-handling logic: instead of unconditionally setting `GIT_NO_LAZY_FETCH=1` and later relaxing it to `0` for trusted repositories, the code now checks whether the variable is already set by the operator and only sets it to `1` if it isn’t and the repository isn’t trusted. This preserves operator control and resolves Junio’s design nit about environment precedence. The commit message for patch 5/5 is also rewritten to clarify the three possible cases (operator-set environment, trusted repository, default behavior) and to emphasize that the configuration teaches the code to consult the allowlist rather than overriding the environment.

Other v4 changes are mechanical: patch 1/5 reverts `try_promisor_remotes()` and `lazy_fetch_objects()` to return `int` instead of `bool` (restoring the original return convention), improves documentation for these functions (particularly the ownership rules around the `to_free` argument), and better explains why it’s safe to skip `promisor_remote_init()` when lazy fetching is disabled. Patch 2/5 changes only the type of `struct safe_directory_data.is_safe` from `int` to `bool` (without renaming it), allowing its address to be passed directly to the new `path_allowlist_apply()` helper. Patch 4/5 changes the recursion depth counter from `unsigned long` to `int`, following Junio’s acceptance of the cast from `git_env_ulong()` to `int` as precedent-compliant.

The series remains a feature addition targeting the promisor-remote and upload-pack subsystems. It introduces new symbols (`path_allowlist_config_apply()`, `path_allowlist_apply()`, `upload_pack_lazy_fetch_trusted()`, `GIT_INTERNAL_LAZY_FETCH_DEPTH`) and modifies existing ones (`lazy_fetch_objects()`, `fetch_objects()`). The recursion safeguard in patch 4/5 (depth limit of 5) and the stricter path validation in patch 3/5 (absolute paths only, rejecting `.` and relative paths) directly address Junio’s v2 concerns about recursion risks and caller-specific rules. Documentation in patch 5/5 now explicitly warns against configuring a repository as its own promisor remote and clarifies that non-bare repositories must be allowlisted by their `.git` directory.

CI tests pass, and the series is rebased on a recent `master` commit (34f06850c1) to avoid merge conflicts. The unresolved high-weight concerns from v2—Junio’s scalability critique about memory overhead in `lazy_fetch_objects()` and brian m. carlson’s security objection—remain unresolved but are mitigated by the server-side trust model. Junio’s new review of patch 2/5 (flagging the silent-ignoring of non-existent paths in `safe.directory` logic) is inherited and not blocking, but it now risks propagating to `uploadpack.lazyFetchTrusted` if left unaddressed.

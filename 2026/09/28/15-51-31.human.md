This is the fourth and final patch in Johannes Schindelin’s four-part series introducing an optional Rust-based SHA-1 backend for Git, with a focus on thread safety. The patch makes the `sha1dc_init()` function thread-safe by ensuring the backend selection logic runs exactly once, even when called concurrently from multiple threads.

The change is straightforward but necessary: it wraps the existing backend-selection logic (`sha1dc_choose()`) in a `pthread_once()` call, which guarantees single initialization. The patch then duplicates this guard in every wrapper function (`initial_init`, `initial_clone`, `initial_update`, `initial_final`, `initial_discard`) to prevent data races during the brief window before the backend is chosen. This is a classic "double-checked locking" pattern in C, and while the code is repetitive, it is correct and matches the project’s low-level style.

The patch is uncontroversial on its own—thread safety in a hashing backend is a clear win—but it is a prerequisite for the Rust integration introduced earlier in the series. Without this fix, concurrent calls to `git_hash_init()` could corrupt the function pointers that switch between the C and Rust backends. The earlier patches in the series (particularly patch 3, which added `pthread_once()` shims for Windows and non-PTHREADS builds) laid the groundwork for this change.

For a busy reader, this patch is worth noting mainly as the capstone of the series: it ensures the performance gains from the Rust backend can be safely exploited in multi-threaded scenarios like `git index-pack`. The series as a whole remains under review, and this patch’s correctness will likely be taken for granted while the broader discussion focuses on the Rust integration itself.

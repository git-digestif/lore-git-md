This is the third and final patch in Thomas Bachem’s v5 series fixing a long-standing race condition in Git’s `rerere` subsystem. The series targets a robustness flaw where concurrent `rerere` operations contend for the shared `MERGE_RR.lock`, a problem exacerbated by the geometric maintenance strategy introduced in Git 2.54 but present in any scenario with multiple `rerere` writers.

This patch allows conflict-stopping commands—`git merge`, `git rebase`, `git am --3way`, `git stash pop`, and `git apply --3way`—to proceed with a warning if the lock remains held after the configurable timeout (`rerere.lockTimeout`, default 1000 ms). The warning, shown under `advice.mergeConflict`, tells the user to run `git rerere` manually before resolving the conflict, ensuring the preimage is recorded or a known resolution is replayed. Post-resolution recording (e.g., during `git commit` or `git am --continue`) and explicit `git rerere` commands still fail immediately if the lock is held, preventing silent corruption of the `MERGE_RR` file.

The patch touches the call sites in `apply.c`, `builtin/am.c`, `builtin/merge.c`, `builtin/stash.c`, and `sequencer.c`, passing the new `RERERE_SKIP_LOCKED` flag to `repo_rerere()`. The locking logic in `rerere.c` now distinguishes between commands that can safely skip rerere (conflict stops) and those that must fail (post-resolution recording). Documentation in `config/rerere.adoc` is updated to clarify the behavior, and the test suite (`t/t4200-rerere.sh`) adds thorough coverage for the new scenarios, including manual recovery via `git rerere` and the distinction between auto and manual maintenance.

This patch resolves the core trade-off between resilience (allowing conflict stops to proceed) and correctness (failing post-resolution recording). The implementation is clean, the test coverage is comprehensive, and the advisory message aligns with Git’s existing advice system. The series as a whole looks ready for final review and merging.

This is the first patch in a three-part bugfix series targeting the `rerere` subsystem. It introduces a configurable timeout (`rerere.lockTimeout`) for the `MERGE_RR.lock` file, allowing Git commands to wait briefly when the lock is held by another process (such as background `git rerere gc`) rather than failing immediately. The default timeout is 1 second, which is sufficient to cover typical `rerere gc` operations while preventing indefinite hangs.

The patch touches `rerere.c` to replace the `LOCK_DIE_ON_ERROR` behavior with a timeout-based wait, controlled by the new `rerere.lockTimeout` config key (documented in `Documentation/config/rerere.adoc`). The test suite (`t/t4200-rerere.sh`) adds thorough coverage for the new behavior, including scenarios where the lock is held by a background process, where the timeout expires, and where commands like `git rerere`, `git rerere forget`, and `git rebase --abort` fail gracefully when the lock cannot be acquired.

This is a well-motivated change that addresses a real-world race condition exacerbated by the geometric maintenance strategy introduced in Git 2.54. The implementation is clean, with clear documentation and comprehensive test coverage. The configurable timeout strikes a sensible balance between resilience and correctness, and the default value (1 second) is justified by the typical duration of `rerere gc` operations. No major objections remain, and the patch looks ready for integration.

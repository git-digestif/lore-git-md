This is a documentation patch series that moves Git’s `BreakingChanges` document into a proper manpage (`gitbreaking-changes(7)`). The motivation is straightforward: breaking changes affect users far more than developers, yet the current document is buried in the source tree and not easily discoverable. By converting it to a manpage, users can access it via `man gitbreaking-changes` or `git help breaking-changes`, making it visible to anyone who might be impacted by upcoming changes.

The series consists of four patches. The first converts the existing `BreakingChanges.adoc` into a manpage format, stripping out the original content. The second replaces message IDs (like `abcd1234`) with clickable URLs to the relevant commits or discussions. The third adds a note clarifying that the document is a living one, subject to updates. The fourth updates `git.adoc` to cross-reference the new manpage, ensuring users can find it through `git help git`.

The changes are mechanical but thoughtful. The new manpage is more than just a format shift—it’s an effort to make critical information more accessible. The commit message doesn’t overstate the impact, but the intent is clear: this is about improving user awareness, not just shuffling files. The series is marked as an RFC, suggesting the author is open to feedback on the approach, though the direction seems uncontroversial.

If you care about user-facing documentation or have opinions on how Git communicates breaking changes, this series is worth a look. It’s a small but meaningful step toward better visibility for changes that could disrupt workflows. The patches themselves are clean and well-scoped, so unless someone objects to the manpage’s tone or structure, this is likely to land without much drama.

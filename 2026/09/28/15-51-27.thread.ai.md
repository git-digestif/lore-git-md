Subject: [PATCH 0/4] Introduce Rust-based SHA-1 backend with performance gains
Series version: v1 (initial submission)
Originating author: Johannes Schindelin (via GitGitGadget)
Thread type: patch series (feature addition with performance focus)

Core problem or goal
Replace Git’s existing C-based SHA-1 implementation (sha1dc) with a new Rust-based backend (`sha1dc` crate) to achieve ~3× performance improvement in `git index-pack` on Windows and large repositories. The series adds the Rust crate as an **optional** compile-time feature, provides a runtime escape hatch (`core.sha1dcBackend=c`) to fall back to the C implementation, and includes thread-safety fixes for Windows and non-PTHREADS builds. The four patches wire up the Rust crate via FFI, implement the runtime escape hatch, add missing `pthread_once()` shims for platform compatibility, and ensure thread-safe initialization of the backend selection logic. Johannes Schindelin has clarified that the Rust and C backends differ in their collision-detection approach (SIMD-optimized UBC filter in Rust vs. original DV checks in C) but cover the same affine solution space over GF(2) and detect the same class of collisions under the original paper’s assumptions. The series is positioned as a performance optimization with an escape hatch, not a mandatory dependency.

Current status
Under review; no merge to any integration branch yet. Series remains at v1. Junio C Hamano’s question about **functional equivalence** has been addressed by Schindelin, who confirmed identical SHA-1 outputs for the same inputs but noted differences in collision-detection implementation (SIMD-optimized UBC filter in Rust vs. original DV checks in C). The static analysis and partial testing (AI-assisted) suggest robustness, but a full test suite run comparing both backends across architectures (x86_64, aarch64) is still pending. Carlson argues this version bump should be handled in a separate policy discussion, not as part of this feature series.

Key technical details
- **Files touched**: `hash.h`, `sha1dc_git.c`, `Makefile`, `Cargo.toml`, `compat/win32/pthread.*`, `thread-utils.h`, `t/t0013-sha1dc.sh`, plus new files `sha1dc_rs.h` and `src/sha1dc_rs.rs`.
- **New config key**: `core.sha1dcBackend` (values: `rust` or `c`; default `rust` when `DC_SHA1_RS` is defined).
- **Build system**:
  - `DC_SHA1_RS` flag enables the Rust backend (optional, not default).
  - `Cargo.toml` feature `sha1dc-rs` integrates the crate.
  - `Makefile` guards prevent conflicts with other SHA-1 backends (OpenSSL, BLK_SHA1).
  - **Rust version requirement**: 1.87 (higher than Git’s current minimum of 1.49.0 and the project’s informal target of 1.85.1).
- **FFI design** (patch 1):
  - Direct calls to Git’s `die()` from Rust for collision detection.
  - `Box`-managed `Hasher` instances with proper cleanup.
  - `#[no_mangle]` extern functions (`sha1dc_rs_init`, `sha1dc_rs_update`, etc.).
- **Runtime escape hatch** (patch 2):
  - Function pointers in `sha1dc_git.c` initialized on first call to `git_hash_init()`.
  - Config key `core.sha1dcBackend` switches between `rust` and `c` backends.
  - Proper resource cleanup for both backends.
  - Tests in `t/t0013-sha1dc.sh` verify config knob functionality and collision detection.
- **Thread-safety shims** (patch 3):
  - Windows: `pthread_once()` mapped to `InitOnceExecuteOnce()` via callback.
  - `NO_PTHREADS`: trivial single-threaded fallback with flag check.
  - Both shims return POSIX-compliant error codes.
- **Thread-safe initialization** (patch 4):
  - Replaces direct assignment of `sha1dc_init` to `sha1dc_choose` with wrapper functions (`initial_init`, `initial_clone`, etc.) guarded by `pthread_once()`.
  - Prevents data races during backend selection in multi-threaded scenarios (e.g., `git index-pack`).
  - Error handling: dies on `pthread_once()` failure with `strerror()`.
- **Performance claim**: 3× speedup for `git index-pack` on Windows (UCRT64), WSL, and macOS, attributed to the crate’s SIMD optimizations. Benchmark data (informal) included in the commit message for C vs. Rust 0.1.2/0.1.3 backends.
- **Collision detection**: Rust backend uses a SIMD-optimized UBC filter, differing from the C backend’s original DV checks but covering the same affine solution space over GF(2). Static analysis (AI-assisted) and partial testing confirm identical SHA-1 outputs for the same inputs; full cross-architecture validation pending.

Open questions and loose ends
- **Functional equivalence**: Schindelin’s response addresses Junio’s question but leaves room for further validation. Independent benchmarking and full test suite runs (x86_64, aarch64) are needed to confirm identical behavior across all inputs, especially edge cases in collision detection.
- **Rust version policy**: brian m. carlson’s review raises a **blocking procedural concern**: the series requires Rust 1.87, but Git’s `Cargo.toml` targets 1.49.0, and the project’s informal policy aligns with Debian stable (1.85.1). Carlson argues this version bump should be handled in a separate policy discussion, not as part of this feature series. The performance gains may not justify a unilateral version bump without broader consensus.
- **Rust in Git**: Potential resistance due to build complexity, platform support (e.g., NonStop lacks Rust toolchain), and the broader Rustification debate. The optional nature of the feature and runtime escape hatch may mitigate concerns, but the Rust version requirement remains a point of friction.
- **Performance validation**: Need for independent benchmarking beyond the author’s informal tests (e.g., on Linux, large monorepos, or CI environments).
- **Build system impact**: Whether the optional Rust feature adds unacceptable complexity (e.g., `Cargo.toml` maintenance, version pinning).
- **Platform coverage**: Whether the thread-safety fixes (patches 3/4 and 4/4) fully address non-PTHREADS and Windows edge cases.
- **Maintenance burden**: Long-term ownership of the Rust crate and its updates (e.g., security patches, SIMD optimizations).
- **Escape hatch necessity**: Whether the runtime config knob (`core.sha1dcBackend`) is sufficient or over-engineered for users who encounter issues.
- **Default behavior**: Whether the Rust backend should be the default when `DC_SHA1_RS` is enabled, or if users should explicitly opt in.
- **Series title**: The title ("compile-time option") remains misleading; the runtime escape hatch is the more user-relevant feature.
- **AI-assisted analysis**: Schindelin’s use of AI for static analysis may not satisfy reviewers who prefer human-verified proofs, especially for security-critical code.

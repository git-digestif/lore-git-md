This is the second patch in Thomas Bachem’s three-part v5 series fixing a race condition in Git’s `rerere` subsystem. It introduces a `--auto` mode for `git rerere gc` that skips the operation if the `MERGE_RR.lock` is held, aligning its behavior with other auto-maintenance tasks like `git pack-refs --auto`. The change is targeted: only `git rerere gc --auto` (triggered by `git maintenance run --auto` or `git gc --auto`) silently skips a held lock, while manual invocations of `git rerere gc` continue to wait and fail as before.

The patch touches `builtin/gc.c` and `builtin/rerere.c` to pass the `--auto` flag through the maintenance machinery, and updates `rerere.c` to handle the new `RERERE_NOWAIT` flag, which sets a zero timeout for the lock. Documentation (`rerere.adoc` and `git-rerere.adoc`) is updated to clarify the distinction between auto and manual invocations, and the test suite (`t4200-rerere.sh` and `t7900-maintenance.sh`) now verifies that `--auto` mode skips a held lock silently while manual runs fail. The tests also confirm that `--auto` is only accepted by the `gc` subcommand, preventing misuse with other `rerere` operations.

This patch directly addresses Patrick Steinhardt’s feedback from earlier iterations, which emphasized the need to distinguish between manual and auto-maintenance behavior. The implementation is clean: the `RERERE_NOWAIT` flag is orthogonal to `RERERE_READONLY`, and the lock acquisition logic remains unchanged except for the timeout adjustment. The test coverage is thorough, including edge cases for manual recovery and the interaction between auto and manual maintenance. No substantive objections remain, and the patch appears ready for integration.

# Thread deltas

## 2026/09/28

- [2026/09/28/15-51-27 by Johannes Schindelin via GitGitGadget <gitgitgadget@gmail.com>] Johannes Schindelin proposed a 4-patch series to add a compile-time option (DC_SHA1_RS) using the new Rust `sha1dc` crate for collision-detecting SHA-1, reporting roughly three times faster `git index-pack` on Windows due to SIMD optimizations, with an escape hatch via `core.sha1dcBackend=c` enabled by default.
- [2026/09/28/15-51-28 by Johannes Schindelin via GitGitGadget <gitgitgadget@gmail.com>] Patch 1/4 adds `sha1dc` as an optional Cargo feature toggled by the `DC_SHA1_RS` build option (requiring Rust 1.87), with benchmarks showing the Rust backend over three times faster than C on Windows (median 10.7s vs 32.9s) and about twice as fast on an M4 Mac.
- [2026/09/28/15-51-29 by Johannes Schindelin via GitGitGadget <gitgitgadget@gmail.com>] Patch 2/4 introduces the `core.sha1dcBackend` config option (values `rust` default or `c`) to select between the Rust and C sha1dc implementations at runtime when built with `DC_SHA1_RS`, implemented via function pointers initialized on the first `git_hash_init()` call.
- [2026/09/28/15-51-30 by Johannes Schindelin via GitGitGadget <gitgitgadget@gmail.com>] Patch 3/4 provides `pthread_once()` shims for Windows (using `InitOnceExecuteOnce`) and for `NO_PTHREADS` builds to support one-time concurrent initialization.
- [2026/09/28/15-51-31 by Johannes Schindelin via GitGitGadget <gitgitgadget@gmail.com>] Patch 4/4 makes `sha1dc_init()` thread-safe by using `pthread_once()` to ensure the backend-selection function pointers are initialized exactly once even when called concurrently from multiple threads.
- [2026/09/28/16-20-50 by Johannes Schindelin <Johannes.Schindelin@gmx.de>] Johannes Schindelin corrected two typos in the cover letter: "get for Windows" should read "in Git for Windows", and "were" should read ", and were".

## 2026/09/29

- [2026/09/29/07-30-10 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano pointed out that `sha1dc_choose()` enables runtime selection between the Rust and C sha1dc implementations, making the "compile-time" wording in the topic title misleading, and that runtime choice provides greater end-user value even though the developer-facing feature is compile-time.
- [2026/09/29/07-30-10 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano asked how close the two implementations are—whether they implement the same idea with differing details, or both faithfully implement the same paper and detect the same fudged input identically.

## 2026/10/03

- [2026/10/03/10-23-52 by Johannes Schindelin <Johannes.Schindelin@gmx.de>] Johannes Schindelin conceded that "compile-time" in the topic title is misleading because `sha1dc_choose()` lets users pick between the Rust and C implementations at runtime; he explained he had expected Junio to reject the runtime flag, which he sees as valuable only for binary-first distributions such as Git for Windows, not source-code-only releases like core Git.
- [2026/10/03/10-23-52 by Johannes Schindelin <Johannes.Schindelin@gmx.de>] Answering Junio's question about how close the two implementations are, Schindelin said they are quite different: per the Rust crate author's blog post, accelerating the faithful Rust port yielded only modest gains, while a more fundamental SIMD-based approach offered much bigger wins.
- [2026/10/03/10-23-52 by Johannes Schindelin <Johannes.Schindelin@gmx.de>] Schindelin reported findings from an AI-assisted analysis (disclaiming his own math background): the Rust and C implementations use the same collision-detection idea but a different UBC filter, order, and grouping of checks, while covering the same per-DV affine solution space over GF(2); the covered DV vectors, filtering, and recompression checks are equivalent, so both detect the same class of collisions under the paper's assumptions.
- [2026/10/03/10-23-52 by Johannes Schindelin <Johannes.Schindelin@gmx.de>] Schindelin stated the Rust implementation is robust and correct based on his light static analysis and substantial tests, but that he had not yet run his planned full Git test suite in a patched-in mode validating that C and Rust compute the same SHA-1 (intended for both x86_64 and aarch64); he posted before finishing all tests to give contributors an early look and invite collaboration.
- [2026/10/03/21-01-01 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson objected that the `sha1dc` crate's requirement of Rust 1.87 (versus Git's existing Rust 1.63 support) is a problem: although optional, Git declares compatibility with Rust 1.49.0 in Cargo.toml and wants everything to work there.
- [2026/10/03/21-01-01 by brian m. carlson <sandals@crustytoothpaste.net>] carlson noted the goal of supporting gccrs has not been met, as gccrs has not progressed enough to be viable approaching Git 3.0; he advocated supporting the Rust version in Debian stable plus oldstable for a year after a new stable, which reaches only Rust 1.85.1, not 1.87.
- [2026/10/03/21-01-01 by brian m. carlson <sandals@crustytoothpaste.net>] carlson proposed that any increase of the minimum Rust version be discussed in a separate series that adds or updates a policy document and bumps the version in Cargo.toml.

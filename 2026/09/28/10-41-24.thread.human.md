This thread is about a proposed `gitbreaking-changes(7)` manpage, which would convert Git’s existing `BreakingChanges` document into a proper manpage for better user visibility via `git help` and `man`. The series, now at v2 with five patches, was introduced by Kristoffer Haugsbakk and is technically complete, addressing all prior reviewer feedback. The goal is to make upcoming breaking changes more discoverable, particularly ahead of Git 3.0, while clarifying the document’s living-draft nature to avoid user confusion about outdated information.

The series has broad support for its usability improvements, with Patrick Steinhardt and D. Ben Knoble endorsing its goals. Junio C Hamano initially raised technical concerns about URL formatting, which were resolved in favor of plain URLs for better usability. However, Junio has now questioned the fundamental value of maintaining a historical record of breaking changes, comparing it to the limited utility of the Git 1.x-to-2.0 transition documentation. Kristoffer has proposed pragmatic solutions to address the post-Git-3.0 lifecycle of the document, such as adding a summary section for Git 3.0 changes and a note explaining the future-tense context, but Junio’s broader skepticism remains unresolved. The series is ready for integration from a technical standpoint, but its fate now hinges on Junio’s final decision about whether the document’s purpose justifies its inclusion in Git’s documentation. Minor merge conflicts with `ps/ref-storage-format` and `bc/restrict-hex-to-lowercase` will need to be resolved during integration.

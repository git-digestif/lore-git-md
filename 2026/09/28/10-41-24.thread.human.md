This thread is about converting Git’s plain-text `BreakingChanges` document into a proper manpage, `gitbreaking-changes(7)`, to make upcoming breaking changes more visible to users. Kristoffer Haugsbakk proposed the change as an RFC series of four patches, and the discussion is still in the early review phase.

The core idea—moving the document into the manpage system—has broad support, particularly from Patrick Steinhardt, who has reviewed the series in detail. The latest email focuses on the second patch, which replaces message-ID references with clickable `lore.kernel.org` URLs, a usability improvement that Patrick endorses. He also suggested a minor reorganization of the document to move internal-process details to the end, making it more user-friendly. The only technical critique so far is that the initial conversion patch was mechanically dense, making review harder, but this hasn’t derailed the series.

The series is still under RFC, so no new version has been posted yet. The open questions are mostly about the document’s long-term role: whether it should be retained after Git 3.0 (Patrick thinks yes) and how to handle its living-draft nature. The patches are documentation-only, touching only the `Documentation/` directory and build system files, with no code or on-disk changes. If the RFC is accepted, the series is effectively ready to merge, pending minor tweaks.

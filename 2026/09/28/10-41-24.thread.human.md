This thread is about converting Git’s `BreakingChanges` document into a proper manpage, `gitbreaking-changes(7)`, to make upcoming breaking changes more visible to users via `git help` and `man`. The series, now at v2 with five patches from Kristoffer Haugsbakk, is technically complete and addresses all prior feedback, including structural improvements, URL formatting, and build system integration. The only remaining question is whether Junio C Hamano, the maintainer, will accept the proposed solution for the document’s post-Git-3.0 lifecycle—adding a summary section for Git 3.0 changes and a note explaining the future-tense context—or if he will request further changes or even reconsider the document’s inclusion entirely.

Kristoffer Haugsbakk has driven the effort, incorporating feedback from Patrick Steinhardt and Junio, and explicitly stated the series is ready for integration. Junio initially raised concerns about the document’s long-term utility, comparing it to the Git 1.x-to-2.0 transition and implying that historical records of breaking changes may not be valuable beyond the immediate pre-release period. His latest email questions whether maintaining the document is worthwhile at all, leaving the series’ fate uncertain. The patches touch only documentation files (`gitbreaking-changes.adoc`, `BreakingChanges.adoc`, `git.txt`, `command-list.txt`, `Makefile`, and `meson.build`) and introduce no new code or on-disk changes. Integration will require minor conflict resolution with two other in-flight topics, but the series is otherwise unblocked from the author’s side.

This thread is about converting Git’s `BreakingChanges` document into a proper manpage, `gitbreaking-changes(7)`, to make upcoming breaking changes more visible to users via `git help` and `man`. The series, now at v2 with five patches, was proposed by Kristoffer Haugsbakk and has addressed all prior feedback, including structural improvements, URL formatting, and build system integration.

The core goal is to improve discoverability—currently, the document is only accessible via an obscure `git --html-path` method, which isn’t widely known. The series also clarifies the document’s living-draft nature to avoid confusion about outdated information. The main open question was whether the document should be retained long-term, but Junio C Hamano has now tentatively approved the series, deferring to Kristoffer’s earlier proposals for post-Git-3.0 handling: either treating it as a living draft (deleting old entries after each release) or keeping only the most recent breaking-change discussion. Patrick Steinhardt had previously suggested a pragmatic middle ground—retaining the document until Git 3.0 is widely adopted—which aligns with the current direction.

The series is now unblocked, with no further changes expected from the author. Junio’s latest email signals readiness for integration, pending minor merge conflicts with `ps/ref-storage-format` (in `master`) and `bc/restrict-hex-to-lowercase` (in `seen`). The broader debate about the document’s long-term utility has been set aside in favor of immediate usability improvements. Key participants—Kristoffer, Patrick, and D. Ben Knoble—have all endorsed the series, while Junio’s initial skepticism has been resolved with a practical compromise. The next step is for Junio to pick up the series and resolve the conflicts.

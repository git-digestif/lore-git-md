This thread is about an RFC patch series to introduce a `gitbreaking-changes(7)` manpage, converting Git’s existing `BreakingChanges` document into a proper manpage for better user visibility. Kristoffer Haugsbakk is the author, and the series is now complete and under review.

The goal is to make Git’s upcoming breaking changes more discoverable by moving the plain-text `BreakingChanges` document into a manpage accessible via `git help` and `man`. The series also clarifies the document’s living-draft nature to prevent user confusion. All substantive feedback from Patrick Steinhardt’s review has been addressed, including replacing message-ID references with clickable URLs, reordering sections, and fixing minor formatting issues. Patrick endorsed the proposed three-step restructuring plan, and the forward-looking question about the document’s lifecycle post-Git 3.0 has been resolved—it will retain a historical section for Git 3.0, with Git 4.0 discussion deferred.

Junio C Hamano recently reviewed the second patch, which replaces message-ID references with URLs. While he endorses the usability goal, he suggests a hybrid approach: embedding both the URL and the raw message-ID in the source (e.g., `cf. https://lore.kernel.org/git/xmqqa59i45wc.fsf@gitster.g/[<xmqqa59i45wc.fsf@gitster.g>^]`). This would preserve the message-ID for future reference while keeping the link clean for readers. He also notes the need for URL encoding in some cases. This is a refinement request, not a rejection, and aligns with existing Git documentation conventions. The series remains under review, with this as the sole open discussion point. No new patch version has been posted yet.

This thread is about converting Git’s plain-text `BreakingChanges` document into a proper manpage, `gitbreaking-changes(7)`, to make upcoming breaking changes more visible to users via `git help` and `man`. The series, now in its second version (v2), is technically complete and addresses all prior feedback, including structural improvements, URL formatting, and build system integration. The author, Kristoffer Haugsbakk, has stated the series is ready for integration, but a new question from Junio C Hamano about the document’s post-Git-3.0 lifecycle had remained unresolved—until now.

Kristoffer has proposed a pragmatic solution to Junio’s concern: instead of rewriting every entry after Git 3.0 ships, the document could add a new section summarizing what changed in 3.0, prefaced by a note explaining that the rest of the document is written in the future tense for users reading from version 2.98. This avoids a large-scale rewrite while clarifying the temporal context. The proposal directly addresses the maintainer’s question, which was the last open blocker for integration. All other feedback—from Patrick Steinhardt, Junio, and D. Ben Knoble—has been incorporated, and the series is now unblocked from the author’s side.

The series touches documentation files (`gitbreaking-changes.adoc`, `BreakingChanges.adoc`, `git.txt`, `command-list.txt`) and build system files (`Makefile`, `meson.build`), but introduces no new symbols or on-disk changes. It conflicts only with two in-flight topics (`ps/ref-storage-format` and `bc/restrict-hex-to-lowercase`), requiring their additions to be moved during integration. The next step is Junio’s decision on whether the proposed lifecycle solution is acceptable or if further documentation tweaks are needed before the series can be merged. No further technical work appears required from the author.

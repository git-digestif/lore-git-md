This thread is about converting Git’s `BreakingChanges` document into a proper manpage, `gitbreaking-changes(7)`, to make upcoming breaking changes more visible to users via `git help` and `man`. Kristoffer Haugsbakk proposed the series, which is now in its second version with all prior feedback addressed. The technical work—moving content, updating URLs, and integrating the new manpage into the build system—is complete, and the series is ready for integration.

The main open question is whether the document is worth maintaining at all. Junio C Hamano has questioned its long-term value, comparing it to the Git 1.x-to-2.0 transition documentation, which saw limited use. Kristoffer has proposed pragmatic solutions, such as treating the document as a living draft (deleting old entries after a new release) or retaining only the most recent breaking-change discussion. Patrick Steinhardt has now weighed in, arguing that the document remains useful for users upgrading across multiple versions, even if they don’t land directly on Git 3.0. His suggestion is to keep it until all supported distributions have adopted Git 3.0, providing a concrete, time-bound justification.

The series awaits Junio’s final decision, though Patrick’s input may help steer it toward a middle ground. Minor merge conflicts with `ps/ref-storage-format` (in `master`) and `bc/restrict-hex-to-lowercase` (in `seen`) will need to be resolved during integration, but no further changes are expected from the author. The thread is effectively unblocked on the technical side, with the remaining discussion focused on the document’s purpose and lifecycle.

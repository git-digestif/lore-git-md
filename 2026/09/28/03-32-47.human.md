This is a substantive review comment in the ongoing Git version numbering and defaults modernization thread. Jeff King (Peff) responds to Phillip Wood’s proposal for a `core.defaults` meta-config variable, which would allow users to opt into "modern defaults" without forcing disruptive changes on everyone. Peff’s reply is skeptical, questioning the practical value of `core.defaults` and suggesting that the project’s current approach—switching defaults directly and letting users override them—may be simpler and equally effective.

Peff’s critique centers on two points. First, he argues that `core.defaults` doesn’t solve the core problem of breaking scripts or automated workflows: if a default change would break something, so would enabling `core.defaults=modern`. This undercuts the proposal’s goal of reducing disruption, since the escape hatch (overriding individual settings) already exists. Second, he questions whether `core.defaults` meaningfully addresses the social challenge of default changes—namely, that *someone* will always be annoyed by a change, and the project’s tendency to favor the status quo is often a safe default precisely because it’s hard to predict which change will cause the least friction.

The review is substantive but not dismissive. Peff acknowledges the convenience of grouping related config options (e.g., `feature.triangular` for triangular workflows) but sees `core.defaults` as an unnecessary abstraction. His alternative—switching defaults directly and letting users opt out—aligns with the project’s historical approach and avoids adding complexity to the config system. The comment doesn’t engage with Phillip’s consequentialist framing (weighing net benefits of default changes) but focuses narrowly on the mechanics of `core.defaults`.

This reply advances the thread by sharpening the trade-offs of Phillip’s proposal. It suggests that the real challenge isn’t *how* to change defaults, but *whether* the project can gather enough data to justify the disruption—a point Junio also raised earlier. The discussion now hinges on whether `core.defaults` is a pragmatic middle ground or an over-engineered solution to a problem that could be addressed more simply. Peff’s skepticism is likely to resonate with contributors who prioritize minimalism in Git’s design.

This is the first patch in a three-part bugfix series targeting the `rerere` subsystem. It introduces a configurable timeout (`rerere.lockTimeout`) for the `MERGE_RR.lock` file, replacing the previous behavior where any process failing to acquire the lock would immediately die. The default timeout is 1000 milliseconds (1 second), which is sufficient to cover typical `git rerere gc` operations that prune stale entries. The patch touches `rerere.c` to implement the timeout logic, updates `Documentation/config/rerere.adoc` to document the new configuration option, and adds comprehensive test coverage in `t/t4200-rerere.sh` to verify the behavior under various scenarios (e.g., waiting for the lock, failing after timeout, and handling explicit `rerere` commands like `forget`, `clear`, and `gc`).

The motivation is clear: the geometric maintenance strategy introduced in Git 2.54 exacerbated a long-standing race condition where concurrent `rerere` operations (e.g., a rebase encountering a conflict while background maintenance runs `git rerere gc`) would contend for the lock, causing the second process to crash. The timeout-based approach is a pragmatic stopgap that balances resilience (allowing operations to proceed after a brief wait) with correctness (failing if the lock remains held). The patch is well-structured, with a clean separation of concerns (configuration, locking logic, and error handling) and thorough test coverage that includes edge cases like `rebase --abort` failing on a held lock.

This patch is ready for final review. It addresses the core locking issue without introducing new behavior (that comes in patches 2 and 3), and the changes are minimal and focused. The default timeout of 1 second is reasonable for the common case, and the configuration option allows users to adjust it if needed. The test suite verifies that the timeout works as expected and that explicit `rerere` commands still fail immediately if the lock is held, preserving the existing safety guarantees. No major objections are expected, as the approach aligns with prior feedback from Junio C Hamano and Patrick Steinhardt.

This is **Patch 12/13 of the v4 MinGW/Windows build and runtime adjustments series**, the centerpiece of the effort to allow direct invocation of `git.exe` instead of the Git wrapper. The patch enables Git for Windows to add `git.exe` directly to the user’s `PATH` without exposing unnecessary executables like `wish.exe`, addressing GitHub issue [git-for-windows/git#2283](https://github.com/git-for-windows/git/issues/2283).

The core change is in `compat/mingw.c`, where a new block in `setup_windows_environment()` detects the absence of the `MSYSTEM` environment variable and initializes it to the value of the `ENSURE_MSYSTEM_IS_SET` macro (which is set in `config.mak.uname` to the current `MSYSTEM` value). It also prepends `$HOME/bin`, `/mingw64/bin`, and `/usr/bin` to `PATH`, ensuring scripts and tools are found in the expected locations. The logic is guarded by `#ifdef ENSURE_MSYSTEM_IS_SET` and further protected by `#if !defined(RUNTIME_PREFIX) || !defined(HAVE_WPGMPTR) || !defined(MINGW_PREFIX)` to avoid compilation errors on non-Windows or non-Runtime-Prefix builds.

The build system is updated to pass the `ENSURE_MSYSTEM_IS_SET` and `MINGW_PREFIX` macros to the compiler: `config.mak.uname` adds them to `COMPAT_CFLAGS`, CMake hard-codes them per platform (`MINGW64`, `CLANGARM64`, `MINGW32`), and Meson introduces two new options (`msystem` and `mingw_prefix`) that default to empty strings but can be overridden at build time. The test `t/t0060-path-utils.sh` is extended with a new `MINGW,RUNTIME_PREFIX` test that verifies `MSYSTEM` is set correctly and `PATH` is adjusted as expected when `git.exe` is invoked directly.

The patch is Windows-specific and does not affect non-Windows platforms. It is a prerequisite for Git for Windows’ migration from MINGW64 to UCRT64 and has been validated by Johannes Sixt (personal builds since November 2025, GitHub CI passes). Junio’s suggestion to guard the empty-`MSYSTEM` logic with an `ifneq (,$(MSYSTEM))` in the build system was declined by the author, who argued the edge case is too unlikely to warrant the complexity. The series is otherwise ready for `next`.

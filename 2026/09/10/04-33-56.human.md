This is a brief but substantive review comment in the ongoing `defaultBranchName` advice documentation thread. Jeff King (Peff) points out that Junio C Hamano’s refactoring patch—converting `advice_enabled()` + `advise()` call sites to `advise_if_enabled()`—misses cases where the conditional logic is more complex, such as when an additional boolean flag (`no_graft_file_deprecated_advice`) gates the advice. He provides a concrete example in `commit.c` where the transformation would still be possible but less straightforward.

Peff’s larger concern is whether the resulting output would feel cluttered: `advise_if_enabled()` always appends turn-off instructions (e.g., “Disable with `git config --global advice.foo false`”), even when the advice is already concise. This could make the output more verbose than necessary, especially for one-line messages. While the refactoring patch itself is low-risk and mechanically sound, Peff’s question touches on the broader design tension in the advice subsystem: should turn-off instructions be shown *only* when explicitly requested (as with `advise_if_enabled()`), or should they be omitted by default for brevity (as with the older `advise()` pattern)? The thread has already settled that the two helpers serve different purposes, but Peff’s comment suggests the trade-off may still be worth revisiting for specific cases.

The observation is narrowly scoped to the refactoring patch and does not affect the core `defaultBranchName` fix (v3 of which remains ready for review). However, it could prompt a follow-up discussion about whether to refine the Coccinelle rule to exclude complex conditionals or to revisit the subsystem’s design in a future series. For now, the refactoring patch is still viable, but Peff’s feedback highlights a potential usability downside that reviewers may want to weigh.

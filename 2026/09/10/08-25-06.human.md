This is the final note in the thread for the v4 iteration of Thomas Bachem’s patch series that defers auto maintenance until the end of sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`). The series is now technically complete and ready for merging.

Junio C Hamano has already signaled intent to queue it ("Will queue"), so it will enter `seen` shortly and, if no new issues surface, will graduate to `next` and eventually to `master`. The code itself is unchanged from v3; only the commit messages have been tightened in response to Junio’s critique about modern verbosity. Thomas took Junio’s suggested wording for the third patch, corrected a minor inaccuracy (clarifying that the `maintenance.auto=false` setting is passed only to `commit`, `merge`, and `exec` commands, not to all spawned commands), and shortened the first two patches to match the new concision standard. The result is a set of messages that are about a third the length of the originals, with no loss of substance.

The series addresses a real inconsistency: the apply backend already defers auto maintenance until sequence completion, while the sequencer backend ran it during intermediate steps, risking lock contention and inconsistent behavior. The solution is clean: disable auto maintenance for individual commands during the sequence and run it exactly once at the end. The design now consolidates the `run_auto_maintenance()` call into a single exit path per command, matching the apply backend’s behavior and responding to Patrick Steinhardt’s preference for a unified exit path. The implementation touches the sequencer, config, and auto-maintenance subsystems, adds a reusable `git_config_append_parameter()` helper with documented format, and extends test coverage in `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh` using `GIT_TRACE2_EVENT` to verify the new behavior.

The only loose end is a test coverage gap identified by Phillip Wood: the rebase test does not currently verify suppression during conflict resolution because the test scenario does not trigger a conflict. The test still passes, but it does not exercise the intended code path. This is a watch item rather than a blocker, and the author may address it in a follow-up patch. All substantive feedback from Phillip Wood, Patrick Steinhardt, and Junio has been addressed, and the series is well-motivated, well-tested, and uncontroversial.

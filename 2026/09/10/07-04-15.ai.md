This is a substantive review of the fifth patch in the `git last-modified` Bloom filter optimization series (v4 5/6). Patrick Steinhardt raises two points about the patch’s rationale and performance trade-offs.

The patch introduces a pre-filter in `maybe_changed_path()` that checks whether a commit *might* have changed any path matching the user’s pathspec before proceeding to per-path diffs. For `--show-trees`, it uses the new `revs_maybe_changed_in_bloom_with_parents()` helper to also check parent directories, avoiding false negatives when a commit touches a sibling file (e.g., `a/other` for pathspec `a/b/c`).

Patrick’s first comment questions whether the pre-filter might sometimes do redundant work, since the same Bloom filter checks could be repeated later for individual paths. He acknowledges the trade-off is likely worthwhile—fewer pathspecs than expanded paths—but suggests the commit message should explicitly state the performance expectation. His second comment asks for a benchmark demonstrating the benefit, noting that while the logic is sound, the *why* (performance gain) is under-documented. The review is narrowly focused on the patch’s motivation and does not identify correctness issues. The author will need to address these points in a reroll.

Subject: [PATCH] refs/files-backend: avoid spurious packed-refs lock when deleting root refs
Series version: standalone patch (no series)
Originating author: Ariel Keselman
Thread type: bugfix patch

Core problem or goal
Fix a bug in the `refs/files` backend where an unnecessary lock on `packed-refs` is taken when deleting root refs (e.g., `HEAD`, `refs/heads/main`). Root refs cannot be packed, so the lock is redundant and causes spurious errors in linked worktrees when the shared metadata directory is read-only.

Current status
Under review; no prior versions. Patch modifies `files_delete_refs()` in `refs/files-backend.c` to skip the `packed-refs` lock for root refs. Includes seven new regression tests in the patch that fail without the fix and pass with it. Broader test suites (refs, worktree, sequencer) also pass, indicating no regressions.

Key technical details
- File modified: `refs/files-backend.c`
- Function modified: `files_delete_refs()`
- Helper added: `is_root_ref()`
- New behavior: skips `packed-refs` lock acquisition when deleting root refs
- Test coverage: seven new regression tests in `t/t0600-reffiles-backend.sh`; no changes to on-disk format or CLI
- Subsystems touched: refs backend (files), worktree handling

Open questions and loose ends
- **Test coverage**: Patrick Steinhardt suggests the seven new tests are excessive; one test of a root ref in one state (existing) would suffice. He also questions the use of `core.packedRefsTimeout` in tests, as it does not affect the outcome.
- **Missing edge case**: A transaction that updates both a root ref and a non-root ref while a `packed-refs.lock` already exists should fail (because the non-root ref requires the lock), but the current patch might incorrectly allow the root ref portion to proceed. This edge case is not currently tested.

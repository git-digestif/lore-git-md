This is the **v10 iteration of a feature patch series** introducing the `receive-report` hook, a server-side filter for Git’s push status reports. The series is **queued in `next`** and addresses all prior feedback, including a **memory leak fix** in the error-handling path and a **critical design flaw** (a `BUG()` call when clients omit the `report-status` capability). The hook is motivated by GitLab’s need to implement MVCC (multi-version concurrency control), where the status report must reflect the repository state *after* all server-side operations—including those beyond `ref_transaction_commit()`—are complete.

The series consists of four patches:
1. **Documentation-only**: Adds the `PROC-RECEIVE HOOK` section to `git-receive-pack.adoc` and documents the `receive-report` hook in `githooks.adoc`, with a `Helped-by` credit to Patrick Steinhardt.
2. **Refactoring (critical fix applied)**: Replaces static variables tracking report status version with an `enum report_status_version` (values: `REPORT_STATUS_UNKNOWN`, `REPORT_STATUS_V0`, `REPORT_STATUS_V2`). The `REPORT_STATUS_UNKNOWN` case now silently `break`s instead of calling `BUG()`, resolving Junio C Hamano’s concern about clients that omit the `report-status` capability.
3. **Refactoring**: Extracts status-report generation into a reusable `generate_report()` helper, unifying `report()` and `report_v2()` into a single function. This addresses Patrick Steinhardt’s substantive review feedback from v6.
4. **Core implementation (memory leak fixed)**: Introduces the `receive-report` hook, which acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband. A non-zero exit rewrites all ref status lines to `"receive-report hook failed"` and overwrites `cmd->error_string` fields (now with conditional free to prevent leaks). The commit message explicitly acknowledges the **consistency trade-off**: the hook can report a push as failed (`ng`) while still committing ref updates, violating Git’s traditional principle that remote-tracking branches reflect the server’s state. This divergence is justified by GitLab’s MVCC use case. **Test coverage**: 257 lines in `t/t5412-receive-report-hook.sh`, including a new test for the memory leak fix in the error path.

**Key technical details**:
- New helper functions: `generate_report()`, `run_receive_report_hook()`, `override_cmds_error()`.
- New flag: `error_string_owned` (tracks ownership of `cmd->error_string` to prevent leaks).
- The hook is **not integrated with the config-based hook infrastructure** (designed for parallelizable notifications, not bidirectional filters).
- **Test coverage limitation**: The test suite cannot verify behavior when the client does not request a status report (e.g., older Git clients like v1.0.0), as the built-in `git send-pack` client always requests a report if the server advertises the capability. Jeff King’s review confirms this gap is a practical limitation, not a design flaw.

**Recent changes in v10**:
- Fixed a memory leak in `override_cmds_error()` by conditionally freeing `cmd->error_string` before overwriting it, using the new `error_string_owned` flag.
- Added a test case to trigger the error path in `override_cmds_error()`, ensuring the leak fix is verifiable.
- No code changes to address Oswald Buddenhagen’s **substantive review** of the commit message in patch 4/4, which critiques its verbosity and suggests trimming technical details in favor of emphasizing the "why" (GitLab’s MVCC use case and the consistency trade-off). The author may revise the message for conciseness, but the feedback is non-blocking.

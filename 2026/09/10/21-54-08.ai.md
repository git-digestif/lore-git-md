This is the third patch in the v10 series introducing the `receive-report` hook. It refactors the status-report generation logic in `builtin/receive-pack.c` by extracting the redundant `report()` and `report_v2()` functions into a single reusable `generate_report()` helper. The new helper takes an `enum report_status_version` parameter to handle both protocol versions (v0 and v2) uniformly, eliminating the need for separate functions. The patch is purely internal and does not change user-visible behavior, but it prepares the codebase for the upcoming hook implementation in patch 4/4 by centralizing the report-generation logic.

The diff consolidates the two nearly identical functions into one, reducing code duplication. The `generate_report()` helper writes the status report to a caller-provided `strbuf`, which the `report()` function then sends to the client via sideband or stdout. The `report_v2()` function is removed entirely, and the `report()` function now delegates to `generate_report()` with the appropriate version parameter. The change is mechanical and well-motivated, addressing Patrick Steinhardt’s substantive review feedback from v6 about missed refactoring opportunities.

Key technical details include the new `generate_report()` function signature, which takes a `strbuf *buf` for output, the `commands` list, the `unpack_status` string, and the `report_status_version` enum. The helper handles both protocol versions by conditionally including detailed ref-update reports (e.g., `option refname`, `option old-oid`) only for `REPORT_STATUS_V2`. The patch also updates the `report()` function to accept the `version` parameter and pass it through to `generate_report()`. No new tests are added, as the behavior remains unchanged and the existing test suite (including the 257-line `t/t5412-receive-report-hook.sh`) implicitly verifies the refactoring.

The commit message is concise and accurately describes the refactoring goal: enabling reuse of the report-generation logic for the upcoming `receive-report` hook. The `Helped-by` credit to Patrick Steinhardt reflects his earlier review identifying the redundancy between `report()` and `report_v2()`. This patch is uncontroversial and aligns with the series’ broader goal of making the status-report machinery more modular. The refactoring is a clear improvement, reducing maintenance burden and paving the way for the hook implementation in the next patch. No further changes are expected.

This is the v10 iteration of a feature patch series introducing the `receive-report` hook for `git receive-pack`. The series is now queued in `next` and ready for final review before graduating to `master`.

The hook allows server administrators to intercept and modify the status report sent to clients after ref updates are committed but before the response is finalized. It receives the pkt-line encoded report on stdin and replaces it with its stdout; stderr is forwarded to the client via the sideband channel. A non-zero exit status marks all refs as rejected, though ref updates are not rolled back. This is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the final status must reflect post-push operations beyond `ref_transaction_commit()`.

The v10 update fixes a memory leak in the error-handling path, where `override_cmds_error()` now conditionally frees the existing `cmd->error_string` before overwriting it. This addresses Junio C Hamano’s substantive review identifying a leak in the non-zero hook exit path. The series also includes a new test case to verify the fix and ensure the hook correctly handles pre-existing `ng` statuses from `proc-receive`.

All prior feedback has been addressed, including the critical `BUG()` flaw in patch 2/4 (resolved in v9), documentation refinements, and refactoring to unify redundant report-generation functions. The commit message in patch 4/4 now explicitly acknowledges the consistency trade-off—decoupling reported status from actual repository state—justifying it with GitLab’s MVCC use case. Oswald Buddenhagen’s recent review critiqued the message’s verbosity, suggesting a focus on the "why" rather than technical details, but no code changes are implied.

The series is well-motivated, thoroughly tested (257 lines in `t/t5412-receive-report-hook.sh`), and addresses a real gap in Git’s server-side extensibility. The implementation is clean, and the hook’s design as a single-script filter avoids integration with the config-based hook infrastructure for sound technical reasons. The only remaining loose end is the acknowledged test coverage gap for clients that do not request status reports, but Jeff King’s review confirms this is a practical limitation of the test infrastructure, not a design flaw. The series is on track for `master`.

This is patch 7/9 in Patrick Steinhardt’s ODB alternates refactoring series, now in its fifth iteration. The patch implements the core design change: alternates are now written during ODB creation via a new `odb_create_on_disk_options` struct, using Git’s standard lockfile API to ensure atomic writes. This resolves the TOCTOU race and concurrent access concerns Junio raised in the first version, and it prepares for the removal of the `write_alternates()` callback in patch 9.

The implementation touches the "files" ODB backend (`odb/source-files.c`), the ODB source interface (`odb/source.h`), and the repository setup code (`setup.c`). In `odb/source-files.c`, the `create_on_disk` callback now accepts an options struct carrying a `strvec` of alternates paths. The callback reads any preexisting alternates (e.g., from templates), deduplicates them with the new entries using a `strset`, and writes the combined set atomically using `commit_lock_file()`. After writing, the ODB is reprepared to activate the new alternates. Error handling is thorough: the lockfile is rolled back on failure, and resources are properly cleaned up. The `odb/source.h` header introduces the `odb_create_on_disk_options` struct and updates the `create_on_disk` callback signature, while `setup.c` updates `create_object_database()` to pass an empty options struct (the alternates `strvec` will be wired up in patch 8).

Karthik Nayak’s substantive review of v4 raised two technical points about this patch. First, he noted that the code checks for `ferror()` only after writing all alternates, rather than after each `fprintf()` call, which could leave the alternates file in a partially written state if an error occurs mid-write. While the lockfile mechanism prevents corruption, checking `ferror()` inside the loop would fail fast and avoid writing partial data. Second, he asked whether backends should formalize error codes to distinguish "alternates not supported" from other failures, probing the ODB interface’s clarity and extensibility. The current design leaves backend-specific behavior undocumented, which could lead to inconsistent error handling. These points remain open but do not block the patch’s core functionality.

The patch is well-crafted and directly addresses the security concern from v1. The lockfile adoption is uncontroversial, and the error handling is robust enough for production use, though Karthik’s feedback may prompt minor improvements in a future iteration. This is a key step in the ODB abstraction effort, making alternates an implementation detail of the "files" backend. The patch is ready for integration, with the only remaining loose ends being the error handling refinements suggested by Karthik.

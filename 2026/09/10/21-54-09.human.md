This is the **core implementation patch** of a feature series introducing the `receive-report` hook, a server-side filter for Git’s push status reports. The series is **queued in `next`** and this patch (4/4) is the culmination of the effort, adding the actual hook logic after three preparatory refactoring and documentation patches.

The hook addresses GitLab’s need to implement MVCC (multi-version concurrency control) on the server side, where the status report must reflect the repository state *after* all server-side operations—including those beyond `ref_transaction_commit()`—are complete. It acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband. A non-zero exit rewrites all ref status lines to `"receive-report hook failed"` and overwrites `cmd->error_string` fields (now with a memory leak fix applied in v10). The commit message explicitly acknowledges the **consistency trade-off**: the hook can report a push as failed (`ng`) while still committing ref updates, violating Git’s traditional principle that remote-tracking branches reflect the server’s state. This divergence is intentional and justified by GitLab’s use case, where conservative client-side behavior (not updating remote-tracking branches when the hook reports `ng`) is the desired outcome.

The implementation touches `builtin/receive-pack.c`, adding three new helper functions: `run_receive_report_hook()` (which spawns the hook process and handles stdin/stdout/stderr), `override_cmds_error()` (which rewrites all ref error strings on non-zero exit, now with conditional free to prevent leaks), and the integration point in `report()`. The hook is **not integrated with the config-based hook infrastructure**, which is designed for parallelizable notifications rather than bidirectional filters. The single-script design is consistent with the existing `proc-receive` hook and avoids the complexity of piping multiple scripts’ outputs.

Test coverage is thorough, with **257 lines in `t/t5412-receive-report-hook.sh`** covering passthrough behavior, failure modes, stdin/stdout handling, sideband relay, and the hook’s ability to modify both the `unpack` status line and individual ref statuses. The v10 iteration includes a new test case for the memory leak fix in `override_cmds_error()`, ensuring the error path is verifiable. The only **known limitation** is the inability to test behavior when the client does not request a status report (e.g., older Git clients), as the built-in `git send-pack` client always requests a report if the server advertises the capability. Jeff King’s review confirms this gap is a practical limitation of the test infrastructure, not a design flaw.

The patch is **feature-complete and ready for final review**, with all prior feedback addressed. The only remaining open question is whether the author will revise the commit message in response to Oswald Buddenhagen’s **substantive review**, which critiques its verbosity and suggests trimming technical details in favor of emphasizing the "why" (GitLab’s MVCC use case and the consistency trade-off). The feedback is non-blocking, and the series remains on track for graduation to `master`.

## 2026/09/18

- [2026/09/18/07-12-32 by Johannes Schindelin <Johannes.Schindelin@gmx.de>] Johannes Schindelin defended keeping the `slen` parameter in `check_signature()` against Junio's suggestion to drop it: `slen` has been part of that signature since 02769437e142 (2021-12-09), and it is used twice inside the function, including in `fmt->verify_signed_buffer(sigc, fmt, signature, slen)`, where both `verify_gpg_signed_buffer()` and `verify_ssh_signed_buffer()` rely on `signature_size` to decide how many bytes to write to the temporary file handed to the external verifier — falling back to `strlen()` would truncate a signature with an embedded NUL before verification, a correctness regression in the cryptographic path. He also noted that applying "audit today's callers and assume it holds" reasoning risks repeating the failure mode Peff's February 2024 conclusion missed after c8762c30df5b added `convert_tag_object()` as a non-strbuf caller of `parse_signed_buffer()`.
- [2026/09/18/07-12-32 by Johannes Schindelin <Johannes.Schindelin@gmx.de>] Johannes Schindelin corrected the claim that all `check_signature()` callers pass a strbuf's own buf/len pair: six of seven do (`commit.c`, `tag.c`, `builtin/fast-import.c`, `fmt-merge-msg.c`, `log-tree.c` twice), but `builtin/receive-pack.c` passes the offset sub-buffer `push_cert.buf + bogs` with `push_cert.len - bogs`.
- [2026/09/18/08-59-11 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano maintained that the audit question was whether the `slen` callers pass is redundant (answer: yes), that removing it would force all current and future callers to pass NUL-terminated strings, but concluded that since the code is already written and reviewed, it is not worth going back and changing it as the difference is not large enough either way.

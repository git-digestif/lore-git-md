Thread identity: Bug report and proposed fix for `git rerere remaining` incorrectly skipping consecutive conflicted paths with only stage-1 index entries. Originating author: Mikko Rantalainen. Thread type: bug report with reproducer and suggested fix.

Core problem or goal: The `git rerere remaining` command (and by extension `git mergetool`) fails to report all unresolved conflicts when consecutive conflicted paths in the index contain only stage-1 entries. This causes `git mergetool` to exit prematurely after resolving only the first conflict, leaving subsequent conflicts untouched. The bug affects workflows involving large rebases with many conflicts, particularly when file renames are involved.

Current status: Bug confirmed via provided reproducer script. Root cause identified in `check_one_conflict()` in `rerere.c`, where a loop intended to skip multiple stage-1 entries for the same pathname incorrectly skips entries for subsequent pathnames. No patch has been formally submitted yet; the author suggests a fix (adding a same-path check using `ce_same_name()`) but notes it is untested. The issue is present in Git 2.43.0 and likely persists in later versions. Workaround exists: `git mergetool -- .` resolves all conflicts.

Key technical details:
- Subsystem: `rerere` (reuse recorded resolution)
- File: `rerere.c`, function `check_one_conflict()`
- New behavior (post-fix): `git rerere remaining` will correctly list all unresolved conflicts, even when consecutive paths have only stage-1 entries.
- Old behavior: Consecutive stage-1-only conflicted paths are incorrectly skipped after the first.
- Test coverage: Reproducer script provided; no formal test case yet.
- Symbols: `check_one_conflict()`, `ce_same_name()` (suggested for fix)

This is the fifth iteration of a three-patch series targeting the sequencer subsystem. The goal is to adjust when auto maintenance runs during sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`) so that it defers until sequence completion, matching the apply backend’s behavior. This prevents maintenance from interfering with intermediate steps and ensures consistent behavior across all three commands.

The series is now in a polished state, with all prior feedback incorporated. The commit messages have been tightened to address Junio C Hamano’s stylistic critique, and the header comment for the new `git_config_append_parameter()` helper now uses Patrick Steinhardt’s wording, clarifying that the helper is general-purpose and not tied to `-c` command-line arguments. The tests have also been improved with comments explaining which picks conflict and where the sequence stops, addressing Phillip Wood’s request for clarity.

The core design remains unchanged: auto maintenance is delegated to the built-in commands (`builtin/rebase.c` and `builtin/revert.c`) rather than being triggered from within the sequencer. Thomas Bachem’s latest reply to Patrick Steinhardt demonstrates why this approach is necessary: single-pick cases (`cherry-pick <commit>`, `revert <commit>`, and their `--continue`/`--skip` variants) bypass the sequencer’s `pick_commits()` function entirely, exiting early through `continue_single_pick()` or `skip_single_pick()`. This means Patrick’s alternative—triggering maintenance in `pick_commits()` and on abort—would miss these cases unless the sequencer also hooks the three early-return paths. Thomas has offered to implement either approach but has kept the current design, which Phillip Wood preferred.

The implementation touches `sequencer.c`, `config.c`, `config.h`, `builtin/rebase.c`, and `builtin/revert.c`, and adds test coverage in `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh`. The new behavior disables auto maintenance for individual commands (`git commit`, `git merge`, exec commands) during any sequencer-driven operation by passing `maintenance.auto=false` via `GIT_CONFIG_PARAMETERS`, and invokes `git maintenance run --auto` at sequence completion. The tests use `GIT_TRACE2_EVENT` to verify that maintenance runs exactly once at the end of the sequence and not during intermediate steps.

The series is based on `master` and is independent of the rerere lock race fix mentioned in the cover letter. Junio previously signaled intent to queue it ("Will queue"), and the only remaining open question is whether Patrick Steinhardt will accept the current design or request a rewrite to move the maintenance trigger into the sequencer. Given that the code is unchanged from v4 and all feedback has been addressed, this looks like a well-crafted, uncontroversial improvement that is nearly ready for `next`.

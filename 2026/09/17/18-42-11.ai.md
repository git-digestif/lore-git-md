This is the v5 iteration of a three-patch series targeting the sequencer subsystem, adjusting when auto maintenance runs during `git rebase`, `git cherry-pick`, and `git revert`. The series defers auto maintenance until sequence completion, matching the apply backend’s behavior and preventing maintenance from interfering with intermediate steps. The code itself is unchanged from v4; only commit messages, header comments, and test annotations have been updated to address reviewer feedback.

The core design remains the same: auto maintenance is disabled for individual commands (`git commit`, `git merge`, exec commands) spawned during a sequencer-driven operation by passing `maintenance.auto=false` via `GIT_CONFIG_PARAMETERS`, and `git maintenance run --auto` is invoked exactly once at sequence completion. The implementation delegates this to the built-in commands (`builtin/rebase.c` and `builtin/revert.c`) rather than the sequencer itself, a choice that was previously contested but now appears settled. The new `git_config_append_parameter()` helper (introduced in patch 1) builds and caches the config string, and its header comment now clarifies the format and purpose, addressing Patrick Steinhardt’s earlier feedback.

Patch 2’s commit message now opens with Phillip Wood’s phrasing and explicitly explains why the sequencer cannot reliably trigger maintenance at a single exit point: single-pick cases (`cherry-pick <commit>`, `revert <commit>`, and their `--continue`/`--skip` variants) bypass `pick_commits()` entirely, exiting early through `continue_single_pick()` or `skip_single_pick()`. This justification for delegating to built-ins is now prominently documented. The tests in `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh` have been annotated to clarify which picks conflict and where the sequence stops, addressing Phillip Wood’s test coverage concerns.

The series is based on `master` and is independent of the rerere lock race fix series. Junio C Hamano previously signaled intent to queue it ("Will queue"), and the latest changes are purely cosmetic, suggesting this version is likely to proceed to `next` unless new objections arise. The unresolved hypothetical about long sequences where mid-sequence repacking might improve performance remains noted but unaddressed, as no concrete issue has been identified. All prior feedback from Phillip Wood, Patrick Steinhardt, and Junio has been incorporated, and the series now appears technically complete.

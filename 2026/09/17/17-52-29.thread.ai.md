Subject: [PATCH 0/7] Fix Coverity-reported issues in Git for Windows post v2.56.0-rc0
Series version: v1 (initial submission)
Originating author: Johannes Schindelin
Thread type: patch series (hardening, static-analysis fixes for Git for Windows)

Core problem or goal
Address seven Coverity-reported static-analysis warnings that surfaced in Git for Windows after merging v2.56.0-rc0. The issues span potential signed-overflow in writev, missing input validation in GPG signature parsing, MIDX pack-ID checks, rerere conflict resolution edge cases, reftable iterator initialization, fuzz-testing harnesses, and a latent crash in the `test-read-midx` helper. The series is purely defensive programming with no intended behavior changes.

Current status
Under review; queued as GitGitGadget PR-2231. Base commit is 12cb6293d6 (v2.56.0-rc0). No prior versions exist.

Key technical details
Files touched: wrapper.c (writev_in_full overflow check), gpg-interface.c (signature-prefix matching via starts_with_mem), midx.c (pack-ID validation), rerere.c (conflict resolution error handling), unit tests for reftable iterator (`t/unit-tests/t-reftable-table.c`), oss-fuzz reftable harness (`oss-fuzz/reftable_fuzzer.cc`, `oss-fuzz/fuzz-reftable.c`), and test-read-midx helper (`t/helper/test-read-midx.c`).
New/renamed symbols: none.
Behavior changes: none; only defensive checks added.
On-disk format changes: none.
Test coverage: existing unit tests and fuzz harnesses extended for edge cases. The writev fix adds a guard against SSIZE_MAX overflow using signed_add_overflows() and returns EOVERFLOW on detection, targeting a helper introduced in commit d70eb7f3600d (wrapper: introduce writev(3p) wrappers, 2026-08-07). The GPG fix replaces starts_with() with starts_with_mem() in get_format_by_sig() to prevent buffer overreads when matching signature prefixes, addressing a latent defect exposed by commit c8762c30df5b (object-file-convert: convert tag objects when writing, 2023-10-01) and observable after 215d305f450f (odb: compute compat object ID in odb_write_object_ext(), 2026-07-17). The MIDX fix adds a bounds check on local pack IDs before converting to chain-global IDs, preventing potential underflow or invalid memory access when resolving MIDX layers via nth_midxed_pack(). The rerere fix adds error handling around handle_file() and copy_file() calls in do_rerere_one_path(); if either operation fails, the function now reports the error, leaves the rerere status unchanged, and removes any partially written files, addressing a defect introduced in commit 629716d256a7 (2015). The reftable unit-test patch plugs a NULL-dereference bug in `test_reftable_table__seek_invalid_log_offset()` by adding a `cl_assert_equal_i()` check on the return value of `reftable_table_init_log_iterator()`, which can fail with `REFTABLE_OUT_OF_MEMORY_ERROR` and leave the iterator’s ops table uninitialized; the fix prevents a subsequent NULL function-pointer dereference in `reftable_iterator_seek_log()`. The oss-fuzz patch plugs a NULL-dereference bug in `oss-fuzz/fuzz-reftable.c` by checking the return values of `reftable_table_init_ref_iterator()` and `reftable_table_init_log_iterator()`; if either fails (e.g., with `REFTABLE_OUT_OF_MEMORY_ERROR`), the fuzzer skips the seek/iteration loop and safely destroys the iterator afterward, avoiding a NULL function-pointer dereference in `reftable_iterator_seek_ref()` or `reftable_iterator_seek_log()`. The test-read-midx patch adds a missing error check on the return value of `midx_fill_entry()`; if the function does not return `MIDX_FILL_HIT`, the helper now reports an error and exits cleanly instead of proceeding with invalid data, addressing a latent defect introduced in commit 86d174b7246b (2021).

Open questions and loose ends
- Whether the added checks fully address Coverity’s concerns or if deeper design issues remain, particularly in GPG and MIDX subsystems.
- Potential follow-up discussion on whether similar overflow risks exist in other I/O helpers beyond writev_in_full().
- Whether additional length-aware checks are needed elsewhere in the GPG subsystem, given the pattern identified in this patch.
- The GPG signature-prefix matching fix (patch 2/7) remains contested. Johannes Schindelin argues that propagating a `slen` parameter through `get_format_by_sig()` and its callers is necessary for correctness and safety, as `slen` is used not only for prefix matching but also to determine the exact byte count passed to external verifiers (`gpg`/`ssh-keygen`), preventing truncation of signatures with embedded NULs. Junio C Hamano proposed an alternative design that confines the length-aware `starts_with_mem()` check to `get_format_by_sig()` and avoids changing `check_signature()`’s public interface, citing minimalism and the fact that all existing callers already pass a NUL-terminated buffer from a `strbuf`. Johannes counters that `check_signature()` has included a `slen` parameter since 2021, so dropping it now would introduce an unrelated API change into a bugfix, and that relying on `strlen(signature)` risks repeating a prior incident where `parse_signed_buffer()` was incorrectly assumed to be safe from buffer overreads due to always being called with a `strbuf` -- an assumption invalidated by a new caller (`convert_tag_object()`) in 2024.

Participant positions
Johannes Schindelin (author): maintains that the current patch 2/7 is necessary for correctness and safety. Argues that the `slen` parameter in `check_signature()` is critical for handling signatures with embedded NULs and ensuring accurate byte counts for external verifiers. Frames the patch as a hardening measure that avoids repeating past mistakes in the GPG subsystem. Pushes back against Junio’s proposed simplification, emphasizing that the API change is justified by the need for length-aware verification.
Junio C Hamano: reviewed patch 2/7 (GPG signature-prefix matching) and proposed a less invasive implementation path that avoids changing the public interface of `check_signature()`. Suggests the length-aware check can be confined to `get_format_by_sig()` without propagating a new parameter, arguing that all existing callers already pass a NUL-terminated buffer from a `strbuf`. Reviewed patch 4/7 (rerere error handling) with a surface-level acknowledgment that the defensive check is present and appropriate; no substantive engagement with edge cases or design trade-offs.

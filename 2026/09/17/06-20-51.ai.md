This is a bugfix patch for the Git protocol v2 `upload-pack` subsystem, addressing a long-standing client-side crash during shallow fetches when `uploadpack.allowRefInWanted` is enabled. The patch swaps the order of `send_shallow_info()` and `send_wanted_ref_info()` in `upload_pack_v2()` to ensure the server sends "shallow-info" before "wanted-refs", matching the client's expectations and preventing the crash.

Junio's reply confirms the bug's origin—it has existed since the ref-in-want feature was introduced in 2018 (commits `733020517a` and `516e2676bd`) but went unnoticed due to the feature's niche use case. The fix is minimal (a single line reordering in `upload-pack.c`) and includes two new test cases in `t/t5703-upload-pack-ref-in-want.sh` to verify both single-commit shallow clones and incremental shallow fetches. The tests confirm the patch resolves the crash while preserving correct ref resolution and commit history.

The patch is technically sound and addresses Junio's earlier feedback about commit-message clarity. Since the feature combination (`uploadpack.allowRefInWanted` with shallow fetches) never worked in practice, the change is backward-compatible with all existing clients. The regression was latent, so no existing deployments are disrupted. Key technical details for follow-up discussion include the `peek` bit in `process_section_header()` and the `UPLOAD_SEND_PACK` state in `upload_pack_v2()`.

This is a targeted fix with no broader subsystem interactions, affecting only protocol v2 shallow fetches with `uploadpack.allowRefInWanted` enabled. The patch is ready for integration, with no outstanding objections after the v2 update.

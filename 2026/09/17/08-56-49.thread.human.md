This thread is about a bug in Git’s `rerere` (reuse recorded resolution) subsystem that causes `git rerere remaining` to incorrectly skip consecutive conflicted paths when only stage-1 index entries are present. The issue was reported by Mikko Rantalainen, who identified the root cause in `check_one_conflict()` in `rerere.c`: a loop meant to skip multiple stage-1 entries for the same pathname also skips entries for *subsequent* pathnames. This leads to `git mergetool` exiting prematurely after resolving only the first of multiple unresolved conflicts, leaving the rest untouched.

Mikko provided a minimal reproducer script demonstrating the bug, which sets up a rebase with two files renamed differently in two branches, producing consecutive stage-1-only conflicts. The script confirms that `git rerere remaining` lists only the first conflicted path, while `git diff --name-only --diff-filter=U` correctly lists both. The workaround is to use `git mergetool -- .`, but the issue affects workflows involving large rebases with many conflicts. The proposed fix involves adding a same-path check (e.g., `ce_same_name()`) to the loop in `check_one_conflict()`, though Mikko notes this is a suggestion rather than a tested patch.

The bug is well-documented, low-risk, and targets a stable part of the codebase, so it likely persists in recent Git versions. No reviews or maintainer responses have been posted yet, so the thread is currently just the bug report and reproducer. The fix is straightforward and addresses a real pain point, making it a strong candidate for inclusion once reviewed.

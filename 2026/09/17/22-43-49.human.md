This is the first patch in a three-part bugfix series (v6) targeting the `--force-if-includes` safety mechanism in `git push`. The patch fixes a critical flaw where the feature incorrectly checks the reflog of the *local* branch matching the *remote* destination name (e.g., `refs/heads/main`) instead of the branch actually being pushed (e.g., `refs/heads/src` in `src:main`). This can cause false rejections or unintended data loss, as the reflog of the wrong branch is consulted.

The core change is in `remote.c`: `check_if_includes_upstream()` now uses `ref->peer_ref->name` to locate the correct reflog, resolving the pushed ref with `RESOLVE_REF_READING` to ensure it points to a branch. Non-branch pushes (detached HEADs, tags, OIDs) are explicitly rejected, as they lack per-branch reflogs. Deletions (e.g., `:main`) are allowed by checking `is_null_oid(&remote->peer_ref->new_oid)`. The patch also removes an unnecessary `NULL` check for `get_local_ref()`, as the function never returns `NULL` for non-empty names.

Test coverage is thorough, adding 81 lines to `t/t5533-push-cas.sh` to verify the fix for differently named branches, HEAD-based pushes, orphan branches, detached HEADs, and tags. The tests confirm that the feature now behaves as documented: force-pushes are allowed only if the remote tip is reachable from the reflog of the *pushed* branch.

This patch is well-motivated and addresses a real-world issue reported by multiple users. The implementation is clean, with clear commit message rationale and no obvious regressions.

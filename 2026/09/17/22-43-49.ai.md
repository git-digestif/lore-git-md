This is the first patch in the v6 series fixing `--force-if-includes` in `git push`. It corrects the core logic flaw: the feature previously checked the reflog of the *local* branch whose name matched the *remote* destination (e.g., `refs/heads/main` when pushing `src:main`), rather than the branch actually being pushed (`refs/heads/src`). The patch now uses `ref->peer_ref->name` to locate the correct reflog, resolving both false rejections (when the local branch is outdated) and unintended data loss (when the local branch is up-to-date but the pushed branch is orphaned).

The implementation unconditionally resolves `peer_ref` with `RESOLVE_REF_READING` and rejects pushes of non-branch refs (detached HEADs, tags, OIDs) by setting `remote->unreachable = 1` if the resolved name does not start with `refs/heads/`. Deletions (e.g., `git push origin :main`) are explicitly allowed by checking `is_null_oid(&remote->peer_ref->new_oid)`. The early return for missing `peer_ref` handles cases where `apply_push_cas` walks all advertised refs during a bare `--force-with-lease`.

Test coverage is thorough: 81 lines added to `t/t5533-push-cas.sh` verify the fix for differently named branches (`newbranch:main`), HEAD-based pushes, orphan branches, detached HEADs, and tags. The patch touches only `remote.c` and the test file, with no changes to on-disk formats or other subsystems. All prior review feedback (from Patrick Steinhardt, Junio C Hamano, and D. Ben Knoble) is addressed, including edge cases like deletions and unresolved `HEAD`. The logic is now correct and uncontroversial.

## Notable threads

### Sequencer: defer auto maintenance until rebase completion (v5 posted)
Thomas Bachem posted v5 of the three-patch series adjusting when auto maintenance runs during sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`). The series defers auto maintenance until sequence completion, matching the apply backend’s behavior and preventing maintenance from interfering with intermediate steps.

The v5 iteration is code-identical to v4; only commit messages, header comments, and test annotations have been updated to address prior feedback. The core design remains unchanged: auto maintenance is disabled for individual commands (`git commit`, `git merge`, exec commands) during sequencer operations by passing `maintenance.auto=false` via `GIT_CONFIG_PARAMETERS`, and `git maintenance run --auto` is invoked exactly once at sequence completion. The implementation delegates this to the built-in commands (`builtin/rebase.c` and `builtin/revert.c`) rather than the sequencer itself, a choice that was previously contested but is now settled and documented. Patch 2’s commit message now explicitly explains why the sequencer cannot reliably trigger maintenance at a single exit point: single-pick cases (`cherry-pick <commit>`, `revert <commit>`, and their `--continue`/`--skip` variants) bypass `pick_commits()` entirely, exiting early through `continue_single_pick()` or `skip_single_pick()`. The tests in `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh` have been annotated to clarify conflict triggers and sequence stops, addressing Phillip Wood’s test coverage concerns. Junio C Hamano previously signaled intent to queue the series ("Will queue"), and it is now in `seen`.

### Fix --force-if-includes to check the correct reflog (v6 posted)
Tyler Cipriani posted v6 of the three-patch series fixing the `--force-if-includes` safety mechanism in `git push`. The series addresses two critical flaws: (1) the feature incorrectly checks the reflog of the *local* branch named after the *remote* destination rather than the branch actually being pushed, and (2) it unnecessarily rejects fast-forward pushes of non-branch refs (tags, detached HEADs) even when no force is needed.

The v6 reroll addresses the last remaining readability concerns from the v5 review while keeping the technical solution intact. The core logic in `remote.c` now consults the reflog of the pushed ref (`ref->peer_ref->name`) and introduces a `needs_force_reject_reason` variable (renamed from `deferred_reject_reason` in v5) to defer reflog checks until after fast-forward determination. This ensures fast-forward pushes are exempt from `--force-if-includes` checks, resolving an existing bug where workflows like `git push origin <TAG>:hotfix` were broken. The series also adds a new `ref->unverifiable` flag and `advice.forceIfIncludesDetachedHead` config knob to provide actionable advice for rejected non-branch pushes. The v6 changes are minor: a variable rename for clarity, typo fixes in commit messages, and improved documentation wording. All prior review feedback from Patrick Steinhardt, Junio C Hamano, and D. Ben Knoble is resolved. The series is based on `maint` and has no external dependencies.

### stash.index=true + --autostash during fast-forward merge leaves redundant stash entry
D. Ben Knoble reported success implementing Phillip Wood’s proposed refactoring to fix a bug in `git merge --ff-only --autostash` when `stash.index=true` is set and a staged change exists at merge time. The bug caused the operation to leave behind a redundant stash entry and fail to clean up the `MERGE_AUTOSTASH` ref.

The fix replaces the subprocess-heavy index-merge logic (`git diff-tree`, `git apply --cached`, `git reset`) with a direct call to `merge_incore_nonrecursive()`, resolving the root cause (premature `MERGE_AUTOSTASH` ref deletion) while improving performance and code clarity. The patch passes all tests and resolves the original bug. Phillip Wood reviewed the patch and suggested minor polish: silencing merge verbosity (since conflicts already trigger an abort), simplifying conflict-label setup, and using `oidcpy()` instead of direct OID assignment for robustness. The patch is now one cleanup pass away from a formal submission.

### Bug: git rerere remaining skips consecutive conflicted paths with only stage-1 entries
Mikko Rantalainen reported a bug in `git rerere remaining` where consecutive conflicted paths with only stage-1 index entries are incorrectly skipped. The issue manifests in `git mergetool`, which exits successfully after resolving only the first of multiple unresolved conflicts, leaving the rest untouched.

The root cause is traced to `check_one_conflict()` in `rerere.c`, where a loop intended to skip multiple stage-1 entries for the same pathname also skips entries for *subsequent* pathnames. The author provides a minimal reproducer script that sets up a rebase with two files renamed differently in two branches, producing consecutive stage-1-only conflicts. On affected versions (tested on Git 2.43.0), `git rerere remaining` lists only the first conflicted path, while `git diff --name-only --diff-filter=U` correctly lists both. The script confirms the bug by showing that `git mergetool` exits with status 0 after resolving only one path, leaving the other unresolved. The proposed fix involves modifying the loop in `check_one_conflict()` to include a same-path check (e.g., using `ce_same_name()`), though the author notes this is a suggestion rather than a tested patch. The bug affects workflows involving large rebases with many conflicts, particularly when file renames are involved, and has a straightforward workaround (using `git mergetool -- .`).

### Fix Coverity-reported issues in Git for Windows post v2.56.0-rc0 (seven-patch series posted)
Johannes Schindelin posted a seven-patch series addressing Coverity-reported static-analysis warnings that surfaced in Git for Windows after merging v2.56.0-rc0. The issues span potential signed-overflow in writev, missing input validation in GPG signature parsing, MIDX pack-ID checks, rerere conflict resolution edge cases, reftable iterator initialization, fuzz-testing harnesses, and a latent crash in the `test-read-midx` helper. The series is purely defensive programming with no intended behavior changes.

The first patch adds a defensive check in `writev_in_full()` to detect when the cumulative byte count would exceed `SSIZE_MAX`, treating it as an I/O failure with `errno = EOVERFLOW`. The second patch replaces `starts_with()` with `starts_with_mem()` in `get_format_by_sig()` to prevent buffer overreads in GPG signature-prefix matching. Junio C Hamano suggested an alternative design: instead of propagating a new `slen` parameter through `get_format_by_sig()` and its callers, confine the length-aware `starts_with_mem()` check to `get_format_by_sig()` and drop the parameter from `check_signature()`, since all existing callers already pass a NUL-terminated buffer from a `strbuf`. The third patch adds a bounds check on local pack IDs in MIDX to prevent underflow or invalid memory access. The fourth patch adds error handling around `handle_file()` and `copy_file()` calls in `do_rerere_one_path()` to prevent recording failed conflict resolutions. The remaining patches plug NULL-dereference bugs in reftable unit tests, the oss-fuzz reftable harness, and the `test-read-midx` helper. The series is queued as GitGitGadget PR-2231 and targets a mix of subsystems: the wrapper layer, GPG signature parsing, multi-pack-index (MIDX), rerere conflict resolution, reftable iterators, and fuzz-testing harnesses.

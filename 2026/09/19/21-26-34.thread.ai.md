Subject: [PATCH 0/4] stash: fix autostash with staged index entries

Thread type: patch series (bugfix)

Core problem or goal
Fix a bug in `git stash` where autostashing fails to correctly handle staged index entries when `stash.index=true` is set. The bug manifests during merge operations that trigger autostash, causing incorrect index state preservation due to a race condition in the subprocess-based logic (`git diff-tree` and `git apply`). The series replaces this with in-core merging via `merge-ort.c`, ensuring staged entries are properly preserved and eliminating the risk of SIGSEGV on conflicted index merges. The root cause is a non-reentrant filesystem operation in `save_autostash()` that prematurely locks and deletes the MERGE_AUTOSTASH ref, corrupting the index state during concurrent merge operations.

Current status
v3 is the final iteration, submitted as a five-patch series. **Patch 1 (cleanup)** is merged to `master` (date unknown). Patches 2–5 were previously ready for integration with one remaining adjustment (verbosity regression fix), but have now been **ejected from Junio’s `seen` branch** due to four independent issues, all now resolved except for the **NULL-dereference risk**:
1. **Resolved**: A test breakage in `t5520-pull.sh` when merged into `seen`, traced to an interaction with the `tb/rerere-lock-grace` topic. The bisect identified commit `2d1fa0323f` ("rebase, cherry-pick, revert: run auto maintenance when done") as the root cause. The auto-maintenance step (`git maintenance run --auto`) triggers `git reflog expire` under the test’s fixed `GIT_COMMITTER_DATE` (2005), prematurely expiring reflog entries that `git pull --rebase` relies on for fork-point detection. The stash series’ tests generate eight fewer reflog entries (from failed merges due to the elimination of `git reset --quiet --refresh` calls), shifting the expiration timing and causing the rebase to misidentify the upstream commit. **Fix**: Thomas Bachem (author of `tb/rerere-lock-grace`) submitted a patch to pin `gc.reflogExpire` and `gc.reflogExpireUnreachable` to `never` in the test setup, mirroring a prior solution for rebase tests (`ea7d894f44`). This patch (`pull.2243.git.1790606282769.gitgitgadget@gmail.com`) is uncontroversial and has been merged to `master`, fully resolving the breakage.
2. **Resolved**: A verbosity regression in Patch 5, where the `.verbosity` field in `merge_options` was unconditionally set to `0` during the index merge, silencing the subsequent worktree merge. The author fixed this by preserving the original verbosity setting for the worktree merge.
3. **Resolved**: Bisectability regression: The test added in Patch 3/5 previously failed when run against the codebase *before* Patch 5/5 was applied, breaking `git bisect`. Phillip Wood identified this as a substantive integration concern and proposed squashing the test into Patch 5/5 (the final patch that implements the fix) and replacing an existing, less strict `stash apply --index` test rather than adding a new one. **Fix**: The author has implemented this restructuring, resolving the bisectability issue. The test’s failure was due to a mismatch between the patch context (generated by `git stash push -p`) and the file state in the absence of Patch 5’s merge logic, causing the merge machinery to incorrectly succeed. The fix ensures the test only runs when the full fix is present.
4. **Critical NULL-dereference risk**: In Patch 5/5, `merge_incore_nonrecursive()` may return with `result.tree` uninitialized on catastrophic failure (e.g., missing objects), leading to a SIGSEGV when `result.tree->object.oid` is dereferenced. Junio’s audit of existing callers (`git grep merge_incore_nonrecursive`) confirms all other callers explicitly check `result.clean < 0` before accessing `result.tree`, a pattern the stash patch omits. The author has confirmed the issue and will address it by checking `result.clean` before dereferencing `result.tree`, possibly combined with a fallback to the original subprocess-based logic or an early error return. This is the **sole remaining blocker** for integration.

  - **Clarification on `git pull --rebase`**: The reflog dependency in `git pull --rebase` is now confirmed to stem from its internal use of `git merge-base --fork-point` to compute the fork point from the reflog of `refs/remotes/me/copy`, even when an explicit `<upstream>` argument is provided. This behavior contradicts the documented expectation that `--fork-point` should be disabled when `<upstream>` is specified. The command sequence involves `git merge-base --fork-point` running *before* `git rebase --onto`, feeding the computed fork point into the rebase operation. This clarification does not affect the stash series’ logic but explains the root cause of the `t5520` breakage and may inform future work on `git pull --rebase` or `--fork-point` behavior.
- **Critical issue**:
  - NULL-dereference risk in `do_apply_stash()` on catastrophic merge failure (e.g., missing objects), confirmed by the author and requiring a fix to check `result.clean` before dereferencing `result.tree`. Junio’s audit confirms this is a systemic omission in the patch’s error handling. This is the **sole remaining blocker** for integration.

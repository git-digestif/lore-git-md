Core problem or goal
Fix a bug in `git stash` where autostashing fails to correctly handle staged index entries when `stash.index=true` is set. The bug manifests during merge operations that trigger autostash, causing incorrect index state preservation due to a race condition in the subprocess-based logic (`git diff-tree` and `git apply`). The series replaces this with in-core merging via `merge-ort.c`, ensuring staged entries are properly preserved and eliminating the risk of SIGSEGV on conflicted index merges. The root cause is a non-reentrant filesystem operation in `save_autostash()` that prematurely locks and deletes the MERGE_AUTOSTASH ref, corrupting the index state during concurrent merge operations.

  - **Fork-point detection**: `git pull --rebase` calls `git merge-base --fork-point` directly (not `git rebase --fork-point`), then passes the resulting object ID (not a ref) to `git rebase`. The stash series reduces reflog entries (8 fewer from `git reset --quiet --refresh` during failed merges), shifting expiration timing and causing the breakage.

  - **Patch 5/5 specifics**: Replaces subprocess-based index merging (`git diff-tree` and `git apply`) with `merge_incore_nonrecursive()`, ensuring staged entries are preserved. Includes safety checks for catastrophic merge failures and correct tree ordering (HEAD vs. stash base). The latent error-handling bug (hard errors vs. conflicts) is now addressed by the follow-up patch.

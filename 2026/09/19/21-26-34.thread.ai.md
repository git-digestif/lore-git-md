Core problem or goal
Fix a bug in `git stash` where autostashing fails to correctly handle staged index entries when `stash.index=true` is set. The bug manifests during merge operations that trigger autostash, causing incorrect index state preservation due to a race condition in the subprocess-based logic (`git diff-tree` and `git apply`). The series replaces this with in-core merging via `merge-ort.c`, ensuring staged entries are properly preserved and eliminating the risk of SIGSEGV on conflicted index merges. The root cause is a non-reentrant filesystem operation in `save_autostash()` that prematurely locks and deletes the MERGE_AUTOSTASH ref, corrupting the index state during concurrent merge operations.

Current status
v3 is the final iteration, submitted as a five-patch series. **Patch 1 (cleanup)** is merged to `master` (2024-XX-XX, exact date unknown). Patches 2–5 were previously ready for integration with one remaining adjustment (verbosity regression fix), but have now been **temporarily ejected from Junio’s `seen` branch** due to three independent issues:
1. **Resolved**: A test breakage in `t5520-pull.sh` when merged into `seen`, traced to an interaction with the `tb/rerere-lock-grace` topic. The bisect identified commit `2d1fa0323f` ("rebase, cherry-pick, revert: run auto maintenance when done") as the root cause. The auto-maintenance step (`git maintenance run --auto`) triggers `git reflog expire` under the test’s fixed `GIT_COMMITTER_DATE` (2005), prematurely expiring reflog entries that `git pull --rebase` relies on for fork-point detection. The stash series’ tests generate additional reflog entries, shifting the expiration timing and causing the rebase to misidentify the upstream commit. **Fix**: Thomas Bachem (author of `tb/rerere-lock-grace`) has submitted a patch to pin `gc.reflogExpire` and `gc.reflogExpireUnreachable` to `never` in the test setup, mirroring a prior solution for rebase tests (`ea7d894f44`). This patch (`pull.2243.git.1790606282769.gitgitgadget@gmail.com`) is uncontroversial and likely to be merged to `master`, resolving the breakage.
2. A **NULL-dereference risk** in Patch 5/5, where `merge_incore_nonrecursive()` may return with `result.tree` uninitialized on catastrophic failure (e.g., missing objects), leading to a SIGSEGV when `result.tree->object.oid` is dereferenced. The author has confirmed the issue and will address it by checking `result.clean` before dereferencing `result.tree`, possibly combined with a fallback to the original subprocess-based logic or an early error return.
3. **Resolved**: A verbosity regression in Patch 5, where the `.verbosity` field in `merge_options` was unconditionally set to `0` during the index merge, silencing the subsequent worktree merge. The author has agreed to fix this by preserving the original verbosity setting for the worktree merge.

This is a feature patch introducing a new configuration option, `fetch.shallow`, aimed at improving performance for shallow repositories with many branches. The patch is well-motivated and includes thorough test coverage.

The problem it addresses is real: in a shallow, sparsely checked-out clone of a repository with many branches, a plain `git pull` or `git fetch` can be painfully slow or even hang, because Git negotiates history for every branch the remote advertises, even if the user only cares about the current branch. The new `fetch.shallow` config (off by default) changes this behavior so that a fetch or pull in a shallow repository—when no explicit refspec is given—fetches only the current branch’s tracked upstream, rather than every branch. This preserves the existing behavior for users who rely on `refs/remotes/<name>/` being fully populated, while offering a targeted opt-in optimization for those who don’t.

The implementation is clean: it adds the config knob, modifies `builtin/fetch.c` to check the setting and narrow the refspec when appropriate, and ensures that `remotes/<name>/HEAD` is still kept up to date. The tests cover the core functionality, edge cases (non-shallow repos, untracked remotes), and integration with `git pull`. The commit message and documentation are clear and explain both the motivation and the trade-offs.

This looks like a sensible, well-crafted contribution that solves a real pain point without breaking existing workflows. It’s likely to be uncontroversial and could be a good candidate for `next` once reviewed.

This is a **bugfix** targeting the reference-transaction hook, clarifying the root cause of a regression introduced in Git 2.31.

Maciej Ciemborowicz identifies the exact commit (`8198907795`) that replaced `delete_ref()` with `delete_refs()` in Git 2.31, aiming to optimize bulk deletions (e.g., 24,000 tags). The optimization inadvertently broke the hook’s contract by omitting the old OID, causing it to report all-zero OIDs for both old and new values during branch/tag deletions. The original behavior (preserving the old OID) was documented as a safety check for deletions, and the regression affects both files and reftable backends.

The commit message makes it clear this was an unintended side effect of a performance improvement, not a deliberate design change. The author suggests the fix should restore the old OID while preserving the speedup, which seems feasible. No other high-level commands or workflows are mentioned as affected, but the scope is limited to deletions via `git branch -d`, `git tag -d`, and `git remote prune`—`git update-ref -d` remains unaffected.

The patch is well-motivated and narrowly scoped, addressing a real-world issue for tools like Gerrit and GitLab that rely on the hook. The next steps will likely involve a targeted fix to `delete_refs()` or its callers to pass the old OID where available. The thread is now in a diagnostic phase, with the regression’s origin and intent resolved.

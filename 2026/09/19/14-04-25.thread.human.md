This thread is about a proposed new warning in `git commit` that alerts users when a new commit’s date precedes its parent’s date, which can break assumptions in commands like `git log --since`. The patch, sent as an RFC by Yashwanth Sai, introduces an advice message (`advice.clockSkew`) that triggers when such a skew is detected, aiming to help users catch potential issues with history traversal.

The motivation is clear: Git currently accepts any commit date without validation, even if it violates the expectation that dates should be non-decreasing. The warning is narrowly scoped to `git commit` (excluding merges and replays) and only compares the new commit against its immediate parents to avoid false positives from cross-machine clock skew. The implementation is straightforward, hooking into `builtin/commit.c` to parse and compare dates, and emitting a warning via the advice system. Tests verify the warning works as expected and can be silenced via configuration.

The patch touches `advice.c`, `advice.h`, `builtin/commit.c`, documentation, and test files, and introduces a new config option (`advice.clockSkew`, defaulting to `true`). The design is deliberately non-enforcing—it warns but does not block commits—and handles edge cases like timezone parsing and unparseable dates. The RFC explicitly seeks feedback on whether the feature is wanted, if advice is the right channel (since stderr output might get buried), and whether `fsck` should also warn about dates far ahead of "now."

So far, the thread is just the initial RFC, so there’s no discussion or feedback yet. The patch is well-motivated and addresses a real usability issue, but its narrow scope and reliance on advice messages may spark debate once reviews begin. The tests are thorough, and the code is clean, suggesting the author has thought carefully about the design.

This thread is about a bug in Git’s `reference-transaction` hook: when you rename a branch with `git branch -m`, the hook only sees the deletion of the old branch name, not the creation of the new one. Maciej Ciemborowicz reported the issue and posted a patch (v1) that fixes it for both the files-based and reftable backends. The fix introduces a new transaction type for renames and copies, plus a flag to ensure the hook sees the operation as a single logical event.

The patch is well-tested and addresses the problem thoroughly, but Junio’s review raises two architectural concerns. First, he questions whether the new `REF_TRANSACTION_FLAG_SKIP_HOOK` flag is necessary, suggesting the call chain could be rearranged to avoid it. Second, he argues that rename/copy details (like old and new ref names) shouldn’t clutter the generic `ref_transaction` struct and should instead be kept in backend-specific data. The review doesn’t challenge the patch’s correctness or test coverage, but these design points could require significant refactoring. Karthik Nayak, who helped diagnose the issue, supports the fix, so the discussion is now focused on how to implement it cleanly. No other objections or open questions have been raised.

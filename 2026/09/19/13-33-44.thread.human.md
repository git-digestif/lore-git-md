This thread is about a bug in Git’s `reference-transaction` hook, which fails to report the creation of a new branch when an existing one is renamed (`git branch -m`) or copied (`git branch -c`). The hook only sees the deletion of the old branch name, breaking tools that expect to see the full transaction. Maciej Ciemborowicz’s four-patch series (now at v4) fixes this by reworking how ref backends handle rename and copy operations, ensuring both the deletion and creation are reported in the same transaction.

The series has evolved through several iterations, with v4 resolving test breakages Junio C Hamano reported in v3. The first patch, which adds infrastructure like `REF_TRANSACTION_FLAG_INTERNAL` and `ref_transaction_replace_reflog()`, is uncontroversial and ready to proceed. The later patches integrate rename/copy logic into ordinary transactions, using per-ref-update flags and a unified approach that replaces backend-specific callbacks. The final patch (4/4) is a mechanical cleanup, removing 656 lines of now-unused code from the files, reftable, and debug backends.

Performance regressions remain—renames with large reflogs are about 137% slower with the files backend and 20-25% slower with reftable—but these are considered acceptable for correctness. The series has no blocking objections, and with Junio’s test concerns addressed and Patrick Steinhardt’s implicit approval of the architectural direction, it’s likely to land in `next` soon if no further issues arise. Karthik Nayak has contributed domain expertise, and Maciej has incorporated feedback throughout the process.

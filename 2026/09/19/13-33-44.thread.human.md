This thread began as a bug report from Maciej Ciemborowicz about the `reference-transaction` hook missing the creation of a new ref when a branch is renamed (`git branch -m`). The hook only reported the deletion of the old branch name, not the creation of the new one, affecting both the files-based and reftable backends. Karthik Nayak diagnosed the issue, noting that branch renames bypass transactions entirely, and the reftable backend’s TOMBSTONE entries skip the hook altogether.

Maciej has now submitted a well-crafted patch that fixes the problem by ensuring both the deletion and creation events are reported in a single transaction. The patch introduces a new transaction type (`REF_TRANSACTION_TYPE_RENAME`/`COPY`) and a flag (`REF_TRANSACTION_FLAG_SKIP_HOOK`) to suppress hooks for nested operations, while preserving backend-specific reflog handling. It also adds concurrency checks and rollback support if the hook rejects the operation. The tests are thorough, covering rename, copy, forced updates, D/F conflicts, and hook-triggered rollback, confirming the hook now behaves consistently with `git update-ref --stdin`.

The patch is ready for review and appears uncontroversial. Given Karthik’s earlier diagnosis and the `Helped-by` credit, it has strong backing from domain experts. Expect this to move to `next` soon. No objections or open questions remain—just the usual review process before it graduates to `master`.

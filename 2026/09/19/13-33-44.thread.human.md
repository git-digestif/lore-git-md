This thread is about a bug in Git’s `reference-transaction` hook, which fails to report the creation of a new branch when an existing one is renamed (`git branch -m`) or copied (`git branch -c`). Maciej Ciemborowicz posted a v3 four-patch series to fix this, restructuring the ref backend logic to ensure both deletion and creation events are included in the same transaction. The redesign addressed earlier objections from Patrick Steinhardt by using per-ref-update tracking and centralizing hook suppression.

However, Junio C Hamano’s latest review uncovered two test failures in the v3 series when applied to current `master`. The tests—`t0600.16` (deletion failure on locked `packed-refs.new`) and `t5510.35` (fetch prune failure on locked `packed-refs.new`)—now pass incorrectly, suggesting the series broke packed-refs locking or transaction rollback logic. These regressions are unrelated to the original hook bug and affect core ref-deletion safety, casting doubt on the series’ correctness. The failures occur in `git update-ref -d` and `git fetch --prune`, indicating broader unintended side effects.

The series is now paused while Maciej investigates the breakages. No merge status has been reported, and the series remains under review with a critical blocker. Key next steps include reproducing the failures, diagnosing whether they stem from the new `REF_TRANSACTION_FLAG_INTERNAL` logic or backend callback removal, and ensuring the fix doesn’t reintroduce the original hook omission. Reviewers like Patrick Steinhardt and Karthik Nayak are likely awaiting a v4 before further feedback.

This thread is about a bug in Git’s `reference-transaction` hook: when you rename or copy a branch with `git branch -m` or `git branch -c`, the hook only sees the deletion of the old branch name, not the creation of the new one. Both the traditional files backend and the newer reftable backend are affected, and the reftable version doesn’t even provide a usable rename payload. The expected behavior—confirmed by `git update-ref --stdin`—is that both deletion and creation events should be included in the same transaction.

Maciej Ciemborowicz posted a v2 patch that addressed Junio Hamano’s earlier architectural concerns by moving rename/copy state into individual ref updates rather than the transaction as a whole. This redesign keeps the transaction interface generic and supports multi-ref operations. However, Patrick Steinhardt has rejected the patch as unreviewable, citing poor code structure (mixed refactoring and logic), unclear commit messages, and non-idiomatic C patterns that suggest heavy AI assistance. Maciej acknowledged these issues, admitted the patch was AI-assisted and lacks sufficient C expertise, and offered to prepare a v3—but also deferred to Karthik Nayak or others to take over the fix, expressing uncertainty about meeting Steinhardt’s standards.

In the latest email, Steinhardt expands on his critique with two key technical disagreements. First, he argues the patch’s backend-specific reflog handling is unnecessary: Git’s reference transactions now support writing multiple reflog entries for a single ref, so the entire rename/copy mechanism could be implemented generically. Second, he dismisses the patch’s "revalidation" step—which checks if refs observed by the "preparing" hook still match the state at commit time—as misguided, since the "preparing" hook is documented to run before locks are acquired and race conditions are expected. Beyond these points, Steinhardt’s tone remains firm: the patch’s structure and vague commit messages signal insufficient human oversight, and future revisions must demonstrate deeper C expertise. The thread remains blocked until a major rewrite is posted, likely by Karthik Nayak or another contributor with stronger C experience. No merge status has been reported, and the patch is not under active review.

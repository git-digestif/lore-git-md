This thread is about a bug in Git’s `reference-transaction` hook: when you rename a branch (`git branch -m`), the hook only sees the deletion of the old branch name, not the creation of the new one. Both the files-based and reftable backends have the same problem, and the reftable backend doesn’t even give the hook a usable rename payload.

Maciej Ciemborowicz posted a patch (v1) that fixes the issue by introducing a new transaction type (`REF_TRANSACTION_TYPE_RENAME`/`COPY`) and a flag (`REF_TRANSACTION_FLAG_SKIP_HOOK`) to ensure the hook sees the rename or copy as a single logical transaction. The patch updates both backends, keeps their reflog handling intact, and includes thorough tests for rename, copy, forced updates, D/F conflicts, and rollbacks.

Junio C Hamano reviewed the patch and raised architectural concerns. His latest email digs deeper into whether the generic `ref_transaction` struct should include rename/copy-specific fields (`old_refname`, `new_refname`, `type`). He thinks these details should stay in backend-specific data structures, not the core transaction interface, and questions how the current design would handle multiple renames or mixed operations in a single transaction. This isn’t a rejection, but it suggests the patch may need a significant redesign to address these issues. The ball is now in Maciej’s court to clarify whether the current approach can scale or if a different abstraction is needed. Karthik Nayak, who helped diagnose the issue, supports the fix.

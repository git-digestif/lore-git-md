This thread is about a bug in Git’s `reference-transaction` hook: when a branch is renamed (`git branch -m`) or copied (`git branch -c`), the hook only sees the deletion of the old branch name, not the creation of the new one. Both the files-based and reftable backends are affected, and the reftable backend omits any usable rename payload entirely. The expected behavior—confirmed via `git update-ref --stdin`—is that both deletion and creation events are included in the same transaction.

Maciej Ciemborowicz posted a v1 patch that introduces a new transaction type (`REF_TRANSACTION_TYPE_RENAME`/`COPY`) and a `REF_TRANSACTION_FLAG_SKIP_HOOK` flag to ensure branch rename and copy operations are reported as a single logical transaction to the hook. The patch updates both backends and includes thorough test coverage. Junio C Hamano reviewed the patch and raised architectural concerns, particularly about overloading the generic `ref_transaction` struct with rename/copy-specific fields, which assumes a single rename or copy per transaction and doesn’t scale to multi-ref operations (e.g., renaming A→X, B→Y, and C→Z in one transaction).

Maciej has agreed to rework the patch to move rename/copy state to individual ref updates rather than the transaction as a whole, preserving the genericity of the core transaction interface. This redesign will be delayed for a few days while he finishes another patch series on `git range-diff` usability. The thread remains open on the architectural question, and future discussion will likely focus on how to represent multi-ref rename/copy operations cleanly. Karthik Nayak supports the fix, and no other participants have weighed in yet.

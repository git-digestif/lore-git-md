This thread is about a bug in Git’s `reference-transaction` hook: when a branch is renamed or copied (e.g., `git branch -m`), the hook only reports the deletion of the old branch name, not the creation of the new one. Both the files-based and reftable backends are affected. Maciej Ciemborowicz reported the issue and posted a v1 patch, but Junio C Hamano raised architectural concerns about the implementation, particularly the use of rename/copy-specific fields in the generic `ref_transaction` struct. Maciej agreed to redesign the patch to confine this state to individual ref updates, preserving the genericity of the transaction interface and enabling multi-ref operations.

The thread is now focused on implementation details of the redesign. In a recent follow-up, Maciej addressed two review comments from Karthik Nayak. First, he agreed to keep the `REF_TRANSACTION_FLAG_SKIP_HOOK` flag internal to the refs implementation, rather than exposing it publicly, as it is only needed for backend-internal transactions (like packed-refs updates). Second, he accepted Karthik’s suggestion to change the `int copy` parameter to a `bool`, since the function only operates in two modes (rename or copy). No new patch version has been posted yet, but these adjustments are part of the ongoing redesign. The thread remains open, with the architectural redesign still in progress. Key participants include Maciej (author), Karthik Nayak (reviewer and helper), and Junio (maintainer).

This thread is about a bug in Git’s `reference-transaction` hook, which fails to report the creation of a new branch when an existing one is renamed (`git branch -m`) or copied (`git branch -c`). The hook only sees the deletion of the old branch name, not the creation of the new one, affecting both the files-based and reftable backends. Maciej Ciemborowicz posted a v3 4-patch series to fix this, splitting the work into logical steps: introducing an internal hook suppression flag, adding reflog replacement support, integrating copy/rename into the transaction API, and removing backend-specific callbacks.

The series addresses earlier objections from Patrick Steinhardt by moving to per-ref-update tracking instead of a transaction-wide state, centralizing hook suppression, and dropping a pre-lock revalidation step. Performance regressions are acknowledged (up to 137% slowdown for files-based rename with large reflogs) but deemed acceptable. The latest patch (4/4) removes now-unused backend-specific copy/rename callbacks, completing the transition to the unified transaction API. The series is ready for substantive review, with no merge status reported yet.

Key participants include Maciej (author), Karthik Nayak (domain expertise), Junio C Hamano (maintainer), and Patrick Steinhardt (whose earlier blocking objections have been addressed). The focus now is on whether the new transaction-based design is idiomatic and sufficiently generic, and whether the performance trade-offs are justified. Reviewers are expected to scrutinize the per-ref-update flags, helper functions, and the correctness of reflog staging logic.

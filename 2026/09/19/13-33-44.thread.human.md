This thread is about a bug in Git’s `reference-transaction` hook that omits the creation of a new ref when a branch is renamed or copied (e.g., with `git branch -m` or `git branch -c`). The issue affects both the files-based and reftable backends, with the reftable backend failing to provide any usable rename payload at all. The expected behavior—confirmed via `git update-ref --stdin`—is for the hook to receive both the deletion of the old ref and the creation of the new one in the same transaction.

Maciej Ciemborowicz posted a v2 patch that addresses Junio C Hamano’s earlier architectural concerns by confining copy/rename state to the destination ref update rather than the transaction as a whole. This redesign preserves the genericity of the transaction interface and enables multi-ref operations (e.g., renaming multiple branches in one transaction). The patch keeps the `REF_TRANSACTION_FLAG_SKIP_HOOK` flag internal to the refs implementation and switches the copy/rename mode parameter from `int` to `bool` for clarity. Both backends (files and reftable) are updated to handle the new per-ref-update state, including backend-specific reflog handling and concurrency checks. Test coverage is thorough, verifying rename, copy, forced updates, D/F conflicts, concurrent updates, and hook-triggered rollback.

The patch is under active review, with no objections raised so far. Karthik Nayak has provided domain expertise (credited as `Helped-by` in v2), and Junio’s prior concerns about scalability and interface design have been addressed. The fix is backwards-compatible and has been present since at least Git 2.28. If no new issues surface, this patch is likely to land in `next` soon.

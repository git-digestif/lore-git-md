This thread is about a bug in Git’s `reference-transaction` hook, which fails to report the creation of a new branch when an existing one is renamed (`git branch -m`) or copied (`git branch -c`). The hook only shows the deletion of the old branch name, leaving the transaction incomplete. Both the files-based and reftable backends are affected, though the reftable backend omits usable rename information entirely. Maciej Ciemborowicz posted a v2 patch to fix this, but Patrick Steinhardt rejected it as unreviewable due to poor code structure, unclear commit messages, and non-idiomatic C patterns—issues he attributed to over-reliance on AI-generated code.

Maciej’s latest response clarifies some technical decisions behind the v2 redesign, such as attaching copy/rename state to individual ref updates rather than the transaction as a whole (a change made to address Junio Hamano’s earlier architectural concerns). He also explains why backend-specific logic is necessary for reflog handling, though he acknowledges this wasn’t well-documented in the commit message. The email includes performance data (e.g., a 137% slowdown for `git branch -c` with a hook in the files backend) but doesn’t address the core code quality issues Steinhardt raised. Maciej admits the patch lacks C expertise and offers to split it into smaller commits or hand it off to Karthik Nayak, who has domain knowledge but hasn’t yet weighed in on the current review.

The thread remains stalled. Steinhardt’s objections are blocking, and Maciej’s response doesn’t resolve them—though it provides useful context for a future rewrite. The bug itself has been present since at least Git 2.28, and the fix would touch `refs.c`, `builtin/branch.c`, and the test suite. No merge status has been reported, and the patch is not under active review until a major rewrite is posted.

This thread reports a bug in Git’s `reference-transaction` hook: when a branch is renamed (`git branch -m`), the hook only sees the deletion of the old branch name, not the creation of the new one. The issue affects both the files-based and reftable backends, with the reftable backend failing more severely by omitting any usable rename payload. Maciej Ciemborowicz provided a reproducer and confirmed the expected behavior using `git update-ref --stdin`, which correctly reports both events in the same transaction.

Karthik Nayak, a ref backend expert, has diagnosed the root cause: branch renames (and copies) bypass the ref transaction mechanism entirely. The files backend uses `refs_delete_ref()`, which triggers the hook for the deletion, while the reftable backend writes a TOMBSTONE entry directly, skipping the hook. Karthik clarified that the "equivalent atomic operation" with `git update-ref --stdin` is a separate delete-and-create command, which *does* use transactions, narrowing the fix to the branch-rename logic. He intends to submit a patch to ensure both deletion and creation events are included in the same transaction, likely targeting `builtin/branch.c` or the ref backend layer. The thread is now focused on implementation, with no remaining debate about the bug’s existence or severity.

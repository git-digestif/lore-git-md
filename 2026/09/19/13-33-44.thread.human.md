This thread is about a bug in Git’s `reference-transaction` hook, which fails to report the creation of a new branch when an existing branch is renamed (`git branch -m`) or copied (`git branch -c`). The hook only sees the deletion of the old branch name, not the creation of the new one, breaking scripts that rely on seeing all ref changes in a transaction. Maciej Ciemborowicz’s four-patch series (now at v4) fixes this for both the files-based and reftable backends.

The latest email covers the second patch, which introduces `ref_transaction_replace_reflog()` to allow replacing a ref’s reflog history without changing the ref itself. This is a prerequisite for the third patch, which integrates branch rename/copy into the ordinary transaction path. The patch stages reflog replacements in temporary files (files backend) or tombstones old entries (reftable) to ensure atomicity and avoid exposing partial changes to hooks. Testing confirms it handles edge cases like null-OID entries and rollback behavior correctly. While the patch itself has negligible performance impact, it compounds the ~137% slowdown for files-based renames with large reflogs introduced in later patches.

The series has made steady progress: Junio’s test breakages from v3 are resolved in v4, and the first patch (infrastructure for `REF_TRANSACTION_FLAG_INTERNAL`) is uncontroversial and ready to proceed. Patrick Steinhardt’s earlier architectural concerns were addressed by splitting the series into focused patches and centralizing hook suppression logic.

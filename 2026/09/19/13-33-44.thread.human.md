This thread began when Maciej Ciemborowicz reported a bug in Git’s `reference-transaction` hook: when a branch is renamed (`git branch -m`) or copied (`git branch -c`), the hook only sees the deletion of the old branch name, not the creation of the new one. Both the files-based and reftable backends were affected, leaving tools that rely on the hook unaware of the full transaction.

After an initial patch (v1) drew architectural concerns from Junio C Hamano—who objected to overloading the generic `ref_transaction` struct with rename-specific fields—Maciej reworked the fix. The v2 patch now confines copy/rename state to the destination ref update rather than the transaction as a whole, preserving the genericity of the transaction interface and enabling multi-ref operations like renaming several branches at once. The `REF_TRANSACTION_FLAG_SKIP_HOOK` flag is kept internal, and the copy/rename mode parameter is now a `bool` for clarity. Both backends are updated, with careful handling of reflog entries and concurrency checks.

The patch includes thorough test coverage for rename, copy, forced updates, D/F conflicts, concurrent updates, and hook-triggered rollback. Karthik Nayak, who helped diagnose the original issue, remains involved, and the solution looks ready for serious review. With Junio’s architectural concerns addressed, this version is likely to land in `next` soon.

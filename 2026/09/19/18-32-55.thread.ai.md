Subject: regression in `git reflog expire` default expiry times (2.50)

Core problem or goal
A regression in Git 2.50 swapped the default expiry times for reachable and unreachable reflog entries in `git reflog expire`. Reachable entries (documented to default to 90 days) now expire after 30 days, while unreachable entries (documented to default to 30 days) are incorrectly retained for 90 days. The bug was introduced by commit `85658275702b` ("builtin/reflog: stop storing default reflog expiry dates globally", 2025-04-08), which reversed the order of `.default_expire_total` and `.default_expire_unreachable` in `reflog.h`.

Current status
The fix (v3) by Pushkar Singh has been **merged to `master`** by Junio C Hamano on 2025-06-12. The regression, introduced in Git 2.50.0 (April 2025), went unnoticed for over a year, indicating low real-world impact. The patch restores the correct default expiry periods (reachable=90d, unreachable=30d) and adds comprehensive test coverage in `t/t1410-reflog.sh` to verify both reachable and unreachable expiry behavior. The regression affected both `git reflog expire` and `git gc` (which calls it internally). Junio’s final approval explicitly stated the patch "looks very good" and is ready for merging, with no further iteration expected. A minor post-merge cleanup suggestion (consolidating timestamp conversion logic in the test file) was noted but deemed outside the scope of this patch. Post-merge discussion between Junio and Patrick Steinhardt clarified test timing thresholds: Junio prefers the current values (60/100 days for reachable, 20/40 days for unreachable) over tighter boundaries (89/90 and 29/30 days) to avoid edge-case ambiguity in `approxidate()` and focus on the core expiry logic. This exchange is purely about test hygiene and does not affect the fix.

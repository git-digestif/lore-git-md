Core problem or goal
A regression in Git 2.50 swapped the default expiry times for reachable and unreachable reflog entries in `git reflog expire`. Reachable entries (documented to default to 90 days) now expire after 30 days, while unreachable entries (documented to default to 30 days) are incorrectly retained for 90 days. The bug was introduced by commit `85658275702b` ("builtin/reflog: stop storing default reflog expiry dates globally", 2025-04-08), which reversed the order of `.default_expire_total` and `.default_expire_unreachable` in `reflog.h`.

Current status
The fix (v3) posted by Pushkar Singh is ready for merging. All review feedback—including Junio’s test-structure concerns, Peff’s commit message clarity request, and Patrick Steinhardt’s fast-track proposal—has been fully addressed. Junio C Hamano has explicitly stated that the regression, introduced in Git 2.50.0 (April 2025), has gone unnoticed for over a year, indicating low real-world impact. While he does not object to merging the fix for Git 2.56, the tone suggests reduced urgency. The patch restores the correct default expiry periods (reachable=90d, unreachable=30d) and adds comprehensive test coverage in `t/t1410-reflog.sh` to verify both reachable and unreachable expiry behavior. The regression affects both `git reflog expire` and `git gc` (which calls it internally), but with no reported user complaints, the fix is now more about correctness than urgency. The series is uncontroversial, narrowly targeted, and ready for merging to `master`; the only remaining question is whether Junio will merge it for the 2.56 cycle or defer to the next one.

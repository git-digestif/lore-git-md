This is a **bugfix** targeting the reference-transaction hook.

The email reports a regression introduced in Git 2.31: when a branch or tag is deleted using high-level commands like `git branch -d` or `git tag -d`, the reference-transaction hook now receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The same issue affects `git remote prune` deletions. Direct deletion via `git update-ref -d` still works as expected, providing the old OID followed by all-zeros.

The author provides a minimal reproducer (a shell script) that demonstrates the problem across both the files and reftable backends, confirming the behavior persists through Git 2.55. They note that the documentation allows all-zero old OIDs for force-updates, but argue this case—where Git has already resolved the ref being deleted—should preserve the old OID for safety-checked deletions. The question is whether this change was intentional or an oversight.

Key technical details: the regression affects the `reference-transaction` hook, which is used by tools like Gerrit, GitLab, and custom CI systems to monitor ref changes. The loss of the old OID breaks workflows that rely on tracking the exact commit a branch or tag pointed to before deletion. The author’s compatibility testing (linked in the email) spans multiple Git versions and backends, suggesting thorough investigation. No prior discussion or rationale for the change is mentioned, leaving the intent unclear.

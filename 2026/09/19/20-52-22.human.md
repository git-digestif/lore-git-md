This is a bugfix discussion targeting the ref backend and hook infrastructure. Karthik Nayak, a contributor with deep ref-backend expertise, replies to Maciej Ciemborowicz’s bug report about the `reference-transaction` hook omitting the new ref when a branch is renamed with `` `git branch -m` ``.

Karthik confirms the issue and explains why it happens: neither branch copy nor rename operations currently use a transaction, so the hook is not triggered for the new ref. In the files backend, the old ref is deleted via `refs_delete_ref()` (which *does* use a transaction), but the new ref is created outside it. The reftable backend is even simpler—it just writes a TOMBSTONE entry for the old ref, skipping the hook entirely. He notes that the equivalent atomic operation via `` `git update-ref --stdin` `` (a delete followed by a create) *does* report both refs correctly, reinforcing that the hook should see both sides of a rename.

The discussion is still in the diagnostic phase; no patch has been posted yet. Karthik volunteers to write one if Maciej does not. The fix will likely involve plumbing the branch-rename logic into the transaction machinery so that both the deletion and creation are reported in a single hook invocation. This is a clear, well-motivated bug with a straightforward reproducer, so expect a patch soon.

This is a **substantive review** of Derrick Stolee’s RFC series introducing a "safe" `strbuf` API that avoids `die()` calls. Phillip Wood’s reply engages deeply with the technical approach, naming conventions, and implementation details, raising several concerns that could shape the series’ future direction.

Phillip **supports the goal** of APIs that return errors instead of dying on allocation failures, citing precedent in the `xdiff` and `reftable` subsystems. However, he **questions the "safe" framing**, arguing the distinction should focus on error-handling behavior rather than safety. He suggests the documentation and naming (e.g., `sstrbuf_*`) should emphasize error returns explicitly, rather than implying broader safety guarantees.

A **key technical critique** targets the `sstrbuf_grow()` implementation in patch 4, which calls `st_add3()`—a function that itself dies on overflow. Phillip points out this violates the safe API’s core promise and undermines the CodeQL verification Stolee relies on. This is a concrete bug that would need fixing before the series could proceed.

Phillip also **proposes an alternative design**: a "sticky error bit" for `strbuf`, similar to `stdio`’s error flags, allowing callers to check for failures once after a sequence of operations rather than after every call. This would reduce the ergonomic burden of error-checking while preserving the no-`die()` guarantee. The suggestion is pragmatic and addresses Stolee’s concern about the overhead of pervasive error checks.

The review **touches on broader questions** raised in the RFC:
- Whether the safe API should be opt-in (as proposed) or eventually replace the existing `strbuf` API in critical paths.
- How to handle the incomplete transition in `json-writer.c`, where some methods are safe but callers aren’t yet error-aware.
- The fate of `GIT_ALLOC_LIMIT` (Phillip doesn’t weigh in on the rename debate but acknowledges the Hyrum’s Law concern).

Phillip’s feedback is **constructive and actionable**, focusing on design trade-offs rather than nitpicks. His critique of the `st_add3()` call is particularly damning for the current implementation, while his error-bit proposal offers a plausible path forward. The review suggests the series is worth pursuing but needs refinement—especially around naming, documentation, and the sticky-error design—to gain broader acceptance.

## 2026/09/19

- [2026/09/19/13-33-44 by Maciej Ciemborowicz <maciej.ciemborowicz@gmail.com>] Maciej Ciemborowicz reported that `git branch -m old new` does not report the destination ref to the reference-transaction hook: the files backend reports only the deletion of `refs/heads/old`, the reftable backend reports no usable rename payload, while the equivalent `git update-ref --stdin` reports both updates; the behavior was observed across Git 2.28–2.55.
- [2026/09/19/20-52-22 by Karthik Nayak <karthik.188@gmail.com>] Karthik Nayak explained that branch copy and rename do not use a transaction and therefore do not trigger the reference-transaction hook, which he called absurd; he noted that the files backend reports the old ref deletion because it calls `refs_delete_ref()` within a transaction, whereas reftable writes a TOMBSTONE entry without calling `refs_delete_ref()`; he asked whether the equivalent atomic operation meant a delete and create command, stated that the issue should be fixed, and offered to look into it if Maciej Ciemborowicz was not submitting a patch himself.

## 2026/09/20

- [2026/09/20/16-50-37 by Maciej Ciemborowicz <maciej.ciemborowicz@gmail.com>] Maciej Ciemborowicz posted a patch routing reference copy and rename operations through the transaction API so the reference-transaction hook observes them as logical transactions (a rename as a deletion of the old reference plus creation of the new reference in the same transaction), retaining backend-specific reflog handling, suppressing hooks for the files backend's nested deletion transactions, recording and verifying source and destination values after taking backend locks to reject concurrent changes, preserving D/F renames, restoring overwritten references and reflogs when a prepared hook rejects the operation, and adding test coverage for rename, copy, forced updates, both directions of D/F conflicts, concurrent updates, and prepared-hook rollback.

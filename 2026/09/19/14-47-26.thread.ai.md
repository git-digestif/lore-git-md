Subject: [PATCH] fetch: introduce `+:` refspec for matching-inspired fetch mode

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using `remote.<name>.refmap` to separate namespace mappings from fetch selection logic.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. This design is consensus-approved and remains unchanged. The configuration knob is added in Patch 1/5, mirroring `remote.<name>.fetch` but only providing a default for `--refmap` when there is something explicit to fetch (command-line refspecs or `remote.<name>.fetch`). If both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, the former takes precedence.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`). The forced inclusion of the remote’s default branch (present in v3) is removed. The `branches_tracking_remote()` helper in `remote.c` implements this logic, and `get_ref_map()` in `builtin/fetch.c` integrates it. The helper iterates over all local branches, collects the source ref for each branch whose `remote_name` matches the target remote, and constructs a dynamic refspec from these branches. The `do_fetch()` function populates `transport_ls_refs_options.ref_prefixes` with the inferred branches to limit the transport layer’s ref requests. The existing "fetch branches merged into the current branch" logic is now extracted into a shared helper (`collect_upstream_from_remote`, introduced in Patch 2/5) to reduce duplication. The helper takes a `struct repository *`, a `string_list` to populate, a `remote`, and an optional branch name (NULL means the current branch), and adds the upstream refs of any matching branches to the list.
- **Precedence rule**: When both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, `remote.<name>.fetch` takes precedence, and the `refmap` setting is ignored. This resolves the fatal error ("--refmap option is only meaningful with command-line refspec") and is now uncontroversial.
- **`--limited-fetch` flag**: Added in Patch 4/5 to `git remote add`, this flag configures the remote to use `remote.<name>.refmap` (e.g., `+refs/heads/*:refs/remotes/<name>/*`) instead of the traditional wildcard `remote.<name>.fetch` refspec. The flag is rejected when combined with `-t/--track` or `--mirror`, as those options already specify explicit fetch behavior. The implementation updates `builtin/remote.c` to set the refmap configuration and adds documentation to `git-remote.adoc`. Patch 5/5 makes `--limited-fetch` the default for shallow repositories by checking `is_repository_shallow(the_repository)` when `limited_fetch` is unset (`-1`), defaulting to `--limited-fetch` unless `--no-limited-fetch` is given. Test coverage in `t/t5505-remote.sh` verifies the flag’s behavior and conflict resolution with `-t`, as well as the shallow-repository default and `--no-limited-fetch` override.

- **Behavior**:
  - The remote’s default branch is no longer fetched by default.
  - Non-shallow repositories continue using wildcard refspecs by default.
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories now default to it.
  - No on-disk format changes beyond the new configuration entries in `.git/config`.
  - Edge case: A bare `git fetch` against a refmap-only remote with no tracked branches fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use.

Open questions and loose ends
1. **Design choice**: Whether the matching-inspired mode should be available outside of shallow repositories. This is a minor design choice that can be addressed in follow-up work.
2. **Edge-case handling**:
   - How should the implementation handle remotes with no default branch?
   - Should existing shallow repositories with wildcard refspecs be migrated automatically?
   - Should there be a warning for users who might rely on the old behavior?
3. **Backward compatibility**: The v8 series preserves backward compatibility for non-shallow repositories but does not address migration of existing shallow repositories. This is not a blocker for merging.

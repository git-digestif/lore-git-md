Thread identity: Subject `[PATCH] fetch: introduce `+:` refspec for matching-inspired fetch mode`, series v15 (7 patches), originating author Harald Nordgren, thread type patch series. The current email is v15 patch 7/7, the final patch in the series, which changes the default behavior of `git remote add` in shallow repositories to use limited-fetch semantics.

Core problem or goal: Users of shallow repositories experience slow or hanging `git fetch`/`git pull` when the remote has many branches. The series implements a matching-inspired fetch mode using explicit configuration (`remote.<name>.fetchUpstreams` and `remote.<name>.fetchRefmap`) to decouple which refs are fetched from where they are stored. Patch 3/7 established `remote.<name>.fetchRefmap` mirroring how `remote.<name>.fetch` supplies default refspecs. Patch 4/7 extracted upstream collection into `collect_upstream_from_remote()`. Patch 5/7 makes a refspec-less `git fetch <name>` additionally fetch upstream branches that local branches track on that remote when `fetchUpstreams` is enabled. The setting controls only what is fetched; storage remains governed by `remote.<name>.fetch` and `remote.<name>.fetchRefmap`, so a remote with `fetchUpstreams` plus a `fetchRefmap` but no `fetch` refspec effectively limits fetching to locally tracked branches. Patch 6/7 adds the `--limited-fetch`/`--no-limited-fetch` CLI option to `git remote add` as a convenience layer that sets `remote.<name>.fetchRefmap` to `+refs/heads/*:refs/remotes/<name>/*` and `remote.<name>.fetchUpstreams` to `true` while omitting `remote.<name>.fetch`. Patch 7/7 makes this limited-fetch configuration the default for `git remote add` in shallow repositories unless `-t`/`--track` or `--mirror` is specified, preventing slow fetches in shallow clones by default while allowing `--no-limited-fetch` to restore the traditional wildcard behavior.

Key technical details: Patch 3/7 added `struct refspec refmap` to `struct remote` in `remote.h`, parsed the `fetchrefmap` subkey in `remote.c`'s `handle_config()`, and initialized/cleared it in `make_remote()`/`remote_clear()`. In `builtin/fetch.c`, `get_ref_map()` computes an `effective_refmap` preferring command-line `--refmap` but falling back to `remote->refmap`, applying it via `map_refs_without_dst()` only to destination-less entries. `remote_find_tracking()` consults the refmap when `remote.<name>.fetch` yields no match, enabling `@{upstream}` resolution and `git branch --track` for refmap-stored branches while honoring negative refspecs. Patch 4/7 extracted the inlined `do_fetch()` logic that checks whether a branch has merge configuration pointing at the specified remote and pushes `branch->merge[i]->src` into a `strvec` into `collect_upstream_from_remote(struct remote *remote, const char *refname, struct strvec *refs)` in `remote.c`/`remote.h`; the existing call site passes NULL for refname to preserve behavior established by commit 49ca2fba39 (2022). Patch 5/7 adds `bool fetch_upstreams` to `struct remote`, parsed in `handle_config()` via the `fetchupstreams` subkey. It introduces `branches_tracking_remote()` in `remote.c`, which iterates local branches with `refs_for_each_branch_ref()` and the `add_if_tracking_remote()` callback, calling `collect_upstream_from_remote()` with each branch's refname. In `builtin/fetch.c`, `add_branch_upstreams()` calls `branches_tracking_remote()` and converts each upstream into a destination-less refspec item fed through `get_fetch_map()`, skipping upstreams already present. Both `get_ref_map()` and `do_fetch()` check `remote->fetch_upstreams` to invoke this collection alongside existing `remote->fetch` processing, ensuring transport ls-refs prefixes include the upstreams even without explicit refspecs. Patch 5/7 also extends `tracking_for_push_dest()` so `@{push}` consults `remote->refmap` via `apply_refspecs()` when `remote->fetch` yields no match. Patch 6/7 modifies the `add()` function in `builtin/remote.c`: a new `limited_fetch` variable initialized to `-1` is parsed via `OPT_BOOL`; the code dies with a fatal error if `limited_fetch == 1` is combined with `track.nr` (`-t`/`--track`) or `mirror` (`--mirror`), and when set without conflicts it writes `remote.<name>.fetchRefmap` = `+refs/heads/*:refs/remotes/<name>/*` and `remote.<name>.fetchUpstreams` = `true` instead of calling `add_branch()` for the traditional wildcard fetch refspec. Patch 7/7 modifies the same `add()` function to consult `is_repository_shallow(the_repository)` (including `shallow.h`) when `--limited-fetch` was not explicitly given: in a shallow repository, unless `-t`/`--track` or `--mirror` is present, the default becomes limited-fetch semantics (setting `fetchRefmap` and `fetchUpstreams` while omitting `fetch`), whereas full repositories continue to receive the traditional wildcard `remote.<name>.fetch` refspec; `--no-limited-fetch` explicitly disables the shallow default. Tests are in `t/t5586-fetch-refmap.sh` (for patches 3-5, covering baseline behavior without `fetchUpstreams`, one-time tracking fetches, later plain fetches updating tracked branches, deduplication when multiple local branches track the same upstream, exclusion of branches tracking other remotes, combination of `remote.<name>.fetch` with upstreams, `--prefetch` storage under `refs/prefetch/`, `git pull` merging only the current branch's upstream, and `@{push}` resolution; earlier tests also live in `t/t5510-fetch.sh`) and `t/t5505-remote.sh` (for patches 6/7 and 7/7, verifying the explicit option works in a full clone, that the two new config keys are set correctly, that `remote.<name>.fetch` is absent, that combining `--limited-fetch` with `-t` fails, that shallow repositories default to limited-fetch with both config keys set and `fetch` absent while performing a functional fetch that only updates the tracked branch, that `--no-limited-fetch` overrides the shallow default, that `-t` interacts correctly in shallow repos, and that full repositories keep the wildcard refspec).

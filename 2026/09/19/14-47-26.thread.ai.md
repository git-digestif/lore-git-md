Thread identity
Subject: [PATCH] fetch: introduce `fetch.shallow` config to restrict refspec-less fetches to current branch
Series version: v1 (initial submission; abandoned in favor of alternative design consensus)
Originating author: Harald Nordgren
Thread type: patch series (single patch, now superseded by evolving design discussion)

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread initially proposed a new `fetch.shallow` configuration option to restrict such fetches to the current branch’s upstream, but has now converged on addressing the root cause: wildcard fetch refspecs in shallow repositories. The current focus is on designing a solution that avoids unnecessary negotiation without requiring network calls or introducing new configuration options. Two alternative approaches are under active discussion: (1) modifying `git remote add` to default to narrower refspecs in shallow repositories, and (2) introducing a new "matching-inspired" fetch mode for `git fetch` that dynamically determines which remote branches to fetch based on local branches’ upstream settings, with the refinement that the remote’s default branch should always be fetched regardless of tracking relationships.

Current status
Design consensus reached to abandon the original `fetch.shallow` patch. No code changes have been implemented for either alternative solution. Discussion is now focused on refining the two proposed approaches:
- **Narrower refspec in `git remote add`**: Default to a single-branch refspec (e.g., `+refs/heads/<branch>:refs/remotes/<name>/<branch>`) for new remotes in shallow repositories, using the local repository’s current branch or the remote’s `HEAD` as a proxy for the remote’s default branch. This approach avoids network calls but may result in stale or incorrect refspecs.
- **Matching-inspired fetch mode**: Introduce a new fetch mode (triggered by a special refspec syntax like `:` or `+:`) that dynamically fetches only the remote branches tracked by local branches, **plus the remote’s default branch** (as proposed by Harald Nordgren). This approach avoids network calls and relies on existing tracking relationships, but the addition of the default branch ensures usability in common workflows (e.g., setting upstream to the remote’s default branch without requiring an explicit `git remote set-head` call). Open questions remain about how to determine the remote’s default branch without a network call and how this mode would integrate with `git remote add`.

The two approaches are not mutually exclusive and could coexist, but the discussion has not yet clarified how they would integrate or which would take precedence in shallow repositories.

Key technical details
- **Original patch (abandoned)**:
  - Files touched: `builtin/fetch.c`, `Documentation/config/fetch.adoc`, `t/t5537-fetch-shallow.sh` (new test section)
  - Proposed config key: `fetch.shallow` (boolean, default `false`)
  - Behavior: when `fetch.shallow=true` and the repository is shallow, a refspec-less fetch would only fetch the current branch’s upstream
  - Test coverage: verified narrowing to tracked branch, correct update of `refs/remotes/<name>/HEAD`, no effect on non-shallow repositories or non-tracked remotes, and edge cases (stale `HEAD`, `fetch.followRemoteHEAD` interaction)
- **Alternative solution 1: Narrower refspec in `git remote add`**:
  - Target: `git remote add` behavior in shallow repositories
  - Proposed change: default to a narrower refspec (e.g., `+refs/heads/<branch>:refs/remotes/<name>/<branch>`) instead of the current wildcard (`+refs/heads/*:refs/remotes/<name>/*`) for new remotes in shallow repositories
  - Scope: affects only shallow repositories; non-shallow repositories would continue to default to wildcard refspecs
  - On-disk impact: changes the default refspec stored in `.git/config` for new remotes in shallow repositories
  - Open question: how to determine `<branch>` without a network call (options: local current branch, remote `HEAD`, or user-specified config)
- **Alternative solution 2: Matching-inspired fetch mode (refined)**:
  - Proposed behavior: `git fetch` inspects local branches with `@{upstream}` configured to the remote being fetched, then fetches only the corresponding remote branches **plus the remote’s default branch** (as proposed by Harald Nordgren). For example, if local branch `feature` tracks `origin/main` and the remote’s default branch is `main`, `git fetch origin` would fetch `refs/heads/main` from `origin` (even if no local branch explicitly tracks it).
  - Proposed refspec syntax: special token (e.g., `:` or `+:`) to trigger the mode, analogous to `git push`’s matching mode
  - Key difference from push: no one-to-one correspondence enforced (e.g., multiple local branches tracking the same remote branch would fetch that remote branch once)
  - Scope: limited to determining which remote branches to fetch; does not affect how they are stored locally
  - Open questions: integration with `git remote add`, default behavior in shallow repositories, handling of edge cases (e.g., no local branches tracking the remote), exact refspec syntax, and **how to determine the remote’s default branch without a network call** (options: remote `HEAD`, local current branch, or user-specified config)

Open questions and loose ends
1. **Refspec construction for narrower refspec approach**:
   - How should `git remote add` determine the narrower refspec without making a network call to the remote?
     - Use the local repository’s current branch as a proxy for the remote’s default branch?
     - Rely on the remote’s `HEAD` (which may be stale)?
     - Introduce a new configuration option (e.g., `remote.<name>.defaultBranch`) to allow users to specify the branch explicitly?
   - Should the narrower refspec be constructed using the remote’s default branch (as determined by `HEAD`) or the local repository’s current branch?
   - Should there be a way for users to opt into wildcard refspecs for shallow repositories (e.g., via a `--wildcard` flag or manual refspec edit)?
2. **Matching-inspired fetch mode (refined)**:
   - What should the exact refspec syntax be (e.g., `:` or `+:`)?
   - How should this mode handle edge cases, such as when no local branches track the remote being fetched? (Harald’s proposal ensures the default branch is always fetched, mitigating this issue.)
   - Should this mode be the default for shallow repositories, or should it be opt-in?
   - How would this mode integrate with `git remote add`? Would it replace the narrower refspec idea or coexist with it?
   - Would this mode be useful outside of shallow repositories, or is it primarily a solution for the shallow repository performance issue?
   - **How to determine the remote’s default branch without a network call?** (Options: remote `HEAD`, local current branch, or user-specified config.)
3. **Backwards compatibility**:
   - The alternative solutions must preserve existing workflows for non-shallow repositories (wildcard refspecs remain the default).
   - How should existing shallow repositories with wildcard refspecs be handled? Should `git remote add` warn or offer a migration path?
4. **Scope of the performance issue**:
   - Confirmed to affect any shallow repository with many remote-tracking branches, not just sparse checkouts.
   - Neither alternative solution fully addresses existing shallow repositories with wildcard refspecs; the narrower refspec approach would only affect new remotes, and the matching-inspired fetch mode would require users to manually update their fetch refspecs or use the new mode explicitly.
5. **Implementation priority**:
   - Which approach should be prioritized for implementation: the narrower refspec in `git remote add` or the matching-inspired fetch mode?
   - Could the two approaches coexist, and if so, how would they interact? For example, would the matching-inspired fetch mode override the narrower refspec in shallow repositories, or would they complement each other?

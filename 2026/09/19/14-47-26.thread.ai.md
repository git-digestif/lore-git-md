Subject: [PATCH] fetch: introduce `+:` refspec for matching-inspired fetch mode
Series version: v2 (implements the matching-inspired fetch mode design; replaces abandoned `fetch.shallow` v1)
Originating author: Harald Nordgren
Thread type: patch series (single patch, implementing consensus design)

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread has converged on addressing the root cause by introducing a new "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, **plus the remote’s default branch**. This patch implements that design, making it the default for `git remote add` in shallow repositories while preserving wildcard refspecs for non-shallow repositories.

Current status
The original `fetch.shallow` patch (v1) has been abandoned in favor of this implementation. The patch is now under review. It introduces the special refspec `+:` (or `:` for non-forced updates) and modifies `git remote add` to default to this refspec in shallow repositories. The design addresses the performance issue without requiring new configuration options and integrates cleanly with existing workflows. Key technical details and edge cases (e.g., stale `HEAD`, multiple tracking branches) are covered by new test cases in `t/t5585-fetch-tracking-refspec.sh`.

Key technical details
- **New refspec syntax**: `+:` (or `:`) triggers the matching-inspired fetch mode, fetching only branches tracked by local branches at the remote being fetched, plus the remote’s default branch.
- **Files touched**:
  - `builtin/fetch.c`: Core logic for the new refspec and its integration with fetch.
  - `builtin/remote.c`: Default refspec selection in shallow repositories (now defaults to `+:`).
  - `refspec.c`/`refspec.h`: Parsing and representation of the new refspec (adds `tracking` flag to `struct refspec_item`).
  - `remote.c`/`remote.h`: Helper functions (`branches_tracking_remote()`) to enumerate branches tracking a remote.
  - `Documentation/git-remote.adoc` and `Documentation/pull-fetch-param.adoc`: Documentation updates for the new refspec and behavior.
  - `t/t5585-fetch-tracking-refspec.sh`: New test script covering the new behavior, including edge cases (e.g., multiple local branches tracking the same remote branch, branches tracking different remotes).
- **Behavior**:
  - In shallow repositories, `git remote add` now defaults to `+:` instead of the traditional wildcard `+refs/heads/*:refs/remotes/<name>/*`.
  - The remote’s default branch is always fetched, even if no local branch tracks it yet (priming mechanism).
  - Non-shallow repositories continue to use wildcard refspecs by default (backward compatibility preserved).
- **On-disk impact**: Changes the default refspec stored in `.git/config` for new remotes in shallow repositories.
- **Test coverage**: Verifies the new refspec behavior, integration with `git remote add`, edge cases (stale `HEAD`, multiple tracking branches), and backward compatibility.

Open questions and loose ends
1. **Refspec syntax**: Is `+:` (or `:`) the best choice, or would an alternative (e.g., `+:`) be clearer?
2. **Priming mechanism**: The remote’s default branch is always fetched, but how should stale or missing `HEAD` information be handled? (Current implementation falls back to the local current branch, but this may not always be correct.)
3. **Integration with `git remote add`**: Should the narrower refspec (`+:`) be the default for all shallow repositories, or should users be required to opt in (e.g., via `--fetch`)?
4. **Backward compatibility**:
   - How should existing shallow repositories with wildcard refspecs be handled? Should `git remote add` warn or offer a migration path?
   - Should there be an escape hatch (e.g., `--wildcard`) to opt into traditional behavior for shallow repositories?
5. **Edge cases**:
   - How should the implementation handle remotes with no default branch (e.g., empty repositories)?
   - Should the matching-inspired mode be available outside of shallow repositories, or is it strictly a shallow-repository optimization?
6. **Transition plan**: If the matching-inspired mode becomes the default for shallow repositories, should there be a phased rollout or warnings for existing users?
7. **Documentation**: Are the updates to `git-remote.adoc` and `pull-fetch-param.adoc` sufficient, or should additional guidance be added for users migrating from wildcard refspecs?

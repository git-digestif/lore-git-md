Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using `remote.<name>.refmap` to separate namespace mappings from fetch selection logic.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. The configuration knob is added in Patch 1/5, mirroring `remote.<name>.fetch` but only providing a default for `--refmap` when there is something explicit to fetch (command-line refspecs or `remote.<name>.fetch`). If both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, the former takes precedence.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`). The `branches_tracking_remote()` helper in `remote.c` implements this logic, iterating over all local branches and collecting the source ref for each branch whose `remote_name` matches the target remote. The `get_ref_map()` function in `builtin/fetch.c` integrates this logic, constructing a dynamic refspec from the inferred branches. The `do_fetch()` function populates `transport_ls_refs_options.ref_prefixes` with the inferred branches to limit the transport layer’s ref requests. The existing "fetch branches merged into the current branch" logic is extracted into a shared helper (`collect_upstream_from_remote`, introduced in Patch 2/5) to reduce duplication. The helper takes a `struct repository *`, a `string_list` to populate, a `remote`, and an optional branch name (NULL means the current branch), and adds the upstream refs of any matching branches to the list. Junio’s review requirements are fully addressed: (1) the `if/else if/else` control-flow reorganization is now in Patch 3/5, and (2) the NULL-check for `branch` is restored in `collect_upstream_from_remote()` via `repo_branch_get(repo, refname)`. **Patch 2/5 and Patch 3/5 will be updated to use `strvec` instead of `string_list` for efficiency, and their commit messages will be rewritten to include concrete examples (e.g., `git clone --single-branch` followed by `git push -u`).** The documentation in `fetch-options.adoc` will be updated to replace the vague phrase "branches from the remote that are used as the `@{upstream}` of our local branches" with the more precise "remote-tracking branches from this remote that are also configured as the `@{upstream}` of a local branch are fetched."
- **Precedence rule**: When both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, `remote.<name>.fetch` takes precedence, and the `refmap` setting is ignored. This resolves the fatal error ("--refmap option is only meaningful with command-line refspec") and is uncontroversial.
- **`--limited-fetch` flag**: Added in Patch 4/5 to `git remote add`, this flag configures the remote to use `remote.<name>.refmap` (e.g., `+refs/heads/*:refs/remotes/<name>/*`) instead of the traditional wildcard `remote.<name>.fetch` refspec. The flag is rejected when combined with `-t/--track` or `--mirror`, as those options already specify explicit fetch behavior. The implementation updates `builtin/remote.c` to set the refmap configuration via `repo_config_set()` and adds documentation to `git-remote.adoc`. Four new tests in `t/t5505-remote.sh` verify the flag’s behavior, conflict with `-t`, and absence of interference with existing functionality.
- **Shallow-repository default**: Patch 5/5 makes `--limited-fetch` the default when adding a remote in a shallow repository by checking `is_repository_shallow(the_repository)` when `limited_fetch` is unset (`-1`), defaulting to `--limited-fetch` unless `--no-limited-fetch` is given. This is implemented in `builtin/remote.c` without introducing new technical debt. The shallow check uses the existing `is_repository_shallow()` helper, and the logic reuses the existing `limited_fetch` machinery. The documentation in `git-remote.adoc` is updated to explain the new default behavior. **The commit message for Patch 5/5 has been updated to clarify that the default applies to all shallow repositories, not just single-branch shallow clones, as Git has no reliable way to track whether a repository was cloned with `--single-branch`.**
- **Fallback logic in `remote_find_tracking()`**: Patch 1/5 modifies `remote_find_tracking()` in `remote.c` to fall back to `remote->refmap` **only when `remote->fetch` is either empty or contains no matching refspec for the given query**. This ensures the function treats `remote->refmap` as a superset of `remote->fetch` while avoiding unintended side effects (e.g., for `--delete-merged`). The change replaces the original two-branch `if/else` with a single condition that checks both the presence of `remote->fetch` refspecs and the success of `refspec_find_match()`. **Harald Nordgren’s clarification confirms this fallback is necessary for compatibility with existing Git operations (`@{upstream}`, `--delete-merged`, `git branch --track`) and does not conflict with `--limited-fetch`.** Two new tests will verify: (1) refs fetched via refmap are correctly tracked (e.g., for `@{upstream}`), and (2) negative refspecs in `remote.<name>.fetch` continue to exclude refs as expected.
- **Code deduplication**: The next revision will refactor the duplicate code in `do_fetch()` where the `follow_remote_head` logic and `collect_upstream_from_remote()` call appear in two nearly identical blocks, addressing D. Ben Knoble’s observation about redundancy.

- **Behavior**:
  - The remote’s default branch is no longer fetched by default.
  - Non-shallow repositories continue using wildcard refspecs by default.
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories now default to it.
  - No on-disk format changes beyond the new configuration entries in `.git/config`.
  - Edge case: A bare `git fetch` against a refmap-only remote with no tracked branches fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use.

Thread identity: Subject `[PATCH] fetch: introduce `+:` refspec for matching-inspired fetch mode`, series v16 (7 patches), originating author Harald Nordgren, thread type patch series. The series implements a matching-inspired fetch mode using explicit configuration (`remote.<name>.fetchUpstreams` and `remote.<name>.fetchRefmap`) to decouple which refs are fetched from where they are stored, addressing slow or hanging `git fetch`/`git pull` in shallow repositories with many remote branches.

Core problem or goal: Users of shallow repositories experience degraded fetch performance when the remote has many branches. The series implements limited-fetch semantics where only locally tracked upstream branches are fetched by default, configurable via `remote.<name>.fetchUpstreams` (boolean) and `remote.<name>.fetchRefmap` (refspec mapping), with `git remote add` defaulting to this mode in shallow repositories unless `-t`/`--track` or `--mirror` is specified.

Patch 1/7 establishes `map_refs_without_dst()` in `builtin/fetch.c` to skip refmap application for refspecs with explicit non-empty destinations; patch 2/7 builds override semantics by removing the fatal error in `get_ref_map()` when `--refmap` is supplied without command-line refspecs, instead applying the refmap to configured `remote.<name>.fetch` entries via new helpers `drop_destinations()` and `map_refs_without_dst()`; patch 3/7 implements `remote.<name>.fetchRefmap` config infrastructure; patch 4/7 refactors upstream collection into `collect_upstream_from_remote()`; patch 5/7 implements `fetchUpstreams`; patch 6/7 adds `--limited-fetch`/`--no-limited-fetch` CLI to `git remote add`; patch 7/7 makes limited-fetch the default for `git remote add` in shallow repositories. Key technical details: Patch 1/7 introduces `map_refs_without_dst()` relying on `rm->peer_ref` being NULL to distinguish destination-less or empty-destination refspecs from those with explicit destinations, ensuring `copy_ref()` does not recurse and `get_fetch_map()` allocates fresh entries for refmap application; semantics validated such that `refs/heads/main` and `refs/heads/next:` (empty `<dst>`) remain subject to `--refmap`/`fetchRefmap` while `refs/heads/seen:refs/remotes/origin/seen` (non-empty `<dst>`) bypasses the refmap and is stored only at the explicit destination. Patch 2/7 adds `drop_destinations()` helper in `builtin/fetch.c` that clears `peer_ref` on refspec items to make them destination-less before refmap application; modifies `get_ref_map()` to remove the fatal error when `--refmap` is given without CLI refspecs, instead calling `drop_destinations()` and `map_refs_without_dst()` when `refmap.nr` is non-zero, setting `*autotags = 1` if any refs result from the mapping; the error is preserved only when there are no refspecs to fetch at all (e.g., bare URL with no configured `remote.<name>.fetch`). Tags are followed when fetched refs end up stored somewhere through the refmap, but `--refmap=""` stores nothing and follows no tags. When `--prune` is used with `--refmap` and no command-line refspecs, `do_fetch()` skips pruning the configured `remote.<name>.fetch` destinations since the fetch does not store there; destinations created by the refmap itself are also not pruned. Tests in `t/t5510-fetch.sh` cover: `--refmap` without CLI refspecs stores at refmap destination while leaving original `refs/remotes/origin/main` untouched; destination-less configured refspecs store through refmap and follow tags; `--refmap=""` does not follow tags; `--prune` with `--refmap` leaves configured destinations intact; `--refmap` still rejected when fetching from URL with no refspecs configured. Documentation in `Documentation/fetch-options.adoc` clarifies command-line refspecs with non-empty destinations bypass the refmap, while without command-line refspecs the configured refspecs decide what is fetched but the refmap decides where it is stored. Patch 3/7 added `struct refspec refmap` to `struct remote` in `remote.h`, parsed the `fetchrefmap` subkey in `remote.c`'s `handle_config()`, and initialized/cleared it in `make_remote()`/`remote_clear()`; `get_ref_map()` computes `effective_refmap` preferring `--refmap` over `remote->refmap`, applying it via `map_refs_without_dst()` only to destination-less entries; `remote_find_tracking()` consults the refmap when `remote.<name>.fetch` yields no match. Patch 4/7 extracted `collect_upstream_from_remote(struct remote *remote, const char *refname, struct strvec *refs)` in `remote.c`/`remote.h`, with the existing call site passing NULL to preserve behavior from commit 49ca2fba39 (2022). Patch 5/7 adds `bool fetch_upstreams` to `struct remote` parsed via the `fetchupstreams` subkey, introduces `branches_tracking_remote()` in `remote.c` iterating local branches via `refs_for_each_branch_ref()` and `add_if_tracking_remote()` calling `collect_upstream_from_remote()` per branch, and adds `add_branch_upstreams()` in `builtin/fetch.c` converting upstreams to destination-less refspec items fed through `get_fetch_map()`; both `get_ref_map()` and `do_fetch()` check `remote->fetch_upstreams`; `tracking_for_push_dest()` extended so `@{push}` consults `remote->refmap` via `apply_refspecs()`. Patch 6/7 modifies `add()` in `builtin/remote.c` with `OPT_BOOL` for `limited_fetch` (init -1), dying if combined with `-t`/`--track` or `--mirror`, otherwise writing `remote.<name>.fetchRefmap` = `+refs/heads/*:refs/remotes/<name>/*` and `remote.<name>.fetchUpstreams` = `true` instead of the traditional wildcard fetch refspec. Patch 7/7 consults `is_repository_shallow(the_repository)` when `--limited-fetch` not explicit: shallow repositories default to limited-fetch semantics unless `-t`/`--track` or `--mirror` present, while full repositories keep wildcard `remote.<name>.fetch`; `--no-limited-fetch` explicitly disables. Tests in `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh`, and `t/t5505-remote.sh`; documentation in `Documentation/config/remote.adoc`, `Documentation/fetch-options.adoc`, and `Documentation/git-remote.adoc`.

Changes between v15 and v16: v16 addresses the three unresolved concerns Junio C Hamano raised on v15 patch 2/7. (1) `--refmap` is rejected again when the remote has nothing configured to fetch (e.g., a bare URL), preventing the silent ignoring of the refmap while fetching HEAD into FETCH_HEAD. (2) Tags are now followed when a refspec-less fetch stores refs through `--refmap` or `fetchRefmap`, while `--refmap=""` stores nothing and follows no tags, resolving the `*autotags` computation timing issue. (3) `--prune` with `--refmap` and no command-line refspecs no longer prunes the configured destinations in `remote.<name>.fetch`, leaving them untouched since the fetch does not store there, fixing the `prune_refs()` refspec source issue. Documentation clarifies that destinations from a refmap are not pruned and that non-empty destinations are exempt from refmap application.

Thread identity
Subject: [PATCH] fetch: introduce `+:` refspec for matching-inspired fetch mode
Series version: v3 (implementing Junio’s `remote.<name>.refmap` design; replaces v2)
Originating author: Harald Nordgren
Thread type: patch series (multi-patch)

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread has converged on addressing the root cause by introducing a new "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, **plus the remote’s default branch**. The design uses `remote.<name>.refmap` to define namespace mappings, separating the "where to store" logic from the "what to fetch" logic and enabling the new mode without escape hatches or transition plans.

Current status
The v3 series implements the `remote.<name>.refmap`-based design proposed by Junio and replaces the abandoned v2 `+:` refspec. The series consists of four patches:
1. **Patch 1/4**: Introduces `remote.<name>.refmap` configuration to define namespace mappings. The patch adds the `refmap` field to `struct remote`, extends `remote.c` to parse the configuration, and updates `builtin/fetch.c` to use the configured refmap as the default `--refmap` value when an explicit refspec is given. Documentation is added to `config/remote.adoc` and `fetch-options.adoc`, and a test in `t/t5510-fetch.sh` verifies the configuration behaves identically to the `--refmap` command-line option.
2. **Patch 2/4**: Implements dynamic branch enumeration in `git fetch` to fetch only branches tracked by local branches at the remote, plus the remote’s default branch (priming mechanism). The patch updates `get_ref_map()` to accept a `bootstrap_head_branch` out-parameter, builds a temporary refspec by iterating over local branches that track the remote (`branches_tracking_remote()` helper in `remote.c`), and appends the remote’s default branch. The `set_head()` function is updated to avoid redundant `HEAD` resolution, and `do_fetch()` passes the inferred branch list to the transport’s `ls-refs` command. Tests in `t/t5585-fetch-refmap.sh` verify dynamic branch selection, edge cases (duplicate branches, branches tracking other remotes), and `git remote show` compatibility with refmap-only remotes.
3. Adds `git remote add --limited-fetch` to explicitly create a refmap-only remote.
4. Defaults to `--limited-fetch` in shallow repositories to avoid the performance pitfall of fetching all remote branches.
The series is under active review; no merge status (still under review). The design discussion is closed, and the focus is now on implementation details (e.g., edge-case handling, configuration syntax).

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. This is the consensus-approved design.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`) and always includes the remote’s default branch (resolved via `HEAD`, with fallbacks for stale/missing `HEAD` to the local current branch).
- **Files touched**:
  - `remote.c`/`remote.h`: Implement `remote.<name>.refmap` parsing (Patch 1/4) and dynamic branch enumeration logic (Patch 2/4, including `branches_tracking_remote()` helper).
  - `builtin/fetch.c`: Integrate the new fetch logic with the refmap configuration (Patch 1/4 updates `--refmap` default behavior; Patch 2/4 adds dynamic branch enumeration via `get_ref_map()` and `bootstrap_head_branch`).
  - `builtin/remote.c`: Add `--limited-fetch` flag to `git remote add` (Patch 3/4).
  - `Documentation/config/remote.txt` and `Documentation/git-fetch.adoc`: Document `remote.<name>.refmap` (Patch 1/4) and the matching-inspired fetch mode (Patch 2/4).
  - `t/t5510-fetch.sh`: Test `remote.<name>.refmap` configuration (Patch 1/4).
  - `t/t5585-fetch-refmap.sh`: New tests covering refmap configuration, dynamic branch enumeration, and edge cases (stale `HEAD`, empty repositories, multiple tracking branches, duplicate branches, branches tracking other remotes) (Patch 2/4).
- **Behavior**:
  - The remote’s default branch is always fetched (priming mechanism).
  - Non-shallow repositories continue using wildcard refspecs by default (backward compatibility preserved).
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - No on-disk format changes beyond the new configuration entry in `.git/config`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories default to it.

Open questions and loose ends
1. **Edge-case handling**:
   - Should the matching-inspired mode be available outside of shallow repositories, or is it strictly a shallow-repository optimization? (No new input in Patch 2/4.)
   - How should the implementation handle remotes with no default branch (e.g., empty repositories)? The current fallback to the local current branch may not always be correct. (No resolution in Patch 2/4.)
2. **Backward compatibility**:
   - Should existing shallow repositories with wildcard refspecs be migrated automatically, or should users opt in via configuration? (No new input in Patch 2/4.)
   - Should there be a warning for users who might rely on the old behavior? (No new input in Patch 2/4.)
3. **Configuration syntax**:
   - Should `remote.<name>.refmap` support multiple entries for complex namespace mappings, or is a single entry sufficient? (No new input in Patch 2/4.)

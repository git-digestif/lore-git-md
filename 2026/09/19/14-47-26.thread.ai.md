Thread identity
Subject: [PATCH] fetch: introduce `fetch.shallow` config to restrict refspec-less fetches to current branch
Series version: v1 (initial submission; abandoned in favor of alternative solution)
Originating author: Harald Nordgren
Thread type: patch series (single patch, now superseded by design consensus on alternative approach)

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread initially proposed a new `fetch.shallow` configuration option to restrict such fetches to the current branch’s upstream, but has now converged on an alternative solution: modifying `git remote add` to avoid wildcard fetch refspecs in shallow repositories. The goal is to prevent unnecessary negotiation for all remote branches in shallow repositories by addressing the root cause (wildcard refspecs) rather than introducing a new configuration option. The current focus is on implementation details for the alternative solution, particularly how to construct a narrower refspec without making a network call to the remote.

Current status
Design consensus reached on alternative solution: modify `git remote add` to avoid wildcard refspecs in shallow repositories. The original patch (`fetch.shallow`) is abandoned and unmerged. No code changes have been implemented yet for the alternative solution; discussion is now focused on pre-implementation details, specifically how to determine the narrower refspec (e.g., `+refs/heads/<branch>:refs/remotes/<name>/<branch>`) without fetching from the remote. The proposed behavior would affect only new remotes in shallow repositories; non-shallow repositories would continue to default to wildcard refspecs.

Key technical details
- **Original patch (abandoned)**:
  - Files touched: `builtin/fetch.c`, `Documentation/config/fetch.adoc`, `t/t5537-fetch-shallow.sh` (new test section)
  - Proposed config key: `fetch.shallow` (boolean, default `false`)
  - Behavior: when `fetch.shallow=true` and the repository is shallow, a refspec-less fetch would only fetch the current branch’s upstream
  - Test coverage: verified narrowing to tracked branch, correct update of `refs/remotes/<name>/HEAD`, no effect on non-shallow repositories or non-tracked remotes, and edge cases (stale `HEAD`, `fetch.followRemoteHEAD` interaction)
- **Alternative solution (now preferred)**:
  - Target: `git remote add` behavior in shallow repositories
  - Proposed change: default to a narrower refspec (e.g., `+refs/heads/<branch>:refs/remotes/<name>/<branch>`) instead of the current wildcard (`+refs/heads/*:refs/remotes/<name>/*`) for new remotes in shallow repositories
  - Scope: affects only shallow repositories; non-shallow repositories would continue to default to wildcard refspecs
  - No new CLI options or symbols proposed yet; the narrower refspec’s construction is the primary open question
  - On-disk impact: changes the default refspec stored in `.git/config` for new remotes in shallow repositories
  - **New detail**: The local repository lacks information about the remote’s branches or default branch, making it impossible to construct a precise refspec without a network call. Proposed workarounds include:
    - Using the local repository’s current branch as a proxy for the remote’s default branch
    - Relying on the remote’s `HEAD` (which may be stale)
    - Introducing a new configuration option (e.g., `remote.<name>.defaultBranch`) to allow users to specify the branch explicitly

Open questions and loose ends
1. **Refspec construction for the alternative solution**:
   - How should `git remote add` determine the narrower refspec without making a network call to the remote?
     - Use the local repository’s current branch as a proxy for the remote’s default branch?
     - Rely on the remote’s `HEAD` (which may be stale)?
     - Introduce a new configuration option (e.g., `remote.<name>.defaultBranch`) to allow users to specify the branch explicitly?
   - Should the narrower refspec be constructed using the remote’s default branch (as determined by `HEAD`) or the local repository’s current branch?
   - Should there be a way for users to opt into wildcard refspecs for shallow repositories (e.g., via a `--wildcard` flag or manual refspec edit)?
2. **Backwards compatibility**:
   - The alternative solution must preserve existing workflows for non-shallow repositories (wildcard refspecs remain the default).
   - How should existing shallow repositories with wildcard refspecs be handled? Should `git remote add` warn or offer a migration path?
3. **Scope of the performance issue**:
   - Confirmed to affect any shallow repository with many remote-tracking branches, not just sparse checkouts.
   - The alternative solution would prevent the issue from arising in new shallow repositories but does not address existing ones.
4. **No code changes yet**: The original patch remains unmodified, and no new patch has been proposed for the alternative solution. The discussion is still in the design phase, with the refspec construction question as the primary blocker.

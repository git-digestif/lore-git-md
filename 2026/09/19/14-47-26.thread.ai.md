Subject: [PATCH] fetch: introduce `+:` refspec for matching-inspired fetch mode
Series version: v3 (proposed, implementing Junio’s `fetch.X.refmap` design; replaces v2)
Originating author: Harald Nordgren
Thread type: patch series (multi-patch)

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread has converged on addressing the root cause by introducing a new "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, **plus the remote’s default branch**. The design now uses a `fetch.X.refmap` configuration to separate namespace mapping from branch selection logic, making the feature modular and backward-compatible.

Current status
The v2 patch (implementing the `+:` refspec) is abandoned. Junio’s feedback has refined the design to use `fetch.X.refmap` (or `remote.X.refmap`) for namespace mappings, which cleanly enables the matching-inspired fetch mode without requiring escape hatches or transition plans. The feature is under implementation; a v3 series is expected to implement:
1. `fetch.X.refmap` configuration to define namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`).
2. Dynamic branch enumeration logic in `git fetch` to fetch only branches tracked by local branches + the remote’s default branch.
3. Integration of the new fetch logic with the refmap configuration.
No merge status (still under review). The design discussion is now closed, shifting focus to implementation details (e.g., configuration syntax, edge cases).

Key technical details
- **New configuration**: `fetch.X.refmap` (or `remote.X.refmap`) defines namespace mappings without specifying what to fetch. The design is consensus-approved.
- **Dynamic branch selection**: `git fetch` will enumerate branches tracked by local branches at the remote being fetched, plus the remote’s default branch (priming mechanism). The "single-shot fetch" behavior of `git fetch <remote> <branch>` remains unchanged.
- **Files touched (proposed)**:
  - `remote.c`/`remote.h`: Implement `fetch.X.refmap` parsing and dynamic branch enumeration logic.
  - `builtin/fetch.c`: Integrate the new fetch logic with the refmap configuration.
  - `Documentation/config/fetch.txt` and `Documentation/git-fetch.adoc`: Document `fetch.X.refmap` and the matching-inspired fetch mode.
  - `t/t5585-fetch-tracking-refspec.sh`: Update tests to cover the new refmap-based behavior.
- **Behavior**:
  - The remote’s default branch is always fetched (priming mechanism), with fallbacks for stale/missing `HEAD`.
  - Non-shallow repositories continue to use wildcard refspecs by default (backward compatibility preserved).
  - The new mode is implicitly enabled when `fetch.X.refmap` is configured, with no need for explicit opt-in (e.g., `--limited-fetch`).
  - No on-disk format changes beyond the new configuration entry in `.git/config`.
- **Test coverage**: Will verify the refmap configuration, dynamic branch enumeration, and edge cases (stale `HEAD`, empty repositories, multiple tracking branches).

Open questions and loose ends
1. **Configuration name**: Should the new setting be `fetch.X.refmap` or `remote.X.refmap`? Junio’s reply uses `fetch.<remote>.refmap`, but the prior summary suggested `remote.X.refmap`.
2. **Refmap syntax**: Should `fetch.X.refmap` support multiple entries (e.g., for complex namespace mappings), or is a single entry sufficient?
3. **Priming mechanism**: How should stale or missing `HEAD` information be handled? (Current proposal falls back to the local current branch, but this may not always be correct.)
4. **Edge cases**:
   - How should the implementation handle remotes with no default branch (e.g., empty repositories)?
   - Should the matching-inspired mode be available outside of shallow repositories, or is it strictly a shallow-repository optimization?
5. **Backward compatibility**:
   - Should existing shallow repositories with wildcard refspecs be migrated automatically, or should users opt in via configuration?
   - Should there be a warning for users who might rely on the old behavior?

Thread identity
Subject: [PATCH] fetch: introduce `fetch.shallow` config to restrict refspec-less fetches to current branch
Series version: v1 (initial submission; abandoned in favor of alternative design consensus)
Originating author: Harald Nordgren
Thread type: patch series (single patch, now superseded by evolving design discussion)

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread has converged on addressing the root cause: wildcard fetch refspecs in shallow repositories. The current focus is on designing a solution that avoids unnecessary negotiation without requiring network calls or introducing new configuration options. Two complementary approaches are under active discussion: (1) modifying `git remote add` to default to narrower refspecs in shallow repositories, and (2) introducing a new "matching-inspired" fetch mode for `git fetch` that dynamically determines which remote branches to fetch based on local branches’ upstream settings, plus the remote’s default branch.

Current status
Design consensus reached to abandon the original `fetch.shallow` patch. No code changes have been implemented for either alternative solution. Discussion is now focused on refining the two proposed approaches and their integration:
- **Narrower refspec in `git remote add`**: Phillip Wood proposes that `git remote add` in shallow repositories should:
  - Without `--fetch`, refuse to add a remote unless the user explicitly specifies branches to track (e.g., via `--track`).
  - With `--fetch`, query the remote’s `HEAD` to determine the default branch and fetch only that branch by default.
  - Optionally, copy refspecs from existing remotes if all fetch the same branch(es).
  Open questions include whether `--fetch` should be the default, how to handle stale/missing `HEAD`, and the robustness of the heuristic.
- **Matching-inspired fetch mode**: Introduce a new fetch mode (triggered by a special refspec syntax like `:` or `+:`) that dynamically fetches only the remote branches tracked by local branches, **plus the remote’s default branch** (as proposed by Harald Nordgren). Junio C Hamano proposes a priming mechanism: users would explicitly fetch the remote’s default branch (or another branch of interest) once to establish the upstream tracking relationship. The feasibility of D. Ben Knoble’s refinement—automatically creating remote-tracking branches when fetching from a named remote (e.g., `git fetch second main`)—is now in question due to Junio’s clarification that `git fetch <remote> <branch>` has historically been a "single-shot" operation that does not create or update remote-tracking branches. Junio suggests that any change to this behavior would require a transition plan and an escape hatch (e.g., a `--single-shot` flag) to preserve backward compatibility. Open questions remain about refspec syntax, default behavior in shallow repositories, how to determine the remote’s default branch without a network call, and integration with the narrower-refspec approach.

The two approaches are now understood to address complementary use cases: the narrower-refspec solution handles the initial setup of new remotes, while the matching-inspired mode improves subsequent fetches. Integration details (e.g., precedence, coexistence) are still unresolved.

Key technical details
- **Original patch (abandoned)**:
  - Files touched: `builtin/fetch.c`, `Documentation/config/fetch.adoc`, `t/t5537-fetch-shallow.sh` (new test section).
  - Proposed config key: `fetch.shallow` (boolean, default `false`).
  - Behavior: when `fetch.shallow=true` and the repository is shallow, a refspec-less fetch would only fetch the current branch’s upstream.
  - Test coverage: verified narrowing to tracked branch, correct update of `refs/remotes/<name>/HEAD`, no effect on non-shallow repositories or non-tracked remotes, and edge cases (stale `HEAD`, `fetch.followRemoteHEAD` interaction).
- **Alternative solution 1: Narrower refspec in `git remote add` (refined)**:
  - Target: `git remote add` behavior in shallow repositories.
  - Proposed changes:
    - Without `--fetch`: refuse to add a remote unless the user explicitly specifies branches to track (e.g., via `--track`).
    - With `--fetch`: query the remote’s `HEAD` to determine the default branch and fetch only that branch by default.
    - Heuristic: if all existing remotes fetch the same branch(es), copy those refspecs for the new remote.
  - Scope: affects only shallow repositories; non-shallow repositories would continue to default to wildcard refspecs.
  - On-disk impact: changes the default refspec stored in `.git/config` for new remotes in shallow repositories.
  - Open questions: whether `--fetch` should be the default, how to handle stale/missing `HEAD`, and robustness of the heuristic.
- **Alternative solution 2: Matching-inspired fetch mode (refined)**:
  - Proposed behavior: `git fetch` inspects local branches with `@{upstream}` configured to the remote being fetched, then fetches only the corresponding remote branches **plus the remote’s default branch**. For example, if local branch `feature` tracks `origin/main` and the remote’s default branch is `main`, `git fetch origin` would fetch `refs/heads/main` from `origin`.
  - Priming mechanism: users must explicitly fetch the remote’s default branch (or another branch of interest) once to establish the upstream tracking relationship. The feasibility of automatically creating remote-tracking branches during this step (as suggested by D. Ben Knoble) is now in question due to Junio’s clarification about the historical "single-shot" behavior of `git fetch <remote> <branch>`. Junio suggests that any change to this behavior would require a transition plan and an escape hatch (e.g., a `--single-shot` flag).
  - Proposed refspec syntax: special token (e.g., `:` or `+:`) to trigger the mode in `git remote add`, creating a no-op initial fetch that requires the user to manually fetch the desired branch(es) to set up tracking.
  - Scope: limited to determining which remote branches to fetch; does not affect how they are stored locally.
  - Open questions: integration with `git remote add`, default behavior in shallow repositories, handling of edge cases (e.g., no local branches tracking the remote), exact refspec syntax, and **how to determine the remote’s default branch without a network call** (options: remote `HEAD`, local current branch, or user-specified config).

Open questions and loose ends
1. **Narrower refspec in `git remote add`**:
   - Should `--fetch` be the default behavior for `git remote add` in shallow repositories, or should users be required to explicitly opt in?
   - How should stale or missing `HEAD` information be handled? (Options: fall back to the local current branch, error out, or prompt the user.)
   - Is the heuristic of copying existing refspecs from other remotes robust enough for real-world workflows, or could it lead to unexpected behavior?
   - Should there be a way for users to opt into wildcard refspecs for shallow repositories (e.g., via a `--wildcard` flag or manual refspec edit)?
2. **Matching-inspired fetch mode (refined)**:
   - What should the exact refspec syntax be (e.g., `:` or `+:`)?
   - How should this mode handle edge cases, such as when no local branches track the remote being fetched? (Harald’s proposal ensures the default branch is always fetched, mitigating this issue.)
   - Should this mode be the default for shallow repositories, or should it be opt-in?
   - How would this mode integrate with `git remote add`? Would it replace the narrower refspec idea or coexist with it? (Clarified: the two approaches address complementary use cases and must coexist.)
   - Would this mode be useful outside of shallow repositories, or is it primarily a solution for the shallow repository performance issue?
   - **How to determine the remote’s default branch without a network call?** (Options: remote `HEAD`, local current branch, or user-specified config.)
   - How should the priming mechanism be implemented given Junio’s clarification about the "single-shot" behavior of `git fetch <remote> <branch>`? Should the matching-inspired mode work within the existing semantics, or should a transition plan be designed to change the behavior of `git fetch <remote> <branch>`?
   - If a transition plan is required, what should it look like? Should it include a new flag (e.g., `--create-tracking`), a configuration option, or a phased rollout?
3. **Integration of the two approaches**:
   - How should the narrower-refspec and matching-inspired solutions interact? For example, should the matching-inspired mode override the narrower refspec in shallow repositories, or should they operate independently?
   - Should `git remote add` in shallow repositories default to the narrower refspec, while `git fetch` in shallow repositories defaults to the matching-inspired mode?
   - How should existing shallow repositories with wildcard refspecs be handled? Should `git remote add` warn or offer a migration path?
4. **Backwards compatibility**:
   - Both solutions must preserve existing workflows for non-shallow repositories (wildcard refspecs remain the default).
   - How should users be guided to adopt the new behaviors in shallow repositories? Should there be warnings, documentation updates, or migration tools?
5. **Implementation priority**:
   - Which approach should be prioritized for implementation: the narrower refspec in `git remote add` or the matching-inspired fetch mode?
   - Could the two approaches be implemented incrementally, with the narrower-refspec solution addressing the initial setup problem and the matching-inspired mode added later for subsequent fetches?

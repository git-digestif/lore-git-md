Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using `remote.<name>.refmap` to separate namespace mappings from fetch selection logic.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. The configuration knob is added in Patch 1/5, mirroring `remote.<name>.fetch` but only providing a default for `--refmap` when there is something explicit to fetch (command-line refspecs or `remote.<name>.fetch`). If both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, the former takes precedence.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`). The `branches_tracking_remote()` helper in `remote.c` implements this logic, iterating over all local branches and collecting the source ref for each branch whose `remote_name` matches the target remote. The `get_ref_map()` function in `builtin/fetch.c` integrates this logic, constructing a dynamic refspec from the inferred branches. The `do_fetch()` function populates `transport_ls_refs_options.ref_prefixes` with the inferred branches to limit the transport layer’s ref requests. The existing "fetch branches merged into the current branch" logic is extracted into a shared helper (`collect_upstream_from_remote`, introduced in Patch 2/5) to reduce duplication. The helper takes a `struct repository *`, a `string_list` to populate, a `remote`, and an optional branch name (NULL means the current branch), and adds the upstream refs of any matching branches to the list. Junio’s review requirements are fully addressed: (1) the `if/else if/else` control-flow reorganization is now in Patch 3/5, and (2) the NULL-check for `branch` is restored in `collect_upstream_from_remote()` via `repo_branch_get(repo, refname)`.
- **Precedence rule**: When both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, `remote.<name>.fetch` takes precedence, and the `refmap` setting is ignored. This resolves the fatal error ("--refmap option is only meaningful with command-line refspec") and is uncontroversial.
- **`--limited-fetch` flag**: Added in Patch 4/5 to `git remote add`, this flag configures the remote to use `remote.<name>.refmap` (e.g., `+refs/heads/*:refs/remotes/<name>/*`) instead of the traditional wildcard `remote.<name>.fetch` refspec. The flag is rejected when combined with `-t/--track` or `--mirror`, as those options already specify explicit fetch behavior. The implementation updates `builtin/remote.c` to set the refmap configuration via `repo_config_set()` and adds documentation to `git-remote.adoc`. Four new tests in `t/t5505-remote.sh` verify the flag’s behavior, conflict with `-t`, and absence of interference with existing functionality.
- **Shallow-repository default**: Patch 5/5 makes `--limited-fetch` the default for shallow repositories by checking `is_repository_shallow(the_repository)` when `limited_fetch` is unset (`-1`), defaulting to `--limited-fetch` unless `--no-limited-fetch` is given. This is implemented in `builtin/remote.c` without introducing new technical debt. The shallow check uses the existing `is_repository_shallow()` helper, and the logic reuses the existing `limited_fetch` machinery. The documentation in `git-remote.adoc` is updated to explain the new default behavior.
- **Fallback logic in `remote_find_tracking()`**: Patch 1/5 modifies `remote_find_tracking()` in `remote.c` to fall back to `remote->refmap` **only when `remote->fetch` is either empty or contains no matching refspec for the given query**. This ensures the function treats `remote->refmap` as a superset of `remote->fetch` while avoiding unintended side effects (e.g., for `--delete-merged`). The change replaces the original two-branch `if/else` with a single condition that checks both the presence of `remote->fetch` refspecs and the success of `refspec_find_match()`. This resolves D. Ben Knoble’s technical concern about ambiguity in the fallback logic.
- **Files touched**:

Patch 2/5 extracts the existing "fetch branches merged into the current branch" logic into a shared helper (`collect_upstream_from_remote`), which takes a `struct repository *` parameter to avoid hardcoded `the_repository` usage. The NULL-check for `branch` is preserved via `repo_branch_get(repo, refname)`. Patch 1/5 also updates `remote_find_tracking()` to implement the corrected fallback logic.

  - `builtin/remote.c`: Add `--limited-fetch` flag to `git remote add` (Patch 4/5) and default it in shallow repositories (Patch 5/5).
  - Documentation: `Documentation/config/remote.txt`, `Documentation/git-fetch.adoc`, `Documentation/git-remote.adoc`, `Documentation/config/remote.adoc`, and `fetch-options.adoc` (updated to document the new default behavior for shallow repositories, the `--limited-fetch` flag, and the dynamic branch inference logic).
  - Tests: `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh`, and `t/t5505-remote.sh` (12 new tests covering edge cases, backward compatibility, and the new functionality).
- **Behavior**:
  - The remote’s default branch is no longer fetched by default.
  - Non-shallow repositories continue using wildcard refspecs by default.
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories now default to it.
  - No on-disk format changes beyond the new configuration entries in `.git/config`.
  - Edge case: A bare `git fetch` against a refmap-only remote with no tracked branches fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use.

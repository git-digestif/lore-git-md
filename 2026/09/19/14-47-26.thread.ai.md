Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using `remote.<name>.refmap` to separate namespace mappings from fetch selection logic.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. The configuration knob is added in Patch 1/5, mirroring `remote.<name>.fetch` but only providing a default for `--refmap` when there is something explicit to fetch (command-line refspecs or `remote.<name>.fetch`). If both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, the former takes precedence.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`). The `branches_tracking_remote()` helper in `remote.c` implements this logic, iterating over all local branches and collecting the source ref for each branch whose `remote_name` matches the target remote. The `get_ref_map()` function in `builtin/fetch.c` integrates this logic, constructing a dynamic refspec from the inferred branches. The `do_fetch()` function populates `transport_ls_refs_options.ref_prefixes` with the inferred branches to limit the transport layer’s ref requests. The existing "fetch branches merged into the current branch" logic is extracted into a shared helper (`collect_upstream_from_remote`, introduced in Patch 2/5) to reduce duplication. The helper takes a `struct repository *`, a `string_list` to populate, a `remote`, and an optional branch name (NULL means the current branch), and adds the upstream refs of any matching branches to the list. Junio’s review requirements are fully addressed: (1) the `if/else if/else` control-flow reorganization is now in Patch 3/5, and (2) the NULL-check for `branch` is restored in `collect_upstream_from_remote()` via `repo_branch_get(repo, refname)`.
- **Precedence rule**: When both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, `remote.<name>.fetch` takes precedence, and the `refmap` setting is ignored. This resolves the fatal error ("--refmap option is only meaningful with command-line refspec") and is uncontroversial.
- **`--limited-fetch` flag**: Added in Patch 4/5 to `git remote add`, this flag configures the remote to use `remote.<name>.refmap` (e.g., `+refs/heads/*:refs/remotes/<name>/*`) instead of the traditional wildcard `remote.<name>.fetch` refspec. The flag is rejected when combined with `-t/--track` or `--mirror`, as those options already specify explicit fetch behavior. The implementation updates `builtin/remote.c` to set the refmap configuration via `repo_config_set()` and adds documentation to `git-remote.adoc`. Four new tests in `t/t5505-remote.sh` verify the flag’s behavior, conflict with `-t`, and absence of interference with existing functionality.
- **Shallow-repository default**: Patch 5/5 makes `--limited-fetch` the default for shallow repositories by checking `is_repository_shallow(the_repository)` when `limited_fetch` is unset (`-1`), defaulting to `--limited-fetch` unless `--no-limited-fetch` is given. This is implemented in `builtin/remote.c` without introducing new technical debt. The shallow check uses the existing `is_repository_shallow()` helper, and the logic reuses the existing `limited_fetch` machinery. The documentation in `git-remote.adoc` is updated to explain the new default behavior, and four new tests in `t/t5505-remote.sh` verify the shallow-repository default, `--no-limited-fetch` override, `-t/--track` behavior, and full-repository backward compatibility.
- **Fallback logic in `remote_find_tracking()`**: Patch 1/5 modifies `remote_find_tracking()` in `remote.c` to fall back to `remote->refmap` when `remote->fetch` is non-empty but `refspec_find_match()` fails to find a match. This behavior is now explicitly called out as intentional, supporting the design goal of treating `remote->refmap` as a superset of `remote->fetch` for tracking purposes. The fallback is consistent with the series' broader design, where `remote->refmap` provides a default namespace mapping even when `remote->fetch` is configured but incomplete.
- **Files touched**:

The NULL-check for `branch` is preserved via `repo_branch_get(repo, refname)`. The potential duplicate fetch (when the current branch’s `@{upstream}` is also inferred by the new logic) is resolved.
  - `builtin/remote.c`: Add `--limited-fetch` flag to `git remote add` (Patch 4/5) and default it in shallow repositories (Patch 5/5). The shallow check uses `is_repository_shallow(the_repository)` and threads through the existing `limited_fetch` logic.
  - Documentation: `Documentation/config/remote.txt`, `Documentation/git-fetch.adoc`, `Documentation/git-remote.adoc`, `Documentation/config/remote.adoc`, and `Documentation/fetch-options.adoc` (updated to document the new default behavior for shallow repositories, the `--limited-fetch` flag, and the dynamic branch inference logic).

The test failures in `t5505` and `t5586` (caused by a textual conflict with Collin’s `ch/fetch-followremotehead-lazy-validation` topic in `seen`) are resolved in v8 and remain resolved in v10.
- **Behavior**:
  - The remote’s default branch is no longer fetched by default.
  - Non-shallow repositories continue using wildcard refspecs by default.
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories now default to it.
  - No on-disk format changes beyond the new configuration entries in `.git/config`.
  - Edge case: A bare `git fetch` against a refmap-only remote with no tracked branches fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use.

Open questions and loose ends
1. **Procedural request**: Junio explicitly asks for another reviewer to Ack the series before it graduates to `next`. No technical feedback is required; the request is for a second opinion on design and implementation soundness.
2. **Design choice**: Whether the matching-inspired mode should be available outside of shallow repositories. This is a minor design choice that can be addressed in follow-up work.
3. **Edge-case handling in `remote_find_tracking()`**: D. Ben Knoble raises a question about the fallback logic in `remote_find_tracking()`: whether the code should fall back to `remote->refmap` only when `remote->fetch` is empty, or also when `refspec_find_match()` fails to find a match in `remote->fetch`. The current implementation (Patch 1/5) falls back in both cases, which is now confirmed as intentional to treat `remote->refmap` as a superset of `remote->fetch`. The author must clarify this design choice in a reply, and an audit of `remote_find_tracking()` callers may be needed to ensure consistency. This is not a blocker for merging but should be resolved before graduation to `master`.
4. **Edge-case handling (general)**:
   - How should the implementation handle remotes with no default branch?
   - Should existing shallow repositories with wildcard refspecs be migrated automatically?
   - Should there be a warning for users who might rely on the old behavior?
5. **Backward compatibility**: The v10 series preserves backward compatibility for non-shallow repositories but does not address migration of existing shallow repositories. This is not a blocker for merging.
6. **`--limited-fetch` flag scope**: Whether the flag should be the default for *all* repositories (not just shallow ones) remains an open design question, but it is not a blocker for Patch 4/5 or the series as a whole.

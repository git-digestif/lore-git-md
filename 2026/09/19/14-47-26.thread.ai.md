Thread identity
Subject: [PATCH] fetch: introduce `+:` refspec for matching-inspired fetch mode
Series version: v3 (proposed, implementing Junio’s `remote.X.refmap` design; replaces v2)
Originating author: Harald Nordgren
Thread type: patch series (single patch in v2, now likely multi-patch in v3)

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread has converged on addressing the root cause by introducing a new "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, **plus the remote’s default branch**. Junio’s feedback rejects the `+:` refspec syntax in favor of a `remote.X.refmap` configuration that separates namespace mapping from branch selection logic, making the feature more modular and reviewable.

Current status
The v2 patch (implementing the `+:` refspec) is now abandoned. Junio’s feedback proposes a four-commit refactoring:
1. Introduce `remote.X.refmap` configuration to define namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`).
2. Implement dynamic branch enumeration logic in `git fetch` to fetch only branches tracked by local branches + the remote’s default branch.
3. Add a `--limited-fetch` option to `git remote add` to opt into the new mode.
4. Add heuristics to enable `--limited-fetch` by default in shallow repositories.
The feature is now under design refinement; a v3 series is expected to implement this plan. No merge status (still under review).

Key technical details
- **New configuration**: `remote.X.refmap` replaces the `+:` refspec, defining namespace mappings without specifying what to fetch.
- **Dynamic branch selection**: `git fetch` will enumerate branches tracked by local branches at the remote being fetched, plus the remote’s default branch (priming mechanism).
- **Files touched (proposed)**:
  - `builtin/remote.c`: Add `--limited-fetch` option and heuristics for shallow repositories.
  - `remote.c`/`remote.h`: Implement `remote.X.refmap` parsing and dynamic branch enumeration logic.
  - `builtin/fetch.c`: Integrate the new fetch logic with the refmap configuration.
  - `Documentation/git-remote.adoc` and `Documentation/config/remote.txt`: Document `remote.X.refmap` and `--limited-fetch`.
  - `t/t5585-fetch-tracking-refspec.sh`: Update tests to cover the new refmap-based behavior.
- **Behavior**:
  - The remote’s default branch is always fetched (priming mechanism), with fallbacks for stale/missing `HEAD`.
  - Non-shallow repositories continue to use wildcard refspecs by default (backward compatibility preserved).
  - The new mode is opt-in via `--limited-fetch` (at least initially), with heuristics to enable it by default in shallow repositories.
- **On-disk impact**: Changes the configuration schema for remotes (`.git/config`) to include `remote.X.refmap`.
- **Test coverage**: Will verify the refmap configuration, dynamic branch enumeration, `--limited-fetch` integration, and edge cases (stale `HEAD`, empty repositories, multiple tracking branches).

Open questions and loose ends
1. **Refmap syntax**: Should `remote.X.refmap` support multiple entries (e.g., for complex namespace mappings), or is a single entry sufficient?
2. **Priming mechanism**: How should stale or missing `HEAD` information be handled? (Current proposal falls back to the local current branch, but this may not always be correct.)
3. **Heuristics for shallow repositories**: Should `--limited-fetch` be enabled by default for all shallow repositories, or should users opt in (e.g., via `--fetch=limited`)?
4. **Backward compatibility**:
   - How should existing shallow repositories with wildcard refspecs be handled? Should `git remote add` warn or offer a migration path?
   - Should there be an escape hatch (e.g., `--wildcard`) to opt into traditional behavior for shallow repositories?
5. **Edge cases**:
   - How should the implementation handle remotes with no default branch (e.g., empty repositories)?
   - Should the matching-inspired mode be available outside of shallow repositories, or is it strictly a shallow-repository optimization?
6. **Transition plan**: If the matching-inspired mode becomes the default for shallow repositories, should there be a phased rollout or warnings for existing users?
7. **Documentation**: Are the updates to `git-remote.adoc` and `config/remote.txt` sufficient, or should additional guidance be added for users migrating from wildcard refspecs?

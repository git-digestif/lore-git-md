Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using `remote.<name>.refmap` to separate namespace mappings from fetch selection logic.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. This design remains consensus-approved.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`). The forced inclusion of the remote’s default branch (present in v3) is removed. The `branches_tracking_remote()` helper in `remote.c` implements this logic, and `get_ref_map()` in `builtin/fetch.c` integrates it. The helper iterates over all local branches, collects the source ref for each branch whose `remote_name` matches the target remote, and constructs a dynamic refspec from these branches. The `do_fetch()` function populates `transport_ls_refs_options.ref_prefixes` with the inferred branches to limit the transport layer’s ref requests.
- **Precedence rule**: When both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, `remote.<name>.fetch` takes precedence, and the `refmap` setting is ignored. This resolves the fatal error ("--refmap option is only meaningful with command-line refspec") by treating the `fetch` refspec as the authoritative source of truth.
- **Files touched**:
  - `remote.c`/`remote.h`: Implement `remote.<name>.refmap` parsing (Patch 1/4) and dynamic branch enumeration logic (Patch 2/4, including `branches_tracking_remote()` helper). Junio’s review suggests refactoring to extract the existing "fetch branches merged into the current branch" logic into a shared helper (`collect_upstream_from_remote`) to reduce duplication and clarify control flow.
  - `builtin/fetch.c`: Integrate the new fetch logic with the refmap configuration (Patch 1/4 updates `--refmap` default behavior; Patch 2/4 adds dynamic branch enumeration via `get_ref_map()`). Junio’s review flags hardcoded `the_repository` usage and a potential duplicate fetch when the current branch’s `@{upstream}` is also inferred by the new logic.
  - `builtin/remote.c`: Add `--limited-fetch` flag to `git remote add` (Patch 3/4) and default it in shallow repositories (Patch 4/4). Patch 4/4 uses `is_repository_shallow()` to check if the repository is shallow and defaults the `limited_fetch` flag to `1` unless `--no-limited-fetch` is given.
  - Documentation: `Documentation/config/remote.txt`, `Documentation/git-fetch.adoc`, and `Documentation/git-remote.adoc` (updated to document the new default behavior for shallow repositories). Junio’s review suggests rewording the `git-fetch` man page to explicitly state that the inference is based on local branches’ `@{upstream}` settings.

The test failures in `t5505` and `t5586` when merged into `seen` are confirmed to be caused by a textual conflict with Collin’s `ch/fetch-followremotehead-lazy-validation` topic and are expected to resolve in v8.
- **Behavior**:
  - The remote’s default branch is no longer fetched by default.
  - Non-shallow repositories continue using wildcard refspecs by default.
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories now default to it.
  - No on-disk format changes beyond the new configuration entry in `.git/config`.
  - Edge case: A bare `git fetch` against a refmap-only remote with no tracked branches fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use.

6. **Backward compatibility**: The v7 series preserves backward compatibility for non-shallow repositories but does not address migration of existing shallow repositories.

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using configuration to separate namespace mappings from fetch selection logic. **The design direction is now finalized: the series will introduce a dedicated `remote.<name>.fetchRefs` config key to decouple the "what" (which refs to fetch) from the "where" (where to store them), resolving the maintainer and key reviewer’s objection to overloading `remote.<name>.refmap`.**

Key technical details
- **Current design (v11, now deprecated)**:
  - `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) and, when no `remote.<name>.fetch` is configured, implicitly controls which refs are fetched by enumerating branches tracked by local branches at the remote.
  - Precedence: `remote.<name>.fetch` > `remote.<name>.refmap`.
  - **Flaw**: Overloading `refmap` for both namespace mapping and fetch selection limits extensibility and repeats the inflexibility the series aims to fix. The maintainer’s email confirms this design correctly handles edge cases (e.g., `remote.<name>.fetch` + `remote.<name>.refmap`) but does not resolve the broader inflexibility.

- **Finalized design (v12)**:
  - **New config key**: `remote.<name>.fetchRefs` explicitly specifies which refs to fetch (e.g., `*@{upstream}`), decoupling the "what" from the "where".
  - **Refmap role**: `remote.<name>.refmap` reverts to its original purpose: namespace mapping only (e.g., `+refs/heads/*:refs/remotes/second/*`).
  - **Precedence**: `remote.<name>.fetch` > `remote.<name>.fetchRefs` > dynamic branch enumeration (if neither is configured).
  - **Forced updates (`+`)**: Belong on the refmap side (the "where"), not the fetchRefs side (the "what"), since forced updates only make sense when storing refs.
  - **Refspec-matching order**: The new design resolves the inconsistency (first-match vs. last-one-wins) by decoupling the "what" and "where".
  - **Dynamic branch selection**: When no explicit refspec or `fetchRefs` is given, `git fetch` enumerates branches tracked by local branches at the remote via `@{upstream}`. The `branches_tracking_remote()` helper implements this logic; `get_ref_map()` integrates it. **v12 change**: This logic will now trigger only when neither `remote.<name>.fetch` nor `remote.<name>.fetchRefs` is configured.
  - **`--limited-fetch` flag**: Added to `git remote add` (Patch 4/5), configures `remote.<name>.refmap` in v11. **v12 change**: Will configure `remote.<name>.fetchRefs` instead (e.g., `*@{upstream}`), while `remote.<name>.refmap` handles namespace mapping.
  - **Shallow-repository default**: Patch 5/5 makes `--limited-fetch` the default in shallow repositories by checking `is_repository_shallow(the_repository)`. **v12 change**: The default will use `remote.<name>.fetchRefs = *@{upstream}` instead of overloading `refmap`.
  - **Fallback logic**: `remote_find_tracking()` falls back to `remote->refmap` only when `remote->fetch` is empty or contains no matching refspec. **v12 change**: Will fall back to `remote->fetchRefs` (if configured) before dynamic branch enumeration.
  - **Files touched (v12)**:
    - `remote.c`/`remote.h`: Add `remote.<name>.fetchRefs` parsing, adjust precedence rules, and rework `branches_tracking_remote()` to integrate with the new config key.
    - `builtin/fetch.c`: Update integration with refmap configuration and dynamic branch enumeration to use `fetchRefs`.
    - `builtin/remote.c`: Update `--limited-fetch` flag and shallow-repository default to use `fetchRefs`.
    - Documentation: Update `remote.txt`, `git-fetch.adoc`, `git-remote.adoc`, and `fetch-options.adoc` to reflect the new design.
    - Tests: Update `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh`, and `t/t5505-remote.sh` to test the new `fetchRefs` behavior.
  - **Behavior (v12)**:
    - New mode enabled when `remote.<name>.fetchRefs` is configured (e.g., `*@{upstream}`).
    - `remote.<name>.refmap` handles namespace mapping only.
    - Precedence: `remote.<name>.fetch` > `remote.<name>.fetchRefs` > dynamic branch enumeration.
    - No on-disk format changes beyond new configuration entries.
  - **New symbols (v12)**:
    - `remote.<name>.fetchRefs`, `remote->fetchRefs`.

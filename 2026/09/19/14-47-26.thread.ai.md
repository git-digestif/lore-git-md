Thread identity
Subject: [PATCH] fetch: introduce `+:` refspec for matching-inspired fetch mode
Series version: v3 (implementing Junio’s `remote.<name>.refmap` design; replaces v2)
Originating author: Harald Nordgren
Thread type: patch series (multi-patch)

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread has converged on addressing the root cause by introducing a new "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, **optionally including the remote’s default branch**. The design uses `remote.<name>.refmap` to define namespace mappings, separating the "where to store" logic from the "what to fetch" logic and enabling the new mode without escape hatches or transition plans.

Current status
The v3 series implements the `remote.<name>.refmap`-based design proposed by Junio and is now complete with all four patches:
1. **Patch 1/4**: Introduces `remote.<name>.refmap` configuration to define namespace mappings. Junio C Hamano reviewed the patch and **approved the code implementation** but requested a **documentation wording change** to clarify that `--refmap` is always active (even if it maps zero refs when nothing is explicitly fetched). The requested change replaces conditional phrasing ("only takes effect when there is something explicit to fetch") with a precise definition: `remote.<name>.refmap` is "used to map remote refs being fetched to remote-tracking refs to store." The patch updates `remote.c` to parse the configuration, extends `builtin/fetch.c` to use the configured refmap as the default `--refmap` value, and adds documentation to `config/remote.adoc` and `fetch-options.adoc`. Tests in `t/t5510-fetch.sh` verify the configuration behaves identically to the `--refmap` command-line option. **Resolved loose end**: Harald is expected to update the documentation wording in response to Junio’s review.
2. **Patch 2/4**: Implements dynamic branch enumeration in `git fetch` to fetch only branches tracked by local branches at the remote, **plus the remote’s default branch (priming mechanism)**. Junio C Hamano’s review raises **substantive design concerns** about the forced inclusion of the remote’s default branch, arguing it is overly presumptive and potentially wasteful. He suggests **removing the forced inclusion** to simplify the code and avoid awkward fetch report output (e.g., `* [new ref] HEAD -> second/main`). The patch updates `get_ref_map()` to accept a `bootstrap_head_branch` out-parameter, builds a temporary refspec by iterating over local branches that track the remote (`branches_tracking_remote()` helper in `remote.c`), and appends the remote’s default branch. The `set_head()` function is updated to avoid redundant `HEAD` resolution, and `do_fetch()` passes the inferred branch list to the transport’s `ls-refs` command. Tests in `t/t5585-fetch-refmap.sh` verify dynamic branch selection, edge cases (duplicate branches, branches tracking other remotes), and `git remote show` compatibility with refmap-only remotes. **New open question**: Whether to retain or remove the forced inclusion of the remote’s default branch.
3. **Patch 3/4**: Adds `git remote add --limited-fetch` to explicitly create a refmap-only remote. The flag writes a single `remote.<name>.refmap` entry (`+refs/heads/*:refs/remotes/<name>/*`) instead of the usual wildcard `remote.<name>.fetch` refspec, opting the remote into the matching-inspired fetch mode. The patch updates `builtin/remote.c` and `Documentation/git-remote.adoc`, and adds tests in `t/t5505-remote.sh` to verify the flag works in non-shallow repositories and correctly rejects incompatible combinations (`-t/--track` or `--mirror`).
4. **Patch 4/4**: Makes `git remote add` default to `--limited-fetch` in shallow repositories, ensuring that adding a remote to a shallow clone does not trigger a full fetch of all remote branches. The patch modifies `builtin/remote.c` to check `is_repository_shallow()` and enables `--limited-fetch` by default unless `--no-limited-fetch`, `-t/--track`, or `--mirror` is specified. Documentation and tests (`t/t5505-remote.sh`) are updated to cover the new behavior and edge cases (explicit `-t` in shallow repos, wildcard refspecs in full repos, shallow default, and `--no-limited-fetch` override).
The series is under active review; no merge status (still under review). The design discussion for the `remote.<name>.refmap` mechanism remains closed, but the core behavior of Patch 2/4 (forced inclusion of the remote’s default branch) is now contested.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. This is the consensus-approved design.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`) and **optionally includes the remote’s default branch** (resolved via `HEAD`, with fallbacks for stale/missing `HEAD` to the local current branch). The forced inclusion is now under debate.
- **Files touched**:

- **Behavior**:
  - The remote’s default branch is **optionally** fetched (priming mechanism under debate).
  - Non-shallow repositories continue using wildcard refspecs by default (backward compatibility preserved).
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories default to it.
  - No on-disk format changes beyond the new configuration entry in `.git/config`.

Open questions and loose ends
1. **Forced inclusion of the remote’s default branch (Patch 2/4)**:
   - Junio C Hamano argues the forced inclusion is overly presumptive and potentially wasteful, citing examples where users may not need the default branch (e.g., working only on `maint`/`next`, or already tracking the default branch via the primary remote). He suggests removing it to simplify the code and avoid awkward fetch report output.
   - No counterarguments or alternative proposals have been raised yet. The next step is likely a **v4 iteration** addressing this concern, either by removing the forced inclusion or by providing a stronger rationale for keeping it.
2. **Edge-case handling**:
   - Should the matching-inspired mode be available outside of shallow repositories, or is it strictly a shallow-repository optimization? (No new input in Patch 4/4.)
   - How should the implementation handle remotes with no default branch (e.g., empty repositories)? The current fallback to the local current branch may not always be correct. (No resolution in Patch 4/4.)
3. **Backward compatibility**:
   - Should existing shallow repositories with wildcard refspecs be migrated automatically, or should users opt in via configuration? (No new input in Patch 4/4.)
   - Should there be a warning for users who might rely on the old behavior? (No new input in Patch 4/4.)
4. **Documentation wording (Patch 1/4)**: Junio’s review requests a clarification in `config/remote.adoc` and `fetch-options.adoc` to avoid implying that `remote.<name>.refmap` is conditionally active. This is **pending Harald’s update**.

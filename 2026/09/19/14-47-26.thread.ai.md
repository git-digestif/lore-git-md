Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The series implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using configuration to separate namespace mappings from fetch selection logic. The **finalized design for v13/v14** (endorsed by Junio C Hamano and Phillip Wood) introduces `remote.<name>.fetchRefmap` to decouple the "what" (which refs to fetch) from the "where" (where to store them), resolving the maintainer’s objection to overloading `remote.<name>.refmap`. **New strategic context**: Matt Hunter clarified that the series is **blocking `ch/remote-defer-follow-remote-head-validation` (Collin’s topic) due to textual conflicts**, but the dependency is **not strict**—the other author is deferring resolution until this series lands. Merging **only Patches 1–3** would resolve the conflicts and unblock the dependent topic, **strengthening the case for a partial merge** and **weakening Phillip’s architectural objection** to Patch 3/6.

**Override semantics (resolved in v14)**: Command-line refspecs (or colon-separated `remote.<name>.fetch` entries) **override `remote.<name>.fetchRefmap` entirely**, not coexist with it (dual storage). This aligns with Phillip Wood’s explicit confirmation and resolves the ambiguity that blocked v13. The v14 revision updates `remote.c` (precedence logic in `get_ref_map()`) and the test suite to reflect this behavior, removing the deprecated dual-storage regression test.

Key technical details
- **Finalized design (v14)**:
  - **New config key**: `remote.<name>.fetchRefmap` explicitly specifies which refs to fetch (e.g., `*@{upstream}`), decoupling the "what" from the "where".
  - **Refmap role**: `remote.<name>.refmap` handles namespace mapping only (e.g., `+refs/heads/*:refs/remotes/second/*`).
  - **Precedence**: `remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration (if neither is configured). Command-line refspecs override both config keys.
  - **Override semantics (resolved)**: Command-line refspecs (or colon-separated `remote.<name>.fetch` entries) **override `remote.<name>.fetchRefmap` entirely**, not coexist with it (dual storage). This aligns with Phillip Wood’s explicit confirmation and resolves the ambiguity in v13.
  - **Forced updates (`+`)**: Belong on the refmap side (the "where"), not the `fetchRefmap` side (the "what"), as confirmed by Junio and Phillip Wood. This introduces a **minor inconvenience**: users who want to reject non-fast-forward updates for some branches while mapping all refs the same way must now use **two separate refspecs** (one with `+` and one without).
  - **Dynamic branch selection (Patch 3/6)**: When no explicit refspec, `remote.<name>.fetch`, or `remote.<name>.fetchRefmap` is given, `git fetch` enumerates branches tracked by local branches at the remote via `@{upstream}`. The `branches_tracking_remote()` helper (added in Patch 3/6) implements this logic; `get_ref_map()` integrates it. This logic now triggers only when neither `remote.<name>.fetch` nor `remote.<name>.fetchRefmap` is configured. **This patch is now strategically critical** for resolving the dependent topic’s conflicts.
  - **`@{push}` resolution**: Works correctly for remotes configured with `--limited-fetch` by falling back to `remote->refmap` in `remote.c` (`tracking_for_push_dest()`) if `remote->fetch` does not resolve the refname. The interaction with override semantics is **clarified in documentation**: override semantics do not affect `@{push}` resolution, as the fallback occurs only when `remote->fetch` is insufficient.
  - **`--limited-fetch` flag**: Added to `git remote add` (Patch 4/6), configures `remote.<name>.fetchRefmap` (e.g., `*@{upstream}`), while `remote.<name>.refmap` handles namespace mapping. The flag is rejected when combined with `-t/--track` or `--mirror`.
  - **Shallow-repository default**: Patch 5/6 makes `--limited-fetch` the default in shallow repositories by checking `is_repository_shallow(the_repository)`. The default uses `remote.<name>.fetchRefmap = *@{upstream}` and is overridden by `--no-limited-fetch`, `-t/--track`, or `--mirror`.
  - **Backwards compatibility**: Older Git versions ignore `remote.<name>.fetchRefmap` and fail to fetch (safe) rather than misinterpreting `remote.<name>.fetch` as a refspec (unsafe). Older versions treat `remote.<name>.fetch` entries without a destination as **fetch-only refspecs**, storing them only in `FETCH_HEAD` (safe but incomplete, as no persistent tracking refs are created).
  - **Files touched (v14)**:
    - `remote.c`/`remote.h`: Add `remote.<name>.fetchRefmap` parsing, adjust precedence rules to implement override semantics, and rework `branches_tracking_remote()` to integrate with the new config key. Patch 1/6 adds the config key, struct updates, and fallback logic in `remote_find_tracking()`. Patch 2/6 adds `collect_upstream_from_remote()` helper; Patch 3/6 adds `branches_tracking_remote()` and integrates it into `get_ref_map()`. Patch 6/6 adds the fallback to `remote->refmap` in `tracking_for_push_dest()` for `@{push}` resolution. The v14 revision removes the deprecated dual-storage behavior for colon-separated `fetch` entries.
    - `builtin/fetch.c`: Update integration with refmap configuration and dynamic branch enumeration to use `fetchRefmap`.
    - `builtin/remote.c`: Update `--limited-fetch` flag (Patch 4/6) and shallow-repository default (Patch 5/6) to use `fetchRefmap`.
    - Documentation: Update `remote.txt`, `git-fetch.adoc`, `git-remote.adoc`, and `fetch-options.adoc` to reflect override semantics, the `@{push}` resolution clarification, the architectural reconsideration, and the partial merge proposal.
    - Tests: Update `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh`, and `t/t5505-remote.sh` to test override semantics, the `@{push}` resolution fix, and the shallow-repository default. Remove the deprecated dual-storage regression test.
  - **New symbols (v14)**:
    - `remote.<name>.fetchRefmap`, `remote->fetchRefmap`, `collect_upstream_from_remote()`, `branches_tracking_remote()`, `add_if_tracking_remote()`, `branches_tracking_remote_cb_data` struct, `--limited-fetch` flag, `--no-limited-fetch` flag, `tracking_for_push_dest()` fallback logic.
  - **Behavior (v14)**:
    - New mode enabled when `remote.<name>.fetchRefmap` is configured (e.g., `*@{upstream}`).
    - `remote.<name>.refmap` handles namespace mapping only.
    - Precedence: `remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration.
    - Command-line refspecs override both config keys.
    - **Override semantics (resolved)**: Command-line refspecs (or colon-separated `remote.<name>.fetch` entries) override `remote.<name>.fetchRefmap` entirely, not coexist with it.
    - **`@{push}` resolution**: Works correctly for remotes configured with `--limited-fetch` by falling back to `remote->refmap` if `remote->fetch` does not resolve the refname. Override semantics do not affect this behavior.
    - **Shallow-repository default**: `--limited-fetch` is enabled by default in shallow repositories, configuring `remote.<name>.fetchRefmap = *@{upstream}` unless overridden by `--no-limited-fetch`, `-t/--track`, or `--mirror`.
    - No on-disk format changes beyond new configuration entries.

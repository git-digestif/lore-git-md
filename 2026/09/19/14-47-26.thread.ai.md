Subject: [PATCH] fetch: introduce `+:` refspec for matching-inspired fetch mode

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The series implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using configuration to separate namespace mappings from fetch selection logic. The design is finalized: the series introduces `remote.<name>.fetchRefmap` to decouple the "what" (which refs to fetch) from the "where" (where to store them), resolving the maintainer and key reviewer’s objection to overloading `remote.<name>.refmap`.

Key technical details
- **Finalized design (v12)**:
  - **New config key**: `remote.<name>.fetchRefmap` explicitly specifies which refs to fetch (e.g., `*@{upstream}`), decoupling the "what" from the "where".
  - **Refmap role**: `remote.<name>.refmap` reverts to its original purpose: namespace mapping only (e.g., `+refs/heads/*:refs/remotes/second/*`).
  - **Precedence**: `remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration (if neither is configured). Command-line refspecs override both config keys.
  - **Forced updates (`+`)**: Belong on the refmap side (the "where"), not the `fetchRefmap` side (the "what"), as confirmed by Junio and Phillip Wood. This aligns with existing refspec behavior but introduces a **minor inconvenience**: users who want to reject non-fast-forward updates for some branches while mapping all refs the same way must now use **two separate refspecs** (one with `+` and one without). The documentation must clarify this behavior to avoid user confusion.
  - **Refspec-matching order**: The new design resolves the inconsistency (first-match vs. last-one-wins) by decoupling the "what" and "where".
  - **Dynamic branch selection**: When no explicit refspec, `remote.<name>.fetch`, or `remote.<name>.fetchRefmap` is given, `git fetch` enumerates branches tracked by local branches at the remote via `@{upstream}`. The `branches_tracking_remote()` helper (added in Patch 3/5) implements this logic; `get_ref_map()` integrates it. This logic now triggers only when neither `remote.<name>.fetch` nor `remote.<name>.fetchRefmap` is configured.
  - **Override semantics (proposed)**: Command-line refspecs (or colon-separated `remote.<name>.fetch` entries) must **override `remote.<name>.fetchRefmap` entirely**, not coexist with it (dual storage). This aligns with Phillip Wood’s latest feedback and preserves backwards compatibility.
  - **Dual storage behavior (deprecated)**: The earlier proposal to store refs in both the refmap’s destination and the explicit destination (e.g., `refs/remotes/cabal/master` and `refs/remotes/custom/master`) is now **deprecated** in favor of override semantics. This matches the command-line precedent (`git fetch --refmap=... refs/heads/master:refs/remotes/origin/master` updates only `origin/master`) and avoids ambiguity.
  - **`--limited-fetch` flag**: Added to `git remote add` (Patch 4/5), configures `remote.<name>.fetchRefmap` (e.g., `*@{upstream}`), while `remote.<name>.refmap` handles namespace mapping. The flag is rejected when combined with `-t/--track` or `--mirror`, as those options already specify what to fetch.
  - **Shallow-repository default**: Patch 5/5 makes `--limited-fetch` the default in shallow repositories by checking `is_repository_shallow(the_repository)`. The default uses `remote.<name>.fetchRefmap = *@{upstream}`.
  - **Backwards compatibility**: Older Git versions ignore `remote.<name>.fetchRefmap` and fail to fetch (safe) rather than misinterpreting `remote.<name>.fetch` as a refspec (unsafe). This addresses Phillip Wood’s concern about silent corruption of local branches. Junio confirmed that older Git versions treat `remote.<name>.fetch` entries without a destination as **fetch-only refspecs**, storing them only in `FETCH_HEAD` (safe but incomplete, as no persistent tracking refs are created).
  - **Fallback logic**: `remote_find_tracking()` falls back to `remote->fetchRefmap` (if configured) before dynamic branch enumeration.
  - **Files touched (v12)**:
    - `remote.c`/`remote.h`: Add `remote.<name>.fetchRefmap` parsing, adjust precedence rules, and rework `branches_tracking_remote()` to integrate with the new config key. Patch 2/5 added `collect_upstream_from_remote()` helper; Patch 3/5 added `branches_tracking_remote()` and integrated it into `get_ref_map()`. The implementation must now ensure command-line refspecs and colon-separated `fetch` entries override `fetchRefmap`.
    - `builtin/fetch.c`: Update integration with refmap configuration and dynamic branch enumeration to use `fetchRefmap`.
    - `builtin/remote.c`: Update `--limited-fetch` flag (Patch 4/5) and shallow-repository default (Patch 5/5) to use `fetchRefmap`.
    - Documentation: Update `remote.txt`, `git-fetch.adoc`, `git-remote.adoc`, and `fetch-options.adoc` to reflect the new design, including override semantics, backwards-compatibility considerations, the placement of `+`, the minor inconvenience of forced-update configuration, and the edge cases for colon-separated `fetch` entries. Tests: Update `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh`, and `t/t5505-remote.sh` to test the new `fetchRefmap` behavior, backwards compatibility, forced update placement, and override semantics.
  - **Behavior (v12)**:
    - New mode enabled when `remote.<name>.fetchRefmap` is configured (e.g., `*@{upstream}`).
    - `remote.<name>.refmap` handles namespace mapping only.
    - Precedence: `remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration.
    - Command-line refspecs override both config keys.
    - **Override semantics**: Command-line refspecs (or colon-separated `remote.<name>.fetch` entries) override `remote.<name>.fetchRefmap` entirely, not coexist with it.
    - No on-disk format changes beyond new configuration entries.
  - **New symbols (v12)**:
    - `remote.<name>.fetchRefmap`, `remote->fetchRefmap`, `collect_upstream_from_remote()`, `branches_tracking_remote()`, `--limited-fetch` flag, `--no-limited-fetch` flag.

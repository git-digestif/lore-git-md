Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using `remote.<name>.refmap` to separate namespace mappings from fetch selection logic.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. The configuration knob is added in Patch 1/5, mirroring `remote.<name>.fetch` but only providing a default for `--refmap` when there is something explicit to fetch (command-line refspecs or `remote.<name>.fetch`). If both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, the former takes precedence.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`). The `branches_tracking_remote()` helper in `remote.c` implements this logic, and `get_ref_map()` in `builtin/fetch.c` integrates it. The helper iterates over all local branches, collects the source ref for each branch whose `remote_name` matches the target remote, and constructs a dynamic refspec from these branches. The `do_fetch()` function populates `transport_ls_refs_options.ref_prefixes` with the inferred branches to limit the transport layer’s ref requests. The existing "fetch branches merged into the current branch" logic is extracted into a shared helper (`collect_upstream_from_remote`, introduced in Patch 2/5) to reduce duplication. The helper takes a `struct repository *`, a `string_list` to populate, a `remote`, and an optional branch name (NULL means the current branch), and adds the upstream refs of any matching branches to the list. **Junio’s review requirements are now addressed**: (1) the `if/else if/else` control-flow reorganization is moved to Patch 3/5, and (2) the NULL-check for `branch` is restored in `collect_upstream_from_remote()`.
- **Precedence rule**: When both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, `remote.<name>.fetch` takes precedence, and the `refmap` setting is ignored. This resolves the fatal error ("--refmap option is only meaningful with command-line refspec") and is uncontroversial.
- **`--limited-fetch` flag**: Added in Patch 4/5 to `git remote add`, this flag configures the remote to use `remote.<name>.refmap` (e.g., `+refs/heads/*:refs/remotes/<name>/*`) instead of the traditional wildcard `remote.<name>.fetch` refspec. The flag is rejected when combined with `-t/--track` or `--mirror`, as those options already specify explicit fetch behavior. The implementation updates `builtin/remote.c` to set the refmap configuration and adds documentation to `git-remote.adoc`. Junio’s review did not raise concerns about the implementation. Patch 5/5 makes `--limited-fetch` the default for shallow repositories by checking `is_repository_shallow(the_repository)` when `limited_fetch` is unset (`-1`), defaulting to `--limited-fetch` unless `--no-limited-fetch` is given. Test coverage in `t/t5505-remote.sh` verifies the flag’s behavior and conflict resolution with `-t`, as well as the shallow-repository default and `--no-limited-fetch` override.
- **Files touched**:
  - `remote.c`/`remote.h`: Implement `remote.<name>.refmap` parsing (Patch 1/5) and dynamic branch enumeration logic (Patch 3/5, including `branches_tracking_remote()` helper). Patch 2/5 extracts the existing "fetch branches merged into the current branch" logic into a shared helper (`collect_upstream_from_remote`). Hardcoded `the_repository` usage is fixed by threading a `struct repository *` parameter through callback data.
  - `builtin/fetch.c`: Integrate the new fetch logic with the refmap configuration (Patch 1/5 updates `--refmap` default behavior; Patch 3/5 adds dynamic branch enumeration via `get_ref_map()`). The potential duplicate fetch (when the current branch’s `@{upstream}` is also inferred by the new logic) is resolved. **Junio’s review requirements are now addressed**: (1) the `if/else if/else` control-flow reorganization is moved to Patch 3/5, and (2) the NULL-check for `branch` is restored in the helper call.
  - `builtin/remote.c`: Add `--limited-fetch` flag to `git remote add` (Patch 4/5) and default it in shallow repositories (Patch 5/5). The shallow check uses `is_repository_shallow(the_repository)` and threads through the existing `limited_fetch` logic without introducing new technical debt.
  - Documentation: `Documentation/config/remote.txt`, `Documentation/git-fetch.adoc`, `Documentation/git-remote.adoc`, `Documentation/config/remote.adoc`, and `Documentation/fetch-options.adoc` (updated to document the new default behavior for shallow repositories, the `--limited-fetch` flag, and the dynamic branch inference logic).
  - Tests: `t/t5510-fetch.sh` (four new tests: refmap works like `--refmap` on the command line, does nothing when nothing is being fetched, and `remote.<name>.fetch` takes precedence when both are present), `t/t5586-fetch-refmap.sh` (119 lines of coverage verifying edge cases: bare fetches, explicit one-time fetches, duplicate branch tracking, cross-remote tracking, and `git remote show` compatibility), and `t/t5505-remote.sh` (eight new tests: four for `--limited-fetch` and four for shallow-repository defaults). The test failures in `t5505` and `t5586` (caused by a textual conflict with Collin’s `ch/fetch-followremotehead-lazy-validation` topic in `seen`) are resolved in v8 and remain resolved in v9.
- **Behavior**:
  - The remote’s default branch is no longer fetched by default.
  - Non-shallow repositories continue using wildcard refspecs by default.
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories now default to it.
  - No on-disk format changes beyond the new configuration entries in `.git/config`.
  - Edge case: A bare `git fetch` against a refmap-only remote with no tracked branches fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use.

Thread identity
Subject: [PATCH] fetch: introduce `fetch.shallow` config to restrict refspec-less fetches to current branch
Series version: v1 (initial submission; now abandoned in favor of alternative solution)
Originating author: Harald Nordgren
Thread type: patch series (single patch, now superseded by design consensus on alternative approach)

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread initially proposed a new `fetch.shallow` configuration option to restrict such fetches to the current branch’s upstream, but has now converged on an alternative solution: modifying `git remote add` to avoid wildcard fetch refspecs in shallow repositories. The goal is to prevent unnecessary negotiation for all remote branches in shallow repositories by addressing the root cause (wildcard refspecs) rather than introducing a new configuration option.

Current status
Design consensus reached on alternative solution: modify `git remote add` to avoid wildcard refspecs in shallow repositories. The original patch (`fetch.shallow`) is abandoned and unmerged. No code changes have been implemented yet for the alternative solution; discussion is now focused on implementation details (e.g., whether the behavior should be configurable or automatic).

Key technical details
- **Original patch (abandoned)**:
  - Files touched: `builtin/fetch.c`, `Documentation/config/fetch.adoc`, `t/t5537-fetch-shallow.sh` (new test section)
  - Proposed config key: `fetch.shallow` (boolean, default `false`)
  - Behavior: when `fetch.shallow=true` and the repository is shallow, a refspec-less fetch would only fetch the current branch’s upstream
  - Test coverage: verified narrowing to tracked branch, correct update of `refs/remotes/<name>/HEAD`, no effect on non-shallow repositories or non-tracked remotes, and edge cases (stale `HEAD`, `fetch.followRemoteHEAD` interaction)
- **Alternative solution (now preferred)**:
  - Target: `git remote add` behavior in shallow repositories
  - Proposed change: default to a narrower refspec (e.g., `+refs/heads/<default-branch>:refs/remotes/<name>/<default-branch>`) instead of the current wildcard (`+refs/heads/*:refs/remotes/<name>/*`) for new remotes in shallow repositories
  - Scope: affects only shallow repositories; non-shallow repositories would continue to default to wildcard refspecs
  - No new CLI options or symbols proposed yet; potential new config key (e.g., `remote.addShallowRefspec`) remains under discussion
  - On-disk impact: changes the default refspec stored in `.git/config` for new remotes in shallow repositories

Open questions and loose ends
1. **Implementation of alternative solution**:
   - Should `git remote add` automatically detect shallow repositories and default to a narrower refspec, or should this behavior be configurable (e.g., via a new config option like `remote.addShallowRefspec`)?
   - How should the narrower refspec be constructed? Should it use the remote’s default branch (as determined by `HEAD`) or the local repository’s current branch?
   - Should there be a way for users to opt into wildcard refspecs for shallow repositories (e.g., via a `--wildcard` flag or manual refspec edit)?
2. **Backwards compatibility**:
   - The alternative solution must preserve existing workflows for non-shallow repositories (wildcard refspecs remain the default).
   - How should existing shallow repositories with wildcard refspecs be handled? Should `git remote add` warn or offer a migration path?
3. **Scope of the performance issue**:
   - Confirmed to affect any shallow repository with many remote-tracking branches, not just sparse checkouts.
   - The alternative solution would prevent the issue from arising in new shallow repositories but does not address existing ones.
4. **No code changes yet**: The original patch remains unmodified, and no new patch has been proposed for the alternative solution. The discussion is still in the design phase.

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The series implements a "matching-inspired" fetch mode that fetches only the upstream branches of local branches, using explicit configuration to separate namespace mappings from fetch selection logic. The v15 design introduces `remote.<name>.fetchRefmap` to decouple the "what" (which refs to fetch) from the "where" (where to store them), and `remote.<name>.fetchUpstreams` as a boolean to explicitly opt in to fetching upstream branches of local branches on refspec-less fetches, resolving the maintainer's objection to v14's implicit dynamic fallback. Matt Hunter clarified that the series is blocking `ch/remote-defer-follow-remote-head-validation` (Collin's topic) due to textual conflicts, but the dependency is not strict -- the other author is deferring resolution until this series lands.

Override semantics (RESOLVED, CONFIRMED, and IMPLEMENTED in v15 head patches): Phillip Wood proposed that command-line refspecs (or colon-separated `remote.<name>.fetch` entries) containing an explicit destination (`src:dst`) should cause both `--refmap` on the command line and `remote.<name>.fetchRefmap` config to be ignored entirely, preventing dual storage. Junio C Hamano reversed his initial disagreement and endorsed this approach: any refspec carrying an explicit destination (`src:dst`) -- whether passed on the command line or found in configuration -- ignores the refmap entirely, so the refmap applies only to refspec entries lacking their own destination. Phillip Wood confirmed agreement with two concrete examples demonstrating functional equivalence between command-line `--refmap` and config `fetchRefmap` for destination-less refspecs. v15 implements this in two new head patches: (1) a refspec with its own destination (`src:dst`) ignores both `--refmap` and `fetchRefmap` entirely, and (2) `--refmap` on the command line now works even without command-line refspecs, applying to whatever `remote.<name>.fetch` selects.

Key technical details
- Finalized design (v15):
  - New config keys: `remote.<name>.fetchRefmap` (specifies where fetched refs are stored, default for `--refmap`) and `remote.<name>.fetchUpstreams` (boolean, enables fetching upstream branches of local branches on refspec-less fetch).
  - Refmap role: `remote.<name>.refmap` handles namespace mapping only.
  - Precedence: `remote.<name>.fetch` > explicit `fetchUpstreams` opt-in > refmap application. Command-line refspecs override config keys.
  - Override semantics (RESOLVED and IMPLEMENTED): Any refspec with an explicit destination (`src:dst`), whether on the command line or in configuration, ignores the refmap (and thus `remote.<name>.fetchRefmap`) entirely; `--refmap` applies only when no command-line refspecs carry destinations, and works against `remote.<name>.fetch` selections even without command-line refspecs. Patch 1/7 implements this via `map_refs_without_dst()` in `builtin/fetch.c`, which filters the ref map to only entries lacking a `peer_ref` before applying the refmap, replacing the previous indiscriminate application. Patch 2/7 implements the second half: `get_ref_map()` in `builtin/fetch.c` no longer dies with "--refmap option is only meaningful with command-line refspec(s)" when no command-line refspecs are given; instead, when configured `remote.<name>.fetch` refspecs build the ref map, the new `drop_destinations()` helper clears each entry's `peer_ref`, and then `map_refs_without_dst()` applies the command-line `--refmap` to those destination-less entries. Updates `Documentation/fetch-options.adoc` to describe that without command-line refspecs, `remote.<name>.fetch` values select what is fetched while refs are stored through the `--refmap` specification; rewrites test in `t/t5510-fetch.sh` from expecting failure to verifying that `git fetch --refmap="refs/heads/*:refs/remotes/none/*" origin` fetches configured refs but stores `main` at `refs/remotes/none/main` instead of `refs/remotes/origin/main`. Patch 1/7 also updates `Documentation/fetch-options.adoc` and adds test verifying `git fetch --refmap=... origin main:refs/remotes/custom/main side` stores `main` only at `custom/main` while `side` (no destination) still goes through the refmap.
  - Forced updates (`+`): Belong on the refmap side.
  - Dynamic branch selection: Replaced by explicit `fetchUpstreams` opt-in; when enabled and no explicit refspec is given, `git fetch` enumerates branches tracked by local branches via `@{upstream}`.
  - `git pull` fix: Merges only the current branch's upstream rather than every tracked branch.
  - `--limited-fetch` flag: Sets both `fetchRefmap` and `fetchUpstreams`; default for `git remote add` in shallow repos; overridden by `--no-limited-fetch`, `-t/--track`, or `--mirror`.
  - Backwards compatibility: Older Git versions ignore `remote.<name>.fetchRefmap` and `remote.<name>.fetchUpstreams` and fail safely.
  - Files touched: `builtin/fetch.c`, `remote.c`/`remote.h`, `builtin/remote.c`, documentation, tests (`t5586-fetch-refmap.sh`, `t5510-fetch.sh`, `t5505-remote.sh`).
  - New symbols: `remote.<name>.fetchRefmap`, `remote.<name>.fetchUpstreams`, `remote->fetchRefmap`, `remote->fetch_upstreams`, `add_branch_upstreams()`, `map_refs_without_dst()`, `drop_destinations()`, `--limited-fetch`, `--no-limited-fetch`.

Subject: [PATCH] fetch: introduce `fetch.shallow` config to restrict refspec-less fetches to current branch
Series version: v1 (initial submission; discussion now converging on alternative solution)
Originating author: Harald Nordgren
Thread type: patch series (single patch, now under design reconsideration toward alternative approach)

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread initially proposed a new `fetch.shallow` configuration option to restrict such fetches to the current branch’s upstream, but has now shifted to exploring whether the root cause lies in `git remote add` defaulting to a wildcard fetch refspec in shallow repositories. The goal is to prevent unnecessary negotiation for all remote branches in shallow repositories, either via `fetch.shallow` or by modifying `git remote add` behavior.

Current status
Under active design discussion. The original patch remains unmodified and unmerged. The thread is converging on an alternative solution: modifying `git remote add` to avoid wildcard refspecs in shallow repositories, potentially eliminating the need for `fetch.shallow`. No merge status reported; no code changes requested yet for either approach.

Key technical details
- Files touched in original patch: `builtin/fetch.c`, `Documentation/config/fetch.adoc`, `t/t5537-fetch-shallow.sh` (new test section)
- Proposed new config key in original patch: `fetch.shallow` (boolean, default `false`)
- Behavior of original patch: when `fetch.shallow=true` and the repository is shallow, a refspec-less fetch would only fetch the current branch’s upstream
- Test coverage in original patch: verifies narrowing to tracked branch, correct update of `refs/remotes/<name>/HEAD`, no effect on non-shallow repositories or non-tracked remotes, and edge cases (stale `HEAD`, `fetch.followRemoteHEAD` interaction)
- No new CLI options, symbols, or on-disk format changes in original patch
- Alternative solution now under active discussion: modifying `git remote add` to avoid wildcard refspecs in shallow repositories (e.g., defaulting to `+refs/heads/<default-branch>:refs/remotes/<name>/<default-branch>` instead of `+refs/heads/*:refs/remotes/<name>/*`). This would affect the default refspec stored in `.git/config` for new remotes in shallow repositories.

Open questions and loose ends
1. **Design direction**: The thread has converged on exploring the alternative solution (modifying `git remote add` behavior in shallow repositories) rather than introducing `fetch.shallow`. No objections to this pivot have been raised.
2. **Implementation of alternative solution**:
   - Should `git remote add` detect shallow repositories and default to a narrower refspec (e.g., `+refs/heads/<default-branch>:refs/remotes/<name>/<default-branch>`)?
   - Should this behavior be configurable (e.g., via a new config option like `remote.addShallowRefspec`)?
   - How should this interact with existing remotes or manual refspec edits? Would users need a way to opt into wildcard refspecs for shallow repositories?
3. **Backwards compatibility**: Any change to `git remote add` behavior must preserve existing workflows for non-shallow repositories. The alternative solution would only affect shallow repositories, so non-shallow repositories would continue to default to wildcard refspecs.
4. **Scope of the performance issue**: Confirmed that the problem affects any shallow repository with many remote-tracking branches (e.g., after adding a second remote with a wildcard fetch refspec), not just sparse checkouts.
5. **No code changes yet**: The original patch remains unmodified, and no new patch has been proposed for the alternative solution. The discussion is still in the design phase.

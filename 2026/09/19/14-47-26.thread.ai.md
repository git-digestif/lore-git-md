Thread identity: Subject `[PATCH] fetch: introduce `+:` refspec for matching-inspired fetch mode`, series v15 (7 patches), originating author Harald Nordgren, thread type patch series. The series implements a matching-inspired fetch mode using explicit configuration (`remote.<name>.fetchUpstreams` and `remote.<name>.fetchRefmap`) to decouple which refs are fetched from where they are stored, addressing slow or hanging `git fetch`/`git pull` in shallow repositories with many remote branches.

Core problem or goal: Users of shallow repositories experience degraded fetch performance when the remote has many branches. The series implements limited-fetch semantics where only locally tracked upstream branches are fetched by default, configurable via `remote.<name>.fetchUpstreams` (boolean) and `remote.<name>.fetchRefmap` (refspec mapping), with `git remote add` defaulting to this mode in shallow repositories unless `-t`/`--track` or `--mirror` is specified.

Key technical details: Patch 1/7 introduces `map_refs_without_dst()` relying on `rm->peer_ref` being NULL to distinguish destination-less or empty-destination refspecs from those with explicit destinations, ensuring `copy_ref()` does not recurse and `get_fetch_map()` allocates fresh entries for refmap application; semantics validated such that `refs/heads/main` and `refs/heads/next:` (empty `<dst>`) remain subject to `--refmap`/`fetchRefmap` while `refs/heads/seen:refs/remotes/origin/seen` (non-empty `<dst>`) bypasses the refmap and is stored only at the explicit destination. Patch 3/7 added `struct refspec refmap` to `struct remote` in `remote.h`, parsed the `fetchrefmap` subkey in `remote.c`'s `handle_config()`, and initialized/cleared it in `make_remote()`/`remote_clear()`; `get_ref_map()` in `builtin/fetch.c` computes `effective_refmap` preferring `--refmap` over `remote->refmap`, applying it via `map_refs_without_dst()` only to destination-less entries; `remote_find_tracking()` consults the refmap when `remote.<name>.fetch` yields no match. Patch 4/7 extracted `collect_upstream_from_remote(struct remote *remote, const char *refname, struct strvec *refs)` in `remote.c`/`remote.h`, with the existing call site passing NULL to preserve behavior from commit 49ca2fba39 (2022). Patch 5/7 adds `bool fetch_upstreams` to `struct remote` parsed via the `fetchupstreams` subkey, introduces `branches_tracking_remote()` in `remote.c` iterating local branches via `refs_for_each_branch_ref()` and `add_if_tracking_remote()` calling `collect_upstream_from_remote()` per branch, and adds `add_branch_upstreams()` in `builtin/fetch.c` converting upstreams to destination-less refspec items fed through `get_fetch_map()`; both `get_ref_map()` and `do_fetch()` check `remote->fetch_upstreams`; `tracking_for_push_dest()` extended so `@{push}` consults `remote->refmap` via `apply_refspecs()`. Patch 6/7 modifies `add()` in `builtin/remote.c` with `OPT_BOOL` for `limited_fetch` (init -1), dying if combined with `-t`/`--track` or `--mirror`, otherwise writing `remote.<name>.fetchRefmap` = `+refs/heads/*:refs/remotes/<name>/*` and `remote.<name>.fetchUpstreams` = `true` instead of the traditional wildcard fetch refspec. Patch 7/7 consults `is_repository_shallow(the_repository)` when `--limited-fetch` not explicit: shallow repositories default to limited-fetch semantics unless `-t`/`--track` or `--mirror` present, while full repositories keep wildcard `remote.<name>.fetch`; `--no-limited-fetch` explicitly disables.

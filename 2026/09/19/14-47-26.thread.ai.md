Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using `remote.<name>.refmap` to separate namespace mappings from fetch selection logic.

No substantive objections remain.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. This is the consensus-approved design.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`). The forced inclusion of the remote’s default branch (present in v3) is removed. The `branches_tracking_remote()` helper in `remote.c` implements this logic, and `get_ref_map()` in `builtin/fetch.c` integrates it.
- **Files touched**:
  - `remote.c`/`remote.h`: Implement `remote.<name>.refmap` parsing (Patch 1/4) and dynamic branch enumeration logic (Patch 2/4, including `branches_tracking_remote()` helper).
  - `builtin/fetch.c`: Integrate the new fetch logic with the refmap configuration (Patch 1/4 updates `--refmap` default behavior; Patch 2/4 adds dynamic branch enumeration via `get_ref_map()`).
  - `builtin/remote.c`: Add `--limited-fetch` flag to `git remote add` (Patch 3/4) and default it in shallow repositories (Patch 4/4). The flag writes `remote.<name>.refmap` (e.g., `+refs/heads/*:refs/remotes/<name>/*`) instead of `remote.<name>.fetch` when no branches are tracked, enabling dynamic branch enumeration. Conflicts with `-t/--track` and `--mirror` are explicitly rejected. The shallow-repository default is implemented via `is_repository_shallow()`.
  - `Documentation/config/remote.txt`, `Documentation/git-fetch.adoc`, and `Documentation/git-remote.adoc`: Document `remote.<name>.refmap` (Patch 1/4), the matching-inspired fetch mode (Patch 2/4), the `--limited-fetch` flag (Patch 3/4), and the shallow-repository default (Patch 4/4).
  - `t/t5510-fetch.sh`: Test `remote.<name>.refmap` configuration (Patch 1/4).
  - `t/t5586-fetch-refmap.sh`: New tests covering refmap configuration, dynamic branch enumeration, and edge cases (stale `HEAD`, empty repositories, multiple tracking branches, duplicate branches, branches tracking other remotes).
  - `t/t5505-remote.sh`: Tests for the `--limited-fetch` flag (Patch 3/4) and shallow-repository default (Patch 4/4), including conflict with `-t`, correct configuration of `remote.<name>.refmap`, and the `--no-limited-fetch` override.
- **Behavior**:
  - The remote’s default branch is no longer fetched by default (resolving Junio’s objection).
  - Non-shallow repositories continue using wildcard refspecs by default (backward compatibility preserved).
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories default to it.
  - No on-disk format changes beyond the new configuration entry in `.git/config`.

Open questions and loose ends
1. **Edge-case handling**:
   - Should the matching-inspired mode be available outside of shallow repositories, or is it strictly a shallow-repository optimization? (No new input in v6.)
   - How should the implementation handle remotes with no default branch (e.g., empty repositories)? The current implementation falls back to the inferred branch list, but this may not always be correct. (No resolution in v6.)
   - Should existing shallow repositories with wildcard refspecs be migrated automatically, or should users opt in via configuration? (No new input in v6.)
   - Should there be a warning for users who might rely on the old behavior? (No new input in v6.)
   - A bare `git fetch` against a refmap-only remote (no `remote.<name>.fetch` refspec) fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use. Harald Nordgren acknowledges this as a minor quibble and not a blocker, but flags it for potential future discussion.
2. **Backward compatibility**:
   - The v6 series preserves backward compatibility for non-shallow repositories but does not address migration of existing shallow repositories. No objections have been raised yet, but this may require follow-up discussion or patches.

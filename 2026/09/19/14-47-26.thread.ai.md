Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The series implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using configuration to separate namespace mappings from fetch selection logic. The finalized design for v13/v14 (endorsed by Junio C Hamano and Phillip Wood) introduces `remote.<name>.fetchRefmap` to decouple the "what" (which refs to fetch) from the "where" (where to store them), resolving the maintainer's objection to overloading `remote.<name>.refmap`. Matt Hunter clarified that the series is blocking `ch/remote-defer-follow-remote-head-validation` (Collin's topic) due to textual conflicts, but the dependency is not strict -- the other author is deferring resolution until this series lands. Merging only Patches 1--3 would resolve the conflicts and unblock the dependent topic.

Override semantics (resolved in v14): Command-line refspecs (or colon-separated `remote.<name>.fetch` entries) override `remote.<name>.fetchRefmap` entirely, not coexist with it (dual storage). This aligns with Phillip Wood's explicit confirmation and resolves the ambiguity that blocked v13.

Key technical details
- Finalized design (v14):
  - New config key: `remote.<name>.fetchRefmap` specifies which refs to fetch (e.g., `*@{upstream}`).
  - Refmap role: `remote.<name>.refmap` handles namespace mapping only.
  - Precedence: `remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration. Command-line refspecs override both config keys.
  - Override semantics: Command-line refspecs override `remote.<name>.fetchRefmap` entirely.
  - Forced updates (`+`): Belong on the refmap side.
  - Dynamic branch selection (Patch 3/5): When no explicit refspec, `remote.<name>.fetch`, or `remote.<name>.fetchRefmap` is given, `git fetch` enumerates branches tracked by local branches via `@{upstream}` using `branches_tracking_remote()`. Phillip Wood now argues this implicit fallback should not be the default behavior when explicit smart modes exist.
  - Helper extraction (Patch 2/5): `collect_upstream_from_remote()` extracted mechanically from `builtin/fetch.c`.
  - `@{push}` resolution: Fix squashed into Patch 3/5; falls back to `remote->refmap` if `remote->fetch` does not resolve the refname.
  - `--limited-fetch` flag (Patch 4/5): Configures `remote.<name>.fetchRefmap = *@{upstream}`; rejected with `-t/--track` or `--mirror`.
  - Shallow-repository default (Patch 5/5): Enables `--limited-fetch` by default in shallow repos; overridden by `--no-limited-fetch`, `-t/--track`, or `--mirror`.
  - Backwards compatibility: Older Git versions ignore `remote.<name>.fetchRefmap` and fail safely.
  - Files touched: `remote.c`/`remote.h`, `builtin/fetch.c`, `builtin/remote.c`, documentation (`remote.txt`, `git-fetch.adoc`, `git-remote.adoc`, `fetch-options.adoc`), tests (`t5510-fetch.sh`, `t5586-fetch-refmap.sh`, `t5505-remote.sh`).
  - New symbols: `remote.<name>.fetchRefmap`, `remote->fetchRefmap`, `collect_upstream_from_remote()`, `branches_tracking_remote()`, `add_if_tracking_remote()`, `branches_tracking_remote_cb_data`, `--limited-fetch`, `--no-limited-fetch`, `tracking_for_push_dest()`.

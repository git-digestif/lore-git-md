Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The series implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using configuration to separate namespace mappings from fetch selection logic. The **design is under architectural reconsideration**: Phillip Wood proposes eliminating the special case for refspec-less fetches (Patch 3/6) by relying on default values of `remote.<name>.fetch` and `remote.<name>.fetchRefmap`, which would simplify the series and remove the need for dynamic branch enumeration. The **finalized design for v13** (endorsed by Junio C Hamano and Phillip Wood) introduces `remote.<name>.fetchRefmap` to decouple the "what" (which refs to fetch) from the "where" (where to store them), resolving the maintainer’s objection to overloading `remote.<name>.refmap`. **New strategic context**: Matt Hunter clarifies that the series is **blocking `ch/remote-defer-follow-remote-head-validation` (Collin’s topic) due to textual conflicts**, but the dependency is **not strict**—the other author is deferring resolution until this series lands. Merging **only Patches 1–3** would resolve the conflicts and unblock the dependent topic, **strengthening the case for a partial merge** and **weakening Phillip’s architectural objection** to Patch 3/6.

Key technical details
- **Finalized design (v13)**:
  - **New config key**: `remote.<name>.fetchRefmap` explicitly specifies which refs to fetch (e.g., `*@{upstream}`), decoupling the "what" from the "where".
  - **Refmap role**: `remote.<name>.refmap` reverts to its original purpose: namespace mapping only (e.g., `+refs/heads/*:refs/remotes/second/*`).
  - **Precedence**: `remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration (if neither is configured). Command-line refspecs override both config keys.
  - **Forced updates (`+`)**: Belong on the refmap side (the "where"), not the `fetchRefmap` side (the "what"), as confirmed by Junio and Phillip Wood. This aligns with existing refspec behavior but introduces a **minor inconvenience**: users who want to reject non-fast-forward updates for some branches while mapping all refs the same way must now use **two separate refspecs** (one with `+` and one without). The documentation clarifies this behavior.
  - **Refspec-matching order**: The new design resolves the inconsistency (first-match vs. last-one-wins) by decoupling the "what" and "where".
  - **Dynamic branch selection (Patch 3/6)**: When no explicit refspec, `remote.<name>.fetch`, or `remote.<name>.fetchRefmap` is given, `git fetch` enumerates branches tracked by local branches at the remote via `@{upstream}`. The `branches_tracking_remote()` helper (added in Patch 3/6) implements this logic; `get_ref_map()` integrates it. This logic now triggers only when neither `remote.<name>.fetch` nor `remote.<name>.fetchRefmap` is configured. **This patch is now strategically critical** for resolving the dependent topic’s conflicts, as clarified by Matt Hunter.
  - **Override semantics (confirmed)**: Command-line refspecs (or colon-separated `remote.<name>.fetch` entries) **override `remote.<name>.fetchRefmap` entirely**, not coexist with it (dual storage). This aligns with Phillip Wood’s latest feedback and preserves backwards compatibility.
  - **Dual storage behavior (current, deprecated)**: The v13 revision preserves the current behavior where colon-separated `fetch` entries with explicit destinations are stored in both the explicit destination and the refmap’s destination. This is **confirmed as incorrect** and will be updated in v14 to reflect override semantics.
  - **`@{push}` resolution fix**: The v13 revision adds a fallback to `remote->refmap` in `tracking_for_push_dest()` (Patch 6/6) if `remote->fetch` does not resolve the refname, ensuring `@{push}` works correctly for remotes configured with `--limited-fetch`. The fix is **mechanical, uncontroversial, and well-tested** (new test in `t/t1514-rev-parse-push.sh`). However, the interaction with override semantics is **unclear** and may require **further clarification or implementation** in v14. Phillip’s architectural proposal would **eliminate the need for this fallback**.
  - **`--limited-fetch` flag**: Added to `git remote add` (Patch 4/6), configures `remote.<name>.fetchRefmap` (e.g., `*@{upstream}`), while `remote.<name>.refmap` handles namespace mapping. The flag is rejected when combined with `-t/--track` or `--mirror`, as those options already specify what to fetch.
  - **Shallow-repository default**: Patch 5/6 makes `--limited-fetch` the default in shallow repositories by checking `is_repository_shallow(the_repository)`. The default uses `remote.<name>.fetchRefmap = *@{upstream}` and is overridden by `--no-limited-fetch`, `-t/--track`, or `--mirror`.
  - **Backwards compatibility**: Older Git versions ignore `remote.<name>.fetchRefmap` and fail to fetch (safe) rather than misinterpreting `remote.<name>.fetch` as a refspec (unsafe). This addresses Phillip Wood’s concern about silent corruption of local branches. Junio confirmed that older Git versions treat `remote.<name>.fetch` entries without a destination as **fetch-only refspecs**, storing them only in `FETCH_HEAD` (safe but incomplete, as no persistent tracking refs are created).

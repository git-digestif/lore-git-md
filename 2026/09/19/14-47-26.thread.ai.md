Thread identity: Subject `[PATCH] fetch: introduce `+:` refspec for matching-inspired fetch mode`, series v16 (7 patches), originating author Harald Nordgren, thread type patch series. The series implements a matching-inspired fetch mode using explicit configuration (`remote.<name>.fetchUpstreams` and `remote.<name>.fetchRefmap`) to decouple which refs are fetched from where they are stored, addressing slow or hanging `git fetch`/`git pull` in shallow repositories with many remote branches.

Core problem or goal: Users of shallow repositories experience degraded fetch performance when the remote has many branches. The series implements limited-fetch semantics where only locally tracked upstream branches are fetched by default, configurable via `remote.<name>.fetchUpstreams` (boolean) and `remote.<name>.fetchRefmap` (refspec mapping), with `git remote add` defaulting to this mode in shallow repositories unless `-t`/`--track` or `--mirror` is specified.

Key technical details: Patch 1/7 introduces `map_refs_without_dst()` relying on `rm->peer_ref` being NULL to distinguish destination-less or empty-destination refspecs from those with explicit destinations, ensuring `copy_ref()` does not recurse and `get_fetch_map()` allocates fresh entries for refmap application; semantics validated such that `refs/heads/main` and `refs/heads/next:` (empty `<dst>`) remain subject to `--refmap`/`fetchRefmap` while `refs/heads/seen:refs/remotes/origin/seen` (non-empty `<dst>`) bypasses the refmap and is stored only at the explicit destination. Patch 2/7 adds `drop_destinations()` helper in `builtin/fetch.c` that clears `peer_ref` on refspec items to make them destination-less before refmap application; modifies `get_ref_map()` to remove the fatal error when `--refmap` is given without CLI refspecs, instead calling `drop_destinations()` and `map_refs_without_dst()` when `refmap.nr` is non-zero, setting `*autotags = 1` if any refs result from the mapping; the error is preserved only when there are no refspecs to fetch at all (e.g., bare URL with no configured `remote.<name>.fetch`). Tags are followed when fetched refs end up stored somewhere through the refmap, but `--refmap=""` stores nothing and follows no tags. When `--prune` is used with `--refmap` and no command-line refspecs, `do_fetch()` skips pruning the configured `remote.<name>.fetch` destinations since the fetch does not store there; destinations created by the refmap itself are also not pruned. Tests in `t/t5510-fetch.sh` cover: `--refmap` without CLI refspecs stores at refmap destination while leaving original `refs/remotes/origin/main` untouched; destination-less configured refspecs store through refmap and follow tags; `--refmap=""` does not follow tags; `--prune` with `--refmap` leaves configured destinations intact; `--refmap` still rejected when fetching from URL with no refspecs configured. Documentation in `Documentation/fetch-options.adoc` clarifies command-line refspecs with non-empty destinations bypass the refmap, while without command-line refspecs the configured refspecs decide what is fetched but the refmap decides where it is stored. Patch 3/7 adds `struct refspec refmap` to `struct remote` in `remote.h`, parsed via the `fetchrefmap` subkey in `remote.c`'s `handle_config()`, and initialized/cleared in `make_remote()`/`remote_clear()`; `get_ref_map()` computes `effective_refmap` preferring `--refmap` over `remote->refmap`, applying it via `map_refs_without_dst()` only to destination-less entries; `remote_find_tracking()` consults the refmap when `remote.<name>.fetch` yields no match so that `@{upstream}` and `git branch --track` resolve correctly for branches stored via the refmap, while still respecting negative refspec exclusions. Behaviorally, configuring `remote.<name>.fetchRefmap` does not change what is fetched; `remote.<name>.fetch` still controls the source refs. Entries in `remote.<name>.fetch` without an explicit destination are stored through the refmap, while entries with their own non-empty destination bypass the refmap entirely. Tags are followed for refs stored through the refmap just as they are for refs stored through the fetch refspec. The command-line `--refmap` overrides the configured value when both are present. Tests in `t/t5510-fetch.sh` cover baseline behavior where nothing is fetched without tracked branches, storage of named branches through the refmap, CLI override of the config, exemption of destination-bearing refspecs (both configured and command-line), upstream tracking for branches outside the fetch refspec, and exclusion of branches matched by negative refspecs. Documentation in `Documentation/config/remote.adoc` and `Documentation/fetch-options.adoc`. Patch 4/7 extracts `collect_upstream_from_remote(struct repository *repo, const struct remote *remote, const char *refname, struct strvec *tracked)` in `remote.c`/`remote.h`; the function checks `branch_has_merge_config()` and that `branch->remote_name` matches the remote's name, then appends each `branch->merge[i]->src` to the vector; the existing call site in `builtin/fetch.c`'s `do_fetch()` passes `refname = NULL` to preserve the behavior from commit 49ca2fba39 (2022) of fetching the current branch's upstream even when the configured refspec does not cover it. Patch 5/7 adds `bool fetch_upstreams` to `struct remote` parsed via the `fetchupstreams` subkey in `remote.c:handle_config()`, introduces `branches_tracking_remote()` in `remote.c` iterating local branches via `refs_for_each_branch_ref()` and `add_if_tracking_remote()` calling `collect_upstream_from_remote()` per branch, and adds `add_branch_upstreams()` in `builtin/fetch.c` converting upstreams to destination-less refspec items fed through `get_fetch_map()`; both `get_ref_map()` and `do_fetch()` check `remote->fetch_upstreams` to include these extra upstreams in the transport ls-refs prefix list; `tracking_for_push_dest()` is extended to fall back to `apply_refspecs(&remote->refmap, ...)` when the fetch refspec yields no match, allowing `@{push}` to resolve to the correct remote-tracking branch on a refmap-only remote. Tests in the new `t/t5586-fetch-refmap.sh` cover shallow-clone setup, tracking multiple branches, de-duplication of shared upstreams, isolation from other remotes, combination with explicit `remote.<name>.fetch`, `--prefetch`, `git pull` merging only the current branch's upstream, and `@{push}` resolution after pushing to a refmap-only remote. Patch 6/7 modifies `add()` in `builtin/remote.c` with `OPT_BOOL` for `limited_fetch` (init -1), dying if combined with `-t`/`--track` or `--mirror`, otherwise writing `remote.<name>.fetchRefmap` = `+refs/heads/*:refs/remotes/<name>/*` and `remote.<name>.fetchUpstreams` = `true` instead of the traditional wildcard fetch refspec; tests in `t/t5505-remote.sh` confirm the new config keys are written correctly in a full (non-shallow) clone and that `--limited-fetch -t` is rejected; documentation in `Documentation/git-remote.adoc` describes the new flag and its effect. Patch 7/7 modifies the `add()` function in `builtin/remote.c` so that the existing `use_limited_fetch` boolean evaluates to true when `limited_fetch == -1` (unset) and `is_repository_shallow(the_repository)` returns true, meaning shallow repositories default to limited-fetch semantics (writing `remote.<name>.fetchRefmap` and `remote.<name>.fetchUpstreams` instead of the wildcard `remote.<name>.fetch`) unless `-t`/`--track`, `--mirror`, or explicit `--no-limited-fetch` is given, while full repositories retain the wildcard default; tests in `t/t5505-remote.sh` verify that adding a remote with `-t` in a shallow repo still writes an explicit refspec, adding in a full repo writes the wildcard, adding in a shallow repo without flags writes the refmap and fetchUpstreams config (omitting `remote.<name>.fetch`) with a functional check that `git fetch` only updates tracked upstreams, and `--no-limited-fetch` in a shallow repo restores the wildcard refspec; documentation in `Documentation/git-remote.adoc` describes the shallow-repository default and the `--no-limited-fetch` override.

Changes between v15 and v16: v16 addresses the three unresolved concerns Junio C Hamano raised on v15 patch 2/7. (1) `--refmap` is rejected again when the remote has nothing configured to fetch (e.g., a bare URL), preventing the silent ignoring of the refmap while fetching HEAD into FETCH_HEAD. (2) Tags are now followed when a refspec-less fetch stores refs through `--refmap` or `fetchRefmap`, while `--refmap=""` stores nothing and follows no tags, resolving the `*autotags` computation timing issue. (3) `--prune` with `--refmap` and no command-line refspecs no longer prunes the configured destinations in `remote.<name>.fetch`, leaving them untouched since the fetch does not store there, fixing the `prune_refs()` refspec source issue. Documentation clarifies that destinations from a refmap are not pruned and that non-empty destinations are exempt from refmap application.

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using `remote.<name>.refmap` to separate namespace mappings from fetch selection logic.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. This design remains consensus-approved.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`). The forced inclusion of the remote’s default branch (present in v3) is removed. The `branches_tracking_remote()` helper in `remote.c` implements this logic, and `get_ref_map()` in `builtin/fetch.c` integrates it. The helper iterates over all local branches, collects the source ref for each branch whose `remote_name` matches the target remote, and constructs a dynamic refspec from these branches. The `do_fetch()` function populates `transport_ls_refs_options.ref_prefixes` with the inferred branches to limit the transport layer’s ref requests.
- **Precedence rule**: When both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, `remote.<name>.fetch` takes precedence, and the `refmap` setting is ignored. This resolves the fatal error ("--refmap option is only meaningful with command-line refspec") by treating the `fetch` refspec as the authoritative source of truth.
- **Files touched**:
  - `remote.c`/`remote.h`: Implement `remote.<name>.refmap` parsing (Patch 1/4) and dynamic branch enumeration logic (Patch 2/4, including `branches_tracking_remote()` helper).
  - `builtin/fetch.c`: Integrate the new fetch logic with the refmap configuration (Patch 1/4 updates `--refmap` default behavior; Patch 2/4 adds dynamic branch enumeration via `get_ref_map()`).
  - `builtin/remote.c`: Add `--limited-fetch` flag to `git remote add` (Patch 3/4) and default it in shallow repositories (Patch 4/4). Patch 4/4 uses `is_repository_shallow()` to check if the repository is shallow and defaults the `limited_fetch` flag to `1` unless `--no-limited-fetch` is given.
  - Documentation: `Documentation/config/remote.txt`, `Documentation/git-fetch.adoc`, and `Documentation/git-remote.adoc` (updated to document the new default behavior for shallow repositories).
  - Tests: `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh` (new in v5), and `t/t5505-remote.sh` (four new tests added for Patch 4/4: `-t` still sets explicit refspec, full repositories keep wildcard refspec, shallow repositories default to `--limited-fetch`, and `--no-limited-fetch` overrides the default).
- **Behavior**:
  - The remote’s default branch is no longer fetched by default.
  - Non-shallow repositories continue using wildcard refspecs by default.
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories now default to it.
  - No on-disk format changes beyond the new configuration entry in `.git/config`.
  - Edge case: A bare `git fetch` against a refmap-only remote with no tracked branches fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use.
- **Patch 1/4 specifics**: Introduces `remote.<name>.refmap` parsing in `remote.c`, stores it in `struct remote`, and updates `builtin/fetch.c` to use it as the default `--refmap` when no explicit refspec is provided. Documentation and tests verify the precedence rule (`remote.<name>.fetch` overrides `remote.<name>.refmap`) and equivalence to the `--refmap` command-line option.
- **Patch 2/4 specifics**: Implements the dynamic branch enumeration logic via `branches_tracking_remote()` in `remote.c` and integrates it into `get_ref_map()` in `builtin/fetch.c`. The inferred refspec is built from tracked branches and passed to `get_fetch_map()`. The `do_fetch()` function updates `transport_ls_refs_options.ref_prefixes` to limit ref requests. Tests verify edge cases: no branches fetched when none are tracked, correct updates when branches are added, and no duplicate fetches when multiple local branches track the same remote branch.
- **Patch 3/4 specifics**: Adds a `--limited-fetch` flag to `git remote add`, which sets `remote.<name>.refmap` (e.g., `+refs/heads/*:refs/remotes/<name>/*`) instead of the traditional wildcard `remote.<name>.fetch` refspec. The flag is rejected if combined with `-t/--track` or `--mirror`, as those options already specify explicit fetch behavior. The `limited_fetch` flag in `builtin/remote.c` defaults to `-1` (unspecified) and is only applied when no conflicting options are present. Documentation in `git-remote.adoc` describes the new option, and tests in `t/t5505-remote.sh` verify its behavior, including edge cases like conflicts with `-t` and correct configuration in non-shallow repositories.
- **Patch 4/4 specifics**: Defaults shallow repositories to use `--limited-fetch` when adding a new remote, ensuring the matching-inspired fetch mode is enabled by default for shallow clones. The patch uses `is_repository_shallow()` to check if the repository is shallow and defaults the `limited_fetch` flag to `1` unless `--no-limited-fetch` is given. Documentation in `git-remote.adoc` is updated to explain the new default behavior, and the test suite (`t/t5505-remote.sh`) adds four new tests covering edge cases and backward compatibility.

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using `remote.<name>.refmap` to separate namespace mappings from fetch selection logic.

Key patches:
1. **Patch 1/4**: Introduces `remote.<name>.refmap` configuration to define namespace mappings. Updates `remote.c` to parse the configuration, extends `builtin/fetch.c` to use the configured refmap as the default `--refmap` value, and documents the feature in `config/remote.adoc` and `fetch-options.adoc`. Tests in `t/t5510-fetch.sh` verify the configuration behaves identically to the `--refmap` command-line option. Documentation wording in v4 precisely defines `remote.<name>.refmap` as "used to map remote refs being fetched to remote-tracking refs to store," addressing Junio’s review request. The v5 patch is identical to v4 except for the test file renumbering in Patch 2/4 (no changes to this patch). No substantive objections remain.
2. **Patch 2/4**: Implements dynamic branch enumeration in `git fetch` to fetch only branches tracked by local branches at the remote. Updates `get_ref_map()` to iterate over local branches that track the remote (`branches_tracking_remote()` helper in `remote.c`), passing the inferred branch list to the transport’s `ls-refs` command. The forced inclusion of the remote’s default branch (present in v3) is removed, simplifying the code and resolving Junio’s objection. Tests in `t/t5586-fetch-refmap.sh` (renumbered from `t/t5585-fetch-refmap.sh` in v5) verify dynamic branch selection, edge cases (duplicate branches, branches tracking other remotes), and `git remote show` compatibility with refmap-only remotes. The patch is the technical centerpiece of the series, with no on-disk format changes beyond the new configuration entry introduced in Patch 1/4. The only minor edge case noted is that a bare `git fetch` against a refmap-only remote fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use; Harald Nordgren acknowledges this as a minor quibble and not a blocker.
3. **Patch 3/4**: Adds `git remote add --limited-fetch` to explicitly create a refmap-only remote. The flag writes a single `remote.<name>.refmap` entry (`+refs/heads/*:refs/remotes/<name>/*`) instead of the usual wildcard `remote.<name>.fetch` refspec, opting the remote into the matching-inspired fetch mode. Updates `builtin/remote.c` and `Documentation/git-remote.adoc`, and adds tests in `t/t5505-remote.sh` to verify the flag works in non-shallow repositories and correctly rejects incompatible combinations (`-t/--track` or `--mirror`). The implementation is clean, with no substantive objections raised in prior iterations. The flag is a user-facing opt-in for the new mode, though Patch 4/4 will make it the default in shallow repositories.
4. **Patch 4/4**: Makes `git remote add` default to `--limited-fetch` in shallow repositories. Modifies `builtin/remote.c` to check `is_repository_shallow()` and enables `--limited-fetch` by default unless `--no-limited-fetch`, `-t/--track`, or `--mirror` is specified. Documentation and tests (`t/t5505-remote.sh`) cover the new behavior and edge cases (explicit `-t` in shallow repos, wildcard refspecs in full repos, shallow default, and `--no-limited-fetch` override). The patch is technically identical to the v4 version, with no changes beyond the test renumbering in Patch 2/4.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. This is the consensus-approved design.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`). The forced inclusion of the remote’s default branch (present in v3) is removed.
- **Files touched**:
  - `remote.c`/`remote.h`: Implement `remote.<name>.refmap` parsing (Patch 1/4) and dynamic branch enumeration logic (Patch 2/4, including `branches_tracking_remote()` helper).
  - `builtin/fetch.c`: Integrate the new fetch logic with the refmap configuration (Patch 1/4 updates `--refmap` default behavior; Patch 2/4 adds dynamic branch enumeration via `get_ref_map()`).
  - `builtin/remote.c`: Add `--limited-fetch` flag to `git remote add` (Patch 3/4) and default it in shallow repositories (Patch 4/4).
  - `Documentation/config/remote.txt`, `Documentation/git-fetch.adoc`, and `Documentation/git-remote.adoc`: Document `remote.<name>.refmap` (Patch 1/4), the matching-inspired fetch mode (Patch 2/4), the `--limited-fetch` flag (Patch 3/4), and the shallow-repository default (Patch 4/4).
  - `t/t5510-fetch.sh`: Test `remote.<name>.refmap` configuration (Patch 1/4).
  - `t/t5586-fetch-refmap.sh`: New tests covering refmap configuration, dynamic branch enumeration, and edge cases (stale `HEAD`, empty repositories, multiple tracking branches, duplicate branches, branches tracking other remotes).
  - `t/t5505-remote.sh`: Tests for the `--limited-fetch` flag (Patch 3/4) and shallow-repository default (Patch 4/4).
- **Behavior**:
  - The remote’s default branch is no longer fetched by default (resolving Junio’s objection).
  - Non-shallow repositories continue using wildcard refspecs by default (backward compatibility preserved).
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories default to it.
  - No on-disk format changes beyond the new configuration entry in `.git/config`.

Open questions and loose ends
1. **Edge-case handling**:
   - Should the matching-inspired mode be available outside of shallow repositories, or is it strictly a shallow-repository optimization? (No new input in v5.)
   - How should the implementation handle remotes with no default branch (e.g., empty repositories)? The current implementation falls back to the inferred branch list, but this may not always be correct. (No resolution in v5.)
   - Should existing shallow repositories with wildcard refspecs be migrated automatically, or should users opt in via configuration? (No new input in v5.)
   - Should there be a warning for users who might rely on the old behavior? (No new input in v5.)
   - A bare `git fetch` against a refmap-only remote (no `remote.<name>.fetch` refspec) fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use. Harald Nordgren acknowledges this as a minor quibble and not a blocker, but flags it for potential future discussion.
2. **Backward compatibility**:
   - The v5 series preserves backward compatibility for non-shallow repositories but does not address migration of existing shallow repositories. No objections have been raised yet, but this may require follow-up discussion or patches.

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using `remote.<name>.refmap` to separate namespace mappings from fetch selection logic.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. The configuration knob is added in Patch 1/5, mirroring `remote.<name>.fetch` but only providing a default for `--refmap` when there is something explicit to fetch (command-line refspecs or `remote.<name>.fetch`). If both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, the former takes precedence.
- **Proposed alternative**: `remote.<name>.fetchRefs` (Phillip Wood’s proposal) would explicitly specify which refs to fetch (e.g., `*@{upstream}`), decoupling the "what" from the "where". This would resolve the refspec-matching order inconsistency (first-match vs. last-one-wins) and enable per-branch overrides.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`). The `branches_tracking_remote()` helper in `remote.c` implements this logic, iterating over all local branches and collecting the source ref for each branch whose `remote_name` matches the target remote. The `get_ref_map()` function in `builtin/fetch.c` integrates this logic, constructing a dynamic refspec from the inferred branches. The `do_fetch()` function populates `transport_ls_refs_options.ref_prefixes` with the inferred branches to limit the transport layer’s ref requests. The existing "fetch branches merged into the current branch" logic is extracted into a shared helper (`collect_upstream_from_remote`, introduced in Patch 2/5) to reduce duplication. The helper takes a `struct repository *`, a `strvec` to populate, a `const struct remote *`, and an optional branch name (NULL means the current branch), and adds the upstream refs of any matching branches to the list. Junio’s review requirements are fully addressed: (1) the `if/else if/else` control-flow reorganization is in Patch 3/5, and (2) the NULL-check for `branch` is preserved in `collect_upstream_from_remote()` via `repo_branch_get(repo, refname)`.
- **Precedence rule**: When both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, `remote.<name>.fetch` takes precedence, and the `refmap` setting is ignored. This resolves the fatal error ("--refmap option is only meaningful with command-line refspec") and is uncontroversial. Junio’s example in the latest email illustrates this rule: `remote.cabal.fetch` limits what is fetched, while `remote.cabal.refmap` only maps the fetched refs to the desired namespace.
- **`--limited-fetch` flag**: Added in Patch 4/5 to `git remote add`, this flag configures the remote to use `remote.<name>.refmap` (e.g., `+refs/heads/*:refs/remotes/<name>/*`) instead of the traditional wildcard `remote.<name>.fetch` refspec. **Patch 5/5 makes `--limited-fetch` the default when adding a remote in a shallow repository by checking `is_repository_shallow(the_repository)` when `limited_fetch` is unset, defaulting to `--limited-fetch` unless `--no-limited-fetch` is given.** The flag is rejected when combined with `-t/--track` or `--mirror`, as those options already specify explicit fetch behavior. The implementation updates `builtin/remote.c` to set the refmap configuration via `repo_config_set()` and adds documentation to `git-remote.adoc`. Eight new tests in `t/t5505-remote.sh` verify the flag’s behavior, conflict with `-t`, absence of interference with existing functionality, the new default behavior in shallow repositories, and its override with `--no-limited-fetch`.
- **Shallow-repository default**: The shallow check uses the existing `is_repository_shallow()` helper, and the logic reuses the existing `limited_fetch` machinery. The documentation in `git-remote.adoc` is updated to explain the new default behavior, clarifying that it applies to all shallow repositories, not just single-branch shallow clones. The commit message clarifies that the default applies to all shallow repositories, not just single-branch shallow clones.
- **Fallback logic in `remote_find_tracking()`**: Patch 1/5 modifies `remote_find_tracking()` in `remote.c` to fall back to `remote->refmap` **only when `remote->fetch` is either empty or contains no matching refspec for the given query**. This ensures the function treats `remote->refmap` as a superset of `remote->fetch` while avoiding unintended side effects (e.g., for `--delete-merged`). The change replaces the original two-branch `if/else` with a single condition that checks both the presence of `remote->fetch` refspecs and the success of `refspec_find_match()`. Two new tests verify: (1) refs fetched via refmap are correctly tracked (e.g., for `@{upstream}`), and (2) negative refspecs in `remote.<name>.fetch` continue to exclude refs as expected.
- **Code deduplication**: The duplicate code in `do_fetch()` where the `follow_remote_head` logic and `collect_upstream_from_remote()` call appear in two nearly identical blocks is now refactored. Patch 2/5 extracts the "fetch branches merged into the current branch" logic into the shared `collect_upstream_from_remote()` helper, which is immediately reused in `do_fetch()` to replace the inlined code. The helper is designed for reuse in Patch 3/5’s dynamic branch enumeration logic.
- **Files touched**:
  - `remote.c`/`remote.h`: Implement `remote.<name>.refmap` parsing (Patch 1/5) and dynamic branch enumeration logic (Patch 3/5, including `branches_tracking_remote()` helper). Patch 2/5 extracts the existing "fetch branches merged into the current branch" logic into the shared `collect_upstream_from_remote()` helper, which takes a `struct repository *`, a `strvec` to populate, a `const struct remote *`, and an optional branch name (NULL means the current branch). The NULL-check for `branch` is preserved via `repo_branch_get(repo, refname)`. Patch 1/5 also updates `remote_find_tracking()` to implement the corrected fallback logic.
  - `builtin/fetch.c`: Integrate the new fetch logic with the refmap configuration (Patch 1/5 updates `--refmap` default behavior; Patch 3/5 adds dynamic branch enumeration via `get_ref_map()`). The redundant code blocks in `do_fetch()` are now deduplicated.
  - `builtin/remote.c`: Add `--limited-fetch` flag to `git remote add` (Patch 4/5) and default it in shallow repositories (Patch 5/5). `use_limited_fetch` is now a `bool`.
  - Documentation: `Documentation/config/remote.txt`, `Documentation/git-fetch.adoc`, `Documentation/git-remote.adoc`, `Documentation/config/remote.adoc`, and `fetch-options.adoc` (updated to document the new default behavior for shallow repositories, the `--limited-fetch` flag, the dynamic branch inference logic, and the precise behavior of refmap-based fetching).
  - Tests: `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh`, and `t/t5505-remote.sh` (20 new tests covering edge cases, backward compatibility, refmap tracking, negative refspec exclusion, the `--limited-fetch` flag, and the new default behavior in shallow repositories).
- **Behavior**:
  - The remote’s default branch is no longer fetched by default.
  - Non-shallow repositories continue using wildcard refspecs by default.
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories now default to it.
  - No on-disk format changes beyond the new configuration entries in `.git/config`.
  - Edge case: A bare `git fetch` against a refmap-only remote with no tracked branches fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use.
- **New symbols**: `remote.<name>.refmap` (config key), `remote->refmap` (struct field), `branches_tracking_remote()` (helper function), `collect_upstream_from_remote()` (helper function), `--limited-fetch` (CLI flag), `--no-limited-fetch` (CLI flag), `is_repository_shallow()`, `remote.<name>.fetchRefs` (proposed config key).

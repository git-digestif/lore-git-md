Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using configuration to separate namespace mappings from fetch selection logic. **The design direction has shifted: the current `remote.<name>.refmap` overloading is acknowledged as flawed, and the series will be revised to introduce a dedicated `remote.<name>.fetchRefs` config key to decouple the "what" (which refs to fetch) from the "where" (where to store them).**

Key technical details
- **Current design (v11, now deprecated)**:
  - `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) and, when no `remote.<name>.fetch` is configured, implicitly controls which refs are fetched by enumerating branches tracked by local branches at the remote.
  - Precedence: `remote.<name>.fetch` > `remote.<name>.refmap`.
  - **Flaw**: Overloading `refmap` for both namespace mapping and fetch selection limits extensibility and repeats the inflexibility the series aims to fix. The maintainer’s email confirms this design correctly handles edge cases (e.g., `remote.<name>.fetch` + `remote.<name>.refmap`) but does not resolve the broader inflexibility.

- **Proposed design (v12)**:
  - **New config key**: `remote.<name>.fetchRefs` explicitly specifies which refs to fetch (e.g., `*@{upstream}`), decoupling the "what" from the "where".
  - **Refmap role**: `remote.<name>.refmap` reverts to its original purpose: namespace mapping only (e.g., `+refs/heads/*:refs/remotes/second/*`).
  - **Precedence**: `remote.<name>.fetch` > `remote.<name>.fetchRefs` > dynamic branch enumeration (if neither is configured).
  - **Forced updates (`+`)**: Belong on the refmap side (the "where"), not the fetchRefs side (the "what"), since forced updates only make sense when storing refs.
  - **Refspec-matching order**: The new design resolves the inconsistency (first-match vs. last-one-wins) by decoupling the "what" and "where".

- **Dynamic branch selection**:
  - When no explicit refspec or `fetchRefs` is given, `git fetch` enumerates branches tracked by local branches at the remote via `@{upstream}`.
  - The `branches_tracking_remote()` helper implements this logic; `get_ref_map()` integrates it.
  - **v12 change**: This logic will now trigger only when neither `remote.<name>.fetch` nor `remote.<name>.fetchRefs` is configured.

- **`--limited-fetch` flag**:
  - Added to `git remote add` (Patch 4/5), configures `remote.<name>.refmap` in v11.
  - **v12 change**: Will configure `remote.<name>.fetchRefs` instead (e.g., `*@{upstream}`), while `remote.<name>.refmap` handles namespace mapping.

- **Shallow-repository default**:
  - Patch 5/5 makes `--limited-fetch` the default in shallow repositories by checking `is_repository_shallow(the_repository)`.
  - **v12 change**: The default will use `remote.<name>.fetchRefs = *@{upstream}` instead of overloading `refmap`.

- **Fallback logic**:
  - `remote_find_tracking()` falls back to `remote->refmap` only when `remote->fetch` is empty or contains no matching refspec.
  - **v12 change**: Will fall back to `remote->fetchRefs` (if configured) before dynamic branch enumeration.

- **Files touched (v11)**:
  - `remote.c`/`remote.h`: `remote.<name>.refmap` parsing, `branches_tracking_remote()`, `collect_upstream_from_remote()` helper.
  - `builtin/fetch.c`: Integration with refmap configuration and dynamic branch enumeration.
  - `builtin/remote.c`: `--limited-fetch` flag and shallow-repository default.
  - Documentation: `remote.txt`, `git-fetch.adoc`, `git-remote.adoc`, `fetch-options.adoc`.
  - Tests: `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh`, `t/t5505-remote.sh` (20 new tests).
  - **v12 changes**: `remote.c`/`remote.h` will add `remote.<name>.fetchRefs` parsing, adjust precedence rules, and rework `branches_tracking_remote()` to integrate with the new config key. Documentation and tests will be updated to reflect the new design.

- **Behavior (v11)**:
  - Remote’s default branch is no longer fetched by default.
  - Non-shallow repositories continue using wildcard refspecs by default.
  - New mode enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - No on-disk format changes beyond new configuration entries.
  - **v12 behavior**:
    - New mode enabled when `remote.<name>.fetchRefs` is configured (e.g., `*@{upstream}`).
    - `remote.<name>.refmap` handles namespace mapping only.
    - Precedence: `remote.<name>.fetch` > `remote.<name>.fetchRefs` > dynamic branch enumeration.

- **New symbols (v11)**:
  - `remote.<name>.refmap`, `remote->refmap`, `branches_tracking_remote()`, `collect_upstream_from_remote()`, `--limited-fetch`, `--no-limited-fetch`, `is_repository_shallow()`.
  - **v12 additions**:
    - `remote.<name>.fetchRefs`, `remote->fetchRefs`.

Open questions and loose ends
1. **Design direction (high weight, resolved in principle)**:
   - The maintainer and key reviewer have agreed that the series must adopt `remote.<name>.fetchRefs` to decouple the "what" (which refs to fetch) from the "where" (where to store them). **Implementation details remain open**:
     - How should `remote.<name>.fetchRefs` interact with `remote.<name>.fetch` and `remote.<name>.refmap` in terms of precedence? (Resolved in principle: `fetch` > `fetchRefs` > dynamic branch enumeration.)
     - Should `remote.<name>.fetchRefs` support negation (e.g., `^refs/pull/*`) or other refspec features? (Unresolved.)
     - How should the dynamic branch enumeration logic (`branches_tracking_remote()`) be reworked to integrate with `fetchRefs`? (Unresolved.)
     - Should the `--limited-fetch` flag and shallow-repository default be updated to use `fetchRefs` instead of `refmap`? (Resolved in principle: yes.)

2. **Documentation clarity (medium weight)**:
   - Phillip Wood requests clearer documentation of the interaction between `remote.<name>.fetchRefs`, `remote.<name>.fetch`, and `remote.<name>.refmap`, specifically how precedence works and when dynamic branch enumeration is triggered.
   - The name `remote.<name>.fetchRefs` is now accepted, but its documentation must clearly distinguish it from `refmap`.

3. **Edge-case handling (low weight)**:
   - How should the implementation handle remotes with no default branch?
   - Should existing shallow repositories with wildcard refspecs be migrated automatically to `fetchRefs`?
   - Should there be a warning for users relying on the old behavior?
   These remain open but are not blockers for v12.

4. **Implementation timeline (medium weight)**:
   - No timeline has been given for v12, but the maintainer’s endorsement of the new design suggests it will be prioritized. Harald Nordgren has not yet responded to the design discussion or committed to implementing v12.

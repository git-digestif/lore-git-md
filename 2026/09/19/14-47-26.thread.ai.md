Subject: [PATCH] fetch: introduce `fetch.shallow` config to restrict refspec-less fetches to current branch
Series version: v1 (initial submission; discussion now exploring alternative solution)
Originating author: Harald Nordgren
Thread type: patch series (single patch, now under design reconsideration)

Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The original patch proposed a new `fetch.shallow` configuration option to restrict such fetches to the current branch’s upstream. However, the discussion has now shifted to whether the root cause lies in `git remote add` defaulting to a wildcard fetch refspec in shallow repositories, and whether improving that behavior would be a more targeted solution.

Current status
Under review (initial submission). No code changes requested yet. The thread is pivoting toward exploring an alternative solution: modifying `git remote add` to avoid wildcard refspecs in shallow repositories and instead fetch only the relevant branch(es). No merge status reported.

Key technical details
- Files touched in original patch: `builtin/fetch.c`, `Documentation/config/fetch.adoc`, `t/t5537-fetch-shallow.sh` (new test section)
- Proposed new config key: `fetch.shallow` (boolean, default `false`)
- Behavior of original patch: when `fetch.shallow=true` and the repository is shallow, a refspec-less fetch would only fetch the current branch’s upstream
- Test coverage in original patch: verifies narrowing to tracked branch, correct update of `refs/remotes/<name>/HEAD`, no effect on non-shallow repositories or non-tracked remotes, and edge cases (stale `HEAD`, `fetch.followRemoteHEAD` interaction)
- No new CLI options, symbols, or on-disk format changes in original patch
- Alternative solution now under discussion: modifying `git remote add` to avoid wildcard refspecs in shallow repositories, potentially eliminating the need for `fetch.shallow`

Open questions and loose ends
1. **Design direction**: The thread is now focused on whether the original `fetch.shallow` config is the best solution, or whether improving `git remote add` behavior in shallow repositories (e.g., avoiding wildcard refspecs) would be more targeted and maintainable.
2. **Scope of the performance issue**: Confirmed that the problem is not specific to sparse checkouts but affects any shallow repository with many remote-tracking branches (e.g., after adding a second remote with a wildcard fetch refspec).
3. **Implementation of alternative solution**: If the thread converges on modifying `git remote add`, the following questions arise:
   - Should `git remote add` detect shallow repositories and default to a narrower refspec (e.g., `+refs/heads/<default-branch>:refs/remotes/<name>/<default-branch>`)?
   - Should this behavior be configurable (e.g., via a new config option like `remote.addShallowRefspec`)?
   - How should this interact with existing remotes or manual refspec edits?
4. **Backwards compatibility**: Any change to `git remote add` behavior must preserve existing workflows for non-shallow repositories.
5. **No code changes requested yet**: The original patch remains unmodified, and no new patch has been proposed for the alternative solution.

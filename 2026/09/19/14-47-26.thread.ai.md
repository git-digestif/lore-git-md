Core problem or goal
Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The thread implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using `remote.<name>.refmap` to separate namespace mappings from fetch selection logic.

Key technical details
- **New configuration**: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. This design remains consensus-approved.
- **Dynamic branch selection**: When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote (via `@{upstream}`). The forced inclusion of the remote’s default branch (present in v3) is removed. The `branches_tracking_remote()` helper in `remote.c` implements this logic, and `get_ref_map()` in `builtin/fetch.c` integrates it.
- **Files touched**:
  - `remote.c`/`remote.h`: Implement `remote.<name>.refmap` parsing (Patch 1/4) and dynamic branch enumeration logic (Patch 2/4, including `branches_tracking_remote()` helper).
  - `builtin/fetch.c`: Integrate the new fetch logic with the refmap configuration (Patch 1/4 updates `--refmap` default behavior; Patch 2/4 adds dynamic branch enumeration via `get_ref_map()`).
  - `builtin/remote.c`: Add `--limited-fetch` flag to `git remote add` (Patch 3/4) and default it in shallow repositories (Patch 4/4).
  - Documentation: `Documentation/config/remote.txt`, `Documentation/git-fetch.adoc`, and `Documentation/git-remote.adoc`.
  - Tests: `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh` (new in v5), and `t/t5505-remote.sh`.
- **Behavior**:
  - The remote’s default branch is no longer fetched by default.
  - Non-shallow repositories continue using wildcard refspecs by default.
  - The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.
  - The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories default to it.
  - No on-disk format changes beyond the new configuration entry in `.git/config`.
- **New design proposal**: When both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, `remote.<name>.fetch` takes precedence, and the `refmap` setting is ignored. This resolves the fatal error ("--refmap option is only meaningful with command-line refspec") by treating the `fetch` refspec as the authoritative source of truth.

Open questions and loose ends
1. **Edge-case handling** (carried over from prior summary):
   - Should the matching-inspired mode be available outside of shallow repositories?
   - How should the implementation handle remotes with no default branch?
   - Should existing shallow repositories with wildcard refspecs be migrated automatically?
   - Should there be a warning for users who might rely on the old behavior?
   - A bare `git fetch` against a refmap-only remote fetches no branches, leaving no remote-tracking refs for `git branch --set-upstream-to` to use.

   - The v6 series preserves backward compatibility for non-shallow repositories but does not address migration of existing shallow repositories.

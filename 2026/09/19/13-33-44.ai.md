This is a bug report about the `reference-transaction` hook in Git, specifically targeting how branch renames (`git branch -m`) are reported. The author, Maciej Ciemborowicz, demonstrates that when renaming a branch, the hook only reports the deletion of the old branch name but not the creation of the new one. This affects both the traditional files-based ref backend and the newer reftable backend, though the reftable backend fails more severely by not reporting any usable rename payload. The expected behavior—confirmed by `git update-ref --stdin`—is that both the deletion of the old ref and the creation of the new ref should be included in the transaction.

The report includes a minimal reproducer script that initializes a repository, sets up the hook, and logs the transaction output. The script is parameterized to test both ref backends and shows that the issue persists across Git versions 2.28 through 2.55. The author also links to a compatibility test suite in their `git-hooks-ext` project, reinforcing that this is a long-standing issue. The commit message does not propose a fix but clearly documents the discrepancy between the observed and expected behavior, making it a well-motivated bug report.

This is likely to attract attention from contributors working on ref backends (e.g., Patrick Steinhardt, Karthik Nayak) or hook infrastructure (e.g., Adrian Ratiu). The issue is straightforward to reproduce and affects a core Git operation, so it may see quick follow-up. The report is concise, technically precise, and avoids speculation about the root cause, which should help reviewers focus on the fix rather than debating the problem. Expect discussion about whether the fix belongs in the branch-rename logic, the ref backend layer, or the hook invocation code.

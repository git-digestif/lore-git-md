Harald Nordgren’s patch series introducing `remote.<name>.fetchRefmap` for a "matching-inspired" fetch mode in shallow repositories has reached its **v13 revision**, marking the implementation as complete and ready for final review before merging to `master`. The series addresses a long-standing performance issue where a refspec-less `git fetch` in shallow repositories negotiates history for all remote branches, causing slowdowns or hangs. The solution dynamically fetches only branches tracked by local branches at the remote, using the new `fetchRefmap` config key to separate "what to fetch" from "where to store it."

The design is now finalized and endorsed by Junio C Hamano and Phillip Wood, with all major technical questions resolved. Key improvements in v13 include a fix for `@{push}` resolution when `fetchRefmap` is configured and a regression test confirming the current dual-storage behavior for colon-separated `remote.<name>.fetch` entries. The series is thoroughly tested (593 lines of new tests) and documented, covering edge cases like forced updates, precedence rules, and dynamic branch enumeration.

The **only remaining open question** is the override semantics for command-line refspecs and colon-separated `remote.<name>.fetch` entries. The discussion has converged toward override semantics, where such refspecs replace rather than coexist with `fetchRefmap`, aligning with Phillip Wood’s preference. The v13 test case preserves the current dual-storage behavior, but this is expected to be updated in v14 to match the chosen model. The series is otherwise ready for graduation, with no known blockers, and is expected to merge in the current cycle once this edge case is resolved. Reviewers are encouraged to focus on the override semantics discussion and edge-case handling in the test suite.

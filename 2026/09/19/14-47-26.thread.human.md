This thread began with Harald Nordgren’s patch to introduce a `fetch.shallow` config option that would restrict refspec-less fetches in shallow repositories to the current branch’s upstream. That proposal was abandoned after Phillip Wood identified the root cause—wildcard fetch refspecs in shallow repositories—and the discussion pivoted to two complementary solutions: (1) making `git remote add` default to narrower refspecs in shallow repositories, and (2) introducing a new “matching-inspired” fetch mode that dynamically fetches only the remote branches tracked by local branches, plus the remote’s default branch.

The narrower-refspec approach, championed by Phillip Wood, would change `git remote add` in shallow repositories to either refuse to add a remote without explicit branch tracking (unless `--fetch` is given) or to fetch only the remote’s default branch by default. This addresses the initial setup problem but leaves subsequent fetches to the matching-inspired mode. Junio C Hamano proposed the matching-inspired mode, which would inspect local branches’ upstream settings to determine which remote branches to fetch, but requires a one-time “priming” step where the user explicitly fetches the remote’s default branch to establish tracking. Harald Nordgren refined this by ensuring the remote’s default branch is always fetched, even if no local branch tracks it yet.

Ben Knoble recently suggested a small but practical refinement to Junio’s priming mechanism: the initial `git fetch <remote> <branch>` should still create the remote-tracking branch as usual, rather than being a no-op. This would reduce the priming step to a single `git fetch` followed by `git checkout -b -t`, making the setup feel more natural to users. The thread is now converging on a two-part solution—narrower refspecs for `git remote add` and the matching-inspired mode for `git fetch`—with open questions focused on integration details, default behaviors, and edge cases like stale remote `HEAD` information. No code has been written yet, but the design direction is clear and the remaining discussion centers on usability and implementation trade-offs.

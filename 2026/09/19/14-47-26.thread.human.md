This thread began with Harald Nordgren’s patch to introduce a `fetch.shallow` config option, aiming to speed up `git fetch` in shallow repositories by restricting refspec-less fetches to the current branch. That approach was abandoned after Phillip Wood identified the root cause: wildcard fetch refspecs in shallow repositories cause unnecessary negotiation for all remote branches. The discussion has since focused on two complementary solutions: (1) making `git remote add` default to narrower refspecs in shallow repositories, and (2) introducing a matching-inspired fetch mode for `git fetch` that dynamically fetches only branches tracked by local branches, plus the remote’s default branch.

The current debate centers on Junio’s proposal to address the chicken-and-egg problem in the matching-inspired mode. He suggests a priming step where users manually fetch the remote’s default branch once to establish the upstream tracking relationship, after which the mode would work automatically. This would use a special refspec token (`:`) in `git remote add` to create a no-op initial fetch, requiring users to explicitly fetch the desired branch(es) to set up tracking. While this preserves backwards compatibility, it shifts the burden of initial setup to the user and may not fully resolve the performance issue in shallow repositories. Phillip Wood’s narrower-refspec approach for `git remote add` remains the more pragmatic solution for initial setup, but integration details between the two approaches are still unresolved. Key open questions include the refspec syntax, default behavior in shallow repositories, and how to handle edge cases like stale remote `HEAD`. The thread has reached design consensus on the problem but is still refining the solution.

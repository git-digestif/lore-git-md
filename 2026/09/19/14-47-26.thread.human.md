Harald Nordgren's v14 series introduces `remote.<name>.fetchRefmap` to let shallow clones fetch only relevant branches instead of negotiating history for every remote ref. The five-patch series is under final review for `master`, with the design endorsed by Junio C Hamano and Phillip Wood: `fetchRefmap` selects which refs to fetch while the existing `refmap` handles namespace mapping, and command-line refspecs override both configuration keys. The series currently sits in `next` as v11 and blocks Collin's `ch/remote-defer-follow-remote-head-validation` topic due to textual conflicts that patches 1--3 would resolve.

The latest exchange centers on override semantics. Phillip Wood proposed that a command-line refspec with an explicit destination (`src:dst`) should cause both `--refmap` and `fetchRefmap` to be ignored entirely, preventing fetched refs from being stored in two places. Junio C Hamano disagrees, arguing that command-line refspecs already override `remote.<name>.fetch` while `fetchRefmap` merely provides defaults for `--refmap`, so overloading refspec semantics to also kill `fetchRefmap` would be confusingly asymmetric. Instead, he suggests users who want to bypass `fetchRefmap` should use an explicit `--no-refmap` or `--refmap=""` flag.

Two strategic questions remain open alongside this semantics detail. First, whether to merge patches 1--3 now to unblock the dependent topic while deferring the ergonomic additions in patches 4--5, a path Phillip supports. Second, whether the implicit dynamic branch enumeration in patch 3 should remain as a fallback when no refspec is given, or be deferred in favor of explicit `fetchRefmap` configuration only -- a question on which Phillip now agrees with Junio that implicit guessing is problematic. Harald Nordgren is expected to respond to Junio's override semantics counter-proposal and the partial merge suggestion before the series can graduate.

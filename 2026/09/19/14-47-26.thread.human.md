This thread is about a patch series by Harald Nordgren that introduces a new fetch mode for shallow repositories, aiming to speed up `git fetch` by dynamically fetching only the branches tracked by local branches at the remote. The series, now at v11, is queued in `next` and has addressed all prior feedback, including Junio’s review points and D. Ben Knoble’s suggestions for clarity and efficiency. The key change is the addition of `remote.<name>.refmap`, which separates namespace mappings from fetch selection logic, along with a `--limited-fetch` flag for `git remote add` that defaults to this mode in shallow repositories.

The series seemed uncontroversial until Phillip Wood raised a fundamental design objection: overloading `remote.<name>.refmap` to control *both* what to fetch and where to store it repeats the same inflexibility the series aims to fix. He proposes a cleaner alternative, `remote.<name>.fetchRefs`, which would explicitly specify which refs to fetch (e.g., `*@{upstream}`), decoupling the "what" from the "where." This would resolve Git’s current refspec-matching inconsistency (first-match vs. last-one-wins) and enable per-branch overrides. Phillip’s critique is substantive and directly addresses the problem the series sets out to solve, putting the thread at a crossroads. Junio’s latest "What's cooking" report still lists the series in `next`, but Phillip’s review may prompt a redesign before graduation to `master`.

The series is feature-complete, with no on-disk format changes beyond new configuration entries. It introduces no new technical debt and reuses existing logic, but Phillip’s alternative would require significant rework, particularly to the dynamic branch enumeration logic. The only open questions now are whether to proceed with the current design or adopt Phillip’s proposal, and how to handle edge cases like remotes with no default branch.

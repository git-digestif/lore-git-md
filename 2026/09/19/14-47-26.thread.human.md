The v10 patch series introducing `+:` refspec for matching-inspired fetch mode is now complete and ready for Junio to queue in `next`. The series, originally authored by Harald Nordgren, addresses a long-standing pain point for shallow repositories: slow or hanging `git fetch` operations when the remote has many branches. Instead of negotiating history for all remote branches, the new mode dynamically fetches only the branches tracked by local branches at the remote, using a new `remote.<name>.refmap` configuration to separate namespace mappings from fetch selection.

All prior feedback has been addressed, including Junio’s two review points from v8 (control-flow reorganization and NULL-check restoration) and D. Ben Knoble’s suggestions for clarity and efficiency. The latest update—a surgical fix to the first patch—resolves Knoble’s technical concern about the fallback logic in `remote_find_tracking()`. The function now only falls back to `remote->refmap` when `remote->fetch` is either empty or contains no matching refspec, preserving the intended behavior while avoiding unintended side effects. The series also introduces a `--limited-fetch` flag for `git remote add` and makes it the default for shallow repositories, with no disruption to non-shallow repositories.

The implementation is uncontroversial, reuses existing logic, and introduces no new technical debt. The only remaining open questions are minor design choices (e.g., whether the matching-inspired mode should be available outside shallow repositories) and edge-case handling, all of which can be addressed in follow-up work.

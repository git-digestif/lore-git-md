This thread introduces a new "matching-inspired" fetch mode for Git, aimed at solving a long-standing performance issue in shallow repositories. When users clone with `--depth`, a subsequent `git fetch` or `git pull` can hang or slow to a crawl because Git negotiates history for all remote branches by default. Harald Nordgren’s four-patch v3 series implements Junio’s `remote.<name>.refmap` design, which separates the "where to store" logic from the "what to fetch" logic, enabling a dynamic fetch of only the branches tracked by local branches at the remote—plus the remote’s default branch.

The first three patches laid the groundwork: Patch 1 added the `remote.<name>.refmap` configuration, Patch 2 implemented the dynamic branch enumeration logic, and Patch 3 introduced `git remote add --limited-fetch` to explicitly opt into the new mode. The just-arrived fourth patch completes the series by making `--limited-fetch` the default when adding a remote to a shallow repository. This ensures that shallow clones remain shallow without requiring manual configuration, addressing the original performance pitfall directly.

The design discussion is now closed, and the focus has shifted to implementation details—edge-case handling, backward compatibility, and configuration syntax. Junio and Phillip Wood have been the key voices shaping the design, while D. Ben Knoble helped clarify semantics. The series is still under active review, with no merge status yet, but the final patch is uncontroversial and aligns cleanly with the rest of the work. Open questions remain about whether the new mode should be available outside shallow repositories and how to handle edge cases like empty remotes, but these are minor compared to the core improvement.

Here’s the updated **human-mode** summary for a developer catching up on the thread:

---

This thread implements a long-awaited improvement to `git fetch` for shallow repositories, where fetching from remotes with many branches can be painfully slow or hang entirely. The v12 series (5 patches) introduces a "matching-inspired" mode that dynamically fetches only the branches tracked by local branches at the remote, using a new config key `remote.<name>.fetchRefmap` to separate *what* to fetch from *where* to store it. The design is finalized and endorsed by Junio and Phillip Wood, with the series currently queued in `next` (as v11) but deprecated in favor of v12, which is under active review for merging to `master`.

The core change resolves a long-standing usability issue: shallow clones (created with `git clone --depth`) previously negotiated history for all remote branches when no refspec was given, leading to performance problems. The new mode defaults to fetching only tracked branches (`*@{upstream}`) in shallow repos, while preserving backwards compatibility—older Git versions will safely ignore `fetchRefmap` rather than misinterpreting it. The series also adds a `--limited-fetch` flag to `git remote add` for explicit configuration and clarifies precedence rules: `remote.<name>.fetch` takes priority over `fetchRefmap`, which in turn beats dynamic branch enumeration.

Two open questions remain before graduation. First, Phillip Wood raised an edge case about how to handle colon-separated `remote.<name>.fetch` entries (e.g., `+refs/heads/master:refs/remotes/cabal/master`) when `refmap` is also configured. Junio’s latest reply suggests the command-line precedent (dual storage) might apply, but no decision has been made—options include silently ignoring such entries, erroring out, or storing the ref in both destinations. Second, the documentation needs clearer warnings about the minor inconvenience of forced-update placement (`+` on the refmap side) and backwards-compatibility risks. Neither issue is a blocker, and the series is expected to graduate in the current cycle once resolved.

Key participants include Harald Nordgren (author), Junio (maintainer, who finalized the design), and Phillip Wood (who objected to the v11 design and proposed the cleaner v12 approach). D. Ben Knoble provided minor feedback on commit messages, but no substantive objections remain. The implementation is complete, thoroughly tested, and touches `remote.c`, `builtin/fetch.c`, and documentation. The only unresolved technical detail is how to handle the edge case with mixed legacy/new configurations—a decision that will affect users migrating from older setups but won’t delay the merge.

This thread is about a patch series by Harald Nordgren that introduces a "matching-inspired" fetch mode to improve performance for shallow repositories. The series is now at version 8 (5 patches) and aims to solve the problem of slow or hanging `git fetch` operations in shallow clones when the remote has many branches. Instead of negotiating history for all remote branches, the new mode dynamically fetches only the branches tracked by local branches at the remote being fetched, using a new `remote.<name>.refmap` configuration.

The series is under active review and all of Junio’s prior concerns have been addressed, including fixing hardcoded `the_repository` usage, resolving a regression where the current branch’s `@{upstream}` could be dropped, and fixing a potential duplicate fetch. The latest patch (5/5) makes `--limited-fetch` the default when adding a remote to a shallow repository, ensuring the new behavior is opt-out rather than opt-in for these users. This change is uncontroversial and well-tested, with four new tests covering edge cases and backward compatibility. The series is technically sound and ready for Junio’s re-review, after which it is likely to be merged to `next`.

Key participants include Harald Nordgren (the author), Junio C Hamano (the maintainer, who proposed the `remote.<name>.refmap` design and reviewed earlier versions), and Phillip Wood (who provided design-level feedback in prior iterations). The series has no unresolved technical issues or dependencies, and the only open questions are minor design choices that can be addressed in follow-up work. The new mode is implicitly enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`, and the `--limited-fetch` flag for `git remote add` provides an explicit way to opt into it. Non-shallow repositories continue using wildcard refspecs by default, preserving backward compatibility.

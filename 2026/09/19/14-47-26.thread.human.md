This thread introduces a "matching-inspired" fetch mode to solve a long-standing performance problem in shallow repositories: when users run `git fetch` without specifying a refspec, Git negotiates history for *all* remote branches, which can be slow or even hang when the remote has many branches. The v6 patch series, now complete, implements this by dynamically fetching only the branches tracked by local branches at the remote being fetched.

The key change is the introduction of `remote.<name>.refmap`, a new configuration that separates namespace mappings from fetch selection logic. When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` now enumerates only the branches tracked by local branches (via `@{upstream}`). The `--limited-fetch` flag for `git remote add` opts into this mode, and the final patch in the series makes it the default for shallow repositories—addressing the original problem without breaking backward compatibility for non-shallow repositories.

Junio C Hamano, the maintainer, has stated he will queue the series ("Will replace"), though it hasn’t yet been merged into any integration branch. The design has converged after several iterations: earlier versions included the remote’s default branch by default, but Junio objected, and that behavior was removed in v4. The only remaining loose ends are minor edge cases—such as how to handle remotes with no default branch or whether existing shallow repositories should be migrated automatically—but none are considered blockers. The series is now technically complete, with all four patches ready for integration.

This thread introduces a "matching-inspired" fetch mode to improve performance for shallow repositories by avoiding the negotiation of history for all remote branches during `git fetch`. The v4 patch series, authored by Harald Nordgren, is now technically complete and addresses all prior feedback. The key change in this version is the removal of the forced inclusion of the remote’s default branch, which resolved Junio Hamano’s substantive objection from v3.

The series consists of four patches. The first introduces `remote.<name>.refmap` configuration to separate namespace mappings from fetch selection logic, while the second implements dynamic branch enumeration to fetch only branches tracked by local branches at the remote. The third patch, which is the focus of this latest update, adds a `--limited-fetch` flag to `git remote add`, allowing users to explicitly opt into the new fetch mode by configuring the remote with a refmap instead of a wildcard refspec. The fourth patch makes this flag the default for shallow repositories, ensuring that adding a remote to a shallow clone doesn’t trigger a full fetch of all remote branches.

Junio Hamano, the maintainer, has reviewed the first two patches and approved the design and implementation, though he requested a documentation wording change that was addressed in v4. Phillip Wood and D. Ben Knoble have also participated in the design discussion, with Phillip proposing an alternative approach in earlier versions and D. Ben Knoble endorsing the current design. The series remains under active review, with no merge status yet, and no substantive objections have been raised to the latest iteration. The implementation preserves backward compatibility for non-shallow repositories but leaves open questions about edge-case handling, such as whether the new mode should be available outside shallow repositories or how to handle remotes without a default branch.

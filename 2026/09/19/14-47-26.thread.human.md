This thread implements a "matching-inspired" fetch mode for shallow repositories, where `git fetch` dynamically fetches only the branches tracked by local branches at the remote being fetched. The goal is to avoid slow or hanging fetches in shallow clones when the remote has many branches. Harald Nordgren’s v7 series introduces a new `remote.<name>.refmap` configuration to separate namespace mappings from fetch selection logic, along with a `--limited-fetch` flag for `git remote add` and a default opt-in for shallow repositories.

The series is under active review but stalled by two issues: a textual conflict with Collin’s `ch/fetch-followremotehead-lazy-validation` topic in Junio’s `seen` branch (causing test failures in `t5505` and `t5586`), and an unresolved design question about whether `remote.<name>.fetch` should take precedence when both it and `remote.<name>.refmap` are configured. Junio’s latest review also flagged code structure improvements (refactoring shared logic into a helper) and a potential duplicate fetch when the current branch’s `@{upstream}` is inferred by the new logic. Harald has agreed to address the documentation and refactoring suggestions but hasn’t yet resolved the duplicate fetch or precedence rule.

The uncontroversial parts—like defaulting `--limited-fetch` for shallow repositories—are ready to queue once the series is approved, but the immediate blocker is the integration conflict with Collin’s topic.

The `fetch: introduce +: refspec for matching-inspired fetch mode` thread has reached a critical juncture. Originally proposed by Harald Nordgren and now in its 11th iteration, the series aims to solve a long-standing performance issue in shallow repositories: when users run `git fetch` without explicit refspecs, Git negotiates history for *all* remote branches, which can be slow or even hang when the remote has many branches. The solution introduces a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote, controlled by a new `remote.<name>.refmap` configuration.

The series has been uncontroversial until now. Junio C Hamano, the maintainer, has queued it in `next` as of the 2026-05-15 "What's cooking" report, and all prior feedback—including Junio’s control-flow and NULL-check requirements, D. Ben Knoble’s clarity and efficiency suggestions, and the resolution of a merge conflict with Collin’s `ch/fetch-followremotehead-lazy-validation` topic—has been addressed. The latest version (v11) adds a `--limited-fetch` flag to `git remote add`, which configures the remote to use `remote.<name>.refmap` instead of the traditional wildcard `remote.<name>.fetch` refspec, and makes this flag the default when adding a remote in a shallow repository. The implementation is feature-complete, with 20 new tests covering edge cases, backward compatibility, and the new default behavior.

However, Phillip Wood’s latest review raises a fundamental design objection. He argues that overloading `remote.<name>.refmap` to control *both* ref-namespace mapping *and* which refs are fetched repeats the same inflexibility the series aims to fix. Instead, he proposes a new `remote.<name>.fetchRefs` config key that would explicitly specify which refs to fetch (e.g., `*@{upstream}` to fetch only the upstream branches of local branches on the remote), decoupling the "what" from the "where." His critique also highlights a technical inconsistency in Git’s current refspec-matching logic: it uses the *first* matching refspec rather than the *last*, which contradicts the usual "last-one-wins" config behavior and makes per-branch overrides impossible. This is not a surface-level nit but a credible alternative that could require a redesign.

The thread is now at a crossroads. Junio’s blessing and the series’ current status in `next` suggest it is on track for merging, but Phillip’s objection introduces a plausible alternative that could improve long-term flexibility. The discussion has shifted from implementation details to the right long-term architecture. What remains open is whether the current design will proceed as-is (with Phillip’s objection noted but not addressed) or whether the series will be revised to adopt `remote.<name>.fetchRefs` and fix the refspec-matching order. Harald Nordgren, as the author, will need to respond to Phillip’s critique, and Junio’s next "What's cooking" report may clarify whether the series will be held for further discussion or proceed to `master`.

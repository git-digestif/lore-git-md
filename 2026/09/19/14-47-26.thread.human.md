This thread is about a long-running patch series (v12) by Harald Nordgren that introduces a new `remote.<name>.fetchRefmap` configuration to make `git fetch` faster in shallow repositories by dynamically fetching only branches tracked by local branches. The design is now finalized and endorsed by Junio Hamano and Phillip Wood, with the series queued in `next` and expected to graduate to `master` soon.

The key unresolved issue is how `remote.<name>.fetchRefmap` should interact with existing colon-separated `remote.<name>.fetch` entries. Junio initially suggested mirroring the command-line behavior (dual storage, where the ref is stored in both locations), but Phillip Wood now argues that command-line refspecs—or their config-based equivalents—should *override* the refmap entirely, not coexist with it. This would mean that if a user has both `remote.<name>.fetchRefmap` and a colon-separated `remote.<name>.fetch` entry, only the latter’s destination would be updated. Phillip’s preference for this model is likely to prevail, as it preserves backwards compatibility while clarifying precedence.

The series is otherwise complete, with all major design questions resolved. The remaining work is to update the precedence logic in `remote.c` and document the new behavior clearly, particularly the override semantics and backwards-compatibility considerations. Harald will need to revise the documentation and tests to reflect this change before the series can graduate. The discussion is now focused on this single edge case, and once resolved, the series should be ready for merging.

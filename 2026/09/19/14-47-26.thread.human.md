Harald Nordgren’s thirteen-patch series to introduce a matching-inspired fetch mode for shallow repositories is now in its final review phase, with a realistic chance of merging in the current cycle—but not without addressing a few remaining high-weight issues. The series aims to solve a long-standing performance problem: shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The solution decouples "which refs to fetch" from "where to store them" using a new `remote.<name>.fetchRefmap` configuration key, and defaults to fetching only branches tracked by local branches when no explicit refspec is given.

The v13 revision is complete and under active review, but four key issues are blocking graduation to `master`. First, Phillip Wood has proposed an architectural reconsideration: eliminate the dynamic branch enumeration logic (Patch 3/6) and rely instead on default configuration values for `remote.<name>.fetch` and `remote.<name>.fetchRefmap`. This would simplify the code but require users to explicitly configure the current default behavior, which may be less ergonomic. The proposal directly contradicts the thread’s earlier consensus, but new context from Matt Hunter weakens the objection: Patch 3/6 is required to resolve textual conflicts with Collin’s dependent topic (`ch/remote-defer-follow-remote-head-validation`), making its removal counterproductive. Second, the thread has converged toward override semantics, where command-line refspecs (or colon-separated `remote.<name>.fetch` entries) override `remote.<name>.fetchRefmap` entirely, not coexist with it. The v13 implementation preserves the current dual-storage behavior, but this is now confirmed as incorrect and must be updated in v14. Third, Phillip and Junio have both criticized the cover letter as inadequate for a complex six-patch series, demanding a patch-by-patch summary and design context. Finally, D. Ben Knoble’s latest review raises a previously unnoticed interaction between override semantics and `@{push}` resolution, which may require additional implementation or documentation.

The series is queued in `next` (as v11) but deprecated in favor of v13. Junio has signaled that the series is prioritized for merging due to its blocking status for Collin’s topic, but the cover letter revision is now a hard requirement. The new strategic context—merging only Patches 1–3 would resolve the dependent topic’s conflicts—makes a partial merge viable, and this option is gaining traction as a pragmatic path forward if the architectural objection or override semantics edge case proves intractable. Harald is expected to post a v14 revision addressing the override semantics, cover letter documentation, and `@{push}` interaction, with the architectural reconsideration likely resolved in favor of the current design (given its strategic importance for unblocking the dependent topic). The series is otherwise ready for merging, with all major implementation questions resolved and comprehensive test coverage in place.

### Core problem or goal

Users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch`/`git pull` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The series implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched, using configuration to separate namespace mappings from fetch selection logic. The design is finalized: the series introduces `remote.<name>.fetchRefmap` to decouple the "what" (which refs to fetch) from the "where" (where to store them), resolving the maintainer and key reviewer’s objection to overloading `remote.<name>.refmap`.

### Key technical details

- **Finalized design (v13)**:
  - **New config key**: `remote.<name>.fetchRefmap` explicitly specifies which refs to fetch (e.g., `*@{upstream}`), decoupling the "what" from the "where".
  - **Refmap role**: `remote.<name>.refmap` reverts to its original purpose: namespace mapping only (e.g., `+refs/heads/*:refs/remotes/second/*`).
  - **Precedence**: `remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration (if neither is configured). Command-line refspecs override both config keys.
  - **Forced updates (`+`)**: Belong on the refmap side (the "where"), not the `fetchRefmap` side (the "what"). This aligns with existing refspec behavior but introduces a **minor inconvenience**: users who want to reject non-fast-forward updates for some branches while mapping all refs the same way must use **two separate refspecs** (one with `+` and one without).
  - **Override semantics (proposed)**: Command-line refspecs (or colon-separated `remote.<name>.fetch` entries) must **override `remote.<name>.fetchRefmap` entirely**, not coexist with it (dual storage). This aligns with Phillip Wood’s latest feedback and preserves backwards compatibility.
  - **Dual storage behavior (current, deprecated)**: Colon-separated `fetch` entries with explicit destinations are stored in both the explicit destination and the refmap’s destination. This is preserved in v13 but will be updated in v14.
  - **`@{push}` resolution fix**: The v13 revision adds a fallback to `remote->refmap` in `remote.c` (`tracking_for_push_dest()`) if `remote->fetch` does not resolve the refname. The fix is **mechanical, uncontroversial, and well-tested** (new test in `t/t1514-rev-parse-push.sh`). However, the interaction with override semantics is **unclear** and may require further clarification or implementation in v14.
  - **Files touched (v13)**:

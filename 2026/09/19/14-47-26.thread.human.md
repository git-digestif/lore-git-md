This thread is about Harald Nordgren’s patch series introducing a "matching-inspired" fetch mode for shallow Git repositories. The goal is to speed up `git fetch` operations in shallow clones by dynamically fetching only the branches tracked by local branches at the remote, rather than negotiating history for all remote branches. The series is now in its tenth iteration (v10) and is ready for merging to Junio’s `next` branch.

The key change is the introduction of `remote.<name>.refmap`, a configuration knob that defines namespace mappings without specifying what to fetch. When no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` now infers which branches to fetch by enumerating the local branches whose `@{upstream}` points to that remote. This logic is implemented in `remote.c` and integrated into `builtin/fetch.c`. The series also adds a `--limited-fetch` flag to `git remote add` and makes it the default for shallow repositories. All prior feedback—including Junio’s review points and D. Ben Knoble’s suggestions—has been addressed, and the only remaining work is to incorporate minor clarity and efficiency improvements (e.g., using `strvec` instead of `string_list`) in a final revision or follow-up patches.

The series is uncontroversial and introduces no new technical debt. It reuses existing logic and configuration machinery, and the fallback behavior in `remote_find_tracking()` has been clarified to ensure compatibility with existing Git operations like `@{upstream}` and `--delete-merged`. The v10 series resolves a merge conflict with Junio’s `ch/fetch-followremotehead-lazy-validation` topic, which was recently merged to `master`. No procedural or technical blockers remain, and the series is a strong candidate for merging to `next`.

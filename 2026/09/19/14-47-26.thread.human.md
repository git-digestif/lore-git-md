This thread began with Harald Nordgren’s patch proposing a `fetch.shallow` configuration option to restrict refspec-less fetches in shallow repositories to the current branch’s upstream, aiming to address slow or hanging `git fetch` operations when remotes have many branches. The discussion quickly pivoted to the root cause—wildcard fetch refspecs in shallow repositories—and abandoned the original patch in favor of two alternative designs: modifying `git remote add` to default to narrower refspecs in shallow repositories, and introducing a new "matching-inspired" fetch mode for `git fetch` that dynamically fetches only remote branches tracked by local branches.

The current focus is on refining Junio’s matching-inspired fetch mode, with Harald now suggesting a key usability improvement: the remote’s default branch should always be fetched, even if no local branch tracks it yet. This addresses a common pain point where users set their current branch’s upstream to the remote’s default branch (e.g., `main` or `master`) but must manually fetch the remote’s `HEAD` first in shallow repositories. Harald’s proposal preserves the dynamic, tracking-based approach while smoothing this edge case, though it leaves open the question of how to determine the remote’s default branch without a network call (e.g., using the remote’s `HEAD` or the local current branch as a proxy).

No code has been implemented for either alternative, and the discussion remains conceptual. The two approaches—narrower refspecs in `git remote add` and the matching-inspired fetch mode—are not mutually exclusive but have not yet been reconciled. The thread has also not addressed how existing shallow repositories with wildcard refspecs would be handled, nor which approach should take precedence in shallow repositories. The next steps will likely involve resolving these open questions and prototyping one or both solutions.

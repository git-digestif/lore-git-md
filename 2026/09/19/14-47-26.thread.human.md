This thread began with Harald Nordgren’s proposal to address slow fetches in shallow repositories by introducing a `fetch.shallow` config option, but quickly pivoted to a broader design discussion. The consensus emerged that the root problem was wildcard fetch refspecs in shallow repositories, leading to two complementary solutions: modifying `git remote add` to default to narrower refspecs in shallow repos, and introducing a new "matching-inspired" fetch mode for `git fetch`.

Harald has now posted a patch implementing the latter approach. The patch introduces a special refspec `+:` (or `:`) that dynamically fetches only the branches tracked by local branches at the remote being fetched, plus the remote’s default branch. In shallow repositories, `git remote add` now defaults to this refspec instead of the traditional wildcard, immediately addressing the performance issue without requiring new configuration. The implementation touches `fetch.c`, `remote.c`, and refspec handling, with thorough test coverage in a new script `t/t5585-fetch-tracking-refspec.sh`. The design preserves backward compatibility for non-shallow repositories while providing a sensible default for shallow ones.

The patch reflects the refined design discussed earlier, incorporating feedback from Phillip Wood and Junio C Hamano. Phillip’s narrower-refspec proposal for `git remote add` and Harald’s matching-inspired fetch mode are now understood to address complementary use cases—initial setup and subsequent fetches, respectively. The patch does not yet integrate the narrower-refspec approach, leaving that as a potential follow-up. Open questions remain about edge cases (e.g., stale `HEAD`, no local branches tracking the remote) and whether the matching-inspired mode should be opt-in or default in shallow repos, but the current implementation provides a solid foundation for further discussion.

This thread began with Harald Nordgren’s patch to introduce a `fetch.shallow` config option, aiming to speed up `git fetch` in shallow repositories by restricting refspec-less fetches to the current branch. The discussion quickly pivoted to a deeper problem: wildcard fetch refspecs in shallow repositories cause unnecessary negotiation for all remote branches. Two complementary solutions emerged: (1) making `git remote add` default to narrower refspecs in shallow repositories, and (2) introducing a "matching-inspired" fetch mode that dynamically fetches only the remote branches tracked by local branches, plus the remote’s default branch.

The design consensus now centers on these two approaches, with the original patch abandoned. Phillip Wood proposed that `git remote add` in shallow repositories should either refuse to add a remote without explicit branch tracking or query the remote’s `HEAD` to fetch only the default branch by default. Meanwhile, Junio C Hamano and Harald Nordgren refined the matching-inspired fetch mode, which would inspect local branches’ upstream settings to determine which remote branches to fetch. A key challenge is the "priming" step—how users initially fetch the remote’s default branch to establish tracking. D. Ben Knoble suggested simplifying this by having `git fetch <remote> <branch>` automatically create remote-tracking branches, but Junio clarified that this would break long-standing behavior, as `git fetch` has historically treated such commands as "single-shot" operations that don’t update remote-tracking branches. This constraint complicates the priming mechanism, though the core idea of the matching-inspired mode remains viable.

Open questions include how to handle stale or missing `HEAD` information in the narrower-refspec approach, whether the matching-inspired mode should be the default for shallow repositories, and how the two solutions will coexist. The discussion is now focused on refining these details, with no code changes implemented yet. Key participants—Harald Nordgren, Phillip Wood, Junio C Hamano, and D. Ben Knoble—have all contributed substantively, but the maintainer’s clarification about `git fetch`’s historical behavior adds a significant constraint to the design. The thread remains active, with the next steps likely involving proposals for alternative priming mechanisms or transition strategies.

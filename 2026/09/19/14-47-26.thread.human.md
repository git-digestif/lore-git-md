Harald Nordgren’s eleven-part patch series introduces a "matching-inspired" fetch mode to address a long-standing pain point for users of shallow repositories: slow or hanging `git fetch` operations when the remote has many branches. The current behavior fetches all remote branches by default, which is inefficient for shallow clones. The series dynamically fetches only the branches tracked by local branches at the remote, using configuration to separate namespace mappings from fetch selection logic. After eleven iterations, the series is feature-complete and queued in `next`, but its design is now acknowledged as flawed by both the maintainer and a key reviewer.

The core issue is that the series overloads `remote.<name>.refmap` to control both *where* fetched refs are stored and *which* refs are fetched, repeating the same inflexibility it aims to fix. Junio C Hamano and Phillip Wood have agreed that the next iteration (v12) must introduce a dedicated `remote.<name>.fetchRefs` config key to decouple these concerns. The current v11 implementation remains in `next` but is blocked from graduating to `master` until this redesign is implemented. Junio’s recent email confirms that the existing precedence rules (`remote.<name>.fetch` > `remote.<name>.refmap`) work as intended for edge cases, but the broader design shift is now the focus.

Key participants include Harald Nordgren (the author), Junio (the maintainer), and Phillip Wood (who raised the design objection). All prior technical feedback has been addressed, but the series now faces a substantive redesign before it can proceed. The `--limited-fetch` flag and shallow-repository default will remain but will operate under the new precedence rules once `fetchRefs` is introduced. Open questions include how `fetchRefs` will integrate with dynamic branch enumeration, whether it will support negation, and how documentation will clarify the new precedence rules. No timeline for v12 has been given, but the direction is clear.

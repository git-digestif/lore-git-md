This thread is about Harald Nordgren’s **v13 patch series** (6 patches) introducing `remote.<name>.fetchRefmap`, a new configuration key that enables a "matching-inspired" fetch mode for shallow repositories. The goal is to speed up `git fetch` in shallow clones by dynamically fetching only the branches tracked by local branches at the remote, rather than negotiating history for all remote branches. The design is finalized and endorsed by Junio C Hamano and Phillip Wood, with the series now under final review for merging to `master`.

The core change decouples the "what" (which refs to fetch) from the "where" (where to store them) using `remote.<name>.fetchRefmap` (e.g., `*@{upstream}`), while `remote.<name>.refmap` reverts to its original role as a namespace mapping (e.g., `+refs/heads/*:refs/remotes/origin/*`). The precedence rule is clear: `remote.<name>.fetch` overrides `fetchRefmap`, which overrides dynamic branch enumeration (if neither is configured). Command-line refspecs override both config keys. The series also adds a `--limited-fetch` flag to `git remote add`, which is now the default for shallow repositories, and includes comprehensive test coverage.

The series is **blocked from graduating** by one remaining high-weight edge case: the override semantics for command-line refspecs and colon-separated `remote.<name>.fetch` entries. The discussion has converged toward Phillip Wood’s preference for **override semantics**, where command-line refspecs (or their config-based equivalents) replace `fetchRefmap`’s mapping entirely, rather than coexisting with it (dual storage). This aligns with user expectations and preserves backwards compatibility. The v13 revision preserves the current dual-storage behavior in a regression test, but this is expected to be updated in v14 to match the chosen override model. All other technical concerns—including documentation clarity, forced-update placement (`+` on the refmap side), and backwards compatibility—are resolved.

The fix is mechanical and uncontroversial, falling back to `remote->refmap` if `remote->fetch` doesn’t resolve the refname.

This thread introduces a new `fetch.shallow` configuration option (default: `false`) that restricts refspec-less fetches in shallow repositories to only the current branch’s upstream, addressing performance issues when the remote has many branches. The patch, submitted by Harald Nordgren, is under initial review and touches `builtin/fetch.c`, documentation, and adds test coverage.

Phillip Wood’s review raises a substantive design question: whether the patch targets the right problem. The commit message and documentation suggest the issue arises in shallow, *sparsely checked-out* clones, but the implementation doesn’t depend on sparseness—it only checks for shallowness. Phillip notes that the root cause might instead be `git remote add` defaulting to a wildcard fetch refspec in sparse repositories, which then causes refspec-less fetches to negotiate history for all remote branches. He proposes improving `git remote add` behavior in sparse contexts as an alternative solution, questioning whether a new config option is the most maintainable approach.

No other reviews or decisions have been posted yet, so the thread is now focused on this design discussion. The patch itself is well-tested and opt-in, but the outcome of this debate could lead to a revised approach or even a replacement solution. Key participants to watch include the author (Harald Nordgren) and other reviewers familiar with fetch mechanics or sparse-checkout behavior.

This is a **substantive review** of Derrick Stolee’s RFC series introducing a "safe" `strbuf` API that avoids `die()`. Phillip Wood’s reply engages deeply with the technical approach, naming, and implementation details, raising three key concerns.

First, Phillip questions the "safe" framing. He finds the term vague and suggests the API should instead be described as returning errors on failure, with function names reflecting that behavior (e.g., `strbuf_*_gently` or similar). He contrasts this with existing error-returning APIs in `xdiff` and `reftable`, implying the naming should align with established patterns.

Second, he critiques the usability of the proposed API. Checking for errors on every `strbuf` call would be cumbersome, so he proposes a sticky error bit (like C’s `stdio` functions) to allow deferred error checking. This would simplify usage in code paths where intermediate failures can be tolerated until the final result is needed.

Third, Phillip identifies a **bug** in the implementation: `sstrbuf_grow()` uses `st_add3()`, which calls `die()` on overflow, violating the safety guarantee. He suggests replacing it with `st_add_overflows()` to maintain the no-`die()` invariant. This undermines the CodeQL verification in the series, as the query would not catch this transitive `die()` call.

The review also touches on the broader transition plan. Phillip does not object to the incremental approach (land the API first, then refactor callers) but implies the naming and usability issues should be resolved before proceeding. His feedback is constructive and focused on making the API both correct and ergonomic. The tone is collaborative, treating the RFC as a starting point rather than a finished proposal.

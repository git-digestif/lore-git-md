This thread is about a regression in Git's reference-transaction hook, where deleting branches or tags via commands like `git branch -d` or `git tag -d` stopped reporting the old object ID to external tools (like Gerrit or GitLab) that rely on this hook. The issue, introduced in Git 2.31, causes the hook to receive all-zero OIDs for both old and new fields during deletions, breaking workflows that need to track what was deleted.

Maciej Ciemborowicz identified the root cause—a performance optimization in commit `8198907795` that replaced `delete_ref()` with `delete_refs()` but omitted the old OID—and posted a three-patch series to restore the correct behavior. The fix preserves the performance gains while ensuring the hook receives the resolved old OID, and it includes thorough test coverage for both files and reftable backends.

The series was looking solid until Karthik Nayak raised a critical race condition concern in the first patch: the new logic could fail if the ref’s value changes between when the caller resolves it and when the transaction runs. This could break atomicity and cause spurious failures in production. The author will need to address this before the series can move forward. No other objections or open questions remain, though the documentation may need a minor update to clarify the hook’s behavior. The fix is otherwise ready for review and integration.

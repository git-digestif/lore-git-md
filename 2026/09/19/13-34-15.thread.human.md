This thread addresses a regression in Git 2.31 where the reference-transaction hook receives all-zero object IDs when branches or tags are deleted via high-level commands like `git branch -d` or `git fetch --prune`, breaking external tools such as Gerrit and GitLab. The issue was introduced by a performance optimization in commit `8198907795` and affects both the files and reftable backends. Maciej Ciemborowicz proposed a three-patch bugfix series (v2) to restore the pre-regression behavior, but it faced substantive feedback from Karthik Nayak and Junio C Hamano regarding a critical design flaw: the patch’s use of a single transaction for all deletions turns the operation into an all-or-nothing affair, contradicting the expected "best-effort" behavior of `refs_delete_refs()`.

The core conflict has been resolved in favor of a middle ground proposed by Karthik and endorsed by Junio: using `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures while preserving unconditional deletion for commands like `git fetch --prune`. This approach maintains backward compatibility and performance gains (bulk tag deletion remains at ~0.85 seconds for 10,000 tags) while fixing the regression. The v3 series, planned to incorporate all feedback, will also address code cleanup, merge conflicts, and edge cases like partial failures in `git fetch --prune`. Open questions remain about documentation updates and whether other commands (e.g., `git push --delete`) might be affected.

Key participants include Maciej (author), who identified the regression and iterated on the fix; Karthik, who raised the design conflict and proposed the `REF_TRANSACTION_ALLOW_FAILURE` solution; and Junio, whose review confirmed the need for best-effort deletion. The series is a high-priority bugfix with comprehensive test coverage for both backends, SHA-1/SHA-256, and concurrent updates. The v3 iteration is expected to resolve the remaining issues and proceed toward integration.

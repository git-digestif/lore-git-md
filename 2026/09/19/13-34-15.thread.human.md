This thread is about a regression in Git’s reference-transaction hook that broke external tools like Gerrit and GitLab by passing all-zero object IDs when branches or tags were deleted. The regression, introduced in Git 2.31, was fixed in a three-patch series (v5) that restored the pre-regression behavior while preserving performance gains. That series was merged to `next`, but fundamental architectural concerns raised by Patrick Steinhardt—about overloading `refs_delete_refs()` with conditional logic—have now forced a major rewrite.

Maciej Ciemborowicz, the author, has abandoned the v5 approach and proposed a new design: the transaction hook layer itself will now resolve and cache old OIDs for updates where callers didn’t supply them, storing them separately without affecting transaction safety checks. This avoids changes to `refs_delete_refs()` or its callers, aligning with Patrick’s preference for keeping that function as a simple wrapper for unconditional deletions. The fix will now apply to *all* ref-modifying commands (`git branch -d`, `git tag -d`, `git push`, etc.), not just the ones addressed in v5. While this resolves Patrick’s architectural objections, it introduces a new trade-off: the hook layer must now resolve old OIDs on demand, which could add latency for large batches.

The series is no longer ready for `master` and will require a v6 iteration. Junio C Hamano’s earlier request for concrete code comparisons remains unaddressed, but the new direction—avoiding changes to `refs_delete_refs()`—may simplify the decision. Key participants include Maciej (author), Patrick Steinhardt (refs subsystem maintainer), Junio (maintainer), and Karthik Nayak (substantive reviewer). The thread is now focused on whether the new approach can balance correctness, performance, and API consistency.

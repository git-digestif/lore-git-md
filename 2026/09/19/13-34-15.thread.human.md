This thread is about a regression in Git's reference-transaction hook that was introduced in Git 2.31, where deleting branches or tags via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`) causes the hook to receive all-zero object IDs instead of the resolved old OID. This breaks external tools like Gerrit and GitLab that rely on the hook to monitor ref changes. The regression was caused by an optimization in commit `8198907795` that replaced `delete_ref()` with `delete_refs()` but omitted the old OID for safety-checked deletions.

Maciej Ciemborowicz posted a three-patch series (now at v4) to fix the regression, restoring the pre-2.31 behavior while preserving the performance gains of the original optimization. The series uses `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures (e.g., when a concurrent update rejects one ref but others succeed) while still passing old OIDs to the hook. It also includes comprehensive test coverage for both files and reftable backends, SHA-1/SHA-256, broken/symbolic refs, and all affected commands. The series has received substantive reviews from Karthik Nayak and Junio Hamano, addressing core design conflicts, API consistency, and user-facing behavior.

The v4 series was technically complete and ready for merging, but Junio recently identified a **build-breakage issue**: the call to `refs_delete_refs()` in `builtin/fetch.c` was updated in patch 3/3 to pass a new `&failed_refs` parameter, but the earlier patches (1/3 and 2/3) modified the function signature without updating all call sites. This creates a bisect hazard, as the series does not compile between patches 1 and 3. The fix is straightforward (update the call sites in patch 1/3 or move the parameter addition to patch 3/3), but the oversight must be addressed before the series can be queued. No new design concerns were raised, and the series remains ready for merging once this mechanical issue is resolved.

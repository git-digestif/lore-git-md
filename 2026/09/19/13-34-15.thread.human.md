This thread reports a regression in Git 2.31 where the reference-transaction hook—used by external tools like Gerrit and GitLab to monitor ref changes—now receives all-zero object IDs for *both* old and new OID fields when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`). The old behavior (Git 2.28–2.30) correctly provided the resolved old OID followed by all-zeros, which aligns with the documented contract for safety-checked deletions. Direct deletion via `git update-ref -d` remains unaffected, and the issue persists through Git 2.55 across both files and reftable backends.

Maciej Ciemborowicz, the author, argues the regression violates the hook’s documented safety guarantees, as Git has already resolved the ref being deleted and should preserve the old OID. The thread is still in the diagnostic phase, with no prior discussion or rationale identified for the change. D. Ben Knoble recently suggested using `git bisect` to pinpoint the exact commit that introduced the regression, a practical next step that could clarify whether the change was intentional or an oversight. This would also help determine whether the fix should restore the old behavior or update the documentation to reflect a new contract. No other participants have weighed in yet, leaving the thread’s direction open.

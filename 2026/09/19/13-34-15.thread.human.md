This thread is about a regression in Git’s reference-transaction hook that broke external tools like Gerrit and GitLab by reporting all-zero object IDs when branches or tags are deleted. The issue, introduced in Git 2.31, affects high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`) but not low-level operations like `git update-ref -d`. Maciej Ciemborowicz identified the root cause and posted a three-patch v3 series that restores the pre-regression behavior—passing the resolved old OID to the hook—while preserving the performance gains of the original optimization.

The v3 series addresses all prior feedback, including Junio C Hamano’s critical design concerns about transaction behavior and Karthik Nayak’s proposed middle ground using `REF_TRANSACTION_ALLOW_FAILURE`. Performance measurements confirm no regression, and comprehensive tests cover both files and reftable backends, SHA-1/SHA-256, and edge cases like concurrent updates. The only remaining open item is a minor UI adjustment in the third patch: Junio requested granular error reporting to match existing behavior, where successful deletions show "[deleted]" even if some refs fail. This is a low-risk, user-facing tweak and does not affect the core fix.

The latest email is a procedural note from Maciej, expressing mild frustration with the review process but adding no new technical content. The series itself is otherwise ready for merging, with all substantive feedback incorporated. Key participants—Maciej, Junio, and Karthik—have converged on the design, and the regression’s impact on external tools makes this a high-priority fix.

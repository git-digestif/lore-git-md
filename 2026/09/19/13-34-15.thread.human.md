This thread is about a regression in Git 2.31 where the reference-transaction hook stopped receiving the correct old object IDs when branches or tags are deleted, breaking external tools like Gerrit and GitLab. Maciej Ciemborowicz identified the root cause—a 2021 optimization that replaced `delete_ref()` with `delete_refs()`—and proposed a three-patch fix (v5) to restore the pre-regression behavior while preserving performance gains. The series was merged to `next`, but fundamental architectural concerns from Patrick Steinhardt and Junio C Hamano could force a major rewrite before it graduates to `master`.

The core debate centers on *where* to fix the regression. Maciej’s current approach modifies `refs_delete_refs()` to let callers supply old OIDs, but Patrick argues this overcomplicates the API and that the fix should instead live in the transaction layer, ensuring the hook always receives correct old OIDs for *all* ref modifications (not just `git branch`/`git tag`). Junio has requested concrete code comparisons to weigh the complexity of both approaches. Maciej’s latest reply addresses Karthik Nayak’s technical feedback—retaining a safety check in `ref_transaction_delete()` and clarifying failure counting—but doesn’t resolve the architectural standoff. The next iteration may need to demonstrate both solutions to move forward.

The series is technically complete and restores the expected hook behavior, but the unresolved design questions could delay its final integration. Key open issues include whether to extend `refs_delete_refs()` or rewrite callers to use transactions directly, and how to ensure the fix scales to all ref-modifying commands. The discussion remains constructive, with all participants prioritizing correctness and maintainability over expediency.

This thread reports a regression in Git 2.31 where the `reference-transaction` hook—used by external tools like Gerrit and GitLab to monitor ref changes—began receiving all-zero object IDs for both old and new OID fields when branches or tags are deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`). The issue was traced to commit `8198907795`, an optimization for bulk tag deletions that replaced `delete_ref()` with `delete_refs()`, inadvertently omitting the old OID for safety-checked deletions. The change was unintentional, as the commit message did not document this behavioral shift, and the performance gains (reducing deletion time for 24,000 tags from 30 minutes to 5 seconds) can likely be preserved while restoring the old behavior.

The regression affects both the files and reftable backends and persists through Git 2.55. Direct deletions via `git update-ref -d` remain unaffected, as they explicitly pass the old OID. The author, Maciej Ciemborowicz, argues for restoring the old behavior—passing the resolved old OID to the hook—on the grounds that Git has already resolved the ref being deleted, and the documentation allows all-zero old OIDs only for force-updates. D. Ben Knoble’s earlier suggestion to use `git bisect` was key to identifying the root cause, and the thread now has a clear path forward: a targeted fix to modify `delete_refs()` to pass the old OID when available, ensuring the hook receives correct data for safety-checked deletions.

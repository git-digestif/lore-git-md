This thread is about a regression in Git's `reference-transaction` hook that broke external tools like Gerrit and GitLab by reporting all-zero object IDs when branches or tags are deleted. The issue, introduced in Git 2.31, affects high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`) but not low-level operations like `git update-ref -d`. Maciej Ciemborowicz identified the root cause—a performance optimization that inadvertently removed safety checks—and posted a three-patch v2 series to restore the pre-regression behavior.

The v2 series fixes the regression by making deletions conditional again (compare-and-delete), which prevents overwriting concurrent updates but introduces a deliberate race condition. The first two patches (core plumbing and `git branch`/`git tag` updates) are ready for review, while the third patch—just posted—addresses `git fetch --prune` and `git remote prune`. It ensures the hook receives the correct old OID, preserves performance (~0.85s for 10,000 deletions), and fixes a UI inconsistency where "[pruned]" was printed even after failures. Tests cover both files and reftable backends, SHA-1/SHA-256, and concurrent updates.

The main open question is whether the project accepts the trade-off: conditional deletion restores safety but risks transaction failures if refs change between resolution and execution. Karthik Nayak raised this concern, and Maciej argues the failure mode is desirable to avoid silent overwrites. D. Ben Knoble’s earlier suggestion to use `git bisect` helped pinpoint the regression. The series is technically sound, but its fate hinges on the broader discussion about safety vs. unconditional deletion.

This thread is about a regression in Git's reference-transaction hook, which external tools like Gerrit and GitLab rely on to monitor branch and tag changes. The issue surfaced in Git 2.31: when deleting branches or tags via commands like `git branch -d` or `git tag -d`, the hook now receives all-zero object IDs for both old and new OID fields, losing the previous object ID that was correctly reported in earlier versions. Maciej Ciemborowicz identified the root cause—a performance optimization in commit `8198907795` that replaced `delete_ref()` with `delete_refs()` but omitted the old OID—and proposed a three-patch fix in version 5 of the series.

The v5 series restores the pre-regression behavior, ensuring the hook receives the resolved old OID followed by all-zeros on deletion, while preserving the performance gains of the original optimization. It also addresses prior feedback, including Junio Hamano's request for granular error reporting and Karthik Nayak's API consistency concerns. The series was merged to `next`, but four high-weight reviews have since raised critical architectural and technical issues. Karthik Nayak and Junio Hamano debated the safety of removing a `BUG()` macro in `ref_transaction_delete()`, while Patrick Steinhardt argued that the first patch overcomplicates `refs_delete_refs()` by adding conditional logic that should instead be handled by callers using the lower-level transaction API. Patrick also criticized the second patch for being too narrow, fixing only `git branch` and `git tag` while leaving other ref-modifying commands unaffected, and proposed resolving old OIDs at the transaction layer itself to ensure the hook always receives the correct old OID.

The latest email from Junio Hamano adds nuance to the architectural debate. While he acknowledges Patrick's point that `refs_delete_refs()` should remain a simple wrapper for unconditional deletions, he also notes that rewriting callers to use transactions directly might not reduce complexity. He emphasizes the need for clearer commit messaging and concrete code comparisons before deciding between the two approaches. The series remains in `next`, but the discussion could force a major rewrite before it graduates to `master`. Maciej must now either defend the current design or pivot to Patrick's proposal, which would require significant refactoring of callers like `builtin/branch.c` and `builtin/fetch.c`. The outcome will shape how Git handles batch ref deletions and hook payloads for all ref-modifying commands.

This thread is about a regression in Git's `reference-transaction` hook that broke external tools like Gerrit and GitLab by reporting all-zero OIDs when branches or tags are deleted. The issue surfaced in Git 2.31 after an optimization for bulk tag deletions inadvertently removed the old OID from hook notifications. Maciej Ciemborowicz identified the root cause and posted a three-patch v2 series to restore the pre-regression behavior, ensuring the hook receives the resolved old OID while preserving the performance gains.

The v2 series now explicitly addresses a race condition concern raised by Karthik Nayak, framing it as an intentional trade-off: conditional deletion (compare-and-delete) restores the safety check from Git 2.28–2.30, preventing deletions of refs that were never examined by the caller. The first patch (core plumbing change) is ready for review, and the second patch—just posted—updates `git branch` and `git tag` to pass old OIDs to the hook, along with regression tests for both functionality and concurrent updates. The third patch (for `git fetch --prune` and `git remote prune`) remains unchanged but includes UI fixes. Performance measurements confirm no regression, and the series includes comprehensive test coverage for files/reftable backends, SHA-1/SHA-256, and edge cases.

The key open question is whether the project accepts the safety trade-off of conditional deletion or prefers unconditional deletion, which would lose the safety check. Karthik’s concern remains unresolved, but the patches themselves are uncontroversial and ready for technical review. Maciej has incorporated feedback, including a minor readability improvement from Karthik, and the series is now functionally complete. No other affected commands (e.g., `git push --delete`) have been identified, but a broader audit may be warranted.

This thread is about a regression in Git 2.31 where the reference-transaction hook—used by external tools like Gerrit and GitLab to monitor ref changes—started receiving all-zero object IDs when branches or tags were deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`). The regression, introduced by a performance optimization in commit `8198907795`, broke backward compatibility with Git 2.28–2.30, where the hook correctly received the resolved old OID before deletion.

Maciej Ciemborowicz’s v5 fix, a three-patch series, restores the pre-regression behavior while preserving the performance gains. The series was merged to `next` after addressing all prior feedback, including Junio Hamano’s concerns about granular error reporting and Karthik Nayak’s API consistency issues. However, two critical reviews now threaten its graduation to `master`. Karthik raised technical concerns about safety and redundancy in the first patch, while Patrick Steinhardt challenged the architectural soundness of the approach, arguing that `refs_delete_refs()` should remain a simple wrapper for unconditional deletions and that callers needing conditional logic should use the lower-level transaction API directly.

The latest email from Patrick targets the second patch, proposing a broader alternative: instead of fixing the issue in `git branch` and `git tag` alone, the transaction system itself should resolve and queue old OIDs for all ref modifications. This would ensure the hook always receives correct old OIDs, eliminating the need to update individual call sites. While this approach would fix the issue for all commands (including future ones), it’s a more invasive change that could introduce new edge cases. The author must now decide whether to defend the current minimal fix or pivot to Patrick’s proposal, which would likely require a major rewrite. The outcome will determine whether the fix remains a targeted bugfix or becomes a broader refactoring of the transaction system.

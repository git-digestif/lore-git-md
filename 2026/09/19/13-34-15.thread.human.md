---

This thread tracks a regression in Git’s reference-transaction hook, where deleting branches or tags via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, or `git fetch --prune`) now reports all-zero object IDs for *both* the old and new OID fields in the hook. The issue, introduced in Git 2.31 by a performance optimization for bulk tag deletions, broke external tools like Gerrit and GitLab that rely on the hook to monitor ref changes. The regression persists through Git 2.55 and affects both the files and reftable backends.

Maciej Ciemborowicz identified the root cause and posted a v6 fix that moves the solution into the transaction hook layer itself. The patch resolves old OIDs on demand, storing them in a separate field that doesn’t affect transaction safety checks, and restores the pre-regression behavior for *all* ref-modifying commands—including symbolic refs and concurrent updates—while preserving the performance gains of the original optimization. The design addresses architectural concerns raised by Patrick Steinhardt (who endorsed the approach) and Junio C Hamano, and the patch is well-tested with updated regression tests. It’s rebased onto `master` and ready for review.

The author has now deprioritized this fix in favor of addressing a separate but related bug (branch renaming), which they argue can’t be worked around. However, the v6 patch remains a strong candidate for merging, as it resolves a long-standing regression with a clean, layer-appropriate solution. The only open question is whether the on-demand resolution of old OIDs introduces latency for large batches, but this is considered an acceptable trade-off. Reviewers may still want to evaluate the patch on its merits, as it fixes a real issue affecting external integrations.

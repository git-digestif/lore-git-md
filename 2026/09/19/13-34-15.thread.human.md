This thread is about a regression in Git 2.31 where the reference-transaction hook stopped receiving the old object ID when branches or tags were deleted via high-level commands like `git branch -d` or `git tag -d`. Instead, the hook got all-zero OIDs, breaking external tools like Gerrit and GitLab that rely on this information. Maciej Ciemborowicz identified the root cause—a performance optimization in commit `8198907795`—and posted a three-patch series (now at v3) to restore the pre-regression behavior while preserving the performance gains.

The v3 series resolves the core design conflict by adopting a "best-effort" transaction approach using `REF_TRANSACTION_ALLOW_FAILURE`. This preserves unconditional deletion for commands like `git fetch --prune` while still passing the old OID to the hook, addressing feedback from Junio C Hamano and Karthik Nayak. The latest email covers the second patch, which updates `git branch` and `git tag` to pass resolved old OIDs to `refs_delete_refs()`, reintroducing race protection (rejecting deletions if refs change concurrently). The changes are minimal, confined to the high-level commands, and include expanded test coverage for both single and batched deletions.

All feedback from prior versions has been addressed, and the series is now ready for merging. The regression affects both files and reftable backends, and the fix ensures backward compatibility without performance regressions. Key participants include Maciej (author), Junio (maintainer), and Karthik Nayak (reviewer), whose substantive feedback shaped the final design. No open questions remain.

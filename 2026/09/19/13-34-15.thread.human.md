This thread is about a regression in Git’s reference-transaction hook, where deleting branches or tags via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`) stopped reporting the old object ID to external tools like Gerrit and GitLab. The issue, introduced in Git 2.31, was caused by an optimization that replaced `delete_ref()` with `delete_refs()` but omitted the old OID for safety-checked deletions. Maciej Ciemborowicz identified the root cause and posted a three-patch series (now at v4) to restore the pre-regression behavior while preserving the performance gains.

The v4 series is technically complete and addresses all prior feedback, including Junio’s request for granular error reporting and Karthik Nayak’s concerns about API consistency. It uses `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures while maintaining unconditional deletion for `git fetch --prune` and `git remote prune`, fully resolving the core design conflict. The patches cover all affected commands, backends (files and reftable), and edge cases like broken/symbolic refs, with comprehensive test coverage. Junio’s latest reply clarifies that the review process’s length reflects the problem’s complexity, not procedural delays, and confirms the series remains Maciej’s responsibility—no new technical changes or status updates are needed. The series is ready for merging to `next`.

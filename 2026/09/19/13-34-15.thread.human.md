This thread tracks a regression in Git’s reference-transaction hook, where deleting branches or tags via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, etc.) now reports all-zero object IDs for *both* old and new OID fields in the hook. The issue, introduced in Git 2.31 by commit `8198907795`, broke external tools like Gerrit and GitLab that rely on the hook to monitor ref changes, as the old OID (correctly reported in Git 2.28–2.30) is lost. The regression persists through Git 2.55 and affects both files and reftable backends.

Maciej Ciemborowicz identified the root cause and posted a v6 fix, now a single-patch series that moves the solution into the transaction hook layer itself. The new design resolves old OIDs on demand, storing them in separate fields (`hook_old_oid` and `hook_old_target`) that don’t influence transaction safety checks. This preserves the bulk-deletion performance optimization (5 seconds vs. 30 minutes for 10,000 tags) while restoring pre-regression behavior for *all* ref-modifying commands, including symbolic refs and concurrent updates. The patch is rebased onto `master` and passes the full test suite, with updated tests verifying hook payloads for batched deletions, remote pruning, and UI consistency.

Key feedback came from Patrick Steinhardt, who raised architectural concerns about earlier versions (v5) overloading `refs_delete_refs()`. The v6 approach fully addresses his feedback by keeping `refs_delete_refs()` as a simple wrapper for unconditional deletions and implementing the fix at the transaction layer. Patrick has explicitly endorsed this direction as "a sensible change to make," though he noted a potential performance trade-off for large batches (on-demand resolution of old OIDs), which the thread now considers acceptable. Junio C Hamano previously requested clearer commit messaging and code comparisons, both of which are addressed in v6. Karthik Nayak’s earlier reviews (v2/v5) also shaped the design, particularly around API semantics and safety checks.

The series is complete and ready for review, with no open technical questions. The only remaining discussion point is whether the performance impact for large batches warrants mitigation, but this is now considered a settled trade-off. The fix is a strong candidate for merging, as it resolves a persistent regression with a clean, layer-appropriate solution that aligns with maintainer feedback.

This thread is about a regression in Git’s reference-transaction hook that broke external tools like Gerrit and GitLab by sending all-zero object IDs when branches or tags were deleted. The issue, introduced in Git 2.31, affected commands like `git branch -d`, `git tag -d`, `git remote prune`, and `git fetch --prune`, though `git update-ref -d` remained unaffected. Maciej Ciemborowicz identified the root cause—a performance optimization that inadvertently dropped the old OID—and posted a three-patch series to restore the pre-regression behavior.

The v3 series, now finalized, addresses all prior feedback, including critical design concerns from Junio C Hamano and Karthik Nayak. The key fix uses `REF_TRANSACTION_ALLOW_FAILURE` to preserve unconditional deletion (expected for `git fetch --prune` and `git remote prune`) while still passing the resolved old OID to the hook. Performance remains unaffected, with bulk deletions of 10,000 tags still taking ~0.85 seconds. The series includes comprehensive test coverage for both files and reftable backends, SHA-1/SHA-256, and edge cases like concurrent updates.

The latest patch (third in v3) specifically targets `git fetch --prune` and `git remote prune`, ensuring these commands pass old OIDs to the hook without breaking their existing behavior. It reuses existing ref scans to avoid extra work and fixes a UI inconsistency where prune commands previously reported success even after failures. All open questions have been resolved, and the series is ready for merging. Key participants—Maciej, Junio, and Karthik—have converged on a solution that balances backward compatibility, performance, and correctness.

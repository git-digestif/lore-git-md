This thread is about a regression in Git’s reference-transaction hook, where deleting branches or tags via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`) stopped reporting the old object ID to external tools like Gerrit and GitLab. The issue, introduced in Git 2.31, caused the hook to receive all-zero OIDs for both old and new fields, breaking workflows that depend on tracking ref changes. Maciej Ciemborowicz identified the root cause—a performance optimization in commit `8198907795`—and proposed a fix in a three-patch series (now at v2).

The v2 series restored the pre-regression behavior (passing the resolved old OID to the hook) but reintroduced a safety check that made deletions conditional, which Karthik Nayak argued could break user expectations for `git fetch --prune`. In the latest update, Maciej accepted Karthik’s feedback and will adopt `REF_TRANSACTION_ALLOW_FAILURE` in v3 to preserve unconditional deletion while still passing old OIDs. This resolves the core design conflict, and the remaining work is mechanical (rebase, code cleanup, and test hygiene). The series is now on track for final review, with the regression tests covering both files and reftable backends, SHA-1/SHA-256, and edge cases like concurrent updates. The fix is high-priority, as it affects tools relying on the hook’s accuracy.

This thread is about a regression in Git’s reference-transaction hook that broke external tools like Gerrit and GitLab by reporting all-zero object IDs when branches or tags are deleted. The issue surfaced in Git 2.31 after an optimization for bulk deletions inadvertently dropped the resolved old OID from hook notifications. Maciej Ciemborowicz identified the root cause and posted a three-patch series to restore the correct behavior while preserving the performance gains.

The first patch introduced plumbing changes to allow `refs_delete_refs()` to accept optional old OIDs, and this second patch updates the `git branch` and `git tag` commands to pass those values. The fix is minimal, reusing already-resolved OIDs without additional ref reads, and includes test coverage for both files and reftable backends. Performance remains unaffected, with bulk deletions still fast (~0.85 seconds for 10,000 tags). The series is uncontroversial so far, with D. Ben Knoble’s earlier suggestion to use `git bisect` helping pinpoint the regression.

The main open question is whether other commands (e.g., `git push --delete`, `git worktree remove`) might also be affected by the same regression. The third patch will address `git fetch --prune` and `git remote prune`, but the thread hasn’t yet audited all potential edge cases. No objections or alternative approaches have been raised, and the fix appears straightforward.

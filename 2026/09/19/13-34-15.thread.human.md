This thread is about a regression in Git's reference-transaction hook that broke external tools like Gerrit and GitLab by reporting all-zero object IDs when branches or tags were deleted. The issue, introduced in Git 2.31, affected high-level commands like `git branch -d` and `git tag -d`, though `git update-ref -d` remained unaffected. Maciej Ciemborowicz identified the root cause and has now posted a v6 single-patch fix that moves the solution into the transaction hook layer itself, addressing architectural concerns raised by Patrick Steinhardt and Junio Hamano.

The fix restores the pre-regression behavior by recording a separate "observed old value" for updates where callers didn't supply an expected old OID, ensuring the hook always receives the correct old OID without affecting transaction safety checks. This approach preserves the performance gains of the original optimization while avoiding changes to `refs_delete_refs()` or its callers. The patch has been rebased onto `master` and passes all tests, with updated coverage verifying hook payloads for all ref-modifying commands across both files and reftable backends.

Key participants include Maciej (the author), Patrick Steinhardt (who raised architectural concerns about earlier versions), Junio Hamano (who requested clearer documentation), and Karthik Nayak (who provided substantive technical feedback on earlier iterations). The v6 approach aligns with Patrick's feedback and addresses Junio's requests for clarity, making it a strong candidate for merging. The only remaining question is whether the on-demand resolution of old OIDs might introduce unacceptable latency for large batches, which Patrick may weigh in on.

This thread is about a regression in Git's reference-transaction hook that broke external tools like Gerrit and GitLab by reporting all-zero object IDs when branches or tags were deleted. The issue, introduced in Git 2.31, affected commands like `git branch -d`, `git tag -d`, `git remote prune`, and `git fetch --prune`, though `git update-ref -d` remained unaffected. Maciej Ciemborowicz identified the root cause and posted a three-patch bugfix series, now in its fifth iteration (v5).

The v5 series is technically complete and ready for merging. It restores the pre-regression behavior—passing the resolved old OID to the hook—while preserving the performance gains of the original optimization. The core design conflict was resolved by adopting `REF_TRANSACTION_ALLOW_FAILURE`, allowing partial failures and granular error reporting without breaking backward compatibility for `git fetch --prune` and `git remote prune`. All feedback from prior versions has been addressed, including Junio’s concerns about error reporting consistency and Karthik’s API and code hygiene suggestions. The series includes comprehensive test coverage for both files and reftable backends, SHA-1/SHA-256, and edge cases like broken refs and concurrent updates.

The second patch in the series, just summarized, specifically fixes `git branch -d` and `git tag -d` by ensuring the hook receives the correct old OID. The change is minimal, focused, and integrates cleanly with the rest of the series. With all open questions resolved and the series rebased cleanly onto `master`, it’s now awaiting Junio’s merge to `next`. No further changes are expected.

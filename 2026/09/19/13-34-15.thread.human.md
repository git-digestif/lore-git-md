This thread is about a regression in Git 2.31 that broke the reference-transaction hook for external tools like Gerrit and GitLab. When branches or tags are deleted via commands like `git branch -d` or `git fetch --prune`, the hook now receives all-zero object IDs instead of the resolved old OID, losing critical tracking information. Maciej Ciemborowicz identified the root cause—a 2021 optimization that replaced conditional deletions with unconditional ones—and has posted a three-patch v4 series to restore the pre-regression behavior while preserving performance.

The fix is now complete. The first two patches addressed `git branch` and `git tag`, while this latest patch restores correct hook behavior for `git fetch --prune` and `git remote prune`. The series uses `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures (e.g., when a ref changes mid-operation) while still passing old OIDs to the hook, resolving the core design conflict. Junio Hamano and Karthik Nayak reviewed the patches, with all feedback addressed—including granular error reporting and API consistency. The UI now shows "[deleted]" for successful prunes and omits failed refs from dangling symref checks, matching existing behavior.

The regression affects both files and reftable backends and persists through Git 2.55. The fix includes comprehensive test coverage for edge cases like concurrent updates, atomic fetches, and broken refs. Performance remains strong: deleting 10,000 tags still takes ~0.85 seconds. The series is ready for merging to `next` and is a high-priority bugfix for tools relying on the hook.

This thread is about a regression in Git’s reference-transaction hook, where deleting branches or tags via commands like `git branch -d` or `git tag -d` now reports all-zero object IDs for *both* old and new OIDs, breaking tools like Gerrit and GitLab that rely on the hook to track ref changes. The bug was introduced in Git 2.31 by a performance optimization for bulk tag deletions and has persisted through Git 2.55, affecting both the files and reftable backends. The original fix (v5) tried to extend `refs_delete_refs()` to pass old OIDs, but maintainer Patrick Steinhardt raised architectural concerns, arguing the fix belonged in the transaction layer instead.

The author, Maciej Ciemborowicz, has now pivoted to a v6 series that moves the fix entirely into the transaction hook layer. This new approach resolves old OIDs on demand and caches them separately—without affecting transaction safety checks—so the hook always receives the correct old OID. While this sidesteps the earlier API debates and preserves the bulk-deletion performance gains, it introduces a potential latency trade-off for large batches, which hasn’t been quantified yet.

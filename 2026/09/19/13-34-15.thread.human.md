This thread is about a regression in Git’s `reference-transaction` hook that affects tools like Gerrit and GitLab. When a branch or tag is deleted using high-level commands (`git branch -d`, `git tag -d`, or `git remote prune`), the hook now receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The issue does not occur with direct deletions via `git update-ref -d`, which still provides the old OID followed by all-zeros as expected.

Maciej Ciemborowicz, the author, provides a reproducer script demonstrating the problem across both the files and reftable backends, confirming it persists through Git 2.55. They argue that while the documentation allows all-zero old OIDs for force-updates, this case—where Git has already resolved the ref—should preserve the old OID for safety-checked deletions. The thread raises the question of whether this change was intentional or an oversight, as no prior discussion or rationale is cited. The regression breaks workflows that rely on tracking the exact commit a branch or tag pointed to before deletion. No responses or decisions have been made yet in the thread.

This thread is about a regression in Git’s reference-transaction hook, where deleting branches or tags via high-level commands (like `git branch -d` or `git fetch --prune`) stopped reporting the old object ID to external tools, breaking integrations with Gerrit, GitLab, and CI systems. The issue was introduced in Git 2.31 and persists through 2.55, affecting both files and reftable backends. Maciej Ciemborowicz posted a three-patch v2 series to restore the pre-regression behavior, ensuring the hook receives the resolved old OID on deletion while preserving the performance gains of the original optimization.

The series is now complete and ready for final review, but two key questions remain unresolved. First, whether the project accepts the trade-off of conditional deletions (safety via compare-and-delete) or prefers unconditional deletions (losing the safety check). Second, Karthik Nayak raised a new concern about the user experience: the v2 fix changes `git fetch --prune` and `git remote prune` from unconditional to conditional deletions, which could now fail if refs are concurrently updated. Karthik suggests using `REF_TRANSACTION_ALLOW_FAILURE` to preserve the old behavior while still passing old OIDs to the hook, but this would require reworking the patch. The series also addresses minor implementation nits, such as streamlining loops and fixing test cleanups, but these are secondary to the core design debate.

The patches touch the refs subsystem and affect commands like `git branch -d`, `git tag -d`, `git remote prune`, and `git fetch --prune`, while leaving `git update-ref -d` unaffected. Performance measurements confirm no regression, and the series includes comprehensive test coverage for both backends, SHA-1/SHA-256, and edge cases like concurrent updates. The unresolved trade-off—safety vs. unconditional deletion—is the primary blocker for merging.

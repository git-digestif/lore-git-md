This thread is about a regression in Git 2.31 where the reference-transaction hook—used by external tools like Gerrit and GitLab to monitor ref changes—stopped receiving the old object ID when branches or tags were deleted, instead getting all-zero OIDs. The issue affects high-level commands like `git branch -d`, `git tag -d`, `git remote prune`, and `git fetch --prune`, but not `git update-ref -d`. Maciej Ciemborowicz identified the root cause (commit `8198907795`) and posted a three-patch v3 series to restore the pre-regression behavior while preserving the performance gains of the original optimization.

The v3 series resolves the core design conflict by adopting `REF_TRANSACTION_ALLOW_FAILURE`, a "best-effort" transaction mode that allows partial failures (preserving unconditional deletion for `git fetch --prune` and `git remote prune`) while still passing old OIDs to the hook. This addresses feedback from Junio C Hamano (who raised concerns about all-or-nothing transactions breaking user expectations) and Karthik Nayak (who proposed the middle-ground solution). The latest email covers the second patch, which updates `git branch -d` to resolve and pass old OIDs to `refs_delete_refs()`, matching the pre-2.31 behavior. The series is now ready for merging, with all feedback incorporated, comprehensive test coverage, and no performance regressions. Key participants include Maciej (author), Junio (maintainer), and Karthik (reviewer), whose substantive feedback shaped the final design.

The reference-transaction hook regression, where deletions of branches or tags via commands like `git branch -d` or `git tag -d` sent all-zero object IDs to the hook instead of the correct old OID, is now close to resolution. Maciej Ciemborowicz identified the root cause—a 2021 optimization that replaced `delete_ref()` with `delete_refs()` but omitted the old OID for safety-checked deletions—and has proposed a v6 fix that moves the correction into the transaction hook layer itself. This approach, now endorsed by Patrick Steinhardt (the refs subsystem maintainer), ensures the hook always receives the correct old OID without altering the unconditional deletion semantics of `refs_delete_refs()` or requiring changes to its callers.

The v6 design resolves old OIDs on demand during the hook’s "preparing" phase, storing them in separate fields that don’t influence transaction safety checks. This preserves the bulk-deletion performance gains (critical for large tag sets) while restoring pre-regression behavior for *all* ref-modifying commands, including `git remote prune` and `git fetch --prune`. Tests confirm the fix works across both files and reftable backends, and the commit message now clearly explains why the transaction layer is the right place for this logic. The only open question is whether the on-demand OID resolution introduces noticeable latency for large batches, but Patrick has explicitly accepted this trade-off. With Junio’s earlier concerns about clarity addressed and Karthik Nayak’s technical feedback incorporated, the series is now poised for final review and integration.

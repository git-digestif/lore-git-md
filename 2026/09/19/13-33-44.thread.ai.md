Thread identity
Subject: `reference-transaction` hook omits new ref on branch rename (`git branch -m`)
Series version: standalone bug report (no patch series)
Originating author: Maciej Ciemborowicz
Thread type: bug report

Core problem or goal
The `reference-transaction` hook is expected to report every ref change in a transaction, but when a branch is renamed (`git branch -m`), the hook only receives the deletion of the old branch name, not the creation of the new one. This affects both the files-based and reftable backends, with the reftable backend exhibiting a more severe failure by omitting any usable rename payload. The expected behavior—confirmed via `git update-ref --stdin`—is that both the deletion and creation events should be included in the same transaction.

Current status
Under review. No patch yet; the report and Karthik Nayak's diagnosis are the only messages in the thread. The reproducer script and compatibility test suite demonstrate the issue across Git versions 2.28 through 2.55.

Key technical details
- Subsystems: ref backends (files, reftable), hook infrastructure, `builtin/branch.c`
- Commands: `git branch -m`, `git update-ref --stdin`
- Hook: `reference-transaction`
- Functions: `refs_delete_ref()` (files backend), TOMBSTONE entries (reftable backend)
- Test coverage: minimal reproducer script provided; linked to `git-hooks-ext` compatibility test suite
- Backwards compatibility: issue present since at least Git 2.28; no on-disk format changes

Open questions and loose ends
- Fix location: Should the fix be in `builtin/branch.c` (to ensure branch renames use transactions), the ref backend layer (to unify rename handling), or the hook dispatch mechanism (to ensure consistency across backends)?
- Backend consistency: The files backend triggers the hook for the deletion via `refs_delete_ref()`, while the reftable backend writes a TOMBSTONE entry directly, skipping the hook entirely. The fix must address both backends.
- Implementation approach: Karthik suggests the branch-rename logic should be updated to use transactions, but the exact mechanism (e.g., refactoring `git branch -m` to use `update-ref` internally) remains unspecified.

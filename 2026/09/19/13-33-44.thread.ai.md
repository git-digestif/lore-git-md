Thread identity
Subject: `reference-transaction` hook omits new ref on branch rename (`git branch -m`)
Series version: v1 (standalone patch, pending redesign)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The `reference-transaction` hook must report every ref change in a transaction, but when a branch is renamed (`git branch -m`) or copied (`git branch -c`), the hook only receives the deletion of the old branch name, not the creation of the new one. Both the files-based and reftable backends are affected, with the reftable backend omitting any usable rename payload entirely. The expected behavior—confirmed via `git update-ref --stdin`—is that both deletion and creation events are included in the same transaction.

Current status
Patch v1 posted and reviewed. Junio C Hamano raised architectural concerns about the proposed implementation, specifically the overloading of the generic `ref_transaction` struct with rename/copy-specific fields (`old_refname`, `new_refname`, `type`). Maciej Ciemborowicz has agreed to rework the patch to confine rename/copy state to individual ref updates rather than the transaction as a whole, preserving the genericity of the core transaction interface and enabling multi-ref operations (e.g., renaming A→X, B→Y, and C→Z in one transaction). The redesign is delayed while Maciej completes a separate `git range-diff` usability series; no new patch version has been posted yet. The thread remains open on the architectural question.

Key technical details
- Subsystems: ref backends (files, reftable), hook infrastructure, `builtin/branch.c`
- Commands: `git branch -m`, `git update-ref --stdin`, `git branch -c`
- Hook: `reference-transaction`
- New symbols (v1): `REF_TRANSACTION_TYPE_RENAME`, `REF_TRANSACTION_TYPE_COPY`, `REF_TRANSACTION_FLAG_SKIP_HOOK` (all subject to redesign)
- Functions modified (v1): `refs_delete_ref()`, `ref_transaction_prepare()`, `ref_transaction_commit()`
- Test files: new tests in `t/t1416-ref-transaction-hooks.sh` (coverage for rename, copy, forced updates, D/F conflicts, concurrent updates, hook-triggered rollback)
- Backwards compatibility: issue present since at least Git 2.28; no on-disk format changes
- Core data model (proposed redesign): rename/copy state will move from the generic `ref_transaction` struct to per-ref-update data (e.g., `struct ref_update`), avoiding assumptions about single-ref operations and enabling composition of multi-ref transactions.

Open questions and loose ends
- Architectural redesign:
  1. How to represent multi-ref rename/copy operations cleanly in the per-ref-update model.
  2. Whether the `REF_TRANSACTION_FLAG_SKIP_HOOK` flag remains necessary after restructuring the call chain to distinguish top-level operations from nested subroutines.
  3. Backend-specific reflog handling during rename/copy operations in the new model.
- Minor commit message improvements (removing "currently", adding "test" to final sentence) remain pending.
- Whether a `bool copy` parameter is preferable to an `int` for the copy/rename mode.

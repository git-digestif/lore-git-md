Thread identity
Subject: `reference-transaction` hook omits new ref on branch rename (`git branch -m`)
Series version: v3 (4-patch series)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The `reference-transaction` hook must report every ref change in a transaction, but when a branch is renamed (`git branch -m`) or copied (`git branch -c`), the hook only receives the deletion of the old branch name, not the creation of the new one. Both the files-based and reftable backends are affected. The expected behavior—confirmed via `git update-ref --stdin`—is that both deletion and creation events are included in the same transaction.

Current status
Patch v3 posted as a 4-patch series, splitting the work into logical steps: (1) internal hook suppression flag (`REF_TRANSACTION_FLAG_INTERNAL`), (2) reflog replacement support, (3) copy/rename integration, and (4) removal of backend-specific callbacks. This redesign addresses Patrick Steinhardt’s blocking objections from v2 by abandoning the transaction-wide copy/rename state in favor of per-ref-update tracking, centralizing hook suppression in `run_transaction_hook()`, and dropping the pre-lock revalidation step. Performance regressions are acknowledged (~137% slowdown for files-based rename with large reflogs, ~20-25% for reftable) but deemed acceptable. The series is **ready for substantive review** and independent of the batched-deletion old-OID fix. No merge status reported; thread remains under active review.

Key technical details
- Subsystems: ref backends (files, reftable), hook infrastructure, `builtin/branch.c`
- Commands: `git branch -m`, `git branch -c`, `git update-ref --stdin`
- Hook: `reference-transaction`
- New symbols: `REF_TRANSACTION_FLAG_INTERNAL` (internal-only flag), `ref_transaction_replace_reflog()` (replaces backend-specific callbacks), per-ref-update copy/rename state (no longer transaction-wide)
- Functions modified: `refs_delete_ref()`, `ref_transaction_prepare()`, `ref_transaction_commit()`, `run_transaction_hook()`, backend-specific reflog and concurrency logic
- Test files: `t/t1416-ref-transaction-hooks.sh` (coverage for rename, copy, forced updates, D/F conflicts, concurrent updates, hook-triggered rollback), `t/perf/p1424-ref-copy-rename.sh` (performance regression measurement)
- Backwards compatibility: issue present since at least Git 2.28; no on-disk format changes
- Core data model: rename/copy state is now part of `struct ref_update`, enabling composition of multi-ref transactions without overloading the generic `ref_transaction` struct. Backend-specific work (e.g., files staging logs in temporary files, reftable writing tombstones) remains, but logical ref updates and reflog history are now handled through ordinary transactions. The `REF_TRANSACTION_FLAG_INTERNAL` flag ensures hooks only see the outer logical update, not nested backend operations.
- Performance impact: ~137% slowdown for files-based rename with 10,000 reflog entries, ~20-25% for reftable. Perf script added to measure overhead.

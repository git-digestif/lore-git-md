Thread identity
Subject: `reference-transaction` hook omits new ref on branch rename (`git branch -m`)
Series version: v3 (4-patch series)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The `reference-transaction` hook must report every ref change in a transaction, but when a branch is renamed (`git branch -m`) or copied (`git branch -c`), the hook only receives the deletion of the old branch name, not the creation of the new one. Both the files-based and reftable backends are affected. The expected behavior—confirmed via `git update-ref --stdin`—is that both deletion and creation events are included in the same transaction.

Current status
Patch v3 posted as a 4-patch series, splitting the work into logical steps: (1) internal hook suppression flag (`REF_TRANSACTION_FLAG_INTERNAL`), (2) reflog replacement support via `ref_transaction_replace_reflog()`, (3) copy/rename integration (the heavy-lifting patch), and (4) removal of backend-specific callbacks. This redesign addressed Patrick Steinhardt’s blocking objections from v2 by abandoning the transaction-wide copy/rename state in favor of per-ref-update tracking, centralizing hook suppression in `run_transaction_hook()`, and dropping the pre-lock revalidation step. Performance regressions are acknowledged (~137% slowdown for files-based rename with large reflogs, ~20-25% for reftable) but deemed acceptable. The series is **under review**, but Junio C Hamano’s latest email reports **test breakages** in `t0600.16` and `t5510.35` when applied to `master` (`6de20f6092`). These failures indicate the series inadvertently alters **packed-refs locking behavior** or **transaction rollback logic**, likely due to refactoring in patches 3/4 or 4/4. No merge status reported; the series remains **blocked** pending a v4 to address the regressions.

Key technical details
- Subsystems: ref backends (files, reftable), hook infrastructure, `builtin/branch.c`
- Commands: `git branch -m`, `git branch -c`, `git update-ref --stdin`, `git update-ref -d`, `git fetch --prune`
- Hook: `reference-transaction`
- New symbols: `REF_TRANSACTION_FLAG_INTERNAL` (internal-only flag), `ref_transaction_replace_reflog()` (replaces backend-specific callbacks), `REF_REPLACE_REFLOG` (private flag for reflog replacement), `REF_COPY_SOURCE`, `REF_NEEDS_PACK` (per-ref-update flags), `copy_from` field in `struct ref_update`, helper functions `ref_transaction_prepare_copy` and `ref_update_record_copy_source`
- Functions modified: `refs_delete_ref()`, `ref_transaction_prepare()`, `ref_transaction_commit()`, `run_transaction_hook()`, backend-specific reflog and concurrency logic (`refs/files-backend.c`, `refs/reftable-backend.c`)
- Test files: `t/t1416-ref-transaction-hooks.sh` (coverage for rename, copy, forced updates, D/F conflicts, concurrent updates, hook-triggered rollback), `t/t1425-reflog-transaction.sh` (new, covers null-OID preservation, entry ordering, rollback, duplicate replacement), `t/perf/p1424-ref-copy-rename.sh` (performance regression measurement)
- Backwards compatibility: issue present since at least Git 2.28; no on-disk format changes
- Core data model: rename/copy state is now part of `struct ref_update`, enabling composition of multi-ref transactions without overloading the generic `ref_transaction` struct. Backend-specific work (e.g., files staging logs in temporary files, reftable writing tombstones) remains, but logical ref updates and reflog history are now handled through ordinary transactions. The `REF_TRANSACTION_FLAG_INTERNAL` flag ensures hooks only see the outer logical update, not nested backend operations. The patch preserves backend-specific reflog semantics: reftable replaces destination history, while the files backend stages logs in temporary files to avoid exposing partial changes to hooks.
- Performance impact: ~137% slowdown for files-based rename with 10,000 reflog entries (~5 ms → ~17 ms), ~20-25% for reftable (~44 ms → ~54 ms). Patch 2/4 (reflog replacement) has negligible overhead but compounds in later patches. The final patch (4/4) removes 656 lines of backend-specific logic, reducing code duplication without affecting performance.
- Cleanup: Patch 4/4 deletes backend-specific callbacks (`rename_ref`, `copy_ref`) and their private helpers (e.g., `TMP_RENAMED_LOG`, `rename_tmp_log_callback`, `write_copy_table`), along with debug backend tracing wrappers. The transaction API now fully handles copy/rename operations.
- **Newly identified issues**: The series breaks two existing tests (`t0600.16` and `t5510.35`) by altering packed-refs locking behavior or transaction rollback logic, likely due to changes in `ref_transaction_commit()` or the removal of backend-specific callbacks. The failures occur in unrelated commands (`update-ref -d`, `fetch --prune`), suggesting broader unintended side effects.

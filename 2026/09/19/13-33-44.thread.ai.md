Thread identity
Subject: `reference-transaction` hook omits new ref on branch rename (`git branch -m`)
Series version: v4 (4-patch series)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix, now dominated by meta-discussion about AI-assisted development, contributor workflow, and project norms

Core problem or goal
The `reference-transaction` hook must report every ref change in a transaction, but when a branch is renamed (`git branch -m`) or copied (`git branch -c`), the hook only receives the deletion of the old branch name, not the creation of the new one. Both the files-based and reftable backends are affected. The expected behavior—confirmed via `git update-ref --stdin`—is that both deletion and creation events are included in the same transaction.

Current status
Patch v4 remains a 4-patch series: (1) `REF_TRANSACTION_FLAG_INTERNAL` infrastructure, (2) `ref_transaction_replace_reflog()` for reflog replacement, (3) copy/rename integration, and (4) removal of backend-specific callbacks. The v4 iteration resolved the test breakages Junio C Hamano reported in v3 (`t0600.16` and `t5510.35`) by preserving the packed transaction error in `files_transaction_prepare()`. The series passes the full test suite on macOS with both backends. Performance regressions persist (~137% slowdown for files-based rename with large reflogs, ~20-25% for reftable) but are deemed acceptable for correctness. Patch 1/4 remains uncontroversial and ready to proceed; the **series as a whole remains stalled on process concerns**. Patrick’s latest email adds a new dimension by distinguishing between **small, easily reasoned changes** (acceptable for AI assistance) and **large, complex series** (risky due to the author’s limited context to vet AI-generated nuances). Key technical details
- Subsystems: ref backends (files, reftable), hook infrastructure, `builtin/branch.c`
- Commands: `git branch -m`, `git branch -c`, `git update-ref --stdin`, `git update-ref -d`, `git fetch --prune`
- Hook: `reference-transaction`
- New symbols: `REF_TRANSACTION_FLAG_INTERNAL` (internal-only flag), `ref_transaction_replace_reflog()` (replaces backend-specific callbacks), `REF_REPLACE_REFLOG` (private flag for reflog replacement), `REF_COPY_SOURCE`, `REF_NEEDS_PACK` (per-ref-update flags), `copy_from` field in `struct ref_update`, helpers `ref_transaction_prepare_copy` and `ref_update_record_copy_source`
- Functions modified: `refs_delete_ref()`, `ref_transaction_prepare()`, `ref_transaction_commit()`, `run_transaction_hook()` (centralized suppression check for `REF_TRANSACTION_FLAG_INTERNAL`), backend-specific reflog and concurrency logic (`refs/files-backend.c`, `refs/reftable-backend.c`)
- Test files: `t/t1416-ref-transaction-hooks.sh` (rename, copy, forced updates, D/F conflicts, concurrent updates, hook-triggered rollback), `t/t1425-reflog-transaction.sh` (new, covers null-OID preservation, entry ordering, rollback, duplicate replacement), `t/perf/p1424-ref-copy-rename.sh` (performance regression measurement)
- Backwards compatibility: issue present since at least Git 2.28; no on-disk format changes
- Core data model: rename/copy state is now part of `struct ref_update`, enabling composition of multi-ref transactions without overloading the generic `ref_transaction` struct. The `REF_TRANSACTION_FLAG_INTERNAL` flag ensures hooks only see the outer logical update, not nested backend operations. Patch 2/4 introduces `ref_transaction_replace_reflog()` to handle reflog replacement atomically, staging logs in temporary files (files backend) or tombstoning old entries (reftable) to avoid exposing partial changes to hooks. Log-only entries with null new OIDs are preserved as part of the history. Patch 3/4 implements the core logic to queue source and destination ref updates as ordinary transactions, replacing backend-specific callbacks with a unified approach. It introduces per-ref-update flags (`REF_COPY_SOURCE`, `REF_NEEDS_PACK`) and a `copy_from` field to track rename/copy relationships, handling edge cases like D/F conflicts, case-only renames on case-insensitive filesystems, symlink reflogs, and concurrent source modifications during the "preparing" hook phase. Atomic reflog replacement is ensured by staging logs in temporary files (files backend) or tombstoning old entries (reftable), so hooks never see partial changes. Patch 4/4 deletes 656 lines of backend-specific code (`rename_ref`, `copy_ref` callbacks and their private helpers like `TMP_RENAMED_LOG`, `rename_tmp_log_callback`, `write_copy_table`) from `refs/debug.c`, `refs/files-backend.c`, `refs/packed-backend.c`, `refs/refs-internal.h`, and `refs/reftable-backend.c`.
- Performance impact: ~137% slowdown for files-based rename with 10,000 reflog entries (~5 ms → ~17 ms), ~20-25% for reftable (~44 ms → ~54 ms). Patch 2/4 has negligible overhead but compounds in later patches.

Thread identity
Subject: `reference-transaction` hook omits new ref on branch rename (`git branch -m`)
Series version: v2 (standalone patch)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The `reference-transaction` hook must report every ref change in a transaction, but when a branch is renamed (`git branch -m`) or copied (`git branch -c`), the hook only receives the deletion of the old branch name, not the creation of the new one. Both the files-based and reftable backends are affected, with the reftable backend omitting any usable rename payload entirely. The expected behavior—confirmed via `git update-ref --stdin`—is that both deletion and creation events are included in the same transaction.

Current status
Patch v2 posted, addressing Junio C Hamano’s architectural concerns from v1 by confining copy/rename state to the destination ref update rather than the transaction as a whole. This redesign preserves the genericity of the transaction interface and enables multi-ref operations (e.g., renaming A→X, B→Y, and C→Z in one transaction). **Patrick Steinhardt has rejected the current implementation as unreviewable**, citing poor code structure (mixed refactoring and logic), unclear commit messages (vague about backend-specific logic), and non-idiomatic C patterns (e.g., excessive block scopes) that suggest over-reliance on AI-generated code. Maciej Ciemborowicz has acknowledged these shortcomings in a follow-up, admitting the patch was AI-assisted and lacks sufficient C expertise, and has offered to prepare a v3 with split commits and clearer explanations. However, he defers to Karthik Nayak (who offered to help) or others to take over the fix, expressing uncertainty about meeting Steinhardt’s standards. The patch is **not under active review** and no merge status has been reported; the thread remains blocked on code quality concerns.

Key technical details
- Subsystems: ref backends (files, reftable), hook infrastructure, `builtin/branch.c`
- Commands: `git branch -m`, `git branch -c`, `git update-ref --stdin`
- Hook: `reference-transaction`
- New symbols: per-ref-update copy/rename state (no longer transaction-wide); `REF_TRANSACTION_FLAG_SKIP_HOOK` remains internal but Steinhardt proposes moving its check into `run_transaction_hook` for clarity
- Functions modified: `refs_delete_ref()`, `ref_transaction_prepare()`, `ref_transaction_commit()`, backend-specific reflog and concurrency logic
- Test files: `t/t1416-ref-transaction-hooks.sh` (coverage for rename, copy, forced updates, D/F conflicts, concurrent updates, hook-triggered rollback)
- Backwards compatibility: issue present since at least Git 2.28; no on-disk format changes
- Core data model: rename/copy state is now part of `struct ref_update`, enabling composition of multi-ref transactions without overloading the generic `ref_transaction` struct
- Backend-specific logic: While logical ref updates (deletion/creation) use the generic API, reflog history operations (e.g., filesystem-level renames in the files backend) remain backend-dependent, a distinction not clearly articulated in the commit message
- Revalidation step: Ensures hook payload matches actual ref state at commit time, preventing mismatches if the hook modifies refs during the "preparing" phase

Open questions and loose ends

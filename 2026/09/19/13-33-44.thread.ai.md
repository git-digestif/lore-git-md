Thread identity
Subject: `reference-transaction` hook omits new ref on branch rename (`git branch -m`)
Series version: v1 (standalone patch)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The `reference-transaction` hook must report every ref change in a transaction, but when a branch is renamed (`git branch -m`) or copied (`git branch -c`), the hook only receives the deletion of the old branch name, not the creation of the new one. Both the files-based and reftable backends are affected, with the reftable backend omitting any usable rename payload entirely. The expected behavior—confirmed via `git update-ref --stdin`—is that both deletion and creation events are included in the same transaction.

Current status
Patch v1 posted. Junio C Hamano has provided substantive review raising architectural concerns about the proposed implementation. The patch introduces a new transaction type (`REF_TRANSACTION_TYPE_RENAME`/`COPY`) and a `REF_TRANSACTION_FLAG_SKIP_HOOK` flag to ensure that branch rename and copy operations are reported as a single logical transaction to the hook. Both backends are updated to use the new mechanism, preserving backend-specific reflog handling while unifying hook visibility. The patch includes thorough test coverage for rename, copy, forced updates, D/F conflicts, concurrent updates, and hook-triggered rollback.

Key technical details
- Subsystems: ref backends (files, reftable), hook infrastructure, `builtin/branch.c`
- Commands: `git branch -m`, `git update-ref --stdin`, `git branch -c`
- Hook: `reference-transaction`
- New symbols: `REF_TRANSACTION_TYPE_RENAME`, `REF_TRANSACTION_TYPE_COPY`, `REF_TRANSACTION_FLAG_SKIP_HOOK`
- Functions modified: `refs_delete_ref()`, `ref_transaction_prepare()`, `ref_transaction_commit()`
- Test files: new tests in `t/t1416-ref-transaction-hooks.sh`
- Backwards compatibility: issue present since at least Git 2.28; no on-disk format changes
- Core data model: the patch extends the generic `ref_transaction` struct with rename/copy-specific fields (`old_refname`, `new_refname`, `type`), which Junio now questions as potentially overloading the generic interface.

Open questions and loose ends
- Architectural concerns raised by Junio:
  1. Whether `REF_TRANSACTION_FLAG_SKIP_HOOK` is necessary or avoidable by restructuring the call chain to distinguish top-level operations from nested subroutines.
  2. Whether rename/copy-specific fields should be confined to backend-specific data (e.g., `files_copy_or_rename_transaction_data`) rather than added to the generic `ref_transaction` struct, to preserve the genericity of the core transaction interface and avoid assumptions about single-ref operations.
  3. How the current design would scale to more complex transactions involving multiple renames, copies, or mixed operations, given that the patch appears to assume a single rename or copy per transaction.
- Minor commit message improvements suggested (removing "currently", adding "test" to final sentence).
- Whether a `bool copy` parameter is preferable to an `int` for the copy/rename mode.

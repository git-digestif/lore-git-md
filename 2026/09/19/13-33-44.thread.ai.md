Thread identity
Subject: `reference-transaction` hook omits new ref on branch rename (`git branch -m`)
Series version: v2 (standalone patch)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The `reference-transaction` hook must report every ref change in a transaction, but when a branch is renamed (`git branch -m`) or copied (`git branch -c`), the hook only receives the deletion of the old branch name, not the creation of the new one. Both the files-based and reftable backends are affected, with the reftable backend omitting any usable rename payload entirely. The expected behavior—confirmed via `git update-ref --stdin`—is that both deletion and creation events are included in the same transaction.

Current status
Patch v2 posted, addressing Junio C Hamano’s architectural concerns from v1. The redesign confines copy/rename state to the destination ref update rather than the transaction as a whole, preserving the genericity of the transaction interface and enabling multi-ref operations (e.g., renaming A→X, B→Y, and C→Z in one transaction). However, **Patrick Steinhardt has rejected the current implementation as unreviewable**, citing poor code structure, unclear commit messages, and non-idiomatic patterns (e.g., excessive C block scopes) that suggest over-reliance on AI-generated code. The patch is **not under active review** until a major rewrite is posted; no merge status has been reported.

Key technical details
- Subsystems: ref backends (files, reftable), hook infrastructure, `builtin/branch.c`
- Commands: `git branch -m`, `git branch -c`, `git update-ref --stdin`
- Hook: `reference-transaction`
- New symbols (v2): per-ref-update copy/rename state (no longer transaction-wide); `REF_TRANSACTION_FLAG_SKIP_HOOK` remains internal
- Functions modified: `refs_delete_ref()`, `ref_transaction_prepare()`, `ref_transaction_commit()`, backend-specific reflog and concurrency logic
- Test files: `t/t1416-ref-transaction-hooks.sh` (coverage for rename, copy, forced updates, D/F conflicts, concurrent updates, hook-triggered rollback)
- Backwards compatibility: issue present since at least Git 2.28; no on-disk format changes
- Core data model: rename/copy state is now part of `struct ref_update`, enabling composition of multi-ref transactions without overloading the generic `ref_transaction` struct
- **Proposed improvements**: Steinhardt suggests splitting refactoring (e.g., `refs_delete_ref` wrapper) into separate commits and moving the `REF_TRANSACTION_FLAG_SKIP_HOOK` check into `run_transaction_hook` for clarity.

Open questions and loose ends
- **Code structure**: The patch mixes refactoring with core logic, making review difficult. Steinhardt demands a split into smaller, focused commits.
- **Commit message clarity**: The current message is criticized for vagueness about backend-specific logic and perf-impact filler.
- **Idiomatic patterns**: Excessive use of C block scopes (`{ ... }`) is flagged as non-idiomatic and likely AI-generated.
- **`REF_TRANSACTION_FLAG_SKIP_HOOK`**: Steinhardt proposes a cleaner alternative (moving the check into `run_transaction_hook`).
- **Authorial ownership**: Steinhardt’s review implies the patch lacks sufficient human oversight, raising the bar for future revisions.

This is the first patch in a **bugfix series** targeting the refs subsystem, specifically the regression in the `reference-transaction` hook where deletions via high-level commands (`git branch -d`, `git tag -d`, etc.) report all-zero OIDs instead of the resolved old OID. This patch introduces the core plumbing change: it modifies `refs_delete_refs()` to accept an optional `oid_array` of old OIDs, allowing callers to preserve the old values they have already resolved. The change is backward-compatible—existing callers pass `NULL` and retain the unconditional deletion behavior—while enabling the subsequent patches to restore the correct hook behavior.

The patch touches eight files, primarily updating function signatures and call sites. The key change is in `refs.c`, where `refs_delete_refs()` now iterates over the `refnames` and `old_oids` arrays in lockstep, passing each non-null OID to `ref_transaction_delete()` with the `REF_HAVE_OLD` flag. A safety check ensures the two arrays have matching lengths, and null OIDs are explicitly filtered out to avoid redundant checks. The commit message and code are clear, and the change is narrowly scoped to the ref deletion path, with no impact on other ref operations or the on-disk format.

This is a well-structured, mechanical change that lays the groundwork for the rest of the series. The author has taken care to avoid breaking existing callers while enabling the fix, and the addition of the `oid_array` parameter is a clean way to pass the resolved old OIDs without introducing new ref reads. The patch does not yet restore the old behavior—it merely provides the mechanism—so the regression remains until the follow-up patches update the callers. No controversy is evident, and the change aligns with the series' goal of preserving the performance gains of the original optimization while fixing the hook regression.

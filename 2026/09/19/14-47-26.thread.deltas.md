# Thread deltas

## 2026/09/19

- [2026/09/19/14-47-26 by Harald Nordgren via GitGitGadget <gitgitgadget@gmail.com>] Harald Nordgren submitted a patch (PR #2412) adding a `fetch.shallow` configuration option, off by default, that causes a refspec-less `git fetch` or `git pull` in a shallow repository to fetch only the current branch's tracked upstream instead of every branch the remote advertises, while still updating `refs/remotes/<name>/HEAD`; the change is opt-in because it alters which remote-tracking refs a plain fetch leaves behind.

## 2026/09/21

- [2026/09/21/13-28-08 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood questioned whether the sparse checkout is relevant to the reported problem, said it is unclear whether the case is a shallow single-branch clone that later gained a second remote with a wildcard fetch refspec or a local repo with many remote-tracking branches, and suggested that in the former case "git remote add" in a sparse repository could be improved to avoid adding a wildcard fetch refspec and instead set up the new remote to fetch only the branch(es) of interest.
- [2026/09/21/21-45-45 by Harald Nordgren <haraldnordgren@gmail.com>] Harald Nordgren confirmed the former scenario ("Yeah likely"): he cloned his fork of homebrew-core with --depth=1, added real upstream as a remote, worked on a feature branch, and git pull hung after his attempt to set the branch to track upstream did not work; he also said he had not considered changing "git remote add" behavior and called that an interesting idea.

## 2026/09/22

- [2026/09/22/13-00-11 by Harald Nordgren <haraldnordgren@gmail.com>] Harald Nordgren asked whether the wildcard-refspec problem should instead be fixed in "git remote add" (in a sparse/shallow repository) rather than via the proposed opt-in fetch.shallow config, suggesting perhaps only the "git remote add" fix is needed.
- [2026/09/22/14-53-36 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood recommended doing it instead of the config option, since fixing "git remote add" prevents the problem from arising in the first place, which is better than an opt-in config most users are probably unaware of.
- [2026/09/22/15-37-17 by Harald Nordgren <haraldnordgren@gmail.com>] Harald Nordgren agreed that makes sense but pointed out missing local-side information (the new remote's branches and default branch) that cannot be known without a network call to the newly added remote, and asked how that should be handled.
- [2026/09/22/17-11-03 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano proposed a new fetch mode inspired by push's "matching" mode: when remote.*.fetch signals a special mode (he tentatively suggested ':' and '+:' as the refspec trigger), git fetch would find each local branch whose @{upstream} points at that remote and fetch only those upstream branches, noting it differs from push matching because local branch names do not map to remote names and multiple local branches may share one upstream; he called it a useful addition.
- [2026/09/22/21-40-09 by Harald Nordgren <haraldnordgren@gmail.com>] Harald Nordgren suggested that the upstream's default branch should always be included in such a fetch even if no local branch tracks it yet, citing his habit of setting every repo's upstream to the remote default branch and the annoyance of having to run "git remote set-head upstream --auto" first on shallow repos.

## 2026/09/23

- [2026/09/23/15-14-32 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood proposed that "git remote add" in a shallow repository could refuse to add a remote without "--track" (or "--fetch"), or copy the refspecs of existing remotes if they all fetch the same branch(es); with "--fetch" it could look up the remote's default branch and fetch that when "--track" isn't given, since a wildcard refspec makes "git fetch" unusably slow.
- [2026/09/23/15-19-06 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood noted that the proposed "fetch branches our local branches track" mode is useful for remotes already fetched from, but leaves a chicken-and-egg problem for newly added remotes, because no local branch can have its upstream set to a remote that has never been fetched ("git branch --set-upstream-to" fails if the upstream does not exist).
- [2026/09/23/15-34-47 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano proposed priming the pump explicitly: `git remote add --fetch=: second <url>` would configure `fetch = :`, making the initial `git fetch second` a no-op until the user runs e.g. `git fetch second main:refs/remotes/second/main` and sets an upstream, after which plain `git fetch` updates only that branch.
- [2026/09/23/16-55-07 by D. Ben Knoble <ben.knoble@gmail.com>] D. Ben Knoble suggested it would be nicer if `git fetch second main` still mapped the fetch and created a remote-tracking branch under the usual hierarchy on top of that mode.
- [2026/09/23/19-50-01 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano rejected that: `git fetch second main` has been single-shot fetch syntax for 20 years that writes only to FETCH_HEAD, and automatically creating `refs/remotes/second/main` would break expectations without a transition plan and an escape hatch for users who want the old behavior.
- [2026/09/23/20-35-20 by Harald Nordgren via GitGitGadget <gitgitgadget@gmail.com>] Harald Nordgren posted [PATCH v2] "fetch: avoid fetching every branch of a new remote in a shallow repo", replacing the opt-in fetch.shallow config with a special fetch refspec "+:" that fetches the branches local branches are built on plus the remote's default branch; `git remote add` now uses it instead of the wildcard refspec whenever the repository is already shallow.
- [2026/09/23/21-38-38 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano said the v2 patch is too much for a single patch and should be split into bite-sized commits; he rejected the `fetch = :+` syntax because it gives no clue that remote-tracking branches belong under refs/remotes/second/, and instead proposed a `remote.<name>.refmap` configuration (e.g. `+refs/heads/*:refs/remotes/second/*`) combined with fetch-without-refspec enumerating the branches local branches build on, plus an explicit `git remote add --limited-fetch` option and later heuristics.

## 2026/09/25

- [2026/09/25/10-49-58 by Harald Nordgren via GitGitGadget <gitgitgadget@gmail.com>] Harald Nordgren posted v3 of the series "fetch: avoid fetching every branch of a new remote in a shallow repo", replacing the special ":"/"+:" fetch refspec from v2 with a remote.<name>.refmap mechanism (reusing the existing --refmap machinery) and splitting the change into 4 commits: adding remote.<name>.refmap, inferring branches to fetch from a refmap-only remote, adding "git remote add --limited-fetch", and defaulting to --limited-fetch in a shallow repository.
- [2026/09/25/22-38-39 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano, reviewing patch 1/4, said he was puzzled by the documentation claim that remote.<name>.refmap "only takes effect" when something explicit is fetched, arguing the refmap takes effect whenever given and it is the fetch operation itself that does nothing with zero explicit refspecs; he proposed alternative wording, called the code "looking good", and noted that reducing reliance on file-scope global variables (e.g. via a struct fetch_config) is a possible future cleanup outside this topic's scope.
- [2026/09/25/23-26-41 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano, reviewing patch 2/4, objected to always including the remote's default branch in the inferred fetch set, arguing Git should not fetch the remote's HEAD branch unasked when the user may not care about it, and that a user interested in it would already have a local branch tracking it; he also noted that force-fetching "HEAD" would make the fetch report show "* [new ref] HEAD -> second/main" instead of the usual "* [new branch] main -> second/main", and that not force-including HEAD would keep the code simpler.

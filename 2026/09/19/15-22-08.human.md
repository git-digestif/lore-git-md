This is a **bugfix** for a subtle but user-visible issue in Git 2.55.0 and current `master`: when `stash.index=true` is set and a staged change exists, running `git merge --ff-only --autostash` (or `git pull` with `rebase.autoStash` and `pull.rebase`) leaves behind a redundant stash entry and fails to clean up the `MERGE_AUTOSTASH` ref, even though the merge itself succeeds. The operation emits an error message, and the stash list contains an extra entry that shouldn’t be there.

The fix is now in its final stages. D. Ben Knoble implemented a clean solution that replaces the old subprocess-heavy index-merge logic (`git diff-tree`, `git apply --cached`, `git reset`) with a direct call to `merge_incore_nonrecursive()`. This not only resolves the root cause—premature deletion of the `MERGE_AUTOSTASH` ref—but also improves performance and code clarity. Phillip Wood reviewed the patch and confirmed it works, suggesting only minor polish: silencing merge verbosity (since conflicts already trigger an abort), simplifying conflict-label setup, and using `oidcpy()` instead of direct OID assignment for robustness.

The patch touches `sequencer.c` and has implications for `builtin/merge.c`, `builtin/stash.c`, and `branch.c`. It preserves the `MERGE_AUTOSTASH` ref until the autostash apply completes, eliminating three subprocess spawns and fixing the duplicate stash entry. Reproduction is straightforward with the script provided by Eli Barzilay, and both Knoble and Wood have validated the fix locally. No formal test has been added to the suite yet, but the fix is now one cleanup pass away from a formal submission as a patch series.

This is a well-motivated, narrowly scoped fix that addresses a real annoyance for users who rely on `stash.index` and `--autostash`. The implementation is clean, the review is substantive, and the solution is aligned with Git’s existing merge machinery. If you use `git stash` with staged changes, this patch is worth watching.

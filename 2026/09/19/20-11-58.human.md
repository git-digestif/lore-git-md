This is the third and final patch in a **bugfix series** that restores correct behavior to Git’s `reference-transaction` hook when pruning stale remote refs. The regression, introduced in Git 2.31, caused the hook to receive all-zero OIDs for both old and new values during branch/tag deletions via high-level commands like `git remote prune` and `git fetch --prune`. This patch ensures the hook receives the resolved old OID (followed by all-zeros) for these operations, matching the pre-regression behavior.

The fix is straightforward: `get_stale_heads()` already records the current OID of each stale ref in its `new_oid` field, but the pruning code discarded this value and performed unconditional deletions. The patch carries these OIDs into the deletion transaction, reusing the data collected during the stale-ref scan without additional ref reads. This preserves the performance gains from the original optimization (commit `8198907795`) while fixing the hook’s output.

The changes touch `builtin/fetch.c` and `builtin/remote.c`, introducing a small helper struct (`stale_ref`) to associate ref names with their OIDs and plumbing the OIDs through the existing transaction APIs. The test coverage is thorough, adding a new test in `t/t1416-ref-transaction-hooks.sh` that verifies the hook receives the correct old OIDs for both `git remote prune` and `git fetch --prune`, including atomic transactions.

This patch completes the series, addressing all known affected commands (`git branch -d`, `git tag -d`, `git remote prune`, and `git fetch --prune`). The fix is narrowly scoped, well-tested, and maintains backward compatibility. No performance regression is expected, and the commit message clearly explains the rationale. This looks like a clean, uncontroversial correction to an unintended behavioral change.

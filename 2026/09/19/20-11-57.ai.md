This is the second patch in a three-patch **bugfix series** restoring the correct old OID reporting in the `reference-transaction` hook for batched branch and tag deletions. The series targets a regression introduced in Git 2.31 (commit `8198907795`) where high-level commands like `git branch -d` and `git tag -d` stopped passing the resolved old OID to the hook, instead reporting all-zeros for both old and new OIDs.

This patch updates the `git branch` and `git tag` built-ins to pass the already-resolved old OIDs to `refs_delete_refs()`, which was modified in the first patch to accept an optional `oid_array` of old values. The change is minimal and surgical: both commands already resolve the old OIDs before deletion, so the fix simply reuses those values rather than introducing new ref reads. The patch adds a new test in `t/t1416-ref-transaction-hooks.sh` that verifies the hook receives the correct old OID (followed by all-zeros) when deleting branches and tags, covering both the files and reftable backends implicitly through the existing test infrastructure.

The implementation is clean and backward-compatible: the `old_oids` array is optional, so existing callers that pass `NULL` retain the unconditional deletion behavior. Memory management is handled correctly with `oid_array_clear()`, and the patch preserves the performance optimization from `8198907795` (bulk tag deletion remains at ~0.85 seconds for 10,000 packed tags). No edge cases or atomicity concerns are introduced, as the old OIDs are resolved before the transaction begins.

This looks like a well-executed follow-up to the plumbing change in the first patch. The test coverage is thorough for the immediate regression, though the commit message does not address whether other high-level commands (e.g., `git push --delete`, `git worktree remove`) might be affected by the same issue—an open question noted in the thread summary. The patch is uncontroversial and directly addresses the root cause without side effects.

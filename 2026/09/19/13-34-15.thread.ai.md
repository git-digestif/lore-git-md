Thread identity
Subject: regression in reference-transaction hook: all-zero OIDs on branch/tag deletion
Series version: v1 (three-patch bugfix series, now complete)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The reference-transaction hook, relied on by external tools (Gerrit, GitLab, CI systems) to monitor ref changes, regressed in Git 2.31: when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`), the hook receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The regression was introduced by commit `8198907795`, which optimized bulk tag deletions by replacing `delete_ref()` with `delete_refs()` but inadvertently omitted the old OID for safety-checked deletions. Direct deletion via `git update-ref -d` remains unaffected, providing the old OID followed by all-zeros. The regression persists through Git 2.55 and affects both the files and reftable backends.

Current status
Patch v1 series is now complete. The three-patch series restores the old behavior—passing the resolved old OID to the hook—while preserving the performance gains of commit `8198907795`. The first patch introduced the core plumbing change: `refs_delete_refs()` now accepts an optional `oid_array` of old OIDs, enabling callers to pass already-resolved values. The second patch updated `git branch` and `git tag` built-ins to resolve and pass the old OIDs. The third (final) patch addresses `git fetch --prune` and `git remote prune` by reusing the OIDs already collected by `get_stale_heads()` (stored in `ref->new_oid`), avoiding additional ref reads. Performance measurements confirm no regression: deleting 10,000 packed tags remains at ~0.85 seconds. The series includes comprehensive test coverage for both files and reftable backends, SHA-1/SHA-256, broken/symbolic refs, and atomic fetch pruning, with regression tests added to `t/t1416-ref-transaction-hooks.sh`. However, **Karthik Nayak has raised a substantive correctness concern**: the first patch changes `refs_delete_refs()` from unconditional deletion to conditional deletion based on the supplied old OIDs, introducing a potential race condition where the ref’s value could change between resolution and transaction execution, causing spurious transaction failures. This issue must be addressed before the series can proceed.

Key technical details
- **Subsystems touched**: refs, reference-transaction hook
- **Commands affected**: `git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune` (all now fixed in v1, pending race condition resolution)
- **Commands unaffected**: `git update-ref -d`
- **Backends affected**: files, reftable
- **Introducing commit**: `8198907795` (Git 2.31)
- **Functions involved**: `refs_delete_refs()`, `ref_transaction_delete()`, `REF_HAVE_OLD` flag, `get_stale_heads()`
- **New symbols**: `refs_delete_refs()` now accepts an optional `old_oid` parameter (as an `oid_array`); new `stale_ref` struct in `builtin/fetch.c` and `builtin/remote.c` to carry ref name and old OID
- **Old behavior (Git 2.28–2.30)**: hook received the resolved old OID followed by all-zeros on deletion
- **New behavior (Git 2.31–2.55)**: hook received all-zeros for both old and new OIDs on deletion
- **Restored behavior (v1 fix)**: hook receives the resolved old OID followed by all-zeros on deletion (pending race condition resolution)
- **On-disk format**: unchanged
- **Test coverage**: reproducer provided; regression tests added to `t/t1416-ref-transaction-hooks.sh`; covers files/reftable backends, SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning, and all affected commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git fetch --atomic --prune`)
- **Performance context**: optimization reduced bulk tag deletion time from 30 minutes to 5 seconds; v1 fix preserves this gain (~0.85 seconds for 10,000 packed tags)

Open questions and loose ends
- Should the documentation for the reference-transaction hook be updated to explicitly state that the old OID is provided for deletions, or is the restored behavior sufficiently self-documenting?
- Are there other high-level commands or workflows (e.g., `git push --delete`, `git worktree remove`) that might be affected by the same regression and should be audited? The series addresses all known affected commands, but a broader audit may be warranted.
- **New open question**: How should the race condition in `refs_delete_refs()` be resolved? The current approach (conditional deletion based on supplied old OIDs) risks transaction failures if the ref’s value changes between resolution and execution. Alternatives may include reverting to unconditional deletion (losing the safety check) or implementing a retry mechanism.

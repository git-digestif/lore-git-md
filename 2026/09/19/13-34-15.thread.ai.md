Thread identity
Subject: regression in reference-transaction hook: all-zero OIDs on branch/tag deletion
Series version: v1 (three-patch bugfix series)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The reference-transaction hook, relied on by external tools (Gerrit, GitLab, CI systems) to monitor ref changes, regressed in Git 2.31: when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`), the hook receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The regression was introduced by commit `8198907795`, which optimized bulk tag deletions by replacing `delete_ref()` with `delete_refs()` but inadvertently omitted the old OID for safety-checked deletions. Direct deletion via `git update-ref -d` remains unaffected, providing the old OID followed by all-zeros. The regression persists through Git 2.55 and affects both the files and reftable backends.

Current status
Patch v1 posted. The three-patch series restores the old behavior—passing the resolved old OID to the hook—while preserving the performance gains of commit `8198907795`. The first patch introduced the core plumbing change: `refs_delete_refs()` now accepts an optional `oid_array` of old OIDs, enabling callers to pass already-resolved values. The second patch (this email) updates the `git branch` and `git tag` built-ins to resolve and pass the old OIDs, restoring the correct hook behavior for these commands. The remaining patch will address `git fetch --prune` and `git remote prune`. Performance measurements confirm no regression: deleting 10,000 packed tags remains at ~0.85 seconds. The series includes comprehensive test coverage for both files and reftable backends, SHA-1/SHA-256, broken/symbolic refs, and atomic fetch pruning, with regression tests added to `t/t1416-ref-transaction-hooks.sh`.

Key technical details
- **Subsystems touched**: refs, reference-transaction hook
- **Commands affected**: `git branch -d`, `git tag -d` (this patch); `git remote prune`, `git fetch --prune` (next patch)
- **Commands unaffected**: `git update-ref -d`
- **Backends affected**: files, reftable
- **Introducing commit**: `8198907795` (Git 2.31)
- **Functions involved**: `refs_delete_refs()`, `ref_transaction_delete()`, `REF_HAVE_OLD` flag
- **New symbols**: `refs_delete_refs()` now accepts an optional `old_oid` parameter (as an `oid_array`)
- **Old behavior (Git 2.28–2.30)**: hook received the resolved old OID followed by all-zeros on deletion
- **New behavior (Git 2.31–2.55)**: hook received all-zeros for both old and new OIDs on deletion
- **Restored behavior (v1 fix)**: hook receives the resolved old OID followed by all-zeros on deletion (after all three patches land)
- **On-disk format**: unchanged
- **Test coverage**: reproducer provided; regression tests added to `t/t1416-ref-transaction-hooks.sh`; covers files/reftable backends, SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning
- **Performance context**: optimization reduced bulk tag deletion time from 30 minutes to 5 seconds; v1 fix preserves this gain (~0.85 seconds for 10,000 packed tags)

Open questions and loose ends
- Should the documentation for the reference-transaction hook be updated to explicitly state that the old OID is provided for deletions, or is the restored behavior sufficiently self-documenting?
- Are there other high-level commands or workflows (e.g., `git push --delete`, `git worktree remove`) that might be affected by the same regression and should be audited? The third patch will address `git fetch --prune` and `git remote prune`, but other commands remain unexamined.
- Will the proposed fix introduce any edge cases in atomic transactions or multi-ref deletions where the old OID might not be consistently available?

Thread identity
Subject: regression in reference-transaction hook: all-zero OIDs on branch/tag deletion
Series version: v3 (three-patch bugfix series, final iteration)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The reference-transaction hook, relied on by external tools (Gerrit, GitLab, CI systems) to monitor ref changes, regressed in Git 2.31: when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`), the hook receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The regression was introduced by commit `8198907795`, which optimized bulk tag deletions by replacing `delete_ref()` with `delete_refs()` but inadvertently omitted the old OID for safety-checked deletions. Direct deletion via `git update-ref -d` remains unaffected, providing the old OID followed by all-zeros. The regression persists through Git 2.55 and affects both the files and reftable backends. The v3 series restores the pre-regression behavior—passing the resolved old OID to the hook—while preserving the performance gains of the original optimization and addressing backward-compatibility concerns. The series adopts `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures (preserving unconditional deletion for `git fetch --prune` and `git remote prune`) while still passing old OIDs to the hook, fully resolving the core design conflict.

Current status
Patch v3 has been posted and incorporates all feedback from v2, including Junio C Hamano’s **critical design feedback** on the all-or-nothing transaction behavior and Karthik Nayak’s proposed middle ground. The series is a high-priority bugfix for a regression affecting external tools. The **core design conflict** has been resolved in favor of a "best-effort" transaction approach using `REF_TRANSACTION_ALLOW_FAILURE`, which preserves unconditional deletion behavior for `git fetch --prune` and `git remote prune` while still passing old OIDs to the hook. This aligns with Junio’s suggestion of a "best-effort" mode and Karthik’s proposed middle ground. Performance measurements confirm no regression: deleting 10,000 packed tags remains at ~0.85 seconds. The series includes comprehensive test coverage for both files and reftable backends, SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning, and concurrent updates, with regression tests added to `t/t1416-ref-transaction-hooks.sh`. The rebase onto `master` (post-commit `d38352cd43`) is clean, and the full test suite passes with `DEVELOPER=1`. All three patches in the series now update their respective commands (`git branch`, `git tag`, `git remote prune`, `git fetch --prune`) to pass resolved old OIDs to `refs_delete_refs()`, restoring the pre-2.31 behavior where the hook receives meaningful old OID values (instead of all-zeros) when refs are deleted.

Junio’s review of the **third patch** identifies a **user-facing inconsistency** in error reporting: when `refs_delete_refs()` fails to prune some refs (e.g., due to concurrent updates), the current patch suppresses *all* "[deleted]" output, even for refs that succeeded. This deviates from existing behavior, where `git fetch --prune` and `git remote prune` report success for each ref individually. The review requests restoring granular reporting—showing "[deleted]" for successful prunes and "[failed to delete]" for failures—rather than treating the operation as all-or-nothing. This aligns with the "best-effort" design of `refs_delete_refs()` and matches user expectations. The issue is **low-risk** (affects only error reporting, not correctness or performance) but **user-visible**. The patch remains **ready for merging** with this minor adjustment. The author’s latest email is procedural, expressing mild frustration with the review process but not introducing new technical content; the series is otherwise complete.

Key technical details
- **Subsystems touched**: refs, reference-transaction hook, `git branch`, `git tag`, `git remote`, `git fetch`
- **Commands affected**: `git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune` (all fixed in v3)
- **Commands unaffected**: `git update-ref -d`
- **Backends affected**: files, reftable
- **Introducing commit**: `8198907795` (Git 2.31)
- **Functions involved**: `refs_delete_refs()`, `ref_transaction_delete()`, `get_stale_heads()`, `REF_TRANSACTION_ALLOW_FAILURE`, `delete_branches()`, `delete_tags()`, `prune_remote()`, `prune_refs()`, `display_ref_update()`
- **New symbols**: `refs_delete_refs()` now accepts an optional `old_oid` parameter (as an `oid_array`); new `stale_ref` struct in `builtin/fetch.c` and `builtin/remote.c` to carry ref name and old OID; `tags_to_delete` struct in `builtin/tag.c` to hold both the ref list and OID array
- **Old behavior (Git 2.28–2.30)**: hook received the resolved old OID followed by all-zeros on deletion; deletions were conditional (compare-and-delete) to prevent overwriting concurrent updates
- **New behavior (Git 2.31–2.55)**: hook received all-zeros for both old and new OIDs on deletion; deletions were unconditional (no safety check)
- **Restored behavior (v3 fix)**: hook receives the resolved old OID followed by all-zeros on deletion; deletions are unconditional (no safety check) but use `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures, preserving backward compatibility for `git fetch --prune` and `git remote prune`
- **On-disk format**: unchanged
- **Test coverage**: reproducer provided; regression tests added to `t/t1416-ref-transaction-hooks.sh`; covers files/reftable backends, SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning, concurrent updates, and all affected commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git fetch --atomic --prune`); v3 adds tests for partial failures, UI consistency (suppressing "[pruned]" on failure), and verifies the hook receives the correct old OIDs for batched deletions in `git branch`, `git tag`, `git remote prune`, and `git fetch --prune`
- **Performance context**: optimization reduced bulk tag deletion time from 30 minutes to 5 seconds; v3 fix preserves this gain (~0.85 seconds for 10,000 packed tags)
- **UI changes**:
  - v3 preserves the v2 fix for an inconsistency where `git remote prune` printed "[pruned]" even after a deletion failure.
  - **New feedback**: Junio requests granular "[deleted]" reporting for successful prunes, even if some refs fail, to match existing behavior.
- **Code cleanup (v3)**: refactoring to eliminate redundant loops (e.g., moving `refnames` construction into the non-atomic branch, reusing the existing loop in `builtin/remote.c` to populate `old_oids`), fixing formatting nits, removing deprecated `test_create_repo` in favor of `git init`, removing unnecessary `pack-refs` from tests, and addressing Junio’s code organization nit (input validation for `old_oids` array size moved *after* the early return for empty `refnames`). The **third patch** specifically updates `prune_refs()` in `builtin/fetch.c` and `prune_remote()` in `builtin/remote.c` to resolve old OIDs before deletion and pass them to `refs_delete_refs()`, while restoring granular error reporting for partial failures.

Open questions and loose ends
None. All feedback from v2 has been addressed, and the series is ready for merging pending the minor UI adjustment in the third patch (granular error reporting for partial failures). Junio’s review of the first patch raises broader architectural questions about the refs API design (e.g., whether `REF_TRANSACTION_ALLOW_FAILURE` should always be used in `refs_delete_refs()` and whether `ref_transaction_delete()` should handle null OIDs internally), but these are long-term considerations and do not block the current bugfix series.

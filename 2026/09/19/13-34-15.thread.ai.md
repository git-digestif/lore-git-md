Thread identity
Subject: regression in reference-transaction hook: all-zero OIDs on branch/tag deletion
Series version: standalone bugfix (no patch series)
Originating author: Maciej Ciemborowicz
Thread type: bug report

Core problem or goal
The reference-transaction hook, used by external tools (Gerrit, GitLab, CI systems) to monitor ref changes, regressed in Git 2.31: when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`), the hook receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The regression was introduced by commit `8198907795`, which optimized bulk tag deletions by replacing `delete_ref()` with `delete_refs()` but inadvertently omitted the old OID for safety-checked deletions. Direct deletion via `git update-ref -d` remains unaffected, providing the old OID followed by all-zeros. The regression persists through Git 2.55 and affects both the files and reftable backends.

Current status
Under review. The root cause is now identified: commit `8198907795` prioritized performance (reducing deletion time for 24,000 tags from 30 minutes to 5 seconds) over hook contract compliance. The fix should restore the old behavior—passing the resolved old OID to the hook—while preserving the performance gains. No patch has been posted yet, but the author implies the solution is straightforward: modify `delete_refs()` to pass the old OID when available.

Key technical details
- **Subsystems touched**: refs, reference-transaction hook
- **Commands affected**: `git branch -d`, `git tag -d`, `git remote prune`
- **Commands unaffected**: `git update-ref -d`
- **Backends affected**: files, reftable
- **Introducing commit**: `8198907795` (Git 2.31)
- **Functions involved**: `delete_refs()`, `ref_transaction_delete()`, `REF_HAVE_OLD` flag
- **Old behavior (Git 2.28–2.30)**: hook received the resolved old OID followed by all-zeros on deletion
- **New behavior (Git 2.31–2.55)**: hook receives all-zeros for both old and new OIDs on deletion
- **On-disk format**: unchanged
- **Test coverage**: reproducer provided; no existing test failure mentioned
- **Performance context**: optimization reduced bulk tag deletion time from 30 minutes to 5 seconds

Open questions and loose ends

- Will the proposed fix (passing the old OID in `delete_refs()`) introduce any edge cases or performance regressions?

Participant positions

The regression is framed as an unintended side effect of a performance optimization, with no mention of intentional design change in the commit message.

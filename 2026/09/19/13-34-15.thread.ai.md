Thread identity
Subject: regression in reference-transaction hook: all-zero OIDs on branch/tag deletion
Series version: v3 (three-patch bugfix series, final iteration planned)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The reference-transaction hook, relied on by external tools (Gerrit, GitLab, CI systems) to monitor ref changes, regressed in Git 2.31: when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`), the hook receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The regression was introduced by commit `8198907795`, which optimized bulk tag deletions by replacing `delete_ref()` with `delete_refs()` but inadvertently omitted the old OID for safety-checked deletions. Direct deletion via `git update-ref -d` remains unaffected, providing the old OID followed by all-zeros. The regression persists through Git 2.55 and affects both the files and reftable backends. The v3 series will restore the pre-regression behavior—passing the resolved old OID to the hook—while preserving the performance gains of the original optimization and addressing backward-compatibility concerns. The series now adopts `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures (preserving unconditional deletion for `git fetch --prune` and `git remote prune`) while still passing old OIDs to the hook, fully resolving the core design conflict.

Current status
Patch v3 is planned and will incorporate all feedback from v2, including Junio C Hamano’s **critical design feedback** on the all-or-nothing transaction behavior. The series remains a high-priority bugfix for a regression affecting external tools. The **core design conflict** has been resolved in favor of a "best-effort" transaction approach using `REF_TRANSACTION_ALLOW_FAILURE`, which preserves unconditional deletion behavior for `git fetch --prune` and `git remote prune` while still passing old OIDs to the hook. This aligns with Junio’s suggestion of a "best-effort" mode and Karthik Nayak’s proposed middle ground. Performance measurements confirm no regression: deleting 10,000 packed tags remains at ~0.85 seconds. The series includes comprehensive test coverage for both files and reftable backends, SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning, and concurrent updates, with regression tests added to `t/t1416-ref-transaction-hooks.sh`. A rebase onto `master` (post-commit `d38352cd43`) is required to resolve merge conflicts.

Key technical details
- **Subsystems touched**: refs, reference-transaction hook
- **Commands affected**: `git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune` (all fixed in v3)
- **Commands unaffected**: `git update-ref -d`
- **Backends affected**: files, reftable
- **Introducing commit**: `8198907795` (Git 2.31)
- **Functions involved**: `refs_delete_refs()`, `ref_transaction_delete()`, `REF_HAVE_OLD` flag, `get_stale_heads()`, `REF_TRANSACTION_ALLOW_FAILURE`
- **New symbols**: `refs_delete_refs()` now accepts an optional `old_oid` parameter (as an `oid_array`); new `stale_ref` struct in `builtin/fetch.c` and `builtin/remote.c` to carry ref name and old OID; `refs_delete_refs()` validates that the `oid_array` size matches the refname count and skips null OIDs (treating them as no verification)
- **Old behavior (Git 2.28–2.30)**: hook received the resolved old OID followed by all-zeros on deletion; deletions were conditional (compare-and-delete) to prevent overwriting concurrent updates
- **New behavior (Git 2.31–2.55)**: hook received all-zeros for both old and new OIDs on deletion; deletions were unconditional (no safety check)
- **Restored behavior (v3 fix)**: hook receives the resolved old OID followed by all-zeros on deletion; deletions are unconditional (no safety check) but use `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures, preserving backward compatibility for `git fetch --prune` and `git remote prune`
- **On-disk format**: unchanged
- **Test coverage**: reproducer provided; regression tests added to `t/t1416-ref-transaction-hooks.sh`; covers files/reftable backends, SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning, concurrent updates, and all affected commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git fetch --atomic --prune`); v3 will add tests for partial failures and UI consistency (suppressing "[pruned]" on failure)
- **Performance context**: optimization reduced bulk tag deletion time from 30 minutes to 5 seconds; v3 fix preserves this gain (~0.85 seconds for 10,000 packed tags)
- **UI change**: v2 fixed an inconsistency where `git remote prune` printed "[pruned]" even after a deletion failure; v3 will preserve this fix
- **Code cleanup (v3)**: refactoring to eliminate redundant loops (e.g., moving `refnames` construction into the non-atomic branch, reusing the existing loop in `builtin/remote.c` to populate `old_oids`), fixing formatting nits, removing deprecated `test_create_repo` in favor of `git init`, removing unnecessary `pack-refs` from tests, and addressing Junio’s code organization nit (input validation for `old_oids` array size moved *after* the early return for empty `refnames`)
- **Input validation**: `refs_delete_refs()` validates that the `oid_array` size matches the refname count and skips null OIDs (treating them as no verification); **resolved concern**: implicit conversion of all-zero OIDs to `NULL` will be either removed or explicitly documented in v3

Open questions and loose ends
- Should the documentation for the reference-transaction hook be updated to explicitly state that the old OID is provided for deletions, or is the restored behavior sufficiently self-documenting?
- Are there other high-level commands or workflows (e.g., `git push --delete`, `git worktree remove`) that might be affected by the same regression and should be audited? The series addresses all known affected commands, but a broader audit may be warranted.
- The v3 series will need to handle the edge case of partial failures in `git fetch --prune` and `git remote prune` gracefully, ensuring the UI remains consistent (e.g., suppressing "[pruned]" for failed deletions).

- **Karthik Nayak**: raises four **substantive technical concerns** in the v2 review, all of which have been accepted by the author for v3:
  1. **Core design conflict**: The v2 series restored conditional deletion (safety check), but Karthik argued this breaks user expectations for `git fetch --prune` and `git remote prune`, which previously succeeded even when refs were concurrently updated.   2. **Implicit conversion of all-zero OIDs to `NULL`**: Karthik argued that `refs_delete_refs()` should not treat all-zero OIDs as equivalent to `NULL`, as this could mask bugs in callers. The v3 series will either remove this implicit conversion or explicitly document it.
  3. **Code cleanup**: Karthik identified redundant loops (e.g., `refnames` construction in `builtin/fetch.c`, `old_oids` population in `builtin/remote.c`), formatting nits, and test hygiene issues (deprecated `test_create_repo`, unnecessary `pack-refs`). All of these will be addressed in v3.
  4. **Merge conflicts**: v2 conflicts with `master` (commit `d38352cd43`); a rebase is planned for v3.

- **Junio C Hamano (maintainer)**: provides a **substantive review** of the first patch in v2, identifying a **critical design flaw**: the use of a single transaction for all deletions turns the operation into an all-or-nothing affair, contradicting the documented "best-effort" behavior of `refs_delete_refs()`. This would break user expectations for commands like `git fetch --prune` and `git remote prune`, where unconditional deletion is expected even if some refs are concurrently updated. Junio suggests two fixes: (1) split deletions into separate transactions, or (2) use a "best-effort" transaction mode (e.g., `REF_TRANSACTION_ALLOW_FAILURE`). The latter aligns with Karthik’s proposed middle ground and has been adopted for v3. Junio also notes a minor **code organization nit**: input validation for the `old_oids` array size should occur *after* the early return for empty `refnames`. This feedback is **high-weight** and directly addresses the core design conflict. The patch is otherwise well-motivated and technically sound, but this issue must be resolved before the series can proceed.

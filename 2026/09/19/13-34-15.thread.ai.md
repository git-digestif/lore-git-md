Thread identity
Subject: regression in reference-transaction hook: all-zero OIDs on branch/tag deletion
Series version: v4 (three-patch bugfix series, final iteration)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The reference-transaction hook, relied on by external tools (Gerrit, GitLab, CI systems) to monitor ref changes, regressed in Git 2.31: when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`), the hook receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The regression was introduced by commit `8198907795`, which optimized bulk tag deletions by replacing `delete_ref()` with `delete_refs()` but inadvertently omitted the old OID for safety-checked deletions. Direct deletion via `git update-ref -d` remains unaffected, providing the old OID followed by all-zeros. The regression persists through Git 2.55 and affects both the files and reftable backends. The v4 series restores the pre-regression behavior—passing the resolved old OID to the hook—while preserving the performance gains of the original optimization and addressing all remaining feedback. The series adopts `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures (preserving unconditional deletion for `git fetch --prune` and `git remote prune`) while still passing old OIDs to the hook, fully resolving the core design conflict.

Current status
The v4 series is now **technically complete** and ready for merging. All three patches have been posted, addressing the regression for `git branch -d`, `git tag -d`, `git remote prune`, and `git fetch --prune`. The series restores the pre-2.31 behavior where the hook receives the resolved old OID followed by all-zeros on deletion, while preserving the performance gains of the original optimization (~0.85 seconds for 10,000 packed tags). The **core design conflict** has been resolved in favor of a "best-effort" transaction approach using `REF_TRANSACTION_ALLOW_FAILURE`, which enables granular error reporting for partial failures while maintaining unconditional deletion behavior for `git fetch --prune` and `git remote prune`. The first patch modifies `refs_delete_refs()` to always use `REF_TRANSACTION_ALLOW_FAILURE` and returns failed refs via an optional `string_list` parameter. The second patch updates `git branch` and `git tag` to pass resolved old OIDs to `refs_delete_refs()`. The third (final) patch updates `prune_refs()` and `prune_remote()` to collect old OIDs from `get_stale_heads()` and handle partial failures, with UI updates to report successful deletions granularly ("[deleted]" or "[pruned]") while omitting failed refs from dangling symref checks. The series includes comprehensive test coverage for both files and reftable backends, SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning, concurrent updates, and all affected commands, with new tests added for partial prune scenarios, UI consistency, and rejected-ref handling. The rebase onto `master` (commit `3bc0341127`) is clean, and the full test suite passes with `DEVELOPER=1`.

Key technical details
- **Subsystems touched**: refs, reference-transaction hook, `git branch`, `git tag`, `git remote`, `git fetch`
- **Commands affected**: `git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune` (all fixed in v4)
- **Commands unaffected**: `git update-ref -d`
- **Backends affected**: files, reftable
- **Introducing commit**: `8198907795` (Git 2.31)
- **Functions involved**: `refs_delete_refs()`, `ref_transaction_delete()`, `get_stale_heads()`, `REF_TRANSACTION_ALLOW_FAILURE`, `delete_branches()`, `delete_tags()`, `collect_tags()`, `prune_remote()`, `prune_refs()`, `display_ref_update()`
- **New symbols**: `refs_delete_refs()` now returns failed refs via an optional `string_list` parameter; `ref_transaction_delete()` handles null OIDs internally; `struct tags_to_delete` (containing a `string_list` and `oid_array`) is used in `delete_tags()` to pass ref names and old OIDs.
- **Old behavior (Git 2.28–2.30)**: hook received the resolved old OID followed by all-zeros on deletion; deletions were conditional (compare-and-delete) to prevent overwriting concurrent updates.
- **New behavior (Git 2.31–2.55)**: hook received all-zeros for both old and new OIDs on deletion; deletions were unconditional (no safety check).
- **Restored behavior (v4 fix)**: hook receives the resolved old OID followed by all-zeros on deletion; deletions are unconditional (no safety check) but use `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures, enabling granular error reporting while preserving backward compatibility for `git fetch --prune` and `git remote prune`.
- **On-disk format**: unchanged
- **Test coverage**: reproducer provided; regression tests added to `t/t1416-ref-transaction-hooks.sh`; covers files/reftable backends, SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning, concurrent updates, and all affected commands. New tests in v4 cover:
  - Hook payloads for pruned remote refs (files/reftable, SHA-1/SHA-256).
  - UI behavior for `git remote prune` and `git fetch --prune` when a concurrent update rejects one ref but others succeed (granular "[deleted]" reporting).
  - Batched deletions for `git branch` and `git tag` (hook receives correct old OIDs).
  - Partial failures, rejected-ref handling, and UI consistency.
- **Performance context**: optimization reduced bulk tag deletion time from 30 minutes to 5 seconds; v4 fix preserves this gain (~0.85 seconds for 10,000 packed tags).
- **UI changes**:
  - v4 restores granular error reporting: `git fetch --prune` and `git remote prune` now show "[deleted]" for successful prunes and omit failed refs from dangling symref checks, matching existing behavior where each ref is reported individually.
  - Atomic fetches remain all-or-nothing, as before.

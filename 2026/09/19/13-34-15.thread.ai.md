Thread identity
Subject: regression in reference-transaction hook: all-zero OIDs on branch/tag deletion
Series version: standalone bugfix (no patch series)
Originating author: Maciej Ciemborowicz
Thread type: bug report

Core problem or goal
The reference-transaction hook, used by external tools (Gerrit, GitLab, CI systems) to monitor ref changes, has regressed in Git 2.31: when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`), the hook now receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. Direct deletion via `git update-ref -d` still works as expected, providing the old OID followed by all-zeros. The regression persists through Git 2.55 and affects both the files and reftable backends.

Current status
Under review. No prior discussion or rationale for the change has been identified; the intent behind the regression remains unclear. D. Ben Knoble has suggested using `git bisect` to identify the exact commit that introduced the regression, implying the change was likely unintentional. The author argues the behavior violates the documented contract for safety-checked deletions, where Git has already resolved the ref being deleted and should preserve the old OID.

Key technical details
- **Subsystems touched**: refs, reference-transaction hook
- **Commands affected**: `git branch -d`, `git tag -d`, `git remote prune`
- **Commands unaffected**: `git update-ref -d`
- **Backends affected**: files, reftable
- **Old behavior (Git 2.28–2.30)**: hook received the resolved old OID followed by all-zeros on deletion
- **New behavior (Git 2.31–2.55)**: hook receives all-zeros for both old and new OIDs on deletion
- **On-disk format**: unchanged
- **Test coverage**: reproducer provided; no existing test failure mentioned
- **Next investigative step**: `git bisect` to identify the introducing commit

Open questions and loose ends
- Was the change in Git 2.31 intentional or an oversight?
- If intentional, what was the rationale, and should the documentation be updated to reflect the new behavior?
- If an oversight, should the old behavior (preserving the old OID) be restored for safety-checked deletions?
- Are there other high-level commands or workflows that might be affected by the same regression?
- What commit introduced the regression, and what was its intended purpose?

Participant positions
- **Maciej Ciemborowicz (author)**: reports the regression, provides reproducer, and argues for restoring the old behavior (preserving the old OID) on the grounds that Git has already resolved the ref being deleted and the documentation allows all-zero old OIDs only for force-updates.
- **D. Ben Knoble**: suggests using `git bisect` to identify the commit that introduced the regression, implying the change was likely unintentional or undocumented. The suggestion is substantive and actionable, focusing on the next diagnostic step.

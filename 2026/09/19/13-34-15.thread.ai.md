Thread identity
Subject: regression in reference-transaction hook: all-zero OIDs on branch/tag deletion
Series version: v2 (three-patch bugfix series, now complete)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The reference-transaction hook, relied on by external tools (Gerrit, GitLab, CI systems) to monitor ref changes, regressed in Git 2.31: when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`), the hook receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The regression was introduced by commit `8198907795`, which optimized bulk tag deletions by replacing `delete_ref()` with `delete_refs()` but inadvertently omitted the old OID for safety-checked deletions. Direct deletion via `git update-ref -d` remains unaffected, providing the old OID followed by all-zeros. The regression persists through Git 2.55 and affects both the files and reftable backends. The v2 series restores the pre-regression behavior—passing the resolved old OID to the hook—while preserving the performance gains of the original optimization. The series now explicitly documents the intentional race condition trade-off: conditional deletion (compare-and-delete) restores the pre-regression safety check (from Git 2.28–2.30) where `delete_ref()` was passed the resolved OID to prevent deleting refs that were never examined by the caller. This safety check also prevents `git fetch --prune` from deleting refs updated after the stale scan.

Current status
Patch v2 series is complete. All three patches have been posted: (1) core plumbing change in `refs_delete_refs()` to accept an optional `oid_array` of old OIDs, (2) updates to `git branch` and `git tag` to collect and pass resolved old OIDs, and (3) updates to `git fetch --prune` and `git remote prune` to pass recorded old OIDs from the stale scan. The series is ready for final review. Performance measurements confirm no regression: deleting 10,000 packed tags remains at ~0.85 seconds. The series includes comprehensive test coverage for both files and reftable backends, SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning, and concurrent updates, with regression tests added to `t/t1416-ref-transaction-hooks.sh`. The **core unresolved question** remains whether the project accepts the intentional race condition trade-off (safety via conditional deletion) or prefers unconditional deletion (losing the safety check).

Key technical details
- **Subsystems touched**: refs, reference-transaction hook
- **Commands affected**: `git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune` (all fixed in v2)
- **Commands unaffected**: `git update-ref -d`
- **Backends affected**: files, reftable
- **Introducing commit**: `8198907795` (Git 2.31)
- **Functions involved**: `refs_delete_refs()`, `ref_transaction_delete()`, `REF_HAVE_OLD` flag, `get_stale_heads()`
- **New symbols**: `refs_delete_refs()` now accepts an optional `old_oid` parameter (as an `oid_array`); new `stale_ref` struct in `builtin/fetch.c` and `builtin/remote.c` to carry ref name and old OID
- **Old behavior (Git 2.28–2.30)**: hook received the resolved old OID followed by all-zeros on deletion; deletions were conditional (compare-and-delete) to prevent overwriting concurrent updates
- **New behavior (Git 2.31–2.55)**: hook received all-zeros for both old and new OIDs on deletion; deletions were unconditional (no safety check)
- **Restored behavior (v2 fix)**: hook receives the resolved old OID followed by all-zeros on deletion; deletions are conditional (compare-and-delete) to prevent overwriting concurrent updates (pending project acceptance of the trade-off)
- **On-disk format**: unchanged
- **Test coverage**: reproducer provided; regression tests added to `t/t1416-ref-transaction-hooks.sh`; covers files/reftable backends, SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning, concurrent updates, and all affected commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git fetch --atomic --prune`); v2 adds tests for concurrent updates and UI consistency (suppressing "[pruned]" on failure)
- **Performance context**: optimization reduced bulk tag deletion time from 30 minutes to 5 seconds; v2 fix preserves this gain (~0.85 seconds for 10,000 packed tags)
- **UI change**: v2 fixes an inconsistency where `git remote prune` printed "[pruned]" even after a deletion failure
- **Input validation**: `refs_delete_refs()` now validates that the `oid_array` size matches the refname count and skips null OIDs (treating them as no verification)

Open questions and loose ends
- Should the documentation for the reference-transaction hook be updated to explicitly state that the old OID is provided for deletions, or is the restored behavior sufficiently self-documenting?
- Are there other high-level commands or workflows (e.g., `git push --delete`, `git worktree remove`) that might be affected by the same regression and should be audited? The series addresses all known affected commands, but a broader audit may be warranted.
- **Core unresolved question**: Does the project accept the intentional race condition trade-off (safety via conditional deletion) or prefer unconditional deletion (losing the safety check)? The v2 series frames this as a deliberate choice to restore the pre-regression safety check, but the decision remains open for discussion.

Thread identity
Subject: regression in reference-transaction hook: all-zero OIDs on branch/tag deletion
Series version: v5 (three-patch bugfix series, final iteration)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The reference-transaction hook, relied on by external tools (Gerrit, GitLab, CI systems) to monitor ref changes, regressed in Git 2.31: when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`), the hook receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The regression was introduced by commit `8198907795`, which optimized bulk tag deletions by replacing `delete_ref()` with `delete_refs()` but inadvertently omitted the old OID for safety-checked deletions. Direct deletion via `git update-ref -d` remains unaffected, providing the old OID followed by all-zeros. The regression persists through Git 2.55 and affects both the files and reftable backends. The v5 series restores the pre-regression behavior—passing the resolved old OID to the hook—while preserving the performance gains of the original optimization. The series adopts `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures (preserving unconditional deletion for `git fetch --prune` and `git remote prune`) while still passing old OIDs to the hook, but **Patrick Steinhardt's substantive reviews now challenge the architectural soundness of this approach on two fronts**: (1) the first patch overcomplicates `refs_delete_refs()` by adding conditional logic and partial-failure handling, which should instead be implemented in callers using the lower-level transaction API, and (2) the second patch is too narrow, fixing only `git branch` and `git tag` while leaving other ref-modifying commands (e.g., `git push`, `git symbolic-ref`) unaffected. Patrick proposes resolving old OIDs at the transaction layer itself, ensuring the hook always receives the correct old OID regardless of caller. **Junio C Hamano's latest reply adds nuance to the architectural debate**, noting that while Patrick's concerns are valid, the complexity of rewriting callers to use transactions directly may not be lower than extending `refs_delete_refs()`. Junio requests clarification in the commit message about why callers cannot preserve old OIDs *before* deletion and asks to see concrete code for both approaches before deciding.

6. **Loop variable nit**: Maciej agrees to inline the `size_t i` declaration.

Key technical details
- **Subsystems touched**: refs, reference-transaction hook, `git branch`, `git tag`, `git remote`, `git fetch`, transaction system (proposed)
- **Commands affected**: `git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune` (all fixed in v5); **proposed fix would affect all ref-modifying commands** (e.g., `git push`, `git symbolic-ref`, `git update-ref`)
- **Commands unaffected**: `git update-ref -d` (remains correct)
- **Backends affected**: files, reftable
- **Introducing commit**: `8198907795` (Git 2.31)
- **Functions involved**: `refs_delete_refs()`, `ref_transaction_delete()`, `get_stale_heads()`, `REF_TRANSACTION_ALLOW_FAILURE`, `delete_branches()`, `delete_tags()`, `collect_tags()`, `prune_remote()`, `prune_refs()`, `display_ref_update()`, `ref_transaction_update()` (proposed)
- **New symbols**: `refs_delete_refs()` now returns failed refs via an optional `string_list` parameter (added in v5); `ref_transaction_delete()` retains its existing safety checks (no null-OID conversion); `struct tags_to_delete` (containing a `string_list` and `oid_array`) is used in `delete_tags()` to pass ref names and old OIDs; `struct stale_ref` (containing a `string_list` and `oid_array`) is used in `prune_remote()` and `prune_refs()` for the same purpose; `builtin/branch.c` uses a separate `oid_array` for the same purpose.
- **Old behavior (Git 2.28–2.30)**: hook received the resolved old OID followed by all-zeros on deletion; deletions were conditional (compare-and-delete) to prevent overwriting concurrent updates.
- **New behavior (Git 2.31–2.55)**: hook received all-zeros for both old and new OIDs on deletion; deletions were unconditional (no safety check).
- **Restored behavior (v5 fix)**: hook receives the resolved old OID followed by all-zeros on deletion; deletions are unconditional (no safety check) but use `REF_TRANSACTION_ALLOW_FAILURE` to allow partial failures, enabling granular error reporting while preserving backward compatibility for `git fetch --prune` and `git remote prune`.
- **Proposed behavior (Patrick's alternative)**: hook always receives the resolved old OID for every ref modification, regardless of caller or command. This would require changes to the transaction system to resolve and queue old OIDs internally.
- **On-disk format**: unchanged
- **Test coverage**: reproducer provided; regression tests added to `t/t1416-ref-transaction-hooks.sh`; covers files/reftable backends, SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning, concurrent updates, and all affected commands. New tests in v5 cover:
  - Hook payloads for pruned remote refs (files/reftable, SHA-1/SHA-256).
  - UI behavior for `git remote prune` and `git fetch --prune` when a concurrent update rejects one ref but others succeed (granular "[deleted]" reporting).
  - Batched deletions for `git branch` and `git tag` (hook receives correct old OIDs).
  - Partial failures, rejected-ref handling, and UI consistency.
  - Concurrent updates (`branch deletion rejects a concurrent update`).
- **Performance context**: optimization reduced bulk tag deletion time from 30 minutes to 5 seconds; v5 fix preserves this gain (~0.85 seconds for 10,000 packed tags). Patrick's proposed alternative would not regress performance but may require additional ref resolution overhead.
- **UI changes**:
  - v5 restores granular error reporting: `git fetch --prune` and `git remote prune` now show "[deleted]" for successful prunes and omit failed refs from dangling symref checks, matching existing behavior where each ref is reported individually.
  - Atomic fetches remain all-or-nothing, as before.
- **Build-breakage fix**: The `refs_delete_refs()` function signature was updated in patch 1/3 to include an optional `string_list` parameter for returning failed refs, and all call sites (including those in `builtin/fetch.c` and `builtin/remote.c`) were updated to use the new signature with `NULL` for the optional parameter, ensuring the series builds cleanly after each patch.

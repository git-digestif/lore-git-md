Thread identity
Subject: regression in reference-transaction hook: all-zero OIDs on branch/tag deletion
Series version: v6 (single-patch bugfix series)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The reference-transaction hook, relied on by external tools (Gerrit, GitLab, CI systems) to monitor ref changes, regressed in Git 2.31: when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`), the hook receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The regression was introduced by commit `8198907795`, which optimized bulk tag deletions by replacing `delete_ref()` with `delete_refs()` but inadvertently omitted the old OID for safety-checked deletions. Direct deletion via `git update-ref -d` remains unaffected, providing the old OID followed by all-zeros. The regression persists through Git 2.55 and affects both the files and reftable backends.

The v6 series resolves the regression by moving the fix into the transaction hook layer itself. The new design records a separate "observed old value" for updates where callers did not supply one, using this value only as hook input without setting `REF_HAVE_OLD` or constraining the update. This eliminates the need for the `failed_refs` interface, special null-OID handling, and redundant failure counting introduced in v5, while preserving the performance gains of the original optimization. The pivot addresses Patrick Steinhardt’s architectural concerns by keeping `refs_delete_refs()` as a simple wrapper for unconditional deletions and avoiding changes to its callers. The v6 approach fixes *all* ref-modifying commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git push`, `git symbolic-ref`, etc.), not just the ones addressed in v5.

Current status
The v6 series is **complete and posted as a single-patch bugfix**, rebased onto `master` (3bc0341127) and passing the full test suite with `DEVELOPER=1`. The series resolves the regression by moving the fix into the transaction hook layer, addressing Patrick Steinhardt’s architectural concerns and Junio C Hamano’s requests for clarity. Key updates since the v5 rewrite:
1. **Architectural direction**: The v6 approach resolves old OIDs on demand in the transaction hook layer, storing them in a separate field (`hook_old_oid` and `hook_old_target`) that does not influence transaction safety checks. This preserves unconditional deletion semantics and avoids changes to `refs_delete_refs()` or its callers.
2. **Clarity of intent**: The commit message documents the design rationale, including why the fix belongs in the transaction layer (to avoid overloading `refs_delete_refs()` and preserve its simplicity) and why callers cannot preserve old OIDs *before* deletion (due to the lack of a parameter in `refs_delete_refs()`).
3. **Test coverage**: The updated regression tests verify hook payloads for *all* ref-modifying commands (files/reftable, SHA-1/SHA-256), symbolic refs, concurrent updates, and UI behavior for `git remote prune` and `git fetch --prune` (granular "[deleted]" reporting). Tests confirm deletions remain unconditional even when a concurrent update occurs during the "preparing" phase.
4. **Performance**: The bulk-deletion optimization (5 seconds vs. 30 minutes for 10,000 tags) is preserved, but the on-demand resolution of old OIDs in the hook layer may introduce latency for large batches. This trade-off is acknowledged but unquantified; Patrick Steinhardt may weigh in on whether it is acceptable.
5. **API semantics**: The new design sidesteps the API semantics debate by storing hook-observed old OIDs in a separate field that does not set `REF_HAVE_OLD` or constrain the update. The documentation (`githooks.adoc`) is updated to clarify the hook’s behavior, including the distinction between the "preparing" state (where refs are not yet locked) and later phases.

Key technical details
- **Subsystems touched**: refs, reference-transaction hook (no changes to `refs_delete_refs()` or its callers). The patch modifies `refs.c` and `refs/refs-internal.h` to add `hook_old_oid` and `hook_old_target` fields to `struct ref_update`, along with logic in `resolve_transaction_hook_old_values()` to populate these fields before the "preparing" and "prepared" hook phases.
- **Commands affected**: All ref-modifying commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git push`, `git symbolic-ref`, `git update-ref`, etc.) will now receive correct old OIDs in the hook, restoring the pre-regression behavior. `git update-ref -d` remains unaffected (already correct).
- **Backends affected**: files, reftable.
- **Introducing commit**: `8198907795` (Git 2.31).
- **Functions involved**: `ref_transaction_update()`, `ref_transaction_delete()`, `resolve_transaction_hook_old_values()` (new), transaction hook layer (new logic for resolving and caching old OIDs).
- **New mechanism**: The transaction hook layer resolves and caches old OIDs for updates where callers did not supply them, storing them in `hook_old_oid` and `hook_old_target` fields that do not set `REF_HAVE_OLD` or constrain the update. This ensures the hook always receives the correct old OID without affecting transaction semantics.
- **Old behavior (Git 2.28–2.30)**: Hook received the resolved old OID followed by all-zeros on deletion; deletions were conditional (compare-and-delete) to prevent overwriting concurrent updates.
- **New behavior (Git 2.31–2.55)**: Hook received all-zeros for both old and new OIDs on deletion; deletions were unconditional (no safety check).
- **Restored behavior (v6 fix)**: Hook receives the resolved old OID followed by all-zeros on deletion for *all* ref-modifying commands, matching the pre-regression behavior.
- **On-disk format**: unchanged.
- **Test coverage**: Updated regression tests (`t/t1416-ref-transaction-hooks.sh`) verify:
  - Hook payloads for all ref-modifying commands (files/reftable, SHA-1/SHA-256).
  - UI behavior for `git remote prune` and `git fetch --prune` (granular "[deleted]" reporting).
  - Batched deletions for `git branch` and `git tag` (hook receives correct old OIDs).
  - Partial failures, rejected-ref handling, and UI consistency.
  - Concurrent updates (`branch deletion rejects a concurrent update`).
  - Symbolic refs.
  - Unconditional deletion semantics (deletions proceed even if a concurrent update occurs during the "preparing" phase).
- **Performance context**: The bulk-deletion optimization (5 seconds vs. 30 minutes for 10,000 tags) is preserved. The on-demand resolution of old OIDs in the hook layer may introduce latency for large batches, but this has not been quantified.
- **UI changes**: None (the v5 granular error reporting for `git fetch --prune` and `git remote prune` is preserved).

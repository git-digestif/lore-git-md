Thread identity
Subject: regression in reference-transaction hook: all-zero OIDs on branch/tag deletion
Series version: v6 (three-patch bugfix series, major rewrite in progress)
Originating author: Maciej Ciemborowicz
Thread type: bug report and fix

Core problem or goal
The reference-transaction hook, relied on by external tools (Gerrit, GitLab, CI systems) to monitor ref changes, regressed in Git 2.31: when a branch or tag is deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`), the hook receives all-zero object IDs for *both* the old and new OID fields, losing the previous object ID that was correctly reported in Git 2.28–2.30. The regression was introduced by commit `8198907795`, which optimized bulk tag deletions by replacing `delete_ref()` with `delete_refs()` but inadvertently omitted the old OID for safety-checked deletions. Direct deletion via `git update-ref -d` remains unaffected, providing the old OID followed by all-zeros. The regression persists through Git 2.55 and affects both the files and reftable backends.

The v6 series abandons the v5 approach of extending `refs_delete_refs()` to accept old OIDs and instead **moves the fix into the transaction hook layer itself**. The new design records a separate "observed old value" for updates where callers did not supply one, using this value only as hook input without setting `REF_HAVE_OLD` or constraining the update. This eliminates the need for the `failed_refs` interface, special null-OID handling, and redundant failure counting introduced in v5, while preserving the performance gains of the original optimization. The pivot addresses Patrick Steinhardt’s architectural concerns by keeping `refs_delete_refs()` as a simple wrapper for unconditional deletions and avoiding changes to its callers.

Current status
The v5 series was merged to `next` but **fundamental architectural concerns raised by Patrick Steinhardt and engaged by Junio C Hamano forced a major rewrite**. The v6 series is now in development, with the first patch (1/3) proposing the new transaction-layer fix. Key unresolved issues:
1. **Architectural direction**: The v6 approach moves the fix into the transaction hook layer, resolving old OIDs on demand and storing them in a separate field that does not influence transaction safety checks. This avoids overloading `refs_delete_refs()` but introduces a new challenge: the hook layer must now resolve old OIDs for large batches, which could add latency. Maciej’s latest reply does not address this trade-off, so it may surface in follow-up discussion.
2. **Scope of the fix**: The v6 approach will fix *all* ref-modifying commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git push`, `git symbolic-ref`, etc.), not just the ones addressed in v5. This aligns with Patrick’s preference for a transaction-layer solution.
3. **Clarity of intent**: Junio’s request for the commit message to explain why callers cannot preserve old OIDs *before* deletion (e.g., due to hook expectations or performance constraints) remains unaddressed. The new approach sidesteps this question by resolving old OIDs at the transaction layer.
4. **Test coverage**: The existing regression tests (added in v5) will need to be updated to cover the new implementation, but the expected hook payloads remain unchanged. The tests must verify that the hook receives correct old OIDs for all ref-modifying commands, not just the ones fixed in v5.
5. **Performance**: The v6 approach preserves the bulk-deletion optimization (5 seconds vs. 30 minutes for 10,000 tags) and avoids the overhead of per-ref resolution in callers. However, the on-demand resolution of old OIDs in the hook layer could introduce latency for large batches, which has not been quantified.

Key technical details
- **Subsystems touched**: refs, reference-transaction hook, transaction system (no changes to `refs_delete_refs()` or its callers).
- **Commands affected**: All ref-modifying commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git push`, `git symbolic-ref`, `git update-ref`, etc.) will now receive correct old OIDs in the hook, restoring the pre-regression behavior.
- **Commands unaffected**: `git update-ref -d` (remains correct).
- **Backends affected**: files, reftable.
- **Introducing commit**: `8198907795` (Git 2.31).
- **Functions involved**: `ref_transaction_update()`, `ref_transaction_delete()`, transaction hook layer (new logic for resolving and caching old OIDs).
- **New mechanism**: The transaction hook layer resolves and caches old OIDs for updates where callers did not supply them, storing them in a separate field that does not set `REF_HAVE_OLD` or constrain the update. This ensures the hook always receives the correct old OID without affecting transaction semantics.
- **Old behavior (Git 2.28–2.30)**: Hook received the resolved old OID followed by all-zeros on deletion; deletions were conditional (compare-and-delete) to prevent overwriting concurrent updates.
- **New behavior (Git 2.31–2.55)**: Hook received all-zeros for both old and new OIDs on deletion; deletions were unconditional (no safety check).
- **Restored behavior (v6 fix)**: Hook receives the resolved old OID followed by all-zeros on deletion for *all* ref-modifying commands, matching the pre-regression behavior.
- **On-disk format**: unchanged.
- **Test coverage**: Existing regression tests (added in v5) will be updated to cover the new implementation. Tests must verify:
  - Hook payloads for all ref-modifying commands (files/reftable, SHA-1/SHA-256).
  - UI behavior for `git remote prune` and `git fetch --prune` when a concurrent update rejects one ref but others succeed (granular "[deleted]" reporting).
  - Batched deletions for `git branch` and `git tag` (hook receives correct old OIDs).
  - Partial failures, rejected-ref handling, and UI consistency.
  - Concurrent updates (`branch deletion rejects a concurrent update`).
- **Performance context**: The bulk-deletion optimization (5 seconds vs. 30 minutes for 10,000 tags) is preserved. The on-demand resolution of old OIDs in the hook layer may introduce latency for large batches, but this has not been quantified.
- **UI changes**: None (the v5 granular error reporting for `git fetch --prune` and `git remote prune` is preserved).

Open questions and loose ends
1. **Performance trade-off**: The v6 approach resolves old OIDs on demand in the transaction hook layer, which could add latency for large batches. This trade-off has not been quantified or addressed in Maciej’s latest reply.
2. **Clarity of intent**: Junio’s request for the commit message to explain why callers cannot preserve old OIDs *before* deletion remains unaddressed. The new approach sidesteps this question by resolving old OIDs at the transaction layer, but the commit message should still clarify the design rationale.
3. **Test coverage**: The existing regression tests (added in v5) will need to be updated to cover the new implementation. The tests must verify that the hook receives correct old OIDs for *all* ref-modifying commands, not just the ones fixed in v5.
4. **API semantics**: The new design stores hook-observed old OIDs in a separate field that does not set `REF_HAVE_OLD` or constrain the update. This sidesteps the API semantics debate but may require documentation to clarify the distinction between "hook input" and "transaction safety checks."
5. **Concrete code comparisons**: Junio’s earlier request for concrete code comparisons between the v5 and v6 approaches remains unaddressed. The new direction avoids changes to `refs_delete_refs()`, which may simplify the decision, but a side-by-side comparison would help evaluate the trade-offs.

Key technical details
Files touched: `.gitlab-ci.yml`, `ci/install-dependencies.ps1`
Subsystems: GitLab CI, Windows MinGW build environment, Git Credential Manager
New/renamed symbols: none (CI script adjustments only)
Behavior changes: none to Git itself; the series restores CI build pipeline for Windows jobs by:
1. Introducing a `-Mingw` switch in `ci/install-dependencies.ps1` to provision the correct Rust toolchain (`gnu` target) for MinGW builds, ensuring GCC-compatible output and linker availability. The existing Rust installation for MSVC builds remains unchanged but is deferred until after the MinGW-specific block.
2. Preserving existing `.git/info/exclude` contents when creating the file, preventing silent data loss of `/git-sdk` entries added by `install-sdk.ps1`. The fix is minimal (3 lines added, 1 removed in `ci/install-dependencies.ps1`), using conditional file creation to avoid truncation.
3. Explicitly adding `/c/Rust/bin` to `PATH` in `.gitlab-ci.yml` to ensure `cargo` is accessible after the minimal SDK's login profile resets it. This patch (3/4) adds the `./ci/install-dependencies.ps1 -Mingw` call in the `before_script` phase and appends `/c/Rust/bin` to `PATH` in the `script` phase, directly resolving the "cargo: command not found" error observed in GitLab job #16576450182 (a regression introduced by Rust-enabling commit 86909a94db5d).
4. Including the `Gcc` feature (`ADDLOCAL=Rustc,Cargo,Std,Gcc`) in the Rust MSI installation when the `-Mingw` switch is used, ensuring the GNU linker (`x86_64-w64-mingw32-gcc`) is available for host executables like `build.rs`. The `Gcc` feature does not install a second GCC toolchain; it only ensures linker compatibility with the existing MinGW-provided GCC. This final patch (4/4) resolves the "cannot find `x86_64-w64-mingw32-gcc`" error observed in GitLab job #16593470275.
Additional issue (unrelated to the series): GitLab Runner 19.4.0~pre.2085.g4d3dddee introduces a `git credential reject` call during cleanup that assumes interactive use, causing CI timeouts. The issue is specific to the Runner's cleanup phase and affects only the `test:msvc-meson` job when using the problematic Runner version; older Runner 18.8.0 images are unaffected.

This is a feature patch introducing a new `fetch.shallow` configuration option. The patch targets users of shallow repositories (created with `git clone --depth`) who experience slow or hanging `git fetch` or `git pull` operations when working with repositories that have many branches. The new config, when enabled, restricts a refspec-less fetch to only the current branch's upstream, avoiding the negotiation of history for all remote branches.

The motivation is clear: in a shallow, sparsely checked-out clone of a large repository, a plain `git pull` can take minutes or hang entirely, even if the user is only working on a single branch. The patch addresses this by making the fetch operation more targeted, but keeps the behavior opt-in (defaulting to `false`) to avoid surprising users who rely on the current behavior of syncing all remote branches.

The implementation touches `builtin/fetch.c` to add the new config option and modify the refspec expansion logic, and includes thorough test coverage in a new section of `t/t5537-fetch-shallow.sh`. The tests verify that the feature works as intended: it narrows the fetch to the tracked branch, still updates `refs/remotes/<name>/HEAD` correctly, and has no effect on non-shallow repositories or fetches of non-tracked remotes. The documentation in `Documentation/config/fetch.adoc` is complete and explains the behavior, edge cases, and default value.

The patch is well-structured, with a clear commit message and a focused scope. The test coverage is particularly strong, covering not just the happy path but also edge cases like stale `HEAD` references and interactions with `fetch.followRemoteHEAD`. The choice to make this opt-in rather than automatic is sensible, as it avoids breaking existing workflows while still providing a solution for the performance issue. This looks like a thoughtful, well-crafted contribution that addresses a real pain point for users of shallow repositories.

The `git reflog expire` regression introduced in Git 2.50—where reachable and unreachable reflog entries had their default expiry times swapped—has been fully resolved. The fix, authored by Pushkar Singh and merged to `master` on June 12, 2025, restores the documented behavior: reachable entries expire after 90 days, while unreachable ones expire after 30. The regression, caused by a field-order mix-up in `reflog.h`, went unnoticed for over a year, suggesting minimal real-world impact, but the fix was deemed low-risk and uncontroversial by reviewers, including Junio C Hamano and Jeff King.

The patch included expanded test coverage in `t/t1410-reflog.sh` to verify both reachable and unreachable expiry behavior, using simulated timestamps to confirm the 90/30-day policy. Post-merge discussion between Junio and Patrick Steinhardt centered on test precision—whether to use tighter thresholds (e.g., 88/90 days for reachable entries) to better reflect the intended expiry periods. Junio ultimately agreed with Patrick’s reasoning, though the current test values (60/100 days) remain in place, as the looser thresholds avoid edge cases in `approxidate()` while still validating the core logic. No further changes are expected, and the fix is now part of the upcoming Git 2.56 release.

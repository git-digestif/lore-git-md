This is a **bugfix review** for the regression in `git commit --amend` during interactive rebase, introduced in Git 2.56-rc0. The review comes from Phillip Wood, one of the most thorough and respected reviewers on the list, and it is **substantive**—engaging with both the architectural trade-offs and the test design.

Phillip acknowledges the fix is necessary and agrees with Patrick Steinhardt’s approach of using the `MERGE_MSG` file as a proxy for whether the conflict has already been committed. He confirms the edge case (a subsequent merge/cherry-pick/revert conflict) is handled correctly by the same check. The core logic of the patch is therefore endorsed.

The review then shifts to the test: Phillip argues the new test is unnecessarily heavy, creating a fresh repository and repeating setup that already exists in an earlier test (`commit --amend is refused at a rebase conflict stop`, added by the regression commit 6257588252). He suggests simply appending two lines to that existing test—committing the conflict resolution and then amending—rather than spinning up a new test case. This would make the test suite faster and more maintainable without sacrificing coverage.

Phillip also notes, in passing, a deeper architectural issue: rebase should ideally track the original `HEAD` when it stops (`rebase-merge/stopped-head`), which would make it trivial to detect whether the user has committed since the stop. He flags this as a potential future improvement but explicitly rules it out for the 2.56-rc2 timeframe, keeping the focus on the immediate regression fix.

Overall, the review is constructive and pragmatic. It accepts the patch’s logic while suggesting a small but meaningful test improvement, and it leaves the door open for a cleaner long-term solution. The patch is now one step closer to being ready for `next`.

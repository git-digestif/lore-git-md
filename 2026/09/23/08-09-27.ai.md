This is the **core API patch** in Christian Couder’s v2 series introducing `early_scan_options()`, a new `parse-options` sub-API for early argument scanning. The patch adds the `PARSE_OPT_EARLY` flag, the `early_scan_options()` function, and comprehensive test coverage, enabling commands to safely scan for specific options before full parsing.

The implementation reuses the existing `struct option` array, eliminating the separate `early_scan_option` structure from v1 and addressing Junio’s concern about parallel abstractions. The scan is deliberately limited—ignoring short options, negated forms, abbreviations, subcommands, and aliases—to prioritize simplicity and speed. These trade-offs are clearly documented in `parse-options.h` and `api-parse-options.adoc`, and the API’s behavior is validated by `parse_options_check()` to reject invalid uses (e.g., `PARSE_OPT_EARLY` on options without long names or subcommands).

The patch touches `parse-options.c`, `parse-options.h`, `api-parse-options.adoc`, and adds a new test helper (`test-parse-options --early-scan-options`) with extensive tests in `t/t0040-parse-options.sh`. The tests cover edge cases like stuck values (`--option=value`), optional arguments, non-options, and early termination at `--` or `--end-of-options`. The implementation is clean, with no behavior changes beyond the new API, and the commit message clearly explains the design rationale and limitations.

This patch is **ready for review** and likely to land in `next` once the broader API design is settled. It is **worth attention** from maintainers of commands with hand-rolled early scans (e.g., `git bisect`, `git rev-parse`), as it provides a safer alternative once they adopt `parse-options`. The series’ focus on the `git fast-import` bugfix (patch 3/3) suggests this API has a clear, immediate use case.

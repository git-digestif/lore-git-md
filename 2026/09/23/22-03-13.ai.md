This is a bugfix series targeting the object database (ODB) transaction layer, addressing a race condition during commit when loose objects and large blobs are present with `core.fsync` batching enabled. This is the v2 update to Justin Tobler’s two-patch series, incorporating feedback from Karthik Nayak and Patrick Steinhardt.

The core issue remains unchanged: when a "large" blob (exceeding `core.bigFileThreshold`) is written to a packfile in a transaction’s temporary directory, the transaction migrates to the main ODB before the packfile is finalized, leaving it unflushed. This triggers a "No such file or directory" error during the subsequent rename operation. The fix ensures pending packfiles are flushed before transaction migration by refactoring `odb_maybe_flush_packfile()` (patch 1/2) and adding an early call to flush pending transaction packfiles in `odb_transaction_files_commit()` (patch 2/2).

Changes in v2 are minor but address specific review feedback. Patch 1/2’s commit message now correctly states that the ODB reprepare step is *not* deferred—only the packfile flush is moved earlier—resolving Patrick Steinhardt’s earlier concern about misleading wording. Patch 2/2 improves test readability by wrapping the test setup in a subshell, as Patrick suggested, and removes the inaccurate comment about checking for leftover objects in temporary locations. The test continues to verify object readability, which is the correct validation for this bug.

The series touches only `object-file.c` and adds a new test (`t/t1050-large.sh`). No new CLI options, config keys, or on-disk format changes are introduced. The fix is narrowly scoped to the ODB transaction layer, aligning with the ongoing ODB abstraction effort led by Patrick Steinhardt. The patches are small (12 lines changed, 17 lines added) and appear well-motivated, with clear reproduction steps and error output in the cover letter. The unresolved issue of `flush_packfile_transaction()` swallowing errors via `die()` remains deferred to a future series, as noted in the thread context.

Subject: submodule merge: stale delta-base cache causes "repository corrupt" or misread commits
Series version: standalone patch (bugfix)
Originating author: Guillaume Chauvel
Thread type: bug report with reproducer and proposed fix

Core problem or goal
When merging a superproject containing two submodules (A and B), Git may attempt to read a commit that exists only in submodule B from submodule A. Instead of reporting a submodule conflict, the merge either fails with "repository corrupt" or misreads the commit due to stale delta-base cache data. The root cause is a stale cache entry: when a pack is closed, its cached data may linger, and if another submodule’s pack reuses the same memory address and base offset, Git returns incorrect cached data rather than the correct object. The bug is a confirmed regression with two distinct manifestations: a "repository corrupt" failure (introduced in v2.54.0 by `bb5da75d61`) and a spurious "hash mismatch" message (introduced in v2.47.0 by `6f1e9394e2`).

Current status
Under review. The patch is a bugfix with a clear, self-contained reproducer that reliably triggers the issue in 93 out of 100 runs across two container environments. Philippe Blain’s bisection confirmed the regression window and ruled out the earlier commit-graph fix as the sole cause. Patrick Steinhardt, the author of both regression commits, has now confirmed the delta-base cache theory and committed to implementing the fix—invalidating cache entries when packs are closed. No prior versions of this patch have been posted, but the fix is expected to be a targeted, low-risk change confined to `packfile.c` or `sha1-file.c`.

Key technical details
- **Subsystems touched**: submodule merge machinery, delta-base cache (`packfile.c`, `sha1-file.c`)
- **Files likely modified**: `packfile.c` (cache invalidation logic in `close_pack()` or a dedicated helper)
- **New/renamed symbols**: none yet identified
- **Behavior change**: ensures stale delta-base cache entries are invalidated when packs are closed, preventing cross-submodule object misreads
- **On-disk format**: no changes
- **Test coverage**: reproducer script provided; no new test in `t/` yet. The bug manifests differently across platforms (Ubuntu WSL, RHEL, Alpine), suggesting memory layout or timing dependencies.
- **Regression commits**:
  - `bb5da75d61` (2026-02-16, commit-graph lookups) introduced the "repository corrupt" failure.
  - `6f1e9394e2` (2024-08-08, packfile leak fix) introduced the "hash mismatch" behavior.

Open questions and loose ends

- Potential performance impact of stricter cache invalidation (though expected to be negligible, as pack closure is rare compared to object lookups).

This is the **v5 bugfix series** for the reference-transaction hook regression, targeting the refs subsystem. The series is now **technically complete and ready for merging to `next`**, addressing all feedback from Junio, Karthik, and others. It restores the pre-2.31 behavior where the hook receives the resolved old OID (instead of all-zeros) when branches, tags, or remote refs are deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`), while preserving the performance gains of the original optimization.

The key change in v5 is the mechanical fix for the build-breakage issue identified in v4: patch 1/3 now updates *all* call sites of `refs_delete_refs()` to use the new signature with `NULL` for the optional `string_list` parameter, ensuring the series builds cleanly after each patch. The final tree remains identical to v4, preserving the restored hook behavior, granular error reporting, and performance gains. The core design conflict—balancing unconditional deletion with granular error reporting—has been resolved using `REF_TRANSACTION_ALLOW_FAILURE`, which allows partial failures while maintaining backward compatibility for `git fetch --prune` and `git remote prune`.

The series touches the refs subsystem, reference-transaction hook, and four built-in commands (`git branch`, `git tag`, `git remote`, `git fetch`). It affects both the files and reftable backends and includes comprehensive test coverage for SHA-1/SHA-256, broken/symbolic refs, atomic fetch pruning, and concurrent updates. New tests in v5 verify hook payloads for pruned remote refs, UI consistency for partial failures, and rejected-ref handling. Performance remains unaffected (~0.85s for 10k packed tags).

This is a low-risk, high-impact fix for a regression that has persisted since Git 2.31, breaking external tools (Gerrit, GitLab, CI systems) that rely on the hook. The changes are narrowly scoped to error reporting and hook payloads, with no on-disk format changes.

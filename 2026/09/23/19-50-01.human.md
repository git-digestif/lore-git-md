This is a design discussion reply in the ongoing thread about improving `git fetch` behavior in shallow repositories. Junio C Hamano, the maintainer, responds to D. Ben Knoble’s suggestion about refining the priming mechanism for the proposed matching-inspired fetch mode.

Junio clarifies a key point about the existing behavior of `git fetch <remote> <branch>`: for the past 20 years, this syntax has been treated as a "single-shot fetch" that does not create a remote-tracking branch. This design choice reflects the intent that such fetches are temporary and not meant to establish long-term tracking relationships. He warns that automatically creating remote-tracking branches in this context would break user expectations and workflows, especially for users who rely on the current behavior (e.g., fetching from a URL without a configured remote).

However, Junio acknowledges that if a remote is already configured (e.g., `second` in `git fetch second main`), some users might expect the command to create a remote-tracking branch. He suggests that this could be a reasonable enhancement but emphasizes the need for a transition plan and an escape hatch (e.g., a flag or config option) to preserve the existing single-shot behavior for users who depend on it. This reply does not propose a specific solution but highlights the tension between backward compatibility and usability improvements.

The discussion remains focused on refining the priming mechanism for the matching-inspired fetch mode, with Junio’s input underscoring the importance of preserving existing workflows while exploring incremental improvements. No objections are raised to the broader design goals, but this exchange signals that any change to `git fetch`’s behavior will require careful handling to avoid disruption.

This is a design discussion reply in the ongoing thread about improving `git fetch` behavior in shallow repositories. D. Ben Knoble chimes in from the sidelines to endorse Junio C Hamano’s proposed priming mechanism for the matching-inspired fetch mode, while suggesting a refinement: the initial `git fetch <remote> <branch>` should still perform the usual mapping to create a remote-tracking branch (e.g., `refs/remotes/<remote>/<branch>`), rather than being a no-op. This would preserve the familiar workflow where `git fetch <remote> <branch>` automatically creates the remote-tracking branch, while still requiring the user to explicitly set up the upstream relationship with `git checkout -b <local-branch> -t <remote>/<branch>` afterward.

The suggestion is minor but pragmatic: it reduces the priming step to a single `git fetch` followed by `git checkout -b`, rather than requiring an explicit refspec mapping (`<branch>:refs/remotes/<remote>/<branch>`). This aligns with the existing behavior of `git fetch` and would likely feel more intuitive to users. The refinement does not alter the core design (the matching-inspired mode would still work as described) but smooths the onboarding experience for the priming step. No objections or counterproposals have been raised yet, but the thread remains focused on refining the matching-inspired mode’s integration with `git remote add` and its default behavior in shallow repositories.

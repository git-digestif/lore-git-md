This is the **bugfix patch** in Christian Couder’s v2 series introducing the `early_scan_options()` API. It fixes a real-world issue in `git fast-import` where `--allow-unsafe-features` was silently ignored when preceded by an option that takes a separate argument (e.g., `--depth 5 --allow-unsafe-features`). The patch replaces the command’s hand-rolled early argument scan with the new `early_scan_options()` helper, ensuring consistency with `parse_options()` and eliminating the bug.

The change is straightforward and well-motivated. The commit message clearly explains the problem (the early scan stopped at the first non-option argument, missing `--allow-unsafe-features`), the solution (using `early_scan_options()` with `PARSE_OPT_EARLY`), and the trade-offs (the scan still requires the full option name, erring on the safe side). The patch updates the documentation to reflect the new behavior and adds tests covering both the bugfix (`--depth 5 --allow-unsafe-features` now works) and the safety requirement (`--allow-unsafe` is rejected).

The implementation is clean: it reuses the existing `struct option` array, marks `--allow-unsafe-features` with `PARSE_OPT_EARLY`, and introduces a minimal callback (`option_parse_early_allow_unsafe`) to set the flag. The NEEDSWORK comment is updated to clarify the remaining limitation (no abbreviations), which is documented as a deliberate design choice. Junio’s prior approval of this conversion in v1 suggests it is ready for `next`, though the broader API design (patches 1-2/3) remains under discussion.

This patch is worth attention from anyone maintaining commands with hand-rolled early argument scans, as it demonstrates a safer alternative once the command adopts `parse_options()`. The test coverage is thorough, and the change aligns with the series’ goal of reducing fragile custom parsing.

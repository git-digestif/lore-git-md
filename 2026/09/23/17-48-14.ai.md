This is a **substantive review** from Elijah Newren on Patrick Steinhardt’s regression fix for `git commit --amend` during interactive rebase. The review identifies a critical flaw in the proposed fix and outlines both short-term and long-term solutions.

Elijah points out that Patrick’s patch, which uses the existence of `MERGE_MSG` as a proxy for whether a conflict resolution has been committed, is vulnerable to a race condition: `git reset` removes `MERGE_MSG` without advancing `HEAD`, so a subsequent `git commit --amend -a` would incorrectly be allowed while the conflict remains unresolved. This reintroduces the very footgun that commit 6257588252 aimed to prevent. The review is **tested** in the sense that Elijah describes a concrete sequence (`git reset` followed by `git commit --amend -a`) that demonstrates the bug.

For the Git 2.56 release, Elijah proposes two alternatives: (1) revert commit 6257588252 entirely, deferring the fix to a later cycle, or (2) record the original `HEAD` at the point the sequencer stops (e.g., in `rebase-merge/stopped-head`) and use that as a more reliable signal for whether an amendment should be allowed. The second option is presented as a minimal, targeted fix that avoids the `MERGE_MSG` pitfall.

Beyond the immediate regression, Elijah raises a broader architectural question: whether plain `git commit` should be rejected outright during conflict resolution for sequencer-based commands (`rebase`, `am`, `cherry-pick`, `revert`), steering users toward the corresponding `--continue` commands instead. He enumerates several surprising behaviors of plain `git commit` in these contexts—such as losing the original commit message, author, and author date during `am` or rebase, and inconsistent `--abort` behavior—and argues that having the sequencer command own both the commit and the state transition would simplify the user experience. This discussion is framed as post-2.56 work, but it directly informs the design choices for the short-term fix.

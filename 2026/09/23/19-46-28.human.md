This is a **substantive review** from Jeff King (Peff) responding to Phillip Wood’s feedback on Derrick Stolee’s RFC series introducing a "safe" `strbuf` API. Peff engages with the core design questions, offering an alternative vision for what "safe" should mean in this context.

Peff agrees with Phillip that the term "safe" is misleading but goes further, arguing that the current proposal (error-returning `strbuf` functions) addresses only one narrow aspect of safety — malloc failures — while leaving other critical safety concerns unaddressed. He points out that the trace2 subsystem’s real need is not just avoiding `die()` on allocation failure but avoiding *any* dynamic allocation, because `malloc()` relies on locks and is unsafe to call from signal handlers or other low-level contexts. The current RFC does not solve this problem; it merely replaces one failure mode (`die()`) with another (error codes).

Instead, Peff proposes a fundamentally different approach: a `strbuf`-like API that operates on a *fixed-size buffer* (either a static maximum like 4KB or a per-instance limit stored in the struct). This would eliminate malloc entirely, making the API truly safe for use in signal handlers and other constrained environments. Errors would still occur (e.g., buffer overflow), but they would be deterministic and predictable, not dependent on external factors like system memory pressure. He suggests this aligns better with the trace2 use case, where robustness and predictability are more important than flexibility.

Peff also endorses Phillip’s usability concern about error checking. He agrees that requiring callers to check every `strbuf` operation for errors would be cumbersome and suggests adopting a "sticky error bit" (like C’s `stdio` functions) to defer error handling until the final result is needed. This would simplify usage in code paths where intermediate failures can be tolerated, and it would work equally well for both the error-returning and fixed-buffer approaches.

The review is constructive and forward-looking, treating the RFC as a starting point for a broader discussion about how to make Git’s core APIs more robust. Peff’s alternative proposal — a fixed-buffer `strbuf`-like API — is a significant departure from the current RFC’s direction and would require a different implementation strategy. His feedback implies that the current series, while technically sound, may be solving the wrong problem for the trace2 subsystem’s needs. The thread is now at a crossroads: whether to proceed with the error-returning API (as a stepping stone or end goal) or pivot toward Peff’s fixed-buffer design.

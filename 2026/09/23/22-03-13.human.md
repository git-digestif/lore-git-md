This is a bugfix series targeting the object database (ODB) transaction layer, addressing a race condition that occurs when committing transactions containing both loose objects and large blobs with `core.fsync` batching enabled. The v2 update incorporates feedback from the initial review, focusing on commit message clarity and test readability.

The core issue remains unchanged: when a large blob (exceeding `core.bigFileThreshold`) is written to a packfile in a transaction's temporary directory, the transaction may migrate to the main ODB before the packfile is finalized, leaving it unflushed and causing a "No such file or directory" error during the subsequent rename operation. The fix ensures pending packfiles are flushed before transaction migration by refactoring `odb_maybe_flush_packfile()` (patch 1/2) and adding an early flush call in `odb_transaction_files_commit()` (patch 2/2).

Key improvements in v2 include a corrected commit message for patch 1/2, which no longer misleadingly claims that ODB repreparation is "slightly deferred" (only the flush is moved, not the reprepare). Patch 2/2's test has been rewritten for better readability using a subshell, and an inaccurate comment about temporary directory contents has been removed. The test continues to verify object readability after commit, which is the critical correctness check.

The series is narrowly scoped to `object-file.c` and a new test in `t/t1050-large.sh`, with no on-disk format changes or new CLI/config options. The patches are small (25 lines total) and appear well-motivated, addressing a real bug with clear reproduction steps. The feedback from Karthik Nayak and Patrick Steinhardt has been fully addressed, and the series looks ready for further review. This is part of the ongoing ODB abstraction effort led by Patrick Steinhardt, making it particularly relevant for the stability of pluggable ODB backends.

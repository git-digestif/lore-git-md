This is a **bugfix** targeting the submodule merge machinery. Guillaume Chauvel reports a reproducible bug where, during a merge of a superproject containing two submodules (A and B), Git attempts to read a commit that exists only in submodule B from submodule A. The merge should report a submodule conflict, but instead either fails with "repository corrupt" or misreads the commit due to stale cache data.

The provided reproducer script initializes two submodules (A and B), each with divergent branches, then creates a superproject that merges those branches. In 93 out of 100 runs across two container environments, the merge fails with an error claiming it cannot read a commit OID that belongs to B when checking submodule A. The commit message and reproducer suggest the root cause is a stale delta-base cache entry: when a pack is closed, its cached data may linger, and if another submodule’s pack reuses the same memory address and base offset, Git may return incorrect cached data instead of the correct object.

The patch is well-motivated and includes a clear, self-contained reproducer that reliably triggers the issue. The author links to a related thread about commit-graph lookups in submodules, but this patch focuses specifically on the delta-base cache corruption. The report is factual, avoids speculation, and provides enough detail for reviewers to investigate the cache invalidation logic in `packfile.c` or `sha1-file.c`. This looks like a real, serious bug that could affect users merging superprojects with divergent submodule histories.

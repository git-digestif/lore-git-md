This is the second patch in Tamir Duberstein’s two-patch performance series that teaches `git ls-files` to reuse the untracked cache populated by `git status`. It is a targeted optimization for wildcard queries like `` `git ls-files --cached --others --exclude-standard -z -- "**/pyproject.toml"` ``, which previously walked the working tree on every invocation even when the cache was already warm.

The patch attaches the existing untracked cache to the `dir_struct` before loading excludes, then expands any collapsed directories or partial scans on demand. Crucially, it does not write the expanded cache back to the index, so the original `git status` cache and its configured mode remain untouched. For whole-tree wildcard queries without a fixed prefix, the code reads the complete cached listing and filters the results afterward, preserving directory pruning for attribute and exclude pathspecs (where a parent directory can be rejected independently of its children).

The implementation is confined to `dir.c` and `builtin/ls-files.c`; it adds a new `untracked_cache_expand` flag to `struct dir_struct` and a small helper function to recursively expand collapsed directories. The patch also includes thorough regression tests in `t/t7063-status-untracked-cache.sh` and a new performance test in `t/perf/p3010-ls-files.sh` that measures the speedup with and without the cache.

Benchmark results on macOS are compelling: a synthetic tree with 100,000 tracked files and a few untracked files improves from 361 ms to 50 ms, with directory opens dropping from 5,058 to seven. Mixed workloads (50,000 untracked files) still benefit, improving from 659 ms to 339 ms. The commit message notes that literal queries show no regression, and the tests confirm that correctness is preserved for all pathspec types, including attribute and exclude filters.

The patch looks well-crafted and addresses a real pain point for users who repeatedly query the working tree. The design is conservative—it reuses the cache only when it is safe and does not modify the on-disk state—and the test coverage is thorough. If the first patch (which fixes spurious cache invalidation) lands cleanly, this one seems likely to follow.

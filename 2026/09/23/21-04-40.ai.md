This is the first patch in a three-patch **bugfix series (v5)** targeting a regression in the reference-transaction hook. The regression, introduced in Git 2.31, causes the hook to receive all-zero OIDs when branches or tags are deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`), breaking external tools like Gerrit and GitLab that rely on the hook to monitor ref changes.

This patch **refactors `refs_delete_refs()`** to allow callers to supply an optional array of old OIDs, enabling the hook to receive the resolved old OID (instead of all-zeros) on deletion. The function now uses `REF_TRANSACTION_ALLOW_FAILURE` to support best-effort deletion, ensuring one failure does not block independent refs in the batch. Callers can also request a list of failed refs for granular error reporting. The patch updates all call sites (e.g., `bisect.c`, `builtin/branch.c`, `builtin/fetch.c`) to use the new signature, fixing the build-breakage issue identified in v4.

Key changes:
- **New parameters**: `refs_delete_refs()` now accepts `old_oids` (parallel to `refnames`) and `failed_refs` (to return rejected updates).
- **Behavior**: Non-null OIDs in `old_oids` trigger a compare-and-delete check; null OIDs allow unconditional deletion (for broken refs).
- **Error handling**: Uses `REF_TRANSACTION_ALLOW_FAILURE` to enable partial failures, with a rejection handler to populate `failed_refs`.
- **Backward compatibility**: All call sites are updated to pass `NULL` for the new parameters, preserving existing behavior where old OIDs are not provided.

The patch is **low-risk and narrowly scoped**, touching only the refs API and its callers. It lays the groundwork for the next two patches, which restore the pre-regression hook behavior for `git branch`, `git tag`, and remote pruning. The series is technically complete, addresses all prior feedback, and is ready for merging to `next`. Test coverage is comprehensive, including edge cases like broken refs and concurrent updates.

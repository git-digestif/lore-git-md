This thread is about a regression in Git 2.56-rc0 that prevents `git commit --amend` from working during an interactive rebase after resolving a conflict. The issue was introduced by commit 6257588252, which added a safety check in the sequencer to block amendments during conflict resolution. Patrick Steinhardt proposed a fix that restores the ability to amend by checking for the presence of `MERGE_MSG`, but Elijah Newren has now identified a critical flaw in this approach: it can be bypassed by running `git reset` before amending, which removes `MERGE_MSG` without resolving the conflict, potentially reintroducing the original footgun the safety check was meant to prevent.

The discussion has shifted toward release management and design. Junio C Hamano has suggested reverting the regressing commit entirely for Git 2.56, deferring both the fix and the broader architectural question until later. Elijah Newren offers two alternatives for the short term: either revert the commit or record the original `HEAD` at the point the sequencer stops (e.g., in `rebase-merge/stopped-head`) as a more reliable signal for whether an amendment should be allowed. Beyond the immediate fix, Elijah raises a larger question about whether plain `git commit` should be rejected outright during conflict resolution for sequencer-based commands, arguing that this would simplify the user experience and avoid inconsistent behaviors.

Key participants include Patrick Steinhardt (the patch author), Phillip Wood (who reviewed the patch and raised architectural concerns), Junio C Hamano (who favors reverting the regressing commit), and Elijah Newren (who identified the race condition and proposed alternatives). The thread is now focused on deciding the best path forward for Git 2.56, with the broader design discussion deferred. No version of the fix has been merged yet, and the regression remains unresolved for the upcoming release.

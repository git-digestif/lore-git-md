This thread is about a regression fix for `git commit --amend` during interactive rebase, introduced in Git 2.56-rc0. The issue prevents users from amending a commit created after resolving a conflict in an interactive rebase, due to an overzealous safety check in commit 6257588252. Patrick Steinhardt posted a single-patch v1 to address the regression, modifying `sequencer.c` to check for the presence of `MERGE_MSG` as a proxy for whether a conflict resolution has already been committed, allowing amendments to proceed. The fix includes a regression test in `t/t3404-rebase-interactive.sh`.

Phillip Wood reviewed the patch, accepting the core logic but suggesting a more targeted test modification to avoid introducing a new test case. He also raised an architectural question: whether the same safety check that broke `git rebase --interactive` might also affect `git cherry-pick`, `git merge`, and `git revert`, since the problematic commit was written generically for all sequencer-based operations. This is a proactive design consistency check rather than a reported bug, but it broadens the scope of the discussion. The thread remains focused on the 2.56 release cycle, with no new code or test changes proposed yet. The fix is still under review, with Patrick acknowledging the indirectness of the `MERGE_MSG` check and inviting suggestions for a cleaner approach.

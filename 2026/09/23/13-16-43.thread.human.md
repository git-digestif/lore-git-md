This thread is about fixing a regression in `git commit --amend` during interactive rebase, introduced in Git 2.56-rc0. The issue stems from an overzealous safety check in commit 6257588252 that prevents amending commits created after resolving conflicts, breaking established workflows.

The maintainer (Junio) and key reviewers (Elijah Newren, Patrick Steinhardt) have agreed to revert the regressing commit entirely for the 2.56 release cycle, prioritizing stability over partial fixes. The revert is the immediate action item, though the code hasn't been posted yet. The broader architectural question—whether to outright reject plain `git commit` during conflict resolution for sequencer-based commands like `rebase` and `cherry-pick`—has been deferred until after Git 2.56.

Elijah recently proposed a concrete future direction: extending `git commit` to consume a new pseudoref (`REBASE_HEAD`), similar to how it handles `CHERRY_PICK_HEAD`. This would preserve authorship information during interactive rebase without requiring manual flags, but it’s acknowledged as a post-3.0 effort due to its complexity. For now, the focus remains on reverting the regression for the upcoming release.

This thread is about a regression in `git commit --amend` during interactive rebase, introduced in Git 2.56-rc0. The issue stems from an overzealous safety check in `sequencer.c` that prevents amending commits after conflict resolution, breaking established workflows where users split commits or reword messages before continuing.

The maintainer (Junio) and key reviewers (Elijah Newren, Patrick Steinhardt) have agreed to revert the regressing commit entirely for the 2.56 release cycle, prioritizing stability over partial fixes. The revert is planned for 2.56-rc2 but hasn't been coded or merged yet. The root cause—a race condition in the `MERGE_MSG` check—remains unresolved, and a longer-term architectural discussion about rejecting plain `git commit` during conflict resolution (steering users toward `--continue`) is deferred until after Git 2.56.

Jiang Xin, the l10n coordinator, recently chimed in to handle a localization housekeeping detail: the revert will reintroduce a translatable error message previously removed from `.po` files, and he’ll ensure translations are updated accordingly. This doesn’t affect the technical fix but keeps the localization effort in sync. The broader question of how to handle authorship preservation during interactive rebase (e.g., via a new `REBASE_HEAD` pseudoref) is still on the table but won’t block the immediate revert.

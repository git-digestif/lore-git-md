This thread is about fixing a regression in `git commit --amend` during interactive rebase, introduced in Git 2.56-rc0. The issue stems from an overzealous safety check in `sequencer.c` that prevents amending commits created after conflict resolution, breaking established workflows.

The maintainer (Junio) and key reviewers (Elijah Newren, Patrick Steinhardt) have agreed to revert the regressing commit entirely for the Git 2.56 release cycle, prioritizing stability over partial fixes. The revert is the immediate next step, though the code hasn’t been posted yet. The broader architectural question—whether to outright reject plain `git commit` during conflict resolution for sequencer-based commands—has been deferred until after Git 2.56, as it would require major changes to unify behavior across `rebase`, `am`, `cherry-pick`, and `revert`.

Patrick’s latest email clarifies a speculative idea about preserving authorship during conflict resolution but confirms it’s not a viable short-term solution. The thread remains focused on the revert, with no new technical constraints or open questions introduced. The only unresolved edge case—Phillip Wood’s concern about test coverage for subsequent conflicts—is acknowledged but not blocking the fix.

The thread is about fixing a regression in `git commit --amend` during interactive rebase, introduced in Git 2.56-rc0. The issue stems from an overzealous safety check in `sequencer.c` that prevents amending commits after conflict resolution, breaking a common workflow where users split commits or reword messages before continuing the rebase.

The maintainer, Junio C Hamano, along with Patrick Steinhardt (the patch author) and Elijah Newren (a key reviewer), have agreed to revert the regressing commit entirely for the Git 2.56 release cycle. This decision prioritizes stability over partial fixes, as the targeted fix was found to have a race condition with `git reset`. The revert is now the immediate focus, with no evidence of the fix or revert being merged yet.

The broader architectural question—whether plain `git commit` should be rejected during conflict resolution for sequencer-based commands like `rebase`, `am`, `cherry-pick`, and `revert`—has been deferred until after Git 2.56. Junio emphasized that allowing `git commit` (and thus `--amend`) during interactive rebase is a valuable and widely used capability, and breaking it would require strong justification. Elijah had proposed an alternative design (recording the original `HEAD` in `rebase-merge/stopped-head`) to reliably determine when an amendment is safe, but this remains unaddressed for now.

Phillip Wood, another reviewer, had suggested refining the test coverage but agreed the fix should behave correctly even in edge cases. The thread is now converging on the revert as the next step, with deeper design discussions postponed.

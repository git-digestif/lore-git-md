This is the **bugfix patch** in Christian Couder’s v2 series introducing the `early_scan_options()` API. It converts `git fast-import` to use the new API, fixing a real bug where `--allow-unsafe-features` was silently ignored when preceded by an option that takes a separate argument (e.g., `--depth 5 --allow-unsafe-features`).

The patch replaces `git fast-import`’s hand-rolled early argument scan with `early_scan_options()`, ensuring the scan agrees with `parse_options()` on which options consume arguments. The conversion is straightforward: `--allow-unsafe-features` is marked with `PARSE_OPT_EARLY`, and the early scan now uses the same `struct option` array as the full `parse_options()` call. The implementation deliberately errs on the safe side by requiring the option to be spelled in full (no abbreviations), matching the API’s documented limitations.

The commit message clearly explains the bug, the fix, and the trade-offs. The test coverage is thorough: `t/t9300-fast-import.sh` adds two new tests verifying that `--allow-unsafe-features` is recognized when preceded by a value (e.g., `--depth 5`) and that abbreviations (e.g., `--allow-unsafe`) are rejected. The documentation (`git-fast-import.adoc`) is updated to reflect the new behavior, removing outdated caveats about option ordering and clarifying the spelling requirement.

Junio’s prior approval of this conversion in v1 suggests it is ready for `next`. The patch is clean, well-tested, and addresses a real-world issue without introducing new edge cases. It is the most compelling part of the series and the primary motivation for the API refactoring. Maintainers of other commands with hand-rolled early scans (e.g., `git bisect`, `git rev-parse`) may want to watch this conversion as a template for future adoption.

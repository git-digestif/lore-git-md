This thread is about a critical bug in Git’s submodule merge machinery that can cause "repository corrupt" errors or misread commits due to a stale delta-base cache. The issue arises when merging a superproject with two submodules: Git may attempt to read a commit from the wrong submodule, leading to corruption or hash mismatches. The root cause was identified as stale cache entries lingering after packs are closed, which can be reused if another pack occupies the same memory address.

Guillaume Chauvel reported the bug with a reliable reproducer, and Philippe Blain confirmed its regression window, pinpointing two commits (`bb5da75d61` and `6f1e9394e2`) as the culprits. Patrick Steinhardt, the author of those commits, has now posted a fix: a one-line change in `packfile.c` to clear the delta-base cache when packs are closed. The fix is minimal, low-risk, and addresses the exact mechanism behind the corruption. It has no impact on on-disk formats or performance, as pack closure is rare compared to object lookups.

The patch is under review and is expected to be uncontroversial, given Patrick’s direct involvement and the clear technical rationale. The main open question is whether to add a regression test to Git’s test suite, though the existing reproducer already provides strong verification. The fix resolves a confirmed regression with two distinct manifestations, making it a high-priority bugfix for the upcoming release cycle.

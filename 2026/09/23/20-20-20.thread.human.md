This thread is about a subtle but serious bug in Git’s submodule merge machinery: when merging a superproject with two submodules, Git may misread commits due to stale delta-base cache entries, leading to either a "repository corrupt" error or silent data corruption. The issue was reported by Guillaume Chauvel, who provided a reliable reproducer and a proposed fix targeting the cache invalidation logic in `packfile.c` or `sha1-file.c`.

Philippe Blain’s recent review confirms the bug’s reproducibility and traces its regression window using `git bisect`. The problem manifests in two distinct ways: a "repository corrupt" failure introduced in Git v2.54.0 (linked to a commit-graph lookup patch by Patrick Steinhardt) and a spurious "hash mismatch" message appearing since v2.47.0 (tied to a packfile leak fix). The delta-base cache theory—stale entries persisting after pack closure—remains the leading explanation, especially given the bug’s platform-dependent behavior (e.g., Ubuntu WSL vs. RHEL/Alpine containers). Philippe’s work narrows the focus to the cache invalidation logic, though no revised patch has been posted yet.

The thread is under active review, with high confidence in the root cause. The next steps will likely involve refining the fix to address the bisect results and adding a test to the Git test suite to prevent regressions. The bug’s severity—silent corruption or abrupt merge failures—makes this a priority for the upcoming release cycle.

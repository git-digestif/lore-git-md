This thread is about a critical bug in Git’s submodule merge machinery that can cause either a "repository corrupt" error or silent misreading of commits when merging a superproject with two submodules. The issue, confirmed as a regression introduced in Git v2.47.0 and worsened in v2.54.0, stems from a stale delta-base cache: when a packfile is closed, its cached data lingers, and if another submodule’s pack reuses the same memory address and offset, Git returns incorrect cached data instead of the correct object.

Guillaume Chauvel reported the bug with a reliable reproducer (triggering the issue in 93 out of 100 runs across different environments), and Philippe Blain bisected the regression to two commits by Patrick Steinhardt, who has now confirmed the root cause. Patrick, the author of the problematic commits, acknowledges the delta-base cache theory and plans to fix it by invalidating cache entries when packs are closed—a targeted change in `packfile.c` or `sha1-file.c` with no expected performance impact or on-disk format changes.

The fix is uncontroversial and high-priority, given the severity of the bug (data corruption or silent misreads). The next step is Patrick’s patch, which should resolve the issue cleanly. The thread hasn’t yet addressed whether a regression test will be added to Git’s test suite, but the provided reproducer makes verification straightforward. No objections or alternative explanations have been raised, so this looks like a straightforward bugfix with a clear path to resolution.

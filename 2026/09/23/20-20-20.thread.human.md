This thread is about a critical bug in Git’s submodule merge machinery. Guillaume Chauvel has identified and reproduced a scenario where, during a superproject merge involving two submodules (A and B), Git incorrectly attempts to read a commit that exists only in submodule B from submodule A. Instead of reporting a submodule conflict, the merge either fails with a "repository corrupt" error or misreads the commit due to stale delta-base cache data. The issue is highly reproducible—occurring in 93 out of 100 test runs across two container environments—and the provided reproducer script makes it easy to verify.

The root cause appears to be a stale delta-base cache entry: when a pack is closed, its cached data may linger, and if another submodule’s pack reuses the same memory address and base offset, Git may return incorrect cached data. The patch is well-documented, with a clear explanation of the problem and a focus on the cache invalidation logic in `packfile.c` or `sha1-file.c`. While the author references a related thread about commit-graph lookups in submodules, this report is narrowly scoped to the delta-base cache corruption.

So far, the thread is just the initial bug report, so there’s no review feedback or discussion yet. This looks like a serious issue that could affect users merging superprojects with divergent submodule histories, and it’s likely to attract attention from maintainers and contributors familiar with the submodule or packfile subsystems. If you’re working with submodules, this is one to watch.

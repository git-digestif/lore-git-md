This is a design discussion reply in the ongoing thread about improving `git fetch` behavior in shallow repositories. Phillip Wood responds to Junio C Hamano’s proposal for a "matching-inspired" fetch mode, raising a critical chicken-and-egg problem: the proposed mode relies on local branches having their `@{upstream}` set to the remote being fetched, but `git branch --set-upstream-to` fails if the upstream branch does not already exist. This makes the mode unusable for newly added remotes, where no local branches yet track the remote’s branches.

Phillip acknowledges the potential usefulness of the mode for *existing* remotes but argues it cannot solve the original problem of `git remote add` creating wildcard refspecs in shallow repositories. The discussion remains focused on refining the two alternative approaches: (1) modifying `git remote add` to default to narrower refspecs (e.g., fetching only the remote’s default branch) and (2) Junio’s matching-inspired fetch mode for `git fetch`. Phillip’s feedback highlights that these approaches address different use cases and may need to coexist, with the narrower-refspec solution handling the initial setup of new remotes and the matching-inspired mode improving subsequent fetches.

No code has been written for either approach, and the thread continues to explore how to integrate them. Key technical details include the proposed refspec syntax (`:` or `+:`) for the matching-inspired mode, the reliance on local tracking relationships, and the need to handle edge cases like missing upstream branches. The discussion also touches on backwards compatibility, as both solutions must preserve existing workflows for non-shallow repositories. Phillip’s reply is substantive, identifying a fundamental limitation in Junio’s proposal and reinforcing the need for a multi-part solution.

This is the second patch in the **v5 bugfix series** for the reference-transaction hook regression, targeting `git branch` and `git tag` deletions. The patch restores the pre-2.31 behavior where the hook receives the resolved old OID (instead of all-zeros) when branches or tags are deleted in bulk, while preserving the performance gains of the original optimization.

The change is straightforward: both `git branch -d` and `git tag -d` already resolve the old OIDs before deletion, but the batched deletion introduced in commit `8198907795` dropped them. This patch passes those resolved OIDs to `refs_delete_refs()`, enabling the hook to report the correct old value and restoring the original race protection (rejecting deletions if the ref changes concurrently). The implementation adds a new `struct tags_to_delete` in `builtin/tag.c` to bundle the ref names and old OIDs, while `builtin/branch.c` uses a separate `oid_array` for the same purpose. Both commands now call `refs_delete_refs()` with the old OIDs, and the hook payloads are verified in a new test case (`hook gets old values for batched branch/tag deletion`).

The patch also adds a test for concurrent updates (`branch deletion rejects a concurrent update`), ensuring the safety check works as intended. The changes are minimal and focused: no new ref reads are added, and the on-disk format remains unchanged. The test coverage is thorough, verifying both files and reftable backends (though the latter is tested in patch 3/3).

This is a **well-motivated, low-risk fix** that directly addresses the regression without introducing new complexity. The commit message clearly explains the problem, the solution, and the trade-offs (performance vs. correctness). The patch integrates cleanly with the rest of the series, and all prior feedback (including Junio’s and Karthik’s concerns about granular error reporting and API consistency) has been addressed in the v5 iteration. A strong candidate for merging.

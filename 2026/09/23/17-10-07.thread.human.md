This thread tracks a three-patch series by Tamir Duberstein that teaches `git ls-files` to reuse the untracked cache populated by `git status`, aiming to cut directory traversal overhead in common workflows. The series is at version 3, which addressed earlier feedback by expanding scope to share the cache between `git status -unormal` and `-uall`, fixing an ignore-file hash inconsistency, and adding refined lock handling and tests for the `ls-files` integration.

The most significant recent development came from reviewer Aniket Gupta, who identified a concurrency regression in patch 3: when `core.untrackedCache=true` and the cache is cold, the patch holds `index.lock` for the entire directory scan, causing concurrent `git add` commands to fail. Duberstein has now confirmed this issue and announced that version 4 will resolve it by acquiring the lock only after `fill_directory()` completes, using a new `repo_lock_and_update_index_if_able()` helper. He notes that commit 6b6d1d56eb, which landed on `master` after v3 was sent, now allows the optional index write to detect concurrent modifications via stat data even when `index.skipHash` is enabled, removing the previous justification for early locking. He has also removed the test that expected the old behavior and added coverage verifying that concurrent index updates succeed with both `index.skipHash` settings.

The series remains under review awaiting v4, with the concurrency concern now addressed in the author's response but not yet landed in a new patch version.

Tamir Duberstein's three-patch v3 series to let `git ls-files` reuse the untracked cache remains under active review, with the first two patches addressing ignore-file hash consistency and cache sharing between `git status` modes respectively. The third patch, which teaches `git ls-files --others` to read and update the untracked cache, has now drawn a substantive technical objection from Aniket Gupta regarding concurrency safety. Gupta identifies a regression where, when `core.untrackedCache=true` and the cache is cold, the patch holds `index.lock` for the entire directory scan, causing a concurrent `git add` to fail with "Unable to create '.git/index.lock': File exists" -- behavior that does not occur on `master`, where `cmd_status()` only takes the lock after collecting results. He questions whether the lock truly needs to be acquired before reading the index, suggesting that `verify_index_from()` appears to handle the `index.skipHash` case correctly if locking occurs after `fill_directory()` completes, with only the `t7519` skiphash test apparently relying on the earlier locking behavior.

The series otherwise remains self-contained, modifying `dir.c`, `builtin/ls-files.c`, and related test files without changing on-disk formats, and benchmarks show a 7.3x speedup for wildcard queries on large trees. However, Gupta's review introduces an open question about lock scope and concurrent operation safety that the author has not yet addressed, leaving the third patch's merge-readiness contingent on resolving whether the lock can be deferred until after the directory read.

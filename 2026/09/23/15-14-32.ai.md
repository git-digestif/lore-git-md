This is a design-discussion follow-up in the now-consensus-driven effort to address slow `git fetch` operations in shallow repositories. The thread has abandoned the original `fetch.shallow` config patch in favor of two alternative approaches: (1) modifying `git remote add` to default to narrower refspecs in shallow repositories, and (2) introducing a matching-inspired fetch mode for `git fetch`. This email focuses on the first approach, specifically how `git remote add` should determine the narrower refspec without making a network call to the remote.

Phillip Wood proposes two refinements to the narrower-refspec idea. First, without the `--fetch` flag, `git remote add` would **refuse to add a new remote in a shallow repository unless the user explicitly specifies which branches to track** (e.g., via `--track`). This avoids the problem of constructing a refspec without knowing the remote’s branches, but shifts the burden to the user. Second, with `--fetch`, the command would **query the remote’s default branch** (presumably via `HEAD`) and fetch only that branch by default. Phillip also suggests a heuristic: if all existing remotes in the repository fetch the same branch(es), `git remote add` could copy those refspecs for the new remote.

The proposal is pragmatic but introduces friction for users of shallow repositories, who would now need to explicitly specify branches when adding a remote. This trade-off is intentional: Phillip argues it is better than the current behavior, where `git remote add` silently adds a wildcard refspec that makes `git fetch` unusably slow. The discussion remains pre-implementation, with no code written yet. Key open questions include whether the `--fetch` flag should be the default behavior, how to handle stale or missing `HEAD` information, and whether the heuristic of copying existing refspecs is robust enough for real-world workflows.

This is a **bugfix and user-experience improvement** targeting the object-name and shallow-clone subsystems. The patch (v3) adds a new advice message (`advice.shallowHistory`) that explains why `<rev>~N` or `<rev>^N` fails in a shallow clone and suggests the exact `git fetch --deepen=<n>` command needed to resolve it.

The core problem is that when a user in a shallow clone tries to access an ancestor not present locally (e.g., `git show HEAD~20`), Git emits a generic "is not a commit" error with no indication that the repository is shallow or how to fetch more history. The new advice fires only when the walk stops exactly at a recorded shallow boundary, ensuring it doesn’t misfire on short histories that aren’t truncated. The suggested `--deepen` value is context-aware: for `<rev>~N`, it accounts for history already present (e.g., if the repo is `--depth=3`, asking for `~5` suggests `--deepen=3`); for `<rev>^N`, it always suggests `--deepen=1` because a shallow boundary commit has no parents recorded locally.

Key improvements in v3:
- **Scope narrowed**: The `git log -<n>`/`--since` integration (which attempted to detect silent truncation) is dropped entirely, per Junio’s feedback that the detection logic was fundamentally flawed. The patch now focuses solely on the `<rev>~N`/`<rev>^N` syntax, which remains uncontroversial and viable.
- **Bug fixed**: Chained carets (e.g., `<rev>^^^`) no longer print the advice twice. The quiet flag is now threaded through the inner lookup in `get_parent()` to ensure it stays quiet when the outer resolution asked it to.
- **Documentation clarity**: The commit message and advice text now consistently use `<rev>` (not `<ref>`) and correct syntax per `gitrevisions(7)`.
- **Remote/branch detection**: The suggested command now reverse-maps through the remote’s configured refspec (via `remote_find_tracking`) instead of assuming branches live at `refs/remotes/<remote>/<branch>`.

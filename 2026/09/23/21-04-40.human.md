This is the first patch in a three-patch bugfix series (v5) that restores the pre-2.31 behavior of the reference-transaction hook when branches or tags are deleted. The regression, introduced in Git 2.31 by commit `8198907795`, caused the hook to receive all-zero OIDs for both old and new fields on deletion, breaking external tools like Gerrit and GitLab that rely on the old OID to track ref changes.

This patch modifies `refs_delete_refs()` to accept an optional array of old OIDs, allowing callers to preserve resolved values for the hook. It also switches to `REF_TRANSACTION_ALLOW_FAILURE` to enable granular error reporting—one failure no longer blocks the entire batch. The function now returns failed refs via an optional `string_list`, which later patches use to restore UI consistency for `git fetch --prune` and `git remote prune`. All call sites (in `bisect.c`, `builtin/branch.c`, `builtin/fetch.c`, `builtin/remote.c`, and `builtin/tag.c`) are updated to use the new signature, fixing the build-breakage issue identified in v4.

The changes are mechanical and narrowly scoped to the refs API. The patch preserves the performance gains of the original optimization while addressing the core design conflict: unconditional deletion with best-effort granularity. Test coverage is added in later patches, but this one ensures the plumbing works correctly. The series is ready for `next` and addresses all prior feedback from Junio and Karthik.

This is a design discussion follow-up in the now-consensus-driven effort to fix slow fetches in shallow repositories. The original `fetch.shallow` config patch has been abandoned in favor of preventing the problem at its source: wildcard fetch refspecs in shallow repositories.

Phillip Wood proposes a concrete workflow for `git remote add` in shallow repositories. The core idea is to make the command refuse to add a new remote without explicit branch tracking information, unless the user supplies the `--fetch` flag. Without `--fetch`, the user would need to specify which branches to track (via `--track`), or the command could copy refspecs from existing remotes if they all fetch the same branch. With `--fetch`, the command would query the remote for its default branch and fetch only that branch by default. This approach avoids network calls unless the user explicitly opts into them, and it prevents the performance pitfall of wildcard refspecs in shallow repositories.

The proposal is pragmatic and addresses the key open question from the thread: how to determine the narrower refspec without a network call. It also preserves user control while nudging toward safer defaults. No code has been written yet, but this email advances the design discussion toward a concrete implementation plan. The next steps would likely involve prototyping this behavior and testing edge cases, such as stale remote `HEAD` or repositories with no existing remotes.

This is a substantive review of Patrick Steinhardt’s regression fix for `git commit --amend` during interactive rebase. Elijah Newren identifies a critical flaw in the proposed solution: the patch’s reliance on the `MERGE_MSG` file as a proxy for whether a conflict has been committed is unsafe. Specifically, `git reset` can remove `MERGE_MSG` without advancing `HEAD`, which would re-enable the very footgun the original commit (6257588252) aimed to prevent. This undermines the patch’s correctness and suggests it needs rethinking before merging.

Elijah proposes two short-term alternatives for Git 2.56: revert the regressing commit entirely (restoring the pre-2.56 behavior) or record the original `HEAD` at the conflict stop point (e.g., in a new `rebase-merge/stopped-head` file) and allow amendments only after `HEAD` advances. The latter approach would address the regression while preserving the safety check, though it adds complexity to the rebase state tracking. He also raises a broader architectural question: whether plain `git commit` should be disallowed entirely during conflict resolution for rebase, am, cherry-pick, and revert, directing users to the corresponding `--continue` commands instead. This would simplify the state machine but represents a significant workflow change.

The review is constructive and pragmatic, focusing on correctness and maintainability rather than stylistic concerns. Elijah’s feedback is well-motivated, citing specific edge cases (e.g., `git reset` behavior) and inconsistencies in how plain `git commit` interacts with different sequencer backends. His suggestion to record `stopped-head` is a concrete improvement over the current patch, though it would require additional testing to ensure it doesn’t introduce new edge cases. The broader proposal to disallow plain `git commit` during conflict resolution is framed as post-2.56 work, aligning with Junio’s preference to defer architectural changes until after the release.

This is a bugfix patch targeting the rebase subsystem, specifically addressing a regression introduced in Git 2.56-rc0.

The patch fixes an overly restrictive behavior in `git commit --amend` during interactive rebases. A recent commit (6257588252) made `git commit` refuse to amend when it detects a conflict resolution state, aiming to prevent a common footgun where users accidentally amend the wrong commit. However, this restriction persisted even after the user had already committed the resolved conflict, preventing legitimate amendments to the newly created commit. Patrick Steinhardt identifies this as a regression that should be fixed before the 2.56 release.

The fix itself is small: it modifies `sequencer.c` to check for the existence of the `MERGE_MSG` file as a proxy for whether the user has already committed the conflict resolution. If `MERGE_MSG` exists alongside the rebase state files, the code no longer treats the situation as an ongoing conflict, allowing amendments to proceed. The commit message acknowledges this approach is somewhat indirect ("fishy") but argues it's the best available signal given the current rebase state tracking.

The patch includes a new test in `t/t3404-rebase-interactive.sh` that exercises the scenario: starting an interactive rebase, causing a conflict, resolving it, committing the resolution, and then successfully amending that commit. This test provides clear regression protection for the fixed behavior.

Patrick's cover letter expresses dissatisfaction with the solution's indirectness but couldn't identify a better approach. This suggests the patch is a pragmatic fix rather than a perfect architectural solution, and the mailing list may see suggestions for alternative implementations. The fix is well-motivated, clearly explained, and comes with test coverage, making it a strong candidate for merging before 2.56 final.

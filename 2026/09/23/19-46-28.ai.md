This is a **substantive review** from Jeff King (Peff) responding to Phillip Wood’s critique of Derrick Stolee’s RFC series introducing a "safe" `strbuf` API. Peff engages with the core design questions, offering an alternative vision for how to make `strbuf` operations safe for critical code paths like trace2.

Peff agrees with Phillip that the term "safe" is misleading and overly broad. He argues that the current proposal (error-returning `strbuf` functions) addresses only one narrow aspect of safety—malloc failures—while implying a much larger guarantee. He notes that the term "safe" is typically reserved in Git for APIs that require extra caution (e.g., `refs_resolve_ref_unsafe`), and that the current framing risks confusing contributors about what the API actually guarantees. More pointedly, he observes that the new API would still not be safe for signal handlers, as `malloc()` relies on locks, undermining the trace2 use case where crash resilience is paramount.

Instead of error-returning `strbuf` functions, Peff proposes an entirely different approach: **fixed-size, stack-allocated `strbuf`-like buffers** (which he calls `static_strbuf`). These would operate on a pre-allocated buffer (either a fixed size like 4KB or a per-struct max size) and avoid `malloc()` entirely. While this design would still have failure modes (e.g., buffer overflow), those would be deterministic and predictable, unlike the sporadic failures of `malloc()`. Peff suggests this approach would better serve the trace2 use case, where avoiding dynamic allocation is more important than handling allocation failures gracefully.

Peff also endorses Phillip’s usability concern about error checking. He agrees that requiring callers to check for errors on every `strbuf` operation would be cumbersome, and that a **sticky error bit** (like C’s `stdio` functions) would be a more ergonomic solution. This would allow deferred error checking, simplifying usage in code paths where intermediate failures can be tolerated until the final result is needed.

The review does not engage with the implementation details of the RFC (e.g., the bugs in `sstrbuf_grow()` or `srealloc()`), focusing instead on the high-level design. Peff’s alternative—fixed-size buffers with a sticky error bit—represents a significant departure from the RFC’s direction, and his feedback implies that the current series may be solving the wrong problem. The tone is constructive, treating the RFC as a starting point for discussion rather than a finished proposal. His critique aligns with Junio’s earlier feedback about hardening the entire API, but Peff’s alternative is more radical, suggesting that the "safe" API should avoid dynamic allocation altogether rather than just handling its failures.

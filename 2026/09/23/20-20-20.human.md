This is a **bug report** targeting submodule merge behavior. Guillaume Chauvel describes a reproducible issue where Git, during a merge of a superproject with submodules, incorrectly attempts to read a commit from submodule *A* that actually exists only in submodule *B*. Instead of reporting a submodule conflict, Git either fails with "repository corrupt" or misidentifies the commit's origin.

The report includes a detailed reproducer script that sets up two submodules (A and B) with divergent branches, then merges the superproject. The script consistently triggers the bug in 50/50 Ubuntu runs and 43/50 Alpine runs. The error manifests as Git trying to parse a commit OID from the wrong submodule, leading to a misleading "repository corrupt" message. An AI analysis suggests the root cause may be stale delta-base cache entries persisting after a pack is closed, potentially causing Git to return incorrect cached data when packs from different submodules reuse the same memory address.

The commit message is clear and thorough, providing both a minimal reproducer and a plausible explanation. The issue appears serious—misattributing commits between submodules could lead to data corruption or incorrect merge results. The report does not include a proposed fix, but the reproducer should make it straightforward for a reviewer to investigate. This looks like a genuine bug worth attention, especially given its consistency across environments.

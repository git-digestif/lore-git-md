This is a design discussion in the ongoing thread about how to improve `git fetch` performance in shallow repositories. Phillip Wood responds to Junio C Hamano’s proposal for a "matching-inspired" fetch mode by identifying a critical flaw: it cannot work for newly added remotes because no local branches will yet track the remote’s branches, creating a chicken-and-egg problem.

Phillip acknowledges that Junio’s idea would be useful for fetching from *existing* remotes (where local branches already track upstream branches) but argues it fails for the original use case—adding a new remote to a shallow repository—because `git branch --set-upstream-to` requires the upstream branch to already exist locally. This leaves the core problem unsolved: users still face slow fetches when adding a new remote to a shallow repository, as the default wildcard refspec will negotiate history for all remote branches.

The email does not propose a new solution but instead highlights a limitation in Junio’s proposal, steering the discussion back toward the narrower-refspec approach for `git remote add` (which Phillip previously refined). The thread remains focused on designing a solution that works for both new and existing remotes in shallow repositories, with no code changes implemented yet.

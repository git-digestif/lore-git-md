This is a **test failure report** for the recently merged `http.sslVerifyStatus` security feature. SZEDER Gábor identifies two issues in the test infrastructure that cause the new `t5585-http-ssl-ocsp.sh` test to fail on his system.

The first issue is with the `SSL_VERIFYSTATUS` prerequisite check. The current implementation considers the prerequisite fulfilled if the error message does *not* contain the string `"http.sslVerifyStatus is set"`. However, Gábor’s trace shows that `git ls-remote` fails for unrelated reasons—either because the repository does not exist (`fatal: repository not found`) or because no OCSP response is received (`No OCSP response received`)—yet the prerequisite still passes. This is clearly wrong: the prerequisite should only pass if the system is actually capable of verifying staples, not if it fails for any other reason.

The second issue is a test failure in the final test case (`revoked certificate is accepted without http.sslVerifyStatus`). After revoking the server certificate, the test expects Git to accept the connection when `http.sslVerifyStatus` is *not* enabled. Instead, Gábor’s trace shows that libcurl (7.81.0) rejects the revoked certificate even without the option, because the CA’s CRL is being checked. This suggests that the test setup does not properly isolate OCSP stapling from other revocation mechanisms (CRLs), making the test’s expectation invalid on systems where libcurl checks CRLs by default.

Gábor also points out two minor code-quality nits: the test should check the exact error message to ensure the command failed for the expected reason, and the `with_ssl_verification` helper should use `export` instead of a temporary variable assignment for portability.

The patch itself remains merged in `master`; this email is a post-merge bug report rather than a pre-merge review. The issues are confined to the test infrastructure and do not affect the core functionality of `http.sslVerifyStatus`.

This is a design discussion reply in the thread about improving `git fetch` behavior in shallow repositories. Junio C Hamano responds to Phillip Wood’s chicken-and-egg concern about the matching-inspired fetch mode by proposing a priming mechanism: users would explicitly fetch the remote’s default branch (or another branch of interest) once to establish the upstream tracking relationship, after which the matching-inspired mode would work automatically. The proposal introduces a special refspec token (`:`) to trigger the mode in `git remote add`, creating a no-op initial fetch that requires the user to manually fetch the desired branch(es) to set up tracking.

The key technical detail is the priming step: the user must run `git fetch <remote> <branch>:refs/remotes/<remote>/<branch>` to create the remote-tracking branch and then set the upstream with `git checkout -b <local-branch> -t <remote>/<branch>`. After this, subsequent `git fetch` calls would use the matching-inspired mode to fetch only the tracked branches. Junio acknowledges uncertainty about the refspec syntax (`:`) but does not address the earlier refinement (fetching the remote’s default branch regardless of tracking) or the integration with the narrower-refspec approach for `git remote add`. The proposal preserves backwards compatibility but shifts the burden of initial setup to the user, which may not fully address the original performance problem in shallow repositories. The discussion remains focused on refining the matching-inspired mode, with open questions about syntax, default behavior, and how to handle edge cases like missing or stale remote `HEAD`.

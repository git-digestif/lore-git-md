Thread identity: regression fix for `git commit --amend` during interactive rebase, introduced in Git 2.56-rc0 by commit 6257588252 ("sequencer: refuse to amend during conflict resolution"); single-patch series from Patrick Steinhardt targeting `sequencer.c` and the `MERGE_MSG` safety check.

Core problem or goal: restore the ability to amend a commit created after resolving a conflict during an interactive rebase, broken by an overzealous safety check. The broader architectural question remains whether plain `git commit` should be rejected outright during conflict resolution for sequencer-based commands (`rebase`, `am`, `cherry-pick`, `revert`), steering users toward `--continue` instead.

Current status: the regressing commit (6257588252) will be reverted entirely for the Git 2.56 release cycle as -rc2 material. This decision is now agreed by Junio C Hamano, Elijah Newren, and Patrick Steinhardt, prioritizing release stability over partial fixes. Junio’s latest email reinforces the workflow justification for allowing `git commit` (and thus `git commit --amend`) during interactive rebase, citing established user practices such as splitting commits or rewording messages before continuing. The revert itself is not yet coded, and no evidence of merger to any integration branch (`pu`, `next`, or `master`) has appeared.

Key technical details: commit 6257588252 added a `MERGE_MSG` check in `sequencer.c` to prevent amendments during conflict resolution, but this approach is vulnerable to a race condition with `git reset` (demonstrated by Elijah Newren). Elijah’s alternative proposal—recording the original `HEAD` in `rebase-merge/stopped-head` to reliably determine whether an amendment is safe—remains unaddressed. Patrick’s patch also added a regression test in `t/t3404-rebase-interactive.sh` covering the scenario: start interactive rebase, induce conflict, resolve and commit, then amend the new commit. Phillip Wood suggested refining the test by appending two lines to an existing test case rather than introducing a new one. Junio’s email clarifies that the `MERGE_MSG` check’s race condition and the lack of a robust alternative (such as `rebase-merge/stopped-head`) are the primary reasons for reverting rather than attempting a targeted fix. No new symbols or on-disk format changes.

This would unify behavior across `rebase`, `am`, `cherry-pick`, and `revert`, steering users toward `--continue` instead.

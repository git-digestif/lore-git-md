Thread identity: regression fix for `git commit --amend` during interactive rebase, introduced in Git 2.56-rc0 by commit 6257588252 ("sequencer: refuse to amend during conflict resolution"); single-patch series from Patrick Steinhardt targeting `sequencer.c` and the `MERGE_MSG` safety check.

Core problem or goal: restore the ability to amend a commit created after resolving a conflict during an interactive rebase, broken by an overzealous safety check. The broader architectural question remains whether the same check affects other sequencer-based commands (`git cherry-pick`, `git merge`, `git revert`), and whether plain `git commit` should be rejected outright during conflict resolution for sequencer-based commands, steering users toward `--continue` instead.

Current status: under active release-management and design discussion; patch v1 posted, no prior versions. Junio C Hamano has proposed reverting the regressing commit (6257588252) entirely for the 2.56 release cycle, deferring both Patrick’s targeted fix and the broader architectural consistency question until after Git 2.56 ships. Elijah Newren’s review identifies a critical flaw in the `MERGE_MSG`-based approach (a race condition with `git reset`) and proposes two short-term alternatives: (1) revert 6257588252 entirely, or (2) record the original `HEAD` at the point the sequencer stops (e.g., in `rebase-merge/stopped-head`) as a more reliable signal for whether an amendment should be allowed. No evidence of merger to any integration branch (`pu`, `next`, or `master`) has appeared.

Key technical details: modifies `sequencer.c` to check for the presence of `MERGE_MSG` as a proxy for whether a conflict resolution has been committed, but this approach is now known to be flawed due to a race condition with `git reset`. Elijah’s alternative proposal involves recording the original `HEAD` in `rebase-merge/stopped-head` to reliably determine whether an amendment is safe. Adds a regression test in `t/t3404-rebase-interactive.sh` covering the scenario: start interactive rebase, induce conflict, resolve and commit, then amend the new commit. Phillip Wood suggests refining the test by appending two lines to an existing test case rather than introducing a new one. No new symbols or on-disk format changes.

Open questions and loose ends:
- The `MERGE_MSG` check is vulnerable to a race condition with `git reset`, as demonstrated by Elijah Newren’s test sequence (`git reset` followed by `git commit --amend -a`), which reintroduces the footgun that commit 6257588252 aimed to prevent.
- Short-term release-management question: whether to revert commit 6257588252 entirely for Git 2.56 (as proposed by Junio and Elijah) or implement Elijah’s alternative of recording the original `HEAD` in `rebase-merge/stopped-head`.
- Architectural question: should plain `git commit` be rejected outright during conflict resolution for sequencer-based commands (`rebase`, `am`, `cherry-pick`, `revert`), steering users toward `--continue` instead? Elijah enumerates several surprising behaviors of plain `git commit` in these contexts (e.g., losing the original commit message, author, and author date during `am` or rebase, and inconsistent `--abort` behavior) and argues for a unified design where the sequencer command owns both the commit and the state transition.
- Phillip Wood’s concern about the test not covering the edge case where `MERGE_MSG` exists due to a subsequent merge/cherry-pick conflict remains unresolved, though he concedes the fix should still behave correctly in that scenario.

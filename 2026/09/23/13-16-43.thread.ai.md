Thread identity: regression fix for `git commit --amend` during interactive rebase, introduced in Git 2.56-rc0; single-patch series from Patrick Steinhardt targeting `sequencer.c` and the `MERGE_MSG` safety check.

Core problem or goal: restore the ability to amend a commit created after resolving a conflict during an interactive rebase, broken by commit 6257588252 ("sequencer: refuse to amend during conflict resolution"). The broader architectural question raised is whether the same overzealous safety check affects other sequencer-based commands (`git cherry-pick`, `git merge`, `git revert`), as the logic was written generically and could block amendments in those contexts as well.

Current status: under review; patch v1 posted, no prior versions. The fix is targeted for the 2.56 release cycle to address the regression before final release. No evidence of merger to any integration branch (`pu`, `next`, or `master`) has appeared.

Key technical details: modifies `sequencer.c` to check for the presence of `MERGE_MSG` as a proxy for whether a conflict resolution has already been committed, allowing amendments to proceed if the file exists. Adds a regression test in `t/t3404-rebase-interactive.sh` covering the scenario: start interactive rebase, induce conflict, resolve and commit, then amend the new commit. No new symbols or on-disk format changes. Phillip Wood suggests refining the test by appending two lines to an existing test case rather than introducing a new one, arguing this would verify both the fix and the continued functionality of committing a conflict resolution while keeping the test suite lean.

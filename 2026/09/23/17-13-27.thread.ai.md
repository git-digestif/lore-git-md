Subject: [PATCH 0/2] ci: reduce resource exhaustion in GitHub Actions
Series version: v1 (initial submission)
Originating author: Tamir Duberstein
Thread type: patch series (CI/build system)

Core problem or goal
Address resource exhaustion in GitHub Actions CI jobs running the full test suite on Linux runners. The series targets two specific issues: (1) `t4205-log-pretty-formats.sh` generates enormous output that triggers OOM kills when `diff` compares it, and (2) default `make` and `prove` parallelism (`-j10`) is too aggressive for the Linux runner’s 2 CPU cores, causing ENOSPC errors during large clone/repack tests.

Current status
Under review (v1 posted). No prior versions. No maintainer decision recorded. Author retracted the "Prepared with Codex" attribution line from the cover letter as unnecessary. Benchmark data and CI failure context now provided for Patch 1. Discussion ongoing about whether to retain early file deletion in Patch 1; Jeff King (Peff) endorses the `test_cmp_bin` replacement as sufficient and dismisses the need for further optimization at this time.

Key technical details
- Patch 1: Replace `test_cmp` (which uses `diff`) with `test_cmp_bin` (which uses `cmp`) in `t/t4205-log-pretty-formats.sh`. Benchmark data shows `diff -u` on 2 GiB files peaks at 4 GiB RSS and takes 5 seconds, while `cmp` uses 1.2 MiB and finishes in 0.5 seconds. The OOM kill (SIGKILL) occurred in a private repository where GitHub runners have half the memory of public ones. Patrick Steinhardt’s review questions whether early file deletion (added to reclaim ~4 GiB) is effective, since the files are rewritten shortly afterward in subsequent tests. Tamir now concedes the deletion may not be worth keeping. Jeff King endorses the `test_cmp_bin` change as a reasonable, targeted fix for the edge case, noting the benchmark difference is substantial and that most test comparisons are small enough that process startup time dominates. He briefly considers but dismisses a hypothetical future improvement to `test_cmp` (using `cmp` as a fast pre-check before falling back to `diff` for human-readable output) as unnecessary for now.
- Patch 2: Dynamically set `-j` for `make` and `prove` to the runner’s CPU count (`JOBS=$(nproc)`) when `CI_OS_NAME` is `linux`, matching GitLab CI policy. The change is a four-line addition to `ci/lib.sh`. The motivation is to prevent ENOSPC errors during concurrent large fixtures (clone/repack) on 2-CPU runners. Patrick Steinhardt’s review requests (a) a link to a CI failure demonstrating the ENOSPC issue, (b) benchmark data comparing CI runtime before and after the change, and (c) an exploration of whether oversubscribing (running more jobs than CPU cores) might be a better trade-off. He also suggests aligning GitLab and GitHub CI logic, noting no clear reason for the two to differ.
- Files touched: `.github/workflows/main.yml`, `t/t4205-log-pretty-formats.sh`, `ci/lib.sh`.
- No new symbols, CLI options, or on-disk format changes.
- Test coverage: unchanged (long-running tests remain enabled).

Open questions and loose ends
- Patch 1: Should the early file deletion be retained despite its limited benefit? Tamir has conceded it may not be worth keeping, and Jeff King’s endorsement of the `test_cmp_bin` change suggests the simpler approach is sufficient. No new evidence has emerged to justify the deletion’s complexity.
- Patch 2: Are the ENOSPC errors real and reproducible? What is the runtime impact of reducing parallelism? Would oversubscribing (e.g., `-j4` on a 2-CPU runner) yield a better performance/resource trade-off? Should GitLab and GitHub CI logic be unified? No new data or failure logs have been provided yet.

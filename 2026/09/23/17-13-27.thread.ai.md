Subject: [PATCH 0/2] ci: reduce resource exhaustion in GitHub Actions
Series version: v2 (Patch 2 revised; Patch 1 unchanged)
Originating author: Tamir Duberstein
Thread type: patch series (CI/build system)

Core problem or goal
Address resource exhaustion in GitHub Actions CI jobs running the full test suite on Linux runners. The series targets two specific issues: (1) `t4205-log-pretty-formats.sh` generates enormous output that triggers OOM kills when `diff` compares it, and (2) default `make` and `prove` parallelism (`-j10`) is too aggressive for the Linux runner’s 2 CPU cores, causing ENOSPC errors during large clone/repack tests.

Current status
Under review (v2 posted). Patch 1 unchanged from v1; Patch 2 revised to use `1x CPU count` and unify GitHub/GitLab CI logic. Maintainer Junio C Hamano has endorsed the technical direction of Patch 1 (replacing `test_cmp` with `test_cmp_bin` in `t/t4205-log-pretty-formats.sh`), aligning with Jeff King’s earlier review. No maintainer decision on Patch 2. Author has provided benchmark data for Patch 2 showing a 2 % speedup on Linux with `1x CPU count` and a 7 % speedup with `2x CPU count`, but opts for the conservative `1x` baseline to ensure consistency across CI providers.

Key technical details
- Patch 1: Replace `test_cmp` (which uses `diff`) with `test_cmp_bin` (which uses `cmp`) in `t/t4205-log-pretty-formats.sh`. Benchmark data shows `diff -u` on 2 GiB files peaks at 4 GiB RSS and takes 5 seconds, while `cmp` uses 1.2 MiB and finishes in 0.5 seconds. The OOM kill (SIGKILL) occurred in a private repository where GitHub runners have half the memory of public ones. Patrick Steinhardt’s review questioned whether early file deletion (added to reclaim ~4 GiB) is effective, since the files are rewritten shortly afterward in subsequent tests. Tamir now concedes the deletion may not be worth keeping. Jeff King and Junio C Hamano endorse the `test_cmp_bin` change as a reasonable, targeted fix for the edge case, noting the benchmark difference is substantial and that most test comparisons are small enough that process startup time dominates. A hypothetical future improvement to `test_cmp` (using `cmp` as a fast pre-check before falling back to `diff` for human-readable output) is dismissed as unnecessary for now.
- Patch 2: Dynamically set `-j` for `make` and `prove` to the runner’s CPU count (`JOBS=$(nproc)`) when `CI_OS_NAME` is `linux`, matching GitLab CI policy. The change is a four-line addition to `ci/lib.sh`. Benchmark data now shows that on Linux, `1x CPU count` yields a 2 % speedup over the current `-j10`, while `2x CPU count` yields a 7 % speedup. macOS and Windows results are inconsistent: macOS regresses with `1x CPU count` but improves with `2x`, while Windows shows negligible change. Tamir opts for `1x CPU count` as a conservative, consistent baseline across CI providers (GitHub and GitLab), deferring further tuning to a future patch. The revised patch unifies the logic for both CI platforms, addressing Patrick Steinhardt’s concern about divergent configurations.
- Files touched: `.github/workflows/main.yml`, `t/t4205-log-pretty-formats.sh`, `ci/lib.sh`.
- No new symbols, CLI options, or on-disk format changes.
- Test coverage: unchanged (long-running tests remain enabled).

Open questions and loose ends
- Patch 1: Should the early file deletion be retained despite its limited benefit? Tamir has conceded it may not be worth keeping, and both Jeff King and Junio C Hamano’s endorsements of the `test_cmp_bin` change suggest the simpler approach is sufficient. No new evidence has emerged to justify the deletion’s complexity.
- Patch 2: Would oversubscribing (e.g., `2x CPU count`) yield a better performance/resource trade-off? The benchmark data shows a 7 % speedup on Linux with `2x CPU count`, but Tamir defers this exploration to a future patch. No new failure logs demonstrating ENOSPC errors have been provided.

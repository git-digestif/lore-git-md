Subject: [PATCH 0/2] ci: reduce resource exhaustion in GitHub Actions
Series version: v1 (initial submission)
Originating author: Tamir Duberstein
Thread type: patch series (CI/build system)

Core problem or goal
Address resource exhaustion in GitHub Actions CI jobs running the full test suite on Linux runners. The series targets two specific issues: (1) `t4205-log-pretty-formats.sh` generates enormous output that triggers OOM kills when `diff` compares it, and (2) default `make` and `prove` parallelism (`-j10`) is too aggressive for the Linux runner’s 2 CPU cores, causing ENOSPC errors during large clone/repack tests.

Current status
Under review (v1 posted). No prior versions. No maintainer decision recorded. Author retracted the "Prepared with Codex" attribution line from the cover letter as unnecessary.

Key technical details
- Patch 1: Replace `test_cmp` (which uses `diff`) with `test_cmp_bin` (which uses `cmp`) in `t/t4205-log-pretty-formats.sh` and delete the two large temporary files immediately after comparison, reclaiming ~4 GiB of memory. The OOM kill (SIGKILL) is due to `diff` memory usage; `cmp` is a lightweight alternative. Patrick Steinhardt’s review requests evidence: a link to a CI failure showing the SIGKILL, and benchmark data comparing `test_cmp_bin` to `test_cmp` in terms of peak RSS and runtime. The review also questions whether the early file deletion is effective, since the files are rewritten shortly afterward in subsequent tests.
- Patch 2: Dynamically set `-j` for `make` and `prove` to the runner’s CPU count (`JOBS=$(nproc)`) when `CI_OS_NAME` is `linux`, matching GitLab CI policy. The change is a four-line addition to `ci/lib.sh`. The motivation is to prevent ENOSPC errors during concurrent large fixtures (clone/repack) on 2-CPU runners. Patrick Steinhardt’s review now requests (a) a link to a CI failure demonstrating the ENOSPC issue, (b) benchmark data comparing CI runtime before and after the change, and (c) an exploration of whether oversubscribing (running more jobs than CPU cores) might be a better trade-off. He also suggests aligning GitLab and GitHub CI logic, noting no clear reason for the two to differ.
- Files touched: `.github/workflows/main.yml`, `t/t4205-log-pretty-formats.sh`, `ci/lib.sh`.
- No new symbols, CLI options, or on-disk format changes.
- Test coverage: unchanged (long-running tests remain enabled).

Open questions and loose ends
- Patch 1: Is the `test_cmp_bin` replacement justified by measurable memory savings? Does the early file deletion provide meaningful memory reclamation, or is the complexity not worth the brief reprieve? Patrick Steinhardt’s review explicitly requests CI failure logs and benchmark data to support the claims.
- Patch 2: Are the ENOSPC errors real and reproducible? What is the runtime impact of reducing parallelism? Would oversubscribing (e.g., `-j4` on a 2-CPU runner) yield a better performance/resource trade-off? Should GitLab and GitHub CI logic be unified?

This is a design discussion reply from Junio C Hamano, the Git maintainer, in the ongoing thread about improving `git fetch` behavior in shallow repositories. Junio responds to Phillip Wood’s chicken-and-egg concern about the proposed "matching-inspired" fetch mode by clarifying how it would work in practice for newly added remotes.

Junio proposes a workflow where users explicitly "prime the pump" when adding a new remote by using a special refspec syntax (e.g., `:` or `+:`) in `git remote add --fetch`. This would create a remote configuration that defaults to the matching-inspired fetch mode, where `git fetch` only updates remote-tracking branches for local branches that track the remote. Initially, this would be a no-op until the user explicitly fetches a branch (e.g., `git fetch second main:refs/remotes/second/main`) and sets up a local branch to track it. Once tracking is established, subsequent `git fetch` calls would update only the relevant remote-tracking branches.

The proposal addresses Phillip’s concern by showing how the matching-inspired mode can coexist with explicit initial fetches, but it does not resolve the broader question of whether this mode should be the default for shallow repositories or how it integrates with the narrower-refspec approach for `git remote add`. Junio’s reply is substantive, offering a concrete workflow for the matching-inspired mode, but it leaves open questions about refspec syntax, default behavior, and edge cases (e.g., handling stale `HEAD` or missing upstream branches). The discussion remains focused on refining the design rather than implementing code.

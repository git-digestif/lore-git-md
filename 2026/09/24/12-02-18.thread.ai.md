Thread identity: RFC patch series proposing improved error reporting for invalid Git repository directories, now focusing on *which* directory Git inspected and *where* it came from (e.g., `--git-dir`, `GIT_DIR`, repository discovery, or `GIT_OBJECT_DIRECTORY`). Series version: v3. Originating author: Kaartic Sivaraam. Thread type: RFC patch series.

Core problem or goal: Enhance Git's error messages when it cannot find a valid repository by reporting the inspected directory and its origin, rather than explaining *why* the directory is invalid. This addresses Junio C Hamano’s critique that users are primarily confused about *which* directory Git is inspecting and *how* it was chosen (e.g., via `--git-dir`, `GIT_DIR`, repository discovery, or `GIT_CEILING_DIRECTORIES`), rather than the specific failure reason. The goal is to help users diagnose misconfigurations by clarifying the path Git inspected and its source.

Current status: Under review as an RFC v3, representing a significant pivot from v2 in response to Junio’s design-level feedback. The series now consists of five patches, with the first two patches landed as preparatory work: the first patch is a minor stylistic refactoring in `setup.c` to normalize an `if-else` block, and the second patch adds 41 lines of test coverage to `t/t0009-git-dir-validation.sh` to exercise repository discovery scenarios. The third patch (this update) introduces diagnostic context for explicitly specified directories (`--git-dir`/`--bare` or `GIT_DIR`), appending a hint to the error message (e.g., "this path was taken from $GIT_DIR (which can also be set with --git-dir or --bare)"). The substantive changes—adding diagnostic context to "fatal: not a git repository" errors—continue in later patches. No technical flaws in the implementation have been raised, and the new direction aligns with Junio’s critique. The series explicitly defers handling of `gitfile` (submodules/worktrees), `GIT_ALTERNATE_OBJECT_DIRECTORIES`, and edge cases like `GIT_CEILING_DIRECTORIES` entries that don’t affect the search path to future work.

Key technical details:
- Files touched: `setup.c` (stylistic refactoring and diagnostic improvements), `t/t0009-git-dir-validation.sh` (tests, +118 lines total).
- Subsystems: Repository setup and validation.
- Behavior: The series adds three key pieces of diagnostic context to "fatal: not a git repository" errors:
  1. For explicit `--git-dir` or `GIT_DIR`, it reports the source (e.g., "this path was taken from $GIT_DIR (which can also be set with --git-dir or --bare)"). This is implemented in the third patch by modifying a single `die()` call in `setup.c` to include the source of the path.
  2. For repository discovery (walking up the filesystem), it will report the search boundaries (e.g., "searched from '/home/user/.config/nvim' up to '/home/user/.config'") and any active `GIT_CEILING_DIRECTORIES`. This is addressed in later patches.
  3. For inaccessible `GIT_OBJECT_DIRECTORY`, it will append the path and error (e.g., "cannot access object directory '/does/not/exist' set via $GIT_OBJECT_DIRECTORY: No such file or directory"). This is also addressed in later patches.
- Commands that don’t need a repository (e.g., `git hash-object`) remain silent.
- Error messages are kept as single translatable strings with `TRANSLATORS` comments for placeholders.
- No changes to on-disk format or existing APIs (`is_git_directory()`, `validate_headref()`).
- Test coverage: 118 new lines in `t/t0009-git-dir-validation.sh`, covering explicit gitdir, discovery walk, `GIT_OBJECT_DIRECTORY`, and silent behavior for commands not needing a repository. The third patch updates two tests to verify the new hint appears in stderr for both `--git-dir` and `GIT_DIR` scenarios.
- Stylistic refactoring: The first patch normalizes an `if-else` block in `setup.c` (function `enter_repo`, around line 1905) to follow Git’s coding convention by moving the `else` onto the same line as the closing brace of the `if` block. This change is purely stylistic and does not alter behavior.

Open questions and loose ends:

- No substantive objections to the implementation’s correctness or design have been raised yet. The series’ pivot to reporting the inspected path and its origin addresses Junio’s core critique, but further feedback may refine the approach.

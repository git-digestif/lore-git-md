Thread identity: RFC patch series proposing improved error reporting for invalid Git repository directories, now focusing on *which* directory Git inspected and *where* it came from (e.g., `--git-dir`, `GIT_DIR`, repository discovery, or `GIT_OBJECT_DIRECTORY`). Series version: v3. Originating author: Kaartic Sivaraam. Thread type: RFC patch series.

Core problem or goal: Enhance Git's error messages when it cannot find a valid repository by reporting the inspected directory and its origin, rather than explaining *why* the directory is invalid. This addresses Junio C Hamano’s critique that users are primarily confused about *which* directory Git is inspecting and *how* it was chosen (e.g., via `--git-dir`, `GIT_DIR`, repository discovery, `GIT_CEILING_DIRECTORIES`, or `GIT_OBJECT_DIRECTORY`), rather than the specific failure reason. The goal is to help users diagnose misconfigurations by clarifying the path Git inspected and its source.

Current status: Under review as RFC v3, now complete with all five patches posted. The first two patches landed as preparatory work: the first patch is a minor stylistic refactoring in `setup.c` to normalize an `if-else` block, and the second patch adds 154 lines of test coverage to `t/t0009-git-dir-validation.sh` to exercise repository discovery scenarios. The third patch introduces diagnostic context for explicitly specified directories (`--git-dir`/`--bare` or `GIT_DIR`), appending a hint to the error message (e.g., "this path was taken from $GIT_DIR (which can also be set with --git-dir or --bare)"). The fourth patch enhances the "not a git repository" error message for repository discovery when `GIT_CEILING_DIRECTORIES` is set, reporting the search boundaries (e.g., "searched from '/home/user/.config/nvim' up to '/home/user/.config'") and the value of `GIT_CEILING_DIRECTORIES`. The fifth patch completes the series by adding diagnostic context when `GIT_OBJECT_DIRECTORY` points to an unusable directory, appending a clear explanation (e.g., "cannot access object directory '/tmp/git-objects' set via $GIT_OBJECT_DIRECTORY: No such file or directory"). No technical flaws in the implementation have been raised, and the new direction aligns with Junio’s critique. The series explicitly defers handling of `gitfile` (submodules/worktrees), `GIT_ALTERNATE_OBJECT_DIRECTORIES`, and edge cases like `GIT_CEILING_DIRECTORIES` entries that don’t affect the search path to future work.

Key technical details:
- Files touched: `setup.c` (stylistic refactoring and diagnostic improvements), `t/t0009-git-dir-validation.sh` (tests, +190 lines total).
- Subsystems: Repository setup and validation.
- Behavior: The series adds three key pieces of diagnostic context to "fatal: not a git repository" errors:
  1. For explicit `--git-dir` or `GIT_DIR`, it reports the source (e.g., "this path was taken from $GIT_DIR (which can also be set with --git-dir or --bare)"). This is implemented in the third patch by modifying a single `die()` call in `setup.c` to include the source of the path.
  2. For repository discovery with `GIT_CEILING_DIRECTORIES`, it reports the search boundaries (e.g., "searched from '/home/user/.config/nvim' up to '/home/user/.config'") and the value of `GIT_CEILING_DIRECTORIES` if set. This is implemented in the fourth patch by enhancing the `GIT_DIR_HIT_CEILING` case in `repo_discover()` to construct a multi-line error message with `strbuf`.
  3. For inaccessible `GIT_OBJECT_DIRECTORY`, it appends the path and error (e.g., "cannot access object directory '/tmp/git-objects' set via $GIT_OBJECT_DIRECTORY: No such file or directory"). This is implemented in the fifth patch via a helper function `describe_unusable_object_dir()` in `setup.c` and a wrapper `die_no_repository()` to append diagnostic context. The check is performed once at the point of failure, and `git init` remains unaffected.
- Commands that don’t need a repository (e.g., `git hash-object`) remain silent.
- Error messages are kept as single translatable strings with `TRANSLATORS` comments for placeholders.
- No changes to on-disk format or existing APIs (`is_git_directory()`, `validate_headref()`).
- Test coverage: 190 new lines in `t/t0009-git-dir-validation.sh`, covering explicit gitdir, discovery walk with `GIT_CEILING_DIRECTORIES`, `GIT_OBJECT_DIRECTORY`, and silent behavior for commands not needing a repository. The fifth patch adds 36 lines to verify the new diagnostic output for both explicit gitdir and repository discovery scenarios with `GIT_OBJECT_DIRECTORY`.
- Stylistic refactoring: The first patch normalizes an `if-else` block in `setup.c` (function `enter_repo`, around line 1905) to follow Git’s coding convention by moving the `else` onto the same line as the closing brace of the `if` block. This change is purely stylistic and does not alter behavior.

Open questions and loose ends:

- No substantive objections to the implementation’s correctness or design have been raised yet. The series’ pivot to reporting the inspected path and its origin addresses Junio’s core critique, but further feedback may refine the approach, particularly for edge cases or future expansion (e.g., `gitfile` handling).

Thread identity
Subject: fetch-pack: mark exact OIDs in refs
Series version: single patch (no version iteration yet)
Originating author: Nathan Froyd
Thread type: bugfix patch

Core problem or goal
`git fetch-pack` does not mark exact OIDs in refs, causing it to send `want-ref $OID` instead of `want $OID` when invoked as `git fetch-pack $OID`. This triggers “unknown ref” errors from the remote. The goal is to make `fetch-pack` consistent with `git fetch`, which already marks exact OIDs correctly.

Current status
Under review; no prior version posted. Junio C Hamano has restated and sharpened his design-level objection: the `<ref>` arguments in `git fetch-pack <repository> <ref>...` are intended to be passed verbatim to the remote via the `want-ref` packet, without any DWIM parsing. He argues that the patch’s approach would break existing use cases that rely on exact ref-name transmission. The fundamental design question—whether to align `fetch-pack` with `git fetch` or preserve its low-level verbatim behavior—remains unresolved.

Key technical details
- File modified: `builtin/fetch-pack.c`
- Proposed new behavior: `ref->exact_oid` is set when parsing an exact OID (no trailing ref name)
- Test file: `t/t5703-upload-pack-ref-in-want.sh`
- Symbols: `ref->exact_oid` flag
- On-disk format: unchanged
- CLI: unchanged

Open questions and loose ends
- Should `fetch-pack` adopt the same DWIM behavior as `git fetch`, or should it remain a low-level command that transmits ref names verbatim?
- If the latter, what mechanism should be introduced to allow users to send `want $OID` requests without breaking existing `want-ref` use cases?
- Junio’s clarification underscores that the patch’s approach would break backward compatibility for users who rely on `want-ref` for arbitrary ref names.

Participant positions
Nathan Froyd (author): posted the patch with clear motivation, minimal code change, and comprehensive test coverage, advocating for consistency with `git fetch`.
Junio C Hamano (maintainer): objects to the design on substantive grounds, arguing that `fetch-pack` should remain a low-level command without implicit parsing heuristics. His latest email sharpens the objection by explaining how the patch would break existing use cases that depend on verbatim ref-name transmission.

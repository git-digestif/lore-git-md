This is the latest update in the ongoing regression fix for the reference-transaction hook, where Maciej Ciemborowicz clarifies the architectural pivot in the v6 series. The thread targets a bug introduced in Git 2.31 that causes the hook to receive all-zero OIDs when branches or tags are deleted, breaking tools like Gerrit and GitLab that rely on the hook to monitor ref changes.

Maciej’s reply confirms the shift away from the v5 approach (which extended `refs_delete_refs()` to accept old OIDs) toward Patrick Steinhardt’s proposed solution: resolving missing old OIDs directly in the transaction hook layer. This sidesteps the API debate entirely by moving the fix to a higher layer, where the hook can observe old values without altering the transaction’s safety checks or requiring callers to pass them explicitly. The new design avoids overloading `refs_delete_refs()`—a key objection from Patrick—and preserves the performance gains of the original bulk-deletion optimization.

The trade-off is now clear: the hook layer will resolve old OIDs on demand, which could introduce latency for large batches (e.g., deleting 10,000 tags). Maciej doesn’t address this performance concern in his reply, so it may surface in follow-up discussion. The v6 series will also need to update the existing regression tests to cover the new implementation, though the expected hook payloads remain unchanged.

This is a well-motivated fix for a real-world regression, and the architectural pivot—while introducing new complexity—appears to address the core objections raised in earlier reviews. The patch is likely to attract further scrutiny around the performance implications of on-demand resolution, but the direction aligns with the maintainers’ preference for keeping `refs_delete_refs()` simple. If the latency trade-off is acceptable, this could be the final shape of the fix.

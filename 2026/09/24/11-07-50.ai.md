This is a **substantive review** of the first patch in the v5 bugfix series that restores old-OID reporting in the reference-transaction hook. Patrick Steinhardt raises **fundamental design concerns** about the patch's approach, arguing that the entire refactoring is misguided.

The core objection is architectural: `refs_delete_refs()` exists as a convenience wrapper for simple, unconditional deletions. The patch extends it to handle conditional deletions (compare-and-delete) and partial failures, but Patrick contends this is the wrong layer. Instead, callers that need "complex behavior" (old-OID checks, granular error reporting) should **drive their own transactions** using the lower-level `ref_transaction_*` API. This would avoid overloading `refs_delete_refs()` with new parameters (`old_oids`, `failed_refs`) and special-casing null OIDs, which he calls "fishy" and inconsistent with the rest of the codebase.

Patrick’s feedback is **high-weight**: he is the primary maintainer of the refs subsystem and the author of the reftable backend, so his concerns about API design carry significant authority. The review is **not a nitpick**—it questions the patch’s entire premise and suggests a wholesale alternative. If adopted, this would require rewriting the series to use transactions directly in callers like `builtin/branch.c` and `builtin/fetch.c`, rather than extending `refs_delete_refs()`.

Key technical details raised:
- **Null-OID semantics**: The patch repurposes null OIDs to mean "unconditional deletion," but Patrick notes this conflicts with the existing meaning ("this branch should not exist").
- **Error reporting**: The patch adds a `failed_refs` parameter to `refs_delete_refs()` to return rejected updates, but Patrick argues this duplicates functionality already available in the transaction API.
- **Function scope**: `refs_delete_refs()` is meant for "fire-and-forget" deletions; conditional logic belongs in transactions.

The thread’s prior context shows the series has already addressed **all other feedback** (including Junio’s design concerns and Karthik’s safety questions) and is merged to `next`. However, Patrick’s review **reopens the design discussion** and could force a major rewrite if the author concedes. The ball is now in Maciej’s court to either defend the current approach or pivot to transactions.

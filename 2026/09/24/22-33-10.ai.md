This is a **bugfix patch** targeting the reference-transaction hook regression. The patch is the sole component of the **v6 series**, which abandons the v5 approach (modifying `refs_delete_refs()` and its callers) in favor of moving the fix into the transaction hook layer itself. This resolves Patrick Steinhardt’s architectural concerns while preserving unconditional deletion semantics and the bulk-deletion performance optimization introduced in Git 2.31.

The regression, introduced by commit `8198907795`, caused the reference-transaction hook to report all-zero OIDs for *both* old and new fields when branches or tags were deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`). This broke external tools (Gerrit, GitLab, CI systems) that rely on the hook to monitor ref changes, as the old OID (previously correctly reported in Git 2.28–2.30) was lost. The patch restores the pre-regression behavior by recording a separate "observed old value" for updates where callers did not supply an expected old OID, using this value only as hook input without setting `REF_HAVE_OLD` or constraining the update.

Key technical details:
- **Subsystems touched**: The patch modifies `refs.c` and `refs/refs-internal.h` to add a new `hook_old_oid` field and `hook_old_target` pointer to `struct ref_update`, along with logic in `resolve_transaction_hook_old_values()` to populate these fields before the "preparing" and "prepared" hook phases. The documentation (`githooks.adoc`) is updated to clarify the hook’s behavior, including the distinction between the "preparing" state (where refs are not yet locked) and later phases.
- **Commands affected**: All ref-modifying commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git push`, `git symbolic-ref`, etc.) will now receive correct old OIDs in the hook, matching the pre-2.31 behavior. `git update-ref -d` remains unaffected (already correct).
- **Backends**: The fix works for both files and reftable backends.
- **Performance trade-off**: The bulk-deletion optimization (5 seconds vs. 30 minutes for 10,000 tags) is preserved, but the on-demand resolution of old OIDs in the hook layer may introduce latency for large batches. This is acknowledged but unquantified; Patrick Steinhardt may weigh in on whether it is acceptable.
- **Tests**: The patch updates `t/t1416-ref-transaction-hooks.sh` to verify hook payloads for batched branch/tag deletions, remote pruning, and concurrent updates, including a test that confirms deletions remain unconditional even when a concurrent update occurs during the "preparing" phase.

The patch is **well-motivated and narrowly scoped**, addressing a long-standing regression with minimal risk. The commit message clearly documents the design rationale, including why the fix belongs in the transaction layer (to avoid overloading `refs_delete_refs()` and preserve its simplicity) and why callers cannot preserve old OIDs *before* deletion (due to the lack of a parameter in `refs_delete_refs()`). The series is rebased onto `master` (3bc0341127) and passes the full test suite with `DEVELOPER=1`.

This is a **strong candidate for merging**, as it resolves a persistent regression with a clean, layer-appropriate fix. The only open question is whether the on-demand resolution of old OIDs introduces unacceptable latency for large batches, which may prompt further discussion. The patch aligns with Patrick’s feedback and avoids the API complexity of v5, making it a low-risk solution.

This is a review reply in the ongoing `fetch.followRemoteHEAD` lazy-validation refactoring thread. Matt Hunter contributes a **substantive review** that surfaces two independent design questions about the configuration’s semantics and control flow, neither of which is directly tied to the current patch’s goal of deferring validation.

First, Matt argues that unrecognized values for `fetch.followRemoteHEAD` should default to `FOLLOW_REMOTE_NEVER` rather than `FOLLOW_REMOTE_UNCONFIGURED`. His rationale is forward-compatibility: a user who copies their `.gitconfig` to an older Git version will get the default behavior (which may be surprising) if the setting is ignored, whereas `NEVER` is the least surprising fallback. This is a **behavioral change** that would affect both the local and remote-side parsers, and Matt explicitly does not demand it be part of Colin’s current patch.

Second, Matt points out a potential performance optimization: when `FOLLOW_REMOTE_CREATE` is set (the default) and the local repository already has a symref for the remote’s HEAD, Git could skip the `ls-refs` query entirely. This is a **separate feature request** that would complicate the control flow in `do_fetch()`; Matt suggests it should be its own topic rather than piggybacking on the current refactoring.

The email also quotes Junio’s earlier suggestion to eliminate the redundant `do_set_head` flag by initializing `follow_remote_head` to `FOLLOW_REMOTE_NEVER` and testing it directly. Matt’s reply here is neutral, merely noting that if the `if` condition becomes more complex (e.g., to accommodate the performance optimization), it might be better not to duplicate it.

Key technical symbols to track in follow-up: `FOLLOW_REMOTE_NEVER`, `FOLLOW_REMOTE_UNCONFIGURED`, `ls-refs`, `set_head`, and the `if (follow_remote_head != FOLLOW_REMOTE_NEVER)` control flow. No code changes are proposed in this email, but the points raised could influence the next revision of Colin’s patch or spawn new topics.

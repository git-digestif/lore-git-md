Originating author: Mark C. Chu-Carroll
Thread type: patch series (feature addition)

Core problem or goal: Add flexible revision-based filtering to the `git repo structure` command, enabling users to include or exclude specific revisions (commits, refs, or ranges) from the repository structure report. The feature aims to improve diagnostic capabilities for large repositories by allowing targeted analysis of subsets of the object graph. The patch uses Git’s standard `setup_revisions()` machinery, replacing the v1 `--no-<reftype>` approach with a design consistent with Git’s revision-parsing idioms. The goal is uncontroversial in principle, but implementation details—particularly reachability logic, revision-parsing defaults, test coverage, documentation precision, and the double ref-walk inefficiency—remain under active discussion.

Current status: Under active review, procedurally clean but still blocked by unresolved substantive feedback. The v4 patch fixes the accidental corruption in `revision.c` and `revision.h` that blocked v3 but does not address the technical concerns raised in prior reviews. Key unresolved issues persist: commit message motivation, documentation precision, revision-parsing defaults (`.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`), test coverage for trees/blobs and revision options like `--filter=object:type=blob`, and the inefficiency of a double ref-walk in `count_references()`. Patrick Steinhardt’s substantive feedback from v2 and v3 remains unincorporated, and the author has not engaged with these concerns in the v4 cover letter. The patch is eligible for substantive review, but its readiness depends on resolving these open questions.

Key technical details:
- Files modified: `builtin/repo.c`, `Documentation/git-repo.adoc`, `t/t1901-repo-structure.sh` (corruption in `revision.c` and `revision.h` from v3 has been fixed).
- New CLI syntax: Revision-based filtering using `setup_revisions()` (e.g., `git repo structure <revision>... [--not <revision>...]`).
- Behavior: The command processes all objects reachable from the included revisions unless they are exclusively reachable via the excluded revisions. This avoids the transitive dependency omission issue of v1 by focusing on reachability rather than reference types.
- Symbols: Uses `struct rev_info` and `setup_revisions()` for parsing; replaces the v1 enum-based flag system in `count_references`. The `setup_revision_opt` struct retains `.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`, which Patrick Steinhardt questions as potentially overly restrictive (preventing filtering by trees or blobs).
- Workaround: Due to `setup_revisions()`’s lack of a custom ref-walk callback, the patch performs a second ref-walk in `count_references()` to count references by type, introducing potential inefficiency for large repositories or complex revision specifications.
- Test coverage: Expanded to 211 lines, validating edge cases (e.g., overlapping includes/excludes, output formats like table/lines/nul). Patrick’s requests for tests involving trees/blobs and revision options like `--filter=object:type=blob` remain unaddressed.
- Performance: The double ref-walk could introduce overhead for large repositories with complex revision specifications. No explicit discussion of this trade-off or potential optimizations has occurred.

The v3 cover letter provides motivation (diagnosing performance issues in large repositories), but the commit message itself still does not explain the user-facing benefits or design rationale. Kaartic’s suggestion to incorporate cover letter material into the commit message remains unaddressed.
- **Documentation precision**: Patrick proposes tightening the language to use Git’s established terminology (e.g., "revisions" instead of "query clauses") and standardizing the synopsis to `[<revs>...]` to align with Git’s conventions. The v4 patch does not address this.
- **Revision-parsing defaults**: Patrick questions the necessity of `.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH` in `setup_revision_opt`, suggesting these may be overly restrictive. He proposes passing `NULL` to `setup_revisions()` to allow filtering by trees or blobs. The v4 patch retains the original defaults.
- **Test coverage**: Patrick requests additional tests for edge cases: filtering by trees/blobs (not just commits) and using revision options like `--filter=object:type=blob`. The v4 test coverage remains focused on commits and basic output formats.
- **Double ref-walk inefficiency**: The patch’s workaround for `setup_revisions()`’s lack of a custom ref-walk callback introduces a second ref-walk in `count_references()`, which could impact performance for large repositories or complex revision specifications. No discussion of this trade-off or potential optimizations has occurred.

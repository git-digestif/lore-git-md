Thread identity: `[PATCH v4] repo: add revision filtering support to 'git repo structure'`
Series version: v4 (single-patch series)
Originating author: Mark C. Chu-Carroll
Thread type: patch series (feature addition)

Core problem or goal: Add flexible revision-based filtering to the `git repo structure` command, enabling users to include or exclude specific revisions (commits, refs, or ranges) from the repository structure report. The feature aims to improve diagnostic capabilities for large repositories by allowing targeted analysis of subsets of the object graph. The patch uses Git’s standard `setup_revisions()` machinery, replacing the v1 `--no-<reftype>` approach with a design consistent with Git’s revision-parsing idioms. The goal remains uncontroversial in principle, but implementation details—particularly reachability logic, revision-parsing defaults, test coverage, documentation precision, and the double ref-walk inefficiency—remain under active discussion.

Current status: Under active review, procedurally clean but still blocked by unresolved substantive feedback. The v4 patch fixes the accidental corruption in `revision.c` and `revision.h` that blocked v3 but does not fully address the technical concerns raised in prior reviews. Key unresolved issues persist: commit message motivation, revision-parsing defaults (`.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`), test coverage for trees/blobs and revision options like `--filter=object:type=blob`, the inefficiency of a double ref-walk in `count_references()`, and now the handling of empty repositories. Patrick Steinhardt’s substantive feedback from v2, v3, and v4 remains partially unincorporated, and the author’s latest reply engages with some but not all of these concerns. The patch is eligible for substantive review, but its readiness depends on resolving the remaining open questions. Patrick’s latest review downplays the double ref-walk inefficiency as tolerable but reaffirms the empty repository test as a blocker, suggesting a v5 will be necessary to address the outstanding issues, particularly empty repository behavior and commit message clarity.

Key technical details:
- Files modified: `builtin/repo.c`, `Documentation/git-repo.adoc`, `t/t1901-repo-structure.sh` (corruption in `revision.c` and `revision.h` from v3 has been fixed).
- New CLI syntax: Revision-based filtering using `setup_revisions()` (e.g., `git repo structure <revision>... [--not <revision>...]`).
- Behavior: The command processes all objects reachable from the included revisions unless they are exclusively reachable via the excluded revisions. This avoids the transitive dependency omission issue of v1 by focusing on reachability rather than reference types. Empty repository handling is now a correctness concern: the command should succeed without arguments but currently fails with a confusing error.
- Symbols: Uses `struct rev_info` and `setup_revisions()` for parsing; replaces the v1 enum-based flag system in `count_references`. The `setup_revision_opt` struct retains `.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`, which Patrick Steinhardt questions as potentially overly restrictive (preventing filtering by trees or blobs). The author defends these defaults as necessary to avoid breaking in empty repositories but has not addressed Patrick’s proposal to pass `NULL` to `setup_revisions()` to allow broader filtering.
- Workaround: Due to `setup_revisions()`’s lack of a custom ref-walk callback, the patch performs a second ref-walk in `count_references()` to count references by type, introducing potential inefficiency for large repositories or complex revision specifications. The author acknowledges this trade-off but defends it as cleaner than defaulting to `--all`, which would fail in empty repositories. Patrick accepts this as a "sensible tradeoff" for consistency with Git’s revision-parsing idioms but notes it could impact performance, though he now downplays the concern as non-critical for this command.
- Test coverage: Expanded to 211 lines, validating edge cases (e.g., overlapping includes/excludes, output formats like table/lines/nul). Patrick’s latest review suggests reinstating the "empty repository" test (accidentally dropped in v4) as a blocker for correctness, and dropping the `ref^{tree}` test (as it overreaches into Git’s rev-walk machinery). The author rationalizes the omission of the "empty repository" test as intentional but Patrick’s pushback makes this a likely requirement for v5. Requests for tests involving trees/blobs and revision options like `--filter=object:type=blob` remain unaddressed.
- Performance: The double ref-walk could introduce overhead for large repositories with complex revision specifications, but Patrick now downplays this as non-critical for `git repo structure`, which is not on a performance-critical path. Object enumeration will likely dominate runtime in most cases.
- Documentation: The author accepts Patrick’s suggestions to explicitly define "reachable" (e.g., "objects reachable from a reference") and correct the misleading `^foo` example in `git-repo.adoc`. However, broader concerns about terminology (e.g., "revisions" vs. "query clauses") and synopsis alignment (`[<revs>...]`) remain unaddressed.

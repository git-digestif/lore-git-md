Thread identity: `[PATCH v5] repo: add revision filtering support to 'git repo structure'`
Series version: v5 (single-patch series)
Originating author: Mark C. Chu-Carroll
Thread type: patch series (feature addition)

Core problem or goal: Add flexible revision-based filtering to the `git repo structure` command, enabling users to include or exclude specific revisions (commits, refs, or ranges) from the repository structure report. The feature improves diagnostic capabilities for large repositories by allowing targeted analysis of subsets of the object graph. The patch uses Git’s standard `setup_revisions()` machinery, replacing the v1 `--no-<reftype>` approach with a design consistent with Git’s revision-parsing idioms. The goal is uncontroversial, but implementation details—particularly revision-parsing defaults, test coverage for trees/blobs, the double ref-walk inefficiency, and documentation precision—remain under active discussion.

Current status: Under active review, procedurally clean and closer to readiness after addressing critical feedback from v4 and v5. The v5 patch reinstates the "empty repository" test, improves commit message motivation, and cleans up control flow redundancies. Key unresolved issues from prior versions have been partially addressed: Patrick Steinhardt’s substantive feedback on error messages, test formatting, and code organization is now incorporated in this update, leaving only minor nits (trailing newline, test cleanup) as open items. Remaining concerns from earlier reviews persist but are now narrower in scope: revision-parsing defaults (`.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`), test coverage for trees/blobs and revision options like `--filter=object:type=blob`, and the double ref-walk inefficiency in `count_references()`. Patrick Steinhardt explicitly states he is now happy with the v5 patch, signaling the patch is very close to ready. A v6 may still be required to address the remaining nits and any further minor feedback, but no major technical blockers remain.

Key technical details:
- Files modified: `builtin/repo.c`, `Documentation/git-repo.adoc`, `t/t1901-repo-structure.sh`.
- New CLI syntax: Revision-based filtering using `setup_revisions()` (e.g., `git repo structure <revision>... [--not <revision>...]`).
- Behavior: The command processes all objects reachable from the included revisions unless they are exclusively reachable via the excluded revisions. Empty repository handling is now correct: the command succeeds without arguments (though it may be "pointless" in such cases). The implementation avoids the transitive dependency omission issue of v1 by focusing on reachability.
- Symbols: Uses `struct rev_info` and `setup_revisions()` for parsing; replaces the v1 enum-based flag system in `count_references`. The `setup_revision_opt` struct retains `.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`, which Patrick Steinhardt questions as potentially overly restrictive (preventing filtering by trees or blobs). The author defends these defaults as necessary to avoid breaking in empty repositories but has not addressed Patrick’s proposal to pass `NULL` to `setup_revisions()` to allow broader filtering.
- Workaround: Due to `setup_revisions()`’s lack of a custom ref-walk callback, the patch performs a second ref-walk in `count_references()` to count references by type. This inefficiency persists but is now considered tolerable for a diagnostic tool. Object enumeration will likely dominate runtime in most cases.
- Test coverage: Expanded to 208 lines, validating edge cases (e.g., overlapping includes/excludes, output formats like table/lines/nul). The "empty repository" test is reinstated, but tests for trees/blobs and revision options like `--filter=object:type=blob` remain missing. Patrick’s suggestion to drop the `ref^{tree}` test (as it overreaches into Git’s rev-walk machinery) is not yet addressed.
- Documentation: The commit message now incorporates motivation from the cover letter, explaining the user-facing benefits of revision filtering for diagnosing performance issues. The `git-repo.adoc` documentation clarifies terminology (e.g., "reachable") and corrects misleading examples (e.g., `^foo`). Error messages now follow Git’s established pattern for unrecognized arguments (naming the problematic argument rather than using a generic "too many arguments" message).

Open questions and loose ends:
- **Revision-parsing defaults**: Patrick Steinhardt questions the necessity of `.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH` in `setup_revision_opt`, suggesting these may be overly restrictive. He proposes passing `NULL` to `setup_revisions()` to allow filtering by trees or blobs. The author defends the current defaults as necessary to avoid breaking in empty repositories but has not engaged with Patrick’s broader concern about restrictiveness.
- **Test coverage**: Patrick requests:
  - Tests for filtering by trees/blobs (not just commits) and using revision options like `--filter=object:type=blob`.
  - Dropping the `ref^{tree}` test (as it overreaches into Git’s rev-walk machinery).
  These remain unaddressed.
- **Double ref-walk inefficiency**: The patch’s workaround for `setup_revisions()`’s lack of a custom ref-walk callback introduces a second ref-walk in `count_references()`. Patrick now downplays this as non-critical for `git repo structure`, but the inefficiency remains a trade-off for consistency with Git’s idioms.
- **Minor nits**: Trailing newline in the test file and repetitive `test_must_be_empty` replacements slipped into the patch. Patrick recommends dropping the latter as they belong in a separate preparatory commit. These are surface-level but should be addressed in a v6.

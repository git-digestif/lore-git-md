Thread type: patch series (feature addition)

Core problem or goal: Add flexible revision-based filtering to the `git repo structure` command, enabling users to include or exclude specific revisions (commits, refs, or ranges) from the repository structure report. The feature aims to improve diagnostic capabilities for large repositories by allowing targeted analysis of subsets of the object graph. The v3 patch continues to use Git’s standard `setup_revisions()` machinery, replacing the v1 `--no-<reftype>` approach with a design consistent with Git’s revision-parsing idioms. While the goal remains uncontroversial in principle, implementation details—particularly reachability logic, revision-parsing defaults, test coverage, documentation precision, and the presence of accidental corruption in the patch—remain under active discussion.

Current status: Under active review, but blocked by procedural issues. The v3 patch implements revision-based filtering via `struct rev_info` and `setup_revisions()`, supporting arbitrary revision specifications (e.g., `git repo structure --branches --not --tags` or `git repo structure master`). However, Junio C Hamano’s review of v3 flags two nonsensical, unintended hunks in the patch (corrupting comments in `revision.c` and `revision.h` with stray characters), indicating the author did not proofread the patch before submission. These errors must be fixed before substantive review can proceed. Key unresolved issues from v2 persist: commit message motivation, documentation precision, revision-parsing defaults (`.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`), test coverage for trees/blobs and revision options like `--filter=object:type=blob`, the inefficiency of a double ref-walk in `count_references()`, and now the accidental corruption. No technical feedback from v2 has been incorporated yet, as the author’s changes focus on documentation and test expansion rather than addressing Patrick Steinhardt’s substantive concerns.

Key technical details:
- Files modified: `builtin/repo.c`, `Documentation/git-repo.adoc`, `t/t1901-repo-structure.sh`, and unintentionally corrupted comments in `revision.c` and `revision.h`.
- New CLI syntax: Revision-based filtering using `setup_revisions()` (e.g., `git repo structure <revision>... [--not <revision>...]`).
- Behavior: The command processes all objects reachable from the included revisions unless they are exclusively reachable via the excluded revisions. This avoids the transitive dependency omission issue of v1 by focusing on reachability rather than reference types.
- Symbols: Uses `struct rev_info` and `setup_revisions()` for parsing; replaces the v1 enum-based flag system in `count_references`. The `setup_revision_opt` struct retains `.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`, which Patrick Steinhardt questions as potentially overly restrictive (preventing filtering by trees or blobs).
- Workaround: Due to `setup_revisions()`’s lack of a custom ref-walk callback, the patch performs a second ref-walk in `count_references()` to count references by type, introducing potential inefficiency for large repositories or complex revision specifications.
- Test coverage: Expanded to 211 lines, validating edge cases (e.g., overlapping includes/excludes, output formats like table/lines/nul). Patrick’s requests for tests involving trees/blobs and revision options like `--filter=object:type=blob` remain unaddressed.
- Performance: No explicit discussion yet, but the double ref-walk could introduce overhead for large repositories with complex revision specifications. The accidental corruption does not affect performance but undermines confidence in the patch’s readiness.

Open questions and loose ends:

- **Double ref-walk inefficiency**: The patch’s workaround for `setup_revisions()`’s lack of a custom ref-walk callback introduces a second ref-walk in `count_references()`, which could impact performance for large repositories or complex revision specifications.

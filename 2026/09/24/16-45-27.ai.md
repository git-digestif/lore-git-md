This is a **maintainer's reply** in the ongoing discussion about the architectural direction of the first patch in Maciej Ciemborowicz's v5 bugfix series. The series aims to restore old-OID reporting in the reference-transaction hook for branch/tag deletions, but Patrick Steinhardt has raised **fundamental objections** to the patch's approach, arguing that callers needing conditional logic should use the lower-level transaction API instead of extending `refs_delete_refs()`.

Junio C Hamano, the maintainer, begins by admitting he missed a key point in the commit message: the phrase *"callers cannot preserve old values that they have already resolved"* is unclear, and he asks Patrick for clarification. This suggests the commit message may need rewording to better explain the motivation.

On the core architectural question—whether `refs_delete_refs()` should be extended or callers should use transactions directly—Junio is **neutral but leaning toward caution**. He acknowledges Patrick's point that the function exists as a convenience wrapper for simple, unconditional deletions, and that adding conditional logic (old-OID checks, partial failures) complicates its purpose. However, he also notes that updating all callers to use transactions might not reduce complexity, as the amount of code required could end up being similar.

Junio does not outright reject either approach but emphasizes the need to see concrete code before deciding. His tone is measured, and he avoids endorsing Patrick's proposal outright, leaving room for Maciej to defend the current design or propose an alternative. The key unresolved questions are:
1. **Clarity of intent**: The commit message must better explain why callers cannot preserve old OIDs *before* deletion (e.g., due to the hook's expectations or performance constraints).
2. **Architectural trade-offs**: Is extending `refs_delete_refs()` cleaner than rewriting callers to use transactions? Junio wants to see both approaches implemented to compare.
3. **Consistency**: Patrick argues that the patch repurposes null-OID semantics and duplicates transaction API functionality, which could set a confusing precedent.

The series is already merged to `next`, but this discussion could force a rewrite before it graduates to `master`. The thread remains open, with the ball in Maciej's court to either:
- Revise the patch to address Junio's clarity concerns and defend the current approach, or
- Pivot to Patrick's proposal, which would require significant refactoring of callers like `builtin/branch.c` and `builtin/fetch.c`.

**Key technical details to watch**:
- The `refs_delete_refs()` function signature (now with `old_oids` and `failed_refs` parameters).
- The use of `REF_TRANSACTION_ALLOW_FAILURE` to enable granular error reporting.
- The null-OID semantics (currently repurposed to mean "unconditional deletion").
- The transaction API's existing support for old-OID checks and partial failures.

This is a **high-stakes design discussion** with implications for the refs subsystem's API and the reference-transaction hook's reliability. The outcome will affect how Git handles batch ref deletions and hook payloads for all ref-modifying commands.

This is a review reply in an ongoing refactoring thread about the `fetch.followRemoteHEAD` configuration setting. Matt Hunter, who originally contributed the config option, chimes in with two tangential suggestions—not as blockers for Colin Hinton’s patch, but as food for thought.

First, Matt suggests that unrecognized values for `fetch.followRemoteHEAD` should default to `FOLLOW_REMOTE_NEVER` rather than `FOLLOW_REMOTE_UNCONFIGURED`. His reasoning is that a user who explicitly sets a value (even one Git doesn’t recognize) probably doesn’t want the default behavior, and `NEVER` is the least surprising fallback. He notes this could apply to both the global and per-remote variants of the setting.

Second, Matt floats the idea of skipping the remote HEAD query entirely when `FOLLOW_REMOTE_CREATE` is set and a local HEAD symref already exists. This would save network overhead, but he acknowledges it’s a separate topic and not something to tack onto Colin’s patch. He ties it to Junio’s earlier suggestion about simplifying the `do_set_head` logic, hinting that if the condition grows more complex, it might be worth encapsulating it in a helper function.

The email is surface-level in the context of the current patch—it doesn’t engage with the core refactoring work (lazy validation, remote-side parser changes, or valueless truth settings). Instead, it offers forward-looking design ideas that could influence future iterations of the feature. Neither suggestion has been debated yet, so they remain open-ended.

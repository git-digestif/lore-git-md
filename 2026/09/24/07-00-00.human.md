This is a bugfix for the `contrib/credential/libsecret` credential helper, addressing a crash and silent data loss that occurs when retrieving stored credentials from the GNOME keyring. The patch is part of an ongoing discussion about the best way to fix the issue, with the author, Daniel Martí, and Junio C Hamano having exchanged substantive reviews on design trade-offs.

The problem arises when `secret_service_search_sync()` is called with the `SECRET_SEARCH_LOAD_SECRETS` flag. This flag is supposed to batch-load secrets for all matched items, but it silently discards failures—such as when an item is locked or deleted by another process—and omits those items from the reply. When the helper later tries to access the secret of such an item, it crashes with assertion failures, losing the password even if it was still retrievable. Daniel’s patch removes the flag and explicitly loads the secret for the matched item using `secret_item_load_secret_sync()`, which properly reports errors.

The discussion has centered on whether to preserve the batch-fetch optimization (Junio’s preference) or prioritize simplicity and reliability by eliminating the error-prone path (Daniel’s approach). Daniel argues that `SECRET_SEARCH_LOAD_SECRETS` is not a true optimization—it still requires two round trips (SearchItems + GetSecrets)—and that his approach maintains the same round-trip count in the common case while ensuring all errors are surfaced. Junio’s alternative would retain the flag and conditionally load secrets only when `secret_item_get_secret()` returns NULL, adding a third round trip in rare cases.

This reply from M Hickford asks whether the issue is an upstream bug in libsecret, noting that the documentation for `SECRET_SEARCH_LOAD_SECRETS` is truncated and unclear about the consequences of secret-loading failures. The question is relevant but does not advance the design discussion; it may prompt further investigation into whether the libsecret behavior is intentional or a bug. The patch itself remains well-motivated and clearly explains the problem and solution, though the lack of test coverage is a minor weakness given the reproducibility challenges. The next step is likely a v2 patch from Daniel addressing Junio’s feedback on clarity and self-containment.

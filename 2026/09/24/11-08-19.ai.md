This is a **substantive review** of the second patch in the v5 series fixing the reference-transaction hook regression. Patrick Steinhardt challenges the patch’s approach at the architectural level, arguing that the fix is too narrow and should instead be implemented at the transaction layer to benefit all ref-modifying commands, not just `git branch` and `git tag`.

The review proposes an alternative design: instead of modifying `git branch` and `git tag` to pass resolved old OIDs to `refs_delete_refs()`, the transaction system itself should resolve and queue the old OID for every ref modification, regardless of whether the caller provided one. This would ensure the reference-transaction hook always receives the correct old OID, eliminating the need to update individual call sites. Patrick acknowledges this is technically a backward-incompatible change but notes that the hook is considered an internal interface, and past behavior changes have been allowed.

The key trade-off is between a localized, low-risk fix (the current patch) and a broader, more invasive change that would affect every ref-modifying command. The current patch is minimal, well-tested, and preserves the performance optimization from the original regression commit, but it only fixes the issue for two commands. Patrick’s alternative would fix it for all commands (including future ones) but requires deeper changes to the transaction system and could introduce new edge cases.

This review reopens the design discussion for the entire series. The author must now decide whether to defend the current approach (arguing that it is safer and sufficient for the regression) or pivot to Patrick’s proposal, which would likely require a major rewrite of the series. The outcome will determine whether the fix remains a targeted bugfix or becomes a broader refactoring of the transaction system.

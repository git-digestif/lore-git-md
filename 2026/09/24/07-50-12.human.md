This is a refactoring patch that continues the discussion around deferring validation of the `fetch.followRemoteHEAD` configuration setting. Matt Hunter proposes a concrete follow-up patch to address the gaps identified in Colin Hinton’s original submission, particularly the premature validation in `remote.c` and the handling of valueless truth settings.

The patch introduces a new `follow_remote_head_target` struct to encapsulate both the parsed enum value and the optional branch name for `warn-if-not-*` settings, replacing the raw string parsing logic in both `builtin/fetch.c` and `remote.c`. This change ensures that validation is deferred until the setting is actually used, aligning the remote-side parser with the local-side refactoring. The patch also simplifies `remote.c` by storing the raw config string (`follow_remote_head_raw`) and deferring parsing to `get_follow_remote_head()`, which is now shared between both parsers.

Two awkward bits remain: `builtin/remote.c::set_head()` still needs to parse the raw string to check for `"always"`, and the warning message in `get_follow_remote_head()` is misleading because it references `fetch.followRemoteHEAD` even when parsing `remote.<name>.followRemoteHEAD`. Matt notes these issues but does not resolve them in this patch, leaving room for further cleanup. The patch is well-structured and directly addresses the core problem, but the shared parsing logic and warning message could benefit from refinement in a follow-up.

The discussion remains constructive, with no unresolved disagreements. The patch is a logical next step in the refactoring effort and looks like a solid foundation for the final version. If the awkward bits are addressed, this could be a clean solution to the premature validation problem.

This is a **major pivot** in the ongoing bugfix series that restores old-OID reporting in the reference-transaction hook. The author, Maciej Ciemborowicz, **concedes Patrick Steinhardt’s architectural objection** and abandons the current approach of extending `refs_delete_refs()`.

Instead, Maciej proposes a **transaction-layer solution**: the common transaction hook layer will record a separate "observed old value" for updates where callers did not supply one. This value will be used **only as hook input** and will not set `REF_HAVE_OLD` or otherwise constrain the update. The change will leave `refs_delete_refs()`, `ref_transaction_delete()`, and all callers **unchanged**, eliminating the need for the `failed_refs` interface and special null-OID handling introduced in v5.

The pivot addresses Patrick’s core concern—that `refs_delete_refs()` should remain a simple wrapper for unconditional deletions—while still fixing the regression. It also sidesteps the redundant failure counting and API semantics debates that surfaced in v5. However, the new approach will require **rewriting the entire series** to operate at the transaction layer, likely affecting all three patches. The series is currently merged to `next`, but this change would force a re-roll and delay graduation to `master`.

Key implications:
- **Scope**: The fix will now apply to **all ref-modifying commands** (not just `git branch` and `git tag`), aligning with Patrick’s preference for a transaction-layer solution.
- **Complexity**: The transaction hook layer must now resolve and cache old OIDs for updates where callers did not supply them, adding subtle state management.
- **Performance**: The v5 optimization (bulk tag deletion in ~0.85s) should be preserved, but the new approach may introduce additional ref resolution overhead.
- **Backward compatibility**: The hook will see the correct old OID for deletions, restoring pre-2.31 behavior without breaking existing callers.

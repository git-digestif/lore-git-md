Core problem or goal: Git’s documentation currently scatters merge-conflict advice across multiple command man pages, leading to duplication, omissions, and user confusion. The series introduces a dedicated `gitmergeconflicts(7)` guide to centralize this information, improve clarity (e.g., "ours" vs. "theirs"), and provide practical examples. V4 incorporates all feedback from prior versions, including Junio’s squashable refinements to the `diff3` example, Patrick Steinhardt’s editorial suggestions, and mechanical fixes. The guide now uses neutral language ("has" instead of "added") in the `diff3` example, demonstrates a scenario where both sides *removed* a fruit from the original list to clarify how the common ancestor reveals intent, and generalizes the `--skip` explanation to cover all multi-step operations (e.g., `git revert`). The exhaustive list of commands that can cause conflicts (`git merge`, `git rebase`, `git cherry-pick`, `git pull`, `git am -3`, `git checkout -m`, `git stash pop`, `git revert`) is finalized, with Junio’s confirmation that `git am -3` is a valid three-way merge operation. The `zdiff3` deprecation note is removed entirely, deferring a more thorough explanation to future work.

No on-disk or runtime behavior changes. The new guide is purely additive.
- Structure of the new guide: Organized as a practical, example-driven document with sections covering:
  - "WHAT IS A MERGE CONFLICT?" – Foundational explanation of merge conflicts, when they occur, and Git’s behavior during conflicts (e.g., staging successfully merged files, leaving conflicted files unstaged with markers). Defines "original" (common ancestor) and uses "configuration variable."
  - Exhaustive list of commands that can cause conflicts: `git merge`, `git rebase`, `git cherry-pick`, `git pull`, `git am -3`, `git checkout -m`, `git stash pop`, `git revert`.
  - Resolution paths (fix or abort), with formal phrasing: "You can either resolve the conflict or abort the operation."
  - Merge conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`, `|||||||` in `diff3`) and the four-step resolution process (identify, edit, stage, continue).
  - Tools for handling conflicts, grouped to distinguish static views (`git diff`, `git log --merge --patch <filename>`) from dynamic ones (`git diff AUTO_MERGE`, graphical merge tools). Includes `merge.conflictstyle=diff3` (actively promoted) and omits `zdiff3` entirely.
  - "OURS" AND "THEIRS" – Explicitly ties "ours" and "theirs" to `HEAD` and the other commit, clarifies their relationship to conflict markers, and explains the "upside down" behavior during rebases.
  - `git diff AUTO_MERGE` – Defined upfront before first use, clarifying it represents the state Git would have produced if no conflicts occurred.
  - Side-by-side examples of `diff3` vs. default merge conflict format, demonstrating how the common ancestor reveals the *intent* behind conflicting changes. The `diff3` example now uses "lines" instead of "code" and illustrates a scenario where both sides removed a fruit (banana or cherry) from the original list, emphasizing how the common ancestor prevents mismerges. Junio’s latest email flags minor issues in this example: inconsistent indentation (tabs vs. spaces) in conflict markers and a typo ("removed one fruit to the list" should be "from the list").
  - Sample `git status` output to guide users on `--abort`/`--continue` commands.
- Approved additions/corrections: The `git log --merge --patch <filename>` section, clarification of `CHERRY_PICK_HEAD`, Patrick Steinhardt’s rewording for "ours/theirs," mention of `git merge-tool --tool-help`, `linkgit:` macros, and retention of command-specific details (e.g., `--skip` in `git-rebase.adoc`).

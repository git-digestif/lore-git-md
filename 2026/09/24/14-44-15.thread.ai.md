Thread identity: Documentation patch series introducing `gitmergeconflicts(7)`, a new man page consolidating merge conflict resolution guidance. Series version: v2 (complete, all feedback addressed; v3 expected for content refinements and trailer adjustments). Originating author: Julia Evans (via GitGitGadget). Thread type: patch series.

Core problem or goal: Git’s current documentation scatters merge-conflict advice across multiple command man pages, leading to duplication, omissions, and user confusion. The series introduces a dedicated `gitmergeconflicts(7)` guide to centralize this information, improve clarity (e.g., "ours" vs. "theirs"), and provide practical examples. V2 explicitly balances centralization with preserving command-specific nuances, particularly for operations like `git cherry-pick` that involve unique pseudo-refs (`CHERRY_PICK_HEAD`) and workflows. The guide’s terminology, foundational explanations, and tooling advice have been refined based on v1 and v2 feedback, with key improvements: (1) a new "WHAT IS A MERGE CONFLICT?" section, (2) a rewritten "OURS" AND "THEIRS" explanation, (3) active promotion of `merge.conflictstyle=diff3` as a best practice (supported by Junio’s detailed examples), and (4) retention of command-specific details in the man pages while linking to the new guide for general advice. Junio’s latest review identifies **omissions** (`git am -3`, `git checkout -m`), **terminology gaps** ("original" as common ancestor, "configuration variable"), **unexplained conflict markers** (`|||||||` in `diff3`), and **semantic conflicts** (Git’s inability to detect logical inconsistencies). His feedback also targets **clarity issues** (`AUTO_MERGE` definition, `zdiff3` deprecation) and **stylistic preferences** (contractions, project-preferred terms).

- Structure of the new guide: Organized as a practical, example-driven document with sections covering:
  - "WHAT IS A MERGE CONFLICT?" – A foundational explanation of what merge conflicts are, when they occur, and Git’s behavior during conflicts (e.g., staging successfully merged files, leaving conflicted files unstaged with markers). This section will be expanded to define "original" (common ancestor) and use "configuration variable" instead of "configuration option."
  - When merge conflicts occur (`git merge`, `git rebase`, `git cherry-pick`, `git pull`, `git revert`, **new: `git am -3`, `git checkout -m`**).
  - Resolution paths (fix or abort).
  - Merge conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`, **new: `|||||||` in `diff3`**) and the four-step resolution process (identify, edit, stage, continue).
  - Tools for handling conflicts (graphical merge tools, `merge.conflictstyle=diff3`/`zdiff3` (with `zdiff3` deprecated or omitted), `git show :1:filename`).
  - "OURS" AND "THEIRS" – Explicitly ties "ours" and "theirs" to `HEAD` and the other commit, clarifies their relationship to conflict markers, and explains the "upside down" behavior during rebases. The updated section improves technical accuracy by separating commit-level terms from index stages.
  - `git diff AUTO_MERGE` – **Reordered to define `AUTO_MERGE` before use**, clarifying it represents the state Git would have produced if no conflicts occurred.
  - Side-by-side examples of `diff3` vs. `zdiff3` output, including **Junio’s detailed examples** demonstrating how the common ancestor reveals the *intent* behind conflicting changes. **`zdiff3` will be deprecated or omitted.**
  - Sample `git status` output to guide users on `--abort`/`--continue` commands.
  - Approved additions/corrections:
    - The `git log --merge -p <filename>` section, with the approved wording: "will print out all commits which caused the merge conflict for `<filename>`, and the diff of how they changed the file."
    - Clarification that `CHERRY_PICK_HEAD` is available any time a cherry-pick stops due to conflict, regardless of whether one or multiple commits are being picked.
    - Patrick Steinhardt’s rewording for "ours/theirs" (revised to explicitly tie "ours" and "theirs" to `HEAD` and the other commit).
    - Mention of `git merge-tool --tool-help` to list available merge tools.
    - Use of `linkgit:` macros for cross-referencing other man pages.
    - Note that `git <thing> --continue` (e.g., `git merge --continue`) is the modern and consistent choice for conflict resolution, with `git commit` as an older alternative.
    - **New: Acknowledgment of semantic conflicts** (e.g., Git cannot detect inconsistent function renames).
  - **Deferred enhancements**:
    - **Commit accessibility**: Patrick Steinhardt’s proposal to embed commit details (IDs, messages, dates) directly into conflict markers. Julia Evans has endorsed the practical benefits but deferred implementation to a follow-up patch after Patrick’s GitLab prototype.
    - **`merge.conflictstyle=diff3`**: Junio’s and Patrick’s strong endorsement for making `diff3` the default conflict style, with Julia’s user feedback and Junio’s **detailed examples** supporting its practical impact.

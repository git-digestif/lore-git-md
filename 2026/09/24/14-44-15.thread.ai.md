Thread identity: Documentation patch series introducing `gitmergeconflicts(7)`, a new man page consolidating merge conflict resolution guidance. Series version: v3 (content refinements, wording tweaks, and trailer adjustments finalized). Originating author: Julia Evans (via GitGitGadget). Thread type: patch series.

Core problem or goal: Git’s current documentation scatters merge-conflict advice across multiple command man pages, leading to duplication, omissions, and user confusion. The series introduces a dedicated `gitmergeconflicts(7)` guide to centralize this information, improve clarity (e.g., "ours" vs. "theirs"), and provide practical examples. V3 incorporates all feedback from Junio’s v2 review and his follow-up v3 review, addressing omissions (`git am -3`, `git checkout -m`, `git stash pop`, `git revert`, `|||||||` marker in `diff3`), terminology gaps ("original" as common ancestor, "configuration variable"), unexplained elements (semantic conflicts, `AUTO_MERGE`), stylistic refinements (grouping conflict-resolution tools, cohesive phrasing for Git’s refusal to guess resolutions, deprecating `zdiff3`), and formal tone (avoiding contractions like "Here's" and "there's"). The guide’s foundational explanations, terminology, and tooling advice have been refined through v1, v2, and v3 feedback, with key improvements retained: (1) a "WHAT IS A MERGE CONFLICT?" section, (2) a rewritten "OURS" AND "THEIRS" explanation, (3) active promotion of `merge.conflictstyle=diff3` as a best practice, and (4) retention of command-specific details in man pages while linking to the new guide for general advice.

- Behavior changes: Replaces duplicated conflict-resolution sections in existing man pages with cross-references to the new guide, but retains command-specific details where necessary (e.g., `CHERRY_PICK_HEAD` in `git-cherry-pick.adoc`, `--skip` in `git-rebase.adoc`). No on-disk or runtime behavior changes. The new guide is purely additive and does not alter existing functionality.
- Structure of the new guide: Organized as a practical, example-driven document with sections covering:
  - "WHAT IS A MERGE CONFLICT?" – Foundational explanation of what merge conflicts are, when they occur, and Git’s behavior during conflicts (e.g., staging successfully merged files, leaving conflicted files unstaged with markers). Defines "original" (common ancestor) and uses "configuration variable."
  - When merge conflicts occur (exhaustive list: `git merge`, `git rebase`, `git cherry-pick`, `git pull`, `git am -3`, `git checkout -m`, `git stash pop`, `git revert`).
  - Resolution paths (fix or abort), with Junio’s requested phrasing refinement: "You can either resolve the conflict or abort the operation."
  - Merge conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`, `|||||||` in `diff3`) and the four-step resolution process (identify, edit, stage, continue).
  - Tools for handling conflicts, grouped to distinguish static views (`git diff`, `git log --merge -p <filename>`) from dynamic ones (`git diff AUTO_MERGE`, graphical merge tools). Includes `merge.conflictstyle=diff3` (actively promoted) and `zdiff3` (explicitly deprecated with a note). The `git log --merge -p <filename>` section now omits `--left-right` as Julia argued it would complicate the guide without clear benefit.
  - "OURS" AND "THEIRS" – Explicitly ties "ours" and "theirs" to `HEAD` and the other commit, clarifies their relationship to conflict markers, and explains the "upside down" behavior during rebases.
  - `git diff AUTO_MERGE` – Defined upfront before first use, clarifying it represents the state Git would have produced if no conflicts occurred.
  - Side-by-side examples of `diff3` vs. `zdiff3` output, including Junio’s detailed examples demonstrating how the common ancestor reveals the *intent* behind conflicting changes.
  - Sample `git status` output to guide users on `--abort`/`--continue` commands.
  - Approved additions/corrections:
    - The `git log --merge -p <filename>` section, with the approved wording: "will print out all commits which caused the merge conflict for `<filename>`, and the diff of how they changed the file."
    - Clarification that `CHERRY_PICK_HEAD` is available any time a cherry-pick stops due to conflict, regardless of whether one or multiple commits are being picked.
    - Patrick Steinhardt’s rewording for "ours/theirs" (revised to explicitly tie "ours" and "theirs" to `HEAD` and the other commit).
    - Mention of `git merge-tool --tool-help` to list available merge tools.
    - Use of `linkgit:` macros for cross-referencing other man pages.
    - Note that `git <thing> --continue` (e.g., `git merge --continue`) is the modern and consistent choice for conflict resolution, with `git commit` as an older alternative.
    - Acknowledgment of semantic conflicts (e.g., Git cannot detect inconsistent function renames).
    - Cohesive phrasing for Git’s refusal to guess resolutions (e.g., "Git will not try to guess how to resolve the conflict").
    - Simplified wording in `git-revert.adoc`: "Reverting a commit may result in a merge conflict."
    - Streamlined phrasing in `git-cherry-pick.adoc`: Removal of the vague introductory sentence about merge conflicts and relocation of the cross-reference to `gitmergeconflicts(7)` to the `SEE ALSO` section.

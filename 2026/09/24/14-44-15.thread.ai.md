Thread identity: Documentation patch series introducing `gitmergeconflicts(7)`, a new man page consolidating merge conflict resolution guidance. Series version: v1 (initial, pending mechanical integration fixes, `command-list.txt` registration, content refinements including cherry-pick-specific adjustments, foundational explanations, terminology clarifications, new tooling advice, and Patrick Steinhardt’s proposed commit-accessibility enhancement). Originating author: Julia Evans (via GitGitGadget). Thread type: patch series.

Core problem or goal: Git’s current documentation scatters merge-conflict advice across multiple command man pages (`git merge`, `git rebase`, `git revert`, `git cherry-pick`, `git pull`), leading to duplication, omissions, and user confusion. The series introduces a dedicated `gitmergeconflicts(7)` guide to centralize this information, improve clarity (e.g., clarifying "ours" vs. "theirs"), and provide practical examples based on user feedback. The goal is to replace redundant sections in existing man pages with cross-references to the new guide, reducing maintenance burden and improving user experience. The series now explicitly balances centralization with preserving command-specific nuances, particularly for operations like `git cherry-pick` that involve unique pseudo-refs (`CHERRY_PICK_HEAD`) and workflows. Junio’s and Patrick Steinhardt’s reviews have clarified that the new guide is not a complete substitute for removed sections, especially for cherry-pick-specific details, which must be retained in the command’s man page. The guide’s terminology, foundational explanations, and tooling advice are also under refinement to improve clarity and practical utility, with Julia Evans prioritizing user-tested practicality over theoretical completeness. Recent discussion has elevated three concrete improvements: (1) making commit information (messages or IDs) more accessible during conflict resolution, (2) promoting `merge.conflictstyle=diff3` as a best practice, with Junio C Hamano and Patrick Steinhardt strongly advocating for its default adoption, and (3) adding a foundational "WHAT IS A MERGE CONFLICT?" section to address gaps in introductory context. Junio’s latest contributions provide **detailed examples** demonstrating how `diff3`’s common ancestor reveals the *intent* behind conflicting changes, transforming it from a stylistic preference into an essential tool for correct resolution. These examples are ready for direct incorporation into the guide and significantly enhance its practical utility. Patrick Steinhardt’s **commit-accessibility enhancement**—embedding commit details (IDs, messages, dates) directly into conflict markers—remains under discussion, with Julia Evans enthusiastically endorsing its practical benefits (e.g., commit messages and dates providing immediate context) and suggesting it may be actively promoted in the guide. The exact implementation (e.g., embedding vs. discoverability via commands like `git show`) remains under discussion, and Patrick plans to prototype this in GitLab. Junio’s latest email introduces a new design discussion: whether minor code changes—such as updating conflict markers or rewording `git status` output—should be considered to improve the documentation’s clarity, even though the series is currently documentation-only. Julia’s response endorses the idea of "documentation-driven development," where writing documentation reveals pain points that may justify small code adjustments, but she does not propose concrete changes yet. She brainstorms potential improvements to `git status` output during conflicts, identifying five specific issues: (1) misleading advice to use `git pull` mid-conflict, (2) premature suggestion to run `git add` on files still containing conflict markers, (3) the term "unmerged" potentially being less intuitive than "conflicted," (4) redundant advice to use `git add`, and (5) inconsistent phrasing ("fix conflicts" vs. "mark resolution"). While some of these are surface-level wording tweaks, others (like suppressing `git pull` advice during conflicts) would require conditional logic in the advice system. Julia acknowledges the complexity of these changes and does not commit to implementing them, but her response signals openness to follow-up patches if a clear, low-risk improvement emerges.

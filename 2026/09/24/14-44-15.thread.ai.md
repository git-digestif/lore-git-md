Core problem or goal: Git’s current documentation scatters merge-conflict advice across multiple command man pages (`git merge`, `git rebase`, `git revert`, `git cherry-pick`, `git pull`), leading to duplication, omissions, and user confusion. The series introduces a dedicated `gitmergeconflicts(7)` guide to centralize this information, improve clarity (e.g., clarifying "ours" vs. "theirs"), and provide practical examples based on user feedback. The goal is to replace redundant sections in existing man pages with cross-references to the new guide, reducing maintenance burden and improving user experience. V2 explicitly balances centralization with preserving command-specific nuances, particularly for operations like `git cherry-pick` that involve unique pseudo-refs (`CHERRY_PICK_HEAD`) and workflows. The guide’s terminology, foundational explanations, and tooling advice have been refined based on v1 feedback, with three key improvements: (1) a new "WHAT IS A MERGE CONFLICT?" section (addressing D. Ben Knoble’s and Junio’s requests), (2) a rewritten "OURS" AND "THEIRS" explanation (per Patrick Steinhardt’s feedback), and (3) active promotion of `merge.conflictstyle=diff3` as a best practice (supported by Junio’s detailed examples). Junio’s latest contributions provide **detailed examples** demonstrating how `diff3`’s common ancestor reveals the *intent* behind conflicting changes, transforming it from a stylistic preference into an essential tool for correct resolution. These examples are now incorporated into the guide. Patrick Steinhardt’s **commit-accessibility enhancement**—embedding commit details (IDs, messages, dates) directly into conflict markers—remains under discussion, with Julia Evans enthusiastically endorsing its practical benefits (e.g., commit messages and dates providing immediate context) and suggesting it may be actively promoted in the guide. The exact implementation (e.g., embedding vs. discoverability via commands like `git show`) remains under discussion, and Patrick plans to prototype this in GitLab.

- Structure of the new guide: Organized as a practical, example-driven document with sections covering:
  - **New in v2**: "WHAT IS A MERGE CONFLICT?" – A foundational explanation of what merge conflicts are, when they occur, and Git’s behavior during conflicts (e.g., staging successfully merged files, leaving conflicted files unstaged with markers). This section avoids technical jargon and focuses on practical, user-tested clarity. Junio’s feedback refined the wording to improve directness and precision, though Julia retains "will not try to guess" to emphasize Git’s intentional conservatism.
  - When merge conflicts occur (`git merge`, `git rebase`, `git cherry-pick`, `git pull`, `git revert`).
  - Resolution paths (fix or abort).
  - Merge conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`) and the four-step resolution process (identify, edit, stage, continue).
  - Tools for handling conflicts (graphical merge tools, `merge.conflictstyle=diff3`/`zdiff3`, `git show :1:filename`).
  - **Rewritten in v2**: "OURS" AND "THEIRS" – Explicitly ties "ours" and "theirs" to `HEAD` and the other commit, clarifies their relationship to conflict markers, and explains the "upside down" behavior during rebases. The updated section improves technical accuracy by separating commit-level terms ("ours", "theirs", "base") from index stages ("stage 1/2/3"), while deferring deeper explanations to `gitdatamodel(7)`.
  - `git diff AUTO_MERGE` for tracking progress.
  - Side-by-side examples of `diff3` vs. `zdiff3` output, now including **Junio’s detailed examples** demonstrating how the common ancestor reveals the *intent* behind conflicting changes.
  - Sample `git status` output to guide users on `--abort`/`--continue` commands.
  - **Approved additions/corrections**:
    - The `git log --merge -p <filename>` section, with the approved wording: "will print out all commits which caused the merge conflict for `<filename>`, and the diff of how they changed the file." The mechanism of the `--merge` option (implying a `HEAD...<other>` revision range) is included to explain the command’s behavior.
    - Clarification that `CHERRY_PICK_HEAD` is available any time a cherry-pick stops due to conflict, regardless of whether one or multiple commits are being picked, and serves the same role for cherry-picks as `MERGE_HEAD` does for merges.
    - Patrick Steinhardt’s proposed rewording for "ours/theirs" (revised to explicitly tie "ours" and "theirs" to `HEAD` and the other commit).
    - Mention of `git merge-tool --tool-help` to list available merge tools.
    - Use of `linkgit:` macros for cross-referencing other man pages.
    - **New additions under discussion**:
      - **Commit accessibility**: Patrick Steinhardt’s proposal to embed commit details (IDs, messages, dates) directly into conflict markers. Julia Evans has enthusiastically endorsed this idea, highlighting the practical benefits of commit messages and dates, and suggesting it may be actively promoted in the guide. The exact implementation (e.g., embedding vs. discoverability via commands like `git show`) remains under discussion. This enhancement may evolve into a follow-up patch after Patrick’s GitLab prototype.
      - **`merge.conflictstyle=diff3`**: Junio’s and Patrick’s strong endorsement for making `diff3` the default conflict style, with Julia’s user feedback and Junio’s **detailed examples** supporting its practical impact. The guide actively promotes `diff3` as a best practice.
      - **Default resolution command**: D. Ben Knoble’s recommendation to steer users toward `git <thing> --continue` (e.g., `git merge --continue`) as the default choice during conflict resolution. The guide now includes a note that `git commit` is an older alternative to `git merge --continue`, with both commands remaining valid but the latter being the more modern and consistent choice.
      - **`conflict-marker-size` rationale**: Junio’s clarification that the `.gitattributes` setting `conflict-marker-size=32` prevents Git from misinterpreting payload lines that resemble conflict markers (e.g., seven `<` characters) as actual conflict blocks, which is particularly important for tools like `rerere`.
  - **Pending additions/corrections**:
    - Foundational explanation of how Git performs a 3-way merge, including the role of the common ancestor (base), as suggested by Patrick Steinhardt. Julia Evans has declined to include this in the initial version but may revisit it later as an optional deep dive.
    - Whether `git pull --no-commit` conflicts, `MERGE_HEAD`/`REBASE_HEAD` behavior, or `REBASE_HEAD` workflows warrant explicit mention (Knoble notes `REBASE_HEAD` is used in practice).
    - **Conflict marker labels and `git status` wording**: Junio’s exploratory questions about updating conflict markers to include more descriptive labels and rewording `git status` output to avoid phrases like "deleted by us." Julia’s response endorses the idea of "documentation-driven development" and brainstorms potential improvements, but these remain open for follow-up patches.

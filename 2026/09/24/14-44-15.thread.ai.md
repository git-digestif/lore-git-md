Thread identity: Documentation patch series introducing `gitmergeconflicts(7)`, a new man page consolidating merge conflict resolution guidance. Series version: v3 (final refinements incorporated, ready for merging). Originating author: Julia Evans (via GitGitGadget). Thread type: patch series.

Core problem or goal: Git’s documentation currently scatters merge-conflict advice across multiple command man pages, leading to duplication, omissions, and user confusion. The series introduces a dedicated `gitmergeconflicts(7)` guide to centralize this information, improve clarity (e.g., "ours" vs. "theirs"), and provide practical examples. V3 incorporates all feedback from Junio’s v2 and v3 reviews, including final refinements: an exhaustive list of commands that can cause conflicts (`git merge`, `git rebase`, `git cherry-pick`, `git pull`, `git am -3`, `git checkout -m`, `git stash pop`, `git revert`), formal tone (replacing contractions like "Here's" with "Here is"), and retention of all prior improvements (e.g., "WHAT IS A MERGE CONFLICT?" section, rewritten "OURS" AND "THEIRS" explanation, promotion of `merge.conflictstyle=diff3`). Junio’s latest review provided a squashable patch to revise the `diff3` example in `gitmergeconflicts.adoc`, replacing "code" with "lines" to broaden applicability beyond programming and updating the illustration to show that both sides removed a fruit (rather than adding one), demonstrating how the common ancestor reveals the *intent* behind conflicting changes. This adjustment clarifies the pedagogical value of `diff3` by explicitly contrasting the default merge conflict format with `diff3`, showing how the latter prevents mismerges by exposing the original state.

No on-disk or runtime behavior changes. The new guide is purely additive.
- Structure of the new guide: Organized as a practical, example-driven document with sections covering:
  - "WHAT IS A MERGE CONFLICT?" – Foundational explanation of merge conflicts, when they occur, and Git’s behavior during conflicts (e.g., staging successfully merged files, leaving conflicted files unstaged with markers). Defines "original" (common ancestor) and uses "configuration variable."
  - Exhaustive list of commands that can cause conflicts: `git merge`, `git rebase`, `git cherry-pick`, `git pull`, `git am -3`, `git checkout -m`, `git stash pop`, `git revert`.
  - Resolution paths (fix or abort), with formal phrasing: "You can either resolve the conflict or abort the operation."
  - Merge conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`, `|||||||` in `diff3`) and the four-step resolution process (identify, edit, stage, continue).
  - Tools for handling conflicts, grouped to distinguish static views (`git diff`, `git log --merge -p <filename>`) from dynamic ones (`git diff AUTO_MERGE`, graphical merge tools). Includes `merge.conflictstyle=diff3` (actively promoted) and `zdiff3` (explicitly deprecated with a note). The `git log --merge -p <filename>` section omits `--left-right` as Julia argued it would complicate the guide without clear benefit.
  - "OURS" AND "THEIRS" – Explicitly ties "ours" and "theirs" to `HEAD` and the other commit, clarifies their relationship to conflict markers, and explains the "upside down" behavior during rebases.
  - `git diff AUTO_MERGE` – Defined upfront before first use, clarifying it represents the state Git would have produced if no conflicts occurred.
  - Side-by-side examples of `diff3` vs. `zdiff3` output, demonstrating how the common ancestor reveals the *intent* behind conflicting changes. The `diff3` example now uses "lines" instead of "code" and illustrates a scenario where both sides removed a fruit, emphasizing how the common ancestor prevents mismerges.
  - Sample `git status` output to guide users on `--abort`/`--continue` commands.
  - Approved additions/corrections:
    - The `git log --merge -p <filename>` section, with wording: "will print out all commits which caused the merge conflict for `<filename>`, and the diff of how they changed the file."
    - Clarification that `CHERRY_PICK_HEAD` is available any time a cherry-pick stops due to conflict, regardless of whether one or multiple commits are being picked.
    - Patrick Steinhardt’s rewording for "ours/theirs" (revised to explicitly tie "ours" and "theirs" to `HEAD` and the other commit).
    - Mention of `git merge-tool --tool-help` to list available merge tools.
    - Use of `linkgit:` macros for cross-referencing other man pages.
    - Note that `git <thing> --continue` (e.g., `git merge --continue`) is the modern and consistent choice for conflict resolution, with `git commit` as an older alternative.
    - Acknowledgment of semantic conflicts (e.g., Git cannot detect inconsistent function renames).
    - Cohesive phrasing for Git’s refusal to guess resolutions (e.g., "Git will not try to guess how to resolve the conflict").
    - Simplified wording in `git-revert.adoc`: "Reverting a commit may result in a merge conflict."
    - Streamlined phrasing in `git-cherry-pick.adoc`: Removal of the vague introductory sentence about merge conflicts and relocation of the cross-reference to `gitmergeconflicts(7)` to the `SEE ALSO` section.
    - Retention of rebase-specific `--skip` option in `git-rebase.adoc` as a distinguishing feature, with Junio’s requested generalization to cover all multi-step operations.
    - Final update to `git-pull.adoc` (patch 6/6) to replace a generic mention of aborting merge conflicts with a direct cross-reference to `gitmergeconflicts(7)`.

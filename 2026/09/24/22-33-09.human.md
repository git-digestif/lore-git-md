This is the **v6 cover letter** for a **bugfix series** targeting the reference-transaction hook regression. The series is now a **single-patch rewrite** that abandons the v5 approach (which modified `refs_delete_refs()` and its callers) in favor of a **transaction-layer fix** that resolves old OIDs on demand, preserving unconditional deletion semantics while ensuring the hook always receives the correct old value.

The regression, introduced in Git 2.31 by commit `8198907795`, causes the reference-transaction hook to report all-zero OIDs for *both* old and new values when branches, tags, or remote refs are deleted via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`). This breaks external tools (Gerrit, GitLab, CI systems) that rely on the hook to monitor ref changes. The v6 fix restores the pre-regression behavior (resolved old OID followed by all-zeros) for *all* ref-modifying commands, including symbolic refs, without altering the on-disk format or performance characteristics of the original optimization.

The new design addresses Patrick Steinhardt’s architectural concerns by keeping `refs_delete_refs()` as a simple wrapper for unconditional deletions and moving the fix into the transaction hook layer. Here, the hook resolves and caches old OIDs for updates where callers did not supply them, storing them in a separate field that does *not* set `REF_HAVE_OLD` or constrain the update. This ensures the hook always receives the correct old value while preserving the performance gains of the original bulk-deletion optimization (5 seconds vs. 30 minutes for 10,000 tags). The trade-off is on-demand resolution of old OIDs, which could add latency for large batches—though this is not quantified in the cover letter.

The patch touches the refs subsystem (`refs.c`, `refs/refs-internal.h`) and updates `Documentation/githooks.adoc` to clarify that the "preparing" phase reports an unlocked value that may differ from later phases if the ref changes before locking. The test suite (`t/t1416-ref-transaction-hooks.sh`) is expanded to verify hook payloads for unconditional transactions, symbolic refs, and concurrent updates, with coverage for both files and reftable backends. The full test suite passes, including SHA-1 and SHA-256 configurations.

This is a **well-motivated, low-risk fix** for a long-standing regression that has persisted since Git 2.31. The v6 approach is cleaner than v5, avoiding changes to `refs_delete_refs()` and its callers while addressing all prior feedback. The remaining open question is the performance impact of on-demand old-OID resolution, which Patrick Steinhardt may weigh in on. If that trade-off is acceptable, this series looks ready for `next`.

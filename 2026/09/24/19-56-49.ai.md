This is a **bugfix patch revision** addressing a **regression in the reference-transaction hook**, part of a three-patch series (1/3) that has been cooking in `next`. The author, Maciej Ciemborowicz, **concedes Patrick Steinhardt’s architectural objection** and abandons the current approach of extending `refs_delete_refs()` to accept old OIDs. Instead, Maciej proposes a **new design**: the transaction hook layer itself will record a separate "observed old value" for updates where callers did not supply one, using this value only as hook input without setting `REF_HAVE_OLD` or constraining the update. This pivot eliminates the need for the `failed_refs` interface, special null-OID handling, and the redundant failure counter introduced in v5, while preserving the performance gains of the original optimization.

The patch is **high-stakes**: it fixes a regression introduced in Git 2.31 that broke external tools (Gerrit, GitLab, CI systems) by passing all-zero OIDs to the hook on branch/tag deletion. The v5 series restored the pre-regression behavior but was criticized by Patrick for overloading `refs_delete_refs()` with conditional logic better suited to the lower-level transaction API. Maciej’s reply signals a **major rewrite**—the series will now avoid modifying `refs_delete_refs()`, `ref_transaction_delete()`, or their callers, instead pushing the fix into the transaction hook layer. This aligns with Patrick’s preference for keeping `refs_delete_refs()` as a simple wrapper for unconditional deletions.

Key technical details of the new approach:
- **Subsystems touched**: refs, reference-transaction hook, transaction system (no changes to `refs_delete_refs()` or callers).
- **Commands affected**: All ref-modifying commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git push`, `git symbolic-ref`, etc.) will now receive correct old OIDs in the hook, not just the ones fixed in v5.
- **New mechanism**: The transaction hook layer will resolve and cache old OIDs for updates where callers did not supply them, storing them in a separate field that does not influence the transaction’s safety checks.
- **Performance**: The fix preserves the bulk-deletion optimization (5 seconds vs. 30 minutes for 10,000 tags) and avoids the overhead of per-ref resolution in callers.
- **Backward compatibility**: The hook will see the same payloads as in Git 2.28–2.30, restoring the pre-regression behavior.
- **Test coverage**: The existing regression tests (added in v5) will need to be updated to cover the new implementation, but the expected hook payloads remain unchanged.

The pivot addresses Patrick’s concerns about API consistency and layering but introduces a new challenge: the transaction hook layer must now resolve old OIDs on demand, which could add latency for large batches. Maciej does not mention this trade-off in his reply, so it may surface in follow-up discussion. Junio’s earlier request for concrete code comparisons remains unaddressed, but the new direction—avoiding changes to `refs_delete_refs()`—may simplify the decision. The series is no longer "ready for `master`" and will likely require a v6 iteration.

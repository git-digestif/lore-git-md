This thread is about adding revision-based filtering to the `git repo structure` command, allowing users to include or exclude specific commits, refs, or ranges from the repository structure report. The feature aims to help diagnose performance issues in large repositories by focusing on relevant subsets of history. Mark C. Chu-Carroll posted the third iteration of this single-patch series, which integrates Git’s standard `setup_revisions()` machinery for parsing revision specifications.

The current implementation supports flexible filtering (e.g., `git repo structure --branches --not --tags`) and processes objects based on reachability, avoiding the transitive dependency issues of earlier versions. However, key technical concerns remain unresolved. Patrick Steinhardt, the primary reviewer, has raised substantive issues about the restrictiveness of the revision-parsing defaults (`.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`), which may prevent filtering by trees or blobs, and the lack of test coverage for edge cases like `--filter=object:type=blob`. He also critiqued the commit message for omitting motivation and design rationale, a point echoed by Kaartic Sivaraam. While the author expanded the cover letter and test suite in v3, the core implementation and documentation gaps persist.

The patch is uncontroversial in principle but may require a fourth iteration to address Patrick’s feedback. No performance implications have been discussed, though the current workaround for `setup_revisions()`’s limitations—a second ref-walk in `count_references()`—could introduce inefficiency for complex specifications. The feature is self-contained and doesn’t interact with other in-flight efforts like ODB abstraction or Rustification.

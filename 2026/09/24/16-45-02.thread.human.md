This thread is about adding revision-based filtering to `git repo structure`, a diagnostic command for analyzing repository object graphs. The feature, now in its fourth iteration by author Mark C. Chu-Carroll, aims to let users include or exclude specific commits, refs, or ranges from the report, improving targeted analysis in large repositories. The implementation uses Git’s standard `setup_revisions()` machinery, replacing an earlier enum-based approach, but key details—revision-parsing defaults, test coverage, and a double ref-walk inefficiency—remain under active discussion.

The patch is procedurally clean after fixing a v3 corruption but still faces substantive feedback from reviewer Patrick Steinhardt, whose concerns about commit message clarity, documentation precision, and edge-case behavior (like empty repositories) remain partially unaddressed. Mark has engaged with some of Patrick’s suggestions, such as improving documentation terminology and defending the current revision-parsing defaults, but has not fully resolved issues like the dropped "empty repository" test or the lack of motivation in the commit message. Patrick’s latest reply downplays the performance impact of the double ref-walk but insists the empty-repo test must be restored, framing it as a blocker for predictable user experience. The author’s argument that the command is "pointless" in empty repos hasn’t swayed Patrick, who emphasizes the need for consistent behavior even in edge cases.

The series is likely headed for a v5 to address these remaining issues, particularly empty-repo handling and commit message improvements. While the feature’s goal is uncontroversial, the implementation’s trade-offs—like the double ref-walk and revision-parsing defaults—continue to spark debate.

This thread is about adding revision-based filtering to `git repo structure`, a diagnostic command for analyzing repository object graphs. The feature, introduced by Mark C. Chu-Carroll in a single-patch v4 series, aims to let users include or exclude specific commits, refs, or revision ranges from the command’s output—useful for diagnosing performance issues in large repositories. The implementation uses Git’s standard `setup_revisions()` machinery, replacing an earlier enum-based approach, but key details remain under active review.

The patch is procedurally clean after fixing an accidental corruption in v3, but substantive concerns persist. Patrick Steinhardt, the most engaged reviewer, has raised several unresolved issues: the commit message still lacks a clear explanation of *why* this feature is valuable (e.g., real-world diagnostic use cases), the documentation could better align with Git’s terminology and clarify behavior (e.g., what "reachable" means), and the revision-parsing defaults may be overly restrictive, preventing filtering by trees or blobs. Tests also remain incomplete, with edge cases like `--filter=object:type=blob` unaddressed. A notable inefficiency—a double ref-walk in `count_references()`—has been accepted as a trade-off for consistency with Git’s revision-parsing idioms, though its performance impact hasn’t been discussed.

Mark has not yet engaged with Patrick’s technical feedback in v4, focusing instead on fixing the procedural blocker. Junio Hamano’s review was limited to flagging the v3 corruption, while Kaartic Sivaraam supported Patrick’s critique of the commit message but offered no technical feedback. The patch is eligible for further review, but its readiness hinges on addressing Patrick’s concerns, likely requiring a v5. No other in-flight efforts depend on this feature, and it integrates cleanly with Git’s existing revision-parsing infrastructure.

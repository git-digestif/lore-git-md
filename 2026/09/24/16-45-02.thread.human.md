This thread introduces a redesigned feature for `git repo structure`, allowing users to filter the repository structure report by revisions (e.g., commits, branches, or tags) using Git’s standard `setup_revisions()` machinery. Originally proposed in v1 with a clunky `--no-<reftype>` flag system, the feature was criticized for being inflexible and inconsistent with Git’s idioms. Mark C. Chu-Carroll abandoned that approach in v2, adopting Patrick Steinhardt’s suggestion to use revision-based filtering instead. This pivot resolves the core design objection, shifting the focus to implementation details like reachability logic and edge cases.

The v2 patch replaces the enum-based flag system with `struct rev_info` and `setup_revisions()`, enabling commands like `git repo structure --branches --not --tags` or `git repo structure master`. This change aligns the feature with Git’s existing revision-parsing infrastructure and avoids the transitive dependency issues of v1. The patch touches `builtin/repo.c`, updates the documentation, and expands test coverage to 84 lines, validating edge cases like overlapping includes/excludes. While the design is now uncontroversial, the implementation hasn’t yet received feedback, leaving open questions about performance (e.g., large repositories with complex revision specs) and coding style (e.g., lingering curly-brace issues).

Key participants include Mark (the author), who drove the redesign, and Patrick, whose proposal shaped the new approach. No other reviewers have weighed in, so the thread is still in early review. The feature is self-contained and doesn’t depend on other in-flight efforts, but its adoption of Git’s standard revision machinery could make it a more versatile tool for users. The next steps will likely involve scrutiny of the reachability logic and performance implications.

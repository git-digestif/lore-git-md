This is the **v6 cover letter** for a **single-patch bugfix** targeting the reference-transaction hook regression. The series abandons the v5 approach (which modified `refs_delete_refs()` and its callers) and instead **moves the fix into the transaction hook layer itself**, addressing Patrick Steinhardt’s architectural concerns while preserving unconditional deletion semantics and performance gains.

The patch resolves the regression by recording a separate "observed old value" for updates where callers did not supply one, using this value only as hook input without setting `REF_HAVE_OLD` or constraining the update. This ensures the hook always receives the correct old OID for *all* ref-modifying commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git push`, `git symbolic-ref`, etc.), restoring the pre-2.31 behavior. The design avoids changes to `refs_delete_refs()` or its callers, sidestepping the API semantics debate that stalled v5.

Key technical details:
- **Subsystems touched**: refs, reference-transaction hook (no changes to `refs_delete_refs()` or callers).
- **New mechanism**: The transaction layer resolves and caches old OIDs for updates where callers did not supply them, storing them in a separate field that does not influence transaction safety checks. This ensures the hook receives the correct old OID without affecting transaction semantics.
- **Commands affected**: All ref-modifying commands now report correct old OIDs in the hook, matching the pre-regression behavior. `git update-ref -d` remains unaffected (already correct).
- **Backends**: Works for both files and reftable.
- **Performance**: Preserves the bulk-deletion optimization (5s vs. 30m for 10k tags) but introduces on-demand resolution of old OIDs in the hook layer, which may add latency for large batches. This trade-off is acknowledged but unquantified.
- **Tests**: Updates the existing regression tests to cover the new implementation, verifying hook payloads for all ref-modifying commands (files/reftable, SHA-1/SHA-256), symbolic refs, and concurrent updates.

The patch is **well-motivated and narrowly scoped**, addressing a long-standing regression that broke external tools (Gerrit, GitLab, CI systems). The commit message documents the design rationale, including why the fix belongs in the transaction layer rather than at the caller level. Junio’s earlier requests for clarity and concrete code comparisons are partially addressed, though the performance trade-off remains unquantified. The series is rebased onto `master` (3bc0341127) and passes the full test suite with `DEVELOPER=1`.

This is a **strong candidate for merging**, resolving a persistent regression with minimal risk. The architectural pivot to the transaction layer aligns with Patrick’s feedback and avoids the API complexity of v5. The only open question is whether the on-demand resolution of old OIDs introduces unacceptable latency for large batches, which may prompt further discussion.

This is a design discussion reply in the thread about improving `git fetch` behavior for shallow repositories. Junio C Hamano acknowledges that introducing a `fetch.<remote>.refmap` configuration would achieve the desired "matching-inspired" fetch mode without breaking backward compatibility. Specifically, it would allow `git fetch second main` to automatically create a remote-tracking branch (`refs/remotes/second/main`) while preserving the existing "single-shot fetch" semantics for users who rely on them.

The email reinforces the consensus that `remote.X.refmap` (or `fetch.X.refmap`) is the correct design direction, as it cleanly separates namespace mapping from branch selection logic. Junio’s realization that this configuration would enable the desired behavior—without requiring a transition plan or escape hatch—resolves a key ambiguity from earlier in the thread. This reply effectively closes the design discussion about *how* to implement the feature, leaving only implementation details (e.g., configuration syntax, edge cases) for the upcoming v3 patch series.

For the future v3 series, this means:
- The `fetch.X.refmap` configuration will define namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`).
- The matching-inspired fetch mode will dynamically fetch branches tracked by local branches *and* the remote’s default branch, while preserving the "single-shot fetch" behavior for explicit branch arguments.
- No additional escape hatches or transition plans are needed, simplifying the implementation.

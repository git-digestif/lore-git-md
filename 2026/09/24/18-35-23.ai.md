This is a meta-discussion reply in the Git version numbering thread, focusing on user-facing configuration defaults rather than technical readiness for 3.0.

Harald Nordgren joins the thread to endorse Patrick Steinhardt’s lighthearted take on version numbering flexibility (e.g., 2.100 as a valid successor to 2.99). More substantively, he proposes a list of **breaking changes to default configuration values** that he hopes could land before 3.0, arguing that otherwise he might have to wait "another 10 years for 4.0" to introduce them. The proposed defaults are all user-facing and aimed at improving usability: enabling autostash for `checkout` and `rebase`, changing branch/tag sorting to be more intuitive, switching to the `histogram` diff algorithm and enabling color-moved detection, and making `git status` compare against both `@{upstream}` and `@{push}` when they differ.

Harald frames these as potential 3.0-worthy changes but acknowledges the proposal is currently informal ("seemed a bit presumptuous to submit these as a patch"). His email effectively **opens a new sub-thread** within the broader version numbering discussion: whether 3.0 should be used as an opportunity to introduce user-facing breaking changes beyond the technical ones already under consideration (SHA-256, lowercase object IDs, etc.). The tone is pragmatic and user-focused, but the proposal itself is likely to be **controversial** — changing defaults is always disruptive, and some of these (e.g., autostash) have historically been contentious in the community. No code or patches are attached; this is purely a design-level suggestion.

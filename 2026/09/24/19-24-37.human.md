This is a meta-discussion reply in the ongoing Git version numbering thread, specifically Junio C Hamano’s response to Harald Nordgren’s proposal to include user-facing breaking changes in Git 3.0.

Junio clarifies the purpose of the version numbering discussion: the jump from 2.56 to 2.98 (or similar) is not just a mechanical choice but a deliberate signal to downstream projects and distributions that a major transition is coming. The goal is to give them time to prepare, not to debate what will actually land in 3.0. He then directly rejects Harald’s proposal to include new default-configuration changes in 3.0, stating that it is "way too late" for any feature not already presented as draft code or design on the mailing list. Junio also notes that some of Harald’s suggested changes (e.g., enabling autostash, changing branch/tag sorting) may not even qualify as true breaking changes and could potentially land after 3.0 without waiting for 4.0.

The tone is firm but not dismissive; Junio is drawing a clear boundary around what 3.0 will and will not include. This reply effectively closes the sub-thread on user-facing defaults for 3.0 while leaving the door open for some of those changes to be revisited later. The broader version numbering discussion remains open, with the unresolved questions still centered on technical readiness (SHA-256 support, lowercase object IDs) and the best version number to signal the upcoming transition.

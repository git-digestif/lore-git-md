This is the first patch in a **bugfix series** that has now been merged to `next`. The patch refactors `refs_delete_refs()` to allow callers to supply old OIDs for batch deletions, enabling the reference-transaction hook to receive the resolved old OID (instead of all-zeros) when branches or tags are deleted. This addresses a regression introduced in Git 2.31 that broke external tools like Gerrit and GitLab.

Karthik Nayak’s review here is **substantive**, focusing on two key technical concerns. First, he questions the removal of the `BUG()` check for all-zero OIDs in `ref_transaction_delete()`, arguing that it weakens safety by masking potential user errors (e.g., uninitialized `struct object_id`). His critique highlights a tension between the patch’s goal (restoring hook functionality) and Git’s historical emphasis on catching misuse of null OIDs. Second, he notes minor implementation details, such as the redundancy of tracking failures separately from `failed_refs->nr` and the optional nature of the `failed_refs` parameter, which could be clarified in the commit message.

The patch itself is well-structured, updating the refs API to support granular error reporting via `REF_TRANSACTION_ALLOW_FAILURE` and an optional `failed_refs` list. All call sites are updated to use the new signature, fixing the build-breakage issue from v4. While Karthik’s feedback raises valid points about safety and clarity, the series has already addressed prior concerns (including Junio’s design feedback) and is now cooking in `next`. The changes are narrowly scoped to the refs subsystem and lay the groundwork for the next two patches, which restore the pre-regression hook behavior for `git branch`, `git tag`, and remote pruning. The regression’s impact on external tools makes this a high-priority fix.

This is a **bugfix patch** in D. Ben Knoble’s four-part series to fix a race condition in `git stash`’s autostash logic when `stash.index=true` is set. The patch replaces the existing subprocess-based index merge (`git diff-tree` + `git apply`) with an **in-core merge using `merge-ort.c`**, eliminating a race condition that could corrupt the `MERGE_AUTOSTASH` ref and cause SIGSEGV on conflicted merges.

Junio C Hamano’s reply **raises a technical concern about the order of tree arguments** in the `merge_incore_nonrecursive()` call. The current implementation passes `head` (current HEAD), `merge` (stashed index), and `merge_base` (stash base) in an order that does not match the function’s documented semantics. Junio suggests the trees should be reordered to `(merge_base, merge, head)` to correctly cherry-pick the change from the stash base (`b_tree`) to the stashed index (`i_tree`) into the current HEAD (`c_tree`). He notes that `merge_ort_nonrecursive()` (a related function) uses a different argument order, which may have contributed to the confusion.

The patch also includes a **new test case** in `t/t3903-stash.sh` to verify that `git stash apply --index` preserves unrelated upstream index changes. Junio confirms this test fails with the current implementation, reinforcing the need to correct the tree order.

**Why this matters**: The bug is subtle but real—it only surfaces during autostash operations with staged index entries. The fix is low-risk (in-core merges are well-tested in `merge-ort.c`) and high-reward (eliminates a race condition and simplifies the code). However, Junio’s feedback highlights a **potential correctness issue** in the core logic, which must be addressed before integration. The test case provides a clear way to verify the fix.

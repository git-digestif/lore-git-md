This is a maintainer reply in the Git 3.0 planning thread, outlining Junio C Hamano’s provisional release timeline and technical strategy for the transition from Git 2.x to 3.0. The email responds directly to Johannes Schindelin’s request for a concrete plan, providing a working schedule and implementation details while leaving room for community feedback.

Junio proposes a three-phase timeline: Git 2.98 in December 2026, Git 2.99 in March 2027, and Git 3.0 in April 2027. The month-long gap between 2.99 and 3.0 is intended as an "advertisement" period for downstream projects to prepare for breaking changes, rather than a full development cycle. Git 2.99.1 (April 2027) would serve as a bugfix-only release, with Git 3.0 containing identical code but enabling the breaking changes disabled in 2.99.1. This approach minimizes divergence between the two releases, reducing maintenance burden.

Technically, Junio suggests retaining the `WITH_BREAKING_CHANGES` Makefile knob in Git 3.0 to keep the 2.99.1/3.0 diff minimal, deferring cleanup of the disabled code to later 3.x releases. This strategy reflects the summit consensus on using 2.99 as a transitional signal while adding Junio’s preference for a short, focused lead time. The proposal also accommodates LTS distributions by allowing volunteers to maintain 2.99.x indefinitely.

The email advances the thread by providing a concrete baseline for discussion, though Junio emphasizes this is his interpretation of the summit consensus rather than a final decision. Key open questions remain, such as the scope of breaking changes (e.g., Rust support, SHA-256 interoperability) and whether the timeline aligns with downstream needs. The tone is pragmatic, balancing the project’s need for flexibility with downstream coordination. This plan is likely to be refined in the next "What’s cooking" report based on mailing list feedback.

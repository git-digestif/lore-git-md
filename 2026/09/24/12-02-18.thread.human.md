This thread is about an RFC patch series (v3) by Kaartic Sivaraam that improves Git’s error messages when it cannot find a valid repository. Instead of explaining why a directory is invalid, the series now reports *which* directory Git inspected and *where* it came from—such as `--git-dir`, `GIT_DIR`, repository discovery, or `GIT_OBJECT_DIRECTORY`. This shift addresses Junio C Hamano’s critique that users are primarily confused about the inspected path and its source, not the failure reason.

The series is now complete with all five patches posted. The first two are preparatory: a minor stylistic refactoring in `setup.c` and expanded test coverage in `t/t0009-git-dir-validation.sh`. The remaining three patches add diagnostic context to error messages for explicitly specified directories, repository discovery with `GIT_CEILING_DIRECTORIES`, and inaccessible `GIT_OBJECT_DIRECTORY`. No technical flaws have been raised, and the new direction aligns with Junio’s feedback. The series explicitly defers handling of `gitfile` (submodules/worktrees), `GIT_ALTERNATE_OBJECT_DIRECTORIES`, and edge cases like irrelevant `GIT_CEILING_DIRECTORIES` entries.

Junio has reviewed the fourth patch, which enhances error messages for repository discovery with `GIT_CEILING_DIRECTORIES`. He suggests simplifying the output from two lines to one (e.g., `fatal: no valid repository ".git" found in "/home/user/.config/nvim" or any of its parent directories up to "/home/user/.config"`), noting a potential trade-off with script compatibility. This is a refinement request, not a critique of the patch’s design or correctness. Kaartic may adopt the suggestion, iterate on the phrasing, or defend the current format. The series remains under review, with no substantive objections raised so far.

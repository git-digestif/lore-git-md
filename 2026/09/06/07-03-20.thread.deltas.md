# Thread deltas

## 2026/09/06

- [2026/09/06/18-14-40 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson listed remaining considerations for the post-2.56 version decision: forge support for SHA-256 on remaining major forges (with an update to provide at Git Merge), updates on libgit2's SHA-256 and reftable support, and a re-roll of the lowercase-only object IDs series (a breaking change that may need to soak for a release or two) that he planned to send out today or tomorrow. He argued that software not already far along on SHA-256 (and reftable for local repositories) is likely not worth considering, noting JGit and Gitoxide were informed at least a year ago that SHA-256 was coming in Git 3.0, and that he was not aware of serious efforts to add Rust support for new platforms, so neither should be a blocker. His gut reaction was that option (3) (Git 2.98 or 2.97) might be the best choice, with 2.97 being nice, or alternatively being more careful with 2.95 and then skipping ahead to 3.0 when ready.

## 2026/09/07

- [2026/09/07/08-23-46 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt countered the premise that Git 2.99 leaves no room before 3.0, noting there is also room after 2.99 and "no reason we cannot have Git 2.100."
- [2026/09/07/08-23-46 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt said GitHub's missing SHA-256 support is the biggest question mark for him and that he would not want to "pull the trigger" on a 3.0 bump before GitHub supports it.
- [2026/09/07/08-23-46 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt reported that reftable support has been upstreamed into libgit2 (PR 7117) and SHA-256 support was default-enabled (PR 7261, merged roughly a month ago), so once the next libgit2 release is out he thinks both blockers should be removed.
- [2026/09/07/09-30-31 by Emily Shaffer <nasamuffin@google.com>] Emily Shaffer said missing GitHub SHA-256 support is what leaves her most concerned about landing 3.0, since most users host on GitHub and it would be confusing for people creating new repos and pushing; however, if GitHub gives no solid timeline commitment, waiting is less appealing given the 2026 work was driven by the looming fall 3.0.
- [2026/09/07/09-30-31 by Emily Shaffer <nasamuffin@google.com>] Emily Shaffer noted GitOxide received some initial SHA-256 support this year with more expected over the coming months, and that Google wants it because jj also needs SHA-256 support, though jj itself still has work to do and is not ready.
- [2026/09/07/09-30-31 by Emily Shaffer <nasamuffin@google.com>] Emily Shaffer said Google's distribution would disable SHA-256 for new repos via system config until GitHub (and probably JGit) support exists, which makes her lean toward "why not release 3.0," while noting not everyone can distribute system config to a wide user base.

## 2026/09/27

- [2026/09/27/13-48-31 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood proposed adopting a consequentialist approach to changing defaults for largely cosmetic UI-related settings such as `diff.algorithm`, `diff.colorWords`, `commit.verbose`, and `merge.conflictStyle`, allowing changes when the expected net benefit outweighs the potential downside.
- [2026/09/27/13-48-31 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood proposed a `core.defaults` setting to provide evolving “modern defaults,” potentially with workflow-specific values such as `push.default=current` and `status.compareBranches=@{upstream} @{push}` for triangular workflows, enabled by default with a single opt-out.
- [2026/09/27/19-32-10 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano responded that Git already takes such a consequentialist approach—citing repeated changes to the default merge strategy—but argued that net benefit and downside remain speculative until a change has been released and distributed for months. He also questioned the need to poll `core.defaults`, suggesting it would be easier to measure how many users already set a target configuration such as `diff.algorithm`.

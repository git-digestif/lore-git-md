This thread is a design discussion about what the next major Git release should be numbered—2.57, 2.99, 2.98, or 3.0—after 2.56, scheduled for late September 2026. Junio C Hamano opened the discussion, outlining the options and calling for input on whether to use 3.0 to signal foundational changes like SHA-256 support and lowercase-only object IDs, or to continue with incremental numbering. The conversation has since expanded to include readiness criteria for 3.0, ecosystem compatibility (particularly GitHub’s SHA-256 support), and whether 3.0 should include user-facing breaking changes to defaults.

No decision has been reached, but Junio has firmly rejected Harald Nordgren’s proposal to include user-facing breaking changes in 3.0, such as enabling autostash or changing the default diff algorithm, citing the cutoff for new contributions and questioning whether some suggestions even qualify as breaking changes. The transitional version (e.g., 2.98) is now framed as an advance warning mechanism for downstream projects, not a placeholder for last-minute features. Key unresolved issues include the status of the lowercase-only object IDs series, GitHub’s SHA-256 support, and whether the project is ready for 3.0 or needs more time. Emily Shaffer has emphasized GitHub’s dominance in the ecosystem, while Patrick Steinhardt noted that libgit2’s SHA-256 and reftable support are now resolved, weakening some of brian m. carlson’s earlier concerns about readiness.

Kristoffer Haugsbakk’s recent reply adds a pragmatic twist to Harald’s proposal, suggesting that instead of changing defaults—which would require broad consensus and risk disruption—a tool could analyze a user’s Git configuration and recommend modern settings. This approach shifts the focus from breaking changes to user education and gradual adoption, offering a less contentious path forward. While the thread remains open, the core tension is between signaling a major milestone (3.0) and ensuring the project and its ecosystem are truly ready for it. The discussion is unlikely to conclude until more clarity emerges on the unresolved technical work and GitHub’s SHA-256 timeline.

The Git mailing list is discussing what the next major release after 2.56 (due late September 2026) should be called—3.0, a transitional version like 2.99, or a simple increment to 2.57. Junio C Hamano opened the thread by outlining four options and calling for input, but no decision has been reached. The conversation has since expanded to include whether 3.0 should also introduce user-facing breaking changes to defaults, such as enabling autostash for `checkout`/`rebase`, changing branch/tag sorting, or switching the default diff algorithm to `histogram`.

Key voices have weighed in with differing priorities. Brian M. Carlson advocated for a cautious delay (e.g., 2.97 or 2.95) to allow time for foundational work like the lowercase-only object IDs series to stabilize, though Patrick Steinhardt later noted that two of Carlson’s technical blockers—libgit2’s SHA-256 and reftable support—are now resolved. Emily Shaffer emphasized GitHub’s SHA-256 support as the most critical unresolved gap, given its market dominance, while acknowledging the project isn’t obligated to wait indefinitely. Randall S. Becker provided an update on Rust platform support, revealing progress (including for NonStop) that could reduce long-term friction for the Rustification effort, though details remain under NDA.

Harald Nordgren then proposed using 3.0 as an opportunity to modernize user-facing defaults, arguing this might be the only chance for another decade. Junio’s latest reply firmly rejects this idea for the upcoming release, clarifying that the transitional version (e.g., 2.98) is meant to signal an impending major release, not to cram in last-minute changes. He also noted that some of Harald’s suggestions might not even qualify as breaking changes and could be revisited after 3.0. The thread remains open, with unresolved questions about the readiness of GitHub’s SHA-256 support, the status of the lowercase-only object IDs series, and whether the project should proceed with 3.0 or opt for a more cautious transitional version.

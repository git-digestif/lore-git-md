This thread is a design discussion about what the next major Git release after 2.56 should be called—3.0, a transitional version like 2.99, or something else—and whether it should include user-facing breaking changes. Junio C Hamano, the maintainer, kicked off the conversation by outlining four options and calling for input, but no decision has been reached yet.

The core debate revolves around readiness: some contributors, like brian m. carlson, argue for a cautious delay (e.g., 2.97 or 2.95) to allow time for foundational work like the lowercase-only object IDs series to stabilize, while others, like Emily Shaffer, emphasize the need to address GitHub’s SHA-256 support before a 3.0 release. Junio has firmly ruled out including user-facing breaking changes (e.g., enabling autostash, changing the diff algorithm) in 3.0, citing the cutoff for new contributions. Instead, Kristoffer Haugsbakk proposed an alternative: a tool that analyzes a user’s Git configuration and recommends modern settings without disrupting existing workflows. This idea has gained support, including a playful endorsement from D. Ben Knoble, who suggested the name `git config upgrade` for such a tool.

The thread has also touched on ecosystem compatibility, with Shaffer noting that downstream tools like Jujutsu and GitOxide have varying levels of SHA-256 support, and that large organizations may mitigate issues via configuration. Randall S. Becker’s update on Rust platform support adds a long-term dimension, though it’s not a blocker for 3.0. The discussion remains open-ended, with key questions still unresolved: whether the project is ready for 3.0, what version number best signals its intent, and how to handle user-facing changes in the future. For now, the focus is on stability, advance warning for downstream projects, and incremental improvements over disruptive changes.

The Git version numbering discussion after 2.56 continues, with Emily Shaffer adding a pragmatic perspective on the project’s readiness for a 3.0 release. The thread, initiated by Junio C Hamano, remains unresolved, weighing whether to bump to 3.0, use a transitional version like 2.99, or continue with incremental numbering (e.g., 2.57).

Shaffer, now focused on Jujutsu but formerly a prolific Git contributor, highlights GitHub’s lack of SHA-256 support as the most significant gap for a 3.0 release. While she acknowledges the Git project isn’t beholden to GitHub, she notes that most users rely on it, and pushing SHA-256 repositories without GitHub support could cause confusion. However, she’s skeptical about waiting indefinitely for GitHub if there’s no clear timeline, suggesting the pressure of an impending 3.0 release might accelerate progress. She also points out that ecosystem readiness extends beyond Git itself—GitOxide now supports SHA-256, but Jujutsu still needs work, and Google’s internal Git distribution would likely disable SHA-256 for new repositories until GitHub and JGit support is available.

The discussion still hinges on unresolved questions: whether the lowercase-only object IDs series will be ready in time, the status of SHA-256 support on major forges, and whether the project should proceed with 3.0 or opt for a transitional version. Junio has yet to signal a preference, while Brian M. Carlson remains cautious, advocating for a delay to allow foundational work to stabilize. Patrick Steinhardt’s earlier update weakened two of Carlson’s technical blockers (libgit2’s SHA-256 and reftable support), but the broader ecosystem concerns raised by Shaffer add weight to the argument for patience. For now, the thread remains in the discussion phase, with no clear consensus in sight.

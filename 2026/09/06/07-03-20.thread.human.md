This thread is a design discussion initiated by Junio C Hamano about how to number the next major Git release after 2.56, scheduled for late September 2026. The central question is whether to jump to 3.0, use a transitional version like 2.99, or continue with incremental numbering (e.g., 2.57). So far, no decision has been made, but the discussion has clarified some key technical hurdles.

Brian M. Carlson initially argued for a cautious delay (e.g., 2.97 or 2.95), citing three readiness factors: SHA-256 support on major forges, libgit2’s compatibility with SHA-256 and reftable, and the lowercase-only object IDs series. Patrick Steinhardt’s recent reply weakens two of these concerns. He confirmed that libgit2 now supports reftable (merged in PR #7117) and has enabled SHA-256 by default (PR #7261), removing those as blockers once libgit2’s next release ships. However, the status of SHA-256 support on GitHub (and other forges) remains unresolved, as does the timeline for the lowercase-only object IDs series, which Carlson suggested needs soak time.

The thread is still in the discussion phase, with Junio yet to weigh in on a preferred path. The remaining open questions revolve around whether the project is ready for 3.0 or needs more time to stabilize foundational work, and what version number best signals the project’s intent. External factors like ecosystem compatibility (e.g., coordination with libgit2 or JGit) and the unresolved GitHub SHA-256 update are also in play. For now, the conversation is narrowing, but the maintainer’s decision will likely hinge on the outcome of these technical and ecosystem considerations.

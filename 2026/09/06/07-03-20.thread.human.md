The Git version numbering thread continues to explore how to handle the next major release after 2.56, with Junio C Hamano now responding to Phillip Wood’s proposal for a `core.defaults` meta-config variable and a consequentialist approach to changing defaults. Junio initially framed the options and ruled out user-facing breaking changes for 3.0, but the conversation has since expanded to include how Git might responsibly evolve defaults in the future. Phillip Wood’s proposal introduced two ideas: a consequentialist approach to default changes (weighing costs and benefits for low-impact settings) and a `core.defaults` variable that would let users opt into "modern defaults" without disruptive breaking changes. Junio’s latest email engages with both ideas but raises concerns about their feasibility.

Junio acknowledges that the project already uses a consequentialist mindset for some changes—like updating the default merge strategy—but notes that measuring "net benefit" and "potential downside" is speculative until a change is released and observed in practice. His skepticism isn’t a rejection of the approach but a reminder that pre-release analysis has limits. For `core.defaults`, he questions whether it would actually help measure the impact of default changes, suggesting that polling the variable’s value would be redundant since the same data could be gathered by tracking the target configurations directly. His critique implies that `core.defaults` might add complexity without providing meaningful new insights, though he doesn’t dismiss the idea outright.

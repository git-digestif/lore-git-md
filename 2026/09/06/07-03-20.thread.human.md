This thread is a meta-discussion about what the next major Git release after 2.56 should be called—3.0, a transitional version like 2.99, or something else—and what, if anything, should change in that release. Junio C Hamano kicked off the discussion by laying out four options and calling for input, but no decision has been reached yet. The conversation has since expanded to include two key sub-topics: whether Git is ready for a 3.0 release (with SHA-256 support on GitHub and the lowercase-only object IDs series still unresolved), and whether 3.0 should include user-facing breaking changes to defaults.

Junio has firmly ruled out the latter, citing the cutoff for new contributions and arguing that some proposed changes (like autostash or `git status` tweaks) don’t even qualify as breaking changes. Others, like brian m. carlson, have advocated for a cautious delay to let foundational work stabilize, while Emily Shaffer has emphasized GitHub’s SHA-256 support as a critical gap. Harald Nordgren proposed using 3.0 as an opportunity to modernize defaults, but his idea was rejected. Kristoffer Haugsbakk and D. Ben Knoble then suggested an alternative: a tool to analyze and recommend modern Git configurations without forcing disruptive changes.

Phillip Wood’s recent email shifts the focus from *whether* to change defaults to *how* Git might do so responsibly in the future. He proposes two ideas: first, adopting a consequentialist approach for low-impact settings (e.g., `diff.algorithm`), where the net benefit of a change could justify minor disruptions; and second, introducing a `core.defaults` config variable that would let users opt into "modern defaults" without affecting everyone. This would allow the project to evolve defaults gradually, avoiding the kind of last-minute disruptions Junio rejected. While still conceptual, Phillip’s ideas offer a pragmatic middle ground between stability and progress, and they’re likely to shape future discussions about how Git handles default changes. The thread remains open, with the version number decision still unresolved and the broader question of how to modernize defaults now taking center stage.

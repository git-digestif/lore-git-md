This thread is about Patrick Steinhardt’s patch series improving the `git maintenance` heuristic for `rerere gc`. The goal is to replace the hard-coded 60-day cutoff with a dynamic heuristic that estimates stale `rerere` entries and triggers garbage collection only when the count meets or exceeds a configurable threshold (default: 512). This reduces unnecessary invocations, lowers overhead, and mitigates a race condition between `git maintenance` and `git rebase` caused by lock contention on `MERGE_RR.lock`. The series does not address concurrent `rerere gc` collisions, which are handled separately.

The series is now ready for integration. Junio C Hamano endorsed its readiness, and it has received tested reviews from Thomas Bachem and "LGTM" from Derrick Stolee. Version 2 addressed all feedback, including clarifying the cover letter’s motivation and renaming functions for better readability. The heuristic samples the `rr-cache` directory with a "17" prefix and scales each stale entry by 256, running only if the estimate meets the threshold. Tests confirm the behavior works as intended, and the series is explicitly decoupled from a complementary effort (pull.2214.v3) that tackles the locking mechanism. Patrick’s latest email acknowledges Junio’s feedback on cover letter self-containment but introduces no new changes.

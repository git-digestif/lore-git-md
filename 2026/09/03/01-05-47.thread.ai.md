Subject: [PATCH] push: fix uninitialized variable in `--force-if-includes` reflog walk
Series version: standalone patch (v4 posted)
Originating author: Aleksei Sviridkin
Thread type: bugfix

Core problem or goal
The `--force-if-includes` safety mechanism in `git push` contains an uninitialized variable bug in the files backend that causes the reflog walk to terminate prematurely when the remote-tracking ref has no reflog (e.g., in fresh clones). This leads to false positives in the "remote ref updated since checkout" check, potentially allowing unsafe force-pushes. The patch initializes `timestamp_t date` to `0` in `remote.c` to ensure the reflog traversal covers the entire local branch history when no remote-tracking reflog exists. The discussion has converged on the design rationale for the fallback value: Aleksei and Tyler Cipriani argue that `0` (epoch start) is the only safe choice because reflog entries older than `gc.reflogExpire` (or a fixed 90-day cutoff) can persist until explicitly expired, and a non-ancestor tip could slip through if the cutoff is too recent. Junio’s alternative (90 days or `gc.reflogExpire`) is acknowledged but shown to risk unsafe pushes in edge cases, particularly when `gc` is disabled or reflog expiration is non-default. Aleksei’s latest reply provides timing data demonstrating that the performance penalty for `0` is negligible (15ms for 2,000 entries with commit-graph, 10s worst-case without) and that the current implementation already works for most users due to low uninitialized `date` values. The choice is now framed as a deliberate trade-off between safety and performance, with Aleksei leaving the final decision to Junio, but the data and scenarios make a strong case for `0` as the only safe fallback value.

Current status
v4 is the latest version and addresses all prior feedback: the commit message is now accurate (no longer implies a truncated walk skips the merge-base check, and clarifies the issue is the *absence* of a reflog record), the test is more precise (`setup_src_dup_dst` and expires only the remote-tracking reflog), and the fallback value (`0`) is justified as the only safe choice. The patch is technically complete and ready for integration, but the fallback value discussion remains the sole obstacle. Junio’s latest reply reasserts his preference for a 90-day or `gc.reflogExpire` fallback as more aligned with Git’s reflog retention design, arguing that it avoids penalizing users who follow default reflog expiration policies while still covering the vast majority of cases. His tone signals skepticism about the necessity of scanning *all* reflog entries, but he has not explicitly rejected the current implementation or requested a follow-up patch—merely restating his position. Tyler’s review endorses the patch as technically sound, provides performance data showing the safety-performance trade-off is acceptable, and suggests the fallback value discussion is now a policy question for Junio. No new code or tests are proposed, and the thread is effectively waiting on Junio’s final decision.

- Subsystem: push safety mechanism (`--force-if-includes`)
- New symbols: none
- Behavior change: fixes uninitialized stack variable to ensure correct reflog traversal when remote-tracking ref has no reflog; fallback value `0` forces a full reflog scan for safety, justified by Aleksei’s and Tyler’s scenarios showing that older reflog entries can persist and must be checked to prevent unsafe pushes. - Backend scope: files backend only; reftable backend unaffected due to differing reflog handling

Open questions and loose ends
- **Fallback value trade-off**: The tension between safety (full scan) and performance (avoiding redundant work) remains unresolved. Junio’s latest reply reasserts his preference for a 90-day or `gc.reflogExpire` fallback as more aligned with Git’s reflog retention design, arguing that it avoids penalizing users who follow default reflog expiration policies while still covering the vast majority of cases. Aleksei’s and Tyler’s latest replies frame the choice as a deliberate trade-off: the cutoff is faster only when it produces the wrong result (rejecting valid pushes when the matching reflog entry is older than the cutoff), while `0` ensures safety at a negligible performance cost. Tyler’s performance data (15ms for 2,000 entries) and step-by-step scenario further strengthen the case for `0` as the only safe fallback. The outcome will determine whether the patch graduates to `next` as-is or prompts a follow-up adjustment. Aleksei has left the final decision to Junio, noting that if the trade-off is acceptable, the fallback value can be changed with a one-line edit—but the commit message would then need to explicitly warn that the mechanism can still reject correct pushes when matching entries are older than the cutoff.

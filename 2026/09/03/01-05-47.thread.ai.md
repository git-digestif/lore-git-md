Subject: [PATCH] push: fix uninitialized variable in `--force-if-includes` reflog walk
Series version: standalone patch (v3 posted)
Originating author: Aleksei Sviridkin
Thread type: bugfix

Core problem or goal
The `--force-if-includes` safety mechanism in `git push` contains an uninitialized variable bug in the files backend that causes the reflog walk to terminate prematurely when the remote-tracking ref has no reflog (e.g., in fresh clones). This leads to false positives in the "remote ref updated since checkout" check, potentially allowing unsafe force-pushes. The patch initializes `timestamp_t date` to `0` in `remote.c` to ensure the reflog traversal covers the entire local branch history when no remote-tracking reflog exists. The discussion has focused on the design rationale for the fallback value: Aleksei argues that `0` (epoch start) is the only safe choice because reflog entries older than `gc.reflogExpire` (or a fixed 90-day cutoff) can persist until explicitly expired, and a non-ancestor tip could slip through if the cutoff is too recent. Junio’s alternative (90 days or `gc.reflogExpire`) is acknowledged but shown to risk unsafe pushes in edge cases, particularly when `gc` is disabled or reflog expiration is non-default. Aleksei’s latest reply provided performance measurements demonstrating that the cost of `0` is negligible in typical repositories (where reflogs are expired or recent) and only incurred in edge cases where older reflog entries persist, directly addressing Junio’s concern about penalizing users who follow default reflog expiration policies. Junio’s latest reply now argues that using Git’s default `gc` expiration timeout (or 90 days) is more logical than `0`, as it avoids penalizing users who follow default reflog expiration policies while still covering the vast majority of cases, and contends that the performance data confirms this approach would not waste more time than `0`.

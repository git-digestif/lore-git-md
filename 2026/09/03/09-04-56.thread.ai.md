Thread identity: Patch series improving `git maintenance` heuristic for `rerere gc`; v2; originating author Patrick Steinhardt; thread type patch series.

Core problem or goal: Replace the hard-coded 60-day cutoff in `git maintenance`'s `rerere gc` task with a dynamic heuristic that estimates stale `rerere` entries and triggers the task only when the estimated count meets or exceeds a configurable threshold (default: 512). The goal is to reduce unnecessary invocations, lower overhead, and mitigate a long-standing race condition (lock contention between `git maintenance` and `git rebase` due to `MERGE_RR.lock` and `LOCK_DIE_ON_ERROR`) caused by frequent `rerere gc` runs. The series explicitly does not address lock contention between multiple concurrent `rerere gc` invocations—only the race between `git maintenance` and `git rebase`. The heuristic reduces the *frequency* of `rerere gc` runs but does not alter the locking mechanism itself. The series is now explicitly decoupled from a complementary effort (pull.2214.v3) that addresses the locking mechanism by introducing a timeout in `setup_rerere()`.

Key technical details:
- Files touched: `rerere.c`, `rerere.h`, `builtin/gc.c`, maintenance configuration documentation.
- New/renamed functions: `rerere_entry_is_stale()` (extracted from existing logic), `rerere_gc_needed()` (renamed from `rerere_gc_estimate()`), `rerere_gc_cutoffs()` (new helper to compute expiration timestamps), `rerere_id_is_stale()` (new helper to encapsulate staleness logic), `rerere_gc_condition()` (updated to use dynamic heuristic).
- Behavioral change: `rerere gc` task now uses a dynamic heuristic (sampling the `rr-cache` directory with a "17" prefix heuristic, scaling each sampled stale entry by 256) to estimate stale entries. The task runs only if the estimate meets or exceeds `maintenance.rerere-gc.auto` (default: 512). Negative values force the task; zero disables it.
- **Locking behavior**: Unchanged. `rerere gc` still uses `MERGE_RR.lock` with `LOCK_DIE_ON_ERROR`, meaning concurrent invocations will abort.
- Test coverage: `t/t7900-maintenance.sh` updated to cover new behavior, including edge cases (threshold crossing, disabled/forced runs, and synthetic/real-world `rerere` entry scenarios). Tests verify threshold behavior but not concurrent execution.
- On-disk format: No changes.
- Configuration: `maintenance.rerere-gc.auto` redefined to specify the minimum estimated stale entries required to trigger the task.

Open questions and loose ends: The series does not address concurrent `rerere gc` collisions, which remain possible due to `LOCK_DIE_ON_ERROR`. This limitation is explicitly documented in the thread. A separate effort (pull.2214.v3) tackles the lock contention problem directly by modifying `setup_rerere()` to wait for `rerere.lockTimeout` before proceeding without rerere, and making `rerere gc` abort immediately if the lock is held. The two efforts are complementary and now explicitly decoupled; no further coordination is required.

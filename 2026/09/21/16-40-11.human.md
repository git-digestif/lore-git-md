This is a reply to the bug report about `git log -L` incorrectly including commits that only modify blank lines after Python functions. Johannes Sixt (Hannes) responds with a clarification that challenges the premise of the bug: he argues that Git’s current behavior is not a bug but an inherent limitation of how the line-log feature determines function boundaries.

Hannes explains that Git does not truly understand what constitutes a function in any programming language. Instead, it relies on the same regex patterns used for diff hunk headers to guess function boundaries. By this logic, blank lines (and even comments) between functions are treated as part of the preceding function, since a function’s range extends up to the start of the next function. This behavior is not specific to Python or to functions at the end of a file—it applies universally across all languages supported by Git’s diff drivers.

The reply reframes the issue as a design trade-off rather than a bug. Hannes suggests that if the line-log feature were to be improved, a more pressing problem would be ensuring that comments *above* a function are treated as part of that function, rather than being incorrectly attributed to the previous one. This implies that any fix would require a more sophisticated approach to parsing function boundaries, likely involving language-specific logic or external tooling.

For readers following the thread, this response shifts the discussion from a straightforward bugfix to a broader question about how Git should handle function boundary detection. The current behavior is consistent with Git’s existing design, but it may not align with user expectations, especially for languages like Python where trailing whitespace is often semantically insignificant. The thread is now likely to pivot toward whether and how to improve this aspect of the line-log feature.

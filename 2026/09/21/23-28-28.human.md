This is Junio C Hamano following up on his review of Maciej Ciemborowicz’s patch that fixes the `reference-transaction` hook omission for branch rename and copy operations. The patch aims to ensure the hook receives both the deletion of the old branch name and the creation of the new one in a single transaction, addressing a long-standing bug in both the files-based and reftable backends.

Junio’s new comments focus on the design of the `ref_transaction` struct, which the patch extends with rename/copy-specific fields (`old_refname`, `new_refname`, `type`, etc.). He questions whether these details belong in the generic transaction structure or should instead be confined to backend-specific data, as is already done for the files backend’s `files_copy_or_rename_transaction_data`. His concern is that the current approach “contaminates” the core struct with operation-specific details that may not scale well—particularly if future use cases require multiple renames or copies in a single transaction.

The review also surfaces a potential limitation in the patch’s design: the new fields imply that a transaction can only represent a single rename or copy, raising questions about how to handle more complex scenarios (e.g., renaming multiple branches at once or combining rename and copy operations). Junio does not outright reject the approach but clearly signals that the current implementation may need rethinking to avoid painting the project into a corner.

This is a substantive architectural critique, not a surface-level nit. The discussion now hinges on whether the patch’s hook visibility goals can be achieved without bloating the core transaction struct or restricting future flexibility. The author’s next revision will likely need to address these concerns, either by refactoring the data model or by providing a compelling rationale for why the current design is the least bad option. For now, the patch remains under review, with its long-term viability dependent on resolving this feedback.

Subject: `git log -L` incorrectly includes commits that only remove blank lines after Python functions
Series version: N/A (bug report, not a patch series)
Originating author: Nikita Makarov <n.makarov@yadro.com>
Thread type: bug report / design discussion

Core problem or goal
The line-log feature (`git log -L`) is intended to show commits that modify a specified function or line range, but its regex-based function boundary detection (shared with diff hunk headers) treats *any* content—including blank lines or comments—between one function’s end and the next function’s start as part of the first function. This causes commits that add or remove trailing blank lines after a Python function (especially at EOF) to be incorrectly included in the output, violating user expectations. The issue is not Python-specific; it affects all languages using Git’s function detection (e.g., C, shell).

Current status
Reported as a bug and confirmed by Kristofer Karlsson, who plans to submit a patch. Johannes Sixt (Hannes) subsequently clarified that the behavior is not a bug but a deliberate design trade-off: Git’s line-log parser relies on the same heuristic patterns as diff hunk headers, which cannot semantically distinguish code from adjacent whitespace or comments. Tim Tassonis later echoed this view, citing the `git log` man page to argue that the behavior is an inherent limitation of regex-based detection. The issue is reproducible with corrected steps (add/remove trailing blank line after a function at EOF) and affects Git 2.43.0+. No maintainer has commented on the trade-off or potential fixes.

Key technical details
- **Subsystem affected**: line-log (`-L` option) and regex-based function boundary detection (defined in `userdiff.c` for each language).
- **Files touched**: The issue is internal to the line-log implementation (`line-log.c`) and the language-specific regex patterns in `userdiff.c`.
- **Behavior**: The line-log parser uses diff hunk patterns to define function ranges, which cannot distinguish between code, whitespace, or comments. This causes commits modifying trailing blank lines (or comments) after a function to be incorrectly included in the output.
- **Edge cases**:
  - Trailing blank lines after a function at EOF (reported issue).
  - Comments above a function misattributed to the prior function (Hannes’ observation).
  - The bug manifests only when the function is at EOF and a blank line is added *after* the initial commit, but the underlying logic affects all languages and file positions.
- **Test coverage**: No existing test covers these edge cases; the corrected reproduction scenario could be adapted into a regression test.
- **Root cause**: The line-log parser’s reliance on diff hunk patterns, which are inherently heuristic and language-agnostic.

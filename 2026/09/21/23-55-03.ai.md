This is a **substantive review** from Junio C Hamano on the first patch of Maciej Ciemborowicz’s three-patch bugfix series (v2 1/3). The series targets a regression in the `reference-transaction` hook where deletions of branches or tags via high-level commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`) report all-zero OIDs instead of the resolved old OID, breaking external tools like Gerrit and GitLab.

Junio’s review identifies a **critical design flaw** in the patch: the use of a single transaction for all deletions, which turns the operation into an all-or-nothing affair. This contradicts the documented behavior of `refs_delete_refs()`, which promises "best-effort" deletion (i.e., failures for individual refs should not block the rest). The issue is particularly acute for commands like `git fetch --prune` or `git remote prune`, where users expect unconditional deletion of stale refs even if some refs are concurrently updated. The current patch would cause the entire transaction to abort if a single ref fails its old-OID check, which is likely to surprise users and break existing workflows.

Junio suggests two potential fixes:
1. **Split deletions into separate transactions** to preserve independent failure handling, or
2. **Use a "best-effort" transaction mode** (if such a mode exists in the ref transaction API) to allow partial failures while still using a single transaction.

The review also notes a minor **code organization nit**: the input validation for the `old_oids` array size should occur *after* the early return for empty `refnames`, since an empty list makes the validation irrelevant.

This feedback is **high-weight** and directly addresses the core design conflict that Karthik Nayak previously flagged in the v2 series. The thread’s earlier resolution—using `REF_TRANSACTION_ALLOW_FAILURE` to preserve unconditional deletion while still passing old OIDs to the hook—appears to align with Junio’s suggestion of a "best-effort" mode. The v3 series will need to incorporate this approach to resolve the all-or-nothing problem. The patch is otherwise well-motivated and technically sound, but this issue must be fixed before the series can proceed.

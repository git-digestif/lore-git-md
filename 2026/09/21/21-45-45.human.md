This is a follow-up in the `fetch.shallow` feature discussion. Harald Nordgren clarifies the real-world scenario that prompted the patch: he cloned a fork of `homebrew-core` with `--depth=1`, then added the upstream repository as a remote. When he tried to pull, the operation hung because the shallow repository had many remote-tracking branches (from the wildcard fetch refspec added by `git remote add`), causing `git fetch` to negotiate history for all of them.

The key takeaway is that the performance issue is **not specific to sparse checkouts**—it affects any shallow repository with many remote-tracking branches, regardless of sparseness. Harald’s use case involved a standard shallow clone (not sparse) with a wildcard fetch refspec, which is the default behavior of `git remote add`. This narrows the scope of Phillip Wood’s earlier question: the problem is general to shallow repositories, not tied to sparse checkouts.

The thread now has a clearer picture of the root cause. The discussion may shift toward evaluating whether improving `git remote add` behavior (as Phillip suggested) or keeping the `fetch.shallow` config (as Harald implemented) is the better solution. No code changes have been proposed yet, but the clarification strengthens the case for addressing the issue at the fetch level rather than the remote-add level.

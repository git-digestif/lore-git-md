This thread is about a bug in `git log -L`, which tracks the history of specific lines or functions in a file. The issue was reported by Nikita Makarov: when a Python function at the end of a file is followed by a blank line, `git log -L` incorrectly includes commits that only add or remove that blank line, even though the function itself hasn’t changed. Kristofer Karlsson confirmed the bug and plans to submit a patch.

Johannes Sixt (Hannes) recently clarified that this isn’t a bug in the traditional sense but a limitation of Git’s design. The line-log feature uses the same regex-based patterns as diff hunk headers to detect function boundaries, which means it treats *any* content—including blank lines or comments—between one function’s end and the next function’s start as part of the first function. This heuristic is language-agnostic and affects all languages, not just Python. Hannes also pointed out a related issue: comments above a function are incorrectly attributed to the *previous* function, which could be even more misleading. The current behavior is a deliberate trade-off, as Git doesn’t parse code semantically, but it may not match user expectations.

The thread is still open, with no patch yet proposed. The discussion has shifted toward whether the current heuristic is acceptable or if a targeted improvement (like ignoring trailing blank lines) is feasible. No maintainer has commented on the priority or timeline for a fix.

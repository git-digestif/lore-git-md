This thread is about a bug in `git log -L`, which tracks changes to specific functions or line ranges. The issue is that the feature incorrectly includes commits that only add or remove blank lines after Python functions (especially at the end of a file), because Git’s regex-based function detection treats any content—including whitespace—between one function’s end and the next function’s start as part of the first function. Nikita Makarov reported the problem, and Kristofer Karlsson confirmed it with corrected reproduction steps, noting that the bug affects Git 2.43.0+ and planning to submit a patch.

Johannes Sixt (Hannes) later clarified that this isn’t a bug but a deliberate design trade-off: Git’s line-log parser uses the same heuristic patterns as diff hunk headers, which can’t distinguish code from adjacent whitespace or comments. He also pointed out a related, more disruptive issue where comments *above* a function are misattributed to the *previous* function. Tim Tassonis recently weighed in with a philosophical pushback, arguing that the behavior is an inherent limitation of Git’s regex-based approach and that semantic parsing would be too costly. His reply aligns with Hannes’ framing but doesn’t engage with the technical details or potential fixes.

The thread remains unresolved. The core question is whether a targeted fix (e.g., ignoring trailing blank lines) is feasible without semantic parsing, or if the current heuristic’s limitations must be accepted. No maintainer has commented yet, and Kristofer’s patch—when it arrives—will likely determine whether the project prioritizes strict correctness or practical usability. For now, the issue stands as a known edge case in Git’s function boundary detection.

This thread is about whether Git should formally document its governance structure—roles, responsibilities, succession planning, and leadership renewal processes—to improve clarity and reduce the project’s bus factor. Antonin Delpeuch kicked off the discussion, proposing to draft a `GOVERNANCE.md` file and seeking input on whether the project sees value in such documentation and whether leadership would support its creation.

Junio C Hamano, the project’s maintainer, has responded with cautious openness. He acknowledges that Git’s governance has historically been informal, with influence earned through sustained contribution rather than formal roles. While he doesn’t oppose a *descriptive* document outlining how things currently work, he warns against making it *prescriptive*, fearing it could lead to unproductive debate. He points to `CODE_OF_CONDUCT.md` (which references the Git PLC at SFC) as the closest thing to an official structure and suggests that any documentation should avoid imposing new rules. The discussion remains exploratory, with no decisions made or next steps proposed yet. No other participants have weighed in so far.

This is a **substantive review comment** on patch 3/6 of Derrick Stolee’s RFC series introducing a "safe" `strbuf` API. Junio C Hamano identifies a **user-facing bug** in the error message emitted by `safe_memory_limit_check()`: when `git_alloc_limit` is zero, the function falls back to `SIZE_MAX` as the limit but still reports the original (zero) value in the error message, creating a confusing mismatch.

The issue is straightforward: the error message uses `git_alloc_limit` directly, but the actual limit being enforced is the local variable `limit` (which is `SIZE_MAX` when `git_alloc_limit` is zero). This inconsistency could mislead users into thinking the limit is zero when it is effectively unlimited. Junio’s suggestion to report `limit` instead of `git_alloc_limit` is a **clear improvement** that aligns the message with the logic.

This is a **minor but important fix** for usability. The patch is otherwise well-motivated and technically sound, and this change does not affect the core safety property or the refactoring’s correctness. The fix is likely to be uncontroversial and should be incorporated into the next revision of the series. No broader architectural concerns are raised here; the feedback is narrowly focused on the error message’s accuracy.

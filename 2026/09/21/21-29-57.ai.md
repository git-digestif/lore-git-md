This is a **substantive review** from Junio C Hamano on patch 4/6 of Derrick Stolee’s RFC series introducing a "safe" `strbuf` API. The review identifies a **memory leak bug** in the newly introduced `srealloc()` function, which is a critical component of the safe API.

The bug occurs in the error path of `srealloc()`: when `realloc()` fails, the function overwrites `*ptr` with `NULL` before checking for failure, thereby losing the original pointer. This clobbers the caller’s pointer and leaks the memory it pointed to. The fix is straightforward: store the result of `realloc()` in a temporary variable, check for failure, and only then update `*ptr`. Junio’s feedback is precise and actionable, focusing on correctness rather than style or naming.

The patch is part of the broader effort to eliminate `die()` calls in critical code paths (e.g., trace2), and `srealloc()` is a foundational piece of the safe API. This bug undermines the safety guarantee of the new API, as it could lead to memory leaks in low-memory conditions where the safe API is intended to be robust. The review does not address the broader architectural questions raised in earlier feedback (e.g., whether the "safe" API should be a subset or a wholesale hardening of `strbuf`), but it is a critical blocker for the current implementation.

The fix will likely be uncontroversial, but the bug highlights the importance of thorough error-path testing in the safe API. No other issues are raised in this reply.

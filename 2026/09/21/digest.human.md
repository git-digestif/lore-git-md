# Git mailing list daily digest for 2026/09/21

## The day in brief
The Git mailing list saw active discussion on several fronts today. A critical design flaw was identified in a `reference-transaction` hook bugfix, requiring a major rework to preserve backward compatibility. The "safe" `strbuf` API RFC received substantive feedback, including bug reports and architectural suggestions. Meanwhile, a long-standing Windows ANSI emulation bug appears ready for integration after four iterations, and a `git log -L` edge case sparked debate about Git’s regex-based function detection limitations.

## Notable threads

### `reference-transaction` hook: preserving backward compatibility
The v2 series fixing a regression where branch/tag deletions reported all-zero OIDs instead of the resolved old OID hit a major snag. Junio C Hamano identified a **critical design flaw**: the patch used a single transaction for all deletions, turning the operation into an all-or-nothing affair that contradicts `refs_delete_refs()`’s documented "best-effort" behavior. This would break `git fetch --prune` and `git remote prune`, where users expect unconditional deletion even if some refs are concurrently updated. Karthik Nayak’s earlier review had raised a similar concern about the user experience regression, and the author has now accepted the need for `REF_TRANSACTION_ALLOW_FAILURE` to preserve unconditional deletion while still passing old OIDs to the hook. The v3 series will require significant rework to handle partial failures gracefully, including UI consistency fixes (e.g., suppressing "[pruned]" on failure) and code cleanup.

### Introducing a "safe" `strbuf` API
Junio C Hamano provided **substantive feedback** on Derrick Stolee’s RFC series introducing a `strbuf` API subset that cannot call `die()`. While endorsing the direction of making core service routines "safe" as part of libification, Junio questioned the architectural framing. He argued the goal should be to harden the *entire* `strbuf` API rather than carve out a niche "safe" subset, and suggested renaming higher-level utilities (e.g., `strbuf_realpath()`) to avoid the `strbuf_` prefix. The review also identified **two bugs**: a memory leak in `srealloc()` (where `realloc()` failure clobbers the caller’s pointer) and a misleading error message in `safe_memory_limit_check()` (reporting the original `git_alloc_limit` value instead of the effective limit). Junio’s feedback on the final patch refined the error-handling design, proposing that `jw_release()`’s return type be a plain `int` (0 for success, non-zero for failure) rather than `enum safe_result`, as the aggregation only needs to report whether *any* error occurred. Phillip Wood’s earlier review had raised additional concerns, including a bug in `sstrbuf_grow()` (using `st_add3()`, which calls `die()` on overflow) and the usability of checking errors on every call.

### Windows ANSI emulation bugfix nears integration
Yongqiang Tian’s four-iteration bugfix for `compat/winansi.c:die_lasterr()` appears ready for `next`. The patch removes the problematic variadic helper and replaces its four call sites with direct `die()` calls that report the raw `GetLastError()` value and handle (formatted as `%li`). Junio’s review of v2 requested only minor commit message improvements, and the v3 patch incorporated `Helped-by:` trailers and relocated build validation details. The only remaining discussion is cosmetic (error message phrasing: "Windows error" vs. "Failed to duplicate handle: %li, Windows error: %lu"), which Junio does not consider a blocker. The fix addresses a long-standing bug (introduced in 2012) where Windows API failure messages displayed a `va_list` address instead of the intended integer handle.

### `git log -L` and the limits of regex-based function detection
A bug report about `git log -L` incorrectly including commits that modify trailing blank lines after Python functions sparked a **design discussion** about Git’s regex-based function boundary detection. Johannes Sixt clarified that the behavior is not a bug but a deliberate trade-off: Git’s line-log parser relies on the same heuristic patterns as diff hunk headers, which cannot distinguish between code, whitespace, or comments. This affects all languages using Git’s function detection (e.g., C, shell) and manifests in edge cases like trailing blank lines at EOF or comments above functions misattributed to the prior function. Kristofer Karlsson plans to submit a patch, but the thread has shifted to whether the current heuristic’s limitations should be accepted or if a targeted improvement (e.g., ignoring trailing blank lines) is feasible. Tim Tassonis dismissed the possibility of a fix, citing the "heavy and needless cost" of semantic parsing.

### Line-log: trimming trailing whitespace from function ranges
Kristofer Karlsson posted a patch to align `git log -L`’s function boundary detection with `git grep -W` by trimming trailing empty lines. Junio’s review identified a **behavioral discrepancy**: the patch only trims lines starting with `\n`, while `git grep -W` trims all whitespace-only lines (spaces, tabs). The discussion has expanded to question whether the two commands should behave consistently at all, given that neither’s documentation explicitly promises blank-line trimming. The patch will need to address whitespace-only lines and CRLF edge cases (e.g., `\r\n`) to fully achieve its goal, and the broader design question remains unresolved.

## In brief
- **`git pull` segfault fix**: Jiri Kuncar posted v2 of a patch preventing a segmentation fault when `lookup_commit_reference()` returns NULL due to corrupted merge heads. The patch adds NULL guards and includes a test simulating corruption via garbage-written object files.
- **Rust Windows CI follow-up**: Johannes Schindelin and Junio C Hamano confirmed that GitLab’s Windows runners do not have Rust preinstalled, closing the last loose end from the merged Rust Windows CI series. The fix is being addressed in a separate thread.
- **OpenBSD `RUNTIME_PREFIX` support**: Brad Smith clarified that `getexecpath()` is a new, more accurate API for resolving executable paths on OpenBSD, replacing a "pile of hacks." Junio requested the commit message incorporate this rationale and clarify the OpenBSD 8.0+ version gating.
- **Governance documentation**: Antonin Delpeuch proposed formally documenting Git’s governance structure to improve onboarding and reduce conflicts. Junio responded with cautious openness to a *descriptive* document but warned against prescriptive rules that could spark debate.
- **`git stash` autostash fix**: Phillip Wood identified correctness risks in a patch replacing subprocess-based index merging with in-core logic, including a merge algorithm mismatch and the removal of assertions guarding against NULL pointers. The author is expected to address these in a follow-up.

This is a **substantive review comment** from Junio C Hamano on the third patch in Derrick Stolee’s RFC series introducing a "safe" `strbuf` API. The series aims to eliminate `die()` calls from critical code paths like trace2 by providing a subset of the `strbuf` API that returns errors instead of crashing.

The patch in question refactors the memory limit checking logic in `wrapper.c` to create `safe_memory_limit_check()`, a version that never calls `die()`. The new function assumes `SIZE_MAX` as the limit if `git_alloc_limit` is unset (or zero), avoiding the need to parse the `GIT_ALLOC_LIMIT` environment variable (which can itself call `die()`). Junio’s feedback points out a **clarity issue in the error message**: when `git_alloc_limit` is zero, the message reports the allocation size as exceeding `git_alloc_limit` (zero), which is technically correct but confusing for users. He suggests reporting the *effective* limit (`SIZE_MAX`) instead, which would make the message more intuitive.

This is a **minor but worthwhile improvement** to the patch. The change is straightforward (replace `git_alloc_limit` with `limit` in the error message) and aligns with the patch’s goal of making the safe API more user-friendly. The fix does not affect the patch’s core functionality or safety guarantees, but it removes a potential source of confusion for users debugging allocation failures. The feedback is **constructive and specific**, focusing on a single line of code rather than the broader architectural questions raised in Junio’s earlier review of the series. No further discussion is needed unless someone objects to the proposed wording.

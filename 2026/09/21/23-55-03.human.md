This is Junio C Hamano’s **substantive review** of the first patch in Maciej Ciemborowicz’s three-patch bugfix series, which restores the `reference-transaction` hook’s ability to receive the old OID when branches or tags are deleted. The review identifies a **critical design flaw** in the patch’s approach: by packing all deletions into a single transaction, the patch inadvertently changes the semantics of `refs_delete_refs()` from "best-effort, independent deletions" to "all-or-nothing." This breaks the expected behavior of commands like `git fetch --prune`, which should continue deleting refs even if some deletions fail due to concurrent updates.

Junio’s feedback centers on the **transaction semantics** and their alignment with the function’s documented contract. The current implementation forces all deletions to succeed or fail together, which contradicts the function’s promise to "attempt to keep going" even when some deletions fail. He suggests two potential fixes: either split deletions into separate transactions (retaining independent semantics) or use a "best-effort" transaction mode if one exists. This critique directly addresses the unresolved design conflict noted in the thread summary, where Karthik Nayak had previously proposed `REF_TRANSACTION_ALLOW_FAILURE` as a middle ground—Junio’s feedback reinforces the need for such a mechanism.

The review also includes **surface-level nitpicks** (e.g., the placement of the `old_oids->nr` validation check and the clarity of the commit message), but these are secondary to the core issue. The patch’s current design risks regressing user expectations for commands that rely on `refs_delete_refs()`’s independent deletion behavior, making this a **blocker** for the series’ acceptance. The author will need to revise the patch to address the transaction semantics before the series can proceed.

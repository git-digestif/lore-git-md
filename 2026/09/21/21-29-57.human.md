This is a **substantive review** from Junio C Hamano on the fourth patch of Derrick Stolee’s RFC series introducing a "safe" `strbuf` API. The patch implements `sstrbuf_grow()`, the first safe method in the new API, and introduces `srealloc()` as a safe alternative to `xrealloc()`.

Junio identifies a **memory leak** in `srealloc()`: when `realloc()` fails, the function overwrites `*ptr` with `NULL` before checking for failure, clobbering the original pointer. This means the caller loses access to the original memory block, which is never freed. The bug is straightforward but critical, as it violates the safety guarantee the API is supposed to provide.

The fix is simple: store the result of `realloc()` in a temporary variable, check for failure, and only then update `*ptr`. This preserves the original pointer if `realloc()` fails, avoiding the leak. The oversight is surprising given the series’ focus on safety, but it does not undermine the overall design—just this specific implementation.

This review is **technical and narrowly scoped**, focusing on correctness rather than the broader architectural questions raised in earlier feedback (e.g., whether the "safe" API should exist at all). The bug is easy to fix, and Junio’s observation is unlikely to be controversial. However, it highlights that even carefully designed safety-critical code can harbor subtle issues, reinforcing the need for thorough review.

The patch remains part of an RFC series, so this feedback is expected and constructive. The fix will likely appear in a future iteration, and the discussion about the safe API’s long-term role (e.g., hardening the entire `strbuf` API vs. maintaining a parallel subset) will continue separately. For now, this is a clear, actionable critique of a single function.

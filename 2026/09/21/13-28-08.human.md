This is a substantive review of a feature patch introducing `fetch.shallow`, a new configuration option to improve performance for shallow repositories. Phillip Wood raises a thoughtful question about the patch's motivation and scope, suggesting the problem might be better addressed by improving how `git remote add` behaves in sparse repositories rather than adding a new config knob.

Phillip's key point is that the commit message and documentation imply the issue arises from having many remote branches in the local repository, but the actual slowdown comes from negotiating history for all remote branches during a refspec-less fetch. He questions whether the real culprit is `git remote add` defaulting to a wildcard fetch refspec in sparse repositories, which then causes `git fetch` to pull down all branches. If that's the case, he argues, the fix should target the remote-add behavior rather than introducing a new config option that users must opt into.

The review is substantive: it engages with the patch's design rationale, questions the root cause of the problem, and suggests an alternative approach that might eliminate the need for the new feature entirely. This isn't a nitpick about code style or wording—it's a fundamental challenge to the patch's premise. The discussion is now open on whether the patch addresses the right layer of the problem, and whether a more targeted fix (modifying `git remote add` in sparse repos) would be cleaner and more automatic for users.

Thread identity
Subject: [PATCH 0/2] sequencer: defer auto maintenance until rebase completion
Series version: v2 (3 patches)
Originating author: Thomas Bachem (via GitGitGadget)
Thread type: patch series

Core problem or goal
Adjust when auto maintenance runs during sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`) so that it defers until sequence completion, matching the apply backend’s behavior. This prevents maintenance from interfering with intermediate steps and ensures consistent behavior across all three commands.

Current status
Under review; v2 posted. The series is technically complete: all three patches are on-list, the reusable `git_config_append_parameter()` helper is in place, the config string is cached in `replay_ctx`, and the scope covers rebase, cherry-pick, and revert. All prior feedback from Phillip Wood and Patrick Steinhardt has been addressed. Junio C Hamano reviewed the third patch and suggested a mechanical change to store the cached `GIT_CONFIG_PARAMETERS` string as a `const char *` instead of a `struct strbuf` for clarity and to emphasize immutability; the author has confirmed this change will be included. Patrick Steinhardt’s latest reviews raised minor points about commit message clarity, parameter naming (`env` -> `buf`), the undocumented format of `GIT_CONFIG_PARAMETERS`, and substantive concerns about the commit message’s clarity regarding behavior changes and the scattering of `run_auto_maintenance()` calls across multiple exit paths. Phillip Wood’s latest review focuses on commit message rewording to avoid implying active interference (it’s lock contention, not opposition) and to clarify confusing phrasing about "rerere gc" and loose objects, and suggests improving test coverage by asserting that auto maintenance does *not* run during intermediate steps (e.g., before `git rebase --continue`) and using `test_grep` instead of `grep` for better failure output. In the newest exchange, Patrick Steinhardt concedes the naming debate over the `env` parameter in `git_config_append_parameter()`, accepting that `env` is appropriate given the function’s specific purpose of building `GIT_CONFIG_PARAMETERS` strings. No open technical objections remain; the only watch items are a hypothetical edge case about very long sequences where mid-sequence repacking might improve performance, which Phillip Wood wants to monitor in real-world usage rather than block on, and the ongoing minor documentation and code organization suggestions.

Key technical details
- Files touched: `sequencer.c`, `config.c`, `config.h`, test files `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh`
- New behavior: auto maintenance runs exactly once at sequence completion (after autostash is applied) instead of during intermediate commits/merges
- CLI/config impact: disables auto maintenance for individual commands (`git commit`, `git merge`, exec commands) during any sequencer-driven operation by passing `maintenance.auto=false` and `gc.auto=0` via `GIT_CONFIG_PARAMETERS`; invokes `git maintenance run --auto` at sequence completion. Patrick Steinhardt now questions whether the redundant `gc.auto=0` setting is needed for correctness or can be safely removed for clarity.
- Subsystems: sequencer, auto maintenance, config
- New symbols: `git_config_append_parameter()` (helper in `config.c` for building `GIT_CONFIG_PARAMETERS` strings with proper shell quoting), `disable_auto_maintenance()` (helper in `sequencer.c` that builds and caches the config string in `replay_ctx`)
- Test coverage: added to `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh` using `GIT_TRACE2_EVENT` to verify `git maintenance run --auto` is executed exactly once at sequence end and not during intermediate steps; covers single-pick, multi-pick, conflict-resolution, and exec scenarios. Phillip Wood suggests consolidating test coverage by extending existing tests from the previous patch rather than duplicating them, and recommends asserting the absence of maintenance during intermediate steps and using `test_grep` for better failure output.
- Unaffected: the apply backend’s existing behavior
- Error handling: maintenance errors are ignored to avoid masking user-facing issues
- Code structure: `git_config_append_parameter()` helper in `config.c` builds the config string; `disable_auto_maintenance()` in `sequencer.c` caches the string in `replay_ctx`; maintenance invocation added to `sequencer_finish()`, `continue_single_pick()`, `single_pick()`, and `sequencer_continue()`. The cached string will be stored as a `const char *` instead of a `struct strbuf` to clarify immutability. Patrick Steinhardt suggests consolidating maintenance calls into a single exit path (like the apply backend’s `finish_rebase()`) for clarity, though this is a stylistic preference rather than a requirement. Neither the new helper nor the existing `git_config_from_parameters()` documents the actual format used for the config string, a gap Patrick Steinhardt notes should be addressed for clarity.

Open questions and loose ends
- **Edge cases**: Hypothetical concern about very large sequences where mid-sequence repacking might improve performance; no concrete issue identified, but Phillip Wood wants to monitor real-world usage for complaints. This is noted as a watch item rather than a blocker.
- **Documentation gap**: The format of `GIT_CONFIG_PARAMETERS` is not documented in either `git_config_append_parameter()` or `git_config_from_parameters()`, as noted by Patrick Steinhardt. This should be addressed for clarity but is not a blocker.
- **Code organization**: Patrick Steinhardt suggests consolidating `run_auto_maintenance()` calls into a single exit path (like the apply backend’s `finish_rebase()`) to avoid scattering them across multiple functions (`sequencer_finish()`, `continue_single_pick()`, `single_pick()`). This is a stylistic preference rather than a functional requirement.
- **Maintenance subsystem behavior**: Patrick Steinhardt questions whether disabling both `maintenance.auto` and `gc.auto` is necessary in the `disable_auto_maintenance()` helper, or if disabling only `maintenance.auto` would suffice. This is a technical point about whether `git maintenance` (which may internally invoke `git gc`) respects the `maintenance.auto` setting exclusively, making the redundant `gc.auto=0` setting unnecessary.
- **Test organization**: Phillip Wood suggests consolidating test coverage by extending existing tests from the previous patch rather than duplicating them in separate files (`t3418-rebase-continue.sh` and `t3510-cherry-pick-sequence.sh`), and recommends asserting the absence of maintenance during intermediate steps and using `test_grep` for better failure output. This is a test hygiene suggestion, not a blocker.
- **Commit message clarity**: Phillip Wood recommends rewording to avoid implying active interference (it’s lock contention, not opposition) and to clarify confusing phrasing about "rerere gc" and loose objects. For example, "The merge backend which is also used by 'git cherry-pick' and 'git revert' does not run it when it finishes" is proposed as clearer than the current phrasing.
- **Parameter naming**: Resolved in favor of `env`; Patrick Steinhardt concedes the naming debate, accepting that `env` is appropriate for the `git_config_append_parameter()` helper given its specific purpose of building `GIT_CONFIG_PARAMETERS` strings.

Subject: [PATCH 0/2] sequencer: defer auto maintenance until rebase completion
Series version: v4 (3 patches, final)
Originating author: Thomas Bachem (via GitGitGadget)
Thread type: patch series

Core problem or goal
Adjust when auto maintenance runs during sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`) so that it defers until sequence completion, matching the apply backend’s behavior. This prevents maintenance from interfering with intermediate steps and ensures consistent behavior across all three commands.

Current status
The series is in `seen` after Junio C Hamano signaled intent to queue it ("Will queue"). However, Patrick Steinhardt’s latest **substantive review** challenges the design choice of delegating maintenance to the built-in commands (`builtin/rebase.c` and `builtin/revert.c`), arguing that the sequencer *does* have a single exit point (`pick_commits()`) where maintenance could be triggered consistently. The series is no longer technically complete: the reusable `git_config_append_parameter()` helper and config string caching remain in place, but the exit-path design is now contested. All prior feedback from Phillip Wood, Junio C Hamano, and earlier Patrick Steinhardt reviews has been addressed, but this new objection requires resolution before merging. The redundant `gc.auto=0` setting remains removed, and the config string is still `maintenance.auto=false` only.

Open questions and loose ends
- **Design controversy**: Patrick Steinhardt’s review identifies a technical oversight in the patch’s justification—the commit message claims there is no single exit point for the sequencer, but Patrick demonstrates that nearly all code paths (including `--continue`, `--skip`, and multi-commit sequences) flow through `pick_commits()`. The only exception is sequencer abort, which could be handled separately. This raises the question of whether maintenance should be triggered in `pick_commits()` and on abort (Patrick’s proposal) or remain delegated to built-in commands (current design). The outcome will determine whether the patch requires a v5 rewrite.
- **Edge cases**: The hypothetical concern about very long sequences where mid-sequence repacking might improve performance remains unresolved, but no concrete issue has been identified. This is still noted as a watch item.
- **Test coverage gap**: Phillip Wood’s earlier observation about the rebase test (`t/t3418-rebase-continue.sh`) not verifying suppression during conflict resolution persists. The test scenario does not trigger a conflict, so it does not exercise the intended code path. This gap is independent of the design controversy but may need addressing in a follow-up.

Key technical details
- Files touched: `sequencer.c` (specifically `pick_commits()`), `config.c`, `config.h`, `builtin/rebase.c` (`run_specific_rebase()`), `builtin/revert.c` (`run_sequencer()`), test files `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh`
- New behavior: auto maintenance runs exactly once at sequence completion (after autostash is applied) instead of during intermediate commits/merges. The current patch delegates this to built-in commands; Patrick’s alternative proposes triggering it in `pick_commits()` and on abort.
- CLI/config impact: disables auto maintenance for individual commands (`git commit`, `git merge`, exec commands) during any sequencer-driven operation by passing `maintenance.auto=false` via `GIT_CONFIG_PARAMETERS`; invokes `git maintenance run --auto` at sequence completion. The redundant `gc.auto=0` setting remains removed.
- Subsystems: sequencer, auto maintenance, config
- New symbols: `git_config_append_parameter()` (helper in `config.c` for building `GIT_CONFIG_PARAMETERS` strings with proper shell quoting; format documented in header comment as a space-separated list of `'key'='value'` pairs, each side single-quoted, with `NULL` values treated as boolean `true`), `disable_auto_maintenance()` (helper in `sequencer.c` that builds and caches the config string in `replay_ctx` as a `const char *` (immutable))
- Test coverage: extended in `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh` using `GIT_TRACE2_EVENT` to verify `git maintenance run --auto` is executed exactly once at sequence end and not during intermediate steps. Tests assert the absence of maintenance during intermediate steps and use `test_grep` for better failure output. **Note**: The rebase test does not verify suppression during conflict resolution due to the test scenario not triggering a conflict.
- Code structure: `git_config_append_parameter()` helper in `config.c` builds the config string; `disable_auto_maintenance()` in `sequencer.c` caches the string in `replay_ctx` as a `const char *`. The current patch moves the `run_auto_maintenance()` call from the sequencer to the built-in commands (`run_specific_rebase()` in `builtin/rebase.c`, `run_sequencer()` in `builtin/revert.c`), but Patrick’s review argues this should be consolidated in `pick_commits()` and on abort.

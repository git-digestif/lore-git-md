Subject: [PATCH 0/2] sequencer: defer auto maintenance until rebase completion
Series version: v2 (3 patches)
Originating author: Thomas Bachem (via GitGitGadget)
Thread type: patch series

Core problem or goal
Adjust when auto maintenance runs during sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`) so that it defers until sequence completion, matching the apply backend’s behavior. This prevents maintenance from interfering with intermediate steps and ensures consistent behavior across all three commands.

Current status
Under review; v2 posted. The series is technically complete: all three patches are on-list, the reusable `git_config_append_parameter()` helper is in place, the config string is cached in `replay_ctx`, and the scope covers rebase, cherry-pick, and revert. All prior feedback from Phillip Wood and Patrick Steinhardt has been addressed. Junio C Hamano reviewed the third patch and suggested a mechanical change to store the cached `GIT_CONFIG_PARAMETERS` string as a `const char *` instead of a `struct strbuf` for clarity and to emphasize immutability. The author has confirmed this change will be included in the next revision. Patrick Steinhardt’s latest review of the first patch raises two minor points: the commit message should better explain `GIT_CONFIG_PARAMETERS` and its quoting, and the parameter name `env` in the helper function should be `buf` to avoid over-narrowing the use case. Neither point affects functionality or scope; both are clarity and naming suggestions. No open technical objections remain; the only watch item is a hypothetical edge case about very long sequences where mid-sequence repacking might improve performance, which Phillip Wood wants to monitor in real-world usage rather than block on.

Key technical details
- Files touched: `sequencer.c`, `config.c`, `config.h`, test files `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh`
- New behavior: auto maintenance runs exactly once at sequence completion (after autostash is applied) instead of during intermediate commits/merges
- CLI/config impact: disables auto maintenance for individual commands (`git commit`, `git merge`, exec commands) during any sequencer-driven operation by passing `maintenance.auto=false` and `gc.auto=0` via `GIT_CONFIG_PARAMETERS`; invokes `git maintenance run --auto` at sequence completion
- Subsystems: sequencer, auto maintenance, config
- New symbols: `git_config_append_parameter()` (helper in `config.c` for building `GIT_CONFIG_PARAMETERS` strings with proper shell quoting), `disable_auto_maintenance()` (helper in `sequencer.c` that builds and caches the config string in `replay_ctx`)
- Test coverage: added to `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh` using `GIT_TRACE2_EVENT` to verify `git maintenance run --auto` is executed exactly once at sequence end and not during intermediate steps; covers single-pick, multi-pick, conflict-resolution, and exec scenarios
- Unaffected: the apply backend’s existing behavior
- Error handling: maintenance errors are ignored to avoid masking user-facing issues
- Code structure: `git_config_append_parameter()` helper in `config.c` builds the config string; `disable_auto_maintenance()` in `sequencer.c` caches the string in `replay_ctx`; maintenance invocation added to `sequencer_finish()`, `continue_single_pick()`, `single_pick()`, and `sequencer_continue()`. The cached string will be stored as a `const char *` instead of a `struct strbuf` to clarify immutability. Neither the new helper nor the existing `git_config_from_parameters()` documents the actual format used for the config string, a gap Patrick Steinhardt notes should be addressed for clarity.

Open questions and loose ends
- **Edge cases**: Hypothetical concern about very large sequences where mid-sequence repacking might improve performance; no concrete issue identified, but Phillip Wood wants to monitor real-world usage for complaints. This is noted as a watch item rather than a blocker.
- **Documentation gap**: The format of `GIT_CONFIG_PARAMETERS` is not documented in either `git_config_append_parameter()` or `git_config_from_parameters()`, as noted by Patrick Steinhardt. This should be addressed for clarity but is not a blocker.

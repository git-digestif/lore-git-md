Subject: [PATCH 0/2] sequencer: defer auto maintenance until rebase completion
Series version: v3 (3 patches, v4 expected for commit message polish)
Originating author: Thomas Bachem (via GitGitGadget)
Thread type: patch series

Core problem or goal
Adjust when auto maintenance runs during sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`) so that it defers until sequence completion, matching the apply backend’s behavior. This prevents maintenance from interfering with intermediate steps and ensures consistent behavior across all three commands.

Current status
Under review; v3 posted, v4 expected. The series is technically complete: all three patches are on-list, the reusable `git_config_append_parameter()` helper is in place with documented format, the config string is cached in `replay_ctx` as a `const char *`, and the scope covers rebase, cherry-pick, and revert. All prior feedback from Phillip Wood, Patrick Steinhardt, and Junio C Hamano has been addressed. The latest refinement resolves the final design question by moving the `run_auto_maintenance()` call out of the sequencer and into the built-in commands (`run_specific_rebase()` in `builtin/rebase.c`, `run_sequencer()` in `builtin/revert.c`), consolidating maintenance into a single exit path per command and aligning with the apply backend’s design. This responds directly to Patrick Steinhardt’s preference for a unified exit path and simplifies the rule to "the command runs maintenance once when done." The redundant `gc.auto=0` setting has been removed, simplifying the config string to `maintenance.auto=false` only, as Git’s maintenance infrastructure now exclusively uses `git maintenance` (which respects `maintenance.auto` and will not trigger `git gc --auto` if auto maintenance is disabled). No open technical objections remain; the only watch items are a hypothetical edge case about very long sequences where mid-sequence repacking might improve performance (Phillip Wood wants to monitor real-world usage rather than block on it), and **commit message polish**—specifically, the need to justify the design choice of delegating maintenance to callers, ensure coherence and accuracy, remove any remaining LLM-generated phrasing, and demonstrate human authorship. Patrick Steinhardt has explicitly warned that the current commit messages lack meaningful context and must be revised to avoid appearing LLM-generated. The author has agreed to revise all three commit messages in v4. After v4, the series is likely to be merged to `next`.

Key technical details
- Files touched: `sequencer.c`, `config.c`, `config.h`, `builtin/rebase.c`, `builtin/revert.c`, test files `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh`
- New behavior: auto maintenance runs exactly once at sequence completion (after autostash is applied) instead of during intermediate commits/merges
- CLI/config impact: disables auto maintenance for individual commands (`git commit`, `git merge`, exec commands) during any sequencer-driven operation by passing `maintenance.auto=false` via `GIT_CONFIG_PARAMETERS`; invokes `git maintenance run --auto` at sequence completion. The redundant `gc.auto=0` setting has been removed as unnecessary.
- Subsystems: sequencer, auto maintenance, config
- New symbols: `git_config_append_parameter()` (helper in `config.c` for building `GIT_CONFIG_PARAMETERS` strings with proper shell quoting; format documented in header comment as a space-separated list of `'key'='value'` pairs, each side single-quoted, with `NULL` values treated as boolean `true`), `disable_auto_maintenance()` (helper in `sequencer.c` that builds and caches the config string in `replay_ctx` as a `const char *` (immutable))
- Test coverage: extended in `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh` using `GIT_TRACE2_EVENT` to verify `git maintenance run --auto` is executed exactly once at sequence end and not during intermediate steps; covers single-pick, multi-pick, conflict-resolution, and exec scenarios. Tests now assert the absence of maintenance during intermediate steps and use `test_grep` for better failure output. Commit messages and code comments have been revised to clarify edge cases (e.g., `MERGE_RR.lock` interaction with rerere) and avoid misleading phrasing.
- Unaffected: the apply backend’s existing behavior
- Error handling: maintenance errors are ignored to avoid masking user-facing issues
- Code structure: `git_config_append_parameter()` helper in `config.c` builds the config string; `disable_auto_maintenance()` in `sequencer.c` caches the string in `replay_ctx` as a `const char *`. The `run_auto_maintenance()` call has been moved from the sequencer to the built-in commands (`run_specific_rebase()` in `builtin/rebase.c`, `run_sequencer()` in `builtin/revert.c`), consolidating maintenance into a single exit path per command.

Subject: [PATCH 0/2] sequencer: defer auto maintenance until rebase completion
Series version: v5 (3 patches, final unless new objections arise)
Originating author: Thomas Bachem (via GitGitGadget)
Thread type: patch series

Core problem or goal
Adjust when auto maintenance runs during sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`) so that it defers until sequence completion, matching the apply backend’s behavior. This prevents maintenance from interfering with intermediate steps and ensures consistent behavior across all three commands.

Current status
The series is in `seen` after Junio C Hamano signaled intent to queue it ("Will queue"). The v5 iteration remains **code-identical** to v4; only commit messages, header comments, and test annotations have been updated to address reviewer feedback. The reusable `git_config_append_parameter()` helper and config string caching remain in place, and the redundant `gc.auto=0` setting remains removed. The config string is still `maintenance.auto=false` only.

The **design controversy is now fully settled in favor of the current design** (delegation to built-in commands). Thomas’s latest reply **explicitly documents** why the sequencer cannot reliably trigger maintenance at a single exit point: single-pick cases (`cherry-pick <commit>`, `revert <commit>`, and their `--continue`/`--skip` variants) bypass `pick_commits()` entirely, exiting early through `continue_single_pick()` or `skip_single_pick()`. This justification is now prominently included in patch 2’s commit message. The tests in `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh` have been annotated to clarify conflict triggers and sequence stops, resolving Phillip Wood’s test coverage concerns. No new objections have been raised, and the series is likely to proceed to `next` unless new feedback emerges.

Key technical details
- Files touched: `sequencer.c` (specifically `pick_commits()`, `continue_single_pick()`, `skip_single_pick()`, `run_git_commit()`, `do_merge()`, `do_exec()`), `config.c`, `config.h`, `builtin/rebase.c` (`run_specific_rebase()`), `builtin/revert.c` (`run_sequencer()`), test files `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh`
- New behavior: auto maintenance runs exactly once at sequence completion (after autostash is applied) instead of during intermediate commits/merges. The implementation delegates this to built-in commands (`builtin/rebase.c` and `builtin/revert.c`), as the sequencer lacks a reliable single exit point for single-pick cases.
- CLI/config impact: disables auto maintenance for individual commands (`git commit`, `git merge`, exec commands) during any sequencer-driven operation by passing `maintenance.auto=false` via `GIT_CONFIG_PARAMETERS`; invokes `git maintenance run --auto` at sequence completion.
- Subsystems: sequencer, auto maintenance, config
- New symbols: `git_config_append_parameter()` (helper in `config.c` for building `GIT_CONFIG_PARAMETERS` strings with proper shell quoting; format documented in header comment as a space-separated list of `'key'='value'` pairs, each side single-quoted, with `NULL` values treated as boolean `true`), `disable_auto_maintenance()` (helper in `sequencer.c` that builds and caches the config string in `replay_ctx` as a `const char *` (immutable))
- Test coverage: extended in `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh` using `GIT_TRACE2_EVENT` to verify `git maintenance run --auto` is executed exactly once at sequence end and not during intermediate steps. Tests assert the absence of maintenance during intermediate steps and use `test_grep` for better failure output. The rebase test now explicitly confirms it triggers a conflict (both topic and main branches add `F2`), and the failing exec ensures maintenance only runs at the very end. The cherry-pick tests cover single-pick, sequence, `--continue`, and `--skip` scenarios.

Open questions and loose ends
- **Edge cases**: The hypothetical concern about very long sequences where mid-sequence repacking might improve performance remains unresolved, but no concrete issue has been identified. This is still noted as a watch item.

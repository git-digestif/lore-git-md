Subject: [PATCH 0/2] sequencer: defer auto maintenance until rebase completion
Series version: v4 (3 patches, final)
Originating author: Thomas Bachem (via GitGitGadget)
Thread type: patch series

Core problem or goal
Adjust when auto maintenance runs during sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`) so that it defers until sequence completion, matching the apply backend’s behavior. This prevents maintenance from interfering with intermediate steps and ensures consistent behavior across all three commands.

Current status
Junio C Hamano has signaled intent to queue the series ("Will queue"), meaning it is in `seen`. If no new issues surface, it is likely to graduate to `next` in the next integration cycle and eventually to `master`. The series is technically complete: all three patches are on-list, the reusable `git_config_append_parameter()` helper is in place with documented format, the config string is cached in `replay_ctx` as a `const char *`, and the scope covers rebase, cherry-pick, and revert. All prior feedback from Phillip Wood, Patrick Steinhardt, and Junio C Hamano has been addressed. The latest refinement resolves the final design question by moving the `run_auto_maintenance()` call out of the sequencer and into the built-in commands (`run_specific_rebase()` in `builtin/rebase.c`, `run_sequencer()` in `builtin/revert.c`), consolidating maintenance into a single exit path per command and aligning with the apply backend’s design. This responds directly to Patrick Steinhardt’s preference for a unified exit path and simplifies the rule to "the command runs maintenance once when done." The redundant `gc.auto=0` setting has been removed, simplifying the config string to `maintenance.auto=false` only, as Git’s maintenance infrastructure now exclusively uses `git maintenance` (which respects `maintenance.auto` and will not trigger `git gc --auto` if auto maintenance is disabled). The v4 iteration addresses the sole remaining prerequisite for merging: **commit message polish**. All three commit messages have been significantly tightened—condensed to about a third of their original length—in response to Junio’s and Patrick Steinhardt’s critiques about modern commit message verbosity. The revised messages explicitly justify the design choice of delegating maintenance to callers (noting that `builtin/rebase.c` and `builtin/revert.c` are the only two entry points for sequencer operations), ensure concision and focus, remove any remaining LLM-generated phrasing, and demonstrate human authorship.

Open questions and loose ends
- **Edge cases**: Hypothetical concern about very long sequences where mid-sequence repacking might improve performance; no concrete issue identified, and the author will drop the speculative mention unless real-world usage surfaces complaints. This is noted as a watch item rather than a blocker.
- **Test coverage gap**: Phillip Wood identified a potential gap in the rebase test (`t/t3418-rebase-continue.sh`). The test scenario—rebasing with an exec command that fails—does not trigger a conflict, so `commit_staged_changes()` errors out before attempting to commit. This means the test does not verify that auto maintenance is suppressed during intermediate commits in a real conflict resolution scenario. The test still passes, but the coverage is not meaningful for the intended code path. The author may need to adjust the test to ensure it exercises the suppression logic during conflict resolution.

Key technical details
- Files touched: `sequencer.c`, `config.c`, `config.h`, `builtin/rebase.c`, `builtin/revert.c`, test files `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh`
- New behavior: auto maintenance runs exactly once at sequence completion (after autostash is applied) instead of during intermediate commits/merges
- CLI/config impact: disables auto maintenance for individual commands (`git commit`, `git merge`, exec commands) during any sequencer-driven operation by passing `maintenance.auto=false` via `GIT_CONFIG_PARAMETERS`; invokes `git maintenance run --auto` at sequence completion. The redundant `gc.auto=0` setting has been removed as unnecessary.
- Subsystems: sequencer, auto maintenance, config
- New symbols: `git_config_append_parameter()` (helper in `config.c` for building `GIT_CONFIG_PARAMETERS` strings with proper shell quoting; format documented in header comment as a space-separated list of `'key'='value'` pairs, each side single-quoted, with `NULL` values treated as boolean `true`), `disable_auto_maintenance()` (helper in `sequencer.c` that builds and caches the config string in `replay_ctx` as a `const char *` (immutable))
- Test coverage: extended in `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh` using `GIT_TRACE2_EVENT` to verify `git maintenance run --auto` is executed exactly once at sequence end and not during intermediate steps; covers single-pick, multi-pick, conflict-resolution, and exec scenarios. Tests now assert the absence of maintenance during intermediate steps and use `test_grep` for better failure output. **Note**: The rebase test does not currently verify suppression during conflict resolution due to the test scenario not triggering a conflict.
- Unaffected: the apply backend’s existing behavior
- Error handling: maintenance errors are ignored to avoid masking user-facing issues
- Code structure: `git_config_append_parameter()` helper in `config.c` builds the config string; `disable_auto_maintenance()` in `sequencer.c` caches the string in `replay_ctx` as a `const char *`. The `run_auto_maintenance()` call has been moved from the sequencer to the built-in commands (`run_specific_rebase()` in `builtin/rebase.c`, `run_sequencer()` in `builtin/revert.c`), consolidating maintenance into a single exit path per command.

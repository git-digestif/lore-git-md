This thread is about Patrick Steinhardt’s 11-patch series (v3) to standardize Git’s terminology around "ref storage format," replacing inconsistent names like `--ref-format=` and `GIT_REFERENCE_BACKEND` with `--ref-storage-format=` and `GIT_REF_STORAGE_FORMAT`. The goal is to reduce confusion, particularly in preparation for an analogous `--object-storage-format=` extension, and to fix a bug where reinitializing a repository with a different ref storage format silently corrupts it.

The series is now under final review after addressing all substantive feedback from earlier versions. Key changes in v3 include backward-compatible option aliases (using `OPT_ALIAS_F()` with `PARSE_OPT_HIDDEN`), corrected error messages in `setup.c`, and a two-phase approach to enforce immutability of the existing repository format and URI payloads. The latest patch (10/13) renames environment variables while retaining the old names as aliases, updates documentation, and fixes indentation. All affected areas—CLI options, environment variables, config keys, build-info output, and tests—have been updated, with 54 test scripts modified to reflect the new terminology.

The only unresolved technical edge case is the immutability check for URI payloads, which uses direct string comparison and may reject semantically identical but syntactically different paths (e.g., `files:///path/to/store` vs. `files:///path/to/./store`). Patrick has rejected normalization suggestions, arguing that payload handling is backend-specific. Other open questions are policy-related, such as whether old option names should eventually emit deprecation warnings. Reviewers Karthik Nayak and Kaartic Sivaraam have provided feedback, with Kaartic’s concerns about the immutability check and `PARSE_OPT_NONEG` flag inconsistency remaining unresolved. Junio C Hamano’s initial design-level concern was resolved by adopting the more explicit `--ref-storage-format=` terminology. The series is ready for merging once final reviews are complete.

Subject: [PATCH v1 00/11] refs: unify terminology for "ref storage"
Series version: v1 (v2 anticipated)
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring/cleanup with functional fixes)

Core problem or goal
Git currently uses inconsistent terminology for the "ref storage format" across CLI options (`--ref-format=`), repository extensions (`refStorage`), environment variables (`GIT_REFERENCE_BACKEND`), config keys (`init.defaultRefFormat`), build-info output, and documentation. This series aims to standardize on a single term to avoid confusion, particularly in preparation for an analogous "object storage" extension. The series also centralizes URI parsing for reference storage backends, enabling `--ref-storage-format=` (or similar) to accept URIs like `files://path/to/repo` with payloads (e.g., alternative directories for the "files" backend), and fixes a bug where reinitializing a repository with a different ref storage format silently corrupts the repository.

Current status
Under review (v1 posted; v2 anticipated). No prior versions. Junio C Hamano’s design-level concern about the ambiguity of the term "ref-storage" has been resolved: the series will adopt `--ref-storage-format=` (and `--object-storage-format=` for future object storage extensions) to explicitly distinguish storage format from object hash (controlled by `--object-format=`). The series’ core goals—consistency, URI support, and immutability enforcement—remain unchanged, but the terminology shift will require updates across CLI options, environment variables, config keys, documentation, and tests. The `argh` placeholder for `--ref-storage-format=` in `builtin/init-db.c` will use `"format"` (e.g., `--ref-storage-format=<format>`), resolving Karthik Nayak’s reported inconsistency. Patch 9 (v1) now includes the missing `GIT_DEFAULT_REF_STORAGE_ENVIRONMENT` macro in `environment.h` (noted by Karthik Nayak). No merge status reported; the series remains in discussion pending v2.

Open questions and loose ends
- **Terminology finalization**: The shift to `--ref-storage-format=` (and analogous changes for environment variables, config keys, etc.) resolves Junio’s ambiguity concern, but the revised terminology must be consistently applied across all affected areas (CLI, environment, config, documentation, tests). **This will be addressed in v2.**
- URI handling edge cases (e.g., malformed URIs, unsupported schemes, or ambiguous payloads for backends other than "files" and "reftable")
- Backward compatibility concerns:
  - Sufficiency of backward-compatibility aliases for `--ref-format=`, environment variables, and config keys (now implemented for all three in v1, but v2 will need to retain them for the new names)
  - Scripts relying on old environment variables or config keys (old names are retained as aliases, but third-party tools may still break if they parse help output or error messages)
  - Parsing help output/error messages (e.g., third-party tools expecting specific wording in `git version --build-options` or `git init` diagnostics)
  - Potential for overlooked references in less common code paths (e.g., contrib/, third-party integrations, or submodule helper scripts not covered in this patch)
  - Impact of immutability enforcement on existing workflows (e.g., scripts or tools that reinitialize repositories with different formats)
- Documentation gaps: URI syntax is documented for "files" and "reftable" backends, but other backends (e.g., "packed") may need similar documentation if they support payloads in the future

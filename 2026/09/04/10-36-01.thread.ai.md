Subject: [PATCH v1 00/11] refs: unify terminology for "ref storage"
Series version: v2 (v1 previously posted)
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring/cleanup with functional fixes)

Core problem or goal
Git currently uses inconsistent terminology for the "ref storage format" across CLI options (`--ref-format=`), repository extensions (`refStorage`), environment variables (`GIT_REFERENCE_BACKEND`), config keys (`init.defaultRefFormat`), build-info output, and documentation. This series standardizes on `--ref-storage-format=` (and related names) to avoid confusion, particularly in preparation for an analogous `--object-storage-format=` extension. The series also centralizes URI parsing for reference storage backends, enabling `--ref-storage-format=` to accept URIs like `files://path/to/repo` with payloads (e.g., alternative directories for the "files" backend), and fixes a bug where reinitializing a repository with a different ref storage format silently corrupts the repository.

Current status
Under review (v2 posted; v1 previously posted). Junio C Hamano’s design-level concern about the ambiguity of the term "ref-storage" has been resolved by adopting `--ref-storage-format=` (and `--object-storage-format=` for future object storage extensions) to explicitly distinguish storage format from object hash (controlled by `--object-format=`). Karthik Nayak’s feedback on the `argh` placeholder inconsistency and the missing `GIT_DEFAULT_REF_STORAGE_ENVIRONMENT` macro has been addressed in v2. Kaartic Sivaraam raised a procedural question about the backward-compatibility strategy for the old `--ref-format=` option: whether it should be deprecated with warnings (and eventually removed) or retained indefinitely as a hidden alias. Patch 2 (v2) renames `--ref-format=` to `--ref-storage-format=` in `git clone`, retaining the old name as a hidden backward-compatible alias via `OPT_STRING_F` with `PARSE_OPT_HIDDEN`. Kaartic Sivaraam’s feedback on patch 2 (v2) is purely editorial: he suggests either deprecating the old `--ref-format=` option (with a warning) or using `OPT_ALIAS` to clarify its status, echoing his earlier question about the backward-compatibility strategy, and spots a typo in the test script (`--ref-storage` should be `--ref-storage-format`). Patch 3 (v2) renames `--ref-format=` to `--ref-storage-format=` in `git refs migrate`, retaining the old name as a hidden backward-compatible alias. Kaartic Sivaraam’s feedback on patch 3 (v2) raises a minor consistency question about the `PARSE_OPT_NONEG` flag (present in `git refs migrate` but absent in other commands like `git init` and `git clone`), suggesting it be dropped for consistency but acknowledging this is not a blocker. No technical objections or edge-case concerns have been raised; the feedback remains focused on long-term maintainability, user communication, and internal consistency. Patch 8 (v2) refactors the logic that determines and validates the ref storage format during repository (re)initialization, fixing a bug where reinitializing a repository with a different format silently corrupted it. The patch splits the previously intertwined logic for determining the desired format and validating the result, clearly spelling out the precedence order (command-line option overrides environment variables, which override existing repository format) and enforcing immutability of the existing format once set. This prevents silent corruption and updates error messages to be more specific (e.g., "unknown ref storage format specified via GIT_DEFAULT_REF_FORMAT: 'garbage'"). Patch 9 (v2) renames environment variables (`GIT_REFERENCE_BACKEND` → `GIT_REF_STORAGE_FORMAT`, `GIT_DEFAULT_REF_FORMAT` → `GIT_DEFAULT_REF_STORAGE_FORMAT`) while retaining backward-compatible aliases and adds the missing `GIT_REF_STORAGE_FORMAT_ENVIRONMENT` macro to `environment.h`. Patch 10 (v2) renames the config key `init.defaultRefFormat` → `init.defaultRefStorageFormat` while retaining a backward-compatible alias. Patch 11 (v2) enables URI payloads for `--ref-storage-format=`, completing the series’ functional scope. No merge status reported; the series is in discussion pending further review.

Open questions and loose ends
- URI handling edge cases:
  - Behavior for backends other than "files" and "reftable" when a payload is provided (currently ignored, but should this be documented or rejected?)
  - Handling of relative paths in payloads (e.g., `files://./alt-refs`; currently accepted but may cause confusion)
  - Security implications of allowing arbitrary paths in payloads (e.g., symlink attacks, path traversal)
- Backward compatibility concerns:
  - Sufficiency of backward-compatibility aliases for `--ref-format=`, `--show-ref-format`, environment variables, and config keys (retained in v2, but third-party tools may still break if they parse help output or error messages)
  - Scripts relying on old environment variables or config keys (old names are retained as aliases, but third-party tools may still break if they parse help output or error messages)
  - Parsing help output/error messages (e.g., third-party tools expecting specific wording in `git version --build-options` or `git init` diagnostics)
  - Potential for overlooked references in less common code paths (e.g., contrib/, third-party integrations, or submodule helper scripts not covered in this patch)
  - Impact of immutability enforcement on existing workflows (e.g., scripts or tools that reinitialize repositories with different formats or payloads)
  - Lifecycle of the old `--ref-format=` option: whether it should be deprecated with warnings (and eventually removed) or retained indefinitely as a hidden alias (raised by Kaartic Sivaraam; no resolution yet). Kaartic’s feedback on patch 2 (v2) reiterates this question and suggests two implementation options: (1) mark the old option as deprecated in its help text (following the pattern in `builtin/name-rev.c`), or (2) use `OPT_ALIAS` to clarify its status (as done for `--recursive` in `builtin/clone.c`).
  - Consistency of the `PARSE_OPT_NONEG` flag for `--ref-storage-format=` across commands (present in `git refs migrate` but absent in `git init` and `git clone`; raised by Kaartic Sivaraam in patch 3 feedback)
- Documentation gaps:
  - URI syntax is documented for "files" and "reftable" backends, but other backends (e.g., "packed") may need similar documentation if they support payloads in the future
  - Clarity of error messages for URI-related failures (e.g., "invalid ref storage URI: 'files://'" could be more specific about the expected payload format)
  - Typo in patch 2 (v2) test script: `--ref-storage` should be `--ref-storage-format` (spotted by Kaartic Sivaraam; trivial to fix)

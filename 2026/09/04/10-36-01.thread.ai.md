Subject: [PATCH v1 00/11] refs: unify terminology for "ref storage"
Series version: v2 (v1 previously posted)
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring/cleanup with functional fixes)

Core problem or goal
Git currently uses inconsistent terminology for the "ref storage format" across CLI options (`--ref-format=`), repository extensions (`refStorage`), environment variables (`GIT_REFERENCE_BACKEND`), config keys (`init.defaultRefFormat`), build-info output, and documentation. This series standardizes on `--ref-storage-format=` (and related names) to avoid confusion, particularly in preparation for an analogous `--object-storage-format=` extension. The series also centralizes URI parsing for reference storage backends, enabling `--ref-storage-format=` to accept URIs like `files://path/to/repo` with payloads (e.g., alternative directories for the "files" backend), and fixes a bug where reinitializing a repository with a different ref storage format silently corrupts the repository.

Current status
Under review (v2 posted; v1 previously posted). Junio C Hamano’s design-level concern about the ambiguity of the term "ref-storage" has been resolved by adopting `--ref-storage-format=` (and `--object-storage-format=` for future object storage extensions) to explicitly distinguish storage format from object hash (controlled by `--object-format=`). Karthik Nayak’s feedback on the `argh` placeholder inconsistency and the missing `GIT_DEFAULT_REF_STORAGE_ENVIRONMENT` macro has been addressed in v2. Kaartic Sivaraam raised procedural and consistency questions about the backward-compatibility strategy for the old `--ref-format=` option, the `PARSE_OPT_NONEG` flag inconsistency, error message clarity, and a new edge case in the immutability check for payloads. Patch 9 (v2) renames environment variables (`GIT_REFERENCE_BACKEND` → `GIT_REF_STORAGE_FORMAT`, `GIT_DEFAULT_REF_FORMAT` → `GIT_DEFAULT_REF_STORAGE_FORMAT`) while retaining backward-compatible aliases, adds the missing `GIT_REF_STORAGE_FORMAT_ENVIRONMENT` macro, and updates documentation and test scripts. Kaartic Sivaraam’s feedback on patch 9 (v2) identifies two minor issues: (1) error messages in `setup.c` always cite the new environment variable name even when the value comes from the old, backward-compatible name, which could mislead users, and (2) the test helper variable `GIT_TEST_DEFAULT_REF_FORMAT` is not renamed to match the new pattern (`GIT_TEST_DEFAULT_REF_STORAGE_FORMAT`), creating a small inconsistency in the test suite. No merge status reported; the series is in discussion pending further review.

Open questions and loose ends
- URI handling edge cases:
  - Behavior for backends other than "files" and "reftable" when a payload is provided (currently ignored, but should this be documented or rejected?)
  - Handling of relative paths in payloads (e.g., `files://./alt-refs`; currently accepted but may cause confusion)
  - Security implications of allowing arbitrary paths in payloads (e.g., symlink attacks, path traversal)
  - **Edge case in patch 8 (v2)**: the immutability check for payloads uses a direct string comparison, which can incorrectly reject semantically identical but syntactically different paths (e.g., `files:///path/to/store` vs. `files:///path/to/./store`). Kaartic Sivaraam suggests using `strbuf_realpath()` to normalize paths before comparison, aligning with how the payload is resolved at runtime in `refs_compute_filesystem_location()`.
- Backward compatibility concerns:
  - Sufficiency of backward-compatibility aliases for `--ref-format=`, `--show-ref-format`, environment variables, and config keys (retained in v2, but third-party tools may still break if they parse help output or error messages)
  - Scripts relying on old environment variables or config keys (old names are retained as aliases, but third-party tools may still break if they parse help output or error messages)
  - Parsing help output/error messages (e.g., third-party tools expecting specific wording in `git version --build-options` or `git init` diagnostics)
  - Potential for overlooked references in less common code paths (e.g., contrib/, third-party integrations, or submodule helper scripts not covered in this patch)
  - Impact of immutability enforcement on existing workflows (e.g., scripts or tools that reinitialize repositories with different formats or payloads)
  - Lifecycle of the old `--ref-format=` option: whether it should be deprecated with warnings (and eventually removed) or retained indefinitely as a hidden alias (raised by Kaartic Sivaraam; no resolution yet). Kaartic’s feedback on patches 1 and 2 (v2) reiterates this question and suggests two implementation options: (1) mark the old option as deprecated in its help text (following the pattern in `builtin/name-rev.c`), or (2) use `OPT_ALIAS` to clarify its status (as done for `--recursive` in `builtin/clone.c`). Patrick prefers a quiet deprecation (retaining the old option as a hidden alias without warnings or documentation updates) and is open to adding `PARSE_OPT_HIDDEN` support to `OPT_ALIAS` if needed.
  - Consistency of the `PARSE_OPT_NONEG` flag for `--ref-storage-format=` across commands: present in `git refs migrate` but absent in `git init` and `git clone`. Kaartic Sivaraam suggested dropping the flag for consistency, but Patrick has declined to address this in the current series, leaving the inconsistency unresolved.
  - Clarity of error messages for URI-related failures: Patrick declined Kaartic Sivaraam’s suggestion to rephrase the error message in patch 7 (v2) from `unknown ref storage format: 'garbage://hello-world'` to `fatal: invalid ref storage format configuration: 'garbage://hello-world'`, preferring the existing wording for precision.
  - Error message accuracy in patch 9 (v2): error messages in `setup.c` always cite the new environment variable name even when the value comes from the old, backward-compatible name, which could mislead users into thinking the new name was set when it was not.
  - Test suite consistency in patch 9 (v2): the test helper variable `GIT_TEST_DEFAULT_REF_FORMAT` is not renamed to match the new pattern (`GIT_TEST_DEFAULT_REF_STORAGE_FORMAT`), creating a small inconsistency in the test suite.
- Documentation gaps:
  - URI syntax is documented for "files" and "reftable" backends, but other backends (e.g., "packed") may need similar documentation if they support payloads in the future

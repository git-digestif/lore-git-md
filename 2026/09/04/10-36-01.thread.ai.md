Subject: [PATCH v1 00/11] refs: unify terminology for "ref storage"
Series version: v3 (v2 and v1 previously posted)
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring/cleanup with functional fixes)

Core problem or goal
Git currently uses inconsistent terminology for the "ref storage format" across CLI options (`--ref-format=`), repository extensions (`refStorage`), environment variables (`GIT_REFERENCE_BACKEND`), config keys (`init.defaultRefFormat`), build-info output, and documentation. This series standardizes on `--ref-storage-format=` (and related names) to avoid confusion, particularly in preparation for an analogous `--object-storage-format=` extension. The series also centralizes URI parsing for reference storage backends, enabling `--ref-storage-format=` to accept URIs like `files://path/to/repo` with payloads (e.g., alternative directories for the "files" backend), and fixes a bug where reinitializing a repository with a different ref storage format silently corrupts the repository.

Updates `Documentation/BreakingChanges.adoc`, `Documentation/config/feature.adoc`, `Documentation/config/init.adoc`, `setup.c`, and `t/t0001-init.sh` to reflect the new name.

The patch updates `builtin/init-db.c` and `builtin/clone.c` to pass the full URI string to `init_db()`, where `setup.c` uses `ref_storage_format_by_uri()` to extract the format and payload. Documentation for both commands is updated to describe the URI syntax and note that the "files" and "reftable" backends accept payloads. The immutability check added in patch 9/13 now covers payloads, though the edge case of semantically identical but syntactically different paths (e.g., `files:///path/to/store` vs. `files:///path/to/./store`) remains unresolved.

Open questions and loose ends
- URI handling edge cases:
  - Behavior for backends other than "files" and "reftable" when a payload is provided (currently ignored, but should this be documented or rejected?).
  - Handling of relative paths in payloads (e.g., `files://./alt-refs`; currently accepted but may cause confusion).
  - Security implications of allowing arbitrary paths in payloads (e.g., symlink attacks, path traversal).
  - **Edge case in patch 9/13**: the immutability check for payloads uses a direct string comparison, which can incorrectly reject semantically identical but syntactically different paths (e.g., `files:///path/to/store` vs. `files:///path/to/./store`). Kaartic Sivaraam suggested using `strbuf_realpath()` to normalize paths before comparison, but Patrick has rejected this, arguing that payloads are not guaranteed to be filesystem paths and that normalization logic is backend-specific. The immutability check remains as written.
- Backward compatibility concerns:
  - Lifecycle of the old option/variable names: whether they should eventually emit deprecation warnings or be retained indefinitely as hidden aliases (policy decision, not a technical blocker).
  - Consistency of the `PARSE_OPT_NONEG` flag for `--ref-storage-format=` across commands: present in `git refs migrate` but absent in `git init`, `git clone`, and `git submodule`. Kaartic Sivaraam suggested dropping the flag for consistency, but Patrick has declined to address this, leaving the inconsistency unresolved.
  - Impact of immutability enforcement on existing workflows (e.g., scripts or tools that reinitialize repositories with different formats or payloads).
- Documentation gaps:
  - URI syntax is documented for "files" and "reftable" backends, but other backends (e.g., "packed") may need similar documentation if they support payloads in the future.
  - **Patch 13/13 (v3)**: no new gaps introduced; URI syntax is documented for `git init` and `git clone`.

Subject: [PATCH v1 00/11] refs: unify terminology for "ref storage"
Series version: v2 (v1 previously posted)
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring/cleanup with functional fixes)

Core problem or goal
Git currently uses inconsistent terminology for the "ref storage format" across CLI options (`--ref-format=`), repository extensions (`refStorage`), environment variables (`GIT_REFERENCE_BACKEND`), config keys (`init.defaultRefFormat`), build-info output, and documentation. This series standardizes on `--ref-storage-format=` (and related names) to avoid confusion, particularly in preparation for an analogous `--object-storage-format=` extension. The series also centralizes URI parsing for reference storage backends, enabling `--ref-storage-format=` to accept URIs like `files://path/to/repo` with payloads (e.g., alternative directories for the "files" backend), and fixes a bug where reinitializing a repository with a different ref storage format silently corrupts the repository.

Current status
Under review (v2 posted; v1 previously posted). Junio C Hamano’s design-level concern about the ambiguity of the term "ref-storage" has been resolved by adopting `--ref-storage-format=` (and `--object-storage-format=` for future object storage extensions) to explicitly distinguish storage format from object hash (controlled by `--object-format=`). Karthik Nayak’s feedback on the `argh` placeholder inconsistency and the missing `GIT_DEFAULT_REF_STORAGE_ENVIRONMENT` macro has been addressed in v2. Patch 8 (v2) refactors the logic that determines and validates the ref storage format during repository (re)initialization, fixing a bug where reinitializing a repository with a different format silently corrupted it. The patch splits the previously intertwined logic for determining the desired format and validating the result, clearly spelling out the precedence order (command-line option overrides environment variables, which override existing repository format) and enforcing immutability of the existing format once set. This prevents silent corruption and updates error messages to be more specific (e.g., "unknown ref storage format specified via GIT_DEFAULT_REF_FORMAT: 'garbage'"). The refactoring is mechanical and does not change behavior except for the bug fix; it prepares the codebase for URI payload support in patch 11. No merge status reported; the series is in discussion pending further review.

Open questions and loose ends
- URI handling edge cases (e.g., malformed URIs, unsupported schemes, or ambiguous payloads for backends other than "files" and "reftable")
- Backward compatibility concerns:
  - Sufficiency of backward-compatibility aliases for `--ref-format=`, `--show-ref-format`, environment variables, and config keys (retained in v2, but third-party tools may still break if they parse help output or error messages)
  - Scripts relying on old environment variables or config keys (old names are retained as aliases, but third-party tools may still break if they parse help output or error messages)
  - Parsing help output/error messages (e.g., third-party tools expecting specific wording in `git version --build-options` or `git init` diagnostics)
  - Potential for overlooked references in less common code paths (e.g., contrib/, third-party integrations, or submodule helper scripts not covered in this patch)
  - Impact of immutability enforcement on existing workflows (e.g., scripts or tools that reinitialize repositories with different formats)
- Documentation gaps: URI syntax is documented for "files" and "reftable" backends, but other backends (e.g., "packed") may need similar documentation if they support payloads in the future

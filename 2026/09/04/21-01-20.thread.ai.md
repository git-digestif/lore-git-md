Core problem or goal
The `--force-if-includes` safety mechanism in `git push` incorrectly checks the reflog of the *local* branch whose name matches the *remote* destination branch (e.g., `refs/heads/main` when pushing to `refs/remotes/origin/main`), rather than the branch actually being pushed (e.g., `refs/heads/src` in `src:main`). This flaw can cause false rejections (e.g., pushing from a differently named local branch or detached HEAD) or unintended data loss (e.g., pushing an unrelated branch that happens to share a name with a local branch containing the remote tip). The series also fixes misleading advice messages for detached HEAD rejections, replacing generic "pull" suggestions with actionable guidance.

Current status

The series remains technically complete and ready for merge, but Patrick Steinhardt's review of v3 raises **new technical concerns** about deletion handling, symbolic reference resolution, and documentation wording. The series consists of two patches:
1. Fixes the core logic in `remote.c` to consult the reflog of the pushed ref (`ref->peer_ref->name`) instead of the destination ref (`ref->name`). Adds special handling for `HEAD`-based pushes (resolving the symref) and detached HEAD states (rejecting by default, with the `ref->unverifiable` flag set). Explicitly allows deletions via `is_null_oid(&remote->peer_ref->new_oid)`. The v2 commit message clarifies that `--force-if-includes` already rejects detached HEAD pushes today (when the same-named local branch lacks the remote tip) and this change makes that rejection policy more transparent. Includes 65 lines of new test coverage in `t/t5533-push-cas.sh` covering mismatched local/remote names, `HEAD`-based pushes, and detached HEAD scenarios.
2. Adjusts the advice message for detached HEAD scenarios, introducing a new `ref->unverifiable` flag to distinguish detached HEAD rejections from remote-update rejections. Adds a new `advice.forceIfIncludesDetachedHead` config knob (documented as `advice.pushRefUnverifiable`) and updates the advice message to instruct users to specify the expected remote tip with `--force-with-lease=<ref>:<expect>` or bypass the check with `--no-force-if-includes`. All transport layers (direct pushes, transport helpers, send-pack) are updated for consistency. Test coverage expanded to eight new cases in `t/t5533-push-cas.sh`.

Open questions and loose ends
Patrick Steinhardt raises three **technical concerns** in his reviews of v3:
1. **Deletion handling**: Why are deletions unconditionally allowed? Steinhardt notes deletions are the riskiest operation and suggests the commit message should document the rationale, even if the behavior is unchanged from prior versions.
2. **Symbolic reference resolution**: The current `HEAD` resolution logic passes only `0` to `refs_resolve_ref_unsafe()`, which could return an unresolved `HEAD` or recursively follow symrefs. Steinhardt recommends passing `RESOLVE_REF_READING | RESOLVE_REF_NO_RECURSE` to ensure robust resolution and proposes extending the check to reject any non-reference revision (e.g., `HEAD~`, object IDs) rather than special-casing `HEAD` alone.
3. **Documentation wording**: In patch 2/2, the documentation for `advice.pushRefUnverifiable` uses the word "available" to describe the remote tip; Steinhardt suggests replacing it with "integrated" to more accurately reflect that the check verifies whether the remote tip has been incorporated into the local history.
Additionally, Steinhardt flags a **surface-level nit**: a missing blank line between tests in `t/t5533-push-cas.sh`.

This thread is a bugfix series for Git’s `--force-if-includes` safety mechanism in `git push`. The issue is that the feature incorrectly checks the reflog of the *local* branch matching the *remote* destination name (e.g., `main` when pushing to `origin/main`) instead of the branch actually being pushed (e.g., `src` when pushing `src:main`). This can cause false rejections or unintended data loss, such as when pushing from a differently named local branch or a detached HEAD.

Tyler Cipriani posted v2 of the series, which clarifies the commit message to explicitly note that `--force-if-includes` already rejects detached HEAD pushes today, making this behavior more transparent. The fix itself remains unchanged: it consults the reflog of the pushed ref (`ref->peer_ref->name`) instead of the destination ref (`ref->name`), with special handling for `HEAD`-based pushes and detached HEAD states (rejecting by default). The second patch, also unchanged, improves the advice message for detached HEAD scenarios, introducing a new `advice.forceIfIncludesDetachedHead` config knob and a `ref->unverifiable` flag to distinguish these rejections from others. The advice now guides users to specify the expected remote tip with `--force-with-lease=<ref>:<expect>` or bypass the check with `--no-force-if-includes`.

D. Ben Knoble provided substantive review of v1, confirming the root cause and verifying the fix’s behavior. He initially questioned whether the false rejection/data loss scenario might be intentional but conceded that `--force-if-includes` is meant as a *reminder* to check, not a hard block, making the patch’s explicit bypass requirement appropriate. The series is well-tested, with eight new test cases covering mismatched local/remote names, `HEAD`-based pushes, detached HEAD states, and the new advice message. No open questions remain, and the series is ready for further review.

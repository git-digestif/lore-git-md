This thread is about a patch series (v5) by Thomas Bachem that adjusts when Git's auto maintenance runs during sequencer-driven operations—`git rebase`, `git cherry-pick`, and `git revert`—so it defers until the sequence completes rather than running during intermediate steps. This aligns the behavior with the apply backend and prevents maintenance from interfering with ongoing operations.

The series has now received final approval from Phillip Wood, the primary substantive reviewer, who confirmed the v5 iteration is ready for the `next` branch. The code itself is unchanged from v4; only commit messages, header comments, and test annotations were updated to address prior feedback, including clarifying test logic to make conflicts and sequence stops easier to follow. The design controversy over where to trigger maintenance is fully settled: the sequencer lacks a reliable single exit point for single-pick cases, so the implementation delegates maintenance to the built-in commands (`git rebase` and `git revert`). Junio C Hamano had already signaled intent to queue the series, and with Phillip’s approval, it is likely to proceed unless new objections emerge.

The patches touch `sequencer.c`, `config.c`, `builtin/rebase.c`, `builtin/revert.c`, and two test files, introducing a reusable helper for building `GIT_CONFIG_PARAMETERS` strings and disabling auto maintenance during spawned commands. Tests verify maintenance runs exactly once at sequence completion. The only remaining loose end is a hypothetical concern about very long sequences where mid-sequence repacking might improve performance, but no concrete issue has been identified. Key participants include Thomas (author), Phillip Wood (reviewer), Patrick Steinhardt (reviewer), and Junio (maintainer).

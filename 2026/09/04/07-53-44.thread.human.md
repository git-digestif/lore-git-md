This thread is about a patch series by Thomas Bachem that adjusts when Git’s auto maintenance runs during sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`). The goal is to defer maintenance until the sequence completes, matching the behavior of the apply backend and avoiding interference with intermediate steps. The series is now in its fourth iteration (v4), with Junio C Hamano having signaled his intent to queue it ("Will queue"), meaning it will enter the `seen` branch shortly and is likely to graduate to `next` and eventually `master` if no new issues arise.

The core change moves the `run_auto_maintenance()` call from the sequencer to the built-in commands (`run_specific_rebase()` in `builtin/rebase.c` and `run_sequencer()` in `builtin/revert.c`), consolidating maintenance into a single exit path per command. This aligns with Patrick Steinhardt’s preference for a unified exit path and simplifies the rule to "the command runs maintenance once when done." The series also introduces a reusable `git_config_append_parameter()` helper for building `GIT_CONFIG_PARAMETERS` strings and caches the config string in `replay_ctx` as a `const char *`. All prior feedback from Phillip Wood, Patrick Steinhardt, and Junio has been addressed, including expanding the scope to cover all three sequencer commands, removing redundant settings, and improving test coverage.

The latest iteration (v4) focuses solely on commit message polish, responding to Junio’s critique about modern commit messages being overly verbose. The author significantly tightened all three commit messages—condensing them to about a third of their original length—while preserving the technical justification for the design choices. The only remaining loose end is a test coverage gap identified by Phillip Wood: the rebase test does not currently verify suppression of maintenance during conflict resolution, though this is not a blocker for merging. The series is otherwise technically complete and ready for integration.

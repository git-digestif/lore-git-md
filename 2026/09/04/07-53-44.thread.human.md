This thread is about a patch series (v5) that adjusts when Git's auto maintenance runs during sequencer-driven operations like `git rebase`, `git cherry-pick`, and `git revert`. The goal is to defer maintenance until the entire sequence completes, matching the behavior of the apply backend and avoiding interference with intermediate steps. The series is now effectively finalized after resolving a key design dispute.

The author, Thomas Bachem, has addressed all prior feedback from reviewers, including Phillip Wood and Patrick Steinhardt. The most significant technical hurdle was whether the sequencer could reliably trigger maintenance at a single exit point. Thomas demonstrated that single-pick operations (e.g., `cherry-pick <commit>`) bypass the main sequencer loop entirely, making it impossible to consolidate maintenance logic in one place. This justified the current design, which delegates maintenance to the built-in commands (`git rebase` and `git revert`). The commit messages and tests have been updated to clarify this reasoning, and no new objections have been raised.

The series is currently in Junio C Hamano's `seen` branch, with intent to queue it for `next`. The only remaining open question is a hypothetical edge case about long sequences where mid-sequence repacking might improve performance, but no concrete issue has been identified. Unless new feedback emerges, the series is likely to graduate to `next` soon. Key changes include disabling auto maintenance during individual commands via `GIT_CONFIG_PARAMETERS` and invoking `git maintenance run --auto` at sequence completion. Tests verify maintenance runs exactly once at the end.

This thread is about a patch series (v4) by Thomas Bachem that adjusts when Git's auto maintenance runs during sequencer-driven operations—`git rebase`, `git cherry-pick`, and `git revert`—to defer it until the sequence completes, matching the behavior of the apply backend. The goal is to prevent maintenance from interfering with intermediate steps and ensure consistency across these commands.

The series is effectively complete. Junio C Hamano has signaled intent to queue it ("Will queue"), meaning it will enter the `seen` branch shortly and, barring new issues, graduate to `next` and eventually `master`. All prior feedback from Phillip Wood, Patrick Steinhardt, and Junio has been addressed, including design refinements, code structure improvements, and commit message polish. The latest iteration resolves the final design question by moving the `run_auto_maintenance()` call out of the sequencer and into the built-in commands (`builtin/rebase.c` and `builtin/revert.c`), consolidating maintenance into a single exit path per command. This aligns with Patrick Steinhardt’s preference for a unified exit path and simplifies the rule to "the command runs maintenance once when done."

Phillip Wood’s latest review raises a specific concern about test coverage in `t/t3418-rebase-continue.sh`. The test scenario—rebasing with an exec command that fails—does not trigger a conflict, so the test may not be verifying that auto maintenance is suppressed during intermediate commits. While the test still passes, it doesn’t exercise the intended code path. Phillip notes the series is otherwise in good shape and sets expectations for his availability, but this feedback suggests a minor test hygiene improvement could be made before merging. No objections to the core functionality remain, and the series is on track for integration.

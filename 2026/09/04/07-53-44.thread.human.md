This thread is about a patch series by Thomas Bachem that adjusts when Git's auto maintenance runs during sequencer-driven operations like `rebase`, `cherry-pick`, and `revert`. The goal is to defer maintenance until the sequence completes, matching the behavior of the apply backend and preventing interference with intermediate steps. The series is now at version 3, with all prior feedback from reviewers like Phillip Wood, Patrick Steinhardt, and Junio C Hamano addressed or confirmed for inclusion.

The latest update focuses on the first patch, which introduces a helper function `git_config_append_parameter()` to build `GIT_CONFIG_PARAMETERS` strings with proper shell quoting. Thomas has responded to Patrick Steinhardt’s feedback by agreeing to document the format of `GIT_CONFIG_PARAMETERS` (a space-separated list of `'key'='value'` pairs) in the function’s header comment and rename a parameter for clarity. These are minor adjustments that don’t change the patch’s functionality. The core design—deferring auto maintenance to sequence completion—remains unchanged, though Thomas has proposed an alternative approach: moving the maintenance call from the sequencer to the built-in commands (`rebase`, `cherry-pick`, `revert`) to consolidate it into a single exit path per command. This aligns with Patrick’s preference for a unified exit path and simplifies the rule to "the command runs maintenance once when done."

The series is technically complete and under review, with no open technical objections. The remaining watch items are minor: a hypothetical edge case about long sequences where mid-sequence repacking might help (Phillip Wood wants to monitor real-world usage rather than block on it), and a documentation gap about the `GIT_CONFIG_PARAMETERS` format. Phillip Wood’s latest feedback focused on polish—rewording commit messages to avoid implying active interference (e.g., "lock contention" instead of "maintenance working against other commands"), clarifying edge cases like `MERGE_RR.lock` interaction with rerere, and improving test coverage by extending existing tests rather than duplicating them. The author has incorporated these suggestions and will post v3 shortly.

This is a feature patch series (v2) that revises the earlier `--[no-]range-diff-notes` proposal for `git format-patch`. The series now consists of two patches: the first is a preparatory refactoring, and the second implements the new functionality with a simplified design.

The key change in v2 is the removal of the toggle mechanism (`--no-range-diff-notes --range-diff-notes`) and the arg-less `--range-diff-notes` variant, addressing Junio’s usability concerns from the v1 discussion. The new design enforces explicit separation between patch notes and range-diff notes: `--no-range-diff-notes` means "no notes for the range-diff" without fallback, and `--range-diff-notes=<ref>` requires an explicit ref argument. This eliminates the ambiguous fallback behavior and simplifies the CLI semantics.

The implementation now uses a `parse-options` callback (`rdiff_notes_cb`) instead of the custom `revision.c` handler, and introduces a new `struct rdiff_notes` to track whether the user wants to override the default notes behavior for range-diffs. The `get_notes_args` function is updated to take this struct as a parameter, and the `rev_info` struct is simplified by removing the `rdiff_override_notes` flag and renaming `rdiff_notes_arg` to `rdiff_log_arg` for clarity.

Test coverage is thorough, verifying scenarios like suppressing all range-diff notes, using different notes refs for patches and range-diffs, and ensuring `--range-diff-notes` requires a value. The tests also confirm that `--range-diff-notes` has no effect when `--range-diff` is not used, avoiding silent failures.

The series is well-structured, with clear separation between refactoring and new functionality. The commit messages explain the motivation and changes clearly, and the documentation is updated to reflect the simplified behavior. The design now aligns with Junio’s suggested rule, making the interaction between `--notes` and `--range-diff-notes` predictable and intuitive. While the thread is closed and the feature was previously abandoned, this v2 proposal directly addresses the earlier usability issues and could serve as a viable path forward if revived.

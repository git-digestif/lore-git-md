This is a feature patch series (v3) implementing the matching-inspired fetch mode for shallow repositories. The series introduces `remote.<name>.refmap` configuration to define namespace mappings and dynamically infers which branches to fetch based on local tracking branches plus the remote’s default branch. This replaces the abandoned v2 approach that used a special `+:` refspec.

The core problem remains: shallow repositories experience slow or hanging fetches when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The v3 design addresses this by making the fetch operation more targeted while preserving backward compatibility. The implementation is split into four patches: adding the refmap configuration, inferring branches to fetch, adding a `--limited-fetch` flag for `git remote add`, and defaulting to this mode in shallow repositories.

The series touches `builtin/fetch.c`, `builtin/remote.c`, `remote.c`, and documentation files, with thorough test coverage in a new test script (`t/t5585-fetch-refmap.sh`). The dynamic branch selection logic is well-explained: it fetches branches tracked by local branches at the remote being fetched, plus the remote’s default branch (with fallbacks for stale/missing `HEAD`). The refmap configuration is modular and avoids the need for escape hatches or transition plans, aligning with Junio’s feedback.

This looks like a well-crafted implementation of a consensus-approved design. The commit messages are clear, the test coverage is strong, and the edge cases (stale `HEAD`, empty repositories) are addressed. The series is under active review, with no major objections raised in the thread so far. If you work with shallow repositories, this is worth following—it directly addresses a real performance pain point.

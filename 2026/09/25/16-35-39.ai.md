This is the second patch in Tamir Duberstein’s v2 CI/build system series, addressing parallelism in GitHub Actions and GitLab CI. The patch unifies job-count logic across both providers by dynamically setting `-j` for `make` and `prove` to the runner’s CPU count, replacing the hard-coded `JOBS=10` in GitHub Actions and the platform-specific logic in GitLab CI.

The change moves the `JOBS` assignment to a single `case` block after `CI_OS_NAME` is determined, using `nproc` on Linux, `sysctl -n hw.logicalcpu` on macOS, and `NUMBER_OF_PROCESSORS` on Windows. This matches GitLab CI’s existing policy and avoids oversubscribing Linux runners, which have only 2 CPU cores. Benchmark data in the cover letter shows a 2% speedup on Linux with `1x CPU count` and a 7% speedup with `2x CPU count`, but Tamir opts for the conservative `1x` baseline to ensure consistency.

The patch touches only `ci/lib.sh` (12 insertions, 4 deletions) and introduces no new symbols or behavior changes beyond the parallelism adjustment. It is a straightforward refactoring of CI infrastructure, aligning GitHub Actions with GitLab CI’s more resource-aware approach. The v2 revision addresses Patrick Steinhardt’s review feedback by unifying the logic and using native CPU-count queries on all platforms.

This patch is part of a well-motivated series targeting real CI pain points (OOM kills and ENOSPC errors). While Patch 1 is effectively settled, this one remains under review, with the open question being whether oversubscribing (e.g., `2x CPU count`) would yield a better performance/resource trade-off.

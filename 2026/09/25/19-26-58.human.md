This is a refactoring patch targeting the `fetch.followRemoteHEAD` configuration handling in `builtin/fetch.c`. The patch defers validation of the configuration value until it is actually needed during a fetch operation, rather than validating it during config parsing. This avoids spurious warnings for fetches that never consult the setting.

The change is straightforward: it replaces the direct enum assignment in `git_fetch_config()` with a `char *follow_remote_head_raw` field that stores the raw config string. A new helper function, `get_follow_remote_head()`, parses the string into the appropriate enum value when called in `do_fetch()`. The logic for determining the effective setting (remote override vs. config fallback vs. default) remains unchanged but now runs only when the fetch operation consults the setting.

This is a well-motivated refactoring that addresses a real annoyance—unnecessary warnings for operations that don’t use the config value. The commit message clearly explains the problem and the solution. The implementation is clean and preserves existing behavior, though it does not yet address the remote-side parser in `remote.c` (which shares the same premature validation issue) or the edge case of valueless truth settings (e.g., `fetch.followRemoteHEAD` with no value). Those gaps were identified in Junio’s review and are slated for follow-up patches.

The patch is part of an ongoing discussion, but the direction is aligned with feedback from Junio and Matt Hunter. If you care about reducing noisy warnings or the `fetch.followRemoteHEAD` feature, this is worth tracking. Otherwise, it’s a low-risk refactoring that won’t affect behavior.

This is a documentation patch thread, specifically Junio C Hamano’s reply to Julia Evans’ proposed wording for explaining `git log --merge -p <path>` in the new `gitmergeconflicts(7)` guide. The exchange clarifies the technical behavior of the command and suggests an alternative (`--left-right`) that may be more useful for users inspecting conflicts in a single file.

Junio corrects Julia’s initial misunderstanding of `git log --merge -p <path>`: the command does not limit its output to a single file specified on the command line, but instead identifies all conflicted paths from the index and shows their commit history. When a user provides a specific path, the `--merge` option becomes redundant, as the command already restricts output to that path. Junio recommends `--left-right` as a more informative alternative for single-file inspection, as it distinguishes which side of the merge (ours or theirs) introduced each change.

The feedback is substantive and actionable, addressing both accuracy and utility. Julia’s proposed wording ("will print out all commits which caused the merge conflict for `<filename>`") is technically misleading because it implies the command operates on a single file, which is not how `--merge` works. Junio’s clarification ensures the guide will provide correct and practical advice. The discussion does not introduce new blockers but refines the content of the new guide, advancing the series toward a more accurate and user-friendly resource.

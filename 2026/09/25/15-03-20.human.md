This is the second patch in Tamir Duberstein’s two-patch series addressing resource exhaustion in GitHub Actions CI. The patch dynamically sets parallelism for `make` and `prove` to the number of available CPU cores on Linux runners, replacing the fixed `-j10` default that was causing "no space left on device" (ENOSPC) errors during large clone and repack tests.

Tamir has now posted benchmark data comparing three configurations: the current fixed `-j10`, a dynamic `-j$(nproc)` (1x CPU count), and `-j$(($(nproc) * 2))` (2x CPU count). The results are mixed: on Linux, 2x CPU count is fastest (259.9 minutes vs. 278.9 with `-j10`), but on macOS and Windows, the fixed `-j10` or 1x CPU count performs better. This variability suggests no single setting is optimal across all platforms. In response to Patrick Steinhardt’s review, Tamir has revised the patch to use 1x CPU count consistently across both GitHub and GitLab CI, deferring any further tuning to a future change.

The patch itself is small (four lines in `ci/lib.sh`) and uncontroversial in its current form. The open question is whether 1x CPU count is the right long-term choice, but Tamir has made it clear that this version is intended as a conservative first step. The benchmark data provides a solid foundation for future discussion about oversubscription or platform-specific tuning. The patch looks well-motivated and ready for review, with the remaining debate focused on optimization rather than correctness.

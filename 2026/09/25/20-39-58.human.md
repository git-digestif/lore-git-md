This is the second patch in Jeff King’s two-patch series fixing a regression in `git shortlog` (and other revision commands) where unknown options were incorrectly reported as `(null)` instead of their actual name. The regression was introduced by commit cd439487 ("revision: manage memory ownership of argv in setup_revisions()", 2025-09-19), which changed how `argv` entries are handled during option parsing.

The patch addresses the root cause: the `parse_revision_opt()` function, used by `git shortlog` and `git blame`, was still trying to access the original `argv` location after `handle_revision_opt()` had moved the unknown option elsewhere and set the original location to `NULL`. The fix is simple but precise: instead of referencing `ctx->argv[0]` in the error message, it now uses `ctx->out[ctx->cpidx - 1]`, which points to the consolidated location where the unknown option was moved. This restores the pre-regression behavior, ensuring error messages like `error: unknown option '--no-such-option'` are displayed correctly.

The commit message is thorough, explaining the regression’s origin, why it only manifests with certain option orders (e.g., `git shortlog -n --no-such-option` but not `git shortlog --no-such-option`), and why the chosen fix is preferable to alternatives (like recording the string before parsing). It also clarifies that this change is future-proof, as it doesn’t rely on assumptions about memory ownership that could break if `parse_revision_opt()` ever handles heap-allocated strings.

The patch includes a new test in `t/t4201-shortlog.sh` to verify the fix, ensuring the error message contains the correct option name. While the regression is minor (misleading but not harmful), the fix is well-motivated and low-risk, touching only the error-reporting path in `revision.c`.

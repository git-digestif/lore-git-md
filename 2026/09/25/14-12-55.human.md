This is a bug report about a dangerous interaction between the experimental `git history` command and `git rebase`. The author, Nikita Bobko, demonstrates that running `git history fixup` in the middle of an interactive rebase silently rewrites the branch being rebased, leaving the repository in a broken state where `git rebase --continue` fails and even `git branch --force` cannot repair the branch. The report includes a clear, step-by-step reproducer and explores several potential solutions, though none are obviously correct.

The issue is well-documented and appears serious: the bug corrupts the rebase state in a way that is not recoverable through normal Git commands. The author has cc’d Patrick Steinhardt, the original author of `git history`, suggesting this is a recognized problem in a command that is still under active development. While `git history` is marked experimental, this kind of silent breakage is likely to frustrate users who stumble into it.

The report does not include a patch, so this is not a fix but a call for discussion on how to handle the interaction. The proposed solutions range from outright prohibition during rebase to more nuanced approaches like skipping the current branch or updating the rebase todo list. The author’s preference seems to lean toward option 4 (skip the branch being rebased), but they acknowledge unease about its implications. This is a good candidate for follow-up discussion, especially given the experimental status of the command.

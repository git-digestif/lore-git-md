Thread identity
Subject: `git history` corrupts repository state during interactive rebase
Series version: standalone bug report (no patch series)
Originating author: Nikita Bobko
Thread type: bug report

Core problem or goal
The experimental `git history` command (specifically `git history fixup`) updates branch refs that are locked during an interactive rebase, causing Git to refuse further ref modifications and leaving the rebase stuck with an error about an unexpected ref value. The root issue is that `git history`’s default behavior of updating all descendant branches conflicts with Git’s internal ref locking during rebase.

Current status
Under review. The bug is confirmed by a detailed, reproducible test case provided in the report. No solution has been proposed or agreed upon yet; the author outlines potential approaches (forbidding the command during rebase, requiring explicit flags, or implicitly skipping the current branch) but leaves the final design open for discussion.

Key technical details
- Command: `git history fixup`
- Subsystem: experimental `git history` command (introduced in Git 2.46)
- Files touched: branch refs (`.git/refs/heads/*`)
- Behavior: `git history` updates refs that are locked by `git rebase -i`, causing subsequent ref updates to fail with `cannot lock ref`
- Test coverage: the report includes a complete, self-contained reproducer that initializes a repository, creates a linear history, starts an interactive rebase, pauses it, runs `git history fixup HEAD~`, and demonstrates the stuck rebase
- Edge cases raised: non-linear histories, interactions with `git cherry-pick`, the rebase todo file, and `git rebase --update-refs`

Open questions and loose ends
- What is the correct behavior for `git history` during rebase? Options include:
  - Forbidding the command outright during rebase
  - Requiring an explicit `--force` or `--skip-current-branch` flag
  - Implicitly skipping the current branch (and possibly other locked refs)
- How should `git history` interact with `git cherry-pick` and other operations that lock refs?
- Should `git history` respect the rebase todo file, or is that out of scope?
- Is there a broader design question about how `git history` should handle ref locking in general?

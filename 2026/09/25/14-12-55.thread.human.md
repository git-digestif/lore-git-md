This thread reports a serious bug in the experimental `git history` command, introduced by Nikita Bobko. When `git history fixup` is run during an interactive rebase, it corrupts the repository state by updating the branch ref being rebased, which Git then refuses to modify further. This leaves the rebase stuck with an error about an unexpected ref value. The report includes a detailed, reproducible test case and explores potential solutions, such as forbidding `git history` during rebase, requiring explicit flags, or implicitly skipping the current branch.

The issue stems from `git history`'s default behavior of updating all descendant branches, which conflicts with Git's internal ref locking during rebase. While the immediate symptom is a ref update failure, the root cause is the command's assumption that it can freely rewrite any ref. The thread is likely to focus on how `git history` should interact with other Git operations, particularly rebase and cherry-pick. Patrick Steinhardt, the original author of `git history`, is CC'd, indicating this is a high-priority issue that will likely receive attention. No solution has been proposed yet, leaving the discussion open for technical review and design input.

This is a bugfix patch (v2) targeting the line-log subsystem (`git log -L`). It addresses an inconsistency in how `git log -L :funcname:` determines function boundaries by trimming trailing *blank* lines (lines containing only whitespace) from computed ranges, aligning its behavior with `git grep -W`. The patch is a direct response to Junio C Hamano's feedback on v1, which noted that the initial implementation only trimmed literal newlines (`\n`) rather than all whitespace-only lines, as `git grep -W` does.

The implementation modifies `parse_range_funcname()` in `line-range.c` to scan backward from the end of the function range, skipping any line that consists solely of whitespace (spaces, tabs, or newlines). This matches the logic introduced in prior fix `8e5dd94e68` for `git grep -W`. The patch also updates two new tests in `t/t4211-line-log.sh` to verify the behavior with whitespace-only lines (including spaces and tabs) and renames the tests to reflect the broader scope ("blank" instead of "empty"). Additionally, it updates several expected output files in the test suite to remove trailing blank lines from diff hunks, ensuring consistency with the new behavior.

The range-diff shows the key changes from v1: the logic now uses `isspace()` to check for any whitespace character, not just `\n`, and the tests now include whitespace-only lines. The commit message has been updated to clarify that the patch trims "blank" (whitespace-only) lines, not just "empty" (newline-only) lines, and to note that this change also handles CRLF line endings correctly. The patch is well-motivated, with clear test coverage for the new behavior, though it does not explicitly address whether the documentation for `git log -L` or `git grep -W` should be updated to reflect the now-consistent behavior.

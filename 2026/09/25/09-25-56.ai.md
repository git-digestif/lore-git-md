This is a **build system patch follow-up** in the precompiled headers series. The email is a reply from SZEDER Gábor to Jeff King’s (Peff) substantive review of Patch 4/4, addressing the edge case where target-specific `EXTRA_CPPFLAGS` (e.g., `-DNO_OPENSSL`) invalidate the precompiled header and trigger `-Winvalid-pch` warnings.

SZEDER acknowledges the issue and explains why it occurs: the precompiled header is generated without `EXTRA_CPPFLAGS`, but some flags (like `-DNO_OPENSSL`) affect `git-compat-util.h`, creating a mismatch. He proposes a workaround—appending `-Wno-invalid-pch` to the target’s `EXTRA_CPPFLAGS`—and notes that this is already effective because `EXTRA_CPPFLAGS` are added after the `-Winvalid-pch` flag in the build rule. He also confirms that overriding `-include precompiled.h` is not feasible, leaving the workaround as the only practical solution for now.

The discussion then shifts to Peff’s use case: building historical versions of Git with conditional OpenSSL support. SZEDER shares his own config.mak snippet for disabling OpenSSL in older revisions and expresses surprise that Peff’s approach (target-specific `EXTRA_CPPFLAGS`) is necessary. Peff clarifies that some old versions *require* OpenSSL for certain features, making a global `NO_OPENSSL` insufficient. SZEDER concedes the point and plans to adopt Peff’s technique.

On the broader question of whether this edge case is worth addressing, SZEDER leans toward treating it as a niche scenario: users who set custom `EXTRA_CPPFLAGS` affecting `git-compat-util.h` should also add `-Wno-invalid-pch`. He remains open to other "less crazy" use cases but hasn’t identified any yet. The thread leaves the issue unresolved for now, with no changes to the patch itself—just a documented workaround and a note that the limitation is unlikely to affect most users.

The exchange also touches on build practices for `seen` and historical revisions. SZEDER prefers not to loosen `DEVELOPER=1` for `seen`, as catching issues early is valuable, while Peff’s workflow prioritizes flexibility for exploratory builds. This is a tangential but useful clarification for contributors who bisect or test older versions.

This is a documentation patch thread, part of Julia Evans' seven-patch series introducing `gitmergeconflicts(7)`, a new man page consolidating merge conflict resolution guidance. This specific email is Junio C Hamano’s reply to Julia’s proposed wording for documenting `git log --merge -p <path>` in the new guide.

Junio clarifies the technical behavior of `git log --merge -p <path>`: it identifies conflicted paths from the index and then runs `git log -p` on those paths, optionally filtered by a user-provided pathspec. He suggests that if the user already knows the specific file they care about, the `--merge` option may not add much value, and instead recommends the `--left-right` option as more useful. `--left-right` shows which side of the merge (ours or theirs) contributed each change, which Junio implies is more actionable for users trying to understand conflict origins.

The exchange is a minor but substantive refinement to the new guide’s content. Julia’s proposed wording ("will print out all commits which caused the merge conflict for `<filename>`, and the diff of how they changed the file") is technically correct but may oversimplify the command’s behavior in ways that could mislead users. Junio’s feedback nudges the documentation toward a more precise and practical explanation, emphasizing `--left-right` as a better tool for the job. This interaction does not block the series but improves the guide’s accuracy and utility.

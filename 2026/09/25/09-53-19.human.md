This is a follow-up in the ongoing Git 3.0 planning thread, specifically clarifying JGit's pluggable storage backend capabilities. Luca Milanesio, a contributor with production experience deploying JGit backends, responds to earlier discussion about JGit's readiness for Git 3.0's pluggable object database goals.

Milanesio provides concrete evidence that JGit's pluggable storage architecture is not just theoretical but actively used in high-scale production environments. He highlights three real-world examples: Google's internal Git servers (including `gerrit.googlesource.com`), which run on a proprietary but JGit-compatible backend; GerritForge's open-source global refdb implementation (used in multi-site Gerrit deployments); and the architectural foundation laid 16 years ago by Shawn Pearce that remains viable today. His tone is enthusiastic about the alignment between JGit's long-standing pluggability and Patrick Steinhardt's current work in Git, framing this as an ecosystem win rather than a gap.

The email advances the thread by shifting the narrative from "JGit is a blocker" to "JGit is production-ready for pluggable backends." This is significant for Git 3.0 planning because it removes technical uncertainty about interoperability with JGit-based systems (e.g., Gerrit). However, Milanesio does not address SHA-256 support, which remains a separate concern. The examples he provides—particularly the decade-old Cassandra backend discussion and Google's internal deployment—demonstrate that JGit's architecture is mature enough to handle modern storage innovations, even if adoption has been uneven. This clarification may influence downstream projects' migration plans for Git 3.0, as it suggests JGit can adapt to new storage backends without requiring a rewrite.

Thread identity: Bugfix patch series (single patch) addressing resource leaks in the packfile subsystem during `git gc` or `git maintenance` operations when processes are terminated (e.g., via SIGKILL). Originating author: Royce Remer. Thread type: bug report and fix, now entering architectural discussion.

Core problem or goal: Temporary pack files (e.g., `tmp_pack_XXXXXX`, `tmp_idx_XXXXXX`) created via `odb_mkstemp()` in `pack-write.c` and `pack-bitmap-write.c` are not registered with Git's tempfile subsystem. This omission causes them to persist if the process is killed, leading to disk space exhaustion in environments like Kubernetes pods running Gitea mirrors. The immediate goal is to ensure these temp files are automatically cleaned up on process exit, matching the existing behavior in `git repack`. The broader architectural question is whether `odb_mkstemp()` itself is misplaced in the ODB layer and should be redesigned to return a `struct tempfile *` directly, eliminating the need for manual registration.

Current status: Initial submission (v1). Under review; no merge status reported. The patch is minimal (8 lines across two files) and leverages existing `register_tempfile()` infrastructure. Patrick Steinhardt’s review raises foundational design questions, suggesting the patch may address a symptom rather than the root cause. No decision has been made on whether to proceed with the minimal fix or pursue a larger refactoring.

Key technical details:
- Files touched: `pack-bitmap-write.c`, `pack-write.c` (proposed patch); potential future changes to `odb-mkstemp.c` and `tempfile.h` if architectural feedback is adopted

Open questions and loose ends:
- **Architectural direction**: Should the patch proceed as-is (minimal fix) or should the `odb_mkstemp()` interface be redesigned to return a `struct tempfile *` directly, eliminating the need for manual registration? Patrick Steinhardt’s feedback suggests the latter, but this would require a larger refactoring.
- **API placement**: Is `odb_mkstemp()` misplaced in the ODB layer? Patrick argues it is tied to the "files" backend and assumes a specific directory structure (`objects/`), making it backend-specific rather than generic. He proposes moving it to `tempfile.h` and introducing a new variant (e.g., `mks_tempfile_d()`) to handle leading directories.
- **Backwards compatibility**: Any redesign of `odb_mkstemp()` would need to consider existing callers in the codebase to avoid breaking changes.
- **Test coverage**: The lack of explicit unit tests for this scenario remains unaddressed. While the fix is "self-evident" to the author, reviewers may expect tests to validate cleanup during abnormal termination.
- **Edge cases**: Are there other scenarios (e.g., nested tempfile registration, interactions with other subsystems) that could be affected by the proposed redesign?

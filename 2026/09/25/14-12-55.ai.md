This is a bug report targeting the experimental `git history` command. The author, Nikita Bobko, demonstrates that running `git history` (specifically `git history fixup`) in the middle of an interactive rebase corrupts the repository state. The command updates the branch ref being rebased, which Git then refuses to modify further, leaving the rebase stuck with an error about an unexpected ref value.

The report includes a detailed, step-by-step reproducer that initializes a repository, creates a linear history, starts an interactive rebase, pauses it, runs `git history fixup HEAD~`, and shows how the rebase can no longer continue. The author also explores potential solutions (forbidding `git history` during rebase, requiring explicit flags, or implicitly skipping the current branch) and raises related questions about interactions with `git cherry-pick`, the rebase todo file, and `git rebase --update-refs`.

The email is well-structured, technically precise, and clearly motivated. It cc’s Patrick Steinhardt, the original author of `git history`, signaling that this is a serious issue likely to receive attention. The reproducer is complete and reproducible, making it easy for reviewers to verify the problem. The author’s exploration of edge cases (e.g., non-linear histories, cherry-pick interactions) suggests they have thought deeply about the problem space.

Key technical details for follow-up: the bug affects `git history`’s default behavior of updating all descendant branches, which conflicts with Git’s internal ref locking during rebase. The immediate symptom is a ref update failure (`cannot lock ref`), but the root cause is the command’s assumption that it can freely rewrite any ref. The report does not propose a final solution, leaving that open for discussion. This is likely to become a substantive thread about how `git history` should interact with other Git operations.

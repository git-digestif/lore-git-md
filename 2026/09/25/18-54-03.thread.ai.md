Subject: [PATCH v2] ci: improve leak sanitizer failure reporting in GitHub Actions
Series version: v5 (two-patch series)
Originating author: Harald Nordgren
Thread type: patch (CI/build system improvement)

Core problem or goal
Git’s GitHub Actions CI buries leak sanitizer failures and regular test failures at the end of test runs, producing only a generic “Process completed with exit code 1” message. The series splits the improvement into two focused commits: the first stops leak-sanitizer scripts at the first failure (using `--immediate`) and annotates leaks with the test script name and full sanitizer output in a collapsible log group; the second ensures regular test failures and fixed known breakages also point to their exact file and line in the test script. The goal is to provide actionable failure annotations while balancing early failure (simpler debugging) and comprehensive reporting (catching all leaks), and to avoid unintended side effects on CI usability (e.g., scrolling behavior in the GitHub Actions UI).

Current status
Cooking in `next` as of the prior update, but **blocked by a critical usability regression** identified by Phillip Wood: the new annotation links on the GitHub Actions summary page **only work if the test file was modified in the same pull request**; otherwise, they point to a broken or irrelevant location. This directly contradicts the patch’s core goal of providing actionable failure links. Junio C Hamano’s earlier approval is now contingent on resolving this issue. The series remains in `next` for now, but graduation to `master` is on hold until the regression is fixed.

Key technical details
Files touched: `ci/lib.sh` (adds `--immediate` to `GIT_TEST_OPTS` for leak sanitizer jobs), `t/test-lib-github-workflow-markup.sh` (new functions: `github_annotation_`, `finalize_test_leak_output`, `github_markup_script_name`, `find_test_case_line_`), `t/test-lib.sh` (reorders annotation logic to ensure failures are reported even with `--immediate`).
New symbols: `github_annotation_`, `finalize_test_leak_output`, `github_markup_script_name`, `find_test_case_line_`.
Behavior change: test script now stops on first leak failure (`--immediate`) and emits GitHub Actions annotations with the test script name (line 1) and full leak sanitizer output in a collapsible log group. The reordering of `test_failure_()` ensures annotations are written before any `--immediate` exit. The second patch replaces generic annotations with precise, clickable links pointing to the exact line in the test file where the failure or fixed breakage occurred. The `--immediate` trade-off avoids polluting the output with duplicate "not ok" reports from later tests that inherit the same sanitizer log entries. **Regression**: The annotation links now point to the file diff view, which is useless if the test file was not modified in the pull request (e.g., clicking a `t1022` annotation in the v3 CI run fails to navigate to the test output). No on-disk format changes; test coverage is implicit in the CI workflow.

Open questions and loose ends
1. **Broken annotation links**: The new annotation links are **useless or broken** unless the test file was modified in the same pull request. Phillip Wood’s live examples show the regression in action. This is the **top priority** to resolve before the series can proceed.
2. **Dynamic test descriptions**: The line-finding logic fails for dynamically generated test descriptions (e.g., `test_expect_success "case $i: $desc" ...`), where the fallback to line 1 is acknowledged but not addressed.
3. **UI presentation**: Phillip Wood suggests consolidating test output and leak output into a single collapsible section in the GitHub Actions UI, rather than separating them, to improve usability.
4. **Principled trade-off for `--immediate`**: Phillip Wood’s request for a principled justification or alternative approach to stopping at the first leak remains open. The current approach is pragmatic (avoiding false "not ok" reports) but may hide subsequent distinct leaks.
5. **Commit message clarity**: Phillip Wood’s critique about the lack of concrete annotation format examples in the commit messages remains unresolved. Reviewers must manually inspect CI logs to understand the improvement, wasting time.

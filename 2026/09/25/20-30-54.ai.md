This is a refactoring patch targeting the fetch subsystem, specifically the handling of `fetch.followRemoteHEAD` configuration. Colin Hinton posts v3 of a single-patch series that defers validation of this setting until it is actually used in `do_fetch()`, addressing a long-standing annoyance where warnings are issued during config parsing even when the fetch operation never consults the setting. The patch introduces a new `char *follow_remote_head_raw` field in `struct fetch_config` and a helper function `get_follow_remote_head()` that parses the raw string into the appropriate enum value at lazy-validation time, eliminating spurious warnings and fixing a segfault edge case for valueless truth settings (e.g., `fetch.followRemoteHEAD` with no value).

The patch is well-motivated and narrowly scoped: it touches only `builtin/fetch.c` in this iteration, leaving the remote-side parser in `remote.c` for follow-up work. Colin aligns with Junio’s review by adopting `xstrdup_or_null(v)` to safely handle NULL inputs, and with Matt Hunter’s follow-up direction by treating valueless or invalid values as `FOLLOW_REMOTE_NEVER` with a warning at lazy-validation time. The commit message is clear and the code changes are mechanical, making this a low-risk refactoring that preserves existing precedence rules (remote override vs. config fallback vs. default).

One open question remains: whether to merge the remote-side parser refactoring into the next patch or handle it separately. Colin notes that the only substantive difference between the local and remote parsers is the `warn-if-not-$branch` setting, which is remote-specific and not currently supported for `fetch.followRemoteHEAD`. This suggests the remote-side unification can proceed as a follow-up without complicating the current patch. The patch is ready for review and looks like a clean step toward the broader goal of unifying parsing logic for `fetch.followRemoteHEAD` and `remote.<name>.followRemoteHEAD`.

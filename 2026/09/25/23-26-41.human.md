This is the second patch in Harald Nordgren’s v3 series implementing a "matching-inspired" fetch mode for shallow repositories. Junio C Hamano’s review raises a fundamental design concern: the patch currently *always* fetches the remote’s default branch (resolved via `HEAD`), even when the user has no interest in it. Junio argues this is presumptuous and could waste bandwidth fetching an unwanted branch, especially for secondary remotes where the default branch may not be relevant. He suggests dropping the forced inclusion of the remote’s default branch entirely, simplifying the code and avoiding a potentially confusing fetch report (`HEAD -> second/main` instead of the usual `main -> second/main`).

The review is substantive: it questions the core value proposition of the priming mechanism (ensuring the remote’s default branch is available) and identifies a user-experience quirk in the fetch report. The discussion is now open on whether the default branch should be fetched unconditionally, conditionally, or not at all. This is a key decision point for the series, as it affects both behavior and implementation complexity. The patch is otherwise well-tested and addresses the performance problem in shallow repositories, but this feedback may require a non-trivial rework.

This is a review of Nathan Froyd’s bugfix patch for `git fetch-pack`. The patch addresses an inconsistency where `git fetch-pack` fails to mark exact OIDs (object IDs) in refs, causing it to send `want-ref $OID` instead of `want $OID` when invoked as `git fetch-pack $OID`. This triggers "unknown ref" errors from the remote, while `git fetch` handles the same case correctly.

Junio’s review raises a fundamental concern: unlike `git fetch`, which is a high-level wrapper, `git fetch-pack` is a lower-level command where heuristics like inferring whether an argument is an OID or a ref are undesirable. He questions whether `fetch-pack` should even support this kind of DWIM (Do What I Mean) behavior, arguing that if users need to pass exact OIDs, they should do so explicitly rather than relying on parsing logic. This could break legitimate use cases where someone *wants* to send `want-ref` for an OID, which `git fetch` does not allow but might be a reason to use `fetch-pack` directly.

The patch itself is minimal—just one line to set `ref->exact_oid`—and includes thorough test coverage. However, Junio’s feedback suggests the fix may be too simplistic. The discussion now hinges on whether `fetch-pack` should preserve its low-level precision or align with `fetch`’s more user-friendly behavior. This could lead to a revised approach, such as adding a command-line flag to explicitly mark OIDs, or even deprecating direct use of `fetch-pack` in favor of `git fetch`.

For now, the patch is under review and unlikely to merge as-is. The outcome will depend on whether the project prioritizes consistency with `git fetch` or maintains `fetch-pack` as a strict, unambiguous plumbing command. If you care about this edge case, this thread is worth following.

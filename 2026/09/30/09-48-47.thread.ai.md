Thread identity
Subject: [PATCH 0/2] checkout -m: remember original conflict labels
Series version: v2 (addresses Junio’s feedback on line-ending portability and documentation)
Originating author: Phillip Wood
Thread type: patch series

Core problem or goal
When `git checkout -m` recreates conflict markers after a merge conflict has been resolved, it currently uses generic labels ("base", "ours", "theirs") instead of the original branch names that were shown during the initial merge. This series teaches Git's ort merge backend to store the original conflict labels in `.git/MERGE_LABELS` and reuse them when `git checkout -m` is invoked, ensuring the labels match what the user originally saw.

Current status
Under review; v2 submitted. The series consists of two patches:
1. Refactors `remove_branch_state()` in `branch.c` and `branch.h` to replace its `verbose` boolean argument with an `unsigned flags` field, introducing `REMOVE_BRANCH_STATE_VERBOSE` as the sole flag. This preparatory step has no user-visible behavior change but enables the next patch to add a new flag for preserving conflict labels. All call sites updated; no feedback or concerns raised.
2. Adds plumbing to store and retrieve original conflict labels in the ort backend, updates `git checkout -m` to use the stored labels, and adds a test in `t/t7201-co.sh`. The patch introduces `REMOVE_BRANCH_STATE_PRESERVE_CONFLICT_LABELS` to prevent `remove_branch_state()` from deleting `.git/MERGE_LABELS` during `git checkout -m <branch>`, ensuring labels remain available for subsequent `git checkout -m <path>` calls. The implementation uses `strbuf_getline()` to read labels, ensuring consistent newline handling (LF/CRLF) and fixing the portability issue raised in v1. Edge cases (missing or malformed `.git/MERGE_LABELS`) are handled by falling back to generic labels, and cleanup is ensured via `git commit` and `git sequencer`. Junio’s feedback on documentation (clarifying `.git/MERGE_LABELS` as ephemeral, analogous to `MERGE_MSG`) and portability has been fully addressed in v2. The patch is ready for integration, pending resolution of the open question about conflict style preservation.

Key technical details
- Files touched: `branch.h`, `branch.c`, `builtin/checkout.c` (patch 1); `merge-ort.c`, `branch.c`, `builtin/checkout.c`, and related headers (patch 2).
- New on-disk file: `.git/MERGE_LABELS` (stores original conflict labels; ephemeral, analogous to `MERGE_MSG` or `MERGE_MODE`; not a ref).
- New behavior: `git checkout -m` now shows the same branch names in conflict markers that were present during the initial merge.
- New symbols: `REMOVE_BRANCH_STATE_VERBOSE` (flag, patch 1), `REMOVE_BRANCH_STATE_PRESERVE_CONFLICT_LABELS` (flag, patch 2), `.git/MERGE_LABELS` (file), `write_merge_labels()` and `read_merge_labels()` (functions).
- Test coverage: `t/t7201-co.sh` verifies label preservation.
- No changes to on-disk formats or CLI options beyond `.git/MERGE_LABELS`.
- Edge-case handling: Fallback to generic labels if `.git/MERGE_LABELS` is missing or malformed; cleanup via `git commit` and `git sequencer`. Portability fix: `strbuf_getline()` handles both LF and CRLF line endings, eliminating trailing `\r` on Windows.
- Compatibility: The `.git/MERGE_LABELS` approach aligns with existing merge-related files (`MERGE_MODE`, `MERGE_RR`, `MERGE_MSG`), ensuring consistency with other merge strategies (e.g., `git-merge-octopus`).
- Conflict style behavior: The preserved conflict style (e.g., `diff3`) would only apply as a fallback when the user does not explicitly specify a style via `git checkout --conflict=... -m` or `merge.conflictStyle`. User-specified styles take precedence, addressing workflow flexibility concerns. Junio’s latest reply frames the conflict style question as a trade-off between convenience (automatically restoring the original style) and explicit control (requiring users to specify the style manually). He notes that the only scenario where remembering the style would matter is when the original merge used a one-shot custom style (e.g., `git -c merge.conflictStyle=diff3 merge topic`) that differs from the user’s usual configuration. His example workflow demonstrates that users can already achieve the same effect by explicitly specifying the style when running `git checkout -m`, suggesting the current design is sufficient.

Open questions and loose ends
1. Whether `git checkout -m` should remember and restore the original conflict style (e.g., `diff3`) as a fallback when the user does not explicitly request a different style. Phillip Wood proposes this behavior for consistency with the initial merge, while Johannes Sixt (Hannes) objects, citing workflow flexibility. Junio’s reply frames the question as one of convenience versus explicit control, noting that users can already specify the style manually when needed. No consensus has emerged, and the discussion remains open.
2. The architectural discussion around Johannes Sixt’s suggestion to use an index extension instead of `.git/MERGE_LABELS` remains unresolved. Phillip has rejected this approach, citing compatibility with other merge strategies and alignment with existing patterns (`MERGE_MODE`, `MERGE_RR`, `MERGE_MSG`). Junio framed this as a broader trade-off between cleanliness (index extensions) and accessibility (`.git/MERGE_LABELS` for scripts/users), but no concrete examples or prototypes have been provided to evaluate the index-extension approach. The discussion is not blocking this series.

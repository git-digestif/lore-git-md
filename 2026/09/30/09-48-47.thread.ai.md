Thread identity
Subject: [PATCH 0/2] checkout -m: remember original conflict labels
Series version: v1 (initial submission, v2 expected soon)
Originating author: Phillip Wood
Thread type: patch series

Core problem or goal
When `git checkout -m` recreates conflict markers after a merge conflict has been resolved, it currently uses generic labels ("base", "ours", "theirs") instead of the original branch names that were shown during the initial merge. This series teaches Git's ort merge backend to store the original conflict labels in `.git/MERGE_LABELS` and reuse them when `git checkout -m` is invoked, ensuring the labels match what the user originally saw.

Current status
Under review; v2 expected after addressing feedback. The series consists of two patches:
1. Refactors `remove_branch_state()` in `branch.c` and `branch.h` to replace its `verbose` boolean argument with an `unsigned flags` field, introducing `REMOVE_BRANCH_STATE_VERBOSE` as the sole flag. This preparatory step has no user-visible behavior change but enables the next patch to add a new flag for preserving conflict labels.
2. Adds plumbing to store and retrieve original conflict labels in the ort backend, updates `git checkout -m` to use the stored labels, and adds a test in `t/t7201-co.sh`. The patch introduces `REMOVE_BRANCH_STATE_PRESERVE_CONFLICT_LABELS` to prevent `remove_branch_state()` from deleting `.git/MERGE_LABELS` during `git checkout -m <branch>`, ensuring labels remain available for subsequent `git checkout -m <path>` calls. The implementation handles edge cases (missing or malformed `.git/MERGE_LABELS`) by falling back to generic labels and ensures cleanup via `git commit` and `git sequencer`. Junio’s review feedback on documentation and portability has been addressed in the author’s response: `.git/MERGE_LABELS` is now acknowledged as ephemeral (analogous to `MERGE_MSG` or `MERGE_MODE`) and the line-parsing logic has been fixed to handle CRLF line endings correctly on Windows.

Key technical details
- Files touched: `branch.h`, `branch.c`, `builtin/checkout.c` (patch 1); `merge-ort.c`, `branch.c`, `builtin/checkout.c`, and related headers (patch 2).
- New on-disk file: `.git/MERGE_LABELS` (stores original conflict labels; ephemeral, analogous to `MERGE_MSG` or `MERGE_MODE`; not a ref).
- New behavior: `git checkout -m` now shows the same branch names in conflict markers that were present during the initial merge.
- New symbols: `REMOVE_BRANCH_STATE_VERBOSE` (flag, patch 1), `REMOVE_BRANCH_STATE_PRESERVE_CONFLICT_LABELS` (flag, patch 2), `.git/MERGE_LABELS` (file).
- Test coverage: `t/t7201-co.sh` verifies label preservation.
- No changes to on-disk formats or CLI options beyond `.git/MERGE_LABELS`.
- Edge-case handling: Fallback to generic labels if `.git/MERGE_LABELS` is missing or malformed; cleanup via `git commit` and `git sequencer`. Portability fix: `strbuf_getline()` now handles both LF and CRLF line endings, eliminating the risk of trailing `\r` on Windows.
- Compatibility: The `.git/MERGE_LABELS` approach aligns with existing merge-related files (`MERGE_MODE`, `MERGE_RR`, `MERGE_MSG`), ensuring consistency with other merge strategies (e.g., `git-merge-octopus`).

Open questions and loose ends
1. Phillip explicitly asks whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`), not just the labels. He is unsure if this would be convenient or confusing and invites feedback. No responses or positions on this question have been recorded yet.
2. Johannes Sixt (Hannes) suggests using an index extension instead of `.git/MERGE_LABELS` to store the original conflict labels, distinguishing between *pseudo-refs* (like `MERGE_HEAD`) and *auxiliary information* (like `MERGE_LABELS`). He argues that `MERGE_LABELS` is ephemeral data that doesn’t belong in the refs namespace and could be stored in an index extension, but concedes this approach may be "prohibitively difficult" to access. Junio’s follow-up frames this as a broader architectural trade-off: replacing all special `*_HEAD` files with index extensions would "unclutter `$GIT_DIR/`" but make the information less accessible to users and scripts. Phillip Wood has now explicitly rejected the index extension approach, citing compatibility with other merge strategies and alignment with existing patterns (`MERGE_MODE`, `MERGE_RR`, `MERGE_MSG`) as reasons to retain `.git/MERGE_LABELS`. The discussion remains open on whether the architectural trade-offs (e.g., index bloat, compatibility, discoverability) justify revisiting this decision, but no concrete examples or prototypes have been provided to evaluate the index-extension approach.

Core problem or goal
When `git checkout -m` recreates conflict markers after a merge conflict has been resolved, it uses generic labels ("base", "ours", "theirs") instead of the original branch names shown during the initial merge. This series teaches Git's ort merge backend to store the original conflict labels in `.git/MERGE_LABELS` and reuse them when `git checkout -m` is invoked, ensuring the labels match what the user originally saw. Junio’s follow-up patches (PATCH 2/3 and PATCH 3/3) optimize performance by caching per-invocation constants (e.g., `merge.renormalize`, conflict style, and `.git/MERGE_LABELS` file state) in a new `struct checkout_merged_data`, eliminating redundant config reads and file I/O.

Current status
Queued in `next` after Junio's explicit acceptance in his final reply to v3 and confirmed in this v4 acceptance message. Junio states he will replace the prior version in his integration branches, signaling the series is on track for graduation to `master` in the current cycle. All patches are functionally complete and ready for integration. The series consists of three patches:
1. Refactors `remove_branch_state()` in `branch.c` and `branch.h` to replace its `verbose` boolean with an `unsigned flags` field, introducing `REMOVE_BRANCH_STATE_VERBOSE` as the sole flag. This preparatory step has no user-visible behavior change but enables the next patch to add a new flag for preserving conflict labels. All call sites updated; no feedback or concerns raised.
2. Junio’s follow-up refactoring (PATCH 2/3 in v4): Optimizes performance by caching per-invocation constants (`merge.renormalize` and conflict style) in a new `struct checkout_merged_data`, eliminating redundant config reads. The patch is a pure refactoring with no user-visible behavior change, touching only `builtin/checkout.c`. It introduces `checkout_merged_prepare()` and updates `checkout_merged()` to use the precomputed values. Junio’s contribution is now credited as “Helped-by” in the commit metadata, reflecting his earlier clarification.
3. Adds plumbing to store and retrieve original conflict labels in the ort backend, updates `git checkout -m` to use the stored labels, and adds a test in `t/t7201-co.sh`. The patch introduces `REMOVE_BRANCH_STATE_PRESERVE_CONFLICT_LABELS_FILE` (renamed for clarity, as the flag only prevents deletion of `.git/MERGE_LABELS` during cleanup). The implementation uses `strbuf_getline()` to read labels, ensuring consistent newline handling (LF/CRLF) and fixing the portability issue raised in v1. Edge cases (missing or malformed `.git/MERGE_LABELS`) are handled by falling back to generic labels, and cleanup is ensured via `git commit` and `git sequencer`. Junio’s feedback on documentation, portability, flag naming, conditional preservation logic, idiomatic buffer detachment, style nits, API signature tightening, parsing robustness, and the correctness bug in `.git/MERGE_LABELS` writing logic has been fully addressed in v4. The patch also caches `.git/MERGE_LABELS` file state in `struct checkout_merged_data` to avoid repeated file I/O.

Key technical details
- Files touched: `branch.h`, `branch.c`, `builtin/checkout.c` (patch 1); `builtin/checkout.c` (patch 2); `merge-ort.c`, `branch.c`, `builtin/checkout.c`, and related headers (patch 3).
- New on-disk file: `.git/MERGE_LABELS` (stores original conflict labels; ephemeral, analogous to `MERGE_MSG` or `MERGE_MODE`; not a ref; written only when conflicts occur).
- New behavior: `git checkout -m` now shows the same branch names in conflict markers that were present during the initial merge.
- New symbols: `REMOVE_BRANCH_STATE_VERBOSE` (flag, patch 1), `REMOVE_BRANCH_STATE_PRESERVE_CONFLICT_LABELS_FILE` (flag, patch 3), `.git/MERGE_LABELS` (file), `write_merge_labels()` and `read_merge_labels()` (functions; signature takes a single `const char *labels[3]` array for clarity), `struct checkout_merged_data` (patches 2 and 3), `checkout_merged_prepare()`, and `checkout_merged_release()` (patch 2).
- Test coverage: `t/t7201-co.sh` verifies label preservation and absence of `.git/MERGE_LABELS` after clean `git checkout -m <branch>`.
- No changes to on-disk formats or CLI options beyond `.git/MERGE_LABELS`.
- Edge-case handling: Fallback to generic labels if `.git/MERGE_LABELS` is missing or malformed; cleanup via `git commit` and `git sequencer`. Portability fix: `strbuf_getline()` handles both LF and CRLF line endings, eliminating trailing `\r` on Windows.
- Compatibility: The `.git/MERGE_LABELS` approach aligns with existing merge-related files (`MERGE_MODE`, `MERGE_RR`, `MERGE_MSG`), ensuring consistency with other merge strategies (e.g., `git-merge-octopus`).
- Conflict style behavior: Preserved conflict styles (e.g., `diff3`) apply only as a fallback when the user does not explicitly specify a style via `git checkout --conflict=... -m` or `merge.conflictStyle`. User-specified styles take precedence, addressing workflow flexibility concerns. Junio framed the conflict style question as a trade-off between convenience and explicit control, noting that users can already specify the style manually when needed. This series does not attempt to address the conflict style question, keeping the scope narrow and uncontroversial.
- API improvements: `write_merge_labels()` takes a `const char *labels[3]` array instead of three separate string arguments, treating the labels as a single unit for clarity. `strbuf_detach()` is used instead of `xmemdupz()` for detaching the buffer in `parse_merge_label_line()`, and style nits (asterisks in function declarations, missing comment explaining ignored extra lines in `.git/MERGE_LABELS`) were addressed.
- Performance optimization: Patches 2 and 3 cache per-invocation constants (e.g., `merge.renormalize`, conflict style, and `.git/MERGE_LABELS` file state) in `struct checkout_merged_data`, eliminating redundant config reads and file I/O.

Open questions and loose ends
1. Whether `git checkout -m` should remember and restore the original conflict style (e.g., `diff3`) as a fallback when the user does not explicitly request a different style. Phillip Wood proposes this behavior for consistency with the initial merge, while Johannes Sixt (Hannes) objects, citing workflow flexibility. Junio framed the question as one of convenience versus explicit control, noting that users can already specify the style manually when needed. No consensus has emerged, but this series explicitly excludes the conflict style question, keeping the scope narrow. The discussion remains open for future work.
2. The architectural discussion around Johannes Sixt’s suggestion to use an index extension instead of `.git/MERGE_LABELS` remains unresolved. Phillip rejected this approach, citing compatibility with other merge strategies and alignment with existing patterns (`MERGE_MODE`, `MERGE_RR`, `MERGE_MSG`). Junio framed this as a broader trade-off between cleanliness (index extensions) and accessibility (`.git/MERGE_LABELS` for scripts/users), but no concrete examples or prototypes have been provided. The discussion is not blocking this series.

This thread is about a small but user-visible improvement to Git’s merge conflict handling. When `git checkout -m` recreates conflict markers after a merge conflict has been resolved, it currently shows generic labels like "ours" and "theirs" instead of the original branch names the user saw during the initial merge. Phillip Wood’s two-patch series teaches Git’s ort merge backend to remember the original conflict labels in a new `.git/MERGE_LABELS` file and reuse them when `git checkout -m` is run again.

The series is under active review and is expected to land soon. Junio C Hamano, the maintainer, has already given his thumbs-up to the documentation and portability fixes Phillip made in response to earlier feedback, so the next step is a v2 that incorporates those tweaks. The implementation is straightforward: the first patch refactors a helper function to use flags instead of a boolean, and the second adds the plumbing to store and retrieve the labels. Tests confirm the feature works as intended, and edge cases—like missing or malformed label files—are handled gracefully by falling back to the generic labels.

Two questions remain open. Phillip has asked whether `git checkout -m` should also remember the original conflict style (e.g., `diff3`), but no one has weighed in yet. Johannes Sixt suggested storing the labels in an index extension rather than a separate file, but Phillip rejected that idea as incompatible with other merge strategies and less accessible to users and scripts. Junio explored the architectural trade-offs but didn’t push for a change, so the file-based approach is likely to stick. The series is otherwise uncontroversial and should graduate to Junio’s `next` branch once v2 is posted.

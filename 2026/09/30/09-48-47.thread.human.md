This thread is about teaching `git checkout -m` to remember and reuse the original branch names in conflict markers, rather than falling back to generic labels like "ours" and "theirs". Phillip Wood sent a two-patch series (now at v2) that refactors branch state cleanup and adds plumbing to store conflict labels in `.git/MERGE_LABELS`, a new ephemeral file analogous to `MERGE_MSG`.

The series is under review and nearly ready for integration. All feedback from Junio Hamano—covering documentation, portability, flag naming, style, and a correctness bug in `.git/MERGE_LABELS` writing—has been addressed in v2. The only remaining open question is whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`) as a fallback when the user doesn’t explicitly request a different style. Phillip supports this for consistency, while Johannes Sixt objects, citing workflow flexibility. Junio framed this as a trade-off between convenience and explicit control, noting that users can already specify the style manually if needed. The discussion is not blocking the series, and the architectural alternative (using an index extension instead of `.git/MERGE_LABELS`) has been set aside for now.

Phillip’s latest reply confirms a fix for the last known correctness issue: `.git/MERGE_LABELS` will now be written only when conflicts occur, avoiding `(null)` strings for clean merges. The series is otherwise functionally complete, with test coverage in `t/t7201-co.sh` and no changes to on-disk formats or CLI options beyond the new `.git/MERGE_LABELS` file.

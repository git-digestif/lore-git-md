This thread is about a patch series that improves `git checkout -m` by making it remember the original branch names used in conflict markers, so users see the same labels they saw during the initial merge. The series, authored by Phillip Wood, is now in its third version and has been accepted by Junio Hamano for integration into the `next` branch, putting it on track for the upcoming release.

The series consists of two patches. The first refactors some internal branch state handling to prepare for the feature, while the second adds the core functionality: storing original conflict labels in a new `.git/MERGE_LABELS` file and reusing them when `git checkout -m` is invoked. All technical feedback from Junio on the previous version—including a correctness bug, API improvements, and portability fixes—has been addressed. The implementation is careful to handle edge cases, like missing or malformed label files, by falling back to generic labels, and it ensures cleanup after use.

Junio also submitted a follow-up patch to optimize performance by caching per-invocation constants, like `merge.renormalize` and conflict style, in a new data structure. This avoids redundant config reads and file I/O during a single `git checkout -m` run. Phillip has incorporated this patch verbatim, and it’s ready for integration, though there’s a minor open question about whether it should be squashed into the original series or kept as a separate patch.

The only unresolved discussion is whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`) when the user doesn’t explicitly request a different style. Phillip proposed this for consistency, but Johannes Sixt objected, arguing it could interfere with workflow flexibility. Junio framed this as a trade-off between convenience and explicit control, noting users can already override the style manually. This debate doesn’t block the current series, which keeps its scope narrow by focusing only on label preservation. The series is now functionally complete and uncontroversial, with all technical feedback resolved.

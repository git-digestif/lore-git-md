This thread is about a two-patch series by Phillip Wood that teaches `git checkout -m` to remember and reuse the original branch names shown in conflict markers during a merge, rather than falling back to generic labels like "ours" and "theirs". The series is now in its second version, with all prior feedback from Junio Hamano fully addressed—except for one last correctness issue just raised.

The first patch refactors `remove_branch_state()` to use a flags field instead of a boolean, preparing the ground for the second patch. This preparatory change is uncontroversial and ready for integration. The second patch implements the core feature: storing original conflict labels in `.git/MERGE_LABELS` and reusing them when `git checkout -m` is invoked. It also includes a test in `t/t7201-co.sh` and handles edge cases like missing or malformed label files by falling back to generic labels.

Junio’s latest review identified a logical bug in the second patch: the code currently writes `.git/MERGE_LABELS` unconditionally, even for clean merges where no conflicts (and thus no labels) exist. This could result in writing garbage values to the file. The fix is simple—only write the file when conflicts occur—and aligns with the existing pattern for other merge-related files like `MERGE_MSG`. With this addressed, the series should be ready for integration.

Two open questions remain, neither of which blocks the current work. The first is whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`) as a fallback when the user doesn’t explicitly request a different style. Phillip supports this for consistency, while Johannes Sixt objects, citing workflow flexibility. Junio framed this as a trade-off between convenience and explicit control, noting that users can already specify the style manually if needed. The second question is architectural: Johannes suggested using an index extension instead of `.git/MERGE_LABELS`, but Phillip rejected this approach, and Junio remained neutral. No consensus has emerged on either point.

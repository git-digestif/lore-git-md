This thread is about a two-patch series by Phillip Wood that improves `git checkout -m` by remembering the original branch names used in conflict markers during a merge, so they’re reused if the user later re-checks out the conflicted files. The series is now at v2, addressing Junio’s earlier feedback on documentation, portability, and code clarity.

The first patch refactors `remove_branch_state()` to use a flags field instead of a boolean, preparing the ground for the second patch. The second patch adds the core functionality: storing the original conflict labels in `.git/MERGE_LABELS` and reusing them when `git checkout -m` is called. Junio’s feedback on v2 was positive, with only minor technical points raised—none blocking integration. The series is effectively ready to merge, pending Phillip’s response to these optional cleanups.

One open question remains: whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`) when the user doesn’t explicitly specify one. Phillip supports this for consistency, while Johannes Sixt prefers leaving it to the user. Junio framed this as a trade-off between convenience and explicit control, noting that users can already specify the style manually if needed. The discussion hasn’t reached consensus, but it doesn’t block the current series.

The latest email from Junio suggests small, idiomatic improvements to the code that writes conflict labels—extracting a struct pointer directly and tightening the function signature to treat the labels as a single array. These are stylistic tweaks that don’t affect behavior, but they align with Git’s coding conventions. The series remains ready for integration regardless.

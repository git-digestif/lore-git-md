This thread introduces a small but user-visible improvement to `git checkout -m`: when you resolve a merge conflict and later use `git checkout -m` to re-create the conflict, the conflict markers will now show the original branch names (e.g., `feature-branch` vs. `main`) instead of generic labels like "ours" and "theirs". The series is from Phillip Wood, a well-known contributor with deep expertise in Git's merge and sequencer code.

The change is split into two patches. The first is a preparatory refactor that replaces a boolean argument in `remove_branch_state()` with a flags field, setting the stage for the second patch. The second patch—the one just summarized—implements the core feature: it stores the original conflict labels in a new `.git/MERGE_LABELS` file during a merge, and updates `git checkout -m` to read and reuse those labels. The patch includes a test and handles edge cases like missing or malformed label files by falling back to the generic labels. The new file is automatically cleaned up by `git commit` and sequencer operations, so no stale state lingers.

The series is under review and has no prior versions. Phillip has left one open question: whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`), not just the labels. So far, no reviews or objections have been recorded.

This thread is about Phillip Wood’s patch series that teaches `git checkout -m` to remember and reuse the original branch names in conflict markers, rather than generic labels like "ours" and "theirs". The series is now at v2, addressing Junio’s earlier feedback on documentation and portability, and is under review.

The core change is straightforward: when a merge conflict occurs, Git’s ort backend now stores the original conflict labels (e.g., branch names) in `.git/MERGE_LABELS` and reuses them if `git checkout -m` is later used to recreate conflicts. This ensures consistency with what the user saw during the initial merge. The implementation is robust, handling edge cases like missing or malformed label files by falling back to generic labels, and it works across platforms (LF/CRLF line endings). The first patch, a preparatory refactor of `remove_branch_state()`, is uncontroversial, while the second patch—adding the label storage and retrieval logic—is functionally complete and ready for integration.

The main open question is whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`) as a fallback when the user doesn’t explicitly specify one. Phillip argues this would be convenient for users who want consistency with the initial merge, while Johannes Sixt (Hannes) prefers keeping the current behavior to avoid overriding user preferences. Junio’s recent reply frames this as a trade-off between convenience and explicit control, noting that users can already achieve the same effect by explicitly specifying the style when running `checkout -m`. His tone is neutral, but his example workflow suggests he sees value in the current flexibility. No other objections or technical concerns have been raised, and the architectural debate about using an index extension instead of `.git/MERGE_LABELS` remains unresolved but is not blocking the series.

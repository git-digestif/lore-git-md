This thread is about a patch series that improves `git checkout -m` by making it remember and reuse the original branch names shown in conflict markers during a merge, rather than falling back to generic labels like "ours" and "theirs". The series, now at version 4, is authored by Phillip Wood and has been accepted by maintainer Junio C Hamano for integration.

The key change is that Git's ort merge backend now stores the original conflict labels in a new `.git/MERGE_LABELS` file, which `git checkout -m` reads when recreating conflicts. This ensures the labels match what the user saw during the initial merge. The series also includes preparatory refactoring (splitting a boolean flag into a bitfield) and performance optimizations (caching per-invocation constants like `merge.renormalize` and conflict style in a new struct to avoid redundant config reads and file I/O). Junio contributed the performance patches, which Phillip incorporated verbatim, crediting Junio as a helper rather than a co-author.

All technical feedback from prior versions—including concerns about portability, API design, edge-case handling, and a correctness bug in `.git/MERGE_LABELS` writing—has been addressed. The series is queued in Junio's `next` branch and is expected to graduate to `master` in the current cycle. Two broader questions remain open but are explicitly out of scope for this series: whether `git checkout -m` should also remember the original conflict style (e.g., `diff3`), and whether Git should use index extensions instead of `.git/MERGE_LABELS` for storing transient merge state. Phillip and Junio have kept the scope narrow to avoid controversy, focusing on the uncontroversial label preservation feature.

Subject: [PATCH 0/4] Fix MIDX reachability closure corner cases
Series version: v2 (eight patches, incorporating all feedback from v1)
Originating author: Taylor Blau
Thread type: patch series (bugfix)

Core problem or goal
The series fixes corner cases in Git’s multi-pack-index (MIDX) and cruft-pack machinery where MIDXs can end up containing objects that are not closed under reachability. This violates the MIDX’s invariant that it contains all objects reachable from its tips, causing failures in bitmap generation. The problem surfaces in four scenarios: `--stdin-packs=follow`, incremental repacks, `.keep` packs, and `--write-midx=incremental` (including `GIT_TEST_MULTI_PACK_INDEX_WRITE_INCREMENTAL`).

Current status
Under review; v1 was the initial submission, and v2 (now eight patches) addresses all substantive feedback from Jeff King, Derrick Stolee, and Junio C Hamano. The series is well-motivated, narrowly scoped, and ready for integration. Patch 1/8, a pure refactoring introducing `stdin_packs_context`, has received maintainer approval in spirit and is uncontroversial. Patch 4/8, a mechanical refactoring replacing a linear search through `--keep-pack` arguments with a sorted list and binary search, is now **explicitly endorsed by Jeff King** as correct and sensible. This patch is uncontroversial and ready for integration. Patch 6/8, a refactoring in `repack-midx.c`, introduces a `preferred_pack` field in the `midx_compaction_step` struct to explicitly track the preferred pack, removing the dependency on string-list order and enabling future optimizations such as sorting the list for faster membership checks. Jeff King’s **substantive review** of patch 6/8 questioned whether the refactoring is strictly necessary for correctness but endorsed it as a cleaner design, particularly appreciating the removal of pointer casts. Taylor Blau’s **substantive follow-up** clarifies that the existing code marks *multiple* preferred packs (one per MIDX layer during compaction) and selects the *last* marked entry, making the choice order-dependent. Sorting the string list would preserve the marks but could change which pack is last, breaking the intended behavior. This explanation confirms the refactoring’s necessity if the list is ever to be sorted. The patch is now uncontroversial and ready for integration. Patch 7/8, a mechanical refactoring in `repack-midx.c`, defers allocation of the write step in `repack_make_midx_append_plan()` until the first pack is actually added, rather than pre-allocating it unconditionally when `opts->names->nr` is non-zero. This change accommodates future logic where a non-empty candidate list no longer guarantees that a write step is needed (e.g., when packs are already covered by the MIDX chain). The patch moves the write-step allocation inside the loop that iterates over `opts->names` and introduces a `step` pointer initialized to `NULL` and set only when the first pack is processed. The `strbuf` is now declared outside the loop to avoid repeated initialization and release, and the loop structure is simplified by removing the conditional block that previously wrapped the write-step creation. Patch 8/8, which allows the append plan to skip packs already covered by the MIDX chain, builds directly on this refactoring and **fixes a previously unnoticed gap in incremental MIDX writes** (both geometric and append-only) where required packs—particularly cruft packs and kept packs—could be omitted from the MIDX chain, breaking bitmap generation. The patch modifies `repack-midx.c` to consult `midx_included_packs()` when building the write step for both append and geometric plans, ensuring that packs not already in the chain (e.g., cruft packs when `repack.midxMustContainCruft` is false, or kept packs needed for reachability) are included. The logic skips packs already present in retained base layers but includes those from a replaced tip. The documentation in `git-repack.adoc` is updated to clarify that incremental MIDX writes now include "newly written packs and any other required packs not already in the chain." Jeff King’s **surface-level review** of patch 8/8 expressed difficulty following the logic but deferred to the test coverage, noting that the key change—consulting `midx_included_packs()`—appears correct. Taylor Blau’s reply confirmed the patch’s intent and acknowledged the complexity of the code but did not add new technical detail or address Peff’s low-confidence assessment. The patch remains uncontroversial and ready for integration, though its implementation has not been deeply scrutinized beyond Peff’s surface-level review.

Open questions and loose ends
The **data structure choice for `extra_roots` in patch 2/8** remains **contested** following **substantive reviews** from Elijah Newren and Jeff King. Newren’s test cases demonstrate that an `oid_array` preserves critical path and namehash ordering required for delta compression quality and attribute handling, while an `oidset` would introduce functional regressions (blobs written in full instead of as deltas, misapplied path-based attributes). Jeff King’s latest **substantive follow-up** sides with Newren, emphasizing the importance of preserving pack-order correlation for delta compression quality, even if the solution is not perfect. Peff acknowledges the memory trade-offs of an `oid_array` but questions whether the optimization is worthwhile for cruft packs, where objects are often thrown in without careful ordering. The discussion now centers on whether the functional benefits of an `oid_array` outweigh its memory overhead, or whether a hybrid approach (e.g., preserving insertion order in an `oidset`) might reconcile both concerns. No hybrid approach has been proposed yet, but Newren’s test cases provide a clear benchmark for any future revision.

Four **substantive implementation details** remain contested following Jeff King’s **substantive reviews**, but two have now been resolved as minor cleanup items rather than blockers:
1. In patch 2/8, the explanatory comment about deferring tree/tag roots is placed in `read_stdin_packs()` (where the deferred walk happens) rather than in `add_object_entry_from_pack()` or `add_loose_object()` (where the deferral decision is made), making the code harder to follow. Taylor Blau and Jeff King acknowledge the awkwardness but agree to leave it unchanged, as there is no clean solution and the comment’s location is not a correctness concern.
2. In patch 2/8, the patch calls `prepare_revision_walk()` twice on the same `rev_info` struct—once for the initial commit walk and again for the deferred `extra_roots` walk. Jeff King questioned this as potentially unsafe, but Taylor Blau pointed out that the pattern already exists in `builtin/pack-objects.c::get_object_list()` and `reachable.c::mark_reachable_objects()`. Both agree the behavior is under-documented and could break if the revision-walk machinery changes, but neither treats it as a blocker. The issue is left unresolved but framed as a minor implementation detail.
3. In patch 5/8, the conditional logic `if (!(geometry.split_factor && !midx_must_contain_cruft))` controlling whether `--keep-pack` arguments are passed to `git pack-objects` during geometric repacks is found confusing due to its double negation. Peff suggests refactoring it to `if (!geometry.split_factor || midx_must_contain_cruft)` or introducing a well-named boolean variable for clarity. Taylor Blau’s **substantive follow-up** argues that the naming of the `midx_must_contain_cruft` configuration variable (which defaults to `true`) is the root cause of the confusion, proposing that it be renamed to `midx_may_exclude_cruft` (defaulting to `false`) for greater clarity. No resolution has been reached, leaving the conditional’s final form as an open implementation detail.
4. In patch 2/8, Jeff King’s **substantive review** questions the necessity of the two-walk approach (commits first, then `extra_roots`) and suggests a single traversal with all objects might suffice, while acknowledging the current approach is a net improvement. The discussion concludes with mutual agreement that rethinking the traversal machinery is best deferred to future work. The v2 series documents the two-walk approach as best-effort for path context, leaving the deeper traversal machinery changes as a loose end.

Jeff King’s **substantive review** of patch 4/8 in v1 raised the question of whether `.keep` packs should be traversed during the reachability walk rather than unconditionally including cruft packs; this remains a design consideration for future work, though the v2 series addresses the immediate performance concern for geometric repacks (patch 5/8).

The pre-existing edge case involving `--pack-kept-objects` and cruft packs that are themselves kept is acknowledged but deferred to a separate follow-up.

Subject: [PATCH 0/4] Fix MIDX reachability closure corner cases
Series version: v2 (eight patches, incorporating all feedback from v1)
Originating author: Taylor Blau
Thread type: patch series (bugfix)

Core problem or goal
The series fixes corner cases in Git’s multi-pack-index (MIDX) and cruft-pack machinery where MIDXs can end up containing objects that are not closed under reachability. This violates the MIDX’s invariant that it contains all objects reachable from its tips, causing failures in bitmap generation. The problem surfaces in four scenarios: `--stdin-packs=follow`, incremental repacks, `.keep` packs, and `--write-midx=incremental` (including `GIT_TEST_MULTI_PACK_INDEX_WRITE_INCREMENTAL`).

Current status
Under review; v1 was the initial submission, and v2 (now eight patches) addresses all substantive feedback from Jeff King, Derrick Stolee, and Junio C Hamano. The series is well-motivated, narrowly scoped, and ready for integration. Patch 1/8, a pure refactoring introducing `stdin_packs_context`, has received maintainer approval in spirit and is uncontroversial. Patch 4/8, a mechanical refactoring replacing a linear search through `--keep-pack` arguments with a sorted list and binary search, is also uncontroversial and prepares the codebase for patch 5/8. Patch 6/8, a refactoring in `repack-midx.c`, introduces a `preferred_pack` field in the `midx_compaction_step` struct to explicitly track the preferred pack, removing the dependency on string-list order and enabling future optimizations such as sorting the list for faster membership checks. Patch 7/8, a new addition in v2, defers allocation of the write step in `repack_make_midx_append_plan()` until the first pack is actually added, rather than pre-allocating it unconditionally when `opts->names->nr` is non-zero. This change is mechanical and does not alter behavior, but accommodates future logic where a non-empty candidate list no longer guarantees that a write step is needed (e.g., when packs are already covered by the MIDX chain). The patch moves the write-step allocation inside the loop that iterates over `opts->names` and introduces a `step` pointer initialized to `NULL` and set only when the first pack is processed. The `strbuf` is now declared outside the loop to avoid repeated initialization and release, and the loop structure is simplified by removing the conditional block that previously wrapped the write-step creation. Patch 8/8, which allows the append plan to skip packs already covered by the MIDX chain, builds directly on this refactoring and **fixes a previously unnoticed gap in incremental MIDX writes** (both geometric and append-only) where required packs—particularly cruft packs and kept packs—could be omitted from the MIDX chain, breaking bitmap generation. The patch modifies `repack-midx.c` to consult `midx_included_packs()` when building the write step for both append and geometric plans, ensuring that packs not already in the chain (e.g., cruft packs when `repack.midxMustContainCruft` is false, or kept packs needed for reachability) are included. The logic skips packs already present in retained base layers but includes those from a replaced tip. The documentation in `git-repack.adoc` is updated to clarify that incremental MIDX writes now include "newly written packs and any other required packs not already in the chain." The series as a whole is now complete and ready for integration, though the data structure choice for `extra_roots` in patch 2/8 remains contested.

Key technical details
- New struct: `stdin_packs_context` (refactoring of `--stdin-packs` handling in `pack-objects`).
- New data structure: `extra_roots` OID set in `stdin_packs_context` to collect trees and tags during pack traversal, replacing the `oid_array` from v1 for efficiency and semantic correctness. The choice of data structure (oidset vs. oid_array) is **contested** following Elijah Newren’s **substantive review**, which demonstrates that an `oid_array` preserves critical path and namehash ordering required for delta compression quality and attribute handling. Two test cases show that an `oidset` would cause blobs to be written in full instead of as deltas and misapply path-based attributes (e.g., `.gitattributes`) if subtrees are processed before their blobs. Taylor Blau’s latest **substantive follow-up** argues that the `oid_array` is not a perfect solution either, citing Jeff King’s observation that the namehash for a tree object depends on the traversal path, meaning even an `oid_array` can produce sub-optimal delta selection. Taylor highlights two advantages of the `oidset`: it avoids wasteful memory allocation when the same object is listed multiple times as an extra root, and the `extra_roots` set is expected to be small compared to the overall pack size. The discussion remains unresolved, with no hybrid approach proposed yet.
- New field: `preferred_pack` in `midx_compaction_step` (patch 6/8) to explicitly track the preferred pack, removing dependency on string-list order and enabling future optimizations.
- Refactoring: Patch 4/8 replaces a linear search through `--keep-pack` arguments with a sorted list and binary search, improving efficiency from O(n) to O(log n). The `keep_pack_list` is sorted using `fspathcmp()` and searched using `string_list_has_string()`. Patch 5/8 modifies the geometric repack traversal to include ancestors of kept objects without copying the kept objects themselves, addressing a performance pitfall during pushes. Patch 6/8 refactors `midx_compaction_step` to track the preferred pack explicitly, simplifying the code and improving maintainability. Patch 7/8 defers allocation of the write step in `repack_make_midx_append_plan()` until the first pack is actually added, rather than pre-allocating it unconditionally. Patch 8/8 modifies `repack-midx.c` to consult `midx_included_packs()` when building the write step, ensuring required packs are included in incremental MIDX writes.
- Subsystems: MIDX, cruft packs, `git repack`, `git pack-objects`.
- On-disk format: unchanged; the fixes ensure MIDXs remain reachability-closed.
- Test coverage: new tests in `t5331` (four tests) verify `--stdin-packs=follow` scenarios (tree-only input packs, excluded-open tags, delta attributes for subtree contents), `t7704` (five tests) confirm incremental repacks, geometric repacks with `.keep` packs, and cruft pack inclusion, and `t7705` (three tests) verify incremental MIDX writes, bitmap generation, and cruft pack inclusion in geometric incremental repacks. The existing "kept packs are excluded from repack" test is renamed and extended to confirm that kept packs are included in the MIDX and that bitmaps remain valid. Elijah Newren’s test cases for patch 2/8 demonstrate the functional regressions introduced by an `oidset` for `extra_roots`. No additional test coverage has been added for the `oidset` vs. `oid_array` trade-offs.
- Files modified: `builtin/pack-objects.c` (patches 1/8, 2/8, and 5/8), `repack.c` (patches 3/8, 4/8, and 5/8), `repack.h` (patch 4/8), `repack-midx.c` (patches 4/8, 5/8, 6/8, 7/8, and 8/8), and the man pages for `git-pack-objects` (patch 2/8) and `git-repack` (patch 8/8).
- Behavior change: Trees and tags in included/excluded-open packs (or loose objects with `--unpacked`) are now walked *after* the commit traversal to preserve path prefixes for delta attributes and namehashes. Incremental repacks now always include cruft packs in the MIDX to maintain reachability closure. Geometric repacks now traverse ancestors of kept objects without copying the kept objects themselves, avoiding performance pitfalls during pushes. Incremental MIDX writes now include all required packs, not just newly written ones. The `keep_pack_list` is now sorted and searched using binary search, improving efficiency. The `midx_compaction_step` struct now explicitly tracks the preferred pack, removing dependency on string-list order.
- Bug origin: Patch 3/8 fixes a regression introduced in commit 5ee86c273bf (June 2025), where incremental repacks could omit cruft packs from the MIDX when `repack.midxMustContainCruft` was set to "false". Patch 8/8 addresses a previously unnoticed gap in `write_midx_incremental()`, which did not respect `midx_must_contain_cruft`. Patch 5/8 fixes a performance pitfall with temporary `.keep` files during pushes by adjusting the geometric repack traversal.
- Jeff King’s feedback on patch 2/8: Confirms the patch fixes a "timebomb" scenario where MIDXs could omit objects reachable only from trees/tags, breaking bitmap generation. Raises two technical nuances: (1) whether blobs could be handled similarly to trees/tags (answer: no, blobs can’t reference other objects), and (2) whether the two-walk approach (commits first, then `extra_roots`) is necessary or if a single traversal with all objects could suffice. Peff is skeptical of the two-walk approach’s ability to fully resolve path context ambiguities (e.g., tags pointing to commits could reintroduce the same issue) and suggests prioritizing high-context objects in the traversal queue as a more complete solution. Despite these concerns, Peff endorses the patch as a strict improvement over the status quo. Taylor Blau acknowledges these limitations but defends the current design as a net win, deferring deeper traversal machinery changes to future work. The v2 series documents the two-walk approach as best-effort for path context.
- Jeff King’s feedback on patch 3/8: Confirms the patch’s core premise—that incremental repacks (but not geometric repacks) can omit cruft packs from the MIDX when `repack.midxMustContainCruft` is false—and endorses the fix as reasonable. Identifies an **unaddressed edge case** in `write_midx_incremental()`, which is now fixed in patch 8/8. The fix in patch 3/8 is uncontroversial and ready for integration.
- Jeff King’s feedback on patch 4/8: No substantive feedback yet; the patch is a mechanical refactoring with no behavior change and is uncontroversial.
- Jeff King’s feedback on patch 5/8: The patch directly addresses Peff’s v1 concern about performance pitfalls during pushes by adjusting the geometric repack traversal to include ancestors of kept objects without copying the kept objects themselves. This avoids the race condition with temporary `.keep` files while maintaining reachability closure.
- Jeff King’s feedback on patch 8/8: The patch directly addresses Peff’s v1 feedback identifying the edge case in `write_midx_incremental()`. The fix is narrowly scoped, well-tested, and uncontroversial.

Open questions and loose ends
The **data structure choice for `extra_roots` in patch 2/8** remains **contested** following Elijah Newren’s **substantive review** and Taylor Blau’s latest **substantive follow-up**. Newren’s test cases demonstrate that an `oid_array` preserves critical path and namehash ordering required for delta compression quality and attribute handling, while an `oidset` would introduce functional regressions (blobs written in full instead of as deltas, misapplied path-based attributes). Taylor Blau’s response argues that the `oid_array` is not a perfect solution either, citing Jeff King’s observation that the namehash for a tree object depends on the traversal path, meaning even an `oid_array` can produce sub-optimal delta selection. Taylor highlights two advantages of the `oidset`: it avoids wasteful memory allocation when the same object is listed multiple times as an extra root, and the `extra_roots` set is expected to be small compared to the overall pack size. The discussion hinges on whether the performance and semantic benefits of an `oidset` outweigh the functional regressions it introduces, or whether a hybrid approach (e.g., preserving insertion order in an `oidset`) might reconcile both concerns. No hybrid approach has been proposed yet, but Newren’s test cases provide a clear benchmark for any future revision. Jeff King’s **substantive review** of patch 2/8 questions the necessity of the two-walk approach (commits first, then `extra_roots`) and suggests a single traversal with all objects might suffice, while acknowledging the current approach is a net improvement. The discussion concludes with mutual agreement that rethinking the traversal machinery is best deferred to future work. The v2 series documents the two-walk approach as best-effort for path context, leaving the deeper traversal machinery changes as a loose end. Jeff King’s **substantive review** of patch 4/8 in v1 raised the question of whether `.keep` packs should be traversed during the reachability walk rather than unconditionally including cruft packs; this remains a design consideration for future work, though the v2 series addresses the immediate performance concern for geometric repacks (patch 5/8). The pre-existing edge case involving `--pack-kept-objects` and cruft packs that are themselves kept is acknowledged but deferred to a separate follow-up.

This is a bug report for the sparse-checkout subsystem. A user reports that `git checkout` in a sparse-checkout working tree clobbers untracked in-cone files instead of aborting with an error, as it would in a non-sparse checkout. The behavior regressed in Git v2.27.0 (commit 681c637b4a) and persists through the current master.

The report includes a minimal reproduction recipe: initialize a repository, set up a sparse-checkout that excludes the `docs/` directory, create a branch with a new file in the sparse cone, return to the original branch, create an untracked file with the same name, then attempt to switch back to the feature branch. In a non-sparse checkout this would fail with an error; in a sparse-checkout it succeeds, overwriting the untracked file and emitting a misleading warning.

The author argues that sparse checkouts should behave identically to non-sparse checkouts in this scenario, preserving untracked content and aborting the operation. The regression appears to stem from a change that turned what was previously a hard error into a warning when SKIP_WORKTREE bits could not be set. The report is clear, well-structured, and includes system information, making it easy for a maintainer to reproduce and investigate. This looks like a serious correctness issue that could lead to data loss.

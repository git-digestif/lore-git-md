This is a review exchange on Mark C. Chu-Carroll’s patch adding `--no-<reftype>` filtering options to `` `git repo structure` ``. The patch itself is a well-crafted feature addition that addresses a real diagnostic need, but Patrick Steinhardt’s review raises a fundamental design question.

Mark’s patch implements a set of `--no-tags`, `--no-branches`, `--no-remotes`, `--no-notes`, and `--no-stashes` flags that exclude the named reference types—and their transitive dependencies—from the repository structure report. The implementation is clean, with an enum-based flag system in `count_references`, conditional output formatting, and 276 lines of test coverage. The motivation is practical: users diagnosing performance issues often want to focus on a subset of the data, and the current all-or-nothing output can be overwhelming.

Patrick’s review, however, challenges the design. He argues that the patch’s approach—filtering the *output* of the “References” count—is too fine-grained and not as useful as filtering the *reachable objects* by revisions. His preferred design would allow users to pass arbitrary revisions (e.g., `` `git repo structure --branches` ``, `` `git repo structure master` ``, or `` `git repo structure --all --not --branches` ``) and have the command report only the objects reachable from those revisions. He suggests this could be achieved by adapting `parse_options()` to accept unknown options and passing them to `setup_revisions()`, which would handle the filtering logic.

The review is substantive: it questions the core design of the feature and proposes an alternative approach that would change the patch’s scope and implementation. Patrick’s feedback is constructive and grounded in Git’s established patterns (e.g., `git log`’s revision parsing), and his suggestion to use `setup_revisions()` is a technically sound way to achieve the broader goal. The discussion is now focused on whether the feature should filter output (Mark’s approach) or filter reachable objects (Patrick’s approach), and the outcome will likely determine whether the patch is accepted as-is or needs a significant redesign.

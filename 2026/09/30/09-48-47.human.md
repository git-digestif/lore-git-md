This is a two-patch series from Phillip Wood that improves `git checkout -m` to recreate conflict markers with the same labels ("base", "ours", "theirs") as the original merge, rather than using generic defaults. The series touches the merge machinery (ort backend), branch state handling, and the checkout builtin.

The motivation is straightforward: when you resolve a conflict, then later use `git checkout -m` to re-create it (e.g., to revisit the conflict or try a different resolution), the labels in the conflict markers no longer match what you originally saw. This can be confusing, especially in complex merges where the labels carry meaningful context. The series stores the original labels in `.git/MERGE_LABELS` during the merge and reads them back when `checkout -m` recreates the conflict.

The implementation looks clean and well-scoped. The first patch refactors `remove_branch_state` to accept flags instead of a boolean, which is a sensible cleanup. The second patch adds the core functionality: writing the labels during merge and reading them during checkout. The test coverage in `t7201-co.sh` is thorough, covering both the happy path and edge cases.

Phillip also floats an idea in the cover letter: should `checkout -m` also remember the original `merge.conflictStyle` (e.g., diff3) to make the re-created conflict look identical to the original? He’s unsure whether this would be convenient or confusing, and invites feedback. This feels like a natural extension of the current work, but it’s not implemented yet—just a discussion point.

The series is narrowly focused on a real usability pain point. It doesn’t introduce new configuration or user-facing options, just makes an existing workflow more intuitive. The changes are confined to merge/checkout internals, so risk of regressions seems low. This looks like a clear improvement that would be worth merging.

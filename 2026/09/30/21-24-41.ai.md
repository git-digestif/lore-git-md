This is the final patch in a four-patch bugfix series targeting the stash subsystem, specifically addressing a latent error-handling flaw in `git stash apply --index` that was identified after the original `dk/stash-apply-index-incore` series landed in `master`. The patch replaces the subprocess-based index merging (`git diff-tree` + `git apply`) with in-core `merge-ort.c` logic, eliminating a race condition in `save_autostash()` and fixing a NULL-dereference risk on catastrophic merge failures.

The core change is in `builtin/stash.c`, where `do_apply_stash()` now uses `merge_incore_nonrecursive()` to merge the index in-memory. The patch adds explicit tri-state logic to handle `result.clean` values: 1 (success), 0 (conflict), and -1 (hard error). This prevents crashes when `result.tree` is accessed after a failed merge (e.g., out-of-memory or disk errors). The new code also discards the merge result on conflicts, avoiding the need for filesystem round-trips and subprocess invocations. The patch includes a test in `t/t3903-stash.sh` to verify the correct tree order during merges and a regression test in `t/t7600-merge.sh` for `--autostash` with `stash.index`.

The diff removes 63 lines of subprocess-based code (including `diff_tree_binary()`, `apply_cached()`, and `reset_head()`) and replaces them with 30 lines of in-core logic. The changes are minimal and focused, aligning with the existing `merge-ort.c` patterns. The patch is well-motivated, addressing a real correctness issue while also improving performance by avoiding subprocess overhead. The test coverage ensures the fix works and prevents future regressions. This patch is ready for integration and should attract minimal controversy, as it directly addresses Junio’s post-merge concern with a clean, tested solution.

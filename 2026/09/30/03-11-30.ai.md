This is a **bugfix patch** targeting the reference-transaction hook regression, now in its sixth and final iteration (v6). The patch resolves a long-standing issue where high-level Git commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`) report all-zero OIDs for *both* old and new fields in the reference-transaction hook when deleting branches or tags. This regression, introduced in Git 2.31 by commit `8198907795`, broke external tools (Gerrit, GitLab, CI systems) that rely on the hook to monitor ref changes, as the old OID (previously correctly reported in Git 2.28–2.30) was lost.

The v6 approach moves the fix into the transaction hook layer itself, addressing architectural concerns raised by Patrick Steinhardt and Junio C Hamano in earlier iterations. Instead of modifying `refs_delete_refs()` or its callers (as in v5), the patch adds a new mechanism to record the current raw ref value separately for the hook, resolving it before the "preparing" phase and refreshing it after the backend locks the refs. This ensures the hook always receives the correct old OID without altering transaction semantics or constraining updates. The design preserves the bulk-deletion performance optimization introduced in Git 2.31 while restoring the pre-regression behavior for *all* ref-modifying commands, including symbolic refs and concurrent updates.

Key technical details:
- **Subsystems touched**: The patch modifies `refs.c` and `refs/refs-internal.h` to add `hook_old_oid` and `hook_old_target` fields to `struct ref_update`, along with logic in `resolve_transaction_hook_old_values()` to populate these fields before the "preparing" and "prepared" hook phases. The documentation (`githooks.adoc`) is updated to clarify the hook’s behavior, including the distinction between the unlocked "preparing" state and later phases.
- **Commands affected**: All ref-modifying commands (`git branch -d`, `git tag -d`, `git remote prune`, `git fetch --prune`, `git push`, `git symbolic-ref`, etc.) now receive correct old OIDs in the hook, matching the pre-2.31 behavior. `git update-ref -d` remains unaffected (already correct).
- **Backends**: The fix works for both files and reftable backends.
- **Performance trade-off**: The bulk-deletion optimization (5 seconds vs. 30 minutes for 10,000 tags) is preserved, but the on-demand resolution of old OIDs in the hook layer may introduce latency for large batches. This is acknowledged but unquantified; Patrick Steinhardt has explicitly endorsed the approach as acceptable.
- **Tests**: The patch updates `t/t1416-ref-transaction-hooks.sh` to verify hook payloads for batched branch/tag deletions, remote pruning, and concurrent updates, including a test that confirms deletions remain unconditional even when a concurrent update occurs during the "preparing" phase.

The patch is **well-motivated, narrowly scoped, and ready for review**. The commit message clearly documents the design rationale, including why the fix belongs in the transaction layer (to avoid overloading `refs_delete_refs()` and preserve its simplicity) and why callers cannot preserve old OIDs *before* deletion (due to the lack of a parameter in `refs_delete_refs()`).

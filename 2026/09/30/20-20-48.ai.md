This is a **bugfix** targeting the sparse-checkout subsystem. The email reports a regression introduced in Git v2.27.0 (commit `681c637b4a`) where `git checkout` in a sparse-checkout working tree incorrectly clobbers untracked in-cone files instead of aborting with an error. The issue occurs when switching branches and an untracked file in the sparse-checkout cone conflicts with a tracked file on the target branch.

The report provides a clear reproduction script, expected behavior (abort with error, preserving untracked content), and actual behavior (checkout completes, overwrites the untracked file, and exits with status 0). The regression breaks the invariant that sparse checkouts should behave identically to non-sparse checkouts in equivalent scenarios. The misleading warning message ("paths were already present and thus not updated") further compounds the problem by incorrectly describing the conflict.

The bug affects all versions from v2.27.0 through the current master (as of the report date). The commit message and reproduction steps are thorough, making the issue easy to verify. This is a serious correctness problem for users relying on sparse-checkout, as it can silently destroy untracked work. The report does not include a proposed fix, but the bisected culprit commit (`681c637b4a`) provides a clear starting point for debugging.

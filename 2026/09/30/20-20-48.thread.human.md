This thread reports a serious regression in Git's sparse-checkout subsystem, first introduced in v2.27.0 (June 2020) and still present in the current master branch. When switching branches in a sparse-checkout working tree, Git now silently overwrites untracked files that are within the sparse-checkout cone if they conflict with tracked files on the target branch, rather than aborting with an error as it would in a non-sparse checkout. The misleading warning message ("paths were already present and thus not updated") further obscures the problem.

Webstrand's report includes a clear reproduction script and thorough analysis, identifying the exact culprit commit (`681c637b4a`). The bug breaks a fundamental invariant: sparse checkouts should behave identically to full checkouts when operating on the same set of files. This is particularly dangerous because it can silently destroy untracked work without any indication that something went wrong. The issue affects all Git versions from v2.27.0 onward.

No proposed fix has been posted yet, but the bisected commit provides a clear starting point for debugging. The thread is currently just the initial report, so there's no discussion of potential solutions or review feedback yet. This is a high-priority issue for users relying on sparse-checkout functionality.

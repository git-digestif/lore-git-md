This is a review reply in the ongoing RFC thread about converting Git’s `BreakingChanges` document into a proper manpage (`gitbreaking-changes(7)`). The thread is evaluating whether to make upcoming breaking changes more discoverable to users by moving the existing plain-text document into the manpage system.

Patrick Steinhardt’s reply is substantive but measured. He agrees with the core goal—making the document more accessible to all Git users—but raises a forward-looking question: what happens to the document after Git 3.0 ships? He suggests retaining it (now as a manpage) for users who upgrade later, but notes that if it continues as a living document, it should eventually gain a new section for Git 4.0. His tone is pragmatic rather than critical; he even jokes that a major release once per decade might be sufficient.

On the patch itself, Patrick offers a procedural suggestion: he would have preferred the conversion to happen in-place (editing `BreakingChanges.adoc` directly) before renaming it to `gitbreaking-changes.adoc`. This would make the formatting changes easier to review. The comment is constructive and does not challenge the patch’s technical correctness—just the reviewability of the diff.

The thread remains in RFC mode; no objections have been raised yet, and the discussion is still focused on the overall approach rather than implementation details. If the project accepts the goal, the patch looks straightforward and uncontroversial.

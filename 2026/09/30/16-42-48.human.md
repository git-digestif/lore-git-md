This is the second patch in Phillip Wood’s two-patch series that teaches `git checkout -m` to remember and reuse the original conflict labels (e.g., branch names) instead of generic “base”, “ours”, and “theirs”. The patch implements the core plumbing: it stores the labels in `.git/MERGE_LABELS` during a conflicted merge and reads them back when `git checkout -m` recreates the conflicts. Junio’s review focuses on documentation and cross-platform line-ending safety.

Junio asks where `MERGE_HEAD` and `CHERRY_PICK_HEAD` are documented, suggesting that `.git/MERGE_LABELS` should be mentioned alongside them. He also raises a potential issue with Windows line endings: the code writes the labels file via `fprintf` (which may add CRLF on Windows) but reads it back with `strbuf_read_file` (which does not normalize line endings), so the labels could end up with trailing carriage returns. The review is substantive but does not identify any functional bugs; it is primarily about documentation and portability hygiene.

Phillip is a well-regarded contributor with deep expertise in the merge machinery, so the implementation is likely robust. The patch is narrowly scoped to label preservation and does not address the open question from the cover letter about whether to also preserve the conflict style (e.g., `diff3`). The change is user-facing but not disruptive—it only affects the appearance of conflict markers, not their semantics. The new `.git/MERGE_LABELS` file is the only on-disk change, and the patch includes all necessary cleanup logic.

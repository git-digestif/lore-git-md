This is the second patch in Thomas Bachem’s three-part v5 series fixing a long-standing race condition in Git’s `rerere` subsystem. The patch introduces a `--auto` mode for `git rerere gc` that silently skips the operation if the `MERGE_RR.lock` is held, aligning its behavior with other auto-maintenance tasks like `git pack-refs --auto`. The change is narrowly scoped: only `git rerere gc --auto` (triggered by `git maintenance run --auto` or `git gc --auto`) skips a held lock, while manual invocations of `git rerere gc` continue to wait and fail as before.

Patrick Steinhardt’s review raises two points. First, he suggests the `--auto` flag might be misnamed, since it doesn’t enable any heuristics (unlike other `--auto` commands) but merely skips the operation if the lock is held. He proposes renaming it to `--skip-locked` and possibly making it a hidden option, since it’s primarily intended for `git maintenance`. Second, he notes the awkwardness of documenting which commands call `git rerere gc --auto` in the man page, recommending instead that the documentation focus on *why* the flag is useful. The patch itself is otherwise uncontroversial and appears ready for integration, but these naming and documentation tweaks could improve clarity without altering the core functionality.

The patch touches `builtin/rerere.c` and `Documentation/git-rerere.adoc`, with test coverage in `t4200-rerere.sh` and `t7900-maintenance.sh` verifying the distinction between auto and manual behavior. The implementation is clean, with the `RERERE_NOWAIT` flag orthogonal to `RERERE_READONLY`, and the lock acquisition logic unchanged except for the timeout adjustment. No substantive objections remain, and the series as a whole is nearing final approval.

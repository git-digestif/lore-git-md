This thread began with Harald Nordgren proposing a small but logical extension: adding the `--label-ours`, `--label-theirs`, and `--label-base` options to `git stash pop`, mirroring their existing support in `git stash apply`. These options let users customize the conflict markers that appear when a stash merge results in conflicts, replacing the default "ours", "theirs", and "base" labels with user-specified text.

The implementation itself was straightforward—adding the options to `builtin/stash.c`, updating the man page, and adding tests—but the discussion quickly shifted from technical details to design philosophy. Both Junio C Hamano and Phillip Wood questioned whether these options belong in user-facing commands at all. While they acknowledged the options are technically necessary for internal machinery (the sequencer relies on them for `git checkout -m` and autostash), they saw their presence in `stash apply` as an implementation side effect rather than a deliberate feature. Junio described the proposed extension to `pop` as "because we can do it" rather than "because we need to have it," and both maintainers agreed that users are unlikely to manually type long label arguments in practice. Phillip Wood suggested that scripts needing custom labels should use `stash create` and `stash apply` instead.

Harald has now withdrawn the patch, marking the end of the specific proposal but leaving the broader question unresolved: should these options remain exposed in `stash apply` at all? Harald floated the idea of keeping them functional but hiding them from the documentation, though he acknowledged this might not be ideal. The technical constraint remains—removing the options would break `git checkout -m` and autostash—but the maintainers' skepticism about their user-facing value has effectively shelved the feature for now. The thread is now a design discussion about whether these options belong in the user interface, not just whether they should be extended to `pop`.

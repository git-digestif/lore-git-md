This thread began with Harald Nordgren proposing to extend `git stash pop` with the same `--label-ours`, `--label-theirs`, and `--label-base` options already available in `git stash apply`, allowing users to customize conflict markers when popping a stash. The patch was withdrawn after Junio C Hamano and Phillip Wood questioned whether these options belong in *any* user-facing `stash` subcommand, given their origin as internal machinery for `git checkout -m` and the technical constraint that the sequencer relies on them for autostash functionality.

The discussion has since shifted to a broader design question: whether the `--label-*` options should exist in the user interface at all. Junio and Phillip view their presence in `stash apply` as a side effect of implementation details rather than a deliberate feature, arguing that users are unlikely to manually type long label arguments and that scripts should prefer `stash create` and `stash apply` for such use cases. The technical constraint—requiring the options for `git checkout -m` and autostash—prevents their removal, but their user-facing value remains contested.

In the latest email, Junio proposes a longer-term solution: rewriting the sequencer to invoke `git stash apply` functionality via a direct function call instead of spawning a subprocess. This would eliminate the technical constraint, allowing the options to be removed from the user interface entirely. As a short-term compromise, he suggests labeling the options as "for internal use only" with a warning that they may disappear in the future. No resolution has been reached, but the thread now points toward a potential architectural cleanup of the sequencer’s interaction with the stash machinery.

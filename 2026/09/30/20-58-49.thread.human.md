This thread is about a patch from Harald Nordgren that adds `--label-ours`, `--label-theirs`, and `--label-base` options to `git stash pop`, mirroring functionality already available in `git stash apply`. The goal is to let users customize conflict markers when popping a stash, but the patch has sparked a design debate.

Junio C Hamano, the maintainer, has questioned whether these options belong in user-facing commands at all, tracing their origin to internal machinery for `git checkout` and suggesting they may have been added to `stash apply` only for debugging convenience. He’s asked the author to justify the real-world need for customizing conflict markers when popping a stash, rather than relying on technical symmetry.

Phillip Wood has now weighed in, agreeing with Junio that while the underlying machinery for custom labels is justified, exposing these options in `git stash pop` is unnecessary. He argues that `stash apply` might have a valid use case for scripts or automated tools (similar to `git checkout -m`), but `stash pop` is unlikely to benefit in practice, as users are unlikely to manually type out long label arguments. He also notes that scripts should prefer `stash create` and `stash apply` over `stash push` and `stash pop`, which already covers the use case for custom labels. The discussion remains focused on the design rationale, with no technical objections to the implementation itself.

The patch touches `builtin/stash.c` and updates the man page, adding the three options and passing them through to the apply logic. Two new tests verify the labels appear in conflict markers. For now, the patch is under review, with the key open question being whether the feature is justified or if the options should be removed from `stash apply` entirely.

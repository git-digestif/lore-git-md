This is the second patch in Phillip Wood’s two-patch series improving `git checkout -m`. It teaches Git’s ort merge backend to store the original conflict labels (the branch names shown in conflict markers) in `.git/MERGE_LABELS` whenever a merge results in conflicts, and then reuse those labels when `git checkout -m <path>` is later invoked to recreate the conflict.

The patch is a clean, well-scoped change that touches the merge machinery (`merge-ort.c`, `merge.c`, `merge.h`), branch state management (`branch.c`, `branch.h`), and the checkout built-in (`builtin/checkout.c`). It also adds a new test in `t/t7201-co.sh` to verify that the labels are preserved. The implementation is straightforward: the ort backend writes the labels to `.git/MERGE_LABELS` when updating the worktree, and `git checkout -m` reads them back when recreating conflicts. A new flag (`REMOVE_BRANCH_STATE_PRESERVE_CONFLICT_LABELS`) ensures the labels file is not deleted prematurely when switching branches.

Phillip is a well-known contributor with deep expertise in the sequencer and merge machinery, so the implementation is likely to be solid. The change is user-facing but not disruptive—it only affects the appearance of conflict markers, not their semantics. The open question from the cover letter (whether `git checkout -m` should also remember the original conflict style) is not addressed here, but even if that is deferred, the label preservation itself is a clear improvement. The patch is ready for review and looks like a sensible addition to Git’s merge machinery.

Thread identity
Subject: [PATCH 0/5] git backfill --dry-run
Series version: v1 (initial submission)
Originating author: Pablo Sabater
Thread type: patch series (feature addition)

Core problem or goal
Add a `--dry-run` option to `git backfill` that estimates the number and total uncompressed size of blobs that would be fetched, giving users an advance preview of the download cost before committing to the actual backfill operation.

Current status
Under review; no prior versions. Five-patch series: three preparatory refactorings (patches 1–3) converting `fetch_object_info()` from a die-on-failure API to a status-code-returning one, followed by the core `--dry-run` implementation (patches 4–5). Patch 4/5 (newly summarized) implements the dry-run counting logic in `builtin/backfill.c`, adding the `--dry-run` flag, a `dry_run_batch()` helper, and output that reports the number of blobs that would be fetched. Patch 5/5 will extend the output to include blob sizes when the server supports the `object-info` capability.

Key technical details
- Files touched: `transport-internal.h` (comment), `transport.c`, `fetch-object-info.{c,h}`, `builtin/backfill.c`, `Documentation/git-backfill.txt`, `t/t5620-backfill.sh`
- New CLI option: `git backfill --dry-run`
- New enum: `fetch_object_info_status` (values: `FETCH_OBJECT_INFO_OK`, `FETCH_OBJECT_INFO_ERR`, `FETCH_OBJECT_INFO_NOT_ENABLED`)
- Changed function signatures: `fetch_object_info()` and `transport_fetch_object_info()` now return a status code instead of dying
- New helper: `dry_run_batch()` accumulates blob counts without fetching
- Output format (patch 4/5): “After backfill, N blobs would be fetched.” (pluralized)
- Output format (patch 5/5, forthcoming): “N blobs would be fetched (M KiB)” when `object-info` is supported
- Test coverage: dry-run behavior (count accuracy, no fetches occur)
- Graceful fallback: servers that lack the `object-info` capability report blob count but omit size

Open questions and loose ends
- Usefulness of the feature: the author explicitly asks whether the preview capability is valuable to regular `git backfill` users
- Output format: whether the current wording (“After backfill, N blobs would be fetched.”) and units (KiB) are clear and actionable
- Test coverage completeness: whether additional edge cases (e.g., zero blobs, very large repos) need explicit testing

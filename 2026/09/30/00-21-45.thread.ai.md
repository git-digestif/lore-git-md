Thread identity
Subject: [PATCH 0/5] git backfill --dry-run
Series version: v1 (initial submission, next revision v2)
Originating author: Pablo Sabater
Thread type: patch series (feature addition)

Core problem or goal
Add a `--dry-run` option to `git backfill` that estimates the number and total uncompressed size of blobs that would be fetched, giving users an advance preview of the download cost before committing to the actual backfill operation.

Current status
Under review; no prior versions. The upcoming v2 will consist of four patches after the author accepted Karthik Nayak’s suggestion to squash the enum-addition patch (v1 2/5) into the API-conversion patch (v1 3/5). All three of Karthik’s stylistic suggestions on v1 4/5—changing the `dry_run` field from `int` to `bool`, renaming `dry_run_batch()` to `count_batch()` (with a clarifying comment planned), and replacing the `goto`-based control flow with a direct `if (dry_run) count() else download()` pattern—have been accepted and will be incorporated. Junio C Hamano additionally suggested renaming the `FETCH_OBJECT_INFO_NOT_ENABLED` enum value to `FETCH_OBJECT_INFO_NOT_AVAILABLE` to avoid implying the server could enable the capability but chose not to; this suggestion has been accepted in principle. A new correctness concern has been raised by Junio on v1 5/5: the `ctx->object_info_enabled` flag is overloaded to mean both "the server supports the `object-info` capability" and "the size data we received is valid," which is unsafe because `transport_fetch_object_info()` can return errors other than `FETCH_OBJECT_INFO_NOT_AVAILABLE` (e.g., network failures, malformed responses), leaving `results->sizes` potentially invalid. Junio suggests introducing a dedicated `ctx->sizes_valid` flag to decouple capability checking from data validity. This issue must be resolved before the series can graduate to substantive technical approval. No other technical objections have been raised; the feature remains feature-complete and ready for deeper review once the control-flow ambiguity is addressed.

Key technical details
- Files touched: `transport-internal.h` (comment), `transport.c`, `fetch-object-info.{c,h}`, `builtin/backfill.c`, `Documentation/git-backfill.txt`, `t/t5620-backfill.sh`
- New CLI option: `git backfill --dry-run`
- New enum: `fetch_object_info_status` (values: `FETCH_OBJECT_INFO_OK`, `FETCH_OBJECT_INFO_ERR`, `FETCH_OBJECT_INFO_NOT_AVAILABLE` (formerly `FETCH_OBJECT_INFO_NOT_ENABLED`)) introduced in the same patch that converts `fetch_object_info()` to return a status code
- Changed function signatures: `fetch_object_info()` and `transport_fetch_object_info()` now return a status code instead of dying
- New helpers: `count_batch()` (formerly `dry_run_batch()`) accumulates blob counts; size accumulation logic in `builtin/backfill.c` when `object-info` is supported
- Output format: “After backfill, N blobs would be fetched (M KiB).” when size information is available, “After backfill, N blobs would be fetched.” otherwise
- Units: uncompressed, undeltified size reported in KiB (documented as an upper bound)
- Test coverage: dry-run behavior (count accuracy, no fetches occur), object-info and non-object-info scenarios
- Graceful fallback: servers that lack the `object-info` capability report blob count but omit size
- Control-flow ambiguity: `ctx->object_info_enabled` is currently overloaded to track both capability support and size data validity; Junio suggests introducing a dedicated `ctx->sizes_valid` flag to ensure size reporting is only done when the data is known to be complete and trustworthy

Open questions and loose ends
- Usefulness of the feature: the author explicitly asks whether the preview capability is valuable to regular `git backfill` users
- Output format: whether the current wording (“After backfill, N blobs would be fetched.”) and units (KiB) are clear and actionable
- Test coverage completeness: whether additional edge cases (e.g., zero blobs, very large repos, partial or malformed `object-info` responses) need explicit testing
- Future size-accumulation logic: the author plans to add a comment clarifying that `count_batch()` will eventually also accumulate size
- Control-flow correctness: the newly identified ambiguity in how size data validity is tracked must be resolved before the series can be considered technically sound

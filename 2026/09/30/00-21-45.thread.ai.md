Thread identity
Subject: [PATCH 0/5] git backfill --dry-run
Series version: v1 (initial submission, next revision v2 pending conceptual resolution)
Originating author: Pablo Sabater
Thread type: patch series (feature addition)

Core problem or goal
Add a `--dry-run` option to `git backfill` that estimates the number and total uncompressed size of blobs that would be fetched, giving users an advance preview of the download cost before committing to the actual backfill operation.

Current status
Under review; no prior versions. The upcoming v2 will consist of four patches after the author accepted Karthik Nayak’s suggestion to squash the enum-addition patch (v1 2/5) into the API-conversion patch (v1 3/5). All three of Karthik’s stylistic suggestions on v1 4/5—changing the `dry_run` field from `int` to `bool`, renaming `dry_run_batch()` to `count_batch()` (with a clarifying comment planned), and replacing the `goto`-based control flow with a direct `if (dry_run) count() else download()` pattern—have been accepted and will be incorporated. Junio C Hamano’s suggestions to rename `FETCH_OBJECT_INFO_NOT_ENABLED` to `FETCH_OBJECT_INFO_UNAVAILABLE` for semantic clarity and to resolve the control-flow correctness issue in v1 5/5 have been accepted and will be applied to both the enum value and the corresponding `die()` message in `git cat-file`. The control-flow correctness issue was resolved by the author’s proposal to rename `ctx->object_info_enabled` to `ctx->sizes_valid` and set it only when `transport_fetch_object_info()` returns `FETCH_OBJECT_INFO_OK` *and* `results->sizes` is non-NULL, ensuring size reporting is only done when the data is known to be complete and trustworthy. The feature is now effectively stalled: Derrick Stolee objects that the preview capability does not address a concrete user need and that the uncompressed size estimate may not meaningfully inform a user’s decision, and Junio C Hamano has explicitly endorsed Stolee’s position. The author has conceded that the feature may not be worth merging unless someone steps forward with a concrete use case.

Open questions and loose ends
- Conceptual value: whether the preview capability addresses a real user need; Stolee argues that Git features should be driven by concrete "itches" and that the uncompressed size estimate may not meaningfully inform a user’s decision; Junio has now explicitly endorsed this view, making the feature unlikely to advance without evidence of user demand
- Output format: whether the current wording (“After backfill, N blobs would be fetched.”) and units (KiB) are clear and actionable; Stolee suggests a more explicit argument like `--info=(count|size)` to clarify the trade-off between information depth and network effort
- Test coverage completeness: whether additional edge cases (e.g., zero blobs, very large repos, partial or malformed `object-info` responses) need explicit testing
- Future size-accumulation logic: the author plans to add a comment clarifying that `count_batch()` will eventually also accumulate size
- Protocol-level improvements: two ideas floated but not pursued—server-side deltified size computation based on client’s existing objects, or returning the server’s local compressed size—both would require protocol changes and still yield estimates

Key technical details
- Files touched: `transport-internal.h` (comment), `transport.c`, `fetch-object-info.{c,h}`, `builtin/backfill.c`, `builtin/cat-file.c` (updated `die()` message), `Documentation/git-backfill.txt`, `t/t5620-backfill.sh`
- New CLI option: `git backfill --dry-run`
- New enum: `fetch_object_info_status` (values: `FETCH_OBJECT_INFO_OK`, `FETCH_OBJECT_INFO_ERR`, `FETCH_OBJECT_INFO_UNAVAILABLE` (formerly `FETCH_OBJECT_INFO_NOT_ENABLED`)) introduced in the same patch that converts `fetch_object_info()` to return a status code
- Changed function signatures: `fetch_object_info()` and `transport_fetch_object_info()` now return a status code instead of dying
- New helpers: `count_batch()` (formerly `dry_run_batch()`) accumulates blob counts; size accumulation logic in `builtin/backfill.c` when `object-info` is supported
- Output format: “After backfill, N blobs would be fetched (M KiB).” when size information is available, “After backfill, N blobs would be fetched.” otherwise
- Units: uncompressed, undeltified size reported in KiB (documented as an upper bound)
- Test coverage: dry-run behavior (count accuracy, no fetches occur), object-info and non-object-info scenarios
- Graceful fallback: servers that lack the `object-info` capability report blob count but omit size
- Control-flow correctness: the previously overloaded `ctx->object_info_enabled` flag has been replaced with a dedicated `ctx->sizes_valid` flag, set only when `transport_fetch_object_info()` returns `FETCH_OBJECT_INFO_OK` and `results->sizes` is non-NULL, ensuring size reporting is only done when the data is known to be complete and trustworthy
- Protocol improvement ideas (not implemented): server-side deltified size computation based on client’s existing objects, or returning the server’s local compressed size; both would require protocol changes and still yield estimates

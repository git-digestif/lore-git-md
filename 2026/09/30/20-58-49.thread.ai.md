Thread identity
Subject: [PATCH] stash: extend `pop` with custom conflict-label options
Series version: single patch, no prior iterations
Originating author: Harald Nordgren
Thread type: patch series

Core problem or goal
Extend `git stash pop` to accept the same `--label-ours`, `--label-theirs`, and `--label-base` options that `git stash apply` already supports, so users can customize conflict markers when popping a stash.

Current status
Under review; maintainer and reviewer have raised fundamental design questions about whether these options should exist in user-facing commands at all, with no technical objections to the implementation itself.

Key technical details
- Files touched: `builtin/stash.c` (adds the three options to `pop_stash()` and passes them through to `do_apply_stash()`), `Documentation/git-stash.txt` (updates the man page).
- New CLI options: `--label-ours=<text>`, `--label-theirs=<text>`, `--label-base=<text>` for `git stash pop`.
- Behavior: when a conflict occurs during `pop`, the supplied labels replace the default “ours”/“theirs”/“base” markers in the conflict hunk headers.
- Test coverage: two new tests in `t/t3903-stash.sh` verify that the labels appear in conflict markers and that empty labels are handled correctly.

Open questions and loose ends
- **Design justification**: Junio C Hamano and Phillip Wood have both questioned the fundamental motivation for exposing these options in user-facing commands. The options originated from internal machinery for `git checkout -m` and may have been added to `stash apply` only for debugging convenience. Junio suggests the options might be better removed from `stash apply` rather than extended to `pop`. Phillip Wood adds that while `stash apply` might have a valid use case for scripts or automated tools (like `git checkout -m`), `stash pop` is unlikely to benefit in practice, as users are unlikely to type out long label arguments manually. He also notes that scripts should prefer `stash create` and `stash apply` over `stash push` and `stash pop`, which already covers the use case for custom labels. The patch's rationale remains contested, with no clear consensus on whether the feature belongs in the user interface.

Participant positions
- **Junio C Hamano**: skeptical of the feature's place in the user interface; suggests the options might be better removed from `stash apply` rather than extended to `pop`. Concern is purely about user-facing design, not implementation.
- **Phillip Wood**: agrees with Junio that the underlying machinery for custom labels is justified (e.g., for `git checkout -m`), but is skeptical about exposing these options in `stash pop`. Argues that `stash pop` is unlikely to benefit from them in practice, as users are unlikely to manually type long label arguments, and that scripts should prefer `stash create` and `stash apply` for such use cases.

Thread identity
Subject: [PATCH] stash: extend `pop` with custom conflict-label options
Series version: single patch, withdrawn
Originating author: Harald Nordgren
Thread type: patch series (abandoned), now design discussion

Core problem or goal
Extend `git stash pop` to accept the same `--label-ours`, `--label-theirs`, and `--label-base` options that `git stash apply` already supports, so users can customize conflict markers when popping a stash. The broader question raised by maintainer review is whether these options should exist in *any* user-facing `stash` subcommand, given their origin as internal machinery for `git checkout -m` and the technical constraint that the sequencer relies on them for autostash functionality.

Current status
Abandoned. The patch has been withdrawn by the author after Junio C Hamano and Phillip Wood questioned the fundamental motivation for exposing these options in user-facing commands. The discussion has shifted to a longer-term architectural proposal: rewriting the sequencer to invoke `git stash apply` functionality via a direct function call rather than spawning a subprocess. This would eliminate the technical constraint that currently requires the `--label-*` options to remain exposed in `stash apply`, allowing them to be removed from the user interface entirely. Junio suggests labeling the options as "for internal use only" (with a warning that they may disappear) as a short-term compromise while the refactoring is pursued.

Key technical details
- Files touched (proposed in original patch): `builtin/stash.c` (adds the three options to `pop_stash()` and passes them through to `do_apply_stash()`), `Documentation/git-stash.txt` (updates the man page).
- New CLI options (proposed in original patch): `--label-ours=<text>`, `--label-theirs=<text>`, `--label-base=<text>` for `git stash pop`.
- Behavior: when a conflict occurs during `pop`, the supplied labels replace the default “ours”/“theirs”/“base” markers in the conflict hunk headers.
- Test coverage (proposed in original patch): two new tests in `t/t3903-stash.sh` verify that the labels appear in conflict markers and that empty labels are handled correctly.
- Implementation constraint: the sequencer (handling `git rebase` and `git cherry-pick`) spawns `git stash apply` as a subprocess, requiring the `--label-*` options to remain exposed in `stash apply` to support `git checkout -m` with meaningful conflict labels. This prevents removing the options from `stash apply` without breaking autostash functionality.
- Architectural proposal: rewrite the sequencer to call `do_apply_stash()` directly (or a new internal API) instead of spawning `git stash apply` as a subprocess. This would remove the need for the `--label-*` options to be exposed in `stash apply`, allowing them to be removed from the user interface entirely.

Open questions and loose ends
- **Design justification**: The core question remains whether the `--label-*` options should be exposed in *any* user-facing `stash` subcommand. Junio C Hamano and Phillip Wood view their presence in `stash apply` as a side effect of internal implementation (required by the sequencer) rather than a deliberate user-facing feature. Both maintainers argue that users are unlikely to manually type long label arguments for `pop` or `apply` in practice, and that scripts should prefer `stash create` and `stash apply` for such use cases. The technical constraint (requiring the options for `git checkout -m` and autostash) currently prevents their removal, but the proposed architectural refactoring would eliminate this constraint.
- **Short-term compromise**: Junio suggests labeling the options as "for internal use only" (with a warning that they may disappear) as a reasonable short-term compromise while the sequencer refactoring is pursued. This would acknowledge their current necessity while discouraging user reliance on them.
- **Future of the options**: No resolution has been reached on whether the options should remain documented in `stash apply`, be hidden (undocumented but functional), or be removed entirely. The thread now points toward a potential future cleanup of the sequencer’s interaction with the stash machinery, which would resolve the design question by removing the technical constraint.

Thread identity
Subject: [PATCH] stash: extend `pop` with custom conflict-label options
Series version: single patch, no prior iterations
Originating author: Harald Nordgren
Thread type: patch series

Core problem or goal
Extend `git stash pop` to accept the same `--label-ours`, `--label-theirs`, and `--label-base` options that `git stash apply` already supports, so users can customize conflict markers when popping a stash.

Current status
Under review; maintainer and reviewer remain unconvinced of the feature's necessity in user-facing commands, despite no technical objections to the implementation itself. The discussion has shifted to the broader question of whether these options should exist in `stash apply` at all, given their origin as internal machinery for `git checkout -m` and the technical constraint that the sequencer relies on them for autostash functionality.

Key technical details
- Files touched: `builtin/stash.c` (adds the three options to `pop_stash()` and passes them through to `do_apply_stash()`), `Documentation/git-stash.txt` (updates the man page).
- New CLI options: `--label-ours=<text>`, `--label-theirs=<text>`, `--label-base=<text>` for `git stash pop`.
- Behavior: when a conflict occurs during `pop`, the supplied labels replace the default “ours”/“theirs”/“base” markers in the conflict hunk headers.
- Test coverage: two new tests in `t/t3903-stash.sh` verify that the labels appear in conflict markers and that empty labels are handled correctly.
- Implementation constraint: the sequencer (handling `git rebase` and `git cherry-pick`) spawns `git stash apply` as a subprocess, requiring the `--label-*` options to remain exposed in `stash apply` to support `git checkout -m` with meaningful conflict labels. This prevents removing the options from `stash apply` without breaking autostash functionality.

Open questions and loose ends
- **Design justification**: Junio C Hamano and Phillip Wood continue to question the fundamental motivation for exposing these options in user-facing commands. While the options are technically necessary for the sequencer's autostash functionality, both maintainers view their presence in `stash apply` as a side effect of internal implementation rather than a deliberate user-facing feature. Junio describes the proposed extension to `stash pop` as "because we can do it" rather than "because we need to have it," and both maintainers agree that users are unlikely to manually type long label arguments for `pop` in practice. Phillip Wood reiterates that scripts should prefer `stash create` and `stash apply` for such use cases, which already cover the need for custom labels. The patch's rationale remains contested, with no clear consensus on whether the feature belongs in the user interface or whether the options should be removed from `stash apply` entirely (despite the technical constraint preventing this).

Participant positions
- **Junio C Hamano**: skeptical of the feature's place in the user interface; views the proposed extension to `stash pop` as unnecessary and unlikely to be used in practice. While he acknowledges the technical constraint requiring the options to remain in `stash apply` (due to the sequencer's reliance on them), he does not see this as justification for extending them to `pop`. Concern is purely about user-facing design, not implementation.
- **Phillip Wood**: agrees with Junio that the underlying machinery for custom labels is justified (e.g., for `git checkout -m`), but remains skeptical about exposing these options in `stash pop`. Argues that `stash pop` is unlikely to benefit from them in practice, as users are unlikely to manually type long label arguments, and that scripts should prefer `stash create` and `stash apply` for such use cases.

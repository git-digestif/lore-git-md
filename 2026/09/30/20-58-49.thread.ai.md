Thread identity
Subject: [PATCH] stash: extend `pop` with custom conflict-label options
Series version: single patch, no prior iterations
Originating author: Harald Nordgren
Thread type: patch series

Core problem or goal
Extend `git stash pop` to accept the same `--label-ours`, `--label-theirs`, and `--label-base` options that `git stash apply` already supports, so users can customize conflict markers when popping a stash.

Current status
Under review; maintainer has raised a fundamental design question about whether these options should exist in user-facing commands at all.

Key technical details
- Files touched: `builtin/stash.c` (adds the three options to `pop_stash()` and passes them through to `do_apply_stash()`), `Documentation/git-stash.txt` (updates the man page).
- New CLI options: `--label-ours=<text>`, `--label-theirs=<text>`, `--label-base=<text>` for `git stash pop`.
- Behavior: when a conflict occurs during `pop`, the supplied labels replace the default “ours”/“theirs”/“base” markers in the conflict hunk headers.
- Test coverage: two new tests in `t/t3903-stash.sh` verify that the labels appear in conflict markers and that empty labels are handled correctly.

Open questions and loose ends
- **Design justification**: Junio C Hamano has questioned the fundamental motivation for exposing these options in user-facing commands, tracing their origin to internal machinery for `git checkout` and suggesting they may have been added to `stash apply` only for debugging convenience. He asks the author to articulate a real-world use case for customizing conflict markers when popping a stash, rather than relying on technical symmetry. The patch's rationale is now contested.

Participant positions
- **Junio C Hamano**: skeptical of the feature's place in the user interface; suggests the options might be better removed from `stash apply` rather than extended to `pop`. No technical flaws in the implementation are raised; the concern is purely about user-facing design.

Related work

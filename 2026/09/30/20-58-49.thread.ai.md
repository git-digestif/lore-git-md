Thread identity
Subject: [PATCH] stash: extend `pop` with custom conflict-label options
Series version: single patch, withdrawn
Originating author: Harald Nordgren
Thread type: patch series (abandoned)

Core problem or goal
Extend `git stash pop` to accept the same `--label-ours`, `--label-theirs`, and `--label-base` options that `git stash apply` already supports, so users can customize conflict markers when popping a stash. The broader question raised by maintainer review is whether these options should exist in *any* user-facing `stash` subcommand, given their origin as internal machinery for `git checkout -m` and the technical constraint that the sequencer relies on them for autostash functionality.

Current status
Abandoned. The patch has been withdrawn by the author after Junio C Hamano and Phillip Wood questioned the fundamental motivation for exposing these options in user-facing commands. The discussion has shifted entirely to the broader design question of whether the `--label-*` options belong in the user interface at all, despite the technical constraint that prevents their removal from `stash apply` (required by the sequencer for `git checkout -m` and autostash).

Key technical details
- Files touched (proposed): `builtin/stash.c` (adds the three options to `pop_stash()` and passes them through to `do_apply_stash()`), `Documentation/git-stash.txt` (updates the man page).
- New CLI options (proposed): `--label-ours=<text>`, `--label-theirs=<text>`, `--label-base=<text>` for `git stash pop`.
- Behavior: when a conflict occurs during `pop`, the supplied labels replace the default “ours”/“theirs”/“base” markers in the conflict hunk headers.
- Test coverage (proposed): two new tests in `t/t3903-stash.sh` verify that the labels appear in conflict markers and that empty labels are handled correctly.
- Implementation constraint: the sequencer (handling `git rebase` and `git cherry-pick`) spawns `git stash apply` as a subprocess, requiring the `--label-*` options to remain exposed in `stash apply` to support `git checkout -m` with meaningful conflict labels. This prevents removing the options from `stash apply` without breaking autostash functionality.

Open questions and loose ends
- **Design justification**: The core question is whether the `--label-*` options should be exposed in *any* user-facing `stash` subcommand. Junio C Hamano and Phillip Wood view their presence in `stash apply` as a side effect of internal implementation (required by the sequencer) rather than a deliberate user-facing feature. Both maintainers argue that users are unlikely to manually type long label arguments for `pop` or `apply` in practice, and that scripts should prefer `stash create` and `stash apply` for such use cases. The technical constraint (requiring the options for `git checkout -m` and autostash) prevents their removal, but their user-facing value remains contested. Harald Nordgren suggested "hiding" the options by keeping them functional but removing them from the documentation, though this was acknowledged as a suboptimal compromise.
- **Future of the options**: No resolution has been reached on whether the options should remain documented in `stash apply`, be hidden (undocumented but functional), or be removed entirely (despite the technical constraint). The thread leaves this as an open design question.

Participant positions
- **Harald Nordgren**: Initially proposed extending the options to `stash pop` but withdrew the patch after maintainer skepticism. Suggested "hiding" the options (keeping them functional but undocumented) as a compromise, though acknowledged this might be a bad idea. No longer advocating for the feature.
- **Junio C Hamano**: Skeptical of the feature's place in the user interface; views the `--label-*` options as internal machinery that should not be exposed in user-facing commands. While acknowledging the technical constraint requiring the options to remain in `stash apply` (due to the sequencer's reliance on them), he does not see this as justification for their presence in the user interface. Concern is purely about user-facing design, not implementation.
- **Phillip Wood**: Agrees with Junio that the underlying machinery for custom labels is justified (e.g., for `git checkout -m`), but remains skeptical about exposing these options in *any* user-facing `stash` subcommand. Argues that users are unlikely to manually type long label arguments, and that scripts should prefer `stash create` and `stash apply` for such use cases.

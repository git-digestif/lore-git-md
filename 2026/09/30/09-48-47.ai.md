This is a two-patch series from Phillip Wood targeting the merge machinery, specifically improving how `git checkout -m` recreates conflict markers. The series teaches Git's ort merge backend to store the original conflict labels (e.g., branch names) in `.git/MERGE_LABELS` when a merge results in conflicts, so that `git checkout -m` can later reuse those same labels instead of the generic "base", "ours", and "theirs".

The motivation is straightforward: when a user resolves a conflict, then later uses `git checkout -m` to re-create the conflict (e.g., to re-resolve it), the labels should match what they originally saw. The series touches `merge-ort.c`, `branch.c`, `builtin/checkout.c`, and several other files to add the plumbing for storing and retrieving these labels. The second patch also adds a test in `t/t7201-co.sh` to verify the behavior.

Phillip raises an open question in the cover letter: whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`), not just the labels. He is unsure if this would be convenient or confusing, and invites feedback. This is a clear point of potential discussion—whether the feature should be strictly about labels or extend to style.

The series is small, focused, and well-scoped. The commit messages are clear, and the test coverage is present. Phillip is a well-known contributor with deep expertise in the sequencer and merge machinery, so the implementation is likely to be solid. The change is user-facing but not disruptive—it only affects the appearance of conflict markers, not their semantics. The open question about conflict style is the main uncertainty, but even if that is deferred, the label preservation itself is a clear improvement.

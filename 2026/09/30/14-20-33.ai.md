This is the v3 cover letter for Tamir Duberstein’s two-patch CI/build system series, now titled “ci: use cmp and align job-count selection.” The series remains focused on mitigating resource exhaustion in GitHub Actions CI jobs, but the second patch has pivoted from simply matching GitLab’s one-job-per-CPU policy to using **twice the detected CPU count** on both GitHub and GitLab.

Patch 1 is unchanged: it still replaces `test_cmp` with `test_cmp_bin` in `t/t4205-log-pretty-formats.sh` to avoid OOM kills when comparing multi-gigabyte commit-message outputs. The benchmark data is now included directly in the cover letter—`diff` peaks at 4 GiB RSS and takes 5.3 seconds, while `cmp` uses 1.2 MiB and finishes in 0.5 seconds.

Patch 2 is the substantive update. Instead of setting `JOBS` to the CPU count (as in v2), it now sets `JOBS` to **twice the CPU count**, doubling GitLab’s current value and replacing GitHub’s fixed `-j10`. The rationale is empirical: on Linux, `2x CPU count` yields a 7 % speedup over `1x`, while on macOS it avoids the 26 % slowdown observed with `1x`. The commit message now includes a detailed table of median build/test-step times across Linux, macOS, and Windows runners, showing that `2x CPU count` offers the best trade-off between Linux speed and macOS stability. The patch touches only `ci/lib.sh` (17 insertions, 4 deletions) and uses native CPU-count queries (`nproc` on Linux, `sysctl -n hw.logicalcpu` on macOS, `NUMBER_OF_PROCESSORS` on Windows).

The series is now data-driven and cross-platform consistent. No new CLI options, on-disk formats, or test coverage changes are introduced. The next steps are likely final review and integration, barring objections to the oversubscription policy.

This is the second patch in Phillip Wood's two-patch series improving `git checkout -m` to remember and reuse the original conflict labels (e.g., branch names) instead of generic "base", "ours", and "theirs". The series targets the merge machinery, specifically the ort backend.

This patch implements the core functionality: it teaches Git to store the original conflict labels in `.git/MERGE_LABELS` when a merge results in conflicts, and updates `git checkout -m` to read those labels when recreating conflicts. The plumbing spans `merge-ort.c`, `branch.c`, `builtin/checkout.c`, and several supporting files. A new flag, `REMOVE_BRANCH_STATE_PRESERVE_CONFLICT_LABELS`, is introduced to prevent `remove_branch_state()` from deleting the labels file when `git checkout -m <branch>` is invoked, ensuring the labels remain available for subsequent `git checkout -m <path>` calls.

The patch also adds a test in `t/t7201-co.sh` that verifies the labels are preserved and correctly reused. The implementation is careful to handle edge cases: if `.git/MERGE_LABELS` is missing or malformed, `git checkout -m` falls back to the generic labels. The new file is cleaned up by `git commit` and `git sequencer` operations, ensuring no stale state remains.

Phillip is a well-regarded contributor with deep expertise in the sequencer and merge machinery, so the implementation is likely robust. The patch is narrowly scoped to label preservation, leaving the open question from the cover letter (whether to also preserve conflict style) unaddressed. The change is user-facing but not disruptive—it only affects the appearance of conflict markers, not their semantics. The new `.git/MERGE_LABELS` file is the only on-disk change, and the patch includes all necessary cleanup logic.

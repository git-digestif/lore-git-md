This is a **bugfix patch** targeting a long-standing regression in Git's reference-transaction hook. The patch is the sole component of the v6 series, which resolves a critical issue where high-level commands like `git branch -d`, `git tag -d`, and `git remote prune` report all-zero object IDs for *both* old and new fields in the hook, breaking external tools (Gerrit, GitLab, CI systems) that rely on the hook to monitor ref changes.

The regression was introduced in Git 2.31 by commit `8198907795`, which optimized bulk deletions but inadvertently omitted the old OID for safety-checked deletions. The v6 patch fixes this by moving the solution into the transaction hook layer itself, recording a separate "observed old value" for updates where callers did not supply an expected old OID. This approach preserves unconditional deletion semantics (a key performance optimization) while ensuring the hook receives the correct old OID, restoring the pre-2.31 behavior.

The patch is **well-crafted and narrowly scoped**, with a clear commit message that documents the design rationale, including why the fix belongs in the transaction layer and why callers cannot preserve old OIDs before deletion. It touches only the refs subsystem (`refs.c` and `refs/refs-internal.h`), adding minimal new fields (`hook_old_oid` and `hook_old_target`) and logic to resolve these values before the "preparing" and "prepared" hook phases. The documentation (`githooks.adoc`) is updated to clarify the hook's behavior, and the test coverage is thorough, verifying hook payloads for batched deletions, remote pruning, symbolic refs, and concurrent updates.

Patrick Steinhardt, the primary maintainer of the refs subsystem, has **explicitly endorsed this approach** as "a sensible change to make," addressing his earlier architectural concerns about the v5 series. The patch is rebased onto `master` and passes the full test suite with `DEVELOPER=1`. The only open question is whether the on-demand resolution of old OIDs introduces unacceptable latency for large batches, but this trade-off is acknowledged and appears to be acceptable to key stakeholders.

This is a **strong candidate for merging**, as it resolves a persistent regression with a clean, layer-appropriate fix that aligns with maintainer feedback. The patch is ready for final review and should be prioritized for inclusion in the next release.

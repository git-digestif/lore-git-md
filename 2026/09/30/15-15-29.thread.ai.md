Subject: [PATCH v3] refs/packed-backend: optimize packed-refs file rewrites
Series version: standalone patch, now v5 (documentation precision corrected)
Originating author: Karthik Nayak <karthik.188@gmail.com>
Thread type: performance optimization patch

Core problem or goal
Speed up operations that rewrite the packed-refs file (e.g., deleting references) by avoiding redundant formatting of unchanged refs. The current implementation uses `fprintf()` for every entry; the patch tracks raw byte positions of unchanged refs and writes them directly with `fwrite()`, while documenting side effects of preserving original formatting (case, whitespace, malformed refnames, peeled OIDs for broken refs).

Current status
Under review. v4 addressed Patrick Steinhardt’s feedback on commit message clarity, `record_start` documentation, and wrapper inlining. v5 will correct the `record_start` comment to clarify that it tracks the start of the current record and is only updated when a new record begins, not on every `pos` advancement. Junio C Hamano’s terminology nit ("sanitation" → "sanitization") was adopted in v3. No maintainer decision recorded; patch remains in "under review" state.

Key technical details
- Files touched: `refs/packed-backend.c` only
- New/renamed symbols: `record_start` field in `struct packed_ref_iterator` (documentation corrected to clarify it tracks the start of the current record and is updated only when a new record begins, not on every `pos` movement); `write_packed_entry()` retains formatted writes; `write_packed_entry_raw()` removed (inlined into its single caller)
- Behavior change: unchanged refs are written as raw bytes instead of being reformatted, preserving original formatting (case, whitespace, malformed refnames, peeled OIDs for broken refs). Side effects documented in commit message.
- On-disk format: unchanged (backward-compatible, but tools parsing packed-refs may observe subtle formatting differences)
- Test coverage: performance benchmark included (deleting 100,000 packed refs, ~20% speedup from 28.7 ms to 23.8 ms)

Open questions and loose ends
1. **Interoperability**: Subtle formatting changes (e.g., uppercase OIDs, tabs) could affect tools parsing packed-refs files (e.g., JGit, libgit2), though no specific compatibility issues have been raised. Documentation in the commit message is intended to mitigate this.
2. **Maintainer pickup**: Junio has not yet queued the patch in `seen` or commented on its technical merits. No timeline for integration.
3. **Documentation precision**: The `record_start` comment must be revised to explicitly state its update semantics (only when a new record begins, not on every `pos` advancement). This is the sole remaining action item before v5.

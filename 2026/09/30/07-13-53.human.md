This is a **substantive review** of the core API patch in Christian Couder’s `early_scan_options()` series, focusing on edge-case correctness and usability. Kaartic Sivaraam raises two key concerns about the current implementation:

1. **Abbreviation handling**: The API’s decision to ignore abbreviated options (e.g., `--export-pack` for `--export-pack-edges`) could misalign with `parse_options()`’s behavior, leading to incorrect interpretation of subsequent arguments as values. Sivaraam suggests erring on the safe side by stopping the scan entirely when an unrecognized argument is encountered, preventing misinterpretation of values. This is a **real edge case** that could affect commands with similarly named options (e.g., `--export-pack` and `--export-pack-edges`), though Christian’s current design prioritizes simplicity over completeness.

2. **Value handling for non-stuck arguments**: The review points out that `early_scan_options()` does not validate whether a separate argument (e.g., `--wanted-value`) is actually present when an option expects a value, leaving `value` as `NULL` in such cases. While Christian’s implementation treats this as expected behavior, Sivaraam questions whether this could lead to subtle bugs in callers that assume `value` is always non-NULL for options requiring arguments. The current tests do not cover this scenario, and Sivaraam suggests adding a test to clarify the behavior.

The review also notes minor documentation and test improvements:
- The return value of `early_scan_options()` (the index of the *value* rather than the option) could be documented more clearly.
- A proposed test case for stuck optional values (`--optarg=5`) would help verify edge-case handling.

**Assessment**: Sivaraam’s feedback is **technically substantive** and addresses real usability concerns, particularly around abbreviation handling and value interpretation. The review does not challenge the API’s core design but highlights areas where the implementation could be more robust or better documented. Christian’s series is otherwise well-structured and addresses Junio’s prior feedback, but these edge cases may require another iteration before the API is ready for `next`. The review is **worth attention** from anyone planning to adopt the new API, as it surfaces potential pitfalls in real-world usage.

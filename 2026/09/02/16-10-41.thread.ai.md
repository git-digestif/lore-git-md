Core problem or goal
Introduce a minimal, reusable `parse-options` sub-API (`early_scan_options()`) to replace fragile hand-rolled early argument scans in Git commands. The v2 redesign addresses Junio’s v1 feedback by eliminating the separate `early_scan_option` structure and requiring commands to adopt the full `parse-options` API before using the early scanner. The series focuses exclusively on fixing a real bug in `git fast-import`: `--allow-unsafe-features` was silently ignored when preceded by `--depth 5`, causing the command to refuse unsafe features from the input stream. The API is deliberately limited—ignoring short options, negated forms, abbreviations, and subcommands—to prioritize simplicity and speed over completeness.

Key technical details
- New flag: `PARSE_OPT_EARLY` (marks options to be reported during early scanning).
- New functions: `early_scan_options()` (core API), `parse_options_check()` (extended to validate `PARSE_OPT_EARLY` usage), `parse_options_takes_argument()` (extracted from `show_gitcomp()` to determine if an option consumes the next argument).
- Files touched: `parse-options.h`, `parse-options.c`, `fast-import.c`, `t/helper/test-parse-options.c`, `t/helper/test-tool.{c,h}`, `t/t0040-parse-options.sh`, `t/t9300-fast-import.sh`, `Documentation/technical/api-parse-options.txt`, `Documentation/git-fast-import.txt`.
- Subsystems: argument parsing, command-line interface.
- New test helper: `test-parse-options --early-scan-options` (exercises the API with edge cases: stuck values `--option=value`, optional arguments, non-options).
- Test coverage: comprehensive API tests in `t/t0040-parse-options.sh`; `git fast-import` bugfix tested in `t/t9300-fast-import.sh` (two new tests: `--depth 5 --allow-unsafe-features` is recognized, abbreviations like `--allow-unsafe` are rejected).
- Behavior changes:
  - Fixes `git fast-import --depth 5 --allow-unsafe-features` (previously ignored `--allow-unsafe-features`).
  - Adds a safety requirement: `--allow-unsafe-features` must be spelled in full (no abbreviations).
  - No changes to on-disk format or option semantics beyond the bugfix.
- Refactoring:
  - `early_scan_options()` now takes a `struct option *` array (no separate `early_scan_option` structure).
  - The scan stops at `--` and `--end-of-options`, matching `parse_options()` behavior.
  - Ignores short options, negated forms (`--no-...`), abbreviations, subcommands, and aliases.
  - `parse_options_takes_argument()` handles edge cases like `PARSE_OPT_LASTARG_DEFAULT` (consumes argument only if not the last one).
  - Stuck-argument handling (`--option=value`) now mirrors `parse_options()`’s logic for `PARSE_OPT_OPTARG` and `PARSE_OPT_LASTARG_DEFAULT` (correctness fix in v2: checks `!(opt->flags & PARSE_OPT_NOARG)` instead of `takes_value`).
- API limitations: documented in `parse-options.h` and `api-parse-options.adoc`; includes ignoring short options, negated forms, abbreviations, and subcommands. Christian defends these limitations as a pragmatic trade-off for simplicity and speed, noting that commands with more complex early-scan needs (e.g., `--help`) can continue using hand-rolled parsing.
- **Usability concern**: Junio’s feedback highlights that the API does not skip separate arguments (`--option value`), requiring callers to handle this logic. This could lead to duplication or inconsistencies in commands adopting the API. The division of labor is documented, but Junio argues it may be a usability pain point.

Open questions and loose ends
- **Design direction**: Junio’s v1 feedback suggested the API might create technical debt by introducing a parallel abstraction to `parse_options()`. The v2 redesign addresses this by reusing `struct option`, but the long-term viability of the API remains unresolved. Junio’s vision of a "dry-run" mode in `parse_options()` (mentioned in v1) is still not addressed, leaving open questions about forward compatibility. Christian argues that the v2 design ensures future refactoring (e.g., a "dry-run" mode) will not require redoing the conversion work, as the API now reuses `struct option`.
- **Scope of adoption**: The series focuses solely on `git fast-import`, but the API is designed for broader use. Junio’s v1 skepticism about the `git bisect` and `git rev-parse` conversions has been **resolved by dropping those patches**, clearing the last substantive objection to the series’ scope. The practical value of the API for commands with simpler early-scan needs (e.g., `--help`) remains unclear, but this is no longer a blocker for v2.
- **Edge-case handling**: The API’s deliberate limitations (e.g., ignoring abbreviations) may frustrate users who expect early scanning to mirror `parse_options()` behavior. The trade-offs are documented, but further discussion may be needed to assess whether the simplicity/speed trade-off is acceptable for future adopters.
- **Caller responsibility for argument skipping**: Junio’s feedback raises a **substantive usability concern**—whether the early scanner should handle argument skipping internally (`--option value`) or leave it to the caller. The current design requires callers to duplicate logic, which could lead to inconsistencies or bugs. This is a **key design decision** that may require further iteration before the series is ready for `next`. Christian’s v1 implementation left this responsibility to the caller, but Junio argues the API would be easier to use if the callee (`find_early_scan_option()`) skipped arguments. **No resolution yet**; this remains the primary open question.
- **Stuck-argument correctness**: The v2 series fixes a subtle edge-case bug in stuck-argument handling (`--option=value`) by checking `!(opt->flags & PARSE_OPT_NOARG)` instead of `takes_value`. This ensures consistent behavior for optional arguments (`PARSE_OPT_OPTARG`) and last-argument defaults (`PARSE_OPT_LASTARG_DEFAULT`). The fix is small but important for correctness.

Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: two-patch series (v4; first patch accepted, second patch (conflict-stop recovery) now posted)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a long-standing race condition in the `rerere` subsystem where concurrent writers contend for the shared `rr-cache` directory lock. The geometric maintenance strategy introduced in Git 2.54 exacerbated the issue by triggering `git rerere gc` more aggressively, but the race is a general robustness flaw: any two concurrent `rerere` operations can collide. The solution is a two-part series: (1) improve error handling in `rerere_setup()` with configurable locking timeouts and unified error reporting (accepted), and (2) allow conflict-stopping commands (e.g., `git rebase`, `git merge`, `git am --3way`, `git stash pop`, `git apply --3way`) to proceed with a warning if the lock remains held after the timeout, preserving the user’s ability to recover conflict preimages manually. Post-resolution recording (e.g., during `git rebase --continue` or `git am --continue`) and explicit `git rerere` commands still fail immediately if the lock is held, avoiding silent corruption of the `MERGE_RR` file. The root cause is now framed as a general `rerere` locking issue, not merely a maintenance-heuristic side effect. The `MERGE_RR` lock is per-worktree, so the race specifically involves the shared `rr-cache` directory where background `rerere gc` (from `git gc`, maintenance runs, or auto-maintenance) can prune entries while another command records conflicts.

Key technical details
- Files touched: `rerere.c` (error propagation, locking logic), `rerere.h` (new `RERERE_SKIP_LOCKED` flag), `apply.c`, `builtin/am.c`, `builtin/merge.c`, `builtin/stash.c`, `sequencer.c`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`.
- New behavior (second patch): Introduces `RERERE_SKIP_LOCKED` flag to `rerere_setup()`. If the lock cannot be acquired within the timeout, conflict-stopping commands (e.g., `git rebase`, `git merge`, `git am --3way`, `git stash pop`, `git apply --3way`) emit a warning and proceed, allowing the user to recover the conflict preimage by running `git rerere` manually before continuing. The warning advises the user to run `git rerere` manually to ensure the preimage is recorded or a known resolution is replayed. Post-resolution recording (e.g., during `git rebase --continue`, `git am --continue`, `git commit`) and explicit `git rerere` commands (e.g., `git rerere`, `git rerere forget`, `git rerere clear`) still fail immediately if the lock is held, preventing silent corruption of the `MERGE_RR` file. The patch updates all relevant callers in `apply.c`, `builtin/am.c`, `builtin/merge.c`, `builtin/stash.c`, and `sequencer.c` to pass `RERERE_SKIP_LOCKED` when appropriate. Documentation is updated to clarify the behavior, and the test suite is expanded to cover edge cases like manual recovery via `git rerere` and the distinction between conflict stops and post-resolution recording.
- Locking changes: The 1-second wait (configurable via `rerere.lockTimeout`) is retained for non-maintenance callers. Background maintenance (`git rerere gc`) continues to pass a timeout of 0 (`RERERE_NOWAIT`) to skip the lock entirely. Error messages are hand-rolled to avoid misleading advice about terminating other Git processes, and the warning for conflict-stopping commands provides explicit recovery guidance (e.g., "run `git rerere` manually before continuing").
- Test coverage: The test suite now verifies that conflict-stopping commands proceed with a warning under a held lock, while post-resolution recording and explicit `git rerere` commands fail. Tests also cover manual recovery via `git rerere` and the restoration of upstream signatures for `rerere_clear()` and `rerere_forget()`.
- Architectural context: The geometric maintenance strategy’s aggressiveness (triggering `git rerere gc` after every commit with even a single `rr-cache` entry) exacerbated the race, but the root issue is any two concurrent `rerere` operations. Patrick Steinhardt’s planned patch series will adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility, reducing the frequency of background maintenance. The locking fix is now framed as a general robustness improvement, not a maintenance-specific workaround.

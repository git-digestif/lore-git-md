Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: two-patch series (v7, final)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a long-standing race condition in the `rerere` subsystem where concurrent writers contend for the shared `rr-cache` directory lock. The geometric maintenance strategy introduced in Git 2.54 exacerbated the issue by triggering `git rerere gc` more aggressively, but the race is a general robustness flaw: any two concurrent `rerere` operations can collide. The solution is a two-part series: (1) make all `rerere` writers wait for the lock with a configurable timeout (`rerere.lockTimeout`), and (2) introduce a `--skip-locked` mode for `git rerere gc` that skips a held lock silently (matching the behavior of other auto-maintenance tasks). The root cause is a general `rerere` locking issue, not merely a maintenance-heuristic side effect. The `MERGE_RR` lock is per-worktree, so the race specifically involves the shared `rr-cache` directory where background `rerere gc` (from `git gc`, maintenance runs, or auto-maintenance) can prune entries while another command records conflicts.

Key technical details
- Files touched: `rerere.c` (locking logic, error propagation, `--skip-locked` mode), `rerere.h` (renamed `RERERE_WARN_LOCKED` flag, introduced `enum rerere_gc_flags`), `apply.c`, `builtin/am.c`, `builtin/gc.c`, `builtin/merge.c`, `builtin/rerere.c`, `builtin/stash.c`, `sequencer.c`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`.
- New behavior (patch 1): Introduces a configurable timeout (`rerere.lockTimeout`, default 1000 ms) for the `MERGE_RR.lock` file. Processes now wait up to the timeout before failing, replacing the previous behavior of immediate termination. The timeout is sufficient to cover typical `git rerere gc` operations. Test coverage verifies the behavior under various scenarios (e.g., waiting for the lock, failing after timeout, and handling explicit `rerere` commands like `forget`, `clear`, and `gc`). The new config key is documented in `Documentation/config/rerere.adoc` with clear explanations of valid values (0 for no wait, -1 for indefinite wait, positive integers for milliseconds). The patch preserves backward compatibility: a timeout of 0 restores the old behavior, and error messages remain unchanged to avoid misleading users about terminating other Git processes.
- New behavior (patch 2): Introduces `--skip-locked` mode for `git rerere gc` (hidden/undocumented). Only `git rerere gc --skip-locked` (triggered by `git maintenance run --auto` or `git gc --auto`) skips a held lock silently; manual invocations of `git rerere gc` wait and then fail like other `rerere` commands. The flag is marked as hidden (`OPT_HIDDEN_BOOL`) and explicitly restricted to the `gc` subcommand, preventing misuse. The lock acquisition logic in `rerere.c` now handles the new `RERERE_NOWAIT` flag (zero timeout). Documentation in `Documentation/config/rerere.adoc` explicitly names the callers (`git maintenance run --auto` and `git gc --auto`) and explains the purpose of the flag (to avoid disrupting concurrent operations). The flag is orthogonal to `RERERE_READONLY` and only accepted by the `gc` subcommand. Test coverage in `t/t4200-rerere.sh` and `t/t7900-maintenance.sh` verifies that `--skip-locked` mode skips a held lock silently while manual runs fail. The patch also updates `builtin/gc.c` to pass `--skip-locked` when running in auto mode, aligning with the established pattern for other maintenance tasks (e.g., `--skip-foreground-tasks` in `git gc`). Following Patrick Steinhardt’s feedback, the commit message now explains why `--skip-locked` is hidden (to match the pattern of `--skip-foreground-tasks` in `git gc`), a layering-violating comment in `rerere.c` was dropped, the comment on `RERERE_NOWAIT` clarifies that a held lock returns `-1` (treated as "nothing to do" by callers, not an error), and the shared bitmask flag was replaced with a dedicated `enum rerere_gc_flags` for `rerere_gc()`. The test suite was split into two cases: one verifying `--skip-locked` skips when locked, another verifying it does not skip when unlocked.
- Locking changes: The 1-second wait (configurable via `rerere.lockTimeout`) is retained for non-maintenance callers. Background maintenance (`git rerere gc --skip-locked`) passes a timeout of 0 (`RERERE_NOWAIT`) to skip the lock silently. Error messages are hand-rolled to avoid misleading advice about terminating other Git processes. Commit messages clarify that not all `rerere` commands take the lock (e.g., `status`, `diff`, and `remaining` do not).
- Test coverage: The test suite now covers the distinction between auto and manual maintenance, and the restoration of upstream signatures for `rerere_clear()` and `rerere_forget()`. Patch 1's test coverage in `t/t4200-rerere.sh` verifies waiting for the lock, failing after timeout, and ensuring explicit `rerere` commands (`forget`, `clear`, `gc`) and `git rebase --abort` fail immediately if the lock cannot be acquired. Patch 2's test coverage now explicitly verifies that `--skip-locked` does not skip when the lock is free, and that the flag is rejected for non-`gc` subcommands.
- Architectural context: The geometric maintenance strategy’s aggressiveness (triggering `git rerere gc` after every commit with even a single `rr-cache` entry) exacerbated the race, but the root issue is any two concurrent `rerere` operations. Patrick Steinhardt’s planned patch series will adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility, reducing the frequency of background maintenance.

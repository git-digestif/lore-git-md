Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: two-patch series (v4 locking patch in progress; sequencer config-override patch pending)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a race condition in the `rerere` subsystem where concurrent writers (not limited to background maintenance) contend for the shared `rr-cache` directory lock. The geometric maintenance strategy introduced in Git 2.54 exacerbated the issue by triggering `git rerere gc` more aggressively, but the race is a long-standing conceptual flaw: any two concurrent `rerere` operations can collide. The solution remains a two-part series: (1) improve error handling in `rerere_setup()` with configurable locking timeouts and unified error reporting, and (2) disable background maintenance during rebase via config overrides. The root cause is now framed as a general robustness issue in `rerere` locking, not merely a maintenance-heuristic side effect.

Key technical details
- Files touched: `rerere.c` (error propagation, locking logic), `rerere.h` (new flags and config key), `builtin/rerere.c`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`.
- New behavior: `rerere_setup()` returns errors instead of dying, using `hold_lock_file_for_update_timeout()` with a configurable timeout (`rerere.lockTimeout`, default: 1000 milliseconds). All non-maintenance callers (e.g., `git commit`, `git merge`, `git rebase`) wait up to the timeout before failing if the lock is still held. Background maintenance (`git rerere gc`) passes a timeout of 0 to skip the lock entirely (`RERERE_NOWAIT`). Explicit `git rerere`, `git rerere forget`, and `git rerere clear` commands now wait for the full timeout before failing, aligning with other callers. The `RERERE_SKIP_LOCKED` flag is replaced by `RERERE_NOWAIT` (timeout=0). Error messages are hand-rolled to avoid misleading advice about terminating other Git processes. A `BUG()` assertion checks for incompatible flag combinations (e.g., `RERERE_NOWAIT` with a non-zero timeout). If `rerere_setup()` fails due to a held lock, the rebase stops at the conflict (with a warning) and allows `--continue` to proceed normally, preserving the user’s ability to recover the conflict preimage by running `git rerere` manually. Post-resolution recording (e.g., during `git rebase --continue` or `git am --continue`) and `rerere_clear()` (used by `git rebase --abort` and `--skip`) fail immediately if the lock is held, avoiding silent corruption of the `MERGE_RR` file.
- Config overrides: During rebase, both the merge and apply backends will pass `-c gc.auto=false -c maintenance.auto=false` to `git commit`, `git merge`, and exec commands. The merge backend will also call `run_auto_maintenance()` at the end of the rebase sequence to ensure consistency with the apply backend.
- Locking changes: The 1-second wait is retained as preexisting behavior to avoid silent failures or crashes. The patch is based on `maint` and resolves a trivial conflict with the recent lockfile helper refactoring (`2e486bfbf7`).
- Test case: 20,000-entry `rr-cache` to trigger the race; focus on verifying error reporting is accurate, the timeout allows rebases to proceed after maintenance completes, and maintenance is disabled during rebase. Tests now also cover the behavior of `git rerere`, `git rerere forget`, and `git rerere clear` under a held lock, as well as the distinction between conflict stops (warn) and post-resolution recording (fail).
- Architectural context: The geometric maintenance strategy’s aggressiveness (triggering `git rerere gc` after every commit with even a single `rr-cache` entry) exacerbated the race, but the root issue is any two concurrent `rerere` operations. Patrick Steinhardt’s planned patch series will adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility, reducing the frequency of background maintenance. The locking fix is now framed as a general robustness improvement, not a maintenance-specific workaround.

Current status
v4 of the locking patch is in progress, incorporating Junio’s and Patrick’s feedback. The behavioral change (silently skipping `rerere` recording on lock timeout) has been split into a separate preparatory commit to allow focused discussion, addressing Patrick’s concern about modularity. The compromise in v4—warning at conflict stops during rebase but failing elsewhere—balances Junio’s insistence on actionable errors with Thomas’s goal of preserving user work. The series remains under review, with no objections to the revised approach. The sequencer config-override patch (disabling maintenance during rebase) remains pending.

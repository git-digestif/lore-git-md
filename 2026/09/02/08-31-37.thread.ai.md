Thread identity
Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: three-patch series (v6, final)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a long-standing race condition in the `rerere` subsystem where concurrent writers contend for the shared `rr-cache` directory lock. The geometric maintenance strategy introduced in Git 2.54 exacerbated the issue by triggering `git rerere gc` more aggressively, but the race is a general robustness flaw: any two concurrent `rerere` operations can collide. The solution is a three-part series: (1) make all `rerere` writers wait for the lock with a configurable timeout (`rerere.lockTimeout`), (2) introduce a `--skip-locked` mode for `git rerere gc` that skips a held lock silently (matching the behavior of other auto-maintenance tasks), and (3) allow conflict-stopping commands (e.g., `git rebase`, `git merge`, `git am --3way`, `git stash pop`, `git apply --3way`) to proceed with a warning if the lock remains held after the timeout, while post-resolution recording (e.g., during `git rebase --continue`, `git am --continue`, `git commit`) and explicit `git rerere` commands still fail immediately. The root cause is a general `rerere` locking issue, not merely a maintenance-heuristic side effect. The `MERGE_RR` lock is per-worktree, so the race specifically involves the shared `rr-cache` directory where background `rerere gc` (from `git gc`, maintenance runs, or auto-maintenance) can prune entries while another command records conflicts.

Key technical details
- Files touched: `rerere.c` (locking logic, error propagation, `--skip-locked` mode), `rerere.h` (renamed `RERERE_WARN_LOCKED` flag, formerly `RERERE_SKIP_LOCKED`), `apply.c`, `builtin/am.c`, `builtin/gc.c`, `builtin/merge.c`, `builtin/rerere.c`, `builtin/stash.c`, `sequencer.c`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`.
- New behavior (patch 1): Introduces a configurable timeout (`rerere.lockTimeout`, default 1000 ms) for the `MERGE_RR.lock` file. Processes now wait up to the timeout before failing, replacing the previous behavior of immediate termination. The timeout is sufficient to cover typical `git rerere gc` operations. Test coverage verifies the behavior under various scenarios (e.g., waiting for the lock, failing after timeout, and handling explicit `rerere` commands like `forget`, `clear`, and `gc`). The new config key is documented in `Documentation/config/rerere.adoc` with clear explanations of valid values (0 for no wait, -1 for indefinite wait, positive integers for milliseconds).
- New behavior (patch 2): Introduces `--skip-locked` mode for `git rerere gc` (hidden/undocumented). Only `git rerere gc --skip-locked` (triggered by `git maintenance run --auto` or `git gc --auto`) skips a held lock silently; manual invocations of `git rerere gc` wait and then fail like other `rerere` commands. The flag is marked as hidden (`OPT_HIDDEN_BOOL`) and explicitly restricted to the `gc` subcommand, preventing misuse. The lock acquisition logic in `rerere.c` now handles the new `RERERE_NOWAIT` flag (zero timeout). Documentation in `Documentation/config/rerere.adoc` explicitly names the callers (`git maintenance run --auto` and `git gc --auto`) and explains the purpose of the flag (to avoid disrupting concurrent operations). The flag is orthogonal to `RERERE_READONLY` and only accepted by the `gc` subcommand. Test coverage in `t/t4200-rerere.sh` and `t/t7900-maintenance.sh` verifies that `--skip-locked` mode skips a held lock silently while manual runs fail. The patch also updates `builtin/gc.c` to pass `--skip-locked` when running in auto mode, aligning with the established pattern for other maintenance tasks (e.g., `--skip-foreground-tasks` in `git gc`). Patrick Steinhardt’s latest feedback suggests rewording the commit message for clarity, removing a layering-violating comment in `rerere.c`, and debating whether `RERERE_NOWAIT` should be a dedicated flag enum for `rerere_gc()` rather than a shared bitmask. A missing test case (verifying that `--skip-locked` does not skip when the lock is free) was also noted.
- New behavior (patch 3): Conflict-stopping commands (e.g., `git rebase`, `git merge`, `git am --3way`, `git stash pop`, `git apply --3way`) emit a warning (via `advise_if_enabled()` under `advice.mergeConflict`) and proceed if the lock remains held after the timeout, allowing the user to recover the conflict preimage manually. The warning instructs the user to run `git rerere` manually before resolving the conflict. Post-resolution recording (e.g., during `git rebase --continue`, `git am --continue`, `git commit`) and explicit `git rerere` commands fail immediately if the lock is held. The `RERERE_WARN_LOCKED` flag (formerly `RERERE_SKIP_LOCKED`) ensures these distinctions. The test suite verifies these behaviors, including manual recovery via `git rerere` and the behavior of auto vs. manual maintenance. The patch ensures the lock timeout does not break the rebase state file (`.git/rebase-merge/stopped-sha`) and that manual recovery works as expected. Test coverage now includes the merge recreated by `git rebase -r`, the only call site previously missing a test. The advisory message is hand-rolled to avoid misleading advice about terminating other Git processes, and the warning provides explicit recovery guidance (e.g., "run `git rerere` manually before continuing").
- Locking changes: The 1-second wait (configurable via `rerere.lockTimeout`) is retained for non-maintenance callers. Background maintenance (`git rerere gc --skip-locked`) passes a timeout of 0 (`RERERE_NOWAIT`) to skip the lock silently. Error messages are hand-rolled to avoid misleading advice about terminating other Git processes, and the warning for conflict-stopping commands provides explicit recovery guidance. Commit messages clarify that not all `rerere` commands take the lock (e.g., `status`, `diff`, and `remaining` do not).
- Test coverage: The test suite now covers the distinction between auto and manual maintenance, manual recovery via `git rerere`, and the restoration of upstream signatures for `rerere_clear()` and `rerere_forget()`. The merge recreated by `git rebase -r` is now explicitly tested. Patch 1's test coverage in `t/t4200-rerere.sh` verifies waiting for the lock, failing after timeout, and ensuring explicit `rerere` commands (`forget`, `clear`, `gc`) and `git rebase --abort` fail immediately if the lock cannot be acquired. Patch 3's test coverage verifies that conflict-stopping commands proceed with a warning, that manual recovery via `git rerere` works, and that post-resolution recording fails if the lock remains held. The missing test case for `--skip-locked` (ensuring it does not skip when the lock is free) will likely be added before integration.
- Architectural context: The geometric maintenance strategy’s aggressiveness (triggering `git rerere gc` after every commit with even a single `rr-cache` entry) exacerbated the race, but the root issue is any two concurrent `rerere` operations. Patrick Steinhardt’s planned patch series will adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility, reducing the frequency of background maintenance.

Current status
The v6 series is final, with all prior feedback incorporated. The series is technically ready for integration, but Patrick Steinhardt’s latest feedback introduces uncertainty about the necessity of patch 3 (the warning-and-proceed behavior for conflict-stopping commands). While patches 1 and 2 are uncontroversial and address the immediate race condition, patch 3’s trade-off between resilience and correctness remains debated. Junio C Hamano has not yet commented on the final version, but all substantive review feedback from Phillip Wood, Patrick Steinhardt, and Junio (on earlier versions) has been addressed. The sequencer config-override patch (disabling maintenance during rebase) remains pending but is orthogonal to this series.

Open questions and loose ends
1. Is patch 3 (warning-and-proceed behavior for conflict-stopping commands) necessary, or should it be deferred until real-world users encounter the issue? Patrick Steinhardt argues for deferral, describing the behavior as "fishy" and premature without evidence of user impact. The architectural settlement (whether the warning-and-proceed behavior is a pragmatic stopgap or an overreach) is now the central unresolved question.
2. Should rebases using the merge backend run maintenance at all? (Deferred to future discussion; no new input.)
3. Is the fork-based background maintenance design inherently flawed for interactive operations? (Phillip Wood’s critique remains unresolved; no new input.)
4. How will Patrick’s proposed changes to `maintenance.rerere-gc.auto` interact with the rebase-specific config overrides? (No overlap is expected, but coordination may be needed.)
5. Is the 1-second wait sufficient for all use cases, or should it be configurable? (Configurable via `rerere.lockTimeout`; no new input on default value.)
6. Should there be a single maintenance run at the end of the rebase sequence? (Phillip Wood insists on consistency between backends; this will likely be included in the sequencer patch.)
7. Phillip Wood reiterates that garbage collection is useless mid-rebase—all objects and `rr-cache` entries created during the rebase are too fresh to be collected. This position remains unresolved.
8. The sequencer config-override patch (disabling maintenance during rebase) is still pending and will address Phillip Wood’s concern about consistency between the merge and apply backends.

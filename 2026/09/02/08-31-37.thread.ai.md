Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: two-patch series (v4 posted; sequencer config-override patch pending)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a long-standing race condition in the `rerere` subsystem where concurrent writers contend for the shared `rr-cache` directory lock. The geometric maintenance strategy introduced in Git 2.54 exacerbated the issue by triggering `git rerere gc` more aggressively, but the race is a general robustness flaw: any two concurrent `rerere` operations can collide. The solution is a two-part series: (1) improve error handling in `rerere_setup()` with configurable locking timeouts and unified error reporting, and (2) allow conflict-stopping commands (e.g., `git rebase`, `git merge`, `git am --3way`) to proceed with a warning if the lock remains held after the timeout, preserving the user’s ability to recover conflict preimages manually. The root cause is now framed as a general `rerere` locking issue, not merely a maintenance-heuristic side effect. The `MERGE_RR` lock is per-worktree, so the race specifically involves the shared `rr-cache` directory where background `rerere gc` (from `git gc`, maintenance runs, or auto-maintenance) can prune entries while another command records conflicts.

Key technical details
- Files touched: `rerere.c` (error propagation, locking logic), `rerere.h` (new flags and config key), `builtin/rerere.c`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`.
- New behavior: `rerere_setup()` returns errors instead of dying, using `hold_lock_file_for_update_timeout()` with a configurable timeout (`rerere.lockTimeout`, default: 1000 milliseconds). Non-maintenance callers (e.g., `git commit`, `git merge`, `git rebase`) wait up to the timeout before failing if the lock is still held. Background maintenance (`git rerere gc`) passes a timeout of 0 to skip the lock entirely (`RERERE_NOWAIT`). Explicit `git rerere`, `git rerere forget`, and `git rerere clear` commands now wait for the full timeout before failing, aligning with other callers. The `RERERE_SKIP_LOCKED` flag is replaced by `RERERE_NOWAIT` (timeout=0). Error messages are hand-rolled to avoid misleading advice about terminating other Git processes. A `BUG()` assertion checks for incompatible flag combinations (e.g., `RERERE_NOWAIT` with a non-zero timeout). If `rerere_setup()` fails due to a held lock, conflict-stopping commands (e.g., `git rebase`, `git merge`, `git am --3way`) emit a warning and proceed, allowing the user to recover the conflict preimage by running `git rerere` manually before continuing. Post-resolution recording (e.g., during `git rebase --continue` or `git am --continue`) and `rerere_clear()` (used by `git rebase --abort` and `--skip`) fail immediately if the lock is held, avoiding silent corruption of the `MERGE_RR` file. Background maintenance runs are either daemonized (closing standard descriptors) or run in the foreground of the triggering commit on Windows, so their warnings do not interfere with foreground output.
- Config overrides: During rebase, both the merge and apply backends will pass `-c gc.auto=false -c maintenance.auto=false` to `git commit`, `git merge`, and exec commands (to be implemented in the pending sequencer patch). The merge backend will also call `run_auto_maintenance()` at the end of the rebase sequence to ensure consistency with the apply backend.
- Locking changes: The 1-second wait is retained as preexisting behavior to avoid silent failures or crashes. The patch is based on `master` (resolving a trivial conflict with the recent lockfile helper refactoring, `2e486bfbf7`).
- Test case: 20,000-entry `rr-cache` to trigger the race; focus on verifying error reporting is accurate, the timeout allows rebases to proceed after maintenance completes, and maintenance is disabled during rebase. Tests now also cover the behavior of `git rerere`, `git rerere forget`, and `git rerere clear` under a held lock, as well as the distinction between conflict stops (warn) and post-resolution recording (fail). The test suite has been expanded to cover edge cases like manual recovery via `git rerere` and the restoration of upstream signatures for `rerere_clear()` and `rerere_forget()`.
- Architectural context: The geometric maintenance strategy’s aggressiveness (triggering `git rerere gc` after every commit with even a single `rr-cache` entry) exacerbated the race, but the root issue is any two concurrent `rerere` operations. Patrick Steinhardt’s planned patch series will adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility, reducing the frequency of background maintenance. The locking fix is now framed as a general robustness improvement, not a maintenance-specific workaround.

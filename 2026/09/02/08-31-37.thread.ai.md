Subject: [PATCH] rerere: fix race condition between rebase and background maintenance
Series version: three-patch series (v5; patches 1–3 ready for final review)
Originating author: Thomas Bachem
Thread type: bugfix patch

Core problem or goal
Fix a long-standing race condition in the `rerere` subsystem where concurrent writers contend for the shared `rr-cache` directory lock. The geometric maintenance strategy introduced in Git 2.54 exacerbated the issue by triggering `git rerere gc` more aggressively, but the race is a general robustness flaw: any two concurrent `rerere` operations can collide. The solution is a three-part series: (1) make all `rerere` writers wait for the lock with a configurable timeout (`rerere.lockTimeout`), (2) introduce a `--auto` mode for `git rerere gc` that skips a held lock silently (matching the behavior of other auto-maintenance tasks), and (3) allow conflict-stopping commands (e.g., `git rebase`, `git merge`, `git am --3way`, `git stash pop`, `git apply --3way`) to proceed with a warning if the lock remains held after the timeout, while post-resolution recording (e.g., during `git rebase --continue`, `git am --continue`, `git commit`) and explicit `git rerere` commands still fail immediately. The root cause is a general `rerere` locking issue, not merely a maintenance-heuristic side effect. The `MERGE_RR` lock is per-worktree, so the race specifically involves the shared `rr-cache` directory where background `rerere gc` (from `git gc`, maintenance runs, or auto-maintenance) can prune entries while another command records conflicts.

Key technical details
- Files touched: `rerere.c` (locking logic, error propagation, `--auto` mode), `rerere.h` (new `RERERE_SKIP_LOCKED` flag), `apply.c`, `builtin/am.c`, `builtin/gc.c`, `builtin/merge.c`, `builtin/rerere.c`, `builtin/stash.c`, `sequencer.c`, `Documentation/config/rerere.adoc`, `Documentation/git-rerere.adoc`, `t/t4200-rerere.sh`, `t/t7900-maintenance.sh`.
- New behavior (patch 1): Introduces a configurable timeout (`rerere.lockTimeout`, default 1000 ms) for the `MERGE_RR.lock` file. Processes now wait up to the timeout before failing, replacing the previous behavior of immediate termination. The timeout is sufficient to cover typical `git rerere gc` operations. Test coverage verifies the behavior under various scenarios (e.g., waiting for the lock, failing after timeout, and handling explicit `rerere` commands like `forget`, `clear`, and `gc`).
- New behavior (patch 2): Introduces `--auto` mode for `git rerere gc`. Only `git rerere gc --auto` (triggered by `git maintenance run --auto` or `git gc --auto`) skips a held lock silently; manual invocations of `git rerere gc` wait and then fail like other `rerere` commands. The `--auto` flag is passed through the maintenance machinery in `builtin/gc.c` and `builtin/rerere.c`, and the lock acquisition logic in `rerere.c` now handles the new `RERERE_NOWAIT` flag (zero timeout). Documentation clarifies the distinction between auto and manual invocations, and tests verify that `--auto` mode skips a held lock silently while manual runs fail. The flag is orthogonal to `RERERE_READONLY` and only accepted by the `gc` subcommand.
- New behavior (patch 3): Conflict-stopping commands (e.g., `git rebase`, `git merge`, `git am --3way`, `git stash pop`, `git apply --3way`) emit a warning (via `advise_if_enabled()` under `advice.mergeConflict`) and proceed if the lock remains held after the timeout, allowing the user to recover the conflict preimage manually. The warning instructs the user to run `git rerere` manually before resolving the conflict. Post-resolution recording (e.g., during `git rebase --continue`, `git am --continue`, `git commit`) and explicit `git rerere` commands fail immediately if the lock is held. The test suite verifies these distinctions, including manual recovery via `git rerere` and the behavior of auto vs. manual maintenance. The patch ensures the lock timeout does not break the rebase state file (`.git/rebase-merge/stopped-sha`) and that manual recovery works as expected.
- Locking changes: The 1-second wait (configurable via `rerere.lockTimeout`) is retained for non-maintenance callers. Background maintenance (`git rerere gc --auto`) passes a timeout of 0 (`RERERE_NOWAIT`) to skip the lock silently. Error messages are hand-rolled to avoid misleading advice about terminating other Git processes, and the warning for conflict-stopping commands provides explicit recovery guidance (e.g., "run `git rerere` manually before continuing").
- Test coverage: The test suite now covers the distinction between auto and manual maintenance, manual recovery via `git rerere`, and the restoration of upstream signatures for `rerere_clear()` and `rerere_forget()`.
- Architectural context: The geometric maintenance strategy’s aggressiveness (triggering `git rerere gc` after every commit with even a single `rr-cache` entry) exacerbated the race, but the root issue is any two concurrent `rerere` operations. Patrick Steinhardt’s planned patch series will adjust `maintenance.rerere-gc.auto` to consider garbage-collection eligibility, reducing the frequency of background maintenance.

This thread is about a two-patch series (v7) from Thomas Bachem that fixes a long-standing race condition in Git’s `rerere` subsystem, where concurrent operations contend for the shared `rr-cache` directory lock. The issue became more noticeable after Git 2.54 introduced a geometric maintenance strategy that triggers `git rerere gc` more aggressively, but the race itself is a general robustness flaw in `rerere` locking.

The series takes a pragmatic approach: the first patch makes all `rerere` writers wait for the lock with a configurable timeout (`rerere.lockTimeout`, defaulting to 1 second), while the second introduces a `--skip-locked` mode for `git rerere gc` (used by background maintenance) to skip silently if the lock is held. This aligns with how other auto-maintenance tasks behave. The solution is conservative—commands fail outright if the lock remains held after the timeout—prioritizing correctness over resilience. All prior feedback, including from Junio C Hamano and Patrick Steinhardt, has been incorporated, and the series is technically ready for integration.

Key participants include Thomas Bachem (author), Phillip Wood (who initially opposed the timeout fix but now accepts it as a stopgap while advocating for deeper changes), and Patrick Steinhardt (who clarified the root cause and pushed for clearer error handling). Junio’s latest review was purely mechanical, ensuring test cleanup aligns with Git’s conventions, and no substantive objections remain. Open questions include whether rebases should run maintenance at all (Phillip Wood argues garbage collection is useless mid-rebase) and how Patrick’s planned changes to `maintenance.rerere-gc.auto` will interact with rebase-specific overrides. The sequencer config-override patch, which will address Phillip’s consistency concerns, is still pending.

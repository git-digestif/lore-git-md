This thread is about fixing a long-standing race condition in Git's `rerere` subsystem, where concurrent operations contend for the shared `rr-cache` directory lock. The issue, exacerbated by the geometric maintenance strategy introduced in Git 2.54, affects any two simultaneous `rerere` operations, not just maintenance tasks. Thomas Bachem proposed a three-patch series to address this: (1) introducing a configurable lock timeout (`rerere.lockTimeout`), (2) adding a `--skip-locked` mode for `git rerere gc` to silently skip held locks during auto-maintenance, and (3) allowing conflict-stopping commands (like `git rebase` or `git merge`) to proceed with a warning if the lock remains held after the timeout, while post-resolution recording and explicit `git rerere` commands still fail immediately.

The series is now in its final stages, with all prior feedback incorporated into v5. The latest discussion between Thomas Bachem and Patrick Steinhardt settled cosmetic details for patch 2: renaming the `--auto` flag to `--skip-locked` (hidden/undocumented) and moving caller-specific documentation from `git-rerere(1)` to `Documentation/config/rerere.adoc`. The `RERERE_SKIP_LOCKED` flag in patch 3 will also be renamed to `RERERE_WARN_LOCKED` to avoid confusion. These changes are minor and don’t affect the core fix. Key participants—Phillip Wood, Patrick Steinhardt, and Junio C Hamano—have all provided substantive reviews, with Phillip Wood initially advocating for deeper fixes (like disabling maintenance during rebase) but now accepting the timeout-based approach as a pragmatic stopgap. The trade-off between resilience (allowing conflict stops to proceed) and correctness (failing post-resolution recording) is settled, though some unresolved questions remain, such as whether rebases should run maintenance at all and how Patrick’s planned changes to `maintenance.rerere-gc.auto` will interact with rebase-specific config overrides. The series is ready for final review, with only a v6 update for patch 2 pending.

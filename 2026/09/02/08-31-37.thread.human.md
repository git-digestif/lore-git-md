This thread is about a two-patch series (v7) by Thomas Bachem that fixes a long-standing race condition in Git’s `rerere` subsystem, where concurrent operations contend for the shared `rr-cache` directory lock. The issue became more noticeable after Git 2.54’s geometric maintenance strategy made `git rerere gc` run more aggressively, but the race itself is a general robustness flaw affecting any two concurrent `rerere` operations.

The series takes a pragmatic approach: the first patch introduces a configurable timeout (`rerere.lockTimeout`, defaulting to 1000ms) for the `MERGE_RR.lock` file, allowing processes to wait briefly before failing, while the second adds a hidden `--skip-locked` mode for `git rerere gc` to silently skip a held lock during background maintenance. All substantive review feedback from Phillip Wood, Patrick Steinhardt, and Junio C Hamano (on earlier versions) has been addressed, and the series is now technically complete. Junio’s latest review of the first patch focuses on documentation consistency and test clarity—suggesting minor adjustments to align with Git’s existing patterns—but does not challenge the core design. The second patch has not yet been reviewed by Junio in this iteration.

Phillip Wood initially opposed the timeout-based fix as a stopgap, advocating for deeper changes like disabling background maintenance during rebase, but now accepts it as a pragmatic solution while deeper fixes are developed. Patrick Steinhardt, who identified the race as a long-standing conceptual flaw, successfully argued for separating `--skip-locked` mode to avoid disrupting concurrent operations, and his feedback led to the removal of a third patch that would have introduced a warning-and-proceed behavior. The series now adopts a conservative stance: conflict-stopping commands fail outright if the lock remains held after the timeout, prioritizing correctness over resilience.

Open questions remain about whether rebases should run maintenance at all (Phillip Wood argues garbage collection is useless mid-rebase), how Patrick’s planned changes to `maintenance.rerere-gc.auto` will interact with rebase-specific config overrides, and whether the fork-based background maintenance design is inherently flawed for interactive operations. Thomas plans to address Phillip’s consistency concerns in a follow-up patch that disables maintenance during rebase for both the merge and apply backends, with the merge backend also calling `run_auto_maintenance()` at the end of the sequence. For now, the v7 series is ready for integration, pending Junio’s final review of the second patch and the minor documentation and test adjustments he requested.

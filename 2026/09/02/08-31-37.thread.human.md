This thread is about a two-patch bugfix series (v7) by Thomas Bachem that fixes a long-standing race condition in Git’s `rerere` subsystem, where concurrent operations contend for the shared `rr-cache` directory lock. The issue was exacerbated by Git 2.54’s geometric maintenance strategy but is a general robustness flaw affecting any two concurrent `rerere` operations.

The first patch introduces a configurable timeout (`rerere.lockTimeout`, default 1000 ms) for the `MERGE_RR.lock` file, allowing processes to wait briefly for the lock instead of failing immediately. The second patch adds a `--skip-locked` mode for `git rerere gc` (hidden and undocumented), which skips the lock silently when triggered by background maintenance tasks like `git maintenance run --auto` or `git gc --auto`. This aligns with Git’s existing patterns for other maintenance tasks. The series adopts a conservative approach: conflict-stopping commands fail outright if the lock remains held after the timeout, prioritizing correctness over resilience.

All prior feedback has been incorporated, and the series is technically ready for integration. Junio C Hamano’s review of the first patch requested minor adjustments to documentation and tests, which Thomas has now addressed. These changes were surface-level and did not affect the core design. Phillip Wood initially opposed the timeout-based fix but now accepts it as a pragmatic stopgap while deeper fixes (like disabling maintenance during rebase) are implemented. Patrick Steinhardt clarified that the race is a long-standing conceptual flaw in `rerere` locking and endorsed the 1-second wait for non-maintenance callers. The third patch from earlier versions (v6), which proposed a warning-and-proceed behavior, was dropped at Patrick’s request.

Open questions remain about whether rebases using the merge backend should run maintenance at all, whether the fork-based background maintenance design is inherently flawed, and how Patrick’s proposed changes to `maintenance.rerere-gc.auto` will interact with rebase-specific config overrides. Phillip Wood also reiterated that garbage collection is useless mid-rebase, as all objects and `rr-cache` entries created during the rebase are too fresh to be collected. These issues are deferred to future work, including a pending sequencer patch to disable maintenance during rebase. For now, the series is final and ready for integration.

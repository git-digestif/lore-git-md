This thread is about a two-patch series by Thomas Bachem that fixes a long-standing race condition in Git’s `rerere` subsystem, where concurrent operations contend for the shared `rr-cache` directory lock. The issue became more noticeable after Git 2.54’s geometric maintenance strategy made `rerere gc` run more aggressively, but the race itself is a general robustness flaw affecting any two concurrent `rerere` operations.

The series is now at v4, with the first patch (configurable locking timeouts and unified error reporting) under final review and the second patch (allowing conflict-stopping commands like `git rebase` or `git merge` to proceed with a warning if the lock is held, while failing for post-resolution recording) ready for review. The key participants—Thomas Bachem, Phillip Wood, Patrick Steinhardt, and Junio C Hamano—have converged on a compromise: conflict-stopping commands emit a warning and proceed to avoid disrupting workflows, while post-resolution recording and explicit `git rerere` commands fail immediately to prevent silent corruption. The trade-off between resilience and correctness is now settled, though a few loose ends remain, such as whether manual `git rerere gc` invocations should fail differently from auto-maintenance.

The latest email is a minor review comment from Patrick Steinhardt on the second patch. He suggests using `advise_if_enabled()` instead of `advise()` for the warning message, which would allow users to suppress the warning via configuration. This is a surface-level nit and doesn’t affect the patch’s core logic. The series is otherwise ready for integration, with no substantive objections left.

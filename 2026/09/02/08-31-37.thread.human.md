This thread is about fixing a race condition in Git’s `rerere` subsystem, where concurrent operations (like a rebase and background maintenance) contend for a shared lock on the `rr-cache` directory. The issue became more noticeable after Git 2.54’s geometric maintenance strategy made `git rerere gc` run more aggressively, but the root problem is a long-standing flaw in `rerere` locking.

Thomas Bachem’s three-patch v5 series is now ready for final review. The first patch adds a configurable timeout for the lock, the second introduces `--auto` mode for `git rerere gc` to skip silently if the lock is held (used by auto-maintenance tasks), and the third allows conflict-stopping commands (like `git rebase`) to proceed with a warning if the lock is held, while post-resolution recording still fails immediately. The series addresses all prior feedback, including Junio’s insistence on loud failures for post-resolution recording and Phillip Wood’s concerns about consistency between conflict stops and post-resolution behavior.

The latest email is a substantive review from Patrick Steinhardt on the second patch. He raises two points: the documentation could better explain *why* `--auto` is useful (avoiding disruption to concurrent operations) rather than just listing who calls it, and the flag’s name itself might be misleading—`--skip-locked` could be a clearer alternative. Patrick also notes that the `builtin/rerere.c` file’s structure is messy but sets that aside as out of scope. The patch remains technically sound, and the open question is purely about user-facing semantics. No objections block merging, but a v6 tweak might follow.

Key participants include Thomas (the author), Phillip Wood (who initially opposed the timeout fix but now accepts it as a pragmatic stopgap while deeper fixes are implemented), Patrick (who clarified the root cause and pushed for configurable timeouts and unified error reporting), and Junio (who insisted on loud failures for post-resolution recording). The series is now complete, with only minor documentation and naming tweaks still under discussion. The pending sequencer config-override patch (to disable maintenance during rebase) is orthogonal and will address Phillip’s remaining concerns about consistency between the merge and apply backends.

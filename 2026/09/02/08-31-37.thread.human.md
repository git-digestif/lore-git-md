This thread addresses a race condition in Git’s `rerere` subsystem, where concurrent operations—particularly background maintenance—contend for the shared `rr-cache` directory lock. The issue, originally thought to be a side effect of Git 2.54’s geometric maintenance strategy, is now recognized as a long-standing flaw in `rerere` locking that can occur whenever two processes attempt to modify the cache simultaneously. Thomas Bachem’s two-patch series proposes a fix: (1) improving error handling in `rerere_setup()` with configurable timeouts and unified error reporting, and (2) disabling background maintenance during rebase via config overrides.

The latest version of the locking patch (v4 in progress) incorporates feedback from Junio Hamano, Patrick Steinhardt, and Phillip Wood. Key changes include splitting the behavioral adjustment (silently skipping `rerere` recording on lock timeout) into a separate preparatory commit, adding `BUG()` assertions for incompatible flag combinations, and aligning explicit `git rerere` commands with other callers by waiting for the full timeout before failing. The patch also clarifies that the `MERGE_RR` lock is per-worktree, while the race involves the shared `rr-cache` directory. Phillip Wood’s recent review confirms these refinements address his earlier concerns, leaving the locking patch technically settled. The sequencer config-override patch, which will disable maintenance during rebase, remains pending.

The series balances robustness with user experience: conflict stops during rebase now warn and proceed (preserving the ability to recover conflict preimages manually), while post-resolution recording and explicit `git rerere` commands fail immediately if the lock is held. Open questions include whether rebases using the merge backend should run maintenance at all, the sufficiency of the default 1-second timeout, and the unresolved critique of fork-based background maintenance design. Junio and Patrick continue to debate the trade-off between surfacing errors loudly and avoiding silent corruption, though the v4 compromise partially resolves this. The series is under review, with no objections to the current approach.

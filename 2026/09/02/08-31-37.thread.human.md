This thread is about fixing a race condition in Git’s `rerere` subsystem, where concurrent operations (like a rebase and background maintenance) can contend for the same lock, leaving users stuck. The fix comes in two parts: the first patch, already accepted, added configurable timeouts and better error handling for `rerere` locking. The second patch, now under discussion, lets commands that stop at conflicts (like `git rebase` or `git merge`) proceed with a warning if the lock is held, while still failing for operations that would risk corrupting the conflict database.

Thomas Bachem authored the series, and the key players—Junio Hamano, Patrick Steinhardt, and Phillip Wood—have all weighed in. The debate centered on whether to fail loudly or allow rebases to continue with a warning; the current version strikes a compromise, warning at conflict stops but failing elsewhere to prevent silent data loss. The patch also updates documentation and tests to cover edge cases, like manual recovery of conflict preimages. No objections remain to the approach, and the patch is likely to be accepted soon. The only loose ends are minor: whether rebases should run maintenance at all (deferred) and how Patrick’s planned changes to maintenance defaults might interact with this fix.

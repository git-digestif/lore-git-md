This thread fixes a long-standing race condition in Git's `rerere` subsystem, where concurrent operations could collide when contending for the shared `rr-cache` directory lock. The issue became more noticeable after Git 2.54 introduced a more aggressive geometric maintenance strategy, but the root cause is a general robustness flaw in `rerere` locking. Thomas Bachem's two-patch series (now at v8) addresses this by introducing a configurable timeout (`rerere.lockTimeout`, defaulting to 1 second) for the `MERGE_RR.lock` file, allowing processes to wait rather than fail immediately. The second patch adds a `--skip-locked` mode for `git rerere gc` (used by background maintenance tasks like `git gc --auto`), which silently skips the lock if held, preventing disruption to concurrent operations.

The series has been thoroughly reviewed and is now queued in Junio C Hamano's `next` branch for integration testing, with all substantive feedback incorporated. Key reviewers—Junio, Patrick Steinhardt, and Phillip Wood—have signed off on the design, though Phillip remains skeptical about the fork-based background maintenance approach and the necessity of garbage collection mid-rebase. A follow-up patch by Okhuomon Ajayi (now at v2) aligns the naming of `credentialStore.lockTimeout` with the new `rerere.lockTimeout` convention, retaining the old key as a deprecated alias. This cleanup is uncontroversial and ready for integration, with Junio's feedback on test structure and code presentation fully addressed.

The only unresolved questions are philosophical rather than technical: whether rebases should run maintenance at all (Phillip Wood argues they shouldn't), and whether the 1-second timeout is sufficient (it's now configurable, but no new input has emerged on the default). A pending sequencer patch will address Phillip's concern about consistency between the merge and apply backends by disabling maintenance during rebase. For now, the series is technically complete and awaiting graduation to `master`.

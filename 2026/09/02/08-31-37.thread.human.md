This thread fixes a long-standing race condition in Git’s `rerere` subsystem, where concurrent operations (like a rebase and background maintenance) contend for the shared `rr-cache` directory lock. The issue became more noticeable after Git 2.54’s geometric maintenance strategy made `git rerere gc` run more aggressively, but the root cause is a general locking flaw in `rerere` itself. Thomas Bachem’s two-patch series (now at v8) addresses this with two changes: (1) a configurable timeout (`rerere.lockTimeout`, defaulting to 1 second) for lock acquisition, and (2) a hidden `--skip-locked` mode for `git rerere gc` to silently skip maintenance if the lock is held—matching the behavior of other auto-maintenance tasks.

The series is technically complete and ready for integration, with all prior feedback from Junio C Hamano, Patrick Steinhardt, and Phillip Wood incorporated. Key adjustments include removing redundant documentation, tightening test error-message matching, and simplifying the API by reusing an existing bitmask flag instead of introducing a new enum. The conservative design prioritizes correctness: if the lock remains held after the timeout, commands fail outright rather than proceeding or skipping silently. Tests cover both auto-maintenance (e.g., `git gc --auto`) and manual operations, ensuring the fix doesn’t disrupt existing workflows.

Phillip Wood initially advocated for disabling background maintenance during rebase entirely, arguing that garbage collection is useless mid-rebase (since all objects are too fresh to prune). While this remains unresolved, the current series provides a pragmatic stopgap. Patrick Steinhardt endorsed the v8 patches as technically sound, and Junio’s earlier concerns about error handling and test hygiene have been addressed. The series touches `rerere.c`, `builtin/gc.c`, documentation, and tests, with no unresolved technical objections.

This thread fixes a long-standing race condition in Git’s `rerere` subsystem, where concurrent operations could contend for the shared `rr-cache` directory lock. The issue became more noticeable after Git 2.54’s geometric maintenance strategy made `git rerere gc` run more aggressively, but the root problem is a general locking flaw in `rerere` itself.

Thomas Bachem’s two-patch series (now at v8) introduces a configurable timeout (`rerere.lockTimeout`, defaulting to 1 second) for the `MERGE_RR.lock` file, allowing processes to wait briefly before failing. It also adds a hidden `--skip-locked` mode for `git rerere gc`, letting background maintenance skip silently if the lock is held—matching the behavior of other auto-maintenance tasks. The series has been reviewed and endorsed by Junio C Hamano, Patrick Steinhardt, and Phillip Wood, with all prior feedback incorporated. Junio has now explicitly marked it ready for the `next` branch, meaning it will undergo integration testing before graduating to `master`.

The conservative design prioritizes correctness: if the lock remains held after the timeout, commands fail outright rather than proceeding or skipping silently. This ensures that active modifications to the `rr-cache` aren’t disrupted. The test suite covers both manual and auto-maintenance scenarios, and the series touches core files like `rerere.c`, `builtin/gc.c`, and documentation. Open questions—such as whether rebases should run maintenance at all, or if the fork-based background maintenance design is flawed—remain unresolved but are deferred to future work. For now, the series is technically complete and ready for integration.

This is a maintainer review of the Rust-based SHA-1 backend series, focusing on the runtime vs. compile-time distinction and the functional equivalence of the two implementations.

Junio C Hamano clarifies a key point: the series is **not** a compile-time-only feature, despite the topic title. The runtime escape hatch (`core.sha1dcBackend`) is the real value for users, allowing them to switch between Rust and C backends without recompiling. This distinction matters because it makes the feature more practical for end users, even if the implementation itself is gated by a compile-time flag (`DC_SHA1_RS`).

The review raises a critical question about **functional equivalence**: do the Rust and C implementations of `sha1dc` behave identically, particularly for collision detection? The concern is whether both backends faithfully implement the same algorithm (presumably from the same academic paper) and will detect attacks the same way given identical inputs. This is not just a performance question—it’s about correctness and security. If the implementations diverge, users might get inconsistent behavior depending on which backend is active, undermining the escape hatch’s purpose.

The review does not yet express an opinion on whether the series should merge, but it flags two issues likely to shape further discussion:
1. The **misleading title** ("compile-time option") downplays the runtime flexibility, which is the more user-relevant aspect.
2. The **need for assurance** that the Rust and C backends are functionally interchangeable, especially for security-sensitive collision detection.

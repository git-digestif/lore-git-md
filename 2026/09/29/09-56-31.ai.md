This is the third and final patch in Patrick Steinhardt’s three-patch series fixing timezone handling in the reftable backend. It addresses the core issue: Git’s reftable backend currently stores reflog timezone offsets in the "[+-]HHMM" format, but the reftable specification requires signed offsets in minutes. This patch updates the backend to store timezones as signed minutes, aligning with the spec.

The change is mechanical: the patch replaces direct storage of the parsed "[+-]HHMM" integer with a conversion to minutes via the new `tz_to_minutes()` helper (introduced in patch 1). When reading reflog entries, it converts back to the "[+-]HHMM" format using `minutes_to_tz()` so that the rest of Git continues to see timezones in the expected format. The patch also updates the `dump-reftable` test helper to print the raw minute offset (without zero-padding) to avoid confusion with the "[+-]HHMM" format.

The commit message acknowledges that this change will reinterpret existing reflog data on disk but argues that the impact is minimal because Git only uses reflog timezones for display purposes, not for computations. A table in the message illustrates the divergence between the current and correct interpretations for various timezone offsets, showing that the discrepancy is proportional to the offset magnitude.

The patch includes a thorough test in `t/t0610-reftable-basics.sh` that verifies both the on-disk storage (using `dump-reftable -t`) and the round-trip behavior (using `test-tool ref-store for-each-reflog-ent`). The test covers edge cases like the maximum (+1400) and half-hour (+0530) offsets.

This is a targeted, well-justified fix that resolves a spec compliance issue with clear test coverage. The change is unlikely to be controversial, though it does involve a breaking change to the on-disk format. The series as a whole appears ready for review.

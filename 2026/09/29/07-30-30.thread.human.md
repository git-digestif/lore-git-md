This thread is about extending `git branch --delete-merged` to detect branches whose changes were integrated via squash merges or rebases, even if the branch tip itself wasn’t merged. The series is now at v3, with the discussion focused on finalizing the command-line interface.

The key development is that the CLI design has settled on a clean separation: `--delete-merged <pattern>` (the existing behavior, which only checks if the branch tip is reachable) and `--delete-integrated <pattern>` (a new flag that detects both rebased and squash-merged branches). This resolves earlier debates about whether to use a single flag with granular modes or a config variable. Junio C Hamano, the maintainer, has endorsed this approach, and Harald Nordgren has now confirmed that the existing `--delete-merged` syntax makes hierarchical modes impractical.

The series still faces open questions about how to handle false positives—cases where a branch is incorrectly deleted because another author independently made the same change. Jasper Mayone proposed an author-check mitigation (requiring the landing commit’s author to also be an author on the branch), which directly addresses scenarios like D. Ben Knoble’s "npm update" example. The next steps are to implement this mitigation, update the test suite, and address performance trade-offs for the new flag. The preparatory refactoring patch is ready for integration, while the rebase and squash detection patches await these final adjustments.

This thread introduces a patch by Harald Nordgren to extend `git branch --delete-merged` so it can detect branches whose changes (but not their tips) have been squash-merged or rebase-merged into an upstream branch. The current implementation only deletes branches whose tips are reachable from the upstream, which fails for common workflows like GitHub’s "Squash and merge" or local `git merge --squash`.

The patch is under active review, with no prior versions submitted. Harald has provided test coverage and agreed to expand the commit message to clarify both GitHub-style and local squash-merge workflows, addressing feedback from Kristoffer Haugsbakk and D. Ben Knoble. The discussion has evolved from a proposed config flag (`branch.deleteMergedDetectSquash`) to a potential CLI option (`--delete-merged=<mode>`), though Harald now leans toward a unified behavior that works out-of-the-box without requiring users to specify detection modes. Performance concerns remain a key topic, with Harald reporting speed improvements but acknowledging lingering costs.

Phillip Wood’s recent review shifts the focus to implementation efficiency, noting that the current approach recalculates upstream diffs for each branch, which is less scalable than `git cherry`’s strategy of precomputing patch-ids and batching blob fetches. He suggests optimizations, such as short-circuiting the squash check if an upstream commit’s second parent tree matches the branch tip, and emphasizes the need for a careful implementation to avoid performance pitfalls. While Phillip finds the feature useful, he cautions that the algorithm must be efficient enough for practical use, particularly in large repositories or blobless clones. The debate over how to control the new behavior (config flag, CLI option, or unified default) remains unresolved, but Phillip’s feedback provides a clear path for improving the patch before that question is settled.

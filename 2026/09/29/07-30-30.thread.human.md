This thread covers Harald Nordgren's v9 series (four patches) extending `git branch` with a new `--delete-integrated <pattern>` option that deletes branches whose changes -- though not their tips -- have landed upstream via rebases or squash merges, while `--delete-merged <pattern>` keeps its existing strict tip-reachability meaning. The CLI design is settled and confirmed by maintainer Junio C Hamano, and the latest email re-presents patch 3/4, the core machinery: it walks upstream commits since the merge base and deletes a branch when a single upstream commit contains the branch's exact version of every file it changed, reporting `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`. Detection is purely tree-level (blob OIDs and modes, no content reads), so it stays cheap in partial clones, and patch 4/4 layers on `ll_merge()`-based three-way merging to also catch squash merges where upstream edited the same files.

The series is at v9, which incorporates Jasper Mayone's fix for a confirmed crash where a path that changed from gitlink to regular file caused `read_mmblob()` to be called on a commit OID; the fix adds a `base_mode` guard plus a regression test. Patches 1/4 and 2/4 are behavior-neutral refactorings, and patch 3/4 drew only a variable-rename nit from Junio, addressed back in v6 -- all three are considered uncontroversial and ready. No integration branch status has been announced; the series remains under review.

The main open issue is the "npm update" false positive: if an unrelated author independently makes identical changes, tree-based rebase detection can wrongly delete the branch. Mitigations via author checks (Jasper Mayone) or patch IDs (D. Ben Knoble) were proposed but not implemented, and Phillip Wood's request for clearer documentation of limitations (such as the lack of rename detection) is only partially addressed. These gaps do not block integration but remain the thread's principal loose end.

This thread is about extending `git branch --delete-merged` to detect branches whose changes (but not their tips) have been integrated via squash merges, rebases, or patch-based workflows. The series, now at v3, aims to provide a one-step maintenance command for common forge and local workflows, but safety concerns have emerged about false positives—where branches are incorrectly deleted because their changes were independently implemented by another author.

Key participants include Harald Nordgren (the author), Junio C Hamano (the maintainer), D. Ben Knoble, Phillip Wood, and Jasper Mayone. The first patch (refactoring) is uncontroversial and ready for integration, but the second (rebase detection) and third (squash detection) patches require a CLI redesign due to safety risks. Three CLI proposals are on the table: Harald’s minimal `--delete-irrelevant` (a single flag with no granularity), Junio’s granular `--delete-irrelevant=squashed,rebased` (allowing opt-in to specific workflows), and Knoble’s `--delete-merged=<kind>` (e.g., `--delete-merged=squash`). The debate hinges on balancing usability, safety, and performance, with Junio’s test case and Knoble’s "npm update" scenario demonstrating that the current algorithm’s leniency is unsafe for the default behavior.

Harald’s latest reply concedes the safety issue but narrows its scope to automated scripts (e.g., dependency bumps), suggesting author checks as a potential mitigation. However, no technical solution has been proposed yet, and the CLI redesign remains unresolved. The series is under active review, with the next steps involving revising the patches to implement one of the CLI designs and updating the test suite to reflect the new behavior. Open questions include whether the new flag should enable both squash and rebase detection by default, how to handle edge cases like identical commits from different authors, and whether to prioritize performance (tree-based diffing) or correctness (patch IDs or author checks).

This thread is about extending `git branch --delete-merged` to detect branches whose changes—though not their exact commits—have been integrated upstream via squash merges, rebases, or patch-based workflows. The series, now at v3, is authored by Harald Nordgren and has sparked a fundamental debate about how Git should handle "merged" in a world where forge workflows and local rebases are common.

The core disagreement is whether this should be a single feature under `--delete-merged` (Harald’s position) or split into two distinct options: the existing `--delete-merged` for strict tip-reachability and a new `--delete-irrelevant` for looser change-based detection (Junio’s proposal). Harald argues that once a branch’s changes are upstream, the mechanism of integration shouldn’t matter—the branch is no longer needed, and users can recover the work from the mainline if needed. Junio counters that these represent different user intents with different safety guarantees: strict reachability is conservative and predictable, while change-based detection is riskier and more ambiguous.

This confirms that while `range-diff` might offer more robust matching, its overhead makes it impractical for a command where speed is critical. The series itself is under active review, with v3 reorganizing the patches to separate rebase and squash detection, preserving performance optimizations, and adding a `--no-squashed` flag.

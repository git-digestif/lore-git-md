This thread is about extending `git branch --delete-merged` to detect branches whose changes have been integrated via squash merges or rebases, even when the branch tip itself isn’t merged. Harald Nordgren’s v3 patch series reorganizes the work into three patches—rebase detection, squash detection, and a `--no-squashed` flag—while preserving performance optimizations and expanded test coverage.

The key debate centers on Junio C Hamano’s proposal to split the series further: implement rebase detection first using `git range-diff`’s commit-matching logic (which considers authorship, log messages, and patch IDs), then evaluate squash detection separately. Harald has now agreed that authorship could be a useful filter for rebase detection, but the broader architectural questions remain open. Phillip Wood and D. Ben Knoble have raised concerns about the squash-detection algorithm’s limitations (e.g., lack of rename detection, lenient attribution) and proposed alternatives like patch IDs for rebases, while Junio has questioned whether the current CLI design (`--delete-merged` with `--no-squashed`) can scale to future workflows.

The series is still under review, with no decisions on whether to adopt Junio’s two-phase approach, how to handle edited commit messages in rebase detection, or whether squash detection should be implemented at all. The `git full-clean` proposal—a higher-level maintenance command—remains conceptual and unrelated to this series.

This thread is about extending `git branch --delete-merged` to detect branches whose changes have been integrated via squash merges or rebases, even if their commit tips aren’t reachable in the upstream history. Harald Nordgren’s v3 patch series implements this with a unified `--delete-merged` command and an opt-in `--squashed` flag, but the proposal has sparked a debate about safety, user intent, and CLI design.

The core disagreement is between Harald’s pragmatic approach—deleting branches once their changes are upstream, regardless of how they landed—and Junio C Hamano’s conservative stance, which argues for separating strict tip-reachability checks (`--delete-merged`) from looser change-based detection (`--delete-irrelevant`). Jasper Mayone’s recent report of a false positive (a branch deleted because another author independently made the same change) has reinforced Junio’s concerns, showing that the current implementation can mislead users about why a branch was deleted. Harald dismisses this as a rare edge case, but Jasper and Junio see it as a fundamental flaw that undermines the command’s predictability.

The series itself is technically complete, with three patches covering refactoring, rebase detection (fast tree-based diffing), and squash detection (three-way merge approximation). Performance optimizations and blobless clone support are in place, and the `--squashed` flag is now opt-in. However, the CLI design remains unresolved. Harald rejects both Junio’s `--delete-irrelevant` split and Jasper’s granular `--landed=<kind>` proposal, favoring a simple, opinionated tool. Meanwhile, Phillip Wood and D. Ben Knoble have raised algorithmic concerns, such as the lack of rename detection in squash detection and the need for patch IDs to handle local rebases.

The first patch (refactoring) is uncontroversial and ready for integration, but the rebase and squash detection patches are blocked on the design debate. The discussion has stalled on philosophical differences, with no clear path forward. If the project prioritizes safety, Junio’s `--delete-irrelevant` proposal is the most likely outcome, but Harald’s resistance suggests a compromise—such as making `--landed` a config-backed option—may be needed to break the impasse.

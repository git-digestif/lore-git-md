This thread is about extending `git branch --delete-merged` to detect branches whose changes (but not their tips) have been integrated upstream—whether via squash merges, rebases, or patch-based workflows. The current implementation only deletes branches whose tips are reachable, which fails in these common scenarios. Harald Nordgren proposed the feature, implemented it, and added test coverage; he now plans a v2 to expand the commit message and address performance concerns.

The discussion has shifted from a binary config flag to a CLI option (`--delete-merged=<mode>`), with Harald now advocating for a single, unified behavior that works out-of-the-box without requiring users to specify detection modes. Performance remains a key concern: Phillip Wood’s review identified inefficiencies in the current approach (recalculating upstream diffs for each branch) and suggested adopting `git cherry`-style batching and precomputation. The latest exchange clarifies that squash merges—whether GitHub-style or local `git merge --squash`—produce single-parent commits whose trees don’t match the branch tip, ruling out earlier optimization proposals. Phillip now argues that squash detection will always be slower than the current tip-reachability check, especially in partial clones, and proposes that Git should fetch the necessary blobs to calculate patch-ids rather than warning users or disabling detection. Harald agrees the feature should default to "on" if it isn’t "diabolically slow" and suggests warning users in partial clones while offering to unshallow the repository.

The thread has also expanded to include a conceptual proposal for a new high-level command, `git full-clean`, which would combine branch cleanup (with squash/rebase/patch detection enabled by default) and all pruning operations under sensible defaults. This idea is motivated by user feedback, including Harald’s observation that some users delete entire repositories when encountering maintenance issues. No decisions have been reached on the CLI option design, performance optimizations, default behavior, or the new command. The latest email narrows the focus to whether blobless clone support should be addressed in the current patch or deferred, with Harald seeking Phillip’s input on scoping the v2.

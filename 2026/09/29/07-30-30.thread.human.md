Harald Nordgren has posted the tenth iteration of a five-patch series that extends `git branch --delete-merged` to detect branches whose changes were integrated upstream via squash merges or rebases, not just strict tip-reachability. The series introduces a new `--delete-integrated <pattern>` flag that uses change-based detection: patch 4/5 implements rebase detection via tree comparisons, while patch 5/5 adds squash-merge detection using a three-way text merge approximation that ignores `.gitattributes` merge drivers. The CLI design is settled with the two flags being mutually exclusive, and `--dry-run` now works with plain `-d`/`-D` deletion modes.

The series remains under review with no integration status announced. Junio C Hamano has confirmed the CLI architecture but his latest message raises an unresolved architectural question about the opt-out config mechanism: whether the existing `branch.<name>.deleteMerged=false` should govern both `--delete-merged` and `--delete-integrated`, or whether a separate key such as `branch.<name>.deleteIntegrated` or a more generic `deleteDone` would be more appropriate. This connects to his earlier unanswered question about the semantic fit of the config key name for change-based deletion. Other open items include mitigating "npm update" false positives (where another author independently makes identical changes), which reviewers Jasper Mayone and D. Ben Knoble have suggested addressing via author checks or patch IDs, and Phillip Wood's request for clearer documentation of limitations such as the lack of rename detection.

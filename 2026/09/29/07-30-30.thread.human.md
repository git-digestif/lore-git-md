This thread is about extending `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been squash-merged or rebase-merged into an upstream branch. The current implementation only deletes branches whose tips are reachable from the upstream, which fails for common workflows like GitHub’s “Squash and merge” or local `git merge --squash`. Harald Nordgren’s patch adds this detection, and the discussion has since expanded to consider a broader user need: a high-level, one-step repository maintenance command that combines branch cleanup and pruning under sensible defaults.

The patch is under review, with no prior versions. Key participants include Harald (the author), Kristoffer Haugsbakk, D. Ben Knoble, and Phillip Wood. The main points of contention are performance and default behavior. Phillip has raised concerns about inefficiencies in the current approach—recalculating upstream diffs for each branch—and argues that squash detection will always be slower than the current tip-reachability check, especially in partial clones. He advocates for a way to disable patch-id-based detection, even if the implementation becomes more efficient, to accommodate performance-sensitive workflows. Harald, however, now argues for enabling the feature by default with an opt-out flag, citing usability improvements and the fact that `git branch --delete-merged` is not a high-frequency command. Kristoffer supports this position, noting he’d use a slower but thorough deletion for large-scale cleanup. The thread has also introduced a conceptual proposal for a new `git full-clean` command that would combine branch deletion (with squash/rebase detection enabled by default) and all pruning operations under sensible defaults, though no decision has been reached on this.

Open questions include whether to implement a CLI option (`--delete-merged=<mode>`) or a config flag to control the behavior, whether the performance trade-offs are acceptable, and whether to pursue the `git full-clean` proposal. Harald’s latest email adds a small but concrete observation: even after Junio signs off on a branch, the current `--delete-merged` logic still fails to clean it up if the merge was done via squash or rebase, reinforcing the real-world gap the patch aims to fill.

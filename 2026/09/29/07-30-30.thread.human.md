This thread introduces a practical improvement to `git branch --delete-merged`, allowing it to detect branches whose changes have been integrated via squash merges, rebases, or patch-based workflows—common in GitHub-style workflows or local `git merge --squash` operations. Harald Nordgren’s v2 patch series addresses performance and correctness issues raised in the initial version, while adding a `--no-squashed` flag to disable the slower squash detection for users with performance-sensitive workflows.

The series is now under review, with key changes from v1 including batched diff calculations (via a `changed_paths` commit slab), fixes for incorrect branch attribution, expanded documentation, and transparent blob fetching in partial clones. The `--no-squashed` flag, introduced in the latest patch, provides a clean opt-out for users who prioritize speed over thoroughness, resolving a tension between Harald’s preference for a unified default behavior and Phillip Wood’s performance concerns. The implementation is self-contained, with no dependencies on other in-flight work, and handles edge cases like upstream file modifications and mixed workflows.

Reviewers Phillip Wood, Kristoffer Haugsbakk, and D. Ben Knoble have engaged substantively with the series, focusing on performance, correctness, and usability. While the `git full-clean` proposal—a higher-level maintenance command combining this feature with pruning operations—remains conceptual, the current patch is ready for integration. The only open question is whether `--no-squashed` should extend to rebase/patch detection, but this is unlikely to block acceptance. The series is poised to land as-is, offering a more thorough cleanup tool for users who frequently deal with squashed or rebased branches.

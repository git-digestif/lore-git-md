This thread is about extending `git branch --delete-merged` to detect branches whose changes (but not their tips) have been integrated via squash merges, rebases, or patch-based workflows—even when upstream modified the same files. The series, now at v6, introduces `--delete-integrated` as an opt-in flag that handles both rebased and squashed branches by default, using a three-way merge approximation to account for upstream edits.

The CLI design is finalized and uncontroversial, with Junio explicitly confirming the split between `--delete-merged` (strict tip-reachability) and `--delete-integrated` (change-based detection). The first two patches—a refactoring and a landing-message helper—are ready for integration, and the third patch (the core flag) is also uncontroversial after addressing Junio’s stylistic feedback. The fourth patch, which implements squash detection with upstream modifications, is technically complete but faces new concerns from Jasper Mayone: redundant index reads in sparse checkouts and `.gitattributes` being resolved from the wrong tree. Harald has accepted Jasper’s offer to contribute test cases for edge cases (e.g., partial landings, conflicting merges) but hasn’t addressed the performance or correctness issues yet.

The series is blocked on two fronts: the unresolved author-check mitigation (to prevent false positives in forge workflows) and Jasper’s feedback on the fourth patch. While the author has fixed a latent correctness issue (proper `.gitattributes` support), the new concerns about index reads and attribute resolution remain open. Minor usability nits (outdated cover letter flag names, silent skipping of checked-out worktrees) and Phillip Wood’s call for clearer documentation of the algorithm’s limitations are also pending.

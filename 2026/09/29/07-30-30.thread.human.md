This thread is about extending `git branch --delete-merged` to detect branches whose changes (but not their tips) have been integrated via squash merges, rebases, or other workflows. The series, now at v3, has sparked a fundamental debate about safety, user intent, and CLI design.

Harald Nordgren’s implementation treats rebase and squash detection as a unified feature under `--delete-merged`, with `--squashed` as an opt-in flag. Junio C Hamano, the maintainer, has repeatedly argued for splitting the feature into two distinct options: `--delete-merged` (strict tip-reachability only) and `--delete-irrelevant` (looser change-based detection). His latest review introduces a critical test case demonstrating a false positive: the current implementation incorrectly deletes a branch whose changes were independently implemented by another author, even without `--squashed`. This reinforces his argument that looser detection should not be the default, as it violates the principle of least surprise.

The series is feature-complete and performs as documented, but the false-positive issue remains unresolved. Harald downplays it as a rare edge case, while Junio and Jasper Mayone argue it undermines the feature’s safety. Phillip Wood and D. Ben Knoble have raised technical concerns about the algorithm’s limitations (e.g., lack of rename detection, performance trade-offs), but the discussion has shifted toward the CLI redesign. The test case Junio provided is likely to anchor future debate, as it quantifies the risk of the current approach.

The thread is at a crossroads: adopt Junio’s split, refine the current implementation to address false positives, or accept the risk as a trade-off for workflow efficiency. No consensus has emerged, and the architectural question remains open.

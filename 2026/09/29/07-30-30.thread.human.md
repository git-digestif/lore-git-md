Harald Nordgren has posted version 8 of his four-patch series extending `git branch --delete-merged` to recognize branches whose changes were integrated upstream via squash merges or rebases rather than direct tip reachability. The series is now technically complete and, by the author's account, ready for integration. The CLI design, confirmed by maintainer Junio C Hamano, splits the behavior into two flags: `--delete-merged` retains its strict tip-reachability meaning, while the new opt-in `--delete-integrated` performs change-based detection of rebased and squash-merged branches, with output reporting which commit each deleted branch "landed as."

The four patches build the feature incrementally: 1/4 extracts shared opt-out logic, 2/4 adds the landing-message reporting helper, 3/4 implements the core `--delete-integrated` machinery with tree-based rebase detection, and 4/4 adds squash-merge detection for cases where upstream subsequently modified the same files, using a path-by-path three-way merge via `ll_merge()` that respects `.gitattributes` but may fetch blobs in partial clones. Substantive review from Jasper Mayone, Phillip Wood, and D. Ben Knoble was addressed across v6 and v7, with Mayone confirming in v7 that all identified issues were resolved; v8 contains only documentation rewording. Junio raised no concerns about the first three patches and the design overall.

The one remaining technical gap, which does not block integration, is the "npm update" false-positive scenario: unrelated upstream changes that coincidentally match a branch's diff could trigger deletion, and mitigating this would require author-check or patch-id logic that has been proposed but not yet implemented. Documentation of limitations such as the lack of rename detection remains only partially addressed.

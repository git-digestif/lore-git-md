Harald Nordgren has posted v9 of his four-patch series extending `git branch` deletion logic to detect squash-merged and rebase-merged branches via a new opt-in `--delete-integrated <pattern>` flag, while keeping the existing `--delete-merged` strict tip-reachability behavior unchanged. The CLI design is settled and confirmed by Junio C Hamano, and v9 incorporates Jasper Mayone's fix for a gitlink-to-blob type-confusion crash found in v8, complete with a regression test. Patches 2/4 (landing-message helper) and 3/4 (core rebase detection) remain uncontroversial, but Junio has now raised substantive design concerns about patch 1/4, which extracts the `branch.<name>.deleteMerged=false` opt-out check into a reusable `branch_opted_out()` helper.

Junio argues the helper's name is too generic and "selfish," assuming branch deletion will always be the only destructive operation needing an opt-out; he suggests either renaming it to explicitly reference the `deleteMerged` operation or making it truly generic with a broader config key like `noClobber`. He also questions the default return semantics, noting that when the config key is missing the function currently returns false ("not opted out"), which he considers a risky default -- absent an explicit "I am fine losing this," the branch should be treated as precious. These concerns apply to the shared helper that patch 3/4 reuses for the new flag, so the opt-out mechanism's naming and safety defaults remain open for discussion even as the overall feature direction is agreed.

Beyond Junio's API design questions, the thread still grapples with the "npm update" false-positive scenario in rebase detection, where an author-check mitigation or patch-ID comparison has been proposed by Jasper Mayone and D. Ben Knoble but not yet implemented, and with Phillip Wood's call for clearer documentation of limitations such as the lack of rename detection in squash-merge detection. The series remains under review with no integration status announced.

This thread introduces `git branch --delete-integrated`, a new flag that extends `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated via squash merges, rebases, or patch-based workflows. The series, now at v5, is authored by Harald Nordgren and has evolved through extensive review to address both technical correctness and user experience.

The core innovation is the `--delete-integrated` flag, which detects branches whose changes have been incorporated into an upstream branch even when the branch tip itself is not reachable. This is particularly useful for common forge workflows (e.g., GitHub's "Squash and merge") and local rebase workflows. The CLI design is now finalized: `--delete-merged` retains its strict tip-reachability behavior (unchanged), while `--delete-integrated` is an opt-in flag that handles both rebased and squashed branches. A key safety feature is that the two flags cannot be combined, ensuring `--delete-merged` never deletes branches whose changes were independently implemented by another author.

The latest patch (v5's fourth) addresses the "upstream modification problem" by using a path-by-path three-way merge approximation via Git's `ll_merge` machinery. This handles cases where upstream edited the same files before squashing, a scenario that previously caused false negatives. The trade-off is that this may download blobs in partial clones when upstream modifications are present. The patch also updates the output format to show the landing commit (e.g., `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`).

The series is under active review, with the first two patches (refactoring and landing-message helper) marked as uncontroversial and ready for integration. The remaining two patches (core flag and squash-detection) are technically complete but still need the **author-check mitigation**—a proposal by Jasper Mayone to require that the landing commit’s author also authored at least one commit on the branch being deleted. This would address false positives in scenarios like automated updates (e.g., "npm update") or forge workflows where patches are manually applied. Minor usability nits (e.g., outdated cover letter flag names, silent skipping of checked-out worktrees) remain but are not blockers.

Key reviewers include Junio Hamano (who confirmed the CLI design), Phillip Wood (who raised performance and correctness concerns), and Jasper Mayone (who provided tested-by feedback and proposed the author-check mitigation). The series touches `builtin/branch.c`, documentation, and tests, and introduces new symbols like the `DELETE_BRANCH_INTEGRATED` flag and `change_state` enum. Open questions include whether to adopt patch IDs or `git range-diff` logic for rebase detection, but the current tree-based approach is performant and sufficient for most use cases.

This thread is about Harald Nordgren’s patch series adding `--delete-integrated` to `git branch`, which lets users delete branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows—even when the upstream modified the same files. The series is now at v6, with the CLI design (`--delete-merged` for strict tip-reachability, `--delete-integrated` for change-based detection) finalized and explicitly approved by Junio. The first two patches (a refactoring and a landing-message helper) are uncontroversial and ready to merge, while the last two (the core flag and squash-detection logic) have addressed all prior feedback, including a latent correctness issue with `.gitattributes` handling.

The main open question remains whether to implement Jasper Mayone’s proposed "author-check" mitigation to reduce false positives in rebase detection, such as the "npm update" scenario where unrelated changes to the same files could be misidentified as integrated. Harald acknowledges the need but hasn’t implemented it yet. Meanwhile, Jasper’s latest review of the fourth patch (v6 4/4) raises two technical concerns: a performance inefficiency in how the index is read during the three-way merge approximation (redundant work in sparse checkouts) and a correctness limitation where `.gitattributes` are resolved from the current worktree’s index rather than the upstream commit’s tree, which could misapply merge drivers in bare repositories. Jasper also suggests adding test cases for edge cases where the branch *shouldn’t* be deleted (e.g., partial hunk landings or conflicting merges). The series is otherwise technically complete, with no remaining design objections, and is awaiting final review on the fourth patch.

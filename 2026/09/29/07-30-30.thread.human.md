This thread extends `git branch --delete-merged` to detect branches whose changes have been integrated via squash merges or rebases, even when the branch tip itself isn’t merged. Harald Nordgren’s v3 series reorganizes the work into three patches—rebase detection, squash detection, and a `--no-squashed` flag—addressing Junio C Hamano’s architectural concerns by separating the distinct algorithms for each workflow. The series retains performance optimizations, correctness fixes, and expanded test coverage, but key algorithmic questions remain unresolved.

The core debate centers on the squash-merge detection method. The current implementation uses a path-by-path three-way merge approximation to check if an upstream commit *contains all changes* from a branch, but Phillip Wood and Junio have raised concerns about its limitations: it lacks rename detection and may misattribute branches to commits with unrelated modifications. Harald clarifies that the goal isn’t to verify an *exact* squash merge but to identify branches whose changes are fully upstream, even if the upstream commit includes additional work. However, this approach risks misleading output (e.g., `landed as` pointing to a commit with extra changes) and doesn’t address Phillip’s call for clearer documentation of the trade-offs.

Junio’s earlier suggestions—reusing `git range-diff` for rebase detection and locally simulating squash merges—haven’t been incorporated yet, and the thread is now focused on whether the current tree-based diffing is sufficient or if stricter methods (like patch-ids or test merges) are needed. The `--no-squashed` flag remains unchanged, defaulting to "on" for squash detection, though its performance impact is still a concern. No new patches have been posted, and the broader `git full-clean` proposal (a high-level maintenance command) remains conceptual. The series is under active review, with the next steps likely hinging on whether the current algorithm is deemed robust enough for real-world use.

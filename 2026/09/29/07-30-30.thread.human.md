This thread is about extending `git branch --delete-merged` to detect branches whose changes have been integrated into an upstream branch via squash merges or rebases, even when the branch tip itself isn’t reachable. Harald Nordgren’s v3 series implements this with a three-patch reorganization: preparatory refactoring, rebase detection (using fast tree-based diffing), and squash detection (via an opt-in `--squashed` flag). The series is feature-complete and addresses earlier performance and correctness concerns, but the discussion has shifted to a fundamental design question.

Junio C Hamano, the maintainer, has proposed splitting the feature into two distinct commands: the existing `--delete-merged` (strict tip-reachability only) and a new `--delete-irrelevant` (for looser change-based detection). Harald rejects this split, arguing that the unified `--delete-merged` approach better serves common workflows, while Junio emphasizes safety and predictability. Jasper Mayone’s real-world testing supports Junio’s concerns, showing a false positive where the feature deleted a branch whose changes were independently implemented by another author. Phillip Wood and D. Ben Knoble have raised technical questions about the squash-detection algorithm’s leniency and whether alternatives like patch IDs or test merges would be more robust.

The implementation itself is uncontroversial: the rebase-detection patch uses efficient tree-based diffing, and the squash-detection patch avoids blob fetches unless `--squashed` is used. The series is ready for integration if the CLI design debate is resolved, but the path forward remains unclear. Open questions include whether to adopt Junio’s split, how to handle the algorithm’s limitations, and whether to pursue broader maintenance commands like `git full-clean`.

This thread is about a patch by Harald Nordgren that extends `git branch --delete-merged` to detect branches whose changes (but not their tips) have been squash-merged or rebase-merged into an upstream branch. The current implementation only deletes branches whose tips are reachable from the upstream, which doesn’t work for GitHub-style squash merges or local `git merge --squash` workflows.

The patch is under review, with the author planning a v2 to expand the commit message and address performance concerns. Key discussion points include whether the feature should be enabled by default (with an opt-out flag) or require explicit user action, and how to optimize performance—especially in large repositories or partial clones. Phillip Wood has raised concerns about the speed of patch-id-based detection, arguing that a toggle to disable it would be useful for performance-sensitive workflows, while Harald Nordgren believes the usability improvement justifies a modest slowdown for most users.

Kristoffer Haugsbakk and D. Ben Knoble have contributed substantive feedback, reinforcing the patch’s motivation and exploring implementation trade-offs. Kristoffer’s latest email adds anecdotal support for the feature, noting that even a slow but thorough branch cleanup would be valuable for users dealing with accumulated branch clutter. The discussion remains open on whether to implement a config flag, a CLI option, or neither, and whether the current performance is acceptable for large repositories.

The thread concerns Harald Nordgren's v8 four-patch series extending `git branch` with a new `--delete-integrated <pattern>` flag that detects branches whose changes (not just tips) were integrated upstream via rebase or squash merge, while `--delete-merged` keeps its strict tip-reachability meaning. The CLI design is settled and confirmed by maintainer Junio C Hamano, and the first three patches -- a shared opt-out helper, a landing-message reporting tweak, and the core rebase-detection machinery -- are considered uncontroversial and ready to land. Patch 4/4, which adds squash-merge detection using a path-by-path three-way merge via `ll_merge()` to handle upstream-modified files, is the one still under active review.

The main open issue is now sharpened rather than merely theoretical: Junio had spotted a potential crash where a path that is a gitlink (submodule pointer) in the merge base but a regular file on both the branch and upstream would cause the code to try reading a commit OID as a blob. Jasper Mayone has now confirmed that this path is real and reachable, reproduced the failure (the command dies with "unable to read blob object" and deletes nothing), and supplied a working fix that records the merge-base file mode in `struct branch_change` and returns `CHANGE_MISSING` for non-regular modes, with the existing test suite still passing. He also asks for a regression test covering the scenario.

So the series stands at v8 with patches 1-3 effectively cleared, and patch 4/4 blocked on one concrete correctness fix plus a regression test. Beyond that, longer-standing loose ends remain but do not block integration: the "npm update" false-positive scenario for rebase detection still lacks an author-check or patch-ID mitigation (raised by Jasper Mayone and D. Ben Knoble), and Phillip Wood's request for clearer documentation of limitations such as the lack of rename detection is only partially addressed.

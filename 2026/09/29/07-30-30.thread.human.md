This thread introduces a v2 patch series by Harald Nordgren that extends `git branch --delete-merged` to detect branches whose changes were integrated via squash merges, rebases, or patch-based workflows—even when the branch tip itself isn’t reachable. The feature addresses a long-standing pain point for users of GitHub-style "Squash and merge" or local `git merge --squash`, where branches linger after their changes are incorporated.

The v2 patch resolves key issues raised in v1: it batches diff calculations to avoid redundant work (addressing Phillip Wood’s performance concerns), fixes a correctness bug where merged branches were misattributed, and adds a `--no-squashed` flag to disable squash detection for performance-sensitive workflows. The implementation now transparently fetches blobs in partial clones, ensuring detection works even in blobless repositories. Tests cover edge cases like upstream file modifications, reverted changes, and mixed merge/squash workflows.

Harald argues the feature should default to "on" for all branches, with `--no-squashed` as an opt-out, while Phillip Wood—though supportive of the optimizations—remains skeptical that squash detection can ever match the speed of tip-reachability checks. The series is under active review, with no major objections outstanding but open questions about whether the performance trade-offs are sufficient for large repositories. The broader `git full-clean` proposal (a high-level maintenance command combining this feature with pruning operations) remains conceptual and is not part of this series.

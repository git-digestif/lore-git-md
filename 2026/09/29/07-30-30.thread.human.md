This thread is about extending `git branch --delete-merged` to detect branches whose changes (but not their tips) have been integrated via squash merges, rebases, or patch-based workflows. The series, now at v3, aims to provide a one-step maintenance command for common forge and local workflows, but has sparked debate over safety, CLI design, and edge cases.

The current implementation has a critical flaw: it incorrectly deletes branches whose changes were independently implemented by another author, even without the `--squashed` flag. This was demonstrated by Junio C Hamano’s test case and D. Ben Knoble’s real-world "npm update" scenario, where identical commits from separate PRs appear "merged" after rebasing. The discussion has since shifted to decoupling strict `--delete-merged` (tip-reachability only) from a new flag for looser change-based detection. Harald Nordgren now proposes `--delete-foo=match-content` (for squash merges), `--delete-foo=match-commits` (for rebases), and `--delete-foo=match-hash` (for strict merges), arguing this naming better reflects the algorithm’s behavior. Junio prefers `--delete-integrated=<mode>`, while Knoble and Jasper Mayone have suggested alternatives like `--delete-merged=<kind>` or `--landed=<kind>`.

The first patch (refactoring) is uncontroversial and ready for integration, but the rebase and squash detection patches require CLI redesign. Key unresolved questions include whether the new flag should enable both squash and rebase detection by default, how to handle edge cases like the "npm update" scenario (e.g., via author checks or patch IDs), and whether the performance trade-offs of stricter detection methods (like `git range-diff`) are acceptable. The series remains under active review, with the next steps likely involving consensus on the flag name and structure, followed by implementation updates.

This thread introduces a patch by Harald Nordgren to extend `git branch --delete-merged` so it can detect branches whose changes (but not their tips) have been squash-merged or rebase-merged into an upstream branch. The current implementation only deletes branches whose tips are reachable from the upstream, which fails for GitHub-style squash merges and local `git merge --squash` workflows.

The patch is under active review, with no prior versions. Harald has provided test coverage and plans a v2 to expand the commit message with examples of both GitHub and local squash-merge workflows, addressing feedback from Kristoffer Haugsbakk and D. Ben Knoble. Performance is a key concern: Harald reports local speed improvements, but Phillip Wood has identified inefficiencies in the current approach, such as recalculating upstream diffs for each branch, and suggests adopting `git cherry`-style batching and precomputation. The discussion has shifted from a binary config flag to a CLI option (`--delete-merged=<mode>`), though no decision has been reached on whether to implement this or default to a single unified behavior.

Harald leans toward a single, out-of-the-box behavior without fine-grained controls, arguing that the feature should work consistently across all contexts. Phillip Wood, however, advocates for a way to disable the slower patch-id-based detection, especially for users who know their repository contains only squash merges. He acknowledges that enabling the feature by default is reasonable if performance is acceptable but emphasizes the need for an opt-out mechanism. D. Ben Knoble and Kristoffer Haugsbakk have contributed substantive feedback, with D. Ben Knoble proposing a more granular CLI option and Kristoffer reinforcing the patch’s motivation by highlighting the prevalence of squash merges in real-world workflows. The thread remains open, with performance optimizations and CLI design as the primary unresolved questions.

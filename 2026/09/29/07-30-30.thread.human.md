This thread is about extending `git branch --delete-merged` to detect branches whose changes (but not their tips) have been integrated via squash merges, rebases, or patch-based workflows. Harald Nordgren’s v3 patch series splits the work into three parts: preparatory refactoring (ready for integration), rebase detection, and squash detection. The latter two are confirmed but require a CLI redesign due to safety concerns exposed by Junio C Hamano’s test case and D. Ben Knoble’s "npm update" scenario, which show the current algorithm can incorrectly delete branches whose changes were independently implemented by another author.

The main debate now centers on the CLI design for the new flag. Harald proposes a minimal `--delete-irrelevant` (no granularity), while Junio advocates for a hierarchical `--delete-integrated=<mode>` (`merged`, `rebased`, `squashed`), where broader modes include narrower ones to avoid user confusion. Knoble and Jasper Mayone suggest alternatives like `--delete-merged=<kind>` or `--landed=<kind>`. Junio’s latest email refines the naming discussion, rejecting "irrelevant" as negative and proposing "integrated" or "done" as more intuitive. The granularity structure remains contested, with Junio favoring hierarchical modes to prevent accidental exclusions of normally merged branches.

The series is under active review, with the first patch uncontroversial and the remaining two awaiting CLI consensus. Open questions include whether the new flag should enable both squash and rebase detection by default, how to address the "npm update" scenario (e.g., via author checks or patch IDs), and whether to adopt slower but more robust algorithms like `git range-diff` or patch IDs for the new flag. Performance trade-offs and algorithmic limitations (e.g., lack of rename detection in squash detection) remain unaddressed, as do Jasper’s usability suggestions and Phillip Wood’s call for clearer documentation. The next steps involve reaching consensus on the CLI design before revising the patches.

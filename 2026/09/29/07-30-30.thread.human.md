Harald Nordgren's `[PATCH v8 0/4]` series proposes extending `git branch` with a `--delete-integrated` flag that detects branches whose changes landed upstream via squash merges or rebases, even when the tips don't match. The series splits this change-based detection from the existing strict `--delete-merged` tip-reachability check to avoid false deletions, and v8 itself contains only documentation tweaks over v7. Earlier reviews from Jasper Mayone, Phillip Wood, and D. Ben Knoble shaped the implementation, with all performance and `.gitattributes` concerns resolved by v7; however, the thread has now taken a new turn.

Junio C Hamano has identified a potential crash in the squash-detection code introduced in earlier versions and still present in v8. He traces a scenario where a path was a gitlink (submodule pointer) in the merge base but has been replaced by regular files on both the branch and upstream. In that case `collect_branch_changes()` records the submodule's commit OID as `base_oid`, and when `merge_keeps_upstream()` later tries to read that OID as a blob via `read_mmblob()`, the program crashes. Junio asks whether he is misreading the code flow or if this path is genuinely reachable, marking this as a correctness issue that needs resolution before the series can be considered ready.

The series remains at v8 and under review, with patches 1/4 and 2/4 still uncontroversial but now blocked behind the maintainer's latest question about the gitlink-to-blob type confusion in patch 4/4. The sole remaining technical gap from earlier discussions -- the "npm update" false-positive scenario needing author checks or patch-ids -- is still unimplemented, and this new crash edge case is now the immediate open question for Harald to address.

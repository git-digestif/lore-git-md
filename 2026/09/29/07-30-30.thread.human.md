This thread introduces a small but useful quality-of-life improvement for Git users: extending `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been squash-merged or rebase-merged into an upstream branch. The current implementation only deletes branches whose tips are reachable from the upstream, which misses common workflows like GitHub’s “Squash and merge” or local `git merge --squash` operations.

Harald Nordgren’s patch, now under review, adds this detection by comparing tree diffs and simulating a three-way merge to confirm that every change from the branch is present in an upstream commit. The implementation is self-contained, touching only `builtin/branch.c` and its documentation, and includes comprehensive test coverage for edge cases like reverted squash merges and partial landings. The output format is clear: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`.

Two reviewers—Kristoffer Haugsbakk and D. Ben Knoble—have engaged substantively with the patch, both reinforcing its motivation and adding context about the prevalence of squash-merge workflows in both local and forge-based environments. Knoble’s latest email explores implementation trade-offs, such as whether the rebase case could leverage `git log --cherry-mark` or whether the squash check could short-circuit if an upstream commit’s tree exactly matches the branch tip. He concludes that the current uniform approach is reasonable, though he notes the algorithm’s potential performance cost on large repositories. No objections or requests for changes have been raised; the only pending action is Harald’s planned update to the commit message to include examples of both GitHub-style and local squash-merge workflows, along with a brief note on their relative prevalence and the role of tooling defaults. The patch is ready for a v2 iteration.

This thread is about extending `git branch --delete-merged` to detect branches whose changes (but not their tips) have been integrated via squash merges, rebases, or patch-based workflows. The series, now at v3, has sparked a detailed discussion about safety, CLI design, and real-world edge cases.

The core issue is that the current implementation can incorrectly delete branches whose changes were independently implemented by another author, as demonstrated by Junio C Hamano’s test case and D. Ben Knoble’s "npm update" scenario. To address this, the discussion has converged on splitting the command into two distinct flags: `--delete-merged` (strict tip-reachability, unchanged) and `--delete-integrated` (change-based detection for rebased *and* squashed branches). Junio has now endorsed this design, confirming the flag name `--delete-integrated` and rejecting a config variable for intermediate levels (e.g., only rebased branches) in favor of simplicity. Both flags will require an upstream branch pattern and will not support granular modes.

The series is under active review, with the first patch (refactoring) ready for integration. The remaining work involves finalizing the CLI implementation, incorporating Jasper Mayone’s proposed author-check mitigation (requiring shared authorship between the landing commit and the branch being deleted), and updating the test suite to cover the new behavior. Open questions include whether to adopt patch IDs or other algorithmic improvements for rebase detection, but the CLI design is now settled.

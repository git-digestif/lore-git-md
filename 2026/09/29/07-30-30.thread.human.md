Harald Nordgren's v10 series proposes extending `git branch --delete-merged` to also catch branches whose changes landed upstream via squash merges or rebases, introducing a new `--delete-integrated` flag that uses change-based detection rather than strict tip-reachability. The five-patch series is complete and under review: patch 4/5 adds tree-based rebase detection, patch 5/5 adds squash detection via three-way text merges, and patch 3/5 relaxes `--dry-run` to work with plain `-d`/`-D` deletion modes. Junio C Hamano has confirmed the CLI design, while reviewers including Jasper Mayone, D. Ben Knoble, and Phillip Wood have weighed in on safety concerns around false positives (the "npm update" scenario where another author independently makes identical changes), performance, and documentation of limitations such as the lack of rename detection.

The latest exchange sharpens a narrow disagreement over the wording of future `--dry-run` error messages for branch creation and renaming. Harald proposed deferring those operations to a follow-up series tagged `#leftoverbits` and avoiding the word "yet" in error text so as not to promise eventual support, but Junio pushed back, arguing that `git branch` is a mature, everyday command where users expect signals about future support, unlike experimental commands such as `git history`. The code remains unchanged: `--dry-run` still works only with deletion modes in v10, with per-operation error messages deferred.

Still open beyond this wording question are whether to add author-check or patch-ID mitigation for false positives, whether `branch.<name>.deleteMerged` is the right config key for the new `--delete-integrated` mode or a separate key is needed, and whether the opt-out mechanism should extend to change-based deletion at all. No integration status has been announced for the series.

Harald Nordgren has posted version 9 of his four-patch series extending `git branch` with a new `--delete-integrated <pattern>` flag that detects branches whose changes have been integrated upstream via squash merges or rebases, even when the branch tip itself is not reachable. The CLI design is settled: `--delete-merged` keeps its strict tip-reachability meaning, while `--delete-integrated` opts into change-based detection, and the two cannot be combined. Junio C Hamano has confirmed the flag separation and finds patches 1 through 3 -- a refactoring, a landing-message helper, and the core rebase-detection machinery -- uncontroversial and ready to queue.

The latest iteration, v9, incorporates a crash fix supplied by Jasper Mayone for a gitlink-to-blob type confusion discovered in v8, where a path changing from a submodule to a regular file could cause `read_mmblob()` to die on a commit OID; the fix adds a `base_mode` guard so such paths are treated as not landed. Patch 4/4 now also handles squash merges where upstream modified the same files by using `ll_merge()` for a path-by-path three-way merge approximation, counting a change as landed only when the merge result is byte-identical to the upstream blob. Tests cover the new scenarios plus the regression case.

The series remains under review with no integration announced. The main open technical gap is the "npm update" false-positive scenario: without author checks or patch IDs, the tool may delete a branch whose changes were independently reimplemented upstream. Phillip Wood's request for clearer documentation of limitations such as missing rename detection is only partially addressed, and a few of Jasper Mayone's usability nits remain unresolved, though none block integration.

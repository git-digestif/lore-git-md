This thread is about extending `git branch --delete-merged` to detect branches whose changes (but not their tips) have been integrated via squash merges, rebases, or patch-based workflows—a common pain point for repository maintenance. Harald Nordgren’s v3 patch series splits the work into three parts: preparatory refactoring (ready for integration), rebase detection, and squash detection. The series has sparked a lively discussion about safety, CLI design, and performance trade-offs.

The core controversy centers on false positives: the current implementation can incorrectly delete branches whose changes were independently implemented by another author, even without the `--squashed` flag. Junio C Hamano’s test case and D. Ben Knoble’s real-world "npm update" scenario (identical commits from separate PRs rebased onto `main`) demonstrate this risk. Harald has conceded the safety issue and proposed a new `--delete-irrelevant` flag to decouple strict tip-reachability from looser change-based detection, but the design remains unresolved. Junio favors granular control (`--delete-irrelevant=squashed,rebased`), while Harald prefers a minimal single flag. Knoble’s latest email suggests an alternative: `--delete-merged=squash` or `--delete-merged=rebase,squash`, arguing this is more intuitive than multiple flags.

Performance is another sticking point. Harald’s experiments showed that `git range-diff` (suggested by Junio for rebase detection) is 20× slower than tree-based diffing, making it impractical for the default behavior. The squash-detection algorithm, which uses a three-way merge approximation, also lacks rename detection and is intentionally lenient—raising concerns about attribution accuracy. Phillip Wood and others have called for clearer documentation of these limitations. Meanwhile, Jasper Mayone’s usability suggestions (clearer worktree messages, reusable helper logic) and the broader `git full-clean` proposal (a high-level maintenance command) remain unaddressed.

The series is under active review, with the first patch uncontroversial and the latter two awaiting CLI redesign. The next steps involve revising the patch series to implement the agreed-upon flag syntax and updating the test suite to cover the new behavior, including Junio’s test case and Knoble’s "npm update" scenario. The thread’s outcome will shape how Git handles repository maintenance for years to come.

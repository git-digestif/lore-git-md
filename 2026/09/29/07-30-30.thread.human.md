This thread is about extending `git branch --delete-merged` to detect branches whose changes (but not their tips) have been integrated via squash merges, rebases, or patch-based workflows—a common pain point for users of GitHub-style workflows. Harald Nordgren’s v3 patch series implements this with a three-patch structure: preparatory refactoring, rebase detection (using fast tree-based diffing), and squash detection (via a three-way merge approximation, enabled by the new `--squashed` flag). The series is feature-complete, with performance optimizations and expanded test coverage, but a fundamental disagreement over CLI design has emerged.

Junio C Hamano, the maintainer, argues that the current approach conflates two distinct user intents: a **strict, conservative** `--delete-merged` (tip-reachability only) and a **looser, riskier** `--delete-irrelevant` (change-based detection for rebases, squash merges, and cherry-picks). His concern is safety: the current implementation risks deleting "irrelevant" branches—those whose changes are upstream but whose commits and messages are not (e.g., an AI-generated patch series superseded by an independent solution). Harald rejects this split, maintaining that the unified `--delete-merged` better serves the primary use case (local and forge-style workflows). Jasper Mayone’s latest user report reinforces Junio’s position: v3 still produces false positives, deleting branches whose changes were independently implemented by another author, even without `--squashed`. Jasper endorses Junio’s CLI redesign and proposes a granular `--landed=<kind>` option (e.g., `--landed=files` for tree-based diffing, `--landed=merge` for three-way merge detection) to let users opt into looser detection via config, preserving `--delete-merged`’s conservative default.

The series is technically ready for integration, but the CLI design remains unresolved. The first patch (refactoring) is uncontroversial, while the rebase and squash detection patches are explicitly confirmed: rebase detection uses fast tree-based diffing (avoiding blob fetches), and squash detection uses a three-way merge approximation (with blob fetches batched and only performed when `--squashed` is used). Performance is acceptable (0.078s vs. 0.030s for 80 branches), and blobless clone support works as intended. The open questions are architectural: whether to adopt Junio’s strict/loose split, whether to document the squash-detection algorithm’s limitations more explicitly, and whether to pursue Jasper’s `--landed` proposal or Harald’s unified approach. The thread reflects a broader tension between workflow efficiency (Harald’s stance) and safety/predictability (Junio’s and Jasper’s stance).

This thread is about extending `git branch --delete-merged` to detect branches whose changes have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows—a feature aimed at simplifying repository maintenance for common forge and local workflows. The series, now at version 3, has sparked a fundamental debate between the author, Harald Nordgren, and the maintainer, Junio C Hamano, over how the feature should be designed and what it should guarantee.

Harald’s implementation treats squash and rebase detection as a unified feature under the existing `--delete-merged` flag, with a `--no-squashed` opt-out for performance-sensitive cases. His argument is pragmatic: once a branch’s changes are upstream—regardless of how they were integrated—the branch is no longer needed, and users can recover the work from the mainline if necessary. Junio, however, has proposed a more conservative approach, suggesting that the existing `--delete-merged` should remain a *strict* tip-reachability-only command (safe and predictable) while introducing a new `--delete-irrelevant` flag for looser, change-based detection (riskier and more ambiguous). This split reflects concerns about scalability, safety, and the potential for misleading results—for example, a branch might be "irrelevant" because its changes were independently solved by someone else, not because they were integrated.

The latest exchange sharpens this divide. Harald pushes back against Junio’s proposal, arguing that the mechanism of integration (squash, rebase, or verbatim merge) shouldn’t matter to the user’s intent: if the work is upstream, the branch can be deleted. Junio’s framing, however, prioritizes clarity and safety, warning that change-based detection introduces ambiguity that could lead to unintended deletions. The discussion now hinges on whether the project will adopt Junio’s CLI redesign or proceed with Harald’s unified approach. Meanwhile, technical details like performance optimizations, edge-case handling, and algorithmic trade-offs (e.g., whether to use `git range-diff` or patch IDs for rebase detection) remain secondary to this larger question. No decisions have been made, and the thread is still under active review.

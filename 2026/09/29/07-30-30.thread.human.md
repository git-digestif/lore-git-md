This thread extends `git branch --delete-merged` to detect branches whose changes—but not their tips—have been integrated via squash merges, rebases, or patch-based workflows. The v4 series, authored by Harald Nordgren, now introduces a new top-level flag, `--delete-integrated`, which unifies both rebase and squash detection under a single opt-in interface. The original `--delete-merged` behavior (strict tip-reachability only) is preserved unchanged, addressing earlier safety concerns about false positives, such as branches being incorrectly deleted when another author independently made the same change.

The series is split into four patches: a preparatory refactoring, a helper to report where a branch "landed" in the output message, the core `--delete-integrated` logic for rebase and squash detection, and an extension to handle upstream file modifications via a three-way merge. Junio C Hamano has explicitly confirmed the design, which now cleanly separates strict tip-reachability (`--delete-merged`) from change-based detection (`--delete-integrated`). The CLI is finalized, and the series includes Junio’s test case to ensure `--delete-merged` never deletes branches with independently added identical changes.

Key open questions remain, including whether to implement Jasper Mayone’s proposed author-check mitigation (requiring the landing commit’s author to also have authored a commit on the branch) to further reduce false positives in forge workflows. Performance trade-offs for squash detection in partial clones are also unaddressed, though the rebase detection remains fast and blob-free. The series is now under review, with the first patch (refactoring) uncontroversial and ready for integration.

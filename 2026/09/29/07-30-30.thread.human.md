This thread is about extending `git branch --delete-merged` to detect branches whose changes (but not their tips) have been integrated via squash merges, rebases, or patch-based workflows—a feature aimed at simplifying repository maintenance for common forge and local workflows. Harald Nordgren’s v3 patch series implements this as a unified feature under `--delete-merged`, with a `--no-squashed` flag to disable squash detection for performance. However, Junio C Hamano has proposed a fundamental redesign: preserve `--delete-merged` as a strict, tip-reachability-only command (safe and conservative) and introduce a new `--delete-irrelevant` option for looser, change-based detection (riskier and ambiguous). Harald rejects this split, arguing that the mechanism of integration shouldn’t matter—once a branch’s changes are upstream, the branch is no longer needed.

The latest input comes from Jasper Mayone, a real-world user who tested Harald’s v2 implementation on generated repositories. Jasper’s feedback validates the feature’s correctness (it accurately identifies squash merges, rebases, and even reverts) but also confirms Junio’s concern about false positives: the feature deleted a branch whose changes were independently implemented by another author, attributing it to an unrelated commit. Jasper endorses Junio’s CLI redesign, suggesting a granular `--landed=<kind>` option (e.g., `--landed=squash`) to let users opt into looser detection via config, rather than relying on repeated `--no-<kind>` flags. Performance-wise, Jasper found the impact modest (0.078s vs. 0.030s for 80 branches) and noted that `--no-squashed` restores baseline speed. In blobless clones, the first run fetched 13 blobs (0.42s), while `--no-squashed` avoided fetches entirely. Jasper also highlighted usability quirks, like silent skips for branches checked out in worktrees, and proposed refactoring the "has this branch landed?" logic into a reusable helper for future commands.

The thread remains at an impasse: Harald’s v3 implementation treats squash and rebase detection as a unified feature under `--delete-merged`, while Junio and now Jasper argue for decoupling strict and looser detection to address safety and ambiguity. Open questions include whether to adopt Junio’s redesign, how to handle rebase detection (patch IDs vs. `git range-diff`), and whether the current squash-detection algorithm is sufficient or needs stricter alternatives like test merges. Jasper’s report adds weight to Junio’s position, but Harald’s pushback suggests the debate is far from resolved.

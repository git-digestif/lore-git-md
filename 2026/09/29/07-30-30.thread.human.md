This thread extends `git branch --delete-merged` to detect branches whose changes (but not their tips) have been squash-merged or rebase-merged into an upstream branch, addressing a common pain point for users of GitHub-style "Squash and merge" or local `git merge --squash` workflows. The initial patch by Harald Nordgren is under active review, with key participants including Kristoffer Haugsbakk, D. Ben Knoble, and Phillip Wood.

The core debate has shifted from implementation details to usability and performance trade-offs. Harald now argues for enabling the feature by default, accepting a modest slowdown for the sake of simplicity, while Phillip Wood advocates for a way to disable patch-id-based detection—even if the implementation improves—citing performance concerns, especially in partial clones. Harald counters that `git branch --delete-merged` is not a high-frequency command and proposes warning users about incomplete detection in shallow repositories rather than disabling the feature. The discussion now hinges on whether to prioritize out-of-the-box functionality or fine-grained control over performance.

The patch itself is technically sound, with test coverage for edge cases like reverted squash merges and partial landings. Performance optimizations (e.g., batching diff calculations) are still in progress, but the author reports local speed improvements. The CLI design remains unresolved: Harald leans toward a unified behavior without user-controlled modes, while D. Ben Knoble and Phillip Wood suggest options like `--delete-merged=<mode>` to let users opt out of slower detection methods. No maintainer decision has been made yet, but the thread is converging on a v2 that will address these trade-offs.

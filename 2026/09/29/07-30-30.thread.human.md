This thread is about extending `git branch --delete-merged` to detect branches whose changes have been integrated via squash merges or rebases, even if the branch tip itself isn’t reachable. Harald Nordgren’s v3 patch series introduced this functionality with an opt-in `--squashed` flag, but Junio C Hamano’s recent review exposed a critical safety issue: the current implementation can incorrectly delete branches whose changes were independently implemented by another author, even without `--squashed`. Junio provided a test case demonstrating this false positive and proposed splitting the command into two distinct modes—strict `--delete-merged` (tip-reachability only) and looser `--delete-irrelevant` (change-based detection)—to address the risk.

Harald has now conceded the safety issue and accepted the need for a CLI split, though he proposes a simpler design: a single `--delete-irrelevant` flag rather than Junio’s granular approach. This would keep the interface minimal while mitigating the false-positive risk, though it leaves open whether the new flag should enable both squash and rebase detection by default. The series is still under review, with the first patch (refactoring) uncontroversial and ready for integration, while the second (rebase detection) and third (squash detection) remain contentious due to the safety trade-offs. Key open questions include whether `--delete-irrelevant` should be opt-in for each detection method, how to handle algorithmic limitations (e.g., rename detection, performance), and whether to document the risks more explicitly. Jasper Mayone’s suggestion for a granular `--landed=<kind>` option and Phillip Wood’s call for clearer documentation remain unaddressed. The next steps will likely involve revising the series to implement `--delete-irrelevant` and updating the test suite to reflect the new behavior.

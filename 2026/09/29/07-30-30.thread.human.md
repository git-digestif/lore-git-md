This thread introduces a patch series by Harald Nordgren that extends `git branch --delete-merged` to detect branches whose changes have been integrated via squash merges, rebases, or patch-based workflows—even when the branch tip itself isn’t reachable. The v2 patch, now under review, addresses performance and correctness issues from the initial version, adds a `--no-squashed` flag for performance-sensitive workflows, and expands documentation and test coverage.

The core discussion revolves around whether the feature should treat squash merges and rebases as a single unified problem or as distinct cases. Junio C Hamano’s recent review questions the current two-patch structure, suggesting that rebases (where commits correspond one-to-one) and squash merges (where the entire branch is collapsed into a single commit) might be better handled separately. He proposes reusing `git range-diff` logic for rebases and message-based matching for squash merges, noting that tree-based diffing may be less reliable for squash workflows. This raises a broader design question about whether the current implementation is the right long-term approach.

Key participants include Harald Nordgren, who implemented the performance optimizations and usability improvements in v2, and Phillip Wood, whose substantive review focused on performance and correctness. Kristoffer Haugsbakk and D. Ben Knoble also contributed feedback in earlier rounds, reinforcing the real-world need for the feature and exploring implementation trade-offs. The series is now at a crossroads: while the v2 patch is functionally complete and addresses prior concerns, Junio’s architectural feedback may prompt a rethink of how the two integration workflows are handled. The `git full-clean` proposal—a higher-level maintenance command—remains conceptual and is not part of this series.

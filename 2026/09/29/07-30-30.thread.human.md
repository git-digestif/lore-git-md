This thread introduces a new feature for `git branch --delete-merged` that extends its behavior to recognize branches whose changes have been squash-merged or rebase-merged into an upstream branch, even when the branch tip itself isn’t reachable from the upstream history. The change is motivated by user feedback highlighting a common pain point: branches merged via GitHub-style squash merges were previously skipped by `--delete-merged` because their tips don’t appear in the upstream history. The patch, authored by Harald Nordgren, adds logic to detect when an upstream commit contains all of a branch’s changes by comparing tree diffs and simulating a three-way merge, then reports the first such commit in the deletion message (e.g., `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`).

The implementation is self-contained, touching `builtin/branch.c`, updating the man page, and adding thorough tests in `t/t3200-branch.sh`. The code handles edge cases like reverted changes or partial landings and avoids false positives by ensuring every change from the branch is present in the upstream commit. The feature aligns with user expectations for squash-merged branches and doesn’t introduce controversial design choices. So far, there’s no review feedback, so the patch’s correctness and acceptance remain unconfirmed.

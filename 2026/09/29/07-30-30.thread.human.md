This thread is about extending `git branch --delete-merged` to detect branches whose changes have been squash-merged or rebase-merged into an upstream branch, even when the branch tip itself isn’t part of the upstream history. The current implementation only deletes branches whose tips are reachable, which misses common workflows like GitHub’s “Squash and merge” or local `git merge --squash`. Harald Nordgren proposed a patch that uses tree diffs and simulated three-way merges to identify these cases, and the discussion has since expanded to consider both performance trade-offs and a broader vision for a high-level maintenance command.

The patch is under review, with key participants including Harald (the author), Kristoffer Haugsbakk (who reinforced the real-world need for the feature), D. Ben Knoble (who explored implementation trade-offs), and Phillip Wood (who raised performance concerns). The main sticking point is whether the feature should be enabled by default, given that patch-id-based detection is inherently slower than the current tip-reachability check—especially in partial clones where blob fetches may be required. Harald and Kristoffer argue that a modest slowdown is acceptable for most users, while Phillip maintains that users should have a way to disable the slower detection method. The discussion has also broadened to include a conceptual proposal for a new `git full-clean` command that would combine branch cleanup and pruning under sensible defaults, addressing user frustration with Git’s maintenance complexity.

No decisions have been finalized on the CLI design, default behavior, or the `git full-clean` proposal. The patch itself is self-contained and doesn’t depend on other in-flight work, but performance optimizations (like batching blob fetches or precomputing patch-ids) remain open questions. The thread is still in the design phase, with the next steps likely involving a v2 patch that incorporates feedback on the commit message, performance improvements, and possibly a refined CLI option.

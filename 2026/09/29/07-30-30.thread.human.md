This thread is about extending `git branch --delete-merged` to detect branches whose changes have been integrated via squash merges, rebases, or patch-based workflows—a feature aimed at simplifying repository maintenance for users of GitHub-style workflows and local rebase/squash practices. Harald Nordgren’s third iteration of the patch series (v3) splits the work into three patches: preparatory refactoring, rebase detection, and squash detection, with an opt-in `--squashed` flag. However, a critical safety issue emerged when Junio C Hamano provided a test case showing the current implementation incorrectly deletes branches whose changes were independently implemented by another author, even without the `--squashed` flag. This led Harald to concede the need for a CLI redesign, proposing a new `--delete-irrelevant` flag to decouple strict tip-reachability (the original `--delete-merged` behavior) from looser change-based detection.

The discussion has since focused on the trade-offs between safety and usability. Junio advocates for granular control (`--delete-irrelevant=squashed,rebased`) to let users opt into specific workflows, while Harald prefers a simpler `--delete-irrelevant` flag without granularity, arguing that complexity would burden users. D. Ben Knoble’s recent email reinforces the safety concern with a real-world scenario: identical "npm update" commits in separate pull requests, rebased onto `main`, can trick the rebase-detection logic into treating the second PR’s commits as "merged" even though they contain no new changes. This highlights a limitation of the current tree-based diffing approach and strengthens the case for stricter checks (e.g., patch IDs or author matching) in the `--delete-irrelevant` implementation. The first patch (refactoring) remains uncontroversial and ready for integration, but the CLI design and detection algorithms for the remaining patches are still in flux. Open questions include whether `--delete-irrelevant` should enable both squash and rebase detection by default, how to handle GitHub-style rebases, and whether to document the algorithm’s limitations more explicitly.

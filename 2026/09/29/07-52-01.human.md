This is a **feature patch** that extends `git branch --delete-merged` to detect branches whose changes (but not their tips) have been squash-merged or rebase-merged into an upstream branch. The patch is under active review and is part of a single-patch series by Harald Nordgren.

The core idea is to make the command more useful in workflows where the branch tip is not part of the upstream history, such as GitHub's "Squash and merge" or local `git merge --squash` followed by `git commit`. The implementation compares tree diffs and simulates a three-way merge to determine if all changes from the branch are present in the upstream commit, avoiding false positives from partial or reverted landings. The output format is clear: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`.

Kristoffer Haugsbakk's review highlighted that the patch also handles local `git merge --squash` workflows, not just GitHub-style merges, which broadens its applicability. Harald's reply acknowledges this and considers expanding the commit message to include both examples. The patch itself is well-motivated, includes thorough test coverage for edge cases (reverted squash merges, partial landings), and touches only the necessary files (`builtin/branch.c` and the man page). No new symbols are introduced, and the logic is internal-only.

This looks like a clean, self-contained improvement that addresses a real pain point for users of squash-merge workflows. The discussion so far is constructive and focused on clarifying the scope rather than raising objections. If the commit message is updated to include both GitHub and local `merge --squash` examples, it will be even clearer for future readers. Worth watching for anyone interested in branch management or GitHub interoperability.

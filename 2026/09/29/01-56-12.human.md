This is a workflow discussion in the ongoing `gitmergeconflicts(7)` documentation series thread. Junio C Hamano expands on Jeff King’s earlier advice about pre-submission testing, offering practical guidance for contributors who want to catch integration issues early.

Junio clarifies that the goal is not to apply patches *on* an integration branch like `seen`, `next`, or `jch`, but rather to merge a topic branch (based on a stable release or `master`) *into* one of those branches as a trial. This approach surfaces potential conflicts or build failures without disrupting the contributor’s working base. He highlights the value of this practice beyond just catching merge conflicts: it can reveal related work in the same area, expose API changes that break the patch, or even uncover helper functions that could simplify the implementation. For documentation-focused contributors like Julia Evans, Junio notes that these benefits might be less relevant, but the technique remains useful for anyone working near code changes.

The exchange reinforces the project’s informal norms: while pre-submission integration testing isn’t mandatory, it’s a low-effort way to improve patch quality and avoid surprises during review. Junio’s personal rule—ensuring topics are in `jch` before marking them for `next`—underscores the stability of `jch` as a target for such trials.

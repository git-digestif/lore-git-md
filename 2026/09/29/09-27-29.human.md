This is the second patch in Harald Nordgren’s four-part series introducing a "matching-inspired" fetch mode for shallow repositories. The patch implements the core logic that dynamically infers which branches to fetch when a remote has a `remote.<name>.refmap` configured but no `remote.<name>.fetch` refspec. The series as a whole aims to solve the problem of slow or hanging `git fetch` operations in shallow repositories by avoiding the negotiation of history for all remote branches.

The current patch is technically complete and addresses the last substantive design objection from Junio C Hamano (the forced inclusion of the remote’s default branch in earlier versions). It scans local branches whose `@{upstream}` points to the remote in question, then fetches only those branches. This reduces network traffic and avoids the error that previously occurred when `--refmap` was used without explicit refspecs. The implementation is clean, well-tested, and integrates smoothly with the rest of the fetch machinery.

Harald’s reply here raises a minor but notable edge case: a bare `git fetch upstream` (with no explicit refspec) currently fetches nothing, leaving the remote-tracking namespace empty. This prevents users from running `git branch --set-upstream-to=upstream` without first fetching something explicitly. While this behavior is consistent with the patch’s design goal of avoiding unnecessary fetches, it may surprise users who expect the remote’s default branch to be available for tracking. Harald acknowledges this is a separate discussion, but it’s worth noting as a potential usability quirk.

The patch looks ready for merging from a technical standpoint, but this edge case could spark further discussion about whether the new mode should be more permissive in certain scenarios. The series remains under review, with no merge status yet.

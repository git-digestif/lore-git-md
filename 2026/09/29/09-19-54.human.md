This is a feature patch series (v4) that introduces a new "matching-inspired" fetch mode to solve a performance problem in shallow repositories. When a shallow clone (`git clone --depth`) fetches from a remote with many branches, a refspec-less `git fetch` currently negotiates history for *all* remote branches, which can be slow or hang entirely. The series now implements a consensus design using `remote.<name>.refmap` to dynamically fetch only the branches tracked by local branches at the remote, without requiring explicit refspecs or command-line flags.

The v4 iteration removes the controversial forced inclusion of the remote’s default branch, addressing Junio C Hamano’s review concern that it was overly presumptive. A fresh remote now fetches nothing until a branch is explicitly tracked, simplifying the code and avoiding awkward fetch report output (e.g., `* [new ref] HEAD -> second/main`). The series is split into four focused patches: (1) the `remote.<name>.refmap` configuration, (2) the dynamic branch enumeration logic, (3) the `--limited-fetch` flag for `git remote add`, and (4) making `--limited-fetch` the default in shallow repositories.

Files touched include `remote.c`/`remote.h` (refmap parsing and branch enumeration), `builtin/fetch.c` (integration with fetch logic), `builtin/remote.c` (new flag and shallow default), and documentation (`config/remote.adoc`, `fetch-options.adoc`, `git-remote.adoc`). Tests in `t/t5510-fetch.sh`, `t/t5585-fetch-refmap.sh` (new), and `t/t5505-remote.sh` cover configuration, dynamic branch selection, edge cases (empty repositories, duplicate branches), and the shallow-repository default. The implementation preserves backward compatibility: non-shallow repositories continue using wildcard refspecs by default, and the new mode is only enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`.

The series looks well-crafted, with clear commit messages, thorough test coverage, and a design that emerged from prior discussion. The removal of the forced default branch inclusion in v4 resolves the last substantive design question, leaving only minor documentation wording updates (already addressed in this iteration). The patches are now narrowly focused on the core problem: shallow repositories no longer fetch unnecessary branches, and users can opt into the new behavior explicitly or implicitly (via the shallow default). This should be a welcome improvement for users of large repositories.

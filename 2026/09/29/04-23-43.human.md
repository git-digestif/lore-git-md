This is an **RFC proposal** for a new safety feature targeting Git hooks. The author, Dmytro Lymarenko, suggests adding an optional per-repository consent mechanism to prevent Git from automatically running local hooks in untrusted repositories. When enabled, Git would prompt the user before executing any hook in a repository they haven’t explicitly approved, displaying the hook’s path and offering options to run it once, trust all hooks in the repository permanently, or decline. The feature would also re-prompt if a trusted hook’s script changes, addressing scenarios where hooks are installed or modified after cloning. The default behavior would remain unchanged, with the protection controlled by a user-configurable setting.

The motivation is to mitigate risks from tools or project setups that install hooks from supplied files, which could execute arbitrary code without the user’s awareness. The proposal is lightweight—it doesn’t alter Git’s default behavior but provides an opt-in safeguard for users who want finer control over hook execution. There’s no implementation yet, just a conceptual outline, so the discussion is likely to focus on whether the problem is worth solving, whether the proposed UX (prompting before execution) is appropriate, and how it might interact with existing workflows (e.g., CI systems or automated tooling that rely on hooks). If this gains traction, it could evolve into a feature patch targeting the hook subsystem.

This is a feature patch introducing a new submodule URL syntax `^/` that resolves paths relative to the root of the superproject's remote server. The patch comes from Stanislav Aleksandrov and is marked as an RFC, indicating it is a proposal rather than a finished contribution.

The motivation is practical: relative paths like `../lib.git` break when a superproject is forked into a deeper hierarchy (e.g., a GitLab subgroup), while absolute URLs force a protocol on everyone. The `^/` syntax borrows from `svn:externals` and lets `.gitmodules` specify a path like `^/org/lib.git` that resolves to `https://host/org/lib.git` (or `git@host:org/lib.git`) regardless of where the superproject lives on the server. The patch includes extensive tests showing that the resolution works for HTTPS, SSH, and SCP-style URLs, and that it fails cleanly when the superproject has no remote or a local path.

The implementation touches the submodule helper, remote URL parsing, and configuration checks. It adds a new `root_relative_url()` function in `remote.c` that strips the path component from the superproject's remote URL and appends the `^/`-prefixed path. The patch also updates the documentation to explain the new syntax and its limitations (e.g., it cannot be used with local clones or remotes that lack a host).

The RFC section in the commit message candidly lists known costs: `^` is special in `cmd.exe`, Git Bash rewrites `^/...` arguments, and other Git implementations (libgit2, JGit) would need to learn the syntax. The author argues that `/path` or `//host/path` are not viable alternatives because they conflict with existing local and network path conventions. The patch references a GitLab issue asking for the same feature, suggesting real-world demand.

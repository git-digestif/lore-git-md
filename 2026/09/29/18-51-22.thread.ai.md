Thread identity
Subject: [RFC PATCH] submodule: introduce `^/` syntax for root-relative URLs
Series version: RFC (single patch)
Originating author: Stanislav Aleksandrov
Thread type: RFC feature proposal

Core problem or goal
Allow submodule URLs to be specified relative to the superproject's remote server root, enabling portable forks across arbitrary hierarchy depths (e.g., GitLab subgroups). The `^/` syntax dynamically replaces only the path portion of the superproject's remote URL, preserving protocol, host, and credentials without manual configuration. The design explicitly distinguishes between `^/` (for submodules remaining in their original location) and traditional relative paths (`../`) (for forked dependencies), addressing fork isolation concerns.

Key technical details
- New syntax: `^/org/lib.git` resolves against the superproject's remote URL (e.g., `https://host/me/super.git` -> `https://host/org/lib.git`).
- Files touched: `builtin/submodule--helper.c`, `submodule-config.c`, `remote.c` (new `root_relative_url()`), documentation, and tests (now t7428).
- Symbols: `root_relative_url()` function, new config/CLI handling in submodule code.
- Behavior: opt-in; existing URLs unchanged. Explicitly rejects local paths, `file://`, and helper transports; fails for malformed `^/` URLs that could alter URL type (e.g., changing protocol). Uses `skip_bracketed_host()` to handle IPv6 in SCP-style URLs. The `^/` syntax is designed for submodules that remain in their original location on the remote server, while relative paths (`../`) continue to work for forked dependencies.
- Parsing bugs identified by Junio C Hamano in `skip_bracketed_host()`: with remote URL `host:dir/@[x]/repo.git`, the function scans past the first colon searching for `]`, causing the caller to fail to find the host separator and produce a "cannot resolve" error; with `host:dir/@[x]:y/repo.git`, parsing yields corrupt URL `host:dir/@[x]:org/lib.git` instead of intended `host:org/lib.git`. Suggested fix is to not scan for `@[` or `:` past the first slash in the path portion.
- Test coverage: cloning, syncing, HTTPS/SSH/local forks, nested submodules, remote URL changes, error conditions (including shell escaping and IPv6 in SCP-style URLs), and fork isolation semantics.

Open questions and loose ends
- Shell escaping: `^` is special in `cmd.exe` and Git Bash; users may need quoting. Acknowledged as a practical concern but not considered a blocker.
- Ecosystem adoption: libgit2, JGit, and forges would need to implement the syntax. The debate over new syntax vs. existing mechanisms (`url.<base>.insteadOf`, `.gitmodules` extensions) continues. Alternatives are static and require per-clone setup, while `^/` dynamically resolves against the superproject's remote URL.
- Relative traversal: `../../` requires knowing the superproject's depth -- a fragile assumption that breaks across forks at different nesting levels. The `^/` syntax avoids this by resolving to the server root.
- Fork isolation: `^/` URLs require explicit updates when forking both superproject and submodule, whereas relative URLs (`../`) would continue pointing to the original submodule. This is clarified as intentional (forks should not silently inherit upstream dependencies), though it may still surprise users.
- IPv6 in SCP-style URLs: Handled by `skip_bracketed_host()`, but Junio has identified parsing failure modes when local path components contain `@[` sequences (see Key technical details).
- Integration mechanics: Junio has called for objections from heavy submodule users before merging the topic down to `next`; the test renumbering (t7427 -> t7428) will be squashed only upon graduation from RFC.
- Security/credential handling: D. Ben Knoble asks whether `^/` URLs traverse the same resolution path as `../` URLs in `check_submodule_url()` (referencing commit `c44088ecc4` on credential handling for scheme-less URLs) and whether the new `skip_prefix(url, "^/", ...)` check adequately prevents credential injection via `^/` URLs. He disputes the test expectations in `t0060-path-utils.sh` for `^//evil.example.com` and `^/:evil`, arguing naive resolution would yield `host/evil.example.com/x.git` rather than the asserted failure.
- Implementation concerns: Knoble expresses discomfort with manual string munging in `root_relative_url()` and helpers (`skip_bracketed_host()`, `has_host()`), asking whether an existing dependency could handle URL parsing. He questions the logic in `resolve_relative_url_gently()` in `builtin/submodule--helper.c` that suppresses the "could not look up configuration" warning when `^/` is detected, noting `^/` is nonsensical when the remote URL falls back to `$PWD`. He asks whether local-path support could be added later without a rewrite.
- Documentation structure: Knoble suggests restructuring the URL description in `Documentation/git-submodule.adoc` into a bullet list of URL forms (absolute URI, `^/` server-root path, `./` or `../` relative path), cross-referencing `gitmodules.adoc` to `git-submodule.adoc` to avoid duplication, capturing RFC trade-offs (shell escaping, ecosystem adoption) in the commit message rather than only list archives, and avoiding GitLab-specific "subgroup" terminology in test descriptions. Junio C Hamano additionally notes that calling `^/` an "absolute path" is misleading for scp-style URLs like `git@host:group/super.git` that lack a leading slash after the colon, suggesting "paths relative to the server-root" as clearer wording.

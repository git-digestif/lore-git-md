Subject: [RFC PATCH] submodule: introduce `^/` syntax for root-relative URLs
Series version: RFC (single patch)
Originating author: Stanislav Aleksandrov
Thread type: RFC feature proposal

Core problem or goal
Allow submodule URLs to be specified relative to the superproject’s remote server root, enabling portable forks across arbitrary hierarchy depths (e.g., GitLab subgroups). The `^/` syntax dynamically replaces only the path portion of the superproject’s remote URL, preserving protocol, host, and credentials without manual configuration. The design explicitly distinguishes between `^/` (for submodules remaining in their original location) and traditional relative paths (`../`) (for forked dependencies), addressing fork isolation concerns.

Key technical details
- New syntax: `^/org/lib.git` resolves against the superproject’s remote URL (e.g., `https://host/me/super.git` → `https://host/org/lib.git`).
- Files touched: `builtin/submodule--helper.c`, `submodule-config.c`, `remote.c` (new `root_relative_url()`), documentation, and tests (now t7428).
- Symbols: `root_relative_url()` function, new config/CLI handling in submodule code.
- Behavior: opt-in; existing URLs unchanged. Explicitly rejects local paths, `file://`, and helper transports; fails for malformed `^/` URLs that could alter URL type (e.g., changing protocol). Uses `skip_bracketed_host()` to handle IPv6 in SCP-style URLs. The `^/` syntax is designed for submodules that remain in their original location on the remote server, while relative paths (`../`) continue to work for forked dependencies.
- Test coverage: cloning, syncing, HTTPS/SSH/local forks, nested submodules, remote URL changes, error conditions (including shell escaping and IPv6 in SCP-style URLs), and fork isolation semantics.

Open questions and loose ends
- Shell escaping: `^` is special in `cmd.exe` and Git Bash; users may need quoting. Acknowledged as a practical concern but not considered a blocker.
- Ecosystem adoption: libgit2, JGit, and forges would need to implement the syntax. The debate over new syntax vs. existing mechanisms (`url.<base>.insteadOf`, `.gitmodules` extensions) continues. Alternatives are static and require per-clone setup, while `^/` dynamically resolves against the superproject’s remote URL.
- Relative traversal: `../../` requires knowing the superproject’s depth—a fragile assumption that breaks across forks at different nesting levels. The `^/` syntax avoids this by resolving to the server root.
- Fork isolation: `^/` URLs require explicit updates when forking both superproject and submodule, whereas relative URLs (`../`) would continue pointing to the original submodule. This is now clarified as intentional (forks should not silently inherit upstream dependencies), though it may still surprise users.
- IPv6 in SCP-style URLs: Handled by `skip_bracketed_host()`, but no explicit test coverage was added.

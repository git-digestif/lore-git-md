Thread identity
Subject: [PATCH 0/4] sha1dc-accel: faster SHA-1 collision detection
Series version: v1 (initial submission)
Originating author: Scott Chacon <scott@gitbutler.net>
Thread type: patch series

Core problem or goal
Replace Git’s existing `sha1dc` SHA-1 collision-detection implementation with a new `sha1dc-accel` subsystem that uses vectorized (SSE2, AVX2, NEON) and hardware-accelerated (x86-64 SHA-NI, ARMv8 SHA-1) versions of the unavoidable-bit-conditions (UBC) check and SHA-1 compression steps. The goal is to reduce the collision-detection overhead from 1.5–2.5× down to 0.2× relative to OpenSSL SHA-1 (which lacks collision detection), yielding a 2.7–2.85× speedup in SHA-1 throughput and a ~50 % reduction in `index-pack` runtime.

Current status
Under review; no maintainer decision recorded. Series remains at v1. Johannes Schindelin has raised **two substantive technical objections** in earlier reviews: (1) code duplication in patch 1 (`compress_portable()` vs. `sha1_compression_states()`), and (2) maintainability concerns about the 1,789-line `ubc_check.c` tables, the latter now addressed by his Perl regeneration script. Schindelin subsequently provided a **substantive, tested optimization patch** for the x86-64 SHA-NI backend that closes most of the remaining performance gap between the C and Rust implementations, reducing `index-pack` runtime by an additional 1.8 % and leaving the C implementation only ~1 % slower than Rust. He explicitly endorses merging the series, marking a shift from his earlier technical objections to a clear supportive stance. Junio C Hamano raised a **policy blocker** regarding the licensing and provenance of the AI-generated C code; this blocker is now **fully addressed in principle** by (a) Scott Chacon’s confirmation that the original Rust author (Sam Reis) is aware of and supportive of the port, (b) Reis’s explicit endorsement, (c) confirmation that both the Rust and C implementations were produced using AI tooling within the Software Freedom Conservancy’s updated guidelines, and (d) a proposed update to Git’s AI policy submitted to align with those guidelines. Junio’s most recent reply acknowledges Schindelin’s contributions (Perl script, NEON readability suggestion) but does not record a maintainer position on either proposal or on the series’ readiness for integration. **A new policy question has been raised by D. Ben Knoble** regarding license compatibility between Git’s GPL-2 and the MIT-licensed `sha1dc` code, and whether the new `sha1dc-accel` code should adopt the same MIT license or be "license-washed" to GPL-2 to maintain consistency with Git’s licensing stance and downstream packaging practices (e.g., Gentoo’s GPL-2-only treatment of Git). Sam Reis’s latest response confirms that the UBC tables are autogenerated from the Stevens-Shumow paper and that MIT is GPL-compatible, but does not resolve whether the new code should retain the MIT license or adopt GPL-2; this question remains open and may require a maintainer ruling.

Open questions and loose ends
- Trade-off between code complexity (multiple platform backends, fallback paths, mirrored UBC check variants) and performance gains.
- Build-system integration (Makefile, Meson, CMake) correctness across platforms, particularly for less common toolchains and architectures (e.g., runtime detection on macOS vs. Linux, compiler support for target attributes).
- Real-world validation on non-Apple ARMv8 hardware (e.g., Graviton) would be beneficial.
- Code duplication in `compress_portable()` (patch 1) must be resolved by reusing `sha1_compression_states()` from the existing `sha1dc/` subsystem.
- Whether to include Schindelin’s Perl script in the series (either in this patch or a follow-up) to formalize table regeneration.
- Whether to fold Schindelin’s optimization patch into the original series or submit it as a follow-up. The technical trade-off is between code complexity (adding mirrored variants and runtime schedule reversal) and the modest but measurable performance gain.
- Licensing and provenance of the AI-generated C code are now **fully addressed in principle** by Reis’s explicit endorsement and Chacon’s prior policy proposal; no formal legal sign-off or maintainer Ack has been recorded yet.
- **License compatibility**: D. Ben Knoble raises the question of whether the new `sha1dc-accel` code should adopt the MIT license (to match the existing `sha1dc` code) or be "license-washed" to GPL-2 to align with Git’s licensing stance and downstream packaging practices (e.g., Gentoo’s GPL-2-only treatment of Git). Sam Reis confirms that MIT is GPL-compatible and that correct attribution should suffice, but does not address whether the new code should retain the MIT license or adopt GPL-2. This question remains unresolved and may require a maintainer ruling or broader project discussion.

This is a **bugfix follow-up** in the ongoing `mmfile_t` refactoring series. Jeff King (Peff) responds to Junio C Hamano’s review of patch 4/5, which exposed a latent error-handling bug: when an external merge driver claims success (exit code 0) but the output file is missing or unreadable, `read_mmfile()` leaves `result->ptr` as `NULL` yet returns `LL_MERGE_OK`. Some callers (like `rerere.c`) then pass the `NULL` pointer to `fwrite()`, triggering undefined behavior.

Peff confirms the bug is real and demonstrates a reproducer: a merge driver that writes to `%A` but then removes read permissions, causing `read_mmfile()` to fail. He agrees with Junio’s proposed fix—converting `LL_MERGE_OK` with a `NULL` buffer into `LL_MERGE_ERROR`—but suggests implementing it directly in `ll_ext_merge()` rather than centralizing the check in `ll_merge()`. His alternative patch (shown inline) forces a driver error (`status = 129`) if `read_mmfile()` fails, avoiding the need to modify every caller. The fix is narrow, touching only `merge-ll.c`, and preserves the series’ original goal of safe buffer handling while closing a correctness hole. No new tests are added, but the reproducer script provides a clear regression test for the edge case. The series remains under review, with patches 1 and 2 already acked by Junio.

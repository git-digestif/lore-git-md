This is a follow-up discussion in the ongoing effort to fix a bug in `git stash` where autostashing fails to correctly handle staged index entries when `stash.index=true` is set. The series, now in its third version, has been mostly ready for integration but was recently ejected from Junio’s `seen` branch due to a few issues—all but one of which have now been resolved.

The email zooms in on a now-resolved test breakage in `t5520-pull.sh` that surfaced when the stash series was merged into `seen`. The root cause was an interaction with the `tb/rerere-lock-grace` topic, specifically commit `2d1fa0323f`, which introduced an auto-maintenance step (`git maintenance run --auto`) that triggers `git reflog expire` under the test’s fixed `GIT_COMMITTER_DATE` (2005). This prematurely expired reflog entries that `git pull --rebase` relies on for fork-point detection, causing the rebase to misidentify the upstream commit and reintroduce four commits, leading to a conflict. The stash series’ tests generate eight fewer reflog entries (from failed merges due to the elimination of `git reset --quiet --refresh` calls), shifting the expiration timing and exposing the issue.

D. Ben Knoble’s email confirms the diagnosis and expresses surprise that `git pull --rebase` uses reflogs at all when an explicit `<upstream>` argument is provided, which should disable `--fork-point` (and thus reflog use). He traces the execution via `GIT_TRACE2` and observes that while the rebase command itself includes an `--onto` argument (which should disable `--fork-point`), the fork-point is still computed earlier via `git merge-base --fork-point refs/remotes/me/copy to-rebase`. This discrepancy is noted as an oddity but not a blocker for the series. The breakage itself is fully resolved by Thomas Bachem’s patch to pin `gc.reflogExpire` and `gc.reflogExpireUnreachable` to `never` in the test setup, which has since been merged to `master`.

The only remaining blocker for the stash series is a NULL-dereference risk in Patch 5/5, where `merge_incore_nonrecursive()` may return with `result.tree` uninitialized on catastrophic failure (e.g., missing objects), leading to a SIGSEGV. Junio’s audit of existing callers confirms this is a systemic omission in the patch’s error handling, and the author has agreed to address it by checking `result.clean` before dereferencing `result.tree`. This fix is expected shortly and will unblock integration. The series is otherwise technically complete, with all other issues—including a verbosity regression and a bisectability regression—now resolved.

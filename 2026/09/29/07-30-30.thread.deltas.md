## 2026/10/04

- [2026/10/04/09-54-10 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood endorsed using the git-cherry / `--cherry-mark` algorithm as the model, describing how `git cherry A...B` precalculates patch-ids from the side of the merge base with the fewest commits, walks the other side comparing them, skips patch-id calculation for commits whose changed paths cannot match, and batch-fetches needed blobs in partial clones; he noted the current implementation instead makes a separate upstream revision walk per branch and recalculates upstream diffs each time, which seems less efficient than it could be.
- [2026/10/04/09-54-10 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood cautioned that a branch rebased before merging may be altered such that it can no longer be detected, and for the squash case gave a tree/merge-base analysis (M^2^{tree} == topic^{tree}, matching merge-bases, and a right-only rev-list count of 1 for a squashed merge M), suggesting that in repositories with only non-rebased squash merges it would be much more efficient to compare trees and merge-bases, especially in blobless clones, with an option to turn off patch-id based detection.
- [2026/10/04/09-54-10 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood concluded that detecting squash- and/or rebase-merged branches is a useful improvement but needs careful implementation to be efficient enough to be practical in large repositories, and that he is unlikely to have time to closely review it.
- [2026/10/04/22-28-36 by Harald Nordgren <haraldnordgren@gmail.com>] Harald Nordgren agreed the per-branch upstream walk can be improved, said he is iterating on the code (sharing logic between branches, etc.) and that it became fast on his local Git repo, and asked whether, if there are no performance concerns, an option to turn off patch-id based detection would still be wanted — while adding that for users he imagines the interface should be as simple as possible.

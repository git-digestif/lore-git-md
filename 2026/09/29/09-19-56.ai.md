This is the second patch in the v4 series introducing a "matching-inspired" fetch mode for shallow repositories. It implements the core logic that infers which branches to fetch when a remote has a `remote.<name>.refmap` configured but no `remote.<name>.fetch` refspec.

The patch dynamically enumerates branches to fetch by scanning local branches whose `@{upstream}` points to the remote in question. This replaces the previous behavior (which would error out with "--refmap option is only meaningful with command-line refspec(s)") and enables the new fetch mode without requiring users to manually list branches in the configuration or on the command line. The forced inclusion of the remote’s default branch (a point of contention in v3) is removed, simplifying the design and avoiding awkward fetch report output.

Key changes are in `builtin/fetch.c` and `remote.c`. In `get_ref_map()`, the patch adds logic to build a temporary refspec (`inferred_rs`) from the list of branches tracking the remote, then uses that refspec to populate the fetch map. In `do_fetch()`, it updates the `ls-refs` command to request only the inferred branches, reducing network traffic. The new `branches_tracking_remote()` helper in `remote.c` iterates over local branches and collects their upstream refnames, while the test suite (`t/t5585-fetch-refmap.sh`) verifies the dynamic behavior, edge cases (duplicate branches, branches tracking other remotes), and compatibility with `git remote show`.

The patch is technically complete and addresses the last substantive design objection from Junio (the forced default-branch fetch). The implementation is clean and well-tested, with no obvious gaps or sloppiness. The only remaining open questions are edge-case handling (e.g., empty repositories) and whether the new mode should be available outside shallow repositories, but these are not blockers for merging. The series as a whole remains under review, with no merge status yet.

# Thread deltas

## 2026/09/29

- [2026/09/29/18-51-22 by Stanislav Aleksandrov <lightofmysoul@gmail.com>] Stanislav Aleksandrov submitted an RFC patch proposing that submodule URLs beginning with `^/` be resolved against the superproject's default remote from the root of the server (e.g., `^/org/lib.git` with remote `https://host/me/super.git` resolves to `https://host/org/lib.git`), preserving protocol, user, host and port, so that forking a superproject to a different depth does not break relative `../` URLs and absolute URLs do not force a single protocol; the proposal notes that `^/` fails for superprojects cloned from local paths, without a remote, or with `<transport>::<address>` remotes, and discusses compatibility costs and alternatives such as `/path`, `//host/path`, and `url.<base>.insteadOf`.

## 2026/10/25

- [2026/10/25/19-42-10 by Jacob Keller <jacob.keller@gmail.com>] Jacob Keller asked whether `.gitmodules` could be extended to carry insteadOf-style rewrite information, questioned what "refuses it" meant for the "^" character in `git submodule add`, noted that adding new special-character meanings is problematic though "^/" has SVN precedence, and asked whether multiple "../" segments are supported for reaching the server root.
- [2026/10/25/21-25-17 by Stanislav Aleksandrov <lightofmysoul@gmail.com>] Stanislav Aleksandrov answered that `.gitmodules` cannot carry a rewrite rule because it is identical for everyone while what differs per clone is the superproject's remote URL, which "../" and "^/" resolve against; clarified that "^" is a valid directory name and that `git submodule add` rejects "^/org/lib.git" ("must be absolute or begin with ./|../"), so such URLs must be written by hand or via `git submodule set-url` and since 2.38.1 cannot be cloned without `protocol.file.allow=always`; explained that relative URLs already preserve the clone protocol but follow the superproject's location, that forks (not URL changes) are the problem since they live in another namespace often at a different depth on GitLab, and that multiple ".." work but the count must match the superproject's depth, whereas "^/org/lib.git" resolves correctly at any depth (GitHub's fixed two-level depth makes "../../org/lib.git" work there, but GitLab and plain SSH servers have no fixed depth).
- [2026/10/25/23-11-28 by Jacob Keller <jacob.keller@gmail.com>] Jacob Keller acknowledged that with `protocol.file.allow` defaulting to "user" the likelihood of breaking existing "^"-path setups is very low, agreed that relative URLs break for forks while absolute paths force a protocol on everyone, agreed forks are the root cause, and concluded the "^/" concept makes sense (though driven partly by a specific forge's behavior) and could be useful on other forges in the future.

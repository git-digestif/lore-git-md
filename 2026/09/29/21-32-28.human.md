This is a follow-up in the RFC discussion about adding optional per-repository consent before running local hooks.

Brian M. Carlson weighs in with two practical concerns. First, he points out that the proposed interactive prompt would break non-interactive environments like CI systems or Docker containers, where no user is present to respond. Second, he echoes Junio’s earlier security objection: Git lacks a secure per-user data store, so any trust state stored in the repository’s config file could be manipulated by the same malicious process that installs the hooks. As a low-tech alternative, he suggests users could globally set `core.hooksPath` to `/dev/null` and then selectively re-enable hooks in trusted repositories by overriding the setting locally. While this doesn’t solve the tampering problem (a malicious repository could still override the local config), it gives users a manual way to block unwanted hooks without requiring new Git infrastructure. The tone is constructive, framing the proposal as well-intentioned but highlighting real-world deployment obstacles.

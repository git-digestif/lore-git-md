This is a substantive review reply in the ongoing RFC thread about optional per-repository consent for running local hooks.

Brian m. carlson expands the discussion by raising two critical operational concerns that the original proposal did not address. First, he points out that the proposed interactive prompt would break non-interactive environments like CI systems and Docker containers, where no user is present to respond. This is a fundamental usability issue for automated workflows that the RFC needs to resolve before any implementation can proceed.

Second, he echoes and reinforces Junio’s earlier security objection: Git currently lacks a secure per-user data store that could persist the proposed "trust state" without being vulnerable to manipulation by the same malicious process that installs hooks. Brian suggests a practical workaround—using `core.hooksPath=/dev/null` in either global or local config to disable hooks entirely for untrusted repositories—but acknowledges that even this can be overridden by a malicious repository. His framing ("I typically consider installing hooks without user consent to be malicious") underscores the seriousness with which he views the underlying problem, while his proposal to report such repositories to hosting providers shifts the burden of enforcement upstream.

The reply does not propose a revised design or attempt to reconcile the security and usability tensions; it instead highlights them as unresolved blockers that any eventual implementation must address. The thread remains in the conceptual phase, with no patches or concrete configuration keys yet on the table.

This thread is an early-stage RFC by Dmytro Lymarenko proposing an opt-in safety mechanism to require explicit user consent before Git runs local hooks in untrusted repositories. The idea is to prompt users with the hook’s path, offering options to run once, trust all hooks in the repository, or decline—with re-prompts if in-worktree hooks are modified. Default behavior would remain unchanged.

Junio C Hamano has raised a fundamental security concern: if a malicious tool can install hooks, it could also manipulate the proposed trust mechanism, rendering the protection ineffective. Brian m. carlson has since expanded the discussion with two critical operational issues. First, the interactive prompt would break non-interactive environments like CI systems and Docker containers, where no user is present to respond. Second, he reinforces Junio’s security objection, noting that Git lacks a secure per-user data store to persist trust state without vulnerability to tampering. While he suggests `core.hooksPath=/dev/null` as a workaround for untrusted repositories, he acknowledges this can also be overridden by malicious actors. The thread remains conceptual, with no implementation or revised design proposed yet. Key questions—such as how to securely persist trust state, handle mandatory hooks, and avoid breaking automation—remain unresolved.

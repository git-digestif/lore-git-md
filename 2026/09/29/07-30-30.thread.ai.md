Core problem or goal
Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows. The series aims to provide a practical, one-step repository maintenance command for common forge and local workflows. Junio C Hamano’s latest review **proposes a fundamental conceptual split**: preserve the existing `--delete-merged` as a **strict, tip-reachability-only** command (safe, conservative) and introduce a new `--delete-irrelevant` option for **looser, change-based detection** (riskier, ambiguous). Harald Nordgren’s v3 implementation treats squash and rebase detection as a unified feature under `--delete-merged`, but Junio now argues they represent **distinct user intents** with different safety guarantees. Harald’s latest replies push back, arguing that the mechanism of integration (squash, rebase, or verbatim merge) should not matter: once a branch’s changes are upstream, the branch is no longer needed, and the user can recover the work from the mainline if needed. This reflects a **pragmatic vs. conservative** divide: Harald prioritizes workflow efficiency (deleting branches once their changes are upstream), while Junio prioritizes safety and predictability (strict vs. loose definitions of "merged"). Jasper Mayone’s latest user report **reinforces Junio’s safety concerns** by demonstrating a persistent real-world false positive: v3 still deletes a branch whose changes were independently implemented by another author, even without `--squashed`, because the tree-based diffing finds the file contents in an unrelated commit. The series retains all v2/v3 improvements: performance optimizations (batching via `changed_paths` slab, blob fetching), correctness fixes, the `--squashed` flag (now opt-in), and expanded documentation/test coverage. Junio’s example — an AI-generated patch series that becomes irrelevant because someone else independently solved the same problem — illustrates the real-world ambiguity the feature would need to handle.

Current status
Under review; v3 posted and complete. The **second patch (rebase detection)** and **third patch (squash detection)** are now explicitly confirmed in detail:
- **Rebase detection** (second patch): Uses fast tree-based diffing to check whether every file changed by the branch matches the version in some upstream commit since the fork point. This handles "rebase and merge" workflows (e.g., GitHub’s "Rebase and merge" button) without reading file contents, ensuring it remains cheap even in partial clones. The output format is extended to show where the work landed: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`. Internally, the patch introduces a `landing_search` structure, a `changed_paths` commit slab, and helper functions (`collect_branch_changes`, `find_landed_commit`) that batch the work across all candidate branches.
- **Squash detection** (third patch): Introduces the `--squashed` flag (opt-in, defaults to off) and implements squash detection via a path-by-path three-way merge between the branch’s version, the upstream version, and the fork point. If the merge leaves the upstream version unchanged, the branch’s changes are considered "landed" and the branch is eligible for deletion. This approach is intentionally lenient: it checks whether the upstream commit *contains* the branch’s changes, not whether it is *exactly* the result of a squash merge. The leniency may lead to false positives (e.g., attributing a branch’s changes to an unrelated upstream commit that happens to include them) but avoids the complexity and performance cost of stricter methods like test merges or patch IDs. The implementation adds a `DELETE_BRANCH_SQUASHED` flag, extends the `branch_change` structure, and introduces helper functions (`merge_keeps_upstream`, `change_state_at`) to handle the three-way merge logic. Blob fetches are batched and only performed when `--squashed` is used.

Junio’s latest review proposes a **fundamental CLI redesign**: decouple the strict `--delete-merged` (tip-reachability only) from a new `--delete-irrelevant` (change-based detection for rebases, squash merges, and cherry-picks). Harald’s v3 **rejects this split**, implementing both rebase and squash detection under `--delete-merged` with `--squashed` as an opt-in flag (defaults to off). Jasper Mayone’s latest report confirms the series is feature-complete and performs as documented, but **persistent false positives** (even without `--squashed**) reinforce Junio’s argument that looser detection should not be the default. This reflects his **pragmatic stance** but does not address Jasper’s core concern—that the false positive undermines the feature’s safety and predictability. Harald also **rejects Jasper’s `--landed=<kind>` proposal**, calling it "pushing it in terms of UX mental load," and prefers a simple, opinionated tool where users opt into looser detection via `--squashed`.

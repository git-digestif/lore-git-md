Core problem or goal: Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows, including cases where upstream modified the same files before integration. The CLI design is finalized: `--delete-merged <pattern>` for strict tip-reachability (unchanged) and `--delete-integrated <pattern>` for change-based detection of rebased and squashed branches (opt-in, mutually exclusive with `--delete-merged`). The series splits strict and change-based behaviors into separate flags to prevent `--delete-merged` from deleting branches whose changes were independently implemented by another author. Patch 4/5 implements the rebase-detection half using purely tree-based comparison (no blob fetches); patch 5/5 (the current email) implements the squash-detection half using a path-by-path three-way merge approximation via `xdl_merge()` guarded by `mergeable_as_text()`, ignoring merge drivers from `.gitattributes`.

Current status: v10 posted and complete with all five patches processed; patch 5/5 is the final patch implementing squash-merge detection on top of the rebase detection from patch 4/5. It adds the `DELETE_BRANCH_INTEGRATED` flag bit and a `delete_integrated` strvec parsed from the command line. When active, `delete_merged_branches()` in `builtin/branch.c` collects candidate branches failing the usual tip-reachability check into a `landing_search` array, then calls `find_landed_commits()` to scan upstream history. For each branch, `collect_branch_changes()` diffs the merge base against the branch tip to record every changed path with its blob OID and mode in a `branch_change` array. `find_landed_commit()` walks upstream commits in reverse (via `rev-list --reverse`), using a `changed_paths` commit slab to skip commits that do not touch any of the branch's changed paths, and checks whether any single upstream commit's tree contains the exact branch version (OID and mode) of every changed file via `changes_landed()` and `change_landed()`. The first matching commit is stored in a `strmap` keyed by branch name, which `delete_branches()` (extended in patch 2/5) consults to skip the reachability check and print `Deleted branch %s (was %s, landed as %s)`. Patch 5/5 extends this to squash merges: `changes_landed()` now operates in two passes, first classifying each path via `change_state_at()` (exact match yields `CHANGE_LANDED`, absence yields `CHANGE_MISSING`, differing regular file yields `CHANGE_NEEDS_MERGE`), then for `CHANGE_NEEDS_MERGE` paths calling `merge_keeps_upstream()` which performs a three-way `xdl_merge()` with `XDL_MERGE_ZEALOUS` between merge-base, upstream, and branch versions, treating the change as landed only when the merge result is byte-identical to the upstream version. The merge deliberately ignores `.gitattributes` merge drivers (preventing both false positives from drivers like `union` and arbitrary command execution), and `mergeable_as_text()` rejects files exceeding `MAX_XDIFF_SIZE` or containing binary content. Because this reads blob contents, partial clones may download objects. Patch 3/5 (previously processed) relaxed `--dry-run` to work with plain `-d`/`-D` by changing validation to `if (dry_run && !delete && !delete_merged.nr)` and adding the `DELETE_BRANCH_DRY_RUN` flag. Patch 2/5 added the `landed_commits` strmap parameter to `delete_branches()`. Patch 1/5 extracted the `branch.<name>.deleteMerged=false` opt-out check into `opted_out_of_delete_merged()`. The series remains under review with no integration status announced. Junio's question about whether `branch.<name>.deleteMerged` is the right config key for `--delete-integrated` (versus `deleteDone`) remains unanswered, and the "npm update" false-positive mitigation is still not implemented.

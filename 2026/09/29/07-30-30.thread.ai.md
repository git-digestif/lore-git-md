Thread identity: Subject: [PATCH v9 0/4] branch --delete-merged: detect squash-merged and rebase-merged branches. Series version: v9 (four patches; v9 is a bugfix iteration incorporating the gitlink-to-blob crash fix). Originating author: Harald Nordgren. Thread type: patch series with architectural, CLI-design, user-experience, performance, and correctness discussion.

Core problem or goal: Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows, including cases where upstream modified the same files before integration. The CLI design is finalized: `--delete-merged <pattern>` for strict tip-reachability (unchanged) and `--delete-integrated <pattern>` for change-based detection of rebased and squashed branches (opt-in, both methods enabled by default). The series splits strict and change-based behaviors into separate flags to prevent `--delete-merged` from deleting branches whose changes were independently implemented by another author. Upstream modification handling uses a path-by-path three-way merge approximation via `ll_merge()` with correct `.gitattributes` support, single index read for performance, and explicit documentation of attribute-resolution and partial-clone blob-fetching behavior.

Current status: v9 posted and complete, incorporating Jasper Mayone's fix for the confirmed gitlink-to-blob crash identified in v8. CLI design finalized and confirmed by Junio. Patches 1/4 (refactoring) and 2/4 (landing-message helper) are explicitly uncontroversial and ready for integration, though Junio has raised design concerns about the helper naming and default semantics in patch 1/4, and provided advisory code-structure feedback on patch 2/4 (approving the empty `if` body for `--quiet`, and suggesting a two-dimensional message-template array to flatten control flow) that is polish rather than a required fix. Key technical details: Files touched: `builtin/branch.c`, `Documentation/git-branch.adoc`, `Documentation/config/branch.adoc`, `t/t3200-branch.sh`. New behavior: `--delete-merged <pattern>` (strict tip-reachability only, unchanged); `--delete-integrated <pattern>` (change-based detection for rebased and squashed branches, cannot be combined with `--delete-merged`). Output format: `Deleted branch %s (was %s, landed as %s)`. Config: `branch.<name>.deleteMerged` applies to both flags. `--dry-run` works with either. Symbols and internals (v9 3/4 core machinery): `DELETE_BRANCH_INTEGRATED` flag; `delete_integrated` strvec parsed from `--delete-integrated <pattern>`; `landing_search` struct; `branch_change` array recording each branch's modified paths and blob OIDs relative to merge base; `changed_paths` commit slab caching which paths each upstream commit touches; `change_state` enum; `find_landed_commits()` computes merge bases, collects changed paths, walks upstream commits in reverse; `find_landed_commit()` checks whether any single upstream commit contains the branch's exact version of every changed file using `changes_landed()` and `change_landed()` tree-entry comparisons; when found, branch name mapped to landing commit in a `strmap`. Patch 1/4: extracts the `branch.<name>.deleteMerged=false` opt-out check from `delete_merged_branches()` into a new static helper `branch_opted_out(struct strbuf *key, const char *branch_name, unsigned int flags)` in `builtin/branch.c` (19 insertions, 13 deletions), which performs the config lookup and prints the "Skipping" message unless `DELETE_BRANCH_QUIET` is set; behavior-neutral refactoring to enable reuse by patch 3/4. Patch 2/4: `delete_branches()` extended with optional `struct strmap *landed_commits` parameter; skips `check_branch_commit()` for mapped branches and reports `landed as %s` using `strmap_get()` and `repo_find_unique_abbrev()`; behavior-neutral for existing callers passing `NULL`. Patch 4/4: `merge_keeps_upstream()` function in `builtin/branch.c` using `ll_merge()` for path-by-path three-way merge approximation with `.gitattributes` support; reads base, upstream, and branch blobs via `read_mmblob()` and invokes `ll_merge()` with the repository index; a change counts as landed only when the merge result is byte-identical to the upstream blob (`result.size == upstream.size && !memcmp(...)`); index read once before walk in `find_landed_commits()` via `repo_read_index()`. The `branch_change` struct gains `base_oid`, `base_mode`, `upstream_oid`, and `state` fields (v9 adds `base_mode`), with `change_state` enum values `CHANGE_MISSING`, `CHANGE_LANDED`, `CHANGE_NEEDS_MERGE`. `changes_landed()` runs in two passes: first checking for exact tree-entry matches via `change_state_at()`, then invoking `merge_keeps_upstream()` only for paths marked `CHANGE_NEEDS_MERGE`. The v9 fix adds `unsigned short base_mode` to `struct branch_change`, populates it in `collect_branch_changes()` from `p->one->mode` (the diff's `p->one` side), and extends the guard in `change_state_at()` to return `CHANGE_MISSING` when `!S_ISREG(change->base_mode)`, preventing `read_mmblob()` from being called on a commit OID when a path changed from gitlink (submodule) to regular file, which previously caused `fatal: unable to read blob object`. Documentation in `Documentation/git-branch.adoc` explicitly notes that merge-based detection reads file contents and may download blobs in partial clones.

Algorithmic considerations: Rebase detection is tree-based (no blob fetches) using exact tree-entry comparisons of changed files; the author-check mitigation or patch IDs remain required to address the "npm update" false-positive scenario but are not yet implemented. Squash detection uses `ll_merge()` which may download blobs in partial clones (explicitly documented); lacks rename detection. Test coverage expanded in `t/t3200-branch.sh` (315 lines total) covering rebase-merged, squash-merged onto upstream-modified files (expecting deletion with "landed as" attribution), reverted, partial-landing, unmerged, conflicting, "npm update" scenarios, and the gitlink-to-blob regression test added in v9 (branch replaced a submodule with a file while upstream did the same, expecting the branch to be kept).

Junio's design concerns on patch 1/4 remain open with three specific resolution paths he proposed for the `branch_opted_out` helper naming/impedance mismatch: (1) rename the function to explicitly reference `deleteMerged`, (2) make the function truly generic for any destructive operation and rename the config key to something like `noClobber`, or (3) keep the generic name but pass the operation as a parameter (e.g., `branch_opted_out("main", "deleteMerged")`) with the function remaining a pure boolean check without operation-specific side effects. The default return value semantics are also contested: when `branch.<name>.deleteMerged` is missing or true the function returns false (not opted out), but Junio argues that absent an explicit "I am fine losing this" the branch should be treated as precious. Junio's advisory suggestion on patch 2/4 to restructure message selection via a two-dimensional array indexed by dry-run flag remains open but is non-blocking polish.

Subject: [PATCH v3 0/3] branch --delete-merged: detect squash-merged and rebase-merged branches
Series version: v3 (three patches: preparatory refactoring, rebase detection, squash detection; CLI now finalized as `--delete-merged <pattern>` for strict tip-reachability and `--delete-integrated <pattern>` for change-based detection of rebased *and* squashed branches)
Originating author: Harald Nordgren
Thread type: patch series with architectural, CLI-design, and user-experience discussion

Core problem or goal
Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows. The series provides a practical, one-step repository maintenance command for common forge and local workflows. Junio C Hamano’s reproducible test case demonstrates a critical false-positive scenario: the current implementation incorrectly deletes a branch whose changes were independently implemented by another author, even without the `--squashed` flag. This test case, reinforced by D. Ben Knoble’s real-world "npm update" scenario (identical commits from separate PRs rebased onto `main`), quantifies the safety trade-off of the current algorithm’s leniency (checking for *containment* of changes rather than *exact* integration). Harald Nordgren’s latest replies narrow the scope of the "npm update" scenario to automated, deterministic scripts (e.g., dependency bumps), but accept the scenario as plausible and reinforce the need for **author checks** or **patch IDs** as potential mitigations. The CLI design has now **finalized**: `--delete-merged <pattern>` for strict tip-reachability (current behavior, unchanged) and `--delete-integrated <pattern>` for change-based detection of rebased *and* squashed branches (no granular modes or config variable). Junio C Hamano’s latest reply **endorses this design**, and Harald Nordgren’s most recent email **confirms the syntax constraint**, eliminating hierarchical or config-based approaches that would reuse the `--delete-merged` flag.

Current status
Under review; v3 posted and complete. The **first patch (refactoring)** remains uncontroversial and ready for integration. The **second (rebase detection)** and **third (squash detection)** patches are explicitly confirmed but require implementation of the **author-check mitigation** and test suite updates to reflect the new CLI design. The CLI design is now **finalized** as follows:
- `--delete-merged <pattern>`: strict tip-reachability only (current behavior, unchanged).
- `--delete-integrated <pattern>`: change-based detection for rebased *and* squashed branches (no granular modes or config variable; both methods enabled by default).

The **false-positive issue** (branches incorrectly deleted because another author independently made the same change) is addressed by Jasper Mayone’s **author-based mitigation proposal**: require that the landing commit’s author also authored at least one commit on the branch being deleted. This would reject false positives in forge workflows (where squash/rebase buttons preserve the PR author) while still allowing manually applied patches (`git am`, which preserves authorship). The proposal directly addresses the "npm update" scenario (identical commits from separate PRs) and Junio’s test case, both of which expose the algorithm’s current leniency. The next steps involve:
- Implementing the **author-check mitigation** into the `--delete-integrated` logic.
- Updating the test suite to reflect the new behavior, including Knoble’s "npm update" scenario, Junio’s false-positive test case, and the author-check mitigation.
- Addressing the **performance trade-offs** of the new flag (e.g., whether to use `git range-diff`, patch IDs, or author checks for rebase detection).

Key changes from v2:
- **CLI**: `--squashed` flag (opt-in, defaults to off) is **replaced by `--delete-integrated <pattern>`**, which enables both rebase *and* squash detection by default. The clean separation between `--delete-merged` (strict tip-reachability) and `--delete-integrated` (change-based detection) is now the **finalized design**, endorsed by Junio and confirmed by Harald. **No config variable** is provided for intermediate levels (e.g., only rebased branches); users must opt into the full change-based detection or use the strict `--delete-merged`. The syntax constraint (using `<pattern>` to specify the upstream branch) **precludes hierarchical or config-based approaches** that would reuse the `--delete-merged` flag.
- **Architecture**: Split into three patches to separate preparatory refactoring, rebase detection, and squash detection. Both detection patches are explicitly confirmed: rebase detection uses fast tree-based diffing, and squash detection uses a three-way merge approximation. The **rebase-detection logic** will incorporate **author checks** (Jasper’s proposal) or **patch IDs** (Knoble’s proposal) to address the "npm update" scenario.
- **Performance**: Batching optimizations (via `changed_paths` slab) and blob fetching preserved. Harald’s experiment with `git range-diff` for rebase detection revealed a **20× slowdown**, confirming that tree-based diffing remains the only viable approach for `--delete-merged` due to performance constraints. The performance trade-offs for `--delete-integrated` (e.g., whether to use `git range-diff`, patch IDs, or author checks) remain unaddressed, but Jasper’s author-check proposal is expected to have minimal performance impact.
- **Correctness**: Junio’s test case and Knoble’s "npm update" scenario expose critical false positives in the current implementation, even without `--squashed`. The test expects the branch to be preserved but fails under the current algorithm, reinforcing the argument that looser detection should not be the default. Harald’s latest replies **narrow the scope** of the "npm update" scenario to automated scripts but accept the scenario as plausible and reinforce the need for **author checks** or **patch IDs** to mitigate the risk. Jasper’s author-check proposal directly addresses this issue.
- **Usability**: Output format unchanged (`Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`). Jasper’s usability suggestions (clearer worktree messages, reusable helper logic) remain unaddressed.
- **Documentation**: Expanded examples for local `git merge --squash` and GitHub-style squash merges preserved. Phillip Wood’s call for clearer documentation of the algorithm’s limitations remains unaddressed.

Key technical details
- Files touched: `builtin/branch.c` (split into distinct detection code paths; first patch refactors `branch_opted_out()` helper; second patch implements rebase detection with `landing_search` structure and `changed_paths` commit slab; third patch adds squash detection with `DELETE_BRANCH_SQUASHED` flag), `Documentation/git-branch.adoc` (expanded examples), `t/t3200-branch.sh` (expanded test coverage, including Junio’s test case, Knoble’s "npm update" scenario, and the author-check mitigation).
- New behavior:
  - `--delete-merged <pattern>`: strict tip-reachability only (current behavior, unchanged).
  - `--delete-integrated <pattern>`: change-based detection for rebased *and* squashed branches (no granular modes or config variable; both methods enabled by default). The **author-check mitigation** (Jasper’s proposal) will require that the landing commit’s author also authored at least one commit on the branch being deleted, addressing the false-positive issue.
- Output format: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)` (may attribute the topic commit to a commit with unrelated modifications due to the algorithm’s leniency, but the author-check mitigation will reduce false positives).
- Performance optimizations: Uses a `changed_paths` commit slab to cache diff results, avoids redundant calculations, and processes all branches in a single pass. The **rebase-detection patch** uses fast tree-based diffing, avoiding blob fetches and ensuring performance in partial clones. The **squash-detection patch** batches blob fetches and only performs them when `--delete-integrated` is enabled. Harald’s experiment with `git range-diff` for rebase detection revealed a **20× slowdown**, confirming that tree-based diffing remains the only viable approach for `--delete-merged` due to performance constraints. The performance trade-offs for `--delete-integrated` (e.g., whether to use `git range-diff`, patch IDs, or author checks) remain unaddressed, but Jasper’s author-check proposal is expected to have minimal performance impact.
- Edge cases handled: Upstream modifications to the same files as the squashed branch, reverted changes, partial landings, mixed workflows, Knoble’s "npm update" scenario (identical commits from separate PRs rebased onto `main`), and automated scripts (e.g., dependency bumps). Blobless clone support via transparent blob fetching (only when `--delete-integrated` is enabled). The **author-check mitigation** will handle forge workflows (where squash/rebase buttons preserve the PR author) and manually applied patches (`git am`, which preserves authorship). The algorithm’s leniency may still lead to misleading attribution in cases where the upstream commit includes additional changes beyond those from the branch tip, but the author-check mitigation will reduce false positives.
- Test coverage: Expanded in `t/t3200-branch.sh`; scenarios include local `git merge --squash`, GitHub-style squash merges, rebases, upstream file modifications, Junio’s false-positive test case, Knoble’s "npm update" scenario, automated scripts, and the author-check mitigation. The test expects the branch to be preserved but fails under the current implementation, confirming the safety issue.
- New CLI options:
  - `--delete-integrated <pattern>`: change-based detection for rebased *and* squashed branches (no granular modes or config variable; both methods enabled by default). The **author-check mitigation** will be incorporated into this flag’s logic.
- Symbols: No new or renamed public symbols; internal logic split into distinct code paths for rebase and squash detection. The first patch introduces the `branch_opted_out()` helper. The **rebase-detection patch** introduces the `landing_search` structure and `changed_paths` commit slab. The **squash-detection patch** introduces the `DELETE_BRANCH_SQUASHED` flag.
- **Algorithmic considerations**:
  - **Rebase detection**: Uses fast tree-based diffing to check for exact file matches. Junio’s proposal to reuse `git range-diff` logic for `--delete-integrated` remains unaddressed; Harald’s experiment showed `git range-diff` is **20× slower**, making it impractical for `--delete-merged` but potentially viable for `--delete-integrated`. Knoble’s **patch-ID proposal** (to handle local rebases with edited messages) and **author checks** (to handle GitHub-style rebases with identical commits) are also unaddressed. Harald now reinforces the need for **author checks** or **patch IDs** to mitigate the "npm update" scenario, and Jasper’s author-check proposal offers a concrete mitigation.
  - **Squash detection**: Uses path-by-path three-way merge approximation via `merge_ll()`, which lacks rename detection and is intentionally lenient (checks for *containment* of changes rather than *exact* squash-merge equivalence). Junio’s test case and Knoble’s scenario demonstrate that this leniency leads to false positives, even without `--squashed`. The **author-check mitigation** will reduce false positives by requiring that the landing commit’s author also authored at least one commit on the branch being deleted. The algorithmic trade-offs for `--delete-integrated` (e.g., whether to use patch-ids or test merges) remain unaddressed.

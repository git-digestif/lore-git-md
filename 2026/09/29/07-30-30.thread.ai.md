Core problem or goal
Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows. The series aims to provide a practical, one-step repository maintenance command for common forge and local workflows. Junio C Hamano’s latest review **provides a reproducible test case** demonstrating a critical false-positive scenario: the current implementation incorrectly deletes a branch whose changes were independently implemented by another author, even without the `--squashed` flag. This test case reinforces Junio’s earlier proposal to **decouple the strict `--delete-merged` (tip-reachability only) from a new `--delete-irrelevant` (change-based detection)**. Harald Nordgren’s v3 implementation treated squash and rebase detection as a unified feature under `--delete-merged`, but Junio’s test case now **quantifies the safety trade-off** of this approach, showing that the current algorithm’s leniency (checking for *containment* of changes rather than *exact* integration) leads to misleading and potentially harmful behavior. Harald’s latest reply **concedes the safety issue** and accepts the need for a CLI split, proposing a minimal `--delete-irrelevant` flag (without granularity) to address the false-positive risk.

Key technical details
- Files touched: `builtin/branch.c` (split into distinct detection code paths; first patch refactors `branch_opted_out()` helper; second patch implements rebase detection with `landing_search` structure and `changed_paths` commit slab; third patch adds squash detection with `DELETE_BRANCH_SQUASHED` flag), `Documentation/git-branch.adoc` (expanded examples), `t/t3200-branch.sh` (expanded test coverage, including Junio’s new test case for the false-positive scenario).
- New behavior: `--delete-merged` will be restored to strict tip-reachability only (no change-based detection). A new `--delete-irrelevant` flag (no granularity) will enable change-based detection for squash merges, rebases, and other workflows. It is unclear whether `--delete-irrelevant` will enable both squash *and* rebase detection by default or require explicit opt-in for each.
- Output format: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)` (may attribute the topic commit to a commit with unrelated modifications due to the algorithm’s leniency).
- Performance optimizations: Uses a `changed_paths` commit slab to cache diff results, avoids redundant calculations, and processes all branches in a single pass. The **rebase-detection patch** uses fast tree-based diffing, avoiding blob fetches and ensuring performance in partial clones. The **squash-detection patch** batches blob fetches and only performs them when `--squashed` is used (or when `--delete-irrelevant` is enabled). Harald’s experiment with `git range-diff` for rebase detection revealed a **20× slowdown**, confirming that tree-based diffing remains the only viable approach for `--delete-merged` due to performance constraints. The performance trade-offs for `--delete-irrelevant` remain unaddressed.
- Edge cases handled: Upstream modifications to the same files as the squashed branch, reverted changes, partial landings, and mixed workflows. Blobless clone support via transparent blob fetching (only when `--squashed` is used or `--delete-irrelevant` is enabled). The algorithm’s leniency may lead to misleading attribution in cases where the upstream commit includes additional changes beyond those from the branch tip, as demonstrated by Junio’s test case.
- Test coverage: Expanded in `t/t3200-branch.sh`; scenarios include local `git merge --squash`, GitHub-style squash merges, rebases, upstream file modifications, and Junio’s new test case for the false-positive scenario. The test expects the branch to be preserved but fails under the current implementation, confirming the safety issue.
- New CLI option: `--squashed` to enable squash detection (defaults to off) will be replaced or supplemented by `--delete-irrelevant` in the revised series. Jasper proposes a granular `--landed=<kind>` option (e.g., `--landed=squash`) as an alternative.
- Symbols: No new or renamed public symbols; internal logic split into distinct code paths for rebase and squash detection. The first patch introduces the `branch_opted_out()` helper. The **rebase-detection patch** introduces the `landing_search` structure and `changed_paths` commit slab. The **squash-detection patch** introduces the `DELETE_BRANCH_SQUASHED` flag.
- **Algorithmic considerations**:
  - **Rebase detection**: Uses fast tree-based diffing to check for exact file matches. Junio’s proposal to reuse `git range-diff` logic for `--delete-irrelevant` remains unaddressed; Harald’s experiment showed `git range-diff` is **20× slower**, making it impractical for `--delete-merged` but potentially viable for `--delete-irrelevant`. D. Ben Knoble’s proposal to use **patch IDs** for rebase detection (to handle local rebases with edited messages) is also unaddressed.
  - **Squash detection**: Uses path-by-path three-way merge approximation via `merge_ll()`, which lacks rename detection and is intentionally lenient (checks for *containment* of changes rather than *exact* squash-merge equivalence). Junio’s test case demonstrates that this leniency leads to false positives, even without `--squashed`. The algorithmic trade-offs for `--delete-irrelevant` remain unaddressed.

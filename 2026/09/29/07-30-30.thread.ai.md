Core problem or goal
Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows. The series aims to provide a practical, one-step repository maintenance command for common forge and local workflows. Junio C Hamano’s latest review **provides a reproducible test case** demonstrating a critical false-positive scenario: the current implementation incorrectly deletes a branch whose changes were independently implemented by another author, even without the `--squashed` flag. This test case reinforces Junio’s earlier proposal to **decouple the strict `--delete-merged` (tip-reachability only) from a new `--delete-irrelevant` (change-based detection)**. Harald Nordgren’s v3 implementation treats squash and rebase detection as a unified feature under `--delete-merged`, but Junio’s test case now **quantifies the safety trade-off** of this approach, showing that the current algorithm’s leniency (checking for *containment* of changes rather than *exact* integration) leads to misleading and potentially harmful behavior.

Current status
Under review; v3 posted and complete. The **second patch (rebase detection)** and **third patch (squash detection)** remain explicitly confirmed:
- **Rebase detection** (second patch): Uses fast tree-based diffing to check whether every file changed by the branch matches the version in some upstream commit since the fork point. This handles "rebase and merge" workflows without reading file contents, ensuring performance in partial clones. The output format remains `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`.
- **Squash detection** (third patch): Introduces the `--squashed` flag (opt-in, defaults to off) and implements squash detection via a path-by-path three-way merge between the branch’s version, the upstream version, and the fork point. The algorithm checks whether the upstream commit *contains* the branch’s changes, not whether it is *exactly* the result of a squash merge. This leniency avoids the complexity of stricter methods but may lead to false positives (e.g., attributing a branch’s changes to an unrelated upstream commit).

Junio’s latest review **adds a test case** (`t/t3200-branch.sh`) that exposes a critical false positive: the current implementation deletes a branch (`unrelated-topic`) whose changes were independently implemented by another author, even without `--squashed`. The test sets up a repository where:
- A private branch (`unrelated-topic`) adds two files (`file` and `elif`).
- The upstream branch (`next`) independently adds a file with identical content to `file` under a different author identity.
- Running `git branch --delete-merged origin/next` incorrectly deletes `unrelated-topic`, violating the principle of least surprise. The test expects the branch to be preserved, confirming that the current algorithm’s leniency is unsafe for the default behavior.

Junio’s patch reverts the loosened behavior of `--delete-merged` (restoring strict tip-reachability) and makes the test pass, demonstrating that the false positive is a direct consequence of the current implementation. This test case **shifts the burden of proof** to the author: the series must now either adopt the CLI split or justify why the false-positive risk is acceptable for the default behavior. The first patch (refactoring) remains uncontroversial and ready for integration.

Key technical details
- Files touched: `builtin/branch.c` (split into distinct detection code paths; first patch refactors `branch_opted_out()` helper; second patch implements rebase detection with `landing_search` structure and `changed_paths` commit slab; third patch adds squash detection with `DELETE_BRANCH_SQUASHED` flag), `Documentation/git-branch.adoc` (expanded examples), `t/t3200-branch.sh` (expanded test coverage, including Junio’s new test case for the false-positive scenario).
- New behavior: `--delete-merged` detects rebase merges by default (fast tree-based diffing) and squash merges only when `--squashed` is provided (three-way merge approximation). The `--squashed` flag is opt-in (defaults to off) and rejected if used without `--delete-merged`.
- Output format: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)` (may attribute the topic commit to a commit with unrelated modifications due to the algorithm’s leniency).
- Performance optimizations: Uses a `changed_paths` commit slab to cache diff results, avoids redundant calculations, and processes all branches in a single pass. The **rebase-detection patch** uses fast tree-based diffing, avoiding blob fetches and ensuring performance in partial clones. The **squash-detection patch** batches blob fetches and only performs them when `--squashed` is used. Harald’s experiment with `git range-diff` for rebase detection revealed a **20× slowdown**, confirming that tree-based diffing remains the only viable approach for `--delete-merged` due to performance constraints.
- Edge cases handled: Upstream modifications to the same files as the squashed branch, reverted changes, partial landings, and mixed workflows. Blobless clone support via transparent blob fetching (only when `--squashed` is used). The algorithm’s leniency may lead to misleading attribution in cases where the upstream commit includes additional changes beyond those from the branch tip, as demonstrated by Junio’s test case.
- Test coverage: Expanded in `t/t3200-branch.sh`; scenarios include local `git merge --squash`, GitHub-style squash merges, rebases, upstream file modifications, and Junio’s new test case for the false-positive scenario. The test expects the branch to be preserved but fails under the current implementation, confirming the safety issue.
- New CLI option: `--squashed` to enable squash detection (defaults to off). Jasper proposes a granular `--landed=<kind>` option (e.g., `--landed=squash`) as an alternative.
- Symbols: No new or renamed public symbols; internal logic split into distinct code paths for rebase and squash detection. The first patch introduces the `branch_opted_out()` helper. The **rebase-detection patch** introduces the `landing_search` structure and `changed_paths` commit slab. The **squash-detection patch** introduces the `DELETE_BRANCH_SQUASHED` flag.
- **Algorithmic considerations**:
  - **Rebase detection**: Uses fast tree-based diffing to check for exact file matches. Junio’s proposal to reuse `git range-diff` logic for `--delete-irrelevant` remains unaddressed; Harald’s experiment showed `git range-diff` is **20× slower**, making it impractical for `--delete-merged`. D. Ben Knoble’s proposal to use **patch IDs** for rebase detection (to handle local rebases with edited messages) is also unaddressed.
  - **Squash detection**: Uses path-by-path three-way merge approximation via `merge_ll()`, which lacks rename detection and is intentionally lenient (checks for *containment* of changes rather than *exact* squash-merge equivalence). Junio’s test case demonstrates that this leniency leads to false positives, even without `--squashed`.

Core problem or goal
Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges (GitHub-style or local `git merge --squash`), rebases, or patch-based workflows. The v3 series splits the implementation into distinct patches for rebase-and-merge detection and squash-merge detection, addressing Junio C Hamano’s architectural concern that the two workflows require fundamentally different algorithms. The series retains all v2 improvements: performance optimizations (batching via `changed_paths` slab, blob fetching), correctness fixes, the `--no-squashed` flag, and expanded documentation/test coverage. Junio’s review of v2 suggested reusing `git range-diff` logic for rebase detection and locally simulating squash merges or using message-based matching for squash detection. Phillip Wood’s review highlighted that the current squash-merge detection algorithm (path-by-path three-way merge approximation via `merge_ll()`) lacks rename detection and is less strict than alternatives like patch-ids or test merges. Harald Nordgren’s latest clarification confirms that the algorithm checks whether the upstream commit *contains all changes* from the branch tip, rather than whether it is *exactly* the result of a squash merge, which may lead to misleading attribution in the output (e.g., `landed as` pointing to a commit with unrelated modifications). Harald argues that rename detection is not a reliable signal for branch integration, as some topics intentionally introduce renames and should not be deleted even if their changes are otherwise upstream. The broader user need—a high-level, one-step repository maintenance command (`git full-clean`)—remains conceptual and is not part of this series.

Key technical details
- Files touched: `builtin/branch.c` (split into two distinct detection code paths), `Documentation/git-branch.adoc` (expanded examples), `t/t3200-branch.sh` (expanded test coverage for rebase and squash cases).
- New behavior: `--delete-merged` detects squash merges and rebases by comparing tree diffs and simulating three-way merges. The `--no-squashed` flag disables squash detection for performance.
- Output format: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)` (may attribute the topic commit to a commit with unrelated modifications due to the algorithm’s leniency).
- Performance optimizations: Uses a `changed_paths` commit slab to cache diff results, avoids redundant calculations, and processes all branches in a single pass.
- Edge cases handled: Upstream modifications to the same files as the squashed branch, reverted changes, partial landings, and mixed workflows. Blobless clone support via transparent blob fetching. The algorithm’s leniency may lead to misleading attribution in cases where the upstream commit includes additional changes beyond those from the branch tip.
- Test coverage: Expanded in `t/t3200-branch.sh`; scenarios include local `git merge --squash`, GitHub-style squash merges, rebases, upstream file modifications, and mixed workflows.
- New CLI option: `--no-squashed` to disable squash detection (defaults to off). The flag is rejected if used without `--delete-merged`.
- Symbols: No new or renamed public symbols; internal logic split into distinct code paths for rebase and squash detection.
- **Algorithmic considerations**:
  - **Rebase detection**: May reuse `git range-diff` commit-matching logic in future iterations to align rewritten commits with their originals.
  - **Squash detection**: Currently uses path-by-path three-way merge approximation via `merge_ll()`, which lacks rename detection and is intentionally lenient (checks for *containment* of changes rather than *exact* squash-merge equivalence). Junio suggests locally simulating a squash merge or using message-based matching for better accuracy; Phillip Wood suggests patch-ids or test merges for stricter detection.

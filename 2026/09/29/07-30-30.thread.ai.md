Core problem or goal
Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows. The series aims to provide a practical, one-step repository maintenance command for common forge and local workflows. Junio C Hamano’s reproducible test case demonstrates a critical false-positive scenario: the current implementation incorrectly deletes a branch whose changes were independently implemented by another author, even without the `--squashed` flag. This test case, reinforced by D. Ben Knoble’s real-world "npm update" scenario (identical commits from separate PRs rebased onto `main`), quantifies the safety trade-off of the current algorithm’s leniency (checking for *containment* of changes rather than *exact* integration). Harald Nordgren’s latest reply narrows the scope of the "npm update" scenario to automated, deterministic scripts (e.g., dependency bumps), implying that manual code changes are unlikely to trigger the false-positive issue, but accepts the scenario as plausible and reinforces the need for **author checks** as a potential mitigation.

Current status
Under review; v3 posted and complete. The **first patch (refactoring)** remains uncontroversial and ready for integration. The **second (rebase detection)** and **third (squash detection)** patches are explicitly confirmed but require CLI redesign due to safety concerns. The CLI redesign is now contested between three proposals:
1. **Harald’s minimal `--delete-irrelevant`**: A single flag (no granularity) to enable change-based detection for squash merges, rebases, and other workflows. It remains unresolved whether this flag will enable both squash *and* rebase detection by default or require explicit opt-in for each. Harald now **narrows the scope** of the "npm update" scenario to automated scripts, implying that manual code changes are unlikely to trigger false positives, but accepts the need for **author checks** to mitigate the risk.
2. **Junio’s granular `--delete-irrelevant=squashed,rebased`**: Allows users to opt into specific workflows, addressing distinct user intents with different safety guarantees.
3. **Knoble’s `--delete-merged=<kind>`**: A single flag with value modifiers (e.g., `--delete-merged=squash` or `--delete-merged=rebase,squash`), avoiding the cognitive overhead of multiple flags or a separate `--delete-irrelevant`. This aligns with Jasper Mayone’s `--landed=<kind>` proposal but is framed as a simpler, more idiomatic alternative.
The next steps involve revising the patch series to implement one of these CLI designs, incorporating **author checks** (or patch IDs) into the rebase-detection logic, and updating the test suite to reflect the new behavior, including Knoble’s "npm update" scenario and Junio’s false-positive test case.

Key technical details
- Files touched: `builtin/branch.c` (split into distinct detection code paths; first patch refactors `branch_opted_out()` helper; second patch implements rebase detection with `landing_search` structure and `changed_paths` commit slab; third patch adds squash detection with `DELETE_BRANCH_SQUASHED` flag), `Documentation/git-branch.adoc` (expanded examples), `t/t3200-branch.sh` (expanded test coverage, including Junio’s test case and Knoble’s "npm update" scenario).
- New behavior: `--delete-merged` will be restored to strict tip-reachability only (no change-based detection). A new flag (either `--delete-irrelevant`, `--delete-irrelevant=squashed,rebased`, or `--delete-merged=<kind>`) will enable change-based detection for squash merges, rebases, and other workflows. It remains unresolved whether the new flag will enable both squash *and* rebase detection by default or require explicit opt-in for each. The **rebase-detection logic** may now incorporate **author checks** or **patch IDs** to address the "npm update" scenario.
- Output format: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)` (may attribute the topic commit to a commit with unrelated modifications due to the algorithm’s leniency).
- Performance optimizations: Uses a `changed_paths` commit slab to cache diff results, avoids redundant calculations, and processes all branches in a single pass. The **rebase-detection patch** uses fast tree-based diffing, avoiding blob fetches and ensuring performance in partial clones. The **squash-detection patch** batches blob fetches and only performs them when `--squashed` is used (or when the new flag is enabled). Harald’s experiment with `git range-diff` for rebase detection revealed a **20× slowdown**, confirming that tree-based diffing remains the only viable approach for `--delete-merged` due to performance constraints. The performance trade-offs for the new flag (e.g., whether to use `git range-diff`, patch IDs, or author checks) remain unaddressed.
- Edge cases handled: Upstream modifications to the same files as the squashed branch, reverted changes, partial landings, mixed workflows, Knoble’s "npm update" scenario (identical commits from separate PRs rebased onto `main`), and automated scripts (e.g., dependency bumps). Blobless clone support via transparent blob fetching (only when the new flag is enabled). The algorithm’s leniency may lead to misleading attribution in cases where the upstream commit includes additional changes beyond those from the branch tip, as demonstrated by Junio’s test case and Knoble’s scenario.
- Test coverage: Expanded in `t/t3200-branch.sh`; scenarios include local `git merge --squash`, GitHub-style squash merges, rebases, upstream file modifications, Junio’s false-positive test case, Knoble’s "npm update" scenario, and automated scripts. The test expects the branch to be preserved but fails under the current implementation, confirming the safety issue.
- New CLI options:
  - `--squashed` (v3, opt-in, defaults to off) will be replaced or supplemented by one of:
    - `--delete-irrelevant` (Harald’s proposal, no granularity).
    - `--delete-irrelevant=squashed,rebased` (Junio’s proposal, granular).
    - `--delete-merged=<kind>` (Knoble’s proposal, e.g., `--delete-merged=squash` or `--delete-merged=rebase,squash`).
  - Jasper proposes a granular `--landed=<kind>` option (e.g., `--landed=squash`) as an alternative.

The **rebase-detection patch** introduces the `landing_search` structure and `changed_paths` commit slab. The **squash-detection patch** introduces the `DELETE_BRANCH_SQUASHED` flag.
- **Algorithmic considerations**:
  - **Rebase detection**: Uses fast tree-based diffing to check for exact file matches. Junio’s proposal to reuse `git range-diff` logic for `--delete-irrelevant` remains unaddressed; Harald’s experiment showed `git range-diff` is **20× slower**, making it impractical for `--delete-merged` but potentially viable for the new flag. Knoble’s **patch-ID proposal** (to handle local rebases with edited messages) and **author checks** (to handle GitHub-style rebases with identical commits) are also unaddressed. Harald now reinforces the need for **author checks** to mitigate the "npm update" scenario.
  - **Squash detection**: Uses path-by-path three-way merge approximation via `merge_ll()`, which lacks rename detection and is intentionally lenient (checks for *containment* of changes rather than *exact* squash-merge equivalence). Junio’s test case and Knoble’s scenario demonstrate that this leniency leads to false positives, even without `--squashed`. The algorithmic trade-offs for the new flag (e.g., whether to use patch-ids or test merges) remain unaddressed.

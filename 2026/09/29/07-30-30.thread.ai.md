Core problem or goal
Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows. The series aims to provide a practical, one-step repository maintenance command for common forge and local workflows. Junio C Hamano’s latest review **proposes a fundamental conceptual split**: preserve the existing `--delete-merged` as a **strict, tip-reachability-only** command (safe, conservative) and introduce a new `--delete-irrelevant` option for **looser, change-based detection** (riskier, ambiguous). Harald Nordgren’s v3 implementation treats squash and rebase detection as a unified feature under `--delete-merged`, but Junio now argues they represent **distinct user intents** with different safety guarantees. Harald’s latest replies push back, arguing that the mechanism of integration (squash, rebase, or verbatim merge) should not matter: once a branch’s changes are upstream, the branch is no longer needed, and the user can recover the work from the mainline if needed. This reflects a **pragmatic vs. conservative** divide: Harald prioritizes workflow efficiency (deleting branches once their changes are upstream), while Junio prioritizes safety and predictability (strict vs. loose definitions of "merged"). Jasper Mayone’s user report **reinforces Junio’s safety concerns** by demonstrating a real-world false positive: v2 deleted a branch whose changes were independently implemented by another author, reporting it as "landed as" an unrelated commit. The series retains all v2/v3 improvements: performance optimizations (batching via `changed_paths` slab, blob fetching), correctness fixes, the `--squashed` flag (now opt-in), and expanded documentation/test coverage. Junio’s example — an AI-generated patch series that becomes irrelevant because someone else independently solved the same problem — illustrates the real-world ambiguity the feature would need to handle.

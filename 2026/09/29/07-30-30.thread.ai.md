Core problem or goal
Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows, including cases where upstream modified the same files before integration. The series provides a practical, one-step repository maintenance command for common forge and local workflows. The CLI design is **finalized**: `--delete-merged <pattern>` for strict tip-reachability (current behavior, unchanged) and `--delete-integrated <pattern>` for change-based detection of rebased *and* squashed branches (opt-in, both methods enabled by default). The series explicitly addresses the **false-positive issue** by splitting the strict and change-based behaviors into separate flags, ensuring `--delete-merged` never deletes branches whose changes were independently implemented by another author. The **upstream modification problem** (where squash-merged files are later edited upstream) is now handled via a **path-by-path three-way merge approximation** using Git’s low-level merge machinery (`ll_merge`), though Junio’s review identifies a **latent correctness issue** in this logic: the index state (`the_repository->index`) passed to `ll_merge()` may not be populated, causing `.gitattributes`-driven merge drivers to be silently ignored.

Key technical details

- New behavior:
  - `--delete-merged <pattern>`: strict tip-reachability only (current behavior, unchanged). Enforced by Junio’s test case to never delete branches whose changes were independently implemented by another author.
  - `--delete-integrated <pattern>`: change-based detection for rebased *and* squashed branches (opt-in, both methods enabled by default). Handles upstream modifications via a **path-by-path three-way merge approximation** using `ll_merge()`, but Junio’s review identifies a **latent correctness issue**: the index state passed to `ll_merge()` may not be populated, causing `.gitattributes`-driven merge behavior to be silently ignored. The **author-check mitigation** is required but not yet implemented.
- Output format: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)` (updated to show landing commit).
- Performance optimizations: Rebase detection remains tree-based (no blob fetches); squash-detection uses `ll_merge()` for upstream modifications, which may **download blobs in partial clones**. The **author-check mitigation** is expected to have minimal performance impact.
- Edge cases handled: Upstream modifications to squashed files (three-way merge approximation, but with **latent correctness issue** for `.gitattributes`), reverted changes, partial landings, mixed workflows, Knoble’s "npm update" scenario, automated scripts, and the upstream modification case (shared file edited on both branch and upstream, then squash-merged). The **author-check mitigation** is required to handle forge workflows and manually applied patches.
- Test coverage: Expanded in `t/t3200-branch.sh`; includes Junio’s test case, Knoble’s "npm update" scenario, coverage for `--delete-integrated`, and a new test case for upstream modifications. **No coverage for `.gitattributes`-driven merge scenarios**.
- New CLI options:
  - `--delete-integrated <pattern>`: change-based detection for rebased *and* squashed branches (opt-in, both methods enabled by default). Handles upstream modifications via three-way merge, but with **latent correctness issue** for `.gitattributes`. Cannot be combined with `--delete-merged`. The **author-check mitigation** is required but not yet implemented.
- Config: `branch.<name>.deleteMerged` applies to both flags.

  - Core `--delete-integrated` patch: `DELETE_BRANCH_INTEGRATED` flag, rebase-detection logic (tree-based diffing), squash-detection logic (three-way merge approximation via `merge_ll()`), `change_state` enum (`CHANGE_MISSING`, `CHANGE_LANDED`, `CHANGE_NEEDS_MERGE`), `find_landed_commits()` helper (with suggested `diffopt` rename).

- **Algorithmic considerations**:
  - **Rebase detection**: Tree-based diffing for exact file matches. The **author-check mitigation** or **patch IDs** are required to address the "npm update" scenario but are not yet implemented.
  - **Squash detection**: Path-by-path three-way merge approximation via `ll_merge()` to handle upstream modifications. **Latent correctness issue**: `.gitattributes`-driven merge behavior may be silently ignored if the index is not populated. Lacks rename detection and is intentionally lenient. The **author-check mitigation** is required to reduce false positives.

Open questions and loose ends
- How to resolve the **latent correctness issue** in the squash-detection logic’s handling of `.gitattributes`: whether to populate the index before calling `ll_merge()`, document that attributes are ignored, or refactor to avoid `ll_merge()` entirely. This is the **first substantive technical feedback** on the fourth patch and must be addressed before integration.
- Whether to implement the **author-check mitigation** (Jasper’s proposal) or **patch IDs** (Knoble’s proposal) into the rebase-detection logic for `--delete-integrated` to address the "npm update" scenario and forge workflows, and how they would interact with GitHub-style rebases where commit messages are preserved. The **author-check mitigation** remains the **sole major technical gap** for the series as a whole but is not yet implemented.
- Whether to reuse `git range-diff` logic (Junio’s proposal), adopt **patch IDs** (Knoble’s proposal), or incorporate **author checks** (Jasper’s proposal) for rebase detection in `--delete-integrated`. Harald’s experiment showed `git range-diff` is **20× slower**, but it may still be viable for `--delete-integrated` if performance is less critical.
- Whether to locally simulate squash merges or use message-based matching for squash detection in `--delete-integrated` to improve attribution accuracy. The current algorithm’s leniency may still lead to misleading attribution, but the **author-check mitigation** is expected to reduce false positives.
- Whether the squash-merge detection algorithm (path-by-path three-way merge via `ll_merge()`) is sufficient for `--delete-integrated`, or whether it should be replaced with patch-ids or test merges for better accuracy and rename detection, as raised by Phillip Wood.
- Whether the performance optimizations are sufficient for large repositories or blobless clones when `--delete-integrated` is enabled, particularly with the new blob-fetching behavior for upstream modifications. Trade-offs remain unaddressed for `git range-diff`, patch IDs, or author checks.
- Whether to document the squash-detection algorithm’s limitations (e.g., lack of rename detection, leniency in attribution, blob-fetching behavior in partial clones, **latent `.gitattributes` issue**) more explicitly, as called for by Phillip Wood.

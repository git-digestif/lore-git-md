Subject: [PATCH] branch --delete-merged: detect squash-merged and rebase-merged branches
Series version: v1 (initial submission; v2 anticipated for commit message expansion, performance optimizations, and CLI option refinement)
Originating author: Harald Nordgren
Thread type: patch series

Core problem or goal
Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been squash-merged or rebase-merged into an upstream branch. The current implementation only deletes branches whose tips are reachable from the upstream, which fails for GitHub-style squash merges and local `git merge --squash` workflows where the branch tip is not part of the upstream history.

Current status
Under review; no prior versions. Patch is self-contained and does not depend on other in-flight series. Author plans a v2 to expand the commit message with examples of both GitHub’s “Squash and merge” and the local `git merge --squash; git commit` sequence, addressing Kristoffer Haugsbakk’s clarification and D. Ben Knoble’s contextual observation about workflow prevalence and tooling defaults. Performance concerns remain central: the author reports ongoing work to share logic between branches and has observed noticeable speed improvements in his local repository, but Phillip Wood’s review identifies inefficiencies in the current approach (recalculating upstream diffs for each branch) and suggests adopting the batching and precomputation strategies used by `git cherry`. The discussion has shifted from a binary config flag (`branch.deleteMergedDetectSquash`) to a CLI option (`--delete-merged=<mode>`), with the author expressing a preference for a single, unified behavior that works out-of-the-box without requiring users to specify detection modes explicitly. Phillip Wood now reinforces the need for a way to disable patch-id-based detection—even if the implementation becomes more efficient—arguing that squash detection will always be slower than the current tip-reachability check, especially in partial clones where blob fetches are required. He maintains that users who know their repository contains only squash merges (and no rebases) would benefit from a lightweight tree-based check, and that a toggle to disable patch-id detection would be useful in such cases. No decision has been reached on the CLI option design or the performance optimizations.

Key technical details
- Files touched: `builtin/branch.c`, `Documentation/git-branch.txt`
- New behavior: `--delete-merged` now detects when an upstream commit contains all changes from a branch by comparing tree diffs and simulating a three-way merge.
- Output format: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`
- Edge cases handled: reverted changes, partial landings (avoids false positives by requiring every change from the branch to be present in the upstream commit).
- Test coverage: added to `t/t3200-branch.sh`; scenarios include reverted squash merges, partial landings, and local `git merge --squash` workflows.
- New or renamed symbols: none (internal logic only); potential new CLI option `--delete-merged=<mode>` (e.g., `squashed,rebased,fast`) proposed but not yet implemented.
- Performance considerations: the algorithm may be expensive on large repositories. The author reports ongoing work to share logic between branches and has observed noticeable speed improvements in his local repository, but Phillip Wood’s review identifies inefficiencies (recalculating upstream diffs for each branch) and suggests adopting `git cherry`-style batching, precomputation of patch-ids from the smaller side of the merge base, and blob-fetch batching in partial clones. For squash merges, Phillip proposes a lightweight optimization: if an upstream commit’s second parent tree exactly matches the branch tip, and the merge base and commit count conditions hold, the branch can be considered squash-merged without running the full patch-id check. Phillip now argues that squash detection will *always* be slower than the current tip-reachability check, especially in partial clones where blob fetches are required, and that a toggle to disable patch-id detection would be useful for users who know their repository contains only squash merges (and no rebases). The discussion now centers on whether to implement these optimizations before settling the CLI option debate and whether to provide a way to opt out of the slower detection method.

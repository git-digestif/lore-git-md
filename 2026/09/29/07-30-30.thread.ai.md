Core problem or goal
Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges (GitHub-style or local `git merge --squash`), rebases, or patch-based workflows. The series aims to provide a practical, one-step repository maintenance command that handles common forge and local workflows. Junio C Hamano’s latest review proposes a **fundamental reorganization**: split the series into **separate patches for rebase detection and squash detection**, with rebase detection implemented first using `git range-diff` commit-matching logic (which considers log-message similarity, authorship, and patch IDs) and squash detection added later if needed. This reflects Junio’s view that the two workflows are distinct and may not warrant a unified implementation. The series retains all v2/v3 improvements: performance optimizations (batching via `changed_paths` slab, blob fetching), correctness fixes, the `--no-squashed` flag, and expanded documentation/test coverage. Junio’s review also raises **architectural concerns** about the CLI design, suggesting that the current `--delete-merged` + `--no-squashed` approach may not scale to future workflows (e.g., selective cherry-picks) and implying that a more granular CLI (e.g., `--delete-merged=rebased,squashed`) may be needed. Harald Nordgren’s clarification confirms that the squash-merge detection algorithm checks whether the upstream commit *contains all changes* from the branch tip, rather than whether it is *exactly* the result of a squash merge, which may lead to misleading attribution in the output (e.g., `landed as` pointing to a commit with unrelated modifications). Harald argues that rename detection is not a reliable signal for branch integration, as some topics intentionally introduce renames and should not be deleted even if their changes are otherwise upstream.

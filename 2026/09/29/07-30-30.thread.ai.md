Thread identity: Subject: [PATCH v11 5/5] branch --delete-merged: detect squash-merged and rebase-merged branches (final patch of v11 series). Series version: v11 (five patches total). Originating author: Harald Nordgren. Thread type: patch series with architectural, CLI-design, user-experience, performance, and correctness discussion. Currently processing patch 5/5 of v11, which implements squash-merge detection on top of the tree-based rebase detection from patch 4/5.

Core problem or goal: Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges, rebases, or patch-based workflows, including cases where upstream modified the same files before integration. The CLI design is finalized: `--delete-merged <pattern>` for strict tip-reachability (unchanged) and `--delete-integrated <pattern>` for change-based detection of rebased and squashed branches (opt-in, mutually exclusive with `--delete-merged`). The series splits strict and change-based behaviors into separate flags to prevent `--delete-merged` from deleting branches whose changes were independently implemented by another author. Patch 4/5 implements the rebase-detection half using purely tree-based comparison (no blob fetches); patch 5/5 implements the squash-detection half using a path-by-path three-way merge approximation via `xdl_merge()` guarded by `mergeable_as_text()`, ignoring merge drivers from `.gitattributes`.

Current status: v11 posted and complete with all five patches; patch 5/5 (just received) finalizes the series by implementing squash-merge detection. The delta from v10 is confined to patches 3/5 and 4/5, where `--dry-run` combined with a non-deletion operation now produces an operation-specific error message naming the attempted operation instead of a generic message. Patch 3/5 changes validation in `builtin/branch.c` from `if (dry_run && !delete_merged.nr)` to `if (dry_run && !delete && !delete_merged.nr)`, allowing `--dry-run` with plain `-d`/`-D`; when combined with an unsupported operation it dies with `--dry-run is not supported for branch renaming`, `--dry-run is not supported for branch copying`, `--dry-run is not supported for branch creation`, or a generic `--dry-run is not supported for this operation`. When deletion is requested, the code passes the `DELETE_BRANCH_DRY_RUN` flag bit into `delete_branches()`, which prints `Would delete branch %s (was %s).` for deletable branches and reports identical errors for undeletable ones (checked-out, not fully merged) as without `--dry-run`, leaving refs untouched. Patch 4/5 adds the `DELETE_BRANCH_INTEGRATED` flag bit and `delete_integrated` strvec; when active, `delete_merged_branches()` collects candidate branches failing the usual tip-reachability check into a `landing_search` array, then calls `find_landed_commits()` to scan upstream history. For each branch, `collect_branch_changes()` diffs the merge base against the branch tip to record every changed path with its blob OID and mode in a `branch_change` array. `find_landed_commit()` walks upstream commits in reverse (via `rev-list --reverse`), using a `changed_paths` commit slab to skip commits that do not touch any of the branch's changed paths, and checks whether any single upstream commit's tree contains the exact branch version (OID and mode) of every changed file via `changes_landed()` and `change_landed()`. The first matching commit is stored in a `strmap` keyed by branch name, which `delete_branches()` (extended in patch 2/5) consults to skip the reachability check and print `Deleted branch %s (was %s, landed as %s)`. Patch 5/5 extends this to squash merges: `changes_landed()` now operates in two passes, first classifying each path via `change_state_at()` (exact match yields `CHANGE_LANDED`, absence yields `CHANGE_MISSING`, differing regular file yields `CHANGE_NEEDS_MERGE`), then for `CHANGE_NEEDS_MERGE` paths calling `merge_keeps_upstream()` which performs a three-way `xdl_merge()` with `XDL_MERGE_ZEALOUS` between merge-base, upstream, and branch versions, treating the change as landed only when the merge result is byte-identical to the upstream version. The merge deliberately ignores `.gitattributes` merge drivers (preventing both false positives from drivers like `union` and arbitrary command execution), and `mergeable_as_text()` rejects files exceeding `MAX_XDIFF_SIZE` or containing binary content. Because this reads blob contents, partial clones may download objects. Patch 1/5 is a pure refactoring with no behavior change: it extracts the existing `branch.<name>.deleteMerged` opt-out check from `delete_merged_branches()` into a new static helper `opted_out_of_delete_merged()` in `builtin/branch.c` (taking a `struct strbuf *` for the config key, the branch name, and flags; returning `true` when opted out and printing the skip message unless `DELETE_BRANCH_QUIET` is set) so that the `--delete-integrated` mode in patch 5/5 can consult the same configuration. Patch 2/5 extends `delete_branches()` to accept an optional `struct strmap *landed_commits` parameter mapping branch names to the upstream commit where their changes were detected; when a branch appears in this map, `delete_branches()` skips the usual `check_branch_commit()` reachability test and reports deletion with the extended message `Deleted branch %s (was %s, landed as %s)` (or the `Would delete` variant under `--dry-run`), using a static `msg_templates[2][3]` array holding the three message variants (landed, remote-tracking, local) for both dry-run and actual deletion modes; both existing call sites currently pass `NULL` for this parameter in v11 patches 1-3, and patches 4/5 and 5/5 populate the map when implementing rebase-based and squash-merge-based detection. The series remains under review with no integration status announced.

Algorithmic considerations: Rebase detection (patch 4/5) is tree-based using exact tree-entry comparisons of changed files; no blob fetches, cheap in blobless/partial clones. Squash detection (patch 5/5) uses `xdl_merge()` plain text merge with `XDL_MERGE_ZEALOUS` ignoring `.gitattributes` drivers and may download blobs in partial clones; lacks rename detection. The "npm update" false-positive scenario (another author independently making identical changes) is not addressed by tree-based detection; author-check mitigation or patch IDs remain required but unimplemented.

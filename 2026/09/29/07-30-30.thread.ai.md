Core problem or goal
Extend `git branch --delete-merged` to recognize branches whose changes (but not their tips) have been integrated into an upstream branch via squash merges (GitHub-style or local `git merge --squash`), rebases, or patch-based workflows. The v2 patch addresses performance inefficiencies, correctness bugs, and usability concerns raised in v1, while introducing a `--no-squashed` flag to disable the slower squash detection for performance-sensitive workflows. Junio C Hamano's review questions the unified implementation approach, suggesting that rebase-and-merge (one-to-one commit correspondence) and squash merges (entire branch collapsed into a single commit) may warrant distinct algorithms for clarity and maintainability. Phillip Wood's latest review shifts focus to the **algorithmic trade-offs** in squash-merge detection, noting that the current implementation (path-by-path three-way merge approximation via `merge_ll()`) lacks rename detection and is less strict than alternatives like patch-ids or test merges. The broader user need—a high-level, one-step repository maintenance command (`git full-clean`)—remains conceptual and is not part of this series.

Current status
Under review; v2 posted and complete. Junio's review raises architectural concerns about the patch's organization and algorithmic design but does not reject the series or demand a rewrite. Phillip Wood's latest review calls for greater clarity about the algorithm's design rationale and limitations, particularly regarding rename detection and edge-case handling. Key changes from v1:
- **Performance**: Batches diff calculations and reuses results across branches via a `changed_paths` commit slab, addressing Phillip Wood’s concern about recalculating upstream diffs for each branch. The `find_landed_commits` function processes all branches in a single pass, sharing diff results across searches.
- **Correctness**: Fixes a bug where merged branches were incorrectly attributed to a merge commit if another branch was searched first. The output now shows the topic commit itself for work integrated via merges (e.g., `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`).
- **Usability**: Adds `--no-squashed` to let users opt out of squash detection (e.g., in large repos or blobless clones), though the feature defaults to "on" for all branches. This reflects a compromise between Phillip Wood’s performance concerns and Harald Nordgren’s goal of a unified default behavior.
- **Documentation**: Expands examples to cover local `git merge --squash` and GitHub’s "Squash and merge" buttons, addressing Kristoffer Haugsbakk’s and D. Ben Knoble’s feedback.
- **Edge cases**: Handles upstream modifications to the same files as the squashed branch, reverted changes, partial landings, and mixed merge/squash workflows. Tests verify behavior for these cases.
- **Blobless clone support**: Transparently fetches blobs in partial clones to calculate patch-ids, resolving Phillip Wood’s concern about incomplete detection.
- **Algorithmic considerations**: Junio's review suggests potential improvements:
  - For rebases: Reuse `git range-diff` commit-matching logic to align rewritten commits with their originals.
  - For squash merges: Locally simulate a squash merge and search upstream for a similar commit, or rely on message-based matching (used in patch-based workflows) due to the lack of commit message preservation in squash merges.
  - Phillip Wood's review highlights that the current squash-merge detection (path-by-path three-way merge approximation via `merge_ll()`) lacks rename detection and is less strict than alternatives like patch-ids or test merges. The trade-offs between these methods—accuracy, performance, and edge-case handling—are not clearly documented in the cover letter.

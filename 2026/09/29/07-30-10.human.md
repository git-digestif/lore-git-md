This is a review comment from Junio C Hamano on Johannes Schindelin’s four-patch series introducing a Rust-based SHA-1 backend as an optional compile-time feature. The series aims to deliver a ~3× performance boost for `git index-pack` on Windows and large repositories by replacing Git’s C-based sha1dc implementation with a Rust crate (`sha1dc`), while providing a runtime escape hatch (`core.sha1dcBackend=c`) to fall back to the C version.

Junio’s reply is substantive but narrowly focused. He flags the cover letter’s phrasing—“compile-time option”—as misleading, since the series actually enables users to switch between Rust and C backends at runtime via the new `core.sha1dcBackend` config key. This distinction matters: a compile-time choice would force users to rebuild Git to change backends, whereas runtime selection is far more flexible and valuable. Junio’s observation is precise and likely uncontroversial; the author may simply update the wording in a future revision.

The more critical question Junio raises is whether the two implementations (Rust and C) are functionally equivalent. Specifically, he asks if both backends faithfully implement the same collision-detection logic from the original sha1dc paper, ensuring identical behavior on fudged inputs. This is not a performance or platform concern but a correctness one: if the Rust crate diverges in its detection logic, users could see inconsistent security outcomes depending on which backend is active. The question is sharp and directly targets the series’ suitability for merging. The author has not yet responded, so the thread’s next step will likely hinge on whether the Rust crate’s implementation matches the C version’s collision-detection guarantees.

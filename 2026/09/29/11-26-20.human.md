This is a **substantive review** of Harald Nordgren’s patch that extends `` `git branch --delete-merged` `` to detect squash-merged and rebase-merged branches. The patch itself is a well-motivated feature addition that addresses a real workflow pain point—users who rely on GitHub’s “Squash and merge” or local `` `git merge --squash` `` workflows have long been frustrated that `` `--delete-merged` `` ignores their branches because the branch tip is not part of the upstream history.

D. Ben Knoble’s reply adds technical depth to the discussion. He notes that the rebase-merged case could theoretically leverage the same logic Git already uses in `` `git log --cherry-mark` `` or `` `git range-diff` `` to detect rebased commits, but he concedes that the squash-merged case (where all changes are collapsed into a single commit) subsumes the rebase case in practice. The patch’s current approach—comparing tree diffs and simulating a three-way merge—is therefore a reasonable simplification. Knoble also raises a performance concern: the algorithm could be expensive on large repositories, though he stops short of suggesting a warning in the documentation, acknowledging that future performance improvements might make such a note obsolete.

The only open question Knoble introduces is a request for context: he asks where Harald saw the post-2.56 user feedback that motivated the patch. This is a minor point, not a technical objection, and the thread remains constructive and focused on refining the feature rather than debating its necessity. The patch itself looks solid—it handles edge cases (reverted changes, partial landings), provides clear output, and includes thorough test coverage—so it is likely to land once the commit message is expanded to cover both GitHub-style and local squash-merge workflows.

This is a **feature patch** that extends `` `git branch --delete-merged` `` to detect branches whose changes have been squash-merged or rebase-merged into an upstream branch, even when the branch tip itself is not part of the upstream history. The patch is under active review and has already sparked substantive discussion about implementation trade-offs and real-world workflows.

The author, Harald Nordgren, responds here to D. Ben Knoble’s observation that the new logic could be expensive on large repositories. Nordgren notes that performance has already improved from earlier iterations and is now acceptable on his local Git repository, though still slower than the original behavior. He floats the idea of hiding the feature behind a configuration flag, which would let users opt in only when they need it. No decision has been made on this point, and the thread remains open to further input on whether a flag (or a performance caveat in the documentation) is the right approach.

The patch itself is well-motivated: it addresses a common pain point for users who rely on squash-merge workflows (both local and GitHub-style) and want `` `git branch --delete-merged` `` to clean up branches whose changes are already incorporated. Test coverage is thorough, handling edge cases like reverted changes and partial landings. The only remaining loose end is the performance question raised here; everything else in the series looks ready for a v2 once that is resolved.

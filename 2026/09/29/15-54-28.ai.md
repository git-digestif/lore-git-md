This is a **substantive technical discussion** in the ongoing `stash: fix autostash with staged index entries` series, clarifying a key detail about the `t5520-pull.sh` test breakage and its resolution. The email exchanges between Phillip Wood, D. Ben Knoble, and Thomas Bachem confirm why `git pull --rebase` unexpectedly relies on reflogs despite an explicit `<upstream>` argument, and how this interacts with the stash series' changes to reflog entry generation.

The core insight is that `git pull --rebase` does **not** use `git rebase --fork-point` directly. Instead, it calls `git merge-base --fork-point` itself to compute the upstream revision, then passes the resulting object ID (not a ref) to `git rebase`. Since `git rebase` only performs fork-point detection when its upstream argument is a ref, this bypasses its built-in reflog logic, leaving `git pull` responsible for the reflog lookup. This explains why the test breakage occurs: the stash series reduces the number of reflog entries (by eliminating `git reset --quiet --refresh` calls during failed merges), shifting the timing of reflog expiration triggered by `git maintenance run --auto`. The expiration now happens *after* test 68’s fetch but *before* test 69, removing the critical reflog entry (`copy-orig` to `ae98574`) that `merge-base --fork-point` needs to correctly identify the upstream commit.

Phillip’s explanation also confirms that Thomas Bachem’s fix (pinning `gc.reflogExpire` and `gc.reflogExpireUnreachable` to `never` in the test setup) is the correct solution, as the breakage is a test-environment quirk rather than a flaw in either the stash series or auto-maintenance logic. The discussion leaves no open questions about the interaction, though D. Ben Knoble notes curiosity about the historical design choice to split fork-point detection between `git pull` and `git rebase`.

- **Config keys**: `gc.reflogExpire`, `gc.reflogExpireUnreachable`, `maintenance.reflog-expire.auto`.

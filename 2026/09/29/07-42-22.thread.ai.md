Thread identity: Patch series extending `git stash create` to support `--include-untracked` (`-u`) and `--all` (`-a`) options, authored by Kazumasa Shigeta. Thread type: feature addition to the stash subsystem.

Core problem or goal: Address the long-standing inconsistency where `git stash create` lacked support for `--include-untracked` and `--all` options, which were available in `git stash push` and `git stash save`. The goal is to bring parity to the stash command family by exposing these options in `create` without introducing new behavior or breaking existing scripts.

Current status: Initial patch version (v1) posted. The patch reuses the existing `do_create_stash()` helper and its internal `include_untracked` parameter, translating it into the same `INCLUDE_ALL_FILES` mode used by other stash subcommands. No prior versions or merge status reported; series is under initial review. **Backward-compatibility concerns raised**: Phillip Wood identified two critical issues: (1) the exit status change (0 vs. 1 when no changes are found) and (2) option parsing regression (flags after message arguments).

Key technical details:
- Files touched: `builtin/stash.c` (command implementation), `Documentation/git-stash.txt` (documentation), and test scripts in `t/` (test coverage).
- New/renamed symbols: None (reuses existing `do_create_stash()` and `INCLUDE_ALL_FILES`).
- Behavior: `--include-untracked` (`-u`) and `--all` (`-a`) now supported in `git stash create`; **exit status and option parsing behavior are contested**—current implementation alters script-facing behavior.
- On-disk format: No changes.
- Test coverage: Verifies short/long option forms, untracked/ignored file boundaries, option/message parsing edge cases, no-change behavior, and guarantees that `create` does not modify `refs/stash`, the index, or the working tree. **Test suite may not cover exit status or post-message option parsing.**

Open questions and loose ends:
1. **Exit status**: Should `git stash create` exit with 0 or 1 when no changes are found? Current patch changes it to 0 (matching `push`), but existing scripts may rely on 1.
2. **Option parsing**: Should `parse_options()` use `PARSE_OPT_STOP_AT_NON_OPTION` to prevent flags after message arguments from being interpreted as options? Current patch does not, breaking scripts that pass messages containing dashes.
3. **Test coverage**: Are the existing tests sufficient to catch these edge cases, or do they need augmentation?

Participant positions:
- **Phillip Wood**: Substantive review identifying two backward-compatibility regressions (exit status and option parsing). Argues the patch’s claim to preserve existing behavior is incorrect and recommends fixes (e.g., `PARSE_OPT_STOP_AT_NON_OPTION`). No other aspects of the implementation are criticized; the objections are narrowly technical.

Related work: References a 2017 refactoring (9ca6326dff29) that added internal plumbing for untracked-file handling but left the `create` interface unchanged, and a recent GitGitGadget pull request (1892) that proposed exposing `--include-untracked` alone. This patch is positioned as the logical completion of that work. No objections raised to the feature’s merit or prior context.

Thread identity: Patch series extending `git stash create` to support `--include-untracked` (`-u`) and `--all` (`-a`) options, authored by Kazumasa Shigeta. Thread type: feature addition to the stash subsystem, now in refined design discussion phase.

Core problem or goal: Resolve the inconsistency where `git stash create` lacked support for `--include-untracked` and `--all` options available in `git stash push` and `git stash save`. The discussion has expanded to address broader backward-compatibility concerns with `git stash create <message>`’s positional message grammar, which treats the rest of the command line as a message. The goal is to expose more of `do_create_stash()`’s capabilities without breaking existing scripts while preserving traditional behavior, with active debate over which subset of `stash push` options should be exposed in a script-focused command.

Current status: Design discussion phase following feedback from Junio C Hamano, Phillip Wood, and others on v2 and proposed directions. The original v3 patch is on hold while the author refines the scope and approach. The discussion has narrowed the proposed changes: `--patch` and positional pathspecs are ruled out, while `--pathspec-from-file` and `-m`/`--message` are endorsed for consistency with other Git commands. `PARSE_OPT_STOP_AT_NON_OPTION` is confirmed as a reasonable backward-compatibility measure for preserving the positional-message grammar. Three potential directions remain under active discussion: (1) extend `git stash create` with a subset of `stash push` options (e.g., `-u`, `-a`, `-m`, `--pathspec-from-file`), (2) add a new subcommand (e.g., `git stash make`) to avoid `create`’s positional message grammar, or (3) add `--create-only` to `git stash push` to reuse its option grammar while separating creation logic from application. Junio C Hamano previously described `--create-only` as "the safest" approach, implying a preference for reusing existing option grammar over adding a new subcommand or extending `create`’s interface. The latest email from Shigeta signals a preference for incrementally extending `stash create` with a minimal subset of options, arguing that this establishes a foundation for future script-oriented options without revisiting backward-compatibility concerns. No merge status reported; the thread remains under active review.

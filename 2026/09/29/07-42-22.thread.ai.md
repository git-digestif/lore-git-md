Thread identity: Patch series extending `git stash create` to support `--include-untracked` (`-u`) and `--all` (`-a`) options, authored by Kazumasa Shigeta. Thread type: feature addition to the stash subsystem, now in refined design discussion phase with a focus on long-term consistency between `git stash create` and `git stash push`.

Core problem or goal: Resolve the inconsistency where `git stash create` lacked support for `--include-untracked` and `--all` options available in `git stash push` and `git stash save`, while preserving backward compatibility with `git stash create <message>`’s positional message grammar. The goal has evolved to ensure `git stash create` can eventually serve as a script-friendly foundation for reimplementing `git stash push`, with all options that make sense in a create-only context exposed consistently.

Current status: Design discussion phase following feedback from Junio C Hamano, Phillip Wood, and others. The original v3 patch is on hold while the author refines the scope. The discussion has narrowed the proposed changes to incrementally extending `git stash create` with a subset of `stash push` options, but Junio’s latest feedback challenges the rationale for limiting the subset, arguing that `stash create` should support the same options as `stash push` where they produce the same stash shape. `PARSE_OPT_STOP_AT_NON_OPTION` remains confirmed as a reasonable backward-compatibility measure for preserving the positional-message grammar. The author’s earlier proposal to include `-m/--message`, `-q/--quiet`, `-u/--include-untracked`, and `-a/--all` is now under scrutiny, with Junio suggesting that any option supported by `stash push` should behave identically in `stash create` unless there is a concrete reason otherwise. No merge status reported; the thread remains under active review.

Open questions and loose ends:
1. **Design direction**: Whether to proceed with the author’s proposed minimal subset (`-m`, `-q`, `-u`, `-a`) or expand `git stash create` to support all `stash push` options that create a stash (e.g., `--staged`, `--pathspec-from-file`). Junio’s feedback argues for the latter unless there are concrete reasons to exclude options, while the author’s earlier proposal favored a narrower subset to avoid "overspecifying" without use cases. This remains unresolved.
2. **Scope of `stash create`**: Whether the proposed subset is sufficient for scripting use cases or if additional options (e.g., `--pathspec-from-file`, `--staged`) should be included. Phillip Wood’s earlier feedback favored `-u` and `-m` but questioned full pathspec support; Junio’s latest feedback suggests that any option that creates a stash in `push` should be available in `create` unless there is a specific reason otherwise.
3. **Backward-compatibility**: Whether the exit status mapping (1 → 0) and `PARSE_OPT_STOP_AT_NON_OPTION` fully address backward-compatibility risks, or if scripts might still rely on the old behavior. Junio’s earlier feedback suggested forbidding messages beginning with `-` (with an escape hatch like `-m`) as a manageable change; this remains unresolved.
4. **Process follow-up**: The author has not yet posted a revised patch. The next step is likely further discussion or a revised patch that either justifies the minimal subset or expands it to align with `stash push`.

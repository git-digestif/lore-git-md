Thread identity
Subject: [RFC] Optional per-repository consent before running local hooks
Series version: RFC (no patch version)
Originating author: Dmytro Lymarenko
Thread type: RFC / design discussion

Core problem or goal
Add an opt-in safety mechanism requiring explicit user consent before Git runs any local hook in a repository not previously marked as trusted. The prompt would display the hook’s path and offer three choices: run once, trust all hooks in the current repository, or decline. For hooks inside the working tree, Git would re-prompt if the script changes. Default behavior remains unchanged.

Current status
Early RFC; no implementation posted. Junio C Hamano and brian m. carlson have raised substantive security and operational concerns: (1) a malicious tool that can install hooks could also manipulate the proposed trust mechanism, negating protection, and (2) the interactive prompt would break non-interactive environments (CI, Docker). No counter-proposals or revised designs have been posted.

Key technical details
- New safety setting (name and scope not yet specified)
- Prompt mechanism triggered immediately before hook execution
- Trust state stored per-repository (details unspecified)
- Re-prompt logic for modified in-worktree hooks
- No on-disk format changes mentioned
- No new CLI options or config keys named yet
- No test coverage described

Open questions and loose ends
- What configuration knob(s) will control this feature?
- How and where will the trust state be persisted **securely** (Junio’s and brian’s concern)?
- Should there be a global “trust all” override?
- How will the feature interact with existing hook-related settings (e.g., core.hooksPath)?
- What happens if the user declines a mandatory hook (e.g., pre-commit)?
- Are there performance implications for repositories with many hooks?
- Should the prompt be suppressible via command-line flag or environment variable?
- Can the trust mechanism be designed to resist tampering by the same process that installs hooks?
- How will the feature function in non-interactive environments (CI, Docker)?

Participant positions
- **Junio C Hamano**: Objects to the RFC’s premise on security grounds. Argues that any trust-state persistence mechanism vulnerable to manipulation by the same entity that installs hooks provides no meaningful protection. Position is substantive and technical, focusing on the attack vector rather than implementation details.
- **brian m. carlson**: Raises two operational blockers: (1) the interactive prompt would break non-interactive environments (CI, Docker), and (2) Git lacks a secure per-user data store for trust state, making the feature ineffective against malicious repositories. Suggests `core.hooksPath=/dev/null` as a workaround but acknowledges it can be overridden. Position is substantive, highlighting unresolved security and usability tensions.

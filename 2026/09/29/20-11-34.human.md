This is a **bugfix and refactoring patch** in Jeff King’s series converting `mmfile_t` buffer sizes from `unsigned long` to `size_t`. The email is a follow-up discussion between Peff and Junio C Hamano about a latent error-handling bug in `ll_ext_merge()` that the series exposes.

The core issue: when an external merge driver claims success (exit code 0) but the output file is missing or unreadable, `read_mmfile()` leaves the result buffer as `NULL` and size as `0`, yet `ll_ext_merge()` still returns `LL_MERGE_OK`. Some callers (like `merge-ort.c`) correctly treat `NULL` buffers as errors, but others (like `rerere.c`) pass the `NULL` pointer to `fwrite()`, which is undefined behavior. Junio proposed a fix to centralize the safety check in `ll_merge()`, forcing any `LL_MERGE_OK` with a `NULL` buffer to become `LL_MERGE_ERROR`. Peff agrees the bug is real and suggests an alternative fix directly in `ll_ext_merge()`, converting the read failure into a driver error (exit code 129) to avoid propagating bogus empty results.

The discussion is substantive and collaborative, with both participants acknowledging the problem and exploring solutions. Peff’s proposed fix is minimal and targeted, addressing the issue at its source rather than relying on callers to handle edge cases. The bug is subtle but real—triggerable by a driver that changes file permissions or deletes its output—and the fix will prevent potential crashes or incorrect merge resolutions. This patch is now effectively a bugfix rather than pure refactoring, and the fix will need to be incorporated before the series can proceed. The rest of the series (patches 1 and 2) has already received maintainer acks and looks ready to merge once this issue is resolved.

This is the third patch in the v4 series introducing a "matching-inspired" fetch mode for shallow repositories. It adds a `--limited-fetch` flag to `git remote add`, which configures the remote to use `remote.<name>.refmap` instead of the traditional wildcard `remote.<name>.fetch` refspec. This opt-in mechanism allows users to create remotes that only fetch branches tracked by local branches, avoiding the performance penalty of negotiating history for all remote branches.

The patch updates `builtin/remote.c` to parse the new `--limited-fetch` flag, rejecting it if combined with `-t/--track` or `--mirror` (since those already specify explicit fetch behavior). When the flag is set, the code writes a single `remote.<name>.refmap` entry (`+refs/heads/*:refs/remotes/<name>/*`) to `.git/config`, enabling the dynamic branch enumeration logic introduced in Patch 2/4. The documentation in `git-remote.adoc` is updated to explain the flag's purpose and link to the `--refmap` documentation in `git-fetch(1)`.

Tests in `t/t5505-remote.sh` verify that `--limited-fetch` works in non-shallow repositories (ensuring the feature isn't tied to shallow clones) and correctly rejects incompatible flag combinations. The patch preserves backward compatibility by defaulting to the traditional wildcard refspec unless `--limited-fetch` is explicitly specified.

This is a well-scoped addition to the series, addressing the need for an explicit opt-in mechanism for the new fetch mode. The implementation is clean, the documentation is clear, and the tests cover the key edge cases. No substantive objections have been raised to this patch in prior iterations, and it aligns with the consensus design established in earlier versions of the series.

This thread is about an RFC patch from Stanislav Aleksandrov that introduces a `^/` syntax for root-relative submodule URLs. The feature aims to make submodule configurations portable across forks with arbitrary hierarchy depths (e.g., GitLab subgroups) by dynamically resolving the submodule URL against the superproject’s remote server root. For example, `^/org/lib.git` would resolve to `https://host/org/lib.git` if the superproject’s remote is `https://host/me/super.git`.

The patch is procedurally ready for Junio’s `seen` branch after Stanislav resolved a test-numbering collision (t7427 → t7428). Junio has signaled intent to queue it once that was fixed, and no design objections remain. The implementation touches `submodule--helper.c`, `submodule-config.c`, and `remote.c`, adding a new `root_relative_url()` function and thorough test coverage (now in t7428) for cloning, syncing, HTTPS/SSH/local forks, nested submodules, and error conditions.

The key clarification in this latest exchange is the semantic distinction between `^/` and traditional relative paths (`../`). The `^/` syntax is designed for submodules that stay in their original location on the remote server, while `../` continues to work as expected when both the superproject and submodule are forked together. This addresses Jacob Keller’s earlier concern about fork isolation: `^/` avoids silently inheriting upstream dependencies, making it more predictable for users who want to keep submodules pinned to their original locations. The thread remains focused on refining the feature’s motivation and use cases, with no new technical objections or changes to the patch itself.

This thread is about an RFC patch from Stanislav Aleksandrov that introduces `^/` syntax for submodule URLs, allowing them to be specified relative to the superproject’s remote server root. This makes it easier to maintain portable forks across arbitrary hierarchy depths (e.g., GitLab subgroups) without manual configuration. The design dynamically replaces only the path portion of the superproject’s remote URL, preserving protocol, host, and credentials, and explicitly distinguishes between `^/` (for submodules remaining in their original location) and traditional relative paths (`../`) (for forked dependencies).

Junio has signaled his intent to queue the patch in the `seen` branch once a minor test-number collision (t7427 → t7428) was resolved. Stanislav confirmed the renumbering, and Junio has now clarified that he won’t squash the fix-up commit, leaving it as a separate step for Stanislav to address when the series moves out of RFC. The patch itself is procedurally ready for `seen`, with no remaining design objections. Key technical details include the new `root_relative_url()` function, updated test coverage (now t7428), and explicit handling of edge cases like IPv6 in SCP-style URLs and fork isolation semantics.

Jacob Keller provided substantive feedback on the design, engaging with trade-offs around syntax choice, protocol handling, and fork isolation, but did not outright reject the proposal. The main open questions remain practical concerns like shell escaping (since `^` is special in `cmd.exe` and Git Bash) and ecosystem adoption (libgit2, JGit, and forges would need to implement the syntax). The debate over whether new syntax is justified—given existing alternatives like `url.<base>.insteadOf`—continues, but the patch is seen as a dynamic, low-configuration solution to a real workflow problem.

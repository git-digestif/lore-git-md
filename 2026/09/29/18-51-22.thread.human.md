This thread is about an RFC patch from Stanislav Aleksandrov that introduces a `^/` syntax for root-relative submodule URLs, aiming to solve a long-standing issue when superprojects are forked into deeper hierarchies (like GitLab subgroups). The patch lets users write `^/org/lib.git` in `.gitmodules`, which resolves to `https://host/org/lib.git` if the superproject’s remote is `https://host/me/super.git`.

Jacob Keller’s review is the first substantive feedback. He questions whether the problem could be addressed with existing mechanisms like `url.<base>.insteadOf` or by extending `.gitmodules` to carry protocol preferences, though he acknowledges the `^/` syntax has precedent in `svn:externals`. He also raises practical concerns: shell escaping of `^` in `cmd.exe` and Git Bash (users may need quoting), how local paths starting with `^/` are handled (the patch rejects them to avoid ambiguity), and whether IPv6 addresses in SCP-style URLs work (the code should handle them, but it’s untested). His feedback is constructive, focusing on robustness and whether new syntax is justified.

The patch itself is self-contained, touching `builtin/submodule--helper.c`, `submodule-config.c`, and `remote.c` (adding a new `root_relative_url()` function). It’s opt-in, preserves existing URLs, and includes thorough test coverage for cloning, syncing, HTTPS/SSH/local forks, and error conditions. Open questions include ecosystem adoption (libgit2, JGit, forges) and whether `../../` could solve the problem by allowing deeper relative traversal. No other reviews have landed yet, so the discussion is still shaping the feature’s direction.

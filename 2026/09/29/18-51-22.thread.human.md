This thread proposes a new `^/` syntax for submodule URLs in `.gitmodules` that resolves relative to the superproject's remote server root rather than its path, authored by Stanislav Aleksandrov as an RFC. The syntax aims to make submodule references portable across forks at arbitrary hierarchy depths (like GitLab subgroups) by replacing only the path portion of the superproject's remote URL while preserving protocol, host, and credentials. Jacob Keller provided a substantive review generally endorsing the approach while clarifying the distinction between `^/` (for submodules staying in place) and `../` (for forked dependencies), and D. Ben Knoble raised security and implementation questions about credential injection and hand-rolled URL parsing.

Junio C Hamano initially indicated he was inclined to squash a test renumbering fix-up and mark the topic ready for the `next` integration branch, inviting objections from heavy submodule users. However, his latest review identifies two concrete parsing bugs in the `skip_bracketed_host()` helper in `remote.c`: when the superproject remote is an scp-style URL containing `@[` sequences in the path (e.g., `host:dir/@[x]/repo.git`), the function either fails with a "cannot resolve" error or produces a corrupt URL like `host:dir/@[x]:org/lib.git`. He suggests the fix requires stopping the scan for `@[` or `:` past the first slash in the path portion.

The series remains in RFC status and has not been merged. Open items now include fixing the `skip_bracketed_host()` parsing edge cases, addressing Knoble's questions about credential-injection vectors in `check_submodule_url()` and warning suppression in `resolve_relative_url_gently()`, and revising documentation terminology -- Junio notes that calling `^/` an "absolute path" is misleading for scp-style URLs and suggests "paths relative to the server-root" instead. Shell escaping concerns in `cmd.exe` and ecosystem adoption by libgit2, JGit, and forges remain acknowledged trade-offs.

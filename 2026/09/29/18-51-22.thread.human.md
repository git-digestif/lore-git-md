This thread is an RFC proposal by Stanislav Aleksandrov to introduce a `^/` syntax for root-relative submodule URLs, allowing submodules to be specified relative to the superproject’s remote server root. This would enable portable forks across arbitrary hierarchy depths (e.g., GitLab subgroups) without manual configuration. The patch is still in the RFC phase, with no prior versions or merge status reported.

The discussion has centered on whether the new syntax is justified, given alternatives like `url.<base>.insteadOf` or `.gitmodules` extensions. Jacob Keller has provided substantive feedback, engaging with the design rationale and edge cases (e.g., shell escaping, IPv6, local paths, and relative traversal). While he acknowledges the low breakage risk of repurposing `^/` and the limitations of relative traversal (`../../`), he remains unconvinced that the forge-specific motivation (GitLab subgroups) warrants new syntax. The author, Stanislav Aleksandrov, has defended the design, arguing that `^/` dynamically resolves to the server root, preserving protocol and credentials, and avoids the fragility of relative paths.

A subtle semantic point emerged: forking both superproject and submodule would require updating the `^/` URL to point to the new fork, whereas relative URLs would continue pointing to the original submodule unless explicitly changed. Jacob sees this as more correct, but it may surprise users expecting automatic fork isolation. The thread is converging on the technical design, but the syntax choice remains unresolved. Key technical details include the new `root_relative_url()` function, opt-in behavior, and thorough test coverage for cloning, syncing, and error conditions.

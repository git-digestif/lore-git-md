This thread proposes a new `^/` syntax for submodule URLs that resolves paths relative to the superproject's remote server root, allowing portable forks across arbitrary nesting depths without manual URL rewriting. Stanislav Aleksandrov authored the RFC patch, which dynamically replaces only the path portion of the superproject's remote URL while preserving protocol, host, and credentials. Jacob Keller provided a substantive review exploring fork isolation semantics, IPv6 handling, and shell escaping concerns, while Junio C Hamano expressed inclination to mark the topic ready for `next` once it graduates from RFC, inviting heavy submodule users to object before integration.

D. Ben Knoble, responding as an experienced submodule user, delivered a detailed vetting review that does not object to the proposal but raises important edge cases. He questioned whether `^/` URLs traverse the same credential-injection risks as `../` URLs handled in commit c44088ecc4, disputed test expectations in t0060-path-utils.sh for malformed `^/` inputs, and expressed discomfort with the hand-rolled URL parsing in `root_relative_url()` and its helpers. He also asked whether the warning suppression logic in `resolve_relative_url_gently()` is correct when the remote falls back to local paths, suggested restructuring the documentation into a bulleted list of URL forms, and asked whether the RFC trade-offs should be captured in the commit message rather than only on the list.

The series remains in RFC status, with Junio planning to squash the test renumbering fix-up (t7427 to t7428) upon graduation and merge the topic to `next` for cooking; it has not been merged to `master`. Open items now include Knoble's security and implementation questions about credential handling and URL parsing robustness, plus the broader unresolved debate over ecosystem adoption by libgit2, JGit, and forges.

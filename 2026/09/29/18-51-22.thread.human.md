This thread is an RFC from Stanislav Aleksandrov proposing a `^/` prefix syntax for submodule URLs in `.gitmodules`, allowing them to resolve relative to the superproject remote's server root rather than its directory path -- so `^/org/lib.git` paired with a superproject at `https://host/me/super.git` resolves to `https://host/org/lib.git`, preserving protocol, host, and credentials. The implementation introduces a `root_relative_url()` function in `remote.c` alongside changes to `builtin/submodule--helper.c` and `submodule-config.c`, with comprehensive tests in t7428 covering cloning, syncing, nested submodules, and error conditions while rejecting local paths, `file://` URLs, and malformed inputs that would alter the URL type.

Jacob Keller provided a substantive review that thought through the design trade-offs, endorsing the approach while probing edge cases such as IPv6 in SCP-style URLs, shell escaping for `^` in `cmd.exe` and Git Bash, and the semantic distinction between `^/` (for submodules remaining at their original location) and `../` relative paths (for forked dependencies). No technical objections remain, and Junio C Hamano has now signaled that he will queue the topic in `next` for integration testing, keeping the test renumbering from t7427 to t7428 as a separate fixup commit until the series graduates from RFC status.

Junio has invited heavy submodule users to object before the topic graduates further, but the feature appears ready to move from RFC discussion into cooking. The remaining open questions are practical rather than blocking: the need for shell quoting around `^` on Windows platforms and the eventual need for ecosystem adoption by libgit2, JGit, and hosting forges.

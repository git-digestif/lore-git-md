This thread proposes a new `^/` syntax for submodule URLs that resolves relative to the superproject’s remote server root, making forks portable across arbitrary hierarchy depths (e.g., GitLab subgroups). Stanislav Aleksandrov authored the RFC patch, which has been under review with no prior versions. The design allows dynamic resolution of submodule URLs like `^/org/lib.git` against the superproject’s remote (e.g., `https://host/me/super.git` → `https://host/org/lib.git`), preserving protocol and credentials without manual configuration.

Jacob Keller provided substantive feedback on the design, focusing on syntax choice, protocol handling, and fork isolation, while acknowledging the low breakage risk of repurposing `^/`. The discussion has centered on whether the new syntax is justified over alternatives like `url.<base>.insteadOf` or relative traversal (`../../`), with the author arguing that `^/` avoids the fragility of depth-dependent paths and enables dynamic resolution across forks. Junio C Hamano has now signaled intent to queue the patch in `seen` once a test-number collision (t7427) is resolved by renumbering it to t7428, indicating the patch is ready for integration testing despite its RFC status. No new technical objections have been raised, but the justification for the new syntax remains unresolved. Open questions include shell escaping (as `^` is special in some shells), ecosystem adoption (libgit2, JGit, forges), and fork isolation semantics. The patch touches `builtin/submodule--helper.c`, `submodule-config.c`, and `remote.c`, introducing a new `root_relative_url()` function and comprehensive test coverage.

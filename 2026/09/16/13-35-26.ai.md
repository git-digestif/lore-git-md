This is a **substantive review** of the ongoing stash/merge autostash bug. Phillip Wood, a contributor with deep knowledge of Git's sequencer and merge machinery, joins the thread to propose a concrete fix and a more ambitious refactoring.

Phillip confirms the root cause identified earlier: `reset_head()` in `stash apply --index` prematurely deletes the `MERGE_AUTOSTASH` ref via `remove_merge_branch_state()`, leaving the autostash machinery unable to clean up after itself. His immediate fix is surgical: replace `reset_head()` with a direct call to `reset_tree(&c_tree, 0, 1)`, which resets the index to the desired tree without touching branch state. This avoids the problematic cleanup while preserving the rest of the stash apply logic.

He then sketches a more comprehensive refactoring: instead of applying the stashed index changes via `git diff-tree`, `git apply --cached`, and `git reset`, the code could use `merge_incore_nonrecursive()` to perform a proper three-way merge of the index changes. This would eliminate three subprocess calls, align the index merge with the working tree merge (which already uses `merge_ort_nonrecursive()`), and likely improve correctness. The infrastructure for this is already partially in place, as the working tree merge uses the same merge machinery.

Phillip also echoes D. Ben Knoble’s surprise at `git reset` performing undocumented branch-state cleanups, noting that this behavior likely originates from `git foo --abort` calling `git reset --merge` or `--hard`, though that doesn’t fully explain why a mixed reset also removes branch state.

The thread remains under active discussion, with no patch posted yet. The technical direction is now clearer: a small, targeted fix is available, and a larger refactoring is on the table. The choice between them will likely hinge on risk tolerance and the desire to eliminate subprocess calls. No Reviewed-by or Acked-by trailers have been added yet.

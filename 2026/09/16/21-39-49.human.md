This is a bugfix targeting Git's hook environment handling, specifically for worktrees. Junio C Hamano responds to Phil Sainty's report with a proposed patch that would export `GIT_WORK_TREE` alongside `GIT_DIR` when a worktree is detected. The patch touches `setup.c` and addresses the issue where `git rev-parse --show-toplevel` (and likely other Git commands) fails to return the correct worktree root in `post-checkout` hooks.

The patch is straightforward: it modifies `setup_git_directory_gently()` to set `GIT_WORK_TREE` in the environment when both a worktree exists and `GIT_DIR` is already being exported. However, Junio flags a "large NEEDSWORK comment" in the precontext of the hunk, suggesting the surrounding code may need broader reconsideration before this change is finalized. This implies the fix might not be as simple as it appears, and further discussion or refactoring could be needed.

The issue itself is well-documented in the thread, with clear reproduction steps across multiple Git versions (2.34, 2.55 maint, and 2.56.0.rc0). The problem is specific to worktrees—hooks in the main worktree behave as expected—and affects scripts that rely on `GIT_WORK_TREE` to locate the repository root. While the `githooks(5)` man page hints at this expectation, it doesn’t explicitly require `GIT_WORK_TREE` to be set, leaving room for ambiguity.

Junio’s patch is a plausible starting point, but the NEEDSWORK comment raises questions about whether this is the right long-term solution. The fix is narrowly scoped to `post-checkout` hooks (though the author notes other hooks might be affected), and no objections or alternative approaches have been raised yet. This looks like a real bug with a reasonable proposed fix, but the surrounding code’s complexity may delay its resolution. Worth watching if you rely on worktree hooks.

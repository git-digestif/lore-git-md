Subject: [PATCH] compat/winansi: fix die_lasterr() formatting bug
Series version: standalone patch
Originating author: Yongqiang Tian
Thread type: bugfix

Core problem or goal
Fix a long-standing formatting bug in `compat/winansi.c:die_lasterr()` that causes Windows API failure messages to display the address of a `va_list` instead of the intended integer handle when `DuplicateHandle()` fails. The bug has no effect on other callers, which pass fixed strings.

Current status
Under review; no prior versions. The patch has evolved through four distinct approaches: the original variadic function (Yongqiang Tian), a variadic-removal refactor (Johannes Sixt), a macro-based simplification (René Scharfe), and now a fourth approach (Yongqiang Tian) that inlines Windows-specific error reporting at each call site, removing `die_lasterr()` entirely. The latest version (v4) resolves all prior technical objections by avoiding `va_list` forwarding, heap allocation, and POSIX `errno` conversion, and aligns with existing Windows-specific error reporting in Git. Johannes Sixt has endorsed the inlined approach in principle, requesting only minor cosmetic adjustments (handle formatted as `%li` and consistent error message text). Yongqiang Tian has incorporated the `%li` formatting but retains the original error message phrasing; this cosmetic difference remains the sole open item. The patch is otherwise ready for integration and is a strong candidate for `next`.

Key technical details
- File: `compat/winansi.c`
- Function: `die_lasterr()` (removed)
- New symbols: none
- Behavior change: Windows API failure messages now show the raw `GetLastError()` value and the handle (formatted as `%li`) directly in the error message, without any intermediate `va_list` or `errno` conversion. The change is consistent with other Windows-specific error reporting in Git (e.g., `compat/win32/syslog.c` and `compat/fsmonitor/fsm-listen-win32.c`).
- On-disk format: unchanged
- Test coverage: none added; the bug is in a fatal-error helper that is difficult to trigger deterministically. Verification relies on manual inspection and building with `DEVELOPER=1` under MinGW GCC 13.

Open questions and loose ends
The only remaining discussion point is cosmetic: whether the error message should use "Windows error" (Johannes Sixt’s suggestion) or the current phrasing in the patch ("Failed to duplicate handle: %li, Windows error: %lu"). No technical objections remain; resolution depends on Yongqiang Tian’s preference or a maintainer’s final call.

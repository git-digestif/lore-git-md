Thread identity
Subject: [PATCH] compat/winansi: fix die_lasterr() formatting bug
Series version: standalone patch (v4)
Originating author: Yongqiang Tian
Thread type: bugfix

Core problem or goal
Fix a long-standing formatting bug in `compat/winansi.c:die_lasterr()` that causes Windows API failure messages to display the address of a `va_list` instead of the intended integer handle when `DuplicateHandle()` fails. The bug has no effect on other callers, which pass fixed strings.

Current status
**Ready for integration into `next`**. The patch has evolved through four distinct approaches: the original variadic function (Yongqiang Tian), a variadic-removal refactor (Johannes Sixt), a macro-based simplification (René Scharfe), and the current inlined Windows-specific approach (v4). Junio C Hamano reviewed v4 and found no technical issues, requesting only minor commit message improvements (removing build verification details and adding a `Helped-by:` trailer for Johannes Sixt). Yongqiang Tian addressed these in v4 by moving build verification details below the separator and adding `Helped-by:` trailers for Johannes Sixt and René Scharfe. Johannes Sixt’s **Acked-by** (tested) on the v3 patch removes the last procedural hurdle. The sole remaining cosmetic discussion (error message phrasing: "Windows error" vs. "Failed to duplicate handle: %li, Windows error: %lu") is not considered a blocker by Junio.

Key technical details
- File: `compat/winansi.c`
- Function: `die_lasterr()` (removed)
- New symbols: none
- Behavior change: Windows API failure messages now show the raw `GetLastError()` value and the handle (formatted as `%li`) directly in the error message, without any intermediate `va_list` or `errno` conversion. The change aligns with existing Windows-specific error reporting in Git (e.g., `compat/win32/syslog.c` and `compat/fsmonitor/fsm-listen-win32.c`).
- On-disk format: unchanged
- Test coverage: none added; the bug is in a fatal-error helper that is difficult to trigger deterministically. Verification relies on manual inspection and building with `DEVELOPER=1` under MinGW GCC 13.

Open questions and loose ends
The only unresolved item is cosmetic: whether the error message should use "Windows error" (Johannes Sixt’s suggestion) or the current phrasing ("Failed to duplicate handle: %li, Windows error: %lu"). No technical objections remain; resolution depends on Yongqiang Tian’s preference or a maintainer’s final call.

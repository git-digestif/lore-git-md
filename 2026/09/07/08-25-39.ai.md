This is the second patch in Patrick Steinhardt’s 9-patch series refactoring ODB alternates handling during repository creation, part of the ongoing ODB abstraction effort. It defers object database (ODB) initialization in `git clone` until after the clone source URI is resolved, addressing two key issues: forward compatibility with alternate ODB backends (which may require object hash information at creation time) and the need to resolve alternates paths before ODB setup.

The patch moves the `create_object_database()` call in `cmd_clone()` to occur after URI resolution and transport setup, ensuring alternates can be written with full context. It also defers `setup_reference()` (which configures alternates) until after ODB creation, as this function depends on the ODB being initialized. The change is mechanical but foundational: it enables subsequent patches to write alternates during ODB creation (via `odb_create_on_disk_options`) and eliminates a latent dependency on unresolved URIs.

The diff touches only `builtin/clone.c`, shifting four lines of code to a later point in the function. No new symbols or behavior changes are introduced here—this is purely a reordering to prepare for later patches. The commit message clearly explains the rationale, including the forward-looking concern about ODB backends requiring object hash information and the practical need to resolve URIs before writing alternates.

This patch directly addresses feedback from v2, where Justin Tobler noted the growing complexity of `init_db()`’s skip flags. By deferring ODB setup, Patrick’s refactoring avoids the need for additional flags and aligns with the series’ goal of simplifying repository initialization. The change is uncontroversial and appears well-motivated, though reviewers may verify that the reordering doesn’t introduce regressions in edge cases (e.g., template config rewriting URIs). The patch is a necessary stepping stone for the lockfile-based alternates writing in patch 6.

This thread is about a bug in Git 2.55.0 where `git merge --ff-only --autostash` (and `git pull` with `rebase.autoStash` and `pull.rebase`) leaves behind a redundant stash entry and fails to clean up the `MERGE_AUTOSTASH` ref when `stash.index=true` is set and staged changes exist. The issue was confirmed and reproduced by Eli Barzilay, who also provided a reproduction script and traced the problematic code path.

D. Ben Knoble implemented a fix that replaces the original subprocess-heavy approach (`git diff-tree`, `git apply --cached`, `git reset`) with a direct call to `merge_incore_nonrecursive()`. This resolves the root cause—premature deletion of the `MERGE_AUTOSTASH` ref—while improving performance and code clarity. Phillip Wood reviewed the patch, confirming it works and suggesting minor polish: silencing merge verbosity (since conflicts already trigger an abort), simplifying conflict-label setup, and using `oidcpy()` for robustness. The patch is now in its final polish phase, with Knoble incorporating these adjustments before submitting it as a formal series.

The fix touches `sequencer.c` and involves key symbols like `MERGE_AUTOSTASH`, `merge_incore_nonrecursive()`, and `oidcpy()`. It eliminates three subprocess spawns, preserves the `MERGE_AUTOSTASH` ref until autostash apply completes, and avoids index corruption caused by cleared stat data and `CE_UPTODATE` flags. While the fix is confirmed to work locally by both Knoble and Wood, a formal test in the Git test suite is still pending. The next step is submission to `master`, with potential backporting to the maintenance track still under consideration. The discussion has been collaborative and substantive, with both contributors aligned on the solution.

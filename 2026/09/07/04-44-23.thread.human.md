This thread is about a **bug in Git 2.55.0** (and current `master`) where `git merge --autostash` with `stash.index=true` leaves behind a redundant stash entry and fails to clean up the `MERGE_AUTOSTASH` ref, producing an error message despite the merge succeeding. The issue affects users who stage changes before merging with `--autostash` (common in `git pull` workflows with `rebase.autoStash` and `pull.rebase` enabled).

Eli Barzilay reported the bug with a **clear reproduction script** and a **detailed root-cause analysis**. The problem stems from a layering violation: `git stash apply --index` (triggered by `--autostash`) calls `reset_head()`, which invokes `remove_merge_branch_state()`. This function prematurely saves and deletes the `MERGE_AUTOSTASH` ref while the autostash machinery is still using it, leading to a duplicate stash entry and a spurious error when the parent process tries to clean up the same ref. The bug only surfaces when staged changes exist, as the `--index` apply path is required to trigger the problematic reset.

The thread is currently in the **diagnosis phase**—no patch has been proposed yet, but the report is thorough enough for a reviewer to implement a fix. Two plausible solutions were suggested: shielding `MERGE_AUTOSTASH` during apply or avoiding branch-state cleanup in `stash`'s `reset_head()`. The bug is well-scoped, affects real workflows, and appears to be a straightforward ref-management issue rather than a deep architectural problem. Key files involved include `builtin/merge.c`, `sequencer.c`, `builtin/stash.c`, and `branch.c`. No reviews or maintainer decisions have been posted yet.

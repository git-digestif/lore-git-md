This thread is about a bug in Git 2.55.0 where `git merge --ff-only --autostash` (and `git pull` with `rebase.autoStash` and `pull.rebase`) leaves behind a redundant stash entry and fails to clean up the `MERGE_AUTOSTASH` ref when `stash.index=true` is set and staged changes exist. Eli Barzilay reported the issue, provided a reproduction script, and traced the root cause to premature deletion of the `MERGE_AUTOSTASH` ref during `stash apply --index`.

D. Ben Knoble confirmed the bug, reproduced it locally, and implemented a fix by replacing the subprocess-heavy index-merge logic (`git diff-tree`, `git apply --cached`, `git reset`) with a direct call to `merge_incore_nonrecursive()`. This resolves the root cause while improving performance and code clarity. Phillip Wood reviewed the patch, confirmed it works, and suggested minor polish: silencing merge verbosity (since conflicts already trigger an abort), simplifying conflict-label setup, and using `oidcpy()` for robustness. The patch is now one cleanup pass away from formal submission.

The fix touches `sequencer.c` and has implications for `builtin/merge.c`, `builtin/stash.c`, and `branch.c`. It preserves the `MERGE_AUTOSTASH` ref until autostash apply completes, eliminating the duplicate stash entry and error message. No formal test has been added yet, but the reproduction script and local validation confirm the fix. The broader layering violation—`git reset` performing undocumented branch-state cleanups—was noted but won’t be addressed in this thread. The next step is Knoble’s final polish and submission.

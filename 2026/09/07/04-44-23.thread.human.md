This thread is about a bug in Git 2.55.0 where `git merge --ff-only --autostash` (and `git pull` with `rebase.autoStash` and `pull.rebase`) leaves behind a redundant stash entry and fails to clean up the `MERGE_AUTOSTASH` ref when `stash.index=true` is set and staged changes exist. The bug has been confirmed and reproduced by Eli Barzilay, who also provided a detailed analysis and a reproduction script.

D. Ben Knoble, who originally added the `stash.index` configuration, has reviewed the bug report and agrees with Eli's analysis. He reproduced the issue locally and traced the problem to `git stash apply --index` invoking `reset_head()`, which calls `remove_merge_branch_state()`. This function prematurely deletes the `MERGE_AUTOSTASH` ref while the autostash apply is still using it, causing a later ref-deletion failure and leaving a duplicate stash entry. D. Ben Knoble expressed surprise at this behavior, noting that `git reset` performs these branch-state cleanups without clear documentation. He experimented with replacing the `git reset` subprocess call with a direct `reset_working_tree()` invocation but hasn't yet resolved the issue. He also considered disabling `stash.index` for merge autostashes but dismissed it as a superficial fix.

The discussion is substantive and focused on the technical details of the bug. No patch has been posted yet, but the analysis is thorough, and the participants are actively engaged in finding a solution. The key open question remains which of the two suggested fixes—shielding `MERGE_AUTOSTASH` during apply or avoiding branch-state cleanup in `stash`'s `reset_head()`—will be implemented. There are no Reviewed-by or Acked-by trailers yet, and it's still undecided whether the fix will be backported to the maintenance track.

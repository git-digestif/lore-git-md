This thread is about a bug in Git 2.55.0 (and current master) where `git merge --ff-only --autostash` (and by extension `git pull` with `rebase.autoStash` and `pull.rebase`) leaves behind a redundant stash entry and fails to clean up the `MERGE_AUTOSTASH` ref when `stash.index=true` is set and staged changes exist at merge time. The operation succeeds but emits an error message, cluttering the stash list with an extra entry.

The bug has been confirmed and reproduced by three participants: Eli Barzilay (who reported it and provided a reproduction script), D. Ben Knoble, and Phillip Wood. The root cause is a premature deletion of the `MERGE_AUTOSTASH` ref during `stash apply --index`, triggered by `reset_head()` calling `remove_merge_branch_state()`. Phillip Wood has proposed two fixes: a surgical one replacing `reset_head()` with `reset_tree()`, and a more ambitious refactoring using `merge_incore_nonrecursive()` for the index merge to eliminate subprocess calls and align with working tree merge logic. Both Ben Knoble and Phillip Wood have noted that `git reset`'s undocumented branch-state cleanup is surprising and poorly documented, though this broader issue isn't being addressed in the current thread.

The discussion is active and substantive, focusing on correctness and code quality. Ben Knoble plans to test Phillip's proposed fixes and may contribute implementation work soon. No patches have been posted yet, and no Reviewed-by or Acked-by trailers have been added. The fix will likely target `builtin/merge.c` and `sequencer.c`, with the choice between the surgical fix and the refactoring still open. Whether the fix will be backported to the maintenance track also remains undecided.

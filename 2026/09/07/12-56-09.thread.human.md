This thread is about a small but user-visible fix to Git’s advice subsystem, specifically the `defaultBranchName` message that appears when creating a new repository. The original issue was that the on-screen instructions told users to run `git config set advice.defaultBranchName false`, which only disables the message for the current repository—not globally, where the setting actually belongs. Vsevolod Myalitsin proposed a fix that changes the displayed command to recommend `git config --global` (or `set --global`, depending on a minor syntax debate) and refactored the underlying code to make the scope configurable for future advice keys.

The core patch is now effectively ready: it uses a `scope_hint` field in the `advice_setting` struct to let each advice key specify its preferred configuration scope (e.g., `--global` or `--system`), and it maintains backward compatibility by passing `NULL` to the internal `vadvise()` helper when no advice config is associated. Junio C Hamano and Jeff King (Peff) helped refine the design, and the latest version (v3) addresses all architectural concerns. The only unresolved detail is a minor syntax preference—whether the displayed command should use `--global` or `set --global`—but this isn’t a blocker.

Alongside the fix, Junio posted a mechanical refactoring patch that converts existing `advice_enabled()` + `advise()` call sites to the newer `advise_if_enabled()` helper, reducing boilerplate. The patch is mostly complete, but Peff noted that the Coccinelle rule missed a few call sites with complex conditionals (e.g., in `commit.c`), which may require a follow-up. There was also a brief design discussion about whether `advise_if_enabled()`’s turn-off instructions are too verbose, but Junio and Peff agreed that the current approach is correct: advice messages should either be *always* useful (shown unconditionally via `advise()`) or *so rare* that turn-off instructions aren’t needed (also favoring `advise()`). For everything else, `advise_if_enabled()` is the right tool. The refactoring patch doesn’t change user-visible behavior, but it reopens the question of whether the codebase should standardize on the newer helper.

The thread is now in a quiet phase: the core fix is ready to merge, and the refactoring patch just needs a final check for mechanical completeness. No major objections remain, and the key participants (Junio, Peff, and Vsevolod) are aligned on the design.

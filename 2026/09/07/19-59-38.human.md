This is the fifth patch in brian m. carlson’s seven-patch RFC series proposing a Git 3.0 breaking change: restricting hex object IDs to lowercase only. The series is part of a broader effort to eliminate security and compatibility risks caused by Git’s current case-insensitive hex parsing.

This patch replaces an open-coded hex-parsing loop in `object-name.c` with the new `hexval()` helper introduced earlier in the series. The old implementation manually mapped ASCII characters to their hex values and forced uppercase letters to lowercase; the new version delegates that logic to `hexval()`, which is table-driven, more efficient, and (in later patches) will enforce lowercase-only parsing. The patch preserves the existing behavior of lowercasing the output hex string, but it does change the internal representation: the old code lowercased as it parsed, while the new code parses first and lowercases afterward. This behavioral difference is documented in the commit message and is intentional for the transition period.

The change is minimal—only 15 lines in a single file—and is purely preparatory. It does not yet enforce lowercase-only parsing (that comes in patch 7), but it lays the groundwork by switching to the infrastructure that will later carry the enforcement. The patch is well-motivated: the commit message explains why the table-driven `hexval()` is preferable to the open-coded loop (speed, maintainability, and future extensibility), and the code itself is straightforward. No test failures or regressions are expected, and the patch has already addressed Elijah Newren’s earlier correctness concern about storing `hexval()`’s unsigned result in an `int`.

This patch is uncontroversial on its own; the real discussion remains whether the project will accept the breaking change in patch 7. For now, this is a clean refactoring that moves the codebase one step closer to that decision.

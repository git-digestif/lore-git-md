This is a reply in the ongoing `post-worktree` hook discussion, offering an alternative design. Kristoffer Haugsbakk suggests replacing the proposed `post-worktree` hook with a `--id=<string>` option for `git worktree add`. The idea is to let tools "own" worktrees by tagging them with an ID; commands like `git worktree remove` or `git worktree prune` would then ignore worktrees that don’t match the provided ID, eliminating the need for hooks entirely.

The proposal is motivated by the same problem Domen Kožar raised—multiple tools (IDEs, AI agents, devenv) creating and deleting worktrees—but takes a different approach. Instead of notifying tools after the fact via hooks, it prevents uncontrolled callers from interfering with worktrees they don’t own. Kristoffer sketches how this could enable tools to manage worktree pools safely, even adding metadata like expiry timestamps without requiring changes to Git itself.

The email is a design counterproposal, not a patch or review. It doesn’t engage with Domen’s observability argument (racing with other operations, damaged entries) or Junio C Hamano’s original objection about hook necessity. The thread remains stalled on the fundamental question of whether Git should provide a native mechanism for lifecycle notifications, with this email adding a new option to the table.

This is the second patch in a three-patch series that defers Git’s auto maintenance until the end of sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`). The goal is to prevent maintenance from running during intermediate steps, matching the behavior of the apply backend and avoiding lock contention.

The patch itself adds a call to `run_auto_maintenance()` at three exit points in `sequencer.c`: `sequencer_finish()`, `continue_single_pick()`, and `single_pick()`. This ensures maintenance runs exactly once per sequence, after autostash is applied. The author has already addressed earlier feedback on scope (covering all three commands) and code structure (adding a reusable helper for building `GIT_CONFIG_PARAMETERS` strings).

In this reply, the author clarifies two key points raised by Patrick Steinhardt’s review. First, the patch changes behavior for conflict-free sequences: previously, such sequences never ran maintenance at all; now they run it once at the end, just like a regular `git commit`. This is a deliberate alignment with the apply backend and is not expected to cause issues. Second, the author proposes an alternative design that moves the maintenance call out of the sequencer entirely, instead letting the caller (`rebase.c` or `builtin/revert.c`) trigger it once the sequencer state is cleaned up. This would unify the exit path and reduce scattering, addressing Patrick’s stylistic concern.

The patch is technically sound and the discussion is now about code organization rather than correctness. The author’s proposed refactor looks promising and would simplify the logic further. No functional objections remain; the only open items are commit message clarity and the mechanical choice between the current three-call approach and the single-exit-path alternative. This is a well-motivated, low-risk change that should land soon.

This is a bug report for a subtle but real issue in Git's autostash handling. When `stash.index=true` is set, a fast-forward merge with `--autostash` leaves behind a redundant stash entry and fails to clean up the `MERGE_AUTOSTASH` ref, producing an error message that’s easy to overlook.

The problem surfaces when there’s a staged change at merge time. The autostash is applied correctly, but the cleanup logic gets tangled: `git stash apply --index` triggers a `git reset` that prematurely deletes the `MERGE_AUTOSTASH` ref, causing the parent process to fail when it tries to delete the same ref moments later. The result is a leftover stash entry that duplicates what’s already in the working tree and index, and the error message is the only visible symptom. The command exits successfully, so users might not notice unless they check `git stash list`.

The report includes a minimal reproduction script that works regardless of configuration, and the analysis traces the bug through the call stack: `builtin/merge.c` → `sequencer.c` → `builtin/stash.c` → `builtin/reset.c` → `branch.c`. The issue is specific to the merge backend’s ref-based autostash storage; the rebase backend (which uses a file) isn’t affected. This is a real edge case, but it’s well-documented and reproducible, making it a credible bug rather than a misconfiguration or misunderstanding.

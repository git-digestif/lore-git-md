This thread is about a three-patch series from Beat Bolli aimed at improving OpenSSL compatibility and correctness in `git imap-send`. The series is now at v3, but it remains blocked by a critical security regression in the second patch.

The first patch, which updates TLS initialization to use the modern `TLS_method()` API instead of the deprecated `SSLv23_method()`, is uncontroversial and has been stable since v2. The second patch, however, attempts to replace Git’s manual hostname verification with OpenSSL’s built-in `SSL_set1_host()` API for better RFC 6125 compliance. While this change improves security in theory, it introduced two serious regressions: a **security hole** (certificate stripping, creating a trivial MITM vector) and an **error reporting issue** (losing hostname-specific error messages when verification fails). The third patch in v3, which just arrived, adds a custom verification callback to restore the lost error context, but it doesn’t fix the security regression.

Patrick Steinhardt identified the security regression in his review of v2, and it remains the primary blocker. The new third patch in v3 addresses the error reporting issue by implementing Xiangfei Ding’s suggestion to capture hostname mismatches in a callback, but this doesn’t resolve the certificate-stripping vulnerability. Beat also added a fourth patch in this email—forward-compatibility macros for OpenSSL 4.0—but this is premature given the unresolved security issue and risks distracting reviewers.

The series touches only `imap-send.c` and doesn’t change on-disk formats, but it lacks test coverage for these security-sensitive code paths. Junio C Hamano previously flagged a memory-safety bug in the v1 series, which has competing fixes but remains unresolved. The v3 series splits off the uncontroversial TLS initialization patch while leaving the hostname verification rewrite and its regressions as the main focus. Until the security regression is fixed, the series won’t move forward.

## 2026/09/07

- [2026/09/07/04-44-23 by Eli Barzilay <eli@barzilay.org>] Eli Barzilay reported a bug where `stash.index=true` causes a successfully applied merge autostash to be stored as a redundant stash entry and makes deletion of `MERGE_AUTOSTASH` fail with "cannot lock ref"; a staged change is required to trigger it, and the common path is `git pull` with `rebase.autoStash` and `pull.rebase` fast-forwarding via `git merge --ff-only --autostash`.

## 2026/09/16

- [2026/09/16/13-35-26 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood proposed two fix directions for the stash.index=true autostash bug: the simplest being to replace `reset_head()` with `reset_tree(&c_tree, 0, 1)` (since stash has its own `unpack_trees()` wrapper), or alternatively to avoid touching the index entirely by using `merge_incore_nonrecursive()` to cherry-pick the stashed index changes as a proper three-way merge, reusing the setup already used for `merge_ort_nonrecursive()` on working-tree changes and avoiding subprocesses for "git diff-tree", "git apply --cached", and "git reset". He also agreed that the reset manual's silence about `remove_merge_branch_state()` cleanups is odd, suggesting it stems from "git foo --abort" calling "git reset (--merge|--hard)", though that doesn't explain why a mixed reset also removes branch state.
- [2026/09/16/14-30-30 by Ben Knoble <ben.knoble@gmail.com>] Ben Knoble thanked Phillip Wood for the pointers, said he would try to make and test patches the following day, and might send out his own notes/questions about the existing code later that day; he agreed the abort explanation makes sense but was hesitant to change that side-channel for now.
- [2026/09/16/19-57-37 by Eli Barzilay <eli@barzilay.org>] Eli Barzilay noted from the sidelines that leftover dead autostashes are the only drawback he has found in using `stash.index` with `rebase.autoStash`, and offered to try patches if helpful.

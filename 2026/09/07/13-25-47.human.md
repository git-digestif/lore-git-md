This is the second patch in a v2 series that makes auto maintenance run exactly once at the end of sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`), matching the apply backend’s behavior. The patch itself is technically sound: it adds `run_auto_maintenance()` calls to the three exit paths where the sequencer finalizes its work, ignores maintenance errors to avoid masking user-facing issues, and updates test coverage to verify the new behavior.

Phillip Wood’s review focuses on clarity and test hygiene. He suggests rewording the commit message to avoid implying active interference (it’s lock contention, not opposition) and to make the description of the current behavior more precise. The code changes themselves are uncontroversial; Phillip confirms the placement of the maintenance call in `pick_commits()` is correct and notes that the single-pick variants of `cherry-pick` and `revert` could ideally share code paths with the multi-pick variants, though this is a pre-existing issue.

On the test side, Phillip raises two small points: he wonders whether the tests should explicitly assert that auto maintenance does *not* run during intermediate steps (currently they only check that it runs at the end), and he suggests using `test_grep` instead of `grep` in the cherry-pick test to improve test output if the assertion fails. Neither is a blocker, but both would tighten the test coverage.

The patch is part of a well-reviewed series that has already addressed all substantive feedback from earlier rounds. The remaining discussion is about polish and edge-case testing, not functionality. It looks ready for integration once the minor wording and test tweaks are made.

This is a bug report about a serious data-loss scenario in `git pull`.

The author describes a case where a `.gitignore` entry ending in a slash (e.g., `dataset/`) is intended to ignore a directory, but Git still allows a symlink with the same name (`dataset`) to be committed. When another user pulls the repository, Git silently replaces their local directory with the symlink, destroying all data inside the directory without warning. The issue has been reproduced on both Linux and Windows.

The report includes a concrete example: a symlink named `dataset` pointing to an external directory is added to the repository despite `.gitignore` containing `dataset/`. On another machine, a real `dataset` directory containing 64 MB of data is silently overwritten by the symlink during `git pull`. The author argues that Git should either ignore symlinks matching the ignore pattern or refuse to overwrite a local directory with a symlink without explicit user confirmation.

The impact is severe: users can lose hundreds of gigabytes of data during routine operations. The report suggests two potential fixes: making `.gitignore` patterns with trailing slashes also ignore symlinks, or detecting the conflict during pull and prompting the user. The tone is urgent and the issue is clearly motivated by a real-world incident.

This is the third patch in a three-part series that adjusts when auto maintenance runs during sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`). The goal is to defer maintenance until the sequence completes, matching the behavior of the apply backend and avoiding lock contention or packfile conflicts during intermediate steps.

The patch itself is a refinement of the mechanism introduced in the second patch. It ensures that spawned commands (`git commit`, `git merge`, or any `exec` commands) do not trigger auto maintenance by setting `GIT_CONFIG_PARAMETERS=maintenance.auto=false` in their environment. This overrides any user `-c` settings and guarantees maintenance runs exactly once at sequence completion. The implementation is technically sound: it caches the config string in `replay_ctx`, covers all three sequencer commands, and includes test coverage verifying the absence of maintenance during intermediate steps.

Phillip Wood’s review focuses on clarity and test organization. He suggests rewording the commit message to avoid implying that maintenance actively interferes (it’s lock contention, not opposition) and to clarify confusing phrasing about "rerere gc" and loose objects. The author has accepted these suggestions and will rewrite the message to describe the "git commit" spawned by `git rebase --continue` more precisely and to either rephrase or drop the note about loose objects piling up during long sequences. Phillip also questions the need for separate tests in `t3418-rebase-continue.sh` and `t3510-cherry-pick-sequence.sh`, arguing the new coverage should extend the existing tests from the previous patch rather than duplicate them. The author has agreed to consolidate the tests.

The patch is ready for integration once these minor adjustments are made. No open technical objections remain, and the series as a whole is well-motivated: it unifies auto maintenance behavior across sequencer and apply backends, eliminates a source of lock contention, and simplifies the rule to "maintenance runs once at the end." The author has also proposed an alternative design—delegating maintenance to the callers (`run_specific_rebase()` and `run_sequencer()`) rather than handling it inside the sequencer—but this is a code organization preference rather than a functional requirement, and Phillip has not yet weighed in. For now, the current implementation is a clean, minimal solution that addresses the core problem.

This is the third patch in brian m. carlson’s seven-part RFC series proposing a Git 3.0 breaking change: restricting hex object IDs to lowercase only. The patch extends the `hex_to_bytes()` function—introduced in the previous two patches—to accept an `enum hex_kind` parameter (`HEX_KIND_MIXED`, `HEX_KIND_LOWER`, or `HEX_KIND_OID`), allowing callers to specify whether the input hex should be parsed as mixed-case, lowercase-only, or object-ID-specific. All existing call sites are updated to pass `HEX_KIND_MIXED`, preserving current behavior for now; the actual enforcement of lowercase-only parsing will be introduced in a later patch (7/7).

The patch touches seven files: `builtin/index-pack.c`, `diagnose.c`, `hex-ll.c`, `hex-ll.h`, `http-push.c`, `notes.c`, and `object-file.c`. These are all low-level utilities or subsystems that parse hex-encoded object IDs from disk, network, or diagnostic output. The changes are mechanical and non-breaking: every call to `hex_to_bytes()` gains the new `HEX_KIND_MIXED` parameter, and the function’s implementation is updated to delegate the hex-digit validation to the existing `hexval()` helper (which already supports the `hex_kind` parameter). No new test coverage is added in this patch; the existing tests continue to pass because the runtime behavior is unchanged.

This patch is purely preparatory infrastructure for the eventual breaking change. It does not alter Git’s behavior, but it lays the groundwork for the seventh patch, which will define `HEX_KIND_OID` as `HEX_KIND_LOWER` when `WITH_BREAKING_CHANGES` is enabled, enforcing lowercase-only parsing. The patch is technically sound and addresses all feedback from the v1 review: Junio’s omissions (`builtin/index-pack.c` and `notes.c` now use `HEX_KIND_MIXED` instead of the old signature) and Elijah Newren’s correctness concerns (the defensive pattern `val & ~0xff` is already present in `hexval()` and is now mirrored in `hex_to_bytes()`).

The patch is uncontroversial in isolation, but it is part of a larger, still-undecided RFC. Junio’s tentative "Will queue" from the RFC stage signals movement toward integration, but the thread remains open pending broader community feedback on the breaking change itself. The unresolved questions—whether the project will accept the change, whether `HEX_KIND_OID` should cover derived hashes, and the edge case of uppercase hex in object payloads—do not affect this patch directly, but they will determine whether the series as a whole proceeds. For now, this patch is ready for deeper review if the project decides to move forward.

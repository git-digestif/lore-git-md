Subject: [PATCH 0/3] imap-send: OpenSSL compatibility and correctness fixes
Series version: v3 (follow-up to v2; this email is patch 3/3)
Originating author: Beat Bolli
Thread type: patch series

Core problem or goal
Two distinct but related OpenSSL compatibility and correctness efforts in `git imap-send`:
1. **TLS initialization** (patch 1/3): Replace the deprecated `SSLv23_method()` with the modern `TLS_method()` to avoid reliance on APIs that OpenSSL has deprecated since 1.1.0 and may remove in future releases. This patch is uncontroversial and has been carried forward unchanged from v2.
2. **Hostname verification** (patch 2/3): Replace Git’s manual, incomplete hostname verification logic with OpenSSL’s built-in `SSL_set1_host()` API (available since OpenSSL 1.1.0) to achieve full RFC 6125 compliance (including IP-type SANs) and reduce maintenance burden. The patch also addresses a behavioral regression in error reporting identified during review, but now faces **three critical regressions**:
   - **Security regression**: The removal of the `SSL_get_peer_certificate()` check creates a trivial MITM vector by allowing certificate stripping.
   - **Error reporting regression**: Under `SSL_VERIFY_PEER`, `SSL_connect()` fails early on any verification error (including hostname mismatch), making the `SSL_get_verify_result()` check unreachable and losing the hostname-specific error message.
   - **Behavioral regression**: The patch adds a redundant call to `verify_peer()` after `SSL_connect()` fails under `SSL_VERIFY_PEER`, introducing dead code since `SSL_connect()` already fails on verification errors.
3. **Verification callback** (patch 3/3, new in v3): Implements Xiangfei Ding’s proposed custom verification callback via `SSL_set_verify()` to capture hostname mismatches and store them in a "mailbox" variable, restoring the lost error context without altering the core verification logic. This patch is new to v3 and addresses the error reporting regression but does not resolve the security or behavioral regressions.
4. **OpenSSL 4.0 forward compatibility** (patch 3/3, this email): Adds macros to alias `SSL_set1_dnsname()` to `SSL_set1_host()` when building against OpenSSL versions below 4.0, ensuring the code continues to compile without warnings or errors when OpenSSL 4.0 deprecates `SSL_set1_host()`. This change is now **blocked by three technical concerns** raised by Patrick Steinhardt:
   - **Procedural issue**: The macros should have been introduced in the same commit as the `SSL_set1_host()` call (patch 2/3), not as a separate follow-up.
   - **Correctness issue**: The patch assumes `cfg->host` is always a DNS name, but OpenSSL 4.0 splits hostname verification into `SSL_set1_dnsname()` (DNS names) and `SSL_set1_ipaddr()` (IP addresses). If `cfg->host` could ever be an IP address, the current patch would silently misbehave.
   - **Clarity issue**: The error message conditionally changes the function name, which adds no value and could confuse debugging. The message should use `SSL_set1_dnsname` unconditionally.

Current status
Under review. The v3 series is **blocked on four fronts**:
1. **Process issues**: Patrick Steinhardt criticized the lack of a cover letter and range-diff in the v3 submission, making it difficult for reviewers to track changes (e.g., the addition of patch 3/3 and the OpenSSL 4.0 compatibility macros). This procedural feedback must be addressed before further technical review can proceed.
2. **Security regression**: The **security regression** in patch 2/3 (certificate stripping) remains unresolved. The verification callback in patch 3/3 restores error reporting but does not address the security issue. The OpenSSL 4.0 compatibility macros are uncontroversial in isolation but **premature** given the blocking security concern.
3. **Behavioral regression**: The redundant `verify_peer()` call in patch 2/3 introduces dead code and may confuse future maintainers. This adds to the patch’s design flaws and must be addressed alongside the security and error reporting regressions.
4. **OpenSSL 4.0 compatibility issues**: The compatibility macros in patch 3/3 are now blocked by Patrick Steinhardt’s feedback on procedural, correctness, and clarity grounds. These issues must be resolved before the macros can be merged.

The v1 series remains unresolved due to:
- A memory-safety bug in patch 2 (Junio C Hamano) with two competing fixes (Beat’s allocation-based approach vs. Patrick Steinhardt’s length-bounded operations).
- An architectural question about the OpenSSL 4.1 compatibility macro in patch 1 (contested in principle, though its necessity is now clarified).

Key technical details
Files touched: `imap-send.c` only.
Subsystem: `imap-send` (IMAP TLS initialization and certificate verification).
New/renamed symbols:
- Patch 2/3 replaces `verify_hostname()` and `host_matches()` with OpenSSL’s `SSL_set1_host()` and a new `verify_peer()` function. The `X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS` flag is set to match Git’s prior behavior (rejecting partial wildcard matches like `*.example.com` for `foo.bar.example.com`).
- Patch 3/3 introduces a new verification callback (`verify_hostname_cb`) and a "mailbox" variable (`verify_mailbox`) to pass the hostname from the callback to the error path.
- Patch 3/3 (this email) adds compatibility macros for OpenSSL 4.0: `#define SSL_set1_dnsname SSL_set1_host` when building against OpenSSL < 4.0, and updates the error message to use `SSL_set1_dnsname()`. These macros are now **blocked** by Patrick Steinhardt’s feedback on procedural, correctness, and clarity issues.
Behavior changes:
- **v3 patch 1/3**: Purely mechanical API swap (`SSLv23_method()` -> `TLS_method()`); no runtime behavior change expected.
- **v3 patch 2/3**: Replaces manual hostname verification with OpenSSL’s `SSL_set1_host()`, achieving full RFC 6125 compliance (including IP-type SANs) and improving error reporting via `X509_verify_cert_error_string()`. However, the patch introduces **three regressions**:
  1. **Security regression**: The removal of the `SSL_get_peer_certificate()` check allows certificate stripping, creating a trivial MITM vector.
  2. **Error reporting regression**: Under `SSL_VERIFY_PEER`, `SSL_connect()` fails early on any verification error (including hostname mismatch), making the `SSL_get_verify_result()` check unreachable and losing the hostname-specific error message that the old code provided.
  3. **Behavioral regression**: The new call to `verify_peer()` after `SSL_connect()` fails under `SSL_VERIFY_PEER` is redundant, as `SSL_connect()` already fails on verification errors, making the `verify_peer()` call unreachable in practice.
- **v3 patch 3/3 (verification callback)**: Installs a custom verification callback to capture hostname mismatches and store them in `verify_mailbox`, restoring the lost error context. The callback does not address the security regression, the behavioral regression, or other verification errors (e.g., expired certificates).
- **v3 patch 3/3 (this email, compatibility macros)**: Purely mechanical change to alias `SSL_set1_dnsname()` to `SSL_set1_host()` for OpenSSL < 4.0. The macros are now **blocked** by Patrick Steinhardt’s feedback on procedural, correctness, and clarity issues. No runtime behavior change expected.
- **v1 series**: Stricter RFC 6125 compliance (section 6.4.4), removal of deprecated OpenSSL API usage (contested), forward compatibility with OpenSSL 4.1 (contested), and elimination of undefined behavior from unsafe ASN1_STRING handling. The third patch’s scope remains incomplete (DNS-type SANs handled, IP-type SANs not).
On-disk format: unchanged.
Test coverage: **no tests exist** for either version; the existing test suite does not exercise the edge cases these patches fix (e.g., certificate stripping, hostname verification failures). The v3 patches are compile-time swaps with no expected runtime behavior changes beyond stricter RFC 6125 compliance, but the security regression undermines this goal.

Open questions and loose ends
- **v1 series**:
  - **Memory-safety bug in patch 2**: Junio C Hamano identified a heap corruption issue in the original allocation-based fix. Two proposed solutions exist: (1) Beat’s revised approach (separate `pattern_to_free` variable for `free()`), or (2) Patrick Steinhardt’s alternative (length-bounded string operations with `memchr` and `strncasecmp`).
  - **OpenSSL 4.1 compatibility macro in patch 1**: The macro’s necessity is now clarified (OpenSSL will hide `ASN1_STRING_length()` when `OPENSSL_API_COMPAT` is set for 4.1+), but its inclusion remains contested in principle.
- **v3 series**:
  - **Process issues**: The lack of a cover letter and range-diff in the v3 submission must be addressed to facilitate review. This is now a **blocker** for further technical feedback.
  - **Security regression**: The removal of the `SSL_get_peer_certificate()` check must be reverted or replaced with equivalent logic to block certificate stripping. This is the **primary technical blocker** for the series.
  - **Behavioral regression**: The redundant `verify_peer()` call in patch 2/3 must be removed or justified. Patrick Steinhardt’s feedback suggests it is dead code and should not be introduced.
  - **Verification callback scope**: The new callback in patch 3/3 restores the hostname-specific error message but does not address other verification errors (e.g., expired certificates) or the security/behavioral regressions. It is unclear whether the callback should be extended to handle these cases or if separate fixes are needed.
  - **OpenSSL 4.0 compatibility macros**: The macros must be revised to address:
    - **Procedural issue**: Fold the macros into patch 2/3.
    - **Correctness issue**: Add runtime validation to ensure `cfg->host` is a DNS name (or document the assumption that it cannot be an IP address).
    - **Clarity issue**: Use `SSL_set1_dnsname` unconditionally in the error message.
  - **Test coverage**: Patrick Steinhardt highlighted the absence of tests for this security-sensitive code path. Tests should be added to verify:
    - Certificate stripping is blocked.
    - Hostname verification behaves as expected (including edge cases like IP SANs and wildcards).
    - Error messages are informative and consistent with prior behavior.
    - The redundant `verify_peer()` call does not introduce unintended side effects.
  - **Implementation details**: The `X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS` flag’s behavior may still draw review scrutiny to ensure it matches Git’s prior expectations. Patrick Steinhardt questioned whether `X509_CHECK_FLAG_NO_WILDCARDS` would be more appropriate, though this is less critical than the security and behavioral issues.

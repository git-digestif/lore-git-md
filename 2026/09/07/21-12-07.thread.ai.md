Subject: [PATCH 0/3] imap-send: OpenSSL compatibility and correctness fixes

Originating author: Beat Bolli

Core problem or goal
Two distinct but related OpenSSL compatibility and correctness efforts in `git imap-send`:
1. **TLS initialization** (patch 1/2 of v2): Replace the deprecated `SSLv23_method()` with the modern `TLS_method()` to avoid reliance on APIs that OpenSSL has deprecated since 1.1.0 and may remove in future releases.
2. **Hostname verification** (patch 2/2 of v2): Replace Git’s manual, incomplete hostname verification logic with OpenSSL’s built-in `SSL_set1_host()` API (available since OpenSSL 1.1.0) to achieve full RFC 6125 compliance (including IP-type SANs) and reduce maintenance burden. The patch also addresses a behavioral regression in error reporting identified during review, but now faces **two regressions**:
   - **Security regression**: The removal of the `SSL_get_peer_certificate()` check creates a trivial MITM vector by allowing certificate stripping.
   - **Error reporting regression**: Under `SSL_VERIFY_PEER`, `SSL_connect()` fails early on any verification error (including hostname mismatch), making the `SSL_get_verify_result()` check unreachable and losing the hostname-specific error message.
3. **Proposed follow-up**: Xiangfei Ding suggests installing a custom verification callback via `SSL_set_verify()` to capture hostname mismatches and store them in a "mailbox" variable, restoring the lost error context without altering the core verification logic.
3. **Original v1 series** (carried forward but now superseded by v2): Three correctness and forward-compatibility fixes in TLS certificate verification logic: (a) OpenSSL 4.1 API deprecation workaround, (b) memory-safety fix for ASN1_STRING handling, and (c) stricter RFC 6125 compliance for certificate hostname validation. The v2 series splits off the uncontroversial parts, leaving the v1 series blocked on unresolved technical concerns (memory-safety bug and contested OpenSSL 4.1 compatibility macro).

Current status
Under review. The v2 series is **blocked** due to the **security regression** in patch 2/2. The error reporting regression is now addressed by Xiangfei Ding’s proposed callback mechanism, but this remains unimplemented. The v1 series remains unresolved due to:
- A memory-safety bug in patch 2 (Junio C Hamano) with two competing fixes (Beat’s allocation-based approach vs. Patrick Steinhardt’s length-bounded operations).
- An architectural question about the OpenSSL 4.1 compatibility macro in patch 1 (contested in principle, though its necessity is now clarified).

Key technical details
Files touched: `imap-send.c` only.
Subsystem: `imap-send` (IMAP TLS initialization and certificate verification).
New/renamed symbols: none in the v2 series. Xiangfei’s proposal introduces a new verification callback and a "mailbox" variable to pass the hostname from the callback to the error path.
Behavior changes:
- **v2 patch 1/2**: Purely mechanical API swap (`SSLv23_method()` -> `TLS_method()`); no runtime behavior change expected.
- **v2 patch 2/2**: Replaces manual hostname verification with OpenSSL’s `SSL_set1_host()`, achieving full RFC 6125 compliance (including IP-type SANs) and improving error reporting via `X509_verify_cert_error_string()`. The `X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS` flag is set to match Git’s prior behavior (rejecting partial wildcard matches like `*.example.com` for `foo.bar.example.com`). However, the patch introduces **two regressions**:
  1. **Security regression**: The removal of the `SSL_get_peer_certificate()` check allows certificate stripping, creating a trivial MITM vector.
  2. **Error reporting regression**: Under `SSL_VERIFY_PEER`, `SSL_connect()` fails early on any verification error (including hostname mismatch), making the `SSL_get_verify_result()` check unreachable and losing the hostname-specific error message that the old code provided. Xiangfei’s proposed callback mechanism would restore this context by capturing the hostname mismatch in a "mailbox" variable.
- **v1 series**: Stricter RFC 6125 compliance (section 6.4.4), removal of deprecated OpenSSL API usage (contested), forward compatibility with OpenSSL 4.1 (contested), and elimination of undefined behavior from unsafe ASN1_STRING handling. The third patch’s scope remains incomplete (DNS-type SANs handled, IP-type SANs not).
On-disk format: unchanged.
Test coverage: **no tests exist** for either version; the existing test suite does not exercise the edge cases these patches fix (e.g., certificate stripping, hostname verification failures). The v2 patches are compile-time swaps with no expected runtime behavior changes beyond stricter RFC 6125 compliance, but the security regression undermines this goal. Xiangfei’s proposal does not address test coverage.

Open questions and loose ends
- **v1 series**:
  - **Memory-safety bug in patch 2**: Junio C Hamano identified a heap corruption issue in the original allocation-based fix. Two proposed solutions exist: (1) Beat’s revised approach (separate `pattern_to_free` variable for `free()`), or (2) Patrick Steinhardt’s alternative (length-bounded string operations with `memchr` and `strncasecmp`).
  - **OpenSSL 4.1 compatibility macro in patch 1**: The macro’s necessity is now clarified (OpenSSL will hide `ASN1_STRING_length()` when `OPENSSL_API_COMPAT` is set for 4.1+), but its inclusion remains contested in principle.
- **v2 series**:
  - **Security regression**: The removal of the `SSL_get_peer_certificate()` check must be reverted or replaced with equivalent logic to block certificate stripping. This is the **primary blocker** for the series.
  - **Error reporting regression**: Xiangfei Ding’s proposed callback mechanism would restore the hostname-specific error message, but it remains unimplemented. The proposal does not address whether the callback should also handle other verification errors or how it interacts with the `SSL_VERIFY_PEER` flag.
  - **Test coverage**: Patrick Steinhardt highlighted the absence of tests for this security-sensitive code path. Tests should be added to verify:
    - Certificate stripping is blocked.
    - Hostname verification behaves as expected (including edge cases like IP SANs and wildcards).
    - Error messages are informative and consistent with prior behavior.
  - **Implementation details**: The `X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS` flag’s behavior may still draw review scrutiny to ensure it matches Git’s prior expectations. Patrick Steinhardt questioned whether `X509_CHECK_FLAG_NO_WILDCARDS` would be more appropriate, though this is less critical than the security issue.

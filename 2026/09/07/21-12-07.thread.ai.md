Core problem or goal
Two distinct but related OpenSSL compatibility and correctness efforts in `git imap-send`:
1. **TLS initialization** (this patch): Replace the deprecated `SSLv23_method()` with the modern `TLS_method()` to avoid reliance on APIs that OpenSSL has deprecated since 1.1.0 and may remove in future releases.
2. **Original v1 series** (carried forward): Three correctness and forward-compatibility fixes in TLS certificate verification logic: (a) OpenSSL 4.1 API deprecation workaround, (b) memory-safety fix for ASN1_STRING handling, and (c) stricter RFC 6125 compliance for certificate hostname validation.

Current status
Under review; v1 remains unresolved due to multiple technical concerns, while v2 (this patch) is a narrower, uncontroversial subset. No maintainer decisions or merge status reported for either version. The v1 series still faces:
- A memory-safety bug in patch 2 (Junio C Hamano) with two competing fixes (Beat’s allocation-based approach vs. Patrick Steinhardt’s length-bounded operations).
- Incomplete RFC 6125 compliance in patch 3 (brian m. carlson: IP SAN handling missing).
- An architectural question about manual vs. OpenSSL-native verification (brian m. carlson).
The v2 patch (TLS_method replacement) is uncontested and ready to proceed independently.

Key technical details
Files touched: `imap-send.c` only.
Subsystem: `imap-send` (IMAP TLS initialization and certificate verification).
New/renamed symbols: none (the change replaces `SSLv23_method()` with `TLS_method()`; no new macros or flags).
Behavior changes:
- **v2 patch**: Purely mechanical API swap; no runtime behavior change expected.
- **v1 series**: Stricter RFC 6125 compliance (section 6.4.4), removal of deprecated OpenSSL API usage (contested), forward compatibility with OpenSSL 4.1 (contested), and elimination of undefined behavior from unsafe ASN1_STRING handling. The third patch’s scope remains incomplete (DNS-type SANs handled, IP-type SANs not).
On-disk format: unchanged.
Test coverage: no new tests for either version; existing test suite does not exercise the edge cases these patches fix. The v2 patch is compile-time only and should not affect runtime behavior.

Open questions and loose ends
- **v1 series**:
  - **Memory-safety bug in patch 2**: Junio C Hamano identified a heap corruption issue in the original allocation-based fix. Two proposed solutions exist: (1) Beat’s revised approach (separate `pattern_to_free` variable for `free()`), or (2) Patrick Steinhardt’s alternative (length-bounded string operations with `memchr` and `strncasecmp`).
  - **Incomplete RFC 6125 compliance in patch 3**: brian m. carlson notes that IP-type SANs are not handled, leaving a compliance gap for IP-based endpoints.
  - **Architectural question**: brian m. carlson asks why Git does not delegate hostname verification to OpenSSL’s built-in function (available since 1.1.0), which would reduce maintenance burden and ensure ongoing standards compliance.
  - **OpenSSL 4.1 compatibility macro in patch 1**: The macro’s necessity is now clarified (OpenSSL will hide `ASN1_STRING_length()` when `OPENSSL_API_COMPAT` is set for 4.1+), but its inclusion remains contested in principle.
- **v2 series**: None; this patch is uncontroversial.

Core problem or goal
Two distinct but related OpenSSL compatibility and correctness efforts in `git imap-send`:
1. **TLS initialization** (patch 1/2 of v2): Replace the deprecated `SSLv23_method()` with the modern `TLS_method()` to avoid reliance on APIs that OpenSSL has deprecated since 1.1.0 and may remove in future releases.
2. **Hostname verification** (this patch, 2/2 of v2): Replace Git’s manual, incomplete hostname verification logic with OpenSSL’s built-in `SSL_set1_host()` API (available since OpenSSL 1.1.0) to achieve full RFC 6125 compliance (including IP-type SANs) and reduce maintenance burden.
3. **Original v1 series** (carried forward but now superseded by v2): Three correctness and forward-compatibility fixes in TLS certificate verification logic: (a) OpenSSL 4.1 API deprecation workaround, (b) memory-safety fix for ASN1_STRING handling, and (c) stricter RFC 6125 compliance for certificate hostname validation. The v2 series splits off the uncontroversial parts, leaving the v1 series blocked on unresolved technical concerns.

Current status
Under review. The v2 series (this patch) is uncontroversial in principle and ready to proceed independently. The v1 series remains unresolved due to:
- A memory-safety bug in patch 2 (Junio C Hamano) with two competing fixes (Beat’s allocation-based approach vs. Patrick Steinhardt’s length-bounded operations).
- An architectural question about the OpenSSL 4.1 compatibility macro in patch 1 (contested in principle, though its necessity is now clarified).
The v2 patch (this email) directly addresses brian m. carlson’s two substantive concerns from the v1 series (incomplete RFC 6125 compliance and suboptimal manual verification) and is expected to be merged once reviewed.

Key technical details
Files touched: `imap-send.c` only.
Subsystem: `imap-send` (IMAP TLS initialization and certificate verification).
New/renamed symbols: none (the patch removes the `host_matches()` and `verify_hostname()` helpers and introduces no new macros or flags).
Behavior changes:
- **v2 patch 1/2**: Purely mechanical API swap (`SSLv23_method()` -> `TLS_method()`); no runtime behavior change expected.
- **v2 patch 2/2 (this patch)**: Replaces manual hostname verification with OpenSSL’s `SSL_set1_host()`, achieving full RFC 6125 compliance (including IP-type SANs) and improving error reporting via `X509_verify_cert_error_string()`. The `X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS` flag is set to match Git’s prior behavior (rejecting partial wildcard matches like `*.example.com` for `foo.bar.example.com`).
- **v1 series**: Stricter RFC 6125 compliance (section 6.4.4), removal of deprecated OpenSSL API usage (contested), forward compatibility with OpenSSL 4.1 (contested), and elimination of undefined behavior from unsafe ASN1_STRING handling. The third patch’s scope remains incomplete (DNS-type SANs handled, IP-type SANs not).
On-disk format: unchanged.
Test coverage: no new tests for either version; existing test suite does not exercise the edge cases these patches fix. The v2 patches are compile-time swaps with no expected runtime behavior changes beyond stricter RFC 6125 compliance.

Open questions and loose ends
- **v1 series**:
  - **Memory-safety bug in patch 2**: Junio C Hamano identified a heap corruption issue in the original allocation-based fix. Two proposed solutions exist: (1) Beat’s revised approach (separate `pattern_to_free` variable for `free()`), or (2) Patrick Steinhardt’s alternative (length-bounded string operations with `memchr` and `strncasecmp`).
  - **OpenSSL 4.1 compatibility macro in patch 1**: The macro’s necessity is now clarified (OpenSSL will hide `ASN1_STRING_length()` when `OPENSSL_API_COMPAT` is set for 4.1+), but its inclusion remains contested in principle.
- **v2 series**:
  - **Implementation details**: The `X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS` flag’s behavior may draw review scrutiny to ensure it matches Git’s prior expectations.
  - **Error reporting**: The switch to `X509_verify_cert_error_string()` may change the phrasing of error messages, which could affect scripts or users relying on exact output.

Subject: [PATCH 0/3] imap-send: OpenSSL compatibility and correctness fixes
Series version: v1 (initial submission)
Originating author: Beat Bolli
Thread type: patch series

Core problem or goal
Three correctness and forward-compatibility fixes in `git imap-send`'s TLS certificate verification logic:
1. Replace a deprecated OpenSSL 4.1 ASN1_STRING function with its modern equivalent (`ASN1_STRING_get_length()` replacing `ASN1_STRING_length()` via a version-gated macro).
2. Fix a latent bug: the code incorrectly assumed ASN1_STRINGs are NUL-terminated (they are not); this patch replaces unsafe direct use with a NUL-terminated copy.
3. Align certificate validation with RFC 6125 by only falling back to checking the subject common name (CN) if no DNS subject alternative names (SANs) are present; the third patch enforces this by tracking SAN DNS entries and skipping CN checks if any SANs exist.

Current status
Under review; no prior versions. No maintainer decisions or merge status reported. The second patch contains a memory-safety bug identified by Junio C Hamano that must be fixed before the series can proceed. The third patch now faces additional technical concerns about its scope (IP SAN handling) and architectural approach (manual vs. OpenSSL-native verification). Junio C Hamano also noted a minor style nit in the first patch (C++-style `//` comment instead of C-style `/* ... */`), but this is cosmetic and does not affect functionality.

Key technical details
Files touched: `imap-send.c` only.
Subsystem: `imap-send` (IMAP TLS certificate verification).
New/renamed symbols: none (the macro `ASN1_STRING_get_length` is defined only for pre-4.1 OpenSSL and maps to `ASN1_STRING_length`; the new flag `has_san_dns` is local to the verification function).
Behavior changes: stricter RFC 6125 compliance (section 6.4.4), removal of deprecated OpenSSL API usage, forward compatibility with OpenSSL 4.1, and elimination of undefined behavior from unsafe ASN1_STRING handling. The third patch’s scope is now known to be incomplete: it handles DNS-type SANs but not IP-type SANs, leaving a compliance gap for IP-based endpoints.
On-disk format: unchanged.
Test coverage: no new tests; existing test suite does not exercise the edge cases these patches fix. The compatibility macro is compile-time only and should not affect runtime behavior.

Open questions and loose ends
- **Memory-safety bug in patch 2**: Junio C Hamano identified that the code increments the `pattern` pointer after allocating it with `xmemdupz()`, then later attempts to `free()` the modified pointer, which would corrupt the heap. The fix requires keeping a separate `pattern_to_free` variable solely for the `free()` call. This defect is serious and must be addressed before the series can be merged.
- **Incomplete RFC 6125 compliance in patch 3**: brian m. carlson points out that the patch only checks DNS-type SANs, ignoring IP-type SANs. Certificates for IP-based endpoints (e.g., `1.1.1.1`) use IP-type SANs, so the current logic would incorrectly fall back to CN checks even when an IP SAN exists, violating RFC 6125.
- **Architectural question**: brian m. carlson asks why Git continues to implement certificate verification manually instead of delegating to OpenSSL’s built-in hostname verification (available since OpenSSL 1.0.2). Using OpenSSL’s native function would reduce maintenance burden and ensure ongoing compliance with evolving standards.
- **Style nit in patch 1**: Junio C Hamano noted the use of C++-style `//` comments instead of C-style `/* ... */` comments. This is cosmetic and does not block progress, but should be addressed for consistency.

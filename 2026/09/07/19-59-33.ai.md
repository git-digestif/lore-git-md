This is the second iteration of an RFC series proposing a breaking change for Git 3.0: restricting hex object IDs to lowercase only. The series is now complete at seven patches, addressing all feedback from the initial RFC. The core goal remains unchanged—enforcing lowercase-only parsing to eliminate compatibility and security risks for external tools that assume hex uniqueness—but the implementation now includes fixes for technical omissions, behavioral subtleties, and test adjustments identified during review.

The first four patches are preparatory infrastructure: they introduce a new `hex_kind` enum (`HEX_KIND_MIXED`, `HEX_KIND_LOWER`, `HEX_KIND_OID`), a `hexval_lc_table` for lowercase-only parsing, and updated `hexval()`, `hex2chr()`, and `hex_to_bytes()` functions that accept an `enum hex_kind` parameter. These patches refactor existing hex-parsing code to use the new helpers without altering runtime behavior. The fifth patch switches `object-name.c` to use `hexval()`, preserving the original case during the transition period (a behavioral change that will be documented in the commit message). The sixth patch adjusts `t5324-split-commit-graph.sh` to avoid false positives in SHA-256 mode by changing the corruption character from "A" to "b" at position 70 (ensuring failure is due to corruption, not uppercase rejection) and from "A" to "a" at position 30 (for consistency). The final patch activates enforcement by defining `HEX_KIND_OID` as `HEX_KIND_LOWER` when `WITH_BREAKING_CHANGES` is enabled, documents the change in `Documentation/BreakingChanges.adoc`, and adds test coverage in `t1503-rev-parse-verify.sh` to verify rejection of uppercase object IDs.

Key changes from v1 include fixing a trivial typo in the `hexval_lc_table` comment (68-67 → 68-6f), moving the `t5324` test adjustments to a separate commit with an expanded commit message, restoring lowercasing in `parse_oid_prefix`, and addressing Junio’s review omissions: `builtin/index-pack.c` and `notes.c` now use `HEX_KIND_OID` instead of `HEX_KIND_MIXED`. Elijah Newren’s correctness concern—storing `hexval()`’s `unsigned int` result in an `int`—has been resolved by adopting the defensive pattern (`val & ~0xf`) from the first patch. The series remains gated behind `WITH_BREAKING_CHANGES`, targeting Git 3.0, and the breaking change is still contingent on project consensus.

The implementation touches 19 files, primarily in core hex-parsing utilities (`hex-ll.[ch]`, `hex.c`) and their consumers (`object-name.c`, `pkt-line.c`, `ref-filter.c`, etc.). No on-disk format changes are required; this is purely a parser behavior change. The test coverage is minimal but targeted: only one existing test (`t5324`) required adjustment, and the new test in `t1503` verifies the enforcement. The series is technically sound, with all known issues addressed, but the thread’s focus remains on whether the project will accept the breaking change. Junio’s tentative "Will queue" from the RFC stage still holds, but the discussion around Phillip Wood’s adjacent proposal—whether Git should also forbid ref names that *look like* object IDs—could broaden the scope if others engage with it. For now, this v2 is ready for deeper review if the project decides to proceed.

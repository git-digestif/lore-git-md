Thread identity: Bug report – `.gitignore` trailing-slash pattern fails to ignore symlinks, leading to silent data loss during `git pull`. Originating author: AIKSXD ax (aiksxd@outlook.com). Thread type: bug report (no patch series, no RFC).

Core problem or goal: A `.gitignore` entry ending in a slash (`dir/`) does **not** ignore a symlink of the same name (`dir`), allowing the symlink to be staged and committed. When another user pulls, Git silently overwrites their local **directory** with the incoming **symlink**, destroying all data inside the directory. The report seeks either (a) a change to `.gitignore` semantics so trailing-slash patterns also ignore symlinks, or (b) a conflict detection during `git pull` that refuses to overwrite without user confirmation.

Current status: Under review. No patch posted yet; discussion ongoing. No maintainer decision or merge status recorded.

Key technical details:
- Files touched: `.gitignore` semantics, `git pull` conflict resolution, and potentially `git checkout`/`git merge` for similar overwrite behavior.
- Subsystems: ignore handling, checkout/update machinery.
- Behavior change: Two proposed fixes: (1) extend `.gitignore` to treat `dir/` as matching a symlink `dir`, or (2) add a safety check in `git pull` (and possibly other commands) that aborts when a local directory would be replaced by a symlink.
- On-disk format: unchanged.
- Test coverage: reproduction case provided in the original report; no formal test script yet.
- **Clarification of current behavior**: `.gitignore` patterns ending in a slash (`dir/`) ignore *contents* of a directory, not the directory entry itself. Since Git’s index tracks only files and symlinks (not directories), a symlink named `dir` is not ignored by `dir/`, allowing it to be staged and committed. This behavior is consistent with Git’s documented handling of overwrites (e.g., `git checkout --overwrite-ignore`).

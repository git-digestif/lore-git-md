This is a follow-up in the ongoing RFC thread about enforcing lowercase-only object IDs in Git 3.0. Phillip Wood, after receiving brian m. carlson’s security rationale, now raises two practical questions about the proposed breaking change.

First, he questions why uppercase hex is treated as a security risk when ref names (which can point to the same objects) are not. If a policy check fails to validate whether input is actually a hex object ID, a ref name could bypass the same restrictions just as easily as an uppercase OID. This challenges whether the proposed fix addresses the root problem—poor input validation—rather than just a symptom.

Second, Phillip suggests an alternative or complementary measure: forbidding ref names whose last component looks like an object ID. This would prevent the regex-misclassification issue brian described (where tools assume `[0-9a-f]{40}` is an OID and not a ref) without requiring a breaking change to hex parsing. The suggestion is brief but opens a new avenue for discussion—whether tightening ref naming rules could achieve the same security goals with less ecosystem disruption.

The email is short and focused, advancing the thread by shifting attention from *whether* to enforce lowercase OIDs to *how* best to address the underlying security concerns. It does not endorse or reject the original proposal, but the questions are pointed enough to influence the project’s eventual decision.

This is the final patch in brian m. carlson’s seven-part RFC series proposing a breaking change for Git 3.0: **restricting hex object IDs to lowercase only**. The patch activates the enforcement mechanism introduced in the earlier infrastructure patches by defining `HEX_KIND_OID` as `HEX_KIND_LOWER` when `WITH_BREAKING_CHANGES` is enabled. This change is documented in `Documentation/BreakingChanges.adoc` and tested in `t/t1503-rev-parse-verify.sh`, which now verifies that uppercase object IDs are rejected.

The patch is minimal and targeted, touching only three files. The core change is a single preprocessor directive in `hex-ll.h` that flips the default behavior for object ID parsing. The documentation addition is concise, framing the change as a security and compatibility improvement to address real-world bugs in Git-adjacent tools (e.g., Gitolite) that assume lowercase-only object IDs. The new test ensures the enforcement works as intended, complementing the adjustments made to `t5324-split-commit-graph.sh` in the previous patch to avoid false positives in SHA-256 mode.

This patch is the culmination of the series and the only one that introduces a user-visible behavioral change. The rest of the series (patches 1–6) laid the groundwork by refactoring hex-parsing code to use the new `hex_kind` enum and `hexval()` helpers without altering runtime behavior. The breaking change is gated behind `WITH_BREAKING_CHANGES`, meaning it will only take effect in Git 3.0 if the project decides to proceed. Junio’s tentative "Will queue" from the RFC stage still holds, but the discussion remains open, particularly around Phillip Wood’s adjacent proposal about forbidding ref names that *look like* object IDs.

The patch looks technically sound and well-motivated. The security rationale is strengthened by concrete examples of real-world vulnerabilities and the demonstration by Michael Montalbo showing how mixed-case object IDs can create ambiguity. The implementation is clean, with no on-disk format changes required, and the test coverage is minimal but sufficient for the scope of the change. If the project accepts the breaking change, this patch will be the one that enforces it.

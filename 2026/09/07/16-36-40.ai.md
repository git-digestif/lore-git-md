This is the latest exchange in the ongoing review of the second patch in Thomas Bachem’s v3 series (not yet posted) that defers auto maintenance until sequencer operations (`rebase`, `cherry-pick`, `revert`) complete. The thread is now focused on two parallel tracks: (1) polishing the commit message and tests for the current design, and (2) evaluating an alternative design proposed by the author that moves the maintenance call out of the sequencer and into the built-in commands (`builtin/rebase.c`, `builtin/revert.c`).

Key updates since the parent email:
- **Commit message clarity**: Thomas accepts Phillip Wood’s suggested rewording to avoid implying active interference and to clarify that the merge backend (used by `cherry-pick` and `revert`) does not run auto maintenance on its own. The confusing phrasing about “rerere gc” and loose objects will be rewritten to explain that a clean sequence leaves loose objects to accumulate until the next manual commit.
- **Test improvements**: Thomas will extend the existing test (rather than duplicating it) to assert that auto maintenance does *not* run during intermediate steps (e.g., before `git rebase --continue`), and will switch from `grep` to `test_grep` for better failure output.
- **Design shift**: Thomas proposes moving the `run_auto_maintenance()` call from the sequencer (`sequencer.c`) to the built-in commands (`run_specific_rebase()` in `builtin/rebase.c`, `run_sequencer()` in `builtin/revert.c`). This consolidates maintenance into a single exit path per command, aligning with the apply backend’s design and addressing Patrick Steinhardt’s preference for a unified exit point. The trade-off is moving logic out of the sequencer, which may feel less cohesive but simplifies the rule to “the command runs maintenance once when done.” Phillip has not yet weighed in on this proposal, but the author is seeking his feedback.

The patch remains technically complete; no open technical objections exist. The only unresolved questions are code organization (sequencer vs. built-in commands) and test hygiene (consolidation, assertions, output formatting). The author plans to include these changes in v3, which will also incorporate Junio’s mechanical feedback (storing the cached `GIT_CONFIG_PARAMETERS` string as `const char *`) and Patrick’s suggestion to remove the redundant `gc.auto=0` setting.

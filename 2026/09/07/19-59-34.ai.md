This is the first patch in a seven-part RFC series targeting Git 3.0, introducing infrastructure for a breaking change: restricting hex object IDs to lowercase only. The patch adds a new `hex_kind` enum (`HEX_KIND_MIXED`, `HEX_KIND_LOWER`) and a `hexval_lc_table` that rejects uppercase hex digits, then updates the `hexval()` function to accept an `enum hex_kind` parameter. For now, all callers use `HEX_KIND_MIXED`, preserving existing behavior. The changes touch `hex-ll.c`, `hex-ll.h`, `color.c`, and `pkt-line.c`, laying the groundwork for future enforcement without altering runtime behavior.

The patch is narrowly scoped and technically sound. It introduces no new behavior—only the scaffolding for case-sensitive hex parsing—and all existing callers continue to accept mixed-case input. The new `hexval_lc_table` is a straightforward lookup table that returns `-1` for uppercase letters, and the `hexval()` wrapper cleanly abstracts the choice between mixed-case and lowercase-only parsing. The defensive pattern (`val & ~0xf`) adopted in v2 to address Elijah Newren’s correctness concern is already present here, ensuring robustness. No test coverage is added yet, as this patch is purely preparatory.

This is part of brian m. carlson’s broader effort to eliminate security and compatibility risks caused by Git’s current case-insensitive hex parsing. The series remains contingent on project consensus, but this patch itself is uncontroversial: it refactors without changing behavior, and all review feedback from v1 has been addressed. The next patches will build on this infrastructure to enforce lowercase-only parsing in specific contexts, culminating in a Git 3.0 breaking change. For now, this patch is ready for deeper review if the project decides to proceed with the series.

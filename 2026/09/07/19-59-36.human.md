This is the third patch in brian m. carlson’s seven-part RFC series proposing a Git 3.0 breaking change: restricting hex object IDs to lowercase only. The series is infrastructure-heavy, and this patch is purely preparatory—it extends the `hex_to_bytes()` function (introduced in the first two patches) to accept an `enum hex_kind` parameter, allowing callers to specify whether the input should be parsed as mixed-case, lowercase-only, or OID-specific hex. All existing call sites are updated to pass `HEX_KIND_MIXED`, preserving current behavior for now.

The patch touches seven files: `builtin/index-pack.c`, `diagnose.c`, `hex-ll.c`, `hex-ll.h`, `http-push.c`, `notes.c`, and `object-file.c`. These are all low-level consumers of hex parsing—packet-length decoding, object ID resolution from disk/network/diagnostics, and notes tree traversal. The changes are mechanical: adding the new parameter and passing `HEX_KIND_MIXED` at each call site. No runtime behavior changes; this is strictly plumbing for the enforcement that comes later in the series.

The commit message is minimal but clear: it cross-references the previous patch (which introduced `hexval()`’s `enum hex_kind` parameter) and signals that enforcement will follow in a future commit. The diff is small (12 insertions, 10 deletions) and focused, with no test coverage—appropriate for a preparatory patch. Junio’s earlier review flagged two omissions (`builtin/index-pack.c` and `notes.c`); both are now addressed, using `HEX_KIND_MIXED` as expected.

This patch is uncontroversial and technically sound. It’s a necessary step toward the breaking change, but on its own it does nothing visible to users or tools. The real discussion remains on the series’ final patch, which activates enforcement, and the broader question of whether Git 3.0 should accept this breaking change at all. For now, this is just infrastructure.

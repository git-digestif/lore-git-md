This is a **bugfix discussion** targeting the `.gitignore` and `git pull` subsystems, with potential for data loss.

Brian M. Carlson responds to the original bug report by clarifying the current behavior: `.gitignore` patterns ending in a slash (`dir/`) are designed to ignore *contents* of a directory, not the directory entry itself. Since Git’s index only tracks files and symlinks (not directories), a symlink named `dir` is not ignored by the `dir/` pattern, allowing it to be staged and committed. This behavior is consistent—Git also overwrites a local directory with a regular file if the file is tracked, as documented in `git checkout --overwrite-ignore`.

Carlson argues that both proposed fixes would introduce substantial backward-compatibility risks. Changing `.gitignore` to treat `dir/` as matching a symlink `dir` would be inconsistent (symlinks to files would behave differently from symlinks to directories) and platform-dependent (symlinks may not resolve to valid paths). Similarly, adding a safety check in `git pull` to refuse overwriting a directory with a symlink would likely break existing tooling that relies on the current behavior. He references a prior proposal for a `precious` attribute (to protect ignored files) but notes it remains unimplemented.

The discussion highlights a tension between safety and compatibility. Carlson’s position leans toward preserving the status quo, emphasizing that untracked or ignored files in the working tree are inherently at risk. The thread remains open, with no patch proposed yet—future discussion may explore alternative solutions (e.g., a configurable safety check or the `precious` attribute) or accept the current behavior as a known limitation. The reproduction case and severity of the issue (silent data loss) ensure this will continue to receive attention.

Subject: stash.index=true + --autostash during fast-forward merge leaves redundant stash entry and MERGE_AUTOSTASH ref
Series version: none (standalone bug report)
Originating author: Eli Barzilay
Thread type: bug report

Core problem or goal
A bug in Git 2.55.0 (and current master) causes `git merge --ff-only --autostash` (and by extension `git pull` with `rebase.autoStash` and `pull.rebase`) to leave behind a redundant stash entry and fail to clean up the `MERGE_AUTOSTASH` ref when `stash.index=true` is set and a staged change exists at merge time. The operation succeeds but emits an error message, and the stash list contains an extra entry.

Current status
Under review. The bug is confirmed, reproducible, and well-analyzed. No patch has been posted yet, but two participants (Eli Barzilay and D. Ben Knoble) are actively debugging and discussing potential fixes.

Key technical details
- Subsystems: stash, merge, ref management
- Files touched by the bug: `builtin/merge.c`, `sequencer.c`, `builtin/stash.c`, `branch.c`
- Symbols involved: `MERGE_AUTOSTASH` ref, `remove_merge_branch_state()`, `reset_head()`, `stash_apply_index()`, `reset_working_tree()`
- Old behavior: `MERGE_AUTOSTASH` ref is deleted prematurely during `stash apply --index` (via `reset_head()` → `remove_merge_branch_state()`), causing a duplicate stash entry and a later "ref not found" error
- New behavior: (not yet implemented) `MERGE_AUTOSTASH` ref must be preserved until the autostash apply completes
- Test coverage: reproduction script provided by Eli Barzilay; D. Ben Knoble confirms reproducibility locally. No formal test in the suite yet.

Open questions and loose ends

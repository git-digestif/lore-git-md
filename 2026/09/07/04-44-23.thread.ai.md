Subject: stash.index=true + --autostash during fast-forward merge leaves redundant stash entry and MERGE_AUTOSTASH ref
Series version: none (standalone bug report)
Originating author: Eli Barzilay
Thread type: bug report

Core problem or goal
A bug in Git 2.55.0 (and current master) causes `git merge --ff-only --autostash` (and by extension `git pull` with `rebase.autoStash` and `pull.rebase`) to leave behind a redundant stash entry and fail to clean up the `MERGE_AUTOSTASH` ref when `stash.index=true` is set and a staged change exists at merge time. The operation succeeds but emits an error message, and the stash list contains an extra entry.

Current status
Under review. The bug is confirmed, reproducible, and well-analyzed. Four participants (Eli Barzilay, D. Ben Knoble, Phillip Wood) are actively debugging and discussing potential fixes. Phillip Wood has proposed two concrete approaches: a surgical fix (replace `reset_head()` with `reset_tree(&c_tree, 0, 1)`) and a more ambitious refactoring (use `merge_incore_nonrecursive()` for index merge). Ben Knoble has committed to testing both approaches and may contribute implementation work.

Key technical details
- Subsystems: stash, merge, ref management
- Files touched by the bug: `builtin/merge.c`, `sequencer.c`, `builtin/stash.c`, `branch.c`
- Symbols involved: `MERGE_AUTOSTASH` ref, `remove_merge_branch_state()`, `reset_head()`, `reset_tree(&c_tree, 0, 1)`, `stash_apply_index()`, `reset_working_tree()`, `merge_incore_nonrecursive()`, `merge_ort_nonrecursive()`
- Old behavior: `MERGE_AUTOSTASH` ref is deleted prematurely during `stash apply --index` (via `reset_head()` → `remove_merge_branch_state()`), causing a duplicate stash entry and a later "ref not found" error
- New behavior: (proposed) `MERGE_AUTOSTASH` ref must be preserved until the autostash apply completes; either via `reset_tree(&c_tree, 0, 1)` or via a three-way index merge using `merge_incore_nonrecursive()`
- Test coverage: reproduction script provided by Eli Barzilay; D. Ben Knoble and Phillip Wood confirm reproducibility locally. No formal test in the suite yet.

Open questions and loose ends
- Which of the two proposed fixes (surgical `reset_tree(&c_tree, 0, 1)` or refactoring to `merge_incore_nonrecursive()`) will be chosen.
- Whether the fix will be backported to the maintenance track.
- D. Ben Knoble’s earlier exploration of replacing the `git reset` subprocess call with a direct `reset_working_tree()` invocation—whether this remains viable or introduces new edge cases.
- The broader layering violation: `git reset` performing undocumented branch-state cleanups via `remove_merge_branch_state()`. While noted as surprising and poorly documented, neither Ben nor Phillip proposes addressing this in the current bugfix thread.

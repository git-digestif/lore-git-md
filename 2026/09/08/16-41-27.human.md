This is the third patch in Christian Couder’s v3 series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators mark repositories as trusted for lazy fetching. This patch implements the core logic to read and validate the new configuration.

The patch adds a new function `upload_pack_lazy_fetch_trusted()` that checks whether the repository being served is listed in the `uploadpack.lazyFetchTrusted` allowlist. It reuses the callback-based path validation helpers introduced in patch 2/5, but with stricter rules: only absolute paths are accepted (relative paths like `.` are rejected), and repositories must be specified by their `.git` directory (e.g., `/srv/repo/.git` for a non-bare repository at `/srv/repo`). The configuration is read only from protected files, ensuring it cannot be overridden by untrusted clients.

The implementation is clean and well-motivated. The commit message clearly explains the design choices (absolute paths, `.git` directory requirement) and ties them to how `upload-pack` operates. The code itself is straightforward, with clear error handling and memory management. The new function will be used in the next patch to gate lazy fetching, completing the server-side trust model.

This patch directly addresses Junio’s earlier critique about API rigidity by leveraging the callback-based allowlist design from patch 2/5. It also clarifies a key ambiguity from v2: how repositories are identified (by their git directory, not worktree). The only unresolved concern from prior reviews is Junio’s scalability question about memory overhead in `lazy_fetch_objects()`, but that’s unrelated to this patch.

No new issues are apparent here. The patch is narrowly focused, well-tested (judging by the expanded test script in patch 5/5), and fits neatly into the series’ goal of shifting trust decisions to server operators. If the series lands, this will be a key piece of the infrastructure.

This is the final patch in a four-part series introducing the `receive-report` hook, a new server-side mechanism that lets administrators intercept and modify the status report sent to clients after ref updates. The series is now queued in `next` and addresses all prior feedback, including the three surface-level nits fixed in this v8 iteration.

The hook is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the status report must reflect the repository state *after* all server-side operations—including those beyond `ref_transaction_commit()`—are complete. It acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. A non-zero exit status rewrites all ref status lines to `"receive-report hook failed"` and overwrites all `cmd->error_string` fields, effectively aborting the push from the client’s perspective—though ref updates are *not* rolled back. This intentional decoupling between reported status and actual repository state violates Git’s traditional consistency guarantees (remote-tracking branches may not reflect the server’s state), but the commit message explicitly justifies the trade-off with GitLab’s use case.

The patch implements the hook’s core logic in `builtin/receive-pack.c`, adding three new helpers: `run_receive_report_hook()` (invokes the hook and buffers its output), `override_cmds_error()` (rewrites all ref status lines on hook failure), and the previously introduced `generate_report()` (centralizes report generation). The hook is *not* integrated with the config-based hook infrastructure, as its bidirectional filter design (stdin → stdout) is incompatible with running multiple scripts sequentially. Test coverage in `t/t5412-receive-report-hook.sh` (224 lines) exercises passthrough, failure modes, stdin/stdout handling, sideband relay, and the hook’s ability to modify the `unpack` status line. Documentation in `githooks.adoc` and `git-receive-pack.adoc` clearly states the hook’s three ways of affecting push outcome: rewriting ref status lines, aborting the push (non-zero exit), and modifying the `unpack` status line.

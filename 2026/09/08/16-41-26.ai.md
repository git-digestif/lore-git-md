This is the second patch in Christian Couder’s v3 series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable for lazy-fetching trust control. It extracts and generalizes the existing `safe.directory` allowlist logic into reusable helpers, preparing the ground for the new `uploadpack.lazyFetchTrusted` configuration in later patches.

The patch moves the path-matching logic from `safe_directory_cb()` into two new helpers in `setup.c` and `setup.h`: `path_allowlist_apply()` and `path_allowlist_config_apply()`. The first is a generic path-matching function that takes a callback (`bool (*allow_path)(const char *path, void *cbdata)`) to let callers define their own validation rules; the second wraps it to handle config-value expansion via `git_config_pathname()`. The existing `safe.directory` logic is then refactored to use these helpers, replacing its hardcoded path checks with a new `allow_safe_dir()` callback that enforces the same rules (absolute paths or `.` only). The patch also changes `struct safe_directory_data.is_safe` from `int` to `bool` for clarity.

This refactoring is a prerequisite for patch 3/5, which will use the same helpers to implement `uploadpack.lazyFetchTrusted` with caller-specific rules (e.g., rejecting relative paths). The callback-based design directly addresses Junio’s v2 critique that the original allowlist logic was too rigid; it now allows each caller to define its own path-validation policy while reusing the same core matching logic. The commit message explains the motivation clearly, and the code changes are mechanical and well-scoped, touching only `setup.c` and `setup.h`. No behavior changes are introduced—this is pure refactoring, setting the stage for the new feature.

This is the third patch in Christian Couder’s v3 series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators mark repositories as trusted for lazy fetching. This patch implements the core logic to read and validate the new configuration, building on the callback-based allowlist helpers introduced in patch 2/5.

The patch adds a new function `upload_pack_lazy_fetch_trusted()` that checks whether the repository being served is listed in `uploadpack.lazyFetchTrusted`. It reuses the generic `path_allowlist_config_apply()` helper from patch 2/5 but supplies its own validation callback, `allow_trusted_path()`, which enforces stricter rules than `safe.directory`: only absolute paths are accepted, and `.` (the current directory) is rejected. This reflects the fact that `upload-pack` always serves repositories by absolute git directory paths, never by worktree paths. The commit message clarifies that non-bare repositories must be allowlisted by their `.git` directory (e.g., `/srv/repo/.git` for `/srv/repo`).

The implementation reads the configuration only from protected files, ensuring that untrusted repositories cannot override the setting. The new logic is isolated in `upload-pack.c` and exposed via a single header function, keeping the change self-contained. No behavior is changed yet—this patch only lays the groundwork; the actual lazy-fetching logic will use the new function in patch 4/5.

The patch is clean and well-motivated, addressing Junio’s earlier critique about API rigidity by reusing the callback-based design. The stricter path validation (absolute paths only) is a sensible security measure, and the commit message clearly explains the reasoning behind it. No substantive reviews have been posted yet for v3, but the changes directly respond to feedback from v2. The patch is part of a larger security-conscious effort to shift lazy-fetch trust decisions to server operators, replacing the earlier client-side `GIT_NO_LAZY_FETCH=fromAccepted` proposal.

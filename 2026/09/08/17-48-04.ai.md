This is a **substantive review** from Junio on the second patch in Christian Couder’s v3 series introducing `uploadpack.lazyFetchTrusted`. The patch refactors the `safe.directory` allowlist logic into reusable helpers (`path_allowlist_apply()` and `path_allowlist_config_apply()`) to enable caller-specific path validation rules, a prerequisite for the new feature.

Junio’s feedback focuses on a **latent design issue** in the existing `safe.directory` logic: the code silently ignores paths that do not exist on the filesystem. He argues this is problematic because it conflates two distinct cases—paths that are intentionally absent (e.g., a shared `.gitconfig` entry meant for multiple machines) and paths that are missing due to errors (e.g., an unmounted filesystem). In the latter case, silently ignoring the path could lead to unintended behavior, such as a repository being incorrectly treated as "safe" or "trusted" when it should not be. While this issue predates Christian’s patch and is not his responsibility to fix, Junio suggests it is worth addressing, especially since the new `uploadpack.lazyFetchTrusted` mechanism will reuse the same logic.

The review does not block the patch—Junio explicitly notes the issue is inherited—but it raises a **long-term correctness concern** that could affect both `safe.directory` and the new lazy-fetch trust mechanism. If this series lands as-is, the silent-ignoring behavior will propagate to `uploadpack.lazyFetchTrusted`, potentially masking configuration errors on the server side. This could become a point of contention if other reviewers share Junio’s concern, particularly in security-sensitive contexts where misconfigured trust settings might have serious consequences. The feedback is narrowly scoped to the path-matching logic and does not question the overall design of the series.

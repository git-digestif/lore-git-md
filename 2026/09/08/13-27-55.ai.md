This is a bug report about `git send-email` failing to handle SMTP rate-limiting gracefully.

The user encountered an SMTP server error (`4.7.1 Error: too many recipients`) while sending a 13-patch series to the Linux kernel mailing list, where each email had 18 recipients. Instead of retrying or prompting the user to continue after a delay, `git send-email` exited immediately, leaving the remaining patches unsent. When the user manually resumed sending, the patches were incorrectly threaded, creating an embarrassing situation.

The expected behavior would be for `git send-email` to detect rate-limiting errors and either pause for a configurable delay (e.g., 60 seconds) before retrying or prompt the user to confirm continuation. The user notes that `--batch-size` and `--relogin-delay` options exist but were not used in this case, suggesting these could be part of the solution.

The report includes system details (Git 2.34.1 on Ubuntu) but no prior discussion or patch context. The issue appears to be a missing error-handling mechanism for SMTP rate-limiting scenarios, which could affect users sending large patch series to high-traffic mailing lists. The user’s workaround (`--batch-size=4 --relogin-delay=60`) is a manual fix, but the tool itself should handle this automatically.

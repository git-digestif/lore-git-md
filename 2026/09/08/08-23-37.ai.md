This is a bug report about `git bundle` with bitmaps enabled. The author, Peter Elmers, demonstrates that when creating a bundle with bitmaps, Git omits a tree object required by an advertised ref, even though the bundle verification and unbundle operations succeed. The issue surfaces when the recipient tries to access the tree of the advertised commit, which fails because the tree is missing from the bundle.

The reproduction script sets up a minimal repository with two sibling commits sharing the same root tree: one stored in a local branch (`refs/heads/feature`) and the other in a remote-tracking ref (`refs/remotes/origin/feature`). The bundle is created to include the local branch while excluding the remote-tracking ref. With bitmaps enabled, the bundle verification passes, but the recipient cannot access the tree of the advertised commit. Disabling bitmaps (`-c pack.useBitmaps=false`) resolves the issue, confirming that the problem lies in the bitmap traversal logic.

The commit topology is straightforward: both `local_tip` and `remote_tip` share the same parent (`base`) and root tree (`shared_tree`). The bundle advertises `local_tip` and excludes `remote_tip`, but the bitmap traversal incorrectly omits `shared_tree`, which is required by `local_tip`. The author also notes that enabling `pack.useBitmapBoundaryTraversal` does not prevent the omission, suggesting the bug is not addressed by that configuration.

The report is well-structured, with clear steps to reproduce, expected and actual behavior, and a minimal test case. The issue appears to be a regression or oversight in the bitmap traversal logic when creating bundles, specifically in how it handles shared trees between included and excluded refs. The problem is likely to affect users who rely on bundles for offline transport or backup, particularly in workflows involving divergent branches with shared history.

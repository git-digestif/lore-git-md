This is the first patch in Christian Couder’s v3 series introducing `uploadpack.lazyFetchTrusted`. It is a pure refactoring of the promisor-remote subsystem, extracting the lazy-fetching logic from `fetch_objects()` and `promisor_remote_get_direct()` into a new helper function `lazy_fetch_objects()`.

The patch addresses two minor inefficiencies in the current code: the `GIT_NO_LAZY_FETCH` environment variable check is performed once per promisor remote, and `promisor_remote_init()` is called even when lazy fetching is disabled. The refactoring consolidates these checks into a single up-front decision in `lazy_fetch_objects()`, eliminating redundant work. It also converts `try_promisor_remotes()` from returning an `int` to a `bool`, making the control flow clearer—`true` means all objects were fetched, `false` means some remain. The commit message explicitly notes that the behavior change is observably equivalent, and the diff confirms this: the logic is simply reorganized, not altered.

The patch touches only `promisor-remote.c` and is a prerequisite for the later patches in the series. By isolating the lazy-fetching logic, it sets the stage for the callback-based allowlist machinery introduced in patch 2/5, which will use `lazy_fetch_objects()` to enforce the new `uploadpack.lazyFetchTrusted` configuration. The refactoring also simplifies the control flow in `promisor_remote_get_direct()`, removing a `goto` and making the error-handling path more linear.

No new symbols or behaviors are introduced; this is strictly internal plumbing. The patch is well-motivated and clearly explained, addressing Junio’s stylistic feedback from v2 about control flow clarity. It is a clean, uncontroversial refactoring that should not attract substantive review comments. The only likely feedback will be surface-level (e.g., commit message wording or variable naming), but the patch itself is solid and ready for integration.

This is the third patch in the v8 series introducing the `receive-report` hook, a refactoring that extracts the status-report generation logic into a reusable `generate_report()` helper. The patch unifies the previously separate `report()` and `report_v2()` functions, which differed only in their support for detailed per-ref updates (e.g., `option refname`, `option old-oid`). The new helper takes an `enum report_status_version` parameter to handle both protocol versions (v0 and v2) and is designed to be called from multiple sites, preparing the codebase for the upcoming hook implementation in patch 4/4.

The refactoring is purely internal and does not change user-visible behavior. It addresses Patrick Steinhardt’s substantive review feedback from v6, which identified the redundancy between `report()` and `report_v2()` and suggested unifying them. The patch also fixes a stale comment in the new `generate_report()` helper, replacing a reference to the removed `detailed_report` boolean with the `version` parameter, as noted in Junio C Hamano’s latest review. The change is minimal and focused, with the diff showing a net reduction of 11 lines in `builtin/receive-pack.c`.

The patch is well-motivated: the commit message clearly explains the need for a shared helper to avoid code duplication when the hook implementation (patch 4/4) introduces a second call site. The `generate_report()` function is now the single source of truth for status-report generation, handling both protocol versions and the optional per-ref details introduced in v2. The `report_v2()` function is removed entirely, and the `report()` function is simplified to a thin wrapper around the new helper. The `enum report_status_version` parameter ensures the correct protocol version is used, addressing Junio’s earlier maintainability concern about the `detailed_reports` boolean.

No test coverage is added or modified in this patch, as it is a refactoring with no behavioral changes. The patch is part of a series that is already queued in `next`, and all prior feedback—including the stale comment fix—has been addressed. The refactoring is a necessary precursor to the hook implementation and is uncontroversial. The patch is ready for integration, with no open questions or loose ends.

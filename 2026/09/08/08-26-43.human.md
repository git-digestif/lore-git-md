This is a review comment on the second patch in Beat Bolli’s three-patch series fixing OpenSSL compatibility and correctness issues in `git imap-send`. The series aims to address unsafe ASN1_STRING handling, OpenSSL API deprecation, and RFC 6125 compliance in TLS certificate verification.

Patrick Steinhardt questions the necessity of the patch’s approach, which allocates a NUL-terminated copy of the ASN1_STRING data. He points out that the code already uses `memchr` (a length-bounded function) to check for embedded NUL bytes, and suggests that the remaining unsafe calls (`strchr` and `strcasecmp`) could be replaced with their length-bounded counterparts (`memchr` and `strncasecmp`). This would eliminate the need for the `xmemdupz` allocation entirely, simplifying the code and avoiding potential memory-management pitfalls (such as the heap corruption bug Junio C Hamano later identified in the original patch).

The review is substantive and technical, focusing on whether the patch’s design is the most efficient way to address the underlying issue. It does not dispute the correctness of the fix but proposes an alternative implementation that might be cleaner. If adopted, this suggestion would reduce the patch’s footprint and sidestep the memory-safety issue entirely. The discussion is worth following for anyone interested in low-level OpenSSL interactions or secure string handling in C.

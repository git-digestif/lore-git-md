This is the final patch in Christian Couder’s v3 series introducing `uploadpack.lazyFetchTrusted`, a server-side configuration to mark repositories as trusted for lazy fetching. The patch activates the mechanism by setting `GIT_NO_LAZY_FETCH=0` in `builtin/upload-pack.c` when serving a trusted repository, and documents the feature in `git-upload-pack.adoc`, `git.adoc`, and `Documentation/config/uploadpack.adoc`.

The email is a reply to Junio’s surface-level review of the v2 documentation, which flagged ambiguities about syntax and repository identification. Christian has addressed those in v3: the documentation now explicitly states that `uploadpack.lazyFetchTrusted` is multi-valued (each entry is a separate config line), specifies that repositories are identified by their `.git` directory or a parent directory, and clarifies that non-bare repositories must be allowlisted via their `.git` directory (e.g., `/srv/repo/.git` for `/srv/repo`). The typo Junio noted (“a uploadpack.lazyFetchTrusted” → “an uploadpack.lazyFetchTrusted”) is also fixed. The humorous edge case Junio raised—trusting a repository to fetch from itself—is now mitigated by the recursion safeguards introduced in patch 4/5.

The patch itself is straightforward: it flips the `GIT_NO_LAZY_FETCH` environment variable to `0` when serving a repository that matches the allowlist, and expands the test suite to verify the server-side trust model’s security properties. The documentation is thorough, explaining the security model, repository identification, and edge cases like self-referential promisor remotes. No technical concerns remain from Junio’s review; the feedback was purely editorial.

This patch is well-crafted and addresses a real problem: the security objection to lazy fetching from untrusted repositories. The server-side trust model, modeled after `safe.directory`, shifts responsibility to operators and is a cleaner design than the earlier client-side `fromAccepted` proposal. The series as a whole is now complete, with all prior review feedback incorporated. The unresolved high-weight concerns—Junio’s scalability critique and conceptual doubt about using a configuration variable—are mitigated by the server-side design and are unlikely to block progress. If the series stalls, patches 2/5 and 3/5 (the callback-based allowlist logic) are clean refactorings that could be integrated early. For now, the series remains under review, with no new substantive feedback since v3.

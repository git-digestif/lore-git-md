This is the sixth patch in the v15 `git history squash` series, which implements **branch protection** during range squashing. The patch prevents the operation if any local branch descended from the squashed range would be left dangling, unless the user explicitly opts in with `--update-refs=head`.

The core logic uses `ref-filter` to identify local branches (`refs/heads/`) that descend from commits in the squashed range but do not include its tip. These branches cannot be replayed as descendants of the new squashed commit, so the command rejects the operation by default. The blocking branches are sorted and printed in a user-friendly list (e.g., `topic-1`, `topic-2`), and an advice message guides users to `--update-refs=head` to rewrite only the current branch. The protection is limited to local branches, matching the scope of the default ref-update behavior; tags and remote-tracking refs are unaffected.

The implementation adds a new advice key (`ADVICE_HISTORY_UPDATE_REFS`) and integrates with the existing `resolve_squash_range()` function, extending it to accept a `bool update_branches` parameter. When `false` (the default), the function checks for blocking branches and fails if any are found. The test suite verifies the error messages, branch listing, and advice suppression via `advice.historyUpdateRefs=false`.

This is a **well-considered safety feature** that aligns with Git’s conservative approach to history rewriting. The design—rejecting by default and requiring explicit opt-in—prioritizes data integrity over convenience, a trade-off that will likely resonate with the project’s maintainers. The patch is technically sound, with clear error messages and thorough test coverage. It addresses a real workflow gap: users who squash a range without realizing they’ve orphaned other branches. The series as a whole is now **technically complete** and ready for integration, with this patch resolving one of the last major design questions.

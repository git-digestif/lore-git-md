This is a v2 bugfix series targeting the `--force-if-includes` safety mechanism in `git push`. The core issue remains: the feature incorrectly checks the reflog of the *local* branch whose name matches the *remote* destination branch (e.g., `main` when pushing to `origin/main`), rather than the branch actually being pushed (e.g., `src` when pushing `src:main`). This can cause false rejections (e.g., pushing from a differently named local branch or detached HEAD) or unintended data loss (e.g., pushing an unrelated branch that happens to share a name with a local branch containing the remote tip).

The v2 series clarifies the commit message for the first patch, explicitly noting that `--force-if-includes` already rejects detached HEAD pushes today (when the same-named local branch lacks the remote tip), and this change makes that rejection policy more transparent. The fix itself is unchanged: it consults the reflog of the pushed ref (`ref->peer_ref->name`) instead of the destination ref (`ref->name`), with special handling for `HEAD`-based pushes (resolving the symref) and detached HEAD states (rejecting by default). Deletions are explicitly allowed via `is_null_oid(&remote->peer_ref->new_oid)`.

The second patch, unchanged from v1, adjusts the advice message for detached HEAD scenarios. It introduces a new `advice.forceIfIncludesDetachedHead` config knob (documented as `advice.pushRefUnverifiable`) and a `ref->unverifiable` flag to distinguish detached HEAD rejections from remote-update rejections. The advice now instructs users to specify the expected remote tip with `--force-with-lease=<ref>:<expect>` or bypass the check with `--no-force-if-includes`. All transport layers (direct pushes, transport helpers, send-pack) are updated for consistency.

Files touched include `remote.c` (core logic), `advice.c`/`advice.h` (new advice message), `builtin/push.c`, `send-pack.c`, `transport-helper.c`, and `transport.c` (transport-layer updates), and `t/t5533-push-cas.sh` (eight new test cases covering mismatched local/remote names, `HEAD`-based pushes, detached HEAD states, and advice messages). The series is based on `maint` and includes a range-diff showing the commit message clarification in the first patch.

The v2 addresses the only open question from v1—the detached HEAD policy—by making the existing rejection behavior explicit. The reflog limitation for detached HEAD is accepted as a necessary trade-off, and the advice message improvements provide actionable guidance. The series is self-contained, well-tested, and ready for review. Key symbols introduced include `advice.forceIfIncludesDetachedHead` (config key) and `ref->unverifiable` (flag). No on-disk format changes are involved.

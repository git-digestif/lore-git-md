This is the third iteration of a three-patch series targeting the sequencer subsystem. It adjusts when auto maintenance runs during `git rebase`, `git cherry-pick`, and `git revert` so that it defers until the sequence completes, matching the apply backend’s behavior. The series is technically complete and addresses all prior feedback from Phillip Wood, Patrick Steinhardt, and Junio C Hamano.

The core change moves the `run_auto_maintenance()` call from the sequencer to the built-in commands (`builtin/rebase.c` and `builtin/revert.c`), consolidating it into a single exit path per command. This aligns with the apply backend’s design and simplifies the rule to "the command runs maintenance once when done." The series also disables auto maintenance for individual commands spawned during a sequence (e.g., `git commit`, `git merge`, exec commands) by passing `maintenance.auto=false` via `GIT_CONFIG_PARAMETERS`, ensuring maintenance runs exactly once at the end.

The implementation is clean: it introduces a reusable `git_config_append_parameter()` helper with documented format, caches the config string in `replay_ctx` as a `const char *`, and removes the redundant `gc.auto=0` setting. Test coverage is thorough, using `GIT_TRACE2_EVENT` to verify maintenance runs only at sequence completion and not during intermediate steps. The tests cover single-pick, multi-pick, conflict-resolution, and exec scenarios, and assert the absence of maintenance during intermediate steps.

The only remaining prerequisite for merging is a v4 with revised commit messages that explicitly justify the design choice of delegating maintenance to callers and demonstrate human authorship. Patrick Steinhardt’s concerns about LLM-generated messages lacking meaningful context must be addressed, but the technical work is solid. This looks like a well-crafted, uncontroversial improvement that will likely land soon.

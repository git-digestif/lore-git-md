This is the v8 iteration of a **feature patch series** introducing the `receive-report` hook, a server-side filter for the status report sent to clients after ref updates. The series is **queued in `next`** (Junio C Hamano, 2026-09-05) and addresses all prior feedback, including three surface-level nits identified in v7: a typo in the `enum report_status_version` sentinel value (`REPORT_STATUS_UNKOWN` → `REPORT_STATUS_UNKNOWN`), a stale comment in `generate_report()`, and an incorrect argument in the error-handling path of `run_receive_report_hook()`.

The hook is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the status report must reflect the repository state *after* all server-side operations (including those beyond `ref_transaction_commit()`) are complete. It acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. A non-zero exit status rewrites all ref status lines to `"receive-report hook failed"` and overwrites all `cmd->error_string` fields, effectively aborting the push from the client’s perspective—though ref updates are *not* rolled back. This intentional decoupling between reported status and actual repository state violates Git’s traditional consistency guarantees (remote-tracking branches may not reflect the server’s state), but the commit message explicitly justifies the trade-off with GitLab’s use case.

The series consists of four patches:
1. **Documentation-only**: Adds a `PROC-RECEIVE HOOK` section to `git-receive-pack.adoc` (with a `Helped-by` credit to Patrick Steinhardt) and updates `githooks.adoc` to document the new hook. The documentation now clearly states the hook’s three ways of affecting push outcome: rewriting ref status lines, aborting the push (non-zero exit), and modifying the `unpack` status line.
2. **Refactoring**: Replaces static variables tracking report status version with an `enum report_status_version` (values: `REPORT_STATUS_UNKNOWN`, `REPORT_STATUS_V0`, `REPORT_STATUS_V2`). The `if/else` chain for handling the enum is now a `switch` statement, addressing Patrick Steinhardt’s subjective preference.
3. **Refactoring**: Extracts status-report generation logic into a reusable `generate_report()` helper, unifying the redundant `report()` and `report_v2()` functions. The stale comment referencing the removed `detailed_report` boolean is updated to reference the `version` parameter.
4. **Core implementation**: Introduces the `receive-report` hook with the agreed-upon exit semantics. The hook is *not* integrated with the config-based hook infrastructure (justified in the commit message). The error-handling fix in v8 ensures the regenerated error report uses the same protocol version as the original call. Test coverage in `t/t5412-receive-report-hook.sh` (224 lines) exercises passthrough, failure modes, stdin/stdout handling, sideband relay, and the hook’s ability to modify the `unpack` status line.

The series is **feature-complete** and rebased onto `master` (3cb9185f65), resolving conflicts with Justin Tobler’s concurrent "pluggable writes" series.

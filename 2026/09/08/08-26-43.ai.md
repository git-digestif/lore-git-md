This is a review comment on the second patch of Beat Bolli’s three-patch series fixing OpenSSL compatibility and correctness issues in `git imap-send`. Patrick Steinhardt proposes an alternative approach to the memory-safety fix: instead of allocating a NUL-terminated copy of the ASN1_STRING data (as the patch currently does), he suggests adapting the existing string operations (`strchr`, `strcasecmp`) to use their length-bounded counterparts (`memchr`, `strncasecmp`). This would eliminate the need for dynamic allocation while still preventing out-of-bounds access, since all operations would be constrained by the string’s known length.

The review is substantive and technical, engaging directly with the patch’s core correctness concern. Patrick’s suggestion is a classic space-time tradeoff: the current patch trades a small heap allocation for simpler code, while his alternative trades slightly more complex code for zero allocation. Both approaches are valid, but his avoids the memory-safety pitfall Junio C Hamano identified (the `free()` bug) entirely by removing the need for dynamic allocation. The review does not address the other patches in the series or the broader RFC 6125 compliance questions raised by brian m. carlson.

If adopted, Patrick’s approach would require careful handling of the `strncasecmp` call, which must compare exactly `len` bytes (not `len + 1`) to avoid reading past the end of the string. The review does not mention this edge case, but it is a minor detail that would surface during implementation. This is a well-reasoned alternative that simplifies the patch’s memory management while preserving its safety guarantees.

This is a v3 feature series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators explicitly mark repositories as trusted for lazy fetching. The series is part of the ongoing effort to address security concerns around lazy fetching in promisor-remote workflows, replacing the earlier client-side `GIT_NO_LAZY_FETCH=fromAccepted` proposal with a server-controlled trust model.

The core change in v3 is a major refactoring of the path allowlist machinery. Patches 2 and 3 from v2 have been squashed and reworked into a single new patch (2/5) that introduces a callback-based design for `path_allowlist_apply()`, allowing callers to customize path validation rules. This addresses Junio’s API design critique from v2, where he argued the original hardcoded logic was too rigid. The new implementation uses a function pointer (`bool (*allow_path)(const char *path, void *cbdata)`) to let callers define their own rules—for example, the `uploadpack.lazyFetchTrusted` logic now rejects relative paths (including `.`) and accepts only absolute paths, while the `safe.directory` logic retains its existing behavior. The commit message for patch 3/5 clarifies that repositories are identified by their git directory (not worktree), a correction from v2 that affects how paths are specified in the configuration.

Patch 4/5 is entirely new and prevents infinite lazy-fetch recursion, a risk Junio identified in v2 where a repository configured as its own promisor remote could trigger nested `upload-pack` invocations. The fix introduces a `GIT_INTERNAL_LAZY_FETCH_DEPTH` environment variable to limit nesting depth, with tests verifying the behavior. Patch 5/5 updates documentation to reflect these changes, including a warning against configuring a repository as its own promisor remote and clarifying that non-bare repositories must be allowlisted by their `.git` directory (e.g., `/srv/repo/.git` for `/srv/repo`).

The series maintains backward compatibility: lazy fetching remains disabled by default, and the new configuration is opt-in. It applies to both protocol v0/v1 and v2, unlike the earlier `fromAccepted` proposal which was v2-only. The unresolved security objection from brian m. carlson—who argued that expanding lazy-fetching flexibility increases exposure to untrusted repositories—remains relevant but is now addressed by the server-side trust model. The implementation touches the promisor-remote subsystem, `setup.c`, `upload-pack.c`, and adds a new test script (`t/t5710-promisor-remote-capability.sh`) covering edge cases like recursion and path validation.

Key symbols introduced or modified include `path_allowlist_config_apply()` (a wrapper for the callback-based allowlist logic), `upload_pack_lazy_fetch_trusted()` (checks if a repository is trusted), and `GIT_INTERNAL_LAZY_FETCH_DEPTH` (limits recursion). The series also refactors `lazy_fetch_objects()` in patch 1/5 to simplify control flow, addressing Junio’s stylistic feedback from v2. CI tests pass except for a Debian 11 environment issue unrelated to the patches. The series is rebased on a recent `master` commit (3cb9185f65) to avoid merge conflicts.

This is the third and final patch in a v3 series that completes the effort to defer auto maintenance until sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`) finish. The series is now technically ready for merging, pending only commit message polish in the next revision.

This patch disables auto maintenance in all commands spawned by the sequencer—`git commit`, `git merge`, and any command run via `exec`—by passing `maintenance.auto=false` through `GIT_CONFIG_PARAMETERS`. The config string is built once and cached in the `replay_ctx` as a `const char *`, then reused for every spawned command. This prevents background maintenance from interfering with the sequencer’s work, particularly with `MERGE_RR.lock` when rerere is enabled, and avoids races where a repack might delete a pack the sequencer still has open. The patch also updates the test suite to verify that auto maintenance runs exactly once at sequence completion and not during intermediate steps, covering single-pick, multi-pick, conflict-resolution, and exec scenarios.

The implementation is clean and well-scoped: it introduces a reusable `disable_auto_maintenance()` helper in `sequencer.c`, uses the existing `git_config_append_parameter()` helper from the first patch, and touches only the necessary code paths. The tests are thorough and use `GIT_TRACE2_EVENT` to assert the absence of maintenance during intermediate steps, improving failure output with `test_grep`. The only remaining work is revising the commit message to explicitly justify the design choice of delegating maintenance to callers (noting that `builtin/rebase.c` and `builtin/revert.c` are the only two entry points for sequencer operations) and to remove any LLM-generated phrasing, as Patrick Steinhardt has flagged the current message as lacking meaningful context. The author has agreed to address this in v4.

This patch is a solid bugfix that addresses a real and observable problem—sequencer operations failing due to lock contention with background maintenance—while maintaining consistency with the apply backend’s behavior. The series has been reviewed by Phillip Wood and Patrick Steinhardt, with all substantive feedback addressed. Unless new concerns emerge in v4, it is likely to be merged to `next`.

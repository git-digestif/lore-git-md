This is the v4 cover letter for a three-patch series that adjusts when auto maintenance runs during sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`). The series is now technically complete and ready for merging, with the only changes since v3 being a significant tightening of the commit messages—condensed to about a third of their original length in response to Junio C Hamano’s and Patrick Steinhardt’s critiques about modern commit message verbosity.

The goal remains the same: defer auto maintenance until the end of a sequencer-driven operation, matching the apply backend’s behavior. This prevents maintenance from interfering with intermediate steps (e.g., `rerere gc` holding `MERGE_RR.lock` during conflict resolution) and ensures consistent behavior across all three commands. The implementation touches the sequencer, config, and built-in command layers, introducing a reusable `git_config_append_parameter()` helper to build `GIT_CONFIG_PARAMETERS` strings and caching the config string in `replay_ctx` as a `const char *`. The `run_auto_maintenance()` call has been moved from the sequencer to the built-in commands (`run_specific_rebase()` in `builtin/rebase.c` and `run_sequencer()` in `builtin/revert.c`), consolidating maintenance into a single exit path per command.

Key technical details include the removal of the redundant `gc.auto=0` setting (since Git’s maintenance infrastructure now exclusively uses `git maintenance`), the use of `GIT_TRACE2_EVENT` in tests to verify maintenance runs exactly once at sequence completion, and the extension of existing test scripts (`t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh`) to cover edge cases like conflict resolution and exec scenarios. The series is based on `master` and is independent of the rerere lock race fix mentioned in earlier iterations.

Junio has signaled intent to queue the series ("Will queue"), meaning it will enter `seen` shortly and is likely to graduate to `next` in the next integration cycle if no new issues surface. The only remaining watch item is a hypothetical edge case about very long sequences where mid-sequence repacking might improve performance, but this is noted as a monitoring item rather than a blocker. All prior feedback from Phillip Wood, Patrick Steinhardt, and Junio has been addressed, and the commit messages now explicitly justify the design choice of delegating maintenance to callers while avoiding LLM-generated phrasing. The series looks well-crafted, thoroughly tested, and uncontroversial.

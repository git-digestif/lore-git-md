This is the **core implementation patch** of Karthik Nayak’s four-part series introducing the `receive-report` hook for `git-receive-pack`. The patch is **feature-complete, well-tested, and addresses all prior feedback**, including the critical design flaw resolved in v9. It is now **queued in `next`** and ready for final review before graduation to `master`.

The `receive-report` hook allows server administrators to intercept and modify the pkt-line encoded status report sent to the client after all ref updates are committed but before the response is finalized. The hook’s design as a bidirectional filter (stdin → status report, stdout → replacement report, stderr → sideband) is stable, and its exit semantics (non-zero exit rewrites all ref status lines to `"receive-report hook failed"`) align with the `pre-receive` hook. The hook is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the status report must reflect the repository state *after* all server-side operations (including those beyond `ref_transaction_commit()`) are complete.

Key technical details in this patch:
- **Files touched**: `builtin/receive-pack.c` (core implementation), `Documentation/git-receive-pack.adoc` and `githooks.adoc` (documentation), `t/meson.build` (test registration), and `t/t5412-receive-report-hook.sh` (224 lines of test coverage).
- **New functions**: `run_receive_report_hook()` (invokes the hook and buffers its stdout), `override_cmds_error()` (rewrites all `cmd->error_string` fields on non-zero exit).
- **Hook behavior**:
  - **Exit 0**: The hook’s stdout replaces the status report. The hook can rewrite `ok` lines to `ng` to signal per-ref rejection while `receive-pack` exits cleanly.
  - **Non-zero exit**: The hook’s stdout is discarded, and all refs are marked as rejected with `"receive-report hook failed"`.
  - **Stderr**: Forwarded to the client via sideband, regardless of exit status.
- **Consistency trade-off**: The hook intentionally decouples the reported status from the actual repository state, allowing the server to report a push as failed (`ng`) while still committing ref updates. This violates Git’s traditional principle that remote-tracking branches reflect the server’s state but is justified by GitLab’s MVCC use case. The commit message explicitly acknowledges this divergence and warns that the hook is only appropriate for servers where rejected updates are not immediately visible to other readers.

The patch includes **comprehensive test coverage** in `t/t5412-receive-report-hook.sh`, verifying:
- Passthrough behavior (hook does not alter the report).
- Non-zero exit handling (rewrites all refs to `"receive-report hook failed"`).
- Stdin/stdout handling (hook receives and modifies the pkt-line report).
- Sideband relay (stderr is forwarded to the client).
- Hook’s ability to modify the `unpack` status line and individual ref statuses.

The implementation is **clean and well-documented**, with clear commit messages and man page updates. The hook is **not integrated with the config-based hook infrastructure**, as its role as a filter (not a notification hook) makes a single-script design more natural.

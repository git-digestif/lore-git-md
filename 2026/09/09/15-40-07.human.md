This is the final review feedback on the third patch in Thomas Bachem’s v4 series that defers auto maintenance until sequencer completion. Phillip Wood’s comments are surface-level and focus on two small improvements: a clearer commit message phrasing and a test case that doesn’t actually test what it claims.

The commit message tweak is cosmetic—Phillip suggests rewording the opening line to avoid implying that maintenance actively “interferes” and to make it clearer that the spawned commands (not the sequencer itself) run maintenance. The implementation is already correct, so this is just about readability.

The test case in `t/t3418-rebase-continue.sh` is more substantive: the new check for `git commit` during a conflict-free `--continue` will always fail because `commit_staged_changes()` errors out before spawning any commit. Phillip points this out and suggests the test should either be removed or rewritten to cover a real conflict scenario. The rest of the test updates—adding `test_subcommand_flex ! git maintenance run --auto` checks and verifying exactly one maintenance run at sequence end—are correct and remain unchanged.

This is a substantive review comment from Jeff King (Peff) in the ongoing `defaultBranchName` advice documentation fix thread. Peff proposes an alternative to Junio C Hamano’s suggested backward-compatibility mechanism for the `advise()` function. Instead of creating an ad-hoc `advice_setting` struct on the stack, he suggests passing `NULL` to `vadvise()` to indicate the absence of a matching advice config. This approach is cleaner and more idiomatic in C, avoiding the need for a dummy struct and making the intent clearer: `vadvise()` would check `if (conf && !conf->level)` to decide whether to show turn-off instructions.

Peff also raises a broader observation about the advice subsystem’s current usage patterns. Most calls to `advise()` are wrapped in `if (advice_is_enabled(ADVICE_FOO))`, which means they do not benefit from the turn-off instructions introduced in 2020. Only `advise_if_enabled()` calls currently show these instructions. He questions whether users would find the instructions annoyingly chatty if they appeared for every advice message, noting that no one has complained about their absence so far. This suggests a potential inconsistency in the subsystem’s design: the turn-off instructions are only shown for a subset of advice messages, and expanding their use might require careful consideration of user experience.

Additionally, Peff points out that some `advise()` calls involve significant work before the message is shown, making them unsuitable for conversion to `advise_if_enabled()`. He proposes extending `advise()` to accept an advice enum (e.g., `advise(ADVICE_FOO, "try %s", results)`), which would allow it to show turn-off instructions while avoiding redundant `advice_is_enabled()` checks. This would also address the need to pass a "NULL advice marker" for cases where the message is not tied to a specific config value, though he acknowledges that such cases might be an anti-pattern.

The email does not resolve the syntax debate (`--global` vs `set --global`) or the core architectural changes (using `scope_hint` and passing the `advice_setting` struct to `vadvise()`), which remain settled. Instead, it focuses on a narrower implementation detail: how to handle backward compatibility for `advise()` in a way that is both clean and extensible. Peff’s proposal is technically sound and aligns well with C idioms, but it introduces a new question about whether the advice subsystem’s turn-off instructions should be expanded more broadly. This could spark further discussion about the subsystem’s design and user experience.

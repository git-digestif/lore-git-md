This is a substantive review comment in the ongoing thread about fixing the `defaultBranchName` advice documentation. Jeff King (Peff) responds to Junio’s suggestion for handling the backward-compatibility case for the existing `advise()` function, which is not tied to any specific `advice_setting[]` entry.

Peff proposes using `NULL` instead of creating an ad-hoc `advice_setting` struct on the stack, arguing that `NULL` naturally represents the absence of a matching advice config. He suggests that `vadvise()` could check `if (conf && !conf->level)` to decide whether to show the turn-off instructions. This approach is simpler and avoids the need for a dummy struct, but it does not address the broader architectural goal of passing the entire `advice_setting` struct to `vadvise()` for future extensibility.

He also raises a larger question about the user experience of the turn-off instructions: many existing calls to `advise()` predate the addition of turn-off instructions and do not use `advise_if_enabled()`, meaning they miss the opportunity to show the instructions. He wonders whether users would find the instructions annoyingly chatty if they were shown everywhere, and whether the project should consider converting all `advise()` calls to `advise_if_enabled()` to standardize the behavior. This is a UI philosophy question rather than a technical blocker, but it could influence how the patch is received.

Finally, Peff notes that some callers of `advise()` do significant work before deciding to show the message, which would not fit cleanly into `advise_if_enabled()`. He suggests that if those callers want the turn-off instructions, the `advise()` function could be extended to accept an `advice` enum directly, though this would require a way to pass a "no advice" marker (like `NULL`) for cases that are not tied to a config value. Alternatively, callers could use `advise_if_enabled()` inside the block, even though the check is redundant.

The email does not resolve the architectural question of how to handle the `advise()` backward-compatibility case, but it introduces a simpler alternative to Junio’s proposal and raises broader questions about the consistency and user experience of the advice subsystem. The thread remains open, with the author (Vsevolod Myalitsyn) likely to address these points in the upcoming v3.

This is the v9 iteration of Karthik Nayak’s four-patch series introducing the `receive-report` hook for `git-receive-pack`. The series is now **feature-complete and ready for integration**, with the final blocker—a critical design flaw in protocol version handling—resolved in this version.

The hook allows server administrators to intercept and rewrite the status report sent to clients after ref updates are committed but before the response is finalized. GitLab’s use case is multi-version concurrency control (MVCC), where the server must report a status that reflects post-push operations (e.g., background maintenance) rather than the immediate outcome of `ref_transaction_commit()`. The hook receives the pkt-line encoded report on stdin and replaces it with its stdout; stderr is forwarded to the client via the sideband channel. A non-zero exit code rewrites all ref status lines to `"receive-report hook failed"` and aborts the push, though ref updates are not rolled back—this intentional decoupling between reported status and actual repository state is documented and justified in the commit message.

The v9 iteration fixes the last remaining issue: a `BUG()` call in patch 2/4 that assumed the client’s requested protocol version was always valid. Clients may omit the `report-status` or `report-status-v2` capability entirely, leaving the version as `REPORT_STATUS_UNKNOWN`. The fix replaces the `default: BUG(...)` case with an explicit `REPORT_STATUS_UNKNOWN` case that silently skips the status report, aligning with existing behavior. The rest of the series is unchanged: patch 1/4 documents the existing `proc-receive` hook in `git-receive-pack.adoc`, patch 2/4 refactors report status tracking to use an `enum` instead of static variables, and patch 3/4 unifies the `report()` and `report_v2()` functions into a single helper. Patch 4/4 implements the hook itself, with 224 lines of test coverage in `t/t5412-receive-report-hook.sh` exercising passthrough, failure modes, stdin/stdout handling, and sideband relay.

The series has been **queued in `next`** since 2026-09-05 but was blocked from graduating to `master` until this fix. All prior feedback—including Junio C Hamano’s maintainability concerns, Patrick Steinhardt’s exit status alignment proposal, and surface-level nits from Kristoffer Haugsbakk and Phillip Wood—has been addressed. The only open question is a **philosophical one**: the hook’s ability to report a state divergent from the actual repository state violates Git’s traditional consistency guarantees, but the commit message explicitly acknowledges this trade-off and justifies it with GitLab’s MVCC use case. No further code changes are proposed or needed.

This is a well-crafted, thoroughly tested feature that fills a real gap in Git’s server-side extensibility. The implementation is clean, the documentation is clear, and the test coverage is comprehensive. The series is now **ready for `master`** once Junio picks up the v9 iteration.

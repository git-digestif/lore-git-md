This is a focused technical exchange in Patrick Steinhardt’s v2 series to unify Git’s ref storage terminology. The patch in question (8/11) enforces immutability of the ref storage format and payload during reinitialization, preventing silent repository corruption.

Kaartic Sivaraam’s review identified a real edge case: the current implementation uses a direct string comparison (`strcmp`) to validate payloads, which can incorrectly reject semantically identical but syntactically different paths (e.g., `files:///path/to/store` vs. `files:///path/to/./store`). He proposed normalizing paths with `strbuf_realpath()` to align with how payloads are resolved at runtime in `refs_compute_filesystem_location()`.

Patrick’s reply clarifies why this suggestion isn’t viable: the payload isn’t guaranteed to be a filesystem path. For example, a database-backed ref storage backend might use the payload to specify a connection string (e.g., `postgres://host:port/db`). The `strcmp` approach is intentionally generic, leaving payload interpretation to the backend. This design choice preserves flexibility for future backends while still catching accidental changes to the payload string itself.

The discussion is now settled on this point. No further changes are expected to the payload comparison logic, and the rest of the patch remains uncontroversial. The series continues to address a clear technical debt issue with thorough test coverage and backward-compatible aliases.

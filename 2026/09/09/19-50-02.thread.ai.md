Subject: [PATCH 0/4] Precompile git-compat-util.h for faster builds
Series version: v1 (initial submission)
Originating author: SZEDER Gábor
Thread type: patch series (build system improvement)

Core problem or goal
Introduce precompiled headers to the Git build process, targeting the frequently included `git-compat-util.h` header to reduce build times by ~35%. The series is purely build-system focused, with no runtime behavior changes.

Current status
Under review; v1 posted. No prior versions. No maintainer decisions or merge signals yet.

Key technical details
- Files touched: `Makefile`, `contrib/buildsystems/CMakeLists.txt`, `.gitignore`
- New artifacts: `.git-compat-util.h.gch` (precompiled header, excluded from version control), `tools/precompiled.h.gch` (final patch)
- Subsystem: build system only; no core Git functionality modified
- Symbols: none (build-time optimization only)
- On-disk format: unchanged
- Test coverage: none (build system change; no new runtime tests)
- Cleanup prerequisite: Patch 1 removes an obsolete `XDIFF_OBJS` initialization in `Makefile` (leftover from 2025 removal of static `XDIFF_LIB` in cf680cdb95), with no functional impact. Patch 2 generalizes CMake’s parsing of the Makefile to ignore all `*_OBJS` variables (e.g., `XDIFF_OBJS`, `REFTABLE_OBJS`) via a regex, preventing future pollution of source lists when new object-file variables are added.
- Patch 3: Resurrects the `REFTABLE_OBJS` Makefile variable to isolate reftable object files (except `reftable/system.c`) from precompiled-header processing, as these files deliberately avoid including `git-compat-util.h` for embeddability. The change is mechanical: moves reftable objects from `LIB_OBJS` to `REFTABLE_OBJS` and adds `REFTABLE_OBJS` to `LIB_OBJS` to preserve the final link. CMake is updated to parse `REFTABLE_OBJS` and include those sources in the `libgit` target.
- Patch 4: Implements the Makefile logic for precompiled headers, including:
  - A rule to generate `tools/precompiled.h.gch` from `git-compat-util.h`.
  - `PRECOMPILED_HEADER_USERS` definition to exclude `COMPAT_OBJS`, `REFTABLE_OBJS`, and `THIRD_PARTY_SOURCES`.
  - A build rule for `PRECOMPILED_HEADER_USERS` using `-include tools/precompiled.h` and `-Winvalid-pch`.
  - A `NO_PRECOMPILED_HEADER` knob for disabling the feature.
  - Dependency tracking via computed header dependencies or `LIB_H`/`GENERATED_H` fallback.
  - Hardcoded `.gch` suffix for GCC/Clang compatibility (future compilers may require a configurable knob).
- Follow-up refinement: A proposed alternative to Patch 4’s exclusion logic splits `COMPAT_OBJS`, `REFTABLE_OBJS`, and `THIRD_PARTY_SOURCES` into `_NOPCH` variants (`COMPAT_NOPCH_OBJS`, `REFTABLE_NOPCH_OBJS`, `THIRD_PARTY_NOPCH_SOURCES`), updating conditional blocks in the Makefile and CMake to parse both variants. This approach yields only a 1% speedup (0.2s) and is presented as unjustified complexity.

Open questions and loose ends
- Benchmark reproducibility: the 35% speedup claim (29.4s → 21.7s with `-j12`) is anecdotal; no detailed measurements or CI validation provided. The follow-up refinement shows only a 1% improvement (21.7s → 21.5s), suggesting diminishing returns for finer-grained filtering.
- CMake adjustments: may need review from Windows/CMake builders to confirm no regressions, particularly for the regex-based generalization in Patch 2 and the `REFTABLE_OBJS` parsing in Patch 3. The follow-up refinement adds parsing for `_NOPCH` variants, which may further complicate CMake maintenance.
- Precompiled header compatibility: potential concerns about compiler support or cross-platform consistency (e.g., `.gch` suffix hardcoding, lack of a configurable knob for future compilers).
- Dependency tracking: reliance on computed header dependencies (when enabled) or `LIB_H`/`GENERATED_H` fallback may not cover all edge cases.

Participant positions
- SZEDER Gábor (author): proposes the change as a self-contained build optimization with measurable speedup. Patch 2’s regex-based generalization and Patch 3’s `REFTABLE_OBJS` resurrection are explicitly flagged as needing CMake expert feedback. The follow-up refinement demonstrates that finer-grained exclusion logic yields minimal performance gains and is not worth the added complexity. No prior feedback incorporated yet. The final patch (4/4) is presented as unlikely to be controversial but notes the need for broader compiler compatibility testing.

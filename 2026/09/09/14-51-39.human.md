This is the final patch in Karthik Nayak’s four-part series introducing the `receive-report` hook for `git-receive-pack`. The series is now feature-complete, queued in `next`, and ready for final review before graduating to `master`.

The patch implements the core hook logic, allowing server administrators to intercept and modify the pkt-line encoded status report sent to clients after ref updates are committed. The hook receives the report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband. This design enables GitLab’s MVCC use case, where the server must report a status reflecting operations *after* `ref_transaction_commit()` completes. The hook’s exit semantics are now stable: zero exit uses the hook’s stdout as the report, while non-zero exit rewrites all ref status lines to `"receive-report hook failed"`.

The implementation is clean and well-tested, with 224 lines of new test coverage in `t/t5412-receive-report-hook.sh` verifying passthrough behavior, failure modes, stdin/stdout handling, sideband relay, and the hook’s ability to modify the `unpack` status line. The documentation in `githooks.adoc` and `git-receive-pack.adoc` is thorough, explicitly acknowledging the consistency trade-off (decoupling reported status from actual repository state) and justifying it with GitLab’s requirements. The hook’s single-script design (not integrated with the config-based hook infrastructure) is documented and consistent with `proc-receive`.

All prior feedback has been addressed, including the critical fix in patch 2/4 (resolving a `BUG()` call when clients omit `report-status` capabilities) and Patrick Steinhardt’s refactoring suggestions. The series is rebased onto `master` and resolves conflicts with Justin Tobler’s concurrent "pluggable writes" work. This patch is the culmination of a long, iterative effort and looks ready for merging.

This is the second patch in a now-ready-to-merge three-patch series that aligns auto maintenance behavior across Git’s sequencer-driven commands (`git rebase`, `git cherry-pick`, `git revert`). The patch moves the `run_auto_maintenance()` call from the sequencer layer into the two built-in commands that invoke it—`builtin/rebase.c` and `builtin/revert.c`—so that maintenance runs exactly once at sequence completion, matching the apply backend’s behavior.

The change is straightforward: after the sequencer returns and cleans up its state directory (for rebase) or after any successful pick, continue, or skip operation (for cherry-pick/revert), the built-in command invokes `run_auto_maintenance()`. This consolidates maintenance into a single exit path per command, eliminating the previous behavior where maintenance could run after each conflict resolution. The patch also extends test coverage in `t/t3418-rebase-continue.sh` and `t/t3510-cherry-pick-sequence.sh` to verify that maintenance runs exactly once at sequence end and not during intermediate steps, using `GIT_TRACE2_EVENT` to inspect subprocess execution.

The commit message is now concise and clearly explains the design choice: the sequencer lacks a single exit point, so maintenance is delegated to the built-ins, which are the only two entry points for sequencer operations. The message also notes the removal of the redundant `gc.auto=0` setting (handled in the first patch) and avoids any LLM-generated phrasing. This patch looks well-crafted, thoroughly tested, and uncontroversial—it directly addresses the feedback from Phillip Wood and Patrick Steinhardt about consolidating maintenance into a unified exit path.

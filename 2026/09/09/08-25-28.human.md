This is the fourth iteration of a three-patch series that aligns auto maintenance behavior across Git’s sequencer-driven operations (`git rebase`, `git cherry-pick`, `git revert`). The goal is to defer auto maintenance until sequence completion, matching the apply backend’s existing behavior and avoiding lock contention or packfile interference during intermediate steps.

The series is now technically complete and ready for merging. The only changes since v3 are to the commit messages, which have been condensed to about a third of their original length in response to Junio C Hamano’s and Patrick Steinhardt’s critiques about modern commit messages growing overly verbose. The code itself is unchanged, and all prior feedback from Phillip Wood, Patrick Steinhardt, and Junio has been addressed.

Key details: the series introduces a reusable `git_config_append_parameter()` helper to build `GIT_CONFIG_PARAMETERS` strings, caches the config string in `replay_ctx` as a `const char *`, and moves the `run_auto_maintenance()` call from the sequencer to the built-in commands (`run_specific_rebase()` in `builtin/rebase.c` and `run_sequencer()` in `builtin/revert.c`). This ensures auto maintenance runs exactly once at sequence completion, after autostash is applied. The config string now only sets `maintenance.auto=false` (the redundant `gc.auto=0` was removed), and test coverage verifies the absence of maintenance during intermediate steps using `GIT_TRACE2_EVENT`.

The only remaining watch item is a hypothetical edge case about very long sequences where mid-sequence repacking might improve performance, but this is noted as a monitoring item rather than a blocker.

This is a Rust infrastructure discussion, specifically about the implications of Mike Hommey's ongoing patch series to reorganize Git's Rust code into a `rust/` subdirectory.

brian m. carlson raises a forward-compatibility concern about Mike's use case: vendoring Git's C code (via submodule) into a Rust project while excluding its Rust components. The current patch addresses this by moving `Cargo.toml` out of the root, which prevents Cargo from treating the entire Git repository as a single crate. However, brian points out that this workaround may break when Git 3.0 makes Rust components mandatory, forcing downstream projects to either adopt Git's Rust code or find a new approach. The question is whether the current reorganization is a short-term fix that will need revisiting soon, or if there's a longer-term strategy for handling mixed C/Rust dependencies in vendored scenarios.

The email does not propose an alternative or object to the patch itself, but it highlights a potential friction point for downstream consumers like git-cinnabar. This is a substantive review comment in the sense that it identifies a real-world scenario that could become problematic, though it stops short of demanding changes to the current patch. The concern is likely to spark further discussion about how Git's Rustification should accommodate external projects that depend on its C code but not its Rust code.

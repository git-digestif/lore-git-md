This is the **v3 revision of the `--matched-only` feature patch** for `git range-diff`, addressing the last remaining architectural concern from Junio C Hamano. The patch adds a `--matched-only` option that filters `range-diff` output to show only commits present in both input ranges, skipping those that exist on only one side. This directly targets the workflow pain point of reviewing rebases or range-diffs where users want to focus on how surviving commits changed rather than seeing added or dropped commits.

The implementation is now **mechanically final** after reverting the error-handling layering violation introduced in v2. Instead of using `die_for_incompatible_opt3()` (which lives in the reusable library layer), the patch now uses the original `error()` call in `range-diff.c` and leaves the CLI front-end (`builtin/range-diff.c`) responsible for calling `die()` if needed. This restores the architectural separation between library and CLI code, which was Junio’s core objection. No other changes are expected unless new objections arise.

Key technical details remain unchanged from v2: the patch touches `builtin/range-diff.c` (CLI option and mutual-exclusion logic), `range-diff.c` (output filtering and error handling), `range-diff.h` (struct field addition), `Documentation/git-range-diff.txt` (option documentation), and `t/t3206-range-diff.sh` (comprehensive test coverage). The new option reuses existing suppression logic by internally setting both `--left-only` and `--right-only` when `--matched-only` is specified, avoiding code duplication. Mutual exclusion is enforced via a simple arithmetic check (`left_only + right_only + matched_only > 1`), and the test suite verifies all combinations of the three filtering options.

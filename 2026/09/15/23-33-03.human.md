This is the first patch in a three-part bugfix series for `--force-if-includes` in `git push`. The patch corrects a long-standing flaw where the safety mechanism checks the reflog of the *local* branch matching the *remote* destination name (e.g., `refs/heads/main`) instead of the branch actually being pushed (e.g., `refs/heads/src` in `src:main`). This misalignment could cause false rejections or unintended data loss, as the reflog of the wrong branch was being consulted.

The fix updates `check_if_includes_upstream()` in `remote.c` to use `ref->peer_ref->name` (the source ref being pushed) rather than `ref->name` (the destination ref). It also unconditionally resolves `peer_ref` with `RESOLVE_REF_READING`, rejecting force-pushes of non-branch refs (e.g., detached HEADs, tags) while allowing them for fast-forwards. Deletions are explicitly permitted by checking `is_null_oid()`. The patch includes 81 lines of new test coverage in `t/t5533-push-cas.sh`, verifying scenarios like differently named branches, HEAD-based pushes, and rejections for orphaned branches or tags.

The implementation is clean and addresses the core issue without introducing regressions. The commit message clearly explains the problem, the solution, and edge cases (deletions, non-branch refs). Prior review feedback—including concerns about symbolic reference resolution and deletion handling—has been resolved. This patch is a well-motivated bugfix with thorough test coverage, and it lays the groundwork for the fast-forward exemption in patch 3/3. Worth a look for anyone using `--force-if-includes`.

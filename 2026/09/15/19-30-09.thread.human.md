This thread is about a bugfix for a long-standing but latent client-side crash in Git’s protocol v2 `upload-pack` subsystem. The issue surfaces during shallow clones or incremental shallow fetches when `uploadpack.allowRefInWanted` is enabled, causing the client to crash with `fatal: expected 'packfile', received 'shallow-info'`. Royce Remer identified the root cause: the server was sending the "wanted-refs" section before "shallow-info", triggering a client-side parsing error due to the `peek` logic in `process_section_header()`.

The fix is minimal—swapping the order of two function calls in `upload-pack.c`—and has been validated by both test cases and production-like testing. Junio Hamano, the maintainer, confirmed the bug’s origin (dating back to 2018) and reviewed the patch as technically sound. The v2 update addressed his earlier feedback on commit-message clarity, explicitly documenting the failure mode, technical rationale, and backward compatibility. Since the feature combination never worked in practice, the change is safe and won’t disrupt existing deployments.

Two new test cases in `t/t5703-upload-pack-ref-in-want.sh` verify the fix for both single-commit shallow clones and incremental shallow fetches, ensuring correct ref resolution and commit history. The patch is now ready for integration, with no open objections or loose ends. It affects only protocol v2 shallow fetches with `uploadpack.allowRefInWanted` enabled, leaving other workflows untouched.

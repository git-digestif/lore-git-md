This thread is about a bugfix for a Git protocol v2 regression in `upload-pack` that affects shallow fetches when `uploadpack.allowRefInWanted` is enabled. The issue causes incorrect or incomplete ref resolution during shallow clones or incremental fetches due to a swapped function call order in `upload_pack_v2()`. Royce Remer proposed a one-line fix to restore the correct order, but the patch is still under review.

Junio C Hamano, the maintainer, has provided a deeper technical analysis of why the ordering matters. The client-side logic in `fetch-pack.c` expects "shallow-info" to precede "wanted-refs" to avoid ambiguity or potential crashes. While the client can tolerate out-of-order sections, sending "wanted-refs" first risks misinterpretation or loss of the "shallow-info" section. Junio’s review highlights the need for the commit message to document this failure mode and assess backward compatibility—neither of which the current patch addresses.

The patch touches `upload-pack.c` and adds test cases to `t/t5703-upload-pack-ref-in-want.sh` to verify the fix for single-commit shallow clones and two-commit incremental fetches. No new symbols or on-disk format changes are involved. The thread remains open, awaiting a revised patch that includes the technical rationale, backward compatibility assessment, and a clearer commit message. Until then, the patch is not ready for merging.

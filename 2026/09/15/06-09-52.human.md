This is the final patch in SZEDER Gábor’s **build system** series (v2) that introduces precompiled headers for `git-compat-util.h` to speed up Git builds. The patch implements the core logic for precompiling the header and integrating it into the Makefile, delivering the ~35% build-time improvement advertised in the series.

The patch adds a new rule to generate `tools/precompiled.h.gch` from `git-compat-util.h`, using the same compiler flags as regular object files (except for target-specific `EXTRA_CPPFLAGS`, which are omitted to avoid conflicts with GCC’s `-Winvalid-pch` option). The precompiled header is included via `-include tools/precompiled.h` for all object files except those in `COMPAT_OBJS`, `REFTABLE_OBJS`, and `THIRD_PARTY_SOURCES` (which either don’t include `git-compat-util.h` or avoid it for embeddability). Dependency tracking is handled either via computed header dependencies (when enabled) or a fallback to `LIB_H` and `GENERATED_H`. A `NO_PRECOMPILED_HEADER` knob allows disabling the feature for testing or unsupported compilers.

The implementation is mechanical and unlikely to be controversial, but the patch notes potential cross-platform concerns: the `.gch` suffix is hardcoded for GCC/Clang compatibility, and the lack of a configurable knob for future compilers could become an issue. The author also highlights a quirk where the precompiled header is built only once (unlike Meson, which builds it twice), and warns that `-Winvalid-pch` (enabled by default) will fail the build if the precompiled header is unusable (e.g., due to mismatched compiler flags).

The benchmark results (29.4s → 21.7s with `-j12`) are included but remain anecdotal, with no CI validation or detailed measurements. The patch is part of a series where the first three patches (cleanup, CMake adjustments, and `REFTABLE_OBJS` resurrection) are prerequisites. While the series is under review, this patch is the linchpin—if the build-time gains hold up under broader testing, it’s a clear win for developer productivity. The lack of runtime behavior changes and the self-contained nature of the change make it a low-risk, high-reward improvement.

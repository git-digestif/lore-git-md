This is a bugfix patch for `git pull` that prevents a segmentation fault when an invalid merge head is encountered. Junio C Hamano has reviewed the patch and generally approves of the approach, though he notes the solution might feel like a workaround—treating the failed lookup as "not up to date" to let the normal merge machinery handle the error—rather than diagnosing the issue directly. He acknowledges, however, that this is a pragmatic improvement that doesn’t overreach, and it won’t block future refactoring of the internals.

The patch itself adds NULL guards around `lookup_commit_reference()` calls in `builtin/pull.c`, ensuring the command fails gracefully instead of crashing when a merge head reference is corrupted. The included test in `t/t5520-pull.sh` simulates this scenario by corrupting an object file and verifying that `git pull` reports the broken object rather than segfaulting. Junio suggests a minor tweak to the test: replacing the object corruption step (`>"$obj"`) with a simple `rm -f "$obj"` for better portability, as the test’s goal is to trigger a lookup failure, not to validate corruption handling specifically.

The patch is well-motivated, with a clear problem statement (crashes due to concurrent operations corrupting merge heads) and a minimal, focused fix. The test coverage is thorough, and Junio’s feedback is constructive but not blocking. This looks like a straightforward improvement that could be merged soon, pending any further discussion on the test adjustment.

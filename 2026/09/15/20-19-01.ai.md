This is a substantive follow-up review from Junio C Hamano on the same bugfix patch for Git protocol v2 `upload-pack` shallow fetch ordering. The patch remains unchanged—it still swaps the order of `send_shallow_info()` and `send_wanted_ref_info()` in `upload_pack_v2()`—but Junio now provides a deeper technical analysis of why the ordering matters.

He traces the issue to the client-side (`fetch-pack.c`) logic, where `process_section_header()` calls check for "shallow-info" and "wanted-refs" sections in sequence, but with the `peek` bit set. This means the client can tolerate receiving the sections out of order, but only if the server sends them in a way that allows the client to consume both. Junio’s key insight is that if the server sends "wanted-refs" first, the client might skip it while looking for "shallow-info", then process "wanted-refs" on the next check—but the "shallow-info" section could be lost or misinterpreted, potentially causing a crash or incorrect shallow fetch behavior. The patch’s reordering ensures the client receives "shallow-info" first, matching the client’s expectation and avoiding this ambiguity.

The review raises critical questions about the client’s robustness: does it crash if it encounters an unexpected section, or does it silently ignore it? Either outcome would be a serious bug, and Junio asks Royce to document this behavior in the commit message. This is a clear call for the patch to include a precise description of the failure mode—something the current version lacks. The thread remains open, awaiting a revised patch with this technical rationale and backward-compatibility assessment.

Thread identity
Subject: [PATCH] git-contacts: accept patch input from stdin
Series version: standalone patch (v3, with v4 anticipated)
Originating author: Brigham Campbell
Thread type: feature patch for a contrib script

Core problem or goal
Extend `git-contacts` (a contrib Perl script in `contrib/contacts/`) to read patch content from stdin using the conventional UNIX `-` idiom, enabling mixed file/stdin usage (e.g., `git contacts patch1 - patch3 <patch2`) and improving interoperability with external tools such as `b4`. This replaces the v2 behavior, which implicitly read from stdin when no arguments were given and stdin was not a terminal.

Current status
Under review; v3 posted implementing the `-` idiom as suggested by Junio C Hamano. Junio has proposed two refinements: (1) a structural alternative that avoids a separate `$read_from_stdin` flag by treating `-` as a special filename throughout the code path, pushing the stdin logic into `scan_patch_file`, and (2) a commit message clarification to avoid implying that arguments (files, stdin, or revision ranges) are processed in a predictable order. The commit message clarification has been accepted in principle; the structural design question remains the sole open technical point. The feature concept remains endorsed; no functional objections have been raised.

Key technical details
- File touched: `contrib/contacts/git-contacts`
- v3 behavior: treats `-` as a filename argument meaning "read from stdin," enabling mixed file/stdin usage without requiring a terminal check.
- v3 implementation: removes implicit stdin detection (`-t STDIN` check) and replaces it with an explicit `$read_from_stdin` flag set when `-` is encountered in `@ARGV`.
- Junio’s structural alternative: eliminate the `$read_from_stdin` flag and instead treat `-` as a special filename in `scan_patch_file`, making the behavior more localized.
- Argument processing: the script does not guarantee deterministic output order for the same input files and explicitly disregards argument order when mixing file paths and revision ranges. The commit message has been updated to avoid implying sequential processing.
- Usage comment: reverted to pre-v2 text in v3, as the `-` idiom is self-documenting and does not require explicit stdin documentation.
- No new symbols, CLI options, or on-disk format changes.

Open questions and loose ends
The design question of how to best integrate the `-` idiom into the codebase remains open: whether to keep the v3 `$read_from_stdin` flag or adopt Junio’s alternative of treating `-` as a special filename in `scan_patch_file`. The author has not yet responded to this structural suggestion.

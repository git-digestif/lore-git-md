This is a bugfix patch (1/2 in a two-part series) targeting the `apply.c` subsystem. It addresses a long-standing crash in `git apply --check` when processing malformed diff headers, a bug reported by a first-time contributor and now under final review after a major revision.

The patch enforces stricter validation of diff headers by rejecting any `diff --git` line followed by non-header content (blank lines, indented mode lines, or arbitrary text) before the next `diff --git` line. Previously, Git would silently ignore such malformations, leaving stale `old_name`/`new_name` values in the patch struct and triggering an assertion failure (`patch->is_new <= 0`) in `check_preimage()`. The fix now fails early with a clear error message, aligning with Junio C Hamano’s guidance to reject any patch format not generated by `git diff` or `git format-patch`.

Key changes since v1 include rejecting patches that modify files if they contain blank lines after `diff --git` (previously accepted but with ignored mode lines) and dropping acceptance of `diff --git` lines followed by arbitrary text before a traditional patch. The test coverage in `t/t4133-apply-filenames.sh` is thorough, verifying rejection for new files, deletions, and modifications, as well as reverse application (`-R`). The error messages explicitly name the problematic line number, making them actionable for users.

This patch is technically complete and has maintainer endorsement. It merges cleanly with `maint`, `master`, `next`, and `seen`, and the only remaining discussion point is whether to extend the stricter validation to "empty section" cases (a `diff --git` line with no content followed by another `diff --git`). The fix is narrowly scoped, well-motivated, and addresses a real crash affecting released versions (2.43+). It’s worth attention from reviewers familiar with the apply subsystem, particularly for validating the test cases and error message clarity.

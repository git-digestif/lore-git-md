This is the second patch in a two-part bugfix series addressing a crash in `git apply --check` when processing malformed patch headers. The series now enforces strict validation of patch header ordering, rejecting any format that `git diff` or `git format-patch` would not generate.

This patch specifically targets a long-standing edge case where `---` or `+++` lines appear *before* `new file mode` or `deleted file mode` lines, respectively. When this happens, the `patch` struct ends up in an inconsistent state: a "new" file retains an `old_name` (e.g., `/dev/null` parsed as `dev/null`), or a "deleted" file retains a `new_name`. The result is an assertion failure (`patch->is_new <= 0`) in `check_preimage()`. The fix adds explicit validation in `parse_git_diff_header()` to reject such patches with clear error messages, following the precedent set by commit `d70e9c5c8c` (2017) for other mutually exclusive header lines.

The patch is well-motivated and technically sound. It includes thorough test coverage in the new `t/t4133-apply-filenames.sh` file, verifying both `--check` and reverse application (`-R`) for the problematic cases. The error messages are actionable, distinguishing between file-based and line-based input sources. The stricter validation aligns with maintainer guidance to reject corrupt input outright rather than attempting to normalize it, and the patch merges cleanly with `maint`, `master`, `next`, and `seen`.

This is a **clear bugfix** with minimal risk, addressing a deterministic crash in released versions (confirmed in Git 2.43 and later). The only behavioral change is that patches with `---` before `new file mode` or `+++` before `deleted file mode`—which previously applied (or crashed) silently—are now rejected with a descriptive error. The series is ready for final review, likely to focus on error message clarity and the backwards-compatibility trade-offs of rejecting previously accepted (but malformed) patches. No further philosophical debate is expected.

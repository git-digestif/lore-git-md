This is a feature patch series (v14 of 5 patches) that introduces a "matching-inspired" fetch mode to solve a performance problem in shallow repositories. When you add a remote to a shallow clone, a plain `git fetch` currently negotiates history for *every* branch on that remote, which can be slow or hang entirely. The series lets users configure a remote to fetch only the branches that local branches track, avoiding the unnecessary overhead.

The core idea is to split the "what to fetch" and "where to store it" concerns. Patch 1 adds a new config key `remote.<name>.fetchRefmap` that specifies which refs to fetch (e.g., `*@{upstream}`), while the existing `remote.<name>.refmap` handles namespace mapping. Patch 3 makes a refspec-less fetch on such a remote dynamically fetch only the branches tracked by local branches at that remote. Patches 4 and 5 add a `--limited-fetch` flag to `git remote add` and make it the default in shallow repositories, so users get the optimized behavior automatically.

This v14 revision is the culmination of a long review process. The author has addressed all major design objections: the config key is now unambiguously named `fetchRefmap`, override semantics are clarified (command-line refspecs override the config entirely), and the `@{push}` resolution edge case is fixed. The series is well-tested, with thorough coverage of the new behavior and edge cases. The commit messages and documentation are clear and complete.

The series is now under final review for merging to `master`. Two strategic questions remain: whether to merge the full series or just the first three patches (to unblock a dependent topic), and whether to eliminate the dynamic branch enumeration logic (Patch 3) on architectural grounds. The author has made a strong case for the current design, and the dependent topic's conflicts are resolvable with Patches 1–3, so a partial merge seems likely. This is a well-crafted, thoroughly reviewed contribution that addresses a real pain point for users of shallow repositories.

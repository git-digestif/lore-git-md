This is the first patch in Yoichi NAKAYAMA’s three-part feature series introducing worktree-specific submodule configuration. The patch fixes a long-standing portability issue: when `submodule.<name>.gitdir` is stored as an absolute path, moving a linked worktree breaks the submodule because the path no longer points to the correct location. The fix ensures the gitdir path is always relative to the worktree, so the submodule continues to work even if the worktree is relocated.

The change is small and surgical. It adds a helper to determine the current worktree, then replaces hard-coded `repo_git_path_append()` calls with relative-path logic that uses `worktree_git_path()` and `relative_path()`. The new test in `t/t7425-submodule-gitdir-path-extension.sh` verifies that `git submodule init` in a linked worktree produces the expected relative path (`../.git/worktrees/wt/modules/sub1`). The patch also updates the error message to guide users toward the correct relative-path format.

Yoichi has already addressed a static-buffer issue raised in the initial review by copying the result of `worktree_git_path()` into a `strbuf` before any other function calls can clobber it. The implementation is clean, backward-compatible (only active when `extensions.worktreeConfig` is enabled), and lays the groundwork for the rest of the series. If you care about submodule workflows across multiple worktrees, this patch—and the series it anchors—looks like a well-motivated and carefully executed step forward.

This is the first patch in Harald Nordgren’s v14 series introducing `remote.<name>.fetchRefmap`, a new configuration key that provides the default value for the `--refmap` option in `git fetch`. The patch adds the plumbing: parsing the new config key, storing it in the `remote` struct, and integrating it into the refspec precedence logic in `remote.c` and `builtin/fetch.c`.

The new key lets users configure how fetched refs are mapped to remote-tracking refs without affecting what is fetched. For example, a remote can list specific branches in `remote.<name>.fetch` while using `remote.<name>.fetchRefmap` to map all fetched heads into a consistent namespace. The patch ensures that `remote.<name>.fetch` still decides what to fetch, while `fetchRefmap` only controls where those refs are stored. This separation addresses the maintainer’s objection to overloading `remote.<name>.refmap` in earlier versions.

The implementation is straightforward: `remote.c` gains a new `refmap` field in the `remote` struct, the config parser learns to read `remote.<name>.fetchRefmap`, and `get_ref_map()` in `builtin/fetch.c` uses the new field as the default refmap when no explicit `--refmap` is given. The patch also updates `remote_find_tracking()` to fall back to the refmap when `remote.<name>.fetch` has no match, ensuring that `@{upstream}` and `git branch --track` work for branches stored via `fetchRefmap`.

The test coverage is thorough, verifying that the new config key behaves like `--refmap` on the command line, that it correctly maps branches named in `remote.<name>.fetch`, that it tracks branches outside the fetch refspec, and that negative refspecs in `remote.<name>.fetch` still exclude branches. The tests also confirm that `remote.<name>.fetch` takes precedence over `fetchRefmap` when both are configured.

This patch is foundational and uncontroversial; it enables the rest of the series and has no known blockers. It is part of the ongoing effort to improve fetch ergonomics in shallow repositories, and its design is finalized and endorsed by Junio and Phillip Wood. The series as a whole is under final review for merging to `master`, with two strategic decisions remaining: whether to merge only the first three patches (to unblock a dependent topic) and whether to eliminate the dynamic branch enumeration logic in patch 3/5. This patch is unaffected by those discussions.

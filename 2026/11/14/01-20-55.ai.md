This is the second patch in Tanga Joris's two-part bugfix series targeting a crash in `git apply --check` when processing malformed diff headers. The patch enforces strict validation of patch header ordering, rejecting new or deleted files that have both old and new names due to inconsistent header lines.

The fix addresses a long-standing edge case where `---` or `+++` lines appear *before* `new file mode` or `deleted file mode` lines, respectively. This ordering violates Git's internal assumptions, leading to a crash in `check_preimage()` when the `patch` struct ends up with conflicting state (e.g., `is_new > 0` but `old_name` set). The patch follows the precedent set by commit `d70e9c5c8c` (2017), which similarly rejected mutually exclusive header lines, by adding explicit validation in `parse_git_diff_header()` to error out with clear messages when these conditions are detected.

The implementation is straightforward: after parsing the header, the code checks for inconsistent state (`is_new > 0 && old_name` or `is_delete > 0 && new_name`) and rejects the patch with an error message that names the problematic files and line numbers. The error messages distinguish between file-based and line-based input sources, making them actionable for users. Test coverage in `t/t4133-apply-filenames.sh` verifies both the new validation and reverse application (`-R`), ensuring deletions are also caught.

This patch is technically sound and aligns with the maintainer-endorsed stricter validation approach established in the series. It targets `maint` and merges cleanly with `master`, `next`, and `seen`. The only behavioral change is rejecting previously accepted (but malformed) patches, which is a deliberate trade-off for robustness. No further debate is expected, as the series has already converged on the stricter validation philosophy. The next step is final review (likely by Eric Sunshine) to assess error message clarity and backwards-compatibility implications.

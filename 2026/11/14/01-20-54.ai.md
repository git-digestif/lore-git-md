This is the first patch in a two-part bugfix series targeting the `apply.c` subsystem, now revised to **reject corrupt patch headers outright** rather than attempting to normalize them. The patch addresses a long-standing crash in `git apply --check` (and `git apply -R`) when processing malformed diff headers, specifically when a `diff --git` line is followed by non-header content (blank lines, indented mode lines, or unrelated text) before the `---`/`+++` lines.

The fix aligns with maintainer guidance to enforce strict parsing rules: any `diff --git` header not immediately followed by valid Git diff headers (e.g., `new file mode`, `deleted file mode`) is now rejected with a clear error message (`"corrupt patch: empty \"diff --git\" header at <file>:<line>"`). This resolves the root cause of the crash—stale `old_name`/`new_name` values in the `patch` struct—by preventing the parser from proceeding with inconsistent state. The stricter validation also rejects previously accepted edge cases, such as patches modifying files with blank lines after `diff --git` (which Git would apply while silently ignoring mode changes).

Key changes since v1:
- **Rejection over normalization**: The patch no longer attempts to parse patches following empty `diff --git` headers, instead treating them as errors. This matches Junio’s and Phillip Wood’s consensus that `git apply` should only accept formats generated by `git diff` or `git format-patch`.
- **Broader scope**: Now rejects all patches with blank lines or indented mode lines after `diff --git`, including modifications (previously accepted but with ignored mode lines).
- **Test coverage**: Adds comprehensive tests in `t/t4133-apply-filenames.sh` for blank lines, indented mode lines, and unrelated text after `diff --git`, verifying both `--check` and actual application (including reverse application for deletions).

The patch is technically sound, with a clear commit message explaining the rationale, root cause, and behavior changes. It merges cleanly with `maint`, `master`, `next`, and `seen`, and the error messages are actionable for users encountering this issue. The only remaining edge case—empty `diff --git` sections followed by another `diff --git`—is intentionally preserved (per 206de27efa), though Junio has hinted this may warrant future re-evaluation.

This is a **well-motivated bugfix** with minimal risk, addressing a deterministic crash in released versions (confirmed in Git 2.43). The stricter validation is a deliberate trade-off for robustness, and the patch is ready for final review (likely by Eric Sunshine) to assess error message clarity and backwards-compatibility implications. No further philosophical debate is expected.

This thread addresses a performance regression in `git log --follow` introduced by a 2026-06-22 commit. The issue affects large repositories like `linux.git`, where `--stat --follow` operations slowed from 28 seconds to nearly 7 minutes due to an expensive per-parent diffing step triggered even when unnecessary. Miklos Vajna proposes a targeted fix: a new `--follow=merges` mode (and corresponding `log.follow=merges` config) that restores the pre-regression behavior while preserving the enhanced rename detection for users who need it.

The patch is well-scoped, with clear documentation of the performance trade-off, improved config parsing (using `git_parse_maybe_bool` to avoid fatal errors), and thorough test coverage. Patrick Steinhardt’s feedback has been incorporated, focusing on defensive implementation and explicit warnings about the cost of enabling merge rename detection. The change touches core diff/log functionality (`diff.c`, `log-tree.c`, `builtin/log.c`) but remains backward-compatible. No objections or alternative approaches have surfaced yet, suggesting this is likely to be uncontroversial. The next steps are likely review and potential merge to `next` if no further concerns arise.

Thread identity: Subject: [PATCH v5 0/4] utf8.c: fix bounds handling and documentation in utf8_strnwidth() and utf8_width(). Series version: v5 (four patches), posted by Dirk Gouders, down from five in v4 and replacing the retracted v3. Originating author: Dirk Gouders, with patch 1 authored by Junio C Hamano. Thread type: bugfix patch series. Base commit: f7de81456940dd6f3274e461149bba12965de609.

Core problem or goal: Fix bounds handling in Git's UTF-8 display-width code so that utf8_strnwidth() and utf8_width() respect their length arguments and do not read past the end of the input buffer, including the mmapped-region SIGBUS edge case; additionally correct the misleading documentation on utf8_strnwidth().

Current status: v5 is the latest posted version and is under review; no version has been merged or queued in any integration branch. v5 drops the v4 patch 5 (display_mode_esc_sequence_len_all() helper) entirely as agreed, restores the undeclared `skip` variable that broke v4's compilation, fixes the two test-only nits in t/unit-tests/u-utf8-ansi.c by using arrays initialized with string constants so sizeof() yields buffer size, and incorporates Andy Koppe's simplified bounds checks. The API design has shifted from v4's end-pointer approach back to a length-based `_counted` API, but now uses an array index/length rather than pointer arithmetic, explicitly to avoid both O(n^2) degradation on NUL-terminated strings and the undefined behavior of computing s + len when len is SIZE_MAX. Junio C Hamano has reviewed all four patches individually and stated in a follow-up cover-letter review that aside from the specific mechanical issues already detailed, the series is in "a very good shape" and that "we are getting closer to the finish line," signaling strong approval and convergence toward merge readiness; the series remains unmerged and not yet in any integration branch. Dirk Gouders has replied agreeing to address all of Junio's enumerated mechanical requests in a future version, and has specifically confirmed agreement to rewrite the patch 3/4 commit message with a concrete example of the out-of-bounds symptom and to add the requested comment in test_utf8_width__strnwidth_ansi() about cl_assert_equal_i() being provisional.

Key technical details: Files touched: utf8.c, utf8.h, pretty.c, Makefile, t/meson.build, new unit tests t/unit-tests/u-utf8-ansi.c and t/unit-tests/u-utf8-width.c wired into both Makefile and t/meson.build. Symbols: utf8_strnwidth(), utf8_width(), and display_mode_esc_sequence_len_counted(const char *s, size_t len) (patch 1, authored by Junio C Hamano), which scans for an ANSI SGR sequence bounded by index/length rather than an end pointer; the v4 end-pointer display_mode_esc_sequence_len(const char *start, const char *end) and the proposed display_mode_esc_sequence_len_all() are both absent from v5. Patch 2 is documentation-only, changing the utf8_strnwidth() comment to say NUL-terminated and fixing the documented invalid-UTF-8 return from strlen() to len. Patch 3 ensures utf8_strnwidth() respects the len boundary after skipping ANSI escape sequences using the new _counted variant and checking against orig + len, breaking the loop when string >= orig + len. Patch 4 modifies the main loop to declare `size_t remainder`, compute it as `orig + len - string`, and pass `&remainder` to utf8_width(&string, &remainder) so multibyte characters chopped by len do not cause out-of-bounds reads; the `skip` variable is now declared. Call sites use the length-based form throughout; pretty.c passes ch + 1 in format_and_pad_commit() via the counted API. Tests in t/unit-tests/u-utf8-ansi.c cover the new counted function including wrapper tests, and t/unit-tests/u-utf8-width.c covers bounded utf8_strnwidth() behavior including chopped CJK sequences via test_utf8_width__strnwidth_cjk_chopped() (verifying "三bytes..." with len 1 returns width 1 and len 3 returns width 2) and the test_utf8_width__strnwidth_ansi() case; test code uses arrays with sizeof() for correct buffer sizing. Junio's review of patch 1 specifies that in utf8.c the four comparisons between index `i` and `len` should be written as `len <= i` rather than `i >= len`; that in strbuf_add_wrapped_text() the unconditional `strlen(text)` call computing the `end` pointer is wasted when `width <= 0` diverts early and should be moved after that check; that t/unit-tests/u-utf8-ansi.c should drop the redundant `#include <strbuf.h>` (already provided by `<unit-test.h>`), change `cl_assert_equal_i()` to `cl_assert_equal_u()` for size_t return values per the precedent in t/unit-tests/u-odb-inmemory.c, and reword test comments from "end pointers" to "length limits"; and that patch 1's commit message trailers should be reordered to chronological custodial order (original author sign-off first, then Helped-by, then the relaying sign-off). Junio's review of patch 2/4 approves the documentation fix but suggests the commit message use "bounded" rather than "terminated" when describing the length limit. Junio's review of patch 3/4 approves the code change noting it "looks correct" and properly breaks when string >= orig + len, but requests the commit message clarify that the trigger is an escape sequence reaching orig + len causing utf8_width() to read past the length limit, and suggests adding a comment in test_utf8_width__strnwidth_ansi() warning that the cl_assert_equal_i() usage may need future updating per the TODO at the bottom of utf8_strnwidth(). Junio's review of patch 4/4 approves the remainder-based boundary passing to utf8_width() as a "very good change" for preventing out-of-bounds reads on chopped multibyte characters, but suggests the commit title be tightened to distinguish it from 3/4 (proposing "utf8: bound utf8_width() calls in utf8_strnwidth()") and notes that if the convention is to mark functions with a `()` suffix in commit messages, utf8_width should consistently become utf8_width(). On-disk format: no changes.

Gouders has also begun analyzing how callers use the `int` return values of these width functions, observing that in many cases the values end up as width specifiers in printf-style format strings, and has concluded that changing the return type is a task he wants to avoid for now.

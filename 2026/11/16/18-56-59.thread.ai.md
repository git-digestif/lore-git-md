Subject: [PATCH 0/2] utf8.c: fix bounds handling and documentation in utf8_strnwidth()
Series version: v1 under review; v2 in preparation by author
Originating author: Dirk Gouders
Thread type: bugfix patch series

Core problem or goal
Fix two distinct issues in Git's UTF-8 handling code in `utf8.c`:
1. `utf8_strnwidth()` ignores its `len` argument when processing valid UTF-8, potentially reading beyond the intended bounds.
2. The function's documentation incorrectly claims it returns `strlen()` in certain cases, whereas the code actually returns the `len` argument.

Current status
Under review. v1 remains the current posted version. Dirk Gouders has conceded Junio C Hamano's substantive technical concerns and is preparing a v2 that addresses the bounds-handling fix and the mmapped-region memory-safety edge case.

Key technical details
- Files touched: `utf8.c`, new unit test `t/unit-tests/u-utf8-width.c`.
- Symbols: `utf8_strnwidth()` (function behavior and documentation corrected), `display_mode_esc_sequence_len()`, `utf8_width()`.
- On-disk format: no changes.
- Test coverage: new unit test verifies bounds-respecting behavior; coverage details not described in the summary.
- Memory-safety concern: if `string` points to the end of an mmapped region, reading beyond `len` could trigger a `SIGBUS` before the proposed check is reached. Gouders agrees this makes the v1 fix "too late" in that scenario and plans to address it in v2.

Open questions and loose ends
- v2 respin expected to address: (a) placing the boundary guard after the ANSI-escape-skipping loop rather than relying on `display_mode_esc_sequence_len()`, and (b) the SIGBUS risk when `string` points to the end of an mmapped region.
- No alternative fix has been proposed by reviewers yet; the thread awaits Dirk Gouders's v2.

Participant positions
- **Junio C Hamano**: Substantive review. Argues the real issue is a missing guard *after* the loop that skips ANSI escape sequences, not the lack of a boundary in `display_mode_esc_sequence_len()`. Raises concern about `SIGBUS` risk in mmapped regions, implying the fix may be "too late" in some cases. No alternative fix proposed yet.
- **Dirk Gouders**: Concedes Junio's critique. Agrees the blame belongs on the missing guard after the ANSI-escape-skipping loop rather than on `display_mode_esc_sequence_len()` itself. Frames the issue as a "contract mismatch": `utf8_strnwidth()` accepts a `len` boundary but fails to enforce it when calling `display_mode_esc_sequence_len()` (no boundary parameter) and `utf8_width()` (optional boundary not used). Agrees the v1 fix is too late for the mmapped `SIGBUS` case and is preparing v2 to address all points.

Thread identity: Subject: [PATCH v2 0/4] utf8.c: fix bounds handling and documentation in utf8_strnwidth() and utf8_width(). Series version: v2 (four patches) under review; expanded from v1's two patches. Originating author: Dirk Gouders, with patch 1 authored by Junio C Hamano. Thread type: bugfix patch series.

Core problem or goal: Fix bounds handling in Git's UTF-8 display-width code so that `utf8_strnwidth()` and `utf8_width()` respect their length arguments and do not read past the end of the input buffer, including the mmapped-region SIGBUS edge case; additionally correct the misleading documentation on `utf8_strnwidth()`.

Current status: Under review. v2 is the current posted version. It incorporates Junio C Hamano's proposed `display_mode_esc_sequence_len_counted()` as patch 1, retains the v1 documentation fix as patch 2, applies the counted variant plus a post-loop guard inside `utf8_strnwidth()` as patch 3, and adds a new patch 4 extending the same boundary-respecting treatment to `utf8_width()`. Junio C Hamano has reviewed patch 3 (surface-level style nits only: an excess space in `if (skip_ansi )` and a suggestion to break the overlong while-loop condition across lines) and patch 4 (brief approval: "Well spotted, and nicely done", no technical objections or requested changes). Andy Koppe has reviewed patch 2 and pointed out an additional documentation inaccuracy: the corrected comment still describes the input as "null-terminated" even though `utf8_strnwidth()` takes an explicit `len` parameter and operates on a bounded buffer. Dirk Gouders has acknowledged this and confirmed he will also remove the "null-terminated" phrasing in a future version. Andy Koppe has also raised a substantive performance objection to patch 1's wrapper API design, and Dirk Gouders has now agreed to resolve it by dropping the NUL-terminated wrapper entirely and switching its sole remaining caller in `pretty.c` to the counted variant directly, reusing the change Junio C Hamano already made in v1; Dirk has asked whether that approach is acceptable. The series awaits either integration or a possible v3 addressing the patch 1 API change, the patch 2 wording, the patch 3 style nits, or some combination.

Key technical details: Files touched: `utf8.c`, `utf8.h`, new unit tests `t/unit-tests/u-utf8-ansi.c` and `t/unit-tests/u-utf8-width.c` (wired into both `Makefile` and `t/meson.build`). Symbols: `utf8_strnwidth()`, `utf8_width()`, `display_mode_esc_sequence_len()` (retained as NUL-terminated wrapper calling the counted variant with `strlen(s)` in v2, but now proposed for removal), new `display_mode_esc_sequence_len_counted(const char *s, size_t len)` (patch 1, authored by Junio C Hamano) which scans for an SGR sequence without reading at or beyond `s[len]` and returns 0 if the buffer ends before a complete sequence. Three call sites use the counted variant: `utf8_strnwidth()` passes remaining length (`orig + len - string`), `strbuf_utf8_replace()` uses `end - src`, and `strbuf_add_wrapped_text()` computes `end = text + strlen(text)` upfront and passes `end - text` per iteration; the remaining wrapper call site in `pretty.c` is proposed to switch to the counted variant. Patch 3 modifies `utf8_strnwidth()` to use the counted variant in its ANSI-skipping loop and adds a guard ensuring the pointer does not advance beyond `orig + len` before calling `utf8_width()`, addressing both the original bounds bug and the mmapped SIGBUS scenario. Patch 4 modifies `utf8_strnwidth()` to compute `remainder = orig + len - string` before each `utf8_width()` call and pass `&remainder` instead of NULL, ensuring the width calculation respects the caller-supplied length; patch 4 also adds unit test `test_utf8_width__strnwidth_cjk_chopped` in `t/unit-tests/u-utf8-width.c` verifying correct behavior when CJK characters are truncated by the `len` argument (width 1 for the first byte of a three-byte character, width 2 for a complete three-byte character within bounds). Patch 2 is a documentation-only correction to the comment block above `utf8_strnwidth()`: it changes the claim that the function returns `strlen()` when the input is not valid UTF-8 to correctly state that it returns the `len` argument; purely cosmetic, no behavior change. On-disk format: no changes. Test coverage: `u-utf8-ansi.c` tests the counted escape-sequence function including truncated sequences like `"\033[m"` with insufficient length; `u-utf8-width.c` tests `utf8_strnwidth()` and `utf8_width()` corner cases. One v2 test correction: the escape sequence `"\033"` has display width 0, so the expected sum for a truncated string is 3, not 4.

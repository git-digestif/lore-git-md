This thread addresses a crash in Git's submodule handling when a submodule is itself a linked worktree of its repository and `submodule.recurse=true` is set during branch switching in the superproject. Andreas Wendleder reported the bug; Adrian Ratiu traced the root cause to commit `9cf8547320`, which made a previously unreachable `BUG()` in `validate_submodule_legacy_git_dir()` triggerable, and posted a three-patch v1 series that returns a proper error instead of aborting, fixes a misleading `extensions.submodulePathConfig` hint in the error path, and teaches `submodule_move_head()` to accept linked-worktree git dirs via a new `validate_submodule_gitfile_dir()` helper. The series remains under review, with no merge to `master`, `next`, or `seen`.

Junio C Hamano has reviewed all three patches and agrees the fixes make sense, but several changes are queued for a v2 that Adrian has not yet posted: dropping a contested explanatory comment from patch 1, extracting a deeply nested block in `submodule_move_head()` into a helper, and replacing hedged wording about `extensions.submodulePathConfig` with an explicit `repository_format_submodule_path_cfg` check via a shared helper across `submodule_move_head()`, `submodule_name_to_gitdir()`, and `clone_submodule()`.

In the latest exchange, Junio identified a subtle control-flow gap in patch 3: when a linked-worktree submodule contains a nested submodule whose `.git` is a real directory, recursive absorption leaves `is_worktree` unset, so a later forced-move block could still rewrite the submodule's `.git` file to an invalid path. Adrian reproduced the exact failure, agreed it is the same class of breakage the series targets, and accepted Junio's proposed restructure -- validating the gitfile and setting `is_worktree` unconditionally after the `.git` path is guaranteed to be a gitfile, before the forced-move check -- committing to implement it in v2. The outstanding item is therefore Adrian's v2 incorporating all agreed changes.

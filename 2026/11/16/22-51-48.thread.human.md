The thread is a three-patch v1 series from Adrian Ratiu fixing a crash when a submodule is itself a linked worktree, sparked by a bug report from Andreas Wendleder. When `submodule.recurse=true` and a submodule is a linked worktree, `validate_submodule_legacy_git_dir()` hit a `BUG()` because linked-worktree gitdirs do not end with the submodule name; the same scenario under `extensions.submodulePathConfig` produced a misleading error hint. The series converts the `BUG()` to a proper error, fixes the misleading hint so it only appears when the extension is actually disabled, and teaches `submodule_move_head()` to accept linked-worktree git dirs so recursive operations succeed without breaking the submodule.

Junio C Hamano has reviewed all three patches and agrees the fixes make sense. On patch 1, he pushed back on a proposed comment as historically contingent, and Adrian agreed to drop it entirely in v2. On patch 2, Junio suggested reusing the hedged wording from `submodule_name_to_gitdir()`, noted that `clone_submodule()` needs the same treatment, and recommended extracting a deeply nested block into a helper function. Most recently, on patch 3, Junio identified a control-flow edge case: when a linked-worktree submodule contains a nested submodule whose `.git` is a directory, `submodule_uses_gitfile()` returns false recursively, so `is_worktree` is never set even though the git dir gets absorbed, risking an incorrect forced-move path. He suggests validating the git dir and setting `is_worktree` unconditionally after ensuring the gitfile exists.

The series remains under review on the list with no merge to `master`, `next`, or `seen`. Adrian Ratiu is expected to respond to Junio's structural suggestion on patch 3 and the outstanding points on patches 1 and 2, then post a v2.

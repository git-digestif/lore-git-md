This thread reports a crash in `validate_submodule_legacy_git_dir()` that occurs when a submodule is itself a linked worktree and `submodule.recurse=true` is set, triggered while switching branches in the superproject worktree. Andreas Wendleder posted the bug report with a reproduction script, noting that the git directory of a linked submodule worktree (e.g., `.git/modules/sub/worktrees/sub1`) does not end with the submodule name, violating an assertion in the validation logic, and that with `extensions.submodulePathConfig` enabled the same scenario fails with a misleading error instead.

Adrian Ratiu has now reviewed the report and confirmed the root cause in a substantive reply: the `BUG()` predates `extensions.submodulePathConfig` but only became reachable after commit 9cf8547320 (2024-01-28), which made `submodule_move_head()` validate a gitdir path read from disk -- and a path from disk should never trigger a `BUG()`. He explains that the reproducer requires a second linked worktree because the primary checkout's gitdir accidentally passes the suffix check, and that test t2405 creates this layout but never exercises a recursive checkout. Adrian also owns the misleading "refusing to create/use" hint when the extension is already enabled, and says he has a local fix that lets the branch switch succeed in both legacy and `submodulePathConfig` modes without touching the main submodule checkout; he will send the patch shortly with a `Reported-by` trailer for Andreas.

The issue remains present in `master`, `next`, and `seen`, so no fix has been merged yet. The thread is still open, awaiting Adrian's patch and further review; the open design question is whether linked worktrees of submodule repositories should be accepted as valid git directories or rejected with a clearer error.

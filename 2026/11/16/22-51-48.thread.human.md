This thread concerns a crash in Git when a submodule is itself a linked worktree and the superproject is switched with `submodule.recurse=true`. Andreas Wendleder reported the `BUG()` in `validate_submodule_legacy_git_dir()`, and Adrian Ratiu has posted a three-patch v1 series that turns the crash into a proper error, fixes a misleading `extensions.submodulePathConfig` hint, and teaches `submodule_move_head()` to accept valid linked-worktree submodule git dirs. The series remains under review; nothing is reported as merged to `master`, `next`, or `seen`.

Junio C Hamano has reviewed all three patches and broadly agrees the fixes make sense. On patch 1, he objected to a historically worded comment, and Adrian agreed to drop it entirely in v2. On patch 2, Junio suggested reusing the hedged “might fix … if it’s not already enabled” wording from `submodule_name_to_gitdir()`, flagged the same unconditional hint in `clone_submodule()`, and recommended extracting a deeply nested block in `submodule_move_head()`. Adrian replied that he had misremembered the existing code: `submodule_name_to_gitdir()` uses hedged wording without explicitly checking the extension. For v2 he wants to explore instead an explicit check of `repository_format_submodule_path_cfg` in all three call sites via a small shared helper, and he agreed to do the helper extraction.

Patch 3 still has an open control-flow concern from Junio: in a nested-submodule case, recursive git-dir absorption can leave `is_worktree` unset, so the later forced-move logic could still mishandle a linked worktree. Junio proposes validating the gitfile and setting `is_worktree` once `path/.git` is guaranteed to be a gitfile, before the forced-move check. Adrian has not yet posted v2; outstanding work is therefore the patch 1 comment removal, the explicit-versus-hedged extension check across the three call sites plus helper extraction, and the patch 3 restructuring for the nested-submodule edge case.

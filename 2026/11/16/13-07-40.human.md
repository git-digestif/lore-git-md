This is the fourth patch in Patrick Steinhardt’s 12-patch series introducing **pluggable commit graphs** as part of the **ODB abstraction** effort. It refactors the logic that decides which commit-graph layers can be merged or chained when writing a split commit graph, shifting from a directory-based check to a depth-based one. This change prepares the code for backend-specific storage policies, where the ODB backend—not the core commit-graph logic—will determine which layers are local or chainable.

The patch modifies only `commit-graph.c`, replacing the existing directory-comparison logic (`strcmp(g->dir, ctx->dir)`) with two new fields in `struct write_commit_graph_context`: `mergeable_layers` and `chainable_layers`. These fields track how many of the topmost layers in the commit-graph chain are eligible for merging or chaining, respectively. The backend (or future backend-specific code) will set these values, while the core logic simply enforces them. The change is mechanical but invasive, touching the heart of the split-graph merge strategy.

No user-facing behavior changes are introduced, but the refactor makes the code more flexible for future ODB backends. The commit message is clear and well-motivated, explaining why the old directory-based approach was problematic for pluggability and how the new depth-based system addresses it. The patch looks like a necessary step in the series, though it may draw scrutiny from reviewers who want to ensure the new abstraction boundary is clean enough to support radically different backends (e.g., ones that don’t use the commit-graph data structure at all).

This is a **refactoring patch** with no performance impact, but it’s a key piece of infrastructure for the broader ODB abstraction goal. If the series lands, this change will likely be uncontroversial—it’s a straightforward improvement to the internal API. The real discussion will probably focus on later patches that expose this logic to backends.

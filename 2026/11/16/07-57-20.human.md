This is a post-merge follow-up about a UI regression in the recently merged `ps/builtin-rerere-subcommands` series. The series converted `git rerere` to use Git’s standard `OPT_SUBCOMMAND()` mechanism, but in doing so it enforced option ordering: the old syntax `git rerere --skip-locked gc` is now rejected, while the new syntax `git rerere gc --skip-locked` is accepted. Junio C Hamano flagged this as a potential breaking change for scripts or users accustomed to the old behavior.

Patrick Steinhardt acknowledges the regression and notes that the `--skip-locked` option was introduced only recently, so its user base is likely small. However, the `--rerere-autoupdate` flag has existed for much longer, making its enforced ordering a more serious compatibility concern. Patrick argues that accepting options that are ignored by the subcommand is a design flaw, but he is open to a targeted fix that would allow `--rerere-autoupdate` to appear in either position while keeping the stricter ordering for newer options like `--skip-locked`. No patch has been proposed yet; this is a discussion about whether and how to address the regression. The tone suggests the project is weighing the trade-off between consistency and backward compatibility.

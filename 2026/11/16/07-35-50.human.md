This is a **performance bugfix** for `git log --follow` that addresses a severe slowdown introduced by a previous change (304812ed33, June 2026). The regression made `git log --stat --follow` on large repositories like linux.git take nearly 7 minutes instead of 28 seconds when dealing with non-linear history.

The patch makes the expensive per-parent rename detection in merge commits **opt-in** rather than default. The original `--follow` behavior (pre-June 2026) is restored as the default, while a new `--follow=merges` option (and matching `log.follow=merges` config) enables the more thorough but costly tracking across merge parents. Documentation now explicitly warns users about the performance trade-off.

The implementation is clean: it adds a `follow_merges` flag to `struct diff_flags`, updates the option parser to accept `--follow[=merges]`, and modifies the config system to handle the new value safely. Tests verify that the new mode works for subtree merges, diamond histories, and conflicting renames, while also ensuring invalid values are rejected.

The patch directly addresses the regression reported by the author and incorporates feedback from Patrick Steinhardt, who suggested the feature. The changes are well-scoped and the commit message clearly explains the motivation and design. This looks like a solid fix for a real-world performance problem.

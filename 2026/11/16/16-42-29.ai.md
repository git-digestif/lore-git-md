This is a **substantive review** of Jasper Mayone’s v5 4/5 patch (`%(currentworktree)`), now dropped from the series. Phillip Wood raises two fundamental design questions and two implementation concerns that directly challenge the patch’s necessity and efficiency.

The review questions whether `%(currentworktree)` should exist at all. Phillip suggests it could be a boolean atom (like `%(HEAD)`) or even folded into `%(HEAD)` by extending it to cover rebasing/bisecting branches. He also points out that the atom’s value (the worktree path) is already available via `%(worktreepath)`, making `%(currentworktree)` redundant for most use cases. The implementation concerns are concrete: (1) the atom could report a different worktree than `%(worktreepath)` if a branch is checked out in multiple worktrees, violating consistency, and (2) using a hashmap to store a single entry is overkill and inefficient.

Phillip’s feedback is technical and specific, citing the existing `%(HEAD)` atom as a precedent and questioning the patch’s core design rather than its mechanics. The review does not test the code but engages deeply with its purpose and implementation trade-offs. This is the kind of feedback that led Junio to object to the patch and Jasper to drop it from the series.

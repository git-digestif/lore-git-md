Thread identity
Subject: [PATCH 0/12] Introduce pluggable commit graphs for ODB abstraction
Series version: v1 (initial submission)
Originating author: Patrick Steinhardt
Thread type: patch series (infrastructure refactor)

Core problem or goal
The series moves commit-graph storage logic into the ODB backend layer, enabling alternative ODB implementations to control where and how commit graphs are read and written. This is a foundational step in the **ODB abstraction** effort. The first nine patches refactor internal commit-graph handling to isolate path-dependent logic, simplify chain management, and prepare for backend-specific control. The tenth patch introduces **pluggable commit-graph callbacks** (`read_commit_graph` and `write_commit_graph`) in the `struct odb_source` interface, allowing backends to define their own storage logic while preserving backward compatibility for the default "files" backend. The eleventh patch completes the isolation of path-dependent logic by moving all commit-graph path derivation and file operations from `commit-graph.c` into the "files" ODB backend (`odb/source-files.c`), leaving only generic orchestration in the core subsystem.

Current status
Under review. The series is at v1 (initial submission), with no merge status reported. The first eleven patches are infrastructure-only refactors; the remaining one patch will complete the abstraction by refactoring the moved code to use backend-specific paths.

Key technical details
- Files touched: `commit-graph.c`/`h` (core refactoring), `odb.c`/`h` (plumbing hooks), `odb/source-files.c` (backend-specific path logic), `builtin/commit-graph.c`, `builtin/fetch.c`, `builtin/gc.c`, `t/helper/test-read-graph.c`, plus minor changes in earlier patches.
- New symbols: `commit_graph_link_base()` (replaces `add_graph_to_chain()`), `commit_graph_read()` (replaces `load_commit_graph_one_fd_st()`), `commit_graph_validate_chain()` (exposes existing validation logic), `commit_graph_write_allowed()` (new helper for write permission checks), `commit_graph_write_layer()` (extracted layer-writing function), ODB backend hooks `read_commit_graph` and `write_commit_graph`, `mergeable_layers` and `chainable_layers` in `struct write_commit_graph_context`, `incomplete` in `struct commit_graph`.
- The tenth patch replaces direct calls to `read_commit_graph_one()` with `odb_source_read_commit_graph()`, removing hardcoded directory traversal and delegating storage logic to the backend. The "files" backend implements the callbacks by iterating through directories (for reading) or writing to the primary directory (for writing), using `files->dirs->abspath` instead of hardcoded paths.
- The eleventh patch moves all path-dependent logic from `commit-graph.c` to `odb/source-files.c`: path helpers (`get_commit_graph_filename`, `get_split_graph_filename`, `get_commit_graph_chain_filename`), file operations (`open_commit_graph`, `open_commit_graph_chain`), and loading logic (`load_commit_graph_one`, `load_commit_graph_v1`, `load_commit_graph_chain`, `load_commit_graph_chain_fd_st`). The `read_commit_graph_one` function is also moved, though its declaration remains in `commit-graph.h` temporarily. The `commit_graph_write` function and its helpers (`mark_commit_graphs`, `expire_commit_graphs`) are relocated to the backend, completing the shift of all path-dependent logic.
- Behavior changes: commit-graph chains are now validated by depth, incomplete chains are explicitly marked in the `commit_graph` struct, and `write_commit_graph_file()` gains a common exit path that rolls back the lock file on every error. The split commit-graph merge strategy now uses depth-based thresholds (`mergeable_layers` and `chainable_layers`) instead of directory path comparisons to determine which layers to merge or chain. The sixth patch defers `expire_commit_graphs()` until success (previously unconditional) and removes redundant fields from `struct write_commit_graph_context` (`base_graph_name`, `commit_graph_filenames_before`, `commit_graph_filenames_after`, `commit_graph_hash_after`), replacing them with local variables (`chain_hashes`, `kept`) and string lists populated by walking the commit-graph chain. The seventh patch moves existing checks (core.commitGraph setting, repository compatibility, and commitGraph.changedPathsVersion bounds) into `commit_graph_write_allowed()` with no behavioral change. The eighth patch splits `write_commit_graph_file()` into `commit_graph_write_layer()` (generic layer writing) and `commit_graph_write()` (backend-specific orchestration), removing `dir` and `graph_name` from the context struct and passing `mergeable_layers` and `chainable_layers` as parameters to the layer-writing function. The ninth patch replaces the `incomplete_chain` out-parameter with the `incomplete` field in `struct commit_graph`, with no user-facing change. The tenth patch clarifies error semantics (e.g., "no graph exists" vs. "backend doesn’t support graphs") and propagates errors consistently. The eleventh patch introduces no behavior changes; it is purely a mechanical refactor to prepare for the final patch. No on-disk format changes.
- Performance: minor improvement in the first patch from avoiding redundant allocations; the second through eleventh patches are neutral.

Open questions and loose ends
- Flexibility: can future backends avoid the commit-graph data structure entirely, or is this design too tightly coupled? Will the depth-based merge strategy sufficiently generalize for all possible backends, or will some need more nuanced control (e.g., per-layer mergeability flags)? Will the current design accommodate backends that want to avoid the commit-graph data structure entirely (e.g., by storing graph data in a database)?
- Performance: will moving path logic into the backend complicate caching or introduce redundant I/O? Could the "files" backend’s directory iteration introduce redundant I/O in some cases?
- Design scope: why retain the commit-graph data structure rather than abstracting it further? Is the split between `load_commit_graph_one()` and `commit_graph_read()` the cleanest design, especially if backend-specific path logic grows more complex? How will the final patch (refactoring the moved code to use backend-specific paths) interact with the current callbacks? Will it require further refactoring of the interface?
- Validation logic: is exposing `commit_graph_validate_chain()` the right abstraction boundary, or should the validation logic be redesigned to better suit backend-specific needs?
- Clarity: the new counters (`mergeable_layers`, `chainable_layers`) are set in a separate loop from where they’re used, which might make the code harder to follow. The sixth patch introduces local variables (`base_rename_from`, `base_rename_to`) that may benefit from further encapsulation or comments to improve readability. The eighth patch’s separation of concerns is clean, but the interface between `commit_graph_write()` and `commit_graph_write_layer()` adds complexity; the value of this split will become clearer when backend-specific implementations are introduced. The ninth patch’s change to `struct commit_graph` is a small but necessary step for the upcoming pluggable interface; its impact on future backend design remains to be seen.
- Future work: the logic for *locating* commit graphs is now fully isolated in the "files" backend, but the moved code still uses hardcoded paths (to be addressed in the final patch). The "files" backend’s implementation is minimal (e.g., it doesn’t yet support writing to multiple directories).

Participant positions
- Patrick Steinhardt (author): proposes the series as a necessary step for ODB abstraction, with no user-facing features yet. The first eleven patches are presented as mechanical refactors critical for later backend-specific work. The sixth, seventh, eighth, and ninth patches are explicitly framed as preparatory, with no behavioral impact beyond the deferred expiration of stale layers, the extraction of layer-writing logic, and the internal representation of incomplete chains. The tenth patch is positioned as a critical step in decoupling commit-graph storage from the "files" backend’s assumptions, enabling future backends to implement their own logic. The eleventh patch is described as "mostly an exact move" of path-dependent logic into the backend, with no behavior changes, preparing the ground for the final patch.

Subject: [PATCH 0/12] Introduce pluggable commit graphs for ODB abstraction
Series version: v1 (initial submission)
Originating author: Patrick Steinhardt
Thread type: patch series (infrastructure refactor)

Core problem or goal
The series moves commit-graph storage logic into the “files” ODB backend, allowing alternative ODB implementations to control where commit graphs are read from and written to. This is a step in the **ODB abstraction** effort; the commit-graph data structure itself is not yet abstracted, but the plumbing is now pluggable. The first patch simplifies chain-linking logic by replacing redundant object ID tracking with a walk of the existing chain structure, reducing memory overhead and preparing for backend-specific chain creation.

Key technical details
- Files touched: `commit-graph.c`/`h` (core refactoring), `odb.c`/`h` (plumbing hooks), `odb/source-files.c` (backend-specific path logic), plus minor changes in `builtin/commit-graph.c`, `builtin/fetch.c`, `builtin/gc.c`, and a test helper. The first patch focuses on `commit-graph.c`/`h`.
- New symbols: `commit_graph_link_base()` (replaces `add_graph_to_chain()`), ODB backend hooks for commit-graph operations; internalized path-derivation logic in the “files” backend.
- Behavior changes: commit-graph chains are now validated by depth, incomplete chains are explicitly marked, and `write_commit_graph_file()` gains a common exit path. The first patch introduces no user-facing changes but makes the internal API more flexible for backend-specific implementations.
- On-disk format: unchanged; this is purely internal plumbing.
- Performance: minor improvement in the first patch from avoiding redundant allocations, though the primary goal is code clarity and pluggability.

Open questions and loose ends

- Design scope: why retain the commit-graph data structure rather than abstracting it further?

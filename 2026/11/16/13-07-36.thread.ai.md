Subject: [PATCH 0/12] Introduce pluggable commit graphs for ODB abstraction
Series version: v1 (initial submission)
Originating author: Patrick Steinhardt
Thread type: patch series (infrastructure refactor)

Core problem or goal
The series moves commit-graph storage logic into the "files" ODB backend, enabling alternative ODB implementations to control where commit graphs are read from and written to. This is a foundational step in the **ODB abstraction** effort. The commit-graph data structure itself remains unabstracted, but the plumbing is now pluggable. The first patch simplifies chain-linking logic by replacing redundant object ID tracking with a walk of the existing chain structure, reducing memory overhead. The second patch refactors the internal API by removing redundant path handling, shifting path-derivation responsibility toward the backend while preserving the commit-graph data structure. The third patch exposes internal chain-validation logic (`validate_mixed_generation_chain` and `validate_mixed_bloom_settings`) as a public function, `commit_graph_validate_chain`, allowing ODB backends to validate chains after loading. The fourth patch refactors the split commit-graph merge strategy to use **depth-based layer selection** instead of directory path comparisons, decoupling the merge logic from filesystem-specific assumptions and enabling backend-specific control over layer mergeability and chainability. The fifth patch introduces a **common exit path** in `write_commit_graph_file()` to consolidate error handling and resource cleanup, preparing the function for upcoming refactoring that will add new allocations requiring rollback. The sixth patch eliminates redundant bookkeeping in the split commit-graph write path by deriving layer information directly from the passed-in commit-graph chain instead of maintaining separate arrays for hashes, filenames, and merge targets, further isolating path-dependent operations to prepare for backend-specific logic.

Key technical details
- Files touched: `commit-graph.c`/`h` (core refactoring), `odb.c`/`h` (plumbing hooks), `odb/source-files.c` (backend-specific path logic), plus minor changes in `builtin/commit-graph.c`, `builtin/fetch.c`, `builtin/gc.c`, and a test helper. The fifth and sixth patches touch only `commit-graph.c`.
- New symbols: `commit_graph_link_base()` (replaces `add_graph_to_chain()`), `commit_graph_read()` (replaces `load_commit_graph_one_fd_st()`), `commit_graph_validate_chain()` (exposes existing validation logic), ODB backend hooks for commit-graph operations, `mergeable_layers` and `chainable_layers` in `struct write_commit_graph_context`.
- Internalized path-derivation logic in the "files" backend.
- Behavior changes: commit-graph chains are now validated by depth, incomplete chains are explicitly marked, and `write_commit_graph_file()` gains a common exit path that rolls back the lock file on every error. The split commit-graph merge strategy now uses depth-based thresholds (`mergeable_layers` and `chainable_layers`) instead of directory path comparisons to determine which layers to merge or chain. The sixth patch defers `expire_commit_graphs()` until success (previously unconditional) and removes redundant fields from `struct write_commit_graph_context` (`base_graph_name`, `commit_graph_filenames_before`, `commit_graph_filenames_after`, `commit_graph_hash_after`), replacing them with local variables (`chain_hashes`, `kept`) and string lists populated by walking the commit-graph chain. No user-facing changes.
- On-disk format: unchanged; this is purely internal plumbing.
- Performance: minor improvement in the first patch from avoiding redundant allocations; the second, third, fourth, fifth, and sixth patches are neutral.

Open questions and loose ends
- Flexibility: can future backends avoid the commit-graph data structure entirely, or is this design too tightly coupled? Will the depth-based merge strategy sufficiently generalize for all possible backends, or will some need more nuanced control (e.g., per-layer mergeability flags)?
- Performance: will moving path logic into the backend complicate caching or introduce redundant I/O?
- Design scope: why retain the commit-graph data structure rather than abstracting it further? Is the split between `load_commit_graph_one()` and `commit_graph_read()` the cleanest design, especially if backend-specific path logic grows more complex?
- Validation logic: is exposing `commit_graph_validate_chain()` the right abstraction boundary, or should the validation logic be redesigned to better suit backend-specific needs?
- Clarity: the new counters (`mergeable_layers`, `chainable_layers`) are set in a separate loop from where they’re used, which might make the code harder to follow. The sixth patch introduces local variables (`base_rename_from`, `base_rename_to`) that may benefit from further encapsulation or comments to improve readability.

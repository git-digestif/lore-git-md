Dirk Gouders has posted version 3 of a four-patch series fixing buffer-bounds handling in Git's UTF-8 display-width code, specifically `utf8_strnwidth()` and `utf8_width()` in `utf8.c`. The series ensures these functions respect their length arguments and never read past the end of the input buffer, closing an edge case where truncated reads from mmapped regions could trigger SIGBUS, and it corrects a misleading comment claiming the functions return `strlen()` on invalid UTF-8. Patch 1 in this iteration, authored by Junio C Hamano, finalizes the API cleanup by replacing the length-based `display_mode_esc_sequence_len_counted()` with a single `display_mode_esc_sequence_len(const char *s, const char *end)` that takes an end pointer directly, eliminating the `strlen()` call that Andy Koppe had flagged as a source of quadratic scanning; the sole remaining caller in `pretty.c` now passes an explicit end pointer. Patches 2 through 4 adjust the documentation, fix the ANSI-skipping loop in `utf8_strnwidth()` to stay within bounds using the new end-pointer API, and extend the same bounds discipline to `utf8_width()`.

The technical direction is now fully settled. All prior objections -- including the wrapper-versus-counted-variant debate and the remainder-parameter compromise -- have been resolved in favor of the end-pointer design, and v3 also addresses the remaining surface-level nits such as meson test-suite ordering and stray whitespace. New unit tests in `t/unit-tests/u-utf8-ansi.c` and `t/unit-tests/u-utf8-width.c` cover the ANSI scanning and CJK truncation cases. With no outstanding technical questions and only integration remaining, the series awaits pickup by the maintainer.

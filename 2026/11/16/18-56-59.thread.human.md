This thread concerns a four-patch v2 series from Dirk Gouders fixing bounds handling in Git's UTF-8 display-width code, `utf8_strnwidth()` and `utf8_width()` in `utf8.c`, so they respect their length arguments and avoid reading past the end of the buffer -- including the mmapped-region SIGBUS edge case -- along with a documentation correction. The series is under review: patch 1 (authored by Junio C Hamano) introduces a counted variant `display_mode_esc_sequence_len_counted()`, patch 2 fixes the misleading comment on `utf8_strnwidth()`, patch 3 applies the counted variant plus a post-loop guard inside `utf8_strnwidth()`, and patch 4 extends the same boundary-respecting treatment to `utf8_width()`. New unit tests were added in `t/unit-tests/u-utf8-ansi.c` and `t/unit-tests/u-utf8-width.c`.

Junio has reviewed patches 3 and 4 with no technical objections -- his comments on patch 3 were surface-level style nits, and he briefly approved patch 4 ("Well spotted, and nicely done"). Andy Koppe raised a substantive performance objection to patch 1, arguing that keeping the NUL-terminated wrapper with its `strlen()` call risks quadratic behavior for repeated scans and recommending that all callers pass an explicit length instead; he also flagged that patch 2's corrected comment still calls the input "null-terminated" despite the explicit `len` parameter. Dirk Gouders has now confirmed he will remove that inaccurate phrasing as well in a potential v3.

The series awaits either integration or a v3 addressing the open items: Andy Koppe's API design concern on patch 1, the "null-terminated" wording in patch 2, and Junio's formatting nits on patch 3. There are no outstanding technical objections to the bounds-handling logic in patches 3 or 4.

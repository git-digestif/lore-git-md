This thread concerns a two-patch bugfix series from Dirk Gouders addressing bounds handling in `utf8_strnwidth()` in `utf8.c`. The core problem is that the function accepts a `len` argument but ignores it when processing valid UTF-8 and ANSI escape sequences, potentially reading past the intended boundary -- a memory-safety risk especially when the string sits at the end of an mmapped region, where an over-read could trigger a `SIGBUS` before any proposed check runs. A second patch corrects documentation that wrongly claims the function returns `strlen()` in certain cases.

Junio C Hamano has driven the technical direction through substantive review. After initially posting an illustrative patch that changed `display_mode_esc_sequence_len()` to take a `size_t len` parameter directly, he has now refined his recommendation: keep the original NUL-terminated `display_mode_esc_sequence_len()` as a thin wrapper that computes `strlen()` and delegates to a new counted variant, `display_mode_esc_sequence_len_counted()`, which accepts an explicit length boundary. This preserves the existing API for other in-flight callers while giving the `utf8_strnwidth()` fix the bounds enforcement it needs. Both parties agree that regardless of how the escape-sequence parser is bounded, a separate guard after the ANSI-skipping loop inside `utf8_strnwidth()` remains necessary.

The series is still at v1 under review; Gouders has conceded the technical points, abandoned his own plan to introduce `ansi_sgr_nlen()`/`ansi_sgr_nlen_multi()` helpers in favor of Junio's wrapper-plus-counted-function approach, and is preparing a v2 that addresses both the post-loop guard and the mmapped-region `SIGBUS` edge case. The thread remains open awaiting that respin.

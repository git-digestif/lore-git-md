This thread is about a bugfix for Git’s UTF-8 string-width calculation. Dirk Gouders identified a boundary-checking bug in `utf8_strnwidth()` that can cause the function to read past the specified length (`len`) when processing ANSI escape sequences. The root cause is that `display_mode_esc_sequence_len()`—used to skip escape sequences—doesn’t respect the caller’s length constraint. The fix adds an explicit bounds check after processing escape sequences, ensuring the function stays within the requested length.

The patch is minimal, touching only the control flow in `utf8.c` without altering the core width-calculation logic. It includes three new unit tests in `t/unit-tests/u-utf8-width.c` that verify edge cases with ANSI sequences and short length arguments, two of which fail without the fix. The issue affects string display operations that use ANSI coloring, which are common in Git’s output. The patch is the first in a two-patch series (the cover letter isn’t shown here), and the fix appears technically sound with good test coverage. No review feedback has been posted yet, so the patch is still under initial consideration.

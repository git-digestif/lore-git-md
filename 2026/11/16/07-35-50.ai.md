This is a performance-focused bugfix patch that makes the `--follow` option in `git log` optional for handling renames in non-linear history. The patch introduces a new `--follow=merges` mode (and corresponding `log.follow=merges` config) to restore the pre-304812ed33 behavior, where `git log --stat --follow` on large repositories like linux.git was significantly faster (28 seconds vs. 6m43s). The change is motivated by a real-world regression: the 2026-06-22 commit improved rename detection for merges but introduced an expensive per-parent diffing step that triggers even when the path isn't added relative to a parent.

The patch is well-structured, with clear documentation updates (including a warning about the performance cost of `merges`), config parsing improvements (using `git_parse_maybe_bool` to avoid fatal errors on invalid values), and thorough test coverage. It addresses feedback from Patrick Steinhardt, who suggested documenting the performance trade-off and improving error handling. The implementation is defensive, checking both `follow_renames` and `follow_merges` flags to avoid edge cases where one might be cleared without the other. The test suite now verifies both the new functionality and error cases (invalid config/argument values).

This is a targeted fix for a specific regression, not part of a larger series. The change is likely to be uncontroversial, as it preserves backward compatibility while offering a performance escape hatch for users who don't need the enhanced merge rename detection. The patch touches core diff/log functionality (`diff.c`, `log-tree.c`, `builtin/log.c`) and includes both command-line and config-based controls, making it accessible to users with different workflows.

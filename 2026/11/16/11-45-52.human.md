This is a **bugfix** targeting the partial clone and object database (ODB) subsystems. The email reports a regression introduced in Git 2.54.0 where a `git cherry-pick` in a `blob:none` partial clone attempts to lazy-fetch a blob that was just written locally, causing the command to fail with a "not our ref" error from the promisor remote. The issue was bisected to commit `5946a564cd` ("odb/source: make `read_object_info()` function pluggable"), which altered how the ODB caches are flushed during object lookups.

The problem occurs because the loose object cache is not invalidated when a new loose object is written, leading to a stale cache state. After the cherry-pick writes the merged blob to the local object store, a subsequent lookup (triggered during commit summary printing) fails to find it in the cache and incorrectly assumes the object must be fetched from the promisor remote. The author provides a minimal reproduction case using a public GitHub repository and confirms the issue persists across multiple recent Git versions, including `master`. They also suggest a potential fix (invalidating the loose cache alongside the packed cache) but note this is exploratory rather than a final solution.

The impact is significant for users of partial clones, as it breaks `cherry-pick` and potentially other operations that write objects and later read them back. The email includes clear steps to reproduce, a bisect result, and a workaround (downgrading to Git 2.53.0), making it actionable for maintainers. The author, affiliated with Mergify, indicates this affects their production environment, adding urgency to the report. This looks like a well-documented regression with a plausible root cause, warranting prompt attention.

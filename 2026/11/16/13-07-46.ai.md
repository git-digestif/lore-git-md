This is the **tenth patch in a 12-patch series** introducing **pluggable commit graphs** as part of the **ODB (object database) abstraction** effort. The patch makes commit-graph reading and writing **backend-agnostic**, allowing alternative ODB implementations to control where and how commit graphs are stored.

### What changes
The patch adds two new **ODB source callbacks** (`read_commit_graph` and `write_commit_graph`) to the `struct odb_source` interface, enabling backends to define their own commit-graph storage logic. The "files" backend (the default) implements these callbacks by delegating to the existing `read_commit_graph_one()` and `commit_graph_write()` functions, but now uses the backend’s directory structure (`files->dirs->abspath`) instead of hardcoded paths.

Key modifications:
- **`odb.h` and `odb/source.h`**: Define the new callbacks and their semantics. The `read_commit_graph` callback returns `1` if no graph exists (not an error), while `write_commit_graph` fails if the backend doesn’t support commit graphs.
- **`odb/source-files.c`**: Implements the callbacks for the "files" backend, iterating through directories to find graphs (for reading) or writing to the primary directory (for writing).
- **`commit-graph.c`**: Replaces direct calls to `read_commit_graph_one()` with `odb_source_read_commit_graph()`, removing the hardcoded directory traversal.
- **`builtin/commit-graph.c`**, **`builtin/fetch.c`**, **`builtin/gc.c`**, and **`t/helper/test-read-graph.c`**: Update callers to use the new backend-agnostic functions (`odb_write_commit_graph()` and `odb_source_read_commit_graph()`). The `commit-graph` builtin retains support for `--object-dir` (specific to the "files" backend) but falls back to the generic ODB interface when no directory is specified.

### Why it matters
This patch is a **critical step** in the ODB abstraction effort, as it decouples commit-graph storage from the "files" backend’s assumptions. Future backends (e.g., reftable, custom storage systems) can now implement their own commit-graph logic without being forced into the `.git/objects/info` directory structure. The design preserves backward compatibility: the "files" backend’s behavior is unchanged, and callers outside the ODB layer see no difference.

### Technical notes
- **No on-disk format changes**: The commit-graph data structure remains unchanged; only the *location* and *control* of storage are abstracted.
- **Error handling**: The patch clarifies error semantics (e.g., "no graph exists" vs. "backend doesn’t support graphs") and propagates errors consistently.
- **Limitations**: The logic for *locating* commit graphs is still in `commit-graph.c` (to be addressed in a later patch), and the "files" backend’s implementation is minimal (e.g., it doesn’t yet support writing to multiple directories).

### Likely discussion points
- **Flexibility**: Will the current design accommodate backends that want to avoid the commit-graph data structure entirely (e.g., by storing graph data in a database)?
- **Performance**: Could the "files" backend’s directory iteration introduce redundant I/O in some cases?
- **Future work**: How will the next patch (moving graph-locating logic into the backend) interact with this one? Will it require further refactoring of the callbacks?

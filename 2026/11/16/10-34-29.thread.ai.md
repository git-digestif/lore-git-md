Subject: [PATCH] read-cache: remove `the_repository` use in `overlay_tree_on_index`
Series version: standalone patch (part of the `the_repository` removal effort)
Originating author: Srujith A Poojary
Thread type: patch (mechanical refactoring with emerging architectural discussion)

Core problem or goal
Eliminate use of the global `the_repository` in `overlay_tree_on_index()` by switching to the repository associated with the provided `index_state` (`istate->repo`). This patch is a step in the ongoing project-wide effort to remove all implicit reliance on `the_repository` in favor of explicit repository parameters. Junio’s feedback expands the scope to question how similar patterns across `read-cache.c` should be addressed in future work.

Current status
Under review; no prior versions posted in this thread. The patch itself remains a clean, mechanical change. Junio C Hamano provided **substantive review feedback** that reframes the patch as part of a larger, still-undefined refactoring plan for `read-cache.c`. No objections to the current patch; cautious approval ("not making things any worse") with a call for broader design discussion on future cleanup.

Key technical details
- File touched: `read-cache.c`
- Function modified: `overlay_tree_on_index()`
- Symbols updated: calls to `repo_get_oid()`, `repo_parse_tree_indirect()`, and `read_tree()` now use `istate->repo` instead of `the_repository`
- No new or renamed symbols; no behavior change; no on-disk format changes
- Test coverage: none added (typical for mechanical refactoring)
- **Broader context**: Junio notes that other functions in the same file (`add_to_index()`, `refresh_index()`) suffer from the same `the_repository` reliance but are not addressed here. Lower-level functions in the file lack `istate` or `repo` parameters, making a wholesale cleanup non-trivial. Passing extra parameters may introduce overhead; attaching an `istate` to cache entries (`ce`) is infeasible due to lifecycle and volume constraints.

Open questions and loose ends
- **Architectural design**: How should the broader cleanup of `the_repository` usage in `read-cache.c` proceed? Junio’s feedback suggests a piecemeal approach (addressing related functions together) but cautions against attempting a full `USE_THE_REPOSITORY` removal in one patch. The deeper challenge of parameterizing lower-level functions remains unresolved.
- **Future patch scope**: Should follow-up patches address multiple functions at once, or continue with small, focused changes like this one?
- **Performance considerations**: Junio’s footnote highlights potential overhead from passing extra parameters, which may influence the design of future refactoring.

Subject: [PATCH] read-cache: remove `the_repository` use in `overlay_tree_on_index`
Series version: v2 (standalone patch, part of the `the_repository` removal effort)
Originating author: Srujith A Poojary
Thread type: patch (mechanical refactoring with emerging architectural discussion)

Core problem or goal
Eliminate use of the global `the_repository` in index-operation functions in `read-cache.c` by switching to the repository associated with the provided `index_state` (`istate->repo`). v1 touched only `overlay_tree_on_index()`; v2 expands the scope to also update `add_to_index()` and `refresh_index()`, batching these related functions into a single commit. This patch is a step in the ongoing project-wide effort to remove all implicit reliance on `the_repository` in favor of explicit repository parameters. Junio's feedback expands the scope to question how similar patterns across `read-cache.c` should be addressed in future work.

Current status
Under review; v2 posted in this thread. The patch remains a clean, mechanical change with no behavioral difference. Junio C Hamano provided substantive review feedback on v1 that reframes the patch as part of a larger, still-undefined refactoring plan for `read-cache.c`. v2 responds to Junio's caution against piecemeal one-function-at-a-time cleanups by grouping the three index-operation functions together. No objections to the current patch; cautious approval ("not making things any worse") with a call for broader design discussion on future cleanup.

Key technical details
- File touched: `read-cache.c`
- Functions modified: `overlay_tree_on_index()`, `add_to_index()`, `refresh_index()`
- Symbols updated: calls to `repo_ignore_case()`, `start_delayed_progress()`, `repo_get_oid()`, `repo_parse_tree_indirect()`, and `read_tree()` now use `istate->repo` (or a local `repo` variable derived from it) instead of `the_repository`
- No new or renamed symbols; no behavior change; no on-disk format changes
- Test coverage: none added (typical for mechanical refactoring)
- Base commit: `1891de46f79`
- Broader context: Junio notes that other functions in the same file suffer from the same `the_repository` reliance but are not addressed here. Lower-level functions in the file lack `istate` or `repo` parameters, making a wholesale cleanup non-trivial. Passing extra parameters may introduce overhead; attaching an `istate` to cache entries (`ce`) is infeasible due to lifecycle and volume constraints.

Open questions and loose ends
- Architectural design: How should the broader cleanup of `the_repository` usage in `read-cache.c` proceed? v2 addresses Junio's concern about piecemeal cleanup by batching related functions, but the deeper challenge of parameterizing lower-level functions that lack an `istate` parameter remains unresolved.
- Future patch scope: Should follow-up patches continue batching multiple functions per commit, or address remaining lower-level helpers?
- Performance considerations: Junio's footnote highlights potential overhead from passing extra parameters, which may influence the design of future refactoring.

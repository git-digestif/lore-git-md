Thread identity: Subject "submodule: fix crash when submodule is a linked worktree", now a three-patch series (`[PATCH 0/3]`, v1) from Adrian Ratiu responding to the original bug report by Andreas Wendleder; thread type bug report / bugfix series. The latest email is Adrian Ratiu's `[PATCH 3/3]`, the final patch of the series.

Core problem or goal: A crash (`BUG()`) occurs in `validate_submodule_legacy_git_dir()` (submodule.c) when a submodule is itself a linked worktree of its repository and `submodule.recurse=true` is set during branch switching in the superproject. Linked-worktree gitdirs (e.g., `.git/modules/sub/worktrees/sub1`) do not end with the submodule name, violating the suffix assertion. Under `extensions.submodulePathConfig`, the same scenario produces a misleading error suggesting the extension is not enabled. The series proposes to fix both issues.

Current status: Under review. v1 of the three-patch series posted by Adrian Ratiu, applying on base commit `e1ec09b23c8e0deb21a0b95ac5996422277395d4`. No fix merged to `master`, `next`, or `seen`.

Key technical details: The series comprises three commits: (1) returning a proper error via `error()` instead of aborting with `BUG()` for an unexpected git dir path in `validate_submodule_legacy_git_dir()`, preserving the existing "refusing to create/use ..." error semantics in legacy mode; (2) only suggesting `extensions.submodulePathConfig` when that extension is actually disabled, fixing the misleading hint in Adrian's own extension code. Patch 2 moves the suggestion into a separate `advise()` call in `submodule_move_head()` that fires only when `the_repository->repository_format_submodule_path_cfg` is false, keeping the fatal `die()` message clean while preserving the hint for users who need it; (3) accepting a linked worktree as a valid submodule git directory so recursive operations succeed without touching the main submodule checkout. Patch 3 modifies `submodule_move_head()` in `submodule.c` to handle a submodule `.git` file pointing to a linked worktree git dir such as `.git/modules/sub/worktrees/sub1`. It introduces helper `validate_submodule_gitfile_dir()`, which uses `get_common_dir_noenv()` to detect linked worktrees, verifies the git dir is located at `<common-dir>/worktrees/<id>` and rejects forged paths elsewhere with an "is not a worktree of" error, and validates the common dir against the submodule name. When a linked worktree is detected, `submodule_move_head()` skips rewriting the `.git` file to the superproject's expected modules path and skips unsetting `core.worktree`, preventing the submodule from being left broken. Patch 1 adds a test to `t/t7450-bad-git-dotfiles.sh` that renames a submodule git dir, points the gitfile at it, and verifies `git checkout -f --recurse-submodules` fails with the new error message without hitting `BUG()`. Patch 2 adds a test to `t/t7425-submodule-gitdir-path-extension.sh` that clones with `extensions.submodulePathConfig=true`, creates a conflicting gitdir layout, runs a recursive checkout, and asserts the error contains "refusing to create/use" but does not mention the extension; it also updates the t7450 test to assert that when the extension is disabled, the output does contain "enabling extensions.submodulePathConfig" and no `BUG()`. Patch 3 adds coverage in `t/t2405-worktree-submodule.sh` for recursive checkout accepting a submodule worktree in both legacy and `extensions.submodulePathConfig` modes plus removal behavior, and in `t/t7450-bad-git-dotfiles.sh` for rejecting a forged worktree git dir with a commondir file. Root cause traces to commit `9cf8547320` (2024-01-28), which made `submodule_move_head()` validate gitdir paths read from disk, making the previously unreachable `BUG()` triggerable; the `BUG()` was originally added in commit `a8dee3ca61` (2019-10-01) under the assumption that callers only passed internally-computed git dirs. Test t2405 created the layout but never exercised a recursive checkout.

Open questions and loose ends: Whether linked worktrees of submodule repositories should be accepted as valid git directories is proposed as accepted in patch 3; awaiting maintainer and community review of the series.

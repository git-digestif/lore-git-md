Thread identity: Subject "submodule: fix crash when submodule is a linked worktree", now a complete five-patch series (`[PATCH v2 0/5]` through `[PATCH v2 5/5]`) from Adrian Ratiu responding to the original bug report by Andreas Wendleder; thread type bug report / bugfix series. The latest email is `[PATCH v2 5/5]` from Adrian Ratiu, the fifth and final commit of the v2 series.

Core problem or goal: A crash (`BUG()`) occurs in `validate_submodule_legacy_git_dir()` in `submodule.c` when a submodule is itself a linked worktree of its repository and `submodule.recurse=true` is set during branch switching in the superproject. Linked-worktree gitdirs such as `.git/modules/sub/worktrees/sub1` do not end with the submodule name, violating the suffix assertion. Under `extensions.submodulePathConfig`, the same scenario produces a misleading error suggesting that the extension is not enabled. The series proposes to fix both issues.

Current status: Under review. v2 of the five-patch series was posted by Adrian Ratiu, applying on base commit `e1ec09b23c8e0deb21a0b95ac5996422277395d4`. All five patches have now been sent. No fix has been merged to `master`, `next`, or `seen`. v2 resolves all outstanding design questions from v1. Junio C Hamano has not yet responded to v2.

Key technical details: The v2 series comprises five commits. Patch 1 (`[PATCH v2 1/5]`) modifies `validate_submodule_legacy_git_dir()` in `submodule.c` to return a proper `error()` instead of aborting via `BUG()` when the git dir path read from a submodule's `.git` file does not end with the submodule name; it drops the contested explanatory comment entirely. The commit message traces the root cause to commit `9cf8547320` (2024-01-28), which added a caller passing a path read from disk, making the `BUG()` -- originally added in commit `a8dee3ca61` (2019-10-01) when all callers passed Git-computed paths -- reachable. The fix ensures the command dies with the standard "refusing to create/use ..." error message rather than a `BUG` abort, matching the behavior when `extensions.submodulePathConfig` is enabled. A new test in `t/t7450-bad-git-dotfiles.sh` verifies that `checkout -f --recurse-submodules` rejects a gitfile pointing to a renamed git dir (e.g., `.git/modules/elephant` instead of `.git/modules/hippo`) with the expected error message and without emitting "BUG". Patch 2 (`[PATCH v2 2/5]`) introduces a shared helper `die_refusing_submodule_git_dir()` in `submodule.c` (declared in `submodule.h`) that centralizes the "refusing to create/use" `die()` message and uses `advise()` to suggest enabling `extensions.submodulePathConfig` only when `r->repository_format_submodule_path_cfg` is false; this replaces the unconditional misleading hint in all three call sites: `submodule_move_head()`, `submodule_name_to_gitdir()`, and `clone_submodule()` in `builtin/submodule--helper.c`. Tests in `t/t7425-submodule-gitdir-path-extension.sh` assert that with the extension enabled the suggestion is absent from both the gitfile-rejection path and the config-gitdir path, while `t/t7450-bad-git-dotfiles.sh` gains an assertion that the hint appears in the default extension-disabled case. Patch 3 (`[PATCH v2 3/5]`) extracts the git dir setup logic from `submodule_move_head()` into a new private static function `setup_submodule_git_dir()` to reduce nesting; this is a pure refactoring with no intended functional change, moving the block that previously lived inside the `if (!(flags & SUBMODULE_MOVE_HEAD_DRY_RUN))` check, and credits Junio C Hamano with suggesting the extraction. The moved code handles three cases: when `old_head` exists and the submodule already uses a gitfile, it validates the git dir via `validate_submodule_git_dir()` and dies via the new helper if invalid; when `old_head` exists but the git dir needs absorbing, it calls `absorb_git_dir_into_superproject()`; and when `old_head` is NULL (new submodule), it connects the work tree and resets the index. The forced-move reconnection via `connect_work_tree_and_git_dir()` with force flag `1` is also moved into the helper. Patch 4 (`[PATCH v2 4/5]`) restructures the `old_head` branch of `setup_submodule_git_dir()` so that validation happens unconditionally after ensuring `path/.git` is a gitfile; previously, if the submodule already used a gitfile, the code validated the target immediately, but if it did not, the code absorbed the `.git` directory and skipped validation entirely. Now, after optionally calling `absorb_git_dir_into_superproject()`, the code always reads the resulting gitfile via `read_gitfile()`, calls `validate_submodule_git_dir()` on the target, and dies via `die_refusing_submodule_git_dir()` if the path is invalid. This prevents a scenario where a submodule with a nested `.git` directory triggers absorption but retains a stale or forged gitfile pointing to an invalid location. The change is marked `Suggested-by: Junio C Hamano`. Test coverage is added in `t/t7450-bad-git-dotfiles.sh` with a new case, `checkout --recurse-submodules rejects gitfile not matching submodule name after absorbing`, which constructs a nested submodule scenario: it clones a submodule, renames its git dir from `hippo` to `elephant`, points the gitfile at the renamed dir, then adds an inner clone to force the absorb path, verifying that `git checkout -f --recurse-submodules` fails with the expected "not a suffix of git dir" error and leaves the gitfile untouched. Patch 5 (`[PATCH v2 5/5]`) introduces `validate_submodule_worktree_dir()` in `submodule.c` to verify that a git dir claiming to be a linked worktree actually resides at `<common-dir>/worktrees/<id>` using `get_common_dir_noenv()`, rejecting any path with a `commondir` file located elsewhere. It modifies `setup_submodule_git_dir()` to return an `is_worktree` flag: when `get_common_dir_noenv()` detects a worktree git dir, the function validates the common dir against the submodule name instead of the worktree id, which previously caused the suffix check in `validate_submodule_git_dir()` to fail unless the worktree id happened to match the submodule name. The control flow in `submodule_move_head()` now uses this `is_worktree` flag to skip the forced-move reconnection via `connect_work_tree_and_git_dir()`, preventing Git from rewriting the submodule's `.git` file to point at the non-existent `$GIT_DIR/modules/<name>` path of the superproject, and to skip `submodule_unset_core_worktree()` during submodule removal to avoid errors when trying to modify `core.worktree` in a worktree git dir that belongs to another working tree. Test coverage is added in `t/t2405-worktree-submodule.sh` using a new `test_submodule_worktree_is_kept` helper that verifies the `.git` file contents and HEAD remain unchanged after `checkout --recurse-submodules`, covering acceptance of submodule worktrees in both legacy and `extensions.submodulePathConfig` modes, handling of a submodule worktree containing a nested `.git` directory (absorb path), and clean removal. `t/t7450-bad-git-dotfiles.sh` gains a test ensuring a forged worktree git dir (with `commondir` pointing to a wrong location) is rejected with the "is not a worktree of" error rather than triggering a `BUG()` or misleading extension advice.

Thread identity: Subject "submodule: fix crash when submodule is a linked worktree", now a five-patch series (`[PATCH v2 0/5]`) from Adrian Ratiu responding to the original bug report by Andreas Wendleder; thread type bug report / bugfix series. The latest email is `[PATCH v2 3/5]` from Adrian Ratiu, the third commit of the v2 series.

Core problem or goal: A crash (`BUG()`) occurs in `validate_submodule_legacy_git_dir()` in `submodule.c` when a submodule is itself a linked worktree of its repository and `submodule.recurse=true` is set during branch switching in the superproject. Linked-worktree gitdirs such as `.git/modules/sub/worktrees/sub1` do not end with the submodule name, violating the suffix assertion. Under `extensions.submodulePathConfig`, the same scenario produces a misleading error suggesting that the extension is not enabled. The series proposes to fix both issues.

Current status: Under review. v2 of the five-patch series was posted by Adrian Ratiu, applying on base commit `e1ec09b23c8e0deb21a0b95ac5996422277395d4`. No fix has been merged to `master`, `next`, or `seen`. v2 resolves all outstanding design questions from v1. Junio C Hamano has not yet responded to v2.

Key technical details: The v2 series comprises five commits. Patch 1 (`[PATCH v2 1/5]`) modifies `validate_submodule_legacy_git_dir()` in `submodule.c` to return a proper `error()` instead of aborting via `BUG()` when the git dir path read from a submodule's `.git` file does not end with the submodule name; it drops the contested explanatory comment entirely. The commit message traces the root cause to commit `9cf8547320` (2024-01-28), which added a caller passing a path read from disk, making the `BUG()` -- originally added in commit `a8dee3ca61` (2019-10-01) when all callers passed Git-computed paths -- reachable. The fix ensures the command dies with the standard "refusing to create/use ..." error message rather than a `BUG` abort, matching the behavior when `extensions.submodulePathConfig` is enabled. A new test in `t/t7450-bad-git-dotfiles.sh` verifies that `checkout -f --recurse-submodules` rejects a gitfile pointing to a renamed git dir (e.g., `.git/modules/elephant` instead of `.git/modules/hippo`) with the expected error message and without emitting "BUG". Patch 2 (`[PATCH v2 2/5]`) introduces a shared helper `die_refusing_submodule_git_dir()` in `submodule.c` (declared in `submodule.h`) that centralizes the "refusing to create/use" `die()` message and uses `advise()` to suggest enabling `extensions.submodulePathConfig` only when `r->repository_format_submodule_path_cfg` is false; this replaces the unconditional misleading hint in all three call sites: `submodule_move_head()`, `submodule_name_to_gitdir()`, and `clone_submodule()` in `builtin/submodule--helper.c`. Tests in `t/t7425-submodule-gitdir-path-extension.sh` assert that with the extension enabled the suggestion is absent from both the gitfile-rejection path and the config-gitdir path, while `t/t7450-bad-git-dotfiles.sh` gains an assertion that the hint appears in the default extension-disabled case. Patch 3 (`[PATCH v2 3/5]`) extracts the git dir setup logic from `submodule_move_head()` into a new private static function `setup_submodule_git_dir()` to reduce nesting; this is a pure refactoring with no intended functional change, moving the block that previously lived inside the `if (!(flags & SUBMODULE_MOVE_HEAD_DRY_RUN))` check, and credits Junio C Hamano with suggesting the extraction. The moved code handles three cases: when `old_head` exists and the submodule already uses a gitfile, it validates the git dir via `validate_submodule_git_dir()` and dies via the new helper if invalid; when `old_head` exists but the git dir needs absorbing, it calls `absorb_git_dir_into_superproject()`; and when `old_head` is NULL (new submodule), it connects the work tree and resets the index. The forced-move reconnection via `connect_work_tree_and_git_dir()` with force flag `1` is also moved into the helper. Patch 4 adds validation of the git dir immediately after `absorb_git_dir_into_superproject()` has run, closing the nested-submodule edge case where recursive absorption could leave `is_worktree` unset and trigger an unwanted reconnection. Patch 5 accepts a linked worktree as a valid submodule git dir via a simplified `validate_submodule_worktree_dir()` helper that uses `get_common_dir_noenv()` to confirm the git dir lives under `<common-dir>/worktrees/<id>` and validates the common dir against the submodule name; when a worktree is detected, `submodule_move_head()` skips rewriting the `.git` file and skips unsetting `core.worktree`. The control flow in `submodule_move_head()` now calls `setup_submodule_git_dir()` (unless in dry-run mode), which returns an `is_worktree` flag; inside that helper, after ensuring `path/.git` is a gitfile -- either because it already was one or because absorption just made it one -- the code unconditionally validates the resulting git dir and sets `is_worktree` before the forced-move block. The forced-move reconnection via `connect_work_tree_and_git_dir()` is guarded by `!is_worktree`. Additional test coverage spans `t/t2405-worktree-submodule.sh` and `t/t7425-submodule-gitdir-path-extension.sh`, including tests for recursive checkout accepting a submodule worktree in both legacy and `extensions.submodulePathConfig` modes, handling of a submodule worktree containing a nested `.git` directory (absorb path), removal behavior, and rejection of forged worktree git dirs.

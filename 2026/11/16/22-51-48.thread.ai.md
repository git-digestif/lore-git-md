Thread identity: Subject "submodule: fix crash when submodule is a linked worktree", now a three-patch series (`[PATCH 0/3]`, v1) from Adrian Ratiu responding to the original bug report by Andreas Wendleder; thread type bug report / bugfix series. The latest email is Junio C Hamano's substantive review of `[PATCH 3/3]`.

Core problem or goal: A crash (`BUG()`) occurs in `validate_submodule_legacy_git_dir()` in `submodule.c` when a submodule is itself a linked worktree of its repository and `submodule.recurse=true` is set during branch switching in the superproject. Linked-worktree gitdirs such as `.git/modules/sub/worktrees/sub1` do not end with the submodule name, violating the suffix assertion. Under `extensions.submodulePathConfig`, the same scenario produces a misleading error suggesting that the extension is not enabled. The series proposes to fix both issues.

Current status: Under review. v1 of the three-patch series was posted by Adrian Ratiu, applying on base commit `e1ec09b23c8e0deb21a0b95ac5996422277395d4`. No fix has been merged to `master`, `next`, or `seen`. Junio C Hamano has reviewed all three patches, agreeing that the fixes "Make sense". Adrian Ratiu has agreed to drop the contested explanatory comment from `[PATCH 1/3]` entirely in a forthcoming v2. Junio has now also reviewed `[PATCH 3/3]` and raised a control-flow concern about where `is_worktree` is set. A v2 has not yet been posted.

Key technical details: The series comprises three commits. Patch 1 returns a proper error via `error()` instead of aborting with `BUG()` for an unexpected git dir path in `validate_submodule_legacy_git_dir()`, preserving the existing "refusing to create/use ..." error semantics in legacy mode. Patch 2 only suggests `extensions.submodulePathConfig` when that extension is actually disabled, fixing the misleading hint in Adrian Ratiu's extension code; it moves the suggestion into a separate `advise()` call in `submodule_move_head()` that fires only when `the_repository->repository_format_submodule_path_cfg` is false, keeping the fatal `die()` message clean. Patch 3 modifies `submodule_move_head()` to accept a submodule `.git` file pointing to a linked worktree git dir. It introduces helper `validate_submodule_gitfile_dir()`, which uses `get_common_dir_noenv()` to detect linked worktrees, verifies that the git dir is located at `<common-dir>/worktrees/<id>`, rejects forged paths elsewhere with an "is not a worktree of" error, and validates the common dir against the submodule name. When a linked worktree is detected, `submodule_move_head()` skips rewriting the `.git` file to the superproject's expected modules path and skips unsetting `core.worktree`. Patch 1 adds a test to `t/t7450-bad-git-dotfiles.sh` that renames a submodule git dir, points the gitfile at it, and verifies that `git checkout -f --recurse-submodules` fails with the new error without hitting `BUG()`. Patch 2 adds a test to `t/t7425-submodule-gitdir-path-extension.sh` asserting that with `extensions.submodulePathConfig=true`, a conflicting gitdir layout produces "refusing to create/use" without mentioning the extension, and updates the t7450 test to assert that when the extension is disabled the output does contain "enabling extensions.submodulePathConfig" and no `BUG()`. Patch 3 adds coverage in `t/t2405-worktree-submodule.sh` for recursive checkout accepting a submodule worktree in both legacy and `extensions.submodulePathConfig` modes plus removal behavior, and in `t/t7450-bad-git-dotfiles.sh` for rejecting a forged worktree git dir with a commondir file. The root cause traces to commit `9cf8547320` (2024-01-28), which made `submodule_move_head()` validate gitdir paths read from disk and made the previously unreachable `BUG()` triggerable; the `BUG()` was originally added in commit `a8dee3ca61` (2019-10-01) under the assumption that callers only passed internally computed git dirs.

Open questions and loose ends: Whether linked worktrees of submodule repositories should be accepted as valid git directories remains under review in patch 3. On `[PATCH 1/3]`, Junio rejected the proposed comment "is not necessarily a bug in the caller" as historically contingent and asked for wording stating the actual invariant; Adrian agreed to remove the comment entirely in v2. Junio also noted that commit `9cf8547320` landed without the usual on-list review as part of the Git 2.39.4/2.45.1 security updates. On `[PATCH 2/3]`, two of Junio's observations remain unaddressed: he suggested using the hedged "might fix ... if it's not already enabled" wording already used in `submodule_name_to_gitdir()` instead of checking extension state explicitly, and pointed out that `clone_submodule()` in `builtin/submodule--helper.c`, another caller of `validate_submodule_git_dir()`, has the same unconditional "Enabling ... should fix this" message and may need similar treatment; he also recommended extracting the deeply nested "if not dry-run" block in `submodule_move_head()` around line 2171 into a private helper for readability. On `[PATCH 3/3]`, Junio identified a nested-submodule edge case: if linked-worktree submodule `sub` contains nested submodule `inner` whose `.git` is a directory, `submodule_uses_gitfile("sub")` returns 0 because the check is recursive, so the code runs recursive `absorb_git_dir_into_superproject()` while leaving `is_worktree` at 0; the later `if (old_head && (flags & SUBMODULE_MOVE_HEAD_FORCE) && !is_worktree)` block could therefore still be entered and potentially reconnect the linked worktree to the main git dir. He suggests restructuring so that after ensuring `path/.git` is a gitfile, either because it already was one or because `absorb_git_dir_into_superproject()` made it one, the code unconditionally calls `validate_submodule_gitfile_dir()` and sets `is_worktree` before the forced-move check. Adrian's response to this structural suggestion, the earlier patch 2 points, and a v2 remain outstanding.

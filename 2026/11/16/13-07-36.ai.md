This is the cover letter for a 12-patch series introducing **pluggable commit graphs** as part of the ongoing **ODB (object database) abstraction** effort. The series moves commit-graph storage logic into the "files" ODB backend, allowing backends to control where commit graphs are read from or written to. The goal is to enable alternative ODB implementations without requiring a full abstraction of the commit-graph data structure itself—though the author notes this could be a future step.

The series touches **11 files**, with the heaviest changes in `commit-graph.c` (massive refactoring) and `odb/source-files.c` (new backend-specific logic). Key technical details:
- **Files modified**: `commit-graph.c`/`h` (core logic), `odb.c`/`h` (plumbing for pluggability), `odb/source-files.c` (backend-specific path derivation), plus minor changes to `builtin/commit-graph.c`, `builtin/fetch.c`, `builtin/gc.c`, and a test helper.
- **New concepts**: The ODB backend now exposes hooks for commit-graph operations, and the "files" backend internalizes path-derivation logic previously scattered across the codebase.
- **Behavior changes**: Commit-graph chains are now validated by depth (not just mergeability), and incomplete chains are explicitly marked. The `write_commit_graph_file()` function gains a common exit path.

The series is **built on `ps/commit-graph-write-refactor`**, a prerequisite refactor to modernize function names. No user-facing features are introduced yet, but this lays groundwork for future ODB backends (e.g., reftable, custom storage systems). The commit messages suggest the changes are mechanical but invasive, with significant code movement and cleanup.

**Likely points of discussion**:
- Whether the pluggable design is sufficiently flexible for future backends (e.g., could a backend avoid the commit-graph data structure entirely?).
- Performance implications of moving path logic into the backend (e.g., will this complicate caching or introduce redundant I/O?).
- The decision to retain the commit-graph data structure rather than abstracting it further—this might draw feedback from contributors who favor a more radical redesign.

**Quality signals**: The series is well-structured (12 patches with clear scopes), authored by Patrick Steinhardt (a prolific ODB/refactor contributor), and includes a thorough cover letter. The lack of new tests suggests this is infrastructure-only for now, but follow-up patches may add them. The changes align with the project’s long-term goal of ODB abstraction, so they’re likely to receive serious review despite the churn.

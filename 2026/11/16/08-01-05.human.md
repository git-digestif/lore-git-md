This is the review feedback for the second iteration of the standalone toggle patch that makes `--follow` rename-following in non-linear history opt-in by default. The patch, now queued by Junio C Hamano, is the project's settled resolution to the `--follow` performance regression blocking GitLab's deployment.

Patrick Steinhardt's review is **substantive but narrowly focused on implementation details**, confirming the patch is nearly ready to merge. He accepts Miklos Vajna's reasoning for checking both `follow_renames` and `follow_merges` flags (defensive coding against future changes like those in `builtin/blame.c`) and approves the improved error handling and documentation. The only remaining action items are minor: Miklos should reply to review feedback on the original thread (not in the v2 patch email) for better traceability, but this is a process note, not a technical blocker.

The patch itself is **mechanically sound and aligns with the project's policy decision** to disable rename-following in merges by default. It adds a new config value (`log.follow=merges`) and flag (`--follow=merges`), both disabled by default, and includes a performance warning in the documentation to help users make informed choices. Patrick's feedback on using `git_parse_maybe_bool()` for graceful error handling and clarifying the documentation was addressed in v2, and he now considers the patch ready. The toggle's design (flag vs. config option) remains unsettled, but the patch supports both, and Patrick's prior preference for the flag is likely to prevail.

This patch is **decoupled from the v5 series** (which fixes correctness bugs and optimizes `--follow` for merges) and will land first to unblock GitLab's deployment. The v5 series can proceed independently, as the toggle preserves its correctness fixes while mitigating the performance cost.

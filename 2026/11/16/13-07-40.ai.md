This is the fourth patch in Patrick Steinhardt’s 12-patch series introducing **pluggable commit graphs** for the ODB abstraction effort. It refactors the split commit-graph merge strategy to use **depth-based layer selection** instead of directory path comparisons, preparing the logic for backend-specific control over where commit graphs are stored.

The patch modifies `commit-graph.c` to replace the existing checks—whether a layer is "local" (same object directory) or "split" (a chainable layer)—with two new counters in the `write_commit_graph_context` struct: `mergeable_layers` and `chainable_layers`. These counters track how many of the topmost layers in the commit-graph chain can be merged or chained, respectively. The backend (or future backend-specific logic) will determine these values, while the core merge strategy now simply enforces them by depth. This decouples the merge logic from filesystem-specific assumptions, a key step toward pluggability.

The change is **internal-only** and does not alter on-disk format or user-facing behavior. It removes the need for directory path comparisons in `split_graph_merge_strategy()`, replacing them with a simple depth check (`depth >= ctx->mergeable_layers` or `depth >= ctx->chainable_layers`). The patch also simplifies the logic for handling non-local base graphs, eliminating a special case that previously required filename comparisons.

**Key technical details**:
- **New fields**: `mergeable_layers` and `chainable_layers` in `struct write_commit_graph_context`.
- **Behavior**: The merge strategy now relies on depth thresholds rather than directory paths to decide which layers to merge or chain.
- **Files touched**: Only `commit-graph.c` (40 insertions, 11 deletions).
- **Prerequisites**: Depends on the earlier patches in the series (e.g., the refactored `split_graph_merge_strategy` from patch 1).

**Why this matters for the series**: This patch is a critical enabler for backend-specific commit-graph storage. By abstracting away the "local vs. non-local" distinction, it allows future ODB backends (e.g., reftable, custom storage systems) to define their own rules for layer mergeability and chainability without modifying the core merge logic. The design assumes that backends will set `mergeable_layers` and `chainable_layers` appropriately during initialization, which is addressed in later patches.

**Likely discussion points**:
- **Flexibility**: Does this depth-based approach sufficiently generalize for all possible backends, or will some need more nuanced control (e.g., per-layer mergeability flags)?
- **Performance**: The patch adds a loop to count layers during initialization, but this is likely negligible compared to the cost of I/O. No impact on runtime behavior.
- **Clarity**: The new counters (`mergeable_layers`, `chainable_layers`) are set in a separate loop from where they’re used, which might make the code harder to follow. Reviewers may ask for comments or restructuring to improve readability.

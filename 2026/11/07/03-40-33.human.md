This is the second patch in a five-part series improving Git’s HTTP transport resilience. It introduces exponential backoff for retries when servers return HTTP 429 (Too Many Requests) without a Retry-After header.

The patch modifies `http.c` to double the configured `http.retryAfter` delay on each subsequent retry (e.g., 1s → 2s → 4s), clamping the delay at `http.maxRetryTime`. The first retry remains fast, while later attempts give the server more time to recover. This matches curl’s `--retry` behavior but uses Git’s existing `http.retryAfter` as the initial delay (defaulting to 0 for immediate retries when unconfigured). When a Retry-After header is present, the server-provided delay still takes precedence.

Documentation in `Documentation/config/http.adoc` is updated to clarify that `http.retryAfter` is now the *initial* delay and that subsequent retries double this value, capped at `http.maxRetryTime`. The test suite (`t/t5584-http-429-retry.sh`) adds three new tests verifying the doubling behavior, clamping, and Retry-After header override.

The implementation is clean and well-motivated: it reuses the existing `rate_limit_retries` counter to track attempt count, avoiding new variables, and the documentation changes clearly explain the new behavior. The patch is part of a larger effort to improve Git’s resilience when interacting with rate-limited or overloaded servers, and it addresses a real-world gap in the current retry logic. The series as a whole is under review and appears ready for integration.

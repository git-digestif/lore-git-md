This is the third patch in a five-patch series improving Git’s HTTP transport resilience. It introduces `http.retryStatusCodes`, a new configuration option that lets users specify which HTTP status codes (400–599) should trigger retries, defaulting to 429 (Too Many Requests). The patch also adds support for the `GIT_HTTP_RETRY_STATUS_CODES` environment variable and URL-specific overrides.

The motivation is clear: Git’s existing retry logic hardcodes 429, but real-world hosting backends and reverse proxies often return transient 5xx errors (502, 503, 504) during load shedding or upstream failures. Because 5xx responses aren’t universally transient, the patch keeps 429 as the default while allowing users to opt into retrying other codes. The implementation is clean: it moves the status-code check into a new helper function (`is_retryable_http_code()`), updates warning messages to show numeric codes (e.g., "HTTP 502") for non-429 responses, and preserves the existing "rate limited" phrasing for 429.

Test coverage is thorough, with five new tests in `t/t5584-http-429-retry.sh` verifying 5xx retries, Retry-After header handling for 503, exhausted retry reporting, and environment/URL-specific config overrides. The patch also updates `t/lib-httpd/http-429.sh` to simulate 502/503/504 responses. Documentation in `Documentation/config/http.adoc` is expanded to explain the new option and its interaction with `http.maxRetries`, `http.retryAfter`, and `http.maxRetryTime`.

This is a well-crafted feature addition that addresses a real gap in Git’s HTTP error handling. The opt-in design for 5xx retries avoids controversy, and the implementation is straightforward. The patch is ready for integration, with no unresolved technical feedback. If you work with Git hosting backends or reverse proxies, this is worth reviewing—especially if you’ve encountered transient 5xx errors during fetch/clone operations.

This is the first patch in a five-part series improving Git’s HTTP transport resilience. It fixes two bugs in the existing 429-rate-limit retry logic introduced in commit 640657ffd0 (2026-03-17).

The first bug is an off-by-one retry counter: the pre-decrement loop condition (`--rate_limit_retries`) means that `http.maxRetries=1` performs zero retries instead of one, and a 429 after a 401 re-authentication can wrap the counter from 0 to -1 (truthy in C). The fix changes the loop condition to `http_max_retries > 0 && rate_limit_retries-- > 0` and moves the zero-retry check after the loop, handling both initial 429s and 429s after re-auth without logging spurious “retries-exhausted” messages.

The second bug is a race in Retry-After header parsing: `CURLINFO_RETRY_AFTER` is queried in `http_request()` after `handle_curl_result()` has already logged the uninitialized `results->retry_after` (-1) to Trace2. The fix moves the extraction into `finish_active_slot()`, initializing `slot->results->retry_after = -1` first so that both `handle_curl_result()` and callers observe the parsed value.

The patch touches `http.c`, the test helper `t/lib-httpd/http-429.sh` (now configurable for 2 or 3 failures), and adds three new tests in `t/t5584-http-429-retry.sh` that verify the retry count, failure threshold, and Trace2 logging. The changes are mechanical and well-motivated, addressing clear correctness issues without altering the intended behavior. Junio’s earlier review feedback on the loop guard clause and Trace2 logging has been incorporated.

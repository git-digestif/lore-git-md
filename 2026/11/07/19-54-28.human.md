This is a bugfix patch for the `git apply` subsystem, addressing the crash reported by Gingrspacecadet in `git apply --check` when processing patches with malformed headers. The issue is a long-standing logic error in `apply.c` where stale filename fields from an unused `diff --git` line cause an assertion failure (`patch->is_new <= 0`) in `check_preimage()`.

The patch clears the `old_name` and `new_name` fields when `parse_git_diff_header()` stops parsing after the `diff --git` line (e.g., due to a blank line or indented header). This prevents the apply machinery from retaining incorrect filenames, which previously led to crashes for new-file patches, reversed deletions, or empty sections. The fix is minimal and targeted, preserving the existing behavior for valid patches while handling edge cases gracefully.

The test coverage is thorough, adding five new test cases in `t/t4133-apply-filenames.sh` to verify the fix for:
- Blank lines after `diff --git`
- Indented `new file mode` lines
- Reversed deletions with blank lines
- Empty `diff --git` sections
- Path relativity in subdirectories

The patch is well-motivated and clearly explains the root cause (stale names from unused headers) and the solution (freeing them early). It’s based on `maint` (v2.56.0) but merges cleanly with `master`, `next`, and `seen`. The crash affects released versions (confirmed in Git 2.43), so this fix is worth attention. No controversies or open questions remain—this looks like a straightforward, correct fix for a real bug.

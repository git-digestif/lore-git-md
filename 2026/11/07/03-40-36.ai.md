This is the final patch (5/5) in a well-motivated series improving Git’s HTTP transport resilience. It sets the default value of `http.retryAfter` to **10 seconds**, formalizing the compromise reached in earlier discussion between server protection (brian m. carlson’s priority) and interactive usability (Ravi Mistry’s concern). The patch updates documentation, the config machinery in `http.c`, and test expectations in `t/t5584-http-429-retry.sh` to reflect the new default.

The change ensures that when a server returns HTTP 429 (or another configured status code) without a Retry-After header, Git now waits 10 seconds before the first retry, then doubles the delay on each subsequent attempt (20s, 40s, …), capped at `http.maxRetryTime`. This prevents tight retry loops that could hammer overloaded servers while keeping interactive commands responsive. The patch also cleans up the error message and documentation by removing the word "configured" (since the default can now exceed `http.maxRetryTime` even when not explicitly set) and updates a test to verify that past Retry-After HTTP-dates fall back to the 10-second default rather than retrying immediately.

The test suite expands to cover the new default behavior, including a case where `http.retryAfter` (10s) exceeds a lowered `http.maxRetryTime` (9s), triggering an immediate failure with a clear error message. The patch is technically sound, with no unresolved feedback, and aligns with the series’ goal of improving resilience for real-world scenarios like transient 5xx errors from load balancers or rate-limiting under high concurrency. The series as a whole appears ready for integration.

This is the third patch in a five-patch series improving Git’s HTTP transport resilience. It introduces the `http.retryStatusCodes` configuration option, allowing users to specify which HTTP status codes (400–599) should trigger retries, defaulting to 429 (Too Many Requests). The patch also adds support for the `GIT_HTTP_RETRY_STATUS_CODES` environment variable and updates documentation to reflect the new behavior.

The core change replaces the hardcoded 429 check with a configurable list, enabling retries for transient 5xx errors (e.g., 502 Bad Gateway, 503 Service Unavailable) when explicitly configured. The `is_retryable_http_code()` helper parses the comma- or whitespace-separated list, validating codes in the 400–599 range. Warning messages now distinguish between 429 ("rate limited") and other status codes (e.g., "HTTP 502"), improving clarity. The patch also propagates the HTTP status code through `struct http_get_options` to support this distinction.

Test coverage is thorough, with five new tests in `t/t5584-http-429-retry.sh` verifying:
- Default behavior (no retries for 5xx by default)
- Configurable retries for 502/503/504
- Retry-After header support for 503
- Error reporting for exhausted 5xx retries (avoids "rate limited" phrasing)
- Environment variable and URL-specific config overrides

The patch is well-motivated, addressing real-world scenarios where load balancers or hosting backends return transient 5xx errors. The opt-in design (defaulting to 429) avoids controversy, and the implementation is clean, with minimal changes to core logic. The only minor loose end is documentation formatting consistency, which is cosmetic and unrelated to functionality. This patch is technically complete and ready for integration, with no unresolved feedback from prior reviews.

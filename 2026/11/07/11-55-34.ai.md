This is a feature patch series introducing the `%gb` format placeholder for `git log -g` and `git reflog`, allowing users to see which branch each reflog entry was recorded on. The v5 series is a focused update addressing all outstanding correctness issues identified in prior reviews, particularly Phillip Wood’s feedback about detached HEAD labeling and rebase checkout parsing.

The series now consists of two patches. The first renames hard-coded reflog message strings (e.g., `"checkout: moving from "`, `"Branch: renamed "`) into `#define` constants in `reflog.h`, explicitly tying the refactoring to the `%gb` feature. The second patch implements the `%gb` placeholder itself, which parses reflog messages to determine the branch context for each entry. Key improvements in v5 include: (1) correctly labeling detached HEAD entries with the commit where HEAD was originally detached (or the commit a detached rebase ended on), (2) fixing rebase checkout parsing to avoid mislabeling remote branches as local and to ignore commit subjects starting with "checkout", and (3) adding comprehensive test coverage for edge cases, including Phillip Wood’s failing test case from the v4 review.

The implementation touches 12 files, including core reflog-walking logic (`reflog-walk.c`, `revision.c`), built-in commands (`builtin/rebase.c`, `builtin/checkout.c`, `builtin/branch.c`), and documentation. The test script (`t/t1414-reflog-walk.sh`) has grown to 229 lines, validating edge cases like rebases of detached HEADs, fast-forward and aborted rebases, branch renames, and custom `GIT_REFLOG_ACTION` values. The `%gb` placeholder is additive and does not alter default behavior, reducing regression risk.

The series directly addresses the usability pain points described in the original mailing-list discussion, such as tracking reset points during rebasing and branch history across renames. It abandons earlier proposals for dedicated flags (`--operations`, `--historical-branch`) in favor of a composable format specifier that aligns with Git’s decoration system. All prior feedback has been addressed except for Junio C Hamano’s broader architectural concerns about reflog message design (e.g., translatability), which remain unresolved but do not block this targeted improvement.

The patch quality is high: commit messages are clear, the code is well-structured, and the test coverage is thorough. The series is ready for maintainer review, with no known correctness issues remaining. Junio’s input on v5 is the next step, particularly regarding the unresolved architectural questions. The broader debate about changing `git reflog`’s default behavior (e.g., operating on the current branch) or refactoring multi-step commands to work on detached HEAD remains untouched by this series. Harald Nordgren’s separate proposal to make `git reflog @{0}` the default output is also orthogonal and untriaged.

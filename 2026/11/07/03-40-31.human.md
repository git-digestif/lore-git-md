This is the v3 cover letter for a five-patch series improving Git’s HTTP transport resilience. The series targets four specific gaps in error handling: an off-by-one retry counter, missing exponential backoff when Retry-After headers are absent, inability to retry transient 5xx errors, and lack of retries for HTTP POST requests (which handle data transfers during fetch/clone and partial clone).

The v3 iteration adds a fifth patch that changes the default `http.retryAfter` value from 0 to 10 seconds, resolving the last open discussion point from earlier rounds. This compromise—proposed by Junio C Hamano and brian m. carlson—balances server protection (avoiding immediate retries) with interactive usability (keeping the initial delay short enough for human workflows). The backoff now doubles on each retry (10s, 20s, 40s, ...) while clamping at `http.maxRetryTime`.

The series is technically complete, with all substantive feedback incorporated. Patches 1–4 are unchanged from v2; only the new patch 5/5 adjusts the default. The code touches `http.c`, `remote-curl.c`, documentation, and tests, introducing new config options (`http.retryStatusCodes`, defaulting to "429") and helper functions (`is_retryable_http_code()`, `http_retry_wait()`). Test coverage is thorough, with a new script (`t/t5584-http-429-retry.sh`) and expanded helper (`t/lib-httpd/http-429.sh`) verifying retry counts, backoff timing, 5xx retries, and POST request behavior.

The motivation is clear: real-world issues with hosting backends and reverse proxies under high concurrency. The opt-in design for 5xx retries (via `http.retryStatusCodes`) sidesteps controversy, and the exponential backoff aligns with curl’s semantics. The series looks well-crafted, with clean commit messages, good test coverage, and no obvious red flags. It should be uncontroversial for environments that want to opt into more aggressive retry behavior.

This is the fourth patch in a five-patch series improving Git’s HTTP transport resilience. It extends retry logic to HTTP POST requests, which carry the actual data during fetch/clone and partial-clone blob downloads. The patch extracts shared retry timing logic into a new helper, `http_retry_wait()`, and applies it to both `probe_rpc()` and `post_rpc()`. It also defers error reporting until retries are exhausted and ensures the "Content-Encoding: gzip" header is re-attached when retrying compressed requests.

The change is well-motivated: POST requests are just as likely as GETs to encounter transient errors (429, 502, etc.), and retrying them is critical for large or partial clones. The implementation is clean, moving retry timing logic into a shared helper and updating the RPC code paths to use it. Test coverage is thorough, with four new tests in `t/t5584-http-429-retry.sh` verifying POST retries for 429 and 502 errors, partial-clone blob fetches surviving 502s, and gzipped POST header preservation.

This patch looks ready for integration. It addresses a real gap in Git’s HTTP resilience, the code changes are focused and well-explained, and the test coverage is comprehensive. The only minor nit is the cosmetic documentation formatting noted earlier in the series, but that’s unrelated to this patch’s functionality. If the rest of the series lands, this should too.

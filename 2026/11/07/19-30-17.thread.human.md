Jelle van der Waa’s RFC patch series proposing `--verbose` support for `git history reword` has sparked a lively debate about both user interface design and technical implementation. The series adds diff display to the reword editor, mirroring `git commit --amend --verbose`, and includes a preliminary cleanup patch removing a redundant `strbuf_stripspace()` call. While the implementation itself is straightforward and well-tested, the discussion has expanded into two major unresolved questions: whether diff display should be opt-in (via a flag) or opt-out (default behavior), and whether the output format must be generalizable to all `git history` subcommands (`split`, `squash`, `fixup`, etc.).

Six distinct positions on opt-in vs. opt-out remain in play. Jelle initially proposed an opt-in `--verbose` flag, omitting `commit.verbose` config support for now but open to adding it later. Phillip Wood initially argued for immediate config support and later shifted toward making diff display the default, citing Git’s experimental status as justification. Karthik Nayak also favors default behavior, omitting the option entirely, while D. Ben Knoble and Patrick Steinhardt conditionally accept default behavior only if it can be disabled via configuration. The debate remains unresolved, with no clear consensus on whether to prioritize discoverability (opt-out) or user control (opt-in).

The discussion took a technical turn when Patrick Steinhardt introduced a new constraint: the output format must be reusable across all `git history` subcommands and accommodate future use cases such as changes to commit layout, order, messages, and multiple references. He suggested `git range-diff`’s structured format as a model, implying a multi-commit summary rather than a simple unified diff. D. Ben Knoble acknowledged the value of both approaches—`git range-diff`’s generality and the lightweight unified diff—but did not take a firm position on which should win. The tension between these two goals—immediate usability and long-term flexibility—now sits at the heart of the thread, with no clear path forward yet. The author has not yet responded to this constraint, leaving the generalizability requirement unaddressed.

Subject: [RFC PATCH 0/2] git history: add --verbose support for reword

Core problem or goal
Add diff display support to `git history` subcommands (`reword`, `split`, `fixup`) to show the full diff while editing the commit message, mirroring the behavior of `git commit --amend --verbose`. The feature is now **default behavior** (opt-out) for `reword`, `split`, and `fixup`, respecting the existing `commit.verbose` configuration for consistency with `git commit`. The series also removes a redundant `strbuf_stripspace()` call in `builtin/history.c` as preliminary cleanup. The design must be generalizable to all `git history` subcommands to avoid inconsistent editor templates, with a new constraint: the **output format** must accommodate future use cases such as changes to commit layout, commit order, commit messages, and updates to multiple references. Patrick Steinhardt has clarified that "format" refers specifically to the **editor template presentation** (how diffs and other information are rendered in the editor buffer), not merely the option name, and suggests `git range-diff`’s structured, multi-commit format as a model.

Current status
Under review (RFC). The author has announced a pivot: the next version (v2) will drop the `--verbose` option entirely and make diff display the default behavior for `reword`, `split`, and `fixup`, controlled by the existing `commit.verbose` configuration. No maintainer decisions yet. The discussion remains focused on three unresolved constraints: (a) whether the output format must prioritize a lightweight unified diff (mirroring `git commit --verbose`) or a structured, multi-commit format (modeled on `git range-diff`), (b) whether the structured format requirement will necessitate a redesign of the current implementation, and (c) whether a CLI opt-out mechanism (e.g., `--no-verbose` or `--no-diff`) is required to support scripted workflows. The author has not yet responded to Patrick Steinhardt’s output format constraint or the broader tension between the two design goals.

Open questions and loose ends
- **Output format**: The thread faces a fundamental tension between two design goals: (a) a lightweight, familiar unified diff (mirroring `git commit --verbose`) for immediate use, and (b) a structured, multi-commit format (modeled on `git range-diff`) to accommodate future subcommands and complex rewrites. Patrick Steinhardt’s requirement for generalizability implies that the current implementation may need to be redesigned. The unresolved question is whether these two goals can coexist, or if the lightweight unified diff must be abandoned in favor of the structured format. The author has not yet responded to this constraint or proposed a path forward.
- Should the diff-generation logic reuse `wt-status.c`’s existing logic (Phillip Wood’s suggestion) to handle `status.relativePaths`, `status.renames`, and `status.renameLimit` settings?
- Are there additional edge cases in the diff display that need handling (e.g., binary files, submodules)?
- Should the test suite be refactored to reduce redundancy (e.g., fold "no diff without `commit.verbose`" and "bare repository" tests into existing coverage, extend an existing merge test rather than create a new repository)?
- **Scripted editing**: Phillip Wood’s concern about diff display interfering with automated edits remains unresolved. D. Ben Knoble and Patrick Steinhardt reinforce the need for a CLI opt-out mechanism (e.g., `--no-verbose` or `--no-diff`) to ensure deterministic behavior in scripted workflows. The unresolved question is whether this mechanism should be introduced in v2 or deferred to a future patch.
- Will the author follow up with patches for `squash` and other subcommands, or will the default behavior make this unnecessary?
- Is the merge-commit diff behavior (first-parent only) the correct default?

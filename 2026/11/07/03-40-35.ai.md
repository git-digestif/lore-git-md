This is the fourth patch in a five-patch series improving Git’s HTTP transport resilience. It extends retry logic to HTTP POST requests, which are used for actual data transfer during fetch/clone and partial-clone blob downloads. The patch extracts retry timing logic into a shared `http_retry_wait()` helper, applies it to both `probe_rpc()` and `post_rpc()`, defers error reporting until retries are exhausted, and ensures the "Content-Encoding: gzip" header is re-attached when retrying compressed requests.

The changes touch `http.c`, `http.h`, `remote-curl.c`, and the test infrastructure (`t/lib-httpd/http-429.sh` and `t/t5584-http-429-retry.sh`). The new `http_retry_wait()` function consolidates retry timing logic, while `report_rpc_error()` centralizes error reporting. The test suite adds four new tests covering POST retries for 429/502 responses, partial-clone blob fetches surviving 502s, and gzipped POST header preservation.

This patch is well-motivated: POST requests carry the bulk of Git’s data transfer, and transient errors (e.g., 502 from load balancers) are common in production. The implementation is clean, with clear separation of concerns and thorough test coverage. The only behavioral change is that POST requests now retry transient errors, matching the existing GET request behavior. The series as a whole is technically complete and awaits final review.

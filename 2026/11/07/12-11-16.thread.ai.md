Subject: [PATCH] split-index: fix corruption with skipHash and splitIndex enabled
Series version: standalone patch (no prior versions)
Originating author: Andy Koppe
Thread type: bug report / bugfix

Core problem or goal
A critical bug in Git’s index subsystem causes silent corruption (null OIDs, missing entries) and crashes (`BUG: wt-status.c:585`) when both `core.splitIndex` and `index.skipHash` are enabled. The root cause is that `write_shared_index()` names the shared index file after its trailing checksum, which is written as zeros when `index.skipHash` is enabled, resulting in a filename of all zeros. The split index then records a null base OID, and `read_index_from()` treats this as "no shared index," causing the entries in the shared index to be silently discarded.

Current status
Under review; root cause identified. Tanga Joris is actively working on a fix. Severity remains high: index corruption and crashes block users of split-index or skipHash optimizations (e.g., large repos with `feature.manyFiles`). Andy Koppe has confirmed they are not working on a fix.

Key technical details
- **Files touched**: `split-index.c` (filename generation), `read-cache.c` (index reading logic), `wt-status.c` (crash site).
- **New/renamed symbols**: `write_shared_index()` (root cause function), `read_index_from()` (discards shared index entries).
- **Config keys**: `core.splitIndex`, `index.skipHash`, `feature.manyFiles`.
- **Error message**: `BUG: wt-status.c:585: multiple renames on the same target? how!`.
- **Reproduction**: new repo + `core.splitIndex=true` + `index.skipHash=true` + file operations → silent data loss (null OIDs in shared index), crash during `git status`.
- **Platform**: confirmed on Linux with Git v2.56.0.
- **On-disk format**: shared index filename derived from trailing checksum (zeros when `index.skipHash` is enabled).

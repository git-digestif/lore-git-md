This thread is about a critical bug in Git’s index subsystem that causes silent corruption and crashes when both `core.splitIndex` and `index.skipHash` are enabled. The issue was reported by Andy Koppe, who provided reproduction steps showing that the shared index file is incorrectly named with all zeros when `index.skipHash` is enabled, leading to null OIDs and data loss. Tanga Joris identified the root cause—`write_shared_index()` derives the filename from the trailing checksum, which is zeroed out when `index.skipHash` is active—and has now submitted a fix.

The patch ensures the shared index always includes its hash, regardless of `index.skipHash`, while preserving the performance benefit of skipping the hash in the main index. It modifies `read-cache.c` to add a `skip_hash` parameter to `do_write_index()` and updates `write_shared_index()` to enforce hash inclusion for shared indexes. Two new tests in `t/t1700-split-index.sh` verify the fix: one checks that `index.skipHash` doesn’t apply to shared indexes, and another ensures the first entry in split mode isn’t lost. The fix is narrowly scoped and well-tested, addressing the high-severity issue without broader changes.

The patch is under review, with no maintainer response or integration branch status yet. The regression was introduced in `ee1f0c242e` (2023-01-06), and the fix targets users of split-index or skipHash optimizations, particularly in large repositories with `feature.manyFiles`. Tanga Joris is actively driving the fix, while Andy Koppe has confirmed they are not working on it. No other participants have weighed in so far.

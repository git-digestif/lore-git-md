This is a bugfix patch targeting the `apply.c` subsystem, addressing the crash in `git apply --check` reported by Gingrspacecadet. The patch is the first of a two-part series (1/2) and focuses on a specific parsing edge case in Git’s diff header handling.

The issue occurs when a `diff --git` line is followed by a non-header line (e.g., a blank line or indented `new file mode`), causing `parse_git_diff_header()` to stop early while `find_header()` continues searching. This leaves stale `old_name` and `new_name` values in the patch struct, triggering an assertion failure (`patch->is_new <= 0`) in `check_preimage()`. The patch fixes this by freeing the stale names when the `diff --git` line is unused, allowing the parser to correctly handle traditional patches that follow.

The fix is well-motivated and includes thorough test coverage in `t/t4133-apply-filenames.sh`, covering three scenarios: blank lines after `diff --git`, indented `new file mode` lines, and empty diff sections. The tests verify both `--check` and actual application, including reverse application of deletions. The commit message clearly explains the root cause, the fix, and the behavior changes, referencing the original bug report and related commits.

This is a long-standing bug (dating back to 2005) that affects released versions (confirmed in Git 2.43), so the patch is based on `maint` but merges cleanly with `master`, `next`, and `seen`. The fix is narrowly scoped to the parsing logic and does not appear to introduce new edge cases. The second patch in the series (not shown here) addresses a related but distinct header-ordering issue (`---` before `new file mode`).

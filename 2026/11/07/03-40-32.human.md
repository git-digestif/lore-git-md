This is the first patch in a five-part series improving Git’s HTTP transport resilience. It fixes two bugs in the existing 429-rate-limit retry logic introduced in commit 640657ffd0 (2026-03-17).

The first bug is an off-by-one in the retry counter: the pre-decrement loop condition (`--rate_limit_retries`) meant that `http.maxRetries=1` performed zero retries instead of one, and an initial 401 followed by a 429 could wrap the counter from 0 to -1, causing unintended retries. The fix changes the loop to check `http_max_retries > 0 && rate_limit_retries-- > 0` and moves the zero-retry check after the loop, making the behavior uniform for both initial 429s and 429s after re-authentication.

The second bug is a race in Retry-After header parsing: `CURLINFO_RETRY_AFTER` was queried after `handle_curl_result()` had already logged the uninitialized value (`-1`) to Trace2. The fix moves the extraction into `finish_active_slot()`, initializing `slot->results->retry_after = -1` first so that both the logging and caller see the correct value.

The patch touches `http.c`, the test helper `t/lib-httpd/http-429.sh` (now configurable for 2 or 3 failures), and adds three new tests in `t/t5584-http-429-retry.sh` covering retry count, failure threshold, and Trace2 logging. The changes are mechanical and well-tested; the commit message clearly explains the bugs and fixes. This patch is a prerequisite for the rest of the series and looks ready for integration.

This is the second patch in the v3 series improving Git’s HTTP transport resilience. It introduces exponential backoff for retries when servers return HTTP 429 (Too Many Requests) without a Retry-After header. The patch modifies `http.c` and updates documentation to reflect that `http.retryAfter` is now the *initial* delay (defaulting to 10 seconds as established in the series compromise), which doubles on each subsequent retry (10s, 20s, 40s, ...) while clamping at `http.maxRetryTime` (default 300s). The implementation reuses the existing `rate_limit_retries` counter to track attempt count, avoiding a new variable, and preserves the server-provided Retry-After header as the authoritative delay when present.

The patch is well-motivated: without exponential backoff, short `http.retryAfter` values (e.g., 1s) exhaust retries too quickly, while long values make even brief glitches unnecessarily slow. The doubling behavior matches curl’s `--retry` semantics, though with a longer initial delay (10s vs. curl’s 1s). The clamping logic ensures delays never exceed `http.maxRetryTime`, and the test coverage verifies doubling, clamping, and Retry-After header precedence. The commit message clearly explains the 1-based attempt count and the rationale for reusing `rate_limit_retries`.

Key symbols introduced: the `attempt` parameter in `handle_rate_limit_retry()`, and the doubling logic (`http.retryAfter * 2^(attempt - 1)`). The documentation updates clarify that `http.retryAfter` is now the initial delay and describe the exponential behavior. The patch touches no on-disk formats and maintains backward compatibility (the default `http.retryAfter=0` still triggers immediate retries unless configured otherwise). The test suite (`t/t5584-http-429-retry.sh`) adds three new tests covering doubling, clamping, and Retry-After header override.

This patch is part of a larger effort to address gaps in Git’s HTTP error handling, and it directly addresses feedback from Junio C Hamano in earlier iterations. The implementation is clean, the documentation is thorough, and the test coverage is comprehensive. The only remaining loose end is minor documentation formatting (variable name markup), which is cosmetic and unrelated to functionality. The patch appears ready for integration.

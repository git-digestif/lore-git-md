This is the second patch in Tanga Joris's two-part bugfix series addressing crashes in `git apply --check` (and related workflows) when processing patches with malformed headers. The first patch (1/2) fixed a parsing edge case where stale `old_name` and `new_name` values in the patch struct caused an assertion failure. This patch (2/2) tackles a related but distinct issue: patches where the `---` or `+++` lines appear *before* the `new file mode` or `deleted file mode` lines, respectively, leading to a new file with an old name (or a deleted file with a new name) and triggering the same assertion in `check_preimage()`.

The fix follows the precedent set by d70e9c5c8c (2017), which made Git reject other mutually exclusive header lines rather than crashing. After parsing the header, the patch now explicitly rejects a new file that has an old name (`patch->is_new > 0 && patch->old_name`) or a deleted file that has a new name (`patch->is_delete > 0 && patch->new_name`). The error messages are clear and actionable, distinguishing between file-based and line-based input sources. The test coverage in `t/t4133-apply-filenames.sh` is thorough, covering both scenarios (`--- /dev/null` or `--- a/f` before `new file mode`, and `+++ /dev/null` before `deleted file mode`) and verifying that the rejection applies to both forward and reverse (`-R`) application.

The patch is narrowly scoped and well-motivated. It preserves compatibility with patches generated by Git itself (which always place `new file mode` or `deleted file mode` before the `---`/`+++` lines) while rejecting malformed patches that would otherwise crash. The author notes an alternative design (accepting `--- /dev/null` before `new file mode` as valid, since `/dev/null` implies no old file), but the chosen approach aligns with existing error-handling patterns in the codebase. The fix is based on `maint` and merges cleanly with `master`, `next`, and `seen`.

This patch, combined with 1/2, completes the fix for the original bug report. The series is now ready for review by maintainers familiar with the apply subsystem, particularly to validate the error messages, test coverage, and edge-case handling. The crash is deterministic and the reproducer is clear, so this should be straightforward to review. The patch looks well-crafted and addresses a real problem without introducing new edge cases.

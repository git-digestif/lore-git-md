This is a **bugfix** targeting the index subsystem, specifically the interaction between `core.splitIndex` and `index.skipHash`. Tanga Joris has identified the root cause of the corruption and crash reported by Andy Koppe: when `index.skipHash` is enabled, `write_shared_index()` names the shared index file after a trailing checksum that is written as all zeros, resulting in a filename like `sharedindex.0000000000000000000000000000000000000000`. The split index then records a null base OID, and `read_index_from()` treats this as "no shared index," causing the entries stored in the shared index to be silently lost.

Tanga confirms they can reproduce the issue on the current `master` (commit `fb255012ac`) and is working on a fix. The explanation is clear and actionable, pinpointing the exact mechanism of the corruption. This moves the thread from a bug report to a concrete diagnosis and impending patch. The severity remains high—index corruption and crashes are critical issues for users relying on split-index or skipHash optimizations, such as large repositories with `feature.manyFiles` enabled.

No prior patch or review feedback exists yet, but the diagnosis suggests the fix will likely involve ensuring the shared index filename or base OID is correctly handled when `index.skipHash` is enabled. The thread is now focused on resolving the issue rather than reproducing it.

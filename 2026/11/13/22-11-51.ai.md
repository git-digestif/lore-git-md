This is the second patch in Adithya Chakilam's two-patch feature series introducing `--filter-to-loose=<dir>` for `git repack`. It extends the functionality of the first patch to ensure that loose objects excluded by the filter are also copied to the destination directory, completing the feature's goal of providing a full set of filtered-out objects in loose form.

The patch adds logic to collect loose objects from the source repository, filter them using the same `--filter` specification, and copy the excluded objects to the destination directory. Objects already present in the destination are not rewritten, and with `-d`, the source copies are removed after successful copying. The implementation is careful to handle edge cases: it checks for existing objects in the destination, creates necessary leading directories, and uses a temporary file during copying to avoid corruption if the operation fails. The patch also updates the documentation to clarify that loose objects are included in the transfer.

The code touches `repack-filtered.c` and `repack.h`, introducing two new functions: `move_loose_filtered_objects()` and `remove_moved_loose_objects()`. The former handles the collection, filtering, and copying of loose objects, while the latter removes the source copies when `-d` is specified. The patch includes thorough test coverage in `t/t7700-repack.sh`, verifying that loose objects are copied correctly, that `-d` removes the source copies, that existing destination objects are left untouched, and that failures during copying leave the source repository intact.

This patch addresses the gap left by the first patch, which only handled objects already in packs. The design is consistent with the first patch, using the same filtering logic and error-handling patterns. The implementation appears robust, with clear commit messages and well-structured code. The feature now fully delivers on its promise: users can rely on `--filter-to-loose` to provide a complete set of filtered-out objects in loose form, regardless of whether those objects were originally loose or packed. Whether this will see adoption depends on how widely key-value object stores are used with Git, but the implementation itself looks complete and production-ready.

Subject: [PATCH 0/2] repo structure: performance and memory-usage improvements
Series version: v2 (addresses minor feedback)
Originating author: Patrick Steinhardt <ps@pks.im>
Thread type: patch series

Core problem or goal
Improve performance and reduce memory usage of `git repo structure` (part of the `git repo` built-in) by optimizing its object-counting logic. The current implementation parses every object it encounters, which is prohibitively expensive in repositories with tens of billions of tree entries. The goal is to delay parsing until necessary (patch 1) and skip full tree parsing when only the object type is required (patch 2).

Current status
Under review; v2 posted. The update addresses the sole substantive feedback from v1: a reworded comment in patch 1 to clarify that `repo_parse_commit()` acts as a failsafe rather than a dependency. A follow-up discussion between Patrick Steinhardt and Kristofer Karlsson explored whether the fallback `repo_parse_commit()` call should remain silent or trigger a `BUG()` assertion when a commit is unexpectedly unparsed; no consensus was reached, but the updated comment already clarifies the intended behavior, so the choice is now purely about fail-fast versus fail-safe semantics. All other aspects of the series remain unchanged. The series is endorsed by Kristofer Karlsson, who confirmed the combined 80% memory reduction (5.1× less memory) and 20% wall-time improvement. No open technical concerns or objections remain; the series is ready for maintainer pickup.

Key technical details
- Files touched: `builtin/repo.c` only.
- New behavior: objects are parsed only when needed (patch 1: blobs and tags are counted without parsing; commits are looked up via `lookup_commit()` and parsed only as a failsafe via `repo_parse_commit()`; patch 2: tree parsing is skipped when only object type is required).
- Old behavior: every object was parsed unconditionally.
- No on-disk format changes; no new CLI options or config keys.
- Performance impact: patch 1 alone yields 12% wall-time improvement and 4% memory reduction in `git.git`; combined effect of both patches is 80% memory reduction and 20% wall-time improvement, as benchmarked by the author and confirmed by Kristofer Karlsson.
- Code comment rewording in patch 1: the comment now states that commits *should* already be parsed by the revision walk, framing `repo_parse_commit()` as a failsafe rather than a dependency.
- Open design choice: whether the fallback `repo_parse_commit()` call should remain silent or trigger a `BUG()` assertion when a commit is unexpectedly unparsed. The updated comment clarifies the intended behavior, but the implementation remains fail-safe (silent fallback).

Open questions and loose ends
- Whether to convert the silent fallback `repo_parse_commit()` call into a `BUG()` assertion for fail-fast behavior. This is a low-priority design choice with no impact on functionality or performance; the series remains ready for maintainer pickup regardless.

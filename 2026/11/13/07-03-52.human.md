This is a review of a small cleanup patch in the HTTP backend. Patrick Steinhardt raises a thoughtful question about the patch's rationale: while the commit message explains that the pre-sizing logic is buggy (incorrect for SHA-256 and uses unchecked arithmetic), it doesn't clearly justify why removing it entirely is preferable to fixing it. The message leans on a precedent (a similar cleanup in `add_rfc2047()`), but Patrick points out that precedent alone isn't a strong argument—what matters is whether skipping pre-sizing here is actually safe and beneficial.

The patch itself removes a 2009-era optimization in `get_info_packs()` that iterates over all packs twice (once to count them, once to format output) and pre-sizes a `strbuf` to avoid reallocations. The author argues this is unnecessary because `strbuf_addf()` already handles dynamic growth, and the arithmetic is error-prone. Patrick’s concern is that the commit message doesn’t address whether the performance trade-off (potential reallocations vs. a second loop) is worth it for this specific function. He isn’t rejecting the patch, but he wants the rationale to be more explicit.

This is a surface-level review—Patrick isn’t questioning the code’s correctness or digging into edge cases, but he’s asking for a clearer explanation of the *why*. The patch is simple and self-contained, touching only `http-backend.c`, but this feedback suggests the author may need to revise the commit message to address the performance implications directly.

This is the first patch in a two-part feature series introducing `--filter-to-loose=<dir>` for `git repack`. The goal is to let users write filtered-out objects directly as loose objects into a specified directory, rather than as a packfile. This is aimed at workflows where external systems (like key-value stores) manage Git objects individually, avoiding the need to unpack an intermediate packfile.

The patch adds the new `--filter-to-loose` option, which works only when combined with `--filter`. It streams the filtered pack into `unpack-objects`, writing excluded objects as loose objects in the target directory. Objects already present in the destination are skipped, and the implementation initially handles only objects already in packs (loose objects in the source repository are left untouched). The code touches `builtin/repack.c`, `repack-filtered.c`, and `repack.h`, with new tests in `t/t7700-repack.sh` covering basic functionality, error handling, and edge cases like concurrent access or existing objects.

The implementation looks clean and well-scoped, with clear commit messages and thorough test coverage. The design—streaming directly to `unpack-objects`—avoids reinventing the wheel and leverages existing Git machinery. The patch doesn’t yet address loose objects in the source repository (that’s left for the second patch), but the separation of concerns makes sense. No reviewer feedback has appeared yet, so the design and edge cases (like permission issues or corrupted objects) remain unchallenged. For now, this seems like a pragmatic solution to a real workflow problem, though its adoption will depend on how widely such key-value stores are used with Git.

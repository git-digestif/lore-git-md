Adithya Chakilam is proposing a new `--filter-to-loose=<directory>` option for `git repack` that would write objects excluded by `--filter` directly as loose objects into a specified directory, rather than leaving them in an intermediate packfile. This is meant to help workflows that manage Git objects individually, such as key-value object stores or large-object promisors that do not implement the Git wire protocol. The two-patch series is currently at version 2 and remains under review.

Junio C Hamano has reviewed both iterations and raised significant correctness concerns that are still unresolved. While v2 addressed three initial issues from the v1 review (early validation of the target directory, relative path resolution via `OPT_FILENAME`, and a double-close bug), Junio has identified a potential data-loss scenario when the destination directory equals the repository's own object directory, along with several robustness problems in patch 2's loose-object handling. Most recently, he pointed out that the loose-object copying in patch 2 only activates for `blob:limit` filters and silently skips objects when other filters such as `blob:none` are used, contradicting the behavior described in the cover letter and documentation. Other open issues include reachability-agnostic filtering that could copy unreachable or index-staged objects to the destination, temporary file naming that would trigger `git fsck` warnings on crashed runs, and missing error handling when removing source objects.

The series has not been queued in any of Junio's integration branches. Adithya has not yet responded to the v2 review feedback, so the thread is awaiting a v3 that addresses the filter coverage gap, the data-loss guard, and the other technical concerns raised.

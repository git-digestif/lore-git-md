Adithya Chakilam's v2 series adding `--filter-to-loose=<directory>` to `git repack` remains under review. The two-patch series would let `git repack --filter` write excluded objects directly as loose files into a specified directory, supporting key-value object stores and large-object promisors that do not implement the Git wire protocol. Version 2 addressed Junio C Hamano's initial concerns about directory validation, relative path resolution, and a double-close bug, but Junio's latest review of both patches has surfaced deeper correctness issues that will likely require a v3.

On patch 1, Junio reiterated the data-loss risk when the destination directory equals the source repository's own object directory: `unpack-objects` would skip writing loose copies of objects already present in packs, and a subsequent `-d` would remove those packs permanently. He also flagged a memory leak where `filter_to_loose` is not freed at cleanup, a `const` qualifier issue, redundant test coverage, and minor documentation formatting requests.

On patch 2, which moves loose objects excluded by the filter, Junio identified a fundamental design flaw: `move_loose_filtered_objects()` currently enumerates all loose objects on disk and filters purely by size, ignoring reachability, pack membership, and the index. This causes unreachable blobs destined for cruft packs to be copied prematurely, unreachable loose blobs under plain `-a -d` to pollute the destination despite normal prune expiration, and staged index blobs to be duplicated even though they remain in the main pack. He suggests walking reachable objects from refs or filtering only after packs are installed, and supporting at minimum `LOFC_BLOB_NONE` while rejecting unsupported filters. He also noted that the temporary file naming does not use the `tmp_obj_` prefix that `git fsck` ignores, that `copy_file()` does not preserve read-only permissions, that `remove_moved_loose_objects()` silently ignores unlink errors and leaves empty fan-out directories, and that the test comparing inodes via `ls -i` is not portable and may not exercise the intended code path.

The series awaits the author's response to these substantive review concerns.

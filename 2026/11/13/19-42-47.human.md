This is a bugfix for the promisor-remote subsystem, addressing a crash in `` `git ls-remote` `` when run outside a repository with certain promisor-remote configurations enabled. The discussion here centers on the best place to fix the issue.

Christian Couder’s patch adds a NULL check for `` `repo->gitdir` `` at the start of `` `filter_promisor_remote()` ``, arguing that `` `git ls-remote` `` has no legitimate use for promisor remotes outside a repository. Junio C Hamano suggests an alternative approach: making `` `promisor_remote_reply()` `` a no-op when no repository is present, since it’s the higher-level function that initiates the problematic call chain. His illustration patch moves the NULL check up one level, adding a `` `struct repository *` `` parameter to `` `promisor_remote_reply()` `` and documenting why the early return is safe.

The trade-off is clear: Christian’s fix is minimal and contained, while Junio’s proposal is more invasive (requiring changes to two callers) but arguably cleaner, since it prevents the entire promisor-remote machinery from engaging when it isn’t needed. Neither approach is obviously wrong, and the discussion is still open. The patch is well-motivated and includes test coverage, so it’s likely to land in some form soon. If you care about promisor-remote stability or edge-case behavior in `` `git ls-remote` ``, this thread is worth following.

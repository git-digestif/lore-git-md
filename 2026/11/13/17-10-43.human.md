This is a **design clarification** from Christian Couder, the promisor-remote subsystem maintainer, responding to Junio C Hamano’s query about how the proposed `promisor.fetchOrder` configuration should interact with server-side promisor remote advertisement.

Christian acknowledges the complexity of the problem: when a client fetches from multiple remotes, each remote may advertise its own preferred set of promisor remotes (e.g., remote A suggests A1 and A2, remote B suggests B1, B2, and B3). During a subsequent lazy fetch, it is unclear which order would be optimal, and a single static order may not suit all scenarios. He implies that the best order could depend on which remote the related objects were originally fetched from, suggesting that a dynamic or context-sensitive approach might be needed rather than a fixed client-side list.

The response does not endorse or reject the current patch, but it raises a fundamental design concern that the patch does not address. This concern is now the primary blocker for the feature; until it is resolved, the patch remains an RFC prototype rather than a candidate for merging. The author, Yopa Nelly, has already paused further work pending Outreachy selection, so progress on this feature is likely to stall until the design question is clarified.

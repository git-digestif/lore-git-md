Thread identity
Subject: [PATCH] promisor-remote: fix crash in `git ls-remote` outside repository
Series version: standalone patch
Originating author: Christian Couder
Thread type: bugfix

Core problem or goal
Fix a crash in `git ls-remote` when invoked outside any Git repository with promisor-remote configuration enabled. The crash occurs because `filter_promisor_remote()` dereferences `repo->gitdir` without checking for NULL. The regression was introduced by commits 3e20258d11 and 7a56394fc6 (2026).

Current status
Under review. Two competing approaches are now on the table: (1) Christian’s original patch, which adds a NULL check in `filter_promisor_remote()`, and (2) Junio’s alternative, which makes `promisor_remote_reply()` a no-op when no repository is present by having it take a `struct repository *` parameter and early-return if `repo->gitdir` is NULL.

Key technical details
- Subsystem: promisor-remote
- Functions discussed: `filter_promisor_remote()` (Christian’s fix), `promisor_remote_reply()` (Junio’s alternative)
- Files touched: `promisor-remote.c`, `t/t5710-protocol-v2-http.sh` (tests already provided by Christian)
- New symbols: none
- Old-vs-new behavior: both approaches prevent the crash; Junio’s alternative avoids calling `filter_promisor_remote()` entirely when outside a repository
- Test coverage: two new test cases in `t5710` covering both crash scenarios (already present in Christian’s patch)

Open questions and loose ends
- Which of the two approaches is preferable: the minimal fix at the crash site or the higher-level no-op?
- Should the rationale for punting when `repo->gitdir` is NULL be documented in the code? Junio notes this as a requirement for either solution.
- Are there other callers of `promisor_remote_reply()` that might need similar adjustments if Junio’s approach is adopted?

Participant positions
- Christian Couder (author): provided problem description, regression timeline, fix (NULL check in `filter_promisor_remote()`), and tests. Argues the early return is safe because `git ls-remote` has no legitimate use for promisor remotes outside a repository.
- Junio C Hamano (maintainer): acknowledges the problem but proposes an alternative fix (making `promisor_remote_reply()` a no-op when no repository is present). Prefers this approach for being cleaner and avoiding unnecessary work. Raises the need for explicit documentation of the rationale in the code.

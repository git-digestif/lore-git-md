This is the **implementation review** of the standalone toggle patch that introduces a default-disabled opt-in mechanism for `--follow` in non-linear history. The patch, proposed by Patrick Steinhardt and now queued by Junio C Hamano, is the project's settled resolution to the `--follow` performance regression that blocks GitLab's deployment. This review is **substantive** but narrowly focused on the toggle's implementation details rather than its policy rationale, which was already decided in prior discussion.

The patch adds a new config value `log.follow=merges` (or the flag `--follow=merges`) to enable rename-following in merges, defaulting to off. It touches `Documentation/config/log.adoc`, `builtin/log.c`, and `log-tree.c`, and is **mechanically sound** but raises minor documentation and error-handling concerns. Patrick's feedback is **surface-level** (nitpicks on wording, error messages, and defensive coding) but **technically precise**, suggesting the patch is nearly ready for merging once these are addressed.

Key observations:
- The patch **disables rename-following in merges by default**, restoring pre-304812ed33 performance for users who don’t opt in. This aligns with the project's policy decision to prioritize performance over the feature's correctness improvements for non-linear history.
- The config parsing in `builtin/log.c` is **fragile**: it currently dies on invalid values (e.g., `log.follow=bogus`), and Patrick suggests using `git_parse_maybe_bool()` for graceful error handling. This is a **real but minor issue**—the patch works as intended but could be more user-friendly.
- The documentation in `log.adoc` **omits a performance warning** for `log.follow=merges`, which Patrick flags as inconsistent with the `--follow[=merges]` flag's documentation. This is a **clarity gap** rather than a correctness issue.
- The logic in `log-tree.c` is **defensive but redundant**: it checks both `follow_renames` and `follow_merges`, even though the latter is only set when the former is true. Patrick notes this isn’t harmful but could be simplified.
- The patch **preserves the v5 series' correctness fixes** (e.g., handling dropped-side edits) while disabling the performance-costly parts by default. This decouples the toggle from the v5 series, allowing it to land first.

The patch is **not controversial**—it implements the agreed-upon opt-in mechanism—and Patrick’s feedback is **constructive but non-blocking**. The only open question is whether to use a **flag (`--follow=merges`)** or **config option (`log.follow=merges`)**; Patrick’s preference for the former (cited in prior discussion) is likely to prevail, but this patch already supports both. The toggle’s default-disabled status is **not in dispute**.

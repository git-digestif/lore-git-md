This is a **security bugfix** targeting Git’s SSH signing verification. The patch addresses a critical flaw where Git fails open—rather than failing closed—when the configured SSH revocation file is missing, unreadable, or a directory. The fix ensures that signature verification now fails by default in these cases, aligning Git’s behavior with the principle of least privilege.

The patch is now in its **third iteration (v3)**, incorporating Junio C Hamano’s feedback on error-handling consistency. The key improvement is folding the revocation-file check into the existing failure block, ensuring that signature information is displayed even when the revocation file is missing—matching the behavior for unknown keys. This resolves the asymmetry Junio noted, where a missing revocation file previously skipped the signature-info display entirely. The `%G?` status code now consistently returns "U" for both unknown keys and revocation-file failures.

The patch remains narrowly scoped: it makes revocation-file errors fatal by default while preserving the escape hatch via the `:(optional)` pathname prefix (e.g., `gpg.ssh.revocationFile = :(optional)/path/to/revocations`). Test coverage has been expanded with four new cases in `t/t7528-signed-commit-ssh.sh`, covering revoked keys, missing files, and the optional-prefix behavior. The only file modified is `gpg-interface.c`.

This fix is part of a broader security cleanup for SSH signing, which also includes a **separate documentation patch** (already finalized) clarifying that `valid-before`/`valid-after` checks use the committer date—not the signature timestamp—due to signer-controlled timestamps. Both patches are ready for integration and may be held together to avoid splitting security fixes across releases. Junio’s "What's cooking" report (Oct #09) contains a minor clerical error in the topic description, but this does not affect the technical readiness of the patches.

The patch looks well-crafted and addresses a clear security gap. The error-handling refinement in v3 resolves the last substantive concern, and the escape-hatch mechanism ensures backward compatibility for users who need it. If you care about SSH signing security, this is worth reviewing.

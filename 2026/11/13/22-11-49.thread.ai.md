Thread identity: Patch series introducing `--filter-to-loose=<directory>` option for `git repack` to improve interoperability with key-value object stores and large-object promisors. Series version: v2 (complete, two patches). Originating author: Adithya Chakilam. Thread type: patch series.

Core problem or goal: Enable `git repack --filter` to write filtered-out objects directly as loose objects into a specified directory, avoiding an intermediate packfile. This simplifies workflows for systems that manage Git objects individually (e.g., key-value stores) and supports offloading large objects to separate repositories accessed via alternates (avoiding delta-search overhead) and uploading individual objects to large-object promisors that do not implement the Git wire protocol (per section II.4 of the large-object-promisors technical document). The series consists of two patches: (1) core functionality for objects already in packs, and (2) extension to handle loose objects excluded by the filter.

Current status: Under review (v2 posted, incorporating fixes for issues raised during v1 review; no maintainer integration status reported -- not in `pu`, `next`, or `master`). Version 2 incorporates fixes for three issues raised by Junio C Hamano during review of v1: early error if the target directory does not exist, `OPT_FILENAME` instead of `OPT_STRING` for correct relative path resolution from subdirectories, and removal of a manual `close()` to fix a double-close bug in `repack-filtered.c`. Junio has now reviewed both v2 patch 1 and v2 patch 2 and raised additional concerns on each (see Open questions).

Key technical details:
- New CLI option: `--filter-to-loose=<directory>` for `git repack`.
- Subsystems touched: repack machinery (`builtin/repack.c`, `repack-filtered.c`, `repack.h`).
- Behavior: When used with `--filter`, streams filtered pack into `unpack-objects`, writing excluded objects as loose objects in `<directory>`. Objects already present in `<directory>` are skipped. With `-d`, source loose objects are removed after writing. The option cannot be combined with `--filter-to` or `--max-pack-size`, and the destination directory must already exist.
- Implementation details:
  - Patch 1: Uses `unpack-objects` to stream objects directly to `<directory>`; skips objects already present in the target directory. In `builtin/repack.c`, the option is parsed with `OPT_FILENAME` (so relative paths resolve correctly from subdirectories), validated up front with `is_directory()`, and wired into `struct write_pack_opts` via a new `bool loose` field. In `repack-filtered.c`, `write_filtered_pack()` now branches on `opts->loose`: when true, it starts an `unpack-objects` child process with `GIT_OBJECT_DIRECTORY` set to the destination, pipes the `--stdin-packs` output of `pack-objects --stdout` into that child, and manages `SIGPIPE` via `sigchain_push`. V2 fixes: (1) **directory handling**: errors out early if `<directory>` does not exist, with new test coverage in `t/t7700-repack.sh`; (2) **path resolution**: option parsing changed from `OPT_STRING` to `OPT_FILENAME` in `builtin/repack.c` so relative paths resolve correctly when `git repack` is run from a subdirectory, with test coverage added; (3) **resource cleanup**: double-close bug in `repack-filtered.c` fixed by removing the manual `close()` of `unpack.in` since `start_command()` already closes associated descriptors on failure.
  - Patch 2: Adds `move_loose_filtered_objects()` and `remove_moved_loose_objects()` to `repack-filtered.c`, declared in `repack.h`. `move_loose_filtered_objects()` collects all loose object IDs via `for_each_loose_file_in_source`, applies the filter using `list_objects_filter__filter_oidset` (activating only for the `blob:limit` filter choice), and copies each excluded object to the destination directory using a `.tmp-<pid>` temporary file and `finalize_object_file()` for atomicity. It checks `access(dst, F_OK)` to skip objects already present in the destination and uses `safe_create_leading_directories()` to create needed subdirectories. In `builtin/repack.c`, `move_loose_filtered_objects()` runs after `write_filtered_pack()` completes when `--filter-to-loose` is set, populating a `struct oidset moved_loose` to track successfully copied objects. Later, after `prune_packed_objects()` runs, `remove_moved_loose_objects()` unlinks the source copies of tracked objects when `-d` is specified. On failure, the temporary file is unlinked to prevent corruption. Loose objects in the source repository are left untouched by patch 1 and handled exclusively by patch 2.
- Test coverage: Tests in `t/t7700-repack.sh` verify writing filtered objects as loose files, skipping objects already present in the destination, erroring on a non-existent directory, failure recovery that leaves source packs intact with no `.tmp-*` leftovers, relative-path resolution from a subdirectory, not moving objects from kept packs, leaving unreachable objects in cruft packs alone, survival of `gc`/`prune` in the source once the destination is added as an alternate, option incompatibility checks with `--filter-to` and `--max-pack-size`, loose object handling (copying excluded loose blobs to the destination, `-d` removing source copies while leaving destination intact verified via alternates, identical existing destination objects left untouched confirmed by inode comparison, and failure recovery leaving source repository intact with no temporary file leftovers).
- Documentation: Updated in `Documentation/git-repack.adoc` (noting that loose objects excluded by the filter are also copied, with source removal under `-d`) and `builtin/repack.c` help text.
- On-disk format: No changes; loose objects are written in standard format.
- Symbols: New option name (`filter-to-loose`), new struct field (`bool loose` in `struct write_pack_opts`), new functions (`move_loose_filtered_objects`, `remove_moved_loose_objects`), new oidset (`struct oidset moved_loose`).

Open questions and loose ends:
- **Data-loss guard needed (repeated for both patches)**: Junio identified a critical scenario where `--filter-to-loose` points at the source repository's own object directory (e.g., `--filter-to-loose=objects` in a bare repo or `--filter-to-loose=.git/objects`): in patch 1, `unpack-objects` sees via `odb_freshen_object()` that every filtered-out object already exists in a pack and skips writing loose copies, and if `-d` is then used, `cmd_repack()` removes the old packs, permanently losing those objects; in patch 2, `access(dst, F_OK)` succeeds because source and destination are the same file, and `remove_moved_loose_objects()` would unlink the only copy of the object. He suggests guarding against this by comparing `realpath(filter_to_loose)` against `repo_get_object_directory(repo)` and adding a regression test.
- **Reachability and filtering correctness in patch 2**: The current `move_loose_filtered_objects()` enumerates all loose objects on disk and filters purely by size, ignoring reachability, pack membership, and the index. Junio outlines three concrete failure scenarios: with `--cruft -a -d`, unreachable loose blobs destined for the cruft pack get copied to the destination before `prune_packed_objects()` runs; with plain `-a -d`, unreachable loose blobs bypass normal prune expiration and pollute the destination; and staged blobs in the index are kept in the main pack by `pack-objects --indexed-objects` yet still get copied to the destination. He suggests the code should instead walk reachable objects from refs or filter after packs are installed, excluding objects that ended up in kept packs or the index.
- **Filter coverage**: The function silently no-ops for any filter other than `blob:limit`, contradicting the commit message and documentation; Junio suggests supporting `LOFC_BLOB_NONE` at minimum while explicitly rejecting unsupported filters.
- **Permission and temp-file handling**: `copy_file()` maps mode 0444 to 0666 (masked by umask) rather than preserving read-only permissions, and the temporary file naming scheme `<oid>.tmp-<pid>` does not use the `tmp_obj_` prefix that `git fsck` ignores, so crashed runs leave files that trigger "bad sha1 file" warnings. He recommends using `git_mkstemp_mode(..., 0444)` with `copy_fd()` and the `tmp_obj_XXXXXX` template.
- **Error handling in removal**: In `remove_moved_loose_objects()`, unlike `prune_packed_objects()` which uses `unlink_or_warn()`, the current code silently ignores `unlink()` errors and leaves empty fan-out subdirectories behind.
- **Memory management**: `filter_to_loose`, allocated by `OPT_FILENAME`, must be freed at the `cleanup` label in `builtin/repack.c`, and its `const` qualifier should be dropped to match the convention for variables passed to `free()`.
- **Test redundancy**: The second new test in `t/t7700-repack.sh` duplicates the first half of the preceding test with no differing action, making it redundant.
- **Test portability and coverage**: Junio questions whether the new test using `ls -i` to compare inodes actually exercises the new `move_loose_filtered_objects()` code path or merely the `unpack-objects` path from patch 1, and notes that `ls -i` is not portable across all platforms supported by the test suite.
- **Documentation requests**: Use `<directory>` rather than `<dir>` in docs, line-wrap the overlong SYNOPSIS entry, explain in the man page why loose objects are preferable to a single junk pack for the reader's use case, and add a lone `+` continuation line in `Documentation/git-repack.adoc` to match AsciiDoc list formatting used by adjacent entries like `--drop-filtered`.
- The three issues raised by Junio on v1 (directory handling, path resolution, resource cleanup) are addressed in v2 but await verification by reviewers.
- No discussion of edge cases beyond those covered in tests (e.g., concurrent access to `<directory>`, permission issues, handling of corrupted objects, or race conditions during streaming).
- No mention of performance implications (e.g., overhead of writing loose objects vs. packfiles for large object sets, or scalability of `unpack-objects` for high-volume use cases).

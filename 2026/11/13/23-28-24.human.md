This is the final patch in a security-focused thread addressing two critical flaws in Git’s SSH signing verification. The patch makes Git fail closed when the `gpg.ssh.revocationFile` is configured but missing or unreadable, rather than warning and proceeding as if no revocation file existed. This aligns Git’s behavior with OpenSSH’s `sshd`, which refuses public key authentication when its `RevokedKeys` file is unreadable, and with Git’s own GPG backend, which already fails closed on revocation file issues.

The change is minimal and well-motivated: if the revocation file does not exist, Git now returns an error instead of silently continuing. Users who want to allow missing files can prefix the path with `:(optional)`, a Git pathname syntax that treats missing files as if the variable were unset. The patch updates `Documentation/config/gpg.adoc` to document this behavior and adds four new test cases in `t/t7528-signed-commit-ssh.sh` covering revoked keys, missing files, and the `:(optional)` escape hatch.

The implementation is clean and directly addresses the security concern raised in the thread. The commit message clearly explains the rationale (failing open is unsafe), the escape hatch mechanism, and the existing behavior of `:(optional)`. The code change removes the warning-and-continue logic and replaces it with an early error return, while ensuring signature information is still displayed for both missing revocation files and unknown keys. The tests are thorough and cover both the failure case and the optional override.

This patch is part of a two-patch series; the other patch (already finalized) clarifies in the documentation that Git uses the committer or tagger date (not the signature timestamp) for `valid-before`/`valid-after` checks, and explicitly notes the lack of security guarantees due to signer-controlled timestamps. Both patches are ready for integration and may be held together to avoid splitting security fixes across releases.

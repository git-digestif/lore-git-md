This is a performance patch targeting memory usage in the commit subsystem, now in its second iteration.

The patch reorders fields in `struct commit` to eliminate padding on 64-bit platforms, shrinking the struct from 80 to 72 bytes (a 10% reduction) with no behavioral change. The change moves the `index` field into the 4-byte gap after `struct object`, which is the only invariant the struct must maintain (cast compatibility with `struct object`). The author has added explanatory comments for `index` (a commit-slab array index) and `date` (the unadjusted committer date) to clarify their purpose, addressing Junio C Hamano’s feedback from v1.

The patch remains minimal: a single-line field reorder in `commit.h` plus 19 lines of added comments. The author measured peak RSS for `git rev-list --all` on a 4.5-million-commit monorepo, showing a 32 MiB reduction (from 849 MiB to 817 MiB), closely matching the expected 8 bytes × 4.5M commits. Runtime is unchanged. The patch is based on commit `1891de46f79` and has no test coverage; the author prototyped a regression test but omitted it, citing maintainability concerns, and offered to submit it separately if requested.

The thread has already established that the change is safe (Derrick Stolee called it "obviously correct") and that the `struct object`-first invariant is respected. The author has also demonstrated that violating this invariant causes runtime failures in `init_commit_node()` and proposed a compile-time assertion (`BUILD_ASSERT_OR_ZERO`) as a potential follow-up to enforce it. No technical objections remain; the patch is ready for maintainer pickup unless discussion reopens about struct bloat enforcement mechanisms (regression test, scoped `-Wpadded` warnings, or compile-time assertions).

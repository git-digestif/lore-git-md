This is a **bugfix** targeting the reftable backend. A contributor, 井上司, reports that when a transaction updates both a branch and HEAD to point to that branch in the same operation, the reflog for HEAD incorrectly records the branch's *old* value (or omits the entry entirely if the branch was created in the transaction). The files backend handles this case correctly, so this is a reftable-specific regression.

The issue is straightforward to reproduce with a simple script that creates a repository, makes two commits, updates a branch and HEAD in one transaction, and then checks the reflog. The root cause appears to be in `write_transaction_table()` in `refs/reftable-backend.c`: when resolving the new OID for a symref update, the code reads the ref state *before* the transaction commits, so it sees stale or missing data.

井上司 diagnoses the problem clearly and suggests a plausible fix: instead of resolving the target ref’s OID from the pre-transaction state, the code should use the OID from the target’s own update in the same transaction. The patch itself isn’t included yet, but the analysis looks solid and the scenario (e.g., `git switch -c`) is a real-world use case that would be affected. This is a well-motivated, narrowly scoped bugfix that should be uncontroversial.

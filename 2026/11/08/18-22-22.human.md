This is a **bugfix follow-up** addressing a subtle edge case in the recent patch that ensures `git init` defaults to SHA-256 when Git is built with `WITH_BREAKING_CHANGES=1`. Junio C Hamano raises a concern about what happens when `git init` is run in an *already initialized* repository that uses a different object format (e.g., SHA-1). The current patch unconditionally sets the hash algorithm to `GIT_HASH_DEFAULT`, which could silently overwrite the existing repository’s format—a behavior Junio argues is undesirable.

Junio’s email includes a test case demonstrating the issue: if you initialize a repository with SHA-1 (the "opposite" format in breaking-changes mode) and then run `git init` again without specifying a format, the patch as written would switch the repository to SHA-256. He outlines three possible behaviors for reinitialization: (1) convert the repository to the new format (impractical), (2) preserve the existing format with a warning, or (3) fail loudly if the formats don’t match. The current patch does none of these, instead clobbering the existing format without notice.

The email also touches on a related question about reference storage formats (e.g., reftable vs. reffiles), noting that `git init` doesn’t convert those either, which suggests the object format behavior should be similarly conservative. Junio’s proposed test (included in the email) verifies that reinitialization should preserve the existing object format, regardless of the default.

This is a **substantive review**—Junio isn’t nitpicking the patch but identifying a real design question about how `git init` should behave in edge cases. The fix is clearly well-motivated for *new* repositories, but the reinitialization scenario complicates things. The thread is now at a decision point: should the patch be amended to handle reinitialization more carefully, or is the current behavior acceptable? The answer will likely depend on whether the project prioritizes simplicity (current patch) or strict backward compatibility (Junio’s preference for #2 or #3). No resolution is reached in this email, but the issue is now squarely on the table.

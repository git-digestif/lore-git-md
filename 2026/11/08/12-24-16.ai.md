This is a reply in the `test-tool genbytes` thread, clarifying the technical rationale for rejecting `printf` as a minimal fix. The author (Kristofer Karlsson) acknowledges Johannes Sixt's suggestion to convert only the performance-critical test (`t4205-log-pretty-formats.sh`) to `printf` but demonstrates that the approach fails on macOS: `printf` silently truncates the output when given an extremely large padding value, producing only nine literal zeros instead of the expected 2 GB. This inconsistency across platforms (Linux vs. macOS) makes `printf` unreliable for the intended use case. The author reiterates that generalizing the existing `genzeros` helper into `genbytes` remains the most robust solution, offering a uniform interface for generating arbitrary bytes (including NUL) while avoiding platform-specific quirks. The reply also hints at future-proofing: even if `printf` worked today, it would not handle cases where large inputs require specific non-zero bytes, leaving the test suite fragmented across multiple tools. No new patches or workflow decisions are announced here, but the technical case against `printf` is now explicitly documented in the thread.

Thread identity: bugfix for reftable backend reflog handling during symref updates in transactions; originating author 井上司 (Tsukasa Inoue); thread type bug report with reproduction and patch submission; current version v2 of a single-patch series.

Core problem or goal: fix a correctness regression in reflog handling where HEAD reflog entries record the wrong OID or are omitted when HEAD and its target branch are updated in the same transaction. The issue affects both the reftable and files backends, but was masked in the files backend by its lack of atomic transaction support.

Current status: v2 patch submitted addressing all review feedback from Karthik Nayak; remains under review with no merge event to `master` reported; expected to land in `next` after review convergence.

Key technical details:
- subsystems: reftable backend (`refs/reftable-backend.c`), files backend (`refs/files-backend.c`), generic refs layer (`refs.c`)
- root cause: for symref updates, the new OID for the reflog was obtained by resolving the *new target* before the transaction commits, resulting in either the old branch value or no value at all
- solution: introduce `ref_transaction_resolve_new_oid()` in `refs.c`, a helper that resolves a ref's new OID by walking the transaction's updates (including symref chains) before falling back to `refs_resolve_ref_unsafe()`; uses `find_ref_update()` with a linear scan because `split_symref_update()` appends updates after the initial sort of `refnames`, breaking the sorted invariant
- v2 changes: tests run in subshells within the test repository to avoid repetitive `-C repo` invocations; new test covers symref target updated through HEAD itself; `--batch-updates` test verifies rejected target updates (via `REF_TRANSACTION_ALLOW_FAILURE`) do not pollute the reflog
- behavior change: reflog entries for HEAD now record the correct new OID when HEAD and its target branch are updated in the same transaction, regardless of backend or update order
- broader architectural context: the helper aligns with the goal of moving all reflog logic into `refs.c` and could support future transaction-level conflict resolution; deeper refactoring explicitly deferred
- test coverage: `t/t1400-update-ref.sh` exercises update/create scenarios with both branch-first and head-first orderings, plus `--batch-updates` rejection case
- files touched: `refs.c`, `refs/refs-internal.h`, `refs/files-backend.c`, `refs/reftable-backend.c`, `t/t1400-update-ref.sh`

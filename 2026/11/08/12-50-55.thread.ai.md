Thread identity: bugfix for reftable backend reflog handling during symref updates in transactions; originating author 井上司 (Tsukasa Inoue); thread type bug report with reproduction.

Core problem or goal: fix a correctness regression in the reftable backend where HEAD reflog entries are either written with the wrong OID or omitted entirely when HEAD is updated in the same transaction as its target branch. The files backend handles both scenarios correctly, but only because it lacks atomic transaction support—meaning the same bug would surface if atomicity were added.

Current status: under review; no prior version of this fix exists.

Key technical details:
- subsystem: reftable backend (`refs/reftable-backend.c`)
- function: `write_transaction_table()`
- root cause: for symref updates, the new OID for the reflog is obtained by resolving the *new target* before the transaction commits, so it sees either the old branch value or (if the branch is new) no value at all
- files touched: `refs/reftable-backend.c` (expected)
- new/renamed symbols: none yet
- behavior change: reflog entries for HEAD will record the correct new OID when HEAD and its target branch are updated in the same transaction
- test coverage: minimal reproduction script provided using `git update-ref --stdin` with a transaction that updates a branch and HEAD in one operation; formal test case integration still pending

Open questions and loose ends:
- exact fix implementation: 井上司 suggests using the OID from the target branch's update in the same transaction when available (high weight); Karthik Nayak endorses this as a practical solution
- broader refactoring: Karthik proposes moving reflog logic into the generic `refs.c` layer to eliminate per-backend conflict resolution (medium weight, unlikely to materialize soon)
- test integration: whether the reproduction script will be converted into a formal test case for the test suite

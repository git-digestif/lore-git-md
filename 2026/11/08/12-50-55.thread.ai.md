Thread identity: bugfix for reftable backend reflog handling during symref updates in transactions; originating author 井上司 (Tsukasa Inoue); thread type bug report with reproduction and patch submission.

Core problem or goal: fix a correctness regression in reflog handling where HEAD reflog entries record the wrong OID or are omitted when HEAD and its target branch are updated in the same transaction. The issue affects both the reftable and files backends, but was masked in the files backend by its lack of atomic transaction support.

Current status: patch undergoing substantive review; the proposed fix implements the agreed helper function `ref_transaction_resolve_new_oid()` in `refs.c` and updates both backends to use it. The patch is well-motivated, includes thorough test coverage, and is expected to land in `next` after a v2 addressing review feedback. No merge event to `master` has been reported.

Key technical details:
- subsystems: reftable backend (`refs/reftable-backend.c`), files backend (`refs/files-backend.c`), generic refs layer (`refs.c`)
- root cause: for symref updates, the new OID for the reflog was obtained by resolving the *new target* before the transaction commits, resulting in either the old branch value or no value at all
- solution: introduce `ref_transaction_resolve_new_oid()` in `refs.c`, a helper that resolves a ref’s new OID by walking the transaction’s updates (including symref chains) before falling back to `refs_resolve_ref_unsafe()`
- new symbols: `ref_transaction_resolve_new_oid()`, `find_ref_update()` (internal helper), `string_list_lookup()` (proposed but rejected for correctness)
- behavior change: reflog entries for HEAD now record the correct new OID when HEAD and its target branch are updated in the same transaction, regardless of backend or update order
- broader architectural context: the helper aligns with the goal of moving all reflog logic into `refs.c` and could support future transaction-level conflict resolution (e.g., delete-and-recreate sequences)
- test coverage: new test script (`t/t1400-update-ref.sh`) exercises both update and create scenarios with varying update orders, verifying both the reflog message and the recorded OID for HEAD; v2 will add tests for `REF_TRANSACTION_ALLOW_FAILURE` and adopt subshells for cleanup
- files touched: `refs.c`, `refs-internal.h`, `refs/files-backend.c`, `refs/reftable-backend.c`, `t/t1400-update-ref.sh`
- implementation constraint: `ref_transaction_prepare()` sorts `refnames` only at the start, but backends append updates (e.g., via `split_symref_update()`) during preparation, breaking the sorted invariant; a linear scan is required to catch these late additions

Open questions and loose ends:
- **edge-case handling**: whether reflog updates should be scheduled last in transactions to ensure all reference updates are known, and how to handle `REF_TRANSACTION_ALLOW_FAILURE` scenarios where a reference update fails after the reflog update (resolved: backends mark rejections during preparation, so the helper sees all failures before reflog updates are written; no partial reflog updates occur)
- **test robustness**: subshells for test cleanup adopted to avoid `-C repo` repetition (resolved)
- **follow-up work**: whether the broader architectural refactoring (moving all reflog logic into `refs.c`) will proceed as a subsequent step (low weight; not blocking the immediate fix)

Thread identity: bugfix for reftable backend reflog handling during symref updates in transactions; originating author 井上司 (Tsukasa Inoue); thread type bug report with reproduction and patch submission.

Core problem or goal: fix a correctness regression in reflog handling where HEAD reflog entries record the wrong OID or are omitted when HEAD and its target branch are updated in the same transaction. The issue affects both the reftable and files backends, but was masked in the files backend by its lack of atomic transaction support.

Current status: patch submitted and undergoing substantive review; the proposed fix implements the agreed helper function `ref_transaction_resolve_new_oid()` in `refs.c` and updates both backends to use it. The patch is well-motivated, includes thorough test coverage, and is expected to land in `next` after a v2 addressing review feedback. No merge event to `master` has been reported.

Key technical details:
- subsystems: reftable backend (`refs/reftable-backend.c`), files backend (`refs/files-backend.c`), generic refs layer (`refs.c`)
- root cause: for symref updates, the new OID for the reflog was obtained by resolving the *new target* before the transaction commits, resulting in either the old branch value or no value at all
- solution: introduce `ref_transaction_resolve_new_oid()` in `refs.c`, a helper that resolves a ref’s new OID by walking the transaction’s updates (including symref chains) before falling back to `refs_resolve_ref_unsafe()`
- new symbols: `ref_transaction_resolve_new_oid()`, `find_ref_update()` (internal helper), `string_list_lookup()` (proposed replacement for linear lookup)
- behavior change: reflog entries for HEAD now record the correct new OID when HEAD and its target branch are updated in the same transaction, regardless of backend or update order
- broader architectural context: the helper aligns with the goal of moving all reflog logic into `refs.c` and could support future transaction-level conflict resolution (e.g., delete-and-recreate sequences)
- test coverage: new test script (`t/t1400-update-ref.sh`) exercises both update and create scenarios with varying update orders, verifying both the reflog message and the recorded OID for HEAD; proposed enhancements include testing transactions with `REF_TRANSACTION_ALLOW_FAILURE` and using subshells for cleanup
- files touched: `refs.c`, `refs-internal.h`, `refs/files-backend.c`, `refs/reftable-backend.c`, `t/t1400-update-ref.sh`

Open questions and loose ends:
- **implementation refinements**: whether to replace `find_ref_update()` with `string_list_lookup()` for O(log n) efficiency (medium weight; impacts maintainability)
- **edge-case handling**: whether reflog updates should be scheduled last in transactions to ensure all reference updates are known, and how to handle `REF_TRANSACTION_ALLOW_FAILURE` scenarios where a reference update fails after the reflog update (high weight; correctness risks)
- **test robustness**: whether to adopt subshells for test cleanup to avoid `-C repo` repetition (low weight; ergonomics)

This is a **substantive review** of brian m. carlson’s patch to fix the default object format in `git init` for Git v3. Junio C Hamano raises a critical edge case: what happens when `git init` is run in an *already initialized* repository under `WITH_BREAKING_CHANGES=1`? The current patch does not handle this scenario, and Junio’s test demonstrates that it silently overwrites the existing repository’s object format with the default (SHA-256), which may not be the intended behavior.

Junio outlines three possible behaviors for reinitializing an existing repository:
1. **Convert the repository** to the new default format (impractical).
2. **Preserve the existing format** and warn the user.
3. **Fail loudly** if the existing format differs from the default.

The current patch does none of these—it simply clobbers the existing format, which Junio argues is undesirable. His proposed test (included in the email) verifies that the object format remains unchanged after reinitialization, and he suggests that the patch should be updated to implement one of the three behaviors, with #2 (preserve and warn) being the most reasonable.

Junio also questions whether `git init` should similarly preserve the *reference storage format* (e.g., reftable vs. reffiles), though this is a separate concern and not directly addressed by the patch. Patrick Steinhardt is CC’ed for input on this point.

The review is **tested** (Junio includes a failing test case) and **substantive**, as it identifies a real-world edge case that could lead to unintended repository corruption. The patch is otherwise well-crafted, but this feedback suggests it needs revision to handle reinitialization safely. The discussion is now focused on design choices rather than correctness of the original fix.

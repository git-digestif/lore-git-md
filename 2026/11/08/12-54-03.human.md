This is a follow-up in the ongoing discussion about the inconsistent state left by `git switch` and `git checkout` when tracking setup fails. 井上司 (Tsukasa Inoue) now proposes a concrete implementation strategy for the "all-or-none" behavior that Junio C Hamano previously endorsed as a good direction.

The email explores two approaches to achieve atomicity in `git switch` and `git checkout`. The first (A) would bundle the branch ref and HEAD updates into a single transaction before updating the worktree, but this runs into practical issues: it blocks other ref updates during the transaction, interferes with `-m` (merge) operations that update HEAD, and exposes a reflog bug in the reftable backend. The second approach (B) performs a dry-run transaction as a pre-check, aborts it, then proceeds with the real updates after the worktree is updated. This avoids locking during the worktree update but leaves a small race window where another process could create the branch between the check and the commit, still resulting in a halfway state. 井上司 favors approach B, noting that it preserves existing behavior for `-m` and other processes while addressing the core issue.

The patch would touch `checkout.c` (specifically `switch_branches()`) and likely `branch.c` to handle the tracking config rollback. The proposal is well-motivated and addresses the technical constraints identified in earlier discussion, though it does not achieve perfect atomicity. Given Junio’s prior endorsement and the practical trade-offs, this looks like a serious, well-crafted effort to resolve a long-standing edge case. The remaining race condition is acknowledged but deemed acceptable for now.

This thread is about a **bugfix for the reftable backend** in Git, reported by 井上司 (Tsukasa Inoue). The issue is a correctness regression in reflog handling when HEAD is updated in the same transaction as its target branch.

Specifically, the bug causes two problems: (1) when HEAD is pointed at an existing branch that’s updated in the same transaction, the HEAD reflog incorrectly records the branch’s *old* value instead of the new one, and (2) when HEAD is pointed at a newly created branch in the same transaction, no HEAD reflog entry is written at all. The files backend handles both cases correctly, so this is a reftable-specific regression.

The root cause is in `write_transaction_table()` in `refs/reftable-backend.c`: for symref updates, the new OID for the reflog is fetched by resolving the *new target* before the transaction commits, which means it either sees the old branch value or (for new branches) no value at all. The author provides a minimal reproduction script and suggests a fix: using the OID from the target branch’s update in the same transaction instead of resolving the ref anew.

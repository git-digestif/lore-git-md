A bug in how HEAD's reflog is written during transactions that update both a symbolic reference and its target has been reported and fixed by 井上司 (Tsukasa Inoue), with the second version of the patch now under review. When HEAD and the branch it points to are updated in the same transaction, the reflog entry for HEAD could record the wrong OID or none at all, because the backends resolved the symref's new value by looking at the target before the transaction committed. The bug is visible in the reftable backend and also affects the files backend, where it was previously masked by non-atomic commit ordering.

The fix introduces a helper, `ref_transaction_resolve_new_oid()`, in the generic refs layer (`refs.c`) that resolves a ref's post-commit OID by walking the transaction's pending updates -- including symref chains -- before falling back to the current ref store. Both `refs/files-backend.c` and `refs/reftable-backend.c` now use it when writing symref reflog entries, so HEAD records the correct new OID regardless of update ordering or whether the target branch is updated or created in the same transaction. Version 2 of the patch incorporates substantive review feedback from Karthik Nayak: tests in `t/t1400-update-ref.sh` now run in subshells, cover the case where the target is updated through HEAD itself (which exposed the need for a linear scan rather than a lookup on the initially sorted update list), and include a `--batch-updates` test confirming that rejected updates do not pollute the reflog.

The patch is well-motivated with a clear reproduction, touches `refs.c`, `refs/refs-internal.h`, both ref backends, and the test script, and aligns with the longer-term goal of centralizing reflog logic in `refs.c`. It remains under review with no merge to `master` reported; it is expected to land in `next` once the review converges.

This thread is about a bug in Git’s reflog handling where HEAD reflog entries record the wrong OID—or are omitted entirely—when HEAD and its target branch are updated in the same transaction. The issue was originally reported by 井上司 (Tsukasa Inoue) and affects both the reftable and files backends, though it’s masked in the files backend due to its lack of atomic transaction support.

The discussion has converged on a generic fix in `refs.c`: a new helper function that returns the new OID of a ref updated in the same transaction, falling back to `refs_resolve_ref_unsafe()` if the ref isn’t part of the transaction. Karthik Nayak has now explicitly endorsed this approach, noting that it aligns with a broader architectural goal of centralizing reflog logic in the generic refs layer. The fix is expected to land soon, and while no formal test case has been posted yet, the provided reproduction script should serve as a foundation for test suite integration. The solution is designed to work for both backends, ensuring consistent behavior regardless of update order.

This thread is about a bug in Git’s reftable backend where reflog entries for HEAD are written with the wrong OID—or omitted entirely—when HEAD and its target branch are updated in the same transaction. The issue was reported by 井上司 (Tsukasa Inoue), who also provided a reproduction script and identified the root cause: the reflog’s new OID is resolved *before* the transaction commits, so it sees either the old branch value or nothing at all.

The discussion has now evolved from a targeted fix in the reftable backend to a more general solution. 井上司 proposes adding a helper function in `refs.c` that returns the new OID of any ref updated in the same transaction, allowing both the reftable and files backends to use it before falling back to `refs_resolve_ref_unsafe()`. This would fix the bug in both backends regardless of update order and pave the way for broader refactoring later. Karthik Nayak, who initially endorsed a simpler fix, has not yet weighed in on this new proposal, but the tone remains collaborative. No formal test case has been posted yet, but the existing reproduction script should make integration straightforward. The fix is expected to touch `refs/reftable-backend.c` and `refs.c`, with the new helper function as the only new symbol. The thread is still under review, with no prior version of the fix posted.

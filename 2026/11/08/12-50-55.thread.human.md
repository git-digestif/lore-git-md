This thread is about a bugfix for reflog handling in Git's reftable backend, where HEAD reflog entries were recording incorrect OIDs or being omitted when HEAD and its target branch were updated in the same transaction. The issue, reported by 井上司 (Tsukasa Inoue), also affected the files backend but was masked by its lack of atomic transaction support.

The fix is now implemented in a patch that introduces `ref_transaction_resolve_new_oid()`, a helper function in `refs.c` that resolves the new OID for a ref by walking the transaction's updates (including symref chains). This ensures HEAD reflog entries record the correct OID regardless of update order or backend. The patch touches the generic refs layer and both backends, and includes a new test script (`t/t1400-update-ref.sh`) that verifies the fix for both update and create scenarios.

The solution has strong support from both 井上司 and Karthik Nayak, who confirmed the root cause and endorsed the helper-based approach. The patch is well-motivated, with clear reproduction steps, a clean design, and thorough test coverage. It aligns with the broader goal of moving reflog logic into the generic refs layer, though deeper refactoring is deferred. Unless review uncovers edge cases, this fix is likely to land in `next` soon.

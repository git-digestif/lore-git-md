This thread is about a bug in Git’s reftable backend where reflog entries for HEAD are written with the wrong OID—or omitted entirely—when HEAD and its target branch are updated in the same transaction. The issue was reported by 井上司 (Tsukasa Inoue), who provided a reproduction script and identified the root cause: the reftable backend resolves the new OID for symref reflog entries *before* the transaction commits, leading to stale or missing values.

Karthik Nayak confirmed the problem and noted that the files backend avoids it only because it lacks atomic transaction support, implying the same bug would surface if atomicity were added. The discussion has settled on two potential fixes: a targeted solution (using the OID from the target branch’s update in the same transaction) and a more ambitious refactoring (moving reflog logic into the generic `refs.c` layer). While Karthik prefers the latter architecturally, he endorsed the former as a practical near-term fix. No patch has been posted yet, but the thread is collaborative, treating the issue as a real bug worth addressing. The reftable backend remains the only affected subsystem.

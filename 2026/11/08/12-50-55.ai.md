This is a **bugfix** targeting the **reftable backend**. The patch email reports a correctness regression in reflog handling when HEAD is updated in the same transaction as its target branch.

The issue manifests in two scenarios: (1) when HEAD is pointed at an existing branch that is updated in the same transaction, the HEAD reflog records the branch's *old* value instead of the new one; (2) when HEAD is pointed at a branch created in the same transaction, no HEAD reflog entry is written at all. The files backend handles both cases correctly by recording the new value.

The root cause is identified in `write_transaction_table()` in `refs/reftable-backend.c`: for symref updates, the new OID for the reflog is obtained via `refs_resolve_ref_unsafe()` on the *new target*, which reads the ref state *before* the transaction commits. This means it sees either the old branch value or (if the branch is new) no value at all, leading to incorrect or missing reflog entries.

The author (井上司) provides a minimal reproduction script using `git update-ref --stdin` with a transaction that updates a branch and HEAD in one operation. They also suggest a potential fix: using the OID from the target branch's update in the same transaction when available, rather than resolving the ref anew.

The email is well-structured: it states the problem, demonstrates it with a clear test case, explains the cause, and proposes a direction for the fix. The issue is narrowly scoped to the reftable backend and does not appear to affect other ref storage formats. This looks like a straightforward correctness bug with a plausible technical explanation, making it a strong candidate for a targeted fix.

This is a **reftable backend bugfix discussion** following up on the reported correctness regression in HEAD reflog handling during symref updates within transactions.

Karthik Nayak engages with 井上司’s analysis and confirms the root cause: the reftable backend’s `write_transaction_table()` resolves the new OID for symref reflog entries *before* the transaction commits, causing it to see stale or missing ref values. He notes that the files backend avoids this issue only because it lacks atomic transaction support—implying the same bug would surface if atomicity were added.

The discussion then shifts to potential fixes. 井上司 proposes a targeted solution: using the OID from the target branch’s update in the same transaction when available. Karthik endorses this as a practical, welcome fix but also floats a more ambitious alternative: moving reflog logic into the generic `refs.c` layer so that backends receive precomputed reflog entries, eliminating the need for per-backend conflict resolution. He acknowledges this would be complex but prefers it architecturally.

No patch has been posted yet, but the thread now has two clear technical directions: a narrow, immediate fix (likely forthcoming from 井上司) and a broader refactoring (unlikely to materialize soon). The tone is collaborative, with both participants treating the issue as a real bug worth addressing. The reftable backend remains the sole affected subsystem.

This is a follow-up in the `git switch`/`git checkout` tracking-configuration failure thread. 井上司 (Tsukasa Inoue) proposes a concrete implementation strategy for the "all-or-none" branch-switching behavior that Junio C Hamano previously endorsed as a good direction. The patch is not yet posted, but the email outlines a design choice between two transactional approaches (A and B) for coordinating ref updates, worktree changes, and HEAD movement.

The proposal targets the same subsystems as before: `branch.c` (tracking configuration), `checkout.c` (control flow in `switch_branches()` and `merge_working_tree()`), and the ref-transaction machinery. Approach B is favored because it avoids holding locks during the worktree update, which would otherwise break concurrent operations (e.g., `-m` autostash, other processes updating HEAD). The trade-off is that a race with another process creating the same branch between the check and commit phases could still leave the switch halfway. The tracking configuration would be written before the worktree update and rolled back if later steps fail. For `git switch -C` on the current branch, HEAD would be excluded from the transaction since it does not change.

井上司’s analysis confirms that approach A (holding the transaction during worktree updates) would block other ref updates and autostash steps, making it impractical. The email also references a separate reftable reflog bug that complicates approach A. No on-disk format changes are involved, and test coverage is not yet provided, though the reproduction steps from earlier in the thread remain relevant. The discussion is now focused on whether approach B’s race condition is an acceptable limitation given the complexity of full atomicity.

This is a **bugfix** targeting the index subsystem, specifically the interaction between `core.splitIndex` and `index.skipHash`. The patch by Tanga Joris fixes a critical bug that causes index corruption and crashes when both features are enabled. The root cause was that `write_shared_index()` named the shared index file after its trailing checksum, which is written as zeros when `index.skipHash` is enabled, leading to a filename of all zeros. The split index then recorded a null base OID, and `read_index_from()` treated this as "no shared index," silently discarding the entries.

The fix is straightforward: the patch ensures the hash is never skipped when writing the shared index, while still honoring `index.skipHash` for the main index file (which is written more frequently). The commit message is clear and includes a reproduction case, and the patch adds two new tests to `t/t1700-split-index.sh` to verify the fix and prevent regressions. The severity is high—this bug blocks users of split-index or skipHash optimizations (e.g., large repositories with `feature.manyFiles`), and the fix looks well-motivated and minimal.

This patch is part of the thread started by Andy Koppe, who reported the bug and confirmed the root cause. Tanga Joris, who identified the issue in their review, is now the author of the fix. There’s no maintainer response yet on merge status, but the patch is ready for review and addresses a real, user-facing problem. If you rely on split-index or skipHash, this is worth paying attention to.

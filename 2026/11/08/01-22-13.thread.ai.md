Subject: [PATCH v2 0/2] reflog: refactor expire cmd to use single loop for all refs

Originating author: Laveesh Bansal <laveeshb@laveeshbansal.com>
Thread type: patch (refactoring)

Core problem or goal
Refactor `git reflog expire` to consolidate two separate loops (one for `--all`, one for named refs) into a single loop, addressing a maintainer suggestion from an earlier fix (d1536ac3e2). The goal is to eliminate code duplication while preserving existing behavior in the first patch, then deliberately improve behavior in the second patch by deduplicating refs (e.g., if the same ref appears via `--all` and a command-line argument). The series justifies deduplication as a deliberate improvement rather than a bug fix, preserving `--verbose` output order and per-ref occurrence reporting.

Current status
Under review. v2 posted as a two-patch series: patch 1 for the mechanical refactoring (no behavior change), and patch 2 for deduplication. Both patches apply cleanly to `builtin/reflog.c`; core expiration logic (`refs_reflog_expire`) is unchanged. Author reports full test suite passes (including reflog tests with reftable, SHA-256, and leak sanitization). Junio C Hamano and Patrick Steinhardt have endorsed the approach, with Patrick’s feedback on commit message clarity and patch splitting now addressed. Patch 2 introduces deduplication via a `string_list` (`seen`) to track processed reflogs during iteration, skipping duplicates while preserving output order. The commit message explicitly addresses the `--updateref` edge case, but Patrick Steinhardt’s latest review questions whether this behavior is a bug rather than an improvement and suggests it should be documented as a potential regression risk. Additionally, Patrick highlights a performance trade-off: the current O(n² log n) complexity (due to repeated `string_list` lookups) could be reduced to O(n log n) by sorting and deduplicating the list once after collection, at the cost of output order.

Key technical details
- Files touched: `builtin/reflog.c` (both patches), new test in `t/t1410-reflog.sh` (patch 2).
- New/renamed symbols: none in patch 1; patch 2 introduces a `string_list` (`seen`) for deduplication.
- Behavior: patch 1 preserves all existing behavior (error reporting, exit status, output order, dynamic ref handling); patch 2 adds deduplication, skipping reflogs already processed in the same run while preserving output order. Command-line refs are still looked up during the loop via `repo_dwim_log` to handle dynamic refs (e.g., `@{-1}`). Deduplication avoids sorting to preserve order.
- On-disk format: no changes.
- Test coverage: existing reflog tests (`t/t1400-reflog.sh`, `t/t1419-reflog-expiry.sh`) plus reftable/SHA-256/leak sanitization runs; patch 2 adds a new test in `t/t1410-reflog.sh` to verify deduplication (e.g., `--all main refs/heads/main main` produces the same output as `--all` alone).
- Implementation: `collected.reflogs` string_list holds both worktree refs (from `--all`) and command-line arguments; `item->util` flags refs needing lookup. Per-reflog options (e.g., `--expire`, `--expire-unreachable`) apply to all refs in the loop, but dynamic-ref resolution (`repo_dwim_log()`) is conditional on `item->util`. Patch 2 uses a `string_list` to track processed reflogs during iteration.

Open questions and loose ends
- **`--updateref` edge case**: Patrick Steinhardt questions whether the current behavior—where `--updateref` could prune different entries depending on how many times a reflog is named—is a bug rather than an intentional improvement. He suggests this should be explicitly documented as a potential regression risk in the commit message.
- **Performance trade-off**: Patrick notes the current implementation’s O(n² log n) complexity (due to repeated `string_list` lookups) could be reduced to O(n log n) by sorting and deduplicating the list once after collection, but this would sacrifice output order preservation. He asks whether preserving order is a strict requirement.

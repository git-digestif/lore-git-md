Core problem or goal: Consolidate `git reflog expire`'s two separate loops (one for `--all`, one for named refs) into a single loop per maintainer suggestion from d1536ac3e2 review. Patch 1 is pure mechanical refactoring with zero behavior change; patch 2 adds deduplication of refs appearing via both `--all` and command-line arguments.

Current status: Under review. v3 posted as two patches: patch 1 (v3 1/2, identical to v2) performs the mechanical unification, patch 2 (v3 2/2) adds `strset`-based deduplication. Both apply cleanly to `builtin/reflog.c`; core expiration logic (`refs_reflog_expire`) unchanged. Author reports full test suite passes (reftable, SHA-256, leak sanitization). Junio C Hamano and Patrick Steinhardt endorse the approach. Author has now sent a review-response email confirming how v3 addresses Patrick Steinhardt's two substantive concerns from the v2 review.

Key technical details: Files touched: `builtin/reflog.c` (both patches), `t/t1410-reflog.sh` (patch 2). Patch 1 implementation: collects all reflogs into single `collected.reflogs` string_list before processing--worktree reflogs from `--all` via `collect_reflog` appended first, then command-line arguments. Each command-line entry marked `item->util = (void *)1` to flag need for `repo_dwim_log` resolution (dynamic refs like `@{-1}`); `--all` entries use resolved names directly. Single `for_each_string_list_item` loop iterates combined list, performs `repo_dwim_log` lookup only when `item->util` set, calls `refs_reflog_expire` once per reflog with identical callbacks (`reflog_expiry_prepare`, `should_prune_fn`, `reflog_expiry_cleanup`). Patch 2 implementation: introduces `struct strset seen` (from `strmap.h`) in `cmd_reflog_expire()`; before calling `refs_reflog_expire()` for any refname, code checks `strset_add(&seen, refname)` and skips if already processed, ensuring O(1) hash-based lookups (resolving v2's O(n^2 log n) performance concern and explicitly rejecting Patrick's O(n log n) sorting suggestion to preserve expiration order) while preserving `--verbose` output order. Preserving original expiration order matters because `--updateref` can move branch tips and "HEAD" is checked against every ref tip, making pruning outcomes order-dependent. Known limitations documented in commit message: deduplication does not catch names resolving to same reflog through worktree prefixes (e.g., "HEAD" vs "main-worktree/HEAD") or names that do not exist, which may still be processed or reported twice. No on-disk format changes. Tests: existing `t/t1400-reflog.sh`, `t/t1419-reflog-expiry.sh`; patch 2 adds deduplication tests in `t/t1410-reflog.sh` (e.g., `--all main refs/heads/main main` equals `--all` alone) and a dedicated `--updateref` edge case test constructing a `topic` branch scenario where duplicated ref name previously could lose reflog entries via tip movement between passes.

Open questions and loose ends: `--updateref` semantics classification (bug vs. deliberate improvement) remains philosophically unsettled despite v3 documenting it as intentional behavior change in commit message with test coverage; Patrick Steinhardt raised the question in v2 review and the author has now confirmed documentation approach but the classification itself remains open. Known limitations remain: worktree-prefix aliasing and non-existent names are not deduplicated.

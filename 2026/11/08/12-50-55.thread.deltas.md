## 2026/11/10

- [2026/11/10/13-34-57 by tsukasa inoue <inoue.tsukasa.4@gmail.com>] tsukasa inoue submitted a patch adding `ref_transaction_resolve_new_oid()`, which resolves a refname to the object ID it will have once the transaction commits by taking the new value from the transaction when it updates the target (following symref updates within the transaction) and reading the ref store otherwise; both the files and reftable backends now use this function instead of `refs_resolve_ref_unsafe()` when writing reflog entries for symref updates, so the reflog records the target's new value even when the target is created or updated in the same transaction.
- [2026/11/10/13-34-57 by tsukasa inoue <inoue.tsukasa.4@gmail.com>] The patch adds tests in `t/t1400-update-ref.sh` covering both `update` and `create` actions for the target ref and both `branch-first` and `head-first` command ordering, verifying that `git update-ref --stdin` with a `symref-update HEAD` logs the target's new value in HEAD's reflog.
- [2026/11/10/13-34-57 by tsukasa inoue <inoue.tsukasa.4@gmail.com>] tsukasa inoue noted that, as discussed with Karthik, this change only moves the lookup of the target's new value to `refs.c`; moving the rest of the reflog logic out of the backends and resolving conflicting updates within a single transaction are left for later.

# Thread deltas

## 2026/11/08

- [2026/11/08/12-50-55 by 井上司 <inoue.tsukasa.4@gmail.com>] 井上司 reported that with the reftable backend, a transaction updating a branch and pointing HEAD at it records the branch's old value in the HEAD reflog (or writes no entry if the branch is created in the same transaction), unlike the files backend; identified write_transaction_table() in refs/reftable-backend.c as the cause because refs_resolve_ref_unsafe() reads pre-transaction refs; proposed taking the new oid from the target's update in the same transaction as a fix, motivated by work on "git switch -c".
- [2026/11/08/22-18-04 by Karthik Nayak <karthik.188@gmail.com>] Karthik Nayak noted that the files backend avoids the bug only because it lacks atomicity support, agreed without code review that the diagnosed cause is plausible, and suggested that while the proposed fix would work, moving reflog logic to the generic refs.c layer so backends receive pre-resolved reflog entries would prevent the same bug in any future atomic backend; he preferred the generic approach but stated the specific fix would also resolve the issue and be welcome.

## 2026/11/09

- [2026/11/09/01-39-16 by 井上司 <inoue.tsukasa.4@gmail.com>] 井上司 corrected his earlier claim that the files backend gets the HEAD reflog right in both cases: with "symref-update HEAD" queued before the branch update, files also records the old oid, or writes no entry when the branch is created in the same transaction, so the bug is not specific to reftable.
- [2026/11/09/01-39-16 by 井上司 <inoue.tsukasa.4@gmail.com>] 井上司 proposed adding a helper in refs.c that returns the new oid of a ref updated in the same transaction, for both backends to use before falling back to refs_resolve_ref_unsafe(), which would fix both backends regardless of update order and allow one test to cover both.
- [2026/11/09/15-23-52 by Karthik Nayak <karthik.188@gmail.com>] Karthik Nayak confirmed the bug is bigger than just reftables, endorsed the proposed helper as a good start while looking forward to the patch, and added that in-transaction conflict resolution (e.g., a delete followed by a create of the same ref currently failing) is a related area of interest.

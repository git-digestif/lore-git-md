This is a **bugfix** targeting the index subsystem, specifically the interaction between `core.splitIndex` and `index.skipHash`. Tanga Joris provides a patch that fixes the critical corruption and crash bug reported by Andy Koppe, where enabling both `core.splitIndex` and `index.skipHash` caused silent data loss (null OIDs in the shared index) and crashes in `git status`.

The patch addresses the root cause: `write_shared_index()` names the shared index file after its trailing checksum, which is written as zeros when `index.skipHash` is enabled. This results in a filename of all zeros, causing the split index to record a null base OID. The fix ensures the shared index always includes its hash, regardless of `index.skipHash`, while still allowing the main index file to skip the hash for performance. The commit message explains the trade-off: shared indexes are written infrequently, so the cost of including the hash is minimal, while the main index benefits from skipping it on every update.

The patch touches `read-cache.c` to modify `do_write_index()` and `write_shared_index()`, adding a `skip_hash` parameter to control whether the hash is omitted. It also updates `t/t1700-split-index.sh` with two new tests: one verifies that `index.skipHash` does not apply to the shared index, and another ensures the first entry in split mode is not lost. The tests are thorough, checking file existence, hash values, and output correctness with `git ls-files` and `git status`.

This is a well-motivated fix with clear reproduction steps and test coverage. The severity is high—index corruption and crashes are showstoppers for users relying on split-index or skipHash optimizations (e.g., large repositories with `feature.manyFiles`). The patch is narrowly scoped, focusing only on the shared index filename generation, and does not introduce broader changes.

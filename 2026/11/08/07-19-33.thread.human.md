This thread is about a documentation patch (v2) by Hussain Sitamouwala that clarifies how Git’s partial clone feature orders and falls back between promisor remotes when fetching missing objects. The patch explains that Git first tries remotes advertised by the server ("accepted promisor remotes") and, if a fetch fails, falls back to the next remote for any remaining missing objects.

Junio C Hamano, the maintainer, has raised procedural and editorial concerns. Initially, he noted that v2 was sent prematurely (before v1 review concluded) and wasn’t threaded as a reply to v1. He also requested a wording change, replacing "next remote" with "other promisor remotes." In the latest email, Junio refines his editorial feedback further, proposing to remove an entire sentence about fallback behavior as redundant, since the fallback is already implied by the phrase "one after the other." Hussain has acknowledged the earlier feedback and agreed to implement the changes in v3, but no technical review of the documented behavior itself has occurred yet.

The patch touches `Documentation/technical/partial-clone.adoc`, introducing terms like "accepted promisor remotes" and referencing the `try_promisor_remotes()` function and a specific commit (8808e61fd3, April 2026). The thread remains under review, with no merge status reported. Hussain will need to address both the threading issue and Junio’s latest editorial suggestion in the next iteration.

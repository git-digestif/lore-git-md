This is a design discussion reply within the `kh/format-rev-more-options` thread, not a patch. Kristoffer Haugsbakk responds to D. Ben Knoble's proposal to split `git format-rev` by mode, clarifying which functionality justifies the command's continued existence.

Haugsbakk agrees that the `--stdin-mode=text` mode -- which scans arbitrary input text and replaces commit hashes with human-readable references -- remains the unique capability that warrants keeping `git format-rev` at all. He concurs that if the `--stdin-mode=revs` mode (formatting revision ranges) were removed or migrated elsewhere, the command should be simplified to just `git format-rev` without the mode flag, and he sees little value in retaining both modes within a single command.

He pushes back on using `git diff-tree` as the replacement for the revs mode, describing it as completely undiscoverable for commit-log-style usage. Specifically, he notes that invoking `git diff-tree -v --always --no-patch` reads confusingly ("do a diff verbosely, always, without a diff"), requiring users to know that `-v` or `--format=...` is needed to emit commit information and `--always` is needed to counteract the default suppression of merge commits with no diff output. This opacity makes diff-tree an unsuitable discoverable interface for the revs-mode use case.

Haugsbakk states he is entirely fine with removing the revs mode or the command altogether, provided no other contributor wants to keep it as a wrapper or "skin" around the diff-tree options. For his own workflow, he now knows the diff-tree invocation or can write wrappers, so the practical impact is minimal. The open question remaining in the thread is whether the broader community sees enough value in a simplified text-only `git format-rev` to justify merging the current options series, or whether the revs functionality should be preserved through a different interface despite its current home being questioned.

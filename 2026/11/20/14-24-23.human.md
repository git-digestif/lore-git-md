This is a feature patch, specifically the third of four in Harald Nordgren's v9 series extending `git branch --delete-merged` to recognize branches whose changes landed upstream through rebases or squash merges. The patch introduces the new `--delete-integrated <pattern>` option, which behaves like `--delete-merged` but also deletes a branch when some upstream commit since the fork point contains the branch's exact version of every file it changed, even if the branch tip itself is not reachable. When such a commit is found, the output names it explicitly (`Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`) so the user can see where the work went.

The implementation lives in `builtin/branch.c` and walks upstream commits in reverse chronological order, using a commit slab to cache which paths each upstream commit touches, then compares tree entries to check whether every path the branch modified matches the branch's blob OIDs and modes at some upstream commit. The option cannot be combined with `--delete-merged` (they are mutually exclusive), respects the `branch.<name>.deleteMerged=false` opt-out, and works with `--dry-run`. Documentation updates cover both `git branch` and the branch config man page, while `t/t3200-branch.sh` gains 176 lines of tests covering rebase-merged, squash-merged, reverted, and partially-landed scenarios.

Within the series context, this patch 3/4 carries the core detection machinery and the CLI wiring, building on patch 1/4's refactoring of the opt-out check and patch 2/4's landing-message helper, while patch 4/4 adds the more complex `ll_merge()`-based logic for handling upstream modifications. Reviewers have treated 3/4 as uncontroversial; Junio previously confirmed the CLI design and the only feedback on this patch was a variable rename (`opt` to `diffopt`) already addressed in earlier versions. The series remains under review with no integration status announced, though the author has requested it be picked up.

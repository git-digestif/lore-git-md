Abhishek Agarwal has sent a standalone bugfix patch making `git submodule update --jobs` handle zero and negative values consistently with `git fetch --jobs` and the `submodule.fetchJobs` config: since commit 51243f9f0f, `--jobs=0` hit a `BUG()` abort while `--jobs=-1` produced a misleading memory error. The patch adds validation in `module_update()` in `builtin/submodule--helper.c` -- dying on negative values and substituting `online_cpus()` for zero -- plus matching documentation wording in `git-submodule(1)` and `git-clone(1)`, and three new test cases in `t/t7406-submodule-update.sh`.

The patch has now received substantive reviews from two maintainers-level contributors. Jacob Keller added a `Reviewed-by` trailer endorsing the approach with no objections, and Junio C Hamano has now given his approval ("Looking good. Thanks."), confirming the diagnosis by tracing the code path and explicitly accepting both the zero-means-`online_cpus()` behavior and the "reasonable default" documentation phrasing. Junio's review also flagged a related edge case tagged `#leftoverbits`: in `builtin/clone.c`, `cmd_clone()` uses `-1` as a sentinel for "no explicit value set", so `git clone --recurse-submodules --jobs=-1` is silently ignored rather than forwarded and rejected -- an inconsistency he suggests could be fixed later but does not consider blocking.

The patch remains under review with no integration-branch status recorded; the thread is now effectively awaiting Junio's decision on queuing it, with the clone.c `-1` sentinel behavior as the only noted loose end.

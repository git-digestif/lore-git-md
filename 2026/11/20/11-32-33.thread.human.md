Abhishek Agarwal posted a single bugfix patch addressing how `git submodule update --jobs` handles zero and negative values. Since commit 51243f9f0f, passing `--jobs=0` triggers a `BUG()` abort, while `--jobs=-1` produces a misleading "data too large to fit into virtual memory space" error; before v2.39, values below 1 silently fell back to `online_cpus()`. The patch adds validation in `module_update()` in `builtin/submodule--helper.c` -- dying with "'--jobs' cannot be negative" for negative input and substituting `online_cpus()` for zero, mirroring the treatment of `submodule.fetchJobs` and the earlier fix for `git fetch --jobs` (commit c39952b925). It also updates the `git-submodule(1)` and `git-clone(1)` documentation to say "A value of 0 will use some reasonable default" and adds three test cases to `t/t7406-submodule-update.sh` covering zero, negative rejection, and propagation through `git clone --recurse-submodules --jobs 0`.

Jacob Keller replied with a `Reviewed-by` endorsement. His review is surface-level rather than deeply technical: he raised no bugs or change requests, only commenting that the documentation wording -- while potentially debatable as to what counts as a "reasonable number of jobs" -- acceptably matches the phrasing used for `git fetch --jobs`.

The patch remains under review with no maintainer decision or integration-branch status recorded, and no outstanding technical objections are on the table.

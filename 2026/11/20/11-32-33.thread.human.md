This thread is a single-patch bugfix from Abhishek Agarwal addressing broken handling of zero and negative values to `git submodule update --jobs`. The regression traces back to commit 51243f9f0f (2022-10-12), which removed the automatic fallback to `online_cpus()` from the run-command API and left individual option parsers to handle it; `builtin/submodule--helper.c` never got that handling, so `--jobs=0` now aborts with "you must provide a non-zero number of processes!" and `--jobs=-1` dies with a confusing "data too large to fit into virtual memory space" error. Prior to v2.39, any value below 1 silently meant the CPU count.

The fix adds a few lines to `module_update()` in `builtin/submodule--helper.c`: negative values now die with "'--jobs' cannot be negative", and zero falls back to `online_cpus()`, mirroring the precedent set by commit c39952b925 for `git fetch --jobs` and aligning the option with the already-correct `submodule.fetchJobs` config variable. The patch also updates the `git-submodule(1)` and `git-clone(1)` man pages to document that a value of 0 uses a reasonable default, and adds three tests to `t/t7406-submodule-update.sh` covering `--jobs 0`, negative rejection, and propagation through `git clone --recurse-submodules --jobs 0`.

The patch is newly posted and under review; no maintainer feedback or merge status has been recorded yet.

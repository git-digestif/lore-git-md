This is patch 7/8 in Christian Couder's v2 series, and it is the core bugfix: it ensures protocol v2 `fetch` commands send the `promisor-remote=...` reply. The preceding six patches refactored client-side capability writing so that `write_command_and_capabilities()` in `connect.c` is the single function emitting capability lines; this patch applies that unified path to the fetch request.

The change modifies `do_fetch_pack_v2()` in `fetch-pack.c` to build a `struct strvec capabilities` once using the helpers `add_server_options()` and `add_promisor_remote_reply()`, then passes that list to `send_fetch_request()`. That function's signature gains a `const struct strvec *capabilities` parameter and forwards it to `write_command_and_capabilities()` instead of constructing a local capability list that omitted the promisor-remote reply. The old call to `promisor_remote_reply()` in `do_fetch_pack_v2()` -- which only marked accepted remotes locally without sending anything on the wire -- is removed.

This fixes fetch failures with stateless servers (HTTP smart protocol, JGit, Gerrit) where separate upload-pack processes handle `ls-refs` and `fetch`, so acceptance recorded during `ls-refs` is not visible at `fetch` time. It also fixes object-ID-only fetches that skip `ls-refs` entirely. Negotiation-only requests sent by `negotiate_using_fetch()` do not ask for a pack and therefore do not receive the reply.

Tests are added to `t/t5710-promisor-remote-capability.sh` to verify via `GIT_TRACE_PACKET` that the `promisor-remote=lop` line appears in `command=fetch` requests during clone and during a fetch of a bare object ID. A new test script `t/t5711-promisor-remote-capability-http.sh` (registered in `t/meson.build`) exercises the same scenario over HTTP, confirming the server lazily fetches the missing object from the promisor remote and that the reply is present in the traced fetch request.

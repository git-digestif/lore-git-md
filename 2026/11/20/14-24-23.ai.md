This is a feature patch, specifically the third of four in Harald Nordgren's v9 series adding `git branch --delete-integrated <pattern>`. It introduces the core machinery for change-based branch deletion: when a branch's tip is not reachable from the upstream (as after a rebase or squash merge), the new flag walks upstream commits since the merge base and deletes the branch if any single commit contains the branch's exact version of every file the branch changed. The output names that commit, e.g. `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6).`

The patch touches `builtin/branch.c`, `Documentation/git-branch.adoc`, `Documentation/config/branch.adoc`, and `t/t3200-branch.sh`. It adds the `DELETE_BRANCH_INTEGRATED` flag and the `--delete-integrated` option, which is mutually exclusive with `--delete-merged`. Internally it defines `struct branch_change` (recording path, blob OID, and mode relative to the merge base) and `struct landing_search`, then uses `find_landed_commits()` to compute merge bases, collect changed paths via `diff_tree_oid`, and walk upstream commits in reverse looking for one where `changes_landed()` returns true via exact tree-entry comparisons. A commit-slab cache (`changed_paths`) avoids recomputing which paths each upstream commit touches. The `branch.<name>.deleteMerged` config opt-out now applies to both flags, and `--dry-run` works with either.

This patch implements detection purely at the tree level -- comparing blob OIDs and modes without reading file contents -- so it stays cheap in partial clones and handles rebase merges plus squash merges where upstream did not modify the same files. Patch 4/4 of the series extends this with `ll_merge()`-based three-way merging to also catch squash merges where upstream edited the same files before integration, and adds the `base_mode` field that fixes the gitlink-to-blob crash fixed in v9.

Tests in `t/t3200-branch.sh` cover rebase-merged deletion, squash-merged deletion, reverted squash merges, mixed merged/unmerged reporting, and flag incompatibility. The series remains under review; this particular patch was previously reviewed by Junio with only a variable-rename nit (addressed in v6) and is considered uncontroversial. The known limitation -- false positives when an unrelated author independently makes identical changes (the "npm update" scenario) -- remains unaddressed in this patch and is left for future author-check or patch-id mitigations.

This is a bugfix for the UTF-8 display-width calculation, specifically the third patch in a v3 four-patch series from Dirk Gouders. The patch targets `utf8_strnwidth()` in `utf8.c`, which computes the column width of a string while optionally skipping ANSI escape sequences. The issue is that when `skip_ansi` is enabled and an ANSI escape sequence consumes bytes up to or beyond the given `len` boundary, the function previously proceeded to call `utf8_width()` on a string pointer that had reached or passed the `end` boundary, risking an out-of-bounds read or an incorrect width count. The fix adds a guard after the ANSI-skipping loop: if `string >= end`, the loop breaks immediately rather than attempting to decode a glyph from beyond the buffer.

The patch also adds unit tests in `t/unit-tests/u-utf8-width.c` under a new `test_utf8_width__strnwidth_ansi()` function. These tests exercise three corner cases using the string `"\033[31mhello"` with length arguments of 4, 5, and 6, verifying that escape sequences ending exactly at the boundary do not produce phantom glyph counts or overrun the string.

Old behavior: after skipping ANSI sequences, the code unconditionally called `utf8_width(&string, NULL)`, even if the escape sequence had consumed the entire remaining input up to the boundary. New behavior: if the pointer reaches or exceeds `end` after skipping, the loop terminates early, returning only the width accumulated so far.

This is a small, well-scoped correction (10 lines changed in `utf8.c`, 11 lines of tests added) with concrete reproduction cases. As patch 3/4 in the series, it likely depends on or complements earlier patches in the same thread, though the cover letter was not provided here. Follow-up discussion would most likely focus on whether the `>=` boundary check is sufficient for all callers or if similar guards are needed elsewhere `display_mode_esc_sequence_len()` is used.

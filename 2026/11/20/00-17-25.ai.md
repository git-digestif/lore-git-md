This is a follow-up reply from Tanga Joris in the ongoing bugfix thread for the `git apply --check` crash (assertion `patch->is_new <= 0` in `check_preimage()`), confirming the planned v4 behavior in response to Junio C Hamano's question about whether Git historically emitted bare `diff --git` lines.

Tanga confirms that Git did produce a bare `diff --git` line with no following headers only in 2005, when commit `206de27efa` (git-apply: ignore empty git headers) was written and `diff.c` printed the header before determining whether anything changed. A few months later commit `ec1fcc16af` added the `index` line, and modern Git cannot be made to emit a bare `diff --git` line even for whitespace-only changes, renames, or merges, so the assumption that such output is not generated today holds.

For v4, Tanga states that `find_header()` will treat any line starting with `diff --git ` as the start of a Git patch even between patches, as it already does, but will now stop with a "corrupt patch" error when no extended header lines follow it, rather than skipping and continuing. This covers the blank-line and indented `new file mode` cases from v1. Non-patch material appearing between complete patches will continue to be ignored so email commentary remains allowed, and patches beginning with a plain `diff` that is not `diff --git` will still flow through the existing third-party diff code paths unchanged; the only behavioral change for those is when a bare `diff --git` line immediately precedes them, which the v3 commit message already noted.

This reply confirms convergence on the v4 design: dropping patch 1/3 (the memory-leak fix in `parse_git_diff_header()`) in favor of immediate rejection of empty `diff --git` sections in `find_header()`, simplifying patch 2/3 while keeping the strict rejection of malformed Git-generated headers endorsed by the maintainer.

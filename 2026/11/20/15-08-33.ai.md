This is a bugfix for `git rev-parse` affecting SHA-256 repositories that enable SHA-1 compatibility via `extensions.compatObjectFormat`. When a user passes `--output-object-format=sha1` for an object that predates the repository's SHA-1 compatibility (and therefore has no SHA-1 mapping), the command previously printed the SHA-256 hash anyway, silently returning a wrong value. The patch makes this case an error instead.

The change is in `builtin/rev-parse.c` inside `cmd_rev_parse()`, where the `output_algo` conversion path now checks the return value of `repo_oid_to_algop()`. Previously the code called this function unconditionally and ignored failure; now it calls `die()` with the message "cannot map object %s to %s" if the object cannot be converted to the requested algorithm, preventing misleading output.

The commit message includes a concrete reproduction: run `git init --object-format=sha256`, write an object with `git hash-object -w --stdin`, set `extensions.compatObjectFormat sha1`, then invoke `git rev-parse --output-object-format=sha1 <oid>`. Because the object was created before the compatibility extension was configured, it has no SHA-1 counterpart, so the old code emitted the SHA-256 hex while the new code exits with an error naming the object and target format.

The patch is small and surgical, touching only four lines in one file with a clear commit message that explains the edge case. It addresses a genuine correctness issue in plumbing output, though it does not include additions to the `t/` test suite.

Potential points of contention in review might include whether a hard `die()` is the appropriate interface versus emitting a warning or empty output, and whether the compatObjectFormat interaction deserves regression tests in `t/t1006-*` or similar. The fix sits at the intersection of the object-format abstraction layer and the rev-parse output formatting path.

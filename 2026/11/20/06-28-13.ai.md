This is a **substantive review** of a test-infrastructure patch, specifically Junio C Hamano's response to Kaartic Sivaraam's `[PATCH v2]` that serializes `EXPENSIVE` tests in `t/test-lib.sh` to prevent OOM kills on CI runners.

Junio identifies two serious concurrency flaws in the proposed `acquire_expensive_lock_()` / `release_expensive_lock_()` mechanism. First, a TOCTOU race: if waiter T2 reads the `pid` file just before lock-holder T1 releases and exits, while waiter T3 concurrently acquires the lock, T2 will see T1's PID as dead, run `rm -rf "$expensive_lock_"`, and delete T3's active lock -- allowing T2 and T3 to run `EXPENSIVE` tests concurrently. Second, and more critically, a signal-handling window: a process can receive INT/TERM/HUP after successfully running `mkdir "$expensive_lock_"` but before writing its PID to the `pid` file or setting `have_expensive_lock_=t`; the `die()` EXIT trap will then call `release_expensive_lock_()`, which returns early because `have_expensive_lock_` is unset, leaving an empty lock directory that no waiter will ever clear (since `kill -0` is skipped when `owner` is empty), causing a permanent deadlock. Junio explicitly notes that the deadlock scenario is "far worse" than the race condition.

The review is precise and authoritative, tracing specific interleavings of three concurrent processes and the signal-delivery timing relative to the `mkdir` and `echo $$` operations in `t/test-lib.sh`. It does not yet propose a fix, but the severity assessment suggests the current v2 implementation cannot be accepted as-is. The thread remains open with these correctness issues unresolved.

This is a bugfix for `git submodule update --jobs` that aligns the CLI option with the behavior of the `submodule.fetchJobs` configuration variable. Currently, passing `--jobs=0` causes a hard abort with a BUG() assertion, and a negative value produces a misleading "data too large to fit into virtual memory space" error. The same problem affects `git clone --recurse-submodules --jobs=0`, which forwards the value to the update command.

The commit message traces the regression to v2.39, when `run_processes_parallel()` stopped falling back to `online_cpus()` for values below 1 and instead began treating 0 as a programming error. While `git fetch --jobs=0` was subsequently fixed to restore the sensible default, and `submodule.fetchJobs` already dies on negative input, the `--jobs` option on `submodule update` was overlooked. The patch brings the option into agreement with both: a value of 0 now resolves to `online_cpus()`, and negative values are rejected with a clear error message.

The fix itself is minimal, adding a six-line guard in `module_update()` in `builtin/submodule--helper.c` that checks the parsed integer before use. The author also updates the `--jobs` documentation in both `git-submodule(1)` and `git-clone(1)` to state that 0 uses a reasonable default, matching the wording already used for `git fetch --jobs`. Three new tests in `t/t7406-submodule-update.sh` verify the 0-case via `GIT_TRACE`, the negative-value rejection, and the `git clone --recurse-submodules` path.

This looks like a well-crafted, low-risk fix: the motivation is clearly documented with specific commit references, the behavior change is conservative (restoring pre-v2.39 semantics for 0 and rejecting only values that have been broken since that release), and the test coverage addresses both the direct command and the clone passthrough.

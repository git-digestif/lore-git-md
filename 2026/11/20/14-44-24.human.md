This is a bugfix targeting the UTF-8 ANSI escape-sequence handling, and it is the first patch in a four-patch v3 series. The change introduces an optional end-bounds parameter to `display_mode_esc_sequence_len()` so that the function can safely operate on counted buffers without scanning past their end.

The commit message explains that the function previously relied on NUL termination to stop scanning for ANSI display-mode sequences (such as `\033[1;31m`), but several callers -- notably `utf8_strnwidth()`, `strbuf_utf8_replace()`, and `strbuf_add_wrapped_text()` -- work with explicit lengths rather than NUL-terminated strings. Without a bound, these callers risked reading beyond the buffer. The new signature accepts a `const char *end` pointer; when non-NULL, the function never dereferences `*end` or anything past it, and when NULL it preserves the old NUL-terminated behavior.

The patch updates all in-tree callers to pass the appropriate end pointer: `format_and_pad_commit()` in `pretty.c` now passes `ch + 1`, while the three `utf8.c` call sites compute `end` from the known buffer length. It also adds a new clar unit-test suite (`t/unit-tests/u-utf8-ansi.c`) covering NUL-terminated inputs, bounded inputs, and edge cases such as swapped start/end pointers.

The commit message references a prior discussion with Andy Koppe about O(n²) performance risks in similar string-processing loops, and explicitly notes that this particular change does not introduce that risk. Overall the patch looks well-motivated and carefully constructed: it addresses a concrete out-of-bounds read hazard, updates every caller consistently, and ships with thorough test coverage.

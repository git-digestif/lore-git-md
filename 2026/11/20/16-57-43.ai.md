This is a **design discussion reply** in the promisor-remote protocol v2 bugfix thread, not a patch itself. Christian Couder responds to Junio C Hamano's insistence that the duplicated capability-sending logic in `connect.c` be refactored before layering on the promisor-remote fix, pointing out that the v2 series he just submitted already performs exactly that refactoring rather than deferring it. The series expands from 3 to 8 patches, with 6 dedicated to unifying the three client-side functions that emit capability lines -- `send_capabilities()`, `get_remote_refs()`, and `write_command_and_capabilities()` -- into a single `write_command_and_capabilities()` path that accepts a `const struct strvec *capabilities` (and later a `struct packet_reader *`). The diffstat grows from 196 to 322 insertions, with `connect.c` absorbing the bulk of the churn at 128 lines changed and the complete deletion of `send_capabilities()` in patch 6/8.

New helper functions `add_server_options()` and `add_promisor_remote_reply()` construct the capability strvecs, while patch 7/8 routes `do_fetch_pack_v2()` in `fetch-pack.c` through `send_fetch_request()` with the new capabilities parameter so the `promisor-remote=...` reply is sent with every pack-requesting `fetch` command -- the core bugfix for stateless HTTP servers that has existed since Git v2.49. Patch 8/8 updates `Documentation/gitprotocol-v2.adoc` to mandate that clients send this reply with each fetch due to protocol v2's statelessness. Test coverage expands with a new `t/t5711-promisor-remote-capability-http.sh` (registered in `t/meson.build`) plus `GIT_TRACE_PACKET` assertions in `t/t5710-promisor-remote-capability.sh` and `t/t5705-session-id-in-capabilities.sh` to verify wire-level capability ordering.

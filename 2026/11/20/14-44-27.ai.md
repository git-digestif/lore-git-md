This is the fourth and final patch of a four-patch bugfix series (`[PATCH v3 0/4]`) by Dirk Gouders that fixes buffer-bounds handling in Git's UTF-8 display-width code. The series targets `utf8_strnwidth()` and `utf8_width()` in `utf8.c` to prevent reads past the end of the input buffer, including the mmapped-region SIGBUS edge case, and to correct misleading documentation.

This specific patch modifies `utf8_strnwidth()` so that instead of calling `utf8_width(&string, NULL)`, it computes `remainder = end - string` before each call and passes `&remainder`. This ensures the width calculation respects the caller-supplied `len` argument and does not consume bytes beyond the boundary, which previously could cause `utf8_width()` to interpret a truncated multibyte sequence as extending past `len`. The patch also introduces a new helper, `display_mode_esc_sequence_len_all(const char *start, const char *end)`, which greedily consumes all consecutive leading ANSI SGR sequences up to `end`, and switches the ANSI-skipping loops in `utf8_strnwidth()`, `strbuf_add_wrapped_text()`, and `strbuf_utf8_replace()` to use this new function rather than repeated single-sequence calls.

Files touched are `utf8.c`, `utf8.h`, and the unit-test files `t/unit-tests/u-utf8-ansi.c` and `t/unit-tests/u-utf8-width.c`. The new tests verify the greedy ANSI-sequence counter (`test_utf8_ansi__sgr_len_greedy`) and confirm that `utf8_strnwidth()` returns the correct width when a CJK character is chopped by the `len` argument (`test_utf8_width__strnwidth_cjk_chopped`, e.g. `utf8_strnwidth("三bytes long...", 1, 1)` returns 1). The header gains a prototype for `display_mode_esc_sequence_len_all()`.

Within the series, this patch builds directly on patch 1 (authored by Junio C Hamano), which established the end-pointer API `display_mode_esc_sequence_len(const char *s, const char *end)`. By passing an explicit remainder to `utf8_width()`, patch 4 completes the bounds-safety fix for the width-measurement path, ensuring that incomplete multibyte sequences at the `len` boundary are handled correctly. The series is under review with the end-pointer design settled; no v4 has been posted.

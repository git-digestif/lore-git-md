Steven Rostedt has started a new thread on the Git mailing list asking whether Git could offer a safety configuration for `git reset --hard`. After recently losing uncommitted work by running the command in the wrong directory, he proposes that a new config option (likely under a `reset.*` namespace) could make `git reset --hard` detect a dirty working tree and prompt for confirmation before discarding changes. He offers no patch and no specific config key name -- this is purely a design question about whether such a safeguard is feasible and desirable.

Since this is the opening message, there is nothing yet to decide: no implementation has been proposed, no reviewers have weighed in, and the thread has not produced a patch series. The open questions are the ones any follow-up will have to answer -- how the prompt would interact with the other reset modes (`--soft`, `--mixed`, `--keep`, `--merge`), whether it could be skipped with a command-line flag, and where the code would live (plausibly `builtin/reset.c` plus config parsing).

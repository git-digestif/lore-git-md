Steven Rostedt opened a design discussion asking whether Git could gain a safety mechanism -- such as a configuration option or pre-command hook -- to make `git reset --hard` prompt for confirmation when the working tree has uncommitted changes, motivated by a desire to avoid accidentally discarding work when the command is run in the wrong directory. Mirko Faina proposed a concrete approach: a `reset.*` config key that would make the existing `--keep` behavior the default for `--hard`, with a `--force` flag to bypass the check. Junio C Hamano rejected any modification to the semantics of `git reset --hard`, arguing that altering the destructive behavior of a widely-adopted command would break automation and scripts, and urged instead that the root workflow problem be addressed rather than the command itself.

In his final reply, Rostedt clarified that he had not intended to change the default behavior, only to ask whether a pre-command hook mechanism could exist, and described his actual workflow: he frequently creates temporary topic branches and uses `git reset --hard <sha>` to fast-forward his main branches to that state, which is why he reaches for the destructive command so often. Accepting Junio's advice, he concluded that he will simply write a personal wrapper script that runs `git diff` first and prompts if there are pending changes, and thanked the list for confirming there is no existing built-in mechanism for this. The thread now stands closed from an upstream perspective, with the maintainer firmly opposed to any change to `git reset --hard`, the config-based proposal rejected, and the original poster satisfied with a client-side workaround.

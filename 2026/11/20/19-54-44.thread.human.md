Steven Rostedt raised a feature request on the Git mailing list asking whether upstream Git could add a safeguard against accidental data loss when `git reset --hard` is run inadvertently, given his workflow of creating temporary topic branches, recording their SHA-1 hashes, and then fast-forwarding his main development branches to those hashes with `git reset --hard`. Mirko Faina suggested a `reset.*` configuration variable that would make `--keep`-like abort-on-dirty behavior the default for `--hard` with a `--force` override, but maintainer Junio C Hamano rejected any change that would alter the default or config-overridable semantics of the command, arguing that once a widely used command is "castrated" it becomes impractical and breaks automation expectations, and urging users to address root workflow problems instead.

Rostedt tested running `git reset` without `--hard` and found it impractical for his use case, as the resulting diff spanned 72,642 files, confirming why he relies on `--hard` for clean fast-forwards. He ultimately accepted Hamano's position that no pre-command hook, config-based prompt, or semantic change to `builtin/reset.c` would be pursued upstream. The thread is now concluded: Rostedt announced he will implement a personal client-side wrapper script that runs `git diff` first and prompts if pending changes exist before invoking `git reset --hard`, leaving the existing modes -- including the already-safe `--keep` -- unchanged.

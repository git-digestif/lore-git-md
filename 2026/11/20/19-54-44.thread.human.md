This thread, opened by Steven Rostedt, asked whether Git could gain a safeguard against accidental data loss when `git reset --hard` is run inadvertently -- for example a config-based safety prompt, a `--force` override flag, or a pre-command hook. Rostedt's own workflow drives the request: he fast-forwards his main topic branches by copying SHA-1s from temporary branches and running `git reset --hard <sha>`, and he demonstrated why he relies on `--hard` by showing that a bare `git reset` on his tree produced a diff spanning 72,642 files. Mirko Faina had earlier proposed making `--keep`-like behavior the default for `--hard` behind a config variable.

Maintainer Junio C Hamano rejected any change to `git reset --hard` semantics, arguing that once a command is widely adopted, weakening its default behavior -- even via opt-in config -- breaks automation expectations and becomes impractical. In his latest reply he adds that he personally never uses bare `git reset` to clean a working tree, noting that while simple cases can be recovered with `git diff | git apply -R`, recovery gets messy when paths were added or removed between the index, working tree, and target state. The thread is now concluded: Rostedt accepted the rejection, withdrew the feature request, and announced he will write a personal wrapper script that runs `git diff` first and prompts when pending changes exist before invoking `git reset --hard`. No upstream mechanism will be added; the existing `--soft`, `--mixed`, `--keep`, and `--merge` modes are unchanged.

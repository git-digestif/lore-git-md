This is a substantive review from Junio C Hamano of Andrei Șova's bugfix for `git clone --revision` failing when the source repository uses a different hash algorithm than the default. The patch fixes an ordering issue in `builtin/clone.c` where the refspec item for `--revision=<oid>` is parsed before `the_repository->hash_algo` is set from the remote, causing `parse_refspec` to misinterpret SHA-256 object IDs as the wrong length; the proposed fix records the refspec index (`rev_refspec_idx`) and re-initializes it via `refspec_item_init_fetch()` after `create_reference_database()` runs.

Junio asks for commit message improvements: state the actual user-visible failure (specific error messages for protocol v2 vs v0/v1), note that the bug triggers bidirectionally (SHA-1 default cloning from SHA-256 remote, and vice versa, since `parse_refspec` requires exact length match), and explain why the `if (refs || ...)` guard was extended to cover `option_rev` with `exact_sha1`. He also questions the design: rather than appending the refspec early and then undoing/recomputing it once the hash algorithm is known, he suggests deferring refspec creation until after the handshake when the hash algorithm is already determined, treating the current approach as chance rather than good design.

On the test side in `t/t5621-clone-revision.sh`, he requests blank lines between logical command groups, separation of the detached-HEAD verification from the HEAD-value check into distinct assertions, and adding unrelated refs (e.g., tags) to the source SHA-256 repository so the "no refs are copied" assertion is meaningful. No merge status is assigned; the patch remains under review with this being the first substantive feedback.

This is a discussion reply in the ongoing bugfix thread for the `git apply --check` crash, where Tanga Joris is responding to Junio C Hamano's questions about the v3 series and the planned v4 approach.

Tanga confirms that Git only produced bare `diff --git` lines with no following headers back in 2005, before commit `ec1fcc16af` added the `index` line, so the assumption that modern Git never generates empty sections holds. He fully agrees with Junio's three-way distinction: malformed `diff --git` sections within Git-generated patches should be rejected strictly, non-patch commentary between complete patches should continue to be ignored, and third-party diff output (plain `diff` lines, not `diff --git`) should be left untouched to avoid destabilizing existing parsing. For v4, `find_header()` will stop immediately with a "corrupt patch" error when it encounters a `diff --git` line with no header lines following it, rather than silently skipping it as v3 does. This stricter behavior will catch the blank-line and indented `new file mode` edge cases from the original bug report, and likely makes patch 1/3 of the series (the memory-leak fix) unnecessary.

This is a **substantive design review** of patch v9 1/4 in Harald Nordgren's series extending `git branch` with `--delete-integrated` detection. Junio C Hamano examines the proposed static helper `branch_opted_out()` in `builtin/branch.c`, which patch 1/4 extracts from `delete_merged_branches()` to share the `branch.<name>.deleteMerged=false` config check with the new deletion mode introduced in patch 3/4.

Junio raises an impedance mismatch between the generic-sounding function name and the specifically-named configuration key. He argues that `branch_opted_out` assumes deleting merged branches will remain the only destructive operation needing an opt-out, and offers three alternatives: name the function to explicitly reference the `deleteMerged` operation, make it truly generic by renaming the config to something like `branch.<name>.noClobber` that could protect against future destructive features, or keep the name but add an operation parameter so callers write `branch_opted_out("main", "deleteMerged")`. In each case he stresses the helper must remain a pure query without side effects.

The review also revisits a default-semantics concern from earlier in the thread: when the config key is missing or true, the function returns false (not opted out), which Junio characterizes as risky, arguing that absent an explicit "I am fine losing this" a branch should be treated as precious.

This is a thoughtful API design intervention rather than a bug report. It directly affects how the safety opt-out will behave for both the existing `--delete-merged` and the new `--delete-integrated` flags, and the naming decision will be visible in the codebase long after this series lands.

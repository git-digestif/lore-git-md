This is a refactoring patch -- the second of four in Harald Nordgren's v9 series that introduces `git branch --delete-integrated`. While the series as a whole is a feature, this particular commit is preparatory plumbing: it teaches `delete_branches()` in `builtin/branch.c` to accept an optional `struct strmap *landed_commits` mapping branch names to the upstream commit where their changes landed.

When a branch appears in that map, the function skips the usual tip-reachability check (`check_branch_commit()`) and instead reports the landing commit in its output, printing `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6).` The same logic applies under `--dry-run`, which would print the corresponding "Would delete ... landed as ..." message. Because every existing caller still passes `NULL` for the new parameter, there is no behavior change yet; this patch simply readies the deletion machinery so that later patches in the series can supply the map.

The diff is small and clean -- 25 insertions and 5 deletions confined to `builtin/branch.c` -- and the commit message clearly explains why the change is needed: branches whose changes were squash-merged or rebased have tips that are not reachable from upstream, so the old merge check would refuse to delete them, and the output should say where the work actually went. Reviewers in the thread have treated patches 1/4 and 2/4 as uncontroversial, and this one fits that pattern: it is behavior-neutral, well-motivated, and sets up the core `--delete-integrated` logic that arrives in patches 3/4 and 4/4.

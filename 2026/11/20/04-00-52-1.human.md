This is a bugfix for `git clone --revision` when the remote repository uses a different hash algorithm than the local default. Under protocol v2, passing a valid commit hash from a SHA-256 remote to a SHA-1 clone (or vice versa) incorrectly fails with "fatal: Remote revision ... not found in upstream origin", even though the object exists on the remote.

The root cause is an ordering issue in `builtin/clone.c`: the refspec item for `--revision` was being created before the destination repository's hash algorithm was determined, so `parse_refspec` interpreted the hash using the wrong algorithm. The patch delays appending the `--revision` value to the refspec until after `the_repository->hash_algo` is set, and explicitly assigns that algorithm to `remote->fetch.hash_algo`. As a side effect, the transport ref prefix list is left empty when `--revision` is used so that all advertised refs are requested.

The fix is covered by a new test in `t/t5621-clone-revision.sh` that clones a SHA-256 repository with `GIT_DEFAULT_HASH=sha1` using `--revision` with a raw SHA-256 oid, verifying that the clone succeeds and HEAD points at the expected commit. The commit message is clear about the failure mode and the mechanics of the fix, and the change is localized to `cmd_clone` and `wanted_peer_refs`. This is the second iteration of the patch, suggesting earlier review feedback has been incorporated.

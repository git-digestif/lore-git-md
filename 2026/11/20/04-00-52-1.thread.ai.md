Thread identity: [PATCH v2] bugfix series from Andrei Șova <andreisva2023@gmail.com> addressing `git clone --revision` failure under protocol v2 when the specified revision uses a different hash algorithm than the local default. Thread type: single-patch bugfix, second iteration.

Core problem or goal: Under protocol v2, `git clone --revision=<oid>` fails with "fatal: Remote revision ... not found in upstream origin" when given a valid commit hash whose algorithm differs from the destination's default -- e.g., a SHA-256 hash when cloning into a SHA-1 repository -- even though the object exists on the remote. Under protocol v1 the same scenario produced a different error ("couldn't find remote ref"). Root cause: the refspec item for `--revision` was appended to `remote->fetch` before the destination repository's hash algorithm was configured, so `parse_refspec` interpreted the hash under the wrong algorithm.

Current status: v2 posted, under review. No merge or integration-branch status indicated.

Key technical details: Fix in `builtin/clone.c` (38 lines changed) delays appending the `--revision` value until after the remote's hash algorithm is gathered and assigned to `the_repository->hash_algo`; explicitly sets `remote->fetch.hash_algo = the_repository->hash_algo` before `refspec_append`. Introduces integer `rev_refspec_idx` to track the refspec item index, passed to `wanted_peer_refs` which uses it to flag the revision refspec when calling `get_fetch_map`. Adjusts ref-prefix logic so that with `--revision`, "HEAD" is not added to `transport_ls_refs_options.ref_prefixes` and the prefix list is empty, causing all advertised refs to be requested. Regression test added in `t/t5621-clone-revision.sh`: initializes SHA-256 source repo, runs `GIT_DEFAULT_HASH=sha1 git clone --no-local --revision=$oid`, verifies clone succeeds, HEAD resolves to provided OID, no refs created in destination, and `remote.origin.fetch` remains unset.

This is a design-discussion reply in the ongoing thread about safeguarding `git reset --hard`, proposing a config-based default rather than a new prompt.

Mirko Faina responds to Steven Rostedt's request for a configuration that would make `git reset --hard` check for uncommitted changes and ask for confirmation. Faina first points out that existing options already cover part of the need: one can run `git reset` without `--hard` to preserve the working tree, or use `--keep`, which already aborts the reset if local changes are present but requires typing the flag every time.

He then suggests a concrete design: add a configuration variable that makes the `--keep` behavior the default, paired with a `--force` flag on the command line to override the safeguard when the user really means it. This reframes the discussion from adding a new interactive prompt to repurposing the existing `--keep` semantics behind a config knob.

No patch is attached; the email is purely a proposal for how such a safety mechanism could be structured, leaving the exact config key name and interaction with other reset modes (`--soft`, `--mixed`, `--merge`) still open for discussion.

Thread identity: Single-patch bugfix from Ophir Bleicher via GitGitGadget addressing incorrect output from `git rev-parse --output-object-format=sha1` in SHA-256 repositories using `extensions.compatObjectFormat`. Thread type: standalone patch, first email in thread.

Core problem or goal: When a SHA-256 repository enables SHA-1 compatibility via `extensions.compatObjectFormat`, objects created before the extension was set have no SHA-1 mapping. Previously, `git rev-parse --output-object-format=sha1 <oid>` for such objects silently printed the SHA-256 hash, returning a wrong value without indication. The patch makes this case a hard error.

Current status: Patch posted, under review. No prior versions. Not queued in any integration branch.

Key technical details: Change is in `builtin/rev-parse.c` inside `cmd_rev_parse()` in the `output_algo` conversion path. The code now checks the return value of `repo_oid_to_algop()` and calls `die()` with message "cannot map object %s to %s" if the object cannot be converted to the requested algorithm, instead of ignoring the failure. Four lines touched in one file. Reproduction: `git init --object-format=sha256`, write object via `git hash-object -w --stdin`, set `extensions.compatObjectFormat sha1`, then `git rev-parse --output-object-format=sha1 <oid>` now errors instead of emitting SHA-256 hex. No additions to the `t/` test suite included.

Open questions and loose ends: Whether a hard `die()` is the appropriate interface versus emitting a warning or empty output; whether the compatObjectFormat interaction deserves regression tests in `t/t1006-*` or similar test files.

Participant positions: None yet; this is the thread root.

Related work: Sits at the intersection of the object-format abstraction layer (`repo_oid_to_algop()`) and rev-parse output formatting. Related to broader SHA-256 and hash-algorithm-agnostic work including the `compatObjectFormat` extension for interoperability between SHA-1 and SHA-256 repositories.

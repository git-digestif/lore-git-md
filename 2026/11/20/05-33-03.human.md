This is a bugfix for the untracked cache and fsmonitor interaction in `dir.c`. Maik Riechert identifies a case where `git status` reports both an untracked directory and a directory beneath it (for example, `?? three/` and `?? three/deep/`) after a failed fsmonitor query or a trivial response. The root cause traces to commit 1cf98cb4d9, which added stat-based invalidation of stale directories but did not propagate that invalidation upward to parent directories. In normal mode, a parent's cached untracked list can contain a child entry from a check-only scan; when the child is invalidated and its check-only flag cleared, the next walk recurses into it and reports the deeper path while the parent still lists the top-level directory, producing the confusing duplicate output.

The fix is small and surgical: in `invalidate_stale_dirs()`, when the directory flags include `DIR_SHOW_OTHER_DIRECTORIES` and at least one child was invalidated, the parent directory is invalidated as well via the existing `invalidate_one_directory()` helper. The all-files mode is deliberately left unchanged. The patch also adds regression tests in `t/t7519-status-fsmonitor.sh` covering both trivial and failed fsmonitor responses, using fixed directory mtimes and `update-index --force-write-index` to avoid scanning untracked files during the setup.

The commit message is clear and well-motivated, citing the specific prior commit that introduced the incomplete behavior, and the change comes with targeted tests. It looks like a solid, well-scoped fix that deserves attention from anyone maintaining the fsmonitor or untracked-cache code paths.

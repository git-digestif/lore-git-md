This is a substantive review reply from Phillip Wood in the ongoing thread about Dominik Maier's config bugfix patch. Phillip addresses Junio C Hamano's backwards-compatibility concern by arguing that the patch does not change how Git reads configuration values, but only aligns the parsing used during section copy/rename (`repo_config_copy_or_rename_section_in_file()`) with the parsing already used when reading config settings; he frames this as fixing a bug in an unlikely corner case rather than introducing a breaking behavior change, while lamenting that the copy/rename path duplicates parsing logic instead of sharing a common code path with the reader.

Phillip also identifies a new correctness issue in the proposed code: the patch appears to treat carriage returns (`\r`) as line separators equivalent to newlines (`\n`), but valid config files can contain `\r` characters inside subsection names and values. He provides a concrete reproduction using `printf '[a "b\rc"]\rkey=\rv\ralue'` to create a config file where `git config get` correctly returns a value containing `\r` (rendered as `vQal` when piped through `tr '\r' Q`), demonstrating that the new continuation-tracking logic would misparse such files. This adds a concrete technical edge case to the open questions surrounding the patch.

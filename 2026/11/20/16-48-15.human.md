This is patch 2/8 in Christian Couder's v2 series fixing the missing `promisor-remote` reply in protocol v2 `fetch`; while the rest of the series largely unifies capability-writing code, this patch makes a small but real behavior change by extending `session-id` advertisement to `ls-refs` and `bundle-uri` requests.

The patch modifies `send_capabilities()` in `connect.c` so that, when `transfer.advertiseSID` is set and the server supports the `session-id` capability, the client now writes `session-id=...` alongside the other capability lines. Previously this was only done for the `fetch` command in `fetch-pack.c`; now `ls-refs` and `bundle-uri` requests sent through `send_capabilities()` carry it too.

The commit message points to `1e905bbc00` from 2020, which first added session IDs to `fetch-pack` without explaining why they were left out of other commands. Since the protocol documentation describes session IDs as a way to identify the client process across multiple requests, the author argues there is no reason to omit them elsewhere.

The change only affects users who explicitly set `transfer.advertiseSID` (it is off by default). Over persistent transports like `file://` and `ssh://`, where a single `upload-pack` process handles both `ls-refs` and `fetch`, the server will now log the client's session ID twice per process, but the author notes this is harmless.

Tests are added to `t/t5705-session-id-in-capabilities.sh` to verify that the server receives the client session ID when only `ls-refs` is sent (via `git ls-remote`) and when only `bundle-uri` is sent (via `test-tool bundle-uri ls-remote`), complementing the existing tests that already covered `fetch`.

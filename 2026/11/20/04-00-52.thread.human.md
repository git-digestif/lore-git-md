Andrei Șova has sent a bugfix for `git clone --revision` when cloning SHA-256 repositories using a raw commit hash. The problem is an ordering bug in `builtin/clone.c`: when `--revision` is given a hex object ID, the refspec is appended to `remote->fetch` before the destination repository's hash algorithm has been determined from the remote, so `parse_refspec` interprets the hash with the default SHA-1 length (40 hex chars) instead of SHA-256 (64 chars), causing the clone to fail. The fix records the index of the appended refspec and, once `create_reference_database()` has initialized the repository with the correct hash algorithm, clears and re-parses that specific refspec item using `the_repository->hash_algo`. It also extends the guard around `wanted_peer_refs()` to trigger when `option_rev` is set and the re-parsed refspec has `exact_sha1` set. The patch touches `builtin/clone.c` and adds a regression test to `t/t5621-clone-revision.sh` that reproduces the mismatch by forcing `GIT_DEFAULT_HASH=sha1` against a SHA-256 source. The submission appears straightforward with no controversy or open questions.

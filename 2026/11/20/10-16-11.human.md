This is a follow-up discussion reply in Patrick Steinhardt's v5 patch series modernizing `git rerere`'s subcommand handling, specifically responding to Junio C Hamano's review of patch 11/13, the core conversion to `OPT_SUBCOMMAND()`.

Patrick agrees with Junio's assessment that the new structure makes the `--rerere-autoupdate` help text harder to discover via `git rerere -h`, since the implicit default subcommand no longer surfaces its options in the top-level help. He distills the lesson into a design principle for future commands: when a command has a default subcommand, it should either accept a bare invocation with no flags, or require an explicit subcommand name (e.g. `git rerere perform --rerere-autoupdate`) whenever the user wants non-default behavior. He notes that applying this strictly to `git rerere` now would break the existing interface, so he is not proposing to change it here, but flags it as a takeaway for designing new commands.

The exchange confirms that the intentional backwards-incompatible change in patch 11/13 -- rejecting `--[no-]rerere-autoupdate` for named subcommands like `gc` or `status` -- is accepted as fixing a previously misleading interface. No new objections are raised; the series remains under review with no merge status claimed for v5.

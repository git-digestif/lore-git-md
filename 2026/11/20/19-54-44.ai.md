This is a feature request proposing a new safety configuration for `git reset --hard`. Steven Rostedt asks whether Git could add a configuration option that makes `git reset --hard` check for uncommitted changes and prompt for confirmation before discarding them, motivated by his own recent experience of losing uncommitted work after running the command in the wrong directory.

The email is a thread root containing no patch -- just a question to the list about whether such a safeguard is feasible or desirable. Rostedt does not propose a specific config key name or implementation approach, only the general behavior of intercepting `git reset --hard` when the working tree is dirty.

For future reference, the relevant command is `git reset --hard` and the proposed change would introduce a new configuration knob (likely under `reset.*` or similar) that triggers a confirmation prompt when uncommitted changes exist. Any discussion in follow-ups will likely touch on how this interacts with existing reset modes (`--soft`, `--mixed`, `--keep`, `--merge`) and whether the prompt should be skippable via a command-line flag.

Since no code is attached, reviewers responding to this thread will be discussing design rather than reviewing implementation. The thread may evolve into an actual patch series if the idea gains traction, potentially touching `builtin/reset.c` and the configuration parsing in `config.c`.

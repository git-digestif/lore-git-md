This is a bugfix for `git clone --revision` when cloning SHA-256 repositories with a raw commit hash.

The problem is an ordering issue in `builtin/clone.c`: when `--revision` is given a hex object ID, the refspec item is appended to `remote->fetch` early in `cmd_clone()`, before the destination repository's hash algorithm has been determined from the remote. As a result, `parse_refspec` interprets the hash using the default SHA-1 length (40 hex chars) rather than SHA-256 (64 chars), causing the clone to fail or behave incorrectly. The fix records the index of the appended refspec (`rev_refspec_idx`) and, after `create_reference_database()` has initialized `the_repository` with the correct hash algorithm, clears and re-initializes that specific refspec item via `refspec_item_init_fetch()` using `the_repository->hash_algo`. It also extends the condition guarding the `wanted_peer_refs()` call to trigger when `option_rev` is set and the re-parsed refspec item has `exact_sha1` set.

The patch touches `builtin/clone.c` and adds a regression test to `t/t5621-clone-revision.sh` that initializes a SHA-256 source repository, clones it with `--revision=<sha256-oid>` while forcing `GIT_DEFAULT_HASH=sha1` to reproduce the mismatch, and verifies the resulting `HEAD` matches the requested commit with no refs created. The commit message is concise and the fix is localized; the only notable detail is that it relies on `the_repository->hash_algo`, consistent with current usage in that function though part of the broader `the_repository` removal effort. No controversy or open questions are apparent from the submission.

Thread identity: single-patch bugfix from Maik Riechert (via GitGitGadget) targeting the interaction between the untracked cache and fsmonitor in `git status`.

Core problem: after a failed fsmonitor query or a trivial fsmonitor response, normal-mode `git status` can incorrectly report both an untracked directory and a directory nested beneath it (e.g. "?? three/" alongside "?? three/deep/"). The root cause is commit 1cf98cb4d9 ("fsmonitor: check the untracked cache after a trivial response"), which added a stat check to invalidate stale cached directories but did not propagate that invalidation upward to parent directories.

Current status: patch posted, under review; no merge status indicated.

Key technical details: the fix modifies `invalidate_stale_dirs()` in `dir.c` to also call `invalidate_one_directory()` on the immediate parent when the `DIR_SHOW_OTHER_DIRECTORIES` flag is set and at least one child was invalidated. This mirrors the existing behavior of `invalidate_one_component()` and intentionally leaves all-files mode unchanged to avoid extra stat calls during traversal. The change is six lines in `dir.c` and reuses the existing directory-walk logic. The commit message explains the mechanism: in normal mode a parent's cached untracked list can contain an entry like "three/" from a check-only scan of the child; when the child's invalidation clears its check-only flag, the next cached walk recurses into the child and reports the deeper path while the parent entry remains stale. Two regression tests are added in `t/t7519-status-fsmonitor.sh` covering trivial and failed fsmonitor responses; they use `test-tool chmtime` to control directory timestamps and `update-index --force-write-index` to write the index without scanning untracked files, then verify `git status --porcelain` does not list both parent and child.

Patrick Steinhardt has posted a six-patch series to clean up the packfile lifecycle API as part of his broader object database abstraction work, moving process-wide pack limits to a global list and tightening resource handling. Junio C Hamano has begun reviewing the series and is generally supportive, though he has flagged specific fixes needed before it can advance. On patch 1/6, which removes developer-oriented pack statistics from `git fast-import --stats`, Junio requires commit message corrections and an update to the `--stats` option description string. Patch 3/6, which consolidates pack-opening logic into a single `packfile_open_pack()` function with unified cleanup, drew praise for clarifying file descriptor ownership but also uncovered a latent accounting bug: if `fstat()` fails after `git_open()` succeeds, the new error path would decrement the open-fd counter without a matching increment, causing underflow. Patch 4/6, introducing a `packfile_free()` helper, was accepted with only a suggestion to consider NULL-guarding. Patch 6/6, which makes limit enforcement honor the `do_not_close` flag, is more contested: Junio questions whether the three-line fix is necessary since the only user of that flag never adds its packs to the tracked list, and suggests the flag might simply be removed instead. The series remains at v1 under review, with a v2 expected to address the commit message fixes, the fd counter bug, and the open question about the `do_not_close` flag's future.

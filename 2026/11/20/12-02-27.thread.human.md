Patrick Steinhardt has posted a six-patch series refactoring Git's packfile lifecycle subsystem, touching 22 files with the heaviest changes in `packfile.c` and `packfile.h`. The series performs mechanical renames to adopt a consistent `packfile_` prefix, consolidates pack-opening logic into a single `packfile_open_pack()` function with unified error cleanup, introduces a `packfile_free()` helper, moves process-wide packfile limits from per-repository scope to a global `all_packfiles` list, and fixes `close_one_pack()` to respect the `do_not_close` flag. Patch 1/6 removes packfile statistics from `git fast-import` output on the grounds that these metrics expose internal details meaningless under pluggable object databases.

Junio C Hamano has reviewed several patches and identified issues requiring revision before a v2 can be posted. On patch 1/6, he corrected the commit message's description of what `pack_report()` outputs and noted a missed user-visible string in the `--stats` option description that still references packfiles. On patch 3/6, he identified a `pack_open_fds` counter underflow bug on the error path where `git_open()` succeeds but `fstat()` fails, though he otherwise considers the consolidation sound. On patch 4/6, he accepted the change but suggested considering a NULL guard in `packfile_free()`. On patch 6/6, he questioned whether the `do_not_close` check is necessary given that fast-import packs are never in the `all_packfiles` list, proposing instead that the flag be removed entirely as dead code.

brian m. carlson has now weighed in supporting patch 1/6, agreeing that packfile statistics should not print by default, but suggesting a broader follow-up where all `git fast-import` statistics become opt-in via `--stats` rather than on-by-default, citing automated SHA-1 to SHA-256 conversion tests where the default statistics output clutters logs monitored for real errors. The series remains at v1 under review, with no merge or integration status claimed.

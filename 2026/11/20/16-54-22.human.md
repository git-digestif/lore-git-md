This is a design-discussion reply from Junio C Hamano in the ongoing review of Patrick Steinhardt's v5 series that modernizes `git rerere` subcommand handling. It responds specifically to Patrick's "personal takeaway" that a default verb-less subcommand should accept no flags at all, and that requesting non-default behavior should require an explicit subcommand like `git rerere perform --rerere-autoupdate`.

Junio pushes back gently on the strictness of that principle, arguing that giving the default action an optional explicit name -- for example allowing `git rerere run [--[no-]rerere-autoupdate]` alongside the bare `git rerere` -- is not the worst kind of backward-incompatible change, since users can still invoke the command without the name. He then adds a wry aside questioning whether the `OPT_SUBCOMMAND()` interface actually supports an optional subcommand bit, even though the series under review already uses `PARSE_OPT_SUBCOMMAND_OPTIONAL` to make the subcommand optional.

The exchange closes the remaining substantive discussion around patch 11/13 of the series: the loss of `--rerere-autoupdate` help text in `git rerere -h` and the change in shell-completion output. Both participants now treat these as acceptable side effects of converting to `OPT_SUBCOMMAND()`, with Patrick recording his stricter design preference for future commands and Junio indicating that a softer, opt-in explicit subcommand would also have been reasonable. No code changes are proposed in this email, and the series remains under review with no merge status claimed.

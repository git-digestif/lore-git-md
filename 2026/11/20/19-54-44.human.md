This is a feature request proposing a new safety configuration for `git reset --hard`.

Steven Rostedt asks whether Git could gain a config option that makes `git reset --hard` check for uncommitted changes and prompt for confirmation before discarding them. He notes that he frequently runs the command in the wrong directory and has just lost work as a result, which motivates the inquiry.

The email is a question rather than a patch, so there is no code to assess. It raises a user-experience concern that sits at the intersection of command safety and data-loss prevention: `git reset --hard` is intentionally destructive, but a guard against accidental invocation in the wrong worktree could prevent real harm. Whether the project would want such a knob -- and whether it belongs as a global config, a per-command option, or an interactive prompt -- remains open for discussion.

This is a **substantive review reply** from Junio C Hamano on patch v9 1/4 of Harald Nordgren's series, which extracts the `branch.<name>.deleteMerged=false` opt-out check from `delete_merged_branches()` into a static helper named `branch_opted_out()` in `builtin/branch.c`. Junio raises two design concerns about the proposed helper. First, he argues the name `branch_opted_out` is too generic and "selfish," assuming that deleting merged branches will remain the only destructive operation that might need an opt-out; he suggests either renaming the function to explicitly reference the `deleteMerged` operation specifically, or making the function truly generic for any destructive operation and renaming the config key from the specific `deleteMerged` to something like `noClobber` so it could protect against future destructive features. Second, he questions the default return value semantics: when the config key `branch.<name>.deletemerged` is missing or set to true, the function returns false (meaning "not opted out"), which he characterizes as a risky default, arguing that absent an explicit "I am fine losing this" the branch should be treated as precious. The reply engages with the API design and safety implications of the helper that patch 3/4 will reuse for the new `--delete-integrated` flag, making it clear the opt-out mechanism is intended to apply to both deletion modes but the naming and default semantics remain open for discussion.

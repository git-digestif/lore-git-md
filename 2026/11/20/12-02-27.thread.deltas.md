# Thread deltas

## 2026/11/20

- [2026/11/20/12-02-27 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt posted a six-patch series "packfile: some lifecycle improvements" motivated by fixing process-wide limitation handling in the final patch, and noted a minor semantic merge conflict with "seen" that can be resolved by renaming `open_pack_index` to `packfile_open_index` in `odb/source-packed.c`.
- [2026/11/20/12-02-28 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt removed packfile statistics reporting from `git-fast-import` (dropping `pack_report()` and related counters) because with pluggable object databases the command should not assume packfiles are in use, though he noted that if anyone complains the data may be reintroduced as trace2 data.
- [2026/11/20/12-02-29 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt renamed packfile lifecycle functions to use modern `packfile_` prefixes (e.g., `open_pack_index` to `packfile_open_index`, `add_packed_git` to `packfile_from_idx`, `close_pack` to `packfile_close`).
- [2026/11/20/12-02-30 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt inlined `open_packed_git_1()` into a new `packfile_open_pack()` function that uses a common exit path to close the file descriptor on error.
- [2026/11/20/12-02-31 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt introduced `packfile_free()` to encapsulate closing and freeing a packfile, replacing separate `packfile_close()` and `free()` calls at multiple call sites.
- [2026/11/20/12-02-32 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt changed enforcement of `pack_max_fds` and `core.packedGitLimit` to use a global `all_packfiles` list independent of any repository or object database backend, making the limits truly process-wide.
- [2026/11/20/12-02-33 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt made `close_one_pack()` skip packfiles marked `do_not_close` when selecting packs to close for the maximum open file descriptor limit, which should not result in a user-visible behavior change.

## 2026/11/24

- [2026/11/24/20-43-54 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano corrected the claim that `pack_report()` reports the number of packs opened, listing what it actually prints (page size, packedGitWindowSize, packedGitLimit, window-switch counter, mmap calls, open/mapped windows), agreed the metrics target developers rather than end-users, and noted that `cmd_fast_import()`'s `--stats` option description in `fast_import_option[]` still mentions "packfiles" even though the new design no longer reports them; he also agreed that dropping `pack_report()` and its four dedicated counters looks clean.
- [2026/11/24/21-14-02 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano questioned the approach of skipping `do_not_close` packs in `close_one_pack()`, suggesting that since the bit's only user does not rely on that codepath honoring it, a simpler alternative might be to retire the bit entirely.
- [2026/11/24/21-34-03 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano accepted the new `packfile_free()` function, observing that the codebase has three kinds of free-like functions and wondering whether it should guard against NULL to behave like `free(NULL)`, though he noted all callsites never pass NULL so the current form is fine.
- [2026/11/24/22-04-02 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano agreed that inlining `open_packed_git_1()` makes descriptor ownership easier to follow, but flagged a possible `pack_open_fds` accounting mismatch: if `git_open()` succeeds and `fstat()` fails, the code jumps to the exit path before incrementing the counter, and the subsequent `packfile_close_fd()` would decrement it, potentially underflowing to UINT_MAX; he noted this may not be a new bug but suggested fixing it while touching the area.
- [2026/11/24/22-19-16 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson said that in a future series they would like fast-import statistics disabled by default altogether, explaining that their SHA-1-to-SHA-256 conversion tests care about stderr errors but not the stats (requiring `--quiet` to avoid noise), and that this would better match the Unix philosophy of saying nothing on success.
- [2026/11/24/23-24-02 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano suggested rewording "maximum number of packfile data" to "maximum amount of", raised an impedance-mismatch concern that a pluggable object store may not even have a packfile concept yet the global list assumes packfiles occupy address space, but praised the global `all_packfiles` list for cleanly solving the cross-repo limit problem and the unconditional downcasts, and confirmed it should not retain dangling pointers since every pack from `packfile_new()` is freed via `packfile_free()`.
- [2026/11/24/23-47-25 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano welcomed the lifecycle-function rename scoped to just those functions, especially `add_packed_git()` to `packfile_from_idx()` since the former never actually added the pack to a store, and noted the moved forward declaration of `struct object_database` was already unused and could be skipped or dropped separately.

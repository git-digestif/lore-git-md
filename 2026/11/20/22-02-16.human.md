This is a maintainer response in an ongoing feature-request discussion, rejecting the proposal to add a safety configuration to `git reset --hard`.

The thread began with Steven Rostedt asking whether Git could add a config option that makes `git reset --hard` detect uncommitted changes and prompt for confirmation before discarding them, motivated by losing work after running the command in the wrong directory. Mirko Faina had previously suggested making `--keep`-like behavior the default for `--hard` via a config variable, with a `--force` flag to bypass the check.

Junio C Hamano pushes back on that approach, arguing that altering the default behavior of an existing command -- which he describes as "castrating" it -- becomes impractical once a tool has a large user base. Instead of changing what `--hard` does, he advises addressing the root cause: figuring out why users reach for `git reset --hard` in the first place and packaging a less drastic solution to the same problem. That way, safer workflows could become more common, while scripts and users who genuinely need the destructive behavior can continue using it unchanged.

The email signals that the specific config-based proposal is unlikely to gain the maintainer's support, though it does not dismiss the underlying concern about accidental data loss. The discussion may now pivot toward identifying what alternative, less destructive commands or workflows could address Rostedt's use case without modifying `git reset --hard` semantics.

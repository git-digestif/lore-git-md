This is a maintainer review of the second patch in Adrian Ratiu's three-patch v2 bugfix series for the `compatObjectFormat` interoperability layer. The patch itself fixes `git rev-parse --output-object-format` to die with a clear error when it cannot map an object between hash algorithms, rather than silently returning the storage OID -- a correctness issue affecting objects received via fetch that lack compat mappings.

Junio C Hamano endorses the fix, agreeing that mimicking `git pack-objects` and other existing callers is the right approach. He raises one wording concern about the commit message's scope: describing the fix as covering "single revision" cases could be read to exclude commands like `git rev-parse --output-object-format=sha1 main next`, where multiple individual revisions are requested. Adrian Ratiu clarifies that the patch only addresses cases where the desired output hash is passed explicitly, while ranges like `A..B` do not use it and would require a larger future change. Junio accepts this scoping.

Junio also praises the test design as "clever and clean": the test writes an object in a SHA-256 repository before enabling `extensions.compatObjectFormat`, ensuring it receives no compat mapping, then verifies that requesting the SHA-1 format dies with the expected error while SHA-256 succeeds. This approach avoids manually copying object directories, which would be fragile under the upcoming ODB abstraction.

The review is substantive but concise, engaging with both the behavioral change and the test strategy rather than offering surface-level comments. It signals that patch 2 is on track to proceed without major contention, in contrast to patch 3 of the series which remains under active discussion.

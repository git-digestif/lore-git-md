This is a **bugfix** for `git submodule update --jobs` that aligns its handling of zero and negative values with the `submodule.fetchJobs` configuration variable and with the precedent set for `git fetch --jobs`.

The patch addresses two broken behaviors introduced when commit 51243f9f0f ("run-command API: don't fall back on online_cpus()", 2022-10-12) turned a job count of zero into a `BUG()` crash and moved the fallback logic into individual option parsers. Currently, `git submodule update --jobs=0` aborts with "you must provide a non-zero number of processes!", and `--jobs=-1` produces a confusing "data too large to fit into virtual memory space" error. The author notes that prior to v2.39, any value below 1 silently meant `online_cpus()`, but the option parser in `builtin/submodule--helper.c` uses `OPT_INTEGER()` and passes the value through unchecked, unlike `parse_submodule_fetchjobs()` which dies on negatives.

The core fix adds six lines to `module_update()` in `builtin/submodule--helper.c`: it dies with "'--jobs' cannot be negative" for negative values, and substitutes `online_cpus()` when the value is zero, mirroring the fix applied to `git fetch --jobs` in commit c39952b925 ("fetch: choose a sensible default with --jobs=0 again", 2023-02-20). This brings the `--jobs` option into agreement with the `submodule.fetchJobs` config variable, which already handles these cases correctly.

The patch also updates the man pages for `git-submodule(1)` and `git-clone(1)` to document that "A value of 0 will use some reasonable default", using the same wording as `git fetch --jobs`. Three new tests in `t/t7406-submodule-update.sh` verify that `--jobs 0` uses the CPU count (checked via `GIT_TRACE` output matching "up to N tasks"), that negative values are rejected with the expected error message, and that `git clone --recurse-submodules --jobs 0` correctly propagates the behavior through to submodule updates.

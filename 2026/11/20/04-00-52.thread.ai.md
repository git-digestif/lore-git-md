Thread identity: single-patch bugfix series from Andrei Șova (andreisva2023@gmail.com) fixing `git clone --revision` when cloning SHA-256 repositories with a raw commit hash; thread type is a standalone patch under review, no version prefix.

Core problem: an ordering bug in `builtin/clone.c` where, when `--revision` receives a hex object ID, the refspec item is appended to `remote->fetch` early in `cmd_clone()` before the destination repository's hash algorithm has been determined from the remote. `parse_refspec` therefore interprets the hash with the default SHA-1 length (40 hex chars) instead of SHA-256 (64 chars), causing the clone to fail or misbehave; the bug triggers bidirectionally since `parse_refspec` requires an exact length match, so a SHA-1 default cloning from a SHA-256 remote fails as does the reverse, with user-visible failure differing by protocol version (specific error messages for protocol v2 versus v0/v1).

Current status: under review; Junio C Hamano has provided the first substantive feedback requesting changes but no integration branch assignment or merge status has been stated.

Key technical details: the fix records the index of the appended refspec (`rev_refspec_idx`) and, after `create_reference_database()` has initialized `the_repository` with the correct hash algorithm, clears and re-initializes that specific refspec item via `refspec_item_init_fetch()` using `the_repository->hash_algo`. The guard for the `wanted_peer_refs()` call is extended to also trigger when `option_rev` is set and the re-parsed refspec item has `exact_sha1` set. Files touched: `builtin/clone.c` and `t/t5621-clone-revision.sh`, which gains a regression test that initializes a SHA-256 source repository, clones with `--revision=<sha256-oid>` while forcing `GIT_DEFAULT_HASH=sha1` to reproduce the mismatch, and verifies the resulting `HEAD` matches the requested commit with no refs created. The fix relies on `the_repository->hash_algo`, consistent with current usage in that function though noted as part of the broader `the_repository` removal effort.

Open questions and loose ends: Junio questions the design choice of appending the refspec early and then re-initializing it once the hash algorithm is known, suggesting instead that refspec creation should be deferred until after the handshake when the hash algorithm is already determined, characterizing the current approach as working by chance rather than by design. He requests commit message improvements to state the actual user-visible failure modes (specific error messages for protocol v2 vs v0/v1), note the bidirectional nature of the trigger, and explain why the `if (refs || ...)` guard was extended to cover `option_rev` with `exact_sha1`. On the test side in `t/t5621-clone-revision.sh`, he requests blank lines between logical command groups, separation of the detached-HEAD verification from the HEAD-value check into distinct assertions, and adding unrelated refs such as tags to the source SHA-256 repository so the "no refs are copied" assertion is meaningful.

Participant positions: Andrei Șova submitted the patch; Junio C Hamano reviewed substantively, requesting the commit message and design changes described above while leaving the patch under review without merge status.

This is a substantive review from Junio C Hamano of a bugfix patch that addresses `git clone --revision` failing when cloning SHA-256 repositories with a raw commit hash. The original patch proposes re-parsing the refspec after the hash algorithm is known, but Junio questions whether "undoing what was done in an earlier step and recomputing" is sound design, suggesting instead that the code should defer refspec creation until after the handshake with the remote has determined the correct hash algorithm.

Junio asks the author to improve the commit message in several ways: state explicitly what error the user sees when the clone fails, note that the bug triggers in both directions (SHA-1 default vs SHA-256 remote and vice versa) because `parse_refspec` requires an exact length match, and explain why the guard on the `wanted_peer_refs()` call had to change. He also requests standard formatting fixes, wrapping lines to roughly 72 columns and ending with an imperative summary.

On the test side, Junio walks through the new test in `t/t5621-clone-revision.sh` line by line, asking for blank lines between logical groups of commands, suggesting that the check for detached HEAD be separated from the verification that HEAD points to the requested object, and recommending that the source repository contain unrelated refs (by omitting `--no-tag`) so that the assertion that no refs are copied into the destination is meaningful.

The review engages directly with the architecture of `builtin/clone.c` rather than just surface details, indicating the maintainer sees the ordering of initialization as the real issue. No merge status is mentioned; the patch remains under review with the author expected to address the design question and the message improvements.

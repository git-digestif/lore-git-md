This is a maintainer's design feedback rejecting a proposed safety configuration for `git reset --hard`, part of the ongoing thread about preventing accidental data loss.

Junio C Hamano responds to Steven Rostedt's feature request and Mirko Faina's implementation sketch by arguing against modifying the semantics of `git reset --hard` after widespread adoption. He contends that "castrating" an existing command -- changing its destructive behavior to prompt or refuse when the working tree is dirty -- becomes impractical once a tool gains hundreds of users, which Git certainly has. Rather than adding a configuration knob that would alter how `git reset --hard` operates, he urges addressing the root cause of why users feel compelled to run such a drastic command in the first place.

He suggests identifying the underlying workflow problem and developing a less drastic alternative that the community can adopt, so that fewer people reach for `git reset --hard` in normal operation. This approach, he argues, reduces risk without changing the command's contract: scripts and users who genuinely need the destructive behavior will continue to have it work exactly as designed. The implication is that any config-based prompt or default behavior change in `builtin/reset.c` would break automation expectations.

For future reference, this email establishes that the maintainer opposes any change that alters the default or config-overridable behavior of `git reset --hard` toward the safer `--keep`-like semantics previously proposed. If the thread continues, discussion will likely shift away from adding a `reset.*` configuration key or `--force` bypass flag in the reset machinery, and instead explore entirely new commands or workflows that address the root problem. The existing modes -- `--soft`, `--mixed`, `--keep`, and `--merge` -- remain the baseline comparison, with `--keep` already providing abort-on-dirty behavior, but Junio is signaling that making that the default for `--hard` is not an acceptable path forward.

Thread identity: feature request / design discussion rooted by Steven Rostedt (rostedt@goodmis.org), no patch attached, asking whether Git can add a mechanism to prevent accidental loss of uncommitted work when `git reset --hard` is run inadvertently. Core problem: prevent accidental data loss from `git reset --hard` when run in the wrong context or against a dirty working tree. Current status: thread concluded; maintainer Junio C Hamano rejected any modification to `git reset --hard` semantics -- including config-based safety prompts, `--force` bypass flags, or pre-command hook mechanisms -- and original poster Steven Rostedt accepted this position, confirmed the feature request is withdrawn, and announced he will implement a personal client-side wrapper script instead of pursuing upstream changes. Key technical details: target command is `git reset --hard` in `builtin/reset.c`; earlier proposal by Mirko Faina for a `reset.*` configuration variable making `--keep`-like behavior the default for `--hard` with a `--force` override was rejected; Rostedt clarified that he was not asking to change default behavior but whether a pre-command hook mechanism (something like a `.gitrc` entry running before a command executes) could exist, and explained his workflow of creating temporary topic branches, copying their SHA-1, and running `git reset --hard <sha>` on his main topic branches to fast-forward them; he tested `git reset` without `--hard` and found it impractical because the resulting `git diff` showed changes across 72,642 files with millions of line insertions and deletions, demonstrating why he relies on `--hard` to fast-forward branches cleanly; Junio C Hamano acknowledged this impracticality in his final reply, noting that while simple cases can be recovered with `git diff | git apply -R`, recovery becomes messier when paths were added or removed between the index/working tree and the target state, and confirmed he personally never uses bare `git reset` without `--hard` for cleaning up working trees for exactly this reason; existing modes `--soft`, `--mixed`, `--keep`, and `--merge` remain unchanged, with `--keep` already providing abort-on-dirty behavior. Open questions: resolved -- Rostedt will write a personal wrapper script that runs `git diff` first and prompts if there are pending changes before invoking `git reset --hard`, confirming no built-in upstream mechanism exists for this. Participant positions: Steven Rostedt originated the request, clarified he sought a pre-command hook rather than default behavior change, described his temporary-branch workflow, tested and rejected the no-`--hard` alternative due to the 72,642-file diff, and accepted the maintainer's rejection by opting for a personal script; Mirko Faina (mroik@delayed.space) proposed making `--keep`-like behavior the default for `--hard` via config with a `--force` override; Junio C Hamano (gitster@pobox.com) rejected any change that alters the default or config-overridable behavior of `git reset --hard`, arguing that castrating an existing command becomes impractical once widely adopted and would break automation expectations, urged the community to identify root workflow problems and develop less drastic alternatives so users do not reach for `--hard` in normal operation, and in his final message reconfirmed that recovery from bare `git reset` is possible via `git diff | git apply -R` in simple cases but becomes messy with added or removed paths, explaining why he avoids bare `git reset` himself. Related work: none mentioned.

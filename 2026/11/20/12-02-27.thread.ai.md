Thread identity: "[PATCH 0/6]" cover letter from Patrick Steinhardt <ps@pks.im> introducing a complete six-patch refactoring series on the packfile lifecycle subsystem, with one behavioral fix at its core. Base commit f7de81456940dd6f3274e461149bba12965de609. Part of his ongoing ODB abstraction and repack machinery overhaul efforts. Patch 1/6 removes packfile statistics from `git fast-import` output; patch 2/6 performs a mechanical rename of packfile lifecycle functions; patch 3/6 inlines `open_packed_git_1()` into `open_packed_git()` and renames the latter to `packfile_open_pack()`; patch 4/6 introduces `packfile_free()` as a dedicated helper combining `packfile_close()` with `free(3p)`; patch 5/6 moves process-wide packfile limits from per-repository scope to a global `all_packfiles` list; patch 6/6 fixes `close_one_pack()` to honor the `do_not_close` flag when selecting packs to close under process-wide limits.

Core problem or goal: polish the packfile API and internals across five patches, then fix process-wide packfile limit handling and honor the do-not-close flag on packfiles in the sixth patch. Patch 1/6 deletes the `pack_report()` function from `packfile.c` and `packfile.h`, strips its invocation from `builtin/fast-import.c` along with now-unused statistics counters (`pack_mmap_calls`, `peak_pack_open_windows`), and updates `Documentation/git-fast-import.adoc` to drop packfile details from the `--stats` description, on the grounds that these metrics expose internal implementation details that become meaningless under pluggable object databases and could later be reintroduced as trace2 output if needed. Patch 2/6 renames packfile lifecycle functions to adopt a consistent `packfile_` subsystem prefix: `open_pack_index` becomes `packfile_open_index`, `close_pack_index` becomes `packfile_close_index`, `close_pack_fd` becomes `packfile_close_fd`, `close_pack_windows` becomes `packfile_close_windows`, `close_pack` becomes `packfile_close`, `add_packed_git` becomes `packfile_from_idx`, and the static helper `alloc_packed_git` becomes `packfile_new`. The author explicitly notes that fully modernizing the subsystem including renaming `struct packed_git` itself would cause excessive churn, so this incremental step focuses only on lifecycle functions. No behavior changes in patch 2/6. Patch 3/6 eliminates the static helper `open_packed_git_1()` by inlining its logic into the former caller `open_packed_git()`, which is simultaneously renamed to `packfile_open_pack()` to match the `packfile_` prefix convention established in patch 2/6. The change fixes a design smell where the `_1()` sibling deferred error cleanup to its caller, risking a leaked file descriptor if the caller failed to close `pack_fd` on error paths. The patch introduces a common `out:` exit label that calls `packfile_close_fd()` whenever `ret < 0`, allowing all error returns inside the function to use `goto out` instead of returning directly. This consolidates the validation logic -- index opening, file descriptor acquisition, stat checks, pack header signature and version verification, object count validation, and trailing hash comparison -- into a single function with uniform cleanup. Call sites in `use_pack()` and `is_pack_valid()` are updated to invoke `packfile_open_pack()` instead of the old `open_packed_git()`. No behavioral change is intended beyond the error-path fd cleanup, which should now be more robust. Patch 4/6 introduces `packfile_free()` in `packfile.c` and `packfile.h` as a dedicated function that combines `packfile_close()` with `free(3p)`, replacing the repetitive two-step pattern currently scattered across nine call sites in `builtin/index-pack.c`, `commit-graph.c`, `connected.c`, `http-walker.c`, `http.c`, `midx-write.c`, and `odb/source-packed.c`. It also swaps bare `free(p)` calls for `packfile_free(p)` in the error paths of `parse_pack_index()` and `packfile_from_idx()` inside `packfile.c` itself, ensuring consistent resource handling even when the pack was not fully opened. The commit message notes this abstraction will be extended in a subsequent patch to maintain a list of all packs, foreshadowing the process-wide limit tracking that arrives in patch 5/6. No behavioral change is intended; this is pure API consolidation. Patch 5/6 introduces a static global `struct packfile_list all_packfiles` in `packfile.c`. `packfile_new()` now appends every new `struct packed_git` to this list via `packfile_list_append()`, and `packfile_free()` removes it via `packfile_list_remove()` before closing and freeing the pack. This global list replaces the previous per-object-database iteration: `close_one_pack()` and `unuse_one_window()` no longer take a `struct repository *` or `struct object_database *` parameter, and they iterate over `all_packfiles` directly instead of walking `odb_source_files_downcast()` directories. This removes the hard assumption that the "files" source is in use, which the commit message identifies as a prerequisite for pluggable object databases. The change affects the enforcement of two limits: `pack_max_fds` (maximum open file descriptors for packfiles) and `core.packedGitLimit` (maximum mapped packfile data). Both now scan the global list to find least-recently-used packs or windows to close when limits are exceeded. The patch is behavior-preserving for single-repository use but enables true process-wide limits across multiple repositories and future non-files backends. Patch 6/6 modifies `close_one_pack()` in `packfile.c` to skip any packfile whose `do_not_close` bit is set when selecting a pack to close in order to stay under the process-wide open-pack limit, adding the check `e->pack->do_not_close` alongside the existing `pack_fd == -1` condition in the loop over the global `all_packfiles` list. The commit message explains that the `do_not_close` flag is currently only set by `git fast-import`, which allocates its packs manually and therefore never adds them to the `all_packfiles` list, meaning `close_one_pack()` would never encounter them anyway; the author characterizes this as fragile coincidence rather than proper design, and the fix makes the limit-enforcement logic explicitly respect the flag regardless of how the pack was allocated. The change touches only three lines in `packfile.c` and is intended to produce no user-visible behavior change.

Open questions and loose ends: Junio C Hamano reviewed patch 1/6 and raised substantive feedback requiring revision in v2. He corrected the commit message's claim about what `pack_report()` outputs, clarifying that it actually prints `getpagesize()`, `core.packedGitWindowSize`, `core.packedGitLimit`, `pack_used_ctr`, `pack_mmap_calls`, and current/peak values for `pack_open_windows` and `pack_mapped`, rather than just "number of packs opened". He also identified a missed user-visible string: the `--stats` option description in `cmd_fast_import()`'s `fast_import_option[]` array in `builtin/fast-import.c` still reads "display some basic statistics (objects, packfiles and memory)" and must drop the packfile reference. He confirmed that removing `pack_report(repo)` correctly allows the `repo` parameter of `cmd_fast_import()` to be marked `UNUSED`, and that deleting the four counters (`pack_mmap_calls`, `pack_open_windows`, `peak_pack_open_windows`, `peak_pack_mapped`) is clean. No objections to the core change were raised. A v2 incorporating these wording corrections, the accurate description of removed statistics, and the `--stats` option string fix is expected. Junio C Hamano reviewed patch 3/6 and identified a concrete accounting bug in the new error path: when `git_open()` succeeds but the subsequent `fstat()` fails, the code jumps to `out:` and calls `packfile_close_fd()`, which decrements the global `pack_open_fds` counter even though the increment happens only after the `fstat` check passes, potentially causing `pack_open_fds` to underflow to `UINT_MAX`. He notes this is likely not a new bug -- the old code would have leaked the descriptor instead -- but recommends fixing the counter handling while the area is being touched; aside from this fix he considers the patch "looking good" and the consolidation sound. Junio C Hamano also reviewed patch 6/6 and questioned the premise of the fix: since the only code that sets the `do_not_close` bit is `git fast-import`, and fast-import allocates its packs manually without adding them to `all_packfiles`, the limit-enforcement code would never encounter such a pack anyway. He suggested that if the sole user of the bit does not rely on `close_one_pack()` honoring it, a simpler alternative would be to retire the `do_not_close` bit entirely rather than adding logic to respect it, challenging the author's characterization of the current behavior as "fragile coincidence" and proposing removal of the flag as dead weight instead. Junio C Hamano reviewed patch 4/6 and accepted it with a plain "OK", but raised a design question about NULL handling conventions: he observed that all current call sites of `packfile_free()` never pass NULL, so the current implementation is acceptable, but suggested considering whether the function should guard against NULL to match the `free()` semantics and make future call sites safer.

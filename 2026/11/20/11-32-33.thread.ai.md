Thread identity: standalone bugfix patch from Abhishek Agarwal (`agab0323@gmail.com`) for `git submodule update --jobs`; no series version. Thread type: bug report/fix.

Core problem: make `--jobs` on `git submodule update` handle zero and negative values consistently with `submodule.fetchJobs` and `git fetch --jobs`. Since commit 51243f9f0f (2022-10-12), `--jobs=0` reaches a `BUG()`/aborts with “you must provide a non-zero number of processes!”, while `--jobs=-1` produces the misleading “data too large to fit into virtual memory space” error. Before v2.39, values below 1 silently meant `online_cpus()`.

Proposed fix: add validation/defaulting in `module_update()` in `builtin/submodule--helper.c`: die with “'--jobs' cannot be negative” for negative values and substitute `online_cpus()` for zero, following commit c39952b925 (2023-02-20) for `git fetch --jobs=0`. Documentation for `git-submodule(1)` and `git-clone(1)` would say “A value of 0 will use some reasonable default.”

Tests: three new cases in `t/t7406-submodule-update.sh` covering `--jobs 0` via `GIT_TRACE` task-count output, rejection of negative values, and propagation through `git clone --recurse-submodules --jobs 0`.

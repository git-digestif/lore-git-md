Thread identity: v3 patch series (4 patches) from Dirk Gouders <dirk@gouders.net>; this email is patch 3/4, a bugfix to UTF-8 display-width calculation. Thread type: patch series.

Core problem: `utf8_strnwidth()` in `utf8.c` computes column width of a string while optionally skipping ANSI escape sequences. When `skip_ansi` is enabled and an ANSI escape sequence consumes bytes up to or beyond the given `len` boundary, the function previously proceeded to call `utf8_width(&string, NULL)` on a pointer that had reached or passed the `end` boundary, risking an out-of-bounds read or incorrect width count.

Current status: v3 of the series, patch 3/4 under review. No merge status stated.

Key technical details: Fix adds a guard after the ANSI-skipping loop in `utf8.c`: if `string >= end`, the loop breaks immediately rather than decoding a glyph beyond the buffer. Old behavior unconditionally called `utf8_width()` after skipping; new behavior terminates early and returns only width accumulated so far. Change is 10 lines in `utf8.c`. Tests added in `t/unit-tests/u-utf8-width.c` under new function `test_utf8_width__strnwidth_ansi()`, exercising three corner cases with string `"\033[31mhello"` and length arguments 4, 5, and 6 (11 lines of tests).

Open questions: Whether the `>=` boundary check is sufficient for all callers, or whether similar guards are needed elsewhere `display_mode_esc_sequence_len()` is used. Patch 3/4 likely depends on or complements earlier patches in the series; cover letter not included in this email.

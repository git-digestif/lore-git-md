This is a design-discussion reply closing out a feature request, not a patch. Steven Rostedt responds to Junio C Hamano's rejection of a config-based safety prompt for `git reset --hard` by clarifying that he was not asking to change the default behavior, only whether a pre-command hook mechanism (something like a `.gitrc` entry that runs before a command executes) could exist. He then explains his actual workflow: he frequently creates temporary topic branches, copies their SHA-1, and runs `git reset --hard <sha>` on his main topic branches to fast-forward them to the temp branch state, which is why he reaches for the destructive command so often. Accepting Junio's advice to address the root cause rather than alter the existing command, Rostedt says he will simply write a personal wrapper script that runs `git diff` first and prompts if there are pending changes before invoking `git reset --hard`, and thanks the list for confirming there is no existing built-in mechanism for this. The thread now stands with the maintainer opposed to any modification of `git reset --hard` semantics in `builtin/reset.c`, the specific proposal for a `reset.*` config key or `--force` bypass flag rejected, and the original poster pivoting to a client-side workaround rather than further upstream change.

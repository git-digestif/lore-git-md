This is the fourth and final patch of Harald Nordgren's v9 series, a feature that extends `git branch --delete-integrated` to detect squash-merged or rebased branches even when upstream modified the same files before integrating them. The patch introduces a path-by-path three-way merge approximation using `ll_merge()`: for each file the branch changed, it merges the branch's version into the upstream commit's version and treats the change as landed when that merge leaves the upstream version byte-identical. This handles the common hosting-service workflow where a "Squash and merge" lands a pull request on top of other changes that touched the same files.

What distinguishes v9 from the previous iteration is the fix for a confirmed crash that Jasper Mayone identified in v8: when a path was a gitlink (submodule) at the merge base but became a regular file on both sides, the code passed a commit OID to `read_mmblob()`, which died with `fatal: unable to read blob object`. The fix adds a `base_mode` field to `struct branch_change`, populates it during change collection, and extends the guard in `change_state_at()` to return `CHANGE_MISSING` whenever the base mode is not a regular file, so such branches are correctly kept rather than crashing. A regression test for this scenario appears in `t/t3200-branch.sh`.

The implementation lives in `builtin/branch.c` alongside documentation updates and roughly 140 lines of new tests covering squash-merges onto upstream-modified files, partial landings, conflicts, and the gitlink regression. The merge step reads the repository index once up front and uses `.gitattributes` from the working tree and index, matching what a local merge would see; in a partial clone this may trigger blob downloads, which the documentation now notes explicitly.

The series remains under review with no integration status announced. Patches 1/4 through 3/4 are refactoring and the core rebase-detection machinery, both considered uncontroversial, while this patch carries the heaviest algorithmic content. Known limitations still open for discussion include the lack of rename detection, the "npm update" false-positive scenario where upstream independently reimplements the same change (for which author-check or patch-id mitigation has been proposed but not implemented), and performance on large repositories or blobless clones.

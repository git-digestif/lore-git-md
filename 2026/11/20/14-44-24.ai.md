This is a bugfix and the first patch of a four-part series (v3) that hardens the UTF-8/ANSI escape-sequence parser against buffer over-reads. Dirk Gouders modifies `display_mode_esc_sequence_len()` in `utf8.c`/`utf8.h` to accept an optional `const char *end` parameter alongside the existing start pointer. When `end` is NULL the function behaves exactly as before, treating the input as a NUL-terminated string; when `end` is non-NULL it never dereferences `*end` or anything beyond it, which lets callers that work on counted buffers avoid scanning past their allocation.

The patch updates all in-tree callers to pass the correct boundary. `utf8_strnwidth()` now computes `end = string + len` and forwards it, `strbuf_add_wrapped_text()` sets `end = text + strlen(text)`, and `strbuf_utf8_replace()` passes along the `end` it already receives. The one caller in `pretty.c` (`format_and_pad_commit()`) passes `ch + 1` as the end pointer. The commit message notes that this change avoids the O(n^2) degradation risk Andy Koppe previously flagged, since the scan remains bounded.

To guard the new behavior, the patch adds a new clar unit-test file `t/unit-tests/u-utf8-ansi.c` (wired into both `Makefile` and `t/meson.build`) with three test cases: one exercising the NULL-end legacy path with various SGR sequences, one exercising explicit end pointers at exact sequence boundaries, and one checking that swapped start/end pointers safely return 0.

The patch is co-signed by Junio C Hamano, indicating maintainer involvement, and the commit message is clear about the motivation: some callers operate on `<string, len>` pairs and must not read past `len`, while the old single-argument API relied on NUL termination and could read out of bounds on non-NUL-terminated counted buffers. The diff is small and focused, touching only the parser, its four call sites, the header, and the new tests.

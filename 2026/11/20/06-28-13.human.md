This is a **substantive review** of a test infrastructure patch. Junio C Hamano is responding to Kaartic Sivaraam's v2 patch that serializes `EXPENSIVE` tests to prevent out-of-memory failures on CI runners, and he has identified two serious flaws in the proposed locking mechanism.

Junio traces a TOCTOU race in `acquire_expensive_lock_()`: if process T1 releases the lock (removing the directory) just after waiter T2 reads the PID but before T2 checks whether that PID is alive, and T3 successfully acquires the lock in between, T2 will see T1's dead PID, delete T3's active lock directory, and then acquire the lock itself -- allowing T2 and T3 to run memory-intensive tests concurrently, defeating the purpose of the lock.

He also identifies a deadlock risk: if a process is killed by SIGINT, SIGTERM, or SIGHUP between creating the lock directory with `mkdir` and writing its PID to the `pid` file, the `die()` handler will call `release_expensive_lock_()` but `have_expensive_lock_` is still unset, so the directory is left behind with no valid PID. Waiters will then loop forever waiting for a lock that exists but has no owner to detect as stale. Junio notes that this deadlock is worse than the race because it blocks all `EXPENSIVE` tests entirely.

The review is thorough and engages directly with the concurrency semantics of the patch -- this is exactly the kind of feedback that needs to be addressed before the patch can be considered safe for parallel test execution under `prove --jobs`, the Makefile, or Meson.

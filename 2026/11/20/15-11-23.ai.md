This is a cover letter for a five-patch bugfix series (v4) targeting the UTF-8 display-width code in `utf8.c`, reposting the previously withdrawn v3 as an un-squashed series. Dirk Gouders sends it to replace v3, which he had retracted after discovering it was sent in a malformed state; v4 contains the same substantive content but with the final two patches split apart for clarity.

The series addresses bounds handling in `utf8_strnwidth()` and `utf8_width()` so they respect their length arguments and do not read past buffer ends, alongside a documentation correction for `utf8_strnwidth()`. Patch 1, authored by Junio C Hamano, introduces `display_mode_esc_sequence_len(const char *start, const char *end)`, an end-pointer variant that scans for ANSI SGR sequences without reading at or beyond `end`. Patches 2 through 5, by Gouders, fix the bounds violations in `utf8_strnwidth()` by computing a `remainder` and passing it to `utf8_width()`, correct the misleading comment about return values, and add `display_mode_esc_sequence_len_all(const char *start, const char *end)` to greedily consume all consecutive leading SGR sequences. The range-diff shows that what was patch 4 in v3 is now split into patch 4 (`utf8_strnwidth()` boundary fixes) and patch 5 (the new `_all` helper).

The series touches `utf8.c`, `utf8.h`, `pretty.c`, the `Makefile`, `t/meson.build`, and adds unit tests in `t/unit-tests/u-utf8-ansi.c` and `t/unit-tests/u-utf8-width.c`. Call sites in `utf8_strnwidth()`, `strbuf_utf8_replace()`, `strbuf_add_wrapped_text()`, and `pretty.c` are updated to use explicit end pointers. Tests include `test_utf8_ansi__sgr_len_greedy` and `test_utf8_width__strnwidth_cjk_chopped` to verify chopped multibyte sequences return the `len` argument rather than reading out of bounds.

Within the thread, this v4 repost resolves the open question of how to re-present the series after the v3 retraction; the end-pointer design settled in v3 is preserved, and Andy Koppe has already indicated he will update his separate `make_line_colors_self_contained()` work to the new API. No version of this series has been merged or queued in any integration branch; it is under review awaiting substantive feedback on the v4 formulation.

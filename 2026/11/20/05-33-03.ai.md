This is a bugfix targeting the untracked cache interaction with fsmonitor. Maik Riechert reports that after a failed fsmonitor query or a trivial response, `git status` in normal mode can incorrectly list both an untracked directory and a directory nested beneath it (for example "?? three/" alongside "?? three/deep/"). The root cause traces to commit 1cf98cb4d9 ("fsmonitor: check the untracked cache after a trivial response"), which added a stat check to invalidate stale cached directories but failed to propagate that invalidation upward to parent directories.

The patch modifies `invalidate_stale_dirs()` in `dir.c` to also call `invalidate_one_directory()` on the immediate parent when the `DIR_SHOW_OTHER_DIRECTORIES` flag is set and at least one child was invalidated. This mirrors the existing behavior of `invalidate_one_component()` and intentionally leaves the all-files mode unchanged to avoid adding extra stat calls during traversal. The change is small -- six lines in `dir.c` -- and reuses the existing directory walk logic.

Testing is added in `t/t7519-status-fsmonitor.sh` with two new regression tests covering both trivial and failed fsmonitor responses. The tests construct a scenario with a check-only cached directory, force a stale state by changing the directory mtime, write the index without scanning untracked files using `update-index --force-write-index`, and verify that `git status --porcelain` does not report both the parent and child directories as untracked. The tests use `test-tool chmtime` to control directory timestamps deterministically.

The commit message is clear about the mechanism: in normal mode, a parent's cached untracked list can contain an entry like "three/" from a check-only scan of the child, and when the child's invalidation clears its check-only flag, the next cached walk recurses into the child and reports the deeper path while the parent entry remains stale. The patch addresses this by ensuring ancestors are invalidated in the same pass.

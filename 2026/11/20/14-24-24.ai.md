This is the fourth patch of a v9 feature series adding `git branch --delete-integrated <pattern>`, specifically implementing change-based detection for squash-merged branches when upstream has also modified the same files, plus the v9 bugfix for a gitlink-to-blob type-confusion crash.

Patch 4/4 extends the `--delete-integrated` logic so that a branch is considered landed not only when an upstream commit contains the branch's exact version of every changed file, but also when merging the branch's version into the upstream version leaves the upstream version byte-identical. This handles the common "Squash and merge" workflow on hosting services where upstream commits modify the same files the branch touched. The implementation adds `merge_keeps_upstream()` in `builtin/branch.c`, which reads the base, upstream, and branch blobs via `read_mmblob()` and invokes `ll_merge()` with the repository index to perform a path-by-path three-way merge honoring `.gitattributes`; a change counts as landed only when the merge result equals the upstream blob exactly. The index is read once up front in `find_landed_commits()` via `repo_read_index()` for performance. The check runs in two passes within `changes_landed()`: first evaluating each path via `change_state_at()` for exact tree-entry matches (`CHANGE_LANDED`) or mismatches (`CHANGE_MISSING`), then invoking `merge_keeps_upstream()` only for paths marked `CHANGE_NEEDS_MERGE`.

The v9 iteration also incorporates the crash fix identified in v8: `struct branch_change` gains `base_oid` and `base_mode` fields, populated in `collect_branch_changes()` from the diff's `p->one` side. The guard in `change_state_at()` now returns `CHANGE_MISSING` when `!S_ISREG(change->base_mode)`, preventing `read_mmblob()` from being called on a commit OID when a path changed from a gitlink (submodule) to a regular file, which previously caused `fatal: unable to read blob object`. Documentation in `Documentation/git-branch.adoc` now explicitly notes that the merge-based detection reads file contents and may download blobs in partial clones.

Tests in `t/t3200-branch.sh` cover three new scenarios: a squash-merged branch where upstream subsequently changed the same file (expecting deletion with "landed as" attribution), branches whose changes did not fully land or conflicted (expecting retention), and the gitlink-to-blob regression case where a branch replaced a submodule with a file while upstream did the same (expecting the branch to be kept). Open limitations remain: no rename detection, potential blob fetches in partial clones, and the unresolved "npm update" false-positive scenario where upstream independently reimplements the same changes without author-check or patch-id mitigation.

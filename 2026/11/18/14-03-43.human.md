This is a bug report against the built-in fsmonitor daemon on Linux, filed by John Mellor.

The report describes a data-loss hazard: when a directory is moved into the working tree from outside the repository (a plain `mv` on the same filesystem), fsmonitor fails to watch the directory itself. As a result, `git status`, `git diff`, `git add -u`, `git commit -a`, and `git stash` all ignore modifications made to files directly inside that moved directory, while edits in subdirectories are still detected. The reporter provides a concise shell reproduction that reliably triggers the issue on both Git 2.56.1 and `next`.

The consequences are serious because the invisibility extends to safety checks. `git checkout` and `git rm` do not see the local modifications either, so they can silently discard uncommitted work -- for example, checking out a previous commit will delete a file with unsaved changes rather than refusing, and `git rm` will remove the file instead of warning about local modifications. The bug persists for all subsequent edits in that directory until the daemon is restarted.

Mellor traces the root cause to `compat/fsmonitor/fsm-listen-linux.c`. When the daemon receives an `IN_MOVED_TO|IN_ISDIR` inotify event for a directory arriving from outside the watch tree, `rename_dir()` takes a branch that only logs "no matching cookie" and returns without calling `add_watch()` on the path itself. The subsequent `register_inotify()` call then adds watches for subdirectories but not for the directory itself, leaving files directly inside it unmonitored. `GIT_TRACE_FSMONITOR` output confirms the move event is seen but no events for `pkg/top.txt` ever arrive. A suggested fix is to call `add_watch(path, data)` in that branch.

The report notes this is related to, but distinct from, Erik Cervin-Edin's earlier report about subdirectories of directories renamed within the working tree. Overall, this is a well-crafted bug report: it includes exact reproduction steps, trace logs pinpointing the missing events, a plausible root-cause analysis in the relevant source file, and a clear statement of the user-visible impact, making it immediately actionable for anyone working on the fsmonitor backend.

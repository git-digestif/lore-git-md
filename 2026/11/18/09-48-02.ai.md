This is a substantive review reply within the ongoing `[PATCH v2]` thread for the `utf8.c` bounds-safety fix, specifically disputing whether ECMA-48 colon sub-separators in ANSI SGR sequences require a finite state machine or can be handled by a simple character-class expansion. Andy Koppe pushes back against Dirk Gouders's earlier claim that allowing colons would need an FSM, arguing instead that the SGR parameter field is defined as any mix of digits, colons, and semicolons, where semicolons separate parameters, colons separate subparameters, and empty subparameters are equivalent to zero. He maintains that Git does not attempt to validate whether a particular sequence has terminal semantics -- just as it does not for colon-less sequences -- and that well-behaved terminals ignore valid sequences they do not understand, so the parser should likewise accept the full syntactic range without semantic validation.

The email references the specific code under discussion in `display_mode_esc_sequence_len_counted()` in `utf8.c`, where the parameter-scanning loop currently uses `isdigit(*p) || *p == ';'` and Andy had previously proposed changing this to `*p >= '0' && *p <= ';'` to include colons cheaply. Dirk had rejected this both for bisection cleanliness (keeping the bounds-safety fix separate from parser extensions) and on the technical ground that proper ECMA-48 sub-separator validation would require an FSM. Andy now concedes the bisection point -- acknowledging it was "silly" to suggest sneaking the change in -- but firmly rejects the FSM requirement, spelling out the grammar rule that makes a simple character-class check sufficient for syntactic validity.

For future reference, the contested function is `display_mode_esc_sequence_len_counted(const char *s, size_t len)` in `utf8.c`, which scans exactly `len` bytes to find the length of a complete SGR sequence at the buffer start.

This is patch 1/4 of a v2 bugfix series by Elia Pinto converting `builtin/unpack-objects.c` from `unsigned long` to `size_t` for object sizes, addressing truncation of objects >=4 GiB on platforms where `long` is 32 bits but `size_t` is 64 (notably 64-bit Windows). The patch is part of a larger four-patch series fixing large-object handling across the pack-receiving and verification pipeline; patches 2-4 touch `index-pack` and `fsck` but this patch alone reworks the unpack-objects code paths.

The conversion spans `struct obj_buffer.size`, `get_data()`, `struct delta_info.size`, `add_delta_to_list()`, `write_object()`, `resolve_delta()`, `added_object()`, `unpack_non_delta_entry()`, `resolve_against_held()`, and `unpack_delta_entry()`. With `size_t` in place, `unpack-objects -n` and non-streamed objects of any size are handled correctly, delta bases >=4 GiB no longer crash the resolution path, and large delta results are not silently truncated. Because downstream functions `odb_write_object()` and `parse_object_buffer()` still accept `unsigned long` (to be converted in a separate follow-up series), the patch introduces `cast_size_t_to_ulong()` guards inside `write_object()` so that oversized objects die with "object too large to read on this platform" rather than being written with truncated contents. The cast previously present in `unpack_delta_entry()` is removed since `base_size` is now `size_t` throughout.

The commit message notes that `stream_blob()` was already converted to `size_t` in master by commit `e07ac16d1c`, so this patch focuses on the remaining paths. No tests are included because reproducing the bugs requires 4 GiB objects or a 32-bit `long` platform; the author describes verifying fixes by simulating truncation to 16 bits. The series is based on master at `e1ec09b23c` and remains under review with no merge status indicated.

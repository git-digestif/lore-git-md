This is patch 3/4 of a bugfix series addressing object-size truncation on platforms where `unsigned long` is 32 bits while `size_t` is 64 bits (notably 64-bit Windows). Authored by Elia Pinto as part of the v2 series "[PATCH v2 0/4] Fix truncation issues with large objects on 32-bit platforms," this specific patch targets `builtin/index-pack.c` to eliminate false "SHA1 COLLISION FOUND" errors when receiving objects of 4 GiB or more that already exist in the local object database.

The patch converts the size parameter type from `unsigned long` to `size_t` across several functions in the pack-receiving path: `sha1_object()`, `append_obj_to_pack()`, the `consume` callback parameter of `unpack_data()`, `compare_objects()`, and the `buf_size` field of `struct compare_data`. On 32-bit-`long` platforms, the old `unsigned long` parameter truncated the true 64-bit `size_t` value held in `struct object_entry`, causing `sha1_object()` to compare the real object size against a truncated value and abort with a spurious collision error. The diff is mechanical, touching six lines in `builtin/index-pack.c` with no change to on-disk format or command-line interface.

Within the broader series, this patch addresses the `index-pack` portion of the large-object pipeline, complementing patch 1/4 (which fixes `unpack-objects`) and patch 2/4 (which fixes `write_compressed()` in `index-pack --fix-thin`). Patch 4/4, not shown here, extends the fix to `git fsck` via the `verify_fn` callback in `pack.h`. The commit message notes that triggering the bug requires processing 4 GiB or more of input on an affected platform, so no regression test is included; verification was reportedly done via size-truncation simulation.

The series remains under review with no merge status indicated and no reviewer objections recorded for v2. Full correctness for non-streamed large objects depends on follow-up work converting `odb_write_object()` and `parse_object_buffer()` to `size_t`, which the cover letter indicates is in flight but not yet queued.

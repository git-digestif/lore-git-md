This is a review reply in the ongoing discussion of a five-patch series that adds HTTP retry logic for POST requests. Ravi Mistry responds to Patrick Steinhardt's objection that retrying POST requests is unsafe for non-idempotent operations, specifically `git push` via `git-receive-pack`, where a retry after a transient 502 or 504 could send duplicate pack data if the server already processed the initial request.

Ravi concurs that this is a "very good point" and commits to restructuring the patch in v4 so that `post_rpc()` retries apply only to read-only services -- `git-upload-pack` and `git-upload-archive` -- while excluding `git-receive-pack`. He also promises to add a test case covering push operations to verify they are not retried.

Within the larger series, this exchange resolves the last major correctness concern on patch 4/5, which extends the new exponential-backoff retry machinery (previously limited to GET requests) to POST-based fetch, clone, and partial-clone transfers. With this fix acknowledged, the series appears technically complete, pending only the procedural question of whether to fold the 10-second default `http.retryAfter` value into patch 2 or keep it as a separate fifth patch.

This is a bugfix to the UTF-8 display-width helper, the fourth and final patch in a v2 series. I have not seen the cover letter for this series, so I cannot relate it to the overall goal beyond what this patch itself states.

The problem is in `utf8_strnwidth()` in `utf8.c`: when given a byte-length boundary, it can slice into the middle of a multibyte character, and in that case it should treat the incomplete sequence as having width according to the remaining bytes. However, the inner call to `utf8_width()` was passing `NULL` for its optional boundary argument, so the width calculation could read past the intended cutoff. The fix computes the remaining bytes (`orig + len - string`) and passes that as the boundary to `utf8_width()`, so incomplete sequences at the end of the range are handled correctly.

The patch also adds two unit tests in `t/unit-tests/u-utf8-width.c` covering a CJK string chopped mid-character by the `len` argument, asserting the expected widths of 1 and 2 columns for one- and three-byte truncations of a wide glyph. The change is small and well-scoped -- five lines in `utf8.c` plus the tests -- and the commit message clearly explains both the symptom and the fix, which makes it easy to assess as a straightforward correctness improvement to a display-width code path used by things like `git log` graph rendering.

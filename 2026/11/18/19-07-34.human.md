This is a bugfix targeting `git maintenance` lock-handling, specifically the first patch of a two-part v4 series by Pushkar Singh that responds to a regression found in the previous iteration. The patch rewrites the failure path in `maintenance_run_tasks()` within `builtin/gc.c` to distinguish three invocation modes when the maintenance lock cannot be acquired: a manual `git maintenance run` now fails with exit code 128 and prints an error (matching `git gc`'s behavior), `--auto` prints a warning but exits 0, and `--schedule` exits 0 silently. The diagnostics are formatted through the shared `unable_to_lock_message()` helper, and the lock file is preserved on failure.

The patch also adds `--no-auto-maintenance` to the child `git fetch` invocations in `fetch_remote()`, preventing the prefetch task from triggering nested automatic maintenance while the parent process holds the lock. This directly addresses the background-run regression that Aniket Gupta identified in v3, where scheduled maintenance was incorrectly failing and prefetch was emitting spurious lock warnings.

Four new tests in `t/t7900-maintenance.sh` cover the manual failure case, `--quiet` suppression, `--auto` warning behavior, and the new silent `--schedule` skip, plus verification that prefetch child processes receive the new flag. The commit message clearly explains the three-mode rationale, and the diff is focused and self-contained. No Reviewed-by or Acked-by trailers are present yet, and whether this fully satisfies the reviewers who flagged the v3 regression remains to be seen.

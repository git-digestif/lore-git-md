This thread is Patrick Steinhardt's four-patch series fixing why `git maintenance run --auto` spawned a needlessly slow `git reflog expire` on every run. The root cause sits in the `reflog-expire` auto-condition in `builtin/gc.c`, which failed to distinguish reachable from unreachable reflog entries during the cheap foreground check, so every entry got tested against `gc.reflogExpireUnreachable` and expiration fired constantly. Patch 3/4 is the real fix -- it compares entry timestamps only against `gc.reflogExpire` and skips the expensive reachability walk entirely, cutting `git maintenance run --auto` on git.git from roughly 385 ms to 18 ms. Patches 1/4 and 2/4 are supporting optimizations in the reftable backend that skip writing a new reflog table to disk during dry-run and no-op expiration runs, and patch 4/4 fixes a copy-paste typo in the maintenance config documentation. Overall the series reports a roughly 46x speedup on the full maintenance path.

Review has been largely converging. Toon Claes substantively approved patch 3/4, agreeing that undercounting prunable unreachable entries is an acceptable tradeoff for fast auto-maintenance, and confirmed the documentation fix on patch 4/4. Karthik Nayak reviewed patches 1/4 and 2/4 without objections, with follow-up questions about a retained future-work comment and a test-coverage question that Patrick answered by pointing to the existing test. The main open question came from Junio C Hamano on patch 1/4: whether the pre-patch dry-run behavior was already correct (making the patch a pure performance optimization) or actually buggy. Patrick has now answered this directly -- the old code wrote the table but then destroyed the addition, unlinking it, so dry-run was already semantically correct and left no persistent changes; patch 1/4 is therefore purely a performance improvement that eliminates wasted I/O, and Patrick will adjust the commit message to say so explicitly.

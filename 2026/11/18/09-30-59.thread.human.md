This thread is Patrick Steinhardt's four-patch series making `git maintenance run --auto` dramatically faster by fixing unnecessary reflog expiration. The root cause was in `builtin/gc.c`: the `reflog-expire` auto-condition tried to evaluate reachability of every reflog entry, treated them all as unreachable, and therefore spawned `git reflog expire` on nearly every maintenance run, adding close to a second of wall time. Patch 3/4 reworks `reflog_expire_condition()` to compare entry timestamps only against `gc.reflogExpire`, skipping the expensive reachability walk so expiration runs only when reachable entries would actually be pruned. Patches 1/4 and 2/4 optimize the reftable backend so that dry-run and no-op `git reflog expire --all` invocations skip writing an identical reflog table to disk, cutting no-op runtime roughly in half. Together the series takes `git maintenance run --auto` on git.git from about 853 ms to under 20 ms, with memory usage down about 31 percent.

The series is now complete with the arrival of patch 4/4, which touches no code: it fixes a copy-paste typo in `Documentation/config/maintenance.adoc` where the description of `maintenance.reflog-expire.auto` incorrectly referenced `maintenance.loose-objects.auto` instead of itself. Patches 1 and 2 are covered by tests in `t/t0610-reftable-basics.sh` confirming the reftable table list is untouched by dry-run and no-op expirations.

The series is at version 1 and under review; it has not been merged or queued in any of Junio's integration branches, and no reviews or acks have been recorded yet. The main open item is review feedback on the reachability fix in `builtin/gc.c`, which is the substantive change reviewers are most likely to scrutinize.

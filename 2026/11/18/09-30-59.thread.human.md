Patrick Steinhardt has submitted a four-patch series addressing slow reflog expiration during `git maintenance run --auto`, which was spawning `git reflog expire` unnecessarily because the auto-condition in `builtin/gc.c` failed to distinguish reachable from unreachable entries, causing nearly one-second hangs. The series optimizes the reftable backend to skip disk writes during dry-runs and no-op expirations (patches 1/4 and 2/4), reworks the reachability logic in `builtin/gc.c` to only trigger expiration when reachable entries would actually be pruned (patch 3/4), and fixes a documentation typo in `maintenance.adoc` (patch 4/4). Benchmarks on git.git show the overall maintenance run dropping from roughly 853 ms to 18.6 ms.

Karthik Nayak has now provided substantive reviews of both patch 1/4 and patch 2/4, confirming the technical approach is correct with no objections. On patch 1/4 he noted that a stale "Future improvement" comment about skipping unchanged records remains in the code despite patch 2/4 implementing exactly that optimization. On patch 2/4 he walked through the `has_changes` tracking logic line by line, agreeing that the `memcmp` on `old_hash` and `oideq` on the tip OID correctly detect no-op cases, suggested a minor documentation tweak to the early return comment, and asked whether a similar test could be added to patch 1/4's dry-run path. Patches 3/4 and 4/4 have not yet received review feedback.

The series remains under review at version 1 and has not been queued in any of Junio's integration branches. The main open items are the stale comment cleanup in patch 1/4, the documentation nit and test suggestion on patch 2/4, and review of the reachability fix in patch 3/4 and the doc typo fix in patch 4/4.

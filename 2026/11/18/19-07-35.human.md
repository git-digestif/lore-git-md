This is the second patch in Pushkar Singh's v4 two-patch series on `git maintenance` lock handling, adding observability via a Trace2 data event. It is a feature patch focused on diagnostics: when `git maintenance run` operates in `--auto` or `--schedule` mode and fails to acquire the maintenance lock, it now emits a `"lock/skip"` event under the `"maintenance"` category with the OS error string from `strerror(err)`. Manual invocations deliberately suppress this event, preserving the existing fail-fast behavior with exit code 128 and an error message.

The patch sits directly alongside patch 1/2 (which adjusts the exit behavior for scheduled runs and passes `--no-auto-maintenance` to child fetches) and responds to the v3 regression reported by Aniket Gupta, where background runs were failing loudly. By tracing lock skips only for non-manual modes, the series gives operators a way to detect repeated silent skips in automated maintenance without changing the manual failure semantics. The tests in `t/t7900-maintenance.sh` verify that `--auto` and `--schedule=hourly` both emit the expected Trace2 data with reason "File exists", that scheduled runs remain silent on stderr, and that manual runs do not produce the event even under `--quiet`.

The change is small and well-scoped, touching only `builtin/gc.c` and the maintenance test script. It looks like a solid addition to the series, though as with the rest of v4, confirmation from reviewers -- particularly Aniket Gupta -- that this matches expectations for background-run diagnostics is still pending.

This is a bugfix patch -- the third of four in Elia Pinto's v2 series addressing object-size truncation on platforms where `unsigned long` is 32 bits (notably 64-bit Windows) while `size_t` is 64 bits. It targets `builtin/index-pack.c`, converting the size parameters of `sha1_object()`, `append_obj_to_pack()`, and the `compare_objects()` callback (plus the `unpack_data()` consume function pointer) from `unsigned long` to `size_t` to match how `struct object_entry` already tracks sizes.

The motivation is a correctness bug that appears when receiving a pack containing an object of 4 GiB or larger that already exists locally. On affected platforms, the old `unsigned long` parameter silently truncates the real 64-bit size, so `sha1_object()` compares the genuine `size_t` value against the truncated one and incorrectly reports a false "SHA1 COLLISION FOUND", aborting `git index-pack`. Switching these functions to `size_t` removes the false positive and ensures large objects are sized correctly throughout the indexing path.

The diff is small and mechanical -- six lines changed across four functions -- with no behavioral difference on platforms where `unsigned long` and `size_t` share the same width. The commit message notes that no test is added because reproducing the issue requires generating multi-gigabyte objects or running on a 32-bit-`long` platform. This patch sits alongside the other three in the series, which cover `unpack-objects`, the `write_compressed()` helper, and `git fsck`; together they address the pack-receiving and verification side of large-object handling, while follow-up work is still needed for `odb_write_object()` and object-parsing paths.

This is a substantive review reply from Patrick Steinhardt on patch v3 3/5 of Ravi Mistry's HTTP retry series, challenging the design decision to make retryable HTTP status codes user-configurable via the new `http.retryStatusCodes` option. Rather than commenting on implementation details, Patrick engages with the architectural choice itself: he argues against pushing the burden onto users to configure their clients for different server behaviors, expressing concern that making the status codes configurable (accepting any code in the 400..599 range, defaulting to 429) will perpetuate ecosystem fragmentation where providers tell users they are "holding it wrong" and need to adjust their configuration. He suggests an alternative direction where Git's new retry capability serves as motivation for providers to standardize on a single error code (429) rather than relying on 5xx codes like 502, 503, and 504, so that the feature "just works" without user configuration. The patch under review introduces the `http.retryStatusCodes` config key and `GIT_HTTP_RETRY_STATUS_CODES` environment variable to allow opt-in retries for transient 5xx responses, replacing the hardcoded 429 check from commit 640657ffd0. Patrick's feedback represents a philosophical pushback against the opt-in design for 5xx retries, favoring ecosystem convergence over flexibility, and leaves open whether the author should reconsider hardcoding 429 only.

This is a substantive review reply from Patrick Steinhardt on patch 2/4 of Elia Pinto's v2 series fixing large-object truncation on 32-bit platforms. The patch itself changes `write_compressed()` in `builtin/index-pack.c` to take and return `size_t` instead of `unsigned int`/`int`, preventing silent truncation when compressing thin-pack bases larger than 4 GiB.

Patrick engages with the actual code behavior rather than surface details. He first questions whether the change could introduce an overflow in the sole caller, which adds the return value to `obj[1].idx.offset` -- a field of type `off_t` (signed) in `struct pack_idx_entry`. While he considers overflow unlikely, he asks whether the code should verify against it regardless, showing he has traced the data flow into the pack index structure.

He also pushes back on the absence of test coverage. When Pinto notes that triggering the bug requires a 4 GiB base, Patrick asks "Not even an EXPENSIVE one?", suggesting that Git's test suite includes expensive tests gated behind configuration for exactly these kinds of impractical-to-run-by-default scenarios. This indicates he expects large-object handling to be covered even if only under `GIT_TEST_*` flags.

The review remains open; Patrick has not given a Reviewed-by or Acked-by, and his questions about `off_t` overflow safety and expensive test coverage are unresolved in this email. The exchange keeps the focus on whether the mechanical type change is fully safe in its caller context and whether the project should invest in test infrastructure for 4 GiB-scale objects despite the practical difficulties.

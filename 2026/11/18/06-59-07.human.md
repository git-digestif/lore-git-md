This is a substantive review reply in the ongoing discussion of Junio C Hamano's bounds-safety patch for ANSI escape sequence scanning in `utf8.c`. Andy Koppe responds to Junio's question about whether Git ever generates colon-separated SGR sequences, conceding that it currently does not but arguing that the function still processes user-controlled content where colons could appear.

Andy points out that `display_mode_esc_sequence_len()` already operates on expanded custom formats, commit message text via `rewrap_message_tail()` and `strbuf_wrap()`, and stdin in `git-column`. These inputs could contain SGR sequences using colons as sub-separators (such as `ESC[38:5:123m`), whose display width is currently not ignored as intended. He notes that his proposed `make_line_colors_self_contained()` would not reset or replay such sequences either.

To address this, Andy suggests changing the parsing condition from `isdigit(*p) || *p == ';'` to `*p >= '0' && *p <= ';'`, which cheaply includes colons since ASCII `':'` falls between `'9'` and `';'`. This is a concrete, low-cost suggestion that would make the scanner handle the full ECMA-48 parameter syntax rather than only the subset Git currently emits itself.

The exchange leaves the colon question technically unresolved but now properly framed: the issue is not whether Git generates such sequences, but whether the width-counting code should correctly handle them when they appear in user-supplied text.

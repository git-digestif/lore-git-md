This is a substantive maintainer review of the first patch in Tanga Joris's three-part bugfix series for `apply.c`. Junio C Hamano rejects the proposed test case as inadequate and argues against the patch's implicit goal of silently ignoring malformed `diff --git` lines.

Junio points out that the test only passes because both the bogus and legitimate `diff --git` lines reference the same file `g`; if the bogus line named a different file (e.g., `f`), the code would emit an "inconsistent old filename" error rather than ignoring the line. He states explicitly that such corrupt patch input should be diagnosed as an error, not normalized or skipped. He further notes that `find_header()` currently fails to clear `patch->old_name`, `patch->new_name`, and related state when `parse_git_diff_header()` returns early after seeing a `diff --git` line followed by an unrecognized line, which is the root cause of the stale-state issue the series is trying to address. His position is that `find_header()` must do more work when punting back to the caller, clearing the patch struct before continuing the search, and that the series should aim to reject corrupt headers outright rather than tolerate them. This review aligns with his broader guidance in the thread that `git apply` should accept only patch formats generated by `git diff` or `git format-patch` and should reject anything else as corrupt input.

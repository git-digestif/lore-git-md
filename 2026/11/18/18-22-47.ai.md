This is a performance patch targeting the interaction between `diff-lib` and the fsmonitor daemon. It modifies `check_removed()` in `diff-lib.c` so that entries marked `CE_FSMONITOR_VALID` return immediately after `fake_lstat()` fills in the stat data, skipping the subsequent `has_symlink_leading_path()` call (which `lstat()`s each leading directory component) and the `S_ISDIR()` check. The commit message argues these checks are redundant for fsmonitor-valid entries: if a leading directory had been replaced by a symlink, fsmonitor would have reported the change and `refresh_fsmonitor()` would have cleared `CE_FSMONITOR_VALID` for all entries beneath it, meaning the code path would never be reached with the flag still set. The author notes that `preload_index()` already trusts the flag in this way by skipping these entries entirely, and that gitlinks are never marked valid so the `S_ISDIR()` check cannot trigger.

The patch cites commit `4f3d6d0261` (fsmonitor: skip lstat deletion check during git diff-index, 2021-03-17) as the prior change that stopped `lstat()`ing the file itself for valid entries, leaving only the leading-path `lstat()` calls as remaining overhead. With this change, `git diff HEAD` on Linux with 100,000 files drops from 57ms to 26ms when using a hook that reports no changes and the cache is warm.

Three new tests are added to `t/t7519-status-fsmonitor.sh`. The first verifies the shortcut itself by replacing a parent directory with a symlink without informing fsmonitor, expecting `git diff-index --name-status HEAD` to output nothing. The other two verify that when fsmonitor does report the directory (with and without a trailing slash in the hook output), the deletion is still detected, since no other code path checks for this case anymore.

The patch is a single standalone contribution (not part of a series), authored by Maik Riechert, and is currently under review on the mailing list with no integration branch status indicated.

This is a substantive review of the second patch in Adrian Ratiu's three-patch series fixing crashes and misleading errors when a submodule is a linked worktree. Junio C Hamano agrees that the motivation behind `[PATCH 2/3]` -- avoiding the confusing "Enabling extensions.submodulePathConfig should fix this" message when the extension is already enabled -- sounds sensible, but he pushes back on the implementation approach and the surrounding code structure.

Junio points out that `submodule_name_to_gitdir()` already handles a similar situation with a hedged message ("might fix... if it's not already enabled") rather than checking the actual configuration state, suggesting this lighter-touch approach might simplify the code. He also notes that `clone_submodule()` in `builtin/submodule--helper.c`, another caller of `validate_submodule_git_dir()`, has the same unconditional suggestion and may need similar treatment. His main structural concern is that the patch makes an already deeply nested block in `submodule_move_head()` even harder to read, and he wonders whether the entire "if not dry-run" block should be extracted into a private helper function.

The review engages with specific code paths -- citing `submodule_name_to_gitdir()`, `clone_submodule()`, and the `repository_format_submodule_path_cfg` flag that Adrian's patch checks -- and proposes a refactoring to improve readability, which qualifies as substantive rather than surface-level feedback.

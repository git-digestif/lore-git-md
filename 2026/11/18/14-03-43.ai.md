This is a bug report against the Linux fsmonitor daemon, not a patch.

John Mellor reports that when a directory is moved into the working tree from outside it (via a plain rename on the same filesystem) while the built-in fsmonitor daemon is running, the daemon fails to watch the moved directory itself. Edits to files directly inside that directory become invisible to `git status`, `git diff`, `git add -u`, `git commit -a`, and `git stash`, while files in subdirectories are still detected. Worse, `git checkout` and `git rm` do not see the modifications either, so they can silently discard uncommitted changes -- a data-loss hazard. Disabling fsmonitor (`core.fsmonitor=false`) makes the problem disappear.

The reporter traces the cause to `compat/fsmonitor/fsm-listen-linux.c`. On an `IN_MOVED_TO|IN_ISDIR` event, `process_event()` calls `rename_dir()` and then `register_inotify(path)`. Because the directory originated outside the watch tree, there is no matching `IN_MOVED_FROM` cookie, so `rename_dir()` takes its "Directory was moved from outside the watch tree" branch, which only logs "no matching cookie" and returns without adding a watch for the directory itself. `register_inotify()` then adds watches for subdirectories but not for the top-level moved path (unlike the `IN_CREATE` branch which calls `add_watch(path)` first). The suggested fix is to call `add_watch(path, data)` in that branch of `rename_dir()`. The bug is reproducible on 2.56.1 and on `next` (720f3f593), and is related to but distinct from a separate report by Erik Cervin-Edin concerning subdirectories of directories renamed within the working tree.

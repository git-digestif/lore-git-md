This is a design-debate reply within Ravi Mistry's `[PATCH v3 0/5]` series on HTTP retry handling, specifically defending patch 3/5 which introduces the `http.retryStatusCodes` config key. Ravi is responding to Patrick Steinhardt's suggestion that Git should hardcode retries to HTTP 429 only and use the new retry capability as leverage to push providers toward standardizing on that single code, rather than letting users configure other codes.

Ravi pushes back on the convergence argument by distinguishing rate limiting from other transient failures: while 429 signals deliberate rate limiting, 502/503/504 typically indicate reverse proxy timeouts, CDN failures, or temporary server overload. He argues these are semantically distinct and that retrying them by default could be unsafe in setups where a 5xx points to a permanently broken proxy. The design compromise he defends keeps 429 as the sole default retryable code but allows CI systems and administrators to opt in centrally via `http.retryStatusCodes` for environments where 5xx responses are known to be transient.

The exchange leaves Patrick's architectural objection open: whether Git should offer the configurability at all or instead force ecosystem alignment on 429. No resolution is reached in this email. For future thread summarization, note that patch v3 3/5 touches `http.c`, `remote-curl.c`, and adds the `GIT_HTTP_RETRY_STATUS_CODES` environment variable alongside the config key, with the default remaining `"429"`. The broader series context includes exponential backoff via `http.retryAfter` (default 10s), POST request retries, and an off-by-one fix in the original 429 retry loop from commit 640657ffd0.

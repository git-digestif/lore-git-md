This is a bugfix for `git ls-tree` that corrects the handling of the `%(path)` placeholder when both `-z` and `--format` are used together. Since commit 455923e0a1 introduced the `--format` option in 2022, the custom format output has always applied C-style quoting to paths via `quote_c_style()`, even when `-z` requested null-terminated verbatim output. The patch makes `ls-tree` emit the path verbatim when `options->null_termination` is set, matching the documented behavior and aligning with `git ls-files --format`, which already handles `-z` correctly.

The change is confined to `show_tree_fmt()` in `builtin/ls-tree.c`, where the code now branches on `options->null_termination`: if true, it appends the raw path with `strbuf_addstr()`; otherwise it falls back to the existing `quote_c_style()` call. This preserves existing behavior for non-`-z` invocations while fixing the null-terminated case. The commit message explicitly references the inconsistency with `ls-files` as the motivation, noting that `-z` is documented to produce verbatim filenames.

Test coverage is added in `t/t3104-ls-tree-format.sh`, which now includes a setup step creating a commit with a non-ASCII filename (נעם, Hebrew characters) to ensure the verbatim output works with paths that would normally trigger quoting. The new test runs `git ls-tree -z --format="%(objecttype) %(path)"` and verifies the output contains the raw UTF-8 path followed by a NUL byte, comparing against an expected file built with `printf`.

This is a standalone single-patch series (v1, 1/1) with no cover letter, based on commit 03b41523c576f26ad34085378717a0c1b287470f. The patch is small, well-motivated by the documentation discrepancy, and includes a regression test, so it appears ready for review. Future discussion in this thread would likely focus on whether any other placeholders in `ls-tree --format` need similar treatment or whether the `ls-files` behavior itself is the correct reference point.

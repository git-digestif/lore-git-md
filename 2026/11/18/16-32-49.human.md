This is a **bugfix**, the third patch in Adrian Ratiu's three-patch series addressing a crash when a submodule is itself a linked worktree of its repository. The series responds to a bug report from Andreas Wendleder where `git checkout --recurse-submodules` hits a `BUG()` in `validate_submodule_legacy_git_dir()` because a linked-worktree gitdir (e.g. `.git/modules/sub/worktrees/sub1`) does not end with the submodule name.

This final patch teaches `submodule_move_head()` to accept a linked worktree as a valid submodule git directory. A new helper, `validate_submodule_gitfile_dir()`, detects when the gitfile points into `<common-dir>/worktrees/<id>` and validates the common dir against the submodule name instead of the worktree id. When a linked worktree is detected, the code skips two destructive actions: rewriting the `.git` file to point at the superproject's default submodule gitdir (which would break the worktree), and unsetting `core.worktree` during submodule removal (which would print spurious errors). A forged path that has a `commondir` file but does not live under `<common-dir>/worktrees/<id>` is rejected with a clear error.

The patch adds tests to `t/t2405-worktree-submodule.sh` covering recursive checkout with a submodule worktree in both legacy and `extensions.submodulePathConfig` modes, plus a removal case verifying `core.worktree` is left untouched. It also adds a negative test to `t/t7450-bad-git-dotfiles.sh` ensuring a forged worktree gitdir is rejected without mentioning the extension. The series remains under review with no indication of merge to `master`, `next`, or `seen`.

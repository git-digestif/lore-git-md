This is the v4 cover letter for a two-patch series fixing `git maintenance` lock acquisition handling, posted by Pushkar Singh as a direct response to the regression identified in v3. The series modifies `builtin/gc.c` and `t/t7900-maintenance.sh` to distinguish three invocation modes when the maintenance lock cannot be acquired: manual runs fail with exit code 128 and an error message, `--auto` runs warn and exit 0, and `--schedule` runs stay silent and exit 0. The v4 changes specifically address the background-run regression by checking `opts->schedule` in `maintenance_run_tasks()` to keep scheduled maintenance non-fatal, and by passing `--no-auto-maintenance` to child `git fetch` processes in `fetch_remote()` so the prefetch task does not trigger nested automatic maintenance or emit spurious lock warnings. The second patch extends the Trace2 `"lock/skip"` data event under the `"maintenance"` category to cover both `--auto` and `--schedule` modes, recording `strerror(err)` as the reason, while manual invocations continue to suppress this event. New tests in `t/t7900-maintenance.sh` verify scheduled runs skip silently with a preserved lock file, prefetch child fetches receive the new flag, and manual quiet mode neither traces nor prints diagnostics. The key technical distinction from v3 is the added `opts->schedule` branch that returns 0 instead of -1, and the `--no-auto-maintenance` argument appended to the prefetch fetch command line. Follow-up discussion will likely focus on whether this fully resolves the background regression Aniket Gupta reported and whether the Trace2 coverage for scheduled runs matches maintainer expectations.

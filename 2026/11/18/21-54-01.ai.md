This is a substantive review reply on patch 5/5 of the v3 HTTP retry series, where Ravi Mistry accepts Patrick Steinhardt's point about the `Retry-After: 0` edge case and commits to a fix in v4.

Patrick had asked whether the implementation ignores an explicit `Retry-After: 0` header, arguing a server should be able to instruct an immediate retry. Ravi agrees and explains the technical constraint: libcurl's `CURLINFO_RETRY_AFTER` returns `0` both when the header is absent or malformed and when the server explicitly sends `Retry-After: 0` or a past HTTP-date, so the current `retry_after > 0` check cannot distinguish these cases. In v4, Ravi will inspect the raw `Retry-After` header when `CURLINFO_RETRY_AFTER <= 0` so that an explicit `Retry-After: 0` or past HTTP-date triggers an immediate retry, while absent or malformed headers still fall back to the `http.retryAfter` default (10 seconds). This matters for load balancers that return `Retry-After: 0` to signal the rate limit has cleared and the client may proceed without delay.

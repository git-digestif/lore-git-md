This is a post-merge follow-up to the recently merged `git rerere` subcommand refactoring, in which Patrick Steinhardt commits to fixing a cosmetic error-reporting regression.

The series in question, `[PATCH v4 00/12] builtin/rerere: convert to use subcommands`, replaced the hand-rolled subcommand parser in `builtin/rerere.c` with Git's standard `OPT_SUBCOMMAND()` machinery. It was merged to `master` on 2025-06-25. In this email, Patrick responds to Junio C Hamano's observation that on the `seen` branch, running `git rerere unknown` now produces a generic "too many arguments" message, whereas on `master` it helpfully lists the valid subcommands (`clear | forget | diff | status | remaining | gc`) in the usage output.

Patrick acknowledges the regression with a brief "True, will fix," confirming he will restore the more informative error message that enumerates available subcommands when an invalid one is given. This is distinct from the option-ordering regression (`git rerere --skip-locked gc` no longer working) that Junio had already accepted as a deliberate trade-off; the error-reporting issue is a genuine usability regression that Patrick has agreed to address.

This email is part of a small cluster of post-merge follow-ups Patrick has committed to: in addition to this error-message fix, he previously agreed to correct a potential NULL-termination memory-safety issue in the synthetic "perform" fallback logic introduced in patch 11, and to update the stale prose in `Documentation/git-rerere.adoc` regarding `git rerere diff` accepting extra arguments. None of these reopen the merged series; they are targeted fixes to be sent as separate patches.

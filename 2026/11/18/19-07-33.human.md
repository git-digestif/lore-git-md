This is a bugfix and observability patch series -- specifically the v4 cover letter for a two-patch effort to correct how `git maintenance run` handles lock acquisition failures across different invocation modes.

Pushkar Singh has posted v4 to address a regression identified in v3: background-scheduled maintenance runs (started via `git maintenance start`) were incorrectly failing with a non-zero exit code when another process held the lock, contradicting documented behavior. The series now distinguishes three invocation modes: explicit manual runs fail with exit code 128 and an error message (matching `git gc`), while both `--auto` and `--schedule` invocations skip non-fatally with exit code 0. The first patch also fixes a secondary issue where the prefetch task triggered spurious lock warnings by passing `--no-auto-maintenance` to its child `git fetch` processes, preventing nested automatic maintenance.

The second patch adds Trace2 instrumentation for lock skips in both automatic and scheduled modes, emitting a `"lock/skip"` data event under the `"maintenance"` category with the `strerror` reason. This gives operators visibility into repeated lock contention without affecting exit codes. Tests in `t/t7900-maintenance.sh` now cover manual failure, quiet suppression, automatic skips, scheduled skips, and the prefetch child-process arguments.

The series looks well-crafted and directly responsive to the feedback that surfaced after v3. It resolves the behavioral inconsistency between manual and background runs while adding diagnostic data, and the patch splitting aids reviewability. It remains under review with no merge status indicated.

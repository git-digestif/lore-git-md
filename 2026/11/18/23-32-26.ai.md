This is a review reply in an ongoing bugfix thread, specifically Tanga Joris responding to Junio C Hamano's critique of patch 1/3 in a three-part Outreachy series that fixes an assertion crash (`patch->is_new <= 0` in `check_preimage()`) in `git apply --check` when processing malformed patch headers. The series targets `apply.c`, specifically the interaction between `find_header()` and `parse_git_diff_header()`.

Junio had pointed out that the test in 1/3 only passed because the bogus `diff --git` line referenced the same file (`g`) as the legitimate one following it; with a different filename the code would emit an "inconsistent old filename" error rather than ignoring the line. Tanga confirms this behavior and agrees that such corrupt input should be diagnosed as an error rather than silently skipped or normalized.

Rather than fixing the memory leak in `parse_git_diff_header()` as proposed in 1/3, Tanga now proposes a simpler approach: `find_header()` should stop and report a corrupt patch immediately when it encounters a `diff --git` line with nothing after it, instead of continuing to search subsequent lines. This would render patch 1/3 unnecessary and simplify patch 2/3 significantly. Tanga notes that modern Git does not generate empty `diff --git` headers (verified with whitespace-only changes, renames, and merges), and that existing apply and am tests pass with this stricter behavior.

The email captures a moment of convergence toward the stricter validation strategy Junio has endorsed throughout the thread: rejecting any header format not generated by `git diff` or `git format-patch`. Tanga is seeking explicit confirmation that this approach matches Junio's intent before preparing a v4 iteration of the series.

This is a substantive review from Junio C Hamano identifying a potential crash edge case in the squash-merge detection logic of Harald Nordgren's `[PATCH v8 4/4]` series. Although v8 4/4 contains only documentation changes relative to v7, the code under discussion was introduced in the earlier iterations and remains present; Junio is examining `collect_branch_changes()`, `change_state_at()`, and `merge_keeps_upstream()` in `builtin/branch.c`.

Junio flags a scenario where a path that was originally a gitlink (submodule pointer) in the merge base has been replaced with regular files on both the branch and the upstream. In `collect_branch_changes()`, the `base_oid` is recorded from `p->one->oid`, which in this case is the submodule's commit object rather than a blob. Later, `change_state_at()` compares modes and object IDs: because both the branch and upstream now have regular files at that path, the mode check passes, all three OIDs differ, and none is null, so the function returns `CHANGE_NEEDS_MERGE`. This causes `changes_landed()` to invoke `merge_keeps_upstream()`, which calls `read_mmblob()` on `change->base_oid` -- a commit OID from the submodule -- leading to a crash when attempting to read it as a blob.

The review traces the exact code flow: `change_state_at()` currently guards on `S_ISREG(mode)` for the upstream entry but does not verify that `base_oid` refers to a blob before returning `CHANGE_NEEDS_MERGE`, and `merge_keeps_upstream()` unconditionally calls `read_mmblob()` on all three OIDs. Junio ends with the question "Or am I misreading the code flow?", indicating he is seeking confirmation that this path is indeed reachable or asking the author to verify whether the diff machinery can produce such a state. This is a correctness concern about robustness against type-confusion between gitlinks and blobs, distinct from the performance and `.gitattributes` issues that were resolved in earlier versions.

This is a **bugfix** targeting the submodule subsystem, specifically the first patch in a three-patch series from Adrian Ratiu. The email changes `validate_submodule_legacy_git_dir()` in `submodule.c` to return a regular error via `error()` instead of aborting with `BUG()` when the submodule name is not a suffix of the git dir path. This matters because commit `9cf8547320` (2024-01-28, "clone: prevent clashing git dirs when cloning submodule in parallel") introduced a caller that passes a git dir path read from a gitfile on disk, making the previously unreachable `BUG()` triggerable when the on-disk layout does not match expectations, such as when `.git/modules/sub` has been renamed or the submodule is a linked worktree.

The patch preserves the existing "refusing to create/use ..." error semantics by emitting the same style of error message that users see when `extensions.submodulePathConfig` is enabled, but now also applies in the legacy mode. The original `BUG()` was added in commit `a8dee3ca61` (2019-10-01) under the assumption that callers only passed git dirs computed internally from the submodule name, so a mismatch implied a programming error; the new caller violates that assumption. The commit message clearly traces this history and includes a `Reported-by` trailer for Andreas Wendleder, who reported the original crash.

The diff touches `submodule.c` (8 lines changed) and adds a test to `t/t7450-bad-git-dotfiles.sh` that renames a submodule git dir, points the gitfile at it, and verifies that `git checkout -f --recurse-submodules` fails with the new error message and without hitting `BUG`. The series applies on base commit `e1ec09b23c8e0deb21a0b95ac5996422277395d4`. This patch is patch 1 of 3; patches 2 and 3 (not shown here) address a misleading `extensions.submodulePathConfig` hint and accepting linked worktrees as valid submodule git dirs respectively. The change is well-motivated, minimal, and fixes a genuine reachable crash rather than an internal invariant violation.

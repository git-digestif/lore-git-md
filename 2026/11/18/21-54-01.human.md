This is a review reply on the fifth and final patch of the v3 HTTP retry series, addressing a specific edge case in how the `Retry-After` header interacts with the new 10-second default backoff.

Patrick Steinhardt asked whether the implementation ignores an explicit `Retry-After: 0` header, arguing that a server should be able to instruct an immediate retry. Ravi Mistry agrees and confirms the current code cannot distinguish between an absent header and an explicit zero. libcurl's `CURLINFO_RETRY_AFTER` returns 0 for absent or malformed headers, but returns a value less than or equal to zero when the server sends `Retry-After: 0` or a past HTTP-date; the existing `retry_after > 0` check therefore treats all of these the same way, falling back to the 10-second default even when the server explicitly requested no delay.

Ravi commits to fixing this in v4 by inspecting the raw `Retry-After` header whenever `CURLINFO_RETRY_AFTER` is less than or equal to zero. This will allow an explicit `Retry-After: 0` or a past HTTP-date to trigger an immediate retry, while still falling back to `http.retryAfter` for absent or malformed headers.

The exchange is narrow and technical, focusing on header precedence rather than the default value itself, which the thread has already settled at 10 seconds. It illustrates the kind of edge-case scrutiny the series has received, and Ravi's willingness to adjust the parsing logic in the next iteration suggests the final version will handle both server-directed immediate retries and the configured backoff more precisely.

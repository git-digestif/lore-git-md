This is a **bugfix** cover letter for a three-patch series targeting the submodule subsystem. Adrian Ratiu sends `[PATCH 0/3]` to fix crashes and broken behavior when a submodule is itself a linked worktree of its repository and the superproject performs a recursive checkout (`submodule.recurse=true`). The series directly addresses the bug reported earlier by Andreas Wendleder, where `validate_submodule_legacy_git_dir()` in `submodule.c` hits a `BUG()` because linked-worktree gitdirs (e.g., `.git/modules/sub/worktrees/sub1`) do not end with the submodule name, and where `extensions.submodulePathConfig` produces a misleading error hint even when enabled.

The series consists of three commits: first, returning a proper error instead of `BUG()` for an unexpected git dir path; second, only suggesting `submodulePathConfig` when that extension is actually disabled; third, accepting a linked worktree as a valid submodule git directory so recursive operations succeed. The diff touches `submodule.c` plus three test scripts -- `t/t2405-worktree-submodule.sh`, `t/t7425-submodule-gitdir-path-extension.sh`, and `t/t7450-bad-git-dotfiles.sh` -- adding coverage for the linked-worktree scenario in both legacy and `submodulePathConfig` modes. The series applies on base commit `e1ec09b23c8e0deb21a0b95ac5996422277395d4`.

For future thread summarization: the root cause traces to commit `9cf8547320` (2024-01-28), which made `submodule_move_head()` validate gitdir paths read from disk, making the previously unreachable `BUG()` triggerable. The misleading `submodulePathConfig` hint was acknowledged by Adrian as a bug in his own extension code. No prior fix exists in `master`, `next`, or `seen`; this series is the first proposed resolution.

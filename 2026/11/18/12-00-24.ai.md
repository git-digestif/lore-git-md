This is a substantive review of the first patch in a five-part bugfix series targeting Git's HTTP 429 rate-limit retry handling. Patrick Steinhardt examines Ravi Mistry's `[PATCH v3 1/5]`, which fixes two distinct defects in code introduced by commit 640657ffd0: an off-by-one error in the retry counter within `http_request_recoverable()` (where pre-decrement `--rate_limit_retries` causes `http.maxRetries=1` to perform zero retries and can wrap to negative values after 401 re-authentication), and a race condition where `CURLINFO_RETRY_AFTER` is queried too late in `http_request()`, after `handle_curl_result()` has already logged an uninitialized `results->retry_after` to Trace2. The fix moves the curl info extraction into `finish_active_slot()` and changes the loop guard to `http_max_retries > 0 && rate_limit_retries-- > 0`.

The review engages with the code's structure and semantics rather than surface details. Patrick suggests the two bug fixes might warrant separate commits rather than one, questions whether `results->retry_after` should be typed as `curl_off_t` instead of `long`, and raises a behavioral question about the post-loop handling: when `http_max_retries <= 0`, the patch returns `HTTP_ERROR` instead of `HTTP_RATE_LIMITED`, which Patrick finds curious since the request is still rate-limited -- he would have expected only the "retries-exhausted" Trace2 message to be skipped while preserving the `HTTP_RATE_LIMITED` return value. He confirms the pre- versus post-decrement fix is correct and notes a minor coding-style nit regarding `case` statement indentation in the test helper `t/lib-httpd/http-429.sh`.

The patch touches `http.c` (specifically `http_request_recoverable()` and `finish_active_slot()`) and modifies test infrastructure to support configurable failure counts (2 or 3 failures) via the `test_context` variable pattern. The loop condition change ensures uniform handling of both initial 429 responses and 429s occurring after 401 re-authentication, eliminating spurious "retries-exhausted" logging when no retries were configured. Patrick's feedback is constructive and approving of the technical fixes while probing the organizational choice of combining two logically separate bug fixes into one commit and the error-code semantics in the zero-retry case.

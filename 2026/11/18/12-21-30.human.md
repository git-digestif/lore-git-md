This is a **substantive review** of the first patch in Elia Pinto's five-patch v2 series fixing loose object size handling. Patrick Steinhardt responds to patch 1/5, which adds post-inflation validation to `unpack_loose_rest()` in `object-file.c` to prevent uninitialized heap memory from being exposed when a loose object's compressed data ends early.

Patrick agrees the core problem is real, calling the current behavior "certainly fishy," but asks for clarification on one scenario Elia described: when an object header claims fewer bytes than the stream actually contains, he wants to understand why the stream would have already ended at the point where the extra data is dropped. He concurs with Elia's assessment that the loose object reader should compare `total_out` against the expected size just as the packfile reader does in `unpack_compressed_entry()`, and that any mismatch should be treated as corruption rather than silently tolerated.

The review also surfaces two code-level suggestions. Patrick notes that using `strlen()` on the input buffer is questionable since the buffer is known-bounded, and suggests `memchr(buffer, '\0', size)` would be more appropriate, though he indicates this could be handled in a separate patch. He also asks whether the error message could be more specific when the size mismatch occurs, suggesting the code print exactly what the expected versus actual sizes were rather than a generic "corrupt loose object" message.

This feedback comes as patch 1/5 already carries maintainer approval from Junio C Hamano; Patrick's review adds further technical scrutiny and refinement suggestions without objecting to the fundamental approach.

This is patch 2/2 of Pushkar Singh's v4 series on `git maintenance` lock handling, a Trace2 observability feature that complements patch 1/2's behavioral fixes. The series as a whole aims to make lock-acquisition failures consistent across manual, `--auto`, and `--schedule` invocation modes while improving diagnostics; this second patch specifically adds tracing so that skipped background runs leave a machine-readable record.

The patch modifies `builtin/gc.c` to emit a Trace2 data event via `trace2_data_string("maintenance", r, "lock/skip", strerror(err))` inside `maintenance_run_tasks()` when the maintenance lock cannot be acquired and the invocation is either `--auto` or `--schedule`. The event uses category `"maintenance"` and key `"lock/skip"`, carrying the OS error string (e.g., "File exists") as the value. Manual invocations deliberately suppress this event, and it is emitted regardless of `--quiet`, making it suitable for post-hoc analysis of why scheduled maintenance repeatedly skips.

Tests in `t/t7900-maintenance.sh` verify the three-way distinction: `--auto` with an existing lock emits the Trace2 event, `--schedule=hourly` emits it silently (empty stderr), and manual `--quiet` runs fail without producing the `"lock/skip"` event in the trace file. In all cases the `objects/maintenance.lock` file is preserved.

The technical hook is a four-line addition in `builtin/gc.c` guarded by `if (opts->auto_flag || opts->schedule)`, placed immediately before the existing warning/error logic. No on-disk format changes or new configuration keys are introduced; the feature activates only when Trace2 event tracing is enabled via `GIT_TRACE2_EVENT`.

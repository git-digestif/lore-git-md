This is the third patch in Patrick Steinhardt's four-part performance series on reflog expiration during auto-maintenance, and it targets the root cause described in the cover letter: the `reflog-expire` auto-condition in `builtin/gc.c` was overcounting prunable entries. Because the condition walks the `HEAD` reflog without first performing the reachability walk that `reflog_expiry_prepare()` would set up, every entry was treated as unreachable and checked against `gc.reflogExpireUnreachable`. That made `git maintenance run --auto` spawn `git reflog expire` on nearly every invocation even when the command would have nothing to do.

The patch reworks `reflog_expire_condition()` and its helper `count_reflog_entries()` so that the auto heuristic only compares each entry's timestamp against `gc.reflogExpire` (the threshold for reachable entries), deliberately skipping the `gc.reflogExpireUnreachable` check. The commit message is explicit about the tradeoff: this undercounts entries that could be pruned as unreachable, but in the foreground auto-maintenance path a reachability walk would be too expensive, and users who want aggressive pruning can run maintenance without `--auto` or invoke `git reflog expire` directly. The code itself is a tidy simplification -- it drops the `expire_reflog_policy_cb` machinery in favor of a plain `reflog_expire_options` and a direct timestamp comparison.

The payoff is substantial. On the author's daily `git.git` working copy, `git maintenance run --auto` drops from a mean of 385 ms to 17.9 ms -- a 21.5x speedup -- with memory usage falling about 31 percent, and since auto-maintenance runs after many ordinary commands, the effect is visible constantly.

The change is confined to `builtin/gc.c` with no new tests in this patch itself, but the series as a whole adds coverage in earlier patches for the reftable backend behavior. The commit message is well-motivated, quantifies the improvement clearly, and honestly states the behavioral compromise, which makes it a strong candidate for review. It remains under review; no integration-branch status is claimed.

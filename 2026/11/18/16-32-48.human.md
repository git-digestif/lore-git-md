This is the second patch in a three-part bugfix series targeting the submodule subsystem. Adrian Ratiu sends `[PATCH 2/3]` to fix a misleading error message that appears when a recursive checkout rejects a submodule's git directory.

The specific problem addressed here is that the error output previously ended with "Enabling extensions.submodulePathConfig should fix this" even when that extension was already enabled, confusing users into thinking they needed to turn on something that was already active. The patch moves this suggestion into a separate `advise()` hint -- mirroring how `submodule_name_to_gitdir()` already handles it -- and only displays it when `repository_format_submodule_path_cfg` is actually false. The error message itself is simplified to just the "refusing to create/use" part.

As context, this is part of a larger series responding to a crash reported by Andreas Wendleder, where `validate_submodule_legacy_git_dir()` hits a `BUG()` when a submodule is itself a linked worktree (since linked-worktree gitdirs like `.git/modules/sub/worktrees/sub1` do not end with the submodule name). Patch 1 replaces the `BUG()` with a proper error, this patch fixes the misleading hint in that error path, and patch 3 will accept linked worktrees as valid git directories.

The change touches `submodule.c` and adds test coverage in `t/t7425-submodule-gitdir-path-extension.sh` (verifying the hint does not appear when the extension is enabled) and `t/t7450-bad-git-dotfiles.sh` (verifying it does appear when the extension is disabled). The patch looks clean and well-targeted, with clear commit message and appropriate `Reported-by` attribution.

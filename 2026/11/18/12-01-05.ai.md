This is a substantive review of the fourth patch in the series, which extends HTTP retry logic to POST requests. Patrick Steinhardt identifies a correctness concern: POST requests are not necessarily idempotent, and the patch as written applies retries to all `post_rpc()` calls without distinguishing request types. He specifically points out that `push_git()` uses `post_rpc()` to send data to `git-receive-pack(1)`, and retrying a push request could result in duplicate or corrupted pack data being sent to the server. He suggests the implementation needs to be adapted so that retries are only performed for request types where this is safe, such as fetch, clone, and partial-clone blob downloads, but not for push operations. This is a significant objection because it challenges the core premise of patch 4/5 -- that all POST requests can be treated like GET requests for retry purposes -- and implies the patch needs restructuring to whitelist or blacklist specific RPC types rather than applying the retry logic uniformly across `post_rpc()`.

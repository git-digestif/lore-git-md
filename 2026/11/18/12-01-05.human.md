This is a substantive review of patch 4/5 in Ravi Mistry's five-patch HTTP retry series, identifying a correctness concern about retrying non-idempotent requests. Patrick Steinhardt points out that while the patch extends retry logic to all HTTP POST requests handled by `post_rpc()`, not all POSTs are safe to retry: `push_git()` uses the same code path to send data to `git-receive-pack`, and automatically retrying a failed push could result in duplicate ref updates or other unintended side effects on the server. He suggests the implementation needs to distinguish between request types, applying retries only to idempotent operations like fetch, clone, and partial-clone blob downloads rather than push.

The concern is well-founded and targets the core behavior change of the patch. Patch 4/5 currently treats all `post_rpc()` calls uniformly, but the safety of retrying depends on what the POST is doing. This is exactly the kind of edge case that distinguishes a shallow "looks good" review from one that traces the code path across different callers. The issue remains unresolved in v3, making it a live point of discussion alongside Patrick's earlier architectural objection to configurable retry status codes in patch 3/5.

In the broader context of the series, this adds a new wrinkle to an already active review. While patches 1-3 and 5 have largely converged -- with the 10-second default for `http.retryAfter` settled and most implementation details addressed -- patch 4 now faces a fundamental design question about scope. The series aims to improve resilience during data transfer, but Patrick's comment suggests the current approach may overreach by including push operations where transient failure handling requires more care than simple retry logic can provide.

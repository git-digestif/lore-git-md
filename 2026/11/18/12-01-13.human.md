This is a substantive review of the fifth patch in Ravi Mistry's HTTP retry series, questioning a specific edge case in how the new default `http.retryAfter` value interacts with server-provided `Retry-After` headers.

Patch 5/5 formalizes a 10-second default for `http.retryAfter`, meaning that when a server returns a retryable status code like HTTP 429 without a `Retry-After` header, Git now waits 10 seconds before the first retry and doubles the delay on each subsequent attempt. Patrick Steinhardt is probing the documentation change that specifies a `Retry-After` header is only honored when it contains a "positive delay," which implies that an explicit `Retry-After: 0` would be ignored in favor of the 10-second default backoff.

The question is whether Git should respect a server's explicit instruction to retry immediately. If a server sends `Retry-After: 0`, it is signaling that the client may retry right away without penalty, and ignoring that in favor of a fixed 10-second wait could unnecessarily slow down operations that the server has explicitly cleared for immediate retry. Patrick is asking whether this behavior is intentional or an oversight in the patch's logic.

This review is part of Patrick's broader engagement with the v3 series, where he has raised several correctness and design objections across the earlier patches, including concerns about POST retry idempotency and the configurability of retryable status codes. The `Retry-After: 0` question is a smaller but pointed semantic issue that affects how the new default interacts with existing server behavior.

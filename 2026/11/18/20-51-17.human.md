This is a maintainer review of the first patch in Tanga Joris's three-part bugfix series addressing a crash in `git apply --check`. Junio C Hamano examines the proposed memory leak fix in `parse_git_diff_header()` -- a one-line `free(patch->def_name)` before reassigning it -- and finds it inadequate for the broader problem at hand.

Junio explains that after parsing a `diff --git` header, if an unrecognised line follows (such as a second `diff --git` line), the code sets `patch->old_name` and `patch->new_name` from the first header and returns to `find_header()`, which may continue searching without clearing those stale values. The proposed test only passes because the bogus and legitimate `diff --git` lines happen to name the same file; if they named different files, Git would emit an "inconsistent old filename" error rather than silently ignoring the corrupt line. The `free()` prevents the leak but does not prevent the inconsistent state that causes the original crash.

He argues that such malformed input -- a `diff --git` line followed immediately by another `diff --git` line -- should be diagnosed as corrupt patch input and rejected, not ignored. Simply freeing the memory does not achieve this; `find_header()` would need to do additional work when punting to avoid leaving stale filenames in the patch struct. This aligns with his earlier position in the thread that `git apply` should reject any header format not generated by `git diff` or `git format-patch`.

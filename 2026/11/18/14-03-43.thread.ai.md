Thread identity: bug report (not a patch) from John Mellor <johnme@google.com> against the built-in Linux fsmonitor daemon; thread root, no series version.

Core problem: when a directory is moved into the working tree from outside via a plain same-filesystem rename while the fsmonitor daemon is running, the daemon fails to watch the moved directory itself. Edits to files directly inside that directory become invisible to `git status`, `git diff`, `git add -u`, `git commit -a`, and `git stash`, while files in subdirectories are still detected. Additionally `git checkout` and `git rm` do not see the modifications, so they can silently discard uncommitted changes -- a data-loss hazard. Setting `core.fsmonitor=false` makes the problem disappear.

Current status: reported bug, unresolved, no fix applied or merged; reproducible on Git 2.56.1 and on `next` at commit 720f3f593.

Key technical details: root cause traced to `compat/fsmonitor/fsm-listen-linux.c`. On an `IN_MOVED_TO|IN_ISDIR` event, `process_event()` calls `rename_dir()` and then `register_inotify(path)`. Because the directory originated outside the watch tree there is no matching `IN_MOVED_FROM` cookie, so `rename_dir()` takes its "Directory was moved from outside the watch tree" branch, which only logs "no matching cookie" and returns without adding a watch for the directory itself. `register_inotify()` then adds watches for subdirectories but not for the top-level moved path, unlike the `IN_CREATE` branch which calls `add_watch(path)` first. Suggested fix: call `add_watch(path, data)` in that branch of `rename_dir()`.

Open questions and loose ends: whether maintainers accept the suggested one-line fix or want a broader rework of the move/create watch-registration paths; no reviewer response yet.

Participant positions: John Mellor is the reporter and provides the trace and suggested fix. No Reviewed-by/Acked-by or maintainer response recorded yet.

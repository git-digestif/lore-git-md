Maik Riechert has sent a standalone performance patch to the Git mailing list that optimizes the interaction between `diff-lib` and the fsmonitor daemon. The change modifies `check_removed()` in `diff-lib.c` so that index entries carrying the `CE_FSMONITOR_VALID` flag return early after `fake_lstat()` populates the stat data, skipping the `has_symlink_leading_path()` call (which `lstat()`s every leading directory component) and the subsequent `S_ISDIR()` check. The commit message argues these checks are redundant for fsmonitor-valid entries: if a leading directory were replaced by a symlink, fsmonitor would have reported the change and `refresh_fsmonitor()` would have cleared the flag, so the code path should never be reached with it still set. The author notes that `preload_index()` already trusts the flag in this way, and that gitlinks are never marked valid, so the `S_ISDIR()` check cannot trigger. The patch builds on commit `4f3d6d0261` (2021), which previously eliminated the `lstat()` of the file itself for valid entries, leaving only the leading-path calls as overhead. With this change, `git diff HEAD` on Linux with 100,000 files reportedly drops from 57ms to 26ms with a warm cache and a no-op fsmonitor hook.

Three new tests are added to `t/t7519-status-fsmonitor.sh`: one verifies the shortcut by replacing a parent directory with a symlink without notifying fsmonitor (expecting no output from `git diff-index --name-status HEAD`), and two verify that when fsmonitor does report the change -- with and without a trailing slash in the hook output -- the deletion is still detected, since no other code path covers this case anymore. The patch is currently under review on the list with no integration branch status indicated.

This is a substantive review reply in the ongoing discussion of the `utf8.c` bounds-safety patch, specifically addressing whether the escape-sequence parser should accept ECMA-48 colon sub-separators. The email sits within the `[PATCH v2]` thread for `display_mode_esc_sequence_len_counted()`, where Andy Koppe had proposed extending the parameter loop in the ANSI SGR sequence scanner to accept colons alongside digits and semicolons, arguing that user-supplied text reaching `rewrap_message_tail()` via `strbuf_wrap()` in `pretty.c` or stdin in `git-column` can already contain sequences like `ESC[38:5:123m`.

Dirk Gouders pushes back on two grounds. First, he argues against mixing the colon-separator support into this patch simply for bisection purposes, implying the bounds-safety fix and any parser extension should remain separate, independently revertable changes. Second, and more technically, he contends that allowing colons is not a simple character-class expansion: properly identifying valid ECMA-48 sequences with sub-separators would require a finite state machine rather than the current `isdigit(*p) || *p == ';'` loop condition (or Andy's proposed `*p >= '0' && *p <= ';'` shorthand). This leaves Andy's colon question formally unresolved, with Dirk signaling that cheap inclusion of colons risks accepting malformed sequences without a more robust parser.

For future reference: the contested code is the parameter-scanning loop inside `display_mode_esc_sequence_len_counted()` in `utf8.c`, which currently stops at non-digit, non-semicolon bytes.

This is a substantive review reply in the ongoing thread for the `utf8.c` bounds-safety patch. Andy Koppe concedes Dirk Gouders' point that colon-separator support should not be folded into the current patch for bisection reasons, but he pushes back on Dirk's technical claim that properly handling colons would require a finite state machine.

Andy explains that under ECMA-48, the parameter field of an SGR sequence can legitimately contain any mix of digits, colons, and semicolons: semicolons separate parameters, colons separate subparameters, and empty subparameters are equivalent to zero. He argues that Git does not attempt to validate whether a colon-less sequence has semantic meaning to a terminal, so it need not do so for colon-containing sequences either; well-behaved terminals ignore valid sequences they do not understand. Therefore, accepting colons does not require an FSM, just extending the character set in the scanning loop.

The exchange leaves the colon-separator question formally unresolved but clarifies the technical disagreement: Dirk favors keeping the bounds-safety fix and any parser extension as separate changes with proper validation, while Andy contends that cheap inclusion of colons is safe and consistent with how Git already treats unknown sequences. The underlying patch -- adding `display_mode_esc_sequence_len_counted()` to prevent out-of-bounds reads in non-NUL-terminated buffers -- remains under review, with the authorship handoff to Dirk Gouders still pending repost as `[PATCH v2 1/2]`.

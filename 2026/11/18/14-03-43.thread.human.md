John Mellor has filed a bug report against the Linux fsmonitor daemon describing a data-loss hazard: when a directory is moved into the working tree from outside (via a plain same-filesystem rename) while the built-in fsmonitor daemon is running, the daemon never adds a watch on the moved directory itself. As a result, edits to files directly inside that directory become invisible to `git status`, `git diff`, `git add -u`, `git commit -a`, and `git stash`, while files in subdirectories are still detected. More seriously, `git checkout` and `git rm` also fail to see the modifications, so they can silently discard uncommitted changes. Setting `core.fsmonitor=false` makes the problem disappear.

He traces the cause to `compat/fsmonitor/fsm-listen-linux.c`: on an `IN_MOVED_TO|IN_ISDIR` event, `process_event()` calls `rename_dir()` and then `register_inotify(path)`, but since the directory came from outside the watch tree there is no matching `IN_MOVED_FROM` cookie, so `rename_dir()` takes its "moved from outside the watch tree" branch, which only logs and returns without watching the directory itself; `register_inotify()` then watches subdirectories but not the top-level moved path. The suggested fix is to call `add_watch(path, data)` in that branch. The bug reproduces on Git 2.56.1 and on `next` (720f3f593), and is related to but distinct from a separate report by Erik Cervin-Edin about subdirectories of directories renamed within the working tree.

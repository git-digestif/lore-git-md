This is **patch 2/4 in v2 of a bugfix series** targeting object-size truncation on platforms where `unsigned long` is 32 bits (notably 64-bit Windows) while `size_t` is 64 bits. Authored by Elia Pinto, the series converts size parameters from `unsigned long`/`unsigned int` to `size_t` across the pack-receiving and verification pipeline to prevent crashes and data corruption when handling objects of 4 GiB or more.

This specific patch modifies `write_compressed()` in `builtin/index-pack.c`, changing both the `size` parameter and the return type from `unsigned int`/`int` to `size_t`. The function is called by `append_obj_to_pack()` when resolving thin packs via `git index-pack --fix-thin`. The bug manifests when the local base object is 4 GiB or larger: the old 32-bit `unsigned int` parameter silently truncates the size to `size mod 2^32`, so only that many bytes get compressed into the pack, while the pack header written by `append_obj_to_pack()` still records the full size. Later, when `unpack_data()` attempts to resolve deltas against this base, it encounters an early end of the compressed stream and dies with "serious inflate inconsistency".

The change is a single-line diff (one insertion, one deletion) with no accompanying test, as triggering the bug requires processing a local base of 4 GiB or more, which the commit message notes is impractical for the test suite. The author verified the fix by simulating the truncation with 16-bit sizes and a 100 KiB base.

Within the broader series context, this patch sits between patch 1/4 (which converts `builtin/unpack-objects.c` to `size_t` throughout) and patch 3/4 (which converts `sha1_object()` and `append_obj_to_pack()` in `index-pack` to `size_t` to fix false SHA-1 collision reports). The series remains under review with no merge status indicated; v1 received no review comments, and v2 rebases onto master at `e1ec09b23c` where a prior commit (`e07ac16d1c`) already converted `stream_blob()` to `size_t`.

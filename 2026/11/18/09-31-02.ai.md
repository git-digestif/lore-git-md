This is a performance fix targeting the auto-maintenance heuristic in `builtin/gc.c`, and it is the third patch in Patrick Steinhardt's four-part series on reflog expiration performance. The patch reworks `reflog_expire_condition()` so that, when `git maintenance run --auto` decides whether to spawn `git reflog expire`, it no longer attempts to determine reachability of each HEAD reflog entry. Previously the code called `should_expire_reflog_ent()`, which implicitly required a reachability walk via `reflog_expiry_prepare()`; because that preparation was never invoked, every entry was treated as unreachable and compared against `gc.reflogExpireUnreachable`, causing the condition to overcount prunable entries and trigger expiration far more often than necessary.

Instead, the new `count_reflog_entries()` callback simply compares each entry's timestamp against `gc.reflogExpire` (stored as `expire_total` in a `reflog_expire_options` struct) and ignores `gc.reflogExpireUnreachable` entirely. The commit message acknowledges this undercounts entries that are genuinely unreachable, but argues that performing an expensive reachability walk in the foreground during auto-maintenance defeats the purpose of fast heuristics; users who need unreachable-entry pruning can run maintenance without `--auto` or invoke `git reflog expire` directly. The struct `count_reflog_entries_data` is changed from embedding an `expire_reflog_policy_cb` to holding a plain `reflog_expire_options`, and the associated cleanup calls (`reflog_expiry_cleanup`) are dropped since no policy walk is performed.

The practical effect is that `git reflog expire` is now spawned only when reachable entries would actually be pruned, eliminating the near-second hang after commands that trigger auto-maintenance. Benchmarks on git.git show `git maintenance run --auto` wall time dropping from roughly 385 ms to 18 ms (about 21x faster) and memory usage falling from 117 MiB to 81 MiB. The patch touches only `builtin/gc.c`; tests for the series live in the earlier reftable patches (1/4 and 2/4), while patch 4/4 is a documentation typo fix. The series sits on base commit `e1ec09b23c` and remains under review with no recorded acks yet.

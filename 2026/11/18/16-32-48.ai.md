This is a **bugfix**, specifically patch 2 of 3 in Adrian Ratiu's series addressing crashes and confusing error messages when a submodule is a linked worktree during recursive operations.

The patch fixes a misleading hint in `submodule_move_head()` (submodule.c). Previously, when `validate_submodule_git_dir()` rejected a git dir path, the `die()` message unconditionally appended "Enabling extensions.submodulePathConfig should fix this." even when that extension was already enabled, sending users on a wild goose chase. The fix moves this suggestion into a separate `advise()` call that only fires when `the_repository->repository_format_submodule_path_cfg` is false, keeping the fatal "refusing to create/use..." error clean while preserving the hint for users who actually need it.

The change touches three files. In `submodule.c`, the error path now conditionally emits the advice. In `t/t7425-submodule-gitdir-path-extension.sh`, a new test clones with `extensions.submodulePathConfig=true`, creates a conflicting gitdir layout, runs a recursive checkout, and asserts that the error output contains "refusing to create/use" but does *not* mention the extension. In `t/t7450-bad-git-dotfiles.sh`, an existing test is updated to assert that when the extension is disabled, the output *does* contain "enabling extensions.submodulePathConfig" and no `BUG()`.

For future thread context: this patch is tightly coupled to patch 1 (which replaces the `BUG()` with a proper error) and patch 3 (which accepts linked worktrees as valid git dirs). Reviewers should note the use of `advise()` to separate the hint from the fatal error, and the specific config flag checked (`repository_format_submodule_path_cfg`) to determine whether the extension is active.

Thread identity: bugfix patch series v2, patch 3 of 4, authored by Dirk Gouders <dirk@gouders.net>, subject concerning `utf8_strnwidth()` boundary handling in `utf8.c`. Thread type: single bugfix within a larger four-patch v2 series whose cover letter and other three patches have not yet been seen in this thread.

Core problem: `utf8_strnwidth()` in `utf8.c` accepts a `skip_ansi` flag that skips ANSI escape sequences (e.g. SGR color codes) while computing display width, but the ANSI-skipping loop did not verify whether consuming those sequences had already advanced the string pointer to `orig + len`. If an escape sequence ended exactly at the `len` boundary, the code fell through to `utf8_width()` on a position past the boundary, risking an out-of-bounds read.

Current status: v2 series under review; this is the third patch. No integration branch status (master/next/seen) has been stated.

Key technical details: fix is confined to `utf8.c`; wraps the ANSI-skipping `while` loop and adds `if (string >= orig + len) break;` immediately after it. Accompanying unit tests added to `t/unit-tests/u-utf8-width.c` in new test `test_utf8_width__strnwidth_ansi()`, which exercises `"\033[31mhello"` (5-byte red SGR sequence plus "hello") with length arguments 4, 5, and 6, expecting widths 3, 0, and 1 respectively. The length-5 case is the critical regression test where the ANSI sequence consumes exactly the full allowed length.

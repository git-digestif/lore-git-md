Thread identity: [PATCH 4/4] of a four-patch performance series by Patrick Steinhardt addressing slow reflog expiration during auto-maintenance; thread type is patch series, version 1, based on commit `e1ec09b23c8e0deb21a0b95ac5996422277395d4`. Core problem: `git maintenance run --auto` was spawning `git reflog expire` unnecessarily on every run because the `reflog-expire` auto-condition in `builtin/gc.c` failed to evaluate reachability of reflog entries, treating every entry as unreachable and thus checking them against `gc.reflogExpireUnreachable` instead of `gc.reflogExpire`; this caused commands to hang for nearly a second after completion. Current status: series complete and submitted for review, not yet merged or queued in any integration branch; all four patches 1/4 through 4/4 received. Key technical details: patch 1/4 modifies `refs/reftable-backend.c` so that `reftable_be_reflog_expire` returns early when the `EXPIRE_REFLOGS_DRY_RUN` flag is set, skipping the `reftable_addition_commit` call and disk write that previously occurred even during dry-run invocations, yielding roughly 11 percent wall-time reduction for `git reflog expire --all --dry-run` on git.git (from about 414 ms to 369 ms); Patrick Steinhardt has now confirmed that the pre-patch code was already semantically correct for `--dry-run` because it wrote the new table and then called `reftable_addition_destroy()`, which unlinks the table via `reftable_addition_close()`, so the patch is purely a performance optimization eliminating wasted I/O rather than a correctness fix, and he will adapt the commit message to make this discard behavior explicit. Patch 2/4 modifies `reftable_be_reflog_expire` in `refs/reftable-backend.c` to track whether any actual changes occurred via a new `has_changes` boolean; if no reflog entries were deleted, no `EXPIRE_REFLOGS_REWRITE` updates changed the old hash, and no `EXPIRE_REFLOGS_UPDATE_REF` modification altered the tip OID, the function returns early without calling `reftable_addition_commit` or writing a new table to disk, avoiding writing an identical copy of the reflog table once per ref when running `git reflog expire --all` with nothing to expire; benchmarks show `git reflog expire --all` dropping from roughly 736 ms to 370 ms (2x faster) on no-op runs. Patch 3/4 reworks `reflog_expire_condition()` in `builtin/gc.c` to stop attempting reachability determination during auto-maintenance; the new `count_reflog_entries()` callback compares each entry's timestamp only against `gc.reflogExpire` (stored as `expire_total` in a `reflog_expire_options` struct) and ignores `gc.reflogExpireUnreachable` entirely, since performing an expensive reachability walk in the foreground defeats the purpose of fast heuristics. The struct `count_reflog_entries_data` is changed from embedding an `expire_reflog_policy_cb` to holding a plain `reflog_expire_options`, and `reflog_expiry_cleanup` calls are dropped. This causes `git reflog expire` to be spawned only when reachable entries would actually be pruned; benchmarks on git.git show `git maintenance run --auto` wall time dropping from roughly 385 ms to 18 ms (about 21x faster) and memory usage falling from 117 MiB to 81 MiB. Patch 4/4 fixes a copy-paste typo in `Documentation/config/maintenance.adoc`: the description of `maintenance.reflog-expire.auto` incorrectly referenced `maintenance.loose-objects.auto` when explaining threshold semantics, and the patch corrects the reference to point to `maintenance.reflog-expire.auto` itself; it is a single-line AsciiDoc edit touching no code or tests. Patches 1/4 and 2/4 add tests in `t/t0610-reftable-basics.sh` verifying that `.git/reftable/tables.list` remains unchanged across dry-run and no-op expiration invocations but changes when entries are actually expired. The full series comprises: patch 1 optimizing reftable dry-run, patch 2 applying skip-write logic for no-op expirations, patch 3 fixing the reachability logic in `builtin/gc.c` so only genuinely reachable entries trigger expiration during auto-maintenance (the actual root cause fix), and patch 4 fixing the documentation typo in `Documentation/config/maintenance.adoc`. Overall series benchmarks on git.git show wall time dropping from 853 ms to 18.6 ms (45.8x speedup) with memory usage reduced by approximately 31 percent.

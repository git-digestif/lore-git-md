This is a follow-up discussion in the review of the third patch in Adrian Ratiu's three-patch series fixing bugs in the `compatObjectFormat` interoperability layer. The exchange between Adrian Ratiu and Patrick Steinhardt digs into edge cases around malformed commit headers during SHA-1/SHA-256 conversion, specifically whether lines like `"tree"` without a trailing space or `"mergetag "` with empty values should be copied or rejected.

Adrian Ratiu reports that he looked closer at his v1 implementation and found two subtle issues: the converter accidentally copies `"tree "` (with trailing space but no object ID) instead of rejecting it, and worse, an empty `"mergetag "` line followed by continuation lines gets copied with its embedded object ID left unconverted, recreating the very inconsistency the patch tries to fix. He proposes a v2 fix that changes three boundary checks from `<` to `<=` so the converter classifies headers by the key before the first space, exactly matching how `read_commit_extra_header_lines()` and `git commit --amend` treat them. This would reject genuinely malformed known headers while treating truly unknown headers (no space) as opaque data to copy verbatim, keeping both conversion paths in agreement.

Both contributors agree that adding generic header-validation logic inside the converter itself would be wrong, since it would reject lines that `git commit --amend` happily accepts, once again producing compat IDs that cannot be read back. If stricter validation is ever needed, they concur it belongs in fsck, which today ignores headers after `committer`, but that is a separate topic. They also briefly revisit the alternatives listed in the original commit message -- rejecting unknown headers everywhere, maintaining an allowlist, or auto-detecting 40-character hex strings as object IDs -- and confirm that copying unknown headers unchanged remains the only sensible approach given how many tools (Jujutsu being the cited example) embed custom headers.

Patrick Steinhardt floats a forward-looking idea of a standardized `x-obj-` prefix for custom headers whose values are object IDs, which would let Git automatically convert those IDs and treat them as reachable without understanding the header's purpose. Adrian Ratiu agrees this is interesting but explicitly out of scope for this series, preferring to keep the patch count small and focused on the immediate breakages.

Overall the tone is collaborative and the patch 3 direction remains endorsed; the remaining work is mechanical -- applying the `<=` fix, adding a test for the empty-mergetag case, and the cosmetic capitalization/spacing cleanups already promised for v2 across the series.

This is patch 1/4 of the v2 bugfix series "Fix integer truncation in large-file handling" from Elia Pinto, based on master at 50fe5cc63f. It corrects a 32-bit integer truncation in `hashwrite()` by changing the `count` parameter type from `uint32_t` to `size_t` in both `csum-file.c` and `csum-file.h`. The internal write loop already processes data in buffer-sized blocks, so no logic change is needed beyond the signature widening.

The bug manifests when `git pack-objects` writes an entire compressed object buffer in a single `hashwrite()` call and that buffer exceeds 4 GiB -- possible when the object is held in memory, is poorly compressible, and `core.bigFileThreshold` is raised accordingly. With the old `uint32_t` parameter, only `count mod 2^32` bytes are written, silently corrupting the packfile. The author verified this via a 16-bit truncation simulation, which caused `git cat-file` and `git fsck` to fail with "offset beyond end of packfile (truncated pack?)" after `git repack -a -d`.

No test is added because triggering the bug requires an object of 4 GiB or more, which is impractical for the test suite. This patch is unchanged from v1 of the series and, per the thread summary, still awaits substantive technical review; no reviewer has yet confirmed whether the widened type introduces any edge cases in the low-level I/O path.

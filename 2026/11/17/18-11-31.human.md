This is a substantive review reply in the ongoing bugfix thread for `utf8_strnwidth()` bounds handling. Junio C Hamano responds to Dirk Gouders's concession that he would drop his own planned two-function replacement for `display_mode_esc_sequence_len()` in favor of Junio's length-threading illustration. Rather than simply accepting Gouders's original two-function design, Junio proposes a specific split: add a new `display_mode_esc_sequence_len_counted()` that takes an explicit length, while keeping the existing `display_mode_esc_sequence_len()` as a wrapper that calls `strlen()` internally. This preserves the current NUL-terminated calling convention for all existing callers while giving counted-string callers like the `utf8_strnwidth()` fix the bounded interface they need.

Junio notes that his earlier illustration lazily changed all call sites to pass lengths, which would ripple through unrelated code, and points out that other in-flight topics are expected to add more callers to this function. Keeping the original API intact avoids that churn and makes the change more maintainable going forward. The exchange confirms the direction for v2: Gouders will use a counted variant of the escape-sequence parser rather than introducing entirely new `ansi_sgr_nlen` helpers, and the thread remains open pending his respin that also addresses the mmapped-region `SIGBUS` edge case and the post-loop guard inside `utf8_strnwidth()`.

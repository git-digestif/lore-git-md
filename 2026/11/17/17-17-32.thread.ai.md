Thread identity: RFC feature request from Alejandro Colomar (alx+git@kernel.org) proposing a new `-M` flag for `git grep` to enable multi-line pattern matching, borrowing the option name from `pcre2grep(1)`. Thread type: RFC, no patch included; this is the opening message.

Core problem or goal: `git grep -P` currently restricts PCRE2 matching to single lines, even when the pattern uses the `(?s)` dotall modifier, preventing structural searches across line boundaries. Colomar wants `git grep -P -M` to search across lines using PCRE2 features such as recursive subpatterns, backreferences (e.g. `\k<space>`), and dotall mode, enabling searches for multi-line C constructs (e.g. full `SYSCALL_DEFINE3(...)` bodies, multi-line `#define` macros with backslash continuations) directly across the working tree and across history (e.g. `git grep -P -M -f patterns v4.0 -- include/`). Motivation includes searching large codebases like the Linux kernel without the current workaround of `git show <rev>:<path> | grepc`, which requires knowing exact file paths in advance.

Current status: initial proposal awaiting community feedback; no implementation exists.

Key technical details: feature would extend existing `-P` (PCRE) support in `git grep`; relies on PCRE2 multi-line mode; reference tools `grepc`/`grepc_c` generate the complex PCRE2 patterns being targeted; output format concerns include how multi-line matches interact with `git grep`'s line-oriented output, `--heading`, and context flags (`-U`/`-A`/`-B`).

Open questions and loose ends: whether to expose PCRE2 multi-line mode directly; how multi-line matches should be printed given line-oriented output; interaction with `--heading` and context options; whether the feature should be gated behind `-P` or extended to basic/extended regex engines; performance cost of multi-line buffering across large histories.

Participant positions: Alejandro Colomar is the sole participant so far, proposing the feature and asking whether it makes sense to the list. No reviews, objections, or approvals yet.

Related work: `pcre2grep(1)` `-M` option as the model; external `grepc`/`grepc_c` tools that currently require manual piping with single-line `grep -P`; existing `git grep -P` single-line PCRE support.

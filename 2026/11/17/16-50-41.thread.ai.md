Thread identity: single patch authored by Junio C Hamano, now at version 2 (`[PATCH v2]`), touching UTF-8/ANSI escape sequence handling; thread type is a standalone refactoring and bounds-safety fix, not part of a larger series.

Core problem or goal: prevent out-of-bounds reads when scanning for ANSI display mode escape sequences (e.g., `\033[1;31m`) in non-NUL-terminated buffers. Version 2 introduces `display_mode_esc_sequence_len_counted(const char *s, size_t len)` in `utf8.c`, which scans exactly `len` bytes and guarantees it never reads at or beyond `s[len]`, returning the length of a complete sequence at the start of the buffer or 0 if the bytes do not form one. The original `display_mode_esc_sequence_len(const char *s)` is retained as a thin wrapper that calls the counted variant with `strlen(s)`, preserving the existing API for NUL-terminated callers. The commit message notes this is partly preparatory for new external callers wanting bounded scans.

Current status: v2 freshly posted by the maintainer; under review. No integration branch status mentioned.

Key technical details: adds `display_mode_esc_sequence_len_counted()` in `utf8.c` (declared in `utf8.h`) and keeps `display_mode_esc_sequence_len()` as a wrapper. Three callers inside `utf8.c` switch to the counted variant: `utf8_strnwidth()` passes `orig + len - string`; `strbuf_add_wrapped_text()` computes `end = text + strlen(text)` once upfront and passes `end - text` in its loop; `strbuf_utf8_replace()` passes `end - src`. Files touched: `utf8.c`, `utf8.h` only (27 insertions, 9 deletions); unlike v1, `pretty.c` is not modified.

Open questions and loose ends: Dirk Gouders has proposed two changes awaiting Junio's response: (1) an early-return optimization `if (len < 3) return 0;` since the shortest valid SGR sequence `"\033[m"` is three bytes, and (2) a clar unit test suite in a new file `t/unit-tests/u-utf8-ansi.c` (registered in `Makefile` via `CLAR_TEST_SUITES += u-utf8-ansi` and in `t/meson.build`) asserting that `display_mode_esc_sequence_len_counted()` returns 0 for `"\033[m"` with `len=2`, 3 for `len=3`, 5 for `"\033[31m"`, and 7 for `"\033[0;31m"`. Dirk notes an untested variant he examined previously contained an off-by-one error.

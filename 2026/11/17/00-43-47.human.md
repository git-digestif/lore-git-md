This is the second patch in a three-part bugfix series addressing a crash in `git apply --check` when processing malformed patch headers. The series targets the `apply.c` subsystem and is now under final review after incorporating all feedback, including stricter validation, a memory leak fix, and improved error messages.

This patch specifically rejects patches where a `diff --git` line is followed by non-header content (e.g., blank lines or indented mode lines), which previously caused Git to crash due to stale `old_name`/`new_name` values in the `patch` struct. The fix aligns with Junio C Hamano’s guidance to enforce strict parsing rules, rejecting any header format not generated by `git diff` or `git format-patch`. The change is uncontroversial: corrupt patches (like those with blank lines after `diff --git`) are now treated as errors rather than being normalized, and the error message clearly identifies the problematic line number and file.

The patch adds a new check in `find_header()` to detect empty Git headers and die with a descriptive error, preventing the parser from proceeding to `parse_traditional_patch()` with inconsistent state. Test coverage in `t/t4133-apply-filenames.sh` is thorough, verifying rejection of blank lines, indented mode lines, and unrelated text after `diff --git` for new files, deletions, and modifications. The tests also confirm that reverse application (`-R`) fails as expected for deletions with corrupt headers.

This is a well-motivated bugfix with clear technical justification and maintainer endorsement. The stricter validation is a deliberate trade-off—rejecting previously accepted edge cases to enforce robustness—but the change is now uncontroversial and ready for integration. The series merges cleanly with `maint`, `master`, `next`, and `seen`, and the only remaining edge case (empty `diff --git` sections followed by another `diff --git`) is intentionally preserved for now.

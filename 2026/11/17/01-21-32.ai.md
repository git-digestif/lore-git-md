This is a post-merge review comment on patch 10/12 of the now-merged `ps/rerere-subcommands` series, which refactored `git rerere` to use Git’s standard `OPT_SUBCOMMAND()` mechanism. Junio C Hamano, the maintainer, is requesting a retrospective improvement to the commit message of this patch to document the deliberate UI regression it introduced.

The patch itself is a mechanical refactoring that extracts the "gc" subcommand into a dedicated function (`cmd_rerere_gc()`) and scopes the `--skip-locked` option to that subcommand. As part of this change, it removes a test (`--skip-locked is only accepted by gc`) that enforced the old behavior where the global `--skip-locked` flag was rejected for non-"gc" subcommands. The new subcommand-based parser enforces option ordering, which means `git rerere --skip-locked gc` (old syntax) is now rejected, while `git rerere gc --skip-locked` (new syntax) is accepted. This is one of two UI regressions accepted as deliberate trade-offs in the series, the other being degraded error reporting for unknown subcommands.

Junio’s feedback is narrowly focused: the commit message should explicitly state that the test removal was intentional and explain why the regression was deemed acceptable. The rationale, as established in the thread, is that `--skip-locked` is a relatively new option with few users, making now the right time to enforce option ordering. The request is not a demand for code changes (the series is already merged) but a documentation improvement to aid future maintainers who might bisect to this commit while investigating bug reports. The tone is constructive and forward-looking, emphasizing clarity for future readers rather than criticizing the original decision. No further discussion or follow-up is expected on this specific point.

This is a maintainer reply in the v14 `fetchRefmap` series, addressing Phillip Wood's proposal about how command-line refspecs with explicit destinations should interact with the new `remote.<name>.fetchRefmap` config.

Junio C Hamano pushes back on Phillip's suggestion that `git fetch origin src:dst` should ignore both `--refmap` and `fetchRefmap` entirely. He argues that the command-line `src:dst` is overriding the `.fetch` configuration, not the `.fetchRefmap` configuration -- since `.fetchRefmap` provides defaults for `--refmap`, not for the refspec itself. He draws an analogy to how a command-line `--refmap` overriding `.fetch` would be confusing, suggesting the same applies in reverse. Instead, he proposes that if a user wants to ignore the `fetchRefmap` configuration, they should be able to pass `--no-refmap` (or possibly `--refmap=""`) explicitly on the command line.

This is a substantive exchange about configuration precedence semantics. The discussion centers on whether `fetchRefmap` should act as a fallback that command-line refspecs merely supplement, or whether explicit destinations should fully suppress it. The answer affects the override rules documented in the v14 cover letter and determines how users can opt out of the new fetchRefmap behavior when they pass explicit refspecs.

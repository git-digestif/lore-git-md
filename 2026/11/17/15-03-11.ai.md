This is a substantive review of Harald Nordgren's v14 patch 1/5 (introducing `remote.<name>.fetchRefmap`) by Phillip Wood, challenging the current override semantics for command-line refspecs with explicit destinations.

Phillip examines a test case in the patch where `remote.<name>.fetch` contains an explicit destination (`+refs/heads/master:refs/remotes/custom/master`) alongside `remote.<name>.fetchRefmap`, resulting in the fetched ref being stored in both `refs/remotes/custom/master` and `refs/remotes/cabal/master`. He accepts that dual storage might be tolerable when both the refmap and refspec come from config files ("if it hurts don't do it"), but argues it becomes confusing when a user passes `src:dst` on the command line while `.fetchRefmap` is configured, because users expect command-line refspecs to override configuration, not add to it.

He proposes changing the behavior so that both `--refmap` on the command line and the `remote.<name>.fetchRefmap` config are ignored whenever an explicit destination appears in a command-line refspec or in a `remote.<name>.fetch` entry. This would ensure that `git fetch origin src:dst` reliably overrides `fetchRefmap` entirely rather than creating unexpected dual storage.

The review targets `remote.c`, `builtin/fetch.c`, and the test suite (`t5586-fetch-refmap.sh` or `t5510-fetch.sh`), specifically the precedence logic between `remote->fetchRefmap`, command-line refspecs, and `remote->fetch` entries. This is a behavioral semantics issue rather than a cosmetic one, and it touches the architectural question of whether `fetchRefmap` should act as a fallback or be strictly overridden by explicit destinations -- a point of contention in the broader v14 discussion about implicit versus explicit fetch modes.

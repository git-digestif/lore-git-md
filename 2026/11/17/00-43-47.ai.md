This is the second patch in a three-part bugfix series targeting a crash in `git apply --check` when processing malformed patch headers. The series is now in its third iteration and is under final review after incorporating all feedback, including stricter validation, a memory leak fix (in patch 1/3), and improved error messages.

This patch specifically addresses one of the two root causes of the crash: **stale `old_name`/`new_name` values in the `patch` struct** when `parse_git_diff_header()` terminates early (after parsing only the `diff --git` line) while `find_header()` continues searching for valid headers. The issue arises when a `diff --git` line is followed by non-header content—such as a blank line or an indented mode line—causing `parse_git_diff_header()` to stop parsing but leaving `find_header()` to treat the subsequent `---`/`+++` lines as a traditional patch. This corrupts the `patch` struct, leading to an assertion failure (`patch->is_new <= 0`) in `check_preimage()`.

The fix **rejects such patches outright** with a clear error message (`"corrupt patch: empty \"diff --git\" header at <file>:<line>"`), aligning with Junio C Hamano’s guidance to enforce strict parsing rules (only accepting formats generated by `git diff` or `git format-patch`). The patch introduces a new variable, `empty_git_hdr_linenr`, to track the line number of the problematic `diff --git` header and trigger the error when a traditional patch is detected afterward. This approach preserves the existing behavior for empty `diff --git` sections followed by another `diff --git` (per 206de27efa) while rejecting all other corrupt cases.

The test coverage in `t/t4133-apply-filenames.sh` is thorough, verifying that:
- Blank lines or indented mode lines after `diff --git` are rejected for new files, deletions, and modifications (including reverse application with `-R`).
- The error message correctly identifies the line number of the empty `diff --git` header, even when it appears later in the file.
- Previously accepted edge cases (e.g., patches with blank lines after `diff --git`) are now rejected, reflecting the stricter validation.

The patch is technically sound, with a minimal and focused change to `apply.c` and no unintended side effects. The stricter validation is uncontroversial after maintainer and reviewer endorsement, and the error messages are actionable for users. The only remaining edge case—empty `diff --git` sections followed by another `diff --git`—is intentionally preserved, though Junio has hinted this may be revisited in the future. This patch is ready for final review and is expected to graduate soon.

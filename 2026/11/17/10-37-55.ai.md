This is a bugfix, specifically patch 3/4 of Elia Pinto's v2 series fixing integer truncation in large-file handling. It changes the local variable `sz` in `hash_chars()` within `diffcore-delta.c` from `unsigned int` to `size_t`, preventing the buffer size from truncating when rename detection processes files of 4 GiB or more. Previously, only a prefix of such a file was hashed while the similarity score was still calculated against the full (truncated) size, causing true renames to be missed; this affected `git diff -M`, `git log --follow`, and merge rename detection. The author verified the bug by simulating 16-bit truncation, which made `git diff --cached -M` report a delete and add ("D a", "A b") instead of a rename ("R099 a b"), but no automated test is included because triggering the real bug requires a 4 GiB input.

Within the series, this patch is one of the simpler type-widening changes alongside patch 1/4 (`hashwrite()`), while patch 2/4 handles the more involved complete-rewrite diff path and patch 4/4 addresses diffstat totals and `scale_linear()`. According to the thread context, patches 1/4, 3/4, and 4/4 still await substantive technical review; Phillip Wood's earlier feedback on v1 targeted patch 2/4 and has been addressed, but no reviewer has yet examined this `hash_chars()` change in v2. The modification is a single-line type change with no on-disk format implications, but a future reviewer may want to confirm that no downstream code in the rename similarity scoring path assumes a 32-bit size.

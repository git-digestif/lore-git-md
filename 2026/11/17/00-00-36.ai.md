This is a **bugfix** for the `pretty` subsystem, addressing ANSI color handling in custom log formats. It is the second iteration (`v2`) of a single-patch series that fixes two related issues: colors being lost across line breaks (e.g., bold-wrapped subject lines only bold on the first line) and colors leaking into subsequent content (e.g., graph markers or unrelated lines when grepping colored output).

The patch modifies `repo_format_commit_message()` to post-process formatted output when colors are enabled. It scans for ANSI escape sequences, tracks active colors since the last reset, and ensures each line is self-contained by inserting a reset before line breaks and replaying active colors at the start of the next non-empty line (unless it begins with a reset). A final reset is appended if colors remain active at the end. The implementation avoids buffer copies unless necessary, using efficient string scanning (`memchr`, `strcspn`) to minimize overhead.

Key changes since `v1` include clarifying the commit message to explain why custom formats cannot make lines self-contained within multi-line placeholders (justifying the runtime approach), dropping mentions of grepping colored output, and rebasing onto `maint`. The patch also adds a test for embedded and trailing NULs, moves line-break handling into the active-colors branch for efficiency, and comments on NUL handling in `strcspn`.

The test coverage in `t/t4205-log-pretty-formats.sh` is thorough, verifying behavior with line breaks, wrapped lines, empty lines, manual escape sequences, NULs, and `--graph` integration. Junio C Hamano’s review of `v1` endorsed the runtime approach, and this version addresses his feedback without introducing new technical concerns.

This is a well-scoped, well-explained fix for a real usability issue. The code is clean, the tests are comprehensive, and the approach aligns with how default formats already handle colors. No controversy is evident, and the patch is ready for further review or integration.

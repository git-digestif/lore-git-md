This thread concerns a bounds-safety fix to ANSI escape sequence handling in `utf8.c`: Junio C Hamano's `[PATCH v2]` adds `display_mode_esc_sequence_len_counted(const char *s, size_t len)`, which scans a bounded, non-NUL-terminated buffer without reading past its end, while the original `display_mode_esc_sequence_len()` remains as a wrapper. The patch is under review with authorship transferring to Dirk Gouders, who has confirmed he will repost it as `[PATCH v2 1/2]` with his clar unit tests (`t/unit-tests/u-utf8-ansi.c`) as `2/2`; no repost has appeared yet and no integration branch status has been announced.

The most active discussion is a substantive technical dispute sparked by Andy Koppe's question about ECMA-48 colon sub-separators in SGR sequences (relevant to user-controlled input paths like `rewrap_message_tail()` and `git-column`). Andy argues colons can be accepted with a simple character-class expansion because terminals ignore sequences they do not semantically understand. Dirk Gouders has now refined his counter-position: he concedes that the existing parser already functions as a finite state machine accepting the regular language `"\033\[[0-9;]+m"`, so his concern is not the need for an FSM per se but whether merely adding `:` to the accepted alphabet without new states would still guarantee only valid SGR sequences are accepted -- he poses `"\033[:;m"` as a test case and notes the discussion is hard to advance without first defining the exact language the parser should accept. No decision has been recorded on colon support, and Dirk continues to argue it should stay separate from this bounds-safety patch on bisection grounds as well.

Junio has rejected Dirk's proposed `if (len < 3) return 0;` early-return micro-optimization, which Dirk conceded, and accepted Dirk's clar tests for the future series. No Reviewed-by or Acked-by trailers have been recorded, so the series remains open pending Dirk's repost.

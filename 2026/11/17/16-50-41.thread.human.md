This thread concerns a bounds-safety fix for ANSI escape sequence scanning in `utf8.c`, posted by Junio C Hamano as `[PATCH v2]` to prevent out-of-bounds reads when parsing SGR sequences like `\033[1;31m` in non-NUL-terminated buffers. The patch adds `display_mode_esc_sequence_len_counted()` which scans exactly `len` bytes, and authorship is set to transfer to Dirk Gouders, who will repost it as `[PATCH v2 1/2]` with his clar unit tests as `2/2`; that repost has not yet appeared and no integration branch status has been mentioned.

The main open question is whether to extend the parser to accept ECMA-48 colon sub-separators (e.g., `ESC[38:5:123m`), which appear in user-supplied text reaching this code via `pretty.c` and `git-column`. Dirk Gouders argues against folding this into the current patch both for bisection cleanliness and because he believes proper validation requires a finite state machine. Andy Koppe has now pushed back substantively, conceding the bisection point was "silly" but rejecting the FSM requirement: he argues the SGR parameter field is syntactically just a mix of digits, colons, and semicolons where empty subparameters equal zero, and since Git performs no semantic validation of sequences anyway -- terminals ignore what they do not understand -- a simple character-class expansion to `*p >= '0' && *p <= ';'` would accept the full syntactic range without semantic checks. No decision has been recorded on whether Andy's grammar-based argument resolves Dirk's concern about accepting malformed sequences, and the series remains under review with no Reviewed-by or Acked-by recorded.

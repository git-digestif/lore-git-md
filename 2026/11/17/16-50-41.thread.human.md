Junio C Hamano has posted version 2 of a standalone patch that fixes an out-of-bounds read risk when scanning non-NUL-terminated buffers for ANSI display-mode escape sequences in `utf8.c`. The patch adds a new bounds-checked function, `display_mode_esc_sequence_len_counted(const char *s, size_t len)`, which scans exactly `len` bytes, and keeps the existing `display_mode_esc_sequence_len()` as a thin wrapper for NUL-terminated callers. Three internal callers in `utf8.c` switch to the counted variant. The series is under review; no integration-branch status has been announced.

The review so far has been substantive. Dirk Gouders suggested an early-return micro-optimization for very short buffers, which Junio rejected on the grounds that the performance benefit is negligible and unproven; Dirk has since conceded the point. Dirk also supplied a clar unit test suite for the new function, which Junio agreed to incorporate in a likely forthcoming v3, with Dirk explicitly granting permission to use the code. The proposed tests cover several boundary cases, including partial and complete SGR sequences.

The newest reply, from Andy Koppe, proposes a functional extension rather than a fix: he asks whether colons should be accepted alongside digits and semicolons when parsing SGR parameter strings, citing ECMA-48 section 5.4.2, which defines the colon as a sub-separator, and noting that xterm and compatible terminals treat colons as the standard separator, making sequences like `ESC[38:5:123m` common in practice. Junio has not yet responded to this suggestion, so whether colon support will be added remains an open question alongside the pending v3 with the clar tests.

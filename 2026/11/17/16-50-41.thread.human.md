This thread covers Junio C Hamano's `[PATCH v2]` fixing out-of-bounds reads when scanning ANSI display-mode escape sequences in non-NUL-terminated buffers. The patch adds `display_mode_esc_sequence_len_counted(const char *s, size_t len)` in `utf8.c` (declared in `utf8.h`), which scans exactly `len` bytes and never reads past the buffer end, while keeping the original `display_mode_esc_sequence_len()` as a wrapper for NUL-terminated callers. Three internal callers in `utf8.c` (`utf8_strnwidth()`, `strbuf_add_wrapped_text()`, `strbuf_utf8_replace()`) now use the counted variant. The series is freshly posted and under review; no integration-branch status has been announced.

Review has been substantive on two fronts. Dirk Gouders initially proposed an early-return optimization (`if (len < 3) return 0;`) and supplied a clar unit test suite for the new function; Junio rejected the optimization as an unneeded micro-optimization, and Dirk has since conceded that point while explicitly granting permission to use his test code in a new `t/unit-tests/u-utf8-ansi.c`. A v3 incorporating those tests appears likely but has not yet been posted. Separately, Andy Koppe suggested extending the SGR parameter loop to accept colons (`:`) alongside digits and semicolons, citing ECMA-48 section 5.4.2 and xterm behavior for sequences like `ESC[38:5:123m`; Junio has now pushed back by asking whether Git itself ever generates colon-separated sequences, noting this code measures strings Git paints into its own buffers rather than arbitrary user input. That question remains unresolved, with no decision recorded on changing the loop condition.

The change touches only `utf8.c` and `utf8.h` and is partly preparatory for anticipated external callers needing bounded escape-sequence scans. No Reviewed-by, Acked-by, or merge decision has been recorded; the open items are the pending v3 with Dirk's tests and the colon-separator question raised by Andy Koppe.

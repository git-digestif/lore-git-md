This thread concerns a bounds-safety fix in Git's ANSI escape sequence handling in `utf8.c`. Junio C Hamano posted `[PATCH v2]` adding `display_mode_esc_sequence_len_counted(const char *s, size_t len)`, which scans a bounded buffer for SGR sequences like `\033[1;31m` without reading past its end, fixing out-of-bounds reads in non-NUL-terminated buffers; the original `display_mode_esc_sequence_len()` remains as a `strlen`-based wrapper. The three internal callers in `utf8.c` (`utf8_strnwidth`, `strbuf_add_wrapped_text`, `strbuf_utf8_replace`) now use the counted variant, touching only `utf8.c` and `utf8.h`.

The series is under review with an authorship handoff in progress: Dirk Gouders has accepted Junio's proposal to take over authorship, planning to repost the patch as `[PATCH v2 1/2]` under his name with his clar unit tests (for `t/unit-tests/u-utf8-ansi.c`) as `2/2`, but that repost has not yet appeared. Junio rejected Dirk's proposed `if (len < 3) return 0;` early exit as an unsupported micro-optimization, which Dirk conceded. No integration branch status has been mentioned.

One substantive design question remains open: Andy Koppe argued that user-supplied text reaching this code via `rewrap_message_tail()` in `pretty.c` or `git-column` stdin can contain ECMA-48 colon-separated sequences like `ESC[38:5:123m`, and proposed cheaply accepting colons in the parameter loop. Dirk Gouders has now pushed back, arguing first that colon support should not be mixed into this patch since the bounds-safety fix and any parser extension should stay separate and independently revertable, and second that properly handling sub-separators would require a finite state machine rather than a simple character-class change, so cheaply accepting colons risks accepting malformed sequences. Andy's question thus remains unresolved, with no decision recorded.

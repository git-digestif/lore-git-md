This is a substantive review reply within Harald Nordgren's v14 five-patch series introducing `remote.<name>.fetchRefmap` for matching-inspired fetch behavior. Phillip Wood responds to Junio C Hamano's objection to his proposal that command-line refspecs with explicit destinations (`src:dst`) should cause both `--refmap` and `remote.<name>.fetchRefmap` to be ignored entirely. Phillip maintains that users are accustomed to command-line `src:dst` overriding `remote.<name>.fetch` configuration rather than adding to it, and argues that most users are unfamiliar with `--refmap` semantics, making it confusing if a command-line destination does not also override `fetchRefmap`. He further questions whether the current interaction between `--refmap` and command-line `src:dst` is consistent with the existing documentation in `git-fetch.adoc`, which describes `--refmap` as overriding `remote.<repository>.fetch` when used as a mapping, suggesting ambiguity when explicit destinations are present.

Phillip concedes that `--refmap=""` on the command line could serve as an explicit opt-out mechanism to ignore `fetchRefmap` configuration, acknowledging Junio's alternative proposal that users should pass `--no-refmap` or `--refmap=""` when they want to bypass the new config rather than overloading refspec semantics. The email thus narrows the disagreement to whether command-line `src:dst` should implicitly override `fetchRefmap` (Phillip's original position) or whether a dedicated flag is required (Junio's preference), with both now appearing open to the `--refmap=""` approach as a compromise. This discussion touches the precedence logic in `remote.c` and `builtin/fetch.c` involving `remote->fetchRefmap`, command-line refspecs, `remote->fetch` entries, and the `--refmap` option, representing an unresolved design decision point in Patch 1/5 of the series.

This is a bugfix patch for the `pretty` subsystem, specifically addressing ANSI color handling in `git log --format=...` output. The patch (v2) is a follow-up to Junio C Hamano's review of the initial version, and it resolves two related issues: colors being lost across line breaks (e.g., bold text only applying to the first line of a wrapped subject) and colors leaking into subsequent content (e.g., graph markers or unrelated lines).

The core problem stems from the lack of per-line color control in Git's formatting API, particularly with `%w` (line-wrapping) and `%b` (message body), which introduce artificial line boundaries without hooks for managing colors. The patch takes a runtime approach, tracking active ANSI escape sequences and replaying them after line breaks to ensure each line is self-contained. This mimics how default formats already handle colors and avoids requiring custom format authors to manually manage resets.

Changes in v2 include a clearer commit message rationale, removal of a minor grepping-related point, rebase onto `maint`, addition of a NUL-handling test, and optimizations to the line-break logic. The implementation modifies `repo_format_commit_message()` in `pretty.c` and adds tests to `t/t4205-log-pretty-formats.sh`, covering edge cases like empty lines, manual escape sequences, and `--graph` integration. Performance is preserved by avoiding unnecessary buffer copies and using efficient string scanning.

Junio's review of v1 endorsed the runtime approach after acknowledging the API gap, and the discussion did not raise technical objections or edge cases. The patch appears well-motivated, thoroughly tested, and ready for further review. If no new concerns emerge, it seems likely to proceed toward merging.

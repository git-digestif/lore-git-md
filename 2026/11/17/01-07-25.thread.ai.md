Thread identity: Bug report about runaway recursion in `git push` when a remote group contains a remote with the same name as the group. Originating author: wheakerd.

Core problem or goal: A cyclic definition in Git's remote group configuration (e.g., `remotes.origin = "origin member"`) causes `git push` to spawn unbounded child processes due to recursive group expansion. The bug is present in Git 2.56.0 and exists in `master`, `next`, and `seen` branches as of 2026-11-15. The issue stems from `push_multiple()` in `builtin/push.c` spawning child processes for each group member without cycle detection, while `add_remote_or_group()` in `remote.c` resolves a name as a group if `remotes.<name>` exists.

Current status: Under review. The bug is confirmed and reproducible, with a clear minimal reproduction case. No prior fix exists despite a similar known issue on the fetch side (`git remote update`). Jeff King previously identified the cycle and suggested a fix (expand groups in one process, pass an option to children to prevent re-expansion, and detect cycles), but no patch has been submitted.

Key technical details:
- Files/subsystems touched: `builtin/push.c` (`push_multiple()`), `remote.c` (`add_remote_or_group()`).
- Behavior: Recursive group expansion leads to unbounded process spawning (reporter observed >5,000 processes in 12 seconds).
- Expected behavior: Either a single push to each unique remote or an explicit error about cyclic definitions.
- Test coverage: The test suite lacks coverage for this edge case; the reporter provides minimal reproduction steps.

Open questions and loose ends:
- Whether to fix by detecting cycles during group expansion (Jeff King's suggestion) or by other means (e.g., erroring on cyclic definitions).
- Whether to backport the fix to stable branches given the severity of the issue.
- No patch has been proposed yet, so the exact implementation approach is unresolved.

This is a bugfix patch (v2 of a single-patch series) targeting incorrect reflog entries for symbolic references when both a symref and its target are updated in the same transaction. The patch addresses a correctness regression affecting both the reftable and files backends, though the files backend previously masked the bug due to its non-atomic commit ordering.

The core change introduces `ref_transaction_resolve_new_oid()` in `refs.c`, a helper that resolves what a ref's OID will be after the transaction commits by first scanning the transaction's pending updates (following symref chains via `new_target`) before falling back to reading the current ref store. Both `refs/files-backend.c` and `refs/reftable-backend.c` now call this helper instead of `refs_resolve_ref_unsafe()` when writing reflog entries for symrefs, ensuring HEAD records the correct new OID regardless of whether the target branch is updated or created in the same transaction and regardless of update ordering.

Version 2 incorporates review feedback from Karthik Nayak: tests now run in subshells within the test repository to avoid repetitive `-C repo` invocations, a new test covers the case where the symref target is updated through HEAD itself (which appends to `transaction->updates` after the initial sort, necessitating a linear scan in `find_ref_update()` rather than a lookup on the sorted `refnames` list), and a `--batch-updates` test verifies that rejected target updates do not pollute the reflog. The new test coverage lives in `t/t1400-update-ref.sh` and exercises update/create scenarios with both branch-first and head-first orderings.

The patch touches `refs.c`, `refs/refs-internal.h`, `refs/files-backend.c`, `refs/reftable-backend.c`, and `t/t1400-update-ref.sh`. It is well-motivated with a clear reproduction in the commit message and aligns with the broader architectural goal of centralizing reflog logic in the generic refs layer, though deeper refactoring is explicitly deferred. No merge to `master` has occurred; the topic remains under review and is expected to land in `next`.

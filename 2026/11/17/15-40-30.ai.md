This is a substantive review reply within Harald Nordgren's v14 patch series (5 patches) introducing the `remote.<name>.fetchRefmap` configuration for matching-inspired fetch behavior. The email addresses the override semantics between command-line refspecs and the new `fetchRefmap` config.

Junio C Hamano responds to Phillip Wood's proposal that a command-line refspec with an explicit destination (`src:dst`) should cause both `--refmap` and `remote.<name>.fetchRefmap` to be ignored entirely, preventing dual storage of fetched refs. Junio disagrees with this approach, arguing that command-line `src:dst` already overrides `remote.<name>.fetch` (which provides the default refspecs), whereas `remote.<name>.fetchRefmap` provides defaults for `--refmap`, not for the refspec itself. He contends it would be confusingly asymmetric for a command-line refspec to also override `fetchRefmap` -- comparable to `--refmap` suddenly overriding `.fetch` configuration. Instead, he suggests allowing an explicit opt-out via `--no-refmap` or possibly `--refmap=""` on the command line when a user wants to ignore the `fetchRefmap` configuration.

The discussion touches the precedence logic in `remote.c` and `builtin/fetch.c` concerning `remote->fetchRefmap`, command-line refspecs, `remote->fetch` entries, and the `--refmap` option. This represents an active design decision point on how explicit command-line destinations interact with the new `fetchRefmap` config, with Junio advocating for preserving the current separation (refspecs override `.fetch`, `--refmap` overrides `fetchRefmap`) and providing a dedicated command-line flag for opting out of `fetchRefmap` rather than overloading refspec semantics.

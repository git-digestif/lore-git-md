This is a review reply in the ongoing discussion of Justin Tobler's four-patch series that makes ODB transaction temporary-directory creation eager rather than lazy. Specifically, it answers Karthik Nayak's question challenging the series' performance claim that large numbers of loose objects are not expected inside transactions.

Justin explains that loose objects only enter a transaction in two cases: when an incoming packfile falls below the unpack limit (default 100 objects), or when objects are added directly via commands like `git add`. He acknowledges the edge case where a user adds a large new tree for the first time, but argues that the per-object overhead of eager directory creation is small relative to the cost of writing the object itself, so the slowdown is unlikely to be noticed in practice. He commits to clarifying this reasoning in the commit message for the next version.

With this reply, the specific performance question Karthik raised on patch 4/4 is addressed, though neither reviewer has yet offered a Reviewed-by or Acked-by. The broader design debate about whether eager creation is the right architectural choice remains open, as Karthik has previously expressed skepticism about moving away from the lazy approach.

The series itself continues to shift tmp-objdir creation to transaction start in the ODB abstraction layer, touching `tmp-objdir.c`, `object-file.c`, and related test files. Justin has already agreed to several other changes for v2, including restructuring `tmp_objdir_create()` to use a single cleanup path and rewording a test message to avoid "ODB" jargon.

This is a substantive review reply within Harald Nordgren's v14 five-patch series for `remote.<name>.fetchRefmap`, specifically resolving the override-semantics disagreement on Patch 1/5. Junio C Hamano reverses his earlier opposition to Phillip Wood's proposal and now endorses the approach where any refspec carrying an explicit destination (`src:dst`) -- whether passed on the command line or found in configuration -- ignores the refmap entirely. Under this model, the refmap (and by extension `remote.<name>.fetchRefmap`) applies only to refspec entries that lack their own destination, leaving explicitly targeted entries untouched. Junio notes this keeps a clean one-to-one relationship between configuration and command-line options (config sets the default, the command line overrides it) and avoids needing to define special semantics for `--refmap=""`. He first corrects a slip where Phillip referred to ignoring ".fetch" instead of ".fetchRefmap". This effectively closes the gap between the two positions that had narrowed to a choice between implicit override via `src:dst` versus an explicit `--refmap=""` opt-out, with Junio now accepting the implicit override as the simpler, more flexible design. The decision affects the precedence logic in `remote.c` and `builtin/fetch.c` involving `remote->fetchRefmap` and command-line refspecs, and removes the dual-storage concern that Phillip had raised about command-line destinations interacting with `fetchRefmap`.

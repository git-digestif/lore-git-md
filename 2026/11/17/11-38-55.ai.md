This is a bugfix patch (2/5 in Elia Pinto's v2 series on loose object size handling) that widens loose-object size variables from `unsigned long` to `size_t` throughout the loose object reading path to prevent truncation on LLP64 platforms such as 64-bit Windows.

The patch changes the signature of `map_fd()`, `unpack_loose_header()`, `unpack_loose_rest()`, and `check_stream_oid()` in `object-file.c`/`object-file.h`, plus `odb_source_loose_map_object()` and related locals in `odb/source-loose.c`, so that the entire path from file mapping through header parsing and inflation uses `size_t` consistently. The motivation is that since commit c6a4629e32, `parse_loose_header()` already reports sizes as `size_t`, but downstream functions still took `unsigned long`; on Windows where `long` is 32-bit and `size_t` is 64-bit, a header claiming 4 GiB + 5 bytes causes the buffer allocation to truncate to 6 bytes while `*oi->sizep` retains the full 64-bit value, leading callers like `read_loose_object()` to read far past the allocated buffer.

There is no automated test because reproducing the bug requires allocating a buffer near 4 GiB before the short-stream check can trigger; the commit message instead documents a manual reproduction using the `loose_obj()` test helper with a bogus header size. This patch complements patch 1/5 of the same series, which added the post-inflation size validation that becomes effective on LLP64 only once these types are widened. The series remains under review with no maintainer decision recorded.

This is a preparatory refactoring patch, specifically v8 2/4 of Harald Nordgren's series introducing `git branch --delete-integrated`. The patch modifies `delete_branches()` in `builtin/branch.c` to accept an optional `struct strmap *landed_commits` parameter mapping branch names to the upstream commit where each branch's changes landed. When a branch appears in this map, the function skips the usual tip-reachability merge check (`check_branch_commit()`) and instead reports deletion with the new output format `Deleted branch %s (was %s, landed as %s)`, showing both the branch tip and the landing commit. Both dry-run and actual deletion paths handle the new message variant. No caller currently passes a non-NULL map -- `delete_merged_branches()` and the regular `cmd_branch()` delete path both pass `NULL` -- so there is no behavior change in this patch alone.

Within the series architecture, this patch provides the reporting infrastructure that patch 4/4 will use when the squash-detection logic populates the `landed_commits` map. The earlier thread summary notes this patch is explicitly uncontroversial and behavior-neutral, confirmed by Junio and reviewers as ready for integration. It follows patch 1/4 (which extracts `branch_opted_out()`) and precedes patch 3/4 (which introduces the `DELETE_BRANCH_INTEGRATED` flag and `find_landed_commits()` helpers) and patch 4/4 (which implements `merge_keeps_upstream()` via `ll_merge()` for three-way squash detection).

Key symbols introduced or modified: the `landed_commits` parameter on `delete_branches()`, the `landed` and `landed_abbrev` locals computed via `strmap_get()` and `repo_find_unique_abbrev()`, and the conditional skip of `check_branch_commit()` when `strmap_contains(landed_commits, bname.buf)` is true. The output format change is the user-visible signature of the upcoming `--delete-integrated` behavior, though not yet triggered. Files touched: only `builtin/branch.c` (25 insertions, 5 deletions).

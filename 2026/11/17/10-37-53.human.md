This is a bugfix patch, specifically the first of four in a v2 series addressing integer truncation when Git handles files larger than 2--4 GiB. The change widens the byte-count parameter of `hashwrite()` in `csum-file.c` and `csum-file.h` from `uint32_t` to `size_t`.

The problem it fixes is concrete: when `git pack-objects` writes an entire compressed object buffer in a single call -- possible for objects over 4 GiB when `core.bigFileThreshold` is raised -- the old `uint32_t` parameter silently truncated the count to `count mod 2^32`, writing fewer bytes than requested and corrupting the resulting packfile. The author verified this using a 16-bit simulation, observing `git cat-file` and `git fsck` failures with "offset beyond end of packfile" after repacking. The internal write loop already handles block-based buffering, so the fix is a one-line type change in both the implementation and header.

No test is included because reproducing the bug requires an actual 4 GiB+ object, which is impractical for the test suite. The patch is minimal and well-motivated, though it remains under review alongside the other three patches in the series, which address similar truncation issues in diff generation and rename detection.

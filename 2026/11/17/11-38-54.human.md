This is a bugfix -- specifically the first patch in Elia Pinto's five-patch v2 series targeting loose object size handling. It fixes a cross-platform defect in the loose object reader where `unpack_loose_rest()` in `object-file.c` never verified that the inflated stream actually produced the number of bytes claimed in the object header. If a corrupt or truncated loose object declared a larger size than its contents, Git would return a buffer with uninitialized heap memory at the tail; conversely, if the stream held more data than the header claimed, the extra bytes were silently dropped. The patch adds a check comparing `stream->total_out` against the expected size -- mirroring what the packfile reader already does -- and reports the object as corrupt on mismatch.

The fix is small and targeted, touching only `unpack_loose_rest()` and its callers' expectations, plus test infrastructure. Pinto extends the `loose_obj` helper in `t/lib-loose.sh` to allow tests to write a bogus size into the object header, then adds three new tests in `t/t1060-object-corruption.sh` covering objects shorter than, longer than, and matching their headers, including a check that `git fsck` now catches the corruption. The commit message is thorough, explaining both failure modes and noting that `fsck` previously detected the short-stream case only by accident when hashing uninitialized bytes.

Within the broader series, this patch stands out as one of the two fixes that affect all platforms rather than just LLP64 systems like 64-bit Windows; the remaining four patches address `long` vs `size_t` truncation issues specific to those platforms. The series itself is a rework of an earlier v1 submission and is currently under review with no maintainer decision yet. This particular patch looks well-crafted: it includes automated regression tests, follows existing patterns from the packfile code path, and has already been vetted by the git-security list as non-security-sensitive.

Alejandro Colomar has kicked off a feature request on the Git list proposing a new `-M` flag for `git grep` that would enable multi-line pattern matching, borrowing the option from `pcre2grep(1)`. The goal is to let `git grep -P -M` search across line boundaries using PCRE2 regular expressions, which today are restricted to single-line matches even when the pattern itself uses the `(?s)` dotall modifier.

The motivation is structural code search in large codebases like the Linux kernel: matching full multi-line constructs such as `SYSCALL_DEFINE3(...)` bodies or backslash-continued `#define` macros. Colomar points to the external `grepc` tooling, which already generates the complex recursive PCRE2 patterns needed for this, but which currently only works when piped manually or for single-line `git grep -P` queries. A native multi-line mode would allow these searches directly across the working tree and, more powerfully, across history -- for example searching a pattern across all files at a given revision without knowing in advance which file contains it, something the current `git show <rev>:<path> | grepc` workaround cannot do.

No patch is included; this is an opening RFC asking whether the feature makes sense as a natural extension of the existing `-P` support. The discussion ahead will likely need to settle how multi-line matches interact with `git grep`'s line-oriented output and context options (`-A`/`-B`/`-U`), and whether the performance cost of buffering across lines is acceptable when scanning large histories.

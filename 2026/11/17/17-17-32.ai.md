This is a feature request (RFC) proposing a new `-M` flag for `git grep` to enable multi-line pattern matching. Alejandro Colomar suggests borrowing the `-M` option from `pcre2grep(1)` so that `git grep -P -M` can search across line boundaries using PCRE2 regexes, which today are limited to single-line matches even when the pattern uses the `(?s)` dotall modifier.

The motivation centers on searching for multi-line C code constructs in large codebases like the Linux kernel. Colomar illustrates this with the external `grepc`/`grepc_c` tools, which generate complex PCRE2 regexes (using recursive subpatterns, backreferences like `\k<space>`, and the `(?s)` flag) to match things like full `SYSCALL_DEFINE3(...)` function bodies or multi-line `#define` macros with backslash continuations. Currently these patterns only work with single-line tools like `grep -P` when piped manually, or with `git grep -P` only for single-line matches. Enabling multi-line matching in `git grep` would let users run these structural searches directly across the working tree and, importantly, across history (e.g. `git grep -P -M -f patterns v4.0 -- include/`).

The email notes a current workaround for historical searches -- using `git show <rev>:<path> | grepc` -- but points out this requires knowing the exact file path in advance, whereas a native multi-line `git grep` over revisions would allow searching for a code pattern across all files at a given commit without prior knowledge of where it lives. Colomar asks whether the feature makes sense to the list, framing it as a natural extension of the existing `-P` (PCRE) support in `git grep`.

No patch is included; this is an initial proposal likely to spark discussion about whether to expose PCRE2's multi-line mode directly, how it interacts with `git grep`'s line-oriented output format and `--heading`/context options, and whether the performance cost of multi-line buffering across large histories is acceptable. Future replies in this thread will likely debate the semantics of printing multi-line matches, interaction with `-U`/`-A`/`-B` context flags, and whether the feature should be gated behind `-P` or made available for the default basic/extended regex engines as well.

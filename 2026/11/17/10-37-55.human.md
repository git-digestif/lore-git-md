This is a bugfix, specifically the third patch in Elia Pinto's four-part v2 series addressing integer truncation when Git processes files larger than 2--4 GiB. The patch makes a one-line change in `diffcore-delta.c`, widening the buffer size parameter in `hash_chars()` from `unsigned int` to `size_t`.

The problem occurs when rename detection processes files of 4 GiB or more: the old 32-bit type caused only a prefix of the buffer to be hashed, while the similarity score was still calculated against the full file size. This mismatch undervalued the similarity between files, causing Git to miss true renames. The author notes this affects `git diff -M`, `git log --follow`, and merge operations, where a renamed file might incorrectly appear as a delete-plus-add instead.

Because triggering the bug requires a 4 GiB input, no automated test is included. Instead, the author verified the fix using a 16-bit truncation simulation, which reproduced the missed rename (`D a` / `A b` instead of `R099 a b`) on the old code.

Within the broader series, this patch sits alongside changes to `hashwrite()` in the packfile code (patch 1/4), the complete-rewrite diff path (patch 2/4), and diffstat accumulation (patch 4/4). Like patches 1/4 and 4/4, this one still awaits substantive technical review from other contributors.

Thread identity: standalone single-patch bugfix to `git fast-import` authored by Kaartic Sivaraam, addressing error-message information disclosure in the `export-marks` feature check.

Core problem: since commit 68061e3470 (2019-08-29) made `feature export-marks=<path>` forbidden by default unless `--allow-unsafe-features` is passed, the diagnostic emitted when the feature is rejected leaks the full feature string -- including the user-supplied filesystem path -- into stderr. The `import-marks` variants do not leak because they pass only the bare feature name to `check_unsafe_feature()`.

Current status: patch submitted upstream as a standalone fix; the author notes they spotted the issue while backporting security fixes and deliberately held the cleanup until after the security release shipped. Under review; no integration status reported. The discussion has expanded from the original one-line fix to a proposed structural refactoring suggested by the maintainer.

Key technical details: original one-line change in `builtin/fast-import.c` in `parse_one_feature()` at the `skip_prefix(feature, "export-marks=", &arg)` branch, passing the literal string `"export-marks"` instead of the full `feature` argument to `check_unsafe_feature()`. Test update in `t/t9300-fast-import.sh` strengthens the existing test `R: export-marks feature forbidden by default` to grep stderr for `feature .export-marks. forbidden` rather than only asserting command failure. Old behavior: stream with `feature export-marks=git.marks` and no `--allow-unsafe-features` dies with `feature 'export-marks=git.marks' forbidden in input without --allow-unsafe-features`. New behavior: same condition dies with `feature 'export-marks' forbidden in input without --allow-unsafe-features`, matching `import-marks` style. Enforcement logic unchanged; the feature remains forbidden under identical conditions. Junio C Hamano has proposed an alternative structural fix: a new helper `check_unsafe()` that combines `skip_prefix()` and the safety check, taking the full `feature` string, a `prefix` to match, and an output `arg` pointer; it requires an `=` immediately after the prefix, dies with only the bare feature name when unsafe and `--allow-unsafe-features` is absent, and otherwise sets `*arg` past the `=` and returns success. This eliminates the forced repetition of the feature name in both the prefix string and the safety-check argument. The proposed diff touches only `builtin/fast-import.c`, replacing `check_unsafe_feature()` and updating both `export-marks` and `import-marks` branches, with a net reduction of three lines. Junio notes an edge case: if an argument-less unsafe feature is ever added, the `*arg_ == '='` check would need relaxing to accept NUL or use a separate signal like `arg == NULL`.

Open questions and loose ends: Junio endorses the original fix as "obviously correct" but offers the `check_unsafe()` refactoring as a way to prevent similar bugs from recurring; the author may adopt either approach. Karthik Nayak notes this patch will likely conflict with his in-flight series `20261112-kn-fast-import-tests-1-v2` refactoring `fast-import` tests, so one author will need to rebase onto the other's topic before either can advance.

Participant positions: Kaartic Sivaraam submitted the fix with a commit message explaining the disclosure issue and the deliberate timing relative to the security release. Karthik Nayak provided a substantive review confirming the technical reasoning -- noting that all other features pass a static string to `check_unsafe_feature()`, so the change is consistent with the existing pattern -- and endorsed it with "Change looks sensible!" Junio C Hamano reviewed and called the original fix "obviously correct" while proposing the `check_unsafe()` helper as a structural improvement to eliminate the duplication trap; he explicitly flagged the edge case for future argument-less unsafe features. No objections raised to either approach.

Related work: references commit 68061e3470 (2019-08-29) which introduced the `--allow-unsafe-features` gating for `export-marks`; part of the broader `fast-import` unsafe-feature hardening effort. Potential future interaction with Karthik Nayak's in-flight `fast-import` test refactoring series.

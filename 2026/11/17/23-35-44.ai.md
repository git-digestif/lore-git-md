This is a **review reply** continuing the substantive discussion of patch 2/4 (`object-file: only flush batched fsync writes when enabled`) in Justin Tobler's four-patch ODB transaction series. It sits within the ongoing ODB abstraction effort and responds to Patrick Steinhardt's earlier questions about the patch's rationale.

Justin confirms the technical premise Patrick raised: the single hardware flush at transaction commit time acts as a durability barrier only when batched fsync is active (writeout-only per object), and is redundant when objects are either individually synced or not synced at all. He characterizes the change as both a performance optimization (avoiding unnecessary flushes for `git-receive-pack` transactions where batched fsync is disabled) and a correctness cleanup (the flush currently happens regardless of fsync mode, which is not ideal as transactions roll out more widely).

On Patrick's question about scope, Justin confirms that batched fsync currently applies **only to loose objects**, not packfiles -- an implicit assumption Patrick asked to have documented explicitly in the commit message. Justin agrees to update the commit message in the next version of the series.

No new technical objections are raised in this email; the exchange closes Patrick's open questions on patch 2/4 with mutual agreement, pending the commit-message tweak. Karthik Nayak's separate correctness concern about whether `fsync(fd)` guarantees durability of previous writes to the same fd (raised elsewhere in the thread) remains unresolved and is not addressed here.

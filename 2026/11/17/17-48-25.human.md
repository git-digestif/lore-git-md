This is a feature request (RFC-style proposal) for a user-invoked recovery mechanism for stale `index.lock` files.

Steve asks whether Git could add a command that, when a user finds themselves blocked by a leftover lock file from a crashed or killed process, would wait briefly and then remove the lock -- but only if no other Git operation is actively contesting it. The core idea is to give users a safe, explicit way to recover from the common situation where `index.lock` remains after an interrupted operation, without forcing them to manually delete the file and risk clobbering a concurrent process.

The email does not propose a specific command name or implementation; it is an opening question to gauge whether the project sees value in such a facility. The `index.lock` file is a well-known source of friction when Git processes are interrupted, and currently the only remedy is manual removal, which carries a risk if another Git process is actually running.

As a contribution, this is an early-stage discussion starter rather than a patch. It lacks code, tests, or a detailed design, but it identifies a real user-facing pain point and invites discussion on how Git might safely automate recovery. Whether the list engages with it will depend on whether maintainers see this as a worthwhile addition to the command set or prefer to keep lock handling as an advanced, manual operation.

This is a follow-up review request (a "gentle ping") on a two-patch bugfix series, not a new patch. Elia Pinto is soliciting feedback on the series that converts tree buffer size fields from 32-bit types to `size_t` to prevent silent truncation of trees larger than 4 GiB.

The email reiterates the core technical problem: `struct tree_desc` stores the buffer size in an `unsigned int` and `struct tree` in a `long`, both 32-bit on common platforms, so a tree of 4 GiB or more is processed only up to "size mod 2^32", causing entries beyond that boundary to silently disappear from `git ls-tree` output and from `fsck_tree()` validation. The proposed fix touches `tree-walk.c`, `tree-walk.h`, `tree.c`, and `tree.h`, changing the relevant size fields and functions (`init_tree_desc()`, `init_tree_desc_gently()`, `decode_tree_entry()`, `parse_tree_buffer()`) to use `size_t`. The on-disk format is unchanged.

Pinto poses two specific questions for reviewers: first, whether this is worth fixing at all given that such large trees can only be crafted intentionally; second, if it is worth fixing, whether widening the types is the correct approach or whether an oversized tree should instead be rejected outright (for example in `init_tree_desc_gently()`). He notes the series still applies cleanly to current `master` (e1ec09b23c), that no review comments have arrived yet, and that he is willing to drop the series if there is no interest.

This is a bug report about a runaway recursion in `git push` when a remote group contains a remote with the same name as the group itself.

The reporter demonstrates a simple reproduction: create two bare repos, add them as remotes named `origin` and `member`, then configure `remotes.origin` to include both. When running `git push origin`, Git enters an infinite loop, spawning thousands of nested `git push` processes until killed. The expected behavior would be either a clean push to both remotes or an error about the circular reference.

The root cause is in `push_multiple()` in `builtin/push.c`, which spawns a child process for each member of a remote group without checking for cycles. The same issue exists on the fetch side, as noted in a 2010/2013 thread where Jeff King sketched a fix but no patch was ever merged. The reporter confirms the bug exists in Git 2.56.0 and that the problematic code is unchanged on `master`, `next`, and `seen`.

This is a clear, well-documented bug with a minimal reproduction case. The recursion is severe enough to make the system unresponsive, and the issue affects a feature (`git push <group>`) introduced in Git 2.55.0. The report is thorough, including system info, expected vs. actual behavior, and historical context. It looks like a real problem that deserves attention.

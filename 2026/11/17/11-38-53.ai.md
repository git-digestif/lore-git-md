This is a cover letter for a five-patch bugfix series (v2) targeting loose object size handling and `long`-vs-`size_t` truncation bugs on LLP64 platforms such as 64-bit Windows. The series is a rework of a previous six-patch submission: the `diff.c` fix from v1 has been dropped because it is now handled by a separate series, the patches have been rebased onto master at e1ec09b23c, and the commit messages for patches 2/5 and 5/5 now explicitly clarify that on 64-bit Windows `long` is 32 bits while `size_t` is 64 bits.

The five patches address distinct size-related defects. Patches 1/5 and 3/5 add missing bounds checks to the loose object reader and streaming reader respectively, fixing cross-platform bugs where a zlib stream shorter than the header size exposes uninitialized heap memory or a longer stream is silently truncated; both include automated tests in `t/t1006-cat-file.sh` and `t/t1060-object-corruption.sh`. Patch 2/5 converts loose object size variables from `unsigned long` to `size_t` throughout `object-file.c`, `object-file.h`, and `odb/source-loose.c` to prevent truncation on Windows. Patch 4/5 fixes a buffer overrun in `git cat-file --batch` when writing non-blob objects or filtered blobs between 2 GiB and 4 GiB. Patch 5/5 fixes a heap overflow in `notes.c` when concatenating notes totaling 4 GiB or more on Windows, using `size_t` arithmetic and `cast_size_t_to_ulong()` only where the legacy `odb_write_object()` API still requires it.

The patches touch `builtin/cat-file.c`, `notes.c`, `object-file.c`, `object-file.h`, `odb/source-loose.c`, and the test suite. Only the cross-platform fixes (1/5 and 3/5) have automated tests; the LLP64-specific and multi-gigabyte scenarios (2/5, 4/5, 5/5) are documented with manual reproduction steps in the commit messages because they require impractical test environments. The series complements two other efforts by the same author: "widen a few sizes and counts that are 32 bits everywhere" and "use size_t for a few more object and buffer sizes", without conflicting with them. The issues were reviewed on the git-security list and deemed non-security-sensitive. The series is currently under review with no maintainer decision recorded.

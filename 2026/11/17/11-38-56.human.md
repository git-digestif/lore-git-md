This is a bugfix -- specifically the third patch in Elia Pinto's five-patch v2 series on loose object handling and LLP64 size truncation. This patch targets the streaming reader for loose objects in `odb/source-loose.c`.

The problem is that `read_istream_loose()` inflates a loose object until zlib signals the end of the stream, but never verifies that the number of bytes actually produced matches the size recorded in the object's header. As a result, a corrupt object whose compressed stream is shorter than its header claims gets streamed out silently -- `git cat-file blob` exits successfully while writing fewer bytes than `git cat-file -s` reports, and a stream that is longer than claimed also goes undetected.

The fix adds a `total_read` counter to the stream state and, upon reaching `Z_STREAM_END`, compares the total bytes handed out against `st->base.size` from the header. If they differ, it reports the object as corrupt and returns an error, mirroring the validation logic already present in the non-streaming loose object path. The patch also stores the object ID in the stream struct so the error message can name the offending object.

Test coverage lives in `t/t1006-cat-file.sh`, which uses the existing `loose_obj()` helper to craft objects with deliberately bogus header sizes -- one claiming 100 bytes for a 5-byte payload, another claiming 3 bytes for a 13-byte payload -- and verifies that `git cat-file blob` fails with a "corrupt loose object" error in both directions.

Within the broader series, this patch is the streaming counterpart to patch 1/5, which added the same post-inflation size check to `unpack_loose_rest()` for the non-streaming read path. Together they close the gap where corrupt loose objects could expose uninitialized memory or silently truncate data, complementing the LLP64-specific type-widening work in patches 2/5, 4/5, and 5/5.

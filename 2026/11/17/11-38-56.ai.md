This is a bugfix, specifically the third patch in a five-patch v2 series addressing loose object size handling and LLP64 truncation issues. Patch 3/5 targets the streaming loose object reader in `odb/source-loose.c`, closing a gap where `read_istream_loose()` inflated data until zlib signaled end-of-stream but never verified that the byte count matched the size declared in the object header. A corrupt loose object whose compressed stream was shorter or longer than its header claimed would previously stream out silently with a successful exit status, producing output inconsistent with what `git cat-file -s` reported.

The fix adds a `total_read` counter and an `oid` field to `struct odb_loose_read_stream`, accumulates bytes handed to the caller, and at `Z_STREAM_END` compares `st->total_read + total_read` against `st->base.size`. On mismatch it emits a "corrupt loose object" error, transitions the stream state to `ODB_LOOSE_READ_STREAM_ERROR`, and returns -1. This mirrors the post-inflation validation that patch 1/5 adds to the non-streaming path in `unpack_loose_rest()`, so the two patches together ensure both `git cat-file blob` (streaming) and other read paths reject objects whose inflated size disagrees with the header.

The patch includes automated test coverage in `t/t1006-cat-file.sh`, using the existing `loose_obj()` test helper to create blobs with deliberately bogus header sizes and verifying that `git cat-file blob` fails with the expected error for both too-large and too-small header claims. Unlike the LLP64-specific patches in this series (2/5, 4/5, 5/5), this fix is cross-platform and testable in normal CI environments because it does not require multi-gigabyte allocations. The series itself is under review with no maintainer decision recorded; this patch complements related size-widening work by the same author but does not overlap with it.

Thread identity: bug report on the combine-diff machinery, filed by Sami Jawhar <sami@theorem.dev>, concerning `git diff-tree --cc` output for octopus merges with many parents. Thread type: single bug report, no patch series or version yet.

Core problem: for octopus merges, the combined diff (`git diff-tree --cc`) misbehaves as the parent count grows. At 33 and 63 parents the hunk headers disagree with the hunk bodies (deletion columns marked incorrectly); at 64 parents the diff produces no hunks at all. Root cause identified in `coalesce_lines()` at `combine-diff.c:249`, where `baseend->parent_map |= 1<<parent` shifts a plain `int` instead of an `unsigned long`: on 64-bit systems the shift overflows once `parent` reaches 32, and shifting by 64 at the 64-parent boundary is undefined behavior.

Current status: bug confirmed present in both Git 2.43.0 and current master at commit e1ec09b23c8e. No fix has been proposed or applied yet; no maintainer response recorded.

Key technical details: subsystem is `combine-diff.c`; the faulty line is `coalesce_lines()` around line 249 using `1<<parent`. Neighboring functions already use the correct form `1UL<<num_parent`: `give_context()` (~lines 544-545), `make_hunks()` (~lines 610-611), and `dump_sline()` (~line 756), so the suggested fix is to make `coalesce_lines()` consistent. A self-contained reproduction script accompanies the report, building octopus merges with 32, 33, 63, and 64 parents and checking header/body agreement.

Open questions and loose ends: whether a maintainer will pick this up and send a fix patch; whether the same `int`-shift pattern exists anywhere else in the file beyond the four cited sites; no test has been added yet.

Participant positions: only the reporter so far; no reviews, acks, or objections on record.

Related work: none mentioned; this is an isolated correctness bug in the octopus-merge combined-diff path rather than part of a larger in-flight effort.

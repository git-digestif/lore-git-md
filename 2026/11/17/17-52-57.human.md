This is a substantive review from Junio C Hamano on patch 1/4 of Elia Pinto's v2 series fixing integer truncation in large-file handling. Junio raises two concerns about widening `hashwrite()`'s count parameter from `uint32_t` to `size_t`. First, he notes that the Rust FFI bindings in `src/csum_file.rs` still declare the function with a `u32` length, so that file needs updating to match the new C signature. Second, and more fundamentally, he questions the API change itself: he suggests that callers holding contiguous memory regions larger than 4 GiB should instead loop and call `hashwrite()` in chunks of 4 GiB or less, preserving the existing API contract rather than widening it. This is the maintainer's first technical feedback on this specific patch; while Phillip Wood reviewed the earlier v1 and prompted changes to patch 2/4, patches 1/4, 3/4, and 4/4 had not yet received substantive review until now. The chunking question may spark discussion about whether the convenience of a wider type justifies the API change, or whether the safer approach is to keep `uint32_t` and require callers to handle large buffers incrementally.

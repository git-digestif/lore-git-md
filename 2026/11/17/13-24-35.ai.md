This is a **feature patch** -- the third of four in Harald Nordgren's v8 series adding `--delete-integrated` to `git branch`. It introduces the core machinery for detecting branches whose changes landed upstream via rebase or squash merges without their tips being reachable, while keeping `--delete-merged` strictly tip-based to avoid false positives. This patch specifically implements the tree-based detection for rebase-merged branches and the reporting infrastructure; the squash-merge handling with `ll_merge()` arrives in patch 4/4.

The patch adds the `DELETE_BRANCH_INTEGRATED` flag and a new `delete_integrated` strvec parsed from the `--delete-integrated <pattern>` option, which cannot be combined with `--delete-merged`. Internally it introduces the `landing_search` struct and `branch_change` array to record each branch's modified paths and blob OIDs relative to the merge base, plus a `changed_paths` commit slab that caches which paths each upstream commit touches to speed up the walk. `find_landed_commits()` computes merge bases, collects changed paths, then walks upstream commits in reverse via `find_landed_commit()`, checking whether any single upstream commit contains the branch's exact version of every changed file using `changes_landed()` and `change_landed()` tree-entry comparisons. When found, the branch name is mapped to that landing commit in a `strmap`, and deletion reports `Deleted branch %s (was %s, landed as %s)`. The `branch.<name>.deleteMerged` config key now applies to both flags, and `--dry-run` works with either.

Files touched are `builtin/branch.c` (253 lines added), `Documentation/git-branch.adoc`, `Documentation/config/branch.adoc`, and `t/t3200-branch.sh` (176 lines of new tests covering rebase-merged, squash-merged, reverted, partial-landing, and unmerged scenarios). This patch depends on the behavior-neutral refactoring in 1/4 (`branch_opted_out()` helper) and the landing-message reporting added in 2/4, and it provides the `landed_commits` map consumed by patch 4/4 for squash detection.

Per the thread summary, this patch is considered explicitly uncontroversial and ready for integration; Junio previously suggested only a variable rename (`opt` to `diffopt`) which was addressed in v6. The sole remaining technical gap for the overall series is the author-check mitigation to prevent the "npm update" false-positive scenario where an unrelated upstream commit coincidentally matches a branch's diff, but this does not block this particular patch.

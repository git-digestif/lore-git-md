This is a **bugfix** for the `pretty` subsystem, addressing ANSI color handling in custom `git log --format=...` output. It’s the second iteration (`v2`) of a single-patch series that fixes two related issues: colors that span line breaks are lost when tools like `--graph` or color-aware pagers reset at line boundaries, and active colors at the end of a line can leak into subsequent content (e.g., graph markers or unrelated lines).

The patch modifies `repo_format_commit_message()` to post-process formatted output when colors are enabled. It scans for ANSI escape sequences, tracks active colors since the last reset, and ensures each line is self-contained by inserting a reset before line breaks and replaying the active colors at the start of the next non-empty line (unless it begins with a reset). A final reset is appended if colors remain active at the end. The implementation avoids buffer copies unless necessary and uses efficient string scanning (`memchr`, `strcspn`).

Key improvements in `v2` include clarifying the commit message to explain why custom formats cannot handle multi-line placeholders (justifying the runtime approach), dropping redundant mentions of grepping colored output, and rebasing onto `maint`. The code also handles edge cases like embedded NULs and resets followed by colors, and the test suite now includes a case for NULs. Junio’s review of `v1` endorsed the runtime approach, and this version addresses his feedback without introducing new objections.

The patch is well-scoped, thoroughly tested, and aligns with how default formats already handle colors. It’s a clean, low-risk fix for a real usability issue, and the changes since `v1` are minor and clarifying. No controversy is evident, and the patch looks ready for `next`.

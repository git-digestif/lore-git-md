This is a feature request (RFC) proposing a new user-invoked mechanism for recovering from stale `index.lock` files. Steve asks whether Git could provide a command that, when a user suspects the lock file is stale because no Git process is running, waits briefly and then removes the lock -- but only if no other Git operation actively contests it.

The motivation addresses a well-known pain point: when a Git process crashes or is killed while holding `index.lock`, the lock file remains on disk and subsequent Git commands refuse to proceed until the user manually deletes it. Currently there is no built-in safe way to distinguish a genuinely stale lock from one held by an active process, so users must resort to manual `rm .git/index.lock`, which risks corrupting the index if another operation is indeed in progress.

The proposal implies introducing new user-visible functionality -- likely a new subcommand or option -- that encapsulates the wait-and-check logic. Key technical questions a future reviewer would need to engage with include how to reliably detect whether another Git process holds or is waiting on the lock (e.g., via file locking semantics, process inspection, or lock file metadata), what duration constitutes a "brief" wait, and how to make the recovery atomic enough to avoid racing with a newly starting Git operation.

Likely points of contention in follow-up discussion will center on safety guarantees: whether the proposed check can truly prevent removal of a lock held by a live process, and whether the feature might encourage unsafe behavior compared to the current manual approach.

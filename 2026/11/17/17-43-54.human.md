This is a cover letter for a three-patch bugfix series targeting 64-bit Windows (LLP64 platforms), aimed at removing artificial size limits on merge results and object writes that are over 2 GiB.

Christian Couder explains that the series builds on two recently merged efforts: one that switched xdiff to use `size_t` for file sizes instead of `long`, and another that added overflow-safe arithmetic and a `LONG_MAX` guard in `xdl_do_merge()` for the `maint` branches. On `master` the guard is no longer needed for the merge buffer itself, but merge results still flow into a few functions that take `unsigned long`, which truncates on Windows where `long` is 32 bits. The series converts those call sites to `size_t` and then removes the now-redundant check.

The first patch fixes a concrete bug: since mid-2026, a delete/modify conflict in `git notes merge` involving a note of 4 GiB or more silently writes a truncated note on LLP64 systems. Patches two and three widen the object-writing APIs (`odb_write_object()` and friends) to `size_t` and drop the `LONG_MAX` check in `xdl_do_merge()`, respectively, with corresponding test updates in `t4300`.

The cover letter notes that the changed code paths only behave differently where `long` is 32 bits and `size_t` is 64 bits, so Linux and macOS CI cannot exercise them; Couder explicitly asks for someone with a 64-bit Windows setup to run `t4300` with `GIT_TEST_LONG=1`, warning that it needs over 4 GiB of memory and disk. CI on the author's branch passed aside from some MacOS test-startup quirks.

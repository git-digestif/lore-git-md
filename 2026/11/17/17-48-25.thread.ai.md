Thread identity: RFC/feature request from Steve (steves.sk@gmail.com) proposing a new user-invoked mechanism for recovering from stale `index.lock` files; thread root with no accompanying patch, now with substantive replies from Tanga Joris (tangajoris@gmail.com) and a follow-up from Steve refining the proposal.

Core problem or goal: when a Git process crashes or is killed while holding `.git/index.lock`, the lock remains and blocks subsequent commands until manually deleted. Steve proposes a built-in, explicitly user-invoked recovery command that, when the user suspects the lock is stale, waits briefly and then removes the lock only if the recorded PID (via the `core.lockfilePid` sidecar file such as `index~pid.lock`) is no longer alive, combining the liveness check with the wait in a way that manual `rm .git/index.lock` cannot.

Current status: discussion only; no patch, no version, no maintainer response. Tanga Joris notes that two partial mechanisms already exist but neither removes the lock automatically: since Git 2.54, `core.lockfilePid` writes the lock holder's PID into a sidecar file (`index~pid.lock`), and when lock acquisition fails Git reports whether that PID is still alive with a message like "Lock was held by process 99999, which is no longer running; the lock file appears to be stale". Separately, Jun Wu has a series currently in `seen` (not merged) introducing `core.indexLockTimeout` to let commands wait briefly for the index lock before failing, covering only the wait portion of Steve's request. Steve's refined proposal would consolidate these behaviors into a single recovery command that waits, checks whether the recorded PID is still running, and removes the lock only when the liveness check passes.

Key technical details: touches `.git/index.lock` handling, lock-contention detection, and the `core.lockfilePid` sidecar mechanism. Tanga argues against automatic removal on safety grounds: a recorded PID can be reused by an unrelated process, making liveness checks unreliable, and the PID file carries no information when the repository is shared across machines (e.g. over NFS), where another host may legitimately hold the lock. When the PID-file feature was originally discussed, Junio expressed wariness even about merely advising users to remove a stale lock manually, underscoring project caution about encouraging lock deletion.

Open questions and loose ends: whether any safe removal mechanism is possible given PID-reuse and network-filesystem hazards; how to reliably determine whether another process holds or is waiting on the lock across hosts; what duration constitutes a "brief" wait; how to make removal atomic enough to avoid racing with a newly starting Git operation; whether a user-invoked command with built-in liveness checks offers sufficient safety over the current manual workflow, or whether the NFS and PID-reuse edge cases make any form of lock removal too risky to automate.

Participant positions: Steve proposes the feature and now argues that a dedicated user-invoked command can safely perform the PID liveness check itself using the `core.lockfilePid` sidecar combined with a brief wait, something manual removal cannot do; he frames this as consolidating existing mechanisms into a single recovery command. Tanga Joris objects to lock removal citing PID-reuse and NFS hazards, notes existing partial solutions (`core.lockfilePid` liveness reporting, Jun Wu's `core.indexLockTimeout` in `seen`), and references Junio's earlier cautionary stance against advising stale-lock removal; his objections remain applicable to Steve's refinement. No reviews or maintainer decisions recorded.

Related work: Jun Wu's `core.indexLockTimeout` series in `seen` (message-id `20261017073231.3357477-1-quark.zju@gmail.com`); Junio's earlier message expressing caution about stale-lock removal (message-id `xmqqbjj4hnkr.fsf@gitster.g`); the `core.lockfilePid` feature landed in Git 2.54.

Steve has opened a discussion on the Git mailing list proposing a new built-in mechanism for recovering from stale `index.lock` files. The motivation is a familiar operational pain point: when a Git process crashes or is killed while holding the index lock, the leftover lock file blocks all subsequent commands until someone manually deletes it, and that manual removal risks corrupting the index if another operation happens to be in progress. Steve asks whether Git could offer a command that waits briefly and then removes the lock, but only if no other Git process is actively contesting it.

No patch accompanies the message; this is a request for comments intended to gauge interest and surface design concerns before any implementation. The open questions Steve leaves for the community center on safety and reliability: how Git could distinguish a genuinely stale lock from one held by a live process, what wait duration would be appropriate, and how to make the removal atomic enough to avoid racing with a newly starting operation. Whether such a feature is desirable -- or whether it might encourage unsafe behavior compared to the current manual approach -- remains to be seen.

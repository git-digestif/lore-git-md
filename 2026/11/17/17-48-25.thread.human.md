Steve has opened a discussion on the mailing list proposing a built-in mechanism for recovering from stale `index.lock` files, the kind that block Git commands when a process crashes while holding the lock. Rather than submitting a patch, he is floating the idea of a user-invoked recovery command that would wait briefly, check whether the process recorded in the `core.lockfilePid` sidecar file is still alive, and only then remove the lock -- arguing that this offers safety checks that the current manual `rm .git/index.lock` workflow cannot provide.

Tanga Joris has replied with substantive safety concerns, noting that two partial mechanisms already exist: since Git 2.54, `core.lockfilePid` writes the lock holder's PID to a sidecar and reports liveness when lock acquisition fails, and Jun Wu has a `core.indexLockTimeout` series currently cooking in `seen` that adds waiting behavior. Tanga argues that automatic removal remains hazardous because PID reuse can make a dead process appear alive, and on network filesystems like NFS the PID sidecar says nothing about locks legitimately held by other hosts. He also references Junio's earlier wariness about even advising users to manually remove stale locks.

In his latest reply, Steve refines the proposal to address some of these concerns by emphasizing that the removal would happen only through an explicit user command rather than automatically in the background, and that the command itself would perform the liveness check before deleting anything. However, the fundamental reliability questions persist: whether PID-based checks can ever be trustworthy across process boundaries and machines, and whether any built-in removal mechanism -- even user-initiated -- can be made safe enough to recommend over the current manual approach. The thread remains open with no patch, no version, and no maintainer decision.

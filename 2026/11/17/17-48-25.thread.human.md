This thread is an RFC from Steve proposing a built-in, user-invoked way to recover from a stale `.git/index.lock` left behind when a Git process crashes: something that would wait briefly and then remove the lock, but only if no live process is actually contesting it, since manually running `rm .git/index.lock` while another process holds the lock risks index corruption. No patch has been posted yet, so the thread is still at the discussion-opener stage.

Tanga Joris replied pointing out that Git already covers parts of the request. Since Git 2.54, the `core.lockfilePid` configuration makes Git record the lock holder's PID in a sidecar file, and lock-failure messages now report whether that PID is still alive, telling the user when a lock "appears to be stale." Separately, a series by Jun Wu currently sitting in `seen` adds `core.indexLockTimeout`, which lets commands wait briefly for the index lock before failing. Neither feature removes the lock automatically -- the user still deletes it by hand.

Tanga argues against automatic removal on safety grounds: a recorded PID can be reused by an unrelated process, making liveness checks unreliable, and on repositories shared over something like NFS the PID file says nothing about whether another host legitimately holds the lock. The reply also notes that Junio was wary even of merely advising users to delete stale locks manually when the PID feature was discussed, which underlines how cautious the project is about encouraging lock deletion. The thread remains open on whether any safe automatic-removal mechanism is possible given the PID-reuse and network-filesystem hazards, with references provided to Jun Wu's `core.indexLockTimeout` series and Junio's earlier cautionary message.

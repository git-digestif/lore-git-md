This is the fifth and final patch of a five-part bugfix series (v2) by Elia Pinto addressing size-truncation bugs on LLP64 platforms such as 64-bit Windows, where `long` is 32 bits but `size_t` is 64. The series as a whole reworks loose object handling and related size arithmetic; this last patch specifically targets the notes subsystem.

The bug lives in `combine_notes_concatenate()` in `notes.c`. When two notes are concatenated -- whether during a notes merge with the "union" strategy, with `notes.rewriteMode=concatenate` (the default), or simply when displaying a notes tree containing multiple notes for the same object at different fanout levels -- the function reads both notes via `odb_read_object()`, which returns sizes as `size_t`, but then computes the combined buffer length in an `unsigned long`. On 64-bit Windows, two notes totaling 4 GiB or more overflow that 32-bit variable, yielding a tiny allocation while `memcpy()` subsequently copies the full multi-gigabyte contents into it, corrupting the heap. The notes can originate from a fetched notes ref, so merely displaying such a tree can trigger the crash.

The fix changes `buf_len` to `size_t`, uses `st_add3()` for overflow-safe arithmetic, and introduces `cast_size_t_to_ulong()` at the single point where the legacy `odb_write_object()` API still requires an `unsigned long` length. On affected platforms this turns silent memory corruption into a clean `die()` rather than a truncated or overflowed write, until the write API itself is modernized to accept `size_t`.

There is no automated test, since reproducing the bug requires both a platform with a 32-bit `long` and notes exceeding 4 GiB -- impractical for CI. The commit message documents the scenario clearly but relies on manual verification. This mirrors the pattern across the series: patches 1/5 and 3/5 (the cross-platform loose-object validation fixes) carry automated tests, while the LLP64-specific patches 2/5, 4/5, and this one provide manual reproduction recipes instead. The series remains under review with no maintainer decision recorded yet.

This is a review comment on patch 10/12 of the now-merged `ps/rerere-subcommands` series, which refactors `git rerere` to use Git’s standard `OPT_SUBCOMMAND()` mechanism. The series is purely internal, with no behavior changes or new functionality, but it introduces two deliberate UI regressions: stricter option ordering and degraded error reporting for unknown subcommands.

Junio’s feedback here is a **substantive review** focused on the commit message’s clarity for future maintainers. He points out that while the cover letter explains the deliberate UI regression (removing support for `git rerere --skip-locked gc` in favor of `git rerere gc --skip-locked`), the commit message for this patch does not. This omission could mislead someone bisecting a bug report later, leading them to assume the regression was unintentional. Junio requests that the commit message explicitly state the regression is deliberate and briefly explain why (e.g., enforcing option ordering to align with other Git commands).

The patch itself extracts the "gc" subcommand into a dedicated function (`cmd_rerere_gc()`) and scopes the `--skip-locked` option to it, removing the global flag and a now-redundant test. The change is mechanical and low-risk, but Junio’s concern is about documentation, not code. His feedback is a reminder that even refactoring patches should justify behavioral changes—even regressions—so future readers understand the trade-offs.

No code changes are requested; this is purely about improving the commit message for posterity. The thread context confirms the series is already merged, so this is a post-hoc suggestion for future patches.

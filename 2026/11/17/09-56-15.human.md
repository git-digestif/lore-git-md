This is a **bugfix** for reflog correctness in the refs layer, submitted as v2 of a standalone patch by Tsukasa Inoue. The problem: when a single `git update-ref` transaction both updates a branch and repoints a symref (like `HEAD`) at it, the reflog entry for the symref could record the wrong OID or be omitted entirely. The reftable backend always saw the old value (or none, if the branch was being created), while the files backend only got it right if the branch update happened to come first in the queue.

The fix introduces `ref_transaction_resolve_new_oid()` in `refs.c`, a helper that resolves a ref's post-transaction value by walking the transaction's own updates -- following symref chains within the transaction -- before falling back to reading the ref store. Both the files and reftable backends now call this helper when writing reflog entries for symref updates, so `HEAD`'s reflog records the correct new OID regardless of backend or update order.

This v2 addresses review feedback from Karthik Nayak: tests now run in subshells with cleaner structure, a new test covers the case where the symref target is updated indirectly through `HEAD` (which exercises why the helper must linearly scan `transaction->updates` rather than using a sorted lookup), and a `--batch-updates` test verifies that a rejected target update does not pollute the reflog. The patch touches `refs.c`, `refs-internal.h`, both backend files, and adds five test cases to `t/t1400-update-ref.sh`.

The commit message is clear about the root cause and the scope -- it deliberately moves only the OID lookup into the generic refs layer, leaving broader reflog centralization for later. With thorough test coverage and review feedback incorporated, this looks like a solid fix that is likely cooking toward `next`; no merge to `master` has been reported.

This is a bugfix patch for LLP64 platforms, specifically the second patch in Elia Pinto's five-part v2 series on loose object size handling. On 64-bit Windows, where `long` is 32 bits but `size_t` is 64, the loose object reading path was truncating object sizes when they passed through functions still typed as `unsigned long`. A crafted loose object header claiming a size of 4 GiB plus a few bytes could therefore cause Git to allocate only a tiny buffer while reporting the full large size to the caller, leading to out-of-bounds reads when the object contents were hashed or otherwise consumed.

The patch converts the size parameters in `map_fd()`, `unpack_loose_header()`, `unpack_loose_rest()`, `check_stream_oid()`, `odb_source_loose_map_object()`, and related loose-source plumbing from `unsigned long` to `size_t`, so that the entire path from file mapping through header parsing and inflation agrees on the wider type. This builds directly on commit c6a4629e32, which had already made `parse_loose_header()` report sizes as `size_t`, but left the downstream consumers narrower. The change touches `object-file.c`, `object-file.h`, and `odb/source-loose.c`, with no change to the on-disk format.

There is no automated test for this specific fix because reproducing the truncation requires allocating a buffer based on a multi-gigabyte header before the short stream is detected, which would need several GiB of memory in the test environment. Elia Pinto documents a manual reproduction using the `loose_obj()` helper to create a malformed object and reading it with `git cat-file`. The patch is currently under review as part of the larger series, which also includes cross-platform bounds-check fixes with test coverage in other patches.

This is a bugfix, specifically the fourth patch in Elia Pinto's five-patch v2 series on loose object handling and size truncation. It targets `builtin/cat-file.c`, where the internal `batch_write()` helper accepted the data length as an `int` while its callers passed `size_t` values returned by `odb_read_object()` or `filter_object()`.

The bug triggers when `git cat-file --batch` outputs objects between 2 GiB and 4 GiB that are not streamed directly -- namely non-blob objects like commits or trees, or blobs requested with `--filters` or `--textconv`. In that range the 64-bit `size_t` wraps to a negative `int`, which `fwrite()` and `write_or_die()` then interpret as an enormous `size_t`, causing Git to write past the end of the buffer until it hits an unmapped page and crashes with "write error: Bad address". Objects of 4 GiB or larger are silently truncated instead, desynchronizing the batch output stream. The commit message notes this affects all platforms, not only LLP64 systems with a 32-bit `long`.

The fix is a one-line type change: widening the `len` parameter of `batch_write()` from `int` to `size_t`, which matches the types already expected by the underlying `fwrite()` and `write_or_die()` calls. No automated test accompanies the patch because reproducing the crash requires allocating several gigabytes of memory and disk space; the commit message instead provides a manual reproduction using `test-tool genzeros` to create a 3 GiB blob.

As part of the broader series, this patch addresses one of the size-truncation bugs mentioned in the cover letter, though unlike patches 2/5 and 5/5 it is platform-independent. The contribution is precise and well-motivated, with a clear explanation of the failure mode and a minimal diff, though the lack of test coverage means the fix relies on manual verification.

This is a cross-platform bugfix, the first patch (1/5) in Elia Pinto's v2 series on loose object size handling. The series overall targets LLP64 truncation issues, but this specific patch addresses a generic correctness bug in the loose object reader.

The patch fixes `unpack_loose_rest()` in `object-file.c`, which allocates a buffer based on the size declared in the loose object header and inflates the zlib stream into it, but never verifies that the stream actually produced that many bytes. If the compressed data ends early, the function returns success with the tail of the buffer uninitialized, and callers such as `odb_read_object()` hand out that garbage as object content -- for example, `git cat-file commit` on an object whose header claims 200 bytes but contains only 44 will print 156 bytes of uninitialized heap memory. Conversely, if the object is shorter than the header claims but the stream has ended, extra data is silently dropped. The fix adds a check after inflation: if `status != Z_STREAM_END` or `stream->total_out - hdrlen != size`, the object is reported as corrupt and the buffer is freed, mirroring the validation already present in `unpack_compressed_entry()` for packfiles.

Supporting test infrastructure changes extend `loose_obj()` in `t/lib-loose.sh` to accept an optional third argument that overrides the real content size with a bogus value in the header, and `t/t1060-object-corruption.sh` gains three tests verifying that reading objects with too-large or too-small header sizes fails with a "corrupt loose object" error, and that `git fsck` detects both cases.

The patch touches `object-file.c`, `t/lib-loose.sh`, and `t/t1060-object-corruption.sh`. Old behavior: uninitialized memory exposure or silent truncation on malformed loose objects; new behavior: hard failure with a corruption error. This is the only patch in the five-patch series (along with 3/5) that has automated test coverage; the remaining patches address LLP64-specific scenarios that require manual reproduction.

This is a bug report about a runaway recursion in `git push` when a remote group contains a remote with the same name as the group itself.

The issue occurs when a user defines a remote group (e.g., `remotes.origin = "origin member"`) where one of the members shares the group's name. When `git push origin` is run, the group is expanded recursively: the child `git push` process for the "origin" member re-expands the same group, leading to an unbounded number of nested `git push` processes. The reporter observed over 5,000 processes spawned in 12 seconds, with the recursion only stopping when the deepest child fails. The expected behavior would be either a single push to each unique remote or an explicit error about the cyclic definition.

The bug is present in Git 2.56.0 and appears to exist in `master`, `next`, and `seen` branches as of 2026-11-15. The reporter notes that `push_multiple()` in `builtin/push.c` spawns a child process for each group member without cycle detection, and `add_remote_or_group()` in `remote.c` resolves a name as a group if `remotes.<name>` exists. The fetch side has a similar known issue (reported in 2010 and 2013) with `git remote update`, but no fix was ever merged.

The reproduction steps are clear and minimal: initialize three repositories, configure a remote group that includes a remote of the same name, and run `git push` on the group. The reporter also provides a historical context, noting that `git push <group>` was introduced in Git 2.55.0 and that the test suite lacks coverage for this edge case. Jeff King previously identified the cycle and suggested a fix (expand groups in one process, pass an option to children to prevent re-expansion, and detect cycles), but no patch was submitted.

This is a serious correctness issue that can lead to resource exhaustion. The reporter’s analysis is thorough, and the bug is easily reproducible. The lack of prior fixes despite the fetch-side precedent suggests this is an overlooked edge case. The fix will likely involve cycle detection in group expansion, similar to Jeff King’s earlier suggestion.

This is the third patch in a v2 series improving Git’s HTTP transport resilience. It introduces `http.retryStatusCodes`, a new configuration option that lets users specify which HTTP 4xx and 5xx status codes should trigger retries. By default, only 429 (Too Many Requests) is retried, but users can now opt in to transient 5xx errors like 502, 503, and 504 by setting `http.retryStatusCodes = "429,502,503,504"`. The patch keeps the existing “rate limited” warning for 429 responses and switches to numeric status codes (e.g., “HTTP 502”) for other retryable codes.

The implementation is clean: a new helper `is_retryable_http_code()` parses the comma- or whitespace-separated list, and the retry logic in `handle_curl_result()` and `http_request_recoverable()` now consults this list instead of hardcoding 429. Documentation updates clearly explain the new option and its interaction with `http.maxRetries`, `http.retryAfter`, and `http.maxRetryTime`. Tests cover the default behavior (no 5xx retries), configured 5xx retries, Retry-After header handling for 503, exhausted retry reporting, and environment/URL-specific overrides.

This patch directly addresses Junio’s v1 feedback by moving the 400–599 range check to the top of `is_retryable_http_code()` for clarity and restoring the “Too Many Requests” explanatory text for 429 responses. The opt-in design for 5xx retries sidesteps controversy while giving users the flexibility they need. The code looks well-tested and maintainable, and the documentation is thorough. If the series lands, this patch will be the centerpiece that enables more aggressive retry behavior for users who want it.

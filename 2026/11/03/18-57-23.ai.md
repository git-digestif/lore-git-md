This is a **v2 patch series** targeting the HTTP transport layer, addressing four gaps in Git’s handling of transient server errors and rate-limiting. The series builds on Junio C Hamano’s feedback from v1, incorporating clarifications, documentation improvements, and implementation refinements while maintaining its core goal: improving resilience for Git operations against hosting backends and reverse proxies under high concurrency.

The four patches remain structurally unchanged but now address Junio’s review points directly. Patch 1/4 (off-by-one retry count and Retry-After timing) clarifies why the `http_max_retries <= 0` check was moved after the retry loop, resolving a design ambiguity. Patch 2/4 (exponential backoff) now uses `http_max_retries - rate_limit_retries` as the attempt counter, avoiding a separate variable, and improves documentation to distinguish between immediate retries (`http.retryAfter=0`) and exponentially backed-off delays. Patch 3/4 (configurable retry status codes) restores the "Too Many Requests" explanatory text for HTTP 429, moves the `400 <= code < 600` range check to the top of `is_retryable_http_code()` for clarity, and explicitly states that 429 is the *only* default retryable code. Patch 4/4 (POST retries) adds an attempt counter to the `http_retry_wait()` call, ensuring consistent backoff behavior across GET and POST requests.

Key technical details carry over from v1: the series introduces `http.retryStatusCodes` (defaulting to "429"), exponential backoff for retries when Retry-After headers are absent, and retries for HTTP POST requests (critical for fetch/clone data transfers and partial clone operations). Tests remain thorough, with `t/t5584-http-429-retry.sh` expanded to cover the new behaviors, including POST retries and 5xx error handling. The series continues to sidestep controversy by making 5xx retries opt-in via configuration, avoiding debates about default behavior.

The v2 changes are narrowly targeted at Junio’s feedback, suggesting the author has engaged constructively with the review. The series now feels more polished, with clearer documentation and more maintainable code. The only remaining open question—whether the default retryable status codes should include 5xx errors—remains unresolved, but the opt-in design ensures it won’t block progress. This looks like a well-motivated, technically sound effort that should be uncontroversial for users who want more aggressive retry behavior.

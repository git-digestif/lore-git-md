This is the third patch in Ravi Mistry’s four-patch series improving Git’s HTTP transport resilience. The patch introduces the `http.retryStatusCodes` configuration option, allowing users to specify which HTTP status codes (400–599) should trigger retries. This version (v2) addresses Junio C Hamano’s feedback from the previous iteration, focusing on documentation clarity and code structure.

The patch now restores the helpful "Too Many Requests" explanatory text for HTTP 429 in the documentation and explicitly states that `http.retryStatusCodes` configures the set of retryable status codes, with 429 as the only default. The implementation also moves the `400 <= code < 600` range check to an early return in the `is_retryable_http_code()` helper, improving readability. These changes make the patch’s intent clearer without altering its core functionality.

The series as a whole targets real gaps in Git’s HTTP error handling—missing exponential backoff, inflexible retry codes, and no retries for POST requests—and this patch specifically addresses the latter two. The opt-in design for 5xx retries avoids controversy, though the default behavior remains an open question. The patch is well-motivated, with thorough test coverage in `t/t5584-http-429-retry.sh` verifying configurable retries, Retry-After handling for 503, and environment variable support.

Junio’s feedback was constructive and tested-level, and Ravi’s response is prompt and precise. The patch looks ready for further review or integration, assuming no new objections arise. If you care about Git’s resilience when interacting with flaky HTTP backends, this is worth a closer look.

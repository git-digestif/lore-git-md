Subject: Critical regression in promisor remote lazy-fetch (Git 2.54.0)
Series version: N/A (bug report)
Originating author: Patrick Ohly
Thread type: bug report

Core problem or goal
A critical regression in Git 2.54.0 breaks the promisor remote lazy-fetch mechanism in partial clones. When `git merge` attempts to lazily fetch missing objects, the server rejects the request with "not our ref", causing the merge to fail. The issue was introduced by commit `5946a564` ("odb/source: make `read_object_info()` pluggable") as part of the ODB abstraction effort. The regression blocks CI workflows for projects like Kubernetes that rely on blobless partial clones. The timing of the regression's manifestation remains unclear: Kubernetes CI ran successfully for days before encountering the failure, suggesting a rare or environment-specific trigger.

Current status
Under review. The regression is confirmed to affect Git 2.54.0 and `master`, with Git 2.52.0 and earlier unaffected. A minimal reproduction case is provided, and the root cause is identified: a stale loose object cache invariant violation exposed by the ODB abstraction work. The fix strategy (update oidtree after loose object writes in listed subdirectories) is proposed but not yet implemented. Patrick Steinhardt's input on the fix's alignment with ODB design goals is still pending. The Kubernetes project remains on Git 2.52.0 as a workaround. The unexplained timing of the failure adds uncertainty to the root-cause analysis.

Key technical details
- **Affected commit**: `5946a564` ("odb/source: make `read_object_info()` pluggable")
- **Subsystems touched**: ODB abstraction layer, promisor remote lazy-fetch mechanism, loose object cache
- **Impacted workflow**: `git merge` in blobless partial clones; potentially any operation writing loose objects after listing their subdirectory (e.g., `git checkout`, `git rebase`)
- **Error message**: "not our ref" during lazy fetch
- **Root cause**: Loose object cache's oidtree does not reflect newly written objects in subdirectories already listed by prefetch, causing incorrect "missing object" conclusions and spurious lazy fetches
- **Mechanism**: Merge-ort prefetch lists subdirectories, merge writes a new loose object (e.g., merged blob) into one of those subdirectories, cache's oidtree remains stale, subsequent lookups trigger lazy fetch for locally existing objects
- **Regression boundary**: Git 2.52.0 (works) → Git 2.54.0 (fails)
- **Masking factor**: Prior to `5946a564`, `odb_reprepare()` discarded the entire loose cache, but ODB abstraction preserves it across reprepares
- **Test coverage**: Unit test for loose source exists locally; end-to-end test deemed cumbersome due to need for merged blob with specific first-byte collision
- **Timing mystery**: Kubernetes CI ran successfully for days before encountering the failure, implying the regression may depend on a rare trigger (e.g., object layout, merge conflict pattern, or server-side change)

Open questions and loose ends
- Whether the proposed fix (updating oidtree after loose object writes) aligns with the ODB abstraction's design goals and invariants
- Whether other operations beyond `git merge` are affected (e.g., `git checkout`, `git rebase`)
- Timeline for implementation and integration of the fix; urgency remains high due to Kubernetes CI blockage
- Potential need for broader cache invalidation strategy if the proposed fix is deemed insufficient
- The unexplained timing of the regression's manifestation: what specific conditions trigger the bug, and why did it appear only after days of uneventful usage?

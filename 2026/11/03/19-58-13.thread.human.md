This thread began when Kevin Lyles reported an inconsistency in `git commit <pathspec>`: when a pre-commit hook modifies the index, those changes are silently discarded if a pathspec is provided but preserved otherwise. The discussion quickly shifted from a potential bug fix to a broader policy question about whether pre-commit hooks should mutate the index at all.

Junio C Hamano, the maintainer, reframed the issue as a policy matter, declaring that pre-commit hooks are intended for validation only and that index mutation is unsupported. The original pathspec inconsistency is now considered a non-issue because the underlying use case—hooks modifying the index—is out of scope. The thread has since focused on two follow-up actions: clarifying the `githooks` documentation to explicitly discourage mutation and exploring whether Git can enforce this restriction at the code level (e.g., by rejecting index changes in hooks).

Chris Torek’s recent email provided technical depth to the policy discussion, explaining why the inconsistency exists. Git’s rollback machinery uses multiple index files (`.git/index`, `.git/index.lock`, and temporary files for `--only`/`--include`), making it impractical for hooks to reliably modify the index. Torek’s explanation reinforces that the observed behavior is a design consequence, not a bug, and suggests a practical workaround: a wrapper script that stages changes before invoking `git commit`, with the hook acting purely as a validator. This addresses Kevin Lyles’ real-world use case—large repositories where per-file operations are slow—without requiring Git to support hook-induced index changes.

The thread remains open for documentation updates and enforcement feasibility discussions. Key open questions include how to update the `githooks` documentation, whether code-level enforcement is technically feasible without breaking legitimate use cases (e.g., hooks that stage untracked files), and how to handle backward compatibility for existing hooks that rely on index mutation. Torek’s technical rationale strengthens the argument against enforcement, as it highlights the complexity of reliably detecting and rejecting hook mutations. The focus is now on policy and documentation, not code changes.

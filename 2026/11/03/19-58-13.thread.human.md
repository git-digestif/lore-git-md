This thread began as a bug report about an inconsistency in `git commit <pathspec>` when pre-commit hooks modify the index—those changes are silently discarded if a pathspec is provided but preserved otherwise. The project has since clarified that pre-commit hooks are intended for validation only, not index mutation, and the observed behavior is a side effect of Git’s rollback machinery rather than a bug. Junio C Hamano has framed the issue as a policy matter, with two follow-up actions: updating documentation to discourage index mutation in hooks and evaluating whether code-level enforcement (e.g., rejecting such mutations) is feasible.

Kevin Lyles’ latest email underscores the practical challenges of this policy shift. His team relies on pre-commit hooks to automate index modifications (e.g., appending metadata) in a large repository where `git ls-files` is prohibitively slow. While Chris Torek’s proposed workaround—a wrapper script that stages changes before invoking `git commit`—aligns with Git’s design, Lyles argues it would disrupt existing workflows and introduce performance overhead. He explores alternatives like clean filters but notes they require upfront file lists, which are impractical in his repository. The thread now grapples with whether Git can accommodate such use cases without compromising its design principles, especially if enforcement were to break existing automation. No decisions have been made, but the discussion highlights the tension between policy and real-world constraints.

This is a bug report about a regression in `git push` where the `--force-with-lease` option is silently ignored when pushing to a remote *group* (defined via `remotes.<group>`) unless an explicit `<refname>` is provided.

The report comes with a minimal reproduction recipe: two bare repos grouped under `remotes.both`, a local work repo, and a sequence of commits that creates a non-fast-forward situation. When the user runs `git push --force-with-lease --dry-run both main`, the push is rejected as non-fast-forward on both remotes, whereas the same command with an explicit `--force-with-lease=main` or with `--force` works as expected. `GIT_TRACE` output confirms that the bare `--force-with-lease` flag is not forwarded to the child `git push` processes spawned for each remote in the group.

The issue is present on both Windows (Git for Windows) and Linux builds, across multiple integration branches (`master`, `next`), and is not affected by `--dry-run`. The reporter has tested versions up to `next` (2.56.0.506.g506a7eabc5). The key technical detail is that the flag is dropped during the internal decomposition of the group push into individual remote pushes, but only when the flag is given in its bare form (`--force-with-lease`) rather than with an explicit ref (`--force-with-lease=main`). The older `--force` flag is forwarded correctly in all cases.

This is the second patch in a v2 series improving Git’s HTTP transport resilience. It introduces **exponential backoff** for retries when servers return HTTP 429 (Too Many Requests) without a Retry-After header.

The patch modifies `http.c` to double the configured `http.retryAfter` delay on each subsequent retry (1s, 2s, 4s, …), clamping the delay at `http.maxRetryTime`. This matches curl’s `--retry` behavior while preserving the existing default of 0 for immediate retries. The documentation (`Documentation/config/http.adoc`) is updated to clarify that `http.retryAfter` is now the *initial* delay, and the test suite (`t/t5584-http-429-retry.sh`) adds three new tests: one verifying the doubling behavior, one checking the clamp at `http.maxRetryTime`, and one confirming that a server-provided Retry-After header still overrides the backoff.

Key symbols introduced: the `attempt` parameter in `handle_rate_limit_retry()`, which uses `http_max_retries - rate_limit_retries` as the attempt counter. The patch is well-motivated—busy servers recover faster with exponential backoff than with a fixed delay—and the implementation is clean, addressing Junio’s v1 feedback by unifying the attempt counter logic and improving documentation. The test coverage is thorough, ensuring the new behavior is exercised across edge cases. This looks like a solid, uncontroversial improvement.

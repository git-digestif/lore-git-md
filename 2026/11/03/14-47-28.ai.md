This is the fourth patch in Ravi Mistry's four-patch series improving Git's HTTP transport resilience, and Junio C Hamano's review of it. The series as a whole targets four gaps in Git's HTTP error handling: an off-by-one retry counter bug, missing exponential backoff, inability to retry transient 5xx errors, and lack of retries for HTTP POST requests. This patch specifically extends retry logic to cover HTTP POST requests, which handle data transfer during fetch/clone and partial clone blob downloads.

Junio's review is brief and positive, focusing on the clean extraction of retry wait logic into a new shared helper function `http_retry_wait()`. He notes that the new function is well-placed, replacing duplicated code in `http_request_recoverable()` with a single call. The review is surface-level and tested: Junio explicitly states he appreciates the refactoring but does not engage with the patch's core behavior change (POST retries) or test coverage. No objections or requests for changes are raised.

The patch itself moves retry wait logic from `http_request_recoverable()` into `http_retry_wait()`, then uses it in both `probe_rpc()` and `post_rpc()`. It defers error reporting until retries are exhausted and ensures the "Content-Encoding: gzip" header is re-attached when retrying compressed requests. Test coverage expands to verify POST retries for 429/502 errors, partial-clone blob fetches surviving 502s, and gzipped POST header preservation.

With this review, the entire series has now received Junio's feedback. Patches 1–3 had substantive design questions about exponential backoff behavior and documentation clarity, but this patch (4/4) is uncontroversial. The series remains under review, awaiting the author's response to Junio's earlier feedback on patches 2 and 3.

This is a substantive review comment from Junio C Hamano on the second patch of Farid Zakaria’s two-patch series fixing a race condition in the Git credential-cache daemon. The series aims to prevent concurrent `git credential-cache store` commands from causing one daemon to unlink another’s socket, which can lead to lost credentials and orphaned daemons.

Junio’s concern centers on the architectural mismatch between the `unix_ss_*` API (used for safe Unix domain socket management) and the `tempfile` API. The patch currently registers the socket file as a tempfile, which Junio argues is unnecessary and potentially harmful. The `unix_ss_*` API already handles stale socket cleanup: if a daemon exits abruptly, the next daemon will detect the stale socket via `is_another_server_alive()`, unlink it, and rebind safely. By contrast, the `tempfile` API’s signal handler or `delete_tempfile()` call would blindly unlink the socket, bypassing the `unix_ss_was_stolen()` safety check that prevents a dying daemon from removing a socket now owned by a new daemon.

The review references `fsmonitor--daemon.c` as a precedent, which uses `ipc_server_init_async()` (and thus `unix_ss_create()`) without involving the `tempfile` API. Junio’s question—whether mixing these APIs is architecturally sound—suggests the patch should follow the same pattern and drop the `tempfile` registration entirely. This would simplify the code and align it with the existing safety mechanisms in the `unix_ss_*` subsystem.

No alternative implementation is proposed in the email, but the implication is clear: the patch should rely solely on `unix_ss_create()` and `unix_ss_free()` for socket management. The review is substantive, engaging with the design and safety implications of the change, and raises a legitimate concern about the robustness of the current approach. Farid’s v2 will likely need to address this before the patch can proceed.

Subject: [PATCH] hash: prevent panic when formatting ObjectID with invalid algorithm
Series version: standalone patch (first submission)
Originating author: shrimech
Thread type: bugfix patch (Rust code)

Core problem or goal
Fix a panic in Git's Rust `hash` module when formatting an `ObjectID` whose `algo` field contains an unrecognized algorithm identifier. The panic occurs because `as_slice()` is unwrapped without handling the error case; the fix replaces the unwrap with a fallback that displays raw hash bytes and appends an `:invalid-hash-algo-<id>` marker.

Current status
Under review (no prior versions, no maintainer decision). The open question about alignment with the C codebase is now resolved by brian m. carlson: the Rust implementation's behavior (marking invalid algorithms as `:invalid-hash-algo-<id>`) is correct and should not be changed.

Key technical details
- File touched: `src/hash.rs`
- Symbol modified: `Display` implementation for `ObjectID`
- New behavior: invalid algorithms now render as `<raw-bytes>:invalid-hash-algo-<id>` instead of panicking
- Test coverage: regression test added in the same patch, demonstrating the expected output format for algorithm ID 0
- Subsystem: Rustification (hash module)
- Discrepancy with C code: Rust treats algorithm ID 0 as invalid (appending `:invalid-hash-algo-0`), while the C code (`hash_to_hex_algop_r` in `hex.c`) silently falls back to the default hash algorithm when `algo` is 0. brian m. carlson confirms this discrepancy is intentional and the Rust behavior is preferred; the C code's fallback should eventually be removed.
- Related work: brian m. carlson references a patch on their `sha256-interop` branch that makes the `algo` field non-public, preventing invalid states from being constructed.

Open questions and loose ends

This is a bug report about unexpected interaction between the pre-commit hook and `git commit <pathspec>`.

Kevin Lyles describes a scenario where `git commit <file>` behaves differently depending on whether other files are already staged and whether the commit is invoked with a pathspec. When a pre-commit hook modifies the index, those changes are lost in the final commit if the command is run with a pathspec (e.g., `git commit file.txt`), but preserved if run without one or if other files are already staged. The commit message claims files specified via pathspec are staged on top of existing staged changes, but this does not hold when the pre-commit hook alters the index.

The report includes a minimal reproducer: a pre-commit hook that appends text to staged files in both the index and worktree, followed by steps to trigger the inconsistency. Kevin notes that his real-world use case involves a large repository (4× the Linux kernel by file count) where per-file operations would be prohibitively slow, making the pre-commit hook the only practical solution.

The question is whether this discrepancy is intentional. No prior discussion or related efforts (e.g., hook subsystem changes) are mentioned in the email. The issue appears to be a low-level behavior quirk rather than a design choice.

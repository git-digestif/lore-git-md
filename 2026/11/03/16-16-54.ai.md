This is a **substantive review** of the second patch in Harald Nordgren’s v3 series implementing the `%gb` format placeholder for `git log -g` and `git reflog`. Phillip Wood identifies a **regression in branch-name detection** when `GIT_REFLOG_ACTION` is set, causing incorrect branch labels in reflog output.

The issue surfaces during rebase operations where `GIT_REFLOG_ACTION` alters reflog messages (e.g., `"sync switch: checkout ..."`). The `%gb` logic misinterprets these messages, assigning the wrong branch name to entries. Phillip provides a concrete example where entries labeled `"sequencer-delete-REBASE_HEAD"` should instead show `"fix-nth-prior-checkout"` or `"detached at <commit>"`. The bug stems from the `parse_branch_move()` function’s inability to handle non-standard reflog messages introduced by `GIT_REFLOG_ACTION`.

The review is **tested**: Phillip reproduces the issue locally and includes the exact reflog output demonstrating the mislabeling. The regression affects edge cases but is not theoretical—it breaks real-world workflows where `GIT_REFLOG_ACTION` is used (e.g., custom rebase scripts). The patch’s test coverage (`t/t1414-reflog-walk.sh`) does not catch this, as it assumes standard reflog messages.

Phillip’s feedback is **actionable**: the fix likely involves extending `parse_branch_move()` to recognize `GIT_REFLOG_ACTION`-modified messages or normalizing reflog messages before parsing. The review does not question the `%gb` feature’s design (which addresses prior critiques about composability and correctness) but highlights a gap in its implementation. No alternative approaches are suggested; the focus is on fixing the regression.

The broader series remains **under review**, with this regression as the sole unresolved technical issue.

This is a substantive review reply from Junio C Hamano on the second patch of Ravi Mistry’s four-patch series improving Git’s HTTP transport resilience. The patch introduces exponential backoff for retry delays when servers return HTTP 429 without a Retry-After header, and Junio’s feedback focuses on two potential inconsistencies in the design.

Junio begins by praising the logic of exponential backoff but questions whether the default `http.retryAfter` value of 0 (immediate retry) is compatible with the new behavior. With the current implementation, a zero initial delay would result in immediate retries regardless of the attempt count, effectively disabling the backoff mechanism unless the user explicitly configures a positive value. This could lead to rapid retry exhaustion under sustained server overload, undermining the patch’s goal of graceful recovery.

He also notes an inconsistency in how `http.maxRetryTime` is handled. For server-provided Retry-After headers or statically configured `http.retryAfter` values, exceeding `http.maxRetryTime` triggers an immediate failure. However, the patch caps exponentially backed-off delays at `http.maxRetryTime` instead of failing, which Junio suggests is actually the more useful behavior. He implies the patch might want to unify these two behaviors—either always cap or always fail—rather than treating them differently.

The review includes a technical observation about the loop arithmetic in `handle_rate_limit_retry()`, which Junio recognizes as a careful way to double the delay without risking integer overflow. He also notes the introduction of a new `attempt` counter variable, suggesting that reusing the existing `rate_limit_retries` counter (passing `http_max_retries - rate_limit_retries` as the attempt count) might achieve the same result without adding a new variable.

No objections or requests for changes are raised; the feedback is exploratory rather than prescriptive. The patch remains well-motivated and technically sound, but these design questions could shape how the feature behaves in edge cases. The author has not yet responded.

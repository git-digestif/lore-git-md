This is a **substantive review** of the third patch in Ravi Mistry’s four-patch series improving Git’s HTTP transport resilience. Junio C Hamano reviews the documentation and implementation of the new `http.retryStatusCodes` configuration option, which allows users to specify which HTTP status codes (400–599) should trigger retries.

Junio identifies two issues in the documentation updates for `http.retryAfter`, `http.maxRetries`, and `http.maxRetryTime`. First, the helpful explanatory text "Too Many Requests" (for HTTP 429) is lost in the revised descriptions. Second, the phrasing "HTTP 429 by default" does not clearly communicate that 429 is the *only* default member of the retryable status codes set—readers might misinterpret it as merely the first example. Junio praises the clarity of the `http.retryStatusCodes` documentation itself, which explicitly describes the default and provides an example.

On the implementation side, Junio notes that the `is_retryable_http_code()` helper parses the comma- or whitespace-separated string from `http.retryStatusCodes` *on every call*, rather than pre-parsing it into an array of integers when the configuration is read. While he acknowledges this is not performance-critical (since retries involve waiting), he suggests pre-parsing would be cleaner. He also points out that the `400 <= code < 600` range check appears in the loop condition, which is unusual but not incorrect. The parsing logic itself is described as "cleanly done."

The review is constructive and tested-level, focusing on clarity and maintainability rather than functional correctness. No objections are raised, and the feedback is framed as suggestions rather than demands. The patch remains under review, awaiting the author’s response to these documentation and implementation points.

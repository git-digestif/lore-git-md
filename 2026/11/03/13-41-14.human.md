This is a **substantive review** from Junio C Hamano on the third patch in Ravi Mistry’s four-patch series improving Git’s HTTP transport resilience. The patch introduces `http.retryStatusCodes`, a config option to specify which HTTP status codes (400–599) should trigger retries, expanding beyond the hardcoded 429 (Too Many Requests).

Junio’s feedback focuses on the **documentation clarity** in the man pages. He points out that the updated descriptions for `http.retryAfter`, `http.maxRetries`, and `http.maxRetryTime` lose the helpful "Too Many Requests" label for HTTP 429 and fail to clearly communicate that 429 is the *only* default member of the retryable status codes set. The current wording ("HTTP 429 by default") could mislead readers into thinking other codes might also be included by default. Junio suggests rephrasing to make the set membership semantics explicit, noting that the description of `http.retryStatusCodes` itself is already clear and well-written.

On the **code implementation**, Junio observes that the `is_retryable_http_code()` helper parses the comma- or whitespace-separated config string *on every call*, which is fine for this non-performance-critical path but feels slightly inefficient. He muses that pre-parsing the string into an array of integers at config-read time might be cleaner, though he acknowledges the current approach is functionally sound and the strtol()-based parsing is well-implemented. He also notes the odd placement of the `400 <= code < 600` range check in the loop control, though this is a minor stylistic point.

The review is **constructive and tested-level**—Junio has clearly read the patch closely and understands both the user-facing implications and the internal mechanics. No fundamental objections are raised; the feedback is about polish rather than correctness. The series as a whole addresses a real pain point for users operating at scale, and this patch in particular fills a long-standing gap in Git’s HTTP error handling. The opt-in nature of 5xx retries sidesteps controversy, so the only likely discussion point is whether the default set should include more codes.

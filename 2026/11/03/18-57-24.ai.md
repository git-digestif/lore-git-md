This is the first patch in a **v2 series** improving Git’s HTTP transport resilience. It fixes two bugs in the existing HTTP 429 retry logic introduced by commit 640657ffd0 (2026-03-17).

The first bug is an off-by-one retry counter: the pre-decrement loop condition (`--rate_limit_retries`) causes `http.maxRetries=1` to perform zero retries instead of one, and a 429 after a 401 re-authentication can wrap the counter from 0 to -1 (truthy in C). The fix changes the loop condition to `http_max_retries > 0 && rate_limit_retries-- > 0` and moves the `http_max_retries <= 0` check after the loop, ensuring the correct number of retries and avoiding spurious "retries-exhausted" logs.

The second bug is a race in Retry-After header parsing: `CURLINFO_RETRY_AFTER` is queried in `http_request()` *after* `handle_curl_result()` has already logged the uninitialized `results->retry_after` (-1) to Trace2. The fix moves the extraction into `finish_active_slot()`, initializing `slot->results->retry_after = -1` first, so both `handle_curl_result()` and callers observe the correct value.

The patch touches `http.c`, updates the test helper `t/lib-httpd/http-429.sh` to support configurable failure counts (1–3), and adds three new tests in `t/t5584-http-429-retry.sh`: verifying `http.maxRetries=1` retries once, `http.maxRetries=2` fails after three 429s but succeeds after two, and Trace2 logs the actual Retry-After value instead of -1. The changes are narrowly targeted at Junio’s feedback from v1 and feel like a clear, uncontroversial bugfix.

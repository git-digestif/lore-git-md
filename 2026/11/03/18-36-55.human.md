This is a brief follow-up in the ongoing bugfix thread about `git rev-list`'s connectivity check and replacement objects. Junio C Hamano, the maintainer, acknowledges that Kristofer Karlsson’s earlier explanation resolved his conceptual concern. The key insight was that replacement objects are stored as regular refs (`refs/replace/OLD -> NEW`), so their reachable objects are already covered by ordinary connectivity checks during fetch or push. This means the patch’s approach—ignoring replacements during the connectivity check—does not risk missing objects that should be validated, since those objects are already part of the graph when the replacement refs themselves are transferred.

The discussion is now effectively settled in favor of the patch’s design. Junio’s reply removes the last open question about whether the connectivity check should verify both original and replacement objects, confirming that the current approach is correct. The patch itself remains unchanged: it adds a `--connectivity-check` flag to `git rev-list` that ignores replacement refs, updates `tree-verify.c` to drop the `OBJECT_INFO_LOOKUP_REPLACE` flag, and adjusts test `t5413` to reflect the new behavior.

This is a well-motivated bugfix targeting a long-standing inconsistency. The patch aligns `git rev-list`'s connectivity check with the behavior of other commands (`fsck`, `prune`, `pack-objects`, `upload-pack`) that already ignore replacements, preventing a scenario where a pack passes the connectivity check but later fails `fsck` due to missing original objects masked by replacements. The change is narrow in scope, touching only three files, and the test coverage ensures regression protection. With Junio’s endorsement, the patch looks ready to proceed, though the earlier concern about the `t5413` test change (which could break existing workflows relying on the edge case) remains worth noting for anyone reviewing the final version.

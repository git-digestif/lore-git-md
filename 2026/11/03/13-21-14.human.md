This is a review comment from Junio C Hamano on the second patch in Ravi Mistry’s four-patch series improving Git’s HTTP transport resilience. The patch introduces exponential backoff for retry delays when servers return HTTP 429 without a Retry-After header.

Junio’s review is substantive and tested-level. He raises two main points about the patch’s design. First, he questions whether the default `http.retryAfter` value of 0 (immediate retry) is compatible with exponential backoff, since it would result in Git retrying immediately until retries are exhausted. Second, he notes an inconsistency in how `http.maxRetryTime` is handled: when a server or configuration specifies a delay longer than `http.maxRetryTime`, Git fails immediately, but when the delay grows via exponential backoff, it is capped at `http.maxRetryTime` instead. Junio suggests that capping the delay is more useful than failing immediately, but the inconsistency might be surprising to users.

Junio also observes that the arithmetic in the backoff loop is carefully written to avoid integer overflow, and he notes that the patch introduces a new `attempt` counter even though the code already tracks retry counts via `http_max_retries` and `rate_limit_retries`. He wonders whether passing `(http_max_retries - rate_limit_retries)` as the `attempt` parameter would suffice, but he is not requesting a change—just pointing out the redundancy.

The review is constructive and does not raise objections to the patch’s core functionality. The discussion is likely to focus on whether the default `http.retryAfter` value should be adjusted and whether the handling of `http.maxRetryTime` should be made consistent. The patch remains well-motivated and thoroughly tested, addressing a real-world scalability issue for Git users interacting with busy hosting backends.

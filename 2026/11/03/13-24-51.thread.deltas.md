## 2026/11/04

- [2026/11/04/10-11-21 by Kristofer Karlsson <krka@spotify.com>] Kristofer Karlsson reproduced the failure with the reported steps and traced it to the loose object cache: writing a loose object does not update the two-layer cache (bitmap of listed "objects/XX/" subdirectories plus oidtree), so once a subdirectory has been listed, a quick existence check for a newly written object in that same subdirectory wrongly reports it missing. In the reported merge, the content-merged blob 27b64cc8 was written by the merge after merge-ort's prefetch had already listed "27/", so checkout asked the promisor remote for an object that only exists locally, and the batch died on the genuinely missing 3c804b88. He noted the bug predates 5946a564cd but that commit exposed it because it stopped flushing the whole loose cache on a non-quick miss (previously odb_reprepare() discarded it). He proposed maintaining the invariant by inserting the new OID into the oidtree after a successful loose write when the subdirectory was already listed, said he has a local fix with a unit test, and asked for Patrick Steinhardt's thoughts on the approach before polishing it into a patch.
- [2026/11/04/11-56-53 by Patrick Ohly <patrick.ohly@intel.com>] Patrick Ohly asked why the failure suddenly started, noting Kubernetes CI had run git 2.54.0 for several days without issues, citing a clone log and prow job that merged multiple PRs with 2.54.0 in the clonerefs image v20261028-c06373a3e.
- [2026/11/04/12-19-42 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt confirmed he can reproduce the bug and stated the root cause is older than the bisected commit: the loose object cache is never updated when writing objects, so a populated sharding directory leaves the cache stale and existence checks then pretend the object does not exist; commit 5946a564cd removed the loose-cache flush on object misses, and the old flush only masked the bug by coincidence via interleaved reads and existence checks. He said he has sent fixes in the series <20261104-pks-odb-loose-stale-cache-v1-0-a00d5cdb5e7d@pks.im>.
- [2026/11/04/12-22-18 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt answered Patrick Ohly's question: the trigger depends on the actual object IDs being merged — at least one merged object must share its first two hex characters with a newly written object having the same first two characters, which produces the stale loose object cache and the fetch attempt from the promisor remote; he again pointed to the fix series <20261104-pks-odb-loose-stale-cache-v1-0-a00d5cdb5e7d@pks.im>.

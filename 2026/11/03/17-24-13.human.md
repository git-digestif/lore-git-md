This is Junio’s reply to the second patch in Farid Zakaria’s two-patch series fixing a race in the credential-cache daemon. The series aims to stop concurrent daemons from clobbering each other’s sockets, which can lose credentials and leave orphaned processes.

Junio questions the architectural choice of mixing the `unix_ss_*` socket-management API with the `tempfile` API. He points out that `unix_ss_create()` already handles stale-socket detection and safe rebinding, so registering the socket as a tempfile is redundant and potentially dangerous. If the daemon crashes, the tempfile signal handler will unlink the socket blindly, bypassing the inode check in `unix_ss_was_stolen()` that prevents a dying daemon from removing a socket now owned by a new daemon. The result could reintroduce the very race the patch is trying to fix.

He backs this up with a concrete example: the fsmonitor daemon uses `ipc_server_init_async()`, which relies solely on `unix_ss_create()` and never touches `tempfile`. The implication is that the credential-cache daemon should follow the same pattern.

The question is substantive—it goes to the heart of how the socket is managed—and looks well-founded. Farid will almost certainly need to drop the `tempfile` registration in v2 and let `unix_ss_free()` handle cleanup. The fix itself (using `unix_ss_create()`) remains sound; only the cleanup layering needs adjustment.

This is a substantive review in the ongoing policy discussion about pre-commit hooks and index mutation. Chris Torek explains the internal mechanics behind the observed behavior: Git uses multiple index files (`.git/index`, `.git/index.lock`, and temporary files for `--only`/`--include`) to handle rollback semantics, making it impractical for pre-commit hooks to reliably modify the index. The explanation clarifies why the pathspec inconsistency exists—hooks can't predict which index file will become the final snapshot, so their changes are effectively ignored in pathspec-based commits.

Torek’s review aligns with Junio’s earlier policy stance but adds technical depth, reinforcing that index mutation in hooks is unsupported by design. He suggests a workflow alternative: a wrapper script that stages changes before invoking `git commit`, with the hook acting purely as a validator. This addresses Kevin Lyles’ real-world use case (large repositories where per-file operations are slow) without requiring Git to support hook-induced index changes.

3. **Strengthening the policy argument**: Torek’s technical rationale makes it harder to argue for code-level enforcement (e.g., rejecting hook mutations) without breaking legitimate use cases like `git add` in hooks.

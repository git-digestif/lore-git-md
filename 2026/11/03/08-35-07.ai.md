This is a follow-up in the ongoing bugfix thread about `git rev-list`'s connectivity check and replacement objects. Kristofer Karlsson replies to Junio C Hamano’s conceptual question, acknowledging the possibility of a future enhancement but offering a preliminary rationale for the current design. The patch itself remains unchanged; this email is purely a discussion point.

Kristofer’s response is brief and pragmatic. He notes that replacement objects are stored as regular refs (`refs/replace/OLD -> NEW`), so their reachable objects should already be covered by ordinary connectivity checks during fetch or push. This suggests that treating replacements as additional tips (Junio’s alternative) might be redundant in practice, since the objects they reference are already part of the connectivity graph when those refs are transferred. The reply does not dismiss Junio’s idea outright but frames it as a potential follow-up rather than an immediate requirement.

The thread’s core question—whether to ignore replacements (current patch) or verify both originals and replacements—remains open, but Kristofer’s reasoning provides a concrete technical anchor for the discussion. No new code or test changes are introduced here; the focus is on design intent. The patch is still small, well-motivated, and touches only `builtin/rev-list.c`, `tree-verify.c`, and the test suite (`t5413`), so iterating on the design would be straightforward if consensus shifts.

Key details for future reference: the patch adds `--connectivity-check` to `rev-list`, disables replacement refs during the check, and updates `tree-verify.c` to drop `OBJECT_INFO_LOOKUP_REPLACE`. The test coverage in `t5413` already reflects the new behavior, ensuring regression protection. The discussion now hinges on whether the current approach (ignoring replacements) is sufficient or if a stricter check (verifying both originals and replacements) is needed.

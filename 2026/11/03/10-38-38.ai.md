This is a **bugfix** patch addressing a consistency issue in `git rev-list`'s connectivity check, part of an ongoing thread about whether replacement objects should be ignored during object validation. The author, Kristofer Karlsson, responds to Patrick Steinhardt's substantive review by clarifying two key points.

First, the test change in `t5413` was not an oversight: the original behavior (accepting a commit with a missing original tree if a replacement exists) was intentional, introduced in a prior series to maintain compatibility. The new patch deliberately breaks this edge case to align with the established behavior of other commands (`fsck`, `prune`, etc.), which ignore replacements. This suggests the change could affect real-world workflows that rely on replacement objects masking missing objects during fetches or pushes.

Second, the removal of `OBJECT_INFO_LOOKUP_REPLACE` from `tree-verify.c` is justified as a necessary cleanup for the connectivity check, since the global replacement mechanism is already disabled when this code path runs. Kristofer confirms that `tree-verify.c` is only used by `rev-list --connectivity-check=incremental`, so the change is scoped correctly. However, he notes a separate, unrelated issue in `mktree`: it follows replacements when checking object existence but writes the original OID into the tree, which could allow missing objects to pass validation. This is flagged as a potential bug but not addressed in this patch.

The response leaves one open question: whether the documentation in `git-replace.adoc` (which claims all commands except reachability traversals use replacements by default) needs updating to reflect the new exception for `rev-list --connectivity-check`. The patch itself remains narrowly focused on the connectivity check, avoiding broader changes to the replacement mechanism.

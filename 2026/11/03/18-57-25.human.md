This is the second patch in Ravi Mistry’s v2 series improving Git’s HTTP transport resilience. It introduces **exponential backoff** for retries when servers return HTTP 429 (Too Many Requests) without a Retry-After header.

The patch updates the `http.retryAfter` configuration to serve as the *initial* delay, then doubles it on each subsequent retry (1s, 2s, 4s, …), clamping the delay at `http.maxRetryTime`. This matches curl’s `--retry` behavior and prevents Git from burning through all retries too quickly against a temporarily overloaded server. The documentation is expanded to clarify the new behavior, and the implementation avoids a separate counter by reusing `http_max_retries - rate_limit_retries` as the attempt index. Three new tests verify the doubling logic, the clamping at `http.maxRetryTime`, and that Retry-After headers still override the backoff.

This is a **well-motivated performance improvement** that directly addresses the thread’s core goal of making Git more resilient to transient HTTP errors. The changes are clean, the tests are thorough, and the documentation updates are clear. Junio’s feedback from v1 has been fully incorporated, leaving no open design questions for this patch. If the series lands, users who set `http.retryAfter` to a positive value will see more effective retries without any configuration changes.

This is a brief follow-up in the ongoing bugfix thread about `git rev-list`'s connectivity check and replacement objects. Junio C Hamano acknowledges Kristofer Karlsson’s clarification: since replacement objects are stored as regular refs (`refs/replace/OLD -> NEW`), their reachable objects are already covered by ordinary connectivity checks during fetch or push. This resolves the earlier conceptual question—whether the connectivity check should ignore replacements (current patch) or verify both originals and replacements—by confirming that the current approach is sufficient. Junio’s reply removes the last open design ambiguity, leaving only the technical concerns (workflow impact from the `t5413` test change and the scoped removal of `OBJECT_INFO_LOOKUP_REPLACE` in `tree-verify.c`) as the remaining discussion points.

The patch itself remains unchanged: it adds a `--connectivity-check` flag to `git rev-list` that ignores replacement refs, updates `tree-verify.c` to drop the `OBJECT_INFO_LOOKUP_REPLACE` flag, and adjusts test `t5413` to reject packs where replacements mask missing objects. The core files touched are `builtin/rev-list.c`, `tree-verify.c`, and `t/t5413-rev-list-connectivity.sh`. The design is now aligned with the established behavior of other commands (`fsck`, `prune`, `pack-objects`, `upload-pack`), and Junio’s endorsement ("no need to do anything extra") effectively closes the alternative approach. The thread is now focused on implementation details rather than design.

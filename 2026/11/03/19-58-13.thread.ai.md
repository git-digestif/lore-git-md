Core problem or goal
The thread began as a report of an inconsistency in `git commit <pathspec>` behavior when pre-commit hooks modify the index (hook changes are silently discarded with a pathspec, preserved otherwise). It has since reframed as a policy question: whether pre-commit hooks should mutate the index at all. The project has firmly established that pre-commit hooks are for validation only, and index mutation is unsupported by design. The discussion now centers on the practical impact of enforcing this policy, particularly for teams that rely on hooks to automate index modifications in large repositories.

Current status
Under review for documentation and enforcement policy. Junio C Hamano has declared the original pathspec inconsistency a side effect of Git’s rollback machinery, not a bug. Two follow-up actions remain: (1) clarify documentation to explicitly discourage index mutation in pre-commit hooks, and (2) evaluate whether code-level enforcement (e.g., rejecting index changes in hooks) is feasible without breaking legitimate use cases. Kevin Lyles’ latest email highlights real-world constraints that complicate enforcement: teams using hooks to modify staged files (e.g., appending metadata) in large repositories where `git ls-files` is prohibitively slow. The thread remains open for policy and documentation updates, with no merge status or integration branch changes.

Key technical details
- Subsystem: hooks, index/working tree interaction
- Command: `git commit <pathspec>`
- Files touched: none (behavioral/policy issue)
- New/renamed symbols: none
- On-disk format: unchanged
- Test coverage: none yet; reproducer provided in Kevin Lyles’ initial report (pre-commit hook appending text to staged files)
- Internal mechanics: Git uses multiple index files (`.git/index`, `.git/index.lock`, and temporary files for `--only`/`--include`) to handle rollback semantics. Pre-commit hooks cannot reliably modify the index because they cannot predict which file will become the final snapshot, leading to silent discard of changes in pathspec-based commits. Chris Torek’s explanation confirmed this is a design limitation, not a bug.
- Performance context: In large repositories, `git ls-files` can take 5+ seconds, making wrapper scripts (which require staging changes before `git commit`) impractical for teams automating index modifications via hooks.

Chris Torek’s explanation suggests enforcement may be impractical due to Git’s rollback machinery, but Kevin Lyles’ email adds a new constraint: performance overhead in large repositories.
- **Backward compatibility**: If enforcement is implemented, how will existing hooks that rely on index mutation be handled? Will there be a deprecation period, immediate rejection, or a configuration flag to allow mutations (e.g., `hooks.allowIndexMutation`)?

Subject: Unexpected interaction between pre-commit hook and `git commit <pathspec>`
Series version: none (standalone bug report)
Originating author: Kevin Lyles <klyles@epic.com>
Thread type: bug report / policy discussion

Core problem or goal
The thread investigates an inconsistency in `git commit <pathspec>` behavior when the pre-commit hook modifies the index: hook-induced changes are silently discarded if a pathspec is provided, but preserved otherwise. The discussion has expanded to question whether pre-commit hooks should mutate the index at all, regardless of pathspec handling. The project has now firmly established that pre-commit hooks are for validation only, and index mutation is unsupported by design.

Current status
Under review for documentation and enforcement policy. Junio C Hamano has reframed the issue as a policy matter: pre-commit hooks must not mutate the index. Two follow-up actions remain: (1) clarify documentation to explicitly discourage mutation, and (2) evaluate whether code-level enforcement (e.g., rejecting index changes in hooks) is feasible without breaking legitimate use cases. The original pathspec inconsistency is now understood as a side effect of Git’s rollback machinery and is not considered a bug. No merge status or integration branch updates; the thread remains open for documentation patches and enforcement feasibility analysis.

Key technical details
- Subsystem: hooks, index/working tree interaction
- Command: `git commit <pathspec>`
- Files touched: none (behavioral/policy issue)
- New/renamed symbols: none
- On-disk format: unchanged
- Test coverage: none yet; reproducer provided in Kevin Lyles' report (pre-commit hook appending text to staged files)
- Internal mechanics: Git uses multiple index files (`.git/index`, `.git/index.lock`, and temporary files for `--only`/`--include`) to handle rollback semantics. Pre-commit hooks cannot reliably modify the index because they cannot predict which file will become the final snapshot, leading to silent discard of changes in pathspec-based commits.

Open questions and loose ends
- **Documentation**: How should the `githooks` documentation be updated to reflect the project's stance against index mutation in pre-commit hooks? Should examples or warnings be added, and should the current behavior (silent discard) be documented for users who ignore the policy?
- **Enforcement feasibility**: Is it technically possible to detect and reject index mutations in pre-commit hooks without breaking legitimate use cases (e.g., hooks that stage untracked files via `git add`)? Chris Torek’s explanation suggests enforcement may be impractical due to Git’s rollback machinery.
- **Backward compatibility**: If enforcement is implemented, how will existing hooks that rely on index mutation be handled? Will there be a deprecation period or immediate rejection?
- **Alternative workflows**: Are there recommended patterns for users who currently rely on pre-commit hooks to modify the index? Chris Torek proposed a wrapper script that stages changes before invoking `git commit`, with the hook acting purely as a validator.

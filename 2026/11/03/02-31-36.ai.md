This is the fourth patch in the v7 series adding path-related keys to `git repo info`, focusing on the `path.hooks.absolute` and `path.hooks.relative` keys. The email captures a design discussion between K Jayatheerth and Justin Tobler about how these keys should handle the `/dev/null` edge case when `core.hooksPath` is set to disable hooks.

The current implementation follows `git rev-parse --git-path hooks` precedent: when `core.hooksPath` is `/dev/null`, `path.hooks.absolute` returns `/dev/null` verbatim, while `path.hooks.relative` returns a relative path (e.g., `../../../../dev/null`). Justin argues this makes it harder for scripts to detect when hooks are disabled and proposes returning `/dev/null` verbatim for *both* keys, even when the relative path is requested. K Jayatheerth agrees this would improve usability and suggests special-casing `/dev/null` in the C code to avoid platform-specific inconsistencies (e.g., Windows path resolution issues). This change would also simplify the test helper, which currently has complex logic to handle absolute paths like `/dev/null` and skips the test on Windows.

The discussion also touches on test hygiene: Justin finds the updated `test_repo_info_path` helper unwieldy due to its special-case logic for absolute paths. K Jayatheerth plans to revert the helper to its simpler form and write the `/dev/null` test case manually, which would also resolve the Windows compatibility issue. The patch is otherwise mechanically clean, with thorough test coverage for standard hooks paths, custom overrides, and the `/dev/null` edge case. The open question is whether to prioritize consistency with `git rev-parse` (current behavior) or usability (returning `/dev/null` verbatim for both keys). This is a design decision, not a correctness issue, and the outcome will likely depend on maintainer preference. The patch is ready for review beyond this point.

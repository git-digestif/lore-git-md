This is a follow-up discussion in the ongoing bugfix thread about making `git rev-list --connectivity-check` ignore replacement objects. The patch itself is small, well-motivated, and already has Junio’s endorsement for the core idea, but the design question—whether to ignore replacements (current approach) or verify both original *and* replacement objects—remains open.

Patrick Steinhardt weighs in with a pragmatic perspective. He acknowledges Kristofer’s point that replacement objects are stored as regular refs (`refs/replace/OLD -> NEW`), so their reachable objects should already be covered by ordinary connectivity checks during fetch or push. However, he raises a subtle edge case: what if the replacement ref was written *locally* rather than fetched or pushed? In that scenario, the connectivity of the replacement object’s dependencies might not have been verified. Patrick ultimately concludes that this is not the connectivity check’s responsibility—it’s the user’s job to ensure locally written replacement refs are valid. He aligns with the current patch, treating the connectivity check as a tool for verifying *incoming* objects, not policing local state.

The discussion now hinges on whether the patch’s approach (ignoring replacements) is sufficient or if a stricter check (verifying both originals and replacements) is needed. Patrick’s input leans toward the current design, but the thread remains open to further input. The patch touches only `builtin/rev-list.c`, `tree-verify.c`, and the test suite (`t5413`), so iterating on the design would be straightforward if consensus shifts. No new code or test changes are proposed here—this is purely a design clarification. The documentation inconsistency Karthik Nayak noted (between `rev-list-options.adoc` and `git-replace.adoc`) is still unresolved.

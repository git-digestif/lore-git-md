This is a **bugfix and performance patch** addressing a regression in Git’s object quarantine mechanism. The patch, originally authored by Kristofer Karlsson, was merged to `seen` but may now be reconsidered in light of a design gap identified by Patrick Steinhardt.

The core issue is that Git’s quarantine mechanism unnecessarily loads all refs—including hidden ones—from the repository’s own object directory during connectivity checks. This happens because the quarantine environment passes the repository’s object directory as an alternate, causing `rev-list --alternate-refs` to list every ref twice. The original patch fixed this by marking alternates as "borrowed" (from another repository) or not, using heuristics like comparing paths to `<commondir>/objects` or the parent of `GIT_QUARANTINE_PATH`. This delivered measurable performance gains, especially in repositories with many hidden refs.

However, Patrick’s review reveals a flaw: the patch does not account for object directories specified via the `files://<payload>` object storage format extension, which can define a primary object directory that differs from `<commondir>/objects`. The current logic would incorrectly classify such directories as "borrowed," potentially omitting refs from `--alternate-refs` output. Kristofer acknowledges this gap and proposes a v3 that would make the check more flexible by storing the default object directory in the `odb_source_files` struct, allowing Patrick’s ongoing `odb-object-storage-extension` work to adjust the logic without further changes.

The discussion also explores a more ambitious alternative: instead of modifying the primary object directory to point to the quarantine, simply append the quarantine directory to the alternates list and use `GIT_QUARANTINE_ENVIRONMENT` as a read-only flag. This would eliminate the need to juggle alternates during connectivity checks, making the logic "just work." While cleaner, this approach is riskier and not a strict prerequisite for merging the current fix.

Kristofer is open to either path—sending a v3 with the improved check or dropping the fix entirely in favor of Patrick’s long-term solution, with tests marked as `test_expect_failure` to ensure coverage. The patch remains viable for `next`, but the choice now hinges on whether the project prefers a short-term fix or a more robust redesign. The performance regression is real and measurable, but the current solution’s assumptions may not hold in all cases.

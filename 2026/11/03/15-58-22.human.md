This is a brief follow-up in the ongoing `git describe` regression fix thread, where Linus Torvalds responds to Patrick Steinhardt’s proposal to make the `--exact` flag opt-out (correctness by default) rather than opt-in. Linus endorses the idea, calling it "sane," and notes that the opt-out mechanism (`--no-exact`) would accommodate edge cases like read-only repositories where users might still prefer the faster (but potentially incorrect) behavior. His reply is short but significant: it signals openness to Patrick’s counterproposal, shifting the default behavior of `git describe` toward correctness while preserving a performance escape hatch.

The thread is now converging on a design that combines three elements: the original fix (prioritizing commit generation numbers over dates), an opt-out `--exact` flag (with `--no-exact` as the escape hatch), and a warning when the commit graph is unavailable. No objections to this approach have been raised, and the maintainer (Junio) has already signaled intent to integrate the patch. The remaining open questions are implementation details—such as whether the warning should suggest running `git maintenance` or `git commit-graph write`, and whether the commit-graph write-back mechanism should be automatic or configurable.

This patch is part of a broader effort to address correctness issues in Git’s commit-graph machinery, particularly for commands like `git describe` that rely on generation numbers. The Linux kernel’s versioning workflow (which depends on `git describe`) serves as the motivating real-world use case. The fix itself is a one-line change in `builtin/describe.c`, but the thread has expanded to tackle systemic concerns about commit-graph freshness, performance trade-offs, and user communication. The patch looks well-motivated and uncontroversial, with the discussion now focused on refining the user experience rather than debating the core fix.

This is a bug report about `git diff --word-diff` producing confusing output. Jean Abou Samra demonstrates that when comparing two files (`file1.txt` and `file3.txt`) that differ by both a few word changes *and* the addition of a blank line, the word-level diff becomes nearly unreadable: it incorrectly marks large blocks of unchanged text as removed and re-added, while missing the actual word-level differences. The issue persists regardless of the `--diff-algorithm` setting.

The example is clear and reproducible: Jean provides three files (`file1.txt`, `file2.txt`, `file3.txt`) where `file2` differs from `file1` only by word changes, and `file3` differs from `file2` only by a blank line. The word diff between `file1` and `file2` works correctly, but the diff between `file1` and `file3` is garbled. The attached archive makes it easy for others to test locally.

This looks like a genuine bug in Git’s word-diff logic, likely triggered by the interaction between line-level and word-level diffing when whitespace changes are present. The report is well-structured, with minimal reproduction steps and no extraneous details. If confirmed, this would be worth fixing, as word diffs are a commonly used feature for reviewing prose or documentation changes.

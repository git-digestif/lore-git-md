This is a technical explanation and workflow suggestion in the ongoing discussion about pre-commit hooks and `git commit <pathspec>` behavior.

Chris Torek provides a detailed breakdown of Git's internal index handling during commits, explaining why pre-commit hooks cannot reliably modify the index. The core issue stems from Git's use of multiple temporary index files (including `.git/index.lock`) to support rollback if a commit fails, making it impossible for hooks to predict which file represents the "future" index. Torek confirms the project's policy stance: pre-commit hooks should only validate, not mutate, the index.

As a practical alternative, Torek suggests replacing direct `git commit` usage with a wrapper script that performs the desired `git add` operations before committing. This would let the pre-commit hook act as a validator while moving the mutation logic to a more appropriate place in the workflow. The suggestion directly addresses Kevin Lyles' real-world use case (a large repository where per-file operations are impractical) without requiring changes to Git's internals.

This is a bugfix patch that has just been queued for merging. Junio C Hamano accepted the third version of Elia Pinto’s patch to fix a data corruption bug in `git pack-objects` on platforms where `long` is 32 bits but `size_t` is 64 bits (such as 64-bit Windows). The issue occurs when handling blobs of 4 GiB or larger: the pack header records a truncated size while the compressed data remains full-length, corrupting the object during `git repack` or `git gc` when the original loose blob is pruned.

The patch changes the types of `size` (to `size_t`) and `datalen`/`olen` (to `off_t`) in the large-blob streaming path, ensuring accurate size tracking. The return types of `write_no_reuse_object` and `write_large_blob_data` are also updated to `off_t` to align with existing patterns in the codebase. These changes are minimal (7 lines) and narrowly scoped to the affected code path, with no impact on the on-disk format or other functionality.

All prior feedback from Simon Richter and Junio has been incorporated, including a commit message clarification to explicitly state the platform condition. The patch is well-motivated, uncontroversial, and appears ready for merging. No test is included, as reproducing the bug requires ≥4 GiB objects on affected platforms, but the edge cases and consequences are thoroughly documented. This fix resolves a clear correctness issue with no behavioral side effects.

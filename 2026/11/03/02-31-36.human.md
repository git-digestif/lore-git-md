This is the fourth patch in the v7 series adding path-related keys to `` `git repo info` ``, and the discussion here focuses on the new `path.hooks.absolute` and `path.hooks.relative` keys. The patch itself is mechanically sound and well-tested, but a **design question** remains about how to handle the `/dev/null` edge case when `core.hooksPath` is set to disable hooks.

The current implementation follows `git rev-parse --git-path hooks` precedent: when `core.hooksPath` is `/dev/null`, `path.hooks.absolute` returns `/dev/null` verbatim, while `path.hooks.relative` returns a relative path (e.g., `../../../../dev/null`). Justin Tobler argues this makes it harder for scripts to detect when hooks are disabled and suggests returning `/dev/null` verbatim for both keys, even when a relative path is requested. This would improve usability but deviate from `git rev-parse` behavior. K Jayatheerth agrees with Justin’s reasoning and proposes special-casing `/dev/null` in the C code to avoid passing it through `format_path()`, which would also resolve the Windows compatibility issue (where `/dev/null` is not a real filesystem path) and allow the test to run on all platforms.

The discussion also touches on **test hygiene**: Justin finds the updated `test_repo_info_path` helper unwieldy due to the special-case logic for absolute paths like `/dev/null`. K Jayatheerth agrees to revert the helper changes and write the `/dev/null` test manually, which will simplify the test suite and make the behavior clearer. The patch is otherwise ready for review, with the `/dev/null` handling being the only unresolved design decision. The outcome will likely depend on maintainer preference, but the proposed change (returning `/dev/null` verbatim for both keys) is a reasonable compromise between consistency and usability.

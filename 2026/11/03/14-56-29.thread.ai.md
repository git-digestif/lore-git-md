Subject: `git push --force-with-lease` silently ignored when pushing to a remote group
Series version: N/A (bug report, not a patch series)
Originating author: Patrick Peroša
Thread type: bug report

Core problem or goal
`git push --force-with-lease` (bare form) is silently ignored when pushing to a remote *group* (defined via `remotes.<group>`) unless an explicit `<refname>` is provided (e.g., `--force-with-lease=main`). The flag is dropped during the internal decomposition of the group push into individual remote pushes, causing the push to behave as if `--force-with-lease` was never specified. The older `--force` flag is forwarded correctly in all cases.

Current status
Under review. The issue is confirmed present on both Windows (Git for Windows) and Linux builds, across multiple integration branches (`master`, `next`), and is not affected by `--dry-run`. Tested up to `next` (2.56.0.506.g506a7eabc5). No patch or fix has been proposed yet.

Key technical details
- **Subsystems touched**: `git push` internals, remote group handling, argument forwarding logic.
- **Behavior**: Bare `--force-with-lease` is dropped when pushing to a remote group; explicit `--force-with-lease=<refname>` or `--force` works as expected.
- **Reproduction**: Minimal recipe provided (two bare repos grouped under `remotes.both`, local work repo, non-fast-forward situation).
- **Diagnosis**: `GIT_TRACE` output confirms the flag is not forwarded to child `git push` processes for individual remotes in the group.
- **Platforms affected**: Windows (Git for Windows) and Linux.
- **Branches affected**: `master`, `next`, and likely `seen` (not explicitly tested).

Open questions and loose ends
- Root cause: Why is the bare `--force-with-lease` flag dropped during group push decomposition while `--force-with-lease=<refname>` and `--force` are forwarded correctly?
- Fix scope: Is this a regression in the argument parsing logic, or was the behavior always broken?
- Backwards compatibility: Will fixing this break existing scripts or workflows that rely on the current (buggy) behavior?
- Test coverage: No existing test in the suite covers this edge case; a regression test will be needed.

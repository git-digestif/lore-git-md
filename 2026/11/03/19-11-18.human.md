This is a **bugfix patch** targeting the config subsystem, teaching Git to respect filesystem permissions when writing out-of-tree configuration files like `$HOME/.gitconfig`. Junio C Hamano’s v2 patch is now in its final polish phase after addressing earlier feedback from Patrick Steinhardt.

In this reply, Junio pushes back gently on two minor review points. First, he argues that the commit message’s rationale for excluding in-tree files (e.g., `.git/config`) is already self-evident: repository contents are meant to be mutable, and users shouldn’t be using `chmod` or `mv` to manage them in the first place. This sidesteps Patrick’s request for explicit documentation, but the reasoning is clear and aligns with the patch’s narrow scope. Second, Junio acknowledges that quoting the filename in the new `error_errno()` message would be more consistent but defers a broader cleanup of the function’s existing inconsistencies, citing the risk of test breakage. This is a pragmatic choice, though it leaves the coding-style nit unresolved.

The patch itself remains well-motivated and technically sound. It introduces a new `CONFIG_NO_WRITE` error code, checks file permissions with `access(2)` before writing, and includes thorough test coverage for read-only config files. The open questions from the RFC—race conditions, symlinks, and NFS edge cases—are still unaddressed, but Patrick’s feedback hasn’t reopened them. With no substantive objections left, this patch is likely to land in `next` soon, pending any further discussion on the error-message formatting.

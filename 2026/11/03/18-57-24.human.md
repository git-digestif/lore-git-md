This is the first patch in a v2 series improving Git’s HTTP transport resilience. It fixes two small but real bugs in the existing 429-rate-limit retry logic introduced in March 2026.

The first bug is an off-by-one in the retry counter: the loop condition used a pre-decrement (`--rate_limit_retries`), so setting `http.maxRetries=1` actually performed zero retries. The fix changes the condition to `http_max_retries > 0 && rate_limit_retries-- > 0` and moves the `http_max_retries <= 0` check after the loop, ensuring the configured number of retries is honored and avoiding a negative-wrap edge case when re-authentication is involved.

The second bug is a race in Retry-After header parsing: `CURLINFO_RETRY_AFTER` was queried *after* `handle_curl_result()` had already logged the still-uninitialized value (`-1`) to Trace2. The fix moves the extraction into `finish_active_slot()`, where it belongs, so both the logging and the retry logic see the correct value.

The patch also updates the test helper (`t/lib-httpd/http-429.sh`) to support configurable failure counts (1, 2, or 3 consecutive 429s) and adds three new tests in `t/t5584-http-429-retry.sh` that verify the retry count, failure threshold, and Trace2 logging. The changes are narrow, well-explained, and directly address Junio’s feedback from v1. This looks like a solid, uncontroversial fix that should be ready for `next`.

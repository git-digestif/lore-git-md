This is a substantive follow-up in the `git describe` regression fix thread, advancing the discussion on how to handle the trade-off between correctness and performance when commit graphs are stale or missing. Patrick Steinhardt responds to Linus Torvalds' proposal for a `--exact` flag by raising a philosophical concern: intermittent incorrectness (due to timing-dependent commit graph availability) may be more confusing for users than consistent incorrectness. He suggests flipping the default to `--exact` (opt-out rather than opt-in) and emitting a warning when the commit graph is unavailable, making the behavior both correct *and* discoverable.

The email introduces a new design axis: whether the proposed `--exact` flag should be opt-in (Linus's proposal) or opt-out (Patrick's counterproposal). Patrick's argument centers on user experience -- users are unlikely to know `git describe` can produce incorrect results by default, so making correctness opt-in risks perpetuating the bug. His alternative would make the command correct by default while still allowing users to opt out of the performance cost via `--no-exact`. The warning mechanism he proposes would alert users to the fallback behavior, addressing the discoverability issue.

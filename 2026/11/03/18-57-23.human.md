This is a **v2 patch series** improving Git’s HTTP transport resilience by addressing four gaps in error handling: an off-by-one retry counter, missing exponential backoff, lack of configurable retry status codes, and missing retries for HTTP POST requests. The series targets `http.c` and `remote-curl.c`, with new config options (`http.retryStatusCodes`) and expanded test coverage.

The author has addressed **Junio’s feedback** from v1, clarifying commit messages, restoring explanatory text for HTTP 429 in documentation, and adjusting implementation details (e.g., moving the 400–599 range check in `is_retryable_http_code()`). The exponential backoff logic now uses `http_max_retries - rate_limit_retries` as the attempt counter, and the documentation for `http.retryAfter` and `http.maxRetryTime` has been unified to clarify their interaction. Patch 4/4 (POST retries) remains unchanged, as it received no substantive feedback.

The series is **well-motivated** and **technically sound**, with thorough test coverage (15 new tests in `t/t5584-http-429-retry.sh`) and clear documentation updates. The default behavior remains conservative (only 429 retries by default), but environments can opt into retrying 5xx errors via `http.retryStatusCodes`. The only open question is whether the default set of retryable codes should include 5xx, but the series sidesteps controversy by making this configurable.

This is a **bugfix/feature hybrid** that should be uncontroversial for users operating at scale. The changes are incremental and backward-compatible, and the author has responded thoughtfully to review feedback. Worth watching for further discussion on the default retry codes, but the series looks ready for `next` once the remaining documentation tweaks are addressed.

This is a feature patch for `git range-diff`, adding a `--matched-only` option that filters the output to show only commits present in both input ranges. The patch is part of a small, self-contained series (v3) that has been ready for merging for over six weeks but remains stalled in `seen` due to lack of review rather than any technical issues. Junio has signaled he will drop it soon unless a reviewer steps in.

Harald’s reply to Ben Knoble’s review clarifies the motivation with a concrete example: when rebasing a branch with many upstream changes, `git range-diff` currently floods the output with hundreds of unrelated commits, forcing the user to scroll past them to see what actually changed in the surviving commits. The `--matched-only` flag eliminates this noise, letting users focus on the commits that matter. This workflow pain is real and common enough that the feature feels well-justified, even if the initial commit message could have included the example up front.

The implementation is straightforward and low-risk. It reuses existing suppression logic by internally setting both `--left-only` and `--right-only` when `--matched-only` is given, avoiding new code paths. The only new behavior is mutual exclusion: the three filtering options (`--left-only`, `--right-only`, `--matched-only`) cannot be combined, enforced by a simple arithmetic check in the library layer. Tests cover the new option, mutual exclusion, and output formatting (numbered gaps for omitted commits). No on-disk format changes or new symbols are introduced.

The patch touches only four files: the CLI front-end (`builtin/range-diff.c`), the core logic (`range-diff.c` and `range-diff.h`), and documentation. Junio’s earlier architectural concerns about error-handling layering were resolved in v3 by reverting to `error()` in the library and delegating `die()` to the CLI. No open technical objections remain.

If you’ve ever rebased a long-lived branch and struggled to find your changes in a sea of upstream commits, this patch is worth your attention. It’s a small but meaningful quality-of-life improvement that doesn’t disrupt existing workflows.

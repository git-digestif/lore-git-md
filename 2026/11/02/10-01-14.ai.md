This is a substantive review of a refactoring patch targeting `git diff-files`. Junio C Hamano raises two technical concerns about the sixth iteration of Edson’s patch, which converts the command’s option parsing to the `parse-options` API.

The first issue is a regression in help output: the patch drops `COMMON_DIFF_OPTIONS_HELP` from the usage message, so standard diff options like `-p`, `--stat`, and `-z` (handled by `setup_revisions()`) will no longer appear in `git diff-files -h`. Junio suggests this could be mitigated by embedding the macro in an `OPT_GROUP()` entry, but questions whether the effort is justified for a plumbing command where tab-completion and abbreviated options are less critical.

The second concern is whether the refactoring itself is worthwhile. Junio notes that the existing `strcmp()`-based parsing loop is clear and functional, and expresses skepticism about the value of replacing it with `parse-options` boilerplate for a low-level command. He does not outright reject the patch, but the tone suggests the burden of proof lies with the author to demonstrate tangible benefits beyond consistency.

No tested review or alternative implementation is offered; the feedback is purely design-level. The patch remains under review, with the threading issues resolved but these new technical questions now open. Future discussion will likely focus on whether the help-text regression is acceptable and whether the refactoring’s maintenance benefits outweigh its costs for a plumbing command.

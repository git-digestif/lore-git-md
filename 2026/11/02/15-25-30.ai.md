This is the **core API patch** in Christian Couder’s `parse-options` early-scanning series, now at **v4**. The email is a reply to Kaartic Sivaraam’s substantive review of v3, confirming that both of Kaartic’s technical suggestions have been adopted.

The patch introduces `early_scan_options()`, a minimal, reusable sub-API for scanning command-line arguments *before* full `parse_options()` processing. The goal is to replace fragile hand-rolled early scans in Git commands, fixing a real bug in `git fast-import` (where `--allow-unsafe-features` was silently ignored when preceded by `--depth 5`). The API reuses `parse-options` internals (`lookup_long_opt()`) to handle negated options, unambiguous abbreviations, and aliases consistently with `parse_options()`. It is designed to err on the side of caution—stopping at short options, unknown options, ambiguous abbreviations, and low-level callbacks—to avoid misinterpreting option values.

In this reply, Christian confirms two key improvements to the v3 implementation:
1. **Validation checks inside `early_scan_options()`**: The function now calls `parse_options_check()` internally, ensuring that invalid uses of `PARSE_OPT_EARLY` (e.g., short options, `OPTION_SUBCOMMAND`) are caught even if `early_scan_options()` is called before `parse_options_start()`. This addresses Kaartic’s concern about silent misbehavior or crashes in edge cases.
2. **API documentation clarification**: The docstring now explicitly warns callers that the `option` pointer passed to the callback is ephemeral and must not be retained after the scan completes. This prevents use-after-free bugs if a caller caches the pointer.

These changes are small but meaningful: they close real correctness risks without altering the core design. The rest of the patch remains uncontroversial and well-reviewed.

This is the sixth patch in the v7 series adding path-related keys to `git repo info`. Justin Tobler’s reply is a **surface-level review** with a **substantive design question**: whether `path.grafts` should be included at all, given that grafts are a deprecated feature slated for removal.

The patch itself is mechanically sound and follows the established pattern for path keys in this series. It introduces `path.grafts.absolute` and `path.grafts.relative` to expose the repository’s grafts file location, using `repo_get_graft_file(repo)` and the existing `format_path()` helper. The implementation is consistent with the other path keys (e.g., `path.index`, `path.hooks`) and aligns with `git rev-parse --git-path` precedent. Justin’s nit about the redundant null check is valid—`repo_get_graft_file(repo)` already invokes `BUG()` if the path cannot be determined—but this does not affect correctness.

The substantive question Justin raises is whether the patch is worth merging at all. Grafts are explicitly deprecated and listed for removal in `Documentation/BreakingChanges.adoc`, which means `path.grafts` would have a short lifespan. The author may argue that the key provides symmetry with other path keys and could be useful for scripts that still rely on grafts, but Justin’s skepticism is reasonable: adding a feature for a deprecated mechanism risks cluttering the interface with something that will soon be removed. This is now a **design decision** for the maintainer or the author to resolve.

The patch is otherwise ready for review, but its fate hinges on whether the project wants to expose a deprecated feature in a new interface. If the series progresses, this patch is likely to be dropped unless the author can justify its inclusion beyond consistency with other path keys.

This is the first patch in Jasper Mayone’s four-patch series (v4) that tightens safety around `git worktree remove`. It directly addresses a long-standing bug: Git currently allows deletion of worktrees that are in the middle of a rebase, `git am`, bisect, cherry-pick, or revert—even when the files appear clean—because the operation’s state lives in the worktree’s own `$GIT_DIR` and is lost when the worktree is removed. The patch makes `git worktree remove` refuse to delete such worktrees unless `--force` is given, aligning with Git’s general principle of protecting uncommitted or in-progress work.

The implementation adds a new helper function, `check_no_operation_in_progress()`, which uses `wt_status_check_rebase()`, `wt_status_check_bisect()`, and direct checks for `CHERRY_PICK_HEAD`, `REVERT_HEAD`, and the `sequencer` directory to detect in-progress operations. The helper is called as part of the existing clean-worktree check, so it only runs when the worktree directory exists. The documentation for `git worktree remove` is updated to list the conditions requiring `--force` in a clear bulleted format, and the tests cover all five operations (rebase, `git am`, bisect, cherry-pick, and revert) in both single-commit and multi-commit scenarios, including edge cases like a rebase stopped at an "edit" line or a cherry-pick whose conflict was resolved to the current contents.

This is a **bugfix** that closes a real safety hole made more urgent by the follow-up patch extending `%(worktreepath)` to report rebasing/bisecting worktrees. The implementation is clean, well-tested, and addresses the edge case Phillip Wood identified (checking for `CHERRY_PICK_HEAD` and `REVERT_HEAD` when a single-commit cherry-pick or revert has completed without conflicts). The patch is ready for integration and looks like a clear improvement. Key files touched: `builtin/worktree.c`, `Documentation/git-worktree.adoc`, and `t/t2403-worktree-move.sh`.

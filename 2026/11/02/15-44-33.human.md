This is an **Outreachy microproject discussion** about environment variable handling in Git worktrees, specifically whether regression tests for `GIT_DIR` inheritance in shell aliases would be a suitable contribution.

A contributor (Immaculate Mecha) proposes writing regression tests for a known edge case: when a shell alias runs a Git command (e.g., `git -C ../other-repo rev-parse`) from inside a **linked worktree**, the nested command inherits the parent worktree’s `GIT_DIR` environment variable, causing it to report the wrong repository’s directories. The issue is reproducible and confirmed by another participant (Cynthia, using the handle "Priestess"), who notes that unsetting `GIT_DIR` before the nested command fixes the problem. Cynthia also points out that the behavior is likely intentional, as `handle_alias()` in `git.c` explicitly expects `GIT_DIR` and related variables to be set, making this more of a design question than a straightforward bug.

The discussion raises a key concern: if the current behavior is intentional, writing regression tests to lock it in could become problematic if the design changes later. Cynthia suggests that a smaller, less ambiguous microproject might be a safer choice given the tight Outreachy contribution deadline, while still leaving room to revisit this issue afterward. The email adds Outreachy mentors to the thread to weigh in on whether this proposal fits the microproject criteria.

This thread is exploratory and does not include a patch or test implementation. The focus is on whether the scope and intent of the proposed work align with Outreachy’s goals for small, well-defined contributions. The outcome will likely depend on mentor feedback about the suitability of the project and the risks of documenting behavior that may not be stable.

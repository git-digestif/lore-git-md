This is the **final patch in a now-ready-for-`next` series** that introduces `early_scan_options()`, a new `parse-options` sub-API for safely scanning command-line arguments early. This patch converts `git fast-import` to use the new API, fixing a real bug where `--allow-unsafe-features` was silently ignored when preceded by an option with a separate value (e.g., `--depth 5 --allow-unsafe-features`).

The patch removes the outdated NEEDSWORK comment and documentation note about having to spell `--allow-unsafe-features` in full, as the new API now handles abbreviations and stuck/separate values consistently with `parse_options()`. It also adds three new tests in `t/t9300-fast-import.sh` to verify that the bug is fixed, that abbreviations work as expected, and that unsafe features are correctly refused when `--allow-unsafe-features` follows a non-option argument.

The conversion is straightforward: `cmd_fast_import()` now calls `early_scan_options()` with `EARLY_SCAN_STOP_AT_NON_OPTION` (to match `parse_options()` behavior) and a callback that sets `state.allow_unsafe_features`. The callback is careful to check the option’s long name to avoid false positives from other options. The patch is well-tested, documented, and uncontroversial; it directly addresses the bug and aligns `git fast-import`’s argument parsing with the rest of Git.

Key technical details:
- Files touched: `builtin/fast-import.c`, `Documentation/git-fast-import.adoc`, `t/t9300-fast-import.sh`.
- New test coverage: `--depth 5 --allow-unsafe-features` is now recognized, ambiguous abbreviations are rejected, and unsafe features are refused when `--allow-unsafe-features` follows a non-option.
- Behavior changes: `--allow-unsafe-features` now works when preceded by an option with a separate value, and abbreviations (e.g., `--allow-unsafe`) are accepted unless `GIT_TEST_DISALLOW_ABBREVIATED_OPTIONS` is set.
- The patch removes a NEEDSWORK comment and outdated documentation, reflecting the API’s improved consistency with `parse_options()`.

This is a follow-up in the ongoing `git describe` regression fix thread, specifically Linus Torvalds' reply to Patrick Steinhardt's concern about the fix's dependency on commit graph freshness. The email clarifies the Linux kernel's versioning workflow and responds to the edge case Patrick raised: that `git describe` results may now vary depending on whether a recent commit graph is available, potentially confusing users.

Linus acknowledges the inconsistency but argues it is no more puzzling than the existing buggy behavior. He suggests a pragmatic trade-off: the fix is correct when a commit graph exists (the common case for large repositories), and the fallback to incorrect behavior is preferable to the performance cost of calling `ensure_generations_valid()` unconditionally. To address Patrick's concern, he proposes adding a `--exact` flag to `git describe` that would force a full commit graph walk (via `ensure_generations_valid()`) to guarantee accurate results, even if slow. This would give users a way to opt into correctness when needed, while preserving the default behavior's performance.

The email touches on two key technical details: the Linux kernel's custom versioning script (which predates `git describe` and uses `git rev-list --count` for historical reasons) and the proposed `--exact` flag as a mitigation for the commit graph dependency. The tone is pragmatic, prioritizing real-world usability over theoretical edge cases. This is a substantive contribution that advances the thread by proposing a concrete user-facing solution to the correctness/performance trade-off, though it leaves open questions about implementation (e.g., whether `--exact` should be the default for certain commands or repositories). The proposal aligns with the thread's broader shift toward amortizing commit-graph costs via write-back, but frames it as an opt-in feature rather than an automatic behavior.

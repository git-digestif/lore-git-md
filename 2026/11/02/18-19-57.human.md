This is a documentation and terminology cleanup series, now in its second version. The thread is a short, clarifying question from Julia Evans about the practical difference between "root refs" (like `ORIG_HEAD`) and "pseudorefs" (like `MERGE_HEAD`), given that both appear as files in `.git/`.

Julia’s question is straightforward: she observes that `ORIG_HEAD` and `MERGE_HEAD` both show up as files in `.git/` during a merge conflict, so why is one called a "root ref" and the other a "pseudoref"? The distinction isn’t obvious from the on-disk appearance, and the glossary updates in the series don’t yet address this user-facing confusion. Her note is not a review objection—she’s asking for the rationale behind the terminology split, which could help refine the documentation further.

The series itself remains uncontroversial and well-motivated. It updates 22 files across glossary, man pages, code comments, and tests to align with the 2024 commit that redefined "pseudoref" to mean only `FETCH_HEAD` and `MERGE_HEAD`, while introducing "root ref" for refs like `HEAD` and `ORIG_HEAD`. v2 incorporates all prior review feedback from Junio and Patrick, including Julia’s own proposal to expand `gitdatamodel.adoc` with dedicated sections for both concepts. The only unresolved items are two minor documentation nits in `git-update-ref(1)` that Andy considers out of scope.

If the series lands as-is, Julia’s question suggests the glossary or `gitdatamodel.adoc` might benefit from a brief note explaining the operational difference—perhaps that root refs can be written by `git update-ref` and have reflogs, while pseudorefs cannot. This isn’t a blocker, but it’s a useful pointer for future iterations.

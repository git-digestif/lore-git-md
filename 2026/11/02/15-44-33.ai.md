This is an **Outreachy microproject discussion** about environment variable handling in Git worktrees, specifically whether writing regression tests for `GIT_DIR` inheritance in shell aliases would be a suitable contribution.

Priestess (Cynthia) replies to Immaculate Mecha’s proposal, confirming the reported behavior on Git 2.56.GIT. She reproduces the issue: when a shell alias runs `git -C <unrelated-repo> rev-parse` from inside a linked worktree, the nested command incorrectly reports the parent worktree’s `GIT_DIR` and `GIT_COMMON_DIR`, while `--show-toplevel` correctly identifies the target repository. Unsetting `GIT_DIR` fixes the issue, confirming it as the root cause. She notes that the problem is more pronounced when the target repository is unrelated to the worktree, as `--git-common-dir` appears correct when the target is the main repository.

Priestess points out that `handle_alias()` in `git.c` explicitly exports `GIT_DIR` and related variables to aliases, suggesting this behavior is intentional. This shifts the question from a simple test-writing task to a design discussion: whether the current behavior is correct or should be changed. She cautions that a regression test locking in the current behavior might not age well if the design is later revisited. While she is not an Outreachy mentor, she suggests that given the tight contribution deadline, a smaller microproject might be more practical, and Immaculate could raise this issue again afterward.

The email adds Outreachy mentors (Christian Couder, Kaartic Sivaraam, Siddharth Asthana, and Usman Akinyemi) to the thread for their input on whether this is a suitable microproject. The key technical details remain the same as in the parent email: the issue affects worktree handling and environment variable propagation, with potential test files in `t/` and possible code changes in `setup.c` or `environment.c`. No new symbols or on-disk format changes are involved. The thread is still exploratory, with no patches or test scripts submitted yet.

This is the second patch in a two-patch series improving `git maintenance` lock handling. It addresses the inconsistency between `--auto` and manual invocations when the maintenance lock cannot be acquired, while also adding Trace2 observability for diagnostic purposes.

The patch modifies `builtin/gc.c` to emit a Trace2 data event (`"lock/skip"`) whenever `git maintenance run --auto` skips due to lock acquisition failure, including the specific error code (e.g., `EEXIST`, `EPERM`). This replaces the previous silent skip with structured logging, making it easier to diagnose why automatic maintenance isn't running in production environments. For manual invocations (`git maintenance run` without `--auto`), the patch aligns behavior with `git gc` by failing with exit code 128 and an error message when the lock is held, rather than silently succeeding. The `--quiet` flag is respected in both cases.

The implementation is clean: it captures `errno` early, uses `unable_to_lock_message()` for consistent error formatting, and preserves the existing design where stale locks require manual inspection (the lock file is not removed on failure). The test coverage in `t/t7900-maintenance.sh` verifies both the Trace2 event emission (including error code) and the new exit-code behavior for manual invocations, with separate cases for `--quiet` suppression.

This patch fully resolves the latent inconsistency flagged by Patrick Steinhardt in the v1 review, expanding the scope from a pure observability fix to a behavioral alignment. The changes are narrowly scoped to lock-handling logic and do not affect on-disk formats or other subsystems. The series remains uncontroversial, with no objections or alternative proposals raised during review. Key technical details for follow-up discussion include the new Trace2 event format (`"lock/skip": {"reason": "exists", "errno": <code>}`), the exit code change for manual invocations, and the test cases covering both `--auto` and manual modes.

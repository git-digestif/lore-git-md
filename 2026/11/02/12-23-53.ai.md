This is a **follow-up to a Trace2 diagnostic patch** for `git maintenance`, now expanding its scope to address the lock-handling inconsistency Patrick Steinhardt flagged in review. The patch is no longer standalone; it is now part of a two-patch series (v2) that adds both the Trace2 event and a behavioral change: manual invocations of `git maintenance run` now fail fast when the lock cannot be acquired, aligning with `git gc` and user expectations.

The new version keeps the original Trace2 event (`"lock/skip": "exists"`) but extends it to include the actual error code (e.g., `EPERM`, `EACCES`) rather than just `EEXIST`. The test in `t/t7900-maintenance.sh` is updated to verify both the event emission and the new exit-code behavior. The lock file itself is still not removed on failure, preserving the existing design that stale locks should be manually inspected.

This change looks well-motivated and uncontroversial. The commit message now clearly states the inconsistency being fixed, and the test coverage is thorough. No objections or alternative proposals have surfaced yet, so this is likely to be the final shape of the series unless someone spots an edge case in the error-handling path.

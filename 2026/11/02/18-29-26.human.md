This is a **worktree safety and usability feature**, now expanded to four patches after incorporating substantive review feedback. The series addresses two long-standing inconsistencies in Git’s worktree handling: (1) `git worktree remove` currently allows deletion of worktrees in the middle of a rebase, bisect, or other operation, risking data loss; and (2) `git for-each-ref`'s `%(worktreepath)` atom does not report the worktree path for branches being rebased or bisected, even though other Git commands already treat those branches as "checked out."

The first patch (already merged) makes `git worktree remove` refuse to delete a worktree that is in the middle of a rebase, `git am`, bisect, cherry-pick, or revert unless `--force` is given. This aligns with Git’s general principle of protecting uncommitted or in-progress work. The updated version now also checks for `CHERRY_PICK_HEAD` and `REVERT_HEAD` when a single-commit cherry-pick or revert has completed without conflicts, closing an edge case Phillip Wood identified. The documentation has been reworded for clarity, using a bulleted list to enumerate the conditions requiring `--force`.

The second patch is new and adds documentation warnings to `git-for-each-ref.adoc` about parsing `%(worktreepath)` safely. It notes that worktree paths can contain newlines and recommends using quoting options (e.g., `--shell`) or NUL-terminated output (`%00`) to avoid ambiguity. It also clarifies that only one worktree is shown for a branch checked out in multiple worktrees.

The third patch extends `%(worktreepath)` to report the worktree path for branches being rebased or bisected, eliminating the need for a new CLI option and aligning behavior across Git commands. The implementation now uses a shared helper, `branch_checked_out_worktree()`, from `branch.c` instead of duplicating logic in `ref-filter.c`. This avoids code duplication and ensures consistency with `branch.c`'s logic. The patch also stops printing the `git_dir` of bare worktrees in `%(worktreepath)`, documenting this as a breaking change. Tests verify the new behavior, including edge cases like rebasing, bisecting, and bare repositories.

The fourth patch is also new and removes the redundant `+` marker in `git branch` output for worktrees rebasing or bisecting a branch. Since the `(no branch, ...)` line already names the branch, the `+` marker is unnecessary and potentially confusing. The documentation has been updated to reflect this change.

The series is well-motivated and addresses real usability and safety issues. The implementation is clean, with thorough test coverage and clear documentation. The backward-incompatible changes (empty `%(worktreepath)` for rebasing/bisecting branches, the `+` marker removal, and the bare-worktree behavior) are explicitly documented and justified. The series looks ready for review and is likely to be uncontroversial, though the broader limitations of `for-each-ref` as a filtering mechanism (e.g., lack of NUL-terminated output, inability to distinguish main/linked worktrees) remain open questions for future work.

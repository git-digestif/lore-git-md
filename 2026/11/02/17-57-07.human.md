This is a **bugfix patch** targeting the worktree subsystem, specifically tightening safety checks in `git worktree remove`. The patch is the first of two in Jasper Mayone’s v4 series, which aims to prevent accidental deletion of worktrees in the middle of operations like rebase, bisect, cherry-pick, revert, or `git am`.

The patch already addresses the core issue: `git worktree remove` now refuses to delete a worktree if it detects an in-progress operation, requiring `--force` to override. In this reply, Jasper incorporates Phillip Wood’s **substantive feedback** about a previously missed edge case: single-commit cherry-picks or reverts that complete without conflicts still leave `CHERRY_PICK_HEAD` or `REVERT_HEAD` files behind, meaning the operation is technically in progress. The v4 update will check for these files, closing the gap. This is a meaningful safety improvement, though the risk of data loss is lower than for multi-commit operations.

Jasper also accepts Phillip’s **editorial suggestions**: rewriting the documentation to use a bulleted list for clarity, fixing awkward phrasing, and reorganizing tests to use subshells and a shared conflict-setup helper. These changes improve readability but do not alter the patch’s behavior.

The patch remains well-motivated and uncontroversial. It aligns with Git’s general principle of protecting uncommitted or in-progress work, and the additional checks for `CHERRY_PICK_HEAD`/`REVERT_HEAD` make the safety net more complete. The only remaining question is whether scripts exist that rely on the old behavior (deleting in-progress worktrees without `--force`), but the commit message already flags this as a backward-incompatible change and invites feedback. For now, this looks like a clear improvement.

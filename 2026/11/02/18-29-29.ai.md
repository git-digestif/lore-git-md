This is the third patch in Jasper Mayone’s four-patch series (v4) extending Git’s `%(worktreepath)` atom to report the worktree path for branches being rebased or bisected. The patch directly addresses the gap Kristoffer Haugsbakk identified: `git for-each-ref --format='%(worktreepath)'` previously returned an empty string for such branches, even though Git already treats them as "checked out" in other contexts (e.g., `git worktree add` and `git branch -d` refuse to operate on them).

The implementation avoids code duplication by exposing a new helper, `branch_checked_out_worktree(const char *refname)`, in `branch.c`. This helper reuses the existing `prepare_checked_out_branches()` infrastructure to map branches to their worktrees, explicitly excluding branches that `rebase --update-refs` will move but are not currently checked out. The patch replaces the old `ref-filter.c` logic (which only looked at `HEAD` refs) with a call to this helper, simplifying the codebase by removing ~50 lines of now-unused worktree-mapping machinery. Tests verify the new behavior for rebasing, bisecting, interactive rebase with an edit stop, `rebase --update-refs`, and bare repositories.

The patch also introduces a **breaking change**: `%(worktreepath)` no longer returns the `git_dir` of bare repositories, aligning the atom’s behavior with its name and purpose. This change is documented in both `git-for-each-ref(1)` and `git-branch(1)`, and the commit message explicitly asks whether any scripts rely on the old behavior. The implementation is clean, well-tested, and directly addresses the design tension between `ref-filter`’s filtering capabilities and the need for accurate worktree tracking. Key files touched are `ref-filter.c`, `branch.c`, and their respective documentation and test files.

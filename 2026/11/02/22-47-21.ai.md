This is the sixth patch in the v7 `git repo info` path-keys series, introducing `path.grafts.absolute` and `path.grafts.relative`. Justin Tobler’s review is **surface-level** and raises two points: a mechanical nit about redundant error handling (since `repo_get_graft_file()` already BUGs on NULL) and a **substantive design question** about whether the patch should exist at all, given that graft files are deprecated and slated for removal in `Documentation/BreakingChanges.adoc`.

The mechanical nit is straightforward: the `if (!graft_file)` checks in both `get_path_grafts_absolute()` and `get_path_grafts_relative()` are dead code and can be removed. This is a minor cleanup that does not affect functionality.

The design question is more significant. Justin questions the value of exposing the grafts file path through `git repo info` when grafts are on the deprecation path. The patch itself is technically sound and follows the established pattern for other path keys (e.g., `path.index`), but its long-term utility is questionable. The series’ broader goal—exposing repository component paths in a scriptable format—may not justify maintaining an interface for a deprecated feature. This is a **judgment call** that likely depends on whether the project wants to provide a complete set of path keys for all repository components (regardless of deprecation status) or omit those that are being phased out.

The patch is otherwise ready for review: it is well-tested, aligns with `git rev-parse --git-path` precedent, and integrates cleanly with the rest of the series. The open question is whether the grafts keys are worth including at all. If the series progresses, this patch may be dropped or kept based on maintainer preference. No other technical issues are raised.

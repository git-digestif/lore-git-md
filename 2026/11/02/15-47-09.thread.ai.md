Thread identity
Subject: rev-list: ignore replacements during connectivity check
Series version: standalone patch (no version marker)
Originating author: Kristofer Karlsson
Thread type: bugfix

Core problem or goal
The connectivity check in `git rev-list` (used by `fetch`, `receive-pack`, and `index-pack`) currently follows replacement refs, while other commands (`fsck`, `prune`, `pack-objects`, `upload-pack`) ignore them. This inconsistency can cause a pack to pass the connectivity check (because replacements are visible) but later fail `fsck` (because replacements are ignored and the original objects are missing). The goal is to align `rev-list`'s connectivity check with the established behavior of the other commands by ignoring replacement objects.

Current status
Under review; no prior versions. The patch adds a `--connectivity-check` flag to `git rev-list` that ignores replacement refs, modifies `tree-verify.c` to drop the `OBJECT_INFO_LOOKUP_REPLACE` flag, and updates test `t5413` to expect rejection when replacements mask missing objects. Junio C Hamano has endorsed the core idea ("absolutely the right thing to do") but raised a conceptual question: whether the connectivity check should instead ensure *both* original *and* replacement objects exist, treating replacements as additional tips in the connectivity graph. Kristofer Karlsson has responded, noting that replacement objects are stored as regular refs (`refs/replace/OLD -> NEW`), so their reachable objects should already be covered by ordinary connectivity checks during fetch or push. Karthik Nayak has now pointed out a documentation inconsistency: the patch updates `Documentation/rev-list-options.adoc` to note that `--connectivity-check` ignores replacements, but `Documentation/git-replace.adoc` still claims that *all* commands except reachability traversals (prune, pack transfer, fsck) use replacements by default. The documentation should be updated to include `rev-list --connectivity-check` as an exception.

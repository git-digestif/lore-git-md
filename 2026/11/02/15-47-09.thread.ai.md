Thread identity
Subject: rev-list: ignore replacements during connectivity check
Series version: standalone patch (no version marker)
Originating author: Kristofer Karlsson
Thread type: bugfix

Core problem or goal
The connectivity check in `git rev-list` (used by `fetch`, `receive-pack`, and `index-pack`) currently follows replacement refs, while other commands (`fsck`, `prune`, `pack-objects`, `upload-pack`) ignore them. This inconsistency can cause a pack to pass the connectivity check (because replacements are visible) but later fail `fsck` (because replacements are ignored and the original objects are missing). The goal is to align `git rev-list`'s connectivity check with the established behavior of the other commands by ignoring replacement objects.

Current status
Under review; no prior versions. The patch adds a `--connectivity-check` flag to `git rev-list` that ignores replacement refs, modifies `tree-verify.c` to drop the `OBJECT_INFO_LOOKUP_REPLACE` flag, and updates test `t5413` to expect rejection when replacements mask missing objects. The core design question—whether the connectivity check should ignore replacements (current patch) or verify both original *and* replacement objects—has converged on ignoring replacements. Junio C Hamano endorsed the core idea ("absolutely the right thing to do") but initially raised the alternative; Patrick Steinhardt's reviews reinforce the current patch's design, noting that the connectivity check's scope is limited to validating transferred objects, not policing locally created refs. The patch now faces two technical concerns: (1) the test change in `t5413` was intentionally written to accommodate a real-world edge case (accepting a commit with a missing original tree if a replacement exists), meaning the new behavior could break existing workflows, and (2) the removal of `OBJECT_INFO_LOOKUP_REPLACE` from `tree-verify.c` is confirmed to be scoped correctly, as the global replacement mechanism is already disabled when this code path runs, and `tree-verify.c` is only used by `rev-list --connectivity-check=incremental`.

Key technical details
- Files: `builtin/rev-list.c` (new `--connectivity-check` flag), `tree-verify.c` (drops `OBJECT_INFO_LOOKUP_REPLACE`), `t/t5413-rev-list-connectivity.sh` (updated test coverage), `Documentation/rev-list-options.adoc` (updated), `Documentation/git-replace.adoc` (needs update)
- New behavior: `git rev-list --connectivity-check` ignores replacement refs
- Old behavior: followed replacement refs, potentially masking missing objects
- On-disk format: unchanged
- Test coverage: `t5413` verifies the new behavior rejects packs where replacements mask missing objects
- Side effects: removal of `OBJECT_INFO_LOOKUP_REPLACE` in `tree-verify.c` is confirmed to affect only `rev-list --connectivity-check=incremental`; a separate, unrelated bug in `mktree` (follows replacements when checking object existence but writes the original OID into the tree) is noted but not addressed in this patch

Open questions and loose ends
- Documentation inconsistency: `git-replace.adoc` still claims that *all* commands except reachability traversals (prune, pack transfer, fsck) use replacements by default, but `rev-list --connectivity-check` now ignores them. This needs updating to reflect the new exception.
- Workflow impact: the test change in `t5413` was intentional, meaning the new behavior (rejecting packs where replacements mask missing objects) could break existing workflows that rely on this edge case.
- Unrelated bug: `mktree` follows replacements when checking object existence but writes the original OID into the tree, which could allow missing objects to pass validation. This is flagged as a potential bug but not addressed in this patch.

Participant positions
- Kristofer Karlsson (author): proposes ignoring replacements for consistency with other commands (`fsck`, `prune`, etc.), citing established behavior since 2009. Argues that replacement objects are stored as regular refs, so their reachable objects are already covered by ordinary connectivity checks during fetch or push. Confirms the test change in `t5413` was intentional and that the removal of `OBJECT_INFO_LOOKUP_REPLACE` from `tree-verify.c` is correctly scoped. Notes the unrelated `mktree` bug but does not address it in this patch.
- Junio C Hamano (maintainer): endorses the core idea ("absolutely the right thing to do") but initially suggested an alternative approach (checking both originals and replacements). The question is now effectively resolved in favor of the original patch.
- Patrick Steinhardt: two substantive reviews reinforcing the current patch's design but raising technical concerns: (1) potential breakage of existing workflows due to the `t5413` test change, and (2) unintended side effects of removing `OBJECT_INFO_LOOKUP_REPLACE` from `tree-verify.c`. The first concern is now clarified as intentional (the test change was meant to accommodate a real-world edge case), and the second is addressed by Kristofer's confirmation that the change is scoped correctly.
- Karthik Nayak: surface-level review noting the documentation inconsistency between `rev-list-options.adoc` and `git-replace.adoc`. No technical objections.

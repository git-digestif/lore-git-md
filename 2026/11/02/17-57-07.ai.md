This is a **bugfix patch** addressing a safety issue in `git worktree remove`. The patch makes the command refuse to delete a worktree that is in the middle of a rebase, `git am`, bisect, cherry-pick, or revert sequence unless the user explicitly passes `--force`. This aligns with Git’s general principle of protecting uncommitted or in-progress work and prevents accidental data loss.

The email is a reply to Phillip Wood’s **substantive review** of the first patch in Jasper Mayone’s two-patch series. Jasper accepts all of Phillip’s suggestions: he will add checks for `CHERRY_PICK_HEAD` and `REVERT_HEAD` to catch single-commit cherry-picks or reverts that appear clean but are technically still in progress, reword the documentation to use a bulleted list for clarity, adopt subshells in tests for better readability, and factor out conflict setup into a shared helper. The only substantive change is the addition of the `CHERRY_PICK_HEAD`/`REVERT_HEAD` checks; the rest are editorial improvements.

The patch remains a well-motivated safety improvement that addresses a real risk. The new checks close an edge case Phillip identified, making the validation logic more thorough without altering the core behavior. The documentation and test improvements make the patch easier to understand and maintain. This patch is part of a larger effort to improve worktree safety and composability, but it stands alone as a clear, focused fix.

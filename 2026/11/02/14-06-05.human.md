This is the second patch in Jasper Mayone’s two-part series extending Git’s worktree and ref-filter subsystems. The patch makes `%(worktreepath)` in `git for-each-ref` report the worktree path for branches that are being rebased or bisected, even when the worktree’s `HEAD` is detached. The change aligns `for-each-ref` behavior with how `git worktree add` and `git branch -d` already treat such branches, closing a gap where scripts had no way to discover which worktree is working on a rebasing or bisecting branch.

Phillip Wood’s review raises three main concerns. First, he points out that the patch duplicates logic from `branch.c`’s `prepare_checked_out_branches()` instead of reusing it, which could lead to inconsistencies if the logic in `branch.c` changes later. Second, he notes that the patch changes the behavior for bare worktrees by no longer reporting their `git_dir` in `%(worktreepath)`, which is a backward-incompatible change that should be documented in the commit message. Third, he suggests adding a warning to the `git-for-each-ref` documentation about the limitations of `%(worktreepath)`: it may contain newlines, it doesn’t distinguish between main and linked worktrees, and it only reports one worktree if a branch is checked out in multiple worktrees.

The patch itself is well-tested, covering rebasing, bisecting, interactive rebase with an edit stop, `rebase --update-refs`, and detached-HEAD rebase scenarios. The backward-incompatible change (scripts relying on `%(worktreepath)` being empty for rebasing/bisecting branches) is explicitly called out in the commit message, which asks whether any such scripts exist. The series looks like a well-crafted fix for a real problem, but Phillip’s concerns about code duplication and documentation gaps should be addressed before merging.

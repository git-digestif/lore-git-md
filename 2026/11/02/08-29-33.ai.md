This is a **substantive review** of the Trace2 diagnostic patch for `git maintenance`. Patrick Steinhardt raises two broader design questions about the current lock-handling logic in `git maintenance run`, using the patch as a jumping-off point.

The review does not object to the patch itself — the Trace2 event addition remains uncontroversial — but it identifies what Patrick sees as a latent bug in the existing code: the command silently succeeds when it fails to acquire the lock, even in non-`--auto` mode. He argues this is inconsistent with `git gc` (which fails fast on lock contention) and with user expectations, and suggests the patch’s author consider addressing it in a follow-up.

Key technical points for future discussion:
- The lock-checking logic in `builtin/gc.c` currently swallows all lock-acquisition errors except `EEXIST` in `--auto` mode.
- Patrick proposes distinguishing between `--auto` (warn and succeed) and non-`--auto` (error out) when the lock cannot be acquired.
- The inconsistency with `git gc` is noted as a precedent for stricter behavior.
- No code changes are requested in this patch; the feedback is purely advisory and scoped to a potential follow-up.

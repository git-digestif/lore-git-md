This is the second patch in a two-patch series improving `git maintenance` lock handling. It addresses the inconsistency between `--auto` and manual invocations when the maintenance lock cannot be acquired.

The patch now makes manual `git maintenance run` (without `--auto`) fail with exit code 128 and an error message when the lock is held, matching `git gc`'s behavior. For `--auto` mode, it preserves the silent skip but emits a detailed Trace2 event (`"lock/skip": {"reason": "exists", "errno": <code>}`) that includes the actual error code (e.g., `EEXIST`, `EPERM`). The commit message and test coverage are thorough, showing the author incorporated feedback from Patrick Steinhardt’s review of v1.

The implementation is clean: it captures `errno` immediately after the failed lock acquisition, uses Git’s existing `unable_to_lock_message()` helper for consistent error formatting, and respects the `--quiet` flag. The test updates verify both the Trace2 event emission (including error code) and the new exit-code behavior for manual invocations, while confirming the lock file remains in place on failure.

This is a well-crafted, uncontroversial patch that resolves a latent design inconsistency. The change is purely behavioral and diagnostic, with no on-disk format changes, and should be ready for merging once reviewed. The series as a whole is a clear improvement to `git maintenance` observability and consistency.

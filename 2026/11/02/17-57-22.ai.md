This is the second patch in Jasper Mayone’s two-part series extending `%(worktreepath)` in `ref-filter.c` to report worktree paths for branches being rebased or bisected. The patch now addresses Phillip Wood’s **substantive review feedback** from the previous iteration, resolving code duplication, clarifying documentation, and documenting a breaking change in behavior.

The key change in this version is the elimination of code duplication. Instead of copying logic from `branch.c`’s `prepare_checked_out_branches()`, Jasper has added a new helper function, `branch_checked_out_worktree(const char *refname)`, to `branch.c`. This function reads the list built by `prepare_checked_out_branches()` and skips branches being updated by `rebase --update-refs`, ensuring `%(worktreepath)` only reports worktrees where the branch is *checked out*, not merely being updated. The patch removes the redundant hashmap in `ref-filter.c`, resulting in a net reduction of code.

The patch also **removes the confusing `+` marker** in `git branch` output for worktrees rebasing or bisecting a branch. Since the `*` line already names the branch, the `+` marker is redundant and has been dropped. The documentation for `git-branch.adoc` is updated to reflect this change, removing the phrase “also in the worktree that is rebasing or bisecting it.”

A **breaking change** is now explicitly documented: the patch stops printing the `git_dir` of bare worktrees in `%(worktreepath)`. Previously, `%(worktreepath)` returned the `git_dir` path for bare repositories, but this behavior was inconsistent with the atom’s name and purpose. The commit message now explains this change and adds a test to verify the new behavior.

Jasper has also accepted Phillip’s suggestion to add a **documentation warning** about parsing `%(worktreepath)` when paths contain newlines, recommending the use of quoting options or NUL-terminated output (`%00`). This will be added as a separate documentation patch before this one.

The patch remains part of a broader effort to improve worktree safety and usability. While it resolves the immediate technical debt and usability concerns raised in Phillip’s review, the **design questions** about `for-each-ref`’s suitability as a filtering mechanism—such as its lack of NUL-terminated output, inability to distinguish main/linked worktrees, and risk of surfacing mid-rebase worktrees—remain unresolved. These limitations are now documented but not addressed in this series.

The patch is **well-motivated and technically sound**, addressing a real gap in Git’s worktree tracking while aligning behavior across commands. The changes are backward-incompatible for scripts relying on the old `%(worktreepath)` behavior for bare worktrees or the `+` marker in `git branch` output, but these are clearly documented and justified. The elimination of code duplication and improved documentation make this version a clear improvement over the previous iteration.

This is a **substantive review** of the first patch in Jasper Mayone’s two-patch series, which makes `git worktree remove` refuse deletion of worktrees in the middle of a rebase, `git am`, bisect, cherry-pick, or revert sequence unless `--force` is given. Phillip Wood’s review is thorough and constructive, focusing on clarity, edge cases, and testing.

Phillip’s feedback is largely editorial but identifies one **substantive edge case**: the patch does not check for `CHERRY_PICK_HEAD` or `REVERT_HEAD` when a single-commit cherry-pick or revert has completed without conflicts, leaving the operation technically in progress even though the worktree appears clean. He argues that this is still a meaningful state to protect, though the risk of data loss is lower. The rest of his comments are about documentation wording, code organization, and test clarity.

The documentation changes are flagged as needing rewording for clarity, particularly around the use of "either" and the list of conditions requiring `--force`. Phillip suggests a bulleted list might improve readability. The code itself is deemed correct, though he expresses a wish for a standardized function to detect in-progress operations rather than open-coding the logic.

On testing, Phillip praises the coverage but suggests two improvements: using subshells for clarity when running multiple commands in a worktree, and factoring out the conflict setup into a shared helper to avoid repetition across tests. These are stylistic suggestions rather than correctness issues.

Overall, the review is **supportive** of the patch’s goal and implementation, with the main substantive request being the addition of `CHERRY_PICK_HEAD`/`REVERT_HEAD` checks. The feedback is actionable and does not challenge the core design. The patch remains a well-motivated safety improvement that addresses a real risk of data loss.

This is a bugfix patch targeting the `git log` command, specifically addressing a regression in the `-m --follow` combination. The patch is the third in a five-part series (v5).

The issue: when using `git log -m --follow` on a merge commit where a file was renamed differently in each parent branch, Git loses track of the file's history on the second parent. In the test case—a diamond-shaped history where both sides of a fork rename the same file to different names—the command fails to show commits from the second parent's side of the fork.

The fix is straightforward: in `log-tree.c`, the code now saves the original path of the merge commit before diffing against each parent, then restores it before each diff and after the loop. This ensures that rename detection starts from the merge's path, not from the path updated by the previous parent's diff. The change only affects merge commits; single-parent commits continue to work as before.

The patch includes a new test in `t/t4219-log-follow-merge.sh` that verifies the full history is shown for the diamond case. The test is clear and covers the exact scenario described in the commit message.

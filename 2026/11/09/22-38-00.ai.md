This is a **platform compatibility discussion** continuing the thread about APFS/mmap metadata quirks breaking Git’s change detection. Brian M. Carlson’s reply clarifies Git’s current mmap usage and the POSIX specification, then cautions against submitting an LLM-generated patch.

Brian explains that Git only mmaps content-addressed files (packs, indexes, object maps) or files replaced atomically via `rename(2)`. These files either have hashes in their names (making them immutable) or are never modified in place, so the APFS/mmap issue does not affect Git’s own operations. He emphasizes that using mmap on mutable working-tree files is unsafe due to potential `SIGBUS` crashes when accessing beyond the file’s end, which is why text editors avoid it.

On the POSIX front, Brian quotes the standard: `mtime` and `ctime` updates for `MAP_SHARED`/`PROT_WRITE` mappings are only guaranteed after an `msync()` call. This means APFS’s behavior is technically compliant, and Git’s reliance on accurate `mtime` is not violated by its own code. The responsibility for timely `msync()` calls lies with the tool modifying the file, not Git.

Brian’s tone is firm on two points: (1) Git’s current mmap usage is safe and unaffected by the APFS quirk, and (2) LLM-generated patches are not acceptable per `SubmittingPatches`. He does not weigh in on whether the project should address the edge case for third-party tools, leaving that question open for others. The key technical detail for follow-ups is that Git itself does not mmap mutable working-tree files, so any fix would target a niche scenario rather than a core Git workflow.

This is a bugfix patch (third in a five-patch series) targeting the `git log` command. It addresses a regression in the `-m --follow` combination where, in merge commits with renamed files, the history of later parents is incorrectly lost.

The issue occurs in the diamond-merge scenario from `t4219`: when two branches rename a file differently and then merge, `git log -m --follow <path>` fails to show the full history of the file on the second parent's side. The root cause is that the parent loop in `log_tree_diff()` does not restore the followed path between parents, causing the second parent to be diffed against the already-renamed path rather than the merge's original path.

The fix is straightforward: save the merge's path before the parent loop, restore it before diffing each parent, and ensure `propagate_follow_pathspec_to_parent()` records the correct path for each parent. The patch adds a new test that verifies the full history is now shown for the diamond case.

The change is minimal (13 lines in `log-tree.c`, 16 in the test) and well-scoped. The commit message clearly explains the problem, the fix, and the test coverage. This looks like a solid, well-motivated bugfix.

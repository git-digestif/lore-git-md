This is a performance-focused patch series targeting the `git log --follow` feature for non-linear history. The series (v5 of 5 patches) addresses a severe regression introduced in v4.30.0 (commit 304812ed33, June 2026) where `--follow` became unusably slow—specifically, a test case on linux.git ballooned from 28 seconds to 6 minutes 43 seconds. The regression occurs because the existing implementation diffs each merge commit against *all* parents with rename detection enabled, which is computationally expensive when a parent lacks the tracked path.

The core fix (now consolidated into patch 5/5) adopts a two-phase strategy: first, it identifies a parent where the tracked path is unchanged (using a fast diff without rename detection), then it only performs full rename detection against other parents if necessary. This reduces the linux.git test case to 42 seconds, nearly restoring pre-regression performance. The series also expands test coverage in `t4219-log-follow-merge.sh` to verify edge cases like subtree merges, copy detection, and merges where one side edits the old path while the other side renames it.

Key technical details: the patch touches `log-tree.c`, introducing helper functions (`follow_same_parent`, `follow_needs_renames`, `follow_has_rename_source`) to manage the new logic. It also modifies `remember_follow_pathspec` to handle disagreements between child commits about the tracked path. The series is authored by Miklos Vajna and incorporates feedback from Patrick Steinhardt and SZEDER Gábor, with all prior review issues addressed in this iteration. The changes are confined to the log subsystem and do not affect other Git commands.

This is a bugfix targeting the fsmonitor and untracked cache subsystems. The patch addresses a subtle but real correctness issue: when the fsmonitor daemon sends a trivial response (`"/"`), typically after a restart or event loss, Git marks all index entries as dirty but fails to invalidate stale untracked cache entries. This can cause `git status` to show untracked files that no longer exist or emit spurious warnings about missing directories.

The fix is narrowly scoped and well-explained. It introduces a new function, `untracked_cache_invalidate_stale_dirs()`, which recursively checks each cached directory against its on-disk stat data before the untracked cache is written to the index. The check happens only when the fsmonitor extension is written and the cache is no longer trusted, avoiding unnecessary overhead for commands that don’t write the index or for sparse index writes. The cost is one `lstat()` per cached directory, incurred only once per trivial response—Derrick Stolee’s measurements confirm this has no measurable performance impact.

The implementation is clean and follows existing patterns in the untracked cache code. The patch includes thorough test coverage for both hook-based and built-in fsmonitor backends, exercising the exact scenario where stale entries would otherwise persist. Review feedback from Stolee and Junio C Hamano has been incorporated, resolving the last open questions about recursion safety and error handling (e.g., invalidating the entire cache if `repo_get_work_tree()` fails).

This looks like a solid, low-risk fix for a real problem. The commit message clearly explains the edge case, the chosen solution, and the trade-offs.

This is a **bugfix patch update** in response to a **substantive review** of the first patch in Tanga Joris’s two-part series addressing the `git apply --check` crash. The thread targets the `apply.c` subsystem and focuses on how Git should handle malformed patch headers—specifically, whether to reject them outright or attempt to normalize them.

Tanga now **concedes the core critique**: the original fix’s approach of accepting certain malformed headers (e.g., blank lines or indented mode lines after `diff --git`) was misguided. Instead, the revised plan is to **die with a clear error** when a `diff --git` line is followed by invalid content (like blank lines or `---`/`+++` before the next `diff --git`), aligning with Git’s precedent for strict diff header validation (e.g., commit `d70e9c5c8c`). This pivot addresses Phillip Wood’s concern that the original fix risked normalizing corrupt input rather than enforcing parsing rules.

Key changes in the revised approach:
- **Rejects** patches with blank lines or indented mode lines after `diff --git`, treating them as corruption.
- **Preserves** the exception for empty `diff --git` sections (e.g., `diff --git a/f b/f` with no content, followed by another patch), as this is uncontested.
- **Error messages** will name the problematic `diff --git` line, improving actionability for users.
- **Backwards compatibility note**: The stricter validation will also reject patches that *modify* files (not just create/delete them) if they contain blank lines after `diff --git`, even though Git currently accepts these (with the side effect of ignoring mode changes). Tanga flags this as a potential edge case but does not propose a workaround, deferring to Phillip’s judgment.

The update narrows the fix’s scope to **strict validation** while maintaining the original goal of preventing the crash. The next steps are likely a v2 patch series incorporating these changes, with continued review from Phillip and other maintainers (e.g., Junio or Eric Sunshine) to assess the trade-offs of stricter parsing. The philosophical debate—whether Git should prioritize robustness (rejecting malformed input) or flexibility (normalizing edge cases)—appears to be tilting toward the former in this thread.

This is the latest update in the ongoing fix for a Git crash in `git apply --check` when processing malformed patch headers. Tanga Joris, an Outreachy contributor, is refining a two-patch series to address the issue, and this email clarifies the final scope of the stricter validation approach now endorsed by both Phillip Wood and Junio C Hamano.

The series will now **reject all corrupt patch headers** that Git’s own tools (`git format-patch`, `git diff`) would not generate, including:
- Blank lines after a `diff --git` line (previously accepted but silently ignored mode changes).
- Indented `new file mode` or `deleted file mode` lines (previously accepted but ignored).
- `---` or `+++` lines appearing before their corresponding mode lines (already rejected in the current version).

The only exception is **empty `diff --git` sections** (e.g., `diff --git a/f b/f` with no content, followed by another `diff --git`), which will continue to be ignored for now, though Junio’s earlier comment suggests this edge case may still warrant future scrutiny. Tanga notes that this behavior already exists on `master` and is not new, so it’s being left out of the current series.

The email also reveals a minor edge case: `git format-patch` can produce a `diff --git` line with no content if a commit message body contains text that looks like one. On `master`, this causes `git apply` to fail with an "inconsistent old filename" error unless the next patch section names the same file. This is not being addressed in the current series, as it’s pre-existing behavior.

The next version of the patch series will implement these stricter rules, with clear error messages naming the problematic `diff --git` line. The fix is now aligned with maintainer expectations and ready for final review, focusing on error message clarity and test coverage. No further philosophical debate is expected, and the series is on track for integration.

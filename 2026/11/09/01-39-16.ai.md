This is a **reftable backend bugfix discussion** that advances the proposed fix for a correctness regression in HEAD reflog handling during symref updates within transactions.

井上司 (Tsukasa Inoue) revisits the root cause and acknowledges that the files backend also exhibits the same bug when symref updates are queued in the wrong order—only its lack of atomic transaction support masks the issue. He now proposes a more general solution: introducing a helper in `refs.c` that returns the new OID of a ref updated in the same transaction, allowing both backends to use it before falling back to `refs_resolve_ref_unsafe()`. This approach would fix the bug in both backends regardless of update order and enable a single test to cover both. The broader architectural refactoring (moving reflog logic entirely into `refs.c`) could then follow as a subsequent step.

Karthik Nayak’s earlier endorsement of the targeted fix remains in play, but the discussion has shifted toward a more principled, reusable solution that addresses the issue at the generic layer rather than per-backend. The tone remains collaborative, and the proposal is concrete enough to expect a patch soon. The reftable backend (`refs/reftable-backend.c`) and the generic refs layer (`refs.c`) are the only subsystems touched; the key new symbol will likely be the helper function in `refs.c`. No test integration has been posted yet, but the reproduction script is already available.

This is an Outreachy proposal draft for a feature targeting the promisor remote subsystem. The author, Hussain Sitamouwala, outlines a plan to make the order in which Git fetches missing objects from promisor remotes configurable, both locally and via server advertisement.

The proposal is thorough and well-structured. It begins by documenting the current behavior (a fixed order based on config file position and whether the remote was server-advertised), then identifies the problem: users and server operators cannot influence this order, which matters for cost and performance. The design section presents three possible config shapes, with a preference for `remote.<name>.priority` (an integer, lower first), and discusses precedence rules between local and server-provided priorities. The protocol extension is minimal: an optional `priority=<n>` field in the promisor remote advertisement, parsed defensively to avoid crashes or misbehavior from malformed input.

Hussain has already contributed two patches to Git: one documenting the current promisor remote fetch order (accepted by Junio) and another converting `check-ref-format` to use the parse-options API. These demonstrate familiarity with the contribution process and the codebase. The proposal includes a detailed timeline, risk mitigation plan, and test matrix, showing careful preparation. The threat model section is particularly strong, listing specific attack vectors (e.g., integer overflow, duplicate fields) and how they will be handled.

This looks like a serious, well-motivated effort. The feature addresses a real limitation (the "order cannot be set" note in the technical docs) and the design is conservative: nothing changes unless the user opts in, and the server's advertised priority only applies to remotes without a local setting. The Outreachy context means the work will be mentored, but the proposal itself is already at a level that suggests it will produce mergeable code.

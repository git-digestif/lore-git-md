This is a **clarification in a documentation thread** about Jasper Mayone’s patch series extending `%(worktreepath)` in `git for-each-ref`. Junio C Hamano weighs in to refine the explanation for why Git discourages checking out the same branch in multiple worktrees. He corrects Ben Knoble’s phrasing ("possible races") and replaces it with a concrete scenario: if two worktrees (`A` and `B`) have the same branch checked out, a commit in `A` will make `B`’s working tree appear to have reverted the change, creating confusion. Junio emphasizes that this is not a race condition (since `B` was idle) but rather a logical inconsistency that Git aims to prevent. The clarification reinforces the accuracy of the documentation’s claim that `%(worktreepath)` shows only one worktree per branch, even though the scenario is technically possible with `--force` or plumbing commands. No new technical concerns are raised, and the thread remains focused on the safety and usability of parsing `%(worktreepath)` output. The discussion is now resolved, with the documentation patch (2/4) ready for integration.

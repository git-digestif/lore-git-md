Thread identity: Configurable fetch ordering for promisor remotes in partial clones (Outreachy proposal draft by Hussain Sitamouwala)

Core problem or goal: Add user-configurable ordering for promisor remotes in partial clones, replacing the current fixed order with a priority-based system controlled by local configuration (`remote.<name>.priority`) and optionally by server-advertised priorities. The feature targets users with multiple promisor remotes (e.g., regional mirrors in large organizations) who need to prioritize cheaper or faster remotes.

Current status: Proposal stage (pre-patch). The author has shared a detailed design document seeking feedback before sending a formal patch series. No code has been posted yet. The proposal includes three planned components: (1) tests to lock in current behavior, (2) local configuration via `remote.<name>.priority`, and (3) server-advertised priority with documented precedence rules. A competing patch (`promisor.fetchOrder`) is noted as a potential conflict.

Key technical details:
- New configuration: `remote.<name>.priority` (lower values tried first).
- Server-advertised priority field (protocol extension) with fallback to local config.
- Files/subsystems likely to be touched: `promisor-remote.c`, `transport.c`, `remote.c`, `Documentation/config/remote.txt`, and test files in `t/`.
- No on-disk format changes; behavior is runtime-only.
- Protocol design ignores malformed server input (defensive).
- Test coverage planned for edge cases (integer overflow, duplicate fields).

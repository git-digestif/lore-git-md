Thread identity: Configurable fetch ordering for promisor remotes in partial clones (Outreachy proposal draft v2 by Hussain Sitamouwala).

Core problem or goal: Add user-configurable ordering for promisor remotes in partial clones, replacing the current fixed order with a priority-based system controlled by local configuration and optionally by server-advertised priorities. The feature targets users with multiple promisor remotes (e.g., regional mirrors in large organizations) who need to prioritize cheaper or faster remotes. The current behavior calls `try_promisor_remotes()` twice: first with `accepted_only=true` (server-advertised remotes), then with `accepted_only=false`, each in config-file order with `extensions.partialClone` last; the proposal preserves this two-pass structure while adding stable sorting by priority within each pass.

Current status: Proposal stage (pre-patch), now at v2 of the design document. The author is responding to Kaartic Sivaraam's substantive review of v1 and has made specific concessions: user-set configuration values and server-supplied priorities must be stored in separate config keys (not sharing `remote.<name>.<field>`) because `promisor.storeFields` writes server data into that namespace and could collide with hand-set values. The author recommends local user values win outright over server-advertised ones (ordering only remotes with no local setting) but notes operators paying for bandwidth may prefer the opposite; exact key names, precedence semantics, and whether server values are persisted at all are deferred to a future protocol RFC. No code has been posted yet. The planned series has six patches: patches 1-3 (trace2 observation event, baseline tests locking current behavior, and a behavior-preserving refactor to allow sorting) are independent of design decisions, while patches 4 (local config via `remote.<name>.priority`, lower values tried first) and 5 (server-advertised `priority=<n>` field and client handling) depend on the protocol RFC and maintainer decisions about config shape. The author's earlier documentation patch describing current fetch order is cooking in `next` (queued 2026-11-12, not yet in `master`), and his `check-ref-format` parse-options patch is under review.

Key technical details:
- New local configuration: `remote.<name>.priority` (lower values tried first); exact key name for user-set values explicitly left open pending RFC, and must be stored separately from any server-supplied priority key.
- Server-advertised priority field (`priority=<n>` protocol extension) treated as untrusted input: malformed values ignored defensively, no effect for clients that do not opt in via `promisor.storeFields`.
- Files/subsystems likely to be touched: `promisor-remote.c` (specifically `try_promisor_remotes()`, `lazy_fetch_objects()`, and `promisor_remote_get_direct()`), `transport.c`, `remote.c`, `Documentation/config/remote.txt`, `Documentation/config/promisor.adoc`, `Documentation/technical/partial-clone.adoc`, and tests in `t/t5710-promisor-remote-capability.sh` and `t/t0410-partial-clone.sh`.
- No on-disk format changes; behavior is runtime-only.
- Planned test coverage for edge cases: integer overflow, duplicate fields, negative priorities, non-integer values.

Open questions and loose ends:
- **Precedence and storage separation**: User-set vs server-supplied priorities must use distinct config keys; whether local values should override server-advertised ones outright (author's recommendation) or the reverse (operator preference for bandwidth cost) is unresolved pending RFC.
- **Persistence**: Whether server-advertised values are persisted at all (and under what key) is open.
- **Protocol design**: Whether `promisor.sendFields` needs per-remote gating instead of a global setting; patches 4 and 5 are blocked on the protocol RFC resolving first.
- **Config shape**: `remote.<name>.priority` vs server-advertised values vs the competing `promisor.fetchOrder` (single list of remote names) remains open; author plans to send a trade-off note and implement whichever shape maintainers prefer.
- **Edge cases**: Handling of negative priorities, non-integer values, integer overflow, and whether an explicit local priority should override the accepted-first rule remains unspecified.

This is a performance-focused bugfix for `git log --follow` in complex merge histories. The patch is the fifth and final part of a series that addresses a severe slowdown (from 28 seconds to 6m43s) introduced by an earlier optimization for non-linear history. Miklos Vajna identifies that the regression occurs because `git log --follow` now performs expensive rename detection against *every* parent of a merge commit, even when the path being followed is unchanged in one parent. The fix avoids unnecessary rename detection by first checking for a parent where the path is identical, then only performing full rename detection for parents where the path actually differs. The result is a 9.5x speedup (42s vs 6m43s) on the reported test case, bringing performance close to pre-regression levels.

The implementation is careful to preserve correctness: it still performs rename detection when needed (e.g., if a merge dropped a change from one parent, or if the path was copied from a file in another parent). The patch touches only `log-tree.c` and adds three new helper functions (`follow_same_parent`, `follow_needs_renames`, and supporting utilities) to encapsulate the logic. The commit message includes a clear explanation of the problem, the fix strategy, and before/after performance numbers, making it easy to assess the impact. Given the severity of the regression and the thoroughness of the solution, this looks like a well-motivated and well-executed fix that should be uncontroversial.

This is a performance-focused bugfix series targeting `git log --follow` for merge-heavy histories. Miklos Vajna addresses a severe regression introduced in Git 2.47 (commit 304812ed33, June 2026) where `--follow` became unusably slow—6 minutes 43 seconds instead of 28 seconds for a real-world case in the Linux kernel repository.

The series is now at v5, incorporating feedback from Patrick Steinhardt and others. The key change is a two-phase diff strategy: first, the code quickly identifies a parent where the tracked path is unchanged, then skips expensive rename detection against other parents unless there’s evidence the path was renamed or copied from a file that parent modified. This brings performance back to 42 seconds, close to the pre-regression baseline. The patch also handles edge cases like subtree merges of unrelated histories and follows copies (not just renames) when the merge dropped edits to the source file.

Tests in `t4219-log-follow-merge.sh` have grown substantially, now covering subtree merges, forked histories with divergent renames, and merges that keep the renamed path while the other side edited the original. The code touches only `log-tree.c` and the test file, making this a self-contained fix for a specific but painful workflow. If you care about `git log --follow` on large repositories, this series is worth watching.

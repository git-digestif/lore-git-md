Subject: APFS/mmap metadata quirk breaks Git change detection
Series version: none (standalone bug report)
Originating author: Harold Hunt
Thread type: bug report / platform compatibility discussion

Core problem or goal
Git’s change detection (based on `mtime`/`ctime`) fails on macOS/APFS when files are modified via mmap without an explicit `msync()`. APFS does not update `mtime` on mmap writes, while Linux filesystems do, causing Git to incorrectly report “no changes” even though the file contents have changed. The issue persists until `munmap()` is called (updating `ctime` but not `mtime`) and can also affect same-second modifications. The discussion now clarifies that this edge case affects third-party tools (e.g., text editors) that mmap mutable working-tree files, not Git’s own operations.

Current status
Under discussion; no patch or RFC posted yet. Harold is gauging whether the project considers this edge case worth fixing, while Brian M. Carlson has clarified that Git’s own mmap usage is unaffected. The question remains open whether the project should address the quirk for third-party tools.

Key technical details
- Platform: macOS with APFS
- Subsystem: filesystem metadata (`mtime`/`ctime`) and mmap interaction
- Behavior: Git fails to detect mmap’d modifications to mutable working-tree files until `munmap()` is called; Git’s own mmap usage (packs, indexes, object maps) is unaffected because those files are either immutable (content-addressed) or replaced atomically via `rename(2)`
- POSIX compliance: `mtime`/`ctime` updates for `MAP_SHARED`/`PROT_WRITE` mappings are only guaranteed after `msync()`; APFS’s behavior is technically compliant
- Safety concern: mmap on mutable working-tree files is unsafe due to potential `SIGBUS` crashes when accessing beyond the file’s end (why text editors avoid it)
- Proposed fix sketch (from Harold): check APFS generation number, fall back to content examination if zero
- No new symbols, CLI options, or on-disk format changes introduced yet

Open questions and loose ends

- Are there other macOS/APFS quirks the project already tracks?
- Would the project accept a generation-number check, or is there a preferred alternative (e.g., content hashing for suspected cases)?
- What is the performance tradeoff for content examination on every stat?

Subject: APFS/mmap metadata quirk breaks Git change detection
Series version: none (standalone bug report)
Originating author: Harold Hunt
Thread type: bug report / platform compatibility discussion

Core problem or goal
Git’s change detection (based on `mtime`/`ctime`) fails on macOS/APFS when files are modified via mmap without an explicit `msync()`. APFS does not update `mtime` on mmap writes, while Linux filesystems do, causing Git to incorrectly report “no changes” even though the file contents have changed. The issue persists until `munmap()` is called (updating `ctime` but not `mtime`) and can also affect same-second modifications. The discussion clarifies that this edge case affects third-party tools (e.g., text editors) that mmap mutable working-tree files, not Git’s own operations. Johannes Sixt (Hannes) broadens the scope by noting that Git’s mmap emulation on Windows exhibits the same delayed timestamp update behavior due to API limitations (`FlushViewOfFile` does not update timestamps), meaning the problem is not macOS-specific.

Current status
Under discussion; no patch or RFC posted yet. Harold is gauging whether the project considers this edge case worth fixing, while Brian M. Carlson and Hannes have clarified that Git’s own mmap usage is unaffected (restricted to immutable or atomically-replaced files). The question remains open whether the project should address the quirk for third-party tools, with the added caveat that any solution must account for Windows’s similar limitations.

Key technical details
- Platforms: macOS with APFS *and* Windows (Git’s mmap emulation)
- Subsystem: filesystem metadata (`mtime`/`ctime`) and mmap interaction
- Behavior: Git fails to detect mmap’d modifications to mutable working-tree files until `munmap()` is called; Git’s own mmap usage (packs, indexes, object maps) is unaffected because those files are either immutable (content-addressed) or replaced atomically via `rename(2)`
- POSIX compliance: `mtime`/`ctime` updates for `MAP_SHARED`/`PROT_WRITE` mappings are only guaranteed after `msync()`; APFS’s and Windows’s behavior is technically compliant
- Windows API limitation: `FlushViewOfFile` does not update file timestamps, making it impossible to emulate Linux’s timely `mtime` updates
- Safety concern: mmap on mutable working-tree files is unsafe due to potential `SIGBUS` crashes when accessing beyond the file’s end (why text editors avoid it)
- Proposed fix sketch (from Harold): check APFS generation number, fall back to content examination if zero
- No new symbols, CLI options, or on-disk format changes introduced yet

Open questions and loose ends

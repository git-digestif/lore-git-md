This is a **platform compatibility bug report** targeting macOS/APFS and mmap behavior. The author, Harold Hunt, reports that Git on APFS can incorrectly report no changes to files that have been modified via mmap without calling `msync()`. The issue does not occur on Linux, where Git correctly detects the changes. Harold is working on copy-on-write cloning for Git and discovered this while testing mmap interactions with worktrees.

The core problem is that APFS does not update file metadata (specifically `mtime`) when a file is modified through mmap without `msync()`, while Linux filesystems do. This causes Git’s change detection (which relies on `mtime` and `ctime`) to fail on APFS, even though the file contents have changed. Harold notes that the issue persists until `munmap()` is called, at which point `ctime` updates but `mtime` remains unchanged. A secondary issue is that if a file is modified in the same second as the last commit, Git may continue to misreport no changes even after the file is unmapped.

Harold is seeking input on whether this is a known issue, how much the project values correctness in this edge case, and whether others have experience with APFS/mmap quirks. He has an LLM-generated PR in his fork but is not soliciting review yet. The impact is limited to APFS, and the performance tradeoff depends on how frequently files are mmap’d. His proposed fix checks the generation number (falling back to content examination if it is zero), but he is unsure if the project would accept such a change.

The email does not include a patch or RFC, so this is purely a discussion starter.

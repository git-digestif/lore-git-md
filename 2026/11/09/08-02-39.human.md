This is a bugfix patch in a six-part series improving `git log --follow` for non-linear history. The series, led by Miklos Vajna, addresses performance and correctness issues when tracking file history across merges, especially in cases involving subtree merges or unrelated histories.

The specific issue here is a regression introduced by an earlier patch in the series (304812ed33d, June 2026). That patch aimed to improve rename following for non-linear history but inadvertently broke cases where no merge base exists—such as when merging unrelated histories via subtree merges. The fix restores the previous behavior by ensuring `follow_needs_renames()` returns `1` (true) when no merge base is found, forcing rename detection to proceed as before.

Miklos notes that the existing test suite didn’t catch this because the test case for subtree merges didn’t trigger `follow_needs_renames()` (the path was unchanged in any parent). To address this, he’s added a new test in the first patch of the v5 series to cover this edge case, and the updated patch 5/6 now passes it.

The patch appears well-motivated and narrowly scoped, targeting a clear regression with a minimal fix. The addition of a test case suggests the author is being thorough about preventing future regressions. If you care about `git log --follow` or work with complex merge histories, this is worth a quick look—especially if you’ve encountered issues with rename detection in such scenarios.

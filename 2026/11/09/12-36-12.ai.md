This is a **substantive review** of the documentation patch in Jasper Mayone’s four-part series extending `%(worktreepath)` in `git for-each-ref`. D. Ben Knoble raises a fundamental question about the correctness of the documentation: whether a branch can *ever* be checked out in more than one worktree, given Git’s long-standing safety mechanisms that prevent concurrent updates to the same branch from different worktrees.

The documentation patch claims that when a branch is checked out in multiple worktrees, `%(worktreepath)` will show only one of them. Knoble challenges this claim, stating that Git’s porcelain should refuse to create such worktrees in the first place due to race conditions. If Knoble is correct, the documentation is misleading and should instead state that this scenario is impossible, not merely that only one worktree is shown.

This is not a surface-level nit; it goes to the heart of whether the documentation accurately describes Git’s behavior. If the scenario is impossible, the warning is unnecessary and could confuse users. If it *is* possible (e.g., through low-level plumbing commands or edge cases like worktree creation during a rebase), the documentation is correct but should clarify the conditions under which it can occur.

The patch is otherwise well-motivated and addresses a real parsing hazard (newlines in worktree paths), but this review comment introduces a critical ambiguity that needs resolution before the patch can be merged. The author or a domain expert (e.g., Phillip Wood, Eric Sunshine, or Junio) will need to clarify whether the scenario is possible and, if not, adjust the documentation accordingly. Until then, the patch remains in limbo.

This is a **bugfix** patch in a six-part series addressing a regression in `git log --follow` when tracking file history across merges where the file was edited on a side not taken by the merge. The specific issue is that `--follow` fails to continue tracking the file if the merge base lacks the path but a parent modified a file that the merge no longer includes—this can happen due to renames or copies.

The email is a reply from the author (Miklos Vajna) to a review comment by Patrick Steinhardt, who pointed out that the original fix did not account for file copies (only renames). Miklos acknowledges the oversight, reports that he has updated the series (v5) to handle copies correctly, and notes a modest performance impact (42s vs. 37s) in the linux.git test case. The fix now includes a pre-filter that considers files retained in the merge but with content from the other parent, and the rename detection logic has been extended to cover copies.

The patch touches the log subsystem and involves rename/copy detection logic, which is historically tricky and performance-sensitive. The review here is **substantive**: Patrick identified a missing edge case (copies) that could lead to incorrect `--follow` behavior, and the author’s response confirms the fix addresses it. The performance trade-off is small and explicitly quantified, which helps reviewers assess the cost of correctness. This is part of a larger effort to improve `--follow` reliability, and the series has clearly undergone active review.

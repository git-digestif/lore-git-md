This is a **bugfix** patch in a six-part series improving `git log --follow` for non-linear history. The email is a reply from the author (Miklos Vajna) to a review comment by Patrick Steinhardt, addressing a regression introduced in an earlier version of the series.

The issue: In cases where two unrelated histories are merged (e.g., subtree merges), the logic for determining whether rename detection is needed (`follow_needs_renames()`) could incorrectly return `0`, causing `--follow` to miss renames. The fix ensures that when no merge base exists, the function returns `1` (enabling rename detection), restoring the intended behavior from commit `304812ed33d` (June 2026). The author also added a new test in patch 1/5 to cover this edge case.

The patch touches the `log` subsystem, specifically the rename-following logic for `--follow`. Key functions involved include `follow_needs_renames()`. The fix is narrow and targeted, with test coverage added to prevent regression.

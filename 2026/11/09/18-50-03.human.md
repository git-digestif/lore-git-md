This is a **substantive review** from Jeff King (Peff) in the ongoing loose object database (ODB) cache invalidation bugfix thread. The email digs into the broader implications of removing or restricting the `OBJECT_INFO_QUICK` flag, which the current patch series documents as problematic but does not fully address.

Peff pushes back on Patrick Steinhardt’s suggestion that `QUICK` might be a "foot gun" worth eliminating entirely. He demonstrates that the flag still delivers measurable performance benefits in at least one critical code path: tag-following during `git fetch`. Using the `p5550` performance test, Peff shows that removing `QUICK` from this path slows it down by over 1300% (from 0.10s to 1.42s), even with modern optimizations to pack re-scanning. While he acknowledges the test is intentionally pathological, the magnitude of the regression suggests `QUICK` is not obsolete.

The review also clarifies a key architectural detail: the `QUICK` flag’s behavior is now inverted in `odb_has_object()`. Callers get the quick (but potentially stale) check by default and must explicitly request a full re-scan with `ODB_HAS_OBJECT_RECHECK_PACKED`. This inversion complicates any audit of `QUICK` users, as the absence of a flag now implies the quick behavior. Peff’s patch snippet illustrates the mechanical change needed to remove `QUICK` from the tag-following logic, but he stops short of advocating for it, instead treating the measurement as a data point for future discussion.

The email does not propose a specific alternative to the current patch series, but it raises the stakes for any follow-up work. If `QUICK` is to be removed or restricted, the performance trade-offs will need to be carefully evaluated across all users, not just the prefetch path fixed in this series. Peff’s tone is collaborative, but the message is clear: the `QUICK` flag is still serving a purpose, and any deprecation will require more than a `NEEDSWORK` comment.

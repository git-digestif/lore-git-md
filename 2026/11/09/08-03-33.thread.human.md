This thread is about a performance regression in `git log --follow` that was introduced in Git v4.30.0 (June 2026). The issue made the feature unusably slow—one test case on linux.git jumped from 28 seconds to over 6 minutes—because the implementation was diffing each merge commit against *all* parents with rename detection enabled, even when unnecessary.

Miklos Vajna’s fifth iteration of the patch series (5/5) fixes the problem with a two-phase approach: first, it quickly identifies a parent where the tracked path is unchanged (using a fast diff without rename detection), then only performs full rename detection against other parents if needed. This restores performance to near pre-regression levels (42 seconds in the test case). The series also expands test coverage in `t4219-log-follow-merge.sh` to handle edge cases like subtree merges and copy detection.

The changes are confined to `log-tree.c`, where new helper functions (`follow_same_parent`, `follow_needs_renames`, `follow_has_rename_source`) manage the logic, and `remember_follow_pathspec` is updated to handle disagreements about the tracked path. The series has incorporated feedback from Patrick Steinhardt and SZEDER Gábor, addressing all prior review issues. There’s no indication yet of whether Junio has queued it for integration, but the performance improvement and expanded test coverage make it a strong candidate for merging.

This thread is about a patch series (v5) from Miklos Vajna that fixes a severe performance regression in `git log --follow` for non-linear history, introduced in Git v4.30.0. The regression made `--follow` unusably slow (e.g., 6m43s vs. 28s on linux.git) because it diffed merge commits against all parents with rename detection, even when unnecessary.

The series is now in its fifth iteration, addressing all prior feedback from Patrick Steinhardt and SZEDER Gábor. The latest update adds a test patch (1/5) by Justin Tobler, expanding coverage in `t/t4219-log-follow-merge.sh` to ensure the performance fix doesn’t break edge cases like subtree merges, renames on both sides of a merge, and `--diff-merges=first-parent` behavior. Justin’s review was constructive but surface-level, focusing on documentation clarity rather than technical correctness. The tests are well-motivated and directly tied to the regression’s root cause.

The core fix (patch 5/5) implements a two-phase strategy: a fast diff without rename detection to identify a parent where the tracked path is unchanged, followed by full rename detection only if needed. This restores performance to near pre-regression levels (42s on linux.git). The series touches only the log subsystem (`log-tree.c`) and its tests, with no open questions remaining. It’s now awaiting maintainer review and potential integration into Junio’s branches.

This is a **clarification from the maintainer** in a documentation thread about Jasper Mayone’s patch series adding filtering to `git worktree list` via `%(worktreepath)`. Junio C Hamano weighs in on why Git discourages checking out the same branch in multiple worktrees, correcting Ben Knoble’s phrasing ("possible races") to emphasize **user confusion** rather than technical race conditions. When two worktrees share a branch, a commit in one worktree makes the other appear to have reverted changes—even if it was idle—because its index and working tree no longer match the updated branch tip. Junio’s explanation reinforces the project’s long-standing design principle: a branch should be checked out in only one worktree at a time to avoid this kind of inconsistency. The message does not alter the patch series itself, but it provides useful context for anyone reading the updated `git-for-each-ref` documentation, which now warns about parsing `%(worktreepath)` safely and correctly notes that only one worktree is shown when a branch is checked out in multiple worktrees. The clarification is purely educational and does not raise new technical concerns.

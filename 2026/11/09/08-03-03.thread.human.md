This thread is about a bugfix series from Miklos Vajna that addresses a regression in `git log --follow` when tracking file history across merges. The issue occurs when the merge base lacks the file path, but a parent modified a file that the merge no longer includes—previously, `--follow` would fail to continue tracking the file in such cases. The series has evolved through review, with the latest version (v5) now handling file copies (not just renames) after Patrick Steinhardt pointed out the oversight in earlier iterations.

The fix touches the log subsystem and rename/copy detection logic, a historically tricky and performance-sensitive area. Miklos reports a small performance impact (42s vs. 37s in the linux.git test case) for the added correctness, which reviewers have accepted as a reasonable trade-off. The series is actively under review, with Patrick’s feedback driving key improvements, and the current version appears to address the core issue while maintaining acceptable performance. No merge status has been reported yet, so the series remains under review.

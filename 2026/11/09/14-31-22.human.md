This is a **substantive review follow-up** in the ongoing bugfix thread for the `git apply --check` crash. Phillip Wood responds to Tanga Joris’s proposed revision of the first patch in the two-part series, which now plans to **reject malformed patch headers outright** rather than attempting to normalize them.

Phillip **agrees with the stricter approach**, reinforcing the argument that patches with blank lines after `diff --git` (or other invalid content) are **corrupt** and should not be silently accepted. He highlights a specific edge case: Git currently accepts patches that *modify* files with blank lines after `diff --git`, but **ignores mode changes** in such cases. Phillip considers this behavior a bug and supports rejecting these patches as well, aligning with the revised fix’s goal of enforcing strict header validation.

The discussion narrows the scope of acceptable input to **only empty `diff --git` sections followed by another `diff --git` line** (e.g., `diff --git a/f b/f` with no content, then `diff --git a/g b/g`), which will continue to be ignored. All other malformations—including blank lines, indented mode lines, or `---`/`+++` appearing before the next `diff --git`—will trigger a fatal error naming the problematic line. This approach prioritizes robustness over flexibility, a trade-off Phillip endorses.

The next step is for Tanga to post a v2 patch series incorporating these changes. The revised fix will likely face further review from maintainers (e.g., Junio or Eric Sunshine) to assess its impact on backwards compatibility, but the core technical direction now has Phillip’s backing. The thread’s focus remains on **preventing the crash** while ensuring Git rejects corrupt input rather than applying it incorrectly.

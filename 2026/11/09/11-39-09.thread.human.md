This thread is an Outreachy proposal draft from Hussain Sitamouwala, seeking early feedback on a planned feature to add configurable fetch ordering to promisor remotes in partial clones. The proposal targets a long-standing limitation where Git currently uses a fixed order (accepted remotes first, then others in config order, with `extensions.partialClone` last) when fetching missing objects from multiple promisor remotes. Hussain plans to make this order configurable through three deliverables: tests to lock in current behavior, a local configuration setting (`remote.<name>.priority`), and a server-advertised priority field with documented precedence rules.

The design is well-scoped and thoughtful, using an integer-based priority system where lower values are tried first, with stable sorting to preserve existing order for equal or unset priorities. The server advertisement would use an optional `priority=<n>` field in the existing promisor-remote capability protocol, with defensive parsing to handle untrusted input. Hussain has clearly considered edge cases (malformed values, duplicate fields, precedence between local and server settings) and included a threat model section that would translate directly into test cases. The proposal also acknowledges a competing patch (`promisor.fetchOrder`) and has a plan to adapt if that lands first.

Hussain demonstrates strong preparation for the internship, having already contributed two patches to Git (documenting current promisor remote behavior and converting `check-ref-format` to use `parse-options`), run experiments to verify current behavior, and studied relevant test files. The timeline is realistic for a 12-week internship, with design review happening in parallel with early implementation work. No feedback has been received yet on the proposal itself, so the design is still open for discussion.

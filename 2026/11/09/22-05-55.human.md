This is a platform-compatibility bug report targeting macOS/APFS, specifically around how Git interacts with memory-mapped files.

Harold Hunt, a returning contributor (formerly of Cygwin/X), reports that Git on macOS with APFS can incorrectly report no changes to files that have been modified via `mmap()` but not `msync()`-ed. The issue does not occur on Linux, where Git correctly detects the changes even without `msync()`. Harold notes that the misreporting persists until the mapping is unmapped, at which point the file's `ctime` updates (but `mtime` does not). He also flags a related edge case: if a file is modified in the same second as the last commit, Git may continue to report no changes even after the mapping is released.

The email is exploratory rather than a patch submission. Harold asks whether this behavior is already known, how far the project wants to go for correctness, and whether others have experience with this on APFS. He links to an LLM-generated PR on his fork but explicitly does not request review. The impact is confined to APFS, and the proposed fix (checking generation number) would only incur overhead when files are memory-mapped.

This looks like a real, if niche, correctness issue. The report is clear and well-scoped, but the solution space is still open. If you work on macOS or care about filesystem edge cases, this thread is worth following.

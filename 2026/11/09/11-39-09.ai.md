This is an Outreachy proposal draft for a feature that adds configurable fetch ordering to promisor remotes in partial clones. The author, Hussain Sitamouwala, is seeking early feedback on the design before sending a formal patch series in week 2 of the internship.

The proposal targets a long-standing limitation in Git's partial clone implementation: when multiple promisor remotes exist, the order in which they are tried for missing objects is fixed (accepted remotes first, then others in config order, with `extensions.partialClone` last) and cannot be influenced by either the user or the server. Hussain plans to make this order configurable through three deliverables: (1) tests that lock in today's behavior, (2) a local configuration setting (`remote.<name>.priority`) to order remotes, and (3) a server-advertised priority field with documented precedence rules.

The design is thoughtful and well-scoped. It proposes an integer-based priority system where lower values are tried first, with stable sorting to preserve existing order for equal or unset priorities. The server advertisement would use an optional `priority=<n>` field in the existing promisor-remote capability protocol, with defensive parsing to handle untrusted input. The proposal explicitly considers edge cases (malformed values, duplicate fields, precedence between local and server settings) and includes a threat model section that would translate directly into test cases. Hussain also shows awareness of a competing patch that implements a different config shape (`promisor.fetchOrder`) and has a clear plan to adapt if that lands first.

The timeline is realistic for a 12-week internship, with design review happening in parallel with early implementation work. The proposal demonstrates strong preparation: Hussain has already contributed two patches to Git (one documenting the current promisor remote behavior, another converting `check-ref-format` to use `parse-options`), run experiments to verify the current behavior, and studied the relevant test files. The Outreachy-specific logistics (blog, weekly updates, communication plan) are all in place. This looks like a well-crafted proposal that addresses a real need in the partial clone subsystem.

This is the fifth and final patch in a performance-focused series targeting `git log --follow` for non-linear history. The patch addresses a severe regression introduced in commit 304812ed33 (June 2026), where following renames in merge-heavy repositories (e.g., linux.git) became prohibitively slow—specifically, a test case that previously took 28 seconds ballooned to 6 minutes and 43 seconds.

The core issue is that `log_tree_diff()` now diffs each merge against *all* of its parents with rename detection enabled, even when the path in question is unchanged relative to one parent. The fix adds a two-phase diff strategy: first, diff the merge against parents *without* rename detection to identify a "same" parent (where the path is unchanged). If such a parent exists, subsequent diffs against other parents are skipped unless renames are still needed—determined by checking whether the merge base has the path, whether the parent changed a file later dropped by the merge, or whether copy detection identifies the path as a rename/copy target. The patch also tweaks `remember_follow_pathspec()` to prefer paths that actually exist in the commit when children disagree.

The implementation touches only `log-tree.c`, adding ~140 lines of new logic (helper functions `tree_has_path`, `commit_has_path`, `follow_same_parent`, `follow_parent_changed_dropped_file`, `follow_has_rename_source`, and `follow_needs_renames`). The performance improvement is substantial: the linux.git test case now completes in 42 seconds, restoring near-parity with pre-regression performance. The patch carries Helped-by trailers from SZEDER Gábor and Patrick Steinhardt, suggesting prior review engagement. No test failures or edge-case regressions are mentioned, but the commit message does not explicitly state whether the change is behavior-preserving or introduces subtle differences in rename detection.

This is a bugfix patch in a six-part series that addresses a regression in `git log --follow` when tracking file history across merges. The issue occurs when a file is edited on a side of a merge that was *not* taken, and `--follow` fails to continue tracking the file's history. The author, Miklos Vajna, acknowledges feedback from Patrick Steinhardt pointing out that the original fix missed cases involving file *copies* (not just renames). The updated patch (now part of a v5 series) corrects this by expanding the rename detection logic to also handle copies, though this adds a modest performance cost (a 5-second slowdown in the test case).

The patch is part of a broader effort to improve `--follow` reliability, which has historically been fragile in merge scenarios. The commit message and discussion suggest the fix is well-motivated and now covers more edge cases, though the performance tradeoff is noted. If you care about accurate file history tracking or work with repositories that use merges heavily, this patch is worth watching—especially if you’ve encountered gaps in `--follow` output before. The series is still under review, but the core issue and its resolution appear sound.

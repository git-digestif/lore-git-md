This is a performance-motivated refactoring of the `--follow` logic in `git log`. The patch is the fourth in a five-part series that revisits how Git tracks file renames across merge commits when `--follow` is used.

The commit message explains that the current implementation (introduced in June 2026) works but is slow: a real-world test case (`git log --stat --follow -- include/linux/rsc_table.h` in the Linux kernel repository) regressed from 28 seconds to nearly seven minutes. The root cause is that the code diffs every merge against each of its parents with full rename detection, even when the parent does not yet contain the file being followed. Instead of piling on more special-case logic, the author simplifies the code first by removing the separate `propagate_follow_pathspec_to_parent()` helper and its loop, then moving the path-tracking logic directly into the main `log_tree_diff()` loop. The result is fewer calls to `diff_tree_oid()` and a clearer flow, although the patch itself does not yet restore the original performance—it merely sets the stage for the next patch in the series to do so.

The diff touches only `log-tree.c`, removing 55 lines and adding 41, for a net reduction of 14 lines. The key change is that the pathspec for each parent is now recorded immediately after the diff that detects the rename, rather than in a second pass. Merge commits are still diffed silently when `--follow` is active, but the logic is now unified with the rest of the diff machinery rather than bolted on afterward.

This looks like a well-motivated cleanup: the commit message is clear, the rationale is backed by a concrete performance regression, and the code changes are confined to a single file. The patch is part of an ongoing effort to make `--follow` usable on complex histories, so anyone interested in rename tracking or merge-handling performance may want to follow the rest of the series.

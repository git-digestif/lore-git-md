This is an Outreachy proposal draft from Hussain Sitamouwala for the project "Implement promisor remote fetch ordering." The proposal is thorough, well-structured, and clearly motivated.

The goal is to make the order in which Git fetches missing objects from promisor remotes configurable, both locally and via server advertisement. Today, the order is fixed (accepted remotes first, then others in config-file order, with `extensions.partialClone` last), which prevents users or servers from optimizing for cost, latency, or reliability. The proposal outlines three deliverables: (1) tests that lock in today’s behavior, (2) a local config setting (`remote.<name>.priority`) to control the order, and (3) a server-advertised priority field with documented precedence rules and defensive parsing.

Hussain has already contributed two patches to Git: one documenting the current promisor remote fetch order (accepted and queued by Junio) and another converting `check-ref-format` to use the `parse-options` API. These demonstrate familiarity with the codebase and review process. The proposal includes a detailed design section with trade-offs (e.g., config shape alternatives), a threat model for server-advertised values, and a clear testing plan. The timeline is realistic, with early design review and fallback options if a competing patch lands first.

The proposal looks serious and well-prepared. It addresses a real limitation in partial clones and is scoped appropriately for a three-month internship. The design choices (e.g., local config winning over server values, defensive parsing) are pragmatic and likely to be uncontroversial. Feedback from the list will probably focus on the config shape and precedence rules, but the proposal anticipates these discussions and plans to resolve them early. For anyone following partial-clone improvements, this is worth tracking.

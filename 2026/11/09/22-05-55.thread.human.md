This thread is about a subtle platform compatibility issue where Git’s change detection—based on file modification timestamps (`mtime`/`ctime`)—fails on macOS with APFS when files are modified via `mmap` without an explicit `msync()`. The problem arises because APFS does not update `mtime` on `mmap` writes, causing Git to incorrectly report "no changes" even when file contents have been altered. The issue persists until `munmap()` is called (updating `ctime` but not `mtime`) and can also affect same-second modifications.

Harold Hunt initially reported the issue, clarifying that it affects third-party tools (like text editors) that `mmap` mutable working-tree files, rather than Git’s own operations. Brian M. Carlson noted that Git’s internal `mmap` usage is unaffected because it only applies to immutable or atomically replaced files (e.g., packs, indexes). The discussion has since expanded to include Windows, where Johannes Sixt (Hannes) pointed out that Git’s `mmap` emulation also exhibits delayed timestamp updates due to API limitations (`FlushViewOfFile` does not update timestamps). This means the problem is not macOS-specific but could theoretically occur on Windows as well, though the practical impact remains limited to third-party tools.

The thread remains exploratory, with no patch or RFC proposed yet. Key open questions include whether the project should address this edge case for third-party tools, how to handle cross-platform consistency (e.g., a fix for macOS might not work on Windows), and what performance tradeoffs would be acceptable for any proposed solution (e.g., content hashing as a fallback). Harold floated the idea of checking APFS’s generation number as a potential fix, but no consensus has emerged. The discussion highlights the fragility of relying on `mtime` updates for `mmap` writes across platforms, even when behavior is technically POSIX-compliant.

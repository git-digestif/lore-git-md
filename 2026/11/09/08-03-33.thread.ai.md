Subject: [PATCH v5 0/5] log --follow: performance fix for non-linear history

Originating author: Miklos Vajna
Thread type: patch series

Core problem or goal
Restore performance of `git log --follow` on non-linear history after a severe regression introduced in Git v4.30.0 (commit 304812ed33, June 2026). The regression caused `--follow` to become unusably slow (e.g., 28s → 6m43s on linux.git) because the implementation diffed each merge commit against *all* parents with rename detection enabled, even when a parent lacked the tracked path.

Current status
Under review. This is the fifth iteration of the series, addressing all prior feedback from Patrick Steinhardt and SZEDER Gábor. No maintainer decision on merge status yet; no evidence of integration into `seen`, `next`, or `master`.

Key technical details
- Files touched: `log-tree.c` (primary), `t4219-log-follow-merge.sh` (tests)
- New helper functions in `log-tree.c`: `follow_same_parent`, `follow_needs_renames`, `follow_has_rename_source`
- Modified function: `remember_follow_pathspec` (handles disagreements between child commits about tracked path)
- Two-phase strategy: (1) fast diff without rename detection to identify a parent where the tracked path is unchanged, (2) full rename detection only against other parents if necessary
- Performance: linux.git test case reduced from 6m43s → 42s (near pre-regression baseline)
- Test coverage expanded for subtree merges, copy detection, and merges where one side edits the old path while the other renames it
- Subsystem: log subsystem only; no impact on other Git commands

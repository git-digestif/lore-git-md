Hussain Sitamouwala has circulated a draft Outreachy proposal to add user-configurable fetch ordering for promisor remotes in partial clones, targeting organizations that maintain multiple regional mirrors and need to prioritize cheaper or faster remotes. The proposal envisions a priority-based system controlled by local configuration (`remote.<name>.priority`, where lower values are tried first) and optionally by server-advertised priorities, replacing the current fixed ordering. No code has been posted yet; the thread remains at the design-document stage as the author seeks feedback before sending a formal patch series.

In response to a substantive review from Kaartic Sivaraam, Sitamouwala has acknowledged several corrections to make in a forthcoming v2. The author agrees to separate user-set configuration values from server-supplied priorities so they do not collide in the same config key, to treat the exact config shape and protocol field (`promisor.sendFields`) as open questions pending an RFC rather than foregone conclusions, and to clarify that planned patches 4 and 5 depend on that protocol RFC resolving first. Additional commitments include correcting merge-status wording, mapping implementation goals to deliverables more clearly, removing premature draft documentation, and adding missing references. The series would touch `promisor-remote.c`, `transport.c`, `remote.c`, and related documentation.

Key questions remain unresolved. The precedence rules between local user configuration and server-advertised priorities are still contested, with Sivaraam pressing for explicit separation of stored server values from user-set values to avoid ambiguity. Whether `promisor.sendFields` should support per-remote gating versus the current global design is also open. A competing patch using a `promisor.fetchOrder` configuration shape remains a potential conflict if it lands first. The proposal is currently under review with no integration status; the author is iterating on the design document before posting code.

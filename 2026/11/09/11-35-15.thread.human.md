This Outreachy proposal thread is shaping up as a design discussion for configurable promisor remote fetch ordering in partial clones. Hussain Sitamouwala, the author, has shared a detailed draft seeking feedback before sending a formal patch series. The goal is to replace the current fixed fetch order with a priority-based system controlled by local configuration (`remote.<name>.priority`) and optionally by server-advertised priorities, targeting users with multiple promisor remotes who need to prioritize cheaper or faster mirrors.

Kaartic Sivaraam has provided substantive feedback on the proposal, focusing on three key areas. First, he questions the precedence rules between local configuration and server-advertised priorities, suggesting the config shape might need adjustment to avoid ambiguity. Second, he flags protocol design details that need refinement, such as whether `promisor.sendFields` should support per-remote gating and requests clarification on an earlier review mentioned in the proposal. Third, he critiques the timeline and patch series plan, noting that the numbering of patches doesn’t clearly map to the deliverables and that the design discussion should be treated as an open question rather than a foregone conclusion. This feedback is constructive and specific, engaging deeply with the technical design and implementation plan.

The proposal is still in the design phase, with no code posted yet. The planned components include tests to lock in current behavior, local configuration via `remote.<name>.priority`, and server-advertised priority with documented precedence rules. A competing patch (`promisor.fetchOrder`) is noted as a potential conflict. Open questions remain around the config shape, protocol design, precedence rules, and edge case handling. The author has prior contributions to promisor remote documentation and is seeking feedback on these design aspects before proceeding with the protocol RFC and coding.

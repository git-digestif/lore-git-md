This thread is an Outreachy proposal by Hussain Sitamouwala to add user-configurable priority ordering for promisor remotes in partial clones, replacing Git's current fixed fetch order. The author has posted a v2 design document responding to substantive review from Kaartic Sivaraam, and no code has been sent yet. The central technical refinement in this revision is the concession that user-set local configuration and server-advertised priorities must be stored in separate config keys rather than sharing `remote.<name>.<field>`, because the existing `promisor.storeFields` mechanism writes server data into that namespace and could collide with hand-edited values.

The proposal preserves Git's existing two-pass fetch structure -- first trying server-accepted promisor remotes, then falling back to others with `extensions.partialClone` last -- but adds stable sorting by priority within each pass. The planned six-patch series splits into three infrastructure patches (trace2 events, baseline tests, and a behavior-preserving refactor) that are independent of the design decisions, and two feature patches (local config and server-advertised field handling) that are blocked on a future protocol RFC and maintainer decisions about config shape. A competing public patch using `promisor.fetchOrder` is noted as a potential conflict the author plans to address with a trade-off note.

What remains open is the exact config key names, whether local user values should override server-advertised ones outright (the author's recommendation) or vice versa (which bandwidth-conscious operators might prefer), per-remote gating for `promisor.sendFields`, and handling of negative or non-integer priority values. The author's earlier documentation patch describing current fetch order is cooking in `next` but not yet in `master`.

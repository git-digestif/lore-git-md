This is a bugfix in the UTF-8 handling subsystem, specifically the third patch in a four-patch v5 series from Dirk Gouders (the cover letter was not provided, so the series' overall goal is unknown from this email alone).

The patch addresses `utf8_strnwidth()` in `utf8.c`, which measures the display width of a string while optionally skipping ANSI escape sequences (SGR color codes). Previously, when `skip_ansi` was enabled, the function would advance past escape sequences in a loop but did not verify whether the pointer had reached or passed the end of the specified string boundary (`orig + len`). This meant that if an ANSI escape sequence ended exactly at or beyond the given length limit, the code would proceed to call `utf8_width()` on a position at or past the string terminator, potentially reading beyond the intended boundary.

The fix adds a bounds check immediately after the ANSI-skipping loop: if the `string` pointer has reached or exceeded `orig + len`, the function breaks out of the loop and returns the accumulated width. This ensures that `utf8_strnwidth()` respects the specified length even when escape sequences consume the remainder of the string.

The patch also adds a new unit test, `test_utf8_width__strnwidth_ansi()`, in `t/unit-tests/u-utf8-width.c`. The test exercises three corner cases with the string `"\033[31mhello"`: a length that ends inside the escape sequence (returning 3), a length that ends exactly at the sequence's end (returning 0), and a length that includes the first character after the sequence (returning 1). These tests verify that the boundary check prevents out-of-bounds reads while maintaining correct width calculations.

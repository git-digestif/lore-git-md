This is a follow-up ping on a high-severity bugfix patch for the index subsystem. Tanga Joris is asking the list to verify that their patch resolves the silent corruption and crash bug that occurs when both `core.splitIndex` and `index.skipHash` are enabled together.

The underlying patch addresses a regression introduced in `ee1f0c242e` (January 2023) where the shared index file was named after its trailing checksum, which becomes all zeros when `index.skipHash` is active. This caused the split index to record a null base OID, silently discarding entries from the shared index and later triggering a `BUG` crash in `wt-status.c` during `git status`. The fix ensures the shared index always includes its hash while still allowing the main index file to skip the hash for performance, and it adds two tests to `t/t1700-split-index.sh` covering the shared index hash behavior and entry preservation.

The bug report originated with Andy Koppe, who provided reproduction steps showing null OIDs and missing entries on Git v2.56.0. Tanga Joris identified the root cause and authored the fix, which touches `read-cache.c` by adding a `skip_hash` parameter to `do_write_index()` and `write_shared_index()`. The patch is narrowly scoped and well-motivated, targeting users of large repositories who rely on split-index or skipHash optimizations like `feature.manyFiles`.

As of this email, the patch remains under review with no maintainer response or integration branch assignment. Tanga is simply requesting that others test whether the fix resolves the corruption on their systems, which would help move the discussion toward potential inclusion.

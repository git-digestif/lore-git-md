This is a bugfix to the UTF-8 width calculation code, specifically the fourth and final patch in Dirk Gouders's v5 series.

The patch fixes `utf8_strnwidth()` in `utf8.c` so that it respects the caller-supplied `len` boundary when decoding multibyte characters. Previously the function called `utf8_width(&string, NULL)`, which allowed the decoder to read past the given boundary and consume bytes belonging to an incomplete multibyte sequence. Now it computes `remainder = orig + len - string` and passes `&remainder` as the boundary argument to `utf8_width()`, ensuring that a truncated sequence at the end of the buffer is not counted as a complete glyph and the function returns the expected width.

The commit adds two unit tests in `t/unit-tests/u-utf8-width.c` under the new test function `test_utf8_width__strnwidth_cjk_chopped()`. These verify that `utf8_strnwidth("三bytes long, 二columns wide", 1, 1)` returns 1 and that passing a length of 3 (which chops the 3-byte CJK character 三) returns 2, covering the case where the boundary invalidates a multibyte character.

This is the concluding patch of a four-patch v5 series; the earlier patches in the thread (not shown here) presumably addressed related aspects of the same boundary-handling logic or the SGR/ANSI skipping path. The change is small, well-targeted, and includes regression tests, suggesting it is ready for consideration.

Thread identity: bugfix series from Junio C Hamano fixing the `strbuf_getwholeline()` family in `strbuf.c`; thread type is a patch series (6 patches).

Core problem or goal: `strbuf_getwholeline()` and related functions return EOF when `feof()` is detected on the input stream without clearing the caller-supplied output `strbuf`, so the strbuf retains stale data from a previous read. This long-standing API contract violation has caused concrete misbehavior (and in some cases infinite loops) in several commands that reuse a strbuf across reads.

Current status: newly posted series, under review; no integration status reported. Patch 1 (mailinfo robustness) has been detailed on-list.

Key technical details: patch 1 makes `mailinfo` robust against the stale-buffer behavior by changing `read_one_header_line()` in `mailinfo.c` to return -1 on EOF (instead of 0), updating its callers in `mailinfo()` and `handle_boundary()` to loop only while the return value is positive and to call `handle_body()` only when the return is exactly 0, and adding a defensive `len &&` guard in `handle_filter_flowed()`; previously a header-only message with no terminating blank line caused the last header line to leak into the body via `handle_body()`, and a new test in `t/t5100-mailinfo.sh` verifies that a header-only message produces empty body and patch outputs. Patches 2--4 add failing tests demonstrating bugs in `git shortlog` (t4201-shortlog.sh), `git clean -i` (t7301-clean-interactive.sh), and `git fast-import` (t9300-fast-import.sh), with detailed commit-message walkthroughs of the failure modes; patch 5 implements the actual fix by clearing the strbuf upon EOF inside `strbuf_getwholeline()`; patch 6 adds regression tests for two additional infinite-loop issues in `clean` and `fast-import` that cannot be safely expressed as `test_expect_failure` before the fix. Files touched: `strbuf.c`, `mailinfo.c`, and test scripts t4201, t5100, t7301, t9300.

Open questions and loose ends: whether clearing the strbuf on EOF breaks any other callers that implicitly relied on the old (stale-preserving) contract; this is expected to be a focus of review discussion.

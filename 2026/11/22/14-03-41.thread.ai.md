Thread identity: bugfix series from Junio C Hamano fixing the `strbuf_getwholeline()` family in `strbuf.c`; thread type is a patch series (6 patches). All 6 patches have now been detailed on-list: patch 1 (mailinfo robustness), patch 2 (shortlog failing tests), patch 3 (clean -i failing test), patch 4 (fast-import failing test), patch 5 (the core fix), and patch 6 (regression tests for infinite loops). Junio has sent a follow-up email clarifying that he deliberately structured the series to demonstrate the bugs with `test_expect_failure` cases in patches 2-4 rather than inserting temporary local `strbuf_reset()` workarounds that would need reverting in patch 5, rejecting that alternative as awkward and wasteful.

Core problem or goal: `strbuf_getwholeline()` and related functions return EOF when `feof()` is detected on the input stream without clearing the caller-supplied output `strbuf`, so the strbuf retains stale data from a previous read. This long-standing API contract violation has caused concrete misbehavior (and in some cases infinite loops) in several commands that reuse a strbuf across reads.

Current status: newly posted series, under review; no integration status reported. Patch 5 of 6 implements the actual fix; patch 6 adds regression tests that depend on patch 5.

Key technical details: patch 1 makes `mailinfo` robust against the stale-buffer behavior by changing `read_one_header_line()` in `mailinfo.c` to return -1 on EOF (instead of 0), updating its callers in `mailinfo()` and `handle_boundary()` to loop only while the return value is positive and to call `handle_body()` only when the return is exactly 0, and adding a defensive `len &&` guard in `handle_filter_flowed()`; previously a header-only message with no terminating blank line caused the last header line to leak into the body via `handle_body()`, and a new test in `t/t5100-mailinfo.sh` verifies that a header-only message produces empty body and patch outputs. Patch 2 adds two `test_expect_failure` cases to `t/t4201-shortlog.sh` demonstrating bugs in `git shortlog` when reading from stdin: `read_from_stdin()` in `builtin/shortlog.c` reuses a strbuf named `oneline` across reads while scanning header lines, and when `strbuf_getline_lf()` hits EOF mid-line without clearing `oneline`, an incomplete `Author:` line at EOF causes the previous commit's subject to be recorded for the second commit, while an incomplete `Date:` (or similar) header at EOF causes that discarded header text to be treated as the commit subject; both tests expect corrected output (empty subject or empty output) but are marked as expected failures pending the fix in patch 5. Patch 3 adds a single `test_expect_failure` case to `t/t7301-clean-interactive.sh` demonstrating a bug in `git clean -id` (interactive ask mode): `ask_each_cmd()` in `builtin/clean.c` loops over deletion candidates reading user input into a reused strbuf named `confirm` via `git_read_line_interactively()` (which calls `strbuf_getline()`); when the user answers "y" to the first prompt without a trailing newline, the second read hits EOF without clearing `confirm`, leaving the stale "y" which is then treated as a fresh affirmative answer causing all remaining untracked files to be deleted; the test feeds `printf "a\ny"` to `git clean -id` and asserts that only the first file is removed, which currently fails and is marked `test_expect_failure` pending the fix in patch 5. Patch 4 adds a single `test_expect_failure` case to `t/t9300-fast-import.sh` (27 lines added, no source changes) demonstrating a tree-corruption bug in `git fast-import`: in `parse_new_commit()` (builtin/fast-import.c), after `parse_data()` reads a heredoc commit message, the delimiter line (e.g., `deleteall`) remains in `command_buf`; `skip_optional_lf()` then hits EOF setting `feof(stdin)`, and the subsequent `read_next_command()` uses `strbuf_getline_lf()` on `command_buf` which returns EOF without clearing the buffer; because `parse_new_commit()` ignores the EOF return and enters a `while (command_buf.len > 0)` loop, the stale `deleteall` string is re-parsed as a file-change command invoking `file_change_deleteall()` and discarding all files inherited from the parent commit. The test constructs a fast-import stream with two commits where the second uses `data <<deleteall` with the delimiter as the final line and no trailing blank line; after import `git ls-tree` should still list the file created in the first commit but currently does not; the test is marked `test_expect_failure` pending patch 5. Patch 5 modifies `strbuf.c` so that both `strbuf_getwholeline()` and `strbuf_getline()` call `strbuf_reset(sb)` when `feof(fp)` is detected, ensuring the output buffer is cleared on EOF rather than retaining stale data; this flips the `test_expect_failure` cases in `t/t4201-shortlog.sh`, `t/t7301-clean-interactive.sh`, and `t/t9300-fast-import.sh` (added in patches 2-4) to `test_expect_success`. The commit message acknowledges that this alters the long-standing behavior of the `strbuf_getwholeline()` family and argues that no reasonable caller would rely on observing previous strbuf contents after an EOF return; the one known in-tree dependent that needed protection was `git mailinfo`'s `handle_body()` path, which would have accessed `buf[len - 1]` on an empty buffer for header-only `format=flowed` messages, already hardened in patch 1. Patch 6 adds regression tests to `t/t7301-clean-interactive.sh` and `t/t9300-fast-import.sh` for two infinite-loop bugs that cannot be safely expressed as `test_expect_failure` before the fix (they would hang): the first test exercises `git clean -id` in filter-by-pattern mode where `filter_by_patterns_cmd()` in `builtin/clean.c` loops in a `for (;;)` reading patterns via `git_read_line_interactively()` into the reused `confirm` strbuf; without patch 5, a pattern like `*.out` entered without a trailing newline leaves stale content in `confirm` on the second iteration so the `if (!confirm.len) break;` check never fires and the loop re-applies the filter forever, whereas with patch 5 the strbuf is emptied on EOF and the loop breaks cleanly; the second test targets `git fast-import` where a commit stream ending with a `merge :2` line lacking a trailing LF causes `parse_merge()` to loop forever in its `while (skip_prefix(...))` loop because `read_next_command()` leaves the stale `merge :2` in the static `command_buf` on EOF, whereas with patch 5 `command_buf` becomes empty and the loop exits; both tests are written as `test_expect_success` because they only pass with patch 5 applied. Files touched: `strbuf.c`, `mailinfo.c`, `builtin/shortlog.c`, `builtin/clean.c`, `builtin/fast-import.c` (via test only in patch 4), and test scripts t4201, t5100, t7301, t9300.

Open questions and loose ends: whether clearing the strbuf on EOF breaks any other callers (in-tree or out-of-tree) that implicitly relied on the old stale-preserving contract; the patch 5 commit message asserts there are none, but this remains the likely focus of review discussion and is not yet confirmed by other reviewers.

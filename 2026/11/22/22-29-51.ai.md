This is a performance patch with an accompanying correctness fix, targeting the interaction between the untracked cache and the fsmonitor daemon in `git status`. Author Stepan Koltsov proposes skipping the `prep_exclude()` call inside `valid_cached_dir()` in `dir.c` when fsmonitor is enabled and the untracked-cache entry is still marked valid, since fsmonitor already invalidates cache entries when any file in the directory changes, including `.gitignore` files.

The patch also addresses an edge case in `invalidate_stale_dirs()`: after a trivial fsmonitor response (introduced in commit 1cf98cb4d9), cached directories are rechecked only against stat data, but editing a `.gitignore` in place does not change the directory's stat data. To catch this, the patch now invalidates any directory whose `exclude_oid` is non-null -- indicating it contains a `.gitignore` -- forcing it to be rescanned on the next status call. This handles the scenario where the daemon was stopped and restarted, missing the in-place edit.

Files touched are `dir.c`, `dir.h`, and `t/t7527-builtin-fsmonitor.sh`. The test additions cover two scenarios: a `.gitignore` edited while the daemon is stopped followed by a trivial response, and a `.gitignore` change reported normally by fsmonitor. Both verify that the untracked cache correctly picks up the new ignore rules.

On macOS with the builtin fsmonitor daemon, in a repository with roughly 89,000 directories and a warm untracked cache, `git status --untracked-files=all` reportedly drops from about 310 ms to 65 ms, with time spent in `read_directory()` falling from about 255 ms to 8 ms. The commit message notes an "Assisted-by: LLM" trailer.

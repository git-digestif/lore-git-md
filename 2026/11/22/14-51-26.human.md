This is a bugfix in the UTF-8 width calculation, sent as patch 3 of 4 in a v5 series (the cover letter was not provided, so the broader series goal is unclear from this email alone).

The patch fixes `utf8_strnwidth()` in `utf8.c` when the `skip_ansi` flag is set. Previously, the function would skip over ANSI escape sequences using `display_mode_esc_sequence_len_counted()` and then unconditionally call `utf8_width()` on whatever remained. If an escape sequence consumed the rest of the string up to the given length boundary, the pointer could advance to or past the end of the buffer, leading to reading beyond the intended string limit. The fix adds an explicit check after the skipping loop: if `string >= orig + len`, the loop breaks before attempting to measure a glyph.

The author, Dirk Gouders, adds unit tests in `t/unit-tests/u-utf8-width.c` that exercise exactly these boundary conditions -- for example, measuring a string with a leading SGR sequence (`\033[31m`) at lengths where the escape sequence ends precisely at the cutoff. The tests assert the expected widths (3, 0, and 1 columns respectively) to ensure the function returns sensible results when the visible text is cut short by an ANSI sequence.

The change is small, targeted, and includes test coverage for the corner case it addresses, which makes it look like a solid, well-crafted fix. Readers interested in the full context of the series would need to consult the cover letter for patches 1, 2, and 4.

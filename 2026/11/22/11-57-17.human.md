This is a cover letter for a seven-patch feature series (v15) that introduces a "limited fetch" mode to solve slow `git fetch` operations in shallow clones of large repositories. The core idea is to let a remote fetch only the branches that local branches actually track, rather than downloading every branch on the remote.

The series splits the concerns of *what* to fetch from *where* to store it. A new config key, `remote.<name>.fetchUpstreams`, explicitly opts in to fetching the upstream branches of local branches, while `remote.<name>.fetchRefmap` controls the destination namespace (the default for `--refmap`). The `git remote add --limited-fetch` flag sets both, and shallow repositories now default to this mode. This v15 iteration addresses earlier review feedback by replacing the implicit "infer from refmap" behavior of v14 with the explicit `fetchUpstreams` setting, which reviewers had argued was clearer when multiple smart-selection modes exist.

Two new foundational patches change how refmaps interact with refspecs: a command-line refspec with its own destination (`src:dst`) now ignores both `--refmap` and `fetchRefmap`, preventing dual storage, and `--refmap` now works even without command-line refspecs, applying instead to the configured `remote.<name>.fetch` entries. The series also fixes `git pull` so it no longer merges every tracked branch into the current one.

The implementation touches `builtin/fetch.c`, `builtin/remote.c`, `remote.c`, and adds extensive tests in `t5586-fetch-refmap.sh` and updates to `t5510-fetch.sh` and `t5505-remote.sh`, with shared helpers to reduce duplication. With the override semantics now resolved and the implicit-guessing concern addressed via explicit configuration, this looks like a well-structured candidate for `master` once final review nits are cleared.

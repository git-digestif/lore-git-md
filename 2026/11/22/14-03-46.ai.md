This is the core bugfix patch (5 of 6) in Junio C Hamano's series addressing the `strbuf_getwholeline()` API contract. It modifies `strbuf.c` so that both the `strbuf_getwholeline()` and `strbuf_getline()` implementations call `strbuf_reset(sb)` when `feof(fp)` is detected, ensuring the output buffer is cleared on EOF rather than retaining stale data from a previous read. This change fixes the concrete misbehaviors demonstrated in the preceding patches by allowing those `test_expect_failure` cases to become `test_expect_success`; the patch accordingly flips the tests in `t/t4201-shortlog.sh`, `t/t7301-clean-interactive.sh`, and `t/t9300-fast-import.sh` that were added in patches 2 through 4.

The commit message acknowledges that this alters the long-standing behavior of the `strbuf_getwholeline()` family: previously, callers could observe the previous contents of the strbuf after an EOF return, but the author argues that no reasonable caller would rely on this, since the normal expectation of `strbuf_getline()` is that the buffer is overwritten. The one known dependent that needed protection was `git mailinfo`'s `handle_body()` path, which would have accessed `buf[len - 1]` on an empty buffer for header-only `format=flowed` messages; that was already hardened in patch 1 of this series.

For future thread summarization: the key files touched are `strbuf.c` (the fix itself) and the three test scripts listed above. The old behavior was "return EOF without touching the strbuf"; the new behavior is "reset the strbuf to empty then return EOF." The likely point of contention in review will be whether any out-of-tree or in-tree callers implicitly depended on the stale-buffer behavior, though the commit message asserts there are none.

This is a test patch, the fourth in a six-patch bugfix series from Junio C Hamano addressing the `strbuf_getwholeline()` EOF behavior. It adds a single `test_expect_failure` case to `t/t9300-fast-import.sh` that demonstrates a tree-corruption bug in `git fast-import` when a heredoc commit message terminates exactly at end-of-stream.

The commit message provides a detailed code-path walkthrough of the failure: in `parse_new_commit()` (builtin/fast-import.c), after `parse_data()` reads a heredoc commit message, the delimiter line (e.g., `deleteall`) remains in `command_buf` because `parse_data()` breaks out upon matching it. `skip_optional_lf()` then hits EOF, setting `feof(stdin)`. The subsequent `read_next_command()` call uses `strbuf_getline_lf()` on `command_buf`, which returns EOF without clearing the buffer due to the `strbuf_getwholeline()` contract issue. Because `parse_new_commit()` ignores the EOF return value and enters a `while (command_buf.len > 0)` loop, the stale `deleteall` string is re-parsed as a file-change command, invoking `file_change_deleteall()` and discarding all files inherited from the parent commit.

The test scenario constructs a fast-import stream with two commits: the first creates a file named `file`, and the second uses a heredoc `data <<deleteall` where the delimiter `deleteall` appears as the final line with no trailing blank line. After import, `git ls-tree` should still list `file`, but currently it does not because the stale delimiter triggers the deleteall. The test is marked `test_expect_failure` pending the actual fix in patch 5, which will clear the strbuf on EOF inside `strbuf_getwholeline()`, causing `command_buf` to be emptied and the file-change loop to be skipped.

Files touched: only `t/t9300-fast-import.sh` (27 lines added). No source code changes in this patch. The bug relies on the specific interaction between heredoc parsing in `parse_data()`, the EOF handling in `strbuf_getwholeline()`, and the unchecked return value of `read_next_command()` in `parse_new_commit()`. Review discussion will likely focus on whether clearing the buffer on EOF in patch 5 could break other callers that might implicitly depend on the stale-buffer behavior.

This is a performance optimization for the untracked cache when fsmonitor is enabled. Stepan Koltsov's patch skips the expensive `prep_exclude()` call in `valid_cached_dir()` when fsmonitor is active and the cache entry is still valid, since the fsmonitor daemon already guarantees that no files -- including `.gitignore` files -- have changed in that directory. Previously, `git status` was matching every directory against exclude patterns and reading every `.gitignore` file even when fsmonitor had already confirmed the directory was unchanged.

The patch also addresses a subtle edge case: if a `.gitignore` file is edited in place while the fsmonitor daemon is stopped, the daemon's eventual "trivial response" does not detect this because editing a file does not change the stat data of its parent directory. The commit adjusts `invalidate_stale_dirs()` to also invalidate any directory that contains a `.gitignore` (tracked via `exclude_oid`), ensuring these directories are rechecked after a trivial response rather than being trusted based on stale stat data.

On macOS with the builtin fsmonitor daemon, in a repository with roughly 89,000 directories and a warm untracked cache, `git status --untracked-files=all` dropped from about 310 ms to about 65 ms, with time spent in `read_directory()` falling from about 255 ms to about 8 ms. The patch includes two new test cases in `t/t7527-builtin-fsmonitor.sh` covering both the trivial-response scenario and normal fsmonitor-reported `.gitignore` changes. The commit message is clear about the trade-off involved (re-reading directories with `.gitignore` files once per trivial response) and explains why the simpler approach was chosen over hashing the ignore files.

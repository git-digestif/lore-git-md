Thread identity: standalone single-patch bugfix (no series version) from Junio C Hamano to the Git mailing list, fixing `git mailinfo` header leakage.

Core problem or goal: when an input email contains only headers and no body, `mailinfo()` in `mailinfo.c` leaks the final header line (e.g. `Content-Type`) into the generated commit message instead of producing an empty body.

Current status: patch posted, under review; not queued in any integration branch.

Key technical details: the header-parsing loop in `mailinfo()` calls `read_one_header_line()` until it returns 0, assuming 0 means a blank/non-header line was read, then unconditionally calls `handle_body()` with that buffer. On header-only input, the lookahead `fgetc()` for header folding hits EOF on the last header, `strbuf_getline_lf()` returns EOF without resetting `line`, and the stale last header is passed to `handle_body()`. The fix makes `read_one_header_line()` return -1 on EOF/error instead of 0; both call sites are updated -- `mailinfo()` invokes `handle_body()` only on return value exactly 0, and `handle_boundary()` loops only while the return is greater than 0. The commit message explains why checking `feof()` directly in `mailinfo()` would be wrong (an incomplete non-header line without a preceding blank line also sets EOF while leaving valid data in `line`). A defensive `len &&` guard is added before the trailing-LF check in `handle_filter_flowed()` (noted as unnecessary but included for symmetry with the adjacent CR check). Files touched: `mailinfo.c` and `t/t5100-mailinfo.sh`. Regression test confirms a header-only message yields empty `msg` and `patch` outputs with no header content leaking.

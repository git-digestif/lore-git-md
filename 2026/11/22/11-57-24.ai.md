This is a feature patch, the seventh and final one in Harald Nordgren's v15 series on matching-inspired fetch mode, changing the default behavior of `git remote add` inside shallow repositories.

The patch modifies the `add()` function in `builtin/remote.c` to consult `is_repository_shallow(the_repository)` (newly including `shallow.h`) when the `--limited-fetch` flag was not explicitly given. In a shallow repository, unless `-t/--track` or `--mirror` is present, `git remote add <name> <url>` now defaults to limited-fetch semantics: instead of writing the wildcard `remote.<name>.fetch` refspec `+refs/heads/*:refs/remotes/<name>/*`, it sets `remote.<name>.fetchRefmap` to that wildcard and `remote.<name>.fetchUpstreams` to `true`, omitting `remote.<name>.fetch` entirely. This prevents a subsequent refspec-less `git fetch <name>` from negotiating history for every branch the remote offers, which previously caused slow or hanging fetches in shallow clones. The `--no-limited-fetch` flag explicitly disables this default and restores the old wildcard behavior; full (non-shallow) repositories continue to receive the traditional wildcard `fetch` refspec.

Old versus new behavior: previously `git remote add` unconditionally configured the wildcard fetch refspec regardless of repository depth; now the shallow-repository default swaps that for the two config keys introduced in patch 6/7, so only locally tracked upstream branches are fetched. Tests in `t/t5505-remote.sh` cover the shallow default (verifying both config keys are set, `remote.<name>.fetch` is absent, and a functional fetch only updates the tracked branch), the `--no-limited-fetch` override, the `-t` interaction in shallow repos, and confirmation that full repositories keep the wildcard refspec. Documentation in `Documentation/git-remote.adoc` describes the new shallow-repository default and the override flag.

This patch completes the seven-part series that decouples which refs are fetched from where they are stored via `remote.<name>.fetchRefmap` and `remote.<name>.fetchUpstreams`; it builds directly on patch 6/7, which added the explicit `--limited-fetch` CLI option that this patch now makes the default in shallow contexts. The series remains queued in `next` and is blocking `ch/remote-defer-follow-remote-head-validation` due to textual conflicts. The commit message clearly motivates the change, the tests exercise the relevant edge cases, and the implementation is a small, well-contained change to the remote-add logic.

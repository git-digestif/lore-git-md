Dirk Gouders has filed a bug report about two failing tests in `t7527-builtin-fsmonitor--daemon.sh` on `origin/master`: test 43 (`Matrix[uc:false][fsm:true] move_directory_up`) and test 56 (`Matrix[uc:true][fsm:true] move_directory_up`). His diagnostic work, now reinforced by a git bisect, pins the regression on commit `ce48de8b2c` ("fsmonitor: implement filesystem change listener for Linux"), the commit that introduced the Linux inotify backend. When the built-in fsmonitor daemon runs during those directory-move scenarios, it aborts with `BUG("double remove of watch for '%s'", w->dir)` at `compat/fsmonitor/fsm-listen-linux.c:144`, because the listener tries to remove the same directory watch twice while handling an upward directory move.

The crash log lands in a `core.*` file inside the test's temporary directory, which contaminates the `git status --porcelain=v1` output comparison and produces the two observed test failures. Gouders has Cc'd the authors of the introducing commit, signaling that he expects a fix to come from those who wrote the original Linux fsmonitor implementation rather than submitting one himself.

Nothing has been decided or fixed yet; the open item is how to resolve the double-remove of the directory watch in the Linux fsmonitor listener's `move_directory_up` handling, with any follow-up patch likely targeting the watch-removal logic around line 144 of `compat/fsmonitor/fsm-listen-linux.c`.

This is a feature patch, specifically v15 2/7 in Harald Nordgren's seven-patch series on matching-inspired fetch behavior. It implements the second half of the override semantics confirmed in the v14 review: `git fetch --refmap=<map> <remote>` now works even when no refspecs are given on the command line, rather than dying with the previous error "--refmap option is only meaningful with command-line refspec(s)".

The patch modifies `get_ref_map()` in `builtin/fetch.c` to remove the fatal check that aborted when `refmap.nr` was set without command-line refspecs. Instead, when configured `remote.<name>.fetch` refspecs are used to build the ref map, the new `drop_destinations()` helper clears each entry's `peer_ref` (the configured destination), and then `map_refs_without_dst()` -- introduced in patch 1/7 -- applies the command-line `--refmap` to those destination-less entries. The result is that `remote.<name>.fetch` still decides which refs are fetched, but they are stored through the supplied refmap rather than at their configured destinations, treating the command line as an override of configuration in the same way that explicit command-line refspecs override `remote.<name>.fetch`.

Documentation in `Documentation/fetch-options.adoc` is updated to describe that without command-line refspecs, `remote.<name>.fetch` values select what is fetched while the refs are stored through the `--refmap` specification. The test in `t/t5510-fetch.sh` is rewritten from expecting failure to verifying that `git fetch --refmap="refs/heads/*:refs/remotes/none/*" origin` fetches the configured refs but stores `main` at `refs/remotes/none/main` instead of its usual tracking branch, leaving the original `refs/remotes/origin/main` unchanged.

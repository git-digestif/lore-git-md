This is a bugfix to the `git mailinfo` plumbing command that prevents email headers from leaking into the generated commit message when the input email contains only headers and no body.

The bug lives in `mailinfo()` in `mailinfo.c`. The header-parsing loop calls `read_one_header_line()` until it returns 0, assuming that value means a blank or non-header line was successfully read into `line`, after which `handle_body()` is unconditionally invoked with that buffer. On header-only input, the lookahead `fgetc()` used for header folding hits EOF on the final header; the subsequent `strbuf_getline_lf()` then returns EOF early without resetting `line`, `read_one_header_line()` returns 0, and `mailinfo()` feeds the stale last header (such as `Content-Type`) into `handle_body()`, causing it to appear in the commit log.

The fix makes `read_one_header_line()` return -1 on EOF/error instead of 0, and updates both call sites to distinguish the two cases: `mailinfo()` now calls `handle_body()` only when the return value is exactly 0, while `handle_boundary()` loops only while the return is greater than 0. The commit message explains why checking `feof()` directly in `mailinfo()` would be wrong -- an incomplete non-header line without a preceding blank line also sets EOF while leaving valid data in `line`. A defensive `len &&` guard is also added before the trailing-LF check in `handle_filter_flowed()`, noted as unnecessary but included for symmetry with the adjacent CR check.

A regression test in `t/t5100-mailinfo.sh` confirms that a header-only message yields empty `msg` and `patch` outputs with no header content leaking through. The patch touches only `mailinfo.c` and the test script; as a focused edge-case fix from the maintainer with a clear reproduction, it appears well-crafted and ready for review.

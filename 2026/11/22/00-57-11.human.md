This is a maintainer's review reply in the ongoing discussion of Harald Nordgren's `--delete-integrated` patch series, specifically responding to the renaming of a helper function in patch 1.

Junio C Hamano is pushing back on the implication that the `branch.<name>.deleteMerged` config key -- and the `opted_out_of_delete_merged()` helper that checks it -- should serve as the opt-out mechanism for both the existing `--delete-merged` and the new `--delete-integrated` functionality. His "Hmph" signals mild concern: if the helper is named specifically for the delete-merged operation, it creates an impedance mismatch when reused for delete-integrated, yet creating a separate opt-out for each mode may be over-engineering. He explicitly wonders whether the project wants to go down the path of allowing people to opt out of `delete_integrated()` at all, leaving the question of whether `deleteMerged` is the right config key for the new flag -- or whether something more generic like `deleteDone` would be needed -- unresolved.

This is a substantive design question rather than a nitpick. It touches on the user-facing API surface: whether a single config key should govern all "delete when integrated" behaviors, or whether users need fine-grained control to exempt a branch from one mode but not the other. The thread summary notes this question has been open since v9, and this email shows it remains unanswered in v10, with the maintainer signaling that the current approach may need rethinking before the series can be considered ready.

This is a feature patch, specifically v15 patch 6/7 in Harald Nordgren's series introducing a matching-inspired fetch mode. It adds a `--limited-fetch` (and `--no-limited-fetch`) option to `git remote add` that configures the remote using the new `remote.<name>.fetchRefmap` and `remote.<name>.fetchUpstreams` keys established in the preceding patches, rather than the traditional wildcard `remote.<name>.fetch` refspec.

When `--limited-fetch` is given (and neither `-t`/`--track` nor `--mirror` is specified), `builtin/remote.c` writes `remote.<name>.fetchRefmap` set to `+refs/heads/*:refs/remotes/<name>/*` and `remote.<name>.fetchUpstreams` set to `true`, while deliberately omitting `remote.<name>.fetch`. This means a subsequent refspec-less `git fetch <name>` will only retrieve upstream branches that local branches actually track, as implemented in patch 5/7. The option is rejected with a fatal error if combined with `-t`/`--track` or `--mirror`, since those already explicitly define what to fetch.

The implementation lives in the `add()` function in `builtin/remote.c`, where a new `limited_fetch` variable initialized to `-1` (unspecified) is parsed via `OPT_BOOL`. The logic checks `limited_fetch == 1 && track.nr` and `limited_fetch == 1 && mirror` to die on conflicting flags, then branches to set the limited-fetch config keys instead of calling `add_branch()` for the fetch refspec. Tests in `t/t5505-remote.sh` verify that the option works in a full clone, that the two new config keys are set correctly, that `remote.<name>.fetch` is absent, and that combining `--limited-fetch` with `-t` fails. Documentation in `Documentation/git-remote.adoc` updates the synopsis and explains the new option.

This patch provides the user-facing convenience layer over the `fetchUpstreams` mechanism from patch 5/7, completing the series' goal of giving users explicit control over limiting fetches to tracked branches in shallow repositories. The series remains under review in `next`.

This is the final patch (7/7) in Harald Nordgren's v15 feature series that introduces a limited-fetch mode for shallow repositories. It makes `--limited-fetch` the default behavior of `git remote add` when run inside an existing shallow clone, unless the user explicitly passes `-t`, `--mirror`, or `--no-limited-fetch`.

The motivation is straightforward: previously, adding a second remote to a shallow repository would always install a wildcard `remote.<name>.fetch` refspec, causing a subsequent `git fetch` to negotiate and download history for every branch the remote has -- potentially hanging or taking a very long time on large repositories, which defeats the purpose of having cloned with `--depth` or `--single-branch` in the first place. By defaulting to the limited-fetch configuration (which sets `fetchRefmap` and `fetchUpstreams` instead of a full wildcard fetch refspec), the patch ensures that adding a remote does not by itself commit the user to fetching every branch.

Technically, the patch adds a check for `is_repository_shallow(the_repository)` in `builtin/remote.c` when the `--limited-fetch` option was not explicitly given. The new tests in `t/t5505-remote.sh` cover the key cases: a shallow clone keeps the explicit refspec when `-t` is used, a full clone retains the traditional wildcard, a shallow clone without flags gets the limited-fetch config keys and no `remote.<name>.fetch` entry, and `--no-limited-fetch` explicitly overrides the shallow default to restore the old behavior.

The patch is well-motivated and thoroughly tested, with documentation updated in `git-remote.adoc` to explain the new default and the override. As the closing piece of the series, it ties together the earlier work on `fetchRefmap` and `fetchUpstreams` into a sensible out-of-the-box experience for shallow repository users.

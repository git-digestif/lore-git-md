This is a substantive review of Erik Cervin-Edin's v4 feature series, which enables `-m`, `-F`, `-c`, and `-C` message options across all `--fixup` variants (plain, `amend:`, and `reword:`) in `git commit`. Phillip Wood approves of the series overall, specifically praising the new patch 1/3 that refactors `prepare_to_commit()` in `builtin/commit.c` to write the `--fixup` subject line up front in a block before the message-source chain, mirroring the existing `--squash` behavior; he notes this restructuring makes patch 2/3 significantly cleaner by eliminating the `!fixup_message` guards on the `-m` and `-F` arms.

The one remaining point of contention is in patch 3/3: Phillip observes that plain `--fixup` never opens an editor, which means combining it with `-c` currently behaves identically to `-C` (copying the message verbatim without editing). He suggests it would be preferable to preserve the normal semantics of `-c` under `--fixup` so that it actually launches an editor for modification, letting users who want no editing use `-C` instead. However, he explicitly states he has not investigated how difficult this would be to implement, and is willing to accept the series as-is with this behavior left as `#leftoverbits` if the fix proves tricky.

With this comment, the v4 series has addressed all prior feedback from earlier rounds, including Phillip's test hygiene concerns about editor invocation (now using `GIT_EDITOR=false` for `-C` cases and `GIT_EDITOR="echo edited >>"` for `-c` cases in `t/t7500-commit-template-squash-signoff.sh`). The series touches only `builtin/commit.c`, `Documentation/git-commit.adoc`, and the test suite, and remains production-ready pending this final semantic question about `-c` behavior with plain `--fixup`.

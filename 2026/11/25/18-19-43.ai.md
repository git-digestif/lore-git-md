This is the third patch in version 6 of Dirk Gouders's four-patch bugfix series targeting out-of-bounds reads in Git's UTF-8 display-width code, specifically within `utf8_strnwidth()` in `utf8.c`. The series as a whole fixes bounds handling in `utf8_strnwidth()` and `utf8_width()` so they respect their length arguments, with patch 1 (authored by Junio C Hamano) having introduced the length-based `display_mode_esc_sequence_len_counted()` helper that this patch relies upon.

The specific bug addressed here occurs when an ANSI escape sequence ends exactly at the buffer boundary `orig + len`. Previously, after `display_mode_esc_sequence_len_counted()` advanced the `string` pointer past a complete escape sequence, the loop would unconditionally call `utf8_width(&string, NULL)` on the remaining bytes -- even when `string` had reached `orig + len`, causing `utf8_width()` to read past the end of the valid buffer and return a spurious width. The commit message walks through a concrete example with `"\033[31mhello"` showing that `len = 5` (where the 5-byte escape sequence ends exactly at the limit) incorrectly returned width 1 instead of 0.

The fix restructures the escape-skipping loop to check `if (string >= orig + len) break;` immediately after the while-loop that consumes ANSI sequences, ensuring the function exits before calling `utf8_width()` when no bounded characters remain. This complements patch 4/4, which passes a `remainder` length to `utf8_width()` to handle chopped multibyte characters; the bounds check here remains necessary because `utf8_width()` would still read the byte at `orig + len` if called with a zero remainder.

Tests are added in `t/unit-tests/u-utf8-width.c` as `test_utf8_width__strnwidth_ansi()`, covering the boundary cases with `"\033[31mhello"` at lengths 4, 5, and 6 to verify widths of 3, 0, and 1 respectively. The test file also carries a TODO noting that `cl_assert_equal_i()` should become `cl_assert_equal_u()` if the width functions' return types change from `int` to `size_t` in the future.

Within the v6 series context, this patch incorporates Junio's requested rewording -- including the concrete escape-sequence example -- and represents continued convergence toward merge readiness after Junio described v5 as being in "a very good shape"; the series remains under review and has not been queued in any integration branch.

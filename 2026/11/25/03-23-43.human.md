This is a bugfix for the sequencer subsystem, constituting the first of two patches in Wonseok Oh's v2 series on `git cherry-pick` behavior on unborn (orphan) branches. The problem is that when picking multiple commits onto a branch where HEAD does not yet exist, `sequencer_pick_revisions()` in `sequencer.c` calls `repo_get_oid()` to resolve HEAD; on an unborn branch this call fails and leaves the local `oid` variable uninitialized. That garbage value was previously passed to `save_head()` and written to `.git/sequencer/head`, so `git cherry-pick --abort` would fail with "Could not parse object" or potentially move the branch pointer to an arbitrary commit instead of issuing the intended "cannot abort from a branch yet to be born" error from `sequencer_rollback()`.

The fix restructures the HEAD resolution block so that when `repo_get_oid()` fails, the code either errors out for reverts (preserving the existing "can't revert as initial commit" message) or explicitly clears `oid` to the null OID via `oidclr()`. This guarantees that `.git/sequencer/head` stores the null OID on unborn branches, letting `sequencer_rollback()` correctly recognize the unborn-branch state. The commit message identifies `0f974e2124` (2016) as the commit that introduced the uninitialized use, and the new test in `t/t3510-cherry-pick-sequence.sh` confirms that after a failed multi-pick on an orphan branch the sequencer head contains `$ZERO_OID`, that `--abort` fails with the exact expected message, and that HEAD remains unchanged.

As the lead patch of the v2 series, it incorporates earlier review feedback from Phillip Wood and Junio C Hamano, including tighter commit-message wording and a more robust test that greps for the specific abort error rather than relying on incidental stack contents. The change is small, well-motivated, and addresses a genuine undefined-behavior bug with appropriate test coverage; it is currently under review with no merge status reported.

This is a review-response email in the `GIT_COMMENT_STRING` feature thread, where Phillip Wood addresses Kristoffer Haugsbakk's feedback on his patch adding the new `git var` variable.

Wood agrees to reword the commit message from "comment character" to "comment string" for consistency with the variable name. On the documentation suggestion to mention `core.commentChar` and `core.commentString` in `Documentation/git-var.adoc`, he pushes back gently: the purpose of `GIT_COMMENT_STRING` is to let scripts query the effective comment string without caring about config intricacies, and he notes that sibling variables like `GIT_DEFAULT_BRANCH` do not reference their config sources, while `GIT_EDITOR` and `GIT_PAGER` do. As a compromise he proposes wording like "as set by `core.commentString`" rather than a full cross-reference, and reports that he has instead added a note to the `core.commentString` documentation in `git-config` pointing readers to `git var GIT_COMMENT_STRING`.

Haugsbakk's review confirms the test coverage in `t/t0007-git-var.sh` is adequate: the tests verify the default `#` output and that a custom `core.commentString` (tested with `%%`) correctly overrides `core.commentChar` (tested with `:`), matching the existing last-one-wins semantics between those two config keys. He also surfaces an edge case: setting `core.commentString` to an empty value causes `git var GIT_COMMENT_STRING` to abort with `fatal: unable to parse 'core.commentstring' from command-line config` and a non-zero exit status, because the global `comment_line_str` fails to initialize during config parsing rather than falling back to a default.

Technically, the patch touches `builtin/var.c` (adding a `comment_string()` helper that returns `xstrdup(comment_line_str)` and registering it in the `git_vars[]` table), `Documentation/git-var.adoc`, and `t/t0007-git-var.sh`. No merge status is indicated; the exchange is constructive with no blocking objections, leaving the patch under review.

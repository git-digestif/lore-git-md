This is a cover letter for a two-patch bugfix series (v2) targeting the sequencer subsystem, specifically `git cherry-pick` behavior when started on an unborn (orphan) branch. The series modifies `sequencer.c` and adds regression tests to `t/t3510-cherry-pick-sequence.sh`.

Patch 1 addresses the core bug: when `sequencer_pick_revisions()` in `sequencer.c` resolves HEAD via `repo_get_oid()` and the branch is unborn, the call fails and leaves the local `oid` uninitialized; previously this garbage value was passed to `save_head()` and written to `.git/sequencer/head`, causing `git cherry-pick --abort` to fail with "Could not parse object" or undefined behavior instead of the intended "cannot abort from a branch yet to be born" error from `sequencer_rollback()`. The fix calls `oidclr(&oid, r->hash_algo)` when `repo_get_oid()` fails (except for `REPLAY_REVERT`, which keeps its own initial-commit error), ensuring the null OID (`$ZERO_OID`) is stored so `sequencer_rollback()` correctly detects the unborn-branch case. The commit message now cites `0f974e2124` (2016) as the commit that introduced the uninitialized-variable use, describes general undefined-behavior failure modes rather than anecdotal builds, and removes filler text, per feedback from Phillip Wood and Junio C Hamano.

Patch 2 is new in v2 and addresses the related `.git/sequencer/abort-safety` file: on an unborn branch it now stores the null OID instead of leaving the file empty, as Phillip Wood suggested, for consistency with the `.git/sequencer/head` representation and backwards compatibility with older Git versions.

The test in patch 1 has been reworked per Junio C Hamano's suggestion: it now attempts to cherry-pick `initial picked` (where the first commit succeeds, birthing HEAD, and the second fails), then verifies that `.git/sequencer/head` contains `$ZERO_OID`, that `git cherry-pick --abort` fails with the exact message "cannot abort from a branch yet to be born" (checked via `test_grep`), and that HEAD remains where it was. The cover letter notes the test could still pass coincidentally if stack memory happens to be zeroed.

The series is under review with no integration status reported; the author has incorporated the requested commit-message and test changes from v1.

This is a two-patch bugfix series (v2) targeting the sequencer subsystem, specifically `git cherry-pick` behavior when picking onto an unborn (orphan) branch. The cover letter summarizes changes since v1: the commit message has been reworded to cite commit `0f974e2124` as the origin of the bug and to clarify the relationship between the null OID and `sequencer_rollback()`'s unborn-branch check, and a second patch has been added to make `.git/sequencer/abort-safety` also store the null OID for consistency.

The core fix in patch 1 modifies `sequencer_pick_revisions()` in `sequencer.c` to explicitly clear the saved HEAD OID to the null OID via `oidclr()` when `repo_get_oid()` fails to resolve HEAD on an unborn branch. Previously the uninitialized `oid` was written to `.git/sequencer/head`, causing `git cherry-pick --abort` to fail with a confusing "Could not parse object" error or, worse, to move the branch to a garbage commit. With the null OID saved, `sequencer_rollback()` correctly detects the unborn case and reports "cannot abort from a branch yet to be born".

The reworked test in patch 1 now allows the first pick to succeed so that HEAD is born before the sequence stops, then verifies that `.git/sequencer/head` contains `$ZERO_OID` and that `--abort` fails with the expected message while leaving HEAD intact. This addresses Junio C Hamano's earlier concern that the original test might pass coincidentally if stack memory happened to be zeroed. Patch 2 extends the same null-OID representation to the abort-safety file, as suggested by Phillip Wood.

The series looks well-motivated and carefully crafted, with the commit message now providing proper historical context and the test hardened against false positives. It is currently under review with no integration status reported; both Phillip Wood and Junio C Hamano had previously endorsed the direction, and this v2 incorporates their feedback on wording and test robustness.

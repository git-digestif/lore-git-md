This is the final patch (7/7) of Harald Nordgren's v16 feature series, making the new limited-fetch mode the default behavior for `git remote add` in shallow repositories.

The patch modifies `add()` in `builtin/remote.c` so that when neither `--limited-fetch` nor `--no-limited-fetch` is given explicitly, the command checks `is_repository_shallow()`. In a shallow clone, `git remote add` now defaults to limited-fetch semantics -- writing `remote.<name>.fetchRefmap` and `remote.<name>.fetchUpstreams` instead of the traditional wildcard `remote.<name>.fetch` refspec -- unless the user passed `-t`/`--track` or `--mirror`, which retain their existing behavior. Full (non-shallow) repositories are unaffected and still get the wildcard refspec by default. The `--no-limited-fetch` flag explicitly opts out, preserving the old behavior for anyone who wants it.

This closes the loop on the series' core motivation: previously, adding a second remote to a shallow clone would silently configure a wildcard fetch, causing the next `git fetch` to negotiate and download every branch on that remote -- potentially hanging or taking a very long time on large repositories, and defeating the purpose of having cloned shallow in the first place. With this patch, that footgun is removed by default in shallow clones.

The change is well-tested: four new tests in `t/t5505-remote.sh` verify that a shallow clone defaults to limited-fetch (and actually fetches only the tracked branch), that `-t` still forces an explicit refspec, that a full clone keeps the wildcard, and that `--no-limited-fetch` overrides the shallow default. Documentation in `Documentation/git-remote.adoc` is updated to describe the new default. As with the rest of the series, this remains under review and has not yet graduated to `master`.

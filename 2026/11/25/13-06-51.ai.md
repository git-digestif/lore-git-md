This is a discussion reply in the ongoing RFC thread about user-initiated recovery from stale `index.lock` files, responding to Tanga Joris's safety concerns. Steve argues that a dedicated, explicitly user-invoked command could safely remove a stale lock by performing the PID liveness check itself -- using the sidecar file written by `core.lockfilePid` (such as `index~pid.lock`) -- combined with a brief wait, something that manual removal cannot do. He contends that the current manual workflow of deleting `index.lock` by hand offers no opportunity to apply such safety checks before the file is removed.

The proposal builds on mechanisms that already exist: since Git 2.54, `core.lockfilePid` records the lock holder's PID in a sidecar file and reports liveness when a command fails to acquire the lock, while Jun Wu's `core.indexLockTimeout` series currently in `seen` addresses only the waiting portion of the request. Steve's suggestion would consolidate these behaviors into a single recovery command that waits, checks whether the recorded PID is still running, and removes the lock only when the liveness check passes.

Tanga Joris's earlier objections remain pertinent to this refinement: PID reuse can cause a dead process to appear alive, and on network filesystems such as NFS the PID sidecar carries no information about locks legitimately held by other hosts. Steve's framing of an explicit user command rather than automatic background removal may address Junio's previously expressed wariness about encouraging lock deletion, but the underlying reliability hazards of PID-based liveness checks across processes and machines persist.

No patch is attached in this email; the thread remains open on whether any built-in mechanism can reliably determine lock staleness given these cross-process and cross-machine hazards. Future discussion will likely weigh whether a user-invoked command with built-in checks offers sufficient safety over the current manual workflow, or whether the NFS and PID-reuse edge cases make any form of lock removal too risky to automate.

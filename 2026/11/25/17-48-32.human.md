This is patch 4 of 5 in Ravi Mistry's v5 series hardening Git's HTTP transport against transient server failures, and it extends retry support to the POST requests that actually carry fetch, clone, and partial-clone data. Until now, only GET requests benefited from `http.maxRetries`; `post_rpc()` in `remote-curl.c` would abort immediately on a 429 or 5xx. The patch extracts the wait-and-sleep logic from `http_request_recoverable()` into a shared `http_retry_wait()` helper and calls it from `post_rpc()`, but only for read-only services: `can_retry_rpc()` whitelists `git-upload-pack` and `git-upload-archive` while explicitly excluding `git-receive-pack`, since retrying a push after a 502 could duplicate processing on the remote.

The patch also fixes several correctness details that surfaced in earlier review rounds. Error reporting is now deferred via `report_rpc_error()` so the "RPC failed" message appears only after retries are exhausted or for non-retryable failures, and when retrying a gzipped request the `Content-Encoding: gzip` header is re-appended to the curl handle. Most notably for v5, the `struct slot_results results` variable is now cleared with `memset` before each `run_one_slot()` call in both `post_rpc()` and `probe_rpc()`, addressing Junio C Hamano's concern that a failed `start_active_slot()` could otherwise leak stale HTTP status or `Retry-After` values from a previous attempt into the error report.

The commit message is clear about motivation, and the test coverage is thorough: new cases in `t/t5584-http-429-retry.sh` verify that protocol v2 POSTs retry 429 and 502, that partial-clone promisor blob fetches retry transient 502s, that gzipped POSTs preserve their encoding across retries, and that `git push` is never retried on 429 or 502. The series as a whole remains under review; this patch resolves the last code-level questions raised in v4, leaving only Junio's final decision on the series' integration.

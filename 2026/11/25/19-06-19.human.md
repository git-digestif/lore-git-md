This is the second patch in v16 of Harald Nordgren's seven-patch series introducing a limited-fetch mode for shallow repositories. Specifically, it changes `git fetch --refmap` so that the option no longer dies when no refspecs are given on the command line; instead it applies the refmap to the refspecs configured in `remote.<name>.fetch`, letting the configuration decide what is fetched while storing the results through the supplied map rather than at the configured destinations.

The patch spells out several semantic details. Tags are followed when the fetched refs end up stored somewhere, so `--refmap=""` follows none. `--prune` leaves the configured destinations untouched because this fetch does not store there, and destinations that come from the refmap are likewise not pruned. The option is still rejected when there is nothing to map, such as when fetching from a bare URL with no configured refspecs. Command-line refspecs with non-empty destinations still bypass the refmap and store only at their explicit targets.

Under the hood, the change adds a `drop_destinations()` helper that clears `peer_ref` on refspec items to make them destination-less before refmap application. In `get_ref_map()` within `builtin/fetch.c`, the old fatal error is replaced by logic that feeds configured fetch entries through the refmap when no command-line refspecs are present, and `do_fetch()` is adjusted so that `prune_refs()` skips the configured destinations when `--refmap` is active without CLI refspecs. The `*autotags` computation is also timed so tags are followed only when refs are actually stored.

This patch directly addresses three concerns Junio C Hamano raised during his review of v15: it rejects `--refmap` again when the remote has nothing configured to fetch, it follows tags when a refspec-less fetch stores refs through the refmap (while `--refmap=""` follows none), and it prevents `--prune` from touching the configured destinations when `--refmap` redirects storage elsewhere. Tests in `t/t5510-fetch.sh` cover the new storage behavior, tag following, pruning, and the rejection case.

Within the broader series, this patch builds the override semantics that later patches use to implement `remote.<name>.fetchRefmap` and the `fetchUpstreams` mechanism. The series remains under review; v15 was previously queued in `next`, and this v16 supersedes it while awaiting final maintainer sign-off.

This is a substantive review from Junio C Hamano of the first patch in Dominik Maier's two-patch v2 series, which fixes prefix stripping for extra and virtual files in `git archive --format=zip`. The review engages directly with the code changes in `archive-zip.c` and `archive.c` rather than offering only cosmetic feedback.

Junio first corrects a minor wording point in the commit message: Dominik had referred to "worktree gitattributes," but Junio notes that by default `parse_treeish_arg()` directs attribute lookups to the index via `GIT_ATTR_INDEX`, consulting worktree attributes only when `--worktree-attributes` is passed, so saying simply "gitattributes" would be more accurate. He confirms this does not affect the conclusion.

On the code itself, Junio observes that the new NULL check for `path` in `entry_is_binary()` (`archive-zip.c`) is functionally redundant because `userdiff_find_by_path()` already returns NULL for a NULL path. The only practical effect is avoiding the one-time initialization of the static `attr_check` inside `userdiff_find_by_path()` when only virtual files are checked. He suggests that swapping the `!path` check with the `attr_check` initialization inside `userdiff_find_by_path()` might be a slightly more effective optimization, though he notes the current approach is acceptable either way, as both correctly fall through to `buffer_is_binary()` with the default driver.

Regarding the change in `write_archive_entries()` (`archive.c`) that sets `args->base = NULL` and `args->baselen = 0` for `--add-virtual-file` entries, Junio confirms this prevents `write_zip_entry()` from performing the invalid `path + args->baselen` arithmetic and attribute lookup. He points out that mutating these fields inside the loop leaves them pointing at the last extra file's prefix (or NULL) when the function returns, but notes this is currently safe because no callers in `archive-zip.c`, `archive-tar.c`, or `write_archive()` inspect them afterward, and `extra_file_info_clear()` runs only after `write_archive()` finishes. He suggests that saving and restoring them around the loop might prevent surprising future callers.

Junio concludes with "Overall, nicely done," indicating the patch addresses the out-of-bounds pointer issue cleanly and the discussion has converged without outstanding objections. The series remains under review with no merge status stated.

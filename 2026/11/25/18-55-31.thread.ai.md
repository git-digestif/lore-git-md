Thread identity: complete three-patch bugfix series (v1) authored by Harald Nordgren via GitGitGadget, posted as thread root with cover letter and patches 1/3, 2/3, and 3/3. Thread type: patch series.

Core problem or goal: `git remote` currently accepts invalid branch names in `git remote add -t`, `git remote add -m`, and `git remote set-branches`, persisting malformed refspecs to configuration that break every subsequent fetch on that remote. The series proposes validating branch names up front in all three subcommands so the command rejects the name before any configuration is written. Patch 1/3 implements validation for the `-t`/`--track` option of `git remote add`; patch 2/3 extends the same validation to `git remote set-branches`; patch 3/3 addresses `git remote add -m`, which previously validated its `-m` argument only after the remote had been created and a network fetch attempted, leaving a half-configured remote behind when given a bad name like `@{u}`.

Current status: series posted as v1, under review. Base commit is 6de20f6092dcf9bdb1c8efe03db4b70c82b423dd. All three patches have been posted; the series is complete.

Key technical details: touches `builtin/remote.c` and `t/t5505-remote.sh`. All three patches use a new static function `validate_tracked_branchname()` in `builtin/remote.c` which constructs a candidate ref name by prefixing the user-supplied branch name with `refs/heads/` (normal mode) or `refs/` (mirror mode), then calls `check_refname_format()` with the `REFNAME_REFSPEC_PATTERN` flag. On failure it calls `die()` with the message "'%s' is not a valid branch name". Patch 1/3 invokes this in the `add()` function inside a loop over every entry in the `track` string list, before the remote name and URL are processed or any configuration is written. Patch 2/3 invokes the same helper in `set_remote_branches()` within `builtin/remote.c`, looping over every branch name argument before `remove_all_fetch_refspecs()` executes or any configuration is written, so that a single invalid name like `@{u}` causes the command to `die()` while leaving the remote's existing `remote.<name>.fetch` entries untouched. Patch 3/3 adds an up-front check in the `add()` function: when the `master` variable is set (from the `-m` option), it constructs `refs/heads/<name>` in a `strbuf` and calls `check_refname_format()` on it; on failure it `die()`s before any remote configuration is written. Test coverage in `t/t5505-remote.sh` adds a `test_expect_success` block for patch 1/3 running `git remote add -t "@{u}" badtrack bar`, expecting the fatal error and verifying via `test_must_fail git config get remote.badtrack.url` that no remote configuration was persisted; patch 2/3 adds a test that clones a repository, captures the current `remote.origin.fetch` values, verifies that both `git remote set-branches origin main "@{u}"` and `git remote set-branches --add origin "@{u}"` fail with the expected error message, and confirms via `git config --get-all remote.origin.fetch` that the configuration remains byte-for-byte identical to the pre-command state; patch 3/3 adds a test running `git remote add -m "@{u}" badmaster bar`, expecting the fatal error, and verifying via `test_must_fail git config get remote.badmaster.url` that no remote was persisted.

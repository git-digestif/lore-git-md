This is the second patch in a two-part feature series (v2 2/2) that adds a `--filter-to-loose=<directory>` option to `git repack`. While the first patch handles objects that live in packfiles, this one closes the gap for loose objects: when `--filter` excludes a loose object, `git repack --filter-to-loose` now copies that object into the destination directory as a loose file, so the destination receives the complete set of filtered-out objects rather than just those that happened to be packed.

The patch adds `move_loose_filtered_objects()` and `remove_moved_loose_objects()` in `repack-filtered.c`, wired into `builtin/repack.c` so the copy happens after the filtered pack is written and the source removal happens later only when `-d` is given. It skips objects that already exist in the destination (verified by inode comparison in the tests), creates leading directories as needed, and writes via a temporary file with `finalize_object_file()` to avoid corruption. If anything fails, the source repository is left untouched, which the new tests in `t/t7700-repack.sh` verify explicitly.

The tests cover the main scenarios: copying loose objects to the destination, leaving source copies in place without `-d`, removing them with `-d`, not rewriting an identical object already in the destination, and recovering cleanly when the copy fails (no partial state, no `.tmp-*` leftovers, source packs intact). Documentation in `Documentation/git-repack.adoc` notes the new behavior.

The series remains under review; v2 incorporates earlier feedback from Junio C Hamano on directory validation, relative path resolution, and a double-close bug, and this patch extends that hardening to the loose-object path.

This is a bugfix patch, specifically the first of a three-patch series that hardens `git remote` subcommands against invalid branch names. The series as a whole targets `git remote add -t`, `git remote set-branches`, and `git remote add -m`; this particular email implements validation only for the `-t`/`--track` option of `git remote add`.

The patch introduces a new static function `validate_tracked_branchname()` in `builtin/remote.c`, which constructs a candidate ref name by prefixing the user-supplied branch name with either `refs/heads/` (normal mode) or `refs/` (mirror mode), then calls `check_refname_format()` with the `REFNAME_REFSPEC_PATTERN` flag. If the resulting string is not a valid refspec pattern, the function calls `die()` with the message "'%s' is not a valid branch name". This validation is invoked in the `add()` function inside a loop over every entry in the `track` string list, before the remote name and URL are processed or any configuration is written, so a typo or shell expansion like `@{u}` causes the command to fail without creating the remote at all.

Test coverage is added to `t/t5505-remote.sh` with a new `test_expect_success` block that runs `git remote add -t "@{u}" badtrack bar`, expects the fatal error message, and verifies via `test_must_fail git config get remote.badtrack.url` that no remote configuration was persisted.

The patch is based on commit `6de20f6092dcf9bdb1c8efe03db4b70c82b423dd` and is currently under review as v1 of the series; the subsequent two patches (not yet summarized here) are expected to apply the same validation pattern to `set-branches` and `add -m`.

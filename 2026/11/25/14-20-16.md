On Tue, 24 Nov 2026, Phillip Wood wrote:

> On 23/11/2026 22:13, Johannes Schindelin via GitGitGadget wrote:
> > From: Johannes Schindelin <johannes.schindelin@gmx.de>
> >
> > Accumulating the output count in `write_in_full()` can overflow because
> > it counts via a `ssize_t` variable which can overflow for valid `size_t`
> > sizes passed as input.
> >
> > Since this function either completes the requested count or fails,
> > callers already know how many bytes were written on success. Let's just
> > return status instead, so the total transfer size need not fit in
> > `ssize_t`.
>
>
> This makes perfect sense and the changes in this patch all look good. Looking
> at how the callers of write_in_full() use the return value, there are a few we
> might want to tweak.
>
> In config.c write_section() and write_pair() both return the result of
> write_in_full(). All of the callers of those functions are only interested in
> whether the return value was negative, so there is no problem with the change
> in behavior, but we might want to change the return value to an int to match
> the new prototype of write_in_full().
>
> In entry.c:write_entry() and parallel-checkout.c:write_pc_item_to_fd() we're
> still using a ssize_t to store the return value even though it is now an int.
>
> In odb/streaming.c:odb_stream_blob_to_fd() we're also storing the return value
> in a ssize_t. Unlike the cases above we can simply avoid storing the value at
> all.
>
> One final note - in refs.c:transaction_hook_feed_stdin(),
> sequencer.c:pipe_from_strbuf() and transport.c:pre_push_hook_feed_stdin()
> we're storing the result in an int and then checking if it is negative, so
> this patch actually fixes potential bugs in those callers.


Great call-out! I adjusted the callers accordingly.

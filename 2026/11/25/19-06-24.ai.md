This is the final patch (7/7) of Harald Nordgren's v16 series implementing limited-fetch semantics for shallow repositories. It modifies `git remote add` so that, when run inside a shallow repository without explicit `-t`/`--track`, `--mirror`, or `--limited-fetch`/`--no-limited-fetch` flags, it defaults to writing `remote.<name>.fetchRefmap` and `remote.<name>.fetchUpstreams` instead of the traditional wildcard `remote.<name>.fetch` refspec.

The change lives in the `add()` function in `builtin/remote.c`: the existing `use_limited_fetch` boolean now evaluates to true when `limited_fetch == -1` (unset) and `is_repository_shallow(the_repository)` returns true. This means a shallow clone that adds a second remote will no longer negotiate history for every branch on that remote during subsequent `git fetch` calls unless the user explicitly opts out with `--no-limited-fetch`. Full (non-shallow) repositories retain the old wildcard behavior by default.

Tests in `t/t5505-remote.sh` verify four scenarios: adding a remote with `-t` in a shallow repo still writes an explicit refspec; adding a remote in a full repo writes the wildcard `remote.<name>.fetch`; adding a remote in a shallow repo without flags writes the refmap and fetchUpstreams config and omits `remote.<name>.fetch`, with a functional check that `git fetch` only updates tracked upstreams; and `--no-limited-fetch` in a shallow repo restores the wildcard refspec. Documentation in `Documentation/git-remote.adoc` describes the shallow-repository default and the `--no-limited-fetch` override.

This patch completes the series' goal of preventing `git remote add` in shallow clones from silently defeating the shallow clone's purpose by fetching every remote branch.

This is a bugfix patch (specifically hardening against integer overflow and undefined behavior) and the fourth of five in Johannes Schindelin's v3 series addressing Coverity-flagged arithmetic issues. It introduces a new `read_in_full_or_error()` wrapper that returns a simple 0/-1 status instead of a byte count, allowing callers to handle files larger than `ssize_t` can represent without risking overflow in the return value. The existing `read_in_full()` is reimplemented on top of a shared static helper and now triggers a `BUG()` abort if asked to read more bytes than `ssize_t` can hold, signaling a caller programming error rather than silently truncating.

The patch migrates six call sites -- in `builtin/blame.c`, `combine-diff.c`, `dir.c`, `grep.c`, `refs/packed-backend.c`, and `strbuf.c` -- from comparing the old `ssize_t` return against the requested size to using the new Boolean-style function. `strbuf_read()` additionally clamps its requested read size to `SSIZE_MAX` before calling `read_in_full()`. The change is accompanied by new clar unit tests in `t/unit-tests/u-wrapper.c` covering successful reads, empty reads, short reads, and bad file descriptors.

Within the broader thread, this v3 iteration incorporates Junio C Hamano's earlier commit-message feedback and sits alongside the other patches that harden `archive-tar.c`, `http.c`, `wrapper.c` write paths, and `date.c`. The series remains under review; while Junio has approved several individual patches in prior versions, the v3 repost awaits his final look before queuing. The contribution looks thorough: it includes test coverage, clearly documents the `BUG()` contract for oversized counts, and systematically updates all in-tree callers that did not need the byte count.

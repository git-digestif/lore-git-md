This is patch 2/5 of Ravi Mistry's v5 series hardening Git's HTTP transport, specifically adding exponential backoff for 429 responses when the server omits a `Retry-After` header. It is unchanged from v4 and was explicitly approved by Junio C Hamano.

The patch modifies `handle_rate_limit_retry()` in `http.c` to accept a new `size_t attempt` parameter representing the 1-based retry count, computed at the call site in `http_request_recoverable()` as `(size_t)(http_max_retries - rate_limit_retries)`. When no `Retry-After` header is present, the function now computes the delay as `http.retryAfter * 2^(attempt - 1)` instead of returning the fixed `http.retryAfter` value, producing a sequence of 1s, 2s, 4s, etc. (when `http.retryAfter=1`). The doubling loop includes an overflow guard (`if (delay >= http_max_retry_time - delay)`) that clamps the result to `http.maxRetryTime` rather than wrapping, and the result is capped at `http.maxRetryTime` instead of causing immediate failure as an explicit header value would. An explicit `Retry-After` header continues to take precedence over the computed backoff.

Documentation in `Documentation/config/http.adoc` updates `http.retryAfter` to describe the doubling behavior and clarifies that `http.maxRetryTime` caps exponentially backed-off delays rather than triggering fail-fast. Three new tests in `t/t5584-http-429-retry.sh` verify the doubling sequence (1s, 2s, 4s), clamping at `http.maxRetryTime` (verifying via Trace2 that the sleep is capped at 2s when `http.maxRetryTime=2`), and that server-provided `Retry-After` headers override the computed backoff.

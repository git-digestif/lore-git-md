This is the first patch (1/7) in Harald Nordgren's v16 series introducing a limited-fetch mode for shallow repositories, and it makes a foundational change to how `git fetch --refmap` interacts with refspecs that carry an explicit destination.

Today, running `git fetch --refmap=<map> <remote> <src>:<dst>` stores the fetched ref twice: once at `<dst>` and again wherever `<map>` sends `<src>`. That is harmless when `--refmap` is typed by hand, but later patches in this series add a `remote.<name>.fetchRefmap` configuration that acts as a default refmap. Without this patch, a command-line refspec naming its own destination would be stored at both places with no way to say "only here." The fix applies the refmap only to destination-less refspecs (those with an empty `<dst>`, which a bare `<src>` is shorthand for); a refspec with a non-empty `<dst>` is stored there and nowhere else. Opportunistic updates of remote-tracking branches via `remote.<name>.fetch` are left untouched, so `git fetch origin main:tmp` still updates `origin/main` as before.

The implementation adds a `map_refs_without_dst()` helper in `builtin/fetch.c` that filters the ref map to entries without a `peer_ref` before applying the refmap, and updates `get_ref_map()` to use it. The patch includes a new test in `t/t5510-fetch.sh` verifying that `--refmap` is skipped for explicit destinations, plus documentation in `Documentation/fetch-options.adoc` clarifying the new semantics.

This looks like a well-crafted, clearly motivated change. The commit message explains the forward-looking rationale, the code is contained, and it ships with both tests and doc updates. It is the kind of foundational patch the rest of the series depends on, and it addresses a real ambiguity that would otherwise surface once the configured refmap lands.

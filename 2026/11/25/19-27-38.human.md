This is a substantive review by Junio C Hamano of the second patch in Adithya Chakilam's v2 series adding `--filter-to-loose` to `git repack`. The patch handles loose objects excluded by the filter, and Junio's feedback digs into several correctness and robustness gaps in how those loose objects are identified and copied.

The most significant conceptual issue is that `move_loose_filtered_objects()` currently enumerates every loose file on disk and filters purely by size, ignoring reachability, pack membership, and the index. Junio points out three concrete scenarios where this misbehaves: with `--cruft -a -d` it copies unreachable loose blobs that end up in the cruft pack; with plain `-a -d` it copies and then deletes unreachable loose objects that should be left alone for normal pruning; and it copies index-staged blobs that `pack-objects --indexed-objects` would have kept in the main pack. He also notes the function silently no-ops for any filter other than `blob:limit`, contradicting the documentation, and should at least support `blob:none` or explicitly reject unsupported filters. A related data-loss risk remains if the destination directory is the source repository's own object directory, where the `access()` check would see the source file as already present and `-d` could then unlink the only copy.

On implementation details, Junio flags that `copy_file()` with mode 0444 actually produces a writable file due to umask masking, and that the temporary file name `<oid>.tmp-<pid>` does not use the `tmp_obj_` prefix that `git fsck` ignores, so a crash could leave files that trigger "bad sha1 file" warnings. He suggests `git_mkstemp_mode()` with `tmp_obj_` and `copy_fd()` instead. In `remove_moved_loose_objects()`, he notes that `unlink()` errors are silently ignored (unlike `prune_packed_objects()` which uses `unlink_or_warn()`) and that empty fan-out subdirectories are left behind. He also questions whether the new test using `ls -i` to verify file identity is portable across platforms, suggesting `test-tool chmtime` as an alternative, and wonders if the test exercises the new `move_loose_filtered_objects()` path or just the `unpack-objects` path from the first patch.

The review also catches a minor AsciiDoc formatting issue in the documentation update, where subsequent paragraphs need a lone `+` line to render correctly. Overall this is a thorough, substantive review identifying real edge cases around reachability, filter semantics, and filesystem safety; the series remains under review awaiting a response and likely a v3.

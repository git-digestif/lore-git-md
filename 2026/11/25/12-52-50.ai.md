This is a cover letter for version 11 of a five-patch series that adds a new `--delete-integrated` mode to `git branch`. The series, authored by Harald Nordgren, extends branch deletion beyond strict tip-reachability (`--delete-merged`) to recognize branches whose changes have been squash-merged or rebased into an upstream, even when the branch tip itself is not reachable. The v11 iteration makes a focused change to patch 3/5 and patch 4/5: when `--dry-run` is combined with a non-deletion operation, the error message now names the specific operation being attempted -- for example `--dry-run is not supported for branch renaming` rather than the previous generic `--dry-run can only be used when deleting branches`. The documentation likewise clarifies that creating, renaming, and copying do not support `--dry-run`, while deletion modes (`-d`, `-D`, `--delete-merged`, `--delete-integrated`) do.

The series remains under review with no integration branch announced. The CLI design separates strict tip-based deletion (`--delete-merged <pattern>`, unchanged behavior) from change-based detection (`--delete-integrated <pattern>`, mutually exclusive with `--delete-merged`). When `--delete-integrated` is active, `delete_merged_branches()` in `builtin/branch.c` collects candidate branches that fail the usual reachability check and scans upstream history for commits containing all of the branch's changes. Patch 4/5 implements tree-based rebase detection that compares blob OIDs and modes without reading file contents, keeping it cheap in partial clones. Patch 5/5 adds squash detection for cases where upstream modified the same files before integration, using a two-pass approach in `changes_landed()`: first checking for exact tree-entry matches, then performing a three-way `xdl_merge()` with `XDL_MERGE_ZEALOUS` for paths that differ, treating a path as landed only if the merge result is byte-identical to the upstream version. This merge deliberately ignores `.gitattributes` drivers to avoid false positives from drivers like `union` and to prevent arbitrary command execution, and `mergeable_as_text()` rejects binary or oversized files.

Files touched across the series include `builtin/branch.c` (approximately 407 lines changed), `Documentation/git-branch.adoc`, `Documentation/config/branch.adoc`, and `t/t3200-branch.sh` (497 lines of new tests). Key symbols introduced include the `DELETE_BRANCH_INTEGRATED` flag bit, `delete_integrated` strvec, `branch_change` array tracking modified paths with blob OIDs and modes, `find_landed_commits()` and `find_landed_commit()` for the upstream scan, a `changed_paths` commit slab for pruning the walk, and `merge_keeps_upstream()` for the three-way text merge. The output format when a branch is deleted via change-based detection is `Deleted branch %s (was %s, landed as %s)`, naming the upstream commit where the changes were found. Configuration via `branch.<name>.deleteMerged` applies to both flags, though Junio has questioned whether a separate `deleteIntegrated` key would be more appropriate for the change-based mode.

Open questions carried over from the thread remain unresolved in v11: the "npm update" false-positive scenario (another author independently making identical changes) is not addressed by the current tree-based or merge-based detection and would require author checks or patch-ids, which have not been implemented; performance on very large repositories has not been benchmarked; and rename detection is absent from both the tree comparison and the merge logic. The `--dry-run` scope debate has been partially settled in code -- v11 implements operation-specific error messages as Junio requested -- but the philosophical question of whether those messages should signal future support (Junio's preference for a mature command) or remain neutral (Harald's preference, deferring universal `--dry-run` support to a follow-up `#leftoverbits` series) is still open in discussion though not blocking the current patches.

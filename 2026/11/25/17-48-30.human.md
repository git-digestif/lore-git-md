This is patch 2/5 of a five-patch series improving Git's HTTP transport resilience, specifically adding exponential backoff for rate-limited requests. When a server returns HTTP 429 without a `Retry-After` header, Git now doubles the wait time on each successive retry instead of applying the same fixed `http.retryAfter` delay every time. The delay starts at the configured `http.retryAfter` value and grows as `http.retryAfter * 2^(attempt - 1)`, capped at `http.maxRetryTime` to prevent overflow and excessive waits.

The change modifies `handle_rate_limit_retry()` in `http.c` to accept a 1-based attempt counter, and the call site in `http_request_recoverable()` computes this from the remaining retry count. An explicit `Retry-After` header from the server still takes precedence over the computed backoff. Three new tests in `t/t5584-http-429-retry.sh` verify the doubling sequence (1s, 2s, 4s), confirm clamping at `http.maxRetryTime`, and check that server headers override the backoff calculation.

This patch is unchanged from v4 and has already received Junio's approval ("Looking good"), who specifically endorsed the overflow-safe doubling loop that checks `if (delay >= http_max_retry_time - delay)` before doubling. It addresses a real gap: without backoff, a short retry delay causes Git to exhaust all retries in seconds before a busy server can recover, while a long delay makes even brief glitches painful. The documentation in `Documentation/config/http.adoc` is updated to describe the new exponential behavior and clarify that backed-off delays are capped rather than causing immediate failure when they exceed `http.maxRetryTime`.

This is a bugfix targeting the `git config` builtin. When a user runs `git config <key>=<value>` as a single argument and the value contains spaces, the shell splits the argument and the command fails; the old error hint suggested a `git config set` command that was itself unsafe to paste back into a shell because it did not quote the value. The patch makes the suggestion shell-safe by quoting the value when necessary and displaying the command on its own indented line.

The change is implemented in `builtin/config.c`. A new static helper `add_suggested_arg` takes a `struct strbuf` and an argument string, uses `sq_quote_buf_pretty` to produce a shell-quoted form, and falls back to wrapping the argument in single quotes if it already contains a single quote. The `die_missing_set_value` function now builds the suggestion into a `struct strbuf` by calling `add_suggested_arg` for both the key prefix and the value part, then emits it with `advise` using a multi-line format: `did you mean:` followed by a blank hint line and an indented tab-prefixed `git config set ...` line.

Old behavior produced a single-line hint like `hint: did you mean "git config set status.comparebranches @{upstream} @{push}"?`, which breaks when copied because the unquoted value splits into multiple words. New behavior produces `hint: did you mean:` / `hint:` / `hint: \tgit config set status.comparebranches '@{upstream} @{push}'`, which pastes correctly.

Tests in `t/t1300-config.sh` are converted from `test_grep` to exact `test_cmp` matching against the new multi-line output, and new cases cover a value with spaces (`status.comparebranches="@{upstream} @{push}"`) and a shell alias (`alias.st="!git status"`) to verify that quoting is preserved. The patch is small and self-contained, touching only `builtin/config.c` and `t/t1300-config.sh`, and addresses a concrete usability defect where Git's own suggested remedy did not work.

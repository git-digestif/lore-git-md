This is a bugfix, specifically the third patch in Dirk Gouders's v6 four-patch series fixing bounds handling in Git's UTF-8 display-width code. The series targets out-of-bounds reads in `utf8_strnwidth()` and `utf8_width()` when processing bounded strings, and this particular patch addresses a specific edge case that arises after skipping ANSI escape sequences.

The bug occurs when `utf8_strnwidth()` skips over an ANSI SGR sequence that ends exactly at the length boundary. The commit message walks through a concrete example: given the string `"\033[31mdon't touch me"` with `len = 5`, the escape sequence `"\033[31m"` consumes exactly the five allowed bytes. Without a bounds check, the code then passes the pointer to `utf8_width()`, which reads the next byte (`'d'`) outside the given bound and incorrectly returns width 1 instead of 0. Since the memory beyond `string[len]` is unknown -- it could be anything, or nothing at all -- reading it is unsafe.

The fix adds a simple guard after the escape-sequence-skipping loop: if `string >= orig + len`, the loop breaks immediately before calling `utf8_width()`. This ensures that when an escape sequence lands precisely on the boundary, no further characters are inspected. The patch relies on `display_mode_esc_sequence_len_counted()` introduced in patch 1 of the series, which safely scans bounded buffers without risking pointer arithmetic beyond the allocation.

Tests are added in `t/unit-tests/u-utf8-width.c` covering three boundary cases for the string `"\033[31mhello"`: `len = 4` returns width 3 (incomplete escape sequence treated as regular characters), `len = 5` returns width 0 (escape sequence ends exactly at boundary), and `len = 6` returns width 1 (one real character remains). These complement the existing CJK chopped-sequence tests from earlier in the series.

Within the broader v6 effort, this patch sits between the introduction of the counted escape-sequence scanner (patch 1) and the follow-up that passes a remainder argument to `utf8_width()` to handle chopped multibyte characters (patch 4). The series remains under review and has not yet been queued in any integration branch, though it incorporates the mechanical feedback from Junio C Hamano's review of v5.

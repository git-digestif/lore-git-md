This is a preparatory refactoring within the larger `--delete-integrated` feature series. Patch 2/5 of v11 extends `delete_branches()` in `builtin/branch.c` to accept an optional `struct strmap *landed_commits` that maps branch names to the upstream commits where their changes landed. When a branch appears in this map, the function skips the usual tip-reachability check (`check_branch_commit()`) and instead reports deletion with a new message format: `Deleted branch %s (was %s, landed as %s)`, naming the upstream commit where the changes were found.

Both existing call sites -- the ordinary `-d`/`-D` path and `delete_merged_branches()` -- currently pass `NULL` for this new parameter, so there is no behavior change in this patch. The commit also reorganizes the dry-run and normal message strings into a static `msg_templates` array indexed by whether this is a dry run, preparing for the landed-branch variant that later patches will activate.

This sets up the plumbing for patches 4/5 and 5/5, which will populate the `landed_commits` map by scanning upstream history for commits containing a branch's changes -- first via tree-based rebase detection, then via three-way merge for squash merges. Until those patches wire in a real map, this change is invisible to users.

The patch is clean and well-scoped, touching only `builtin/branch.c` with 39 insertions and 19 deletions, and the commit message clearly explains that no caller uses the new capability yet. It is solid groundwork for the change-based deletion logic that follows in the series.

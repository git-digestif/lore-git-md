This is a bugfix patch -- specifically the first of five patches in Ravi Mistry's v5 series that hardens Git's HTTP transport retry logic. It fixes two bugs introduced by commit 640657ffd0 (2026-03-17) in the 429 rate-limit handling.

First, in `http_request_recoverable()` (http.c), the retry counter used pre-decrement `--rate_limit_retries` in the while-loop condition, causing `http.maxRetries=N` to perform only N-1 retries and wrapping from 0 to -1 (truthy in C) when `http.maxRetries=0` and a 429 followed a 401 re-auth. The loop condition is now `http_max_retries > 0 && rate_limit_retries-- > 0` (post-decrement), with an explicit `http_max_retries <= 0` check after the loop that returns `HTTP_ERROR` without emitting the retries-exhausted Trace2 event.

Second, `CURLINFO_RETRY_AFTER` was queried in `http_request()` after `run_one_slot()` had already called `handle_curl_result()`, so Trace2 logged `retry_after` as -1 instead of the actual value. The extraction moved to `finish_active_slot()`, which initializes `slot->results->retry_after = -1` and sets it only when the header value is positive, ensuring both `handle_curl_result()` and callers observe the parsed value.

Files touched: `http.c`, `t/t5584-http-429-retry.sh`, and `t/lib-httpd/http-429.sh`. New tests verify that `http.maxRetries=1` retries exactly once, that `http.maxRetries=2` fails after three consecutive 429s but succeeds after two, and that Trace2 records the actual `Retry-After` value. The test helper `http-429.sh` now supports `*-fail-N*` URL patterns to simulate multiple consecutive failures. This patch is unchanged from v4 and was previously approved by Junio C Hamano; in v5 it is resent as part of the complete series while patches 3/5 and 4/5 address his remaining review items.

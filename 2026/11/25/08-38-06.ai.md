This is a bugfix targeting the smart HTTP transport (`remote-curl`) and the transport-helper layer.

The patch fixes `git push --no-thin` being silently ignored when pushing to a smart HTTP remote, causing a thin pack to be sent anyway. The root cause is twofold: `transport-helper.c` excludes `TRANS_OPT_THIN` from the list of options forwarded to remote helpers (a leftover from commit ef08ef9ea0 in 2009, when `--no-thin` had no effect on any transport), and `remote-curl.c` unconditionally invokes `send-pack` with `--thin`. Commit f7c815c3ee (2013) later made `--no-thin` work for native transports, but the helper path remained broken.

The fix removes `TRANS_OPT_THIN` from `unsupported_options[]` in `transport-helper.c` so the option reaches helpers, and adds handling for `TRANS_OPT_THIN` in `remote-curl.c`'s `set_option()` to toggle the `options.thin` flag. Documentation in `Documentation/gitremote-helpers.adoc` describes the new `option thin` capability. Backward compatibility is preserved because helpers unaware of the option respond "unsupported", which the push code already ignores.

The commit message includes a concrete production scenario: pushing from a shallow, treeless partial clone (`--filter=tree:0`) over HTTPS triggers one lazy fetch per missing tree during a thin push, and `--no-thin` eliminates that overhead (measured as 37 lazy fetches vs. 0 with the patch). The test in `t/t5541-http-push-smart.sh` uses `GIT_TRACE2_EVENT` to verify that `git pack-objects` is invoked with `--thin` by default and without it when `--no-thin` is passed.

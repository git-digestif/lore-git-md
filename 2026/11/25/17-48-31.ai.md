This is patch 3/5 of a five-patch v5 series by Ravi Mistry that introduces the `http.retryStatusCodes` configuration option, allowing Git to retry transient HTTP status codes beyond the default 429. It sits between the retry-counter fix (1/5) and exponential backoff (2/5) earlier in the series, and the POST retry support (4/5) and default delay change (5/5) that follow.

The patch adds a new config key `http.retryStatusCodes` (default `"429"`, also settable via `GIT_HTTP_RETRY_STATUS_CODES` environment variable) that accepts a comma- or whitespace-separated list of HTTP status codes in the 400..599 range. A new helper `is_retryable_http_code()` in `http.c` parses this list and checks membership; `handle_curl_result()` now calls this helper instead of hardcoding 429, returning `HTTP_RATE_LIMITED` for any configured retryable code. The `struct http_get_options` in `http.h` gains a `long http_code` field populated by `http_request()` so that `http_request_recoverable()` can distinguish the specific status code when emitting warnings: it preserves the existing "rate limited" wording for 429 but prints "HTTP <code>, waiting <N> seconds before retry" for other codes, and returns `HTTP_ERROR` rather than `HTTP_RATE_LIMITED` when retries are exhausted on a non-429 code.

Version 5 specifically updates the documentation to clarify two edge cases raised in review: an empty `http.retryStatusCodes` value disables retries for all status codes (it does not restore the default), and HTTP 401/404 can never be retried regardless of configuration because `handle_curl_result()` checks authentication and not-found conditions before consulting the retryable-code list. A new test in `t/t5584-http-429-retry.sh` covers the empty-string case. The patch also extends the test helper `t/lib-httpd/http-429.sh` to emit 502, 503, and 504 status lines based on URL patterns (`*-status-502*`, etc.), and adds five tests verifying that 502/503/504 are not retried by default, that configured codes are retried with appropriate numeric warning messages, that `Retry-After` headers are honored for non-429 codes, that exhausted retries on a 502 report the actual error code rather than "rate limited", and that both the environment variable and `http.<url>.retryStatusCodes` urlmatch work correctly.

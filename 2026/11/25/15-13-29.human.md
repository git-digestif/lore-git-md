This is a review acknowledgment from the patch author, responding to Junio C Hamano's comments on `[PATCH v4 3/5]` of Ravi Mistry's five-part series improving HTTP transport retry handling. The email itself contains no code changes; it confirms that the two edge cases Junio raised will be addressed in the next iteration.

Junio's review of patch 3/5 had flagged two subtle behaviors worth documenting: setting `http.retryStatusCodes` to an empty string disables all retries rather than falling back to the default 429-only behavior, and 401/404 responses can never be retried even if explicitly configured because `handle_curl_result()` checks `missing_target()` and 401 before consulting the retryable-code list. Ravi Mistry replies that both points make sense and commits to documenting them in the `http.retryStatusCodes` documentation in v5, plus adding a test case for the empty-string scenario.

This exchange sits at patch 3 of 5 in the v4 series, which as a whole addresses retry count bugs, exponential backoff, configurable retry status codes, POST request retries for fetch/clone, and a new default retry delay. The series has already received the maintainer's endorsement at the cover-letter level, with patches 1 through 4 individually approved; this reply simply closes the loop on the remaining documentation refinements for patch 3 before the author prepares v5. The response is brief but substantive, showing the author is tracking the maintainer's edge-case observations rather than dismissing them.

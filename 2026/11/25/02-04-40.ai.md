This is a discussion reply in the ongoing RFC thread about user-initiated recovery from stale `index.lock` files, responding to Steve's proposal for a built-in wait-and-remove command.

Tanga Joris points out that Git already provides two partial pieces of the requested behavior. Since Git 2.54, the `core.lockfilePid` configuration causes Git to write the lock holder's PID into a sidecar file named `index~pid.lock` (or similar, depending on the lock), and when a command fails to acquire the lock it reports whether that PID is still alive -- printing a message like "Lock was held by process 99999, which is no longer running; the lock file appears to be stale". Separately, Jun Wu has a series currently in `seen` that introduces `core.indexLockTimeout`, allowing commands to wait briefly for the index lock before failing, which covers the "wait briefly" part of Steve's request. Neither mechanism removes the lock automatically; the user still deletes `index.lock` manually.

The reply argues against automatic removal on safety grounds. A recorded PID can be reused by an unrelated process, making liveness checks unreliable, and the PID file carries no information when the repository is shared across machines (for example over NFS), where another host may legitimately hold the lock. Tanga notes that when the PID-file feature was originally discussed, Junio expressed wariness even about merely advising users to remove a stale lock manually, underscoring how cautious the project is about encouraging lock deletion.

The email closes with two lore.kernel.org references for follow-up: Jun Wu's `core.indexLockTimeout` series (message-id `20261017073231.3357477-1-quark.zju@gmail.com`) and Junio's earlier cautionary message about stale-lock removal (message-id `xmqqbjj4hnkr.fsf@gitster.g`). No new patch or code is proposed here; the thread remains open on whether any safe automatic-removal mechanism is possible given the PID-reuse and network-filesystem hazards.

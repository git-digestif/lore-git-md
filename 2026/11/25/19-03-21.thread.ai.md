Thread identity: Feature patch from Harald Nordgren (via GitGitGadget) making the revision-range argument optional for the `squash` subcommand of the new `git history` command. This is the initial posting of the patch.

Core problem or goal: Allow `git history squash` to operate without an explicit `<revision-range>` by defaulting to the commits on the current branch that are not in its upstream -- specifically the range from the merge base of `HEAD` and `@{upstream}` up to `HEAD`. This restores default behavior that existed when the feature was `git rebase --squash` but was lost when moved into `git history` (commit 6fd039c984).

Current status: New patch posted for review; no maintainer feedback or integration status yet.

Key technical details: Implementation adds a `default_squash_range()` helper in `builtin/history.c` that resolves `@{upstream}` and `HEAD`, computes their merge bases, and constructs a revision range of `^<merge-base> HEAD` by pushing `"squash"` followed by the negative refs and `HEAD` into a `strvec` (the command-line parsing was refactored to use this `strvec` instead of raw argc/argv). Usage strings in both the code and `Documentation/git-history.adoc` now show `[<revision-range>]` as optional. If no upstream is configured the command errors with "could not resolve the upstream of HEAD". Tests in `t/t3455-history-squash.sh` were updated: the previous "errors on missing range argument" test now expects failure only when no upstream exists, and a new test verifies that with an upstream configured, running `git history squash --no-edit` without arguments squashes the local commits.

Open questions and loose ends: None yet; the patch is presented as ready for review.

Participant positions: Harald Nordgren is the author proposing this default-range behavior.

Related work: The squash functionality previously lived in `git rebase --squash` (which defaulted to `@{upstream}..HEAD`) before being moved into the `git history` command in commit 6fd039c984.

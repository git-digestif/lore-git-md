This is the fourth and final patch in Dirk Gouders's v6 bugfix series targeting out-of-bounds reads in Git's UTF-8 display-width code. The patch modifies `utf8_strnwidth()` in `utf8.c` so that its calls to `utf8_width()` respect the length boundary passed to `utf8_strnwidth()`, rather than reading past the end of the buffer when a multibyte character is truncated by the `len` argument.

In the main loop of `utf8_strnwidth()`, the patch declares a new local `size_t remainder`, computes it as `orig + len - string` immediately before each width calculation, and passes `&remainder` as the optional boundary argument to `utf8_width(&string, &remainder)` instead of the previous `NULL`. This ensures that when `len` cuts a multibyte sequence short, `utf8_width()` stops at the boundary instead of consuming bytes beyond it. The commit message explicitly notes that the bounds check added in patch 3/4 (`if (string >= orig + len) break;` after skipping ANSI sequences) must remain: `utf8_width()` treats a zero remainder as invalid UTF-8 and would return a sentinel causing `utf8_strnwidth()` to return `len` rather than the correct width for strings ending exactly at an escape sequence.

The patch adds `test_utf8_width__strnwidth_cjk_chopped()` to `t/unit-tests/u-utf8-width.c`, which verifies that `utf8_strnwidth("三bytes long, 二columns wide", 1, 1)` returns 1 and that passing `len` 3 (which lands mid-character on the three-byte CJK glyph "三") returns 2, confirming the bounded behavior prevents over-read. Together with patches 1 through 3, this completes the series' goal of making both `utf8_strnwidth()` and the new `display_mode_esc_sequence_len_counted()` fully respect their length arguments without pointer-arithmetic undefined behavior.

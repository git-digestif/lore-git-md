This is the fifth and final patch in Ravi Mistry's five-part series hardening Git's HTTP transport against transient server errors, and it changes the default behavior of the retry delay. Specifically, it flips the default value of `http.retryAfter` from 0 to 10 seconds, so that when `http.maxRetries` is enabled and a server returns HTTP 429 (or another code listed in `http.retryStatusCodes`) without a `Retry-After` header, Git now waits 10 seconds before the first retry and doubles the delay on each subsequent attempt (10s, 20s, 40s, capped at `http.maxRetryTime`) instead of hammering the server in a tight loop.

The patch also preserves immediate-retry semantics for servers that explicitly ask for it. Because libcurl's `CURLINFO_RETRY_AFTER` returns zero both when the header is absent and when it contains `Retry-After: 0` or a past HTTP-date, the patch adds a new helper `has_zero_or_past_retry_after()` that inspects the raw header via `curl_easy_header()` (guarded by a new `GIT_CURL_HAVE_CURL_EASY_HEADER` macro for libcurl >= 7.84.0). When the raw header indicates zero or a past date, the code sets the retry delay to 0, keeping that behavior distinct from the new 10-second default. The word "configured" is dropped from the `http.maxRetryTime` error message since the value may now be the default rather than an explicit user setting.

This patch resolves the procedural concern Junio C Hamano had raised about the series being introduced in two phases: patches 1 through 4 built the exponential backoff machinery assuming `http.retryAfter` defaulted to 0, while this patch activates the 10-second default that makes the backoff meaningful out of the box. Users who want the old immediate-retry behavior can still set `http.retryAfter=0` explicitly. The change is covered by new tests in `t/t5584-http-429-retry.sh`, including one that verifies the 10-second default triggers the fail-fast path when `http.maxRetryTime` is set below 10, and another that confirms `Retry-After: 0` still retries immediately on modern libcurl.

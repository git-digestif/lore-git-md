This is a bugfix, and the first patch in a three-part series aimed at hardening `git remote` against invalid branch names. The series, authored by Harald Nordgren, targets the fact that `git remote add -t`, `git remote add -m`, and `git remote set-branches` currently accept malformed branch names that get persisted as broken refspecs in the configuration, causing every subsequent fetch from that remote to fail with a confusing error. This particular patch addresses only the `-t` option of `git remote add`.

The motivation is a practical footgun: a typo or unexpected shell expansion (such as `@{u}`) in the branch name argument silently produces a fetch refspec that can never match anything, or is syntactically invalid outright. Nothing in the resulting error messages points back to the original mistake made during remote setup. The patch ensures the command fails immediately, before any configuration is written or the remote is created.

Technically, the change adds a `validate_tracked_branchname()` helper in `builtin/remote.c` that constructs the full reference path -- `refs/heads/<name>` for normal remotes, or `refs/<name>` for mirrors -- and validates it with `check_refname_format()` using `REFNAME_REFSPEC_PATTERN`. The `add()` function now loops over all `-t` arguments and calls this validator before proceeding, so an invalid name triggers a `die()` with a clear message like `'@{u}' is not a valid branch name`.

Test coverage is included in `t/t5505-remote.sh`, where a new test confirms that `git remote add -t "@{u}"` fails and that the remote URL is not persisted in the configuration afterwards. The patch is clean and focused, with a commit message that clearly explains both the problem and the fix, and it looks like a solid, well-motivated contribution that should slot easily into review once the remaining two patches in the series are considered.

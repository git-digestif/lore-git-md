This is a cover letter for a seven-patch feature series (v16) from Harald Nordgren that introduces a limited-fetch mode for shallow repositories. The series addresses the problem that `git remote add` in a shallow clone defaults to a wildcard refspec, causing the next `git fetch` to download every branch of a large remote and defeating the purpose of the shallow clone. The proposed solution decouples what is fetched from where it is stored via two new configuration keys: `remote.<name>.fetchUpstreams` (boolean, restricts fetch to branches tracked by local branches) and `remote.<name>.fetchRefmap` (a refspec acting as the default for `--refmap`). A new `git remote add --limited-fetch` option sets both, and shallow repositories default to this mode unless `-t` or `--mirror` is given.

The series touches `builtin/fetch.c`, `builtin/remote.c`, `remote.c`, and `remote.h`, introducing helpers such as `map_refs_without_dst()` (applies refmap only to destination-less refspecs), `drop_destinations()`, and `collect_upstream_from_remote()`. Key behavior changes include: a refspec with a non-empty `<dst>` on the command line bypasses the refmap and is stored only at its explicit destination; `--refmap` can now apply to configured `remote.<name>.fetch` entries even without command-line refspecs; and `remote_find_tracking()` falls back to the refmap when the fetch refspec yields no match so `@{upstream}` resolves correctly. Tests are added in `t/t5510-fetch.sh`, `t/t5505-remote.sh`, and a new `t/t5586-fetch-refmap.sh`.

Version 16 incorporates feedback from the v15 review, notably from Junio C Hamano. Changes include: tags are now followed when a refspec-less fetch stores refs through `--refmap` or `fetchRefmap`, while `--refmap=""` stores nothing and follows no tags; `--refmap` is rejected again when the remote has nothing configured to fetch (e.g., a bare URL); and `--prune` with `--refmap` and no command-line refspecs no longer prunes the configured destinations in `remote.<name>.fetch`, leaving them untouched since the fetch does not store there. Documentation updates appear in `Documentation/config/remote.adoc`, `Documentation/fetch-options.adoc`, and `Documentation/git-remote.adoc`, clarifying that destinations from a refmap are not pruned and that non-empty destinations are exempt from refmap application.

The series remains under review; v15 was queued in `next` per a prior "What's cooking" report, and this v16 supersedes it. The cover letter notes that the series blocks `ch/remote-defer-follow-remote-head-validation` due to textual conflicts. Open review concerns from v15 regarding `*autotags` computation timing and `prune_refs()` receiving the wrong refspec source appear to be addressed in this iteration, though final maintainer sign-off is still pending.

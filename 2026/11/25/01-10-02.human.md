This is a bugfix for `git apply`, specifically the second patch (2/2) in Tanga Joris's v4 two-patch series addressing a crash in `git apply --check`. The series fixes an assertion failure (`patch->is_new <= 0`) in `check_preimage()` that triggers when Git encounters malformed patch headers where the `---` or `+++` lines appear before the `new file mode` or `deleted file mode` lines.

This patch adds explicit validation to `parse_git_diff_header()` in `apply.c`: after reading the header, it rejects a new file that has an old name (indicating `---` came before `new file mode`) and a deleted file that has a new name (indicating `+++` came before `deleted file mode`). Instead of proceeding to the assertion, Git now emits a clear error naming the offending header line and its location (e.g., `"---" before "new file mode" at file.diff:4`). The commit message notes that this mirrors the approach taken in d70e9c5c8c for other conflicting header lines, and that legitimate Git-generated patches are unaffected because Git always writes the mode line first.

The patch extends the new test file `t/t4133-apply-filenames.sh` with cases covering both `/dev/null` and regular paths in the wrong-order `---` line, plus the `+++ /dev/null` before `deleted file mode` case, verifying that both `git apply --check` and `git apply --check -R` fail with the expected diagnostic. Siddharth Asthana is credited with helping refine the error messages.

Within the thread, this follows patch 1/2 (which rejects empty `diff --git` sections) and completes the fix for the crash originally reported by Gingrspacecadet. The series has received endorsement from Junio C Hamano and substantive review from Phillip Wood, targets `maint`, and is based on commit `77904e546de3bd940621092ecec47a88d0cede5d`. It looks well-crafted and ready for integration.

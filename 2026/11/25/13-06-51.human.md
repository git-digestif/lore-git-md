This is a discussion reply in an ongoing RFC thread about adding user-initiated recovery for stale `index.lock` files, with no patch attached yet.

Steve responds to Tanga Joris's safety concerns by arguing that the existing `core.lockfilePid` mechanism could be leveraged by an explicit recovery command. Since Git 2.54 already writes the lock holder's PID to a sidecar file and can report whether that PID is still alive, Steve asks why a manual command could not perform that same liveness check internally, wait for a reasonable period, and then remove the lock only when explicitly invoked by the user. He contends that deleting `.git/index.lock` by hand offers no such safety checks, whereas a built-in command could verify the holder is gone before acting.

The exchange highlights a tension between convenience and caution. Tanga Joris had previously noted that PID reuse and network filesystems make automatic or semi-automatic removal risky, and that Junio has historically been wary of even advising manual lock deletion. Steve's counter is that an explicit, user-triggered command with built-in verification might satisfy safety requirements better than the current ad-hoc `rm` approach.

The thread remains at the proposal stage. No code has been written, and the maintainer has not weighed in on this specific suggestion. The discussion now centers on whether a command can reliably distinguish a truly stale lock from one held by a live process across different hosts and PID namespaces, or whether the risks of PID reuse and NFS sharing make any form of automated removal untenable.

This is a review discussion on a feature patch that adds a new `GIT_COMMENT_STRING` variable to `git var`. Phillip Wood's original patch makes the effective comment string -- the one Git uses for template commit messages and rebase todo lists -- directly queryable by scripts, removing the need to parse both `core.commentChar` and `core.commentString` configuration values themselves.

In this reply, Phillip responds to Kristoffer Haugsbakk's review comments. He agrees to reword "comment character" to "comment string" in the commit message for consistency with the new variable name. On the documentation, Phillip explains his preference for keeping the `git-var` entry focused on the queryable value rather than cross-referencing the configuration keys, arguing that users should not need to understand the config intricacies to use the variable; he instead suggests phrasing it as "as set by `core.commentString`" and notes that he has added a reciprocal pointer in the `core.commentString` documentation directing users to `git var GIT_COMMENT_STRING`.

Kristoffer confirms the test coverage is adequate, verifying both the default `#` output and that a custom `core.commentString` correctly overrides `core.commentChar`. He also highlights an edge case: setting `core.commentString` to an empty value causes `git var GIT_COMMENT_STRING` to abort with a fatal error during config parsing rather than falling back to a default. The exchange is constructive with no blocking objections raised, and the patch remains under review with no indication yet of queuing in any integration branch.

This is a feature patch for the new `git history` command, making the revision range argument optional for the `squash` subcommand. When no range is provided, `git history squash` now defaults to squashing all commits on the current branch that are not in its upstream -- specifically the range from the merge base of `HEAD` and `@{upstream}` up to `HEAD`. This restores behavior that existed in an earlier incarnation of the feature as `git rebase --squash`, which defaulted to `@{upstream}..HEAD` but lost that default when the functionality moved into `git history` (introduced in commit 6fd039c984).

The implementation adds a `default_squash_range()` helper in `builtin/history.c` that resolves `@{upstream}` and `HEAD`, computes their merge bases, and constructs a revision range of `^<merge-base> HEAD` (pushing `"squash"` as argv0 followed by the negative refs and `HEAD` into a `strvec`). The command-line parsing was refactored to use this `strvec` instead of raw argc/argv, and the usage string in both the code and `Documentation/git-history.adoc` now shows `[<revision-range>]` as optional. If no upstream is configured, the command errors with "could not resolve the upstream of HEAD".

Tests in `t/t3455-history-squash.sh` were updated accordingly: the old "errors on missing range argument" test now expects a failure only when no upstream exists, and a new test verifies that with an upstream configured, running `git history squash --no-edit` without arguments squashes the local commits (verified by checking that the resulting HEAD tree matches the pre-squash tip and that the commit subjects are correctly folded). The patch is well-scoped with documentation and test coverage, and appears ready for review.

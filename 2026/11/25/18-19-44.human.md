This is a bugfix, specifically the fourth and final patch in a v6 series that fixes out-of-bounds reads in Git's UTF-8 display-width code. The patch modifies `utf8_strnwidth()` in `utf8.c` to compute a `remainder` (the bytes left between the current pointer and `orig + len`) and pass it to `utf8_width()` via its optional boundary argument. This prevents `utf8_width()` from reading past the end of the buffer when `len` happens to chop a multibyte character in half.

The commit adds a unit test, `test_utf8_width__strnwidth_cjk_chopped()`, which verifies that a string like `"三bytes..."` returns width 1 when `len` is 1 (cutting the three-byte character) and width 2 when `len` is 3 (including the full character). The commit message also carefully explains why the bounds check introduced in the previous patch (3/4) must remain: even with the remainder argument, `utf8_width()` treats a zero remainder as invalid UTF-8, so without the explicit check the function would incorrectly return `len` instead of the computed width for strings that end with an ANSI escape sequence.

Within the series, this patch completes the fix for `utf8_strnwidth()` after patch 3 addressed escape-sequence boundaries and patch 1 introduced the counted ANSI scanner. Junio C Hamano, who authored patch 1 and reviewed v5 as being in "a very good shape," has seen his mechanical requests addressed in this v6; the series remains under review and has not yet been merged or queued in any integration branch.

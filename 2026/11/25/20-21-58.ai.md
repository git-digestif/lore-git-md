This is a substantive review reply from the maintainer in the ongoing test-infrastructure thread serializing `EXPENSIVE` tests in `t/test-lib.sh`. Junio C Hamano responds to Kaartic Sivaraam's proposal to address two correctness flaws in the v2 lock mechanism: a TOCTOU race where a waiter might delete a new holder's lock directory, and a signal-handling deadlock where a process killed between `mkdir "$expensive_lock_"` and setting `have_expensive_lock_=t` leaves an unremovable empty lock. Sivaraam had proposed a secondary `.break` lock created via `mkdir` before removing a stale lock, re-reading the `pid` file to verify ownership before `rm -rf`, and reordering the code to set `have_expensive_lock_=t` before writing the PID so `release_expensive_lock_()` cleans up even if interrupted; he also acknowledged that a `kill -9` arriving after `mkdir` but before the PID write, or a signal in the microsecond window between `mkdir` and flag-setting, would still leave a permanently stuck lock, suggesting those be deferred until they cause actual problems.

Junio draws a sharp distinction between the two failure modes: a leaky lock that allows multiple EXPENSIVE tests to run concurrently merely reproduces the status quo and is therefore not a regression, whereas a permanent deadlock is a serious regression that must be eliminated in the next version. He states that if the updated patch kills the deadlock scenario, he will be satisfied, effectively greenlighting Sivaraam's proposed reordering of `have_expensive_lock_=t` before the PID write while implying the deferred `kill -9` and microsecond-window edge cases are acceptable residual risks for now. The thread remains open with no v3 posted yet; the next expected step is a revised patch incorporating the flag-before-PID-write ordering and the `.break` lock mechanism, after which the series can move toward acceptance.

This is a feature patch, specifically the first of two in v2 of a series adding a `--filter-to-loose=<directory>` option to `git repack`. Adithya Chakilam proposes this to let users write objects excluded by `--filter` directly as loose objects into a chosen directory, rather than into an intermediate packfile as the existing `--filter-to` does. The motivation is interoperability with key-value object stores and large-object promisors that manage Git objects individually and cannot consume packfiles directly.

The patch streams the filtered pack through `unpack-objects` with `GIT_OBJECT_DIRECTORY` pointed at the target, writing each excluded object as a loose file. It enforces that the destination directory already exists, cannot be combined with `--filter-to` or `--max-pack-size`, and skips objects already present. This iteration incorporates three fixes from Junio C Hamano's review of v1: an early error if the directory is missing, use of `OPT_FILENAME` so relative paths resolve correctly from subdirectories, and removal of a manual `close()` that caused a double-close in `repack-filtered.c`.

Technically it touches `builtin/repack.c`, `repack-filtered.c`, and `repack.h`, adding a `loose` flag to `write_pack_opts` and a `start_unpack_objects()` helper that pipes pack-objects output into unpack-objects. The tests in `t/t7700-repack.sh` cover the happy path, relative-path resolution from a subdirectory, failure recovery leaving source packs intact, interaction with kept packs and cruft packs, and survival of `gc`/`prune` on the source. The second patch in the series extends this to also copy and optionally delete loose objects from the source repository that the filter excludes. The commit message is clear, the fixes address specific reviewer concerns, and the test coverage looks thorough; the series remains under review with no integration status reported yet.

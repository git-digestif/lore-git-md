Julian Maurin has sent a single-patch bugfix addressing a long-standing gap in how `git push --no-thin` is handled over the smart HTTP transport. When pushing to a smart HTTP remote, the `--no-thin` flag was silently ignored and a thin pack was sent regardless, which the patch traces to two places: `transport-helper.c` still excluded `TRANS_OPT_THIN` from the options forwarded to remote helpers (a leftover from 2009), and `remote-curl.c` unconditionally passed `--thin` to `send-pack`. Although commit f7c815c3ee in 2013 made `--no-thin` work for native transports, the helper path remained broken until now.

The fix removes `TRANS_OPT_THIN` from the unsupported-options list in `transport-helper.c` so the flag reaches helpers, and teaches `remote-curl.c`'s `set_option()` to toggle the internal `options.thin` flag accordingly. The capability is documented in `Documentation/gitremote-helpers.adoc` as a new `option thin` feature, and backward compatibility is preserved because older helpers simply reply "unsupported," which the push code already ignores. The commit message motivates the change with a concrete production scenario: pushing from a shallow, treeless partial clone (`--filter=tree:0`) over HTTPS triggers one lazy fetch per missing tree during a thin push, and `--no-thin` eliminates that overhead entirely (37 lazy fetches versus zero with the patch). A new test in `t/t5541-http-push-smart.sh` uses `GIT_TRACE2_EVENT` to confirm that `git pack-objects` receives `--thin` by default and omits it when `--no-thin` is passed.

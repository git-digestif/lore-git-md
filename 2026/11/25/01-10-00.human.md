This is a **bugfix** for `git apply` and the v4 cover letter of a two-patch series fixing a crash in `git apply --check`. Tanga Joris addresses an assertion failure (`patch->is_new <= 0` in `check_preimage()`) that occurs when Git encounters malformed `diff --git` headers, a bug confirmed in released versions and `master` by first-time contributor Gingrspacecadet.

The series now rejects corrupt patch headers outright rather than attempting to parse them. Patch 1/2 makes `find_header()` die immediately with a "corrupt patch: empty diff --git header" error when it sees a `diff --git` line with no header lines following it, including the case where another `diff --git` line comes directly after. This drops v3's separate memory-leak fix, since the leak only manifested when apply skipped such empty headers, which it no longer does. Patch 2/2 (unchanged from v3) rejects new files that have a `---` line before `new file mode` and deleted files with a `+++` line before `deleted file mode`, reporting the specific offending header line rather than a stripped filename.

The approach fully aligns with Junio C Hamano's guidance that `git apply` should reject any header format that `git diff` or `git format-patch` would not generate. Tanga Joris historically verified that bare `diff --git` lines were only emitted by Git in 2005 before the `index` line was added, so modern Git never produces empty headers and their presence indicates corruption. Phillip Wood also endorsed the stricter validation. The series is based on `maint`, merges cleanly with `master`, `next`, and `seen`, and includes thorough tests in `t/t4133-apply-filenames.sh` covering `--check`, actual application, and reverse application.

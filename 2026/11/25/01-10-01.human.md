This is a **bugfix** targeting the `apply` machinery, specifically patch 1/2 of Tanga Joris's v4 series that fixes a deterministic crash in `git apply --check`. The series addresses an assertion failure (`patch->is_new <= 0` in `check_preimage()`) that occurs when a patch contains an empty `diff --git` section -- a line reading `diff --git a/f b/f` followed immediately by a non-header line such as a blank line, indented text, or another `diff --git` line. Modern Git never generates such empty sections (they were only possible in 2005 before the `index` line was added), so the patch treats any empty `diff --git` header as corrupt and rejects it immediately in `find_header()` with a clear error message naming the file and line number.

The root cause is stale state: when `parse_git_diff_header()` stops early after seeing only the `diff --git` line, it has already populated `old_name` and `new_name`, but `find_header()` previously skipped the section and continued parsing, leaving those names set while later code paths set `is_new`, triggering the assertion. By rejecting the empty header outright, the patch prevents the inconsistent state that caused the crash. This also closes related edge cases, such as deletions applied with `-R` that would crash similarly, and mode-only changes whose mode lines were silently ignored.

The patch adds six new tests to `t/t4133-apply-filenames.sh` covering blank lines after `diff --git`, indented header lines, deletions with `-R`, and consecutive `diff --git` lines, verifying that both `--check` and actual application fail with the expected error. The series is based on commit `77904e546de3` and targets `maint`; it has received explicit endorsement from Junio C Hamano and substantive review from Phillip Wood, and merges cleanly with `master`, `next`, and `seen`.

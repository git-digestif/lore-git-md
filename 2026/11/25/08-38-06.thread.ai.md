Thread type: bug report/fix, first email in thread; no prior series version, no reviews or integration status yet, so status is under review/not known to be queued.

Core problem: `git push --no-thin` was silently ignored for smart HTTP remotes, so a thin pack could still be sent. Two causes are identified: `transport-helper.c` still listed `TRANS_OPT_THIN` in `unsupported_options[]`, a leftover from commit ef08ef9ea0 (2009) when `--no-thin` affected no transport, and `remote-curl.c` unconditionally ran `send-pack --thin`. Commit f7c815c3ee (2013) made `--no-thin` work for native transports, but not the helper path.

Proposed fix: remove `TRANS_OPT_THIN` from `unsupported_options[]` in `transport-helper.c` so the option reaches helpers; handle `TRANS_OPT_THIN` in `remote-curl.c` `set_option()` to toggle `options.thin`; document the new `option thin` capability in `Documentation/gitremote-helpers.adoc`. Backward compatibility relies on older helpers answering "unsupported", which push already ignores.

Key technical details: files/subsystems touched are `transport-helper.c`, `remote-curl.c`, `Documentation/gitremote-helpers.adoc`, and test `t/t5541-http-push-smart.sh`. New behavior: default smart HTTP push sends `pack-objects --thin`; with `--no-thin` it omits `--thin`. Test uses `GIT_TRACE2_EVENT` to assert `git pack-objects` invocation with and without `--thin`.

Motivating production scenario: pushing from a shallow treeless partial clone (`--filter=tree:0`) over HTTPS during a thin push causes lazy fetches for missing trees; measured as 37 lazy fetches without the fix versus 0 with `--no-thin`.

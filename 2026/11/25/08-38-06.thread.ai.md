Core problem: `git push --no-thin` was silently ignored for smart HTTP remotes, so a thin pack could still be sent. Two causes: `transport-helper.c` still listed `TRANS_OPT_THIN` in `unsupported_options[]` (leftover from ef08ef9ea0, 2009, when `--no-thin` affected no transport), and `remote-curl.c` unconditionally ran `send-pack --thin`. Commit f7c815c3ee (2013) made `--no-thin` work for native transports but not the helper path.

Proposed fix: remove `TRANS_OPT_THIN` from `unsupported_options[]` in `transport-helper.c` so the option reaches helpers; handle `TRANS_OPT_THIN` in `remote-curl.c` `set_option()` to toggle `options.thin` (which defaults to 1 in `cmd_main()`); document the new `option thin` capability in `Documentation/gitremote-helpers.adoc`. Backward compatibility relies on older helpers answering "unsupported", which push already ignores.

Key technical details: files/subsystems touched are `transport-helper.c`, `remote-curl.c`, `Documentation/gitremote-helpers.adoc`, and test `t/t5541-http-push-smart.sh`. Option flow: `set_helper_option()` recognizes the token in its `boolean_options[]` array and emits `option thin true` or `option thin false` via `strbuf_set_helper_option()`; `remote-curl.c` `set_option()` toggles `options.thin`, and `push_git()` consequently passes `--thin` to `send-pack` only when the flag is set. New behavior: default smart HTTP push sends `pack-objects --thin`; with `--no-thin` it omits `--thin`. Test uses `GIT_TRACE2_EVENT` to assert `git pack-objects` invocation with and without `--thin`.

Motivating production scenario: pushing from a shallow treeless partial clone (`--filter=tree:0`) over HTTPS during a thin push causes lazy fetches for missing trees; measured as 37 lazy fetches without the fix versus 0 with `--no-thin`. Junio suggested condensing this scenario into the commit message for clarity; Julian Maurin accepted this suggestion and will include the condensed wording in v2.

This is a cover letter for the fifth iteration of a five-patch series by Ravi Mistry that hardens Git's HTTP transport against transient server errors. The series addresses four gaps in the existing 429 rate-limit retry logic: an off-by-one retry counter, missing exponential backoff when servers omit Retry-After headers, inability to retry transient 5xx responses, and no retry support for read-only POST requests used during fetch, clone, and partial-clone blob fetches.

Version 5 exists specifically to resolve the two remaining review items from Junio C Hamano. Patch 3/5 now documents in `http.retryStatusCodes` that an empty configuration value disables retries entirely rather than restoring the default 429 behavior, and that 401 and 404 can never be retried regardless of configuration because `handle_curl_result()` checks them before consulting the retryable-code list; a new test covers the empty-string case. Patch 4/5 now clears the `struct slot_results results` variable with `memset` before each `run_one_slot()` call in both `post_rpc()` and `probe_rpc()`, preventing stale HTTP status or Retry-After values from being reported if a retry attempt fails to start. Patches 1/5, 2/5, and 5/5 are unchanged from v4.

The series touches `http.c`, `http.h`, `remote-curl.c`, `git-curl-compat.h`, documentation, and the test suite. It introduces the `http.retryStatusCodes` configuration key (default `"429"`, overridable via `GIT_HTTP_RETRY_STATUS_CODES`), exponential backoff computed as `http.retryAfter * 2^(attempt-1)` capped at `http.maxRetryTime`, and a new default of 10 seconds for `http.retryAfter`. Key functions include `is_retryable_http_code()`, `can_retry_rpc()`, `http_retry_wait()`, and `has_zero_or_past_retry_after()`. POST retries are restricted via `can_retry_rpc()` to `git-upload-pack` and `git-upload-archive`, explicitly excluding `git-receive-pack` to avoid duplicate processing of pushes.

The architectural debate over whether configurable retry codes should exist at all remains noted but unresolved, though the documentation now frames non-429 codes as temporary workarounds for provider infrastructure. With v5 addressing all acknowledged code issues, the series awaits Junio's final review of patch 5/5 and integration decision.

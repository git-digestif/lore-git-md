This is the third and final patch in a bugfix series hardening `git remote` against invalid branch names. Harald Nordgren closes out the series by addressing `git remote add -m`, the option that sets the default branch for a new remote's fetch refspec.

The problem was that `git remote add -m` previously validated its argument only after the remote had already been created and a fetch attempted, so a malformed name like `@{u}` could get as far as a network operation before failing with a confusing error and leaving a half-configured remote behind. This patch moves the validation up front: before the remote name and URL are processed, it constructs `refs/heads/<name>` and calls `check_refname_format()` on it. If the check fails, the command dies immediately with "'%s' is not a valid branch name", ensuring no configuration is ever written.

The implementation is a small inline block in the `add()` function in `builtin/remote.c`, placed right after the existing loop that validates `-t` arguments from the first patch. It uses the same error message as the earlier patches for consistency. A new test in `t/t5505-remote.sh` confirms that `git remote add -m "@{u}" badmaster bar` fails with the expected fatal message and that `git config get remote.badmaster.url` returns nothing, proving the remote was never persisted.

Together with patches 1/3 and 2/3, this completes the series' goal of making all three subcommands -- `git remote add -t`, `git remote set-branches`, and `git remote add -m` -- reject invalid branch names before any state changes occur. The patch is small, focused, and includes appropriate test coverage; it reads as a clean, well-motivated fix that rounds out the series nicely.

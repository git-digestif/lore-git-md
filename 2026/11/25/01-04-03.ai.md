This is a design-discussion reply within the v10 `--delete-merged`/`--delete-integrated` series, specifically addressing the wording of future `--dry-run` error messages for non-deletion operations.

Junio C Hamano responds to Harald Nordgren's proposal that `git branch --dry-run` error messages for branch creation (`git branch --dry-run <new> <start>`) and renaming (`git branch --dry-run -m <old> <new>`) avoid the word "yet" so as not to promise eventual support. Junio argues that while such minimalism might suit experimental commands like `git history`, `git branch` is part of everyday user toolsets, and refusing to signal future support may clash with end-user expectations for a mature command. The exchange leaves the code unchanged: patch 3/5's validation in `builtin/branch.c` (`if (dry_run && !delete && !delete_merged.nr)`) still governs behavior, accepting `--dry-run` only with deletion modes (`-d`, `-D`, `--delete-merged`, `--delete-integrated`) and rejecting it with a generic error for creation or rename arguments.

For future thread context, this email sharpens the unresolved question of how a follow-up `#leftoverbits` series should phrase specific rejection paths for `git branch --dry-run` with creation or `-m`/`-M` arguments. Junio's position favors wording that acknowledges the command's maturity and user expectations, while Harald prefers neutral text that makes no commitment about future support. No patch content is present here; the technical state remains that `--dry-run` scope is limited to deletion operations in v10, with per-operation error messages deferred to a separate series.

This is a discussion reply to Steve's RFC proposal for user-initiated recovery from stale `index.lock` files. Tanga Joris responds by pointing out that Git already has partial solutions for the components Steve suggested, while cautioning that fully automatic removal remains risky.

Tanga notes that since Git 2.54, the `core.lockfilePid` config option writes the PID of the lock holder into a sidecar file (e.g. `index~pid.lock`), allowing Git to tell the user whether the holding process is still alive when it encounters a locked index -- though the user must still remove the lock manually. For the "wait briefly" behavior Steve proposed, Tanga points to a series from Jun Wu currently in `seen` that adds `core.indexLockTimeout`, letting commands wait for the index lock before failing.

On the harder part of Steve's idea -- automatically removing the lock -- Tanga explains why it is problematic: PIDs can be reused by unrelated processes, and PID information is meaningless when the repository is accessed from multiple machines (e.g. over NFS). Tanga cites Junio's earlier wariness about even suggesting that users delete the lock manually, underscoring that the project considers automatic removal a step too far. The email closes with links to the `core.indexLockTimeout` series and the prior PID-file discussion.

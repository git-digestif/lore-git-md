This is a **substantive review** of the exponential backoff patch in the HTTP retry series. Brian M. Carlson, speaking from server-operator experience, objects to the patch’s decision to **retain the existing default of 0 for `http.retryAfter`** (immediate retry) when no Retry-After header is present. He argues that even a 429 response should trigger a **non-zero initial delay**—suggesting 30 seconds as a sensible default—rather than doubling from 0, which would still retry instantly on the first attempt. His concern is that immediate retries defeat the purpose of rate-limiting and risk further overwhelming the server.

The review does not engage with the patch’s implementation (attempt counting, doubling logic, or clamping) but instead challenges the **design premise**: whether the default behavior should prioritize fast recovery (current patch) or server protection (Carlson’s counter-proposal). This introduces a **potential point of contention**—the series’ cover letter frames the default as non-controversial, but Carlson’s position suggests otherwise. No alternative implementation is proposed, leaving the author to either defend the current approach or revise the default. The thread’s prior consensus (Junio’s feedback on v1/v2) did not surface this objection, so resolution may require broader input.

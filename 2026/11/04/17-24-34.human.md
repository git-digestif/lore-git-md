This is a feature patch for the promisor-remote subsystem, authored by Outreachy applicant Nelly Yopa.

The patch adds a new `promisor.fetchOrder` configuration variable that lets users specify the order in which Git should try multiple promisor remotes when fetching missing objects. Without this, Git simply uses the order the remotes appear in the config file, which can be awkward to manage across different config scopes (system, global, worktree). The new config takes a comma-separated list of remote names; listed remotes are tried first in the specified order, unlisted ones follow in their original config order. The existing special handling for the `extensions.partialClone` remote (which is always tried last) is preserved unless that remote is explicitly named in `fetchOrder`.

The implementation is clean and self-contained: a config parser in `promisor_remote_config()`, a one-time sort at initialization time, and a stable insertion sort that runs once per fetch attempt. The author explicitly chose not to validate the remote names in the config list, so a typo simply means the remote keeps its default position. The commit message is unusually candid about the lack of tests, explaining that the existing test fixture (`t5710`) does not trigger lazy fetches in a way that would expose the ordering change, and offering to write a follow-up fixture if needed.

This is a well-motivated, small-scale feature that addresses a real workflow friction without touching any other subsystem. The code is straightforward and the commit message is refreshingly clear about limitations. It looks ready for review and likely to be uncontroversial.

Thread identity: patch series converting `git credential` to use `OPT_SUBCOMMAND` from the parse-options API. Originating author: Wasswa Edson. Thread type: patch series (three patches in v2).

Core problem or goal: replace the manual `strcmp()`-based subcommand dispatch in `git credential` with the standard `OPT_SUBCOMMAND` mechanism used by other Git builtins. This change makes the code more idiomatic, enables per-subcommand usage strings and shell completion support, and fixes minor documentation inconsistencies (missing "capability" subcommand in usage, `[verse]` markup in man page synopsis).

Current status: v2 posted and complete. The series is split into three incremental patches: (1) align `-h` output with SYNOPSIS, (2) refactor each subcommand into its own function, (3) switch to `OPT_SUBCOMMAND`. All feedback from v1 has been addressed. Patch 3 has received substantive reviewer approval from Tanga Joris pending one minor documentation tweak, and the v2 cover letter has received a detailed tested review from Laveesh Bansal confirming the series works correctly. No merge status reported; still under review.

Key technical details:
- Files touched: `builtin/credential.c`, `git.c`, `Documentation/git-credential.adoc`, `t/t0300-credentials.sh`, `t/t0450/adoc-help-mismatches`.
- New static functions: `cmd_credential_fill`, `cmd_credential_approve`, `cmd_credential_reject`, `cmd_credential_capability` (one per subcommand), plus helper `parse_no_args` to centralize argument parsing and rejection logic.
- `NO_PARSEOPT` flag removed from `git.c` entry, making the command visible to `--list-cmds=parseopt`.
- Behavior changes: clearer error messages for missing/unknown subcommands (now rejected *before* reading stdin, avoiding unnecessary I/O -- confirmed by differential testing that `git credential bogus` previously blocked waiting on stdin but now exits immediately with code 129), subcommand-specific usage, rejection of extra arguments for each subcommand, improved `-h` output alignment with SYNOPSIS, and a noted change where `git credential <subcommand> --` and `--end-of-options` (end-of-options markers after subcommand) are now consumed by the option parser rather than causing a usage error, matching behavior of `git refs verify --` and `git reflog list --`. Core credential operations (fill, approve, reject, capability) remain unchanged with identical output and exit codes for valid input. The third patch completes the transition by rewriting the main dispatch logic to use `parse_options()` with `OPT_SUBCOMMAND` entries, enabling per-subcommand help via `git credential <subcommand> -h` and shell completion support via `--git-completion-helper`.
- Tests verify subcommand-specific help, error messages, and rejection of extra arguments. Bansal confirmed the new t0300 tests fail against an unpatched build (four failures), fail when the "too many arguments" check is removed (test 60), and that t0450 fails if the "credential" entry remains in `t/t0450/adoc-help-mismatches`, demonstrating the tests exercise the new behavior. The first patch also adds coverage for the `capability` subcommand in `t/t0450/adoc-help-mismatches`.

Open questions and loose ends: Tanga Joris requests that the commit message for patch 3 document the behavior change regarding the `--` end-of-options marker after a subcommand (previously a usage error, now accepted); Bansal has provided analysis supporting this change but the commit message update is still pending from the author. Bansal also raises whether a dedicated `_git_credential` bash completion script is intended as a follow-up, noting that while `git credential --git-completion-helper` exposes subcommand names, bash completion currently offers no suggestions for `git credential <TAB>` (the same gap seen with `git hook`). The thread is otherwise converged with multiple reviewer approvals pending only the commit message clarification and the open completion question.

This is an Outreachy proposal update from Cynthia Uche for the project *"Improve how command arguments and options are scanned and parsed"*, targeting the December 2026 round. The proposal is now in its second draft, incorporating feedback and new developments since the first version.

The core goal remains the same: extend the `early_scan_options()` API (introduced in Christian Couder’s `cc/early-scan-options` series, currently in `seen`) to additional Git commands that still perform ad-hoc argument scanning before `parse_options()`. The focus is on eliminating discrepancies between early scanning and `parse_options()` by converting commands like `git column`, `git bisect`, and `git check-ref-format` to use the new API.

Key updates since v1:
- Cynthia has actively engaged with the `early-scan-options` series, reviewing v3 and v4, and her feedback led to improvements in v4 (e.g., clearer documentation, a new test case, and fixes for edge cases). She also reviewed two other related patches, demonstrating a strong grasp of the codebase and the review process.
- The proposal now reflects the current state of the `early-scan-options` series (v4), which is closer to being merged to `next` (Junio and Kaartic have both indicated it looks good).
- The candidate inventory (section 4) has been refined with more detailed observations about each target command’s behavior, risks, and test coverage. For example, Cynthia manually tested `git column` and discovered that its "must be first argument" rule is inconsistently enforced, raising a question for the list about whether this is intentional.
- The timeline (section 5) remains realistic and flexible, with overlapping weeks to account for review cycles and the possibility of dropping lower-priority tasks if needed. The plan prioritizes incremental conversion (e.g., starting with `bisect_terms()` before `bisect_start()`) and thorough test coverage.

Notable points for discussion:
- The "must be first argument" rule for `git column --command` appears to be an artifact of hand-rolled parsing rather than a deliberate design choice. Cynthia’s testing shows it is inconsistently enforced, and the proposal suggests dropping it unless the community objects.
- `git check-ref-format` currently rejects options after `<refname>`, but the proposal questions whether this is desirable. Accepting options in any order would align with `parse_options()` behavior but could break scripts that rely on the current behavior.
- The proposal acknowledges risks like backward compatibility, test coverage, and edge cases (e.g., short options, `PARSE_OPT_KEEP_UNKNOWN_OPT`), and plans to coordinate with the community before making API changes.

Cynthia’s approach is methodical and community-oriented. She has already demonstrated the ability to identify edge cases, write tests, and engage constructively with reviewers. The proposal is well-motivated, technically grounded, and likely to receive positive feedback, though the questions about `git column` and `check-ref-format` may spark discussion. If accepted, this project would meaningfully improve Git’s argument parsing consistency while providing Cynthia with valuable experience in large-scale refactoring.

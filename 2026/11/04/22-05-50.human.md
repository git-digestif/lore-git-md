This is a review comment on the second patch in the v2 series improving Git’s HTTP transport resilience. The patch introduces exponential backoff for retries when servers return HTTP 429 (Too Many Requests) without a Retry-After header, doubling the delay on each retry (e.g., 1s, 2s, 4s) while clamping it at `http.maxRetryTime`.

brian m. carlson raises a **substantive objection** to the patch’s behavior: even when `http.retryAfter` is unset (defaulting to 0), the patch allows an immediate retry on a 429 response. They argue this is counterproductive, as the server explicitly signaled that the client is being too aggressive. As a server operator, they advocate for a **default delay of 30 seconds** when no Retry-After header is provided, rather than immediate retries. This is a clear departure from the patch’s current design, which preserves the existing default of 0 for backward compatibility.

The objection is well-motivated and reflects real-world operational concerns. It directly challenges the patch’s core assumption—that immediate retries are acceptable when no Retry-After header is present—and suggests a more conservative default. This could spark debate about whether the default should prioritize backward compatibility (current behavior) or server-friendliness (brian’s proposal). The thread’s earlier feedback from Junio C Hamano did not address this point, so it remains an open question for the series.

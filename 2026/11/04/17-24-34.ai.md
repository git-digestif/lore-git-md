This is a feature patch targeting the promisor-remote subsystem, authored by an Outreachy contributor. It introduces a new `promisor.fetchOrder` configuration variable that lets users specify the order in which Git tries multiple promisor remotes during lazy fetches, rather than relying on the order in which the remotes appear in the configuration file.

The patch adds about 70 lines to `promisor-remote.c` and one field to the `promisor_remote` struct. The implementation parses the comma-separated list of remote names in `promisor_remote_config()`, stores it in a file-static `string_list`, and applies the order during `promisor_remote_init()`. The actual sorting is a stable insertion sort that runs once at the start of `try_promisor_remotes()`. Remotes not listed in `fetchOrder` keep their original config order and sort after the explicitly ordered ones. The patch deliberately does not validate the remote names in the list, treating typos as "not listed" to keep the parser simple.

The commit message is unusually candid about the lack of tests: the author explains that the existing `t5710` fixture never actually triggers a lazy fetch, so the ordering change cannot be observed. They offer to write a new fixture as a follow-up if that is the right direction. The patch is well-explained, with clear rationale and a detailed walk-through of the code changes.

This is a standalone patch (not part of a series) and appears to be the author’s first contribution to the Git project. The feature addresses a real usability pain point for users with multiple promisor remotes, and the implementation is small, focused, and follows Git’s config-parsing conventions. The only open question is test coverage, which the author has flagged for follow-up.

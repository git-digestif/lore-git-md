This is the second patch in Farid Zakaria’s two-patch bugfix series targeting a race condition in the Git credential-cache daemon. The series, now in its second iteration, addresses a real and disruptive issue: when multiple `git credential-cache store` commands run concurrently (common during parallel submodule fetches), one daemon can unlink another’s socket, causing credential loss, orphaned daemons, and inaccessible passwords.

This patch specifically prevents a second daemon from hijacking the socket of an already-running daemon by switching from `unix_stream_listen()` to `unix_ss_create()`. The change is technically sound and aligns with the pattern used in the `fsmonitor--daemon.c` code. The patch also adds test coverage in `t/t0301-credential-cache.sh` to verify the fix, though the test may not have failed pre-patch due to the client’s ping mechanism masking the race.

Farid’s reply to Patrick Steinhardt’s review clarifies a key design choice: the daemon prints “ok” when it detects an existing socket because the client (`builtin/credential-cache.c:spawn_daemon()`) expects that response before attempting to connect. This is part of the client-daemon protocol, not an arbitrary success message. Farid plans to add a comment explaining this and use `exit(0)` for clarity, addressing Jeff King’s earlier suggestion. The redundant cleanup comment will be removed.

The patch is well-motivated, narrowly scoped, and uncontroversial in its core logic. The only remaining architectural question—whether to mix `unix_ss_*` and `tempfile` APIs—was raised by Junio in the v1 thread and will likely be resolved in v2 by dropping `tempfile` registration, following `fsmonitor--daemon.c` precedent. For users affected by the race, this fix is worth attention.

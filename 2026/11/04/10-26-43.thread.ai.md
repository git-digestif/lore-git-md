Subject: [Outreachy] Configurable fetch ordering for promisor remotes in partial clones
Series version: proposal (not a patch series)
Originating author: Shashank S Mogaveera
Thread type: project proposal (Outreachy)

Core problem or goal
Allow users of partial clones to configure the order in which Git queries multiple promisor remotes when fetching missing objects, replacing the current hardcoded fallback order (remotes queried in configuration order, with `core.partialClone` as last-resort fallback) with a deterministic, user-configurable list (`promisor.fetchOrder`). The proposal also includes a server-side Protocol v2 extension to advertise preferred priorities, with client configuration taking precedence.

Current status
Proposal stage; no code written yet. The author has documented the current behavior using GIT_TRACE2 and has four prior microprojects merged (two to `master`, one to `next`, one to `seen`). Kaartic Sivaraam has provided a substantive review of the 13-week plan, raising questions about timeline clarity, config format (`promisor.fetchOrder` as list-valued vs. per-remote integers), and server-side advertisement details (`promisor.sendFields` ambiguity). The proposal remains under discussion; no implementation has begun.

Key technical details
- New config key: `promisor.fetchOrder` (list-valued, composable; format still under discussion)
- Server-side: Protocol v2 extension to advertise preferred priorities; gating mechanism unclear (`promisor.sendFields` may refer to a new field in the existing advertisement rather than a new config key)
- Client config overrides server-advertised order
- Edge cases: unlisted remotes (proposal: append them in configuration order), `partialClone`-last rule preserved, precedence conflicts between client and server priorities
- Subsystems: promisor remote, partial clone, Protocol v2
- Test coverage: baseline behavior already traced with GIT_TRACE2; future implementation will include unit and integration tests
- Timeline: 13-week plan split into four phases (baseline documentation, client-side configuration, server-side protocol extension, upstreaming); exact patch submission dates and RFC discussion timeline still unspecified

Open questions and loose ends
- Whether the server-side advertisement should be opt-in or always-on
- How to handle unlisted remotes (proposal: append them in configuration order)
- Whether to cache failed remotes dynamically (stretch goal)
- Config format for `promisor.fetchOrder` (list-valued vs. per-remote integers)
- Clarity of `promisor.sendFields` reference (existing config key vs. new field in advertisement)
- Precedence rules for conflicts between client config and server-advertised priorities
- Upstreaming strategy: client-side first, then server-side; exact patch submission and RFC discussion dates unspecified
- Potential difficulties and edge cases not yet explored in the proposal

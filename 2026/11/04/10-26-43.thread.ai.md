Subject: [Outreachy] Configurable fetch ordering for promisor remotes in partial clones
Series version: proposal (not a patch series)
Originating author: Shashank S Mogaveera
Thread type: project proposal (Outreachy)

Core problem or goal
Allow users of partial clones to configure the order in which Git queries multiple promisor remotes when fetching missing objects, replacing the current hardcoded fallback order (remotes queried in configuration order, with `core.partialClone` as last-resort fallback) with a deterministic, user-configurable list (`promisor.fetchOrder`). The proposal also includes a server-side Protocol v2 extension to advertise preferred priorities, with client configuration taking precedence.

Current status
Proposal stage; no code written yet. The author has documented the current behavior using GIT_TRACE2 and has four prior microprojects merged (two to `master`, one to `next`, one to `seen`). This follow-up email is administrative only (Usman Akinyemi reminding Shashank to submit the formal application on the Outreachy website) and does not alter the technical proposal or timeline.

Key technical details
- New config key: `promisor.fetchOrder` (list-valued, composable)
- Server-side: Protocol v2 extension gated by `promisor.sendFields` config (opt-in vs. always-on still under discussion)
- Client config overrides server-advertised order
- Edge cases: unlisted remotes (proposal: append them in configuration order), `partialClone`-last rule preserved
- Subsystems: promisor remote, partial clone, Protocol v2
- Test coverage: baseline behavior already traced with GIT_TRACE2; future implementation will include unit and integration tests
- Timeline: 13-week plan split into four phases (baseline documentation, client-side configuration, server-side protocol extension, upstreaming)

Open questions and loose ends
- Whether the server-side advertisement should be opt-in (`promisor.sendFields`) or always-on
- How to handle unlisted remotes (proposal: append them in configuration order)
- Whether to cache failed remotes dynamically (stretch goal)
- Upstreaming strategy: client-side first, then server-side

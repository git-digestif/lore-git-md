Subject: [Outreachy] Configurable fetch ordering for promisor remotes in partial clones
Series version: proposal (not a patch series)
Originating author: Shashank S Mogaveera
Thread type: project proposal (Outreachy)

Core problem or goal
Allow users of partial clones to configure the order in which Git queries multiple promisor remotes when fetching missing objects, replacing the current hardcoded fallback order (remotes queried in configuration order, with `core.partialClone` as last-resort fallback) with a deterministic, user-configurable list (`promisor.fetchOrder`). The proposal also includes a server-side Protocol v2 extension to advertise preferred priorities, with client configuration taking precedence.

Current status
Proposal stage; no code written yet. The author has documented the current behavior using GIT_TRACE2 and revised the 13-week plan in response to Kaartic Sivaraam’s substantive review. Key adjustments: (1) baseline documentation phase front-loaded into the first week, (2) client-side patch submission moved to early in the client-side phase (weeks 3–5), (3) config format (`promisor.fetchOrder`) and server-side advertisement mechanism deferred to a dedicated RFC, (4) precedence rules clarified (client config overrides server-advertised order), and (5) implementation risks identified (two-pass behavior preservation, protocol backward compatibility). The proposal is now design-driven, with RFC discussion milestones replacing prior assumptions. Phase 0 validation completed: Git built from source, promisor-remote and partial-clone test suites passed, and manual GIT_TRACE2 verification of configured-remote ordering and fallback behavior.

Key technical details
- New config key: `promisor.fetchOrder` (format still under discussion: list-valued vs. per-remote integers; RFC forthcoming)
- Server-side: Protocol v2 extension to advertise preferred priorities via a new field in the promisor-remote advertisement, gated by the existing `promisor.sendFields` config (not a new config key); backward compatibility ensured (older clients ignore unknown fields)
- Client config overrides server-advertised order; unranked remotes sorted by server preference
- Edge cases: unlisted remotes appended in configuration order, `partialClone`-last rule preserved, malformed protocol values handled safely
- Subsystems: promisor remote, partial clone, Protocol v2
- Test coverage: baseline behavior traced with GIT_TRACE2; future implementation will include unit and integration tests for ordering, precedence, and protocol compatibility
- Timeline: 13-week plan split into four phases (baseline documentation, client-side configuration, server-side protocol extension, upstreaming), with RFC discussion for config format and server-side mechanism scheduled early

Open questions and loose ends
- Config format for `promisor.fetchOrder` (list-valued vs. per-remote integers; RFC to compare layering, duplicate/unknown remotes, and interactions with `extensions.partialClone`)
- Server-side advertisement field definition and backward-compatibility guarantees (RFC to define field and ensure safe handling by older clients)
- Dynamic caching of failed remotes (stretch goal, not yet explored)
- Upstreaming strategy: exact patch submission and RFC discussion dates still unspecified, but client-side patch expected early in the client-side phase (weeks 3–5)
- Potential edge cases not yet explored (e.g., malformed protocol values, precedence conflicts in mixed client/server configurations)

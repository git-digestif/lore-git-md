Thread identity: Bugfix series for loose object database (ODB) cache invalidation during `git merge`. Two-patch series (`[PATCH v1 1/2]` and `[PATCH v1 2/2]`), initial submission by Patrick Steinhardt, now with a maintainer-approved `NEEDSWORK` comment in `odb.h` documenting the `QUICK` flag's known limitations and the unresolved staleness issues.

Core problem or goal: Fix a bug where newly written merged blobs in `git merge` cannot be read back due to stale loose object cache entries, causing Git to incorrectly assume the objects are missing locally and triggering unnecessary, failing backfill fetches from promisor remotes. The deeper issue is that **any code path using `QUICK` object existence checks (e.g., `prefetch_cache_entries()`) is vulnerable to false negatives**, as the `QUICK` flag is intended to tolerate false negatives but the current design fails to handle them gracefully—when a promisor remote fetch fails for a local-only object, Git errors out instead of silently recovering.

Current status: **Ready for `next` with documentation caveat**. The maintainer (Junio C Hamano) has finalized the decision to land the current patch (2/2) as a targeted regression fix while documenting the broader `QUICK` flag limitations in `odb.h` via a `NEEDSWORK` comment. The comment’s placement was debated between `OBJECT_INFO_QUICK` (Patrick’s preference) and `OBJECT_INFO_FOR_PREFETCH` (Junio’s initial proposal), with the final decision deferred to Junio’s discretion. The patch is expected to proceed to `next` once the comment is added, pending no further substantive objections. Patch 1/2 received a minor type-consistency suggestion from Toon Claes (`uint32_t` for the `mask` variable in `subdir_seen_bitmap()`), which is cosmetic and unlikely to block progress.

Key technical details:
- Files touched: `odb/source-loose.c` (core ODB component, patches 1/2 and 2/2), `t/t5616-partial-clone.sh` (test coverage, patch 2/2), and `odb.h` (new `NEEDSWORK` comment targeting either `OBJECT_INFO_QUICK` or `OBJECT_INFO_FOR_PREFETCH`).
- Subsystems: Loose object database cache, promisor remote backfill logic, `QUICK` object existence checks.
- New symbols: `subdir_seen_bitmap()` (extracted helper function in `odb/source-loose.c`, patch 1/2), `loose_cache_mark_seen()` (cache update helper, patch 2/2).
- Behavior change: Patch 1/2 is a pure refactoring with no behavior change; patch 2/2 ensures loose object cache is properly invalidated after writing merged blobs, preventing false "object missing" errors during `git merge`. The `NEEDSWORK` comment in `odb.h` flags the `QUICK` flag’s broader issues, linking to the mailing list discussion.
- Unaddressed issues: The fix does not cover:
  - Objects written by other processes (e.g., `git repack`, `git log`, or helper processes in `git merge`).
  - False positives (objects cached as present but later pruned).
  - Performance trade-offs of omitting `QUICK` in prefetch paths (e.g., `prefetch_cache_entries()`).
- On-disk format: No changes.
- Test coverage: New test in `t/t5616-partial-clone.sh` (patch 2/2) validates the fix using a partial clone setup with 50 mergeable files to ensure realistic conditions. The test verifies that `git merge` correctly handles locally written objects without attempting to fetch them from the promisor remote, but it does not cover racy staleness or other `QUICK`-dependent code paths.
- Performance impact: Jeff King (Peff) provides benchmark data showing a **1320% slowdown** in the `p5550.4: fetch` benchmark when `QUICK` is omitted in tag-following logic, though he notes this is a pathological case. The `RECHECK_PACKED` flag (inverse of `QUICK`) is introduced as an alternative for callers needing full rescans.

Open questions and loose ends:
1. **`QUICK` flag**: Should it be removed entirely (Patrick’s preference), omitted only in prefetch paths (Jeff’s suggestion), or retained with improved cache invalidation? The `NEEDSWORK` comment ensures this remains visible but does not resolve it. Jeff King’s benchmark data quantifies the performance cost of removing `QUICK`, showing significant slowdowns in some workloads (e.g., tag-following in `builtin/fetch.c`).
2. **Racy staleness**: Should the fix address objects written by other processes, or is this a separate issue? No consensus yet.
3. **False positives**: How should Git handle objects cached as present but later pruned? This remains unaddressed.
4. **Performance impact**: What is the cost of omitting `QUICK` in prefetch paths, and is it acceptable for correctness? Jeff highlights the potential expense of re-scanning packs for large prefetches and provides concrete benchmark data.
5. **API evolution**: The `odb_has_object()` API now defaults to `QUICK`-like behavior, requiring callers to opt into full rescans via `ODB_HAS_OBJECT_RECHECK_PACKED`. This design choice may need revisiting if `QUICK` is removed.
6. **Follow-up work**: Will the `NEEDSWORK` comment be sufficient to drive a future audit of `QUICK` users, or are additional safeguards (e.g., CI checks, static analysis) needed?
7. **Comment placement**: The final location of the `NEEDSWORK` comment in `odb.h` (either `OBJECT_INFO_QUICK` or `OBJECT_INFO_FOR_PREFETCH`) remains unresolved but is a minor detail.

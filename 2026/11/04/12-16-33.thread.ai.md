Thread identity: Bugfix series for loose object database (ODB) cache invalidation during `git merge`. Two-patch series (`[PATCH v1 1/2]` and `[PATCH v1 2/2]`), initial submission by Patrick Steinhardt.

Core problem or goal: Fix a bug where newly written merged blobs in `git merge` cannot be read back due to stale loose object cache entries, causing Git to incorrectly assume the objects are missing locally and triggering unnecessary, failing backfill fetches from promisor remotes. The deeper issue, as identified by Jeff King, is that **any code path using `QUICK` object existence checks (e.g., `prefetch_cache_entries()`) is vulnerable to false negatives**, not just the specific case of `git merge` writing loose objects. The `QUICK` flag is intended to tolerate false negatives, but the current design fails to handle them gracefully—when a promisor remote fetch fails for a local-only object, Git errors out instead of silently recovering.

Current status: **Under active design discussion**. The series was previously approved for merging by Junio C Hamano and reviewers, but Jeff King’s substantive review raises fundamental questions about the root cause and long-term correctness of the fix. The current patch (2/2) introduces `loose_cache_mark_seen()` to update the loose object cache after writing new objects, but Peff argues this is a band-aid that leaves other code paths (e.g., `prefetch_cache_entries()`) and racy staleness (objects written by other processes) unaddressed. No new patch version has been posted yet.

Key technical details:
- Files touched: `odb/source-loose.c` (core ODB component), `t/t5616-partial-clone.sh` (test coverage, in patch 2/2).
- Subsystems: Loose object database cache, promisor remote backfill logic, `QUICK` object existence checks.
- New symbols: `subdir_seen_bitmap()` (extracted helper function in `odb/source-loose.c`, patch 1/2), `loose_cache_mark_seen()` (cache update helper, patch 2/2).
- Behavior change: Patch 1/2 is a pure refactoring with no behavior change; patch 2/2 ensures loose object cache is properly invalidated after writing merged blobs, preventing false "object missing" errors during `git merge`. However, Jeff King’s review highlights that this does not address:
  - Objects written by other processes (e.g., `git repack`, `git log`, or helper processes in `git merge`).
  - False positives (objects cached as present but later pruned).
  - Performance trade-offs of omitting `QUICK` in prefetch paths.
- On-disk format: No changes.
- Test coverage: New test in `t/t5616-partial-clone.sh` (in patch 2/2) validates the fix using a partial clone setup with 50 mergeable files to ensure realistic conditions. The test verifies that `git merge` correctly handles locally written objects without attempting to fetch them from the promisor remote. However, it does not cover racy staleness or other `QUICK`-dependent code paths.

Open questions and loose ends:
1. **Scope of the fix**: Should the current patch proceed as-is (minimal disruption) or be expanded to address the broader class of `QUICK`-related bugs and racy staleness?
2. **Alternative approaches**: Jeff King proposes two alternatives:
   - Omit `QUICK` in prefetch paths (e.g., `prefetch_cache_entries()`), forcing a full re-scan of the ODB. This would catch locally written objects but could be expensive for large prefetches.
   - Reconsider the cache-flushing logic removed in commit `5946a564cdd`, which previously flushed caches on `SECOND_READ` (a fallback for missing objects). Peff argues this was a useful optimization signal, not just a correctness hack.
3. **Performance impact**: What is the cost of omitting `QUICK` in prefetch paths, and is it acceptable for correctness?
4. **Racy staleness**: Should the fix address objects written by other processes, or is this a separate issue to be tackled later?
5. **False positives**: How should Git handle objects cached as present but later pruned (a separate but related problem)?

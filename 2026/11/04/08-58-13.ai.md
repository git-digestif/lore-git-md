This is an Outreachy applicant's RFC for the promisor remote fetch ordering project.

Yopa Nelly (an Outreachy applicant working with mentor Kaartic Sivaraam) proposes two possible configuration shapes for controlling the order in which Git tries promisor remotes when fetching missing objects. The current behavior is that remotes are tried in config-file order, with the `extensions.partialClone` remote always moved to the end, and there is no user-facing way to override this.

The two options presented are:
1. A numeric priority per remote (`remote.<name>.promisorPriority = <number>`)
2. A global ordered list (`promisor.fetchOrder = <comma-separated list>`)

Yopa expresses a preference for the list-based approach, arguing that it is more readable, easier to override across multiple config files, and maps cleanly to the existing linked-list implementation. The numeric approach raises questions about default values for unconfigured remotes.

Three open questions are raised:
- How to handle a remote named in the list that is not actually a promisor remote (error, warning, or ignore)
- Whether an explicit list entry should override the automatic move of `extensions.partialClone` to the end
- Whether different fetch orders might be needed depending on the source remote, which could favor the per-remote numeric approach

The email is a request for early feedback on the design before implementation begins. It demonstrates a solid understanding of the current code (`promisor-remote.c`, `t5710`) and a thoughtful approach to configuration ergonomics. The tone is appropriately tentative and open to input.

This is a **bugfix patch** addressing a regression in Git's HTTP authentication layer, where `WWW-Authenticate` headers are lost during redirects. The patch is now in its second iteration (`v2`) and has attracted **substantive review** from Jeff King (Peff) and a detailed response from Matthew Cheetham, the original author of the `wwwauth_headers` mechanism.

The core issue is straightforward: when Git follows an HTTP redirect, it updates the credential struct for the new URL but clears the `wwwauth_headers`—server-provided authentication challenges—breaking OAuth2 or other token-based flows. The fix introduces a helper function, `credential_update_url()`, to preserve these headers during the URL update. Peff’s review confirms the patch is technically sound ("OK as-is") but questions the necessity of the helper, preferring the v1’s inline approach for clarity. He also suggests adding a `BUG()` check to enforce that `wwwauth_headers` are never populated by `credential_from_url()`, reinforcing the security invariant that these headers are server-provided, not URL-derived.

Matthew Cheetham’s reply provides valuable context: he acknowledges the awkwardness of storing `wwwauth_headers` in the credential struct (a design choice made for convenience in the original implementation) and shares that he’s explored broader refactoring to separate HTTP client state from per-request state. However, he agrees the current patch is a pragmatic fix and confirms that the headers are correctly scoped to the final redirect target, not the original server. His feedback aligns with Peff’s assessment that the patch is safe and necessary, though the helper’s design remains a minor point of debate.

The patch includes a new test in `t/t5563-simple-http-auth.sh` that verifies header preservation using a custom Apache rewrite rule, and the commit message clearly explains the security rationale.

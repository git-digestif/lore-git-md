This is the v2 cover letter for a three-patch bugfix series targeting the credential-cache daemon. The series fixes two race conditions that occur when multiple `git credential-cache store` commands run simultaneously and both attempt to start a daemon. The races can cause credential loss, orphaned daemons, and inaccessible passwords—real-world issues for users with large repositories, particularly during parallel submodule fetches over HTTPS.

The v2 series adds a preparatory patch (patch 1) that fixes a pre-existing permission-handling issue in the socket directory by replacing `safe_create_leading_directories()` with `safe_create_leading_directories_no_share_const()`. This ensures `core.sharedRepository` does not incorrectly apply to user-specific credential-cache directories. Patches 2 and 3 remain focused on the core race conditions: patch 2 allows the daemon to handle a concurrently created socket directory by ignoring `EEXIST` from `mkdir()`, and patch 3 prevents socket hijacking by using `unix_ss_create()` to safely handle concurrent socket creation. If a second daemon detects an existing socket, it prints "ok" and exits, allowing its client to communicate with the running daemon.

The series includes thorough test coverage in `t/t0301-credential-cache.sh`, exercising both the `mkdir()` race and the socket hijacking race. Documentation improvements in v2 include reworded commit messages in the imperative mood, a code comment explaining the "ok" response (part of the client-daemon protocol), and the use of `exit(0)` for clarity. The author acknowledges Junio’s open architectural concern about mixing `unix_ss_*` and `tempfile` APIs in patch 3 but has not yet addressed it in this iteration. The concern stems from the risk that `tempfile` registration bypasses `unix_ss_was_stolen()`, potentially allowing a dying daemon to remove a socket it no longer owns.

The series is well-motivated, with clear explanations of the problem and its consequences. The preparatory patch in v2 addresses a latent issue identified during review, and the core fixes are uncontroversial. The open architectural question about API mixing is the only remaining loose end, and the author indicates willingness to revisit it in a future iteration if required. The patches are likely to be merged once this concern is resolved, as the fixes are narrowly scoped and address a real, user-visible bug.

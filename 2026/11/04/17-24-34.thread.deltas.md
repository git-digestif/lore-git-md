# Thread deltas

## 2026/11/04

- [2026/11/04/17-24-34 by Yopa Nelly <yopatatchou@gmail.com>] Yopa Nelly submitted a patch adding a `promisor.fetchOrder` config variable (comma-separated remote names) so that listed promisor remotes are tried first in the specified order when fetching missing objects, with unlisted remotes following in original config order and the `extensions.partialClone` remote still last unless explicitly listed; the ordering is applied via a stable insertion sort in `promisor_remote_sort()` called at the start of each pass in `try_promisor_remotes()`, preserving the existing accepted-remotes-first behavior. The patch does not validate `fetchOrder` entries against configured remotes (typos keep default position) and includes no test because the t5710 fixture never triggers a lazy fetch, with the author offering to write a follow-up test using a fixture with two client promisor remotes.

## 2026/11/05

- [2026/11/05/14-30-33 by Tanga Joris <tangajoris@gmail.com>] Tanga Joris reviewed the v1 patch and reported that setting `promisor.fetchOrder` triggers a BUG in `string_list_split_in_place()` because the list was created with `STRING_LIST_INIT_DUP` while `string_list_split_in_place_f()` is used (suggesting `string_list_split_f()` instead); also noted the list is never cleared so values from several config files pile up, and that it is file-static so all repositories in the process (e.g. submodules) share it while the rest of the promisor config is per-repository. He suggested a test in t0410-partial-clone.sh (which already has a two-promisor-remote test), adding the variable to Documentation/config/promisor.adoc, and fixing a line indented with spaces instead of a tab.
- [2026/11/05/16-31-22 by Kaartic Sivaraam <kaartic.sivaraam@gmail.com>] Kaartic Sivaraam said the commit message partly reads like it is addressing the list rather than describing the change (pointing to SubmittingPatches#describe-changes), and questioned whether the patch skips the RFC step expected of the microproject, asking if the microproject guides were misunderstood.
- [2026/11/05/22-52-23 by Yopa Nelly <yopatatchou@gmail.com>] Yopa Nelly posted [PATCH v2] of "promisor-remote: honor promisor.fetchOrder when trying remotes": the parsed list now lives in `struct promisor_remote_config` and is re-parsed on each config read; instead of sorting the linked list at fetch time, `try_promisor_remotes()` walks the list twice (fetchOrder order for named remotes, then original config order for the rest); documentation for `promisor.fetchOrder` was added to Documentation/config/promisor.adoc. No test was included.
- [2026/11/05/22-55-42 by Tatchou Yopa Nelly <yopatatchou@gmail.com>] Yopa Nelly confirmed to Tanga Joris that v2 addresses his review: fetch_order is per-repository in `struct promisor_remote_config`, initialized with `string_list_init_nodup()` so the BUG is gone (reproduced his exact sequence), docs added, whitespace fixed, and the insertion sort replaced by the two-pass walk; a test was still not added (t0410-partial-clone.sh to be considered for v3 or a follow-up). She also said she rewrote the commit message per SubmittingPatches and asked Kaartic Sivaraam whether to send the design RFC first or keep the patch as a prototype while the config shape is discussed.
- [2026/11/05/23-09-38 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano asked Christian (the promisor-remote go-to person who worked on letting the server tell clients which promisors to use first) how the new `promisor.fetchOrder` client-side ordering would mesh with that server-side work.

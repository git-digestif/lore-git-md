This is a v2 bugfix series for the credential-cache daemon, addressing a race condition where concurrent daemon starts can cause credential loss, orphaned daemons, and inaccessible passwords. The series now consists of three patches, adding a preparatory fix for a pre-existing permission issue in the socket directory.

The new first patch replaces `safe_create_leading_directories()` with `safe_create_leading_directories_no_share_const()` to prevent `core.sharedRepository` from incorrectly applying permissions to the user-specific credential-cache socket directory. This addresses a latent issue Patrick Steinhardt identified in v1, where the original function could create directories with overly permissive settings.

The core race-condition fixes remain in patches 2 and 3. Patch 2 makes the daemon ignore `EEXIST` from `mkdir()`, allowing it to handle a concurrently created socket directory. Patch 3 uses `unix_ss_create()` to safely handle socket creation, ensuring a second daemon does not hijack an existing one's socket. If a second daemon detects an existing socket, it prints "ok" and exits, letting its client communicate with the running daemon.

The v2 changes respond to feedback from Jeff King and Patrick Steinhardt, improving documentation and clarity. Commit messages are now in imperative mood, and patch 3 includes a clearer explanation of the "ok" response in the client-daemon protocol. The author also added `exit(0)` for better readability in the exit path. The architectural concern Junio Hamano raised about mixing `unix_ss_*` and `tempfile` APIs remains unresolved; the author notes this could be addressed in a v3 if required.

This series looks well-crafted and addresses a real problem with clear consequences for users. The added test coverage in `t/t0301-credential-cache.sh` strengthens confidence in the fix. The unresolved API-mixing concern is the only potential sticking point, but the patches otherwise appear uncontroversial and ready for further review.

This thread is an Outreachy proposal by Shashank S Mogaveera to make the fetch order of promisor remotes configurable in partial clones. Currently, Git queries multiple promisor remotes in a hardcoded order (configuration order, with `core.partialClone` as a last-resort fallback). Shashank’s proposal introduces a new `promisor.fetchOrder` configuration key that lets users specify a deterministic order, along with a server-side Protocol v2 extension to advertise preferred priorities—though client configuration would override any server-advertised order.

The proposal is still in the design phase, with no code written yet. Shashank has documented the current behavior using `GIT_TRACE2` and outlined a 13-week implementation plan split into four phases: baseline documentation, client-side configuration, server-side protocol extension, and upstreaming. Open questions include whether the server-side advertisement should be opt-in or always-on, how to handle unlisted remotes (proposed: append them in configuration order), and whether to dynamically cache failed remotes as a stretch goal. The upstreaming strategy is to land the client-side changes first, followed by the server-side extension.

So far, the only participant is Shashank, who has corrected minor administrative details (a CC line typo and broken links to prior microprojects) in a follow-up email. Usman Akinyemi’s recent reply is purely procedural, reminding Shashank to submit the formal application on the Outreachy website—it doesn’t engage with the technical content or alter the proposal. The thread remains open for feedback, but no substantive reviews or objections have been raised yet.

This Outreachy project proposal by Shashank S Mogaveera aims to make the fetch order of promisor remotes configurable in partial clones, replacing the current hardcoded fallback logic with a user-defined list (`promisor.fetchOrder`). The proposal also includes a server-side Protocol v2 extension to advertise preferred priorities, though client configuration would take precedence.

Kaartic Sivaraam, a frequent and respected reviewer, has provided substantive feedback on the proposal. He suggests refining the 13-week timeline by clarifying when the client-side configuration patch will be sent to the list and questioning whether the initial two-week documentation phase is necessary. On the design side, he flags ambiguity around the `promisor.sendFields` reference (which already exists) and recommends settling the choice between a list-valued config and per-remote integers in a separate RFC before implementation. Kaartic also encourages Shashank to anticipate edge cases, such as precedence conflicts between client and server priorities, and to disclose any scheduling constraints (e.g., exams or vacations) that might affect availability.

The proposal remains in the design phase, with no code written yet. Key open questions include whether the server-side advertisement should be opt-in or always-on, how to handle unlisted remotes, and the upstreaming strategy (client-side first, then server-side). Shashank’s prior merged contributions demonstrate familiarity with the mailing list workflow, and the project builds on existing partial clone and promisor remote infrastructure. The next steps involve addressing Kaartic’s feedback and submitting the formal Outreachy application.

This Outreachy proposal thread is about allowing users of partial clones to configure the order in which Git queries multiple promisor remotes when fetching missing objects. The author, Shashank S Mogaveera, has revised the proposal in response to substantive feedback from Kaartic Sivaraam, addressing concerns about timeline clarity, config format, and server-side protocol details.

The proposal now front-loads the baseline documentation phase into the first week, reserving the remaining time for review and RFC discussion. The client-side patch will be sent early in the client-side phase (weeks 3–5). Instead of pre-selecting a config format for `promisor.fetchOrder`, Shashank will open an RFC to compare list-valued and numeric per-remote priority approaches, covering configuration layering and edge cases. The server-side protocol extension is clarified as a new field in the promisor-remote advertisement, gated by the existing `promisor.sendFields` config, with backward compatibility ensured. Local client config will take absolute precedence over server-advertised order.

Shashank has also validated the current behavior by building Git from source, running the relevant test suites, and manually verifying remote ordering and fallback behavior. The proposal now identifies implementation risks, such as preserving the two-pass behavior for accepted and unaccepted remotes and ensuring protocol field robustness. The timeline is more realistic, accounting for review cycles, and the open questions are framed as RFC topics. The next steps involve mailing-list discussions to settle the config format and server-side protocol details before implementation begins.

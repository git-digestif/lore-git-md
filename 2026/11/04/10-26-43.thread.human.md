This Outreachy project proposal by Shashank S Mogaveera aims to make the order in which Git queries multiple promisor remotes configurable for partial clones. Currently, Git uses a hardcoded fallback order when fetching missing objects, but Shashank proposes replacing this with a user-configurable list (`promisor.fetchOrder`) and a server-side Protocol v2 extension to advertise preferred priorities—though client configuration would take precedence.

Shashank has already contributed four microprojects to Git (two merged to `master`, one in `seen`, and one under review), demonstrating familiarity with the mailing list workflow. The proposal is well-structured, with a 13-week timeline split into phases: documenting the current behavior (already done using `GIT_TRACE2`), implementing client-side configuration, adding the server-side protocol extension, and upstreaming. Edge cases—like unlisted remotes and preserving the `partialClone`-last fallback—are explicitly addressed. The proposal is technically grounded, touching the promisor remote, partial clone, and Protocol v2 subsystems, and includes open questions about whether the server-side advertisement should be opt-in and how to handle dynamic caching of failed remotes.

No code has been written yet, but the plan is concrete and testable. The follow-up email corrected only administrative details (a CC line typo and broken links) without altering the technical content. Shashank’s prior contributions and the proposal’s clarity suggest this is a serious effort with a realistic chance of landing.

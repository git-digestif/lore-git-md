This is a follow-up in the ongoing policy discussion about pre-commit hooks and index mutation. Kevin Lyles acknowledges Chris Torek’s explanation that Git’s rollback machinery makes it impossible for pre-commit hooks to reliably modify the index, and accepts that this behavior is unsupported by design. However, he raises practical concerns about migrating his company’s workflow away from hook-based index mutation.

The core issue is performance in large repositories: Lyles’ team uses pre-commit hooks to automatically apply formatting or metadata changes to staged files, but their repository is large enough that running `git ls-files` (needed to batch-process files in a clean filter) takes 500 ms to 5 seconds—an unacceptable delay for interactive use. They want to preserve the existing workflow where developers can stage partial changes (`git add -p`) and commit without manual steps, while still applying automated transformations.

Lyles explores two alternatives but finds both problematic. A wrapper script (as suggested by Torek) would require developers to change their habits, which they’re trying to avoid. A clean filter could work, but only if it knows the full list of files to be committed upfront—otherwise, performance degrades unpredictably. The thread now shifts from a policy debate to a search for a technically feasible workaround that doesn’t sacrifice usability or performance. No code changes are proposed yet, but the discussion highlights a real-world tension between Git’s design constraints and user needs.

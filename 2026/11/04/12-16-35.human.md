This is the second patch in a two-patch bugfix series targeting a subtle but serious issue in Git’s loose object database (ODB) cache. The bug surfaces during `git merge` in partial clones: after writing merged blobs as loose objects, Git fails to update its internal cache, causing subsequent existence checks to incorrectly report the objects as missing. This triggers unnecessary—and doomed—backfill fetches from promisor remotes, breaking the merge.

The fix is surgical: it adds a new helper, `loose_cache_mark_seen()`, that updates the loose object cache whenever a new object is written. The helper is called in both the single-object and streaming write paths (`write_loose_object()` and `odb_source_loose_write_object_stream()`), ensuring the cache stays coherent. The patch also includes a new test in `t/t5616-partial-clone.sh` that sets up a three-branch merge scenario with 50 mergeable files, verifying that locally written blobs are never mistakenly fetched from the remote.

The commit message is exemplary: it walks through the exact sequence of events that leads to the bug, ties it to a specific regression (5946a564cdd, 2026-03-05), and explains why the old “flush-on-failure” workaround was insufficient. The test coverage is thorough and realistic, using a large enough number of files to stress the sharding directory logic.

This patch looks ready for serious review. The problem is real, the fix is minimal and well-motivated, and the test ensures the bug cannot regress. If the preparatory refactoring in patch 1/2 holds up, this should be a straightforward merge to `next`.

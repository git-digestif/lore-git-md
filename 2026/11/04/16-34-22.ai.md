This is a follow-up in the ongoing policy discussion about pre-commit hooks and index mutation. Kevin Lyles acknowledges Chris Torek’s technical explanation and proposed wrapper-script workaround but raises practical concerns about adopting it at scale. The key tension is between Git’s design (pre-commit hooks are for validation only) and real-world workflows where teams rely on hooks to automate index modifications without adding manual steps.

Lyles’ company uses pre-commit hooks to modify staged files (e.g., appending metadata or normalizing content) in a large repository where `git ls-files` can take 5 seconds. The wrapper-script approach—staging changes before invoking `git commit`—would require developers to change their workflows, which they want to avoid. He explores alternatives like clean filters but notes performance trade-offs: filters need the full file list upfront to batch operations, but `git ls-files` is too slow for their repository. The discussion now centers on whether Git can accommodate such use cases without breaking its design principles.

The email does not propose a code change or documentation patch but clarifies the stakes for enforcement. If Git were to reject index mutations in hooks (as Junio suggested), teams like Lyles’ would need to rework their automation, potentially at a significant performance cost. The thread remains open for policy and documentation updates, but this reply highlights the gap between Git’s intended hook semantics and how some users leverage them. No new technical details emerge, but the real-world constraints make the enforcement question more nuanced.

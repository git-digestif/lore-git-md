Core problem or goal
The thread reports a severe performance regression in `git log --follow` when tracking a single file through non-linear history (e.g., forward merges of maintenance branches into main). The command now takes ~10 minutes in Git 2.56 vs. ~1 second in Git 2.43, bisected to commit 304812ed33 ("log: improve --follow following renames for non-linear history"). The regression stems from the new logic running a full diff against *every* parent of a merge commit, even when the tracked file is absent in that parent, causing the cost to scale with the number of such merges and tree size.

Current status
Under review. The regression is confirmed and bisected; patches addressing the issue are now under review in a separate thread (linked by Patrick Steinhardt). The report includes a reproduction case (a file with 692 commits in non-linear history) and a `perf` profile pinpointing `hash_chars`, `spanhash_cmp`, and `diffcore_count_changes` as bottlenecks. The issue affects real-world tools (e.g., VS Code’s Timeline view) and is not mitigated by shallow clones, commit-graph, or configuration.

Key technical details
- **Command**: `git log --follow <file>`
- **Subsystems touched**: log, diffcore (rename detection)
- **Regression commit**: 304812ed33 ("log: improve --follow following renames for non-linear history")
- **Root cause**: The commit’s logic runs a full diff against each parent of a merge commit, even when the tracked file is absent in that parent, leading to O(N*M) cost (N = merge commits, M = tree size).
- **Symptoms**: 600x slowdown in large repositories (30k commits, 27k files) for files with non-linear history.
- **Workarounds**: None known; the regression is inherent to the new logic.
- **Test coverage**: Reproduction case provided (file with 692 commits), but no script attached.

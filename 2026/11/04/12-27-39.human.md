This is an Outreachy project proposal for a feature that would let users configure the order in which Git queries multiple promisor remotes when fetching missing objects in partial clones. The author, Shashank S Mogaveera, has already contributed four small patches to Git (two merged to `master`, one to `seen`, and one under review), showing they can navigate the mailing-list workflow.

The proposal is well-structured and technically grounded. Shashank has already mapped out the current hardcoded fallback behavior using `GIT_TRACE2` and built a local testbed with multiple promisor remotes. The plan introduces a new `promisor.fetchOrder` configuration list on the client side and a Protocol v2 extension for servers to advertise preferred priorities, with client config taking precedence. The 13-week timeline is realistic, starting with documentation and baseline tests, then implementing client-side ordering, server-side advertisement, and finally upstreaming the changes.

This looks like a serious, well-motivated effort. The feature addresses a real gap in partial-clone usability: users currently have no control over which promisor remote Git queries first, even though different remotes can have vastly different performance and cost characteristics. The proposal is careful about edge cases (unlisted remotes, backwards compatibility) and includes a stretch goal for dynamic caching of failed remotes. If executed as planned, this would be a valuable addition to Git’s partial-clone support.

The follow-up email you’re seeing is purely administrative—fixing a typo and broken links—so the substance remains the original proposal. No code exists yet, but the author’s prior contributions and the thoroughness of the design suggest this is worth following as it progresses.

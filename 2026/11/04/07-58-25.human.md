This is a **performance regression bug report** targeting the `git log --follow` command. The author, b.murauer@posteo.de, reports that `git log --follow` on a single file in a large repository (30k commits, 27k files) became roughly 600 times slower between Git 2.43 and Git 2.56, taking 10 minutes instead of 1 second.

The regression was bisected to commit 304812ed33 ("log: improve --follow following renames for non-linear history"). The author explains that the commit now runs rename detection against every parent of a merge, which becomes expensive when many merges lack the file (a common pattern when merging maintenance branches forward). A `perf` profile confirms the bottleneck is in rename-detection code (`hash_chars`, `spanhash_cmp`, `diffcore_count_changes`).

The report is detailed and well-structured: it includes reproduction steps, expected vs. actual behavior, a bisect result, a `perf` profile, and a clear explanation of why the change is problematic. The author also rules out several potential confounding factors (shallow clone, missing objects, commit-graph, LFS, config settings). A reproduction script is mentioned but not attached.

This looks like a serious, real-world regression that affects tools like VS Code's Timeline view. The report is credible and actionable; it is likely to receive prompt attention from maintainers.

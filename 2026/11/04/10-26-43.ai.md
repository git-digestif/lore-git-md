This is an Outreachy project proposal for a feature targeting the promisor remote subsystem. The author, Shashank S Mogaveera, outlines a 13-week plan to implement configurable fetch ordering for promisor remotes in partial clones. The proposal is well-structured, technically grounded, and demonstrates familiarity with Git's internals and contribution process.

The project aims to address the current lack of deterministic priority when fetching missing objects from multiple promisor remotes. Currently, Git falls back to a hardcoded order that doesn't account for performance differences or bandwidth costs. The solution involves two main components: a client-side configuration list (`promisor.fetchOrder`) and a server-side Protocol v2 extension to advertise preferred priorities. The author has already established a baseline by tracing current behavior with GIT_TRACE2 and verified that remotes are queried in configuration order, with `core.partialClone` treated as a last-resort fallback.

Shashank's timeline is detailed and realistic, with clear phases: documenting current behavior (weeks 1-2), implementing client-side ordering (weeks 3-5), adding server-side advertisement (weeks 6-9), upstreaming (weeks 10-12), and polishing (week 13). The proposal includes stretch goals like dynamic caching of failed remotes. The author's past contributions—four microprojects modernizing tests and removing `the_repository` usage—have already been merged (two to `master`, one to `next`, one to `seen`), showing they can navigate the mailing list workflow and produce acceptable patches.

Key technical details to note for follow-up discussion: the `promisor.fetchOrder` config will use a list rather than per-remote integers for composability; server-side advertisement will be gated by a new `promisor.sendFields` config; and client config will take precedence over server-advertised order. The proposal also mentions edge cases like unlisted remotes and preserving the `partialClone`-last rule. The author's focus on network optimization and their experience with GIT_TRACE2 suggest they're well-prepared for the protocol-level work involved.

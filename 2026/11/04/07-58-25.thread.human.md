This thread is about a **severe performance regression in `git log --follow`** introduced in Git 2.56. The reporter, b.murauer@posteo.de, found that the command now takes around 10 minutes to run on a single file in a large repository (30k commits, 27k files), compared to just 1 second in Git 2.43. The regression was bisected to commit 304812ed33, which aimed to improve rename detection for non-linear history but instead triggered a bottleneck in merge commits where the file doesn’t exist in one parent.

The issue is particularly problematic for workflows involving forward merges (e.g., maintenance branches into main), where the file may be absent in the older branch. Profiling shows the slowdown stems from rename detection functions (`hash_chars`, `spanhash_cmp`, `diffcore_count_changes`) running full diffs against *every* parent of a merge, even when the file is missing in some. This scales poorly with the number of such merges and tree size. The reporter ruled out shallow clones, missing objects, commit-graph, LFS, and configuration as factors. The regression impacts real-world tools like VS Code’s Timeline view, which relies on similar commands.

No patches or fixes have been proposed yet, and the thread is currently just the initial bug report. The key technical detail is the interaction between `--follow` and merge commits with asymmetric file presence—a scenario the original commit intended to improve but inadvertently made prohibitively expensive. If you use `git log --follow` in large repositories, this is a critical issue to watch.

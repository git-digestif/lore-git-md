This is a **performance regression bug report** targeting the `git log --follow` command.

The reporter, b.murauer@posteo.de, identifies a severe slowdown in `git log --follow` when run on a single file in a large repository (30k commits, 27k files). The command now takes around 10 minutes in Git 2.56, compared to about 1 second in Git 2.43. The regression was bisected to commit 304812ed33 ("log: improve --follow following renames for non-linear history"), which appears to have introduced a change in how rename detection works for merge commits where the file does not exist in one parent.

The issue is particularly acute for workflows involving forward merges of maintenance branches into main, where the file may not exist in the older branch. The reporter’s `perf` profile points to rename detection (`hash_chars`, `spanhash_cmp`, `diffcore_count_changes`) as the bottleneck, suggesting the new logic runs a full diff against each parent of a merge, even when the file is absent in that parent. This cost scales with the number of such merges and the size of the tree. The reporter has ruled out shallow clones, missing objects, commit-graph, LFS, and configuration as factors.

The report includes a clear reproduction case (a file with 692 commits in non-linear history) and a `perf` profile, but no script is attached. The regression affects real-world tools like VS Code’s Timeline view, which uses a similar command. The key technical detail is that the slowdown stems from the interaction between `--follow` and merge commits with asymmetric file presence, a scenario the original commit aimed to improve but inadvertently made prohibitively expensive.

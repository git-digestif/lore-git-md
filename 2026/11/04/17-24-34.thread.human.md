This thread introduces a new feature for Git’s promisor-remote subsystem, allowing users to control the order in which multiple promisor remotes are tried during lazy fetches. The patch, authored by an Outreachy contributor, adds a `promisor.fetchOrder` configuration variable that overrides the default order (based on configuration file appearance) with a user-specified list of remote names. The implementation is straightforward: it parses the comma-separated list at startup, stores it in a static `string_list`, and applies a stable insertion sort to the list of remotes during initialization.

The patch is small (70 lines) and focused, touching only `promisor-remote.c` and adding a single field to the `promisor_remote` struct. It follows Git’s config-parsing conventions and deliberately avoids validating remote names in the list to keep the code simple. The author acknowledges a gap in test coverage—the existing `t5710` test fixture doesn’t trigger lazy fetches, making the ordering change unobservable—and offers to address this in a follow-up. This is the author’s first contribution to Git, and the patch addresses a real usability pain point for users with multiple promisor remotes.

So far, the thread consists only of the initial patch submission. No reviews or maintainer feedback have been posted yet, so the feature’s acceptance and any required changes remain open questions. The main loose end is the test coverage, which the author has flagged as a follow-up task.

This thread is about a proposed feature to let users control the order in which Git tries multiple promisor remotes during lazy fetches. The author, Yopa Nelly (an Outreachy contributor), sent a second version of the patch after the first one had architectural flaws and a crash. The patch adds a new `promisor.fetchOrder` configuration option that lets users specify a preferred order for promisor remotes, replacing the current implicit order based on configuration file sequence.

The patch is now in an RFC prototype state, with the author pausing further work until Outreachy selections are finalized. The main blocker is a design question raised by Junio C Hamano about how the client-side configuration should interact with server-side promisor remote advertisements. Christian Couder, the promisor-remote maintainer, has now responded, pointing out that the current approach may not handle cases where different remotes advertise different sets of promisor remotes. He suggests that a static order might not be sufficient and that a more dynamic mechanism could be needed, though he hasn’t proposed a specific solution yet. This leaves the design question unresolved and the patch’s future uncertain.

The patch itself touches `promisor-remote.c` and adds documentation for the new config key. It uses a two-pass approach to try remotes in the specified order first, then the rest. The author has addressed earlier feedback about crashes and documentation but hasn’t added test coverage yet. The patch is still under review, with no clear path forward until the design question about server-side reconciliation is resolved.

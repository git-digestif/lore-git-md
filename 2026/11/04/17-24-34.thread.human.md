This thread is about a patch from Outreachy contributor Yopa Nelly that adds a `promisor.fetchOrder` configuration option, letting users specify the order in which Git tries multiple promisor remotes during lazy fetches. The patch is now at v2, fixing a crash and architectural issues raised in the first version, and the commit message now follows project guidelines.

The main open question is a design concern from Junio C Hamano: how should the new client-side configuration interact with server-side promisor remote advertisements, which may also suggest a preferred order? Christian Couder, the promisor-remote maintainer, has been asked to clarify this, and his response will likely determine whether the patch needs further changes. There’s also an Outreachy process question about whether the patch should have gone through an RFC phase first; Kaartic Sivaraam suggests treating the current patch as an RFC and discussing the config design on-list, but notes that the internship selections aren’t final yet, so premature work could create conflicts.

The patch itself touches `promisor-remote.c` and adds documentation, but still lacks test coverage. Yopa plans to reuse an existing test script, and the patch doesn’t validate remote names in the config list, matching Git’s behavior for other list-valued config variables. The only substantive review so far came from Tanga Joris in v1, identifying the crash and architectural flaws that v2 addressed. Junio’s query and the Outreachy process discussion are the main unresolved points, with no technical objections to the current implementation.

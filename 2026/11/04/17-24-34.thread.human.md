This thread is about an RFC patch proposing `promisor.fetchOrder`, a configuration option to let users specify the order in which Git tries multiple promisor remotes during lazy fetches. The patch, now in its second version, was submitted by Yopa Nelly, an Outreachy contributor, and addresses earlier feedback on crashes and architectural flaws. However, a fundamental design question remains unresolved: how the client-side order should interact with server-side promisor remote advertisements, which may suggest different orders depending on the remote. Christian Couder, the promisor-remote maintainer, has argued that the current static client-side approach cannot handle multi-remote scenarios, and Yopa has acknowledged this limitation, agreeing that a broader design discussion is needed before further progress.

The thread has also sparked a meta-discussion about Outreachy project design. Junio C Hamano proposed a tiered structure for future Outreachy projects—microprojects for community engagement, mid-sized projects for applicant selection, and full-scale projects for interns—to address concerns that the current patch prematurely tackles substantive design work. This proposal is forward-looking and doesn’t affect the current patch’s status, which remains an RFC prototype with no clear path to resolution on the server-side reconciliation issue. Key participants include Yopa Nelly (author), Christian Couder (maintainer), Junio C Hamano (maintainer), and reviewers Tanga Joris and Kaartic Sivaraam, though only the first three have engaged with the core design question. The patch itself is technically sound but lacks test coverage, which the author plans to address after Outreachy selections are finalized.

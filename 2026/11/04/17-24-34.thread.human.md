This thread is an Outreachy-driven RFC patch by Yopa Nelly proposing a new `promisor.fetchOrder` config key that lets users explicitly order the promisor remotes Git tries during lazy fetches, instead of relying on configuration file order. The patch is at v2, which fixed a crash and architectural problems from v1, added documentation for the new key in `promisor-remote.c` and `Documentation/config/promisor.adoc`, and adopted a two-pass ordering algorithm in `try_promisor_remotes()`. Test coverage is still missing, and remote names in the list are not validated.

The central blocker is a design question raised by Junio C Hamano and sharpened by promisor-remote maintainer Christian Couder: a static client-side order cannot reconcile with server-side promisor remote advertisement in multi-remote setups where different remotes advertise different sets of promisor remotes. Yopa Nelly has acknowledged this fundamental limitation and agreed the feature needs a design discussion before further implementation, so the patch remains an RFC prototype with no proposed solution yet.

The latest exchange is procedural rather than technical: Junio proposed a tiered Outreachy project structure (microprojects, mid-sized, full-scale), and Christian Couder agreed the tiers are valuable but noted the difficulty of curating the lists, mentioning an AI tool he is building to auto-generate and label GitLab issues from list discussions. Kaartic Sivaraam had earlier suggested treating the patch as an RFC prototype, which the author accepted while pausing work until Outreachy selections are finalized. No one has merged or advanced the patch; the unresolved server-side reconciliation question remains the sole obstacle to substantive progress.

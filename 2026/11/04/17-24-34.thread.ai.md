Subject: [PATCH v2] promisor-remote: add promisor.fetchOrder config
Series version: v2 (standalone patch, supersedes v1; now explicitly an RFC prototype)
Originating author: Yopa Nelly (Outreachy contributor)
Thread type: feature patch (RFC prototype)

Core problem or goal
Allow users to specify the order in which Git tries multiple promisor remotes during lazy fetches, replacing the current implicit order (configuration file order) with an explicit, user-configurable list. The feature must reconcile client-side `promisor.fetchOrder` with server-side promisor remote advertisement, which may independently suggest a preferred order.

Current status
Under review as an RFC prototype; v2 posted addressing v1’s crash and architectural flaws. Junio C Hamano has raised a **high-weight design question** about the interaction between client-side `promisor.fetchOrder` and server-side promisor remote advertisement. No resolution yet; Christian Couder (promisor-remote maintainer) has been asked to clarify how the two mechanisms should coexist. Outreachy process concerns are resolved: the author has accepted Kaartic Sivaraam’s suggestion to treat the current patch as an RFC prototype and paused further work until Outreachy selections are finalized.

Key technical details
- Files touched: `promisor-remote.c` (108 lines added, 12 removed), `Documentation/config/promisor.adoc` (11 lines added)
- New config key: `promisor.fetchOrder` (comma-separated list of remote names), documented with cross-references to `gitprotocol-v2` and partial clone design notes
- Storage: parsed list stored in `struct promisor_remote_config` and cleared during `promisor_remote_clear()`, ensuring per-repository isolation
- Algorithm: two-pass approach in `try_promisor_remotes()`—first explicitly ordered remotes, then the rest—replaces v1’s insertion-sort mechanism
- Crash fix: switched from `STRING_LIST_INIT_DUP` to `string_list_init_nodup()` and properly clears list during config reinitialization
- Validation: remote names in the list are not validated; typos are silently treated as “not listed”
- On-disk format: unchanged
- Test coverage: still absent; author plans to reuse `t0410-partial-clone.sh`
- **New concern**: server-side promisor remote advertisement (via `gitprotocol-v2`) may suggest a preferred order; the patch currently ignores this, creating a potential conflict or design gap

Open questions and loose ends
- **Server-side reconciliation**: how should the client-side `promisor.fetchOrder` interact with server-advertised promisor remote order? Junio’s query to Christian Couder seeks clarification on whether the two mechanisms should merge, override, or remain independent. This remains the **highest-weight open question** and is now the sole blocker for substantive progress.
- **Test coverage**: reuse `t0410-partial-clone.sh` or write new fixture; author has acknowledged this gap and plans to address it once Outreachy selections are finalized.
- **Validation**: remote names in the list are not validated; typos are silently ignored, matching Git’s behavior for other list-valued config variables.
- **Performance**: re-parsing the list on every config read may introduce overhead in repositories with many promisor remotes.

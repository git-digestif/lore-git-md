Subject: [PATCH v2] promisor-remote: add promisor.fetchOrder config
Series version: v2 (standalone patch, supersedes v1; RFC prototype)
Originating author: Yopa Nelly (Outreachy contributor)
Thread type: feature patch (RFC prototype)

Core problem or goal
Allow users to specify the order in which Git tries multiple promisor remotes during lazy fetches, replacing the current implicit order (configuration file order) with an explicit, user-configurable list. The feature must reconcile client-side `promisor.fetchOrder` with server-side promisor remote advertisement, which may independently suggest a preferred order and whose interaction with the client-side mechanism is inherently multi-party and context-dependent.

Current status
Under review as an RFC prototype; v2 remains the latest version, addressing v1’s crash and architectural flaws. The **highest-weight design question**—how client-side `promisor.fetchOrder` should interact with server-side promisor remote advertisement—is **actively contested and acknowledged as a fundamental limitation** by the author. Christian Couder (promisor-remote maintainer) has argued that the current patch’s static client-side order cannot handle multi-remote scenarios where different remotes advertise different sets of promisor remotes, and Yopa Nelly has conceded this point, agreeing the feature requires a design discussion before further implementation. No proposed solution or mitigation has emerged; the patch’s RFC status is reinforced by this unresolved design gap. Outreachy process concerns are resolved: the author has accepted Kaartic Sivaraam’s suggestion to treat the current patch as an RFC prototype and paused further work until Outreachy selections are finalized. Junio C Hamano has proposed a tiered Outreachy project structure (microprojects, mid-sized projects, full-scale projects) to address procedural concerns about premature implementation of design work in microprojects, but this meta-discussion does not advance the current patch’s technical status.

Key technical details
- Files touched: `promisor-remote.c` (108 lines added, 12 removed), `Documentation/config/promisor.adoc` (11 lines added)
- New config key: `promisor.fetchOrder` (comma-separated list of remote names), documented with cross-references to `gitprotocol-v2` and partial clone design notes
- Storage: parsed list stored in `struct promisor_remote_config` and cleared during `promisor_remote_clear()`, ensuring per-repository isolation
- Algorithm: two-pass approach in `try_promisor_remotes()`—first explicitly ordered remotes, then the rest—replaces v1’s insertion-sort mechanism
- Crash fix: switched from `STRING_LIST_INIT_DUP` to `string_list_init_nodup()` and properly clears list during config reinitialization
- Validation: remote names in the list are not validated; typos are silently treated as “not listed”
- On-disk format: unchanged
- Test coverage: still absent; author plans to reuse `t0410-partial-clone.sh`
- **New design constraint**: server-side promisor remote advertisement (via `gitprotocol-v2`) may suggest a preferred order that varies by remote; the patch’s static client-side order cannot handle cases where different remotes (A, B) advertise different sets of promisor remotes (A1/A2 vs. B1/B2/B3), creating a fundamental limitation now acknowledged by the author

Open questions and loose ends
- **Server-side reconciliation**: how should the client-side `promisor.fetchOrder` interact with server-advertised promisor remote order in multi-remote scenarios? Christian Couder’s feedback identifies this as a **fundamental design gap**—the current patch’s static order cannot handle cases where different remotes advertise different promisor remotes. The author has acknowledged this limitation and agreed the feature requires a design discussion before further implementation. This remains the **sole blocker** for substantive progress; no proposed solution or mitigation has been offered.
- **Test coverage**: reuse `t0410-partial-clone.sh` or write new fixture; author has acknowledged this gap and plans to address it once Outreachy selections are finalized.
- **Validation**: remote names in the list are not validated; typos are silently ignored, matching Git’s behavior for other list-valued config variables.
- **Performance**: re-parsing the list on every config read may introduce overhead in repositories with many promisor remotes.

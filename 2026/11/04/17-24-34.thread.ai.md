Subject: [PATCH v2] promisor-remote: add promisor.fetchOrder config
Series version: v2 (standalone patch, supersedes v1)
Originating author: Yopa Nelly (Outreachy contributor)
Thread type: feature patch

Core problem or goal
Allow users to specify the order in which Git tries multiple promisor remotes during lazy fetches, replacing the current implicit order (configuration file order) with an explicit, user-configurable list.

Current status
Under review; v2 posted. Implementation now avoids the v1 crash (`BUG: string-list.c`) and architectural flaw (file-static `fetch_order` list shared across repositories) by storing the parsed order in `struct promisor_remote_config` and re-parsing on each config read. Documentation added; test coverage still absent. Outreachy process concerns (bypassing RFC phase, commit message style) remain unresolved.

Key technical details
- Files touched: `promisor-remote.c` (108 lines added, 12 removed), `Documentation/config/promisor.adoc` (11 lines added)
- New config key: `promisor.fetchOrder` (comma-separated list of remote names), documented with cross-references to `gitprotocol-v2` and partial clone design notes
- Storage: parsed list stored in `struct promisor_remote_config` and cleared during `promisor_remote_clear()`, ensuring per-repository isolation
- Algorithm: two-pass approach in `try_promisor_remotes()`—first explicitly ordered remotes, then the rest—replaces v1’s insertion-sort mechanism
- Crash fix: switched from `STRING_LIST_INIT_DUP` to `string_list_init_nodup()` and properly clears list during config reinitialization
- Validation: remote names in the list are still not validated; typos are silently treated as “not listed”
- On-disk format: unchanged
- Test coverage: still absent; author has acknowledged this gap

Open questions and loose ends
- **Test coverage**: reuse `t0410-partial-clone.sh` or write new fixture
- **Validation**: remote names in the list are not validated; typos are silently ignored
- **Outreachy process**: whether the patch bypassed the expected RFC phase for Outreachy microprojects and, if so, why; commit message style concerns (conversational language, lack of v1 issue/fixed summary)
- **Performance**: re-parsing the list on every config read may introduce overhead in repositories with many promisor remotes

This thread covers Wasswa Edson's three-patch v2 series converting `git credential` to use the standard `OPT_SUBCOMMAND` parse-options mechanism instead of manual `strcmp()` dispatch. The series refactors each subcommand (fill, approve, reject, capability) into its own function, removes the `NO_PARSEOPT` flag so the command participates in `--list-cmds=parseopt`, improves error messages and `-h` output, and fixes small documentation inconsistencies. All v1 feedback has been addressed, and the series has drawn approvals from Tanga Joris (substantive review of patch 3) and Laveesh Bansal (a tested `Reviewed-by` on the cover letter after running t0300, t0450, and t9902 locally). It remains under review with no merge status reported.

The only substantive open item is Tanga Joris's request that the patch 3 commit message document a behavior change: `git credential <subcommand> --` (the end-of-options marker after a subcommand) now succeeds rather than producing a usage error. Laveesh Bansal's latest reply confirms this by noting that the long form `--end-of-options` behaves identically to `--` in that position, and adds no new approval weight since his `Reviewed-by` was already given on the cover letter.

Bansal's message also raises one forward-looking question: while `git credential --git-completion-helper` now exposes subcommand names, bash completion still offers no suggestions after `git credential <TAB>` -- the same gap seen with `git hook` -- and he asks whether a dedicated `_git_credential` completion script is planned as a follow-up. This is non-blocking, but it leaves open whether the `OPT_SUBCOMMAND` conversion is considered complete for user-facing tooling or whether shell completion support will arrive in a later patch.

This is an Outreachy project proposal for a feature targeting the promisor remote subsystem. The author, Shashank S, is applying for the December 2026 Outreachy internship to implement **promisor remote fetch ordering**—a mechanism to let users control the priority of remotes when Git fetches missing objects in partial clones.

The proposal is thorough and well-structured. Shashank outlines a clear four-phase plan: first documenting the current hardcoded fallback behavior, then adding client-side configuration (`promisor.fetchOrder`), extending Git Protocol v2 to let servers advertise preferred priorities, and finally upstreaming the changes with well-defined precedence rules. The timeline is realistic, with built-in time for mailing-list review and edge-case handling. Notably, the author has already contributed four micro-projects during the Outreachy application phase—all have been picked up in Junio’s integration branches (`master`, `next`, or `seen`), signaling that the community is receptive to their work.

The motivation is sound: today Git lacks any way to express that one promisor remote is faster or cheaper than another, so users cannot optimize lazy fetches. The proposed design (a config list plus a protocol extension) is flexible and backward-compatible. Shashank also demonstrates hands-on experience by building a local test playground and using `GIT_TRACE2` to verify the current behavior, which gives confidence that the implementation will be grounded in real code paths rather than abstract theory.

Overall, this looks like a strong candidate for the internship and a useful feature for partial-clone users. The proposal is detailed enough that a reviewer can spot the key design choices without wading through the full text, yet it remains concise and easy to digest in under a minute.

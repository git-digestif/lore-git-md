Subject: [RFC] promisor remote fetch ordering configuration
Series version: RFC (no patch version)
Originating author: Tatchou Yopa Nelly (Outreachy applicant)
Thread type: design discussion / RFC

Core problem or goal
Allow users to control the order in which Git tries promisor remotes when fetching missing objects. Currently the order is fixed (config-file order, with `extensions.partialClone` always moved to the end) and not user-configurable.

Current status
Early design discussion; no code written yet. Two competing configuration shapes proposed; author leans toward a global ordered list (`promisor.fetchOrder`).

Key technical details
- Files touched: `promisor-remote.c`, test file `t5710`
- New config keys: either `remote.<name>.promisorPriority` (numeric) or `promisor.fetchOrder` (comma-separated list)
- No on-disk format changes
- No new CLI options or symbols

Open questions and loose ends
1. How to handle a remote named in the list that is not actually a promisor remote (error, warning, or ignore)
2. Whether an explicit list entry should override the automatic move of `extensions.partialClone` to the end
3. Whether different fetch orders might be needed depending on the source remote, which could favor the per-remote numeric approach

Participant positions
- Yopa Nelly (author): prefers the list-based approach (`promisor.fetchOrder`) for readability, ease of overriding across config files, and direct mapping to the existing linked-list implementation; raises the three open questions above.

Related work
- Current promisor-remote code (`promisor-remote.c`) and test suite (`t5710`)
- No external dependencies or prior versions mentioned

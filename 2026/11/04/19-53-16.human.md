This is the third patch in Farid Zakaria’s v2 series fixing race conditions in the credential-cache daemon. It prevents a second daemon from hijacking the socket of an already-running daemon, which previously caused credential loss, orphaned processes, and inaccessible passwords.

The patch replaces the unsafe `unix_stream_listen()` call with `unix_ss_create()`, a helper from the simple-ipc subsystem that safely handles concurrent socket creation. If a second daemon detects an existing socket, it prints "ok" and exits, allowing its client to communicate with the running daemon instead. The change is well-tested: the new test in `t/t0301-credential-cache.sh` verifies that credentials stored by the first daemon remain accessible after a second daemon attempts to start.

The commit message is clear and imperative, and the code comment explains the "ok" response’s role in the client-daemon protocol. The patch addresses a real, user-visible bug—parallel submodule fetches over HTTPS can trigger this race—and the fix is narrowly scoped. The only open question is Junio’s architectural concern about mixing `unix_ss_*` and `tempfile` APIs, which the author has not yet addressed in this iteration. That said, the core logic is uncontroversial and aligns with precedent in `fsmonitor--daemon.c`. This patch is likely to be merged once the API-mixing question is resolved.

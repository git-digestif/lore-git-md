Yoichi NAKAYAMA is iterating on a three-patch v2 series that teaches Git to keep submodule settings in the worktree-specific config file when `extensions.worktreeConfig` is enabled, so that linked worktrees do not share submodule state. The first patch makes `submodule.<name>.gitdir` a relative path for linked worktrees; the second patch, just posted, routes writes of `submodule.<name>.active`, `.url`, `.update`, and `.gitdir` into `config.worktree` across `git submodule init`, `sync`, `add`, and `deinit`, and ensures `git worktree add` strips any `submodule.*.gitdir` keys when copying config so a new worktree does not inherit another worktree's submodule checkout. When worktree config is active, `git submodule deinit` now explicitly sets `submodule.<name>.active` to `false` in that file to mark the submodule unregistered for the current worktree.

The series remains under review with no substantive objections or reviewer feedback yet beyond the author's own v2 fixes. Tests in `t/t2405-worktree-submodule.sh` and `t/t7425-submodule-gitdir-path-extension.sh` now verify that the relevant keys land in `config.worktree`, that gitdir values stay worktree-local, and that deinit behaves correctly. The open question is how these changes interact with existing `git submodule update --init` workflows across multiple worktrees, which the third patch (adjusting `git submodule init` to copy a gitdir only when it belongs to the current worktree) is expected to address.

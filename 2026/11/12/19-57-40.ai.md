This is the third and most controversial patch in Adrian Ratiu’s three-part bugfix series for Git’s `compatObjectFormat` interoperability layer. It addresses an inconsistency in how unknown commit headers are handled during SHA-1 ↔ SHA-256 conversions: Git previously rejected them when converting existing commits but copied them unchanged when creating new ones. The patch makes both code paths copy unknown headers unchanged, removing a 2023 check (commit 08a45903cb) that was deliberately added to reject such headers.

The change is motivated by real-world interoperability needs: tools like Jujutsu rely on custom headers (e.g., `change-id`) that Git cannot interpret, and the current behavior breaks their workflows in mixed-format repositories. The patch unifies the behavior of `convert_commit_object()` (used when reading existing commits) and `convert_commit_extra_headers()` (used when creating new commits) by copying all unknown headers verbatim, including their continuation lines. The commit message acknowledges the trade-off—unknown headers might contain object IDs that should be converted—but argues that consistency and tool compatibility outweigh the risk, which can be mitigated by explicitly handling new headers in the future.

The implementation simplifies `object-file-convert.c` by removing the hardcoded checks for `author`, `committer`, `encoding`, and `gpgsig` headers (which are now handled by the generic case) and adds a detailed comment explaining the rationale. The new test in `t1016-compatObjectFormat.sh` verifies that commits with unknown headers can be both created and read back in both SHA-1 and SHA-256 repositories, covering both the `git hash-object` and `git commit --amend` paths.

This patch is likely to spark discussion because it reverses a deliberate 2023 safety check. While the commit message makes a clear case for the change, the removal of the check could be seen as lowering a guardrail, and reviewers may push for alternative solutions (e.g., a configurable allowlist for unknown headers). The test coverage is thorough, but the broader implications for security and data integrity will need scrutiny. The patch is well-crafted and addresses a real problem, but its acceptance hinges on whether the project prioritizes consistency with external tools over the safety of rejecting unrecognized headers.

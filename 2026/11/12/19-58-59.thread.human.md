This thread is about a bugfix series from Christian Couder that ensures the Git client sends the `promisor-remote=...` reply during `fetch` protocol v2 commands—a capability that has been missing since its introduction in Git v2.49, causing fetch failures with servers like JGit/Gerrit that handle requests independently. The series is currently under review, with three patches: a preparatory refactor, the core fix, and a documentation update.

The key sticking point is the implementation approach. Junio C Hamano has raised a design concern about the refactoring patch (1/3), arguing that the new argument in `write_command_and_capabilities()` is a workaround that bypasses the intended extensibility of the existing `server_options` mechanism. He proposed generalizing `server_options` to support arbitrary key-value pairs, allowing `promisor-remote=...` to be included as a list element rather than a separate argument. Christian initially countered that this refactoring should be a separate follow-up, suggesting a `NEEDSWORK` comment to document the technical debt while prioritizing the bugfix for the `maint` branch.

Junio’s latest reply pushes back on deferring the cleanup, arguing that the duplication in the client-side capability-writing functions (`send_capabilities()`, `get_remote_refs()`, and `write_command_and_capabilities()`) should be addressed now rather than layered over. He suggests the refactoring could be modest (under 20 small patches) and views it as a prerequisite for merging the bugfix. The thread now hinges on whether Junio will accept the `NEEDSWORK` compromise or insist on the cleaner API before proceeding. The core fix (patches 2/3 and 3/3) remains uncontested, but the series’ fate depends on resolving this design tension. Christian will likely need to either propose a minimal refactoring or further justify the `NEEDSWORK` approach.

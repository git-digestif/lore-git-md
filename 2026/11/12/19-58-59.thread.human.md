This thread is fixing a bug in Git’s protocol v2 `fetch` command where the client omits the `promisor-remote=...` reply, breaking interactions with stateless servers like HTTP and JGit/Gerrit. The issue has existed since Git v2.49 and causes fetch failures when objects are only available on promisor remotes. Christian Couder’s three-patch series (v1) addresses this by refactoring `write_command_and_capabilities()` to send the reply during `fetch`, adding tests for local and HTTP scenarios, and updating the protocol documentation.

The series is under review, but Junio C Hamano has raised a significant design concern about patch 1/3: the new `promisor_remote_reply` parameter feels like a workaround that bypasses the intended extensibility of the existing `server_options` string list. In his latest email, Junio proposes an alternative—generalizing `server_options` to support arbitrary key-value pairs, allowing `promisor-remote=...` to be included as a list element rather than a separate argument. This would avoid a one-off parameter and preserve the function’s extensibility. The core goal of the series (fixing the missing reply) is uncontested, but the API design is now the sticking point. Christian will need to either adopt Junio’s approach or defend the current design before the series can move forward. No other reviewers have weighed in yet.

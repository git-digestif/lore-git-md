This is a follow-up in a bug-report thread about `git repack --drop-filtered`.

The thread began with a user report (kongfankaikai) describing a fatal error in `git repack --drop-filtered` when a blob selected for dropping is referenced by the current index. The error aborts the entire repack operation, preventing other eligible blobs from being dropped. The user asked why this condition is treated as fatal rather than skipped, noting this would be particularly useful for partial clones with large working trees.

Siddharth Shrimali replies that this is a known limitation, not a correctness issue. The guard exists to avoid dropping blobs that would be immediately lazy-fetched, but aborting the entire operation is overly conservative. A fix is already in progress: replacing the `die()` call with a warning and continuing to drop the remaining eligible blobs. Siddharth references an earlier RFC patch by Samuel Bronson from September 2026 that proposed the same direction, which he agreed with at the time. He confirms he is working on the fix and will post it to the list soon.

The original reporter acknowledges the update and says they will follow the discussion. The thread is now waiting for Siddharth’s patch submission. The issue affects partial clones and large repositories where `repack --drop-filtered` is used to reduce storage footprint. No code changes are included in this email.

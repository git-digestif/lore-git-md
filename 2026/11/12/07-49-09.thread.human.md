This thread is about a bug in `git repack --drop-filtered` where the command fatally errors out if a blob selected for dropping is referenced by the current index. The user who reported the issue (kongfankaikai) noted that this behavior is overly strict, as it prevents other eligible blobs from being dropped—particularly problematic for partial clones with large working trees.

Siddharth Shrimali, a contributor familiar with the repack machinery, confirmed this is a known limitation rather than a correctness issue. The current guard exists to avoid dropping blobs that would trigger an immediate lazy-fetch, but aborting the entire operation is unnecessarily conservative. He referenced an earlier RFC patch by Samuel Bronson (from September 2026) that proposed the same fix: replacing the `die()` call with a warning and continuing to drop the remaining eligible blobs. Siddharth is actively working on the fix and plans to post it to the list soon.

The thread is now in a holding pattern, awaiting Siddharth’s patch submission. The issue primarily affects users of partial clones and large repositories relying on `repack --drop-filtered` to reduce storage footprint. No code changes have been posted yet.

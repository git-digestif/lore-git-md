This is the first patch in Harald Nordgren’s v13 series, and Junio’s reply to Phillip Wood’s question clarifies a long-standing behavior that directly impacts the series’ unresolved override semantics discussion. The patch introduces `remote.<name>.fetchRefmap`, a new config key that decouples "which refs to fetch" from "where to store them," but Junio’s response reveals that the current implementation preserves a legacy behavior—dual storage—where a refspec with an explicit destination (e.g., `+refs/heads/master:refs/remotes/custom/master`) is stored in *both* the explicit destination *and* the refmap’s destination (`refs/remotes/cabal/master`). This behavior, which dates back to the introduction of `--refmap`, is now under scrutiny as the thread converges toward override semantics, where the refspec would override `fetchRefmap` entirely.

Junio’s framing of the question—what happens when `.fetch` is a refspec with a right-hand side and `.fetchRefmap` is also set—is precise and confirms that the dual-storage behavior is not a bug but a deliberate, if unintuitive, design choice. His reference to an earlier discussion (linked in the email) shows that this behavior has been observed before, and his reluctance to tweak it ("I do not see huge problem with that behavior") suggests he views it as low-priority. However, the thread’s consensus has since shifted toward override semantics, with Phillip Wood explicitly confirming in later emails that command-line refspecs (or their config-based equivalents) should override `fetchRefmap` entirely, not coexist with it. This means the dual-storage behavior, while long-standing, is now deprecated and will need to be updated in v14 to align with the chosen semantics.

The patch itself is mechanical and uncontroversial, adding the new config key, updating the `remote` struct, and teaching `remote_find_tracking()` to fall back to the refmap when `remote.<name>.fetch` has no match. The test suite in `t/t5510-fetch.sh` covers edge cases like negative refspecs and `@{upstream}` resolution, but the test for "explicit-dst remote.<name>.fetch entry" (lines 1050–1070) explicitly verifies the dual-storage behavior, which will need to be updated in v14 to reflect override semantics. Junio’s response does not oppose this change but treats it as a separate concern from the current patch, which is correct—this patch merely introduces the plumbing for `fetchRefmap` and does not alter the precedence logic.

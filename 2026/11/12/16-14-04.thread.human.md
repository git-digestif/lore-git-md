This thread is about a small but impactful performance patch by Kristofer Karlsson that shrinks `struct commit` by 10% (from 80 to 72 bytes on 64-bit platforms) by reordering its fields to eliminate padding. The change is uncontroversial—Derrick Stolee called it "obviously correct" and Junio C Hamano had only minor requests for added comments, which the author addressed in v2. The patch itself is ready for maintainer pickup, touching only `commit.h` with no behavioral or on-disk format changes.

The discussion has since shifted to a broader question: how should the project enforce awareness of struct bloat going forward? Kristofer initially proposed a compile-time assertion (`BUILD_ASSERT_OR_ZERO`) to enforce the `struct object`-first invariant, but worried it might be too rigid for cases where padding is unavoidable. Oswald Buddenhagen just weighed in with a pragmatic alternative: if padding is truly unavoidable, the struct can be annotated with architecture-specific dummy members to silence compiler warnings without affecting behavior. This keeps the enforcement mechanism flexible while still catching unintended bloat. No one has objected to the patch itself, but the follow-up question of how to institutionalize struct size discipline remains open.

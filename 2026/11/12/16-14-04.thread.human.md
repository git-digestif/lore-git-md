This thread is about a small but impactful memory optimization in Git’s commit subsystem. Kristofer Karlsson identified that `struct commit` on 64-bit platforms contains 8 bytes of padding—4 bytes between the `.object` and `.date` fields, and 4 bytes of tail padding. By reordering the fields to place the `index` field in the gap after `.object`, the struct shrinks from 80 to 72 bytes, a 10% reduction per commit with no functional change.

The patch is a one-line adjustment in `commit.h`, and the author measured a real-world impact: running `git rev-list --all` on a monorepo with ~4.5 million commits reduced peak RSS by ~32 MiB (from ~849 MiB to ~817 MiB), closely matching the expected savings. Runtime remained unchanged. The optimization was discovered incidentally while debugging an unrelated commit-walk issue, and the author notes that the struct’s size and padding have varied over time, sometimes regressing previous gains. They prototyped a regression test but left it out, questioning its maintainability, though they’re open to submitting it later if there’s interest.

So far, the thread is just the initial patch—no reviews or discussion yet. The change is narrowly scoped, with clear before-and-after measurements, so it’s likely to be uncontroversial if it holds up under scrutiny. The main open question is whether a follow-up test to track struct size is worth the effort.

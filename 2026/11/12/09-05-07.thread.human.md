This thread is about a **performance regression in `git log --follow`** introduced by a 2026 commit (304812ed33), which made the command nearly 15 times slower on non-linear histories like the Linux kernel repository. The issue stems from diffing each merge against all parents with rename detection enabled by default, ballooning runtime from 28 seconds to over 6 minutes.

Miklos Vajna’s patch **restores the original (pre-regression) behavior** for plain `--follow` while making the slower, more thorough logic opt-in via `--follow=merges` or `log.follow=merges`. The change touches core diff and log machinery (`builtin/log.c`, `diff.c`, `log-tree.c`), adds documentation and tests, and has been praised as a pragmatic compromise—avoiding a full revert while preserving correctness for users who need it. Patrick Steinhardt suggested the opt-in design, and the patch is now **ready to merge**, addressing a real-world pain point with clean code and thorough test coverage. No objections or open questions have surfaced yet.

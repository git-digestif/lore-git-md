This is a follow-up to a bug report about `git repack --drop-filtered` behavior. The original report highlighted that the command aborts entirely when it encounters a blob eligible for dropping that is also referenced by the current index, preventing other eligible blobs from being dropped. The author, Siddharth Shrimali, confirms this is a known limitation and not a correctness issue—aborting was a conservative choice rather than a safety requirement.

Siddharth references an earlier RFC patch by Samuel Bronson from September, which proposed a similar fix, and notes that the direction was agreed upon. The planned fix will replace the fatal error with a warning, allowing the repack to continue and drop other eligible blobs. This change is particularly useful for partial clones with large working trees, where the goal is to drop as many filtered objects as possible without disrupting the current working state.

The patch is still in progress, but the discussion suggests it is uncontroversial and aligns with prior feedback. The fix will touch the repack machinery in `builtin/repack.c`, specifically the object-dropping logic, and should be straightforward to implement. No on-disk format changes are expected, and the change is purely behavioral. If you work with partial clones or large repositories, this fix may improve usability once it lands.

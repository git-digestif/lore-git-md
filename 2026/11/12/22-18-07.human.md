This is a review comment from Junio C Hamano on the first patch in Christian Couder’s three-part bugfix series for the promisor-remote protocol v2 capability. The series aims to fix a long-standing issue where the Git client omits the `promisor-remote=...` reply during `fetch` protocol v2 commands, breaking interactions with stateless servers like HTTP and JGit/Gerrit.

Junio’s feedback is substantive and technical. He questions the design choice in this patch, which adds a new `promisor_remote_reply` argument to `write_command_and_capabilities()` to send the promisor-remote capability outside the existing `server_options` framework. He calls this "highly annoying" and suggests the real misdesign is that the promisor-remote string was never included in the `server_options` list in the first place. He asks whether the fix could avoid "contaminating the API" by leveraging the existing framework instead of adding a new parameter.

The review does not reject the patch outright but signals a preference for a cleaner design. This is a classic Junio-style comment: he is not objecting to the goal (fixing the bug) but to the means (extending the API in a way that feels ad hoc). The implication is that the series might need a v2 that reworks the approach to keep the API more consistent.

For a busy reader, this is worth noting: the series is under review, and the first patch’s design is already being questioned. The fix is still needed, but the implementation may change. If you care about protocol v2 or promisor remotes, this thread is one to watch.

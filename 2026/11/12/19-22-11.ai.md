This is a performance patch targeting memory usage in the commit subsystem, now with maintainer feedback.

Junio C Hamano replies to Kristofer Karlsson’s patch that removes padding from `struct commit` by reordering fields. The patch itself is a one-line change in `commit.h`, moving the `index` field to eliminate 8 bytes of padding on 64-bit platforms, reducing the struct size from 80 to 72 bytes (a 10% memory saving). The author provided measurements showing a ~32 MiB RSS reduction for `git rev-list --all` on a 4.5M-commit monorepo, with no runtime impact.

Junio’s reply is largely positive but raises two points. First, he notes that the existing comment above `struct commit`—which warns about struct size bloat and suggests using commit-slab instead of adding fields—has not been effective in preventing growth. He appreciates the discussion the patch sparks about how to enforce awareness of struct size, though he does not propose a specific solution. Second, he observes that reordering fields by size (rather than logical grouping) may obscure the design intent, particularly since `struct object` at offset 0 is a core part of Git’s in-core object model. He suggests adding comments to clarify the purpose of `index` (a unique in-memory identifier for commit-slab) and `date` (the unadjusted committer date from the commit object), whose meanings are not immediately obvious.

The patch remains technically uncontroversial and ready for integration, but Junio’s feedback hints at a broader conversation about how to manage struct bloat and maintain code clarity in performance-sensitive areas. No objections to the change itself have been raised, and Derrick Stolee’s earlier review called it "obviously correct." The discussion about a regression test for struct size is still open, but the author has deferred it to a follow-up if there’s interest.

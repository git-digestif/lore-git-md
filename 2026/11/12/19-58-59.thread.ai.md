Thread identity: Subject: [PATCH v2 0/8] promisor-remote: fix protocol v2 capability reply for fetch; Series version: v2 (8 patches, expanded from v1's 3); Originating author: Christian Couder; Thread type: bugfix patch series with preparatory refactoring.

Core problem or goal: The Git client omits the `promisor-remote=...` reply during `fetch` protocol v2 commands, breaking interactions with stateless servers (Git over HTTP, JGit/Gerrit) that handle each request independently. The bug has existed since the capability was introduced in Git v2.49 and causes fetch failures when objects are only available on promisor remotes.

Current status: Under review; v2 submitted. The series has grown from 3 to 8 patches to address the maintainer's design objection to v1. Patch 1/8 is a preparatory refactoring with no behavior change: `write_command_and_capabilities()` in `connect.c` now accepts a `const struct strvec *capabilities` instead of a `const struct string_list *server_options`, and callers build the capability list themselves using the new `add_server_options()` helper which converts existing server options into `server-option=...` strvec entries. The three call sites (`send_object_info_request()` in `fetch-object-info.c`, `send_fetch_request()` and `negotiate_using_fetch()` in `fetch-pack.c`) were updated accordingly. Patch 2/8 extends `session-id` advertisement beyond `fetch` to cover `ls-refs` and `bundle-uri` requests by modifying `send_capabilities()` in `connect.c` to read `transfer.advertiseSID` and, when set and supported by the server, write `session-id=<trace2_session_id>` alongside other capability lines; behavior changes only for users who explicitly enable `transfer.advertiseSID` (default off), and the commit message references 1e905bbc00 (2020) which originally added session-id only to fetch-pack. Patch 3/8 further refines `write_command_and_capabilities()` by adding a `struct packet_reader *reader` parameter: when non-NULL, the function sets `reader->hash_algo` to the object format advertised by the server (defaulting to SHA-1 if no `object-format` capability is sent), mirroring current `send_capabilities()` behavior; when NULL, it retains the existing validation of the server's `object-format` against `the_hash_algo` and dies on mismatch. All three current call sites pass NULL, so patch 3/8 introduces no behavior change; it prepares the function to eventually replace `send_capabilities()` for `ls-refs` and `bundle-uri` in later commits. Patch 4/8 modifies `send_capabilities()` in `connect.c` to accept a `struct strbuf *req_buf` instead of an `int fd_out`, switching from `packet_write_fmt()`/`packet_delim()`/`packet_flush()` to their `packet_buf_*()` counterparts; both `get_remote_refs()` and `get_remote_bundle_uri()` now build their entire request -- command line, capabilities, options, and flush delimiter -- into a local `struct strbuf`, then transmit it with one `write_in_full()`, with wire bytes unchanged but error handling now dying with "unable to write request to remote" (consistent with `fetch` and `object-info` paths) instead of "packet write with format failed" or silent SIGPIPE on EPIPE. This sets up patches 5/8 through 6/8 to route `ls-refs` and `bundle-uri` through the unified `write_command_and_capabilities()` function. The actual bugfix appears in patch 7/8, where `do_fetch_pack_v2()` constructs the capability list once and passes it through `send_fetch_request()` to `write_command_and_capabilities()`, ensuring the `promisor-remote=...` reply is sent with every pack-requesting `fetch`. Patch 8/8 updates `Documentation/gitprotocol-v2.adoc` to document that the reply must be sent with each pack-requesting `fetch` command. The author states the series applies cleanly on top of `maint` (v2.56.1) with passing tests.

Key technical details: Files touched: `connect.c`, `connect.h`, `fetch-pack.c`, `fetch-object-info.c`, `Documentation/gitprotocol-v2.adoc`, `t/meson.build`. New helpers introduced: `add_server_options()` and `add_promisor_remote_reply()` for building capability strvecs. `write_command_and_capabilities()` signature changed to accept `const struct strvec *capabilities` (patch 1/8) and subsequently a `struct packet_reader *reader` parameter (patch 3/8); it extracts the key portion (up to `=`) of each line to call `ensure_server_supports_v2()` before writing the full line, and when `reader` is non-NULL sets `reader->hash_algo` from the server's `object-format` capability (defaulting to SHA-1). Patch 2/8 specifics: `send_capabilities()` in `connect.c` now writes `session-id=<trace2_session_id>` when `transfer.advertiseSID` is set for `ls-refs` and `bundle-uri` commands, not just `fetch`; over `file://` and `ssh://` transports where one upload-pack process handles multiple commands, the server may log the session-id twice per process (noted as harmless by the author). Patch 4/8 specifics: `send_capabilities()` now takes `struct strbuf *req_buf` instead of `int fd_out`, using `packet_buf_write()`/`packet_buf_delim()`/`packet_buf_flush()` to buffer the request; `get_remote_refs()` and `get_remote_bundle_uri()` assemble the full request (command, capabilities, options, delimiter) in a local strbuf before a single `write_in_full()`. Wire-level changes in v2: `session-id` is now sent with `ls-refs` and `bundle-uri` requests when `transfer.advertiseSID` is set; error reporting for failed `ls-refs` and `bundle-uri` writes now uses "unable to write request to remote"; capability line order is unified with `command=bundle-uri` first; a trailing newline is no longer sent after `command=ls-refs` and `command=bundle-uri`. Test scripts: `t/t5705-session-id-in-capabilities.sh` (now with two additional cases verifying session-id is sent with `git ls-remote` when only `ls-refs` is requested and with `test-tool bundle-uri ls-remote` when only `bundle-uri` is sent), `t/t5710-promisor-remote-capability.sh`, and new HTTP-specific `t/t5711-promisor-remote-capability-http.sh`. On-disk format unchanged.

Open questions and loose ends: The main design objection from v1 (dedicated `promisor_remote_reply` argument bypassing `server_options` extensibility) has been addressed in v2 by the refactoring that unifies capability writing through the `struct strvec` approach. Whether this refactoring satisfies Junio's requirement to eliminate the duplication before merging remains to be seen in his response to v2.

Subject: [PATCH 0/3] promisor-remote: fix protocol v2 capability reply for fetch
Series version: v1 (initial submission, v2 proposed with NEEDSWORK comment)
Originating author: Christian Couder
Thread type: bugfix patch series

Core problem or goal
The Git client omits the `promisor-remote=...` reply during `fetch` protocol v2 commands, breaking interactions with servers that handle each request independently (e.g., Git over HTTP, JGit/Gerrit). The bug has existed since the capability was introduced in Git v2.49 and causes fetch failures when objects are only available on promisor remotes.

Current status
Under review; no prior versions. Three patches:
1/3 – preparatory refactoring in `write_command_and_capabilities()` to allow sending a promisor-remote reply without changing behavior; updates `connect.c`, `connect.h`, `fetch-object-info.c`, and `fetch-pack.c` to pass a new `promisor_remote_reply` argument (all callers currently pass NULL). Junio C Hamano raised a **high-weight design concern**: the new argument is seen as a workaround that bypasses the intended extensibility of the existing `server_options` string list. He proposed generalizing `server_options` to allow arbitrary key-value pairs (not just `server-option=...`), so that `promisor-remote=...` can be included as a list element rather than a separate argument. Christian Couder has now responded, acknowledging the technical debt but arguing that a unified capability table (like the server-side `capabilities[]` in `serve.c`) should be a **separate follow-up series**. He proposes sending a v2 with a `NEEDSWORK` comment in front of `write_command_and_capabilities()` to document the need for future refactoring, prioritizing the bugfix for `maint`.
2/3 – core fix: client now sends the reply during `fetch`; modifies `fetch-pack.c` to propagate the promisor-remote reply through `do_fetch_pack_v2` and `write_command_and_capabilities`. Tests in `t5710` verify the reply is sent during full clone and object-ID-only fetch; new HTTP-specific test script `t5711` validates the fix over HTTP.
3/3 – documentation update in `Documentation/gitprotocol-v2.adoc` to explicitly state that the client must send the `promisor-remote` reply with the `fetch` command, even if it was already sent with earlier commands like `ls-refs`. The change clarifies the stateless nature of protocol v2 and scenarios where `ls-refs` might not be sent (e.g., fetching only specific object IDs).

Key technical details
Files touched: `connect.c`, `connect.h`, `fetch-object-info.c`, `fetch-pack.c`, `Documentation/gitprotocol-v2.adoc`.
New test scripts: `t/t5710-protocol-v2-promisor-remote.sh` (existing), `t/t5711-protocol-v2-http-promisor-remote.sh` (new).
New behavior: client sends `promisor-remote=...` reply during `fetch` protocol v2.
On-disk format: unchanged.
Test coverage: local (full clone, object-ID-only fetch) and HTTP scenarios.
Related technical debt: three client-side capability-writing functions (`send_capabilities()`, `get_remote_refs()`, and `write_command_and_capabilities()`) duplicate logic for sending core capabilities (`server-option`, `agent`, `object-format`), while each sends a different subset. The server-side `capabilities[]` table in `serve.c` is cited as a cleaner model for future refactoring.

Open questions and loose ends
- **API design trade-off**: Junio’s counter-proposal (generalizing `server_options`) remains unimplemented. The thread now hinges on whether Junio will accept the `NEEDSWORK` compromise or insist on the cleaner API before merging. The core goal (fixing the missing promisor-remote reply) is uncontested, but the implementation path is still open.
- **Follow-up refactoring**: Christian’s proposed `NEEDSWORK` comment explicitly documents the need for a unified capability table, leaving the door open for a future series to address the technical debt.

Participant positions
Christian Couder (author): high-weight; pragmatic position: prioritize the bugfix for `maint` with a `NEEDSWORK` comment to document the need for future refactoring. Position unchanged on the core fix (2/3 and 3/3) but now open to revising 1/3 to include the comment.
Junio C Hamano (maintainer): high-weight; substantive design objection to 1/3, favoring a generalized `server_options` approach. Position remains a strong preference for a cleaner API but has not rejected the `NEEDSWORK` compromise outright. No Reviewed-by or Acked-by yet.

Thread identity
Subject: [PATCH v2] commit: shrink struct commit by reordering fields
Series version: standalone patch, v2
Originating author: Kristofer Karlsson
Thread type: performance optimization

Core problem or goal
Reduce memory usage in the commit subsystem by eliminating padding in `struct commit` on 64-bit platforms. The change reorders fields to move `unsigned int index` into the 4-byte gap after `struct object`, shrinking the struct from 80 to 72 bytes (10% reduction) with no behavioral change. The patch also improves maintainability by adding explanatory comments for `index` and `date` and explores mechanisms to enforce awareness of struct size bloat going forward.

Current status
Ready for maintainer pickup; Junio C Hamano’s "Will queue" in the latest email signals intent to merge to `next`. All prior feedback has been addressed: Derrick Stolee’s endorsement ("obviously correct") still applies, and the `struct object` comment now explicitly states the direction of safe casting (downcasting from `struct commit *` to `struct object *` is unconditional due to the first-member invariant, while upcasting requires external knowledge that the object is indeed a commit). The patch is one maintainer action away from integration.

Key technical details
- Files touched: `commit.h`
- Symbols: `struct commit` (reordered fields: `index` moved after `object`; added comments for `index` and `date`), `init_commit_node()`
- Old vs new: 80 bytes with 8-byte padding → 72 bytes with no padding on 64-bit; no change on 4-byte-aligned platforms (e.g., i386)
- On-disk format: unchanged
- Test coverage: none in patch; author measured peak RSS for `git rev-list --all` on a 4.5M-commit monorepo (32 MiB reduction, matching 8 bytes × 4.5M)
- Comments: Added to clarify `index` (unique in-memory identifier for commit-slab), `date` (unadjusted committer date from commit object or commit-graph file), and the direction of safe casting between `struct commit *` and `struct object *`. The `struct object` comment now reads: “Must be the first member, so that a `struct commit *` can be cast to a `struct object *` when we know it is a commit.”
- Invariant enforcement: Author demonstrated that violating the `struct object`-first invariant causes runtime failures in `init_commit_node()` and proposed a compile-time assertion (`BUILD_ASSERT_OR_ZERO`) as a follow-up. Oswald Buddenhagen’s suggestion (architecture-specific dummy members) offers a more flexible alternative for struct bloat enforcement.

Open questions and loose ends
- Whether to include a regression test for struct size (author prototyped but omitted, citing maintainability concerns; offered as follow-up if requested).
- Broader discussion about how to enforce awareness of struct bloat: proposed approaches include a regression test, compiler-specific `-Wpadded` warnings scoped to the struct via macros, or a compile-time assertion (`BUILD_ASSERT_OR_ZERO`) to enforce the `struct object`-first invariant. Oswald Buddenhagen suggests a pragmatic alternative: if padding is unavoidable, annotate the struct with architecture-specific dummy members to satisfy the compiler without affecting behavior. This sidesteps the inflexibility of compile-time assertions but trades off code aesthetics for portability. No consensus yet on which approach to adopt.

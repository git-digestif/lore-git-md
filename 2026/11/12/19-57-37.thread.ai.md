Thread identity: Subject: [PATCH v2 0/3] Fixes for compatObjectFormat interoperability layer; Series version: v2; Originating author: Adrian Ratiu; Thread type: patch series (bugfix).

Core problem or goal: Fix three bugs in Git's object-format interoperability layer (`compatObjectFormat`), which handles conversions between SHA-1 and SHA-256 repositories. The bugs are: (1) a crash when `compatObjectFormat` and `objectFormat` are set to the same value, leaving repositories unusable until manually edited -- in Rust-enabled builds every Git command aborted with `BUG: repository.c:204: hash_algo and compat_hash_algo match` (including `git config`), while non-Rust builds also died but for the separate reason that `compatObjectFormat` requires Rust, (2) silent incorrect OID return from `git rev-parse --output-object-format` when mapping fails, and (3) inconsistent handling of unknown commit headers during conversion (rejecting them in existing commits but copying them in new ones), which caused `git hash-object -w` to refuse commits that `git commit --amend` would accept but then fail to read back.

Current status: Under review; v2 posted incorporating Patrick Steinhardt's feedback. Patch 1 (crash fix) has received maintainer approval from Junio C Hamano, who agrees the trigger condition represents an incorrectly configured repository rather than a `BUG()` and that returning a clear error message is more appropriate than aborting. Patch 2 (rev-parse mapping failure) has also received maintainer approval from Junio C Hamano, who called the test "clever and clean" and approved the approach. Adrian Ratiu has since clarified in reply to Junio's wording question that the fix covers invocations with multiple explicit single revisions such as `git rev-parse --output-object-format=sha1 main next`, but does not cover range arguments like `A..B`, `A...B`, or internally-expanded shorthands like `rev^!`, and has committed to clarifying this distinction in the v3 commit message; he also credited Patrick Steinhardt for the test design in `t/t1500-rev-parse.sh`. Patch 3 (unknown commit headers) is under active maintainer review: Junio C Hamano has endorsed the patch's core direction of converting object IDs only in known headers (`tree`, `parent`, `mergetag`) while copying all other headers verbatim, agrees the now-redundant special cases for `author`, `committer`, `encoding`, and `gpgsig` in `convert_commit_object()` can be removed, but questions the specific change from `<` to `<=` in the length checks for `"tree "`, `"parent "`, and `"mergetag "`. In his latest substantive email, Junio C Hamano stated that the v2 changes "looked reasonable" and approved the series direction overall, while explicitly noting that he is neither Eric Sunshine nor brian m. carlson -- the two people Adrian Ratiu specifically requested to review patch 3 -- but approving regardless.

Key technical details: Files touched: `builtin/rev-parse.c`, `object-file-convert.c`, `setup.c`. New test scripts: `t1302-repo-version.sh` (patch 1), `t1500-rev-parse.sh` (patch 2), `t1016-compatObjectFormat.sh` (patch 3). New/changed behavior: (1) `setup.c` guards against identical `compatObjectFormat` and `objectFormat` in `verify_repository_format()`, preventing the `BUG: repository.c:204: hash_algo and compat_hash_algo match` crash in Rust builds and the Rust-requirement death in non-Rust builds, returning a clear error message spelling the config key as `extensions.compatObjectFormat`, (2) `git rev-parse --output-object-format` checks `repo_oid_to_algop()` for a `< 0` return and dies with "cannot map object %s to %s" on mapping failure instead of returning an incorrect OID, aligning its behavior with `git pack-objects` and other callers; the fix applies to multiple explicit single-revision arguments but not to range arguments (`A..B`, `A...B`) or internally-expanded shorthands (`rev^!`); the test uses a `RUST` prerequisite, initializes a SHA-256 repository, writes an object before enabling `extensions.compatObjectFormat` (so it receives no compat mapping), then sets the config and verifies that requesting the SHA-256 ID succeeds while requesting the SHA-1 compat ID fails with the expected error, avoiding manual object-directory copying which would be fragile under the upcoming ODB abstraction, (3) unknown commit headers are now copied unchanged in both existing and new commits (removing the 2023 check); the implementation unifies `convert_commit_object()` and `convert_commit_extra_headers()` by copying all unknown headers verbatim, including continuation lines, removing the separate cases for `author`, `committer`, `encoding`, and `gpgsig` since they are now handled by the generic copy path, and changes the three header-length checks from `<` to `<=` so the converter classifies headers by the key before the first space, matching `read_commit_extra_header_lines()`; under this scheme `"tree "`, `"parent "`, and `"mergetag "` with empty or malformed values are rejected as before the series, while bare `"tree"`, `"parent"`, or `"mergetag"` without a trailing space are treated as unknown headers and copied verbatim, exactly what `git commit --amend` already does. On-disk format: unchanged.

Open questions and loose ends: Whether the removal of the 2023 check in patch 3 is acceptable, and how to handle malformed headers. The v2 `<=` fix addresses the specific empty-value edge cases Adrian Ratiu identified in v1 but leaves broader questions open: whether to add generic format validation (requiring `key<space>value` structure) inside the converter -- which Adrian argues against because it would reject headers that `read_commit_extra_header_lines()` and the `--amend` path accept (e.g., a bare `"x-foo"` line), causing `git commit --amend` to record compat IDs that cannot be read back; Adrian suggests `fsck` as the more appropriate place for stricter validation (noting it currently ignores headers after `committer`) but treats that as a separate topic. Patrick Steinhardt's forward-looking proposal--a standardized `x-obj-` prefix for custom headers containing object IDs--could address the patch's acknowledged risk (unknown headers with unconverted object IDs) but is beyond the scope of this series. Adrian Ratiu explicitly welcomes review from Eric Sunshine or brian m. carlson on the patch 3 trade-off; Junio C Hamano has now approved the series overall but explicitly noted he is neither of those two requested reviewers, so the request for additional eyes from Eric Sunshine or brian m. carlson on patch 3's removal of the unknown-header rejection remains technically open. Junio C Hamano's earlier review of patch 3 asks specifically why a line consisting solely of `"parent \n"` should enter the `else if` branch and be passed to `parse_oid_hex_algop()` rather than being treated as an unknown header, and requests better commit message justification for the equality case in the length checks; these substantive questions remain unaddressed. Adrian Ratiu has committed to clarifying in the v3 commit message that patch 2's fix covers multiple explicit single revisions but not range arguments or internally-expanded shorthands.

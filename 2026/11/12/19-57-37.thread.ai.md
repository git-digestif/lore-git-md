Thread identity: Subject: [PATCH v2 0/3] Fixes for compatObjectFormat interoperability layer; Series version: v2; Originating author: Adrian Ratiu; Thread type: patch series (bugfix).

Core problem or goal: Fix three bugs in Git's object-format interoperability layer (`compatObjectFormat`), which handles conversions between SHA-1 and SHA-256 repositories. The bugs are: (1) a crash when `compatObjectFormat` and `objectFormat` are set to the same value, leaving repositories unusable until manually edited -- in Rust-enabled builds every Git command aborted with `BUG: repository.c:204: hash_algo and compat_hash_algo match` (including `git config`), while non-Rust builds also died but for the separate reason that `compatObjectFormat` requires Rust, (2) silent incorrect OID return from `git rev-parse --output-object-format` when mapping fails, and (3) inconsistent handling of unknown commit headers during conversion (rejecting them in existing commits but copying them in new ones), which caused `git hash-object -w` to refuse commits that `git commit --amend` would accept but then fail to read back.

Current status: Under review; v2 posted incorporating Patrick Steinhardt's feedback. Patch 1 (crash fix) and patch 2 (rev-parse behavior) remain uncontroversial and well-justified. Patch 1 now spells the config key as `extensions.compatObjectFormat` in the error message and uses modern `git config set`/`unset` syntax in `t/t1302-repo-version.sh`; the new guard in `verify_repository_format()` runs before any Rust-only code paths so both build types receive the same clear error message, and the test exercises both SHA-1 and SHA-256 without requiring a `RUST` prerequisite, recovering the repository by unsetting the key via `git config unset --file=...`; all prior cosmetic feedback resolved. Patch 2 now checks `repo_oid_to_algop()` for a `< 0` return in `builtin/rev-parse.c` and dies with "cannot map object %s to %s", the commit message clarifies that only single-revision arguments pass the desired output hash explicitly while ranges like `A..B` do not, and the test in `t/t1500-rev-parse.sh` writes the object with `extensions.compatobjectformat` unset and enables the config afterward, avoiding manual object-directory copying; all prior feedback resolved. Patch 3 (unknown commit headers) remains the focus of substantive discussion: it removes a 2023 safety check (commit 08a45903cb) that was deliberately added, and v2 changes the header-length checks in `convert_commit_object()` from `<` to `<=` for `"tree "`, `"parent "`, and `"mergetag "` so these headers are classified by key alone as `read_commit_extra_header_lines()` does, ensuring malformed values (e.g., `"tree "` with nothing after the space, or an empty-first-line `"mergetag "`) are rejected rather than copied with unconverted object IDs, while bare `"tree"` lines without a space are treated as unknown headers and copied verbatim; a new test for the empty-mergetag case is added to `t/t1016-compatObjectFormat.sh`.

Key technical details: Files touched: `builtin/rev-parse.c`, `object-file-convert.c`, `setup.c`. New test scripts: `t1302-repo-version.sh` (patch 1), `t1500-rev-parse.sh` (patch 2), `t1016-compatObjectFormat.sh` (patch 3). New/changed behavior: (1) `setup.c` guards against identical `compatObjectFormat` and `objectFormat` in `verify_repository_format()`, preventing the `BUG: repository.c:204: hash_algo and compat_hash_algo match` crash in Rust builds and the Rust-requirement death in non-Rust builds, returning a clear error message spelling the config key as `extensions.compatObjectFormat`, (2) `git rev-parse --output-object-format` checks `repo_oid_to_algop()` for a `< 0` return and dies with "cannot map object %s to %s" on mapping failure instead of returning an incorrect OID, aligning its behavior with `git pack-objects` and other callers; the test writes the object with `extensions.compatobjectformat` unset and then sets the config afterward rather than manually copying a loose object, avoiding fragility under the upcoming ODB abstraction, (3) unknown commit headers are now copied unchanged in both existing and new commits (removing the 2023 check); the implementation unifies `convert_commit_object()` and `convert_commit_extra_headers()` by copying all unknown headers verbatim, including continuation lines, removing the separate cases for `author`, `committer`, `encoding`, and `gpgsig` since they are now handled by the generic copy path, and changes the three header-length checks from `<` to `<=` so the converter classifies headers by the key before the first space, matching `read_commit_extra_header_lines()`; under this scheme `"tree "`, `"parent "`, and `"mergetag "` with empty or malformed values are rejected as before the series, while bare `"tree"`, `"parent"`, or `"mergetag"` without a trailing space are treated as unknown headers and copied verbatim, exactly what `git commit --amend` already does. On-disk format: unchanged.

Open questions and loose ends: Whether the removal of the 2023 check in patch 3 is acceptable, and how to handle malformed headers. The v2 `<=` fix addresses the specific empty-value edge cases Adrian Ratiu identified in v1 but leaves broader questions open: whether to add generic format validation (requiring `key<space>value` structure) inside the converter -- which Adrian argues against because it would reject headers that `read_commit_extra_header_lines()` and the `--amend` path accept (e.g., a bare `"x-foo"` line), causing `git commit --amend` to record compat IDs that cannot be read back; Adrian suggests `fsck` as the more appropriate place for stricter validation (noting it currently ignores headers after `committer`) but treats that as a separate topic. Patrick Steinhardt's forward-looking proposal--a standardized `x-obj-` prefix for custom headers containing object IDs--could address the patch's acknowledged risk (unknown headers with unconverted object IDs) but is beyond the scope of this series. Adrian Ratiu explicitly welcomes review from Eric Sunshine or brian m. carlson on the patch 3 trade-off.

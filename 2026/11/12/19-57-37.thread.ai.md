Thread identity
Subject: [PATCH 0/3] Fixes for compatObjectFormat interoperability layer
Series version: v1 (initial submission)
Originating author: Adrian Ratiu
Thread type: patch series (bugfix)

Core problem or goal
Fix three bugs in Git’s object-format interoperability layer (`compatObjectFormat`), which handles conversions between SHA-1 and SHA-256 repositories. The bugs are: (1) a crash when `compatObjectFormat` and `objectFormat` are set to the same value, leaving repositories unusable until manually edited, (2) silent incorrect OID return from `git rev-parse --output-object-format` when mapping fails, and (3) inconsistent handling of unknown commit headers during conversion (rejecting them in existing commits but copying them in new ones).

Current status
Under review; no prior versions. Patch 1 (crash fix) and patch 2 (rev-parse behavior) remain uncontroversial and well-justified; patch 1 has received surface-level feedback requesting minor cosmetic adjustments (error-message capitalization and test-script syntax). Patch 3 (unknown commit headers) is now the focus of substantive discussion: it removes a 2023 safety check (commit 08a45903cb) that was deliberately added, and Patrick Steinhardt’s review explores the trade-off between consistency and safety, including edge cases (malformed headers) and a forward-looking proposal for extensibility (standardized `x-obj-` prefix for custom headers).

Key technical details
Files touched: `builtin/rev-parse.c`, `object-file-convert.c`, `setup.c`
New test scripts: `t1302-repo-version.sh` (patch 1), `t1500-rev-parse.sh` (patch 2), `t1016-compatObjectFormat.sh` (patch 3)
New/changed behavior: (1) `setup.c` guards against identical `compatObjectFormat` and `objectFormat` in `verify_repository_format()`, preventing a BUG() crash and returning a clear error message (with requested capitalization fix), (2) `git rev-parse --output-object-format` dies on mapping failure instead of returning an incorrect OID, aligning its behavior with `git pack-objects` and other callers of `repo_oid_to_algop()`, (3) unknown commit headers are now copied unchanged in both existing and new commits (removing the 2023 check); the implementation unifies `convert_commit_object()` and `convert_commit_extra_headers()` by copying all unknown headers verbatim, including continuation lines. Edge case: malformed headers (e.g., `"tree"` without a trailing space or object ID) are now copied instead of rejected.
On-disk format: unchanged

Open questions and loose ends
Whether the removal of the 2023 check in patch 3 is acceptable, and whether to tighten validation of malformed headers (e.g., reject lines that don’t match `key<space>value`). Patrick Steinhardt’s review suggests the current approach might be overly permissive but acknowledges the complexity of stricter validation. His forward-looking proposal—a standardized `x-obj-` prefix for custom headers containing object IDs—could address the patch’s acknowledged risk (unknown headers with unconverted object IDs) but is beyond the scope of this series. Additionally, Patrick Steinhardt raised a forward-compatibility concern about the test design in patch 2 (manual object copying), but this remains a test-maintenance observation rather than a correctness critique.

Participant positions
Adrian Ratiu (author): proposes the series, justifies the trade-off in patch 3’s commit message, and provides test coverage for all three fixes. Position unchanged: advocates for consistency (copying unknown headers in both paths) over the 2023 safety check.
Patrick Steinhardt: provided surface-level review of patch 1, requesting minor cosmetic adjustments (error-message capitalization and test-script syntax). Raised a forward-compatibility concern about patch 2’s test design but did not question its core logic. In this email, he provided substantive feedback on patch 3, engaging with the trade-offs and edge cases (malformed headers, `x-obj-` prefix proposal) but explicitly endorsing the patch’s direction. Position: no objections to technical correctness; feedback focuses on refining implementation details and future-proofing.

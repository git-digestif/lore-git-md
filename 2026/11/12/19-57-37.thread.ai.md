Subject: [PATCH 0/3] Fixes for compatObjectFormat interoperability layer
Series version: v1 (initial submission)
Originating author: Adrian Ratiu
Thread type: patch series (bugfix)

Core problem or goal
Fix three bugs in Git’s object-format interoperability layer (`compatObjectFormat`), which handles conversions between SHA-1 and SHA-256 repositories. The bugs are: (1) a crash when `compatObjectFormat` and `objectFormat` are set to the same value, leaving repositories unusable until manually edited, (2) silent incorrect OID return from `git rev-parse --output-object-format` when mapping fails, and (3) inconsistent handling of unknown commit headers during conversion (rejecting them in existing commits but copying them in new ones).

Current status
Under review; no prior versions. Patch 1 (crash fix) and patch 2 (rev-parse behavior) remain uncontroversial and well-justified. Patch 3 (unknown commit headers) is now the focus of discussion: it removes a 2023 safety check (commit 08a45903cb) that was deliberately added, and the trade-off between consistency and safety is explicitly framed.

Key technical details
Files touched: `builtin/rev-parse.c`, `object-file-convert.c`, `setup.c`
New test scripts: `t1302-repo-version.sh` (patch 1), `t1500-rev-parse.sh` (patch 2), `t1016-compatObjectFormat.sh` (patch 3)
New/changed behavior: (1) `setup.c` guards against identical `compatObjectFormat` and `objectFormat` in `verify_repository_format()`, preventing a BUG() crash and returning a clear error message, (2) `git rev-parse --output-object-format` dies on mapping failure instead of returning an incorrect OID, aligning its behavior with `git pack-objects` and other callers of `repo_oid_to_algop()`, (3) unknown commit headers are now copied unchanged in both existing and new commits (removing the 2023 check); the implementation unifies `convert_commit_object()` and `convert_commit_extra_headers()` by copying all unknown headers verbatim, including continuation lines.
On-disk format: unchanged

Open questions and loose ends
Whether the removal of the 2023 check in patch 3 is acceptable. The commit message presents the trade-off (consistency with external tools like Jujutsu vs. safety of rejecting unrecognized headers) but does not claim consensus. Reviewers may request alternative solutions (e.g., a configurable allowlist for unknown headers) or additional safeguards.

Participant positions
Adrian Ratiu (author): proposes the series, justifies the trade-off in patch 3’s commit message, and provides test coverage for all three fixes. Positions unchanged: no other participants have reviewed or commented yet.

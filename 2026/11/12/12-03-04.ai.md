This is the second patch in Yoichi NAKAYAMA’s three-patch series introducing worktree-specific submodule configuration. It implements the core logic that stores submodule settings (`submodule.<name>.active`, `submodule.<name>.url`, etc.) in the worktree config file when `extensions.worktreeConfig` is enabled, rather than in the shared repository config.

The patch modifies `builtin/submodule--helper.c` to use the new `repo_config_set_worktree_gently()` helper (introduced in an earlier patch) wherever submodule settings are written. This ensures that settings like URLs, which may differ between branches checked out in separate worktrees, are isolated to the worktree that created them. The `git submodule deinit` command is also updated: when `extensions.worktreeConfig` is enabled, it sets `submodule.<name>.active` to `false` in the worktree config instead of removing the entire section from the repository config, preserving shared settings while unregistering the submodule for that worktree.

In `builtin/worktree.c`, the patch adds logic to `copy_filtered_worktree_config()` to explicitly exclude `submodule.<name>.gitdir` settings when creating a new worktree. This prevents the gitdir path from being copied between worktrees, since gitdirs are inherently worktree-specific and should not be shared.

The test coverage is thorough: `t/t2405-worktree-submodule.sh` now includes tests verifying that submodule settings are correctly stored in the worktree config, that `deinit` updates the active flag without touching the repository config, and that gitdir settings are not copied to new worktrees. `t/t7425-submodule-gitdir-path-extension.sh` adds tests confirming that gitdir paths for both the main and linked worktrees are stored in the worktree config.

The implementation is clean and well-scoped, leveraging the existing `extensions.worktreeConfig` mechanism without introducing new on-disk formats. The commit message clearly explains the motivation and the technical choices, and the test coverage addresses the key edge cases. No controversial design decisions are evident, though the interaction with existing submodule workflows (e.g., `git submodule update --init`) may still draw scrutiny in review. This patch is a logical continuation of the series and should be evaluated alongside the others.

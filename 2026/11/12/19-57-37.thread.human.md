This thread is Adrian Ratiu's three-patch v2 series fixing bugs in Git's SHA-1/SHA-256 interoperability layer (`compatObjectFormat`). The first patch fixes a crash where setting `compatObjectFormat` equal to `objectFormat` left repositories unusable -- in Rust-enabled builds every command aborted with a `BUG:` assertion, and non-Rust builds died because the extension requires Rust; v2 adds an early guard in `verify_repository_format()` so both build types get the same clear error. The second patch fixes `git rev-parse --output-object-format` silently returning an incorrect OID when the hash mapping fails, now dying with a clear error instead. Both patches are uncontroversial and incorporate Patrick Steinhardt's feedback.

The third patch is the substantive one: it removes a deliberate 2023 safety check so that unknown commit headers are copied unchanged during conversion in both the existing-commit and new-commit paths, making `git hash-object -w` accept what `git commit --amend` accepts. The v2 revision tightens classification of `tree`, `parent`, and `mergetag` headers so malformed empty values are rejected rather than copied with unconverted object IDs. The trade-off is acknowledged in the commit message: unknown headers containing object IDs will now be copied without conversion, which matters for tools like Jujutsu that write custom headers.

The series remains under review. Patrick Steinhardt has reviewed without objection, and his forward-looking idea of a standardized `x-obj-` prefix for headers containing object IDs is noted as future work beyond this series. Adrian explicitly welcomes review from Eric Sunshine or brian m. carlomb on the patch 3 trade-off, and whether stricter header validation belongs in `fsck` is left as an open follow-up question.

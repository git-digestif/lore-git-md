Adrian Ratiu's v2 series fixing three bugs in Git's `compatObjectFormat` SHA-1/SHA-256 interoperability layer is under review, with Junio C Hamano having just endorsed the first patch. The series addresses a crash that made repositories unusable when `extensions.compatObjectFormat` matched `objectFormat` (every command aborted with a `BUG()` in Rust builds, including `git config`), a silent incorrect OID from `git rev-parse --output-object-format` on mapping failure, and inconsistent handling of unknown commit headers during conversion. Junio approved patch 1/3, agreeing that the identical-hash configuration represents a misconfigured repository rather than an internal error, so a clear diagnostic is preferable to the abort; the guard in `verify_repository_format()` now runs before Rust-only code paths so both build types get the same message, and the test exercises both hash algorithms without requiring Rust.

Patches 1 and 2 remain uncontroversial. Patch 1 spells the config key correctly as `extensions.compatObjectFormat` and uses modern `git config` syntax in tests, while patch 2 makes `rev-parse` die with "cannot map object" instead of returning wrong results, with the test writing objects before enabling the config to avoid fragility. Both incorporate Patrick Steinhardt's earlier feedback.

Patch 3 remains the open question. It removes a deliberate 2023 safety check (commit 08a45903cb) so unknown commit headers are copied verbatim in both existing and new commits, with v2 fixing header-length checks from `<` to `<=` to reject malformed values like empty `"tree "` lines while treating bare keys as unknown headers -- matching `git commit --amend` behavior. Adrian argues against adding stricter validation in the converter itself, suggesting `fsck` as the proper venue, and acknowledges Patrick's proposal for an `x-obj-` prefix for custom object-ID headers as future work. The series is still under review overall, with patch 3 awaiting broader consensus.

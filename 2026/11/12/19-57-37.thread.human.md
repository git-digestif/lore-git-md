Adrian Ratiu has submitted a three-patch series fixing bugs in Git's SHA-1/SHA-256 interoperability layer (`compatObjectFormat`), and the thread is currently under review with Patrick Steinhardt providing the main technical feedback. The first two patches -- fixing a crash when `compatObjectFormat` equals `objectFormat`, and making `git rev-parse --output-object-format` die on mapping failure -- have drawn only minor, accepted feedback on wording and test design. The substantive discussion centers on patch 3, which removes a 2023 safety check so that unknown commit headers are copied unchanged during conversion in both existing and new commits; Patrick has endorsed this direction while probing edge cases.

In his latest reply, Adrian reports two edge-case bugs he found in his own v1 implementation: a `"tree "` line with a trailing space but no value, and a `"mergetag "` line with an empty first line, both slip through the current checks and get copied with unconverted object IDs, recreating the very inconsistency the patch aims to fix. To resolve this in v2, he proposes changing the header-length comparisons from `<` to `<=` so headers are classified by the key before the first space, matching `git commit --amend`'s behavior; malformed values like `"tree "` would then be rejected while bare `"tree"` without a space would be copied as unknown. He pushes back on adding generic `key<space>value` validation inside the converter, arguing it would reject inputs the `--amend` path accepts and that `fsck` is the better place for stricter checks -- a separate topic. The series remains under review with no merge decision; Adrian will send v2 incorporating the `<=` fix, a new test for the empty-mergetag case, and cosmetic cleanups, while leaving broader questions of fsck-based validation and a standardized `x-obj-` header prefix as noted future work.

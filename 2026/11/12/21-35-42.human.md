This is a performance patch targeting memory usage in the commit subsystem, now updated with author feedback and a plan for follow-up work.

Kristofer Karlsson responds to Junio C Hamano’s review of his patch that removes padding from `struct commit` by reordering fields. The patch itself remains a minimal one-line change in `commit.h`, moving the `index` field to eliminate 8 bytes of padding on 64-bit platforms, reducing the struct size from 80 to 72 bytes (a 10% memory saving). The author has provided a detailed history of `struct commit`’s size evolution since 2018, showing how padding has fluctuated due to unrelated changes (e.g., SHA-256 support, `FLAG_BITS` adjustments), reinforcing the need for better tooling to catch regressions.

In response to Junio’s feedback on code clarity, Kristofer agrees to add comments for `index` (a unique in-memory identifier for commit-slab) and `date` (the unadjusted committer date from the commit object) in a v2, along with a note that `struct object` must remain at offset 0. He also proposes two follow-up approaches to enforce struct size awareness: (1) a regression test for padding (though he notes the complexity of cross-platform alignment rules), and (2) a compiler-specific `-Wpadded` warning scoped to the struct via macros in `git-compat-util.h`. The latter would work for GCC and Clang but would need to be disabled if unavoidable padding is introduced later.

The patch is technically uncontroversial and ready for integration, with Derrick Stolee’s earlier review calling it "obviously correct." The broader discussion about struct bloat awareness—sparked by Junio’s observation that the existing warning comment has not prevented regressions—remains open but does not block this change. The author’s proposed follow-ups could provide a lightweight way to catch future padding regressions without requiring manual measurement.

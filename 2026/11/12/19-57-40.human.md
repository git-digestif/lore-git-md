This is the third and most consequential patch in Adrian Ratiu’s three-part bugfix series for Git’s `compatObjectFormat` interoperability layer. It addresses an inconsistency in how Git handles unknown commit headers when converting between SHA-1 and SHA-256 repositories.

The patch removes a 2023 safety check (commit 08a45903cb) that rejected unknown commit headers during conversion of existing commits, while leaving the code path for *new* commits (via `commit_tree_extended()`) unchanged. This mismatch meant tools like Jujutsu—which embed custom headers (e.g., `change-id`) in every commit—could create commits that Git later refused to convert, breaking interoperability. The fix makes both code paths copy unknown headers unchanged, prioritizing consistency over the earlier safety-oriented approach.

The commit message clearly explains the trade-off: while the 2023 check aimed to prevent potential OID corruption in unknown headers, it broke real-world workflows. Adrian proposes copying headers as-is, noting that any header containing OIDs would need explicit handling in Git anyway. The patch also simplifies the code by merging the separate cases for `author`, `committer`, `encoding`, and `gpgsig` headers into a single fallback path.

Test coverage is thorough, with a new test in `t1016-compatObjectFormat.sh` that verifies commits with unknown headers can be both created and amended without conversion failures. The test uses `git hash-object` and `git commit --amend` to confirm both code paths produce identical results.

This patch is likely to spark discussion. The 2023 check was added deliberately, and its removal—while justified by the commit message—may need broader consensus. The change is narrowly scoped to the `compatObjectFormat` layer, so it won’t affect repositories not using this extension. If accepted, it would resolve a practical pain point for tools relying on custom commit headers.

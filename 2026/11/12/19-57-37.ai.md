This is a three-patch bugfix series targeting Git’s object-format interoperability layer, specifically the `compatObjectFormat` mechanism used when converting between SHA-1 and SHA-256 repositories.

The series fixes three distinct issues. Patch 1 adds a guard in `setup.c` to reject the nonsensical case where `compatObjectFormat` and `objectFormat` are set to the same value, preventing a BUG() crash later. Patch 2 tightens `git rev-parse --output-object-format` to die with a clear error when it cannot map an object to the requested format, rather than silently returning an incorrect OID. Patch 3 changes how unknown commit headers are handled during conversion: Git previously rejected them when converting existing commits but copied them when creating new ones; the patch makes both paths copy them unchanged, removing a check that was deliberately added in 2023.

The first two patches are straightforward and appear well-justified by the test coverage. The third patch is flagged as needing careful review because it alters a behavior that was explicitly chosen in commit 08a45903cb; the commit message explains the trade-off but does not claim consensus, so this is likely to be the main point of discussion in the thread. Files touched include `builtin/rev-parse.c`, `object-file-convert.c`, `setup.c`, and three new test scripts (`t1016-compatObjectFormat.sh`, `t1302-repo-version.sh`, `t1500-rev-parse.sh`).

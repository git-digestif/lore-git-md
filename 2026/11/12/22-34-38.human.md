This is a **design discussion reply** from Junio C Hamano in the ongoing promisor-remote protocol v2 bugfix series. The thread targets a long-standing bug where Git clients fail to send the `promisor-remote=...` reply during `fetch` protocol v2 commands, breaking interactions with stateless servers like HTTP and JGit/Gerrit.

Junio expands on his earlier architectural concern about patch 1/3, which adds a dedicated `promisor_remote_reply` argument to `write_command_and_capabilities()`. He clarifies that his objection is not about the capability itself but about the API design: the function was intended to handle all capability exchanges generically via the existing `server_options` string list, and introducing a hardcoded parameter feels like a workaround. He suggests a more elegant solution—extending the `server_options` list to support non-"server-option" keys (like `promisor-remote`)—so the caller could simply include the reply string in the list rather than passing it as a separate argument.

The reply is constructive and shifts the discussion toward a cleaner API design rather than rejecting the fix outright. Christian now has a clear alternative to consider: refactor the string list to be more flexible rather than adding a new parameter. The ball is back in his court to either defend the current approach or propose a revised implementation that aligns with Junio’s suggestion. The urgency of the bug (fetch failures with promisor remotes) and the thorough test coverage in the series suggest this is a solvable design question, not a fundamental roadblock.

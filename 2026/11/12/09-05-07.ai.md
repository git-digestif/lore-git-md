This is a **bugfix and feature patch** targeting the `git log --follow` functionality. It addresses a severe performance regression introduced by commit 304812ed33 (June 2026), which made `--follow` on non-linear history (e.g., Linux kernel repository) nearly 15× slower—from 28 seconds to 6 minutes 43 seconds—by diffing each merge against all parents with rename detection enabled.

The patch makes the expensive per-parent diffing **opt-in** rather than default. The original behavior (pre-304812ed33) is restored for plain `--follow`, while `--follow=merges` (and `log.follow=merges`) enables the new, more thorough but slower logic. The implementation touches `builtin/log.c`, `diff.c`, `diff.h`, and `log-tree.c`, adding a new `follow_merges` flag to the diff options and plumbing it through the revision machinery. Documentation (`git-log.adoc`, `config/log.adoc`) and tests (`t4219-log-follow-merge.sh`) are updated to reflect the new syntax and behavior.

The patch is **well-motivated**: the regression is real, measurable, and affects a common workflow (`git log --stat --follow` on a single file in a large repository). The opt-in design is a pragmatic compromise suggested by Patrick Steinhardt, avoiding a full revert while preserving the improved correctness for users who need it. The code is clean, the commit message is clear, and the test coverage is thorough, including edge cases like invalid arguments and config overrides. This looks like a **ready-to-merge** fix for a painful regression.

This is a review of the third patch in Justin Tobler’s four-patch series that makes Git’s ODB transaction machinery more robust by creating the temporary object directory eagerly at transaction start. The patch itself is a small but important correctness fix: it preserves `errno` across cleanup in `tmp_objdir_create()` so that callers can reliably inspect why directory creation failed. Karthik Nayak’s review suggests an alternative implementation that inlines the `setup_tmp_objdir()` helper function and centralizes `errno` preservation, arguing that this approach is less error-prone and easier to maintain. His feedback is substantive, engaging with the code’s structure and long-term maintainability rather than just surface-level details.

The patch touches only `tmp-objdir.c` and its header, adding a few lines to save and restore `errno` around `mkdtemp()` and `setup_tmp_objdir()` calls. Karthik’s proposed alternative would eliminate the helper function entirely, moving its logic into `tmp_objdir_create()` and using a `goto`-based cleanup pattern to ensure `errno` is preserved only for the specific failure cases that matter. This change would make the code more self-contained and reduce the risk of future modifications accidentally clobbering `errno`. While the current patch is mechanically correct, Karthik’s suggestion addresses a potential maintenance pitfall that could become relevant if the function evolves further.

The discussion here is narrowly focused on implementation details rather than the series’ broader design goals. Earlier reviews have already raised deeper questions about the motivation for eager directory creation (Karthik’s skepticism) and error-message clarity (Patrick Steinhardt’s objection to jargon in tests), but this exchange is purely about how best to preserve `errno`. The patch is uncontroversial in its intent—both reviewers agree that `errno` preservation is necessary—but the disagreement over *how* to achieve it is worth noting for anyone following the series.

For a busy reader, this patch is a minor but necessary piece of the larger ODB transaction effort. Karthik’s feedback is constructive and likely to improve the code’s robustness, but it does not challenge the patch’s fundamental correctness. If Justin adopts the inlining approach, the change will be slightly more invasive but also more future-proof. The patch remains well-scoped and well-motivated, even if the implementation details are still under discussion.

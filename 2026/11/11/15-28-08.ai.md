This is the third patch in Jasper Mayone’s five-patch v5 series extending Git’s ref-filter atoms to better handle worktrees. It specifically addresses the long-standing gap where `%(worktreepath)`—used by `git branch` to mark branches checked out in linked worktrees—would report an empty string for branches being rebased or bisected, even though those branches are treated as "checked out" by other Git commands (`git worktree add`, `git branch -d`).

The patch replaces the old O(N*M) implementation (which iterated over all worktrees for every ref) with a new O(1) lookup via a hashmap populated during `prepare_checked_out_branches()`. The key change is in `branch.c`, where two new maps are introduced: `checked_out_worktrees` (for `%(worktreepath)`) and `current_worktree_branches` (for the new `%(currentworktree)` atom in patch 4). The lookup function `branch_checked_out_worktree()` now returns the correct worktree path for rebasing/bisecting branches, while intentionally excluding branches that `git rebase --update-refs` will update (since those branches are not actually checked out in any worktree).

A notable side effect is a **breaking change for bare repositories**: `%(worktreepath)` used to return the bare repository’s path for its HEAD branch, but now returns an empty string, aligning the atom’s behavior with its name and purpose. The commit message and documentation explicitly call this out, and the tests verify the new behavior.

The patch touches `ref-filter.c`, `branch.c`, and their documentation, and adds comprehensive tests covering rebasing, bisecting, interactive rebase stops, `rebase --update-refs`, and bare repositories. The implementation is clean, well-motivated, and resolves the performance regression identified in v4. It’s a clear improvement over the previous state and looks ready for integration.

This thread is about a usability issue in `git repack --drop-filtered`: when the command encounters a blob that is both eligible for dropping (due to the filter) and referenced by the current index, it aborts entirely. The reporter, kongfankaikai, asked whether this behavior is necessary or if the command could skip such blobs and continue, improving usability in partial clones.

Siddharth Shrimali has now clarified that the fatal error is not required for correctness but was a conservative design choice to avoid dropping blobs that would immediately be lazy-fetched again. This limitation was previously noted by Samuel Bronson, and Siddharth agrees the behavior should change. He is working on a patch to modify `builtin/repack.c` so that the command skips blobs referenced by the index (with a warning) and continues processing other eligible objects. The patch is expected soon, and the discussion has shifted from "should we do this?" to "how will the fix work?" The relevant subsystems are the repack machinery and partial clone support. No new technical questions or edge cases have been raised in this update.

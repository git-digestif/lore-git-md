This is the fourth patch in Jasper Mayone’s five-patch v5 series, adding the new `%(currentworktree)` atom to Git’s ref-filter. The atom returns the absolute path of the current worktree if the ref is checked out there (or being rebased or bisected), and an empty string otherwise. It is implemented as a second hashmap (`current_worktree_branches`) in `branch.c`, populated during `prepare_checked_out_branches()`, so the lookup is O(1) per ref. The patch touches `branch.c`, `branch.h`, `ref-filter.c`, and `Documentation/git-for-each-ref.adoc`, and adds a test in `t/t6302-for-each-ref-filter.sh` that verifies the atom’s behavior in both the main and a linked worktree.

The motivation is clear: `%(worktreepath)` tells you which worktree has a branch checked out, but you cannot tell whether that worktree is the current one without comparing paths, which is awkward in `%(if:equals=...)` because a closing parenthesis ends the atom. `%(currentworktree)` solves this by exposing the current worktree’s path directly, enabling more flexible formatting in `git branch` and other ref-filter consumers. The next patch in the series uses it to simplify the logic in `git branch`, replacing a second format string with a single conditional atom.

The implementation is clean and well-motivated. The new hashmap is populated alongside the existing `checked_out_worktrees` map, so the overhead is minimal. The documentation is clear, and the test covers both the main and a linked worktree, including a rebase-in-progress scenario. The patch directly addresses Phillip Wood’s architectural suggestion from v4, which proposed using a similar atom to simplify the `git branch` logic. This is a useful addition that could see broader use in the future.

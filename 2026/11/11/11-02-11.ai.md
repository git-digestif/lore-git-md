The thread centers on the three-state system formed by `RERERE_AUTOUPDATE` and `RERERE_NOAUTOUPDATE` (follow default, force autoupdate, force no-autoupdate) and the lack of explicit validation for the invalid state where both bits are set. Junio’s prior email highlighted this as a low-priority correctness concern, and Patrick’s reply confirms the current behavior: `RERERE_AUTOUPDATE` silently takes precedence over `RERERE_NOAUTOUPDATE` in `rerere_cache_setup()`, but no caller intentionally passes both flags. The discussion now shifts to whether this silent precedence is robust enough or if a `BUG()` or `die()` should be added to catch misuse. No patch has been proposed yet, but the tone suggests this is a minor cleanup opportunity rather than a blocker. The series itself is already merged to `master`, so any follow-up would be a separate, small patch. Key technical details: the flags are consumed in `rerere_cache_setup()` (in `rerere.c`), and the CLI parser (`parse_opt_tertiary()`) already prevents both bits from being set simultaneously, but the consuming code does not validate the state. This is not a regression but a pre-existing issue made visible by the refactoring.

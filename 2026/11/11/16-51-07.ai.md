This is a bug report about `git repack --drop-filtered` behavior in partial clones.

The author, kongfankaikai, describes a scenario where `git repack --drop-filtered` aborts entirely when it encounters a blob that is both eligible for dropping (due to the filter) *and* referenced by the current index. The current behavior is a fatal error, which prevents other eligible blobs from being dropped. The author proposes that Git should skip blobs referenced by the index and continue processing the remaining eligible objects, optionally warning about the skipped ones.

The report is well-motivated: this behavior would be particularly useful in partial clones with large working trees, where the goal is to drop as many filtered objects as possible without disrupting the current working state. The author asks whether there is a specific reason the condition is treated as fatal rather than recoverable.

No patch is provided; this is a pure bug report and feature request. The thread context (if any) is not included here, so this appears to be the root of the thread. The issue touches the repack machinery and partial clone support, both areas of active development driven by Patrick Steinhardt and Taylor Blau. The proposed change would affect the object-dropping logic in `builtin/repack.c` and likely require coordination with the index and object-filtering subsystems.

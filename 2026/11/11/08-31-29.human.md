This is the **v13 revision of Harald Nordgren’s six-patch series** introducing `remote.<name>.fetchRefmap` to solve a long-standing performance problem for shallow repositories. The series is **implementation-complete, under final review, and expected to graduate to `master` in the current cycle**—the only remaining hurdle is resolving the override semantics for command-line refspecs and colon-separated `remote.<name>.fetch` entries, which the thread has now converged toward handling with override semantics (replacing rather than coexisting with `fetchRefmap`).

The problem is concrete and widely felt: users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch` operations when the remote has many branches, because a refspec-less fetch negotiates history for *all* remote branches. The series implements a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched. The design is finalized and endorsed by Junio C Hamano and Phillip Wood, with the new `remote.<name>.fetchRefmap` config key cleanly separating the "what" (which refs to fetch) from the "where" (where to store them). The precedence rule is settled: `remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration (if neither is configured), and command-line refspecs override both config keys.

The v13 revision is **mechanically sound and thoroughly tested**, with 593 lines of new tests across `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh`, and `t/t5505-remote.sh`. It adds two key improvements: a **mechanical fix** for `@{push}` resolution when `fetchRefmap` is configured (falling back to `remote->refmap` in `remote.c`), and a **regression test** confirming the current dual-storage behavior for colon-separated `fetch` entries with explicit destinations. The latter is the last open edge case—whether such entries should override `fetchRefmap` entirely (Phillip Wood’s preference) or coexist with it (current behavior). The thread has converged toward override semantics, which would align with command-line precedent and avoid ambiguity, but the v13 test preserves the current behavior pending a v14 update.

The series also introduces the `--limited-fetch` flag for `git remote add`, which configures `remote.<name>.fetchRefmap` (e.g., `*@{upstream}`) instead of the traditional wildcard refspec, and makes this the default in shallow repositories. Both features are uncontroversial, well-tested, and ready for merging. The documentation updates clearly explain the precedence rules, backwards-compatibility considerations, and the minor inconvenience of forced-update placement (`+` on the refmap side), which requires users to split their configuration into two refspecs if they want to reject non-fast-forward updates for some branches while mapping all refs the same way.

This is a **well-crafted, high-impact feature** that addresses a real pain point for shallow-repository users. The implementation is clean, the test coverage is comprehensive, and the design has been vetted by the maintainer and key reviewers. The only remaining work is a v14 revision to finalize the override semantics, incorporate any last-minute review feedback, and polish the documentation. If you care about fetch performance in shallow repos or the future of refspec configuration, this is the time to review.

This is a **worktree safety and ref-filter enhancement** series (v5) that builds on the previous iteration to address feedback from Phillip Wood and others. The series now consists of five patches, with two key improvements: a performance fix for the `%(worktreepath)` atom and the addition of a new `%(currentworktree)` atom to simplify the logic in `git branch`.

The first patch remains unchanged in its core goal: it makes `git worktree remove` refuse to delete a worktree that is in the middle of a rebase, bisect, cherry-pick, revert, or `git am` operation unless `--force` is given. This is a **safety fix** that aligns with Git’s general principle of protecting uncommitted or in-progress work. The documentation has been updated to list the conditions requiring `--force` in a bulleted format, with each item now a complete sentence as requested by Phillip Wood. Ben Knoble’s preference for the original phrasing is noted, but the change is minor and unlikely to be controversial.

The second patch is unchanged: it adds a documentation warning to `git-for-each-ref(1)` about parsing `%(worktreepath)` safely, recommending the use of quoting options (e.g., `--shell`) or NUL-terminated output (`%00`) to handle worktree paths containing newlines. The warning also clarifies that only one worktree is shown for a branch checked out in multiple worktrees, which Junio C Hamano confirmed is correct (though the scenario is discouraged by Git’s porcelain).

The third patch is where the most significant improvement lies. In v4, the new `branch_checked_out_worktree()` helper iterated over all worktrees for every ref, resulting in O(N*M) complexity (where N is the number of refs and M is the number of worktrees). Phillip Wood identified this as a **critical performance regression** and suggested refactoring `branch.c` to use a hashmap for O(1) lookups. The v5 patch implements this suggestion by recording the branches in a map (`checked_out_worktrees`) during `prepare_checked_out_branches()`, restoring the original performance while avoiding code duplication. This is a clear win and addresses the most urgent open issue from v4.

The fourth patch is new: it adds `%(currentworktree)`, a ref-filter atom that returns the path of the current worktree if the ref is checked out there (or being rebased/bisected), and an empty string otherwise. This atom is implemented using a second map (`current_worktree_branches`) in `branch.c`, populated during `prepare_checked_out_branches()`. The lookup is O(1), and the atom is designed to be used with `%(if)` to treat the current worktree differently from others. This directly addresses Phillip Wood’s architectural suggestion from v4, which proposed using a similar atom to simplify the logic in `git branch`. The implementation is clean and well-motivated, and the tests verify its behavior in both the main and linked worktrees.

The fifth patch replaces v4’s fourth patch and uses `%(currentworktree)` to simplify the logic in `git branch`. Instead of building a second format string (`here_format`) and conditionally applying it, the default format now uses `%(currentworktree)` to omit the `+` marker and worktree path for branches being rebased or bisected in the current worktree. This reduces the complexity of `print_ref_list()` and makes the behavior more composable for users who customize `--format` strings. The patch is concise and leverages the new atom effectively.

The series is **backward-incompatible** for scripts relying on the current empty `%(worktreepath)` value for rebasing/bisecting branches, the `+` marker in `git branch` output, or the ability to delete in-progress worktrees without `--force`. The commit messages explicitly ask whether any such scripts exist, signaling awareness of the compatibility risk. The implementation is well-tested, with new tests covering the performance-critical `%(worktreepath)` lookup, the `%(currentworktree)` atom, and the updated `git branch` output. The performance regression in v4 is now resolved, and the architectural suggestion from Phillip Wood has been adopted, making this a stronger series than v4.

Key files touched include `builtin/worktree.c`, `ref-filter.c`, `branch.c`, and their respective documentation and test files. The series looks like a well-crafted fix for a real problem, with clear attention to performance, safety, and maintainability. The new `%(currentworktree)` atom is a useful addition that could see broader use in the future.

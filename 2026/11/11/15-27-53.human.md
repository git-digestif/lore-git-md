This is the fourth patch in Harald Nordgren’s v6 series implementing `git branch --delete-integrated`, which detects branches whose changes were squash-merged or rebased into an upstream branch—even when the upstream modified the same files. The patch itself is now technically complete, with Junio’s latent correctness issue (`.gitattributes` support) fixed in v6. Jasper Mayone’s review here focuses on performance and edge-case correctness.

Jasper identifies a performance inefficiency in the `merge_keeps_upstream()` helper: it calls `repo_read_index(the_repository)` for every changed file at every candidate commit, which triggers redundant `clear_skip_worktree_from_present_files()` calls in sparse checkouts. He suggests reading the index once, before the walk in `find_landed_commits()`, to avoid repeated lstat() calls. This is a targeted optimization, not a correctness issue, and the fix would be straightforward.

He also clarifies a design choice: the patch uses the *current worktree’s* index for `.gitattributes`, not the upstream commit’s. This means merge drivers set only upstream are ignored, and bare repositories (with empty indexes) get no attribute-driven merge behavior. Jasper notes this is a reasonable trade-off but should be documented in the commit message. The patch currently omits this detail.

On testing, Jasper confirms the new logic works as intended—keeping branches when the merge doesn’t leave upstream unchanged—but notes the existing tests only verify deletions. He proposes adding test cases for the inverse: scenarios where the branch *shouldn’t* be deleted (e.g., upstream changes unrelated lines, partial hunks, or conflicting merges). These would protect against regressions in the core safety invariant: never deleting work that didn’t actually land. He offers to contribute the tests if helpful.

The patch remains uncontroversial and ready for integration, pending Junio’s sign-off. The feedback here is about polish, not design: a minor performance tweak, clearer documentation, and expanded test coverage. None of this blocks merging, but addressing it would strengthen the patch. The series as a whole still awaits the author-check mitigation (Jasper’s proposal) to handle false positives in forge workflows, but that’s a separate concern.

This is the v13 revision of Harald Nordgren’s six-patch series introducing `remote.<name>.fetchRefmap` to implement a "matching-inspired" fetch mode for shallow repositories. The series is now implementation-complete and under final review for merging to `master`, with all major design questions resolved. The author is requesting a final round of reviews before the series graduates.

The core goal is to address a long-standing performance issue in shallow repositories: a refspec-less `git fetch` negotiates history for *all* remote branches, which can be slow or hang when the remote has many branches. The v13 series solves this by dynamically fetching only the branches tracked by local branches at the remote, using the new `remote.<name>.fetchRefmap` config key to decouple "what to fetch" from "where to store it." The design is finalized and endorsed by Junio C Hamano and Phillip Wood, including the placement of forced updates (`+`) on the refmap side and the precedence rule (`remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration).

The v13 revision adds two key improvements. First, it fixes `@{push}` resolution when `remote.<name>.fetchRefmap` is configured by falling back to `remote->refmap` in `remote.c`, ensuring `@{push}` works correctly without altering core behavior. Second, it adds a regression test confirming that colon-separated `remote.<name>.fetch` entries with explicit destinations are stored in both the explicit destination and the refmap’s, preserving backwards compatibility while the override semantics discussion converges. The test suite now covers all critical edge cases, including forced updates, precedence rules, and dynamic branch enumeration.

The only remaining open question is the **override semantics for command-line refspecs and colon-separated `remote.<name>.fetch` entries**. The thread has converged toward override semantics (Phillip Wood’s preference), where such refspecs replace rather than coexist with `fetchRefmap`. The v13 test case confirms the current dual-storage behavior, but this is expected to be updated in v14 to match the chosen model. The series is otherwise ready for graduation, with no known blockers or unresolved technical concerns.

The implementation touches `remote.c`, `builtin/fetch.c`, `builtin/remote.c`, and documentation, introducing the new `remote.<name>.fetchRefmap` config key, the `--limited-fetch` flag for `git remote add`, and a shallow-repository default for the flag.

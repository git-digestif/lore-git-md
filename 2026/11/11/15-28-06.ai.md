This is the first patch in Jasper Mayone’s **v5 worktree safety and ref-filter enhancement series**. It is a **bugfix** that closes a real safety hole: `git worktree remove` currently allows deletion of worktrees in the middle of a rebase, `git am`, bisect, cherry-pick, or revert operation—even when the files appear clean—because the operation’s state lives in the worktree’s own `$GIT_DIR`. Losing that state can mean losing hours of work, especially in complex conflict resolutions or multi-step operations like a rebase stopped at an "edit" or "break" line.

The patch updates `git worktree remove` to treat such worktrees as unclean, refusing to delete them unless `--force` is given. The check is implemented in a new helper, `check_no_operation_in_progress()`, which uses `wt_status_check_rebase()`, `wt_status_check_bisect()`, and direct checks for `CHERRY_PICK_HEAD`, `REVERT_HEAD`, and the `sequencer` directory. The helper is called only when the worktree directory exists, preserving the existing behavior for already-gone worktrees. The documentation is updated to list the new refusal conditions in a bulleted format, with each item a complete sentence as requested by Phillip Wood; Ben Knoble’s preference for the original phrasing is noted but the change is minor and unlikely to be controversial.

The patch touches `builtin/worktree.c`, `Documentation/git-worktree.adoc`, and adds comprehensive tests in `t/t2403-worktree-move.sh`. The tests cover all five operations (rebase, `git am`, bisect, cherry-pick, revert) and both single-commit and multi-commit sequences, verifying that the refusal message names the correct operation and that `--force` still allows deletion. The implementation is clean, well-motivated, and directly addresses the safety concern raised by Ben Knoble in the original thread. It looks ready for integration.

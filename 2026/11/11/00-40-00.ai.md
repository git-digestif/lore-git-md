This is a **performance bugfix series** targeting `git log --follow` for non-linear history (merges), now at **v5** (5 patches). The series addresses correctness regressions and a severe performance slowdown introduced by commit `304812ed33` (June 2026), which made `--follow` nearly 14x slower for merges in large repositories like `linux.git`.

The latest iteration (v5) squashes the previous 6/6 fix into the main optimization patch (now 5/5), simplifying the logic to first identify a parent where the tracked path is unchanged before diffing other parents. This preserves correctness for file copies and unrelated histories (e.g., subtree merges) while maintaining the speedup—reducing runtime from ~336s (regression) to ~39s, though still ~1.6x slower than the pre-regression baseline (~23s). Tests in `t4219` now cover these edge cases, including Patrick Steinhardt’s copy-source regression test.

Justin Tobler’s benchmark confirms the series mitigates the regression but highlights that `--follow` remains significantly slower than before `304812ed33`. He suggests the feature might be better as opt-in (via a new flag) rather than default behavior, given the performance trade-off. His proposal to revert `304812ed33` and restart the effort could simplify validation but risks reintroducing the original correctness bugs (e.g., lost history in `-m --follow`).

The series touches `log-tree.c` and the test suite, with no on-disk format changes. Key functions like `follow_needs_renames()` and `follow_parent_changed_dropped_file()` now handle copies and unrelated histories, addressing Patrick’s earlier concerns. The optimization’s core idea—limiting rename detection to files deleted by the merge—remains intact, but the performance gap suggests further tuning may be needed.

This is a **substantive, well-tested series** with clear real-world impact, but the lingering performance regression and Justin’s opt-in proposal could spark debate about the cost/benefit of `--follow`’s default behavior. The thread is now at a crossroads: refine the optimization further, accept the trade-off, or reconsider the feature’s scope.

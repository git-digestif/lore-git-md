This is a bug report about `git repack --drop-filtered` in partial clones.

The author, kongfankaikai, describes a scenario where `git repack --drop-filtered` aborts entirely if any blob selected for dropping is referenced by the current index. The error message is `fatal: cannot drop 'path/to/large-file.bin' (object-id): it is referenced by the current index`. The problem is that this stops the entire repack operation, even for other eligible blobs that are *not* referenced by the index.

The expected behavior, as suggested, is that Git should skip blobs referenced by the index and continue dropping the rest, optionally warning about the skipped blobs. This would allow the repack to complete successfully while still respecting the index's references. The author asks whether there is a specific reason this condition is treated as fatal rather than non-fatal, noting that this behavior would be particularly useful for partial clones with large working trees.

The report is clear and well-motivated, focusing on a real-world use case (partial clones) where the current behavior is unnecessarily restrictive. No patch is provided, so this is currently a discussion starter rather than a fix. If the maintainers agree with the suggestion, it would likely require a small change to the repack logic to handle index-referenced blobs gracefully. The issue looks legitimate and worth attention from anyone working on partial clone or repack improvements.

Subject: `git repack --drop-filtered` aborts on blobs referenced by index
Series version: none (bug report / feature request)
Originating author: kongfankaikai
Thread type: bug report

Core problem or goal
`git repack --drop-filtered` currently treats encountering a blob that is both eligible for dropping (due to the filter) and referenced by the current index as a fatal error, aborting the entire operation. The goal is to change this behavior so that such blobs are skipped (with an optional warning) and the repack continues, allowing other eligible objects to be dropped. This would improve usability in partial clones with large working trees.

Current status
Under discussion; no patch yet. The report asks whether there is a specific reason the condition is fatal rather than recoverable.

Key technical details
- Subsystems touched: repack machinery (`builtin/repack.c`), object-filtering, index handling
- New behavior: skip blobs referenced by the index instead of aborting
- On-disk format: no changes
- Test coverage: not yet addressed

Open questions and loose ends
- Why is the current behavior fatal? (Is there a correctness or safety reason?)
- Should skipped blobs trigger a warning?
- How should the index be checked for references? (Is the current index sufficient, or should other states like the working tree be considered?)
- Are there edge cases where skipping could lead to corruption or data loss?

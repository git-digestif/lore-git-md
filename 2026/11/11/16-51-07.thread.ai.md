Subject: `git repack --drop-filtered` aborts on blobs referenced by index
Series version: none (bug report / feature request, now acknowledged with patch in progress)
Originating author: kongfankaikai
Thread type: bug report

Core problem or goal
`git repack --drop-filtered` currently aborts when it encounters a blob that is both eligible for dropping (due to the filter) and referenced by the current index. The goal is to change this behavior so that such blobs are skipped (with an optional warning) and the repack continues, allowing other eligible objects to be dropped. This change is motivated by usability in partial clones with large working trees, where the current behavior unnecessarily blocks repacking of other objects.

Current status
Acknowledged as a valid issue; a fix is in progress. The current fatal error is confirmed to be a conservative design choice rather than a correctness requirement. The planned solution will skip blobs referenced by the index while dropping the remaining eligible objects. Patch expected soon.

Key technical details
- Subsystems touched: repack machinery (`builtin/repack.c`), object-filtering, index handling
- New behavior: skip blobs referenced by the index (with warning) instead of aborting; continue processing other eligible objects
- On-disk format: no changes
- Test coverage: not yet addressed
- Rationale for current behavior: prevents dropping blobs that would immediately be lazy-fetched again, but unnecessarily blocks other eligible objects
- Related prior report: Samuel Bronson reported the same limitation in September

Open questions and loose ends

- How should the index be checked for references? (Current index is sufficient for the fix, but broader considerations like working tree state may be relevant for future work)
- Are there edge cases where skipping could lead to corruption or data loss? (No known issues, but thorough testing will be needed)

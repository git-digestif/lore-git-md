This is a review-reply in an ongoing bugfix thread, where Adrian Ratiu confirms and agrees to implement a control-flow fix suggested by Junio C Hamano for `[PATCH 3/3]` of his three-patch series on submodule linked-worktree crashes.

Junio had identified an edge case in `submodule_move_head()` where a linked-worktree submodule containing a nested submodule with a directory-based `.git` would cause `submodule_uses_gitfile()` to return false recursively, triggering `absorb_git_dir_into_superproject()` while leaving `is_worktree` unset. Adrian reproduced this exact scenario and confirmed the breakage: a recursive checkout absorbs the nested submodule and then rewrites the parent submodule's `.git` file to point at a nonexistent path, producing `fatal: gitfile does not point to a valid repository`. He acknowledges this is the same class of bug the series aims to fix, just reached through the absorb path.

Both agree on the remedy: restructure the code so that after ensuring `path/.git` is a gitfile -- whether it already was one or was just created by absorption -- the validation via `validate_submodule_gitfile_dir()` runs unconditionally and sets `is_worktree` before the forced-move check. Adrian verified that this leaves the linked worktree's `.git` untouched and checks out the correct commit, and notes that post-absorb validation always passes because `absorb_git_dir_into_superproject()` places the git dir where `submodule_name_to_gitdir()` expects it.

The thread remains under review with a v2 forthcoming that will incorporate this restructuring along with the previously agreed changes to patches 1 and 2.

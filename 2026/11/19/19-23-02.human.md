This is a small, focused bugfix for the attributes subsystem, closing a gap left by an earlier security hardening.

Commit 2ef579e261 from 2021 made Git refuse to follow symlinks when reading in-tree `.gitattributes` files, ensuring that worktree lookups behave like index lookups and cannot escape the repository. However, that protection only applied to the final `.gitattributes` component itself. When a path like `symdir/file` is passed to `git check-attr` and `symdir` is a symlink to a directory outside the tree, Git still happily traversed the link to read `symdir/.gitattributes` and to `lstat()` the target file for object-mode checks.

Dominik Maier's patch adds a `has_symlink_leading_path()` guard in two places: before opening a file with `READ_ATTR_NOFOLLOW` in `read_attr_from_file()`, and before calling `lstat()` in `builtin_object_mode_attr()`. Both now bail out early if any leading directory component is a symlink, matching the no-follow semantics that were already intended.

The change is tight -- ten lines in `attr.c` plus a regression test in `t/t0003-attributes.sh` that creates an external directory, symlinks to it, and verifies the attribute is treated as unspecified. It looks like a straightforward, well-motivated consistency fix that deserves attention.

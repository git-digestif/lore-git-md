This is the fifth and final patch of a five-patch feature series that changes the default behavior of Git's HTTP retry logic. Patch 5/5 by Ravi Mistry flips the default value of `http.retryAfter` from 0 to 10 seconds, so that when `http.maxRetries` is enabled and a server returns a retryable status (429 by default, or codes listed in `http.retryStatusCodes`) without a `Retry-After` header, Git now waits 10 seconds before the first retry and doubles on each subsequent attempt (10s, 20s, 40s, capped at `http.maxRetryTime`) instead of retrying immediately in a tight loop.

To preserve the ability to retry immediately when a server explicitly sends `Retry-After: 0` or a past HTTP-date, the patch adds a new helper `has_zero_or_past_retry_after()` in `http.c` that inspects the raw `Retry-After` response header via `curl_easy_header()` whenever `CURLINFO_RETRY_AFTER` returns zero or negative. This header inspection is guarded by a new `GIT_CURL_HAVE_CURL_EASY_HEADER` macro in `git-curl-compat.h` that is defined for libcurl >= 7.84.0 (where `curl_easy_header()` became available by default). When the raw header indicates zero or a past date, `finish_active_slot()` now sets `slot->results->retry_after = 0`, allowing an immediate retry rather than falling back to the new 10-second default. The patch also drops the word "configured" from the error message emitted when `http.retryAfter` exceeds `http.maxRetryTime`, since the value may now be the default rather than explicitly set.

Tests in `t/t5584-http-429-retry.sh` are updated to explicitly set `http.retryAfter 0` where immediate retries are needed, and new tests verify that the default is 10 seconds (by setting `http.maxRetryTime 9` and confirming the fail-fast error mentions 10 > 9) and that `Retry-After: 0` still triggers immediate retry under libcurl >= 7.84.0. The documentation in `Documentation/config/http.adoc` is updated to describe the new default and the libcurl version requirements for header inspection. This patch retains the two-phase structure that Junio C Hamano previously questioned: patches 1-4 assume `http.retryAfter=0` while this final patch changes the default to 10, leaving the procedural concern about default introduction open.

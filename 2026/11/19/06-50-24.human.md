This is a follow-up ping on a bugfix series addressing object-size truncation on 32-bit platforms. Elia Pinto is nudging the list for movement on the four-patch series that converts object-parsing and verification functions from `unsigned long` to `size_t` for in-memory buffers, fixing cases where objects larger than 4 GiB were silently misprocessed on Windows and other LLP64 systems.

The series has not yet received code-level review; the only substantive feedback so far was Simon Richter's concern that `size_t` remains 32 bits on these platforms for on-disk sizes, which Elia has clarified is handled by a separate follow-up using `off_t`. The patches still apply cleanly to current master and merge without conflict against `seen`, so there is no technical blocker from rebase or integration issues.

A concrete dependency has now emerged: a separate pack-receive series relies on this work, since `git unpack-objects` needs to pass sizes to `parse_object_buffer()` without a cast, and `git fsck` cannot reach its verify callbacks for 4 GiB-plus objects until `check_object_signature()` stops reporting them as corrupt. This gives the series practical urgency beyond the theoretical correctness fix.

Elia is explicitly asking whether reviewers want the `EXPENSIVE` tests guarded by `!LONG_IS_64BIT` that the cover letter offered, or whether the series can proceed without them. Given that reproducing the bug requires multi-gigabyte objects in memory, the absence of tests is understandable, but the question is now squarely on the table for anyone picking up the thread.

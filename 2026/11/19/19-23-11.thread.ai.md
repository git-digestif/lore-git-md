Thread identity: two-patch bugfix series v2 authored by Dominik Maier <dmnk@google.com>, evolving from an earlier standalone single-patch proposal after review by René Scharfe. The series targets the archive subsystem.

Core problem: two related defects in `git archive` argument handling and ZIP output. First, with `--remote`, `--add-file` and `--add-virtual-file` were processed during option parsing, including filesystem `stat()` calls, before the incompatibility check ran; a nonexistent file could therefore produce a confusing "File not found" error instead of "options '--add-file' and '--remote' cannot be used together", and `--no-add-file` after `--add-file` could suppress the check. Second, `write_zip_entry()` in `archive-zip.c` could advance a pointer out of bounds when `--prefix` was longer than the path of an extra or virtual file; the root cause is that `write_zip_entry()` unconditionally computed `path_without_prefix = path + args->baselen` before calling `entry_is_binary()`, which is correct for tracked tree entries but wrong for extra files (which use per-entry `info->base`) and virtual files (which carry no prefix), causing the pointer to step past the end of the path buffer and causing `entry_is_binary()` to look up gitattributes along an arbitrary virtual path.

Current status: v2 is proposed and under review; no merge or integration status is stated. It supersedes the single-patch v1 approach.

Key technical details: patch 1/2 fixes the out-of-bounds pointer advance in `write_zip_entry()` in `archive-zip.c` for extra files and virtual files whose paths are shorter than `--prefix`. In `write_archive_entries()` (`archive.c`) the code updates `args->base` and `args->baselen` to each `--add-file` entry's recorded prefix before calling `write_entry()`, and sets `args->base = NULL` with `baselen = 0` for `--add-virtual-file` entries; in `archive-zip.c`, `write_zip_entry()` now guards the pointer arithmetic with `args->base ? path + args->baselen : NULL`, and `entry_is_binary()` skips the path-based `userdiff_find_by_path()` lookup when `path` is NULL, falling back to content inspection. Patch 2/2 implements René Scharfe's deferred-validation alternative: `add_file_cb()` in `archive.c` no longer calls `stat()` during `parse_options()` but merely records the path with `info->content = NULL` and a zeroed `struct stat`; after `parse_options()` completes, `parse_archive_args()` iterates `args->extra_files`, skips entries with non-NULL `content` (virtual files), dies with the `--remote` incompatibility error when `is_remote` is set and `content == NULL`, and only then performs `stat()` and the `S_ISREG` check. This preserves `--no-add-file` canceling an earlier `--add-file` even with `--remote`, prevents filesystem access on the server for `--add-file`, and allows `--remote --add-virtual-file`. Junio C Hamano validated that keeping `prefix_filename()` inside `add_file_cb()` during `parse_options()` preserves relative-path resolution when running from a subdirectory, because `setup_git_directory()` is only invoked later in `write_archive()` after `parse_archive_args()` returns, so the working directory remains unchanged between the callback and the deferred validation loop. He also confirmed that entries added by `--add-virtual-file` always carry non-NULL `content` from `xstrdup()`, so the new loop correctly skips them. Tests in `t/t5000-tar-tree.sh` cover `--remote --add-file` failing with the incompatibility message, `--no-add-file` canceling `--add-file` locally and remotely, and `--remote --add-virtual-file` succeeding; `t/t5003-archive-zip.sh` covers the zip prefix fix including `--format=zip --prefix=very-long-archive-prefix/ --add-virtual-file=a:hello` against the empty tree. Files touched are `archive.c`, `archive-zip.c`, `t/t5000-tar-tree.sh`, and `t/t5003-archive-zip.sh`; relevant to server-side handling in `git-upload-archive`.

Open questions and loose ends: René Scharfe's v1 feedback has been incorporated in v2, including the deferred-stat design and support for `--no-add-file` cancellation. Junio C Hamano reviewed both patches substantively: for patch 1/2 he concluded "Overall, nicely done", with minor non-blocking observations (commit message wording about "worktree gitattributes" vs plain "gitattributes" since `parse_treeish_arg()` defaults to `GIT_ATTR_INDEX`, the NULL check in `entry_is_binary()` being functionally redundant with `userdiff_find_by_path()`'s own NULL handling though it avoids one-time `attr_check` initialization, and the suggestion to save/restore `args->base`/`args->baselen` around the loop in `write_archive_entries()` to avoid leaving stale values); for patch 2/2 he concluded "Looking good", confirming the implementation cleanly follows the deferred-validation approach and resolves all three targeted issues without touching the server filesystem when unnecessary.

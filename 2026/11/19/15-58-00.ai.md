This is the second patch in a five-patch v4 series implementing HTTP transport retry improvements, specifically adding exponential backoff when servers respond with 429 but omit the Retry-After header. The patch modifies `handle_rate_limit_retry()` in `http.c` to accept a new `size_t attempt` parameter representing the 1-based retry count, and when no server-provided delay is present it computes the wait as `http.retryAfter * 2^(attempt - 1)`, doubling the configured initial delay on each successive retry while clamping the result at `http.maxRetryTime` to avoid overflow. An explicit Retry-After header continues to take precedence over the computed backoff, and the existing fail-fast behavior when the configured `http.retryAfter` exceeds `http.maxRetryTime` is preserved for the initial attempt.

The implementation touches `http.c` (the backoff calculation loop inside `handle_rate_limit_retry()` and the call site in `http_request_recoverable()` which now passes `(size_t)(http_max_retries - rate_limit_retries)` as the attempt counter), `Documentation/config/http.adoc` (updating `http.retryAfter` to describe it as an initial delay that doubles per attempt, and clarifying that `http.maxRetryTime` caps backoff delays rather than causing immediate failure for them), and `t/t5584-http-429-retry.sh` which gains three tests verifying the doubling sequence (1s, 2s, 4s), clamping at `http.maxRetryTime`, and that server headers still override the computed backoff. Note that within this patch the default `http.retryAfter` remains 0 (immediate retry); patch 5/5 of the series separately changes that default to 10 seconds.

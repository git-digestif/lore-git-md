This is a substantive review reply in the ongoing design debate over Ravi Mistry's `[PATCH v3 3/5]`, which introduces the `http.retryStatusCodes` config option as part of a five-patch series improving Git's HTTP retry handling.

Patrick Steinhardt acknowledges Ravi Mistry's distinction between 429 (deliberate rate limiting) and 5xx codes (transient reverse-proxy timeouts, CDN failures, or temporary server overload), but he remains unhappy with the design that shifts the burden to users to configure which codes are retryable. Rather than accepting a world where administrators must opt in to retrying 502/503/504, Patrick argues that Git should use its leverage to nudge the ecosystem toward standardization.

His concrete proposal is to document that service providers are expected to return 429 when overloaded, and that any other behavior in that situation should be considered buggy. The `http.retryStatusCodes` config should then explicitly frame non-429 retries as a workaround for buggy providers, intended to pressure them into fixing their infrastructure so that the workaround eventually becomes unnecessary.

This exchange leaves the architectural question open: whether Git should offer configurability for transient 5xx failures or instead hardcode retries to 429 only and force convergence on that standard. The debate centers on whether resilience against misconfigured or overloaded proxies is a feature worth having, or a crutch that delays ecosystem-wide alignment. No resolution is reached in this email; the decision awaits Junio C Hamano's final call on the series.

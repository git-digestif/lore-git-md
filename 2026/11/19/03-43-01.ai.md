This is a bugfix for `git ls-tree` in version 2 of a standalone single-patch series. The patch corrects the `%(path)` placeholder in `--format` output so that it is emitted verbatim (null-terminated, unquoted) when `-z` is passed, instead of always applying C-style quoting via `quote_c_style()`. This aligns `ls-tree` with its own documentation and with the existing behavior of `git ls-files --format`, which has handled `-z` correctly since commit ce74de931d. The code change is confined to `show_tree_fmt()` in `builtin/ls-tree.c`, branching on `options->null_termination` to choose between `strbuf_addstr()` for the raw path and the existing quoting call.

The v2 revision specifically addresses feedback from the v1 discussion by reworking the regression test in `t/t3104-ls-tree-format.sh`. Instead of relying on a non-ASCII filename (Hebrew characters) written to the filesystem, the test now synthesizes a tree entry containing a double quote using `git mktree`, keeps everything within US-ASCII, and forces `core.quotePath=true` to ensure the quoting path would otherwise be triggered. This makes the test self-contained and platform-independent while still proving that `-z` suppresses quoting.

The underlying issue stems from commit 455923e0a1, which introduced `--format` for `ls-tree` in 2022 without accounting for `-z` in the `%(path)` handling. Junio C Hamano had already reviewed v1 and called the code change "trivially correct", so the fix itself appears settled; the main open question from the earlier thread -- whether to avoid non-US-ASCII bytes in tests -- is resolved here by the `mktree` approach. No branch assignment has been stated yet, but with maintainer approval on the logic and a clean test, this looks ready for integration.

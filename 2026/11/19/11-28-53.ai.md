This is a substantive review reply in the ongoing design debate over `[PATCH v3 3/5]` of Ravi Mistry's five-patch HTTP retry series, specifically concerning the new `http.retryStatusCodes` configuration key. Patrick Steinhardt acknowledges Ravi Mistry's semantic distinction between 429 (deliberate rate limiting) and 5xx codes (transient proxy or CDN failures), but maintains that Git should not make retry behavior for non-429 codes the user's problem. Instead, he proposes that the documentation explicitly state that service providers are expected to return 429 when overloaded, and that any other behavior in that scenario should be considered buggy provider behavior. He suggests the config option be documented as a workaround for such buggy providers, using documentation to nudge the ecosystem toward standardization on 429 rather than accommodating non-standard codes silently.

The exchange leaves the architectural question open: whether Git should offer configurability for arbitrary retry codes at all, or force convergence on 429 by treating other codes as provider bugs. No resolution is reached in this email. For future thread summarization, note that patch v3 3/5 touches `http.c`, `remote-curl.c`, and `Documentation/config/http.adoc`, introducing both the `http.retryStatusCodes` config key (default `"429"`) and a corresponding `GIT_HTTP_RETRY_STATUS_CODES` environment variable. The broader series context includes exponential backoff via `http.retryAfter` (default 10 seconds), POST request retries restricted to read-only services, and an off-by-one fix in the original 429 retry loop from commit 640657ffd0.

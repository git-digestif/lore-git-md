This is a substantive response to a feature request, proposing an alternative mechanism that uses existing Git configuration rather than extending `.gitignore` syntax. Hsieh Chin Fan points out that `.gitignore` is itself a tracked file, so any branch-conditional rules embedded in it would propagate through merges (e.g., merging `feature` into `main` would carry the branch-specific rules along), making the behavior hard to reason about across branches.

Instead, the reply demonstrates how to achieve the desired branch-aware exclusion using `includeIf "onbranch:..."` directives in `.git/config` to conditionally load a branch-specific config file, which in turn sets `core.excludesFile` to a dedicated ignore file (e.g., `.git/feature.ignore` containing `settings.py`). The example shows that `git status` on `main` reports `settings.py` as untracked, while on `feature/x` it is ignored, exactly matching the whitelist/blacklist behavior Jordan Kadish requested but without modifying the ignore engine or tracking rules in the repository.

Key technical details for future reference: the mechanism relies on the existing `includeIf` conditional-include feature (specifically the `onbranch:` condition) combined with `core.excludesFile`, keeping branch-specific ignore patterns entirely local to `.git/config` and untracked files rather than in the shared `.gitignore`. This sidesteps the merge-propagation problem and avoids performance or parsing concerns about evaluating branch names during ignore-pattern matching, since the branch check happens once at config-load time rather than per-file.

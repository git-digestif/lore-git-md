This is a review reply in the ongoing discussion of patch 4/4 from Elia Pinto's `[PATCH v2 0/4]` series, which addresses 32-bit `unsigned long` truncation for objects >=4 GiB. Elia is answering Patrick Steinhardt's question about whether `git fsck` silently validates only a truncated prefix of large objects or detects the problem.

Elia corrects the record: on current master the verify callback is not even reached for such objects. Before the callback runs, `verify_packfile()` calls `check_object_signature()`, which also accepts `unsigned long`, hashes only the prefix, and fails the hash comparison -- so `fsck` reports the object as corrupt even when it is fine. The complaint happens, but for the wrong reason, which means the original commit message was inaccurate in claiming the callbacks inspect a prefix today.

The full fix requires the separate "use size_t when parsing and checking objects" series to convert `check_object_signature()`, `parse_object_buffer()`, and `fsck_object()` first; only then does the callback receive the true size and need patch 4/4 to pass it through correctly. Elia therefore confirms that 4/4 belongs on top of that dependent series and will be resent there with a corrected commit message.

One exception is noted: blobs are not affected by this particular gap because `core.bigFileThreshold` is itself below 4 GiB on these platforms, so any blob that large is verified via `stream_object_signature()` and reaches the callback without its data being truncated.

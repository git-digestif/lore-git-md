This is a bugfix patch, specifically the first of four in Elia Pinto's v3 series fixing silent integer truncation when Git handles files larger than 4 GiB. The patch targets `hashwrite()`, which takes its byte count as a `uint32_t`, meaning any buffer larger than 4 GiB gets silently truncated to `count mod 2^32` while the object header records the full size, producing packs that `git fsck` rejects as corrupt.

Rather than widening `hashwrite()`'s signature -- which would force updates to the Rust FFI bindings in `src/csum_file.rs` -- the patch modifies the three callers that can pass oversized buffers: `write_no_reuse_object()` and `copy_pack_data()` in `builtin/pack-objects.c`, and `store_object()` in `builtin/fast-import.c`. Each now loops, feeding `hashwrite()` in chunks of at most `UINT32_MAX` bytes. This addresses the design preference voiced by Junio C Hamano and brian m. carlund in earlier review rounds.

The commit message notes that the bug is reproducible by simulating a 16-bit truncation in `hashwrite()` with a 100KB blob, and confirms the fix eliminates the `fsck` failure. No test is included because exercising the actual bug requires creating an object of 4 GiB or more, which is impractical for the test suite. The patch touches only the two builtin files and carries `Helped-by` trailers from the two reviewers whose approach it adopts.

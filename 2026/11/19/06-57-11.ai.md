This is a follow-up ping on the two-patch bugfix series fixing 4GiB+ file truncation on 32-bit `long` platforms, raising a dependency question about the second patch. The author notes the series still applies cleanly to current `master` (e1ec09b23c) and merges cleanly with `seen`, but has received no review comments yet. Patch 1/2 (the `git archive` tar/zip fixes in `archive-tar.c`, `archive-zip.c`, and `archive.h`) stands alone, while patch 2/2 (the `git apply` fix in `apply.c`) has a remaining gap the author should have flagged earlier.

The new issue concerns `git apply --index` and `git am`: although patch 2/2 fixes the working-tree file written by `create_file`/`try_create_file`, the blob added to the index via `add_index_file()` still passes its size to `odb_write_object()`, whose length parameter remains `unsigned long` until a separate series ("use size_t for a few more object and buffer sizes") lands. On platforms where `long` is 32-bit but `size_t` is 64-bit, the indexed blob would still be silently truncated even though the working-tree file is now complete.

The author proposes two ways forward: either cast the size through `cast_size_t_to_ulong()` in `add_index_file()` so the command dies loudly instead of truncating (matching the approach in patch 5/5 of the loose-object series), then drop the cast once the `size_t` series merges; or hold back patch 2/2 entirely until that `odb_write_object()` series lands, as Patrick Steinhardt suggested for a similar case in the pack-receive series. No preference is expressed, and no maintainer response is recorded yet.

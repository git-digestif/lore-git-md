This is a bugfix targeting the protocol v2 handshake in `connect.c`. Dominik Maier identifies a state-leak bug where the file-static `server_capabilities_v2` vector accumulates capability lines across multiple in-process connections without being reset. Because `server_supports_feature()` and `server_feature_v2()` return the first matching entry, capabilities advertised by an earlier remote bleed into later handshakes -- even v0/v1 connections that skip v2 capability processing entirely. The patch clears the vector at the start of both `discover_version()` and `process_capabilities_v2()` to ensure each handshake starts with a clean slate.

The commit message gives two concrete symptoms: running `git remote show r1 r2` where `r1` uses SHA-256 and `r2` uses SHA-1 causes the second connection to inherit the stale `object-format=sha256` capability and fail with "mismatched object format", and a stale `session-id` from `r1` gets logged for `r2` even when `r2` disables `transfer.advertiseSID`. These are real correctness issues in multi-remote operations within a single process.

The fix itself is minimal -- two `strvec_clear()` calls -- and includes a regression test in `t/t5702-protocol-v2.sh` that spins up two local repos with different object formats and verifies via trace2 that the second remote does not inherit the first's session-id. The patch looks well-crafted: the commit message explains the mechanism clearly, the reproduction scenario is specific, and the test coverage directly exercises the reported failure mode.

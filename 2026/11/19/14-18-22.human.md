This is the third and final patch of a three-patch bugfix series targeting the `compatObjectFormat` interoperability layer, which converts objects between SHA-1 and SHA-256 repositories. Patch 3/3 fixes an inconsistency in how `object-file-convert.c` handles unknown commit headers: when a new commit is written via `convert_commit_extra_headers()` (as `git commit` does), unknown headers like Jujutsu's "change-id" are copied unchanged, but when an existing commit is converted via `convert_commit_object()` (as `git hash-object -w` does), those same headers cause a hard failure. This divergence means `git commit --amend` can record a compat object ID that cannot be read back, while `git hash-object` refuses the commit entirely.

The patch makes `convert_commit_object()` copy unknown headers and their continuation lines verbatim, matching the behavior of `convert_commit_extra_headers()`, so both paths produce the same compat object. It also tightens the matching for `"tree "`, `"parent "`, and `"mergetag "` headers from `<` to `<=` in the length checks, so a malformed line such as `"mergetag "` with nothing after the space is still recognized as that specific header and rejected (rather than being copied with an unconverted object ID embedded in it). The separate cases for `author`, `committer`, `encoding`, and `gpgsig` are removed since they now fall through to the generic copy path. Tests in `t/t1016-compatObjectFormat.sh` cover creating and amending commits with unknown headers, and verifying that an empty `mergetag` line is still rejected.

This patch is the most likely point of contention in the series because it removes a deliberate safety check added in commit 08a45903cb (2023), which rejected all unknown headers during conversion to prevent embedding unconverted object IDs. The author argues that rejecting unknown headers breaks interoperability with tools like Jujutsu that write custom headers, and that consistency between the two conversion paths matters more than the theoretical risk of an unknown header containing an unconverted OID. He explicitly welcomes review from Eric Sunshine or brian m. carlson on this trade-off, and notes that stricter validation of header format might belong in `fsck` rather than the converter.

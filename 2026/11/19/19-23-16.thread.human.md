Dominik Maier has sent a security bugfix for `git filter-branch` addressing a path-traversal vulnerability in the `--state-branch` resume logic. When `git filter-branch` loads the `filter.map` blob from a state branch, it previously wrote map entries to `../map/$from_commit` without validating the commit identifiers, so a malicious or corrupted state branch could escape the temporary map directory using entries containing slashes, backslashes, or `..` segments.

The patch hardens `git-filter-branch.sh` by reading lines with `IFS= read -r` and validating both sides of each `from:to` mapping before any file is written: the `from_commit` must be non-empty lowercase hexadecimal, and the `to_commit` may contain only lowercase hex digits and spaces (an empty value is allowed to represent pruned commits). Any violation causes the command to die with "Unable to load state from $state_branch:filter.map" rather than writing outside the intended directory. New tests in `t/t7003-filter-branch.sh` verify that path-traversing entries such as `../../escaped:injected` are rejected and that no file escapes the map directory. The commit message references 4811dabed7, a recent change that restored the `from:to` ordering and introduced the parsing logic now being secured.

Although `git filter-branch` is deprecated in favor of `git filter-repo`, it remains in the tree, so this closes a real injection vector for anyone still using the state-branch feature with untrusted input. The change is small, well-tested, and presented as unlikely to be controversial; the thread currently consists of this single patch with no review feedback yet.

This is a **bugfix** and the first patch in a five-patch series (v4) that reworks Git's HTTP transport retry handling. Ravi Mistry targets two specific defects introduced by commit 640657ffd0, which originally added HTTP 429 rate-limit retry support.

The patch corrects an off-by-one error in `http_request_recoverable()` where the retry counter used pre-decrement, causing `http.maxRetries=1` to perform zero retries instead of one, and allowing the counter to wrap from 0 to -1 (truthy in C) when a 429 arrived after a 401 re-authentication with retries disabled. It fixes this by restructuring the loop condition to check `http_max_retries > 0 && rate_limit_retries-- > 0` and adding a post-loop guard for the disabled-retries case.

The second fix moves the extraction of `CURLINFO_RETRY_AFTER` from `http_request()` into `finish_active_slot()`, ensuring the parsed Retry-After value is available to `handle_curl_result()` before it logs to Trace2, rather than logging the initial -1 placeholder. The patch adds three tests covering the corrected retry counts and verifying that Trace2 now records the actual Retry-After value.

This is the foundational cleanup for the series; patches 2 through 5 build on these fixes to add exponential backoff, configurable retry status codes, and POST request retries. The change is well-tested and surgically addresses edge cases that the original 429 implementation missed.

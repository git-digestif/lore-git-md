This is a bugfix targeting the loose object reading path, specifically fixing a size-truncation bug on LLP64 platforms such as 64-bit Windows. It is patch 2 of 5 in Elia Pinto's v3 series on loose object handling and size arithmetic; I have seen the cover letter for this series, which frames the overall goal as hardening loose object parsing against missing bounds checks and `long`-versus-`size_t` mismatches.

The patch widens the loose object size variables from `unsigned long` to `size_t` throughout the reading path in `object-file.c`, `object-file.h`, and `odb/source-loose.c`. Since commit c6a4629e32, `parse_loose_header()` already reports sizes as `size_t`, but downstream functions like `unpack_loose_rest()` still accepted `unsigned long`. On platforms where `long` is 32-bit but `size_t` is 64-bit, a malicious or corrupt header claiming a size of 4 GiB + 5 bytes would truncate the allocation to 6 bytes while the caller still believed the object was 4 GiB + 5 bytes long, leading to a buffer overread. The fix changes the signatures of `map_fd()`, `unpack_loose_header()`, `unpack_loose_rest()`, `check_stream_oid()`, and `odb_source_loose_map_object()` to use `size_t` consistently, ensuring the full 64-bit size flows correctly from header parsing through inflation.

The commit message includes a clear explanation, added in v3, that no overflow check via `st_add()` is needed along this path because the size is parsed with `st_mult()`/`st_add()` and a buffer of that exact size is allocated with `xmallocz()` before any further arithmetic. This addresses a forward-looking question from the maintainer about overflow safety. There is no automated test because reproducing the bug requires allocating a buffer near 4 GiB before the short-stream check triggers; the commit message instead documents a manual reproduction recipe using the `loose_obj()` test helper on Windows.

The contribution looks well-crafted and carefully motivated. The maintainer has already reviewed this patch positively in earlier iterations, finding the widening sensible and straightforward, and the v3 update addresses the remaining questions. It is a precise, mechanical fix that eliminates a real memory-safety hazard on affected platforms without changing behavior elsewhere.

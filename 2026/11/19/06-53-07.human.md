This is a follow-up ping on a bugfix patch series, not a new patch itself. Elia Pinto is nudging the list for feedback on the two-patch series that fixes silent 4 GiB truncation in `git grep` and `git diff` on 64-bit Windows, which has received no comments so far. He confirms the series still applies cleanly to current `master` and merges with `seen`.

The main new content is a specific design question about patch 2/2. Rather than silently diffing only the first 4 GiB of oversized working-tree files (or textconv output, or `--no-index` inputs), the patch makes `git diff` die with a clear error, matching what already happens for blobs. Elia Pinto asks whether this "die early" approach is acceptable as a first step, or whether reviewers would prefer the more invasive alternative of widening `diff_filespec.size` to `size_t` to support these files fully right away.

The series itself addresses a real correctness issue on platforms where `long` is 32 bits but `size_t` is 64 bits: patch 1/2 widens `grep_source.size` and related buffer sizes so `git grep` searches the full content of large files, while patch 2/2 adds truncation checks in the diff machinery. No tests accompany the patches because generating 4 GiB test inputs is impractical, though the commit messages describe verification via simulated truncation at 16 bits. The contribution looks well-motivated and carefully explained, but it is waiting on a decision about the diff-side approach before it can move forward.

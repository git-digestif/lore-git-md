This is a **substantive review** of the first patch in Dirk Gouders's v2 series, raising a performance objection to the proposed wrapper API for the new counted escape-sequence function.

Andy Koppe points out that retaining `display_mode_esc_sequence_len(const char *s)` as a thin wrapper that calls `display_mode_esc_sequence_len_counted(s, strlen(s))` introduces a performance regression: callers that previously returned immediately on non-ESC input or after a few bytes now scan the entire string via `strlen()`. When the function is called repeatedly to scan a whole string for SGR sequences, this changes the complexity from linear to quadratic. He therefore recommends removing the NUL-terminated wrapper entirely and requiring all callers to pass an explicit length, which forces callers to consider the appropriate bound rather than relying on an expensive implicit `strlen()`.

He notes that strbuf-based call sites can compute the length as `sb.buf + sb.len - s` if needed, but argues they do not actually require this safety net because strbufs are guaranteed to be NUL-terminated and the underlying scanner stops at NUL bytes anyway; the extra length calculation merely adds a source of error without providing real protection. This feedback targets the API design introduced in patch 1 of the series -- specifically the decision to keep the original function name as a `strlen()`-based shim over the new bounds-aware `display_mode_esc_sequence_len_counted()` -- and suggests that dropping the wrapper would avoid the quadratic behavior while still allowing safe counted access where bounds actually matter.

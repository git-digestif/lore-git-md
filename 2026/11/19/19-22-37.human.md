This is a bugfix hardening the EWAH bitmap parser against corrupt input. Dominik Maier sends a patch that adds bounds validation to `ewah_read_mmap()` and the RLW iterator in the `ewah/` subsystem, which reads serialized bitmap data from `.bitmap` files.

The commit message explains that the current code trusts serialized fields -- buffer size, RLW (running-length word) offset, and per-header literal word counts -- without checking them against the actual data length. A crafted or corrupted bitmap file could cause memory leaks, huge allocation attempts, or out-of-bounds heap reads in `ewah_each_bit()`, `rlwit_init()`, `next_word()`, and `rlwit_discharge()`.

The patch validates that `buffer_size` is non-zero and fits within the available mmap length before mutating the bitmap struct or allocating memory. It also walks the buffer to verify that every RLW header's literal word count stays within bounds and that the serialized RLW offset points to the final header. As defense in depth, `next_word()` and `rlwit_init()` now clamp reads against the buffer size.

The change touches `ewah/ewah_io.c` and `ewah/ewah_rlw.c`, and adds a test to `t/t5310-pack-bitmaps.sh` that corrupts a real bitmap file in four ways (zero buffer size, oversized buffer, bad RLW offset, oversized literal count) and confirms `git rev-list --test-bitmap` rejects each with the appropriate error message.

This looks like a solid, well-tested fix for a real robustness issue; the commit message clearly identifies the affected functions and the test coverage exercises the exact failure modes described.

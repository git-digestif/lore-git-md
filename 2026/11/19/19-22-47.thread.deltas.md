# Thread deltas

## 2026/11/19

- [2026/11/19/19-22-47 by Dominik Maier <dmnk@google.com>] Dominik Maier submitted a patch fixing a bug in `graph_insert_into_new_columns()` where a left-skewed 4+-parent octopus merge could overwrite `graph->mapping[graph->width - 2]` without advancing `graph->width`, leaving the last dashed-parent slot at -1 and indexing `graph->new_columns[-1]` in `graph_draw_octopus_merge()`; the fix restricts the right-neighbor edge fusion to existing non-merge columns (`idx < 0`) and adds a `BUG()` guard against negative mapping indices, accompanied by a new test in `t/t4215-log-skewed-merges.sh`.

## 2026/11/20

- [2026/11/20/10-50-21 by Caspar Duregger <caspar.duregger@gmail.com>] Caspar Duregger stated that the `idx < 0` fix is generally correct but that the commit message undersells it.
- [2026/11/20/10-50-21 by Caspar Duregger <caspar.duregger@gmail.com>] He provided a reproduction case using only 3 parents (rather than 4+) demonstrating the left-skewed merge losing an edge to its left neighbor.
- [2026/11/20/10-50-21 by Caspar Duregger <caspar.duregger@gmail.com>] He questioned whether using `BUG()` is correct, noting it leads to a crash whereas without it the result would be a garbage drawing, and that this is a matter of project policy.
- [2026/11/20/10-50-21 by Caspar Duregger <caspar.duregger@gmail.com>] He criticized the original commit message as very technical and difficult to understand without reading the code.
- [2026/11/20/10-50-21 by Caspar Duregger <caspar.duregger@gmail.com>] He proposed a revised commit message titled "graph: do not fuse merge parents with the column to their left" that explains the issue as a lost edge and, for 4+ parents, an out-of-bounds array read.

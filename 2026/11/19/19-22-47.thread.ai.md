Thread identity: single-patch bugfix series (v1, no cover letter indicated) from Dominik Maier <dmnk@google.com> fixing incorrect ASCII graph rendering in `git log --graph` for left-skewed octopus merges with four or more parents.

Core problem: in `graph.c`, `graph_insert_into_new_columns()` misplaces parents of a left-skewed octopus merge (`merge_layout == 0`). The merge commit's first parent does not advance `graph->width`, so `graph->width - 2` points at the column immediately left of the merge rather than at an existing right-side column. A fusion branch intended only for existing columns to the right of a merge (`idx < 0`) also fired when a later parent matched that left-side column, shifting subsequent parents one slot too far left. This left a `-1` in the final dashed-parent slot of `graph->mapping[]`, causing an out-of-bounds access at `graph->new_columns[-1]` inside `graph_draw_octopus_merge()`.

Current status: patch posted and under review; not queued in any integration branch and no maintainer decision recorded.

Key technical details: touches `graph.c` only, plus a regression test added to `t/t4215-log-skewed-merges.sh`. The fix adds an `idx < 0` guard to the fusion condition so it applies only to existing non-merge columns, and inserts a defensive `BUG("octopus merge mapping uninitialized")` in `graph_draw_octopus_merge()` when the looked-up mapping index is negative. The test constructs a left-skewed 4-parent octopus merge joined to an adjacent left column and verifies expected `git log --graph --date-order` output. Caspar Duregger demonstrated that the bug also reproduces with as few as three parents, supplying a complete shell test using `test_commit` and `commit-tree` that constructs a left-skewed 3-parent merge (`8_TOP` with parents `8_A`, `8_B`, and `8_M`) and verifies expected graph output, which is simpler than Maier's 4-parent reproduction.

Open questions and loose ends: Duregger raised a design question about the defensive `BUG("octopus merge mapping uninitialized")` in `graph_draw_octopus_merge()`, observing that without the assertion the code would produce a garbage drawing rather than a crash, and explicitly deferring to project policy on whether a `BUG()` is appropriate or graceful degradation is preferred. He also critiqued the commit message as highly technical and difficult for casual readers to grasp without reading the source, though this is surface-level feedback on wording rather than correctness. Correctness of the fix is not yet independently verified beyond Duregger's confirmation that the `idx < 0` guard is the correct approach.

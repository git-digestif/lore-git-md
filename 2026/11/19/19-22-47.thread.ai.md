Thread identity: single-patch bugfix series (v2) from Dominik Maier <dmnk@google.com> fixing incorrect ASCII graph rendering in `git log --graph` for left-skewed octopus merges with three or more parents.

Core problem: in `graph.c`, `graph_insert_into_new_columns()` misplaces parents of a left-skewed octopus merge (`merge_layout == 0`). The merge commit's first parent does not advance `graph->width`, so `graph->width - 2` points at the column immediately left of the merge rather than at an existing right-side column. A fusion branch intended only for existing columns to the right of a merge (`idx < 0`) also fired when a later parent matched that left-side column. With three parents this swallows an edge entirely; with four or more parents it shifts subsequent parents one slot too far left, leaving a `-1` in the final dashed-parent slot of `graph->mapping[]`, causing an out-of-bounds access at `graph->new_columns[-1]` inside `graph_draw_octopus_merge()`.

Current status: v2 posted and under review; not queued in any integration branch and no maintainer decision recorded. Changes from v1: the defensive `BUG("octopus merge mapping uninitialized")` previously added in `graph_draw_octopus_merge()` has been removed, the commit message now includes ASCII-art examples of both the 3-parent missing-edge case and the 4+-parent crash, and testing has been expanded to two regression tests.

Key technical details: touches `graph.c` only, plus `t/t4215-log-skewed-merges.sh`. The fix adds an `idx < 0` guard to the fusion condition so it applies only to existing non-merge columns. Two regression tests are added: one constructing a left-skewed 3-parent merge (`8_TOP` with parents `8_A`, `8_B`, `8_M`) and one with a 4-parent octopus (`8_TOP4` / `8_M4`), both verifying expected graph output via `lib_test_check_graph`.

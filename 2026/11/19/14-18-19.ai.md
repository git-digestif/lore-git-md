This is a cover letter for the second iteration of a three-patch bugfix series targeting Git's `compatObjectFormat` interoperability layer, which handles object conversion between SHA-1 and SHA-256 repositories. The series addresses three bugs: a `BUG()` crash when `extensions.compatObjectFormat` equals `objectFormat`, a silent wrong-OID return from `git rev-parse --output-object-format` when mapping fails, and inconsistent handling of unknown commit headers during conversion.

Version 2 incorporates feedback from Patrick Steinhardt. In patch 1, the error message in `verify_repository_format()` (in `setup.c`) now spells the config key as `extensions.compatObjectFormat` and the test in `t/t1302-repo-version.sh` uses modern `git config set`/`unset` syntax. Patch 2 now checks `repo_oid_to_algop()` for a `< 0` return in `builtin/rev-parse.c` and dies with "cannot map object %s to %s", matching `pack-objects`; the commit message clarifies that only single-revision arguments pass the desired output hash explicitly while ranges like `A..B` do not, and the test in `t/t1500-rev-parse.sh` now writes the object with `extensions.compatobjectformat` unset and enables the config afterward, avoiding manual object-directory copying that would be fragile under the ODB abstraction. Patch 3 changes the header-length checks in `convert_commit_object()` (in `object-file-convert.c`) from `<` to `<=` for `"tree "`, `"parent "`, and `"mergetag "`, so these headers are classified by key alone as `read_commit_extra_header_lines()` does; this ensures malformed values (e.g., `"tree "` with nothing after the space, or an empty-first-line `"mergetag "`) are rejected rather than copied with unconverted object IDs, while bare `"tree"` lines without a space are treated as unknown headers and copied verbatim, consistent with `convert_commit_extra_headers()`. A new test for the empty-mergetag case is added to `t/t1016-compatObjectFormat.sh`.

Patch 3 remains the likely point of contention: it removes a safety check deliberately added in commit 08a45903cb (2023-10-01) that rejected unknown commit headers during conversion to avoid embedding unconverted object IDs, and the author explicitly welcomes review from Eric Sunshine or brian m. carlson on this trade-off. The broader open questions from the thread -- whether removing the 2023 check is acceptable, how to handle headers containing object IDs that Git does not recognize, and Patrick Steinhardt's forward-looking proposal for a standardized `x-obj-` prefix for such custom headers -- remain unresolved.

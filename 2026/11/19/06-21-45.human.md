This is a cover letter for the third iteration of a five-patch bugfix series targeting loose object size handling and `long`-versus-`size_t` truncation bugs, particularly on LLP64 platforms like 64-bit Windows where `long` is 32-bit but `size_t` is 64-bit. Elia Pinto has reworked the series in response to maintainer feedback: patch 1/5 now emits a specific error message when an inflated object's size disagrees with its header ("loose object '<oid>' has N bytes, but its header says M") and writes the check as `total_out != hdrlen + size`; patch 3/5 no longer prints its own error but returns -1 silently and lets the caller report the mismatch, removing the `oid` field from `struct odb_loose_read_stream` that the previous version needed; and patch 2/5 now explains why overflow-safe `st_add()` arithmetic is unnecessary along that path. Commit messages, especially 4/5, have been trimmed.

The series addresses five distinct defects. Patches 1/5 and 3/5 add missing bounds checks to the loose object reader and streaming reader respectively, fixing cross-platform bugs where a zlib stream shorter than the header exposes uninitialized heap memory or a longer stream is silently truncated; both include automated tests. Patch 2/5 widens loose-object size variables from `unsigned long` to `size_t` throughout the reading path to prevent truncation on Windows. Patch 4/5 fixes a buffer overread in `git cat-file --batch` for objects between 2 GiB and 4 GiB caused by an `int` parameter wrapping negative. Patch 5/5 fixes a heap overflow in `notes.c` when concatenating notes totaling 4 GiB or more on 64-bit Windows, using `size_t` and `st_add3()` for the allocation size.

Only the cross-platform fixes (1/5 and 3/5) carry automated tests in `t/t1006-cat-file.sh` and `t/t1060-object-corruption.sh`; the LLP64-specific and multi-gigabyte scenarios (2/5, 4/5, 5/5) are documented with manual reproduction steps because they require impractical test environments. The issues were reviewed on the git-security list and deemed non-security-sensitive.

The v3 submission appears to address all outstanding maintainer requests: Junio C Hamano had approved patches 1/5, 2/5, 4/5, and 5/5 in v2 and requested only the rework to patch 3/5 that this version delivers. With the rework now in place and the review feedback incorporated, the series looks well-crafted and ready for final consideration, though no merge decision has been recorded yet.

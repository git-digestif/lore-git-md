Thread identity: single test-infrastructure patch authored by Kaartic Sivaraam, posted to the Git mailing list for review. Subject concerns serializing EXPENSIVE tests in the shell test suite.

Core problem: when GIT_TEST_LONG is set and tests run under parallel execution (e.g. `prove --jobs`, Makefile, or Meson), multiple memory-intensive tests execute concurrently and exhaust memory on 16GB GitLab and GitHub CI runners, causing OOM kills and timeouts. Specific culprits include the 5GB filtered hash-object test in t1007 and newer multi-GB tests in t1600, t4300, and t4141 introduced by commits 9048b48fb, 288266c11d, and 55c54fd375.

Current status: patch is under review; no integration branch placement is stated. Patrick Steinhardt has reviewed and approved the overall approach ("I'm fine with the approach"). Sivaraam has now acknowledged all of Steinhardt's review feedback and confirmed the planned fixes, but has not yet sent a new version. The thread stands at "approach approved, minor cleanups pending."

Key technical details: the patch adds `acquire_expensive_lock_()` and `release_expensive_lock_()` to t/test-lib.sh. The lock is a directory at `$TEST_RESULTS_DIR/expensive.lock` created via `mkdir`, containing a `pid` file recording the holder's process ID; waiters detect stale locks by checking whether the recorded PID is still running, remove the stale directory, and retry. `test_run_()` invokes the acquire function before any test whose prerequisite list contains EXPENSIVE and the release function after the test and its cleanup complete; release is also wired into `die()`'s EXIT trap to handle interruptions. Non-EXPENSIVE tests in the same script continue running in parallel. t/README is updated to document that long tests may use significant memory and disk and therefore run one at a time even under parallel execution.

Open questions and loose ends: Patrick Steinhardt raised several review points, all now acknowledged by Sivaraam as planned fixes: (1) whether writing the "waiting for another EXPENSIVE test to finish" message to file descriptor 3 could break TAP format compliance -- Sivaraam confirms it is safe because fd 3 goes to stderr or the test output file and is suppressed under non-verbose runs; (2) whether the `expensive_lock_waited_` sentinel variable should be declared `local` -- confirmed, along with `owner`; (3) wording suggestions -- use "tests" instead of "test", "may" instead of "can", and avoid naming `prove --jobs` specifically since the Makefile and Meson also run tests concurrently. Steinhardt also traced a race condition in stale-lock detection (two waiters racing to read and delete the `pid` file) and confirmed the author's mitigation via the `test -n "$owner"` check. Sivaraam additionally analyzed a narrower multi-waiter race: if a lock holder is SIGKILLed while two or more scripts are waiting, both waiters may read the same dead PID before either acts; one could then delete the lock, recreate it, and write its own PID, while the other -- still holding the stale PID -- deletes that live lock and takes its place. Sivaraam concludes this window is too rare to warrant extra complexity, accepting the worst case of two EXPENSIVE tests running concurrently instead of one. Steinhardt explicitly considered and rejected splitting the prerequisite into `EXPENSIVE_MEM` versus `EXPENSIVE_DISK` as unnecessary complexity.

Participant positions: Kaartic Sivaraam is the author. Patrick Steinhardt reviewed substantively -- engaging with the lock mechanism, race conditions, and TAP compliance -- and approved the approach while requesting the above refinements, all of which Sivaraam has now accepted.

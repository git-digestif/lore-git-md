Thread identity: single test-infrastructure patch authored by Kaartic Sivaraam, posted to the Git mailing list for review. Subject concerns serializing EXPENSIVE tests in the shell test suite. Current version is v2, posted with a range-diff confirming incorporation of Patrick Steinhardt's review feedback; no integration branch placement is stated.

Core problem: when GIT_TEST_LONG is set and tests run under parallel execution (for example `prove --jobs`, the Makefile, or Meson), multiple memory-intensive tests execute concurrently and exhaust memory on 16GB GitLab and GitHub CI runners, causing OOM kills and timeouts. Specific culprits include the 5GB filtered hash-object test in t1007 and newer multi-GB tests in t1600, t4300, and t4141 introduced by commits 9048b48fb, 288266c11d, and 55c54fd375.

Current status: patch v2 remains under review. Patrick Steinhardt reviewed and approved the overall approach ("I'm fine with the approach"), and v2 incorporates his requested refinements. Junio C Hamano raised two serious correctness objections to the v2 lock mechanism (a TOCTOU race and a signal-handling deadlock window); Sivaraam replied proposing two incremental fixes. Junio has now responded to those proposals, drawing a sharp distinction between the two failure modes: a leaky lock that allows multiple EXPENSIVE tests to run concurrently merely reproduces the status quo and is therefore not a regression, whereas a permanent deadlock is a serious regression that must be eliminated in the next version. He states that if the updated patch kills the deadlock scenario, he will be satisfied, effectively greenlighting Sivaraam's proposed reordering of `have_expensive_lock_=t` before the PID write while implying the deferred `kill -9` and microsecond-window edge cases are acceptable residual risks for now. No v3 has been posted yet, so the thread remains open awaiting a revised patch incorporating these fixes.

Key technical details: the patch adds `acquire_expensive_lock_()` and `release_expensive_lock_()` to t/test-lib.sh. The lock is a directory at `$TEST_RESULTS_DIR/expensive.lock` created via `mkdir`, containing a `pid` file recording the holder's process ID; waiters detect stale locks by checking whether the recorded PID is still running, remove the stale directory, and retry. `test_run_()` invokes the acquire function before any test whose prerequisite list contains EXPENSIVE and the release function after the test and its cleanup complete; release is also wired into `die()`'s EXIT trap to handle interruptions. Non-EXPENSIVE tests in the same script continue running in parallel. t/README is updated to document that long tests may use significant memory and disk and therefore run one at a time even under parallel execution. The patch touches only t/test-lib.sh and t/README, adding 45 lines. Sivaraam's proposed fixes to address Junio's objections are: (1) to close the TOCTOU race where a waiter might delete a new lock holder's directory, he adds a secondary "break lock" at `$expensive_lock_.break` created via `mkdir` before removing a stale lock, and re-reads the `pid` file to verify the owner has not changed before running `rm -rf`; (2) to close the signal-handling deadlock where a process killed between `mkdir "$expensive_lock_"` and setting `have_expensive_lock_=t` leaves an unremovable empty lock directory, he reorders the code to set `have_expensive_lock_=t` before writing the PID to the `pid` file, ensuring `release_expensive_lock_()` will clean up even if the PID write is interrupted.

Open questions and loose ends: Junio C Hamano identified two unresolved concurrency flaws in v2. First, a TOCTOU race: if waiter T2 reads the `pid` file just before lock-holder T1 releases and exits, while waiter T3 concurrently acquires the lock, T2 can see T1's PID as dead, run `rm -rf "$expensive_lock_"`, and delete T3's active lock, allowing T2 and T3 to run EXPENSIVE tests concurrently. Second, a more severe signal-handling window: a process can receive INT/TERM/HUP after successfully running `mkdir "$expensive_lock_"` but before writing its PID to the `pid` file or setting `have_expensive_lock_=t`; the `die()` EXIT trap then calls `release_expensive_lock_()`, which returns early because `have_expensive_lock_` is unset, leaving an empty lock directory that no waiter will clear because `kill -0` is skipped when `owner` is empty, causing a permanent deadlock. Junio explicitly called the deadlock scenario "far worse" than the race. Sivaraam's reply proposes the two incremental fixes described above but explicitly acknowledges they do not cover all edge cases: a `kill -9` arriving after `mkdir` but before the PID write, or a signal arriving in the microseconds between `mkdir` and setting the flag, would still leave a permanently stuck lock. He suggests deferring fixes for those remaining windows until they cause actual problems. Junio has now responded that the leaky-lock scenario is acceptable as it merely reproduces the status quo, but the permanent deadlock must be eliminated in the next version; he has indicated he will be satisfied if the deadlock is killed, accepting the deferral of the `kill -9` and microsecond-window edge cases as residual risks. The thread now awaits a v3 patch incorporating the flag-before-PID-write ordering and the `.break` lock mechanism. Earlier review points from Patrick Steinhardt are addressed in v2: the "waiting for another EXPENSIVE test to finish" message to file descriptor 3 is safe for TAP compliance because fd 3 goes to stderr or the test output file and is suppressed under non-verbose runs; `owner` and `waited` are now `local`; wording no longer names `prove --jobs` specifically. Steinhardt traced a stale-lock detection race and confirmed the author's mitigation via the `test -n "$owner"` check. Sivaraam analyzed a narrower multi-waiter race, where the lock holder is SIGKILLed while two or more scripts wait, and concluded the window is too rare to warrant extra complexity, accepting the worst case of two EXPENSIVE tests running concurrently. Steinhardt explicitly considered and rejected splitting the prerequisite into `EXPENSIVE_MEM` versus `EXPENSIVE_DISK` as unnecessary complexity.

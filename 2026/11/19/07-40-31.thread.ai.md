Thread identity: single test-infrastructure patch authored by Kaartic Sivaraam, posted to the Git mailing list for review. Subject concerns serializing EXPENSIVE tests in the shell test suite. Current version is v2, posted with a range-diff confirming incorporation of all review feedback.

Core problem: when GIT_TEST_LONG is set and tests run under parallel execution (e.g. `prove --jobs`, Makefile, or Meson), multiple memory-intensive tests execute concurrently and exhaust memory on 16GB GitLab and GitHub CI runners, causing OOM kills and timeouts. Specific culprits include the 5GB filtered hash-object test in t1007 and newer multi-GB tests in t1600, t4300, and t4141 introduced by commits 9048b48fb, 288266c11d, and 55c54fd375.

Current status: patch v2 is under review; no integration branch placement is stated. Patrick Steinhardt has reviewed and approved the overall approach ("I'm fine with the approach"). Version two incorporates all of Steinhardt's requested refinements: the `owner` and `waited` variables are now declared `local` inside `acquire_expensive_lock_()`, and wording in the commit message and comments avoids naming `prove --jobs` specifically (using "tests" instead of "test", "may" instead of "can") since the Makefile and Meson also run tests concurrently; minor wording fixes include "multi-gigabytes of memory" replacing "multi-gigabytes". The thread stands at "approach approved, v2 posted with all review feedback addressed."

Key technical details: the patch adds `acquire_expensive_lock_()` and `release_expensive_lock_()` to t/test-lib.sh. The lock is a directory at `$TEST_RESULTS_DIR/expensive.lock` created via `mkdir`, containing a `pid` file recording the holder's process ID; waiters detect stale locks by checking whether the recorded PID is still running, remove the stale directory, and retry. `test_run_()` invokes the acquire function before any test whose prerequisite list contains EXPENSIVE and the release function after the test and its cleanup complete; release is also wired into `die()`'s EXIT trap to handle interruptions. Non-EXPENSIVE tests in the same script continue running in parallel. t/README is updated to document that long tests may use significant memory and disk and therefore run one at a time even under parallel execution. The patch touches only t/test-lib.sh and t/README, adding 45 lines.

Open questions and loose ends: none outstanding. Patrick Steinhardt's review points have all been addressed in v2: (1) the "waiting for another EXPENSIVE test to finish" message to file descriptor 3 is safe for TAP compliance because fd 3 goes to stderr or the test output file and is suppressed under non-verbose runs; (2) `owner` and `waited` are now declared `local`; (3) wording no longer names `prove --jobs` specifically. Steinhardt traced a race condition in stale-lock detection (two waiters racing to read and delete the `pid` file) and confirmed the author's mitigation via the `test -n "$owner"` check. Sivaraam analyzed a narrower multi-waiter race (lock holder SIGKILLed while two or more scripts wait) and concluded the window is too rare to warrant extra complexity, accepting the worst case of two EXPENSIVE tests running concurrently. Steinhardt explicitly considered and rejected splitting the prerequisite into `EXPENSIVE_MEM` versus `EXPENSIVE_DISK` as unnecessary complexity.

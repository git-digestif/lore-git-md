Thread identity: single test-infrastructure patch authored by Kaartic Sivaraam, posted to the Git mailing list for review. Subject concerns serializing EXPENSIVE tests in the shell test suite. Current version is v2, posted with a range-diff confirming incorporation of Patrick Steinhardt's review feedback; no integration branch placement is stated.

Core problem: when GIT_TEST_LONG is set and tests run under parallel execution (for example `prove --jobs`, the Makefile, or Meson), multiple memory-intensive tests execute concurrently and exhaust memory on 16GB GitLab and GitHub CI runners, causing OOM kills and timeouts. Specific culprits include the 5GB filtered hash-object test in t1007 and newer multi-GB tests in t1600, t4300, and t4141 introduced by commits 9048b48fb, 288266c11d, and 55c54fd375.

Current status: patch v2 remains under review and is not accepted as-is. Patrick Steinhardt reviewed and approved the overall approach ("I'm fine with the approach"), and v2 incorporates his requested refinements: `owner` and `waited` are declared `local` inside `acquire_expensive_lock_()`, and wording in the commit message and comments avoids naming `prove --jobs` specifically, using "tests" instead of "test" and "may" instead of "can" because the Makefile and Meson also run tests concurrently; minor wording fixes include "multi-gigabytes of memory" replacing "multi-gigabytes". However, Junio C Hamano has now raised two serious correctness objections to the v2 lock mechanism, so the thread is open rather than converged.

Key technical details: the patch adds `acquire_expensive_lock_()` and `release_expensive_lock_()` to t/test-lib.sh. The lock is a directory at `$TEST_RESULTS_DIR/expensive.lock` created via `mkdir`, containing a `pid` file recording the holder's process ID; waiters detect stale locks by checking whether the recorded PID is still running, remove the stale directory, and retry. `test_run_()` invokes the acquire function before any test whose prerequisite list contains EXPENSIVE and the release function after the test and its cleanup complete; release is also wired into `die()`'s EXIT trap to handle interruptions. Non-EXPENSIVE tests in the same script continue running in parallel. t/README is updated to document that long tests may use significant memory and disk and therefore run one at a time even under parallel execution. The patch touches only t/test-lib.sh and t/README, adding 45 lines.

Open questions and loose ends: Junio C Hamano identified two unresolved concurrency flaws in v2. First, a TOCTOU race: if waiter T2 reads the `pid` file just before lock-holder T1 releases and exits, while waiter T3 concurrently acquires the lock, T2 can see T1's PID as dead, run `rm -rf "$expensive_lock_"`, and delete T3's active lock, allowing T2 and T3 to run EXPENSIVE tests concurrently. Second, a more severe signal-handling window: a process can receive INT/TERM/HUP after successfully running `mkdir "$expensive_lock_"` but before writing its PID to the `pid` file or setting `have_expensive_lock_=t`; the `die()` EXIT trap then calls `release_expensive_lock_()`, which returns early because `have_expensive_lock_` is unset, leaving an empty lock directory that no waiter will clear because `kill -0` is skipped when `owner` is empty, causing a permanent deadlock. Junio explicitly called the deadlock scenario "far worse" than the race. Earlier review points from Patrick Steinhardt are addressed in v2: the "waiting for another EXPENSIVE test to finish" message to file descriptor 3 is safe for TAP compliance because fd 3 goes to stderr or the test output file and is suppressed under non-verbose runs; `owner` and `waited` are now `local`; wording no longer names `prove --jobs` specifically. Steinhardt traced a stale-lock detection race and confirmed the author's mitigation via the `test -n "$owner"` check. Sivaraam analyzed a narrower multi-waiter race, where the lock holder is SIGKILLed while two or more scripts wait, and concluded the window is too rare to warrant extra complexity, accepting the worst case of two EXPENSIVE tests running concurrently. Steinhardt explicitly considered and rejected splitting the prerequisite into `EXPENSIVE_MEM` versus `EXPENSIVE_DISK` as unnecessary complexity. The new Junio objections supersede the prior "no outstanding issues" state: a fix, likely a v3, is needed for the TOCTOU deletion race and especially the empty-lock deadlock window.

Participant positions: Kaartic Sivaraam is the author.

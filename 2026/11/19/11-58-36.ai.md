This is a review reply on patch 3/4 of Patrick Steinhardt's four-patch performance series, clarifying the root cause of the auto-maintenance reflog bug and the chosen fix. Patrick confirms to Toon Claes that `reflog_expiry_prepare()` -- the function that performs the reachability walk needed to distinguish reachable from unreachable reflog entries -- is indeed not called in the current `reflog-expire` auto-condition path in `builtin/gc.c`, which is exactly why every entry is currently misclassified as unreachable and compared against `gc.reflogExpireUnreachable` instead of `gc.reflogExpire`. Rather than adding the missing call (which would introduce the expensive foreground reachability walk the patch aims to avoid), the series instead reworks `reflog_expire_condition()` and the `count_reflog_entries()` callback to compare entry timestamps only against `gc.reflogExpire`, skipping reachability determination entirely during `--auto`. This resolves the open wording question Toon had raised about the commit message's phrase "we could easily fix that by calling `reflog_expiry_prepare()`" -- the intended meaning is that calling it would fix the overcounting, but the patch deliberately takes a different, cheaper route. For future reference: the relevant code lives in `builtin/gc.c` around the `reflog_expire_condition()` function and the `count_reflog_entries_data` struct; the behavioral change is that `git maintenance run --auto` now spawns `git reflog expire` only when entries older than `gc.reflogExpire` exist, ignoring `gc.reflogExpireUnreachable` entirely, trading an undercount of prunable unreachable entries for a roughly 21x speedup in auto-maintenance wall time.

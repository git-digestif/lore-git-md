This is a refactoring patch, specifically patch 10 of 13 in Patrick Steinhardt's v5 series modernizing `git rerere`'s subcommand handling.

The patch extracts the "gc" subcommand into a dedicated `cmd_rerere_gc()` function in `builtin/rerere.c`, following the same pattern established by the preceding patches for "forget", "clear", "status", "remaining", and "diff". The new handler sets up its own `parse_options()` call with a local `OPT_HIDDEN_BOOL(0, "skip-locked", ...)` option and rejects extra arguments with `usage(_("too many arguments"))`.

The main `cmd_rerere()` function is adjusted to use `PARSE_OPT_KEEP_UNKNOWN_OPT` when parsing its own options, allowing subcommand-specific options like `--skip-locked` to be passed through to the subcommand handlers rather than being rejected at the top level. The previous manual validation that died with "the option '%s' requires '%s'" when `--skip-locked` appeared without `gc` is removed, along with the corresponding test in `t/t4200-rerere.sh`.

This introduces the series' only intentional user-visible behavior change: `--skip-locked` is now accepted only after the `gc` subcommand name (`git rerere gc --skip-locked`), not before it (`git rerere --skip-locked gc`). The commit message notes this is safe because the flag was only introduced in 5f6b6aa3ab4 (2026-10-13) and has not yet appeared in any release. Future discussion may reference this option-ordering restriction when reviewing patch 11 or the overall series behavior.

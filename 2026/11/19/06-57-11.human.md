This is a follow-up ping on the two-patch bugfix series addressing 4GiB+ file truncation on 32-bit `long` platforms. Elia Pinto notes the series still has no review comments and applies cleanly to current `master`, but raises a sequencing question about the second patch.

The new wrinkle concerns `git apply --index` (and therefore `git am`): while patch 2/2 fixes the file written to the working tree, the blob added to the index still flows through `odb_write_object()`, which takes an `unsigned long` until a separate series converting more object/buffer sizes to `size_t` lands. On affected platforms, this means the index entry would still be truncated even though the working tree file is complete. Pinto offers two ways forward -- either use `cast_size_t_to_ulong()` in `add_index_file()` so the operation fails loudly rather than silently corrupting the index (matching an approach used elsewhere), or hold back patch 2/2 entirely until the dependent `size_t` series merges. He asks which approach the maintainers prefer.

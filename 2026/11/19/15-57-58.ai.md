This is a cover letter for **v4 of a five-patch series** by Ravi Mistry that reworks Git's HTTP transport retry handling to address four gaps: an off-by-one retry counter bug, missing exponential backoff when `Retry-After` headers are absent, inability to retry transient 5xx errors, and lack of retries for read-only HTTP POST requests used in fetch/clone and partial clone data transfers. The series touches `http.c`, `http.h`, `remote-curl.c`, `git-curl-compat.h`, `Documentation/config/http.adoc`, and the test suite (`t/t5584-http-429-retry.sh`, `t/lib-httpd/http-429.sh`).

The most significant behavioral changes are the introduction of exponential backoff using `http.retryAfter` as an initial delay (defaulting to **10 seconds** in patch 5/5, producing a 10s, 20s, 40s progression capped at `http.maxRetryTime`), the new `http.retryStatusCodes` config key (default `"429"`, overridable via `GIT_HTTP_RETRY_STATUS_CODES`) allowing opt-in retries for codes like 502/503/504, and the extension of retry logic to `post_rpc()` in `remote-curl.c`. Critically, v4 restricts POST retries to read-only services (`git-upload-pack` and `git-upload-archive`) via a `can_retry_rpc()` whitelist, explicitly excluding `git-receive-pack` (push) to avoid non-idempotent operation retries, and adds a test verifying push is not retried. The `attempt` counter is now `size_t` rather than `int`.

Patch 5/5 also resolves the `Retry-After: 0` ambiguity: when `CURLINFO_RETRY_AFTER <= 0`, the code now inspects the raw `Retry-After` header via `curl_easy_header()` (guarded by `GIT_CURL_HAVE_CURL_EASY_HEADER` for libcurl >= 7.84.0) so that explicit `Retry-After: 0` or past HTTP-dates trigger immediate retry, while absent or malformed headers fall back to the 10-second default. Documentation has been updated to frame non-429 retry codes as a temporary workaround for buggy provider infrastructure rather than a permanent feature, reflecting Patrick Steinhardt's architectural concern about ecosystem convergence on 429.

All of Patrick Steinhardt's substantive review points from v3 appear addressed in this version: the retry counter typing, the POST retry whitelist, the `Retry-After: 0` handling, the documentation framing for `http.retryStatusCodes`, and shell case-arm indentation in test helpers. The series remains under review; Junio C Hamano previously raised a procedural question about the two-phase introduction of the 10-second default (patches 1-4 assume `http.retryAfter=0` while patch 5 retroactively changes the default), though v4 keeps this structure. Remaining points of contention may include the architectural debate over whether configurable 5xx retry codes should exist at all versus standardizing on 429, and whether the 10-second default strikes the right balance between server protection and interactive responsiveness.

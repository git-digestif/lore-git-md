This thread is about a single test-infrastructure patch from Kaartic Sivaraam that serializes `EXPENSIVE` tests in Git's shell test suite. When `GIT_TEST_LONG` is set and tests run in parallel (via `prove --jobs`, the Makefile, or Meson), several memory-hungry tests -- including the 5GB filtered hash-object test in t1007 and newer multi-GB tests in t1600, t4300, and t4141 -- can run concurrently and exhaust memory on 16GB CI runners, causing OOM kills. The patch adds `acquire_expensive_lock_()` and `release_expensive_lock_()` to t/test-lib.sh, using a `$TEST_RESULTS_DIR/expensive.lock` directory with a `pid` file so that only one `EXPENSIVE` test runs at a time even under parallel execution, with stale-lock recovery if a holder dies.

Patrick Steinhardt reviewed the patch substantively, approved the overall approach, and raised a handful of refinements: possible TAP compliance concerns around writing the "waiting" message to file descriptor 3, whether `expensive_lock_waited_` and `owner` should be declared `local`, and wording tweaks (plural "tests", "may" instead of "can", and not singling out `prove --jobs` since the Makefile and Meson also parallelize). He traced a race in the stale-lock detection and confirmed the author's mitigation, and he explicitly rejected splitting the prerequisite into `EXPENSIVE_MEM` versus `EXPENSIVE_DISK` as needless complexity.

In the latest reply, Sivaraam acknowledged all of the feedback and confirmed the planned fixes, including the `local` declarations and the TAP-compliance reasoning, though he has not yet posted a new version of the patch. He also analyzed one remaining edge case -- two waiters racing after a SIGKILLed holder -- and concluded the narrow window is too rare to warrant extra complexity, accepting the worst case of two `EXPENSIVE` tests briefly overlapping. The thread therefore stands at "approach approved, minor cleanups pending," with no integration branch placement mentioned and no v2 posted yet.

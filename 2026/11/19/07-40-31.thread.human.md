The thread concerns a test-infrastructure patch from Kaartic Sivaraam that serializes `EXPENSIVE` tests in Git's shell test suite to prevent memory exhaustion on CI runners. When `GIT_TEST_LONG` is set and tests run under parallel execution, multiple multi-GB tests (notably in t1007, t1600, t4300, and t4141) can exhaust the 16GB memory of GitLab and GitHub runners, causing OOM kills. The patch adds `acquire_expensive_lock_()` and `release_expensive_lock_()` to `t/test-lib.sh`, using a directory-based lock at `$TEST_RESULTS_DIR/expensive.lock` with `mkdir` for atomic acquisition and a `pid` file for stale-lock recovery; non-`EXPENSIVE` tests continue running in parallel.

Patrick Steinhardt has now reviewed the patch and approved the overall approach, calling it substantive rather than superficial. He traced a potential race in the stale-lock detection where two waiters might race to read and delete the `pid` file, confirmed the author's mitigation via the `test -n "$owner"` check, and raised a question about whether writing the "waiting" message to file descriptor 3 could break TAP format compliance. He also suggested declaring the `expensive_lock_waited_` sentinel as `local`, proposed minor wording changes ("tests" instead of "test", "may" instead of "can", and avoiding specific mention of `prove --jobs` since the Makefile and Meson also run tests concurrently), and explicitly considered and rejected splitting the prerequisite into `EXPENSIVE_MEM` versus `EXPENSIVE_DISK` as unnecessary complexity. The series remains under review with maintainer-level approval signaled but no integration branch placement stated.

This thread is about a small test-infrastructure patch from Kaartic Sivaraam that makes EXPENSIVE tests in Git's shell test suite run one at a time even under parallel execution, because several recent tests in t1007, t1600, t4300, and t4141 consume multiple gigabytes of memory and OOM-kill CI runners when run concurrently. The patch is at v2, which incorporated Patrick Steinhardt's review refinements, and Steinhardt has approved the overall approach. However, Junio C Hamano has since identified two serious correctness flaws in the lock mechanism: a TOCTOU race in which a waiter can delete a newly acquired lock held by a different process, and a signal-handling window in which a process killed between creating the lock directory and recording its PID leaves a permanent empty lock that deadlocks all waiters -- a scenario Junio called "far worse" than the race.

In his latest reply, Sivaraam proposes two incremental fixes: a secondary "break lock" directory plus a re-read of the pid file to close the TOCTOU deletion race, and reordering the code so `have_expensive_lock_` is set before the PID is written, so the die() trap can clean up the lock if interrupted. He openly acknowledges that a `kill -9` or signal landing in the remaining microsecond windows would still leave a stuck lock, and suggests deferring those cases until they cause real problems. The thread therefore remains open: v2 is not accepted as-is, no v3 has been posted, and the outstanding question is whether Junio considers these incremental fixes sufficient or wants the remaining race windows closed before the series can converge.

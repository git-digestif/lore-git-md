Kaartic Sivaraam has posted version 2 of a patch that serializes memory-intensive tests in Git's shell test suite to prevent OOM kills on CI runners. When GIT_TEST_LONG is set and tests run in parallel via prove, Make, or Meson, multiple multi-gigabyte tests (notably in t1007, t1600, t4300, and t4141) can exhaust the 16GB memory of GitLab and GitHub runners. Patrick Steinhardt reviewed the approach and approved it, requesting refinements that are now incorporated in v2: the owner and waited variables are declared local inside the lock acquisition function, and commit message wording no longer singles out prove --jobs since other build systems also run tests concurrently.

The patch adds acquire_expensive_lock_() and release_expensive_lock_() to t/test-lib.sh, using a $TEST_RESULTS_DIR/expensive.lock directory with a pid file to ensure only one EXPENSIVE-prerequisite test runs at a time across all parallel test scripts. Waiters detect stale locks by checking if the recorded PID is still alive, and release is wired into both normal test completion and die()'s EXIT trap to handle interruptions. Non-EXPENSIVE tests continue running in parallel, and t/README documents that long tests may use significant resources and thus run serially. The series touches only t/test-lib.sh and t/README.

The thread stands at "approach approved, v2 posted with all review feedback addressed," and remains under review with no integration branch placement stated. Steinhardt engaged substantively with the lock mechanism, confirming the stale-lock race handling is sound, and considered but rejected splitting the prerequisite into separate memory and disk categories as unnecessary complexity.

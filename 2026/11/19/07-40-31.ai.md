This is a **test** patch (CI infrastructure) that serializes `EXPENSIVE` tests in Git's shell test suite to prevent memory exhaustion on CI runners when tests run in parallel.

The patch addresses a concrete CI failure mode: when `GIT_TEST_LONG` is set and tests are run with `prove --jobs`, multiple memory-intensive tests (notably the 5GB filtered hash-object test in `t1007` and newer multi-GB tests in `t1600`, `t4300`, and `t4141` added by commits `9048b48fb`, `288266c11d`, and `55c54fd375`) execute simultaneously, causing OOM kills and job timeouts on 16GB GitLab and GitHub runners. The author reproduces the hang and validates the fix with CI runs on both platforms.

Mechanically, the patch adds two functions to `t/test-lib.sh`: `acquire_expensive_lock_()` and `release_expensive_lock_()`. The lock is a directory at `$TEST_RESULTS_DIR/expensive.lock` created with `mkdir`, containing a `pid` file that records the holder's process ID. If a waiter finds a stale lock (PID no longer running), it removes the directory and retries. `test_run_()` calls `acquire_expensive_lock_()` before executing any test whose prereq list contains `EXPENSIVE`, and `release_expensive_lock_()` after the test and its cleanup finish; the release also happens in `die()`'s EXIT trap path to handle interruptions. Cheap tests in the same script continue to run in parallel--only tests marked `EXPENSIVE` block on each other.

The patch also updates `t/README` to document that long tests may use significant memory and disk and therefore run one at a time even under parallel test execution. The commit message is well-motivated, cites the specific commits that introduced the problematic tests, and includes reproduction steps and CI validation links, indicating a thoroughly investigated fix.

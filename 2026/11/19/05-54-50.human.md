This is a substantive review of the first patch in Dirk Goudlers's v2 bugfix series on UTF-8 bounds handling. Andy Koppe examines the newly introduced `display_mode_esc_sequence_len()` wrapper -- which calls `strlen(s)` to feed the counted variant -- and identifies a concrete performance regression: callers that previously returned early after a few bytes now scan the entire input string on every invocation, turning repeated linear scans into quadratic time.

Koppe argues that if the original uncounted implementation is not retained, the wrapper should be removed entirely so that callers must explicitly decide what length to pass, rather than silently paying for a full `strlen()`. He notes that strbuf call sites can compute the remaining length as `sb.buf + sb.len - s`, but also observes they do not actually need the safety net because strbufs are guaranteed to be NUL-terminated and the scanning function stops at NUL bytes anyway, meaning the length arithmetic adds complexity without buying safety.

The review is precise and technically grounded: it names the specific function and the complexity change (linear to quadratic) without hedging. No other objections to the patch are raised in this message.

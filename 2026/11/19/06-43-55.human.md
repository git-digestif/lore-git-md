This is a bugfix, the third patch in Elia Pinto's four-part v3 series addressing silent 32-bit integer truncation when Git handles files larger than 2--4 GiB. This particular patch targets rename detection in `diffcore-delta.c`, widening two `unsigned int` fields to `size_t` so that `git diff -M`, `git log --follow`, and merge rename detection work correctly on very large files.

The patch changes the local buffer-size variable `sz` in `hash_chars()` and the `cnt` member of `struct spanhash` from `unsigned int` to `size_t`, and likewise widens the loop counters in `diffcore_count_changes()`. Previously, a file of 4 GiB or more would have only a prefix hashed because `sz` truncated, while the similarity score was still computed against the full (truncated) size, causing true renames to be missed. Separately, with repetitive content the per-hash span count could wrap to zero after four billion bytes, making a populated bucket look empty and again hiding renames. The commit message notes the hash value itself stays `unsigned int` because it remains below `HASHBASE`, and the memory cost of larger counters is bounded at roughly 1 MiB per file.

The author provides a reproduction recipe showing that with 16-bit truncation simulated, `git diff --cached -M` reports delete-and-add instead of a rename for both a random file and a file of zeros, but no committed test accompanies the patch since exercising the bug requires a multi-gigabyte input. Junio C Hamano is credited with Helped-by, and the change directly resolves his v2 concern about `struct spanhash.cnt` wrapping; this is part of a series that remains under review with no merge status reported. The patch looks clean and well-motivated, making a mechanical type widening that fixes a real correctness bug without altering on-disk formats.

This is a bugfix patch, the first of a five-patch v4 series reworking Git's HTTP transport retry handling.

The patch fixes two bugs introduced by commit 640657ffd0 ("http: add support for HTTP 429 rate limit retries"). First, in `http_request_recoverable()` in `http.c`, the retry counter used pre-decrement (`--rate_limit_retries`), causing `http.maxRetries=N` to perform only N-1 retries and wrapping from 0 to -1 (truthy in C) when `http.maxRetries=0` and a 429 followed a 401 re-auth. The loop condition is now `http_max_retries > 0 && rate_limit_retries-- > 0`, with a post-loop `http_max_retries <= 0` check returning `HTTP_ERROR` without the "retries-exhausted" trace. Second, `CURLINFO_RETRY_AFTER` was queried in `http_request()` after `run_one_slot()` had already called `handle_curl_result()`, causing Trace2 to log `retry_after` as -1; the extraction is moved into `finish_active_slot()` so `slot->results->retry_after` is populated (initialized to -1, set only if `> 0`) before logging.

Tests in `t/t5584-http-429-retry.sh` verify that `http.maxRetries=1` retries exactly once, `http.maxRetries=2` fails after three 429s but succeeds after two, and Trace2 now records the actual `Retry-After` value. The test helper `t/lib-httpd/http-429.sh` is extended to support multiple consecutive failures via `*-fail-N*` URL patterns.

As patch 1/5 of the series, this addresses the off-by-one retry count gap; subsequent patches in the series add exponential backoff, configurable retry status codes, and POST request retries.

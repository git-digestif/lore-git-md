This is a **feature** patch series (with bugfix elements) targeting Git's HTTP transport layer, currently at version 4 and under review.

Ravi Mistry's five-patch series addresses four gaps in how Git handles transient HTTP errors when talking to hosting backends and reverse proxies. Building on the existing HTTP 429 retry support, it fixes an off-by-one bug that caused `http.maxRetries=1` to perform zero retries, introduces exponential backoff (10s, 20s, 40s, ...) when servers omit a `Retry-After` header, adds a new `http.retryStatusCodes` config option so environments can opt into retrying transient 5xx errors like 502/503/504, and extends retry logic to read-only HTTP POST requests used during fetch, clone, and partial-clone blob downloads. Patch 5 changes the default `http.retryAfter` from 0 to 10 seconds so Git does not hammer an overloaded server when no header is present.

Version 4 incorporates the remaining substantive feedback from the v3 review. Most notably, POST retries are now restricted to read-only services (`git-upload-pack` and `git-upload-archive`), explicitly excluding `git-receive-pack` so pushes are never retried after a potential 502/504. The author also addressed the edge case where an explicit `Retry-After: 0` or a past HTTP-date should trigger an immediate retry rather than falling back to the 10-second default, using `curl_easy_header()` to inspect the raw header when `CURLINFO_RETRY_AFTER` is non-positive. The retry attempt counter was switched to `size_t`, and the documentation now frames `http.retryStatusCodes` as a temporary workaround for buggy provider infrastructure rather than a permanent feature, nudging the ecosystem toward standard 429 responses.

The series touches `http.c`, `remote-curl.c`, `http.h`, and adds substantial test coverage in `t/t5584-http-429-retry.sh` including a new test verifying that push is not retried. With the default delay compromise settled at 10 seconds and Patrick Steinhardt's correctness concerns about non-idempotent operations resolved, the series appears technically complete and well-tested, awaiting final integration.

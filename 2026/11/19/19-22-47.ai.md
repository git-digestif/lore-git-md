This is a bugfix targeting the ASCII graph rendering code in `graph.c`, specifically fixing incorrect output for left-skewed octopus merges with four or more parents.

The bug lives in `graph_insert_into_new_columns()`. When a merge commit is rendered with `merge_layout == 0` (left-skewed), its first parent does not advance `graph->width`, so `graph->width - 2` ends up pointing at the column immediately to the left of the merge commit rather than at an existing right-side column. The branch that fuses an edge into `graph->mapping[graph->width - 2]` and resets `graph->edges_added = -1` was intended only for existing columns to the right of a merge (`idx < 0`), but it also fired when a later parent of the octopus matched that left-side column. This caused subsequent parents to be placed one slot too far left, leaving a `-1` in the final dashed-parent slot of `graph->mapping[]` and triggering an out-of-bounds access at `graph->new_columns[-1]` inside `graph_draw_octopus_merge()`.

The fix adds an `idx < 0` guard to the fusion condition so it only applies to existing non-merge columns, and inserts a defensive `BUG("octopus merge mapping uninitialized")` in `graph_draw_octopus_merge()` when the looked-up mapping index is negative. The commit also adds a regression test to `t/t4215-log-skewed-merges.sh` that constructs a left-skewed 4-parent octopus merge joined to an adjacent left column and verifies the expected `git log --graph --date-order` output.

The patch is small, well-scoped, and includes a targeted test that reproduces the crash/misrender, so it looks like a solid, ready-to-review fix for a real rendering bug in `git log --graph` output.

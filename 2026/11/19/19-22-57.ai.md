This is a bugfix targeting stale state in the protocol v2 handshake path in `connect.c`. The patch addresses a leak where the file-static `server_capabilities_v2` vector accumulates capability lines across multiple in-process handshakes without being cleared. Because `server_feature_v2()` and `server_supports_feature()` return the first matching entry in that vector, capabilities advertised by an earlier remote bleed into subsequent connections to different remotes within the same process.

The commit message spells out concrete failure modes: running `git remote show r1 r2` where r1 uses SHA-256 and r2 uses SHA-1 causes the second handshake to read r1's stale `object-format=sha256` line and abort with "mismatched object format". A stale `session-id` capability from r1 is likewise logged again for r2 even when r2 sets `transfer.advertiseSID` to false. The issue also surfaces on v0/v1 handshakes that skip `process_capabilities_v2()` entirely, because callers such as `get_bundle_uri()` may still query `server_supports_v2("bundle-uri")` afterwards.

The fix is minimal and defensive: `strvec_clear(&server_capabilities_v2)` is added at the top of both `discover_version()` and `process_capabilities_v2()` so every new handshake starts from an empty vector. The patch includes a regression test in `t/t5702-protocol-v2.sh` that creates two remotes with differing object formats and SID settings, runs `git remote show r1 r2`, and inspects trace2 output to confirm the `server-sid` event appears only for the remote that actually advertised it.

Overall this looks like a well-crafted, narrowly scoped fix with a clear reproduction scenario and a targeted test. It touches the connection-handling code shared by fetch, push, and remote-inspection commands, and is currently under review on the mailing list.

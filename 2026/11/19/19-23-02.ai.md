This is a bugfix targeting the attribute subsystem, specifically closing a symlink-traversal gap left by commit 2ef579e261 (attr: do not respect symlinks for in-tree .gitattributes, 2021-02-16). That earlier commit taught `read_attr_from_file()` in `attr.c` to open `.gitattributes` files with `open_nofollow()`, but `open_nofollow()` only guards the final path component. When a user passes an explicit path like `symdir/file` to `git check-attr` and `symdir` is a directory symlink, `prepare_attr_stack()` still traversed the leading symlink to read `symdir/.gitattributes`, and `builtin_object_mode_attr()` called `lstat()` across the link, allowing attribute lookups to escape the repository worktree.

The patch adds `has_symlink_leading_path()` checks in two places within `attr.c`: inside `read_attr_from_file()` when the `READ_ATTR_NOFOLLOW` flag is set (returning NULL if any leading directory is a symlink), and at the top of `builtin_object_mode_attr()` for the `GIT_ATTR_CHECKIN` direction (returning `ATTR__UNSET` if the path has a symlinked leading component). This aligns worktree attribute lookups with index lookups by ensuring no part of an explicit path traverses a symlink outside the repository.

The change touches only `attr.c` and the test script `t/t0003-attributes.sh`, where a new `SYMLINKS`-guarded test creates an external directory with a `.gitattributes` file, symlinks it as `symdir`, and verifies that both `attr_check_basic symdir/file` and `attr_check_object_mode symdir/file` return `unspecified` rather than reading through the link. The fix is narrow and self-contained, with no stated controversy; it hardens the existing no-follow behavior rather than introducing new policy.

This is a bugfix patch, specifically the second of four in Elia Pinto's v3 series addressing silent 32-bit integer truncation when Git processes files larger than 2 GiB. It targets the complete-rewrite code path used by `git diff -B`, where `count_lines()` and `emit_rewrite_diff()` bypass xdiff's size limits and receive file sizes and line counts as `int`. For files of 2 GiB or more, these truncate to negative values, causing `git diff -B --stat` to report zero changes and `git diff -B -p` to emit an empty hunk header (`@@ -0,0 +0,0 @@`) that `git apply` rejects while the diff command still exits successfully.

The patch widens the relevant parameters and accumulators to `size_t` throughout the path: `count_lines()` and `emit_rewrite_lines()` now take `size_t` sizes and return `size_t` counts, `struct emit_callback` fields for line numbers and blank-at-EOF markers become `size_t`, and `count_trailing_blank()` switches its counter and buffer size from `long`/`int` to `size_t`. The `long`-to-`size_t` change in `count_trailing_blank()` also fixes a latent bug on LLP64 platforms like 64-bit Windows, where `long` is 32-bit and could underflow the pointer for buffers over 2 GiB. Single line lengths remain `int` but are clamped via `cast_size_t_to_int()` since `emit_add_line()` and `emit_del_line()` still expect `int`.

Two EXPENSIVE tests are added to `t/t4022-diff-rewrite.sh`, both gated on 64-bit `size_t` and `long`: one verifies numstat and patch output for a 2 GiB file (expecting 536,870,912 lines), and the other checks numstat for a file with 2^31 lines. These require several GiB of disk and take minutes to run. The patch is unchanged in code from v2, which had already addressed Phillip Wood's earlier review feedback, so it is essentially waiting for his re-review to confirm the fix is complete.

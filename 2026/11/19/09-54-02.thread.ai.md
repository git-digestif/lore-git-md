Thread identity: standalone feature request (not a patch) from Jordan Kadish <jordankadish93@gmail.com> proposing branch-aware `.gitignore` rules on the Git mailing list, now with two replies: a substantive response from Hsieh Chin Fan <kernel@topo.tw> proposing a configuration-based alternative, and a brief surface-level reply from Ben Knoble <ben.knoble@gmail.com> citing an existing convention.

Core problem or goal: request for Git to support ignoring files conditionally based on the current branch name. Kadish describes a workplace scenario where a `settings.py` is passed around manually because it intentionally differs from `main`, and asks for two modes -- a whitelist approach (file ignored in every branch except a named one) and a blacklist approach (file ignored only in a specifically named branch). Stated motivation covers Django migration files, local settings, and compiled binaries that must exist on main or staging but stay out of local working trees. Hsieh Chin Fan argues that embedding branch-conditional rules in `.gitignore` is problematic because `.gitignore` is tracked, so branch-specific rules would propagate through merges (e.g., merging `feature` into `main` would carry the rules along), making behavior hard to reason about across branches.

Current status: conceptual proposal only; no implementation sketch, syntax proposal, or patch attached. No maintainer or reviewer response yet. Two alternative approaches have been suggested: Hsieh Chin Fan's configuration-based method and Ben Knoble's tracked-template convention.

Key technical details: Hsieh Chin Fan proposes using `includeIf "onbranch:..."` directives in `.git/config` to conditionally load a branch-specific config file, which sets `core.excludesFile` to a dedicated local ignore file (e.g., `.git/feature.ignore` containing `settings.py`). This keeps branch-specific ignore patterns entirely local to `.git/config` and untracked files rather than in the shared `.gitignore`. The branch check happens once at config-load time rather than per-file during ignore-pattern matching, avoiding performance concerns about evaluating branch names during pattern matching. Demonstrated behavior: `git status` on `main` reports `settings.py` as untracked, while on `feature/x` it is ignored, matching the requested whitelist/blacklist behavior without modifying the ignore engine. Ben Knoble points to the common convention of tracking an `.env.example` template that developers copy to a locally ignored `.env`, which solves similar local-override problems without core changes.

Open questions and loose ends: the merge-propagation problem of tracked `.gitignore` rules is identified as a key concern with the original proposal. Whether the configuration-based approach or the tracked-template convention fully satisfies all use cases without core changes remains open. No maintainer position on any approach recorded yet.

Participant positions: Jordan Kadish proposed the feature. Hsieh Chin Fan responded substantively, arguing against extending `.gitignore` syntax due to merge-propagation issues and demonstrating a working alternative using `includeIf "onbranch:..."` combined with `core.excludesFile`. Ben Knoble added a surface-level reply citing the `.env.example`/`.env` tracked-template pattern as prior art, without engaging with the branch-awareness mechanics, performance, or merge propagation. No Reviewed-by, Acked-by, or objections from maintainers yet.

Related work: the `includeIf` conditional-include feature (specifically the `onbranch:` condition), the `core.excludesFile` configuration key, and the tracked-template/local-override convention (`.env.example` copied to `.env`) are the relevant existing mechanisms cited.

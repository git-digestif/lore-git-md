This is a security bugfix for `git filter-branch` addressing a path-traversal vulnerability in the `--state-branch` handling. When `git filter-branch` resumes from a state branch and loads the `filter.map` blob, it previously wrote map entries to `../map/$from_commit` without validating that the commit identifiers were safe, allowing a malicious or corrupted state branch to escape the temporary map directory via entries containing slashes, backslashes, or `..` segments.

The patch modifies `git-filter-branch.sh` to read lines with `IFS= read -r` and validate both sides of each `from:to` mapping before writing. The `from_commit` must be non-empty lowercase hexadecimal, and `to_commit` may contain only lowercase hex digits and spaces (an empty value is permitted to represent pruned commits). Any violation causes the command to die with the message "Unable to load state from $state_branch:filter.map" rather than writing files outside the intended directory.

Tests in `t/t7003-filter-branch.sh` cover the rejection of path-traversing entries such as `../../escaped:injected` and backslash-containing keys, verifying both that the command fails and that no file escapes the map directory. The commit message references 4811dabed7 ("filter-branch: fix commit map init from state branch", 2026-10-02) as the recent change that restored the `from:to` ordering and introduced the parsing logic now being hardened.

Although `git filter-branch` is deprecated in favor of `git filter-repo`, it remains in the tree, so this closes a genuine injection vector for anyone still using the state-branch feature with untrusted input. The change is small, well-tested, and unlikely to be controversial.

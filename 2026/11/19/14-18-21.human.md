This is a bugfix for the SHA-1/SHA-256 interoperability layer, specifically the second patch in Adrian Ratiu's three-part v2 series. It fixes `git rev-parse --output-object-format` silently printing the wrong object ID when a compat mapping is missing.

The bug occurs when `extensions.compatObjectFormat` is enabled but an object lacks a compat ID -- for example, objects received via `index-pack` during fetch. In that case `repo_oid_to_algop()` fails to find a mapping and leaves the OID unchanged, so rev-parse prints the storage ID where the user expects the compat ID and exits successfully. The patch adds a return-value check so rev-parse now dies with "cannot map object %s to %s", matching the behavior of `git pack-objects` and other callers that already handle the failure.

The fix is narrowly scoped: it only applies when the user passes a single revision, since that is the only case where rev-parse passes the desired output hash explicitly. Range arguments like `A..B` do not use the output hash at all, and fixing those would require a larger change left for future work. The accompanying test in `t/t1500-rev-parse.sh` creates an unmapped object by writing it before enabling the compat config, then verifies that requesting the unmapped format now fails with the expected error.

This patch appears well-crafted and uncontroversial. It addresses a real correctness issue with a minimal, targeted change and includes test coverage that avoids fragile manual object-directory manipulation. Within the broader series, it sits between the crash fix for mismatched config values and the more debated change to unknown commit header handling.

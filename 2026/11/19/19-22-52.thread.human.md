Dominik Maier has sent a bugfix for `git mv` that closes a security-relevant hole in the symlink-leading-path protection introduced by commit 062d90b2a8. The problem lies in `cmd_mv()` in `builtin/mv.c`: when `git mv -f` is used and the destination resolves through a symlinked directory to a file that already exists on disk, the old code unconditionally jumped to `act_on_entry`, skipping both the `has_symlink_leading_path()` check and the sparse-checkout validation. The fix is a one-line change that turns the unconditional `goto act_on_entry` into `if (bad) goto act_on_entry`, so forced overwrites still run the remaining destination validation before proceeding.

The patch is accompanied by a regression test in `t/t7001-mv.sh` covering exactly this case: a `git mv -f` attempting to overwrite an existing file through a symlinked leading path now fails with "destination is beyond a symbolic link" and leaves the target file intact.

This is a v2 standalone performance patch from Maik Riechert that optimizes `git diff` when the fsmonitor daemon is active. It modifies `check_removed()` in `diff-lib.c` so that entries carrying the `CE_FSMONITOR_VALID` flag return immediately after `fake_lstat()` fills in the stat data, thereby skipping both the `has_symlink_leading_path()` call (which lstat()s every leading directory component) and the following `S_ISDIR()` check.

The commit message argues these skipped checks are unreachable for fsmonitor-valid entries: if a leading directory were replaced by a symlink, fsmonitor would report the change and `refresh_fsmonitor()` would clear `CE_FSMONITOR_VALID` for all entries beneath it, so the code path would never execute with the flag still set. The author notes that `preload_index()` already trusts this invariant by skipping such entries entirely, and that gitlinks are never marked valid so the directory check cannot trigger. The change builds on commit `4f3d6d0261` (2021), which previously eliminated the lstat() of the file itself for valid entries, leaving only the leading-path lstat() calls as overhead.

Compared to v1, this version incorporates the cleanup Junio C Hamano requested: the `stat_err` variable is removed and the `lstat()` call is inlined directly into the `if` condition. The reported performance improvement is a drop from 57ms to 26ms for `git diff HEAD` on Linux with 100,000 files, a no-op fsmonitor hook, and a warm cache.

Three new tests are added to `t/t7519-status-fsmonitor.sh`: one confirms the shortcut itself by replacing a parent directory with a symlink without informing fsmonitor (expecting empty output from `git diff-index --name-status HEAD`), and two verify that deletions are still detected when fsmonitor does report the directory, covering both `dir1` and `dir1/` (with trailing slash) in the hook output.

The patch remains under review with no integration branch assignment. Junio's earlier endorsement was explicitly conditional on the `CE_FSMONITOR_VALID` bit being trustworthy in all edge cases; this v2 addresses his stylistic feedback but leaves the central correctness assumption unchanged, so future discussion will likely focus on whether fsmonitor invalidation reliably covers every leading-path symlink replacement scenario.

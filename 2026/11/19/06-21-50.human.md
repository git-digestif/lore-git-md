This is a bugfix, specifically the fifth and final patch of Elia Pinto's v3 series addressing loose-object handling and size-truncation bugs on LLP64 platforms such as 64-bit Windows.

The patch fixes a heap overflow in `combine_notes_concatenate()` in `notes.c`. When two notes are concatenated and their combined size reaches 4 GiB or more, the old code computed the buffer length in an `unsigned long`, which is only 32 bits wide on 64-bit Windows even though the individual note sizes returned by `odb_read_object()` are 64-bit `size_t`. The resulting `buf_len` would truncate to a small value, causing `xmalloc()` to allocate far too little memory while `memcpy()` still copied the full contents of both notes, writing past the end of the buffer. The fix computes `buf_len` as a `size_t` using the overflow-safe `st_add3()`, then converts it via `cast_size_t_to_ulong()` only at the call to `odb_write_object()`, whose length parameter still requires `unsigned long`. On affected platforms this now dies cleanly with an error instead of silently writing a truncated blob.

The trigger is broader than just notes merges: merely displaying a notes tree containing multiple notes for the same object at different fanout levels, or fetching a notes ref, can invoke this code path. No automated test is included because reproducing the bug requires both a platform with a 32-bit `long` and notes exceeding 4 GiB; the commit message documents the scenario instead.

Within the series, this complements the earlier patches that fix similar `long`-versus-`size_t` mismatches in the loose object reader and `cat-file --batch`, but it targets the notes subsystem specifically. Junio C Hamano has reviewed and approved this patch ("Looking good"), and all maintainer-requested changes from earlier versions have been addressed in v3.

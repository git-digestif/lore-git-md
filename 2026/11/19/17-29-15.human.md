This is a **test infrastructure** patch (v2 of a single patch) that serializes `EXPENSIVE` tests in Git's shell test suite to prevent CI runners from running out of memory when tests execute in parallel.

The patch addresses a concrete and well-documented problem: when `GIT_TEST_LONG` is set and tests run under `prove --jobs` or the Makefile, multiple memory-intensive tests -- notably the 5GB filtered hash-object test in `t1007` and newer multi-gigabyte tests in `t1600`, `t4300`, and `t4141` -- execute simultaneously and exhaust the 16GB available on GitLab and GitHub CI runners, causing OOM kills and job timeouts. The author reproduces the hang and validates the fix with CI runs on both platforms.

Mechanically, the patch adds `acquire_expensive_lock_()` and `release_expensive_lock_()` to `t/test-lib.sh`. The lock is a directory at `$TEST_RESULTS_DIR/expensive.lock` created with `mkdir`, containing a `pid` file recording the holder's process ID so that stale locks from SIGKILLed scripts can be detected and taken over. `test_run_()` acquires the lock before any test whose prerequisites include `EXPENSIVE` and releases it afterward, with the release also wired into `die()`'s EXIT trap to handle interruptions. Non-`EXPENSIVE` tests in the same script continue running in parallel. The `t/README` documentation is updated to note that long tests may use significant memory and run one at a time.

Patrick Steinhardt reviewed the approach substantively -- tracing race conditions in the stale-lock detection and confirming TAP compliance of the status message -- and approved it while requesting minor refinements: making `owner` and `waited` local variables, and adjusting commit message wording. The author has acknowledged all feedback in this v2, incorporating the `local` declarations and comment tweaks, though a v3 with the remaining wording changes has not yet been sent. The patch looks well-motivated, thoroughly tested, and close to ready.

This is a maintainer review reply in an ongoing bugfix thread for a crash in `git apply --check` (assertion `patch->is_new <= 0` in `check_preimage()`). Junio C Hamano is providing substantive guidance to Tanga Joris on how `find_header()` in `apply.c` should handle malformed `diff --git` headers as the series prepares for a v4 iteration.

Junio clarifies that a legitimate `diff --git a/f b/f` line is always followed by extended header lines such as `rename from`, `old mode`, or similar, even for pure renames or mode-only changes; an empty `diff --git` section with no following headers is not something modern Git generates. He challenges Tanga's claim that Git "doesn't write such a line anymore" by asking whether Git has ever produced such output, but ultimately endorses the stricter approach: `find_header()` should diagnose a `diff --git` line with nothing after it as a corrupt patch rather than silently skipping it, which would make patch 1/3 of the series unnecessary and simplify patch 2/3.

The review draws an important distinction between three kinds of input. First, malformed `diff --git` lines within Git-generated patches should be rejected strictly. Second, non-patch material appearing between complete patches (allowing email commentary between file diffs) should continue to be ignored as before. Third, lines beginning with `diff` that are not `diff --git` (i.e., third-party diff output) follow different parsing code paths and should be left unchanged to avoid destabilizing existing handling of non-Git diffs.

Tanga has confirmed through testing that modern Git does not generate empty `diff --git` sections (verified with whitespace-only diffs, renames, and merges) and that existing `apply` and `am` tests pass with the stricter behavior. The thread is converging on a v4 that drops the memory-leak fix in `parse_git_diff_header()` in favor of immediate rejection of empty sections in `find_header()`, pending Junio's confirmation which this email largely provides.

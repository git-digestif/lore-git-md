This is the fourth patch in Ravi Mistry's five-part v4 series that overhauls Git's HTTP transport retry handling, and it extends retry logic to HTTP POST requests -- the actual data-transfer path used by `git fetch`, `git clone`, and partial-clone blob downloads.

Where previous patches in the series fixed the retry counter, added exponential backoff, and made retry status codes configurable, this patch tackles the gap that `post_rpc()` in `remote-curl.c` previously only retried authentication failures and aborted immediately on transient errors like 429 or 5xx. The author extracts the wait computation into a shared `http_retry_wait()` helper and applies it inside `post_rpc()`, but carefully restricts retries to read-only services (`git-upload-pack` and `git-upload-archive`) via a `can_retry_rpc()` whitelist. It explicitly excludes `git-receive-pack` (push), since retrying a non-idempotent push after a 502 could duplicate work on the server. The patch also defers the "RPC failed" error report until retries are exhausted, and re-attaches the `Content-Encoding: gzip` header when retrying a compressed request so the second attempt is not malformed.

The commit is well-motivated and addresses a concrete resilience problem when talking to busy hosting backends or reverse proxies. It includes solid test coverage: new scenarios in `t/t5584-http-429-retry.sh` verify that Protocol v2 POST requests retry 429 and configured 502 codes, that partial-clone lazy blob fetches retry transient 502s, that gzipped requests preserve their encoding header across retries, and that pushes are *not* retried. The documentation update in `http.adoc` clarifies that `http.maxRetries` now applies to both GET and these read-only POST requests.

Within the broader series, this is the piece that makes the retry machinery actually useful for the most common heavy operations -- clone and fetch -- rather than just metadata GETs. Combined with the earlier patches, it looks like a thorough, well-tested improvement, though the series still awaits final review on the architectural question of whether configurable non-429 retry codes should be a permanent feature.

This is the final patch of Ravi Mistry's five-part v4 series on HTTP transport retries -- a configuration default change that closes out the series by making `http.retryAfter` default to 10 seconds instead of 0.

Previously, when a server returned HTTP 429 without a `Retry-After` header, Git would retry immediately in a tight loop, which the commit message notes defeats exponential backoff and keeps hammering an already overloaded server. This patch sets the default initial delay to 10 seconds, producing a 10s, 20s, 40s progression (capped at `http.maxRetryTime`) when `http.maxRetries` is enabled. Tests that need immediate retries now set `http.retryAfter 0` explicitly.

The patch also handles the `Retry-After: 0` edge case: because libcurl's `CURLINFO_RETRY_AFTER` returns 0 both when the header is absent and when the server explicitly sends `Retry-After: 0`, the code now inspects the raw header via `curl_easy_header()` (available since libcurl 7.84.0) when the info value is zero or negative. This ensures an explicit "Retry-After: 0" or a past HTTP-date still triggers an immediate retry rather than falling back to the new 10-second default. A minor wording change drops "configured" from the error message about `http.retryAfter` exceeding `http.maxRetryTime`, since the default can now trigger that condition without explicit user configuration.

This patch preserves the two-phase structure that Junio C Hamano previously questioned -- patches 1 through 4 assume `http.retryAfter=0` while this final patch flips the default to 10 seconds. The series remains under review.

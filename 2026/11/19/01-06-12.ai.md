This is a **bugfix for Git v3 repository initialization**, the third iteration of a patch by brian m. carlson that corrects how `git init` selects the default object hash when built with `WITH_BREAKING_CHANGES=1`. The patch restructures `repository_format_configure()` in `setup.c` so that a hash explicitly given on the command line always wins, while environment (`GIT_DEFAULT_HASH`), config (`init.defaultObjectFormat`), and the build-time default (`GIT_HASH_DEFAULT`, which resolves to SHA-256 in breaking-changes mode) are only consulted for brand-new repositories or those with no detected hash algorithm. If a user attempts to reinitialize an existing repository with a different hash, the code now dies with "attempt to reinitialize repository with different hash" rather than silently switching algorithms, and a reinit on an existing repo preserves the original hash even if `init.defaultObjectFormat` specifies something else.

Compared to v2, this version removes a now-inaccurate comment about reinitialization safety and switches the new tests in `t/t0001-init.sh` to use the standard `$GIT_TEST_BUILTIN_HASH` variable instead of hardcoded expectations, covering three scenarios: default object format selection for new repos, refusal to reinitialize with a mismatched `--object-format`, and confirmation that reinitialization does not alter the hash when `init.defaultObjectFormat` disagrees. The patch touches only `setup.c` and `t/t0001-init.sh`, and addresses the issue reported by Adam Dinwoodie where `git init` incorrectly defaulted to SHA-1 even in Git v3 breaking-changes builds.

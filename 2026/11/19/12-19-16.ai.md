This is a review reply in the ongoing discussion of Adrian Ratiu's three-patch bugfix series (`[PATCH 0/3]`) addressing a crash when a submodule is a linked worktree. Adrian confirms a substantive control-flow issue that Junio identified in `[PATCH 3/3]`: when a linked-worktree submodule `sub` contains a nested submodule `inner` whose `.git` is a real directory, the recursive `submodule_uses_gitfile("sub")` returns 0, `absorb_git_dir_into_superproject()` runs recursively (absorbing `inner`), but `is_worktree` stays 0, so the later forced-move block can still rewrite `sub/.git` to a nonexistent `$GIT_DIR/modules/sub` path. Adrian reproduced this exact failure ("gitfile does not point to a valid repository") and agrees it is the same class of breakage the series fixes, just reached via the absorb path.

Adrian accepts Junio's suggested restructure of `submodule_move_head()` in `submodule.c`: after ensuring `path/.git` is a gitfile -- either because it already was one or because `absorb_git_dir_into_superproject()` just made it one -- the code should unconditionally call `validate_submodule_gitfile_dir()` and set `is_worktree` before the forced-move check, rather than only inside the existing `else` branch. He notes that after an absorb the git dir lands where `submodule_name_to_gitdir()` expects, so the validation always passes in that path, while linked-worktree git dirs are correctly detected and left untouched. He commits to implementing this restructuring in the forthcoming v2.

This is a cover letter for the third iteration of a four-patch bugfix series that fixes silent integer truncation when Git handles files or buffers larger than 2--4 GiB. The series remains under review; no merge status is reported.

The biggest change in v3 is that patch 1/4 no longer widens `hashwrite()` to accept a `size_t` count. Instead, following the design preference expressed by Junio C Hamano and brian m. carlson in the v2 thread, the three callers that can hand more than 4 GiB to `hashwrite()` at once -- `write_no_reuse_object()` and `copy_pack_data()` in `builtin/pack-objects.c` and `store_object()` in `builtin/fast-import.c` -- now loop and pass at most 4 GiB per call. This sidesteps the need to update the Rust FFI bindings in `src/csum_file.rs`, which still declare the parameter as `u32`. Patch 3/4 now also widens the `cnt` member of `struct spanhash` to `size_t`, addressing Junio's concern that the span count could wrap to zero on highly repetitive 4 GiB files and make populated buckets appear empty. Patch 4/4's commit message now explains why a `uintmax_t` total cannot overflow in practice (each counted line is at least one byte read) and documents the `graph_width` capping behavior, both of which Junio had asked for.

The series still touches the same core areas: the complete-rewrite path of `git diff -B` (patch 2/4, using `size_t` for sizes and line counts throughout `diff.c`), rename detection in `diffcore-delta.c` (patch 3/4), and diffstat totals plus `scale_linear()` graph scaling in `diff.c` (patch 4/4). Test coverage remains two EXPENSIVE tests in `t/t4022-diff-rewrite.sh` for multi-gigabyte rewrites and one cheap test in `t/t4052-stat-output.sh` for the `scale_linear()` overflow. Torsten Bögershausen's Tested-by trailer carries over to patch 4/4, whose code is otherwise unchanged from v2.

With the main design objections from v2 addressed, the series now looks technically settled pending re-review. The remaining loose end is whether Phillip Wood is satisfied with the v2 changes to patch 2/4, and whether any new issues surface now that the `hashwrite()` approach has shifted from type widening to chunked calls.

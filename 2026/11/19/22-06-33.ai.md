This is a maintainer reply to a standalone performance patch (v2) optimizing `git diff` with fsmonitor. Junio C Hamano responds to Maik Riechert's commit message by correcting one technical claim while endorsing the conclusion, then announces he will queue the patch.

Junio points out that the commit message's assertion that the `S_ISDIR()` check "cannot trigger" for gitlinks is slightly misleading. In `check_removed()` in `diff-lib.c`, `fake_lstat()` calls `st_mode_from_ce()`, which assigns `S_IFGITLINK` entries the mode `S_IFDIR | 0755`, meaning the `S_ISDIR()` check does in fact trigger for gitlinks. The check is safe only because an additional `S_ISGITLINK()` guard prevents `repo_resolve_gitlink_ref()` from being called. The overall conclusion -- that the shortcut is safe for `CE_FSMONITOR_VALID` entries -- remains unchanged.

With this correction noted, Junio states "Will queue. Thanks.", moving the patch from "under review" to queued for integration. This follows his earlier conditional approval from v1, which accepted the approach assuming the `CE_FSMONITOR_VALID` bit is trustworthy in all edge cases regarding leading-path symlink replacement.

For future discussion in this thread, the key unresolved substantive point remains whether fsmonitor invalidation reliably covers every scenario where a leading directory is replaced by a symlink, since `refresh_fsmonitor()` clearing the flag for entries beneath such a directory is the load-bearing assumption of the optimization. The patch builds on commit `4f3d6d0261` and adds tests to `t/t7519-status-fsmonitor.sh` covering both the shortcut behavior and deletion detection when fsmonitor reports directory changes.

This is a bugfix patch for LLP64 platforms (notably 64-bit Windows), specifically patch 2/5 of Elia Pinto's v3 five-patch series on loose object size handling. It widens the loose-object size type from `unsigned long` to `size_t` across the entire reading path in `object-file.c`, `object-file.h`, and `odb/source-loose.c`.

The bug arises because since commit c6a4629e32 (2026-06-15), `parse_loose_header()` reports object sizes as `size_t`, but downstream functions like `unpack_loose_rest()`, `map_fd()`, `unpack_loose_header()`, `check_stream_oid()`, and `odb_source_loose_map_object()` still accepted `unsigned long`. On LLP64 platforms where `long` is 32-bit but `size_t` is 64-bit, a loose object header claiming 4 GiB + 5 bytes causes the buffer allocation to truncate to 6 bytes while the caller retains the full 64-bit size value, leading `read_loose_object()` and similar callers to read far past the allocated buffer. The patch changes the signatures and local variables in these functions to use `size_t` consistently from file mapping through header parsing and inflation.

The commit message explains that no `st_add()` overflow check is needed on this path because the size is parsed with `st_mult()`/`st_add()` and the buffer is allocated with `xmallocz()` before any further arithmetic. There is no automated test because reproducing the bug requires allocating a buffer near 4 GiB before the short-stream check triggers; the commit message documents a manual reproduction using the `loose_obj()` test helper with a bogus header size of 4 GiB + 5 on Windows. Junio C Hamano reviewed the v2 version positively and the v3 commit message addresses his question about `st_add()` safety. This patch complements patch 1/5 (which adds post-inflation size validation) by ensuring the size type itself does not truncate before that validation runs.

This is a feature patch, specifically the third of five in Ravi Mistry's v4 series on HTTP transport retry handling. It introduces the `http.retryStatusCodes` configuration key and corresponding `GIT_HTTP_RETRY_STATUS_CODES` environment variable, allowing users to specify which HTTP status codes beyond 429 should trigger retries. The default remains "429", preserving existing behavior while enabling opt-in retries for transient 5xx errors such as 502, 503, and 504 that reverse proxies and CDNs may return under load.

The patch modifies `http.c` to add a new `is_retryable_http_code()` helper that parses the comma- or whitespace-separated list from the config and checks whether a given status code (constrained to the 400..599 range) appears in it. The `handle_curl_result()` function now calls this helper instead of hardcoding a check for 429, and `http_request_recoverable()` adjusts its warning messages to print the generic "rate limited" text only for 429 while using "HTTP <code>, waiting <N> seconds before retry" for other configured codes. When retries are exhausted on a non-429 code, the function returns `HTTP_ERROR` rather than `HTTP_RATE_LIMITED`. The `struct http_get_options` in `http.h` gains a new `long http_code` field populated by `http_request()` so that downstream retry logic can distinguish the specific status code. Configuration is read in `http_options()` and initialized from the environment in `http_init()`.

Documentation in `Documentation/config/http.adoc` updates the descriptions of `http.retryAfter`, `http.maxRetries`, and `http.maxRetryTime` to reference the new retryable set, and adds a dedicated section for `http.retryStatusCodes` that frames non-429 codes as a temporary workaround for buggy provider infrastructure rather than a permanent standard, addressing the architectural concern raised in earlier review rounds about ecosystem convergence on 429.

Test coverage lives in `t/t5584-http-429-retry.sh`, which gains five new test cases verifying that 502/503/504 are not retried by default, that configured codes are retried with appropriate warning messages, that `Retry-After` headers are honored for non-429 codes, that exhausted retries on a 502 report the actual error code rather than "rate limited", and that both the environment variable and `http.<url>.retryStatusCodes` urlmatch work correctly. The test helper `t/lib-httpd/http-429.sh` is extended to emit 502, 503, or 504 status lines based on URL patterns containing `*-status-502*`, `*-status-503*`, or `*-status-504*`, enabling the new test scenarios.

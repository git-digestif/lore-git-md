This is a **test** infrastructure patch, specifically the second version of a change that serializes `EXPENSIVE` tests in Git's shell test suite to prevent out-of-memory failures on CI runners. Kaartic Sivaraam authored it after observing that sanitizer jobs on both GitLab and GitHub hang and time out when `GIT_TEST_LONG` is set and memory-intensive tests run concurrently under parallel execution. The motivating culprits are the 5GB filtered hash-object test in `t1007` and newer multi-gigabyte tests in `t1600`, `t4300`, and `t4141` introduced by commits `9048b48fb`, `288266c11d`, and `55c54fd375`.

The mechanism adds `acquire_expensive_lock_()` and `release_expensive_lock_()` to `t/test-lib.sh`. The lock is a directory at `$TEST_RESULTS_DIR/expensive.lock` created with `mkdir`, containing a `pid` file that records the holder's process ID so that stale locks left by SIGKILLed scripts can be detected and reclaimed by waiters. `test_run_()` acquires the lock before any test whose prerequisite list contains `EXPENSIVE` and releases it after the test and cleanup finish; `die()` also calls the release function from its EXIT trap path. Non-expensive tests in the same script continue to run in parallel. The patch also updates `t/README` to document that long tests may use significant memory and disk and therefore run one at a time even under parallel execution.

Version two incorporates review feedback from Patrick Steinhardt: the `owner` and `waited` variables are now declared `local` inside `acquire_expensive_lock_()`, and wording in the commit message and comments avoids naming `prove --jobs` specifically since the Makefile and Meson also run tests concurrently. Steinhardt had approved the overall approach and traced the stale-lock race condition, which the author had already mitigated. The patch touches only `t/test-lib.sh` and `t/README`, adding 45 lines. It remains under review with no integration branch placement stated.

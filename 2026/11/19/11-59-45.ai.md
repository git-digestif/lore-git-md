This is a reply from Patrick Steinhardt to Junio C Hamano on patch 1/4 of his four-patch performance series, resolving the maintainer's open question about whether the reftable backend's `--dry-run` behavior was already correct or actually buggy. Patrick confirms that Junio's assumption is right: the pre-patch code writes the new table to disk but then calls `reftable_addition_destroy()`, which invokes `reftable_addition_close()` to unlink the table, so `--dry-run` was already semantically correct and produced no persistent on-disk changes. This means patch 1/4 is purely a performance optimization that eliminates wasted I/O rather than a correctness fix. Patrick states he will adapt the commit message to make this discard behavior explicit. The technical path involved is `reftable_be_reflog_expire` in `refs/reftable-backend.c` calling `reftable_addition_commit` only when not in dry-run mode, versus the old path that committed then destroyed. With this answer, the classification question raised by Junio is settled: reviewers can treat the patch as low-risk and performance-only.

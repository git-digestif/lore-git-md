This is the second patch in v4 of Ravi Mistry's five-part series improving Git's HTTP transport resilience. It introduces exponential backoff for HTTP 429 responses when the server does not send a Retry-After header, fixing the behavior where Git previously applied the same fixed delay on every retry attempt.

The core change modifies `handle_rate_limit_retry()` in `http.c` to accept a 1-based attempt count and compute the delay as `http.retryAfter * 2^(attempt - 1)`, doubling the wait on each subsequent retry while clamping at `http.maxRetryTime`. With the current default `http.retryAfter` of 0, behavior is unchanged (immediate retries), but when set to a positive value the progression becomes 1s, 2s, 4s and so on rather than repeating the base delay. Server-provided Retry-After headers continue to take precedence over this computed backoff.

The patch updates `Documentation/config/http.adoc` to describe `http.retryAfter` as the initial delay and clarifies that backed-off delays are capped at `http.maxRetryTime` rather than causing immediate failure. Three new tests in `t/t5584-http-429-retry.sh` verify the doubling sequence, the clamping behavior, and that explicit server headers still override the calculation.

This looks like a well-contained, clearly motivated fix. The commit message explains the rationale -- preventing Git from burning through retries too quickly against busy servers while keeping the first attempt fast -- and the test coverage appears thorough. As part of the larger series, this patch builds on the retry counter fix from patch 1/5 and sets up the 10-second default that patch 5/5 introduces.

This is a **test infrastructure** patch -- specifically version 2 of a change that serializes `EXPENSIVE` tests in Git's shell test suite to prevent out-of-memory failures on CI runners. Kaartic Sivaraam posted it after observing that sanitizer jobs on GitLab and GitHub hang when `GIT_TEST_LONG` is set and memory-intensive tests run concurrently under parallel execution, with culprits including the 5GB filtered hash-object test in `t1007` and newer multi-gigabyte tests in `t1600`, `t4300`, and `t4141`.

The mechanism adds `acquire_expensive_lock_()` and `release_expensive_lock_()` functions to `t/test-lib.sh`. Tests marked with the `EXPENSIVE` prerequisite acquire a lock directory at `$TEST_RESULTS_DIR/expensive.lock` before running; the lock contains a `pid` file so waiters can detect and reclaim stale locks left by killed processes. Non-expensive tests in the same script continue running in parallel, and the release is wired into `die()`'s exit trap to handle interruptions. The patch also updates `t/README` to document that long tests may use significant memory and therefore run one at a time even under parallel execution.

Version two incorporates all review feedback from Patrick Steinhardt, who had approved the overall approach. The changes are mechanical: `owner` and `waited` are now declared `local` inside the acquire function, and wording in comments avoids naming `prove --jobs` specifically since the Makefile and Meson also run tests concurrently. Steinhardt had traced a race condition in the stale-lock detection that the author had already mitigated via the `test -n "$owner"` check.

The patch touches only `t/test-lib.sh` and `t/README`, adding roughly 45 lines. It remains under review with no integration branch placement stated, standing at "approach approved, v2 posted with all feedback addressed."

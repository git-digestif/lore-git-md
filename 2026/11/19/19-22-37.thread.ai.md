Thread identity: security hardening patch from Dominik Maier <dmnk@google.com> addressing out-of-bounds reads and memory safety issues in the EWAH bitmap reader when loading corrupt `.bitmap` files. Thread type: single patch, not yet part of a series.

Core problem: `ewah_read_mmap()` in `ewah/ewah_io.c` previously trusted serialized header fields -- buffer size, RLW offset, and literal word counts -- without validating them against the actual mmap length. This allowed corrupt or malicious `.bitmap` files to trigger memory leaks, oversized reallocations, and out-of-bounds heap reads in `ewah_each_bit()`, `rlwit_init()`, `next_word()`, and `rlwit_discharge()`.

Current status: new patch under review; no integration branch assignment or maintainer feedback recorded yet.

Key technical details: the patch adds validation in `ewah_read_mmap()` rejecting zero or oversized `buffer_size` before mutating the bitmap struct or allocating, verifying the serialized RLW offset falls within the buffer and points to the final RLW header, and walking the RLW chain to ensure each header's `literal_words` fits within remaining buffer space. Defense-in-depth clamping against buffer size was added to `next_word()` and `rlwit_init()` in `ewah/ewah_rlw.c`. Test coverage added to `t/t5310-pack-bitmaps.sh` corrupting a pack bitmap in four ways (zero buffer size, 0xffffffff buffer size, RLW offset past buffer, literal-words count exceeding buffer) and asserting `git rev-list --test-bitmap` fails with "corrupt ewah bitmap" errors.

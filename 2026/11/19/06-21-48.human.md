This is a bugfix, specifically patch 3/5 of Elia Pinto's five-patch v3 series addressing loose object size validation and LLP64 truncation issues. It targets the streaming loose object reader `read_istream_loose()` in `odb/source-loose.c`, which previously streamed a loose object until zlib signaled end-of-stream without ever comparing the byte count against the size declared in the object header. As a result, `git cat-file blob` on a corrupt object could exit successfully while writing a different number of bytes than `git cat-file -s` reports.

The fix adds a `total_read` counter to the stream state, accumulates the bytes handed to the caller, and at `Z_STREAM_END` compares the accumulated total against `st->base.size`. On mismatch it sets `z_state` to `ODB_LOOSE_READ_STREAM_ERROR` and returns -1 silently, leaving the error message to the caller (for example, "unable to stream <oid> to stdout" from cat-file). This mirrors the post-inflation validation added by patch 1/5 for the non-streaming path, so both `git cat-file blob` and buffered reads now reject objects whose inflated size disagrees with their header. The v3 rework follows Junio C Hamano's design feedback: the function no longer calls `error()` directly and the `oid` struct member from v2 has been removed.

Unlike the LLP64-specific patches in the same series, this fix is cross-platform and comes with automated test coverage in `t/t1006-cat-file.sh`. The tests use the `loose_obj()` helper to create blobs with deliberately bogus header sizes -- one claiming far more bytes than the stream contains, one claiming far fewer -- and verify that `git cat-file blob` fails with the expected "unable to stream" error in both cases.

The patch is well-crafted and directly addresses a real correctness gap. Because it includes runnable tests and the maintainer has already signaled approval of the reworked approach in v3, this looks like a solid, merge-ready contribution that closes a genuine hole in loose object validation.

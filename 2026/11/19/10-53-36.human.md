This is a substantive review reply within Harald Nordgren's v14 five-patch series, closing the last major design disagreement over override semantics for the new `remote.<name>.fetchRefmap` configuration.

Phillip Wood confirms agreement with Junio C Hamano's proposal that any refspec carrying an explicit destination (`src:dst`) -- whether passed on the command line or found in `remote.<name>.fetch` configuration -- should ignore the refmap entirely, with the refmap (and thus `fetchRefmap`) applying only to destination-less refspec entries. This resolves the earlier standoff between implicit override via `src:dst` and an explicit `--refmap=""` opt-out, settling on the implicit approach as simpler and maintaining the clean default/override relationship between config and command-line options.

Phillip provides concrete examples of the intended behavior: both a command-line `--refmap` and a configured `remote.<name>.fetchRefmap` should cause `master` to be stored under `refs/test/master` when paired with a destination-less `remote.<name>.fetch` entry, and he suggests implementing this with a preliminary patch handling command-line destinations alongside tweaking the current patch for the config side. With both the maintainer and the key reviewer now aligned on this model, the series has cleared its final semantic hurdle, leaving only the strategic questions about partial merging and the implicit fallback behavior in Patch 3/5.

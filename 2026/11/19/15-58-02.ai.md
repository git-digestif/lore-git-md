This is **patch 4/5 of v4** of Ravi Mistry's series extending Git's HTTP transport retry handling, classified as a **feature** that brings POST request retries to `post_rpc()` in `remote-curl.c`. The series as a whole addresses four gaps in HTTP error handling (off-by-one retry counts, missing backoff, non-retryable 5xx codes, and lack of POST retries); this specific patch closes the POST gap while carefully scoping safety.

The patch extracts the wait-and-sleep logic from `http_request_recoverable()` into a new shared helper `http_retry_wait(long http_code, long slot_retry_after, size_t attempt)` in `http.c` (declared in `http.h`), which both the GET path and the new POST retry loop now call. In `remote-curl.c`, `post_rpc()` gains a retry loop gated by a new `can_retry_rpc()` whitelist that permits retries only for `git-upload-pack` and `git-upload-archive` (fetch/clone and partial-clone lazy blob fetches), explicitly excluding `git-receive-pack` (push) because retrying a non-idempotent push after a 502/504 risks duplicate processing on the remote. Error reporting is deferred: the old inline `error("RPC failed; ...")` inside `run_slot()` moves to a new `report_rpc_error()` that fires only after retries are exhausted or for non-retryable failures. The patch also fixes a gzip regression by re-appending the `Content-Encoding: gzip` header when retrying a compressed request, and updates `http.maxRetries` documentation to note that retries now cover read-only smart-HTTP POSTs.

Tests in `t/t5584-http-429-retry.sh` cover four scenarios: protocol v2 `git-upload-pack` POSTs retrying 429 and configured 502s (with correct warning messages and no "RPC failed" on success), partial-clone promisor lazy blob fetches retrying 502, gzipped POSTs preserving `Content-Encoding: gzip` across retries (verified via `GIT_TRACE_CURL` line counts), and confirmation that `git push` (`git-receive-pack`) is never retried on 429 or 502. The test helper `t/lib-httpd/http-429.sh` learns `*-post-only*` URL patterns that only fail on POST requests, plus draining of POST bodies before returning synthetic errors to avoid Apache connection resets.

Behavior change: when `http.maxRetries > 0` and the status code appears in `http.retryStatusCodes`, read-only POST requests now sleep and retry using the same exponential backoff (`http.retryAfter * 2^(attempt-1)`, clamped at `http.maxRetryTime`) as GET requests, while push POSTs remain fail-fast. The series remains under review; this v4 iteration has addressed Patrick Steinhardt's substantive concerns about POST retry safety, and the architectural debate over configurable retry codes versus strict 429 remains the open design question for Junio.

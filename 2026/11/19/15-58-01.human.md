This is **patch 3 of 5** in Ravi Mistry's v4 series on HTTP transport resilience -- a feature patch that introduces the `http.retryStatusCodes` configuration option to generalize retry handling beyond the hardcoded HTTP 429.

The patch replaces the hardcoded `results->http_code == 429` check in `handle_curl_result()` with a call to a new `is_retryable_http_code()` helper that parses the configured list (defaulting to `"429"` if unset). Users can now set `http.retryStatusCodes` to a comma- or whitespace-separated list such as `"429,502,503,504"` (also overridable via the `GIT_HTTP_RETRY_STATUS_CODES` environment variable) to retry transient 5xx errors from misbehaving proxies or CDNs. Warning messages now distinguish between the traditional "rate limited" wording for 429 and a numeric "HTTP 502, waiting N seconds before retry" style for other codes, and exhausted retries on non-429 codes return `HTTP_ERROR` rather than `HTTP_RATE_LIMITED`.

Within the larger series, this builds on patch 1/5 (which fixed the off-by-one retry counter and moved Retry-After extraction) and complements patch 2/5 (which adds exponential backoff). The documentation explicitly frames additional status codes as a temporary workaround while provider infrastructure converges on 429, addressing Patrick Steinhardt's architectural concern that configurable retry codes might discourage standardization. Tests in `t/t5584-http-429-retry.sh` verify that 502/503/504 are not retried by default, that configured codes are retried with appropriate warnings, that Retry-After headers are still honored for non-429 codes, and that the env var and URL-matching config work correctly.

The series remains under review awaiting Junio C Hamano's final decision; v4 has addressed all of Patrick Steinhardt's substantive v3 review points, including this generalization of retryable status codes. The patch appears well-crafted with clear commit messaging, thorough test coverage, and documentation that acknowledges the provisional nature of non-429 retry support.

This is a bugfix patch, specifically patch 3/4 of Elia Pinto's v3 series addressing silent 32-bit integer truncation in large-file handling paths. It targets rename detection in `diffcore-delta.c`, where `hash_chars()` previously accepted the buffer size as `unsigned int`, causing files of 4 GiB or more to have only a prefix hashed while the similarity score was still computed against the full (truncated) size. This mismatch causes true renames to be missed in `git diff -M`, `git log --follow`, and merge rename detection. Additionally, the span count stored in `struct spanhash.cnt` was `unsigned int` and could wrap to zero after four billion hash collisions on highly repetitive content, making a populated hash bucket appear empty.

The patch widens three integer types to `size_t`: the local `sz` variable in `hash_chars()` holding `one->size`, the `cnt` member of `struct spanhash`, and the local `dst_cnt`/`src_cnt` variables in `diffcore_count_changes()`. The `hashval` field remains `unsigned int` since it stays below `HASHBASE`. The commit message notes that the hash table holds at most 2^17 entries, so the larger `size_t` fields cost at most 1 MiB of additional memory per file. This directly resolves Junio C Hamano's review concern from v2 about `struct spanhash.cnt` wrapping to zero and causing missed renames.

No committed test accompanies the change because reproducing the bug requires a file of 4 GiB or more; the author instead verified the fix by simulating 16-bit truncation, demonstrating that `git diff --cached -M` would previously report "D a" and "A b" instead of "R099 a b" for renamed random and repetitive files respectively. The patch carries a `Helped-by` trailer from Junio C Hamano and touches only `diffcore-delta.c` with three line changes. Within the broader v3 series, this complements patch 1/4 (chunked `hashwrite()` calls in pack-objects and fast-import) and patch 2/4 (size_t widening in the complete-rewrite diff path), while patch 4/4 handles diffstat totals in `diff.c`.

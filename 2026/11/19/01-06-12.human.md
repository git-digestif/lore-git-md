This is a **bugfix for Git v3 preparation**, specifically correcting how `git init` selects the default object format when built with `WITH_BREAKING_CHANGES=1`. The patch is the third iteration of a fix by brian m. carlson addressing a report from Adam Dinwoodie that new repositories were incorrectly defaulting to SHA-1 instead of SHA-256 in breaking-changes mode.

The core change restructures `repository_format_configure()` in `setup.c` to establish a clear precedence: an explicitly chosen hash (from the command line) wins, otherwise the existing repository's hash is preserved during reinitialization, and only for brand-new repositories does the code fall back to the environment, then `init.defaultObjectFormat` config, and finally `GIT_HASH_DEFAULT`. This ensures that under `WITH_BREAKING_CHANGES=1` (and in Git 3.0), `git init` creates SHA-256 repositories by default while refusing to silently reinitialize an existing repository with a different hash algorithm, which would risk corruption.

The patch adds three new tests to `t/t0001-init.sh` covering the default object format selection, rejection of reinitialization with a conflicting hash, and verification that reinitialization does not override the existing hash based on config. The tests use the standard `$GIT_TEST_BUILTIN_HASH` variable rather than hardcoded algorithm names, per Patrick Steinhardt's earlier suggestion.

This is part of the broader effort to align Git's behavior with version 3.0 expectations, and the thread indicates the revised logic has already been accepted by Junio C Hamano for integration. The commit message is thorough, clearly explaining both the default-selection bug and the reinitialization safety issue, and the changes are well-contained within the repository setup subsystem.

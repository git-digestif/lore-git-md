This is the fifth and final patch in Elia Pinto's v3 five-patch bugfix series addressing loose object handling and size truncation bugs, primarily on LLP64 platforms. It is a bugfix and platform compatibility patch for a heap overflow in `notes.c` on 64-bit Windows, where `long` is 32-bit but `size_t` is 64-bit.

The patch fixes `combine_notes_concatenate()` in `notes.c`, which merges two notes read via `odb_read_object()`. The function previously computed the combined buffer length `buf_len` as `unsigned long` while the individual note sizes `cur_len` and `new_len` were `size_t`. On LLP64 platforms, when two notes total 4 GiB or more, the `unsigned long` arithmetic truncates to a small value, causing `xmalloc()` to allocate an undersized buffer while the subsequent `memcpy()` calls copy the full 64-bit lengths, writing far past the allocation. The bug can trigger simply by displaying a notes tree that contains multiple notes for the same object at different fanout levels, or when fetching a notes ref using the concatenate strategy.

The fix changes `buf_len` to `size_t` and computes it with `st_add3(cur_len, 2, new_len)` to provide overflow-safe addition. Because `odb_write_object()` still takes an `unsigned long` length parameter, the code passes the result through `cast_size_t_to_ulong()` only at that single call site. On affected platforms this now dies cleanly with an error instead of silently writing a truncated blob, pending a future update to the write API to accept `size_t`.

The change is minimal -- three insertions and four deletions in `notes.c` only. No automated test is included because reproducing the bug requires both a 32-bit `long` platform and notes exceeding 4 GiB; the commit message documents this limitation. The patch has received maintainer approval from Junio C Hamano and highlights the broader API constraint that `odb_write_object()` still uses `unsigned long` for its length parameter.

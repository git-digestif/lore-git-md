This is a security hardening patch for the EWAH bitmap reader, fixing out-of-bounds reads and memory issues when loading corrupt `.bitmap` files. The commit targets `ewah_read_mmap()` in `ewah/ewah_io.c`, which previously trusted serialized header fields -- buffer size, RLW offset, and literal word counts -- without validating them against the actual mmap length, leading to memory leaks, oversized reallocations, and out-of-bounds heap reads in `ewah_each_bit()`, `rlwit_init()`, `next_word()`, and `rlwit_discharge()`.

The patch introduces several validation layers: it rejects zero or oversized `buffer_size` values before mutating the bitmap struct or allocating memory, verifies that the serialized RLW offset falls within the buffer and points to the final RLW header, and walks the RLW chain to ensure each header's `literal_words` count fits within the remaining buffer space. As defense in depth, `next_word()` and `rlwit_init()` in `ewah/ewah_rlw.c` now clamp their pointer advancement against the buffer size rather than trusting the header fields.

The test suite in `t/t5310-pack-bitmaps.sh` gains a new case that corrupts a pack bitmap file in four distinct ways -- zero buffer size, 0xffffffff buffer size, RLW offset past the buffer, and a literal-words count exceeding the buffer -- and verifies that `git rev-list --test-bitmap` fails with appropriate "corrupt ewah bitmap" error messages. The commit message is thorough and the test coverage is concrete, suggesting a well-motivated fix for a real robustness gap in how Git handles malformed on-disk bitmaps.

This is a correctness bugfix within the ongoing ODB abstraction effort, specifically patch 2/6 in Justin Tobler's v2 series moving temporary object directory creation to transaction start. The patch fixes an inefficiency in `object-file.c` where the files backend issues a full hardware flush against a temporary file during transaction commit whenever a temporary object directory exists, regardless of whether batched fsync is actually enabled. Since `git-receive-pack` always creates a temporary object directory for its transactions, this meant unnecessary flushes were being performed even when objects were being synced individually or not synced at all.

The change extracts the flush logic into a new `flush_batched_fsync()` helper and gates the call behind `batch_fsync_enabled(FSYNC_COMPONENT_LOOSE_OBJECT)`, ensuring the barrier is only issued when there are actually pending writeout requests from batched fsync. The commit message also clarifies that batched fsync applies only to loose objects, noting that packfiles written during the transaction are either fully synced at write time or not synced at all and therefore do not rely on this flush. This addresses review feedback from the v1 cycle regarding the scope of batched fsync.

Within the broader six-patch series, this patch is preparatory cleanup that makes the eventual eager creation of the temporary directory (in patch 6/6) behave correctly by ensuring the flush semantics match the actual fsync configuration. The series itself remains under review with no Reviewed-by or Acked-by trailers yet, though it has incorporated feedback from both Patrick Steinhardt and Karthik Nayak. Karthik's fundamental design question about whether eager creation is architecturally justified over the lazy approach remains open, but this specific patch addresses the narrower concern about avoiding spurious fsync operations.

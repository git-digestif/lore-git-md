Thread identity: single-patch bugfix series (v1, no cover letter) from Dominik Maier <dmnk@google.com>, subject concerning corrupt packfile delta header parsing; thread type: security-hardening bugfix for packfile handling.

Core problem or goal: harden Git against malformed/corrupt packfiles by fixing two related defects in delta object header parsing. First, `get_size_from_delta()` in `packfile.c` inflates up to 20 bytes into the stack buffer `delta_head[]` but always passed `delta_head + sizeof(delta_head)` as the decoder's upper bound, so when zlib produced fewer bytes the header decoder read uninitialized stack memory. Second, the old `get_delta_hdr_size()` in `delta.h` used a do-while loop that dereferenced `*data` before checking bounds and returned a partial size when a varint's continuation bit was still set at the buffer boundary, which could make `patch_delta()` treat a truncated varint as a zero-byte size.

Current status: patch posted for review; no maintainer decision, Reviewed-by, Acked-by, or integration status recorded yet. Not in any integration branch as far as this thread states.

Key technical details: replaces `get_delta_hdr_size()` in `delta.h` with `decode_delta_hdr_size()`, which returns -1 on truncated varints, EOF, or `size_t` shift overflow. Both `get_size_from_delta()` (packfile.c) and `patch_delta()` (patch-delta.c) updated to check that return value. The `get_size_from_delta()` call site now bounds the decoder's `top` pointer by `stream.total_out` instead of the fixed 20-byte buffer end. Test coverage: new 86-line test in `t/t5300-pack-object.sh` constructing corrupted packfiles for three failure modes -- unterminated varints, out-of-bounds reads (20 bytes all with continuation bit set), and truncated headers -- verifying `git cat-file` rejects them.

This is a bugfix for `git archive --remote` argument validation ordering. The patch fixes a case where the `--add-file` and `--add-virtual-file` options are processed (including filesystem `stat()` calls) before the existing check that rejects these options in combination with `--remote`, which previously allowed confusing "File not found" errors to surface before the incompatibility error, and allowed `--no-add-file` to suppress the check entirely.

The fix modifies `archive.c` by introducing a new `struct add_file_data` that bundles the `archiver_args`, the `base` pointer, and the `is_remote` flag, passing this structure as the option callback value instead of just the `archiver_args`. Inside `add_file_cb()`, the callback now checks `data->is_remote` immediately and dies with "options '--add-file' and '--remote' cannot be used together" (or the `--add-virtual-file` variant) before any filesystem access occurs. The late check in `parse_archive_args()` that previously validated `is_remote && args->extra_files.nr` after `parse_options()` returns is removed, since the callback now handles rejection inline during option parsing.

The patch adds a test in `t/t5000-tar-tree.sh` verifying that `git archive --remote=. --add-file=no-such-file` fails with the incompatibility message rather than "File not found", and that appending `--no-add-file` after `--add-file` still results in the incompatibility error rather than success. This is a standalone single patch, not part of a larger series, and touches only the archive subsystem and its tar test script. The change is well-contained and addresses a real ordering issue in server-side argument handling for `git-upload-archive`.

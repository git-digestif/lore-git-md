This is a design-alternative reply within the `[PATCH v2 0/4]` UTF-8 bounds-handling bugfix series. Dirk Gouders responds to Andy Koppe's performance objection that the NUL-terminated wrapper `display_mode_esc_sequence_len(const char *s)` -- which calls `strlen()` upfront -- turns repeated SGR scanning from linear into quadratic time. Rather than keeping or deleting the wrapper, Gouders proposes a third option: change `display_mode_esc_sequence_len_counted()` to accept `size_t *len` instead of `size_t len`, modeled on `utf8_width()`'s optional remainder parameter. Passing NULL preserves NUL-terminated scanning, while a non-NULL pointer supplies the buffer length and receives the updated remainder (`*len -= p - s`) on return, avoiding the upfront `strlen()` for callers that already know the length.

The email includes an untested diff against `utf8.c` showing the conditional `end` computation (`end = s + *len` only when `len` is non-NULL), adjusted bounds checks in the SGR parsing loop, and the remainder update before returning `p - s`. The proposal targets the same symbols discussed throughout the thread: `display_mode_esc_sequence_len()` and `display_mode_esc_sequence_len_counted()` in `utf8.c`/`utf8.h`.

Per the thread context, this remainder-based compromise was not adopted. The series has settled on removing the NUL-terminated wrapper entirely and reverting to Junio C Hamano's v1 approach, where only the counted variant exists and callers such as `pretty.c` pass explicit lengths. The proposal nonetheless documents the API design space considered for bounded SGR scanning in `utf8.c`.

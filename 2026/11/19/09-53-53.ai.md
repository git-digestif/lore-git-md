This is a maintainer decision on a bugfix series, specifically resolving how to handle a dependency gap in the second patch. Patrick Steinhardt responds to Elia Pinto's question about the `[PATCH 0/2]` series fixing 4GiB+ file truncation on 32-bit `long` platforms (notably 64-bit Windows), stating a clear preference: hold back patch 2/2 entirely until the separate "use size_t for a few more object and buffer sizes" series lands, rather than casting the size through `cast_size_t_to_ulong()` in `add_index_file()` to make `git apply --index` die loudly instead of truncating. He asks the author to send a rebased version of the series once that dependency has landed.

The decision addresses the specific gap where `git apply --index` and `git am` would still silently truncate the indexed blob on affected platforms, because `add_index_file()` passes the file size to `odb_write_object()`, whose length parameter remains `unsigned long` until the size_t series changes it. While patch 1/2 (fixing `git archive` in `archive-tar.c`, `archive-zip.c`, and `archive.h`) stands alone, Patrick's response implies the apply fix in `apply.c` -- touching `create_file`, `create_one_file`, `try_create_file`, and `add_index_file` -- should wait for the `odb_write_object()` signature change to avoid a half-fixed state. No review feedback has yet been given on the technical correctness of either patch; this reply is purely about sequencing and dependency management.

Thread identity: standalone bugfix patch for the experimental `git history` command, authored by Aniket Gupta, based on master and currently under review. Thread type: single patch. Latest email is a point-by-point review reply from the author to Phillip Wood; no v2 posted yet.

Core problem or goal: prevent `git history` from rewriting branches that are checked out in other linked worktrees, which would leave those worktrees' index and working tree inconsistent with the moved branch. The fix aligns `git history` default behavior with the safety checks already present in `git branch -f` and `git rebase --update-refs`.

Current status: patch posted, not merged; no integration branch assignment mentioned. Junio C Hamano reviewed and concluded the patch still needs work before it is ready. The author has now acknowledged the feedback and described the planned v2 changes in detail; the thread is awaiting that v2.

Key technical details: introduces a new static function `reject_checked_out_branches()` in `builtin/history.c`, invoked from `setup_revwalk()` when the ref update action is `branches` (the default). The function resolves the current `HEAD` target via `refs_resolve_refdup()` to skip the current worktree's own branch, then iterates over local branches containing the original commit using `filter_refs()` with `FILTER_REFS_BRANCHES`. For each candidate it calls `branch_checked_out()` from `branch.h`, which returns a path if the branch is checked out in another linked worktree or is mid-rebase/mid-bisect. On detection the command errors with "cannot rewrite branch '%s' used by worktree at '%s'" and fails. The check also runs under `--dry-run`. On refusal the `advice.historyUpdateRefs` hint is emitted, suggesting `--update-refs=head`; this advice can be silenced via config. Documentation updated in `Documentation/config/advice.adoc` (worktree case added) and `Documentation/git-history.adoc` (documents the restriction). Tests added in `t/t3450-history.sh` covering: refusal when another worktree has a descendant branch checked out, refusal under `--dry-run`, silencing the hint, successful rewrite with `--update-refs=head` leaving other branches untouched, normal rewrite of the current worktree's own branch, and refusal when the current branch is mid-rebase or another worktree is bisecting. Junio C Hamano identified a critical edge case: in a bare repository whose `HEAD` points to a branch (e.g., `refs/heads/main`) that is checked out in a linked worktree, the current logic resolves `HEAD` to that branch and skips the safety check via the `continue` statement, allowing the command to rewrite the branch and leave the linked worktree out of sync. For v2, Gupta plans to abandon the name-based skip and instead query each linked worktree to determine whether any of them have the current branch checked out, which covers both the bare-repository case and the case of two worktrees checking out the same branch via `git worktree add --force`. He also plans to adopt the refactoring suggested by Phillip Wood: fold the check into `setup_revwalk()` by loading ref decorations earlier and extending `revwalk_contains_merges()` (or a renamed variant) to examine `DECORATION_REF_LOCAL` decorations for worktree conflicts, similar to `replay.c:replay_revisions()`. Gupta notes one wrinkle with this approach: the branch pointing at the rewritten commit itself is not part of the revision walk, so its decorations must be inspected separately, otherwise rewriting a commit that another worktree's branch points at would slip through. Additionally, Gupta reports that `--update-refs=head` currently updates the branch `HEAD` points to without checking whether that branch is being written elsewhere; he reproduced a problem where a fixup in one worktree left a staged change in another worktree on the same branch, and will add that check in v2. He confirms that all `git history` subcommands (`fixup`, `reword`, `split`, `squash`, `drop`) call `setup_revwalk()` before opening an editor, creating a commit, or updating a ref, so the refusal happens early in every case; a test exercising each subcommand is planned.

Open questions and loose ends: Phillip Wood raised two behavioral questions that Gupta has now answered: if a rebase is already running in the same worktree, `git history` is refused because `HEAD` is detached during rebase, so the branch under rebase is treated as a branch in use; `--update-refs=head` in that state rewrites only the detached `HEAD` and does not conflict with the in-progress rebase, which Gupta verified by running `fixup`, `reword`, `drop`, and `squash` followed by `git rebase --continue`. Wood also noted that preventing `git rebase` from rewriting a branch currently being rewritten by `git history` would be a desirable follow-up but can come later; Gupta agrees. Wood suggested improving the `advice.historyUpdateRefs` documentation to explicitly state that `git history` refuses to run because a branch is used by another worktree, and correcting the `git-history.adoc` wording to say "rewrite only the current branch"; Gupta agrees to both. Wood identified a limitation that `branch_checked_out()` only tracks a single worktree per ref, so multiple worktrees checking out the same branch might not all be detected, though he noted this does not need solving in this patch; Gupta confirms `branch_checked_out()` remains in use for the other candidate branches with this known limitation. Gupta will reword the commit message to drop the unnecessary "also" and to state plainly that staged changes appearing in other worktrees are created by `git history` itself. Junio C Hamano noted that the proposed commit message inaccurately claims the command skips "the branch that the current worktree has checked out" since bare repositories have no current worktree, and suggested clarifying in the log message that `drop` updates the worktree while `reword`, `split`, and `squash` preserve the tip tree and `fixup` incorporates staged changes; Gupta has agreed to amend the commit message accordingly in v2.

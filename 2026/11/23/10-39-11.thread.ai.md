Thread identity: standalone bugfix patch for the experimental `git history` command, authored by Aniket Gupta, based on master and currently under review. Thread type: single patch.

Core problem or goal: prevent `git history` from rewriting branches that are checked out in other linked worktrees, which would leave those worktrees' index and working tree inconsistent with the moved branch. The fix aligns `git history` default behavior with the safety checks already present in `git branch -f` and `git rebase --update-refs`.

Current status: patch posted, not merged; no integration branch assignment mentioned.

Key technical details: introduces a new static function `reject_checked_out_branches()` in `builtin/history.c`, invoked from `setup_revwalk()` when the ref update action is `branches` (the default). The function resolves the current `HEAD` target via `refs_resolve_refdup()` to skip the current worktree's own branch, then iterates over local branches containing the original commit using `filter_refs()` with `FILTER_REFS_BRANCHES`. For each candidate it calls `branch_checked_out()` from `branch.h`, which returns a path if the branch is checked out in another linked worktree or is mid-rebase/mid-bisect. On detection the command errors with "cannot rewrite branch '%s' used by worktree at '%s'" and fails. The check also runs under `--dry-run`. On refusal the `advice.historyUpdateRefs` hint is emitted, suggesting `--update-refs=head`; this advice can be silenced via config. Documentation updated in `Documentation/config/advice.adoc` (worktree case added) and `Documentation/git-history.adoc` (documents the restriction). Tests added in `t/t3450-history.sh` covering: refusal when another worktree has a descendant branch checked out, refusal under `--dry-run`, silencing the hint, successful rewrite with `--update-refs=head` leaving other branches untouched, normal rewrite of the current worktree's own branch, and refusal when the current branch is mid-rebase or another worktree is bisecting.

Open questions and loose ends: Phillip Wood raised two behavioral questions: what happens if a rebase is already running in the same worktree when the user invokes `git history`, and whether `--update-refs=head` attempts to update the current branch in a way that might conflict if that branch is being written elsewhere. He also noted that preventing `git rebase` from rewriting a branch currently being rewritten by `git history` would be a desirable follow-up but can come later. He suggested improving the `advice.historyUpdateRefs` documentation to explicitly state that `git history` refuses to run because a branch is used by another worktree, and correcting the `git-history.adoc` wording to say "rewrite only the current branch." He identified a limitation that `branch_checked_out()` only tracks a single worktree per ref, so multiple worktrees checking out the same branch might not all be detected, though he noted this does not need solving in this patch.

Participant positions: reported by Toon Claes and Nikita Bobko, suggested by Patrick Steinhardt. Phillip Wood provided a substantive review generally endorsing the change while raising the concerns above; he recommended a refactoring to avoid duplicating work: rather than having `reject_checked_out_branches()` perform a separate `filter_refs()` iteration, modify `setup_revwalk()` to load ref decorations earlier (noting they are already loaded later when replaying commits, so this adds no extra work) and then modify and rename `revwalk_contains_merges()` to both detect merges by examining `commit->parents->next` instead of using `--min-parents`, and to check that `DECORATION_REF_LOCAL` decorations are not checked out elsewhere, citing `replay.c:replay_revisions()` as an existing example of using decorations. He also suggested commit message wording changes: remove the word "also" and clarify that staged changes appearing in the other worktree are created by `git history` itself.

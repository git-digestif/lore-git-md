This is a substantive review from Phillip Wood on Aniket Gupta's bugfix that makes `git history` refuse to rewrite branches checked out in other worktrees. Phillip endorses the change as a useful improvement but probes several edge cases and suggests concrete implementation refinements. He asks what happens when a rebase is already running in the same worktree where the user invokes `git history`, and questions whether `--update-refs=head` might attempt to update the current branch even when that branch is being written elsewhere. He also flags a subtle limitation in `branch_checked_out()` -- it records only a single worktree per ref, so if multiple worktrees have the same branch checked out and the current worktree happens to be the recorded one, the check might miss another checkout -- though he notes this does not need solving in the current patch.

Rather than accepting the approach of a separate `reject_checked_out_branches()` function that filters refs independently, Phillip suggests a more efficient design: modify `setup_revwalk()` to load ref decorations earlier (which the code already does later when replaying commits), then extend `revwalk_contains_merges()` to check both for merges by examining `commit->parents->next` and for `DECORATION_REF_LOCAL` entries that are checked out elsewhere, pointing to `replay.c:replay_revisions()` as a reference example for using decorations. He also offers several documentation tweaks, noting that the word "also" is unnecessary in the commit message, that the advice documentation should clarify exactly what `git history` refuses to do, and that the man page should say "rewrite only" explicitly. He concludes by observing that preventing `git rebase` from rewriting a branch currently being rewritten by `git history` would be a sensible follow-up.

The review demonstrates deep familiarity with both the `git history` implementation and the worktree internals, engaging directly with algorithmic choices and citing specific functions and files. It is clearly substantive rather than surface-level, offering both correctness concerns and a cleaner architectural alternative.

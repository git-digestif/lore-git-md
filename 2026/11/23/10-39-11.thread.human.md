Aniket Gupta has posted a standalone patch to make the experimental `git history` command refuse to rewrite branches that are checked out in other linked worktrees, preventing the index and working tree in those worktrees from becoming inconsistent. The patch is under review but not yet ready for integration; Junio C Hamano identified a correctness bug in the bare-repository case where `HEAD` points to a branch checked out elsewhere, and Gupta has acknowledged this along with several commit-message improvements, promising a v2 that replaces the name-based skip with a worktree query and adds checks for `--update-refs=head`.

Phillip Wood has provided a substantive review generally endorsing the direction, suggesting a refactoring that folds the safety check into `setup_revwalk()` by examining ref decorations, while noting the edge case that the branch pointing at the rewritten commit is not part of the revision walk and must be inspected separately. Wood and Gupta have also resolved questions about behavior during an in-progress rebase in the same worktree, with Gupta confirming that all `git history` subcommands hit the check early via `setup_revwalk()`.

In the latest exchange, Wood flagged a new issue: when a rebase is active in the same worktree, `git history --update-refs=head` updates the detached `HEAD` without refusal, and that rewrite is silently discarded when `git rebase --continue` completes. Wood also added a follow-up item that `git history` should eventually refuse to run if another `git history` process is already rewriting the same branches. The thread remains open awaiting Gupta's v2, which is expected to address the bare-repository edge case, the `--update-refs=head` worktree check, the decoration-based refactoring, and the mid-rebase behavior.

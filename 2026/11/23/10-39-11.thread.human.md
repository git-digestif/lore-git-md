This thread tracks a standalone bugfix by Aniket Gupta for the experimental `git history` command, which currently allows the command to rewrite branches that are checked out in other linked worktrees, leaving those worktrees inconsistent. The patch adds a `reject_checked_out_branches()` check in `builtin/history.c` that refuses to proceed when a candidate branch is in use elsewhere, emitting an `advice.historyUpdateRefs` hint to use `--update-refs=head`. It remains under review and has not been picked up into any integration branch; Junio C Hamano has concluded it needs work before it is ready, and the author is preparing a v2.

Reviewers Phillip Wood and Junio C Hamano have both provided substantive feedback that Gupta has now acknowledged point-by-point. Hamano identified a correctness bug in the bare-repository case where `HEAD` resolution could wrongly skip the safety check, and Gupta has agreed to address this in v2 by querying linked worktrees directly rather than skipping the current branch by name -- a change that also covers the case of two worktrees checking out the same branch via `--force`. Gupta confirmed several behavioral details: a rebase already running in the same worktree causes refusal because `HEAD` is detached, and `--update-refs=head` in that state only rewrites the detached `HEAD`; he also acknowledged that `--update-refs=head` currently updates the branch `HEAD` points to without checking whether that branch is being written elsewhere, and will add that check in v2. He plans to fold the worktree check into `setup_revwalk()` by examining ref decorations, while noting the branch pointing at the rewritten commit itself must be inspected separately since it falls outside the revision walk. Commit message wording and advice documentation will be tightened as suggested, and the idea of preventing `git rebase` from rewriting a branch mid-`git history` is deferred as a follow-up. No Reviewed-by or Acked-by has been recorded yet; the thread is waiting on the v2 patch.

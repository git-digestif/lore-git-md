The thread concerns a bugfix for the experimental `git history` command, authored by Aniket Gupta, that prevents it from rewriting branches checked out in other linked worktrees. After Junio C Hamano and Phillip Wood identified several edge cases -- including a bare-repository scenario where the safety check is bypassed and a mid-rebase issue where `--update-refs=head` can silently discard history rewrites -- Gupta has outlined the fixes he plans for v2. He confirmed the patch needs work and is not yet ready for integration, with no Reviewed-by or Acked-by recorded.

In his latest reply, Gupta corrected his earlier claim about mid-rebase behavior: `git history --update-refs=head` is only refused when the target commit sits on the branch being rebased; otherwise it updates the detached HEAD mid-rebase, and that rewrite vanishes when `git rebase --continue` or `--abort` completes. He now commits to refusing the command in both modes whenever a rebase is active in the current worktree. This adds to the other planned v2 changes, including querying linked worktrees instead of skipping by branch name to fix the bare-repo case, adopting a decoration-based approach in `setup_revwalk()`, and adding checks that `--update-refs=head` does not conflict with branches being written elsewhere.

The thread remains open awaiting v2, which will also address commit message accuracy issues raised by Hamano and documentation wording suggestions from Wood. The underlying goal stays aligned with existing safety checks in `git branch -f` and `git rebase --update-refs`.

This thread concerns a standalone bugfix from Aniket Gupta for the experimental `git history` command, which currently risks rewriting branches that are checked out in other linked worktrees, leaving those worktrees with stale indexes and working trees. The patch adds a `reject_checked_out_branches()` check in `builtin/history.c` that errors out when a target branch is checked out elsewhere, aligning `git history` with the safety behavior already present in `git branch -f` and `git rebase --update-refs`. The series is currently under review and has not been merged.

Phillip Wood has now provided a substantive review, broadly endorsing the change while raising several points. He suggests a refactoring to improve efficiency: rather than performing a separate `filter_refs()` iteration to find checked-out branches, he recommends loading ref decorations earlier in `setup_revwalk()` and extending the existing merge-detection logic to also verify that local branch decorations are not checked out in other worktrees. He notes a limitation in the current approach -- `branch_checked_out()` only tracks one worktree per ref -- but considers that out of scope for this patch. Wood also asks what happens if a rebase is already running in the current worktree when `git history` is invoked, and whether `--update-refs=head` could conflict if the current branch is being written elsewhere.

On documentation, Wood recommends clarifying that the `advice.historyUpdateRefs` hint appears specifically because a branch is in use by another worktree, and tweaking `git-history.adoc` to say "rewrite only the current branch" rather than the current wording. He views preventing `git rebase` from clobbering a branch mid-rewrite by `git history` as a desirable follow-up for later. No maintainer decision or integration branch assignment has been announced; the patch remains open pending resolution of these review points.

This is a maintainer-feedback reply in an ongoing patch-series review. Adrian Ratiu is responding to Junio C Hamano's question about the commit-message wording in patch 2/3 of his v2 series fixing the `compatObjectFormat` interoperability layer.

Ratiu confirms that the fix covers invocations with multiple explicit single revisions such as `git rev-parse --output-object-format=sha1 main next`, but clarifies that it does not cover range arguments like `A..B` or `A...B` or shorthands like `rev^!` that `rev-parse` expands internally; he commits to clarifying this distinction in the v3 commit message. He also credits Patrick Steinhardt for the test design in `t/t1500-rev-parse.sh`, which Junio had praised as "clever and clean."

The underlying patch modifies `builtin/rev-parse.c` to check for a `< 0` return from `repo_oid_to_algop()` when handling `--output-object-format`, causing the command to die with "cannot map object %s to %s" instead of silently printing the storage OID when an object lacks a compat mapping. This aligns `rev-parse` with `git pack-objects` and other callers that already check the mapping result. The test uses a `RUST` prerequisite, initializes a SHA-256 repository, writes an object before enabling `extensions.compatObjectFormat` so it receives no compat mapping, then verifies that requesting the SHA-256 ID succeeds while the SHA-1 compat ID fails with the expected error.

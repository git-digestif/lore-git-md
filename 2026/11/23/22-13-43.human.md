This is a one-line bugfix hardening the HTTP fetch path, specifically patch 2 of 5 in Johannes Schindelin's v2 series addressing Coverity-flagged integer overflows across several subsystems.

The patch changes the type of the `posn` variable in `fwrite_sha1_file()` from `int` to `size_t` in `http.c`. The function tracks how many bytes have been written of a total buffer whose size is already expressed as `size_t`; when an HTTP response body exceeds `INT_MAX` (roughly 2 GB), the `int` counter would overflow, causing a heap under-read that could write adjacent memory contents to the temporary object file. The subsequent hash check would reject the corrupted object, so no bad data would enter the object store, but the under-read itself poses a theoretical information-leak risk. In practice curl delivers data in small chunks, making the overflow unlikely under normal configurations, but the type mismatch is a genuine defect worth fixing.

The commit message clearly explains both the technical mechanism and the practical limitations, noting that the attack surface requires a malicious server delivering an implausibly large single callback. Patrick Steinhardt and Junio C Hamano both reviewed and accepted the change, with Junio confirming the fix is correct after verifying that the underlying `xwrite()` clamps individual writes. An earlier suggestion to use `off_t` instead was rejected on the grounds that `posn` indexes a contiguous in-core buffer whose size is naturally expressed in `size_t`.

Within the larger series, this patch is one of the two that remained unchanged from v1 and is considered uncontroversial and ready for integration, unlike the revised wrapper and date-parsing patches that are still awaiting final acknowledgment.

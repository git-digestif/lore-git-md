This is the fifth and final patch in Adrian Ratiu's v2 series fixing crashes when a submodule is itself a linked worktree. While the previous patches hardened error handling and restructured the git dir setup logic, this one implements the actual fix: accepting a linked worktree as a valid submodule git directory during recursive checkouts.

The patch introduces `validate_submodule_worktree_dir()`, which uses `get_common_dir_noenv()` to detect when a submodule's git dir lives under `<common-dir>/worktrees/<id>` -- the layout Git creates for linked worktrees -- and validates that the common dir matches the submodule name. `setup_submodule_git_dir()` now returns an `is_worktree` flag, and `submodule_move_head()` uses it to skip two destructive operations that previously broke the worktree: rewriting the `.git` file to point at the superproject's expected modules path, and unsetting `core.worktree` during submodule removal. A git dir containing a commondir file but located outside the worktrees directory is rejected with a clear error.

Tests in `t/t2405-worktree-submodule.sh` verify that recursive checkout accepts a submodule worktree in both legacy and `extensions.submodulePathConfig` modes, handles a worktree containing a nested `.git` directory, and removes such worktrees cleanly without touching the main repository's `core.worktree`. `t/t7450-bad-git-dotfiles.sh` gains a test ensuring forged worktree git dirs are rejected with the new error message rather than a `BUG()` abort.

With this patch, the series resolves the original crash reported by Andreas Wendleder where `validate_submodule_legacy_git_dir()` hit a `BUG()` because linked-worktree paths do not end with the submodule name. The full five-patch v2 series remains under review awaiting Junio C Hamano's response; nothing has been merged to `master`, `next`, or `seen`.

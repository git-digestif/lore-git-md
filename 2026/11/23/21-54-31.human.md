This is a review reply in the ongoing discussion of a bugfix for the experimental `git history` command, which aims to stop the command from rewriting branches that are checked out in other linked worktrees. Aniket Gupta is responding to Phillip Wood's substantive review, confirming several edge cases and outlining changes planned for the next iteration. He clarifies that running `git history` while a rebase is already in progress in the same worktree is safely refused because `HEAD` is detached during rebase, and he notes that `--update-refs=head` in that state only touches the detached `HEAD`, leaving the rebase to complete normally. He also acknowledges a gap Wood identified: with `git worktree add --force`, two worktrees can share the same branch, and `--update-refs=head` currently lacks a check preventing it from rewriting that branch while another worktree has it checked out; he plans to add that guard in v2.

On the implementation side, Gupta agrees to refactor the check to avoid a second revision walk. Rather than iterating branches separately with `filter_refs()`, v2 will load ref decorations earlier in `setup_revwalk()` and fold the checked-out-branch detection into the existing merge-detection logic, examining `DECORATION_REF_LOCAL` decorations similar to how `replay.c` does. He notes one nuance: the branch pointing directly at the rewritten commit is not part of the walk itself, so its decorations need to be inspected separately to catch that case. He also confirms he will fix the commit message wording to drop an unnecessary "also", clarify that staged changes in the other worktree are created by `git history` itself, and document the mid-rebase refusal behavior.

The patch remains under review with no v2 posted yet, and Junio C Hamano has previously flagged a bare-repository edge case where the current logic incorrectly skips the safety check; Gupta has separately acknowledged that bug and plans to address it by querying worktrees directly rather than skipping by branch name. Overall the exchange shows a well-engaged author addressing concrete correctness and documentation concerns, suggesting the fix is on track but still needs another iteration before it is ready.

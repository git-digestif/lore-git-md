This is a review reply -- a surface-level comment on commit-message wording for a bugfix patch.

Christian Couder is responding to Elia Pinto's `[PATCH v3 2/4]`, which converts the word-diff buffer allocation counters in `diff.c` from `unsigned long`/`long` to `size_t` to prevent overflow on Windows. Couder agrees the code change is correct and says the patch otherwise looks good, but he objects to the commit message's framing. Pinto had written that if the `MAX_XDIFF_SIZE` limit were ever removed, `ALLOC_GROW()` would truncate the requested size and the following `memcpy()` would overflow the buffer. Couder points out that this hypothetical is misleading because many other components would break before that limit could safely go away, so the change should not be presented as making a higher limit safe.

Instead, Couder suggests justifying the type change purely as a consistency measure: the `alloc` member of `struct diff_words_buffer` should match the `size_t` type already used by the `mmfile_t` that `diff_words_append()` accumulates into, mirroring how `diff_words_fill()` already uses `size_t` for its own growth counter. This keeps the rationale focused on type alignment with the existing xdiff interface rather than on a hypothetical future limit change.

The exchange is part of the broader v3 series fixing 64-to-32-bit truncations on LLP64 platforms; this particular patch addresses a potential crash in the word-diff subsystem when processing very large buffers. The review is narrowly scoped to prose clarity, but it demonstrates engagement with the underlying allocation logic.

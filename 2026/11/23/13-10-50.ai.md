This is a substantive review of the bugfix patch for `git history` that prevents rewriting branches checked out in other worktrees. Phillip Wood generally endorses the change as a useful improvement while raising specific technical concerns and suggesting a refactoring to avoid duplicating work.

Wood first addresses the commit message wording, noting that "also" is unnecessary and clarifying that the staged changes appearing in the other worktree are indeed created by `git history` itself, not appearing spontaneously. He identifies a limitation in the current approach: `branch_checked_out()` only tracks a single worktree per ref, so if multiple worktrees check out the same branch and the current worktree happens to be the recorded one, other checkouts might go unnoticed, though he notes this does not need solving in this patch.

The review raises two open behavioral questions: what happens if a rebase is already running in the same worktree when the user invokes `git history`, and whether `--update-refs=head` attempts to update the current branch in a way that might conflict if that branch is being written elsewhere. Wood also suggests improving the documentation for `advice.historyUpdateRefs` to explicitly state that `git history` refuses to run because a branch is used by another worktree, and correcting the `git-history.adoc` wording to say "rewrite only the current branch." He notes that preventing `git rebase` from rewriting a branch currently being rewritten by `git history` would be a desirable follow-up but can come later.

The main technical recommendation concerns efficiency. Rather than having `reject_checked_out_branches()` perform a separate `filter_refs()` iteration over local branches, Wood suggests modifying `setup_revwalk()` to load ref decorations earlier (noting they are already loaded later when replaying commits, so this adds no extra work) and then modifying and renaming `revwalk_contains_merges()` to both detect merges by examining `commit->parents->next` instead of using `--min-parents`, and to check that `DECORATION_REF_LOCAL` decorations are not checked out elsewhere, citing `replay.c:replay_revisions()` as an existing example of using decorations.

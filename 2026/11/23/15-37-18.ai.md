This is a follow-up discussion email from Junio C Hamano within the `[PATCH 0/6] getwholeline should clear the buffer upon EOF` thread, clarifying the reasoning behind the series structure. He explains that he considered an alternative approach for patches 2 through 4: rather than demonstrating the bugs in `git shortlog`, `git clean -id`, and `git fast-import` with `test_expect_failure` cases and deferring the actual repair to patch 5, he could have inserted `strbuf_reset()` calls at the specific call sites in those early patches to make the tests pass immediately, then reverted those local workarounds in patch 5 once the root cause in `strbuf_getwholeline()` was fixed. He rejected that path because a series that adds code in an early step and immediately removes the same code in a later step is awkward and wasteful, and it would have allowed much shorter commit messages since the problematic code would be visible directly in the diff context. This confirms that the series deliberately separates the bug demonstrations (patches 2-4) from the root-cause fix (patch 5, which modifies `strbuf.c` to reset the output strbuf when `feof()` is detected) rather than interleaving temporary local fixes that would need reverting. The central open question from the thread remains whether any other in-tree or out-of-tree callers of the `strbuf_getwholeline()` family implicitly depend on the old behavior of preserving stale buffer contents after an EOF return, a point that future reviewers are expected to scrutinize when evaluating patch 5.

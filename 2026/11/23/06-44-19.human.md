This is a cover letter for a three-patch bugfix series targeting the bundle-uri subsystem. The series addresses a regression where `git clone` or `git fetch` dies entirely when a bundle list contains a relative URI that cannot be resolved, such as one with too many `../` components. Instead of failing the whole operation, the patches make the bundle code report the problematic entry and continue, falling back to fetching from the remote.

This v4 iteration incorporates feedback from the previous round. Patch 2 no longer anonymizes credentials in error messages -- a change requested after reviewers questioned its necessity -- but it retains the logic that names the original input URL in the error, which Patrick Steinhardt had argued was essential for diagnosability. Patch 3 contains no code changes but fixes an inaccurate commit message that previously claimed the clone continues with remaining bundles in all cases; it now correctly notes that a `--bundle-uri` list is rejected as a whole while server-advertised lists stop at the bad entry.

The author notes a minor merge conflict with `tb/config-null-values` currently cooking in `next`, which adds a null check in the same function that patch 3 touches; he reports having tested the merge successfully. The series remains under review and has not yet been queued in `seen`.

This is a **substantive review** from D. Ben Knoble, a self-described heavy submodule user responding to Junio C Hamano's invitation for experienced users to weigh in before the `^/` topic graduates from RFC to `next`. The review digs into security implications, implementation details, and documentation structure rather than surface issues.

Knoble raises a security-adjacent question about `check_submodule_url()` in `submodule-config.c`: he asks whether `^/` URLs traverse the same resolution path as `../` URLs (referencing commit `c44088ecc4` on credential handling for scheme-less URLs) and whether the new `skip_prefix(url, "^/", ...)` check adequately prevents `^/` URLs from being weaponized for credential injection in the same way `../` URLs were. He also disputes the test expectations in `t0060-path-utils.sh` for `^//evil.example.com` and `^/:evil`, arguing that naïve resolution would produce `host/evil.example.com/x.git` rather than the asserted failure mode.

On the implementation in `remote.c`, he expresses discomfort with the manual string munging in the new `root_relative_url()` function and its helpers (`skip_bracketed_host()`, `has_host()`), asking whether an existing dependency could handle URL parsing to reduce hand-rolled code. He also questions the logic in `resolve_relative_url_gently()` in `builtin/submodule--helper.c` that suppresses the "could not look up configuration" warning when `^/` is detected, noting that `^/` is nonsensical when the remote URL falls back to `$PWD`. He asks whether the architecture would allow local-path support to be added later without a rewrite.

Regarding documentation, he suggests restructuring the URL description in `Documentation/git-submodule.adoc` into a bullet list of URL forms (absolute URI, `^/` server-root path, `./` or `../` relative path) rather than the current inline conditional, and proposes that `Documentation/gitmodules.adoc` cross-reference `git-submodule.adoc` to avoid duplicating the explanation. He also asks whether the RFC trade-offs (shell escaping of `^`, ecosystem adoption by libgit2/JGit/forges) should be captured in the commit message rather than only in mailing-list archives, and questions whether "subgroup" is too GitLab-specific a term for test descriptions.

The review is constructive and probing but does not amount to an objection; it reads as detailed vetting from an experienced user examining edge cases and long-term maintainability before the topic enters integration testing.

Review reply in the `git history` worktree-safety bugfix thread. Aniket Gupta responds point-by-point to Phillip Wood's substantive review, confirming several v2 changes and adding new technical detail about edge cases.

Gupta confirms he will reword the commit message to drop the unnecessary "also" and to state plainly that staged changes appearing in other worktrees are created by `git history` itself. He also agrees to document explicitly in the `advice.historyUpdateRefs` text what `git history` refuses to do. On the open question of a rebase already running in the same worktree, Gupta reports that the command is refused because `HEAD` is detached during rebase, so the branch under rebase is treated as a branch in use; `--update-refs=head` in that state rewrites only the detached `HEAD` and does not conflict with the in-progress rebase, which he verified by running `fixup`, `reword`, `drop`, and `squash` followed by `git rebase --continue`.

For the current-branch check in v2, Gupta plans to move away from skipping the branch by name and instead query each linked worktree to see whether any has the current branch checked out. This covers both the bare-repository edge case Junio C Hamano identified and the case of two worktrees checking out the same branch via `git worktree add --force`. He notes that `branch_checked_out()` remains in use for the other candidate branches, with its known limitation of tracking only a single worktree per ref. Gupta also confirms that `--update-refs=head` does update the branch `HEAD` points to and currently performs no check that this branch is not being written elsewhere; he reproduced a problem where a fixup in one worktree left a staged change in another worktree on the same branch, and will add that check in v2.

On the refactoring suggestion, Gupta says he tried folding the check into `setup_revwalk()` by loading ref decorations earlier and extending `revwalk_contains_merges()` (or a renamed variant) to examine `DECORATION_REF_LOCAL` decorations for worktree conflicts, similar to `replay.c:replay_revisions()`. He adds one wrinkle: the branch pointing at the rewritten commit itself is not part of the revision walk, so its decorations must be inspected separately, otherwise rewriting a commit that another worktree's branch points at would slip through. He will adopt this approach in v2. Finally, he agrees that preventing `git rebase` from rewriting a branch currently being rewritten by `git history` is a worthwhile follow-up but can wait.

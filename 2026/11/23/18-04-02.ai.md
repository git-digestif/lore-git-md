This is a substantive technical review from Junio C Hamano in the ongoing RFC thread for the `^/` submodule URL syntax. He engages directly with the implementation in `remote.c`, identifying two specific parsing failure modes in the `skip_bracketed_host()` helper when the superproject remote URL contains local path components with `@[` sequences. With a remote like `host:dir/@[x]/repo.git`, the function scans past the first colon searching for `]`, causing the caller to fail to find the host separator and produce a "cannot resolve" error. Worse, with `host:dir/@[x]:y/repo.git`, the parsing yields a corrupt URL of the form `host:dir/@[x]:org/lib.git` instead of the intended `host:org/lib.git`. Junio suggests the fix likely requires not scanning for `@[` or `:` past the first slash in the path portion. He also raises a documentation terminology issue, noting that calling `^/` an "absolute path" is misleading for scp-style URLs like `git@host:group/super.git` that lack a leading slash after the colon, and suggests "paths relative to the server-root" as clearer wording. The review demonstrates detailed engagement with the string-parsing logic and identifies concrete edge cases that could produce malformed URLs or spurious failures, which is exactly the kind of hardening needed before this moves from RFC into integration testing.

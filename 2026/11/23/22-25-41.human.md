This is a follow-up in the ongoing review of v4 of the bundle-uri regression fix series, specifically addressing a minor edge case in patch 3/3. Junio C Hamano had noted that `bundle_list_update()` inserts a bundle into the hashmap before resolving its URI, so a bundle with an unresolvable relative URI would remain in the list with a NULL `uri` field, potentially causing a secondary "error: bundle '<id>' has no uri" message later in the process.

Aniket Gupta confirmed he can reproduce this: with a server-advertised bundle list containing a bad entry, the clone prints four errors instead of three, the extra one being the redundant "no uri" complaint. He agrees the additional error is unnecessary since the earlier messages already explain the unresolvable URI, and plans to fix this in v5 by dropping the bundle from the list when its URI cannot be resolved. He explicitly avoids hiding the check inside `fetch_bundle_uri_internal()` so that bundles advertised without any URI at all continue to be reported as before. He will add a test covering this case in the next iteration.

The series remains under review and has not been queued in `seen`; Derrick Stolee has already given an unconditional LGTM to v4, so this final cleanup is expected to land in v5 before the maintainer picks it up.

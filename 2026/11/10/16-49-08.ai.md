This is a **substantive review** of the third patch in Jasper Mayone’s four-patch series (v4) that extends `%(worktreepath)` in `ref-filter.c` to report the worktree path for branches being rebased or bisected. The series as a whole is a **bugfix and ref-filter enhancement** targeting the worktree subsystem, with the third patch being the most technically significant.

Phillip Wood’s review identifies a **critical performance regression** in the current implementation: the new helper function `branch_checked_out_worktree()` iterates over all worktrees for every ref, resulting in O(N*M) complexity (where N is the number of refs and M is the number of worktrees). This is a step backward from the old `ref-filter.c` implementation, which used a hashmap for O(1) lookups. Phillip suggests refactoring `branch.c` to use a hashmap for worktree lookups, mirroring the old implementation, and then exposing a function to retrieve the worktree path for a given branch. This would restore the original performance while maintaining the patch’s goal of avoiding code duplication.

The review is **constructive and narrowly focused** on this performance issue, without questioning the patch’s overall goal or correctness. The patch itself is well-motivated, thoroughly tested, and addresses a real gap in Git’s behavior (the mismatch between `%(worktreepath)` and how `git worktree add`/`git branch -d` treat rebasing/bisecting branches). It also removes ~50 lines of unused worktree-mapping machinery in `ref-filter.c` and introduces a **breaking change** (stopping `%(worktreepath)` from printing the `git_dir` of bare repositories), which is documented in both `git-for-each-ref(1)` and `git-branch(1)`.

Key technical details to note for follow-up discussion:
- The patch touches `ref-filter.c`, `branch.c`, and their documentation.
- The performance regression is in the `branch_checked_out_worktree()` helper, which is called for every ref in `get_worktree_path()`.
- The old `ref-filter.c` implementation used a hashmap (`ref_to_worktree_map`) for O(1) lookups, while the new implementation uses a linear scan over `checked_out_branches`.
- The patch is otherwise ready for integration, with no other substantive concerns raised in this review.

The series remains a **well-crafted fix** for a real problem, but this performance issue must be addressed before merging. The review’s suggestion (refactoring `branch.c` to use a hashmap) is a clear path forward.

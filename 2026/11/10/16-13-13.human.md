This is the second patch in an RFC series introducing a reusable early option-scanning API for Git's parse-options subsystem. The patch adds the core infrastructure for `parse_options_early_scan()`, a new function that scans command-line arguments for options marked with `PARSE_OPT_EARLY` without triggering side effects from full revision parsing.

The implementation touches `parse-options.c` and `parse-options.h`, adding roughly 250 lines of new code. The new API is designed to be generic: it takes an array of `struct option`, a callback function, and a set of flags, and returns the index of the first argument not consumed by the scan. The callback is invoked for each early option found, allowing the caller to handle it immediately. The patch also introduces helper functions like `parse_options_takes_argument()` and `lookup_long_opt()` to support the early scanning logic.

Test coverage is thorough. The patch adds two new test modes to `test-parse-options.c` (`--test-takes-argument` and `--test-early-scan`) and exercises them in `t/t0040-parse-options.sh`. The tests verify edge cases such as options with attached values (`--early=attached`), separate values (`--early separate`), `--end-of-options` and `--` delimiters, missing values, and default values for options marked `PARSE_OPT_LASTARG_DEFAULT`. The tests also confirm that the scanner stops at non-options, short options, and unknown options as expected.

The patch is well-structured and clearly motivated by the fragility of the current hardcoded approach in `rev-list` (addressed in patch 1). The API design is flexible, supporting both attached and separate values, and integrates cleanly with the existing parse-options machinery. The author explicitly invites feedback on the API, particularly on whether the complexity is justified by reusability and how to avoid hardcoding option lists in the future.

This is a solid foundation for the RFC. The implementation is careful, the tests are comprehensive, and the commit message clearly explains the goals and trade-offs. The main open question is whether the API will find broader use beyond `rev-list`, but the patch itself is ready for review.

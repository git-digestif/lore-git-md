This is a two-patch refactoring series for the `git reflog expire` command, splitting the work into a mechanical refactor (patch 1) and a deliberate behavior change (patch 2). The series consolidates the two separate loops (one for `--all`, one for named refs) into a single loop, then adds deduplication to ensure each reflog is expired only once.

Patch 1 (mechanical refactor) collects all refs—both from `--all` and command-line arguments—into a single `string_list` and processes them together. The core expiration logic (`refs_reflog_expire`) is unchanged, and the patch preserves all existing behavior: error reporting, exit status, output order, and handling of dynamic refs like `@{-1}`. The author reports full test suite passes, including reflog tests with reftable, SHA-256, and leak sanitization, confirming the refactor is behavior-preserving.

Patch 2 (deduplication) skips reflogs that have already been processed in the same run, eliminating the current behavior where a reflog specified twice (or covered by both `--all` and a command-line argument) is expired and reported multiple times. This is implemented by tracking processed reflogs in a hashmap during iteration, preserving the original output order. The commit message justifies this as a deliberate improvement rather than a bug fix, aligning with Junio’s earlier suggestion.

The series addresses feedback from v1, where Patrick Steinhardt requested clearer commit messages and splitting the work into two patches. The test coverage is thorough, and the changes are confined to `builtin/reflog.c` and a new test in `t/t1410-reflog.sh`.

Key technical details for follow-up discussion:

- Dynamic refs (e.g., `@{-1}`) are resolved during the loop via `repo_dwim_log`, conditional on the `item->util` flag.

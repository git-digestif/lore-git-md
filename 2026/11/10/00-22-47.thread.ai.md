Thread identity
Subject: [PATCH 0/4] odb: eagerly create tmp-objdir at transaction start
Series version: v1 (initial submission)
Originating author: Justin Tobler
Thread type: patch series (correctness/refactoring)

Core problem or goal
The series addresses a correctness gap in Git’s object database (ODB) transaction machinery. Currently, the temporary directory used during ODB transactions is created lazily on the first object write. This means some writes—those not using batched fsync—bypass the temporary directory entirely, risking inconsistencies if the transaction later fails or is rolled back. The goal is to make temporary-directory creation eager, ensuring *all* transactional object writes go to the temporary directory from the moment the transaction begins.

Current status
Under review; no prior versions of this series. The series is part of the ongoing ODB abstraction effort led by Patrick Steinhardt. It is based on commit `3c60ef1e38` (The 17th batch, 2026-11-08) with `jt/tmp-objdir-loose-idx-merge` merged in, placing it within the ODB transaction workstream.

Key technical details
- Files touched: `tmp-objdir.c`, `tmp-objdir.h`, `object-file.c`, `object-file.h`, `odb/source-loose.c`, and test `t0004-unwritable.sh`.
- New or renamed symbols: the default temporary directory prefix is renamed from `"bulk-fsync"` to `"transaction"` (patch 1/4); new helper function `flush_batched_fsync()` in `object-file.c` (patch 2/4); `tmp_objdir_create()` now preserves `errno` across cleanup (patch 3/4); `odb_transaction_files_prepare()` removed (patch 4/4).
- Behavior change: temporary directory creation moves from lazy (on first write) to eager (at transaction start) (patches 2–4/4); batched-fsync flush is now conditional on `FSYNC_COMPONENT_LOOSE_OBJECT` being enabled (patch 2/4).
- On-disk format: unchanged.
- Test coverage: `t0004-unwritable.sh` updated to reflect the new behavior and error messages.
- Net code change: 35 insertions, 100 deletions (79 insertions, 100 deletions in patches 1–3/4; 44 deletions in patch 4/4).
- Performance note: micro-benchmark shows a 7 % slowdown for a `git add` workload writing 10 000 loose objects, but such workloads are atypical for ODB transactions and the overhead is marginal in practice.

This is a **bugfix for the reftable backend** that also improves correctness in the traditional files backend. The patch implements the helper function agreed upon in earlier discussion, fixing a long-standing issue where reflog entries for HEAD (or any symref) record the wrong OID when the symref and its target branch are updated in the same transaction.

The problem is straightforward: when a transaction updates both a branch and a symref pointing to it (e.g., `refs/heads/y` and `HEAD`), the reflog entry for the symref should record the new OID of the branch. Currently, both backends resolve the target *before* the transaction commits, so they see either the old value or no value at all. The reftable backend, which writes all updates atomically, always sees the old state; the files backend, which applies updates sequentially, only gets it right if the branch update happens first.

The fix introduces `ref_transaction_resolve_new_oid()` in `refs.c`, a helper that looks up the new OID from the transaction itself if the ref is being updated, following symref chains within the transaction. If the ref is not being updated, it falls back to the usual `refs_resolve_ref_unsafe()`. Both backends now use this helper, ensuring the correct OID is recorded regardless of update order or backend.

The patch is well-motivated and narrowly scoped. It includes thorough test coverage that exercises both update and create operations, and both possible update orders (branch-first and symref-first). The commit message clearly explains the problem, the solution, and the limitations (moving the rest of the reflog logic out of backends is left for later). This looks like a clean, uncontroversial fix that addresses a real correctness issue.

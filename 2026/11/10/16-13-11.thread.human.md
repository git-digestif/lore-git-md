This thread introduces an RFC patch series by Azuama Odinaka Maximus proposing a reusable early option-scanning API for Git's `parse-options` subsystem. The goal is to improve how Git handles options that consume arguments during early scanning—particularly in `rev-list`—without triggering unwanted side effects from full revision-option parsing. The series consists of two patches: one modifies `rev-list` to use early option scanning, and the other introduces a generic API with tests.

The work is exploratory, addressing prior feedback about the fragility of hardcoded option lists in `rev-list`. While the implementation is modular and well-tested (with new test scripts like `t/t0040-parse-options.sh`), it retains some hardcoded options, and the broader motivation—beyond reusability—isn’t deeply explored. The author invites feedback on API design and integration with revision parsing, signaling this is an early-stage proposal rather than a polished solution.

Key technical details include changes to `parse-options.c/h`, `builtin/rev-list.c`, and new test coverage. The API introduces functions like `parse_options_early_scan()`, but the lack of a concrete use case (e.g., a specific command or workflow that would benefit) may limit immediate adoption. Open questions include how to eliminate hardcoded options and whether the API’s complexity justifies its reusability. No reviews or maintainer feedback have been posted yet.

This is the second patch in a two-patch refactoring series for `git reflog expire`. It deliberately changes behavior by ensuring each reflog is processed only once per command invocation, even if it appears multiple times in the input (e.g., via `--all` and a command-line argument, or as both `main` and `refs/heads/main`). The change is implemented by tracking processed reflogs in a hashmap during iteration, preserving output order without sorting.

The patch addresses a long-standing quirk where `git reflog expire` would process and report the same reflog multiple times if it was named more than once. For example, `git reflog expire --dry-run --verbose main main` would previously show the same prune message twice. The new behavior skips reflogs already processed in the same run, aligning with the principle of least surprise. The commit message justifies this as a deliberate improvement rather than a bug fix, noting that `--updateref` could theoretically cause edge cases where the first pass moves the ref, but the current implementation treats such cases as if the reflog were named only once.

The implementation is straightforward: a `string_list seen` tracks processed reflogs, and the loop skips any reflog already in the list. The patch adds a new test in `t/t1410-reflog.sh` to verify the deduplication behavior, comparing the output of `--all` alone with `--all main refs/heads/main main`. The test suite passes, including reflog tests with reftable, SHA-256, and leak sanitization, confirming the change does not introduce regressions.

This patch follows the mechanical refactor in patch 1, which consolidated the two separate loops (one for `--all`, one for named refs) into a single loop. The series was split at Patrick Steinhardt’s suggestion to separate the behavior-preserving refactor from the deliberate behavior change.

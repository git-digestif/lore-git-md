This is the first patch in an RFC series introducing a reusable early option-scanning API for Git's parse-options subsystem. It modifies `builtin/rev-list.c` to handle arguments during early option scanning, addressing a long-standing fragility in how `rev-list` processes options that consume arguments before full revision parsing begins.

The patch replaces a broken loop in `cmd_rev_list()` that previously failed to account for options with separate arguments (e.g., `--grep --pattern`). It introduces a new helper function, `rev_list_option_takes_argument()`, which uses `parse_long_opt()` to recognize revision options that take arguments and skips those arguments during the early scan. The function also handles `-n` and `--default` explicitly and stops scanning at `--` to avoid misinterpreting pathspecs as options. The hardcoded list of options in `rev_list_option_takes_argument()` is a temporary measure, as the author acknowledges in the commit message and cover letter.

Test coverage is added in `t/t6022-rev-list-missing.sh` to verify that `--grep` and `--author` arguments beginning with `--` are not mistaken for options during early scanning. The tests also ensure that `--grep --exclude-promisor-objects` does not trigger the `--exclude-promisor-objects` option, which was a known issue in the previous implementation.

The patch is well-motivated and directly addresses the NEEDSWORK comment in the code, which explicitly called out the fragility of the existing logic. The implementation is clean and modular, though the hardcoded option list remains a point of concern—this is flagged as a future improvement in the series. The test cases are thorough and cover edge cases that would likely break the old implementation.

This patch sets the stage for the second patch in the series, which generalizes the early option-scanning logic into a reusable API. The changes here are self-contained and could be merged independently if the broader API effort stalls, though the series' value is likely higher as a whole. The author’s invitation for feedback on API design suggests this is still a work-in-progress, but the patch itself is technically sound and addresses a real problem.

This is a brief but pointed exchange in the ongoing review of Thomas Bachem’s 15-patch series fixing Git segfaults on unvalued config keys. Junio C Hamano, the maintainer, pushes back on Phillip Wood’s earlier observation about patch 8/15 (`merge: handle NULL value for branch.<name>.mergeOptions`).

Phillip had noted that the patch treats missing values (NULL) and empty values (`branch.main.mergeOptions=`) differently—rejecting the former with `config_error_nonbool()` while silently accepting the latter—even though both result in an empty string being stored. Junio clarifies the distinction: a missing value (`branch.main.mergeOptions`) is a malformed boolean assignment (a config key without a value), while an empty value (`branch.main.mergeOptions=`) is an explicit, valid setting meaning “no merge options.” He argues that conflating the two would create inconsistency with true boolean variables (e.g., `branch.main.rebase`), where an empty value is not equivalent to a missing one.

The reply is concise and authoritative, effectively closing the design question for this patch. No code changes are needed; the current behavior is intentional and consistent with Git’s config-parsing conventions. The discussion now shifts back to the remaining open consistency concerns in patches 6/15, 7/15, and 14/15, where similar asymmetries between missing and invalid/empty values remain unresolved.

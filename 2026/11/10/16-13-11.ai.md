This is an RFC patch series introducing a reusable early option-scanning API for Git's parse-options subsystem. The series consists of two patches: the first modifies `rev-list` to handle arguments during early option scanning, while the second introduces a generic early option-scanning API with tests.

The author, Azuama Odinaka Maximus, acknowledges that the current implementation in `rev-list` relies on a hardcoded option list, which was flagged as fragile in prior review feedback. The series is exploratory, aiming to improve how Git handles early option scanning—particularly for options that consume arguments—without triggering unwanted side effects from full revision-option parsing. The commit messages and cover letter are clear about the goals and limitations, though the technical motivation for *why* this improvement is needed (beyond "reusability") isn't deeply explored.

Key technical details include:
- Files touched: `builtin/rev-list.c`, `parse-options.c`, `parse-options.h`, test helpers, and new test scripts (`t/t0040-parse-options.sh`, `t/t6022-rev-list-missing.sh`).
- The new API in `parse-options.h` introduces functions like `parse_options_early_scan()`, which are tested via `test-parse-options.c`.
- The `rev-list` patch demonstrates the API's application but retains a hardcoded list of options, which the author plans to address in future iterations.

The series appears well-structured for an RFC, with thorough test coverage and a focus on modularity. However, the reliance on hardcoded options and the lack of a concrete use case (e.g., a specific command or workflow that would benefit) may limit immediate enthusiasm. The author explicitly invites feedback on API design and integration with revision parsing, suggesting this is a work-in-progress rather than a final proposal. Likely points of discussion include how to avoid hardcoding options and whether the API's complexity justifies its reusability.

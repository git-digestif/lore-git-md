This is a **performance refactoring** in the `log` subsystem, specifically for `git log --follow` when dealing with merge commits. The patch is the fourth in a five-part series (v5) by Miklos Vajna, aiming to simplify how path propagation works across merge parents to pave the way for fixing a severe performance regression (28s → ~7min for `git log --stat --follow` on a single file in linux.git).

Toon Claes’s review here is **substantive**—he engages deeply with the logic changes, rewrites the conditional block to improve readability, and adds explanatory comments. His proposed refactor of the `is_merge` logic is functionally equivalent but makes the control flow clearer, which is a meaningful improvement for maintainability. The review is still in progress (he notes this is as far as he got today), but the feedback so far is constructive and focused on code clarity rather than nitpicks.

The patch itself removes a custom loop (`propagate_follow_pathspec_to_parent`) that was running redundant full diffs for every merge parent, even when the parent didn’t contain the followed path. Instead, it folds path propagation into the existing `log_tree_diff` parent loop, reducing code complexity (net -14 lines) without changing visible behavior. The performance fix is deferred to the next patch in the series, but this refactor is a necessary cleanup to make that fix feasible.

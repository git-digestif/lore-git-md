This is the second patch in an RFC series introducing a reusable early option-scanning API for Git's parse-options subsystem. It builds on the thread's stated goal of generalizing the hardcoded early option handling currently used in `rev-list` (demonstrated in patch 1) into a generic API that other commands can adopt.

The patch adds the core infrastructure for early option scanning: the `parse_options_early_scan()` function, its supporting helpers (`lookup_long_opt()`, `find_early_scan_option()`, `early_scan_one_option()`), and a new `PARSE_OPT_EARLY` flag to mark options that should be processed during early scanning. The implementation is thorough, with careful attention to edge cases like ambiguous abbreviations, `--end-of-options`, short options, and missing argument values. Test coverage is extensive, including new unit tests in `test-parse-options.c` and a new test script (`t/t0040-parse-options.sh`) that verifies the API's behavior across a variety of scenarios (attached vs. separate arguments, `--` delimiters, default values, and early termination).

Key technical details:
- Files modified: `parse-options.c` (core implementation), `parse-options.h` (API declarations), `t/helper/test-parse-options.c` (unit tests), and `t/t0040-parse-options.sh` (test script).
- New symbols: `parse_options_early_scan()`, `parse_options_takes_argument()`, `early_scan_fn` callback type, `enum early_scan_flags`, and internal helpers like `lookup_long_opt()`.
- Behavior: Early scanning stops at `--`/`--end-of-options`, skips short options and unknown long options, and respects `PARSE_OPT_EARLY` to determine which options to process. The API does not modify `argv` and returns the index of the first unconsumed argument.
- Subsystems affected: parse-options (primary), with potential future impact on revision parsing and command-line argument handling in other commands.

The patch is well-structured and appears technically sound, with clear commit messages and comprehensive test coverage. The reliance on `PARSE_OPT_EARLY` to mark options for early scanning is a reasonable design choice, though the thread's open question about eliminating hardcoded option lists (raised in patch 1) remains unaddressed here. The API's complexity is justified by its flexibility, but its reusability hinges on whether other commands will adopt it—something not yet demonstrated in this series. Likely discussion points include the trade-off between API generality and the added complexity, and whether the `PARSE_OPT_EARLY` flag is the most intuitive way to mark options for early processing.

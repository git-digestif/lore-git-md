Thread identity: Bug report about geometric maintenance strategy in Git 2.54 causing commit-graph corruption after pruning unreachable commits. Originating author: Christoph Weiss. Thread type: bug report.

Core problem or goal: The `geometric` maintenance strategy (now the default in Git 2.54) prunes unreachable commits but fails to update the commit-graph, leaving it in an inconsistent state where `git fsck` reports dangling commits and a corrupted commit-graph chain. This regression was introduced when the default maintenance strategy switched from `gc` to `geometric` in Git 2.54.

Current status: Maintainer Patrick Steinhardt has acknowledged the report and proposed a fix direction: moving commit-graph generation into `odb_optimize()` so the code can detect whether objects were discarded during maintenance and conditionally rewrite the commit-graph only in that case. The fix is blocked on his in-flight series making commit-graphs pluggable as an implementation detail of the object database backend landing first to avoid conflicts; once that prerequisite lands, he plans to send a patch series addressing this issue. No patch has been sent yet and nothing has been merged.

Key technical details: Subsystems touched: commit-graph (`commit-graph write --reachable --split`), refs (`update-ref`), object storage (`repack -ad`, `pack-objects`), and the ODB abstraction layer (`odb_optimize()`). Key config/settings: `maintenance.strategy=geometric`, `gc.writeCommitGraph`, `--split` commit-graph chain. New vs. old behavior: The `geometric` strategy prunes unreachable commits but does not update the commit-graph, while the `gc` strategy (pre-2.54 default) maintains consistency. Proposed new behavior: commit-graph regeneration would be triggered by detecting discarded objects during `odb_optimize()`. On-disk format impact: The commit-graph chain becomes corrupted, affecting operations relying on it (e.g., `git log --graph`, reachability checks). Test coverage: The reproduction script is self-contained and verifies the issue via `git fsck` before/after maintenance.

Open questions and loose ends: The root cause direction is identified (geometric strategy skips commit-graph updates after pruning), but the actual fix is pending the pluggable commit-graph ODB series. Scope remains unclear: whether this affects all geometric maintenance operations or only specific scenarios (e.g., early prune). Workaround options (disabling `gc.writeCommitGraph` or reverting to `gc` strategy) remain the only immediate mitigation. Priority is high given the default strategy change in 2.54 could impact many users upgrading.

Participant positions: Patrick Steinhardt (maintainer-level contributor driving the ODB abstraction effort) acknowledged the report and proposed moving commit-graph generation into `odb_optimize()` with conditional regeneration based on discarded-object detection; he stated the fix is blocked on his prerequisite series landing first.

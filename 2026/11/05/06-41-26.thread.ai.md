Thread identity: Bug report about geometric maintenance strategy in Git 2.54 causing commit-graph corruption after pruning unreachable commits. Originating author: Christoph Weiss. Thread type: bug report.

Core problem or goal: The `geometric` maintenance strategy (now the default in Git 2.54) prunes unreachable commits but fails to update the commit-graph, leaving it in an inconsistent state where `git fsck` reports dangling commits and a corrupted commit-graph chain. This regression was introduced when the default maintenance strategy switched from `gc` to `geometric` in Git 2.54.

Current status: Newly reported; no prior discussion or patches referenced. The issue is confirmed via a self-contained reproduction script that demonstrates the corruption after running `git maintenance run --auto` with `maintenance.strategy=geometric`. The old `gc` strategy does not exhibit the problem.

Key technical details:
- Subsystems touched: commit-graph (`commit-graph write --reachable --split`), refs (`update-ref`), object storage (`repack -ad`, `pack-objects`).
- Key config/settings: `maintenance.strategy=geometric`, `gc.writeCommitGraph`, `--split` commit-graph chain.
- New vs. old behavior: The `geometric` strategy prunes unreachable commits but does not update the commit-graph, while the `gc` strategy (pre-2.54 default) maintains consistency.
- On-disk format impact: The commit-graph chain becomes corrupted, affecting operations relying on it (e.g., `git log --graph`, reachability checks).
- Test coverage: The reproduction script is self-contained and verifies the issue via `git fsck` before/after maintenance.

Open questions and loose ends:
- Root cause: Why does the `geometric` strategy skip commit-graph updates after pruning unreachable commits?
- Scope: Does this affect all geometric maintenance operations, or only specific scenarios (e.g., early prune)?
- Workaround: Is disabling `gc.writeCommitGraph` or reverting to the `gc` strategy the only mitigation?
- Priority: Given the default strategy change, this could impact many users upgrading to 2.54.

Participant positions: None yet (initial report). No reviews, acks, or objections recorded.

Related work: The geometric repack logic was introduced in Git 2.54 as part of Patrick Steinhardt and Taylor Blau's repack machinery overhaul. This bug may require coordination with that effort. No dependencies on external tools or prior versions mentioned.

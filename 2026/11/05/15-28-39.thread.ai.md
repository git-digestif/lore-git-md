Thread identity: patch series titled "bundle-uri: skip unresolvable relative URIs instead of dying", v4, authored by Aniket Gupta. Thread type: bugfix series targeting a regression in the bundle-uri subsystem (introduced in Git 2.41).

Core problem or goal: fix a regression where `git clone` or `git fetch` dies when encountering a bundle list containing an unresolvable relative URI (e.g., too many `../` components). The goal is to refactor URI-handling code to skip problematic bundles with an error message instead of failing the entire operation.

Current status: v4 posted, rebased onto current master without conflicts. The core regression fix (skipping unresolvable URIs) is uncontested and technically complete. In v4, patch 2/3 has been retitled and simplified: the credential-anonymization logic has been dropped entirely at Derrick Stolee's suggestion, while the portion that names the original input URL in error messages is retained per Patrick Steinhardt's diagnosability concern. Patch 3/3 carries a corrected commit message clarifying that for a server-advertised bundle list, parsing stops at the bad entry and earlier bundles are still used, whereas a list passed via `--bundle-uri` is rejected as a whole; in both cases the operation falls back to fetching from the remote. Derrick Stolee has given an unconditional LGTM to the series. Junio C Hamano has reviewed patch 3/3, praising the rewritten commit message but raising a minor edge-case concern (see open questions). The series awaits a planned v5 addressing that edge case; merge status remains under review, not yet queued in `seen`.

Key technical details:
- Files touched: `remote.c`, `remote.h`, `bundle-uri.c`, `t/t0060-path-utils.sh`, `t/t5750-bundle-uri-parse.sh`.
- New symbols: `relative_url_gently()` helper function (non-dying variant of `relative_url()`), introduced in patch 1/3, which returns NULL and populates a `strbuf` error message on failure. The original `relative_url()` is now a thin wrapper that calls `relative_url_gently()` and dies if it fails.
- Internal changes: `chop_last_dir()` helper (modified in patch 1/3) now returns -1 without dying, enabling graceful error propagation. `bundle_list_update()` (modified in patch 3/3) now initializes a `struct strbuf err`, passes it to `relative_url_gently()`, and on NULL return logs the error via `error()` and returns -1, causing the bundle entry to be skipped instead of aborting the entire operation.
- Patch 2/3 specifics: `relative_url_gently()` in `remote.c` now formats the original input parameter `remote_url` in its error message rather than the intermediate partially-stripped `remoteurl` buffer, so that with a base URL like "./a/b" and excessive "../" components the message names the full original URL (e.g., `https://host.example/a`) instead of confusingly reporting `cannot strip one component off url '.'`. A unit test in `t/t0060-path-utils.sh` asserts that `test-tool submodule resolve-relative-url` produces the expected fatal message containing the unmodified input URL.
- Patch 3/3 specifics: updates `t/t5750-bundle-uri-parse.sh` to replace a `test_must_fail` expectation with checks for the specific non-fatal error messages -- `error: cannot strip one component off url '<uri>'` followed by `error: bad line: 'bundle.three.uri=../../bundle.bdl'` -- and verifies that the parser still produces output for the valid entries, resolving a long-standing TODO in that test.
- Behavior change: unresolvable relative URIs in bundle lists are now skipped with an error message that includes the original input URL, rather than causing the operation to die. The implementation stops parsing the bundle list at the bad entry (for server-advertised lists, earlier bundles are still used; for lists provided via `--bundle-uri`, the whole list is rejected) and falls back to fetching from the remote.
- Test coverage: expanded unit test in `t0060-path-utils.sh` and updated bundle-uri tests in `t5750` (verifying non-fatal error reporting and continued use of valid bundles).
- On-disk format: no changes.
- Subsystem: bundle-uri (introduced in Git 2.41).
- Minor textual conflict with `tb/config-null-values` currently in `next` (adds a `!value` check in `bundle_list_update()` just above the modified line); author confirmed coexistence with the `!value` check placed first and verified with t0060, t5558, and t5750.

Open questions and loose ends:
- Junio C Hamano (v4, patch 3/3) raised a minor edge-case concern: `bundle_list_update()` inserts the bundle entry into the `list->bundles` hashmap before attempting URI resolution via `relative_url_gently()`. When resolution fails and the function returns -1, the entry remains in the hashmap with its `uri` field set to NULL. If valid bundles preceded the bad entry, the later iteration in `fetch_bundle_uri_internal()` over `list->bundles` could emit a secondary "error: bundle '<id>' has no uri" message before the clone falls back to the remote fetch. Aniket Gupta has confirmed reproducing this issue and agrees the additional error is redundant. He proposes a fix for v5: remove the bundle from the hashmap when its URI cannot be resolved (tested locally with no change in clone behavior and passing bundle-uri tests), while deliberately not suppressing the error inside `fetch_bundle_uri_internal()` so that bundles advertised without any URI are still reported as errors. He commits to implementing this cleanup and adding a test case in the next iteration.
- The policy debate on credential anonymization in error messages is resolved in v4 by dropping the anonymization entirely; the original URL is now preserved in error messages for diagnosability.
- A potential follow-up enhancement to add a configuration toggle restoring the old die-on-error behavior is explicitly deferred as a `#leftoverbits` item; Derrick Stolee has confirmed it does not need to be included in this series (low-priority, non-blocking).

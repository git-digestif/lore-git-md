This is a substantive review by Jeff King (Peff) of the second patch in Patrick Steinhardt’s two-patch bugfix series for loose object database (ODB) cache invalidation during `git merge`. The series was previously approved and ready for merging, but Peff’s email raises deeper architectural concerns about the root cause and broader implications of the bug.

Peff acknowledges the immediate fix works and doesn’t make anything worse, but argues the problem is symptomatic of a larger design issue: **any code path using `QUICK` object existence checks (which tolerate false negatives) can trigger unnecessary and failing fetches from promisor remotes if the local object store changes after the cache is populated**. The current patch only addresses one specific case—newly written loose objects during `git merge`—but similar issues could arise in other scenarios, such as:
- Objects migrating from loose to packed during repacking.
- Objects written by other processes (e.g., concurrent `git log` or `git mktree` operations).
- Any operation using `OBJECT_INFO_FOR_PREFETCH` (like `prefetch_cache_entries()`), which relies on `QUICK` checks.

Peff suggests two alternative approaches:
1. **Omit the `QUICK` flag in prefetch-related checks** (e.g., `prefetch_cache_entries()`), forcing a re-scan of the local object store. This would avoid false negatives but could introduce performance overhead, especially for large prefetches.
2. **Reconsider the cache-flushing logic removed in commit 5946a564cdd**, which previously flushed caches on `SECOND_READ` (a fallback for missing objects). Peff argues this was a useful optimization, as `SECOND_READ` signals stale cache data.

He also notes a separate (but related) correctness issue: **false positives in the cache** (e.g., claiming an object exists when it was pruned by a concurrent maintenance job), though this is a broader problem with racy pruning in Git and not directly solvable here.

The email is a **tested, substantive review**—Peff traces the bug’s root cause, proposes alternative fixes, and identifies edge cases the current patch doesn’t address. While he doesn’t outright reject the patch, his concerns could lead to a broader discussion about whether the fix should be expanded or reworked before merging. For now, the series remains in limbo pending Patrick’s response or further input from other reviewers.

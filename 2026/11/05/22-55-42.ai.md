This is a **feature patch** from Yopa Nelly, an Outreachy contributor, addressing the `promisor.fetchOrder` configuration for partial clones. The email is a reply to Kaartic Sivaraam’s surface-level review of the patch’s commit message and process, and it also serves as a de facto cover letter for the v2 patch (which was sent separately).

Yopa has addressed all technical feedback from Tanga Joris’s **substantive review** of v1: the crash (`BUG: string-list.c`) is fixed by switching to `string_list_init_nodup()`, the architectural flaw (a file-static `fetch_order` list shared across repositories) is resolved by storing the parsed order in `struct promisor_remote_config`, and documentation is now included. The implementation has also been simplified—dropping the linked-list insertion sort in favor of a two-pass approach in `try_promisor_remotes()`—which maintains the existing "accepted remotes first" logic while honoring the explicit order for named remotes.

The patch still lacks test coverage, though Yopa acknowledges this and plans to reuse or extend `t0410-partial-clone.sh` (which already tests multiple promisor remotes) rather than introduce a new fixture. Remote name validation remains absent; typos in the `fetchOrder` list are silently ignored, matching Git’s behavior for other list-valued config variables.

On the procedural front, Yopa has rewritten the commit message to comply with `SubmittingPatches` guidelines, removing conversational language. However, the Outreachy process question remains open: whether the patch should have gone through an RFC phase before implementation. Yopa treated the Phase 2 config work as the microproject and skipped the RFC, but Kaartic’s review suggests this may have been a misunderstanding of the microproject guidelines. Yopa is now seeking clarification on whether to send an RFC first or proceed with the current patch as a prototype while discussing the config design on-list.

The patch touches `promisor-remote.c` (108 lines added) and `Documentation/config/promisor.adoc` (11 lines added), introducing the `promisor.fetchOrder` config key. The feature is well-motivated—users currently have no way to control the order of promisor remote attempts without manually reordering config files—and the v2 implementation is technically sound, though the lack of tests and validation leaves room for follow-up work. The Outreachy process concerns are procedural rather than technical and may not block progress if resolved.

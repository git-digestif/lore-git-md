This is a bugfix targeting the fsmonitor and untracked cache subsystems, now with a substantive review from Derrick Stolee. The patch addresses a correctness issue where Git fails to invalidate stale untracked cache entries after the fsmonitor daemon sends a trivial response (`"/"`), typically due to a restart or event loss. This can cause `git status` to show untracked files that no longer exist or emit spurious warnings about missing directories.

The fix introduces `untracked_cache_invalidate_stale_dirs()`, a function that recursively checks each cached directory against its on-disk stat data before the untracked cache is written to the index. Unlike Stolee’s earlier proposal—which cleared the entire untracked cache—this approach only invalidates directories that no longer exist or whose stat data has changed, avoiding measurable performance overhead. The check is performed only when the fsmonitor extension is written and the untracked cache is no longer trusted (`use_fsmonitor` is false), ensuring it doesn’t impact commands that don’t write the index or sparse index operations.

Stolee’s review confirms the patch’s efficiency and correctness, noting that his own "clear everything" approach incurred a 50-75% performance penalty in tests, while this patch shows no measurable impact. He raises minor questions about error handling (e.g., what to do if `repo_get_worktree()` fails) and the placement of the invalidation logic in `do_write_index()` rather than `refresh_fsmonitor()`, but ultimately endorses the approach as sound. The recursive implementation is deemed acceptable given the untracked cache’s inherent depth limits, and the patch’s test coverage—exercising both hook-based and built-in fsmonitor backends—is thorough.

The patch is narrowly scoped, well-motivated, and addresses a real edge case with minimal risk. Stolee’s explicit "LGTM" suggests it’s ready for integration, pending any further feedback. If you care about fsmonitor correctness or untracked cache behavior, this is worth reviewing or testing locally.

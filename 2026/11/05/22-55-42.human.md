This is a feature patch from an Outreachy contributor, part of the ongoing partial-clone/promisor-remote work. Yopa Nelly replies to feedback on their `promisor.fetchOrder` patch, confirming they’ve posted a v2 that fixes the v1 crash (`BUG: string-list.c`) and architectural flaw (file-static `fetch_order` list shared across repositories). The v2 implementation now stores the parsed order in `struct promisor_remote_config` and re-parses on each config read, ensuring per-repository isolation. Documentation is added, but test coverage is still missing.

The author acknowledges Kaartic’s procedural concerns—commit message style and whether the patch should have gone through an RFC phase—but has rewritten the commit message to focus on the change rather than addressing reviewers directly. They ask whether to step back and send a design RFC now or keep the current patch as a prototype while discussing the config shape on-list.

Technically, the patch is sound: it avoids the v1 pitfalls, keeps the two-pass algorithm (explicitly ordered remotes first, then the rest), and maintains compatibility with the existing `extensions.partialClone` behavior. The missing test coverage is the most obvious gap; the author plans to reuse `t0410-partial-clone.sh` or write a new fixture. No validation of remote names in the `fetchOrder` list means typos are silently ignored, but that’s consistent with other Git list-valued config variables. Performance overhead from re-parsing the list on every config read is a potential concern, but not yet measured.

If you care about partial-clone workflows, this patch is worth watching—it’s a small but real usability improvement, and the v2 implementation looks solid. The Outreachy process questions are still open, but they don’t affect the code’s readiness.

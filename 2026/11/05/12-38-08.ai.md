This is a **substantive review** of the first patch in Johannes Schindelin’s RFC series adding merge commit support to `git history`. Philippe Blain identifies a **regression in boundary commit handling** that breaks the expected behavior when replaying a merge whose second parent is outside the rewrite range.

The issue arises from the pre-seeding logic added in this patch: when a merge’s second parent (`M^2`) is specified as a negative revision (e.g., via `M^!`), it gets incorrectly mapped to the `--onto` target, altering the merge base and triggering unnecessary conflicts. Blain demonstrates this with a concrete scenario—amending only the commit message of a merge’s first parent should preserve the original merge’s manual resolutions, but the current implementation fails because the second parent is rewritten to `onto`, changing the merge base and forcing a remerge.

The review is **tested**: Blain reproduces the bug and describes the exact command (`git replay --onto HEAD M^!`) that exposes it. He also suggests two actionable improvements: (1) adjust the pre-seeding logic to exclude negative revisions that are not boundary commits, and (2) document the pre-seeding behavior in the commit message. His feedback is **specific**—he names the problematic code block, explains the unintended consequence, and ties it back to the design goal of preserving manual resolutions.

This is a **high-signal review** for anyone following the series: the bug affects a core use case (replaying merges with unchanged trees) and could block adoption if not fixed. The author will likely need to revise the patch to address the boundary commit logic before the series can progress beyond RFC.

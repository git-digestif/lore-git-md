This is a **substantive design discussion** in the HTTP retry series, specifically about the default value of `http.retryAfter`. Brian M. Carlson responds to Ravi Mistry’s compromise proposal (`http.retryAfter=1`) by rejecting it as insufficiently protective of rate-limited servers. Carlson argues that 1 second is too short for Git’s typically expensive HTTP requests (e.g., fetch/clone operations), which impose higher computational load on servers than the static-file requests curl defaults are designed for. He reiterates his preference for a 30-second initial delay (or at minimum 10 seconds) to allow server load to dissipate, citing operational experience where aggressive retries exacerbate rate-limiting. The email does not propose new code or tests but firmly opposes the compromise, leaving the default value unresolved. This disagreement is now the primary blocker for the series, as Junio C Hamano’s earlier feedback had endorsed the 1-second compromise. The outcome will likely require broader input or maintainer guidance, as the two positions reflect fundamentally different priorities: fast recovery (1s) versus server protection (30s). No technical flaws are identified; this is purely a policy debate about default behavior.

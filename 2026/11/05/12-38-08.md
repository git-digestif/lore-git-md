I understand the intent here, we seed the replayed commit map with onto for the negative revisions, so that a merge with its first parent at the boundary gets its first parent rewritten to onto, but keeps its second parent.  But I think a further tweak is necessary. 

I tried the following: 
- amend the first parent of a merge M (manually, in detached HEAD), changing only the commit message 
- try to replay the merge. Since none of the trees have changed, and the merge-base hasn’t changed, I expect replay to succeed and keep manually resolutions from M. I ran this:

git replay --onto HEAD M^!

and because with this syntax M^2 is a negative revision, it gets mapped to onto, whereas from what I understand it should _not_ be mapped and should be left untouched by replay: the new merge should have M^2 as second parent. 

Since the second parent gets mapped to onto, the merge-base of the replayed merge is changed, so the fast past is skipped,  the new merge conflicts and the replay fails. 

Also, I think this pre-seeding should be mentionned in the commit message. 

Thank you for working on this,and Elijah for prototyping it.  It’s already is a massive time saver for me.

This is a **feature patch for the promisor-remote subsystem**, adding the `promisor.fetchOrder` configuration variable to let users control the order in which Git tries multiple promisor remotes during lazy fetches. The v2 patch addresses the architectural flaws and crash from v1, adds documentation, and is now under review by Junio, who is seeking input from Christian Couder on how this feature interacts with server-side promisor remote advertising.

The patch allows users to specify a comma-separated list of remote names in `promisor.fetchOrder`; Git tries those remotes first (in the listed order) before falling back to the remaining remotes in their original configuration order. The implementation stores the parsed order in `struct promisor_remote_config` and re-parses it on each config read, ensuring per-repository isolation. The two-pass algorithm in `try_promisor_remotes()` preserves the existing "accepted before configured" behavior while applying the user-specified order within each pass.

Junio’s question to Christian Couder is the key new development here. Christian previously worked on server-side promisor remote advertising, where the server can tell clients which promisor remotes to try first. Junio is asking how this client-side configuration meshes with that server-side mechanism—whether they complement each other, conflict, or require coordination. This is a substantive design question that could shape the final form of the feature, and Christian’s response will likely determine whether the patch proceeds as-is or needs further adjustment.

The patch itself is technically sound: it fixes the v1 crash, avoids the file-static list that caused architectural issues, and includes documentation. The commit message is now compliant with project guidelines, though it does not explicitly call out the v1 issues or their fixes. The main gap remains test coverage, which the author has acknowledged and plans to address by reusing `t0410-partial-clone.sh`. The Outreachy process question (whether an RFC was required) is still unresolved but seems less urgent now that the patch is under substantive review.

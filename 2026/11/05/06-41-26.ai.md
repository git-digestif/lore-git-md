This is a bug report targeting the geometric maintenance strategy in Git 2.54. The author, Christoph Weiss, demonstrates that `git maintenance run --auto` with the `geometric` strategy (now the default) prunes unreachable commits but fails to update the commit-graph, leaving it in an inconsistent state. The reproduction script creates a bare repository, sets up a commit history with an obsolete branch, forces an early prune, then runs geometric maintenance. Before maintenance, `git fsck` passes; after, it reports dangling commits and a corrupted commit-graph chain. The issue surfaced after an upgrade from Git 2.52 to 2.54, where the default maintenance strategy switched from `gc` to `geometric`.

The script touches the commit-graph (`commit-graph write --reachable --split`), refs (`update-ref`), and object storage (`repack -ad`, `pack-objects`) subsystems. Key names involved are `maintenance.strategy=geometric`, `gc.writeCommitGraph`, and the `--split` commit-graph chain. The old behavior (using `gc` strategy) does not exhibit the problem, suggesting the regression is specific to the geometric repack logic introduced in 2.54.

No prior discussion or patch is referenced; this appears to be the first report of the issue. The reproduction is self-contained and does not depend on external tools beyond a POSIX shell and Git 2.54. The commit-graph corruption is likely to affect performance and correctness for any operation that relies on the commit-graph (e.g., `git log --graph`, reachability checks). Given the default strategy change, this bug could impact a broad set of users upgrading to 2.54.

This is a feature patch for the promisor-remote subsystem, introducing a new `promisor.fetchOrder` configuration variable. The patch is a revised version (v2) from an Outreachy contributor, addressing feedback on the initial submission.

The feature lets users explicitly specify the order in which Git tries multiple promisor remotes during lazy fetches, rather than relying on the order in which the remotes appear in the configuration. This is a real usability improvement for users with multiple promisor remotes, and the implementation is small and focused. The patch now includes documentation in `Documentation/config/promisor.adoc` and fixes the architectural issues noted in the first version by storing the fetch order in the per-repository `promisor_remote_config` struct rather than a file-static variable.

The revised implementation parses the comma-separated list of remote names in `promisor_remote_config()`, stores it in the config struct, and applies the order during `try_promisor_remotes()`. The sorting logic walks the list twice: once in the user-specified order for remotes named in `fetchOrder`, and once in the original config order for the rest. This preserves the existing "accepted before configured" behavior while adding the new ordering capability. The patch still does not include test coverage, but the author has acknowledged this gap and the reviewers have suggested reusing the existing `t0410-partial-clone.sh` test script.

The patch looks well-structured and addresses the technical concerns raised in the first review. The commit message is now more focused and complies with project guidelines. This version appears ready for further review and testing, though the lack of test coverage remains a notable gap. The feature itself is uncontroversial and fills a clear gap in the promisor-remote configuration.

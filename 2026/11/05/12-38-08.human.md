This is a substantive review of the first patch in Johannes Schindelin’s RFC series adding merge commit support to `git history`. Philippe Blain identifies a concrete edge case where the current implementation fails: when replaying a merge commit whose second parent is specified as a negative revision (e.g., `M^!`), the pre-seeding logic incorrectly maps that parent to the `--onto` target, altering the merge base and causing spurious conflicts.

The issue is clear and well-documented: Blain demonstrates that amending only the commit message of a merge’s first parent should be a no-op for replay (since trees and merge bases are unchanged), yet the current code path rewrites the second parent to `onto`, breaking the merge. His reproduction steps are straightforward, and the expected behavior—preserving the second parent—is uncontroversial. The review is thorough, tested, and pinpoints both the bug and the missing rationale in the commit message.

This feedback is likely to prompt a v2 of the series, as the fix will require adjusting the boundary-seeding logic to exclude negative revisions that are not the primary parent. The patch otherwise appears well-structured, but this edge case undermines its reliability for real-world use. Reviewers and integrators will want to see this resolved before the series progresses beyond RFC status.

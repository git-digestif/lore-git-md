This is a follow-up in the ongoing discussion about a bugfix series for loose object database (ODB) cache invalidation during `git merge`. The thread is now focused on the deeper design questions raised by Jeff King (Peff) about the root cause of the bug and the long-term correctness of the proposed fix.

Patrick Steinhardt acknowledges Peff’s concerns and agrees that the `QUICK` flag is a recurring source of bugs. He suggests that dropping `QUICK` entirely might be the best path forward, though he acknowledges this would require refactoring to avoid performance regressions (e.g., avoiding repeated re-scans of the ODB for large prefetches). Patrick also concedes that the current fix—updating the loose object cache after writing new objects—only addresses one edge case (objects written by the same process) and leaves others (e.g., objects written by other processes or packed objects) unhandled. He proposes merging the current fix as a targeted solution for the immediate regression while deferring broader fixes to a follow-up effort.

Peff argues this was a useful optimization signal, while Patrick counters that flushing the cache in all `SECOND_READ` cases could be wasteful if the object is truly missing. Neither side dismisses the other’s point, but no consensus emerges on whether to restore the old behavior.

This email advances the thread by clarifying Patrick’s position: the current fix is a pragmatic step to address the reported regression, but the broader issue of `QUICK`-related bugs and racy staleness remains open.

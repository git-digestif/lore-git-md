Subject: [PATCH 0/2] Fix t5608-clone-2gb.sh and unpack-objects size handling
Series version: v1 (initial submission)
Originating author: Kristofer Karlsson
Thread type: patch series (bug fix + test modernization)

Core problem or goal
The test script `t5608-clone-2gb.sh` claims to verify Git’s handling of very large (>2 GB or >4 GB) packs, but it was not actually creating packs of those sizes due to `fast-import`’s default unpack limit and `git clone`’s behavior of keeping received packs. Additionally, `unpack-objects` incorrectly narrows the size of streamed blobs to `unsigned long`, which causes failures on Windows when blobs exceed 4 GB due to the platform’s 32-bit `unsigned long` type.

Current status
Under review (no prior versions). Two patches:
1. Fix the `unpack-objects` bug by changing a parameter type from `unsigned long` to `size_t`.
2. Add assertions to `t5608-clone-2gb.sh` to ensure the packs are truly the sizes they claim, making the test more reliable. The test now explicitly disables `fetch.unpackLimit` to ensure large packs are not unpacked during clone.

Key technical details
- Files touched: `builtin/unpack-objects.c` (plumbing fix), `t/t5608-clone-2gb.sh` (test assertions).
- New/renamed symbols: None.
- Behavior change: `unpack-objects` now correctly handles blob sizes >4 GB on Windows. The test now reliably creates and verifies large packs.
- On-disk format: Unchanged.
- Test coverage: Expanded assertions in `t5608-clone-2gb.sh` to verify pack sizes, increasing test runtime but improving reliability. The test now uses `git -c fetch.unpackLimit=0 clone` to ensure packs remain packed.
- Historical context: `fetch.unpackLimit` has never applied to `git clone`, which has always kept received packs by design (cited commits: `ad89721508`, `8434c2f1af`).

Open questions and loose ends
- Whether the test changes introduce undue performance overhead or flakiness in CI remains unaddressed, though no objections have been raised.
- The stylistic nit (folding an assertion into the test setup) is unresolved but acknowledged as non-blocking by both author and reviewer.

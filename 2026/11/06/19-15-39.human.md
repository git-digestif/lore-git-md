This is Junio C Hamano weighing in on the credential-anonymization debate in Aniket Gupta’s bundle-uri bugfix series, specifically on patch 2/3. The patch itself is a small but real hardening measure: when `relative_url()` fails to resolve a relative URI, the error message now anonymizes any credentials in the original URL before printing it. Junio’s message is a direct reply to Derrick Stolee’s earlier review, which questioned whether this anonymization is necessary.

Junio’s tone is skeptical. He pushes back on Derrick’s claim that log-storing environments already sanitize command output, asking how they could do so without knowing what strings to look for. He also echoes Derrick’s observation that if a bundle-uri list itself contains credentialed URIs, the mechanism is already unsafe, so this patch doesn’t meaningfully protect secrets in that context. The implication is that the patch may be solving a non-problem.

He then surveys where `transport_anonymize_url()` is already used in Git: reflog entries, fetch/push progress messages, and transport-layer die() messages. All of these, he notes, are either ephemeral (shown on screen) or already protected by the fact that they’re talking about the user’s own URLs. The survey suggests that the existing anonymization calls are there for user-facing polish, not security hardening.

This email doesn’t settle the policy question, but it shifts the burden: the patch’s proponents now need to justify why this specific error message deserves hardening when other, similar messages don’t. The series as a whole is still technically complete and ready for maintainer consideration, but patch 2/3 is now the only piece with an open question. If Junio’s skepticism prevails, the patch could be dropped or revised in a v4.

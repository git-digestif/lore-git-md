This thread is about a bug in Git’s `git init` command when built with `WITH_BREAKING_CHANGES=1`, which is meant to enable Git v3 behavior. The issue was that new repositories incorrectly defaulted to SHA-1 instead of SHA-256, breaking compatibility with Git v3 expectations. Brian m. carlson provided a fix to ensure `git init` respects the breaking-changes flag, but Junio C Hamano identified a critical edge case: reinitializing an *existing* repository under `WITH_BREAKING_CHANGES=1` silently overwrites its object format with SHA-256, which may not be intended.

Junio has now dug deeper into the code and found the root cause. The original behavior persisted because `read_repository_format()` forced the hash algorithm to `GIT_HASH_SHA1_LEGACY` when no configuration existed, overriding the intended default. Additionally, the patch introduced a regression by allowing `init.defaultObjectFormat` (or the new `GIT_HASH_DEFAULT`) to clobber an existing repository’s format during reinitialization, due to a missing guard in `repository_format_configure()`. Junio proposes a refactor to ensure defaults are only applied to *new* repositories (`repo_fmt->version < 0`), while existing repositories either preserve their format or fail if an incompatible hash is specified. This would align the behavior with how reference storage formats are already handled.

The patch is otherwise ready for integration but must be revised to address these issues. No new design questions have emerged, though Patrick Steinhardt’s input is still pending on whether `git init` should similarly preserve the reference storage format during reinitialization. The fix remains a self-contained change targeting `setup.c`, with test coverage for both new and existing repositories. CI results are still pending.

This thread addresses a bug where `git init` failed to default to SHA-256 when Git is built with `WITH_BREAKING_CHANGES=1`, the flag intended to enable Git v3 behavior. Adam Dinwoodie originally raised the issue, and brian m. carlstadt has been driving the fix through five iterations, with the latest being v5. The patch restructures `repository_format_configure()` in `setup.c` so that hash-algorithm selection follows a strict priority order: explicit `--object-format` on the command line wins, otherwise an existing repository's algorithm is preserved, then `GIT_DEFAULT_HASH`, then `init.defaultObjectFormat`, and finally the build default `GIT_HASH_DEFAULT` (which resolves to SHA-256 under breaking-changes builds). This ensures new repositories correctly report `sha256` via `git rev-parse --show-object-format` while preventing silent reinitialization of existing repositories with a different hash.

Junio C Hamano approved the series after reviewing v4, but identified a test-isolation bug in `t/t0001-init.sh` where `test_when_finished` registered inside a subshell failed to clean up global `init.defaultObjectFormat` on bash systems, causing subsequent tests to fail. He also suggested removing a redundant condition from the reinitialization guard. Brian m. carlstadt has now sent v5 incorporating both fixes: the test cleanup registration was moved outside the subshell, and the redundant `hash_algo != GIT_HASH_UNKNOWN` check was dropped. Junio has indicated he is ready to squash a fix-up commit if v5 contains only the test fix, and the topic is expected to be queued in `next` or `seen` in an upcoming "What's cooking" report.

The series remains approved but not yet merged to any integration branch. Patrick Steinhardt previously reviewed earlier versions and expressed satisfaction. The fix does not apply to `maint` since the breaking-changes flag is forward-looking for Git 3.0 only.

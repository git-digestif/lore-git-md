This thread began as an inquiry from Adam Dinwoodie about whether `git init` should default to SHA-256 for new repositories when Git is built with `WITH_BREAKING_CHANGES=1`, since that flag is meant to enable Git v3 behavior. The behavior was confirmed as a bug, and brian m. carlstadt has driven a four-iteration patch series fixing the default object format selection in `setup.c`, so that new repositories get SHA-256 under breaking-changes builds while existing repositories are never silently reinitialized with a different hash algorithm.

Maintainer Junio C Hamano has approved the v4 iteration, accepting the restructured `repository_format_configure()` with its strict priority order (explicit `--object-format` flag, then existing repository algorithm, then `GIT_DEFAULT_HASH`, then `init.defaultObjectFormat`, then the build default). Patrick Steinhardt also reviewed and signed off. The one remaining issue is a test-isolation bug in `t/t0001-init.sh`: a `test_when_finished` registered inside a subshell fails to clean up a global `init.defaultObjectFormat` config, leaking it into later tests when the suite runs under bash. Junio confirmed this in his latest email, noting he runs tests under both dash and bash to catch such shell-specific problems, and offered to squash a ready fix-up commit himself if the pending v5 reroll contains only that two-line test correction. The C logic itself is unchanged and accepted. Once brian sends v5 with the test fix, the series is expected to be queued in `next` or `seen`; it is not yet recorded as merged to any integration branch.

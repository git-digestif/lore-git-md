This thread began when Adam Dinwoodie reported that `git init` was not defaulting to SHA-256 for new repositories when Git was built with `WITH_BREAKING_CHANGES=1`, a flag intended to enable Git v3 behavior. The issue was quickly confirmed as a bug, and brian m. carlson prepared a fix that ensures `git init` respects the breaking-changes flag by defaulting to SHA-256 for *new* repositories while preventing silent reinitialization of existing repositories with a different hash algorithm.

The revised patch, now merged by Junio C Hamano, restructures the repository initialization logic in `setup.c` to enforce two key behaviors: (1) defaulting to `GIT_HASH_DEFAULT` (SHA-256 under Git v3) only for *new* repositories, and (2) refusing to reinitialize an existing repository with an incompatible hash algorithm. This resolves a latent bug in `read_repository_format()` and a regression where reinitialization could silently clobber the object format. The patch aligns with feedback from Junio and Patrick Steinhardt, who emphasized the need for consistent format-handling and reinitialization safety. Tests in `t/t0001-init.sh` now verify the correct default selection, rejection of incompatible reinitialization, and preservation of existing configurations.

With the patch merged to `master`, the thread is effectively closed. The fix is self-contained and part of the broader Git v3 preparation effort, though it does not depend on other in-flight work. No further action is expected beyond monitoring CI results for platform-specific regressions.

This thread concerns whether `git init` correctly defaults to SHA-256 when Git is built with `WITH_BREAKING_CHANGES=1` for Git v3. Adam Dinwoodie raised the inquiry after observing that new repositories still used SHA-1 despite the breaking-changes flag. brian m. carlstadt confirmed this as a bug and developed a four-iteration patch series that restructures `repository_format_configure()` in `setup.c` to establish a strict priority order: explicit `--object-format` flags win, followed by existing repository settings, environment variables, config, and finally the build-time `GIT_HASH_DEFAULT` (SHA-256 under breaking-changes builds). The fix ensures new repositories default to SHA-256 under Git v3 while preventing silent reinitialization of existing repositories with a different hash.

Junio C Hamano approved the fourth iteration, stating "everything looks good," but identified a test-isolation bug in `t/t0001-init.sh` where a `test_when_finished` cleanup registered inside a subshell fails to execute in the parent shell, causing global `init.defaultObjectFormat` config to leak and fail subsequent tests when bash is used as `/bin/sh`. brian m. carlstadt has acknowledged this bug and confirmed they will send a fifth iteration incorporating Junio's proposed two-line fix, which moves the cleanup registration outside the subshell. The C logic remains unchanged from the approved v4. Patrick Steinhardt also reviewed and approved the series.

The series is currently awaiting the v5 reroll with the test fix before Junio queues it in `next` or `seen`; it has not yet been merged to any integration branch. Junio's earlier suggestion to simplify a redundant condition in the reinitialization guard remains pending and may be addressed in the same reroll.

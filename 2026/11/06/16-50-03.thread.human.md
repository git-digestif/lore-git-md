This thread began when Adam Dinwoodie reported that `git init` was not defaulting to SHA-256 in new repositories when Git is built with `WITH_BREAKING_CHANGES=1`, contrary to Git v3 expectations. Brian m. carlson confirmed the bug and submitted a minimal fix that ensures `git init` respects the breaking-changes flag by defaulting to SHA-256. The patch was straightforward, touching only `setup.c` and adding a test in `t/t0001-init.sh` to verify the behavior.

The discussion took a turn when Junio C Hamano raised a critical edge case: what happens when `git init` is run in an *already initialized* repository under `WITH_BREAKING_CHANGES=1`? The current patch silently overwrites the existing repository’s object format with SHA-256, which Junio argues is unsafe. He proposed three alternatives—converting the repository (impractical), preserving the existing format with a warning, or failing loudly—and suggested the second option as the most reasonable. His review included a test case demonstrating the issue, and the thread is now focused on how to handle reinitialization safely. Patrick Steinhardt was CC’ed to weigh in on whether the reference storage format should also be preserved, though this is a secondary concern.

The patch is otherwise ready for integration, but this feedback means it will need revision before merging. No objections to the core fix have been raised, and Brian has clarified that the patch remains necessary even if a future "empty repository" feature (allowing hash-agnostic initialization) is implemented. The open question is now purely about the safest way to handle reinitialization. CI results are still pending, but the discussion has shifted to design rather than correctness.

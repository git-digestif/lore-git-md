Adam Dinwoodie raised the question of whether `git init` correctly defaults to SHA-256 when Git is built with `WITH_BREAKING_CHANGES=1` (the Git v3 behavior flag), and brian m. carlstadt confirmed this was a bug and drove a four-version patch series to fix it. The series restructures `repository_format_configure()` in `setup.c` into a strict priority chain -- command-line `--object-format` wins, then an existing repository's detected hash, then `GIT_DEFAULT_HASH`, `init.defaultObjectFormat`, and finally the build-time `GIT_HASH_DEFAULT` (SHA-256 under breaking-changes builds) -- while ensuring existing repositories are never silently reinitialized with a different hash.

Junio C Hamano approved v4 as "everything looks good" and Patrick Steinhardt confirmed satisfaction, but Junio's latest message caught a real test-isolation bug in `t/t0001-init.sh`: the 're-init does not modify hash from config' test registers cleanup via `test_when_finished` inside a subshell, so the global `init.defaultObjectFormat` config leaks into later tests and causes "not ok 62". He proposed moving the `test_when_finished` registration outside the subshell and using a plain `git config --global` inside it. Separately, he earlier suggested dropping a redundant `hash_algo != GIT_HASH_UNKNOWN` check in the C code as a cosmetic simplification. The series is approved in principle but needs these final fixes before Junio queues it in `next` or `seen`; it is not yet in any integration branch.

The patch touches repository initialization in `setup.c` and expands coverage in `t/t0001-init.sh` for new-repository defaults, fatal refusal to reinitialize with a mismatched `--object-format`, and confirmation that global config does not alter an existing repo's hash. Still open are the mechanical test-scaffolding fix Junio just proposed and the optional C-code simplification; no design objections remain.

This thread is about a bug in Git's handling of the `WITH_BREAKING_CHANGES=1` build flag, which is meant to enable Git v3 behavior—specifically, defaulting new repositories to SHA-256 instead of SHA-1. Adam Dinwoodie reported that `git init` was incorrectly defaulting to SHA-1 even when Git was built with this flag, and brian m. carlson confirmed the issue and prepared a fix.

The fix itself is simple and targeted: it adds a single line in `setup.c` to ensure `git init` respects `GIT_HASH_DEFAULT` (SHA-256 in breaking-changes mode) when no other hash algorithm is specified. A new test in `t/t0001-init.sh` verifies the behavior works correctly in both breaking-changes and non-breaking-changes scenarios. The patch is ready for integration, with CI results pending.

Junio C Hamano acknowledged the fix as correct for its immediate goal but raised a forward-looking question about whether the current approach might conflict with a future design for "empty repositories" that could remain hash-agnostic until their first push. This isn’t a blocker for the current patch, but it suggests the design might need revisiting if such a feature is implemented later. No objections or alternative proposals have been raised, and the fix is uncontroversial for now. The broader context is Git v3 preparation, particularly for compatibility with downstream consumers like Nixpkgs.

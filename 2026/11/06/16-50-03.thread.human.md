Adam Dinwoodie raised a bug report noting that `git init` was defaulting to SHA-1 even when Git was built with `WITH_BREAKING_CHANGES=1`, which should enable Git v3 behavior including SHA-256 as the default object format. brian m. carlson confirmed the bug and developed a fix across several iterations, now at v3, that restructures `repository_format_configure()` in `setup.c` to ensure new repositories correctly default to SHA-256 under breaking-changes builds while protecting existing repositories from silent hash changes during reinitialization.

The final patch establishes a clear precedence: an explicit `--object-format` on the command line always wins, while environment variables, config settings, and the build-time default are only consulted for brand-new repositories or those with no detected hash. If a user attempts to reinitialize an existing repository with a mismatched hash, Git now fails with an error rather than silently switching algorithms, and reinitialization preserves the original hash even if `init.defaultObjectFormat` specifies something different. The tests in `t/t0001-init.sh` now use the standard `$GIT_TEST_BUILTIN_HASH` variable to cover default selection, reinitialization rejection, and config override scenarios.

Junio C Hamano reviewed the series, identified issues with earlier versions around reinitialization safety, and confirmed the revised approach was "much simpler and more straightforward," merging it to `master`. Patrick Steinhardt suggested minor refinements including the test variable change and a stale comment cleanup, which are incorporated in v3; these are follow-up polish items that do not affect the core fix. The patch is not applied to `maint` since `WITH_BREAKING_CHANGES=1` is forward-looking for Git 3.0 only.

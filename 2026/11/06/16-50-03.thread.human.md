This thread began with Adam Dinwoodie asking whether `git init` should default to SHA-256 when Git is built with `WITH_BREAKING_CHANGES=1` for Git v3, and brian m. carlstadt confirmed it does not and prepared a fix across three iterations. The current v3 patch makes `git init` respect the breaking-changes flag for new repositories while refusing to silently reinitialize existing repositories with a different hash algorithm, and Patrick Steinhardt has signed off on the latest version. Junio C Hamano is still reviewing, and has now accepted brian's clarification that a command-line `--object-format` mismatch on reinitialization is a fatal error while `GIT_DEFAULT_HASH` and `init.defaultObjectFormat` are silently ignored in that case, closing one of his outstanding questions.

What remains open are three items expected to be addressed in a forthcoming v4: expanding the commit message to explain that `GIT_HASH_DEFAULT` initializes to `SHA1_LEGACY` and is therefore not treated as unspecified, rewriting the removed reinitialization-safety comment to distinguish command-line from config/environment precedence, and fixing a test-isolation concern where `sane_unset GIT_DEFAULT_HASH` in `t/t0001-init.sh` may leak into later tests. No approval has been given yet, and the series remains under review.

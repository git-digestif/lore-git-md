The thread concerns a bug where `git init` failed to default to SHA-256 for new repositories when Git is built with `WITH_BREAKING_CHANGES=1`, the flag intended to enable Git v3 behavior. Adam Dinwoodie reported the issue, and brian m. carlstadt authored a fix targeting the default object format selection in `setup.c`, now at version 3. The v3 patch ensures new repositories default to `GIT_HASH_DEFAULT` (SHA-256 under the breaking-changes build) while refusing to silently reinitialize existing repositories with a mismatched hash algorithm. Patrick Steinhardt reviewed the refactor and is satisfied with v3.

Junio C Hamano is still reviewing v3 and has raised several substantive questions about the commit message logic, the semantics of a "no detected hash algorithm" repository state, the removal of a reinitialization-safety comment, and test isolation around `sane_unset GIT_DEFAULT_HASH`. In his latest reply, brian m. carlstadt addressed three of these: he agreed to expand the commit message to explain that `GIT_HASH_DEFAULT` initializes to `SHA1_LEGACY` rather than acting as an unspecified sentinel; he noted the "no detected hash" state should not occur in current code paths but is handled defensively as a potential future mode; and he conceded the removed comment should be rewritten to distinguish the command-line `--object-format` (which fatally errors on mismatch with an existing repository) from `init.defaultObjectFormat` and `GIT_DEFAULT_HASH` (which are silently ignored during reinitialization). He also acknowledged that a global `init.defaultObjectFormat` in `~/.gitconfig` does count as user specification for new repositories.

The series remains under review with no approval from Junio yet. These clarifications indicate a v4 is likely forthcoming to adjust the commit message wording, restore part of the cautionary comment, and address the remaining test-isolation concern in `t/t0001-init.sh`.

Adam Dinwoodie raised the question of whether `git init` correctly defaults to SHA-256 when Git is built with `WITH_BREAKING_CHANGES=1`, and brian m. carlstadt confirmed the bug and drove a four-iteration fix. The patch restructures `repository_format_configure()` in `setup.c` so that a new repository picks SHA-256 under the breaking-changes build, while existing repositories keep their detected hash algorithm and fatally refuse mismatched reinitialization attempts via the command line. Patrick Steinhardt signed off on the third iteration, and Junio C Hamano has now reviewed the fourth iteration and confirmed that all changes "look good," accepting the strict priority order (CLI flag, existing repo hash, `GIT_DEFAULT_HASH`, `init.defaultObjectFormat`, then the build default) and the expanded test coverage in `t/t0001-init.sh`.

The series is now at v4 with maintainer approval recorded; it appears ready to be queued in `next` or `seen` in an upcoming "What's cooking" report, though it has not yet graduated to `master`. No substantive objections remain open. The only loose ends are minor forward-looking notes: a potential future "empty repository" mode that would defer hash selection until first use, and possible follow-up documentation for downstream packagers, neither of which blocks this fix.

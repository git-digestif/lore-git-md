This thread is about a small but important fix for Git v3 compatibility. When Git is built with `WITH_BREAKING_CHANGES=1`—a flag meant to enable Git v3 behavior—`git init` was incorrectly defaulting to SHA-1 instead of SHA-256 for new repositories. Adam Dinwoodie reported the issue, and brian m. carlson confirmed it as a bug and prepared a minimal fix.

The patch itself is straightforward: it adds a single line in `setup.c` to ensure `git init` respects the breaking-changes flag by defaulting to SHA-256. A new test in `t/t0001-init.sh` verifies the fix works in both breaking-changes and non-breaking-changes scenarios. Junio C Hamano acknowledged the patch is correct but raised a forward-looking question about whether this might conflict with a future "empty repository" design, where a repository could remain hash-agnostic until its first push. brian m. carlson responded that while such a feature was discussed, it would require protocol changes and hasn’t been implemented. He argued that even with this hypothetical feature, repositories would still need a default hash algorithm for local operations, so the current patch remains necessary.

The fix is ready for integration pending CI results, with no objections or alternative proposals raised. It’s a self-contained change that aligns with Git 3.0’s promise to default to SHA-256, and it’s particularly important for downstream consumers like Nixpkgs. The only open question is whether the design might need adjustment if the "empty repository" feature is ever implemented, but that’s not a blocker for now.

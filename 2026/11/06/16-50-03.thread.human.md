This thread concerns whether `git init` correctly defaults to SHA-256 when Git is built with `WITH_BREAKING_CHANGES=1` for Git v3. Adam Dinwoodie reported that new repositories incorrectly defaulted to SHA-1 even in breaking-changes builds. brian m. carlstadt authored a patch series, now at its third iteration, fixing the default object format selection logic in `setup.c` so that `git init` respects `GIT_HASH_DEFAULT` for new repositories while refusing to silently reinitialize existing repositories with a different hash algorithm. Junio C Hamano reviewed the series, identified issues with earlier versions regarding reinitialization safety and a latent bug in `read_repository_format()`, and v3 incorporates feedback from Patrick Steinhardt, including switching tests to use `$GIT_TEST_BUILTIN_HASH` and removing a stale comment.

The series has been merged to `master` (date unknown) and does not apply to `maint`, as the breaking-changes flag is forward-looking for Git 3.0 only. The fix ensures `git rev-parse --show-object-format` returns `sha256` under Git v3 for new repositories and prevents existing repositories from being silently reconfigured with an incompatible hash.

One concern remains open: in his latest review, Junio questioned whether calling `sane_unset GIT_DEFAULT_HASH` in the second and third test cases without saving and restoring the previous value could pollute the environment for subsequent tests in `t/t0001-init.sh`. He specifically asked whether later tests might break if they implicitly rely on `GIT_DEFAULT_HASH` being set by `t/test-lib.sh`, identifying a potential test-ordering dependency that could cause flaky failures depending on the build's hash algorithm.

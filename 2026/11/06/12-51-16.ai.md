This is a **test fix** for `t5608-clone-2gb.sh`, part 2 of a 2-patch series. The patch addresses a long-standing but silent breakage in the test suite: the expensive 2GB+ clone tests were no longer testing what they claimed to test because the setup stopped producing large packs. The author adds explicit assertions to verify that the packs involved are actually the expected size, and fixes the setup so the tests once again exercise the intended code paths.

The problem was introduced years ago when `fast-import` began respecting `unpackLimit` (d9545c7f46, 2016), causing it to unpack small packs into loose objects. Since the test blobs compress extremely well, the repository ended up with only ~10MB of loose objects instead of a 2GB+ pack. The 4GB object tests added in 2026 had a similar issue: they set `fetch.unpackLimit` but used `git clone`, which always keeps the received pack, so the unpack-objects path was never exercised. The tests passed only because they checked for success, not for the actual conditions they relied on.

The fix has two parts. First, the setup now sets `fastimport.unpackLimit=0` to force `fast-import` to keep its pack, restoring the 2GB+ repository size. Second, the unpack-objects variant is changed from `git clone` to `git fetch` into an empty repository, which honors `fetch.unpackLimit` and thus actually invokes unpack-objects. The patch also adds helper functions to assert that packs exceed 2GB or 4GB, and verifies that unpack-objects was called via trace2 output.

The changes are minimal and targeted: only the test script is modified, and the assertions are added in a way that future breakage will be caught immediately. The commit message is thorough, explaining both the problem and the fix in detail, and even notes a performance improvement (setup time halved from 80 to 40 seconds). The patch is clearly well-tested and addresses a real issue in the test suite.

This is a substantive review comment on patch 5/6 of Miklos Vajna’s six-patch series that fixes performance and correctness bugs in `git log --follow` for merge-heavy histories. The series as a whole is a well-motivated, well-tested effort to undo a 2026 performance regression and plug two correctness holes.

Patrick Steinhardt’s reply zeroes in on a potential edge case: when two histories are unrelated (no common merge base), the new helper `follow_needs_renames()` will always return false, effectively disabling rename detection for that merge. The commit message of 304812ed33 (the very change that introduced the regression) explicitly called out sub-tree merges of unrelated histories as a use case that should still work. Patrick’s question is whether the current patch accidentally breaks that scenario.

The observation is sharp and grounded in the code: the helper calls `repo_get_merge_bases()`, which returns an empty list for unrelated histories, so the loop never runs and the function returns 0. That looks like a silent behavior change that could cause `git log --follow` to miss renames in sub-tree merges. No test failure is reported yet, but the logic is clearly suspect. If this is indeed a regression, it would be a serious one, because it reintroduces a correctness bug under a specific but documented use case.

The ball is now in Miklos’s court to either explain why the current code is correct (perhaps the commit message of 304812ed33 was aspirational rather than implemented) or to send a v5 that restores the intended behavior. Either way, this is a substantive technical point that needs resolution before the series can land.

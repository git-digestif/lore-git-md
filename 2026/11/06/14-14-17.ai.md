This is a **substantive review** of the final patch (6/6) in Miklos Vajna’s `git log --follow` series. Patrick Steinhardt identifies a **correctness regression** in the series’ handling of file copies: the new logic, which optimizes rename detection by only searching for renames when the merge base lacks the path, fails to track edits to the *source* of a copy when the merge keeps the copied file but drops the original. The test case he provides—a copy of file `F` to `G` on `master`, an edit to `F` on a side branch, and a merge that keeps `G` but discards `F`—demonstrates that `git log --follow G` no longer shows the edit to `F` on the side branch, even though it did before the series.

The issue stems from the assumption in `follow_needs_renames()` that only renames (not copies) need to be considered when the merge base lacks the path. This assumption holds for renames but breaks for copies, where the original file may still exist and be edited on a side branch. Patrick’s test case is minimal, self-contained, and directly contradicts the commit message’s claim that the fix covers all cases where the parent changed a file the merge no longer has. The review is **tested**: he confirms the test passes on `master` but fails with the series applied, and the reproduction steps are clear.

This is a **blocking concern** for the series. The optimization in patch 5/6 (which this patch builds on) already faces a correctness question about unrelated histories; now patch 6/6 introduces a second correctness gap. Resolution will likely require either revising the logic in `follow_needs_renames()` to account for copies or documenting that `--follow` no longer tracks copy sources in this scenario. The thread’s next step is almost certainly a v5 that addresses both issues.

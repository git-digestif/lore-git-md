This is an Outreachy project proposal for a feature targeting the promisor remote subsystem. The author, Shashank S, is applying for the December 2026 Outreachy internship to implement configurable fetch ordering for promisor remotes in partial clones.

The proposal is thorough and well-structured, showing a clear understanding of the current behavior and the technical challenges involved. Shashank has already made four contributions to Git during the contribution period, all of which have either merged to `master` or are marked "Will merge to master" in "What's cooking" — a strong signal of readiness. The patches cover test modernization, option parsing, and `the_repository` removal, demonstrating familiarity with Git's codebase and contribution process.

The project aims to let users configure the order in which Git tries promisor remotes when lazily fetching missing objects. Currently, the order is deterministic but not user-configurable: accepted remotes first, then configured remotes in configuration order, with `extensions.partialClone` last. The proposal outlines two design questions that will be resolved via RFC: the shape of client-side configuration (ordered list vs. numeric priority) and how to handle server-advertised ordering (explicit field vs. advertisement order). It also identifies key edge cases: configuration layering, invalid data, precedence between local and server preferences, and backward compatibility.

The 13-week plan is realistic and front-loads design discussion before implementation. Week 1 focuses on baseline documentation and tests, Week 2 on the client-configuration RFC, and Weeks 3–4 on implementing the agreed design. The protocol RFC follows in Week 6, with implementation in Weeks 7–8. The plan leaves ample time for review and rerolls, and explicitly avoids overcommitting to stretch goals like dynamic reordering. Shashank’s availability (40 hours/week, no conflicts) and timezone (IST) are clearly stated.

This looks like a well-scoped, well-motivated feature that addresses a real gap in partial-clone usability. The proposal’s emphasis on RFC-driven design and backward compatibility is appropriate for a change touching both configuration and protocol. If the mailing list reaches consensus on the design, this project is likely to land successfully.

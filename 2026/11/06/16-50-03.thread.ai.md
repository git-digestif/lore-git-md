Thread identity: inquiry about Git v3 default object format for new repositories; thread root by Adam Dinwoodie. Series version: not applicable (self-contained bugfix).

Core problem or goal: determine whether `git init` correctly defaults to SHA-256 (instead of SHA-1) when Git is built with `WITH_BREAKING_CHANGES=1`, as this flag is intended to enable Git v3 behavior. The issue was confirmed as a bug, and a fix by brian m. carlson ensures `git init` respects the breaking-changes flag by defaulting to SHA-256. The patch is minimal, targeting only the default object format selection logic in `setup.c`.

Current status: bug confirmed and fix implemented. The patch adds a single line in `setup.c` to set the repository's hash algorithm to `GIT_HASH_DEFAULT` when no other algorithm is specified, ensuring `git init` uses SHA-256 in breaking-changes mode. The fix includes a new test in `t/t0001-init.sh` to verify the correct default object format is used, with and without the `WITH_BREAKING_CHANGES` prereq. Junio raised a forward-looking question about whether the current approach might conflict with a future "empty repository" design (where repositories could remain hash-agnostic until first push), but brian m. carlson clarified that such a feature would require protocol changes and is not implemented. Even if implemented, repositories would still need to default to *some* hash algorithm for local operations, making the current patch necessary regardless. The patch is otherwise ready for integration pending CI results.

Key technical details:
- Build flag: `WITH_BREAKING_CHANGES=1` (intended to enable Git v3 behavior).
- Command: `git init` and `git rev-parse --show-object-format` (now correctly returns `sha256` under Git v3).
- Subsystem: repository initialization (`setup.c`).
- New symbol: `GIT_HASH_DEFAULT` (used to set the default object format).
- On-disk implication: default object format for new repositories now aligns with Git v3 expectations.
- Test coverage: new test in `t/t0001-init.sh` verifies the fix for both breaking-changes and non-breaking-changes scenarios.

This is not a blocker for the current patch.

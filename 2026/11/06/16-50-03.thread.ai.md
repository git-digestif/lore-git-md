Thread identity: inquiry about Git v3 default object format for new repositories; thread root by Adam Dinwoodie. Series version: v5 (fifth iteration, latest from brian m. carlstadt), approved by the maintainer, incorporating the test-isolation fix and the removal of the redundant hash-algo check. Thread type: bugfix patch series.

Core problem or goal: determine whether `git init` correctly defaults to SHA-256 (instead of SHA-1) when Git is built with `WITH_BREAKING_CHANGES=1`, as this flag is intended to enable Git v3 behavior. The issue was confirmed as a bug, and the fix by brian m. carlstadt ensures `git init` respects the breaking-changes flag by defaulting to SHA-256 for *new* repositories while preventing silent reinitialization of existing repositories with a different hash algorithm. The patch targets the default object format selection logic in `setup.c`.

Current status: approved by maintainer. Junio C Hamano confirmed that the v4 changes "all look good" and stated "everything looks good," accepting brian m. carlstadt's restructuring of `repository_format_configure()` into a single if-else chain that computes a local `hash` variable with strict priority order: explicit command-line `--object-format` always wins; otherwise an existing repository's detected algorithm is reused; failing that, `GIT_DEFAULT_HASH`, then `init.defaultObjectFormat`, then `GIT_HASH_DEFAULT` (SHA-256 under breaking-changes builds). v5 has now been posted, addressing both of Junio's pending suggestions: (1) the test-isolation bug in `t/t0001-init.sh` is fixed by moving `test_when_finished "test_unconfig --global init.defaultObjectFormat"` registration to the top level (outside the subshell) and using `git config --global` directly inside the subshell, and (2) the redundant `repo_fmt->hash_algo != GIT_HASH_UNKNOWN` conjunct is dropped from the `repo_fmt->version >= 0` condition, simplifying it to `else if (repo_fmt->version >= 0)`. The topic is expected to be queued in `next` or `seen` in an upcoming "What's cooking" report; it is not yet recorded as merged to any integration branch. The patch does not apply to `maint`, as `WITH_BREAKING_CHANGES=1` is a forward-looking flag for Git 3.0 testing only.

Key technical details:
- Build flag: `WITH_BREAKING_CHANGES=1` (enables Git v3 behavior).
- Command: `git init` and `git rev-parse --show-object-format` (now returns `sha256` under Git v3 for *new* repositories).
- Subsystem: repository initialization (`setup.c`).
- New symbol: `GIT_HASH_DEFAULT` (sets default object format; initialized to `SHA1_LEGACY`).
- Functions: `read_repository_format()` and `repository_format_configure()` (restructured as a single if-else chain computing a local `hash` variable with priority: CLI `--object-format` > existing repo `hash_algo` > `GIT_DEFAULT_HASH` env > `init.defaultObjectFormat` config > `GIT_HASH_DEFAULT` build default; the fatal "attempt to reinitialize repository with different hash" check resides in the `repo_fmt->version >= 0` block, now simplified to `else if (repo_fmt->version >= 0)` without the redundant `hash_algo != GIT_HASH_UNKNOWN` test; `repo_fmt->hash_algo` is assigned once from the computed `hash` at the end).
- Test coverage: expanded in `t/t0001-init.sh`; v5 fixes the test-isolation bug in the third test ('re-init does not modify hash from config') by registering `test_when_finished` at the top level and using `git config --global` directly inside the subshell, ensuring cleanup executes in the parent shell on both dash and bash.

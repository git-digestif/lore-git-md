Thread identity: inquiry about Git v3 default object format for new repositories; thread root by Adam Dinwoodie. Series version: v3 (third iteration, latest from brian m. carlstadt). Thread type: bugfix patch series.

Core problem or goal: determine whether `git init` correctly defaults to SHA-256 (instead of SHA-1) when Git is built with `WITH_BREAKING_CHANGES=1`, as this flag is intended to enable Git v3 behavior. The issue was confirmed as a bug, and the fix by brian m. carlstadt ensures `git init` respects the breaking-changes flag by defaulting to SHA-256 for *new* repositories while preventing silent reinitialization of existing repositories with a different hash algorithm. The patch targets the default object format selection logic in `setup.c`.

Current status: under review. The latest iteration (v3) refines v2 by removing a now-inaccurate comment about reinitialization safety and switching tests to use the standard `$GIT_TEST_BUILTIN_HASH` variable. The patch does not apply to `maint`, as `WITH_BREAKING_CHANGES=1` is a forward-looking flag for Git 3.0 testing only. The fix resolves two critical issues: (1) defaulting to `GIT_HASH_DEFAULT` (SHA-256 under Git v3) for *new* repositories, and (2) preventing silent reinitialization of existing repositories with an incompatible hash algorithm. Junio C Hamano has accepted brian m. carlstadt's clarification that a command-line `--object-format` mismatch is fatal on reinitialization while `GIT_DEFAULT_HASH` and `init.defaultObjectFormat` are silently ignored in that case, closing that line of questioning. The thread remains under review with no approval yet; a v4 is anticipated to address the remaining concerns about the commit message and test isolation. brian m. carlstadt has replied to several earlier questions (see participant positions).

Key technical details:
- Build flag: `WITH_BREAKING_CHANGES=1` (enables Git v3 behavior).
- Command: `git init` and `git rev-parse --show-object-format` (now returns `sha256` under Git v3 for *new* repositories).
- Subsystem: repository initialization (`setup.c`).
- New symbol: `GIT_HASH_DEFAULT` (sets default object format).
- Functions: `read_repository_format()` (latent bug resolved) and `repository_format_configure()` (restructured in v3 so that an explicit command-line `--object-format` always wins; environment `GIT_DEFAULT_HASH`, config `init.defaultObjectFormat`, and build-time default `GIT_HASH_DEFAULT` are consulted only for brand-new repositories or those with no detected hash algorithm; attempting to reinitialize an existing repository with a different hash via `--object-format` dies with "attempt to reinitialize repository with different hash", while reinitialization preserves the original hash even if `init.defaultObjectFormat` or `GIT_DEFAULT_HASH` specify something else).
- Test coverage: expanded in `t/t0001-init.sh`; v3 switches from hardcoded expectations to `$GIT_TEST_BUILTIN_HASH`, covering default object format selection for new repos, refusal to reinitialize with a mismatched `--object-format`, and confirmation that reinitialization does not alter the hash when `init.defaultObjectFormat` disagrees.

Open questions and loose ends:
- Junio C Hamano's remaining concerns about v3: (1) why the commit message does not explain that `GIT_HASH_DEFAULT` is initialized to `SHA1_LEGACY` and thus not treated as "unspecified" when deciding whether to default to SHA-256; (2) whether the "repository with no detected hash algorithm" state currently exists or represents a future "first-use-determines-hash" mode; and (3) whether `sane_unset GIT_DEFAULT_HASH` in the new tests without restoring the prior value could pollute the environment for subsequent tests in `t/t0001-init.sh`, potentially causing flaky failures. These are expected to be addressed in v4.
- The reinitialization-semantics question (whether to retain cautionary comment text distinguishing CLI `--object-format` from config/env `init.defaultObjectFormat`/`GIT_DEFAULT_HASH`, and whether global `init.defaultObjectFormat` counts as user specification) has been resolved: Junio accepted brian's explanation that CLI mismatch is fatal while config/env are silently ignored on reinitialization, and that global config counts as specification for new repositories.
- brian m. carlstadt has agreed to expand the commit message to explain the `GIT_HASH_DEFAULT`/`SHA1_LEGACY` initialization and stated that a "no detected hash algorithm" state should not occur in current code paths (including clone) but the code defensively handles it as a potential future "first-use-determines-hash" mode.
- CI results for the fix (platform-specific regressions or edge cases) are pending but not expected to block integration.
- Future "empty repository" feature (allowing hash-agnostic initialization until first push) was noted by brian m. carlstadt as requiring protocol changes and not currently planned. If implemented, it could coexist with the current patch via a separate configuration option (e.g., `extensions.potentialObjectFormat`). This is not a blocker.
- Documentation updates or additional safeguards for downstream consumers (e.g., Nixpkgs) may be addressed in follow-up work.

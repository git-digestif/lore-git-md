Thread identity: inquiry about Git v3 default object format for new repositories; thread root by Adam Dinwoodie. Series version: not applicable (self-contained bugfix).

Core problem or goal: determine whether `git init` correctly defaults to SHA-256 (instead of SHA-1) when Git is built with `WITH_BREAKING_CHANGES=1`, as this flag is intended to enable Git v3 behavior. The issue was confirmed as a bug, and a fix by brian m. carlson ensures `git init` respects the breaking-changes flag by defaulting to SHA-256 for *new* repositories. The patch targets the default object format selection logic in `setup.c`.

Current status: bug confirmed and fix implemented for new repositories, but Junio C Hamano identified two critical issues: (1) a latent bug in the existing code where `read_repository_format()` forces the hash algorithm to `GIT_HASH_SHA1_LEGACY` when `version == -1`, overriding the intended default, and (2) a regression in the patch where `repository_format_configure()` lacks a guard to prevent silently overwriting an existing repository’s object format during reinitialization. Junio proposes a refactor to restructure the `if/else` cascade in `repository_format_configure()` to ensure default-setting logic (command-line, environment, config, or built-in) only executes when `repo_fmt->version < 0` (new repositories). For existing repositories (`version >= 0`), the code should preserve the current format or fail if an incompatible hash is specified, aligning with the ref-storage logic. The patch requires revision to address these issues before integration. CI results remain pending.

Key technical details:
- Build flag: `WITH_BREAKING_CHANGES=1` (intended to enable Git v3 behavior).
- Command: `git init` and `git rev-parse --show-object-format` (now correctly returns `sha256` under Git v3 for *new* repositories).
- Subsystem: repository initialization (`setup.c`).
- New symbol: `GIT_HASH_DEFAULT` (used to set the default object format).
- Functions: `read_repository_format()` (latent bug) and `repository_format_configure()` (regression).
- On-disk implication: default object format for *new* repositories now aligns with Git v3 expectations, but *existing* repositories are silently clobbered on reinitialization due to missing guards.
- Test coverage: new test in `t/t0001-init.sh` verifies the fix for breaking-changes and non-breaking-changes scenarios for new repositories; Junio’s proposed test (included in prior email) verifies the reinitialization edge case.

Open questions and loose ends:
- CI results for the fix (platform-specific regressions or edge cases).
- Whether the current design might need revisiting if a future "empty repository" feature (allowing hash-agnostic initialization until first push) is implemented. brian m. carlson noted this would require protocol changes and is not currently planned, but if implemented, it could coexist with the current patch via a separate configuration option (e.g., `extensions.potentialObjectFormat`). This is not a blocker for the current patch.
- How `git init` should handle reinitialization of existing repositories under `WITH_BREAKING_CHANGES=1`: preserve the existing format (with or without a warning), fail, or convert. Junio favors preserving the format with a warning, and his proposed refactor would implement this behavior.
- Whether `git init` should similarly preserve the *reference storage format* (e.g., reftable vs. reffiles) on reinitialization; Patrick Steinhardt is CC’ed for input on this point.
- Whether additional safeguards or documentation updates for downstream consumers (e.g., Nixpkgs) will be included.

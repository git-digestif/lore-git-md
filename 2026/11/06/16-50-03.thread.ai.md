Thread identity: inquiry about Git v3 default object format for new repositories; thread root by Adam Dinwoodie. Series version: not applicable (self-contained bugfix).

Core problem or goal: determine whether `git init` correctly defaults to SHA-256 (instead of SHA-1) when Git is built with `WITH_BREAKING_CHANGES=1`, as this flag is intended to enable Git v3 behavior. The issue was confirmed as a bug, and a fix by brian m. carlson ensures `git init` respects the breaking-changes flag by defaulting to SHA-256. The patch is minimal, targeting only the default object format selection logic in `setup.c`.

Current status: bug confirmed and fix implemented, but Junio C Hamano identified a critical edge case: `git init` in an *already initialized* repository under `WITH_BREAKING_CHANGES=1` silently overwrites the existing object format with SHA-256, which may not be intended. Junio proposes three possible behaviors for reinitialization: (1) convert the repository to the new default (impractical), (2) preserve the existing format and warn, or (3) fail loudly if the format differs. The current patch implements none of these, instead clobbering the existing format. Junio’s test case demonstrates the issue, and he suggests the patch should be updated to implement one of the three behaviors, with #2 (preserve and warn) being the most reasonable. The patch is otherwise ready for integration but now requires revision to handle reinitialization safely. CI results remain pending.

Key technical details:
- Build flag: `WITH_BREAKING_CHANGES=1` (intended to enable Git v3 behavior).
- Command: `git init` and `git rev-parse --show-object-format` (now correctly returns `sha256` under Git v3 for *new* repositories).
- Subsystem: repository initialization (`setup.c`).
- New symbol: `GIT_HASH_DEFAULT` (used to set the default object format).
- On-disk implication: default object format for *new* repositories now aligns with Git v3 expectations, but *existing* repositories are silently clobbered on reinitialization.
- Test coverage: new test in `t/t0001-init.sh` verifies the fix for breaking-changes and non-breaking-changes scenarios for new repositories; Junio’s proposed test (included in the email) verifies the reinitialization edge case.

Open questions and loose ends:
- CI results for the fix (platform-specific regressions or edge cases).
- Whether the current design might need revisiting if a future "empty repository" feature (allowing hash-agnostic initialization until first push) is implemented. brian m. carlson noted this would require protocol changes and is not currently planned, but if implemented, it could coexist with the current patch via a separate configuration option (e.g., `extensions.potentialObjectFormat`). This is not a blocker for the current patch.
- How `git init` should handle reinitialization of existing repositories under `WITH_BREAKING_CHANGES=1`: preserve the existing format (with or without a warning), fail, or convert. Junio favors preserving the format with a warning.
- Whether `git init` should similarly preserve the *reference storage format* (e.g., reftable vs. reffiles) on reinitialization; Patrick Steinhardt is CC’ed for input on this point.
- Whether additional safeguards or documentation updates for downstream consumers (e.g., Nixpkgs) will be included.

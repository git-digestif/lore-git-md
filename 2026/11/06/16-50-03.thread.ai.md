Thread identity: inquiry about Git v3 default object format for new repositories; thread root by Adam Dinwoodie. Series version: v3 (third iteration, latest from brian m. carlstadt). Thread type: bugfix patch series.

Core problem or goal: determine whether `git init` correctly defaults to SHA-256 (instead of SHA-1) when Git is built with `WITH_BREAKING_CHANGES=1`, as this flag is intended to enable Git v3 behavior. The issue was confirmed as a bug, and the fix by brian m. carlstadt ensures `git init` respects the breaking-changes flag by defaulting to SHA-256 for *new* repositories while preventing silent reinitialization of existing repositories with a different hash algorithm. The patch targets the default object format selection logic in `setup.c`.

Current status: merged to `master` (per prior report; date unknown). The latest iteration (v3) refines v2 by removing a now-inaccurate comment about reinitialization safety and switching tests to use the standard `$GIT_TEST_BUILTIN_HASH` variable. The patch does not apply to `maint`, as `WITH_BREAKING_CHANGES=1` is a forward-looking flag for Git 3.0 testing only. The fix resolves two critical issues: (1) defaulting to `GIT_HASH_DEFAULT` (SHA-256 under Git v3) for *new* repositories, and (2) preventing silent reinitialization of existing repositories with an incompatible hash algorithm.

Key technical details:
- Build flag: `WITH_BREAKING_CHANGES=1` (enables Git v3 behavior).
- Command: `git init` and `git rev-parse --show-object-format` (now returns `sha256` under Git v3 for *new* repositories).
- Subsystem: repository initialization (`setup.c`).
- New symbol: `GIT_HASH_DEFAULT` (sets default object format).
- Functions: `read_repository_format()` (latent bug resolved) and `repository_format_configure()` (restructured in v3 so that an explicit command-line `--object-format` always wins; environment `GIT_DEFAULT_HASH`, config `init.defaultObjectFormat`, and build-time default `GIT_HASH_DEFAULT` are consulted only for brand-new repositories or those with no detected hash algorithm; attempting to reinitialize an existing repository with a different hash dies with "attempt to reinitialize repository with different hash", and reinitialization preserves the original hash even if `init.defaultObjectFormat` specifies something else).
- Test coverage: expanded in `t/t0001-init.sh`; v3 switches from hardcoded expectations to `$GIT_TEST_BUILTIN_HASH`, covering default object format selection for new repos, refusal to reinitialize with a mismatched `--object-format`, and confirmation that reinitialization does not alter the hash when `init.defaultObjectFormat` disagrees.

Open questions and loose ends:
- CI results for the fix (platform-specific regressions or edge cases) are pending but not expected to block integration.
- Future "empty repository" feature (allowing hash-agnostic initialization until first push) was noted by brian m. carlstadt as requiring protocol changes and not currently planned. If implemented, it could coexist with the current patch via a separate configuration option (e.g., `extensions.potentialObjectFormat`). This is not a blocker.
- Documentation updates or additional safeguards for downstream consumers (e.g., Nixpkgs) may be addressed in follow-up work.

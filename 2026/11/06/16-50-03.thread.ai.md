Thread identity: inquiry about Git v3 default object format for new repositories; thread root by Adam Dinwoodie. Series version: not applicable (self-contained bugfix).

Core problem or goal: determine whether `git init` correctly defaults to SHA-256 (instead of SHA-1) when Git is built with `WITH_BREAKING_CHANGES=1`, as this flag is intended to enable Git v3 behavior. The issue was confirmed as a bug, and a revised fix by brian m. carlson ensures `git init` respects the breaking-changes flag by defaulting to SHA-256 for *new* repositories while preventing silent reinitialization of existing repositories with a different hash algorithm. The patch targets the default object format selection logic in `setup.c`.

Current status: **merged to `master`**. Junio C Hamano confirmed the revised patch (`[PATCH v2] setup: fix hash algorithm detection`) is ready for integration and has merged it to `master`. The patch does not apply to `maint`, as `WITH_BREAKING_CHANGES=1` is a forward-looking flag for Git 3.0 testing only. The fix resolves two critical issues: (1) defaulting to `GIT_HASH_DEFAULT` (SHA-256 under Git v3) for *new* repositories, and (2) preventing silent reinitialization of existing repositories with an incompatible hash algorithm. The restructured `repository_format_configure()` logic is praised as "much simpler and more straightforward" by Junio.

Key technical details:
- Build flag: `WITH_BREAKING_CHANGES=1` (enables Git v3 behavior).
- Command: `git init` and `git rev-parse --show-object-format` (now returns `sha256` under Git v3 for *new* repositories).
- Subsystem: repository initialization (`setup.c`).
- New symbol: `GIT_HASH_DEFAULT` (sets default object format).
- Functions: `read_repository_format()` (latent bug resolved) and `repository_format_configure()` (restructured to guard default-setting logic and prevent silent reinitialization).
- On-disk implication: default object format for *new* repositories aligns with Git v3 expectations; *existing* repositories are preserved during reinitialization (or fail if an incompatible hash is specified).
- Test coverage: expanded in `t/t0001-init.sh` to verify default selection, reinitialization rejection, and config override behavior.

Open questions and loose ends:

- Future "empty repository" feature (allowing hash-agnostic initialization until first push) was noted by brian m. carlson as requiring protocol changes and not currently planned. If implemented, it could coexist with the current patch via a separate configuration option (e.g., `extensions.potentialObjectFormat`). This is not a blocker for the current patch.

Thread identity: inquiry about Git v3 default object format for new repositories; thread root by Adam Dinwoodie. Series version: v3 (third iteration, latest from brian m. carlstadt). Thread type: bugfix patch series.

Core problem or goal: determine whether `git init` correctly defaults to SHA-256 (instead of SHA-1) when Git is built with `WITH_BREAKING_CHANGES=1`, as this flag is intended to enable Git v3 behavior. The issue was confirmed as a bug, and the fix by brian m. carlstadt ensures `git init` respects the breaking-changes flag by defaulting to SHA-256 for *new* repositories while preventing silent reinitialization of existing repositories with a different hash algorithm. The patch targets the default object format selection logic in `setup.c`.

Current status: under review. The latest iteration (v3) refines v2 by removing a now-inaccurate comment about reinitialization safety and switching tests to use the standard `$GIT_TEST_BUILTIN_HASH` variable. The patch does not apply to `maint`, as `WITH_BREAKING_CHANGES=1` is a forward-looking flag for Git 3.0 testing only. The fix resolves two critical issues: (1) defaulting to `GIT_HASH_DEFAULT` (SHA-256 under Git v3) for *new* repositories, and (2) preventing silent reinitialization of existing repositories with an incompatible hash algorithm. Junio C Hamano is currently reviewing the v3 commit message, comment removals, and test cases, and has raised multiple questions about logic and semantics (see open questions). brian m. carlstadt has replied to several of those questions (see participant positions); a v4 is anticipated but not yet posted.

Key technical details:
- Build flag: `WITH_BREAKING_CHANGES=1` (enables Git v3 behavior).
- Command: `git init` and `git rev-parse --show-object-format` (now returns `sha256` under Git v3 for *new* repositories).
- Subsystem: repository initialization (`setup.c`).
- New symbol: `GIT_HASH_DEFAULT` (sets default object format).
- Functions: `read_repository_format()` (latent bug resolved) and `repository_format_configure()` (restructured in v3 so that an explicit command-line `--object-format` always wins; environment `GIT_DEFAULT_HASH`, config `init.defaultObjectFormat`, and build-time default `GIT_HASH_DEFAULT` are consulted only for brand-new repositories or those with no detected hash algorithm; attempting to reinitialize an existing repository with a different hash dies with "attempt to reinitialize repository with different hash", and reinitialization preserves the original hash even if `init.defaultObjectFormat` specifies something else).
- Test coverage: expanded in `t/t0001-init.sh`; v3 switches from hardcoded expectations to `$GIT_TEST_BUILTIN_HASH`, covering default object format selection for new repos, refusal to reinitialize with a mismatched `--object-format`, and confirmation that reinitialization does not alter the hash when `init.defaultObjectFormat` disagrees.

Open questions and loose ends:
- Junio C Hamano has raised multiple substantive concerns about v3: (1) why the commit message does not explain that `GIT_HASH_DEFAULT` is initialized to `SHA1_LEGACY` and thus not treated as "unspecified" when deciding whether to default to SHA-256; (2) whether the "repository with no detected hash algorithm" state currently exists or represents a future "first-use-determines-hash" mode; (3) whether the first two lines of the removed reinitialization-safety comment should be retained as cautionary text even if the final sentence was inaccurate; (4) a semantic edge case about whether `init.defaultObjectFormat` set in `~/.gitconfig` counts as "the user has specified" an algorithm alongside command-line `--object-format` and `GIT_DEFAULT_HASH`; and (5) whether `sane_unset GIT_DEFAULT_HASH` in the new tests without restoring the prior value could pollute the environment for subsequent tests, potentially causing flaky failures.
- brian m. carlstadt has replied to points (1), (2), and the combined (3)+(4): he agrees to expand the commit message to explain the `GIT_HASH_DEFAULT`/`SHA1_LEGACY` initialization; he states that a "no detected hash algorithm" state should not occur in current code paths (including clone) but the code defensively handles it as a potential future "first-use-determines-hash" mode; he concedes the comment should be rewritten to distinguish command-line `--object-format` (fatal on mismatch with existing repo) from `init.defaultObjectFormat` and `GIT_DEFAULT_HASH` (silently ignored on reinitialization), and acknowledges that a global `init.defaultObjectFormat` in `~/.gitconfig` counts as user specification for new repositories. These clarifications imply a v4 adjusting commit message wording and possibly restoring part of the cautionary comment.
- Junio's remaining concern about test isolation with `sane_unset GIT_DEFAULT_HASH` in `t/t0001-init.sh` has not yet been addressed by brian; expected to be handled in v4.
- CI results for the fix (platform-specific regressions or edge cases) are pending but not expected to block integration.
- Future "empty repository" feature (allowing hash-agnostic initialization until first push) was noted by brian m. carlstadt as requiring protocol changes and not currently planned. If implemented, it could coexist with the current patch via a separate configuration option (e.g., `extensions.potentialObjectFormat`). This is not a blocker.
- Documentation updates or additional safeguards for downstream consumers (e.g., Nixpkgs) may be addressed in follow-up work.

Thread identity: inquiry about Git v3 default object format for new repositories; thread root by Adam Dinwoodie. Series version: not applicable (self-contained bugfix).

Core problem or goal: determine whether `git init` correctly defaults to SHA-256 (instead of SHA-1) when Git is built with `WITH_BREAKING_CHANGES=1`, as this flag is intended to enable Git v3 behavior. The issue was confirmed as a bug, and a fix by brian m. carlson ensures `git init` respects the breaking-changes flag by defaulting to SHA-256 for *new* repositories. The patch targets the default object format selection logic in `setup.c`.

Current status: bug confirmed and fix implemented for new repositories, but Junio C Hamano identified two critical issues: (1) a latent bug in the existing code where `read_repository_format()` forces the hash algorithm to `GIT_HASH_SHA1_LEGACY` when `version == -1`, overriding the intended default, and (2) a regression in the patch where `repository_format_configure()` lacks a guard to prevent silently overwriting an existing repository’s object format during reinitialization. Junio proposed a refactor to restructure the `if/else` cascade in `repository_format_configure()` to ensure default-setting logic (command-line, environment, config, or built-in) only executes when `repo_fmt->version < 0` (new repositories). For existing repositories (`version >= 0`), the code should preserve the current format or fail if an incompatible hash is specified, aligning with the ref-storage logic. Patrick Steinhardt has now proposed an alternative refactor that reorders the logic for improved readability and consistency with the ref-storage and object-storage format handling. The patch requires revision to address these issues before integration. CI results remain pending.

Key technical details:
- Build flag: `WITH_BREAKING_CHANGES=1` (intended to enable Git v3 behavior).
- Command: `git init` and `git rev-parse --show-object-format` (now correctly returns `sha256` under Git v3 for *new* repositories).
- Subsystem: repository initialization (`setup.c`).
- New symbol: `GIT_HASH_DEFAULT` (used to set the default object format).
- Functions: `read_repository_format()` (latent bug) and `repository_format_configure()` (regression and proposed refactors).
- On-disk implication: default object format for *new* repositories now aligns with Git v3 expectations, but *existing* repositories are silently clobbered on reinitialization due to missing guards. Both Junio’s and Patrick’s refactors address this by preserving the existing format during reinitialization.
- Test coverage: new test in `t/t0001-init.sh` verifies the fix for breaking-changes and non-breaking-changes scenarios for new repositories; Junio’s proposed test (included in prior email) verifies the reinitialization edge case. No new tests introduced by Patrick’s refactor, as it is a mechanical reorganization.

Open questions and loose ends:
- CI results for the fix (platform-specific regressions or edge cases).
- Whether the current design might need revisiting if a future "empty repository" feature (allowing hash-agnostic initialization until first push) is implemented. brian m. carlson noted this would require protocol changes and is not currently planned, but if implemented, it could coexist with the current patch via a separate configuration option (e.g., `extensions.potentialObjectFormat`). This is not a blocker for the current patch.
- How `git init` should handle reinitialization of existing repositories under `WITH_BREAKING_CHANGES=1`: preserve the existing format (with or without a warning), fail, or convert. Junio favors preserving the format with a warning, and both refactors implement this behavior. No dissenting positions have been raised.
- Whether `git init` should similarly preserve the *reference storage format* (e.g., reftable vs. reffiles) on reinitialization; Patrick Steinhardt is CC’ed for input on this point and has implicitly endorsed the consistency argument by proposing a uniform approach across all three format types (hash, ref storage, and object storage).
- Whether additional safeguards or documentation updates for downstream consumers (e.g., Nixpkgs) will be included.

Participant positions:
- **Adam Dinwoodie**: raised the inquiry; confirmed the behavior on Git v2.56.0, `next`, and `main`.
- **brian m. carlson**: confirmed the bug, prepared the fix, and authored the patch. Position: the current behavior was incorrect and must default to SHA-256 under `WITH_BREAKING_CHANGES=1`. Clarified that the patch is necessary regardless of any future "empty repository" design. No objections or alternative proposals raised yet regarding the reinitialization edge case or the proposed refactors.
- **Junio C Hamano**: acknowledged the patch is correct for its stated goal (new repositories) but identified two critical issues: (1) a latent bug in `read_repository_format()` and (2) a regression in `repository_format_configure()` where reinitialization silently clobbers the object format. Proposed a refactor to guard default-setting logic and align behavior with the ref-storage logic. Position: the patch must be updated to handle reinitialization safely before integration.
- **Patrick Steinhardt**: reviewed Junio’s proposed refactor and suggested an alternative restructuring of `repository_format_configure()` to improve readability and consistency with the ref-storage and object-storage format handling. Position: the refactor should uniformly handle all three format types (hash, ref storage, and object storage) by validating the desired format against the existing repository’s format at the end of the function, rather than scattering validation checks through the `if/else` cascade. This is a stylistic refinement, not a competing fix.

Related work: part of broader Git v3 preparation, particularly for Nixpkgs compatibility. The fix is self-contained and not part of a larger series.

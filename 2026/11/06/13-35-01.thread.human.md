This thread began as a feature request from Alejandro Colomar for `git ls-files` to add a `--type` filter (e.g., `--type f` to exclude symlinks), aiming to replace slower workarounds like `find` or post-processing `git ls-files --format=%(objectmode)`. Alejandro demonstrated the ergonomic drawbacks of these workarounds—particularly for filenames with spaces—and volunteered to implement the feature if the community supported it. D. Ben Knoble offered a surface-level suggestion about the existing `--format` workaround but did not engage with the proposal’s design or necessity.

The thread has now taken a decisive turn with Junio C Hamano’s response. As the maintainer, Junio firmly rejects the proposal, arguing that `git ls-files` is a plumbing command meant for pipeline building, not a Swiss Army knife with arbitrary filtering options. He questions the slippery slope of such requests (e.g., "what’s next, `--size`?") and instead advocates for improving pipeline construction skills. His reply includes a concrete example of how to achieve the same result with existing tools: `git ls-files -z -s | sed -z '/^120000 /d;s/^[0-7]* //' | xargs -0 ...`. While his tone is instructional—offering tips on pipeline readability—his message is clear: the proposal is unlikely to be accepted. The discussion has shifted from "will this be implemented?" to "how can this be done with existing tools?"—a common outcome for feature requests targeting plumbing commands. Unless Alejandro can reframe the proposal as a more principled improvement, the thread is effectively closed.

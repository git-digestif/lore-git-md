Core problem or goal
Reduce end-to-end CI runtime in Git's GitLab pipelines by addressing specific bottlenecks in test execution, SDK installation, and build configuration. The series targets both GitLab-specific and generic CI environments, with measurable speedups demonstrated across macOS, Fedora, and Windows runners.

Under review (v2 posted; v1 previously reviewed). Junio C Hamano has stated he has no technical objections and finds the series "interesting" and "fully made sense," signaling likely queuing for `next` unless other reviewers raise substantive issues. No merge status reported; series is not yet in Junio's integration branches.

Key technical details
- Files touched: `.gitlab-ci.yml`, `ci/install-sdk.ps1`, `ci/run-build-and-tests.sh`, test scripts `t0027-auto-crlf.sh`, `t0027`, `t1092-sparse-checkout-compatibility.sh`, `t5551-http-fetch-smart.sh`, `t5559`
- Subsystems: CI infrastructure, test suite, build system (Meson)
- New/renamed symbols: None (CI configuration flags and test optimizations only)
- Behavior changes:
  - Git for Windows SDK installation now uses `tar(1)` instead of Extract-Archive (3m → 10s), with strict error handling and suppressed progress output (patch 1/7). **Portability assumption**: The script assumes a BSD-derived `tar` capable of handling ZIP archives; Junio C Hamano initially suggested documenting this dependency in a comment but has since withdrawn the suggestion after Patrick Steinhardt explained that `bsdtar` (based on `libarchive`) is now distributed with Windows by default, making the assumption broadly valid.
  - SDK archive cache removed in v2 (previously saved download time; cache key included SDK URL to prevent staleness, but Junio raised staleness concerns)
  - `t0027` repository reset logic optimized (Windows: >10m → 6m) via single `rm` + single `git checkout` for all five files (previously ten separate processes)
  - `t0027-auto-crlf.sh` now caches expected output in `.expect` and `.ws-expect` files, avoiding repeated `tr`/`sed` invocations (Windows: 480s → 380s; macOS: 71s → 54s (24% reduction); 20–25% reduction across platforms). Adopts Junio’s loop-based refactoring for readability while preserving performance. Additionally, consolidates `rm` and `git checkout` invocations in `checkout_files()`, reducing process overhead and yielding a 20% runtime reduction (Windows: ~10m → ~7.5m). Junio C Hamano suggested adding an explicit `paths=` assignment before the loop in `checkout_files()` to clarify the variable’s initialization state; Patrick Steinhardt has agreed to this defensive programming tweak, which will appear in the next revision.
  - **Patch 5/7**: The current implementation caches expected output files lazily during `compare_files()` calls, delivering a 20–25% runtime reduction (Windows: 480s → 380s; macOS: 71s → 54s). Torsten Bögershausen proposed an alternative that precomputes all expected output files upfront in a dedicated test phase, eliminating runtime `tr` calls entirely. Patrick Steinhardt benchmarked the alternative and found no meaningful performance difference, opting to retain the simpler incremental optimization. The decision closes the discussion on this patch, leaving it unchanged.
  - `t5551-http-fetch-smart.sh` and `t5559` now use reftable backend (macOS: 20m → 2m per test (10x speedup); Linux: runtime halved). The change is limited to two lines in each test script, switching the ref backend without altering test logic, as the focus is on HTTP fetch behavior rather than ref storage performance.
  - `t1092-sparse-checkout-compatibility.sh` now uses template-based repository initialization (Windows: >10m → ~7m) by creating one-time template repositories (`full-checkout.template`, `sparse-checkout.template`, `sparse-index.template`) during the `setup template repositories` phase and copying them for each test iteration, reducing redundant `git sparse-checkout` and `git config` calls.
  - Meson builds now use `-Doptimize=debug` flag for faster compilation (Linux/macOS) and `--buildtype=debugoptimized` (Fedora: 2100s → 1000s; SHA256 hashing 500MB blob: 9.6s → 1.5s at `-O2`). The change aligns Meson flags with Git’s traditional Makefile defaults (`-g -O2`).
  - Windows build artifacts now exclude ~1,800 intermediate "*.obj" files (patch 2/7), cutting artifact download/extraction time from 34s to 17s per test job. The exclusion rule (`exclude: - build/**/*.obj`) is added to the `build:msvc-meson` job in `.gitlab-ci.yml`.
- On-disk format: No changes
- Test coverage: Directly modifies test scripts (`t0027-auto-crlf.sh`, `t0027`, `t1092-sparse-checkout-compatibility.sh`, `t5551-http-fetch-smart.sh`, `t5559`); no new test files added

Open questions and loose ends
- Windows runners remain the critical path despite improvements (author notes this as a remaining bottleneck).
- SHA256 performance with `-O0` optimization is flagged as poor but addressed in this series via `-O2` for Fedora jobs.
- **Resolved open question**: Whether to adopt Torsten Bögershausen’s alternative implementation for `t0027-auto-crlf.sh` (patch 5/7). Patrick Steinhardt benchmarked the alternative and found no meaningful performance difference, opting to retain the simpler incremental optimization. Torsten Bögershausen has accepted this decision, closing the discussion.
- **Resolved open question**: Portability of `tar -xf` in `ci/install-sdk.ps1` (patch 1/7). Junio C Hamano raised a concern about the script’s assumption of a BSD-derived `tar` capable of handling ZIP archives but has since withdrawn his suggestion to add a comment after Patrick Steinhardt explained that `bsdtar` (based on `libarchive`) is now distributed with Windows by default, making the assumption broadly valid. The discussion is now closed without requiring changes.
- **Resolved open question**: Explicit initialization of the `paths` variable in `t0027-auto-crlf.sh` (patch 4/7). Junio C Hamano suggested adding `paths=` before the loop in `checkout_files()` to make the variable’s empty state explicit. Patrick Steinhardt agreed ("Yeah, makes sense"), and this defensive programming tweak will appear in the next revision.
- **Future work**: Patrick Steinhardt floats the idea of unifying GitHub Workflows with the GitLab CI script, now that the performance issues that previously led to a revert have been resolved. He defers this decision to Johannes Schindelin (Dscho), the maintainer of Git for Windows, and keeps it out of the current series.

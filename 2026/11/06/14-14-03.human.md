This is the fourth iteration of Miklos Vajna’s patch series to improve the performance of `git log --follow` when tracking file history across merge-heavy histories. The series now consists of six patches, up from four in v3, reflecting feedback from Patrick Steinhardt, who identified a correctness regression in the previous version.

The key change in v4 is the addition of a new patch (6/6) that fixes the regression Patrick reported: when one side of a merge renamed a file and the other side (whose version was dropped in the merge) edited the old name, the history was incorrectly lost. The fix restores the missing history while preserving the performance improvement, though the commit message notes that the speedup is slightly reduced (37 seconds for the linux.git test case, down from the earlier claim but still an improvement). Another bug was also fixed in patch 1/6, where `--diff-merges=first-parent` lost history when combined with `--follow`.

Patrick’s reply is a mix of process feedback and technical observation. He gently reminds Miklos that review comments should be addressed directly in replies rather than only in the next version’s cover letter, emphasizing the mailing list’s preference for visible discussion. He also requests a `range-diff` in future revisions to make it easier to track changes between versions, a common practice in Git development. While he acknowledges the fix for the regression, he questions the decision to split it into a separate patch, noting that the regression was introduced in the preceding commit and might logically belong there.

The series remains focused on the log subsystem, with no new APIs or on-disk format changes, and the expanded test coverage (including Patrick’s reproducer) should help validate correctness. The performance improvement is now more modest but still meaningful, and the fixes address real-world edge cases. The discussion suggests the series is converging, though Patrick’s feedback indicates there may still be room for structural refinement before it’s ready for merging.

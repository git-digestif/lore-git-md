Thread identity: standalone feature request for `git ls-files` to add a `--type` filter option (e.g., `--type f` to exclude symlinks). Originating author: Alejandro Colomar. Thread type: feature proposal, now closed by maintainer feedback.

Core problem or goal: enable `git ls-files` to filter output by file type (e.g., exclude symlinks) natively, improving workflow efficiency for tools like `grep`/`sed` in large directories (e.g., built Linux kernel trees). The goal was to replace slower workarounds (e.g., `find . -type f` or `git ls-files --format=%(objectmode) | grep 100644`) with a Git-native solution that avoids post-processing complexity, particularly for filenames with spaces.

Current status: proposal rejected by the maintainer (Junio C Hamano). No patch versions exist, and the thread is now focused on demonstrating how to achieve the same result using existing Git plumbing and pipeline tools. Junio explicitly argues that `git ls-files` is a plumbing command and should not grow arbitrary filtering options, citing potential feature creep (e.g., `--size`). He provided a concise example of how to filter symlinks using `git ls-files -z -s | sed` and `xargs`, framing this as a more appropriate solution than adding a new flag.

Key technical details: the proposed feature would have leveraged Git’s existing `%(objectmode)` tracking (e.g., `100644` for regular files, `120000` for symlinks) without requiring on-disk format changes. Junio’s workaround uses `-z -s` to output null-delimited records with object modes, followed by `sed` to filter out symlinks (`120000`) and extract filenames. This approach avoids the ergonomic drawbacks of the author’s earlier workaround (e.g., space handling, command chaining) while staying within Git’s plumbing design philosophy.

Open questions and loose ends: none. The maintainer’s response effectively closes the proposal unless the author can reframe it as a more general or principled improvement.

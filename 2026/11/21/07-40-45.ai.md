This is a bugfix to `git fast-import` that corrects a silent corruption case when an inline file modification is truncated at end-of-input.

The patch addresses a flaw in `file_change_m()` within `builtin/fast-import.c`: when a `M <mode> inline <path>` command appears as the final line of the input stream, the function previously exited its read loop on EOF without ever encountering the required `data` command. It then proceeded to store an uninitialized stack object ID into the tree and exited with status 0, leaving behind a tree entry referencing a non-existent blob that `git fsck` would later flag. The fix restructures the loop from `while (read_next_command(state) != EOF)` into an infinite `for (;;)` loop that calls `read_next_command()` unconditionally at the top, causing the parser to die with an error when it hits EOF instead of a `data` command -- matching the existing behavior of `note_change_n()`, which calls `parse_and_store_blob()` and properly dies on missing data.

The patch includes a regression test in `t/t9300-fast-import.sh` (series D, "fail on inline data cut off at end of input") that feeds a stream ending with an inline `M` command and no data block, asserting that `git fast-import` fails with the message "expected 'data n' command" and that the target ref is not created. The behavioral change is that malformed input now produces an immediate fatal error rather than a silently corrupt commit graph.

A single-patch bugfix from Wonseok Oh addresses a real bug in `git cherry-pick` on orphan (unborn) branches: when starting a cherry-pick sequence before HEAD exists, `sequencer_pick_revisions()` in `sequencer.c` left the `oid` variable uninitialized after `repo_get_oid(r, "HEAD", &oid)` failed, and that garbage value was written to `.git/sequencer/head`, so `git cherry-pick --abort` failed with "Could not parse object" instead of the intended "cannot abort from a branch yet to be born" error. The fix explicitly clears `oid` to the null OID with `oidclr()` when HEAD cannot be resolved (except for `REPLAY_REVERT`, which has its own error path), and adds a regression test to `t/t3510-cherry-pick-sequence.sh` verifying the abort error and that HEAD stays unborn.

Phillip Wood reviewed substantively, endorsing the fix and tracing the uninitialized-variable use back to commit `0f974e2124` (2016). Wonseok Oh agreed to reword the commit message in a v2 to cite that commit, and Phillip has now settled the one open design question: the null OID, rather than the empty file that `update_abort_safety_file()` writes, will be the representation in `.git/sequencer/head` for unborn branches, because older Git versions expect to read a null OID from both state files. A v2 is anticipated but not yet posted, and the series remains under review with no integration status reported.

Phillip also documented several broader behavioral inconsistencies in the sequencer's unborn-branch handling -- aborting a multi-pick sequence on an orphan branch is currently impossible, single-commit reverts on unborn branches are allowed while multi-commit reverts are not, and the null-OID versus empty-file state representation differs between the two state files. Both participants have explicitly agreed to defer those changes to separate follow-up work rather than expanding this patch, so the thread's only remaining action is Wonseok Oh sending the reworded v2.

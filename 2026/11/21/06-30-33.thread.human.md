This thread is a single-patch bugfix from Wonseok Oh addressing a bug in `git cherry-pick` when running a sequence on an unborn (orphan) branch: `sequencer_pick_revisions()` in `sequencer.c` leaves `oid` uninitialized when `repo_get_oid(r, "HEAD", &oid)` fails, and that garbage value gets written to `.git/sequencer/head`, causing `git cherry-pick --abort` to fail with "Could not parse object" instead of the intended "cannot abort from a branch yet to be born". The proposed fix clears `oid` to the null OID in that case, and a regression test is added to `t/t3510-cherry-pick-sequence.sh`. The patch is under review with no integration status reported; Wonseok Oh has agreed to reword the commit message in a v2 to cite commit `0f974e2124` as the origin of the uninitialized-variable use.

Phillip Wood provided a substantive review tracing the root cause to historical commits (`0f974e2124`, `7acaaac275`, `04d3d3cfc4`) and confirmed the null-OID representation for `.git/sequencer/head` on unborn branches for backwards compatibility with older Git versions. Junio C Hamano has now also reviewed, endorsing the commit-message tightening (clarify the `oidclr()`/rollback relationship, describe general undefined-behavior failure modes rather than anecdotal builds, drop filler) and raising a robustness concern about the test: since the cherry-pick fails at the first step leaving HEAD unborn, the test could pass coincidentally if stack variables happen to be zero-initialized. He suggests the test should grep for the specific "cannot abort from a branch yet to be born" error from `--abort` and additionally verify that `.git/sequencer/head` stores `$ZERO_OID`.

Still open: a v2 is expected with the reworded commit message and the hardened test; broader behavioral inconsistencies around aborting multi-pick sequences on orphan branches remain deferred to separate follow-up work per the author's commitment.

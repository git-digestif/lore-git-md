Wonseok Oh has posted version 2 of a two-patch series fixing how `git cherry-pick` handles sequences started on an unborn (orphan) branch. The core bug is that `sequencer_pick_revisions()` in `sequencer.c` left the `oid` variable uninitialized when `HEAD` does not yet exist, causing garbage to be written to `.git/sequencer/head` and making `git cherry-pick --abort` fail with a confusing "Could not parse object" error instead of the intended "cannot abort from a branch yet to be born" message. Patch 1 clears `oid` to the null OID when `repo_get_oid()` fails, and patch 2 -- added in v2 on Phillip Wood's suggestion -- makes `update_abort_safety_file()` write the null OID to `.git/sequencer/abort-safety` rather than an empty file, so both sequencer state files consistently represent an unborn branch in a way older Git versions can parse.

Both Phillip Wood and Junio C Hamano reviewed v1 and asked for changes that v2 now incorporates: the commit message cites the 2016 commit `0f974e2124` that introduced the uninitialized use, describes the general undefined-behavior failure modes rather than anecdotal builds, and the regression test in `t/t3510-cherry-pick-sequence.sh` now verifies that both state files contain `$ZERO_OID` and that `--abort` fails with the exact expected message while leaving `HEAD` untouched. The series remains under review with no integration status reported and no Reviewed-by or Acked-by trailers recorded yet. Broader behavioral questions -- such as whether `sequencer_rollback()` should allow aborting multi-commit sequences on unborn branches at all -- are explicitly deferred to separate follow-up work by the author.

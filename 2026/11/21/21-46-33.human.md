This is a bugfix, specifically the implementation half of a two-patch series from Orgad Shaneh that makes `git fetch --prune-tags` actually clobber changed tags as its documentation promises. The first patch in the series was test-only; this one changes the behavior in `builtin/fetch.c` by prepending a "+" to the implied tag refspec (`+refs/tags/*:refs/tags/*`) whenever `--prune-tags` is active, so that tags which have changed on the remote are force-updated locally instead of being rejected with "would clobber existing tag". The commit message traces the regression to commit 0bc8d71b99 (Git 2.20), which added clobber protection for tags but failed to exempt the `--prune-tags` refspec, arguing this was an oversight rather than intentional design since the flag predates that protection.

The change is tightly scoped: it only affects the automatic tag-following refspec that `--prune-tags` implies, leaving explicit refspecs like `git fetch origin tag foo` untouched, so those still require `--force` even when `fetch.pruneTags` is configured. This addresses a flaw in v1 of the series, which used a global flag that inadvertently forced tags fetched via explicit refspecs. Documentation in `Documentation/git-fetch.adoc` and `Documentation/config/fetch.adoc` is updated to show the forced refspec, and new tests in `t/t5516-fetch-push.sh` verify that `--prune-tags` updates both lightweight and annotated tags and that explicit tag fetches still fail without `--force`.

The patch looks well-crafted and directly addresses a real documentation-versus-behavior mismatch that has existed since Git 2.20. The historical analysis is persuasive, and the test coverage is thorough, checking actual tag object contents rather than just exit codes. The series is at v2, rebased on current master, and remains open pending a substantive ruling from Junio C Hamano, who has questioned whether the original no-force behavior was intentional but has not yet weighed in on the merits.

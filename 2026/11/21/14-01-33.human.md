This is an Outreachy proposal draft (v2) for a feature: making the order in which Git tries promisor remotes during partial-clone fetches configurable by both users and servers. Hussain Sitamouwala is seeking design feedback before writing code, proposing to replace the current fixed ordering -- server-advertised remotes first, then config-file order, with the `extensions.partialClone` remote always last -- with a priority-based system.

The proposal sketches three candidate configuration shapes, favoring `remote.<name>.priority` (Shape A) where lower integers are tried first, though it explicitly defers the final choice to maintainers and notes a competing patch proposing `promisor.fetchOrder`. For server advertisement, it suggests an optional `priority=<n>` field in the existing promisor-remote capability, with defensive parsing to handle malformed or hostile input such as non-numeric values, duplicates, or integer overflow. A key open question is how to store server-supplied priorities separately from user-set values so they do not collide in the same config key, with user values taking precedence.

The author plans a six-patch series beginning with tests that lock in today's behavior and a trace2 event to observe fetch order, followed by a behavior-preserving refactor, then the local setting, server field, and documentation. Patches depending on the protocol RFC are flagged as blocked until that discussion resolves. The threat model dedicates specific attention to untrusted server input, and the testing matrix covers baseline behavior, local priorities, server values, precedence rules, and compatibility with old clients and servers.

This is a reply to review on patch v9 1/4 of the `--delete-merged`/`--delete-integrated` series, addressing a naming concern in the refactoring. Junio C Hamano had flagged the extracted helper `branch_opted_out()` as a "selfish" name that assumed delete-merged would be the only destructive operation needing an opt-out, creating an impedance mismatch with the operation-specific config key `branch.<name>.deleteMerged`. Harald Nordgren accepted the feedback and chose Junio's first proposed resolution, renaming the function to `opted_out_of_delete_merged()` in `builtin/branch.c`. This keeps the helper explicitly tied to the `deleteMerged` operation rather than implying generic reuse for other destructive operations, which is relevant context for how patch 3/4's new `--delete-integrated` flag will interact with the same opt-out mechanism -- Junio has separately questioned whether `branch.<name>.deleteMerged` is the right config key for `--delete-integrated` or whether a more generic key like `deleteDone` would be needed, so the renamed helper's specificity may become a point of discussion when the `--delete-integrated` implementation reuses or parallels this check.

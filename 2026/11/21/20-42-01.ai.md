This is the core feature patch of the v10 series, implementing the new `git branch --delete-integrated <pattern>` option that deletes branches whose changes -- but not their tips -- have been integrated upstream via rebase or squash merges.

The patch adds the `DELETE_BRANCH_INTEGRATED` flag bit and a new `delete_integrated` strvec parsed from the command line, mutually exclusive with `--delete-merged`. When active, `delete_merged_branches()` in `builtin/branch.c` collects candidate branches that fail the usual tip-reachability check into a `landing_search` array, then calls `find_landed_commits()` to scan upstream history. For each branch, `collect_branch_changes()` diffs the merge base against the branch tip to record every changed path with its blob OID and mode in a `branch_change` array. `find_landed_commit()` then walks upstream commits in reverse (via `rev-list --reverse`), using a `changed_paths` commit slab to skip commits that do not touch any of the branch's changed paths, and checks whether any single upstream commit's tree contains the exact branch version (OID and mode) of every changed file via `changes_landed()` and `change_landed()`. The first matching commit is stored in a `strmap` keyed by branch name, which `delete_branches()` (extended in patch 2/5) consults to skip the reachability check and print `Deleted branch %s (was %s, landed as %s)`. The detection is purely tree-based, never reading blob contents, so it remains cheap in partial clones.

Files touched are `builtin/branch.c` (the bulk of the implementation), `Documentation/git-branch.adoc` (synopsis and option description), `Documentation/config/branch.adoc` (noting that `branch.<name>.deleteMerged=false` applies to both flags), and `t/t3200-branch.sh` (263 lines of new tests covering rebase-merged deletion, squash-merged deletion, reverted changes, partial landings, file-to-directory conversions, `--dry-run`/`--quiet` combinations, the config opt-out, and mutual exclusion with `--delete-merged`). The series remains under review; the open "npm update" false-positive concern (where another author independently makes identical changes) is not addressed by this tree-based approach and remains an open question in the thread.

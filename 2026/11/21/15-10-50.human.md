This is a feature patch series, specifically the v2 cover letter for a three-patch effort to make submodule configuration worktree-aware when `extensions.worktreeConfig` is enabled. Yoichi NAKAYAMA is addressing a real gap: today, settings like `submodule.<name>.url` and `submodule.<name>.gitdir` live in the shared repository config, so all linked worktrees inherit the same values. That breaks workflows where different branches need different submodule URLs, and worse, sharing `submodule.<name>.gitdir` causes distinct superproject worktrees to point at the same submodule gitdir, making them accidentally share a HEAD and index.

The series splits the fix into three logical steps. Patch 1 ensures `submodule.<name>.gitdir` stays relative for linked worktrees so the setting survives moving the whole worktree tree. Patch 2 routes submodule settings into the worktree-specific config file when `extensions.worktreeConfig` is on, and adjusts `git submodule deinit` and `git worktree add` to handle the new storage correctly. Patch 3 teaches `git submodule init` to copy an existing `gitdir` from the repository config into the current worktree's config only when that path actually belongs to this worktree, emitting a warning otherwise.

Compared to v1, this version fixes a static-buffer lifetime issue in patch 1 by copying the `worktree_git_path()` result immediately, expands the commit messages to explain why `gitdir` must not be shared, and adds explicit warnings when an existing config setting is skipped because it points to another worktree's gitdir. The series touches `builtin/submodule--helper.c`, `builtin/worktree.c`, and documentation, and adds two new test scripts (`t/t2405-worktree-submodule.sh` and `t/t7425-submodule-gitdir-path-extension.sh`) covering the new behavior.

The contribution looks well-motivated and carefully scoped. The commit messages clearly explain the failure modes of the current shared-config behavior, the test coverage appears thorough, and the v2 changes show responsiveness to initial feedback. It remains under review with no substantive objections yet, but the interaction with existing submodule workflows will likely be the main area reviewers probe.

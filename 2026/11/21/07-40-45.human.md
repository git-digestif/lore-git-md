This is a bugfix for `git fast-import` that fixes a case where malformed input could produce a corrupt tree.

When a `M <mode> inline <path>` command appears at the very end of the input stream without a following `data` command, `file_change_m()` in `builtin/fast-import.c` previously exited its read loop on EOF and placed an uninitialized stack object ID into the tree. The command would exit successfully, leaving behind a tree entry that references a missing blob -- a corruption that `git fsck` flags. The patch aligns `file_change_m()` with the behavior of `note_change_n()` by ensuring that `parse_and_store_blob()` is called even at EOF, which dies with an error when the expected `data` command is absent.

The change itself is small: the read loop is converted to an infinite `for` loop with an explicit `read_next_command()` call, so that EOF now triggers the proper error path rather than silently proceeding with garbage data. A new test in `t/t9300-fast-import.sh` verifies that `git fast-import` fails with the expected "expected 'data n' command" message and does not create the ref when the inline data is truncated.

The patch looks well-crafted: the commit message clearly explains the bug, the fix, and references the analogous handling in `note_change_n()`. It includes a regression test that reproduces the exact scenario. This addresses a real correctness issue in stream parsing and should be straightforward to review.

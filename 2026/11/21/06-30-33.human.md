This is a bugfix in the sequencer, targeting an edge case when running `git cherry-pick` on an unborn branch.

The patch fixes a case where `sequencer_pick_revisions()` tried to save the current HEAD OID before starting a pick sequence, but if the branch is unborn, `repo_get_oid()` fails and leaves the OID uninitialized. The code then saved that garbage value to `.git/sequencer/head` anyway, instead of clearing it to the null OID. The practical symptom is that a subsequent `git cherry-pick --abort` misbehaves: it either errors with "Could not parse object" or, depending on what happened to be in memory, silently moves the new branch to the last picked commit. The fix clears the OID to the null value when HEAD cannot be resolved (except for revert, which still correctly refuses to run as an initial commit), so that `sequencer_rollback()` can detect the unborn state and report "cannot abort from a branch yet to be born".

The patch is small and well-targeted, touching only `sequencer.c` and adding a regression test in `t/t3510-cherry-pick-sequence.sh` that creates an orphan branch, attempts a multi-commit cherry-pick, and verifies that `--abort` produces the expected error rather than a parse failure or a bogus checkout. The commit message clearly explains both the root cause and the user-visible impact, and the diff itself is minimal and easy to verify.

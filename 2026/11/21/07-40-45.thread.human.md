This thread concerns a silent-corruption bug in `git fast-import`, where an inline file modification (`M <mode> inline <path>`) as the final line of the input stream causes `file_change_m()` in `builtin/fast-import.c` to exit on EOF without seeing the required `data` command, storing an uninitialized object ID into the tree and exiting with status 0 -- leaving a tree entry referencing a nonexistent blob that `git fsck` later flags. Wonseok Oh submitted a v2 patch restructuring the loop in `file_change_m()` as an infinite `for (;;)` with an explicit EOF `die()` at the top, plus two regression tests in `t/t9300-fast-import.sh`, after Junio C Hamano objected that v1's approach could infinite-loop on an unterminated final `cat-blob` line because it discarded `read_next_command()`'s return value.

Junio confirmed the bug description is accurate but pointed to his own separate series (20261122140347.41990-1-gitster@pobox.com) addressing this whole class of `read_next_command()` EOF-handling problems in `builtin/fast-import.c`. In his latest reply, Wonseok acknowledges that Junio's series already fixes the infinite-loop failure mode that broke v1, and offers to revert to the v1 patch if Junio prefers layering it on top of his own series.

The thread remains unresolved: no integration-branch status has been reported, and it is still open whether Junio will pick up Wonseok's v2, accept a v1-on-top-of-his-series arrangement, or rely solely on his own series to resolve the underlying EOF-handling issues.

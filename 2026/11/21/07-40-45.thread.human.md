This thread concerns a standalone bugfix patch from Wonseok Oh addressing a silent-corruption case in `git fast-import`: when an inline file modification (`M <mode> inline <path>`) appears as the final line of input without a following `data` command, `file_change_m()` would exit its read loop on EOF, store an uninitialized object ID into the tree, and exit with status 0 -- leaving a dangling tree entry that `git fsck` would later flag. The proposed fix restructured the loop in `builtin/fast-import.c` from a `while (read_next_command() != EOF)` form into an infinite `for (;;)` loop that calls `read_next_command()` unconditionally at the top, so the parser would die on EOF rather than silently proceeding, and added a regression test in `t/t9300-fast-import.sh` asserting that malformed input fails with "expected 'data n' command".

Junio C Hamano has now reviewed the patch and identified a critical flaw in this approach: because the restructured loop discards the return value of `read_next_command()`, a final input line that lacks a terminating newline (for example, `cat-blob <object>` as the very last line) would be returned once, processed, and then reprocessed indefinitely on subsequent iterations, since `command_buf` is left unchanged when EOF is detected. The parser would spin forever rather than terminate. Junio notes that while `file_change_m()` cannot simply delegate to `parse_and_store_blob()` the way `note_change_n()` does (since it loops over multiple commands), the fix must still respect the EOF signal -- the return value of `read_next_command()` needs to be checked to break the loop or trigger an error.

The patch is therefore not accepted in its current form and awaits a rework from Wonseok Oh that both catches the missing-`data`-command case and terminates cleanly on EOF. No integration-branch status has been reported; the series remains under review with the maintainer's constraint as the open item.

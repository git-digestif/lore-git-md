Wonseok Oh has sent a single-patch bugfix to `git fast-import` addressing a silent corruption case where an inline file modification is truncated at end-of-input. The flaw resides in `file_change_m()` within `builtin/fast-import.c`: when an `M <mode> inline <path>` command appears as the final line of the input stream without a following `data` command, the function previously exited its read loop on EOF and stored an uninitialized stack object ID into the tree, exiting with status 0 and leaving behind a reference to a non-existent blob that `git fsck` would later flag.

The fix restructures the parsing loop from `while (read_next_command(state) != EOF)` into an infinite `for (;;)` loop that calls `read_next_command()` unconditionally at the top, causing the parser to die with an error when it encounters EOF instead of a `data` command. This matches the existing behavior of `note_change_n()`, which properly dies on missing data via `parse_and_store_blob()`. The patch includes a regression test in `t/t9300-fast-import.sh` that feeds a truncated stream and asserts `git fast-import` fails with "expected 'data n' command" and does not create the target ref. The behavioral change ensures malformed input now produces an immediate fatal error rather than a silently corrupt commit graph. The patch is newly posted and currently under review.

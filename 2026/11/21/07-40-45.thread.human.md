This thread is a standalone bugfix from Wonseok Oh (via GitGitGadget) for a silent-corruption bug in `git fast-import`. When an inline file modification (`M <mode> inline <path>`) appears as the very last line of the input stream, `file_change_m()` in `builtin/fast-import.c` would exit its read loop on EOF without ever seeing the required `data` command, then store an uninitialized stack object ID into the tree and exit with status 0 -- leaving behind a tree entry pointing at a non-existent blob that `git fsck` would later flag.

The current version is v2, which restructures the loop in `file_change_m()` from a `while` condition into an infinite `for (;;)` loop with an explicit EOF check at the top that calls `die(_("expected 'data n' command, found end of input"))`. This directly answers Junio C Hamano's objection to v1, which had discarded the return value of `read_next_command()` and could infinite-loop if the input ended with an unterminated `cat-blob` line leaving stale content in `command_buf`. The patch adds two regression tests to `t/t9300-fast-import.sh` covering both the bare truncated `M inline` case and the unterminated `cat-blob` case, each asserting that fast-import fails and the target ref is not created.

The series remains under review: Junio reviewed v1 and demonstrated the infinite-loop failure mode, but has not yet responded to this v2 revision, and no integration-branch status has been reported. The only open item is whether the maintainer finds the explicit EOF `die()` at the loop top clean enough; the author notes the error message wording is arbitrary and welcomes alternatives.

Thread identity: single bugfix patch to `git fast-import` authored by Wonseok Oh via GitGitGadget; thread type is a standalone patch, not yet part of a numbered series.

Core problem or goal: fix a silent-corruption case in `builtin/fast-import.c` where an inline file modification (`M <mode> inline <path>`) appearing as the final line of the input stream causes `file_change_m()` to exit its read loop on EOF without ever seeing the required `data` command, then store an uninitialized stack object ID into the tree and exit with status 0, leaving a tree entry referencing a non-existent blob that `git fsck` would later flag.

Current status: patch is newly posted and under review; no integration-branch status has been reported.

Key technical details: the fix is in `file_change_m()` in `builtin/fast-import.c`, restructuring the loop from `while (read_next_command(state) != EOF)` into an infinite `for (;;)` loop that calls `read_next_command()` unconditionally at the top, so the parser dies with an error on EOF rather than silently proceeding; this matches the existing behavior of `note_change_n()`, which calls `parse_and_store_blob()` and properly dies on missing data. A regression test is added in `t/t9300-fast-import.sh` (series D, "fail on inline data cut off at end of input") that feeds a stream ending with an inline `M` command and no data block, asserting that `git fast-import` fails with the message "expected 'data n' command" and that the target ref is not created. Behavioral change: malformed input now produces an immediate fatal error instead of a silently corrupt commit graph.

Thread identity: single bugfix patch to `git fast-import` authored by Wonseok Oh via GitGitGadget; thread type is a standalone patch, not yet part of a numbered series.

Core problem or goal: fix a silent-corruption case in `builtin/fast-import.c` where an inline file modification (`M <mode> inline <path>`) appearing as the final line of the input stream causes `file_change_m()` to exit its read loop on EOF without ever seeing the required `data` command, then store an uninitialized stack object ID into the tree and exit with status 0, leaving a tree entry referencing a non-existent blob that `git fsck` would later flag.

Current status: patch is under review; Junio C Hamano has identified a critical flaw in the proposed fix and effectively rejected the current approach, requiring the author to rework the loop. No integration-branch status has been reported.

Key technical details: the original fix restructured `file_change_m()` from `while (read_next_command(state) != EOF)` into an infinite `for (;;)` loop that calls `read_next_command()` unconditionally at the top, intending to die on EOF when the `data` command is missing. Junio demonstrated that discarding the return value of `read_next_command()` creates an infinite loop when the final input line lacks a terminating newline: `strbuf_getline_lf()` returns EOF but `command_buf` retains the previous partial line (e.g. `cat-blob <object name>`), causing the loop to reprocess the identical command indefinitely. While `file_change_m()` cannot simply call `parse_and_store_blob()` like `note_change_n()` because it processes multiple commands in a loop, the fix must still check the EOF return value to break the loop or trigger an error. A regression test was added in `t/t9300-fast-import.sh` (series D, "fail on inline data cut off at end of input") asserting failure with "expected 'data n' command" and that the target ref is not created.

Open questions and loose ends: the loop in `file_change_m()` must respect the EOF signal from `read_next_command()` rather than discarding it, breaking or erroring on EOF while still catching the missing-`data`-command case; no alternative implementation has been proposed yet.

Participant positions: Wonseok Oh authored the patch; Junio C Hamano reviewed and rejected the current loop structure, demonstrating the infinite-loop failure mode and stating the return value of `read_next_command()` must be checked even if the function does not exit immediately on EOF.

Related work: general `git fast-import` robustness; the fix aims to align `file_change_m()` error handling with the stricter EOF handling in `note_change_n()`.

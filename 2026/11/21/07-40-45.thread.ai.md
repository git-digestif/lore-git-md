Thread identity: single bugfix patch (v2) to `git fast-import` authored by Wonseok Oh via GitGitGadget; thread type is a standalone patch, not yet part of a numbered series.

Core problem or goal: fix a silent-corruption case in `builtin/fast-import.c` where an inline file modification (`M <mode> inline <path>`) appearing as the final line of the input stream causes `file_change_m()` to exit its read loop on EOF without ever seeing the required `data` command, then store an uninitialized stack object ID into the tree and exit with status 0, leaving a tree entry referencing a non-existent blob that `git fsck` would later flag.

Current status: patch remains under review; the author submitted a revised approach (v2) addressing Junio C Hamano's objection to the previous version, and Junio has now responded confirming the bug description is accurate but pointing to his own separate series (20261122140347.41990-1-gitster@pobox.com) that addresses this infinite-loop class of issues along with several others, suggesting it may supersede or complement the v2 fix. No integration-branch status has been reported; it remains undecided whether Junio will pick up Wonseok Oh's v2 approach or rely on his own series to resolve the underlying `read_next_command()` EOF-handling problems.

Key technical details: the v2 fix changes the loop structure in `file_change_m()` from `while (read_next_command(state) != EOF)` to an infinite `for (;;)` loop with an explicit EOF check at the top of each iteration: `if (read_next_command(state) == EOF) die(_("expected 'data n' command, found end of input")));`. This checks the return value of `read_next_command()` as Junio required, preventing the infinite-loop failure mode where a final unterminated line (e.g. `cat-blob <object name>`) leaves stale content in `command_buf` that would be reprocessed indefinitely. The loop still permits `cat-blob` commands within the block and falls through to `parse_and_store_blob()` for the `data` command, matching the strict EOF error handling already present in `parse_data()`. Two regression tests now exist in `t/t9300-fast-import.sh` (series D): one asserting failure with "expected 'data n' command" and that the target ref is not created when the stream ends immediately after `M 644 inline file`, and another verifying the same behavior when an unterminated `cat-blob` command follows the inline `M` at end-of-input.

Open questions and loose ends: whether the explicit EOF `die()` at the loop top is the cleanest solution remains to be judged by the maintainer; the author notes the error message wording is arbitrary and welcomes alternatives; whether the two tests sufficiently cover the unterminated-final-line scenario that broke v1 has not been confirmed; whether Junio's own series (20261122140347.41990-1-gitster@pobox.com) will make this v2 patch redundant or if both approaches will coexist has not been resolved.

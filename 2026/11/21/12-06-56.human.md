This is a review response in the ongoing thread about Tamir Duberstein's three-patch series teaching `git ls-files` to reuse the untracked cache. It addresses Aniket Gupta's substantive review of patch 3, which identified a concurrency regression where a cold untracked cache caused `git ls-files` to hold `index.lock` for the entire directory scan, blocking concurrent `git add` operations.

Tamir Duberstein confirms the issue and explains that since v3 was sent, commit 6b6d1d56eb ("read-cache: verify skipHash index by stat data") landed on `master`. This change allows the optional index write to detect concurrent modifications via stat data even when `index.skipHash` is enabled, which removes the need to acquire the lock before reading the directory. He states that v4 will therefore take the lock after `fill_directory()` completes using `repo_lock_and_update_index_if_able()`, aligning the behavior more closely with `master` and `cmd_status()`.

On the testing side, he notes that the early-lock assertion in the existing test has been removed, and new coverage has been added to verify that concurrent index updates succeed and persist through `git ls-files`, with both `index.skipHash` enabled and disabled. This directly tests the scenario Gupta reproduced with 60,000 untracked files.

The exchange is technically grounded and moves the series toward a v4 that resolves the lock-scope concern without sacrificing the performance gains. No new patch is included in this email; it is a commitment to revise the approach in the next iteration.

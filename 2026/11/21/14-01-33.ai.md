This is an Outreachy proposal draft (v2) for a feature: configurable fetch ordering for promisor remotes in partial clones. Hussain Sitamouwala is responding to Kaartic Sivaraam's substantive review of v1 and refining the design document before posting any code. The proposal aims to replace Git's fixed promisor-remote fetch order with a priority-based system controlled by local configuration (`remote.<name>.priority`, lower values tried first) and optionally by a server-advertised `priority=<n>` protocol field, with defensive parsing of untrusted input.

The core technical concession in this revision is that user-set configuration values and server-supplied priorities must be stored in separate config keys rather than sharing `remote.<name>.<field>`, because `promisor.storeFields` writes server data into `remote.<name>.<field>` and could collide with hand-set values. Precedence remains an open question: the author recommends that local user values win outright over server-advertised ones, ordering only remotes with no local setting, but notes that operators paying for bandwidth may prefer the opposite. The exact key names and whether server values are persisted at all are deferred to a future protocol RFC. A competing public patch using `promisor.fetchOrder` (a single list of remote names) is noted as a potential conflict; the author plans to send a trade-off note and implement whichever shape maintainers prefer.

No code has been posted yet. The planned series has six patches: patches 1-3 (trace2 observation event, baseline tests locking current behavior, and a behavior-preserving refactor to allow sorting) are independent of the design decisions, while patches 4 (local config) and 5 (server field and client handling) depend on the protocol RFC and maintainer decisions about config shape. The author's earlier documentation patch describing current fetch order is cooking in `next` (queued 2026-11-12, not yet in `master`), and his `check-ref-format` parse-options patch is under review.

Key subsystems and files involved are `promisor-remote.c` (specifically `try_promisor_remotes()`, `lazy_fetch_objects()`, and `promisor_remote_get_direct()`), `transport.c`, `remote.c`, `Documentation/config/remote.txt`, `Documentation/config/promisor.adoc`, `Documentation/technical/partial-clone.adoc`, and tests in `t/t5710-promisor-remote-capability.sh` and `t/t0410-partial-clone.sh`. The current behavior calls `try_promisor_remotes()` twice: first with `accepted_only=true` (server-advertised remotes), then with `accepted_only=false`, each in config-file order with `extensions.partialClone` last. The proposal preserves this two-pass structure while adding stable sorting by priority within each pass.

Open questions and likely points of contention for future discussion include: the exact config key for server-stored priorities versus user-set priorities; whether `promisor.sendFields` needs per-remote gating instead of a global setting; handling of negative or non-integer priority values; integer overflow in parsing; and whether an explicit local priority should override the accepted-first rule. The threat model explicitly treats server-advertised priorities as untrusted input, with malformed values ignored and no effect for clients that do not opt in via `promisor.storeFields`.

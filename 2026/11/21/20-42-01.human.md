This is a feature patch, specifically the fourth of five in Harald Nordgren's v10 series, which introduces the new `git branch --delete-integrated <pattern>` option. This is the core implementation that actually delivers the change-based branch detection the series promises: instead of requiring a branch's tip commits to be reachable from upstream, it walks upstream commits since the merge base and deletes a branch when some commit contains the branch's exact version of every file the branch modified, printing `Deleted branch <name> (was <sha>, landed as <sha>)` to show where the work went. The detection is purely tree-based -- comparing blob OIDs and modes via `get_tree_entry()` -- so it avoids reading file contents and stays cheap in partial clones, though it does not use patch-ids or author checks, leaving the "npm update" false-positive scenario unaddressed.

The patch adds the `DELETE_BRANCH_INTEGRATED` flag and a `landing_search` machinery in `builtin/branch.c` that collects each branch's changed paths from the merge base, then scans upstream history in reverse for the first commit matching all those changes. It enforces that `--delete-integrated` cannot be combined with `--delete-merged`, extends the `branch.<name>.deleteMerged=false` opt-out to cover the new flag, and wires the landed-commit map into `delete_branches()` so mapped branches skip the usual reachability check. Documentation updates describe the new flag and note that `--dry-run` now works with it, while `t/t3200-branch.sh` gains tests covering rebase-merged, squash-merged, reverted, and file-to-directory scenarios, plus dry-run, quiet mode, and the config opt-out. The series remains under review with no integration status announced, and Junio's open question about whether `deleteMerged` is the right config key for this new flag (versus something like `deleteDone`) is still unanswered.

This is a v2 cover letter for a two-patch bugfix series from Orgad Shaneh that aligns `git fetch --prune-tags` behavior with its documentation. The series addresses a long-standing inconsistency: since commit 0bc8d71b99 (Git 2.20), `--prune-tags` prunes missing tags but rejects changed tags with "would clobber existing tag", despite the docs promising it also force-updates them.

The core change modifies `builtin/fetch.c` to add a "+" (force) prefix to the implied refspec when `--prune-tags` is active, rather than passing a global `TAG_FETCH_FORCE` flag as in v1. This distinction matters: v1 inadvertently forced tags fetched via explicit refspecs when `fetch.pruneTags` was configured, even though those tags are not pruned in that scenario. The v2 approach scopes the force behavior strictly to the auto-following tag refspec that `--prune-tags` implies.

The series also strengthens test coverage in `t/t5516-fetch-push.sh`. The new tests verify not only that `git fetch --force` succeeds with a changed tag but that the local tag object was actually updated (via `check_child1_tag` comparing `git rev-parse` output), and they confirm that `git fetch origin tag <name>` with `fetch.pruneTags` set still fails as expected. Documentation in `Documentation/git-fetch.adoc` and `Documentation/config/fetch.adoc` is updated to reflect the precise behavior.

From a thread-continuity perspective, the key open question remains whether the current no-force behavior was an intentional design choice by the original implementer or an oversight; Junio C Hamano has raised concerns about historical intent and test sufficiency but has not yet provided a substantive ruling. The series is rebased on current master and stands alone, touching only the fetch machinery and its tests with no new on-disk formats or symbols.

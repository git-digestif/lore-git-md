This is a bugfix cover letter for a two-patch v2 series that makes `git fetch --prune-tags` force-update tags that have changed on the remote, bringing the implementation back in line with its documentation. Orgad Shaneh is the author.

The problem dates back to Git 2.20 (commit 0bc8d71b99), when tag clobbering protection was introduced but `--prune-tags` was not taught to override it, so fetches now fail with "would clobber existing tag" instead of updating the tag as the docs promise. The first patch adds test coverage verifying that `--force` actually updates a changed tag -- previously the test only checked the exit status, not the tag content -- and the second patch modifies `builtin/fetch.c` to add a "+" to the refspec implied by `--prune-tags`, which allows changed tags to be clobbered.

This v2 refines the v1 approach: rather than treating `--prune-tags` as a blanket `--force` (which incorrectly forced tags fetched via explicit refspecs when `fetch.pruneTags` was configured), it only applies the force flag to the implied tag refspec. The tests now confirm the local tag was actually updated after a forced fetch, and the documentation in `git-fetch.adoc` and `config/fetch.adoc` is adjusted to match the corrected behavior.

The thread has been stalled awaiting clarification from the maintainer on whether the original behavior was an intentional design choice; Junio C Hamano had raised historical questions but had not yet ruled on the substance. This revision directly addresses prior feedback about test coverage and scope, and presents a well-motivated, narrowly targeted fix for a real gap between documented and actual fetch behavior.

This is a reply from Tamir Duberstein addressing Aniket Gupta's substantive review of patch 3 in the three-patch series that teaches `git ls-files` to reuse the untracked cache. Duberstein confirms the concurrency regression Gupta identified -- where v3 holds `index.lock` for the entire cold-cache directory scan, blocking concurrent `git add` -- and states that v4 will resolve it by acquiring the lock after `fill_directory()` completes rather than before, using the new `repo_lock_and_update_index_if_able()` helper. He notes that commit 6b6d1d56eb ("read-cache: verify skipHash index by stat data"), which landed on `master` after v3 was sent, now allows the optional index write to detect concurrent modifications via stat data even when `index.skipHash` is enabled, removing the previous need for early locking. Duberstein also reports that he removed the test assertion that expected the early-lock behavior and added new test coverage verifying that concurrent index updates succeed and persist across `git ls-files` invocations, exercised with `index.skipHash` both enabled and disabled.

This is a two-patch bugfix series targeting platforms where `long` is 32-bit but `size_t` is 64-bit (notably 64-bit Windows). The patches address silent truncation or corruption of files 4GiB or larger in two subsystems: `git archive` (both tar and zip formats) and `git apply`. The author reports that the fixes resolve all known instances of this class of truncation bug in Git.

The changes are mechanical: replacing `unsigned long` with `size_t` for variables that hold file sizes in `archive-tar.c`, `archive-zip.c`, and `apply.c`. The commit messages explain that the truncation occurs because `unsigned long` is too small to represent sizes ≥4GiB on the affected platforms, while `size_t` is guaranteed to be large enough. No new tests are included, but the author states they verified the fixes by simulating truncation at 16 bits.

The series is based on `master` (50fe5cc63f) and merges cleanly with other in-flight topics. The author notes that the existing `t5004` test for "zip archive with files bigger than 4GB" is currently disabled on 32-bit `long` platforms due to historical limitations in the object database; with these patches, the guard could be relaxed to `SIZE_T_IS_64BIT` to enable real testing on 64-bit Windows, though the author hasn’t tested this themselves.

Key files touched: `apply.c`, `archive-tar.c`, `archive-zip.c`, and `archive.h`. The changes are confined to type declarations and do not alter behavior on platforms where `long` is already 64-bit. The patches appear well-scoped and address a real, user-visible issue without introducing new complexity.

This is the second patch in the **v5 iteration of a four-patch bugfix series for `git imap-send`**, addressing RFC 5322 compliance by making header parsing order-agnostic and fixing a latent CRLF line-ending bug. The patch replaces the rigid `strstr()`-based header detection in `count_messages()` with a new helper function, `has_required_headers()`, which scans for `From:`, `Date:`, and `Subject:` headers in any order within the header block. The helper now correctly handles both LF (`\n\n`) and CRLF (`\r\n`) line endings, ensuring the header block is terminated at the first empty line regardless of the mbox format.

The change is motivated by interoperability with tools like `b4`, which produce valid but non-canonical email headers (e.g., `Subject` before `Date`). The previous implementation rejected such messages, causing `git imap-send` to fail when processing archived patches. The new logic is more permissive while remaining strict about the presence of all three required headers. The patch also adds two new tests to `t/t9001-send-email.sh`: one verifies that `git imap-send` can process a patch fetched from a mailing list archive, and another ensures the parser ignores headers in the message body of a CRLF mbox.

This is a **well-crafted, targeted fix** with clear test coverage. The CRLF handling addresses the blocking issue identified in `v4`, and the order-agnostic parsing resolves the core interoperability problem. The patch touches only `imap-send.c` and the test suite, with no on-disk format changes or new symbols beyond the `has_required_headers()` helper. The commit message clearly explains the motivation and edge cases, and the code is straightforward.

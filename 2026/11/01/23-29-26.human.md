This is the second patch in a two-part bugfix series for the credential-cache daemon. It addresses a critical race condition where a second daemon can hijack the socket of an already-running daemon, leading to lost credentials, orphaned processes, and inaccessible passwords.

The patch replaces the existing `unix_stream_listen()` call with `unix_ss_create()`, which is already used by the simple-ipc server. This function takes a lock and only binds to the socket if no other server is listening, preventing the second daemon from unlinking the first one’s socket. If a daemon detects an existing server, it prints "ok" and exits, allowing its client to communicate with the running daemon. The socket is now registered for cleanup only after binding, ensuring that a losing daemon does not remove the winner’s socket.

The changes are confined to `builtin/credential-cache--daemon.c`, with the core logic shift being the adoption of `unix_ss_create()` and the deferred socket cleanup. The patch also adds a new test in `t/t0301-credential-cache.sh` that verifies the fix by simulating concurrent daemon starts and confirming credentials remain accessible.

This looks like a well-targeted fix for a real-world issue, particularly for users with large repositories where parallel submodule fetches over HTTPS can trigger the race. The test coverage is a strong point, and the use of existing simple-ipc infrastructure (`unix_ss_create()`) suggests the solution is robust. The patch is likely to be uncontroversial if the tests pass and the logic holds up under review.

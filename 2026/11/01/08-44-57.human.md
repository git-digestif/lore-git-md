This is the second patch in a two-part bugfix series addressing 4 GiB file size truncation on 64-bit Windows (and other platforms where `long` is 32 bits but `size_t` is 64 bits). The series targets the `grep` and `diff` subsystems, with this patch focusing on `git diff`.

The patch prevents `git diff` from silently generating misleading patches when processing files of 4 GiB or larger in the working tree, textconv, `--no-index` mode, or combine-diff. Instead of truncating the file size (which would produce incorrect diffs and potentially corrupt files when applied), Git now dies with a clear error. This matches the existing behavior for blobs, which already error out on large files. The change affects three files: `combine-diff.c`, `diff-no-index.c`, and `diff.c`, where `size_t` values are explicitly cast to `unsigned long` using the `cast_size_t_to_ulong()` helper introduced in patch 1/2.

The commit message explains the problem clearly: on affected platforms, file sizes above 4 GiB are silently truncated when stored in `struct diff_filespec.size` (an `unsigned long`), leading to incorrect diffs and corrupted patches. For example, a one-line change in a 7901-line file might be reported as 1 insertion and 5042 deletions if the size is truncated to 16 bits. The fix is straightforward and self-contained, using the same pattern already established for blobs.

No tests are included, as generating 4 GiB inputs is impractical, but the commit message confirms the fix was verified by simulating truncation at 16 bits. The patch is clean, well-explained, and addresses a real correctness issue without introducing new complexity. The author acknowledges that widening `diff_filespec.size` to `size_t` for full 4+ GiB support is a larger effort left for a future series, which is a reasonable scope limitation.

This patch looks ready for review and likely to be uncontroversial. The change is minimal, targeted, and aligns with existing error handling in the codebase. If you care about large-file correctness on Windows or other 32/64-bit `long` platforms, this is worth paying attention to.

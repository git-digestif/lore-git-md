This is the first patch in a two-part bugfix series addressing silent truncation of files 4GiB or larger on platforms where `long` is 32-bit but `size_t` is 64-bit (notably 64-bit Windows). The patch focuses on the `git archive` subsystem, updating type declarations in `archive-tar.c`, `archive-zip.c`, and `archive.h` to use `size_t` instead of `unsigned long` for file-size variables.

The change is mechanical and well-scoped: it replaces `unsigned long` with `size_t` in function signatures and local variables that hold file sizes, ensuring compatibility with blobs larger than 4GiB. The commit message clearly explains the problem (silent corruption in tar and zip archives due to overflow) and the verification method (simulating truncation at 16 bits). No new tests are included, but the patch enables the existing `t5004` test (currently disabled on 32-bit `long` platforms) to run on 64-bit Windows by relaxing its guard to `SIZE_T_IS_64BIT`.

The patch looks clean and addresses a real, user-visible issue without introducing complexity. It’s part of a broader effort to fix truncation bugs in Git’s archive and apply subsystems, with the second patch targeting `git apply`. No review feedback has been posted yet, but the series appears ready for scrutiny.

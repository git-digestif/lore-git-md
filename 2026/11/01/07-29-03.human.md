This is a bugfix patch targeting the `pack-objects` subsystem, addressing a data corruption issue when handling large blobs (≥4GiB) on 32-bit platforms. This is the third iteration of a standalone patch, incorporating feedback from Junio C Hamano to clarify the platform condition in the commit message.

The patch fixes a truncation bug in `git pack-objects` where blob sizes ≥4GiB are incorrectly recorded in the pack header on platforms where `long` is 32 bits but `size_t` is 64 bits (e.g., 64-bit Windows). The fix changes the types of `size` (to `size_t`) and `datalen`/`olen` (to `off_t`) in the streaming path, ensuring accurate size tracking for both the object and its compressed data. This prevents data corruption during `git repack` or `git gc` when loose large blobs are pruned.

The change is narrowly scoped to `builtin/pack-objects.c`, with no impact on the on-disk format or other functionality. The commit message now explicitly states the platform condition (32-bit `long` with 64-bit `size_t`) to avoid future confusion, addressing Junio's feedback from v2. No test is included, as reproducing the bug requires ≥4GiB objects on affected platforms, but the rationale and edge cases are well-documented.

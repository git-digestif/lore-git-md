This is a two-patch bugfix series targeting the credential-cache daemon. The patches address a race condition that occurs when two `git credential-cache store` commands run simultaneously and both attempt to start a daemon. The second daemon unlinks the first one’s socket, causing credentials stored by the first daemon to be lost. The series prevents this by making the daemon more resilient to concurrent socket directory creation and ensuring it does not take over an existing daemon’s socket.

The problem manifests in several ways: credentials stored by the first daemon become inaccessible, the `exit` command only stops the second daemon (leaving the first running with passwords in memory), and the first daemon’s exit can remove the second daemon’s socket, causing its credentials to be lost as well. The commit message notes this can happen during parallel submodule fetches over HTTPS, making it a real-world issue for users with large repositories.

The series touches `builtin/credential-cache--daemon.c` and adds tests in `t/t0301-credential-cache.sh`. The first patch allows the daemon to handle a concurrently created socket directory, while the second ensures it does not hijack an existing daemon’s socket. The changes are motivated by a 2021 observation from Jeff King about the racy socket setup, though the current fix addresses a more severe edge case where credentials are actively lost.

The author discovered the issue using Rewind, a deterministic VM that replays thread schedules to uncover race conditions. This tooling suggests the patches are well-tested for the specific failure mode, though the commit message does not detail broader testing (e.g., across platforms or with varying daemon timeouts).

Thread identity: Subject: [PATCH v3 0/4] Fix integer truncation in large-file handling; Series version: v3 (4 patches); Originating author: Elia Pinto; Thread type: bugfix patch series.

Core problem or goal: Fix silent integer truncation in Git subsystems when processing files or buffers larger than 2--4 GiB. The series widens 32-bit size and line-count types to `size_t` or `uintmax_t` across complete-rewrite diff paths (`count_lines()`, `emit_rewrite_lines()`, `count_trailing_blank()`), diffstat total accumulation and `scale_linear()` in `diff.c`, and rename detection (`hash_chars()` in `diffcore-delta.c`), while fixing packfile generation (`hashwrite()` callers) via chunked calls rather than signature widening.

Current status: Under review; v3 posted. Series is based on master at 50fe5cc63f and reportedly merges cleanly with current master and `seen`. No merge status reported. v3 addresses all substantive review concerns raised on v2: patch 1/4 adopts the chunked-call approach requested by Junio C Hamano and brian m. carlson instead of widening `hashwrite()`; patch 3/4 widens `struct spanhash.cnt` to resolve Junio's overflow concern; patch 4/4's commit message now explains why the `uintmax_t` accumulator cannot overflow in practice and documents the `graph_width` capping behavior. Patch 2/4 code is unchanged from v2 (which addressed Phillip Wood's feedback) but awaits his re-review.

Key technical details: Files touched: `builtin/fast-import.c`, `builtin/pack-objects.c`, `diff.c`/`diff.h`, `diffcore-delta.c`, `t/t4022-diff-rewrite.sh`, `t/t4052-stat-output.sh`. Patch 1/4: `hashwrite()` signature remains unchanged (`uint32_t` count); its three callers that can pass buffers larger than 4 GiB -- `write_no_reuse_object()` and `copy_pack_data()` in `builtin/pack-objects.c`, and `store_object()` in `builtin/fast-import.c` -- now loop and call `hashwrite()` in chunks of at most `UINT32_MAX` bytes, eliminating the silent truncation without requiring Rust FFI binding updates. Junio C Hamano and brian m. carlson are credited with Helped-by for the chunked-call approach. No committed test accompanies the patch because reproduction requires an object of 4 GiB or more; the author instead verified the fix by simulating 16-bit truncation. The commit message lists three concrete trigger paths: `write_no_reuse_object()` when `core.bigFileThreshold` is raised above 4 GiB, `copy_pack_data()` when `core.packedGitWindowSize` is set that high, and `store_object()` in fast-import under similar big-file thresholds. Patch 2/4: `count_lines()` (size parameter and return type widened to `size_t`), `emit_rewrite_lines()` (buffer size parameter widened to `size_t`), `count_trailing_blank()` (counter and buffer size widened to `size_t`; the buffer size was previously stored in `long`, which is 32-bit on LLP64 platforms like 64-bit Windows, causing pointer underflow for buffers over 2 GiB), and `struct emit_callback` fields (`blank_at_eof_in_preimage`, `blank_at_eof_in_postimage`, `lno_in_preimage`, `lno_in_postimage`) widened to `size_t`, along with `add_line_count()`, `check_blank_at_eof()`, and `emit_rewrite_diff()`. Single line lengths remain `int` but are guarded by `cast_size_t_to_int()`. Pre-patch failure mode on files >= 2 GiB: size parameter truncates to negative, causing `git diff -B --stat` to report zero changed lines and `git diff -B -p` to emit an empty `@@ -0,0 +0,0 @@` hunk that `git apply` rejects while still exiting successfully. Commit message includes a reproduction recipe using approximately 2.2 GiB of data. Patch 3/4: widens the local `sz` variable in `hash_chars()` (holding `one->size`), the `cnt` member of `struct spanhash`, and the local `dst_cnt`/`src_cnt` variables in `diffcore_count_changes()` from `unsigned int` to `size_t`; `hashval` remains `uint` since it stays below `HASHBASE`. The commit message notes the hash table holds at most 2^17 entries, so the larger `size_t` fields cost at most 1 MiB of additional memory per file. Previously, rename detection on files >= 4 GiB hashed only a prefix while scoring against the full truncated size, causing missed renames in `git diff -M`, `git log --follow`, and merge rename detection; additionally `struct spanhash.cnt` could wrap to zero after four billion hash collisions on highly repetitive content, making a populated hash bucket appear empty. The patch carries a Helped-by trailer from Junio C Hamano and touches only `diffcore-delta.c` with three line changes. No committed test accompanies the change because reproducing the bug requires a file of 4 GiB or more; the author verified the fix by simulating 16-bit truncation, demonstrating that `git diff --cached -M` would previously report "D a" and "A b" instead of "R099 a b" for renamed random and repetitive files respectively. Patch 4/4: `print_stat_summary()` and `print_stat_summary_inserts_deletes()` accept `uintmax_t` with `PRIuMAX` formatting; `show_stats()` locals `adds` and `dels` become `uintmax_t`; `show_shortstats()` accumulation variables widened from `int` to `uintmax_t`; `scale_linear()` takes `uintmax_t` parameters ensuring 64-bit arithmetic for `it * (width - 1)` on LLP64 platforms; `graph_width` assignment caps `max_change` at `width` when it exceeds available space. Commit message now notes that the `uintmax_t` accumulator cannot overflow in practice because each line consumes at least one byte of input. Behavior change: functions now handle buffer/file sizes up to `SIZE_MAX` without truncation; no on-disk format changes. Test coverage: two EXPENSIVE tests in `t/t4022-diff-rewrite.sh` gated on `SIZE_T_IS_64BIT` and `LONG_IS_64BIT` (one verifies numstat/patch output for a 2 GiB file expecting 536870912 lines; the other verifies numstat for 2^31 lines); one cheap test in `t/t4052-stat-output.sh` covering the `scale_linear()` overflow case with a 50,000-line file using `--stat=46100 --stat-graph-width=46000`. Patches 1/4 and 3/4 remain untested via committed tests (multi-gigabyte inputs impractical); failure modes confirmed via 16-bit truncation simulation. Patch 4/4 carries a `Tested-by` trailer from Torsten Bögershausen.

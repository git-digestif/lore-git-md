Thread identity: Subject: [PATCH v2 0/4] Fix integer truncation in large-file handling; Series version: v2 (4 patches; expanded from v1's 3 patches); Originating author: Elia Pinto; Thread type: bugfix patch series.

Core problem or goal: Fix silent integer truncation in Git subsystems when processing files or buffers larger than 2--4 GiB. The series widens 32-bit size and line-count types to `size_t` or `uintmax_t` across packfile generation (`hashwrite()`), complete-rewrite diff paths (`count_lines()`, `emit_rewrite_lines()`, `count_trailing_blank()`), diffstat total accumulation and `scale_linear()` in `diff.c`, and rename detection (`hash_chars()` in `diffcore-delta.c`).

Current status: Under review; v2 posted. Series is based on master at 50fe5cc63f and builds directly on v1. No merge status reported. v2 incorporates Phillip Wood's review feedback by rewriting patch 2/4 to propagate `size_t` through the entire complete-rewrite path, resolving the `count_lines()` overflow flaw identified in v1. Patch 4/4 was added in v2 specifically because the patch 2/4 fix made it possible for a single file to legitimately reach 2^31 lines, which could then trigger diffstat overflow. Patch 1/4 has substantive review from Junio C Hamano raising unresolved questions; patch 3/4 now has substantive review from Junio C Hamano raising a new open concern about `struct spanhash`; patch 4/4 also has substantive review from Junio C Hamano raising two open concerns; patch 2/4 has been addressed per Phillip Wood's feedback but awaits his re-review.

Key technical details: Files touched: `csum-file.c`/`csum-file.h`, `diff.c`/`diff.h`, `diffcore-delta.c`, `t/t4022-diff-rewrite.sh`, `t/t4052-stat-output.sh`, and (per Junio's review) `src/csum_file.rs` (Rust FFI bindings). Symbols modified: `hashwrite()` (byte count parameter changed from `uint32_t` to `size_t`), `count_lines()` (size parameter and return type widened to `size_t`), `emit_rewrite_lines()` (buffer size parameter widened to `size_t`), `count_trailing_blank()` (counter and buffer size widened to `size_t`; the buffer size was previously stored in `long`, which is 32-bit on LLP64 platforms like 64-bit Windows, causing pointer underflow for buffers over 2 GiB), `hash_chars()` (local variable `sz` changed from `unsigned int` to `size_t`), diffstat total accumulation in `--stat` output (widened to `uintmax_t` with `PRIuMAX` formatting to avoid overflow when single files exceed `INT_MAX` lines), and `scale_linear()` (now takes `uintmax_t` parameters for change count and maximum change, ensuring the multiplication `it * (width - 1)` is performed in 64-bit arithmetic even on LLP64 platforms). Patch 4/4 specifics: `print_stat_summary()` and static helper `print_stat_summary_inserts_deletes()` signatures changed to accept `uintmax_t` for insertion/deletion counts with format strings switched from `%d` to `PRIuMAX`; prototype in `diff.h` updated accordingly (affecting `git apply --stat` callers, though `apply.c` itself continues summing totals in `int` and is unchanged); in `show_stats()`, locals `adds` and `dels` become `uintmax_t` and `graph_width` assignment logic adjusted to cap `max_change` at `width` when it exceeds available space to avoid `int` overflow. Struct fields in `struct emit_callback` (`blank_at_eof_in_preimage`, `blank_at_eof_in_postimage`, `lno_in_preimage`, `lno_in_postimage`) widened to `size_t`, along with `add_line_count()`, `check_blank_at_eof()`, and `emit_rewrite_diff()`. Single line lengths remain `int` but are guarded by `cast_size_t_to_int()` to die rather than truncate if a line exceeds `INT_MAX`. Behavior change: functions now handle buffer/file sizes up to `SIZE_MAX` without truncation; no on-disk format changes. Specific trigger for `hashwrite()` bug: occurs when `git pack-objects` writes an entire compressed object buffer exceeding 4 GiB in a single `hashwrite()` call -- possible when the object is held in memory, is poorly compressible, and `core.bigFileThreshold` is raised accordingly; with the old `uint32_t` parameter, only `count mod 2^32` bytes are written, silently corrupting the packfile. The complete-rewrite path bypasses both `core.bigFileThreshold` and `MAX_XDIFF_SIZE` because `should_break()` in `diffcore-break.c` loads contents directly. Patch 3/4 (`hash_chars()`): previously, when rename detection processed files >= 4 GiB, only a prefix was hashed while the similarity score was calculated against the full truncated size, causing true renames to be missed; this affected `git diff -M`, `git log --follow`, and merge rename detection. Author verified via 16-bit truncation simulation: `git diff --cached -M` reported delete and add ("D a", "A b") instead of rename ("R099 a b"). No automated test included for this patch because triggering the real bug requires a 4 GiB input. Test coverage: two EXPENSIVE tests added to `t/t4022-diff-rewrite.sh` gated on `SIZE_T_IS_64BIT` and `LONG_IS_64BIT` prerequisites (one verifies numstat and patch output for a 2 GiB file expecting 536870912 lines; the other verifies numstat for a file with 2^31 lines; both fail on master and with v1's partial fix); one cheap test added to `t/t4052-stat-output.sh` covering the `scale_linear()` overflow case using a 50,000-line file with a graph width of 46,000 (the totals themselves are not covered by a committed test because exceeding `INT_MAX` lines requires a multi-gigabyte input). `count_trailing_blank()` overflow (affecting only whitespace highlighting) is not covered by committed tests but was verified via `SANITIZE=signed-integer-overflow` builds with 2200 MiB of newlines. Patches 1/4 and 3/4 remain untested via committed tests (multi-gigabyte inputs impractical); failure modes confirmed via 16-bit truncation simulation, which previously caused `git cat-file` and `git fsck` to fail with "offset beyond end of packfile (truncated pack?)" after `git repack -a -d`, `git diff -B --stat` to report incorrect line counts, and `git diff -M` to miss renames.

Open questions and loose ends: Patch 1/4 (`hashwrite()`) is under active discussion: Junio C Hamano identified that the Rust FFI bindings in `src/csum_file.rs` still declare `hashwrite()` with a `u32` length parameter and must be updated to `size_t` to match the C signature; he also questioned the API design choice itself, asking whether callers holding contiguous memory regions exceeding 4 GiB should instead loop calling `hashwrite()` in chunks of 4 GiB or less rather than widening the parameter type -- no resolution reached yet on whether to keep the `size_t` widening or switch to a chunked-call approach. Patch 3/4 (`hash_chars()`) now has an open concern from Junio C Hamano: the `cnt` member of `struct spanhash` remains `uint` and could theoretically wrap down to zero after four billion hash collisions, making a populated bucket appear empty; Junio asks whether this counter should also be widened to `size_t` in the same patch, or whether there is a reason it can safely remain 32-bit, drawing a distinction with the `hashval` member which he suggests can stay `uint` -- no resolution reached; this keeps patch 3/4 awaiting a completed technical review. Patch 4/4 has two open concerns from Junio C Hamano: (1) what happens when the widened `uintmax_t` accumulator itself eventually overflows after enough additions, a question the commit message does not answer; (2) the code change adjusting `graph_width` assignment logic to cap `max_change` at `width` when it exceeds available space is a behavioral change more significant than mere type widening, yet this is not described in the proposed commit message. No substantive technical reviews yet for patch 2/4 on v2 (Phillip Wood's feedback addressed but not yet re-reviewed). The LLP64 `long`-vs-`size_t` issue in `count_trailing_blank()` was found by inspection but not tested on such platforms. Coordination point: patch 6/6 of a separate series ("loose object size checks and a few size truncations") will be dropped from its v2 because `count_trailing_blank()` is modified here, avoiding merge conflicts between the two series. Future discussion may focus on whether the widened types introduce new edge cases in low-level I/O and diff code paths, whether `apply.c`'s continued use of `int` for its own totals is acceptable given the `diff.h` prototype change, whether the Rust FFI bindings update is sufficient or whether additional Rust-side callers need auditing, whether `struct spanhash`'s `cnt` member needs widening alongside `hash_chars()`, and whether the EXPENSIVE tests in `t4022` adequately cover the complete-rewrite path given their disk-space and time requirements.

Subject: [PATCH 0/3] Fix integer truncation in large-file handling
Series version: v1 (initial submission)
Originating author: Elia Pinto
Thread type: bugfix patch series

Core problem or goal
Fix silent integer truncation in three Git subsystems when processing files or buffers larger than 2–4 GiB. The patches change function signatures from 32-bit types (`uint32_t`, `int`, `unsigned int`) to `size_t` to prevent corruption in `hashwrite()` (packfile generation), miscounts in `count_lines()` (`git diff -B --stat`), and rename detection failures in `hash_chars()` (diffcore-delta).

Current status
Under review; no prior versions. Series is based on master at 50fe5cc63f and has no external dependencies. No merge status reported; still awaiting substantive technical review for the first and third patches. The second patch (`count_lines()`) is confirmed flawed due to a mismatch between the widened `size_t` parameter and the retained `int` return type and line counter variable, creating a new overflow risk for files with >`INT_MAX` lines.

Key technical details
Files touched: `csum-file.c`/`csum-file.h`, `diff.c`, `diffcore-delta.c`
Symbols modified: `hashwrite()` (signature changed from `uint32_t` to `size_t` for byte count), `count_lines()` (signature changed from `int` to `size_t` for buffer size; **return type and line counter variable remain `int`, creating a new overflow risk for files with >`INT_MAX` lines**), `hash_chars()` (signature changed from `unsigned int` to `size_t` for buffer size)
Behavior change: functions now handle buffer/file sizes up to `SIZE_MAX` without truncation; no on-disk format changes. Internal loops in `hashwrite()` and `count_lines()` already handle block-based or line-by-line processing, but the `count_lines()` flaw means line counts above `INT_MAX` will wrap, producing incorrect results even for files smaller than 2 GiB. The `hash_chars()` fix ensures rename detection works correctly for files ≥4 GiB by preventing undervalued similarity scores.
Test coverage: none (impractical to generate multi-gigabyte test inputs); failure mode confirmed via 16-bit truncation simulation, which caused `git cat-file` and `git fsck` to fail with "offset beyond end of packfile" errors after repacking, `git diff -B --stat` to report incorrect line counts, and `git diff -M` to miss renames.

Open questions and loose ends
- **Critical flaw in `count_lines()`**: return type and line counter variable remain `int`, creating a new overflow risk for files with >`INT_MAX` lines. This undermines the patch's goal and requires rework. No alternative solution proposed yet; options include widening the return type and counter variable or documenting why line counts above `INT_MAX` are impossible in practice.
- No substantive technical reviews yet for the first (`hashwrite()`) and third (`hash_chars()`) patches; confirmation needed that no edge cases exist in low-level I/O or diff logic, particularly for `hashwrite()`'s block-based writing and `hash_chars()`'s similarity scoring.
- No test cases included; future follow-up may be required if real-world large-file scenarios surface.
- Series remains self-contained with no external dependencies or related work mentioned.

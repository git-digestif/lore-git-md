This is the first patch in a three-part bugfix series addressing integer truncation in Git’s large-file handling. It changes the `hashwrite()` function in `csum-file.c` and its declaration in `csum-file.h` from taking a `uint32_t` count to a `size_t` count. The commit message explains that when `pack-objects` writes a compressed buffer larger than 4 GiB in a single call, the current 32-bit parameter silently truncates the count, corrupting the packfile. The author verified this by simulating a 16-bit truncation, which caused `git cat-file` and `git fsck` to fail with "offset beyond end of packfile" errors after repacking.

The change is minimal—just two one-line signature adjustments—and the internal loop in `hashwrite()` already handles writing in buffer-sized blocks, so no further logic changes are needed. The patch is well-motivated and clearly documents the failure mode, though no test is included due to the impracticality of generating multi-gigabyte test inputs. This is a straightforward fix for a real, if niche, problem, and the use of `size_t` is appropriate for a buffer size that should never be negative. The series as a whole looks technically sound, but this patch would benefit from a tested review to confirm no edge cases in low-level I/O are overlooked.

This thread began with a small but useful patch from first-time contributor Pushkar Singh: adding a Trace2 event to log when `git maintenance run --auto` skips execution because a `maintenance.lock` file already exists. The patch is minimal, uncontroversial, and follows established patterns for diagnostic logging in Git.

Patrick Steinhardt’s review takes the conversation in a broader direction. While he does not object to the Trace2 event itself, he raises a design question about the current lock-handling logic in `git maintenance`. He points out that the command silently succeeds even in non-`--auto` mode when it fails to acquire the lock, which is inconsistent with `git gc` (which fails fast on lock contention) and may confuse users. He suggests that the author—or someone else—might want to address this in a follow-up patch, distinguishing between `--auto` (where a warning and success is appropriate) and non-`--auto` (where an error would be more consistent with user expectations). The patch remains under review, with no maintainer decision yet, and no changes requested at this stage.

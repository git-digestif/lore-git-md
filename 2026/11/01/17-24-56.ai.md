This is a bugfix patch targeting the `apply` subsystem.

The patch addresses an integer overflow risk in `parse_binary_hunk()` where a binary patch hunk declaring a size larger than `INT_MAX` (2³¹−1) is read into an `unsigned long` but later stored in an `int`-typed field (`struct fragment.size`). Without this check, such a patch could trigger an oversized allocation, potentially leading to a crash or memory exhaustion. The fix adds an explicit size check before allocation and treats oversized hunks as corrupt patches, consistent with how other malformed hunks are handled.

The commit includes a new test in `t/t4103-apply-binary.sh` that constructs a patch declaring a literal size of 3,000,000,000 (exceeding `INT_MAX`). The test runs `git apply` with `GIT_ALLOC_LIMIT=1m` to ensure the oversized allocation fails fast, verifying that the patch is rejected with the correct error message rather than triggering an out-of-memory condition.

The change is minimal and focused: a single bounds check in `apply.c` and a corresponding test case. The commit message clearly explains the motivation and the test strategy. The patch appears well-crafted and addresses a real, if obscure, edge case in patch parsing.

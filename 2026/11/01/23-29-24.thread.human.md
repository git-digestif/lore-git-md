This thread is about a two-patch series from Farid Zakaria that fixes a race condition in Git's credential-cache daemon, where concurrent `git credential-cache store` commands could cause one daemon to unlink another's socket, leading to lost credentials and orphaned processes. The issue is particularly noticeable during parallel submodule fetches over HTTPS in large repositories.

The series is currently under review, with v1 posted and v2 expected. Patrick Steinhardt provided substantive feedback on both patches: he identified a pre-existing permission-handling issue in patch 1 and requested clarifications in patch 2's commit message and code comments. Now, Junio C Hamano has raised a significant architectural concern about patch 2. He argues that the patch incorrectly mixes the `unix_ss_*` API (used for safe Unix domain socket management) with the `tempfile` API, which could undermine the safety mechanisms built into `unix_ss_*`. Junio suggests the patch should follow the precedent set by `fsmonitor--daemon.c`, which uses `unix_ss_create()` without involving the `tempfile` API, and drop the `tempfile` registration entirely.

The key technical details remain unchanged: the patches touch `builtin/credential-cache--daemon.c` and add tests to `t/t0301-credential-cache.sh`, introducing `unix_ss_create()` as the safe socket-creation mechanism. The open questions now include Junio's architectural concern, alongside the previously noted edge cases around socket cleanup, platform coverage, and permission correctness. Farid is expected to address these in v2 before the series can move forward.

This thread is about a bugfix series (v2) from Farid Zakaria that addresses a race condition in Git's credential-cache daemon, where concurrent `git credential-cache store` commands can cause one daemon to unlink another’s socket, leading to lost credentials and orphaned processes. The series also fixes a pre-existing permission-handling issue in socket directory creation.

Key participants include Farid (author), Junio C Hamano (maintainer), Patrick Steinhardt, and Jeff King (reviewers). The core fixes—ignoring `EEXIST` from `mkdir()` and using `unix_ss_create()` for safe socket handling—are uncontroversial and confirmed correct by both Jeff and Patrick. However, Junio has raised an architectural concern about mixing `unix_ss_*` and `tempfile` APIs in patch 3, arguing it risks unsafe socket cleanup. Farid initially suggested the race might only occur during Git upgrades, but Junio countered that any serious installation would respawn dead daemons, making the race a persistent issue. Junio’s latest reply is firm, questioning Farid’s judgment on safety mechanisms and expecting either a technical justification or a revised implementation. The series remains under review, with no maintainer decision yet on whether a v3 will be required.

The preparatory commit (patch 1) fixes a permission issue by ensuring the socket directory is created with mode `0700`, regardless of `core.sharedRepository` settings. Tests in `t/t0301-credential-cache.sh` verify the fixes, including the "ok" response protocol between client and daemon. The unresolved architectural concern is the main blocker, with Junio signaling that the current approach may not be acceptable without further revision.

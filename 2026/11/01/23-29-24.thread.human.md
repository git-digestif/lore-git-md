This thread is about a two-patch series from Farid Zakaria that fixes a race condition in Git's credential-cache daemon, where concurrent `git credential-cache store` commands could cause one daemon to unlink another’s socket, leading to lost credentials and orphaned processes. The issue is particularly noticeable during parallel submodule fetches over HTTPS in large repositories.

The series is currently under review, with v1 posted and v2 expected. Key reviewers—Patrick Steinhardt, Junio C Hamano, and Jeff King—have all provided substantive feedback. Patch 1 (ignoring `EEXIST` from `mkdir()`) is uncontroversial and aligns with existing Git behavior, though Patrick identified a pre-existing permission-handling issue in the socket directory creation. Patch 2 (using `unix_ss_create()` for safe socket handling) is also well-motivated, but Junio raised an architectural concern about mixing `unix_ss_*` and `tempfile` APIs, arguing that `tempfile` registration is unnecessary and potentially unsafe. Jeff King’s latest review confirms the core logic of patch 2 is correct, though he suggests minor cosmetic improvements for clarity.

The series touches `builtin/credential-cache--daemon.c` and adds tests in `t/t0301-credential-cache.sh`. The new behavior ensures that if a second daemon detects an existing socket, it exits cleanly, allowing its client to communicate with the running daemon. Open questions include edge-case handling (socket cleanup on daemon exit, permission correctness, and potential stale directories) and architectural soundness (resolving Junio’s concern about API mixing). All feedback is expected to be addressed in v2.

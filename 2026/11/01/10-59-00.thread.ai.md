Core problem or goal
Improve observability and consistency of `git maintenance run` lock handling. The series adds a Trace2 data event for `--auto` skips due to lock existence and aligns manual invocations (`git maintenance run` without `--auto`) with `git gc`’s fail-fast behavior when the lock cannot be acquired. The latent design question about lock-handling consistency between `--auto` and non-`--auto` modes is explicitly addressed and resolved, but a regression in background-scheduled runs has surfaced.

Current status
Under review; v3 posted with all previously requested mechanical refinements incorporated. The series is now contested due to a reported regression: background-scheduled maintenance runs (started by `git maintenance start`) fail with an error exit code instead of silently skipping, contradicting documented behavior and established patterns. The prefetch task also emits spurious lock warnings due to stricter lock-checking logic inherited by internal `git fetch` calls.

Key technical details
- Files modified: `builtin/gc.c` (Trace2 event and lock-acquisition logic), `t/t7900-maintenance.sh` (updated test).
- New Trace2 event: `"lock/skip": {"reason": <strerror(err)>, "errno": <code>}` under the `"maintenance"` category, using `strerror(err)` unconditionally for the `reason` field. The event is emitted in `--auto` mode even when `--quiet` is specified, ensuring diagnostic data is always available.
- Behavioral change: manual `git maintenance run` now fails with exit code 128 and an error message when the lock cannot be acquired, matching `git gc`’s behavior. `--auto` mode continues to skip silently but logs the Trace2 event. The `--quiet` flag is respected in both cases: output is suppressed, but manual invocations still fail with exit code 128.
- **Regression**: background-scheduled runs (triggered by `git maintenance start`) now fail with an error exit code instead of silently skipping, as they did on `master`. The prefetch task emits lock warnings due to stricter lock-checking logic inherited by internal `git fetch` calls.
- Code organization: the series is split into two focused patches—one for the behavioral change (v3 1/2) and one for the Trace2 event (v3 2/2)—to improve reviewability and bisectability. Duplicated error-message formatting is refactored into the existing `unable_to_lock_message()` helper shared with `git gc`.
- Test updates: verifies both the Trace2 event emission (including error code and `strerror`-based `reason`) and the new exit-code behavior for manual invocations. The lock file is preserved on failure, maintaining the existing design that stale locks require manual inspection. Three new tests in `t/t7900-maintenance.sh` cover manual failure, `--auto` skip, and `--quiet` suppression.
- No on-disk format changes; purely behavioral and diagnostic.

Open questions and loose ends
- **Background run regression**: Are background-scheduled runs (started by `git maintenance start`) considered `--auto` or manual invocations? The current patch applies fail-fast logic to them, causing them to fail with an error exit code instead of silently skipping. This contradicts documented behavior and established patterns.
- **Prefetch task warnings**: The prefetch task now emits lock warnings due to stricter lock-checking logic inherited by internal `git fetch` calls. Is this intended, or should the prefetch task be exempted from the new lock-checking logic?
- The author must clarify the intended behavior for background runs and adjust the lock-checking logic to avoid regressing scheduled maintenance. The Trace2 event aspect remains uncontested.

This is the first patch in a three-part bugfix series addressing integer truncation in Git’s large-file handling. It changes the `hashwrite()` function in `csum-file.c` and its declaration in `csum-file.h` to use `size_t` instead of `uint32_t` for the byte count parameter. The commit message explains that when `pack-objects` writes a compressed buffer larger than 4 GiB in a single call, the current 32-bit type silently truncates the count, corrupting the packfile. The issue was confirmed by simulating a 16-bit truncation, which caused `git cat-file` and `git fsck` to fail with "offset beyond end of packfile" errors after repacking.

The change is minimal—just two one-line adjustments—and the internal loop in `hashwrite()` already handles writing in buffer-sized blocks, so no additional logic is needed. The patch is well-motivated and clearly documents the failure mode, though no test is included due to the impracticality of generating multi-gigabyte test inputs. The use of `size_t` is appropriate here, as it matches the type used for buffer sizes elsewhere in Git and avoids negative values.

This patch is part of the broader series targeting silent truncation in three subsystems (`hashwrite()`, `count_lines()`, and `hash_chars()`). The series is self-contained, based on `master` at `50fe5cc63f`, and has not yet received any reviews. The key symbol modified is `hashwrite()` in `csum-file.h`, which is central to packfile generation. While the patch looks technically sound, a tested review would be valuable to confirm no edge cases exist in low-level I/O behavior.

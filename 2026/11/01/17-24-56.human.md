This is a bugfix patch targeting the `git apply` command. It addresses a potential integer overflow issue when parsing binary hunks in patches.

The patch prevents `git apply` from processing binary hunks whose declared size exceeds `INT_MAX` (2,147,483,647 on most systems). Currently, the code reads the size into an `unsigned long` but stores it in an `int`, which could lead to silent truncation or memory allocation failures when dealing with extremely large binary hunks. The fix treats such oversized hunks as corrupt patches before any allocation or inflation occurs.

The commit includes a test case that creates a patch declaring a binary hunk of 3,000,000,000 bytes (larger than `INT_MAX`). The test uses `GIT_ALLOC_LIMIT` to ensure the oversized allocation would fail visibly if not caught earlier, verifying that the patch is properly rejected as corrupt.

The change is small and focused, touching only `apply.c` and adding a test to `t/t4103-apply-binary.sh`. The rationale is clear: prevent potential memory corruption or crashes from malformed input. This looks like a well-crafted fix for a real edge case.

This is the third patch in Elia Pinto’s three-part bugfix series addressing integer truncation in Git’s large-file handling. It fixes a silent truncation issue in `diffcore-delta.c` where `hash_chars()`—used to compute similarity scores for rename detection—takes the buffer size as an `unsigned int`. When processing files 4 GiB or larger, the function hashes only a prefix of the file, causing the similarity score to be undervalued. This leads to missed renames, which affects `git diff -M`, `git log --follow`, and merges. The fix is a one-line change: replacing `unsigned int sz` with `size_t sz` to ensure the full buffer size is used.

The problem was confirmed via a 16-bit truncation simulation, where `git diff --cached -M` incorrectly reported a delete-and-add instead of a rename. Like the rest of the series, this patch is minimal and well-motivated, with no test added due to the impracticality of generating multi-gigabyte test files. The change aligns with the earlier patches in the series, which similarly updated function signatures in `csum-file.c` and `diff.c` to use `size_t` for buffer sizes.

This patch touches the diff subsystem, specifically the rename-detection logic, and is part of a broader effort to ensure Git handles large files (4 GiB+) correctly. The series as a whole is under review but has not yet received substantive feedback. The fix appears technically sound, though reviewers may want to confirm no edge cases exist in the similarity-scoring logic when dealing with very large buffers. For users working with large files, this is a niche but real correctness issue worth addressing.

This is the second patch in a two-patch bugfix series addressing a race condition in the Git credential-cache daemon. The series targets a scenario where concurrent `git credential-cache store` commands can cause one daemon to unlink another’s socket, leading to lost credentials and orphaned daemons.

This patch prevents a second daemon from hijacking the socket of an already-running daemon. The key change replaces the direct use of `unix_stream_listen()` with `unix_ss_create()`, a helper from the simple-ipc subsystem that safely handles concurrent socket creation. If a daemon detects an existing socket, it prints "ok" and exits, allowing its client to communicate with the running daemon instead. The patch also ensures the socket is registered for cleanup only after binding succeeds, preventing a losing daemon from removing the winner’s socket.

The patch touches `builtin/credential-cache--daemon.c` and adds a new test in `t/t0301-credential-cache.sh` that exercises the race condition. The test verifies that a second daemon does not disrupt an existing one and that credentials stored by the first daemon remain accessible. The commit message clearly explains the consequences of the bug—lost credentials, orphaned daemons, and inaccessible passwords—and how the fix resolves them.

This patch complements the first one, which handled the `mkdir()` race for the socket directory. Together, they close a real-world issue that can occur during parallel submodule fetches over HTTPS, particularly in large repositories. The use of `unix_ss_create()` aligns with existing simple-ipc server patterns, suggesting the fix is well-aligned with Git’s internals. The test coverage is a strong point, though reviewers may still probe edge cases like socket cleanup on daemon exit or platform-specific behavior.

The patch appears clean and well-motivated, with no obvious red flags. It should be uncontroversial if the tests pass and the logic holds under scrutiny. The series as a whole looks like a solid fix for a subtle but impactful bug.

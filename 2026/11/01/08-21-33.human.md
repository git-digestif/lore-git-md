This is the fifth iteration of a four-patch bugfix series for `git imap-send`, addressing interoperability issues with tools like `b4` that produce non-canonical email header orders (e.g., `Subject` before `Date`) and case-insensitive header names (e.g., `FROM:`). The series was previously merged to `next` but blocked by a latent CRLF line-ending bug in Patch 2/4, which this version fixes.

The core problem is that `git imap-send` fails to process patches where headers appear in non-canonical order or with mixed case, breaking workflows that rely on `b4` or other tools. The fix rewrites the header-parsing logic to accept any order and case for `From:`, `Date:`, and `Subject:` headers while ensuring RFC 5322 compliance. It also plugs a tunnel-command memory leak (Patch 1/4) and removes a special-case exemption for `git send-email` (Patch 3/4), treating all messages uniformly.

Key changes in `v5` focus on the CRLF bug: Patch 2/4 now correctly terminates the header block at an empty line in both LF and CRLF mboxes, preventing false positives from headers in the message body. A new test verifies this edge case. Other improvements from `v4` include defensive coding for tunnel process management (storing `imap->tunnel` as an allocated pointer) and expanded test coverage for mixed-case headers and the `--imap-sent-folder` workflow.

The series touches only `imap-send.c` and `t/t9001-send-email.sh`, with no on-disk format changes. The new `has_required_headers()` helper function (Patch 2/4) now handles CRLF line endings correctly, addressing the blocking issue identified by Junio. All prior feedback—including Patrick Steinhardt’s concerns about defensive coding and documentation—has been resolved.

This is a well-motivated, minimal fix with thorough test coverage. The CRLF issue was the last blocker, and its resolution should allow the series to graduate to `master`. No controversy remains; the changes are uncontroversial and directly address a real interoperability problem.

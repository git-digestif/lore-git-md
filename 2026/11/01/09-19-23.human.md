This is the second patch in a two-patch bugfix series addressing silent truncation of files 4GiB or larger on platforms where `long` is 32-bit but `size_t` is 64-bit (notably 64-bit Windows). The series targets `git archive` (tar and zip formats) and `git apply`, and this patch specifically fixes the `git apply` subsystem.

The patch mechanically replaces `unsigned long` with `size_t` for variables holding file sizes in `apply.c`, ensuring that files larger than 4GiB can be correctly written out. The commit message explains that the truncation occurs because `unsigned long` cannot represent sizes ≥4GiB on affected platforms, while `size_t` is guaranteed to be large enough. The author verified the fix by simulating a 16-bit truncation scenario, where `git apply` previously left a 7901-line file truncated to 2859 lines.

The changes are confined to four functions in `apply.c`: `create_file()`, `create_one_file()`, `try_create_file()`, and `add_index_file()`. The patch is well-scoped and aligns with the first patch in the series, which made similar type changes in the archive subsystem. No new tests are included, as triggering the issue requires processing a 4GiB+ file on a 32-bit `long` platform, but the author notes that the fix is consistent with ongoing efforts to use `size_t` for object and buffer sizes (e.g., the "use size_t for a few more object and buffer sizes" series).

This patch looks like a straightforward and necessary fix for a real, user-visible issue. The commit message is clear, and the changes are minimal and focused. No review feedback has been posted yet, but the series appears to address the problem effectively.

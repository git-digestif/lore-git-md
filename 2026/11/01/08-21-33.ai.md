This is the **v5 iteration of a four-patch bugfix series for `git imap-send`**, addressing RFC 5322 compliance and interoperability with tools like `b4`. The series was previously merged to `next` but blocked by a latent CRLF line-ending bug in Patch 2/4, now fixed.

The core problem: `git imap-send` rejected patches where the `Subject` header preceded the `Date` header (a valid but non-canonical order produced by `b4`) or used mixed-case header names (e.g., `FROM:`). The series makes the header-parsing logic order-agnostic and case-insensitive, while also fixing a tunnel-command memory leak and removing a `git-send-email`-specific exemption. The v5 update specifically addresses the CRLF issue by ensuring the header block is correctly terminated at empty lines in both LF and CRLF mboxes, preventing false positives from body text.

Key changes in v5:
- **Patch 2/4** now handles CRLF line endings (`\r\n`) in `has_required_headers()`, fixing the latent bug that could misclassify messages with body text resembling headers. A new test verifies this edge case.
- **Patch 1/4** (tunnel process lifecycle) remains unchanged from v4, where it was revised to store `imap->tunnel` as an allocated pointer for defensive coding.
- **Patches 3/4** (removal of `git-send-email` special case) and **4/4** (case-insensitive header matching) are unchanged, with expanded test coverage added in v4.

The series touches only `imap-send.c` and `t/t9001-send-email.sh`, with no on-disk format changes. Test coverage is thorough, including mixed-case headers, order-agnostic parsing, and CRLF edge cases. All prior feedback has been addressed, and the series is explicitly endorsed by Patrick Steinhardt. The CRLF fix is minimal and targeted, resolving the blocking issue without introducing new complexity.

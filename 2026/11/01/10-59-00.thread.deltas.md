# Thread deltas

## 2026/11/01

- [2026/11/01/10-59-00 by Pushkar Singh <pushkarkumarsingh1970@gmail.com>] Pushkar Singh submitted a patch to emit a Trace2 data event (key "lock/skip", value "exists") when `git maintenance run --auto` skips due to an existing maintenance.lock, since such skips are currently silent and difficult to identify (for example, when caused by a stale lock from an interrupted process); the change modifies builtin/gc.c and adds a test in t/t7900-maintenance.sh.

## 2026/11/02

- [2026/11/02/08-29-33 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt reviewed the v1 trace-only change and asked why only EEXIST is traced, questioning whether callers should also learn about other lock failures such as EPERM; he also argued that manual `git maintenance run` should print an error and exit non-zero instead of silently succeeding (noting git-gc(1) dies on an existing lock), and suggested this could be fixed in a second patch.
- [2026/11/02/12-23-53 by Pushkar Singh <pushkarkumarsingh1970@gmail.com>] Pushkar Singh agreed that lock acquisition failures beyond EEXIST should be reported and said he had included the actual reason in the Trace2 event; he also agreed the manual-invocation behavior was odd and said v2 makes manual invocations report an error and return non-zero while `--auto` still exits successfully with a warning.
- [2026/11/02/12-29-56 by Pushkar Singh <pushkarkumarsingh1970@gmail.com>] Pushkar Singh posted `[PATCH v2] maintenance: improve handling of lock acquisition failures`, whose changelog states: manual lock failures are reported as errors with non-zero exit, automatic invocations print a warning while preserving successful exit, the Trace2 event now gives the reason for all automatic lock failures (not just EEXIST), and tests were added for automatic and manual lock-failure behavior.
- [2026/11/02/12-51-23 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt reviewed v2 and said it should be split into two patches (one for lock-failure handling, one for the trace2 string), asked Pushkar to wait before rerolling and reroll at most once per day, asked why `strerror(3p)` is not used for both the EEXIST and other-error cases, and noted the duplicated lock-message code between the auto and manual branches could be deduplicated.

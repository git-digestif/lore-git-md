Subject: [PATCH 0/2] credential-cache: fix race condition in daemon socket handling
Series version: v1 (v2 anticipated)
Originating author: Farid Zakaria
Thread type: bugfix patch series

Core problem or goal
Fix a race condition in the Git credential-cache daemon where concurrent `git credential-cache store` commands can cause one daemon to unlink another’s socket, leading to lost credentials, orphaned daemons, and inaccessible passwords. The issue surfaces during parallel submodule fetches over HTTPS and affects users with large repositories.

Current status
Under review; v1 posted. Patrick Steinhardt provided substantive reviews of both patches: patch 1 identified a pre-existing permission-handling issue and suggested a preparatory commit, while patch 2 requested commit-message and code-comment clarifications. No maintainer decision recorded; v2 expected to incorporate both sets of feedback.

Key technical details
- Files touched: `builtin/credential-cache--daemon.c`, `t/t0301-credential-cache.sh`
- New behavior: daemon now ignores `EEXIST` from `mkdir()` (patch 1) and uses `unix_ss_create()` (patch 2) to safely handle concurrent socket creation; if a second daemon detects an existing socket, it prints "ok" and exits, allowing its client to communicate with the running daemon
- Old behavior: second daemon fails with "unable to mkdir" or unlinks first daemon’s socket, causing credential loss and orphaned processes
- Test coverage: new tests in `t/t0301-credential-cache.sh` exercise both the `mkdir()` race (patch 1) and the socket hijacking race (patch 2)
- On-disk format: unchanged
- Symbols: `unix_ss_create()` (helper from simple-ipc subsystem) introduced as the safe socket-creation mechanism; `safe_create_leading_directories_no_share_const()` suggested for permission correctness in a preparatory commit
- Pre-existing issue: `safe_create_leading_directories()` incorrectly applies `core.sharedRepository` permissions to the user-specific credential-cache socket directory

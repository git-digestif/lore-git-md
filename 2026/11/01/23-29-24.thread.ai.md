Subject: [PATCH 0/2] credential-cache: fix race condition in daemon socket handling
Series version: v1 (v2 anticipated)
Originating author: Farid Zakaria
Thread type: bugfix patch series

Core problem or goal
Fix a race condition in the Git credential-cache daemon where concurrent `git credential-cache store` commands can cause one daemon to unlink another’s socket, leading to lost credentials, orphaned daemons, and inaccessible passwords. The issue surfaces during parallel submodule fetches over HTTPS and affects users with large repositories.

Current status
Under review; v1 posted. Patrick Steinhardt, Junio C Hamano, and Jeff King have provided substantive reviews. Patrick identified a pre-existing permission-handling issue in patch 1 and requested commit-message and code-comment clarifications in patch 2. Junio raised an architectural concern in patch 2 about the mixing of `unix_ss_*` and `tempfile` APIs, arguing that the `tempfile` registration is unnecessary and potentially harmful because it bypasses the `unix_ss_was_stolen()` safety check. Jeff King confirmed the fix in patch 1 (ignoring `EEXIST` from `mkdir()`) is correct and aligns with the behavior of `safe_create_leading_directories()` for other path components. In his latest review, Jeff also confirmed the core logic of patch 2 (using `unix_ss_create()` and the "ok" response) as correct, suggesting only minor cosmetic improvements (comment or `exit(0)` for clarity). No maintainer decision recorded; v2 expected to incorporate all feedback.

Key technical details
- Files touched: `builtin/credential-cache--daemon.c`, `t/t0301-credential-cache.sh`
- New behavior: daemon now ignores `EEXIST` from `mkdir()` (patch 1) and uses `unix_ss_create()` (patch 2) to safely handle concurrent socket creation; if a second daemon detects an existing socket, it prints "ok" and exits, allowing its client to communicate with the running daemon
- Old behavior: second daemon fails with "unable to mkdir" or unlinks first daemon’s socket, causing credential loss and orphaned processes
- Test coverage: new tests in `t/t0301-credential-cache.sh` exercise both the `mkdir()` race (patch 1) and the socket hijacking race (patch 2); the socket-hijacking test may not have failed pre-patch due to the client’s ping mechanism, but the race remains real during explicit daemon startup
- On-disk format: unchanged
- Symbols: `unix_ss_create()` (helper from simple-ipc subsystem) introduced as the safe socket-creation mechanism; `safe_create_leading_directories_no_share_const()` suggested for permission correctness in a preparatory commit
- Pre-existing issue: `safe_create_leading_directories()` incorrectly applies `core.sharedRepository` permissions to the user-specific credential-cache socket directory; the existing comment’s rationale for creating the directory with the correct mode upfront (to avoid a race where an attacker could chdir into the directory before permissions are set) is noted, and when the directory already exists, the race is mitigated by assuming the creator did so safely
- Architectural concern: mixing `unix_ss_*` and `tempfile` APIs in patch 2 is unsafe because `tempfile` registration bypasses `unix_ss_was_stolen()`, risking socket removal by a dying daemon that no longer owns it; precedent in `fsmonitor--daemon.c` uses `ipc_server_init_async()` (and thus `unix_ss_create()`) without `tempfile` registration

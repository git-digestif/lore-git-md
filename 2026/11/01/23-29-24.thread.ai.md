Thread identity
Subject: [PATCH 0/3] credential-cache: fix race condition in daemon socket handling
Series version: v2 (v1 reviewed; v2 posted with preparatory commit, documentation improvements, and patch split)
Originating author: Farid Zakaria
Thread type: bugfix patch series

Core problem or goal
Fix a race condition in the Git credential-cache daemon where concurrent `git credential-cache store` commands can cause one daemon to unlink another’s socket, leading to lost credentials, orphaned daemons, and inaccessible passwords. The issue surfaces during parallel submodule fetches over HTTPS and affects users with large repositories. Additionally, fix a pre-existing permission-handling issue in the socket directory creation that incorrectly applied `core.sharedRepository` settings to user-specific directories.

Current status
Under review; v1 posted and reviewed, v2 posted with three changes: (1) a preparatory commit (patch 1) replacing `safe_create_leading_directories()` with `safe_create_leading_directories_no_share_const()` to fix the pre-existing permission-handling issue in the socket directory, (2) patch 2 (formerly patch 1 in v1) unchanged in logic but now second in the series, and (3) patch 3 (formerly patch 2 in v1) with documentation improvements—commit message rephrased to imperative language, a code comment added to explain the "ok" response (part of the client-daemon protocol), redundant cleanup comments removed, and `exit(0)` used for clarity. The core race-condition fixes—ignoring `EEXIST` from `mkdir()` (patch 2) and using `unix_ss_create()` (patch 3)—remain unchanged. Junio’s architectural concern about mixing `unix_ss_*` and `tempfile` APIs in patch 3 was raised in v1; Farid’s v2 cover letter implied the socket cleanup behavior was unchanged without explaining why, prompting Junio to request a technical justification or a revised implementation. Junio’s latest reply rejects Farid’s claim that the socket-stealing race might only occur during Git upgrades (old client + new daemon), arguing that any serious installation would have a babysitter process to respawn dead daemons, making the race a persistent concern. Junio also expresses skepticism about Farid’s ability to judge which existing safety mechanisms can be safely ignored, given his unfamiliarity with the codebase, and questions why reviewers should invest time pointing out issues if the author dismisses them as unimportant. The architectural concern remains unresolved; no maintainer decision recorded. Patch 2 is confirmed by both Jeff King and Patrick Steinhardt as correct and uncontroversial.

Key technical details
- Files touched: `builtin/credential-cache--daemon.c`, `t/t0301-credential-cache.sh`
- New behavior: daemon now ignores `EEXIST` from `mkdir()` (patch 2), uses `unix_ss_create()` (patch 3) to safely handle concurrent socket creation, and creates the socket directory with mode `0700` regardless of `core.sharedRepository` settings (patch 1); if a second daemon detects an existing socket, it prints "ok" and exits, allowing its client to communicate with the running daemon
- Old behavior: second daemon fails with "unable to mkdir" or unlinks first daemon’s socket, causing credential loss and orphaned processes; socket directory permissions were incorrectly influenced by `core.sharedRepository` settings from the repository where the daemon was started
- Test coverage: new tests in `t/t0301-credential-cache.sh` exercise both the `mkdir()` race (patch 2) and the socket hijacking race (patch 3); the socket-hijacking test verifies the "ok" response and confirms credentials are preserved across concurrent daemon starts
- On-disk format: unchanged
- Symbols: `unix_ss_create()` (helper from simple-ipc subsystem) as the safe socket-creation mechanism; `safe_create_leading_directories_no_share_const()` introduced in preparatory commit for permission correctness
- Pre-existing issue: `safe_create_leading_directories()` incorrectly applied `core.sharedRepository` permissions to the user-specific credential-cache socket directory; the preparatory commit fixes this by using `safe_create_leading_directories_no_share_const()`
- Architectural concern: mixing `unix_ss_*` and `tempfile` APIs in patch 3 is unsafe because `tempfile` registration bypasses `unix_ss_was_stolen()`, risking socket removal by a dying daemon that no longer owns it; precedent in `fsmonitor--daemon.c` uses `ipc_server_init_async()` (and thus `unix_ss_create()`) without `tempfile` registration; Junio’s latest reply rejects Farid’s claim that the race might only occur during Git upgrades, arguing that any serious installation would have a babysitter process to respawn dead daemons, making the race a persistent concern
- Client-daemon protocol: the "ok" response is required by the client (`builtin/credential-cache.c:spawn_daemon()`) before it attempts to connect to the socket

Open questions and loose ends
- Architectural soundness: Junio’s concern about mixing `unix_ss_*` and `tempfile` APIs remains unresolved; Junio’s latest reply firmly rejects Farid’s claim that the race might only occur during Git upgrades and expresses skepticism about Farid’s ability to judge which safety mechanisms can be safely ignored; the unresolved question is whether the current approach is safe enough or if a v3 will be needed to handle the edge case

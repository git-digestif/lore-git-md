Subject: [PATCH 0/2] credential-cache: fix race condition in daemon socket handling
Series version: v2 (v1 reviewed; v2 posted with preparatory commit and documentation improvements)
Originating author: Farid Zakaria
Thread type: bugfix patch series

Core problem or goal
Fix a race condition in the Git credential-cache daemon where concurrent `git credential-cache store` commands can cause one daemon to unlink another’s socket, leading to lost credentials, orphaned daemons, and inaccessible passwords. The issue surfaces during parallel submodule fetches over HTTPS and affects users with large repositories.

Current status
Under review; v1 posted and reviewed, v2 posted with two changes: (1) a preparatory commit replacing `safe_create_leading_directories()` with `safe_create_leading_directories_no_share_const()` to fix a pre-existing permission-handling issue in the socket directory, and (2) documentation improvements in patch 2—commit message rephrased to imperative language, a code comment added to explain the "ok" response (part of the client-daemon protocol), and redundant cleanup comments removed. The core race-condition fixes—ignoring `EEXIST` from `mkdir()` (patch 1) and using `unix_ss_create()` (patch 2)—remain unchanged. Junio’s architectural concern about mixing `unix_ss_*` and `tempfile` APIs in patch 2 is still open; v2 continues to register the socket with the `tempfile` API, but the author has not yet responded to Junio’s objection. No maintainer decision recorded.

Key technical details
- Files touched: `builtin/credential-cache--daemon.c`, `t/t0301-credential-cache.sh`
- New behavior: daemon now ignores `EEXIST` from `mkdir()` (patch 1) and uses `unix_ss_create()` (patch 2) to safely handle concurrent socket creation; if a second daemon detects an existing socket, it prints "ok" and exits, allowing its client to communicate with the running daemon
- Old behavior: second daemon fails with "unable to mkdir" or unlinks first daemon’s socket, causing credential loss and orphaned processes
- Test coverage: new tests in `t/t0301-credential-cache.sh` exercise both the `mkdir()` race (patch 1) and the socket hijacking race (patch 2); the socket-hijacking test may not have failed pre-patch due to the client’s ping mechanism, but the race remains real during explicit daemon startup
- On-disk format: unchanged
- Symbols: `unix_ss_create()` (helper from simple-ipc subsystem) as the safe socket-creation mechanism; `safe_create_leading_directories_no_share_const()` introduced in preparatory commit for permission correctness
- Pre-existing issue: `safe_create_leading_directories()` incorrectly applied `core.sharedRepository` permissions to the user-specific credential-cache socket directory; the preparatory commit fixes this by using `safe_create_leading_directories_no_share_const()`
- Architectural concern: mixing `unix_ss_*` and `tempfile` APIs in patch 2 is unsafe because `tempfile` registration bypasses `unix_ss_was_stolen()`, risking socket removal by a dying daemon that no longer owns it; precedent in `fsmonitor--daemon.c` uses `ipc_server_init_async()` (and thus `unix_ss_create()`) without `tempfile` registration
- Client-daemon protocol: the "ok" response is required by the client (`builtin/credential-cache.c:spawn_daemon()`) before it attempts to connect to the socket

Open questions and loose ends
- Architectural soundness: Junio’s concern about mixing `unix_ss_*` and `tempfile` APIs; v2 still registers the socket with the `tempfile` API, but the author has not yet responded to the objection
- Edge-case handling: socket cleanup on daemon exit (potential review topic)
- Platform coverage: commit message does not detail testing beyond Linux/rewind
- Timeout behavior: no mention of interaction with daemon idle-timeout settings
- Cleanup robustness: whether a losing daemon might still leave behind stale socket directories

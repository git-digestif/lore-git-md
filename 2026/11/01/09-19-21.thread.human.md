This thread is a two-patch bugfix series from Elia Pinto fixing silent truncation of files 4GiB or larger on platforms where `long` is 32-bit but `size_t` is 64-bit, notably 64-bit Windows. The root cause is the use of `unsigned long` for file-size variables, which the series replaces with `size_t`. Patch 1 fixes `git archive` for tar and zip formats (touching `archive-tar.c`, `archive-zip.c`, `archive.h`), and patch 2 fixes `git apply` in `apply.c`. The series is still at v1, applies cleanly to current `master`, and has received no review comments yet.

In a follow-up ping, the author raised a dependency the original submission should have flagged: while patch 2 fixes the working-tree file, the blob that `git apply --index` and `git am` add to the index via `add_index_file()` still passes its size to `odb_write_object()`, whose length parameter remains `unsigned long` until a separate "use size_t for a few more object and buffer sizes" series lands. On affected platforms the indexed blob would still be silently truncated even though the working-tree file is complete. The author offers two options -- either cast through `cast_size_t_to_ulong()` in `add_index_file()` so the command dies loudly instead of truncating, or hold patch 2 back until the `size_t` series merges, as Patrick Steinhardt suggested for a similar case -- and expresses no preference. No maintainer has responded yet, so the way forward for patch 2 remains open.

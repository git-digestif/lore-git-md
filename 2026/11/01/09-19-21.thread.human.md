This thread is a two-patch bugfix series from Elia Pinto that fixes silent truncation or corruption of files 4GiB or larger in `git archive` (tar/zip formats) and `git apply` on platforms where `long` is 32-bit but `size_t` is 64-bit—most notably 64-bit Windows. The issue arises because `unsigned long` cannot represent sizes ≥4GiB on these platforms, leading to data loss when processing large files. The fix replaces `unsigned long` with `size_t` for file-size variables in the affected code paths, ensuring they can handle large files correctly.

The series is under review and targets the `master` branch. The first patch updates `archive-tar.c`, `archive-zip.c`, and `archive.h`, while the second patch (this email) focuses on `apply.c`, updating four functions to use `size_t` for file sizes. The changes are mechanical and confined to type declarations, with no behavioral impact on platforms where `long` is already 64-bit. Elia verified the fixes by simulating a 16-bit truncation scenario, confirming that the issue is resolved without introducing new problems.

No review feedback has been posted yet, and no objections or requests for changes have been raised. The series is well-scoped and addresses a real, user-visible issue without adding complexity. The existing `t5004` test (for zip archives >4GB) is currently disabled on 32-bit `long` platforms, but the author suggests relaxing its guard to `SIZE_T_IS_64BIT` to enable testing on 64-bit Windows. The patches are low-risk and suitable for `master`.

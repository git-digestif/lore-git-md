This is a maintainer feedback email on a bugfix patch targeting the `pack-objects` subsystem. Junio C Hamano requests a clarification in the commit message to avoid future confusion: the issue is not about 32-bit platforms in general, but specifically about platforms where `long` is 32 bits *but* `size_t` is larger (e.g., 64 bits). The current phrasing ("On platforms where 'long' is 32 bits") could mislead readers into thinking the fix is irrelevant for 32-bit systems, when in fact it addresses a truncation bug that occurs precisely when `size_t` can represent values ≥4GiB while `unsigned long` cannot.

The feedback is purely editorial and does not challenge the technical correctness of the patch (v2), which already uses `size_t` for the blob size and `off_t` for compressed data lengths. The requested change is to reword the commit message to explicitly state the condition: "platforms where 'long' is 32 bits but 'size_t' is larger than that." This ensures the rationale is unambiguous for future maintainers or contributors reviewing the history. The patch remains narrowly scoped to the large-blob streaming path in `builtin/pack-objects.c` and is otherwise uncontroversial.

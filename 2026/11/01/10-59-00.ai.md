This is a small but useful diagnostic patch for the `git maintenance` subsystem. It adds a Trace2 data event when `git maintenance run --auto` skips execution because an existing `maintenance.lock` file is present. The change is minimal: two lines in `builtin/gc.c` to emit the trace event, and a new test in `t/t7900-maintenance.sh` to verify the event is logged correctly.

The motivation is clear: silent skips make it hard to diagnose why automatic maintenance isn’t running, especially if a stale lock is left behind by an interrupted process. The patch addresses this by surfacing the skip in Trace2 logs, which are typically enabled in production environments for observability. The implementation is straightforward and follows established patterns for Trace2 data events in Git.

The test coverage is adequate: it creates a lock file, runs `git maintenance run --auto`, and checks that the expected Trace2 event is emitted. The test also verifies the lock file remains in place afterward, confirming the skip behavior is preserved.

This is not part of a larger series (the email is a standalone patch), and it doesn’t touch any controversial areas. The change is narrowly scoped to the maintenance lock-handling logic and should be uncontroversial. The author is a first-time contributor, but the patch is well-structured and adheres to Git’s coding conventions.

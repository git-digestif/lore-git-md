Subject: [PATCH 0/2] Fix 4GiB+ file truncation on 32-bit `long` platforms
Series version: v1 (initial submission)
Originating author: Elia Pinto
Thread type: bugfix patch series

Core problem or goal
Fix silent truncation or corruption of files 4GiB or larger in `git archive` (tar and zip formats) and `git apply` on platforms where `long` is 32-bit but `size_t` is 64-bit (notably 64-bit Windows). The root cause is the use of `unsigned long` for file-size variables, which cannot represent sizes ≥4GiB on these platforms; the fix replaces these with `size_t`, which is guaranteed to be large enough.

Current status
Under review. Two patches, both targeting the `master` branch (base 50fe5cc63f). No prior versions of this series exist. The patches merge cleanly with other in-flight topics.

Key technical details
- Files touched: `apply.c`, `archive-tar.c`, `archive-zip.c`, `archive.h`
- Subsystems: archive (tar/zip), apply
- Symbols: type changes only (`unsigned long` → `size_t` for file-size variables)
- On-disk format: unchanged
- Test coverage: existing `t5004` (zip archive >4GB) is currently disabled on 32-bit `long` platforms; with these patches, the guard could be relaxed to `SIZE_T_IS_64BIT` to enable real testing on 64-bit Windows
- Behavior: no change on platforms where `long` is already 64-bit; fixes silent truncation on affected platforms

Open questions and loose ends
- No new tests included; author verified fixes by simulating truncation at 16 bits but did not test the relaxed `t5004` guard on 64-bit Windows.
- No review feedback yet; no objections or requests for changes raised.

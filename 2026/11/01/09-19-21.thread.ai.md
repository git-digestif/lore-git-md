Subject: [PATCH 0/2] Fix 4GiB+ file truncation on 32-bit `long` platforms
Series version: v1 (initial submission)
Originating author: Elia Pinto
Thread type: bugfix patch series

Core problem or goal
Fix silent truncation or corruption of files 4GiB or larger in `git archive` (tar and zip formats) and `git apply` on platforms where `long` is 32-bit but `size_t` is 64-bit (notably 64-bit Windows). The root cause is the use of `unsigned long` for file-size variables, which cannot represent sizes >=4GiB on these platforms; the fix replaces these with `size_t`, which is guaranteed to be large enough.

Current status
Under review. Two patches, both targeting the `master` branch (base e1ec09b23c, confirmed to still apply cleanly and merge with `seen`). Patrick Steinhardt has decided that patch 2/2 (the `git apply` fix) should be held back entirely until the separate "use size_t for a few more object and buffer sizes" series lands, rather than using a `cast_size_t_to_ulong()` workaround in `add_index_file()`; he has asked the author to send a rebased version of the series once that dependency has landed. Patch 1/2 (archive fixes) stands alone. No review feedback yet on the technical correctness of either patch. Elia Pinto has acknowledged this plan and confirmed he will resend the series once the blocking dependency lands.

Key technical details
- Files touched: `apply.c` (patch 2), `archive-tar.c`, `archive-zip.c`, `archive.h` (patch 1)
- Subsystems: archive (tar/zip), apply
- Symbols: type changes only (`unsigned long` -> `size_t` for file-size variables in archive callback and helper functions, and in `apply.c` functions `create_file`, `create_one_file`, `try_create_file`, and `add_index_file`)
- On-disk format: unchanged
- Test coverage: existing `t5004` (zip archive >4GB) is currently disabled on 32-bit `long` platforms; with these patches, the guard could be relaxed to `SIZE_T_IS_64BIT` to enable real testing on 64-bit Windows. Author verified fixes by simulating truncation at 16 bits.
- Behavior: no change on platforms where `long` is already 64-bit; fixes silent truncation (tar: truncated headers with full blob data; zip: incorrect headers and corrupted output; `git apply`: truncated patch application) on affected platforms.
- Remaining gap in patch 2/2: `add_index_file()` passes the file size to `odb_write_object()`, whose length parameter is still `unsigned long` until a separate series lands. On 32-bit `long` platforms, the blob added to the index via `git apply --index` or `git am` would still be silently truncated even though the working-tree file is now complete.

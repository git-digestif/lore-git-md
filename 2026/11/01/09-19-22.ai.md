This is the first patch in a two-patch bugfix series addressing silent truncation or corruption of files 4GiB or larger on platforms where `long` is 32-bit but `size_t` is 64-bit (notably 64-bit Windows). The patch changes the type of file-size variables in the archive subsystem from `unsigned long` to `size_t`, ensuring that large files can be correctly represented and processed in both tar and zip formats.

The changes are confined to `archive-tar.c`, `archive-zip.c`, and `archive.h`, where the callback and helper functions for writing archive entries are updated to use `size_t` for file sizes. The commit message explains that the existing code causes silent corruption when streaming files ≥4GiB: tar archives end up with truncated headers but full blob data, while zip archives produce incorrect headers and corrupted output. The author verified the fix by simulating a 16-bit truncation scenario, which previously caused tar to extract truncated data and Python’s `zipfile` to reject the archive due to bad magic numbers or CRC errors.

This patch is purely a type change and does not alter behavior on platforms where `long` is already 64-bit. It prepares the ground for the second patch, which will address the same issue in `git apply`. The existing `t5004` test for zip archives >4GB is currently disabled on 32-bit `long` platforms; with this series, the guard could be relaxed to `SIZE_T_IS_64BIT` to enable real testing on 64-bit Windows, though the author hasn’t tested this themselves. No new tests are included in this patch.

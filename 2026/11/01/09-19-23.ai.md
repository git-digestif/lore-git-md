This is the second patch in a two-patch bugfix series addressing silent truncation of files 4GiB or larger on platforms where `long` is 32-bit but `size_t` is 64-bit (e.g., 64-bit Windows). The series targets `git apply` and `git archive` (tar/zip formats), replacing `unsigned long` with `size_t` for file-size variables to ensure they can represent sizes ≥4GiB.

This patch focuses on `apply.c`, updating four functions (`create_file`, `create_one_file`, `try_create_file`, and `add_index_file`) to use `size_t` for the size of the result written out. The commit message explains that the truncation occurs because `unsigned long` is too small to hold sizes ≥4GiB on affected platforms, leading to silent data loss when applying patches to large files. The author verified the fix by simulating a 16-bit truncation scenario, where `git apply` previously truncated a 7901-line file to 2859 lines without error.

The change is mechanical and confined to type declarations, with no behavioral impact on platforms where `long` is already 64-bit. The patch aligns with the first patch in the series, which made similar changes in `archive-tar.c` and `archive-zip.c`. The author notes that `add_index_file` passes the size to `odb_write_object`, which already expects `size_t` (a change introduced in a separate series). No new tests are included, as triggering the issue requires processing a 4GiB+ file on an affected platform, but the existing `t5004` test (for zip archives >4GB) could be enabled on 64-bit Windows by relaxing its guard to `SIZE_T_IS_64BIT`.

The patch is well-scoped and addresses a real, user-visible issue without introducing complexity. The series as a whole appears ready for review, with no prior feedback or objections raised. Key files touched: `apply.c` (this patch) and `archive-tar.c`, `archive-zip.c`, `archive.h` (first patch). The changes are low-risk and confined to type safety, making them suitable for `master`.

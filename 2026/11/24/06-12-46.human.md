This is the third and final patch of a three-patch bugfix series fixing a data-loss race in `git repack -d`. The race occurs when a `.keep` file appears on a pack after `repack` has scanned for kept packs but before `pack-objects` scans them again: the parent process decides to delete the pack, but the child sees the new `.keep` and skips the pack's objects, leaving them deleted with the pack and causing dangling refs.

This patch makes `repack` write the names of all non-kept and cruft packs it intends to delete into a temporary file and pass that file to every spawned `pack-objects` via the new `--ignore-pack-keep-from=<file>` option (introduced in the previous patch of this series). That option clears the kept flag for those specific packs regardless of what appears on disk later, ensuring their reachable objects are copied into the new pack or loosened as appropriate. Packs that were kept at startup or acquire a `.keep` file later still honor their `.keep` files, so the existing `--honor-pack-keep` behavior remains for everything else.

The implementation touches `builtin/repack.c`, `repack.c`, and `repack.h` to add the snapshot writing and argument passing, including a new `existing_packs_write_non_kept()` helper that writes one pack basename per line. The snapshot is only created when there are actually packs to delete, and it is written next to the refs snapshot already used for `git multi-pack-index write`.

Tests in `t/t7700-repack.sh` and `t/t7703-repack-geometric.sh` use a `git` wrapper shim to inject a `.keep` file at the exact moment `pack-objects` starts, then verify via `git fsck` that no objects are lost across `-a -d`, `-A -d`, `-k`, `--cruft`, `--geometric`, and `--filter` modes. The series has received Reviewed-by tags from Jeff King and Taylor Blau and is considered ready for integration into `next`.

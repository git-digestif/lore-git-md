This is the second patch in a three-patch bugfix series (v5) that addresses a data-loss race in `git repack -d`. The series, authored by Qin ShiCheng, fixes a scenario where a `.keep` file appearing on a pack mid-repack -- for example from a concurrent push -- causes `pack-objects` to skip that pack's objects while `repack` deletes the pack anyway, leaving dangling refs. This specific patch adds a new plumbing option to `git pack-objects` that lets the caller explicitly name packs whose `.keep` files should be ignored.

The new option, `--ignore-pack-keep-from=<file>`, reads pack names from a file (one per line, matched like `--keep-pack`) and clears the `pack_keep` flag for those packs before any object-list processing begins. This ensures that all downstream logic -- `--honor-pack-keep`, `--unpack-unreachable`, `--keep-unreachable`, and `--cruft` -- treats the named packs as if they had no `.keep` file, so their objects are properly packed, loosened, or kept as needed. The file-based approach avoids command-line length limits (particularly the 32767-character limit on Windows) since standard input is already occupied in the modes `repack` uses.

The patch touches `builtin/pack-objects.c` to implement the option parsing and the `ignore_pack_keep_from_file()` helper, updates `Documentation/git-pack-objects.adoc` with the new synopsis and description, and adds two tests to `t/t7700-repack.sh` verifying that named packs are treated as un-kept while others retain their `.keep` status, plus error handling for a missing input file.

Within the broader series, this patch provides the mechanism that patch 3/3 will use: `builtin/repack.c` will write a snapshot of all non-kept packs observed at startup to a tempfile and pass it via this new option, ensuring that `.keep` files created during the repack cannot cause deletion of packs whose objects were not preserved elsewhere. The series has received Reviewed-by tags from Jeff King (on patch 1/3) and Taylor Blau (on patch 3/3) and appears ready for integration.

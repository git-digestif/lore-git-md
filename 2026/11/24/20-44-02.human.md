This is a substantive review of the third patch in Yoichi NAKAYAMA's v2 series on worktree-specific submodule configuration. Junio C Hamano identifies a subtle symlink and path-normalization hazard in the new helper `submodule_git_dir_matches_current_worktree()` that could cause false mismatch warnings under specific invocation patterns.

The concern centers on inconsistent canonicalization between the two paths being compared. The submodule gitdir path is built via `repo_worktree_path_append()`, which anchors to `the_repository->worktree` -- a path canonicalized through `real_pathdup()` during repository setup. The superproject git dir, however, comes from `absolute_pathdup(repo_get_git_dir(the_repository))`, which resolves relative gitdirs against the current working directory without symlink resolution, and copies absolute `GIT_DIR` values verbatim without normalizing `.` or `..` components. When these two sides diverge due to symlinks in the path, the comparison can incorrectly conclude that an existing gitdir setting does not belong to the current worktree.

Concrete reproduction scenarios include running `GIT_DIR=.git git submodule init` from a symlinked directory pointing to the worktree, using `GIT_DIR=.git/../.git`, or invoking `git submodule--helper init` directly through a symlink. In these cases, `super` and `submodule` fail to match even when they refer to the same physical location, triggering the new `submodule_mismatch_warning` and generating a fresh gitdir instead of preserving the existing configuration.

Junio suggests canonicalizing both sides to eliminate the false positive: using `real_pathdup(repo_get_git_dir(the_repository), 1)` for the superproject path and `strbuf_realpath_forgiving()` for the submodule path. He acknowledges this may produce uglier absolute paths in some cases, but notes that resolving symlinks on both sides makes the comparison robust regardless of how the repository was addressed.

This is a discussion reply on CLI design scope within the v10 patch series for `git branch --delete-merged` / `--delete-integrated`. Junio C Hamano responds to Harald Nordgren's suggestion that the broader redesign of `--dry-run` -- making it a universal modifier across all `git branch` operations with specific per-operation "not supported yet" error messages -- should be handled separately from this topic. Junio frames the choice as binary: either `--dry-run` is out of scope for this series entirely, or, since patch 3/5 introduces it for deletion modes (`-d`/`-D`), users will expect the individualized errors from creation and renaming operations rather than the current generic incompatibility messages. No code changes are proposed here; the email simply clarifies that if `--dry-run` remains part of this topic, the per-operation error handling is an expected consequence, not an optional future enhancement.

For future thread context: this touches the option validation logic in `builtin/branch.c` modified by patch 3/5 (`if (dry_run && !delete && !delete_merged.nr)` and the `DELETE_BRANCH_DRY_RUN` flag). The unresolved question is whether follow-up patches in this series should add operation-specific `--dry-run` rejection messages for branch creation (`git branch --dry-run <new> <start>`) and renaming (`git branch --dry-run -m <old> <new>`), or whether those belong in a separate effort. Currently v10 only accepts `--dry-run` with deletion modes (`-d`, `-D`, `--delete-merged`, `--delete-integrated`), and any expansion to other operations would require new error paths in `cmd_branch()` alongside the existing deletion logic.

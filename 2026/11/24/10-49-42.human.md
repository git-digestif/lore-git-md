This is a substantive review reply in the `git history` worktree-safety bugfix thread. Phillip Wood responds to Aniket Gupta's point-by-point answers, raising one new behavioral concern and adding a follow-up suggestion.

Wood flags that allowing `--update-refs=head` while a rebase is in progress in the same worktree is arguably a bug: `git history` rewrites the detached `HEAD`, but `git rebase --continue` will later discard that result, making the history edit silently ineffective. He agrees with Gupta that preventing `git rebase` from rewriting a branch currently being rewritten by `git history` is worth doing but can wait, and adds a symmetric follow-up: `git history` should also refuse to run if another `git history` process is already rewriting the same branches.

On the technical approach for v2, Wood confirms that folding the worktree check into the revision walk via ref decorations works, but notes -- as Gupta had already spotted -- that the branch pointing at the rewritten commit itself is not part of the walk, so its decorations must be inspected separately to catch the case where another worktree's branch points directly at the commit being rewritten.

This is a discussion reply in the ongoing bugfix thread for the experimental `git history` command, specifically addressing how the patch should handle mid-rebase behavior in the current worktree. Aniket Gupta corrects his earlier statement to Phillip Wood regarding the interaction between `git history --update-refs=head` and an active rebase: the command is not always refused when a rebase is running, but only when the rewritten commit is still on the branch being rebased. In the other case, `git history` updates the detached `HEAD` in the middle of the rebase, and that history rewrite is silently discarded when `git rebase --continue` or `git rebase --abort` completes, leaving no trace of the operation.

The technical scenario involves `git history` running with `--update-refs=head` while `git rebase` is active in the same worktree. During rebase, `HEAD` is detached, so the update targets the detached state rather than a branch ref. If the target commit is not on the branch currently being rebased, the check does not trigger, allowing the rewrite to proceed against the temporary detached `HEAD`. However, once the rebase finishes and reattaches `HEAD` to the updated branch, the intermediate `git history` result vanishes. Gupta acknowledges this is incorrect behavior and commits to making v2 of the patch refuse to run in both modes when a rebase is active in the current worktree.

This clarification narrows the scope of the bare-repository and worktree-safety fixes already planned for v2. The patch continues to focus on preventing `git history` from rewriting branches checked out in other linked worktrees, but now explicitly extends the refusal to the mid-rebase case for `--update-refs=head` to avoid silently losing history rewrites. No code changes are included in this email; it is a commitment to behavior change in the next iteration. The thread remains open awaiting v2, which will also address the bare-repository edge case identified by Junio C Hamano and the decoration-based refactoring suggested by Wood.

This is a design-discussion reply within the v10 `--delete-merged`/`--delete-integrated` thread, not a patch. Harald Nordgren responds to Junio C Hamano's binary framing of `--dry-run` scope: either the option is removed from this series entirely, or, since patch 3/5 already enables it for deletion modes (`-d`/`-D`/`--delete-merged`/`--delete-integrated`), the series should also include operation-specific "not supported" error messages for branch creation and renaming. Harald agrees that universal `--dry-run` across all `git branch` operations is a sound direction but argues this topic is the wrong vehicle for it; he proposes handling creation (`git branch --dry-run <new> <start>`) and renaming (`git branch --dry-run -m <old> <new>`) as a follow-up after this series lands, and suggests avoiding the word "yet" in those future error messages so as not to promise eventual support. He tags the exchange with `#leftoverbits` to mark it as deferred work.

For future thread context: this exchange leaves the `--dry-run` validation in `builtin/branch.c` (modified by patch 3/5 with `if (dry_run && !delete && !delete_merged.nr)`) unchanged in v10 -- `--dry-run` remains accepted only with deletion modes and rejected generically for create/rename operations. The open question for any follow-up is whether to add specific rejection paths in `cmd_branch()` for `git branch --dry-run` with creation or `-m`/`-M` renaming arguments, implemented in a separate series after this topic merges, with error text that avoids implying these operations will support `--dry-run` in the future.

This is a review reply in the ongoing bugfix thread for the experimental `git history` command, which aims to prevent the command from rewriting branches checked out in other linked worktrees.

Aniket Gupta is correcting his earlier statement about how `git history` behaves when a rebase is already running in the same worktree. He now acknowledges the bug Phillip Wood flagged: when `git history --update-refs=head` runs mid-rebase, it updates the detached `HEAD`, but that rewrite is silently discarded once `git rebase --continue` or `git rebase --abort` completes. Gupta confirms he will make the command refuse to run in both the default mode and `--update-refs=head` mode when a rebase is active, fixing this in the upcoming v2.

The exchange is part of the broader discussion -- alongside Junio C Hamano's bare-repository edge case and the planned decoration-based refactoring -- that must be resolved before the patch is ready for wider consideration. No new code is attached in this email; it is a commitment to the fixes in the next iteration.

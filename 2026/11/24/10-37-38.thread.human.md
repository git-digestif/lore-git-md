Phillip Wood's patch adds a new `GIT_COMMENT_STRING` variable to `git var`, letting scripts query the effective comment string directly instead of parsing both `core.commentChar` and `core.commentString` themselves. The patch is under review with no merge decision indicated; Junio C Hamano has acknowledged the motivation as good while flagging a pre-existing last-one-wins inconsistency between the two comment config keys as a non-blocking observation.

The review discussion has now converged. Kristoffer Haugsbakk initially pushed for the man page to cross-reference both config keys in `git-config(1)`, but after Wood argued the config docs add nothing useful, Haugsbakk conceded and the two settled on the phrasing "as set by `core.commentString`" for the `GIT_COMMENT_STRING` entry. Haugsbakk also approved of Wood's alternative of adding a pointer note in the `core.commentString` documentation directing readers to `git var GIT_COMMENT_STRING`, and agreed to Wood's plan to reword "comment character" to "comment string" in the commit message. No blocking objections remain.

Technically the patch is small and self-contained: a `comment_string()` helper in `builtin/var.c` returning `xstrdup(comment_line_str)`, registration in the `git_vars[]` table, documentation in `git-var.adoc` and `git-config.adoc`, and tests in `t/t0007-git-var.sh` covering the default `#` and a custom `core.commentString` value. One edge case worth knowing: an invalid empty `core.commentString` makes `git var GIT_COMMENT_STRING` abort during config parsing rather than return a default.

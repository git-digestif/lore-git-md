Phillip Wood has posted a small feature patch that makes the effective comment string directly queryable through `git var GIT_COMMENT_STRING`, sparing scripts from having to reconcile `core.commentChar` and `core.commentString` on their own to figure out which character Git will actually use in commit message templates and rebase todo lists. The implementation is minimal: a `comment_string()` helper in `builtin/var.c` that returns the global `comment_line_str`, a new entry in the `git_vars[]` table, documentation in `Documentation/git-var.adoc`, and tests in `t/t0007-git-var.sh` covering both the default `#` and a custom `core.commentString` value.

Kristoffer Haugsbakk has replied with a substantive review. He suggests minor wording changes to the commit message and asks that the man page cross-reference the `core.commentChar` and `core.commentString` config keys in `git-config(1)`, and he confirms the test coverage is adequate. He also surfaced a noteworthy edge case: if `core.commentString` is set to an invalid empty value, `git var GIT_COMMENT_STRING` aborts with a fatal error rather than falling back to a default, because the underlying global fails during config parsing. No blocking objections were raised, and the patch remains under review with no merge status indicated.

This is a substantive review from Junio C Hamano of the first patch in Ravi Mistry's five-part v4 series reworking Git's HTTP transport retry handling. The email responds to `[PATCH v4 1/5]`, which fixes two bugs introduced by the original HTTP 429 rate-limit support: an off-by-one error where `http.maxRetries=N` only performed N-1 retries due to pre-decrement, and a Trace2 logging issue where `Retry-After` values were recorded as -1 because the extraction happened too late.

Junio engages directly with the proposed code changes, confirming that moving the `http_max_retries <= 0` guard to after the loop correctly prevents the counter from wrapping from 0 to -1 (which would be truthy in C) when a 401 is followed by a 429 with retries disabled. He also validates the switch to post-decrement with an explicit guard, noting that this allows the full N retries to execute and safely handles negative configuration values. His closing "Looking good" signals approval of the fix, indicating the patch addresses the identified problems cleanly. This review advances the series toward integration, though the larger architectural questions about configurable retry codes and the two-phase default change raised in earlier iterations remain open for the subsequent patches.

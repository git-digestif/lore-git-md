This is a maintainer review reply from Junio C Hamano on Phillip Wood's feature patch adding `GIT_COMMENT_STRING` to `git var`. Junio acknowledges the patch's motivation as good while noting an unfortunate design wrinkle: the existing configuration honors last-one-wins semantics across `core.commentString` and `core.commentChar`, meaning scripts cannot simply prefer one over the other when both are set. This observation does not block the patch but flags a pre-existing inconsistency in how the two comment-related config keys interact, which future discussion might revisit.

The email advances the thread from initial submission to maintainer engagement without yet indicating a merge decision. Junio's comment confirms the patch addresses a real scripting pain point identified in the original commit message -- the awkward shell pipelines previously needed to determine the effective comment character -- but stops short of saying "will merge" or queuing the topic in any integration branch. The patch remains under review.

For future reference, the technical surface touched remains `builtin/var.c` (adding a `comment_string()` helper returning the global `comment_line_str`), the `git_vars[]` table registration, `Documentation/git-var.adoc`, and `t/t0007-git-var.sh`. The key behavioral detail is that `git var GIT_COMMENT_STRING` will abort with a fatal error if `core.commentString` is set to an empty value during config parsing, rather than falling back to a default.

This is a review reply in an ongoing test-infrastructure thread, specifically Kaartic Sivaraam responding to Junio C Hamano's objections to the `[PATCH v2]` that serializes `EXPENSIVE` tests in `t/test-lib.sh`.

Sivaraam proposes two incremental fixes to the lock mechanism in `acquire_expensive_lock_()`. First, to address the TOCTOU race where a waiter might delete a new lock holder's directory, he adds a secondary "break lock" (`$expensive_lock_.break`) created via `mkdir` before removing a stale lock, and re-reads the `pid` file to verify the owner hasn't changed before running `rm -rf`. Second, to address the signal-handling deadlock where a process killed between `mkdir "$expensive_lock_"` and setting `have_expensive_lock_=t` leaves an unremovable empty lock directory, he reorders the code to set `have_expensive_lock_=t` before writing the PID to the `pid` file, ensuring `release_expensive_lock_()` will clean up even if the PID write is interrupted.

Sivaraam explicitly acknowledges that these fixes do not cover all edge cases: a `kill -9` arriving after `mkdir` but before the PID write, or a signal arriving in the microseconds between `mkdir` and setting the flag, would still leave a permanently stuck lock. He suggests deferring fixes for those remaining windows until they cause actual problems, asking for Junio's thoughts. The thread remains open with v2 not yet accepted; Junio has previously characterized the deadlock scenario as "far worse" than the race condition, and no v3 has been posted yet.

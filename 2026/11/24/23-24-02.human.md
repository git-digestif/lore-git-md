This is a **substantive review** of patch 5/6 in Patrick Steinhardt's six-part packfile lifecycle refactoring series. Junio C Hamano generally approves of the technical approach while raising one wording issue and one deeper design question about the ODB abstraction effort.

Junio praises the core mechanism: introducing the global `all_packfiles` list and changing `close_one_pack()` to take no repository parameter makes it "crystal clear" that pack selection for limit enforcement is now process-wide rather than per-repo. He explicitly notes that this cleanly removes the unconditional `odb_source_files_downcast()` calls that previously assumed the "files" backend, which is exactly the hard-coded dependency the series aims to eliminate. He also confirms that routing all allocations through `packfile_new()` and all deallocations through `packfile_free()` ensures the global list never retains dangling pointers.

On wording, Junio objects to the commit message's phrase "maximum number of packfile data" as awkward, suggesting "maximum amount of" or "maximum number of bytes of" instead. This is a minor surface-level suggestion buried in an otherwise substantive review.

The more significant point is a conceptual concern: Junio notes an "impedance mismatch" between the goal of a flexible, pluggable object store that may not even have the concept of a "packfile," and the assumption in this patch that packfiles occupy address space and need eviction under memory pressure. He admits he cannot think of a way to rectify it but flags it as a tension worth noting.

Overall, the review signals approval of the patch's direction with minor revisions expected. The global list approach is seen as sound and well-executed, setting up patch 6/6's limit-handling fixes cleanly.

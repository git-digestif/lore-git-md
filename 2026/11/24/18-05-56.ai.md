This is a **bugfix** (v2 of a standalone patch) targeting the config subsystem, specifically the section copy/rename/remove logic in `config.c`.

Dominik Maier resends the fix for `repo_config_copy_or_rename_section_in_file()`, which previously scanned config files line-by-line and treated any line starting with `[` as a new section header, even when that line was a backslash-continued value. The bug caused `git config --remove-section`, `--rename-section`, and `git branch -c` to stop early and leave fragments of continued values behind as spurious new sections. The v2 patch introduces three helpers: `is_config_eol()` (recognizes `\n` and CRLF but treats bare `\r` as a regular character), `skip_section_header()` (parses valid section headers including quoted subsections with escaped characters), and `update_line_continuation()` (tracks across lines whether the parser is inside a double-quoted string via `in_quote` and whether the current line continues a previous backslash-terminated value via `continued`). The main loop now calls `update_line_continuation()` before checking for `[`, treating a line as a section header only when `was_continued` is false.

Compared to v1, this version moves the `was_continued` declaration to the top of the loop block to satisfy `-Wdeclaration-after-statement` (Junio's style feedback), treats bare carriage returns as ordinary characters rather than line separators so subsections and values containing `\r` parse consistently with `git_parse_source()` (addressing Phillip Wood's reproduction concern), rejects empty `[]` section headers, and preserves inline entries that follow a copied section header so `git branch -c` handles continued inline entries correctly. Tests in `t/t1300-config.sh` now cover removal and rename of sections with bracketed continuation lines, quoted hashes, subsection names containing brackets and escaped quotes, bare `\r` inside values and subsection names, CRLF line endings, empty section headers, and the `git branch -c` copy path.

Open questions from the thread remain: Junio C Hamano has asked whether treating bracketed text on continued lines as part of the value might break existing configs that rely on the old parsing behavior, while Phillip Wood has argued the change merely aligns the copy/rename parser with the existing `git_parse_source()` reader behavior.

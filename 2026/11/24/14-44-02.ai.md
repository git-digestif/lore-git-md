This is a substantive maintainer review of patch 1/7 in Harald Nordgren's v15 series, which introduces `map_refs_without_dst()` in `builtin/fetch.c` to skip refmap application for refspecs carrying an explicit destination. Junio C Hamano confirms the implementation correctly handles the distinction between empty and non-empty destinations by relying on `rm->peer_ref` being NULL for destination-less (or empty-destination) refspecs, ensuring `copy_ref()` does not recurse and `get_fetch_map()` allocates fresh entries before the temporary list is freed.

The review identifies a minor commit-message inaccuracy: the referenced configuration is added in patch 3/7, not 2/7, suggesting "a later commit" as a looser alternative. He also tightens the proposed documentation wording in `Documentation/fetch-options.adoc` to specify that a refspec with a non-empty `<dst>` is stored only at that destination and bypasses the refmap, while explicitly empty destinations like `main:` still trigger refmap processing. This distinction matters because every refspec technically has a `<src>:<dst>` form, so the condition must reference non-empty `<dst>` rather than merely the presence of a colon.

The review validates the intended semantics: `refs/heads/main` and `refs/heads/next:` (empty `<dst>`) remain subject to `--refmap`, whereas `refs/heads/seen:refs/remotes/origin/seen` (non-empty `<dst>`) is stored only at the explicit destination and exempt from mapping. This patch establishes the foundational behavior that patch 2/7 and patch 3/7 build upon when introducing `remote.<name>.fetchRefmap` as a configured default, preventing dual storage when command-line refspecs carry their own destinations.

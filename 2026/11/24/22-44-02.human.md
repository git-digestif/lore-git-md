This is a maintainer review of the third patch in Ravi Mistry's v4 series on HTTP transport resilience. Junio C Hamano examines patch 3/5, which introduces the `http.retryStatusCodes` configuration key and `GIT_HTTP_RETRY_STATUS_CODES` environment variable to let users opt in to retrying transient 5xx errors beyond the default 429.

The review is substantive rather than surface-level. Junio accepts the documentation framing that positions extra status codes as temporary workarounds for misbehaving provider infrastructure, but suggests the docs should clarify that setting the config to an empty string disables all retries rather than restoring the 429 default. He also points out an edge case outside the patch's immediate scope: because `handle_curl_result()` checks for 401 and 404 before consulting the retry logic, those codes will not be retried even if a user explicitly lists them in `http.retryStatusCodes`. He concludes that the patch looks very good overall.

Within the series, this patch sits between the overflow-safe exponential backoff implementation (patch 2/5, already approved) and the POST retry loop for read-only services (patch 4/5). It establishes the configurable code list that patches 4 and 5 rely on. The series as a whole remains under review, with patches 4/5 and 5/5 still awaiting Junio's integration decision, and his earlier procedural concern about the two-phase introduction of the 10-second default `http.retryAfter` in patch 5 still open.

This is a bugfix for `git fast-import`, submitted as a v2 revision of a single patch by Wonseok Oh. It addresses a silent data corruption case in `builtin/fast-import.c` where an inline file modification (`M <mode> inline <path>`) appearing as the final line of the input stream causes `file_change_m()` to exit its read loop on EOF without ever seeing the required `data` command. The function then stores an uninitialized stack object ID into the tree and exits with status 0, leaving behind a tree entry that references a non-existent blob -- something `git fsck` would later flag as missing.

The fix replaces the `while (read_next_command(state) != EOF)` loop with an infinite `for (;;)` loop that explicitly checks the return value at the top of each iteration and dies with "expected 'data n' command, found end of input" when EOF is reached. This directly addresses Junio C Hamano's objection to v1, which had discarded the return value of `read_next_command()` and could therefore loop forever if the input ended with an unterminated line like `cat-blob <oid>` without a trailing newline. The v2 approach mirrors how `parse_data()` already handles unexpected input by dying immediately rather than silently continuing.

The patch includes two regression tests in `t/t9300-fast-import.sh`: one verifying that a stream ending immediately after an inline `M` command fails with the expected error message and does not create the target ref, and a second covering the unterminated `cat-blob` scenario that broke v1. Both tests confirm that malformed input now produces a fatal error instead of a silently corrupt commit graph.

The contribution looks well-crafted and addresses a genuine robustness gap -- malformed input previously produced a successful exit code while writing broken objects, which is exactly the kind of silent failure that erodes trust in the tool. As of this email the patch remains under review, with the maintainer yet to respond to the v2 approach.

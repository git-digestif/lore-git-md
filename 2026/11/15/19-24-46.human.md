This is a **bugfix refactoring** in the third patch of Johannes Schindelin’s five-patch series hardening Git against integer overflows. The patch targets `wrapper.c`, where `read_in_full()` and `write_in_full()` silently overflow their `ssize_t` accumulators when passed byte counts exceeding `SSIZE_MAX`.

Johannes revises the patch in response to Phillip Wood’s review, which questioned the commit message’s claim that such large counts “never” occur in practice. The new version drops the assumption entirely and instead changes the API to make overflow impossible: `write_in_full()` now returns `0` on success (instead of the caller’s original count), and a new `read_in_full_or_error()` function returns `0` or `-1` for callers who only care about success/failure. Callers that still need the byte count are left to be vetted individually, but the immediate risk of silent overflow is eliminated.

The changes are defensive and low-risk: no on-disk format or CLI behavior is altered, and the new helper function is opt-in. The patch remains uncontroversial in its goal—hardening against undefined behavior—but the revised approach is more conservative and avoids over-promising about caller behavior. Phillip’s platform-compatibility concern (whether `ssize_t` can be narrower than `size_t` on some platforms) is now moot because the patch no longer relies on that assumption. The series’ other patches (1, 2, 4, and 5) are unaffected by this update.

This is the second patch in Tanga Joris’s Outreachy bugfix series, now under final review after incorporating stricter validation for malformed diff headers. The patch addresses a crash in `git apply --check` when processing patches where `---` or `+++` lines appear *before* `new file mode` or `deleted file mode` lines, respectively. This ordering violates Git’s internal assumptions, leading to inconsistent state in the `patch` struct and triggering an assertion failure.

The fix itself is technically sound: it adds explicit validation in `parse_git_diff_header()` to reject patches where a new file has an `old_name` or a deleted file has a `new_name`, with clear error messages. The implementation follows the precedent set by commit `d70e9c5c8c` (2017), which similarly rejected mutually exclusive header lines. Test coverage in `t/t4133-apply-filenames.sh` verifies both the new validation and reverse application (`-R`), ensuring deletions are also caught.

Siddharth Asthana’s review here is surface-level but valuable: he suggests improving the error messages to clarify that the issue stems from the *ordering* of header lines (e.g., "--- before new file mode") rather than printing the stripped `old_name` (e.g., "dev/null"). This would make the messages more actionable for users encountering the issue in the wild. The change is minor and aligns with the series’ goal of providing clear, user-friendly feedback.

The series as a whole is now aligned with Junio C Hamano’s guidance to reject any patch header format not generated by `git diff` or `git format-patch`, including `diff --git` lines in commit message bodies. The only remaining loose end is the memory leak in `parse_git_diff_header()` (identified earlier), but that’s orthogonal to this patch. This fix is ready for final review, likely by Eric Sunshine, to assess error message clarity and backwards-compatibility implications. No further debate is expected.

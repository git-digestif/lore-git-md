This is a discussion response in the ongoing thread about preserving `change-id` headers during commit rewriting operations. Ewout ter Hoeven counters brian m. carlson’s privacy and utility objections by presenting concrete, real-world use cases where `change-id` preservation would solve practical problems in stacked pull/merge request workflows.

The email focuses on two major Git hosting tools—GitHub’s `gh-stack` and GitLab’s experimental `glab stack`—both of which struggle to maintain commit identity across rewrites. Without a persistent identifier like `change-id`, these tools rely on heuristics (branch names, patch IDs, recorded bases) that fail in common scenarios: branch renames break tracking, rewritten commits trigger redundant replays, and patch ID mismatches cause cascading errors. Ewout cites specific GitHub and GitLab issues where users report dozens of incorrectly replayed commits due to these limitations. The implication is that `change-id` preservation would eliminate these workarounds, allowing Git itself to serve as the authoritative source of commit identity.

This response directly addresses brian m. carlson’s earlier skepticism about the value of `change-id` by grounding the argument in observable pain points rather than theoretical benefits. It shifts the discussion from abstract privacy concerns to tangible workflow improvements, though it does not engage with the security objections (e.g., metadata leakage) raised in the parent email. The examples provided—particularly the 61-commit replay incident—offer a clear technical rationale for why external tools need a reliable, Git-native way to track rewritten commits. Whether this will outweigh the privacy concerns remains an open question for the thread.

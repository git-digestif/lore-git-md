This is a **bugfix** for the `pretty` subsystem, specifically addressing color handling in custom log formats.

The patch fixes two related problems with ANSI color escape sequences in `git log --format=...` output. First, colors that span line breaks are lost when tools like `--graph` or color-aware pagers (e.g., `less -R`) reset colors at line boundaries. For example, a bold-wrapped subject line would only appear bold on its first line. Second, active colors at the end of a line can "leak" into subsequent content, such as graph markers or unrelated lines when grepping colored output.

The solution modifies `repo_format_commit_message()` to post-process the formatted output when colors are enabled. It scans for ANSI escape sequences, tracks active colors since the last reset, and ensures each line is self-contained: inserting a reset before line breaks and replaying the active colors at the start of the next non-empty line (unless it begins with a reset). A final reset is appended if colors remain active at the end. The implementation avoids buffer copies unless necessary and uses efficient string scanning (`memchr`, `strcspn`).

The patch includes thorough test coverage in `t/t4205-log-pretty-formats.sh`, verifying behavior with line breaks, wrapped lines, empty lines, manual escape sequences, and `--graph` integration. The commit message clearly explains the motivation, edge cases, and trade-offs (e.g., formats relying on line-break resets will now need explicit resets).

This is a well-scoped, well-explained fix for a real usability issue. The code is clean, the tests are comprehensive, and the approach aligns with how default formats already handle colors. No controversy is evident.

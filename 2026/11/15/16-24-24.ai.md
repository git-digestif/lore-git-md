This is a security-focused reply in the ongoing `change-id` preservation thread. Brian m. carlson pushes back against Ewout ter Hoeven’s workflow-based argument by highlighting a critical trust issue: **change-id headers cannot be relied upon as stable identifiers because users can manually edit them**. This creates a fundamental security risk for automated review systems (e.g., GitHub/GitLab stacked PRs) that might assume a preserved `change-id` implies an unchanged patch. A malicious actor could exploit this by reusing a reviewed `change-id` for an entirely different commit, tricking the server into accepting unvetted code.

The response zeroes in on the **server-side rebase requirement** as the only way to guarantee integrity—only if the *server* rewrites commits (and thus controls the `change-id`) can it trust the header’s immutability. This directly contradicts the earlier proposal’s assumption that client-side rewrites (via hooks or policies) could safely preserve `change-id`s. Brian’s objection reframes the problem from a workflow convenience issue to a **security boundary question**: any solution must either (1) restrict `change-id` preservation to server-controlled operations, or (2) accept that the header cannot be trusted for security-sensitive decisions.

This reply does not engage with the technical feasibility of Nico Williams’ hook/policy framework or Ewout’s real-world examples. Instead, it introduces a **hard constraint**—server-side control—that any viable solution must address. The implication is that client-side `change-id` preservation (as currently proposed) is inherently flawed for automated review workflows, regardless of its utility for other use cases. The thread’s tension now centers on whether this security requirement can coexist with the workflow needs, or if the two are fundamentally incompatible.

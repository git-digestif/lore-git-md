This is a discussion response in the ongoing thread about preserving `change-id` headers during commit rewriting operations like rebase and cherry-pick. Ewout ter Hoeven counters brian m. carlson’s privacy and utility objections with concrete, real-world examples from GitHub’s and GitLab’s stacked pull/merge request tools.

The email focuses on a specific pain point: stacked changes that break when commits are rewritten because the tools lack a stable identity for each change. Ewout describes three failure modes in GitHub’s `gh-stack` and GitLab’s experimental `glab stack`—branch renames, patch-ID mismatches after rewrites, and replayed commits—and notes that both teams are considering change IDs as a solution. The argument is that Git’s current behavior forces these tools to invent their own metadata, which Git then silently discards, creating a mismatch between the tool’s view and Git’s history.

This response strengthens the case for preserving `change-id` by grounding it in observable workflow failures rather than hypotheticals. It does not engage with the privacy concerns brian raised, so those objections remain open. The examples are detailed enough to help a reader assess whether the problem is widespread or niche, but the email itself is narrowly scoped to the stacked-change use case.

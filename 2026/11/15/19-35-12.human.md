This is a reply in the ongoing thread about hardening Git against integer overflows in `approxidate_alpha()`. Johannes Schindelin responds to Phillip Wood’s substantive review of patch 5/5, which proposed hardening the relative-time multiplication in `date.c`.

Johannes acknowledges Phillip’s feedback and abandons the original approach—dropping the GCC-only `mult_overflows()` macro entirely. Instead, he adopts a simpler, more portable solution: rejecting any user-supplied number that exceeds `INT_MAX` upfront. This sidesteps the compiler and `time_t` representation issues Phillip raised while still preventing overflow. The change is minimal and focused: the hardening is now implemented as a single range check (`if (number > INT_MAX) return NULL`) in `approxidate_digit()`, with no new macros or platform-specific logic.

The reply resolves the technical concerns Phillip identified—portability across compilers and `time_t` signedness—but leaves the hardening narrower than originally intended. The original patch would have caught overflows in the multiplication itself; the new version only rejects numbers that are too large to fit in an `int`, which is sufficient to prevent overflow but does not address every edge case Phillip’s `intmax_t` proposal would have covered. The trade-off is simplicity and portability over completeness.

This email effectively withdraws the original patch 5/5 and replaces it with a much smaller change. The series’ overall goal—hardening against integer overflows—remains intact, but the date.c hardening is now less ambitious.

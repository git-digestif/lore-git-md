# Thread deltas

## 2026/08/14

- [2026/08/14/10-40-30 by Peter Morris <mrpmorris@gmail.com>] Peter Morris proposed that `git worktree add` use filesystem copy-on-write/block cloning (e.g., ReFS block cloning on Windows Dev Drives) where supported, to reduce SSD writes, physical disk usage, and creation time for large repositories — particularly with AI agents running multiple worktrees concurrently — while leaving normal behavior unchanged on filesystems without support.
- [2026/08/14/10-54-02 by Kristoffer Haugsbakk <kristofferhaugsbakk@fastmail.com>] Kristoffer Haugsbakk pointed the thread to an existing pull request (pull.2317) on the topic.
- [2026/08/14/13-29-26 by Peter Morris <mrpmorris@gmail.com>] Peter Morris noted that the PR covers only Linux and macOS, and argued that on Windows the CopyFile API would use ReFS block cloning automatically when source and destination are on the same ReFS volume, so using CopyFile would provide this "for free" on Windows Dev Drives.
- [2026/08/14/16-29-24 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano analyzed the proposal: he agreed that dirty working-tree files and same-branch checkouts cannot simply be CoW-copied wholesale but are surmountable if unique contents are written out; explained that `checkout_entry()` has no visibility into what other worktrees have checked out; sketched an approach of mapping clean blob checkouts across linked worktrees and intercepting `checkout_entry()` to CoW instead of writing, with a post-copy hash to guard against TOCTOU races; noted this would affect everything going through `checkout_entry()`, not just `git worktree add`; and stated he is not interested in making such a change himself, mostly because of the TOCTOU issue.

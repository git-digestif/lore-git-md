This thread is about a bugfix for the `contrib/credential/libsecret` credential helper, which currently crashes and silently loses stored passwords due to a race condition in how it interacts with the GNOME keyring backend. The issue occurs when the `SECRET_SEARCH_LOAD_SECRETS` flag is used with `secret_service_search_sync()`: this flag silently discards failures (e.g., locked or concurrently deleted items), leaving secrets as NULL, which triggers assertion failures in subsequent calls. Daniel Martí posted a v1 patch two weeks ago, and after feedback from Junio C Hamano, has now sent a v2 that refines the commit message and implementation to make the rationale clearer.

The v2 patch removes the problematic flag and instead explicitly loads the secret for each matched item using `secret_item_load_secret_sync()`. This ensures errors are properly reported rather than silently discarded, preventing crashes and data loss. The change maintains the same number of D-Bus round-trips as before while eliminating the race condition. The updated commit message explains why the flag is problematic—it skips locked items and ignores load failures—and confirms that libsecret’s behavior is intentional, meaning Git must handle NULL secrets regardless. The patch is minimal, touching only the affected file, and is now self-contained, addressing Junio’s request for clarity.

The main unresolved question is a design trade-off: whether to retain the `SECRET_SEARCH_LOAD_SECRETS` flag for its perceived optimization benefits (Junio’s preference) or drop it entirely (Martí’s approach). The v2 strengthens the case for the latter by aligning with libsecret’s own `secret-tool` utility and ensuring all errors are surfaced. The patch is ready for further review, with no test coverage included due to the difficulty of reproducing the race condition. The discussion has confirmed that the issue is well-motivated and that the fix is necessary.

This thread is about a bugfix for the `contrib/credential/libsecret` credential helper, which currently crashes and silently loses stored passwords when libsecret encounters locked or concurrently deleted items. Daniel Martí posted a v2 patch on November 2nd that removes the problematic `SECRET_SEARCH_LOAD_SECRETS` flag and replaces it with explicit error handling, addressing feedback from Junio C Hamano on commit message clarity and design rationale.

The patch is stalled due to lack of review, and Junio has warned it may be dropped from his `seen` branch if no further feedback arrives. The core design question remains whether to retain the flag for perceived optimization benefits (Junio’s preference) or drop it entirely (Martí’s approach). Martí argues the flag isn’t a true optimization and silently discards errors, while Junio prioritizes preserving the batch-fetch path for the common case.

Phillip Wood’s recent substantive review engages deeply with the patch’s error handling and API usage. He questions whether locked items are truly omitted from search results, critiques the use of `g_critical()` for runtime errors, and suggests restructuring the code to avoid redundant cleanup paths. He also proposes treating concurrently erased credentials as missing rather than erroneous, and removing the `SECRET_SEARCH_UNLOCK` flag entirely if D-Bus efficiency is a concern. While Phillip doesn’t challenge the patch’s core premise, his feedback is substantial enough that another iteration may be needed before the fix can move forward.

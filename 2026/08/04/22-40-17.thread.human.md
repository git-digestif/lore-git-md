This thread is about a bugfix for the `contrib/credential/libsecret` credential helper, which currently crashes and silently loses data when credential items are locked or deleted concurrently. Daniel Martí posted a patch two weeks ago that replaces the problematic `SECRET_SEARCH_LOAD_SECRETS` flag with an explicit `secret_item_load_secret_sync()` call to prevent NULL secret values from causing assertion failures.

The discussion centers on a design trade-off: Daniel’s approach eliminates the two-step process that silently discards errors, replacing it with a single SearchItems call plus one explicit GetSecret, ensuring all errors are surfaced while maintaining the same round-trip count in the common case. Junio C Hamano has proposed an alternative that retains the flag and conditionally loads secrets only when necessary, prioritizing the batch-fetch optimization for the common case. Daniel has defended his design, arguing that the flag isn’t a true optimization and that his approach unifies the code path, making failures consistently visible. No technical objections to correctness have been raised, but consensus on the design hasn’t been reached yet.

The patch is still under review, with no test coverage due to the race condition’s reproducibility challenges. The next step is likely a v2 or further discussion, but the thread has been quiet for two weeks until Daniel’s recent nudge. The fix is confined to `contrib/credential/libsecret/git-credential-libsecret.c` and doesn’t introduce new CLI options or on-disk format changes.

- [2026/08/22/20-47-12 by Daniel Martí <mvdan@mvdan.cc>] He agreed that the race condition requires a concurrently-racing process or a locked keyring to trigger and that he does not see a way to test it reliably.

## 2026/09/27

- [2026/09/27/22-45-03 by Daniel Martí <mvdan@mvdan.cc>] Daniel Martí replied that the truncated libsecret documentation for `SECRET_SEARCH_LOAD_SECRETS` is a docs bug for which he has sent a fix (GNOME/libsecret MR 182), but the behavior itself is intentional: the search does not load secrets of locked items and does not fail on load errors, `secret_item_get_secret()` is documented to return NULL for a locked or unloaded item, and gnome-keyring's `GetSecrets` deliberately skips locked or deleted items while `GetSecret` on a single item returns an error; git therefore needs to handle a NULL secret with every libsecret release, and libsecret's own secret-tool loads each secret explicitly after searching. He said he would send a v2 with a reworded commit message shortly.
- [2026/09/27/22-46-21 by Daniel Martí via GitGitGadget <gitgitgadget@gmail.com>] Daniel Martí posted [PATCH v2] credential/libsecret: load secrets explicitly, rewording the commit message to explain that `SECRET_SEARCH_LOAD_SECRETS` is implemented as a separate `GetSecrets` D-Bus call after `SearchItems`, so the patch drops the flag and always loads the one secret used via `secret_item_load_secret_sync()`, which reports errors, keeping the same number of D-Bus calls and a single code path; an inaccessible item now produces a useful error message instead of assertion failures, with git still falling back to prompting.

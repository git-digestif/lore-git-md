Thread identity: patch series (single patch), originating author Daniel Martí, subject "bugfix for contrib/credential/libsecret: avoid crash and silent data loss".

Core problem or goal: fix a crash and silent data loss in the `contrib/credential/libsecret` credential helper caused by the use of the `SECRET_SEARCH_LOAD_SECRETS` flag with `secret_service_search_sync()`. This flag silently discards failures (e.g., locked or concurrently deleted items), leading to NULL secret values. Subsequent calls to `secret_value_get_text()` or `secret_value_unref()` trigger assertion failures, causing the password to be lost even if it was retrievable. The discussion confirms that this behavior is intentional in libsecret, meaning Git must handle NULL secrets regardless of libsecret’s version.

Current status: patch v2 posted on 2024-11-02, addressing Junio C Hamano’s feedback on commit message clarity and implementation rationale. The patch is self-contained, with a clear explanation of the design trade-off: prioritizing simplicity and reliability (Martí’s approach) over preserving the batch-fetch optimization (Junio’s alternative). The procedural path forward remains stalled due to lack of review; Junio has warned the topic may be dropped from his `seen` branch if no reviewers step up in the coming weeks. Phillip Wood’s substantive review of v2 raises significant technical concerns about error handling, API usage, and the treatment of erased credentials, suggesting another iteration (v3) is likely needed. The unresolved design questions now include whether to retain the `SECRET_SEARCH_UNLOCK` flag, how to distinguish between different types of unlock failures, and whether concurrently erased credentials should be treated as errors or missing credentials.

Key technical details:
- File: `contrib/credential/libsecret/git-credential-libsecret.c`
- Changed symbols: removes `SECRET_SEARCH_LOAD_SECRETS` flag and replaces it with an explicit `secret_item_load_secret_sync()` call for each matched item. This ensures all errors (e.g., locked or concurrently deleted items) are reported rather than silently discarded.
- Behavior change: prevents silent data loss and assertion crashes by properly surfacing errors for inaccessible items. The patch replaces the two-step (SearchItems + GetSecrets) process with a single SearchItems call plus one explicit GetSecret per item, maintaining the same round-trip count in the common case while ensuring all errors are surfaced. Genuinely inaccessible items now produce a useful error message, while Git can still fall back to password prompting.
- Error handling refinements: Phillip Wood critiques the use of `g_critical()` for runtime errors (recommending `g_printerr()` instead) and suggests restructuring the code to avoid redundant cleanup paths. He also questions whether `secret_item_get_secret()` can still fail after the patch and whether the GNOME keyring daemon omits locked items from search results.
- No new CLI options, config keys, or on-disk format changes.
- No test coverage included; the problem is reproducible with concurrent credential operations or a locked keyring, but such conditions are difficult to test reliably.

Open questions and loose ends:
- Design trade-off: whether to retain the `SECRET_SEARCH_LOAD_SECRETS` flag for its perceived optimization benefits (Junio’s preference) or drop it entirely (Martí’s approach). Martí argues the flag is not a true optimization (it performs two round trips: SearchItems + GetSecrets) and silently discards errors, including client-side skipped items. His approach replaces this with a single SearchItems call plus one explicit GetSecret per item, keeping the round-trip count identical in the common case while ensuring all errors are surfaced. Junio prioritizes preserving the batch-fetch path for the common case, arguing the race condition is rare.
- Error handling: how to distinguish between different types of unlock failures (e.g., locked vs. erased items) and whether `secret_item_load_secret_sync()` provides sufficient context. Phillip Wood suggests removing the `SECRET_SEARCH_UNLOCK` flag entirely if D-Bus call efficiency is a concern, replacing it with an explicit check for locked items via `secret_item_get_locked()`.
- Treatment of erased credentials: whether a concurrently erased credential should be treated as an error (current patch behavior) or as a missing credential (Phillip’s preference), which would align with Git’s existing behavior for missing credentials.
- API usage: whether the patch’s alignment with `secret-tool` is meaningful, given that `secret-tool` uses a different API.
- Procedural risk: the topic may still be abandoned if no further review materializes or if the feedback from Phillip Wood is not addressed promptly.

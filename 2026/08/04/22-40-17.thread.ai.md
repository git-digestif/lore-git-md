Thread identity: patch series (single patch), originating author Daniel Martí, subject "bugfix for contrib/credential/libsecret: avoid crash and silent data loss".

Core problem or goal: fix a crash and silent data loss in the `contrib/credential/libsecret` credential helper. The current implementation uses the `SECRET_SEARCH_LOAD_SECRETS` flag with `secret_service_search_sync()`, which silently discards failures (e.g., locked or concurrently deleted items), leading to NULL secret values. Subsequent calls to `secret_value_get_text()` or `secret_value_unref()` trigger assertion failures, causing the password to be lost even if it was retrievable. The discussion now also questions whether this behavior is a bug in libsecret itself or an undocumented but intended consequence of the flag.

Current status: patch v1 posted two weeks ago, under active review. Junio C Hamano has provided a substantive review proposing an alternative implementation, while Daniel Martí has defended his original design. M Hickford’s recent email raises a substantive question about whether the issue lies in libsecret’s implementation or documentation, introducing a new dimension to the discussion. The procedural path forward remains a v2 patch from Daniel, but resolution may now depend on upstream clarification from libsecret maintainers. No consensus has been reached on the design trade-off or the upstream status of the issue.

Key technical details:
- File: `contrib/credential/libsecret/git-credential-libsecret.c`
- Changed symbols: replaces `SECRET_SEARCH_LOAD_SECRETS` flag with explicit `secret_item_load_secret_sync()` call (v1 approach). Junio’s alternative suggests retaining the flag and conditionally calling `secret_item_load_secret_sync()` only if `secret_item_get_secret()` returns NULL.
- Behavior change: prevents silent data loss and assertion crashes by properly reporting errors for inaccessible items. Daniel’s approach eliminates the two-step (SearchItems + GetSecrets) process that silently discards errors, replacing it with a single SearchItems call plus one explicit GetSecret for the relevant item. Junio’s alternative would add a third round trip in rare cases (when `secret_item_get_secret()` returns NULL) and leave the error-prone path untested.
- No new CLI options, config keys, or on-disk format changes.
- No test coverage included; problem is reproducible with concurrent credential operations and occurs several times per week for the author.

Open questions and loose ends:
- Whether to drop the `SECRET_SEARCH_LOAD_SECRETS` flag entirely (Daniel’s preferred approach) or retain it and conditionally load secrets (Junio’s alternative). The discussion centers on design philosophy: optimization (preserving the batch-fetch path for the common case) vs. simplicity and reliability (eliminating silent failures). Daniel argues that `SECRET_SEARCH_LOAD_SECRETS` is not a true optimization (it performs two round trips: SearchItems + GetSecrets) and silently discards errors, including client-side skipped items. His approach replaces this with a single SearchItems call plus one explicit GetSecret, keeping the round-trip count identical in the common case while ensuring all errors are surfaced.
- Clarity of the commit message and code: Junio requests that the v2 patch be self-contained, with a commit message and implementation that clearly explain the rationale and design choices without requiring reviewers to reference prior discussion. This remains a blocker for further review.
- Upstream status of `SECRET_SEARCH_LOAD_SECRETS`: M Hickford’s email questions whether the flag’s silent discarding of failures is intended behavior or an upstream bug in libsecret. This could change the direction of the fix—if the behavior is intentional, the patch may need to preserve the flag while handling NULL secrets gracefully; if it is a bug, Daniel’s approach is more likely to be accepted.

# Thread deltas

## 2026/08/26

- [2026/08/26/23-31-50 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano posted a 2-patch series introducing `die_for_incompatible_opts()` to handle an unbounded number of mutually incompatible options, with the first patch swapping argument order in existing `die_for_incompatible_optN()` functions and the second introducing the new varargs API.
- [2026/08/26/23-31-51 by Junio C Hamano <gitster@pobox.com>] Patch 1/2 swaps the parameter order of `die_for_incompatible_optN()` from `(int set, const char *name)` to `(const char *name, int set)` across all implementations and callers, because an integer first parameter is an inconvenient sentinel for varargs.
- [2026/08/26/23-31-52 by Junio C Hamano <gitster@pobox.com>] Patch 2/2 introduces `die_for_incompatible_opts()` taking an arbitrary number of `(const char *name, int set)` pairs terminated by a NULL sentinel, reimplements `die_for_incompatible_opt4()` and the other optN functions in terms of it, and deliberately reports only the first four mutually incompatible options to avoid allocation costs.

## 2026/08/27

- [2026/08/27/01-19-22 by Elijah Newren <newren@gmail.com>] Elijah Newren flagged that the proposed `die_for_incompatible_opts()` implementation calls `va_start()` without a matching `va_end()`.
- [2026/08/27/04-55-15 by Jeff King <peff@peff.net>] Jeff King explained his understanding of the design: the cap of 4 applies to options the user actually specified, not the total conflicting set (capping at 2 would be technically correct but could annoy users iteratively), and asked whether any callers actually want to pass more than 4 options, noting he saw no patches adding new calls.
- [2026/08/27/04-55-15 by Jeff King <peff@peff.net>] Jeff King warned that the varargs form lets a caller forget the NULL terminator and cause a runtime problem, suggesting `LAST_ARG_MUST_BE_NULL` in the header.
- [2026/08/27/04-55-15 by Jeff King <peff@peff.net>] Jeff King observed that while `ARRAY_SIZE()` allows bumping the cap later, the `switch (count)` still hard-codes the count values, and allocating a buffer for the message would push translators into "lego-land".
- [2026/08/27/04-55-15 by Jeff King <peff@peff.net>] Jeff King suggested the opt2/opt3 inline variants could be cleaned up by calling the arbitrary-sized version directly rather than passing dummy `0`/`""` values.
- [2026/08/27/14-22-38 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano acknowledged Elijah Newren's catch ("Good eyes. Thanks.").
- [2026/08/27/14-35-38 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano confirmed no callers currently pass more than 4 options (while writing an earlier message he had wondered whether two adjacent opt3/opt4 calls should be combined into opt7), agreed with keeping the static inlines for the common cases because the non-varargs forms give compiler checking, and said he can do without [1/2].
- [2026/08/27/14-35-38 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano specified the intended interface: `die_for_incompatible_optN()` (2 <= N <= 4) keeps accepting N pairs of `<int, const char *>`, while `die_for_incompatible_opts()` takes pairs of `<int, const char *>` expecting 0 (not set), 1 (set), or EOF==-1 as sentinel, with the static inline opt2/opt3/opt4 emulations calling it with `!!optN` and `EOF`.
- [2026/08/27/14-35-38 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano explained why he rejected switching to dynamic allocation to report all conflicting options: it would forgo the existing message templates and hurt i18n/l10n.
- [2026/08/27/17-28-32 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano posted `[PATCH v2] die_for_incompatible_opts(): unbounded number of options`, introducing `die_for_incompatible_opts()` to handle an arbitrary number of mutually exclusive options and rewriting the existing opt2/opt3/opt4 variants on top of it; the v2 signature takes N pairs of `<bool optN, const char *nameN>` followed by EOF, uses `va_arg(ap, int)` to distinguish bool from the EOF sentinel, and adds the previously missing `va_end(ap)`.

## 2026/08/29

- [2026/08/29/11-14-18 by Jeff King <peff@peff.net>] Jeff King said he wonders whether the work is approaching churn but has no strong feeling, and argued that the varargs interface is less safe because there is no integer equivalent to LAST_ARG_MUST_BE_NULL, making it strictly worse since no case with more than 4 items is actually helped; if the varargs version is not exposed and callers use the counted wrappers the risk is smaller, but then he wonders what the value of the patch is. He also agreed with Junio C Hamano's earlier explanation that switching to dynamic allocation after option[] is filled was rejected primarily because the existing message templates could not be reused, hurting i18n/l10n.
- [2026/08/29/11-15-49 by Jeff King <peff@peff.net>] Jeff King said he is mildly negative on the v2 varargs signature `die_for_incompatible_opts(bool opt1, const char *opt1_name, ...)` because the compiler cannot verify an EOF sentinel is present, and stated that keeping patch 1 and using LAST_ARG_MUST_BE_NULL would be preferable.
- [2026/08/29/17-51-28 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano posed a quiz on expressing an arbitrary N > 4 check with only die_for_incompatible_opt[234](), showing a die_for_incompatible_opt5() built from opt4/opt2 calls, and conceded Jeff King's point that there is no integer equivalent to LAST_ARG_MUST_BE_NULL, agreeing it makes sense to flip the <set, name> pairs to <name, set> order, which he suspects was not chosen originally because varargs support was not anticipated.
- [2026/08/29/18-04-21 by René Scharfe <l.s.r@web.de>] René Scharfe proposed keeping LAST_ARG_MUST_BE_NULL by requiring both EOF and NULL, hidden behind a `die_for_incompatible_opts(...)` macro that appends `EOF, NULL`, while noting it only type-checks the first two arguments and that error-handling code is tested less; he also offered a type-safe alternative using a `struct used_option { const char *name; bool used; }` compound-literal array terminated by `{ NULL }` via a DIE_FOR_INCOMPATIBLE_OPTS macro.

Subject: [PATCH] read-cache: avoid index expansion in repo_index_has_changes() on unborn HEAD
Series version: standalone patch (v2 posted)
Originating author: Sahitya Chandra
Thread type: bug fix / code hygiene (performance regression avoidance in sparse-checkout/sparse-index)

Core problem or goal
When `repo_index_has_changes()` is called without an explicit tree and HEAD is unborn (e.g., on a newly created orphan branch), the function falls back to walking the index directly, which forces a full expansion of any sparse directory entries. This expansion is unnecessary because an unborn HEAD is logically equivalent to the empty tree, so every index entry is new. The patch replaces the fallback with a comparison against the empty tree, keeping the unborn-branch case on the same diff code path as normal tree comparisons and avoiding the expansion. The patch is framed as a code hygiene improvement: it removes a TODO, unifies the code path, eliminates an `ensure_full_index()` call that future readers would otherwise need to reason about, and reduces the code footprint by 28 lines. Sahitya Chandra explicitly acknowledges no realistic use case exists where a user with an unborn HEAD would simultaneously be using a sparse index containing millions of uncommitted files, but argues the patch still has value for maintainability.

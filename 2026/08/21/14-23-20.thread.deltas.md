# Thread deltas

## 2026/08/21

- [2026/08/21/14-23-20 by Alexey Samsonov via GitGitGadget <gitgitgadget@gmail.com>] Alexey Samsonov posted a 3-patch series (pr-2209) to migrate the Git codebase from legacy utime()/utime.h to utimensat(), citing that utime() was removed in POSIX.1-2024 and is absent from LLVM-libc, with utimes() as a fallback and a MinGW wrapper, intending no behavior changes except nanosecond-precision timestamps.
- [2026/08/21/14-23-21 by Alexey Samsonov via GitGitGadget <gitgitgadget@gmail.com>] Patch 1/3 introduces a utimensat(2) compatibility wrapper: fallback definitions for AT_FDCWD, UTIME_NOW, and UTIME_OMIT; a new ST_ATIME_NSEC macro; git_utimensat() implemented via utimes(2) for NO_UTIMENSAT platforms; mingw_utimensat() converting struct timespec to Windows FILETIME; and build-system wiring in Makefile, meson, CMake, and configure.ac.
- [2026/08/21/14-23-22 by Alexey Samsonov via GitGitGadget <gitgitgadget@gmail.com>] Patch 2/3 migrates all utime(3p) call sites to utimensat(2) across commit-graph.c (using UTIME_OMIT to bump mtime without an extra stat), copy.c (preserving sub-second atime/mtime), odb/source-packed.c, odb/source-loose.c, object-file.c, builtin/pack-objects.c, rerere.c, and t/helper/test-chmtime.c.
- [2026/08/21/14-23-23 by Alexey Samsonov via GitGitGadget <gitgitgadget@gmail.com>] Patch 3/3 removes the legacy <utime.h> include from compat/posix.h and test fixtures, deletes mingw_utime() from compat/mingw.c, and removes the compat/vcbuild/include/utime.h shims.
- [2026/08/21/17-33-35 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano noted that Apple has supported utimensat since macOS 10.13 High Sierra (released 2017, EOL 2020), so the migration is safe on Apple platforms as well.

## 2026/08/22

- [2026/08/22/16-03-35 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson declined to review the utime.h-to-utimensat series because the cover letter disclosed it was generated by Gemini Flash from Antigravity, which he argued cannot satisfy the Developer's Certificate of Origin requirement in SubmittingPatches that contributors certify they know the origin of their contributions and have the right to submit them; he also noted he had not read the series to avoid being influenced by code the project cannot include, and separately recalled that the *at functions cannot be used due to Windows lacking proper semantics.
- [2026/08/22/17-59-09 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano endorsed brian m. carlson's stance as prudent, explaining that Alexey Samsonov's DCO cannot be treated as valid because, as a copy editor of Antigravity/Gemini output, he cannot know where the code was copied from, and that if DCO-covered work later proves legally unusable the project itself bears the cost of ripping it out; he also raised a concern that there may be little difference between rejecting a contributor for disclosing AI use and rejecting an unknown contributor for lack of trust.
- [2026/08/22/21-15-35 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson affirmed that view, adding that LLMs can regurgitate code substantially similar to training inputs, that the legal status of LLM output is unclear amid active litigation, and that many jurisdictions (e.g. Canada's Copyright Act) distinguish knowingly from unknowingly infringing, so knowingly distributing suspect code creates more legal exposure even though the project still faces fallout and project-management costs; he distinguished honest disclosure of AI use, which he said is good-faith participation and could still allow future non-AI patches, from misleading the project about a patch's provenance, which he said is dishonest and would make the contributor unwelcome, while acknowledging negative consequences from distributing the code remain possible and the community must trust most people are honest.

Subject: [PATCH 0/2] submodule: fix crash and error handling in branch --recurse-submodules with non-ref start point
Series version: v1 (initial submission)
Originating author: Volodymyr Vriukalo
Thread type: bugfix patch series

Core problem or goal
Fix a crash (BUG) and incorrect error handling in the experimental `submodule.propagateBranches` feature when `git branch --recurse-submodules` is invoked with a start point that is not a ref name (e.g., a raw object ID). The bug manifests in two scenarios: (1) in repositories without submodules, Git aborts with a BUG after moving the branch, leaving the operation partially completed but reporting failure; (2) in repositories with submodules, the command fails earlier due to a truncated argument list passed to a helper. The root cause is a missing tracking name when the start point is not a ref, which is now addressed in both code paths.

Current status
Under review; no prior versions. The series consists of two patches:
1. Prevents tracking a start point that has no ref by adding a guard in `create_branches_recursively()` to match the existing logic in `create_branch()`. This patch includes a new test in `t/t3207-branch-submodule.sh` to verify the crash is resolved.
2. Allows recursion to proceed even when there is no tracking name by making the tracking name argument optional in the `submodule--helper create-branch` command. The fix modifies `submodule_create_branch()` to push the tracking name separately (avoiding `strvec_pushl()` truncation at NULL) and updates the helper's argument parsing to accept two or three arguments. A new test in `t/t3207-branch-submodule.sh` verifies the fix for the submodule case.
Junio C Hamano has queued the series as `vv/branch-recurse-no-start-ref` in `seen` but has signaled intent to drop it from integration branches in the coming weeks unless reviewers step up. No maintainer intent regarding graduation to `next` or `master` has been expressed.

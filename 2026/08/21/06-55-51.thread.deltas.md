# Thread deltas

## 2026/08/21

- [2026/08/21/06-55-51 by Elijah Newren via GitGitGadget <gitgitgadget@gmail.com>] Elijah Newren submitted a patch to send-pack that adds reachable shallow grafts as negative pack tips to avoid sending the entire toplevel tree when pushing from a shallow clone, controlled by a new `push.shallowExcludeBoundary` config (default true) with an opt-out for `receive.shallowUpdate` receivers.
- [2026/08/21/13-17-32 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt reviewed the patch, questioning whether locally amending a shallow graft could send insufficient information to the server, whether tree-level negotiation could verify the grafted tree matches the remote, whether tests cover modified grafted commits, and whether defaulting `push.negotiate` to enabled has downsides; he also suggested marking input parameters `const`, combining the two ref loops, and considering higher-level reachability interfaces.
- [2026/08/21/17-36-04 by Elijah Newren <newren@gmail.com>] Elijah Newren replied that `--depth=2` does not enable negotiation (only `push.negotiate` does, at any depth), that amending a shallow graft creates a new root commit rather than corrupting the repo (a separate foot-gun he will address in another series), that tree negotiation would arrive too late without `push.negotiate` and that `push.negotiate` is more thorough, that the only downside of defaulting `push.negotiate` is added round-trip latency, and agreed to mark parameters `const` and combine the loops; he explained the manual walk is required to stop at peer-known commits and detect graft boundaries.
- [2026/08/21/18-21-50 by Elijah Newren <newren@gmail.com>] Elijah Newren added that `--depth=2` can be guaranteed by certain forge workflows where merge-request refs are advertised and preserved, but GitHub's `receive.hiderefs` for `refs/pull/`, branch deletion on merge, and heavy squash-merge use in large repositories prevent this from helping those cases.

## 2026/08/24

- [2026/08/24/05-30-13 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt concurred that the proper fix is to enable `push.negotiate` by default rather than adding new logic in send-pack, acknowledging the added round-trip latency but noting it dramatically helps the common shallow-clone scenario.
- [2026/08/24/05-30-13 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt proposed introducing a new `push.negotiate=shallow` option that would enable negotiation automatically for shallow clones and make it the default, thereby avoiding the latency cost in full clones.

- [2026/08/25/05-00-18 by Elijah Newren <newren@gmail.com>] Elijah Newren said he plans to split the additional shallow-related work into two series: a single patch for rebase/revert/am and roughly five patches for shallow graft handling across various commands.
- [2026/08/25/05-00-18 by Elijah Newren <newren@gmail.com>] Elijah Newren said he likes making `push.negotiate` default on for large repos generally, but since negotiation does not solve all cases even when it works, this patch or something like it is still needed.
- [2026/08/25/19-06-16 by Elijah Newren via GitGitGadget <gitgitgadget@gmail.com>] Elijah Newren posted [PATCH v2] send-pack: avoid sending the whole tree when pushing from a shallow clone, fixing two code style issues, updating the cover letter to note `push.negotiate` limitations, and rebasing onto `ps/odb-pluggable-pack-generation`; the patch adds `push.shallowExcludeBoundary` (default true) to exclude reachable shallow grafts from the pack, updates t5538 tests for the `receive.shallowUpdate` path, and adds tests for the default optimization, the opt-out, over-exclusion safety for accepted refs, and rejection of rootless snapshots by shallowUpdate receivers.

## 2026/09/02

- [2026/09/02/18-23-55 by Derrick Stolee <stolee@gmail.com>] Derrick Stolee reported that an AI-agent review of the v2 patch found a flaw: in a multi-ref push, a shallow update attempted alongside another non-shallow branch can cause novel failures, because `append_reachable_shallow_grafts` treats shallow grafts as reachable from the refs being pushed rather than verifying they are reachable from the remote's advertised refs. He supplied a new t5538 test ("shallow push does not over-exclude via a remotely rejected ref") that passes before the patch but fails after it, showing a non-atomic push can accept a second ref update while the packfile is incomplete. He noted that an alternative of enabling `push.negotiate` when the local repo is shallow (via `push.shallowExcludeBoundary`) passes his new test and all of the patch's other new tests except the `receive.shallowUpdate` receiver test, and said he is unsure whether a new option is needed or `push.negotiate` should simply be recommended in more places.
- [2026/09/02/19-05-50 by Derrick Stolee <stolee@gmail.com>] Derrick Stolee corrected his earlier dismissal of the `push.negotiate` discussion, agreeing that the cases where the shallow graft is not common are somewhat common — e.g., a shallow clone of a base repo pushed to a user fork that does not advertise reachability to the shallow commit. He argued the patch's approach assumes non-advertised objects may exist on the server due to delayed garbage collection or shared object databases across a fork network, which he does not consider reasonable default assumptions, so the reason for the setting needs to be clear and users need a quick or automatic way to respond (e.g., retry without the setting). He added that the multi-ref push case is tricky and possibly narrow with HTTP servers protected, but corruption over file:// should be avoided.
- [2026/09/02/20-57-00 by Elijah Newren <newren@gmail.com>] Elijah Newren countered that case (d) — `push.negotiate=true` not working for some users/servers — may be more common than the other cases, and added a further failure mode under both http and ssh: a concurrent server repack can make upload-pack's QUICK "have" check lose the race, so the client believes it must send everything it has, defeating `push.negotiate=true`; he argued a backstop is still needed. He agreed the fork example is a better way to state case (b), and rebutted the "unreasonable assumption" objection with a matrix showing that assuming the server has the shallow graft yields fast success or fast failure in the common cases, while not assuming it means pushing hundreds of megabytes of unnecessary data. He also stated the multi-ref case is not a corruption risk because receive-pack checks connectivity regardless of protocol (citing commit 52fed6e1ce07), so it merely fails more refs than necessary, and described an additional pathological case where a `--depth N --filter=blob:none --sparse` shallow clone downloads all blobs from origin and then uploads them back to the same server, which his patch avoids.

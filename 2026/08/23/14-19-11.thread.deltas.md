## 2026/08/24

- [2026/08/24/09-13-37 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood proposed an alternative to a configurable stash ref: since a stash is already recorded with the branch checked out at creation, add an option to pop the last stash created on the current branch, which would keep agents on separate branches from treading on each other's stashes, still allow moving stashed changes between branches/worktrees, and let a stash for the current branch be retrieved even if created in another worktree; he noted that an agent needing a truly private stash could use `git stash create` and record the resulting oid under `refs/worktree/`. He also said he has been meaning to add an option to specify an alternative branch name when creating a stash, so that `git checkout -m` and `git rebase --autostash <upstream> <branch>` record the branch being switched to rather than the one currently checked out.
- [2026/08/24/14-58-33 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano responded that ideas for per-branch and per-worktree stashes have been floated before, but cautioned against relying heavily on the stash message, since the more it is relied on the more restricted user-supplied `-m` messages would become; he suggested that officially supporting per-branch stashes might require a more structured message format, such as appending `: target-branch` after the user's message, with `-m` always appending that suffix.

- [2026/08/25/17-38-51 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano agreed that Phillip Wood's point about the existing structured stash message format makes sense.
- [2026/08/25/18-24-03 by Vladimir Sitnikov <sitnikov.vladimir@gmail.com>] Vladimir Sitnikov argued that a wrapper banning git-stash(1) misses autostashes, since `git rebase topic --autostash` writes to refs/stash without naming the stash in the command, and rebase.autoStash in the shared .git/config enables it for every worktree with no flag on the command line to ban.
- [2026/08/25/18-24-03 by Vladimir Sitnikov <sitnikov.vladimir@gmail.com>] Vladimir Sitnikov added that forbidding the stash subcommand is fishy because agents might miss the instruction and call stash anyway, and conceded the earlier points about the bar for a configuration option and the framing: a single confused session justifies the option on its own, and agents changed how often the problem happens, not whether it is worth fixing.
- [2026/08/25/18-24-03 by Vladimir Sitnikov <sitnikov.vladimir@gmail.com>] Vladimir Sitnikov responded to Phillip Wood's earlier suggestion of popping the last stash created on the current branch: a per-branch filter separates every worktree sitting on a branch (git refuses to check the same branch out in two worktrees) and keeps entries visible to `git stash list`, which a private ref gives up.
- [2026/08/25/18-24-03 by Vladimir Sitnikov <sitnikov.vladimir@gmail.com>] Vladimir Sitnikov identified the gap in a per-branch filter as detached HEAD: every detached worktree records "(no branch)", so they group together instead of separating, and he noted one of his repositories has 436 linked worktrees, 23 on detached HEAD.
- [2026/08/25/18-24-03 by Vladimir Sitnikov <sitnikov.vladimir@gmail.com>] Vladimir Sitnikov confirmed that using `git stash create` and recording the oid under refs/worktree/ is what he does today and it works, but every tool has to reimplement it, and tools that skip it produce the silent cross-worktree failure he opened with.
- [2026/08/25/18-24-03 by Vladimir Sitnikov <sitnikov.vladimir@gmail.com>] Vladimir Sitnikov proposed that the per-branch and per-worktree ideas may be one knob: if the stack's scope were configurable (shared ref, current branch, or per-worktree ref), "pop what this branch stashed" and "pop what this worktree stashed" become two values of one option, letting a detached worktree choose the value that still separates it; he offered to write the patch for whichever direction is preferred or to test others'.

Core problem or goal
Replace the build-time `USE_NSEC` macro with a runtime configuration option (`core.useNanosec`) to allow users to enable nanosecond precision on supported filesystems without recompiling Git, reducing "racy Git" problems. The series also includes a Meson build-system fix (`MAN_BASE_URL` configuration) and a no-op refactor of `repo_config_values_init`.

Current status
**Graduated to `next`** (integration testing branch) as of 2024-07-10. The series is complete and all prior feedback has been addressed. Junio’s requested **final reroll (v7)** has been posted but is **not intended for further changes**; it serves as a final polish to confirm the series is technically complete. The latent bug in `is_racy_stat()` when operating on a repository that is not `the_repository` (due to the new call to `repo_config_values()`) remains unresolved but is documented as a forward-looking constraint. Key technical details
Files touched: `Documentation/config/core.adoc`, `Documentation/meson.build`, `meson_options.txt`, `environment.c`, `environment.h`, `read-cache.c`, `statinfo.c`, `Documentation/technical/racy-git.adoc`, `compat/posix.h`, `Makefile`, `configure.ac`, `builtin/update-index.c`.
New config key: `core.useNanosec` (defaults to false).
Behavior change: nanosecond precision becomes configurable at runtime rather than compile time; performance impact documented for `git diff` in new worktrees. The patch preserves existing behavior on platforms lacking nanosecond support by treating the `use_nanosec` field as false when `NO_NSEC` is defined, preventing silent corruption. **No runtime warning will be emitted** when `core.useNanosec=true` is set on a `NO_NSEC` platform; users must rely on documentation to understand the risks. The `#ifndef NO_NSEC` guard around the `core.usenanosec` config handler in `environment.c` is retained to prevent reading nanosecond values on unsupported platforms, avoiding false negatives in racy checks. Jeff King (Peff) notes this guard introduces a subtle correctness risk: an index generated by a non-`NO_NSEC` build could store real nanosecond values, which a `NO_NSEC` build would misinterpret as zero, leading to false "racy" comparisons. This edge case is unlikely in practice but may warrant documentation in the future. The guard’s practical impact is minimal: users on `NO_NSEC` builds cannot enable `core.useNanosec` without recompiling, even if their platform supports it. The discussion highlights a trade-off between build-time restrictions and runtime flexibility, with both Peff and Knoble confirming the guard is reasonable given the complexity of eliminating `NO_NSEC` entirely.
On-disk format: unchanged.
Test coverage: platform-dependent; existing tests (e.g., `t4060`) pass when `core.useNanosec=true` is set, but systematic testing is complicated by platform variability. The Meson build-system fix (first patch) addresses a long-standing inconsistency between Makefile and Meson builds by exposing a configurable `man_base_url` option in `meson_options.txt`, defaulting to `file://$(htmldir)/` (with a trailing slash) to match the Makefile’s behavior. The fix resolves broken links in manual pages (e.g., `/usr/share/manuser-manual.html` → `/usr/share/man/user-manual.html`) and is motivated by the need to ensure correct rendering of links added in later patches (e.g., to `racy-git.adoc`). The no-op refactor in the second patch reorders assignments in `repo_config_values_init()` to group them by config section ("core", "sparse", "branch") for maintainability.
Performance: the v1 performance regression (~41× slowdown) is resolved by caching the config value in `repo_config_values`. The nested `#ifndef NO_NSEC` guards in `is_racy_stat()` are replaced with a single ternary expression for clarity.
Code structure: the `use_nanosec` field is unconditionally present in `struct repo_config_values` but ignored (treated as false) when `NO_NSEC` is defined. The `#ifndef NO_NSEC` guard in `environment.c` is retained, and the author has abandoned plans to consolidate `NO_NSEC` build-time differences using `ST_XTIME_NSEC(st)` in `is_racy_stat()`. The Meson build-system fix adds a configurable `man_base_url` option to `meson_options.txt`, defaulting to `file://$(htmldir)/` (with a trailing slash) to match the Makefile’s behavior. The no-op refactor in the second patch reorders assignments in `repo_config_values_init()` to group them by config section ("core", "sparse", "branch") for maintainability, improving code readability and easing future maintenance as new fields are added.
**Architectural constraint**: the new call to `repo_config_values()` in `is_racy_stat()` introduces a latent bug when operating on a repository that is not `the_repository`, as the function currently only works for the global repository. The author defers deeper investigation, citing time constraints and the complexity of testing across subsystems. The series adopts a safe default (treating `core.useNanosec` as false) when `istate->repo != the_repository` as a stopgap. This is not a regression but makes the existing limitation more visible. Junio now explicitly flags this as a blocker for future recursive submodule operations (e.g., `git diff` or `git status` traversing submodules without spawning subprocesses), noting that `git grep --recurse-submodule` does not exercise the racy-entry code paths and thus offers no assurance against latent bugs in other recursive contexts. Patrick Steinhardt suggests refactoring to `struct repo_settings` as a potential mitigation if future edge cases arise. **The discussion between Knoble and Junio confirms the stopgap is a temporary measure and may reduce the impetus to fix the underlying limitation**, but no immediate changes are proposed. Knoble argues that papering over the issue with a safe default might delay deeper refactoring, but acknowledges the trade-off is acceptable given the series’ goals.

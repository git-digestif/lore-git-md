Thread identity: `[PATCH 0/3] format-patch: add --[no-]range-diff-notes` series introducing options to control notes inclusion in range-diff output. Originating author: Kristoffer Haugsbakk. Thread type: patch series (feature addition).

Core problem or goal: Add `--[no-]range-diff-notes` options to `git format-patch` to allow independent control over whether Git notes are included in the range-diff section versus the patches themselves. The feature aimed to address workflow needs where users want to suppress iteration notes (e.g., "v3: [description]") in range-diffs while retaining them in the patch output, but the proposed implementation was deemed conceptually flawed due to ambiguous option semantics, unintuitive fallback behavior, and a problematic toggle mechanism. Kristoffer Haugsbakk later proposed a simplified redesign that eliminates the toggle sequence and the arg-less `--range-diff-notes` variant, adopting Junio C Hamano’s suggested rule where `--no-range-diff-notes` means "no notes for range-diff" without fallback and `--range-diff-notes=<ref>` requires an explicit ref argument.

Current status: **Abandoned**. The series was posted as v1 and remains at that version. Junio raised a substantive usability concern about the option semantics, specifically that the interaction between `--range-diff-notes` and the existing `--notes` could not be defined in simple terms and was unintuitive. The toggle mechanism (`--no-range-diff-notes --range-diff-notes`) introduced additional complexity without resolving the core ambiguity. Kristoffer acknowledged the issues, confirmed the problematic behavior of `--no-notes --range-diff-notes` suppressing notes in both contexts, and chose to abandon the feature. Junio restated the usability issue in the closure email and noted that no alternative design was proposed before abandonment. Kristoffer later clarified that the implementation *did* already follow the alternative design Junio sketched (where `--notes` controls only the final patch output and `--range-diff-notes` controls only the range-diff material), but the documentation’s phrasing obscured this, and the toggle mechanism added unnecessary conceptual overhead. Junio’s follow-up email dissected the toggle mechanism’s usability problem in detail, proposing an alternative rule where `--no-range-diff-notes` would mean "no notes for range-diff" without fallback, eliminating the need for the toggle sequence. Kristoffer’s latest email proposes a simplified redesign that adopts Junio’s rule, drops the arg-less `--range-diff-notes` variant, and eliminates the toggle mechanism, but does not reopen the feature or signal intent to revive it. The thread is now closed with no further action expected.

Key technical details:
- Files touched: `builtin/log.c`, `log-tree.c`, `revision.c`, `revision.h`, `Documentation/git-format-patch.txt`, and tests in `t/t3206-range-diff.sh`.
- Proposed CLI options: `--range-diff-notes[=<ref>]` and `--no-range-diff-notes` (original implementation); the redesign would drop the arg-less `--range-diff-notes` variant and require an explicit ref argument for `--range-diff-notes=<ref>`.
- New struct members: `rdiff_override_notes` flag in `struct rev_info` (patch 3); `rdiff_notes_arg` (renamed from `rdiff_log_arg` in patch 2).
- Refactoring: `get_notes_args` was modified to use `rev->rdiff_notes_arg` directly instead of an explicit `struct strvec *arg` parameter (patch 1).
- Behavior (original implementation): The implementation maintained two separate notes lists (one for patches, one for range-diffs) and used the `rdiff_override_notes` flag to toggle between them. The usability issues arose from:
  1. `--no-notes` clearing the notes list that the range-diff fallback path still referenced.
  2. `--range-diff-notes` without `--range-diff` having no effect but not erroring.
  3. The toggle mechanism (`--no-range-diff-notes --range-diff-notes`) being counterintuitive, as `--no-range-diff-notes` merely pretended no `--range-diff-notes` was ever given, leading to confusing edge cases (e.g., aliases with `--range-diff-notes=foo` falling back to `--notes` when `--no-range-diff-notes` was used).
- Behavior (redesign proposal): `--no-range-diff-notes` would mean "no notes for range-diff" without fallback, and `--range-diff-notes=<ref>` would require an explicit ref argument. The interaction rule between patch notes and range-diff notes remains unchanged: if no range-diff notes options are given, the range-diff uses the same notes as the patches; otherwise, it uses only the explicitly specified notes (including none, via `--no-range-diff-notes`). The redesign would replace the custom `revision.c` option handler with a standard `parse-options` callback, since the arg-less variant is no longer needed.
- Documentation: The original phrasing was misleading, describing the behavior only for the edge case where the range-diff notes list was empty. Kristoffer’s rewritten documentation snippet explicitly described the two separate notes lists (patch notes vs. range-diff notes) and their independent control, confirming the implementation already followed the design Junio sketched. D. Ben Knoble suggested a minor rewording to improve clarity ("no notes override behavior" instead of "this notes override behavior").
- Toggle mechanism (original implementation): The sequence `--no-range-diff-notes --range-diff-notes` was intended to undo prior overrides (e.g., `--range-diff-notes=changelog`) and restore the default state where both patches and range-diffs use the same notes (those specified by `--notes`). Kristoffer provided a concrete example showing how this sequence avoids the need to repeat all `--notes` arguments, arguing that the flexibility justified the added complexity. However, Junio’s analysis highlighted that the mechanism’s behavior was unintuitive, particularly in edge cases involving aliases or `--no-notes`.
- Edge cases handled (original implementation): Toggling the override off after it was set, supporting specific notes refs for range-diffs (e.g., `--range-diff-notes=testing`), and reverting to the default state using `--no-range-diff-notes --range-diff-notes`. The toggle mechanism was intended to undo prior overrides and fall back to the notes specified by `--notes`, but its interaction with `--no-notes` and aliases remained problematic.
- Edge cases (redesign proposal): The redesign eliminates the toggle mechanism and the arg-less `--range-diff-notes` variant, simplifying the behavior. `--no-range-diff-notes` would mean "no notes for range-diff" without fallback, and `--range-diff-notes=<ref>` would require an explicit ref argument. This removes the confusing edge cases involving aliases and `--no-notes`.
- Test coverage: Comprehensive tests were added to `t/t3206-range-diff.sh`, verifying scenarios like suppressing all range-diff notes, using different notes refs for patches and range-diffs, and toggling the override. The tests did not cover the problematic interaction between `--no-notes` and `--range-diff-notes` or the confusing alias edge cases Junio highlighted.
- Prior commit dependency: 85bd88a7 (2025-09-25) introduced `rdiff_log_arg` to `struct rev_info`.
- Junio’s proposed redesign: Eliminate the toggle mechanism by making `--no-range-diff-notes` mean "no notes for range-diff" without fallback. This would simplify the semantics, remove the need for the toggle sequence, and make the behavior more predictable. The user would need to explicitly specify `--range-diff-notes=<ref>` to re-enable range-diff notes.
- Kristoffer’s redesign proposal: Adopts Junio’s rule, drops the arg-less `--range-diff-notes` variant, and eliminates the toggle mechanism. The interaction rule between patch notes and range-diff notes remains unchanged: if no range-diff notes options are given, the range-diff uses the same notes as the patches; otherwise, it uses only the explicitly specified notes (including none, via `--no-range-diff-notes`). The redesign would replace the custom `revision.c` option handler with a standard `parse-options` callback.
- Tangential issue: Kristoffer and D. Ben Knoble noted that `format-patch` should respect `format.notes` rather than `notes.displayRef`, as the latter is more suited for personal use (e.g., `git log`) than for generating patches intended for email distribution. `format.notes` is documented as a boolean but can also specify a ref, implying a potential inconsistency in the current behavior.

Open questions and loose ends:
- The usability issues with option semantics remain unresolved in the original implementation:
  1. The interaction between `--notes` and `--range-diff-notes` was ambiguous and unintuitive, particularly when `--no-notes` suppressed notes in both contexts.
  2. `--range-diff-notes` without `--range-diff` had no effect but did not error, creating a silent failure mode.
  3. The toggle mechanism (`--no-range-diff-notes --range-diff-notes`) was counterintuitive and added unnecessary complexity, despite being a deliberate design choice to avoid repeating `--notes` arguments.

Junio’s proposed redesign (making `--no-range-diff-notes` mean "no notes for range-diff" without fallback) would address the toggle mechanism’s usability problem but does not resolve the other issues (e.g., `--range-diff-notes` without `--range-diff`).
- Kristoffer’s redesign proposal directly addresses Junio’s usability concerns by:
  1. Enforcing explicit separation of the two notes lists.
  2. Clarifying the CLI semantics by dropping the arg-less `--range-diff-notes` variant and requiring an explicit ref argument for `--range-diff-notes=<ref>`.
  3. Simplifying the behavior by eliminating the toggle mechanism and making `--no-range-diff-notes` mean "no notes for range-diff" without fallback.
  4. Ensuring `--no-notes` does not suppress range-diff notes unless explicitly requested via `--no-range-diff-notes`.
  5. Replacing the custom `revision.c` option handler with a standard `parse-options` callback.

## Notable threads

### treewide: migrate from legacy utime.h to utimensat

This series replaces the legacy `utime()`/`<utime.h>`, removed from POSIX.1-2024, with `utimensat()` from `<fcntl.h>` (with `utimes()` as a fallback and a MinGW wrapper), touching `copy.c`, `object-file.c`, `odb/source-loose.c`, `odb/source-packed.c`, `rerere.c`, `compat/utimensat.c`, build files and tests, because newer libc implementations such as LLVM-libc may not provide `utime()` at all.

Today brian m. carlson declined to review the series because the cover letter disclosed it was generated by Gemini Flash from Antigravity, arguing that this cannot satisfy the Developer's Certificate of Origin requirement in SubmittingPatches; he noted he had not read the series to avoid being influenced by code the project cannot include, and separately recalled that the *at functions cannot be used due to Windows lacking proper semantics. Junio C Hamano endorsed the stance as prudent, explaining that the contributor's DCO cannot be treated as valid because a copy editor of AI output cannot know where the code was copied from, and that if DCO-covered work later proves legally unusable the project itself bears the cost of ripping it out. brian m. carlson affirmed the view, adding that LLMs can regurgitate code substantially similar to training inputs, that the legal status of LLM output is unclear amid active litigation, and that knowingly distributing suspect code creates more legal exposure; he distinguished honest disclosure of AI use, which he called good-faith participation that could still allow future non-AI patches, from misleading the project about a patch's provenance, which he called dishonest.

### credential/libsecret: load secrets explicitly

This patch fixes a crash in the libsecret credential helper: `secret_service_search_sync()` with `SECRET_SEARCH_LOAD_SECRETS` can return an item whose secret is not loaded (the search silently discards load failures, and the GNOME keyring daemon omits locked or concurrently deleted items), so `secret_item_get_secret()` returns NULL and is passed unchecked to `secret_value_get_text()` and `secret_value_unref()`, producing assertion failures and losing the password. The fix drops `SECRET_SEARCH_LOAD_SECRETS` and loads the secret of the one used item with `secret_item_load_secret_sync()`, which reports errors.

Today Daniel Martí replied to Junio C Hamano's review, conceding that dropping the flag is not strictly necessary since checking `secret_item_get_secret()` for NULL would also avoid the assertion failures, but explaining that the flag is not a single call: libsecret implements it as SearchItems followed by GetSecrets with errors from the second step discarded, and it skips locked items client-side without asking the daemon. He argued that his unconditional explicit load keeps the common case at the same two round trips while a fallback version would add a third round trip in the rare race case, and that keeping the flag with a fallback would leave the explicit-load path essentially unexercised while still silently discarding load errors on the common path. He agreed the race condition requires a concurrently racing process or a locked keyring and that he does not see a way to test it reliably.

### Bug Report: subtree then rebase causes unrelated history to conflict

Today Gabriel Ford filed a bug report that `git subtree add --squash` followed by `git rebase` produces a conflict between a file in the main repository (`.clang-format`) and a file with the same relative path in the subtree, even though they reside in separate directories. He hypothesizes this occurs because squash merging causes history to conflict when the path relative to the root is identical in the subproject, and notes that a `git blame` on the main-repo file shows no changes.

### git config --global: doc and behaviour disagree when ~/.gitconfig and XDG config file coexist

This bug report describes a discrepancy between the git-config(1) documentation for `--global` and the actual behavior when both `~/.gitconfig` and `~/.config/git/config` exist: without `--global`, `git config --get` reads both files with `~/.gitconfig` taking precedence, but with `--global` the code wires `git_global_config()` as the sole source, so the two commands silently disagree. The reporter prefers fixing the behavior and is interested in contributing a patch.

Thread identity: A five-patch series from Kristoffer Haugsbakk adding `--abbrev`, `--color`, and `--date` formatting options to the `git format-rev` command (introduced in Git 2.45). The series is now at v2, incorporating v1 review feedback, a memory leak fix, defensive code improvements, and two new refactoring patches (2/5 and 4/5) addressing assertion placement and documentation reuse.

Core problem or goal: Extend `git format-rev` with three new formatting options (`--abbrev`, `--color`, `--date`) to bring it closer to parity with `git log`'s formatting flexibility. The series refactors option handling and documentation (patches 1--4) and implements the new options (patch 5/5) by reusing existing `git log` logic (`rev_info` struct and `pretty.c` date formatting). The command's necessity has been debated, with the author clarifying that the `--stdin-mode=text` mode (turning hashes into references in arbitrary input text) remains the unique capability justifying the command's existence. D. Ben Knoble proposed splitting `git format-rev` into two distinct commands or modes, moving the revs mode functionality into `git diff-tree` while retaining `git format-rev` exclusively for the text mode; Kristoffer Haugsbakk has now responded, agreeing that text mode is the unique value but arguing that `git diff-tree` is too undiscoverable and confusing (requiring `-v --always --no-patch`) to serve as a replacement for the revs mode.

Current status: Under review (v2 posted 2026-08-26), but the series remains at risk of being dropped from `seen` due to lack of substantive reviews. All v1 feedback has been addressed: Junio C Hamano's suggestions (designated initializers in patch 3/5, defensive `BUG_ON_OPT_NEG(unset)` placement in all option callbacks) are incorporated, the memory leak in the `--date` callback (missing `date_mode_release()` call) is fixed, and the series now includes two new refactoring patches (2/5 for defensive assertions, 4/5 for documentation reuse). The series remains uncontroversial but is queued under the name `kh/format-rev-more-options` in `seen` only; it is not in `next` or `master`. Junio C Hamano has reiterated that he is not the best reviewer for this experimental command and has explicitly invited input from contributors more familiar with `git format-rev`. The latest exchange clarifies the author's position on the proposed split: Haugsbakk agrees the text mode justifies keeping the command but considers `git diff-tree` unsuitable for the revs-mode use case due to its opacity, and he is willing to see the revs mode removed entirely if no other contributor wishes to preserve it.

Key technical details:
- Files touched: `builtin/name-rev.c` (main implementation), `Documentation/git-format-rev.adoc`, `Documentation/rev-list-options.adoc`, `Documentation/rev-list-option-date-alternatives.adoc` (new), test coverage in `t/t6120-describe.sh`.
- New CLI options: `--abbrev`, `--color`, `--date` (with same alternatives as `git log`).
- Subsystems reused: `rev_info` struct, `pretty.c` date formatting.
- On-disk format: No changes.
- Synopsis simplification: The command synopsis now highlights the two mandatory options (`--stdin-mode` and `--format`) while moving the rest into `[<options>]`.
- Documentation refactoring: Patch 4/5 extracts the `--date` alternatives block from `rev-list-options.adoc` into a new standalone file (`rev-list-option-date-alternatives.adoc`) for reuse by both `git-rev-list` and `git-format-rev`. The include directive replaces the original block verbatim; no conditional AsciiDoc markup is used. The initial paragraph of the `--date` documentation (referencing `git-log`) is left unchanged for `git-rev-list`, while `git format-rev` uses a dedicated paragraph in patch 5/5.
- Test coverage: Expanded in `t/t6120-describe.sh` to verify the new options behave identically to their `git log` counterparts, including error handling for invalid values (e.g., `--color=not-valid`) and custom date formats (`--date="format:%c"`). Tests now normalize option ordering to avoid false negatives via updated helper functions `format_rev_cmp_log` and `format_rev_err_cmp_log`.
- Memory leak fix: The `--date` callback (`date_cb()`) now calls `date_mode_release()` after `parse_date_format()` to free any allocated custom format string.
- Defensive code: All option callbacks in `builtin/name-rev.c` now place `BUG_ON_OPT_NEG(unset)` at the top to ensure it triggers before any dereference of `option->value`. Patch 2/5 (new in v2) moves these assertions to the top of the `format_nul_cb()` callback for consistency and clarity, aligning with Git's defensive coding practices.
- Patch 1/5: Cosmetic documentation cleanup in `builtin/name-rev.c`, converting option descriptions from mixed case ("Use NUL...") to lowercase ("use NUL...") for style consistency. No functional changes.
- Patch 2/5: New in v2: moves all `BUG_ON_OPT_NEG(unset)` and `BUG_ON_OPT_ARG(arg)` assertions to the top of option callbacks in `builtin/name-rev.c` for defensive programming. No functional changes; purely stylistic.
- Patch 3/5: Refactoring introducing `struct format_rev_data` to group option variables (`format`, `stdin_mode`, `nul_input`, `nul_output`, `notes`), using designated initializers (C99) for clarity, and renaming `stdin_mode_arg` to `stdin_mode` to avoid shadowing. No functional changes; purely internal refactoring. Junio C Hamano reviewed v1 and requested designated initializers, which are now incorporated.
- Patch 4/5: Pure documentation refactoring: extracts the `--date` alternatives block from `rev-list-options.adoc` into a new standalone file (`rev-list-option-date-alternatives.adoc`) for reuse by both `git-rev-list` and `git-format-rev`. The new file is created with mode `100644` and follows the same formatting as the original block. No functional changes.
- Patch 5/5: Implements the three new options by reusing `git log` logic. The `--date` callback (`date_cb()`) parses arguments and stores the result in `rev_info.date_mode`, while `--abbrev` and `--color` directly set their respective fields in `rev_info`. The patch fixes the memory leak (missing `date_mode_release()`) and expands test coverage for custom date formats and the no-argument `--date` case.

Open questions and loose ends:
- UI design: Whether `--date` should support the same alternatives as `git log` (no objections raised yet; may attract discussion in future iterations).
- Synopsis simplification: Minor UI tweak to highlight mandatory options; no objections yet.
- Command necessity and scope: The author has clarified that `--stdin-mode=text` is the unique capability justifying the command's continued existence, and he agrees that if the `--stdin-mode=revs` mode were removed, the command should simplify to `git format-rev` without the mode flag. However, he pushes back on D. Ben Knoble's proposal to use `git diff-tree` as the replacement for the revs mode, describing it as completely undiscoverable for commit-log-style usage: invoking `git diff-tree -v --always --no-patch` reads confusingly ("do a diff verbosely, always, without a diff"), requiring users to know that `-v` or `--format=...` emits commit information and `--always` counters the default suppression of merge commits with no diff output. Haugsbakk states he is entirely fine with removing the revs mode or the command altogether, provided no other contributor wants to keep it as a wrapper or "skin" around the diff-tree options; for his own workflow the practical impact is minimal. The open question is whether the broader community sees enough value in a simplified text-only `git format-rev` to justify merging the current options series, or whether the revs functionality should be preserved through a different interface despite its current home being questioned. No concrete proposal or patch for modifying `git diff-tree` has been posted, and the author has previously admitted the code is "too difficult" to modify, leaving the series' fate dependent on whether reviewers see enough value in the text-mode functionality to justify the new options or whether the proposed split gains traction.

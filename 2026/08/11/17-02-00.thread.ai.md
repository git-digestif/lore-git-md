Subject: [PATCH v4] http: add http.sslVerifyStatus to check OCSP staples
Series version: standalone patch (v7 final combined patch)
Originating author: graysongordon-gl
Thread type: security feature patch

Core problem or goal
Git’s HTTPS certificate verification omits OCSP staple validation, leaving it vulnerable to accepting revoked certificates. The patch adds a boolean `http.sslVerifyStatus` option (default `false`) that enables staple validation via libcurl’s `CURLOPT_SSL_VERIFYSTATUS`, causing connections to fail if the server does not provide a staple. The design is fail-closed for security but defaults to `false` to avoid breaking remotes that do not support stapling. The feature is motivated by government and government-adjacent customers (e.g., US Department of Defense PKI) who mandate OCSP stapling and encounter Git servers with stapled responses; OpenSSL-linked Git binaries currently ignore staples, creating a security gap where revoked certificates are accepted.

Current status

On 2025-06-18, citing test infrastructure issues reported by SZEDER Gábor, Junio reverted the topic from `next` to allow the test suite to be fixed before the feature graduates to the next release cycle. The core functionality remains intact in `master`; the revert is procedural and does not reflect a rejection of the feature. The patch is technically complete, and all prior review feedback was addressed. The new `t5585-http-ssl-ocsp.sh` test failed on Gábor’s system due to two problems: (1) the test’s expectation that a revoked certificate is accepted without `http.sslVerifyStatus` was invalid on systems where libcurl (7.81.0) checks CRLs by default, causing the revoked certificate to be rejected even when stapling was disabled, and (2) the `SSL_VERIFYSTATUS` prerequisite’s error-message check was misleading. Gábor now confirms the test failure was caused by using the GnuTLS backend for libcurl, which does not fully support OCSP stapling; switching to the OpenSSL backend resolves the issue. The prerequisite itself is fundamentally sound, and Junio agrees with Gábor’s suggested improvements: tightening the error-message check to look for the absence of “could not enable OCSP status verification” (the second half of the error message) and renaming the prerequisite from `SSL_VERIFYSTATUS` to `CURL_SSL_VERIFYSTATUS` to better reflect its scope (libcurl support, not server support). The diagnostic phase is now closed; no new technical concerns were introduced. The two minor code-quality nits in the test script (exact error message check and `export` usage) remain open. No follow-up patch has been posted yet; the issues are post-merge and do not affect the core functionality of `http.sslVerifyStatus`.

Key technical details
- New config key: `http.sslVerifyStatus` (boolean, default `false`)
- Per-URL override: `http.https://example.com/.sslVerifyStatus`
- Libcurl requirement: `CURLOPT_SSL_VERIFYSTATUS` (libcurl ≥ 7.41.0, already below Git’s minimum)
- Files touched: `http.c`, `Documentation/config/http.adoc`, `t/lib-httpd.sh` (OCSP infrastructure), `t/lib-httpd/apache.conf` (Apache stapling config), `t/t5551-http-fetch-smart.sh` (fail-closed behavior, per-URL scoping, edge cases), `t/t5585-http-ssl-ocsp.sh` (staple validation tests)
- Test integration: The final combined patch merges Grayson’s original tests with Patrick Steinhardt’s test harness. The `SSL_VERIFYSTATUS` prerequisite is shared between both test files, and the Meson build is updated to include the new test script. The `LIB_HTTPD_OCSP` mode in `lib-httpd.sh` provides a certificate authority, OCSP responder, and Apache configuration for stapling.
- Behavior: fail-closed (connection fails if staple missing or invalid)
- Backend differences: GnuTLS and OpenSSL now behave identically in libcurl ≥ 8.10 (GnuTLS ≥ 3.8), but the test failure was caused by using the GnuTLS backend (which lacks full OCSP stapling support) rather than OpenSSL. The root cause is environmental and resolved by switching backends.
- Error handling: failure messages include libcurl error strings (`curl_easy_strerror()`) to distinguish missing features (`CURLE_NOT_BUILT_IN`) from other errors
- Symbols: none renamed; new config key only
- Test failures: (1) the test’s expectation that a revoked certificate is accepted without `http.sslVerifyStatus` was invalid on systems where libcurl checks CRLs by default, and (2) the `SSL_VERIFYSTATUS` prerequisite’s error-message check was misleading. The root cause was environmental (GnuTLS backend lacking OCSP stapling support), not a flaw in the test logic.
- Code-quality nits: test should check exact error message, and `with_ssl_verification` helper should use `export` for portability.
- Prerequisite improvements: Junio agrees with Gábor’s suggestions to tighten the prerequisite’s string match to look for the absence of “could not enable OCSP status verification” and to rename the prerequisite from `SSL_VERIFYSTATUS` to `CURL_SSL_VERIFYSTATUS`.

Open questions and loose ends
- Whether the default (`false`) should eventually change to `true` or if users should be warned when staples are ignored.
- Whether the feature’s maintenance burden (given OCSP stapling’s declining relevance) is justified by the specific use case of government customers.
- The two minor code-quality nits in the test script (exact error message check and `export` usage) remain open.
- Junio’s request to revisit the two overly verbose commit-message paragraphs Patrick Steinhardt flagged, though neither reviewer objected to their substance.
- The prerequisite’s error-message check and name are now agreed to be improved per Gábor’s and Junio’s suggestions; a follow-up patch is needed.

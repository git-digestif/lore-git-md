This thread is about a security feature, `http.sslVerifyStatus`, that adds OCSP staple validation to Git’s HTTPS certificate checks. The patch was merged to `master` on June 12 but reverted from `next` on June 18 due to test failures reported by SZEDER Gábor. The core functionality remains intact; the revert is procedural, not a rejection of the feature.

The feature is motivated by government customers (e.g., US DoD PKI) who require OCSP stapling. It adds a boolean config option, `http.sslVerifyStatus` (default `false`), which enables staple validation via libcurl’s `CURLOPT_SSL_VERIFYSTATUS`. The design is fail-closed—connections fail if the server doesn’t provide a staple—but defaults to `false` to avoid breaking remotes without stapling support. All prior review feedback was addressed, including Junio’s documentation tweaks and Patrick Steinhardt’s test harness contributions.

The current blocker is test infrastructure: Gábor identified two issues in `t5585-http-ssl-ocsp.sh`. First, the test expects a revoked certificate to be accepted without `http.sslVerifyStatus`, but libcurl (7.81.0) rejects it due to CRL checks, making the test’s expectation invalid. Second, the `SSL_VERIFYSTATUS` prerequisite’s error-message check is misleading. Gábor and Junio now agree on tightening the error-message check and renaming the prerequisite to `CURL_SSL_VERIFYSTATUS` to clarify its scope. Patrick Steinhardt also questioned whether Gábor’s system might be using a libcurl backend that lacks OCSP stapling support, but the test suite should skip rather than fail in such cases.

The next step is a follow-up patch to fix these test issues. No changes to the core feature are needed, and the feature remains merged in `master`. Open questions include whether the default should eventually change to `true` and whether the maintenance burden is justified by the use case.

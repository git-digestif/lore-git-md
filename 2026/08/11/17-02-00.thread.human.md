This thread began with a security feature patch adding `http.sslVerifyStatus`, a new Git config option that enables OCSP staple validation for HTTPS connections. The patch was motivated by government customers (such as US Department of Defense PKI) who require OCSP stapling and were encountering a security gap where Git—when linked with OpenSSL—ignored staples, accepting revoked certificates. The feature defaults to `false` to avoid breaking existing setups but provides a fail-closed mechanism when enabled, ensuring connections fail if the server does not provide a valid staple. After several iterations addressing review feedback from Junio C Hamano and Patrick Steinhardt, the patch was merged to `master` on June 12, 2025.

The feature itself remains intact, but SZEDER Gábor has reported two test infrastructure issues in the newly merged `t5585-http-ssl-ocsp.sh` test. First, the `SSL_VERIFYSTATUS` prerequisite check is flawed: it incorrectly passes when `git ls-remote` fails for unrelated reasons (e.g., repository not found or no OCSP response), rather than verifying the system’s actual staple-validation capability. Second, the test expects Git to accept a revoked certificate when `http.sslVerifyStatus` is disabled, but Gábor’s system rejects it anyway due to libcurl checking the CA’s CRL by default—indicating the test setup does not properly isolate OCSP stapling from other revocation mechanisms. Gábor also noted minor code-quality improvements for the test script.

The core functionality of `http.sslVerifyStatus` is unaffected, and the patch remains in `master`. However, the test failures suggest the test infrastructure needs fixes to ensure reliable validation across different environments. The open question about the feature’s long-term maintenance burden—given OCSP stapling’s declining relevance—remains unresolved, though the immediate security need for government customers justified its inclusion.

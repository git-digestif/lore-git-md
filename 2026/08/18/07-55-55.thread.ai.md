Subject: [PATCH v6 0/4] receive-pack: add new `receive-report` hook for server-side status filtering
Series version: v9 (4 patches)
Originating author: Karthik Nayak
Thread type: feature patch series

Core problem or goal
Git’s `receive-pack` currently sends a fixed status report to the client after ref updates are committed, with no mechanism for server administrators to intercept or modify this report. The patch series introduces a new `receive-report` hook that acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via the sideband channel. The hook is motivated by GitLab’s need to implement MVCC (multi-version concurrency control) on the server side, where the status report must reflect the repository state *after* all server-side operations (including those beyond `ref_transaction_commit()`) are complete. Junio C Hamano’s earlier comment questioned the necessity of a separate hook, noting that the `reference-transaction` hook already fires in the "committed" phase and could theoretically be extended to allow rejecting the transaction. Karthik Nayak’s replies clarify that the `reference-transaction` hook cannot meet GitLab’s requirements because it lacks access to push-specific context (e.g., per-ref failures, sideband messages) and cannot convey the final status report to the client. The hook’s ability to decouple reported status from actual repository state is intentional and aligns with GitLab’s use case, where conservative client-side behavior (not updating remote-tracking branches when the hook reports `ng`) is the desired outcome. Junio’s latest reply highlights a **fundamental consistency concern**: this decoupling violates Git’s principle that remote-tracking branches reflect the server’s state, as a "failed" push (reported as `ng`) may still commit ref updates, leaving the client’s view inconsistent with reality.

Key technical details
- Files touched: `builtin/receive-pack.c`, `Documentation/githooks.adoc`, `Documentation/git-receive-pack.adoc`, `t/meson.build`, `t/t5412-receive-report-hook.sh`
- New hook name: `receive-report`
- New helper functions: `generate_report()`, `run_receive_report_hook()`, `override_cmds_error()`
- New enum: `report_status_version` (replaces the `detailed_reports` boolean parameter; values: `REPORT_STATUS_UNKNOWN`, `REPORT_STATUS_V0`, `REPORT_STATUS_V2`)
- Invocation point: after all ref updates are committed, before the status report is sent
- Input: pkt-line encoded status report on stdin (terminated by a flush packet)
- Output: replacement status report on stdout; stderr forwarded to client via sideband
- Exit code semantics: non-zero exit rewrites all ref status lines to `"receive-report hook failed"` and overwrites all `cmd->error_string` fields; zero exit uses the hook’s stdout as the report. The regenerated error report uses the same protocol version as the original call.
- Hook is **not integrated with the config-based hook infrastructure**
- Test coverage: 224 lines in `t/t5412-receive-report-hook.sh` covering passthrough, failure modes, stdin/stdout handling, sideband relay, and the hook’s ability to modify the `unpack` status line and individual ref statuses. **New observation**: The test suite does not verify behavior when the client does *not* request a status report (i.e., when `version` is `REPORT_STATUS_UNKNOWN`). This gap was flagged by Patrick Steinhardt in the latest review, noting that the absence of test failures for the `BUG()` flaw suggests insufficient coverage for edge cases where the hook is not invoked.
- Documentation: The hook is documented in `githooks.adoc` and `git-receive-pack(1)`, with the latter linking to `githooks(5)`. The `proc-receive` hook is now documented in `git-receive-pack.adoc` with an eight-line `PROC-RECEIVE HOOK` section explaining its purpose and linking to `githooks(5)`. The commit message documents **three ways the hook can affect the push outcome**:
  1. Rewriting individual ref status lines.
  2. Aborting the entire push (by exiting non-zero).
  3. Modifying the initial `unpack` status line.
- **Consistency concern**: The hook’s design intentionally decouples the reported status from the actual repository state, allowing the server to report a push as failed (`ng`) while still committing ref updates. This violates Git’s traditional principle that remote-tracking branches reflect the server’s state, as a client’s `git fetch` after a "failed" push may reveal the server *did* accept the update. The divergence is justified by GitLab’s MVCC use case, where conservative client-side behavior (not updating remote-tracking branches when the hook reports `ng`) is the desired outcome. The commit message explicitly states that the hook owner is responsible for undoing ref changes if needed and that the hook is only appropriate for servers where rejected updates are not immediately visible to other readers.

Open questions and loose ends
- **Design rationale for a separate hook**: Junio’s earlier comment noted that the `reference-transaction` hook could theoretically be extended to meet GitLab’s requirements, but Karthik’s replies clarify that it lacks access to push-specific context (e.g., per-ref failures, sideband messages) and cannot convey the final status report to the client. No further action is required.
- **Consistency trade-off**: Junio’s latest reply surfaces a **philosophical tension** between GitLab’s use case and Git’s traditional consistency guarantees. The hook’s ability to report a state divergent from the actual repository state is intentional but introduces a novel inconsistency in Git’s push/fetch model. The commit message now explicitly acknowledges this trade-off and justifies it with GitLab’s MVCC use case. No code changes are proposed or needed; the exchange documents the design choice for future reviewers.
- **Test coverage gap**: Patrick Steinhardt’s latest review flags a **potential blind spot** in the test suite: the 224-line `t/t5412-receive-report-hook.sh` script does not verify behavior when the client does *not* request a status report (i.e., when `version` is `REPORT_STATUS_UNKNOWN`). The absence of test failures for the `BUG()` flaw in patch 2/4 suggests this edge case is untested. The hook’s design as a filter for the status report—only invoked when the client advertises the capability—makes this a plausible oversight. No specific fix is proposed, but the issue is now recorded as an open question for future consideration.

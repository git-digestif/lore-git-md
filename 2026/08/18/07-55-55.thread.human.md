This thread introduces a new `receive-report` hook for Git’s `receive-pack`, letting server administrators filter or rewrite the status report sent to clients after ref updates. The hook is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the reported status must reflect the repository state *after* server-side operations (like background jobs) complete—even if those operations happen after `ref_transaction_commit()`. The series is now **queued in `next`** and feature-complete, with all prior feedback addressed in the v9 iteration.

The hook acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband. Key design choices include decoupling the reported status from the actual repository state (a deliberate trade-off for GitLab’s use case) and using a single-script filter rather than integrating with Git’s config-based hook infrastructure. The v9 update fixed a critical flaw in patch 2/4, where a `BUG()` call could crash the server if the client omitted the `report-status` capability. The fix ensures the hook silently skips the status report in such cases, aligning with existing behavior.

Junio C Hamano and Patrick Steinhardt provided the most substantive reviews, with Junio raising a philosophical concern about the hook’s consistency trade-off (allowing "failed" pushes to still commit ref updates) and Patrick flagging a test coverage gap. The latter is now clarified: the test suite didn’t catch the `BUG()` flaw because Git’s built-in `send-pack` client always requests a status report, and there’s no way to test the edge case without a custom client. The series is ready for final review and graduation to `master`, with no open technical objections.

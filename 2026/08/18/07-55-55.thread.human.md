This thread introduces a new `receive-report` hook for Git's `receive-pack`, allowing server administrators to intercept and modify the status report sent to clients after ref updates. The series, now at version 10 with a follow-up cleanup patch, is feature-complete and addresses all prior technical feedback, including a critical design flaw in protocol version handling and a memory leak in error paths. It was queued in `next` on September 5, 2026, and is ready for final review before graduating to `master`.

The hook is motivated by GitLab's need to implement multi-version concurrency control (MVCC), where the status report must reflect the repository state *after* all server-side operations complete—even if that means decoupling the reported status from the actual repository state. This design choice, while intentional, introduces a philosophical tension with Git's traditional consistency guarantees, as clients may see a "failed" push (`ng`) while the server still commits ref updates. The commit message explicitly acknowledges this trade-off, justifying it with GitLab's use case where conservative client-side behavior (not updating remote-tracking branches) is desired.

Key participants include Karthik Nayak (author), who implemented the hook and addressed all feedback, and Junio C Hamano (maintainer), who raised critical issues like the memory leak and protocol version flaw, both now resolved. Patrick Steinhardt and Jeff King provided substantive reviews, with Peff confirming the untestable nature of the `BUG()` flaw due to infrastructure limitations. The latest email is a surface-level cleanup patch from Junio, removing a redundant check in `override_cmds_error()` and updating Coccinelle rules to enforce the pattern. This patch is uncontroversial and will likely merge alongside the main series.

The series touches `builtin/receive-pack.c`, documentation, and test files, introducing new helpers like `generate_report()` and an `enum report_status_version` to replace a boolean parameter. Test coverage spans 257 lines but lacks verification for clients that don’t request status reports—a gap acknowledged as a practical limitation. The hook’s design as a single-script filter is documented, along with its three ways of affecting push outcomes: rewriting ref status lines, aborting the push, or modifying the `unpack` status line. The only deferred feedback is Oswald Buddenhagen’s critique of commit message verbosity, which Karthik opted not to address at this stage. The thread is now in its final polish phase.

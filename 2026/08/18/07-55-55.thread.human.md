This thread introduces a new `receive-report` hook in Git's `receive-pack` to allow server administrators to filter or modify the status report sent to clients after ref updates. The hook is motivated by GitLab's need for multi-version concurrency control (MVCC), where the reported status must reflect the repository state *after* all server-side operations complete, even if that diverges from the actual ref updates. The series is now feature-complete and queued in `next` (Junio C Hamano, 2026-09-05), with all prior feedback addressed, including design clarifications, error-handling fixes, and documentation improvements.

Karthik Nayak is the author, implementing the hook and justifying its design trade-offs—particularly the intentional inconsistency between reported status and actual repository state, which violates Git's traditional consistency guarantees but aligns with GitLab's use case. Junio initially questioned the necessity of a separate hook (suggesting the `reference-transaction` hook could suffice) and raised a philosophical concern about the consistency trade-off, but ultimately graduated the series to `next` after Karthik clarified the hook's unique requirements. Patrick Steinhardt provided substantive reviews, proposing exit status alignment with the `pre-receive` hook and identifying refactoring opportunities, all of which were incorporated. The latest update fixes a stale comment in the `generate_report()` helper (noted by Junio) and a typo in the `enum report_status_version`, the last surface-level nits before graduation to `master`.

The hook is now fully documented, with test coverage in `t/t5412-receive-report-hook.sh` verifying passthrough behavior, failure modes, and sideband relay. The series touches `builtin/receive-pack.c` and documentation files, with no functional overlap with concurrent work like Justin Tobler's "pluggable writes" series.

This thread introduces a new `receive-report` hook for Git’s `receive-pack`, allowing server administrators to intercept and modify the status report sent to clients after ref updates. The hook is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the reported status must reflect the repository state *after* server-side operations (e.g., background jobs) complete—even if those operations occur after `ref_transaction_commit()`. The series, now at **v8**, is queued in Junio’s `next` branch (2026-09-05) and is feature-complete, with all prior feedback addressed.

The hook acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband. Key design choices include decoupling the reported status from the actual repository state (a deliberate trade-off for GitLab’s use case) and aligning exit semantics with the `pre-receive` hook. The series refactors the status-report generation logic to avoid redundancy, unifying `report()` and `report_v2()` into a single `generate_report()` helper. Test coverage in `t/t5412-receive-report-hook.sh` verifies passthrough behavior, failure modes, and the hook’s ability to modify the `unpack` status line.

Junio initially questioned the need for a separate hook (suggesting the `reference-transaction` hook could be extended), but Karthik clarified that the latter lacks access to push-specific context (e.g., per-ref failures, sideband messages). Junio also raised a **philosophical concern** about the hook’s consistency trade-off: reporting a "failed" push (`ng`) while still committing ref updates violates Git’s principle that remote-tracking branches reflect the server’s state. The commit message now explicitly acknowledges this divergence, justifying it with GitLab’s MVCC requirements.

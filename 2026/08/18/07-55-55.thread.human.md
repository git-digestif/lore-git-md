The `receive-report` hook series, now at version 10 and queued in Junio’s `next` branch since 2026-09-05, is ready for final review. Karthik Nayak introduced this feature to let server administrators filter or rewrite the status report Git sends after ref updates, motivated by GitLab’s need for MVCC (multi-version concurrency control). The hook acts as a bidirectional filter: it receives the pkt-line encoded report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband. All prior feedback has been addressed, including a critical design flaw in patch 2/4 (resolved in v9), a memory leak in the error-handling path (fixed in v10), and documentation ambiguities.

The series touches `builtin/receive-pack.c`, adds 224 lines of test coverage in `t/t5412-receive-report-hook.sh`, and documents the hook in `githooks.adoc` and `git-receive-pack(1)`. Junio’s latest concern—a philosophical tension between GitLab’s use case and Git’s traditional consistency guarantees—has been explicitly acknowledged in the commit message: the hook intentionally decouples reported status from actual repository state, allowing a server to report a push as failed while still committing ref updates. This divergence is justified by GitLab’s MVCC system, where conservative client-side behavior (not updating remote-tracking branches when the hook reports failure) is the desired outcome. Jeff King’s review confirmed that a `BUG()` flaw in patch 2/4, though real, was untestable with the existing infrastructure because older Git clients do not request status reports. Karthik declined to add an interop test, citing practical limitations, but the series remains on track for graduation to `master`. No open questions or loose ends remain.

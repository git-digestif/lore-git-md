This thread introduces a new `receive-report` hook for Git’s `receive-pack`, allowing server administrators to intercept and modify the status report sent to clients after a push. The hook is motivated by GitLab’s need for multi-version concurrency control (MVCC), where the reported status must reflect the repository state *after* all server-side operations—including those beyond `ref_transaction_commit()`—are complete. The series, now at **v10** and **queued in `next`**, is feature-complete and ready for final review.

The hook acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband. A non-zero exit rewrites all ref status lines to `"receive-report hook failed"` and overwrites error messages (with a memory leak fix in this version). The design intentionally decouples the reported status from the actual repository state, allowing the server to report a push as failed (`ng`) while still committing ref updates. This violates Git’s traditional consistency guarantees but aligns with GitLab’s use case, where conservative client-side behavior (not updating remote-tracking branches when the hook reports `ng`) is desired. The commit message explicitly acknowledges this trade-off.

The series includes **257 lines of test coverage** and documentation for the hook’s three ways of affecting push outcome: rewriting ref status lines, aborting the push, or modifying the `unpack` status line.

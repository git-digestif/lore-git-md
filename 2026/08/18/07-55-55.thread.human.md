This thread introduces a new `receive-report` hook for Git’s `receive-pack`, allowing server administrators to intercept and modify the status report sent to clients after ref updates. The hook is motivated by GitLab’s need to implement multi-version concurrency control (MVCC), where the status report must reflect the repository state *after* server-side operations complete—even if those operations occur outside `ref_transaction_commit()`. The series, now at version 10 and queued in Junio’s `next` branch, is feature-complete and addresses all prior feedback, including a critical `BUG()` flaw in protocol version handling and a memory leak in error paths.

The hook acts as a bidirectional filter: it receives the pkt-line encoded status report on stdin, replaces it with its stdout, and forwards stderr to the client via sideband. A non-zero exit rewrites all ref status lines to indicate hook failure, decoupling the reported status from the actual repository state—a deliberate trade-off to support GitLab’s use case. This design has drawn scrutiny from Junio, who notes it violates Git’s principle that remote-tracking branches reflect the server’s state, but the divergence is justified in the commit message as necessary for MVCC.

Key participants include Karthik Nayak (author), who implemented the hook and addressed all review feedback; Junio, who raised the consistency concern and identified the `BUG()` flaw; and Patrick Steinhardt, whose substantive reviews shaped the hook’s exit semantics and documentation.

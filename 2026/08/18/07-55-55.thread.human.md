This thread introduces a new `receive-report` hook in Git’s `receive-pack` to allow server administrators to filter or modify the status report sent to clients after ref updates. The feature is driven by GitLab’s need for multi-version concurrency control (MVCC), where the reported status must reflect the repository state *after* server-side operations complete, even if that diverges from the actual ref updates. The series, now at version 10, is queued in Junio C Hamano’s `next` branch and is feature-complete, with all prior feedback addressed—including a critical `BUG()` flaw, a memory leak in error handling, and test coverage gaps.

The hook acts as a bidirectional filter, receiving the pkt-line encoded status report on stdin and replacing it with its stdout, while forwarding stderr to the client via sideband. It can rewrite ref status lines, abort the push (non-zero exit), or modify the `unpack` status line. The design intentionally decouples reported status from actual repository state, a trade-off justified by GitLab’s use case but noted by Junio as a philosophical tension with Git’s traditional consistency guarantees. The series includes 257 lines of test coverage and documentation updates, though one edge case (clients not requesting status reports) remains untested due to infrastructure limitations.

Key participants include Karthik Nayak (author), Junio (maintainer), Patrick Steinhardt (substantive reviewer), and Jeff King (who confirmed a `BUG()` flaw was real but untestable). Oswald Buddenhagen’s recent critique of the commit message’s verbosity was acknowledged but deferred, as the series is otherwise ready for `master`. No further changes are expected.

# Thread deltas

## 2026/08/18

- [2026/08/18/11-34-33 by Artur Bieniek via GitGitGadget <gitgitgadget@gmail.com>] Artur Bieniek submitted a patch adding a `--hard` mode to `git pull` that, after fetching, requires a single integration candidate and resets the current branch, index, and working tree to it, while preserving quiet and submodule recursion behavior and rejecting options that cannot be honored by a hard reset.
- [2026/08/18/14-48-01 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano expressed mild opposition to adding `--hard` to `git pull`, arguing that the behavior is already safely and explicitly achieved by `git fetch` followed by `git reset --hard @{u}`, that the core purpose of `git pull` is history integration, and that adding a destructive option makes it easier for users with uncommitted work to trigger data loss by accident.

## 2026/08/20

- [2026/08/20/09-58-56 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood proposed an alternative design, `git pull --reset [--discard-changes | --autostash]`, that would error out by default when there are uncommitted changes, arguing it would be safer than "git fetch; git reset --hard @{u}" and would let users carry changes over with `--autostash`; he asked whether refusing to reset by default with uncommitted changes would be safe enough, noting uncommitted changes would be protected and unreachable local commits remain retrievable from the reflog.
- [2026/08/20/15-59-18 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano replied that `git pull --ff-only` already serves the "no development in this repository, just keep the latest sources" audience, and said he was not sure of the use case for a working tree managed by discarding uncommitted local changes.
- [2026/08/20/16-43-08 by Artur Bieniek <abieniek@antmicro.com>] Artur Bieniek identified a case `--ff-only` does not cover: when the upstream branch itself is rebased or force-updated, `--ff-only` refuses to update because the histories have diverged; he said `git pull --reset` on a clean working tree would mean "make this checkout match the fetched upstream" while still refusing by default to discard uncommitted changes, and noted he now prefers that distinction over his original `--hard` proposal since the destructive working-tree behavior would no longer be implicit in the primary option.
- [2026/08/20/17-29-08 by Kristoffer Haugsbakk <kristofferhaugsbakk@fastmail.com>] Kristoffer Haugsbakk questioned the need for a local branch in that scenario, saying he just uses the remote-tracking branch (e.g. `origin/main`) instead.

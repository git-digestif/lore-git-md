# Thread deltas

## 2026/08/25

- [2026/08/25/20-46-42 by Andrew Pleeter via GitGitGadget <gitgitgadget@gmail.com>] Andrew Pleeter submitted a patch (PR #2388) adding a `git whoami` builtin that displays resolved author/committer identity and commit signing configuration, supporting --author, --committer, --name, --email, --signing-key, and --verbose flags, with documentation in Documentation/git-whoami.adoc and tests in t/t0015-whoami.sh.
- [2026/08/25/21-24-30 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson advised using a real name in the From and Signed-off-by lines, suggested adding a machine-readable output format (such as key=value pairs) because existing endpoints use translated strings, proposed a possible `-z` option for NUL-terminated output, recommended moving the MOTIVATION section into the commit message, suggested explaining why the command is preferable to `git var`, advised using the `repo` function argument instead of `the_repository`, and asked whether X.509 keys should also be handled; he stated he has no strong need for the command but sees how it could be useful.
- [2026/08/25/21-41-43 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano expressed general reluctance to add more subcommands, noted that the interaction between -a/-c and -n/-e is confusing (with -n, omitting -a defaults to committer, but without -n/-e, committer information requires an explicit -c), and suggested making -a/-c/-n/-e additive so they can be combined.

## 2026/09/01

- [2026/09/01/04-39-44 by Jeff King <peff@peff.net>] Jeff King proposed that instead of adding a new 'git ident' command, 'git var' should be taught to provide broken-down identity components (such as GIT_COMMITTER_NAME, GIT_COMMITTER_EMAIL, GIT_COMMITTER_DATE, and the GIT_AUTHOR_* equivalents), arguing that the proposed command's features—including component selectors, role labels, signing-key resolution, porcelain output, and NUL termination—could instead enhance git-var for reading both idents and its other variables, and that adding another specialized command is undesirable given the existing command count.
- [2026/09/01/05-00-56 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano endorsed Jeff King's assessment, noting that long-time reviewers had already expressed the same sentiment and that Jeff's response was the best among theirs.

## 2026/09/03

- [2026/09/03/02-49-52 by Andrew Pleeter via GitGitGadget <gitgitgadget@gmail.com>] Andrew Pleeter posted PATCH v3 of "var: support broken-down idents, default key, multiple args, and -z", adding GIT_AUTHOR_NAME/EMAIL/DATE, GIT_COMMITTER_NAME/EMAIL/DATE, GIT_DEFAULT_KEY (with GIT_SIGNING_KEY alias), support for multiple variable arguments, and -z NUL termination, with Documentation/git-var.adoc and t/t0007-git-var.sh updated.
- [2026/09/03/17-40-48 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano reviewed the patch: endorsed multiple variable arguments as useful for serious scripting; suggested splitting the synopsis into separate lines for the -l and variable modes; objected to the inherited "of a piece of code" phrasing in the new GIT_AUTHOR_*/GIT_COMMITTER_* doc entries and proposed instead describing them as the authorship information that would be recorded in the resulting commit if 'git commit' were run right now; and suggested describing GIT_DEFAULT_KEY as the key that would be used to sign a commit run now, moving away from "DEFAULT" in the name.
- [2026/09/03/17-40-48 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano raised code-level points: use an enum instead of a char for ident_part's part argument; wrap overly long lines to around ~70 columns; avoid "== 0" numeric comparisons; questioned why default_key checks commit.gpgsign when the signing key would be used either way; proposed a table-driven alias member for GIT_SIGNING_KEY instead of the strcmp special case; questioned the special-casing of "--"; suggested using the parse_options() API instead of the handwritten argument loop; and argued that "git var" with zero variables should output nothing rather than show usage, to be friendlier to scripts.
- [2026/09/03/18-22-46 by Ben Knoble <ben.knoble@gmail.com>] Ben Knoble responded to the empty-argument-list point: noted that 'git var' currently prints usage and exits 129, said lifting the limitation may be sensible but the empty case likely indicates a logic error earlier in the calling script, and judged it probably out of scope for now.

## 2026/09/04

- [2026/09/04/09-11-30 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood reviewed the v3 series, agreeing with Junio's comments, and questioned the GIT_SIGNING_KEY alias for GIT_DEFAULT_KEY, asking whether the alias is needed and what the use case is, since GIT_DEFAULT_KEY is less meaningful than GIT_SIGNING_KEY and scripts signing via git do not need to query the key.
- [2026/09/04/09-11-30 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood pointed out that a key can contain "=", making the `var=value` output format ambiguous, and proposed that with `-z` the code use the same format as `git config list -z` (`printf("%s%c%s%c", var, eol == '\n' ? '=' : '\n', value, eol)`), and suggested checking and matching what `git config list -z` prints for a valueless key ("key\n\0" vs "key\0").
- [2026/09/04/09-11-30 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood suggested breaking out of the argument loop when an arg is "--" or does not begin with '-', treating the rest as variable names, since a plumbing command need not support options interleaved after variable names.
- [2026/09/04/09-11-30 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood noted that multi-valued variables assume values contain no newline, which may not hold for paths, and proposed that with `-z` a '\0' be printed after each value, with a simple fix of using '\0' instead of '\n' to separate individual values so they can be split unambiguously; he also called the ability to specify multiple variables printed unambiguously a really useful improvement.
- [2026/09/04/15-57-33 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano clarified that by "key" Phillip meant "var", noting that `git var` also exposes configuration variables whose three-level names can contain '=', and endorsed the suggestion as excellent.
- [2026/09/04/15-57-33 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano agreed that options should come first and then args per "git help cli", and said he is fine with tightening the option/argument ordering rule at the Git 3.0 boundary.
- [2026/09/04/15-57-33 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano asked what `git config -l` does for multi-valued keys and said `git var` should mimic it, and additionally suggested considering separating the `git config -l` handling out of `git var` with a breaking change at a big version boundary.

Thread identity: patch series extending `git var` to provide unified identity and signing configuration, replacing the earlier `git ident` proposal. Originating author: Andrew Pleeter (via GitGitGadget). Thread type: patch series (implementation of design consensus).

Core problem or goal: provide a unified, scriptable interface to Git’s identity (author/committer names/emails/dates) and signing configuration (GPG/SSH/X.509 keys, `commit.gpgsign` status) by extending the existing `git var` plumbing command. The solution must support both interactive use and scripting, with composable arguments and machine-readable output.

Current status: **implementation under active review, approaching readiness for integration**. The v4 patch addresses all **substantive, high-weight review feedback** from Junio C Hamano and Phillip Wood, including output format ambiguity, argument parsing strictness, and signing key resolution logic. The series remains **not yet merged** and is still in `seen`. The next step is addressing **mechanical improvements** to `-z` output format (alignment with `git config -z`, multi-valued variable handling) and argument parsing before integration. Junio and Phillip Wood have not yet reviewed v4, but the changes align with their prior feedback and the latest design consensus.

Key technical details:
- **Files touched**: `builtin/var.c`, `Documentation/git-var.adoc`, `t/t0007-git-var.sh`.
- **New variables**: `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_AUTHOR_DATE`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `GIT_COMMITTER_DATE`, `GIT_SIGNING_KEY` (resolves the key that would be used for a commit, regardless of `commit.gpgsign` status).
- **Behavior**: supports multiple variable arguments in a single invocation, `-z` for NUL-terminated output (now aligned with `git config -z`: `key\nvalue\0`), and strict argument ordering (options precede variable names, enforced via `parse_options()` with `PARSE_OPT_STOP_AT_NON_OPTION`). Maintains backwards compatibility with existing `git var` usage, though scripts relying on the current output format may need updates for `-z` mode.
- **Code structure**: uses `enum ident_part` for type safety, table-driven variable handling, and Git’s standard argument parsing infrastructure. The `GIT_SIGNING_KEY` variable resolves keys for all signing schemes (GPG/SSH/X.509) without requiring knowledge of the scheme.
- **Output format**: `-z` mode now matches `git config -z` (`key\nvalue\0` or `key\0` for no-value variables), resolving ambiguity when keys contain `=` characters. Multi-valued variables (e.g., `GIT_CONFIG_GLOBAL`) will use `\0` as a separator in `-z` mode, with two proposed approaches: either print the variable name before each value (e.g., `key\nvalue1\0key\nvalue2\0`) or add an extra delimiter after the last value (e.g., `key\nvalue1\0value2\0\0`). Neither approach is finalized, but both are straightforward to implement.
- **Argument parsing**: enforces strict ordering (options before variable names) and rejects ambiguous invocations (e.g., `git var GIT_AUTHOR_NAME -z`). `--` is not currently handled but could be added in a future iteration.
- **Edge cases**: empty variable lists (e.g., `git var` with no args) still exit with code 129 and print usage, though this may be revisited in a future iteration. Signing key resolution ignores `commit.gpgsign` status, as requested by Junio. Multi-valued variables (e.g., paths) are now explicitly handled in `-z` mode to avoid parsing failures when values contain newlines.
- **Test coverage**: comprehensive, including `-z` output format, multi-valued variables, argument ordering, and signing key resolution. Tests verify alignment with `git config -z` behavior for edge cases (e.g., no-value variables, multi-valued variables with newlines).
- **No on-disk format changes or new configuration options**; the patch extends an existing plumbing command predictably.

Open questions and loose ends:
- **Output format**: finalize the handling of multi-valued variables in `-z` mode (either print the variable name before each value or add an extra delimiter after the last value). Both approaches are viable and await implementation in v4.
- **Documentation**: variable descriptions are now clear and concise, but Junio may request further mechanical improvements (e.g., shorter lines, clarifying comments).
- **Code structure**: remaining mechanical improvements (e.g., shorter lines, table-driven alias handling) are expected to be trivial.
- **Usability**: whether to allow empty variable lists (e.g., `git var` with no args) remains deferred to Junio’s broader usability argument. `--` handling is not implemented but could be added later.
- **Long-term CLI rules**: whether Git 3.0 should enforce stricter flag/variable ordering across all commands, and whether `git var` should stop handling `git config -l` output. Neither is a blocker for the current patch.

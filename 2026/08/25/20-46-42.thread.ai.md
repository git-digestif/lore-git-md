Thread identity: patch series extending `git var` to provide unified identity and signing configuration, replacing the earlier `git ident` proposal. Originating author: Andrew Pleeter (via GitGitGadget). Thread type: patch series (implementation of design consensus).

Core problem or goal: provide a unified, scriptable interface to Git’s identity (author/committer names/emails/dates) and signing configuration (GPG/SSH/X.509 keys, `commit.gpgsign` status) by extending the existing `git var` plumbing command. The solution must support both interactive use and scripting, with composable arguments and machine-readable output.

Current status: **active review; polishing phase**. The v6 patch addressed all substantive feedback from Junio’s and Phillip Wood’s reviews of v5, but Phillip’s **high-weight review of v6** identifies **remaining edge cases in error handling, documentation clarity, and test robustness**. The series remains in `seen`; no maintainer has signaled readiness to graduate it to `next`. The patch is **technically sound but requires a final polishing pass** before integration. Key technical blockers from prior rounds (multi-valued variable implementation, output format backward-compatibility, signing key resolution) are resolved, but **minor adjustments** are still needed to address Phillip’s feedback.

Key technical details:
- **Files touched**: `builtin/var.c`, `Documentation/git-var.adoc`, `t/t0007-git-var.sh`.
- **New variables**: `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_AUTHOR_DATE`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `GIT_COMMITTER_DATE`, `GIT_SIGNING_KEY` (resolves the key that would be used for a commit, regardless of `commit.gpgsign` status).
- **Behavior**: supports multiple variable arguments in a single invocation, `-z` for NUL-terminated output (aligned with `git config -z`: `key\nvalue\0`), and strict argument ordering (options precede variable names, enforced via `parse_options()` with `PARSE_OPT_STOP_AT_NON_OPTION`). Maintains backwards compatibility with existing `git var` usage, though scripts relying on the current output format may need updates for `-z` mode.
- **Code structure**: uses `enum ident_part` for type safety, table-driven variable handling, and Git’s standard argument parsing infrastructure. The `GIT_SIGNING_KEY` variable uses Git’s standard `get_signing_key()` (from `gpg-interface.c`) for consistency with actual commit signing.
- **Output format**: `-z` mode matches `git config -z` (`key\nvalue\0` or `key\0` for no-value variables). Multi-valued variables are handled via a `string_list`-based `multiread` callback, avoiding edge cases with empty strings. Single-variable queries and `git var -l` do not print extra delimiters after multi-valued variables, while multi-variable queries include an extra NUL delimiter to disambiguate the stream. Non-`-z` output remains unchanged.
- **Error handling**: prints an empty record (blank line or NUL) for any unset variable and continues processing remaining variables, exiting with code 1 if any variable was unset. Phillip Wood’s review argues this is **overly strict** for scripts expecting non-fatal handling of unset variables (e.g., `GIT_CONFIG_NOSYSTEM`). The current behavior may need adjustment to decouple exit codes from empty values.
- **Multi-valued variables**: implemented via a `string_list`-based `multiread` callback, replacing the prior NUL-delimited string approach. This avoids edge cases with empty strings and aligns with Git’s standard practices. Documentation does not yet explicitly label multi-valued variables (e.g., `GIT_CONFIG_GLOBAL`), which Phillip recommends addressing.
- **Argument parsing**: enforces strict ordering (options before variable names) and rejects ambiguous invocations (e.g., `git var GIT_AUTHOR_NAME -z`). `--` is not currently handled but could be added in a future iteration.
- **Signing key resolution**: uses `get_signing_key()` (from `gpg-interface.c`) to ensure consistency with actual commit signing. Phillip’s review notes the **use case for `GIT_SIGNING_KEY` remains unanswered**—whether the key alone is sufficient for callers to determine the signing mechanism (GPG/SSH/X.509).
- **Documentation**: expanded descriptions of identity variables (`GIT_AUTHOR_NAME`, etc.) to explicitly state they reflect the values that would be used by `git commit`. Phillip recommends **explicitly labeling multi-valued variables** in the man page.
- **Edge cases**: empty variable lists (e.g., `git var` with no args) still exit with code 129 and print usage, though this may be revisited in a future iteration. Multi-valued variables are explicitly handled in `-z` mode to avoid parsing failures when values contain newlines.
- **Test coverage**: comprehensive, including `-z` output format, multi-valued variables, argument ordering, unset variables, and signing key resolution. Tests use `test_cmp()` on files containing NUL bytes, which Phillip notes can cause `diff` to treat them as binary; he recommends using Git’s `nul_to_q` helper to avoid false test failures.
- **No on-disk format changes or new configuration options**; the patch extends an existing plumbing command predictably.

Open questions and loose ends:
- **Error handling**: whether to decouple exit codes from empty values to avoid breaking scripts that expect non-fatal handling of unset variables (e.g., `GIT_CONFIG_NOSYSTEM`). Phillip’s review argues the current behavior is overly strict.
- **Multi-valued variable documentation**: the man page does not explicitly label which variables are multi-valued (e.g., `GIT_CONFIG_GLOBAL`). Phillip recommends addressing this to set user expectations.
- **`GIT_SIGNING_KEY` use case**: whether the key alone is sufficient for callers to determine the signing mechanism (GPG/SSH/X.509). Andrew has not replied to Phillip’s prior question, leaving a **minor but unresolved design question**.
- **Code structure**: Phillip suggests splitting the `string_list`-based refactor of `git_config_val_global()` into a **separate preparatory patch** for clarity, and simplifying the multi-valued variable handling logic.
- **Test robustness**: tests using `test_cmp()` on NUL-containing files may trigger false failures due to `diff` treating them as binary. Phillip recommends using Git’s `nul_to_q` helper.
- **Usability**: whether to allow empty variable lists (e.g., `git var` with no args) remains deferred to Junio’s broader usability argument. `--` handling is not implemented but could be added later.
- **Long-term CLI rules**: whether Git 3.0 should enforce stricter flag/variable ordering across all commands, and whether `git var` should stop handling `git config -l` output. Neither is a blocker for the current patch.

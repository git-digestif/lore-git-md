Thread identity: patch series extending `git var` to provide unified identity and signing configuration, replacing the earlier `git ident` proposal. Originating author: Andrew Pleeter (via GitGitGadget). Thread type: patch series (implementation of design consensus).

Core problem or goal: provide a unified, scriptable interface to Git’s identity (author/committer names/emails/dates) and signing configuration (GPG/SSH/X.509 keys, `commit.gpgsign` status) by extending the existing `git var` plumbing command. The solution must support both interactive use and scripting, with composable arguments and machine-readable output.

Current status: **active review; not ready for integration**. The v5 patch addressed all mechanical and polish-level feedback from Junio C Hamano and Phillip Wood, but Junio’s **substantive review of v5** raises new concerns about **documentation clarity, output format backward-compatibility, error handling robustness, and multi-valued variable implementation**. The series remains **not yet merged** and is still in `seen`. No maintainer has signaled readiness to graduate it; Junio’s latest feedback explicitly blocks integration until the issues are resolved.

Key technical details:
- **Files touched**: `builtin/var.c`, `Documentation/git-var.adoc`, `t/t0007-git-var.sh`.
- **New variables**: `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_AUTHOR_DATE`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `GIT_COMMITTER_DATE`, `GIT_SIGNING_KEY` (resolves the key that would be used for a commit, regardless of `commit.gpgsign` status).
- **Behavior**: supports multiple variable arguments in a single invocation, `-z` for NUL-terminated output (aligned with `git config -z`: `key\nvalue\0`), and strict argument ordering (options precede variable names, enforced via `parse_options()` with `PARSE_OPT_STOP_AT_NON_OPTION`). Maintains backwards compatibility with existing `git var` usage, though scripts relying on the current output format may need updates for `-z` mode.
- **Code structure**: uses `enum ident_part` for type safety, table-driven variable handling, and Git’s standard argument parsing infrastructure. The `GIT_SIGNING_KEY` variable uses Git’s standard `get_signing_key()` (from `gpg-interface.c`) for consistency with actual commit signing.
- **Output format**: `-z` mode matches `git config -z` (`key\nvalue\0` or `key\0` for no-value variables). Multi-valued variables are delimited by internal NUL bytes, and an extra NUL delimiter is printed after the last value when querying multiple variables to disambiguate the stream. Junio’s review flags this as a potential backward-incompatibility and requests clarification on whether non-`-z` output is affected.
- **Error handling**: prints an empty record (blank line or NUL) for any unset variable and continues processing remaining variables, exiting with code 1 if any variable was unset. Junio’s review criticizes the permissive handling of NULL pointers in `ident_part()` after successful `split_ident_line()`, arguing these should trigger `BUG()` to catch programming errors.
- **Multi-valued variables**: implemented as NUL-delimited strings, but Junio notes this could silently skip valid values if an empty string is present. He suggests a more robust design using a `string_list`-based `multiread` callback.
- **Argument parsing**: enforces strict ordering (options before variable names) and rejects ambiguous invocations (e.g., `git var GIT_AUTHOR_NAME -z`). `--` is not currently handled but could be added in a future iteration.
- **Signing key resolution**: uses `get_signing_key()` (from `gpg-interface.c`) to ensure consistency with actual commit signing. The documentation for `GIT_SIGNING_KEY` is praised for clarity, but the identity variable descriptions are criticized as too terse.
- **Edge cases**: empty variable lists (e.g., `git var` with no args) still exit with code 129 and print usage, though this may be revisited in a future iteration. Multi-valued variables are explicitly handled in `-z` mode to avoid parsing failures when values contain newlines.
- **Test coverage**: comprehensive, including `-z` output format, multi-valued variables, argument ordering, unset variables, and signing key resolution. Tests verify alignment with `git config -z` behavior for edge cases (e.g., no-value variables, multi-valued variables with newlines).
- **No on-disk format changes or new configuration options**; the patch extends an existing plumbing command predictably.

Open questions and loose ends:
- **Documentation**: the descriptions for identity variables (`GIT_AUTHOR_NAME`, etc.) must be expanded to explain their purpose and relationship to `GIT_AUTHOR_IDENT`. The `GIT_SIGNING_KEY` description is already sufficient.
- **Output format backward-compatibility**: whether the extra newline/NUL after multi-valued variables in `-z` mode breaks existing scripts, and whether non-`-z` output is affected. Junio requests clarification.
- **Error handling**: whether `ident_part()` should trigger `BUG()` on NULL pointers after successful `split_ident_line()`, or continue with permissive handling.
- **Multi-valued variable implementation**: whether to switch to a `string_list`-based `multiread` callback to avoid edge cases with empty strings.
- **Usability**: whether to allow empty variable lists (e.g., `git var` with no args) remains deferred to Junio’s broader usability argument. `--` handling is not implemented but could be added later.
- **Long-term CLI rules**: whether Git 3.0 should enforce stricter flag/variable ordering across all commands, and whether `git var` should stop handling `git config -l` output. Neither is a blocker for the current patch.

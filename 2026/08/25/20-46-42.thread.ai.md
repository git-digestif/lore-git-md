Thread identity: patch series extending `git var` to provide unified identity and signing configuration, replacing the earlier `git ident` proposal. Originating author: Andrew Pleeter (via GitGitGadget). Thread type: patch series (implementation of design consensus).

Core problem or goal: provide a unified, scriptable interface to Git’s identity (author/committer names/emails/dates) and signing configuration (GPG/SSH/X.509 keys, `commit.gpgsign` status) by extending the existing `git var` plumbing command. The solution must support both interactive use and scripting, with composable arguments and machine-readable output.

Current status: **technically complete but awaiting final documentation and output format clarification**. The v7 patch addresses all prior feedback except for two **documentation-implementation discrepancies** raised by Junio in the latest review: (1) a mismatch between the commit message’s stated exit code behavior and the actual implementation, and (2) lingering ambiguity in the output format for multi-valued variables. The series remains in `seen`; no maintainer has signaled graduation to `next`, but the patch is **ready for integration once the documentation is corrected and Junio confirms the output format trade-off**.

Key technical details:
- **Files touched**: `builtin/var.c`, `Documentation/git-var.adoc`, `t/t0007-git-var.sh`.
- **New variables**: `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_AUTHOR_DATE`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `GIT_COMMITTER_DATE`, `GIT_SIGNING_KEY` (resolves the key that would be used for a commit, regardless of `commit.gpgsign` status).
- **Behavior**: supports multiple variable arguments in a single invocation, `-z` for NUL-terminated output (aligned with `git config -z`: `key\nvalue\0`), and strict argument ordering (options precede variable names, enforced via `parse_options()` with `PARSE_OPT_STOP_AT_NON_OPTION`). Maintains backwards compatibility with existing `git var` usage, though scripts relying on the current output format may need updates for `-z` mode.
- **Code structure**: uses `enum ident_part` for type safety, table-driven variable handling, and Git’s standard argument parsing infrastructure. The `GIT_SIGNING_KEY` variable uses Git’s standard `get_signing_key()` (from `gpg-interface.c`) for consistency with actual commit signing.
- **Output format**: `-z` mode matches `git config -z` (`key\nvalue\0` or `key\0` for no-value variables). Multi-valued variables are handled via a `string_list`-based `multiread` callback, and multi-variable queries print an extra delimiter after multi-valued variables to disambiguate the stream. **Junio’s latest review highlights ambiguity in this design**: scripts must know in advance which variables are multi-valued to parse the output correctly. Junio suggests prefixing each line with the variable name (e.g., `GIT_CONFIG_GLOBAL=value`) to eliminate ambiguity, but this would require scripts to strip prefixes and may break backward compatibility.
- **Error handling**: prints an empty record (blank line or NUL) for any unset variable and continues processing remaining variables. **Exit code behavior**: multi-variable queries exit with code 0 if at least one variable is set (matching Phillip Wood’s recommendation), while single-variable queries exit with code 1 for unset variables. **Junio’s latest review notes a discrepancy**: the commit message claims the command exits with code 1 if *any* requested variable has no value, but the code only enforces this for single-variable queries or empty multi-valued lists. The fix is trivial—either update the documentation or adjust the exit logic.
- **Multi-valued variables**: implemented via a `string_list`-based `multiread` callback, replacing the prior NUL-delimited string approach. **Documentation now explicitly labels multi-valued variables** (e.g., `GIT_CONFIG_GLOBAL`), addressing Phillip Wood’s v6 feedback.
- **Argument parsing**: enforces strict ordering (options before variable names) and rejects ambiguous invocations (e.g., `git var GIT_AUTHOR_NAME -z`). `--` is not currently handled but could be added in a future iteration.
- **Signing key resolution**: uses `get_signing_key()` (from `gpg-interface.c`) to ensure consistency with actual commit signing. **The unresolved question about whether `GIT_SIGNING_KEY` alone is sufficient for callers to determine the signing mechanism (GPG/SSH/X.509) remains**, but this is not a blocker for integration.
- **Documentation**: streamlined to avoid repetitive descriptions of identity variables, linking them to `git commit` once upfront as suggested by Junio. Multi-valued variables are explicitly labeled, and the `-z` output format is clearly documented. **Junio’s latest review requests corrections** to align the documentation with the actual exit code behavior and clarify the output format for multi-valued variables.
- **Edge cases**: empty variable lists (e.g., `git var` with no args) still exit with code 129 and print usage. Multi-valued variables are explicitly handled in `-z` mode to avoid parsing failures when values contain newlines.
- **Test coverage**: comprehensive, including `-z` output format, multi-valued variables, argument ordering, unset variables, and signing key resolution. Tests now use Git’s `nul_to_q` helper to avoid binary comparison errors, addressing Phillip Wood’s v6 feedback.
- **No on-disk format changes or new configuration options**; the patch extends an existing plumbing command predictably.

Open questions and loose ends:
- **Exit code documentation**: the commit message claims the command exits with code 1 if *any* requested variable has no value, but the code only enforces this for single-variable queries or empty multi-valued lists. **Junio requests either a documentation update or a code change to resolve the discrepancy**.
- **Output format for multi-valued variables**: Junio finds the current design ambiguous for scripts, as it requires prior knowledge of which variables are multi-valued. He suggests prefixing each line with the variable name (e.g., `GIT_CONFIG_GLOBAL=value`) to eliminate ambiguity, but this may break backward compatibility. The trade-off remains unresolved.
- **`GIT_SIGNING_KEY` use case**: whether the key alone is sufficient for callers to determine the signing mechanism (GPG/SSH/X.509). Andrew has not replied to Phillip Wood’s prior question, but this is not a blocker for integration.
- **Usability**: whether to allow empty variable lists (e.g., `git var` with no args) remains deferred to Junio’s broader usability argument. `--` handling is not implemented but could be added later.
- **Long-term CLI rules**: whether Git 3.0 should enforce stricter flag/variable ordering across all commands, and whether `git var` should stop handling `git config -l` output. Neither is a blocker for the current patch.

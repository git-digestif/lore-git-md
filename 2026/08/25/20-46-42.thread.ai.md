Thread identity: patch series extending `git var` to provide unified identity and signing configuration, replacing the earlier `git ident` proposal. Originating author: Andrew Pleeter (via GitGitGadget). Thread type: patch series (implementation of design consensus).

Core problem or goal: provide a unified, scriptable interface to Git’s identity (author/committer names/emails/dates) and signing configuration (GPG/SSH/X.509 keys, `commit.gpgsign` status) by extending the existing `git var` plumbing command. The solution must support both interactive use and scripting, with composable arguments and machine-readable output.

Current status: **implementation under active review, approaching readiness for integration**. The v4 patch addresses all **substantive, high-weight review feedback** from Junio C Hamano and Phillip Wood, including output format ambiguity, argument parsing strictness, and signing key resolution logic. The series remains **not yet merged** and is still in `seen`. The next step is addressing **mechanical improvements** to `-z` output format (multi-valued variable handling, alignment with `git config -z`), error behavior, and signing key resolution before integration. Junio and Phillip Wood have not yet reviewed v4, but the changes align with their prior feedback and the latest design consensus.

Key technical details:
- **Files touched**: `builtin/var.c`, `Documentation/git-var.adoc`, `t/t0007-git-var.sh`.
- **New variables**: `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_AUTHOR_DATE`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `GIT_COMMITTER_DATE`, `GIT_SIGNING_KEY` (resolves the key that would be used for a commit, regardless of `commit.gpgsign` status).
- **Behavior**: supports multiple variable arguments in a single invocation, `-z` for NUL-terminated output (aligned with `git config -z`: `key\nvalue\0`), and strict argument ordering (options precede variable names, enforced via `parse_options()` with `PARSE_OPT_STOP_AT_NON_OPTION`). Maintains backwards compatibility with existing `git var` usage, though scripts relying on the current output format may need updates for `-z` mode.
- **Code structure**: uses `enum ident_part` for type safety, table-driven variable handling, and Git’s standard argument parsing infrastructure. The `GIT_SIGNING_KEY` variable resolves keys for all signing schemes (GPG/SSH/X.509) without requiring knowledge of the scheme.
- **Output format**: `-z` mode now matches `git config -z` (`key\nvalue\0` or `key\0` for no-value variables). Multi-valued variables (e.g., `GIT_CONFIG_GLOBAL`) require explicit handling to avoid parsing failures when values contain newlines. Two proposed approaches for `-z` mode: (1) print the variable name before each value (e.g., `key\nvalue1\0key\nvalue2\0`), or (2) add an extra NUL delimiter after the last value (e.g., `key\nvalue1\0value2\0\0`). Neither is finalized; the choice awaits implementation and further review.
- **Argument parsing**: enforces strict ordering (options before variable names) and rejects ambiguous invocations (e.g., `git var GIT_AUTHOR_NAME -z`). `--` is not currently handled but could be added in a future iteration.
- **Signing key resolution**: the current implementation uses a custom `git_signing_key()` function in `builtin/var.c`, which Phillip Wood notes diverges from Git’s standard `get_signing_key()` (from `gpg-interface.c`). This discrepancy may lead to inconsistent behavior between `git var GIT_SIGNING_KEY` and actual commit signing. The documentation should clarify the variable’s intended use.
- **Error handling**: the patch exits with an error if any requested variable is unset, which Phillip Wood argues is unfriendly for scripts requesting multiple variables. A proposed alternative is to print a blank record and continue.
- **Edge cases**: empty variable lists (e.g., `git var` with no args) still exit with code 129 and print usage, though this may be revisited in a future iteration. Multi-valued variables are now explicitly handled in `-z` mode to avoid parsing failures when values contain newlines. A redundant check (`*val`) in multi-valued variable handling was flagged for removal.
- **Test coverage**: comprehensive, including `-z` output format, multi-valued variables, argument ordering, and signing key resolution. Tests verify alignment with `git config -z` behavior for edge cases (e.g., no-value variables, multi-valued variables with newlines).
- **No on-disk format changes or new configuration options**; the patch extends an existing plumbing command predictably.

Open questions and loose ends:
- **Output format**: finalize the handling of multi-valued variables in `-z` mode (either print the variable name before each value or add an extra NUL delimiter after the last value). Both approaches are viable and await implementation and further review.
- **Signing key resolution**: align `git_signing_key()` with `get_signing_key()` to ensure consistency with actual commit signing, or document the divergence if intentional.
- **Error handling**: decide whether to exit on unset variables or print blank records and continue. The latter is more script-friendly.
- **Documentation**: clarify the intended use of `GIT_SIGNING_KEY` and update variable descriptions to reflect the finalized output format.
- **Code structure**: simplify the `show_config()` callback (e.g., always pass a non-NULL `null_term` flag, use `NUL` for clarity), defer variable name validation until variables are read, and remove redundant checks.
- **Usability**: whether to allow empty variable lists (e.g., `git var` with no args) remains deferred to Junio’s broader usability argument. `--` handling is not implemented but could be added later.
- **Long-term CLI rules**: whether Git 3.0 should enforce stricter flag/variable ordering across all commands, and whether `git var` should stop handling `git config -l` output. Neither is a blocker for the current patch.

Patrick Steinhardt’s nine-patch series to refactor ODB alternates handling during repository creation is now complete and under active review. The goal is to simplify the ODB interface by removing the ability to write alternates after repository creation, consolidating all alternates logic into the ODB creation step. This prepares the ground for alternates to become an implementation detail of the ODB backend, giving backends more control over their configuration.

The series has evolved through four iterations, with v4 incorporating all substantive review feedback. The most significant changes were the addition of clarifying documentation for the new repository creation helpers (`create_repository()`, `create_reference_database()`, and `create_object_database()`) and the `reinit_ok` parameter, addressing Justin Tobler’s requests. Patches 5 and 6 consolidated alternates logic for both shared and non-shared local clones into a single code path, fixing a latent bug in worktree alternates handling and ensuring alternates are only added when explicitly requested. Patch 7, the latest addition, implements the core design change: alternates are now written during ODB creation using Git’s standard lockfile API, resolving Junio C Hamano’s earlier security concern about TOCTOU races and concurrent access. The patch handles preexisting alternates (e.g., from templates) by reading and deduplicating them before writing new entries, and reprepares the ODB to activate the new alternates. This paves the way for the final cleanup in patch 9, which removes the `write_alternates()` callback and its supporting infrastructure.

The series is now well-documented, addresses all known correctness issues, and has no remaining technical blockers. Justin Tobler’s forward-looking question about the ODB interface’s long-term flexibility—whether user-facing options like `--shared` should be restricted to the "files" backend or left to the backend’s discretion—remains unresolved but does not impede integration. The lockfile adoption in patch 7 ensures robustness, and the incremental approach taken in patches 5 and 6 has been confirmed correct by Justin. With all patches posted as v4 and no outstanding objections, the series is a strong candidate for integration into Junio’s `next` branch.

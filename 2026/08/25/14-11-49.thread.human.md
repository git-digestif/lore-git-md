This thread is about Patrick Steinhardt’s 9-patch series refactoring how Git handles ODB alternates during repository creation, part of the larger ODB abstraction effort. The goal is to simplify the ODB interface by removing the ability to write alternates after repository creation, consolidating all alternates logic into a single code path during ODB setup. This prepares for alternates to become an implementation detail of the ODB backend, giving backends more control over their configuration.

The series is now at v3, with all patches posted and under review. The key changes since v2 include refactoring `init_db()` into `create_repository()` (patches 1-2), which splits repository initialization into distinct phases for skeleton creation, ODB setup, and refdb setup. This eliminates the need for skip flags and moves command-specific logic out of the core initialization function. Patch 2 specifically defers ODB initialization in `git clone` until after the clone source URI is resolved, addressing forward compatibility with alternate ODB backends and ensuring alternates paths are resolved before ODB setup. Patches 3-6 consolidate alternates logic into `collect_alternates()`, fixing a latent bug in worktree alternates handling and preparing for the lockfile API adoption in patch 7. Patch 7 implements the core design change: alternates are now written during ODB creation via `odb_create_on_disk_options` using Git’s standard lockfile API, ensuring atomic writes and resolving TOCTOU race and concurrent access concerns. Patches 8-9 wire up the new interface and remove the now-unused `write_alternates()` infrastructure.

Justin Tobler and Toon Claes have reviewed parts of the series, with Justin’s feedback being more substantive. His review of patch 1 in v3 endorsed the direction but requested better documentation for the new helpers, which Patrick is expected to address. Junio C Hamano’s earlier concern about the lockfile API in patch 7 was resolved in v2. The series is built on `ps/odb-eagerly-load-alternates` and is foundational for the ODB abstraction effort, though an open question remains about whether user-facing options like `--shared` should be backend-specific or standardized. The series appears uncontroversial and is likely to proceed to integration once remaining ODB-focused contributors review patches 7-9.

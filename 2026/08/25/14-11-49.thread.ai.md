Thread identity: Refactoring ODB alternates handling during repository creation. 8-patch series (`[PATCH v2 0/8]`) by Patrick Steinhardt, part of the ongoing ODB abstraction effort. Thread type: patch series.

Core problem or goal: Remove the ability to write ODB alternates after repository creation, simplifying the ODB interface. Currently, alternates can be added at any time via `odb_source_write_alternate()`, but Git only uses this during initial setup (e.g., `git clone --reference`). The series introduces a new option in `odb_source_create_on_disk()` to handle alternates at creation time, eliminating the need for a separate `write_alternates()` callback. This change prepares for alternates to become an implementation detail of the ODB backend, giving backends more control over their configuration.

Current status: Under review. The series is built on `ps/odb-eagerly-load-alternates` and remains in the review phase. All 8 patches have been posted as v2, addressing the primary blocker from v1: the adoption of Git’s standard lockfile API for writing the `info/alternates` file in patch 6, resolving TOCTOU race and concurrent access concerns raised by Junio C Hamano and Toon Claes. Patches 1-5 refactored reference handling in `git clone`, deferring ODB setup and consolidating alternates logic into `collect_alternates()`. Patch 1 introduced the `INIT_DB_SKIP_ODB` flag to `init_db()` and made `create_object_database()` public, deferring ODB initialization until after URI resolution and alternates collection in `cmd_clone()`. This ensures alternates are written with full context, including any URI rewrites from template `.git/config` files, and addresses forward compatibility with alternate ODB backends that may require object format information at creation time. Patch 2 moved the `setup_reference()` function in `builtin/clone.c` closer to `copy_alternates()` to prepare for patch 3, avoiding a forward declaration. Patch 3 refactored the `--reference` and `--reference-if-able` logic in `git clone` by renaming `setup_reference()` to `collect_alternates()` and changing its behavior to gather alternates paths into a `strvec` instead of immediately writing them to the ODB. This introduced new structures (`struct add_one_alternate_data`) and helper functions (`add_one_alternate()`) to track whether an alternate is required or optional, centralizing alternates logic while preserving existing behavior. Patch 4 extended `collect_alternates()` to handle shared local clones by accepting `src_repo` and `is_local` parameters, resolving the source repository’s common directory and adding its `objects` directory to the alternates list when `--shared` is specified. This removes the manual alternates file update in `clone_local()` for shared clones, deferring it to the unified alternates collection step. Patch 5 completed the consolidation of alternates logic by extending `collect_alternates()` to handle non-shared local clones via the newly renamed `read_alternates()` (formerly `copy_alternates()`), fixing a latent bug in worktree alternates handling where unresolved common directory paths caused failures. This patch also removed the manual alternates file update in `clone_local()` and added test coverage for worktree clones and relative path resolution. A minor code hygiene suggestion from Toon Claes (moving `fclose(in)` before the `out` label) was declined by Patrick Steinhardt, who explained that the current placement reduces fragility for future extensions. Patch 6 implemented the core design change, introducing `odb_create_on_disk_options` to write alternates during ODB creation using the lockfile API (`repo_hold_lock_file_for_update()` and `commit_lock_file()`). The patch reads preexisting alternates (e.g., from template directories) to avoid duplicates, uses `strset` for deduplication, and ensures the ODB is reprepared after writing to activate the new alternates. It also updates `create_object_database()` to pass an empty options struct, preparing for the consolidated alternates logic in later patches. Patch 7 wires up the new mechanism in `cmd_clone()`, removing the last direct use of `odb_add_to_alternates_file()`. The change is mechanical: `create_object_database()` now accepts a `strvec` of alternates paths (collected by `collect_alternates()`) and passes them to the ODB backend via the `odb_create_on_disk_options` struct, consolidating alternates setup into a single step during ODB creation. The patch removes 6 lines from `builtin/clone.c` and updates `setup.c` to pass the alternates `strvec` to `create_object_database()`, while preserving backward compatibility with existing callers (e.g., `init_db()`) via the `NULL` alternates parameter. Justin Tobler’s surface-level review of patch 7 offers brief approval ("This patch looks good") without engaging with technical details, edge cases, or testing. The patch is now ready for integration, pending final review of patch 8. Patch 8 removes the now-unused `odb_source_write_alternates()` function and its supporting infrastructure across all ODB backends, including the lockfile mechanism, which is now acknowledged as unnecessary due to the lockfile API adoption in patch 6. The patch deletes 117 lines across seven files, completing the transition to the new design.

The follow-up discussion between Patrick Steinhardt and Justin Tobler clarifies the architectural implications of the `init_db()` interface. Patrick acknowledges the awkwardness of the growing flag-based interface and proposes a more radical refactoring: lifting repository initialization messages out of `init_db()` entirely (since `git clone` always passes `QUIET` and never allows preexisting repositories) and renaming the function to `create_repository()` to better reflect its narrowed scope. This would move command-specific logic (e.g., printing messages, handling preexisting repos) to the commands themselves, simplifying the interface. Patrick also explains that deferring `setup_reference()`—which configures alternates, not refs—is necessary because alternates can only be written after the ODB exists. The commit message for patch 1 will be updated to clarify this alternates-specific purpose. The discussion is forward-looking and may influence future iterations of the series or broader refactoring of repository initialization, though no immediate code changes are proposed.

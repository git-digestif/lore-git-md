Here’s the updated human-readable summary for a developer catching up:

This thread is about an inconsistency in Git’s branch-name validation: porcelain commands like `git checkout -b` and `git switch -c` allow creating a branch named `@`, even though `@` is rejected by `git check-ref-format` and can’t be checked out afterward (since `@` is interpreted as `HEAD`). The debate hinges on whether to tighten validation to prevent accidental branch creation or preserve `@` as a convenient shorthand for `HEAD` in complex expressions like `git range-diff long-branch-name{^..otherbranch,..@}`.

The discussion remains split, but Junio C Hamano has now weighed in firmly against allowing `@` as a branch name, calling its use a "bad habit" that should be unlearned. This aligns with the safety argument (preventing user mistakes) but doesn’t address the usability trap—once created, the branch can’t be checked out via porcelain commands. Bence Csókás, who reported the issue, argues for preserving `@` as a shorthand, citing real-world usage (74 instances in their bash history). Jeff King (Peff) previously suggested a targeted fix: reject bare `@` in `--branch` mode while allowing compound names like `foo@bar`, but no patch has been proposed yet.

Key participants include D. Ben Knoble (who confirmed the inconsistency and highlighted the usability trap) and Kristoffer Haugsbakk (who initially cited Junio’s 2024 stance on deprecating `@` but later clarified it was incomplete). The thread is still under review, with no clear resolution. The next step will likely depend on whether someone submits a patch to tighten validation, and how it balances safety with the convenience argument.

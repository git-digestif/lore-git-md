This thread is about an inconsistency in Git’s branch name validation: porcelain commands like `git checkout -b` and `git switch -c` allow creating a branch named `@`, even though `@` is rejected by `git check-ref-format` and cannot later be checked out (since `@` is interpreted as `HEAD`). The discussion pits convenience—using `@` as a shorthand for `HEAD` in complex expressions—against stricter validation to prevent accidental branch creation and usability traps.

Junio C Hamano, the maintainer, has taken a firm stance against allowing `@` as a branch name, calling it a "bad habit" that violates Git’s ref name rules. He dismisses workarounds (like `git symbolic-ref refs/H HEAD`) as insufficient and insists the only resolution is to reject bare `@` in branch names while preserving its use in compound names (e.g., `foo@bar`). This aligns with Jeff King’s earlier suggestion to treat `@` like `HEAD`, which is already rejected in `--branch` mode for porcelain safety. Bence Csókás and D. Ben Knoble argue for preserving `@` as a shorthand, citing its practicality in workflows, but Junio’s opposition makes a compromise unlikely.

The thread remains under review with no patch proposed yet. The next step is a targeted fix to tighten `--branch` validation in `refs.c` and `check-ref-format.c`, which Junio would likely accept if it cleanly rejects bare `@`. The usability trap (inability to check out `@` via porcelain commands) is acknowledged but not addressed—Junio’s focus is on eliminating the inconsistency at its source. No backwards compatibility issues are expected, as the change would affect porcelain safety rather than low-level ref storage.

This thread is about an inconsistency in Git’s branch name validation: porcelain commands like `git checkout -b` and `git switch -c` allow creating a branch named `@`, even though `@` is rejected by `git check-ref-format` and cannot later be checked out via those same commands (since `@` is interpreted as `HEAD`). The discussion pits convenience—`@` is a useful shorthand for `HEAD` in complex expressions—against consistency and usability.

The debate remains split. Bence Csókás, who reported the issue, argues that `@` is a valuable shorthand, backed by real-world usage data (74 instances in their bash history). D. Ben Knoble supports this view, defending shorthands as practical for interactive workflows. However, Junio C Hamano, the maintainer, has taken a firm stance against allowing `@` as a branch name, calling it a "bad habit" that conflicts with Git’s ref name rules and creates a usability trap. Jeff King (Peff) has proposed a middle ground: reject bare `@` while preserving compound names like `foo@bar`, aligning with precedent (e.g., `HEAD` is already rejected in `--branch` mode).

No patch has been proposed yet, and the thread is at an impasse. Junio’s opposition makes it unlikely the status quo will change without a compromise or a shift in his position. The next step may hinge on whether someone submits a patch that tightens validation for bare `@` while preserving its use in compound names. Until then, the inconsistency remains, and users are left with workarounds like `git symbolic-ref refs/H HEAD` to check out such branches.

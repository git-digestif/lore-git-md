This thread is about an inconsistency in Git’s branch name validation: porcelain commands like `git checkout -b` and `git switch -c` allow creating a branch named `@`, but this branch can’t later be checked out via the same commands because `@` is interpreted as `HEAD`. The root issue is that `git check-ref-format --branch` incorrectly accepts `@` as a valid branch name, while `git check-ref-format` (without `--branch`) rejects it.

The discussion remains split on whether to tighten validation to reject `@` as a branch name. Junio C Hamano, the maintainer, has taken a firm stance against allowing `@` as a branch name, calling its use a "bad habit" that should be unlearned. This aligns with the stricter validation argument, which prioritizes consistency and porcelain safety. On the other side, Bence Csókás and D. Ben Knoble defend `@` as a useful shorthand for `HEAD` in complex expressions, backed by Csókás’s real-world usage data (74 instances of `@` in their bash history). Jeff King (Peff) has proposed a targeted fix: reject bare `@` as a branch name while preserving its use in compound names like `foo@bar`, citing precedent (e.g., `HEAD` is already rejected in `--branch` mode).

No patch has been proposed yet, and the usability trap—being unable to check out a branch named `@` via porcelain commands—remains unaddressed. Kristoffer Haugsbakk recently shared a workaround (`git symbolic-ref refs/H HEAD`) to sidestep the issue, but this doesn’t resolve the underlying inconsistency. The next step will likely depend on whether someone submits a patch to tighten `--branch` validation in `check-ref-format.c`. Until then, the thread is stalled on the design trade-off between convenience and safety.

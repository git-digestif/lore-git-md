Subject: Inconsistent branch name validation in porcelain commands
Series version: N/A (bug report / design discussion)
Originating author: Bence Csókás
Thread type: bug report / design discussion

Core problem or goal
Git’s porcelain commands (`checkout -b`, `switch -c`, `branch`) allow creating a branch named `@`, even though `@` is rejected by `git check-ref-format` as an invalid ref name. The inconsistency stems from `git check-ref-format --branch` incorrectly accepting `@` as valid, creating a usability trap: the branch cannot be checked out afterward (due to `@` being interpreted as `HEAD`) but can be deleted. The discussion centers on whether the convenience of `@` as a shorthand for `HEAD` in complex expressions (e.g., `git range-diff long-branch-name{^..otherbranch,..@}`) outweighs the risk of accidental branch creation and the usability trap of being unable to check out `@` via porcelain commands.

Current status
Under review. No patch proposed yet. The thread remains split on the design trade-off, but Junio C Hamano’s maintainer authority now unambiguously opposes preserving `@` as a branch name, framing its use as a "bad habit" that violates Git’s ref name rules and introduces inconsistency. The convenience argument (supported by Bence Csókás and D. Ben Knoble) remains a counterpoint but is explicitly rejected by Junio. The usability trap (inability to check out `@` via porcelain commands) has been acknowledged but not addressed beyond Kristoffer Haugsbakk’s workaround (`git symbolic-ref refs/H HEAD`).

Key technical details
- Commands affected: `git checkout -b @`, `git switch -c @`, `git branch @`
- Validation discrepancy: `git check-ref-format` (without `--branch`) rejects `@`; `git check-ref-format --branch` accepts it
- On-disk consequence: branch ref `refs/heads/@` is created but cannot be checked out via porcelain commands (e.g., `git switch @` fails, interpreting `@` as `HEAD`)
- Workaround: `git symbolic-ref refs/H HEAD` allows `git switch H` as a substitute for `git switch @`
- Subsystem: ref name validation logic in `refs.c` and `check-ref-format.c`
- Usability impact: manual manipulation of `.git/HEAD` or the workaround above is required to check out the branch; `@` remains useful as a shorthand in complex expressions (e.g., `git range-diff long-branch-name{^..otherbranch,..@}`)
- Design precedent: `--branch` mode already rejects `HEAD` as a branch name for porcelain safety; bare `@` could be treated similarly while preserving compound names like `foo@bar`
- Historical context: Junio C Hamano’s 2024 stance on deprecating bare `@` as a synonym for `HEAD` was clarified as incomplete; his current position is now unambiguous in opposing `@` as a branch name.

Open questions and loose ends
- Implementation: exact patch to tighten `--branch` validation for bare `@` (no patch proposed yet). Junio’s stance suggests such a patch would be welcomed if it rejects bare `@` while preserving `@` in compound names (e.g., `foo@bar`), but the convenience argument remains explicitly opposed.
- Backwards compatibility: no known breakage expected if the change targets porcelain safety, but the convenience argument (defended by Csókás and Knoble) may still influence the timeline or design. Junio’s rejection of the trade-off reduces the likelihood of a compromise.
- Design resolution: whether to proceed with stricter validation (reject bare `@`) despite the convenience argument, or await a patch that addresses the usability trap without preserving the problematic shorthand. The thread is unlikely to advance without a targeted fix or a shift in Junio’s position.

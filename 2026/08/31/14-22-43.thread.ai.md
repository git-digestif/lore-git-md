Subject: Inconsistent branch name validation in porcelain commands
Series version: N/A (bug report / design discussion)
Originating author: Bence Csókás
Thread type: bug report / design discussion

Core problem or goal
Git’s porcelain commands (`checkout -b`, `switch -c`, `branch`) allow creating a branch named `@`, even though `@` is rejected by `git check-ref-format` as an invalid ref name. The inconsistency stems from `git check-ref-format --branch` incorrectly accepting `@` as valid, creating a usability trap: the branch cannot be checked out afterward (due to `@` being interpreted as `HEAD`) but can be deleted. The discussion centers on whether the convenience of `@` as a shorthand for `HEAD` in complex expressions (e.g., `git range-diff long-branch-name{^..otherbranch,..@}`) outweighs the risk of accidental branch creation and the usability trap of being unable to check out `@` via porcelain commands.

Current status
Under review. No patch proposed yet. Junio C Hamano’s maintainer authority now unambiguously opposes preserving `@` as a branch name, framing its use as a "bad habit" that violates Git’s ref name rules and introduces inconsistency. His latest reply dismisses Kristoffer Haugsbakk’s workaround (`git symbolic-ref refs/H HEAD`) as insufficient, reinforcing that the only acceptable resolution is to reject bare `@` as a branch name outright while preserving `@` in compound names (e.g., `foo@bar`). The convenience argument (supported by Bence Csókás and D. Ben Knoble) remains explicitly rejected, and the thread is unlikely to advance without a patch that aligns with Junio’s position.

Key technical details
- Commands affected: `git checkout -b @`, `git switch -c @`, `git branch @`
- Validation discrepancy: `git check-ref-format` (without `--branch`) rejects `@`; `git check-ref-format --branch` accepts it
- On-disk consequence: branch ref `refs/heads/@` is created but cannot be checked out via porcelain commands (e.g., `git switch @` fails, interpreting `@` as `HEAD`)
- Workaround: `git symbolic-ref refs/H HEAD` allows `git switch H` as a substitute for `git switch @` (dismissed by Junio as insufficient)
- Subsystem: ref name validation logic in `refs.c` and `check-ref-format.c`
- Usability impact: manual manipulation of `.git/HEAD` or the workaround above is required to check out the branch; `@` remains useful as a shorthand in complex expressions (e.g., `git range-diff long-branch-name{^..otherbranch,..@}`)
- Design precedent: `--branch` mode already rejects `HEAD` as a branch name for porcelain safety; bare `@` could be treated similarly while preserving compound names like `foo@bar`
- Historical context: Junio’s 2024 stance on deprecating bare `@` as a synonym for `HEAD` was clarified as incomplete; his current position is now unambiguous in opposing `@` as a branch name.

Open questions and loose ends
- Implementation: exact patch to tighten `--branch` validation for bare `@` (no patch proposed yet). Junio’s stance suggests such a patch would be welcomed if it rejects bare `@` while preserving `@` in compound names (e.g., `foo@bar`).
- Backwards compatibility: no known breakage expected if the change targets porcelain safety, as the inconsistency is a usability trap rather than a functional regression.
- Design resolution: whether to proceed with stricter validation (reject bare `@`) despite the convenience argument, or await further discussion. Junio’s rejection of the trade-off makes the former the likely path forward.

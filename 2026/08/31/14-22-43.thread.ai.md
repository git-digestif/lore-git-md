Subject: Inconsistent branch name validation in porcelain commands
Series version: N/A (bug report / design discussion)
Originating author: Bence Csókás
Thread type: bug report / design discussion

Core problem or goal
Git’s porcelain commands (`checkout -b`, `switch -c`, `branch`) allow creating a branch named `@`, even though `@` is rejected by `git check-ref-format` as an invalid ref name. The inconsistency stems from `git check-ref-format --branch` incorrectly accepting `@` as valid, creating a usability trap: the branch cannot be checked out afterward (due to `@` being interpreted as `HEAD`) but can be deleted. The discussion centers on whether the convenience of `@` as a shorthand for `HEAD` in complex expressions (e.g., `git range-diff long-branch-name{^..otherbranch,..@}`) outweighs the risk of accidental branch creation and the usability trap of being unable to check out `@` via porcelain commands.

Current status
Under review. No patch proposed yet. The thread remains split on the design trade-off, but Junio C Hamano has now taken a clear stance against preserving `@` as a branch name, describing its use as a "bad habit" that needs "unlearning." This aligns with the stricter validation argument (prioritizing safety over convenience) and adds maintainer weight to that position. The convenience argument, supported by Bence Csókás’s real-world usage data (74 instances of `@` in their bash history), remains a counterpoint but is now explicitly opposed by Junio. The usability trap (inability to check out `@` via porcelain commands) has not been addressed by Junio’s reply.

Key technical details
- Commands affected: `git checkout -b @`, `git switch -c @`, `git branch @`
- Validation discrepancy: `git check-ref-format` (without `--branch`) rejects `@`; `git check-ref-format --branch` accepts it
- On-disk consequence: branch ref `refs/heads/@` is created but cannot be checked out via porcelain commands (e.g., `git switch @` fails, interpreting `@` as `HEAD`)
- Subsystem: ref name validation logic in `refs.c` and `check-ref-format.c`
- Usability impact: manual manipulation of `.git/HEAD` is required to check out the branch; `@` remains useful as a shorthand in complex expressions (e.g., `git range-diff long-branch-name{^..otherbranch,..@}`)
- Design precedent: `--branch` mode already rejects `HEAD` as a branch name for porcelain safety; bare `@` could be treated similarly while preserving compound names like `foo@bar`
- Historical context: Junio C Hamano’s 2024 stance on deprecating bare `@` as a synonym for `HEAD` was clarified as incomplete; his current position is now unambiguous in opposing `@` as a branch name.

Open questions and loose ends
- Implementation: exact patch to tighten `--branch` validation for bare `@` (no patch proposed yet). Junio’s stance suggests such a patch would be welcomed, but it must address the convenience argument (e.g., by preserving `@` in compound names like `foo@bar`).
- Backwards compatibility: no known breakage expected if the change targets porcelain safety, but the convenience argument (now explicitly opposed by Junio) may still influence the timeline or design.
- Design resolution: whether to proceed with stricter validation (reject bare `@`) despite the convenience argument, or seek a compromise (e.g., preserving `@` in compound names while rejecting it as a standalone branch name).

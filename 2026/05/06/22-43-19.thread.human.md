This thread is about Johannes Schindelin’s RFC patch series adding merge commit support to `git history`, a feature introduced in Git 2.54. The series extends the tool to handle merges by using a three-way merge composition algorithm, but Phillip Wood has proposed an optimization for single-parent rebases that is now being considered alongside the original approach.

The latest development is a substantive review from Philippe Blain identifying a regression in how boundary commits are handled. When replaying a merge whose second parent is outside the rewrite range (e.g., via `M^!`), the current implementation incorrectly maps that parent to the `--onto` target, altering the merge base and triggering unnecessary conflicts. This breaks the expected behavior of preserving manual merge resolutions when only the commit message of a merge’s first parent is amended. Blain’s feedback is actionable: he suggests adjusting the pre-seeding logic to exclude negative revisions that aren’t boundary commits and improving documentation. This bug affects a core use case and will likely need to be fixed before the series can progress.

Other key points include the resolution of DSL syntax questions (thanks to Toon Claes) and ongoing work to integrate Wood’s single-parent-rebase optimization. The series touches `replay.c`, `builtin/historian.c`, and test infrastructure, with extensive coverage in `t3454-history-merges.sh`. No formal reviews (Reviewed-by/Acked-by) have been given yet, but Blain’s feedback and Wood’s optimization proposal are shaping the next iteration. The thread remains in RFC stage, with no merge status reported.

This is a substantive CI/build system review reply in the ongoing thread about GitHub Actions failure reporting improvements. Phillip Wood identifies a critical usability regression in the patch series: the new annotation links on the GitHub Actions summary page **only work if the test file was modified in the same pull request**, otherwise they point to a broken or irrelevant location. This undermines the patch's core goal of providing actionable failure links.

The issue surfaces when a test fails in a file that was not changed by the patch under test. In the current (unpatched) behavior, clicking an annotation takes the user to the test output for the failed job, which is useful. With the patch applied, the link instead points to the file diff view, which is useless if the file was not modified. Phillip demonstrates this with concrete examples: in the v3 CI run, clicking the `t1022` annotation fails to navigate to the test output, while a recent unpatched run correctly links to the job output.

This is a **functional regression** that directly contradicts the patch's stated purpose. The problem is not theoretical: Phillip provides live GitHub URLs showing the broken behavior in the wild. The review is substantive and tested, with clear reproduction steps and comparative analysis of old vs. new behavior. No new technical issues are raised beyond this usability flaw, but the finding is sharp and actionable.

The ball is now in Harald Nordgren's court to either revert the annotation link logic or find a way to make the links context-aware (e.g., falling back to job output when the file was not modified). Until this is addressed, the series cannot be considered ready for `next`, despite Junio's earlier approval.

This is a **design discussion** about the proposed "limbo" object-format state for empty Git repositories, continuing the RFC thread between Jeff King and brian m. carlson.

Jeff responds to brian’s compatibility and policy concerns with a concrete proposal: introduce a new capability (`magic-limbo`) to signal limbo support, while advertising `object-format=sha1` for backward compatibility. This would allow newer clients to recognize the limbo state while older clients (2.29+) default to SHA-1, avoiding the breakage brian identified. Jeff acknowledges that the choice of SHA-1 as the advertised format is intentional—since Git 3.0’s SHA-256 transition hasn’t happened yet, users with SHA-256 repos are assumed to be deliberate and can configure the server accordingly.

On the question of multiple `object-format` directives, Jeff dismisses the idea due to potential corner cases, reinforcing the need for a dedicated capability. Regarding policy enforcement (e.g., disallowing SHA-1), he treats it as a forge-level concern, not a Git protocol one, suggesting UI controls (e.g., a tri-state selector in GitHub’s repo creation flow) rather than config-driven solutions. The discussion now hinges on whether this capability-based approach resolves the compatibility issues while leaving room for server-side policy hooks. Key technical details for follow-up include the exact wire protocol changes, atomicity of the state transition, and how forges might expose limbo configuration to users.

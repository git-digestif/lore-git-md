Ben Knoble responds to Alejandro Colomar’s question about how to robustly check whether `git bisect` has narrowed the range to a single commit without relying on the porcelain `git bisect visualize` command. Ben suggests using `git rev-list` to count the commits between the `bisect/bad` ref and all `bisect/good-*` refs, which would avoid the instability of porcelain commands. He notes that this approach would not account for skipped commits (which could leave multiple commits in the range), but observes that Alejandro’s script does not use skipping, so this limitation is not a problem here.

The reply is practical and directly addresses the original question, offering a concrete alternative that aligns with Git’s plumbing interfaces. It does not propose a patch or engage in deeper design discussion, but it provides a clear, actionable suggestion for scripting against `git bisect` in a version-stable way. No objections or follow-up questions are raised in this email.

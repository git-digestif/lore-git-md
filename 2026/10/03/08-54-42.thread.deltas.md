## 2026/10/05

- [2026/10/05/06-57-36 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt objected to Carlisle T. Hamlin's earlier reply as adversarial to a simple question, stating the community should be welcoming and that such replies drive people away.
- [2026/10/05/06-57-42 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt explained that in a shallow clone the boundary commit (B) is rewritten to have no parents, so it looks like a root commit that added all files at once, and reverting it therefore deletes everything; he corrected the original understanding by noting Git considers the empty root tree valid (so a commit with no files can be created) but never writes an empty sub-tree, confirmed there is no general safeguard warning when all tracked files are deleted (though untracked data is treated carefully since committed data is trivially restorable), and agreed Git should warn about—or even refuse by default—editing a shallow boundary commit, with an override for the rare intended case.
- [2026/10/05/10-41-31 by Matt Hunter <m@lfurio.us>] Matt Hunter asked, as a separate sideline question, whether shallow boundary commits could be munged to preserve original commit IDs in the clone so that a future fast-forward pull still works.
- [2026/10/05/16-38-53 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano answered that something similar to "graft" (and now "replace") is done under the hood to stop history traversal from seeing the true parents of boundary commits, and since the commit object itself (its "parent" header lines) is not modified, object names are unaffected.
- [2026/10/05/17-35-36 by Sphinx <sphinx9692@gmail.com>] Sphinx thanked Patrick Steinhardt, revised their initial view that the empty tree was the unsafe part, and confirmed the surprising behavior stems from the shallow boundary, along with the absence of a safeguard for editing shallow boundary commits and the possibility of warning or refusing such operations by default.

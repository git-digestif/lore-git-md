This is a follow-up in the `git brebase` RFC thread, offering a counterproposal to integrate the incremental rebase functionality directly into `git rebase` rather than introducing a new command. Nico Williams argues that the behavior proposed in `git brebase`—automatically bisecting to the first conflicting commit and guiding the user through resolution—should be the *default* behavior of `git rebase` when conflicts arise, not a separate tool or flag.

The email suggests two concrete changes to `git rebase`:
1. When a rebase encounters conflicts, it should use bisection to identify the first upstream commit that introduces a conflict, stop there, and instruct the user to resolve conflicts and run `git rebase --continue` until the rebase completes. This mirrors `git brebase`'s core workflow but integrates it into the existing command.
2. When `git rebase --continue` finishes a segment, it should automatically resume the rebase against the original target committish (e.g., `$upstream/$branch`) if the rebase is not yet complete. This would require recording the target committish in the rebase state, a small but non-trivial change to the rebase machinery.

Nico frames this as a usability improvement, arguing that the proposed behavior would feel "very natural" and that `git rebase` "should always have been this useful." He acknowledges the need for a `--direct` flag to disable the new behavior but leans toward making it the default eventually, possibly after shipping it as an opt-in feature first. The tone is enthusiastic, but the proposal is still speculative—Nico explicitly asks whether there are "good reasons not to" pursue this approach.

This reply shifts the discussion from evaluating `git brebase` as a standalone tool to considering whether its core functionality belongs in `git rebase` itself. The implications are significant: integrating this behavior into `git rebase` would avoid fragmenting the user experience across multiple commands but would require careful design to avoid breaking existing workflows. The proposal touches on rebase internals (state management, conflict handling) and would likely require C changes, unlike the shell-based `git brebase`. No implementation details or edge cases (e.g., merge commits, `--rebase-merges`) are addressed yet, so this remains a high-level design suggestion.

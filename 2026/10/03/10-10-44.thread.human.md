This thread is a user support discussion about finding a robust, version-independent plumbing command to check whether `git bisect` has narrowed the search to a single commit—including handling skipped commits. Alejandro Colomar started the conversation after realizing that common porcelain-based workarounds (like `git bisect visualize --oneline | wc -l`) could break across Git versions.

So far, two plumbing-based approaches have been proposed but remain unconfirmed. The first, a `git rev-list` pipeline using `refs/bisect/good-*`, `refs/bisect/bad`, and `refs/bisect/skip-*` refs, was acknowledged to be incomplete because it doesn’t account for the bisect algorithm’s internal handling of skipped commits. The second, using `git rev-list --bisect` and related options, was suggested by Kristoffer Haugsbakk but hasn’t been tested for this use case. Alejandro later shared a working one-liner (`git refs list | grep refs/bisect/ | sed '/good/s/^/^/' | cut -f1 -d' ' | xargs git rev-list`) that dynamically constructs the candidate set, but even this fails to fully capture the bisect state. As a fallback, he proposed using `git bisect run` with a temporary script, though this sidesteps the original plumbing question.

No maintainer or domain expert has weighed in to clarify whether the `--bisect` family of options can reliably report the number of remaining candidates, including skipped commits. The thread remains open, with the core question still unresolved.

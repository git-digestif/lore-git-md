This is an RFC follow-up from Alejandro Colomar refining his proposal for `git brebase`, a new tool for incremental rebasing of complex histories. The email responds to earlier feedback (notably from Nico Williams and Ben Boeckel) and presents a significantly evolved design that now claims to surpass `git imerge` in both simplicity and power for workflows involving merge commits, arbitrary commit skipping, and semantic conflict detection.

The key advancement here is a concrete 164-line shell script implementation that demonstrates the core workflow: using `git bisect` to locate the first conflicting commit with the target branch, then performing a rebase up to that point with optional pre- and post-execution hooks for filtering commits and validating semantic correctness. The script transparently passes most flags to `git rebase`, making it nearly a drop-in replacement for simple cases while adding three novel features: `--pre-exec` (skip commits before rebasing), `--post-exec` (validate after each step), and native handling of merge commits via `--rebase-merges`-like behavior.

Colomar provides a detailed walkthrough of how `git brebase` handles complex branch topologies (e.g., trees of branches) by resolving conflicts from leaves to root, a workflow he claims reduces redundant conflict resolution compared to `git imerge`. The email also clarifies limitations: no direct merge commit creation (though a manual workaround exists) and no persistent conflict history, which the author frames as an advantage for keeping intermediate histories clean. The shell-based implementation is rudimentary (e.g., only supports `--foo=bar` syntax) but functional, and the author explicitly invites feedback on whether this should be a new Git command or a `git rebase` flag.

This iteration feels more mature than the initial RFC, with a working prototype and clearer positioning against `git imerge`. The design choices (e.g., relying on `git bisect`, using exit code 125 for skipping) are technically sound but may raise questions about robustness for production use. The proposal’s strength lies in its simplicity and focus on incremental, interruptible rebasing, though the lack of persistent conflict history could be a dealbreaker for some workflows.

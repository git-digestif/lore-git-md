This is a substantive review comment on the Rust version requirement in Johannes Schindelin’s Rust-based SHA-1 backend series. Brian M. Carlson raises a policy-level concern: the series requires Rust 1.87, but Git’s `Cargo.toml` currently declares compatibility with Rust 1.49.0, and the project’s informal policy (aligned with Debian stable) targets Rust 1.85.1. The mismatch risks breaking builds for users on older Rust toolchains, even though the feature is optional.

Carlson’s objection is not technical but procedural. He argues that any version bump should be handled in a separate policy discussion, not buried in a feature series. He also notes that the original goal of supporting gccrs (a GCC-based Rust compiler) is now unrealistic given its slow progress and Git 3.0’s impending release. His tone is measured but firm: the version requirement is a blocker unless addressed through a deliberate policy update.

The review is substantive because it engages with project-wide conventions (Debian stable alignment) and long-term toolchain support, not just the patch’s immediate functionality. It does not question the Rust backend’s performance or correctness, but it does challenge the series’ readiness for integration without broader consensus on Rust version policy. This is likely to spark follow-up discussion about whether the performance gains justify a version bump, or whether the series should be revised to target Rust 1.85.1.

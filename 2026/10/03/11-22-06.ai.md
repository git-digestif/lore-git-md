This patch targets Zsh completion in Git's contrib area. It modifies `git-completion.zsh` to exclude files that have already been specified as arguments from further completion candidates, aligning Git's bundled Zsh completion with the behavior of Zsh's own `_git` completion function.

The change is small and focused: it introduces a local array `__git_file_exclude` that collects all file arguments already present in the command line (excluding the current word being completed), then passes this array to `compadd` via the `-F` option to filter out those files. The patch touches only the Zsh-specific completion script (`contrib/completion/git-completion.zsh`) and does not affect Bash completion or core Git functionality.

The motivation is clear: when completing file arguments in commands like `git add`, users expect not to see files they have already specified. The example in the commit message (`git add aa a<tab>` with untracked files `aa` and `ab`) illustrates the problem: without this patch, both `aa` and `ab` would be offered as completions, but with it, only `ab` appears, matching the behavior of Zsh's native `_git` completion.

The implementation is straightforward and idiomatic for Zsh scripting. It uses Zsh's array manipulation features (`${words[2,-1]:#${words[CURRENT]}}`) to build the exclusion list and leverages `compadd -F` to filter candidates. The patch is well-contained, with no changes outside the Zsh completion script.

This is a user-interface polish patch rather than a bugfix or feature. It addresses a minor but observable inconsistency between Git's bundled Zsh completion and the completion function shipped with Zsh itself. The change is unlikely to be controversial, though it may prompt discussion about whether Git's completion should precisely match Zsh's native behavior or maintain its own conventions.

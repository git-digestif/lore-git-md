This is a reply in an ongoing design discussion about Git’s behavior with shallow clones and empty trees.

Carlisle T. Hamlin responds to Sphinx’s question about whether Git should warn users when a destructive operation (like `git revert` or `git restore`) on a shallow clone results in an empty working tree. Hamlin argues that Git should not add such warnings, framing it as a matter of user responsibility. He suggests that anyone capable of setting up or operating a Git repository should understand the consequences of removing the only commit in their shallow clone, and that adding safeguards would be overly paternalistic—both to developers and users.

The reply is opinionated but does not engage with the technical specifics of shallow clone internals or existing safeguards in Git. It reflects a common perspective in the Git community: that the tool should prioritize flexibility and minimal interference over hand-holding for edge cases. However, it does not address whether there are precedents for warnings in similar scenarios (e.g., `git reset --hard` or `git checkout` to a divergent branch) or how this might interact with Git’s broader design philosophy. The tone is informal and dismissive of the concern, which may limit its influence on any eventual consensus.

No code or patches are proposed, and the discussion remains in the early stages. If this thread continues, future replies may clarify whether Hamlin’s view aligns with maintainers’ expectations or if there’s room for a middle ground (e.g., configurable warnings). For now, this email adds a voice to the "no safeguards needed" side of the debate.

This is a **design discussion** continuing the RFC thread on the proposed "limbo" object-format state for empty Git repositories. Brian M. Carlson responds to Jeff King's `magic-limbo` capability proposal, raising two key points: compatibility with future hash algorithms and the urgency of Git 3.0's SHA-256 transition.

Brian argues that the server should advertise *both* SHA-1 and SHA-256 (e.g., via `object-format=sha256` and `alt-object-format=sha1`) to explicitly signal support for SHA-256, rather than relying on a single advertised format. This would also accommodate potential future hash algorithms. He cites a 2023 fix for a multi-valued capability parsing bug (aa962fef27) as evidence that modern Git versions (2.41+) can safely handle multiple `object-format` directives, suggesting this approach is viable if the project is willing to drop support for versions with only experimental SHA-256.

On timing, Brian strongly opposes delaying Git 3.0's SHA-256-by-default transition until the limbo feature is implemented. He notes that the transition was announced in 2024, and the lack of progress on limbo should not block it. His position reflects a priority on moving users away from SHA-1 as soon as possible, even if it means accepting some usability friction for new repositories. This contrasts with Jeff's earlier suggestion to tie the two together.

The discussion also touches on policy enforcement: Brian disagrees with Jeff's view that this is purely a forge-level concern, advocating instead for Git-native support (e.g., via config or command-line options) to handle cases where repositories are modified via APIs or non-push commands. This would ensure consistent behavior regardless of how the repository is accessed. The thread now hinges on whether the project will adopt a multi-format advertisement approach and how it will balance the limbo feature's complexity against the urgency of the SHA-256 transition.

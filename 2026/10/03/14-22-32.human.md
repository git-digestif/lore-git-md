This is a **design discussion** about the proposed "limbo" object-format state for empty Git repositories, continuing the RFC thread between Jeff King and brian m. carlson.

brian m. carlson pushes back on two key aspects of Jeff’s `magic-limbo` proposal. First, he argues that the server must advertise *both* SHA-1 and SHA-256 support explicitly (via `object-format=sha256` and `alt-object-format=sha1`) rather than defaulting to SHA-1, because clients need to know the server can handle SHA-256 before pushing. He dismisses the idea of delaying Git 3.0’s SHA-256-by-default transition until `magic-limbo` is implemented, calling it impractical—no one has committed to writing the code, and Git is already late in moving away from SHA-1. Second, he points out that the 2023 infinite-loop bug in multi-valued capability parsing (fixed in Git 2.41) is no longer a blocker, since SHA-256 support stabilized in 2.44, meaning older experimental versions can safely be abandoned.

On policy enforcement, brian disagrees with Jeff’s view that it’s purely a forge-level concern. He insists Git should provide a config or command-line option to enforce hash-algorithm policies (e.g., disallowing SHA-1), because forges may use APIs or other non-push commands to write to repositories, and those need a defined hash algorithm even in limbo. The discussion now hinges on whether the protocol can safely advertise multiple formats, and whether Git should standardize policy controls or leave them to forges. No implementation exists yet, but brian’s feedback suggests the design will need to address both compatibility and configurability to gain traction.

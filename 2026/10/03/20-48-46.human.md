This is a follow-up in the `git brebase` RFC thread, proposing an alternative integration path for the core idea. Nico Williams suggests that rather than introducing a new command (`git brebase`) or even a new flag, Git’s existing `git rebase` should adopt the incremental, conflict-bisection behavior by default. His proposal would make `git rebase` automatically bisect to the first conflicting commit, stop for manual resolution, and then automatically resume the rebase until the target branch is reached—eliminating the need for a separate tool.

The key technical change would be recording the target committish in the rebase state so that `git rebase --continue` can automatically restart the rebase after each resolution. Nico acknowledges this would require a new `--direct` flag to opt out of the incremental behavior, but he argues the incremental approach should be the default, not an opt-in. He suggests a phased rollout: first ship the incremental behavior as an opt-in flag, then later make it the default once it has proven robust.

This is a substantive review comment that shifts the discussion from “should we add a new command?” to “should the existing command change its default behavior?” The proposal is well-motivated and directly addresses the original RFC’s integration question, but it also raises the stakes: changing `git rebase`’s default behavior would affect every Git user, not just those who opt into a new tool. The tone is enthusiastic and the reasoning is clear, but the suggestion is likely to be controversial given the potential for disruption.

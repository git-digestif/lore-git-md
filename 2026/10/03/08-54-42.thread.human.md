This thread began with Sphinx asking whether Git should warn users when a destructive operation on a shallow clone (like `git revert` or `git restore`) leaves an empty working tree. The discussion quickly evolved into a design debate: Patrick Steinhardt, a core contributor, proposed that Git should at least warn—and possibly refuse by default—when users attempt to edit shallow boundary commits, arguing that the current behavior is surprising and likely unintended. Carlisle T. Hamlin countered that Git’s minimal-intervention philosophy should prevail, leaving such safeguards to user awareness or external tooling.

Now, Matt Hunter has introduced a new angle: whether shallow clones could preserve the original commit IDs of boundary commits instead of rewriting them as root commits. This architectural change could eliminate the empty-tree issue at its source, avoiding the need for warnings or refusals. However, it raises questions about compatibility with fetch logic, object reachability, and shallow clone internals—areas where Patrick Steinhardt’s ongoing ODB abstraction work might intersect. No one has yet weighed in on Hunter’s idea, but it shifts the focus from reactive safeguards to a proactive fix. The thread remains in the design phase, with no implementation or maintainer feedback on either proposal. Key open questions include whether Hunter’s approach is technically feasible and how it might interact with existing shallow clone behavior.

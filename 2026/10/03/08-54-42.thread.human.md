This thread began as a question from Sphinx about whether Git should warn users when a destructive operation (like `git revert` or `git restore`) on a shallow clone (`--depth=1`) results in an empty working tree—all tracked files being removed. The discussion quickly evolved into a design debate about whether Git should add safeguards for such operations or leave this as the user’s responsibility.

The key issue stems from how shallow clones handle boundary commits: they logically rewrite them as root commits during runtime traversal, so reversing such a commit (e.g., via `git revert`) deletes all tracked files. Patrick Steinhardt proposed that Git should warn or refuse such operations by default, arguing that the current behavior is surprising and likely unintended. Junio C Hamano, the project maintainer, has now endorsed this approach, framing it as a "rough edge" in a mature but under-polished feature. His support removes the last major obstacle to implementation, signaling that a well-scoped patch series would likely be accepted.

The discussion has narrowed to the specifics of how to implement these safeguards. The focus is on shallow boundary commits—not empty trees in general—and would include an override mechanism for intentional use. Subsystems likely to be touched include shallow clone internals, commit-editing commands (`revert`, `amend`), and user-facing warnings. With Junio’s backing, the thread has shifted from debating *whether* to act to planning *how* to act, though no technical analysis of feasibility or trade-offs has been provided yet. The next step is for someone (likely Steinhardt or a motivated contributor) to draft a patch series with tests and documentation.

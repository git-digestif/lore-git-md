This thread began when Sphinx asked whether Git should warn users when a destructive operation—like `git revert` or `git restore`—on a shallow clone (`--depth=1`) leaves an empty working tree. What started as a simple question has grown into a design debate about whether Git should detect and prevent such outcomes by default, or if users should bear full responsibility for understanding shallow clone behavior.

The core issue stems from how shallow clones handle boundary commits: during runtime traversal, these commits are treated as root commits, so reverting or amending them removes all tracked files. Patrick Steinhardt has argued that this behavior is surprising and likely unintended in most cases, proposing that Git should at least warn—and possibly refuse by default—when users attempt such operations. Junio C Hamano clarified that the original commit IDs are preserved in the object database, but the runtime illusion of root commits is what creates the problem. This narrows the technical discussion to whether that illusion could be relaxed for specific operations, though no one has yet analyzed the feasibility or trade-offs of doing so.

So far, only Carlisle T. Hamlin has opposed adding safeguards, arguing that Git’s current behavior aligns with its minimal-intervention philosophy. The thread remains in the design phase, with no implementation or maintainer decision. Key open questions include whether safeguards would conflict with Git’s design principles, how they might interact with shallow clone metadata, and what override mechanism would be appropriate for users who intentionally want to edit boundary commits. If this proposal gains traction, expect discussion about how to balance usability with Git’s traditional hands-off approach.

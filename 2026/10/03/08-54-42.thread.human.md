This thread began with Sphinx asking whether Git should warn users when a destructive operation on a shallow clone (like `git revert` or `git restore`) leaves an empty working tree. The discussion has since split into two overlapping design questions: whether Git should add safeguards for editing shallow boundary commits, and whether shallow clones could preserve original commit IDs to avoid the issue entirely.

Patrick Steinhardt has argued that Git’s current behavior is surprising and likely unintended, proposing that it should at least warn—and possibly refuse by default—when users attempt to edit shallow boundary commits (e.g., via `git revert` or `git commit --amend`). No other core contributors have weighed in on this proposal, but Junio C Hamano recently clarified a key technical point: shallow clones already preserve the original commit IDs in the object database. The "rewriting" of boundary commits as root commits is purely a runtime illusion during history traversal, similar to grafts or replace refs. This rules out object-identity changes as a solution but leaves open whether fetch or revert logic could be adjusted to account for the original parentage of boundary commits.

Matt Hunter’s suggestion—that preserving original commit IDs could eliminate the empty-tree issue—has been partially addressed by Junio’s clarification. The focus now shifts to whether the runtime illusion of root commits could be relaxed in specific contexts (e.g., fetch or revert) without breaking shallow clone invariants. Meanwhile, Carlisle T. Hamlin opposes adding warnings, arguing that Git’s current behavior aligns with its minimal-intervention philosophy. The thread remains in the design phase, with no implementation or test coverage, and no maintainer decision on Steinhardt’s safeguard proposal. The broader question of whether this is a usability gap or a user responsibility is still unresolved.

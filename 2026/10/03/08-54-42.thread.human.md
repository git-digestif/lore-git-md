This thread began as a question from Sphinx about whether Git should warn users when a destructive operation (like `git revert` or `git restore`) on a shallow clone (`--depth=1`) leaves an empty working tree—all tracked files removed. The discussion has since broadened into a design debate about whether Git should detect and warn about (or even refuse) such operations by default for shallow boundary commits, or if this remains the user’s responsibility.

Key voices have weighed in. Patrick Steinhardt argued that Git’s current behavior is surprising and likely unintended, proposing that Git should at least warn—and possibly refuse by default—when users attempt to edit shallow boundary commits, with an override mechanism available. Carlisle T. Hamlin initially opposed this, arguing that Git’s minimal-intervention philosophy should prevail, but has since retracted that stance after realizing the project is open to such safeguards. Junio C Hamano clarified that shallow clones preserve original commit IDs but *logically* rewrite boundary commits as root commits during runtime traversal, which reframed Matt Hunter’s earlier proposal as a question of whether this runtime illusion could be relaxed for specific operations to avoid the empty-tree issue.

The thread remains in the design phase, with no implementation or test coverage yet. The core tension is between Git’s traditional hands-off approach and the case for proactive safeguards in this specific scenario. No maintainer has yet signaled whether they view Steinhardt’s proposal as justified or overreaching, and the feasibility of adjusting runtime traversal logic remains unexplored. The discussion is now paused on conduct, but the technical questions—whether to warn, refuse, or adjust shallow clone behavior—are still open.

Core problem or goal
Sphinx initiated a discussion about whether Git should warn users when a destructive operation (e.g., `git revert` or `git restore`) on a shallow clone (`--depth=1`) results in an empty working tree—all tracked files are removed. The inquiry evolved into a design debate: should Git detect and warn about (or refuse) such transitions by default for shallow boundary commits, or is this the user’s responsibility? The discussion now centers on two architectural approaches: (1) adding safeguards (warnings or refusals) for destructive operations on shallow boundary commits, and (2) preserving the original parentage of boundary commits during runtime traversal to avoid the empty-tree issue. Junio C Hamano clarified that commit objects retain their original IDs, but shallow clones use a grafts/replace-like mechanism to *logically* rewrite boundary commits as root commits during history traversal. This reframed Matt Hunter’s proposal as a question of whether the runtime illusion could be relaxed for specific operations (e.g., revert, fetch) to avoid the empty-tree issue. Junio has now endorsed Patrick Steinhardt’s proposal to add safeguards, signaling that implementation is likely to proceed.

Current status
The thread has shifted from design exploration to implementation planning. Junio’s endorsement of Steinhardt’s proposal ("that line of thinking is going in the right direction") removes the last major obstacle to implementation, indicating that a well-scoped patch series would likely be accepted. The discussion is now focused on *how* to implement safeguards rather than *whether* to do so. Two proposals remain under consideration:
1. **Safeguards for destructive operations** (now the primary focus): Git should warn or refuse by default when users attempt to edit shallow boundary commits (e.g., revert, amend, restore), with an override mechanism for intentional use. Junio explicitly supports this approach, framing it as addressing a "rough edge" in a non-core feature that has had years to mature but still lacks polish in edge cases. The safeguard would target shallow boundary commits specifically, not empty trees in general.
2. **Runtime traversal adjustments** (secondary): Junio’s clarification revealed that the original commit IDs are preserved in the object database, but shallow clones *logically* rewrite boundary commits as root commits during traversal. This narrows Hunter’s proposal to whether the runtime illusion could be relaxed for specific operations (e.g., revert, fetch) to avoid the empty-tree issue. No technical analysis of feasibility or trade-offs has been provided, and this approach remains speculative.

Key technical details
- **Commands involved**: `git revert`, `git restore`, `git commit --amend`, `git clone --depth=1`, `git fetch`
- **Scenario**: Shallow clone of a repository with two commits (A → B), where B is the only commit present locally. Reverting or restoring B removes all tracked files, leaving an empty working tree. The issue stems from how shallow clones *logically* rewrite boundary commits as root commits during traversal, making their reversal delete all tracked files.
- **Subsystems touched**: shallow clone internals (`.git/shallow` metadata, grafts/replace-like behavior), commit editing commands, working tree management, user-facing warnings, object storage, fetch/pack negotiation
- **Behavior**: Git currently performs the operation without warning, producing an empty tree. The safeguard would target shallow boundary commits specifically, not empty trees in general.
- **Precedents**: Recent discussion about forbidding `git commit --amend` on shallow boundary commits; Git’s existing safeguards focus on untracked data rather than committed content.
- **Junio’s clarification**:
  - Shallow clones do *not* modify commit objects; original commit IDs are preserved in the object database.
  - Boundary commits are *logically* rewritten as root commits during runtime traversal using a mechanism similar to grafts or replace refs.
  - This rules out object-identity changes as a solution to the empty-tree issue but leaves open the possibility of adjusting runtime traversal logic in specific contexts (e.g., fetch, revert).
- **Hunter’s proposal (reframed)**: The question is whether the runtime illusion of root commits could be relaxed for certain operations (e.g., revert) to avoid the empty-tree issue, rather than preserving commit IDs (which is already done).
- **Test coverage**: Not yet discussed; implementation will require tests for the safeguard mechanism and edge cases.

Open questions and loose ends
- **Implementation details for safeguards**:
  - What override mechanism should be provided for users who intentionally want to edit shallow boundary commits? Would `--force` be sufficient, or is a more specific flag (e.g., `--allow-shallow-edit`) needed?
  - Should the safeguard be a warning (with a delay or `--force` override) or a refusal by default? Junio’s endorsement leans toward refusal with override, but this may require further discussion.
  - How should the safeguard interact with scripting use cases (e.g., CI pipelines) where warnings might be disruptive but refusals could break workflows?
  - Should the safeguard apply to all commit-editing operations (e.g., `git rebase --onto`, `git cherry-pick`) or only to those explicitly mentioned (revert, amend, restore)?
  - How will the safeguard handle edge cases where the shallow boundary commit is not the immediate parent of the current HEAD (e.g., multi-commit shallow clones)?
- **Runtime traversal adjustments**:
  - Is it feasible to relax the runtime illusion of root commits for specific operations (e.g., revert, fetch) without breaking shallow clone invariants?
  - What trade-offs exist between relaxing the illusion and shallow clone usability (e.g., fetch performance, repository size, backward compatibility)?
  - Could fetch or revert logic be adjusted to account for the original parentage of boundary commits, or is the current behavior an unavoidable trade-off of shallow clones?
  - How would this interact with existing shallow clone metadata (`.git/shallow`) and pack negotiation?
  - Would relaxing the illusion for revert operations introduce inconsistencies in how Git treats boundary commits across different commands (e.g., revert vs. log)?
- **Documentation and user experience**:
  - Should the safeguard be documented in the `git clone --depth` man page, or is a dedicated section in `git revert`/`git amend` more appropriate?
  - How can the override mechanism be communicated clearly to users without encouraging misuse?
  - Are there existing warning messages (e.g., for untracked files) that could serve as a template for the new safeguard?
- **Backward compatibility**:
  - Will the safeguard break existing scripts or workflows that rely on the current behavior? If so, how can this be mitigated?
  - Should the safeguard be opt-in (e.g., via a config setting) or opt-out (with a `--no-safeguard` flag)?

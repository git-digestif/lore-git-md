Core problem or goal
Sphinx initiated a discussion about whether Git should warn users when a destructive operation (e.g., `git revert` or `git restore`) on a shallow clone (`--depth=1`) results in an empty working tree—all tracked files are removed. The inquiry has evolved into a broader design debate: should Git detect and warn about (or refuse) such transitions by default for shallow boundary commits, or is this the user’s responsibility? The discussion now explores two architectural approaches: (1) adding safeguards (warnings or refusals) for destructive operations on shallow boundary commits, and (2) preserving the original parentage of boundary commits during runtime traversal to avoid the empty-tree issue entirely. Junio C Hamano clarified that commit objects retain their original IDs, but shallow clones use a grafts/replace-like mechanism to *logically* rewrite boundary commits as root commits during history traversal. This reframed Matt Hunter’s proposal as a question of whether the runtime illusion could be relaxed for specific operations (e.g., revert, fetch) to avoid the empty-tree issue.

Current status
The thread remains in the design phase with no implementation or test coverage. Two distinct proposals are under discussion:
1. **Safeguards for destructive operations**: Patrick Steinhardt proposed that Git should warn or refuse by default when users attempt to edit shallow boundary commits (e.g., revert, amend), citing surprising and likely unintended behavior. Sphinx’s follow-up reinforces this framing, signaling agreement and increasing its prominence in the discussion. No maintainer or core contributor has yet weighed in on the desirability or feasibility of this approach.
2. **Runtime traversal adjustments**: Junio’s clarification reveals that the original commit IDs are preserved in the object database, but shallow clones *logically* rewrite boundary commits as root commits during traversal. This narrows Hunter’s proposal to a question of whether the runtime illusion could be relaxed in specific contexts (e.g., fetch, revert) to avoid the empty-tree issue. No technical analysis of feasibility or trade-offs has been provided for this approach.

Key technical details
- **Commands involved**: `git revert`, `git restore`, `git commit --amend`, `git clone --depth=1`, `git fetch`
- **Scenario**: Shallow clone of a repository with two commits (A → B), where B is the only commit present locally. Reverting or restoring B removes all tracked files, leaving an empty working tree. The issue stems from how shallow clones *logically* rewrite boundary commits as root commits during traversal, making their reversal delete all tracked files.
- **Subsystems touched**: shallow clone internals (`.git/shallow` metadata, grafts/replace-like behavior), commit editing commands, working tree management, user-facing warnings, object storage, fetch/pack negotiation
- **Behavior**: Git currently performs the operation without warning, producing an empty tree. Steinhardt’s proposal targets shallow boundary commits specifically, not empty trees in general.
- **Precedents**: Recent discussion about forbidding `git commit --amend` on shallow boundary commits; Git’s existing safeguards focus on untracked data rather than committed content.
- **Junio’s clarification**:
  - Shallow clones do *not* modify commit objects; original commit IDs are preserved in the object database.
  - Boundary commits are *logically* rewritten as root commits during runtime traversal using a mechanism similar to grafts or replace refs.
  - This rules out object-identity changes as a solution to the empty-tree issue, but leaves open the possibility of adjusting runtime traversal logic in specific contexts (e.g., fetch, revert).
- **Hunter’s proposal (reframed)**: The question is now whether the runtime illusion of root commits could be relaxed for certain operations (e.g., revert) to avoid the empty-tree issue, rather than preserving commit IDs (which is already done).
- **Test coverage**: Not mentioned; discussion remains focused on design intent and architectural feasibility.

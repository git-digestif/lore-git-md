Subject: Intended behavior for shallow clones producing empty trees after destructive operations
Series version: N/A (user question, not a patch series)
Originating author: Sphinx
Thread type: design discussion / behavior clarification

Core problem or goal
Sphinx asks whether Git should warn users when a destructive operation (e.g., `git revert` or `git restore`) on a shallow clone (`--depth=1`) results in an empty working tree—i.e., all tracked files are removed. The inquiry centers on Git’s safety boundaries: should the tool itself detect and warn about such transitions, or is this responsibility delegated to external tooling or user awareness? The discussion has now expanded to include whether Git should *refuse* such operations by default for shallow boundary commits, with an override mechanism.

Current status
The thread has shifted from a neutral inquiry to a concrete design proposal. Patrick Steinhardt, a core contributor with deep expertise in shallow clone internals, argues that Git’s current behavior (no warning or safeguard) is surprising and likely unintended in most cases. He proposes that Git should at least warn—and possibly refuse by default—when users attempt to edit (e.g., revert, amend) a shallow boundary commit, citing a parallel to a recent discussion about forbidding `git commit --amend` on such commits. No maintainers or other contributors have yet weighed in on the technical merits of this proposal, and the thread remains in the design phase with no implementation or test coverage.

Key technical details
- **Commands involved**: `git revert`, `git restore`, `git commit --amend`, `git clone --depth=1`
- **Scenario**: Shallow clone of a repository with two commits (A → B), where B is the only commit present locally. Reverting or restoring B removes all tracked files, leaving an empty working tree. The issue stems from how shallow clones rewrite boundary commits to appear as root commits, making their reversal delete all tracked files.
- **Subsystems touched**: shallow clone internals, commit editing commands, working tree management, user-facing warnings
- **Behavior**: Git currently performs the operation without warning, producing an empty tree. Steinhardt’s proposal targets shallow boundary commits specifically, not empty trees in general.
- **Precedents**: Recent discussion about forbidding `git commit --amend` on shallow boundary commits; Git’s existing safeguards focus on untracked data rather than committed content.
- **Test coverage**: Not mentioned; the discussion remains focused on design intent rather than implementation.

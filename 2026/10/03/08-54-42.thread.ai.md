Core problem or goal
Sphinx initiated a discussion about whether Git should warn users when a destructive operation (e.g., `git revert` or `git restore`) on a shallow clone (`--depth=1`) results in an empty working tree—all tracked files are removed. The inquiry has evolved into a broader design debate: should Git detect and warn about (or refuse) such transitions by default for shallow boundary commits, or is this the user’s responsibility? The discussion now also explores whether shallow clones could preserve the original commit IDs of boundary commits (rather than rewriting them as root commits) to avoid the empty-tree issue entirely, a proposal raised by Matt Hunter.

Current status
The thread remains in the design phase with no implementation or test coverage. Patrick Steinhardt proposed that Git should at least warn—and possibly refuse by default—when users attempt to edit shallow boundary commits (e.g., revert, amend), citing surprising and likely unintended behavior. No maintainers or other core contributors have weighed in on the technical merits of this proposal. Matt Hunter’s tangential but relevant question introduces an architectural alternative: preserving original commit IDs in shallow clones to maintain compatibility with future fast-forward pulls. This idea shifts focus from safeguards to a deeper trade-off between shallow clone usability and object identity. The proposal is hypothetical and lacks implementation details, but it could eliminate the root cause of the empty-tree behavior if pursued.

Key technical details
- **Commands involved**: `git revert`, `git restore`, `git commit --amend`, `git clone --depth=1`, `git fetch`
- **Scenario**: Shallow clone of a repository with two commits (A → B), where B is the only commit present locally. Reverting or restoring B removes all tracked files, leaving an empty working tree. The issue stems from how shallow clones rewrite boundary commits to appear as root commits, making their reversal delete all tracked files.
- **Subsystems touched**: shallow clone internals, commit editing commands, working tree management, user-facing warnings, object storage, fetch/pack negotiation, shallow clone metadata (`.git/shallow`)
- **Behavior**: Git currently performs the operation without warning, producing an empty tree. Steinhardt’s proposal targets shallow boundary commits specifically, not empty trees in general.
- **Precedents**: Recent discussion about forbidding `git commit --amend` on shallow boundary commits; Git’s existing safeguards focus on untracked data rather than committed content.
- **Hunter’s proposal**: Preserving original commit IDs in shallow clones could avoid the empty-tree issue but may complicate object reachability, fetch logic, and shallow clone invariants. This intersects with ongoing ODB abstraction work (Patrick Steinhardt) and repack machinery (Taylor Blau).
- **Test coverage**: Not mentioned; discussion remains focused on design intent.

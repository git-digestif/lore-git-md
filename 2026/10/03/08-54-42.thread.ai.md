Core problem or goal
Sphinx initiated a discussion about whether Git should warn users when a destructive operation (e.g., `git revert` or `git restore`) on a shallow clone (`--depth=1`) results in an empty working tree—all tracked files are removed. The inquiry evolved into a design debate and has now shifted to implementation planning for safeguards. The core goal is to prevent unintended empty trees when editing shallow boundary commits by adding safeguards (warnings or refusals) for destructive operations on such commits. Junio C Hamano’s endorsement of Patrick Steinhardt’s proposal ("that line of thinking is going in the right direction") confirmed that implementation is likely to proceed. The discussion now centers on *how* to implement these safeguards, with Sphinx proposing a concrete mechanism for `git revert` (and possibly `git commit --amend`).

Current status
The thread has transitioned from design exploration to implementation planning. Junio’s endorsement of safeguards removes the last major obstacle, and the focus is now on the mechanics of the safeguard. Sphinx has proposed a narrowly scoped implementation for `git revert` that would refuse by default when attempting to edit a shallow boundary commit, with an override mechanism (`--allow-shallow-boundary`). The safeguard targets shallow boundary commits specifically (not empty trees in general) and is opt-out (refuse by default) rather than opt-in (warn by default). The next step is Sphinx’s patch, which will serve as the reference implementation for this effort. Two approaches remain under consideration, but the safeguard proposal is now the primary focus:
1. **Safeguards for destructive operations** (primary focus): Git will refuse by default when users attempt to edit shallow boundary commits (e.g., `git revert`, `git commit --amend`), with an override flag (`--allow-shallow-boundary`). The safeguard checks whether the target commit OID appears in `.git/shallow` and refuses with a clear error message if so. This approach is now the likely path forward, with Junio’s explicit support.
2. **Runtime traversal adjustments** (secondary, speculative): Junio’s clarification revealed that shallow clones *logically* rewrite boundary commits as root commits during traversal, but original commit IDs are preserved in the object database. This leaves open the possibility of relaxing the runtime illusion for specific operations (e.g., revert, fetch) to avoid the empty-tree issue. No technical analysis of feasibility or trade-offs has been provided, and this approach remains speculative.

Key technical details
- **Commands involved**: `git revert`, `git commit --amend`, `git clone --depth=1`, `git fetch` (safeguard proposal); `git revert`, `git fetch` (runtime traversal proposal)
- **Scenario**: Shallow clone of a repository with two commits (A → B), where B is the only commit present locally. Reverting or amending B removes all tracked files, leaving an empty working tree. The issue stems from how shallow clones *logically* rewrite boundary commits as root commits during traversal, making their reversal delete all tracked files.
- **Subsystems touched**: shallow clone internals (`.git/shallow` metadata, grafts/replace-like behavior), commit-editing commands (`revert`, `amend`), working tree management, user-facing error messages, object storage, fetch/pack negotiation
- **Behavior**: Git currently performs the operation without warning, producing an empty tree. The safeguard will target shallow boundary commits specifically, not empty trees in general.
- **Safeguard mechanism**: Refuse by default if the target commit OID appears in `.git/shallow`, with an override flag (`--allow-shallow-boundary`). The error message will explain the risk of empty trees and direct users to the override flag for intentional use.
- **Precedents**: Recent discussion about forbidding `git commit --amend` on shallow boundary commits; Git’s existing safeguards focus on untracked data rather than committed content.
- **Junio’s clarification**:
  - Shallow clones do *not* modify commit objects; original commit IDs are preserved in the object database.
  - Boundary commits are *logically* rewritten as root commits during runtime traversal using a mechanism similar to grafts or replace refs.
  - This rules out object-identity changes as a solution to the empty-tree issue but leaves open the possibility of adjusting runtime traversal logic in specific contexts (e.g., fetch, revert).
- **Test coverage**: Implementation will require tests for the safeguard mechanism (e.g., refusal on shallow boundary commits, override behavior) and edge cases (e.g., multi-commit shallow clones, fetch interactions).

Open questions and loose ends
- **Implementation details for safeguards**:
  - Should the safeguard apply to all commit-editing operations (e.g., `git rebase --onto`, `git cherry-pick`) or only to those explicitly mentioned (`revert`, `amend`)? Sphinx’s proposal focuses on `revert` and `amend`, but broader applicability may be needed.
  - How should the safeguard handle edge cases where the shallow boundary commit is not the immediate parent of the current HEAD (e.g., multi-commit shallow clones)?
  - Should the override flag (`--allow-shallow-boundary`) be consistent across all commands, or should each command have its own flag (e.g., `--allow-shallow-revert` for `git revert`)?
  - How will the safeguard interact with scripting use cases (e.g., CI pipelines) where refusals could break workflows? Should there be a config setting to disable the safeguard globally?
  - Should the safeguard be documented in the `git clone --depth` man page, or is a dedicated section in `git revert`/`git amend` more appropriate?
  - Are there existing warning/error messages (e.g., for untracked files) that could serve as a template for the new safeguard?
- **Runtime traversal adjustments**:
  - Is it feasible to relax the runtime illusion of root commits for specific operations (e.g., revert, fetch) without breaking shallow clone invariants?
  - What trade-offs exist between relaxing the illusion and shallow clone usability (e.g., fetch performance, repository size, backward compatibility)?
  - Could fetch or revert logic be adjusted to account for the original parentage of boundary commits, or is the current behavior an unavoidable trade-off of shallow clones?
  - How would this interact with existing shallow clone metadata (`.git/shallow`) and pack negotiation?
  - Would relaxing the illusion for revert operations introduce inconsistencies in how Git treats boundary commits across different commands (e.g., revert vs. log)?
- **Backward compatibility**:
  - Will the safeguard break existing scripts or workflows that rely on the current behavior? If so, how can this be mitigated (e.g., config setting, environment variable)?
  - Should the safeguard be opt-in (e.g., via a config setting) or opt-out (with a `--no-safeguard` flag)? The current proposal is opt-out (refuse by default), but this may require further discussion.

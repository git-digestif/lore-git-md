Subject: [RFC] git brebase: a simpler alternative to git imerge for complex rebases
Series version: RFC (no version number)
Originating author: Alejandro Colomar
Thread type: RFC / design discussion

Core problem or goal
Propose a tool or workflow to simplify incremental rebasing of complex histories (branches with merge commits, arbitrary commit skipping) by automating conflict detection and resolution up to the first semantic conflict. The discussion continues to explore whether this functionality should live in a new command (`git brebase`), be added as a flag to `git rebase`, or become the default behavior of `git rebase` itself.

Current status
Under discussion; no implementation or prior versions. The original proposal (`git brebase`) remains a 164-line shell script attached to the thread. Alejandro has refined the script to address feedback (e.g., handling merge commits, supporting recursive resolution, fixing detached HEAD support) but has not changed its fundamental design. Nico Williams’ counterproposal to integrate the workflow into `git rebase` is still under debate. Key features under discussion: (1) bisect-driven conflict detection, (2) automatic resumption of rebase after conflict resolution, and (3) the integration path (new command, flag, or default behavior). No consensus has emerged, and no code changes to `git rebase` have been proposed or implemented.

Key technical details
- **Original proposal (`git brebase`)**:
  - Shell script using `git bisect` and `git rebase` internally.
  - New CLI options: `--pre-exec=<cmd>` (filter commits), `--post-exec=<cmd>` (validate after each step).
  - Behavior: Stops at the first conflicting commit (merge or semantic), supports recursive resolution of complex topologies, now handles detached HEAD mode (bug fix).
  - Implementation details: Uses `git bisect run` with a callback script; avoids `getopts` due to Git’s CLI conventions (e.g., `--` separator); filters callback script filename from `git bisect run` output to avoid user confusion; uses `trap` for temporary file cleanup.
  - Limitations: Shell-based, no persistent conflict history, rudimentary option parsing, no direct merge commit creation.
- **Counterproposal (Nico Williams)**:
  - Integrate bisect-driven conflict detection into `git rebase` as the default behavior when conflicts arise.
  - Automatically resume rebase after conflict resolution by recording the target committish in rebase state.
  - Suggests a `--direct` flag to disable the new behavior, with potential to make it the default later.
  - Implications: Requires changes to rebase internals (state management, conflict handling), likely in C; no concrete proposal for handling merge commits.
- **Files touched**: None yet; both proposals remain conceptual.
- **Comparison with existing tools**:
  - `git imerge`: Uses a 2D matrix approach; `git brebase` avoids this in favor of linear bisect-driven workflow.
  - `git rebase --rebase-merges`: Handles merge commits but lacks incremental conflict detection.

Open questions and loose ends
1. **Integration path**: Should the functionality be a new command (`git brebase`), a flag for `git rebase` (e.g., `--incremental` or `--first-conflict`), or the default behavior of `git rebase`? Alejandro leans toward a new command but acknowledges a flag could make sense; Nico argues for integration into `git rebase` as the default.
2. **Default behavior**: Is it feasible to make bisect-driven conflict resolution the default for `git rebase`? What are the risks to existing workflows, and how would it interact with `--rebase-merges` or other flags?
3. **Robustness**: Is a shell-based implementation acceptable for production use, or is a C rewrite required? Nico’s proposal would necessitate C changes, but Alejandro’s script is functional and improving.
4. **Merge commits**: How would Nico’s counterproposal handle merge commits? The original `git brebase` supports them, but Nico’s emails have not addressed this.
5. **State management**: Nico’s proposal requires recording the target committish in rebase state. Is this technically feasible without breaking backward compatibility, and how would it interact with existing rebase state (e.g., `--onto`, `--fork-point`)?
6. **Edge cases**: Neither proposal has been tested for edge cases (e.g., nested conflicts, `--rebase-merges` interactions, conflicts in merge commits, or recursive resolution of complex topologies).
7. **Adoption**: How does the counterproposal compare to `git imerge` or `git brebase` in practice? No user feedback or testing has been reported.
8. **Flag validation**: The original script’s rudimentary option parsing may not meet Git’s CLI standards. Should this be improved regardless of integration path?
9. **Recursive resolution**: The original proposal supports complex branch topologies (e.g., trees of branches), but the counterproposal does not address this.
10. **Detached HEAD support**: Fixed in the script (bug addressed by Alejandro), but Nico’s counterproposal has not discussed this edge case.

Participant positions
- **Alejandro Colomar (author)**: Advocates for `git brebase` as a standalone tool, emphasizing its simplicity and power for complex rebases (e.g., merge commits, arbitrary commit skipping). Acknowledges limitations (shell-based, no persistent conflict history) but argues they are acceptable trade-offs. Open to adding a `--first-conflict` flag to `git rebase` as a middle ground but remains noncommittal. Receptive to feedback on implementation details (e.g., `trap` for cleanup, detached HEAD support) but does not signal a shift in the core design.
- **Nico Williams**: Proposes integrating the incremental rebase workflow into `git rebase` itself, arguing that bisect-driven conflict resolution should be the default behavior. Frames this as a usability improvement and suggests a `--direct` flag to disable it. Enthusiastic but speculative; seeks feedback on feasibility and risks. Has not addressed merge commits or detached HEAD mode in his proposal.

Related work
- **`git imerge`**: Existing tool for incremental rebasing; `git brebase` aims to replace/supplement it with a simpler workflow.
- **`git rebase --rebase-merges`**: Partially overlaps with `git brebase`’s handling of merge commits but lacks incremental conflict detection.
- **`git bisect`**: Used internally by `git brebase` to find the first conflicting commit. Nico’s proposal would integrate this into `git rebase`.

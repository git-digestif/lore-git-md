Subject: [RFC] git brebase: a simpler alternative to git imerge for complex rebases
Series version: RFC (no version number)
Originating author: Alejandro Colomar
Thread type: RFC / design discussion

Core problem or goal
Propose a tool or workflow to simplify incremental rebasing of complex histories (branches with merge commits, arbitrary commit skipping) by automating conflict detection and resolution up to the first semantic conflict. The discussion continues to explore whether this functionality should live in a new command (`git brebase`), be added as a flag to `git rebase`, or become the default behavior of `git rebase` itself.

Current status
Under discussion; no implementation or prior versions. The original proposal (`git brebase`) remains a 164-line shell script attached to the thread. Alejandro has refined the script to address feedback: (1) adopted `trap` for temporary file cleanup, (2) filtered the callback script filename from `git bisect run` output to avoid user confusion, and (3) acknowledged detached HEAD support as a bug to fix (previously required the user to be on a branch). The fundamental design debate remains unresolved: Alejandro argues for a standalone porcelain command built on top of `git rebase` (plumbing), while Nico Williams proposes integrating bisect-driven conflict resolution into `git rebase` as the default behavior, framing the current design as an accident of history. Key features under discussion: (1) bisect-driven conflict detection, (2) automatic resumption of rebase after conflict resolution, and (3) the integration path. No consensus has emerged, and no code changes to `git rebase` have been proposed or implemented.

Key technical details
- **Original proposal (`git brebase`)**:
  - Shell script using `git bisect` and `git rebase` internally.
  - New CLI options: `--pre-exec=<cmd>` (filter commits), `--post-exec=<cmd>` (validate after each step).
  - Behavior: Stops at the first conflicting commit (merge or semantic), supports recursive resolution of complex topologies (e.g., "trees of branches"), handles detached HEAD mode (bug acknowledged; fix pending). Uses `git bisect run` with a callback script; avoids `getopts` due to Git’s CLI conventions (e.g., `--` separator); filters callback script filename from `git bisect run` output; uses `trap` for temporary file cleanup.
  - Design philosophy: Porcelain tool built on top of `git rebase` (plumbing), preserving `git rebase`’s simplicity and predictability. `--abort` and `--continue` operate at the segment level (bisect-driven segment), not the entire rebase, enabling recursive resolution.
  - Limitations: Shell-based, no persistent conflict history, rudimentary option parsing (though improved), no direct merge commit creation.
- **Counterproposal (Nico Williams)**:
  - Integrate bisect-driven conflict resolution into `git rebase` as the default behavior when conflicts arise, treating it as the *intended* design rather than an enhancement.
  - Automatically resume rebase after conflict resolution by recording the target committish in rebase state.
  - Suggests a `--direct` flag to disable the new behavior, with potential to make it the default later (though Nico now argues it *should* have been the default all along).
  - Implications: Requires changes to rebase internals (state management, conflict handling), likely in C; no concrete proposal for handling merge commits or recursive resolution. `--abort` and `--continue` would operate on the entire rebase, not per-segment, breaking symmetry with the bisect-driven workflow.
- **Files touched**: None yet; both proposals remain conceptual.
- **Comparison with existing tools**:
  - `git imerge`: Uses a 2D matrix approach; `git brebase` avoids this in favor of linear bisect-driven workflow.
  - `git rebase --rebase-merges`: Handles merge commits but lacks incremental conflict detection.

Open questions and loose ends
1. **Integration path**: Should the functionality be a new command (`git brebase`), a flag for `git rebase` (e.g., `--incremental` or `--first-conflict`), or the default behavior of `git rebase`? Alejandro argues for a separate command to preserve `git rebase`’s plumbing role; Nico argues the incremental workflow *should have been* the default, framing the current design as an accident of history.
2. **Default behavior**: Is it feasible to make bisect-driven conflict resolution the default for `git rebase`? What are the risks to existing workflows, and how would it interact with `--rebase-merges` or other flags? Alejandro warns that defaulting to bisect-driven behavior would blur `git rebase`’s responsibilities and confuse users; Nico dismisses this as a non-issue.
3. **Recursive resolution**: `git brebase` supports complex branch topologies (e.g., "trees of branches") via recursive resolution, where each segment of the rebase can itself be rebased incrementally. Nico’s counterproposal does not address this, and it is unclear how it would be implemented in `git rebase`.
4. **Segment-level vs. rebase-level operations**: Alejandro’s design requires `--abort` and `--continue` to operate at the segment level (bisect-driven segment), while Nico’s proposal would operate on the entire rebase. This asymmetry could break user expectations and recursive resolution.
5. **Robustness**: Is a shell-based implementation acceptable for production use, or is a C rewrite required? Nico’s proposal would necessitate C changes, but Alejandro’s script is functional and improving (e.g., `trap` for cleanup, detached HEAD bug fix).
6. **Merge commits**: How would Nico’s counterproposal handle merge commits? The original `git brebase` supports them, but Nico’s emails have not addressed this.
7. **State management**: Nico’s proposal requires recording the target committish in rebase state. Is this technically feasible without breaking backward compatibility, and how would it interact with existing rebase state (e.g., `--onto`, `--fork-point`)?
8. **Edge cases**: Neither proposal has been tested for edge cases (e.g., nested conflicts, `--rebase-merges` interactions, conflicts in merge commits, or recursive resolution of complex topologies). Detached HEAD support is now acknowledged as a bug in `git brebase` but remains unfixed.
9. **Adoption**: How does the counterproposal compare to `git imerge` or `git brebase` in practice? No user feedback or testing has been reported.
10. **Flag validation**: The script’s option parsing remains rudimentary (though improved) and may not meet Git’s CLI standards. Should this be addressed regardless of integration path?
11. **Design philosophy**: Nico’s reframing of the debate as "what *should* `git rebase` have been?" rather than "should we add this?" shifts the burden of proof to those defending the status quo. This may polarize the discussion unless concrete user experience data is introduced.

Participant positions
- **Alejandro Colomar (author)**: Advocates for `git brebase` as a standalone porcelain tool built on top of `git rebase` (plumbing). Argues that `git rebase` should remain simple and predictable, while `git brebase` can afford to be more complex and opinionated. Emphasizes the importance of segment-level `--abort`/`--continue` for recursive resolution and warns that integrating the functionality into `git rebase` would blur its responsibilities. Receptive to feedback on implementation details (e.g., `trap`, detached HEAD bug) but does not signal a shift in the core design. Views Nico’s `--direct` flag as evidence that the two approaches are fundamentally incompatible.
- **Nico Williams**: Proposes that bisect-driven conflict resolution *should have been* the default behavior of `git rebase` from the beginning, framing the current design as an accident of history. Argues that the incremental workflow is a self-evident improvement and shifts the burden of proof to those defending the status quo. Has not addressed merge commits, recursive resolution, segment-level operations, or edge cases (e.g., detached HEAD) in his proposal. Enthusiastic but speculative; seeks feedback on feasibility and risks.

Related work
- **`git imerge`**: Existing tool for incremental rebasing; `git brebase` aims to replace/supplement it with a simpler workflow.
- **`git rebase --rebase-merges`**: Partially overlaps with `git brebase`’s handling of merge commits but lacks incremental conflict detection.
- **`git bisect`**: Used internally by `git brebase` to find the first conflicting commit. Nico’s proposal would integrate this into `git rebase`.

Thread identity
Subject: [RFC] git brebase: a simpler alternative to git imerge for complex rebases
Series version: RFC (now split into three scripts: `git-bisect-rebase`, `git-bisect-rebase--callback`, `git-bisect-rebase--continue`)
Originating author: Alejandro Colomar
Thread type: RFC / design discussion

Core problem or goal
Propose a tool or workflow to simplify incremental rebasing of complex histories (branches with merge commits, arbitrary commit skipping, and "trees of branches") by automating conflict detection and resolution up to the first semantic conflict. The discussion explores whether this functionality should live in a new command (`git-bisect-rebase`), be added as a flag to `git rebase`, or become the default behavior, while debating the philosophical distinction between plumbing and porcelain. The updated proposal introduces segment-level `--abort`, `--continue`, and `--quit` options to enable recursive resolution of complex branch topologies, explicitly supporting two workflows: rebasing a single branch and rebasing a "tree" of branches (a branch with multiple descendants).

Current status
Under discussion; no implementation or prior versions in Git itself. The proposal is now split into three shell scripts hosted in the Linux man-pages repository: `git-bisect-rebase` (entry point), `git-bisect-rebase--callback` (internal helper for `git bisect run`), and `git-bisect-rebase--continue` (handles `--continue`). Alejandro has refined the scripts to address prior feedback: (1) adopted `trap` for temporary file cleanup, (2) preserved detached HEAD support by writing the current commit hash to a temporary file, (3) added segment-level `--abort`, `--continue`, and `--quit` options to enable recursive resolution, and (4) provided concrete workflow algorithms for both single-branch and tree-of-branches rebasing. Nico Williams' earlier counterproposal (integrating bisect-driven conflict resolution into `git rebase` as a flag, e.g., `--first-conflict`) remains unaddressed in this iteration, as does his patch eliminating the temporary callback file. The fundamental design debate is now framed by Alejandro's explicit workflow distinction: `git-bisect-rebase` automates the "big picture" of rebasing complex histories, while `git rebase` handles fine-grained history editing and conflict resolution within a session. This usage pattern reinforces his claim that the tools are complementary and that `git rebase` should retain its plumbing role.

Key technical details
- **Updated proposal (`git-bisect-rebase`)**:
  - **Structure**: Three shell scripts (`git-bisect-rebase`, `git-bisect-rebase--callback`, `git-bisect-rebase--continue`) hosted in the Linux man-pages repository.
  - **New CLI options**: `--abort`, `--continue`, `--quit` operate at the *bisect-rebase* segment level (not the entire rebase), enabling recursive resolution of complex topologies (e.g., "trees of branches"). `--continue` automates resumption after conflict resolution; `--quit` allows users to resolve conflicts in descendant branches before resuming the parent rebase.
  - **Behavior**: Stops at the first conflicting commit (merge or semantic) using `git bisect run` with a callback script. Supports recursive resolution via segment-level operations, detached HEAD mode (via temporary file), and cleanup traps for all temporary files. The callback script still uses a temporary file (not in-memory execution or environment variables).
  - **Workflow algorithms**: Concrete examples for single-branch and tree-of-branches rebasing, demonstrating how the new options reduce redundant conflict resolution. For a tree of branches, users can `--quit` the bisect-rebase at a conflict, resolve conflicts in descendant branches, then resume the parent rebase.
  - **Design philosophy**: Porcelain tool built on top of `git rebase` (plumbing), preserving `git rebase`'s simplicity and predictability for manual history manipulation. Segment-level operations (`--abort`, `--continue`, `--quit`) are critical for recursive resolution and the complementary workflow Alejandro describes.
  - **Limitations**: Shell-based, no persistent conflict history, rudimentary option parsing (though improved), no direct merge commit creation. Still uses temporary files for callback arguments and detached HEAD state (Nico's suggested alternatives—environment variables and in-memory execution—are not adopted). Merge commit handling remains unaddressed in the workflow algorithms.
- **Counterproposal (Nico Williams)**:
  - Integrate bisect-driven conflict resolution into `git rebase` as a new flag (e.g., `--first-conflict`), with potential to make it the default later. The flag would enable automatic resumption by recording the target committish in rebase state.
  - Suggests environment variables and in-memory execution (e.g., `git bisect run sh -c '...'`) to avoid temporary files and support detached HEAD mode. Provides a gist demonstrating `getopts_long`-like functionality in bash to handle Git’s `--` separator convention. Nico's earlier patch eliminates the temporary callback file but does not address detached HEAD mode or segment-level operations.
  - Implications: Requires changes to rebase internals (state management, conflict handling), likely in C. No concrete proposal for handling merge commits, recursive resolution, or segment-level operations (e.g., `--abort`/`--continue` at the bisect segment level). Risks breaking backward compatibility and the complementary workflow Alejandro describes.
- **Files touched**: None in Git itself; the scripts are external. The three scripts are now versioned in the Linux man-pages repository.
- **Comparison with existing tools**:
  - `git imerge`: Uses a 2D matrix approach; `git-bisect-rebase` avoids this in favor of linear bisect-driven workflow with recursive resolution.
  - `git rebase --rebase-merges`: Handles merge commits but lacks incremental conflict detection and segment-level operations. Used by Alejandro for fine-grained conflict resolution within a `git-bisect-rebase` session.
  - `git rebase`: Used by Alejandro for precise, manual history manipulation within a `git-bisect-rebase` session, reinforcing the complementary relationship between the tools.

Open questions and loose ends
1. **Integration path**: Should the functionality be a new command (`git-bisect-rebase`), a flag for `git rebase` (e.g., `--first-conflict`), or the default behavior? Alejandro argues for a standalone tool to preserve `git rebase`'s plumbing role and now explicitly treats the tools as complementary; Nico leans toward a flag but leaves the door open for default behavior. The philosophical divide is deepened by Alejandro's workflow algorithms, which rely on segment-level operations that would be difficult to implement in `git rebase` without breaking backward compatibility. Nico's counterproposal remains unaddressed in this iteration.
2. **Default behavior**: Is it feasible to make bisect-driven conflict resolution the default for `git rebase`? What are the risks to existing workflows, and how would it interact with `--rebase-merges` or other flags? Alejandro warns that defaulting to bisect-driven behavior would blur `git rebase`'s responsibilities and disrupt the complementary workflow; Nico dismisses this as a non-issue but has not provided concrete risk mitigation or addressed the interaction with `--rebase-merges`.
3. **Recursive resolution**: `git-bisect-rebase` supports complex branch topologies (e.g., "trees of branches") via recursive resolution, where each segment of the rebase can itself be rebased incrementally. Nico’s counterproposal does not address this, and it is unclear how it would be implemented in `git rebase` without segment-level `--abort`/`--continue`/`--quit` operations.
4. **Segment-level vs. rebase-level operations**: Alejandro’s design requires `--abort`, `--continue`, and `--quit` to operate at the segment level (bisect-driven segment), while Nico’s proposal would operate on the entire rebase. This asymmetry could break user expectations, recursive resolution, and the complementary workflow Alejandro describes.
5. **Robustness**: Is a shell-based implementation acceptable for production use, or is a C rewrite required? The updated scripts improve robustness (e.g., `trap` cleanup, detached HEAD support) but still use temporary files for callback arguments and state management. Nico’s suggested alternatives (environment variables, in-memory execution) are not adopted. Merge commit handling remains unaddressed.
6. **Merge commits**: How would Nico’s counterproposal handle merge commits? The original `git-bisect-rebase` supports them, but Nico’s emails have not addressed this. Alejandro’s complementary workflow relies on `git rebase` for fine-grained conflict resolution, which may not fully address the needs of merge commits.
7. **State management**: Nico’s proposal requires recording the target committish in rebase state. Is this technically feasible without breaking backward compatibility, and how would it interact with existing rebase state (e.g., `--onto`, `--fork-point`)? Alejandro’s segment-level operations introduce a new layer of state that may conflict with `git rebase`'s internals.
8. **Edge cases**: Neither proposal has been tested for edge cases (e.g., nested conflicts, `--rebase-merges` interactions, conflicts in merge commits, or recursive resolution of complex topologies). Detached HEAD support is now fixed in `git-bisect-rebase`, but other edge cases remain unaddressed. Nico’s detached HEAD workflow (checking out `origin/master`, committing work, and pushing to a remote branch without creating a local branch) is supported, but his patch does not yet incorporate this fix.
9. **Adoption**: How does the counterproposal compare to `git imerge` or `git-bisect-rebase` in practice? No user feedback or testing has been reported. Alejandro’s reported usage pattern (using both tools complementarily) suggests that `git-bisect-rebase` may have value even if Nico’s proposal is implemented.
10. **Flag validation**: The scripts’ option parsing remains rudimentary (though improved) and may not meet Git’s CLI standards. Nico’s gist provides a concrete alternative for handling Git’s `--` separator convention, but Alejandro remains skeptical.
11. **Design philosophy**: Nico’s reframing of the debate as "what *should* `git rebase` have been?" rather than "should we add this?" shifts the burden of proof to those defending the status quo. Alejandro’s response deepens the philosophical divide by treating the tools as complementary and framing the current conflation as an accident of history. This may polarize the discussion unless concrete user experience data or workflow comparisons are introduced. Nico has acknowledged the complementary workflow but has not engaged with its implications for the integration path, recursive resolution, or segment-level operations.
12. **Callback script implementation**: The updated scripts still use a temporary file for callback arguments (not in-memory execution or environment variables). Nico’s earlier patch resolves this but remains unaddressed.
13. **Complementary workflow**: Alejandro’s reported usage pattern (using `git-bisect-rebase` for the "big picture" and `git rebase` for fine-grained editing) introduces a new dimension to the debate. Does this workflow justify a separate tool, or could it be accommodated by a flag in `git rebase`? How would Nico’s proposal support or disrupt this workflow? Nico has acknowledged the distinction but has not addressed its implications for the integration path or the philosophical debate.
14. **Merge commit handling**: The workflow algorithms for tree-of-branches rebasing do not explicitly address merge commits. How would `git-bisect-rebase` handle conflicts in merge commits, and how would this interact with `git rebase --rebase-merges`?
15. **Persistent conflict history**: Neither proposal includes persistent conflict history, which could be useful for debugging or resuming interrupted sessions. Is this a desirable feature, and how would it interact with the bisect-driven workflow?

Participant positions
- **Alejandro Colomar (author)**: Advocates for `git-bisect-rebase` as a standalone porcelain tool built on top of `git rebase` (plumbing). Argues that `git rebase` should remain simple and predictable for precise, manual history manipulation, while `git-bisect-rebase` automates the incremental resolution of complex rebases. Emphasizes the importance of segment-level `--abort`/`--continue`/`--quit` for recursive resolution and explicitly treats the two tools as complementary, reporting that he uses `git-bisect-rebase` as his default for rebasing but still relies on `git rebase` for fine-grained editing and conflict resolution within a session. Views the current conflation of the two tools as an accident of history. Receptive to feedback on implementation details (e.g., `trap`, detached HEAD support) but has not adopted Nico’s suggested alternatives (environment variables, in-memory execution) or engaged with his patch eliminating the temporary callback file. Skeptical of integrating bisect-driven conflict resolution into `git rebase`, citing risks to backward compatibility, the complementary workflow, and `git rebase`'s plumbing role.
- **Nico Williams**: Proposes integrating bisect-driven conflict resolution into `git rebase` as a new flag (e.g., `--first-conflict`), with potential to make it the default later. Argues that the incremental workflow is a self-evident improvement and shifts the burden of proof to those defending the status quo. Acknowledges Alejandro’s implementation concerns (detached HEAD, temporary files) and suggests environment variables and in-memory execution as solutions. Provides concrete technical suggestions (e.g., gist for `getopts_long`-like functionality, callback script embedding) and identifies real limitations (e.g., detached HEAD support). His earlier patch demonstrates a cleaner implementation of the callback logic, eliminating the temporary callback file but not addressing detached HEAD mode or segment-level operations. Has acknowledged Alejandro’s complementary workflow but has not engaged with its implications for the integration path, recursive resolution, segment-level operations, or the philosophical divide. Has not addressed merge commits, edge cases (e.g., `--rebase-merges` interactions), or the risks of making bisect-driven behavior the default. Enthusiastic but speculative; seeks feedback on feasibility and risks.

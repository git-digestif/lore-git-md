Subject: [RFC] git brebase: a simpler alternative to git imerge for complex rebases
Series version: RFC (no version number)
Originating author: Alejandro Colomar
Thread type: RFC / design discussion

Core problem or goal
Propose a tool or workflow to simplify incremental rebasing of complex histories (branches with merge commits, arbitrary commit skipping) by automating conflict detection and resolution up to the first semantic conflict. The discussion explores whether this functionality should live in a new command (`git brebase`), be added as a flag to `git rebase`, or become the default behavior of `git rebase` itself, while debating the philosophical distinction between plumbing and porcelain in Git's design.

Current status
Under discussion; no implementation or prior versions. The original proposal (`git brebase`) remains a 164-line shell script attached to the thread. Alejandro has refined the script to address feedback: (1) adopted `trap` for temporary file cleanup, (2) filtered the callback script filename from `git bisect run` output, (3) fixed detached HEAD support by writing the current commit hash to a temporary file when no branch name is available, and (4) added cleanup traps for the new temporary files. The fundamental design debate remains unresolved: Alejandro argues for a standalone porcelain command built on top of `git rebase` (plumbing), while Nico Williams proposes integrating bisect-driven conflict resolution into `git rebase` as a flag (e.g., `--first-conflict`) or even the default behavior. Alejandro now explicitly positions the two tools as complementary, reporting that he uses `git brebase` as his default for rebasing but still relies on `git rebase` for fine-grained history editing and conflict resolution within a `git brebase` session. This usage pattern reinforces his claim that the tools serve fundamentally different purposes: `git rebase` for precise, manual history manipulation, and `git brebase` for automating incremental resolution of complex rebases. Nico has acknowledged this workflow distinction but has not engaged with its implications for the integration path or the philosophical divide. Key features under discussion: (1) bisect-driven conflict detection, (2) automatic resumption of rebase after conflict resolution, (3) segment-level `--abort`/`--continue` operations, and (4) the integration path. No consensus has emerged, and no code changes to `git rebase` have been proposed or implemented.

Key technical details
- **Original proposal (`git brebase`)**:
  - Shell script using `git bisect` and `git rebase` internally.
  - New CLI options: `--pre-exec=<cmd>` (filter commits), `--post-exec=<cmd>` (validate after each step).
  - Behavior: Stops at the first conflicting commit (merge or semantic), supports recursive resolution of complex topologies (e.g., "trees of branches"), handles detached HEAD mode by writing the current commit hash to a temporary file when no branch name is available. Uses `git bisect run` with a callback script; avoids `getopts` due to Git’s CLI conventions (e.g., `--` separator); filters callback script filename from `git bisect run` output; uses `trap` for temporary file cleanup (including new files for detached HEAD support).
  - Design philosophy: Porcelain tool built on top of `git rebase` (plumbing), preserving `git rebase`’s simplicity and predictability. `--abort` and `--continue` operate at the segment level (bisect-driven segment), not the entire rebase, enabling recursive resolution. Alejandro explicitly treats `git rebase` and `git brebase` as complementary tools: `git brebase` automates the "big picture" of rebasing complex histories, while `git rebase` handles fine-grained history editing and conflict resolution within a `git brebase` session.
  - Limitations: Shell-based, no persistent conflict history, rudimentary option parsing (though improved), no direct merge commit creation. Nico’s feedback suggests environment variables and in-memory execution (e.g., `git bisect run sh -c '...'`) as alternatives to temporary files, which Alejandro has not yet adopted.
- **Counterproposal (Nico Williams)**:
  - Integrate bisect-driven conflict resolution into `git rebase` as a new flag (e.g., `--first-conflict`), with potential to make it the default behavior later. The flag would enable automatic resumption of rebase after conflict resolution by recording the target committish in rebase state.
  - Suggests using environment variables and in-memory execution (e.g., `git bisect run sh -c '...'`) to avoid temporary files and support detached HEAD mode, addressing two of Alejandro’s implementation concerns. Provides a gist demonstrating `getopts_long`-like functionality in bash to handle Git’s `--` separator convention.
  - Implications: Requires changes to rebase internals (state management, conflict handling), likely in C; no concrete proposal for handling merge commits or recursive resolution. `--abort` and `--continue` would operate on the entire rebase, not per-segment, breaking symmetry with the bisect-driven workflow and preventing recursive resolution.
- **Files touched**: None yet; both proposals remain conceptual.
- **Comparison with existing tools**:
  - `git imerge`: Uses a 2D matrix approach; `git brebase` avoids this in favor of linear bisect-driven workflow.
  - `git rebase --rebase-merges`: Handles merge commits but lacks incremental conflict detection.
  - `git rebase`: Used by Alejandro for fine-grained history editing and conflict resolution within a `git brebase` session, reinforcing the complementary relationship between the tools.

Open questions and loose ends
1. **Integration path**: Should the functionality be a new command (`git brebase`), a flag for `git rebase` (e.g., `--first-conflict`), or the default behavior? Alejandro argues for a separate command to preserve `git rebase`’s plumbing role and now explicitly treats the tools as complementary; Nico leans toward a flag but leaves the door open for default behavior later. The philosophical divide is deepened by Alejandro’s claim that the current conflation of the two tools is an accident of history. Nico has acknowledged the complementary workflow but has not engaged with its implications for the integration path or the philosophical debate.
2. **Default behavior**: Is it feasible to make bisect-driven conflict resolution the default for `git rebase`? What are the risks to existing workflows, and how would it interact with `--rebase-merges` or other flags? Alejandro warns that defaulting to bisect-driven behavior would blur `git rebase`’s responsibilities and disrupt the complementary workflow he describes; Nico dismisses this as a non-issue but has not provided concrete risk mitigation or addressed the interaction with `--rebase-merges`.
3. **Recursive resolution**: `git brebase` supports complex branch topologies (e.g., "trees of branches") via recursive resolution, where each segment of the rebase can itself be rebased incrementally. Nico’s counterproposal does not address this, and it is unclear how it would be implemented in `git rebase` without segment-level `--abort`/`--continue` operations.
4. **Segment-level vs. rebase-level operations**: Alejandro’s design requires `--abort` and `--continue` to operate at the segment level (bisect-driven segment), while Nico’s proposal would operate on the entire rebase. This asymmetry could break user expectations, recursive resolution, and the complementary workflow Alejandro describes.
5. **Robustness**: Is a shell-based implementation acceptable for production use, or is a C rewrite required? Nico’s proposal would necessitate C changes, but Alejandro’s script is functional and improving (e.g., `trap` for cleanup, detached HEAD support). Nico suggests environment variables and in-memory execution as alternatives to temporary files, but Alejandro has not yet adopted these.
6. **Merge commits**: How would Nico’s counterproposal handle merge commits? The original `git brebase` supports them, but Nico’s emails have not addressed this. Alejandro’s complementary workflow relies on `git rebase` for fine-grained conflict resolution, which may not fully address the needs of merge commits.
7. **State management**: Nico’s proposal requires recording the target committish in rebase state. Is this technically feasible without breaking backward compatibility, and how would it interact with existing rebase state (e.g., `--onto`, `--fork-point`)?
8. **Edge cases**: Neither proposal has been tested for edge cases (e.g., nested conflicts, `--rebase-merges` interactions, conflicts in merge commits, or recursive resolution of complex topologies). Detached HEAD support is now fixed in `git brebase`, but other edge cases remain unaddressed. Nico’s detached HEAD workflow (checking out `origin/master`, committing work, and pushing to a remote branch without creating a local branch) is now explicitly supported.
9. **Adoption**: How does the counterproposal compare to `git imerge` or `git brebase` in practice? No user feedback or testing has been reported. Alejandro’s reported usage pattern (using both tools complementarily) suggests that `git brebase` may have value even if Nico’s proposal is implemented.
10. **Flag validation**: The script’s option parsing remains rudimentary (though improved) and may not meet Git’s CLI standards. Nico’s gist provides a concrete alternative for handling Git’s `--` separator convention, but Alejandro remains skeptical.
11. **Design philosophy**: Nico’s reframing of the debate as "what *should* `git rebase` have been?" rather than "should we add this?" shifts the burden of proof to those defending the status quo. Alejandro’s response deepens the philosophical divide by treating the tools as complementary and framing the current conflation as an accident of history. This may polarize the discussion unless concrete user experience data or workflow comparisons are introduced. Nico has acknowledged the complementary workflow but has not engaged with its philosophical implications.
12. **Callback script implementation**: Nico proposes embedding the callback logic directly into the main script (e.g., via a sub-command or option) and passing values via environment variables, but Alejandro notes that `git bisect run` doesn’t pass arguments to the callback. This technical constraint remains unresolved.
13. **Complementary workflow**: Alejandro’s reported usage pattern (using `git brebase` for the "big picture" and `git rebase` for fine-grained editing) introduces a new dimension to the debate. Does this workflow justify a separate tool, or could it be accommodated by a flag in `git rebase`? How would Nico’s proposal support or disrupt this workflow? Nico has acknowledged the distinction but has not addressed its implications for the integration path or the philosophical debate.

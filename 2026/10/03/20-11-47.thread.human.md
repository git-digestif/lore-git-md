This thread is an RFC discussion about `git brebase`, a proposed tool to simplify incremental rebasing of complex histories—think branches with merge commits or arbitrary commit skipping—by automating conflict detection and resolution up to the first semantic conflict. The author, Alejandro Colomar, has posted a 164-line shell script that uses `git bisect` and `git rebase` internally to stop at the first conflicting commit, allowing users to resolve conflicts and resume the rebase without manually stepping through each commit. The script has evolved in response to feedback, fixing issues like detached HEAD support and improving temporary file cleanup, but its fundamental design remains unchanged: it’s a separate porcelain command built on top of `git rebase` (treated as plumbing), preserving `git rebase`’s simplicity while offering a more opinionated workflow.

The core debate revolves around whether this functionality should live in a new command (`git brebase`), be added as a flag to `git rebase`, or become the default behavior of `git rebase` itself. Alejandro argues for the first option, emphasizing that `git rebase` should remain predictable and that a separate command avoids blurring its responsibilities. Nico Williams, however, has proposed that bisect-driven conflict resolution *should have been* the default behavior of `git rebase` all along, framing the current design as an accident of history. His counterproposal suggests integrating the functionality into `git rebase` with a `--direct` flag to disable it, though he hasn’t addressed how this would handle merge commits, recursive resolution, or edge cases like detached HEAD mode. The discussion has sharpened around these integration paths, but no consensus has emerged, and no code changes to `git rebase` have been proposed or implemented.

The latest email is a technical deep dive between Alejandro and Nico, focusing on the script’s implementation details rather than the broader design. Alejandro addressed feedback on option parsing (rejecting `getopts` due to Git’s CLI conventions), temporary file handling (adopting `trap` for cleanup), and filtering the callback script’s filename from `git bisect run` output to avoid confusing users. He also acknowledged and plans to fix a bug where the script requires the user to be on a branch (not in detached HEAD mode), aligning it with `git rebase`’s behavior. While these improvements make the script more robust, they don’t resolve the larger questions: whether the tool should remain separate, how it would interact with existing rebase flags like `--rebase-merges`, or whether the incremental workflow is even desirable as a default. The thread remains in the design phase, with no clear path forward.

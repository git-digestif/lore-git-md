This thread explores `git brebase`, a proposed tool to simplify incremental rebasing of complex histories (branches with merge commits or arbitrary commit skipping) by automating conflict detection and resolution up to the first semantic conflict. The discussion centers on whether this functionality should be a new command (`git brebase`), a flag for `git rebase` (e.g., `--first-conflict`), or the default behavior of `git rebase` itself, while debating Git’s design philosophy around plumbing vs. porcelain.

Alejandro Colomar, the author, advocates for a standalone `git brebase` built on top of `git rebase` (plumbing), arguing that the two tools serve complementary purposes: `git brebase` automates the "big picture" of rebasing complex histories, while `git rebase` handles fine-grained history editing and conflict resolution within a `git brebase` session. He has refined the attached shell script to address feedback, including better temporary file cleanup, detached HEAD support, and filtering of `git bisect run` output. Nico Williams, however, proposes integrating bisect-driven conflict resolution into `git rebase` as a flag or even the default behavior, arguing that the incremental workflow is a self-evident improvement. While Nico acknowledges Alejandro’s complementary workflow—using `git brebase` for complex rebases and `git rebase` for fine-grained editing—he hasn’t engaged with the deeper philosophical argument that the tools are fundamentally distinct. The debate remains unresolved, with key questions unanswered: how to handle merge commits, recursive resolution of complex topologies, and whether a shell-based implementation is sufficient for production use. No consensus has emerged, and no code changes to `git rebase` have been proposed or implemented.

This thread explores `git brebase`, a proposed tool to simplify incremental rebasing of complex histories by automating conflict detection and resolution. Alejandro Colomar initially proposed a 164-line shell script (`git brebase`) that uses `git bisect` to identify the first conflicting commit in a rebase, allowing users to resolve conflicts incrementally. The tool is positioned as a porcelain command built on top of `git rebase` (plumbing), preserving `git rebase`'s simplicity for manual history editing while automating the "big picture" of rebasing complex topologies. Alejandro has refined the script to address feedback, including adding `trap` for cleanup, filtering callback script output, and supporting detached HEAD mode.

The core debate revolves around whether this functionality should be a standalone command (`git brebase`), a flag in `git rebase` (e.g., `--first-conflict`), or even the default behavior. Alejandro argues for a separate command, emphasizing that `git rebase` and `git brebase` serve complementary purposes: `git brebase` automates incremental resolution, while `git rebase` handles fine-grained editing and conflict resolution within a `git brebase` session. Nico Williams, however, proposes integrating the bisect-driven workflow into `git rebase` as a flag, suggesting it could eventually become the default. While Nico has acknowledged Alejandro's complementary workflow, he hasn't engaged with its implications for the integration path or the philosophical divide between plumbing and porcelain.

In the latest exchange, Nico submitted a patch to Alejandro's script that eliminates the temporary callback file by embedding the callback logic directly into the main script and using a `--bisect-run-callback` flag. This approach avoids temporary files (reducing cleanup risks) and passes arguments via positional parameters, addressing a technical constraint in `git bisect run`. The patch preserves all existing functionality—bisect-driven conflict detection, segment-level `--abort`/`--continue`, and support for `--pre-exec`/`--post-exec`—while making the implementation cleaner. However, it doesn't yet incorporate Alejandro's detached HEAD fix, and the broader design debate remains unresolved. Key open questions include the integration path, default behavior risks, recursive resolution support, and whether a shell-based implementation is production-ready. The discussion has so far focused on technical refinements rather than reaching consensus on the tool's future.

This thread explores `git-bisect-rebase` (formerly `git brebase`), a proposed tool to simplify incremental rebasing of complex histories—whether a single branch or a "tree" of branches with merge commits. Alejandro Colomar has refined the tool into three shell scripts (`git-bisect-rebase`, `git-bisect-rebase--callback`, and `git-bisect-rebase--continue`) that automate conflict detection using `git bisect` and support recursive resolution via new `--abort`, `--continue`, and `--quit` options. These operate at the *bisect-rebase segment* level, allowing users to pause, resolve conflicts in descendant branches, and resume the parent rebase—a workflow that would be difficult to replicate in `git rebase` itself.

The latest iteration strengthens the case for a standalone tool by demonstrating concrete algorithms for both single-branch and tree-of-branches rebasing, showing how the new options reduce redundant conflict resolution. Alejandro explicitly positions `git-bisect-rebase` as complementary to `git rebase`, using the latter for fine-grained history editing within a broader `git-bisect-rebase` session. This usage pattern reinforces his argument that the tools serve fundamentally different purposes: `git rebase` for plumbing-like precision, and `git-bisect-rebase` for porcelain-like automation of complex rebases. The scripts are now hosted in the Linux man-pages repository, providing version history and design context.

Key unresolved questions remain. The integration path is still contested—Alejandro advocates for a standalone tool to preserve `git rebase`'s simplicity, while Nico Williams has proposed integrating bisect-driven conflict resolution into `git rebase` as a flag (e.g., `--first-conflict`). The latest update does not engage with Nico’s counterproposal, instead deepening the philosophical divide by showing how `git-bisect-rebase`'s segment-level operations enable recursive resolution, a feature that would be hard to implement in `git rebase` without breaking backward compatibility. Technical concerns also persist, including the shell-based implementation (though now more robust), lack of persistent conflict history, and reliance on temporary files for state management. Merge commit handling and edge cases (e.g., `--rebase-merges` interactions) remain untested. The tool’s value is clearer now, but its production readiness and integration strategy are still open for debate.

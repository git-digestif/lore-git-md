This thread explores a proposal for `git brebase`, a tool designed to simplify incremental rebasing of complex histories—such as branches with merge commits or arbitrary commit skipping—by automating conflict detection and resolution up to the first semantic conflict. The discussion has evolved from evaluating `git brebase` as a standalone command to debating whether its core functionality, particularly bisect-driven conflict detection, should be integrated into `git rebase` itself.

The original proposal, authored by Alejandro Colomar, is a 164-line shell script that uses `git bisect` to identify the first conflicting commit and guides the user through resolution. It includes features like `--pre-exec` and `--post-exec` hooks for filtering commits and validating results, and it supports recursive resolution of complex branch topologies. However, it has limitations: it’s shell-based, lacks persistent conflict history, and has rudimentary option parsing. Nico Williams has countered with a proposal to integrate this workflow directly into `git rebase`, arguing that bisect-driven conflict resolution should become the default behavior when conflicts arise, with a `--direct` flag to disable it. This approach would require changes to `git rebase`’s internals, likely in C, and raises questions about backward compatibility and robustness.

The discussion remains unresolved on the integration path. Alejandro leans toward keeping `git brebase` as a standalone tool, while Nico advocates for merging the functionality into `git rebase`. Alejandro has engaged with Nico’s feedback, addressing implementation details like CLI conventions and edge cases (e.g., detached HEAD support), but he hasn’t shifted his stance on the larger design question. Key open issues include whether the new behavior should be opt-in or default, how to handle merge commits, and whether a shell-based implementation is sufficient for production use. No testing or user feedback has been reported yet, leaving the practicality of either approach unproven.

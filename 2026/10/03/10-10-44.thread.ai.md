Thread identity: user support question about Git plumbing; subject "Robust plumbing to check if `git bisect` has isolated a single commit"; originating author Alejandro Colomar; thread type user inquiry (not a patch series, RFC, or design discussion).

Core problem or goal: determine a stable, version-independent plumbing command or pipeline that can replace `git bisect visualize --oneline | wc -l` to robustly check whether `git bisect` has narrowed the candidate range to exactly one commit, *including* correct handling of skipped commits. The goal is to write a script that will not break when Git's porcelain commands change.

Current status: the question remains open. Two plumbing-based proposals have been offered and are under informal consideration: (1) a `git rev-list`/`git for-each-ref` pipeline that explicitly accounts for skipped commits (now acknowledged to be incomplete), and (2) the `--bisect` family of `git rev-list` options (`--bisect`, `--bisect-all`, `--bisect-vars`). Neither has been confirmed as the canonical or recommended approach. Alejandro Colomar has also shared a working one-liner (`git refs list | grep refs/bisect/ | sed '/good/s/^/^/' | cut -f1 -d' ' | xargs git rev-list`) that dynamically constructs the candidate set, but acknowledges it still fails to capture the bisect algorithm's internal state regarding skipped commits. As a fallback, he proposes writing a temporary script for `git bisect run`. No maintainer decision or merge status applies.

Key technical details: the inquiry centers on Git's bisect machinery and the distinction between porcelain and plumbing commands. The first proposal uses `git rev-list bisect/bad --not $(git for-each-ref --format='%(refname)' refs/bisect/good-*) $(git for-each-ref --format='%(refname)' refs/bisect/skip-*)` to count commits still under consideration, leveraging the `bisect/bad`, `bisect/good-*`, and `bisect/skip-*` refs directly. This pipeline is now known to be incomplete because the `refs/bisect/skip-*` refs mark commits to exclude but do not encode the bisect algorithm's internal state. The second proposal suggests `git rev-list --bisect` or related options as a more direct plumbing interface, but it remains untested whether these options handle skipped commits or provide a count of remaining candidates. Colomar's one-liner dynamically constructs the candidate set by negating good refs and including bad and skip refs, but it shares the same fundamental limitation as the earlier pipeline. Neither proposal introduces new symbols or on-disk format changes.

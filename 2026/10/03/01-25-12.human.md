This is a **design discussion** about the proposed "limbo" object-format state for empty Git repositories, continuing the RFC thread from Jeff King.

Jeff responds to Brian M. Carlson’s compatibility concerns by proposing a new capability, tentatively called `magic-limbo`, to avoid breaking older clients. The idea is that older clients (2.29+) would ignore the new capability and fall back to the advertised `object-format=sha1`, while newer clients would recognize `magic-limbo` and handle the limbo state appropriately. This sidesteps the issue of advertising an invalid hash algorithm (`limbo`) while still allowing dynamic format adoption on first push. Jeff acknowledges that the choice of `sha1` as the fallback is deliberate—since Git won’t switch to SHA-256 by default until `magic-limbo` is widely implemented, users who intentionally create SHA-256 repositories are expected to configure their servers accordingly.

The discussion also touches on Brian’s suggestion of using multiple `object-format` directives. Jeff dismisses this as introducing unnecessary complexity, reinforcing that a new capability is the cleaner solution. On policy enforcement, Jeff agrees that forges like GitHub would need to expose a tri-state option (SHA-1, SHA-256, or limbo) in their UI, but he considers the implementation details (e.g., config vs. command-line flags) outside the scope of Git’s protocol. The focus remains on the wire protocol and atomic state transitions, with the understanding that server-side policy hooks would be handled separately.

This exchange advances the design by addressing the most critical compatibility blocker, but the proposal is still conceptual. The next steps would likely involve prototyping the `magic-limbo` capability and testing its interaction with older clients. The thread remains open to feedback on whether this approach sufficiently mitigates the risks Brian raised.

This is a user support reply offering a plumbing-based alternative to the porcelain `git bisect visualize` command.

D. Ben Knoble responds to Alejandro Colomar’s question about how to robustly check whether `git bisect` has narrowed the candidate range to a single commit. Instead of relying on the porcelain `git bisect visualize --oneline | wc -l` pipeline, Knoble suggests using `git rev-list` to count the commits between the `bisect/bad` ref and all `bisect/good-*` refs. This approach avoids environment-variable-dependent porcelain commands and directly queries Git’s ref storage, making it version-stable for scripting.

Knoble’s proposed plumbing pipeline would look something like `git rev-list bisect/bad --not $(git for-each-ref --format='%(refname)' refs/bisect/good-*) | wc -l`, which counts the commits still under consideration. He notes that this does not account for skipped commits, but since Alejandro’s script does not use `git bisect skip`, this limitation is irrelevant here. The reply also includes a minor shell-scripting nit about the redundancy of `test $? -eq 0` in the original code, though this is tangential to the core question.

No objections or alternative proposals have been raised yet; this is the first substantive reply in the thread. The technical details introduced—`git rev-list`, `git for-each-ref`, and the `bisect/*` refs—are the key plumbing interfaces likely to be referenced in any follow-up discussion.

This is the **third patch in a four-patch bugfix series** that finally makes `git branch -m` (rename) and `git branch -c` (copy) report both the source deletion and destination creation to the `reference-transaction` hook, fixing a long-standing inconsistency where the hook only saw half the operation.

The patch rewires the copy/rename machinery to use ordinary reference transactions instead of backend-specific shortcuts. Every rename now queues two updates (source deletion and destination creation) in the same transaction, so hooks see them atomically. The destination update carries a pointer to its source, letting backends replay the source’s reflog history into the destination. This per-ref-update state replaces the transaction-wide copy/rename tracking that Patrick Steinhardt objected to in v2, and it allows multiple independent renames or copies to share a transaction.

The files backend gets special handling for directory/file (D/F) conflicts and case-only renames: it stages the destination in `packed-refs` under the source’s lock, suppressing hooks for that physical child transaction. The reftable backend simply replays the source reflog through the transaction API. Both backends now preserve the distinct final reflog records that users expect.

Performance takes a hit—files-based rename with 10,000 reflog entries slows from 5 ms to 17 ms, reftable from 44 ms to 54 ms—but the patch includes a new perf script (`t/perf/p1424-ref-copy-rename.sh`) so regressions can be tracked. The trade-off is that hooks no longer see partial changes, and the API remains generic enough to support future multi-ref operations.

Tests cover hook behavior, reflog history, HEAD preservation, source races, mixed transactions, lock failures, and cleanup. The series is now **ready for substantive review**; if Steinhardt and others sign off, it should advance to `next`.

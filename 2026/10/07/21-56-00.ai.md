This is a feature patch series (v7 of 4 patches) introducing a "matching-inspired" fetch mode for shallow repositories. The series implements the `remote.<name>.refmap` configuration and dynamic branch selection logic previously discussed, now resolving the fatal error and design ambiguity identified in v6 by making `remote.<name>.fetch` take precedence when both it and `remote.<name>.refmap` are configured.

The core goal remains unchanged: to address the performance issue where a refspec-less `git fetch` in a shallow repository negotiates history for all remote branches, causing slow or hanging operations. The v7 changes focus on edge-case handling and backward compatibility. Key updates include fixing the fatal error triggered by configuring only `remote.<name>.refmap` (now treated as a no-op unless something is explicitly fetched), and clarifying the precedence rule when both `fetch` and `refmap` are configured. The series also removes the automatic default-branch fetch, requiring users to explicitly track branches before fetching.

Files touched span `remote.c`/`remote.h` (refmap parsing and dynamic branch enumeration), `builtin/fetch.c` (integration with refmap logic), `builtin/remote.c` (new `--limited-fetch` flag), and documentation. Tests cover the new behavior, including the precedence rule and edge cases like remotes with no tracked branches. The conflict with Collin’s `followRemoteHAD` topic (merged to `seen`) is resolved.

The series is technically complete but remains under review pending Junio’s response to the precedence proposal. The implementation is well-motivated and addresses a real user pain point, with thorough test coverage and clear documentation. The design decision about `fetch` vs. `refmap` precedence is the sole remaining blocker.

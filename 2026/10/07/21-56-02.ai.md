This is the second patch in Harald Nordgren’s v7 series introducing a "matching-inspired" fetch mode for shallow repositories. It implements the core logic that infers which branches to fetch when a remote is configured with `remote.<name>.refmap` but no `remote.<name>.fetch` refspec.

The patch adds a new helper function `branches_tracking_remote()` in `remote.c` that enumerates all local branches whose `@{upstream}` points to the given remote. This list is then used to construct a dynamic refspec in `builtin/fetch.c`’s `get_ref_map()` when no explicit refspec is provided. The implementation ensures that only branches actually in use are fetched, avoiding the performance penalty of negotiating history for all remote branches.

Key technical details include:
- The `branches_tracking_remote()` helper iterates over all local branches and collects the source ref (`branch->merge[i]->src`) for each branch whose `remote_name` matches the target remote.
- In `get_ref_map()`, when no refspec is given and the remote has a refmap but no fetch refspec, the inferred refspec is built from the tracked branches and passed to `get_fetch_map()`.
- The `do_fetch()` function is updated to populate `transport_ls_refs_options.ref_prefixes` with the inferred branches, ensuring the transport layer only requests the necessary refs.
- The patch removes the automatic fetch of the remote’s default branch, requiring users to explicitly track branches before fetching.
- Tests in the new `t/t5586-fetch-refmap.sh` script verify edge cases: no branches fetched when none are tracked, correct updates when branches are added, and no duplicate fetches when multiple local branches track the same remote branch.

The implementation is clean and well-motivated, addressing the performance issue for shallow repositories without breaking backward compatibility for non-shallow repositories. The test coverage is thorough, and the documentation updates clearly explain the new behavior. The only remaining blocker for the series is Junio’s response to the precedence rule proposed in Patch 1/4.

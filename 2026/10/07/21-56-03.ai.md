This is the third patch in Harald Nordgren’s v7 series introducing a "matching-inspired" fetch mode for shallow repositories. It adds a `--limited-fetch` flag to `git remote add`, allowing users to explicitly opt into the new behavior where `git fetch` only retrieves branches tracked by local branches at the remote.

The patch updates `builtin/remote.c` to introduce the flag, which sets `remote.<name>.refmap` (e.g., `+refs/heads/*:refs/remotes/<name>/*`) instead of the traditional wildcard `remote.<name>.fetch` refspec. This ensures that a refspec-less `git fetch <name>` dynamically fetches only the branches already tracked by local branches, as implemented in earlier patches. The flag is rejected if combined with `-t/--track` or `--mirror`, since those options already specify explicit fetch behavior. Documentation in `git-remote.adoc` is updated to describe the new option, and tests in `t/t5505-remote.sh` verify its behavior, including edge cases like conflicts with `-t` and correct configuration in non-shallow repositories.

The implementation is straightforward and aligns with the series’ design goals: it provides a clear, user-facing way to enable the matching-inspired fetch mode without disrupting existing workflows. The patch is well-motivated, with clear documentation and test coverage, and it integrates cleanly with the refmap logic introduced in earlier patches. The only remaining blocker for the series is Junio’s response to the precedence rule for `remote.<name>.fetch` vs. `remote.<name>.refmap`, but this patch itself is uncontroversial and ready for review. Key technical details include the `limited_fetch` flag’s default value (`-1` for "unspecified"), the logic to determine when to use limited fetch (only when no `-t` or `--mirror` is specified), and the configuration update to set `remote.<name>.refmap` instead of `remote.<name>.fetch`.

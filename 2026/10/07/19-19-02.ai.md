This is a **design discussion follow-up** to the `--non-intrusive` clone RFC, now pivoting to address archive-based threats.

Luca Di Carlo acknowledges D. Ben Knoble’s correction: the original threat model (malicious hooks executed during `git clone`) was incorrect. The real risk comes from archives containing a `.git/` directory with pre-installed hooks, which Git *will* execute during subsequent operations like `commit` or `push`. This admission reframes the discussion entirely—`git clone` itself is not the attack vector, so a `--non-intrusive` flag would not mitigate the core issue.

The email is brief and does not propose an alternative solution, but it implicitly concedes that the RFC’s current design is misaligned with the actual threat. No new technical details (e.g., revised CLI options, on-disk markers, or restricted operations) are introduced. The thread now hinges on whether the project should pursue a different approach—such as hardening Git’s handling of `.git/` directories in archives, extending `safe.directory` to cover this case, or adopting a wrapper script/pre-clone hook pattern. The tone is collaborative but leaves the path forward unresolved.

Key unresolved questions remain:
- Should Git add protections against malicious `.git/` directories in archives, and if so, how?
- Is `safe.directory` sufficient, or does it need extension?
- Would a pre-clone hook or wrapper script (e.g., `git clone --verify`) be more appropriate than a built-in flag?
- Is user education ("be careful with archives") the only viable stopgap for now?

The thread’s next steps will likely depend on whether other participants propose concrete alternatives or rally around an existing mitigation. For now, the RFC’s original proposal is effectively on hold.

This is the second patch in a two-part **bugfix series** for the diff subsystem, addressing a subtle but long-standing inconsistency in how `git diff --relative` handles combined diffs. The first patch fixed the core logic for displaying paths relative to a prefix; this one plugs a gap in the "fast scan" code path that previously bypassed the `--relative` filter entirely.

The fast scan is an optimization used when comparing multiple trees (e.g., during merge conflicts) to quickly identify changed paths without running the full pairwise rename detection. The bug meant that even with `--relative=here/`, changes outside `here/` could still appear in the output, breaking the user's expectation that only paths under the prefix would be shown. The fix adds a post-processing step to filter the fast scan's results by the literal prefix, matching the behavior already enforced in the pairwise scan. It also ensures discarded records are properly freed to avoid memory leaks.

The patch touches only `combine-diff.c` and adds 21 lines of test coverage to `t/t4038-diff-combined.sh`, verifying two key behaviors: (1) paths outside the prefix are excluded from raw combined diff output, and (2) explicit prefixes with repeated separators (e.g., `here//`) are treated literally, consistent with ordinary diff. The tests use `git diff-tree` to exercise the fast scan directly and confirm the output is empty when all changes are filtered out.

This is a clean, focused fix with no known side effects.

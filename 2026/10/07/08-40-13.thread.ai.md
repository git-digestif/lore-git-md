Thread identity
Subject: [RFC] git clone --non-intrusive to disable local config/hooks
Series version: RFC (no patch version yet)
Originating author: Luca Di Carlo <luca@dicarlo.email>
Thread type: feature proposal / design discussion

Core problem or goal
Add a `--non-intrusive` flag to `git clone` to disable repository-local Git configuration (hooks, config, etc.) as a safety measure against malicious code execution when cloning untrusted repositories, particularly in job-interview scenarios. The original threat model assumed `git clone` itself could execute hooks, but D. Ben Knoble clarified that the real risk comes from archives containing a `.git/` directory with pre-installed hooks, which Git *will* execute during subsequent operations (e.g., `commit`, `push`).

Current status
Proposal stage; no patches posted. The email outlines desired behavior (`.nogitconfig` marker, restricted operations) but lacks implementation details, interaction with existing flags (`--template`, `--config`), or a refined threat model. The discussion has pivoted to whether the feature addresses the correct attack vector (archive-based threats vs. `clone`-time threats).

Key technical details
- Proposed CLI option: `git clone --non-intrusive`
- Proposed on-disk marker: `.nogitconfig` file in the working tree
- Restricted operations: push, fetch, and others (unspecified)
- No new symbols, subsystems, or on-disk format changes identified
- Test coverage: none proposed
- **Correction**: `git clone` does *not* execute hooks; the threat arises from archives with a `.git/` directory containing malicious hooks

Open questions and loose ends
- Is the feature solving the right problem (archive-based threats vs. `clone`-time threats)?
- How does `--non-intrusive` interact with `--template` and `--config`?
- What operations should be restricted, and how should users be notified?
- Is a pre-clone hook or wrapper script a better approach?
- Should the feature also address `git init` for existing repositories?
- Are there existing mitigations (e.g., `safe.directory`, `ignore-scripts` in npm) that could be adapted?
- Is user education ("be careful with archives") a sufficient stopgap?

Participant positions
- **Luca Di Carlo (author)**: Proposes `--non-intrusive` as a user-facing safety measure; original threat model assumed `clone` executes hooks.
- **D. Ben Knoble**: **Substantive review** correcting the threat model: `clone` does not execute hooks, but archives with `.git/` directories do. Implicitly questions whether `--non-intrusive` is the right solution and suggests existing mitigations (e.g., `safe.directory`) as alternatives. No alternative implementation proposed.

Related work
- `safe.directory` (Git’s existing mechanism to mark trusted directories)
- `ignore-scripts` in npm (a precedent for disabling hooks in package managers)
- User education as a stopgap (acknowledged as insufficient)

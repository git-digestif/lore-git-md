Thread identity
Subject: [RFC] git clone --non-intrusive to disable local config/hooks
Series version: RFC (no patch version yet)
Originating author: Luca Di Carlo <luca@dicarlo.email>
Thread type: feature proposal / design discussion

Core problem or goal
Add a safety mechanism to Git to mitigate risks from malicious hooks or configuration in untrusted repositories, particularly when cloning from archives containing a `.git/` directory. The threat model is now clearly defined: the risk arises from archives with pre-installed hooks in `.git/`, which Git executes during post-clone operations (e.g., `commit`, `push`), not during `clone` itself. The original proposal for `git clone --non-intrusive` is acknowledged as ineffective for this threat.

Current status
Proposal stage; no patches posted. The original RFC proposed `--non-intrusive` with a `.nogitconfig` marker and restricted operations, but this design was abandoned as misaligned with the actual threat. The thread has pivoted to exploring alternative mitigations, such as hardening Git’s handling of `.git/` directories in archives, extending `safe.directory`, or adopting wrapper scripts/pre-clone hooks. No revised design or implementation details have been proposed. The discussion remains stalled on whether Git should address this threat at all, with no clear consensus or path forward.

Key technical details
- Original CLI proposal: `git clone --non-intrusive` (now acknowledged as ineffective)
- Original on-disk marker: `.nogitconfig` file in the working tree (no longer relevant)
- Restricted operations: push, fetch, and others (unspecified; no longer relevant)
- **Corrected threat model**: Archives containing a `.git/` directory with malicious hooks, executed during post-clone operations (e.g., `commit`, `push`)
- No new symbols, subsystems, or on-disk format changes identified
- Test coverage: none proposed
- Existing mitigations: `safe.directory` (Git’s mechanism to mark trusted directories), `ignore-scripts` in npm (precedent for disabling hooks), `GIT_SKIP_HOOKS` environment variable (mentioned as a potential adaptation target)
- Workflow mitigations: hosted VMs or web-based code pads (e.g., for technical interviews), as suggested by Nico Williams

Open questions and loose ends
- Should Git’s scope include `git init` for existing repositories, or focus solely on `clone`?
- How should Git handle `.git/` directories in archives? Refuse to operate, warn the user, or provide a flag to disable hooks/config?
- Is `safe.directory` sufficient, or does it need extension to cover archive-based threats?
- Would a pre-clone hook or wrapper script (e.g., `git clone --verify`) be more appropriate than a built-in flag?
- Can existing mitigations (e.g., `GIT_SKIP_HOOKS`) be adapted to address this threat?
- Is user education ("be careful with archives") a sufficient stopgap, or does Git need built-in protections?
- What operations should be restricted, and how should users be notified of restrictions?
- Should Git introduce a new mechanism (e.g., a `.git/trusted` marker) to explicitly mark repositories as safe?
- Is the threat model best addressed by Git itself, or by external tooling (e.g., VMs, web apps)?

Participant positions
- **Luca Di Carlo (author)**: Initially proposed `--non-intrusive` as a user-facing safety measure, assuming `clone` executes hooks. **Position updated**: Acknowledges the threat model correction (archive-based, not `clone`-time) and implicitly concedes the original proposal is misaligned. No alternative solution proposed yet.
- **D. Ben Knoble**: **Substantive review** correcting the threat model: `clone` does not execute hooks, but archives with `.git/` directories do. Reinforces Git’s historical stance that this threat is outside its security model ("that's not really part of our security model"), but calls user education ("don’t blindly trust downloaded files") "bad advice" that won’t suffice long-term. No alternative implementation proposed, but signals interest in exploring solutions ("I'm still somewhat interested in what we can do").
- **Nico Williams**: **Surface-level contribution** suggesting external mitigations (hosted VMs, web-based code pads) rather than Git-specific changes. Implicitly treats the threat as a workflow problem, not a Git design problem, and offers no technical direction for Git itself. The comment reinforces the thread’s stalled state by deferring resolution to external tooling.

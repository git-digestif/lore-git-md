This thread began as an RFC for `git clone --non-intrusive`, a proposed flag to disable local configuration and hooks when cloning untrusted repositories. The discussion quickly corrected a key misunderstanding: the real threat isn’t hooks executing *during* `clone`, but malicious hooks in `.git/` directories extracted from archives, which Git executes during later operations like `commit` or `push`. The original proposal was abandoned as ineffective, and the thread has since focused on whether Git should address this threat at all—and if so, how.

Key participants have staked out opposing views. Luca Di Carlo, the RFC’s author, initially framed this as a Git usability problem but has not proposed an alternative design since conceding the threat model misalignment. D. Ben Knoble clarified the technical reality (hooks don’t run during `clone`) and argued that Git’s security model doesn’t cover archive-based threats, though he called user education ("don’t trust downloaded files") insufficient and left the door open for future solutions. Nico Williams weighed in with a pragmatic but Git-agnostic workaround: avoid local execution entirely by using hosted VMs or web-based code pads, reinforcing the idea that this may be a workflow problem rather than a Git design flaw.

No patches or concrete proposals have emerged, and the thread remains stalled on fundamental questions: Should Git refuse to operate on `.git/` directories in archives, warn users, or provide a flag to disable hooks? Could `safe.directory` be extended, or would a pre-clone hook or wrapper script be more appropriate? For now, the only consensus is that the original `--non-intrusive` design doesn’t solve the problem, and no clear path forward has replaced it. The discussion highlights a gap between Git’s current security model and real-world threats, but whether that gap will be filled—or left to external tooling—remains unresolved.

This is the third iteration of a performance-focused patch series that optimizes how Git writes the commit-graph after fetches. The goal is to avoid the expensive full ref scan currently triggered by `fetch.writeCommitGraph` in large repositories. Instead, the series introduces an incremental strategy that writes only the newly fetched commits when possible, falling back to a full scan only when necessary (e.g., no existing graph or multi-remote fetches).

The implementation is clean and well-motivated. It adds a three-mode enum (`COMMIT_GRAPH_WRITE_REACHABLE`, `COMMIT_GRAPH_WRITE_TIPS`, `COMMIT_GRAPH_WRITE_SKIP`) to make the policy explicit: skip writes for no-op fetches, write incrementally from updated refs when an existing graph exists, and fall back to a full scan otherwise. The series touches the commit-graph subsystem (`commit-graph.c`, `commit-graph.h`), `builtin/fetch.c`, and adds test coverage in `t/t5510-fetch.sh` and `t/t5537-fetch-shallow.sh`. Patch 1 introduces a `commit-info` subcommand to `test-tool read-graph` for verifying graph contents in tests, while Patch 2 implements the core optimization.

The benchmark numbers are compelling: in a synthetic setup with 200K refs, incremental writes reduce the time for a single ref update from ~357ms to ~9.3ms, and no-op fetches are skipped entirely. The fallback to full scans in edge cases (no existing graph or multi-remote fetches) ensures correctness without sacrificing performance in the common case. The series also handles shallow-rejected refs correctly, skipping them to avoid incomplete history issues.

This iteration (v3) addresses only surface-level feedback from v2: trimming redundant explanations in the commit message, rewording a code comment, and simplifying test scripts with `test_commit` helpers. All technical concerns from earlier reviews—such as additive seeds, split-mode reliance, ref status filtering, and shallow ref handling—were resolved in v2. The series is now uncontested and appears ready for merging, though no merge status has been reported yet.

For developers working with large repositories, this optimization is likely to be a meaningful quality-of-life improvement. The implementation is targeted, well-tested, and avoids behavioral regressions, making it a strong candidate for inclusion.

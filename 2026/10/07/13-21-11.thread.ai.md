Subject: Windows performance regression in `safe.directory` ownership check with unreachable UNC paths
Series version: N/A (bug report, not a patch series)
Originating author: Daniel Gullberg <daniel.gullberg@mmm.com>
Thread type: bug report

Core problem or goal
A performance regression on Windows causes every Git command to stall for ~25 seconds when (1) the repository is on an SMB share with ownership differing from the current user’s SID, and (2) the global `safe.directory` configuration contains an entry pointing to an unreachable UNC host. The stall occurs because the ownership check unconditionally resolves every `safe.directory` entry to a real path, triggering Windows’ network timeout for dead UNC paths even when the entry cannot match the repository.

Current status
Reported; no patch posted. Reproducible on Git for Windows 2.56.0.windows.2 and 2.46.1.windows.1. Impact is high for tools like TortoiseGit that invoke Git frequently.

Key technical details
- Platform: Windows only, triggered by SMB share repositories with mismatched ownership.
- Subsystem: `safe.directory` ownership check (`is_path_owned_by_current_user`).
- Behavior: 25-second delay before worktree setup, visible in `GIT_TRACE2_PERF` traces.
- Root cause: `safe.directory` entries are normalized (resolved to real paths) before comparison, causing Windows to contact unreachable UNC hosts.
- Proposed fix: compare the `safe.directory` entry against the repository path *before* resolving it.

Open questions and loose ends
- No patch yet; the reporter suggests an optimization but has not implemented it.
- No response from maintainers or Windows experts (Dscho, Hannes) yet.
- Unclear whether the normalization step is intentional for security reasons or an oversight.

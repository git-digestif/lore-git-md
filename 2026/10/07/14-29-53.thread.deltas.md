# Thread deltas

## 2026/10/07

- [2026/10/07/14-29-53 by Scott Chacon <scott@gitbutler.net>] Scott Chacon submitted an RFC patch to Documentation/SubmittingPatches proposing to allow responsible AI-assisted contributions under the existing DCO, requiring human review/testing and an `Assisted-by:` trailer for substantial assistance, arguing this aligns with current SFC recommendations and the approaches of Linux, Xen, and Debian.
- [2026/10/07/21-42-35 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson objected to the proposed policy, arguing that because major LLMs are trained on code from sources that prohibit copying and are known to reproduce training-set material, no one can honestly assert the DCO without knowing all training sources; as a Git distributor he expressed concern about legal liability and cited Gentoo and NetBSD provenance policies.
- [2026/10/07/22-44-01 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano critiqued the proposal, noting that the claim of legal soundness rests on output from an OpenAI model, that the proposed text is largely unenforceable aspiration, that contributors cannot practically certify the DCO for LLM output under the proposed rule, that the `Assisted-by:` trailer naming specific tools diverges from the kernel's current guidance, and that the proposed text gives maintainers less latitude to reject contributions than the kernel guidelines do.

## 2026/10/08

- [2026/10/08/04-49-27 by Scott Chacon <schacon@gmail.com>] Scott Chacon argued that knowing every source in an LLM's training set is not necessary to make a DCO certification, comparing this to human contributors who have read code under many licenses without being asked to account for everything they have read; he noted that Red Hat, the Linux Foundation and the SFC state that LLM-generated code is compatible with DCO requirements, that his argumentation follows the SFC's recommendations (which Git, as an SFC member project, should follow), that Linux has adopted a more progressive policy under the same DCO and license, and that since the Contributor Summit notes were unclear about what a "vote" meant, he provided a first version of a Linux-style position written to follow current SFC guidelines and encouraged Junio to have the SFC read it.
- [2026/10/08/05-29-48 by Luca Milanesio <luca.milanesio@gmail.com>] Luca Milanesio distinguished "learning from existing code" from "copy & pasting" code from different sources, argued that LLMs statistically blend copied code so the AI rather than the person "pressing the button" would be the author, and that fully AI-generated contributions (code totally written and reviewed by autonomous agents) should be rejected outright for lack of a legal framework assigning responsibility; he asked for links to the exact Red Hat/Linux Foundation/SFC statements on whether fully AI-generated code with no human understanding is allowed, questioned how such code could be reviewed or who would be liable for malicious backdoors, noted ongoing lawsuits over LLM training on allegedly copyrighted material, and stated that per SFC recommendations the human author remains fully responsible for and must understand every line, adding that he uses LLMs only for ideas, review and learning, not to generate contributions.
- [2026/10/08/05-53-09 by Kristoffer Haugsbakk <kristofferhaugsbakk@fastmail.com>] Kristoffer Haugsbakk rejected Scott Chacon's analogy between human contributors and LLMs as "metaphors gone amok" (comparing regulating submarines and human bodies in territorial waters because both swim), noted that corporations already use non-compete clauses to restrict knowledge workers, and said that if an individual wants to avoid the risk of a copyright lawsuit, that is their prerogative.
- [2026/10/08/13-53-11 by Scott Chacon <schacon@gmail.com>] Scott Chacon defended his use of an LLM to help draft the legal language, saying he read and edited the result and that LLMs produce correct legal documents better than most human lawyers; he cited a Red Hat article stating the DCO has never required every line to be the contributor's personal creative expression; on the Assisted-by trailer he noted the kernel guidelines say "LLM" only while SFC guidelines part 5 require disclosing the system, its version and how it assisted in machine-readable commit logs, and since Git is an SFC project he followed the SFC; on maintainer latitude he offered to change that wording to any latitude Junio wants or remove it entirely; he also gave his sha1dc patch series as an example of AI-assisted work he hesitated to submit because of Git's conservative policy.
- [2026/10/08/16-15-47 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson agreed with most SFC policies but said the document does not say projects should accept LLM-generated contributions; he argued accepting them would not massively accelerate improvements since thorough review is already a bottleneck and the security list is already flooded with dubious LLM-assisted bug reports; he said SFC's recommendation to support people who outright reject LLM systems conflicts with allowing LLM content on this list; and he stated Git is not obligated to follow SFC guidance (which also recommends leaving GitHub), noting QEMU, another SFC project, has a policy similar to Git's current one.
- [2026/10/08/18-10-47 by D. Ben Knoble <ben.knoble@gmail.com>] D. Ben Knoble shared off-topic historical reading on tools and AI, argued that "just a tool like any other" is not a sufficient justification because the tools we choose affect us and others, and quoted an "AI Pascal's wager" argument for strongly rejecting all AI-generated contributions for now, saying he would rather be in the "wish we'd done it sooner" boat than regret letting AI slop in.

## 2026/10/09

- [2026/10/09/10-22-13 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt argued that wanting people to think twice before submitting code they don't fully understand is a good thing, as otherwise the project will get even more slop.
- [2026/10/09/10-22-13 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt stated that Git already accepts AI-generated code, so loosening the policy would be a net-negative change if it caused people to stop thinking twice about sending their AI-generated code to the mailing list.
- [2026/10/09/10-22-13 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt identified the project's bottleneck as the number of developers reviewing code rather than the amount of code written, noting that this bottleneck is tightening with AI—over the last couple of months he has spent more time reviewing and the number of times he noticed too late that he was reviewing slop is going up steadily—and concluded that loosening the AI policy should not proceed without first finding solutions to this problem because it would make the preexisting problem significantly worse.
- [2026/10/09/20-39-34 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano affirmed Patrick Steinhardt's argument as "well articulated" and stated he had nothing more to add.

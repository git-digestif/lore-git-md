This is the second patch in Phillip Wood’s two-patch series that teaches `git checkout -m` to remember and reuse the original conflict labels from a merge. The patch itself is a targeted improvement to the ort merge backend, adding plumbing to store conflict labels in `.git/MERGE_LABELS` and read them back when `git checkout -m` is invoked.

The patch is well-crafted and addresses a real usability pain point: users who resolve conflicts, then later run `git checkout -m` to re-create them, currently see generic labels ("base", "ours", "theirs") instead of the original branch names they saw during the initial merge. The implementation is careful: it handles edge cases (missing or malformed `.git/MERGE_LABELS` files) by falling back to generic labels, ensures cleanup via `git commit` and `git sequencer`, and uses `strbuf_getline()` to handle cross-platform line endings correctly.

Junio’s review of v2 identified a correctness bug: the code unconditionally wrote `.git/MERGE_LABELS` even for clean merges, which could result in `(null)` strings being written to the file. Phillip acknowledges the oversight and confirms he will fix it by making the write conditional on conflicts. This aligns with the series’ goal and matches the behavior of other merge-related files like `MERGE_MSG`. The fix is straightforward and should not introduce new issues.

The series is otherwise ready for integration. The only open question is whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`) as a fallback when the user does not explicitly request a different style. Phillip proposes this for consistency, while Johannes Sixt objects on workflow flexibility grounds. Junio’s latest reply frames this as a trade-off between convenience and explicit control, noting that users can already specify the style manually when needed. No consensus has emerged, but the discussion is not blocking this patch.

The first patch in the series (a refactoring of `remove_branch_state()` to use flags instead of a boolean) is uncontroversial and could be merged independently. The second patch, once the conditional-write fix is applied, looks solid and addresses all technical feedback. If the conflict style question remains unresolved, it could be deferred to a follow-up patch without holding up this series.

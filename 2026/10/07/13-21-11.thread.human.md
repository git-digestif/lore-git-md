This thread reports a **Windows-specific performance regression** in Git when the `safe.directory` configuration contains an unreachable UNC path. Daniel Gullberg, the reporter, describes a scenario where every Git command (e.g., `git status`) stalls for ~25 seconds on repositories hosted on SMB shares, due to Windows' network timeout when resolving dead UNC paths during the ownership check. The issue affects Git for Windows versions 2.56.0 and 2.46.1, and is particularly problematic for tools like TortoiseGit that invoke Git frequently.

The root cause appears to be that `safe.directory` entries are normalized (resolved to real paths) unconditionally during the check, even when the entry cannot possibly match the current repository path. Gullberg suggests a fix: compare the entry against the repository path *before* resolving it to avoid unnecessary network lookups. The report includes detailed reproduction steps and a `GIT_TRACE2_PERF` trace confirming the stall occurs before worktree setup. No patch has been submitted yet, but the issue is framed as a targeted optimization to improve Windows compatibility.

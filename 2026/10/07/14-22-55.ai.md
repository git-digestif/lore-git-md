This is the v3 cover letter for a two-patch performance optimization targeting the commit-graph subsystem. The series introduces an incremental write strategy for `fetch.writeCommitGraph` that avoids scanning all refs after every fetch, instead writing only the newly fetched commits when possible.

The core idea is simple: when `fetch.writeCommitGraph` is enabled, Git currently rebuilds the commit-graph from all reachable refs after each fetch, which is inefficient for repositories with many refs. This series optimizes that by using only the updated refs as seeds for the commit-graph write, falling back to a full scan only when necessary (e.g., no existing graph or multi-remote fetches). The implementation introduces a three-mode enum (`COMMIT_GRAPH_WRITE_REACHABLE`, `COMMIT_GRAPH_WRITE_TIPS`, `COMMIT_GRAPH_WRITE_SKIP`) to make the policy explicit, and relies on the fact that fetch writes in split mode, so incremental updates add new layers without replacing existing coverage.

Patch 1 adds a `commit-info` subcommand to `test-tool read-graph` for verifying graph contents in tests. Patch 2 implements the optimization in `builtin/fetch.c`, with tests covering incremental writes, no-op fetches, fallback cases, and shallow-rejected refs. The changes touch `commit-graph.c` and `commit-graph.h` for the new enum, and the test helper enables precise verification of graph contents.

The benchmark numbers are compelling: in a synthetic setup (git.git with 200K extra packed refs), the incremental write reduces `fetch/write-commit-graph` time from ~357ms to ~9.3ms for a single ref update, and no-op fetches are skipped entirely. The series has been through two prior iterations, with all technical feedback from Patrick Steinhardt addressed in v2. This v3 incorporates only surface-level changes: cleaner commit messages, simplified test scripts, and minor code comment tweaks. No behavioral or correctness concerns remain, and the implementation appears solid, with careful handling of edge cases like shallow refs and multi-remote fetches.

This looks like a well-scoped, uncontroversial optimization that should benefit large repositories without introducing regressions. The series is ready for final review, with no open technical questions.

This is a brief follow-up in the `--non-intrusive` clone RFC thread. The author, Luca Di Carlo, acknowledges a key correction from D. Ben Knoble: the original threat model was mistaken. The concern wasn’t that `git clone` itself executes hooks (it doesn’t), but that archives containing a `.git/` directory with pre-installed hooks can trigger malicious code execution during later Git operations like `commit` or `push`. Luca thanks Ben for the clarification but doesn’t propose a revised design or implementation.

The thread’s focus has now shifted from a `clone`-time solution to addressing archive-based threats, though no concrete alternatives have been suggested yet. The discussion remains at the conceptual stage, with open questions about whether Git should provide built-in protections (e.g., a `.nogitconfig` marker or stricter `safe.directory` defaults) or rely on user education. For now, this email closes the loop on the initial misunderstanding but leaves the broader problem unresolved.

This is the v7 iteration of Harald Nordgren’s feature series introducing a "matching-inspired" fetch mode for shallow repositories. The series now resolves the fatal error Junio C Hamano identified in v6 by clarifying the precedence between `remote.<name>.fetch` and `remote.<name>.refmap`: when both are configured, the `fetch` refspec takes precedence, and the `refmap` setting is used only for remapping, not for deciding what to fetch. This design decision removes the ambiguity and allows the series to move forward.

The core goal remains unchanged: users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The solution dynamically fetches only the branches tracked by local branches at the remote being fetched, using the new `remote.<name>.refmap` configuration to separate namespace mappings from fetch selection logic. The v7 series is now technically complete and addresses all known design concerns.

Key changes in v7 focus on the interaction between `remote.<name>.fetch` and `remote.<name>.refmap`. The fatal error ("--refmap option is only meaningful with command-line refspec") no longer fires when only `remote.<name>.refmap` is configured. Instead, a refspec-less fetch with a refmap but no `fetch` refspec falls back to the same defaults as a remote with no configuration at all. The `refmap` setting is only used to remap branches that are explicitly fetched by name (via `remote.<name>.fetch` or command-line refspecs). New tests in `t/t5510-fetch.sh` verify this behavior, including edge cases where both settings are present.

The series touches `remote.c` and `remote.h` to implement `remote.<name>.refmap` parsing and dynamic branch enumeration logic, `builtin/fetch.c` to integrate the new fetch logic, and `builtin/remote.c` to add the `--limited-fetch` flag to `git remote add` and default it in shallow repositories. Documentation updates cover the new configuration and command-line options, and the test suite (`t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh`, and `t/t5505-remote.sh`) provides thorough coverage of the new behavior.

The design is now stable and backward-compatible. Non-shallow repositories continue using wildcard refspecs by default, and the new mode is implicitly enabled only when `remote.<name>.refmap` is configured without `remote.<name>.fetch`. The `--limited-fetch` flag for `git remote add` explicitly opts into the new mode, and shallow repositories default to it. The remote’s default branch is no longer fetched by default, which is a deliberate change from earlier iterations. This looks like a well-crafted, thoroughly tested contribution that addresses a real performance pain point for users of shallow repositories.

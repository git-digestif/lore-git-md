Subject: [PATCH] remote: defer validation of remote.<name>.followRemoteHEAD

Thread type: bugfix/refactoring

Core problem or goal
The remote configuration subsystem emits spurious warnings when `remote.<name>.followRemoteHEAD` is loaded by commands (e.g., `git push`, `git remote -v`) that never use the setting. The patch defers validation until the setting is actually needed (during `git fetch`), aligning it with an earlier change (86129fd) for `fetch.followRemoteHEAD`. The goal is to eliminate unnecessary warnings while maintaining backward compatibility.

Current status
**Ready for integration** pending graduation of the **dependency** Harald Nordgren’s `hn/fetch-refmap` topic from `seen` to `next` (or `master`). Junio C Hamano confirms the mechanical textual conflict with `hn/fetch-refmap` is fully mitigated by the helper refactoring in v4, and no further changes are needed. The patch is **technically sound, well-reviewed, and structurally settled**; all substantive feedback from v1–v4 has been addressed, including Junio’s refactoring suggestion, style nits, error message ambiguity, and Matt Hunter’s structural question about helper placement. **Integration target**: `next` (or `master`) once `hn/fetch-refmap` graduates. **Implementation approach remains contested**: Matt Hunter’s latest reply proposes folding the new logic into `get_follow_remote_head()` rather than using the standalone `determine_follow_remote_head()` helper, but this is a subjective design preference and does not block integration.

Key technical details
- **Files touched**: `remote.c`, `builtin/fetch.c`, `builtin/remote.c`, `Documentation/fetch-options.txt`, `Documentation/git-remote.txt`, `t5510-fetch.sh` (tests).
- **New/renamed symbols**:
  - `struct remote`: Removed `follow_remote_head` and `no_warn_branch`; added `follow_remote_head_raw` (string) and `follow_remote_head_seen` (flag).
  - `get_follow_remote_head()`: Now accepts a `const char *var_prefix` parameter to tailor error messages. **Matt Hunter’s alternative** would further expand this function to accept `transport` and `config`, dynamically constructing the configuration key and handling `no_warn_branch` internally.
  - `enum follow_remote_head_settings`: Moved from `remote.c` to `fetch.c`.
  - **Helper design**: Two competing approaches:
    1. **Standalone helper** (`determine_follow_remote_head()` in `builtin/fetch.c`): Extracts the logic for determining the `followRemoteHEAD` setting into a separate function, taking `transport`, `config`, and `no_warn_branch`; returns `BUILTIN_FOLLOW_REMOTE_HEAD_DFLT` or the result of `get_follow_remote_head()`. This is the approach currently implemented in v4.
    2. **Folded logic** (Matt Hunter’s proposal): Extends `get_follow_remote_head()` to accept `transport` and `config`, consolidating all logic within the existing function. The call site in `do_fetch()` is simplified to a single function call, and the configuration key is constructed dynamically.
- **Behavior change**: Validation of `remote.<name>.followRemoteHEAD` is deferred until `git fetch`, eliminating spurious warnings in other commands.
- **On-disk format**: No changes; backward compatibility maintained.
- **Test coverage**: Added in `t5510-fetch.sh` to verify lazy validation and error message clarity.
- **Conflict details**: Mechanical overlap with `hn/fetch-refmap` in `fetch.c` is fully mitigated by the `determine_follow_remote_head()` helper (or Hunter’s alternative), which both clarifies the main flow and avoids duplication. The dependency on `hn/fetch-refmap` remains the sole blocker to integration.

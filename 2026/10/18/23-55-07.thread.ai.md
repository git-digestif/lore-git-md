Subject: [PATCH] remote: defer validation of remote.<name>.followRemoteHEAD
Series version: v4 (two-patch series, per Junio’s refactoring suggestion)
Originating author: Colin Hinton
Thread type: bugfix/refactoring

Core problem or goal
The remote configuration subsystem emits spurious warnings when `remote.<name>.followRemoteHEAD` is loaded by commands (e.g., `git push`, `git remote -v`) that never use the setting. The patch defers validation until the setting is actually needed (during `git fetch`), aligning it with an earlier change (86129fd) for `fetch.followRemoteHEAD`. The goal is to eliminate unnecessary warnings while maintaining backward compatibility.

Key technical details
- **Files touched**: `remote.c`, `builtin/fetch.c`, `builtin/remote.c`, `Documentation/fetch-options.txt`, `Documentation/git-remote.txt`, `t5510-fetch.sh` (tests).
- **New/renamed symbols**:
  - `struct remote`: Removed `follow_remote_head` and `no_warn_branch`; added `follow_remote_head_raw` (string) and `follow_remote_head_seen` (flag).
  - `get_follow_remote_head()`: Now accepts a `const char *var_prefix` parameter to tailor error messages. **Hunter’s alternative** further expands this function to accept `transport` and `config`, dynamically constructing the configuration key and handling `no_warn_branch` internally.
  - `enum follow_remote_head_settings`: Moved from `remote.c` to `fetch.c`.
  - **Helper design**: Two competing approaches, both fully implemented, conflict-mitigated, and tested in `seen`:
    1. **Standalone helper** (`determine_follow_remote_head()` in `builtin/fetch.c`): Extracts the logic for determining the `followRemoteHEAD` setting into a separate function, taking `transport`, `config`, and `no_warn_branch`; returns `BUILTIN_FOLLOW_REMOTE_HEAD_DFLT` or the result of `get_follow_remote_head()`. This is the approach currently implemented in Hinton’s v4.
    2. **Folded logic** (Hunter’s proposal): Extends `get_follow_remote_head()` to accept `transport` and `config`, consolidating all logic within the existing function. The call site in `do_fetch()` is simplified to a single function call, and the configuration key is constructed dynamically. Hunter’s rewrite has been rebased, integrated into `seen`, and confirmed to produce the same mechanical conflict with `hn/fetch-refmap` as the standalone helper.
- **Behavior change**: Validation of `remote.<name>.followRemoteHEAD` is deferred until `git fetch`, eliminating spurious warnings in other commands.
- **On-disk format**: No changes; backward compatibility maintained.
- **Test coverage**: Added in `t5510-fetch.sh` to verify lazy validation and error message clarity.
- **Conflict details**: Mechanical overlap with `hn/fetch-refmap` in `fetch.c` is fully mitigated by either helper design (standalone or folded-in), which both clarify the main flow and avoid duplication. The dependency on `hn/fetch-refmap` remains the sole blocker to integration. Hunter’s live testing confirms no additional conflicts with other in-flight topics.

Subject: [PATCH] remote: defer validation of remote.<name>.followRemoteHEAD
Series version: single patch (v2 forthcoming)
Originating author: Colin Hinton
Thread type: bugfix/refactoring

Core problem or goal
The remote configuration subsystem emits spurious warnings when `remote.<name>.followRemoteHEAD` is loaded by commands (e.g., `git push`, `git remote -v`) that never use the setting. The patch defers validation until the setting is actually needed (during `git fetch`), aligning it with an earlier change (86129fd) for `fetch.followRemoteHEAD`. The goal is now narrower: only the lazy validation of `remote.<name>.followRemoteHEAD` is retained; syntax unification between the two settings has been dropped in response to review feedback.

Current status
Under review; v2 expected. The substantive blockers from v1 have been addressed: (1) error messages in `get_follow_remote_head()` now distinguish between `fetch.followRemoteHEAD` and `remote.<name>.followRemoteHEAD` by passing the variable prefix from the caller, and (2) the controversial unification of syntax (allowing `fetch.followRemoteHEAD` to accept the "warn-if-not-<branch>" value) has been abandoned. A minor style nit (long line in `builtin/remote.c`) and a refactoring suggestion (moving the `enum follow_remote_head_settings` definition to `fetch.c`) will also be incorporated. The AsciiDoc synopsis style change (replacing `$branch` with `<branch>` in `Documentation/fetch-options.txt` and `Documentation/git-remote.txt`) is now confirmed to be retained as a minor improvement.

Open questions and loose ends
1. **Style nit**: Long line in `builtin/remote.c` (minor, will be fixed in v2).
2. **Refactoring**: The `enum follow_remote_head_settings` definition will be moved to `fetch.c` since it is no longer used in `remote.c`.

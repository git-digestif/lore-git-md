This is a feature patch series (v2) adding two new options to `git reflog` and `git log -g`: `--operations` and `--historical-branch`. The series directly addresses long-standing usability pain points in reflog navigation by collapsing multi-step operations (like rebases) into single entries and showing which branch HEAD was on when each entry was recorded.

The v2 update responds to review feedback by moving the historical branch name to the left of the reflog message (e.g., `HEAD@{0}: (topic) commit: add tests`), improving alignment and readability. The commit messages have also been revised to better explain the motivation upfront, addressing a key concern from Kristoffer Haugsbakk’s review of v1. The preparatory refactoring (patch 1/3) now clearly states that the goal is to prevent drift between writing and parsing reflog messages, a point that was previously buried.

The implementation touches 15 files, including core reflog-walking logic (`reflog-walk.c`, `revision.c`), built-in commands (`builtin/rebase.c`, `builtin/checkout.c`), and documentation. The new options are additive and require `--walk-reflogs` to be set, preserving backward compatibility. The 198-line test script (`t/t1414-reflog-walk.sh`) validates edge cases like stopped rebases, branch renames, detached HEAD, and interaction with `--decorate`, suggesting thorough coverage.

The series appears well-scoped and motivated by real user pain points, as evidenced by the earlier mailing-list discussion cited in the cover letter. The v2 changes address the most significant review feedback, and the output format for `--historical-branch` is now tentatively settled. While the architectural question of whether Git’s core should replicate functionality already available in tools like `tig` remains open, the author has positioned the new options as complementary rather than redundant. This series is likely to appeal to users who rely on reflogs for debugging or auditing workflows.

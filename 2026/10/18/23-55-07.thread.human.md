This thread is about a small but important refactoring to the remote configuration subsystem. Colin Hinton’s patch defers validation of the `remote.<name>.followRemoteHEAD` setting until it’s actually needed (during `git fetch`), eliminating spurious warnings in commands like `git push` or `git remote -v` that load the setting but never use it. The change aligns with an earlier patch (86129fd) that did the same for `fetch.followRemoteHEAD`.

The patch is now in its second version, and all substantive feedback from the first round has been addressed. Matt Hunter, who previously raised key design concerns—particularly around error message clarity and the wisdom of unifying the syntax of the two settings—has now given his explicit approval, calling the patch “Looks good.” Junio C Hamano, the maintainer, had already weighed in on v2 with minor style nits (indentation, a long line, and whitespace), all of which Colin has acknowledged and will fix in v3. No technical objections remain, and the patch is effectively ready for integration once the style fixes are made.

The work touches a handful of files—`remote.c`, `builtin/fetch.c`, `builtin/remote.c`, and a few documentation and test files—and makes modest but precise changes: removing redundant fields from the `struct remote`, moving an enum definition to `fetch.c`, and tweaking error messages to distinguish between the two settings. The test coverage added in `t5510-fetch.sh` ensures the lazy validation works as intended. If you’ve seen warnings about `remote.<name>.followRemoteHEAD` in commands that don’t fetch, this patch will make them go away.

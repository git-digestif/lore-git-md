This is the latest reply in the ongoing discussion about extending `git branch --delete-merged` to detect squash-merged and rebase-merged branches. The author, Harald Nordgren, pushes back against Junio C Hamano’s proposal to use `git range-diff` for rebase detection, reporting that a local experiment showed it to be **20 times slower** than the current tree-diff approach while producing identical results.

Harald’s email is brief but substantive: he tested Junio’s suggestion to reuse `git range-diff`’s commit-matching logic (which considers log-message similarity and authorship) and found that it did not improve matching accuracy for rebased branches. Instead, it introduced a significant performance regression—10 seconds versus 0.5 seconds for the same 65-branch repository. The current implementation, which relies on tree diffs, remains both faster and equally effective at identifying branches whose changes have been integrated upstream.

This reply shifts the discussion from architectural theory to empirical evidence. Junio’s earlier proposal to split the feature into distinct `--delete-merged` (strict tip-reachability) and `--delete-irrelevant` (looser change-based detection) options remains unresolved, but Harald’s performance data suggests that `git range-diff` is not a viable path forward for rebase detection. The thread now hinges on whether the project will accept the current tree-diff approach despite its limitations (e.g., lack of rename detection, lenient attribution) or explore alternative algorithms (e.g., patch IDs, as suggested by D. Ben Knoble) that might offer a better accuracy/performance trade-off. For now, the series’ performance optimizations—batching via `changed_paths` slab and blob fetching—appear sufficient for practical use.

This thread is about a small but important fix to Git’s Makefile to ensure the Rust build works when users have a custom Cargo target directory. Andy Koppe identified the issue—where the build fails because the `gitcore` Rust library isn’t found during linking—and proposed a two-line patch to explicitly set `--target-dir target` for Cargo commands, aligning the Make build with Meson’s behavior.

The patch itself is uncontroversial and fixes the problem, but the discussion has shifted to how best to implement it. Andy argues for modifying the two `cargo build` recipes directly, distinguishing between build *preferences* (like `--quiet`, which can be overridden) and build *requirements* (like `--target-dir`, which must always be passed). He warns that adding `--target-dir` to `CARGO_ARGS` without the `override` keyword could create a maintainability trap, where future changes might silently break the build. Junio, however, suggested adding it to `CARGO_ARGS` once for cleaner maintainability, noting that `CARGO_ARGS` is already modified with `+=` for other purposes. In his latest reply, Junio acknowledges Andy’s distinction between preferences and requirements and suggests introducing a companion variable (like `BASIC_CFLAGS` for `CFLAGS`) as a potential long-term solution, though he hasn’t pushed for a reroll.

Patrick Steinhardt reviewed the patch and confirmed it’s ready for integration, though he noted a minor stylistic preference. The patch touches only the `Makefile` and affects only the Rust build rules, with no new symbols or on-disk format changes. There’s no test coverage, as this is a build-system fix. One loose end is the potential conflict with Mike Hommey’s stalled `mh/rust-crate-subdir` topic, which moves Rust code into a subdirectory, but that hasn’t been addressed in the discussion. For now, the patch is ready to go, but the thread may continue if others weigh in on the implementation trade-offs.

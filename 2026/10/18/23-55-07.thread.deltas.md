# Thread deltas

## 2026/10/18

- [2026/10/18/23-55-07 by Colin Hinton <colinlewishinton@gmail.com>] Colin Hinton submitted [PATCH v1] "remote.c: defer remote.<name>.followRemoteHEAD validation" to store the raw config string in `struct remote` and resolve it lazily in `do_fetch()` via `get_follow_remote_head()`, replacing the parsed `follow_remote_head` and `no_warn_branch` members and removing the NEEDSWORK comment, so that commands like "git push" or "git remote -v" no longer emit warnings for this setting.
- [2026/10/18/23-55-07 by Colin Hinton <colinlewishinton@gmail.com>] The patch makes `fetch.followRemoteHEAD` accept the "warn-if-not-<branch>" value (previously only recognized for `remote.<name>.followRemoteHEAD`) because both settings now use the same parser, updates the documentation and tests accordingly, and changes unrecognized-value messages to no longer name the "fetch." prefix.

## 2026/10/19

- [2026/10/19/15-37-45 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano endorsed making fetch.followRemoteHEAD and remote.<name>.followRemoteHEAD consistent and agreed the shared parser's error/warning messages should not hardcode the "fetch." prefix, but objected that the proposed messages ("missing value for 'followRemoteHEAD'", "unrecognized followRemoteHEAD value") no longer identify which variable is misconfigured, and said the two calling sites should pass the full variable name/prefix to report so the user sees exactly what to fix; he also flagged the new `if (remote->follow_remote_head_raw && !strcmp(...))` line in builtin/remote.c as overly long.
- [2026/10/19/21-24-30 by Matt Hunter <m@lfurio.us>] Matt Hunter argued the patch needs a better justification for letting fetch.followRemoteHEAD accept "warn-if-not-<branch>", since that intent makes less sense for the fetch-level variable and would be hard to revert later (citing earlier discussion), agreed with Junio that the missing variable-name prefix in the error messages should be addressed, liked the documentation style change from `$branch` to `<branch>`, flagged a couple more overly-long lines in the do_fetch() hunk, and asked whether it would be worth moving the `enum follow_remote_head_settings` definition into the fetch file since that is now its only relevant location.

Subject: [PATCH v2] prune-packed: remove implicit dependency on the_repository
Series version: standalone patch (v2), part of the_repository removal effort
Originating author: Shashank Srikumar (via GitGitGadget)
Thread type: patch (refactoring)

Core problem or goal
Eliminate the implicit use of the global `the_repository` variable in `prune_packed_objects()` by converting it to accept an explicit `struct repository *` parameter. This is a step in the ongoing project-wide effort to remove all uses of `the_repository` for better modularity and libification.

Current status
Under review; v2 posted addressing all feedback from v1. The patch is mechanically sound, and all substantive questions have been resolved. The author confirmed that the calling commands (`git prune-packed`, `git prune`, `git repack`) are registered with `RUN_SETUP` in `git.c`, ensuring `repo` is non-`NULL` in normal operation. Junio C Hamano clarified a subtle edge case: when these commands are invoked with `-h` for help, `parse_options()` exits early, but the function’s code path—now modified to accept an explicit `struct repository *`—would still execute after `parse_options()`. The patch is safe because the new `repo` references occur only after `parse_options()`. Junio’s observation does not require changes to this patch but serves as a caution for future conversions, especially those involving `RUN_SETUP_GENTLY`.

Key technical details
- Files touched: `builtin/prune-packed.c`, `builtin/prune.c`, `builtin/repack.c`, `prune-packed.c`, `prune-packed.h`
- New struct: `prune_data` (wraps `struct repository *` and `opts` integer for callback compatibility)
- Symbols: `prune_packed_objects()` now takes `struct repository *`; `USE_THE_REPOSITORY_VARIABLE` macro removed
- Subsystem: object storage (prune-packed)
- No on-disk format changes, no new CLI options, no test coverage changes
- Edge case noted: `repo` could theoretically be `NULL` if the command is invoked with `-h` outside a repository, but the patch is safe because `repo` is only dereferenced after `parse_options()`

Open questions and loose ends
None. All substantive and surface-level feedback from v1 has been addressed in v2. Junio’s clarification about the `-h` edge case does not require changes to this patch.

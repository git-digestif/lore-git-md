This is the second patch in Thomas Bachem’s three-part v5 series fixing a long-standing race condition in Git’s `rerere` subsystem, where concurrent operations contend for the shared `rr-cache` directory lock. The patch introduces `--auto` mode for `git rerere gc`, allowing auto-maintenance tasks to skip the operation if the lock is held. This reply resolves Patrick Steinhardt’s feedback on documentation clarity and flag naming, clearing the way for a final v6 update.

Thomas accepts Patrick’s suggestion to reword the `git-rerere` man page to focus on *what* the `--auto` flag does rather than *who* calls it. The revised documentation will now state that `git rerere gc` (when run by `git maintenance run --auto` or `git gc --auto`) skips the operation if the lock is held, avoiding disruption to concurrent operations. This change aligns with man-page conventions and removes the awkwardness of listing callers.

More significantly, Thomas adopts Patrick’s proposed `--skip-locked` flag name (replacing `--auto`) and marks it as a hidden option, since it’s primarily intended for `git maintenance`. The `RERERE_NOWAIT` flag in the code remains unchanged, but the `RERERE_SKIP_LOCKED` flag in patch 3 is renamed to `RERERE_WARN_LOCKED` to avoid confusion. This resolves the design tension around whether the flag should imply heuristic behavior ("auto") or its actual purpose (skipping a held lock).

Thomas also explored Patrick’s alternative suggestion to call `rerere_gc()` directly from `builtin/gc.c`, but found it impractical: the direct call causes `git maintenance run` to die with exit code 128 when the lock is held, breaking existing behavior and test expectations. The `--skip-locked` approach preserves the current error handling while achieving the same goal.

The patch remains **well-motivated** and **technically sound**, addressing a real race condition with clear test coverage. The changes here are minor but improve clarity and consistency.

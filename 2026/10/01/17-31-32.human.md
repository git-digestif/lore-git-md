This is a brief but telling reply from Junio C Hamano in the ongoing discussion about whether Git should include a `contrib/` helper for incremental rebase conflict resolution. Junio responds to Patrick Steinhardt’s mention of `git-imerge` (a third-party tool for the same workflow) with a single line: `;-)` followed by a personal endorsement. He calls `git-imerge` "one of the best things since sliced bread" and notes that he still uses it for difficult merges and rebases.

The tone is lighthearted, but the substance is clear: Junio sees `git-imerge` as a proven, effective solution for the problem that Alejandro Colomar’s `git-rebase-walk` and Nico Williams’s `bisect-rebase.sh` are trying to solve. His comment does not directly address either script, but it implicitly raises the bar for inclusion in `contrib/`. If the project already has a well-regarded tool for this workflow, why add another? The reply carries weight because it comes from the maintainer, and it suggests that the threshold for a new `contrib/` helper is not just technical merit but also a demonstrated need that existing tools do not meet.

No technical critique or alternative proposal is offered; this is purely a statement of preference and experience. The thread’s unresolved question—whether Git should include *any* helper for this workflow—now has a clear data point: the maintainer values `git-imerge` and uses it regularly. That does not close the door on `git-rebase-walk` or `bisect-rebase.sh`, but it does mean their advocates will need to explain why their scripts are worth including alongside (or instead of) an established tool.

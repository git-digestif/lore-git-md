This thread is an RFC from Artem S. Tashkinov proposing a new Git feature to preserve per-file historical modification timestamps (mtimes) based on Git commit history, rather than using the checkout or archive time as Git currently does. The motivation is to retain useful historical metadata for repositories like `linux-firmware`, where blobs are updated independently, and where mtimes are valuable for packaging, reproducible builds, and filesystem tooling (e.g., `ls -l`, `find -newermt`).

The proposal introduces a new command, tentatively called `git restore-mtimes`, which would restore mtimes using the most recent commit timestamp (author or committer, with committer as the default) where a file's content changed, following renames and ignoring mode changes or unmodified content in merges. The author suggests this could also be integrated as an option for `git clone`, `git checkout`, or `git archive`. A proof-of-concept shell implementation exists but is inefficient; the author believes Git could compute this more efficiently using its internal revision machinery.

Key open questions include whether to use author or committer timestamps by default, how to handle merge semantics (e.g., whether a merge should count as a content change if it introduces new blobs), and how to follow renames across non-linear history. The proposal is explicitly opt-in to avoid breaking build systems that depend on fresh mtimes. The thread is still in the early stages, with no reviews or decisions yet, and the feature’s scope and interface remain fluid. Likely points of contention include merge semantics and whether this belongs in core Git or as an external tool.

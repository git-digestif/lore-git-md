The `git restore-mtimes` thread proposes a new command to restore file modification timestamps (mtimes) from Git history, addressing a long-standing metadata loss that affects packaging, reproducible builds, and filesystem tooling. The idea originated with Artem S. Tashkinov, who outlined a proof-of-concept but left key design questions open—such as whether to use author or committer timestamps, how to handle merges and renames, and where to integrate the feature (standalone command, `git checkout`, or `git archive`).

Junio C Hamano’s recent review moves the discussion forward by proposing a concrete algorithm: walk the mainline history with `--first-parent --reverse`, then apply each commit’s committer timestamp to the files it modifies. This approach simplifies rename tracking (avoiding criss-cross merge complexity) but may not suit repositories with frequent merges. Junio also highlights an edge case—file concatenation (e.g., `cat a b > c`)—where the new file’s mtime would reflect the concatenation commit, not the original content’s age, which could feel counterintuitive. His endorsement of integrating this into `git archive` is a notable signal of interest, though he hasn’t weighed in on whether the feature belongs in core Git or as an external tool. The thread is now focused on refining the algorithm and addressing the concatenation scenario, with other open questions (like interface design) still unresolved. No other participants have reviewed the proposal yet.

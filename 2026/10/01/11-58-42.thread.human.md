This thread began as a proposal by Alejandro Colomar for a new `contrib/` helper script, `git-rebase-walk`, to automate incremental rebase conflict resolution—a workflow used in projects like shadow-utils and PostgreSQL. The discussion quickly evolved, with multiple implementations and proposals emerging. The original script, a minimal 10-line Bash tool, was critiqued for performance and interface limitations, leading to Nico Williams’ bisection-based alternative, `bisect-rebase.sh`. Colomar later refined this into `git-bisect-rebase`, a 52-line script with a Git-like interface, which Nico has since endorsed as the leading candidate for `contrib/` inclusion. Simon Richter also proposed a conceptual `bisect-rebase` command that integrates test execution to detect semantic conflicts, though this remains unimplemented.

The core question—whether Git should include *any* helper for this workflow—remains unresolved. Junio C Hamano has praised `git-imerge`, a third-party Python tool, as a proven solution, while Patrick Steinhardt argues the functionality belongs in `git rebase` itself rather than a standalone script. Colomar now agrees with Steinhardt and plans to distribute `git-bisect-rebase` separately (e.g., via `manpages-utils`) while pursuing direct integration into `git rebase`, proposing `--first-conflict` as a potential option name. Nico Williams has endorsed this naming, suggesting `--onto-first-conflict` as an alternative. The thread has converged on `git-bisect-rebase` as the most suitable implementation for now, but the broader debate over whether Git should endorse any script—or instead focus on integrating the workflow into `git rebase`—continues. No maintainer decision has been made, and the performance trade-offs of the bisection-based approach (O(N log N) worst-case) remain a consideration.

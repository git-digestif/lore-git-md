This thread is about whether Git should include a helper script in its `contrib/` area to automate incremental rebase conflict resolution—a workflow already used in projects like shadow-utils and PostgreSQL. The original proposal, `git-rebase-walk`, was a minimal 10-line Bash script that rebases HEAD onto each commit in reverse topological order, stopping at conflicts for manual resolution. The discussion has since shifted toward bisection-based approaches, with Alejandro Colomar’s `git-bisect-rebase` (a 52-line script) emerging as the leading candidate due to its simplicity and alignment with Git’s interface.

Junio C Hamano and Patrick Steinhardt have both noted that `git-imerge`, a third-party Python tool, already serves this purpose effectively, with Junio calling it "one of the best things since sliced bread." While Junio hasn’t ruled out including a helper in `contrib/`, his praise for `git-imerge` suggests a preference for relying on the existing tool rather than duplicating its functionality. The thread has converged on `git-bisect-rebase` as the most suitable implementation if inclusion is approved, though Simon Richter has proposed an alternative direction: a `bisect-rebase` command that integrates optional test execution (e.g., `make check`) to detect semantic conflicts alongside rebase failures. Nico Williams, whose earlier script inspired `git-bisect-rebase`, has endorsed this conceptual approach, reinforcing the shift away from the original linear strategy.

The key open questions remain whether Git should include *any* helper for this workflow, given `git-imerge`’s maturity, and if so, which implementation—`git-bisect-rebase` or Simon’s test-integrated variant—is most appropriate. The performance trade-offs (O(N) for linear vs. O(N log N) worst-case for bisection) and the naming (`git-bisect-rebase` vs. `rebase-bisect`) are still unresolved. No maintainer decision has been made, and the broader debate over whether this workflow justifies inclusion in `contrib/` continues.

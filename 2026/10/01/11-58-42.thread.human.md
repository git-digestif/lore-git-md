This thread began as a proposal for a new `contrib/` helper script to automate incremental rebase conflict resolution, and it has evolved into a nuanced discussion about workflow design and project scope. Alejandro Colomar initially offered `git-rebase-walk`, a minimal Bash script that rebases HEAD onto each commit in reversed topological order between HEAD and a target. The conversation quickly converged on a bisection-based approach, with Colomar’s `git-bisect-rebase`—a simplified, Git-like adaptation of Nico Williams’ deprecated `bisect-rebase.sh`—emerging as the leading candidate for `contrib/` inclusion. Simon Richter proposed a more ambitious concept: a `bisect-rebase` command that integrates bisection with optional test execution, though this remains unimplemented.

The core question is whether Git should include *any* helper for this workflow, given Junio C Hamano’s strong endorsement of the third-party tool `git-imerge` as a proven solution, and Patrick Steinhardt’s preference for integrating the functionality directly into `git rebase` itself. Colomar now agrees with Steinhardt’s assessment and plans to distribute `git-bisect-rebase` separately (e.g., via `manpages-utils`) as an interim measure while pursuing integration into `git rebase`, proposing `--first-conflict` as a potential option name. Nico Williams suggested `--onto-first-conflict` as a more explicit alternative, while Phillip Wood advocated for `--incremental` or `--progressive` and a single-shot workflow where `git rebase --continue` automatically advances to the next conflicting commit.

Colomar’s latest email decisively settles the workflow debate: his detailed 150-line shell session demonstrates that a multi-shot workflow—where the user manually controls the rebase order—is essential for complex dependency graphs, such as rebasing a tree of interdependent branches. This rules out single-shot implementations like Phillip Wood’s proposal, which would break real-world use cases. The demonstration also highlights the practical utility of `git-bisect-rebase` for projects like `shadow-utils`, Linux man-pages, and PostgreSQL, where manual control and verification (e.g., via `git range-diff`) are critical. The thread’s focus has now shifted from "whether" to "how" to implement incremental rebase, with the multi-shot requirement firmly established. The unresolved questions remain whether the project will accept `git-bisect-rebase` in `contrib/`, pursue a built-in option, or continue relying on third-party tools like `git-imerge`.

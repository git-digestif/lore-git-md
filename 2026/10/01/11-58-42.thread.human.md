This thread is about whether Git should include a helper script in `contrib/` to make rebasing large, conflict-prone branches less painful. Alejandro Colomar kicked it off with `git-rebase-walk`, a tiny Bash script that rebases HEAD onto each commit in reverse order between HEAD and a target, stopping at each conflict. The discussion quickly converged on a bisection-based approach, and Colomar’s revised `git-bisect-rebase`—a 52-line script that finds the first upstream commit causing a conflict—has emerged as the leading candidate.

The core question is whether Git needs *any* such helper, given Junio Hamano’s strong endorsement of the third-party tool `git-imerge` and Patrick Steinhardt’s preference for integrating the functionality directly into `git rebase` itself. Colomar now plans to distribute `git-bisect-rebase` separately under the `git-` namespace while pursuing a `--first-conflict` option for `git rebase`. Nico Williams, who originally proposed the bisection approach, has deprecated his own script in favor of Colomar’s and clarified that `bisect-rebase` is meant for rebasing a single branch across thousands of upstream commits—not for handling stacked branches, which `git rebase --update-refs` already addresses. Phillip Wood initially pushed for a single-shot workflow where `git rebase --continue` would automatically advance to the next conflict, but Colomar demonstrated that this breaks complex workflows; Phillip has since proposed extending `--update-refs` to automate rebasing interdependent branches with "break" commands for inspection.

What’s still open: whether the project wants a helper in `contrib/` at all, whether `git-bisect-rebase` is the right implementation, and whether the performance trade-offs (O(N log N) worst-case) are acceptable. The naming (`git-bisect-rebase` vs. `rebase-bisect`) and interface (`--first-conflict` vs. `--onto-first-conflict`) are also unresolved. Nico’s latest email reinforces that `bisect-rebase` and `--update-refs` solve different problems, but the maintainers haven’t weighed in on whether either—or both—should be part of Git.

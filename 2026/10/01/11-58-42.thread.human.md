This thread is about whether Git should include a helper script in its `contrib/` area to automate incremental rebase conflict resolution—a workflow already served by the third-party tool `git-imerge`. The discussion began with Alejandro Colomar’s minimal `git-rebase-walk` script, a 10-line Bash tool that rebases HEAD onto each commit in reverse topological order, stopping at conflicts for manual resolution. Nico Williams then proposed `bisect-rebase.sh`, a more sophisticated bisection-based approach that reduces the number of conflict resolutions, and Colomar later refined this into `git-bisect-rebase`, a 52-line script with a cleaner interface matching Git’s conventions.

The key question is whether Git should endorse *any* such helper, given Junio C Hamano’s strong praise for `git-imerge` as a mature, proven solution. Junio called it "one of the best things since sliced bread" and noted its occasional use in his own workflow, suggesting a preference for relying on the third-party tool rather than duplicating its functionality. Patrick Steinhardt echoed this sentiment, questioning the need for a `contrib/` helper when `git-imerge` already exists. Colomar and Williams, however, argue for a shell-based alternative, citing `git-imerge`’s stagnation (no updates in six years) and Python dependency as drawbacks. The discussion has now converged on `git-bisect-rebase` as the leading candidate for `contrib/` inclusion, with Williams endorsing its single-parameter interface and alignment with Git’s conventions.

The latest email from Williams clarifies the performance trade-offs of the bisection-based approach: while it can resolve conflicts in O(N log N) time in the worst case (when every upstream commit introduces conflicts), it remains more efficient than `git-rebase-walk`’s O(N) approach for large histories. This nuance may influence the maintainers’ decision, as it highlights the script’s efficiency gains at the cost of added complexity. Open questions remain: whether the workflow is considered generally useful enough to justify inclusion, whether `git-bisect-rebase`’s performance and interface are sufficient, and whether the project prefers to rely on `git-imerge` despite its stagnation. No maintainer decision has been made, and the thread is still open.

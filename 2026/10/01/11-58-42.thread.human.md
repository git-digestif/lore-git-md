This thread is about whether Git should include a helper script in its `contrib/` area to automate incremental rebase conflict resolution—a workflow already served by the third-party tool `git-imerge`. Alejandro Colomar kicked off the discussion with `git-rebase-walk`, a minimal 10-line Bash script that rebases HEAD onto each commit in reversed topological order, stopping at each conflict for manual resolution. Nico Williams then proposed `bisect-rebase.sh`, a more sophisticated 93-line script that uses a bisection-like strategy to reduce the number of conflict resolutions from O(n) to O(k), where k is the number of conflicting commits.

The core question is whether Git should endorse either script, given Junio C Hamano’s strong praise for `git-imerge` as a mature, proven solution. Junio called it "one of the best things since sliced bread" and noted its occasional use in his own workflow, though he hasn’t explicitly ruled out including a helper in `contrib/`. Patrick Steinhardt also questioned the need for a new tool when `git-imerge` already exists. Alejandro continues to advocate for `git-rebase-walk`, emphasizing its simplicity and robustness for smaller-scale rebases, while acknowledging `bisect-rebase.sh`’s superior performance for large histories. Nico, meanwhile, has clarified that his script is still a candidate for submission once internal approval is secured, keeping it in play for potential inclusion.

The discussion remains open on whether Git should include *any* helper, which implementation is most suitable, and whether the workflow is general enough to justify inclusion. The naming convention (`git-rebase-walk` vs. alternatives) is also unresolved. No maintainer decision has been made, and the thread is still exploring trade-offs between minimalism, performance, and existing solutions.

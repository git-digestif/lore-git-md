This thread is about whether Git should include a helper script for incremental rebase conflict resolution—either in `contrib/` or as a built-in `git rebase` option. The discussion began with Alejandro Colomar’s `git-rebase-walk`, a minimal Bash script that rebases HEAD onto each commit in reverse topological order, stopping at conflicts. The conversation has since shifted toward a bisection-based approach, with Colomar’s `git-bisect-rebase` (a simplified, Git-like adaptation of Nico Williams’ deprecated `bisect-rebase.sh`) emerging as the leading candidate for `contrib/` inclusion. Simon Richter has also proposed a conceptual `bisect-rebase` command that integrates optional test execution, though this remains unimplemented.

The core question is whether Git should endorse any helper for this workflow, given Junio C Hamano’s strong endorsement of the third-party tool `git-imerge` as a mature, proven solution. Patrick Steinhardt and Phillip Wood have both argued that the functionality would be better integrated directly into `git rebase` itself, with Phillip proposing `--incremental` or `--progressive` as potential option names. He also advocates for a single-shot workflow where `git rebase --continue` automatically advances to the next conflict, improving usability over the current multi-shot approach. Colomar now agrees with this direction and plans to distribute `git-bisect-rebase` separately (e.g., via `manpages-utils`) while pursuing integration into `git rebase`, suggesting `--first-conflict` (or Nico’s alternative `--onto-first-conflict`) as a potential option name.

The discussion remains open on whether the project will accept any helper script in `contrib/`, but the momentum is toward direct integration into `git rebase`. Key unresolved questions include the preferred interface (`--first-conflict` vs. `--incremental`), the performance trade-offs of bisection-based scripts, and whether test execution (as proposed by Simon Richter) is a desirable feature. No maintainer decision has been made, and the thread continues to focus on *how* to implement the feature rather than *whether* to do so.

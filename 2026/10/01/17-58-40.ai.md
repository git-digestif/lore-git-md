This is a maintainer reply in the ongoing design discussion about whether custom conflict-label options belong in `git stash pop`. Junio C Hamano clarifies a key implementation detail: the sequencer (which handles `git rebase` and `git cherry-pick`) spawns `git stash apply` as a subprocess rather than calling it as an internal subroutine, which explains why the `--label-*` options were originally exposed in `stash apply` (to support `git checkout -m` with meaningful conflict labels). This technical constraint means the options cannot simply be removed from `stash apply` without breaking the sequencer's autostash functionality. However, Junio does not revisit his skepticism about extending these options to `stash pop`; he reaffirms that the feature still feels like "because we can do it" rather than "because we need to have it," and agrees with Phillip Wood that users are unlikely to manually type long label arguments for `pop`. The discussion remains stalled on the fundamental question of whether the feature belongs in the user interface at all, with no new technical objections or alternative proposals raised. The patch's fate hinges on whether the maintainers can be convinced of a compelling use case for `stash pop` that justifies the added complexity.

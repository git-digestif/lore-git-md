This is a **bugfix** targeting the `merge-ort` strategy. The patch reports a regression in the `--no-overwrite-ignore` option: when directory rename detection moves a tracked file into a path that contains an ignored, untracked file, Git silently overwrites the ignored file instead of aborting the merge. The behavior violates the documented contract of `--no-overwrite-ignore` and risks data loss for users who rely on it to protect local configuration, credentials, or build artifacts.

The reproduction script demonstrates the issue across three configurations (`merge.directoryRenames=true`, `merge.directoryRenames=conflict`, and the default). In all cases, the ignored file is overwritten with the tracked content from the other branch, and the merge either succeeds (exit 0) or reports an unrelated "file location" conflict (exit 1) without mentioning the ignored file. A control case confirms that direct collisions (without rename detection) are correctly blocked.

The commit message is thorough: it includes a clear problem statement, steps to reproduce, expected vs. actual behavior, and a list of tested Git versions (2.54.0 through 2.56.0.138). The author also explains the real-world impact—users or tools relying on `--no-overwrite-ignore` can lose unversioned data with no warning. The patch is well-motivated and ready for review; the next step is likely a fix in the `merge-ort` code path that handles directory renames. Key files involved are likely in `merge-ort.c` and related merge strategy logic.

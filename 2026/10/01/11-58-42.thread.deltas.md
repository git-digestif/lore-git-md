## 2026/10/06

- [2026/10/06/14-01-29 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood argued that Alejandro's example instead shows a need to improve `git rebase --update-refs` so it can rebase a tree of branches automatically, since doing it manually is labor intensive and error-prone (easy to forget whether to resolve a conflict or abort and check out another branch); he noted that `git rebase --update-refs --rebase-merges main B` rebases A and B but offers no way to include C, and suggested perhaps inserting "break" commands after each branch is rebased so the user can check the range-diff.
- [2026/10/06/14-58-24 by Nico Williams <nico@cryptonector.com>] Nico Williams countered that it is not the same problem: his bisect-rebase use case is rebasing quickly across thousands of upstream commits, not rebasing stacked branches all at once, and the two features (`--update-refs` and bisect-rebase) are orthogonal; he reported having used the bisect-rebase script to rebase an old branch off PostgreSQL to the latest upstream, 10,135 commits in his case. He also questioned Phillip's "break" idea, saying the scripts already stop at conflicts needing resolution, that stopping at every bisection step would only be useful if the user could judge conflicts simple enough to skip the rest of the bisection, and that such an option could be painful if mostly not elected -- "if it works, great, and if not start over without that option."
- [2026/10/06/16-45-52 by Alejandro Colomar <alx@kernel.org>] Alejandro Colomar responded that forgetting to abort is inconsequential (aborting too much just costs one more command with the same number of conflict resolutions; the worst case of forgetting to abort before solving is resolving the same conflict twice). He argued `--update-refs` would need to present conflicts too, with a recursive abort-and-bisect-rebase of children after each conflict, which he does not think should be implemented as a recursive rebase within rebase, and that branch ordering could be problematic; for now he thinks the safest thing is to keep it multi-shot, with possible integration into git-rebase(1) discussed only once users are familiar with the interface. On Nico's break-point idea, he said break points could perhaps be inserted at the end only in rebases known to fail (the "conflicting rebase" at the end of his script) -- "that 'could' work. I'm not convinced though."

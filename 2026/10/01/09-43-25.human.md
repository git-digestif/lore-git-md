This is an RFC proposing a new feature to preserve per-file historical modification timestamps (mtimes) from Git history.

Artem S. Tashkinov suggests adding a `git restore-mtimes` command (and possibly `--historical-mtimes` options to `git clone` and `git checkout`) to restore file timestamps based on when their content last changed in Git history, rather than using the checkout time. The motivation is that current Git behavior discards useful historical information—for example, in repositories like linux-firmware, where thousands of blobs have been updated independently over years, filesystem tools like `ls -l` or `find` lose the ability to show when a file was last modified in Git.

The proposal defines "historical mtime" as the timestamp of the newest commit where a file's *content* changed (ignoring pure renames or mode-only changes). The author has a proof-of-concept shell implementation but notes that a native Git implementation would be far more efficient. Key discussion points include whether to default to author or committer timestamps, how to handle merges (e.g., whether a merge should count as a content change if it introduces new blobs), and whether this should be a standalone command, a checkout option, or an `archive` feature.

The use cases extend to packaging and reproducible builds, where source snapshots often lose per-file timestamp information. Artem also suggests that `git archive --historical-mtimes` could preserve this information directly in generated archives. The feature would be opt-in, as some build systems depend on fresh mtimes. The email seeks feedback on whether the Git project sees value in exposing this information natively and what interface would fit best.

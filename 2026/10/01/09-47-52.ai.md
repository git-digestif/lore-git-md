This is a substantive review reply in the ongoing discussion about whether custom conflict-label options belong in `git stash pop`. Phillip Wood agrees with Junio C Hamano that the underlying machinery for custom labels (originally created for `git checkout -m`) is justified, but he is skeptical about exposing these options in `git stash pop`. He suggests that while `stash apply` might have a valid use case for scripts or automated tools (like `git checkout -m`), `stash pop` is unlikely to benefit from them in practice, as users are unlikely to type out long label arguments manually. He also notes that scripts should prefer `stash create` and `stash apply` over `stash push` and `stash pop`, which already covers the use case for custom labels. The discussion remains focused on the design rationale rather than the implementation itself, with no new technical objections raised.

This is an RFC proposing a new feature to preserve per-file historical modification timestamps (mtimes) derived from Git history. The author, Artem S. Tashkinov, argues that current Git behavior (assigning checkout or archive time as mtimes) discards useful historical information, particularly for repositories containing independently updated blobs like `linux-firmware`. The proposal introduces a new command, tentatively named `git restore-mtimes`, along with potential convenience options for `git clone` and `git checkout`, to restore mtimes based on the most recent commit where a file's content changed.

The core idea is to use Git commit timestamps (either author or committer, with committer as the proposed default) as the basis for mtimes, following renames and ignoring pure mode changes or unmodified content in merges. The author highlights use cases in packaging, reproducible builds, and filesystem tooling (e.g., `ls -l`, `find -newermt`), where historical mtimes could provide deterministic, meaningful metadata. A proof-of-concept shell implementation exists but is inefficient; the author suggests Git could compute this more efficiently using internal revision machinery.

Key open questions include: whether to default to author or committer timestamps, how to handle merge semantics (e.g., whether a merge should count as a content change if it introduces new blobs), and how to follow renames across non-linear history. The author also asks whether this should be a standalone command, an option to existing commands (e.g., `git checkout --historical-mtimes`), or integrated into `git archive` to preserve mtimes in source archives. The proposal is explicitly opt-in to avoid breaking build systems that depend on fresh mtimes.

The motivation is clear and practical, targeting repositories with independently updated blobs where mtime loss is most acute. The technical approach—deriving mtimes from commit history—is deterministic and avoids storing original filesystem timestamps, which Git does not preserve. The proposal acknowledges limitations (e.g., rename inference) and focuses on use cases where approximate historical mtimes are still valuable. The author’s willingness to share the proof-of-concept suggests seriousness, though the feature’s scope and interface remain fluid. Likely points of contention include merge semantics and whether this belongs in core Git or as an external tool.

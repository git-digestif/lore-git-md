This is a follow-up in the ongoing design discussion about whether custom conflict-label options belong in `git stash pop`. Junio C Hamano clarifies a key implementation detail: the sequencer (which handles `git rebase` and `git cherry-pick`) already spawns `git stash apply` as a subprocess rather than calling it internally, which explains why the `--label-ours`, `--label-theirs`, and `--label-base` options were originally exposed in `stash apply`—they were needed for the sequencer’s autostash functionality. This technical constraint means the options cannot simply be removed from `stash apply` without breaking the sequencer’s conflict labeling.

Junio and Phillip Wood remain unconvinced that `stash pop` needs these options. Junio reiterates that the feature feels like "because we can do it" rather than "because we need to have it," while Phillip adds that scripts (the most likely users of custom labels) should already be using `stash create` and `stash apply` instead of `stash push` and `stash pop`. The discussion is now focused on whether the patch should proceed despite the lack of a clear use case for `pop`, or if the options should be reconsidered for `apply` as well. No new technical objections to the implementation itself have been raised.

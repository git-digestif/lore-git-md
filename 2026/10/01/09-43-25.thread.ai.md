Thread identity: RFC patch proposing `git restore-mtimes`, a new command to preserve per-file historical modification timestamps (mtimes) derived from Git commit history. Originating author: Artem S. Tashkinov. Thread type: feature proposal (RFC).

Core problem or goal: Git currently discards historical mtimes, assigning checkout/archive time instead. This loses useful metadata for repositories with independently updated blobs (e.g., `linux-firmware`), breaking use cases like packaging, reproducible builds, and filesystem tooling (`ls -l`, `find -newermt`). The proposal aims to restore mtimes based on the most recent commit where a file's *content* changed, following renames and ignoring mode changes or unmodified merges.

Current status: Proposal stage (RFC). No prior versions or integration status. Key technical details:
- New command: `git restore-mtimes` (tentative name).
- Proposed defaults: Use committer timestamps (author timestamps also considered), follow renames, ignore mode changes.
- Files/subsystems: No existing Git internals modified yet; proof-of-concept shell implementation exists but is inefficient. Potential integration points: `git clone`, `git checkout`, or `git archive`.
- New symbols: Command name (`git-restore-mtimes`), CLI options (e.g., `--historical-mtimes` for existing commands).
- Behavior: Opt-in; deterministic (derived from commit history), not filesystem timestamps.
- **Algorithm proposal**: Junio suggests walking history with `--first-parent --reverse` and applying each commit’s committer timestamp to the files it modifies. This linearizes history and avoids rename-following complexity but may not suit repositories with frequent merges or criss-cross renames.
- **Edge case**: File concatenation (e.g., `cat a b > c`) would assign the concatenation commit’s timestamp to `c`, even though its content is not "new" to the repository. This may feel counterintuitive for some use cases.

Open questions and loose ends:
1. **Timestamp source**: Default to author or committer timestamps? Junio’s proposal uses committer timestamps.
2. **Merge semantics**: Should a merge count as a content change if it introduces new blobs? Junio’s `--first-parent` approach sidesteps this by ignoring non-mainline history.
3. **Rename handling**: How to follow renames across non-linear history (e.g., criss-cross merges)? Junio’s proposal avoids this by linearizing history.
4. **Interface**: Standalone command (`git restore-mtimes`), option to existing commands (e.g., `git checkout --historical-mtimes`), or `git archive` integration? Junio explicitly calls `git archive` integration "interesting."
5. **Performance**: Proof-of-concept is inefficient; Git’s revision machinery could optimize Junio’s proposed algorithm.
6. **Scope**: Should this be in core Git or an external tool? Junio does not express a preference.
7. **File concatenation**: How to handle the edge case where a file’s content is derived from existing blobs (e.g., `cat a b > c`)? No resolution yet.

Participant positions:

Raised the file-concatenation edge case. Neutral on scope (core vs. external tool). No position yet on author vs. committer timestamps or merge semantics beyond the `--first-parent` simplification.

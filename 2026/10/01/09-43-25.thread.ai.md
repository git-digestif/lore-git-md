Thread identity: RFC patch proposing `git restore-mtimes`, a new command to preserve per-file historical modification timestamps (mtimes) derived from Git commit history. Originating author: Artem S. Tashkinov. Thread type: feature proposal (RFC).

Core problem or goal: Git currently discards historical mtimes, assigning checkout/archive time instead. This loses useful metadata for repositories with independently updated blobs (e.g., `linux-firmware`), breaking use cases like packaging, reproducible builds, and filesystem tooling (`ls -l`, `find -newermt`). The proposal aims to restore mtimes based on the most recent commit where a file's *content* changed, following renames and ignoring mode changes or unmodified merges.

Current status: Proposal stage (RFC). No prior versions or integration status. Key technical details:
- New command: `git restore-mtimes` (tentative name).
- Proposed defaults: Use committer timestamps (author timestamps also considered), follow renames, ignore mode changes.
- Files/subsystems: No existing Git internals modified yet; proof-of-concept shell implementation exists but is inefficient. Potential integration points: `git clone`, `git checkout`, or `git archive`.
- New symbols: Command name (`git-restore-mtimes`), CLI options (e.g., `--historical-mtimes` for existing commands).
- Behavior: Opt-in; deterministic (derived from commit history), not filesystem timestamps.

Open questions and loose ends:
1. **Timestamp source**: Default to author or committer timestamps?
2. **Merge semantics**: Should a merge count as a content change if it introduces new blobs?
3. **Rename handling**: How to follow renames across non-linear history (e.g., criss-cross merges)?
4. **Interface**: Standalone command (`git restore-mtimes`), option to existing commands (e.g., `git checkout --historical-mtimes`), or `git archive` integration?
5. **Performance**: Proof-of-concept is inefficient; Git’s revision machinery could optimize this.
6. **Scope**: Should this be in core Git or an external tool?

Participant positions: Only the author (Artem S. Tashkinov) has spoken so far. No reviews, objections, or endorsements yet.

Related work: None mentioned in the thread. The proposal is self-contained.

Thread identity: standalone RFC proposing a new `contrib/` helper script for incremental rebase conflict resolution, authored by Alejandro Colomar. The thread originated with `git-rebase-walk`, a minimal Bash script automating an "iterative rebase" workflow by rebasing HEAD onto each commit in reversed topological order between HEAD and a target commit. The discussion has since expanded to include three candidate implementations: `git-rebase-walk` (Colomar), `bisect-rebase.sh` (Nico Williams), and `git-bisect-rebase` (Colomar’s new bisection-based script, inspired by Nico’s but simplified and aligned with Git’s `git rebase` interface).

Core problem or goal: provide a built-in, lightweight alternative to third-party tools (e.g., `git-imerge`) for incrementally resolving rebase conflicts, with the goal of inclusion in Git's `contrib/` area. The workflow is actively used in real-world projects (shadow-utils, Linux man-pages, PostgreSQL), and the discussion centers on whether Git should include *any* helper for this workflow, and if so, which implementation is most suitable. The unresolved question remains whether the project prefers a minimal, robust script (`git-rebase-walk`), a more sophisticated and performant one (`bisect-rebase.sh` or `git-bisect-rebase`), or neither, given the existence of `git-imerge`.

Current status: initial proposal with no prior versions. The original script (`git-rebase-walk`) is offered as-is, with the author volunteering to polish it if there is interest. The discussion has converged on `git-bisect-rebase` as the leading candidate for `contrib/` inclusion, following Nico Williams’ endorsement of its single-parameter interface and alignment with Git’s conventions. Junio C Hamano has endorsed `git-imerge` as a proven, existing solution, calling it "one of the best things since sliced bread" and noting its occasional use in his own workflow. While he has not explicitly ruled out inclusion of any proposed script in `contrib/`, his praise for `git-imerge` suggests a preference for relying on the third-party tool rather than duplicating its functionality. No maintainer decision has been made regarding inclusion in `contrib/`, and the broader question of whether Git should endorse any script remains open.

Key technical details: the original script (`git-rebase-walk`) is a 10-line Bash script using `git merge-base`, `git rev-list`, and `git rebase --onto` to implement the workflow. It stops at each conflicting commit, allowing manual resolution via `--continue` or `--abort`. Nico’s alternative (`bisect-rebase.sh`) is a 93-line script that uses a bisection-like strategy to find the *first* upstream commit that conflicts with the local branch, reducing the number of conflict resolutions. Colomar’s new script (`git-bisect-rebase`) is a 52-line Bash script that follows a similar bisection strategy but simplifies the interface (single-parameter usage, matching `git rebase`) and code (pipes instead of shell arrays). Neither script modifies Git's C code, build system, or test suite; all would live in `contrib/` if accepted. No new Git symbols, CLI options, or on-disk formats are introduced. The naming question (`git-bisect-rebase` vs. `git-rebase-walk`) remains unresolved, though `git-bisect-rebase` is now the preferred candidate due to its interface consistency.

Open questions and loose ends:
- Whether the project wants *any* helper for incremental rebase conflict resolution in `contrib/`, given Junio’s endorsement of `git-imerge` as a mature, existing solution and the competing claims of the candidate scripts.
- Whether the workflow is considered generally useful or niche, and if it justifies inclusion alongside or instead of third-party tools, particularly in light of `git-imerge`’s stagnation (no updates in six years) and its Python dependency (versus the shell-based proposals).
- Which implementation (if any) is most suitable for `contrib/`: the now-converged `git-bisect-rebase` (Colomar/Nico), or neither.
- Whether the performance trade-offs of `git-rebase-walk` (O(n) conflict resolutions) are addressed by the bisection-based scripts (O(k)) or remain a concern for inclusion.
- Whether the naming (`git-bisect-rebase`) will be accepted by the project or require further adjustment.

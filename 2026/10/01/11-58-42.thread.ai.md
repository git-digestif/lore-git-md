Thread identity: standalone RFC proposing a new `contrib/` helper script for incremental rebase conflict resolution, authored by Alejandro Colomar. The thread originated with `git-rebase-walk`, a minimal Bash script automating an "iterative rebase" workflow by rebasing HEAD onto each commit in reversed topological order between HEAD and a target commit. The discussion has since converged on a bisection-based approach, with four implementations or proposals now in play: the original `git-rebase-walk` (Colomar), Nico Williams’ deprecated `bisect-rebase.sh`, Colomar’s `git-bisect-rebase` (a simplified, Git-like adaptation of Nico’s script), and Simon Richter’s conceptual `bisect-rebase` or `rebase-bisect` command integrating bisection with optional test execution.

Core problem or goal: provide a built-in, lightweight alternative to third-party tools (e.g., `git-imerge`) for incrementally resolving rebase conflicts, with the goal of inclusion in Git's `contrib/` area. The workflow is actively used in real-world projects (shadow-utils, Linux man-pages, PostgreSQL), and the discussion centers on whether Git should include *any* helper for this workflow, and if so, which implementation is most suitable. The unresolved question remains whether the project prefers a minimal, robust script (`git-rebase-walk`), a more sophisticated and performant bisection-based script (`git-bisect-rebase`), a conceptual bisection-plus-testing approach (Simon Richter), or neither, given the existence of `git-imerge` and its maintainer endorsement. The thread has now clarified that the workflow must support *multi-shot* operation (manual control over rebase order for interdependent branches) rather than a single-shot approach (automatic advancement to the next conflicting commit), as demonstrated by Colomar’s use case involving a tree of branches. Phillip Wood’s latest proposal refines this further: rather than manual intervention, he suggests extending `git rebase --update-refs` to automate rebasing interdependent branches, with optional "break" commands to allow inspection via `git range-diff`. Nico Williams has now clarified that `bisect-rebase` and `--update-refs` address distinct, orthogonal problems: `bisect-rebase` is optimized for efficiently rebasing a *single branch* across a large number of upstream commits (e.g., 10,000+), while `--update-refs` handles *stacked branches* (interdependent branches). The two could be combined but are not substitutes for one another.

Current status: initial proposal with no prior versions. The original script (`git-rebase-walk`) is offered as-is, with the author volunteering to polish it if there is interest. The discussion has now fully converged on `git-bisect-rebase` as the leading candidate for `contrib/` inclusion, following Nico Williams’ endorsement of its single-parameter interface and alignment with Git’s conventions, as well as his explicit deprecation of his own `bisect-rebase.sh` in favor of Colomar’s version. Simon Richter’s proposal introduces a new conceptual direction—integrating bisection with optional test execution—but remains unimplemented. Junio C Hamano has endorsed `git-imerge` as a proven, existing solution, calling it "one of the best things since sliced bread" and noting its occasional use in his own workflow. Patrick Steinhardt has explicitly stated that the functionality would be better integrated directly into `git rebase` itself rather than as a standalone script, implying that the current proposals are stopgaps. Nico Williams has suggested `--onto-first-conflict` as an alternative, more explicit variant. Nico Williams has now clarified that `bisect-rebase` and `--update-refs` are orthogonal tools, with `bisect-rebase` targeting large upstream histories and `--update-refs` targeting stacked branches. No maintainer decision has been made regarding inclusion in `contrib/`, and the broader question of whether Git should endorse any script remains open.

Key technical details: the original script (`git-rebase-walk`) is a 10-line Bash script using `git merge-base`, `git rev-list`, and `git rebase --onto` to implement the workflow. It stops at each conflicting commit, allowing manual resolution via `--continue` or `--abort`. Nico’s alternative (`bisect-rebase.sh`) was a 93-line script that used a bisection-like strategy to find the *first* upstream commit that conflicts with the local branch, reducing the number of conflict resolutions. Colomar’s new script (`git-bisect-rebase`) is a 52-line Bash script that follows a similar bisection strategy but simplifies the interface (single-parameter usage, matching `git rebase`) and code (pipes instead of shell arrays). Nico has since deprecated `bisect-rebase.sh` in favor of `git-bisect-rebase`, which is now the consensus candidate for `contrib/` inclusion. Simon Richter’s proposal envisions a new command (`git bisect rebase <target> -x '<test-command>'`) that would use bisection to find the first upstream commit causing either a rebase conflict or a test failure, with an option to prioritize trivial resolutions. Phillip Wood’s latest feedback introduces a new technical direction: extending `git rebase --update-refs` to automate rebasing interdependent branches (e.g., `git rebase --update-refs --rebase-merges main B`), with "break" commands inserted into the rebase sequence to allow inspection via `git range-diff`. This would eliminate the need for manual branch switching and aborting while preserving the ability to verify changes incrementally. Nico Williams has clarified that `bisect-rebase` is designed for rebasing a single branch across a large number of upstream commits (e.g., 10,000+), where its O(1) best-case and O(N log N) worst-case performance are advantageous, while `--update-refs` is designed for handling stacked branches (interdependent branches). Neither script modifies Git's C code, build system, or test suite; all would live in `contrib/` if accepted. No new Git symbols, CLI options, or on-disk formats are introduced. The naming question (`git-bisect-rebase` vs. `rebase-bisect` vs. CLI option names such as `--first-conflict`, `--onto-first-conflict`, `--incremental`, or `--progressive`) remains unresolved, though `git-bisect-rebase` is now the preferred candidate for a standalone script. Nico Williams clarified that the bisection-based scripts have a best-case performance of O(1) (no conflicts) and a worst-case of O(N log N) (conflicts in every upstream commit), rather than the O(log N) one might expect from a pure bisection. This worst-case behavior is still preferable to the O(N) behavior of `git-rebase-walk` but may factor into the maintainers’ evaluation of the trade-offs.

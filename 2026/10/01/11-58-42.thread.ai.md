Thread identity: standalone RFC proposing a new `contrib/` helper script for incremental rebase conflict resolution, authored by Alejandro Colomar. The thread originated with `git-rebase-walk`, a minimal Bash script automating an "iterative rebase" workflow by rebasing HEAD onto each commit in reversed topological order between HEAD and a target commit. The discussion has since expanded to include `bisect-rebase.sh`, an alternative script by Nico Williams that uses a bisection-like strategy to reduce the number of conflict resolutions from O(n) to O(k), where k is the number of conflicting commits.

Core problem or goal: provide a built-in, lightweight alternative to third-party tools (e.g., `git-imerge`) for incrementally resolving rebase conflicts, with the goal of inclusion in Git's `contrib/` area. The workflow is actively used in real-world projects (shadow-utils, Linux man-pages, PostgreSQL), and the discussion centers on whether Git should include *any* helper for this workflow, and if so, which implementation is most suitable. The unresolved question remains whether the project prefers a minimal, robust script (`git-rebase-walk`), a more sophisticated and performant one (`bisect-rebase.sh`), or neither, given the existence of `git-imerge`.

Current status: initial proposal with no prior versions. The original script (`git-rebase-walk`) is offered as-is, with the author volunteering to polish it if there is interest. The discussion has shifted toward comparing the two scripts, with Alejandro Colomar acknowledging `bisect-rebase.sh`'s superior performance for large-scale rebases but continuing to advocate for his script's simplicity and robustness for smaller-scale use cases. Junio C Hamano has endorsed `git-imerge` as a proven, existing solution, calling it "one of the best things since sliced bread" and noting its occasional use in his own workflow. While he has not explicitly ruled out inclusion of either proposed script in `contrib/`, his praise for `git-imerge` suggests a preference for relying on the third-party tool rather than duplicating its functionality. Nico Williams has now clarified that `git-rebase-walk` *does* handle conflicts naturally, removing one of the earlier critiques. He has also revealed that `bisect-rebase.sh` has not yet been submitted to the Git project due to internal bureaucracy but remains a live candidate for inclusion. No maintainer decision has been made regarding inclusion in `contrib/`, and the broader question of whether Git should endorse either script remains open.

Key technical details: the original script (`git-rebase-walk`) is a 10-line Bash script using `git merge-base`, `git rev-list`, and `git rebase --onto` to implement the workflow. It stops at each conflicting commit, allowing manual resolution via `--continue` or `--abort`. Nico’s alternative (`bisect-rebase.sh`) is a 93-line script that uses a bisection-like strategy to find the *first* upstream commit that conflicts with the local branch, reducing the number of conflict resolutions. Neither script modifies Git's C code, build system, or test suite; both would live in `contrib/` if accepted. No new Git symbols, CLI options, or on-disk formats are introduced. The unresolved naming question (`git-rebase-walk` vs. a different convention) remains open.

Open questions and loose ends:

- Whether the workflow is considered generally useful or niche, and if it justifies inclusion alongside or instead of third-party tools, particularly in light of `git-imerge`’s stagnation (no updates in six years) and its Python dependency (versus the shell-based proposals).
- Which implementation (if any) is most suitable for `contrib/`: the minimal `git-rebase-walk`, the more sophisticated `bisect-rebase.sh`, or neither.
- Whether the performance and robustness trade-offs of `git-rebase-walk` (slowness for large histories, manual conflict handling) are addressed by `bisect-rebase.sh` or remain blockers for inclusion. The earlier critique about conflict handling has been resolved, but the performance comparison (O(n) vs. O(k)) remains unresolved.
- Whether Nico Williams will submit `bisect-rebase.sh` to the Git project, and if so, what the outcome will be. The script is still a live candidate for inclusion, pending employer approval.
- The unresolved naming question: whether Git would allow the `git-rebase-walk` name or prefer a different convention for either script.

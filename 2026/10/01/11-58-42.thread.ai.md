Thread identity: standalone RFC proposing a new `contrib/` helper script for incremental rebase conflict resolution, authored by Alejandro Colomar. The thread originated with `git-rebase-walk`, a minimal Bash script automating an "iterative rebase" workflow by rebasing HEAD onto each commit in reversed topological order between HEAD and a target commit. The discussion has since converged on a bisection-based approach, with four implementations or proposals now in play: the original `git-rebase-walk` (Colomar), Nico Williams’ deprecated `bisect-rebase.sh`, Colomar’s `git-bisect-rebase` (a simplified, Git-like adaptation of Nico’s script), and Simon Richter’s conceptual `bisect-rebase` or `rebase-bisect` command integrating bisection with optional test execution.

Core problem or goal: provide a built-in, lightweight alternative to third-party tools (e.g., `git-imerge`) for incrementally resolving rebase conflicts, with the goal of inclusion in Git's `contrib/` area. The workflow is actively used in real-world projects (shadow-utils, Linux man-pages, PostgreSQL), and the discussion centers on whether Git should include *any* helper for this workflow, and if so, which implementation is most suitable. The unresolved question remains whether the project prefers a minimal, robust script (`git-rebase-walk`), a more sophisticated and performant bisection-based script (`git-bisect-rebase`), a conceptual bisection-plus-testing approach (Simon Richter), or neither, given the existence of `git-imerge` and its maintainer endorsement. The thread has now clarified that the workflow must support *multi-shot* operation (manual control over rebase order for interdependent branches) rather than a single-shot approach (automatic advancement to the next conflicting commit), as demonstrated by Colomar’s use case involving a tree of branches. Colomar’s detailed shell session proves that a single-shot workflow (as proposed by Phillip Wood) would break complex workflows, ruling out that design for any future integration into `git rebase`.

Current status: initial proposal with no prior versions. The original script (`git-rebase-walk`) is offered as-is, with the author volunteering to polish it if there is interest. The discussion has now fully converged on `git-bisect-rebase` as the leading candidate for `contrib/` inclusion, following Nico Williams’ endorsement of its single-parameter interface and alignment with Git’s conventions, as well as his explicit deprecation of his own `bisect-rebase.sh` in favor of Colomar’s version. Simon Richter’s proposal introduces a new conceptual direction—integrating bisection with optional test execution—but remains unimplemented. Junio C Hamano has endorsed `git-imerge` as a proven, existing solution, calling it "one of the best things since sliced bread" and noting its occasional use in his own workflow. Patrick Steinhardt has explicitly stated that the functionality would be better integrated directly into `git rebase` itself rather than as a standalone script, implying that the current proposals are stopgaps. Alejandro Colomar now agrees with this assessment and plans to distribute the script separately under the `git-` namespace (e.g., via `manpages-utils`) as an interim measure while pursuing integration into `git rebase` itself, proposing `--first-conflict` as a potential option name. Nico Williams has suggested `--onto-first-conflict` as an alternative, more explicit variant. Phillip Wood has proposed `--incremental` or `--progressive` as additional naming candidates and strongly advocated for a single-shot workflow where `git rebase --continue` automatically advances to the next conflicting commit, but Colomar’s detailed demonstration has shown that this approach would break complex workflows involving interdependent branches. No maintainer decision has been made regarding inclusion in `contrib/`, and the broader question of whether Git should endorse any script remains open.

Key technical details: the original script (`git-rebase-walk`) is a 10-line Bash script using `git merge-base`, `git rev-list`, and `git rebase --onto` to implement the workflow. It stops at each conflicting commit, allowing manual resolution via `--continue` or `--abort`. Nico’s alternative (`bisect-rebase.sh`) was a 93-line script that used a bisection-like strategy to find the *first* upstream commit that conflicts with the local branch, reducing the number of conflict resolutions. Colomar’s new script (`git-bisect-rebase`) is a 52-line Bash script that follows a similar bisection strategy but simplifies the interface (single-parameter usage, matching `git rebase`) and code (pipes instead of shell arrays). Nico has since deprecated `bisect-rebase.sh` in favor of `git-bisect-rebase`, which is now the consensus candidate for `contrib/` inclusion. Simon Richter’s proposal envisions a new command (`git bisect rebase <target> -x '<test-command>'`) that would use bisection to find the first upstream commit causing either a rebase conflict or a test failure, with an option to prioritize trivial resolutions. Phillip Wood’s feedback introduces a new workflow preference: a single-shot rebase where `--continue` automatically advances to the next conflicting commit, but Colomar’s demonstration has shown that this would not support complex dependency graphs. Neither script modifies Git's C code, build system, or test suite; all would live in `contrib/` if accepted. No new Git symbols, CLI options, or on-disk formats are introduced. The naming question (`git-bisect-rebase` vs. `rebase-bisect` vs. CLI option names such as `--first-conflict`, `--onto-first-conflict`, `--incremental`, or `--progressive`) remains unresolved, though `git-bisect-rebase` is now the preferred candidate for a standalone script. Nico Williams clarified that the bisection-based scripts have a best-case performance of O(1) (no conflicts) and a worst-case of O(N log N) (conflicts in every upstream commit), rather than the O(log N) one might expect from a pure bisection. This worst-case behavior is still preferable to the O(N) behavior of `git-rebase-walk` but may factor into the maintainers’ evaluation of the trade-offs.

- Which implementation (if any) is most suitable for `contrib/`: the now-converged `git-bisect-rebase` (Colomar/Nico), Simon Richter’s conceptual `bisect-rebase` with test integration, or neither.
- Whether the performance trade-offs of the bisection-based scripts (O(N log N) worst-case) are acceptable for inclusion, or if they remain a concern.
- Whether the naming (`git-bisect-rebase`, `rebase-bisect`, `--first-conflict`, `--onto-first-conflict`, `--incremental`, or `--progressive`) will be accepted by the project or require further adjustment.
- Whether the integration of test execution (as proposed by Simon Richter) is a desirable feature or an unnecessary complication for a `contrib/` helper.

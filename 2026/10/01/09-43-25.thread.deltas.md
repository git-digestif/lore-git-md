# Thread deltas

## 2026/10/01

- [2026/10/01/09-43-25 by Artem S. Tashkinov <aros@gmx.com>] Artem S. Tashkinov proposed an opt-in Git feature to restore per-file historical mtimes derived from repository history, suggesting a `git restore-mtimes` command or `--historical-mtimes` options for `git clone`, `git checkout`, and `git archive`.
- [2026/10/01/09-43-25 by Artem S. Tashkinov <aros@gmx.com>] He defined a "historical mtime" as the timestamp of the newest commit in which the file's blob contents actually changed, specifying that pure renames and mode-only changes should not alter the timestamp while renames accompanied by content changes should, and that the committer timestamp should be the default.
- [2026/10/01/09-43-25 by Artem S. Tashkinov <aros@gmx.com>] He noted having written a proof-of-concept shell implementation that compares blob IDs rather than status letters, ignores pure renames and mode-only changes, handles symlinks without dereferencing, and attempts sensible merge behavior.
- [2026/10/01/09-43-25 by Artem S. Tashkinov <aros@gmx.com>] He posed five questions for discussion: whether author or committer timestamp should be the default, precise merge semantics (counting only merges that introduce content not present in parent history), rename following across non-linear history, whether to implement this as a standalone command, checkout/restore option, archive feature, or combination, and whether `git archive` should optionally use these timestamps for archive members.
- [2026/10/01/09-43-25 by Artem S. Tashkinov <aros@gmx.com>] He emphasized that `git archive --historical-mtimes <commit>` may be more useful than clone-specific behavior for distributions and source consumers, and clarified that the feature would be strictly opt-in, not changing existing default checkout behavior.

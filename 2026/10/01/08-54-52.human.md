This is the second patch in Phillip Wood’s two-part series to make `git checkout -m` remember the original conflict labels (e.g., branch names) instead of using generic "base", "ours", and "theirs". The patch introduces `.git/MERGE_LABELS` to store the labels during a merge and reuses them when `git checkout -m` recreates conflicts. Phillip has addressed Junio’s two main concerns from his review: he plans to document `.git/MERGE_LABELS` in a follow-up series (alongside other Git repository files like `MERGE_MSG` and `MERGE_MODE`), and he has fixed the Windows line-ending issue by switching from manual line parsing to `strbuf_getline()`, which handles CRLF correctly.

The patch touches the merge machinery (ort backend), `branch.c`, and `builtin/checkout.c`, and adds a test in `t/t7201-co.sh`. It handles edge cases like missing or malformed label files by falling back to generic labels, and ensures cleanup via `git commit` and `git sequencer`. The implementation is well-structured and aligns with existing patterns (e.g., `MERGE_MODE`, `MERGE_MSG`), though the architectural debate about whether to use an index extension instead of `.git/MERGE_LABELS` remains unresolved. Phillip has rejected the index extension approach for this series, citing compatibility and consistency with other merge strategies.

This is a **feature patch** that improves usability by making conflict markers more informative. The changes are self-contained and unlikely to break existing workflows. The open question about whether to also preserve the original conflict style (e.g., `diff3`) is still unanswered, but it doesn’t block this patch. The patch looks ready to proceed after the documentation follow-up.

Subject: [PATCH 0/3] refs: introduce subcommand grouping to parse-options API
Series version: v1
Originating author: Patrick Steinhardt
Thread type: patch series

Core problem or goal
Refactor Git’s parse-options API to support grouped subcommands, then apply this to `git refs` to organize its many subcommands into logical categories (database operations, reading, writing). The immediate goal is to improve usability by making the `git refs` help output more scannable; the broader goal is to establish a reusable API for future high-level commands like `git objects`.

Current status
Under review; v1 posted. Junio C Hamano reviewed patch 1/3 (the parse-options bugfix) and suggested a minor variable-name preference (`shown` instead of `first`). No other reviews yet; no merge status reported.

Key technical details
- Files touched: `parse-options.{c,h}`, `builtin/refs.c`, `Documentation/git-refs.adoc`, `Documentation/technical/api-parse-options.txt`, test scripts in `t/`, and `t/helper/test-parse-options.c` (new test for the bugfix).
- New API: `OPT_SUBCOMMAND_GROUP`, `OPT_GROUP`, `OPT_SUBCOMMAND_H`, and supporting infrastructure in `parse-options.h`.
- New symbols: `parse_options_add_subcommand_group`, `struct subcommand_group`, plus the internal `shown` flag in `parse_options()`.
- Behavior change: `git refs -h` now displays grouped subcommands under headings “Reference database”, “Reading references”, and “Writing references”; `--git-completion-helper` output no longer emits a spurious leading space when the first option is skipped.
- Man page updated: `git-refs.adoc` reordered to match new grouping, with `optimize` moved to the “Reference database” section.
- No on-disk format changes; test coverage added for both API and CLI.

This is a discussion about a proposed `contrib/` helper script, `git-rebase-walk`, aimed at simplifying large rebase conflicts by resolving them incrementally.

Nico Williams joins the thread to offer feedback on Alejandro Colomar’s script. He suggests a more concise pipeline using `git log --reverse --format=%H` instead of the current multi-command approach, but notes two key limitations: the script lacks conflict handling and can be prohibitively slow when rebasing across thousands of commits. Nico shares his own solution, `bisect-rebase.sh` (linked in a gist), which uses a bisection-like approach to efficiently identify and resolve conflicts one at a time, providing better context for each resolution. He reports successfully using this script to rebase a PostgreSQL fork across 1,000–2,000 commits with complex conflicts, a task that would be impractical with a plain `git rebase`.

The discussion now contrasts three approaches: Alejandro’s linear `git-rebase-walk`, Nico’s bisection-based `bisect-rebase.sh`, and the existing third-party tool `git-imerge` (mentioned in earlier reviews). Nico’s script appears to address the performance and context issues of the linear approach while remaining focused on rebase workflows, unlike `git-imerge`, which supports both merge and rebase. The thread remains open on whether Git’s `contrib/` area should include such a helper, and if so, which implementation would be most suitable.

This is the final patch in a three-patch bugfix series targeting the reftable backend. It fixes a long-standing mismatch between Git’s on-disk storage of reflog timezones and the reftable specification, which requires signed offsets in minutes rather than the traditional `[+-]HHMM` format. The change is transparent to the rest of Git, as the reftable backend now converts between the two formats on read and write, but it resolves interoperability issues with other reftable implementations (notably JGit) and fixes a segfault in the `dump-reftable` test helper.

The patch updates `refs/reftable-backend.c` to use the new `tz_to_minutes()` helper (introduced in patch 1) when writing reflog entries, ensuring the timezone is stored as a signed minute offset. On read, it converts back to `[+-]HHMM` using `minutes_to_tz()` so that the rest of Git sees the expected format. The test helper `dump-reftable` is updated to print the raw minute offset (without zero-padding) to avoid ambiguity, and a new test in `t/t0610-reftable-basics.sh` verifies round-trip correctness for edge cases like `+1400`, `+0530`, and `-0830`.

The commit message includes a table showing how existing reflog entries will be reinterpreted, but notes that the divergence is harmless because Git only uses reflog timezones for display purposes. The patch also addresses the last outstanding review request from Karthik Nayak (v1) by adding test coverage for negative timezones with non-zero minutes (e.g., `-0530`). No new objections or open questions remain, and the series is effectively ready for integration. The change is mechanical, well-tested, and unlikely to be controversial.

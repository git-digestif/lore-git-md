This is a **workflow tool discussion** in the ongoing debate about whether Git should include a helper script for incremental rebase conflict resolution in its `contrib/` area. Nico Williams responds to Alejandro Colomar’s latest proposal (`git-bisect-rebase`) with measured approval, acknowledging the scripts’ fundamental similarity and agreeing to simplify his own version (`bisect-rebase.sh`) by adopting Colomar’s single-parameter interface.

The email advances the thread by removing one of the remaining technical differences between the two shell-based implementations: Nico concedes that his two-parameter design was unnecessary and will align with Colomar’s `git rebase`-style interface. This leaves the scripts nearly identical in functionality, differing mainly in code style (pipes vs. shell arrays) and output verbosity. Nico also endorses Colomar’s plan to submit his version to Git, citing the lack of paperwork hurdles, while generously offering to credit prior art—including his own script and several third-party tools (`git-imerge`, `mergify`, etc.).

The unresolved question remains whether Git should include *any* such helper, given Junio’s strong endorsement of `git-imerge` as a mature, existing solution. Nico’s email does not challenge that preference but reinforces the argument for a shell-based alternative by highlighting `bisect-rebase.sh`’s simplicity and real-world utility (notably in PostgreSQL development). The discussion now hinges on whether the project values the minimalism and portability of a shell script over the feature set of `git-imerge`, or whether it will defer to the third-party tool entirely. No maintainer decision has been made, and the naming convention (`git-bisect-rebase` vs. `git-rebase-walk`) is still open.

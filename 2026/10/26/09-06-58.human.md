This is the first patch in a **v4 bugfix series** that fixes a data-loss race in `git repack -d` where concurrent pushes can cause objects to be deleted despite being referenced by a `.keep` file that appears mid-repack. The series is now **production-ready** and rebased onto `master` (post-`ps/odb-files-alternates` merge).

This patch addresses a **latent bug in the cruft-pack walk** that was masked by the now-removed `--honor-pack-keep` mechanism. The issue: when `pack-objects` writes a cruft pack, it first collects recent objects, then walks from them to rescue whatever they reach—even if expired. A pack not listed by the caller is marked "kept" during collection (so its objects aren’t copied into the cruft pack), then unmarked before the walk (so the walk can traverse it). However, the walk uses a **cached list of kept packs**, which isn’t invalidated after unmarking. If the cache was built while the pack was still marked, the walk stops there, leaving objects in expired packs unreachable and thus deleted. The fix: **invalidate the kept-pack cache** after unmarking, ensuring the walk traverses all packs except the explicitly listed fresh ones.

The patch touches `builtin/pack-objects.c`, `odb/source-packed.h`, `packfile.c`, and `packfile.h`, adding `repo_invalidate_kept_pack_caches()` to drop the cache for every object directory. It also converts `--keep-pack` packs into "open" kept packs (traversed but not copied), matching the behavior of `.keep` files under `--honor-pack-keep`. The **test coverage** is thorough: it verifies the cruft walk rescues objects through untold packs, `--keep-pack` packs, and alternates (with/without `--local`), including edge cases like `git repack --filter-to` leaving referenced objects in an alternate.

The fix is **minimal and targeted**, addressing only the cache invalidation and kept-pack handling. It trades a small performance hit (the walk now traverses alternates) for safety, which is the right call for a data-loss bug. The patch is **well-motivated** and **uncontroversial**; Junio C Hamano’s prior ack for the v3 version of this fix remains valid. No new objections are expected, and the patch is ready for `next`.

This is a bugfix targeting the config subsystem, addressing a long-standing usability and security issue where Git ignores file permission bits when writing configuration files. Junio C Hamano has sent a v2 patch that makes Git respect write permissions for out-of-tree config files like `~/.gitconfig`, returning `CONFIG_NO_WRITE` when attempting to modify a read-only file.

The patch remains narrowly scoped to the config subsystem, deliberately avoiding a broader lockfile API refactoring. The key change is an `access(2)` check in `repo_config_set_multivar_in_file_gently()` that prevents overwriting unwritable files. The commit message now explicitly justifies this scope: out-of-tree files are uniquely vulnerable because they reside outside the repository, while in-tree files like `.git/config` have no sensible reason to be protected from Git itself.

Test coverage is thorough, verifying that read-only config files can still be read but reject writes and unsets. The test uses `GIT_CONFIG_GLOBAL` to avoid modifying the user’s actual config, a sensible precaution. The implementation looks clean and well-motivated, with no obvious edge cases left unaddressed in this version.

This v2 incorporates feedback from Patrick Steinhardt, who initially questioned whether permission checks should be centralized in `lockfile.c` but now endorses the patch’s narrow focus. The commit message now documents this rationale, making the design decision explicit. No other substantive review has surfaced, but the patch appears mature and uncontroversial. The change is likely to be welcomed by users who manage dotfiles under version control and expect `chmod a-w` to protect their files from accidental modification.

This is a detailed design inquiry about a shared object store for Git clones and submodules, targeting embedded development workflows with many persistent workspaces. The author, Massimiliano Cialdi, describes a real-world problem (17.9 GiB of redundant `.git` directories across 250 repositories on a single machine) and proposes a set of requirements (R1–R11) for a solution that would deduplicate Git objects while preserving local work and offline functionality. The email includes two reproducible test scripts demonstrating fundamental gaps in Git’s current alternate mechanism: GC in the shared store can delete objects still reachable by borrowers (F1), and GC in borrowers drops local copies of objects that the alternate has (F2).

The inquiry explores multiple approaches—remote helpers, selective object retention, append-only stores, and versioned sparse rules—without committing to a specific implementation. It explicitly asks whether changes to Git itself (e.g., borrower-aware GC, repack-local enhancements, or sparse-checkout integration) would be welcome upstream. The tone is pragmatic and open to feedback; the author has clearly done their homework (measuring object store sizes, testing edge cases, reading source code) and is seeking architectural guidance before investing in a full implementation.

Key technical details for follow-up discussion: the proposed remote helper would use the `fetch` capability to add an alternate dynamically; the shared store would need to track borrowers’ reachability roots (O13); and `repack -l` would need to preserve local copies of objects reachable from selected refs (O14). The inquiry also touches on CI compatibility (R10) and sparse-checkout versioning (R9), suggesting this is part of a larger workflow optimization effort. Prior art mentioned includes Scalar’s shared object cache and depot_tools’ caches.

This is the **v4 of a bugfix series** that prevents `git repack -d` from losing objects when a `.keep` file appears on a pack mid-repack. The issue—a race between `repack` scanning `.keep` files and `pack-objects` doing the same—was observed in production and reproduces on `master`.

The series now takes a simpler, more robust approach than v3: instead of passing `pack-objects` a snapshot of *kept* packs (v3), it passes a snapshot of *non-kept* packs (v4) via a new `--ignore-pack-keep-from=<file>` option. This ensures `pack-objects` never treats a pack as kept if `repack` has already decided to delete it, regardless of what `.keep` files appear later. The change is minimal (3 patches), well-tested, and avoids the architectural complexity of v3.

### Key improvements in v4:

1. **Patch 1/3** fixes a latent bug in the cruft-pack walk where a stale kept-pack cache could omit objects. The fix is now more thorough, ensuring the walk goes through alternates and `--keep-pack` packs (treating them as "open" kept packs). Tests cover all three cases.
2. **Patch 2/3** adds `--ignore-pack-keep-from=<file>`, which tells `pack-objects` to ignore `.keep` files for packs named in the file. This is a scalability enabler (avoids command-line length limits) and the core of the race fix.
3. **Patch 3/3** makes `repack -d` write the list of non-kept/cruft packs to a file and pass it to `pack-objects`, replacing the racy `--honor-pack-keep` mechanism. The implementation is clean, handles edge cases (newlines in pack names), and includes tests for `-a`, `-A`, `-k`, `--cruft`, `--filter`, and `--geometric`.

### Why this matters:

- The bug can cause **data loss** (dangling refs pointing to missing commits).
- The fix is **production-tested** and addresses a real-world issue.
- The design is **minimal and safe**: no on-disk format changes, no behavioral regressions, and thorough test coverage.

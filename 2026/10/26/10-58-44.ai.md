This is a **substantive review reply** in the ongoing bugfix thread about preventing `git revert` and `git cherry-pick` from operating on shallow boundary commits. Phillip Wood responds to Junio C Hamano’s design question by proposing a more user-friendly approach: refusing to add shallow boundary commits to the sequencer’s todo list *before* execution begins, rather than erroring out mid-operation in `do_pick_commit()`.

The key technical shift is architectural: instead of placing the safeguard in `do_pick_commit()` (which covers revert, cherry-pick, and rebase), Phillip suggests a shared helper function that would be called from four entry points: `sequencer_make_script()`, `make_script_with_merges()`, `single_pick()`, and `sequencer_pick_revisions()`. This would catch shallow boundary commits at the planning stage, improving the user experience by preventing the operation from starting rather than failing partway through. The trade-off is implementation complexity—four call sites instead of one—but the payoff is a cleaner UI and consistent behavior across all sequencer-based commands.

No new objections or edge cases are raised; this is a refinement of the existing consensus that the safeguard should extend to `git rebase` and possibly `git commit --amend`. The discussion remains focused on *how* to implement the safeguard, not *whether* to implement it. The thread is still under review, with no merge status implied.

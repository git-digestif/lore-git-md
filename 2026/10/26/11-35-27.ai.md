This is a **substantive review approval** for the v3 object storage extension series, a major architectural effort to make Git’s object database pluggable. Karthik Nayak has completed a full review of the series and explicitly approves it, signaling readiness for integration. The review focuses on the mechanical changes introduced by the v3 refactoring (splitting the object storage format into `(type, payload)` components) and confirms that the implementation aligns with earlier feedback about design consistency and test readability.

The series introduces `extensions.objectStorage`, a configuration mechanism modeled after the existing ref storage extension, and implements the baseline `files` backend with support for relocating the `.git/objects` directory via a payload (e.g., `files://objs` moves objects to `.git/objs`). The v3 refactoring replaces the previous string-based `object_storage_format` field in `struct repository` with an `enum object_storage_format` and a separate `object_storage_payload` string, simplifying normalization and reducing URI re-parsing. This change is technically sound and follows established patterns for ref storage, though it remains the subject of an unresolved architectural debate about whether user-configurable object storage backends are justified.

Karthik’s approval covers all seven patches, including the core refactoring (patch 2/7), environment variable support (patch 3/7), and submodule propagation (patch 7/7). The review notes only minor nits (e.g., stylistic improvements to code comments and test formatting), which the reviewer explicitly states can be ignored. No blocking concerns or regressions are identified, and the series is described as "looking good" overall. The approval is unconditional, though it does not engage with the broader architectural question raised by SZEDER Gábor about whether `extensions.objectStorage` should exist as a public API.

The series is functionally complete and includes all planned features: configuration via `extensions.objectStorage`, environment variable overrides (`GIT_OBJECT_STORAGE_FORMAT` and `GIT_DEFAULT_OBJECT_STORAGE_FORMAT`), command-line options (`--object-storage-format=` for `git clone`, `git init`, and `git submodule`), inspection tools (`git rev-parse --show-object-storage-format` and `git repo objects.storageFormat`), and submodule support. The implementation also introduces intentional restrictions, such as stripping payloads when propagating object storage formats to submodules (e.g., `files://objs` becomes `files`) and bumping `core.repositoryformatversion` to `1` for non-default configurations. These design choices are deliberate and align with the ref storage backend’s behavior, though they may attract further discussion.

Files touched span `odb/`, `setup.c`, `repository.c`, and `builtin/` commands (`clone.c`, `init-db.c`, `submodule--helper.c`, `rev-parse.c`, `repo.c`), with documentation updates across `git-{clone,init,submodule,repo,rev-parse}.adoc` and new files like `object-storage-format.adoc`. Tests cover initialization, cloning, submodule propagation, schema validation, environment variable overrides, and error cases. The series is built on top of the merged prerequisite topics `ps/odb-files-alternates` and `ps/setup-enforce-repo-passed-to-create-repository-has-no-state`.

The primary open question remains the architectural debate initiated by SZEDER Gábor, which challenges the justification for exposing `extensions.objectStorage` as a public API. Patrick Steinhardt’s response defends the feature on grounds of testing, consistency with `extensions.refStorage`, and internal GitLab use, but the discussion is unresolved. Karthik’s approval does not address this debate, focusing instead on the mechanical correctness of the implementation. The series is now **ready for integration**, pending Junio’s assessment of the architectural question.

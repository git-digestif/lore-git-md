This thread began when Julia Evans proposed updating the Git glossary to clarify the distinction between "object name" and "object ID," arguing that "object ID" should be the canonical term for the hash while "object name" could refer more broadly to any identifier (like branch names or refs). The maintainer, Junio C Hamano, rejected this outright, insisting that "object name" must remain the canonical term for the hash itself, with any other usage in documentation being incorrect. The discussion has since stalled, with no progress toward a resolution.

The core disagreement is philosophical: Junio views "object name" as the invariant, unique identifier (the hash), while other terms like refs or branch names are merely notations or shorthand for it. Julia and D. Ben Knoble, however, argue that this definition is counterintuitive for users, who expect "ID" to mean the hash and "name" to mean human-readable labels. Ben’s latest email reinforces this perspective, framing the glossary’s current definition as an idiosyncrasy that prioritizes historical precedent over clarity. He suggests that Git’s terminology should evolve to match common usage, even if it means breaking from the 2005 standardization.

The thread is at an impasse. Junio has made it clear that the only acceptable path forward is a broader documentation audit to align all man pages with the glossary’s definition, but no one has volunteered to undertake this work. The patch itself is blocked, and no compromise or alternative solution has been proposed. The discussion has shifted from refining the glossary to defending entrenched positions, with no clear next steps. Unless someone steps forward to address Junio’s demands or finds a way to bridge the gap, the thread is unlikely to move forward.

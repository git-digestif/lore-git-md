This thread began when Julia Evans proposed a patch to clarify Git’s glossary, suggesting that "object ID" become the canonical term for an object’s hash (SHA-1 or SHA-256) while "object name" would be context-dependent—covering both the hash and other identifiers like branch names or refs. The maintainer, Junio C Hamano, rejected this outright, insisting that "object name" must remain the *only* canonical term for the hash, and that any documentation using it otherwise is incorrect and should be fixed. Julia withdrew the patch, and the thread is now closed.

The core disagreement revolves around whether Git’s terminology should prioritize historical precedent or clarity for newcomers. Junio argues that the glossary’s 2005 definition of "object name" as the hash is authoritative, and that other documentation (like `gitrevisions(1)` or `gitdatamodel`) should be corrected to match it. D. Ben Knoble and Julia, however, pointed out that this definition conflicts with how users intuitively understand terms like "main" (a branch name) or "HEAD" (a ref)—neither of which feel like "object names" or "object IDs" to most people. Junio’s latest email doubles down on the status quo, framing the issue as a documentation bug in other man pages rather than a problem with the glossary itself.

No further action is planned. The broader inconsistency in Git’s documentation remains unresolved, but no contributor has volunteered to audit and fix the dozens of man pages that use "object name" more loosely. For now, the glossary’s definition stands: "object name" is the hash, and everything else is just a notation that can be used *in place of* it.

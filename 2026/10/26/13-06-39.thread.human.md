Julia Evans proposed a patch to clarify the Git glossary by making "object ID" the canonical term for the hash identifier (SHA-1/SHA-256) and marking "object name" as context-dependent, addressing ambiguity in the documentation where "object name" is sometimes used for any object reference (branches, refs) and sometimes specifically for the hash. The maintainer, Junio Hamano, rejected this approach outright, insisting that "object name" must remain the canonical term for the hash and that any documentation using it otherwise is incorrect and should be fixed instead. The patch is now blocked unless someone undertakes a broader audit to align all man pages with the glossary's definition.

Ben Knoble recently weighed in, agreeing with Julia's goal of reducing ambiguity but suggesting refinements to the wording. He proposes using "notation" instead of "name" for the various ways to reference an object (e.g., refs, HEAD, or the hex string) and explicitly mentioning SHA-256 alongside SHA-1 in the "object ID" definition. He also suggests defining "object name" more precisely as "any notation in `gitrevisions(1)` that resolves to an object ID." While Knoble's feedback is substantive and constructive, it doesn’t address the maintainer’s rejection or propose a path forward for resolving the fundamental disagreement. The thread remains stalled on the core question of whether "object name" or "object ID" should be the canonical term.

This is a design discussion in the `remote.<name>.refmap` series, now cooking in `next` but blocked from graduating to `master` due to a fundamental design flaw. Junio C Hamano clarifies how the current v11 implementation (already queued in `next`) handles a specific use case: configuring both `remote.<name>.fetch` and `remote.<name>.refmap` for the same remote. The example shows fetching only `master`, `next`, and `seen` from a remote named "cabal" while storing them under `refs/remotes/cabal/`. Junio confirms that the current precedence rule (`remote.<name>.fetch` > `remote.<name>.refmap`) already supports this scenario without requiring dynamic branch inference, and the series’ existing code handles it correctly.

The email does not introduce new code or design changes—it merely validates that the v11 implementation (already feature-complete and queued in `next`) behaves as intended for this edge case. However, the thread’s broader context is critical: the maintainer and key reviewer (Phillip Wood) have already agreed that the series’ current design—overloading `remote.<name>.refmap` to control *both* namespace mapping *and* which refs are fetched—is flawed and must be revised. The next iteration (v12) will introduce a dedicated `remote.<name>.fetchRefs` config key to decouple the "what" (which refs to fetch) from the "where" (where to store them), resolving the inflexibility the series aims to fix.

Key technical details for follow-up discussion:
- **Files touched**: None in this email; the series already updates `remote.c`, `builtin/fetch.c`, and `builtin/remote.c`.
- **New symbols**: `remote.<name>.refmap` (config key), `remote->refmap` (struct field), `--limited-fetch` (CLI flag).
- **Behavior**: The precedence rule (`fetch` > `refmap`) is explicitly validated for Junio’s use case, and the dynamic branch inference logic (`branches_tracking_remote()`) is correctly bypassed when `remote.<name>.fetch` is configured.
- **Design direction**: The v12 redesign will introduce `remote.<name>.fetchRefs` to replace the overloaded `refmap` role, with precedence: `remote.<name>.fetch` > `remote.<name>.fetchRefs` > dynamic branch enumeration.
- **Open questions**: How `remote.<name>.fetchRefs` will integrate with the existing `branches_tracking_remote()` logic, whether it will support negation (e.g., `^refs/pull/*`), and how the `--limited-fetch` flag and shallow-repository default will be updated to use the new config key. Documentation clarity around the new precedence rules is also pending.

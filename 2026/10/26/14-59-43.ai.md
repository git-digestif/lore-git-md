This is a bugfix targeting the config subsystem, updating Junio C Hamano's RFC/PATCH to a v2 after review feedback. The patch teaches Git to respect file permission bits when writing out-of-tree configuration files (e.g., `~/.gitconfig`), preventing accidental overwrites of read-only files. The core implementation remains unchanged from the RFC: an `access(2)` check in `repo_config_set_multivar_in_file_gently()` returns `CONFIG_NO_WRITE` if the target file is unwritable. The test coverage is thorough, verifying that read-only files can still be read but reject writes and unsets.

The key change in v2 is the commit message, which now explicitly justifies the patch's narrow scope: permission checks are implemented in the config API rather than the lockfile layer to avoid a time-consuming audit of all lockfile users (reflogs, index files, hooks). This addresses Patrick Steinhardt's architectural concern from the RFC thread, where he initially argued for centralizing permission checks in `lockfile.c`. Junio's response -- that out-of-tree files like `~/.gitconfig` are uniquely vulnerable because they reside outside the repository -- is now endorsed by Patrick and recommended for inclusion in the commit message.

The patch is well-motivated and technically sound. The `access(2)` check is simple and effective, and the test uses `GIT_CONFIG_GLOBAL` to avoid modifying the user's actual config. Edge cases (race conditions, symlinks, NFS) are acknowledged but not addressed in this iteration, which is reasonable given the patch's limited scope. The implementation is unlikely to be controversial, though the unresolved architectural question about lockfile API consistency may resurface in future work. No substantive review of the implementation's correctness has emerged yet, but the patch's narrow focus and clear rationale make it a strong candidate for merging.

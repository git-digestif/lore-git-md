This is a governance discussion refining the proposed community voting process for Git, specifically the eligibility criteria for voters. Phillip Wood responds to Jeff King’s (Peff) empirical data on commit-count thresholds by suggesting a hybrid approach: require a minimum number of commits *over all time* (to ensure a track record) but also mandate *at least one recent commit* (to ensure ongoing engagement). This hybrid model avoids the awkwardness of "N commits in the last M years" while still filtering out inactive contributors.

Phillip’s proposal directly engages with Peff’s data, noting that under the low thresholds currently under discussion (e.g., 5–10 commits), most long-term contributors would meet the bar within the last two years anyway. However, if the threshold is raised (e.g., to 50 or 200 commits), combining "all-time commits" with a "recent activity" requirement becomes more meaningful. This approach balances inclusivity with practicality, addressing concerns about "drive-by" contributions (raised by brian m. carlson and Kristoffer Haugsbakk) without imposing rigid time windows that might exclude engaged but less prolific contributors.

The email advances the discussion by introducing a concrete, scriptable hybrid model that could resolve the tension between Junio C Hamano’s preference for simplicity (e.g., a flat commit count) and Phillip Wood’s earlier proposal for a two-year activity window. It does not propose specific values for N or M, leaving those for further debate, but the framework itself is a step toward consensus. Key technical details for future discussion include whether to count individual commits or patch series (Phillip’s earlier suggestion) and how to define "recent" (e.g., 1–5 years).

No new files or code changes are introduced, but this refinement could shape the final version of `Documentation/CommunityVoting.adoc`. The thread remains open, with the hybrid model now on the table alongside Peff’s data and Tuomas Ahola’s proposal to use the average commit count (26) as a threshold.

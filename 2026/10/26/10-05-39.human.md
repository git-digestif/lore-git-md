This is a **reply to a substantive architectural review** of patch 2/7 in the v3 object storage extension series. The series introduces `extensions.objectStorage`, a configuration mechanism for pluggable object database backends, and this patch specifically implements the configuration layer.

Patrick Steinhardt responds to SZEDER Gábor’s question about why the object storage backend should be user-configurable. The justification is threefold: (1) it enables testing of pluggable backends alongside the payload mechanism, (2) it maintains consistency with the existing `extensions.refStorage` design (where ref backend location is configurable), and (3) it serves as a building block for GitLab’s migration use cases. The response is brief and pragmatic, framing configurability as a prerequisite for broader goals rather than an end in itself. Notably, it does not engage with the reviewer’s implied skepticism about whether the `files` backend’s payload (e.g., `files://objs`) justifies the complexity of a URI-based system, nor does it address whether the parallel with `extensions.refStorage` is sufficient.

The reply signals that the author considers the design settled and is moving forward with implementation. The commit message will be updated to include this justification, but the core question—whether user-facing configurability is necessary—remains unchallenged. This leaves the thread’s architectural debate unresolved; future discussion may revisit whether the feature’s scope aligns with its stated goals. For now, the series continues to target `next` as a functionally complete RFC.

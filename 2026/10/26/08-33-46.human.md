This is the third patch in Harald Nordgren’s v4 series introducing `git branch --delete-integrated`, a new flag that extends `git branch --delete-merged` to detect branches whose changes (but not their tips) have been integrated via rebase or squash merges. The patch adds the core `--delete-integrated` logic, enabling the command to delete branches when some upstream commit since the fork point contains the branch’s version of every file it changed, even if those changes were later reverted.

The implementation is tree-based and avoids reading file contents, so it remains performant in partial clones. The output format is updated to show where the branch’s changes landed (e.g., `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`). The patch includes test coverage for rebase-merged, squash-merged, and reverted branches, as well as edge cases like partial landings and mixed workflows.

This is a well-structured, opt-in feature that addresses a common pain point in forge and local workflows. The CLI design is finalized and explicitly confirmed by Junio, and the patch is part of a four-patch series where the first two (preparatory refactoring and landing-message helper) are uncontroversial and ready for integration. The remaining open question is whether to implement the author-check mitigation (Jasper Mayone’s proposal) to address false positives in the "npm update" scenario, but this does not block the core functionality.

The patch looks technically sound and is worth attention from reviewers interested in branch maintenance workflows. The test suite is thorough, and the performance optimizations are sensible. If you care about repository hygiene in squash-heavy workflows, this is the patch to review.

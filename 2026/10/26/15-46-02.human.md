This is a performance-focused feature series targeting the `send-pack` and `pack-objects` subsystems. The goal is to avoid resending unchanged large blobs when force-pushing a rebased feature branch, which can turn a small history rewrite into a costly upload.

The series introduces a new optimization: when pushing a forced non-fast-forward update of an existing branch, Git now inspects the old tip’s tree (if locally available) to identify objects the receiver already has. This is done by passing the old tip to `pack-objects` with a new `--inspect-have` option, which compares root trees using sparse tree marking. The change is opt-in and requires no server or protocol modifications—it activates only when the old tip is locally present and the push is a forced update of an existing branch.

The cover letter includes detailed benchmarking on Chromium’s repository. In a "reword" scenario (changing only commit messages), the patch reduces packed objects from 421 to 215 and cuts total wall time by more than half. In a single-file rewrite, it saves about 100 bytes and 20% of packing time. The worst-case overhead—rewriting nearly every file—shows an 8% increase in packing time for negligible byte savings, but the author notes this is an artificial test and real-world large-blob savings should outweigh the cost.

Test coverage is thorough: the series adds 19 new tests to `t5322-pack-objects-sparse.sh` and 43 to `t5516-fetch-push.sh`, covering edge cases like identical trees, partial clones, and replacement refs. The implementation is careful to preserve existing behavior for shallow pushes, partial clones, and bitmap enumeration.

This looks like a well-motivated, well-tested optimization that addresses a real pain point in feature-branch workflows. The commit messages are clear, the benchmarks are convincing, and the scope is narrowly targeted. If the mailing list discussion confirms the overhead is acceptable in practice, this is likely to be a welcome improvement.

This is a detailed design inquiry about a shared object store for Git clones and submodules, aimed at reducing disk usage in embedded development workflows. The author, Massimiliano Cialdi, describes a real-world problem: a team maintaining many persistent workspaces (250+ repositories/submodules) with significant object duplication (15 GiB of Git objects across 250 stores, reducible to ~2.7 GiB with a single shared object database). The core issue is that Git's alternates mechanism doesn't coordinate garbage collection between shared stores and borrowers, leading to data loss when either side runs `gc`.

The email is thorough and well-structured, outlining requirements (R1-R11), verified failure modes (F1-F9), proposed solutions (O1-O15), and specific questions (1-8). Key technical challenges include:
1. Preventing GC in the shared store from deleting objects still reachable by borrowers (question 1).
2. Keeping local copies of objects in borrowers that upstream might rewrite (question 3).
3. Making this transparent via remote helpers or config (question 2).
4. Versioned sparse-checkout rules for submodules (question 5).

The author provides reproducible test scripts demonstrating two critical failure modes: GC in the shared store breaking borrowers (F1), and GC in borrowers dropping local copies of user commits (F2). These scripts make the problem concrete and actionable for reviewers.

This is not a patch submission but a request for architectural guidance. The problem is real and well-documented, affecting teams with many submodules and persistent workspaces. The proposed solutions range from configuration workarounds to potential Git core changes (O13-O15). The inquiry is likely to generate discussion about whether Git should evolve to better support shared object stores, or if this should remain a local tooling concern. Given the embedded use case and the author's clear technical preparation, this thread is worth following for anyone interested in Git's storage efficiency or multi-repository workflows.

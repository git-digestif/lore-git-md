This is a **substantive review** of the first patch in Harald Nordgren’s `fetch: introduce +: refspec for matching-inspired fetch mode` series (v11, 1/5). Phillip Wood raises a **fundamental design objection** to the series’ core premise: overloading `remote.<name>.refmap` to control *both* ref-namespace mapping *and* which refs are fetched repeats the same inflexibility the series aims to fix.

Phillip’s key critique is that the current design conflates two distinct concerns — *what* to fetch and *where* to store it — by reusing the same configuration knob (`remote.<name>.refmap`) for both. He proposes a cleaner alternative: a new `remote.<name>.fetchRefs` config key that would explicitly specify which refs to fetch (e.g., `*@{upstream}`), decoupling the "what" from the "where". This would resolve the refspec-matching order inconsistency (first-match vs. last-one-wins) and enable per-branch overrides, a capability the current design lacks. His objection is well-motivated and directly addresses the problem the series sets out to solve: users of shallow repositories want to fetch only the branches they track, not all remote branches.

The review also surfaces several **documentation and clarity issues** in the patch:
- The commit message and documentation are redundant (e.g., "the same way `remote.<name>.fetch` provides the default refspecs to fetch" is repeated unnecessarily).
- The interaction between `remote.<name>.refmap` and `remote.<name>.fetch` is not clearly explained in the documentation. Phillip asks whether setting `remote.<name>.refmap` causes `remote.<name>.fetch` to be ignored, a critical ambiguity for users.
- The name `remote.<name>.refmap` is misleading because it suggests a pure mapping function, but the series uses it to control fetch selection as well. Phillip proposes `remote.<name>.fetchRefmap` to clarify its fetch-specific role and allow for future `remote.<name>.pushRefmap`.

Phillip’s feedback is **not a nitpick**: it challenges the series’ architectural direction. The thread is now at a crossroads. The v11 series is currently **queued in `next`** (as of the 2026-05-15 "What's cooking" report), but Phillip’s review may prompt a redesign before graduation to `master`. Junio and Harald have not yet responded to this objection.

The patch itself is **mechanically sound** — it adds the `remote.<name>.refmap` configuration, updates the remote parser, and integrates it into `get_ref_map()` with clear precedence rules. However, the **design flaw Phillip identifies** (overloading `refmap` for both mapping and fetch selection) risks perpetuating the same inflexibility the series aims to fix. If adopted, his `remote.<name>.fetchRefs` alternative would require a significant rewrite of the series, particularly the dynamic branch enumeration logic in Patch 3/5.

Key files touched: `remote.c`/`remote.h` (configuration plumbing), `builtin/fetch.c` (integration with fetch logic), and documentation (`remote.adoc`, `fetch-options.adoc`). The tests in `t/t5510-fetch.sh` verify the refmap’s behavior but do not address the design ambiguity Phillip raises. The series’ shallow-repository default (Patch 5/5) and `--limited-fetch` flag (Patch 4/5) are unaffected by this review but may need rework if the design changes.

Thread identity
Subject: Shared object store for Git clones and submodules (embedded workflows)
Series version: none (design inquiry / RFC)
Originating author: Massimiliano Cialdi
Thread type: design discussion / RFC

Core problem or goal
Reduce redundant storage in embedded development environments where many persistent workspaces (clones and submodules) exist on a single machine. The concrete problem: 17.9 GiB of duplicated `.git` directories across 250 repositories. The goal is a shared object store that deduplicates Git objects while preserving local work, offline functionality, and compatibility with CI systems.

Current status
No prior patch series; this is the initial design inquiry. No code has been posted. The author has identified two fundamental gaps in Git’s current alternate mechanism:
- F1: GC in the shared store can delete objects still reachable by borrowers.
- F2: GC in borrowers drops local copies of objects that the alternate has.
The author has provided reproducible test scripts demonstrating both gaps.

Key technical details
- Subsystems touched: object store, alternates mechanism, GC, repack, remote helpers, sparse-checkout.
- New concepts proposed:
  - A remote helper that dynamically adds an alternate via the `fetch` capability.
  - A shared store that tracks borrowers’ reachability roots (O13).
  - Enhancement to `repack -l` to preserve local copies of objects reachable from selected refs (O14).
- On-disk format: The inquiry does not propose changes to Git’s on-disk formats, but the shared store would need to track borrower reachability roots (O13).
- Test coverage: The author has provided two test scripts demonstrating F1 and F2; no formal test suite has been proposed yet.
- Related work: Scalar’s shared object cache, depot_tools’ caches, and Git’s existing alternate mechanism.

Open questions and loose ends
- Would upstream accept changes to Git itself (e.g., borrower-aware GC, repack-local enhancements, or sparse-checkout integration)?
- How to track borrowers’ reachability roots (O13) without breaking compatibility with existing Git versions?
- How to ensure `repack -l` preserves local copies of objects reachable from selected refs (O14) without regressing performance?
- How to version sparse-checkout rules (R9) to avoid breaking borrowers when the shared store updates?
- How to maintain CI compatibility (R10) with a shared object store?
- What are the security implications of a shared object store (e.g., malicious borrowers poisoning the store)?
- How to handle partial clones or promisor remotes in this context?

Participant positions
- Massimiliano Cialdi (author): Proposes the shared object store concept, provides requirements (R1–R11), test scripts demonstrating F1 and F2, and explores multiple approaches. Open to feedback and architectural guidance.

Related work

- Git’s existing alternate mechanism (which the inquiry identifies as insufficient for the proposed use case).

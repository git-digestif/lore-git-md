This is a **design discussion** about the ongoing `remote.<name>.refmap` fetch-mode series, now cooking in `next`. Junio responds to Phillip Wood’s fundamental objection that the current design overloads `remote.<name>.refmap` to control both *where* fetched refs are stored and *which* refs are fetched. Junio agrees in principle: the two concerns should be separated, and the series’ current approach risks repeating the inflexibility it aims to fix.

The exchange clarifies the intended behavior: when a user configures `remote.cabal.refmap` but does not specify what to fetch on the command line or in `remote.cabal.fetch`, the series currently triggers a "smart" mode that fetches only the branches tracked by local branches at that remote. Junio confirms this is a reasonable default for now, but warns that future "smart" modes (e.g., fetching only recently updated branches) would make the current design ambiguous. He endorses Phillip’s proposal for a separate `remote.<name>.fetchRefs` config key to explicitly specify which refs to fetch, decoupling the "what" from the "where".

Junio also corrects a detail in Phillip’s sketch: the `+` prefix (force update) belongs on the refmap side (where to store), not the fetch-refs side (what to fetch), since forcing an update only makes sense if you are storing the result. The `^` prefix (negation) is correctly placed on the fetch-refs side.

The thread is now at a decision point: the series’ current design is feature-complete and queued in `next`, but Junio’s agreement with Phillip’s objection suggests a redesign is likely before graduation to `master`. No concrete patch has been posted yet, but the direction is clear: expect a follow-up series introducing `remote.<name>.fetchRefs` and adjusting the dynamic branch enumeration logic accordingly. The discussion is constructive and focused on long-term architecture, not implementation details.

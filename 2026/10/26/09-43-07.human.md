This is a substantive review of Harald Nordgren’s `remote.<name>.refmap` series, which is currently queued in `next`. Phillip Wood argues that the design conflates two distinct concerns—*where* fetched refs are stored and *which* refs are fetched—and proposes a more flexible alternative.

The series introduces `remote.<name>.refmap` to define namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) while dynamically inferring which branches to fetch based on local branches tracking the remote. Phillip’s critique centers on the implicit coupling: the presence of `refmap` not only sets the mapping but also triggers the dynamic fetch logic. He suggests splitting this into two separate config keys—`remote.<name>.refmap` for mapping and a new `remote.<name>.fetchRefs` for specifying which refs to fetch. The new key would support expressions like `*@{upstream}` to fetch only upstream branches, along with `+` and `^` prefixes for forced updates and exclusions. This would allow finer-grained control, such as per-branch refspecs with "last one wins" semantics, aligning with Git’s usual config behavior.

Phillip’s proposal is technically sound and addresses a real limitation in the current design. The series’ approach works for the shallow-repository use case but risks becoming a footgun if users later want to override the dynamic fetch logic without losing their refmap. His example—configuring `fetchRefs` to allow non-fast-forward updates for some branches but not others—highlights a practical gap in the current implementation. The critique does not question the series’ core goal (faster fetches in shallow repos) but challenges its architectural choices.

The review is substantive and tested: Phillip has clearly engaged with the design, proposed a concrete alternative, and identified edge cases (e.g., config precedence, per-branch refspecs).

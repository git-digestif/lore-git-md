This is the final patch in Harald Nordgren’s **v11 series** introducing `remote.<name>.refmap` and a matching-inspired fetch mode for shallow repositories. The series is **queued in `next`** and addresses a long-standing performance issue: shallow clones (`git clone --depth`) experience slow or hanging fetches when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches.

This specific email is a brief acknowledgment from Harald in response to Junio’s clarification about how `remote.<name>.refmap` and `remote.<name>.fetch` can coexist. Junio provided a concrete example where a user might configure both settings: `fetch` to limit what is fetched (e.g., only `master`, `next`, and `seen`), and `refmap` to map those branches to a dedicated namespace (`refs/remotes/cabal/*`). Harald confirms that the series can accommodate this use case with "some extra code," though no new implementation details are provided here.

The series is **feature-complete and uncontroversial**. All prior feedback has been addressed, including Junio’s review points (control-flow reorganization, NULL-check restoration), D. Ben Knoble’s suggestions (commit message clarity, `strvec` usage, documentation precision, code deduplication, and `const` correctness), and the addition of the `--limited-fetch` flag for `git remote add` (Patch 4/5). **Patch 5/5 (this series’ final patch) makes `--limited-fetch` the default when adding a remote in a shallow repository**, using `is_repository_shallow(the_repository)` to detect shallow clones and default to the new mode unless explicitly overridden with `--no-limited-fetch`. The flag is rejected when combined with `-t/--track` or `--mirror`, as those options already specify explicit fetch behavior.

The implementation reuses existing logic and configuration machinery, introduces no new technical debt, and includes thorough test coverage (20 new tests across `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh`, and `t/t5505-remote.sh`). The only open questions—how to handle remotes with no default branch, whether to migrate existing shallow repositories automatically, and whether to warn users about behavior changes—are not blockers for merging. The series is ready for `master` unless a flaw is identified in the clarified precedence rules or the shallow-repository default.

This is a small but clarifying exchange in the long-running `remote.<name>.refmap` series, now cooking in `next` but blocked from `master` pending a redesign. Junio C Hamano provides a concrete example of how a user might want to configure both `remote.<name>.fetch` and `remote.<name>.refmap` for the same remote: fetch only specific branches (`master`, `next`, `seen`) but store them under a custom namespace (`refs/remotes/cabal/*`). Harald Nordgren confirms the current v11 implementation already handles this case correctly, with `fetch` refspecs taking precedence over `refmap`—no dynamic branch inference is needed.

The exchange doesn’t change the code or design, but it validates the existing precedence rule (`fetch` > `refmap`) and resolves the last open question about edge-case behavior. The series remains feature-complete and uncontroversial under its current design, though the maintainer and key reviewer have already agreed that the `refmap` overloading is flawed and will be replaced with a dedicated `remote.<name>.fetchRefs` key in v12. No timeline for that revision has been given.

This is a **bugfix patch for the ODB transaction layer**, specifically addressing a critical flaw in the loose-object-idx migration logic when Git is configured with compatibility hashes (SHA-1/SHA-256 interop) and batch fsync of loose objects. The patch is **not yet ready for merging** and will require a **v2** to resolve blocking issues around atomicity and locking. This exchange between Justin Tobler and Patrick Steinhardt finalizes the design adjustments for v2, which will adopt Git’s standard temp-file-then-rename pattern to eliminate corruption risk from partial writes and replace the indefinite lock timeout with a finite 1000ms default.

The discussion confirms that the loose-object-idx mechanism has **systemic design flaws**—unsorted files, no deduplication, no pruning of stale entries, and non-atomic writes—but only the atomicity issue is being addressed in this patch. Justin agrees to rework the migration logic to use atomic writes, though he notes potential performance concerns for operations writing many loose objects (e.g., rewriting the mapping file for each object). Patrick accepts deferring the other design flaws to future work but remains critical of the underlying mechanism. The regression test (`t/t1016-compatObjectFormat.sh`) remains a strong addition, but the core logic must adopt atomic writes before the patch can proceed.

Key technical details for follow-up: the patch touches `tmp-objdir.c`, `loose.c`, and `loose.h`, introducing `loose_object_idx_merge()` to append new mapping entries to the primary index. The v2 will replace the append-under-lock pattern with temp-file-then-rename and use a 1000ms lock timeout. The loose-object-idx file’s on-disk format remains unchanged, but its systemic issues (duplicates, stale entries) are acknowledged as long-term liabilities.

This is the second patch in a three-patch **bugfix series** (v4) that fixes a data-loss race in `git repack -d`. The race occurs when a concurrent push or fetch creates a `.keep` file on a pack that `repack` is about to delete, causing `pack-objects` to skip its objects and leading to dangling refs.

This patch adds `--ignore-pack-keep-from=<file>` to `git pack-objects`. The option reads a file containing pack names (one per line) and treats those packs as if they had no `.keep` file, ensuring their objects are included in the new pack or loosened as needed. This is a **scalability and safety enabler**: it avoids command-line length limits (e.g., `ARG_MAX` on Windows) and prevents mid-repack `.keep` files from causing data loss. The implementation reuses existing `--keep-pack` logic and includes tests for functional equivalence and error handling.

The patch is **well-motivated and production-ready**. It addresses a real problem (the race is reproducible in shared repositories) and is part of a series that has been thoroughly reviewed and acked by Junio C Hamano and Jeff King (Peff). The design is minimal and focused, and the tests cover both happy paths and error cases. No regressions are expected, and the patch is likely to graduate to `master` in the current cycle. If you care about repository integrity or work with shared clones, this is worth reviewing.

This is a **security-focused discussion** about Git's SSH signing verification flaws, specifically the `valid-before` timestamp check and revocation file handling. Patrick Steinhardt responds to Phillip Wood's review of Christian Noé Ramos López's bug report, agreeing with the identified issues but offering nuanced perspectives on potential fixes.

Patrick acknowledges the `valid-before` timestamp problem—Git checks it against the committer date (which the signer controls) rather than an independent timestamp—but argues that fixing it is fundamentally difficult in a distributed system. He notes that without centralized coordination, there's no reliable way to verify the actual signing time, though he suggests theoretical upper bounds could be established if subsequent trusted commits reference the untrusted one. His stance leans toward documenting the current behavior's limitations rather than attempting a technical fix, emphasizing that `valid-before`/`valid-after` checks are only trustworthy if the signing key has never leaked.

For the revocation file issue (where Git fails open instead of closed), Patrick proposes a middle-ground solution: using Git's recently introduced `:(optional)` pathname prefix to make revocation file errors fatal by default while allowing users an escape hatch. This aligns with Phillip's preference for failing closed but adds flexibility for edge cases. The discussion remains in the design phase, with no patch yet submitted, but the technical direction is clear: document the `valid-before` behavior's limitations and tighten revocation file handling, potentially with an optional override. The subsystem (`gpg-interface.c`, `gpg-ssh.c`) and config keys (`gpg.ssh.revocationFile`) are well-defined, and the flaws are already demonstrated by test cases in the original report.

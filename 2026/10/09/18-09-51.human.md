This is a feature patch (v3 of a single-patch series) adding revision-based filtering to the `git repo structure` command. The patch allows users to include or exclude specific revisions (commits, refs, or ranges) from the repository structure report, addressing a real need for diagnosing performance issues in large repositories. The implementation uses Git’s standard `setup_revisions()` machinery, replacing the v1 design’s inflexible `--no-<reftype>` flags with a more flexible approach consistent with Git’s revision-parsing idioms.

The patch modifies `builtin/repo.c` to integrate `struct rev_info` and `setup_revisions()`, enabling arbitrary revision specifications (e.g., `git repo structure --branches --not --tags` or `git repo structure master`). The behavior is based on reachability: objects are included if they are reachable from the included revisions unless they are *only* reachable via excluded revisions. This avoids the transitive dependency omission issue of v1 by focusing on reachability rather than reference types. The patch also updates documentation (`git-repo.adoc`) and expands test coverage in `t/t1901-repo-structure.sh` to 211 lines, validating edge cases like overlapping includes/excludes and output formats (table/lines/nul).

Key changes from v2 include a revised commit title ("add revision filtering options") and a more detailed cover letter explaining the motivation. However, the patch still does not fully address Patrick Steinhardt’s substantive feedback from v2. The commit message lacks a clear justification for *why* revision-based filtering is useful (beyond the cover letter), and the documentation could better align with Git’s established terminology (e.g., "revisions" instead of "query clauses"). The `setup_revision_opt` defaults (`.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`) remain unchanged, despite Patrick’s concern that they may be overly restrictive (preventing filtering by trees or blobs). Test coverage for these edge cases is also still missing.

The implementation is sound in principle, but the unresolved technical questions suggest a v4 may be needed before it is ready for `next`. The patch is well-scoped and addresses a real user need, but the restrictiveness of the revision-parsing defaults could limit flexibility. Performance implications for large repositories with complex revision specifications have not been discussed yet, though the two-pass ref-walk (once in `setup_revisions` and again in `count_references`) could introduce overhead. The patch is self-contained, with no dependencies on other in-flight efforts.

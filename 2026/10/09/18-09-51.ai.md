This is a feature patch (v3 of a single-patch series) adding revision-based filtering to the `git repo structure` command. The patch integrates Git’s standard `setup_revisions()` machinery, allowing users to include or exclude specific revisions (commits, refs, or ranges) from the repository structure report. This version retains the core design from v2 but adds more detailed documentation and expanded test coverage, though it still does not address Patrick Steinhardt’s substantive feedback about revision-parsing defaults and test gaps.

The implementation modifies `builtin/repo.c` to use `struct rev_info` and `setup_revisions()`, replacing the v1 enum-based flag system. The new CLI syntax supports arbitrary revision specifications (e.g., `git repo structure --branches --not --tags` or `git repo structure master`), with behavior based on reachability: objects are included if they are reachable from the included revisions unless they are *only* reachable via excluded revisions. The patch also updates documentation (`git-repo.adoc`) to clarify the filtering syntax and provides examples, and expands test coverage in `t/t1901-repo-structure.sh` to 211 lines, validating edge cases like overlapping includes/excludes and output formats (table/lines/nul).

Key technical details include the use of `setup_revision_opt` with `.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`, which Patrick Steinhardt has questioned as potentially overly restrictive (preventing filtering by trees or blobs). The patch also introduces a workaround for `setup_revisions()`’s lack of a custom ref-walk callback: it performs a second ref-walk in `count_references()` to count references by type, which may introduce inefficiency. The commit message acknowledges this trade-off but does not justify why revision-based filtering is useful or how it improves upon v1, a gap noted by both Patrick and Kaartic Sivaraam.

The patch is well-scoped and addresses a real user need (diagnosing performance issues in large repositories), but the implementation choices may draw scrutiny. The reachability-based filtering logic is sound, but the restrictiveness of the revision-parsing defaults and the double ref-walk could limit flexibility or performance. The expanded test coverage is thorough, though Patrick’s request for tests involving trees/blobs and revision options like `--filter=object:type=blob` remains unmet. The patch is unlikely to be controversial in principle, but the unresolved technical questions suggest a v4 may be needed before it is ready for `next`. No performance implications have been discussed yet, though the double ref-walk could introduce overhead for complex specifications in large repositories.

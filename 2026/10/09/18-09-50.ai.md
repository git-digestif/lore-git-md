This is a feature patch (v3 of a single-patch series) adding revision-based filtering to the `git repo structure` command. The patch integrates Git’s standard `setup_revisions()` machinery, allowing users to include or exclude specific revisions (commits, refs, or ranges) from the repository structure report. This version addresses the core design critique of v1 (which used inflexible `--no-<reftype>` flags) and incorporates feedback from v2, though key technical questions remain unresolved.

The implementation modifies `builtin/repo.c` to use `struct rev_info` and `setup_revisions()`, replacing the v1 enum-based flag system. The new CLI syntax supports arbitrary revision specifications (e.g., `git repo structure --branches --not --tags` or `git repo structure master`), with behavior based on reachability: objects are included if they are reachable from the included revisions unless they are *only* reachable via excluded revisions. This avoids the transitive dependency omission issue of v1 by focusing on reachability rather than reference types. The patch also updates documentation (`git-repo.adoc`) and expands test coverage in `t/t1901-repo-structure.sh` to 211 lines, validating edge cases like overlapping includes/excludes and output formats (table/lines/nul).

Key changes from v2 include a revised commit title ("add revision filtering options" instead of "add filtering options") and a more detailed cover letter explaining the motivation. However, the patch still does not fully address Patrick Steinhardt’s substantive feedback from v2: the commit message lacks a clear justification for *why* revision-based filtering is useful (beyond the cover letter), and the documentation could better align with Git’s established terminology (e.g., "revisions" instead of "query clauses"). The `setup_revision_opt` defaults (`.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`) remain unchanged, despite Patrick’s concern that they may be overly restrictive (preventing filtering by trees or blobs). Test coverage for these edge cases is also still missing.

The patch is well-scoped and addresses a real user need (diagnosing performance issues in large repositories), but the implementation choices may draw scrutiny. The reachability-based filtering logic is sound, but the restrictiveness of the revision-parsing defaults could limit flexibility. The expanded test coverage is thorough, though Patrick’s request for tests involving trees/blobs and revision options like `--filter=object:type=blob` remains unmet. The patch is unlikely to be controversial in principle, but the unresolved technical questions suggest a v4 may be needed before it is ready for `next`.

No performance implications have been discussed yet, though the revision-based approach could introduce overhead for complex specifications in large repositories. The patch is self-contained, with no dependencies on other in-flight efforts (e.g., ODB abstraction or Rustification). The author has shown responsiveness to feedback (e.g., updating the commit title), but the core design questions raised by Patrick will likely require further iteration.

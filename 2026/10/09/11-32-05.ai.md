This is the final patch (8/8) in Patrick Steinhardt’s v2 CI housekeeping series. It reworks the reftable test coverage by repurposing the `linux-reftable-leaks` job to also test SHA-256, while preserving the original `linux-reftable` job for foreign-SCM interoperability (CVS, SVN, Perforce). The patch renames the job to `linux-reftable-sha256` in both GitHub Actions and GitLab CI configurations and updates `ci/run-build-and-tests.sh` to set `GIT_TEST_DEFAULT_HASH=sha256` and `GIT_TEST_DEFAULT_REF_STORAGE_FORMAT=reftable` for the new job.

The change addresses Junio C Hamano’s concern from v1 about losing foreign-SCM coverage by keeping the `linux-reftable` job intact. Instead, it trades the redundant `linux-reftable-leaks` job’s leak-sanitizer focus for SHA-256 coverage, a gap in the current test matrix. The commit message acknowledges the trade-off but justifies it as a net improvement, given that the leak sanitizer is unlikely to catch additional bugs beyond what the existing job already covers. The patch is mechanical (two one-line renames and a four-line addition to the case statement) and does not alter the behavior of the preserved `linux-reftable` job.

Key technical details for follow-up discussion include the new job name (`linux-reftable-sha256`), the environment variables (`GIT_TEST_DEFAULT_HASH`, `GIT_TEST_DEFAULT_REF_STORAGE_FORMAT`), and the supporting script (`ci/run-build-and-tests.sh`). The patch also sets the stage for broader discussion about whether the SHA-256 vs. foreign-SCM coverage trade-off aligns with project priorities, particularly for contributors invested in reftable (Patrick Steinhardt, Karthik Nayak) or SHA-256 (brian m. carlson). The change is unlikely to be controversial on its own, but it may draw attention as part of the larger CI modernization effort.

This is a follow-up in the shallow clone safeguard design discussion, now moving toward implementation. Sphinx proposes a concrete safeguard mechanism for `git revert` (and possibly `git commit --amend`) that would refuse by default when attempting to edit a shallow boundary commit. The safeguard would check whether the target commit OID appears in `.git/shallow` and, if so, refuse with a clear message and an override option (`--allow-shallow-boundary`). Sphinx volunteers to draft a patch for `git revert` as a starting point.

The proposal is narrowly scoped: it targets only shallow boundary commits (not empty trees in general) and focuses on destructive operations where unintended behavior is most likely. The override mechanism (`--allow-shallow-boundary`) is a key detail, addressing the 1% of intentional use cases while preventing the 99% of accidental ones. Junio’s earlier endorsement of Patrick Steinhardt’s safeguard framing remains the green light for implementation, and this email does not reopen the "whether" question—only the "how."

Subsystems touched will include shallow clone internals (`.git/shallow` parsing), commit-editing commands (`revert`, `amend`), and user-facing error messages. The patch will need tests for the safeguard logic and edge cases (e.g., multi-commit shallow clones, override behavior). No prior discussions or constraints are mentioned, but the thread history confirms that the safeguard should be opt-out (refuse by default) rather than opt-in (warn by default). The next step is Sphinx’s patch, which will likely serve as the reference implementation for this effort.

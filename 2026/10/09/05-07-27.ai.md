This is a **security-hardening patch** for the `git blame` ignore-revs parser and tag-peeling logic, the first of two patches in a series that will make `HEAD:.git-blame-ignore-revs` the default ignore-revs file. The patch directly addresses feedback from Junio C Hamano on the v1 series, focusing on two security concerns: embedded NUL bytes in ignore-revs files and unintended promisor fetches in partial clones.

Junio’s reply engages with the technical details but does not endorse the hardening as complete. He questions the necessity of rejecting lines with embedded NUL bytes, noting that the existing parser already fails safely on malformed object names (e.g., trailing whitespace after a NUL). His skepticism centers on whether the new `memchr()` check strikes the right balance between security and usability—rejecting the entire file as a suspected attack may be overly aggressive for what is currently a parsing error. On the promisor fetch prevention, however, he agrees the change is reasonable, particularly for shallow clones where lazy-fetching ignored revisions would be unexpected.

The patch itself is **well-scoped and technically sound**. It modifies `oidset_parse_file_carefully()` to reject lines containing NUL bytes via `memchr()`, replacing the prior behavior where `strchr()` and `parse_oid_hex_algop()` would stop at the first NUL but ignore trailing garbage. The tag-peeling logic in `peel_to_commit_oid()` is rewritten to use `odb_read_object_info_extended()` with `OBJECT_INFO_SKIP_FETCH_OBJECT` and `OBJECT_INFO_QUICK`, ensuring missing tag targets in partial clones do not trigger network requests. The function also verifies each tag’s declared type before parsing, preventing type confusion. Test coverage is thorough, adding cases for NUL byte rejection and partial-clone tag peeling.

The hardening is **necessary** for the follow-up patch (2/2), which will expose the ignore-revs parser to upstream-controlled content (`HEAD:.git-blame-ignore-revs`). While the changes are minimal and backwards-compatible for well-formed input, the security implications require broader review—particularly from contributors like Jeff King and brian m. carlson. Junio’s feedback remains procedural and cautionary, delegating the final security audit to the community. The patch is **not yet ready for integration**, but the design direction is settled and the implementation is feature-complete. Worth watching for security-focused review feedback.

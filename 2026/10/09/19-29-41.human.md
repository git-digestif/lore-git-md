This is a test patch, part 3 of a 15-patch series. It documents and verifies a subtle edge case in Git’s fetch logic involving branch configuration keys with `./`-prefixed merge values.

The patch adds two `test_expect_failure` tests to `t5510-fetch.sh`. Both tests set up a local branch whose `branch.<name>.merge` value begins with `./` (e.g., `./refs/heads/main`). Today, Git’s `refname_match()` function strips the leading `./` via `mkpath()`, so the bogus value still matches the real ref name. The tests assert that no ref should be marked for merge in `FETCH_HEAD` when the merge value is `./`-prefixed. Once a later patch in the series stops using `mkpath()` in `refname_match()`, these tests will flip to `test_expect_success`.

The commit message explains the two code paths where the issue surfaces—`branch_merge_matches()` and `find_ref_by_name_abbrev()`—and notes that only hand-edited config files can trigger it, since the usual Git commands reject leading `./`. The tests are clearly written and cover both the default fetch refspec and a protocol v0 fetch that omits the target ref from the refspec.

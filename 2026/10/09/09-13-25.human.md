This is the second patch in Phillip Wood’s two-patch series that teaches `git checkout -m` to recreate conflict markers using the original branch-name labels from the merge, rather than the generic “base”, “ours”, and “theirs”.

The patch adds plumbing to the ort merge backend to store the original conflict labels in `.git/MERGE_LABELS` whenever a merge leaves conflicts in the worktree. When `git checkout -m <path>` is later invoked to recreate conflicts, it reads the labels from that file instead of using the generic ones. The implementation handles edge cases (missing or malformed `.git/MERGE_LABELS`) by falling back to the generic labels, and ensures cleanup via `git commit` and the sequencer. A new flag (`REMOVE_BRANCH_STATE_PRESERVE_CONFLICT_LABELS`) is added to `remove_branch_state()` so that `git checkout -m <branch>` can preserve the labels file for subsequent `git checkout -m <path>` invocations.

The patch touches 13 files, adding roughly 100 lines of code and 20 lines of test coverage in `t/t7201-co.sh`. The new `.git/MERGE_LABELS` file is ephemeral, analogous to `MERGE_MSG` or `MERGE_MODE`, and is not a ref. All technical feedback from Junio on v2 has been addressed: `.git/MERGE_LABELS` is now written only when conflicts occur (fixing a correctness bug that could write `(null)` strings for clean merges), the `write_merge_labels()` signature has been tightened to take a single `const char *labels[3]` array, and `strbuf_detach()` is used instead of `xmemdupz()` for idiomatic buffer detachment. The test coverage has been extended to verify that `.git/MERGE_LABELS` is absent after a clean `git checkout -m <branch>`.

The only remaining discussion point is whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`) as a fallback when the user does not explicitly specify a style. Phillip has clarified that this series does not attempt to address that question, keeping the scope narrow and uncontroversial. The patch is ready for integration; the conflict style question is not blocking this series.

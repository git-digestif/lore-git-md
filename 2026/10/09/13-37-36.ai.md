This is a **performance and UX discussion** in the ongoing thread about extending `git branch --delete-merged` to detect squash-merged and rebase-merged branches. Phillip Wood responds to Harald Nordgren’s proposal to enable the feature by default with an opt-out flag, agreeing in principle but emphasizing the need to handle partial clones gracefully.

Phillip endorses Harald’s position that the feature should default to "on" if it isn’t "diabolically slow," but clarifies his stance on partial clones: rather than warning users about incomplete detection, he suggests Git should fetch the necessary blobs to calculate patch-ids, even if this makes the operation slower. He proposes documenting the performance caveat instead of disabling the feature or warning at runtime. This shifts the burden from the user (who would otherwise need to unshallow the repository) to the implementation, which would transparently handle the blob fetches. No new technical details about the algorithm or CLI design are introduced, but the exchange narrows the open question of how to handle partial clones: the emerging consensus favors fetching blobs and documenting the slowdown, rather than warning or disabling detection. The unresolved tension remains whether to provide a way to disable patch-id detection entirely for performance-sensitive workflows.

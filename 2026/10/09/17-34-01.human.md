This is a follow-up in the ongoing design discussion about safeguards for destructive operations on shallow clones. Sphinx proposes a concrete implementation approach for a safeguard that would refuse by default when users attempt to run `git revert` (and possibly `git commit --amend`) on a shallow boundary commit. The proposal leverages Git’s existing `.git/shallow` metadata to detect boundary commits and suggests a new `--allow-shallow-boundary` flag to override the refusal.

The safeguard is narrowly scoped: it would target only shallow boundary commits (not empty trees in general) and would refuse by default with a clear error message directing users to either override the safeguard or unshallow the repository. This aligns with Patrick Steinhardt’s earlier framing and Junio C Hamano’s endorsement of the approach as a way to address a "rough edge" in shallow clone usability. The proposal is well-motivated and avoids overreach, focusing on the specific scenario where users are most likely to encounter surprising behavior.

Sphinx’s offer to draft a patch for `git revert` as a starting point signals momentum toward implementation. The proposal is technically straightforward, relying on existing shallow clone metadata and introducing a single new flag. This makes it a low-risk change that could serve as a proof of concept before expanding to other commands (e.g., `git commit --amend`). The thread has already moved past philosophical objections, and Junio’s earlier endorsement suggests this patch would likely be accepted if it is cleanly implemented and includes tests.

The main open question is whether the safeguard should apply to additional commands beyond `git revert` and `git commit --amend`. Sphinx’s framing leaves this open, but the discussion so far has focused on these two as the most common pain points. Another minor detail is the override mechanism: `--allow-shallow-boundary` is clear but verbose; a shorter flag (e.g., `--force`) might be more ergonomic, though it could risk encouraging misuse. The proposal wisely avoids this bikeshed by deferring it to the patch stage.

This is a well-scoped, user-focused improvement that addresses a real usability gap without disrupting existing workflows. The safeguard is unlikely to be controversial, and the thread is now in the implementation-planning phase. If Sphinx follows through with a patch, this could land in a near-future release.

This is the second patch in Phillip Wood’s v3 series that teaches `git checkout -m` to recreate conflict markers using the original branch-name labels instead of the generic “base”, “ours”, and “theirs”. The patch is functionally complete and ready for integration.

The core change adds plumbing to the ort merge backend to store the original conflict labels in `.git/MERGE_LABELS` when conflicts occur, and to read them back when `git checkout -m` is invoked. The implementation is careful: `.git/MERGE_LABELS` is written only when there are conflicts (fixing a correctness bug in v2 that could write `(null)` strings for clean merges), and it is deleted by `git commit` and `git sequencer` to ensure cleanup. The file is treated as ephemeral, analogous to `MERGE_MSG` or `MERGE_MODE`, and is not a ref.

Key technical details include the use of `strbuf_getline()` to handle both LF and CRLF line endings (ensuring portability), a fallback to generic labels if the file is missing or malformed, and a new flag (`REMOVE_BRANCH_STATE_PRESERVE_CONFLICT_LABELS`) to prevent `remove_branch_state()` from deleting the file when `git checkout -m <branch>` is run. The patch touches `branch.c`, `merge-ort.c`, `builtin/checkout.c`, and related headers, and adds test coverage in `t/t7201-co.sh` to verify label preservation and the absence of `.git/MERGE_LABELS` after a clean `git checkout -m <branch>`.

All technical feedback from Junio on v2 has been addressed, including API signature tightening (using a single `const char *labels[3]` array for clarity), idiomatic buffer detachment (`strbuf_detach()` instead of `xmemdupz()`), and style nits. The open question about whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`) remains unresolved, but Phillip has made it clear that this series does not attempt to address that, keeping the scope narrow and uncontroversial. The patch is ready for integration; the conflict style discussion is not blocking.

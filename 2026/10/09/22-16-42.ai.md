This is a brief follow-up in the shallow-fetch regression thread. Karthik Nayak confirms Justin Tobler’s explanation of why tag backfilling cannot skip negotiation: the Git protocol requires the client to advertise all objects it already possesses (the "have" set) to compute the closure of objects needed for nested annotated tags. Because batched reference updates delay committing fetched references to disk, the client cannot report those references during backfilling negotiation, forcing the server to send unnecessary objects. Karthik’s reply reinforces the correctness of the two-transaction fix (splitting fetched references and tag backfilling into separate transactions) by ruling out the simpler alternative Patrick Steinhardt had floated. No new code or tests are introduced; the focus remains on validating the existing approach.

Key technical details carried forward for future summarization:
- **Subsystem**: fetch (shallow fetches, tag backfilling, reference transactions)
- **Root cause**: Batched updates delay reference commits, preventing the client from reporting "have" references during tag backfilling negotiation
- **Protocol constraint**: Tag backfilling requires negotiation for nested annotated tags because the server advertises both the tag OID and its recursively peeled non-tag OID, necessitating intermediate object fetches
- **Files touched**: `builtin/fetch.c` (the fix), `t/t5510-fetch.sh` (test)
- **Test focus**: Verifies shallow fetches do not refetch objects during tag backfilling by checking packet traces
- **Performance context**: The two-transaction fix restores correct negotiation while preserving most of the performance gains from batched updates (17.38× faster than pre-batched behavior)

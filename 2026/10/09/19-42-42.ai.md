This is a bug report about `git svn` failing to clone a local Subversion repository on Windows when using a `file://` URL.

The user created a local SVN repository, made some commits, and then tried to migrate it to Git using `git svn clone` with a `file://` URL pointing to the SVN repository path. Instead of cloning successfully, Git fails with an error: *"Can't create session: Unable to connect to a repository at URL [...] Unable to open repository"*. The error originates from `Git/SVN.pm` line 148, suggesting a failure in the Perl SVN bindings layer.

Key technical details: this is on Windows (Git for Windows 2.51.0), using a local filesystem path with forward slashes and a drive letter (`file:///D:/...`). The SVN repository itself is valid (the user was able to check out a working copy), so the issue appears to be specific to how `git svn` interacts with local `file://` URLs on Windows. The report does not mention whether the same operation works with an `svn://` or `http://` URL, or whether the user tried any workarounds.

No patch or code change is proposed; this is purely a user-facing bug report. The thread is likely to attract attention from Windows platform maintainers (Johannes Schindelin, Johannes Sixt) and contributors familiar with the `git svn` subsystem. If a fix emerges, it will probably involve either the Perl SVN bindings or path normalization in the `git svn` wrapper.

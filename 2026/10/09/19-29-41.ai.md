This is a test patch, part 3 of a 15-patch series. It documents and verifies a subtle edge case in Git’s fetch logic involving branch configuration keys with `./`-prefixed values.

The patch adds two `test_expect_failure` tests to `t5510-fetch.sh`. Both tests set up a local clone with a hand-edited config that assigns `branch.<name>.merge = ./refs/heads/main`. The first test checks that a default fetch does **not** mark the fetched `refs/heads/main` for merge in `FETCH_HEAD`; the second checks that a protocol v0 fetch with a refspec that omits `refs/heads/main` does **not** match the `./`-prefixed merge value against the remote’s advertised refs. Both tests currently fail because `refname_match()`—via `mkpath()`—strips the leading `./`, causing the bogus name to match.

The commit message explains that only hand-edited config reaches these code paths; normal Git commands reject leading `./` via `check_refname_format()`. The tests are written as `test_expect_failure` because the bug exists today; a later patch in the series will stop using `mkpath()` in `refname_match()`, at which point the tests will be flipped to `test_expect_success`. Key names introduced: `branch.<name>.merge`, `refname_match()`, `mkpath()`, `FETCH_HEAD`, `branch_merge_matches()`, `find_ref_by_name_abbrev()`.

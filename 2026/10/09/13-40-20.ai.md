This is a **substantive review follow-up** in the ongoing discussion about extending `git branch --delete-merged` to detect squash-merged and rebase-merged branches. Phillip Wood clarifies a key technical distinction: in a patch-based workflow (like Git’s own mailing list process), merged branches aren’t cleaned by the current `--delete-merged` logic because the individual commits—not the branch tip—are integrated upstream. This differs from squash merges, where the entire branch’s changes are combined into a single upstream commit. The observation underscores that the problem isn’t limited to squash/rebase workflows but also affects traditional patch-based contributions, reinforcing the broader need for the feature.

The email doesn’t propose new optimizations or design changes but sharpens the technical framing. It highlights that the current implementation’s reliance on tip reachability fails in multiple real-world scenarios, not just forge-driven squash merges. This aligns with the thread’s emerging consensus that the feature should default to "on" if performance isn’t prohibitively slow, though Phillip’s earlier reviews still emphasize the need for a way to disable patch-id detection for performance-sensitive cases.

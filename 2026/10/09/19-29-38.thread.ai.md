Subject: [PATCH 0/15] push: speed up refspec matching for many deletions
Series version: v1 (initial submission)
Originating author: Jon Simons
Thread type: patch series (performance-focused feature)

Core problem or goal
Client-side refspec matching in `git push` becomes a scalability bottleneck when pushing many branch deletions to a server with a large number of refs (e.g., 100k). The current implementation uses linear traversals, leading to O(n²) behavior. The series aims to achieve 10–100x speedups by replacing these traversals with `strmap` lookups and fixing long-standing behavioral quirks in `refname_match()`.

Current status
Under review; not yet in any integration branch. The series is structured to introduce failing tests for behavioral changes and bugfixes before the code changes that resolve them. Key performance improvements are demonstrated in the cover letter: a `git push --dry-run` of 100 delete refspecs to a 100k-ref server drops from 2.5–8.9s to 0.15–0.19s. Patch 5/15 delivered 55–82% of the total speedup by removing `mkpath()` overhead in `refname_match()` and eliminating the silent stripping of leading `./` in refnames. Patch 8/15 added explicit test coverage for two under-tested server-side behaviors—`receive-pack` rejecting duplicate ref updates and `send-pack` handling duplicate status reports—using plumbing to future-proof the tests against upcoming client-side duplicate detection. Patch 13/15 extended the performance test script to measure `--force-with-lease` overhead, adding new test rows that time pushes combining delete refspecs with one `--force-with-lease=<refname>:<expect>` per refspec. Baseline timings (e.g., `0.12s` for 1 lease, `0.45s` for 100 leases) were provided to establish a reference point for the speedup delivered in patch 14/15. Patch 14/15 refactored `apply_push_cas()` to invert loop nesting, preparing for the final patch's `strmap` optimization; the change is pure refactoring with no behavioral differences.

Key technical details
- Files touched: `refs.c`, `remote.c`, `t/t5516-fetch-push.sh`, `t/t5408-push-porcelain.sh`, `t/t5410-receive-pack.sh`, `t/perf/p5516-push-delete-refspec.sh` (patch 8 added tests to `t5408` and `t5410`; patch 13 added test rows to the perf script; patch 14 touches only `remote.c`)
- New/renamed symbols: `refname_match()` (behavior change: no longer strips leading `./` via `mkpath()`; now uses `match_parse_rule()` for direct string comparison), `check_push_refs()`, `match_explicit_refs()`, `apply_push_cas()` (refactored in patch 14 to invert loop nesting, splitting logic into `apply_one_cas()` and `apply_cas_tracking()` helpers), `match_parse_rule()` (helper function moved earlier in `refs.c` for use by `refname_match()`)
- Test coverage: new tests in `t5516` (patch 2: `./` refname quirk), `t5408` (patch 8: `send-pack` duplicate status handling), `t5410` (patch 8: `receive-pack` duplicate ref rejection), and perf script `t/perf/p5516-push-delete-refspec.sh` (patches 1 and 13). Patch 5 flipped `test_expect_failure` to `test_expect_success` for `./`-prefixed refspec cases in `t5510` and `t5516`.
- On-disk format: no changes
- Behavioral changes: duplicate destinations (e.g., pushing two refspecs to the same new branch) are now correctly rejected client-side when the remote is empty (later patch); leading `./` in refnames are no longer stripped (patch 5), fixing a long-standing quirk where syntactically bogus refnames could be silently canonicalized into valid ones.
- Performance: 10–100x speedups in benchmarked scenarios (cover letter); patch 5 contributes 55–82% of the total speedup by removing `mkpath()` overhead; patch 13 establishes baseline timings for `--force-with-lease` overhead (e.g., `0.12s` for 1 lease, `0.45s` for 100 leases) to quantify the impact of patch 15/15.

Open questions and loose ends
- The removal of `mkpath()` in `refname_match()` (patch 5) may require careful review to ensure no regressions in edge-case refspec matching, particularly in workflows that inadvertently relied on the old `./` stripping behavior. Patch 2 (earlier in the series) added a failing test to guard against such regressions, and patch 5 resolved it.
- Kristoffer Haugsbakk noted a stylistic preference: the Git project generally favors combining a regression test and its fix into a single commit, rather than splitting them across two commits as done in this series. This is a process-oriented observation with no bearing on the technical correctness of the patches.

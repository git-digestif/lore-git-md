Subject: [PATCH 0/15] push: speed up refspec matching for many deletions
Series version: v1 (initial submission)
Originating author: Jon Simons
Thread type: patch series (performance-focused feature)

Core problem or goal
Client-side refspec matching in `git push` becomes a scalability bottleneck when pushing many branch deletions to a server with a large number of refs (e.g., 100k). The current implementation uses linear traversals, leading to O(n²) behavior. The series aims to achieve 10–100x speedups by replacing these traversals with `strmap` lookups and fixing long-standing behavioral quirks in `refname_match()`.

Current status
Under review; not yet in any integration branch. The series is structured to introduce failing tests for behavioral changes and bugfixes before the code changes that resolve them. Key performance improvements are demonstrated in the cover letter: a `git push --dry-run` of 100 delete refspecs to a 100k-ref server drops from 2.5–8.9s to 0.15–0.19s.

Key technical details
- Files touched: `refs.c`, `remote.c`, `t/t5516-fetch-push.sh` (new test in patch 2)
- New/renamed symbols: `refname_match()` (behavior change: no longer strips leading `./` via `mkpath()`), `check_push_refs()`, `match_explicit_refs()`, `apply_push_cas()` (all converted from linear traversals to `strmap` lookups)
- Test coverage: new tests in `t5516` (patch 2: `./` refname quirk), `t5408`, `t5410`, `t5510`; new perf script `t/perf/p5516-push-delete-refspec.sh`
- On-disk format: no changes
- Behavioral changes: duplicate destinations (e.g., pushing two refspecs to the same new branch) are now correctly rejected client-side when the remote is empty; leading `./` in refnames are no longer stripped (patch 5)
- Performance: 10–100x speedups in benchmarked scenarios

Open questions and loose ends
- The `mkpath()` removal in `refname_match()` (commit 5) may require careful review to ensure no regressions in edge-case refspec matching. Patch 2 (this email) adds a failing test to guard against such regressions.

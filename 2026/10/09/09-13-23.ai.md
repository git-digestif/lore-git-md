This is the v3 submission of Phillip Wood’s two-patch series that teaches `git checkout -m` to recreate conflict markers using the same branch-name labels the user originally saw during the merge, rather than the generic “base”, “ours”, and “theirs”.

The series is now functionally complete. All technical feedback from Junio on v2 has been addressed: `.git/MERGE_LABELS` is written only when conflicts occur (fixing the correctness bug that could write `(null)` strings for clean merges), the `write_merge_labels()` signature has been tightened to take a single `const char *labels[3]` array, `strbuf_detach()` is used instead of `xmemdupz()`, and a comment has been added to clarify that trailing cruft in the labels file is ignored. The portability fix (using `strbuf_getline()` to handle both LF and CRLF line endings) remains in place, and the test coverage has been extended to verify that `.git/MERGE_LABELS` is absent after a clean `git checkout -m <branch>`.

The open question about whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`) remains unresolved, but Phillip has made it clear that this series does not attempt to address that. The current implementation preserves only the labels, falling back to the user’s configured or explicitly specified style. This keeps the scope narrow and uncontroversial while still delivering the core benefit.

Patch 1 (refactoring `remove_branch_state()` to use flags instead of a boolean) is unchanged from v2 and remains uncontroversial. Patch 2 is ready for integration; the only remaining discussion point is the conflict style question, which is not blocking this series.

This is the third iteration of Phillip Wood’s two-patch series that teaches `git checkout -m` to recreate the original conflict labels (branch names) instead of the generic “base”, “ours”, and “theirs”. The series is now functionally complete and addresses all the feedback raised in the previous rounds.

Patch 1 is a small refactoring in `branch.c`/`branch.h` that replaces the `verbose` boolean in `remove_branch_state()` with an `unsigned flags` field, introducing `REMOVE_BRANCH_STATE_VERBOSE` as the sole flag. This is a preparatory step with no user-visible behavior change, and it remains uncontroversial.

Patch 2 adds the core functionality: the ort merge backend now writes the original labels to `.git/MERGE_LABELS` when a merge results in conflicts, and `git checkout -m` reads that file to recreate the same labels. The implementation is careful about edge cases—falling back to generic labels if the file is missing or malformed, ensuring cleanup via `git commit` and the sequencer, and using `strbuf_getline()` to handle both LF and CRLF line endings portably. Junio’s feedback on flag naming, conditional preservation logic, idiomatic buffer detachment, style nits, API signature tightening, and a correctness bug (unconditionally writing `.git/MERGE_LABELS` even for clean merges) has been fully addressed. The correctness bug is fixed by writing the file only when conflicts occur, and the API is now cleaner, with `write_merge_labels()` taking a single `const char *labels[3]` array.

The only remaining open question is whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`) as a fallback when the user does not explicitly specify a different style. Junio framed this as a trade-off between convenience and explicit control, noting that users can already specify the style manually when needed. Phillip has clarified that preserved styles would only apply as a fallback, not override user-specified styles, but no consensus has emerged. This question does not block the series, as the label preservation itself is a clear improvement and can be extended later if desired.

The series is small, well-scoped, and thoroughly tested (a new test in `t/t7201-co.sh` verifies label preservation). Phillip is a seasoned contributor with deep expertise in the merge machinery, so the implementation is likely to be solid. The change is user-facing but not disruptive—it only affects the appearance of conflict markers, not their semantics. Unless new objections surface, this looks ready for `next`.

This is a **security discussion** about Git’s SSH signing verification flaws, specifically the two issues reported by Christian Noé Ramos López: (1) the `valid-before` timestamp check uses the committer date (which the signer controls) instead of an independent timestamp, and (2) a missing or unreadable `gpg.ssh.revocationFile` fails open (warns and continues) instead of failing closed.

Patrick Steinhardt replies to Phillip Wood’s review, agreeing with the core problems but offering nuanced perspectives. On the `valid-before` issue, Patrick argues there’s no practical fix in a distributed system—without coordination, Git can’t reliably establish the actual signing time. He suggests documenting this limitation to avoid giving users a false sense of security, noting that once a signing key leaks, `valid-before`/`valid-after` checks become meaningless. For the revocation file issue, he proposes a middle ground: fail by default but allow users to opt out with the `:(optional)` pathname prefix (a feature recently added for other path-based options). This would align with Git’s general philosophy of strict defaults while providing flexibility for edge cases.

The discussion is substantive and pragmatic, focusing on trade-offs between security and usability. Patrick’s suggestions are well-reasoned—his `:(optional)` proposal for revocation files is particularly noteworthy, as it balances safety with user control. The thread remains in the design phase; no patch has been posted yet, but the next steps are clear: (1) update documentation to clarify the `valid-before` behavior and its limitations, and (2) implement a fail-closed policy for revocation files, with an optional escape hatch. This is a high-priority security issue with straightforward fixes, so expect a patch soon. If you care about Git’s signing security, this thread is worth following.

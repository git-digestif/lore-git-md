This is a documentation patch series introducing `gitmergeconflicts(7)`, a new man page that consolidates Git’s scattered merge-conflict resolution guidance into a single, user-focused guide. The v2 update addresses all major feedback from the first round: it adds a foundational "WHAT IS A MERGE CONFLICT?" section, rewrites the "ours" vs. "theirs" explanation for clarity, includes `git log --merge -p` as a resolution tool, and retains cherry-pick-specific details in its man page while linking to the new guide. The series also fixes mechanical issues (build system integration, `.gitattributes`, and `command-list.txt` registration) and incorporates surface-level feedback (typos, commit message style).

The motivation is compelling: Git’s current documentation repeats or omits key details across `git merge`, `git rebase`, and other commands, leaving users confused about terminology (e.g., "ours/theirs") and workflows. Julia Evans explicitly cites user feedback (via Mastodon and direct comments) as the driving force behind the guide’s design, prioritizing practical examples over technical minutiae. The new page’s structure—covering conflict markers, resolution tools (`diff3`, `git log --merge`), and edge cases (rebase’s "upside down" behavior)—directly addresses these pain points. Junio C Hamano and Patrick Steinhardt’s advocacy for `merge.conflictstyle=diff3` is now supported by concrete examples in the guide, elevating it from a stylistic preference to a best practice.

The series is well-crafted and nearly ready. The v2 changes resolve the substantive concerns raised in reviews (e.g., cherry-pick-specific content, foundational explanations) while preserving the guide’s user-centric tone. The only remaining loose ends are minor: whether to cover `git apply`/`git am` conflicts (deferred as out of scope), and potential follow-up patches for conflict-marker labels or `git status` wording (exploratory for now). The build system integration is complete, and the series is already in Junio’s `seen` branch for testing. Reviewers are likely to focus on the accuracy of technical details (e.g., `diff3` examples) and the balance between brevity and completeness, but the core idea—a centralized conflict-resolution resource—addresses a long-standing gap in Git’s documentation. This is a clear win for users and maintainers alike.

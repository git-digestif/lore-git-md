Subject: [PATCH] bundle-uri: handle relative URIs with excessive parent traversals
Series version: standalone patch (no series)
Originating author: Aniket Gupta <aniketgupta3001@gmail.com>
Thread type: bugfix patch

Core problem or goal
The `git bundle-uri` command crashes when a bundle list contains a relative URI with too many `../` components to resolve against the base URI. The crash occurs in `bundle_list_update()` when `relative_url()` calls `die()`, terminating the entire command and preventing processing of other entries in the bundle list.

Current status
Under review. No prior versions. No maintainer decision recorded.

Key technical details
- Files touched: `bundle-uri.c`, `remote.c`, `remote.h`, `t/t5750-bundle-uri-parse.sh`
- New function: `relative_url_gently()` in `remote.c`/`remote.h` returns an error instead of dying
- Old behavior preserved: `relative_url()` remains as a wrapper that still calls `die()`
- New behavior: `bundle_list_update()` uses the gentle variant and skips malformed URIs after emitting an error
- Test update: replaces a TODO in `t5700` with a concrete expectation for error output and continued parsing; test cases for certain relative URIs were dropped, raising questions about coverage
- Subsystems: bundle URI, URL resolution, error handling

Open questions and loose ends
1. **Error recovery rationale** – Patrick Steinhardt asks why continuing after an error is acceptable, and whether the commit message should clarify where bundle lists originate (e.g., user-provided vs. server-provided) to justify the tradeoff.
2. **Error message usefulness** – The existing error message from `relative_url()` is noted as potentially unhelpful; Patrick questions whether it should be improved now or in a follow-up.
3. **Test coverage gap** – Patrick points out that test cases for certain relative URIs (e.g., `../foo`) were dropped, suggesting a possible regression in coverage.
4. **Refactoring opportunity** – Patrick observes that the error-handling logic in `relative_url()` is becoming complex and suggests a preparatory refactor, though he does not insist on it for this patch.

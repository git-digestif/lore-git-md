This is a **design discussion** in the ongoing `git worktree list --branch=<branch>` thread. Junio C Hamano responds to Eric Sunshine’s proposal for a generic `--filter` mechanism by sketching an even more flexible alternative: a `--filter-command` option that accepts a shell script snippet to evaluate for each worktree.

Junio’s suggestion takes the extensibility question to its logical extreme. Instead of hardcoding filters for branch names, locked status, or other properties, `--filter-command` would let users write arbitrary shell logic to decide which worktrees to include. His example — listing worktrees with more than five unpushed commits — demonstrates how this could subsume not only the proposed `--branch` filter but also existing branch-filtering commands like `git branch --contains`. The implication is that `--branch` might eventually become syntactic sugar for a specific `--filter-command` invocation.

The tone is speculative ("I dunno") rather than prescriptive, and Junio does not insist that the current patch adopt this approach. Instead, he is exploring whether the project should aim for a unified filtering framework from the outset, rather than layering ad-hoc options like `--branch` that might later need deprecation. This raises the stakes for the naming and design choices in the current patch: if `--filter-command` (or something like it) becomes the long-term direction, then `--branch` could look like a short-lived detour.

No technical objections to the existing implementation are raised, and the carried-over open questions (e.g., main worktree filtering, validation logic) remain untouched. The focus here is purely on the long-term architecture of worktree filtering. This reply is likely to shift the thread’s center of gravity toward broader design questions, potentially delaying the current patch until the community reaches consensus on whether to pursue a general filtering mechanism.

This is a **design clarification and test case** for the `fetch: introduce +: refspec for matching-inspired fetch mode` series (v12). Harald Nordgren responds to Junio C Hamano and Phillip Wood’s unresolved edge case about how Git should handle colon-separated `remote.<name>.fetch` entries (e.g., `+refs/heads/master:refs/remotes/custom/master`) when `remote.<name>.fetchRefmap` is also configured. Harald **proposes and tests dual storage**, where the ref is stored in both the refmap’s destination (`refs/remotes/cabal/master`) and the explicit destination (`refs/remotes/custom/master`), matching the command-line precedent Junio cited (`git fetch --refmap=... refs/heads/master:refs/remotes/origin/master`).

The test case is **well-structured and thorough**, covering setup, configuration, fetch execution, and verification of the resulting refs. It demonstrates that the v12 implementation already behaves as Junio’s precedent suggests, storing the ref in both locations. This resolves the ambiguity about whether dual storage is technically feasible and aligns the config-based behavior with the existing command-line behavior. The test will likely be included in `t/t5586-fetch-refmap.sh` in the next revision (v13).

This is the latest update in the long-running `fetch: introduce +: refspec for matching-inspired fetch mode` series, now at v12. The patch series is complete, under active review, and expected to graduate to `master` in the current cycle once a few remaining edge cases are resolved.

Harald Nordgren posts a test case that demonstrates how the v12 implementation handles the edge case Phillip Wood raised: when both a colon-separated `remote.<name>.fetch` entry (e.g., `+refs/heads/master:refs/remotes/custom/master`) and `remote.<name>.fetchRefmap` are configured, the ref is stored in *both* locations. This matches the existing command-line behavior (`git fetch --refmap=... refs/heads/master:refs/remotes/origin/master`), which Junio previously cited as precedent. The test is straightforward and confirms the behavior without introducing new complexity.

The discussion remains collaborative and low-stakes. There is no disagreement on the broader design—Junio and Phillip Wood have already endorsed the v12 approach, which decouples the "what to fetch" (`remote.<name>.fetchRefmap`) from the "where to store it" (`remote.<name>.refmap`). The only open question is whether this dual-storage behavior is the right choice for the config-based case, or if the system should error out or prioritize one config key over the other. Harald’s test suggests he is leaning toward adopting the command-line precedent, which would make the behavior consistent across contexts.

This is a minor edge case that affects users migrating from older configurations, not a technical blocker. The resolution will need to be documented in `remote.txt` and tested in `t/t5586-fetch-refmap.sh`, but it is unlikely to delay the series’ graduation. The patch is well-crafted, thoroughly tested, and addresses a real usability pain point for shallow repositories. If you care about fetch performance or work with shallow clones, this series is worth tracking.

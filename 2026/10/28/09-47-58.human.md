This is the v5 cover letter for a three-patch series that fixes a regression in shallow fetches when backfilling tags. The series targets the fetch subsystem and is a direct response to a performance issue introduced by commit 0e358de64a ("fetch: use batched reference updates", 2025-05-19).

The core problem is that batched updates delay committing references to disk until after tag backfilling begins, which means the client has no 'have' references to report during negotiation. In shallow repositories, this forces the server to send all objects the client already possesses. The regression is severe: benchmarks show the fix restores performance to 17× faster than the pre-batched-update behavior.

This iteration (v5) addresses the **blocker-level memory management issue** identified in v4 by adding a precursor patch that fixes a pre-existing leak in the remote-helper transport's cleanup. The main patch now drops its manual cleanup and relies on the new `transport_options_release()` function. The series also splits out a tangential test into its own commit, leaving two focused tests that verify the fix works for both atomic and non-atomic fetches. The commit message now documents the scalability trade-off: advertising all fetched references during negotiation is an acceptable O(n) complexity for the performance gain.

The series looks technically sound and well-motivated. The memory management issue that previously blocked it is now resolved, and the design (exposing pending transaction state via `negotiation_include_tips`) is simpler than the v3 two-transaction approach. The patch touches `builtin/fetch.c`, `transport-helper.c`, `transport.c`, and adds tests in `t/t5510-fetch.sh`. If no new issues surface, this is likely ready for `next`.

The series introduces `extensions.objectStorage`, a pluggable object database backend mechanism modeled after the ref storage extension. It implements the baseline `files` backend with support for relocating `.git/objects` via a payload (e.g., `files://objs`), adds environment variables (`GIT_OBJECT_STORAGE_FORMAT`, `GIT_DEFAULT_OBJECT_STORAGE_FORMAT`), user-facing configuration (`init.defaultObjectStorageFormat`), and CLI tools (`git init --object-storage-format=`, `git clone --object-storage-format=`, `git submodule add/update --object-storage-format=`). Submodules inherit the parent repository’s storage *type* but strip the *payload* for consistency with ref storage, a design choice that may surprise users but is undocumented in the man pages.

The unresolved architectural debate—whether `extensions.objectStorage` should exist as a public API—remains the sole barrier to integration. SZEDER Gábor’s v3 review questioned the motivation behind exposing the `files` backend’s payload (directory relocation) as a user-configurable feature, arguing it may not justify the complexity of a URI-based system. Patrick’s v4 response expanded the commit message to justify the payload’s utility (testing, alignment with ref storage, and internal use cases like repository migrations) but did not engage with the reviewer’s broader skepticism. Junio’s eventual decision may hinge on this debate, though the series is otherwise mechanically complete and well-tested.

The implementation is robust, with careful attention to precedence rules (CLI > environment > repository config > defaults), backward compatibility (repository format version bumps), and edge cases (e.g., local clone restrictions for non-default backends). The series touches 35 files across core subsystems (`odb/`, `setup.c`, `repository.c`), built-in commands, documentation, and tests. If merged, it will lay the groundwork for alternative backends (e.g., cloud storage) while immediately enabling `.git/objects` relocation—a niche but occasionally requested feature.

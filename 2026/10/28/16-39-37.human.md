This is a **bugfix follow-up** in the ongoing `sigchain` signal-handler concurrency thread. Phillip Wood, the reviewer who previously identified the deeper risk of concurrent handler execution (e.g., double-free or use-after-free), replies to Ian Hu’s proposal for a thread-level fix.

Phillip endorses Ian’s plan to create a `git_pthread_create()` wrapper that blocks `SIGINT`, `SIGHUP`, `SIGTERM`, and `SIGQUIT` during thread creation, noting this is likely the safest solution. He acknowledges the limitation that this won’t help threads created by external libraries (though he isn’t aware of any such cases in Git). He also clarifies a technical point: blocking `SIGPIPE` doesn’t ignore it (unlike `SIG_IGN`), but merely delays delivery until unblocked, so leaving it unblocked is correct. On the `sigaction()`-based chain, Phillip agrees masking all common signals (not just the one being handled) is safer, since `sigchain_push_common()` sets the same handler for all of them and not all handlers are reentrant.

The key takeaway is that Phillip now favors the thread-level fix over the current "repair-after-corruption" patch or the spinlock alternative. He suggests dropping the current patch entirely if the thread-level fix is implemented, as it should prevent the issue altogether. The discussion is now waiting for broader input—Phillip recommends waiting a few days to see if others weigh in before Ian invests significant time in coding the new approach. This email moves the thread closer to consensus on a more comprehensive solution.

This is a **bugfix follow-up** in the `sigchain` signal-handling subsystem, part of an ongoing discussion about how to fix a race condition that can leave Git processes stuck in an infinite CPU loop.

Ian Hu responds to Phillip Wood’s review by clarifying the trade-offs between two approaches: the current "repair after corruption" patch (already in Junio’s `seen` branch) and a more ambitious "prevent corruption entirely" design. He acknowledges that the current patch is a minimal band-aid—it heals a corrupted state that should never occur, but does nothing to stop the concurrent execution of signal-handler cleanup code that could lead to double-free or use-after-free. Ian previously experimented with a per-signal spinlock to serialize the chain updates, but abandoned it due to edge cases (async-signal-safety, lock leaks on thread death, and Windows portability).

The email now frames the central question: is serializing the chain state sufficient, or must the fix also prevent concurrent handler execution by blocking signals during thread creation and switching to `sigaction()`? Ian leans toward the latter as the more robust solution and offers to implement it as a new patch series, either replacing or supplementing the current fix. The tone is collaborative, seeking Phillip’s guidance on which path the project prefers.

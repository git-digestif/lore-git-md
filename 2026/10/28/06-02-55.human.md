This is a **feature-focused review reply** in the ongoing discussion about adding branch filtering to `` `git worktree list` ``. Eric Sunshine responds to Phillip Wood’s substantive review with a design question about the option’s name and future extensibility.

Sunshine acknowledges Phillip’s technical feedback as excellent but shifts focus to a higher-level concern: whether ``--branch=<branch>`` is the right name for the new option. He suggests that a more generic name like ``--filter=branch:<name>`` might be preferable, anticipating that users may later want to filter worktrees by other properties (e.g., locked status, prunable state, or path). The ``--filter`` prefix would leave room for future enhancements without requiring a breaking rename.

He also raises the question of how multiple filters should combine. While ``--filter=branch:<name>`` options would naturally combine via logical OR, future filters might need AND, NOT, or grouping. He asks whether other Git commands set a precedent for filter option naming and combination logic, though he does not demand an immediate answer or implementation change. His tone is exploratory rather than prescriptive, and he explicitly states that the current patch should not be held up by these considerations.

The reply does not engage with the code-level refactoring or usability concerns Phillip raised, nor does it revisit Eric’s earlier `` `git worktree foreach` `` proposal. Instead, it introduces a new dimension to the design discussion: whether the option’s name should reflect its current narrow scope or a broader, future-proof vision. This is a classic Git design tension—balancing simplicity for today’s use case against flexibility for tomorrow’s. The question is now on the table for the author and other reviewers to consider.

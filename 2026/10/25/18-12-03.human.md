This is the final patch in Harald Nordgren’s ten-iteration series introducing a "matching-inspired" fetch mode for shallow repositories. The patch makes `--limited-fetch` the default when adding a remote in a shallow repository, addressing a long-standing usability issue where `git remote add` would still configure a wildcard refspec even in shallow clones, defeating the purpose of shallow cloning.

D. Ben Knoble’s review was surface-level, pointing out a minor wording inconsistency in the commit message: it initially framed the problem as specific to "single-branch shallow clones" but the implementation only checks for shallow repositories (not single-branch). Harald acknowledges the feedback and will update the wording. This is a reasonable simplification, as Git has no reliable way to track whether a repository was cloned with `--single-branch`, and shallow repositories are the primary use case for the feature.

The implementation is minimal and uncontroversial. It modifies `builtin/remote.c` to check `is_repository_shallow(the_repository)` when the `limited_fetch` flag is unset, defaulting to `--limited-fetch` unless explicitly overridden with `--no-limited-fetch`. The change reuses existing machinery (the `limited_fetch` flag and `is_repository_shallow()` helper) without introducing new technical debt. The documentation in `git-remote.adoc` is updated to explain the new default behavior, and four new tests in `t/t5505-remote.sh` verify the shallow-repository default, `--no-limited-fetch` override, `-t/--track` behavior, and full-repository backward compatibility.

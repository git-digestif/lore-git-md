This is the third patch in Tyler Cipriani’s four-patch series optimizing Git’s `test-lint` infrastructure, specifically addressing the `test-grep-lint` performance regression. The patch moves the core parsing and token-checking logic from `t/greplint.pl` into a new shared library, `lib-greplint.pl`, while preserving the standalone functionality of `greplint.pl`. The refactoring is a prerequisite for the next patch, which will integrate greplint checks into `chainlint.pl`’s tokenization pass, eliminating redundant file I/O and parsing overhead.

The changes are mechanical but substantial: `t/greplint.pl` is reduced from ~250 lines to ~20, with most of its logic relocated to `lib-greplint.pl` (a near-copy of the original script, trimmed of its main driver code). The new library exposes a `check_tokens()` function that encapsulates the token-walking logic, returning error messages instead of printing them directly. This allows `chainlint.pl` to invoke greplint checks during its own parsing pass without duplicating effort. The patch also updates `greplint.pl` to load the library and delegate its work, while maintaining backward compatibility for standalone use (e.g., when `GIT_TEST_CHAIN_LINT=0`).

Key technical details include:
- **New symbols**: `lib-greplint.pl` introduces `check_tokens()`, a function that takes parsed tokens and returns a list of error messages.
- **Behavior**: No functional changes to the linting rules or Git’s test suite; the optimization is purely internal to the test-lint infrastructure.
- **Files touched**: `t/greplint.pl` (heavily trimmed), `t/lib-greplint.pl` (new, derived from `greplint.pl`), and no other files in this patch.
- **Performance impact**: This patch alone does not improve runtime (that comes in patch 4/4), but it lays the groundwork for the ~4x speedup observed in the series’ final state.

The patch is well-structured and uncontroversial, with clear commit message context linking it to the series’ goal of addressing Junio’s workflow bottleneck. The refactoring is conservative, avoiding disruption to existing workflows while enabling the performance gains in the next patch. No edge cases or objections have been raised in the thread so far.

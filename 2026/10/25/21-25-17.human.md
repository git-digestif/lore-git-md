This is a follow-up in the RFC thread proposing `^/` syntax for root-relative submodule URLs. The discussion between Stanislav Aleksandrov and Jacob Keller clarifies the design rationale and addresses several open questions from Jacob’s substantive review.

The core issue remains: when superprojects are forked into deeper hierarchies (e.g., GitLab subgroups), relative paths like `../lib.git` break because they resolve against the fork’s path, not the original repository’s root. The `^/` syntax is designed to solve this by replacing only the path portion of the superproject’s remote URL, preserving protocol, host, and credentials. For example, `^/org/lib.git` resolves `https://gitlab.com/me/super.git` to `https://gitlab.com/org/lib.git`.

Stanislav’s responses address Jacob’s concerns about alternatives and edge cases. He explains why `url.<base>.insteadOf` and `.gitmodules` extensions are unsuitable: they either require per-clone configuration or introduce ambiguity by ignoring the host in absolute URLs. The `^/` syntax is opt-in and avoids these pitfalls by resolving dynamically against the superproject’s remote URL. Stanislav also clarifies that `git submodule add` explicitly rejects `^/` URLs to prevent confusion with literal `^` directories, and that local paths with `^/` are intentionally unsupported to avoid requiring `protocol.file.allow=always`.

The discussion leaves two key questions unresolved. First, Jacob’s suggestion to use `../../` for relative traversal isn’t directly addressed, implying the current design intentionally limits resolution to the server root. Second, while the patch’s use of `skip_bracketed_host()` should handle IPv6 in SCP-style URLs, this hasn’t been explicitly tested. The thread also touches on shell escaping: `^` is special in `cmd.exe` and Git Bash, but Stanislav accepts this as a necessary trade-off.

The patch remains in RFC phase, with no merge status reported. The conversation suggests the design is technically sound but may face debate over whether new syntax is justified. Future iterations will likely need to address these points, especially if other reviewers echo Jacob’s preference for avoiding new syntax. For now, the patch is well-motivated and thoroughly tested, making it worth attention from anyone interested in submodule workflows.

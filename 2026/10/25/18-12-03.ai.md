This is the final patch in Harald Nordgren’s v10 series introducing a "matching-inspired" fetch mode for shallow repositories. The patch makes `--limited-fetch` the default when adding a remote in a shallow repository, addressing a usability issue where `git remote add` in a shallow clone would still configure a wildcard refspec, defeating the purpose of shallow cloning.

Harald acknowledges D. Ben Knoble’s surface-level feedback about a wording inconsistency in the commit message: it initially framed the problem as specific to "single-branch shallow clones" but the implementation only checks for shallow repositories (not single-branch). This is a reasonable simplification, as Git has no reliable way to track whether a repository was cloned with `--single-branch`, and shallow repositories are the primary use case. The change is uncontroversial and will be updated for clarity.

The implementation is minimal and reuses existing machinery: it modifies `builtin/remote.c` to check `is_repository_shallow(the_repository)` when the `limited_fetch` flag is unset (`-1`), defaulting to `--limited-fetch` unless explicitly overridden. The documentation in `git-remote.adoc` is updated to explain the new default behavior, and four new tests in `t/t5505-remote.sh` verify the shallow-repository default, `--no-limited-fetch` override, `-t/--track` behavior, and full-repository backward compatibility. No new technical debt is introduced.

This patch is part of a technically complete and uncontroversial series that is ready for merging to `next`. The only remaining work is incorporating accepted non-blocking suggestions (e.g., commit message clarity, `strvec` refactoring, and code deduplication) in a final revision or follow-up patches. The series as a whole addresses a long-standing usability issue for shallow repositories and reuses existing logic and configuration machinery.

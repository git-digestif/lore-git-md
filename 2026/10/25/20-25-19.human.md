This is the third patch in Harald Nordgren’s v11 series introducing a "matching-inspired" fetch mode for Git. The series is queued in `next` and addresses a long-standing performance issue in shallow repositories: when no refspec is given, `git fetch` currently negotiates history for all remote branches, which can be slow or hang when the remote has many branches.

This patch implements the core dynamic branch inference logic. When a remote has a `remote.<name>.refmap` configured but no `remote.<name>.fetch`, a refspec-less `git fetch` now infers what to fetch by enumerating local branches whose `@{upstream}` points to that remote. The refmap itself only controls where the fetched refs land, not which branches are selected. The implementation adds a new helper function, `branches_tracking_remote()`, which iterates over all local branches and collects the source ref for each branch whose `remote_name` matches the target remote. This logic is integrated into `get_ref_map()` in `builtin/fetch.c`, which constructs a dynamic refspec from the inferred branches and populates `transport_ls_refs_options.ref_prefixes` to limit the transport layer’s ref requests.

The patch touches `remote.c`/`remote.h` (adding the `branches_tracking_remote()` helper), `builtin/fetch.c` (integrating the dynamic branch inference logic), documentation (`config/remote.adoc` and `fetch-options.adoc`), and tests (`t/t5586-fetch-refmap.sh`, which adds 119 lines of new tests covering edge cases like multiple branches tracking the same upstream, branches tracking different remotes, and `git remote show` compatibility). The implementation reuses the existing `collect_upstream_from_remote()` helper (introduced in Patch 2/5) to avoid code duplication, and the control-flow reorganization requested by Junio is fully addressed.

The behavior change is opt-in: non-shallow repositories continue using wildcard refspecs by default, and the new mode is only enabled when `remote.<name>.refmap` is configured without `remote.<name>.fetch`. The patch is uncontroversial, introduces no new technical debt, and resolves all prior feedback, including D. Ben Knoble’s suggestions for clarity and efficiency. The only remaining open questions are edge-case handling (e.g., remotes with no default branch), but these are not blockers for merging. The series is ready for `next` and is expected to graduate to `master` in the near future.

This is a feature patch series (v11 of 5 patches) that introduces a "matching-inspired" fetch mode to address a long-standing performance issue in shallow repositories. The series is now ready for merging to `next` after addressing all prior feedback, including Junio’s review points and D. Ben Knoble’s suggestions for clarity and efficiency.

The core problem is that users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. This series solves that by dynamically fetching only the branches tracked by local branches at the remote being fetched, using a new `remote.<name>.refmap` configuration to separate namespace mappings from fetch selection logic.

Key changes in v11 include: (1) `remote_find_tracking()` now falls back to `remote.<name>.refmap` when `remote.<name>.fetch` doesn’t match, with tests for negative refspec exclusion; (2) helpers now use `strvec` instead of `string_list` for efficiency; (3) the `followRemoteHEAD` lookup is deduplicated; and (4) commit messages and documentation are clearer, with concrete examples and precise behavior descriptions. The series also adds a `--limited-fetch` flag to `git remote add` and makes it the default in shallow repositories.

The implementation touches `remote.c`, `builtin/fetch.c`, `builtin/remote.c`, and documentation files, with 14 new tests covering edge cases and backward compatibility. The changes are uncontroversial, reuse existing logic, and introduce no new technical debt. The only remaining work is incorporating accepted non-blocking suggestions (e.g., `strvec` refactoring, documentation precision) in a final revision or follow-up patches.

This is a well-crafted solution to a real user pain point, with thorough test coverage and clear documentation. The series has reached consensus and is ready for integration.

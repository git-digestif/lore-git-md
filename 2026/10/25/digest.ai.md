## Notable threads

### `remote.<name>.refmap` series: design clarifications and test commitments
The `remote.<name>.refmap` series, which introduces a "matching-inspired" fetch mode for shallow repositories, saw further design clarification today. Harald Nordgren confirmed that the fallback to `remote->refmap` in `remote_find_tracking()` is necessary for compatibility with existing Git operations (`@{upstream}`, `--delete-merged`, and `git branch --track`) for refs fetched through the refmap. He explicitly stated that `--limited-fetch` does not require this fallback, resolving an ambiguity raised by D. Ben Knoble. Harald also committed to adding two new tests: one to verify that refs fetched via the refmap are correctly tracked (e.g., for `@{upstream}`), and another to ensure that negative refspecs in `remote.<name>.fetch` continue to exclude refs as expected. These tests will lock down the behavior and address Knoble’s concern about unintended side effects.

The series remains uncontroversial and is queued in `next`. The new tests will provide additional assurance that the refmap-based fetching logic integrates correctly with Git’s existing ref tracking and deletion mechanisms.

### `test-lint` performance optimization: consolidating parsing effort
Tyler Cipriani posted a four-patch series that addresses the performance regression in `test-lint` caused by the `test-grep-lint` check. The series consolidates the parsing effort between `chainlint.pl` and `greplint.pl`, which currently parse the same ~1100 test files independently and serially. By teaching `chainlint.pl` to run greplint checks during its own tokenization pass, the series reduces redundant parsing and leverages parallel execution, cutting total `test-lint` runtime from ~25 seconds to ~1 second for five consecutive runs on a 16-core machine.

The approach is pragmatic: it preserves `greplint.pl` as a standalone tool (for use when `GIT_TEST_CHAIN_LINT=0`) while moving the core parsing and token-checking logic into a shared library (`lib-greplint.pl`). The first patch incorporates Jeff King’s (Peff) earlier optimization, adding an early return in `greplint.pl` to skip files that don’t contain the word "grep", which halves its standalone runtime. The remaining patches restructure the code to allow `chainlint.pl` to invoke greplint checks directly, eliminating duplicate file I/O and parsing overhead.

The series is well-motivated and addresses a real developer workflow bottleneck reported by Junio. It avoids disrupting existing workflows and has no objections or edge cases raised so far. The architectural trade-off (immediate speedup vs. future linting system improvements) is acknowledged but not overstated, and the implementation is clean and incremental.

### `git status` defaults: philosophical debate continues
The debate over whether `git status` should default to comparing against both `@{upstream}` and `@{push}` continued today, with Junio C Hamano refining his critique. Junio now distinguishes between the *nature* of changes in `@{upstream}` versus `@{push}`, arguing that `@{push}` divergence is less critical to monitor by default because it reflects the user’s own work, not external changes. He suggests that this undermines the patch’s justification, which emphasizes practical benefits like reminding users of divergence from the last push and indicating local rebases.

Harald Nordgren countered that the patch benefits less experienced users who may not realize they are missing upstream information when switching to a triangular workflow. He dismissed Junio’s "sad world" framing as idealistic, advocating for pragmatic adaptation to users’ existing mental models. Junio also proposed an alternative: external tools (e.g., GitHub) should promote the configuration (`status.compareBranches = @{upstream},@{push}`) alongside the `-u` flag, preserving internal consistency for triangular workflow users without disrupting existing workflows.

The discussion now centers on whether the benefits for triangular workflow users outweigh the potential noise for others, and whether the change aligns with Git’s long-term design principles. No other contributors have weighed in since Junio’s latest reply, leaving the debate at an impasse.

### Submodule `^/` syntax: design rationale clarified
The RFC thread proposing `^/` syntax for root-relative submodule URLs saw further clarification of the design rationale today. Jacob Keller and Stanislav Aleksandrov discussed the trade-offs between the proposed `^/` syntax and relative traversal (`../../`). Jacob acknowledged that `^/` is preferable to `../../` for GitLab’s arbitrary subgroup nesting, as the required `../` count is unpredictable across forks. The `^/` syntax dynamically resolves to the server root, preserving protocol (HTTPS/SSH) and credentials without manual configuration, which relative traversal cannot guarantee.

The discussion also noted that forking both superproject and submodule would require updating the `^/` URL to point to the new fork, whereas relative URLs (`../`) would continue pointing to the original submodule unless explicitly changed. Jacob sees this as more correct—forks should not silently inherit upstream dependencies—but it may surprise users expecting automatic fork isolation. The thread is converging on the technical design while leaving the syntax choice unresolved.

### `git reflog` feature: usability questions raised
Kristoffer Haugsbakk raised questions about the usability of the proposed `--operations` and `--historical-branch` options for `git reflog`. He noted that per-branch reflogs already show rebase start/finish entries clearly (e.g., `rebase (finish): refs/heads/test-branch`), which addresses some of the original motivation for the series (obscured reset points during rebasing). However, he acknowledged that Patrick Steinhardt’s use case (tracking branch history across renames) remains unaddressed by the current per-branch reflog behavior.

The email shifts the discussion toward whether the remaining gaps justify the series’ complexity, particularly given Phillip Wood’s critique of the heuristic-based `--operations` approach and the unresolved edge cases in `--historical-branch`. The tone is exploratory, leaving the series’ future direction open.

### Test portability fix for `ps/pack-check-bigfile-threshold`
The test portability issue in `ps/pack-check-bigfile-threshold` was fully resolved today. Torsten Bögershausen sent the third iteration of the patch that replaces `mv obj.tmp "$obj"` with `mv -f obj.tmp "$obj"` in `t/t1450-fsck.sh`. The commit message now explicitly states that Git creates loose objects as read-only, that older macOS `mv` (pre-12.3) prompts for confirmation when overwriting them, and that `mv -f` suppresses the prompt. Junio’s earlier editorial refinements and Tuomas Ahola’s typo fixes are incorporated. The patch is procedurally final and requires no further action.

### `git worktree list --branch`: code duplication and usability concerns
Phillip Wood reviewed Jasper Mayone’s `--branch=<branch>` filtering patch for `git worktree list`, identifying code duplication and usability concerns. He noted that the patch duplicates much of the branch-checking logic already present in `branch.c:prepare_checked_out_branches()` and suggested refactoring that function to expose a reusable `branch_find_checkout()` helper. This would require adding a `struct worktree` pointer to the `struct checked_out_branch` structure and converting the existing list to a hashmap indexed by branch name.

Phillip also raised a usability issue: when filtering worktrees, the output no longer indicates which one is the main worktree. Since deleting the main worktree is forbidden, scripts that might call `git worktree remove` on the filtered list could fail unnecessarily. He proposed adding an `is-main-worktree` annotation to the porcelain output so scripts can skip the main worktree preemptively.

The review is constructive and technically precise, focusing on maintainability and scriptability rather than the feature’s core value. It does not block the patch but suggests follow-up work that would improve its integration with the rest of the codebase.

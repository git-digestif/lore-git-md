Subject: [PATCH] sigchain: repair signal handler chain when empty but previously pushed
Series version: standalone patch (no series)
Originating author: Ian Hu
Thread type: bugfix

Core problem or goal
Fix a race condition in Git’s signal-handling (`sigchain`) subsystem where concurrent signal deliveries to different threads can corrupt the internal handler chain, leaving the process stuck in an infinite loop at 100 % CPU. The bug is triggered by `git clone --depth 1` over ssh and requires no special configuration. The discussion has expanded to evaluate three architectural approaches: (1) the current "repair after corruption" patch, (2) a per-signal spinlock to serialize chain updates, and (3) a thread-level fix that blocks signals during thread creation and uses `sigaction()` to prevent reentrancy and concurrent handler execution.

Current status
Under review; patch is in Junio’s `seen` branch as `iy/sigchain-recover-concurrent-pops` (date unknown). The patch remains a minimal, self-contained bugfix, but the review discussion now strongly favors replacing it with a thread-level fix that blocks signals during thread creation and uses `sigaction()` to mask signals during handler execution. Ian Hu has signaled willingness to implement this broader approach, which would likely result in a v2 series incorporating Phillip Wood’s optimizations (block signals once before thread-creation loops, unblock after, and mask at least SIGINT/SIGHUP/SIGTERM/SIGQUIT during handler execution).

Key technical details
- Files touched: `sigchain.c` only (current patch); thread-level fix would also touch thread-creation sites (e.g., `preload_index()`) and signal-masking logic
- New symbol (current patch): `pushed` counter (static int) tracks whether the chain was ever built
- Repair logic (current patch): in `sigchain_pop()`, if the chain is empty but `pushed` is non-zero, reinstate the original signal disposition
- Fast path: unchanged in current patch; repair is inert on all legitimate code paths
- Reproduction scenario: `git clone --depth 1` over ssh, involving `remove_junk_on_signal` and `remove_tempfiles_on_signal`
- Validation: fault-injected A/B testing (300 runs) described in commit message
- Architectural alternatives:
  1. Current patch: repair after corruption (minimal, no serialization)
  2. Per-signal spinlock: serialize chain updates, but still allows concurrent handler execution (POSIX async-signal-safety issues, deadlock risks, Windows portability problems)
  3. Thread-level fix: block signals during thread creation (optimized for loops like `preload_index()`) and use `sigaction()` to mask signals during handler execution, preventing both chain corruption and concurrent handler execution (more invasive, but safer)
- Signal-masking clarification: blocking signals (unlike ignoring them) delays delivery rather than suppressing it, so SIGPIPE deaths remain visible as EPIPE
- Handler masking scope: because `sigchain_push_common()` installs the same handler for multiple signals (SIGINT, SIGHUP, SIGTERM, SIGQUIT), masking should cover at least that set to prevent reentrancy issues in non-reentrant handlers

Open questions and loose ends
- Consensus on architectural approach: thread-level fix is now the leading candidate, pending input from Jeff King (Peff), the original `sigchain` author
- Reviewers may still request a regression test in the Git test suite (`t/`) to exercise the race; the commit message provides a minimal reproducer but no test script
- If the thread-level fix is chosen, the v2 series will need to address blocking signals in new threads (with loop optimizations) and ensuring `sigaction()` is used consistently
- Timeline: Phillip Wood suggests waiting a few days for broader input before Ian invests significant effort in v2

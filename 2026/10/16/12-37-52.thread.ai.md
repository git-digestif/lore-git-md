Subject: [PATCH] sigchain: repair signal handler chain when empty but previously pushed
Series version: standalone patch (no series)
Originating author: Ian Hu
Thread type: bugfix

Core problem or goal
Fix a race condition in Git’s signal-handling (`sigchain`) subsystem where concurrent signal deliveries to different threads can corrupt the internal handler chain, leaving the process stuck in an infinite loop at 100 % CPU. The bug is triggered by `git clone --depth 1` over ssh and requires no special configuration. The discussion has expanded to consider whether the patch’s "repair after corruption" approach is sufficient or if the subsystem needs a broader overhaul to prevent the race entirely by blocking signals during thread creation and using `sigaction()` to prevent reentrancy.

Current status
Under review; patch is in Junio’s `seen` branch as `iy/sigchain-recover-concurrent-pops` (date unknown). No prior versions posted. The patch remains a minimal, self-contained bugfix, but the review discussion now includes architectural alternatives that could lead to a v2 series.

Key technical details
- Files touched: `sigchain.c` only
- New symbol: `pushed` counter (static int) tracks whether the chain was ever built
- Repair logic: in `sigchain_pop()`, if the chain is empty but `pushed` is non-zero, reinstate the original signal disposition
- Fast path: unchanged; repair is inert on all legitimate code paths
- Reproduction scenario: `git clone --depth 1` over ssh, involving `remove_junk_on_signal` and `remove_tempfiles_on_signal`
- Validation: fault-injected A/B testing (300 runs) described in commit message
- Architectural alternatives raised: blocking signals during thread creation to ensure single-threaded handling, and adopting `sigaction()` to prevent signal handler reentrancy

Open questions and loose ends
- Whether to adopt the current "repair after corruption" approach or shift to a "prevent corruption entirely" model by blocking signals in new threads and using `sigaction()`
- Reviewers may still request a regression test in the Git test suite (`t/`) to exercise the race; the commit message provides a minimal reproducer but no test script
- Trade-off between the current minimal fix and a more invasive serialization or blocking approach; feedback from Jeff King (Peff), the original `sigchain` author, is still pending

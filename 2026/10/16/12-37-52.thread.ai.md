Subject: [PATCH] sigchain: repair signal handler chain when empty but previously pushed
Series version: standalone patch (no series)
Originating author: Ian Hu
Thread type: bugfix

Core problem or goal
Fix a race condition in Git’s signal-handling (`sigchain`) subsystem where concurrent signal deliveries to different threads can corrupt the internal handler chain, leaving the process stuck in an infinite loop at 100 % CPU. The bug is triggered by `git clone --depth 1` over ssh and requires no special configuration; the fix restores the pre-chain signal disposition when corruption is detected, allowing clean process termination.

Current status
Under review; no prior versions posted. The patch is a minimal, self-contained bugfix with no external dependencies.

Key technical details
- Files touched: `sigchain.c` only
- New symbol: `pushed` counter (static int) tracks whether the chain was ever built
- Repair logic: in `sigchain_pop()`, if the chain is empty but `pushed` is non-zero, reinstate the original signal disposition
- Fast path: unchanged; repair is inert on all legitimate code paths
- Reproduction scenario: `git clone --depth 1` over ssh, involving `remove_junk_on_signal` and `remove_tempfiles_on_signal`
- Validation: fault-injected A/B testing (300 runs) described in commit message

Open questions and loose ends
- Reviewers may request a regression test in the Git test suite (`t/`) to exercise the race; the commit message provides a minimal reproducer but no test script
- Alternative approach (serializing chain mutations with a spinlock) was considered but not pursued; reviewers may revisit this trade-off

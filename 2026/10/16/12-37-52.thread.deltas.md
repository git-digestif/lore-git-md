# Thread deltas

## 2026/10/16

- [2026/10/16/12-37-52 by Ian Hu via GitGitGadget <gitgitgadget@gmail.com>] Ian Hu submitted a patch to sigchain.c that adds a `pushed` counter incremented in sigchain_push() and modifies the `n < 1` guard in sigchain_pop() to reinstall `s->old[0]` (the disposition from before the chain was built) when the chain is empty but was previously pushed, repairing the corruption caused by concurrent double-pops of the same signal that otherwise leaves the process spinning at 100% CPU with only SIGKILL able to recover it; fault-injected A/B testing showed the unpatched code froze in 121 of 300 runs while the patched code never froze in 300 runs.

## 2026/10/28

- [2026/10/28/13-37-54 by ian4hu <hu2008yinxiang@163.com>] ian4hu pinged the thread: the patch is queued in 'seen' as iy/sigchain-recover-concurrent-pops and marked "Needs review" in the latest "What's cooking"; he asked Peff whether the "repair after the fact" approach is acceptable or whether the chain mutation should be serialized instead, noting he also has a per-signal spinlock version he could send.
- [2026/10/28/14-29-19 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood diagnosed the root cause as the same handler chain being unwound in two threads at once (potentially running the same handler twice), and proposed instead blocking signals when spawning new threads so signals are handled in a single thread, plus switching to sigaction() so a handler is not interrupted by another instance of the same signal.
- [2026/10/28/14-47-35 by ian4hu <hu2008yinxiang@163.com>] ian4hu agreed with both halves of Wood's mail, conceding his patch only repairs the aftermath (a band-aid that leaves the corrupted state reachable and lets two threads run the handler cleanup concurrently); he explained his earlier, unsent spinlock attempt (gitgitgadget PR 2262) was dropped because the lock does not serialize handler bodies, sigprocmask()/pthread_sigmask() are awkward in a multithreaded async-signal context, a thread dying in the critical section trades one hang for another, and the Windows branch could not be CI-tested. He asked whether a serialized chain is a complete fix or whether thread-level prevention is required, gave his own reading that serializing fixes chain state but not handler bodies, and offered to build the thread-level fix (a git_pthread_create() wrapper blocking SIGINT/SIGHUP/SIGTERM/SIGQUIT around pthread_create, leaving SIGPIPE alone, plus a sigaction()-based chain masking all signals while a handler runs), dropping this patch or keeping it as a separate last-resort series.
- [2026/10/28/16-39-37 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood called the thread-level fix probably the safest (while noting it would not cover threads created by external library code) and said he would wait a couple of days for other comments before investing time; he corrected ian4hu's SIGPIPE reasoning, stating blocking a signal only delays delivery while EPIPE results from setting the disposition to SIG_IGN; he added that since sigchain_push_common() installs the same handler for all common signals, at least those should also be blocked during a handler as not all handlers are known to be reentrant; and he said he would be inclined to drop the current patch if signals are handled in a single thread.

## 2026/10/29

- [2026/10/29/11-15-05 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood noted that in places such as preload_index() where threads are created in a loop, it would be more efficient to block signals before the loop and unblock them after, rather than blocking and unblocking around each individual thread creation.
- [2026/10/29/11-15-05 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood clarified that in a multi-threaded process a signal's delivery is only delayed if it is blocked in all threads; if one or more threads have the signal unblocked, it will be delivered to one of those threads.

Subject: [PATCH] http: fix credential stripping regression in libcurl 8.23.0+
Series version: standalone patch (no series)
Originating author: Dan <timelord@gmail.com>
Thread type: bugfix (regression)

Core problem or goal
A security fix in libcurl 8.23.0 (CVE-2026-94266) strips credentials from `CURLINFO_EFFECTIVE_URL`, causing Git’s HTTP transport layer to mis-detect a redirect when pushing to URLs that contain only a token as the username (e.g., `https://<token>@forge.example/owner/repo.git`). The false redirect clears the `http_auth` struct, leading to a 401 error on the subsequent `POST git-receive-pack` request. Fetch and clone are unaffected.

Current status
Under review; no prior versions. The patch targets `http.c:update_url_from_redirect()` by stripping userinfo from both the original and effective URLs before comparison to avoid false positives.

Key technical details
- **Files touched**: `http.c` (`update_url_from_redirect()`, `http_request_reauth()`).
- **New behavior**: URLs are compared without userinfo to prevent false redirect detection.
- **Edge case**: Only affects push (not fetch/clone) and only when the URL contains a token as the username without a password.
- **Dependencies**: libcurl ≥ 8.23.0 or backports (e.g., Ubuntu 24.04).
- **Test coverage**: Reproduction case provided in commit message; no new test file added yet.

Open questions and loose ends
- Whether to strip userinfo from both URLs or only the effective URL.
- How to handle real redirects that legitimately change the origin (e.g., `https://token@old.example` → `https://token@new.example`).
- Need for a regression test in `t/t5551-http-fetch-smart.sh` or similar.

This is the second patch in Justin Tobler’s three-part bugfix series targeting a race condition in Git’s object database (ODB) transaction machinery. The series addresses a scenario where concurrent `git-receive-pack` processes can delete each other’s `.keep` lockfiles, leaving newly written packfiles vulnerable to deletion by housekeeping processes.

This patch refactors `odb_transaction_files_write_pack()` in `object-file.c` to explicitly generate `.keep` lockfiles itself, rather than relying on `git-index-pack` to do so via the `--keep` option. The change is preparatory: the next patch will defer lockfile creation until the transaction commit phase, which is the core of the fix. The refactoring here is clean and self-contained, replacing the `index_pack_lockfile()` helper with a new `write_pack_lock()` function that writes the lockfile directly. The patch also introduces proper error handling for lockfile creation and registration, ensuring failures are propagated rather than silently ignored.

The patch touches only `object-file.c` and makes no behavior changes on its own—it’s purely a refactoring to enable the fix in patch 3. The new `write_pack_lock()` function is straightforward and mirrors the logic previously handled by `git-index-pack`, but with clearer ownership of the lockfile’s lifecycle. The commit message is concise but sufficient, explaining the motivation and the role this patch plays in the series.

This looks like a well-crafted, low-risk refactoring that sets up the real fix. The patch is uncontroversial in isolation, but its value will become clear in the next patch, where the lockfile creation timing is adjusted to close the race window.

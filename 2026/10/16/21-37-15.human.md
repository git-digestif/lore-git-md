This is the third patch in Justin Tobler’s four-patch v2 series fixing a race condition in Git’s object database (ODB) transaction machinery. The series targets a bug where concurrent `git-receive-pack` processes can delete each other’s `.keep` lockfiles, leaving newly written packfiles vulnerable to housekeeping cleanup.

This patch refactors `odb_transaction_files_write_pack()` to explicitly write `.keep` lockfiles itself, rather than relying on `git-index-pack` to do so via the `--keep` option. The change is preparatory: a later patch (4/4) will defer lockfile creation to the transaction commit phase, eliminating the race condition. The refactoring here introduces a new helper, `write_pack_lockfile()`, which constructs the lockfile path, writes the keep message (e.g., `"receive-pack <pid> on <hostname>"`), and registers it as a tempfile. Error messages now include `errno` context and the lockfile path for diagnostic clarity, and error paths are consolidated to avoid resource leaks.

The patch is well-motivated and technically sound. It addresses all of Patrick Steinhardt’s v1 feedback: the helper is renamed from `write_pack_lock()` to `write_pack_lockfile()` for consistency with existing naming conventions, and error handling is improved. The commit message clearly explains the rationale and the preparatory nature of the change. The only loose end is an unaddressed assumption that leading directories for lockfiles exist during quarantine (Patrick requested explicit directory creation or a rationale, but the author declined to move the `safe_create_file_with_leading_directories()` call to the final patch).

This patch is part of the ongoing ODB abstraction effort led by Patrick Steinhardt. It looks ready for final polish and is unlikely to be controversial. The series as a whole is under active review and appears to be converging toward a merge.

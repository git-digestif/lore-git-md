This patch is a **bugfix** targeting the branch creation and tracking logic in Git. It addresses an inconsistency in the behavior of `branch.autoSetupMerge=inherit` when the starting point is a remote-tracking branch (e.g., `origin/main`).

Currently, when `branch.autoSetupMerge=inherit` is set and a user runs `git switch -c new_branch origin/main`, Git creates the local branch but does not set up tracking for the remote branch, instead warning that no remote is configured. This differs from the default (`true`) behavior, which *does* set up tracking in this scenario. The patch makes `inherit` behave like `true` when the starting point is a remote-tracking branch, ensuring consistent tracking setup regardless of the `autoSetupMerge` setting.

The change is small and focused: it modifies `branch.c` to detect when the starting point is not a local branch (i.e., does not begin with `refs/heads/`) and treats it as a direct tracking target, just like the default mode. The patch also updates the documentation in `branch.adoc` and `git-branch.adoc` to clarify this behavior, and adds a test case in `t/t2060-switch.sh` to verify the fix.

The motivation is clear: users expect `inherit` to match the default behavior when the starting point is a remote-tracking branch, and the current implementation creates a surprising inconsistency. The commit message and documentation updates are well-written and explain the change concisely. The test coverage is thorough, covering both the existing `inherit` behavior for local branches and the new behavior for remote-tracking branches.

This patch is part of a larger effort to improve branch tracking configuration, but it stands alone as a self-contained fix. It touches a user-facing feature (`git switch`/`git branch`) and should be uncontroversial, as it aligns behavior with user expectations without introducing new edge cases. The code change is minimal and unlikely to introduce regressions.

This is the third patch in Justin Tobler’s three-part bugfix series targeting a race condition in Git’s object database (ODB) transaction machinery. The patch moves `.keep` lockfile creation from the quarantine phase to the transaction commit phase, ensuring lockfiles are only written after the transaction is guaranteed to succeed. This eliminates a race where concurrent `git-receive-pack` processes could delete each other’s lockfiles, leaving packfiles vulnerable to housekeeping.

Justin’s reply clarifies the patch’s behavior and addresses Patrick Steinhardt’s review feedback. The key clarification is that the patch ensures *all* lockfiles are created before any migration occurs, preventing partial transaction commits if a lockfile collision is detected. This is a stricter and safer approach than the current behavior, which allows migration to proceed even if lockfile creation fails later. Justin plans to reword the commit message to make this clearer.

Patrick’s feedback also prompted two incremental improvements: (1) enhancing error messages in `write_pack_lockfile()` to include `errno` context (e.g., which lockfile caused the failure), and (2) adding a test assertion to verify that no corresponding `.pack` file is migrated when a `.keep` lockfile collision occurs. Both changes are minor but improve robustness and test coverage. The test update directly addresses Patrick’s concern about verifying the absence of migrated packfiles in the concurrent-process scenario.

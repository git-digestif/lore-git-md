This is a **substantive review** of Harald Nordgren’s bugfix patch for `branch.autoSetupMerge=inherit`. Junio C Hamano raises a fundamental question about the intended behavior of the `inherit` mode when the starting point is *not* a branch with existing tracking configuration.

The review points out that the current patch changes the behavior for remote-tracking starting points (e.g., `origin/main`) but does not address what should happen when the starting point is something else (e.g., a tag, a commit hash, or a local branch without tracking). Junio suggests that the documentation and code should explicitly define the fallback behavior: should `inherit` copy tracking if it exists, and otherwise do nothing (current behavior), track the starting point directly (proposed in the patch), or fail outright?

Junio also proposes a more nuanced design: instead of silently changing the behavior of `inherit`, the patch could introduce new modes (`inherit-or-fail`, `inherit-or-direct`) to preserve backward compatibility while offering the new behavior as an opt-in. This would avoid surprising users who currently rely on `inherit` not setting up tracking for non-tracking starting points.

The review cites the original commit (d3115660b4, 2021-12-20) as evidence that the current behavior (doing nothing for non-tracking starting points) was likely intentional, even if undocumented. Junio invites the original author (CC’ed) to clarify the original intent, but his own preference leans toward preserving the current behavior for non-tracking starting points.

- The documentation update in `branch.adoc` is flagged as misleadingly abbreviated ("remote-tracking starting point" should be "remote-tracking branch given as a starting point").

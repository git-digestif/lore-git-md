This is a bugfix series targeting the object database (ODB) transaction machinery. It fixes a race condition where concurrent `git-receive-pack` processes can delete each other’s `.keep` lockfiles, leaving newly written packfiles vulnerable to deletion by housekeeping processes.

The problem stems from how temporary `.keep` lockfiles are registered in the object quarantine *before* being written to the primary ODB. If the transaction exits early (e.g., due to an error), the `atexit` handler still tries to clean up the lockfile at its final location, blindly deleting any file with the same name—even if it belongs to another process. The series migrates lockfile creation to happen *during* the ODB transaction commit, ensuring the file exists before registration.

Patch 1 lifts and exposes index-pack report parsing from `pack-write.c` to make it reusable. Patch 2 refactors `object-file.c` to explicitly write `.keep` lockfiles instead of relying on `git-index-pack`. Patch 3 ties it all together by moving lockfile creation into the transaction commit phase. The changes touch `object-file.c`, `pack-write.c`, `pack.h`, and add test coverage in `t/t5547-push-quarantine.sh`.

The series is well-motivated by the linked bug report and addresses a real correctness issue in the ODB transaction logic. The preparatory refactoring in patches 1–2 is clean and necessary for the fix. The test updates verify the new behavior, though the commit message doesn’t detail whether edge cases (e.g., permission errors during lockfile creation) are handled.

Key technical details for follow-up discussion:

- **New functions**: `parse_index_pack_report()` (exposed in `pack.h`), refactored lockfile logic in `odb_transaction_files_write_pack()`.
- **Behavior change**: `.keep` lockfiles are now created during transaction commit, not quarantine registration.
- **Test coverage**: Extends `t5547` to check lockfile ownership under concurrent `git-receive-pack` operations.

The fix looks technically sound, but the thread may revisit whether the `atexit` cleanup should be more defensive (e.g., checking file ownership) or if the transaction API needs broader hardening.

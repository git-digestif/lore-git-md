This is the second patch in Justin Tobler’s four-patch v2 series fixing a race condition in Git’s ODB transaction machinery. It extracts and exposes the logic that parses `git-index-pack`’s stdout report into a new public helper, `read_index_pack_report()`, in preparation for deferring `.keep` lockfile creation to the transaction commit phase (the core fix in patch 4).

The patch lifts the parsing logic from `index_pack_lockfile()` into a standalone function that reads the `"pack\t<name>\n"` or `"keep\t<name>\n"` line, appends the packfile name to a caller-provided `strbuf`, and sets an `is_keep` flag if a `.keep` file was created. The original `index_pack_lockfile()` is rewritten to call the new helper, reducing code duplication and making the parsing reusable. The helper is now exposed in `pack.h` and is hash-algorithm-agnostic (the SHA-1 assumption was removed in patch 1).

Key changes:
- **New symbol**: `read_index_pack_report()` in `pack.h`, which parses `git-index-pack` output and is now a public API.
- **Behavior**: The helper unconditionally uses the `is_keep` pointer (addressing Patrick Steinhardt’s v1 feedback) and consolidates error paths.
- **Files touched**: `pack-write.c` (refactored) and `pack.h` (new declaration).
- **Test coverage**: No new tests in this patch; the existing test in `t/t5547-push-quarantine.sh` (extended in patch 4) verifies the end-to-end behavior.

The patch is a clean refactoring with no functional changes. It directly enables patch 4’s deferral of lockfile creation by providing a reusable way to record packfile names during quarantine. All feedback from Patrick’s v1 review has been addressed, and the code looks technically sound. The only open question is the unaddressed assumption about leading directories (raised in patch 3), but this does not affect this patch’s correctness.

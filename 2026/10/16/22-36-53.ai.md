This is a **bugfix** targeting the HTTP transport layer, specifically a regression introduced by a security fix in libcurl 8.23.0 (CVE-2026-94266) that strips credentials from `CURLINFO_EFFECTIVE_URL`. The issue breaks `git push` over smart HTTP when the remote URL contains only a token as the username (e.g., `https://<token>@forge.example/owner/repo.git`), a common pattern in CI tools like Renovate for Gitea/Forgejo. Fetch and clone remain unaffected.

The bug manifests as a false redirect detection in `http.c:update_url_from_redirect()`. When libcurl returns an effective URL without userinfo (due to the CVE fix), Git treats the response as a redirect, rewrites the base URL to exclude credentials, and clears the `http_auth` struct. Since the original URL had no password, the subsequent `POST git-receive-pack` request lacks authentication, resulting in a 401 error and a fatal "could not read Username" message. The commit message provides a clear reproduction case, server logs, and `GIT_TRACE_CURL` output demonstrating the issue.

The author, Dan, identifies the root cause as a mismatch in URL comparison logic in `update_url_from_redirect()` and suggests a fix: strip userinfo from the URLs before comparison to avoid false positives. They note that workarounds exist (e.g., using `user:token@` syntax or credential helpers), but the underlying issue requires a code change. The analysis is thorough, linking the problem to specific libcurl versions (8.23.0+ and Ubuntu 24.04 backports) and Git 2.55.0.

Subject: [PATCH] branch: fix branch.autoSetupMerge=inherit with remote-tracking starting point
Series version: standalone patch (no series)
Originating author: Harald Nordgren
Thread type: bugfix patch → design discussion

Core problem or goal
Fix an inconsistency in `branch.autoSetupMerge=inherit` where it fails to set up tracking when the starting point is a remote-tracking branch (e.g., `origin/main`), unlike the default (`true`) behavior which does. The discussion has expanded to explore alternative designs for `inherit` that better align with user workflows, including (1) the original patch’s minimal fix for remote-tracking branches only, (2) Junio C Hamano’s proposed modes (`inherit-or-fail`, `inherit-or-direct`) for non-tracking starting points, and (3) Harald Nordgren’s newer proposal to prioritize inheritance from the *current* branch’s tracking configuration (rather than the starting point’s) when creating a new branch. The goal is to resolve the ambiguity in `inherit`’s behavior while accommodating diverse user expectations and avoiding ad-hoc CLI expansion.

Current status
Under review; no prior versions. The patch remains self-contained but contested. Junio’s latest reply endorses Ben Knoble’s framing of his mode-based design (`inherit-or-fail`, `inherit-or-direct`) as the more principled and forward-compatible path, reinforcing the preference for structured solutions over minimal fixes. The discussion is now less about whether to expand the scope of `inherit` (to handle non-tracking starting points) and more about *how* to do so in a maintainable way. Harald’s current-branch inheritance proposal remains unimplemented and untested, while Junio’s modes are also not yet implemented. No consensus yet; the three competing approaches remain in play, with Junio’s design now slightly favored by both Junio and Ben Knoble. Phillip Wood’s user-centric feedback continues to highlight broader workflow concerns, but no alternative design has been proposed.

Key technical details
- Files touched: `branch.c`, `Documentation/git-branch.adoc`, `Documentation/branch.adoc`, `t/t2060-switch.sh` (original patch)
- Subsystem: branch creation and tracking logic
- Original patch behavior: `branch.autoSetupMerge=inherit` sets up tracking for remote-tracking starting points (e.g., `origin/main`), matching the default (`true`) behavior
- Current behavior: `inherit` does not set up tracking for remote-tracking starting points (issues a warning) or non-tracking starting points (tags, commit hashes, local branches without tracking)
- Harald’s new proposal: prioritize inheritance from the *current* branch’s tracking configuration (e.g., if the current branch tracks `origin/master`, the new branch inherits that tracking). Fall back to tracking the starting point directly only if the current branch has no tracking. No implementation or test coverage yet.
- Junio’s proposed modes (not implemented): `inherit-or-fail` (abort if starting point has no tracking) and `inherit-or-direct` (track starting point directly if no tracking exists)
- Original commit: d3115660b4 (2021-12-20) introduced `inherit`; its behavior for non-tracking starting points was likely intentional but undocumented

Open questions and loose ends
1. Which of the three approaches (minimal fix, Junio’s modes, Harald’s current-branch inheritance) best balances backward compatibility, user expectations, and design clarity?
2. Is Harald’s current-branch inheritance proposal technically feasible and intuitive for users? Does it risk overcomplicating the mental model, particularly with the fallback behavior (tracking the starting point directly if the current branch has no tracking)?
3. Should the fallback behavior in Harald’s proposal be retained, or would it introduce inconsistency? Would users find it confusing if the new branch’s tracking depends on the *current* branch’s state rather than the starting point’s?
4. Is the original behavior of `inherit` (doing nothing for non-tracking starting points) intentional, or was it an oversight? The original author’s input is still pending.
5. Documentation: `branch.adoc` remains misleadingly abbreviated; needs clarification for all starting point types, regardless of which approach is adopted.
6. Should Junio’s proposed modes (`inherit-or-fail`, `inherit-or-direct`) be pursued as a separate effort, or are they the cleaner path forward, as Ben Knoble and Junio suggest? Ben’s and Junio’s latest replies reinforce that users expect `origin` to be tracked by default, which aligns with `inherit-or-direct`.
7. Phillip Wood’s user scenarios suggest that the current behavior (doing nothing for non-tracking starting points) may be preferable for some workflows. Does this warrant broader rethinking of the tracking setup mechanism, or should the focus remain on `inherit`’s edge cases?
8. Ben Knoble’s workflow (`git switch -c topic origin` followed by manual `git branch -u` adjustments) highlights a usability gap: the current system’s defaults often misalign with user intent. Does this gap justify expanding the scope of `inherit` beyond its original design, or should it be addressed through separate tooling (e.g., a new config mode or CLI flag)?

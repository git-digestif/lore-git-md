This is a v2 bugfix patch targeting the cache-tree subsystem, addressing a crash in `git rebase` (and related commands) when another process holds the index lock during an in-process commit. The patch is now ready for final review after incorporating feedback from Patrick Steinhardt.

The core issue remains the same: when a background process (e.g., `git status` or Magit) holds `.git/index.lock`, `write_index_as_tree()`—called during `git rebase --continue`—dies due to `LOCK_DIE_ON_ERROR`, leaving the rebase in a half-picked state. The fix replaces the fatal lock attempt with a non-blocking one, allowing the command to proceed while skipping the optional cache-tree write-back if the lock is held. The regression was introduced in 356ee4659b (2017-11-24), which moved commit creation in-process.

Key changes in v2:
- The commit message now follows Git conventions by describing the symptom first, then the cause, and finally the solution. It also clarifies the two distinct roles of `write_index_as_tree()` (tree computation vs. optional index write-back).
- The lock-check condition was tweaked from `0 <= fd` to `fd >= 0` for stylistic consistency, though this was not a blocker.
- The patch retains its minimal, targeted approach: the lock acquisition is made non-fatal, and the write-back step is guarded by the file descriptor check.

The test coverage in `t/t0090-cache-tree.sh` verifies that `git write-tree` succeeds while `.git/index.lock` exists, ensuring the fix works as intended. Patrick Steinhardt’s substantive review in v1 endorsed the technical direction and praised the test coverage, leaving only the commit message reordering as a requested change.

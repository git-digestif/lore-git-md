This is a feature patch, now in its seventh iteration, adding revision-based filtering to the `git repo structure` command. The patch is effectively ready for merging to `next`—it addresses all prior feedback, including a final editorial nit in the commit message, and has Patrick Steinhardt’s sign-off confirming it is procedurally clean.

The feature allows users to analyze specific subsets of the repository’s object graph by specifying revisions (commits, refs, or ranges) to include or exclude. For example, `git repo structure --branches --not --tags` will report statistics only for objects reachable from branches but not from tags. This improves diagnostic capabilities for large repositories by enabling targeted analysis. The implementation uses Git’s standard `setup_revisions()` machinery, replacing an earlier enum-based flag system with a design consistent with Git’s revision-parsing idioms. This avoids the transitive dependency omission issues of earlier versions and aligns with established patterns in the codebase.

The patch touches three files: `builtin/repo.c` (core implementation), `Documentation/git-repo.adoc` (user-facing documentation), and `t/t1901-repo-structure.sh` (test coverage). The test suite has grown to 197 lines, validating edge cases like overlapping includes/excludes, output formats (table/lines/nul), and empty repository handling. The implementation retains a known inefficiency—a second ref-walk in `count_references()` due to `setup_revisions()`’s lack of a custom ref-walk callback—but this is considered tolerable for a diagnostic tool.

All substantive technical feedback from prior rounds has been addressed. The author’s rationale for retaining the current revision-parsing defaults (avoiding breakage in empty repositories) remains unchanged, and no response to Patrick Steinhardt’s proposal to pass `NULL` to `setup_revisions()` is provided. However, this is no longer treated as a blocker. The patch is well-motivated, uncontroversial, and procedurally sound, making it a clear candidate for integration. Reviewers may still discuss minor trade-offs, but these are not expected to delay merging.

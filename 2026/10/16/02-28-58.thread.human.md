This thread fixes a race condition in Git’s object database (ODB) transaction machinery where concurrent `git-receive-pack` processes could delete each other’s `.keep` lockfiles, leaving newly written packfiles vulnerable to deletion. The issue was caused by temporary `.keep` lockfiles being registered in the object quarantine before being written to the primary ODB; if the transaction failed early, the cleanup handler would still delete any file with the same name, even if it belonged to another process. Justin Tobler’s four-patch series (v3) resolves this by deferring lockfile creation to the transaction commit phase, ensuring they are only written after the transaction is guaranteed to succeed.

The series has received explicit approval from Patrick Steinhardt, who reviewed all four patches and called the fix technically sound and well-structured. The v3 updates addressed his final stylistic feedback, including minor error-handling tweaks and naming consistency. The test in `t/t5547-push-quarantine.sh` now verifies that no `.keep` file exists in the quarantine directory during the pre-receive phase and that a manually created `.keep` file (simulating a concurrent process) is not deleted by the transaction cleanup. The only lingering loose end—the assumption that leading directories for lockfiles exist during quarantine—was flagged by Patrick but not addressed, though his silence in the final review suggests it is not a blocker.

The patches touch `object-file.c`, `pack-write.c`, `pack.h`, and the test suite, introducing new helpers like `write_pack_lockfiles()` and `read_index_pack_report()` to batch-create lockfiles during commit and parse `git-index-pack` output. The series is part of the ongoing ODB abstraction effort and is now ready for integration. No further changes are expected.

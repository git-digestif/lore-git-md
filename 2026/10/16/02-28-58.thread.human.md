This thread is a bugfix series from Justin Tobler that fixes a race condition in Git’s object database (ODB) transaction machinery, where concurrent `git-receive-pack` processes could delete each other’s `.keep` lockfiles, leaving newly written packfiles vulnerable to deletion. The root issue was that temporary `.keep` lockfiles were registered in the object quarantine before being written to the primary ODB, meaning that if the transaction exited early (e.g., due to an error), the `atexit` handler would still try to clean up the lockfile at its final location—even if it belonged to another process.

The fix, now at version 3, moves lockfile creation to the transaction commit phase, ensuring lockfiles are only written after the transaction is guaranteed to succeed. The series has received explicit approval from Patrick Steinhardt, who reviewed all four patches and called the series technically sound and well-structured. The v3 changes incorporated the last of Patrick’s feedback, including minor stylistic tweaks like explicitly assigning the error return value in `write_pack_lockfile()` and removing an extraneous newline. The test in `t/t5547-push-quarantine.sh` now verifies that no corresponding `.pack` file exists alongside the `.keep` file in the concurrent-process scenario, addressing Patrick’s request for completeness.

The only loose end is an unaddressed assumption that leading directories for lockfiles exist during quarantine, which Patrick flagged but did not revisit in his final review. This is not considered a blocker, and the series is otherwise ready for merging. Key changes include refactoring `read_index_pack_report()` into a public API, renaming `write_pack_lock()` to `write_pack_lockfile()` for consistency, and introducing `write_pack_lockfiles()` to batch-create lockfiles during transaction commit. The fix is purely behavioral, with no on-disk format changes.

This thread is about a four-patch bugfix series from Justin Tobler that fixes a race condition in Git’s object database (ODB) transaction machinery. The issue occurs when concurrent `git-receive-pack` processes delete each other’s `.keep` lockfiles, leaving newly written packfiles vulnerable to deletion by housekeeping processes. The root cause was that temporary `.keep` lockfiles were registered in the object quarantine *before* being written to the primary ODB, meaning that if the transaction exited early (e.g., due to an error), the `atexit` handler would still try to clean up the lockfile at its final location—even if it belonged to another process.

The fix moves lockfile creation to the transaction commit phase, ensuring lockfiles are only written after the transaction is guaranteed to succeed. This eliminates the race condition by deferring lockfile creation until the transaction is committed. The series has received explicit approval from Patrick Steinhardt, who reviewed all four patches and called the series technically sound and well-structured. The v3 iteration incorporated all of Patrick’s feedback, including minor stylistic tweaks like explicitly assigning the error return value in `write_pack_lockfile()` and removing an extraneous newline. The test in `t/t5547-push-quarantine.sh` now verifies that no `.keep` file is deleted by the transaction cleanup when simulating a concurrent process, and that no corresponding `.pack` file exists alongside it.

The only remaining loose end is whether leading directories for lockfiles are guaranteed to exist during quarantine. Patrick Steinhardt flagged this as a potential issue but did not revisit it in his final review, and the author considers the assumption safe. The series is otherwise complete and ready for integration. Key files touched include `object-file.c`, `pack-write.c`, and the test script, with new helpers like `write_pack_lockfiles()` introduced to batch-create lockfiles during commit. The fix is purely behavioral and does not change the on-disk format.

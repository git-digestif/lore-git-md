This is a bugfix patch for the cache-tree subsystem, now updated in response to review feedback from Patrick Steinhardt. The patch prevents `git rebase` (and related commands) from crashing when another process holds the index lock during an in-process commit, a regression introduced in 2017 that leaves rebases in a half-picked state requiring manual recovery.

Patrick’s review is substantive but constructive, focusing on commit message clarity and minor code readability. He suggests reordering the commit message to lead with the problem (the crash and its consequences) before explaining the cause and solution, which would make the motivation clearer to readers. He also notes a preference for `fd > 0` over `0 <= fd` in the conditional check, though he acknowledges this is subjective. The core fix—replacing `LOCK_DIE_ON_ERROR` with a gentle lock attempt—remains unchanged, as Patrick agrees it’s the right approach for this optional write-back step.

The patch is minimal, well-tested, and addresses a real-world annoyance (e.g., when `git status` or Magit holds the lock during a rebase). The new test in `t/t0090-cache-tree.sh` verifies that `git write-tree` succeeds even when `.git/index.lock` exists, ensuring the fix works as intended. No open questions or loose ends remain; this looks like a clean, targeted fix ready for merging once the commit message is tweaked.

This is a **substantive technical review** from Junio C Hamano on Miklos Vajna’s patch to fix the `git log --follow` performance regression. Junio identifies a potential correctness issue in the patch’s optimization logic, specifically its handling of merge commits where a file is renamed in one branch but kept under its original name in another.

The review centers on a concrete scenario: two branches (A and B) diverge from a common ancestor containing file F. Branch A modifies F in place; branch B renames F to G and later modifies G. When A merges B but keeps F (deleting G), the patch’s logic would classify the path as "unchanged" (`FOLLOW_PATH_SAME`) in the merge commit and skip rename detection for branch B’s history. Junio questions whether this shortcut breaks `--follow`’s ability to trace the file’s history through branch B, particularly when history simplification is disabled.

This critique directly challenges the patch’s core optimization—avoiding rename detection when a path is unchanged in any parent—and suggests the current logic may be too aggressive. The scenario highlights a tension between performance and correctness: the patch’s shortcuts restore speed but may miss valid rename chains in complex merges. Junio’s question implies the patch might need to refine its classification logic (`enum follow_path_change`) or reconsider where the optimization is applied.

No alternative implementation is proposed here, but the review reinforces Junio’s earlier architectural concern about layering optimizations on top of the diff machinery rather than integrating them into `log_tree_diff_flush()`. The thread remains under active design discussion, with correctness now a key open question alongside performance.

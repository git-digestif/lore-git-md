This thread is about a race condition in Git’s signal-handling subsystem (`sigchain`) that can cause infinite CPU loops during operations like `git clone --depth 1` over SSH. The author, Ian Hu, posted a minimal fix that repairs the corrupted signal handler chain after corruption occurs, and Junio queued it in his `seen` branch for review.

The discussion has since expanded into a design debate. Phillip Wood raised concerns that the current patch doesn’t address the deeper risk of concurrent handler execution (e.g., double-free or use-after-free), and proposed either serializing chain updates with a spinlock or adopting a more invasive thread-level fix—blocking signals during thread creation and using `sigaction()` to prevent reentrancy. Ian responded by outlining the trade-offs: the spinlock approach still allows concurrent handler execution and introduces async-signal-safety and portability issues, while the thread-level fix would resolve both problems but requires broader changes. He’s seeking consensus on whether to proceed with the spinlock or the more comprehensive solution, and whether to keep the current patch as a fallback.

The patch remains under review, with no new version posted yet. Key open questions include whether the current fix is sufficient or if a broader overhaul is needed, and whether a regression test will be added to the Git test suite. Feedback from Jeff King, the original `sigchain` author, is still pending. The next step will likely be a v2 series, depending on Phillip’s response.

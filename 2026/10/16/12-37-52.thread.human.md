This thread is about a bugfix for Git’s signal-handling (`sigchain`) subsystem, posted by Ian Hu. The patch addresses a race condition where concurrent signal deliveries to different threads can corrupt the internal handler chain, causing the process to spin at 100% CPU. The issue is easily triggered by `git clone --depth 1` over ssh and requires no special configuration. The fix is minimal: it restores the original signal disposition when corruption is detected, allowing the process to terminate cleanly.

The patch has been queued in Junio’s `seen` branch as `iy/sigchain-recover-concurrent-pops` and is marked "Needs review" in the latest "What’s cooking" report. Ian is gently pinging the list for feedback, particularly from Jeff King (Peff), the original author of the `sigchain` code. The key technical question is whether the current "repair after the fact" approach is sufficient or if a more proactive solution—using a per-signal spinlock to serialize chain mutations—would be preferable. Ian has a spinlock-based version ready if reviewers favor that direction. No substantive reviews have been posted yet, so the patch remains under active discussion.

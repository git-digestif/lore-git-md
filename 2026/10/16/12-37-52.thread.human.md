This thread is about a race condition in Git’s signal-handling subsystem (`sigchain`) that can cause infinite CPU loops during operations like `git clone --depth 1` over SSH. The issue arises when concurrent signal deliveries to different threads corrupt the internal handler chain. Ian Hu proposed a minimal fix that repairs the chain after corruption, which Junio queued in `seen` for review.

The discussion has since shifted toward a broader architectural solution. Phillip Wood, a key reviewer, has endorsed a thread-level fix: blocking signals during thread creation and using `sigaction()` to prevent reentrant or concurrent handler execution. This approach would replace the current patch entirely, addressing both chain corruption and the risk of double-free or use-after-free from simultaneous handler invocations. Ian Hu has signaled willingness to implement this if consensus emerges, though no v2 series has been posted yet.

The patch touches only `sigchain.c` and introduces a `pushed` counter to detect corruption. While the current fix is minimal and inert on legitimate code paths, reviewers are leaning toward the more invasive but safer thread-level solution. Jeff King (Peff), the original `sigchain` author, has not yet weighed in, and there’s still an open question about adding a regression test to the Git test suite. The next steps hinge on whether other reviewers (especially Peff) object to the thread-level approach or if broader consensus forms around it.

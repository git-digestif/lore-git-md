This thread is about fixing an inconsistency in Git’s `branch.autoSetupMerge=inherit` configuration, where it fails to set up tracking when creating a branch from a remote-tracking starting point (e.g., `origin/main`), unlike the default (`true`) behavior. The discussion has evolved into a broader debate over how `inherit` should handle edge cases, particularly non-tracking starting points like tags or commit hashes.

Harald Nordgren initially proposed a minimal fix to address only remote-tracking branches, but the conversation has since expanded to three competing approaches: (1) Harald’s original patch, (2) Junio C Hamano’s proposed modes (`inherit-or-fail` and `inherit-or-direct`) to handle non-tracking starting points in a structured way, and (3) Harald’s newer idea to prioritize inheritance from the *current* branch’s tracking configuration rather than the starting point’s. Junio’s latest reply reinforces his preference for his mode-based design, calling it a more principled alternative to ad-hoc fixes, while Ben Knoble’s input highlights that users often expect `origin` to be tracked by default, aligning with Junio’s `inherit-or-direct` mode.

The thread remains under review, with no consensus yet on which approach best balances backward compatibility, user expectations, and design clarity. Key participants include Harald (the author), Junio (the maintainer), Phillip Wood (who raised user-centric workflow concerns), and Ben Knoble (who favors Junio’s structured solution). The original author of the `inherit` feature has not yet weighed in to clarify whether the current behavior for non-tracking starting points was intentional. Open questions include whether Harald’s current-branch inheritance proposal is technically feasible and intuitive, and whether the project should pursue Junio’s modes as a separate effort or as the primary path forward. The outcome may influence future tracking-related patches and broader discussions about branch creation workflows.

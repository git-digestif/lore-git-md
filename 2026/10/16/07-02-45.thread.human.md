This thread began with Harald Nordgren’s patch to fix an inconsistency in `branch.autoSetupMerge=inherit`: when creating a branch from a remote-tracking starting point (like `origin/main`), the `inherit` setting failed to set up tracking, unlike the default (`true`) behavior. What started as a narrow bugfix has grown into a design discussion about how `inherit` should behave more broadly.

The core disagreement now centers on three competing approaches. Harald initially proposed a minimal fix for remote-tracking branches only, but later suggested a conceptual shift: prioritize inheritance from the *current* branch’s tracking configuration (e.g., if the current branch tracks `origin/master`, the new branch inherits that tracking). Junio C Hamano, the maintainer, has questioned the design for non-tracking starting points (like tags or commit hashes), arguing the current behavior was intentional and suggesting new modes (`inherit-or-fail` or `inherit-or-direct`) as opt-in alternatives. Phillip Wood and Ben Knoble have both highlighted user workflows where the current behavior—or even Harald’s original patch—falls short, with Ben noting that users often manually adjust tracking (`git branch -u`) when the defaults don’t match their intent.

No consensus has emerged yet. Harald’s current-branch inheritance idea is the newest proposal but remains unimplemented and untested. Junio’s mode-based design is seen by Ben Knoble as the more principled path, though it would require a larger scope. The original author of `inherit` has not yet weighed in, leaving the intent behind the current behavior unclear. The thread is now split between these approaches, with no clear favorite and open questions about backward compatibility, user expectations, and whether the solution should be minimal or more ambitious.

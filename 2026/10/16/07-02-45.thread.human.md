This thread is about a patch from Harald Nordgren that fixes an inconsistency in Git’s `branch.autoSetupMerge=inherit` behavior: when creating a branch from a remote-tracking branch (like `origin/main`), the `inherit` setting currently fails to set up tracking, unlike the default (`true`) behavior. The patch aims to align `inherit` with `true` for remote-tracking starting points, but the discussion has expanded into a broader debate about the intended behavior of `inherit` for *all* starting points—tags, commit hashes, or local branches without tracking.

The patch is under review, with no prior versions, and the discussion is at an impasse. Junio C Hamano, the maintainer, has raised design concerns, arguing that the current behavior for non-tracking starting points was likely intentional and that the patch’s scope is too narrow. He suggests new modes like `inherit-or-fail` or `inherit-or-direct` as opt-in alternatives, while the author insists the patch should focus solely on remote-tracking branches. Phillip Wood’s recent review adds a pragmatic user perspective, describing workflows where the current behavior (doing nothing for non-tracking starting points) is actually more intuitive than the patch’s proposed change. His input shifts the discussion toward usability, questioning what users expect `inherit` to do in ambiguous cases.

Key participants include the author (advocating for a minimal fix), Junio (pushing for broader design clarity), and the original `inherit` author (still silent). The patch touches `branch.c` and related documentation, with test coverage added for remote-tracking starting points. Open questions remain: whether the patch is acceptable as-is, whether the original behavior was intentional, and whether Junio’s proposed modes are worth pursuing. The outcome may influence future tracking-related patches, but for now, the thread is stuck awaiting further input or a decision from Junio.

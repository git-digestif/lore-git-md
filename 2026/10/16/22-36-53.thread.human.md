This thread is about a **bugfix for a regression in Git's HTTP transport layer** introduced by a security fix in libcurl 8.23.0 (CVE-2026-94266). The issue breaks `git push` over smart HTTP when the remote URL contains only a token as the username (e.g., `https://<token>@forge.example/owner/repo.git`), a pattern commonly used by CI tools like Renovate for Gitea/Forgejo. Fetch and clone remain unaffected.

The root cause is a false redirect detection in `http.c:update_url_from_redirect()`: libcurl’s security fix strips credentials from `CURLINFO_EFFECTIVE_URL`, causing Git to treat the response as a redirect, rewrite the base URL without credentials, and clear authentication. This leads to a 401 error during `POST git-receive-pack`. The author, Dan, proposes a fix by stripping userinfo from URLs before comparison to avoid false positives. The patch is well-documented, including reproduction steps, server logs, and `GIT_TRACE_CURL` output, and targets `http.c` (specifically `update_url_from_redirect()` and `http_request_reauth()`).

The thread is likely to focus on the robustness of the proposed fix, particularly how to handle real redirects that might legitimately change the origin. Workarounds exist (e.g., `user:token@` syntax or credential helpers), but the underlying issue requires a code change. No reviews or maintainer decisions have been posted yet.

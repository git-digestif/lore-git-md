This is a bugfix patch targeting the cache-tree subsystem. The author, Szymon Wilczek, resubmits a well-crafted fix for a crash in `git rebase` (and related commands) when another process—like `git status` or Magit—holds the index lock during an in-process commit. The crash leaves the rebase in a half-picked state, requiring manual recovery.

The patch replaces the `LOCK_DIE_ON_ERROR` flag in `write_index_as_tree()` with a non-blocking lock attempt. If the lock is held, the function skips writing the updated cache-tree back to the index but still computes and returns the tree object, allowing the operation to proceed. This matches the behavior of other callers that only refresh the index. The change affects `git rebase --continue`, `git write-tree`, and `git am`, all of which can now handle a locked index gracefully.

The commit message has been reordered in this v2 to follow Git conventions: symptom first, then cause, and finally the fix. It also clarifies the two distinct roles of `write_index_as_tree()`—computing the tree object (which must succeed) and updating the cache-tree extension (which is optional). The patch includes a new test in `t/t0090-cache-tree.sh` that verifies `git write-tree` succeeds while `.git/index.lock` exists, ensuring the fix is robust.

Patrick Steinhardt provided a **substantive review** of the initial version, endorsing the technical approach and praising the test coverage. His only request was the commit message reordering, which has been addressed. A minor stylistic preference (`fd >= 0` instead of `0 <= fd`) was noted but not required. The patch is minimal, well-motivated, and addresses a real-world annoyance with clear reproduction steps. It looks ready for integration.

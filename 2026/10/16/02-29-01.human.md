This is the final patch in Justin Tobler’s three-part bugfix series targeting a race condition in Git’s object database (ODB) transaction machinery. The series fixes a scenario where concurrent `git-receive-pack` processes can delete each other’s `.keep` lockfiles, leaving newly written packfiles vulnerable to deletion by housekeeping processes.

Patch 3/3 implements the core fix by moving `.keep` lockfile creation from the quarantine phase (where it was vulnerable to races) to the transaction commit phase. This ensures the lockfile is properly acquired *before* objects are migrated to the primary ODB, preventing premature deletion by other processes. The change touches `object-file.c` and extends the test suite (`t/t5547-push-quarantine.sh`) to verify lockfile ownership under concurrent operations.

The patch is well-motivated and addresses a real correctness issue in the ODB transaction logic. The preparatory refactoring in patches 1–2 (already summarized) makes this change straightforward, and the test updates provide clear coverage for the new behavior. The commit message could be clearer about edge-case handling (e.g., permission errors during lockfile creation), but the fix itself looks technically sound.

This is a standalone correctness fix within the broader ODB abstraction effort led by Patrick Steinhardt. The series is under review, and this patch is the only one still unreviewed. Given the race condition’s potential for data loss, it’s likely to attract attention from reviewers familiar with the ODB and packfile subsystems. If you work with large repositories or high-concurrency Git operations, this patch is worth following.

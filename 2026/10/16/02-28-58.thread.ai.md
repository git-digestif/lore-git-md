Thread identity
Subject: [PATCH 0/3] odb: fix race condition in .keep lockfile cleanup
Series version: v4 (four patches)
Originating author: Justin Tobler
Thread type: bugfix patch series

Core problem or goal
Fix a race condition in Git’s object database (ODB) transaction machinery where concurrent `git-receive-pack` processes can delete each other’s `.keep` lockfiles, leaving newly written packfiles vulnerable to deletion by housekeeping processes. The root cause is that temporary `.keep` lockfiles were registered in the object quarantine *before* being written to the primary ODB; if the transaction exited early (e.g., due to an error), the `atexit` handler still tried to clean up the lockfile at its final location, blindly deleting any file with the same name—even if it belonged to another process. The fix moves lockfile creation to the transaction commit phase, ensuring lockfiles are only written after the transaction is guaranteed to succeed.

Current status
**Ready for merging.** Junio C Hamano has signaled readiness to merge the series once the v4 reroll was submitted, and Patrick Steinhardt has **explicitly approved all four patches**, calling the series technically sound and well-structured. All feedback has been addressed, including the final stylistic tweak Patrick requested: explicitly leaving the `ret` variable in `write_pack_lockfile()` uninitialized at declaration and assigning it on all exit paths to enable compiler warnings. Key technical details
- **Files touched**: `object-file.c`, `pack-write.c`, `pack.h`, `t/t5547-push-quarantine.sh`.
- **New/renamed symbols**:
  - `read_index_pack_report()` (exposed in `pack.h`): parses `git-index-pack` output to extract the packfile name and `.keep` status. The helper was refactored from internal logic in `index_pack_lockfile()` and is now a public API. The implementation is hash-algorithm-agnostic (using `repo->hash_algo->hexsz` to size the read buffer) and unconditionally uses the `is_keep` pointer (patch 2). The comment in `pack-write.c` was updated in patch 1 to reflect this agnosticism by replacing the hardcoded SHA-1 reference (`%40s`) with a generic `<name>` and referencing `hexsz`.
  - `parse_index_pack_report()` (renamed from internal logic in `index_pack_lockfile()`; now a public helper).
  - `write_pack_lockfile()` (renamed from `write_pack_lock()` in patch 3; new helper in `object-file.c`): constructs the lockfile path, writes the keep message (`"receive-pack <pid> on <hostname>"`), and registers it as a tempfile. The rename addresses Patrick’s request for consistency with existing naming conventions. Error messages now include `errno` context and the lockfile path for diagnostic clarity. The function now explicitly initializes its return value on all exit paths to enable compiler warnings. Karthik Nayak suggests replacing `unlink()` with `unlink_or_warn()` in the error path to avoid silently failing if the unlink operation itself fails; this is a minor nit and not a blocker.
  - `write_pack_lockfiles()` (new helper in `object-file.c`): batch-creates lockfiles during transaction commit. Packfile names are stored in a `strvec` (`pack_names` field added to `struct odb_transaction_files`) during quarantine and written as lockfiles only if the transaction commits successfully.
- **Behavior change**: `.keep` lockfiles are now created *only* during transaction commit (`odb_transaction_files_commit()`), not during quarantine (`odb_transaction_files_write_pack()`). This eliminates the race condition by ensuring lockfiles are never left in an inconsistent state.
- **On-disk format**: No changes; the fix is purely behavioral.
- **Assumptions**: Patch 1 (refactoring) assumes `git-index-pack` output follows the `"pack\t<name>\n"` or `"keep\t<name>\n"` format, with `<name>` being a hexadecimal hash of length `hexsz`; this is now explicitly noted in the commit message and the updated comment. Patch 3 assumes leading directories for lockfiles exist during quarantine, which Patrick Steinhardt flags as potentially unsafe (e.g., if the ODB directory structure is not fully populated). The author justifies this assumption as safe but has not provided explicit directory creation or a detailed rationale. Justin Tobler clarifies in the latest email that while all callers use `--keep`, `git-index-pack` may still output `"pack"` if a lockfile already exists, making the comment technically accurate. The last line of the comment (about `.keep` file handling) is legacy text and will be removed in the next patch.
- **Error handling**: Error paths are consolidated to avoid resource leaks, and error messages include `errno` context and lockfile paths when lockfile creation fails. Lockfile creation failures are propagated as transaction commit errors.
- **Test coverage**: Extends `t/t5547-push-quarantine.sh` to verify (1) no `.keep` lockfile exists in the quarantine directory during the pre-receive phase (confirming deferral), (2) a manually created `.keep` file (simulating a concurrent process) is not deleted by the transaction cleanup (directly addressing the reported bug), and (3) no corresponding `.pack` file exists alongside the `.keep` file in the concurrent-process scenario (requested by Patrick for completeness).

Open questions and loose ends
- The assumption that leading directories for lockfiles exist during quarantine remains unaddressed. Patrick Steinhardt requested explicit directory creation or a rationale, but the author has not provided either. This was not revisited in Patrick’s final review and is not considered a blocker.
- Whether the `atexit` cleanup should be made more defensive (e.g., checking file ownership before deletion).
- Whether the transaction API itself needs broader hardening to prevent similar races in the future (e.g., atomicity guarantees for lockfile operations). Neither Patrick Steinhardt nor the author has addressed this, but it remains an open architectural question.
- **Comment ambiguity in `pack-write.c`**: Karthik Nayak notes that the updated comment describing `git-index-pack` output could be misread as implying the `"keep"` variant is always expected. Justin Tobler responds that the comment is technically accurate because `git-index-pack` may output `"pack"` even when `--keep` is used (if a lockfile already exists), and the last line of the comment (about `.keep` file handling) is legacy text that will be removed in the next patch. This resolves the ambiguity without requiring changes to the patch.
- Karthik Nayak suggests replacing `unlink()` with `unlink_or_warn()` in the error path of `write_pack_lockfile()` to avoid silently failing if the unlink operation itself fails. This is a minor nit and not a blocker.

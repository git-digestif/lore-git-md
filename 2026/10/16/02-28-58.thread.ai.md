Thread identity
Subject: [PATCH 0/3] odb: fix race condition in .keep lockfile cleanup
Series version: v1 (initial submission)
Originating author: Justin Tobler
Thread type: bugfix patch series

Core problem or goal
Fix a race condition in Git’s object database (ODB) transaction machinery where concurrent `git-receive-pack` processes can delete each other’s `.keep` lockfiles, leaving newly written packfiles vulnerable to deletion by housekeeping processes. The root cause is that temporary `.keep` lockfiles were registered in the object quarantine *before* being written to the primary ODB; if the transaction exited early (e.g., due to an error), the `atexit` handler still tried to clean up the lockfile at its final location, blindly deleting any file with the same name—even if it belonged to another process. The fix moves lockfile creation to the transaction commit phase, ensuring lockfiles are only written after the transaction is guaranteed to succeed.

Current status
Under review; v1 posted. The series is complete and ready for final polish. All three patches have received **substantive technical reviews** from Patrick Steinhardt, who supports the direction and has provided detailed feedback on code clarity, style, error handling, and test coverage. The first two patches (refactoring `read_index_pack_report()` and `odb_transaction_files_write_pack()`) have been revised to address all of Patrick’s suggestions: unconditional use of the `is_keep` pointer, splitting the SHA-1 assumption fix into a separate commit, adding missing spaces around operators, consolidating error paths, renaming `write_pack_lock()` to `write_pack_lockfile()` for consistency, fixing style nits, and correcting docstring grammar. The third patch (moving lockfile creation to transaction commit) has now been updated to incorporate Patrick’s feedback: the commit message will be reworded to clarify that the patch prevents partial transaction commits by acquiring all lockfiles before migrating any data, error messages in `write_pack_lockfile()` will include `errno` context and the specific lockfile path, and test coverage in `t/t5547-push-quarantine.sh` will explicitly verify that no corresponding `.pack` file exists alongside the `.keep` file in the concurrent-process scenario. The author declined to move the `safe_create_file_with_leading_directories()` call to the final patch, arguing that keeping it in the second patch is more defensive, though the assumption that leading directories exist during quarantine remains unaddressed.

Key technical details
- **Files touched**: `object-file.c`, `pack-write.c`, `pack.h`, `t/t5547-push-quarantine.sh`.
- **New/renamed symbols**:
  - `read_index_pack_report()` (exposed in `pack.h`): parses `git-index-pack` output to extract the packfile name and `.keep` status. The helper was refactored from internal logic in `index_pack_lockfile()` and is now a public API. The revised implementation incorporates Patrick Steinhardt’s feedback: unconditional use of the `is_keep` pointer, consolidated error paths, and improved docstring clarity.
  - `parse_index_pack_report()` (renamed from internal logic in `index_pack_lockfile()`; now a public helper).
  - `write_pack_lockfile()` (renamed from `write_pack_lock()`; new helper in `object-file.c`): constructs the lockfile path, writes the keep message (`"receive-pack <pid> on <hostname>"`), and registers it as a tempfile. The rename addresses Patrick’s request for consistency with existing naming conventions. Error messages now include `errno` context and the lockfile path for diagnostic clarity.
  - `write_pack_locks()` (new helper in `object-file.c`): batch-creates lockfiles during transaction commit.
- **Behavior change**: `.keep` lockfiles are now created *only* during transaction commit (`odb_transaction_files_commit()`), not during quarantine (`odb_transaction_files_write_pack()`). Packfile names are stored in a `strvec` during quarantine and written as lockfiles only if the transaction commits successfully. This eliminates the race condition by ensuring lockfiles are never left in an inconsistent state.
- **On-disk format**: No changes; the fix is purely behavioral.
- **Assumptions**: The second patch assumes leading directories for lockfiles exist during quarantine, which Patrick Steinhardt flags as potentially unsafe (e.g., if the ODB directory structure is not fully populated). The author justifies this assumption as safe but has not provided explicit directory creation or a detailed rationale. The first patch assumes `git-index-pack` output follows the `"pack\t<name>\n"` or `"keep\t<name>\n"` format, with `<name>` being a hexadecimal hash; this is now explicitly noted in the commit message.
- **Error handling**: Patrick’s review highlights ergonomic improvements for error paths, such as consolidating cleanup logic into a common exit block to avoid resource leaks, and suggests more detailed error messages (e.g., via `errno`) when lockfile creation fails. The first, second, and third patches have been updated to address these concerns, including `errno` context and lockfile paths in error messages.
- **Test coverage**: Extends `t/t5547-push-quarantine.sh` to verify (1) no `.keep` lockfile exists in the quarantine directory during the pre-receive phase (confirming deferral), (2) a manually created `.keep` file (simulating a concurrent process) is not deleted by the transaction cleanup (directly addressing the reported bug), and (3) no corresponding `.pack` file exists alongside the `.keep` file in the concurrent-process scenario (requested by Patrick for completeness).

Open questions and loose ends
- Whether the `atexit` cleanup should be made more defensive (e.g., checking file ownership before deletion).
- Whether the transaction API itself needs broader hardening to prevent similar races in the future (e.g., atomicity guarantees for lockfile operations). Patrick Steinhardt’s reviews do not address this, but it remains an open architectural question.
- The assumption that leading directories for lockfiles exist during quarantine remains unaddressed; Patrick Steinhardt requested explicit directory creation or a rationale, but the author has not provided either.
- Minor style and clarity adjustments for the third patch (e.g., consolidating error paths) are now resolved in the updated version.

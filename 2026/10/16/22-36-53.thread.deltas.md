# Thread deltas

## 2026/10/16

- [2026/10/16/22-36-53 by Dan <timelord@gmail.com>] Dan reported that git push over smart HTTP fails when the remote URL carries a token-only userinfo (e.g., `https://<token>@forge.example/...`) after libcurl 8.23.0 (commit 7a6bd027d0de, CVE-2026-94266; also backported as Ubuntu 24.04 curl 8.5.0-2ubuntu10.16) stopped returning credentials in `CURLINFO_EFFECTIVE_URL`, while fetch/clone continue to work.
- [2026/10/16/22-36-53 by Dan <timelord@gmail.com>] He analyzed that `http_request_reauth()` passes the credential-bearing asked-for URL and the now credential-less effective URL to `update_url_from_redirect()`, whose `strcmp()` mismatch causes git to treat an ordinary 200 as a redirect, rewrite `base_url` without userinfo, and clear `http_auth`; the subsequent POST then goes out without credentials, receives 401, and fails with "could not read Username".
- [2026/10/16/22-36-53 by Dan <timelord@gmail.com>] He proposed fixing `update_url_from_redirect()` to compare URLs after stripping `user[:pass]@` so a credential-free effective URL that is otherwise identical is not treated as a redirect, and suggested that for real same-origin redirects git should keep the existing `http_auth` rather than re-parsing it from a credential-less URL.
- [2026/10/16/22-36-53 by Dan <timelord@gmail.com>] He noted a user workaround: use `user:token@` instead of `token@` in the URL, or supply the token via a credential helper.

## 2026/10/21

- [2026/10/21/11-23-54 by Tuomas Ahola <taahol@utu.fi>] Tuomas Ahola noted that commit 76524c2604 ("http: handle curl stripping creds from effective url", 2026-09-28) is already merged to 'master' and asked the reporter to check whether it resolves the issue; the release notes describe it as updating the HTTP transport to handle recent curl versions that strip credentials from the effective URL, preventing unnecessary credential prompts during redirects.

This is a **bugfix** targeting the signal-handling (`sigchain`) subsystem. The patch addresses a race condition in `sigchain_push()`/`sigchain_pop()` where concurrent signal deliveries to different threads can corrupt the signal handler chain, leaving the process stuck in an infinite loop at 100% CPU. The fix is minimal: it adds a repair mechanism to `sigchain_pop()` that reinstalls the pre-chain signal disposition when the chain is found empty but was previously pushed, allowing the process to terminate cleanly instead of hanging.

The commit message is exceptionally thorough, detailing the reproduction scenario (`git clone --depth 1` over ssh), the exact interleaving that triggers the bug, and the validation methodology (fault-injected A/B testing with 300 runs). The patch itself is small (16 insertions, 1 deletion) and touches only `sigchain.c`, introducing a new `pushed` counter to track whether the chain was ever built and using it to repair the signal disposition when corruption is detected. The fast path remains unchanged, and the repair is inert on all legitimate code paths.

This is a real, user-visible bug with a clear impact (process hangs requiring `SIGKILL`), and the fix is well-motivated and tested. The alternative approach (serializing chain mutations with a spinlock) is mentioned but not pursued, as the repair-after-the-fact strategy suffices and avoids locking overhead. The patch is likely to be uncontroversial, though reviewers may ask for additional test coverage in the Git test suite (the commit message describes a minimal reproducer but does not add a test script to `t/`).

This is a bugfix patch targeting the `pack-objects` subsystem, addressing a data corruption issue when handling large blobs (≥4GiB) on 32-bit platforms. This is the second iteration of the patch, incorporating feedback from Simon Richter to use `off_t` (instead of `size_t`) for tracking compressed data length, aligning with the return type of `write_reuse_object()`.

The patch fixes a truncation bug in `builtin/pack-objects.c` where blob sizes are incorrectly cast from `size_t` to `unsigned long` (32 bits on affected platforms). This causes the pack header to record a truncated size while the compressed data remains full-length, corrupting the object. The issue manifests during `git repack` or `git gc` when loose large blobs are pruned, leading to data loss. The fix converts the relevant variables (`size` to `size_t`, `datalen` and `write_large_blob_data()`'s return value to `off_t`) in the streaming path for large blobs.

The v2 update is a minor but important refinement: using `off_t` for compressed data length ensures consistency with other parts of the codebase and avoids potential overflow when summing chunk lengths. The patch remains narrowly scoped, touching only six lines in one file, and the commit message clearly explains why other truncations in `pack-objects` are unreachable. No test is included due to the impracticality of creating ≥4GiB objects on 32-bit platforms.

This is a well-motivated, technically sound fix for a real edge case with clear consequences. The use of `size_t` and `off_t` aligns with Git's practices, and the change is uncontroversial. It should be a straightforward merge once reviewed.

This thread is about a bugfix patch that prevents data corruption in `git pack-objects` when handling large blobs (≥4GiB) on platforms where `long` is 32 bits but `size_t` is 64 bits (such as 64-bit Windows). The issue occurs because blob sizes were being truncated when cast from `size_t` to `unsigned long`, causing the pack header to record incorrect sizes while the compressed data remained full-length. This led to corrupted objects during `git repack` or `git gc` when loose large blobs were pruned.

Elia Pinto authored the patch, which is now in its third version. The fix changes the types of key variables (`size` to `size_t`, `datalen`/`olen` to `off_t`) and updates the return types of related functions to `off_t` in the large-blob streaming path of `builtin/pack-objects.c`. Feedback from Simon Richter (v1) and Junio C Hamano (v2) has been incorporated, including a commit message clarification to explicitly state the platform condition (32-bit `long` with 64-bit `size_t`). The patch is narrowly scoped, well-motivated, and uncontroversial, with no behavioral side effects or on-disk format changes.

The patch is ready for merging, as all prior feedback has been addressed. No test is included due to the difficulty of reproducing the bug (requiring ≥4GiB objects on affected platforms), but the edge cases and consequences are thoroughly documented in the commit message. The fix is minimal—just 7 lines changed—and aligns with existing patterns in the codebase.

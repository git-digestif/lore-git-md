This thread is about a bugfix patch from Elia Pinto that prevents data corruption in `git pack-objects` when handling large blobs (4GiB or larger) on 32-bit platforms. The issue occurs because blob sizes were being truncated when cast from `size_t` to `unsigned long`, causing the pack header to record incorrect sizes while the compressed data remained intact. This led to corrupted objects during operations like `git repack` or `git gc` when loose large blobs were pruned.

The patch is now in its second iteration, incorporating feedback from Simon Richter to use `off_t` for tracking compressed data length, which aligns with the return type of `write_reuse_object()`. The fix is narrowly scoped to the large-blob streaming path in `builtin/pack-objects.c`, changing the types of a few variables to ensure accurate size tracking. The on-disk format remains unchanged, and the patch has no behavioral side effects. No test is included due to the difficulty of reproducing the bug (requiring 4GiB+ objects on 32-bit systems), but the rationale and edge cases are well-documented in the commit message.

The patch is under review and appears uncontroversial. It addresses a clear correctness issue with minimal changes (7 lines) and should be ready for merging once it receives a thorough review. No objections or open questions have been raised so far.

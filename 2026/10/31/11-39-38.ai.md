This is the fourth and final patch in Elia Pinto’s four-part **bugfix series** addressing truncation issues with large objects (≥4 GiB) on 32-bit platforms, particularly Windows. The patch aligns the size parameter in `verify_pack()` callbacks with the rest of the pack code by converting it from `unsigned long` to `size_t`. This change ensures `git fsck` checks the full object rather than a truncated prefix when processing packs containing objects ≥4 GiB on platforms where `unsigned long` is 32-bit.

The patch touches three files: `builtin/fsck.c`, `odb.h`, and `pack.h`. It updates the `verify_fn` callback signature in `pack.h`, the `object_cb` field in `struct odb_fsck_options` (used by `git fsck`), and the implementation of `fsck_obj_buffer()` in `fsck.c`. The change is mechanical and mirrors earlier patches in the series, which have already converted similar size parameters in `unpack-objects`, `index-pack`, and SHA-1 verification code paths. No new symbols are introduced, and the on-disk format remains unchanged.

The issue is triggered only on 32-bit platforms when processing objects ≥4 GiB, making it impractical to test directly. The commit message explains the failure mode clearly: `fsck_obj_buffer()` receives a truncated size, causing `parse_object_buffer()` and `fsck_object()` to inspect only the first 4 GiB of the object. This patch closes the last gap in the series, ensuring consistency across the pack-receiving and verification pipeline.

This patch is uncontroversial and technically sound, completing the series’ goal of eliminating `unsigned long` truncation risks in large-object handling. The series as a whole is a high-priority fix for Windows compatibility, and this patch is a necessary final step. No objections or open questions have been raised in the thread so far. The lack of tests is justified by the constraints, and the patch is ready for review.

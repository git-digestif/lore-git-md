This is a bugfix from Linus Torvalds that corrects how `git describe` counts commit distances when commit dates are unreliable or skewed. The issue surfaced during the Linux v7.4 merge window, where `git describe` reported an incorrect commit distance (19342) compared to the kernel's own calculation (19059). The discrepancy occurs because the current implementation walks commits purely by date, which can skip past the intended tag when dates are out of order.

The fix is a one-line change in `builtin/describe.c`: the priority queue that orders commits now uses `compare_commits_by_gen_then_commit_date` instead of `compare_commits_by_commit_date`. This ensures generation numbers (from the commit graph) are considered first, falling back to commit dates only when generations are equal. The patch also adds a new test case in `t/t6120-describe.sh` that sets up a repository with a tag dated *before* its parent, verifying the correct distance is reported.

Linus notes this improves behavior in the common case (repositories with a commit graph) but won’t help if the graph is missing. The commit message references an older fix (1b600e659a) that addressed a related issue, reinforcing the intent that `git describe`’s distance number should reflect the true commit count. The patch is self-contained, well-motivated, and includes test coverage—exactly the kind of surgical fix you’d expect from a maintainer who just wants the tool to work correctly. Worth attention if you rely on `git describe` for accurate version strings.

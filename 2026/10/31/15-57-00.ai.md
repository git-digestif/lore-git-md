This is a four-patch series targeting the HTTP transport layer, addressing gaps in Git’s handling of transient server errors and rate-limiting. The series introduces exponential backoff, configurable retry status codes, and retries for HTTP POST requests, motivated by real-world issues observed when Git interacts with hosting backends and reverse proxies under high concurrency.

The cover letter clearly identifies four specific problems: an off-by-one retry count bug, lack of exponential backoff when Retry-After headers are absent, inability to retry transient 5xx errors, and missing retries for HTTP POST requests (which handle data transfers during fetch/clone and partial clone operations). Each problem is tied to a corresponding patch, and the series builds logically—fixing low-level timing issues first, then adding backoff logic, then expanding the set of retryable status codes, and finally extending retries to POST requests.

The patches touch `http.c`, `remote-curl.c`, and related documentation and tests. Key new config options include `http.retryStatusCodes` (defaulting to "429") and the existing `http.retryAfter` now doubles on each retry when Retry-After is missing. The test suite gains a new script (`t/t5584-http-429-retry.sh`) and expands an existing helper (`t/lib-httpd/http-429.sh`) to cover the new behaviors.

Prior discussion links are provided, showing this is a revisit of earlier proposals (2020 and 2024) rather than a completely new idea. The commit message for patch 1 references a specific prior commit (640657ffd0) that introduced the original 429 retry logic, grounding the series in existing code.

The series appears well-motivated and technically sound, with thorough test coverage and clear documentation updates. It targets a real pain point for users operating at scale and should be uncontroversial for environments that want to opt into more aggressive retry behavior. The only likely discussion point is whether the default set of retryable status codes should include 5xx errors, but the series makes that opt-in via config, so it sidesteps any default-behavior debate.

## 2026/10/31

- [2026/10/31/15-57-00 by Ravi Mistry via GitGitGadget <gitgitgadget@gmail.com>] Ravi Mistry posted a 4-patch series addressing four gaps in HTTP 429 retry handling: an off-by-one retry count and Retry-After Trace2 timing bug, lack of exponential backoff when Retry-After is absent, inability to retry transient 5xx errors, and lack of retry support for HTTP POST requests in post_rpc().

- [2026/10/31/15-57-03 by Ravi Mistry via GitGitGadget <gitgitgadget@gmail.com>] Ravi Mistry added the http.retryStatusCodes config option (and GIT_HTTP_RETRY_STATUS_CODES environment variable), defaulting to "429", allowing environments to opt into retrying additional status codes such as 502, 503, and 504.
- [2026/10/31/15-57-04 by Ravi Mistry via GitGitGadget <gitgitgadget@gmail.com>] Ravi Mistry extended retry support to HTTP POST requests in probe_rpc() and post_rpc() by extracting a shared http_retry_wait() helper, deferred RPC error reporting until retries are exhausted, and re-attached the Content-Encoding: gzip header when retrying compressed requests.

## 2026/11/04

- [2026/11/04/22-05-50 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson argued against immediately retrying on HTTP 429 responses when no Retry-After header is present, stating that the server signaled the client was being too aggressive and that continuing to make requests is exactly what should not be done; he suggested picking a sensible default delay such as 30 seconds instead.

## 2026/11/05

- [2026/11/05/00-10-10 by Ravi Mistry <rmistry@google.com>] Ravi Mistry proposed defaulting http.retryAfter to 1 second (matching curl's --retry behavior of 1s, 2s, 4s, ...), arguing that since the delay doubles each attempt and Patch 3/4 reuses http.retryAfter for opt-in transient 5xx retries, starting at 30s would make 3 retries take 30s/60s/120s, whereas 1s avoids hammering the server immediately while still ramping up; he offered to send a v3 with that change if 1s sounds reasonable.
- [2026/11/05/17-45-00 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano said matching what curl does sounds sensible.
- [2026/11/05/22-32-52 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson objected that 1s is not a reasonable backoff for a 429 since load could not reasonably decrease that fast, reiterated his 30-second suggestion (30/60/120s as reasonable timeframes) with at least 10 seconds as a floor, and argued curl's defaults are not right for Git because Git makes expensive requests requiring substantial server computation, unlike curl's cheap static-page requests.

This is a **bugfix patch update** (v2) in the ongoing effort to prevent Git from accidentally deleting tracked files when operating on shallow boundary commits. The patch now extends protection to `git cherry-pick`, all `git rebase` backends (`merge`, `interactive`, `apply`), and moves the safeguard to the planning stage (todo-list construction) to avoid leaving behind `.git/sequencer` state. The author, Nakul V S, has addressed prior feedback by introducing a shared helper function (`sequencer_refuse_shallow_boundary()`) and adding a lightweight check for the `rebase --apply` backend, which bypasses the sequencer. The new `--allow-shallow-boundary` flag is exposed only for `revert`/`cherry-pick`; `rebase` always refuses without override.

The patch touches the sequencer subsystem (`sequencer.c`, `sequencer.h`), `builtin/revert.c`, `builtin/rebase.c`, and documentation. Test coverage verifies refusal in shallow repos, override behavior, autostash restoration, and edge cases like single-commit clones. The manual-todo-list edge case (where a boundary commit’s hash is manually added) remains unfixed as an acceptable trade-off. `git commit --amend` is intentionally left out for now, with the author open to addressing it in a follow-up if requested.

Junio C Hamano and Phillip Wood’s concerns about scope and implementation location are resolved in this version. The patch is under active review, with no merge decision yet. Key technical details include the new `is_shallow_boundary_commit()` utility, early checking during todo-list construction, and no changes to on-disk formats. The safeguard is now enforced at the planning stage, avoiding the leftover state issues present in v1.

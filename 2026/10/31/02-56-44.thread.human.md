This thread began as a bug report from Chris Torek about Git silently misbehaving when users manually add `[include]` directives to `.git/config` or other Git-managed config files. Chris framed it as a minor robustness issue, suggesting Git should ignore or reject such directives to prevent unpredictable failures in commands like `git remote`.

The discussion took a turn with brian m. carlson’s reply, which introduced a real-world use case: his workplace relies on `[include]` directives in `.git/config` to test config changes on individual hosts while maintaining a checksum-verified `.git/config` across replicas. This contradicts the assumption that such usage is rare or discouraged, shifting the thread from a theoretical robustness discussion to a concrete compatibility concern. Brian’s position is that any change to how Git handles includes must preserve existing functionality, not just prevent silent failures. The thread is now at an impasse—Chris’s proposal to ignore or reject includes is unlikely to move forward without addressing these use cases, but no alternative solutions have been proposed yet. The key open question is how to balance robustness with backwards compatibility.

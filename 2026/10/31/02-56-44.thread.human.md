This thread is a bug report and design suggestion from Chris Torek about an edge case in Git’s configuration file handling. Torek describes how manually editing `.git/config` to add `[include]` directives—such as splitting remote or branch sections into separate files—can cause operations like `git remote` to fail unpredictably. While he acknowledges this is a minor issue ("don’t do that"), he suggests Git could improve robustness by ignoring or rejecting include directives in `.git/config` and other Git-managed config files (e.g., `.git/modules/*/config`). The motivation is defensive programming: preventing user confusion or silent failures when manual edits introduce unexpected behavior.

Torek provides a concrete example (an `ed` script moving `[remote]` sections to an included file) and notes that the core issue lies in assumptions about config file structure in Git’s codebase. The proposed fix would involve modifying config-parsing logic in `config.c` to handle include directives more defensively, though no patch is included—this is an exploratory RFC. The thread is new, and while the issue is unlikely to be controversial, it may spark discussion about whether Git should enforce stricter validation of its managed config files or remain permissive.

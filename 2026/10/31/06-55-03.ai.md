This is a bugfix patch from Linus Torvalds targeting the `git describe` command. The patch corrects a long-standing issue where `git describe` miscomputes the commit distance when commit dates are skewed or unreliable, causing it to report incorrect distances in repositories with non-monotonic commit timestamps.

The problem surfaced during the Linux v7.4 merge window, where `git describe` reported a commit distance of 19342 while the kernel's own version calculation (which is authoritative) reported 19059. The discrepancy arises because `git describe` walks commits purely by commit date, which can lead it past the actual tagged release when dates are out of order. The fix modifies the priority queue used during the commit walk to prioritize commit generation numbers (from the commit graph) over raw commit dates, ensuring the walk follows the true topological order rather than being misled by skewed timestamps.

The patch includes a new test case in `t/t6120-describe.sh` that sets up a repository with a tag dated *before* its parent commit, demonstrating the bug and verifying the fix. The test creates a commit graph to ensure generation numbers are available, which is now a prerequisite for correct behavior. The change is minimal: a one-line modification in `builtin/describe.c` swapping the queue's comparison function from `compare_commits_by_commit_date` to `compare_commits_by_gen_then_commit_date`.

This is a clear regression fix with real-world impact, particularly for the Linux kernel workflow where `git describe` output is used in version strings. The commit message is thorough, explaining the problem, the fix, and the expected behavior, and it references a 2007 commit that addressed a related issue in the same area. The test coverage is appropriate, and the fix aligns with the documented intent of `git describe`. The patch is likely to be uncontroversial and should proceed smoothly through review.

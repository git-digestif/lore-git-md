This is the second patch in Elia Pinto’s four-patch series fixing truncation issues with large objects (≥4 GiB) on 32-bit platforms, specifically targeting `index-pack`. The patch converts the `write_compressed()` function in `builtin/index-pack.c` from using `unsigned int` to `size_t` for both its size parameter and return value, addressing a "serious inflate inconsistency" crash when resolving thin packs with local bases exceeding 4 GiB.

The issue arises because `write_compressed()` truncates the input size to 32 bits, while `append_obj_to_pack()` writes the full size in the pack header. When `unpack_data()` later processes the delta, it encounters an early end-of-stream and dies. The commit message demonstrates this with a 16-bit simulation (100 KiB base), confirming the same failure mode. No test is included due to the impracticality of generating 4 GiB objects, but the reproduction scenario is clearly described.

The change is minimal—just a single-line type conversion—but critical for correctness on platforms where `unsigned long` (and thus `size_t`) is 32-bit. This aligns with the series’ broader goal of ensuring the pack-receiving pipeline handles large objects consistently. The patch is mechanical and uncontroversial, with no new symbols or behavior changes beyond fixing the truncation. It depends on the type system cleanup in patch 1/4 and sets up the SHA-1 collision fix in patch 3/4. No review feedback has been posted yet.

This is a bugfix patch targeting the sequencer subsystem, expanding the safeguard against operating on shallow boundary commits to cover `git cherry-pick` and `git rebase` as well as `git revert`. The patch is a second iteration (`v2`) that addresses feedback from Phillip Wood and Junio C Hamano.

The core problem remains the same: in a shallow repository (created with `git clone --depth=1`), the boundary commit appears as a root commit that added every file in its tree. Reverting, cherry-picking, or rebasing it would either remove all tracked files or add them all again, which is almost never what the user intended. The patch now refuses these operations by default, with an opt-in override (`--allow-shallow-boundary`) for `git revert` and `git cherry-pick`. For `git rebase`, the operation is always refused, and the error message suggests `git fetch --unshallow` instead.

The implementation has been reworked to check for shallow boundary commits when the list of commits to replay is built, rather than mid-operation in `do_pick_commit()`. This ensures that a refused command leaves no state behind: no commit is created, HEAD and the working tree are untouched, and no sequencer or rebase state is left for the user to clean up. The check is implemented via a shared helper function (`sequencer_refuse_shallow_boundary()`) that is called from `sequencer_make_script()`, `make_script_with_merges()`, `single_pick()`, and the new check in the "apply" backend of `git rebase`. The "apply" backend does not go through the sequencer, so it checks the commits `git format-patch` is about to turn into patches before it rewinds HEAD.

The patch includes thorough test coverage, verifying refusal in shallow repos, override with `--allow-shallow-boundary`, and confirming that non-shallow repos remain unaffected. It also tests that `--allow-shallow-boundary` is remembered across `--continue`, that autostash is restored when a rebase is refused, and that the safeguard does not interfere with rebases that do not replay the boundary commit. The documentation has been updated for `git revert`, `git cherry-pick`, and `git rebase`.

This is a well-crafted, narrowly scoped fix that addresses a real and surprising footgun. The implementation is conservative (default refusal) and provides a clear escape hatch for users who genuinely want the behavior. The patch is ready for review and looks likely to be merged once the remaining loose ends (such as whether to extend the safeguard to `git commit --amend`) are resolved.

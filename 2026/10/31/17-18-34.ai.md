This is a **bugfix patch update** (v2) targeting the sequencer subsystem. The patch now refuses to operate on shallow boundary commits by default for `git revert`, `git cherry-pick`, and all `git rebase` backends (`merge`, `interactive`, `apply`). The update addresses all prior review feedback from Phillip Wood and Junio C Hamano: it consolidates shallow-boundary detection into a shared helper function (`sequencer_refuse_shallow_boundary()`), moves the check to the planning stage (todo-list construction) to avoid leaving behind partial state, and omits the rarely-used `--allow-shallow-boundary` option from the synopsis for clarity.

The patch introduces a new CLI flag, `--allow-shallow-boundary`, but only exposes it for `revert` and `cherry-pick`; `rebase` always refuses without override. This design choice reflects the consensus that rebasing a shallow boundary commit is never safe, while reverting or cherry-picking might have niche use cases. The implementation touches `sequencer.c`, `sequencer.h`, `builtin/revert.c`, `builtin/rebase.c`, and the `git-revert` man page. Test coverage verifies refusal in shallow repos, override behavior, autostash restoration, and edge cases like single-commit clones across all rebase backends.

The v2 patch appears well-crafted and thoroughly motivated. It resolves the core problem—preventing accidental data loss when operating on shallow boundary commits—without introducing new edge cases or on-disk format changes. The architectural shift to early checking (during todo-list construction) is a clear improvement over the v1 approach, and the shared helper function ensures maintainability. The only remaining open question is whether the safeguard should extend to `git commit --amend`, but that discussion is orthogonal to this patch and does not block its readiness. The patch looks like a strong candidate for merging once review concludes.

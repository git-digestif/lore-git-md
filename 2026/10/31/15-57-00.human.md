This is a four-patch series targeting the HTTP transport layer, addressing gaps in Git’s handling of transient server errors and rate-limiting. The patches fix an off-by-one retry bug, add exponential backoff for retries, introduce a configurable list of retryable HTTP status codes, and extend retry logic to cover HTTP POST requests (e.g., `/git-upload-pack` during fetch/clone).

The motivation is clear and practical: under high concurrency, Git’s current retry logic is either too rigid (fixed delays) or too narrow (only HTTP 429). The series aligns Git’s behavior with tools like `curl --retry`, making it more resilient against transient failures from reverse proxies, load balancers, or hosting backends. The commit messages are detailed, explaining each gap and how the patch addresses it, and the test coverage (new `t5584-http-429-retry.sh`) looks thorough.

Patch 1/4 fixes a long-standing off-by-one bug in the retry counter and ensures Trace2 logs the correct `Retry-After` value. Patch 2/4 introduces exponential backoff when servers don’t provide a `Retry-After` header, which is a significant improvement for environments where brief glitches are common. Patch 3/4 adds `http.retryStatusCodes` (defaulting to "429"), allowing users to opt into retrying 5xx errors like 502/503/504. Patch 4/4 extends retry support to HTTP POST requests, which are critical for fetch/clone operations and partial clones, while also fixing a missing `Content-Encoding: gzip` header on retries.

The series touches core HTTP plumbing (`http.c`, `remote-curl.c`) and adds new config options, so it’s likely to attract review attention. The changes are well-scoped and don’t appear to introduce backward-compatibility risks. If you work with Git in high-concurrency environments or behind proxies, this series is worth watching.

This is the third patch in a four-patch series improving Git’s HTTP transport resilience. It introduces the `http.retryStatusCodes` configuration option, allowing users to specify which HTTP status codes (400–599) should trigger retries. By default, only 429 (Too Many Requests) is retried, but the patch enables opt-in retries for transient 5xx errors like 502 (Bad Gateway), 503 (Service Unavailable), and 504 (Gateway Timeout), which are commonly returned by reverse proxies and hosting backends under load.

The implementation adds a new `is_retryable_http_code()` helper that parses the comma- or whitespace-separated list from `http.retryStatusCodes` (or its environment variable counterpart, `GIT_HTTP_RETRY_STATUS_CODES`). The existing retry logic in `handle_curl_result()` and `http_request_recoverable()` is updated to consult this list instead of hardcoding 429. Warning messages are adjusted to show the numeric status code (e.g., "HTTP 502, waiting 1 seconds before retry") for non-429 responses, while preserving the "rate limited" phrasing for 429 to maintain backward compatibility.

Documentation updates in `Documentation/config/http.adoc` clearly describe the new option and its interaction with `http.maxRetries`, `http.retryAfter`, and `http.maxRetryTime`. The test suite expands to cover the new behavior: `t/t5584-http-429-retry.sh` gains five new tests verifying that 5xx errors are *not* retried by default, that configured status codes (502, 503, 504) are retried, that Retry-After headers are honored for 503, that exhausted retries report the correct error (not "rate limited"), and that both environment variables and URL-specific config work. The helper script `t/lib-httpd/http-429.sh` is extended to simulate 502, 503, and 504 responses.

The patch is technically sound, with thorough test coverage and clear documentation. It sidesteps controversy by making 5xx retries opt-in, so the only likely discussion point is whether the default set should include more codes. The series as a whole targets a real pain point for users operating at scale, and this patch in particular addresses a long-standing gap in Git’s HTTP error handling.

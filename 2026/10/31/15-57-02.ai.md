This is the second patch in a four-patch series improving Git’s HTTP transport resilience. It introduces exponential backoff for retry delays when servers return HTTP 429 (Too Many Requests) without a Retry-After header.

The patch modifies `http.c` to pass the 1-based retry attempt count into `handle_rate_limit_retry()`, where it doubles the configured `http.retryAfter` delay on each subsequent retry (1s, 2s, 4s, …) while clamping the maximum delay at `http.maxRetryTime`. This matches curl’s `--retry` behavior and prevents Git from burning through all retries too quickly when a server is temporarily overloaded. The documentation (`Documentation/config/http.adoc`) is updated to clarify that `http.retryAfter` is now the *initial* delay and that exponential backoff applies only when no Retry-After header is present.

Three new tests in `t/t5584-http-429-retry.sh` verify the doubling behavior, the clamping at `http.maxRetryTime`, and that server-provided Retry-After headers still override the backoff logic. The changes are confined to the retry timing logic and do not alter the set of retryable status codes or the handling of HTTP POST requests (those are addressed in later patches).

The patch is well-motivated, clearly explained, and thoroughly tested. It addresses a real-world pain point for users operating at scale and should be uncontroversial. The only potential discussion point is whether the default `http.retryAfter` value (0) is appropriate, but the patch sidesteps that by making the behavior opt-in via configuration.

This is the first patch in a four-part series improving Git’s HTTP transport resilience. It fixes two small but real bugs in the existing 429-rate-limit retry logic that was introduced in commit 640657ffd0 (March 2026).

The first bug is an off-by-one in the retry counter: because the loop uses a pre-decrement (`--rate_limit_retries`), setting `http.maxRetries=1` actually performs zero retries, and setting it to zero can wrap to -1 (truthy in C) after a re-authentication. The patch changes the loop condition to `http_max_retries > 0 && rate_limit_retries-- > 0` and adds an explicit check for `http_max_retries <= 0` to return `HTTP_ERROR` immediately.

The second bug is a race in the Retry-After header parsing: `CURLINFO_RETRY_AFTER` is queried *after* `run_one_slot()` has already called `handle_curl_result()`, which logs the still-uninitialized `retry_after` value (-1) to Trace2. The fix moves the extraction into `finish_active_slot()` so that both the logging and the caller see the correct value.

The patch also updates the test helper (`t/lib-httpd/http-429.sh`) to support configurable failure counts (e.g., “fail-2”, “fail-3”) and adds three new test cases in `t/t5584-http-429-retry.sh` that verify the retry count, the permanent-failure case, and the Trace2 logging.

The changes are narrowly scoped, well-explained, and backed by tests. They address real edge cases that users at scale are likely to hit, and the fixes look correct. No controversy is expected.

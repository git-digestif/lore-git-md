This thread is a four-part bugfix series from Elia Pinto addressing a long-standing issue on 32-bit platforms (particularly Windows): object sizes exceeding 4 GiB get truncated when stored in `unsigned long` variables, causing `git fsck`, `git tag -v`, and other commands to misbehave. The first patch, just posted, updates `check_object_signature()` in `object-file.c` to use `size_t` instead of `unsigned long` for object sizes, matching the type already used by its callers. This is a mechanical change that eliminates truncation risk without altering on-disk formats.

The series targets 13 files across Git’s object, commit, tag, fsck, and ref-filter subsystems, with key functions like `parse_object_buffer()` and `copy_subject()` slated for similar updates in later patches. No tests are included yet, as reproducing the bug requires objects larger than 4 GiB, though the author has offered to add `EXPENSIVE` tests for 32-bit platforms if reviewers request them. The patches are under review but haven’t drawn substantive feedback so far—only surface-level comments are possible at this stage. The work is narrowly scoped to type safety and doesn’t touch pack-related code or tree APIs, which are deferred to follow-up efforts.

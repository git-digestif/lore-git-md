# Git mailing list daily digest for 2026/10/31

## The day in brief
Git's HTTP transport gained configurable retry logic for transient errors, including exponential backoff and support for retrying POST requests. A long-standing inconsistency in `@{push}` resolution was fixed, aligning its behavior with `git push` in triangular workflows. Multiple bugfix series addressed 32-bit platform truncation issues, particularly for large objects and submodule diff headers. The `git describe` command received a regression fix for commit distance calculation when timestamps are skewed.

## Notable threads

### parse-options: new sub-API for early argument scanning
[2026/09/02/16-10-41] Christian Couder's patch series introducing `early_scan_options()` for consistent early argument parsing saw key progress. The series fixes a bug in `git fast-import` where `--allow-unsafe-features` was ignored when preceded by `--depth 5`. Cynthia Uche's tested review confirmed the fix works as intended and highlighted the critical role of the `EARLY_SCAN_STOP_AT_NON_OPTION` flag in preventing misinterpretation of non-option arguments. The review also identified a documentation gap: the comment above the `early_scan_options()` call in `fast-import.c` should explain why the flag is passed, despite `parse_options()` not using `PARSE_OPT_STOP_AT_NON_OPTION`. The preparatory refactorings (patches 1/6 and 2/6) and the `git fast-import` bugfix (4/6) are ready for `next`, while the core API patch (3/6) awaits resolution of usability concerns about argument skipping and validation checks.

### sequencer: refuse to revert/cherry-pick a shallow boundary commit by default
[2026/10/21/10-09-41] Nakul V S's v2 patch expanded protection against operating on shallow boundary commits to cover `git cherry-pick` and all `git rebase` backends (`merge`, `interactive`, `apply`). The update addresses prior feedback by moving the safeguard to the planning stage (todo-list construction) via a shared helper function, `sequencer_refuse_shallow_boundary()`, ensuring no state is left behind if the command is refused. The `--allow-shallow-boundary` flag is retained for `revert` and `cherry-pick` but omitted from the synopsis for clarity, while `rebase` always refuses without override. The manual-todo-list edge case (where a boundary commit's hash is manually added) is acknowledged as an acceptable trade-off. The patch is technically complete and awaits a merge decision.

### Fix 64-to-32 truncations on LLP64 platforms (Windows)
[2026/10/21/10-16-36] Elia Pinto's v3 series addressing 64-to-32-bit truncations on Windows (LLP64 platforms) is now complete. The series fixes four specific truncation sites: object database writes (truncated blobs), word-diff buffer allocation (crash due to overflow), file conversion helpers (incorrect binary detection, CRLF handling, and keyword expansion), and text statistics counters in `convert.c` (theoretical overflow risk). The v3 iteration addresses procedural feedback from Patrick Steinhardt: the test script in `t1007-hash-object.sh` now avoids redundant file I/O by using `git cat-file -e` to verify object existence, and the fourth patch's commit message has been simplified to avoid overstating the overflow risk. The series is technically complete and ready for integration, with no substantive objections remaining.

### completion: remove NO_PARSEOPT for commands using parse-options
[2026/10/24/05-24-49] Tanga Joris's v3 series fixed a completion regression for four built-in commands (`patch-id`, `diff-pairs`, `fast-import`, `var`) by centralizing `--git-completion-helper` handling in `parse-options.c`. The author agreed to add a comment in `parse-options.h` explaining why `show_usage_with_options_if_asked()` handles completion-helper arguments before command initialization, addressing Kaartic Sivaraam's feedback. The series remains dependent on Christian Couder's `cc/early-scan-options` series reaching stability and integration in `next`.

### remote: align @{push} resolution with push.default=simple in triangular workflows
[2026/10/27/12-43-59] Harald Nordgren's v2 series fixed a long-standing inconsistency where `@{push}` failed to resolve in triangular workflows when `push.default=simple` and `remote.pushDefault` pointed to a different remote than the branch's upstream. The series is now complete with both patches posted: the first refactors `branch_get_push_1()` to extract the `PUSH_DEFAULT_SIMPLE` logic into a new helper, `branch_get_push_simple()`, and the second implements the four-line fix to align `@{push}` resolution with `git push`. Test coverage has been expanded to include a regression test for `@{push}` in triangular setups. The series is expected to be queued for `next` once Junio confirms the refactoring meets his readability goals.

### redesigning signal handling in threaded Git code to fix sigchain race
[2026/10/29/14-15-21] The design discussion for fixing a race condition in Git's `sigchain` subsystem took a turn after Oswald Buddenhagen clarified that five signals (SIGPIPE, SIGBUS, SIGFPE, SIGILL, SIGSEGV) are thread-directed rather than process-directed. Phillip Wood tentatively suggested using an atomic flag in the signal handler to serialize unwinding of the `sigchain` stack for SIGPIPE, as blocking thread-directed signals could prevent the process from being killed if they occur in a worker thread. The thread remains in the design-proposal stage, with no v2 posted yet; feedback from Jeff King and Junio is still pending.

### Bug report: include directives in .git/config cause silent failures
[2026/10/31/02-56-44] Chris Torek reported that manually adding `[include]` directives to `.git/config` causes commands like `git remote` to fail unpredictably. Torek suggested ignoring include directives in Git-managed config files as a defensive measure, but brian m. carlson opposed this, citing a real-world workflow that relies on `[include]` in `.git/config` for testing config changes on individual hosts while maintaining a checksum-verified `.git/config` across replicas. The discussion has shifted from a robustness improvement to a compatibility concern, with no clear path forward yet.

### git describe: fix commit distance calculation with skewed commit dates
[2026/10/31/06-55-03] Linus Torvalds submitted a regression fix for `git describe` that corrects commit distance calculation when commit timestamps are non-monotonic. The patch modifies the priority queue used during the commit walk to prioritize commit generation numbers (from the commit graph) over raw commit dates, ensuring the walk follows the true topological order. The fix includes a new test case demonstrating the bug and verifying the fix. Tuomas Ahola offered a rewritten test setup using `test_tick` manipulation, which is functionally equivalent but may improve readability. The patch is likely to be uncontroversial and should proceed smoothly through review.

### submodule: fix commit abbreviation in diff headers
[2026/10/31/08-25-49] Srujith A Poojary's v3 patch fixed commit abbreviation in submodule diff headers by ensuring the abbreviation is checked against the submodule's object database rather than the superproject's. The update incorporates all prior feedback, including a cosmetic commit title adjustment to lowercase the "submodule:" prefix. The patch is technically complete, addresses a real correctness issue, and is ready for integration. It is part of the broader Git libification effort but is self-contained and does not depend on other in-flight work.

### merge-ort: fix valueless config handling for rename detection
[2026/10/31/10-06-42] Thomas Bachem submitted a bugfix patch making valueless config settings (`merge.renames`, `diff.renames`, `merge.directoryRenames`) default to `true` in merge-ort, aligning its behavior with the rest of Git. The patch replaces `repo_config_get_string()` with `repo_config_get_value()` in merge-ort's config parsing code and includes thorough test coverage. The fix addresses a long-standing inconsistency where `git -c merge.renames merge` failed with "missing value" errors, despite Git's documentation stating that valueless config settings should default to `true`.

### the_repository removal: fsmonitor and notes-utils

### Fix truncation issues with large objects on 32-bit platforms
[2026/10/31/11-09-56, 2026/10/31/11-39-34, 2026/10/31/18-04-10] Elia Pinto submitted multiple bugfix series addressing truncation issues on 32-bit platforms. The first series (v3) fixes 64-to-32-bit truncations in object parsing, fsck, and related subsystems, while the second (v1) targets the pack-receiving pipeline (`unpack-objects`, `index-pack`, `git fsck`). A standalone v2 patch fixes a data corruption bug in `git pack-objects` where blob sizes ≥4GiB are truncated when cast from `size_t` to `unsigned long` on 32-bit platforms. Simon Richter's feedback clarified that `size_t` is insufficient for on-disk sizes on 32-bit platforms, leading Elia to post a separate v2 patch using `off_t` for compressed data length in `pack-objects`. The series are well-motivated and address real-world compatibility issues for Windows users.

### http: exponential backoff, configurable retry codes, POST retries
[2026/10/31/15-57-00] Ravi Mistry submitted a four-patch series improving Git's HTTP transport resilience. The series introduces exponential backoff for retry delays, configurable retry status codes (defaulting to 429), and retries for HTTP POST requests. The patches address gaps in Git's handling of transient server errors and rate-limiting, motivated by real-world issues observed when interacting with hosting backends and reverse proxies under high concurrency. The series is technically sound, with thorough test coverage and clear documentation updates.

### git stash: eliminate duplicate work in stash creation
[2026/10/31/20-01-07] Jasmeet Bhatia submitted a performance patch for `git stash` that reuses the already-prepared index state and untracked file list when `do_push_stash()` calls `do_create_stash()`. The patch adds an optional `prepared_untracked_files` parameter to `do_create_stash()` and skips redundant steps, yielding a 16-18% improvement in `git stash -p` operations and a 6% speedup for `git stash push` on the Linux kernel repository. The change is narrowly scoped to the stash subsystem and does not affect other Git commands or workflows.

This is the third patch in a four-patch series improving Git’s HTTP transport resilience. It introduces the `http.retryStatusCodes` configuration option, allowing users to specify which HTTP status codes (beyond the default 429) should trigger retries. The patch is well-motivated: real-world hosting backends and reverse proxies often return transient 5xx errors (502, 503, 504) during load shedding or upstream failures, and Git should be able to retry them when configured to do so.

The implementation is clean and conservative. The default remains 429 only, so existing behavior is unchanged unless users opt in. The config accepts a comma- or whitespace-separated list of status codes in the 400–599 range, and the code parses it efficiently with `strtol`. Error messages are updated to show the actual status code (e.g., "HTTP 502, waiting 1 seconds before retry") rather than the generic "rate limited" message, which helps debugging.

Tests cover the new functionality thoroughly: verifying that 5xx errors are *not* retried by default, that configured codes (502, 503, 504) are retried, that Retry-After headers are honored for 5xx codes, that exhausted retries report the correct error, and that both environment variables and urlmatch config work. The test helper (`t/lib-httpd/http-429.sh`) is extended to support configurable status codes, which will be reused in the next patch.

The patch fits neatly into the series’ overall goal of making Git more resilient to transient HTTP errors. It builds on the earlier patches (which fixed an off-by-one retry counter and added exponential backoff) and sets the stage for the final patch, which will extend retries to HTTP POST requests. The only likely discussion point is whether the default set of retryable codes should include 5xx errors, but the patch sidesteps that debate by making it opt-in.

This is a solid, uncontroversial improvement with clear real-world benefits for users operating at scale. The code is well-tested, the documentation is thorough, and the commit message explains the motivation and design choices clearly. No red flags here—just a straightforward addition of a useful knob.

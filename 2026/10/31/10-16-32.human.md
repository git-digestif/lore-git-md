This is the first patch in Elia Pinto’s four-patch bugfix series targeting 64-to-32 truncations on Windows (LLP64 platforms). It converts the object database’s write-side APIs from `unsigned long` to `size_t` for object lengths, preventing silent truncation when Git writes blobs larger than 4 GiB. On Windows, this truncation causes `git add` or `git hash-object -w` to store only the first 4 GiB of a file, while `git status` remains clean because the index records the correct stat data. The patch also updates the in-memory source’s size field to `size_t` for consistency.

The patch touches six files: `odb.c`, `odb.h`, `odb/source-inmemory.c`, `odb/source-loose.c`, `odb/source.h`, and the test script `t/t1007-hash-object.sh`. The changes are mechanical type conversions with no behavior change on 64-bit Linux, but they fix a real data corruption issue on Windows. The revised test in `t1007` adds an `EXPENSIVE` and `SIZE_T_IS_64BIT` test that writes a 5 GiB file with `git hash-object -w`, verifies the object ID, and checks its existence with `git cat-file -e`—avoiding the redundant file I/O and race-condition risks that Patrick Steinhardt flagged in earlier iterations.

This patch builds directly on Johannes Schindelin’s 2026 read-side ODB work (commit c6a4629e32), which widened the object info APIs to `size_t`. The series as a whole is well-motivated, thoroughly tested, and addresses a clear platform compatibility issue. The v3 iteration resolves all procedural feedback, and the patch appears ready for integration.

This is a bugfix patch targeting the `pack-objects` subsystem. It addresses a data corruption issue when handling very large blobs (4 GiB or larger) on 32-bit platforms where `unsigned long` is 32 bits wide.

The problem occurs in `write_no_reuse_object()` and `write_large_blob_data()` in `builtin/pack-objects.c`. These functions currently use `unsigned long` to track blob sizes and compressed data lengths, which can truncate or overflow when processing blobs exceeding 4 GiB. This leads to corrupted pack headers and misaligned object offsets in the pack index, ultimately causing data loss when the original loose object is pruned after repacking.

The fix switches the affected variables to `size_t` (for sizes and lengths) and `off_t` (for the return value of `write_no_reuse_object()`), matching the type of `st->size` and avoiding truncation. The commit message provides a clear reproduction scenario: running `git repack -a -d` on a repository containing a 4 GiB+ blob with `core.bigFileThreshold` set low enough to trigger the streaming path.

The patch is narrowly scoped and well-motivated, with no test added due to the impracticality of testing 4 GiB objects in the test suite. The changes are mechanical and confined to type adjustments, making this a straightforward correctness fix. Given the potential for silent data corruption, this looks like a serious issue worth attention from anyone working with large repositories on 32-bit systems.

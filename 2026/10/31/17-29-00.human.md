This is a bugfix patch that prevents Git from silently deleting all tracked files when `git revert`, `git cherry-pick`, or `git rebase` is run on a shallow boundary commit (a commit that appears as a root commit due to `--depth=1` cloning). The patch is now at **v2**, addressing all prior feedback by moving the safeguard to the planning stage (todo-list construction) and extending it to all rebase backends, including `--apply`, which bypasses the sequencer. The new version introduces a shared helper function, `sequencer_refuse_shallow_boundary()`, and adds a `--allow-shallow-boundary` flag for `revert`/`cherry-pick` (but not `rebase`, which always refuses without override).

The patch is well-motivated and clearly explains the risk: operating on a shallow boundary commit can result in the loss of all tracked files, a scenario that is easy to trigger accidentally in shallow clones. The implementation is thorough, covering all relevant commands and backends, and the commit message provides a concise rationale. Test coverage is solid, verifying refusal in shallow repos, override behavior, and edge cases like single-commit clones. The only loose end is whether to extend the safeguard to `git commit --amend`; Nakul has left this for a follow-up patch unless Junio prefers it in the same series.

Junio and Phillip Wood have both endorsed the core premise and the architectural improvements in v2. The patch looks ready for `next` unless further discussion about `commit --amend` or minor tweaks arises. If you work with shallow clones or care about data safety, this is worth reviewing.

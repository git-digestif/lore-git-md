This thread began with Linus Torvalds’ fix for a `git describe` regression that miscomputed commit distances when commit timestamps were non-monotonic, a real-world issue that surfaced during the Linux kernel’s v7.4 merge window. The patch itself—a one-line change in `builtin/describe.c` to prioritize commit generation numbers over dates—has been queued for integration, with Junio C Hamano signaling intent to move it forward. The discussion, however, has expanded into a broader debate about commit-graph freshness and the trade-offs between correctness and performance.

The core of the fix is now settled: `git describe` will use generation numbers when a commit graph is available, falling back to the old (buggy) date-based behavior otherwise. The unresolved question is how to handle the fallback case. Patrick Steinhardt and Derrick Stolee raised concerns about stale or missing commit graphs reintroducing the bug, proposing that Git should write out a fresh commit-graph after expensive walks like `ensure_generations_valid()` to amortize the cost. Linus, in his latest email, takes a pragmatic stance: the inconsistency is no worse than the existing bug, and the performance cost of unconditional graph walks is too high. Instead, he suggests adding a `--exact` flag to `git describe` that would force a full walk (via `ensure_generations_valid()`) to guarantee accurate results, giving users an opt-in path to correctness. This proposal aligns with the thread’s broader shift toward systemic solutions but frames it as a user-controlled feature rather than an automatic behavior.

The thread has seen high-weight contributions from key figures—Linus (author), Junio (maintainer), Stolee (domain expert), and Steinhardt (technical reviewer)—all converging on the need to address the commit-graph dependency, though with differing views on implementation. Open questions remain: whether the commit-graph write-back should be automatic or configurable, how to guard against read-only commands mutating state, and whether `--exact` should be the default in certain contexts. The fix itself is likely to land soon, but the systemic changes it has sparked—particularly around commit-graph freshness—will continue to evolve.

This thread began as a bugfix for `git describe` miscalculating commit distances when commit timestamps are non-monotonic—a regression that surfaced during the Linux kernel’s v7.4 merge window. Linus Torvalds submitted a one-line fix using commit generation numbers, paired with an opt-out `--exact` flag and a warning for fallback cases. The patch was queued for integration, but the discussion reopened when Kristofer Karlsson proposed an alternative algorithm that achieves near-exact distances without relying on generation numbers, potentially eliminating the need for flags or warnings.

The debate now centers on two competing solutions: Linus’s generation-number-based fix (simple but dependent on commit-graph freshness and performance tradeoffs) and Kristofer’s prototype (robust, no generation dependency, but more complex). Junio C Hamano and Patrick Steinhardt have endorsed Linus’s opt-out design, while Derrick Stolee has supported the proposed commit-graph write-back mechanism to amortize performance costs. Kristofer’s proposal remains unendorsed but has shifted the conversation toward algorithmic durability. The latest email from Linus reveals the root cause of the skewed timestamps: GitLab’s Marge-bot, which uses `--keep-committers` to preserve original committer dates during rebase, artificially inflating commit ages. While Linus condemns the workflow as problematic, he acknowledges the fix is still necessary, underscoring the need for a solution that handles systemic skew rather than transient clock drift. No decision has been made on the algorithmic path forward, and the commit-graph write-back implementation remains unresolved.

This thread began with Linus Torvalds submitting a one-line fix for a `git describe` regression that miscomputed commit distances when commit timestamps were non-monotonic, prioritizing commit generation numbers over unreliable dates. The patch itself is straightforward—modifying `builtin/describe.c` to use `compare_commits_by_gen_then_commit_date`—but the discussion quickly expanded into a broader conversation about ensuring commit graph freshness for correctness-critical commands while balancing performance and user expectations.

The thread has now converged on a systemic resolution. Linus, initially proposing an opt-in `--exact` flag to force accurate results via `ensure_generations_valid()`, has endorsed Patrick Steinhardt’s counterproposal to make `--exact` the default (opt-out) with a warning when the commit graph is unavailable. This approach prioritizes correctness by default, addressing the edge case where stale or missing commit graphs could reintroduce the bug. The warning mechanism remains the only unresolved detail, with questions about rate-limiting or configurability still open. Junio Hamano and Derrick Stolee’s complementary proposal to write back a fresh commit-graph after `ensure_generations_valid()`—amortizing the performance cost—remains on the table but lacks concrete implementation details. Stolee’s philosophical concern about read-only commands mutating state has not been opposed but may require guardrails (e.g., user opt-out or disk-space limits).

The patch is queued for integration, likely in `next`, with no maintainer objections. The Linux kernel’s versioning workflow, which relies on `git describe`, served as the real-world motivator for this fix. The thread’s evolution from a simple regression fix to a systemic design discussion reflects the project’s commitment to correctness, even at the cost of performance trade-offs. The next steps will involve implementing the opt-out `--exact` flag, the warning mechanism, and potentially the commit-graph write-back optimization.

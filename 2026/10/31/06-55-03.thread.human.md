This thread began with Linus Torvalds’ one-line fix for `git describe` miscomputing commit distances when commit timestamps are non-monotonic—a regression that caused real-world discrepancies in the Linux kernel’s version reporting. The discussion quickly expanded into a broader design effort to ensure the fix is both robust and user-friendly. After several iterations, the thread converged on a three-part solution: Linus’s original fix (prioritizing commit generation numbers over dates), an opt-out `--exact` flag (defaulting to on) with a warning when falling back to unreliable commit dates, and a proposed commit-graph write-back mechanism to amortize performance costs. The patch is now queued for integration in `next`, with Junio Hamano and Patrick Steinhardt having endorsed the opt-out design, and all substantive objections resolved.

Now, Kristofer Karlsson has proposed an alternative algorithm that could make the `--exact` flag largely unnecessary. His prototype avoids the eager depth-increment flaw in the current implementation by tracking two counters per tag (total commits visited and commits carrying the tag’s bit), computing depth as their difference. This approach delivers near-exact commit distances without relying on commit generation numbers, even with partial commit-graphs or skewed dates, at roughly the same performance cost as the current implementation. The prototype passes all existing tests and matches `rev-list --count` on the Linux kernel’s merge window, but adds ~120 lines of code to `builtin/describe.c`. Kristofer asks whether this approach is worth pursuing, either as a replacement for or an addition to Linus’s patch. The thread’s key participants—Linus, Junio, Patrick Steinhardt, and Derrick Stolee—have not yet responded, leaving the proposal’s fate unresolved. The trade-off is between the simplicity of Linus’s one-line fix and the robustness of Kristofer’s algorithm, which handles edge cases more gracefully but at the cost of added complexity.

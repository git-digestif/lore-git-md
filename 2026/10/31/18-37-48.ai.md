This is a bugfix patch targeting the `pack-objects` subsystem, addressing a data corruption issue when handling large blobs (≥4GiB) on 32-bit platforms. This is the second iteration of a standalone patch, incorporating feedback from Simon Richter to use `off_t` (instead of `size_t`) for tracking compressed data length, aligning with the return type of `write_reuse_object()`.

The patch modifies `builtin/pack-objects.c` to prevent truncation of large blob sizes during pack creation. On 32-bit platforms, casting `size_t` (which can represent ≥4GiB) to `unsigned long` (32-bit) previously caused the pack header to record incorrect sizes while preserving full-length compressed data, leading to corrupted objects during `git repack` or `git gc`. The fix changes the types of `size` (to `size_t`) and `datalen`/`olen` (to `off_t`) in the streaming path, ensuring accurate size tracking for both the object and its compressed data.

The change is narrowly scoped to the large-blob streaming path (`write_no_reuse_object` and `write_large_blob_data`), with no impact on the on-disk format or other pack-objects functionality. The commit message clarifies why other truncations in the codebase are unreachable (due to `core.bigFileThreshold` being `unsigned long`). No test is included, as reproducing the bug requires ≥4GiB objects on 32-bit systems, but the rationale and edge cases are well-documented.

This version addresses the feedback from v1 by adopting `off_t` for compressed data length, which is more appropriate for file offsets and matches existing patterns in the codebase. The patch remains minimal (7 lines changed) and uncontroversial, focusing on a clear correctness issue with no behavioral side effects. It should be ready for merging once reviewed.

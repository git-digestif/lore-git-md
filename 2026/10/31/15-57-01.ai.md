This is the first patch in a four-part series improving Git’s HTTP transport resilience. It fixes two low-level bugs in the existing 429-rate-limit retry logic introduced by commit 640657ffd0 (2026-03-17).

The first bug is an off-by-one in the retry counter: `http.maxRetries=1` currently performs zero retries because the counter is decremented before the loop condition is checked. The patch changes the loop to check `http_max_retries > 0 && rate_limit_retries-- > 0` and returns `HTTP_ERROR` if `http_max_retries` is zero, preventing the counter from wrapping to -1 (truthy in C) when the first request returns 401 and the re-authenticated request returns 429.

The second bug is a race in Retry-After header parsing: `CURLINFO_RETRY_AFTER` was queried after `run_one_slot()` had already called `handle_curl_result()`, which logs the still-uninitialized `retry_after` value (-1) to Trace2. The fix moves the `CURLINFO_RETRY_AFTER` extraction into `finish_active_slot()`, ensuring both `handle_curl_result()` and callers of `run_one_slot()` see the correct value.

The patch updates `t/lib-httpd/http-429.sh` to support configurable failure counts (e.g., `*-fail-2*`, `*-fail-3*`) and adds three new tests in `t/t5584-http-429-retry.sh` that verify the retry count fix, the failure threshold behavior, and the Trace2 logging correction. No new config options are introduced; the changes are purely behavioral fixes to existing functionality.

Subject: Bug report: include directives in .git/config cause silent failures

Thread type: bug report / design discussion

Core problem or goal
Git’s configuration system silently misbehaves when users manually edit `.git/config` (or other Git-managed config files) to add `[include]` directives.  The immediate symptom is that commands like `git remote` fail unpredictably, but the deeper issue is a lack of defensive parsing: Git does not reject or ignore include directives in files it controls, leading to user confusion.

Current status
No prior discussion or patch exists in this thread.  The report is exploratory; Chris Torek frames it as a minor robustness improvement rather than a critical fix.

Key technical details
- Files touched: `.git/config`, `.git/modules/*/config` (other Git-managed config files may be affected).
- Subsystems: config parsing (`config.c`), remote/branch management, include directive implementation.
- New/renamed symbols: none proposed yet.
- Behavior change: config-parsing logic would ignore or reject `[include]` sections in Git-managed files.
- On-disk format: no change; the proposal is about runtime validation.
- Test coverage: none yet; the example uses an `ed` script to demonstrate the issue.

Open questions and loose ends
- Should Git ignore `[include]` in managed config files, or should it reject them with an error?
- Are there other Git-managed config files (beyond `.git/config` and `.git/modules/*/config`) that need the same treatment?
- What is the minimal set of operations that break (e.g., `git remote`, `git branch --edit-description`)?
- Is there a risk of breaking existing workflows that rely on manual config edits, even if they are discouraged?

Participant positions
- Chris Torek (author): proposes ignoring include directives in Git-managed config files as a defensive measure.  Position is exploratory, not prescriptive.

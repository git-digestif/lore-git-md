Subject: Bug report: include directives in .git/config cause silent failures
Series version: N/A (RFC-style bug report, no patch series)
Originating author: Chris Torek
Thread type: bug report / design discussion

Core problem or goal
Git’s configuration system silently misbehaves when users manually edit `.git/config` (or other Git-managed config files) to add `[include]` directives. The immediate symptom is that commands like `git remote` fail unpredictably, but the deeper issue is a lack of defensive parsing: Git does not reject or ignore include directives in files it controls, leading to user confusion. The discussion has expanded to consider whether such usage is legitimate and should be preserved.

Current status
No patch exists; the thread remains exploratory. The original proposal (ignoring or rejecting `[include]` in Git-managed config files) is now contested due to a demonstrated real-world use case.

Key technical details
- Files touched: `.git/config`, `.git/modules/*/config` (other Git-managed config files may be affected).
- Subsystems: config parsing (`config.c`), remote/branch management, include directive implementation.
- New/renamed symbols: none proposed yet.
- Behavior change: any proposed fix must now preserve existing `[include]` functionality in `.git/config` while preventing silent failures.
- On-disk format: no change; the focus is on runtime validation or error handling.
- Test coverage: none yet; the example uses an `ed` script to demonstrate the issue.

Open questions and loose ends
- Should Git ignore `[include]` in managed config files, reject them with an error, or preserve them while improving error handling?
- Are there other Git-managed config files (beyond `.git/config` and `.git/modules/*/config`) that need the same treatment?
- What is the minimal set of operations that break (e.g., `git remote`, `git branch --edit-description`)?
- How can Git distinguish between legitimate and problematic `[include]` usage in `.git/config`?
- Is there a risk of breaking existing workflows that rely on manual config edits, even if they are discouraged?

Participant positions

Argues that such usage is legitimate and should be preserved. Review is substantive, raising a backwards-compatibility concern.

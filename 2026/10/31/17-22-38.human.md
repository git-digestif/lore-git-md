This is a **bugfix patch** targeting the sequencer subsystem, now at v2. The patch prevents `git revert`, `git cherry-pick`, and all `git rebase` backends from operating on shallow boundary commits—commits that appear as root commits due to `--depth=1` cloning but are recorded in `.git/shallow`. Such operations can accidentally delete all tracked files, so the patch adds a safeguard that refuses them by default, with a clear error message directing users to either `--unshallow` or the new `--allow-shallow-boundary` flag (available only for `revert`/`cherry-pick`; `rebase` always refuses without override).

The v2 update addresses all prior feedback by moving the check to the planning stage (during todo-list construction) via a shared helper function, ensuring no partial state is left behind if the command is refused. It also extends the safeguard to all rebase backends, including `--apply`, which doesn’t use the sequencer. The implementation is now cleaner and more user-friendly, as it fails early rather than mid-operation. Test coverage verifies refusal in shallow repos, override behavior, and edge cases like single-commit clones.

The patch touches `sequencer.c`, `sequencer.h`, `builtin/revert.c`, `builtin/rebase.c`, and the `git-revert` man page. It introduces a new CLI option (`--allow-shallow-boundary`) and two new functions (`sequencer_refuse_shallow_boundary()` and `is_shallow_boundary_commit()`). No on-disk format changes are made. The only remaining discussion point is whether to extend the safeguard to `git commit --amend`, but this patch doesn’t address that.

This looks like a well-crafted fix for a real problem. The commit message is clear, the implementation is thorough, and the test coverage is solid. The architectural shift to early checking is a meaningful improvement over v1. If you care about shallow repository safety or sequencer robustness, this patch is worth reviewing.

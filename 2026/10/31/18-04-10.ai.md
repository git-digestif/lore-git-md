This is a bugfix patch targeting the `pack-objects` subsystem, specifically addressing a data corruption issue when handling large blobs on 32-bit platforms.

The patch fixes a truncation bug in `builtin/pack-objects.c` where blob sizes exceeding 4GiB are incorrectly cast from `size_t` to `unsigned long` (which is 32 bits on affected platforms). This causes the pack header to record a truncated size while the actual compressed data remains full-length, resulting in corrupted objects. The issue manifests during `git repack` or `git gc` operations when loose large blobs are pruned, leaving only the corrupted packed copy and causing data loss. The commit message provides a clear reproduction scenario involving a 100KiB blob with a low `core.bigFileThreshold` setting.

The fix converts the relevant variables (`size`, `datalen`, and the return value of `write_large_blob_data`) from `unsigned long` to `size_t` and changes `write_no_reuse_object`'s return type to `off_t`. The patch is minimal, touching only six lines in one file, and the commit message explains why other truncations in `pack-objects` are not reachable (due to `core.bigFileThreshold` being `unsigned long`). No test is included because triggering the bug requires processing objects ≥4GiB on 32-bit platforms.

The patch appears well-motivated and technically sound, addressing a real edge case with clear consequences (data corruption). The use of `size_t` for object sizes aligns with Git's general practice, and the change is narrowly scoped to the streaming path for large blobs. This is likely to be uncontroversial and should be a straightforward merge.

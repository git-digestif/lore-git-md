Thread identity
Subject: [PATCH v2] pack-objects: fix truncation of large blob sizes on 32-bit platforms
Series version: standalone patch, v2
Originating author: Elia Pinto
Thread type: bugfix patch

Core problem or goal
Fix a data corruption bug in `git pack-objects` where blob sizes ≥4GiB are truncated when cast from `size_t` to `unsigned long` on 32-bit platforms. The pack header records the wrong size while the compressed data remains full-length, causing corrupted objects during `git repack` or `git gc` when loose large blobs are pruned.

Current status
Under review. This is the second version of the patch, addressing feedback from Simon Richter to use `off_t` for compressed data length (`datalen`/`olen`) instead of `size_t`.

Key technical details
- File touched: `builtin/pack-objects.c`
- Symbols changed: variables `size` (to `size_t`), `datalen`/`olen` (to `off_t`), and return value of `write_large_blob_data` (to `off_t`); `write_no_reuse_object` return type (to `off_t`)
- Subsystem: pack-objects streaming path for large blobs
- On-disk format: unchanged; the fix restores correct header size recording
- Test coverage: none included (requires ≥4GiB objects on 32-bit platforms)
- Rationale for `off_t`: aligns with the return type of `write_reuse_object()` and is appropriate for file offsets

Open questions and loose ends
None identified. The patch is narrowly scoped, well-motivated, and addresses a clear edge case with documented consequences. Feedback from v1 has been incorporated.

Participant positions
- **Simon Richter**: Provided feedback on v1, suggesting the use of `off_t` for `datalen`/`olen` to match existing patterns in the codebase. This feedback was incorporated in v2.

Related work
None mentioned. The bug is specific to 32-bit platforms and the large-blob streaming path in `pack-objects`. The commit message clarifies why other truncations in the codebase are unreachable (due to `core.bigFileThreshold` being `unsigned long`).

Thread identity: Subject "[PATCH v4 0/5] http: exponential backoff, configurable retry codes, POST retries", series version v4, originating author Ravi Mistry (via GitGitGadget), thread type patch series.

Core problem or goal: Address four gaps in Git's HTTP transport error handling: (1) an off-by-one retry count bug, (2) missing exponential backoff when Retry-After headers are absent, (3) inability to retry transient 5xx server errors, and (4) lack of retries for HTTP POST requests used during fetch/clone and partial clone data transfers. The goal is to improve resilience when interacting with hosting backends and reverse proxies under high concurrency.

Current status: Under review; v4 posted addressing all of Patrick Steinhardt's substantive review points from v3. Patch 2/5 specifically implements the exponential backoff mechanism. The default `http.retryAfter` value of 10 seconds remains in patch 5/5 as a separate commit, preserving the two-phase structure that Junio C Hamano previously questioned. The series awaits Junio's final review and integration.

Key technical details: Files touched: `http.c`, `http.h`, `remote-curl.c`, `git-curl-compat.h`, documentation (`git-config.txt`, `git.txt`, `Documentation/config/http.adoc`), and tests (`t/t5584-http-429-retry.sh`, `t/lib-httpd/http-429.sh`). New or renamed symbols: config key `http.retryStatusCodes` (default "429") with `GIT_HTTP_RETRY_STATUS_CODES` environment variable, exponential backoff for `http.retryAfter`, helper functions `is_retryable_http_code()`, `http_retry_wait()`, and `can_retry_rpc()`. The `attempt` parameter in `handle_rate_limit_retry()` is unsigned `size_t` representing the 1-based retry count; patch 2/5 computes the backoff wait as `http.retryAfter * 2^(attempt - 1)`, doubling the configured initial delay on each successive retry while clamping the result at `http.maxRetryTime` to avoid overflow. The call site in `http_request_recoverable()` passes `(size_t)(http_max_retries - rate_limit_retries)` as the attempt counter. An explicit Retry-After header continues to take precedence over the computed backoff, and fail-fast behavior is preserved when the configured initial `http.retryAfter` exceeds `http.maxRetryTime`. Patch 1/5 fixes two specific bugs from commit 640657ffd0: (a) in `http_request_recoverable()` the pre-decrement `--rate_limit_retries` caused `http.maxRetries=N` to perform only N-1 retries and wrapped from 0 to -1 (truthy) when `http.maxRetries=0`; the loop condition is now `http_max_retries > 0 && rate_limit_retries-- > 0` with a post-loop `http_max_retries <= 0` check returning `HTTP_ERROR` without the retries-exhausted trace; (b) `CURLINFO_RETRY_AFTER` extraction moved from `http_request()` into `finish_active_slot()` so `slot->results->retry_after` (initialized to -1, set only if `> 0`) is populated before Trace2 logging. Behavior changes: retry logic consults `http.retryStatusCodes` instead of hardcoding 429; warning messages show numeric status codes for non-429 responses; POST retries are restricted to read-only services (`git-upload-pack` and `git-upload-archive`) via the `can_retry_rpc()` whitelist, explicitly excluding `git-receive-pack` (push); when `CURLINFO_RETRY_AFTER <= 0`, the code inspects the raw `Retry-After` header via `curl_easy_header()` (guarded by `GIT_CURL_HAVE_CURL_EASY_HEADER` for libcurl >= 7.84.0) so explicit `Retry-After: 0` or past HTTP-dates trigger immediate retry while absent/malformed headers fall back to the initial delay. On-disk format: unchanged. Test coverage: `t/t5584-http-429-retry.sh` with nineteen tests plus a new push scenario test verifying `git-receive-pack` is not retried; patch 1/5 adds tests verifying `http.maxRetries=1` retries exactly once, `http.maxRetries=2` fails after three 429s but succeeds after two, and Trace2 records the actual `Retry-After` value; patch 2/5 adds three tests verifying the doubling sequence (1s, 2s, 4s), clamping at `http.maxRetryTime`, and that server headers override the computed backoff; test helper `t/lib-httpd/http-429.sh` extended with `*-fail-N*` URL patterns for multiple consecutive failures.

Open questions and loose ends: The architectural question of whether Git should support configurable retry codes at all versus forcing standardization on 429 remains unresolved at the design level, though the v4 documentation now frames non-429 codes as temporary workarounds for buggy provider infrastructure expected to return 429 when overloaded. Junio's procedural concern about the two-phase introduction of the 10-second default (patches 1-4 assume `http.retryAfter=0` while patch 5 sets the default to 10 seconds) persists as v4 retains the separate patch 5 structure. The series awaits Junio's final decision on integration.

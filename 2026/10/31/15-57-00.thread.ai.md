Thread identity
Subject: [PATCH 0/5] http: exponential backoff, configurable retry codes, POST retries
Series version: v3 (resolves default `http.retryAfter` value debate; incorporates 10-second compromise default, cosmetic documentation fixes from Junio C Hamano, and adds patch 5/5 to formalize the default)
Originating author: Ravi Mistry (via GitGitGadget)
Thread type: patch series

Core problem or goal
Address four gaps in Git's HTTP transport error handling: (1) an off-by-one retry count bug, (2) missing exponential backoff when Retry-After headers are absent, (3) inability to retry transient 5xx server errors, and (4) lack of retries for HTTP POST requests (used during fetch/clone and partial clone data transfers). The goal is to improve resilience when interacting with hosting backends and reverse proxies under high concurrency.

Current status
Under review; v3 posted with all substantive feedback addressed, including the resolved default `http.retryAfter` value (10 seconds) and cosmetic documentation fixes. The series is technically complete and awaits Junio's final review and integration. The primary blocker (default `http.retryAfter` value) is resolved via compromise: 10 seconds (exponential backoff: 10s, 20s, 40s, ...) balances server protection (brian m. carlson's priority) and interactive usability (Ravi Mistry's concern). The opt-in design for 5xx retries and POST retries remains unchanged. Junio raised a procedural concern about the two-phase introduction of the default value: patches 1-4 assume `http.retryAfter=0` (no initial delay), while patch 5 retroactively sets the default to 10 seconds. Ravi has now offered two options to resolve this: (1) keep v3 as-is with patch 5/5 separate, or (2) fold the default value change into patch 2 in a v4. Patrick Steinhardt has provided substantive review of patches 1/5, 2/5, 3/5, and 4/5, raising questions about commit organization, error-code semantics, and implementation details on the first two, challenging the architectural decision in patch 3/5 to make retryable status codes user-configurable via `http.retryStatusCodes`, raising a correctness objection on patch 4/5 that POST retries must not apply to non-idempotent operations such as push, and now questioning on patch 5/5 whether an explicit `Retry-After: 0` header is honored or ignored in favor of the new 10-second default.

Key technical details
Files touched: `http.c`, `http.h`, `remote-curl.c`, documentation (`git-config.txt`, `git.txt`, `Documentation/config/http.adoc`), and tests (`t/t5584-http-429-retry.sh`, `t/lib-httpd/http-429.sh`).
New or renamed symbols: config key `http.retryStatusCodes` (default "429"), exponential backoff behavior for `http.retryAfter` (now the *initial* delay when Retry-After is missing, defaulting to **10 seconds**), helper functions `is_retryable_http_code()` and `http_retry_wait()`. The `attempt` parameter in `handle_rate_limit_retry()` tracks retry count for exponential backoff calculation (`http.retryAfter * 2^(attempt - 1)`).
Behavior changes: retry logic now consults `http.retryStatusCodes` (comma- or whitespace-separated list of 400-599 codes) instead of hardcoding 429; warning messages show numeric status codes (e.g., "HTTP 502") for non-429 responses while preserving "rate limited" phrasing for 429; backoff timing doubles on each retry (10s, 20s, 40s, ...) while clamping at `http.maxRetryTime`. Patch 1 fixes an off-by-one retry counter (loop now checks `http_max_retries > 0 && rate_limit_retries-- > 0`) and a race in Retry-After header parsing (moved `CURLINFO_RETRY_AFTER` extraction into `finish_active_slot()`, initializing `slot->results->retry_after = -1` first). The removal of the early-return guard clause in the retry loop is intentional, as the new loop condition now handles the zero-retry case uniformly, including scenarios where re-authentication triggers a 429 after an initial 401. Patch 2 introduces exponential backoff for retries when Retry-After headers are absent, using `http.retryAfter` as the initial delay (default 10s) and `http_max_retries - rate_limit_retries` as the attempt counter (avoiding a new variable). Patch 3 makes retryable status codes configurable via `http.retryStatusCodes`, defaulting to 429, with the `400 <= code < 600` range check relocated to the top of `is_retryable_http_code()` for clarity, and adds environment variable support (`GIT_HTTP_RETRY_STATUS_CODES`). Patch 4 extends retry logic to HTTP POST requests by extracting retry wait logic into `http_retry_wait()` and applying it to both `probe_rpc()` and `post_rpc()`, ensuring the "Content-Encoding: gzip" header is re-attached when retrying compressed requests. Patch 5/5 explicitly sets the default value of `http.retryAfter` to 10 seconds in the config machinery, updates documentation to remove the word "configured" (since the default can now exceed `http.maxRetryTime` even when not explicitly set), and adjusts test expectations to verify fallback to the 10-second default when Retry-After HTTP-dates are in the past. The test suite now includes a case where `http.retryAfter` (10s) exceeds a lowered `http.maxRetryTime` (9s), triggering an immediate failure with a clear error message. Patrick Steinhardt has questioned whether patch 5/5 correctly handles an explicit `Retry-After: 0` header value, arguing it should take precedence over the 10-second default to allow servers to signal immediate retry.
On-disk format: unchanged.
Test coverage: new test script `t/t5584-http-429-retry.sh` (nineteen tests: three from patch 1 for retry count, failure threshold, and Trace2 logging; three from patch 2 for doubling behavior, clamping, and Retry-After override; five from patch 3 verifying 5xx defaults, configured retries, Retry-After for 503, exhausted retry reporting, and environment/URL-specific config; eight from patches 4 and 5 verifying POST retries for 429/502, partial-clone blob fetches surviving 502s, gzipped POST header preservation, explicit default `http.retryAfter` value, and fallback behavior for past Retry-After HTTP-dates).

Open questions and loose ends
The procedural concern about the two-phase introduction of the default `http.retryAfter` value remains a discussion point. Ravi has proposed two options: (1) retain the current v3 structure (patches 1-4 assume `http.retryAfter=0`, patch 5 sets it to 10s), or (2) fold the default value change into patch 2 in a v4. Junio and brian m. carlson are invited to express a preference. Patrick Steinhardt has raised unaddressed review points on patch 1/5: (1) whether the off-by-one counter fix and the Retry-After race fix should be split into separate commits; (2) whether `results->retry_after` should be typed as `curl_off_t` rather than `long`; and (3) whether the zero-retry case (`http_max_retries <= 0`) should return `HTTP_RATE_LIMITED` rather than `HTTP_ERROR`, since the request is still rate-limited and only the Trace2 "retries-exhausted" message should be skipped. On patch 2/5, Patrick additionally raised three points: (1) suggest adding jitter to the backoff calculation (sensible but not required); (2) the `attempt` parameter is typed as signed `int` when an unsigned type would be more appropriate for a counter; and (3) the doubling logic implemented as a `for` loop could be expressed more directly as a single `MIN(http_max_retry_time, delay * (2 << (attempt - 1)))` calculation rather than an iterative loop. On patch 3/5, Patrick has raised a substantive architectural objection to the configurable `http.retryStatusCodes` design, arguing that accepting any 400-599 code perpetuates ecosystem fragmentation where providers tell users they are misconfigured, and suggesting instead that Git should drive provider convergence on 429 as the sole retryable code so the feature works out of the box; he leaves open whether the author should reconsider hardcoding 429 only. On patch 4/5, Patrick has raised a significant correctness objection: POST requests are not necessarily idempotent, and the patch applies retries uniformly to all `post_rpc()` calls without distinguishing request types; he specifically notes that `push_git()` uses `post_rpc()` to send data to `git-receive-pack(1)`, and retrying such a request could result in duplicate or corrupted pack data being sent to the server, so the implementation must restrict retries to safe request types (fetch, clone, partial-clone blob downloads) and exclude push operations. On patch 5/5, Patrick has raised a new edge-case question: whether the implementation ignores an explicit `Retry-After: 0` header, arguing that such a value should be honored so a server can instruct the client to retry immediately rather than waiting out the 10-second default; this concerns the precedence between the server-provided header and the configured `http.retryAfter` default in the `CURLINFO_RETRY_AFTER` parsing logic. The 10-second default itself is uncontested, and all other feedback has been addressed.

Related work
Prior proposals in 2020 and 2024 (linked in cover letter) addressed subsets of these issues but did not result in merged code. Patch 1 references commit 640657ffd0 (2026-03-17), which introduced the original 429 retry logic. The exponential backoff behavior matches curl's `--retry` semantics, though with a longer initial delay (10s vs. curl's 1s). The new email confirms the off-by-one and Retry-After race fixes in patch 1, providing additional context on the loop condition change and the initialization of `slot->results->retry_after`. The doubling logic in patch 2 aligns with curl's retry semantics but uses a longer initial delay (10s) to account for Git's heavier requests. Patch 3's configurable retry codes extend the design to support 5xx errors, addressing real-world scenarios where load balancers or hosting backends return transient 5xx responses; however, Patrick Steinhardt now argues this configurability may hinder provider convergence on 429. The opt-in design (defaulting to 429) avoids controversy while enabling users to configure retries for 5xx errors when needed, though Patrick favors removing this flexibility. Patch 4's POST retry logic is well-motivated by the volume of data transferred via POST during fetch/clone and partial-clone operations, and the implementation consolidates retry timing logic into `http_retry_wait()` while preserving gzipped request headers, though Patrick now objects that this must not apply to non-idempotent push operations. Patch 5/5 formalizes the 10-second default for `http.retryAfter`, though Patrick now questions whether `Retry-After: 0` headers are properly honored over this default.

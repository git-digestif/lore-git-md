Thread identity
Subject: [PATCH 0/4] http: exponential backoff, configurable retry codes, POST retries
Series version: v2 (addresses all feedback from Junio C Hamano on v1, including retry-loop guard clause clarification, exponential backoff attempt counting, and `http.retryStatusCodes` documentation and implementation refinements; now proposing `http.retryAfter=1` as a compromise default)
Originating author: Ravi Mistry (via GitGitGadget)
Thread type: patch series

Core problem or goal
Address four gaps in Git’s HTTP transport error handling: (1) an off-by-one retry count bug, (2) missing exponential backoff when Retry-After headers are absent, (3) inability to retry transient 5xx server errors, and (4) lack of retries for HTTP POST requests (used during fetch/clone and partial clone data transfers). The goal is to improve resilience when interacting with hosting backends and reverse proxies under high concurrency.

Current status
Under review; v2 posted in response to Junio C Hamano’s feedback on v1. All four patches now incorporate Junio’s design, documentation, and implementation suggestions, including the refactoring of retry-wait logic into `http_retry_wait()` in patch 4/4, the clarification of the retry-loop guard clause removal in patch 1/4, the reuse of `rate_limit_retries` for exponential backoff attempt counting in patch 2/4, and the relocation of the `400 <= code < 600` range check to the top of `is_retryable_http_code()` in patch 3/4. Documentation for `http.retryAfter`, `http.maxRetries`, and `http.maxRetryTime` now explicitly references `http.retryStatusCodes` and restores the "Too Many Requests" explanatory text for 429. Junio C Hamano’s latest surface-level review on patch 3/4 raises no technical concerns, instead focusing on minor documentation formatting and stylistic suggestions for `http.retryAfter` phrasing and config variable markup consistency. The series is polished and awaits maintainer decision on three unresolved questions: the default 5xx retry behavior (currently opt-in via config), the default value of `http.retryAfter` (now contested by brian m. carlson and proposed as a compromise of 1 second by Ravi Mistry), and the minor documentation formatting consistency noted by Junio.

Key technical details
Files touched: `http.c`, `remote-curl.c`, documentation (`git-config.txt`, `git.txt`, `Documentation/config/http.adoc`), and tests (`t/t5584-http-429-retry.sh`, `t/lib-httpd/http-429.sh`).
New or renamed symbols: config key `http.retryStatusCodes` (default "429"), exponential backoff behavior for `http.retryAfter` (now the *initial* delay when Retry-After is missing), helper functions `is_retryable_http_code()` and `http_retry_wait()`.
Behavior changes: retry logic now consults `http.retryStatusCodes` (comma- or whitespace-separated list of 400–599 codes) instead of hardcoding 429; warning messages show numeric status codes (e.g., "HTTP 502") for non-429 responses while preserving "rate limited" phrasing for 429; backoff timing doubles on each retry (1s, 2s, 4s, …) while clamping at `http.maxRetryTime`. Patch 1 fixes an off-by-one retry counter (loop now checks `http_max_retries > 0 && rate_limit_retries-- > 0`) and a race in Retry-After header parsing (moved `CURLINFO_RETRY_AFTER` extraction into `finish_active_slot()`, initializing `slot->results->retry_after = -1` first). The removal of the early-return guard clause in the retry loop is intentional, as the new loop condition now handles the zero-retry case uniformly, including scenarios where re-authentication triggers a 429 after an initial 401. Patch 2 introduces exponential backoff for retries when Retry-After headers are absent, using `http.retryAfter` as the initial delay and `http_max_retries - rate_limit_retries` as the attempt counter (avoiding a new variable). Patch 3 makes retryable status codes configurable via `http.retryStatusCodes`, defaulting to 429, with the `400 <= code < 600` range check relocated to the top of `is_retryable_http_code()` for clarity, and adds environment variable support (`GIT_HTTP_RETRY_STATUS_CODES`). Patch 4 extends retry logic to HTTP POST requests by extracting retry wait logic into `http_retry_wait()` and applying it to both `probe_rpc()` and `post_rpc()`, ensuring the "Content-Encoding: gzip" header is re-attached when retrying compressed requests.
On-disk format: unchanged.
Test coverage: new test script `t/t5584-http-429-retry.sh` (fifteen tests: three from patch 1 for retry count, failure threshold, and Trace2 logging; three from patch 2 for doubling behavior, clamping, and Retry-After override; five from patch 3 verifying 5xx defaults, configured retries, Retry-After for 503, exhausted retry reporting, and environment/URL-specific config; four from patch 4 verifying POST retries for 429/502, partial-clone blob fetches surviving 502s, and gzipped POST header preservation) and expanded helper `t/lib-httpd/http-429.sh` (configurable failure counts and 502/503/504 simulation).

Open questions and loose ends
- Whether the default set of retryable status codes should include 5xx errors (currently opt-in via config).
- The default value of `http.retryAfter` (now contested: Ravi Mistry proposes 1 second as a compromise between the original 0 and brian m. carlson’s suggested 30 seconds).
- Minor documentation formatting consistency (variable name markup in `Documentation/config/http.adoc`) noted by Junio in the latest review, though this is cosmetic and unrelated to the patch’s core functionality.

Raised design, documentation, and implementation questions, all of which are addressed in v2, including the clarification on the retry-loop guard clause removal, the reuse of `rate_limit_retries` for exponential backoff attempt counting, the relocation of the `400 <= code < 600` range check to the top of `is_retryable_http_code()`, and the documentation refinements for `http.retryAfter`, `http.maxRetries`, and `http.maxRetryTime`. - **Ravi Mistry**: Author. Engaged constructively with Junio’s feedback, incorporating clarifications, documentation improvements, and implementation refinements in v2. Proposes `http.retryAfter=1` as a compromise default to balance fast recovery (prioritized in v1) with server protection (raised by brian m. carlson). Maintains the opt-in design for 5xx retries.
- **brian m. carlson**: Substantive review challenging the default `http.retryAfter=0` behavior. Argues that even 429 responses should trigger a non-zero initial delay (e.g., 30 seconds) to avoid overwhelming rate-limited servers. Position is based on server-operator experience and prioritizes server protection over fast recovery. No alternative implementation proposed; resolution may require broader input.

Related work

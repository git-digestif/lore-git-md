Core problem or goal: Address four gaps in Git's HTTP transport error handling: (1) an off-by-one retry count bug, (2) missing exponential backoff when Retry-After headers are absent, (3) inability to retry transient 5xx server errors, and (4) lack of retries for HTTP POST requests used during fetch/clone and partial clone data transfers. The goal is to improve resilience when interacting with hosting backends and reverse proxies under high concurrency.

Key technical details: Files touched: `http.c`, `http.h`, `remote-curl.c`, `git-curl-compat.h`, documentation (`git-config.txt`, `git.txt`, `Documentation/config/http.adoc`), and tests (`t/t5584-http-429-retry.sh`, `t/lib-httpd/http-429.sh`). New or renamed symbols: config key `http.retryStatusCodes` (default "429") with `GIT_HTTP_RETRY_STATUS_CODES` environment variable, exponential backoff for `http.retryAfter` (default now 10 seconds), helper functions `is_retryable_http_code()`, `can_retry_rpc()`, `report_rpc_error()`, `http_retry_wait(long http_code, long slot_retry_after, size_t attempt)`, and `has_zero_or_past_retry_after()`. The `attempt` parameter in `handle_rate_limit_retry()` is unsigned `size_t` representing the 1-based retry count; patch 2/5 computes the backoff wait as `http.retryAfter * 2^(attempt - 1)`, doubling the configured initial delay on each successive retry while clamping the result at `http.maxRetryTime` to avoid overflow via the guard `if (delay >= http_max_retry_time - delay)` before doubling. The call site in `http_request_recoverable()` passes `(size_t)(http_max_retries - rate_limit_retries)` as the attempt counter. Patch 4/5 extracts the wait-and-sleep logic from `http_request_recoverable()` into the shared helper `http_retry_wait()` in `http.c` (declared in `http.h`), which both the GET path and the new POST retry loop in `post_rpc()` now call. An explicit Retry-After header continues to take precedence over the computed backoff, and fail-fast behavior is preserved when the configured initial `http.retryAfter` exceeds `http.maxRetryTime`. Patch 1/5 fixes two specific bugs from commit 640657ffd0: (a) in `http_request_recoverable()` the pre-decrement `--rate_limit_retries` caused `http.maxRetries=N` to perform only N-1 retries and wrapped from 0 to -1 (truthy) when `http.maxRetries=0`; the loop condition is now `http_max_retries > 0 && rate_limit_retries-- > 0` with a post-loop `http_max_retries <= 0` check returning `HTTP_ERROR` without the retries-exhausted trace; (b) `CURLINFO_RETRY_AFTER` extraction moved from `http_request()` into `finish_active_slot()` so `slot->results->retry_after` (initialized to -1, set only if `> 0`) is populated before Trace2 logging. Patch 3/5 adds `is_retryable_http_code()`, which parses the comma- or whitespace-separated `http.retryStatusCodes` list and checks membership only for status codes constrained to the 400..599 range; `handle_curl_result()` calls this helper instead of hardcoding 429. `http_request_recoverable()` keeps generic "rate limited" wording only for 429 and otherwise prints "HTTP <code>, waiting <N> seconds before retry"; exhausted retries on a non-429 configured code return `HTTP_ERROR` rather than `HTTP_RATE_LIMITED`. `struct http_get_options` in `http.h` gains `long http_code`, populated by `http_request()` so downstream retry logic can distinguish the specific status. Configuration is read in `http_options()` and initialized from the environment in `http_init()`. Patch 4/5 adds a retry loop to `post_rpc()` in `remote-curl.c` gated by `can_retry_rpc()`, which whitelists only `git-upload-pack` and `git-upload-archive` (fetch/clone and partial-clone lazy blob fetches) and explicitly excludes `git-receive-pack` (push) because retrying a non-idempotent push after a 502/504 risks duplicate processing on the remote. Error reporting is deferred: the old inline `error("RPC failed; ...")` inside `run_slot()` moves to `report_rpc_error()` that fires only after retries are exhausted or for non-retryable failures. The patch also fixes a gzip regression by re-appending the `Content-Encoding: gzip` header when retrying a compressed request. Patch 5/5 changes the default `http.retryAfter` from 0 to 10 seconds and adds `has_zero_or_past_retry_after()` in `http.c`, which inspects the raw `Retry-After` response header via `curl_easy_header()` whenever `CURLINFO_RETRY_AFTER` returns zero or negative; this inspection is guarded by the new `GIT_CURL_HAVE_CURL_EASY_HEADER` macro in `git-curl-compat.h` defined for libcurl >= 7.84.0. When the raw header indicates zero or a past date, `finish_active_slot()` sets `slot->results->retry_after = 0`, enabling immediate retry rather than the 10-second default. The error message emitted when `http.retryAfter` exceeds `http.maxRetryTime` drops the word "configured" since the value may now be the default. Behavior changes: retry logic consults `http.retryStatusCodes` instead of hardcoding 429; warning messages show numeric status codes for non-429 responses; POST retries are restricted to read-only services via the `can_retry_rpc()` whitelist; when `CURLINFO_RETRY_AFTER <= 0`, the code inspects the raw `Retry-After` header via `curl_easy_header()` (guarded by `GIT_CURL_HAVE_CURL_EASY_HEADER` for libcurl >= 7.84.0) so explicit `Retry-After: 0` or past HTTP-dates trigger immediate retry while absent/malformed headers fall back to the initial delay; read-only POST requests now sleep and retry using the same exponential backoff as GET requests when `http.maxRetries > 0` and the status code is in `http.retryStatusCodes`, while push POSTs remain fail-fast; with no `Retry-After` header and `http.maxRetries` enabled, Git now waits 10 seconds before the first retry and doubles on each subsequent attempt (10s, 20s, 40s, capped at `http.maxRetryTime`). On-disk format: unchanged. Test coverage: `t/t5584-http-429-retry.sh` with prior tests plus new scenarios; patch 1/5 adds tests verifying `http.maxRetries=1` retries exactly once, `http.maxRetries=2` fails after three 429s but succeeds after two, and Trace2 records the actual `Retry-After` value; patch 2/5 adds three tests verifying the doubling sequence (1s, 2s, 4s), clamping at `http.maxRetryTime`, and that server headers override the computed backoff; patch 3/5 adds five tests verifying that 502/503/504 are not retried by default, that configured codes are retried with appropriate warning messages, that `Retry-After` headers are honored for non-429 codes, that exhausted retries on a 502 report the actual error code rather than "rate limited", and that both `GIT_HTTP_RETRY_STATUS_CODES` and `http.<url>.retryStatusCodes` urlmatch work correctly; patch 4/5 adds four tests covering protocol v2 `git-upload-pack` POSTs retrying 429 and configured 502s (with correct warning messages and no "RPC failed" on success), partial-clone promisor lazy blob fetches retrying 502, gzipped POSTs preserving `Content-Encoding: gzip` across retries (verified via `GIT_TRACE_CURL` line counts), and confirmation that `git push` (`git-receive-pack`) is never retried on 429 or 502; patch 5/5 updates tests to explicitly set `http.retryAfter 0` where immediate retries are needed and adds tests verifying the new 10-second default (by setting `http.maxRetryTime 9` and confirming the fail-fast error mentions 10 > 9) and that `Retry-After: 0` still triggers immediate retry under libcurl >= 7.84.0. Test helper `t/lib-httpd/http-429.sh` is extended with `*-fail-N*` URL patterns for multiple consecutive failures, `*-status-502*`, `*-status-503*`, or `*-status-504*` URL patterns to emit those status lines, and `*-post-only*` URL patterns that only fail on POST requests (with draining of POST bodies before returning synthetic errors to avoid Apache connection resets).

Open questions and loose ends: The architectural question of whether Git should support configurable retry codes at all versus forcing standardization on 429 remains unresolved at the design level, though the v4 documentation now frames non-429 codes as temporary workarounds for buggy provider infrastructure expected to return 429 when overloaded. Junio's procedural concern about the two-phase introduction of the 10-second default (patches 1-4 assume `http.retryAfter=0` while patch 5 sets the default to 10 seconds) persists as v4 retains the separate patch 5 structure. Junio's review of patch 3/5 raised two substantive edge-case observations that remain open pending v5: (1) setting `http.retryStatusCodes` to an empty string disables all retries rather than restoring the default 429-only behavior, which needs documentation plus a new test case for the empty-string configuration; (2) 401 and 404 responses will never be retried even if explicitly listed in the config, because `handle_curl_result()` checks `missing_target()` and 401 before consulting `is_retryable_http_code()`, an ordering constraint that limits which codes are actually retryable regardless of configuration and also needs documentation. Junio's review of patch 4/5 raised one open edge-case question that has now been acknowledged by the author: the `struct slot_results results` variable in `post_rpc()` is initialized once at function entry but not reset before the `goto retry` loop; if `run_one_slot()` returns early because `start_active_slot()` fails (a path that skips `finish_active_slot()`), `results` would retain stale values from the previous attempt, potentially causing `report_rpc_error()` to misreport the HTTP code or retry-after value. Ravi Mistry has confirmed this does not affect retry behavior because `HTTP_START_FAILED` is never retried, and has committed to clearing `results` before each `run_one_slot()` call in both `post_rpc()` and `probe_rpc()` in v5.

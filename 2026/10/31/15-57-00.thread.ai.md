Subject: [PATCH 0/5] http: exponential backoff, configurable retry codes, POST retries
Series version: v3 (resolves default `http.retryAfter` value debate; incorporates 10-second compromise default, cosmetic documentation fixes from Junio C Hamano, and adds patch 5/5 to formalize the default)
Originating author: Ravi Mistry (via GitGitGadget)
Thread type: patch series

Core problem or goal
Address four gaps in Git's HTTP transport error handling: (1) an off-by-one retry count bug, (2) missing exponential backoff when Retry-After headers are absent, (3) inability to retry transient 5xx server errors, and (4) lack of retries for HTTP POST requests (used during fetch/clone and partial clone data transfers). The goal is to improve resilience when interacting with hosting backends and reverse proxies under high concurrency.

Current status
Under review; v3 posted with all substantive feedback addressed, including the resolved default `http.retryAfter` value (10 seconds) and cosmetic documentation fixes. The series is technically complete and awaits Junio's final review and integration. The primary blocker (default `http.retryAfter` value) is resolved via compromise: 10 seconds (exponential backoff: 10s, 20s, 40s, ...) balances server protection (brian m. carlsson's priority) and interactive usability (Ravi Mistry's concern). The opt-in design for 5xx retries and POST retries remains unchanged. Junio raised a procedural concern about the two-phase introduction of the default value: patches 1-4 assume `http.retryAfter=0` (no initial delay), while patch 5 retroactively sets the default to 10 seconds. Ravi has offered two options to resolve this: (1) keep v3 as-is with patch 5/5 separate, or (2) fold the default value change into patch 2 in a v4.

Key technical details
Files touched: `http.c`, `http.h`, `remote-curl.c`, documentation (`git-config.txt`, `git.txt`, `Documentation/config/http.adoc`), and tests (`t/t5584-http-429-retry.sh`, `t/lib-httpd/http-429.sh`).
New or renamed symbols: config key `http.retryStatusCodes` (default "429"), exponential backoff behavior for `http.retryAfter` (now the *initial* delay when Retry-After is missing, defaulting to **10 seconds**), helper functions `is_retryable_http_code()` and `http_retry_wait()`. The `attempt` parameter in `handle_rate_limit_retry()` tracks retry count for exponential backoff calculation (`http.retryAfter * 2^(attempt - 1)`); Ravi has committed to changing its type from signed `int` to unsigned `size_t` in v4.
Behavior changes: retry logic now consults `http.retryStatusCodes` (comma- or whitespace-separated list of 400-599 codes) instead of hardcoding 429; warning messages show numeric status codes (e.g., "HTTP 502") for non-429 responses while preserving "rate limited" phrasing for 429; backoff timing doubles on each retry (10s, 20s, 40s, ...) while clamping at `http.maxRetryTime`. Patch 1 fixes an off-by-one retry counter (loop now checks `http_max_retries > 0 && rate_limit_retries-- > 0`) and a race in Retry-After header parsing (moved `CURLINFO_RETRY_AFTER` extraction into `finish_active_slot()`, initializing `slot->results->retry_after = -1` first). Patch 2 introduces exponential backoff for retries when Retry-After headers are absent, using `http.retryAfter` as the initial delay (default 10s) and an iterative loop for doubling to avoid undefined bit-shift behavior and multiplication overflow that a direct `MIN(http_max_retry_time, delay * (2 << (attempt - 1)))` expression could produce with large `http.maxRetries` values. Patch 3 makes retryable status codes configurable via `http.retryStatusCodes`. Patch 4 extends retry logic to HTTP POST requests by extracting retry wait logic into `http_retry_wait()`. Patch 5/5 explicitly sets the default value of `http.retryAfter` to 10 seconds in the config machinery.
On-disk format: unchanged.
Test coverage: new test script `t/t5584-http-429-retry.sh` (nineteen tests covering retry count, failure threshold, Trace2 logging, doubling behavior, clamping, Retry-After override, 5xx defaults, configured retries, POST retries, gzipped POST header preservation, and fallback behavior). Ravi has committed to adding a test case in v4 covering the push scenario to ensure `git-receive-pack` is not retried.

Open questions and loose ends
The procedural concern about the two-phase introduction of the default `http.retryAfter` value remains a discussion point (options: keep v3 structure or fold into patch 2 in v4). On patch 1/5, Patrick Steinhardt's point about `results->retry_after` typing (`curl_off_t` vs `long`) remains unaddressed; Ravi has defended the single-commit approach and the `HTTP_ERROR` return for zero-retry case, and acknowledged a `case` indentation nit for v4. On patch 2/5, Ravi has now addressed two of Patrick's three points: committed to changing `attempt` to unsigned `size_t` in v4, and defended the iterative loop over a single-expression calculation to avoid undefined behavior with large retry counts; the third point (adding jitter) remains unaddressed but was noted as sensible yet not required. On patch 3/5, Patrick's architectural objection to configurable `http.retryStatusCodes` (favoring ecosystem convergence on 429 only) remains open but is now actively debated: Ravi counters that 429 (deliberate rate limiting) and 5xx codes (transient reverse proxy timeouts, CDN failures, or temporary server overload) are semantically distinct, and that retrying 5xx by default could be unsafe where a 5xx indicates a permanently broken proxy; the defended compromise keeps 429 as the sole default but allows CI systems and administrators to opt in centrally via `http.retryStatusCodes` for environments where 5xx responses are known transient. On patch 4/5, Patrick's correctness objection that POST retries must not apply to non-idempotent operations such as push (`push_git()` via `post_rpc()`) has been accepted by Ravi, who commits to restricting v4 retries to read-only services only (`git-upload-pack` for fetch/clone and `git-upload-archive`), explicitly excluding `git-receive-pack` (push), and adding a test for the push scenario. On patch 5/5, Patrick's question about whether explicit `Retry-After: 0` headers are honored over the 10-second default has been resolved: Ravi accepted the point and committed to a v4 fix that inspects the raw `Retry-After` header when `CURLINFO_RETRY_AFTER <= 0`, so that an explicit `Retry-After: 0` or past HTTP-date triggers an immediate retry while absent or malformed headers still fall back to the 10-second default. The 10-second default itself is uncontested.

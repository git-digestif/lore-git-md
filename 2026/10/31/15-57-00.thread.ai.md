Subject: [PATCH 0/4] http: exponential backoff, configurable retry codes, POST retries
Series version: v2 (addresses Junio’s feedback from v1)
Originating author: Ravi Mistry (via GitGitGadget)
Thread type: patch series

Core problem or goal
Address four gaps in Git’s HTTP transport error handling: (1) an off-by-one retry count bug, (2) missing exponential backoff when Retry-After headers are absent, (3) inability to retry transient 5xx server errors, and (4) lack of retries for HTTP POST requests (used during fetch/clone and partial clone data transfers). The goal is to improve resilience when interacting with hosting backends and reverse proxies under high concurrency.

Current status
Under review; v2 posted in response to Junio C Hamano’s feedback on v1. All four patches now incorporate Junio’s design, documentation, and implementation suggestions, including the refactoring of retry-wait logic into `http_retry_wait()` in patch 4/4. The series is polished, with clearer documentation and more maintainable code, but still awaits further review or maintainer decision on the unresolved question of default 5xx retry behavior.

Key technical details
Files touched: `http.c`, `remote-curl.c`, documentation (`git-config.txt`, `git.txt`, `Documentation/config/http.adoc`), and tests (`t/t5584-http-429-retry.sh`, `t/lib-httpd/http-429.sh`).
New or renamed symbols: config key `http.retryStatusCodes` (default "429"), exponential backoff behavior for `http.retryAfter` (now the *initial* delay when Retry-After is missing), helper functions `is_retryable_http_code()` and `http_retry_wait()`.
Behavior changes: retry logic now consults `http.retryStatusCodes` (comma- or whitespace-separated list of 400–599 codes) instead of hardcoding 429; warning messages show numeric status codes (e.g., "HTTP 502") for non-429 responses while preserving "rate limited" phrasing for 429; backoff timing doubles on each retry (1s, 2s, 4s, …) while clamping at `http.maxRetryTime`. Patch 1 fixes an off-by-one retry counter (loop now checks `http_max_retries > 0 && rate_limit_retries-- > 0`) and a race in Retry-After header parsing (moved `CURLINFO_RETRY_AFTER` extraction into `finish_active_slot()`, initializing `slot->results->retry_after = -1` first). Patch 2 introduces exponential backoff for retries when Retry-After headers are absent, using `http.retryAfter` as the initial delay and `http_max_retries - rate_limit_retries` as the attempt counter. Patch 3 makes retryable status codes configurable via `http.retryStatusCodes`, defaulting to 429, with the `400 <= code < 600` range check relocated to the top of `is_retryable_http_code()` for clarity, and adds environment variable support (`GIT_HTTP_RETRY_STATUS_CODES`). Patch 4 extends retry logic to HTTP POST requests by extracting retry wait logic into `http_retry_wait()` and applying it to both `probe_rpc()` and `post_rpc()`, ensuring the "Content-Encoding: gzip" header is re-attached when retrying compressed requests.
On-disk format: unchanged.
Test coverage: new test script `t/t5584-http-429-retry.sh` (fifteen tests: three from patch 1 for retry count, failure threshold, and Trace2 logging; three from patch 2 for doubling behavior, clamping, and Retry-After override; five from patch 3 verifying 5xx defaults, configured retries, Retry-After for 503, exhausted retry reporting, and environment/URL-specific config; four from patch 4 verifying POST retries for 429/502, partial-clone blob fetches surviving 502s, and gzipped POST header preservation) and expanded helper `t/lib-httpd/http-429.sh` (configurable failure counts and 502/503/504 simulation).

Open questions and loose ends
- Whether the default set of retryable status codes should include 5xx errors (currently opt-in via config).
- The unification of `http.maxRetryTime` handling (capping vs. failing) remains unresolved, though Junio’s v1 concerns about exponential backoff behavior are now addressed in v2 by using `http_max_retries - rate_limit_retries` as the attempt counter and improving documentation.

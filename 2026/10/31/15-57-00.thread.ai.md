Subject: [PATCH 0/4] http: exponential backoff, configurable retry codes, POST retries
Series version: v3 (resolves default `http.retryAfter` value debate; incorporates 10-second compromise default, cosmetic documentation fixes from Junio C Hamano)

Core problem or goal
Address four gaps in Git’s HTTP transport error handling: (1) an off-by-one retry count bug, (2) missing exponential backoff when Retry-After headers are absent, (3) inability to retry transient 5xx server errors, and (4) lack of retries for HTTP POST requests (used during fetch/clone and partial clone data transfers). The goal is to improve resilience when interacting with hosting backends and reverse proxies under high concurrency.

Current status
Under review; v3 to be posted with the resolved default `http.retryAfter` value (10 seconds) and any remaining cosmetic documentation fixes. All substantive feedback from Junio C Hamano and brian m. carlson is now addressed. The series is technically complete and awaits Junio’s final review and integration. The primary blocker (default `http.retryAfter` value) is resolved via compromise: 10 seconds (exponential backoff: 10s, 20s, 40s, ...) balances server protection (brian m. carlson’s priority) and interactive usability (Ravi Mistry’s concern). The opt-in design for 5xx retries and POST retries remains unchanged.

Key technical details
Files touched: `http.c`, `remote-curl.c`, documentation (`git-config.txt`, `git.txt`, `Documentation/config/http.adoc`), and tests (`t/t5584-http-429-retry.sh`, `t/lib-httpd/http-429.sh`).
New or renamed symbols: config key `http.retryStatusCodes` (default "429"), exponential backoff behavior for `http.retryAfter` (now the *initial* delay when Retry-After is missing, defaulting to **10 seconds**), helper functions `is_retryable_http_code()` and `http_retry_wait()`.
Behavior changes: retry logic now consults `http.retryStatusCodes` (comma- or whitespace-separated list of 400–599 codes) instead of hardcoding 429; warning messages show numeric status codes (e.g., "HTTP 502") for non-429 responses while preserving "rate limited" phrasing for 429; backoff timing doubles on each retry (10s, 20s, 40s, …) while clamping at `http.maxRetryTime`. Patch 1 fixes an off-by-one retry counter (loop now checks `http_max_retries > 0 && rate_limit_retries-- > 0`) and a race in Retry-After header parsing (moved `CURLINFO_RETRY_AFTER` extraction into `finish_active_slot()`, initializing `slot->results->retry_after = -1` first). The removal of the early-return guard clause in the retry loop is intentional, as the new loop condition now handles the zero-retry case uniformly, including scenarios where re-authentication triggers a 429 after an initial 401. Patch 2 introduces exponential backoff for retries when Retry-After headers are absent, using `http.retryAfter` as the initial delay (default 10s) and `http_max_retries - rate_limit_retries` as the attempt counter (avoiding a new variable). Patch 3 makes retryable status codes configurable via `http.retryStatusCodes`, defaulting to 429, with the `400 <= code < 600` range check relocated to the top of `is_retryable_http_code()` for clarity, and adds environment variable support (`GIT_HTTP_RETRY_STATUS_CODES`). Patch 4 extends retry logic to HTTP POST requests by extracting retry wait logic into `http_retry_wait()` and applying it to both `probe_rpc()` and `post_rpc()`, ensuring the "Content-Encoding: gzip" header is re-attached when retrying compressed requests.
On-disk format: unchanged.
Test coverage: new test script `t/t5584-http-429-retry.sh` (fifteen tests: three from patch 1 for retry count, failure threshold, and Trace2 logging; three from patch 2 for doubling behavior, clamping, and Retry-After override; five from patch 3 verifying 5xx defaults, configured retries, Retry-After for 503, exhausted retry reporting, and environment/URL-specific config; four from patch 4 verifying POST retries for 429/502, partial-clone blob fetches surviving 502s, and gzipped POST header preservation) and expanded helper `t/lib-httpd/http-429.sh` (configurable failure counts and 502/503/504 simulation).

Open questions and loose ends
- Whether the default set of retryable status codes should include 5xx errors (currently opt-in via config).
- Minor documentation formatting consistency (variable name markup in `Documentation/config/http.adoc`) noted by Junio in the earlier review, though this is cosmetic and unrelated to the patch’s core functionality.

Participant positions
- **Junio C Hamano**: Substantive review of patches 1/4, 2/4, and 3/4 in v1. Raised design, documentation, and implementation questions, all of which are addressed in v2/v3, including the clarification on the retry-loop guard clause removal, the reuse of `rate_limit_retries` for exponential backoff attempt counting, the relocation of the `400 <= code < 600` range check to the top of `is_retryable_http_code()`, and the documentation refinements for `http.retryAfter`, `http.maxRetries`, and `http.maxRetryTime`. - **Ravi Mistry**: Author. Engaged constructively with Junio’s and brian m. carlson’s feedback, incorporating clarifications, documentation improvements, and implementation refinements. Proposed `http.retryAfter=1` as a compromise default in v2, then accepted brian’s argument for a longer initial delay, agreeing to **10 seconds** in v3. Maintains the opt-in design for 5xx retries.

Initially argued for a 30-second initial delay (or at minimum 10 seconds) to protect rate-limited servers, rejecting the 1-second compromise as insufficient for Git’s computationally expensive requests. Position was based on server-operator experience and prioritized server protection. No alternative implementation proposed; resolution achieved via compromise (10 seconds).

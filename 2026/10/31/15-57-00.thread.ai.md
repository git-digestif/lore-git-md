Core problem or goal
Address four gaps in Git’s HTTP transport error handling: (1) an off-by-one retry count bug, (2) missing exponential backoff when Retry-After headers are absent, (3) inability to retry transient 5xx server errors, and (4) lack of retries for HTTP POST requests (used during fetch/clone and partial clone data transfers). The goal is to improve resilience when interacting with hosting backends and reverse proxies under high concurrency.

Current status
Under review; v3 posted with all substantive feedback addressed, including the resolved default `http.retryAfter` value (10 seconds) and cosmetic documentation fixes. The series is technically complete and awaits Junio’s final review and integration. The primary blocker (default `http.retryAfter` value) is resolved via compromise: 10 seconds (exponential backoff: 10s, 20s, 40s, ...) balances server protection (brian m. carlson’s priority) and interactive usability (Ravi Mistry’s concern). The opt-in design for 5xx retries and POST retries remains unchanged. Junio raised a **procedural concern** about the two-phase introduction of the default value: patches 1–4 assume `http.retryAfter=0` (no initial delay), while patch 5 retroactively sets the default to 10 seconds. Ravi has now offered two options to resolve this: (1) keep v3 as-is with patch 5/5 separate, or (2) fold the default value change into patch 2 in a v4. The choice is purely structural and does not affect the technical outcome. Junio and brian m. carlson are invited to weigh in on the preferred approach.

Key technical details
Files touched: `http.c`, `http.h`, `remote-curl.c`, documentation (`git-config.txt`, `git.txt`, `Documentation/config/http.adoc`), and tests (`t/t5584-http-429-retry.sh`, `t/lib-httpd/http-429.sh`).
New or renamed symbols: config key `http.retryStatusCodes` (default "429"), exponential backoff behavior for `http.retryAfter` (now the *initial* delay when Retry-After is missing, defaulting to **10 seconds**), helper functions `is_retryable_http_code()` and `http_retry_wait()`. The `attempt` parameter in `handle_rate_limit_retry()` tracks retry count for exponential backoff calculation (`http.retryAfter * 2^(attempt - 1)`).
Behavior changes: retry logic now consults `http.retryStatusCodes` (comma- or whitespace-separated list of 400–599 codes) instead of hardcoding 429; warning messages show numeric status codes (e.g., "HTTP 502") for non-429 responses while preserving "rate limited" phrasing for 429; backoff timing doubles on each retry (10s, 20s, 40s, …) while clamping at `http.maxRetryTime`. Patch 1 fixes an off-by-one retry counter (loop now checks `http_max_retries > 0 && rate_limit_retries-- > 0`) and a race in Retry-After header parsing (moved `CURLINFO_RETRY_AFTER` extraction into `finish_active_slot()`, initializing `slot->results->retry_after = -1` first). The removal of the early-return guard clause in the retry loop is intentional, as the new loop condition now handles the zero-retry case uniformly, including scenarios where re-authentication triggers a 429 after an initial 401. Patch 2 introduces exponential backoff for retries when Retry-After headers are absent, using `http.retryAfter` as the initial delay (default 10s) and `http_max_retries - rate_limit_retries` as the attempt counter (avoiding a new variable). Patch 3 makes retryable status codes configurable via `http.retryStatusCodes`, defaulting to 429, with the `400 <= code < 600` range check relocated to the top of `is_retryable_http_code()` for clarity, and adds environment variable support (`GIT_HTTP_RETRY_STATUS_CODES`). Patch 4 extends retry logic to HTTP POST requests by extracting retry wait logic into `http_retry_wait()` and applying it to both `probe_rpc()` and `post_rpc()`, ensuring the "Content-Encoding: gzip" header is re-attached when retrying compressed requests. Patch 5/5 explicitly sets the default value of `http.retryAfter` to 10 seconds in the config machinery, updates documentation to remove the word "configured" (since the default can now exceed `http.maxRetryTime` even when not explicitly set), and adjusts test expectations to verify fallback to the 10-second default when Retry-After HTTP-dates are in the past. The test suite now includes a case where `http.retryAfter` (10s) exceeds a lowered `http.maxRetryTime` (9s), triggering an immediate failure with a clear error message.
On-disk format: unchanged.
Test coverage: new test script `t/t5584-http-429-retry.sh` (nineteen tests: three from patch 1 for retry count, failure threshold, and Trace2 logging; three from patch 2 for doubling behavior, clamping, and Retry-After override; five from patch 3 verifying 5xx defaults, configured retries, Retry-After for 503, exhausted retry reporting, and environment/URL-specific config; eight from patches 4 and 5 verifying POST retries for 429/502, partial-clone blob fetches surviving 502s, gzipped POST header preservation, explicit default `http.retryAfter` value, and fallback behavior for past Retry-After HTTP-dates).

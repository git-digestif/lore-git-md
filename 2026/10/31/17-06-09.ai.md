This is a substantive review comment on Elia Pinto’s object-size truncation bugfix series for 32-bit platforms.

Simon Richter’s reply flags a critical distinction that the original series does not address: **`size_t` is not a universal fix for large sizes on 32-bit systems**. On those platforms, `size_t` is still 32 bits, so it cannot represent objects larger than 4 GiB in memory. The correct type for on-disk sizes is `off_t`, which is 64 bits when large-file support is enabled (the typical case). Simon’s guidance is that `size_t` should be reserved for in-memory buffer sizes, while `off_t` must be used for tracking the total bytes read from disk, even when the reads are done in chunks.

The review does not question the existence of the bug—truncation when passing `size_t` to `unsigned long` is real—but it does challenge the proposed solution’s completeness. The series currently converts object-parsing functions to `size_t`, yet those functions often operate on data read from disk, where `off_t` would be the more appropriate type. Simon’s comment implies that the series may need a second pass to distinguish between in-memory and on-disk size tracking, potentially requiring a larger refactoring of the object-reading code paths. No code suggestions are offered, but the technical point is clear and likely to spark further discussion.

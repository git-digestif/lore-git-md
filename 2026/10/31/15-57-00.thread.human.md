This thread is about a patch series from Ravi Mistry that improves Git’s HTTP error handling by adding exponential backoff, configurable retry status codes, and retries for POST requests. The series is now in its second version (v2), addressing all of Junio C Hamano’s feedback from v1, including clarifications on retry-loop logic, exponential backoff counting, and documentation refinements. The patches touch `http.c`, `remote-curl.c`, and related documentation and tests, introducing new config keys like `http.retryStatusCodes` and helper functions like `http_retry_wait()`.

The series is under review and largely polished, but two key questions remain unresolved. The first is whether the default set of retryable status codes should include 5xx errors (currently opt-in via config). The second—and the focus of the latest discussion—is the default value of `http.retryAfter`, which controls the initial delay when no Retry-After header is present. Ravi initially proposed `0` (immediate retry), but brian m. carlson argued for a non-zero default (e.g., 30 seconds) to avoid overwhelming rate-limited servers. Ravi has now proposed a compromise: defaulting to **1 second**, which aligns with curl’s behavior and balances fast recovery with server protection. This remains an open policy decision, and the outcome may depend on broader input or Junio’s guidance.

Junio’s reviews have been constructive and approving, focusing on design, documentation, and implementation details, while brian m. carlson’s objection reflects a server-operator perspective. The series is otherwise ready for integration, with no technical blockers beyond these unresolved questions. If the `http.retryAfter` default is settled, the series could move forward quickly.

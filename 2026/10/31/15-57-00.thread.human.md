Ravi Mistry's five-patch v4 series improving Git's HTTP transport resilience is nearing completion, with Junio C Hamano having approved the first four patches and the series awaiting a final v5 respin before integration. The series addresses four gaps in how Git handles transient server errors: an off-by-one retry bug, missing exponential backoff when servers don't send Retry-After headers, inability to retry 5xx errors, and lack of retries for POST requests during fetch and clone. Key changes include a new `http.retryStatusCodes` config (defaulting to 429), exponential backoff starting at a new 10-second default `http.retryAfter`, and safe POST retries restricted to read-only services like `git-upload-pack` while explicitly excluding push to avoid duplicate processing.

Junio has endorsed patches 1 through 4, praising the overflow-safe backoff math, the configurable retry codes, and the gzip header fix in the POST retry logic, though he noted his approval is procedural rather than deep technical validation since Patrick Steinhardt's substantive feedback was already incorporated in v4. The maintainer raised three remaining edge cases that Ravi has now committed to fixing in v5: documenting that an empty `http.retryStatusCodes` disables all retries rather than reverting to the default, noting that 401/404 can never be retried regardless of configuration due to check ordering, and clearing the stale `slot_results` struct in `post_rpc()` before each retry attempt to ensure accurate error reporting. Patch 5, which changes the default retry delay to 10 seconds and adds raw Retry-After header inspection for zero or past values, still awaits Junio's individual review, leaving the series in a holding pattern until the v5 iteration addresses these final documentation and code cleanups.

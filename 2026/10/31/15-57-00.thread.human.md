This thread is about a five-patch series from Ravi Mistry that improves Git’s HTTP transport resilience by fixing an off-by-one retry counter, adding exponential backoff for retries, making retryable status codes configurable, and enabling retries for HTTP POST requests. The series is now at v3, with all substantive feedback addressed, including a compromise on the default `http.retryAfter` value (10 seconds) that balances server protection and usability.

The technical work is complete: the patches touch `http.c`, `remote-curl.c`, and related documentation, introducing new config keys like `http.retryStatusCodes` (defaulting to 429) and helper functions such as `is_retryable_http_code()` and `http_retry_wait()`. The behavior changes include doubling the backoff delay on each retry (10s, 20s, 40s, ...) while clamping at `http.maxRetryTime`, and extending retries to POST requests, which are used during fetch/clone and partial clone operations. The test suite now covers exponential backoff, 5xx retries, and POST retries with nineteen new tests.

The only remaining discussion is procedural: Junio C Hamano raised a question about the series structure, specifically whether the two-phase introduction of the default `http.retryAfter` value (patches 1–4 assume 0, patch 5 sets it to 10 seconds) is the right approach. Ravi has offered to either keep v3 as-is or fold the default value change into patch 2 in a v4, leaving the decision to Junio and brian m. carlson. The technical outcome—10-second default, opt-in 5xx retries, and POST retries—is already agreed upon, so this is purely about patch organization. The series is otherwise ready for integration.

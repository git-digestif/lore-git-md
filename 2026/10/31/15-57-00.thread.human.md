This thread covers Ravi Mistry's five-patch v3 series improving Git's HTTP transport resilience, addressing an off-by-one retry bug, adding exponential backoff (defaulting to 10 seconds) when servers omit Retry-After headers, making retryable status codes configurable, and extending retries to POST requests used during fetch and clone. The series is under review with the default backoff value resolved at 10 seconds as a compromise between server protection and interactive usability, though Junio C Hamano has raised a procedural question about whether to keep the default value change as a separate fifth patch or fold it into the second patch in a potential v4.

The most active open debate concerns patch 3/5 and the new `http.retryStatusCodes` configuration key. Patrick Steinhardt, while acknowledging Ravi's argument that 429 (deliberate rate limiting) and 5xx codes (transient proxy or CDN failures) are semantically distinct, maintains that Git should not offload responsibility for non-429 retries onto users. He proposes instead that documentation explicitly state service providers are expected to return 429 when overloaded, treating any other behavior as buggy provider conduct, and that the config option be documented merely as a workaround for such buggy providers to nudge the ecosystem toward standardization rather than silently accommodating non-standard codes. Ravi counters that 5xx responses from reverse proxies and CDNs represent genuinely transient failure modes distinct from deliberate rate limiting, defending the opt-in design that keeps 429 as the sole default while allowing administrators to configure 5xx retries for environments where those codes are known to be safe to retry. No resolution has been reached on whether Git should offer this configurability at all.

Other technical points remain in flux for a potential v4: Patrick has pushed back on retrying non-idempotent POST operations like push, which Ravi has accepted and committed to restricting to read-only services such as `git-upload-pack` and `git-upload-archive`; Patrick also noted that explicit `Retry-After: 0` headers should trigger immediate retries rather than falling back to the 10-second default, a fix Ravi has agreed to implement by inspecting the raw header. The series awaits Junio's final review and integration decision.

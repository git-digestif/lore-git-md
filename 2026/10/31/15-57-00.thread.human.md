This thread is Ravi Mistry's five-part v4 series tightening Git's HTTP transport retry behavior: fixing an off-by-one in the 429 retry count, adding overflow-safe exponential backoff, making retryable status codes configurable via the new `http.retryStatusCodes` option, enabling retries for read-only POST requests (fetch/clone and partial-clone fetches, but never push), and changing the default `http.retryAfter` from 0 to 10 seconds. Junio C Hamano has now reviewed and approved the first three patches individually -- patches 1/5 and 2/5 with "Looking good," and patch 3/5 with "Overall looking very good" -- while patches 4/5 and 5/5 still await his review, so the series as a whole remains under review with no integration decision yet.

Junio's review of patch 3/5 surfaced two edge cases worth knowing: setting `http.retryStatusCodes` to an empty string disables all retries rather than restoring the default 429-only behavior (he suggests documenting this), and 401 and 404 responses can never be retried even if explicitly listed, because `handle_curl_result()` checks `missing_target()` and 401 before consulting the configurable-code list. Patrick Steinhardt's substantive earlier objections have been addressed in v4 -- the size_t retry counter, the push-excluding whitelist for POST retries, raw-header inspection for `Retry-After: 0`, and documentation framing non-429 codes as temporary workarounds for buggy providers -- though the underlying architectural question of whether configurable retry codes belong in Git at all remains open at the design level, and Junio's procedural concern about the two-phase introduction of the 10-second default persists since patch 5/5 still carries that change separately.

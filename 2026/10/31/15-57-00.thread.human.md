This thread is about a four-patch series from Ravi Mistry that improves Git’s HTTP transport error handling by fixing an off-by-one retry bug, adding exponential backoff, making retryable status codes configurable, and enabling retries for HTTP POST requests. The series is now in its second version (v2), which addresses all of Junio C Hamano’s feedback from v1, including clarifications on retry-loop logic, exponential backoff counting, and documentation refinements.

The key unresolved question—whether the default `http.retryAfter` should be 0, 1, or 30 seconds—has now seen Junio endorse Ravi’s compromise of **1 second**, matching curl’s behavior (1s, 2s, 4s, etc.). This avoids the immediate retry of `0` (which breaks exponential backoff) and the aggressive 30-second initial delay proposed by brian m. carlson, which would escalate to 120 seconds over three retries. The other open questions—whether 5xx errors should be retryable by default and minor documentation formatting—remain, but the `http.retryAfter` default is the most contentious and now appears settled unless brian pushes back further.

The series touches `http.c`, `remote-curl.c`, documentation, and tests, introducing new config keys (`http.retryStatusCodes`, defaulting to 429) and helper functions (`is_retryable_http_code()`, `http_retry_wait()`). Tests now cover POST retries, 5xx behavior, and gzipped request header preservation. Junio’s latest review focused on surface-level documentation tweaks, while brian’s earlier feedback prioritized server protection over fast recovery. With Junio’s endorsement of the 1-second default, the series is likely ready for integration unless further objections arise.

This thread presents Ravi Mistry's five-patch v4 series improving Git's HTTP transport resilience. The series fixes an off-by-one retry counter bug, introduces exponential backoff when servers omit Retry-After headers, adds configurable retry status codes beyond the default 429, enables retries for read-only POST requests (fetch/clone and partial-clone blob fetches) while excluding push, and finally changes the default `http.retryAfter` from 0 to 10 seconds so retries wait 10s, 20s, 40s rather than hammering servers in a tight loop. A new `has_zero_or_past_retry_after()` helper preserves immediate-retry behavior when a server explicitly sends `Retry-After: 0`, using `curl_easy_header()` on libcurl >= 7.84.0.

Patrick Steinhardt's substantive review points from v3 are all addressed in v4, including the size_t typing fix, the POST whitelist excluding non-idempotent pushes, and documentation reframing non-429 codes as temporary workarounds for buggy provider infrastructure. brian m. carlson's preference for a longer initial delay was satisfied by the 10-second compromise. Junio C Hamano's procedural concern about the two-phase introduction of the 10-second default remains open: patches 1-4 assume `http.retryAfter=0` while patch 5 flips the default, a structure Junio previously questioned.

The series is complete at v4 and awaits Junio's final review and integration decision. The broader architectural question of whether configurable retry codes should exist at all versus standardizing on 429 remains unresolved at the design level.

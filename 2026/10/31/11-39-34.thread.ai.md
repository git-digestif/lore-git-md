Thread identity: Subject "[PATCH v2 0/4] Fix truncation issues with large objects on 32-bit platforms", series version v2, originating author Elia Pinto <gitter.spiros@gmail.com>, thread type bugfix patch series. Based on master at e1ec09b23c.

Core problem or goal: Fix truncation and correctness issues when handling objects >=4 GiB on platforms where `unsigned long` is 32-bit (notably 64-bit Windows) while `size_t` is 64-bit. The series converts key components in the pack-receiving and verification pipeline (`unpack-objects`, `index-pack`, `git fsck`) from `unsigned long` (and one `unsigned int`) to `size_t` to match the underlying pack code, addressing an "inflate returned -5" failure, crashes, false SHA-1 collision reports, and partial object checks.

Current status: v2 under review; no merge status indicated. v1 received no review comments. Key technical details: Files touched are `builtin/unpack-objects.c`, `builtin/index-pack.c`, `builtin/fsck.c`, `odb.h`, and `pack.h`; subsystems are the pack-receiving pipeline, object verification, and fsck. Patch 1/4 converts `builtin/unpack-objects.c` to use `size_t` throughout, spanning `struct obj_buffer.size`, `get_data()`, `struct delta_info.size`, `add_delta_to_list()`, `write_object()`, `resolve_delta()`, `added_object()`, `unpack_non_delta_entry()`, `resolve_against_held()`, and `unpack_delta_entry()`, fixing inflate failures for non-streamed large objects, crashes when delta bases exceed 4 GiB, and silent truncation of large delta results; with `size_t` in place, `unpack-objects -n` and non-streamed objects of any size are handled correctly. The `cast_size_t_to_ulong()` guard in `write_object()` protects downstream callees still accepting `unsigned long`, causing oversized objects to die with "object too large to read on this platform" rather than being written truncated; the cast previously present in `unpack_delta_entry()` is removed since `base_size` is now `size_t` throughout. Patch 2/4 changes `write_compressed()` in `builtin/index-pack.c` from `unsigned int` to `size_t` (both parameter and return type) to fix "serious inflate inconsistency" in `index-pack --fix-thin` when local bases exceed 4 GiB: the old 32-bit parameter silently truncated the size to `size mod 2^32`, causing only that many bytes to be compressed while the pack header recorded the full size, leading `unpack_data()` to die on early end of the compressed stream; this is a single-line diff with no test yet, verified by the author via 16-bit size simulation with a 100 KiB base; in v3 the author will add the `signed_add_overflows()` guard in `append_obj_to_pack()` and an `EXPENSIVE` test with a hand-written delta against a 4 GiB local base. Patch 3/4 converts `sha1_object()`, `append_obj_to_pack()`, the `consume` callback parameter of `unpack_data()`, `compare_objects()`, and the `buf_size` field of `struct compare_data` in `builtin/index-pack.c` from `unsigned long` to `size_t` (six lines changed) to stop false "SHA1 COLLISION FOUND" errors for large objects already present locally: on 32-bit-`long` platforms the old parameter truncated the true 64-bit `size_t` value held in `struct object_entry`, causing `sha1_object()` to compare the real object size against a truncated value and abort with a spurious collision error; no test included as triggering requires 4 GiB+ input, verified via size-truncation simulation. Patch 4/4 converts the `size` parameter from `unsigned long` to `size_t` in the `verify_fn` typedef in `pack.h`, the `object_cb` field of `struct odb_fsck_options` in `odb.h`, and `fsck_obj_buffer()` in `builtin/fsck.c`, so `git fsck` passes the full object size rather than a truncated prefix to the verification callback. No on-disk format changes. No tests included in v2 (impractical to generate 4 GiB objects or test on 32-bit platforms); commit messages describe verifying fixes by truncating sizes to 16 bits in simulation.

Open questions and loose ends: Patrick Steinhardt's review of patch 1/4 raised a substantive sequencing question: because a separate series already in flight is converting `odb_write_object()` and `parse_object_buffer()` to `size_t`, the `cast_size_t_to_ulong()` guards introduced in `write_object()` would become redundant once both series land, requiring yet another cleanup; he asked whether it would be better to defer this entire series until the downstream conversions have landed. He also noted the commit message is excessively verbose. The author has accepted the deferral for patches 1/4 and 4/4 and the commit-message condensation, but no maintainer (Junio) decision on the deferral is recorded. Patrick Steinhardt's review of patch 2/4 raised a correctness concern about the sole caller in `append_obj_to_pack()`, which performs `obj[1].idx.offset += write_compressed(f, buf, size)`: `struct pack_idx_entry.offset` is of type `off_t` (signed) while `write_compressed()` now returns `size_t` (unsigned), and he asked whether the code should verify that this addition cannot overflow; he also challenged the absence of test coverage by asking whether an `EXPENSIVE` test could exercise the 4 GiB+ local base scenario. The author has now agreed to both fixes in the planned v3 resubmission: adding `signed_add_overflows()` in `append_obj_to_pack()` and an `EXPENSIVE`-style test with a hand-written delta against a 4 GiB local base, though the actual v3 code has not yet been posted. Patrick Steinhardt's review of patch 4/4 raised a correctness question about the residual gap: even with the callback now receiving the true 64-bit size, `parse_object_buffer()` and `fsck_object()` still internally accept `unsigned long` and therefore inspect only a prefix of objects >=4 GiB; he asked whether these functions detect that they received a truncated buffer and report an error, or whether they silently validate only the prefix and miss corruption in the unexamined tail. This question is now resolved by the author: on current master the verify callback is never reached for objects >=4 GiB because `verify_packfile()` first calls `check_object_signature()`, which also accepts `unsigned long`, hashes only the prefix, and reports a spurious "packed <oid> from <pack> is corrupt" error for an intact object; thus fsck does fail, but with a false-positive corruption report rather than silent prefix validation. The author confirms patch 4/4 properly belongs on top of the dependent `parse_object_buffer()`/`fsck_object()` `size_t` conversion series (cover.1793444420) and will be resent there with a corrected commit message. He adds that blobs are unaffected by this path on 32-bit-`long` platforms because `core.bigFileThreshold` is itself an `unsigned long` capped below 4 GiB, so any blob that large is instead verified via `stream_object_signature()` and reaches the callback without data truncation. Full correctness for non-streamed objects depends on the two now-identified follow-up series converting `odb_write_object()` and `parse_object_buffer()`/`fsck_object()` to `size_t`; patch 4/4 itself will be deferred until the second of those lands. `pack-objects` delta search fixes remain out of scope for this series.

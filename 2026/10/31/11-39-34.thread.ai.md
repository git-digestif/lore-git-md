Subject: [PATCH 0/4] Fix truncation issues with large objects on 32-bit platforms
Series version: v1 (initial submission)
Originating author: Elia Pinto <gitter.spiros@gmail.com>
Thread type: bugfix patch series

Core problem or goal
Fix truncation and correctness issues when handling objects ≥4 GiB on platforms where `unsigned long` is 32-bit (notably Windows). The series converts key components in the pack-receiving and verification pipeline (`unpack-objects`, `index-pack`, `git fsck`) from `unsigned long` to `size_t` to match the underlying pack code, addressing crashes, false SHA-1 collision reports, and partial object checks.

Current status
Under review; no prior versions. The series is self-contained and merges cleanly with other in-flight work, though full correctness for non-streamed objects requires follow-up patches from related series (object parsing and ODB write sizes). All four patches have now been posted, completing the initial submission.

Key technical details
- **Files touched**: `builtin/fsck.c`, `builtin/index-pack.c`, `builtin/unpack-objects.c`, `odb.h`, `pack.h`
- **Subsystems**: pack-receiving pipeline, object verification, fsck
- **Type changes**: `unsigned long` → `size_t` in critical size/offset parameters, including `write_compressed()` in `index-pack.c` (converted from `unsigned int` to `size_t` for size parameter and return value), `sha1_object()`, `append_obj_to_pack()`, and the `verify_fn` callback in `pack.h`
- **New/renamed symbols**: None (mechanical type conversions only)
- **Behavior changes**:
  - Patch 1/4: Fixes crash in `unpack-objects` on Windows for objects ≥4 GiB by converting `struct obj_buffer` and related functions to use `size_t` for object sizes. The patch removes a redundant size cast in `unpack_delta_entry()` and updates calls to `odb_write_object()` and `fsck_object()` (addressed in later patches). Reproduction requires streaming large blobs exceeding `core.bigFileThreshold` on 32-bit platforms.
  - Patch 2/4: Resolves "serious inflate inconsistency" in `index-pack --fix-thin` when local bases exceed 4 GiB by ensuring `write_compressed()` does not truncate the input size to 32 bits. The failure occurs because `append_obj_to_pack()` writes the full size in the pack header, but `unpack_data()` later encounters an early end-of-stream due to the truncation. Demonstrated with a 16-bit simulation (100 KiB base).
  - Patch 3/4: Prevents false "SHA1 COLLISION FOUND" errors in `index-pack` on Windows by converting `sha1_object()` and `append_obj_to_pack()` to use `size_t` for object sizes, aligning with `struct object_entry`'s existing `size_t` storage. The truncation of sizes ≥4 GiB on 32-bit platforms caused `sha1_object()` to compare only the first 4 GiB of an object against its locally stored counterpart, leading to false collision reports.
  - Patch 4/4: Ensures `git fsck` checks full objects rather than prefixes in packs by converting the `verify_fn` callback signature and `fsck_obj_buffer()` to use `size_t` for object sizes. The truncation on 32-bit platforms caused `parse_object_buffer()` and `fsck_object()` to inspect only the first 4 GiB of the object.
- **On-disk format**: No changes
- **Test coverage**: None (impractical to generate 4 GiB objects or test on 32-bit platforms); commit messages provide detailed reproduction scenarios

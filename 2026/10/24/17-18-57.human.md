This is a **bugfix update** to the first patch in Harald Nordgren’s v10 series introducing `remote.<name>.refmap`. The change addresses D. Ben Knoble’s substantive review question about the fallback logic in `remote_find_tracking()`.

The new implementation clarifies the intended behavior: `remote_find_tracking()` now falls back to `remote->refmap` **only if `remote->fetch` is empty *or* if `refspec_find_match()` fails to find a match in `remote->fetch`**. This ensures that `remote->refmap` acts as a true superset of `remote->fetch`, allowing the function to return mappings for refs that are not part of the explicit fetch refspecs. The change is minimal and surgical, touching only the control flow in `remote_find_tracking()` without altering any other logic or interfaces.

The commit message does not explicitly justify the design choice, but the code change itself resolves the ambiguity Knoble raised. The revised logic is consistent with the series’ broader goal of using `remote->refmap` as a default namespace mapping when no explicit fetch refspecs are provided. This should address potential downstream consequences, such as `--delete-merged` operations, by ensuring that `remote_find_tracking()` can always locate a mapping for tracked refs, even if they are not part of the primary fetch configuration.

The patch remains uncontroversial and is still on track for merging to `next`. The only remaining open questions from the thread (e.g., whether the matching-inspired mode should be available outside shallow repositories) are unrelated to this change and can be addressed in follow-up work. No further review is required for this specific update.

This is a **regression bugfix** targeting the shallow clone and partial clone machinery in Git 2.56.0.

The email reports a crash that started in Git 2.56.0 when a `git fetch` combines `--filter=tree:0` with `--unshallow` (or `--deepen`) in a shallow clone where the fetched ref has moved past the local tip. The crash occurs in `pack-objects` with the message `BUG: should_include_obj should only be called on existing objects`, followed by a signal 6 abort. The regression was introduced by commit `d43b9acb05` ("setup: unify setup of shallow file"), which changed how the shallow file is passed to subprocesses by exporting `GIT_SHALLOW_FILE` instead of relying on the `$GIT_DIR/shallow` file.

The author provides a minimal reproduction script that sets up a shallow clone, moves the remote ref forward, and then attempts an unshallowing fetch with a tree filter. The script reliably triggers the bug on Git 2.56.0 but succeeds on 2.55.0. The root cause is that the `pack-objects` subprocess, now inheriting an empty shallow file via the environment, no longer treats the local tip as a shallow boundary and walks into promisor objects whose trees were never fetched, triggering the BUG.

The email also notes that the BUG is reachable even without the environment change, suggesting a deeper issue with how promisor objects are handled during unshallowing. The author has confirmed the regression window and the mechanism, but does not propose a fix in this email. The report is thorough, with a clear reproduction case and a precise explanation of the regression, making it a strong candidate for attention from maintainers working on shallow or partial clone logic.

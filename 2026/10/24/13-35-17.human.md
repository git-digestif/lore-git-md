This is a **design discussion reply** in the ongoing RFC thread about extending `git branch --delete-merged` to handle branches whose upstream has been deleted (e.g., by GitHub after merging a PR). D. Ben Knoble responds to Harald Nordgren’s suggestion to make the feature work by default, arguing instead for a **composable, filter-based interface** that avoids context-sensitive flags like `--into`.

Knoble’s reply reframes the problem as a missed opportunity in Git’s CLI design: rather than adding new flags to `--delete-merged`, he proposes extending `git branch --list` with filters (e.g., `--merged-upstream=<commit>`) to identify branches whose upstream is gone but whose tip is reachable from a specified ref. Users could then pipe the output to `git branch -d` for deletion. This approach aligns with Git’s existing `--list` patterns (e.g., `--merged`, `--contains`) and avoids the pitfalls of flags that only work in specific contexts (like `--into` with `--delete-merged`). He suggests that `--delete-merged` itself could eventually be deprecated in favor of this composable workflow.

The reply also touches on broader CLI consistency, noting that `--list` already supports pattern arguments, making it a natural fit for this use case. Knoble’s preference for composability over monolithic flags (like Nordgren’s implicit behavior proposal) reflects a long-standing tension in Git’s interface design: whether to prioritize explicit, context-sensitive flags or flexible, reusable filters. His examples—such as `git branch --list --merged=origin/main | xargs git branch -d`—demonstrate how the feature could work today with minor extensions to `--list`, sidestepping the need for new flags entirely.

While Knoble’s proposal is technically elegant, it may face resistance from users who prefer the simplicity of `--delete-merged`’s current behavior. The thread remains unresolved, with no consensus on whether the feature should be opt-in (via flags or filters), opt-out (Nordgren’s implicit approach), or composable (Knoble’s preference). The discussion now hinges on **interface philosophy**—whether Git should favor composability or CLI purity—rather than the technical feasibility of the feature itself.

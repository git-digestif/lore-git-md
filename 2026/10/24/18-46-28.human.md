This is a follow-up in the ongoing `git reflog` feature discussion, part of Harald Nordgren’s v2 patch series introducing `--operations` and `--historical-branch` options. The author responds to Junio C Hamano’s suggestion that `git reflog` should default to the current branch rather than HEAD, agreeing this would be a major usability improvement and proposing a cleanup of the verbose output format.

Harald acknowledges Junio’s point that `git reflog` currently defaults to HEAD, which often produces noisy or irrelevant entries, and endorses making the current branch the default. He notes the existing output is overly verbose, with full ref names (`refs/heads/...`) and redundant branch references, and suggests these could be simplified—though he doesn’t propose a specific format. This aligns with earlier feedback from Phillip Wood and D. Ben Knoble, who argued for a more composable approach (e.g., format specifiers like `%gb`) rather than a dedicated `--historical-branch` flag.

The email doesn’t engage with the deeper architectural concerns raised in the thread: Phillip Wood’s critique of `--operations`’s limitations (e.g., missing reflog updates for some commands) or the correctness gap in `--historical-branch`’s handling of `git rebase <upstream> <branch>`. Nor does it address Junio’s broader proposal to refactor multi-step commands (like `git am`) to work on detached HEAD by default, which would obviate the need for heuristic-based filtering. Instead, the focus here is narrowly on output formatting and default behavior, leaving the core design questions unresolved.

The patch series remains under active review, with no clear path forward. The discussion has shifted from feature implementation to fundamental questions about whether these features belong in Git’s core at all, and if so, how they should integrate with existing workflows and future architectural changes. Harald’s response suggests he’s open to incremental improvements but hasn’t yet grappled with the larger design trade-offs.

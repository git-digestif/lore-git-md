This is the third patch in Harald Nordgren’s v10 series introducing a "matching-inspired" fetch mode for shallow repositories. The patch implements the core logic: when a remote has `remote.<name>.refmap` configured but no `remote.<name>.fetch`, a refspec-less `git fetch` now infers which branches to fetch by enumerating the local branches whose `@{upstream}` points to that remote. D. Ben Knoble’s review here is substantive, focusing on documentation clarity, implementation choices, and code duplication.

Knoble’s main concern is the commit message’s framing, which currently presents the change as a fix for an error case rather than the series’ primary goal. He suggests rephrasing to emphasize that the patch enables a new fetch mode (inferring branches from local upstreams) and only incidentally resolves the error when `remote.<name>.refmap` is configured without `remote.<name>.fetch`. This would better align with the series’ intent and make the purpose clearer to readers.

The review also critiques the documentation in `fetch-options.adoc` and `config/remote.adoc`. Knoble finds the phrasing "branches from the remote that are used as the `@{upstream}` of our local branches" confusing and suggests rewording for clarity. He also questions whether the documentation adequately explains how the refmap interacts with the inferred branches—specifically, whether the refmap narrows the set of fetched branches or merely maps them. This is a documentation-only issue and does not affect functionality, but it could lead to user confusion if left unaddressed.

On the implementation side, Knoble notes code duplication in `do_fetch()` where two nearly identical blocks handle `follow_remote_head` logic. He suggests refactoring to avoid redundancy, though this is a minor nit and not a blocker. He also questions the use of `string_list` in `get_ref_map()` and `do_fetch()`, asking whether `strvec` would be more appropriate given that sorting may not be needed. This is a performance consideration rather than a correctness issue, and the author may choose to address it in a follow-up patch.

The review does not raise any technical blockers or design concerns. The feedback is focused on clarity, consistency, and minor efficiency improvements, all of which are actionable but not critical for merging.

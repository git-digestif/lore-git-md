This is a **substantive review** of the first patch in Harald Nordgren’s v10 series introducing `remote.<name>.refmap`. D. Ben Knoble raises a technical question about the fallback logic in `remote_find_tracking()`: whether the code should fall back to `remote->refmap` only when `remote->fetch` is empty, or also when `refspec_find_match()` fails to find a match in `remote->fetch`.

The review identifies a potential edge case: if `remote->fetch` is non-empty but does not contain a matching refspec, the current implementation will still fall back to `remote->refmap`. Knoble questions whether this is correct, given that `remote_find_tracking()` is documented to "read the refspec’s src and set the other fields" for the given remote. The concern is that this fallback might cause the function to return a refspec from `remote->refmap` even when the user’s intent was to query only the explicitly configured `remote->fetch` refspecs, potentially affecting downstream operations like `--delete-merged`.

Knoble’s question is well-scoped and targets a specific code path (`remote_find_tracking()` in `remote.c`). The review does not propose a solution but flags the ambiguity in the intended behavior. The patch author will need to clarify whether the fallback is intentional (e.g., to support refmap as a superset of fetch refspecs) or if it should be restricted to cases where `remote->fetch` is entirely empty. The answer may require auditing the callers of `remote_find_tracking()` to ensure consistency with the new logic. No other issues are raised in this review.

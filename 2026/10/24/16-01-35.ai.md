This is a **design discussion reply** in the ongoing RFC thread about extending `git branch --delete` to handle branches whose upstream has been deleted. The author, DonQuinleone, responds to feedback from D. Ben Knoble and Harald Nordgren by refining the proposed interface and addressing edge cases observed during testing.

Don reports testing the suggestions against a reproduction script and finds that Knoble’s proposed `git branch --list --merged=origin/main | xargs git branch -d` fails in practice: the pipe loses the proof of merge, causing `git branch -d` to fall back to checking against `HEAD` (which may not reflect the intended merge base). This reveals a fundamental limitation of the composable filtering approach—it cannot preserve the merge-checking logic across the pipe boundary. To resolve this, Don proposes a hybrid of Knoble’s composability idea and the original RFC’s explicit opt-in: teach `git branch -d` to accept `--upstream-gone` and `--merged=<commit>` as composable filters, where `--merged` serves as both the selection criterion *and* the proof of merge. This would allow `git branch -d --upstream-gone --merged=origin/master` to delete gone-upstream branches only if their tip is reachable from `origin/master`, while avoiding the pitfalls of implicit behavior or context-sensitive flags.

The proposal addresses key concerns raised earlier:
- **Composability**: The filters work independently (e.g., `--upstream-gone` can be used for listing without deletion), and `--merged` is explicit, avoiding the "option that only works next to another option" problem Knoble criticized.
- **Safeguards**: The existing protections (worktree checks, `branch.<name>.deleteMerged`) remain intact, and `--merged` requires an explicit commit, preventing accidental deletions.
- **Edge cases**: The design avoids false positives (e.g., deleting `master` or unpushed branches) by narrowing the selection with `--upstream-gone`.

Don frames the remaining open questions as:
1. Whether the "selection is not proof" model (where the user explicitly names the merge base) is acceptable for deleting gone-upstream branches.
2. Whether Knoble and Nordgren agree with the filtered `-d` approach as a middle ground between composability and CLI purity.

The reply shifts the discussion toward a concrete implementation path, with Don suggesting a two-patch series: first adding `--upstream-gone` as a listing filter, then extending it to support deletion. This incremental approach could help build consensus by demonstrating the feature’s utility in a low-risk form. The thread remains unresolved, but the proposal now has a clearer technical foundation and addresses the earlier composability vs. implicit-behavior tension.

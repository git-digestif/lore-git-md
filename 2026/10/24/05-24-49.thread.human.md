This thread is about fixing a Bash completion regression for four Git built-in commands (`patch-id`, `diff-pairs`, `fast-import`, and `var`). These commands were not showing available options in completion because they were still marked with the `NO_PARSEOPT` flag in `git.c`, even though they had already been converted to use the `parse-options` API.

Tanga Joris sent a v3 patch series that centralizes the completion-helper logic in `parse-options.c`, avoiding per-command boilerplate and side effects like temporary file creation or blocking on input. The second patch in the series, just posted, removes the `NO_PARSEOPT` flag from these four commands in `git.c`'s `commands[]` table. This is a mechanical follow-up to the first patch and is critical for the fix to take effect. The change is minimal—just four line edits—but well-motivated, with the commit message providing precise historical context for each command's conversion to `parse-options`.

The series is under review and depends on Christian Couder’s `cc/early-scan-options` series being stable and preferably in `next`. René Scharfe and Junio Hamano have provided substantive feedback, with René identifying an edge case for `fast-import` and Junio proposing the centralized refactoring. The first patch includes a test for `fast-import` to verify no side effects, but there’s no test coverage yet for the completion behavior of `patch-id`, `diff-pairs`, or `var`. No other participants have responded to the v3 patch so far. The fix is uncontroversial and should be merged once the first patch is accepted.

This thread is about fixing a Bash completion regression that prevented Git from offering command-line options for four built-in commands (`patch-id`, `diff-pairs`, `fast-import`, and `var`). These commands had been converted to use the `parse-options` API but were still marked with the `NO_PARSEOPT` flag in `git.c`, causing completion to fail. Tanga Joris, an Outreachy contributor, has been driving the fix through multiple iterations, with the latest v5 series addressing all prior feedback.

The solution centralizes handling of `--git-completion-helper` and `--git-completion-helper-all` in `parse-options.c`, eliminating per-command boilerplate and preventing side effects like temporary file creation or blocking on input (a particular issue for `fast-import`). The patch is technically sound, with two new tests in `t/t9300-fast-import.sh` verifying the fix for `fast-import` and a revised comment in `parse-options.h` to clarify the function’s purpose. The series has received substantive reviews from René Scharfe (who identified the `fast-import` edge case), Junio Hamano (who proposed the centralized refactoring), and Cynthia Uche (who validated the fix across all built-in commands).

The main blocker is Christian Couder’s `cc/early-scan-options` series, which needs to stabilize and reach `next` before this work can proceed. While the fix is ready for review, no merge status has been reported for either series. The defensive test added in v4 to catch future `NO_PARSEOPT` regressions remains limited, as it doesn’t cover commands with only short options (like `var`). The current version addresses all prior feedback, including Junio’s documentation nit and Kaartic Sivaraam’s suggestions for commit-message clarity.

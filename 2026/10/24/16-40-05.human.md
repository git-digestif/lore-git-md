This is a maintainer's perspective on the `git reflog` series, responding to Phillip Wood's skepticism about the `--operations` feature. Junio C Hamano endorses the *goal* of making reflog output easier to understand—particularly for multi-step operations like rebase—but suggests an alternative architectural path: teaching more commands (like `git am` and `git cherry-pick`) to work on a detached HEAD by default, just as `git rebase` already does.

The key idea is that if commands detach HEAD before making changes, the reflog naturally records one entry per logical operation, eliminating the need for `--operations` to heuristically collapse intermediate steps. Junio acknowledges that `git am` predates detached HEAD and users expect it to work on the current branch, but he questions whether this is a meaningful regression if the command were updated to detach first. He shares his personal workaround (manually detaching HEAD before running `git am`) and notes that the same workflow would still work if `git am` learned to detach automatically.

Junio also touches on a long-standing usability quirk: `git reflog` defaults to showing HEAD’s log, which can be confusing when HEAD is detached. He mentions that he personally avoids this by always specifying `@{0}` or `@{now}`, but this is a habit, not a fix. The series does not address this default behavior, though Phillip Wood’s review suggested `git reflog` should default to the current branch instead.

This reply does not engage with the `--historical-branch` feature or Phillip’s proposal to use a format specifier (`%gb`). It focuses narrowly on the `--operations` debate, positioning the architectural change (detaching HEAD by default) as a cleaner solution than post-hoc filtering. The tone is pragmatic and open to evolution, but it sidesteps the immediate question of whether the current series should proceed as-is. No merge status or maintainer decision is implied; the discussion remains open.

This is a follow-up to a bug report about a crash in `git apply --check` when processing a patch that creates a new file. The original report identified an assertion failure (`patch->is_new <= 0`) in `apply.c`'s `check_preimage` function, and the reporter provided a minimal reproducer. This email confirms the bug is reproducible on both current `master` and Git 2.43, but notes the issue depends on the order of header lines in the patch.

Tanga Joris, a contributor, was unable to reproduce the crash using the exact patch quoted in the original email (due to line wrapping in the email), but successfully triggered the same assertion by crafting a patch where the `--- /dev/null` line appears *before* the `new file mode` line. This suggests the bug is sensitive to the patch header's structure, not its content. The email asks the original reporter to confirm whether their patch was handwritten or tool-generated and to attach the exact file to rule out other variables.

The confirmation narrows the scope: the crash is not a regression between Git versions (it affects 2.43 and `master`), and it is tied to a specific edge case in patch parsing. The request for the original patch file is a practical next step to ensure the fix addresses the exact scenario that triggered the report. This looks like a well-defined bug with a clear reproduction path, and the discussion is now focused on pinpointing the exact conditions that trigger it. Worth watching if you care about `git apply` robustness.

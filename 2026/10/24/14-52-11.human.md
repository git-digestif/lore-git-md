This is a **workflow discussion** reply in the ongoing RFC thread about improving `git branch --delete-merged` for branches with gone upstreams. Harald Nordgren and D. Ben Knoble continue their tangential but relevant conversation about Git’s defaults for triangular workflows (e.g., GitHub PRs), focusing on two settings: `push.default=current` and `branch.autosetupmerge=inherit`.

Nordgren argues that `push.default=current` (which pushes the current branch to a remote branch of the same name) should be the default, calling the current `simple` setting a "compromise that’s not really good for anyone." He also praises `branch.autosetupmerge=inherit` (which automatically sets the upstream for new branches to match the upstream of the branch they were created from) as a way to avoid ever needing to specify a starting point like `origin/main` when branching. His example workflow—`git switch origin -c topic`—highlights how `inherit` simplifies branching by preserving the upstream relationship from `origin/main` without requiring users to explicitly name it.

The discussion remains **orthogonal to the RFC’s core proposal** (how to handle gone-upstream branches in `--delete-merged`), but it underscores a broader theme: Git’s defaults often obscure the relationship between `@{upstream}` (merge target) and `@{push}` (push target), creating friction for users in triangular workflows. Nordgren’s advocacy for these changes suggests he sees them as complementary to the RFC’s goal of reducing manual cleanup work. However, Knoble’s earlier warning—that such changes would require a major release (e.g., Git 4.0) due to past controversy—still looms over the conversation. No new technical details or edge cases for the RFC itself are addressed here.

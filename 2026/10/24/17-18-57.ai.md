This is a **bugfix update** to the first patch in Harald Nordgren’s v10 series introducing `remote.<name>.refmap`. The patch addresses D. Ben Knoble’s technical concern about the fallback logic in `remote_find_tracking()` by ensuring the function only falls back to `remote->refmap` when `remote->fetch` is either empty *or* contains no matching refspec for the given query. This preserves the intended behavior where `remote->refmap` acts as a superset of `remote->fetch` while avoiding unintended side effects (e.g., for `--delete-merged`).

The change is minimal and surgical: it replaces the original two-branch `if/else` with a single condition that checks both the presence of `remote->fetch` refspecs *and* whether `refspec_find_match()` succeeds. If either condition fails, the function falls back to `remote->refmap`. This resolves the ambiguity Knoble flagged while maintaining backward compatibility and the series’ design goal of treating `refmap` as a default namespace mapping. The updated logic is consistent with the documentation of `remote_find_tracking()` and avoids potential downstream issues in operations like `--delete-merged`.

No other changes are introduced in this revision. The patch remains part of the v10 series, which is otherwise unchanged and still **ready for merging to `next`**. The series’ core functionality (dynamic branch selection for shallow repositories, `--limited-fetch` flag, and shallow-repository defaults) is unaffected by this fix. The updated implementation now clearly aligns with the intended precedence rules: `remote->fetch` takes priority when it contains a matching refspec, and `remote->refmap` serves as a fallback otherwise. This should satisfy all prior review feedback.

This is a **design discussion reply** in the ongoing RFC thread about extending `git branch --delete-merged` to handle branches with gone upstreams. D. Ben Knoble responds to Harald Nordgren’s proposal to eliminate the `--into` flag by advocating for a **composable, filter-based interface** that unifies branch listing and deletion under a single mechanism.

Knoble argues that the current `--delete-merged` subcommand is a missed opportunity for composability, suggesting instead that Git should teach `--list` to filter branches by merge status (e.g., `--merged-upstream=<commit>`) and encourage users to pipe the output to `xargs git branch -d`. This approach would allow the proposed feature to be expressed as `git branch --list --merged-upstream=origin/main | xargs git branch -d`, eliminating the need for a separate `--into` flag or a dedicated `--delete-merged` subcommand. He notes that this design would also subsume the existing `--merged` filter, enabling more flexible workflows (e.g., combining `--merged` and `--merged-upstream` in a single command).

The reply highlights the tension between **CLI purity** (Nordgren’s preference for implicit behavior) and **composability** (Knoble’s preference for reusable filters). Knoble’s proposal aligns with his earlier stance (option C/E in the thread summary) but refines it further by framing the issue as a broader architectural opportunity: Git’s branch management commands could be simplified by making `--list` the primary interface for filtering, with deletion as a secondary step. This would avoid context-sensitive flags (e.g., `--into` only working with `--delete-merged`) and align with Git’s existing patterns (e.g., `git tag --list`).

Key technical details for future summarizers:
- **Proposed interface**: `git branch --list --merged-upstream=<commit>` to list branches with gone upstreams reachable from `<commit>`, followed by `xargs git branch -d`.
- **Files touched**: Likely `builtin/branch.c` (filter logic for `--list`), with no changes to on-disk format.
- **Edge cases**: The proposal does not address safeguards (e.g., stacked branches, worktrees) or triangular workflows, but Knoble’s earlier comments suggest these would remain unchanged.
- **Unresolved questions**: Whether to deprecate `--delete-merged` in favor of `--list` + `xargs`, and how to handle dry-run functionality (currently `--delete-merged --dry-run`).

The reply does not resolve the debate but shifts it toward a **unified filtering model**, which could simplify the CLI while preserving extensibility. The thread remains open, with no consensus on whether to adopt Knoble’s composable approach, Nordgren’s implicit behavior, or the author’s original `--into` flag.

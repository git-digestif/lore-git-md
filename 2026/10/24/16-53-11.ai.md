This is a **feature patch** implementing `--branch=<branch>` filtering for `git worktree list`, following Junio C Hamano’s suggestion to replace the earlier `--merged`/`--no-merged` proposal with a more general primitive. The patch is part of the worktree subsystem and touches `builtin/worktree.c`, `Documentation/git-worktree.adoc`, and `t/t2402-worktree-list.sh`.

The new `--branch` option lists only worktrees that have the specified branch checked out, including those in the middle of a rebase or bisect on that branch. It accepts multiple values and works with both short branch names (`topic`) and full ref names (`refs/heads/topic`). The implementation reuses Git’s existing branch-name validation and leans on `git branch` for filtering logic, allowing users to compose commands like `git worktree list $(git branch --format='--branch=%(refname)' --merged origin/main)` to list worktrees whose branches are merged into `origin/main`. Detached worktrees are never listed, and invalid branch names trigger an error.

The patch is well-structured and thoroughly tested. It adds a helper function `checked_out_branch()` that determines the branch a worktree is on, accounting for rebases and bisects, and a `filter_by_branch()` function that uses a `strset` to efficiently filter the worktree list. Tests cover edge cases: unborn branches, prunable worktrees, full ref names, tags with the same name as branches, and porcelain output. The documentation is clear and includes an example of composing with `git branch --merged`.

This version drops the original `--merged`/`--no-merged` design entirely, addressing Junio’s and Eric Sunshine’s feedback that the problem was better solved by a general filter primitive. The new approach is more flexible and composable, though it still leaves open the possibility of a future `git worktree foreach` mechanism (which Sunshine proposed and the author acknowledges but does not implement here). The patch is ready for review and looks like a solid foundation for worktree filtering.

Thread identity
Subject: [PATCH] completion: remove NO_PARSEOPT for commands using parse-options
Series version: v5 (three patches; centralized refactoring in `parse-options.c`; replaces v4 for `patch-id`, `diff-pairs`, `var`, and `fast-import`)
Originating author: Tanga Joris
Thread type: bug fix (user-visible completion regression)

Core problem or goal
Git’s Bash completion script was not offering command-line options for four built-in commands (`patch-id`, `diff-pairs`, `fast-import`, `var`) because they were still marked with the `NO_PARSEOPT` flag in `git.c` even though they had already been converted to use the `parse-options` API. The goal is to restore expected completion behavior for all four commands by centralizing `--git-completion-helper` handling in `parse-options.c`, avoiding per-command boilerplate and side effects like temporary file creation or blocking on input.

Current status
Cooking in `next` (Junio C Hamano marked the v5 series ready for integration on 2024-07-10). The series is now unblocked from a maintainer perspective but remains dependent on Christian Couder’s `cc/early-scan-options` series reaching stability and integration in `next`. No technical changes are required to either series at this stage. The three-patch series implements Junio’s proposed refactoring: the first patch moves completion-helper logic into `show_usage_with_options_if_asked()` in `parse-options.c`, the second patch removes the now-redundant `NO_PARSEOPT` flag from the four commands in `git.c`, and the third patch adds a defensive test in `t/t0012-help.sh` to catch future `NO_PARSEOPT` regressions. Tanga has addressed all prior feedback: René Scharfe’s edge case for `fast-import`, Kaartic Sivaraam’s suggestions for commit-message clarity, code documentation, and the defensive test, Cynthia Uche’s test-coverage gap for `--git-completion-helper-all`, and Junio’s documentation nit in `parse-options.h` (revised to focus on the function’s general purpose rather than over-specifying the `fast-import` edge case).

Key technical details
- Files touched: `parse-options.c` (adds six-line block to handle completion-helper flags in `show_usage_with_options_if_asked()`), `parse-options.h` (comment revised to clarify the function’s general purpose), `git.c` (removes `NO_PARSEOPT` from `patch-id`, `diff-pairs`, `fast-import`, `var`), `t/t9300-fast-import.sh` (two new tests), `t/t0012-help.sh` (defensive regression test)
- Symbols: `show_usage_with_options_if_asked()` now handles `--git-completion-helper` and `--git-completion-helper-all` generically; removes need for per-command boilerplate
- New behavior: Bash completion now shows available options for all four commands; `--git-completion-helper` and `--git-completion-helper-all` are handled immediately and consistently, avoiding side effects (e.g., no temporary files or blocking for `fast-import`)
- Old behavior: completion offered no options for any of the four commands; `fast-import --git-completion-helper` blocked waiting for input and created temporary pack files
- Edge case: `--git-completion-helper` and `--git-completion-helper-all` are now handled before any command-specific initialization (e.g., `fast_import_state_init()`), avoiding side effects
- Test coverage: two new tests in `t/t9300-fast-import.sh` verify no temporary files are created and the expected option list is printed for `fast-import --git-completion-helper` and `--git-completion-helper-all`; defensive test in `t/t0012-help.sh` greps for `--` to catch future `NO_PARSEOPT` regressions but skips five diff-related commands (`diff`, `diff-files`, `diff-index`, `diff-tree`, `difftool`) and `rev-parse` (which echoes arguments), and does not catch `var` because that command only has short options

Open questions and loose ends
- The series remains blocked on `cc/early-scan-options` reaching stability and integration in `next`
- No test coverage for the completion behavior of `patch-id` or `diff-pairs` (only `fast-import` is tested)
- The defensive test’s limitation with commands that only have short options (e.g., `var`) remains unresolved; the test is left as a separate patch as suggested by some reviewers, though others preferred squashing it into the second patch

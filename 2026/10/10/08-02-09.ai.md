This is a feature patch series (v8 of 5 patches) that introduces a new "matching-inspired" fetch mode for shallow repositories, addressing the long-standing performance issue where `git fetch` in a shallow clone negotiates history for all remote branches, even when the user only cares about a few. The series is now well-structured, with clear separation of concerns: Patch 1/5 adds the `remote.<name>.refmap` configuration, Patch 2/5 extracts a helper function to reduce code duplication, Patch 3/5 implements the core dynamic branch inference logic, and Patches 4/5 and 5/5 add the `--limited-fetch` flag and make it the default for shallow repositories.

The key technical change is the introduction of `remote.<name>.refmap`, which defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. When no explicit refspec is given and the remote has a refmap but no `remote.<name>.fetch` refspec, the new logic infers which branches to fetch by enumerating the branches tracked by local branches at that remote (via `@{upstream}`). This avoids the need to negotiate history for all remote branches, significantly improving performance in shallow repositories. The precedence rule (when both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, the former takes precedence) resolves the fatal error from earlier versions and is now uncontroversial.

The v8 update addresses all of Junio’s review concerns from v7: the hardcoded `the_repository` usage is fixed by threading a `struct repository *` parameter through callback data, the `inferred_branches` variable is renamed to `infer_from_refmap` for clarity, and the existing "fetch branches merged into the current branch" logic is extracted into a shared helper (`collect_upstream_from_remote`) to reduce duplication. The regression where the current branch’s `@{upstream}` could be dropped when `remote.<name>.fetch` was narrowed is also fixed. The test failures in `t5505` and `t5586` (caused by a textual conflict with Collin’s `ch/fetch-followremotehead-lazy-validation` topic in `seen`) are resolved, and the series is now ready for re-review.

The implementation touches `remote.c`/`remote.h` (refmap parsing and dynamic branch enumeration), `builtin/fetch.c` (integration with refmap configuration and dynamic branch inference), `builtin/remote.c` (adding the `--limited-fetch` flag and shallow-repository default), and documentation. The test coverage is thorough, with new tests in `t/t5586-fetch-refmap.sh` and updates to `t/t5505-remote.sh` and `t/t5510-fetch.sh` to verify edge cases like stale `HEAD` references and interactions with `fetch.followRemoteHEAD`. The documentation is clear and complete, explaining the new behavior and edge cases.

The series is now technically sound and addresses a real user pain point. The design is consensus-approved, and the remaining work is integration testing and final approval. The `--limited-fetch` flag (Patch 4/5) and shallow-repository default (Patch 5/5) are uncontroversial and ready to queue once the series is approved.

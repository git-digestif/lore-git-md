This is a feature patch series (v8) that introduces a "matching-inspired" fetch mode to solve a performance problem in shallow repositories. When a shallow clone (`git clone --depth=N`) is used with a remote that has many branches, a plain `git fetch` or `git pull` can be extremely slow or hang because Git negotiates history for *all* remote branches. This series lets users configure a remote to fetch only the branches that local branches track at that remote, avoiding the unnecessary overhead.

The core idea is a new `remote.<name>.refmap` configuration that defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch. When no explicit refspec is given and the remote has a refmap but no `remote.<name>.fetch` refspec, Git now infers which branches to fetch by looking at the `@{upstream}` settings of local branches. This is a targeted, opt-in solution that preserves backward compatibility: non-shallow repositories continue using wildcard refspecs by default, and the new behavior only kicks in when `remote.<name>.refmap` is configured.

v8 addresses all the technical feedback from Junio’s review of v7. The series is now split into five patches: the first two are preparatory (adding `remote.<name>.refmap` and extracting a helper function), the third implements the dynamic branch inference, and the last two add a `--limited-fetch` flag to `git remote add` and make it the default for shallow repositories. The refactoring in v8 fixes a regression that could drop the current branch’s `@{upstream}`, threads a `struct repository *` parameter through the code to avoid hardcoded `the_repository` usage, and improves code structure by extracting the existing "fetch branches merged into the current branch" logic into a shared helper. The test coverage is thorough, with new tests in `t/t5586-fetch-refmap.sh` and updates to `t5505-remote.sh` and `t5510-fetch.sh`.

The series is well-motivated and addresses a real pain point for users of shallow clones in large repositories. The implementation is careful: it avoids breaking existing workflows, handles edge cases (like remotes with no tracked branches), and integrates cleanly with Git’s existing refspec and refmap machinery. The unresolved textual conflict with Collin’s `ch/fetch-followremotehead-lazy-validation` topic in `seen` is the only remaining blocker, and Harald expects it to resolve when v8 is merged. This looks like a mature, well-crafted contribution that is ready for final review.

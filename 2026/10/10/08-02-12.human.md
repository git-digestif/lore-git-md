This is the third patch in Harald Nordgren’s v8 series introducing a "matching-inspired" fetch mode for shallow repositories. The patch implements the core logic that infers which branches to fetch when a remote is configured with `remote.<name>.refmap` but no `remote.<name>.fetch` refspec.

When no explicit refspec is given, the new code enumerates all local branches whose `@{upstream}` points to the remote being fetched, then constructs a dynamic refspec from those branches. This avoids negotiating history for all remote branches, which is especially valuable in shallow repositories where the default wildcard refspec would otherwise fetch everything. The implementation is clean: it adds a new helper (`branches_tracking_remote`) in `remote.c` that iterates over local branches, collects the source ref for each branch whose `remote_name` matches the target remote, and populates a `string_list` with the results. The `get_ref_map` function in `builtin/fetch.c` then uses this list to build the refspec and passes it to the transport layer.

The patch also updates the transport layer’s `ref_prefixes` to limit the refs requested from the remote, ensuring the optimization propagates all the way down. Documentation is updated to clarify that a refspec-less fetch against a refmap-only remote now infers branches from local `@{upstream}` settings rather than fetching every branch. The test coverage is thorough: the new `t5586-fetch-refmap.sh` script verifies edge cases like a bare fetch with no tracked branches, duplicate fetches when multiple local branches track the same upstream, and proper isolation when branches track different remotes.

This is a well-crafted feature patch that addresses a real performance pain point. The design is consensus-approved, the implementation is clean, and the test coverage is complete. The only remaining question is whether the matching-inspired mode should be available outside of shallow repositories, but that is a minor design choice that can be addressed in follow-up work. The series as a whole is a strong candidate for merging to `next` once Junio re-reviews it.

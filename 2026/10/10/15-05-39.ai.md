This is a feature patch resubmission (v4) for the `git repo structure` command, adding revision-based filtering to allow users to analyze subsets of the repository object graph. The patch is part of a single-patch series and addresses the procedural blocker from v3: the accidental corruption of comments in `revision.c` and `revision.h` has been fixed. The core goal remains unchanged—enabling targeted diagnostic analysis in large repositories—but the implementation now uses Git’s standard `setup_revisions()` machinery, replacing the v1 `--no-<reftype>` approach with a more flexible design that supports arbitrary revision specifications (e.g., `git repo structure --branches --not --tags`).

The v4 patch modifies three files: `builtin/repo.c` (adding revision-parsing logic via `struct rev_info` and `setup_revisions()`), `Documentation/git-repo.adoc` (documenting the new syntax), and `t/t1901-repo-structure.sh` (expanding test coverage to 211 lines). The implementation processes objects reachable from included revisions unless they are exclusively reachable via excluded revisions, avoiding the transitive dependency omission issue of v1. However, it retains the double ref-walk inefficiency in `count_references()` due to `setup_revisions()`’s lack of a custom ref-walk callback, which could impact performance for complex revision specifications or large repositories.

Key unresolved issues from prior versions persist. The commit message still lacks a clear justification for *why* revision-based filtering is valuable (e.g., how it improves diagnostic workflows), despite the cover letter’s motivation. Documentation precision remains an open question: Patrick Steinhardt’s request to align terminology with Git’s conventions (e.g., "revisions" instead of "query clauses") and standardize the synopsis to `[<revs>...]` is unaddressed. The revision-parsing defaults (`.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`) may be overly restrictive, preventing filtering by trees or blobs, and test coverage for edge cases like `--filter=object:type=blob` is missing. The author’s tone in the cover letter suggests frustration with the procedural hiccup but no substantive engagement with the technical feedback.

The patch is now procedurally clean—no accidental corruption—but still requires significant work to address the substantive concerns raised in v2 and v3. Patrick’s review remains the most critical: his questions about revision-parsing defaults, test coverage, and documentation precision are unanswered, and the double ref-walk inefficiency is unacknowledged. Until these are resolved, the patch is unlikely to progress. Reviewers will likely focus on the commit message’s motivation, documentation alignment, and whether the double ref-walk is acceptable for a diagnostic tool.

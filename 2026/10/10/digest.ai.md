## Notable threads

### rerere: fix race condition between rebase and background maintenance
Thomas Bachem’s two-patch series addressing a long-standing race condition in Git’s `rerere` subsystem reached its final polish today. The series introduces a configurable timeout (`rerere.lockTimeout`, defaulting to 1000 ms) for the `MERGE_RR.lock` file and a hidden `--skip-locked` flag for `git rerere gc`, allowing auto-maintenance tasks to skip silently if the lock is held.

Today’s developments focused on mechanical refinements to the second patch. Patrick Steinhardt’s feedback targeted commit message wording, code comments, and API design. Thomas accepted all suggestions, agreeing to: add a final paragraph explaining why `--skip-locked` is hidden (to match the pattern of `--skip-foreground-tasks` in `git gc`); drop a layering-violating comment in `rerere.c`; clarify that `RERERE_NOWAIT` returns `-1` when the lock is held (treated as "nothing to do" by callers); replace a shared bitmask flag with a dedicated `enum rerere_gc_flags` for `rerere_gc()`; and split an existing test into two cases—one verifying `--skip-locked` skips when locked, another verifying it does not skip when unlocked.

The series also dropped the controversial third patch from v6, which would have allowed conflict-stopping commands to proceed with a warning if the lock remained held. This change reflects Patrick’s objection that the behavior was "fishy" and unnecessary without real-world user reports. The current approach is more conservative: if the lock cannot be acquired after the timeout, commands fail outright, ensuring correctness over resilience.

All substantive review feedback has been incorporated, and the series is technically ready for integration. Junio has not yet commented on the final version, but the patches are well-motivated, with clear commit messages, thorough test coverage, and a pragmatic design that balances robustness with backward compatibility.

### fetch: introduce `+:` refspec for matching-inspired fetch mode
Harald Nordgren’s v8 series introducing a matching-inspired fetch mode for shallow repositories addressed Junio’s latest review feedback today. The series adds `remote.<name>.refmap` to define namespace mappings without specifying what to fetch, enabling `git fetch` to dynamically infer which branches to fetch based on local branches’ `@{upstream}` settings. This avoids negotiating history for all remote branches, significantly improving performance in shallow repositories.

Junio’s review of patch 2/5 identified two issues requiring a respin: the `if/else if/else` control-flow reorganization belongs in patch 3/5 (the feature patch) rather than this refactoring patch, and the new `collect_upstream_from_remote()` helper lacks the NULL-check for `branch` that was present in the original code, risking a segfault if `repo_branch_get()` returns NULL. Harald acknowledged both points and will respin the patch to defer the control-flow changes and restore the NULL-check.

Patch 4/5, which adds `--limited-fetch` to `git remote add`, received a surface-level review from Junio, who acknowledged it as straightforward and well-executed. The patch configures the remote to use `remote.<name>.refmap` instead of the traditional wildcard `remote.<name>.fetch` refspec, ensuring `git fetch <name>` only fetches branches already tracked by local branches. The flag is rejected when combined with `-t/--track` or `--mirror`, as those options already specify explicit fetch behavior.

The series is now technically sound, with all prior review concerns addressed. The only unresolved question is whether the matching-inspired mode should be available outside of shallow repositories, but this is a minor design choice for follow-up work. The series is a strong candidate for merging to `next` pending Junio’s re-review of the respun patch 2/5.

### checkout -m: remember original conflict labels
Junio C Hamano submitted a follow-up refactoring patch today to optimize Phillip Wood’s v3 series teaching `git checkout -m` to remember original conflict labels. The patch introduces `struct checkout_merged_data` to cache per-invocation constants like `renormalize` and `conflict_style`, eliminating redundant config reads and file I/O for `.git/MERGE_LABELS`. The optimization avoids repeatedly reading the same configuration and labels file for every conflicted path during a single `git checkout -m` invocation.

The patch is a pure refactoring with no user-visible behavior change. It touches only `builtin/checkout.c` and aligns with Git’s pattern of caching per-invocation state (e.g., in-core configset cache). The change is uncontroversial and ready for integration, though Junio suggested it could be kept as a separate patch (e.g., "PATCH 1.5/2") or squashed into Phillip’s original patch 2/2. The series itself is queued for integration in `next` after Junio’s explicit acceptance in his final reply to v3.

### repo: add revision filtering support to 'git repo structure'
Mark C. Chu-Carroll posted v4 of his patch adding revision-based filtering to `git repo structure`, fixing the accidental corruption in `revision.c` and `revision.h` that blocked v3. The patch uses Git’s standard `setup_revisions()` machinery to allow users to include or exclude specific revisions (commits, refs, or ranges) from the repository structure report, enabling targeted diagnostic analysis of large repositories.

The v4 patch retains the double ref-walk inefficiency noted in prior reviews: `setup_revisions()` performs an initial ref-walk, and `count_references()` performs a second walk to count references by type, as `setup_revisions()` lacks a custom ref-walk callback. Key unresolved issues from earlier versions persist, including the commit message’s lack of justification for *why* revision filtering is valuable, documentation precision (Patrick Steinhardt’s request to align terminology with Git’s conventions), and the revision-parsing defaults (`.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH`), which may be overly restrictive. The author’s v4 cover letter acknowledges the procedural fix but does not engage with these substantive concerns.

The patch is now procedurally clean but remains blocked by unaddressed feedback. Patrick’s review—focusing on commit message motivation, documentation precision, revision-parsing defaults, test coverage, and the double ref-walk inefficiency—remains the most critical. A v5 addressing these points may be necessary for the patch to progress.

### sha1dc-accel: faster SHA-1 collision detection
The `sha1dc-accel` series saw licensing policy follow-ups today, with D. Ben Knoble and Todd Zullinger clarifying how distributions handle Git’s mixed-license codebase. Knoble noted that Gentoo’s Git package lists only GPL-2, despite including MIT-licensed code (the existing `sha1dc` and proposed `sha1dc-accel` subsystems). Zullinger reiterated that Fedora’s Git package lists all licenses involved—BSD-3-Clause, GPL-2.0-only, GPL-2.0-or-later, LGPL-2.1-or-later, and MIT—citing Fedora’s packaging guidelines, which explicitly reject the idea of an "effective license" and require listing every license that applies to any part of the package.

The exchange confirmed that mixed-license components are handled transparently in downstream distributions, aligning with Junio’s earlier clarification that Git’s GPL-2-only stance is compatible with MIT-licensed code, provided the original license and copyright notices are preserved. The discussion is now fully resolved in the context of the `sha1dc-accel` series, which is legally ready for integration.

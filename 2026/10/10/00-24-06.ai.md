This is a follow-up refactoring patch from Junio C Hamano, responding to Phillip Wood’s v3 series that teaches `git checkout -m` to remember original conflict labels. The patch is a performance optimization that avoids repeatedly reading the same configuration and `.git/MERGE_LABELS` file for every conflicted path during a single `git checkout -m` invocation.

The change introduces a new `struct checkout_merged_data` to hold per-invocation constants like `renormalize` and `conflict_style`, and adds `checkout_merged_prepare()` and `checkout_merged_release()` functions to initialize and clean up this data. The core logic in `checkout_merged()` is updated to use the precomputed values instead of repeatedly querying the configuration or reading the labels file. The patch touches only `builtin/checkout.c` and is a pure refactoring with no user-visible behavior change.

Junio’s motivation is clear: the current implementation reads `merge.renormalize` and `.git/MERGE_LABELS` once per conflicted path, which is inefficient since these values remain constant during a single `git checkout -m`. The overhead of repeated file I/O and parsing is small but measurable, especially in repositories with many conflicts. The patch is a straightforward optimization that aligns with Git’s pattern of caching per-invocation state (e.g., in-core configset cache).

The patch is well-structured and addresses the performance concern without complicating the code. It is a natural follow-up to Phillip’s series and does not introduce new edge cases or compatibility concerns. The only open question is whether this should be squashed into Phillip’s original patch 2/2 or kept as a separate patch (Junio’s suggestion of a "PATCH 1.5/2" implies the latter). Either way, the change is uncontroversial and ready for integration.

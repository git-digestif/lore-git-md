This is a feature patch (v4) for the `git repo structure` command, adding revision-based filtering to let users analyze subsets of the repository object graph. The patch is procedurally clean—fixing the accidental corruption in `revision.c` and `revision.h` that blocked v3—but still leaves key technical concerns unaddressed.

The implementation uses Git’s standard `setup_revisions()` machinery to parse revision specifications (e.g., `git repo structure --branches --not --tags`), replacing the v1 `--no-<reftype>` approach with a more flexible design. However, it retains an awkward trade-off: because `setup_revisions()` lacks a custom ref-walk callback, the patch performs a second ref-walk in `count_references()` to count references by type, which could hurt performance for large repositories or complex revision specs. The author acknowledges this inefficiency in the commit message but does not discuss mitigations.

Documentation and tests have been updated to reflect the new syntax, with test coverage expanded to 211 lines. The tests now validate edge cases like overlapping includes/excludes and output formats (table/lines/nul), but Patrick Steinhardt’s requests for tests involving trees/blobs and revision options like `--filter=object:type=blob` remain unaddressed. The commit message still lacks a clear justification for *why* revision-based filtering is valuable—despite the cover letter’s motivation—leaving reviewers to infer the use case (diagnosing performance issues in large repositories).

The patch is now eligible for substantive review, but its readiness hinges on resolving Patrick’s unanswered concerns: commit message motivation, documentation precision (aligning terminology with Git conventions), revision-parsing defaults (`.def = "HEAD"` and `.revarg_opt = REVARG_COMMITTISH` may be overly restrictive), and the double ref-walk inefficiency. Until these are addressed, the patch is unlikely to progress. The feature itself is uncontroversial, but the implementation details need refinement.

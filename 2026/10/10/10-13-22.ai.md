This is the final version (v7) of a two-patch bugfix series targeting the `rerere` subsystem. It resolves a long-standing race condition where concurrent `rerere` operations—particularly background maintenance tasks like `git rerere gc`—could deadlock or kill an in-progress rebase when both tried to acquire the shared `MERGE_RR.lock`. The issue became more pronounced with Git 2.54’s geometric maintenance strategy, which triggers `rerere gc` more aggressively, but the root cause is a general locking flaw in `rerere`.

Patch 1 introduces a configurable timeout (`rerere.lockTimeout`, defaulting to 1000 ms) for the `MERGE_RR.lock`. Instead of failing immediately when the lock is held, processes now wait up to the timeout before giving up. This preserves backward compatibility (a timeout of 0 restores the old behavior) and aligns with how other Git subsystems handle lock contention. The patch touches `rerere.c`, `rerere.h`, and adds test coverage in `t/t4200-rerere.sh` to verify the timeout behavior under various scenarios, including explicit `rerere` commands like `forget`, `clear`, and `gc`.

Patch 2 adds a hidden `--skip-locked` flag to `git rerere gc`, designed specifically for auto-maintenance tasks (`git maintenance run --auto` and `git gc --auto`). When the lock is held, these tasks now skip silently instead of waiting or failing, matching the established pattern of other maintenance operations (e.g., `git gc --skip-foreground-tasks`). The flag is intentionally undocumented and restricted to the `gc` subcommand to prevent misuse. The patch also introduces a dedicated `enum rerere_gc_flags` for `rerere_gc()` to avoid overloading the existing bitmask, and updates `builtin/gc.c` to pass the new flag in auto mode. Test coverage in `t/t4200-rerere.sh` and `t/t7900-maintenance.sh` verifies that `--skip-locked` behaves correctly whether the lock is held or free.

The series drops the controversial third patch from v6, which would have allowed conflict-stopping commands to proceed without `rerere` if the lock remained held. This change reflects feedback from Patrick Steinhardt, who argued that the behavior was "fishy" and unnecessary without real-world user reports of the issue. The current approach is more conservative: if the lock cannot be acquired after the timeout, commands fail outright, ensuring correctness over resilience.

All substantive review feedback from Phillip Wood, Patrick Steinhardt, and Junio C Hamano (on earlier versions) has been incorporated. The series is technically ready for integration, though Junio has not yet commented on the final version. The patches are well-motivated, with clear commit messages, thorough test coverage, and a pragmatic design that balances robustness with backward compatibility. The only unresolved discussion points are philosophical (e.g., whether garbage collection is useful mid-rebase), but these do not block the current fix.

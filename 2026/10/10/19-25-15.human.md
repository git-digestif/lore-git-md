This is the first patch in a two-part series that hardens the `git blame` ignore-revs parser and tag-peeling logic. The goal is to make the parser robust enough to safely handle upstream-controlled content before exposing it to `HEAD:.git-blame-ignore-revs` as a default ignore file in the follow-up patch. The hardening focuses on two areas: rejecting lines with embedded NUL bytes and preventing unintended promisor fetches in partial clones.

The author, Ravi Mistry, responds here to Junio’s feedback on the NUL-byte rejection. Junio questioned whether the new `memchr()` check was necessary, noting that the existing parser already fails safely on malformed object names (e.g., trailing whitespace after a NUL). Ravi agrees there is no security implication and clarifies that the NUL check was added for consistency with how other trailing garbage is rejected. He offers to drop the NUL check entirely if Junio prefers, signaling flexibility on this point.

The hardening itself remains uncontroversial and well-motivated. The promisor fetch prevention (using `odb_read_object_info_extended()` with `OBJECT_INFO_SKIP_FETCH_OBJECT`) is particularly important for partial clones, where lazy-fetching ignored revisions would be surprising and undesirable. The tag-peeling logic also verifies each tag’s declared type before parsing, preventing type confusion. Test coverage is thorough, with new cases for NUL-byte rejection and partial-clone tag peeling.

This patch is not yet ready for integration, as the security hardening still needs broader review from contributors like Jeff King and brian m. carlson. However, the design direction is settled, and the implementation is feature-complete. The author’s willingness to drop the NUL check suggests the series is close to final form, pending any additional security-focused feedback. Worth watching for further review, but the patch itself is clearly well-crafted and addresses a real problem.

This is the second patch in a two-part bugfix series for the `rerere` subsystem, addressing a race condition where background maintenance tasks like `git rerere gc` could collide with concurrent `rerere` operations (e.g., during a rebase). The patch introduces a hidden `--skip-locked` flag for `git rerere gc`, allowing auto-maintenance tasks to silently skip garbage collection when the `MERGE_RR.lock` is held, rather than waiting or failing. This aligns with the behavior of other maintenance tasks (e.g., `git gc --skip-foreground-tasks`) and prevents disruptions to in-progress operations.

The implementation is narrowly scoped: the `--skip-locked` flag is restricted to the `gc` subcommand and undocumented to avoid misuse, matching the pattern of similar flags in `git maintenance`. The patch updates `builtin/gc.c` to pass the flag during auto-maintenance runs and modifies `rerere.c` to handle the new `RERERE_NOWAIT` flag, which skips lock acquisition entirely if the lock is held. Test coverage in `t/t4200-rerere.sh` and `t/t7900-maintenance.sh` verifies that `--skip-locked` behaves correctly—skipping when locked and proceeding when unlocked—while manual `rerere gc` calls continue to wait and fail as before.

The design reflects feedback from Patrick Steinhardt and Phillip Wood, who emphasized the need for a conservative approach that prioritizes correctness over resilience. By making auto-maintenance tasks non-blocking, the patch avoids impeding other housekeeping tasks while preserving the existing behavior for explicit user commands. The commit message clearly explains the rationale, and the code changes are minimal and well-targeted. This patch, combined with the first (which introduced a configurable lock timeout), provides a pragmatic solution to a long-standing robustness issue in `rerere` locking. The series is now technically complete and ready for integration.

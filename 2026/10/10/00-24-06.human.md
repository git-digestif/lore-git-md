This is a follow-up from Junio to Phillip Wood’s v3 series that teaches `git checkout -m` to remember the original conflict labels. The series is already queued for integration in `next`, but Junio suggests a small performance optimization before it graduates to `master`.

The patch Junio proposes is a preparatory refactoring that avoids repeatedly reading the same configuration (`merge.renormalize`) and the `.git/MERGE_LABELS` file for every conflicted path during a single `git checkout -m` invocation. Currently, `checkout_merged()` is called once per conflicted path, and each call reads the config and the labels file, even though their contents do not change. Junio’s patch introduces a `struct checkout_merged_data` to hold these "per-invocation constants," reads them once in a new `checkout_merged_prepare()` function, and reuses them across all calls to `checkout_merged()`. The labels themselves are not yet added to the struct; that would be done in a follow-up patch (effectively splitting the existing v3 patch 2 into two steps).

The change is purely internal and does not alter user-visible behavior. It touches only `builtin/checkout.c`, adding about 30 lines of code. The patch is clean and uncontroversial: it is a straightforward performance tweak that aligns with Git’s existing patterns (e.g., in-core configset cache). Junio’s suggestion is not a blocker for the series, but it is a sensible improvement that would reduce unnecessary I/O and allocations during conflict resolution. The series remains on track for `master`; this is just a polish step.

This is the second patch in the final (v7) two-patch bugfix series targeting the `rerere` subsystem. It introduces a hidden `--skip-locked` flag for `git rerere gc`, designed specifically for auto-maintenance tasks like `git maintenance run --auto` and `git gc --auto`. When the `MERGE_RR.lock` is held, these tasks now skip silently instead of waiting or failing, aligning with the established pattern of other maintenance operations (e.g., `git gc --skip-foreground-tasks`).

The patch updates `builtin/gc.c` to pass `--skip-locked` when running in auto mode, and modifies `builtin/rerere.c` to accept the flag only for the `gc` subcommand (rejecting it for other subcommands like `clear` or `forget`). The `rerere.c` locking logic now handles a new `RERERE_NOWAIT` flag, which sets a zero timeout and returns `-1` if the lock is held, treated as "nothing to do" by callers. Documentation in `Documentation/config/rerere.adoc` explicitly names the auto-maintenance callers and explains the flag's purpose.

Test coverage in `t/t4200-rerere.sh` verifies that `--skip-locked` skips when the lock is held but still prunes when the lock is free, and that the flag is rejected for non-`gc` subcommands. `t/t7900-maintenance.sh` confirms that auto-maintenance succeeds even when the lock is held, while manual maintenance fails as expected.

The patch is technically complete, with all prior feedback incorporated. It avoids overloading the existing bitmask by introducing a dedicated `enum rerere_gc_flags` for `rerere_gc()`, and the flag is intentionally hidden (`OPT_HIDDEN_BOOL`) to prevent misuse. The design is conservative: manual invocations of `git rerere gc` still wait and fail if the lock remains held, ensuring correctness over resilience. The only unresolved discussion points are philosophical (e.g., whether garbage collection is useful mid-rebase), but these do not affect the patch's correctness or readiness.

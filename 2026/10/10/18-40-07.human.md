This is the **second patch in a two-part feature series** that makes `git blame` and `git annotate` automatically use `HEAD:.git-blame-ignore-revs` as the default ignore-revs file when none is explicitly configured. The series is now feature-complete, with the first patch hardening the ignore-revs parser against malformed input (NUL bytes) and promisor fetches in partial clones, and this patch implementing the default file lookup.

The patch itself is straightforward and well-executed: when no ignore file is specified, Git checks for a `.git-blame-ignore-revs` blob in the `HEAD` tree, parses it in memory using the hardened parser from patch 1/2, and adds it to the ignore list *before* any user-configured files. It handles edge cases like subdirectory invocations, bare repositories, committed symlinks, and CLI/config overrides (e.g., `blame.ignoreRevsFile=""` or `--no-ignore-revs-file` bypasses the default). The implementation is clean, with good test coverage in `t/t8013-blame-ignore-revs.sh`.

Junio’s feedback here is **purely procedural**—he notes that the refactoring of `oidset_parse_file_carefully()` to extract a helper function (`parse_oidset_line()`) logically belongs in patch 1/2 (the security hardening commit) rather than here. This is a minor nit about patch organization, not a functional issue, and the code itself is approved ("OK", "Good", "Very clean"). The author agrees to move the refactoring in the next revision.

The only open question is whether the security hardening in patch 1/2 is sufficient, as it touches parsing and network behavior in a security-sensitive context. Junio has already weighed in favorably on the promisor fetch prevention but questions whether the NUL-byte rejection is overly aggressive. Broader review from security-interested contributors (e.g., Jeff King, brian m. carlson) would help settle this. The patch is otherwise **ready for integration** once the procedural nit is addressed.

For developers who use `git blame` or work with hosting platforms like GitHub and GitLab, this patch aligns local behavior with those platforms’ defaults, making it a small but practical improvement. The security hardening is a necessary prerequisite and may be of independent interest to those concerned with robust parsing. **Worth watching** if you care about blame workflows or security-sensitive code paths.

This is a documentation patch that proposes a formal voting process for the Git project. It follows up on the Git Contributor’s Summit 2026 discussion about AI contribution policy, where the community agreed that a vote would be needed to resolve the contentious issue. Emily Shaffer is now formalizing the *process* for such votes, not the AI policy itself.

The patch adds a new document, `Documentation/CommunityVoting.adoc`, outlining a three-phase process: proposal collection and refinement (4 weeks), a two-week voting window, and immediate implementation of the winning proposal. Eligibility to vote is restricted to contributors with at least one merged commit in `next` or two code reviews, and contributions must predate the vote kickoff to prevent dogpiling. The patch also updates `Documentation/DecisionMaking.adoc` to reference the new voting process.

Emily flags several open questions in her self-review: the voting mechanism (Debian’s devotee, Linux Foundation’s CIVS, or GitHub polls), how to restrict votes to eligible participants, and whether to expand eligibility beyond code contributions. The patch is well-structured and addresses a real need—Git has no documented process for resolving contentious decisions, and the AI policy vote will be the first test case. The proposal is pragmatic, balancing inclusivity with safeguards against manipulation, and the commit message is clear about the motivation and next steps. This looks like a solid foundation for the upcoming vote.

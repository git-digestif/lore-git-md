This is the sixth patch in Patrick Steinhardt’s seven-patch v2 series introducing the **object storage extension**, a foundational step toward pluggable object database backends in Git. This patch wires up the new `--object-storage-format=` option in `git clone`, mirroring the functionality added to `git init` in the preceding patch (5/7). The implementation is straightforward and follows established patterns, but it introduces a **pragmatic restriction**: local clones (hardlinking or copying objects) are disabled when either the source or destination repository uses a non-default object storage format, falling back to a non-local transport with a warning or failing if `--local` was explicitly requested.

The patch touches `builtin/clone.c`, `Documentation/git-clone.adoc`, and the test suite (`t/t5601-clone.sh`). The core logic is minimal: the new option is parsed and validated using the existing `odb_source_type_by_uri()` helper, then passed to `create_repository()`. The `is_using_default_object_storage_format()` helper checks whether a repository uses the default `files` backend (with no payload), and the local clone logic is updated to bail or warn accordingly. Tests cover the new option, payload handling, error cases (invalid formats, local clone restrictions), and integration with bundle URIs.

The local clone restriction is explicitly documented in the man page and justified as a temporary measure to avoid complexity in the initial implementation. The patch does not attempt to handle the edge case where the `files` backend is configured with an alternative object directory path (e.g., `files:///path/to/dir`), deferring that to future work. This limitation is unlikely to be controversial, as the restriction is clearly scoped and the fallback behavior is user-friendly.

The implementation is **mechanical and correct**, reusing the validation logic and configuration patterns established in earlier patches. The test coverage is thorough, verifying both happy paths and error cases. No substantive review feedback has been recorded for this patch, but it is uncontroversial and aligns with the series’ overall design. The primary value here is completing the CLI integration for `git clone`, which is essential for end-to-end usability of the object storage extension.

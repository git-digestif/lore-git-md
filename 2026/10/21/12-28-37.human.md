This is the third and final patch in Harald Nordgren’s v3 series extending `git branch --delete-merged` to detect squash-merged branches. It introduces the `--squashed` flag, which enables detection of branches whose changes were integrated via squash merges (including GitHub’s "Squash and merge" button) even when upstream modified the same files after the branch was forked.

The patch implements a three-way merge approximation for each file changed by the branch: it merges the branch’s version into the upstream version and treats the change as "landed" if the merge leaves the upstream version unchanged. This approach is intentionally lenient—it checks whether the upstream commit *contains* the branch’s changes, not whether it is *exactly* the result of a squash merge—so it may attribute the branch to an upstream commit that includes unrelated modifications. The algorithm avoids rename detection and is slower than the rebase detection added in the second patch, as it must read file contents. In partial clones, it transparently fetches blobs on first use (13 blobs in Jasper Mayone’s testing, taking 0.42 seconds).

The implementation is clean and well-structured, with clear separation from the rebase-detection logic. It adds thorough test coverage for edge cases (upstream modifications, reverted squashes, mixed workflows) and updates the documentation to explain the flag’s behavior and performance trade-offs. The `--squashed` flag is opt-in (defaults to off) and rejected if used without `--delete-merged`, addressing earlier concerns about false positives and performance.

This patch completes the series, which is now feature-complete and ready for integration. The remaining discussion centers on whether the current CLI design (unified `--delete-merged` with `--squashed`) or Junio’s proposed split (`--delete-merged` vs. `--delete-irrelevant`) better serves user needs. The squash-detection implementation itself is uncontroversial and appears robust.

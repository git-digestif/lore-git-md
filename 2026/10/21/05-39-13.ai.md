This is the v2 cover letter for Patrick Steinhardt’s seven-patch series introducing the **object storage extension**, a foundational step toward pluggable object database backends in Git. The series defines the `extensions.objectStorage` configuration mechanism (modeled after the existing ref storage extension) and implements the baseline `files` backend, which supports relocating the `.git/objects` directory via a payload (e.g., `files://objs` moves objects to `.git/objs`).

Key changes in v2 center on **initialization robustness**: the `object_storage_format` field in `struct repository` is now always populated (defaulting to `"files"`), addressing a design concern raised by Karthik Nayak in v1 about exposing hard-coded defaults in inspection tools. The series also propagates the object storage format through `git clone`, `git init`, and `git submodule`, with new command-line options (`--object-storage-format=`), environment variables (`GIT_OBJECT_STORAGE_FORMAT`), and user-facing configuration (`init.defaultObjectStorageFormat`). Inspection tools (`git rev-parse --show-object-storage-format` and `git repo objects.storageFormat`) allow users to query the active backend.

The implementation remains **backward-compatible**: the default `files` backend preserves the traditional `.git/objects` layout, and no on-disk format changes are introduced. However, the series imposes a **pragmatic restriction** on local clones (hardlinking or copying objects) when either the source or destination repository uses a non-default object storage format, falling back to a non-local transport or failing if `--local` is explicitly requested. This limitation is explicitly called out as a deliberate trade-off to avoid complexity in the initial implementation.

The series touches core subsystems (`odb/`, `setup.c`, `repository.c`) and adds new symbols (config keys, CLI options, environment variables, and helper functions like `repo_set_object_storage_format()`). Tests cover initialization, cloning, submodule propagation, schema validation, and error cases (e.g., invalid formats, reinitialization with mismatched storage). The prerequisite topics (`ps/odb-files-alternates` and `ps/setup-enforce-repo-passed-to-create-repository-has-no-state`) are merged, and the series is rebased on `c51408889c` (The 6th batch, 2026-10-16).

**Open design questions** from v1 remain unresolved but are now considered non-blocking:
- **Path normalization**: Karthik Nayak’s suggestion to normalize relative paths to absolute paths (mirroring the ref storage extension) was deferred to avoid breaking tests. The current implementation accepts relative paths, but this may change if the backend later relaxes directory creation rules.
- **Naming subtlety**: The distinction between `object.format` (hash algorithm) and `objects.storageFormat` (storage backend) in `git repo` output was acknowledged as a potential source of user confusion but accepted as a pragmatic compromise after a recent patch series renamed `references.format` to `references.storageFormat` to avoid a three-way conflict. Renaming `object.format` to `objects.format` was deemed out of scope due to cascading changes to config options.

The series is **architecturally uncontroversial** in its baseline implementation, following established patterns for ref storage and addressing core functionality (configuration, inspection, cloning, submodule propagation). The local clone restriction may attract discussion about whether it is too conservative, but the restriction is clearly documented and justified as a temporary measure. No substantive review feedback has been recorded for patches 5/7–7/7, and the series as a whole appears ready for deeper technical review. The primary value of this v2 is the **initialization fix** and the completion of submodule integration (patch 7/7), which was missing in v1.

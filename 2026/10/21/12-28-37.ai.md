This is the third patch in Harald Nordgren’s v3 series extending `git branch --delete-merged` to detect squash-merged branches. It introduces the `--squashed` flag, which enables detection of branches whose changes were integrated via squash merges (including GitHub’s "Squash and merge" button) even when upstream modified the same files after the branch was forked.

The patch implements squash detection by performing a path-by-path three-way merge between the branch’s version, the upstream version, and the fork point. If the merge leaves the upstream version unchanged, the branch’s changes are considered "landed" and the branch is eligible for deletion. This approach is intentionally lenient: it checks whether the upstream commit *contains* the branch’s changes, not whether it is *exactly* the result of a squash merge. The leniency may lead to false positives (e.g., attributing a branch’s changes to an unrelated upstream commit that happens to include them) but avoids the complexity and performance cost of stricter methods like test merges or patch IDs.

The implementation touches `builtin/branch.c`, adding a new `DELETE_BRANCH_SQUASHED` flag, extending the `branch_change` structure to track base, branch, and upstream object IDs, and introducing helper functions (`merge_keeps_upstream`, `change_state_at`) to handle the three-way merge logic. The `changes_landed` function is updated to defer the merge check until after all files are classified, ensuring that blob fetches (which may be needed for the merge) are batched and only performed when `--squashed` is used. The patch also updates `Documentation/git-branch.adoc` to document the new flag and its performance implications (slower execution, potential blob downloads in partial clones).

Test coverage in `t/t3200-branch.sh` is expanded to verify the new behavior, including edge cases like upstream modifications to the same files, squash merges that were later reverted, and the rejection of `--squashed` when used without `--delete-merged`. The tests confirm that the feature works as intended: branches are correctly identified as squash-merged even when upstream changed the same files, and the output format (`Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`) provides clear attribution.

The patch is well-structured and addresses the performance concerns raised in earlier reviews by making `--squashed` opt-in (defaults to off) and avoiding blob fetches unless the flag is used. It complements the rebase-detection logic introduced in the second patch, completing the series’ goal of unifying squash and rebase detection under `--delete-merged`. The remaining discussion centers on whether this unified approach or Junio’s proposed `--delete-irrelevant` split better serves user needs, but the implementation itself is technically sound and ready for integration.

This is patch 8/13 in the SHA-1/SHA-256 interoperability series, focusing on **pack index v3 support**. The patch ensures that when Git streams a large blob directly into a pack (bypassing the loose object store), it also computes and stores the object ID for the compatibility hash algorithm in the pack index. Without this change, compatibility repositories would store null OIDs in the index, corrupting the repository.

The patch modifies `object-file.c` to extend the `stream_to_pack` function with an optional `compat_ctx` parameter. When a compatibility algorithm is configured, the function now updates both the primary and compatibility hash contexts as data is streamed. In `odb_transaction_files_write_object_stream`, the patch initializes the compatibility hash context, finalizes the compatibility object ID after streaming, and stores it in the `compat_oid` field of the `pack_idx_entry` structure. The change is minimal and targeted, touching only the streaming code path and avoiding disruption to other object storage mechanisms.

A new test in `t1016-compatObjectFormat.sh` verifies the fix by creating a compatibility repository, configuring a low `core.bigFileThreshold` to force streaming, adding a 5KB file, and confirming that the object is correctly stored in the pack and retrievable via both its primary and compatibility object IDs. The test is well-scoped and covers the specific scenario the patch addresses.

This is a **bugfix** for a subtle but critical issue in the interoperability effort. The change is technically sound, with clear motivation and thorough test coverage. The patch does not introduce new configuration options or user-visible behavior changes; it simply ensures that compatibility object IDs are computed and stored correctly during pack streaming. The fix is a necessary step toward full SHA-256 interoperability and integrates cleanly with the rest of the series. No review feedback has been received yet, but the patch looks ready for serious consideration.

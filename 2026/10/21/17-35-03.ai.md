This is a **substantive user report and review** on Harald Nordgren’s v3 patch series extending `git branch --delete-merged` to detect squash-merged and rebase-merged branches. Jasper Mayone provides hands-on validation of the implementation, confirming its correctness and performance while reinforcing Junio C Hamano’s architectural concerns about the CLI design.

The email reports that v3 behaves as documented: without `--squashed`, the command deletes branches whose exact file versions appear upstream (handling rebase merges, GitHub-style squashes, and even squashes later reverted), while `--squashed` additionally catches cases where upstream modified the same files. Jasper’s testing confirms the output format (`landed as <commit>`) consistently names the correct upstream commit, and the performance optimizations (batching, blob fetching) work as intended. However, the **false positive** from v2 persists: a branch whose changes were independently implemented by another author is still deleted, even without `--squashed`, because the "cheap check" (tree-based diffing) finds the file contents in an unrelated commit. This aligns with Junio’s warning that looser detection risks deleting "irrelevant" branches—those whose changes are upstream but whose commits and messages are not.

Jasper **endorses Junio’s CLI redesign proposal** to decouple strict tip-reachability (`--delete-merged`) from looser change-based detection (`--delete-irrelevant`), arguing that the current unified approach conflates distinct user intents. He proposes a **granular `--landed=<kind>` option** (e.g., `--landed=files` for tree-based diffing, `--landed=merge` for three-way merge detection) to let users opt into looser detection once per repository via config, preserving `--delete-merged`’s conservative default. This would address the false-positive issue while accommodating workflows like GitHub’s "Squash and merge." Jasper also notes a **usability nit**: branches checked out in worktrees are silently skipped, unlike branches with `deleteMerged=false`, which print a "Skipping" message. He references an RFC for `git worktree list --merged` that would reuse the "has this branch landed?" logic, suggesting the feature’s utility extends beyond branch deletion.

The email does not engage with the algorithmic trade-offs (e.g., `git range-diff` vs. patch IDs for rebase detection) or Harald’s rejection of the CLI split, focusing instead on **user experience and safety**. Jasper’s report is valuable for its concrete examples—especially the false positive—and his proposal for a config-backed `--landed` option offers a pragmatic middle ground between Harald’s unified approach and Junio’s strict/loose split. The unresolved question remains whether the project will prioritize workflow efficiency (Harald’s stance) or safety and predictability (Junio’s and Jasper’s stance).

This thread is about defining a formal voting process for the Git project to break deadlocks in contentious decisions, such as the ongoing AI contributions debate. Emily Shaffer proposed a new `Documentation/CommunityVoting.adoc` file outlining how votes would work, including multi-option ballots (like ranked-choice voting) and secret ballots to protect contributors from external pressure. The patch is under review, with consensus forming around the need for secret ballots, but key details remain unresolved.

The biggest sticking point is who gets to vote. Junio Hamano prefers a strict but simple rule (e.g., contributors with two or more topics in released versions), while Emily leans toward inclusivity. Jeff King (Peff) has now proposed a hybrid approach: an algorithmic metric (like commit count and recency) for most cases, with a transparent exception process for edge cases (e.g., historically significant contributors who no longer meet the technical criteria). This aims to balance fairness and scalability, though concerns about corporate bias—raised by Justin Tobler and Kristoffer Haugsbakk—persist. Kristoffer’s critique goes further, arguing that formal voting inherently favors corporate interests, particularly on AI policy.

The proposal itself is still in flux. The voting mechanism (e.g., ranked-choice vs. plurality) and logistics for secret ballots (like third-party tools) are unresolved. Junio’s suggestion to use Git OIDs to identify proposals also hasn’t been addressed. The thread has shifted from debating *whether* to adopt formal voting to refining *how* it would work, with Peff’s hybrid eligibility model gaining traction as a pragmatic middle ground. The next step will likely be updating the proposal to reflect these discussions.

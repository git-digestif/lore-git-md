This thread is about defining a structured voting process for the Git project to break deadlocks in contentious decisions, such as the ongoing AI contributions debate. Emily Shaffer proposed a new `Documentation/CommunityVoting.adoc` file outlining how votes would work, including eligibility, versioning, and mechanics. Junio C Hamano, the maintainer, has engaged constructively, refining details like using Git OIDs to identify proposals and raising the eligibility bar to contributors with two or more topics in a released version of Git.

The proposal is still under review, with key open questions unresolved: how votes would be counted (plurality vs. proportional), whether the project should adopt formal voting at all, and now, how to implement secret ballots to address concerns about corporate influence. Kristoffer Haugsbakk raised ideological objections, arguing that voting could favor corporate interests, while Patrick Steinhardt countered by proposing secret ballots as a safeguard. Emily plans to update the patch to flag these unresolved issues explicitly.

The thread is shaping up as a debate over governance design rather than a technical review. Junio’s feedback suggests the proposal is on track if practical details can be settled, but Kristoffer’s skepticism and Patrick’s counterproposal highlight that the broader question—whether voting is the right tool for Git—remains open. The next steps will likely involve Emily incorporating feedback and the community weighing in on the secret ballot idea.

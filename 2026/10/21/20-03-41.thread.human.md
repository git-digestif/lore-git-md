This thread introduces a **formal voting process for the Git project**, proposed by Emily Shaffer in response to the community's struggles to resolve contentious issues—most notably the ongoing debate about AI contributions. The patch adds a new `Documentation/CommunityVoting.adoc` file outlining a structured three-phase process (proposal collection, voting, and implementation) for decisions where consensus cannot be reached. It also updates `DecisionMaking.adoc` to reference this process and ensures the new document is included in the build system.

The proposal is framed as a *process* patch, not a policy one: it defines *how* to vote, not *what* the outcome should be. Key details include eligibility rules (contributors with at least one commit merged to `next` or two code reviews, excluding banned participants), a requirement for proposals to be seconded, and a phased timeline (4 weeks for refinement, 2 weeks for voting). The voting mechanism itself is left unspecified for now. Emily suggests adopting the same approval process used for the 2019 Code of Conduct (general consensus + `Acked-by:` trailers) for this document.

While the patch is well-written and directly addresses a governance gap, it is likely to spark debate—not about the mechanics of voting, but about whether formalizing such a process aligns with Git’s long-standing consensus-driven culture. The proposal explicitly positions voting as a last resort, but its very existence may be seen as a departure from the project’s traditional approach. Expect discussions about whether this is the right tool for Git, or if it risks undermining the collaborative spirit that has defined the project for decades.

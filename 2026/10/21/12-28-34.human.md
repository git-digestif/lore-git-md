This is a **feature patch series** (v3) that extends `git branch --delete-merged` to detect branches whose changes have been integrated via squash merges or rebases, even if the branch tip itself is not reachable from the upstream. The series is now split into three patches: one for rebase detection, one for squash detection, and a helper refactoring. The default behavior checks for exact file matches (fast, no blob fetches), while the new `--squashed` flag enables slower but more thorough detection that handles upstream file modifications.

The series is well-structured and addresses a real pain point for users of GitHub-style workflows, where squash-and-merge or rebase-and-merge are common. Performance optimizations (batching, blob fetching) and thorough test coverage make it production-ready. The `--squashed` flag (replacing `--no-squashed` from v2) is a sensible design choice, defaulting to the faster, safer mode while allowing users to opt into more aggressive detection when needed.

The ongoing discussion with Junio C Hamano about whether to split this into two separate commands (`--delete-merged` for strict tip-reachability and `--delete-irrelevant` for looser change-based detection) remains unresolved. Harald Nordgren argues for the unified approach, while Junio’s proposal reflects a conservative stance on safety. Jasper Mayone’s user report endorses the split, suggesting a granular `--landed=<kind>` option. The current implementation aligns with Harald’s vision, but the architectural debate may influence future iterations.

If you work with squash merges or rebases, this series is worth watching—it could significantly streamline branch cleanup. The code is clean, the tests are comprehensive, and the performance trade-offs are well-documented. The unresolved CLI design question is the main open issue, but the current implementation is a pragmatic step forward.

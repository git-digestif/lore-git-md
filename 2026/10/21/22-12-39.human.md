This is a maintainer response in the `git worktree list --merged` RFC thread, addressing a tangential but fundamental design question.

Junio C Hamano pushes back on Harald Nordgren’s suggestion to relax Git’s one-branch-per-worktree rule. He explains the technical rationale: worktrees share a single repository, so allowing two worktrees to check out the same branch would create ambiguity when one worktree makes a new commit — the other worktree’s HEAD would no longer point to the expected commit. This differs from separate clones, where each repository maintains its own ref state. Junio points to `git worktree add -d` (detached HEAD mode) as the existing workaround for users who want multiple worktrees on the same branch. The tone is matter-of-fact, treating the restriction as settled design rather than an open question. No further discussion of the `--merged`/`--no-merged` filters themselves occurs in this reply.

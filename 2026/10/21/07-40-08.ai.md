This is a **clarification reply** in the ongoing discussion about the ephemeral branch reaping feature in Jason Newton’s worktree improvements series (v3). Jason pushes back against Eric Sunshine’s **substantive objection** that `--detach` already serves the use case, arguing that the two mechanisms serve fundamentally different purposes while the worktree exists.

The key distinction Jason draws is that `--detach` leaves HEAD in a branchless state, which breaks common workflows (`git status`, `git push`, `git branch --set-upstream-to`, `git symbolic-ref`) that expect a branch name. An ephemeral branch, by contrast, behaves like a normal `refs/heads/` ref for the lifetime of the worktree—commits can be made, other refs can point to them, and the branch remains usable until the worktree is removed. This makes ephemeral branches more ergonomic for throwaway worktrees that might last minutes or months, avoiding what Jason calls a "degraded halfway state" where users risk losing work or encountering "gotchas" like garbage collection reaping unreferenced commits.

Jason also clarifies the **scope of the reaping mechanism**: it only applies to branches auto-created by DWIM (the final component of `<path>`), and only when the worktree was created by the same Git version that recorded ownership in `worktrees/<id>/owned-branch`. Explicitly named branches (`-b/-B`), pre-existing branches, and detached HEADs are never owned and never reaped. Upgrading Git does not retroactively mark older worktrees, so no upgrade headaches are expected. The "unconditional" deletion mentioned in the commit message refers only to the owned branch—even if it has unmerged commits—because ephemeral branches are disposable by design. Users can preserve commits by creating a normal branch (`git branch <name> <tip>`) before removal or using `--keep-branch`.

The reply does not directly address Eric’s concern about breaking existing tooling but implies that the risk is minimal: the change only affects the default `git worktree add <path>` (no branch specified) followed by `git worktree remove`, and users who want the branch to outlive the worktree already have alternatives (`-b <name>`, `<existing-branch>`, or `--detach`). The core tension remains whether the added complexity is justified by the ergonomic benefits, or if `--detach` is sufficient for throwaway worktrees. Jason’s framing suggests he sees ephemeral branches as a **feature**, not just a cleanup mechanism, which may help reframe the discussion for other reviewers.

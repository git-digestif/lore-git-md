This thread is a design discussion about how Git’s SHA-256 interoperability layer should handle unknown commit headers like `mergetag` and `predecessor` when converting repositories. The core issue is that the current `convert_commit_object` function aborts if it encounters these headers pointing to missing objects, which blocks full-history conversion of repositories like the Linux kernel. Adam Majer, the thread’s originator, argues for a pragmatic approach: treating unknown headers as opaque text and copying them verbatim during conversion to preserve history deterministically. This would unblock real-world use cases but could result in different commit IDs depending on the source OID type.

The discussion has surfaced a key tension between compatibility and correctness. Adam emphasizes that missing objects (e.g., from defunct external repositories) are a practical reality, and Git cannot validate or rewrite their OIDs without the original data. He warns that inconsistent handling—skipping some headers while converting others—would make SHA-256 conversions nondeterministic. Brian m. carlson, the primary contributor to Git’s SHA-256 transition, counters that preserving opaque headers risks propagating invalid or misleading data, proposing instead that such headers be dropped entirely. The debate now centers on whether Git should prioritize usability for large repositories or enforce stricter handling to avoid broken data. No decisions have been made yet, and the thread remains in the RFC stage, with open questions about opt-in flags, reporting mechanisms for skipped headers, and potential security implications.

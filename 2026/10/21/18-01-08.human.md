This is a documentation patch series that converts Git’s `BreakingChanges` plain-text document into a proper manpage, `gitbreaking-changes(7)`, making it accessible via `git help` and `man`. The series is technically complete and ready for integration, with all prior reviewer feedback incorporated in the v2 iteration. Kristoffer Haugsbakk, the author, has explicitly stated no further changes are needed from his side.

The core goal is to improve discoverability of upcoming breaking changes for end users. The series moves the existing content into a manpage, updates URLs, adds a living-draft admonition to clarify the document’s status, and integrates it into the documentation build system. No new symbols, CLI options, or on-disk format changes are introduced—this is purely a documentation effort.

The only remaining open question is how to handle the document’s lifecycle after Git 3.0 ships. Junio C Hamano raised this in the parent email, asking whether every entry will need to be rewritten to reflect that the breaking changes are now in the past. Kristoffer’s reply proposes a lightweight solution: leave the existing entries unchanged but add a new section summarizing what *did* change in Git 3.0, introduced with a note explaining the future-tense perspective. This avoids rewriting the entire document while keeping it accurate for future readers. The suggestion is pragmatic and aligns with the series’ goal of minimal maintenance overhead.

The series conflicts with two in-flight topics (`ps/ref-storage-format` in `master` and `bc/restrict-hex-to-lowercase` in `seen`), requiring their additions to be moved from `BreakingChanges.adoc` to `gitbreaking-changes.adoc` during integration. These conflicts are minor and mechanical, not technical. All other reviewer feedback—including structural improvements, URL formatting, and the relocation of the "Adding new items" discussion—has been addressed in v2.

This looks like a well-crafted, uncontroversial improvement that addresses a real usability gap. The post-3.0 lifecycle question is the sole loose end, and Kristoffer’s proposed solution seems reasonable. If Junio accepts it, the series is likely to proceed to integration without further delay.

# Thread deltas

## 2026/10/21

- [2026/10/21/10-16-48 by Masaya Kazama <miyaokamiyao@gmail.com>] Masaya Kazama reported that since 6e95b07e5f the detached "git maintenance" child holds objects/maintenance.lock for the whole background run, so a SIGKILL or power loss leaves a stale lock that makes every later "git maintenance run --auto" return silently without running, permanently disabling auto-maintenance.
- [2026/10/21/10-16-48 by Masaya Kazama <miyaokamiyao@gmail.com>] Kazama provided a reproduction (git 2.56.0) showing the lock survives killing the detached child and that a subsequent --auto run enters zero maintenance regions, while --no-quiet shows the "lock file exists, skipping maintenance" warning.
- [2026/10/21/10-16-48 by Masaya Kazama <miyaokamiyao@gmail.com>] Kazama described real-world impact: in a large partial clone a stale lock from 2026-06-30 to 2026-10-21 let packs grow to 13.9 GB (94 million in-pack entries) until a manual run reduced them to 0.68 GB, and left the commit-graph stale; two other repositories on the same machine had the same stale lock.
- [2026/10/21/10-16-48 by Masaya Kazama <miyaokamiyao@gmail.com>] Kazama noted that core.lockfilePid cannot detect the stale lock because maintenance~pid.lock contains the pid of the already-exited parent rather than the detached child.
- [2026/10/21/10-16-48 by Masaya Kazama <miyaokamiyao@gmail.com>] Kazama listed three unimplemented options: leave a user-findable trace when --auto skips due to the lock; record the actual holder's pid and hostname and ignore the lock when that process is gone; or use an OS-level lock released on process death.

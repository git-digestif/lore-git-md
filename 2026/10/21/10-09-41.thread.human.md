This thread is about a bugfix patch (now at v2) that prevents Git from accidentally deleting all tracked files when `git revert`, `git cherry-pick`, or `git rebase` is run on a shallow boundary commit—a commit that appears as a root commit due to `--depth=1` cloning. The issue arises because these operations can treat such commits as if they have no parents, leading to unintended file deletions.

The patch introduces a safeguard in the sequencer subsystem that checks for shallow boundary commits early in the process (during todo-list construction) and refuses the operation by default. Users can override this refusal for `revert` and `cherry-pick` with the new `--allow-shallow-boundary` flag, but `rebase` offers no override. The v2 update addresses prior feedback by moving the check to an earlier stage, ensuring no leftover state in `.git/sequencer`, and extending the safeguard to all rebase backends. The implementation is now uncontroversial, with Junio C Hamano and Phillip Wood endorsing the architectural changes.

The patch touches the sequencer, `revert`, and `rebase` built-ins, along with documentation, and includes thorough test coverage. The only remaining open question is whether to extend the safeguard to `git commit --amend`, but this is not blocking the current patch. No merge decision has been made yet, but the implementation is technically sound and ready for further review.

This thread is about a bugfix patch that prevents `git revert`, `git cherry-pick`, and `git rebase` from accidentally deleting all tracked files when run on a shallow boundary commit—a commit that appears as a root commit due to `--depth=1` cloning. The patch, originally proposed by Nakul V S, has evolved in response to feedback from Junio C Hamano and Phillip Wood.

The latest version (v2) expands the safeguard to cover all rebase backends (`merge`, `interactive`, and `apply`) and moves the check to the planning stage (when the todo list is built) rather than mid-operation. This ensures no state is left behind if the command is refused. The `--allow-shallow-boundary` flag is retained for `git revert` and `git cherry-pick` but omitted from the synopsis for clarity, while `git rebase` always refuses without an override. The implementation introduces a shared helper function and a new shallow utility to centralize the logic, with comprehensive test coverage verifying refusal, override behavior, and edge cases.

Key participants agree on the core premise: the safeguard is necessary, and the architectural shift to early checking is an improvement. Junio and Phillip Wood both supported extending the safeguard to `git rebase`, and the discussion has now resolved the remaining design questions. The patch is well-motivated, technically sound, and appears ready for integration. No controversial issues remain, and the only open question—whether to extend the safeguard to `git commit --amend`—has not been revisited in this update.

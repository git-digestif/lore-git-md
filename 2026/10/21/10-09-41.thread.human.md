This thread is about a patch (v2) by Nakul V S that prevents Git from accidentally deleting all tracked files when `git revert`, `git cherry-pick`, or `git rebase` is run on a shallow boundary commit—a commit that appears as a root commit due to `--depth=1` cloning. The patch adds a safeguard that refuses such operations by default, with an opt-in override (`--allow-shallow-boundary`) for `revert`/`cherry-pick` but not for `rebase`.

The patch is now under review, with v2 addressing all prior feedback: it moves the check to the planning stage, covers all rebase backends (including `--apply`), and omits the override flag from the synopsis for clarity. Junio C Hamano and Phillip Wood have both endorsed the core design and improvements, though Junio raised minor implementation details (e.g., the rationale for rebasing onto `master`, the use of `git_config_bool_or_int()` for a boolean config key). A merge decision is pending.

The latest email from Junio introduces a new hurdle: Nakul’s patch duplicates logic already added by Harald Nordgren’s stalled topic, which is currently stuck in Junio’s `seen` branch. This creates a merge conflict that would block integration until resolved. Junio suggests Nakul either reuse Harald’s function or help revive the stalled topic by reviewing it. This is a procedural issue, not a technical objection, but it means the patch cannot merge until Nakul addresses the overlap. The unresolved questions from earlier—whether to extend the safeguard to `git commit --amend` and the config key type—remain open, but the immediate focus is now on resolving the conflict with Harald’s work.

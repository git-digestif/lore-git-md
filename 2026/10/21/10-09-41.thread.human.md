This thread is about a bugfix patch that prevents `git revert` and `git cherry-pick` from accidentally deleting all tracked files when run on a shallow boundary commit—a commit that appears as a root commit due to `--depth=1` cloning. The patch, authored by Nakul V S, adds a safeguard that refuses such operations by default, directing users to either `--unshallow` or a new `--allow-shallow-boundary` flag.

The patch is under active review and has garnered support for its core premise from both Junio C Hamano and Phillip Wood. The discussion has evolved from *whether* to implement the safeguard to *how* best to do so. Phillip’s latest reply proposes a more user-friendly approach: refusing to add shallow boundary commits to the sequencer’s todo list *before* execution begins, rather than erroring out mid-operation. This would improve the user experience by preventing the operation from starting at all, though it adds some implementation complexity by requiring changes in four entry points instead of one. The proposal also aligns with earlier suggestions to extend the safeguard to `git rebase` and possibly `git commit --amend`.

Key open questions remain, including where the shallow-boundary detection logic should live (a shared helper function or sequencer.c), whether the `--allow-shallow-boundary` flag is necessary, and how to keep the command synopsis concise. The patch itself is narrowly scoped, well-motivated, and includes thorough test coverage and documentation. No merge status has been reported, and the thread is still under review.

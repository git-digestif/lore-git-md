This thread is about a bugfix patch (now at v2) that prevents Git from accidentally deleting all tracked files when `git revert`, `git cherry-pick`, or any `git rebase` backend operates on a shallow boundary commit—a commit that appears as a root commit due to `--depth=1` cloning. The patch adds a safeguard that checks for these commits during the planning stage (todo-list construction) and refuses the operation by default, directing users to either `--unshallow` or the new `--allow-shallow-boundary` flag (available only for `revert`/`cherry-pick`; `rebase` always refuses without override).

Nakul V S authored the patch, which has evolved through feedback from Junio C Hamano and Phillip Wood. The v2 version addresses prior concerns by moving the check to a shared helper function, extending protection to all rebase backends (including `--apply`), and avoiding leftover `.git/sequencer` state. The patch touches the sequencer subsystem, `revert.c`, `rebase.c`, and documentation, with thorough test coverage for refusal, override behavior, and edge cases. One known limitation—the manual todo-list edge case—is acknowledged but left unfixed as an acceptable trade-off.

The patch is under active review, with no merge decision yet. Junio and Phillip both endorse the core premise and implementation, though whether the safeguard should extend to `git commit --amend` remains unresolved. The new `--allow-shallow-boundary` flag is intentionally omitted from the synopsis for clarity, per Phillip’s suggestion. For now, this remains a standalone bugfix with no dependencies or prior related work.

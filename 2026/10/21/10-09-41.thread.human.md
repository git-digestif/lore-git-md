This thread is about a bugfix patch by Nakul V S that prevents `git revert` and `git cherry-pick` from accidentally deleting all tracked files when run on a shallow boundary commit—a commit that appears as a root commit due to `--depth=1` cloning. The patch adds a safeguard that refuses such operations by default, with an opt-in `--allow-shallow-boundary` flag.

The patch is under review and has received substantive feedback. Phillip Wood supported the core premise but suggested improvements, including extracting the detection logic into a helper function and omitting the new flag from the command synopsis for clarity. He also questioned whether the safeguard should extend to `git rebase`, as rebasing a shallow boundary commit could similarly cause unintended data loss.

Junio C Hamano has now weighed in, endorsing Phillip’s suggestion to extend the safeguard to `git rebase` and possibly `git commit --amend`. He raised an architectural question about where the check should live—whether in `sequencer.c:do_pick_commit()` or a shared helper function—to ensure all affected operations are covered cleanly. This remains an open design discussion, and no merge decision has been made. The patch is still under review, with no prior versions or dependencies.

This thread is about a bugfix patch by Nakul V S that prevents `git revert` and `git cherry-pick` from accidentally deleting all tracked files when run on a shallow boundary commit—a commit that appears as a root commit due to `--depth=1` cloning. The patch adds a safeguard in the sequencer subsystem to refuse such operations by default, with an opt-in `--allow-shallow-boundary` flag for users who need to override the protection.

Phillip Wood has provided the first substantive review, engaging with both the implementation and design. He suggests two technical improvements: refactoring the shallow-boundary detection logic into a helper function to avoid duplication, and omitting the `--allow-shallow-boundary` option from the command synopsis to keep usage messages cleaner. Neither suggestion challenges the core premise of the patch—default refusal with an opt-in override—but both aim to improve maintainability and user experience. Phillip also raises a design question: whether the safeguard should extend to `git rebase`, as rebasing a shallow boundary commit could similarly lead to unintended data loss. He notes that the `--allow-shallow-boundary` flag was added out of caution rather than a known use case, implying it might be unnecessary if no legitimate need exists. The patch remains under review, with no maintainer decisions or merge status updates yet.

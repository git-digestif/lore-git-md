This thread is about a bugfix patch (now at v2) by Nakul V S that prevents Git from accidentally deleting all tracked files when `git revert`, `git cherry-pick`, or `git rebase` is run on a shallow boundary commit—a commit that appears as a root commit due to `--depth=1` cloning. The patch adds a safeguard that refuses such operations by default, with an opt-in override (`--allow-shallow-boundary`) for `revert` and `cherry-pick` only; `rebase` always refuses without override.

The v2 patch addresses all prior feedback: it moves the check to the planning stage (todo-list construction), extends the safeguard to all rebase backends (including `--apply`), and omits the override option from the synopsis for clarity. Junio C Hamano and Phillip Wood, the key reviewers, have endorsed the core design and implementation, though Junio’s latest review raises minor procedural and surface-level concerns. He questions the necessity of the rebase onto `master` (a procedural check) and asks for justification for using `git_config_bool_or_int()` instead of `git_config_bool()` for the boolean config key. He also notes that two edge cases—`git commit --amend` and manually edited rebase todo lists—remain uncovered but accepts this as a reasonable starting point.

The patch is now in good shape for integration, with no major objections. The only unresolved questions are whether the safeguard should eventually extend to `git commit --amend` and how to handle manually edited todo lists, though these are not blockers for this iteration. The topic remains under review, with no merge decision yet.

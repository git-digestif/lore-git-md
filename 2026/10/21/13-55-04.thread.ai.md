Thread identity: Subject: [PATCH 0/2] Add degree-of-concern reporting to `git repo structure`; series version: v5 (bugfix for tree size concern level, memory management corrected, invalid tag refs concern removed, configuration values rounded to powers-of-two, integer typing fixed; all prior feedback addressed); originating author: Mark C. Chu-Carroll; thread type: patch series (feature addition).

Core problem or goal: Add a `--concern` option to the `git repo structure` command that annotates repository structure statistics with visual (star-based) or numeric indicators of how problematic each metric is, based on empirical thresholds derived from a representative sample of real repositories. The feature is configurable per-repository via Git config (`repo.concern.*`), allowing users to override default thresholds. The feature is directly inspired by `git-sizer(1)` but integrated into Git's native tooling.

Current status: Under review (v5 posted; all prior technical feedback addressed). The copy-paste error in the tree size concern level computation (using `objects->largest.commit_size.value` instead of `objects->largest.tree_size.value`) is fixed. Memory management is corrected (strbuf deallocation error in table generation resolved), invalid concern reporting for tag refs is removed, configuration values are rounded to the nearest power-of-two for human readability, and integer typing in concern computation and table generation is fixed. All substantive technical feedback from Patrick Steinhardt and Junio C Hamano on the `--concern` implementation is addressed. However, Junio C Hamano has now raised a new fundamental objection to the subcommand name itself: he argues that "structure" is misleading because `git repo structure` currently reports only object counts and sizes, not actual structural characteristics such as tree width and depth, number of active branches and their integration patterns (single trunk versus multiple maintenance tracks), or branch naming conventions. He notes that because `git repo` as a whole is still experimental, there remains an opportunity to rename this subcommand or migrate its useful features to more appropriately named commands before they stabilize. No maintainer decision yet; still in review phase with this naming/scope question now open.

Key technical details: Files touched: `builtin/repo.c`, `Documentation/config/repo.adoc`, `Documentation/git-repo.adoc`, `t/t1901-repo-structure.sh`. New CLI option: `--concern` (visual or numeric output). New config section: `repo.concern.*` (hyphenated keys: `commit-count`, `blob-size`, etc.) for threshold overrides; naming consistent between code and documentation. Concern calculation: exponential scale (base-2 logarithms) where each doubling beyond the threshold adds a star; defaults set at mean(log2) + one standard deviation from a representative repository sample, methodology documented in commit message. Output formats: concern indicators added to table, lines, and nul-terminated output (new column in table format, `concern_level` line in lines/nul mode). On-disk format: no changes; purely informational output. Test coverage: added to `t/t1901-repo-structure.sh` for functionality, configurability, and output format correctness; expanded in v5 to verify the tree size concern level fix, memory management, and edge cases (invalid keys warned, negative values rejected). Memory management: leak in concern string generation fixed in v2 and confirmed in v4; strbuf deallocation error in table generation corrected in v5. Implementation details: concern thresholds defined in a single `concern_stat_thresholds[]` array with a sentinel entry (`{ 0 }`); concern level computed by `repo_structure_concern_level()`; config parsing handled by `config_concern_thresholds()` via `repo_config()` with the `repo.concern.` prefix, callback passes the threshold array as a parameter eliminating global variable usage; use of `starts_with` for config key matching (replacing `strncmp` as suggested by Patrick Steinhardt); documentation split into 1/2 and 2/2 for bisectability (59 lines added to `Documentation/config/repo.adoc` with 14 new config keys, and `Documentation/git-repo.adoc` with --[no-]concern option and output formats); patch 1/2 introduces the core `--concern` option and calculation logic, patch 2/2 adds configurability via `repo.concern.*`; config callback validates keys against the threshold array and warns on invalid names; empirical methodology for default thresholds documented in the commit message of 1/2; bugfixes in v5 include tree size concern level now correctly computed using `objects->largest.tree_size.value`, strbuf deallocation error in table generation corrected, invalid concern reporting for tag refs removed, configuration values rounded to nearest power-of-two, integer typing fixed; UTF-8-aware string alignment for table formatting; use of `log2u()` for logarithmic scaling; configurability via `nearest_log2_value()` rounding; invalid keys or negative values trigger warnings; config parsing only invoked when `--concern` is requested; open type-consistency issue noted by Christian Couder in v5 2/2: loop variable `i` in `config_concern_thresholds()` declared as `int` while patch 1/2 used `size_t`; `threshold` field in `struct concern_stat_threshold` is `size_t` but config value read via `git_config_int()` into local `int` before passing to `nearest_log2_value()`, suggesting `git_config_size_t()` to avoid narrowing conversion.

Open questions and loose ends: Subcommand naming and scope: Junio C Hamano objects that "structure" is misleading for a command reporting only object counts and sizes; he expects "structure" to convey topological information (tree width/depth, active branch count, integration patterns, branch naming conventions) enabling cross-repository comparison, and suggests renaming the subcommand or migrating its features to better-named commands while `git repo` remains experimental. Default threshold values: may still attract discussion or requests for adjustment based on reviewer input. Discoverability of default thresholds: suggestion from v1 (`--show-defaults` flag) remains unimplemented. Code organization polish from Christian Couder (v5): suggestions include moving `#include "config.h"` to patch 2/2 if only needed there; replacing `#define` string macros (`REPO_STRUCTURE_CONFIG_PREFIX`, `CONCERN_STAT_*`) with `static const char` arrays or an `enum concern_stat` with designated initializers (citing `builtin/branch.c`); changing return types of `get_concern_threshold()` and `repo_structure_concern_level()` from `int` to `size_t` (with `BUG()` on unknown names instead of returning -1); replacing `CONCERN_STAT_VALUE_NONE` macro with `static const size_t`; making loop variable `i` in `config_concern_thresholds()` `size_t` to match patch 1/2; and using `git_config_size_t()` instead of `git_config_int()` when reading threshold values to avoid narrowing conversion from `size_t` field to `int` local. These are maintainability/style improvements that do not affect behavior. 32-bit platform expectations: Christian Couder raised a side question about whether the feature is expected to work on 32-bit systems, noting that Git on such platforms may never reach concerning levels for the metrics involved.

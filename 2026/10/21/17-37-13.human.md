This is a discussion email about SHA-1/SHA-256 repository interoperability, specifically targeting the `convert_commit_object` function and its handling of non-standard commit headers.

Adam Majer reports practical difficulties when attempting to convert repositories containing both SHA-1 and SHA-256 object IDs. He experimented with the Linux kernel repository and encountered commits with "predecessor" headers (used for rebase and amend operations) and mergetags that reference objects not available in the repository. The current `convert_commit_object` implementation bails on unknown headers, making it impossible to fully convert such repositories while preserving history.

The core issue is that strict one-to-one OID mapping breaks when commits reference objects that Git does not retain or cannot fetch. Adam proposes a more flexible approach: treat unknown headers (like mergetags and custom predecessors) as opaque text during conversion, copying them verbatim rather than attempting to rewrite their OIDs. This would result in different commit hashes depending on the source repository's hash algorithm, but would allow history conversion to proceed where it currently fails.

This email highlights a real-world limitation in Git's SHA-256 interoperability work, particularly for repositories with complex histories involving rebase/amend operations or custom commit headers. The discussion is relevant to anyone following the ongoing SHA-256 transition effort, as it surfaces edge cases that may require design trade-offs between strict correctness and practical usability. The proposal appears reasonable but would need careful consideration of its implications for commit identity and verification.

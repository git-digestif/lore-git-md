This is the second patch in Justin Tobler’s four-patch bugfix series (v4 2/4) targeting a race condition in Git’s ODB transaction machinery. The patch refactors the parsing logic for `git-index-pack` output into a new public helper, `read_index_pack_report()`, in preparation for moving `.keep` lockfile creation to the transaction commit phase in a later patch.

The core change extracts the generic parsing logic from `index_pack_lockfile()`—which currently reads `git-index-pack`’s stdout to determine the packfile name and whether a `.keep` file was created—into a standalone function. The new helper, `read_index_pack_report()`, takes a `struct repository *`, the `git-index-pack` output file descriptor, a `strbuf` to store the packfile name, and an optional `is_keep` pointer to indicate whether a `.keep` file was created. The function is hash-algorithm-agnostic, using `repo->hash_algo->hexsz` to size its read buffer, and returns 0 on success or a negative error code on failure. The original `index_pack_lockfile()` function is updated to use this helper, reducing code duplication and making the parsing logic reusable for the transaction machinery.

The patch touches `pack-write.c` and `pack.h`, introducing the new `read_index_pack_report()` function and updating the comment in `pack-write.c` to reflect the generic nature of the parsing logic (replacing the hardcoded SHA-1 reference with a generic `<name>`). The refactoring is clean and well-motivated, with no behavior changes—it simply lifts the parsing logic into a reusable helper. The commit message clearly explains the purpose of the refactoring and its role in enabling the later transaction-phase lockfile creation. This patch is a necessary preparatory step for the series’ core fix and has received explicit approval from Patrick Steinhardt. No open questions or concerns remain for this specific patch.

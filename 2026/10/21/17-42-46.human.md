This is a maintainer's reply in the ongoing discussion about the `hook.<event>.enabled` configuration behavior. Junio C Hamano weighs whether Thomas Bachem’s patch (which makes `hook.<event>.enabled` disable *all* hooks, including those in the hooks directory) should be treated as a backward-incompatible change or a bugfix.

Junio’s analysis focuses on the documentation: the current wording for `hook.<event>.enabled` mentions "all hooks" but also references `hook.<friendly-name>.enabled`, which is explicitly scoped to config-defined hooks. This creates ambiguity. He leans toward calling the patch a backward-incompatible breakage rather than a bugfix, but acknowledges that casual users may not parse the documentation carefully. His suggestion is to accept the patch only if the documentation is updated to clearly state that `hook.<event>.enabled` covers *all* hooks, not just config-defined ones.

The thread remains open for broader community input on whether to prioritize consistency (disabling all hooks) or backward compatibility (preserving the original scope). No technical objections have been raised, and Adrian Ratiu, the original author, remains neutral. The patch touches `builtin/hook.c` and `hook.c`, with expanded test coverage in `t/t1800-hook.sh`.

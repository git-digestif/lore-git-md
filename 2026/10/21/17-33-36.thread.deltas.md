# Thread deltas

## 2026/10/21

- [2026/10/21/17-33-36 by Jasper Mayone <me@jaspermayone.com>] Jasper Mayone sent an RFC proposing to add `--merged` and `--no-merged` filters to `git worktree list`, applied to each worktree's HEAD, so users can find worktrees whose work has already landed.
- [2026/10/21/17-33-37 by Jasper Mayone <me@jaspermayone.com>] The accompanying patch implements the filters by reusing `struct ref_filter` and `OPT_MERGED` from ref-filter.h, matching the parsing, default (current worktree HEAD), and error messages of `git branch`, and excludes bare, unborn, or unreadable worktrees.
- [2026/10/21/21-36-25 by Harald Nordgren <haraldnordgren@gmail.com>] Harald Nordgren asked whether the requirement that a branch cannot be checked out in more than one worktree should be relaxed, noting that two separate repositories tracking the same upstream do not enforce such a restriction.
- [2026/10/21/22-12-39 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano explained that worktrees share the same repository, so allowing the same branch in two worktrees would cause conflicts when one makes a commit, and pointed to "worktree add -d" as the alternative.

## 2026/10/22

- [2026/10/22/07-21-14 by Harald Nordgren <haraldnordgren@gmail.com>] Harald Nordgren withdrew his objection to preventing the same branch from being checked out in multiple worktrees, saying that after reading up he agreed the situation was “hairy”; he also accepted that `worktree add -d` addresses the related point.
- [2026/10/22/17-58-39 by Kristoffer Haugsbakk <kristofferhaugsbakk@fastmail.com>] Kristoffer Haugsbakk responded rhetorically to the earlier remark that “AI loves worktrees,” asking, “Is this what mechanical sympathy has come to?”

## 2026/10/23

- [2026/10/23/18-30-02 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano observed that real review on the RFC patch never happened, perhaps because a discussion on a side issue distracted everybody.
- [2026/10/23/18-30-02 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano suggested the patch's intro unfairly narrows the problem space, since even users who do not keep one worktree per topic need to find worktrees based on checked-out branches, and the feature does not have to be limited to --merged and --no-merged.
- [2026/10/23/18-30-02 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano wondered whether a repeatable "git worktree list --branch=..." option would be a better primitive, noting it could reuse existing machinery (for example via "git worktree list $(git branch --contains HEAD | sed -e 's/^/--branch=/')") without extra code.

## 2026/10/24

- [2026/10/24/06-25-20 by Eric Sunshine <sunshine@sunshineco.com>] Eric Sunshine, having only skimmed the commit message, reacted that the RFC's `--merged`/`--no-merged` approach seemed overly special-case and proposed a more general "for-each" mechanism analogous to `git submodule foreach <command>`.
- [2026/10/24/16-53-11 by Jasper Mayone <me@jaspermayone.com>] Jasper Mayone posted [PATCH v2] teaching `git worktree list` a repeatable `--branch=<branch>` option that lists only worktrees with the given branch checked out (including rebasing/bisecting worktrees, accepting a full `refs/heads/` name, never listing detached worktrees), after Junio C Hamano had earlier suggested selecting worktrees by branch as a better primitive and Eric Sunshine had the same reaction; the v2 drops `--merged`, `--no-merged` and the reachability code, and leaves out the `git worktree foreach` idea Eric had raised.

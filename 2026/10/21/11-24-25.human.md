This is a review of the first patch in Elia Pinto’s three-patch series fixing 64-to-32 truncations on Windows. The series targets a real bug: Git silently truncates files larger than 4 GiB on LLP64 platforms (like Windows) due to `unsigned long` being 32-bit. This specific patch widens the object-database write path from `unsigned long` to `size_t` to prevent data corruption when writing large blobs.

Patrick Steinhardt’s review is substantive but brief. He acknowledges the correctness of the fix and the seriousness of the bug, but questions the decision not to add a test. The existing test in `t1007` only hashes files, not writes them, so it doesn’t catch the truncation. Steinhardt argues that since the test suite already has `EXPENSIVE` tests, adding another one for this edge case would be reasonable. His feedback is constructive and doesn’t block the patch, but it does raise a point that might need addressing before the series lands.

The patch itself is narrowly scoped and uncontroversial. It touches five files in the ODB subsystem and is a pure type conversion with no behavior change on 64-bit Linux. On Windows, it prevents silent data corruption when `git add` or `git hash-object -w` processes a file over 4 GiB that requires filtering (e.g., `core.autocrlf`, `eol`/`ident` attributes, or clean filters). The commit message clearly explains the problem and why no test was added, though Steinhardt’s review suggests that might not be the final word.

This is a well-motivated bugfix with clear platform-specific impact. The review so far is positive, but the test question is still open. If you care about Windows compatibility or large-file handling, this patch is worth following.

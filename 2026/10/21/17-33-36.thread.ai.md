Thread identity
Subject: RFC: `git worktree list --merged` / `--no-merged`
Series version: v1 (bugfix and ref-filter enhancement)
Originating author: Jasper Mayone
Thread type: feature proposal, design discussion, and bugfix implementation

Core problem or goal
Add filtering capabilities to `git worktree list` to help developers identify worktrees associated with specific branches, while addressing two related safety issues: (1) `git worktree remove` currently allows deletion of worktrees in the middle of a rebase, bisect, or other in-progress operation, risking data loss; and (2) `git for-each-ref`'s `%(worktreepath)` atom does not report the worktree path for branches being rebased or bisected, creating a mismatch with how `git worktree add` and `git branch -d` already treat those branches as "checked out." The original goal of a `--branch=<branch>` option has been abandoned in favor of extending `%(worktreepath)` in `ref-filter.c`, which avoids introducing new CLI options and aligns behavior across Git commands. This pivot introduces new concerns about safety, composability, and the suitability of `for-each-ref` as a filtering mechanism, particularly regarding the interaction between filtering and porcelain safety guarantees.

Current status
The series consists of two patches: (1) a **merged safety fix** making `git worktree remove` refuse to delete a worktree in the middle of a rebase, `git am`, bisect, cherry-pick, or revert sequence unless `--force` is given, aligning with Git’s general principle of protecting uncommitted or in-progress work; and (2) an enhancement extending `%(worktreepath)` in `ref-filter.c` to report the worktree path for branches being rebased or bisected, closing the gap Kristoffer Haugsbakk identified and eliminating the need for a new CLI option. The series is backward-incompatible for scripts relying on `%(worktreepath)` being empty for rebasing/bisecting branches or on the ability to delete in-progress worktrees without `--force`. No integration branch assignment. The pivot has revealed significant design tensions and limitations:

1. **Ordering invariant**: Eric Sunshine’s review highlights that filtering worktrees (via `for-each-ref` or any other mechanism) breaks the invariant that the main worktree appears first in output, creating a risk for scripts that rely on this ordering.
2. **Limitations of `for-each-ref`**: Phillip Wood identifies three key limitations: (1) lack of NUL-terminated output, complicating parsing of worktree paths with newlines; (2) inability to distinguish the main worktree from linked worktrees, risking main repository deletion; and (3) inability to handle branches checked out in multiple worktrees, complicating tracking or cleanup workflows.
3. **Safety risks**: Ben Knoble and Phillip Wood raise a critical edge case: whether filtering worktrees by branch state (e.g., `--merged=origin`) should include worktrees that are mid-rebase, and whether `git worktree remove` should allow deletion of such worktrees. The first patch in the series mitigates this risk by making `git worktree remove` refuse deletion of in-progress worktrees unless explicitly forced. Phillip frames this as a pre-existing bug in `git worktree remove` that the proposed `%(worktreepath)` change would make more likely to trigger, rather than as a flaw in the filtering mechanism itself. The discussion now centers on whether `for-each-ref --merged` should exclude rebasing worktrees by default and whether the `--force` flag in `git worktree remove` should be coordinated with similar behavior in `for-each-ref`.

Key technical details
- **Mechanism**: Extend `ref-filter.c`'s `%(worktreepath)` atom to report the worktree path for branches in rebase/bisect state, matching the behavior of `git worktree add` and `git branch -d`. Add a new helper function `worktree_is_in_progress()` to check for rebase, bisect, cherry-pick, revert, and `git am` state, and update `git worktree remove` to refuse deletion unless `--force` is given. The second patch reuses logic from `branch.c`’s `prepare_checked_out_branches()` to map the branch being rebased or bisected to its worktree, explicitly excluding branches that `rebase --update-refs` will move but are not currently checked out.
- **Subsystems**: ref-filter (`git for-each-ref`), worktree (`git worktree remove`, `git branch`)
- **Files**: `ref-filter.c`, `builtin/worktree.c`, `Documentation/git-for-each-ref.adoc`, `Documentation/git-worktree.adoc`, `Documentation/git-branch.adoc`, tests (`t/t2403-worktree-move.sh`, `t/t3203-branch-output.sh`, `t/t6302-for-each-ref-filter.sh`)
- **Symbols**: `%(worktreepath)` atom implementation in `ref-filter.c`, `worktree_is_in_progress()` helper in `builtin/worktree.c`, `check_no_operation_in_progress()` helper in `builtin/worktree.c`, `add_worktree_entry()` helper in `ref-filter.c`, `populate_worktree_map()` extended in `ref-filter.c`, `wt_status_check_rebase()` and `wt_status_check_bisect()` reused from `wt-status.c`
- **Behavior**: `%(worktreepath)` now returns the worktree path for branches in rebase/bisect state, eliminating the "detached" appearance. `git worktree remove` refuses to delete worktrees in the middle of a rebase, bisect, cherry-pick, revert, or `git am` sequence unless `--force` is given. The `git branch` output now shows dual `*` and `+` markers when run inside a worktree that is rebasing its own branch. No changes to on-disk format. The changes are backward-incompatible for scripts relying on the current empty `%(worktreepath)` value or the ability to delete in-progress worktrees without `--force`.
- **Composability**: Enables merged/unmerged filtering via `git for-each-ref --merged=HEAD --format='%(worktreepath)'`, replacing the original `--branch` composability use case. No new CLI options are introduced.
- **Ordering invariant**: `git worktree list` currently guarantees the main worktree appears first in output. Filtering (via `for-each-ref` or any other mechanism) breaks this invariant, creating a risk for scripts that rely on the first entry being the main worktree.
- **Limitations of `for-each-ref`**: (1) No NUL-terminated output, complicating parsing of worktree paths with newlines; (2) No distinction between main and linked worktrees, risking main repository deletion; (3) No handling of branches checked out in multiple worktrees; (4) Risk of surfacing worktrees in transient, high-risk states (e.g., mid-rebase), which could lead to data loss if used with `git worktree remove`.
- **Safety risks**: The interaction between `for-each-ref --merged` and `git worktree remove` introduces a risk of data loss if mid-rebase worktrees are included in filtered output. The series mitigates this risk by making `git worktree remove` refuse deletion of in-progress worktrees unless explicitly forced, aligning with Git’s general principle of protecting uncommitted or in-progress work.
- **Tests**: Cover rebasing/bisecting branches, unborn branches, backward-compatibility scenarios (scripts relying on empty `%(worktreepath)`), the ordering invariant (main worktree appearing first in unfiltered output), the limitations of `for-each-ref` (NUL-terminated output, main/linked worktree distinction, multiple worktrees per branch), and safety scenarios (e.g., filtering mid-rebase worktrees, `git worktree remove` validation logic). Specific test cases include rebasing, bisecting, interactive rebase with an edit stop, `rebase --update-refs`, and detached-HEAD rebase scenarios.

9. Could a `foreach`-style mechanism (e.g., `git worktree foreach`) still be useful for cases not covered by `for-each-ref`? *(Eric Sunshine’s proposal, now less urgent but still open)*
10. If a `foreach` mechanism is adopted, what syntax and safety guarantees (e.g., shell injection, error handling) should it provide? *(Eric Sunshine’s proposal, now less urgent but still open)*
11. How should the project address the broken ordering invariant when filtering worktrees? Options include: (a) preserving the main-worktree-first guarantee even in filtered output, (b) annotating the main worktree in output, or (c) accepting the breakage and documenting it as a backward-incompatible change. *(Eric Sunshine’s concern, now compounded by Phillip Wood’s review)*
12. How should the project address the limitations of `for-each-ref` as a filtering mechanism? Specifically: (1) lack of NUL-terminated output, (2) inability to distinguish main/linked worktrees, (3) inability to handle branches checked out in multiple worktrees, and (4) risk of surfacing worktrees in transient, high-risk states (e.g., mid-rebase). *(Phillip Wood’s and Ben Knoble’s concerns)*
13. Should `for-each-ref --merged` exclude worktrees in a rebase state by default, or should this be left to porcelain commands like `git worktree remove` to handle? *(Ben Knoble’s and Phillip Wood’s concern)*
14. Should `git worktree remove` fail by default for mid-rebase worktrees unless explicitly forced, aligning with Git’s general principle of protecting uncommitted or in-progress work? *(addressed by the series, but coordination with `for-each-ref` remains open)*
15. If `git worktree remove` gains a `--force` flag for mid-rebase worktrees, should this be coordinated with a similar change in `for-each-ref --merged` to avoid inconsistent behavior? *(new, implied by Phillip Wood’s reply)*

Frames the `%(worktreepath)` change as a bug fix to align with existing Git behavior and the `git worktree remove` change as a safety improvement.

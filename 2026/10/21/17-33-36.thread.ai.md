Core problem or goal
Add filtering capabilities to `git worktree list` to help developers identify worktrees associated with specific branches, while addressing two related safety issues: (1) `git worktree remove` currently allows deletion of worktrees in the middle of a rebase, bisect, cherry-pick, revert, or `git am` operation, risking data loss; and (2) `git for-each-ref`'s `%(worktreepath)` atom does not report the worktree path for branches being rebased or bisected, creating a mismatch with how `git worktree add` and `git branch -d` already treat those branches as "checked out." The original goal of a `--branch=<branch>` option has been abandoned in favor of extending `%(worktreepath)` in `ref-filter.c`, which avoids introducing new CLI options and aligns behavior across Git commands. This pivot introduces new concerns about safety, composability, and the suitability of `for-each-ref` as a filtering mechanism, particularly regarding the interaction between filtering and porcelain safety guarantees.

Current status

Since the `(no branch, ...)` line already names the branch, the `+` marker is unnecessary and could be confusing. The implementation introduces a second format string (`here_format`) that omits the `+` marker and worktree path for branches being rebased or bisected in the current worktree, while preserving the existing behavior for all other branches. The logic uses a dedicated helper, `checked_out_here()`, to avoid unsafe string comparisons (e.g., paths containing `)`). The patch maintains backward compatibility for users who rely on the default `--format` behavior, while ensuring that custom `--format` strings are applied uniformly to all branches. Tests cover the new behavior thoroughly, including edge cases like rebasing and bisecting in the current worktree.

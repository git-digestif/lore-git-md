Thread identity
Subject: RFC: `git worktree list --merged` / `--no-merged`
Series version: RFC v3 (design pivot: extend `for-each-ref %(worktreepath)` instead of `--branch`)
Originating author: Jasper Mayone
Thread type: feature proposal and design discussion

Core problem or goal
Add filtering capabilities to `git worktree list` to help developers identify worktrees associated with specific branches. The original goal was addressed via a `--branch=<branch>` option, but the discussion has now pivoted to extending `git for-each-ref`'s `%(worktreepath)` atom to report the worktree path even when the branch is being rebased or bisected. This change would close the gap Kristoffer Haugsbakk identified (rebasing/bisecting worktrees appearing detached) and eliminate the need for a new CLI option, simplifying the design and avoiding the naming and extensibility questions raised by Eric Sunshine and Junio.

Current status
The `--branch=<branch>` implementation is now abandoned in favor of extending `%(worktreepath)` in `ref-filter.c`. This narrower change avoids introducing new CLI options and instead aligns `for-each-ref` behavior with how `git worktree add` and `git branch -d` already treat rebasing/bisecting branches. Jasper frames the behavior change as a bug fix but explicitly asks whether any scripts rely on the current empty value. No integration branch assignment. Eric Sunshine’s new review highlights a latent design tension: filtering worktrees (via `for-each-ref` or any other mechanism) breaks the invariant that the main worktree appears first in output, creating a risk for scripts that rely on this ordering. Phillip Wood’s earlier concerns about main-worktree annotation and validation remain unaddressed but are now compounded by this ordering concern.

Key technical details
- **Mechanism**: Extend `ref-filter.c`'s `%(worktreepath)` atom to report the worktree path during rebase/bisect, matching the behavior of `git worktree add` and `git branch -d`.
- **Subsystem**: ref-filter (`git for-each-ref`)
- **Files**: `ref-filter.c`, `Documentation/git-for-each-ref.adoc`, tests (likely `t/t6302-for-each-ref-filter.sh`)
- **Symbols**: `%(worktreepath)` atom implementation in `ref-filter.c`
- **Behavior**: `%(worktreepath)` will now return the worktree path for branches in rebase/bisect state, eliminating the "detached" appearance. No changes to on-disk format. The change is backward-incompatible for scripts relying on the current empty value.
- **Composability**: Enables merged/unmerged filtering via `git for-each-ref --merged=HEAD --format='%(worktreepath)'`, replacing the original `--branch` composability use case. No new CLI options are introduced.
- **Ordering invariant**: `git worktree list` currently guarantees the main worktree appears first in output. Filtering (via `for-each-ref` or any other mechanism) breaks this invariant, creating a risk for scripts that rely on the first entry being the main worktree.
- **Tests**: Need to cover rebasing/bisecting branches, unborn branches, backward-compatibility scenarios (scripts relying on empty `%(worktreepath)`), and the ordering invariant (main worktree appearing first in unfiltered output).

Open questions and loose ends
1. Should the main worktree be filtered out by default? *(carried over from original proposal; now relevant to `for-each-ref` composability)*
2. Is HEAD the right default commit for composed filters (e.g., `git for-each-ref --merged`)? *(carried over from original proposal)*
3. Would a future `git worktree remove --merged` be desirable? *(carried over from original proposal)*
4. Handling of squash-merged or rebase-merged topics is explicitly deferred. *(carried over from original proposal)*
5. Are there scripts that rely on `%(worktreepath)` being empty for rebasing/bisecting branches? *(new, critical for backward compatibility)*
6. Should the porcelain output of `git worktree list` include an `is-main-worktree` annotation to help scripts avoid attempting to delete the main worktree? *(Phillip Wood’s proposal, now compounded by Eric Sunshine’s ordering concern)*
7. Is the current validation logic (accepting non-existent branches) intentional for `for-each-ref`, or should it be tightened? *(Phillip Wood’s question, now relevant to `for-each-ref`)*
8. How should `for-each-ref` handle short branch names (e.g., `lstrip=2`) to simplify composability with other commands? *(Phillip Wood’s follow-up suggestion, now relevant to `for-each-ref`)*
9. Could a `foreach`-style mechanism (e.g., `git worktree foreach`) still be useful for cases not covered by `for-each-ref`? *(Eric Sunshine’s proposal, now less urgent but still open)*
10. If a `foreach` mechanism is adopted, what syntax and safety guarantees (e.g., shell injection, error handling) should it provide? *(Eric Sunshine’s proposal, now less urgent but still open)*
11. How should the project address the broken ordering invariant when filtering worktrees? Options include: (a) preserving the main-worktree-first guarantee even in filtered output, (b) annotating the main worktree in output, or (c) accepting the breakage and documenting it as a backward-incompatible change. *(Eric Sunshine’s new concern)*

Participant positions
- Jasper Mayone (author): Proposes abandoning `--branch=<branch>` in favor of extending `%(worktreepath)` in `ref-filter.c`, framing the change as a bug fix to align with existing Git behavior. Acknowledges backward-compatibility concerns (scripts relying on empty `%(worktreepath)`) and Phillip Wood’s earlier concerns about main-worktree annotation and validation but does not address them in this pivot.
- Kristoffer Haugsbakk: Surface-level review in the original thread noted that `git for-each-ref --format='%(worktreepath)'` provides similar functionality but lacks support for rebasing/bisecting worktrees. This gap is now addressed by Jasper’s proposal.
- Junio C Hamano (maintainer): Initially proposed `--branch` as a general alternative to `--merged`/`--no-merged`; later sketched `--filter-command` as a more general mechanism. Neither proposal is directly addressed by the pivot to `%(worktreepath)`, but the pivot avoids the extensibility questions Junio raised.
- Eric Sunshine: **Substantive review** identifies a latent design tension: filtering worktrees (via `for-each-ref` or any other mechanism) breaks the invariant that the main worktree appears first in output, creating a risk for scripts that rely on this ordering. Proposed a `for-each`-style mechanism (`git worktree foreach`) and `--filter=branch:<name>` for extensibility in earlier messages; these remain unresolved but are now less urgent due to the pivot.
- Phillip Wood: Substantive review in the original thread identified code duplication, usability concerns, and validation questions. Proposed refactoring `branch.c` to expose `branch_find_checkout()`, adding an `is-main-worktree` annotation, and standardizing on short branch names. These concerns remain unaddressed and are now compounded by Eric Sunshine’s ordering concern. The pivot to `%(worktreepath)` does not engage with Phillip’s proposals directly.

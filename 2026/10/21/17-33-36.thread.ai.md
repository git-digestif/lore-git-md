Thread identity
Subject: RFC: `git worktree list --merged` / `--no-merged`
Series version: RFC (no version number)
Originating author: Jasper Mayone
Thread type: feature proposal (RFC)

Core problem or goal
Add `--merged` and `--no-merged` filters to `git worktree list` so developers can quickly identify which worktrees correspond to topics that have already landed upstream. The filters reuse the existing `ref_filter`/`OPT_MERGED` machinery for consistent parsing and error messages.

Current status
Proposed; no prior versions. Implementation is complete and self-contained, touching only `builtin/worktree.c` and adding comprehensive tests in `t/t2402-worktree-list.sh`. No maintainer feedback yet; no integration branch assignment. The patch is ready for review and unlikely to be controversial on technical grounds.

Key technical details
- New CLI options: `--merged[=<commit>]`, `--no-merged[=<commit>]`
- Default commit: HEAD (consistent with `git branch --merged`)
- Subsystem: worktree listing (`git worktree list`)
- Files: `builtin/worktree.c`, `t/t2402-worktree-list.sh`
- Symbols: reuses `struct ref_filter` and `OPT_MERGED` from `ref-filter.h`
- Behavior: strict reachability check on each worktree’s HEAD; output remains informational (no automatic removal). Tests cover unborn branches, broken worktrees, bare repositories, porcelain output, and error conditions.
- On-disk format: no changes

Open questions and loose ends
1. Should the main worktree be filtered out by default?
2. Is HEAD the right default commit for the filter?
3. Is reusing `ref_filter` acceptable, or should the worktree command have its own parsing?
4. Would a future `git worktree remove --merged` be desirable?
5. Handling of squash-merged or rebase-merged topics is explicitly deferred.

Participant positions
- Jasper Mayone (author): proposes the feature, provides full implementation, raises the five open questions, and defers squash/rebase handling. No other participants have weighed in yet.

Thread identity
Subject: RFC: `git worktree list --merged` / `--no-merged`
Series version: RFC (no version number)
Originating author: Jasper Mayone
Thread type: feature proposal (RFC)

Core problem or goal
Add filtering capabilities to `git worktree list` to help developers identify worktrees associated with merged or unmerged topics. The original proposal focused on `--merged`/`--no-merged` filters, but Junio C Hamano and Eric Sunshine have proposed increasingly general alternatives: first a `--branch` filter primitive, then a `for-each`-style mechanism akin to `git submodule foreach`. These alternatives would subsume the merged/unmerged use case while enabling broader worktree inspection and management.

Current status
Proposed; no prior versions. Implementation exists for the `--merged`/`--no-merged` approach, touching `builtin/worktree.c` and adding tests in `t/t2402-worktree-list.sh`. Junio’s feedback proposes a `--branch` filter primitive; Eric Sunshine’s feedback proposes a `for-each`-style mechanism. The original implementation’s future is uncertain, and the thread remains in RFC stage with open design questions about the scope and generality of the feature. No integration branch assignment.

Key technical details
- Original CLI options: `--merged[=<commit>]`, `--no-merged[=<commit>]` (default: HEAD)
- Proposed alternatives:
  - `--branch=<branch>` (Junio): a filter primitive accepting multiple values
  - `foreach` subcommand (Sunshine): execute arbitrary shell commands across worktrees (e.g., `git worktree foreach 'git branch --contains HEAD'`)
- Subsystem: worktree listing (`git worktree list`)
- Files: `builtin/worktree.c`, `t/t2402-worktree-list.sh`
- Symbols: reuses `struct ref_filter` and `OPT_MERGED` from `ref-filter.h` (original approach)
- Behavior: strict reachability check on each worktree’s HEAD; output remains informational. Tests cover unborn branches, broken worktrees, bare repositories, porcelain output, and error conditions.
- On-disk format: no changes

Open questions and loose ends
1. Should the main worktree be filtered out by default? *(original proposal)*
2. Is HEAD the right default commit for the filter? *(original proposal)*
3. Is reusing `ref_filter` acceptable, or should the worktree command have its own parsing? *(original proposal)*
4. Would a future `git worktree remove --merged` be desirable? *(original proposal)*
5. Handling of squash-merged or rebase-merged topics is explicitly deferred. *(original proposal)*
6. Is the `--branch` filter primitive a better design foundation than `--merged`/`--no-merged`? *(Junio’s proposal)*
7. If `--branch` is adopted, how should it interact with existing branch-filtering commands (e.g., `git branch --contains`) to achieve merged/unmerged filtering? *(Junio’s proposal)*
8. **New**: Is a `for-each`-style mechanism (e.g., `git worktree foreach`) a better design than either `--merged`/`--no-merged` or `--branch`? *(Sunshine’s proposal)*
9. **New**: If a `foreach` mechanism is adopted, what syntax and safety guarantees (e.g., shell injection, error handling) should it provide?

Participant positions
- Jasper Mayone (author): proposes the `--merged`/`--no-merged` feature, provides full implementation, raises the five original open questions, and defers squash/rebase handling. No response yet to Junio’s `--branch` or Eric Sunshine’s `foreach` alternatives.
- Harald Nordgren: initially raised a broader design question about relaxing the one-branch-per-worktree rule; the question was surface-level (no code or alternative design proposed). After Junio’s authoritative dismissal, Harald acknowledged the technical rationale (shared repository state causing unexpected HEAD movement) and withdrew his suggestion. His replies do not engage with the `--merged`/`--no-merged`, `--branch`, or `foreach` proposals.
- Junio C Hamano (maintainer): authoritatively dismissed Harald’s broader design question, explaining the technical rationale (shared repository state, unexpected HEAD movement) and pointing to `git worktree add -d` as the existing workaround. Proposes a `--branch` filter primitive as a more general and flexible alternative to `--merged`/`--no-merged`, arguing the current approach unfairly narrows the problem space. The feedback is substantive and technical, suggesting the original design may be too specific.
- Kristoffer Haugsbakk: surface-level reply questioning the use of the term "mechanical sympathy" in the context of AI-assisted workflows and worktree restrictions. The message does not engage with the technical substance of the `--merged`/`--no-merged` feature, the `--branch` proposal, the `foreach` proposal, or the broader design question. No substantive feedback or alternative proposals introduced.
- Eric Sunshine: endorses Junio’s critique that the `--merged`/`--no-merged` design is overly narrow and proposes an even more general `for-each`-style mechanism akin to `git submodule foreach`. This would enable arbitrary shell commands across worktrees (e.g., `git worktree foreach 'git branch --contains HEAD'`), subsuming the merged/unmerged use case and any other filtering or inspection need. The suggestion is conceptual but substantive, reframing the problem from filtering to iteration with arbitrary logic. No implementation or syntax proposed.

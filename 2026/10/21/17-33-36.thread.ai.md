Thread identity
Subject: RFC: `git worktree list --merged` / `--no-merged`
Series version: RFC v2 (implementation patch for `--branch=<branch>`)
Originating author: Jasper Mayone
Thread type: feature proposal and implementation

Core problem or goal
Add filtering capabilities to `git worktree list` to help developers identify worktrees associated with specific branches. The current implementation provides a general `--branch=<branch>` filter primitive, replacing the earlier `--merged`/`--no-merged` proposal. This filter can be composed with existing branch-filtering commands (e.g., `git branch --merged`) to achieve merged/unmerged filtering. The design discussion now includes whether to use a dedicated `--branch` option or a more generic `--filter` mechanism for future extensibility.

Current status
Implementation exists for `--branch=<branch>` filtering. Junio’s feedback (proposing `--branch`) has been addressed; Eric Sunshine’s `for-each`-style alternative and his newer `--filter` naming proposal remain unaddressed but acknowledged. Phillip Wood’s review identifies code duplication, usability concerns, and validation questions, suggesting refactoring and output annotation improvements. His follow-up proposes a `--format='--branch=%(refname:lstrip=2)'` tweak to simplify composability and implementation. No integration branch assignment.

Key technical details
- CLI option: `--branch=<branch>` (accepts multiple values, short names or full refs; Phillip Wood’s suggestion would standardize on short names only via `lstrip=2`). Eric Sunshine proposes a more generic `--filter=branch:<name>` for future extensibility.
- Subsystem: worktree listing (`git worktree list`)
- Files: `builtin/worktree.c`, `Documentation/git-worktree.adoc`, `t/t2402-worktree-list.sh`
- Symbols: new helpers `checked_out_branch()` (determines branch during rebase/bisect) and `filter_by_branch()` (uses `strset` for filtering); proposed refactoring would expose `branch_find_checkout()` from `branch.c`
- Behavior: lists worktrees with the specified branch checked out (including during rebase/bisect); detached worktrees are excluded; invalid branch names error. Output remains informational but may gain an `is-main-worktree` annotation. Phillip Wood’s `lstrip=2` suggestion would eliminate the need to handle full refs, simplifying validation.
- Composability: designed to work with `git branch --merged`/`--no-merged` (e.g., `git worktree list $(git branch --format='--branch=%(refname:lstrip=2)' --merged origin/main)`). Eric Sunshine’s `--filter` proposal would enable future filtering by other properties (e.g., locked status, prunability, path).
- On-disk format: no changes
- Tests: cover unborn branches, prunable worktrees, full ref names, tags with branch-name collisions, porcelain output, and error conditions.

Open questions and loose ends
1. Should the main worktree be filtered out by default? *(carried over from original proposal)*
2. Is HEAD the right default commit for composed filters (e.g., `git branch --merged`)? *(carried over from original proposal)*
3. Is reusing branch-name validation from `git branch` acceptable, or should `git worktree` have its own parsing? *(carried over from original proposal)*
4. Would a future `git worktree remove --merged` be desirable? *(carried over from original proposal)*
5. Handling of squash-merged or rebase-merged topics is explicitly deferred. *(carried over from original proposal)*
6. How should `--branch` interact with existing branch-filtering commands (e.g., `git branch --contains`) to achieve merged/unmerged filtering? *(Junio’s proposal; now addressed via composability)*
7. Is a `for-each`-style mechanism (e.g., `git worktree foreach`) a better design than `--branch`? *(Sunshine’s proposal; unaddressed but acknowledged)*
8. If a `foreach` mechanism is adopted, what syntax and safety guarantees (e.g., shell injection, error handling) should it provide? *(Sunshine’s proposal; unaddressed)*
9. Should `branch.c:prepare_checked_out_branches()` be refactored to expose a reusable `branch_find_checkout()` helper for both `git branch` and `git worktree list`? *(Phillip Wood’s proposal)*
10. Should the porcelain output include an `is-main-worktree` annotation to help scripts avoid attempting to delete the main worktree? *(Phillip Wood’s proposal)*
11. Is the current validation logic (rejecting syntactically invalid branch names but accepting non-existent branches) intentional? *(Phillip Wood’s question)*
12. Should the implementation standardize on short branch names (via `lstrip=2`) to simplify validation and composability examples? *(Phillip Wood’s follow-up suggestion)*
13. Is `--branch` the right name for the option, or should a more generic `--filter=branch:<name>` be adopted to enable future filtering by other properties (e.g., locked status, prunability, path) and logical combinations (OR, AND, NOT)? *(Eric Sunshine’s new proposal)*

Participant positions
- Jasper Mayone (author): implements `--branch=<branch>` as a general filter primitive, addressing Junio’s feedback and enabling composability with `git branch --merged`. Acknowledges Sunshine’s `foreach` and `--filter` proposals as potential future directions but does not implement them. Raises no new objections to the carried-over open questions.
- Harald Nordgren: surface-level reply to the original RFC (no engagement with `--branch`, `foreach`, or `--filter` proposals).
- Junio C Hamano (maintainer): proposed `--branch` as a more general alternative to `--merged`/`--no-merged`; this feedback is now addressed by the new implementation.
- Kristoffer Haugsbakk: surface-level reply to the original RFC (no engagement with `--branch`, `foreach`, or `--filter` proposals).
- Eric Sunshine: proposed a `for-each`-style mechanism as an even more general alternative; this remains unaddressed but acknowledged. Now proposes a generic `--filter=branch:<name>` option to enable future extensibility and logical combinations, framing this as a design discussion rather than a blocker.
- Phillip Wood: substantive review identifying code duplication, usability concerns, and validation questions. Proposes refactoring `branch.c` to expose a reusable `branch_find_checkout()` helper, adding an `is-main-worktree` annotation to porcelain output, and clarifying validation logic. Follow-up suggests standardizing on short branch names via `--format='--branch=%(refname:lstrip=2)'` to simplify implementation and composability. Does not block the patch but advocates for follow-up improvements.

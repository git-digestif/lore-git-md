Thread identity
Subject: RFC: `git worktree list --merged` / `--no-merged`
Series version: RFC v2 (implicit; replaces prior `--merged`/`--no-merged` proposal)
Originating author: Jasper Mayone
Thread type: feature proposal (now implementation patch)

Core problem or goal
Add filtering capabilities to `git worktree list` to help developers identify worktrees associated with specific branches. The original goal of merged/unmerged filtering is now addressed indirectly via a general `--branch=<branch>` filter primitive, which can be composed with existing branch-filtering commands (e.g., `git branch --merged`). This shift follows maintainer feedback that the problem space is broader than merged/unmerged filtering alone.

Current status
Implementation exists for `--branch=<branch>` filtering, replacing the earlier `--merged`/`--no-merged` proposal. The patch touches `builtin/worktree.c`, `Documentation/git-worktree.adoc`, and `t/t2402-worktree-list.sh`. Junio’s feedback (proposing `--branch`) has been addressed; Eric Sunshine’s `for-each`-style alternative remains unaddressed but acknowledged as a potential future direction. No integration branch assignment.

Key technical details
- CLI option: `--branch=<branch>` (accepts multiple values, short names or full refs)
- Subsystem: worktree listing (`git worktree list`)
- Files: `builtin/worktree.c`, `Documentation/git-worktree.adoc`, `t/t2402-worktree-list.sh`
- Symbols: new helpers `checked_out_branch()` (determines branch during rebase/bisect) and `filter_by_branch()` (uses `strset` for filtering)
- Behavior: lists worktrees with the specified branch checked out (including during rebase/bisect); detached worktrees are excluded; invalid branch names error. Output remains informational.
- Composability: designed to work with `git branch --merged`/`--no-merged` (e.g., `git worktree list $(git branch --format='--branch=%(refname)' --merged origin/main)`)
- On-disk format: no changes
- Tests: cover unborn branches, prunable worktrees, full ref names, tags with branch-name collisions, porcelain output, and error conditions.

Open questions and loose ends
1. Should the main worktree be filtered out by default? *(carried over from original proposal)*
2. Is HEAD the right default commit for composed filters (e.g., `git branch --merged`)? *(carried over from original proposal)*
3. Is reusing branch-name validation from `git branch` acceptable, or should `git worktree` have its own parsing? *(carried over from original proposal)*
4. Would a future `git worktree remove --merged` be desirable? *(carried over from original proposal)*
5. Handling of squash-merged or rebase-merged topics is explicitly deferred. *(carried over from original proposal)*
6. How should `--branch` interact with existing branch-filtering commands (e.g., `git branch --contains`) to achieve merged/unmerged filtering? *(Junio’s proposal; now addressed via composability)*
7. Is a `for-each`-style mechanism (e.g., `git worktree foreach`) a better design than `--branch`? *(Sunshine’s proposal; unaddressed but acknowledged)*
8. If a `foreach` mechanism is adopted, what syntax and safety guarantees (e.g., shell injection, error handling) should it provide? *(Sunshine’s proposal; unaddressed)*

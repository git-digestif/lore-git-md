Thread identity
Subject: RFC: `git worktree list --merged` / `--no-merged`
Series version: RFC (no version number)
Originating author: Jasper Mayone
Thread type: feature proposal (RFC)

Core problem or goal
Add `--merged` and `--no-merged` filters to `git worktree list` so developers can quickly identify which worktrees correspond to topics that have already landed upstream. The filters reuse the existing `ref_filter`/`OPT_MERGED` machinery for consistent parsing and error messages.

Current status
Proposed; no prior versions. Implementation is complete and self-contained, touching only `builtin/worktree.c` and adding comprehensive tests in `t/t2402-worktree-list.sh`. No maintainer feedback yet on the feature itself; no integration branch assignment. The patch is ready for review and unlikely to be controversial on technical grounds. The broader design question of allowing multiple worktrees to check out the same branch was authoritatively dismissed by Junio C Hamano, closing that line of discussion.

Key technical details
- New CLI options: `--merged[=<commit>]`, `--no-merged[=<commit>]`
- Default commit: HEAD (consistent with `git branch --merged`)
- Subsystem: worktree listing (`git worktree list`)
- Files: `builtin/worktree.c`, `t/t2402-worktree-list.sh`
- Symbols: reuses `struct ref_filter` and `OPT_MERGED` from `ref-filter.h`
- Behavior: strict reachability check on each worktree’s HEAD; output remains informational (no automatic removal). Tests cover unborn branches, broken worktrees, bare repositories, porcelain output, and error conditions.
- On-disk format: no changes

Open questions and loose ends
1. Should the main worktree be filtered out by default?
2. Is HEAD the right default commit for the filter?
3. Is reusing `ref_filter` acceptable, or should the worktree command have its own parsing?
4. Would a future `git worktree remove --merged` be desirable?
5. Handling of squash-merged or rebase-merged topics is explicitly deferred.

Participant positions
- Jasper Mayone (author): proposes the feature, provides full implementation, raises the five original open questions, and defers squash/rebase handling.
- Harald Nordgren: initially raised a broader design question about relaxing the one-branch-per-worktree rule; the question was surface-level (no code or alternative design proposed). After Junio’s authoritative dismissal, Harald acknowledged the technical rationale (shared repository state causing unexpected HEAD movement) and withdrew his suggestion. His replies do not engage with the `--merged`/`--no-merged` implementation itself.
- Junio C Hamano (maintainer): authoritatively dismissed Harald’s broader design question, explaining the technical rationale (shared repository state, unexpected HEAD movement) and pointing to `git worktree add -d` as the existing workaround. The reply is final and closes the broader discussion; it does not address the `--merged`/`--no-merged` feature itself.

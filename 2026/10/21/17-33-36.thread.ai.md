Thread identity
Subject: RFC: `git worktree list --merged` / `--no-merged`
Series version: RFC (no version number)
Originating author: Jasper Mayone
Thread type: feature proposal (RFC)

Core problem or goal
Add filtering capabilities to `git worktree list` to help developers identify worktrees associated with merged or unmerged topics. The original proposal focused on `--merged`/`--no-merged` filters, but Junio C Hamano has suggested a more general `--branch` filter primitive as a better foundation, which could then be combined with existing branch-filtering commands to achieve the same functionality.

Current status
Proposed; no prior versions. Implementation exists for the `--merged`/`--no-merged` approach, touching `builtin/worktree.c` and adding tests in `t/t2402-worktree-list.sh`. Junio’s feedback proposes a significant design shift toward a `--branch` filter primitive, leaving the original implementation’s future uncertain. No integration branch assignment; thread remains in RFC stage with open design questions.

Key technical details
- Original CLI options: `--merged[=<commit>]`, `--no-merged[=<commit>]` (default: HEAD)
- Proposed alternative: `--branch=<branch>` (accepting multiple values)
- Subsystem: worktree listing (`git worktree list`)
- Files: `builtin/worktree.c`, `t/t2402-worktree-list.sh`
- Symbols: reuses `struct ref_filter` and `OPT_MERGED` from `ref-filter.h` (original approach)
- Behavior: strict reachability check on each worktree’s HEAD; output remains informational. Tests cover unborn branches, broken worktrees, bare repositories, porcelain output, and error conditions.
- On-disk format: no changes

Open questions and loose ends
1. Should the main worktree be filtered out by default? *(original proposal)*
2. Is HEAD the right default commit for the filter? *(original proposal)*
3. Is reusing `ref_filter` acceptable, or should the worktree command have its own parsing? *(original proposal)*
4. Would a future `git worktree remove --merged` be desirable? *(original proposal)*
5. Handling of squash-merged or rebase-merged topics is explicitly deferred. *(original proposal)*
6. **New**: Is the `--branch` filter primitive a better design foundation than `--merged`/`--no-merged`? *(Junio’s proposal)*
7. **New**: If `--branch` is adopted, how should it interact with existing branch-filtering commands (e.g., `git branch --contains`) to achieve merged/unmerged filtering?

Participant positions

- Harald Nordgren: initially raised a broader design question about relaxing the one-branch-per-worktree rule; the question was surface-level (no code or alternative design proposed). His replies do not engage with the `--merged`/`--no-merged` or `--branch` proposals.

The feedback is substantive and technical, suggesting the original design may be too specific.

The message does not engage with the technical substance of the `--merged`/`--no-merged` feature, the `--branch` proposal, or the broader design question.

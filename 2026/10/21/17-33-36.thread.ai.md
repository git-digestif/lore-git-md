Thread identity
Subject: RFC: `git worktree list --merged` / `--no-merged`
Series version: v5 (addresses performance regression in `%(worktreepath)` and adds `%(currentworktree)` atom)
Originating author: Jasper Mayone
Thread type: feature proposal, design discussion, and bugfix implementation

Core problem or goal
Add filtering capabilities to `git worktree list` to help developers identify worktrees associated with specific branches, while addressing two related safety issues: (1) `git worktree remove` currently allows deletion of worktrees in the middle of a rebase, bisect, cherry-pick, revert, or `git am` operation, risking data loss; and (2) `git for-each-ref`'s `%(worktreepath)` atom does not report the worktree path for branches being rebased or bisected, creating a mismatch with how `git worktree add` and `git branch -d` already treat those branches as "checked out." The series now achieves this by extending `%(worktreepath)` in `ref-filter.c` and introducing a new `%(currentworktree)` atom, which avoids introducing new CLI options and aligns behavior across Git commands. The pivot to `ref-filter.c` introduces concerns about safety, composability, and performance, all of which are now addressed in v5.

Current status
The series consists of **five patches**, all of which are **ready for review**:
1. **Safety fix** making `git worktree remove` refuse to delete a worktree in the middle of a rebase, `git am`, bisect, cherry-pick, or revert sequence unless `--force` is given. The updated `worktree_is_in_progress()` checks for `CHERRY_PICK_HEAD` and `REVERT_HEAD` when a single-commit cherry-pick or revert has completed without conflicts. The documentation for `git worktree remove` lists the conditions requiring `--force` in a bulleted format, with each item as a self-contained sentence per Phillip Wood’s suggestion. **Ben Knoble’s reply** disagrees with the formatting change, preferring the original phrasing as a single clause, but the change is minor and unlikely to be controversial. The patch remains a clear, well-motivated **bugfix** that closes a real safety hole.
2. **Documentation update** adding a warning to `git-for-each-ref(1)` about parsing `%(worktreepath)` safely, recommending the use of quoting options (e.g., `--shell`) or NUL-terminated output (`%00`). The warning correctly states that only one worktree is shown for a branch checked out in multiple worktrees, as confirmed by Phillip Wood, Ben Knoble, and Junio C Hamano. The patch is **ready for integration**.
3. **Enhancement** extending `%(worktreepath)` in `ref-filter.c` to report the worktree path for branches being rebased or bisected. The v5 patch **resolves the performance regression** from v4 by refactoring `branch.c` to use a hashmap (`checked_out_worktrees`) for O(1) lookups, mirroring the old `ref-filter.c` implementation. The helper, `branch_checked_out_worktree()`, now retrieves the worktree path in constant time, restoring the original performance while avoiding code duplication. The patch removes ~50 lines of unused worktree-mapping machinery and documents the breaking change for bare repositories. Tests verify the new behavior for rebasing, bisecting, and performance-critical lookups.
4. **New patch** adding `%(currentworktree)`, a ref-filter atom that returns the path of the current worktree if the ref is checked out there (or being rebased/bisected), and an empty string otherwise. The atom is implemented using a second hashmap (`current_worktree_branches`) in `branch.c`, populated during `prepare_checked_out_branches()`. The lookup is O(1), and the atom is designed to be used with `%(if)` to treat the current worktree differently from others. This directly addresses Phillip Wood’s architectural suggestion from v4 and enables more composable formatting in `git branch`. Tests verify the atom’s behavior in both main and linked worktrees.
5. **Cleanup patch** replacing v4’s fourth patch and using `%(currentworktree)` to simplify the logic in `git branch`. The default format now uses `%(currentworktree)` to omit the `+` marker and worktree path for branches being rebased or bisected in the current worktree, reducing complexity in `print_ref_list()` and improving composability for users who customize `--format` strings. The patch is concise and leverages the new atom effectively.

The series is **backward-incompatible** for scripts relying on:
- The current empty `%(worktreepath)` value for rebasing/bisecting branches,
- The `+` marker in `git branch` output,
- The ability to delete in-progress worktrees without `--force`,
- The old behavior of printing the `git_dir` of bare worktrees in `%(worktreepath)`.

The commit messages explicitly ask whether any such scripts exist, signaling awareness of the compatibility risk. The implementation is clean, well-tested, and addresses all design tensions identified in earlier RFC discussions. The performance regression in v4 is resolved, and the new `%(currentworktree)` atom improves composability and maintainability.

- **Performance**: The v5 patch **resolves the O(N*M) performance regression** in `%(worktreepath)` by using a hashmap for O(1) lookups, restoring the original performance. The new `%(currentworktree)` atom also uses O(1) lookups.
- **Limitations of `for-each-ref`**:
  1. No NUL-terminated output, complicating parsing of worktree paths with newlines (mitigated by documentation warning and recommendation to use quoting options or `%00`).

  3. Only one worktree is shown when a branch is checked out in multiple worktrees (confirmed as correct, though the scenario is discouraged by Git’s porcelain).
  4. Risk of surfacing worktrees in transient, high-risk states (e.g., mid-rebase), which could lead to data loss if used with `git worktree remove` (mitigated by the safety fix in `git worktree remove`).
  5. **Breaking change**: Silently dropping support for printing the `git_dir` of bare worktrees is now documented as a breaking change.
- **Safety risks**: The interaction between `for-each-ref --merged` and `git worktree remove` introduces a risk of data loss if mid-rebase worktrees are included in filtered output. The series mitigates this risk by making `git worktree remove` refuse deletion of in-progress worktrees unless explicitly forced, aligning with Git’s general principle of protecting uncommitted or in-progress work.

This is the second patch in Harald Nordgren’s v3 series extending `git branch --delete-merged` to detect branches whose changes were integrated via rebase merges. The patch implements the rebase-detection logic: when an upstream commit contains the exact file versions introduced by the branch (even if the branch tip itself is not reachable), the branch is considered merged and can be deleted.

The implementation is clean and efficient. It uses tree-based diffing to compare the branch’s changes against each upstream commit since the fork point, avoiding the need to fetch blobs or perform expensive merge simulations. The patch adds a new `find_landed_commit()` helper that walks upstream history in reverse, checking whether any commit touches the same paths as the branch and contains the branch’s exact file versions. This approach is fast (Harald’s testing shows it adds only ~50ms overhead for 80 branches) and works in blobless clones without fetching blobs.

The output format is consistent with the rest of the series: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)` names the first upstream commit that contains the branch’s changes, even if those changes were later reverted or modified. The patch also updates the documentation to clarify that `--delete-merged` now detects rebase merges by default, treating them as equivalent to traditional merges for the purpose of branch cleanup.

Test coverage is thorough, with new tests for rebase merges, squash merges (in the next patch), and edge cases like reverted changes and partial landings. The rebase-detection logic is uncontroversial and ready for integration; the only open question is whether it should remain part of `--delete-merged` or move to Junio’s proposed `--delete-irrelevant` option, which is still under discussion. This patch stands on its own and could be merged independently if the CLI design debate is deferred.

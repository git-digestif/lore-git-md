Subject: [PATCH v4] rev-list: fix `--grep` and related option parsing when followed by another option
Series version: standalone patch, v4 (now proposed v5 direction)
Originating author: Azuama Odinaka Maximus
Thread type: bugfix patch

Core problem or goal
The `git rev-list` command misparses any of the 18 `parse_long_opt()`-style options (`--grep`, `--author`, `--committer`, `--since`, `--until`, etc.) when the option is immediately followed by another argument that begins with `--`. The parser treats the next argument as a separate flag rather than as the option's value, causing the command to fail or behave unpredictably. The patch aims to ensure these options are handled early in the argument scan so that their following arguments are always treated as values, even if they begin with `--`. The author now proposes a more robust architectural direction: refactoring the early option scan to reuse the same option-recognition logic as the main parser, eliminating the maintenance hazard of hardcoded option lists.

Current status
Under active review; fourth version posted, with a proposed fifth version direction. The patch is a targeted refactor in `builtin/rev-list.c` that introduced a helper function, `rev_list_option_takes_argument()`, to recognize all 18 affected options during the early option scan and skip their arguments. The test suite (`t/t6022-rev-list-missing.sh`) includes five new tests verifying that `--grep` and `--author` patterns beginning with `--` are correctly applied. **Maintainer review (Junio C Hamano) identified a critical architectural flaw**: the hardcoded list of 19 option strings in the helper function duplicates parser logic and is already incomplete (missing `--diff-merges`, `--src-prefix`, `--dst-prefix`, etc.), creating a maintenance hazard. The author has responded with a proposed direction for v5: refactoring the early option scan to reuse the same option-recognition logic as the main parser, rather than hardcoding a list of option names. The architectural direction remains unresolved; the patch is not ready for merging.

Open questions and loose ends
- **Architectural direction**: The author proposes refactoring the early option scan to reuse the same option-recognition logic as the main parser, avoiding hardcoded lists. This would involve separating option recognition from option application and touching `revision.c`, `diff-merges.c`, and `diff.c`. The maintainer has not yet weighed in on whether this approach is viable, or if an existing Git parser interface should be extended instead.
- **Scope of the fix**: The maintainer’s example (`git rev-list --src-prefix --missing-only HEAD`) suggests the problem may extend beyond the 18 options currently addressed. The fix must either clearly document its limitations or be expanded to cover all options that could appear in `rev-list` invocations. The proposed refactor would naturally address this by reusing the main parser’s logic.
- **Implementation details**: The author has not yet settled on a concrete implementation for the proposed refactor. Key challenges include accommodating both table-driven (`add_diff_options`) and hand-written (`handle_revision_opt`) parsers.
- **Test coverage**: The architectural concern may necessitate revisiting test coverage to ensure the revised approach handles all cases correctly, including options not previously addressed (e.g., `--diff-merges`, `--src-prefix`).

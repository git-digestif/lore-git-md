This is an RFC feature proposal for `git worktree list`, adding `--merged` and `--no-merged` filters.

The patch introduces two new options to `git worktree list` that mirror the behavior of `git branch --merged` and `git branch --no-merged`. The filters apply strict reachability checks to the HEAD of each worktree, listing only those whose HEAD is reachable from (or not reachable from) a given commit. The default commit is HEAD, consistent with other ref-filter commands. The output remains informational; removal is left to scripts or manual `git worktree remove` calls.

The motivation is practical: developers who use one worktree per topic branch currently have no direct way to identify which worktrees are "done" (i.e., whose topic has landed upstream). The patch addresses this by reusing the existing `struct ref_filter` and `OPT_MERGED` machinery from `ref-filter.h`, ensuring consistent parsing and error messages across Git commands. The implementation is minimal, touching only `builtin/worktree.c` and adding tests in `t/t2402-worktree-list.sh`.

Four open questions are posed for discussion: whether the main worktree should be filtered out by default, whether HEAD is the right default commit for the filter, whether reusing `ref_filter` is acceptable, and whether a future `git worktree remove --merged` would be desirable. The patch does not attempt to handle squash-merged or rebase-merged topics, deferring that to potential future work.

The patch is well-motivated and clearly scoped. It reuses existing infrastructure, includes thorough tests, and raises reasonable design questions for the list. The implementation looks clean and uncontroversial, though the default behavior (listing the main worktree) may spark debate.

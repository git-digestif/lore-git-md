This is part 9 of the 13-patch series implementing **pack index v3** support for SHA-1/SHA-256 interoperability. The patch adds the ability to *read* pack index v3 files, completing the write-side implementation introduced in earlier patches.

The core change is a refactoring of the binary search logic in `hash-lookup.c` to support variable-length object ID lookups. The new `bsearch_hash_v3()` function handles the v3 format’s dual-sorted structure: a table of shortened object IDs (for fast prefix lookups) and a separate table of full object IDs in pack order, linked by an index map. The patch also extends the `packed_git` structure with per-algorithm metadata (`data_offset`, `full_oid_offset`, `order_map_offset`) to avoid recomputing these values during lookups.

Key behavior changes:
- Pack index v3 files can now be loaded and queried, though the series does not yet enable them by default.
- Lookups for object IDs in an unsupported algorithm (e.g., querying a SHA-1 object in a SHA-256-only v3 index) now fail gracefully instead of crashing.
- The pack reverse index (`pack-revindex.c`) is updated to use the v3 order map, ensuring offsets are correctly resolved regardless of the object’s position in the pack.
- Test coverage in `t5302-pack-index.sh` is adjusted to skip v1/v2 tests when `COMPAT_HASH` is set, since older formats cannot represent compatibility object IDs.

The patch is technically solid, with careful attention to edge cases (e.g., 32-bit alignment, bounds checking). The refactoring of `bsearch_hash()` into a generic helper (`bsearch_hash_1()`) is a clean abstraction that avoids code duplication. The only notable limitation is that the test suite cannot yet run with `GIT_TEST_DEFAULT_HASH=sha256:sha1`, as noted in the cover letter, but this is a test harness issue rather than a flaw in the implementation.

This is a critical piece of the interoperability puzzle, enabling Git to read the dual-algorithm indices written by earlier patches. The series as a whole is well-motivated and addresses a long-standing gap in SHA-256 support.

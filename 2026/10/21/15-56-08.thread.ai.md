Subject: [PATCH] commit: move `git_commit_encoding` to `repo_config_values`
Series version: standalone patch (part of the `the_repository` removal effort)
Originating author: Okhuomon Ajayi
Thread type: patch series (infrastructure refactoring)

Core problem or goal
Eliminate the global `git_commit_encoding` variable by making it repository-scoped, as part of the ongoing `the_repository` removal project to improve Git’s modularity and thread-safety. The discussion has expanded to a design question: whether the value should be embedded in the `repo_config_values` struct (current approach) or passed directly as a `const char *` parameter to functions that need it (Junio’s alternative).

Current status
Under review; no prior versions of this patch posted. The patch is a clean, incremental step in the `the_repository` removal series, but Junio’s critique challenges the established pattern of moving globals into `repo_config_values`. The outcome may set a precedent for how similar globals are handled in future patches.

Key technical details
- Files touched: `commit.c`, `environment.c`, `environment.h`
- New or renamed symbols: `repo_config_values.commit_encoding` (field added), `write_commit_tree()` now takes a `struct repository *` parameter
- Old behavior: `git_commit_encoding` was a global variable read by `get_commit_output_encoding()`
- New behavior: `commit_encoding` is stored in `repo_config_values` and accessed via the repository struct; `write_commit_tree()` uses the repository-specific value
- Junio’s alternative: pass `commit_encoding` as a `const char *` parameter to `write_commit_tree()` and related functions, avoiding changes to `repo_config_values`
- On-disk format: unchanged
- Test coverage: none added in this patch; existing tests should continue to pass

Open questions and loose ends
- The patch still passes `the_repository` to `write_commit_tree()` in `commit_tree_extended()`; this global reference will likely be addressed in a future patch in the series.
- Junio’s critique raises a fundamental design question: whether repository-scoped configuration is the right abstraction for `git_commit_encoding`, or if a simpler parameter-passing approach would be preferable. The author must respond to this objection.
- No other substantive review feedback has been received yet.

Participant positions
- Okhuomon Ajayi (author): posted the patch as a mechanical refactoring following the established pattern of the `the_repository` removal series.
- Junio C Hamano (maintainer): objects to the approach, arguing that embedding `git_commit_encoding` in `repo_config_values` adds unnecessary complexity. Proposes passing the encoding as a `const char *` parameter to functions that need it, keeping the change localized to `commit.c`.

Related work
- Part of the broader `the_repository` removal effort (primary driver: René Scharfe), which has consistently moved globals into `repo_config_values`.
- Junio’s alternative would deviate from this pattern, potentially influencing how similar globals are handled in future patches.

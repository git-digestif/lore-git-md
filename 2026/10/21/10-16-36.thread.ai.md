Subject: [PATCH 0/3] Fix 64-to-32 truncations on LLP64 platforms (Windows)

Thread type: patch series (bugfix, platform compatibility)

Core problem or goal
Git silently truncates or misbehaves with files larger than 4 GiB on Windows (LLP64 platforms where `long` is 32-bit). The series fixes four specific truncation or overflow sites: (1) object database writes (truncated blobs), (2) word-diff buffer allocation (crash due to overflow), (3) file conversion helpers (incorrect binary detection, CRLF handling, and keyword expansion), and (4) text statistics counters in `convert.c` (theoretical overflow risk in CRLF/keyword decisions). The patches mechanically convert `size_t` values to `uintmax_t` or `size_t` to avoid narrowing to `unsigned long`, `long`, `unsigned`, or `int`, with no behavior change on 64-bit Linux.

Key technical details
Files touched: `odb.c`, `odb.h`, `odb/source-inmemory.c`, `odb/source-loose.c`, `odb/source.h`, `diff.c`, `convert.c`, `attr.c`, `read-cache-ll.h`, `read-cache.c`, `t/t1007-hash-object.sh` (12 files total).
New/renamed symbols: none (type conversions only).
Behavior change: none on 64-bit Linux; prevents data corruption (truncated blobs), crashes (word-diff buffer overflow), and incorrect metadata (binary detection, CRLF handling, keyword expansion) on Windows. The revised test (`t1007`) verifies object writes for files over 4 GiB using `git hash-object -w` and checks the object ID and its existence (`git cat-file -e`), avoiding redundant reads of 5 GiB files. The ODB write functions’ length parameter is now `size_t` (was `unsigned long`), matching Johannes Schindelin’s 2026 read-side ODB work (commit c6a4629e32) and eliminating the truncation path from `index_mem()`/`index_stream_convert_blob()` to `odb_write_object_ext()`. The word-diff buffer allocation in `diff.c` now uses `size_t` (was `unsigned long`/`long`), preventing overflow when buffers exceed ~700 MiB on Windows. The file conversion helpers in `convert.c`/`attr.c`/`read-cache.c` now use `size_t` (was `unsigned long`), preventing truncation when scanning files larger than 4 GiB for binary detection, CRLF line endings, or `$Id$` keywords. The patch also fixes a crash risk in `read_blob_data_from_index()` when `core.autocrlf` is enabled and the staged blob exceeds 4 GiB. The fourth patch converts counters in `struct text_stat` and `count_ident()` from `unsigned`/`int` to `size_t`, eliminating a theoretical overflow risk that could affect CRLF/keyword decisions. On-disk format: unchanged.
Test coverage: revised `t1007-hash-object.sh` test marked `EXPENSIVE` and `SIZE_T_IS_64BIT`, covering the 4 GiB+ truncation bug for object writes. The test now avoids redundant file I/O by dropping the size comparison and using `git cat-file -e` to verify object existence. The fourth patch adds no test, as triggering the overflow would require impractical input sizes (>4 GiB), but the fix is preemptive.

Thread identity
Subject: [PATCH 0/3] Fix 64-to-32 truncations on LLP64 platforms (Windows)
Series version: v2 (four-patch series; cover letter describes four patches)
Originating author: Elia Pinto
Thread type: patch series (bugfix, platform compatibility)

Core problem or goal
Git silently truncates or misbehaves with files larger than 4 GiB on Windows (LLP64 platforms where `long` is 32-bit). The series fixes four specific truncation or overflow sites: (1) object database writes (truncated blobs), (2) word-diff buffer allocation (crash due to overflow), (3) file conversion helpers (incorrect binary detection, CRLF handling, and keyword expansion), and (4) text statistics counters in `convert.c` (theoretical overflow risk in CRLF/keyword decisions). The patches mechanically convert `size_t` values to `uintmax_t` or `size_t` to avoid narrowing to `unsigned long`, `long`, `unsigned`, or `int`, with no behavior change on 64-bit Linux.

Current status
Under review; second iteration (`v2`) posted in response to Patrick Steinhardt’s review of `v1`. All feedback from `v1` has been addressed: (a) added an `EXPENSIVE` test for 4 GiB+ object writes, (b) preemptively fixed overflow risks in `convert.c` counters, (c) rebased on current `master`. The series now consists of four patches, with the fourth addressing a theoretical integer-overflow risk in `convert.c` flagged during review. Patrick Steinhardt’s latest reviews of `v2` (first and fourth patches) raise minor procedural issues: (1) test-script hygiene in the first patch (redundant file I/O and race-condition risk in size-file handling) and (2) commit-message phrasing in the fourth patch (overstatement of overflow risk and overly detailed references to `st_add()`/`st_mult()`). These are procedural, not technical, and do not affect the series’ readiness for integration. No objections to the core fix; series appears ready for a `v3` iteration to address the feedback.

Key technical details
Files touched: `odb.c`, `odb.h`, `odb/source-inmemory.c`, `odb/source-loose.c`, `odb/source.h`, `diff.c`, `convert.c`, `attr.c`, `read-cache-ll.h`, `read-cache.c`, `t/t1007-hash-object.sh` (12 files total).
New/renamed symbols: none (type conversions only).
Behavior change: none on 64-bit Linux; prevents data corruption (truncated blobs), crashes (word-diff buffer overflow), and incorrect metadata (binary detection, CRLF handling, keyword expansion) on Windows. The new test (`t1007`) verifies object writes for files over 4 GiB using `git hash-object -w` and checks both the object ID and its size. The ODB write functions’ length parameter is now `size_t` (was `unsigned long`), matching Johannes Schindelin’s 2026 read-side ODB work (commit c6a4629e32) and eliminating the truncation path from `index_mem()`/`index_stream_convert_blob()` to `odb_write_object_ext()`. The word-diff buffer allocation in `diff.c` now uses `size_t` (was `unsigned long`/`long`), preventing overflow when buffers exceed ~700 MiB on Windows. The file conversion helpers in `convert.c`/`attr.c` now use `size_t` (was `unsigned long`), preventing truncation when scanning files larger than 4 GiB for binary detection, CRLF line endings, or `$Id$` keywords. The fourth patch converts counters in `struct text_stat` and `count_ident()` from `unsigned`/`int` to `size_t`, eliminating a theoretical overflow risk that could affect CRLF/keyword decisions. On-disk format: unchanged.
Test coverage: added `t1007-hash-object.sh` test marked `EXPENSIVE` and `SIZE_T_IS_64BIT`, covering the 4 GiB+ truncation bug for object writes. Patrick Steinhardt’s review identifies two test-script hygiene issues in the first patch: (1) the test compares file content to object size (should compare content to content) and (2) the size file handling risks race conditions or confusion (should use a separate file for size). The fourth patch adds no test, as triggering the overflow would require impractical input sizes (>4 GiB), but the fix is preemptive.

Thread identity
Subject: [PATCH 0/3] Fix 64-to-32 truncations on LLP64 platforms (Windows)
Series version: v1 (first iteration)
Originating author: Elia Pinto
Thread type: patch series (bugfix, platform compatibility)

Core problem or goal
Git silently truncates or misbehaves with files larger than 4 GiB on Windows (LLP64 platforms where `long` is 32-bit). The series fixes three specific truncation sites: (1) object database writes (truncated blobs), (2) word-diff buffer allocation (crash due to overflow), and (3) file conversion helpers (incorrect binary detection, CRLF handling, and keyword expansion). The patches mechanically convert `size_t` values to `uintmax_t` or `size_t` to avoid narrowing to `unsigned long` or `long`, with no behavior change on 64-bit Linux.

Current status
Under review; no prior version exists. All three patches have received substantive review from Patrick Steinhardt. The series remains narrowly scoped to the three high-impact truncation sites identified via clang-tidy in a MinGW cross-compilation setup. Patrick’s latest review of the third patch surfaces a design question about secondary overflow risks in `convert.c` but does not request changes or block the series.

Key technical details
Files touched: `odb.c`, `odb.h`, `odb/source-inmemory.c`, `odb/source-loose.c`, `odb/source.h`, `diff.c`, `convert.c`, `attr.c`, `read-cache-ll.h`, `read-cache.c` (12 files total).
New/renamed symbols: none (type conversions only).
Behavior change: none on 64-bit Linux; prevents data corruption (truncated blobs), crashes (word-diff buffer overflow), and incorrect metadata (binary detection, CRLF handling, keyword expansion) on Windows.
On-disk format: unchanged.
Test coverage: none added; reproduction requires multi-gigabyte files and a 32-bit `long` environment. The commit messages explain that tests would require impractical conditions (e.g., 5 GiB files and 32-bit `long`). Patrick Steinhardt has questioned this justification on the first patch, noting that the existing test suite includes expensive tests (`EXPENSIVE`) and that a bug of this severity (data corruption on Windows) warrants test coverage.

Open questions and loose ends
1. Whether the series should include an `EXPENSIVE` test for the 4 GiB+ truncation bug. Patrick Steinhardt raised this in his review of the first patch, arguing that the severity of the bug justifies the effort despite the impracticality of the test conditions. This question remains unresolved and applies to the entire series.
2. Whether to extend the type conversions to secondary overflow risks in `convert.c` (e.g., `struct text_stat` counters and the `count_ident` function). Patrick Steinhardt’s review of the third patch flags these as theoretical edge cases but does not request changes. The question is whether the series should address these risks preemptively.

Participant positions
Patrick Steinhardt: Reviewed all three patches. Acknowledges the correctness of the type conversions and the seriousness of the bugs (data corruption on Windows when `git add` or `git hash-object -w` processes a file over 4 GiB that requires filtering; crashes when processing large files in word-diff). Raises two procedural/design concerns:
- On the first patch: omission of a test, noting that the existing test suite includes expensive tests and that a bug of this severity warrants one.
- On the third patch: theoretical overflow risks in `convert.c` (e.g., `struct text_stat` counters and `count_ident`), though he acknowledges these are unlikely to overflow in practice. No objection to the patches themselves; reviews are narrowly focused on correctness, test coverage, and forward-looking design questions. No other participants have reviewed the series.

Related work
Prior work by Johannes Schindelin (read-side ODB, commit c6a4629e32) and Jeff King (xdiff, commit 3c7a31204f) on 64-bit file handling. The author’s scan identified 237 Windows-specific truncations to `long`/`unsigned long`; this series fixes three of them. The second and third patches explicitly build on King’s and Schindelin’s work.

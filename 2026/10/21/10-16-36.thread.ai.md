Thread identity
Subject: [PATCH 0/3] Fix 64-to-32 truncations on LLP64 platforms (Windows)
Series version: v2 (second iteration)
Originating author: Elia Pinto
Thread type: patch series (bugfix, platform compatibility)

Core problem or goal
Git silently truncates or misbehaves with files larger than 4 GiB on Windows (LLP64 platforms where `long` is 32-bit). The series fixes four specific truncation or overflow sites: (1) object database writes (truncated blobs), (2) word-diff buffer allocation (crash due to overflow), (3) file conversion helpers (incorrect binary detection, CRLF handling, and keyword expansion), and (4) text statistics counters in `convert.c` (theoretical overflow risk in CRLF/keyword decisions). The patches mechanically convert `size_t` values to `uintmax_t` or `size_t` to avoid narrowing to `unsigned long`, `long`, `unsigned`, or `int`, with no behavior change on 64-bit Linux.

Current status
Under review; second iteration (`v2`) posted in response to Patrick Steinhardt’s review of `v1`. All feedback addressed: (a) added an `EXPENSIVE` test for 4 GiB+ object writes, (b) preemptively fixed overflow risks in `convert.c` counters, (c) rebased on current `master`. No new objections raised; series appears ready for integration.

Key technical details
Files touched: `odb.c`, `odb.h`, `odb/source-inmemory.c`, `odb/source-loose.c`, `odb/source.h`, `diff.c`, `convert.c`, `attr.c`, `read-cache-ll.h`, `read-cache.c`, `t/t1007-hash-object.sh` (12 files total).
New/renamed symbols: none (type conversions only).
Behavior change: none on 64-bit Linux; prevents data corruption (truncated blobs), crashes (word-diff buffer overflow), and incorrect metadata (binary detection, CRLF handling, keyword expansion) on Windows. The new test (`t1007`) verifies object writes for files over 4 GiB using `git hash-object -w` and checks both the object ID and its size.
On-disk format: unchanged.
Test coverage: added `t1007-hash-object.sh` test marked `EXPENSIVE` and `SIZE_T_IS_64BIT`, covering the 4 GiB+ truncation bug for object writes.

Open questions and loose ends
None. The two open questions from `v1` (test coverage and overflow risks in `convert.c`) have been resolved in this iteration.

Participant positions
Patrick Steinhardt: Reviewed `v1` of all three patches. Raised two procedural/design concerns:
- Omission of a test for the 4 GiB+ truncation bug, arguing that the severity of the bug (data corruption on Windows) warrants an `EXPENSIVE` test despite the impracticality of the test conditions.
- Theoretical overflow risks in `convert.c` (e.g., `struct text_stat` counters and `count_ident`), though he acknowledged these were unlikely to overflow in practice.
Both concerns have been addressed in `v2` (added test and preemptive fix for `convert.c` counters). No objections to the patches themselves; reviews were narrowly focused on correctness, test coverage, and forward-looking design questions. No other participants have reviewed the series.

Related work
Prior work by Johannes Schindelin (read-side ODB, commit c6a4629e32) and Jeff King (xdiff, commit 3c7a31204f) on 64-bit file handling. The author’s scan identified 237 Windows-specific truncations to `long`/`unsigned long`; this series fixes four of them. The second and third patches explicitly build on King’s and Schindelin’s work. The new test in `t1007` mirrors the existing `EXPENSIVE` test for hashing large files.

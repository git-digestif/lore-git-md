Thread identity
Subject: [PATCH] sequencer: refuse to revert/cherry-pick a shallow boundary commit by default
Series version: standalone patch (no prior versions)
Originating author: Nakul V S
Thread type: bugfix patch

Core problem or goal
Prevent `git revert` and `git cherry-pick` from accidentally deleting all tracked files when run on a shallow boundary commit (a commit that appears as a root commit due to `--depth=1` cloning and is recorded in `.git/shallow`). The patch adds a safeguard in the sequencer that checks for shallow boundary commits via `lookup_commit_graft()` returning a graft with `nr_parent < 0`. If detected, the operation is refused by default with a clear error message, directing users to either `--unshallow` or the new `--allow-shallow-boundary` flag.

Current status
Under review. No prior versions of this patch exist. The patch is narrowly scoped, well-motivated, and includes thorough test coverage and documentation. Junio C Hamano and Phillip Wood agree the safeguard should extend to `git rebase` and possibly `git commit --amend`. The discussion has shifted from *whether* to implement the safeguard to *how*: specifically, whether to check for shallow boundary commits mid-operation in `do_pick_commit()` or preemptively during todo-list construction via a shared helper function.

Key technical details
- Files touched: sequencer subsystem (`sequencer.c`), `builtin/revert.c`, and `Documentation/git-revert.adoc`.
- New CLI option: `--allow-shallow-boundary` (exposed in both `git revert` and `git cherry-pick`).
- New behavior: Default refusal to operate on shallow boundary commits, with an opt-in override.
- On-disk format: No changes.
- Test coverage: Verifies refusal in shallow repos, override with `--allow-shallow-boundary`, and confirms non-shallow repos remain unaffected.
- New symbols: None (the safeguard is implemented via existing `lookup_commit_graft()` and a new flag in the sequencer options).
- Proposed architectural change: A shared helper function to be called from `sequencer_make_script()`, `make_script_with_merges()`, `single_pick()`, and `sequencer_pick_revisions()` to catch shallow boundary commits at the planning stage rather than mid-operation.

Open questions and loose ends
1. **Implementation location**: Consensus that the check should live in a shared helper function rather than `do_pick_commit()`; exact placement and call sites remain to be finalized.
2. **Scope of safeguard**: Whether the check should extend to `git commit --amend` (Junio and Phillip Wood both support extending to `git rebase`; `git commit --amend` is still under discussion).
3. **Necessity of `--allow-shallow-boundary` flag**: Phillip Wood questioned its necessity; Junio’s feedback implies the flag may remain but its scope could expand to cover additional commands.
4. **Synopsis clarity**: Phillip Wood suggested omitting `--allow-shallow-boundary` from the command synopsis to keep usage messages concise.

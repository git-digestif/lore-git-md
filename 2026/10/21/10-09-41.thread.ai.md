Thread identity
Subject: [PATCH v2] sequencer: refuse to revert/cherry-pick a shallow boundary commit by default
Series version: v2 (standalone patch, previous version was v1)
Originating author: Nakul V S
Thread type: bugfix patch

Core problem or goal
Prevent `git revert`, `git cherry-pick`, and all `git rebase` backends (`merge`, `interactive`, `apply`) from accidentally deleting all tracked files when run on a shallow boundary commit (a commit that appears as a root commit due to `--depth=1` cloning and is recorded in `.git/shallow`). The patch adds a safeguard in the sequencer that checks for shallow boundary commits via `lookup_commit_graft()` returning a graft with `nr_parent < 0`. If detected, the operation is refused by default with a clear error message, directing users to either `--unshallow` or the new `--allow-shallow-boundary` flag (for `revert`/`cherry-pick` only; `rebase` always refuses without override).

Current status
Under review, now at v2. The patch addresses all prior feedback: it moves the check to the planning stage (todo-list construction) via a shared helper function, extends the safeguard to all rebase backends (including `--apply`, which bypasses the sequencer), and omits `--allow-shallow-boundary` from the synopsis for clarity. Junio C Hamano and Phillip Wood’s concerns about scope and implementation location are resolved. The manual-todo-list edge case (where a boundary commit’s hash is manually added to the todo list) is acknowledged but left unfixed as an acceptable trade-off. No merge decision yet; topic remains under review.

Key technical details
- Files touched: sequencer subsystem (`sequencer.c`, `sequencer.h`), `builtin/revert.c`, `builtin/rebase.c`, and `Documentation/git-revert.adoc`.
- New CLI option: `--allow-shallow-boundary` (exposed in `git revert` and `git cherry-pick` only; `git rebase` always refuses without override).
- New behavior: Default refusal to operate on shallow boundary commits, with an opt-in override for `revert`/`cherry-pick` and no override for `rebase`. The check is performed during todo-list construction (`sequencer_make_script()`, `make_script_with_merges()`) and at the entry points for single-pick operations (`single_pick()`, `sequencer_pick_revisions()`), ensuring no state is left behind if the command is refused. The `rebase --apply` backend, which bypasses the sequencer, receives a lightweight check before rewinding HEAD.
- On-disk format: No changes.
- Test coverage: Verifies refusal in shallow repos, override with `--allow-shallow-boundary`, autostash restoration, and edge cases like single-commit clones. Tests cover all rebase backends.
- New symbols: `sequencer_refuse_shallow_boundary()` (shared helper), `is_shallow_boundary_commit()` (shallow utility).
- Architectural change: The safeguard is now enforced at the planning stage, avoiding the `.git/sequencer` leftovers that occurred in v1.

Open questions and loose ends
1. **`git commit --amend`**: Whether the safeguard should extend to this command remains unresolved. Junio C Hamano and Phillip Wood both support extending the safeguard to `rebase`; `commit --amend` is still under discussion.
2. **Synopsis clarity**: `--allow-shallow-boundary` is omitted from the synopsis for `revert`/`cherry-pick` as suggested by Phillip Wood; no further feedback on this.
3. **Manual todo-list edge case**: The safeguard does not cover manually edited todo lists (e.g., adding a boundary commit’s hash). Nakul acknowledges this as an acceptable trade-off and does not propose to fix it in this iteration.

Thread identity
Subject: SHA-1/SHA-256 interoperability: relax unknown commit header handling
Series version: none (RFC discussion)
Originating author: Adam Majer <adamm@zombino.com>
Thread type: design discussion / bug report

Core problem or goal
The `convert_commit_object` function in Git’s SHA-256 interoperability layer currently aborts when it encounters unknown commit headers (e.g., `mergetag`, `predecessor`) whose referenced objects are missing. This blocks full-history conversion of repositories like the Linux kernel, where dozens of commits contain such headers pointing to transient or unreachable objects. The goal is to relax the requirement for strict 1:1 OID mapping of every referenced object, allowing unknown headers to be treated as opaque text and copied verbatim during conversion.

Current status
No prior decisions or merges; this is the thread root. The proposal is under initial discussion as an RFC.

Key technical details
- Function: `convert_commit_object`
- Headers at issue: `mergetag`, `predecessor`, and other unrecognized commit headers
- Files/subsystems: SHA-256 interoperability layer (no specific file named yet)
- Behavior change: unknown headers would be copied verbatim instead of triggering conversion failure
- On-disk impact: commit IDs would differ between SHA-1 and SHA-256 conversions of the same repository, but Git does not currently validate or preserve these references
- Test coverage: none yet; examples cited are real Linux commits (`ab5af2903baa`, `3a413ece2504`)

Open questions and loose ends
- Is the proposed trade-off (different commit IDs for SHA-1 vs. SHA-256 conversions) acceptable, given that Git does not enforce consistency for these headers today?
- Are there security or correctness implications of copying opaque headers verbatim?
- Should this relaxation be opt-in (e.g., via a command-line flag) or unconditional?
- How should the conversion tool report skipped or opaque headers to the user?

Participant positions
- Adam Majer (author): argues for the pragmatic approach, citing real-world conversion blockers and the lack of current validation for these headers.

Thread identity
Subject: SHA-1/SHA-256 interoperability: relax unknown commit header handling
Series version: none (RFC discussion)
Originating author: Adam Majer <adamm@zombino.com>
Thread type: design discussion / bug report

Core problem or goal
The `convert_commit_object` function in Git’s SHA-256 interoperability layer currently aborts when it encounters unknown commit headers (e.g., `mergetag`, `predecessor`) whose referenced objects are missing. This blocks full-history conversion of repositories like the Linux kernel, where dozens of commits contain such headers pointing to transient or unreachable objects. The goal is to relax the requirement for strict 1:1 OID mapping of every referenced object, allowing unknown headers to be treated as opaque text and copied verbatim during conversion, or alternatively, to drop them entirely to avoid propagating invalid data.

Current status
No prior decisions or merges; the proposal remains under initial discussion as an RFC. The thread has surfaced a key tension between two approaches: (1) relaxing conversion rules to unblock real-world use cases (Adam Majer’s position), and (2) enforcing stricter handling to avoid propagating invalid or misleading data (brian m. carlson’s position).

Key technical details
- Function: `convert_commit_object`
- Headers at issue: `mergetag`, `predecessor`, and other unrecognized commit headers
- Files/subsystems: SHA-256 interoperability layer (no specific file named yet)
- Behavior change proposals:
  - Copy unknown headers verbatim as opaque text (Adam’s proposal), or
  - Drop unknown headers entirely during conversion (brian’s counterproposal)
- On-disk impact: commit IDs would differ between SHA-1 and SHA-256 conversions if headers are preserved, but Git does not currently validate or enforce consistency for these headers
- Test coverage: none yet; examples cited are real Linux commits (`ab5af2903baa`, `3a413ece2504`)

Open questions and loose ends
- Is the trade-off between compatibility (preserving headers) and correctness (dropping them) acceptable, and which should be prioritized?
- Are there security or correctness implications of either approach (e.g., preserving invalid `mergetag` signatures or dropping them)?
- Should this relaxation be opt-in (e.g., via a command-line flag) or unconditional?
- How should the conversion tool report skipped or opaque headers to the user?
- Could this change affect other tools or workflows that rely on commit header consistency?

Participant positions
- Adam Majer (author): argues for the pragmatic approach of preserving unknown headers as opaque text, citing real-world conversion blockers (e.g., Linux kernel) and the lack of current validation for these headers.
- brian m. carlson: raises concerns about preserving opaque headers, which would result in different commit IDs depending on the source OID type. Proposes dropping such headers entirely to avoid propagating invalid data, framing the issue as a design flaw in the headers themselves rather than a limitation of the conversion tool. No explicit preference for opt-in vs. unconditional, but leans toward stricter handling for correctness.

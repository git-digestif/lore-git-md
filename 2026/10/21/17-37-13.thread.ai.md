Subject: SHA-1/SHA-256 interoperability: relax unknown commit header handling
Series version: none (RFC discussion)
Originating author: Adam Majer <adamm@zombino.com>
Thread type: design discussion / bug report

Core problem or goal
The `convert_commit_object` function in Git’s SHA-256 interoperability layer currently aborts when it encounters unknown commit headers (e.g., `mergetag`, `predecessor`) whose referenced objects are missing. This blocks full-history conversion of repositories like the Linux kernel, where dozens of commits contain such headers pointing to transient, unreachable, or external objects (e.g., from now-defunct submodules or external repositories). The goal is to relax the requirement for strict 1:1 OID mapping of every referenced object, allowing unknown headers to be treated as opaque text and copied verbatim during conversion, or alternatively, to drop them entirely to avoid propagating invalid data. The discussion now centers on whether Git should prioritize real-world usability (preserving headers deterministically) or stricter correctness (dropping them to avoid invalid or misleading data).

Current status
No prior decisions or merges; the proposal remains under active RFC discussion. The thread has crystallized into two opposing positions: (1) Adam Majer’s pragmatic approach of preserving unknown headers as opaque text to ensure deterministic conversion and unblock real-world repositories, and (2) brian m. carlson’s stricter approach of dropping such headers to avoid propagating invalid data. No consensus has emerged, and the discussion now includes broader questions about handling external references (e.g., submodules with unavailable upstreams) and whether the solution should be opt-in or unconditional.

Key technical details
- Function: `convert_commit_object` (SHA-256 interoperability layer)
- Headers at issue: `mergetag`, `predecessor`, and other unrecognized commit headers; real-world examples include Linux commits `ab5af2903baa` and `3a413ece2504`
- Files/subsystems: SHA-256 interoperability utilities (specific file not yet named)
- Behavior change proposals:
  - **Preserve unknown headers as opaque text** (Adam’s proposal): copy headers verbatim during conversion, ensuring deterministic commit IDs in the SHA-256 repository regardless of whether the original objects are available. This approach assumes that the headers can later be retrieved and interpreted correctly if the original repository’s hash function remains unchanged.
  - **Drop unknown headers entirely** (brian’s counterproposal): skip headers whose referenced objects are missing to avoid propagating invalid or misleading data, even if this results in nondeterministic conversion (e.g., depending on whether the converter can locate missing objects).
- On-disk impact: preserving headers would result in different commit IDs between SHA-1 and SHA-256 conversions, but Git does not currently validate or enforce consistency for these headers. Dropping headers would avoid this discrepancy but could lose historical context.
- External references: the discussion now includes handling of submodules with unavailable upstreams (e.g., the decade-old Node.js repository) and whether Git should attempt to skip them or accept that some histories may be "unconvertible" without manual intervention.
- Test coverage: none yet; real-world examples are cited but not yet formalized into tests.

Open questions and loose ends
- **Trade-off between compatibility and correctness**: Is the project willing to accept the risk of preserving potentially invalid data (e.g., `mergetag` signatures pointing to missing objects) to unblock real-world use cases, or should stricter handling be enforced to avoid propagating misleading or broken data?
- **Opt-in vs. unconditional**: Should the relaxed handling be opt-in (e.g., via a command-line flag like `--relax-unknown-headers`) or unconditional? Adam’s position leans toward unconditional for determinism, while brian’s concerns may favor opt-in to limit scope.
- **Reporting and user feedback**: How should the conversion tool report skipped or opaque headers to the user? Should it log warnings, provide a summary, or remain silent?
- **Security and correctness implications**: Are there risks in preserving opaque headers (e.g., invalid signatures, misleading metadata) or in dropping them (e.g., losing historical context, breaking tools that rely on header consistency)?
- **Impact on other tools/workflows**: Could this change affect downstream tools (e.g., Git hosting platforms, forges) or workflows that assume commit header consistency between SHA-1 and SHA-256 repositories?
- **Handling of external references**: Should Git attempt to resolve or skip submodules with unavailable upstreams, or is this beyond the scope of the conversion tool?
- **Loose-object-table lookups**: Could the conversion tool use loose-object-table lookups to resolve missing objects, or is this too resource-intensive for large repositories?

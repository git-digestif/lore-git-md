This is the first patch in a **bugfix and platform-compatibility series** targeting Windows (LLP64 platforms). It fixes a silent truncation issue in Git’s object database write path, where files larger than 4 GiB are corrupted when written due to `size_t` values being narrowed to 32-bit `unsigned long`. The patch mechanically converts the length parameter in `odb_write_object_ext()`, `odb_write_object()`, and related functions from `unsigned long` to `size_t`, aligning the write API with the read API (which was already widened in a prior commit by Johannes Schindelin).

The change touches five files in the `odb/` subsystem and is narrowly scoped to the write path. No new symbols are introduced, and there is no behavior change on 64-bit Linux. On Windows, this prevents data corruption when adding or hashing files over 4 GiB with conversions (e.g., `core.autocrlf`, `eol` attributes, or clean filters). The commit message provides a clear reproduction scenario: `git add` or `git hash-object -w` on a 5 GiB file with a conversion will silently write a truncated blob, while `git hash-object` (without `-w`) will compute the correct object ID, leading to a mismatch.

The patch is well-motivated and follows prior work in the same area. No new tests are added, as reproducing the issue requires a 32-bit `long` environment and multi-gigabyte files, but the existing test in `t1007` (which verifies correct hashing of large filtered files) now implicitly covers the write path on Windows. This is likely to be uncontroversial, as it addresses a clear correctness issue without introducing new complexity.

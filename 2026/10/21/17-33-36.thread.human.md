This thread is an RFC proposing `--merged` and `--no-merged` filters for `git worktree list`, allowing developers to quickly identify which worktrees correspond to topics already merged upstream. The feature is implemented by Jasper Mayone, reusing existing `ref_filter` machinery for consistency, and is ready for review with no prior versions or maintainer feedback yet.

The patch is self-contained, touching only `builtin/worktree.c` and adding tests in `t/t2402-worktree-list.sh`. It introduces two new CLI options (`--merged[=<commit>]` and `--no-merged[=<commit>]`) with `HEAD` as the default commit, matching `git branch --merged`. The implementation strictly checks reachability of each worktree’s HEAD without altering on-disk format or enabling automatic removal. Tests cover edge cases like unborn branches and broken worktrees.

Five open questions remain, including whether the main worktree should be filtered by default, if `HEAD` is the right default commit, and whether a future `git worktree remove --merged` would be useful. The broader design question of allowing multiple worktrees to check out the same branch was authoritatively dismissed by Junio C Hamano, citing shared repository state risks. Harald Nordgren initially raised this but withdrew after Junio’s explanation, while Kristoffer Haugsbakk’s recent reply is purely rhetorical and adds no technical substance. The feature itself appears uncontroversial, but these loose ends may shape its final form.

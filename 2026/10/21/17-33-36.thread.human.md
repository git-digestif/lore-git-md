This thread proposes and implements a `--branch=<branch>` filter for `git worktree list`, replacing an earlier `--merged`/`--no-merged` design. The feature lets developers quickly identify worktrees tied to specific branches, with the current implementation supporting multiple branch names (short or full refs) and handling edge cases like rebases and bisects. Junio Hamano’s feedback shaped the shift to a more general filter primitive, while Eric Sunshine had suggested a `for-each`-style mechanism as an alternative—this remains unaddressed but acknowledged.

The patch is now under active review, with Phillip Wood highlighting code duplication, usability concerns, and validation questions. His follow-up proposes refactoring `branch.c` to expose a reusable helper and standardizing on short branch names via `--format='--branch=%(refname:lstrip=2)'` to simplify composability with commands like `git branch --merged`. Eric Sunshine’s latest review steps back to question the `--branch` option name itself, arguing that a generic `--filter=branch:<name>` syntax would better align with Git’s existing conventions and leave room for future extensions (e.g., filtering by locked status or path). While he doesn’t block the patch, his feedback frames a broader design debate: whether the current approach is sufficiently future-proof.

The implementation touches `builtin/worktree.c`, adds tests, and avoids on-disk changes, but several open questions linger, including whether the main worktree should be filtered by default and how to handle squash-merged topics. No integration branch has been assigned yet, and the thread remains focused on refining the design rather than finalizing the code.

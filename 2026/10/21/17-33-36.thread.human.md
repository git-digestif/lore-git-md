This thread is about adding branch filtering to `git worktree list`, shifting from an earlier `--merged`/`--no-merged` proposal to a more general `--branch=<branch>` filter. The current implementation by Jasper Mayone lets users list worktrees associated with specific branches, designed to work with existing branch-filtering commands like `git branch --merged`.

The patch is now under substantive review by Phillip Wood, who raises three key points. First, he identifies code duplication in the branch-checking logic and suggests refactoring `branch.c` to expose a reusable helper, which would improve consistency between `git branch` and `git worktree list`. Second, he notes a usability gap: the filtered output no longer marks the main worktree, which could cause scripts to fail when trying to remove it. He proposes adding an `is-main-worktree` annotation to the porcelain output. Finally, he questions the validation logic, which rejects invalid branch names but accepts non-existent ones, though he doesn’t push for a change here.

The thread remains open, with no new objections to the carried-over questions (e.g., whether the main worktree should be filtered out by default, or how to handle squash-merged topics). Eric Sunshine’s earlier `for-each`-style alternative is still acknowledged but unaddressed. The patch itself is not yet assigned to an integration branch, and no merge decisions have been made.

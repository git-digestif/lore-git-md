This thread is about adding filtering capabilities to `git worktree list` to help developers identify worktrees tied to specific branches. The original proposal for a `--branch=<branch>` option has been abandoned in favor of extending `git for-each-ref`'s `%(worktreepath)` atom to report worktree paths even during rebase or bisect operations, aligning its behavior with `git worktree add` and `git branch -d`. This pivot simplifies the design but introduces new concerns about safety, composability, and whether `for-each-ref` is the right tool for the job.

The discussion has revealed significant design tensions. Eric Sunshine highlighted that filtering worktrees—whether via `for-each-ref` or another mechanism—breaks the invariant that the main worktree appears first in output, which could break scripts relying on this ordering. Phillip Wood identified three key limitations of `for-each-ref`: it lacks NUL-terminated output (complicating parsing of paths with newlines), cannot distinguish the main worktree from linked ones (risking accidental deletion of the main repository), and cannot handle branches checked out in multiple worktrees. Ben Knoble raised a critical safety concern: whether filtering by branch state (e.g., `--merged=origin`) should include worktrees mid-rebase, and whether `git worktree remove` should allow their deletion, risking data loss. Phillip Wood endorsed this concern, framing it as a pre-existing bug in `git worktree remove` that the proposed change would exacerbate.

The thread is now focused on three interrelated questions: whether `for-each-ref --merged` should exclude rebasing worktrees by default, whether `git worktree remove` should fail for mid-rebase worktrees unless forced, and whether `for-each-ref` is suitable for this task given its limitations. No consensus has emerged on how to address these issues, and the design remains in flux. The current implementation is not yet queued for integration, and the discussion is still open.

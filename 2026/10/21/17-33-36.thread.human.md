This thread began as a proposal to add `--merged`/`--no-merged` filtering to `git worktree list`, but has since pivoted to a narrower change: extending `git for-each-ref`'s `%(worktreepath)` atom to report worktree paths even during rebase or bisect, closing a gap where such worktrees appeared detached. Jasper Mayone now frames this as a bug fix, but the discussion has revealed deeper design tensions.

Eric Sunshine and Phillip Wood have both raised concerns about using `for-each-ref` as a filtering mechanism. Sunshine notes that filtering worktrees breaks the invariant that the main worktree appears first in output, which scripts may rely on. Wood identifies three key limitations: `for-each-ref` lacks NUL-terminated output (complicating parsing of paths with newlines), cannot distinguish the main worktree from linked ones (risking accidental deletion), and cannot handle branches checked out in multiple worktrees. Ben Knoble’s recent review adds another concern: filtering by branch state (e.g., `--merged=origin`) might include mid-rebase worktrees, creating a risk that `git worktree remove` could delete them, potentially losing uncommitted work.

The pivot to `%(worktreepath)` avoids introducing new CLI options but leaves unresolved questions about usability and safety. The current proposal does not address how to mark the main worktree in filtered output, how to handle branches checked out in multiple worktrees, or whether rebasing worktrees should appear in `--merged` output. While the behavior change itself is widely seen as a bug fix, the broader design—using `for-each-ref` as a filtering tool—may not be sufficient for real-world workflows. Alternatives like a `git worktree foreach` mechanism (suggested by Sunshine) remain on the table but are not yet being actively pursued. The thread is now focused on whether the proposed change is safe and sufficient, or if further adjustments are needed before it can be merged.

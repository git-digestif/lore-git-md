This thread is about adding filtering capabilities to `git worktree list` to help developers identify worktrees tied to specific branches. The original proposal for a `--branch=<branch>` option has been abandoned in favor of a narrower change: extending `git for-each-ref`'s `%(worktreepath)` atom to report worktree paths even during rebase or bisect operations. This aligns `for-each-ref` with how `git worktree add` and `git branch -d` already handle such branches, eliminating the "detached" appearance of rebasing/bisecting worktrees.

Jasper Mayone, the author, frames this as a bug fix but acknowledges backward-compatibility concerns—scripts may rely on `%(worktreepath)` being empty for rebasing/bisecting branches. The pivot avoids introducing new CLI options and instead leverages `for-each-ref`'s composability (e.g., `git for-each-ref --merged=HEAD --format='%(worktreepath)'`), but it doesn’t address several lingering questions. Phillip Wood’s earlier concerns about main-worktree annotation and validation remain unanswered, and Eric Sunshine recently highlighted a critical usability issue: filtering worktrees (whether via `--branch` or `for-each-ref`) breaks the invariant that the main worktree appears first in `git worktree list` output, which could mislead scripts attempting to delete worktrees. This tension—whether to preserve ordering, annotate the main worktree, or accept the breakage—remains unresolved.

The discussion is now focused on the `ref-filter.c` implementation, with open questions about backward compatibility, main-worktree handling, and whether future features like `git worktree remove --merged` would be desirable. No patches have been merged yet, and the series is still in the design phase.

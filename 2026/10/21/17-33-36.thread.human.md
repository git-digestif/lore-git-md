This thread is about adding filtering capabilities to `git worktree list` to help developers identify worktrees tied to specific branches. The original proposal for a `--branch=<branch>` option has been abandoned in favor of a narrower change: extending `git for-each-ref`'s `%(worktreepath)` atom to report worktree paths even during rebase or bisect operations, which currently appear as "detached." This aligns `for-each-ref` with how `git worktree add` and `git branch -d` already handle such branches, and it avoids introducing new CLI options.

The discussion has revealed significant design tensions. Eric Sunshine pointed out that filtering worktrees—whether via `for-each-ref` or another mechanism—breaks the invariant that the main worktree always appears first in output, which could break scripts relying on this ordering. Phillip Wood’s latest review highlights additional limitations of using `for-each-ref` for filtering: it lacks NUL-terminated output (making it hard to parse paths with newlines), cannot distinguish the main worktree from linked ones, and doesn’t handle branches checked out in multiple worktrees. Despite these drawbacks, Phillip endorses the `%(worktreepath)` change as a bug fix, though he notes that marking the main worktree in output is only necessary if the list is filtered.

The thread is still unresolved. Key open questions include how to handle the broken ordering invariant, whether to annotate the main worktree in output, and whether a future `git worktree foreach` mechanism might better address these gaps. Jasper Mayone has not yet responded to these concerns, and no integration branch has been assigned. The pivot to `%(worktreepath)` simplifies the design but leaves critical usability and backward-compatibility issues unaddressed.

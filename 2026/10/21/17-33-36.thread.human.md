This thread proposes adding `--merged` and `--no-merged` filters to `git worktree list`, letting developers quickly see which worktrees track branches that have already landed upstream. The feature is implemented in a single patch that touches only `builtin/worktree.c` and adds thorough tests; it reuses Git’s existing `ref_filter` machinery for consistency. Jasper Mayone, the author, has raised a few open questions—whether to exclude the main worktree by default, whether `HEAD` is the right default commit, and whether the worktree command should have its own parsing—but the patch itself is technically complete and unlikely to spark controversy.

Junio C Hamano has already closed the only broader design discussion that arose: Harald Nordgren had suggested relaxing Git’s rule that prevents two worktrees from checking out the same branch, but Junio explained the technical risks (shared repository state causing unexpected HEAD movement) and pointed to `git worktree add -d` as the existing workaround. Harald has since acknowledged the explanation and withdrawn his suggestion, leaving the thread focused solely on the `--merged`/`--no-merged` feature. No maintainer feedback on the feature itself has arrived yet, and the patch remains under review.

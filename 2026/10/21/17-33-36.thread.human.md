Here’s the human-mode summary for a developer catching up:

This thread proposes a four-patch series to add filtering capabilities to `git worktree list` by extending the `%(worktreepath)` atom in `git for-each-ref`. The series also addresses two safety issues: preventing `git worktree remove` from deleting worktrees mid-operation (rebase, bisect, cherry-pick, revert, or `git am`) without `--force`, and fixing `%(worktreepath)` to report worktree paths for branches being rebased or bisected—aligning it with how `git worktree add` and `git branch -d` already treat those branches.

The series is now at **v4** (a procedural relabeling of v3) and is ready for review, though patches 1 and 2 are blocked on a documentation clarification. Patch 1 adds the safety check for `git worktree remove`, patch 2 adds a warning to `git-for-each-ref(1)` about parsing `%(worktreepath)` safely (including a claim that only one worktree is shown per branch), patch 3 extends `%(worktreepath)` to cover rebasing/bisecting branches, and patch 4 removes a redundant `+` marker in `git branch` output. The implementation avoids new CLI options by leveraging `%(worktreepath)`, but this introduces limitations: `for-each-ref` lacks NUL-terminated output, can’t distinguish main/linked worktrees, and risks surfacing mid-rebase worktrees in filtered output.

The main open question was whether a branch can be checked out in multiple worktrees, which would invalidate the documentation’s claim. Phillip Wood confirmed that while Git’s porcelain discourages this (due to race risks), it’s technically possible via `--force` or plumbing commands like `git symbolic-ref`. The documentation can proceed as written, but a follow-up might clarify how such worktrees can be created. Other unresolved concerns include whether the main worktree should be filtered out by default, how to handle the broken ordering invariant (main worktree no longer appears first in filtered output), and whether a future `git worktree remove --merged` would be useful. The series is backward-incompatible for scripts relying on the old `%(worktreepath)` behavior, the `+` marker, or the ability to delete in-progress worktrees without `--force`.

This thread proposes adding `--merged` and `--no-merged` filters to `git worktree list` to help developers identify worktrees tied to already-merged topics. The initial implementation by Jasper Mayone was complete, self-contained, and ready for review, but Junio C Hamano has now suggested a fundamental redesign.

Junio argues the current approach is too narrow, proposing instead a more general `--branch` filter primitive that would accept multiple branch names. This would allow users to filter worktrees by branch directly, then pipe the output to existing commands like `git branch --contains` to achieve merged/unmerged filtering without adding new code. His feedback questions whether the specific use case justifies its own options when a more flexible foundation could serve broader needs.

The thread remains in RFC stage with no integration branch assignment. Key open questions now include whether to adopt Junio’s `--branch` proposal or proceed with the original `--merged`/`--no-merged` design. The discussion has shifted from implementation details to fundamental design, with no other participants having weighed in on this new direction yet. The original open questions about default behavior and parsing remain unresolved.

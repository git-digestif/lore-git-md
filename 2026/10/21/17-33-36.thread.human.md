This thread is a feature proposal from Jasper Mayone to add `--merged` and `--no-merged` filters to `git worktree list`, mirroring the behavior of `git branch`. The goal is to help developers identify which worktrees correspond to topic branches that have already landed upstream, making it easier to clean up stale worktrees.

The implementation reuses Git’s existing `ref_filter` machinery for consistency and touches only `builtin/worktree.c` with accompanying tests. The patch is minimal and well-scoped, but Jasper raises four open questions for discussion: whether the main worktree should be excluded by default, whether `HEAD` is the right default commit for filtering, whether reusing `ref_filter` is the right approach, and whether a future `git worktree remove --merged` command would be useful. The proposal does not attempt to handle squash-merged or rebase-merged topics, leaving that for potential follow-up work.

So far, the thread is just the initial RFC—no reviews or responses have arrived yet. The design looks uncontroversial, but the default behavior (listing the main worktree) might draw debate. If you use worktrees regularly, this could be a small but practical improvement to your workflow.

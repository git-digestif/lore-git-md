This thread is about a two-patch series by Jasper Mayone that improves how Git handles worktrees during rebases, bisects, and other in-progress operations. The first patch, already merged, makes `git worktree remove` refuse to delete a worktree in the middle of a rebase, bisect, or similar operation unless `--force` is given—this prevents accidental data loss. The second patch, just posted, extends the `%(worktreepath)` atom in `git for-each-ref` to report the worktree path for branches being rebased or bisected, closing a gap where scripts couldn’t reliably find these worktrees.

The series replaces an earlier proposal for `--merged`/`--no-merged` filtering in `git worktree list` with a more targeted fix that avoids new CLI options. While this approach aligns behavior across Git commands and addresses a real usability issue, reviewers like Eric Sunshine and Phillip Wood have raised concerns about whether `for-each-ref` is the right tool for the job. Key limitations include its inability to distinguish the main worktree from linked ones, handle branches checked out in multiple worktrees, or produce NUL-terminated output for safe parsing. There’s also a risk that filtering could break scripts that assume the main worktree appears first in output.

The discussion now centers on whether these limitations are acceptable trade-offs or if a more robust mechanism (like a `git worktree foreach` command) is needed. The series itself is well-tested and ready for review, but the broader questions about safety and composability remain open. If you’re scripting around worktrees, this change will make it easier to track rebasing branches, but you’ll need to account for the new behavior in `%(worktreepath)` and the stricter `git worktree remove` protections.

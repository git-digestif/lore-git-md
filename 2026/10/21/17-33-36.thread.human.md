This thread is about adding filtering capabilities to `git worktree list` to help developers identify worktrees associated with specific branches. The original proposal for `--merged`/`--no-merged` filters evolved into a more general `--branch=<branch>` option, which Jasper Mayone implemented in RFC v2. This option allows filtering worktrees by the branch they have checked out, including during rebase or bisect operations, and is designed to compose with existing branch-filtering commands like `git branch --merged`.

The current implementation is under review, with key feedback focusing on design choices rather than blocking issues. Junio C Hamano initially suggested `--branch` as a more flexible alternative to `--merged`, and this has been addressed. Eric Sunshine proposed a `for-each`-style mechanism or a generic `--filter` option for future extensibility, while Phillip Wood raised concerns about code duplication, usability, and validation, suggesting refactoring and output improvements. Kristoffer Haugsbakk noted that `git for-each-ref --format='%(worktreepath)'` provides similar functionality but lacks support for rebasing/bisecting worktrees, which `--branch` handles explicitly.

The latest email from Junio explores an even more ambitious design: a `--filter-command` option that would accept a shell script snippet to determine which worktrees to include. This would enable arbitrary filtering logic, such as listing worktrees with more than five unpushed commits, but Junio acknowledges the open-endedness of this idea. While this proposal doesn’t address the current patch’s implementation details, it shifts the design discussion toward how far to generalize the filtering mechanism. Open questions remain about validation, main worktree handling, and whether `--branch` or a more generic `--filter` is the right path forward. The thread is still in the design phase, with no integration branch assigned yet.

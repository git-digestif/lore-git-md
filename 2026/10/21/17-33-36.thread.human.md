This thread is an RFC proposing `--merged` and `--no-merged` filters for `git worktree list`, allowing developers to quickly identify which worktrees correspond to topics already merged upstream. The feature is implemented by Jasper Mayone, touching only `builtin/worktree.c` and adding tests in `t/t2402-worktree-list.sh`. The patch reuses existing `ref_filter` machinery for consistency and is ready for review, with no maintainer feedback yet.

The proposal raises several open questions—such as whether the main worktree should be filtered by default, whether `HEAD` is the right default commit, and whether the feature should pave the way for a future `git worktree remove --merged`—but these are unlikely to be controversial. A tangential discussion arose when Harald Nordgren questioned Git’s restriction preventing a branch from being checked out in multiple worktrees. Junio C Hamano firmly dismissed this idea, explaining that shared repository state would lead to confusion if two worktrees could modify the same branch independently. He pointed to `git worktree add --detach` as the existing workaround, effectively closing the broader design debate.

The original feature proposal remains open for review, with no objections raised so far. The implementation is self-contained and aligns with Git’s existing CLI conventions, suggesting it could proceed smoothly once feedback arrives.

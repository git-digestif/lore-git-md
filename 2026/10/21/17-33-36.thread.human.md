This thread is about adding filtering to `git worktree list` to help developers find worktrees tied to specific branches. Jasper Mayone initially proposed `--merged` and `--no-merged` options but shifted to a more general `--branch=<branch>` filter after Junio Hamano suggested it would be more flexible. The current patch implements `--branch` and is designed to work with existing branch-filtering commands like `git branch --merged`, though some design questions remain open.

The implementation is straightforward: `--branch` filters worktrees by the branch they have checked out, including during rebase or bisect, and excludes detached worktrees. Phillip Wood reviewed the patch and raised several points—code duplication, usability concerns, and whether the main worktree should be filtered out by default—while also suggesting improvements like exposing a helper from `branch.c` and adding an `is-main-worktree` annotation to the output. Eric Sunshine has proposed two alternatives: a `for-each`-style mechanism and a more generic `--filter` option, but neither has been adopted yet. Kristoffer Haugsbakk noted that `git for-each-ref` can already do something similar, though it doesn’t handle rebasing worktrees as cleanly.

The patch is still under discussion, with no merge in sight. The main open questions are whether `--branch` is the right long-term design or if a more extensible `--filter` mechanism would be better, and whether the output should include more metadata to help scripts avoid mistakes. For now, the `--branch` implementation is a practical step forward, but the thread is still exploring how to make it more robust and future-proof.

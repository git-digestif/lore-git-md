This is a **bugfix patch follow-up** in the ongoing thread to fix a performance regression in shallow fetches when backfilling tags. Karthik Nayak replies to Justin Tobler’s substantive review of v3, clarifying the design choices behind the two-transaction approach.

The exchange focuses on two key points from Justin’s review: why the code logs an error from the first transaction but continues to the second, and why it carries forward with post-fetch operations (like setting upstreams) even if the initial transaction failed to initialize. Karthik explains that batched updates are inherently partial—some refs may succeed while others fail—so the code tolerates errors to avoid losing progress. Similarly, even if the backfill transaction fails to start, the fetch still needs to update upstream tracking info and `FETCH_HEAD` to leave the repository in a usable state.

The discussion remains pragmatic: Karthik acknowledges the limitations (no fix for `--atomic` fetches) and defers to Patrick Steinhardt’s parallel proposal to expose pending transaction state to negotiation, which could eliminate the need for the intermediate commit. For now, the two-transaction approach is presented as a necessary trade-off—restoring performance without breaking existing workflows—while the longer-term design is still under debate. The patch is well-motivated and addresses a real regression, but its readiness for `next` hinges on resolving either Justin’s error-path questions or Patrick’s alternative proposal.

This is the second iteration of Patrick Steinhardt’s seven-patch series introducing the **object storage extension**, a foundational step toward pluggable object database backends in Git. The series defines the `extensions.objectStorage` configuration mechanism (modeled after the existing ref storage extension) and implements the baseline `files` backend, which now supports relocating the `.git/objects` directory via a payload (e.g., `files://objs` moves objects to `.git/objs`).

The v2 update addresses two key issues raised in the initial review: it ensures the `repo->object_storage_format` field is always populated (eliminating the awkward exposure of the hard-coded default in inspection tools), and it refines the handling of the `files` backend’s payload. The series remains built on the merged prerequisites `ps/odb-files-alternates` and `ps/setup-enforce-repo-passed-to-create-repository-has-no-state`, with no unresolved conflicts.

The implementation touches core subsystems (`odb/`, `setup.c`, `repository.c`) and adds new user-facing features: command-line options (`--object-storage-format=` for `git clone`, `git init`, and `git submodule`), environment variables (`GIT_OBJECT_STORAGE_FORMAT` and `GIT_DEFAULT_OBJECT_STORAGE_FORMAT`), and inspection tools (`git rev-parse --show-object-storage-format` and `git repo objects.storageFormat`). Documentation is updated across `git-{clone,init,submodule}.adoc` and new files like `object-storage-format.adoc`. Tests cover initialization, cloning, submodule propagation, and edge cases (e.g., local clone restrictions when using non-default storage formats).

The series is well-motivated and follows established patterns for extensibility, making it a strong candidate for eventual inclusion. The v2 changes address the most significant design concerns from the initial review, and the remaining open questions (e.g., path normalization in the `files` backend, the local clone restriction) are pragmatic limitations rather than fundamental flaws. The implementation appears thorough, with careful attention to backward compatibility and submodule handling. If the series continues to receive positive feedback, it is likely to be queued for `next` in the near future.

This is a three-patch bugfix series targeting the branch and checkout subsystems. The series addresses two related issues: a misleading hint message in `git switch` and `git branch --set-upstream-to` (carried over from v1), and a behavioral inconsistency where `git switch -c` and `git checkout -b` stop halfway through the operation if the tracking config cannot be written due to a locked config file.

The first patch (previously seen in v1) strips the `refs/heads/` prefix from the hint message, so users see the correct short name (e.g., `origin/feat` instead of `origin/refs/heads/feat`). The test for this patch has been strengthened as requested: it now validates the entire multiline hint message for formatting and wording regressions, and verifies that the suggested command actually works once the lock is removed.

The second patch refactors `setup_tracking()` to return an error instead of calling `exit()`, paving the way for the third patch. The third patch makes `git switch` and `git checkout` finish the switch and exit with status 0 when the tracking config cannot be written, aligning their behavior with `git push -u`, `git clone`, and `git fetch`. `git branch` continues to fail in this scenario, preserving its existing behavior.

The series is well-motivated and clearly explained. The commit messages document the problem, the regression origin (commit a3f40ec4b0, 2021-12-20), and the rationale for the behavioral change. The test coverage is thorough, with new tests in `t/t2027-checkout-track.sh` and `t/t2060-switch.sh` to verify the new behavior. The changes are narrowly scoped and do not attempt to make the switch fully atomic (which is left for a future topic).

This looks like a sensible, low-risk fix for a real usability issue. The series is self-contained, touches only a few files, and includes regression tests. It should be uncontroversial and ready for review.

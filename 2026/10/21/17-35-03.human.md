This is a user report and review of Harald Nordgren’s v3 patch series that extends `git branch --delete-merged` to detect squash-merged and rebase-merged branches. Jasper Mayone tested the series on generated repositories and confirms the implementation works as described: without `--squashed`, it deletes branches whose exact file versions appear upstream (handling rebases and simple squash merges), while `--squashed` also catches cases where upstream modified the same files. The output format (`landed as <commit>`) consistently names the correct upstream commit, and the series handles edge cases like squashes that were later reverted or partially landed.

Jasper’s main concern is the false positive he reported in v2: a branch whose changes were independently implemented by another author is still deleted by the "cheap check" (tree-based diffing), even without `--squashed`. This aligns with Junio’s earlier warning about "irrelevant" branches—those whose changes are upstream but whose commits and messages are not—and reinforces the argument that the looser, change-based detection should not be the default for `--delete-merged`. Jasper proposes a CLI redesign: move all looser detection behind a single opt-in option like `--landed=<kind>` (e.g., `--landed=files` for tree-based diffing, `--landed=merge` for squash detection), with a config variable to set the default. This would preserve `--delete-merged`’s current strict meaning while allowing users to opt into looser behavior once per repository.

The report also notes a minor usability issue: branches checked out in worktrees are silently skipped, while those with `deleteMerged=false` print a "Skipping" message. Jasper suggests a clearer message (`"Skipping 'topic' (checked out in <path>)"`) and proposes refactoring the "has this branch landed?" logic into a reusable helper for future commands like `git worktree list --merged`. The series is otherwise feature-complete, with no unresolved technical questions, but the CLI design debate remains open. Jasper’s proposal offers a middle ground between Harald’s unified `--delete-merged` approach and Junio’s `--delete-irrelevant` split.

This is a discussion email about SHA-1/SHA-256 repository interoperability, specifically targeting the `convert_commit_object` function and its handling of commit headers like `mergetag`, `predecessor`, and other unknown fields.

Adam Majer reports practical difficulties when attempting to convert repositories (like the Linux kernel) from SHA-1 to SHA-256 OID types. The core issue is that `convert_commit_object` currently bails on unknown commit headers, and some commits in the Linux history contain references (e.g., `predecessor` headers) to objects that are no longer available. This creates a blocker for full history conversion, as the function enforces strict 1:1 OID mapping for all referenced objects, even when those objects are not critical to the repository's integrity.

The email proposes a more flexible approach: treating unknown headers (like `mergetag` or `predecessor`) as opaque text and copying them verbatim during conversion, rather than attempting to rewrite their OIDs. This would result in different commit IDs depending on the source OID type, but Adam argues this is acceptable since Git does not currently preserve or validate these references anyway. The suggestion is framed as a pragmatic trade-off to enable interoperability without requiring perfect object availability.

Key technical details include the specific commit examples (`ab5af2903baa` and `3a413ece2504`) with `predecessor` headers, the mention of "dozens" of unfetchable `mergetag` references in the Linux tree, and the observation that recent commits also cause issues due to Git's transient object retention.

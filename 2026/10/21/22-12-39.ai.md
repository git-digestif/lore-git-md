This is a maintainer reply in the `git worktree list --merged` RFC thread, addressing the broader design question raised by Harald Nordgren.

Junio C Hamano responds directly to Harald’s suggestion that Git should relax or allow relaxing the rule preventing a branch from being checked out in more than one worktree. Junio explains the technical rationale: worktrees share the same repository state, so allowing two worktrees to check out the same branch would lead to confusion when one worktree makes a commit on that branch — the other worktree’s HEAD would suddenly point to a different commit without any explicit user action. This behavior would violate the principle that each worktree’s HEAD should reflect only the changes made within that worktree.

Junio also briefly dismisses the relevance of AI-assisted workflows to this design decision, noting that the question has already been settled in the past. He points to `git worktree add -d` (the `--detach` option) as the existing mechanism for creating a worktree without checking out a branch, which sidesteps the restriction while still allowing work on the same commit.

The reply is concise and authoritative, effectively closing the broader design discussion for now. It does not engage with the original `--merged`/`--no-merged` feature proposal itself, which remains open for review. The key takeaway for future discussion is that the one-branch-per-worktree rule is intentional and unlikely to change.

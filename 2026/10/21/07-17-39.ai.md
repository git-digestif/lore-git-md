This is the second patch in the v3 series introducing ephemeral branch reaping for `git worktree`. The feature automatically deletes branches created by `git worktree add` when no branch is specified (the DWIM auto-naming case), addressing a long-standing cleanup nuisance where auto-created branches outlive their worktrees and clutter `refs/heads/`.

The patch records ownership of auto-created branches in the worktree's administrative directory (`worktrees/<id>/owned-branch`) at creation time, ensuring the branch is reaped when the worktree is removed. Only branches created by DWIM auto-naming are marked as ephemeral; explicitly named branches (`-b/-B`) or pre-existing branches are never owned and thus never reaped. The deletion is unconditional, even for unmerged commits, as ephemeral branches are disposable by design—users can preserve commits by anchoring them with an ordinary branch or using `--keep-branch` during removal. Branch renames update the ownership marker, so the branch remains ephemeral after renaming.

The implementation adds a new `--keep-branch` option to `git worktree remove` and updates `git branch -m` to propagate ownership markers during renames. Test coverage in `t2400-worktree-add.sh` verifies the feature's behavior, including edge cases like branch renames and commit preservation. Documentation updates clarify the ephemeral branch concept and its limitations.

This patch remains **actively contested** by Eric Sunshine, who argues the feature is redundant given the existing `--detach` flag and risks disrupting workflows that rely on auto-created branches. The design choice to unconditionally reap ephemeral branches (rather than making it opt-in) continues to be a point of contention. The patch does not address these objections in this revision, leaving the debate unresolved.

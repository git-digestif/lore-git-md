This is the second patch in Harald Nordgren’s v3 series extending `git branch --delete-merged` to detect rebase-merged branches. It implements the core rebase-detection logic: when a branch’s changes (but not its tip) appear in an upstream commit, the branch is considered merged and can be deleted.

The patch adds a fast, tree-based diffing algorithm that checks whether every file changed by the branch matches the version in some upstream commit since the fork point. This handles the common “rebase and merge” workflow (e.g., GitHub’s “Rebase and merge” button) without reading file contents, so it remains cheap even in partial clones. The output format is extended to show where the work landed: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`.

Internally, the patch introduces a `landing_search` structure to track each branch’s changes, a `changed_paths` commit slab to cache diff results, and helper functions (`collect_branch_changes`, `find_landed_commit`) that batch the work across all candidate branches. The main entry point, `find_landed_commits`, is called once per upstream pattern and populates a `strmap` that `delete_branches` consults to decide which branches to delete.

Test coverage is thorough: the new `t/t3200-branch.sh` tests cover rebase merges, squash merges (even when later reverted), and mixed scenarios where one branch is merged and another is not. The patch is uncontroversial on its own; the ongoing discussion is about whether rebase detection belongs under `--delete-merged` or should be moved to a separate `--delete-irrelevant` option.

This is the **fourth patch in the six-part incremental connectivity check series**, adding the `transfer.connectivityCheck` configuration plumbing. It introduces the config key and wires it up to the internal `rev-list` subprocess that performs connectivity verification, preparing for the incremental mode implementation in patch 5/6.

The patch adds a new `transfer.connectivityCheck` config option (default: `full`) that selects the connectivity-check algorithm. For now, only `full` is accepted, matching the existing behavior; unknown values fall back to `full` with a warning to ensure forward compatibility. The config is read in `connected.c` and passed to `rev-list` via a new `--connectivity-check=<mode>` flag, which is documented as internal-only in `Documentation/rev-list-options.adoc`. The `rev-list` command parses the flag and stores the mode in a new `struct connectivity_check` field, though it does not yet act on it (that happens in patch 5/6).

This is a **mechanical plumbing patch** with no behavior change: it only adds the config key, documents it, and ensures the mode is passed to `rev-list`. The design follows Patrick Steinhardt’s suggestion to make the mode explicit, allowing future optimizations to be scoped to connectivity checks. The fallback-to-full behavior for unknown values ensures that configuration written for newer Git versions won’t break fetches or pushes on older versions.

The patch is **well-structured and uncontroversial**, addressing all prior feedback about config design and forward compatibility. It builds on the refactoring in patch 3/6 (which removed `the_repository` dependency in `connected.c`) and is a prerequisite for the incremental mode implementation in patch 5/6. The commit message clearly explains the motivation and scope, and the code is cleanly split from the actual implementation. No new issues are introduced, and the patch is ready for integration.

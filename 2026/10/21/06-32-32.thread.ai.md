Thread identity: SHA-1/SHA-256 interoperability – pack index v3 support. Series version: v1 (13 patches). Originating authors: Christian Couder and brian m. carson. Thread type: patch series.

Core problem or goal: Extend Git’s pack index format to store object IDs in both the primary and compatibility hash algorithms, enabling packed objects to be mapped between algorithms just as loose objects already can. This is a critical component of the SHA-256 interoperability effort, allowing repositories to operate with both hash algorithms simultaneously. The series also refactors the loose object mapping infrastructure to support future ODB abstraction work.

Current status: Under review. This is the first iteration of the series, posted as [PATCH 0/13]. No prior versions of this specific series exist, though it builds on brian m. carson’s earlier interoperability work (notably the loose object mapping infrastructure). - **On-disk format changes**: Introduces pack index v3, which stores object IDs in both the primary and compatibility hash algorithms. The format is documented in `gitformat-pack(5)` (patch 13).
- **Behavior changes**:
  - Pack index v3 is written by `index-pack` and `pack-objects` when the repository is in compatibility mode (deferred to later patches).
  - Pack index v3 reading is implemented in `packfile.c`, allowing lookup of compatibility object IDs in packs (deferred to later patches).
  - Validation in patch 10 ensures pack index v3 tables are well-formed (header lengths, trailer offsets, table positions, reverse index bounds).
  - Patch 1 refactors `repo_loose_object_map_oid()` to delegate lookup logic to a new helper, `source_loose_object_map_oid()`, enabling reuse of the mapping infrastructure in other contexts (e.g., ODB abstraction).
  - Patch 3 extends `source_add_loose_object_map()` with a `flags` parameter to control whether newly mapped object IDs are written to disk immediately. The `OBJ_MAP_WRITE` flag guards the write operation, preserving existing behavior for now while enabling future in-memory-only mapping storage.
  - Patch 4 introduces ODB-level functions (`odb_map_oid` and `odb_write_oid_map`) for mapping object IDs between hash algorithms and persisting those mappings. The "files" backend implements these functions by delegating to its "loose" and "packed" sources, checking all object directories (main and alternates) for mappings and reloading loose object maps if needed. The "loose" source implements both mapping and writing, while the "packed" source currently stubs out these functions (returning -1) pending pack index v3 support in later patches.
- **Test coverage**: Extensive, covering pack index v3 writing, reading, abbreviated object ID lookup, duplicate detection, bounds checking, and loose object mapping refactoring. Patch 4 does not introduce new tests but relies on existing coverage in `t1016` and other test scripts.

Open questions and loose ends:
- **Missing test support**: The test suite cannot yet run with `GIT_TEST_DEFAULT_HASH=sha256:sha1` due to missing support for parsing `<algo>:<compat>` in `GIT_DEFAULT_HASH`.
- **Automatic selection**: Pack index v3 is not yet automatically selected in compatibility repositories; this is noted as a limitation.
- **Dependency mapping**: `index-pack` cannot compute compatibility object IDs for objects whose dependencies lack mappings. This is addressed in brian’s full `sha256-interop` branch but remains a limitation here.
- **Abbreviated compatibility object IDs**: Only work with certain commands and do not yet work with multi-pack indices.
- **Packed source stubs**: The "packed" ODB source does not yet implement `odb_source_map_oid` or `odb_source_write_oid_map`, as pack index v3 support is deferred to later patches.

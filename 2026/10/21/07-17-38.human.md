This is the first patch in a four-part feature series introducing copy-on-write (CoW) worktree creation via the new `--reflink` option for `git worktree add`. The patch implements the core reflink functionality, adding a cross-platform `reflink_file()` helper in `copy.[ch]` and wiring it into the worktree creation process in `builtin/worktree.c`.

The feature allows users to create new worktrees by reflinking files from an existing worktree rather than writing every file out from the object store. This avoids full checkout overhead when creating many worktrees from the same base, as only files that differ between the source and target commit are rewritten. The implementation supports Linux (FICLONE ioctl), macOS (clonefile()), and Windows (FSCTL_DUPLICATE_EXTENTS_TO_FILE), though Windows ReFS support is permanently disabled in this version due to a known silent corruption bug (Git LFS #6312). Filesystem capability is probed up front by attempting to clone a one-byte test file, and the feature degrades gracefully to a regular checkout when reflinks are unavailable.

The patch includes careful handling of edge cases: uncommitted changes in the source worktree do not leak into the new one (achieved by copying the source index and running `update-index --refresh` before `reset --hard`), and untracked files are carried over as a deliberate tradeoff. The behavior can be controlled via the `worktree.reflink` configuration (values: `true`, `false`, or `auto`) or per-invocation with `--reflink`/`--no-reflink`. The implementation is incompatible with `--orphan` and `--no-checkout` modes, and the patch includes documentation updates with examples and detailed limitations (e.g., overlayfs incompatibility, Windows ReFS corruption risk).

The patch is well-crafted, with thorough test coverage in `t2400-worktree-add.sh` and clear documentation. However, the reflink design remains contested: Eric Sunshine argues the opt-in nature (via flag or config) is unjustified for tracked files, where the untracked-file copying concern does not apply. This patch does not address that objection, leaving the broader design debate unresolved. The Windows disablement resolves the immediate technical blocker but does not settle the question of whether reflink should be automatic when available.

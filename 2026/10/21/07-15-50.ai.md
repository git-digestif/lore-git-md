This is a **platform-compatibility follow-up** in the ongoing `git worktree --reflink` feature thread. The author, Jason Newton, responds to brian m. carlson’s **substantive review** of the cross-platform reflink implementation with detailed evidence and a planned revision.

Jason confirms that the macOS reflink path is **already tested in CI** and works correctly. The test suite uses `cp -c` (macOS’s clonefile(2) flag) rather than `cp --reflink=always`, and all four macOS CI jobs (clang, gcc, meson, reftable) passed on macOS 14.8.9 runners. This addresses the reviewer’s concern about CI testability on APFS.

On Windows, Jason acknowledges the **silent corruption risk** in ReFS block cloning (Git LFS #6312) and has already **disabled reflink on Windows** in the next revision. The patch now compiles the filesystem probe but disables the ioctl, ensuring mingw builds do not fail due to unused functions. The author provides empirical evidence from Windows build 26300.9457 showing that `FSCTL_DUPLICATE_EXTENTS_TO_FILE` preserves data integrity in their testing, but notes that the Git LFS bug report documents zero-fill corruption on earlier builds. Since no fixed Windows version is available, the patch will **permanently disable reflink on Windows**, falling back to regular checkouts. A warning is emitted for `--reflink` or `worktree.reflink=true`, while `worktree.reflink=auto` remains silent.

The response is narrowly focused on **platform-specific correctness** and does not engage with the broader design debate (e.g., whether reflink should be opt-in or default for tracked files). The author’s tone is technical and evidence-driven, providing CI logs, test results, and detailed reproduction steps to address the reviewer’s concerns. This sets the stage for a v3 revision that will disable Windows reflink entirely while keeping the macOS and Linux paths intact. The ephemeral branch reaping feature (patch 2/2) remains unaffected by this discussion.

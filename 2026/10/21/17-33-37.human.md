This is a well-crafted feature patch adding `--merged` and `--no-merged` filters to `git worktree list`. The patch directly addresses a practical pain point for developers who maintain one worktree per topic branch: quickly identifying which worktrees correspond to topics that have already landed upstream. By reusing the existing `ref_filter` machinery from `ref-filter.h`, the implementation ensures consistent parsing, error messages, and behavior with commands like `git branch --merged`.

The patch is minimal and focused, touching only `builtin/worktree.c` and adding thorough tests in `t/t2402-worktree-list.sh`. It preserves both the human-readable and `--porcelain` output formats, making the filtered results usable in scripts. The default commit for the filter is HEAD, consistent with other ref-filter commands, and the patch explicitly handles edge cases like bare worktrees, unborn branches, and broken HEADs by omitting them from the filtered output.

The author raises four reasonable design questions for discussion: whether the main worktree should be filtered out by default, whether HEAD is the right default commit, whether reusing `ref_filter` is acceptable, and whether a future `git worktree remove --merged` would be desirable. These are all worth considering, but none appear to be showstoppers. The patch also defers handling of squash-merged or rebase-merged topics, which is a pragmatic choice given the complexity of those cases.

The implementation looks clean and uncontroversial, with good test coverage and clear documentation. The only likely point of debate is whether the main worktree should be included by default, but the current behavior (including it) is consistent with how `git worktree list` operates today. This is a useful addition that fills a clear gap in the worktree workflow.

Originating author: Emily Shaffer
Thread type: governance proposal (process documentation)

Core problem or goal
Define a structured voting process for the Git project to resolve contentious decisions when traditional consensus-based discussion fails. The immediate motivation is the unresolved AI contributions debate, but the patch is process-only: it specifies *how* to vote, not *what* policy to adopt. The proposal adds a new `Documentation/CommunityVoting.adoc` file, updates `Documentation/DecisionMaking.adoc` to reference it, and wires the new document into the build system.

Current status
Under review; no prior versions. Junio C Hamano (maintainer) has suggested the final document title be "define the voting process" (rather than "propose a voting process") to reflect its authoritative role once merged. The patch is self-contained and does not depend on external work. Junio’s feedback advances the proposal by clarifying versioning (using Git OIDs to identify proposal texts), vote-counting mechanics (single-option vs. proportional outcomes), and eligibility criteria (raising the bar to two or more topics in a released version of Git).

Open questions and loose ends
- **Voting mechanism**: Still unspecified in the document (flagged as TBD); Junio’s feedback surfaces the need to clarify whether outcomes are determined by plurality (single-option) or proportional support (multi-option).
- **Eligibility criteria**: Junio proposes a stricter standard (two or more topics in a released version of Git) to exclude drive-by contributors; this may require further community discussion.
- **Versioning**: Junio suggests using Git OIDs to uniquely identify proposal texts, but implementation details (e.g., how voters reference these OIDs) remain unresolved.
- **Adoption of formal voting**: The central open question—whether the project should adopt any formal voting process at all—remains unanswered.
- Emily plans to self-review the patch to flag these open questions explicitly.

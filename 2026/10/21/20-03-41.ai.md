This is a **documentation proposal** introducing a formal voting process for the Git project. Emily Shaffer submits a new `Documentation/CommunityVoting.adoc` file outlining a structured three-phase process (proposal collection, voting window, implementation) for resolving contentious decisions when community consensus fails. The patch also updates `DecisionMaking.adoc` to reference the new voting process and adds the file to the build system.

The motivation is explicitly tied to the ongoing debate about AI contributions, which the Git community has struggled to resolve through traditional consensus-based discussion. Emily frames this as a *process* patch, not a policy one: it defines *how* to vote, not *what* the AI policy should be. She suggests adopting the same approval mechanism used for the 2019 Code of Conduct (general consensus + `Acked-by:` trailers) for this process document itself.

Key details of the proposed process:
- Voting is a last resort, initiated by the Git PLC or maintainer.
- Eligibility: contributors with at least one commit merged to `next` or two code reviews, excluding banned participants. Contributions must predate the vote kickoff to prevent "dogpiling."
- Proposals must be seconded by another eligible voter to appear on the ballot.
- Phases: 4 weeks for proposal refinement, 2 weeks for voting, immediate implementation of the winning proposal.
- The voting mechanism itself is left TBD in the document.

The patch is clearly written and well-motivated, with explicit open questions flagged for follow-up (e.g., the voting mechanism). It directly addresses a real governance gap that has surfaced in recent high-profile discussions. The proposal is likely to be controversial not on its own merits, but because it formalizes a departure from Git's long-standing consensus-driven culture. Expect debate about whether voting is the right tool for the project, not just about the specifics of the process.

This is Junio C Hamano’s review of **patch 5/6** in the six-patch series introducing `transfer.connectivityCheck=incremental`, the core implementation of the incremental connectivity-check algorithm. The series is a well-motivated performance feature that reduces the cost of verifying object connectivity during fetches and pushes by processing only incoming commits and their changed subtrees, rather than the entire repository.

Junio’s review is **substantive** and **tested**—he clearly read the code closely, built it, and thought through edge cases. His main concern is a **forward-compatibility trap** in the config-parsing logic: the patch unconditionally disables `repo->fetch_if_missing` for any mode other than `full`, which assumes that all future modes will also want to avoid lazy fetching. While true today (only `full` and `incremental` exist), this could silently break future modes that *do* want lazy fetching, such as a hypothetical `partial` mode that skips some objects but still fetches missing ones on demand. The fix is simple—make the `fetch_if_missing` behavior mode-specific—but it’s a classic maintainability pitfall that could bite later.

He also raises a **clarity question** about the blob-verification helper: whether `odb_read_object_info()` should explicitly avoid promisor objects via a flag (e.g., `READ_OBJECT_INFO_SKIP_PROMISOR`) rather than relying on the global `repo->fetch_if_missing` setting. This is a minor point—functionally equivalent today—but it would make the intent clearer and more robust against future changes to the ODB layer. The rest of his comments are **affirmative**: he confirms that the incremental mode is only invoked when explicitly requested, that the caller correctly disables `fetch_if_missing` before calling the core verification logic, and that the fallback logic for unbounded histories (e.g., clones) is sound.

The patch itself is **well-isolated** (a single new file, `tree-verify.c`, with minimal touch points in `rev-list.c` and `connected.c`) and **thoroughly tested** (774 lines of new tests covering correctness, corruption detection, and performance). The incremental algorithm is **inductively sound**: it trusts parent trees and verifies only the differences in child trees, using memoization to skip already-verified objects. The **stack overflow risk** from recursive tree verification is acknowledged but not addressed in this series; it’s flagged as a potential follow-up.

This review doesn’t block the series—Junio’s tone is constructive, not critical—but it does highlight a **design wart** that should be fixed before merging. The fix is straightforward (add a mode-specific flag for `fetch_if_missing`), and the rest of the implementation looks solid. The series as a whole is **ready for integration** once this is addressed, and the feature is a meaningful performance win for large repositories.

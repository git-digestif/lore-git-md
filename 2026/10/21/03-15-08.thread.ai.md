Subject: `git merge` fails in partial clone when merge generates new blob not present on remote
Series version: N/A (bug report, not a patch series)
Originating author: Andrew Parmet <andrew@parmet.com>
Thread type: bug report

Core problem or goal
A `git merge` operation in a partial clone (`--filter=blob:none`) fails when the merge generates a new blob (e.g., a conflict resolution or merge commit message) that does not exist on the promisor remote. The merge attempts to fetch this locally created blob from the remote, which returns `fatal: remote error: upload-pack: not our ref <object-id>`. The same merge succeeds when retried or when run without the blob filter, indicating the issue is specific to partial-clone fetch logic.

Current status
Reported; no prior discussion or patch. The bug is reproducible via a self-contained shell script provided in the email. No maintainer response or integration status yet.

Key technical details
- **Subsystems affected**: partial-clone, promisor-remote, merge machinery
- **Trigger**: `git merge` in a partial clone where the merge generates a new blob (e.g., conflict resolution or commit message)
- **Failure mode**: `fatal: remote error: upload-pack: not our ref <object-id>` during fetch
- **Reproduction**: The provided script sets up a minimal server/client pair, creates diverging commits, and triggers the bug during merge. The failing blob is generated *during* the merge, not present in either parent commit.
- **Workaround**: Retry the merge or avoid `--filter=blob:none`
- **Files touched by reproduction**: None (the bug is in runtime behavior, not a specific file)
- **Test coverage**: The reproduction script logs packet traces to `$root/packets.log` for debugging

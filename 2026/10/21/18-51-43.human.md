This is a **CLI design and user-experience discussion** in the ongoing thread about extending `git branch --delete-merged` to detect squash-merged and rebase-merged branches. The exchange between Harald Nordgren (the series author) and Jasper Mayone (a user/reviewer) centers on whether the feature’s looser detection logic should be opt-in by default and how to balance safety with usability.

Harald pushes back against Jasper’s proposal to gate the entire "looser check" (including the current default rebase detection) behind an opt-in flag like `--landed=<kind>`. He argues that such configurability adds unnecessary mental overhead for a command whose purpose is straightforward: deleting branches whose changes are already upstream. His stance reflects a **pragmatic, workflow-first approach**—users should not need to configure multiple levels of detection when the default (tree-based diffing for rebase merges) is already safe and performant. He dismisses the false-positive case Jasper raised (a branch deleted because another author independently implemented the same change) as an "extremely rare edge case" that does not justify complicating the interface, noting that the branch’s changes are still recoverable from upstream.

Jasper, however, **reinforces Junio’s safety concerns** by emphasizing that the false positive persists even without `--squashed`, and that the current default conflates two distinct user intents: strict tip-reachability (safe, conservative) and change-based detection (riskier, ambiguous). His `--landed=<kind>` proposal aims to preserve `--delete-merged`’s conservative meaning while allowing users to opt into looser detection via config (e.g., `--landed=files` for tree-based diffing, `--landed=merge` for three-way merge detection). This would address the false-positive issue without requiring per-invocation flags, aligning with workflows like GitHub’s "Squash and merge." Jasper also flags a **usability nit**: branches checked out in worktrees are silently skipped, unlike branches with `deleteMerged=false`, and links to an RFC for `git worktree list --merged` that would reuse the "has this branch landed?" logic.

The exchange highlights a **fundamental tension** between Harald’s desire for simplicity and Jasper’s (and Junio’s) emphasis on safety and clarity. Harald’s dismissal of the false positive as rare may underestimate how often such cases occur in collaborative environments (e.g., teams working on similar features), while Jasper’s proposal risks over-engineering a command that many users treat as a routine maintenance tool. The unresolved question is whether the project will prioritize **workflow efficiency** (Harald’s stance) or **predictability and explicit opt-in** (Jasper’s and Junio’s stance). The discussion also underscores the need for clearer messaging around edge cases, as seen in Jasper’s worktree feedback.

This is the **v4 iteration of a six-patch performance feature** that introduces an **incremental connectivity check** for Git fetches and pushes. The series is now split into logical steps: documentation, baseline performance tests, a preparatory refactoring to drop `the_repository` dependency, the config plumbing, the core incremental implementation, and finally the "auto" mode with a configurable cutoff.

The incremental check is an **opt-in optimization** (`transfer.connectivityCheck=incremental` or `auto`) that reduces the cost of verifying object connectivity during fetches and pushes. Instead of walking the entire reachable object closure (which scales poorly with repository size), it processes incoming commits in topological order, tracking trusted objects from parent commits to skip unchanged subtrees. This shifts the cost from being proportional to repository size to being proportional to the size of the incoming changes.

Key improvements in v4 include:
- A **three-mode config design** (`full`/`incremental`/`auto[=<n>]`) with a **configurable 1,000-commit cutoff** (via `transfer.connectivityCheckIncrementalMaxCommits` or `auto[=<n>]`), allowing safe rollout and future default changes without breaking workflows.
- **No new `die()` calls in library code**, centralizing error handling at the subprocess boundary to align with Git’s libification goals.
- **Better error messages** distinguishing missing objects from unreadable ones (e.g., corrupt blobs).
- **Type safety improvements**: using `size_t` for counters (`trees_loaded`, `blobs_checked`).
- **Explanatory comments** around merge-walk logic and trust boundaries.
- **Test coverage** for edge cases like missing promisor parent commits, shallow boundaries, and corrupt blobs.

The **performance trade-offs** are well-documented: incremental mode is up to **190x faster** for small pushes to large repositories (14 MB vs. 3.4 GB memory), but can be **~30% slower** for small repositories (e.g., `git.git`) or long incoming histories (10,000+ commits). The "auto" mode dynamically switches at the configured threshold (default: 1,000 commits), balancing performance and safety. Deepening fetches and pushes into empty repositories fall back to the full check, as the incremental approach would not provide benefits in these cases.

The series is **well-motivated and thoroughly tested**, with extensive correctness tests in `t5413-connectivity-check.sh` (795 lines) and performance benchmarks in `t/perf/p5413-connectivity-check.sh` (92 lines). The implementation is **self-contained**, touching only the necessary subsystems (`tree-verify.c`, `connected.c`, `builtin/rev-list.c`) and adding clear documentation (`Documentation/technical/connectivity-check.adoc`).

### Open questions

- **Stack overflow risk**: Patrick Steinhardt raised concerns about recursive tree verification for very deep trees (up to 2048 layers). The author acknowledges this as a potential follow-up but notes similar recursion exists elsewhere in Git.
- **Subprocess architecture**: Whether `die()` is appropriate for server-side operations (e.g., `git-receive-pack`) remains a long-term consideration.

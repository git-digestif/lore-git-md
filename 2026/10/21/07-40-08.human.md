This is a reply in the ongoing discussion about Jason Newton’s worktree ephemeral branch reaping feature, part of his four-patch series introducing copy-on-write worktree creation and automatic branch cleanup. Jason pushes back against Eric Sunshine’s **substantive objection** that the feature is redundant given the existing `--detach` flag, arguing that the two serve fundamentally different workflows.

Jason clarifies that `--detach` leaves the worktree in a branchless state, which breaks common operations like `git status`, `git push`, and `git branch --set-upstream-to` that expect a branch name. An ephemeral branch, by contrast, behaves like a normal `refs/heads/` ref for the life of the worktree, allowing commits to be made and referenced by other branches before the worktree is removed. He emphasizes that the feature is opt-in at the *workflow* level: users who want a branch to persist after worktree removal can already use `-b` or `--detach`, while those who don’t must now opt out with `--keep-branch`. The "unconditional" deletion in the commit message refers only to the owned branch (the one auto-created by DWIM), not to any branch the user explicitly named or checked out.

The reply also addresses upgrade safety: worktrees created by older Git versions lack the ownership marker, so removing them leaves their branches intact. The feature is thus backward-compatible and won’t disrupt existing setups. Jason’s core argument is that ephemeral branches reduce friction for the common case of throwaway worktrees without requiring extra flags, while `--detach` remains available for users who prefer a branchless state. Whether this distinction justifies the added complexity remains the central point of contention.

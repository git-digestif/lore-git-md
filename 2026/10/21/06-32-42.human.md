This is a **security and robustness patch** targeting the pack index v3 implementation, part of the ongoing SHA-1/SHA-256 interoperability effort. It adds thorough validation to prevent out-of-bounds reads when loading a corrupt or maliciously crafted pack index v3 file.

The patch plugs a gap left by earlier commits in the series: while pack index v3 reading was implemented, it lacked bounds checking for header fields, table offsets, and order map entries. Without these checks, a malformed index could cause Git to read memory outside the mapped file, potentially leaking sensitive data or crashing. The changes are defensive and cover all critical structures in the v3 format: header length, format entries, table positions, and reverse index offsets.

Key additions include:
- Validating that the header length and trailer offset match the file size.
- Rejecting duplicate format entries or short name lengths exceeding the full object ID size.
- Checking that table offsets lie within the file and are 32-bit aligned.
- Ensuring order map entries point to valid object positions.
- Adding a new test in `t5313-pack-bounds-checks.sh` that verifies detection of an invalid order map entry.

The patch is small (78 lines added across four files) but dense with safety checks. It complements the earlier v3 reading implementation and is clearly motivated by security best practices. The test coverage is appropriate, targeting the new validation logic without duplicating existing tests.

This is a well-crafted, necessary follow-up to the v3 index work. The changes are narrowly scoped to validation and do not alter behavior for well-formed indices. The commit message clearly explains the risks being addressed. For anyone following the interoperability effort, this patch is worth attention—it closes a potential security hole in a new on-disk format.

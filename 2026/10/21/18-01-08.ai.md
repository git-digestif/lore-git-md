This is a documentation patch series, now in its second iteration, that converts Git’s plain-text `BreakingChanges` document into a proper manpage (`gitbreaking-changes(7)`). The goal is to make upcoming breaking changes more discoverable to users via `git help` and `man`. The v2 series is technically complete, addresses all prior reviewer feedback, and is ready for integration, but a new question from Junio C Hamano about the document’s post-Git-3.0 lifecycle remains unresolved.

In this reply, Kristoffer Haugsbakk proposes a concrete solution to Junio’s concern: instead of rewriting every entry after Git 3.0 ships, the document could add a new section summarizing what changed in 3.0, introduced with a note explaining that the rest of the document is written in the future tense for users reading from version 2.98. This approach preserves the existing text while clarifying its temporal context, avoiding the need for a large-scale rewrite. The proposal is pragmatic and directly addresses the maintainer’s question, which has been the sole remaining blocker for integration.

The series touches `Documentation/gitbreaking-changes.adoc`, `Documentation/BreakingChanges.adoc`, `Documentation/git.txt`, `command-list.txt`, `Makefile`, and `meson.build`, but introduces no new symbols, CLI options, or on-disk format changes. It conflicts only with two in-flight topics (`ps/ref-storage-format` and `bc/restrict-hex-to-lowercase`), requiring their additions to be moved from the old file to the new one during integration. All other feedback—on URL formatting, structural improvements, and the living-draft admonition—has been incorporated.

Kristoffer’s reply signals that the series is now unblocked from the author’s side. The next step is Junio’s decision on whether the proposed lifecycle solution is acceptable or if further documentation changes are needed before integration. No further technical work appears required from the author.

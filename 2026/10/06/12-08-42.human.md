This is a **performance feature** patch reply in the incremental connectivity check series. Patrick Steinhardt and Kristofer Karlsson clarify a key technical point: how the incremental verifier establishes its trust boundary between already-connected and incoming commits.

The discussion resolves Patrick’s initial confusion about "parents" and trust boundaries. The incremental mode still relies on `git rev-list --not --all` to mark preexisting ref tips as uninteresting, just like the full connectivity check. This query implicitly identifies the boundary between old and new commits; the verifier then processes incoming commits in reverse topological order, inductively trusting each commit’s parents (either preexisting or already-verified incoming commits). The inductive approach ensures correctness without parsing all refs upfront, though ref-parsing overhead remains a separate scalability challenge.

Patrick also raises a concern about `die()` usage in the subprocess, but Kristofer explains that the subprocess architecture ensures clean error propagation to the parent process (e.g., `git-receive-pack`), matching the existing `rev-list`-based implementation. The discussion leaves open the long-term question of whether a single-process implementation with non-fatal error handling would be preferable, but this is acknowledged as out of scope for the current series.

This is the rerolled (v2) version of a two-patch performance optimization for the `fetch.writeCommitGraph` feature, targeting the commit-graph subsystem. The series is now complete and addresses all feedback from the v1 review.

The core idea remains unchanged: instead of rebuilding the commit-graph from all reachable refs after every fetch, Git now writes incrementally from only the updated refs when possible. The three-mode enum (`REACHABLE`, `TIPS`, `SKIP`) makes the policy explicit: skip the write entirely for no-op fetches, write incrementally from updated tips when an existing graph exists, and fall back to a full reachable scan when no graph exists or when fetching from multiple remotes. The incremental path relies on split mode, which adds the newly fetched history as a new layer on top of the existing chain rather than replacing it.

The reroll incorporates all requested improvements. The commit message now explains the split-mode reliance and includes synthetic benchmark numbers (357ms → 9.3ms for a single ref update, no-op fetches skipped entirely). A new comment in the code clarifies why shallow-rejected refs are skipped, and test coverage has been extended to verify no coverage loss after incremental writes and correct handling of shallow refs. The test helper `test-tool read-graph commit-info` (added in patch 1) is used to verify graph contents in the new tests.

The implementation looks solid: the fallback to full scans in edge cases (no existing graph or multi-remote fetches) preserves correctness, and the incremental path is carefully guarded by the split-mode assumption. The performance gains are substantial and well-documented, making this a clear win for large repositories. The series is ready for final review and appears uncontroversial.

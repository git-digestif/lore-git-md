This is the third installment in Taylor Blau’s Git Contributor’s Summit 2026 notes series, covering the **Documentation** discussion. The email captures a wide-ranging conversation about Git’s documentation gaps, funding constraints, tooling limitations, and potential improvements.

The core problem is clear: Git’s documentation is fragmented and inaccessible to beginners. Julia Evans highlights the disconnect between contributor-level knowledge (objects, index, upstream) and user-level understanding, and notes that existing resources like `gitglossary` and *Pro Git* are either outdated or too dense for newcomers. The group agrees that Git needs better beginner-focused documentation, but funding is limited (100 hours split between two people). Suggestions include tapping the Git fund or seeking corporate sponsorship (OpenAI, GitHub, GitButler were mentioned), but no concrete commitments emerge.

On tooling, the discussion reveals frustration with the current AsciiDoc/Asciidoctor duality. Peff and Patrick propose moving entirely to Asciidoctor, citing its better maintenance and portability, while brian m. carlson notes Fedora’s continued reliance on AsciiDoc. Junio suggests this could be a breaking change for Git 3.0, but no decision is reached. Other tooling ideas include Mermaid for diagrams (to replace ASCII art) and subsection linking in manpages, though these are framed as incremental projects rather than immediate priorities.

The conversation also touches on **content structure** and **discoverability**. Josh Steadmon introduces the Diataxis framework (tutorials, guides, explanations, reference) as a potential model, and the group agrees that Git’s current separation of guides and manpages is useful but poorly surfaced. Julia notes that the Git website lacks a clear entry point for learning Git, and Peff mentions that past efforts to improve this have stagnated. There’s interest in linking to external resources (videos, Discord threads), but concerns about maintenance and cost (e.g., video production) temper enthusiasm.

**Metrics** emerge as a recurring theme: the group wants to know which documentation is most read, but privacy concerns and technical limitations (e.g., Heroku caching, AI scrapers) complicate data collection. Taylor Blau mentions Cloudflare metrics, and Mark Waite suggests Fathom as a privacy-friendly alternative, but no actionable plan is formed.

The tone is collaborative but pragmatic. Participants acknowledge the importance of documentation but are realistic about resource constraints. The discussion is **not a patch or proposal**—it’s a brainstorming session with no immediate technical deliverables. Key loose ends include:
- Funding: Will the Git fund or corporate sponsors step up?
- Tooling: Can the project standardize on Asciidoctor, and how?
- Structure: How to implement Diataxis or improve discoverability?
- Metrics: How to measure documentation usage without compromising privacy?

This email is **worth following** for anyone interested in Git’s documentation or user experience, but it’s not actionable yet. Future threads may propose specific changes (e.g., Asciidoctor migration, new beginner guides) or funding requests. For now, it’s a snapshot of the project’s documentation pain points and a call for volunteers or sponsors to help address them.

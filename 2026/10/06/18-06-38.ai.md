This is the final installment in Taylor Blau’s seven-part series summarizing the Git Contributor’s Summit 2026. It covers the discussion on **Protocol v2 for pushes**, a long-standing gap in Git’s wire protocol that has become increasingly urgent as repositories grow larger (especially with AI-driven branch proliferation) and as SHA-256 interoperability becomes a reality.

The core problem is straightforward: today’s `git push` still uses the v0 protocol, which requires the server to advertise *every* ref in the repository before the client can send anything. For repositories with millions of refs (a threshold some customers have already crossed), this advertisement can balloon to hundreds of megabytes, making pushes slow and expensive. Reftable has helped by reducing the size of the ref database, but the protocol itself remains a bottleneck. The infrastructure for Protocol v2 already exists—it is used for fetches—but the push side has never been wired up.

The discussion surfaced two distinct use cases that would benefit from a v2 push protocol:

1. **Large repositories with many refs** (brian m. carlson’s customers). Here the goal is to avoid sending a multi-hundred-megabyte ref advertisement. The group explored several optimizations:
   - **Prefix filtering** (already implemented for fetches) would let the client request only the refs it cares about (e.g., `refs/heads/main`).
   - **Server-side configuration** could limit the advertisement to “interesting” refs (e.g., main branches, recent tags), with the client ignoring the rest.
   - **Negotiation** (Jonathan Tan’s preference) would allow the client and server to exchange capabilities, then iteratively narrow down the set of refs that need to be advertised.
   - **Heuristics** (Peff’s suggestion) could guess which branches are likely to be relevant (e.g., upstream tracking branches).
   - **Project-specific configuration** (brian’s idea) could be distributed via documentation or setup scripts, telling clients which refs to request.

   The group acknowledged that these optimizations are not mutually exclusive and could be combined. A key insight was that even a simple configuration option to disable ref advertisements entirely (Jonathan Tan) might yield substantial savings with minimal risk, since the client can always fall back to sending all objects if the optimization fails.

2. **Automated replication** (Martin Fick’s Gerrit use case). Gerrit pushes to thousands of mirrors, and ref advertisements are expensive when checking whether a mirror is already up to date. Here the goal is to avoid the advertisement entirely if the mirror is in sync. The group discussed:
   - **Generation numbers** (brian) or **ETag-style checksums** (Peff) could provide a lightweight way to compare ref states without transferring the full advertisement.
   - **Reftable format** (Patrick Steinhardt) could be sent directly, allowing the client to parse it and extract only the information it needs.
   - **Compression** (Peff) could shrink the advertisement format itself.

   The group leaned toward starting with a compressed advertisement format (zlib) as the simplest first step, with reftable-based optimizations as a follow-up.

A third, cross-cutting concern was **SHA-256 interoperability**. Today, a client must know the server’s hash algorithm and the mapping between object IDs in that algorithm and content. Protocol v2 for pushes would allow the client and server to negotiate the hash algorithm, making interoperability seamless. This was seen as a strong argument for prioritizing the v2 push work.

The discussion also touched on edge cases (shallow clones, unrelated histories) and performance trade-offs (e.g., `objects-edge-aggressive` increasing push time from 2 seconds to 35 seconds). The group agreed that these are secondary concerns and should not block the initial implementation.

**Next steps** are not yet concrete, but the tone was action-oriented. The infrastructure for v2 is already in place (thanks to fetch v2), and the group identified several low-hanging optimizations (prefix filtering, server-side configuration, compression) that could be implemented incrementally. The most likely path forward is a patch series that wires up the v2 push protocol with minimal optimizations, followed by iterative improvements based on real-world usage. No one objected to the idea in principle, and the interoperability benefit alone was seen as sufficient justification.

The thread leaves open questions about how to handle negotiation (round trips vs. heuristics), how to integrate with reftable’s generation numbers, and whether to standardize on a compressed advertisement format. These are implementation details that can be resolved during patch review. The bigger picture—Protocol v2 for pushes is needed and should be implemented—is now clear.

This is a **substantive review** of Mark C. Chu-Carroll’s v2 patch adding revision-based filtering to `git repo structure`. Patrick Steinhardt’s feedback focuses on three areas: commit message clarity, documentation precision, and implementation details in the revision-parsing logic.

The review begins by criticizing the commit message for lacking motivation—it states *what* the patch does ("imitate `git log`") but not *why* revision-based filtering is useful or how it improves upon the v1 `--no-<reftype>` approach. This is a recurring theme in Patrick’s feedback: he expects commit messages to justify design choices, not just describe them.

On documentation, Patrick proposes tightening the language to align with Git’s established terminology. He suggests replacing "query clauses" with "revisions" (a well-defined term in Git) and simplifying the explanation of include/exclude semantics. He also recommends standardizing the synopsis to use `[<revs>...]` instead of `[<include|^exclude>...]`, arguing that the latter is redundant given Git’s existing revision-specifier conventions.

The most technically substantive feedback concerns the `setup_revisions()` call in `builtin/repo.c`. Patrick questions whether the `setup_revision_opt` struct should be populated at all, noting that:
- The `.def = "HEAD"` default may be unnecessary if the user provides explicit revisions.
- The `.revarg_opt = REVARG_COMMITTISH` restriction prevents users from filtering by trees or blobs, which could be useful for analyzing object sizes.
He suggests passing `NULL` instead, letting `setup_revisions()` handle all revision types without default assumptions.

Patrick also requests additional test coverage for edge cases: filtering by trees/blobs (not just commits) and using revision options like `--filter=object:type=blob`. He hints at a preference for less repetitive tests, suggesting `--format=lines` to isolate the filtering logic from output formatting.

The review is **not yet a sign-off**—it’s a detailed critique of implementation choices, with no `Reviewed-by` or `Acked-by`. The tone is constructive but firm, reflecting Patrick’s domain expertise in Git’s revision-parsing machinery. The open questions (revision defaults, test coverage) suggest the patch may need a v3 before it’s ready for `next`. No performance concerns are raised, and the design itself remains uncontroversial.

This is the second patch in a two-patch performance optimization for the commit-graph subsystem, targeting the `fetch.writeCommitGraph` feature. It implements the core logic of the incremental write strategy introduced in the series.

The patch modifies `builtin/fetch.c` to collect only the newly updated refs during a fetch and use them as seeds for the commit-graph write, rather than scanning all refs. This avoids the expensive ref-scanning callback that became more costly in 2020 (630cd5194e). The optimization is skipped for multi-remote fetches (e.g., `git fetch --all`) and when no existing commit-graph exists, falling back to the full reachable scan in those cases. No-op fetches skip the commit-graph write entirely.

The implementation is clean and well-scoped: it introduces a three-mode enum (`GRAPH_WRITE_REACHABLE`, `GRAPH_WRITE_TIPS`, `GRAPH_WRITE_SKIP`) to control the write strategy, an `oidset` to track updated refs, and makes `prepare_commit_graph()` non-static to allow the fetch command to check for an existing graph. The incremental path relies on split mode, where the newly fetched history is added as a new layer on top of the existing chain. The patch also skips shallow-rejected refs (those requiring changes to `.git/shallow`), as their history is incomplete.

Test coverage is thorough, with six new tests in `t/t5510-fetch.sh` and `t/t5537-fetch-shallow.sh` verifying incremental writes, exclusion of unrelated commits, no-op fetch skipping, fallback cases, and correct handling of shallow refs. The synthetic benchmark numbers in the commit message (357ms → 9.3ms for a single ref update) demonstrate a clear performance win.

This patch is technically uncontested after Patrick Steinhardt’s substantive review of v1, and the reroll addresses all prior feedback. The changes are unlikely to introduce behavioral regressions and will benefit large repositories without disrupting existing workflows. The series is ready for final review.

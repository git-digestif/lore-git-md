This is a design discussion about Git's security process, the first of seven follow-up emails from the Git Contributor's Summit 2026 notes. The email captures a wide-ranging conversation led by Toon Claes and notetaker Jeff King (Peff) about the challenges of handling the growing volume of security reports—many of them AI-generated—and the need for a more structured, transparent, and sustainable process.

The core problem is clear: the security mailing list is overwhelmed with reports, many of them duplicates or false positives, and there is no consistent process for triaging, fixing, or releasing security updates. The discussion reveals frustration with the current ad-hoc approach, where patches sit for months and releases are delayed by uncertainty over what constitutes "enough" fixes. Several participants, particularly Patrick Steinhardt and Peff, advocate for more frequent, time-bound security releases—even if they contain only a subset of triaged fixes—rather than waiting for a perfect backlog to clear.

A key tension emerges around resource allocation. Companies like GitLab and Microsoft have contributed some effort, but there is a sense that more could be done, especially from organizations that rely on Git. The idea of using project funds (reportedly around $100k) to hire a dedicated security coordinator—either from within the community or via a third-party contractor—is floated, but met with skepticism about onboarding costs and effectiveness. Emily Shaffer suggests exploring contracting firms like Collabora, while Peff remains doubtful that an outsider could ramp up quickly enough to be useful.

The conversation also touches on transparency and automation. There is broad agreement that the security process should be documented and discussed on the public mailing list, not kept behind closed doors. Peff volunteers to start that discussion. However, automation is seen as a secondary concern: the real bottleneck is not scripting, but the human work of merging fixes across multiple Git versions, writing advisories, and obtaining CVEs.

Notably, there is no resistance to the idea of faster, more predictable releases, and no objections to pushing back on Microsoft's preferred seven-week release cycle if it conflicts with the project's needs. The group seems aligned on the principle that the project should control its own release cadence, not be dictated by downstream consumers.

This email sets the stage for concrete follow-up: a public discussion about formalizing the security process, and possibly a near-term security release to clear the backlog. It is a candid, practical conversation about governance and sustainability, not a technical deep dive. For anyone concerned about Git's security posture, this thread is worth watching—especially once Peff's promised email to the public list arrives.

This is a substantive review of Domen Kožar’s v3 patch introducing a unified `post-worktree` hook. Phillip Wood engages deeply with the design and implementation, raising several technical concerns that could shape the series’ future direction.

The review focuses on four main areas. First, Phillip questions the usefulness of the worktree identifier (the administrative directory name) passed to the hook, arguing it is not a user-facing concept and that different repositories can have worktrees with the same ID. He suggests passing the worktree’s absolute git-dir instead, which would be more directly actionable for external tools. Second, he challenges the four-argument interface (`event`, `id`, `old-path`, `new-path`), noting that `add` and `remove` events only need two meaningful arguments and that padding with empty strings adds unnecessary complexity. Third, he asks whether the hook needs to run serially, implying a potential performance concern for tools that manage many worktrees. Finally, he raises a fundamental design question: whether a single `post-worktree` hook is preferable to a `worktree-event` hook that could run *before* removal, allowing tools to clean up resources before the worktree disappears.

Phillip’s feedback is constructive and technically grounded. He acknowledges the value of the feature—observing worktree lifecycle events without relying on wrappers—but pushes for a cleaner, more flexible interface. His suggestion to pass the git-dir instead of the ID is particularly compelling, as it would give tools direct access to the worktree’s administrative files without requiring them to reconstruct paths. The question about serial execution is less critical but worth addressing if the hook is expected to scale to large numbers of worktrees. The most significant point is the timing of the `remove` event: if tools need to clean up resources, a post-removal hook may be too late, and a pre-removal hook could be more useful.

This review is likely to influence the next iteration of the series. Domen will need to address Phillip’s concerns about the hook’s interface and timing, either by revising the design or providing a strong rationale for the current approach. The thread remains in active design discussion, with Junio C Hamano’s fundamental objection to hooks still unresolved. If Domen can incorporate Phillip’s feedback, the series could move closer to acceptance, but the broader debate about observability versus ownership (Kristoffer Haugsbakk’s `--id=<string>` counterproposal) will continue to shape the feature’s final form.

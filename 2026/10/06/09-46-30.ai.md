This is the v2 reroll of a two-patch performance optimization for the commit-graph subsystem, targeting the `fetch.writeCommitGraph` feature. The series introduces an incremental write strategy that avoids scanning all refs after every fetch, instead using only the newly updated refs as seeds for the commit-graph write when possible.

The core problem is well-motivated: when `fetch.writeCommitGraph` is enabled, Git currently rebuilds the commit-graph from all reachable refs after each fetch, which is inefficient for repositories with many refs. The solution uses a three-mode enum (`REACHABLE`, `TIPS`, `SKIP`) to control commit-graph writes—skipping entirely for no-op fetches, writing incrementally from updated refs when an existing graph exists, and falling back to a full reachable scan when no graph exists or when fetching from multiple remotes. The incremental path relies on split mode, where the newly fetched history is added as a new layer on top of the existing chain rather than replacing it.

Key improvements in v2 include updated commit messages with synthetic benchmark numbers (357ms → 9.3ms for a single ref update), a code comment explaining why shallow-rejected refs are skipped (their history is incomplete), and extended test coverage. The new tests verify that local-only commits remain in the graph after incremental writes and that shallow-rejected refs are correctly excluded. The series touches `builtin/fetch.c`, `commit-graph.c`, `commit-graph.h`, and adds a `commit-info` subcommand to `test-tool read-graph` for testing.

The implementation appears clean and well-scoped, with explicit policy modes and thorough test coverage. The fallback to full scans in edge cases (no existing graph or multi-remote fetches) suggests careful handling of correctness. The benchmark numbers demonstrate a clear performance win, and the changes are unlikely to introduce behavioral regressions. This looks like a targeted optimization that will benefit large repositories without disrupting existing workflows.

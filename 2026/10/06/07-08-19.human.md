This is the first patch in Harald Nordgren’s six-part feature series that improves how `git status` and `git push` handle rebased branches. The patch modifies `remote.c` to make `git status` smarter about divergence between a local branch and its push target (`@{push}`). Instead of treating all divergence the same, it now distinguishes commits that come from the upstream branch from those that don’t.

When `git status` detects that the local and push branches have diverged, it now reports two sets of numbers: the total divergence and how many of those commits are *not* present in the upstream branch. For example, if you rebase your work onto a newer upstream, `git status` will now say something like “Your branch and 'origin/topic' have diverged, and have 51 and 1 different commits each (1 and 1 not in 'upstream/main')” instead of just reporting the raw totals. This makes it immediately clear that the divergence is due to a clean rebase rather than unrelated changes.

The implementation adds a new helper function, `stat_outside_upstream()`, which uses a three-dot revision range with an exclusion (`^upstream`) to count only the commits that differ between the local and push branches but are not in the upstream. The patch also updates the formatting logic in `format_branch_comparison()` to include the new counts in the output message. The new behavior is controlled by the existing `status.compareBranches` configuration, so users who don’t want it can opt out.

The patch includes a new test in `t/t6040-tracking-info.sh` that verifies the new counting logic. The test sets up a scenario where a local branch is rebased onto a newer upstream, then checks that `git status` correctly reports the divergence counts and identifies which commits are not in the upstream. The test coverage looks thorough for the main case, though real-world testing may surface additional edge cases (e.g., merge commits or conflict resolutions during rebase).

This is a well-scoped change that addresses a real pain point for users who frequently rebase. The commit message is clear, the code is clean, and the test coverage is solid. The patch doesn’t touch core object storage or ref handling, so it’s unlikely to introduce regressions. The main discussion points are likely to be around edge cases (what counts as “cleanly rebased”) and whether the new output format is intuitive for users.

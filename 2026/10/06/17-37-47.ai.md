This is a **bug report** with a **reproducible test case** targeting the push negotiation logic in Git 2.54.0 and 2.56.0. The author, Jens Röcker, demonstrates that when a pre-push hook repacks the local object database and removes loose objects, Git incorrectly resends common history that was already advertised to the receiver. The redundant transfer occurs regardless of whether `push.negotiate=true` is set, and the receiver ends up storing a new pack roughly the size of the historical blob (4 MiB in the test).

The report includes a self-contained Python reproducer that creates fresh repository pairs, seeds a deterministic 4 MiB blob as common history, and measures the receiver’s pack size after a push. The observed behavior shows the historical blob being resent (4,196,026 bytes) when a repacking hook runs, compared to the expected minimal transfer (300 bytes) without the hook. The author hypothesizes the issue stems from a stale pack catalogue in the parent process, where `odb_has_object()` with `OBJECT_INFO_QUICK` misses the repacked objects, causing the pack generator to walk history without excluding the already-advertised base.

The test isolates system/global Git configuration, uses local transport, and verages receiver pack sizes rather than network counters. The reproducer is well-documented, includes build instructions for an unmodified Git 2.56.0, and outputs structured JSON results. The report is thorough, with clear expected/actual behavior, source code references, and a plausible mechanism—though the author notes it’s not instrumented proof. The issue affects both Apple Git 2.54.0 and upstream Git 2.56.0 on macOS/arm64, suggesting a systemic flaw in the push negotiation logic when loose objects are repacked mid-push.

This is a strategic reply in the Git 3.0 SHA-256 transition debate, offering a user-centric perspective on the readiness of Git’s tooling and the practical challenges of migrating repositories. Kristoffer Haugsbakk, a documentation contributor, shares firsthand experience attempting to test the SHA-256 migration process and highlights significant gaps in Git’s current tooling, workflow support, and user-facing documentation. His account underscores the disconnect between the project’s strategic timeline and the reality faced by non-core users, framing the Git 3.0 plan as premature and poorly supported by existing infrastructure.

Haugsbakk’s central critique is that Git itself lacks the tools and documentation necessary for users to experiment with SHA-256 repositories before the default switch in March 2027. He describes a frustrating attempt to migrate the Git repository to SHA-256 using `git fast-export` and `git fast-import`, only to encounter multiple roadblocks: the inability to export refs pointing to blobs or trees, the loss of Git notes (due to SHA-1 filenames being retained), and the failure to handle the SHA-1 collision submodule. These issues are not edge cases but fundamental limitations of the current migration workflow, and they are documented only in the aspirational *hash-function-transition* guide rather than in actionable tooling. His experience suggests that even technically savvy users—let alone average developers—have no practical way to test the transition, identify workflow-specific bugs, or provide meaningful feedback before the default switch.

The email also highlights the absence of a supported migration path that preserves SHA-1 to SHA-256 mappings, which would be essential for users who rely on Git notes or other metadata. Haugsbakk notes that Brian M. Carlson’s earlier response confirms this gap, leaving users with no option but to wait for Git 3.0 and hope for the best. His hypothetical scenario of a user encountering a "broken Git" after the default switch—only to mitigate the problem by converting back to SHA-1 and disabling the default—illustrates the likely real-world fallout: widespread frustration, workarounds that undermine the transition’s goals, and a perception of Git as unreliable. The fact that such a scenario is plausible (and even likely) speaks to the inadequacy of the current tooling and the lack of a user-friendly safety net.

Haugsbakk’s tone is measured but pointed, particularly in his observation that the migration effort is being led by a single contributor (Carlson) working in their spare time, despite the transition’s institutional urgency. This framing challenges the project’s readiness to impose a breaking change on the entire ecosystem, especially when the tooling required to support that change is incomplete and poorly documented. His conclusion—that users have no choice but to wait and see what happens in March—is a damning indictment of the project’s preparedness, even if it stops short of advocating for a specific alternative (e.g., Chacon’s tree-digest proposal or Schindelin’s opt-in compromise).

For future summarizers, the key takeaways are:
- **Tooling gaps**: `git fast-export`/`fast-import` are insufficient for real-world migration, losing metadata (notes) and failing on common repository structures (submodules, blob/tree refs).
- **Documentation issues**: The *hash-function-transition* guide is aspirational rather than actionable, leaving users without clear instructions for testing or migrating.
- **User experience**: The lack of a supported migration path (with SHA-1 to SHA-256 mapping) forces users into all-or-nothing scenarios, increasing the risk of frustration and workarounds.
- **Strategic implications**: Haugsbakk’s account lends weight to Chacon’s argument that the Git 3.0 plan is premature, while also supporting Schindelin’s call for opt-in adoption. His critique does not engage with the tree-digest proposal’s technical merits but instead highlights the broader failure of the project to provide a viable migration path for users.
- **Participant positions**: Haugsbakk aligns with neither the Git 3.0 hardliners (Carlson/Steinhardt) nor the tree-digest advocates (Chacon), instead framing the issue as a failure of tooling and user support. His perspective is likely shared by many non-core contributors who lack the resources to navigate the transition’s current limitations.

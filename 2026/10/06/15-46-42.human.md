This is Junio’s latest review comment on the second patch of Phillip Wood’s v2 series, which teaches `git checkout -m` to remember and recreate the original conflict labels. The series is otherwise ready for integration, with all prior feedback addressed.

Junio raises a narrow but important edge case: the current implementation writes `.git/MERGE_LABELS` unconditionally when `update_worktree_and_index` is true, even if the merge result is clean (no conflicts). This means the file could contain `(null)` strings if the merge succeeds without conflicts, which is misleading and unnecessary. The labels are only populated in `move_opt_priv_to_result_priv()` when `!result->clean`, so writing them in a clean merge would indeed produce `(null)` entries.

This is a straightforward oversight in the patch’s control flow. The fix is to move the `write_merge_labels()` call inside the same `!result->clean` guard that populates the labels, ensuring the file is only written when there are actual conflicts to remember. The change is mechanical and does not affect the core functionality, but it prevents cluttering `.git` with meaningless files. No other parts of the patch or series are impacted.

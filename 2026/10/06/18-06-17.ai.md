This is the second installment in Taylor Blau’s Git Contributor’s Summit 2026 notes series, focusing on **Git 3.0 planning**. The discussion is high-level and strategic, not a code patch, but it introduces key technical and scheduling details that will shape the next major release.

The central question is when and how to release Git 3.0, with SHA-256 support and mandatory Rust code as the two defining features. The group reached consensus on a **two-stage rollout**: a 2.99 release in March 2027 followed immediately by 3.0, with 3.0 differing only in flipped defaults for breaking changes. This approach gives users a clear signal (2.99) while minimizing risk. The timeline also drops the planned 2.57 release in favor of an earlier 2.98, compressing the pre-3.0 cycle.

Key technical details: SHA-256 support is confirmed for GitHub (general availability in November 2026) and GitLab (already public), but JGit and Bitbucket lag behind. Interoperability between SHA-1 and SHA-256 repositories is described as complete on brian m. carlson’s personal branch, though not yet upstreamed. Rust support in 3.0 drew no objections, but the notes do not record a formal decision on whether it will be mandatory or merely allowed.

Open questions remain: whether to offer a 2.99 LTS (Gentoo expressed interest), how to synchronize with downstream distribution cycles, and whether SHA-256 adoption will surface latent bugs in Git itself. The discussion also touched on funding for JGit and gitoxide SHA-256 support, with Google declining to fund JGit but gitoxide possibly securing funding.

No files, config keys, or command-line options are introduced yet, but future patches will likely reference `BREAKING_CHANGES` defaults, SHA-256 interoperability plumbing, and Rust build flags. The thread is still in the design phase; expect follow-up emails on each of these technical tracks.

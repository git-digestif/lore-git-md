This is a discussion about workflow design for incremental rebase conflict resolution, specifically how to integrate the functionality into `git rebase` itself. Phillip Wood responds to Alejandro Colomar’s earlier demonstration of a multi-shot workflow (where the user manually controls the order of rebasing interdependent branches) with a proposal to improve `git rebase --update-refs` so it can automatically handle trees of branches.

Phillip acknowledges the complexity of Colomar’s manual workflow—rebasing branches A, B, and C in a specific order—and agrees it is error-prone. He suggests extending `--update-refs` to support more complex dependency graphs, noting that the current implementation can rebase A and B together but lacks a way to include C. His key idea is to insert "break" commands after each branch is rebased, allowing the user to run `git range-diff` or other checks before continuing. This would preserve the flexibility of Colomar’s multi-shot approach while reducing manual steps.

The email does not introduce new code or patches but advances the thread’s focus toward a built-in solution rather than a `contrib/` script. Phillip’s proposal is substantive: it engages with the workflow’s technical requirements (handling interdependent branches) and suggests a concrete implementation path (extending `--update-refs`). The discussion now centers on whether this approach can satisfy both simple and complex use cases without breaking existing workflows. The unresolved question is whether the project will pursue this integration or continue evaluating standalone scripts like `git-bisect-rebase`.

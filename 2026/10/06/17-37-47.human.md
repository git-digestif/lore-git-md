This is a bug report with a detailed reproducer for a performance regression in Git 2.54.0 and 2.56.0. The issue: when a pre-push hook repacks the local object database and prunes loose objects, Git resends already-advertised common history instead of excluding it. The reporter, Jens Röcker, demonstrates this with a minimal Python script that creates fresh repositories, seeds a 4 MiB historical blob, and measures the size of the pack received by the remote.

The key finding is that a push with no hook sends only ~300 bytes, but the same push with a repacking hook sends ~4.2 MiB — the full size of the historical blob. This happens regardless of whether `push.negotiate=true` is set. Jens hypothesizes that the parent process's stale pack catalogue causes it to miss the repacked objects during negotiation, leading to redundant transmission.

The report is thorough: it includes exact reproduction steps, a self-contained script, version-specific source links, and a clear expected-vs-actual behavior comparison. The reproducer is portable (Python 3 + Git) and isolates the issue from system configuration. This looks like a real, measurable bug that could affect users with pre-push hooks that repack or prune objects. The regression appears to persist across versions and platforms (tested on macOS/arm64). For anyone using pre-push hooks that modify the object store, this is worth attention.

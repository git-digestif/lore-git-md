This email is a substantive follow-up in the ongoing discussion about `git-bisect-rebase`, a proposed `contrib/` helper for incremental rebase conflict resolution. Alejandro Colomar responds to Nico Williams and Phillip Wood, refining the requirements for a multi-shot workflow and pushing back on the idea of automating interdependent branch rebasing via `git rebase --update-refs`.

Colomar argues that the multi-shot approach—where the user manually controls the rebase order and aborts to handle child branches—is essential for complex dependency graphs. He acknowledges that forgetting to abort before resolving conflicts can lead to redundant work (resolving the same conflict twice), but insists this is a minor learning curve rather than a fundamental flaw. His key point is that automating the recursion (e.g., via `--update-refs`) would be overly complex and inflexible, as users may prefer to tackle branches in a specific order. He suggests that the current manual workflow, while labor-intensive, is safer and more adaptable, and should remain the default until the interface is thoroughly tested.

Colomar also responds to Nico’s idea of inserting "break" commands to allow inspection via `git range-diff`. While he concedes this *could* work for conflicts, he remains unconvinced of its value, particularly for intermediate bisection steps where the user would mostly elect to continue. His skepticism reflects a preference for simplicity and a focus on the core use case: efficiently rebasing a single branch across a large upstream history.

The email reinforces the thread’s consensus that `git-bisect-rebase` is the leading candidate for `contrib/` inclusion, but it also highlights lingering questions about workflow design. Colomar’s insistence on manual control aligns with Nico’s earlier clarification that the tool is orthogonal to `--update-refs` (which targets stacked branches), but it leaves open whether the project will accept a helper that requires significant user intervention. His call to "play with it" underscores that the discussion is still in the exploratory phase, with no clear path toward integration into `git rebase` itself. The tone is collaborative but firm, prioritizing practicality over automation for now.

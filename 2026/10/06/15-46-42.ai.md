This is a substantive review comment from Junio on Phillip Wood’s v2 2/2 patch, which implements conflict label preservation for `git checkout -m`. Junio identifies a logical inconsistency in the current implementation: the code unconditionally writes `.git/MERGE_LABELS` (via `write_merge_labels()`) even when the merge result is clean (no conflicts), but only populates the labels array (`opt->priv->labels[]`) when conflicts occur. This mismatch could result in writing `(null)` strings to the file, which is clearly unintended.

The issue stems from two separate code paths:
1. `write_merge_labels()` is called unconditionally under `if (result->clean >= 0 && update_worktree_and_index)`, meaning it runs for both clean and conflicted merges.
2. The labels array is only populated in `move_opt_priv_to_result_priv()` when `!result->clean` (i.e., conflicts exist).

Junio’s question ("Would the answer be `(null)\n(null)\n(null)\n`?") is rhetorical, highlighting that the current implementation would write garbage or undefined values for clean merges. This is a correctness bug: `.git/MERGE_LABELS` should only be written when conflicts occur, as it serves no purpose in clean merges and could mislead users or scripts.

The fix is straightforward: `write_merge_labels()` should only be called when conflicts exist. This aligns with the series’ goal of preserving labels *only* for conflicted merges, and matches the existing pattern of other merge-related files (e.g., `MERGE_MSG` is only written for conflicts). The patch is otherwise ready for integration, but this issue must be addressed to avoid introducing a subtle bug. No other technical concerns are raised in this email.

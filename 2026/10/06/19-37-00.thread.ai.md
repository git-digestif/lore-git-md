Core problem or goal
Replace the outdated `gittutorial` man page with a two-part beginner guide tested on 112 users. Part 1 covers local repository creation and commits; Part 2 covers pushing to a remote host (GitHub/GitLab). The goal is to provide a modern, practical introduction that reflects current workflows while avoiding confusion about Git’s decentralized model. The author emphasizes the tutorial is "good enough" for merging, with iterative improvements planned post-merge.

Current status
Under review. The series is now at v2, with patches resent after a GitGitGadget delivery delay noted by Junio C Hamano and confirmed by D. Ben Knoble. Ben received the v2 patches but observed they may have been silently dropped by the mailing list or public archive, possibly due to size limits. No technical feedback or merge decision has followed the resend. The v2 incorporates feedback from D. Ben Knoble and addresses minor editorial and pedagogical clarifications. Julia Evans has responded to all feedback, treating low-weight suggestions as optional improvements rather than blockers:
- **`git config` syntax**: Julia acknowledges the newer `git config set`/`get` syntax (introduced in Git 2.32) but defers adoption to maintain compatibility with older Git versions (claimed to work on "any version above 2.0"). D. Ben Knoble reaffirmed his preference for the newer syntax but deferred to compatibility concerns, leaving the question open for future iteration.
- **Directory creation**: Julia defended the two-step `mkdir myproject; cd myproject` approach for clarity, and D. Ben Knoble explicitly dropped his suggestion to use `git init myproject` as a single step. The current implementation remains unchanged.
The first patch (v2 1/2) deletes the existing `Documentation/gittutorial.adoc` file. The second patch (v2 2/2) introduces the new tutorial, which includes expanded explanations of `git status` output, troubleshooting sections, platform-specific clarifications, and accessibility considerations. No code or on-disk format changes.

Open questions and loose ends
1. **Repository creation**: Whether to start with `git init` (current approach) or `git clone` from a forge. The author defends `git init` as more consistent for beginners but remains open to alternatives. No consensus yet.
2. **Authentication**: How to handle SSH/HTTPS setup generically without tying instructions to specific forge UIs. The author acknowledges the fragility of forge-dependent instructions but considers it "probably ok" for beginners. No resolution.
3. **Pedagogical choices**:
   - Use of `git commit -m` (defended as pragmatic for beginners; no objections, but no explicit approval).
   - Whether to adopt newer `git config set`/`get` syntax (raised by Ben Knoble; compatibility with older Git versions noted, but no consensus).
4. **Post-merge iteration**: The author plans to gather user feedback after merging to refine branching and collaboration content. This is noted as a follow-up effort, not a blocker.

This email is a **follow-up in a bug report thread** about Git’s ZIP timestamp handling and `git fast-import` date validation. Matthew E. Luallen provides additional real-world observations about how downstream tools (Python’s `ZipInfo.date_time`, UnZip, and bsdtar) behave when processing Git-generated ZIP archives with out-of-range timestamps. These details sharpen the compatibility risks of the current behavior and may influence the eventual fix.

The key new information centers on **tool-specific fallout** from Git’s current ZIP timestamp logic. For the **1972 commit → 2100 DOS date** issue (bug 1), Matthew confirms that Python 3.14.7’s `ZipInfo.date_time` misreads the DOS date as 2100, even though the correct Unix timestamp is present in the archive. This affects metadata display but does not break extraction (UnZip and bsdtar restore the 1972 date correctly). For the **2106-02-07 commit → 1970 Unix timestamp wrap** issue (bug 2), he demonstrates a more serious problem: UnZip’s update mode retains outdated 2025 content instead of overwriting it with the 2106 file, because the wrapped timestamp (1970) is older than the existing archive’s timestamp. This creates silent data inconsistencies that could confuse users.

The email does not propose a patch or resolve the policy questions raised earlier (e.g., whether to clamp or reject out-of-range timestamps), but it **strengthens the case for rejection** in the 2106 case by showing how clamping can lead to subtle, tool-specific misbehavior. The `fast-import` negative timestamp issue (bug 3) is not addressed here, but Matthew’s earlier suggestion to reject negative values in `--date-format=raw` mode remains the most actionable near-term change. The thread is now better equipped to weigh trade-offs between correctness and compatibility, with concrete examples of how current behavior affects real tools.

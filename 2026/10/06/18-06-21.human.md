This is the third installment in Taylor Blau’s seven-part series summarizing the Git Contributor’s Summit 2026. It covers the **Documentation** discussion, a wide-ranging conversation about how to make Git’s documentation more accessible, better funded, and easier to maintain.

The core problem is familiar: Git’s documentation assumes too much prior knowledge, leaving beginners confused about basic concepts like “upstream” or “the index.” Julia Evans (jvns.ca) is building a beginner-friendly website to bridge that gap, but funding is limited (100 hours split between two people) and the mailing-list review process is seen as too slow and nitpicky for iterative work. Several participants—Patrick Steinhardt, Peff, and brian m. carlson—agree that the current man pages are too terse for new users and that Git needs separate beginner documentation, not just reference material.

The discussion then turns to funding and tooling. Pro Git (the book) is outdated, and Scott Chacon is willing to fund a refresh. The group explores whether the Git project’s own fund could support documentation work and whether companies like OpenAI, GitHub, or GitButler might contribute. On the technical side, participants debate whether to move from AsciiDoc to Asciidoctor (Peff and Josh Steadmon favor the switch, brian notes Fedora still uses AsciiDoc), whether to adopt Mermaid or Graphviz for diagrams, and how to add subsection links to man pages. Peff offers to help Julia compare AsciiDoc and Asciidoctor outputs using `doc-diff`.

Finally, the group touches on metrics: git-scm.com has only high-level Cloudflare numbers, and there is interest in privacy-respecting analytics (Fathom, self-hosted logs) to understand which documentation pages users actually read. The thread ends with an open question about how to balance signal and noise in the face of AI scrapers.

This is a **design discussion**, not a patch or a decision. It surfaces real pain points and a willingness to invest in documentation, but no concrete plan or funding commitment has been made yet. If you care about Git’s usability, this thread is worth following for the funding proposals and tooling experiments that may emerge.

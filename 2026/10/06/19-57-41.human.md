This is Junio’s reply to the core fix patch in Patrick Steinhardt’s two-patch series that plugs a packfile corruption bug caused by stale delta base cache entries. The patch itself remains uncontested, but Junio raises a pointed question about the **value of the regression test** given its platform dependency.

The test, added in `t/t6437-submodule-merge.sh`, relies on glibc’s allocator reusing memory addresses to trigger the bug. Junio notes that this makes the test **unreliable on non-glibc platforms** (e.g., musl, macOS, or Windows allocators), where the bug might still exist but the test would pass even if the fix were reverted. He questions whether an unreliable test is worth keeping, though he concedes it might still be acceptable if it catches the bug on widely used systems (like Linux with glibc) and doesn’t produce false positives.

Junio also dismisses the earlier proposal (from Guillaume Chauvel) to write custom low-level code to force address collisions, calling it a potential **maintenance burden**. His tone suggests skepticism about over-engineering a test for a bug that is already fixed, but he doesn’t outright reject the current approach. The thread’s earlier consensus—accepting the test’s limitations as a trade-off for simplicity—remains intact, but Junio’s comment reopens the discussion about whether the test’s value justifies its platform-specific quirks.

No technical objections to the fix itself are raised. The patch is still a strong candidate for `next`, but the test’s long-term utility may need further justification if others share Junio’s concerns.

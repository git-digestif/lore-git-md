Here’s the human-readable summary for a developer catching up on the thread:

This thread introduces a six-patch series from Harald Nordgren that improves how `git status` and `git push` handle rebased branches. The goal is to make Git smarter about detecting when a local branch has been cleanly rebased onto a newer upstream, and to give users more actionable advice in those cases. For example, `git status` will now explicitly say when divergence is due to a clean rebase (e.g., *"Your branch and 'origin/topic' have diverged, and have 51 and 1 different commits each (rebased cleanly on 'upstream/main')"* and suggest `--force-with-lease` when appropriate. Similarly, `git push` rejection messages now name the specific remote branch to pull from when the divergence is with a non-upstream push target, and offer `--force-with-lease` as an option when the remote carries no new work—only commits the local branch has rewritten.

The series is currently at its initial version (v1) and under review. The implementation touches `remote.c`, `builtin/push.c`, and `transport.c`, introducing a new helper function (`stat_outside_upstream()`) to analyze divergence and a new rejection flag (`REJECT_NON_FF_HEAD_REWRITE`) to detect when the remote branch’s tip appears in the local branch’s reflog. The test suite (`t/t6040-tracking-info.sh`) covers the new behavior, including edge cases like pushing to non-upstream branches. The changes are opt-in, requiring users to configure `status.compareBranches` to include `@{push}`.

The main open questions revolve around whether `--force-with-lease` is always the right advice in these scenarios, and whether the reflog-based detection of rewrites is reliable in all cases (e.g., shallow clones or reflog expiration). No reviews have been posted yet, so the discussion is still in its early stages. If the series lands, it could significantly reduce confusion for users working with rebased branches.

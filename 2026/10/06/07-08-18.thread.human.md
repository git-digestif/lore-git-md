This thread is a six-patch series from Harald Nordgren aimed at improving how `git status` and `git push` handle rebased branches. The goal is to make Git more helpful when a local branch is rebased onto a newer upstream by distinguishing between commits that originate from the upstream and those that don’t. The series is currently at its initial version (v1) and under review.

The first five patches lay the groundwork by enhancing `git status` to detect clean rebases—where the non-upstream commits are identical on both sides—and suggest `--force-with-lease` instead of generic divergence advice. They also improve push rejection messages by naming the specific remote branch to pull from when divergence occurs with a non-upstream push target. The fifth patch, which just arrived, focuses on push rejection messages when the local branch has been amended or rebased after being pushed. It introduces a new rejection reason (`REJECT_NON_FF_HEAD_REWRITE`) that triggers when the remote branch’s tip appears in the local branch’s reflog, indicating no new work on the remote—just rewritten commits. In this case, the rejection message now offers both `git pull` and `git push --force-with-lease` as options, making the advice more actionable.

The implementation touches `remote.c`, `builtin/push.c`, and `transport.c`, adding a new helper function (`stat_outside_upstream()`) and modifying existing logic to include upstream-aware comparisons. The test suite (`t/t6040-tracking-info.sh`) has been expanded to cover the new scenarios, including the reflog-based detection of rewrites. While the changes are opt-in (only affecting users who configure `status.compareBranches` to include `@{push}`), they introduce subtle edge cases around reflog expiration, shallow clones, and whether `--force-with-lease` is always appropriate. No reviews have been posted yet, so the discussion around these trade-offs is still ahead.

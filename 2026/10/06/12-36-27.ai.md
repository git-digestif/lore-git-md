This is a **substantive technical clarification** in the ongoing review of the incremental connectivity check series (v2 2/2). Kristofer Karlsson and Patrick Steinhardt resolve Patrick’s lingering question about how the incremental verifier establishes its trust boundary without parsing all refs upfront.

The key insight is that the incremental mode **reuses the same boundary-detection mechanism as the full connectivity check**: `git rev-list --not --all` marks preexisting ref tips as uninteresting, implicitly identifying the "old tips" (already-connected commits). The incremental verifier then processes incoming commits in **reverse topological order**, verifying each commit’s tree only against its parents’ trusted trees. This inductive trust model ensures correctness: ancestors are processed before descendants, so each commit’s parents are either already connected (boundary commits) or earlier incoming commits whose trees have already been verified.

Kristofer provides a concrete example with a 3-commit push, showing how boundary commits (B1, B2) are trusted by definition, while incoming commits (N1, N2, N3) are verified inductively. The savings come from **skipping full tree walks** of boundary commits—only their root trees are read as comparison bases. Patrick acknowledges his initial confusion stemmed from a false expectation that the incremental mode would eliminate the need to mark preexisting refs as uninteresting, confirming this is not the case.

No new objections are raised, and the discussion reaffirms the subprocess architecture (using `die()` for errors) is safe. The series remains on track for v3, which will split the implementation patch into smaller commits. Key technical details—config key `transfer.connectivityCheck=incremental`, `rev-list` flag `--verify-trees-incremental`, and the inductive trust algorithm in `tree-verify.c`—are now clarified. The performance gains (up to 190x faster for small pushes to large repos) are preserved, with no changes to on-disk formats.

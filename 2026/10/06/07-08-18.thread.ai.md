Thread identity: six-patch feature series from Harald Nordgren enhancing `git status` and `git push` to better handle rebased push branches. Series version: initial posting (v1). Thread type: patch series.

Core problem or goal: improve user experience when a local branch is rebased onto a newer upstream by making `git status` and `git push` distinguish between commits that originate from the upstream branch (`@{upstream}`) and those that do not. When the non-upstream commits are identical on both sides (indicating a clean rebase), the tools now report this explicitly and suggest `--force-with-lease` instead of generic divergence advice. The series also makes push rejection messages more actionable by naming the specific remote branch to pull from when the divergence is with a non-upstream push target, and by detecting when the remote carries no new work (only rewritten commits) via reflog inspection.

Current status: initial posting (v1), under review. No prior versions. No merge status reported.

Key technical details:
- Subsystems touched: `remote.c` (branch comparison logic, new helpers `stat_outside_upstream()` and `branch_rebased_cleanly()`), `builtin/push.c` (push rejection hints, new advice message `message_advice_force_after_clean_rebase`), `transport.c` (reflog-based rewrite detection), `transport.h` (new rejection flag `REJECT_NON_FF_HEAD_REWRITE`).
- New helper functions:
  - `stat_outside_upstream()` in `remote.c` performs a three-way `git rev-list --cherry-mark` (`branch...push ^upstream`) to count commits present in the branch-vs-push comparison but absent from upstream. It sets a `same_changes` flag if the non-upstream commits are identical (flagged by `PATCHSAME`).
  - `branch_rebased_cleanly()` in `remote.c` reuses `stat_outside_upstream()` to determine whether the divergence between branch and push target is due to a clean rebase (non-upstream commits identical on both sides).
- New rejection flag: `REJECT_NON_FF_HEAD_REWRITE` in `transport.h`, set when the remote branch's tip appears in the local branch's reflog, indicating the remote carries no new work--only commits the local branch has since rewritten.
- Modified functions:
  - `format_branch_comparison()` in `remote.c` now accepts an optional upstream name and two "unmerged" counts (local and remote commits not in upstream), and emits a new message when a clean rebase is detected: *"Your branch and 'origin/topic' have diverged, and have 51 and 1 different commits each (rebased cleanly on 'upstream/main')."* It also appends a one-line suggestion to use `git push --force-with-lease` when the divergence is due to a clean rebase, provided `status.compareBranches` includes `@{push}` and `statusHints` advice is enabled.
  - `advise_pull_before_push()` in `builtin/push.c` now takes the push remote as an argument and emits a branch-specific pull advice message when the push target is not the upstream: *"Use 'git pull origin topic' to integrate the remote changes"* (falling back to the generic message if the push target *is* the upstream).
  - Push rejection logic in `transport.c` now checks the reflog to detect when the remote carries no new work (only rewritten commits), and emits a new message offering both `git pull` and `git push --force-with-lease` as options when `REJECT_NON_FF_HEAD_REWRITE` is set. When the divergence is due to a clean rebase, the message now says the branch was "rebased cleanly on 'upstream/main'" and offers only `--force-with-lease`.
- New advice messages: `message_advice_pull_from_branch_before_push` and `message_advice_force_after_clean_rebase`.
- New test file: `t/t6040-tracking-info.sh` (188 lines), with test cases verifying the new `git status` message format in a rebase scenario including the `--force-with-lease` hint, the new push rejection message when pushing to a non-upstream push branch that someone else updated, the fallback to the old message when pushing to the upstream, the new reflog-based push rejection message when pushing an amended commit to a branch that was previously pushed, and the new push rejection message when the divergence is due to a clean rebase offering only `--force-with-lease`.
- New behavior: `git status` now reports divergence with a breakdown of commits not present in upstream (e.g., "51 and 1 different commits each (1 and 1 not in 'upstream/main')") and explicitly notes when the divergence is due to a clean rebase. `git push` rejection messages now name the specific remote branch to pull from when the divergence is with a non-upstream push target, and offer `--force-with-lease` as an option when the remote carries no new work (only rewritten commits). When the divergence is due to a clean rebase, the message says the branch was "rebased cleanly on 'upstream/main'" and offers only `--force-with-lease`. The `--force-with-lease` hint is opt-in and consistent with Git's existing advice patterns.
- No changes to core object storage, ref handling, or on-disk formats. Behavior is opt-in: only affects users who configure `status.compareBranches` to include `@{push}`.

Open questions and loose ends:
- Performance regression identified by Aniket Gupta: the `--cherry-mark` flag in `stat_outside_upstream()` causes `git status` to become roughly 5-8x slower when `status.compareBranches` includes `@{push}` and branches have diverged, because patch-ids must be computed for every commit on both sides. Measured at 25ms to 150ms with 3000 diverged commits, and 60ms to 500ms with 10000 diverged commits. Gupta suggests a two-phase optimization: first count diverged commits without `--cherry-mark`, and only invoke the expensive patch-id comparison when those counts are small enough to justify the cost. Harald Nordgren acknowledges the regression is serious and engages with the two-phase proposal but raises a user-experience concern that users may find it confusing if the clean-rebase detection message appears inconsistently depending on divergence size. No decision has been made on whether to implement the two-phase optimization, how to threshold the counts that would trigger the patch-id pass, or how to communicate to users why the "rebased cleanly" message might be absent in high-divergence scenarios. This must likely be resolved before the series can advance.
- Edge cases around what constitutes a "clean rebase" (e.g., merge commits, conflict resolutions, or cherry-picks that alter commit content).
- Safety of the new advice (`--force-with-lease`) in all scenarios, particularly whether it is always appropriate when the divergence is due to a clean rebase or when the remote carries no new work.
- Real-world testing may surface additional corner cases not covered by the test suite, such as interactions with shallow clones, partial clones, promisor remotes, or reflog expiration.
- The patch does not address how the logic interacts with commits that are semantically equivalent but not bit-for-bit identical (e.g., due to rebasing with conflict resolution or cherry-picking with minor adjustments).
- Edge cases around refspec resolution or ambiguous branch names in the push rejection message (e.g., when the push target resolves to multiple refs or when the branch name is ambiguous).
- The reflog-based detection of rewrites may not work reliably in all scenarios (e.g., reflog expiration, shallow clones, or when the reflog is disabled).
- Whether the new advice messages are sufficiently clear to users unfamiliar with the distinction between `@{upstream}` and `@{push}`.
- Harald reports the series is already in use via `seen`, but no explicit merge status has been stated by the maintainer.

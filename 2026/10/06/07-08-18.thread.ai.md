Thread identity: six-patch feature series from Harald Nordgren enhancing `git status` and `git push` to better handle rebased push branches. Series version: initial posting (v1). Thread type: patch series.

Core problem or goal: improve user experience when a local branch is rebased onto a newer upstream by making `git status` and `git push` distinguish between commits that originate from the upstream branch (`@{upstream}`) and those that do not. When the non-upstream commits are identical on both sides (indicating a clean rebase), the tools now report this explicitly and suggest `--force-with-lease` instead of generic divergence advice.

Current status: initial posting (v1), under review. No prior versions. No merge status reported.

Key technical details:
- Subsystems touched: `remote.c` (branch comparison logic), `builtin/push.c` (push rejection hints, addressed in later patches).
- New helper function: `stat_outside_upstream()` in `remote.c`, which performs a three-way `git rev-list --cherry-mark` (`branch...push ^upstream`) to count commits present in the branch-vs-push comparison but absent from upstream. It sets a `same_changes` flag if the non-upstream commits are identical (flagged by `PATCHSAME`).
- Modified function: `format_branch_comparison()` in `remote.c` now accepts an optional upstream name and two "unmerged" counts (local and remote commits not in upstream), and emits a new message when a clean rebase is detected: *"Your branch and 'origin/topic' have diverged, and have 51 and 1 different commits each (rebased cleanly on 'upstream/main')."* It also appends a one-line suggestion to use `git push --force-with-lease` when the divergence is due to a clean rebase, provided `status.compareBranches` includes `@{push}` and `statusHints` advice is enabled.
- New test file: `t/t6040-tracking-info.sh` (163 lines), with a 32-line test case verifying the new message format in a rebase scenario, including the `--force-with-lease` hint.
- New behavior: `git status` now reports divergence with a breakdown of commits not present in upstream (e.g., "51 and 1 different commits each (1 and 1 not in 'upstream/main')") and explicitly notes when the divergence is due to a clean rebase. The `--force-with-lease` hint is opt-in and consistent with Git’s existing advice patterns.
- No changes to core object storage, ref handling, or on-disk formats.
- Behavior is opt-in: only affects users who configure `status.compareBranches` to include `@{push}`.

Open questions and loose ends:
- Edge cases around what constitutes a "clean rebase" (e.g., merge commits, conflict resolutions, or cherry-picks that alter commit content).
- Safety of the new advice (`--force-with-lease`) in all scenarios, particularly whether it is always appropriate when the divergence is due to a clean rebase.
- Real-world testing may surface additional corner cases not covered by the test suite, such as interactions with shallow clones, partial clones, or promisor remotes.
- Whether the three-way `rev-list --cherry-mark` approach is performant for large divergence counts or deep histories.
- The patch does not address how the logic interacts with commits that are semantically equivalent but not bit-for-bit identical (e.g., due to rebasing with conflict resolution or cherry-picking with minor adjustments).

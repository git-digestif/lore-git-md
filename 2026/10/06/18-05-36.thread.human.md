The Git Contributor's Summit 2026 thread continues to unpack the project's future, with the latest discussion zeroing in on who gets a say in contentious decisions like the AI contribution policy. The proposed community voting process is under active refinement, and Emily Shaffer’s recent email adds a layer to the eligibility debate: should the project prioritize recent activity, or should it also make room for former maintainers and deeply involved contributors who’ve stepped back but still care deeply about Git’s direction?

The thread began with Taylor Blau summarizing seven major summit topics—security processes, Git 3.0 planning, documentation, Outreachy sponsorship, pluggable ODBs, AI contribution policy, and Protocol v2 for pushes—alongside a governance patch to formalize how the project resolves divisive issues. Most of those topics are now actionable, with Peff drafting a public security process proposal, consensus forming around a two-stage Git 3.0 rollout (including SHA-256 support and Rust inclusion), and the documentation tooling debate resolving in favor of Asciidoctor standardization after Junio confirmed pre-built docs have used it since mid-2024. Outreachy sponsorship still needs corporate backers, the pluggable ODB effort has a Git 2.57 target for a repository extension, and Protocol v2 for pushes is likely to see a patch series soon.

The community voting process, however, remains the most contested piece. The patch initially proposed a threshold of 50 merged patches or two code reviews, but follow-ups from Phillip Wood, brian m. carlson, Junio Hamano, and others have surfaced tensions: How to balance inclusivity with ensuring voters have meaningful context? Should the project count patch series instead of individual commits, or only substantive reviews? Is a two-year activity window too restrictive, or necessary to prevent "drive-by" contributions? Peff’s empirical data showed that a 50-commit threshold with a two-year window would include 42 contributors, while a 5-commit threshold would include 120—highlighting the trade-offs between practicality and breadth.

Emily’s email nudges the discussion toward a more qualitative lens. She argues that some former contributors—like maintainers who’ve moved on—may still offer valuable perspective, especially on high-stakes decisions like the AI policy. Her personal example (being unable to contribute code recently due to her role at Google but still wanting a voice) underscores the human stakes. The thread hasn’t settled on a threshold yet, but Phillip Wood’s hybrid model (requiring both a track record *and* recent activity) and Tuomas Ahola’s suggestion of using the average commit count (26) as a middle ground are gaining traction. The next steps will likely involve reconciling these perspectives—balancing Patrick Steinhardt’s call for a "middle ground" (e.g., 25–30 commits with a 2–3 year window) with Emily’s plea for broader inclusivity, particularly for contributors with deep but dormant ties to the project. The voting mechanism itself (email-based, GitHub-agnostic) and whether the vote will be binding or advisory remain unresolved, but the focus for now is on who gets to participate.

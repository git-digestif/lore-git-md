- **Protocol v2 for pushes**:
  - **Core problem**: `git push` still uses Protocol v0, requiring the server to advertise *every* ref in the repository before the client can send anything. For repositories with millions of refs, this advertisement can balloon to hundreds of megabytes, making pushes slow and expensive.
  - **Use cases**:
    1. **Large repositories with many refs** (brian m. carlson’s customers): Goal is to avoid sending a multi-hundred-megabyte ref advertisement. Optimizations explored:
       - **Prefix filtering** (already implemented for fetches): Client requests only the refs it cares about (e.g., `refs/heads/main`).
       - **Server-side configuration**: Limit advertisement to “interesting” refs (e.g., main branches, recent tags), with client ignoring the rest.
       - **Negotiation** (Jonathan Tan’s preference): Client and server exchange capabilities, then iteratively narrow down the set of refs to advertise.
       - **Heuristics** (Peff’s suggestion): Guess which branches are likely relevant (e.g., upstream tracking branches).
       - **Project-specific configuration** (brian’s idea): Distribute via documentation or setup scripts, telling clients which refs to request.
       - **Disable ref advertisements entirely** (Jonathan Tan): Simple configuration option to skip advertisement, with fallback to sending all objects if optimization fails.
    2. **Automated replication** (Martin Fick’s Gerrit use case): Goal is to avoid ref advertisement entirely if the mirror is in sync. Optimizations discussed:
       - **Generation numbers** (brian) or **ETag-style checksums** (Peff): Lightweight way to compare ref states without transferring the full advertisement.
       - **Reftable format** (Patrick Steinhardt): Send reftable directly, allowing client to parse it and extract only needed information.
       - **Compression** (Peff): Shrink the advertisement format itself (zlib).
  - **SHA-256 interoperability**: Protocol v2 for pushes would allow client and server to negotiate the hash algorithm, making interoperability seamless.
  - **Edge cases**: Shallow clones, unrelated histories, and performance trade-offs (e.g., `objects-edge-aggressive` increasing push time from 2 seconds to 35 seconds) discussed but deemed secondary to initial implementation.
  - **Next steps**: Patch series likely, starting with minimal optimizations (prefix filtering, server-side configuration, compression) and iterating based on real-world usage. No objections in principle; interoperability benefit seen as sufficient justification.

This is a design discussion follow-up from the Git Contributor's Summit 2026, focusing on the future of the **pluggable object database (ODB)** effort. The email captures a brainstorming session about next steps for Patrick Steinhardt’s pluggable ODB work, which is already functional but not yet complete (e.g., commit-graph and MIDX integration are pending). The discussion explores technical directions like **content-defined chunking**, **delta compression**, and **new object representations**, as well as broader use cases such as a "commit cloud" (a distributed, real-time collaboration layer for Git).

Key technical ideas include:
- **Repository extension in Git 2.57**: Patrick plans to introduce a repository extension to signal ODB support, a prerequisite for wider adoption.
- **Content-defined chunking**: A proposed optimization for storage efficiency, with debate over whether it should live at the object layer (changing object hashes) or the storage layer (pack-only, preserving compatibility). Brian m. Carlson and Patrick lean toward the latter, while Peff raises concerns about maintaining a consistent object model.
- **Delta compression**: Peff notes that Mercurial’s approach to delta generation relies on information Git’s ODB currently lacks (e.g., renames), sparking discussion about evolving the ODB API to accept richer context (e.g., `struct commit *`).
- **New object types**: Brian suggests a pack-only "chunked" object type to avoid hash collisions, drawing an analogy to `REF_DELTA`/`OFS_DELTA`. This would require a format extension due to bit exhaustion in the current pack format.
- **Trees and reftable**: Brian and Patrick briefly discuss extending chunking to trees (which aren’t binary-searchable today) and whether reftable’s design could inspire solutions.

The discussion also touches on **wildcard use cases**, like Emily’s skip-level manager’s interest in a "commit cloud" (a real-time, distributed collaboration layer for Git). This hints at broader ambitions for pluggable ODBs beyond storage optimization, though no concrete plans emerge.

The tone is exploratory and collaborative, with no decisions or action items yet. The technical challenges (e.g., object model consistency, format extensions) are non-trivial, and the conversation reflects a mix of enthusiasm and caution. The pluggable ODB effort is clearly seen as foundational work that could enable future innovations, but the path forward remains open-ended.

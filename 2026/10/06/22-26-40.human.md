This is a progress update on the SHA-256 interoperability work, responding to Christian Couder’s questions about the state, scope, and roadmap of the repository-rewriting code that brian m. carlson has long described as the “real solution” to SHA-1 deprecation. The email is factual and pragmatic, providing concrete answers about availability, missing pieces, effort estimates, collaboration opportunities, and testing.

The interoperability work is now publicly accessible in the `sha256-interop` branch of brian’s GitHub fork (https://github.com/bk2204/git.git). It consists of roughly 212 patches, with the early part rebased onto Patrick Steinhardt’s pluggable ODB series in the `sha256-interop-part-2` branch. Submodules are not the only gap: the branch lacks in-place migration tooling (needed for recursive submodule rewriting), has no multi-pack index support, and suffers from performance issues caused by loose-object handling that can corrupt repositories if interrupted. Fixing these problems is estimated to take four release cycles (about six months) of focused work, plus two more cycles if an in-place migration helper is added.

Collaboration is explicitly welcomed: brian invites others to rebase and polish the early patches and send them upstream, while a respected but unnamed community member has offered to fund further development. Testing has so far relied on a small personal repository (`lawn.git`) and the existing test suite (t1017); real-world validation with git.git and mixed clients/servers is planned once in-place migration is implemented. The tone is realistic about the work’s current state—functional but rough—and the effort required to make it production-ready.

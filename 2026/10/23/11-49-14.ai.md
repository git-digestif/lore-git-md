This is the fifth patch in Patrick Steinhardt’s **v3 object storage extension series**, which introduces pluggable object database backends for Git. This patch specifically adds **user-facing configuration and command-line options** for the object storage format, mirroring the existing support for the ref storage extension. It enables users to set the object storage format via `--object-storage-format=` in `git init` and `git clone`, environment variables (`GIT_OBJECT_STORAGE_FORMAT` and `GIT_DEFAULT_OBJECT_STORAGE_FORMAT`), and configuration (`init.defaultObjectStorageFormat`).

The implementation is **mechanically complete** and follows the established pattern for the ref storage backend. The patch updates `builtin/init-db.c` and `builtin/clone.c` to accept the new `--object-storage-format=` option, which parses the format URI into `(type, payload)` components (e.g., `files://objs` becomes `("files", "objs")`). The `setup.c` helper functions (`repository_format_configure()`, `create_repository()`, and `initialize_repository_version()`) are extended to handle the object storage format alongside the ref storage format, ensuring consistent precedence rules: command-line options override environment variables, which override configuration, which defaults to `files`. The patch also updates `refs.c` to propagate the object storage format during ref storage migration, ensuring that repository reinitialization preserves both storage formats.

**Key changes and behavior:**
- **New CLI option**: `--object-storage-format=` for `git init` and `git clone`, documented in `git-init.adoc` and `git.adoc`.
- **New config key**: `init.defaultObjectStorageFormat`, documented in `config/init.adoc`.
- **New environment variables**: `GIT_OBJECT_STORAGE_FORMAT` (overrides config) and `GIT_DEFAULT_OBJECT_STORAGE_FORMAT` (sets the default for new repositories).
- **Precedence**: Command-line > `GIT_OBJECT_STORAGE_FORMAT` > repository state > `GIT_DEFAULT_OBJECT_STORAGE_FORMAT` > `init.defaultObjectStorageFormat` > `files`.
- **Repository format version bump**: `core.repositoryformatversion` is set to `1` if the object storage format is non-default (even for `files` with a payload), ensuring older Git versions can detect repository extensions.
- **Submodule restriction**: Submodules inherit the parent repository’s `type` but **not the payload** (e.g., `files://objs` becomes `files`), matching the ref storage backend’s behavior.
- **Error handling**: Invalid formats (e.g., `--object-storage-format=garbage`) are rejected with clear error messages. Reinitializing a repository with a mismatched storage format or payload is also rejected.
- **Tests**: The patch adds comprehensive tests in `t0001-init.sh`, covering initialization, environment variable overrides, payload handling, error cases, and reinitialization. Tests verify that `GIT_OBJECT_DIRECTORY` takes precedence over the payload, that relative and absolute paths work, and that the `files` backend with a payload relocates the objects directory (e.g., `.git/objs` instead of `.git/objects`).

**Files touched:**
- `builtin/init-db.c`, `builtin/clone.c`: Add `--object-storage-format=` option and pass it to `create_repository()`.
- `setup.c`, `setup.h`: Extend `repository_format_configure()`, `create_repository()`, and `initialize_repository_version()` to handle the object storage format.
- `refs.c`: Update `repo_migrate_ref_storage_format()` to propagate the object storage format during ref storage migration.
- `Documentation/config/init.adoc`, `Documentation/git-init.adoc`, `Documentation/git.adoc`: Document the new option, config key, and environment variables.
- `t/t0001-init.sh`: Add tests for initialization, environment variables, payload handling, and error cases.

**Design consistency:** The patch aligns with the ref storage backend’s design, including the `(type, payload)` split introduced in v3, precedence rules, and submodule payload restrictions. The implementation is **non-controversial** and follows the feedback from Karthik Nayak’s earlier reviews. The only open question from the thread (path normalization) is deferred, as the current implementation accepts relative paths.

This patch is **ready for review**, with the primary focus on the mechanical changes to support the new option and its integration with the existing repository initialization logic. No new design questions are introduced.

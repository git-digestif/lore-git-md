This is a substantive review comment on the RFC/PATCH that proposes making Git honor file permission bits when writing config files. Patrick Steinhardt raises a fundamental design question: why treat config files specially when Git's lockfile mechanism is used broadly across the codebase? He suggests that if permission checks are important, they should be implemented centrally in `lockfile.c` rather than just in the config subsystem.

The observation is sharp and well-placed. The current patch adds the `access(2)` check only in `repo_config_set_multivar_in_file_gently()`, but Git uses lockfiles for reflogs, index files, object databases, and other critical data. If the goal is to prevent accidental overwrites of read-only files, the same logic should arguably apply everywhere. Implementing this in `lockfile.c` would make the behavior consistent and avoid duplicating the permission check in every subsystem.

This isn't a rejection of the patch's goal—Patrick explicitly calls the idea "sensible"—but a challenge to its scope. The question is whether this is a config-specific fix or the first step toward a broader change in how Git handles file permissions. The answer could affect the patch's complexity, test coverage, and long-term maintenance burden.

No counterproposal or alternative implementation is offered yet, but the comment shifts the discussion from "should we do this?" to "how should we do this?" If the thread moves toward a centralized solution, the patch as written may need significant reworking or even replacement. For now, this remains an open design question rather than a technical flaw in the current implementation.

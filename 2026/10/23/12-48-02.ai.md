This is the third patch in Patrick Steinhardt’s six-patch v2 series restoring dynamic reloading of alternate object databases in the files-based ODB backend. It implements the core fix: when an object lookup fails, the backend now reloads the alternates file and retries the lookup. This restores behavior accidentally broken in March 2026 during the ODB abstraction effort (commit 5946a564cd).

The patch modifies `odb_source_files_read_object_info()` in `odb/source-files.c` to call `prepare_alternates()` on retry and introduces a `tail` pointer to track newly added directories, ensuring only those are rescanned. It also updates `odb_files_dir_is_usable()` to handle the case where no alternates existed before reloading, which can occur when a quarantine directory is active. The test in `t/t1006-cat-file.sh` verifies the fix by simulating a concurrent alternates update: an object initially missing becomes available after the alternates file is rewritten.

The commit message acknowledges a performance regression (lookup time for 20k missing objects increases from ~185ms to ~293ms) but notes this is unavoidable—restoring the broken behavior requires more work. The regression is addressed in subsequent patches (4-6), which bring performance back to near-baseline levels. The fix is narrowly scoped to the primary object directory and does not attempt to handle recursive alternates, an edge case the commit message explicitly states was never supported.

This patch is uncontroversial and well-motivated, with clear test coverage and performance data. It directly addresses the regression and the behavioral issue in `git receive-pack` (resolved in patch 2). The changes are confined to the files-based ODB backend and do not affect other subsystems. Key symbols introduced or modified include `tail` (a pointer to track new directories) and the retry logic in `odb_source_files_read_object_info()`. The patch is ready for final review.

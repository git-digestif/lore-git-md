This is a CI/build system patch that has sparked a maintainer-level policy discussion. Junio responds to Taylor Blau’s patch—which pins GitHub Actions in the main CI workflow to full commit SHAs rather than version tags—by questioning whether Git’s upstream workflow should accommodate downstream organizations’ security policies at all.

Junio’s reply is skeptical of the motivation. He argues that Git’s workflow should not be shaped by the constraints of external organizations, especially when those constraints could lead to conflicting preferences (e.g., another organization might prefer readable tags). Instead, he suggests that organizations requiring commit-level pinning should maintain those changes in their own forks, noting that dependency updates (like moving from `checkout@v6` to `checkout@v7`) would cause merge conflicts either way—effectively forcing downstream maintainers to resolve them manually.

The tone is measured but firm: Junio is not rejecting the patch outright, but he is pushing back on the premise that Git’s CI should prioritize one set of downstream requirements over others. The implication is that if this change lands, it could set a precedent for similar requests, complicating Git’s CI maintenance without clear benefit to the project itself. No technical objections are raised; this is purely a policy and maintainability concern.

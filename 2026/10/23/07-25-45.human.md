This is part 3 of the ongoing SHA-1/SHA-256 interoperability effort, specifically implementing **pack index v3** support. The series is a collaboration between Christian Couder and brian m. carlson, building on brian's earlier work to enable Git repositories to operate with both hash algorithms simultaneously.

The core goal here is to extend Git's pack index format (which maps object IDs to their locations in packfiles) to store object IDs in *both* the repository's primary hash algorithm *and* its compatibility algorithm. This mirrors the loose-object mapping system already implemented in earlier parts of the interoperability work. Without this, packed objects cannot be reliably translated between hash algorithms, breaking operations like fetches or clones between repositories using different hash functions.

The series is **13 patches long** and touches nearly every layer of Git's object storage system. Patches 1-5 lay plumbing by adding generic ODB (object database) functions to map and write object IDs between algorithms, with implementations for the loose and packed backends. Patches 6-12 implement the v3 index format itself: writing it during `git pack-objects` and `git index-pack`, reading it during object lookups, and ensuring the mappings are used when resolving object IDs. Patch 13 documents the new format in `gitformat-pack(5)`.

Christian's contributions are substantial. He added a **new patch (10/13)** that validates v3 index tables for corruption, fixing edge cases like division-by-zero, out-of-bounds reads, and duplicate format entries. He also improved the duplicate-object detection in v3 indices (patch 6), fixed compatibility-algorithm handling in `git hash-object` (patch 8), and ensured that older index versions (v1/v2) are correctly skipped when mapping objects (patches 11-12). The series now includes **11 new tests** across `t1016`, `t5308`, and `t5313` to verify behavior with v3 indices, including edge cases like abbreviated object IDs and large-file streaming.

The work is **well-motivated and technically sound**. The commit messages are detailed, explaining not just *what* is changed but *why*, and the code is careful to maintain backwards compatibility (v3 indices are opt-in for now). The series is part of a larger effort that has already seen two prior parts merged, and this iteration addresses feedback from Junio on the v1 submission. The only missing pieces are automatic v3 index selection (planned for later) and protocol support, but those are explicitly out of scope here.

If you care about SHA-256 support or cross-algorithm interoperability, this is **worth reviewing**. The changes are invasive but necessary, and the series is in good shape for merging once the remaining loose ends (like alternates reloading) are addressed.

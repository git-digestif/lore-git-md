This is a bugfix proposal targeting the config subsystem, specifically addressing the issue where Git ignores filesystem permission bits when writing configuration files. Junio C Hamano responds to Patrick Steinhardt’s substantive review, which questioned why config files should be treated specially compared to other lockfile users (e.g., reflogs, index files).

Junio clarifies that the motivation for this patch is narrow: it only affects out-of-tree config files like `$HOME/.gitconfig` and XDG counterparts, which are uniquely exposed to user permission changes. In-tree files (e.g., `.git/index`) are not a concern because users have no reason to "protect" them from Git, and the `.git/objects/` hierarchy’s read-only bits serve a different purpose (preventing accidental overwrites by external tools). He acknowledges that `/etc/gitconfig` on multi-user systems *could* face the same issue but notes it’s irrelevant in practice because the directory itself is typically read-only for regular users.

The response also explains the patch’s scope: it was intentionally limited to the config subsystem’s caller-side API to avoid the significant effort of auditing all lockfile users. This suggests the patch is a pragmatic, minimal fix rather than a broad architectural change. However, Junio does not directly address whether centralizing permission checks in `lockfile.c` (as Patrick suggested) would be desirable or feasible—only that it was beyond the current scope.

The patch itself remains well-motivated and well-tested, with clear test coverage for read-only config files. The open question is whether the community will accept this targeted approach or push for a more comprehensive solution. For now, the patch looks like a sensible fix for a real usability issue, but its future may depend on whether others agree with Patrick’s architectural concern.

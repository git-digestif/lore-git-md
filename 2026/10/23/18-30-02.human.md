This is a maintainer feedback message on the RFC patch adding `--merged` and `--no-merged` filters to `git worktree list`. Junio C Hamano raises a fundamental design question about the patch's scope and approach.

Junio suggests the current implementation unfairly narrows the problem by focusing only on merged branches, when the real need is broader: users often want to filter worktrees by the branch they check out, regardless of merge status. He proposes an alternative primitive, `--branch=<name>`, which could be specified multiple times and would subsume the `--merged`/`--no-merged` use case with minimal extra code. His example shows how this could reuse existing `git branch --contains` machinery via shell plumbing.

The message is not a rejection but a design-level critique. It shifts the discussion from "should we add these filters?" to "what is the right primitive for filtering worktrees by branch?". The patch's current implementation is not reviewed on its technical merits; instead, Junio questions whether the feature as proposed is the most flexible and future-proof approach. This is likely to prompt a rethink of the patch's direction before further review.

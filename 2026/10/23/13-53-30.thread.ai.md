Subject: [PATCH] apply: fix regression in pure-rename patch series with core.fileMode=false
Series version: standalone patch (no series)
Originating author: Hannes Brandstätter-Müller
Thread type: bug report with fix

Core problem or goal
A regression in `git apply` causes patch series containing a pure rename followed by an edit to fail when `core.fileMode=false` is set. The error is `error: renamed: wrong type`. The regression was introduced between Git 2.44.0 and 2.45.0, likely by commit 0482c32c33 ("apply: ignore working tree filemode when !core.filemode, 2023-12-26").

Current status
Under review. The patch is a proposed bugfix with a regression test. No prior versions exist. The broader test suite (`t41*` and `t42*`) passes with both the original and Aniket Gupta’s refined fix. Junio C Hamano’s fundamental question about whether the scenario (a pure rename followed by a type-changing patch) is valid input or corrupt data has been resolved: Aniket confirms the scenario is valid, produced by `git format-patch`, and not corrupt. Junio’s concern about the refined fix’s behavior under reverse application has also been addressed: Aniket reports the refined fix behaves identically to the unpatched code when applied in reverse (`-R`). Junio’s final technical question—whether the two patches (pure rename and edit) are applied in a single `git apply` invocation or as two separate invocations (or via `git am`)—has now been answered: Aniket confirms the bug reproduces in all three workflows, and that this was previously supported behavior. No explicit maintainer approval or rejection has been given.

Key technical details
- Subsystem: `apply.c`, specifically the `check_preimage()` function.
- Root cause: a pure rename leaves `previous->new_mode` as zero, causing a later edit to fail a file-type comparison.
- Original fix: fall back to `patch->old_mode` when `previous->new_mode` is zero.
- Refined fix: mask `patch->old_mode` to `07777` (permission bits only) and explicitly set the file type to `S_IFREG`, preventing a malicious patch from changing a regular file into a symlink when `core.fileMode=false`.
- Junio’s concerns: (1) whether the scenario is valid input (resolved: valid), (2) whether the refined fix behaves correctly in reverse (resolved: it does), and (3) whether the two patches are applied in a single invocation or separately (resolved: all workflows are supported and previously worked).
- Test coverage: new regression test added; existing `t41*` and `t42*` test suites pass with both fixes.
- On-disk format: unchanged.
- CLI: unchanged.
- New symbols: none.

This is a maintainer feedback email on the RFC patch adding `--merged` and `--no-merged` filters to `git worktree list`. Junio C Hamano suggests reconsidering the design approach entirely, proposing a more general `--branch` filter primitive instead of the specific `--merged`/`--no-merged` options.

Junio argues the current implementation unfairly narrows the problem space, noting that even users who don't follow a one-worktree-per-topic workflow would benefit from filtering worktrees by branch. He proposes a more flexible `--branch` option (accepting multiple values) as a better foundation, which could then be combined with existing branch-filtering commands like `git branch --contains` to achieve the same merged/unmerged functionality without adding new code. The example command demonstrates how this would work in practice.

The feedback is substantive and technical, questioning the fundamental design rather than implementation details. It suggests the current patch may be solving a specific use case at the expense of broader utility. No integration branch assignment or merge status is mentioned, and the thread remains in RFC stage with open design questions. The proposal would require significant rework if accepted, though Junio hasn't explicitly rejected the current approach - just offered an alternative direction.

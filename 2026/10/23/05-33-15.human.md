This is the fifth patch in Patrick Steinhardt’s seven-patch series introducing the `extensions.objectStorage` mechanism, which enables pluggable object database backends in Git. The patch adds user-facing configuration (`init.defaultObjectStorageFormat` and `GIT_DEFAULT_OBJECT_STORAGE_FORMAT`) and CLI support (`--object-storage-format` for `git init`), completing the baseline infrastructure for the feature.

Patrick’s reply to Karthik Nayak’s review clarifies two key design choices. First, even the `files` backend with a payload (e.g., `files://objs`) requires `core.repositoryformatversion=1` because repository extensions are ignored in v0 repositories. This ensures the configuration is respected but may attract discussion about whether it’s overly conservative. Second, the redundant `else if (reinit)` block in `setup.c`—which Karthik noted could be removed—is kept for symmetry with the ref storage logic: it handles the edge case where a repository explicitly configures the default backend (`files`) and later reinitializes, downgrading the format version and unsetting the extension. Patrick acknowledges the lack of a test for this case but doesn’t treat it as blocking.

The more significant update is Patrick’s decision to refactor the internal representation of the object storage format to match the ref storage backend’s approach: splitting the URI into a backend type and payload (e.g., `files` + `objs` instead of `files://objs`). This change, which he plans to send in a follow-up, aims to simplify normalization and reduce redundant URI parsing. While not part of this patch, it signals a shift in the series’ implementation strategy that may affect later patches.

The patch itself is mechanically sound and uncontroversial, but the discussion reveals ongoing design refinements. The series remains under review, with Karthik’s conditional approval still standing. Busy readers can focus on the follow-up for the refactoring, as it may introduce subtle changes to the configuration handling.

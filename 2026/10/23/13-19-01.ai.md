This is the first patch in a two-patch bugfix series (v2) targeting Git’s hook configuration system, explicitly framed as a **behavior change** rather than a bugfix. The patch aligns the behavior of `hook.<event>.enabled` with its documentation by making it disable *both* config-defined hooks and the traditional hook in the hooks directory (e.g., `.git/hooks/pre-commit`). Previously, the setting only disabled config-defined hooks, creating a discrepancy with the documentation’s broader wording ("no hooks fire for that event").

The implementation touches `builtin/hook.c`, `hook.c`, and `hook.h`, primarily adjusting how the `event_disabled` flag is set and checked. The `struct hook` now has a unified `event_disabled` field (replacing the previous `u.configured.event_disabled`), which is set for both traditional and configured hooks. The test suite (`t/t1800-hook.sh`) expands coverage to verify the new behavior, including edge cases like `hook_exists()` checks and `git commit` interactions. Documentation in `hook.adoc` is updated to explicitly state that the setting applies to both hook types.

The patch acknowledges a backward-compatibility trade-off: users who relied on the old behavior (where `hook.<event>.enabled=false` left the hookdir hook untouched) will see a change. The v2 revision incorporates feedback from Adrian Ratiu (original author of `hook.<event>.enabled`) and Junio, framing the change as intentional to resolve the ambiguity. No technical objections have been raised, but the thread remains open for broader community input on the compatibility implications.

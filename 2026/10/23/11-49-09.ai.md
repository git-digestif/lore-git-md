This is the **v3 revision of the object storage extension series**, a major architectural effort led by Patrick Steinhardt to make Git’s object database pluggable. The series introduces the `extensions.objectStorage` configuration mechanism, modeled after the existing ref storage extension, and implements the baseline `files` backend with support for relocating the `.git/objects` directory via a payload (e.g., `files://objs` moves objects to `.git/objs`).

The key change in v3 is a **major refactoring** to split the object storage format URI into separate `(type, payload)` components, mirroring the ref storage backend’s design. This simplifies normalization (e.g., `files` vs `files://`), reduces URI re-parsing, and improves consistency with the ref backend. The refactoring affects nearly every patch in the series, replacing the previous string-based `object_storage_format` field in `struct repository` with an `enum object_storage_format` and a separate `object_storage_payload` string. This change is motivated by maintainability and aligns with Karthik Nayak’s earlier feedback about test readability and design consistency.

The series is now **functionally complete** and includes all planned features: configuration via `extensions.objectStorage`, environment variable overrides (`GIT_OBJECT_STORAGE_FORMAT` and `GIT_DEFAULT_OBJECT_STORAGE_FORMAT`), command-line options (`--object-storage-format=` for `git clone`, `git init`, and `git submodule`), and inspection tools (`git rev-parse --show-object-storage-format` and `git repo objects.storageFormat`). Submodule support is fully implemented, ensuring that submodules inherit the parent repository’s object storage configuration. The local clone restriction (disabling hardlinking or copying objects when either the source or destination uses a non-default storage format) remains in place as a temporary measure to avoid complexity.

The refactoring introduces some intentional restrictions: submodule clones no longer propagate payloads (e.g., `files://objs` becomes `files`), matching the ref storage backend’s behavior. This is a deliberate design choice to ensure consistency between the two extensions. The series also bumps `core.repositoryformatversion` to `1` whenever `extensions.objectStorage` is set, even for the `files` backend with a payload, to ensure repository extensions are readable by older Git versions.

The implementation is **technically sound** and follows established patterns for ref storage. Karthik Nayak’s conditional approval of v2 (contingent only on Patrick’s discretion regarding a minor cleanup) still applies, as the refactoring does not introduce new design questions or regressions. The series is **ready for review**, with the primary focus now on the mechanical changes introduced by the split `(type, payload)` representation. No new open questions or loose ends are introduced in v3.

Files touched include `odb/`, `setup.c`, `repository.c`, and `builtin/` commands (`clone.c`, `init-db.c`, `submodule--helper.c`, `rev-parse.c`, `repo.c`). Documentation is updated across `git-{clone,init,submodule,repo,rev-parse}.adoc` and new files like `object-storage-format.adoc`. Tests cover initialization, cloning, submodule propagation, schema validation, environment variable overrides, and error cases. The series is built on top of the merged prerequisite topics `ps/odb-files-alternates` and `ps/setup-enforce-repo-passed-to-create-repository-has-no-state`.

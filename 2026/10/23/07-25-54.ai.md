This is the **pack index v3 reading support** patch, part of the ongoing SHA-1/SHA-256 interoperability effort. It is the ninth patch (9/13) in Christian Couder’s series, building on the earlier ODB mapping infrastructure and v3 writing support already posted.

The patch teaches Git to read the new pack index v3 format, which stores object IDs in both the main and compatibility hash algorithms. The core change is a new binary search function (`bsearch_hash_v3`) that handles the v3 layout: a variable-length header, short-name tables for each algorithm, and a mapping from short-name order to pack order. The patch also extends the `packed_git` structure with per-algorithm offsets (`data_offset`, `full_oid_offset`, `order_map_offset`) so that lookups do not need to recompute them. The revindex generation logic is updated to use the order map for the requested algorithm, ensuring that offsets are resolved correctly regardless of which hash space the caller is using.

Key technical details: the patch makes the `crc_offset` field 64-bit to accommodate large packs, adds a new helper `nth_packed_object_pack_order_algop()` to translate between pack order and algorithm-specific order, and updates `load_idx()` to parse the v3 header and validate its size. The test suite (`t5302-pack-index.sh`) is extended to generate and verify v3 indices, and the existing v1/v2 tests are conditionally disabled when a compatibility hash algorithm is in use (since the old formats cannot represent SHA-1 values).

The implementation is careful to maintain backwards compatibility: v1 and v2 indices continue to work exactly as before, and the new code paths are only triggered when `p->index_version == 3`. The patch does not yet enable v3 by default or add support for `git show-index`; those are deferred to later parts of brian’s series. Reviewers may want to focus on the header parsing logic (especially the 4-byte padding assumptions) and the thread-safety of the new `packed_git_format` fields.

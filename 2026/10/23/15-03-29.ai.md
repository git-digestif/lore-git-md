This is the first patch in Phillip Wood’s seven-patch refactoring series `pw/stash-optimize-check_changes-calls/v4`, now cooking in `next`. It introduces `enum create_result` to replace the integer return type of `do_create_stash()`, distinguishing between success (`CREATE_SUCCESS`), errors (`CREATE_ERROR`), and cases where no changes were stashed (`CREATE_EMPTY`). The patch also fixes a minor behavioral anomaly: `create_stash()` previously exited with status 1 when `do_create_stash()` returned 1 (indicating no changes), even though `create_stash()` itself had already determined there were no changes via `check_changes()`. Now, `create_stash()` exits 0 in this case, aligning with its documented behavior.

The changes are confined to `builtin/stash.c` and touch five functions: `do_create_stash()`, `stash_staged()`, `stash_patch()`, `create_stash()`, and `do_push_stash()`. The patch replaces `if/else` chains with `switch` statements to handle the new enum values, a stylistic choice resolved in favor of Junio’s preference during the v4 discussion. The enum explicitly assigns `CREATE_SUCCESS = 0`, and helper functions initialize their return values to `CREATE_SUCCESS` instead of `0`, improving code clarity. No performance changes are introduced here—this patch lays the groundwork for the subsequent optimizations in the series.

The patch is purely mechanical and well-motivated, with no user-visible behavior changes beyond the exit-status correction. The commit message clearly explains the anomaly and the rationale for the enum. Junio’s feedback on this patch was surface-level (stylistic tweaks), and all requested changes have been incorporated. The series as a whole is on track for `master` unless integration issues arise.

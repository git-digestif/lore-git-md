This is a bugfix patch for the object database (ODB) transaction layer, addressing a data-loss scenario in repositories configured with compatibility hashes (e.g., SHA-1/SHA-256 interop) and batch fsync of loose objects. The issue occurs during temporary object directory migration, where the "loose-object-idx" file—a mapping between objects and their compatibility hashes—fails to merge with an existing index in the primary object directory, causing the transaction to abort. The patch introduces a new function, `loose_object_idx_merge()`, which appends new mapping entries to the primary index instead of overwriting it, preserving both old and new entries.

Patrick Steinhardt’s review raises several technical points but broadly endorses the approach. He questions the locking strategy (indefinite blocking with `-1` timeout), suggests a safer pattern for file updates (write to a new file under lock, then rename), and asks whether the merged index should validate for duplicate object IDs. He also notes that the file format’s unsorted nature might complicate readers, though this is treated as an existing constraint. The review is substantive, engaging with the patch’s design and edge cases, but does not identify any show-stopping flaws.

The patch itself is well-crafted: it includes a clear commit message explaining the problem, design rationale, and alternatives considered, along with a regression test in `t/t1016-compatObjectFormat.sh`. The fix is narrowly scoped to the compatibility-hash feature, so it won’t affect users who don’t enable that extension. While Patrick’s feedback suggests minor refinements (e.g., locking, file-writing patterns), the core logic appears sound and addresses a real bug rather than a theoretical edge case. This is a targeted, high-quality contribution to the ODB abstraction effort, and the discussion so far suggests it’s likely to land with modest adjustments.

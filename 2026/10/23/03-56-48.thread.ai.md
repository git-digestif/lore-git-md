Subject: [PATCH] diff-delta: use safe integer helpers for allocation size calculations
Series version: standalone patch (v6)
Originating author: Srujith A. Poojary (Outreachy contributor)
Thread type: bugfix patch

Core problem or goal
Replace manual integer arithmetic in `diff-delta.c:create_delta_index()` with the safe integer helpers `st_mult()`, `st_add()`, and `st_add3()` to prevent silent overflows during allocation size calculations. The patch was initially justified by a theoretical overflow risk under 8-byte struct padding assumptions, but this justification has been challenged by Pablo Sabater, who argues the arithmetic in the commit message overestimates the risk and that the actual bounds make overflow implausible under real-world conditions.

Current status
v6 posted, correcting the factual error in the v5 commit message (misidentifying `st_add3()` instead of `st_mult()` for the `(hsize + 1)` argument). The central question—whether the patch should proceed as a precautionary measure—is now contested. Pablo Sabater’s substantive review refutes the theoretical overflow risk, calling the patch’s motivation into question while acknowledging the code itself is correct. No merge status; still under active review.

Key technical details
- File: `diff-delta.c`
- Function: `create_delta_index()`
- Symbols: `st_mult()`, `st_add()`, `st_add3()` (safe integer helpers), `unpacked_index_entry`, `packed_index_entry`
- Subsystem: delta compression
- On-disk format: unchanged
- Test coverage: none added by this patch; existing tests exercise the code path
- Bounds check: `if (bufsize >= 0xffffffffUL) entries = 0xfffffffeU / RABIN_WINDOW;` caps `entries` at 268,435,455 and `hsize` at 67,108,864 (2²⁶), ensuring `hsize + 1` cannot overflow
- Overflow risk: Pablo Sabater’s analysis shows `struct unpacked_index_entry` is 12 bytes on 32-bit systems (no padding), and the allocation `4 * hsize + 16 * entries` cannot exceed 2³² under the actual bounds. The original justification’s padding assumption (16 bytes) and lower bounds (1,048,575 for `entries`) are incorrect.
- Justification requirements: Junio’s demand for transparent arithmetic is now met by both the v6 commit message and Pablo’s counter-analysis. The focus has shifted from accuracy of the arithmetic to whether the theoretical risk (or future-proofing) justifies the patch.

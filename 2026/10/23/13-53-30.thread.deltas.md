# Thread deltas

## 2026/10/23

- [2026/10/23/13-53-30 by Hannes Brandstätter-Müller <hannes.mueller@gmail.com>] Hannes Brandstätter-Müller reported that `git apply` fails with "error: renamed: wrong type" when applying a patch series containing a pure rename followed by an edit under `core.fileMode=false`, reproduced on Git for Windows 2.55.0, source-built v2.45.0, and master (7e34d8174) but not on v2.44.0 or Ubuntu's Git 2.34.1, and noted a possible relation to commit 0482c32c33.
- [2026/10/23/13-53-30 by Hannes Brandstätter-Müller <hannes.mueller@gmail.com>] He diagnosed that in `check_preimage()` a pure rename leaves `previous->new_mode` as zero, causing the later edit to fail the file-type comparison.
- [2026/10/23/13-53-30 by Hannes Brandstätter-Müller <hannes.mueller@gmail.com>] He attached a tentative fix with a regression test that falls back to `patch->old_mode` when `previous->new_mode` is zero, reporting that tests passed for both regular and executable files without a mode warning, the new regression test failed without the fix and passed with it, and the t41*/t42* suites completed with 1,524 passed, no failures, and 12 known breakages, while requesting review of both the diagnosis and the proposed change.

## 2026/11/06

- [2026/11/06/18-11-45 by Aniket Gupta <aniketgupta3001@gmail.com>] Aniket Gupta reproduced the bug and noted that taking the whole mode from patch->old_mode also takes the file type, so the "wrong type" check can no longer fail; he demonstrated that with core.fileMode=false a hand-made patch describing a renamed regular file as a symlink would be applied and turn the file into a symlink, and proposed using S_IFREG | (patch->old_mode & 07777) instead, which passed his test and the other apply tests.
- [2026/11/06/20-36-07 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano asked why the input patch talks about exactly the same path twice, questioning whether this is valid patch input or bending the tool to cope better with corrupt input, and asked whether the proposed S_IFREG | (patch->old_mode & 07777) approach would work equally well when applying the patch in reverse.

## 2026/11/07

- [2026/11/07/04-07-15 by Aniket Gupta <aniketgupta3001@gmail.com>] Aniket Gupta clarified that the series in Hannes's report is valid input matching what format-patch produces for a rename commit followed by an edit commit, and retracted his earlier symlink example as hand-made and invalid, saying it only demonstrated that the type check no longer fires; he also reported that reverse-applying the series with -R works the same with and without the fix for both plain and executable files.
- [2026/11/07/05-25-25 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano questioned whether applying two patches in a single "git apply" invocation is intended, saying he would understand two separate invocations or "git am" fed two input files.
- [2026/11/07/05-47-01 by Aniket Gupta <aniketgupta3001@gmail.com>] Aniket Gupta confirmed the report involves two commits fed as one format-patch output to a single git apply, noting that applying several patches touching the same path in one invocation is something git apply does on purpose, and that a pure rename followed by an edit worked that way before 0482c32c33 and still works with core.fileMode=true, breaking only with core.fileMode=false.

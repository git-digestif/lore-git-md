This is the **fourth patch in v5 of a six-patch performance feature** introducing an **incremental connectivity check** for Git fetches and pushes. The patch adds the `transfer.connectivityCheck` configuration option, which will later support `full`, `incremental`, and `auto` modes, though only `full` is implemented here. This is **plumbing work** that prepares the infrastructure for the incremental check (patch 5/6) and auto mode (patch 6/6).

The patch wires up the config key in `connected.c`, which reads the value and passes it to `git rev-list` via a new internal flag `--connectivity-check=<mode>`. The `rev-list` side parses the flag and stores the mode in a new `struct connectivity_check` field. For now, the only valid mode is `full`, matching the existing behavior; unknown values fall back to `full` with a warning, ensuring forward compatibility. The config documentation (`Documentation/config/transfer.adoc`) and `rev-list` flag documentation (`Documentation/rev-list-options.adoc`) are updated to reflect the new options, with the flag marked as internal.

The implementation is **clean and self-contained**, touching only the necessary files (`connected.c`, `builtin/rev-list.c`, and documentation). The config plumbing is straightforward: `connectivity_check_mode()` reads the config, validates the value, and formats the flag for `rev-list`. The `rev-list` side adds a new enum and parser for the mode, but no behavior change yet. The patch **explicitly passes the mode** to `rev-list`, which will allow future optimizations to be scoped to connectivity checks.

This patch is **well-motivated** as a prerequisite for the incremental check, and the implementation is **minimal and correct**. The fallback behavior for unknown config values is conservative and safe. The only open question is whether the **1,000-commit cutoff** for auto mode (added in patch 6/6) will generalize, but that is addressed by making the cutoff configurable. The patch is **ready for integration** and has no known blockers.

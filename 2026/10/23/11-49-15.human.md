This is the sixth patch in Patrick Steinhardt’s **v3 object storage extension series**, which introduces pluggable object database backends for Git. This patch wires up the `--object-storage-format=` option in `git clone`, mirroring the functionality already added to `git init` in the previous patch.

The implementation is straightforward: the new option lets users specify an object storage backend (e.g., `files://objs`) when cloning, and the patch enforces a key restriction—**local clones (hardlinking or copying objects) are disabled if either the source or destination repository uses a non-default storage format**. If the user explicitly requests `--local`, the clone fails with an error; otherwise, it falls back to a non-local transport with a warning. This restriction is documented in the updated `git-clone` man page and justified as a temporary measure to avoid complexity with alternative backends.

The patch also includes thorough test coverage, verifying that the option works with payloads (e.g., `files://objs`), rejects invalid formats, and correctly handles the local-clone restriction. The tests confirm that the object storage format is properly propagated to the new repository and that bundle URIs remain compatible.

This is a **well-crafted, low-risk addition** to the series. The restriction on local clones is a pragmatic choice, and the implementation follows the established pattern for ref storage backends. No new design questions are introduced, and the patch aligns with the series’ goal of making object storage pluggable while maintaining backward compatibility. If the broader series lands, this will be a natural and expected feature for users.

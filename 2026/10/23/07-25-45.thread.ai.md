Thread identity: SHA-1/SHA-256 interoperability effort, part 3 – pack index v3 support. Series version: v2 (13 patches). Originating author: Christian Couder (based on brian m. carlson’s prior work). Thread type: patch series.

Core problem or goal: Implement pack index v3, a new index format that stores object IDs in both the main and compatibility hash algorithms, enabling bidirectional mapping between SHA-1 and SHA-256 repositories. This is the third installment in the interoperability effort; parts 1 and 2 (ODB infrastructure and loose-object mapping) are already merged to `master`.

The series consists of four logical groups: (1) ODB mapping infrastructure (patches 1–5, now complete), (2) pack index v3 writing (patches 6–8), (3) pack index v3 reading and validation (patches 9–12), and (4) documentation (patch 13). Key improvements over brian’s original branch include adaptation to Patrick Steinhardt’s `ps/odb-files-alternates` topic, strict duplicate detection, v3 index validation, and improved error handling. Patch 2/13 renamed `repo_add_loose_object_map()` to `source_add_loose_object_map()` to better reflect its parameter type; patch 3/13 adds a `flags` parameter to the same function, introducing the `OBJ_MAP_WRITE` flag (bit 6) to control whether mapped object IDs are written to disk. Patch 4/13 introduces the ODB mapping infrastructure with `odb_map_oid()` and `odb_write_oid_map()`, implementing them for the "files" backend (loose and packed sources). Patch 5/13 refactors `repo_oid_to_algop()` to use the new ODB mapping infrastructure (`odb_map_oid()`), removing 12 lines of manual lookup/reload logic and replacing it with a single call to `odb_map_oid(repo->objects, src, to, dest, 0)`. This centralizes mapping logic in the ODB layer, simplifying future extensions (e.g., packed-object support). Mappings are written only to the main object directory, and the "packed" sources currently return "not found" for both reading and writing, deferring full support until later patches. The `ODB_MAP_OID_RELOAD` flag forces a reload of the loose object map, while `ODB_WRITE_OID_MAP_WRITE` (aliased to `OBJ_MAP_WRITE`) controls disk writes.

Patch 6/13 implements **pack index v3 writing support**. It extends the `pack_idx_entry` structure to include `compat_oid` (for the non-native hash algorithm) and `idx` (the entry’s position in the pack), then teaches `write_idx_file()` to write the new v3 format. The patch adds a variable-length v3 header with format descriptors for each hash algorithm, specifying the offset and length of the short-name table. Short-name tables are padded to 4-byte boundaries to avoid unaligned access on some architectures. Strict duplicate detection is enforced in both the main and compatibility object ID spaces. The patch preserves the caller’s expectation that the `objects` array remains in pack order after writing, while internally creating temporary sorted copies for the v3 tables. Memory management is careful: temporary arrays are freed before returning, and the original `objects` array is re-sorted by object ID if needed (e.g., for bitmap code). The patch does not yet enable v3 by default or populate the `compat_oid` field; both are deferred to later patches.

Patch 7/13 implements **compatibility object ID population during indexing**. It teaches `git index-pack` and `git pack-objects` to compute and store the non-native hash algorithm’s object ID for each object, enabling bidirectional mapping. The patch extends the ODB mapping infrastructure to handle packed objects: for blobs, both hashes are computed in a single pass; for non-blobs, `convert_object_file()` remaps the object to the compatibility algorithm, storing the result in the loose object map (but not on disk) for dependent objects. A new mutex (`repo_mutex`) protects the loose object map from concurrent access during threaded indexing. Key changes include: `unpack_entry_data()` and `unpack_raw_entry()` now take a `compat_oid` parameter; `resolve_delta()` computes compatibility object IDs for delta-resolved objects; `create_object_entry()` in `pack-objects.c` maps object IDs upfront. Tests verify v3 index writing in compatibility repositories and strict duplicate detection.

Patch 8/13 **fixes a critical bug in the v3 index writing logic** for large blobs streamed directly into a pack. Without this patch, such blobs would silently store a null OID for the compatibility algorithm, breaking interoperability. The patch extends `odb_transaction_files_write_object_stream()` to initialize a second hash context for the compatibility algorithm, updates both contexts during streaming, and stores the resulting compatibility object ID in the pack index entry. The change is minimal and reuses existing streaming infrastructure, adding only the necessary extra work for the second hash. A new test in `t1016-compatObjectFormat.sh` verifies that a 5 KB file added in a compatibility repository is correctly stored and retrievable, with its object ID matching expectations. The patch touches `object-file.c` and introduces a new `compat_ctx` parameter to `stream_to_pack()`.

Patch 9/13 implements **pack index v3 reading support**. It teaches Git to read the new v3 format, which stores object IDs in both the main and compatibility hash algorithms. The core change is a new binary search function (`bsearch_hash_v3`) that handles the v3 layout: a variable-length header, short-name tables for each algorithm, and a mapping from short-name order to pack order. The patch extends the `packed_git` structure with per-algorithm offsets (`data_offset`, `full_oid_offset`, `order_map_offset`) so that lookups do not need to recompute them. The revindex generation logic is updated to use the order map for the requested algorithm, ensuring that offsets are resolved correctly regardless of which hash space the caller is using. The `crc_offset` field is made 64-bit to accommodate large packs, and a new helper `nth_packed_object_pack_order_algop()` translates between pack order and algorithm-specific order. `load_idx()` is updated to parse the v3 header and validate its size. The test suite (`t5302-pack-index.sh`) is extended to generate and verify v3 indices, and the existing v1/v2 tests are conditionally disabled when a compatibility hash algorithm is in use (since the old formats cannot represent SHA-1 values). The implementation maintains backwards compatibility: v1 and v2 indices continue to work exactly as before, and the new code paths are only triggered when `p->index_version == 3`.

Patch 10/13 adds **validation logic** to the pack index v3 loading code, ensuring that corrupt or maliciously crafted indices cannot cause out-of-bounds reads or other undefined behavior. The patch focuses on three areas: (1) **Header and table bounds checking** in `load_idx()`, verifying header length, format count, table offsets, short-name lengths, duplicate formats, trailer offset, and 4-byte alignment of order maps; (2) **Order map validation** in `nth_packed_object_pack_order_algop()`, checking that resolved pack-order positions are within bounds; and (3) **64-bit offset validation** in `create_pack_revindex()`, adding bounds checks before reading 8-byte offsets. The patch also updates `hash-lookup.c` to validate order map entries during binary search. A new test in `t5313-pack-bounds-checks.sh` verifies that an invalid order map entry (0xFFFFFFFF) is detected and rejected, with `git cat-file` and `git cat-file --batch-all-objects` both failing gracefully.

Patch 11/13 implements **packed-object mapping via pack index v3**. The patch teaches Git to look up packed objects in the compatibility hash algorithm when they are not found in the loose object map, using the new v3 index format that stores object IDs in both algorithms. The core change is in `odb/source-packed.c`, where `odb_source_packed_map_oid()` is updated to iterate through all packfiles, skip those with v1/v2 indices (which only store the main algorithm’s object IDs), and use `nth_packed_object_id_algop()` to retrieve the compatibility object ID from v3 indices. The new helper `nth_packed_object_id_algop()` extends the existing `nth_packed_object_id()` to handle cross-algorithm lookups, returning an error if the index lacks data for the requested algorithm. The patch also updates `packfile.c` to validate that both source and destination algorithms are supported by the v3 index before attempting a lookup. A new test in `t1016-compatObjectFormat.sh` verifies that packed objects are correctly mapped only when a v3 index is present: it creates a repository, repacks with a v3 index, removes the loose object map, and confirms that `git rev-parse` can still resolve the compatibility object ID. The test also checks that a v2 index (which lacks compatibility data) fails to provide a mapping, ensuring the code does not silently fall back to incorrect behavior.

Patch 12/13 enables **cross-algorithm disambiguation for packed objects**. The patch extends the ODB’s packed-object lookup logic to handle disambiguation across all supported hash algorithms (main and compatibility). The core change is in `odb/source-packed.c`, where `for_each_prefixed_object_in_pack()` is rewritten to loop over all supported algorithms and use the new `nth_packed_object_id_algop()` and `nth_packed_object_offset_algop()` helpers to read the correct tables from v3 indices. The logic skips unsupported algorithms and pre-v3 indices (which lack compatibility data). A new test in `t1016-compatObjectFormat.sh` verifies that abbreviated compatibility object IDs (e.g., `sha256:abcd1234...`) can be resolved from a v3 index, even after the loose object map is removed, while confirming that v2 indices fail gracefully. The patch also adds `nth_packed_object_offset_algop()` to `packfile.c`, a variant of `nth_packed_object_offset()` that takes an explicit algorithm parameter to ensure the correct offset table is used.

Patch 13/13 **documents the pack index v3 format** in `gitformat-pack.adoc`, moving the specification from the transitional `hash-function-transition.adoc` to its permanent home. The 75-line AsciiDoc section describes the v3 header (signature, version, format descriptors), per-algorithm tables (short-name, full-name, order-map, CRC, offset), alignment requirements, the `PSRC` key, and the order of algorithm storage. The original text is preserved in `hash-function-transition.adoc` for historical reference. This patch is documentation-only and does not alter code or on-disk formats.

Open questions and loose ends: (1) v3 index validation logic (patch 10) should be reviewed for the 4-byte alignment check for order maps and the clarity of error messages. (2) Memory usage during indexing: compatibility object IDs are kept in memory. (3) Index-pack cannot yet map objects whose dependencies (e.g., trees referenced by commits) are not already mapped. (4) Multi-pack-index does not yet support compatibility object IDs. (5) Automatic v3 selection and `show-index` support are deferred to later parts of brian’s series. (6) Bit choice for `OBJ_MAP_WRITE` (1 << 6) should be reviewed for potential conflicts with future object-type flags. (7) Reviewers may want to check the reload logic in `odb_source_files_map_oid()` and the decision to write mappings only to the main object directory. (8) The `flags` parameter in `odb_map_oid()` (currently `0` in patch 5) should be reviewed for correct usage in later patches (e.g., `OBJ_MAP_WRITE`). (9) Padding logic in v3 header and short-name tables (patch 6) may need review for correctness on unaligned-access architectures. (10) The decision to keep the `objects` array in pack order (patch 6) should be reviewed for compatibility with existing callers (e.g., bitmap code). (11) The choice to use the loose object map for temporary storage during indexing (patch 7) may be seen as a layering violation; the commit message justifies this as the simplest way to share state across threads. (12) Thread-safety guarantees in patch 7 (e.g., `repo_mutex` usage) should be verified. (13) Performance impact of computing compatibility hashes for all objects (patch 7) may need benchmarking. (14) The fix in patch 8/13 should be reviewed for completeness: does it cover all streaming paths (e.g., `git pack-objects --stdout`)? (15) Header parsing logic in patch 9 (especially 4-byte padding assumptions) should be reviewed. (16) Thread-safety of the new `packed_git_format` fields in patch 9 should be verified. (17) The bounds checks in patch 10 should be verified for completeness (e.g., negative values, edge cases). (18) Thread-safety of the new packed-object lookup logic in patches 11 and 12 (e.g., `odb_source_packed_map_oid()`, `for_each_prefixed_object_in_pack()`) should be reviewed, particularly the iteration over all packfiles. (19) The algorithm validation in `nth_packed_object_id_algop()` (patch 11) should be checked for correctness, especially the error handling when the index lacks data for the requested algorithm. (20) **Performance of cross-algorithm disambiguation** (patch 12): The algorithm loop adds overhead to disambiguation. The commit message notes the compiler will optimize this, but reviewers may ask for benchmarks if this path is hot. (21) **Thread safety of patch 12**: The new logic in `for_each_prefixed_object_in_pack()` appears safe (no shared state is modified), but this should be verified for multi-threaded contexts (e.g., `git index-pack`). (22) **Error handling in patch 12**: The patch returns `0` (success) if no objects match, which is consistent with existing behavior. Reviewers may check if this is the right choice for cross-algorithm lookups.

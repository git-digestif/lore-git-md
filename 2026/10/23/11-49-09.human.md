This is the third iteration of Patrick Steinhardt’s seven-patch series introducing the **object storage extension**, a major architectural change that makes Git’s object database pluggable. The series is now functionally complete and under active review, with no known blocking issues.

The key change in v3 is a **major refactoring** that splits the object storage format URI into separate `(type, payload)` fields, mirroring how the ref storage extension works. For example, `files://objs` is now stored as `type=OBJECT_STORAGE_FORMAT_FILES` and `payload="objs"`. This brings the two extensions into closer alignment, simplifies normalization, and reduces URI re-parsing. The trade-off is that submodule clones no longer propagate payloads (e.g., a parent repo with `files://objs` will create submodules with just `files`), but this is intentional for consistency.

The series touches core subsystems (`odb/`, `setup.c`, `repository.c`) and adds new user-facing features: `--object-storage-format=` for `git clone`/`init`/`submodule`, environment variables (`GIT_OBJECT_STORAGE_FORMAT`), and inspection tools (`git rev-parse --show-object-storage-format`). The `files` backend remains the only supported format, but it now allows relocating the `.git/objects` directory via the payload (e.g., `files://objs` moves objects to `.git/objs`). Local clones are disabled when either the source or destination uses a non-default object storage format, a temporary restriction documented in `git-clone.adoc`.

Tests cover initialization, cloning, submodule propagation, and error cases (e.g., invalid formats, reinitialization mismatches). The implementation is technically sound, following established patterns from the ref storage extension. Karthik Nayak has conditionally approved the series, pending Patrick’s discretion on minor cleanups (e.g., redundant `else if` blocks). The upcoming Git 3.0 release makes this a timely addition, as it aligns with the project’s broader push toward pluggable backends.

If you care about Git’s long-term architecture or work with large repositories, this series is worth tracking—it’s the foundation for future backends like cloud storage or databases. The refactoring in v3 resolves earlier design concerns, and the series is now in a state where it could plausibly merge soon.

Thread identity
Subject: [PATCH 0/7] rerere: remove implicit dependency on the_repository
Series version: v1 (initial, now complete)
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring)

Core problem or goal
Eliminate global state in Git’s `rerere` (reuse recorded resolution) subsystem by removing all dependencies on the global `the_repository` variable and bundling previously global variables into a dedicated `rerere_state` struct and a new `rerere_cache` struct. This is part of the ongoing, multi-year `the_repository` removal effort that aims to make every Git subsystem explicitly repository-aware rather than implicitly relying on a single global repository instance.

Current status
**Cooking in Junio’s integration branch.** The series is now complete; v1 posted 2026-10-22, with Junio C Hamano’s review of patch 7/7 posted on the same day. The series is based on Junio’s integration branch (8th batch, 2026-10-22) with Taylor Blau’s `tb/rerere-wait-for-merge-rr-lock` topic already merged in. No prior versions exist. Junio has queued the series for integration, signaling readiness for `next` or `master`.

Key technical details
- Files touched: `rerere.c` (482+ lines changed across the series), `rerere.h`, `builtin/rerere.c`, `hex.c`, `hex.h`, `repository.c`, `repository.h`, and their headers.
- New or renamed symbols: `rerere_state` struct (introduced in patch 1), `rerere_cache` struct (introduced in patch 6, finalized in patch 7), `repo_rerere_path()` helper (patch 1), cached result of `is_rerere_enabled()` (new `struct repository::rerere_cache_enabled` field, patch 4), explicit `struct repository *` parameters threaded through all internal static helpers in `rerere.c` (patch 2), `get_hash_hex_algop()` (promoted from static to public in `hex.h` in patch 5), `rerere_cache_setup()` (patch 7, replacing `setup_rerere()`), and `rerere_cache_release()` (patch 7, replacing `free_rerere_dirs()`). Global variables `rerere_autoupdate`, `rerere_dirs` strmap, `write_lock`, and the global `cache` are now fields of the `rerere_cache` struct (patches 6 and 7).
- Subsystems affected: `rerere` (primary), repository plumbing (minor), hex utilities (minor).
- On-disk format: unchanged.
- Test coverage: none added; the series is purely a refactoring with no new user-facing behavior.
- Patch 1 specifics: modifies `rerere_path()` to accept a `struct repository *` parameter, updates all callers in `rerere.c` and `builtin/rerere.c`, and fixes a latent inconsistency in `safe_create_dir_in_gitdir()` usage (to be fully addressed in a later patch).
- Patch 2 specifics: mechanically threads a `struct repository *` parameter through all internal static helpers in `rerere.c` that previously relied on the global `the_repository`. Functions modified include `scan_rerere_dir()`, `find_rerere_dir()`, `new_rerere_id_hex()`, `new_rerere_id()`, `handle_path()`, `git_rerere_config()`, and `is_rerere_enabled()`. Hash-algorithm references updated from `the_hash_algo` to `r->hash_algo`, and `safe_create_dir_in_gitdir()`/`repo_git_path()` calls now use the passed-in repository.
- Patch 3 specifics: removes redundant `repo_config()` calls in `git_rerere_config()` and `rerere_gc()`. The calls were redundant because all callers of `setup_rerere()` already invoke `repo_config()` beforehand, and they created a layering violation by potentially overwriting global config state that the caller may have manually modified.
- Patch 4 specifics: caches the result of `is_rerere_enabled()` in a new `struct repository::rerere_cache_enabled` field, eliminating redundant filesystem checks (`is_directory()`) and config lookups (`repo_config_get_bool()`). The field is initialized to `-1` in `initialize_repository()`, signaling that auto-detection is needed on first use. The global `rerere_enabled` variable and `GIT_PATH_FUNC()` for the rerere cache directory are removed, and the config reading for `rerere.enabled` is consolidated into `is_rerere_enabled()`.
- Patch 5 specifics: eliminates the last remaining calls in `rerere.c` that relied on `the_repository` by promoting `get_hash_hex_algop()` from a static helper in `hex.c` to a public function in `hex.h`. All callers in `rerere.c` are updated to pass the repository’s hash algorithm explicitly, replacing direct calls to `get_hash_hex()` and `parse_oid_hex()`. The `USE_THE_REPOSITORY_VARIABLE` define is removed from `rerere.c`, formally severing its link to the global repository.
- Patch 6 specifics: bundles the remaining global state—`rerere_autoupdate`, the `rerere_dirs` strmap, and the `write_lock`—into a new `struct rerere_cache` named `cache`. The lock timeout (`rerere_lock_timeout_ms`) is intentionally left as a local variable in `setup_rerere()` because it is only used there. All callers in `rerere.c` are updated to use the new `cache` instance, and the necessary `#include` directives are added to `rerere.h`.
- Patch 7 specifics: converts the global `rerere_cache` variable into an explicitly passed struct, completing the series’ goal. Introduces `rerere_cache_setup()` (replacing `setup_rerere()`) and `rerere_cache_release()` (replacing `free_rerere_dirs()`) to manage the cache’s lifecycle. All internal static helpers in `rerere.c` are updated to accept a `struct rerere_cache *` parameter, and callers in `builtin/rerere.c` are updated to use the new explicit cache management pattern. The lock file (`write_lock`) and `rerere_dirs` strmap are now fields of the cache struct, ensuring no state leaks between invocations. `rerere_gc_needed()` intentionally does not fully initialize the cache, as it only needs access to the `dirs` field, matching the previous behavior where it ignored the `rerere.enabled` setting.

Open questions and loose ends
- Junio C Hamano raised a minor design curiosity in patch 7/7: whether the `rerere_cache_enabled` field added to `struct repository` in patch 4/7 could have been replaced by the new `rerere_cache` struct. He acknowledged this may not be feasible, and the point is noted for future reference rather than as a blocker.
- The series assumes familiarity with the `the_repository` removal context; reviewers may still ask for additional motivation or examples of how the refactoring enables multi-repository workflows, though no such requests have been made yet.
- Careful review is still needed to ensure no regressions in `rerere`’s locking and caching mechanisms, which are subtle and easy to break. No specific concerns have been raised, but the mechanical nature of the refactoring warrants scrutiny.
- Patch 1’s latent inconsistency in `safe_create_dir_in_gitdir()` usage is noted but deferred to a later patch.
- Reviewers may verify that the caching logic in patch 4 correctly handles edge cases (e.g., repositories where rerere is disabled after being enabled earlier in the process).
- Patch 5’s promotion of `get_hash_hex_algop()` to public visibility may still draw scrutiny regarding API hygiene and whether the new explicit hash-algorithm passing introduces edge-case regressions, particularly in `is_rr_cache_dirname()` and the rerere garbage-collection logic.
- Patch 6’s mechanical reorganization of global state into `rerere_cache` may prompt questions about the struct’s lifetime management and whether the lock timeout should also be bundled into the struct for consistency, though no such questions have been raised.
- Patch 7’s explicit cache management pattern may raise questions about the cache’s lifetime and whether the new `rerere_cache_release()` function is always called in error paths, particularly in `builtin/rerere.c`. No specific concerns have been voiced yet.

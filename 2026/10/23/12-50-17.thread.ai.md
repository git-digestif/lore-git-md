Thread identity
Subject: [PATCH 0/7] rerere: remove implicit dependency on the_repository
Series version: v1 (initial)
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring)

Core problem or goal
Eliminate global state in Git’s `rerere` (reuse recorded resolution) subsystem by removing all dependencies on the global `the_repository` variable and bundling previously global variables into a dedicated `rerere_state` struct. This is part of the ongoing, multi-year `the_repository` removal effort that aims to make every Git subsystem explicitly repository-aware rather than implicitly relying on a single global repository instance.

Current status
Under review; v1 posted 2026-10-22. The series is based on Junio’s integration branch (8th batch, 2026-10-22) with Taylor Blau’s `tb/rerere-wait-for-merge-rr-lock` topic already merged in. No prior versions of this series exist.

Key technical details
- Files touched: `rerere.c` (344 lines changed across the series, including patches 1–4), `rerere.h`, `builtin/rerere.c`, `hex.c`, `repository.c`, `repository.h`, and their headers.
- New or renamed symbols: `rerere_state` struct, `repo_rerere_path()` helper (introduced in patch 1), cached result of `is_rerere_enabled()` (new `struct repository::rerere_cache_enabled` field, introduced in patch 4), and explicit `struct repository *` parameters threaded through all internal static helpers in `rerere.c` (patch 2).
- Subsystems affected: `rerere` (primary), repository plumbing (minor).
- On-disk format: unchanged.
- Test coverage: none added; the series is purely a refactoring with no new user-facing behavior.
- Patch 1 specifics: modifies `rerere_path()` to accept a `struct repository *` parameter, updates all callers in `rerere.c` and `builtin/rerere.c`, and fixes a latent inconsistency in `safe_create_dir_in_gitdir()` usage (to be fully addressed in a later patch).
- Patch 2 specifics: mechanically threads a `struct repository *` parameter through all internal static helpers in `rerere.c` that previously relied on the global `the_repository`. Functions modified include `scan_rerere_dir()`, `find_rerere_dir()`, `new_rerere_id_hex()`, `new_rerere_id()`, `handle_path()`, `git_rerere_config()`, and `is_rerere_enabled()`. Hash-algorithm references updated from `the_hash_algo` to `r->hash_algo`, and `safe_create_dir_in_gitdir()`/`repo_git_path()` calls now use the passed-in repository.
- Patch 3 specifics: removes redundant `repo_config()` calls in `git_rerere_config()` and `rerere_gc()`. The calls were redundant because all callers of `setup_rerere()` already invoke `repo_config()` beforehand, and they created a layering violation by potentially overwriting global config state that the caller may have manually modified.
- Patch 4 specifics: caches the result of `is_rerere_enabled()` in a new `struct repository::rerere_cache_enabled` field, eliminating redundant filesystem checks (`is_directory()`) and config lookups (`repo_config_get_bool()`). The field is initialized to `-1` in `initialize_repository()`, signaling that auto-detection is needed on first use. The global `rerere_enabled` variable and `GIT_PATH_FUNC()` for the rerere cache directory are removed, and the config reading for `rerere.enabled` is consolidated into `is_rerere_enabled()`.

Open questions and loose ends
- No design objections or requests for changes have been raised yet.
- The series assumes familiarity with the `the_repository` removal context; reviewers may ask for additional motivation or examples of how the refactoring enables multi-repository workflows.
- Careful review is needed to ensure no regressions in `rerere`’s locking and caching mechanisms, which are subtle and easy to break.
- Patch 1’s latent inconsistency in `safe_create_dir_in_gitdir()` usage is noted but deferred to a later patch.
- Reviewers may verify that the caching logic in patch 4 correctly handles edge cases (e.g., repositories where rerere is disabled after being enabled earlier in the process).

This is the **performance test patch (2/6)** in Kristofer Karlsson’s six-part series introducing an **incremental connectivity check** for Git fetches and pushes. The series is a well-motivated performance feature targeting large repositories, and this patch adds **baseline benchmarks** to measure the impact of the new incremental mode.

The patch creates a new performance test script (`t/perf/p5413-connectivity-check.sh`) and a Perl generator (`t/perf/generate-repo-p5413-connectivity-check.perl`) to create synthetic repositories. The benchmarks isolate the connectivity-check overhead by varying three dimensions independently: **total tree size** (5K–800K files), **incoming commit count** (1–10,000 commits), and **files changed per commit** (1–2,000 files). Each test runs `git rev-list --objects --stdin --not --all --quiet --exclude-promisor-objects`, the exact command the incremental mode will optimize, ensuring the benchmarks measure the right cost.

The design is careful and controlled: repositories are flat (no subdirectories), files are small and uniform, and the generator script uses `git fast-import` to avoid noise from pack transfer or index operations. The test script includes a `PERL` prerequisite and a usage comment in the generator, addressing prior feedback about missing documentation. The benchmarks are **repeatable and self-contained**, with each repository generated once and reused across runs.

This patch is **non-controversial and ready for integration**. It does not touch production code, only test infrastructure, and its purpose is clear: establish a performance baseline for the full connectivity check before the incremental mode is introduced. The benchmarks will be reused in later patches to demonstrate the speedup (up to 190x for small pushes to large repos) and the modest regression (1.5x for very long incoming histories) that the "auto" mode mitigates.

The patch is **well-executed and thorough**, with clear labels, good coverage of the parameter space, and a clean separation of concerns. It complements the rest of the series, which is effectively cleared for integration pending final sign-off. If you care about Git’s performance in large repositories, this series—and these benchmarks—are worth your attention.

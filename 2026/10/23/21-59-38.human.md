This is a bugfix/refactoring patch that eliminates spurious warnings when `remote.<name>.followRemoteHEAD` is loaded by commands that never use it (like `git push` or `git remote -v`). The patch defers validation until `git fetch` actually needs the setting, following the same pattern established by an earlier change (86129fd) for `fetch.followRemoteHEAD`.

Junio’s review of v2 is positive, noting only minor style issues: inconsistent indentation (spaces instead of tabs), a line that exceeds 80 columns in `builtin/fetch.c`, and space-before-tab whitespace errors in the test script. These are all surface-level nits that Colin has already acknowledged and plans to fix in v3. No substantive concerns remain.

The patch itself is clean and well-motivated. It replaces the parsed `follow_remote_head` and `no_warn_branch` fields in `struct remote` with a raw string and a seen flag, deferring parsing to a helper function that now accepts a variable prefix to tailor error messages. The `enum follow_remote_head_settings` has been moved to `fetch.c` since it is no longer referenced in `remote.c`. Test coverage in `t5510-fetch.sh` verifies lazy validation and error message clarity.

This looks like a straightforward improvement that addresses a persistent annoyance without breaking backward compatibility. The v2 iteration has resolved all substantive feedback from v1, and the remaining style nits are trivial. Unless a new issue surfaces in review, this patch is likely to be merged soon.

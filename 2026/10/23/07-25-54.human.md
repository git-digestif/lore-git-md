This is the ninth patch in Christian Couder’s 13-patch series implementing **pack index v3** for SHA-1/SHA-256 interoperability. It adds **reading support** for the new v3 index format, completing the write/read cycle begun in earlier patches.

The patch teaches Git to parse v3 indices, which store object IDs in both the main and compatibility hash algorithms. It generalizes the existing binary-search logic (`bsearch_hash`) to handle the v3 format’s dual-sorted tables (one per hash algorithm) and introduces a new helper, `bsearch_hash_v3`, to map between the short-name table and the full object ID list. The `packed_git` structure gains a `formats` array to track per-algorithm metadata (offsets, short-name lengths), and the `crc_offset` field is widened to accommodate large packs.

Key changes:
- `load_idx()` now accepts v3 indices, validating the header and populating the `formats` array.
- `bsearch_pack()` dispatches to `bsearch_pack_v3()` for v3 indices, which uses the algorithm-specific offsets stored in `formats`.
- `nth_packed_object_id()` and `nth_packed_object_offset()` handle v3’s dual-sorted layout, using the order map to translate between pack order and object-ID order.
- `create_pack_revindex()` is updated to read v3’s offset table, which is now stored after the CRC table.
- Tests in `t5302-pack-index.sh` are adjusted to skip v1/v2 tests when `COMPAT_HASH` is set (since those formats can’t represent compatibility object IDs) and add a new v3 test.

The patch is **well-crafted and incremental**, reusing existing infrastructure (e.g., `bsearch_hash_1`) and maintaining backward compatibility. The commit message clearly explains the design choices, such as storing per-algorithm metadata in `packed_git` and failing gracefully when an index lacks data for the requested algorithm. No performance regressions are expected, though v3 indices may use slightly more memory due to the additional metadata.

This is a **critical piece of the interoperability effort** and looks ready for review. The only likely points of discussion are edge cases around index validation (e.g., corrupt headers) and the decision to widen `crc_offset` to 64 bits.

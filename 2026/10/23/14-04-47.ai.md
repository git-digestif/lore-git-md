This is the **v4 cover letter** for the `gitmergeconflicts(7)` documentation series, now fully finalized and ready for merging. The series introduces a new man page consolidating Git’s merge-conflict resolution guidance, replacing scattered and inconsistent advice across multiple command man pages with a single, example-driven guide. All substantive feedback from prior versions (v1–v3) has been incorporated, including Junio’s squashable refinements to the `diff3` example, Patrick Steinhardt’s editorial suggestions, and mechanical fixes (punctuation, phrasing, attribution).

The cover letter highlights the **key improvements in v4**:
- Adopts Junio’s revised `diff3` example, which now uses neutral language ("has" instead of "added") and demonstrates a scenario where both sides *removed* a fruit from the original list, clarifying how the common ancestor reveals intent and prevents mismerges.
- Generalizes the `--skip` explanation to cover all multi-step operations (e.g., `git revert`), not just rebase.
- Replaces "code" with "lines" in the `diff3` section to broaden applicability beyond programming.
- Adds periods to bullet points for consistency and fixes Ben Knoble’s email address in attribution.
- Removes the `zdiff3` deprecation note entirely, deferring a more thorough explanation to future work.
- Clarifies in the commit message why `git apply`/`git am` conflicts are omitted (to avoid conflating patch application with three-way merges).

The series touches 10 files, including the new `Documentation/gitmergeconflicts.adoc` (339 lines) and updates to `git-merge.adoc`, `git-rebase.adoc`, `git-revert.adoc`, `git-cherry-pick.adoc`, and `git-pull.adoc` to cross-reference the new guide. The new page is structured as a practical, example-driven resource with sections covering:
- **What is a merge conflict?** (including semantic conflicts and Git’s behavior during conflicts).
- **Commands that can cause conflicts**: `git merge`, `git rebase`, `git cherry-pick`, `git pull`, `git am -3`, `git checkout -m`, `git stash pop`, and `git revert` (with Junio’s confirmation that `git am -3` is a valid three-way merge operation).
- **Resolution workflow**: Four-step process (identify, edit, stage, continue) with formal phrasing (e.g., "You can either resolve the conflict or abort the operation").
- **Merge conflict markers**: Explanation of `<<<<<<<`, `=======`, `>>>>>>>`, and `|||||||` (in `diff3`), with side-by-side examples contrasting default and `diff3` formats.
- **Tools for handling conflicts**: Static views (`git diff`, `git log --merge --patch <filename>`) vs. dynamic ones (`git diff AUTO_MERGE`, graphical merge tools), with active promotion of `merge.conflictstyle=diff3`.
- **"Ours" and "theirs"**: Explicitly ties these terms to `HEAD` and the other commit, clarifying the "upside down" behavior during rebases.
- **Sample `git status` output**: Guides users to `--abort`/`--continue` commands.

**Open questions deferred to future work**:
1. **`zdiff3`**: The brief deprecation note was removed, but Patrick Steinhardt’s suggestion to clarify its behavior (e.g., "removing matching lines on the two sides") remains unaddressed.
2. **Commit accessibility**: Patrick’s proposed enhancement to embed commit details in conflict markers is acknowledged but not implemented.
3. **`git status` wording**: Junio’s exploratory questions about rewording conflict markers (e.g., avoiding "deleted by us") and improving `git status` output are left for follow-up patches.
4. **Default `diff3`**: The guide promotes `diff3` as a best practice, but whether it will become the default is unresolved.

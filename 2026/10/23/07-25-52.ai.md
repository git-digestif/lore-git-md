This is **patch 7/13 in the SHA-1/SHA-256 interoperability series**, implementing the core logic to populate compatibility object IDs in pack index v3 during indexing. The patch teaches `git index-pack` and `git pack-objects` to compute and store the non-native hash algorithm’s object ID for each object, enabling bidirectional mapping between SHA-1 and SHA-256 repositories.

The patch extends the ODB mapping infrastructure introduced in earlier patches to handle packed objects. For blobs, it takes advantage of the fact that the raw content is identical across hash algorithms, so both hashes can be computed in a single pass. For non-blobs (commits, trees, tags), it uses the existing `convert_object_file()` helper to remap the object to the compatibility algorithm, then stores the result in the loose object map (but not on disk) so that dependent objects can be mapped later. A new mutex (`repo_mutex`) protects the loose object map from concurrent access during threaded indexing.

Key changes:
- `unpack_entry_data()` and `unpack_raw_entry()` now take an additional `compat_oid` parameter and populate it for both blobs and non-blobs.
- `resolve_delta()` computes the compatibility object ID for delta-resolved objects and stores it in the loose object map.
- `create_object_entry()` in `pack-objects.c` maps the object ID to the compatibility algorithm upfront.
- The loose object map is used as temporary storage for compatibility object IDs during indexing, avoiding disk writes until later patches.
- Tests in `t1016-compatObjectFormat.sh` verify that `index-pack` can write a v3 index in a repository with a compatibility algorithm, and `t5308-pack-detect-duplicates.sh` confirms that `--strict` mode rejects packs with duplicate objects in v3 indices.

The patch is **well-motivated and technically sound**, with careful attention to thread safety and memory management. The mutex protects the loose object map during concurrent access, and the decision to avoid disk writes during indexing keeps the implementation simple while ensuring correctness. The test coverage is thorough, including edge cases like duplicate detection and large files.

One potential point of review is the choice to use the loose object map for temporary storage, which could be seen as a layering violation. However, the commit message justifies this as the simplest way to share state across threads without polluting the on-disk index. Another area for scrutiny is the performance impact of computing compatibility hashes for all objects, though the patch mitigates this by hashing blobs in a single pass.

This is a **substantive, incremental step** toward full interoperability, building cleanly on the ODB mapping infrastructure merged in parts 1 and 2. The changes are focused and well-tested, and the patch should be uncontroversial. Reviewers may want to verify the thread-safety guarantees and the handling of non-blob objects, but the implementation appears robust.

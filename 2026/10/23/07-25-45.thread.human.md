This thread is about implementing **pack index v3**, a new Git index format that stores object IDs in both SHA-1 and SHA-256, enabling interoperability between repositories using different hash algorithms. The series, authored by Christian Couder and building on prior work by brian m. carlson, is the third installment in Git’s SHA-1/SHA-256 interoperability effort. The first two parts (ODB infrastructure and loose-object mapping) are already merged to `master`.

The series consists of 13 patches, now fully posted. The first 12 patches implement the core functionality: ODB mapping infrastructure, v3 index writing (including strict duplicate detection and alignment for unaligned-access architectures), compatibility object ID population during indexing, reading and validation logic, packed-object mapping, and cross-algorithm disambiguation. The final patch, just posted, adds documentation by moving the v3 format specification from `hash-function-transition.adoc` to `gitformat-pack.adoc`, where it belongs alongside v1 and v2. This patch is uncontroversial and ready to merge once the rest of the series is reviewed.

Key technical details include new or renamed functions (`odb_map_oid()`, `nth_packed_object_id_algop()`, etc.), on-disk format changes (v3 indices store object IDs in both algorithms, with 4-byte padding for short-name tables), and new test coverage in `t1016`, `t5302`, `t5308`, and `t5313`. The series touches multiple subsystems (`pack-write.c`, `packfile.c`, `odb/`, `object-file.c`, etc.) and introduces thread-safety mechanisms (e.g., `repo_mutex`) for concurrent indexing.

Open questions remain, particularly around performance (e.g., computing compatibility hashes for all objects), thread safety, and the completeness of bounds checks for corrupt indices. Reviewers may also scrutinize the choice of flags (e.g., `OBJ_MAP_WRITE`), alignment logic, and the decision to use the loose object map for temporary storage during indexing. No reviews have been posted yet, so the series is still in the early stages of discussion. The documentation patch, however, is a straightforward addition and unlikely to generate debate.

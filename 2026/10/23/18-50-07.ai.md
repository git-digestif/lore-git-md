This is a bugfix/refactoring patch targeting the remote configuration subsystem. It defers validation of `remote.<name>.followRemoteHEAD` until the setting is actually used (during `git fetch`), eliminating spurious warnings emitted by commands like `git push` or `git remote -v` that load remote configuration but never consult this value. The patch aligns the behavior with an earlier change (86129fd) that did the same for `fetch.followRemoteHEAD`.

The implementation replaces the parsed `follow_remote_head` and `no_warn_branch` members in `struct remote` with a raw string (`follow_remote_head_raw`) and a seen flag, deferring parsing to the `get_follow_remote_head()` helper in `fetch.c`. The helper now accepts a variable prefix parameter to distinguish between `fetch.followRemoteHEAD` and `remote.<name>.followRemoteHEAD` in error messages, addressing a blocker from the v1 review. The `enum follow_remote_head_settings` definition has been moved to `fetch.c` since it is no longer referenced in `remote.c`.

The patch touches `remote.c`, `builtin/fetch.c`, `builtin/remote.c`, and the `remote` configuration documentation, with test coverage added in `t5510-fetch.sh`. The AsciiDoc synopsis style change (replacing `$branch` with `<branch>`) is retained as a minor improvement. The commit message clearly explains the problem (unnecessary warnings) and the solution (lazy validation), and the implementation is clean, removing a NEEDSWORK comment and consolidating duplicate logic.

This v2 addresses all substantive feedback from the v1 review: error message ambiguity is resolved, the controversial syntax unification is dropped, and the `enum` definition is moved to the appropriate file. The patch looks well-crafted and ready for further review, with no obvious loose ends beyond minor style nits already slated for v3. It is a straightforward improvement that eliminates a persistent annoyance while maintaining backward compatibility.

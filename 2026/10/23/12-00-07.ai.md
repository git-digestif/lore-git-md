This is a **substantive review reply** in the ongoing bugfix thread for shallow fetches with tag backfilling. Patrick Steinhardt raises a **memory management concern** about the v4 patch’s approach to exposing pending transaction state via `negotiation_include_tips`.

The core question is whether the patch **leaks fetched refs** when `negotiation_include_tips` is already set by a prior caller. In v4, the patch appends fetched OIDs to the existing `oid_array` (if one exists) and only frees the array if it was newly allocated. Patrick points out that this could cause the fetched tips to persist beyond their intended scope, potentially affecting later negotiation phases or leaking memory if the caller doesn’t expect the array to be modified. This is a **correctness issue**, not just a cleanup nit: the patch’s design assumes exclusive control over `negotiation_include_tips`, but the transport API doesn’t guarantee this.

The discussion touches on **subsystem boundaries**: `backfill_tags()` is a helper for `fetch.c`, but `negotiation_include_tips` is part of the transport layer’s smart options, which may be used by other parts of the codebase. The patch’s current logic doesn’t account for this shared state, creating a potential footgun for future callers. This is a **classic integration risk**—a well-intentioned fix in one subsystem inadvertently breaking assumptions in another.

No resolution is proposed in this email, but the concern is **technically grounded** and likely to require a redesign of the memory management strategy. The author (Karthik Nayak) will need to either:
1. **Document and enforce exclusive ownership** of `negotiation_include_tips` during tag backfilling, or
2. **Copy the existing array** before appending fetched tips, ensuring no side effects for other callers.

This is a **blocker-level issue** for the patch’s readiness, as it affects both correctness and API safety. The thread’s prior convergence on the `negotiation_include_tips` design may need revisiting if the memory management can’t be resolved cleanly. Junio’s eventual review will likely focus on this point.

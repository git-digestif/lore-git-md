This is the **twelfth patch (12/13)** in Christian Couder’s v2 series implementing **pack index v3 support** for SHA-1/SHA-256 interoperability. It enables Git to look up **compatibility object IDs** (e.g., SHA-256 in a SHA-1 repository) in packed objects when using the new v3 index format.

### What the patch does
The patch extends the ODB’s packed-object lookup logic to handle **cross-algorithm disambiguation**. Previously, Git could only resolve object IDs in the repository’s main hash algorithm (e.g., SHA-1). Now, when a user requests an object ID in *any* supported algorithm (e.g., via `git rev-parse --output-object-format`), the code iterates through all valid algorithms (main and compatibility) and checks each packfile for a match. For v3 indices, this includes the compatibility object IDs stored alongside the main ones; for older indices (v1/v2), only the main algorithm is checked.

Key changes:
- **`odb/source-packed.c`**: The `for_each_prefixed_object_in_pack()` function is rewritten to loop over all supported algorithms (main and compatibility) and use the new `nth_packed_object_id_algop()` and `nth_packed_object_offset_algop()` helpers to read the correct tables from v3 indices. The logic skips unsupported algorithms and pre-v3 indices (which lack compatibility data).
- **`packfile.c`**: Adds `nth_packed_object_offset_algop()`, a variant of `nth_packed_object_offset()` that takes an explicit algorithm parameter. This ensures the correct offset table is used for the requested algorithm.
- **`packfile.h`**: Declares the new `nth_packed_object_offset_algop()` helper.
- **Tests**: A new test in `t1016-compatObjectFormat.sh` verifies that abbreviated compatibility object IDs (e.g., `sha256:abcd1234...`) can be resolved from a v3 index, even after the loose object map is removed. The test also confirms that v2 indices (which lack compatibility data) fail gracefully.

### Why this matters
This patch closes a critical gap in the interoperability effort: **packed objects can now be resolved in both hash algorithms**, not just loose ones. This is essential for commands like `git rev-parse` or `git cat-file` when working with repositories that use a compatibility hash (e.g., a SHA-1 repository accessing SHA-256 objects). The implementation is careful to avoid regressions: v1/v2 indices continue to work as before, and the new logic only kicks in for v3 indices.

### Assessment
The patch is **well-crafted and incremental**. It reuses existing infrastructure (e.g., `bsearch_pack`, `nth_packed_object_id_algop`) and adds minimal new code. The algorithm iteration logic is split into two clear `if` statements for readability, and the commit message explains the design choices (e.g., why v2 indices are skipped). The test coverage is thorough, including edge cases like abbreviated IDs and missing loose object maps.

**Likely points of review**:
1. **Performance**: The algorithm loop adds overhead to disambiguation. The commit message notes the compiler will optimize this, but reviewers may ask for benchmarks if this path is hot.
2. **Thread safety**: The patch touches `odb/source-packed.c`, which is used in multi-threaded contexts (e.g., `git index-pack`). The new logic appears safe (no shared state is modified), but this should be verified.
3. **Error handling**: The patch returns `0` (success) if no objects match, which is consistent with the existing behavior. Reviewers may check if this is the right choice for cross-algorithm lookups.

This patch is **ready for review** and should be uncontroversial. It’s a logical extension of the v3 index work and doesn’t introduce new on-disk formats or behavior changes for existing repositories. The series as a whole remains a **high-quality, well-tested step** toward full SHA-1/SHA-256 interoperability.

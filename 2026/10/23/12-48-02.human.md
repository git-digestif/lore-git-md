This is the third patch in Patrick Steinhardt’s six-patch v2 series restoring dynamic reloading of alternate object databases in Git’s files-based ODB backend. It implements the core fix: when an object lookup fails, Git now re-prepares the alternates list and retries the read, restoring the behavior accidentally broken in March 2026 during the ODB abstraction effort.

The patch modifies `odb/source-files.c` to track newly added object directories with a `tail` pointer in `odb_source_files_read_object_info()`, ensuring only those are rescanned on retry. It also removes an assertion in `odb_files_dir_is_usable()` that assumed the directory map was always populated, which no longer holds when a quarantine directory is active. The new test in `t/t1006-cat-file.sh` verifies the fix by simulating a concurrent alternates update: an object initially reported as missing becomes available after the alternates file is rewritten.

Performance data in the commit message shows this unoptimized fix regresses lookup time for 20k missing objects from 185ms to 293ms—nearly matching the pre-regression baseline. The regression is acknowledged as unavoidable, with follow-up patches (4–6) promising to recover most of the lost performance. The commit message is thorough, explaining the edge cases (quarantine directories, recursive alternates) and the rationale for the current scope.

This patch is uncontroversial and well-motivated. The design change to always reload alternates from the repository’s real object directory (introduced in patch 2) has already been agreed upon, and the test coverage is solid. The performance regression is temporary and will be addressed in subsequent patches. For anyone tracking the ODB abstraction effort or debugging missing-object issues in long-running processes, this is a key fix worth reviewing.

This is part of the ongoing SHA-1/SHA-256 interoperability effort, specifically **patch 11/13** in the pack index v3 series. The patch teaches Git to map object IDs using the new pack index v3 format when loose object maps don’t contain the needed entry.

The change is straightforward and well-motivated: previously, the ODB’s packed-object source (`odb/source-packed.c`) could only map objects that existed in the loose object map. Now it falls back to scanning pack indices (v3 only) when the loose map has no entry. The core logic is a new helper, `nth_packed_object_id_algop()`, which generalizes the existing `nth_packed_object_id()` to handle arbitrary source and destination hash algorithms. The patch skips older index versions (v1/v2) because they only store the main algorithm’s object IDs, and it fails gracefully when the requested algorithm isn’t available in the index.

A new test in `t1016-compatObjectFormat.sh` verifies the behavior: a packed object is correctly mapped when a v3 index is present, but not when only a v2 index exists. The test is careful to isolate the loose object map (moving it aside) so the fallback path is exercised.

The patch looks clean and uncontroversial. It touches only the packed-object source and its header, and the test coverage is adequate. No performance impact is expected, since the fallback scan is only attempted when the loose map lookup fails. Reviewers may want to check the error handling in `nth_packed_object_id_algop()` (e.g., the `!pfp->data_offset` check) and the thread-safety of the packfile list traversal, but these are minor points. The patch is a logical next step in the interoperability effort and should be ready for merging once the rest of the series is reviewed.

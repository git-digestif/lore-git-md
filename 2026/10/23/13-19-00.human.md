This is the second iteration of a two-patch bugfix series targeting Git’s hook configuration system. The patches address two longstanding inconsistencies: `hook.<event>.enabled` now correctly disables *all* hooks for the event (including those in the hooks directory), and boolean config values `hook.*.enabled` and `hook.*.parallel` now accept empty values (treated as `true`), matching Git’s standard boolean config behavior.

The key change since v1 is a documentation update in `Documentation/config/hook.adoc` that explicitly states `hook.<event>.enabled` applies to both configured hooks *and* the traditional hook in the hooks directory. This resolves the ambiguity flagged in the first round: the original behavior (disabling only config-defined hooks) was intentional, but the documentation’s broader wording implied universal coverage. The author now frames the first patch as a deliberate behavior change rather than a bugfix, acknowledging the backward-compatibility trade-off. Adrian Ratiu, the original author of `hook.<event>.enabled`, proposed this middle ground, and Junio C Hamano’s feedback leaned toward treating it as a breaking change—though the decision remains open to community input.

The implementation is straightforward: the first patch moves the `event_disabled` flag out of the `u.configured` struct in `hook.c` so it applies to all hooks, while the second patch adjusts boolean config parsing to handle empty values. Test coverage in `t/t1800-hook.sh` has expanded to verify edge cases, including interaction between config and hookdir hooks and empty-value handling for `.parallel`. The series touches only `builtin/hook.c`, `hook.c`, and `hook.h`, with no cross-subsystem impact.

This looks like a well-crafted fix for a real usability issue. The backward-compatibility concern is the only potential sticking point, but the documentation update and Adrian’s endorsement of the middle ground should mitigate objections. The test additions suggest the author took care to verify the changes don’t introduce regressions. If the community accepts the trade-off, this is likely to land in `next` soon.

This is a **bugfix patch update** (v5 preview) in the ongoing thread addressing a performance regression in shallow fetches when backfilling tags. The patch implements Patrick Steinhardt’s `negotiation_include_tips` design to expose pending transaction state during negotiation, replacing the earlier two-transaction approach.

Karthik Nayak responds to Patrick’s v4 review with clarifications and planned adjustments. The key discussion point is **scalability**: the new logic may cause the client to advertise *all* local references (not just newly fetched ones) during negotiation, potentially flooding the server with millions of "haves" in large repositories. Karthik acknowledges this trade-off (O(n) complexity for fetched refs) and agrees to document it in the commit message. Patrick’s concern is procedural rather than technical—he wants the potential impact explicitly discussed, not necessarily changed. The third test (upstream tracking with rejected sibling refs) will be split into a separate patch, as it’s tangential to the core fix.

Code-wise, Karthik accepts Patrick’s suggestions: using a local `struct oid_array` to simplify memory management, inlining the loop variable, and making cleanup unconditional. These are minor cleanups that don’t affect functionality. The patch remains **well-motivated and thoroughly tested**, with no correctness issues raised. The scalability question is the only open topic, but it’s unlikely to block integration—this is more about documentation than design.

The patch is **ready for `next`** unless new concerns emerge. Junio’s position is still unvoiced, but the thread has converged on a design that addresses all prior feedback. The author plans to send v5 after a day to allow for further comments.

This thread is about a **regression in `git repack`** introduced in Git 2.56.0. Coy Geek reports that the `--dry-run` option, when used with `--drop-filtered`, incorrectly mutates the repository by writing new promisor packs and (with `-d`) deleting old packs—directly violating its documented promise to only list candidate objects without making any changes.

The report is detailed and actionable, including a self-contained Python reproduction script that demonstrates the bug across two scenarios: `git repack -a --filter=blob:limit=1m --drop-filtered --dry-run` and the same command with `-d`. In both cases, the command exits successfully but leaves behind new `.pack`, `.idx`, `.promisor`, and `.rev` files, and (with `-d`) deletes the original pack files. The blob remains accessible, so this isn’t a data-loss bug, but it breaks the dry-run contract. The author cites the manual’s guarantee and links to the relevant source code in `builtin/repack.c`, where the issue appears to stem from `delete_redundant` logic not being properly guarded by `!dry_run`.

No prior discussion of this issue is mentioned, suggesting it’s a newly discovered regression. The report is credible, with concrete evidence (SHA-256 hashes, file counts, and extensions) and a clear validation criterion for a fix. The urgency is heightened by the bug’s presence in a recent release, though the author hasn’t tested `master` yet. So far, there are no replies or proposed fixes—this is the thread’s root.

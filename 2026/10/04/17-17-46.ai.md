This is Junio C Hamano's review of the v6 series introducing `remote.<name>.refmap` and matching-inspired fetch mode for shallow repositories. The review identifies two issues: a glitch in the current implementation and an unresolved design question about how to handle simultaneous `remote.<name>.fetch` and `remote.<name>.refmap` configuration.

The glitch is straightforward: when both `remote.<name>.fetch` and `remote.<name>.refmap` are set, the current code errors out with "fatal: --refmap option is only meaningful with command-line refspec". This is not a user-friendly behavior and needs to be resolved—either by ignoring one of the settings, merging them, or explicitly rejecting the combination with a clearer error message.

The design question is more subtle: what should happen when both `remote.<name>.fetch` and `remote.<name>.refmap` are configured? Junio does not propose an answer, only noting that the current behavior (an unhelpful fatal error) is not acceptable. This is a policy decision that will need input from the author and other reviewers.

Junio provides a test script (29 lines added to `t/t5586-fetch-refmap.sh`) that exercises three scenarios:
1. A refmap-only remote with no tracking branches: should fetch nothing without error.
2. A refmap-only remote with an explicit command-line refspec: should fetch only that ref.
3. A remote with both refmap and fetch refspec: currently errors out, but the desired behavior is undefined.

The test script is not a patch—it is a demonstration of what the code should do, and it exposes both the glitch and the design question. Junio invites discussion on how to resolve the ambiguity in the third scenario.

No other substantive issues are raised; the v6 series is otherwise considered technically sound. The ball is now in Harald Nordgren's court to propose a resolution for the two issues. Until these are addressed, the series is unlikely to be queued, despite Junio's earlier "Will replace" statement.

This is a feature patch revising the behavior of `` `git branch --delete-merged` ``. The v2 iteration makes the branch pattern optional: when ``--delete-merged`` appears last on the command line, it now defaults to an implicit ``**`` pattern that matches every configured upstream, rather than requiring the user to type ``*/*`` or similar. The change is backward-compatible—explicit patterns still work as before—and the documentation and help text have been updated to reflect that the pattern is now optional.

The implementation uses the existing ``PARSE_OPT_LASTARG_DEFAULT`` mechanism, so the plumbing is minimal. A new test verifies that a bare ``git branch --delete-merged`` removes only branches whose tips are reachable from their upstreams, and that ``--dry-run`` still works as expected. Edge cases such as multiple ``--delete-merged`` options or ``--dry-run`` in non-last positions are not explicitly tested, but the patch does not break existing behavior.

Junio’s review of v1 raised a design question: whether defaulting to *every* upstream (via ``**``) aligns with the stated goal of “cleaning up every branch whose work has landed upstream.” He contrasted this with other Git commands that default to the *current* branch, implying that a narrower default might be more intuitive. In v2 the author has not changed the default, but the commit message now drops the reference to ``--merged`` and simply states that ``**`` is the default pattern. The discussion remains open on whether the default should be narrower (e.g., only branches merged into the current branch) or if ``**`` is the right abstraction.

The patch is small, well-explained, and touches only three files. It looks like a sensible ergonomic improvement for a common workflow, though the design question Junio raised is still unresolved.

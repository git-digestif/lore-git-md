This is a refactoring patch in the `fetch` subsystem, continuing the effort to defer validation of `fetch.followRemoteHEAD` until the setting is actually used. Junio C Hamano replies to Colin Hinton’s proposed v5 direction, discussing how to handle valueless versus empty-string config settings during lazy validation.

The core issue remains unchanged: the current implementation issues warnings during config parsing even when the fetch operation never consults `fetch.followRemoteHEAD`, which is unnecessary and potentially confusing. Colin’s v4 patch defers validation to `do_fetch()` by storing the raw config string in `follow_remote_head_raw` and parsing it only when needed. Junio’s review of v4 suggested using `xstrdup_or_null(v)` unconditionally in `git_fetch_config()` to preserve the distinction between a valueless setting (`[fetch] followremotehead`) and an explicitly empty string (`[fetch] followremotehead = ""`), allowing the lazy-validation helper to handle each case appropriately.

In this reply, Junio clarifies his position on the design question Colin raised: whether an empty string should trigger a warning or a `die()`. Junio argues that both valueless and empty-string settings are equally unrecognized, so they should behave the same way—either both warn-and-ignore or both complain-and-die. He endorses tightening the rules to `die()` now that validation is deferred until the setting is actually needed, calling the historical warn-and-ignore behavior a "weak excuse" for premature validation. This aligns with the patch’s goal of doing the right thing by validating config values in the correct context.

Colin’s proposed v5 direction introduces a `follow_remote_head_seen` flag in `struct fetch_config` to track whether the setting was encountered during config parsing, regardless of its value. This would allow the code to distinguish between a valueless setting (which should `die()`) and an empty string (which would also `die()` under Junio’s preference). Junio suggests an alternative approach—using a sentinel value (`valueless_true`) to mark valueless settings—but ultimately agrees that Colin’s flag-based design is clearer and easier to work with. The discussion remains narrowly focused on the mechanics of config string handling, with no new edge cases or performance implications introduced.

The patch is now poised to move forward with the `follow_remote_head_seen` flag and tightened validation rules. The remote-side parser (`remote.c::handle_config()`) remains unchanged for now, but the groundwork is laid for a follow-up patch to apply the same lazy-validation pattern there. The only remaining open question is whether Junio will formally approve the tightened `die()` behavior, but his feedback here strongly suggests he will. The patch is a clean refactoring with no behavior changes for valid config values, and the changes discussed here are incremental and well-motivated.

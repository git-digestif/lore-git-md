This is the second patch in the v6 series introducing a "matching-inspired" fetch mode for shallow repositories. It implements the core logic that makes `git fetch` infer which branches to fetch when a remote has a `remote.<name>.refmap` configured but no `remote.<name>.fetch` refspec.

The patch updates `builtin/fetch.c` and `remote.c` to dynamically enumerate branches tracked by local branches at the remote being fetched. When no explicit refspec is given and the remote has a refmap but no fetch refspec, `get_ref_map()` now calls the new `branches_tracking_remote()` helper (added to `remote.c`) to collect the upstream refs of all local branches tracking that remote. These refs are then passed to the transport’s `ls-refs` command, ensuring only the relevant branches are fetched. The forced inclusion of the remote’s default branch (present in earlier versions) is removed, simplifying the logic and resolving Junio’s design objection.

Documentation in `config/remote.adoc` and `fetch-options.adoc` is updated to explain the new behavior: when a refmap is active but there is nothing to fetch from the command line or `remote.<name>.fetch`, Git infers what to fetch from local branches whose `@{upstream}` is on that remote. The new test file `t/t5586-fetch-refmap.sh` verifies dynamic branch selection, edge cases (duplicate branches, branches tracking other remotes), and compatibility with `git remote show`.

The patch is technically sound, well-tested, and aligns with the consensus design established in earlier iterations. No substantive objections remain, and the implementation is ready for integration. The only acknowledged edge case—a bare `git fetch` against a refmap-only remote fetching no branches—is noted in the thread but not considered a blocker. This patch is the technical centerpiece of the series and the most likely candidate for follow-up discussion about edge-case handling or future extensions.

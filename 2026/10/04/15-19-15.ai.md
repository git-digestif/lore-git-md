This is a bugfix targeting the fsmonitor and untracked cache subsystems. The patch addresses a subtle correctness issue that arises when the fsmonitor daemon sends a trivial response (`"/"`), typically after a restart or event loss. In such cases, Git marks all index entries as dirty but fails to invalidate stale untracked cache entries, leading to two observable problems: untracked files may persist in `git status` output even after their directories are removed, and Git may emit spurious warnings about missing directories.

The fix introduces a new function `untracked_cache_invalidate_stale_dirs()` that recursively checks each cached directory against its on-disk stat data before the untracked cache is written to the index. This ensures that stale entries—those whose directories no longer exist or whose stat data no longer matches—are invalidated. The check is performed only when the fsmonitor extension is written and the untracked cache is no longer trusted (i.e., `use_fsmonitor` is false), avoiding unnecessary overhead for commands that do not write the index or for sparse index writes, which discard the fsmonitor extension anyway.

The patch includes thorough test coverage in both `t/t7519-status-fsmonitor.sh` and `t/t7527-builtin-fsmonitor.sh`, exercising the scenario with both hook-based and built-in fsmonitor backends. The tests confirm that after a trivial response, commands like `git add` or `git checkout`—which do not scan for untracked files—correctly invalidate stale cache entries, preventing subsequent `git status` from trusting them.

The implementation is narrowly scoped and well-motivated: it targets a specific edge case (trivial fsmonitor responses) with a targeted solution (stat-based validation at write time), and the commit message clearly explains the problem, the chosen fix, and the trade-offs (one `lstat()` per cached directory, incurred only once per trivial response). The code itself is clean, with clear function naming and recursion that mirrors the existing untracked cache traversal logic. This looks like a solid, low-risk fix for a real correctness issue.

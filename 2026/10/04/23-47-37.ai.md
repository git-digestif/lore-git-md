This is a **bugfix** targeting the `git repack` command in Git 2.56.0. The patch reports a clear regression: the `--dry-run` option, when combined with `--drop-filtered`, incorrectly writes new promisor packs and (with `-d`) deletes old packs, violating its documented promise to only list candidate objects without mutating repository storage.

The report is thorough and well-structured. It includes a self-contained Python reproduction script that creates disposable repositories, disables ambient Git configuration, and snapshots the pack directory before/after each command. The script output demonstrates the bug: both `git repack -a --filter=blob:limit=1m --drop-filtered --dry-run` and the same command with explicit `-d` exit successfully but add four new files (`.pack`, `.idx`, `.promisor`, `.rev`) and (in the `-d` case) delete the original 12 pack files. The blob remains accessible afterward, so this does not demonstrate data loss—only a violation of the dry-run contract.

The author cites the manual’s explicit guarantee ("List the objects that would be dropped... without rebuilding any pack or deleting anything") and links to the relevant source lines in `builtin/repack.c` (v2.56.0), where the `delete_redundant` logic is guarded by `!dry_run` but execution continues past the candidate-printing block. They also reference the original implementation discussion (v5 of the `--drop-filtered` series) to underscore the intended behavior.

The report is credible and actionable. The reproduction script is portable (macOS, but uses only standard Python and Git), and the evidence is concrete: SHA-256 hashes of pack files before/after, exact file counts, and extensions. The author explicitly states they did not test current `master`, but the bug’s presence in a recent release (2.56.0) makes it urgent. No prior discussion of this specific issue is mentioned, so this appears to be a newly discovered regression. The restoration check at the end provides a clear validation criterion for a fix.

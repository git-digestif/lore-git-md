This is a bugfix for the fsmonitor subsystem, specifically addressing a subtle interaction between the untracked cache and fsmonitor's "trivial response" behavior.

When the fsmonitor daemon restarts or loses events, it sends a trivial response ("/") to indicate the entire working directory may have changed. The current code marks all index entries as dirty but only clears the in-memory `use_fsmonitor` flag for the untracked cache, leaving stale directory validity bits intact. This creates a problem: commands like `git add` or `git checkout` that don't scan for untracked files will save these stale bits alongside the new fsmonitor token, causing later `git status` commands to trust invalid cached directories. The result is either phantom untracked files appearing or spurious "could not open directory" warnings.

The patch adds a new function `untracked_cache_invalidate_stale_dirs()` that walks the untracked cache directory tree and invalidates any entries whose stat data no longer matches the working tree. This runs during index writes when a trivial fsmonitor response was received and the untracked cache isn't actively using fsmonitor. The fix includes thorough test coverage in both the hook-based and built-in fsmonitor test scripts, demonstrating the bug and verifying the fix.

The implementation looks clean: it adds about 60 lines of core logic plus tests, uses recursive directory traversal with proper path management, and includes trace2 instrumentation to help diagnose similar issues in the future. The commit message clearly explains the problem, the solution, and why the fix happens at write time rather than during the fsmonitor response processing. This appears to be a well-motivated and well-executed fix for a real edge case in fsmonitor's untracked cache handling.

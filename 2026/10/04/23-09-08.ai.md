This is the second patch in Domen Kožar’s v3 series introducing a unified `post-worktree` hook for worktree lifecycle events. It specifically extends the hook to cover `git worktree prune`, ensuring tools can observe worktree removals even when they are triggered indirectly (e.g., manual deletion, `git worktree prune`, or IDE cleanup).

The patch addresses a key gap in the v2 series: pruning operations now emit `post-worktree remove` events for every administrative entry removed, including duplicates and damaged entries. The hook receives the worktree identifier and its former absolute path (or an empty string if the path cannot be determined). The implementation touches `builtin/worktree.c` (pruning logic and hook invocation), `worktree.c`/`worktree.h` (path resolution during pruning), and adds comprehensive test coverage in `t/t2401-worktree-prune.sh`. Tests validate edge cases like dry runs, missing paths, duplicate entries, relative paths, and hook failures that must not suppress other notifications.

The changes since v2 are mechanical but important: the hook’s execution context is now consistent across all events (the invoking repository, not the affected worktree), and the pruning logic preserves the recorded `.git` path even for damaged entries to ensure the hook receives meaningful arguments. The patch is well-motivated by real-world use cases (e.g., Maciej Ciemborowicz’s report about VS Code with Codex creating worktrees directly) and complements the v3 series’ goal of providing reliable observability for uncontrolled callers.

This patch looks technically sound and directly addresses the thread’s core problem: tools maintaining per-worktree state need to observe deregistration events even when they do not control the caller. The test coverage is thorough, and the commit message clearly explains the design choices (e.g., empty strings for undetermined paths, dry-run suppression). The only unresolved question from prior feedback is whether the relative order of `post-worktree` and `post-checkout` hooks is sufficiently documented, but that is a broader series-level concern rather than a flaw in this patch.

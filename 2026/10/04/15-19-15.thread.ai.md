Subject: [PATCH] fsmonitor: invalidate stale untracked cache directories after trivial response
Series version: standalone patch
Originating author: Ilia (via GitGitGadget)
Thread type: bugfix

Core problem or goal
When the fsmonitor daemon sends a trivial response (`"/"`), typically after a restart or event loss, Git marks all index entries as dirty but fails to invalidate stale untracked cache entries. This causes two observable problems: untracked files may persist in `git status` output even after their directories are removed, and Git may emit spurious warnings about missing directories.

Current status
Under review; no prior versions. The patch is narrowly scoped to the edge case of trivial fsmonitor responses, introducing a new function `untracked_cache_invalidate_stale_dirs()` that recursively checks each cached directory against its on-disk stat data before the untracked cache is written to the index. The check is performed only when the fsmonitor extension is written and the untracked cache is no longer trusted (`use_fsmonitor` is false), avoiding overhead for commands that do not write the index or for sparse index writes.

Key technical details
- Subsystems: fsmonitor, untracked cache
- New function: `untracked_cache_invalidate_stale_dirs()`
- Files touched: `fsmonitor.c`, `fsmonitor.h`, `t/t7519-status-fsmonitor.sh`, `t/t7527-builtin-fsmonitor.sh`
- Behavior change: stale untracked cache entries are now invalidated when the fsmonitor daemon sends a trivial response, ensuring subsequent `git status` does not trust them
- Overhead: one `lstat()` per cached directory, incurred only once per trivial response
- Test coverage: exercises both hook-based and built-in fsmonitor backends

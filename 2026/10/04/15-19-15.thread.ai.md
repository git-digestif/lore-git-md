Subject: [PATCH] fsmonitor: invalidate stale untracked cache directories after trivial response
Series version: standalone patch (v1, updated per review)
Originating author: Ilia (via GitGitGadget)
Thread type: bugfix

Core problem or goal
When the fsmonitor daemon sends a trivial response (`"/"`), typically after a restart or event loss, Git marks all index entries as dirty but fails to invalidate stale untracked cache entries. This causes two observable problems: untracked files may persist in `git status` output even after their directories are removed, and Git may emit spurious warnings about missing directories.

Current status
Ready for integration. The patch has been updated to address the final implementation questions raised during review: (1) when `repo_get_work_tree()` fails, the entire untracked cache is now invalidated (rather than returning 0 or an error), and (2) redundant test comments have been removed. The design—invalidating stale entries only when the fsmonitor extension is written and the cache is untrusted—remains unchanged. Derrick Stolee’s performance measurements and Junio C Hamano’s maintainer-level review have both endorsed the approach. No further revisions are expected unless new edge cases emerge during integration testing.

Key technical details
- Subsystems: fsmonitor, untracked cache
- New function: `untracked_cache_invalidate_stale_dirs()`
- Files touched: `fsmonitor.c`, `fsmonitor.h`, `t/t7519-status-fsmonitor.sh`, `t/t7527-builtin-fsmonitor.sh`
- Behavior change: stale untracked cache entries are invalidated when the fsmonitor daemon sends a trivial response, ensuring subsequent `git status` does not trust them. The check occurs after `refresh_fsmonitor()` and before the index is written, preventing race conditions.
- Overhead: one `lstat()` per cached directory, incurred only once per trivial response; Stolee’s measurements confirm no measurable performance penalty.
- Test coverage: exercises both hook-based and built-in fsmonitor backends.

Open questions and loose ends
None. The two implementation questions (recursion safety and error handling) have been resolved: the recursive traversal is safe due to the untracked cache’s structure, and `repo_get_work_tree()` failures now invalidate the entire cache and continue.

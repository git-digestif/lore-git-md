Core problem or goal
When the fsmonitor daemon sends a trivial response (`"/"`), typically after a restart or event loss, Git marks all index entries as dirty but fails to invalidate stale untracked cache entries. This causes two observable problems: untracked files may persist in `git status` output even after their directories are removed, and Git may emit spurious warnings about missing directories.

Key technical details
- Subsystems: fsmonitor, untracked cache
- New function: `untracked_cache_invalidate_stale_dirs()`
- Files touched: `fsmonitor.c`, `fsmonitor.h`, `t/t7519-status-fsmonitor.sh`, `t/t7527-builtin-fsmonitor.sh`
- Behavior change: stale untracked cache entries are invalidated when the fsmonitor daemon sends a trivial response, ensuring subsequent `git status` does not trust them. The check occurs after `refresh_fsmonitor()` and before the index is written, preventing race conditions.
- Overhead: one `lstat()` per cached directory, incurred only once per trivial response; Stolee’s measurements confirm no measurable performance penalty.
- Test coverage: exercises both hook-based and built-in fsmonitor backends.
- New instrumentation: Trace2 logging of invalidated directory count.

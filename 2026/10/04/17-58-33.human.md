This is a feature patch series adding `--[no-]range-diff-notes` options to `git format-patch`. The series is now in its fifth iteration (v5) and consists of two patches: a preparatory refactoring and the main implementation. Kristoffer Haugsbakk has addressed all feedback from Junio C Hamano, the maintainer, and the series appears technically complete and ready for integration.

The goal is to allow users to control whether Git notes appear in the range-diff section of `format-patch` output independently of whether notes appear in the patches themselves. For example, you can now suppress notes in the range-diff while keeping them in the patch output, or specify a different notes ref for the range-diff. This addresses a workflow need Kristoffer has used privately for months, though the current implementation is entirely new.

The v5 changes are minor and editorial: the commit message for patch 2/2 has been shortened to remove a lengthy explanation about why `--[no-]range-diff-notes` doesn’t error out when used without `--range-diff`, replacing it with a concise three-line rationale that keeps the same information. Thematic breaks (`***`) have also been removed to improve flow. The implementation itself is unchanged from v4, which Junio reviewed and found technically sound.

The series touches `builtin/log.c` and updates the `git-format-patch` documentation, with comprehensive test coverage added to `t/t3206-range-diff.sh`. The new options are `--range-diff-notes=<ref>` (which requires an explicit ref argument) and `--no-range-diff-notes` (which suppresses notes in the range-diff without fallback). The interaction with existing `--notes` options is clean: if no range-diff notes options are given, the range-diff uses the same notes as the patches; otherwise, it uses only the explicitly specified notes.

This looks like a well-crafted, thoroughly reviewed feature addition. The commit messages are clear, the tests cover edge cases (including the single-patch case), and the implementation follows Junio’s guidance on CLI semantics. If you care about fine-grained control over notes in `format-patch` output, this is worth a look.

This is the second patch in Harald Nordgren’s four-part v6 series introducing a "matching-inspired" fetch mode for shallow repositories. It implements the core logic: when a remote has `remote.<name>.refmap` configured but no `remote.<name>.fetch` refspec, a plain `git fetch <name>` now infers which branches to fetch by looking at the local branches whose `@{upstream}` is on that remote. This avoids the slow or hanging behavior that shallow repositories experience when the remote has many branches.

The patch touches `builtin/fetch.c` and `remote.c`, adding a new helper `branches_tracking_remote()` that iterates over local branches and collects the refnames of their upstreams on the given remote. The `get_ref_map()` function in `fetch.c` uses this list to build an inferred refspec when no explicit refspec is given and the remote has a refmap but no fetch refspec. The transport layer (`do_fetch()`) is updated to pass the inferred branch list to `ls-refs`, ensuring the server only advertises the branches the client actually wants. Documentation in `config/remote.adoc` and `fetch-options.adoc` is updated to explain the new behavior, and a new test script (`t/t5586-fetch-refmap.sh`) verifies the dynamic branch selection, edge cases (duplicate branches, branches tracking other remotes), and compatibility with `git remote show`.

The implementation is clean and well-scoped: it reuses existing refspec machinery, avoids on-disk format changes beyond the new configuration entry introduced in Patch 1/4, and preserves backward compatibility for non-shallow repositories. The only acknowledged edge case is that a bare `git fetch` against a refmap-only remote with no tracked branches fetches nothing, leaving no remote-tracking refs for `git branch --set-upstream-to` to use — Harald considers this a minor quibble, not a blocker. No substantive objections remain, and Junio has already stated he will queue the series. This patch is the technical centerpiece of the series and is ready for integration.

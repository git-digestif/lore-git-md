This is a feature patch series (v3) introducing a unified `post-worktree` hook for Git’s worktree subsystem. The series is authored by Domen Kožar and responds directly to the ongoing design discussion about how to provide reliable observability for worktree lifecycle events (creation, removal, movement) when those events are triggered by uncontrolled callers—such as IDEs, AI agents, or manual user actions.

The v3 series consolidates the three separate hooks proposed in v2 (`post-worktree-add`, `post-worktree-remove`, `post-worktree-move`) into a single `post-worktree` hook with a subcommand-style interface. The hook is invoked with four arguments: the event type (`add`, `move`, or `remove`), the worktree’s administrative identifier, the old absolute path, and the new absolute path. Empty strings are used for paths that do not apply (e.g., the new path during removal). This design simplifies configuration—one hook command can handle all three events—and ensures consistent argument passing regardless of the triggering operation. The hook runs in the repository where the command was invoked, not the affected worktree, which avoids environment issues during pruning or when the worktree is damaged.

The implementation covers all worktree operations, including `add --no-checkout`, `add --orphan`, `move`, `remove`, and `prune`. Pruning is particularly well-handled: the hook is invoked once per pruned entry, including duplicates, and continues notifying remaining entries even if one hook invocation fails. The series includes thorough test coverage in `t/t2400-worktree-add.sh`, `t/t2401-worktree-prune.sh`, and `t/t2403-worktree-move.sh`, validating edge cases like relative paths, spaces in paths, bare and linked worktrees, dry runs, and hook failures. Documentation is updated in `Documentation/githooks.adoc` and `Documentation/config/hook.adoc`.

The motivation is clear and compelling: tools managing per-worktree environments (e.g., devenv, IDEs, AI agents) need to observe worktree lifecycle events even when they do not control the caller. Wrappers are insufficient because they can be bypassed, and `post-checkout` does not cover all cases (e.g., `--no-checkout`, pruning). The v3 series directly addresses the core problem—unreliable observability—while remaining agnostic to Kristoffer Haugsbakk’s complementary `--id=<string>` counterproposal, which focuses on ownership enforcement rather than observability. Domen’s framing of hooks and IDs as complementary (not competing) is persuasive, and Maciej Ciemborowicz’s real-world report about VS Code with Codex creating worktrees directly provides concrete evidence that hooks are necessary.

The series is technically sound, well-tested, and addresses the main points of contention from prior reviews. The consolidation into a single hook is a sensible compromise that reduces complexity while maintaining flexibility. The only unresolved issue is Junio C Hamano’s fundamental objection to hooks, which remains unaddressed in this version. However, the v3 series strengthens the observability argument with real-world use cases and edge-case coverage, making it harder to dismiss as unnecessary. If Junio’s concerns are not met with a counterargument, this series is likely to be of high interest to anyone building tooling around Git worktrees. It is now in `seen` and awaiting further review.

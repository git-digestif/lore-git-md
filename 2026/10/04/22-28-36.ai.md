This is a **performance-focused follow-up** in the ongoing discussion about extending `` `git branch --delete-merged` `` to detect squash-merged and rebase-merged branches. The author, Harald Nordgren, responds to Phillip Wood’s **substantive review** identifying inefficiencies in the current implementation.

Harald acknowledges the performance concerns raised by Phillip—specifically, that the patch recalculates upstream diffs for each branch, which is less efficient than the batching and precomputation strategies used by `` `git cherry` ``. He reports that he is already iterating on the code to share logic between branches and has observed noticeable speed improvements in his local Git repository. While he does not provide implementation details, his response suggests that the performance issues may be addressable without introducing new CLI options or config flags.

The email then shifts to the question of whether an optimization toggle (e.g., an option to disable patch-id-based detection in favor of a faster tree-based check) is still warranted if the performance concerns are resolved. Harald argues that users prefer simplicity and questions whether such a toggle would be necessary if the feature performs well out-of-the-box. This reflects his earlier position in the thread: he favors a single, unified behavior that works consistently across all contexts (e.g., `` `git branch --delete-merged` `` and `` `git branch --delete-merged '*/*'` ``) without requiring users to specify detection modes explicitly.

The discussion remains open on two fronts: (1) whether the performance optimizations Harald is implementing will be sufficient for large repositories or blobless clones, and (2) whether a CLI option or config flag is still needed to control the behavior. Phillip’s proposed lightweight optimization—short-circuiting the squash check if an upstream commit’s second parent tree exactly matches the branch tip—has not been directly addressed, but Harald’s focus on sharing logic between branches suggests he may be exploring a similar approach. No new technical details or edge cases are introduced in this reply.

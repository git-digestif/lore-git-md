This is the final patch in the four-part series introducing a "matching-inspired" fetch mode for shallow repositories. It makes `--limited-fetch` the default when adding a remote to a shallow repository, ensuring that `git fetch` does not negotiate history for every branch the remote has.

The patch modifies `builtin/remote.c` to check whether the repository is shallow (using `is_repository_shallow()`) when deciding whether to enable `--limited-fetch` by default. The default is applied only if neither `-t/--track` nor `--mirror` is given, preserving backward compatibility for explicit use cases. The documentation in `git-remote.adoc` is updated to explain the new behavior, and the test suite (`t/t5505-remote.sh`) adds four new tests covering the shallow-repository default, explicit `-t` usage, full-repository behavior, and the `--no-limited-fetch` override.

This patch completes the series by addressing the original problem: shallow clones with multiple remotes no longer suffer from slow or hanging fetches due to wildcard refspecs. The implementation is opt-out (via `--no-limited-fetch`) and preserves existing behavior for non-shallow repositories.

Thread identity
Subject: `git repack --dry-run --drop-filtered` violates dry-run contract
Series version: standalone bugfix (no series)
Originating author: Coy Geek
Thread type: bug report

Core problem or goal
The `--dry-run` option of `git repack`, when used with `--drop-filtered`, incorrectly mutates repository storage by writing new promisor packs and (with `-d`) deleting old packs, despite the manual’s guarantee that it will only list candidate objects without making changes.

Current status
Under review; confirmed present on `master` (commit `6a2b3c4d`). Root cause identified in `builtin/repack.c`: `dry_run` guards `delete_redundant` but execution continues into `finish_repack`, which writes promisor packs and deletes old packs unconditionally. Siddharth Shrimali (original `--drop-filtered` author) has posted a minimal fix (early return after candidate printing when `dry_run` is set) and plans to add a test in `t/t7706-repack-drop-filtered.sh`.

Key technical details
- Command: `git repack -a --filter=blob:limit=1m --drop-filtered --dry-run`
- Files touched: `.pack`, `.idx`, `.promisor`, `.rev` (newly written); original pack files (deleted when `-d` is added)
- Subsystem: `builtin/repack.c`, specifically the `finish_repack` function called after the `dry_run`-guarded candidate-printing block
- On-disk format: new promisor packs are created; no data loss (blobs remain accessible)
- Test coverage: reproduction script provided (Python, self-contained, portable); D. Ben Knoble tested on `master` and verified the fix; Shrimali plans to add a regression test in `t/t7706-repack-drop-filtered.sh`
- New symbols: none (fix is a control-flow change only)

Open questions and loose ends
- Whether the analogous `--geometric` code path should be fixed in the same patch or as a follow-up (still open; no new input)
- Whether the manual’s wording should be tightened to clarify that `--dry-run` applies to *all* side effects, not just pack rebuilding (still open)

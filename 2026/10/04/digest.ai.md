## Notable threads

### Unified `post-worktree` hook (v3)
Domen Kožar posted v3 of the unified `post-worktree` hook series, replacing v2’s three separate hooks (`post-worktree-add`, `post-worktree-remove`, `post-worktree-move`) with a single subcommand-style hook. The new hook takes four arguments: the event type (`add`, `move`, or `remove`), the worktree identifier, the old absolute path, and the new absolute path. Empty strings are used for non-applicable paths (e.g., no old path for `add`). The hook runs in the invoking repository, not the affected worktree, and its exit status is propagated to the caller but does not affect the operation’s outcome.

The series directly addresses the thread’s core goal: providing reliable observability for worktree lifecycle events even when the caller is uncontrolled (e.g., IDEs, manual deletion, or `git worktree prune`). The implementation touches `builtin/worktree.c`, `Documentation/githooks.adoc`, and adds comprehensive test coverage in `t/t2400-worktree-add.sh` and `t/t2403-worktree-move.sh`. The series remains in `seen` pending resolution of Junio C Hamano’s fundamental objection to hooks, which has not yet been addressed in this iteration.

### `--[no-]range-diff-notes` series reaches v5
Kristoffer Haugsbakk’s feature series adding `--[no-]range-diff-notes` to `git format-patch` reached v5 and is now technically complete and ready for integration. The series introduces two new CLI options: `--range-diff-notes=<ref>` (which requires an explicit ref argument) and `--no-range-diff-notes` (which suppresses notes in the range-diff without fallback). The v5 iteration incorporates Junio C Hamano’s final editorial feedback, condensing the commit message for patch 2/2 to remove a meandering explanation of why `--[no-]range-diff-notes` does not error out when used without `--range-diff`.

The implementation touches `builtin/log.c`, updates `Documentation/git-format-patch.adoc`, and adds comprehensive tests in `t/t3206-range-diff.sh`. The interaction rule between patch notes and range-diff notes remains unchanged: if no range-diff notes options are given, the range-diff uses the same notes as the patches; otherwise, it uses only the explicitly specified notes (including none). The series is now in its final form, with all maintainer feedback addressed, and awaits Junio’s queueing.

### Matching-inspired fetch mode for shallow repositories
Junio C Hamano identified a glitch and a design ambiguity in Harald Nordgren’s v6 series introducing `remote.<name>.refmap` and a matching-inspired fetch mode for shallow repositories. The glitch occurs when both `remote.<name>.fetch` and `remote.<name>.refmap` are configured: the current code errors out with "fatal: --refmap option is only meaningful with command-line refspec". Junio provided a test script demonstrating the issue and invited discussion on how to resolve the ambiguity (e.g., precedence rules, merging, or explicit rejection).

Harald Nordgren proposed that `remote.<name>.fetch` should take precedence when both it and `remote.<name>.refmap` are configured, resolving the fatal error by ignoring the `refmap` setting. This proposal directly addresses the design question but does not yet include a rationale or implementation sketch. The series remains blocked on this unresolved design point, despite Junio’s earlier "Will replace" statement.

### Regression in `git repack --dry-run --drop-filtered`
Coy Geek reported a regression in `git repack --dry-run --drop-filtered`: the command incorrectly writes new promisor packs and (with `-d`) deletes old packs, violating its documented promise to only list candidate objects without mutating repository storage. The report includes a self-contained Python reproduction script that demonstrates the bug in Git 2.56.0. The script creates disposable repositories, disables ambient Git configuration, and snapshots the pack directory before/after each command, showing that both `git repack -a --filter=blob:limit=1m --drop-filtered --dry-run` and the same command with explicit `-d` exit successfully but add four new files (`.pack`, `.idx`, `.promisor`, `.rev`) and (in the `-d` case) delete the original 12 pack files.

The author traces the issue to `builtin/repack.c`, where the `delete_redundant` logic is guarded by `!dry_run` but execution continues past the candidate-printing block. The report is credible and actionable, with clear validation criteria for a fix. The regression’s presence in a recent release (2.56.0) makes it urgent, though no prior discussion of this specific issue is mentioned.

### `git branch --delete-merged` squash/rebase detection
Harald Nordgren reported iterating on the `git branch --delete-merged` squash/rebase detection code to share logic between branches, achieving noticeable speed improvements. He questioned whether an optimization toggle (e.g., disabling patch-id checks in favor of a faster tree-based check) is still needed if performance is acceptable. Phillip Wood had earlier identified inefficiencies in the current implementation, noting that it recalculates upstream diffs for each branch and suggesting adopting `git cherry`-style batching and precomputation. For squash merges, Phillip proposed a lightweight optimization: if an upstream commit’s second parent tree exactly matches the branch tip, the branch can be considered squash-merged without running the full patch-id check.

The discussion remains open on two fronts: whether the performance optimizations Harald is implementing will be sufficient for large repositories or blobless clones, and whether a CLI option or config flag is still needed to control the behavior. Phillip’s proposed optimization for squash merges has not been directly addressed, but Harald’s focus on sharing logic between branches suggests he may be exploring a similar approach.

He withdrew his objection to plain URLs, accepting them as the pragmatic solution.
- **Incremental rebase conflict resolution**: Phillip Wood endorsed Patrick Steinhardt’s preference for integrating incremental rebase conflict resolution into `git rebase` itself rather than as a standalone script. He proposed `--incremental` or `--progressive` as potential option names and advocated for a single-shot workflow where `git rebase --continue` automatically advances to the next conflicting commit.
- **`git branch --delete-merged` default pattern**: Harald Nordgren posted v2 of the patch making `git branch --delete-merged` default to all upstreams when no pattern is given. Phillip Wood objected to the use of `PARSE_OPT_LASTARG_DEFAULT`, arguing it creates a usability trap: future options could break the default behavior depending on their position. He suggested using a `--` separator to explicitly mark the end of upstream patterns.
- **Zsh completion regression risk**: SZEDER Gábor identified a regression risk in the Zsh completion patch: the current implementation would incorrectly exclude all arguments from the second word onward (e.g., `-C dir`, `-c foo.bar=baz`, `file1`, `file2`) in commands like `git -C dir -C subdir -c foo.bar=baz add file1 file2 <TAB>`, rather than just the file arguments. Fionn clarified the intent but did not address the technical flaw.
- **`git stash` code consistency**: Phillip Wood replaced a hard-coded integer (`2`) with the named constant `INCLUDE_ALL_FILES` in the option-parsing code for `git stash --all`, improving code consistency.
- **Fsmonitor untracked cache invalidation**: Ilia introduced `untracked_cache_invalidate_stale_dirs()` to invalidate stale untracked cache entries when the fsmonitor daemon sends a trivial response (`"/"`). The function recursively checks each cached directory against its on-disk stat data, ensuring stale entries are invalidated before the untracked cache is written to the index. The patch includes test coverage for both hook-based and built-in fsmonitor backends.

This is a **bugfix** targeting the `git repack` command in Git 2.56.0. The author, Coy Geek, reports that `git repack --drop-filtered --dry-run` violates its documented contract: instead of merely listing objects that would be dropped, it actually writes new promisor packs and, when combined with `-d`, deletes old packs. The repository state is mutated despite the promise of a read-only preview.

The report is thorough and reproducible. Coy provides a self-contained Python script that creates disposable repositories, exercises both the plain `--dry-run` and `--dry-run -d` variants, and snapshots the pack directory before and after. The output shows four new files (`.pack`, `.idx`, `.promisor`, `.rev`) added in both cases, and twelve old files removed when `-d` is present. The blob remains accessible afterward, so no data loss is demonstrated, but the storage layout is altered contrary to expectations.

The commit message and documentation links establish the expected behavior: `--dry-run` should list candidates without rebuilding packs or deleting anything. The author also cites the original implementation discussion (v5 1/6 and 5/6 from August 2026) to reinforce that the intent was a non-mutating preview. A source breadcrumb in `builtin/repack.c` suggests the `delete_redundant` guard is bypassed when `dry_run` is set, but execution continues past the candidate-printing block, which aligns with the observed behavior.

This looks like a clear regression or oversight in the `--drop-filtered` feature. The patch is well-motivated, the reproduction is complete, and the evidence is compelling. Any reviewer interested in the repack machinery or promisor-remote behavior will want to pay attention.

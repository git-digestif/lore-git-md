This is a feature patch series (v3) introducing a unified `post-worktree` hook for Git's worktree subsystem. The series is part of an ongoing design discussion about how to provide reliable observability for worktree lifecycle events (creation, movement, removal) to external tools like IDEs, AI agents, and development environment managers. Domen Kožar is the author, and this version consolidates three separate hooks (`post-worktree-add`, `post-worktree-remove`, `post-worktree-move`) from v2 into a single hook with a subcommand-style interface.

The hook runs after each lifecycle event with four arguments: the event type (`add`, `move`, or `remove`), the worktree identifier (administrative directory name), the old absolute path, and the new absolute path. Empty strings are passed for non-applicable paths (e.g., no old path for `add`). The hook executes in the repository where the command was invoked, not the affected worktree, and its exit status is propagated to the caller but does not affect the operation's outcome. This design covers all worktree operations, including `--no-checkout`, `--orphan`, manual deletions, and `git worktree prune`, and handles edge cases like damaged entries and duplicate pruning.

The implementation touches `builtin/worktree.c` (hook invocation points), `Documentation/githooks.adoc` (documentation), and `worktree.h`/`worktree.c` (pruning logic). The series includes comprehensive test coverage in `t/t2400-worktree-add.sh`, `t/t2401-worktree-prune.sh`, and `t/t2403-worktree-move.sh`, validating ordinary, bare, and linked worktrees, relative paths, configured hooks, and failure handling. The tests also verify that pruning continues to notify remaining entries after a hook failure and that `--dry-run` does not invoke the hook.

Key changes since v2 include: (1) replacing three separate hooks with a single `post-worktree` hook; (2) passing all four arguments for every event (event type, identifier, old path, new path) instead of using argument count to distinguish operations; (3) keeping the execution context in the invoking repository for all events; (4) covering additional edge cases like paths with spaces and relative paths. The series is well-tested, with validation including local test runs (33,881 tests passed), CI checks across platforms, and trial merges into `next` and `seen`.

The series directly addresses the thread's core problem: providing observability for worktree lifecycle events when the caller is uncontrolled (e.g., an IDE or user running `git worktree remove` directly). Domen argues that hooks and ownership identifiers (like Kristoffer Haugsbakk's `--id=<string>` counterproposal) serve complementary purposes—hooks for observability, IDs for ownership—and Maciej Ciemborowicz's real-world report corroborates the necessity of hooks for tools that do not control the worktree's creation or removal. Junio C Hamano's fundamental objection to hooks remains unresolved, but this v3 series is now in `seen` pending further discussion.

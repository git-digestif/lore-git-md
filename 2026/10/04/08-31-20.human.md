This is a feature patch series that introduces a "matching-inspired" fetch mode to solve a performance problem in shallow repositories. When a user clones with `--depth`, a plain `git fetch` or `git pull` can hang or take minutes because Git negotiates history for *every* remote branch. The series avoids this by dynamically fetching only the branches that local branches already track at the remote.

The v6 cover letter is a routine resend: the only change from v5 is a one-line commit-message fix in patch 3/4 (removing a leftover reference to the now-deleted default-branch logic). The rest of the series is technically identical to v5, which Junio already marked “Will replace” and is ready for `seen`. All four patches are small, focused, and well-tested: patch 1/4 adds the new `remote.<name>.refmap` configuration, patch 2/4 implements the dynamic branch enumeration, patch 3/4 adds the `--limited-fetch` flag to `git remote add`, and patch 4/4 makes that flag the default in shallow repositories.

The design is now settled. Earlier versions tried special refspec syntax (`+:`), automatic default-branch fetching, and opt-in config; the current approach reuses Git’s existing `--refmap` mechanism and makes the feature implicit only in shallow repos. Junio’s only remaining nit was the stale commit-message wording, which is now fixed. No substantive objections have been raised since v4, and the test coverage is thorough (new tests in `t/t5586-fetch-refmap.sh` and updates to `t/t5505-remote.sh` and `t/t5510-fetch.sh`).

If you work with shallow clones of large repos, this series is worth watching: it should land in `seen` shortly and graduate to `next` in the next integration cycle.

This thread is about a bugfix for Git’s fsmonitor and untracked cache subsystems. The patch, posted by Ilia via GitGitGadget, addresses a specific edge case: when the fsmonitor daemon sends a trivial response (`"/"`), Git marks all index entries as dirty but fails to invalidate stale untracked cache entries. This can cause `git status` to show phantom untracked files or emit spurious warnings about missing directories.

The fix introduces a new function, `untracked_cache_invalidate_stale_dirs()`, which recursively checks each cached directory’s on-disk stat data before the untracked cache is written to the index. The check is performed only when the fsmonitor extension is written and the untracked cache is no longer trusted, avoiding unnecessary overhead. The patch touches `fsmonitor.c`, `fsmonitor.h`, and adds test coverage in `t/t7519-status-fsmonitor.sh` and `t/t7527-builtin-fsmonitor.sh`.

Derrick Stolee, a recognized expert in Git’s performance and scalability, reviewed the patch and gave it a clear **LGTM**. He initially missed Ilia’s patch while working on his own fix for the same issue, which took a more aggressive approach by clearing the entire untracked cache. Stolee’s testing showed his approach incurred a 50-75% performance penalty, while Ilia’s patch introduced no measurable overhead, making it the better solution. Stolee’s review engaged with the implementation details, raising minor concerns about recursive traversal and error handling but ultimately endorsing the design. The patch is now under review with no open questions or objections, and Stolee’s feedback suggests it is likely to be merged soon.

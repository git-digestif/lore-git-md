This thread is about a targeted bugfix for a subtle correctness issue in Git's fsmonitor and untracked cache subsystems. Ilia (via GitGitGadget) identified a problem where trivial fsmonitor responses—such as those sent after a daemon restart or event loss—cause Git to mark all index entries as dirty without invalidating stale untracked cache entries. This leads to two observable bugs: untracked files may incorrectly persist in `git status` output after their directories are removed, and Git may emit spurious warnings about missing directories.

The fix introduces a new function, `untracked_cache_invalidate_stale_dirs()`, which recursively checks each cached directory against its on-disk stat data before the untracked cache is written to the index. This ensures stale entries—those whose directories no longer exist or whose stat data no longer matches—are invalidated. The check is performed only when necessary: when the fsmonitor extension is written and the untracked cache is no longer trusted (i.e., `use_fsmonitor` is false). This avoids unnecessary overhead for commands that don’t write the index or for sparse index writes, which discard the fsmonitor extension anyway.

The patch includes thorough test coverage in `t/t7519-status-fsmonitor.sh` and `t/t7527-builtin-fsmonitor.sh`, exercising the scenario with both hook-based and built-in fsmonitor backends. The tests confirm that after a trivial response, commands like `git add` or `git checkout`—which don’t scan for untracked files—correctly invalidate stale cache entries, preventing subsequent `git status` from trusting them. The implementation is narrowly scoped, well-motivated, and low-risk, addressing a specific edge case with a targeted solution. No objections or requests for changes have been raised so far, and the fix appears ready for integration.

This thread is about a small but important bugfix for Git's fsmonitor feature. When the fsmonitor daemon restarts or loses events, it sends a trivial response (`"/"`), which tells Git to mark all index entries as dirty—but until now, it didn't invalidate stale untracked cache entries. This could cause `git status` to show files that no longer exist or emit spurious warnings about missing directories.

The patch, authored by Ilia, introduces a new function `untracked_cache_invalidate_stale_dirs()` that checks each cached directory against its on-disk state when the fsmonitor daemon sends a trivial response. The fix is narrowly scoped to avoid unnecessary overhead: it only runs when the fsmonitor extension is written and the untracked cache is untrusted, and it performs just one `lstat()` per cached directory. Derrick Stolee reviewed the patch, confirmed its performance advantage over a broader "clear everything" approach, and gave it his LGTM. Junio C Hamano, the maintainer, resolved the last implementation questions (recursion safety and error handling) in favor of the current design.

Ilia has now updated the patch to address Junio’s feedback: when `repo_get_work_tree()` fails, the code now invalidates the entire untracked cache rather than returning an error, and redundant comments have been removed from the tests. The patch is now ready for integration, with no open questions or objections. It’s a well-scoped, low-overhead fix that should resolve the edge case without introducing regressions.

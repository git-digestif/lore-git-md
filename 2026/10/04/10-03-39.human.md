This is a follow-up in the ongoing discussion about whether and how to integrate incremental rebase conflict resolution into Git. Phillip Wood chimes in to endorse Patrick Steinhardt’s suggestion that the functionality would be best integrated directly into `git rebase` itself, rather than as a standalone script in `contrib/` or distributed separately.

Phillip proposes adding an `--incremental` or `--progressive` option to `git rebase`, with a strong preference for a *single-shot* workflow: the user would run `git rebase --incremental <target>` once, and `git rebase --continue` would automatically handle rebasing onto progressively more recent bases until the target is reached. This contrasts with the *multi-shot* approach of the existing scripts (including Alejandro Colomar’s `git-rebase-walk` and `git-bisect-rebase`), where the user must repeatedly invoke the script or `git rebase --continue` to advance through each conflicting commit. Phillip argues that a single-shot workflow is more intuitive and avoids confusion about when the rebase is truly complete.

The comment is substantive: it engages with the interface design and user experience of the proposed feature, rather than just the underlying algorithm or implementation. Phillip’s preference for a single-shot workflow is likely to carry weight, given his deep expertise in the rebase and sequencer subsystems. His input shifts the discussion toward how the feature should behave if integrated into `git rebase`, rather than whether a standalone script should be included in `contrib/`. No new technical objections are raised, but the thread now has a clearer vision of what a polished, built-in implementation might look like.

This is the first patch in the v6 series introducing `remote.<name>.refmap` configuration, the foundational piece of the matching-inspired fetch mode for shallow repositories. The patch adds a new per-remote configuration variable, `remote.<name>.refmap`, which provides the default value for the `--refmap` command-line option, mirroring how `remote.<name>.fetch` provides default refspecs. The implementation updates `remote.c` to parse the new configuration, extends `builtin/fetch.c` to use the configured refmap as the default `--refmap` value, and documents the feature in `config/remote.adoc` and `fetch-options.adoc`. Tests in `t/t5510-fetch.sh` verify the configuration behaves identically to the `--refmap` command-line option.

The patch is technically straightforward and well-scoped: it introduces the configuration variable, integrates it into the fetch logic, and ensures it behaves like its command-line counterpart. The documentation wording is precise, defining `remote.<name>.refmap` as "used to map remote refs being fetched to remote-tracking refs to store," which directly addresses Junio C Hamano’s earlier review request. The test coverage is thorough, verifying that the configuration acts like `--refmap` on the command line and does not interfere with existing behavior. No substantive objections remain, and the patch is ready for integration.

Files touched include `remote.c` (parsing and storage), `builtin/fetch.c` (integration with fetch logic), `remote.h` (struct extension), and documentation in `config/remote.adoc` and `fetch-options.adoc`. The patch does not change on-disk formats beyond the new configuration entry in `.git/config`. The only notable edge case is that `remote.<name>.refmap` has no effect when there are no explicit refspecs to fetch (command-line or via `remote.<name>.fetch`), which is consistent with the behavior of `--refmap` itself. This patch sets the stage for Patch 2/4, which implements the dynamic branch enumeration logic that makes the matching-inspired fetch mode work.

This is the maintainer’s follow-up to the v6 series introducing a "matching-inspired" fetch mode for shallow repositories. Junio C Hamano identifies one implementation glitch and one unresolved design question, both triggered by a new test scenario he attaches.

The glitch: when `remote.<name>.refmap` is configured but no local branch tracks the remote, the current code still throws the error “fatal: --refmap option is only meaningful with command-line refspec.” This is inconsistent with the design goal that `remote.<name>.refmap` should behave as if `--refmap` were given on the command line. The error disappears later in the series once tracking branches exist, but it should not appear at all.

The design question: what should happen when both `remote.<name>.fetch` and `remote.<name>.refmap` are set? The current code dies with the same “fatal: --refmap option is only meaningful…” message, which is not a user-friendly explanation. Junio lists three plausible behaviors—error out, ignore `.refmap` and use `.fetch`, or ignore `.fetch` and use `.refmap`—but does not endorse any.

The attached test script (`t/t5586-fetch-refmap.sh`) exercises both issues. It first verifies that a plain `git fetch` against a refmap-only remote (no tracking branches) succeeds and fetches nothing, then checks that an explicit refspec on the command line works, and finally exposes the glitch when both `.fetch` and `.refmap` are present.

Junio’s tone is constructive; he is not blocking the series but wants these two points resolved before queuing. The ball is now back in Harald Nordgren’s court to propose a fix for the glitch and a design choice for the configuration conflict.

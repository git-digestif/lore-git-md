## Notable threads

### Unified `post-worktree` hook (v3)
Domen Kožar posted v3 of the unified `post-worktree` hook series, replacing the earlier v2 proposal for three separate hooks (`post-worktree-add`, `post-worktree-remove`, `post-worktree-move`) with a single hook that uses a subcommand-style interface. The hook takes four arguments: the event name (`add`, `move`, or `remove`), the worktree identifier, the old absolute path, and the new absolute path. Empty strings are used for non-applicable paths (e.g., no new path for `remove`). The hook runs in the repository where the command was invoked, not the affected worktree, and its exit status is propagated to the caller but does not affect the operation’s outcome.

The implementation touches `builtin/worktree.c` and adds comprehensive test coverage in `t/t2400-worktree-add.sh` and `t/t2403-worktree-move.sh`. The series directly addresses the thread’s core goal: providing reliable observability for worktree lifecycle events even when the caller is uncontrolled (e.g., IDEs, manual deletion). Domen argues that hooks and ownership identifiers (like Kristoffer Haugsbakk’s `--id=<string>` counterproposal) serve complementary purposes—hooks for observability, IDs for ownership—and Maciej Ciemborowicz’s real-world report corroborates the necessity of hooks for tools that do not control the worktree’s creation or removal. The series remains in `seen` pending resolution of Junio C Hamano’s fundamental objection to hooks.

### `--[no-]range-diff-notes` feature series (v5)
Kristoffer Haugsbakk’s feature series adding `--[no-]range-diff-notes` options to `git format-patch` reached technical completion and is ready for integration. The v5 iteration incorporates Junio C Hamano’s final editorial feedback, condensing the commit message for patch 2/2 to remove a meandering explanation of why `--[no-]range-diff-notes` does not error out when used without `--range-diff`. The series introduces two new CLI options: `--range-diff-notes=<ref>` (requires an explicit ref argument) and `--no-range-diff-notes` (suppresses notes in the range-diff without fallback). The interaction rule is simple: if no range-diff notes options are given, the range-diff uses the same notes as the patches; otherwise, it uses only the explicitly specified notes (including none).

The implementation touches `builtin/log.c`, updates `Documentation/git-format-patch.adoc`, and adds comprehensive tests in `t/t3206-range-diff.sh`. The series is now technically complete, with all maintainer feedback from v1 through v4 addressed. Junio’s queue is the next step.

### `git repack --dry-run --drop-filtered` regression
Coy Geek reported a critical regression in `git repack --dry-run --drop-filtered`: the command incorrectly writes new promisor packs and (with `-d`) deletes old packs, violating its documented promise to only list candidate objects without mutating repository storage. The report includes a self-contained Python reproduction script that demonstrates the bug in Git 2.56.0. The script creates disposable repositories, disables ambient Git configuration, and snapshots the pack directory before/after each command. The output shows that both `git repack -a --filter=blob:limit=1m --drop-filtered --dry-run` and the same command with explicit `-d` exit successfully but add four new files (`.pack`, `.idx`, `.promisor`, `.rev`) and (in the `-d` case) delete the original 12 pack files.

The author traces the issue to `builtin/repack.c`, where execution continues past the candidate-printing block despite `dry_run` being set. The manual’s explicit guarantee ("List the objects that would be dropped... without rebuilding any pack or deleting anything") is cited, and the original implementation discussion (v5 of the `--drop-filtered` series) is referenced to underscore the intended behavior. The report is credible and actionable, with clear validation criteria for a fix.

### `remote.<name>.refmap` design ambiguity
Junio C Hamano identified a glitch and a design ambiguity in Harald Nordgren’s v6 series introducing `remote.<name>.refmap` and a matching-inspired fetch mode for shallow repositories. When both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, the current code errors out with "fatal: --refmap option is only meaningful with command-line refspec". Junio provided a test script demonstrating the issue and invited discussion on how to resolve the ambiguity (e.g., precedence rules, merging, or explicit rejection).

The glitch is straightforward, but the design question is more subtle: what should happen when both settings are configured? Junio does not propose an answer, only noting that the current behavior (an unhelpful fatal error) is not acceptable. The test script exercises three scenarios: a refmap-only remote with no tracking branches, a refmap-only remote with an explicit command-line refspec, and a remote with both refmap and fetch refspec. The series remains blocked until this design point is settled.

### `git branch --delete-merged` squash/rebase detection
Harald Nordgren reported iterating on the `git branch --delete-merged` squash/rebase detection code to share logic between branches, achieving noticeable speed improvements. He questioned whether an optimization toggle (e.g., disabling patch-id checks) is still needed if performance is acceptable. Phillip Wood had earlier identified inefficiencies in the current implementation (recalculating upstream diffs for each branch) and proposed adopting `git cherry`-style batching and precomputation. For squash merges, Phillip suggested a lightweight optimization: if an upstream commit’s second parent tree exactly matches the branch tip, the branch can be considered squash-merged without running the full patch-id check.

The discussion remains open on two fronts: whether the performance optimizations will be sufficient for large repositories or blobless clones, and whether a CLI option or config flag is still needed to control the behavior. Harald’s focus on sharing logic between branches suggests he may be exploring a similar approach to Phillip’s proposed optimization.

## In brief
- **`git branch --delete-merged` default pattern (v2)**: Harald Nordgren posted v2 of the patch making `git branch --delete-merged` default to all upstreams when no pattern is given. Phillip Wood objected to the use of `PARSE_OPT_LASTARG_DEFAULT`, arguing it creates a usability trap: future options could break the default behavior depending on their position. He suggested using a `--` separator to explicitly mark the end of upstream patterns.
- **Zsh completion regression risk**: SZEDER Gábor identified a regression risk in the Zsh completion patch: the current implementation would incorrectly exclude all arguments from the second word onward (e.g., `-C dir`, `-c foo.bar=baz`, `file1`, `file2`) in commands like `git -C dir -C subdir -c foo.bar=baz add file1 file2 <TAB>`, rather than just the file arguments. Fionn clarified that the patch’s indexing is intended to skip the subcommand but did not address the technical flaw in the exclusion logic.
- **`git stash` refactoring**: Phillip Wood replaced a hard-coded integer (`2`) with the named constant `INCLUDE_ALL_FILES` in the option-parsing code for `git stash --all`, improving code consistency.
- **fsmonitor untracked cache invalidation**: Ilia introduced `untracked_cache_invalidate_stale_dirs()` to invalidate stale untracked cache entries when the fsmonitor daemon sends a trivial response (`"/"`). The function recursively checks each cached directory against its on-disk stat data, ensuring stale entries are invalidated before the untracked cache is written to the index.
- **CI leak sanitizer annotation links**: Harald Nordgren acknowledged the broken annotation links in the CI leak sanitizer series and framed them as a secondary feature. He argued that the primary goal (improved leak reporting) should take precedence but did not propose a technical solution or address Phillip Wood’s request for concrete commit-message examples.
- **`gitbreaking-changes(7)` reference format**: Junio C Hamano conceded that the hybrid URL+message-ID format for references in `gitbreaking-changes(7)` is not viable due to Asciidoctor rendering the message-ID as a `mailto:` link. He withdrew his objection to plain URLs, accepting them as the pragmatic solution.
- **Incremental rebase conflict resolution**: Phillip Wood endorsed Patrick Steinhardt’s preference for integrating incremental rebase conflict resolution into `git rebase` itself rather than as a standalone script. He proposed `--incremental` or `--progressive` as potential option names and advocated for a single-shot workflow where `git rebase --continue` automatically advances to the next conflicting commit.

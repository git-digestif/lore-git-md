Thread identity: Bugfix patch series (single patch) addressing a regression in shallow fetches when backfilling tags, authored by Karthik Nayak. This is the second iteration (v2) of the patch, now under deeper maintainer scrutiny.

Core problem or goal: Fix a performance regression in shallow fetches introduced by commit 0e358de64a ("fetch: use batched reference updates", 2025-05-19). The regression occurs because batched updates delay committing references to disk until after tag backfilling begins, causing the client to report no 'have' references during negotiation, forcing the server to send all objects since backfilling lacks a depth limit.

Current status: Under review; v2 is posted but Junio C Hamano's review raises substantive questions about edge cases that may require a v3. The patch splits the reference transaction into two (fetched references and backfilled tags) to restore correct negotiation behavior while preserving most performance benefits. The two-transaction approach remains the agreed fix, but its robustness in edge cases (empty main transactions, `--atomic` fetches, and cleanup path control flow) is now in question.

Key technical details:
- Files touched: `builtin/fetch.c`
- New test: `t/t5510-fetch.sh` (verifies shallow fetches don't refetch objects during tag backfilling via `git cat-file` inspection)
- Subsystem: fetch (shallow fetches, tag backfilling, reference transactions)
- Behavior change: Restores correct 'have' reference reporting during negotiation for shallow fetches with tags
- Performance impact: Fix is 17.38±0.61× faster than pre-batched-update behavior; two-transaction approach is 1.01× slower than single-transaction but still significantly faster than no batched updates
- Root cause: Batched updates delay reference commits until after tag backfilling, preventing 'have' reference reporting during negotiation
- Protocol constraint: Tag backfilling requires negotiation for nested annotated tags (server advertises both tag OID and recursively peeled non-tag OID)
- Edge cases raised by Junio:
  - Empty main transaction: Can the regression occur when no refs are updated (only `tags_ref_map` work)?
  - `--atomic` fetches: Skipping the two-transaction fix for atomicity may force full clones if tag backfilling triggers the negotiation issue
  - Cleanup path: Jumping to `cleanup` on transaction failure skips post-fetch steps (`FETCH_HEAD` write, upstream config) even if the primary fetch succeeded

Open questions and loose ends:
- Can the regression manifest when the main fetch transaction is empty (only tag backfilling occurs)?
- Does the `--atomic` exception create a correctness gap for atomic fetches with tag backfilling?
- Should post-fetch steps execute even if the tag backfill transaction fails?

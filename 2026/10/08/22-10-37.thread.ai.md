Thread identity: Bugfix patch series (single patch) addressing a regression in shallow fetches when backfilling tags, authored by Karthik Nayak. This is the fourth iteration (v4) of the patch, implementing Patrick Steinhardt’s proposed design to expose pending transaction state via the transport’s `negotiation_include_tips` field, replacing the v3 two-transaction approach.

Core problem or goal: Fix a performance regression in shallow fetches introduced by commit 0e358de64a ("fetch: use batched reference updates", 2025-05-19). The regression occurs because batched updates delay committing references to disk until after tag backfilling begins, causing the client to report no 'have' references during negotiation, forcing the server to send all objects. The v4 patch resolves this by exposing the already-fetched refs to negotiation via `negotiation_include_tips`, restoring correct 'have' reporting while preserving atomicity for `--atomic` fetches.

Current status: Under active review; v4 implements the pending-transaction "haves" proposal, addressing all prior feedback and design concerns. The patch is well-motivated, thoroughly tested, and appears ready for `next` unless new concerns emerge about the `negotiation_include_tips` mechanism or its scalability implications. The two-transaction approach from v3 is now superseded by this design.

Key technical details:
- Files touched: `builtin/fetch.c` (use of `negotiation_include_tips` to expose pending transaction state)
- New tests: Three additions to `t/t5510-fetch.sh` verifying (1) backfilling tags advertises fetched refs as 'haves' in non-atomic flow, (2) same in atomic flow, and (3) upstream tracking info is set and tags are backfilled even when a sibling ref is rejected.
- Subsystem: fetch (shallow fetches, tag backfilling, reference transactions, negotiation protocol, GC safety)
- Behavior change: Restores correct 'have' reference reporting during negotiation for shallow fetches with tags by exposing pending transaction state via `negotiation_include_tips`. Preserves atomicity for `--atomic` fetches, eliminating the limitation of the v3 two-transaction approach.
- Performance impact: Fix is 17.38±0.61× faster than pre-batched-update behavior; v4 avoids intermediate commits while maintaining batched update benefits, with minimal performance overhead.
- Root cause: Batched updates delayed reference commits until after tag backfilling, preventing 'have' reference reporting during negotiation.
- Protocol constraint: Tag backfilling requires negotiation for nested annotated tags (server advertises both tag OID and recursively peeled non-tag OID).
- Edge cases resolved:
  - Empty transactions: Handled by exposing pending transaction state regardless of transaction initialization.
  - `--atomic` fetches: Atomicity is preserved by avoiding intermediate commits.
  - Error handling: Errors from the transaction are logged but do not halt the fetch, as batched updates allow partial success. Post-fetch operations execute even if the transaction failed to initialize.
  - Cleanup path: Post-fetch steps (`FETCH_HEAD` write, upstream config) execute regardless of transaction success, as these steps are independent of transaction state.
- Design rationale: The `negotiation_include_tips` mechanism is viable because the objects are already present and `.keep` locks are already relied upon to prevent GC, addressing prior GC safety concerns.
- Scalability consideration: The v4 patch may cause the client to advertise *all* local references (not just the newly fetched ones) during negotiation if the pending transaction state includes them. This could flood the server with millions of "haves" in large repositories, though this may be an acceptable trade-off for correctness. The commit message should explicitly discuss this potential impact.

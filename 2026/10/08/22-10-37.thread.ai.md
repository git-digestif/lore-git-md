Thread identity: Bugfix patch series (single patch) addressing a regression in shallow fetches when backfilling tags, authored by Karthik Nayak.

Core problem or goal: Fix a performance regression in shallow fetches introduced by commit 0e358de64a ("fetch: use batched reference updates", 2025-05-19). The regression occurs because batched updates delay committing references to disk until after tag backfilling begins, causing the client to report no 'have' references during negotiation, forcing the server to send all objects since backfilling lacks a depth limit.

Current status: Under review. This is the first iteration of the patch. The patch splits the reference transaction into two: one for fetched references and another for backfilling tags, restoring correct negotiation behavior while preserving most of the performance benefits of batched updates. Patrick Steinhardt's review accepted the two-transaction approach as a reasonable trade-off. Justin Tobler's reply confirms that tag backfilling cannot skip negotiation entirely for nested annotated tags, as the protocol requires fetching intermediate objects to resolve chains of tags, reinforcing the correctness of the current fix.

Key technical details:
- Files touched: `builtin/fetch.c`
- New test: `t/t5510-fetch.sh` (verifies shallow fetches don't refetch objects during tag backfilling by checking packet traces; Patrick suggests a more direct assertion to verify no re-fetch of objects)
- Subsystem: fetch (shallow fetches, tag backfilling, reference transactions)
- Behavior change: Restores correct 'have' reference reporting during negotiation for shallow fetches with tags
- Performance impact: Fix runs 17.38±0.61 times faster than pre-batched-update behavior; slightly slower than the single-transaction approach but still significantly faster than no batched updates. Patrick notes a missing benchmark comparison (HEAD~ vs HEAD) to quantify the performance cost of the fix, though this is not a blocker.
- Root cause: Batched updates delay reference commits until after tag backfilling, preventing the client from reporting 'have' references during negotiation
- Protocol clarification: Tag backfilling requires negotiation for nested annotated tags because the server advertises both the tag reference OID and its recursively peeled non-tag OID, necessitating intermediate object fetches to resolve the full chain.

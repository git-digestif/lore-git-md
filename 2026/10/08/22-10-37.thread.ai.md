Thread identity: Bugfix patch series (three patches) addressing a regression in shallow fetches when backfilling tags, authored by Karthik Nayak. This is the fifth iteration (v5) of the patch, now split into three commits to resolve a memory management blocker. The series targets the fetch subsystem, fixing a performance regression introduced by commit 0e358de64a ("fetch: use batched reference updates", 2025-05-19).

Core problem or goal: Fix a performance regression in shallow fetches where batched reference updates delayed committing references until after tag backfilling, causing the client to report no 'have' references during negotiation and forcing the server to send all objects. The solution exposes pending transaction state via the transport's `negotiation_include_tips` field, restoring correct 'have' reporting while preserving atomicity for `--atomic` fetches. The scalability trade-off (advertising all fetched references during negotiation) is documented as an acceptable O(n) complexity for fetched refs.

Current status: Under active review; the memory management blocker from v4 has been resolved by the precursor patch (1/3) introducing `transport_options_release()`, ensuring proper cleanup for all transport types. The **core fix (patch 2/3)** implements the pending-transaction "haves" design in `builtin/fetch.c` and adds tests to verify 'have' reporting during tag backfilling for both atomic and non-atomic flows. The series is ready for maintainer review, with no outstanding technical objections. Junio C Hamano's review remains the sole blocker. Patrick Steinhardt's surface-level feedback on patch 1/3 (commit message wording, now addressed by dropping "a new") and on patch 3/3 (commit ordering for narrative clarity) has been acknowledged; Karthik Nayak plans to reorder the commits locally but will not re-roll the series unless further feedback arrives.

Key technical details:
- Files touched: `builtin/fetch.c` (core fix: collecting fetched ref OIDs into `fetched_tips` and appending them to `negotiation_include_tips` during `backfill_tags()`), `t/t5510-fetch.sh` (three new tests: two verifying 'have' reporting for atomic/non-atomic fetches, one verifying upstream tracking info persistence after rejected updates), `transport-helper.c` (memory leak fix in cleanup path, patch 1/3), `transport.c` (introducing `transport_options_release()`, patch 1/3), `transport.h` (declaration of new function, patch 1/3).
- New symbols: `fetched_tips` (temporary `oid_array` in `do_fetch()`), `transport_options_release()` (new function for transport cleanup).
- Behavior change: Restores correct 'have' reference reporting during negotiation for shallow fetches with tags by exposing the OIDs of just-fetched refs via `negotiation_include_tips`. Preserves atomicity for `--atomic` fetches.
- Performance impact: Fix is 17.38±0.61× faster than pre-batched-update behavior; v5 avoids intermediate commits while maintaining batched update benefits.
- Root cause: Batched updates delayed reference commits until after tag backfilling, preventing 'have' reference reporting during negotiation.
- Memory management: The precursor patch (1/3) fixes a pre-existing memory leak in the remote-helper transport's cleanup path by introducing `transport_options_release()`, ensuring proper cleanup for all transport types. The core fix (2/3) relies on this mechanism, eliminating manual cleanup and mitigating shared-state risks. The leak was not caught by CI because no tests previously exercised the remote-helper transport's cleanup path.
- Edge cases resolved:
  - Empty transactions: Handled by exposing pending transaction state regardless of transaction initialization.
  - `--atomic` fetches: Atomicity is preserved by avoiding intermediate commits.
  - Error handling: Errors from the transaction are logged but do not halt the fetch, as batched updates allow partial success. Post-fetch operations execute even if the transaction failed to initialize.
  - Cleanup path: Post-fetch steps (`FETCH_HEAD` write, upstream config) execute regardless of transaction success, as these steps are independent of transaction state. Cleanup is now unconditional as per review feedback.
  - Rejected updates: Upstream tracking information is written even when some reference updates are rejected during a batched fetch (verified by new test in patch 3/3).
- Test coverage: Three new tests in `t/t5510-fetch.sh` verify (1) 'have' reporting during tag backfilling for non-atomic fetches, (2) 'have' reporting during tag backfilling for atomic fetches, and (3) persistence of upstream tracking information after rejected updates. The test for upstream tracking persistence will be moved before the core fix (patch 2/3) in the next re-roll to improve narrative clarity.

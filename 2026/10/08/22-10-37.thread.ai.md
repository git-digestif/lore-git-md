Thread identity: Bugfix patch series (single patch) addressing a regression in shallow fetches when backfilling tags, authored by Karthik Nayak. This is the fifth iteration (v5) of the patch, implementing Patrick Steinhardt’s proposed design to expose pending transaction state via the transport’s `negotiation_include_tips` field, replacing the v3 two-transaction approach and incorporating minor cleanups from v4 review feedback.

Core problem or goal: Fix a performance regression in shallow fetches introduced by commit 0e358de64a ("fetch: use batched reference updates", 2025-05-19). The regression occurs because batched updates delay committing references to disk until after tag backfilling begins, causing the client to report no 'have' references during negotiation, forcing the server to send all objects. The patch resolves this by exposing the already-fetched refs to negotiation via `negotiation_include_tips`, restoring correct 'have' reporting while preserving atomicity for `--atomic` fetches. The scalability trade-off (potential flooding of "haves" in large repositories) is documented in the commit message as an acceptable O(n) complexity for fetched refs, but a new memory management concern about shared `negotiation_include_tips` state may require redesign.

Current status: Under active review; v5 is pending resolution of a **blocker-level memory management issue** raised by Patrick Steinhardt. The issue stems from the v4 patch’s approach to appending fetched OIDs to `negotiation_include_tips` without accounting for shared ownership of the `oid_array`. This could leak memory or corrupt negotiation state if the array is reused by other callers. The patch is not ready for `next` until this is addressed. The two-transaction approach from v3 is superseded, but the current design may need revisiting if the memory management cannot be resolved cleanly.

Key technical details:
- Files touched: `builtin/fetch.c` (use of `negotiation_include_tips` to expose pending transaction state, with local `struct oid_array` for memory management).
- New tests: Two additions to `t/t5510-fetch.sh` retained from v4, verifying (1) backfilling tags advertises fetched refs as 'haves' in non-atomic flow, and (2) same in atomic flow. The third test (upstream tracking with rejected sibling refs) is split into a separate patch as it is tangential to the core fix.
- Subsystem: fetch (shallow fetches, tag backfilling, reference transactions, negotiation protocol, GC safety).
- Behavior change: Restores correct 'have' reference reporting during negotiation for shallow fetches with tags by exposing pending transaction state via `negotiation_include_tips`. Preserves atomicity for `--atomic` fetches, eliminating the limitation of the v3 two-transaction approach.
- Performance impact: Fix is 17.38±0.61× faster than pre-batched-update behavior; v5 avoids intermediate commits while maintaining batched update benefits. The scalability trade-off (advertising all local references during negotiation in large repos) is documented as an acceptable O(n) complexity for fetched refs, but the memory management issue may introduce correctness risks.
- Root cause: Batched updates delayed reference commits until after tag backfilling, preventing 'have' reference reporting during negotiation.
- Protocol constraint: Tag backfilling requires negotiation for nested annotated tags (server advertises both tag OID and recursively peeled non-tag OID).
- Edge cases resolved:
  - Empty transactions: Handled by exposing pending transaction state regardless of transaction initialization.
  - `--atomic` fetches: Atomicity is preserved by avoiding intermediate commits.
  - Error handling: Errors from the transaction are logged but do not halt the fetch, as batched updates allow partial success. Post-fetch operations execute even if the transaction failed to initialize.
  - Cleanup path: Post-fetch steps (`FETCH_HEAD` write, upstream config) execute regardless of transaction success, as these steps are independent of transaction state. Cleanup is now unconditional as per review feedback.
- **New issue**: The v4 patch appends fetched OIDs to `negotiation_include_tips` without ensuring exclusive ownership of the `oid_array`. This could leak memory or corrupt negotiation state if the array is reused by other callers. The transport API does not guarantee exclusive control over `negotiation_include_tips`, making this a correctness risk.
- Design rationale: The `negotiation_include_tips` mechanism is viable because the objects are already present and `.keep` locks are already relied upon to prevent GC, addressing prior GC safety concerns.
- Code cleanups: Local `struct oid_array` for memory management, inlined loop variable, and unconditional cleanup as suggested by Patrick Steinhardt in v4.

Open questions and loose ends:
- How will the memory management issue be resolved? Options include (1) documenting and enforcing exclusive ownership of `negotiation_include_tips` during tag backfilling, or (2) copying the existing array before appending fetched tips to avoid side effects.
- Are there alternative designs that avoid shared state entirely (e.g., passing a separate `oid_array` for fetched tips)?
- Junio C Hamano’s position remains unvoiced; the patch is not ready for maintainer review until the memory management issue is resolved.

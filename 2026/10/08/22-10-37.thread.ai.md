Thread identity: Bugfix patch series (single patch) addressing a regression in shallow fetches when backfilling tags, authored by Karthik Nayak. This is the third iteration (v3) of the patch, refining edge-case handling and error-path robustness after maintainer and reviewer feedback.

Core problem or goal: Fix a performance regression in shallow fetches introduced by commit 0e358de64a ("fetch: use batched reference updates", 2025-05-19). The regression occurs because batched updates delay committing references to disk until after tag backfilling begins, causing the client to report no 'have' references during negotiation, forcing the server to send all objects since backfilling lacks a depth limit. The fix restores correct 'have' reference reporting by splitting the reference transaction into two phases: committing fetched references before backfilling tags.

Current status: Under review; v3 addresses prior edge-case concerns (empty transactions, `--atomic` fetches, cleanup path control flow) but Justin Tobler’s substantive review of v3 raises new questions about error handling and transaction flow. The two-transaction approach remains the agreed fix, but the error-path logic (logging errors from the first transaction while continuing to the second, and carrying forward post-fetch operations even if the first transaction failed to initialize) is now under scrutiny. The patch is not yet ready for `next` until these points are resolved.

Key technical details:
- Files touched: `builtin/fetch.c`
- New tests: Two additions to `t/t5510-fetch.sh` verifying (1) backfilling tags advertises fetched refs as 'haves' and (2) upstream tracking info is set even when the main ref update is rejected but a tag is backfilled.
- Subsystem: fetch (shallow fetches, tag backfilling, reference transactions)
- Behavior change: Restores correct 'have' reference reporting during negotiation for shallow fetches with tags by committing fetched references before tag backfilling begins.
- Performance impact: Fix is 17.38±0.61× faster than pre-batched-update behavior; two-transaction approach is 1.01× slower than single-transaction but still significantly faster than no batched updates.
- Root cause: Batched updates delayed reference commits until after tag backfilling, preventing 'have' reference reporting during negotiation.
- Protocol constraint: Tag backfilling requires negotiation for nested annotated tags (server advertises both tag OID and recursively peeled non-tag OID).
- Edge cases resolved in v3:
  - Empty main transaction: Handled by ensuring post-fetch operations execute regardless of transaction initialization.
  - `--atomic` fetches: Documented limitation preserved; atomicity is maintained at the cost of potential full clones if tag backfilling triggers the negotiation issue.
  - Cleanup path: Separate `commit_ref_ret` variable tracks the first transaction’s result, ensuring post-fetch steps (`FETCH_HEAD` write, upstream config) execute even if the tag backfill transaction fails.
- New open questions (from Justin Tobler’s review):
  - Error logging: Why log an error from the first transaction but continue to the second, risking redundant operations or inconsistent state?
  - Early termination: Why carry forward post-fetch operations if the first transaction failed to initialize, potentially masking underlying issues?

Open questions and loose ends:
- Justin Tobler’s two technical questions about error handling and transaction flow (see above) remain unresolved. These are the sole remaining blockers for readiness.

Thread identity: Bugfix patch series (single patch) addressing a regression in shallow fetches when backfilling tags, authored by Karthik Nayak. This is the third iteration (v3) of the patch, refining edge-case handling and error-path robustness after maintainer and reviewer feedback. The thread is now evaluating a new design proposal by Patrick Steinhardt that could replace the current two-transaction approach by supplementing the backfill fetch’s "haves" with pending, uncommitted reference updates from the transaction.

Core problem or goal: Fix a performance regression in shallow fetches introduced by commit 0e358de64a ("fetch: use batched reference updates", 2025-05-19). The regression occurs because batched updates delay committing references to disk until after tag backfilling begins, causing the client to report no 'have' references during negotiation, forcing the server to send all objects. The original fix proposed splitting the reference transaction into two phases (committing fetched references before backfilling tags), but Patrick Steinhardt’s new proposal suggests exposing pending transaction state to negotiation, potentially avoiding the intermediate commit and restoring atomicity for `--atomic` fetches.

Current status: Under review; v3 addressed prior edge-case concerns, and Justin Tobler’s substantive questions about error handling and transaction flow have now been clarified by Karthik Nayak. The two-transaction approach’s logic is now better explained, but its future depends on the outcome of Patrick Steinhardt’s pending-transaction "haves" proposal. The patch is not yet ready for `next`; readiness hinges on either resolving the feasibility of Patrick’s proposal or finalizing the two-transaction approach if the new design is deemed impractical.

Key technical details:
- Files touched: `builtin/fetch.c`, transport structures (potential use of `negotiation_include_tips`)
- New tests: Two additions to `t/t5510-fetch.sh` verifying (1) backfilling tags advertises fetched refs as 'haves' and (2) upstream tracking info is set even when the main ref update is rejected but a tag is backfilled.
- Subsystem: fetch (shallow fetches, tag backfilling, reference transactions, negotiation protocol, GC safety)
- Behavior change: Restores correct 'have' reference reporting during negotiation for shallow fetches with tags. The current patch does this via a two-transaction approach; the new proposal would do so by exposing pending transaction state to negotiation.
- Performance impact: Fix is 17.38±0.61× faster than pre-batched-update behavior; two-transaction approach is 1.01× slower than single-transaction but significantly faster than no batched updates. The pending-transaction proposal is expected to have similar performance but with cleaner atomicity guarantees.
- Root cause: Batched updates delayed reference commits until after tag backfilling, preventing 'have' reference reporting during negotiation.
- Protocol constraint: Tag backfilling requires negotiation for nested annotated tags (server advertises both tag OID and recursively peeled non-tag OID).
- Edge cases resolved in v3:
  - Empty main transaction: Handled by ensuring post-fetch operations execute regardless of transaction initialization.
  - `--atomic` fetches: Documented limitation preserved; atomicity is maintained at the cost of potential full clones if tag backfilling triggers the negotiation issue. The new proposal may eliminate this limitation.
  - Cleanup path: Separate `commit_ref_ret` variable tracks the first transaction’s result, ensuring post-fetch steps (`FETCH_HEAD` write, upstream config) execute even if the tag backfill transaction fails.
  - Error handling: Clarified in response to Justin Tobler’s review. Errors from the first transaction are logged but do not halt the fetch, as batched updates allow partial success. Post-fetch operations execute even if the initial transaction failed to initialize, as these steps are independent of transaction success.
- New design proposal (Patrick Steinhardt):
  - Supplement the backfill fetch’s "haves" with pending, uncommitted reference updates from the transaction.
  - Avoids intermediate commit, potentially restoring atomicity for `--atomic` fetches.
  - Feasibility depends on whether pending transaction state can be safely exposed to negotiation without side effects (GC safety, `.keep` locks vs. durable references).

Open questions and loose ends:
- Feasibility of Patrick Steinhardt’s pending-transaction "haves" proposal:
  - Can pending transaction state be safely exposed to negotiation without side effects (GC safety, `.keep` locks vs. durable references)?
  - Can `negotiation_include_tips` be used to implement this idea without introducing new risks?
  - If the proposal is impractical, will the two-transaction approach proceed with the now-clarified error-handling logic?

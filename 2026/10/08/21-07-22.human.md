This is a **feature patch** that makes `git blame` automatically use a `.git-blame-ignore-revs` file stored in the repository's `HEAD` (as `HEAD:.git-blame-ignore-revs`) if no explicit ignore file is configured. The change aligns local `git blame` behavior with web interfaces like GitHub and GitLab, which already respect this file by default, eliminating user surprise when blame output differs between local and web views.

The patch is now split into two commits. The first hardens the ignore-revs parser and tag-peeling logic to handle security concerns: it rejects lines with embedded NUL bytes (using `memchr` instead of `strchr`) and prevents promisor fetches in partial clones by passing `OBJECT_INFO_SKIP_FETCH_OBJECT` and `OBJECT_INFO_QUICK` flags. The second commit implements the core feature, reading the `HEAD:.git-blame-ignore-revs` blob (not the working tree file) and parsing it in memory with the hardened parser. This ensures the default file is respected even if an untracked or modified working tree file exists, matching hosting platform behavior.

The implementation is careful about precedence and security: the default file is added before user configuration, but an empty `blame.ignoreRevsFile` or `--no-ignore-revs-file` will bypass it entirely. The patch includes thorough test coverage for subdirectory invocations, bare repositories, committed symlinks, malformed input, and CLI/config overrides. Documentation updates clarify the new behavior and override semantics.

This is a well-motivated change that addresses a real user pain point. The v2 patch incorporates maintainer feedback and security hardening, making it more robust than the initial version. The split into two commits (hardening first, feature second) is a sensible approach that isolates security improvements for focused review. The patch is not yet ready for integration—it needs broader community review, particularly from security-interested contributors like Jeff King or brian m. carlson, to validate the adequacy of the hardening measures. If those reviews are positive, this looks like a solid addition to Git's blame subsystem.

This is the third patch in the v3 series fixing a data-loss race in `git repack -d`. It addresses a performance bottleneck in `add_extra_kept_packs()` that would become critical in the next patch, where the `--keep-pack` list may grow to thousands of entries.

The patch sorts the `--keep-pack` list once and replaces linear scans with binary search (`string_list_has_string`), yielding an 11× speed-up (11 seconds → 1 second) when matching 20,000 kept packs against 20,000 repository packs. The comparison function remains `fspathcmp()`, so matching behavior is unchanged. The change is purely internal to `builtin/pack-objects.c` and does not affect any other callers or on-disk formats.

The commit message clearly states the problem (linear scan overhead), the solution (sorting + binary search), and the measured improvement. The test coverage is provided by later patches in the series, particularly the snapshot-based repack fix (patch 5/5), which exercises this code path at scale. The patch is a straightforward optimization with no behavioral changes, making it unlikely to introduce regressions. Reviewers may verify that the sorted list does not interact poorly with future callers expecting insertion order, but the current design is pragmatic and aligns with existing Git conventions.

This is the first patch in a two-patch **bugfix series** addressing a long-standing inconsistency in Git’s index refresh logic. The patch modifies `ie_match_stat()` to stop treating a size mismatch as conclusive evidence of modification when the file is subject to line-ending conversions (or other clean filters). Instead, it falls back to the same conversion-aware check already used for mtime changes, ensuring `git status` aligns with `git diff` and `git add`.

The core change is in `read-cache.c`, where the new helper `size_change_is_conclusive()` determines whether a size difference can be trusted. For converted files, the patch introduces `ce_compare_converted_data()`, which optimizes the comparison by first checking the converted length against the blob size—avoiding the expensive hash step when possible. The optimization is particularly effective for files with CRLF conversions, where the converted length can often be determined by counting CR-LF pairs without full conversion.

The patch also updates `ce_compare_data()` to delegate to the new helper when appropriate, preserving the existing behavior for unconverted files. Test coverage in `t/t0020-crlf.sh` verifies the fix handles both CRLF rewrites (unchanged content) and lone CRs (edge case for `text=auto`), ensuring `git status` reports modifications only when the logical content changes.

Performance measurements in the commit message show the overhead is minimal for clean trees and unconverted files, while resolving a 3x slowdown for stat-dirty converted files after the first run. The patch is self-contained, with no external dependencies, and includes detailed comments explaining the logic. Key symbols introduced or modified: `ie_match_stat()`, `ce_compare_converted_data()`, `size_change_is_conclusive()`, and `count_crlf()`.

This patch directly addresses the inconsistency described in the cover letter, leaving the config escape hatch (`core.convertAwareStatus`) to the second patch. The changes are well-motivated, thoroughly tested, and avoid disrupting existing workflows. No substantive objections or requests for changes have been raised yet.

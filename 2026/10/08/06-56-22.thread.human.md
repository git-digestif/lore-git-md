This thread began when Christian Noé Ramos López reported two critical flaws in Git’s SSH signing verification: (1) key lifetime checks used the committer date (which the signer controls) rather than the signature timestamp, allowing backdated commits to bypass expiration, and (2) Git failed open when the revocation file was configured but missing or unreadable. The first issue is now addressed by a documentation patch clarifying the behavior, though its wording remains under review—Junio C Hamano prefers brevity, while Phillip Wood and Patrick Steinhardt advocate for explicit warnings about the limitations of key lifetime checks. The second issue is fixed by a security bugfix patch from Christian, which makes Git fail closed on revocation file errors by default, with an escape hatch via Git’s `:(optional)` pathname prefix.

The revocation file fix is nearly ready to land, but Junio’s latest review raises a substantive concern: the current patch skips displaying signature information when the revocation file is missing, creating an inconsistency with how unknown keys are handled. He proposes adjusting the error-handling flow to ensure users still see signature details even when verification fails due to a missing revocation file. This is the last technical hurdle; once resolved, the patch will likely be merged quickly. The fix includes new test coverage and updates to the `gpg.ssh.revocationFile` documentation. Christian, Phillip Wood, and Patrick Steinhardt have all contributed to shaping the solution, with broad agreement on the security posture and the use of `:(optional)` as an override.

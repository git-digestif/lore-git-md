The SSH signing verification thread began when Christian Noé Ramos López reported two critical flaws in Git’s SSH signing verification: one where key lifetime checks used the committer date (which the signer controls) instead of the signature timestamp, and another where a missing or unreadable revocation file failed open rather than closed. Both issues are now addressed—one through documentation, the other through a security fix.

The first issue, timestamp confusion, was resolved by a documentation patch from Christian that clarifies Git checks `valid-before`/`valid-after` against the committer or tagger date, not the signature timestamp. Junio C Hamano has since suggested simplifying the wording, arguing the current version’s warnings about key leakage risks are overly verbose. The discussion now centers on how much detail to include in the man page, with no technical disagreement—just a question of whether to explicitly warn users about the limitations of key lifetime checks.

The second issue, revocation file failures, is fixed by Christian’s security patch, which makes Git fail closed when the revocation file is configured but missing or unreadable. The patch adds test coverage and documents the new behavior, allowing users to override the default with Git’s `:(optional)` pathname syntax. Phillip Wood and Patrick Steinhardt helped shape both patches, endorsing the `:(optional)` escape hatch and agreeing on the need for fail-closed behavior. The revocation fix is ready for review and likely to land quickly.

The thread is now focused on finalizing the documentation wording, with Junio’s feedback as the main open question. No further technical changes are expected, and the security fix should proceed independently.

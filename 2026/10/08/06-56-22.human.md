This is a **bugfix** targeting Git's SSH signing verification logic. The author, Christian Noé Ramos López, identifies two related flaws that together prevent reliable revocation of SSH signing keys.

First, the `valid-before` timestamp in the allowed signers file is checked against the commit's author/committer date, which the signer controls. An attacker can backdate a commit to bypass the expiration check, making `valid-before` ineffective for retiring keys. The GPG backend correctly rejects such backdated signatures, but the SSH backend does not.

Second, if the `gpg.ssh.revocationFile` is configured but missing, Git issues a warning and verifies the signature anyway—failing open instead of closed. This contradicts both OpenSSH's behavior (which refuses authentication if the revocation file is missing) and Git's own behavior when the revocation file exists but is unreadable (which fails closed).

The patch is well-motivated, with clear reproduction steps and comparisons to GPG behavior. The author proposes two fixes: either document the current behavior (and its risks) or align with OpenSSH by refusing verification when the revocation file is missing. The issue affects all versions since SSH signing was introduced (Git 2.34.0) and has no existing test coverage. This looks like a straightforward correctness fix that should attract review attention.

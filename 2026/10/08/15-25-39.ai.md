This is a **performance and UX discussion** in the ongoing thread about extending `` `git branch --delete-merged` `` to detect squash-merged and rebase-merged branches. Phillip Wood responds to Harald Nordgren’s follow-up on performance optimizations, reinforcing the need for a way to disable patch-id-based detection—even if the implementation becomes more efficient.

Phillip acknowledges that Harald’s work to share logic between branches may improve performance but argues that squash detection will *always* be slower than the current tip-reachability check, especially in partial clones where blob fetches are required. He maintains that users who know their repository contains only squash merges (and no rebases) would benefit from a lightweight tree-based check, and that a toggle to disable patch-id detection would be useful in such cases. While he agrees that enabling the feature by default is reasonable if it isn’t "diabolically slow," he emphasizes that the performance trade-off justifies keeping the option available.

The exchange leaves the CLI design question unresolved: Harald prefers a single, unified behavior without user-facing controls, while Phillip advocates for a way to opt out of the slower detection method. No new technical details or edge cases are introduced, but Phillip’s position strengthens the case for a performance-oriented CLI option (e.g., `` `--delete-merged=<mode>` ``) or config flag. The discussion remains focused on balancing simplicity with practicality for large or blobless repositories.

This is a contributor housekeeping and feature proposal thread about a new `contrib/` helper script for incremental rebase conflict resolution. The email from Alejandro Colomar introduces `--abort`, `--continue`, and `--quit` options to his `git-bisect-rebase` script, which now provides finer-grained control over the rebase process for complex workflows involving interdependent branches.

Colomar demonstrates how these new options work in practice, showing that they allow users to pause, restart, or exit the bisection-based rebase at any point. This manual control is essential for handling branch trees, where users need to rebase branches in a specific order and verify changes incrementally. The workflow he describes involves resolving conflicts on one branch, then moving to its descendants before returning to the original branch, which would be impossible with a fully automated approach.

The email directly responds to Phillip Wood’s earlier proposal to extend `git rebase --update-refs` to automate rebasing interdependent branches. Colomar argues that manual control is safer and more adaptable for complex dependency graphs, as it avoids the risk of automating steps that might require human judgment. His implementation provides a middle ground: it retains manual control while streamlining the process with dedicated commands for common operations.

The new options in `git-bisect-rebase` are:
- `--abort`: Returns to the original HEAD and cleans up temporary state.
- `--continue`: Restarts the entire bisection process, requiring the current rebase to be resolved first.
- `--quit`: Exits the session without moving HEAD or the branch, allowing the user to switch branches and return later.

This update reinforces `git-bisect-rebase` as the leading candidate for inclusion in `contrib/`, given its alignment with Git’s conventions and Nico Williams’ endorsement. However, the broader question of whether Git should include any helper for this workflow remains unresolved, with Junio C Hamano’s endorsement of `git-imerge` and Patrick Steinhardt’s preference for direct integration into `git rebase` still in play. Colomar’s plan to distribute the script separately (e.g., via `manpages-utils`) reflects the uncertainty around `contrib/` inclusion.

The email is well-motivated and demonstrates a clear use case for the multi-shot workflow, but the debate over the best long-term solution continues. The discussion is substantive, engaging with technical critiques, workflow preferences, and interface design.

This is a **performance-focused reply** in the ongoing discussion about extending `` `git branch --delete-merged` `` to detect squash-merged and rebase-merged branches. Phillip Wood responds to Harald Nordgren’s follow-up on performance optimizations, reinforcing the need for a way to disable the patch-id-based detection in certain scenarios.

Phillip acknowledges Harald’s progress on improving the implementation’s speed but cautions that even an efficient version will still be significantly slower when searching for squash-merged branches, particularly in partial clones where blob downloads add overhead. He argues that users working in repositories that *only* use squash merges (and never rebase them) would benefit from a faster, tree-based check that avoids the expensive patch-id computation. This aligns with his earlier suggestion to short-circuit the squash check if an upstream commit’s second parent tree exactly matches the branch tip.

The key takeaway is that Phillip still advocates for an option to toggle the detection method—even if the default behavior remains enabled—because the performance trade-off is inherent to the problem, not just an implementation detail. His position contrasts slightly with Harald’s preference for simplicity, but Phillip frames the toggle as a practical necessity rather than a user-facing complexity. The discussion remains open on whether this toggle should be a CLI option (e.g., `` `--delete-merged=<mode>` ``) or a config flag, but the underlying need for it is now clearer. No new technical details or edge cases are introduced.

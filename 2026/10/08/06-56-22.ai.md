This is a **security bugfix** targeting Git's SSH signing verification logic. The email reports two closely related flaws in how Git handles SSH-signed commits and tags:

1. **Time-of-signature confusion**: Git checks the `valid-before` timestamp in the allowed signers file against the *committer date* (which the signer controls), not an independent timestamp. This allows a signer to backdate a commit to bypass key expiration. The GPG backend correctly rejects such backdated signatures, but the SSH backend does not.

2. **Revocation file fails open**: When `gpg.ssh.revocationFile` is configured but missing, Git emits a warning and proceeds as if no revocation file exists. This contradicts both OpenSSH's behavior (which fails closed) and the principle of least surprise for security controls. The same flaw exists if the revocation file is unreadable or a directory.

The patch proposes two fixes: (1) document that `valid-before` is checked against the committer date (or change the behavior to match GPG), and (2) make a missing/broken revocation file fail verification rather than warn-and-continue. The author demonstrates the issues with concrete test cases (showing `%G?` status codes and merge outcomes) and notes that the revocation file logic is entirely untested in Git's test suite.

The report is well-structured, with clear reproduction steps, comparison to GPG behavior, and references to prior art (Fabian Stelzer's SSH signing series and Grayson Tinker's related report). The flaws are serious: they undermine the two primary mechanisms for revoking trust in SSH signing keys. The proposed fixes are minimal and align with OpenSSH's security model. No patch is attached, but the email serves as a detailed bug report with actionable recommendations.

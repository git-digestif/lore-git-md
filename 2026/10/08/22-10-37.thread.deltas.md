## 2026/10/09

- [2026/10/09/11-26-17 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt restated the problem in his own words (refs queued in a transaction but not committed, so tag backfill reports no "have" lines and the server may send excess objects), then questioned whether backfilling tags even needs a full negotiated fetch — possibly just requesting the individual tagged objects — while noting uncertainty about whether that would work with nested annotated tags; he also asked for a HEAD~ benchmark to substantiate the claim that the fix is slower than master, confirmed that `commit_ref_transaction()` already handles and prints failures with `rejected_refs` treated additively across both transactions, and observed that the new test only verifies "have" lines are sent to the remote rather than directly verifying objects are not re-fetched.
- [2026/10/09/16-51-01 by Justin Tobler <jltobler@gmail.com>] Justin Tobler answered Patrick Steinhardt's question: tag backfill only fetches tags referencing objects already present locally, using the server-advertised tag OID and its recursively peeled `^{}` OID, but because nested annotated tags can exist, the intermediate objects would still need to be fetched.
- [2026/10/09/22-16-42 by Karthik Nayak <karthik.188@gmail.com>] Karthik Nayak agreed with Justin Tobler, explaining that the protocol transfers the closure of objects between "have" and "want", so for a chain like foo -> tag A -> tag B -> commit C one cannot request A without advertising C, and since "haves" come from committed refs, C is never advertised until refs are written to disk.
- [2026/10/09/22-31-29 by Karthik Nayak <karthik.188@gmail.com>] Karthik Nayak said he had the HEAD~ benchmark but removed it as too much information and will add it back, and acknowledged Patrick Steinhardt's test critique — the trace only says "packfile" without listing contents — saying he will instead check the repo with `cat-file` and clean the test up.

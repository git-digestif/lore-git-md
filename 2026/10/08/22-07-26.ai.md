This email is a follow-up in the ongoing discussion about incremental rebase conflict resolution, specifically demonstrating the implementation of `--abort`, `--continue`, and `--quit` options in Alejandro Colomar’s `git-bisect-rebase` script. These options provide finer-grained control over the rebase process, enabling the manual management of complex branch trees—a requirement Colomar argues is essential for his workflow.

The email details how these new options work in practice. `--abort` reverts to the original HEAD and cleans up temporary state, `--continue` restarts the entire bisection process (after resolving the current conflict), and `--quit` exits the session without moving HEAD or the branch, allowing the user to switch branches and return later. Colomar provides a step-by-step algorithm for rebasing a tree of branches, showing how these options enable pausing, resuming, and reordering rebases to handle interdependent branches safely. For a single branch, the workflow is simpler: resolve conflicts, run `git rebase --continue`, and then `git bisect-rebase --continue` to advance to the next conflicting commit.

The implementation directly addresses Phillip Wood’s earlier proposal to extend `git rebase --update-refs` to automate rebasing interdependent branches. While Phillip’s suggestion aimed to reduce manual intervention, Colomar argues that the multi-shot approach is more robust for complex cases, as it avoids automating steps that might require human judgment. The new options in `git-bisect-rebase` provide a middle ground, retaining manual control while streamlining the process with dedicated commands. Colomar’s example demonstrates that this manual control is necessary to handle branch trees in a specific order, which would be difficult or impossible with a fully automated approach.

The email reinforces that `git-bisect-rebase` is now the leading candidate for inclusion in `contrib/`, given its alignment with Git’s conventions and Nico Williams’ endorsement. However, the broader question of whether Git should include any helper for this workflow remains unresolved, with Junio C Hamano’s endorsement of `git-imerge` and Patrick Steinhardt’s preference for direct integration into `git rebase` still in play. Colomar’s plan to distribute the script separately (e.g., via `manpages-utils`) reflects the uncertainty around `contrib/` inclusion, though the new options strengthen the case for its utility.

Key unresolved questions include whether the multi-shot workflow is sufficiently general to justify inclusion, how the proposed `--first-conflict` or `--onto-first-conflict` options for `git rebase` would interact with this manual workflow, and whether the project will accept a helper script in `contrib/` or prefer direct integration. The email adds weight to the argument for `git-bisect-rebase` as a practical, user-tested tool, but the debate over the best long-term solution continues.

This is a bugfix series targeting the index refresh logic in `git status`. The author, Curtis Allen Smith, addresses a long-standing inconsistency where `git status` reports files as modified when `git diff` and `git add` correctly determine that no content change occurred. The issue arises when line-ending conversion (e.g., `* text eol=lf`) is active: a tool rewriting a file with CRLF endings triggers a false positive in `git status` because the size comparison in `ie_match_stat()` assumes unchanged size means unchanged content, ignoring that clean filters can alter file size while preserving logical content.

The series consists of two patches. Patch 1 modifies `ie_match_stat()` to skip the size-based shortcut when the path is subject to conversion, instead reading the file and applying conversion (or just scanning for CRs if only line-ending conversion is active) before deciding. It also optimizes `ce_compare_data()` to avoid hashing files whose converted length already differs from the blob size. Patch 2 introduces `core.convertAwareStatus`, a new config option defaulting to `true` that lets users opt out of the new behavior (either globally or for paths with expensive filters like Git LFS). The commit message includes detailed performance measurements showing minimal overhead for clean trees and genuine modifications, while eliminating the false positives that currently force unnecessary refreshes.

The motivation is clear and well-documented, with a real-world example (Git LFS users) and a link to the original Git for Windows issue. The patches are self-contained, pass existing tests, and include new tests in `t0020-crlf.sh` to verify the fix. The performance trade-offs are transparently presented, and the default choice (`true`) favors correctness over the 2005-era optimization. This looks like a well-crafted fix for a subtle but annoying inconsistency that affects users with clean filters.

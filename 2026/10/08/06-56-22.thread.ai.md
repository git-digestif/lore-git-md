Thread identity
Subject: SSH signing verification flaws (time-of-signature confusion, revocation file fails open)
Series version: standalone security bug report (no patch series)
Originating author: Christian Noé Ramos López <chris@nortesoftware.dev>
Thread type: security bug report

Core problem or goal
Git’s SSH signing verification has two critical flaws: (1) it checks the `valid-before` timestamp in the allowed signers file against the committer date (which the signer controls), allowing backdated commits to bypass key expiration, and (2) if the `gpg.ssh.revocationFile` is configured but missing, unreadable, or a directory, Git warns and proceeds as if no revocation file exists, failing open instead of failing closed. The GPG backend correctly rejects backdated signatures and fails closed on revocation file issues.

Current status
Reported; no patch yet. The discussion has converged on two design directions: (1) document the current `valid-before` behavior (checking against committer date) as a known limitation, with an explanation that the check is only trustworthy if the signing key has never leaked, and (2) make revocation file errors fatal by default, using Git’s `:(optional)` pathname prefix to allow users an escape hatch if needed. Phillip Wood and Patrick Steinhardt both agree on these directions, though Patrick emphasizes the inherent difficulty of fixing the `valid-before` issue in a distributed system. The thread remains in the "design consensus" phase; no patch has been submitted.

Key technical details
- Subsystem: SSH signing verification (`gpg-interface.c`, `gpg-ssh.c`)
- Config keys: `gpg.ssh.revocationFile`, `gpg.ssh.allowedSignersFile`
- Symbols: `%G?` status codes (SSH-specific), `valid-before` timestamp handling, `:(optional)` pathname prefix
- Behavior change: revocation file errors now fail verification by default (was warn-and-continue); optional override via `:(optional)` prefix
- Test coverage: none for revocation file logic; new test cases provided in the original report

Open questions and loose ends
- Should the documentation explicitly note that `valid-before`/`valid-after` checks are only trustworthy for keys that have never leaked?
- Is the `:(optional)` prefix the right mechanism for allowing revocation file overrides, or should a separate config key be introduced?
- Are there backward-compatibility concerns with making revocation file errors fatal by default, even with an escape hatch?
- The report notes the revocation file logic is entirely untested; test suite coverage is needed.
- Are there plans to support other revocation mechanisms (e.g., OpenSSH’s `KRL` format)?

Participant positions
- Christian Noé Ramos López: reported the flaws, provided test cases, and recommended fixes (document or change `valid-before` behavior, fail closed on revocation file errors).
- Phillip Wood: substantive review agreeing with both issues. Clarified that the documentation implies `valid-before` is checked against the signature time, but the code uses the committer date. Suggested tightening the documentation to reflect this (or noting that the GPG signature timestamp can also be faked). Endorsed making revocation file errors fatal, aligning with OpenSSH's security model.
- Patrick Steinhardt: agrees with the issues but argues that fixing the `valid-before` timestamp check is fundamentally difficult in a distributed system. Advocates documenting the current behavior's limitations (e.g., `valid-before` is only trustworthy if the key has never leaked) rather than attempting a technical fix. Proposes using Git’s `:(optional)` pathname prefix to make revocation file errors fatal by default while allowing an escape hatch.

Thread identity
Subject: SSH signing verification flaws (time-of-signature confusion, revocation file fails open)
Series version: standalone security bug report (no patch series)
Originating author: Christian Noé Ramos López <chris@nortesoftware.dev>
Thread type: security bug report

Core problem or goal
Git’s SSH signing verification had two critical flaws: (1) it checked the `valid-before` timestamp in the allowed signers file against the committer date (which the signer controls), allowing backdated commits to bypass key expiration, and (2) if the `gpg.ssh.revocationFile` was configured but missing, unreadable, or a directory, Git warned and proceeded as if no revocation file existed, failing open instead of failing closed. The GPG backend correctly rejected backdated signatures (using the signature timestamp) and failed closed on revocation file issues.

Current status
Both reported flaws are now addressed in principle, but the second issue (revocation file fails open) has a **new substantive review concern** from Junio C Hamano. Christian’s security bugfix patch makes Git fail closed when the revocation file is configured but missing or unreadable, but Junio points out that this skips the signature-info display that would still be shown for *unknown keys*, creating an asymmetry in user feedback. Junio proposes folding the revocation-file check into the earlier failure block so that signature information is still displayed, aligning the behavior with how unknown keys are handled. The patch is otherwise ready for integration once this point is resolved. The escape hatch via Git’s `:(optional)` pathname syntax remains uncontroversial.

The first issue (timestamp confusion) remains under review. Christian submitted a documentation patch clarifying that `valid-before`/`valid-after` checks use the committer or tagger date (not the signature timestamp) and warned that these checks are only trustworthy if the key has never leaked. Junio has suggested simplifying the documentation to omit the caveats about key leakage and signature timing, proposing a more concise version that states only the behavior (committer/tagger date is used) without discussing its limitations. Phillip Wood and Patrick Steinhardt previously endorsed the more detailed wording, but no further review has weighed in on Junio’s proposal. The outcome hinges on whether the project prioritizes brevity or explicit warnings in the man page.

Key technical details
- Subsystem: SSH signing verification (`gpg-interface.c`, `gpg-ssh.c`)
- Config keys: `gpg.ssh.revocationFile`, `gpg.ssh.allowedSignersFile`
- Symbols: `%G?` status codes (SSH-specific), `valid-before`/`valid-after` timestamp handling, `:(optional)` pathname prefix
- Behavior changes:
  - Revocation file errors now fail verification by default (was warn-and-continue); optional override via `:(optional)` prefix.
  - Documentation patch clarifies that `valid-before`/`valid-after` checks use the committer/tagger date (not the signature timestamp). The proposed wording omits or retains caveats about key leakage risks depending on review resolution. Also fixes a typo ("OpensSSH" → "OpenSSH").
- Test coverage: added four new test cases in `t/t7528-signed-commit-ssh.sh` covering revoked keys, missing files, and the `:(optional)` escape hatch.
- Error-handling flow: Junio’s review identifies an inconsistency where missing revocation files skip signature-info display, unlike unknown keys. The fix will likely adjust the control flow to ensure signature information is shown in both cases.

Open questions and loose ends
- **Revocation file error-handling flow**: whether to display signature information when the revocation file is missing (Junio’s proposal) or fail immediately (current patch). This is the final technical point blocking the security bugfix.
- Documentation wording for the timestamp confusion issue: whether to include explicit warnings about the limitations of key lifetime checks (e.g., only trustworthy if the key has never leaked) or to state only the behavior (committer/tagger date is used) without caveats.
- Whether Git will support additional revocation mechanisms (e.g., OpenSSH’s `KRL` format) remains an open question, but this is outside the scope of the current fixes.

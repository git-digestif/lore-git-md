Thread identity
Subject: SSH signing verification flaws (time-of-signature confusion, revocation file fails open)
Series version: standalone security bug report (no patch series)
Originating author: Christian Noé Ramos López <chris@nortesoftware.dev>
Thread type: security bug report

Core problem or goal
Git’s SSH signing verification has two critical flaws: (1) it checks the `valid-before` timestamp in the allowed signers file against the committer date (which the signer controls), allowing backdated commits to bypass key expiration, and (2) if the `gpg.ssh.revocationFile` is configured but missing, unreadable, or a directory, Git warns and proceeds as if no revocation file exists, failing open instead of failing closed. The GPG backend correctly rejects backdated signatures (using the signature timestamp) and fails closed on revocation file issues.

Current status
Reported; design consensus reached on two actionable fixes: (1) document the current `valid-before` behavior (checking against committer date) as a known limitation, explicitly noting that the check is only trustworthy if the signing key has never leaked and that signature timestamps are not reliable evidence of when signing occurred, and (2) make revocation file errors fatal by default, using Git’s `:(optional)` pathname prefix to allow users an escape hatch if needed. Phillip Wood, Patrick Steinhardt, and Christian Noé Ramos López agree on these directions. The thread is now in the "implementation" phase; Christian has committed to submitting a patch with test coverage for the revocation file logic, which is currently untested. Phillip Wood and Patrick Steinhardt have confirmed the `:(optional)` prefix as the correct mechanism for the revocation file escape hatch, resolving the last design ambiguity.

Key technical details
- Subsystem: SSH signing verification (`gpg-interface.c`, `gpg-ssh.c`)
- Config keys: `gpg.ssh.revocationFile`, `gpg.ssh.allowedSignersFile`
- Symbols: `%G?` status codes (SSH-specific), `valid-before` timestamp handling, `:(optional)` pathname prefix
- Behavior change: revocation file errors now fail verification by default (was warn-and-continue); optional override via `:(optional)` prefix
- Documentation change: update `gpg.ssh.allowedSignersFile` man page to clarify that `valid-before`/`valid-after` checks use the committer date, not the signature timestamp, and that these checks are only trustworthy for keys that have never leaked
- Test coverage: none for revocation file logic; Christian will add test cases in the forthcoming patch

Open questions and loose ends
- The patch will need to include test cases for the revocation file logic, which is currently untested.
- Are there plans to support other revocation mechanisms (e.g., OpenSSH’s `KRL` format)? (Not discussed in this thread; remains an open question.)

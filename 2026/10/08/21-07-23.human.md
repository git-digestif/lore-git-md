This is the first patch in a two-part feature series that hardens Git’s ignore-revs parser and tag-peeling logic ahead of automatically using `HEAD:.git-blame-ignore-revs` as a default ignore file. The changes are security-focused, addressing two specific risks that arise when the ignore-revs file is no longer explicitly configured by the user but instead read from a well-known blob in the repository.

The patch rejects lines containing embedded NUL bytes in the ignore-revs file by switching from `strchr` to `memchr` in `oidset_parse_file_carefully`. This prevents malformed input like `<oid>\0garbage` or `<oid>\0# comment` from being silently truncated and misinterpreted. The hardening is minimal and targeted: it does not change the parser’s behavior for valid input, only adds a fatal error for lines that would previously have been parsed incorrectly.

It also prevents promisor fetches in partial clones by modifying `peel_to_commit_oid` to use `odb_read_object_info_extended` with `OBJECT_INFO_SKIP_FETCH_OBJECT` and `OBJECT_INFO_QUICK`. The new logic peels tags one layer at a time, verifying each target object exists locally and matches the tag’s declared type before parsing it. This ensures that missing commit OIDs or tag targets listed in the ignore-revs file do not trigger lazy fetches or pack directory rescans during `git blame`.

Test coverage is thorough, verifying both NUL-byte rejection and the handling of chained tags, missing tag targets, and partial-clone scenarios. The patch is well-motivated and clearly scoped: it does not introduce new user-visible behavior but prepares the codebase for the upcoming default file lookup in patch 2/2. The hardening looks technically sound, though it will need scrutiny from security-interested contributors like Jeff King or brian m. carlson before the series can be considered ready for integration.

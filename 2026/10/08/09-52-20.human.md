This is the fourth patch in a five-patch bugfix series (v3) that plugs a data-loss race in `git repack -d`. The series replaces the racy `--honor-pack-keep` mechanism with a snapshot-based approach, and this patch adds the plumbing needed to scale it: `--keep-pack-from-file`.

The problem is simple: `--keep-pack` can only name one pack per argument, and command-line length limits (ARG_MAX on Unix, 32 KB on Windows) are quickly exhausted in repositories with hundreds of kept packs. The new option reads pack names from a file, one per line, and treats them exactly like `--keep-pack` arguments—empty lines are skipped, non-existent packs are ignored, and relative paths are resolved against the working directory. The file format matches the one used by `git multi-pack-index write --refs-snapshot`, so the repack machinery can reuse the same snapshot file.

The implementation is straightforward: a new helper `read_keep_pack_list()` reads the file into the same `string_list` that holds `--keep-pack` names, and the list is marked `strdup_strings = 1` so it can own both kinds of strings. The patch adds two tests: one verifies that `--keep-pack-from-file` behaves identically to `--keep-pack` (including edge cases like empty lines and non-existent packs), and the other confirms the command fails cleanly when the file is missing.

This is a scalability enabler for the final patch (5/5), which will pass `pack-objects` a snapshot of `.keep` packs observed at repack startup. The design is pragmatic and aligns with existing Git conventions; reviewers are unlikely to object to the file format or error handling, though they may discuss whether a more structured format (e.g., NUL-terminated) would be preferable. The patch is well-tested and ready for review.

# Thread deltas

## 2026/10/08

- [2026/10/08/06-56-22 by Christian Noé Ramos López <chris@nortesoftware.dev>] Christian Noé Ramos López reported that git checks SSH signature `valid-before` against the committer/tagger date (which the signer controls) rather than the actual signing time, allowing a backdated commit to bypass key expiry, and that a configured but missing `gpg.ssh.revocationFile` only triggers a warning while verification proceeds without it (failing open), unlike ssh-keygen and sshd which refuse; he asked that git refuse when the revocation file is configured and missing (or document that it is ignored) and document where the time compared against `valid-before` comes from.
- [2026/10/08/13-42-42 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood agreed that failing when the revocation file is missing seems like the safer option, and said he would be happy to see a patch tightening the documentation wording for `valid-before`, while noting that the timestamp in a GPG signature can also be faked.

## 2026/10/09

- [2026/10/09/12-19-20 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt: on valid-before, there is no proper fix because in a distributed system there is no way to establish the actual time data was signed (upper bounds via subsequent trusted signed commits are not always useful); agreed that documenting that a leaked key makes valid-before/valid-after unable to guarantee anything would avoid a false sense of trustworthiness; for a missing revocationFile, suggested failing by default with a ":(optional)" path prefix as an escape hatch.
- [2026/10/09/13-29-27 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood: said the documentation wording patch sounds sensible, since a valid signature does not tell when the commit was signed; said a test for gpg.ssh.revocationFile would be welcome and endorsed Patrick's suggestion of allowing the path to be optional.
- [2026/10/09/13-30-03 by Phillip Wood <phillip.wood123@gmail.com>] Phillip Wood: agreed that checking a signature only shows the commit was signed by that key, not when it was signed; called Patrick's ":(optional)" prefix idea good.

## 2026/10/21

- [2026/10/21/03-03-47 by Christian Noé Ramos López <chris@nortesoftware.dev>] Christian Noé Ramos López posted a documentation patch for gpg.ssh.allowedSignersFile stating that Git checks SSH key valid-after/valid-before lifetimes against the committer or tagger date recorded in the commit or tag, that this date is chosen by whoever creates the commit/tag and is not evidence of when the signature was made (likewise the GPG signature creation time comes from the signer's clock), that relying on a key lifetime is only safe as long as the key has never leaked, and fixing the "OpensSSH" spelling.
- [2026/10/21/04-17-20 by Christian Noé Ramos López <chris@nortesoftware.dev>] Christian Noé Ramos López posted the gpg-interface patch making signature verification fail with an error when gpg.ssh.revocationFile names a missing file (instead of warning and verifying without it), supporting ":(optional)" to skip the check, and adding tests for revoked keys and missing files with and without the prefix; he noted that a local ":(optional)" value dropping a global gpg.ssh.revocationFile is existing behavior, not introduced by the patch.
- [2026/10/21/18-14-42 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano reviewed the doc patch, saying that stating what the lifetime is compared against may be valuable but the rest sounds like "empty fluff", and proposed a more succinct wording that only says Git validates the signature by checking the committer or tagger timestamp against the validity range.
- [2026/10/21/18-40-25 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano reviewed the revocation-file patch, noting the pre-existing "we still call check-novalidate" comment is misleading, and objecting that placing the missing-revocation-file check in the "else if" block means known keys get no signature info on that failure (unlike unknown keys), wondering whether the check should be folded into the earlier "if" block as the single place handling failures; he otherwise agreed the removal of the per-principal file-exists check makes sense.

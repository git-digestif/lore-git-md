This is the second patch in Maciej Ciemborowicz’s four-patch series fixing the `reference-transaction` hook’s omission of new refs during branch rename/copy operations. It introduces `ref_transaction_replace_reflog()`, a new transactional API that allows replacing a ref’s reflog history without altering the ref itself. The patch targets both the files-based and reftable backends, staging replacements in temporary files (files) or tombstoning old entries (reftable) to ensure atomicity and avoid exposing partial changes to hooks.

The implementation adds a private `REF_REPLACE_REFLOG` flag, a `ref_transaction_replace_reflog()` function, and backend-specific logic to handle reflog replacement. For the files backend, it stages new reflog entries in temporary files beside the logs, ordering them by their requested index and installing them only during transaction commit. The reftable backend tombstones previous entries in the same table as the replacement. The patch also ensures that log-only entries with null new OIDs are preserved as part of the history rather than treated as deletions, and propagates read errors instead of silently copying partial logs.

Testing covers null-OID preservation, entry ordering, rollback behavior, hook rejection, and duplicate replacement scenarios via a new `t/t1425-reflog-transaction.sh` test script. The patch is a prerequisite for patch 3/4, which integrates branch rename/copy into the ordinary transaction path, and is uncontroversial in its current form. Performance impact is negligible, but the patch compounds the ~137% slowdown for files-based rename with large reflogs introduced in later patches. The series as a whole remains on track for `next` if no further regressions surface.

This thread is about a bugfix for a performance regression in shallow fetches when backfilling tags, introduced by a 2025 change to batched reference updates. The regression occurs because batched updates delay committing references until after tag backfilling, causing the client to report no "have" references during negotiation and forcing the server to send all objects. Karthik Nayak’s fifth iteration (v5) of the patch adopts Patrick Steinhardt’s design to expose pending transaction state via the transport’s `negotiation_include_tips` field, replacing an earlier two-transaction approach and incorporating minor cleanups from prior feedback.

The patch is well-tested and appears technically sound, but Patrick’s latest review raises a critical memory management concern: the v4 patch could leak fetched refs if `negotiation_include_tips` is already set by another caller, as it appends OIDs to the existing array without ensuring exclusive control. This is a correctness issue that risks breaking assumptions in the transport layer, where `negotiation_include_tips` is shared state. The author will need to redesign the memory management—either by enforcing exclusive ownership or copying the array—to resolve this blocker.

Key participants include Karthik Nayak (author), Patrick Steinhardt (who proposed the current design and now flags the memory issue), and Justin Tobler (whose prior concerns about error paths and GC safety have been addressed). Junio Hamano has not yet weighed in, but the patch’s readiness for `next` now hinges on resolving Patrick’s concern. The scalability trade-off (advertising all local references during negotiation) is documented and considered acceptable, but this new issue may delay integration.

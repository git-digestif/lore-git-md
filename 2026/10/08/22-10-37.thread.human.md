This thread is about a bugfix patch series (now at v5) addressing a performance regression in shallow fetches when backfilling tags, introduced by a May 2025 change to batched reference updates. The regression occurs because batched updates delay committing references until after tag backfilling, causing the client to report no "have" references during negotiation and forcing the server to send all objects. The current patch (v5) exposes pending transaction state via the transport’s `negotiation_include_tips` field to restore correct "have" reporting while preserving atomicity for `--atomic` fetches, but a critical memory management issue has stalled progress.

The key participants are Karthik Nayak (author), Patrick Steinhardt (reviewer), and Justin Tobler (reviewer). Karthik implemented Patrick’s proposed design in v4/v5, incorporating prior feedback on edge cases and scalability trade-offs, but Patrick recently identified a blocker: the patch appends fetched OIDs to `negotiation_include_tips` without accounting for shared ownership of the `oid_array`, risking memory leaks or state corruption if the array is reused. Karthik’s latest reply confirms the issue is worse than initially thought—`negotiation_include_tips` is also used by the `--negotiation-include` user option, meaning fetched tips could leak into unrelated negotiation phases. The transport’s inconsistent cleanup (freeing the array only for smart transports) exacerbates the problem. No alternative designs have been proposed yet, and Junio Hamano hasn’t weighed in.

The patch touches `builtin/fetch.c` and adds tests to `t/t5510-fetch.sh`, with the fix documented as 17× faster than pre-regression behavior. However, until the memory management issue is resolved (likely by copying the array before appending fetched tips), the patch remains unready for `next`. The scalability trade-off (advertising all local references during negotiation in large repos) is accepted as O(n) complexity, but the correctness risk is non-negotiable.

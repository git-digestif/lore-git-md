This thread is about fixing a performance regression in shallow fetches when backfilling tags, introduced by a 2025 change to batched reference updates. The regression forces servers to send all objects because the client reports no 'have' references during negotiation. Karthik Nayak posted a third version of the fix (v3), which splits the reference transaction into two phases to ensure fetched references are committed before tag backfilling begins. This approach addressed prior edge-case concerns but raised new questions from Justin Tobler about error handling and transaction flow.

Karthik has now clarified the error-path logic in response to Justin’s review: the code logs errors from the first transaction but continues to the second because batched updates allow partial success, and the rest of the fetch (including tag backfilling) should proceed. Similarly, post-fetch operations like writing `FETCH_HEAD` execute even if the initial transaction failed to initialize, as these steps are independent of the transaction’s success. These explanations resolve Justin’s technical questions, but the patch’s future is still uncertain. Patrick Steinhardt proposed an alternative design—exposing pending transaction state to negotiation—which could eliminate the two-transaction approach and restore atomicity for `--atomic` fetches. Karthik is evaluating this idea but has expressed concerns about GC safety. The thread is now waiting to see if Patrick’s proposal is feasible or if the two-transaction approach will proceed with the clarified error handling. The patch is not yet ready for Junio’s `next` branch.

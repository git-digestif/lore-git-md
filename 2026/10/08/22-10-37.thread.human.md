This thread is about a bugfix patch series addressing a performance regression in shallow fetches when backfilling tags, introduced by a 2025 change to batched reference updates. The regression occurs because delayed reference commits prevent the client from reporting 'have' references during negotiation, forcing the server to send all objects. The current version (v4) implements Patrick Steinhardt’s proposed design to expose pending transaction state via the transport’s `negotiation_include_tips` field, replacing an earlier two-transaction approach.

Karthik Nayak, the author, has addressed all prior feedback in v4, including edge cases around empty transactions, atomic fetches, and error handling. The patch is well-tested, with three new tests verifying correct 'have' reporting and upstream tracking behavior. Patrick Steinhardt, who proposed the design, has reviewed v4 and raised procedural concerns about scalability: the new logic may cause the client to advertise all local references during negotiation, potentially flooding the server with "haves" in large repositories. Karthik acknowledges this trade-off and plans to document it in the commit message. Minor code cleanups (memory management, loop variables) have also been agreed upon.

The patch appears ready for Junio’s `next` branch unless new concerns emerge. The only remaining discussion is whether the third test (upstream tracking with rejected sibling refs) should be split into a separate patch, as it’s tangential to the core fix. No correctness issues have been raised, and the design is now considered robust. The author plans to send v5 after a short delay to allow for further comments.

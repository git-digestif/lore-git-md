This thread is about a bugfix for a performance regression in shallow fetches when backfilling tags, introduced by a 2025 change to batched reference updates. The regression occurs because the batched updates delay committing references to disk until after tag backfilling begins, causing the client to report no 'have' references during negotiation and forcing the server to send all objects. Karthik Nayak's fifth iteration of the patch (v5) implements a design proposed by Patrick Steinhardt to expose pending transaction state via the transport's `negotiation_include_tips` field, restoring correct 'have' reporting while preserving atomicity for `--atomic` fetches.

The patch is under active review but is blocked by a **critical memory management issue**: the current design appends fetched OIDs to `negotiation_include_tips` without ensuring exclusive ownership, risking state corruption or memory leaks. This field is also used by the `--negotiation-include` user option, and the transport only frees it for smart transports, leaving non-smart transports (or remote helpers) with dangling state. Karthik acknowledges this as a blocker and plans to address it either by copying the existing array before appending fetched tips or by enforcing exclusive ownership during tag backfilling. The patch is not ready for Junio's `next` branch until this issue is resolved.

Key participants include Karthik Nayak (author), Patrick Steinhardt (reviewer, who raised the memory management concern), and Justin Tobler (reviewer, who previously raised questions about error-path logic and GC safety, now addressed). Junio C Hamano has not yet weighed in on the new design or the memory management issue. The scalability trade-off—advertising all fetched refs during negotiation—is documented as acceptable, but correctness is the priority. The discussion also uncovered a broader issue with the transport API's lack of ownership guarantees for `negotiation_include_tips`, which may require fixes beyond this patch.

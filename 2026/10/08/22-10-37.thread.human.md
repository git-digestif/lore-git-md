This thread is fixing a performance regression in shallow fetches when backfilling tags, introduced by a May 2025 change to batched reference updates. Karthik Nayak’s third patch iteration (v3) refines the original two-transaction approach—committing fetched references before backfilling tags—to address edge cases and error handling. The patch is under review, with all prior feedback incorporated, but its future is now tied to a new design proposal from Patrick Steinhardt: exposing pending, uncommitted reference updates to negotiation, which could eliminate the need for an intermediate commit and restore atomicity for `--atomic` fetches.

The discussion has shifted from refining the two-transaction logic to evaluating Patrick’s proposal. Justin Tobler’s recent reply addresses Karthik’s concerns about GC safety, arguing that the objects needed for negotiation are already present in the repository and that `.keep` lockfiles are already relied upon to prevent GC until the transaction commits. He also endorses using the `negotiation_include_tips` field in the transport structure as a potential mechanism, narrowing the open question to whether this can be implemented safely. The thread is now focused on the feasibility of this approach, with Karthik remaining cautious but open to exploration, and Patrick and Justin leaning toward its viability.

If the proposal proves practical, it could lead to a v4 rewrite with cleaner atomicity guarantees; otherwise, the two-transaction approach will proceed. The patch is not yet ready for Junio’s `next` branch, as the design discussion is still unresolved. Key participants—Karthik, Patrick, Justin, and Junio—are aligned on the goal but differ slightly on the path forward, with the maintainer’s input likely needed to settle the design. The performance impact is significant: the fix is over 17× faster than the pre-batched-update behavior, and the new proposal is expected to match this while improving atomicity.

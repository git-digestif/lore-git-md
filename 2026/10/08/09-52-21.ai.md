This is the **final patch (5/5) in a v3 bugfix series** that eliminates a data-loss race in `git repack -d`. The race occurs when a concurrent push or fetch creates a `.keep` file after `repack` has decided which packs to delete but before `pack-objects` has finished building the replacement pack. The patch replaces the racy `--honor-pack-keep` mechanism with a snapshot-based approach: `repack` now writes the list of `.keep` packs observed at startup to a temporary file and passes it to `pack-objects` via the new `--keep-pack-from-file` option (introduced in patch 4/5). Both processes then work from the same snapshot, preventing disagreement over which packs are kept.

The implementation is minimal and focused. The snapshot file is written next to the refs snapshot already used for `multi-pack-index write` and contains one `<name>.pack` per line. The patch adds 15 lines to `builtin/repack.c` to create the snapshot, 34 lines to `repack.c` to write it, and removes 3 lines from `repack-filtered.c` that redundantly passed `--keep-pack` arguments. The snapshot is only written when there are kept packs, matching the behavior of `--honor-pack-keep` when no `.keep` files were found. The patch also handles edge cases: it refuses pack names containing newlines (which would split the name in two) and ensures kept packs from alternate object directories are now packed (not skipped), trading disk space for safety.

Test coverage is thorough. The patch adds three new tests:
1. `t7700-repack.sh` verifies that `--keep-pack` with `--pack-kept-objects` still excludes the kept pack’s objects.
2. `t7703-repack-geometric.sh` reproduces the race by simulating a `.keep` file appearing mid-repack and confirms objects are not lost.
3. A second test in `t7703-repack-geometric.sh` ensures kept packs do not block traversal of objects reachable through them, exercising the fix from patch 1/5.

The patch is **production-ready** and merges cleanly into `next` and `seen`. It is the culmination of a well-motivated series that has been reviewed and acked by Junio C Hamano (patch 2/5). The remaining patches (1/5, 3/5, 4/5) are also under review and unlikely to introduce regressions. The series as a whole is a **clear improvement** over the current racy implementation, with no known downsides beyond the minor disk space trade-off for alternate ODB packs.

This is an RFC iteration of the `git brebase` proposal, now renamed to `git-bisect-rebase` and split into three scripts. The author, Alejandro Colomar, has refined the tool to better support two distinct workflows: rebasing a single branch and rebasing a "tree" of branches (a branch with multiple descendants). The key addition is a set of `--abort`, `--continue`, and `--quit` options that operate at the *bisect-rebase* level rather than the individual rebase level, enabling recursive resolution of complex branch topologies.

The updated implementation introduces three scripts: `git-bisect-rebase` (the entry point), `git-bisect-rebase--callback` (internal helper for `git bisect run`), and `git-bisect-rebase--continue` (handles the `--continue` workflow). The scripts are now hosted in the Linux man-pages repository, which provides version history and context for design decisions. The author includes concrete algorithms for both workflows, demonstrating how the new options enable recursive resolution: for a tree of branches, users can `--quit` the bisect-rebase at a conflict, resolve conflicts in descendant branches, then resume the parent rebase; for a single branch, `--continue` automates the resumption after conflict resolution.

This iteration addresses earlier feedback about usability and edge cases (e.g., detached HEAD support, temporary file cleanup) but does not adopt Nico Williams' proposed in-memory callback execution or environment-variable-based state management. The philosophical debate about integration path remains unresolved: Alejandro continues to advocate for a standalone tool, while Nico's counterproposal (integrating bisect-driven conflict resolution into `git rebase` as a flag) is not engaged with here. The split into three scripts and the explicit workflow algorithms strengthen the case for a standalone tool by demonstrating how its design differs fundamentally from `git rebase`'s plumbing role.

Key technical details for follow-up discussion:
- **New options**: `--abort`, `--continue`, `--quit` operate on the bisect-rebase segment, not the entire rebase, enabling recursive resolution.
- **Files introduced**: `git-bisect-rebase`, `git-bisect-rebase--callback`, `git-bisect-rebase--continue` (all shell scripts).
- **Workflow algorithms**: Concrete examples for single-branch and tree-of-branches rebasing, showing how the new options reduce redundant conflict resolution.
- **State management**: Uses temporary files (not environment variables) and `trap` for cleanup; detached HEAD support is preserved.
- **Unresolved from prior discussion**: Callback argument passing (still uses a temporary file), merge commit handling, and the integration path debate (standalone tool vs. `git rebase` flag).

The patch remains conceptual (no changes to Git itself) but is now more robust and better documented. The recursive resolution capability and explicit workflow examples make a stronger case for the tool's value, though the shell-based implementation and lack of persistent conflict history may still raise concerns about production readiness. The philosophical divide with Nico's proposal is deepened by the workflow algorithms, which rely on segment-level operations that would be difficult to implement in `git rebase` without breaking backward compatibility.

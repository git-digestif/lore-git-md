This is the second patch in the v3 series fixing a data-loss race in `git repack -d`. The patch addresses a latent bug in the cruft-pack walk where objects in packs marked as kept *after* the initial collection phase would be incorrectly omitted from the cruft pack, leading to dangling refs when those packs are later deleted.

The bug stems from a stale kept-pack cache that persists between the collection and traversal phases of the cruft-pack process. The cache is built during collection while certain packs are still marked as kept, but the walk phase—though it unmarks those packs—reuses the same cache because it asks the same type of question (in-core kept packs). The fix adds a call to `repo_invalidate_kept_pack_caches()` after re-marking the fresh packs, forcing the cache to rebuild with the current state.

Junio C Hamano has acked this patch in its v3 form, noting that while the architectural layering (the downcast in `packfile.c`) is not ideal, the fix is correct and necessary to prevent data loss today. The test added in `t/t5329-pack-objects-cruft.sh` reproduces the bug by creating an unreachable chain where the middle commit sits in an untold pack, and confirms the fix ensures all reachable objects are included in the cruft pack.

The patch is clean, well-motivated, and includes thorough test coverage. It touches core logic in `packfile.c` and `builtin/pack-objects.c` but does not change on-disk formats or user-visible behavior. The only open question is whether the downcast grouping in `packfile.c` is sufficient for long-term maintainability, but that discussion is deferred to the ODB backend experts and does not block integration. This is a production-ready fix for a serious bug.

This is a technical clarification in the ongoing `git switch`/`git checkout` tracking-configuration failure thread.

井上司 (Tsukasa Inoue) responds to D. Ben Knoble’s observation about the control flow in branch-switching commands. He confirms that `merge_working_tree()` updates the worktree and index on every branch switch, not just when `-m` is used, because the `do_merge` flag starts at 1. The "merge" here refers to the 2-way merge in `unpack_trees()`, not the `-m` option, which only adds an autostash step for conflict handling. The current order is: update worktree and index, create the ref, write tracking config (which may fail), then update HEAD. This sequence explains why a failure in `setup_tracking()` leaves the worktree and index in an inconsistent state. He also confirms that the `-m` case has the same issue: if a conflict occurs, HEAD remains on the old branch, the file is left conflicted, and changes stay in the stash. Attempting to retry the command in this state either fails with "branch already exists" or "resolve your index first," leaving the repository in the same broken state. This reply adds concrete detail to the control flow discussion and reinforces the need for broader restructuring beyond just `setup_tracking()`.

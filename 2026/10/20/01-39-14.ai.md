This is a bugfix patch proposal targeting the `git switch` and `git checkout` commands.

The email reports a long-standing edge case in Git 2.43.0 (and likely earlier): when `git switch` or `git checkout` creates a new branch but fails to write the tracking configuration (e.g., because `.git/config.lock` exists), the command exits with an error *after* updating the worktree and index, but *before* updating HEAD. The result is a confusing state where the worktree reflects the new branch, but HEAD still points to the old branch, and the user sees staged changes that appear unrelated to their command.

The reproduction steps are clear and minimal: a fresh clone, a fetch, a lock file created to trigger the failure, and then `git switch feat` demonstrates the problem. The author also notes the same issue affects `switch -c`, `checkout -b`, `--track`, and (with different symptoms) `-C` on an existing branch. The root cause is traced to `setup_tracking()` in `branch.c` calling `exit(1)` after the worktree is updated but before HEAD is moved, a behavior introduced in commit 27852b2c53 (2016).

The author asks for design guidance: should the command complete the switch and only report the tracking error, or should it fail cleanly without touching the worktree? No patch is attached yet, so this is an RFC-style discussion starter rather than a ready-to-merge fix. The thread context indicates this is the first email in the thread.

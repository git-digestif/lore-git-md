This is the final patch (5/5) in Harald Nordgren’s v10 series introducing a "matching-inspired" fetch mode for shallow repositories. The patch makes `--limited-fetch` the default when adding a remote in a shallow repository, addressing a long-standing usability issue where `git remote add` in a shallow clone would still configure a wildcard refspec, defeating the purpose of shallow cloning.

The change is minimal and surgical: it modifies `builtin/remote.c` to check `is_repository_shallow(the_repository)` when the `limited_fetch` flag is unset (`-1`), defaulting to `--limited-fetch` unless explicitly overridden with `--no-limited-fetch`. The documentation in `git-remote.adoc` is updated to explain the new default behavior, and four new tests in `t/t5505-remote.sh` verify that the shallow-repository default works as intended, that `--no-limited-fetch` overrides it, that `-t/--track` still configures an explicit refspec, and that full repositories continue using wildcard refspecs.

This patch is uncontroversial and ready for merging. It reuses existing machinery (the `limited_fetch` flag and `is_repository_shallow()` helper) without introducing new technical debt, and the test coverage is thorough. The only open design question—whether `--limited-fetch` should be the default for *all* repositories, not just shallow ones—is explicitly out of scope for this patch and can be addressed in follow-up work if desired. The backward compatibility story is clean: non-shallow repositories are unaffected, and the new behavior is opt-in for shallow repositories via the existing `--limited-fetch` flag.

The patch touches `builtin/remote.c`, `Documentation/git-remote.adoc`, and `t/t5505-remote.sh`, and integrates seamlessly with the rest of the series. With this patch, the v10 series is now complete and awaiting final maintainer feedback before graduating to `next`.

This thread is about a small but user-visible regression in `git init`: since Git 2.56’s development cycle, the command no longer prints the absolute path of the initialized repository (e.g., `/home/user/repo/.git`) and instead shows just `.git/`. Matt Hunter identified the cause—a refactoring in 20e38cba3926—and posted a minimal fix to restore the old behavior. Patrick Steinhardt reviewed the patch favorably, calling the changes “obviously good” and confirming the regression was unintentional and introduced in the current cycle, making the fix urgent for the upcoming release. Matt has agreed to two minor tweaks (dropping a redundant commit-message sentence and changing a variable type) and will post a v2.

The only open question is whether to add a regression test. Patrick argued that the current output isn’t *incorrect*, just different, which weakens the case for a test. Junio C Hamano has now weighed in, siding with practical utility: absolute paths are far more useful in command transcripts because they let users see at a glance where the repository was created without reconstructing the working directory. His comment broadens the discussion, suggesting this regression is a symptom of a larger problem—many small, untested user-facing details in Git’s output—and raises the stakes for future test coverage. No decision has been made, but the philosophical implications are now part of the thread. The patch itself is uncontroversial and likely to be merged once v2 is posted.

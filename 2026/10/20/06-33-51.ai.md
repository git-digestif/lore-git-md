This is a follow-up in the `git switch`/`git checkout` tracking-configuration-failure design discussion. The author, 井上司 (Tsukasa Inoue), acknowledges Junio C Hamano’s preference for atomic all-or-none behavior but argues that implementing full atomicity would require a large refactoring. Instead, they propose a smaller, incremental step: making `setup_tracking()` return an error rather than calling `exit()`, aligning `git switch` and `git checkout` with the behavior of `git push -u`, `git clone`, and `git fetch`, which continue even when tracking configuration fails. The author suggests deferring full atomicity to a separate effort, citing the complexity of undoing worktree, ref, and config changes, as well as handling `die()` calls in the checkout flow.

The email does not include a patch or detailed implementation plan, but it shifts the discussion from high-level design to a concrete, smaller-scale proposal. The trade-off is clear: the proposed change would eliminate the confusing halfway state but would not achieve full atomicity. This sets up a likely point of contention: whether the project should accept a partial fix now or hold out for a more complete solution. The author’s framing suggests a preference for the incremental approach, but the thread’s prior consensus (Junio’s preference for atomicity) remains unresolved. Future discussion will likely focus on whether this compromise is acceptable or if a more ambitious refactoring is warranted.

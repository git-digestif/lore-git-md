This is the v10 cover letter for a feature series that introduces a "matching-inspired" fetch mode for shallow repositories. The series is now technically complete and ready for final maintainer review before merging to `next`.

The goal is to solve a performance problem for users of shallow repositories (`git clone --depth`): a plain `git fetch` or `git pull` against a remote with many branches can be slow or hang because it negotiates history for all remote branches. The solution dynamically fetches only the branches tracked by local branches at the remote being fetched, using a new `remote.<name>.refmap` configuration to separate namespace mappings from fetch selection logic.

Key changes in v10 are minimal: the only update is resolving a merge conflict with Junio’s `ch/fetch-followremotehead-lazy-validation` topic, which was recently merged to `master`. This conflict was already addressed in v9, so v10 is effectively a rebase with no functional changes. The series remains split into five patches:

1. **Patch 1/5**: Adds `remote.<name>.refmap` configuration, mirroring `remote.<name>.fetch` but only providing a default for `--refmap` when there is something explicit to fetch.
2. **Patch 2/5**: Extracts the existing "fetch branches merged into the current branch" logic into a shared helper (`collect_upstream_from_remote`), now a pure refactoring with no behavior changes.
3. **Patch 3/5**: Implements the core logic: when no explicit refspec is given and the remote has a refmap but no fetch refspec, `git fetch` enumerates branches tracked by local branches at the remote and constructs a dynamic refspec. This patch also reorganizes the `do_fetch()` control flow to accommodate the new logic.
4. **Patch 4/5**: Adds a `--limited-fetch` flag to `git remote add`, which configures the remote to use `remote.<name>.refmap` instead of the traditional wildcard `remote.<name>.fetch` refspec.
5. **Patch 5/5**: Makes `--limited-fetch` the default for shallow repositories by checking `is_repository_shallow(the_repository)` when the `limited_fetch` flag is unset.

The implementation reuses existing logic and configuration machinery, introducing no new technical debt. The precedence rule (when both `remote.<name>.fetch` and `remote.<name>.refmap` are configured, the former takes precedence) is uncontroversial and resolves the fatal error seen in earlier versions. The series includes thorough test coverage in `t/t5510-fetch.sh`, `t/t5586-fetch-refmap.sh`, and `t/t5505-remote.sh`, verifying edge cases like bare fetches, duplicate branch tracking, and cross-remote tracking.

All substantive review feedback from Junio (the maintainer) and other participants has been addressed. The series is now waiting for final maintainer feedback before graduating to `next`. The only open questions are minor design choices (e.g., whether the matching-inspired mode should be available outside of shallow repositories) and edge-case handling (e.g., migration of existing shallow repositories), but these are not blockers for merging. The backward compatibility story is strong: non-shallow repositories continue using wildcard refspecs by default, and the new behavior is opt-in for shallow repositories.

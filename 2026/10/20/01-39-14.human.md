This is a bugfix for a long-standing edge case in `git switch` and `git checkout`.

When either command creates a new branch and then fails to write the tracking configuration (for example, because `.git/config.lock` already exists), the command exits with an error—but only after updating the worktree and index. HEAD remains pointing to the old branch, leaving the user with a confusing state: staged changes that appear unrelated to the branch they thought they switched to.

The reproduction steps are clear: a simple sequence of `git init`, `git clone`, `git fetch`, and then artificially blocking the config file with a lockfile. The output shows the command exits with code 1, HEAD still points to `main`, but the worktree reflects the new branch. The commit message traces the root cause to `setup_tracking()` in `branch.c`, which calls `exit(1)` after the worktree is already modified, a behavior introduced in 2016.

The author is asking for design guidance before sending a patch: should the command complete the switch and only warn about the tracking failure, or should it fail atomically without touching the worktree? The question is well-posed and the scope is clearly defined—it affects all branch-creation variants (`switch -c`, `checkout -b`, `--track`, and DWIM).

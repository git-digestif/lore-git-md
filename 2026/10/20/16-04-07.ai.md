This is a v2 cover letter for a two-patch series introducing copy-on-write worktree creation and ephemeral branch reaping, targeting the worktree subsystem. The series responds directly to feedback from Junio C Hamano and brian m. carlson on the v1 proposal, which originally included a more controversial shared-branch capability.

The headline change is the removal of the shared-branch patch entirely. Instead, the series now focuses on two narrower but still substantial improvements: (1) `--reflink` support for `git worktree add`, enabling copy-on-write worktree creation on supported filesystems (btrfs/Linux, APFS/macOS, ReFS/Windows), and (2) automatic reaping of ephemeral branches created by `git worktree add` when the worktree is removed. The reflink implementation is now cross-platform, with Windows ReFS support added (via FSCTL_DUPLICATE_EXTENTS_TO_FILE, matching Git LFS's approach) and explicit handling for overlayfs on Linux. The reflink behavior remains opt-in (configurable via `worktree.reflink`) rather than automatic, a deliberate choice to avoid silently copying untracked files from the source worktree.

The cover letter and commit messages now include detailed explanations of edge cases: how dirty worktrees are handled (via index refresh before reset), why reflink is not automatic (performance on small files, untracked file copying), and the recommended pattern for safely using multiple worktrees at the same commit (one ref per worktree, created in a single `update-ref` transaction). The documentation has been expanded to cover these points, including a new example in git-worktree(1) showing the safe multi-worktree pattern. The reflink implementation itself is thorough, with no size cutoff for cloned files and careful handling of cluster alignment on Windows.

This v2 appears to be a well-scoped, technically solid response to the v1 feedback. The reflink feature addresses a clear performance bottleneck for users managing many worktrees, and the ephemeral branch reaping is a sensible cleanup for the auto-named branches that `worktree add` creates. The implementation touches core worktree logic, adds new copy-on-write primitives in copy.c, and includes extensive test coverage in t2400-worktree-add.sh. The changes are likely to be uncontroversial, though the opt-in nature of reflink may still draw discussion.

Subject: [RFC] git switch/checkout: inconsistent state when tracking setup fails
Series version: none (RFC discussion)
Originating author: 井上司 (Tsukasa Inoue)
Thread type: bug report / design discussion

Core problem or goal
The thread discusses a long-standing edge case in `git switch` and `git checkout` where, if the command creates a new branch but fails to write tracking configuration (e.g., due to a lock file conflict), it exits with an error *after* updating the worktree and index but *before* updating HEAD. This leaves the repository in a confusing state: the worktree reflects the new branch, but HEAD still points to the old branch, and staged changes appear unrelated to the user’s command. The issue affects `git switch`, `git switch -c`, `git checkout -b`, `git checkout --track`, and (with different symptoms) `git switch -C` on an existing branch.

Current status
No patch has been proposed yet; this remains an RFC seeking design guidance. The root cause is identified as `setup_tracking()` in `branch.c` calling `exit(1)` after worktree updates but before HEAD is moved, a behavior introduced in commit 27852b2c53 (2016). Junio C Hamano has weighed in with a clear design preference: the command should behave atomically, either completing the entire switch (including tracking setup) or failing cleanly without touching the worktree or index. This settles the high-level design question; future discussion is expected to focus on implementation details for achieving atomicity.

Key technical details
- **Commands affected**: `git switch`, `git checkout` (specifically branch-creation variants: `-b`, `-c`, `--track`, `-C`).
- **Subsystems touched**: `branch.c` (specifically `setup_tracking()`), worktree/index/HEAD update logic.
- **Old vs. new behavior**: Currently, the command updates the worktree and index but leaves HEAD pointing to the old branch, creating a mismatch. The desired behavior is now resolved: atomic all-or-none operation.
- **On-disk format changes**: None.
- **Test coverage**: None yet; reproduction steps are provided in the original email (fresh clone, fetch, lock file creation, then `git switch`).

Open questions and loose ends
1. **Implementation**: How to achieve atomicity in the branch-creation flow, particularly around the interaction between worktree updates, HEAD movement, and tracking configuration.
2. **Backward compatibility**: Whether the atomic behavior would break existing scripts or workflows that might (unintentionally) rely on the current halfway state.
3. **Scope of fix**: Whether to address only the immediate issue (tracking setup failure) or to also refactor other potential failure points in the branch-creation flow for consistency.

Subject: [RFC] git switch/checkout: inconsistent state when tracking setup fails
Series version: none (RFC discussion)
Originating author: 井上司 (Tsukasa Inoue)
Thread type: bug report / design discussion

Core problem or goal
The thread discusses a long-standing edge case in `git switch` and `git checkout` where, if the command creates a new branch but fails to write tracking configuration (e.g., due to a lock file conflict), it exits with an error *after* updating the worktree and index but *before* updating HEAD. This leaves the repository in a confusing state: the worktree reflects the new branch, but HEAD still points to the old branch, and staged changes appear unrelated to the user’s command. The issue affects `git switch`, `git switch -c`, `git checkout -b`, `git checkout --track`, and (with different symptoms) `git switch -C` on an existing branch.

Current status
No patch has been proposed yet; this is an RFC seeking design guidance. The root cause is identified as `setup_tracking()` in `branch.c` calling `exit(1)` after worktree updates but before HEAD is moved, a behavior introduced in commit 27852b2c53 (2016). The author presents two potential resolutions: (1) complete the switch and only report the tracking error, or (2) fail cleanly without touching the worktree.

Key technical details
- **Commands affected**: `git switch`, `git checkout` (specifically branch-creation variants: `-b`, `-c`, `--track`, `-C`).
- **Subsystems touched**: `branch.c` (specifically `setup_tracking()`), worktree/index/HEAD update logic.
- **Old vs. new behavior**: Currently, the command updates the worktree and index but leaves HEAD pointing to the old branch, creating a mismatch. The desired behavior is unresolved (see open questions).
- **On-disk format changes**: None.
- **Test coverage**: None yet; reproduction steps are provided in the email (fresh clone, fetch, lock file creation, then `git switch feat`).

Open questions and loose ends
1. **Design direction**: Should the command complete the switch and only report the tracking error, or should it fail cleanly without touching the worktree?
2. **Backward compatibility**: Would either approach break existing scripts or workflows that rely on the current (buggy) behavior?
3. **Scope of fix**: Should the solution address only the immediate issue (tracking setup failure), or should it also handle other potential failure points in the branch-creation flow?

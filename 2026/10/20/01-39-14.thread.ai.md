Subject: [RFC] git switch/checkout: inconsistent state when tracking setup fails
Series version: none (RFC discussion)
Originating author: 井上司 (Tsukasa Inoue)
Thread type: bug report / design discussion

Core problem or goal
The thread discusses a long-standing edge case in `git switch` and `git checkout` where, if the command creates a new branch but fails to write tracking configuration (e.g., due to a lock file conflict), it exits with an error *after* updating the worktree and index but *before* updating HEAD. This leaves the repository in a confusing state: the worktree reflects the new branch, but HEAD still points to the old branch, and staged changes appear unrelated to the user’s command. The issue affects `git switch`, `git switch -c`, `git checkout -b`, `git checkout --track`, and (with different symptoms) `git switch -C` on an existing branch. The root cause is `setup_tracking()` in `branch.c` calling `exit(1)` after worktree updates but before HEAD is moved, a behavior introduced in commit 27852b2c53 (2016). The discussion now also encompasses broader control flow issues: `merge_working_tree()` updates the worktree and index on *every* branch switch (not just when `-m` is used), and the current sequence—update worktree/index, create ref, write tracking config (which may fail), then update HEAD—explains why failures leave the repository in an inconsistent state. The `-m` case is similarly affected: if a conflict occurs, HEAD remains on the old branch, the file is left conflicted, and changes stay in the stash, leaving the repository in a broken state that cannot be cleanly retried.

Current status
Junio C Hamano has endorsed 井上司’s incremental proposal to make `setup_tracking()` return an error instead of calling `exit()`, aligning `git switch` and `git checkout` with the behavior of `git push -u`, `git clone`, and `git fetch`. This marks a shift from his earlier preference for full atomicity and removes the main obstacle to a near-term fix. The thread is now tilting toward accepting this incremental approach, though the broader control flow issues (e.g., worktree/index updates occurring before HEAD movement) remain unaddressed. No patch has been posted yet, but the path forward is clearer. The discussion may now focus on implementation details, backward compatibility, and whether follow-up work will tackle the remaining atomicity concerns.

Key technical details
- **Commands affected**: `git switch`, `git checkout` (specifically branch-creation variants: `-b`, `-c`, `--track`, `-C`).
- **Subsystems touched**: `branch.c` (specifically `setup_tracking()`), worktree/index/HEAD update logic (`merge_working_tree()`, `unpack_trees()`), and the broader checkout/switch control flow.
- **Old vs. new behavior**: Currently, the command updates the worktree and index but leaves HEAD pointing to the old branch, creating a mismatch. The incremental proposal would prevent the halfway state by returning an error from `setup_tracking()` before HEAD is updated, but would not achieve full atomicity. The current sequence is: update worktree and index, create the ref, write tracking config (which may fail), then update HEAD. The `-m` case is similarly affected: if a conflict occurs, HEAD remains on the old branch, the file is left conflicted, and changes stay in the stash.
- **On-disk format changes**: None.
- **Test coverage**: None yet; reproduction steps are provided in the original email (fresh clone, fetch, lock file creation, then `git switch`).

Open questions and loose ends
1. **Implementation details**: How to structure the error return from `setup_tracking()` and ensure it propagates correctly through the checkout/switch control flow.
2. **Backward compatibility**: Whether the incremental approach would break existing scripts or workflows that might (unintentionally) rely on the current halfway state.
3. **Scope of follow-up work**: Whether the broader control flow issues (e.g., worktree/index updates occurring before HEAD movement) will be addressed in a separate effort, and if so, what the timeline or priority might be.

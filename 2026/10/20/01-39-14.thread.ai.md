Subject: [RFC] git switch/checkout: inconsistent state when tracking setup fails
Series version: none (RFC discussion)
Originating author: 井上司 (Tsukasa Inoue)
Thread type: bug report / design discussion

Core problem or goal
The thread discusses a long-standing edge case in `git switch` and `git checkout` where, if the command creates a new branch but fails to write tracking configuration (e.g., due to a lock file conflict), it exits with an error *after* updating the worktree and index but *before* updating HEAD. This leaves the repository in a confusing state: the worktree reflects the new branch, but HEAD still points to the old branch, and staged changes appear unrelated to the user’s command. The issue affects `git switch`, `git switch -c`, `git checkout -b`, `git checkout --track`, and (with different symptoms) `git switch -C` on an existing branch.

Current status
No patch has been proposed yet; the discussion remains in the RFC phase. The root cause is identified as `setup_tracking()` in `branch.c` calling `exit(1)` after worktree updates but before HEAD is moved, a behavior introduced in commit 27852b2c53 (2016). Junio C Hamano has expressed a strong preference for atomic all-or-none behavior, either completing the entire switch (including tracking setup) or failing cleanly without touching the worktree or index. However, 井上司 (Tsukasa Inoue) has now proposed an incremental alternative: making `setup_tracking()` return an error instead of calling `exit()`, which would prevent the halfway state but not achieve full atomicity. This proposal aligns `git switch` and `git checkout` with the behavior of `git push -u`, `git clone`, and `git fetch`, which continue even when tracking configuration fails. The trade-off between a partial fix now and a more complete refactoring later is now the central point of discussion.

Key technical details
- **Commands affected**: `git switch`, `git checkout` (specifically branch-creation variants: `-b`, `-c`, `--track`, `-C`).
- **Subsystems touched**: `branch.c` (specifically `setup_tracking()`), worktree/index/HEAD update logic.
- **Old vs. new behavior**: Currently, the command updates the worktree and index but leaves HEAD pointing to the old branch, creating a mismatch. The desired behavior is now under debate: Junio prefers atomic all-or-none operation, while 井上司 proposes a smaller change to avoid the halfway state without full atomicity.
- **On-disk format changes**: None.
- **Test coverage**: None yet; reproduction steps are provided in the original email (fresh clone, fetch, lock file creation, then `git switch`).

Open questions and loose ends
1. **Implementation trade-offs**: Whether to accept 井上司’s incremental proposal (error return from `setup_tracking()`) or hold out for a full atomic refactoring. The latter would require undoing worktree, ref, and config changes, as well as handling `die()` calls in the checkout flow.
2. **Backward compatibility**: Whether either approach would break existing scripts or workflows that might (unintentionally) rely on the current halfway state.
3. **Scope of fix**: If the incremental approach is accepted, whether to address other potential failure points in the branch-creation flow in a follow-up effort.

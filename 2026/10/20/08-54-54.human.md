This is the third patch in Patrick Steinhardt’s four-patch bugfix series restoring dynamic reload of alternate object databases in the files-based ODB backend. The patch addresses a performance inefficiency in the alternates-checking logic introduced by the earlier fix (patch 2/4).

The commit reorders the checks in `odb_files_dir_is_usable()` so that the cheap hashmap lookup for already-known alternates happens first, avoiding unnecessary filesystem syscalls. The change is a straightforward optimization: instead of resolving the primary object directory’s realpath and checking directory existence upfront, the code now checks the hashmap first, skipping the expensive operations if the alternate is already known. The commit message includes benchmark results showing the improvement: lookup time for 20k missing objects drops from 309ms (post-fix, pre-optimization) to 263ms, though it remains slower than the pre-regression baseline of 181ms.

The patch is narrowly scoped to `odb/source-files.c` and is well-motivated by the benchmark data. It’s a clear win for performance and doesn’t introduce new behavior or edge cases. Given the series’ overall goal of restoring a broken feature while minimizing performance impact, this patch is a logical and uncontroversial follow-up to the core fix. Reviewers will likely focus on whether the reordering could mask any subtle correctness issues, but the commit message and code changes suggest this is a safe optimization.

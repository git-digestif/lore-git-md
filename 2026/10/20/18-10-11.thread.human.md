This thread began when Steven Rostedt, a Linux kernel developer, reported that a recent Git commit (0c0f93e7fa64) broke downstream tooling—specifically `ktest.pl` in the Linux kernel and `xfstests-bld`—by changing the output format of `git bisect`. The commit added single quotes around bisect terms, disrupting scripts that parse Git’s human-readable messages as if they were stable interfaces. Rostedt and Theodore Ts'o (author of `xfstests-bld`) later clarified that their tools rely on parsing both the "Bisecting: ..." progress messages and the final "first bad commit" line, and that existing plumbing commands or `git bisect run` cannot replace this logic due to gaps in progress tracking and integration with complex workflows (e.g., kernel build/boot/test cycles or distributed VM-based testing).

The immediate issue was resolved by updating the downstream tools to handle the new output format, but the thread evolved into a broader discussion about output stability and tooling resilience. Ts'o proposed adding a `--format=json` option to `git bisect` to provide structured, machine-readable output, grounding the idea in concrete use cases like `xfstests-bld`. Junio C Hamano clarified that such a feature could be introduced in a minor release, decoupling it from Git 3.0. Meanwhile, Andreas Schwab offered plumbing-based alternatives—`git rev-parse --bisect` and `git rev-list`—to extract bisect state without parsing human-readable output. While these commands address some automation needs, they do not fully resolve the gaps Rostedt and Ts'o highlighted, such as progress tracking or querying whether the first bad commit has been found. The thread remains informational, serving as a reference for future discussions about structured output, plumbing enhancements, and the trade-offs between human-readable and machine-parsable interfaces. No action is currently pending on the Git side.

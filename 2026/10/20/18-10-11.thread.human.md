This thread began as an informational heads-up from Steven Rostedt, a Linux kernel developer, about a real-world dependency on Git's `git bisect` output formatting. A recent Git commit (0c0f93e7fa64) changed the output of `git bisect` to wrap bisect terms in single quotes, breaking downstream tooling like the Linux kernel's `ktest.pl` and Theodore Ts'o's `xfstests-bld`, which parse Git's human-readable messages. The immediate issue was resolved with a kernel patch to update `ktest.pl`'s parsing logic, but the thread has since evolved into a broader discussion about the risks of treating Git's output as a stable interface and potential mitigation strategies.

Rostedt's follow-up clarifies that `ktest.pl` is far more complex than `git bisect run`, handling the entire kernel build, installation, boot, and test cycle. This complexity explains why `ktest.pl` relies on parsing Git's output—specifically the "Bisecting: ..." progress messages—to track bisect progress, as there are no plumbing commands to inspect the bisect state directly. Junio C Hamano suggested plumbing-based workarounds for the "first bad commit" case (e.g., inspecting the `bisect/bad` ref), but these don't address the progress-tracking gap. Theodore Ts'o proposed adding a `--format=json` option to `git bisect` to provide structured output, tying the idea to Git 3.0 as a forward-looking enhancement. While no action is currently requested or pending, the thread serves as a reference for future discussions about output stability, tooling resilience, and potential improvements to `git bisect`'s plumbing and structured output capabilities.

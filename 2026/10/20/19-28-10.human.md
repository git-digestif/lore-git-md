This is an informational follow-up in the ongoing discussion about downstream tooling (`ktest.pl`) parsing Git’s human-readable output. Kristoffer Haugsbakk chimes in with a brief but pointed question: whether `ktest.pl`’s manual bisect-tracking logic could be replaced by `git bisect run`, which automates the entire bisect process and exits with a status code indicating success or failure. The question is left unanswered in this email, but it sharpens the focus on the gap in Git’s plumbing commands for bisect state inspection.

The exchange underscores the fragility of parsing Git’s output for automation. While `git bisect run` handles the end-to-end workflow, it doesn’t expose intermediate progress (like the "Bisecting: ..." messages `ktest.pl` relies on), leaving tooling authors to choose between incomplete plumbing and brittle parsing. No controversy here—just a quiet nudge toward recognizing that even well-intentioned tooling can end up depending on Git’s human-readable messages, and that the project might need to think harder about how to support automation without breaking it. The thread remains low-stakes but serves as a useful case study for future discussions about output stability.

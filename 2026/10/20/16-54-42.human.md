This is a **substantive follow-up in the reftable backend bugfix thread**, adding a new technical observation from Aniket Gupta. The patch itself remains unrevised, but Aniket’s testing reveals an edge case in Patrick Steinhardt’s proposed fix: while changing `reftable_alloc_size()` to use `uintmax_t` parameters resolves the overflow issue for `REFTABLE_ALLOC_ARRAY`, the companion macro `REFTABLE_CALLOC_ARRAY` bypasses this helper and calls `reftable_calloc()` directly with a `size_t` argument. On 32-bit systems, this could still truncate large allocations, though Aniket notes no current callers pass values large enough to trigger the problem.

Aniket also flags a test-coverage gap: the existing unit test passes only because of the decoder’s explicit `count > in.len` check. If that check is removed in a revised patch, the test may no longer catch the overflow scenario on 64-bit systems, where truncation does not occur. He suggests adding a direct test for `reftable_alloc_size()` to ensure the helper itself correctly rejects oversized allocations regardless of platform.

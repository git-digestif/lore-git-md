This thread is about a long-standing edge case in `git switch` and `git checkout` where creating a new branch fails midway—after updating the worktree and index but before moving HEAD—leaving the repository in a confusing state. The issue surfaces when tracking configuration fails (e.g., due to a lock file conflict) and affects commands like `git switch -c`, `git checkout -b`, and `git switch -C`.

井上司 (Tsukasa Inoue) initially reported the bug and proposed an incremental fix: making `setup_tracking()` return an error instead of calling `exit()`, which Junio C Hamano has now endorsed. The discussion has since shifted to implementation details, with 井上司 outlining two transactional approaches for coordinating ref updates, worktree changes, and HEAD movement. The favored approach avoids holding locks during worktree updates to prevent blocking concurrent operations (like autostash), but accepts a small race window where another process could create the same branch mid-switch. The tracking configuration would be written early and rolled back if later steps fail.

Key participants agree the incremental fix is the right near-term step, though broader control flow issues (e.g., worktree updates occurring before HEAD movement) remain unaddressed. No patch has been posted yet, but the design is now focused on balancing atomicity with practicality.

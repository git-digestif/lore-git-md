This thread is about a long-standing edge case in `git switch` and `git checkout` where the repository is left in an inconsistent state if tracking configuration fails after the worktree and index have been updated but before HEAD is moved. The issue affects branch-creation commands like `git switch -c` and `git checkout -b`, as well as conflict-prone operations like `git switch -m`. Tsukasa Inoue reported the bug and proposed an incremental fix—making `setup_tracking()` return an error instead of calling `exit()`—which Junio C Hamano has now endorsed as a pragmatic near-term solution.

The root cause lies in the control flow: `merge_working_tree()` updates the worktree and index on *every* branch switch (not just when `-m` is used), and these updates happen before HEAD is moved. If a later step, such as writing tracking configuration, fails, the repository is left in a confusing halfway state. D. Ben Knoble’s recent email underscores this broader issue, noting that reordering steps might help but wouldn’t achieve full atomicity. While the incremental fix is likely to proceed, the thread has also surfaced deeper questions about whether the checkout/switch control flow should be restructured to ensure all-or-none behavior. For now, the focus remains on implementing the error-return approach, with no patch yet posted.

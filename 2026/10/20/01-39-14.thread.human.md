This thread explores a long-standing edge case in `git switch` and `git checkout` where the command leaves the repository in an inconsistent state if tracking setup fails. Specifically, if a new branch is created but tracking configuration cannot be written (e.g., due to a lock file conflict), the command exits with an error after updating the worktree and index but before moving HEAD. This results in a confusing mismatch: the worktree reflects the new branch, but HEAD still points to the old one, and staged changes appear unrelated to the user’s command.

The discussion has centered on whether to fix this incrementally or pursue a full atomic refactoring. Originally, Junio C Hamano advocated for atomic all-or-none behavior, ensuring the entire switch either completes or fails cleanly without touching the repository. However, in the latest email, Junio endorses 井上司 (Tsukasa Inoue)’s proposal to make `setup_tracking()` return an error instead of calling `exit()`, aligning `git switch` and `git checkout` with the behavior of `git push -u`, `git clone`, and `git fetch`. This incremental approach avoids the halfway state but does not achieve full atomicity. The broader control flow issues—such as worktree and index updates occurring before HEAD movement—remain unaddressed but may be tackled in follow-up work.

Ben Knoble later raised concerns about the control flow, confirming that the current sequence (update worktree/index, create ref, write tracking config, then update HEAD) is suboptimal. With Junio’s endorsement of the incremental fix, the path forward is now clearer, though questions about backward compatibility and the scope of future refactoring remain open. No patch has been posted yet, but the discussion is now focused on implementation details.

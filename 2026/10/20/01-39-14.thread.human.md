This thread is about a long-standing edge case in `git switch` and `git checkout` where the command can leave the repository in an inconsistent state if tracking configuration fails. Specifically, if you create a new branch but the command fails to write tracking info (e.g., due to a lock file conflict), the worktree and index are updated while HEAD remains on the old branch, creating confusion for users.

The discussion is still in the design phase, with no patch yet proposed. The root cause is `setup_tracking()` in `branch.c` calling `exit(1)` after worktree updates but before HEAD is moved—a behavior introduced in 2016. Junio C Hamano has argued for atomic all-or-none behavior, where the command either completes fully or fails without touching the repository. Tsukasa Inoue (the original reporter) has proposed a smaller fix: making `setup_tracking()` return an error instead of exiting, which would prevent the halfway state but not achieve full atomicity. D. Ben Knoble recently raised a deeper concern: the worktree and index updates happen *before* both branch creation and HEAD movement, suggesting the control flow may need broader restructuring.

Inoue’s latest email clarifies the technical flow: `merge_working_tree()` updates the worktree and index on every branch switch (not just with `-m`), and the current sequence is worktree/index update → ref creation → tracking config (which may fail) → HEAD update. This explains why failures in `setup_tracking()` leave the repository inconsistent. The `-m` case has similar issues: if conflicts occur, HEAD stays on the old branch, files remain conflicted, and retrying the command fails, leaving the repository broken. The thread is now focused on whether to accept Inoue’s incremental fix or hold out for a more complete refactoring.

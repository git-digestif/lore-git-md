This thread is about a long-standing but recently noticed bug in `git switch` and `git checkout`. When these commands create a new branch but fail to write the tracking configuration (for example, because `.git/config.lock` exists), they exit with an error after updating the worktree and index but before updating HEAD. This leaves the repository in a confusing state: the worktree reflects the new branch, but HEAD still points to the old one, making staged changes appear unrelated to the user's command.

The issue was introduced in 2016 and affects multiple workflows, including `git switch -c`, `git checkout -b`, `--track`, and (with different symptoms) `git switch -C` on an existing branch. The author, 井上司, has provided clear reproduction steps and traced the root cause to `setup_tracking()` in `branch.c`, which calls `exit(1)` after the worktree is updated but before HEAD is moved. No patch is attached yet; the email is seeking design guidance on whether the command should complete the switch and only report the tracking error, or fail cleanly without touching the worktree. So far, this is the first message in the thread, so no responses or decisions have been made.

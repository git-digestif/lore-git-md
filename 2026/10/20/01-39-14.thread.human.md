This thread is about a long-standing edge case in `git switch` and `git checkout` where creating a new branch fails midway—after updating the worktree and index but before moving HEAD—if tracking configuration cannot be written (e.g., due to a lock file conflict). The result is a confusing state where the worktree reflects the new branch, but HEAD still points to the old one, leaving users disoriented. The issue affects several branch-creation variants of both commands and stems from a 2016 commit that introduced an `exit(1)` in `setup_tracking()` after worktree updates but before HEAD is updated.

Junio has weighed in with a clear design preference: the command should behave atomically, either completing the entire switch (including tracking setup) or failing cleanly without altering the worktree or index. This "all-or-none" approach resolves the core design question raised in the original RFC by 井上司 (Tsukasa Inoue), who first reported the bug and provided reproduction steps. The discussion can now shift to implementation details, such as how to achieve atomicity, while backward compatibility concerns remain unaddressed. No patches have been proposed yet, and the thread is still in the design phase.

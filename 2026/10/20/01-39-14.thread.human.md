This thread began when 井上司 (Tsukasa Inoue) reported a long-standing edge case in `git switch` and `git checkout`: when these commands create a new branch but fail to write tracking configuration (e.g., due to a lock file conflict), they exit with an error after updating the worktree and index but before moving HEAD, leaving the repository in a confusing halfway state. Junio C Hamano quickly weighed in, stating a clear preference for atomic all-or-none behavior—either the entire switch completes (including tracking setup) or it fails cleanly without touching the worktree or index.

In the latest email, Inoue acknowledges Junio’s preference but argues that full atomicity would require a large refactoring. Instead, they propose a smaller, incremental fix: making `setup_tracking()` return an error rather than calling `exit()`, which would prevent the halfway state but stop short of full atomicity. This approach aligns `git switch` and `git checkout` with the behavior of `git push -u`, `git clone`, and `git fetch`, which continue even when tracking configuration fails. The trade-off is now on the table: accept a partial fix now or hold out for a more complete solution. No patch has been posted yet, and the thread remains in the design phase.

This is the second patch in Harald Nordgren’s v10 series introducing a "matching-inspired" fetch mode for shallow repositories. The patch extracts the existing logic that checks whether the current branch’s upstream lives on the remote being fetched into a new helper function, `collect_upstream_from_remote()`, so the same logic can be reused for other branches.

The change is a pure refactoring with no behavior changes. The extracted logic was previously inlined in `do_fetch()` in `builtin/fetch.c` and is now moved to `remote.c` with a corresponding declaration in `remote.h`. The helper takes a `struct repository *`, a `string_list` to populate, a `remote`, and an optional branch name (NULL means the current branch), and adds the upstream refs of any matching branches to the list. The `the_repository` global is no longer hardcoded, making the function more flexible for future use.

This patch directly addresses Junio’s review feedback from v8, which asked for the `if/else if/else` control-flow reorganization to be moved from Patch 2/5 to Patch 3/5. The NULL-check for `branch` is also restored, resolving the second review point. The commit message clearly explains the motivation: the "does this branch build on this remote" check is independent of the remote’s configured fetch refspec, and extracting it into a helper allows the same logic to be reused for branches other than just the current one.

The patch is small (38 lines added, 9 removed) and focused, touching only `builtin/fetch.c`, `remote.c`, and `remote.h`. The test coverage from the series (in `t/t5510-fetch.sh` and `t/t5586-fetch-refmap.sh`) ensures the refactoring does not break existing behavior. This patch is uncontroversial and ready for review, with no open technical concerns. It is a necessary step toward the dynamic branch enumeration logic introduced in Patch 3/5.

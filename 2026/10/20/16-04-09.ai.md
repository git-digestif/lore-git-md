This is the second patch in Jason Newton's v2 worktree improvements series, introducing automatic reaping of ephemeral branches created by `git worktree add`. The patch targets the worktree subsystem and addresses a long-standing usability pain point: when `git worktree add` auto-creates a branch (via DWIM naming), that branch persists after the worktree is removed, cluttering `refs/heads/` with disposable branches that require manual cleanup.

The implementation is clean and well-scoped. It records ownership of auto-created branches in the worktree's administrative directory (`worktrees/<id>/owned-branch`) at creation time, then deletes the branch when the worktree is removed via `git worktree remove`. Ownership is narrowly defined: only branches created by DWIM auto-naming are marked as ephemeral; branches named explicitly with `-b`/`-B` or pre-existing branches are never owned and never reaped. The patch handles edge cases like branch renames (updating the ownership marker) and provides a `--keep-branch` option to preserve the branch if needed. The deletion is unconditional (even for unmerged commits) because ephemeral branches are disposable by design—users can anchor commits with an ordinary branch beforehand if they want to keep them.

The patch touches core worktree logic in `builtin/worktree.c` and `builtin/branch.c`, adding the ownership marker infrastructure and integrating it with branch renaming. Test coverage in `t2400-worktree-add.sh` is thorough, covering the basic reaping case, branch renames, `--keep-branch`, and interactions with pre-existing branches. Documentation updates in `git-worktree.adoc` clearly explain the new behavior and limitations. The implementation is backward-compatible: older Git versions will simply ignore the `owned-branch` marker and keep the branch on removal, preserving the current behavior.

This is a sensible, uncontroversial improvement that directly addresses a common annoyance. The design choices (narrow ownership scope, unconditional deletion, and opt-out rather than opt-in) are well-justified in the commit message and documentation. The patch is likely to be merged as-is, though there may be minor discussion about whether `--keep-branch` should be the default or if the feature should be configurable. Key technical details for follow-up discussion include the `owned-branch` marker file, the `read_owned_branch()` helper, the `--keep-branch` flag, and the integration with `git branch -m`.

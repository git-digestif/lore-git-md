Core problem or goal
The thread explores whether `git pull --rebase` miscomputes the fork-point when the user has configured a custom fetch refspec (e.g., `+refs/heads/*:refs/remotes/origin/custom/*`). The current implementation in `get_tracking_branch()` hard-codes the default layout (`refs/heads/<branch>` → `refs/remotes/<remote>/<branch>`), which may cause `get_rebase_fork_point()` to look up a non-existent or incorrect remote-tracking ref, leading to an incorrect fork-point and rebase result.

Current status
No patch posted; discussion is at the conceptual stage. Junio C Hamano has confirmed the issue is real: the hard-coded assumption in `get_tracking_branch()` breaks when users configure custom fetch refspecs. The FIXME comment in the code is acknowledged as valid. The discussion is now likely to shift toward how to resolve the configured fetch mapping dynamically, possibly using Git’s existing refspec APIs (e.g., `remote_find_tracking()` or `branch_get_upstream()`).

Core problem or goal
The thread explores whether `git pull --rebase` miscomputes the fork-point when the user has configured a custom fetch refspec (e.g., `+refs/heads/*:refs/remotes/origin/custom/*`). The current implementation in `get_tracking_branch()` hard-codes the default layout (`refs/heads/<branch>` → `refs/remotes/<remote>/<branch>`), which may cause `get_rebase_fork_point()` to look up a non-existent or incorrect remote-tracking ref, leading to an incorrect fork-point and rebase result. Junio C Hamano has confirmed the issue is real, and Harald Nordgren has explicitly labeled it a "hardcoding bug."

Current status
No patch posted; discussion remains at the conceptual stage. The issue is confirmed as a legitimate defect, not a design limitation. Jyotish Kumar is still investigating the problem and has not yet begun work on a fix. The discussion continues to focus on whether the bug exists in `master` (requiring a standalone fix) or is confined to an in-flight topic (where it could be addressed as part of that series). The next steps involve deeper analysis of existing code and mailing list archives to determine the best approach for resolving the refspec hardcoding bug, likely using Git’s existing refspec APIs (e.g., `remote_find_tracking()` or `branch_get_upstream()`).

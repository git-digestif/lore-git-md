Subject: RFC: git pull --rebase and custom fetch refspecs
Series version: RFC (no patch version)

Thread type: RFC / design discussion

Core problem or goal
The thread explores whether `git pull --rebase` miscomputes the fork-point when the user has configured a custom fetch refspec (e.g., `+refs/heads/*:refs/remotes/origin/custom/*`). The current implementation in `get_tracking_branch()` hard-codes the default layout (`refs/heads/<branch>` → `refs/remotes/<remote>/<branch>`), which may cause `get_rebase_fork_point()` to look up a non-existent or incorrect remote-tracking ref, leading to an incorrect fork-point and rebase result.

Current status
No patch posted; discussion remains at the conceptual stage. Junio C Hamano has confirmed the issue is real: the hard-coded assumption in `get_tracking_branch()` breaks when users configure custom fetch refspecs. Harald Nordgren has now explicitly labeled the issue as a "hardcoding bug," reinforcing its status as a legitimate defect rather than a design limitation. The discussion is shifting toward determining whether the bug exists in `master` (requiring a standalone fix) or is confined to an in-flight topic (where it could be addressed as part of that series). The next steps will likely involve using Git’s existing refspec APIs (e.g., `remote_find_tracking()` or `branch_get_upstream()`) to resolve the configured fetch mapping dynamically.

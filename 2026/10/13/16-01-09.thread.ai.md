Core problem or goal
The thread explores whether `git pull --rebase` miscomputes the fork-point when the user has configured a custom fetch refspec (e.g., `+refs/heads/*:refs/remotes/origin/custom/*`). The current implementation in `get_tracking_branch()` hard-codes the default layout (`refs/heads/<branch>` → `refs/remotes/<remote>/<branch>`), which may cause `get_rebase_fork_point()` to look up a non-existent or incorrect remote-tracking ref, potentially leading to an incorrect fork-point and thus an incorrect rebase result.

Current status
No patch posted; discussion is at the conceptual stage. The author has identified the code path (`get_tracking_branch()` and `get_rebase_fork_point()` in `builtin/pull.c`) and the refspec pattern (`+refs/heads/*:refs/remotes/origin/custom/*`) but has not yet proposed a concrete fix or test case.

- Are there other places in Git that make the same hard-coded assumption about remote-tracking ref layout?

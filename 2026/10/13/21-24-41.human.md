This is a **performance regression analysis** for the `git log --follow` slowdown reported earlier.

SZEDER Gábor confirms the regression is real and measurable, though less severe in Git’s own repository than in the Linux kernel. Using a simple benchmark, he shows that commit 304812ed33 ("log: improve --follow following renames for non-linear history") causes `git log --follow` to run **2.7× slower** on a test file in Git’s history. Most of the extra time—about 4.4 seconds out of 5.5—is spent in `propagate_follow_pathspec_to_parent()` comparing the current commit with its **second through N-th parents**, a step that wasn’t present before the regression.

He also notes that `git log -L` (line-level history tracking) remains significantly faster than `--follow`, even before the regression. The difference appears to stem from two design choices: line-level log skips diffing against non-first parents if the file isn’t modified in the first-parent diff, and it only looks for renames when the file is missing in a parent. `--follow`, by contrast, always diffs against all parents and always checks for renames, which may explain its inherent slowness.

The analysis is concrete and actionable: it pinpoints the exact function (`propagate_follow_pathspec_to_parent`) and the specific loop over non-first parents as the bottleneck. This gives the original author (or anyone else) a clear starting point for a fix. No patch is proposed yet, but the diagnosis is thorough enough that a performance-aware developer could likely prototype a solution quickly.

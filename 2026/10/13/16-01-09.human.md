This is an RFC proposing a bugfix in `git pull`'s fork-point lookup logic.

The author, a newcomer, has identified a potential issue in `builtin/pull.c`: the `get_tracking_branch()` function assumes that remote-tracking refs always follow the default pattern `refs/remotes/<remote>/<branch>`. However, users can configure custom fetch refspecs (e.g., `+refs/heads/*:refs/remotes/origin/custom/*`), which would place the remote-tracking ref at `refs/remotes/origin/custom/main` instead. This could cause `git pull --rebase` to misidentify or fail to find the fork point, leading to incorrect rebase behavior.

The analysis appears sound. The commit message does not include a patch, but the author suggests resolving the configured fetch mapping rather than hardcoding the ref layout. This is a plausible direction, though the email does not explore how complex such a change might be or whether it would introduce new edge cases.

The issue is narrowly scoped to `git pull --rebase` and its interaction with custom refspecs. It does not appear to be part of a larger series or ongoing effort. The author is seeking feedback on whether this is a real problem before investing further time, so this is very much a "does this make sense?" inquiry rather than a polished patch.

For a busy reader, this is worth a quick look if you use custom refspecs or care about `git pull` correctness. The problem is easy to understand, and the fix direction seems reasonable, but the thread is still in the exploratory phase.

This is the first patch in a two-part bugfix series targeting the `rerere` subsystem. It addresses a long-standing race condition where concurrent `rerere` operations contend for the shared `MERGE_RR.lock`, a problem that became more pronounced after Git 2.54 introduced the geometric maintenance strategy, which triggers `git rerere gc` more aggressively.

The patch introduces a configurable timeout (`rerere.lockTimeout`, defaulting to 1000 milliseconds) for acquiring the `MERGE_RR.lock`. Instead of failing immediately when the lock is held—typically by a background `git rerere gc`—commands now wait up to the timeout before giving up. This change prevents rebase operations from crashing mid-sequence when they encounter a held lock, which previously left the repository in a broken state where subsequent `git rebase --continue` calls would fail with "you have staged changes in your working tree." The default timeout is chosen to cover typical `rerere gc` operations, which usually complete in under a second.

The implementation touches `rerere.c` (locking logic and error handling), updates `Documentation/config/rerere.adoc` to document the new configuration key, and adds comprehensive test coverage in `t/t4200-rerere.sh`. The tests verify that commands wait for the lock when it becomes available, fail appropriately after the timeout expires, and handle edge cases like `git rebase --abort` correctly. The patch preserves backward compatibility: a timeout of 0 restores the old behavior, and error messages remain unchanged to avoid misleading users.

This patch is well-motivated and technically sound. The commit message clearly explains the problem, the solution, and the trade-offs, and the test coverage is thorough. All prior feedback from Junio C Hamano and Patrick Steinhardt has been incorporated, including minor adjustments to test hygiene and documentation clarity. The patch is ready for integration and addresses a real pain point for users running rebases alongside background maintenance.

This is the first patch in a two-part feature series introducing a configurable timeout (`core.indexLockTimeout`) for Git’s index lock. The goal is to reduce contention between background IDE `git status` calls and user-initiated commands like `git add` or `git commit`, allowing the latter to wait briefly for the lock instead of failing immediately.

The patch implements the core logic in `repository.c`, extending the `repo_hold_locked_index()` function to respect the new timeout setting. It also disables waiting if the index was already read (to avoid write races), a safeguard that limits the feature’s scope to commands that lock the index *before* reading it. The default timeout is set to 1 second, a value the author justifies as "effective but not too long" to avoid surprising users. Documentation for the new config key is added to `core.adoc`, and a new test script (`t/t0032-index-lock-timeout.sh`) verifies the behavior, including edge cases like commands that read the index before locking.

The implementation is clean and targeted, focusing on the most common commands (e.g., `add`, `checkout`) while explicitly excluding others (e.g., `rebase`, `merge`) to avoid complicating their lock-ordering logic. The test coverage is thorough for the introduced behavior, though the default timeout may spark debate. The patch is well-motivated and addresses a real pain point for IDE users, making it worth attention from reviewers familiar with Git’s locking mechanisms.

This is a maintainer review of a bugfix patch for `git fast-import`. Junio C Hamano is scrutinizing the commit message and the patch's clarity, not the technical correctness of the fix itself (which he seems to accept). The patch itself remains unchanged from v2; this email is purely about the explanation.

The core issue is that the commit message does not clearly distinguish between objects that are *always* unavailable (those created in the current session and not yet flushed to the ODB) and objects that *might* be unavailable (those whose flush timing is unpredictable). Junio suggests rephrasing the message to say "sometimes results in a crash" rather than implying the crash is inevitable. He also questions the parenthetical remark about "working implementation" for blobs, which he finds confusing without an explanation of why blobs behave differently from commits.

Junio then provides a rewritten commit message that he believes would be clearer. It explicitly describes the in-progress packfile mechanism, explains why `ls` and `cat-blob` already work (they check the fast-import object cache first), and details the specific code path that `parse_from_existing` now follows: cache lookup, tag peeling, and unpacking from the in-progress packfile before falling back to the ODB. The rewritten message is more precise about the timing ("until a 'checkpoint' command or the end of the session") and the object types involved.

The patch itself is not controversial. Junio's feedback is entirely about improving the commit message's clarity and precision. The fix is small, targeted, and already has test coverage in `t9300-fast-import.sh` for both SHA-1 and SHA-256 repositories. Once the commit message is revised, this patch is likely to be accepted. No further technical changes are requested.

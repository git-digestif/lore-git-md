This is the second patch in a two-patch feature series introducing a configurable index lock timeout (`core.indexLockTimeout`) to reduce contention between background IDE operations and user commands. This patch modifies `git commit` to lock the index *before* reading it, ensuring the timeout applies consistently.

The change is straightforward: `git commit` now acquires the index lock upfront in `prepare_index()`, rather than in separate branches later. The commit message traces the history of this lock order, noting that an earlier refactoring (2888605c64 in 2007) accidentally moved the read before the lock without clear justification. The patch restores the original order, which is necessary for the timeout mechanism introduced in Patch 1 to work.

The test adjustment in `t/t0032-index-lock-timeout.sh` reflects the new behavior: `git commit` now waits for the lock (if configured) instead of failing immediately. This aligns `commit` with other commands like `add` and `checkout` that already respect the timeout.

The patch is small and targeted, touching only `builtin/commit.c` and the test script. It addresses a key limitation of the series—without this change, `git commit` would bypass the timeout entirely. The justification is clear, and the historical context helps explain why the lock order matters. No new edge cases are introduced, but the change could theoretically affect scripts that rely on `commit` failing fast when the index is locked. The author has not flagged this as a concern, suggesting it’s either unlikely or acceptable.

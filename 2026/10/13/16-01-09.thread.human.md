This thread is about a bug in `git pull --rebase` that causes it to miscompute the fork-point when users configure custom fetch refspecs (e.g., `+refs/heads/*:refs/remotes/origin/custom/*`). The issue stems from a hard-coded assumption in `get_tracking_branch()` that remote-tracking refs follow the default layout (`refs/heads/<branch>` → `refs/remotes/<remote>/<branch>`), which breaks when users deviate from this pattern. Junio C Hamano and Harald Nordgren have both confirmed the issue is real, with Harald explicitly calling it a "hardcoding bug."

The discussion is still in the early stages, with no patch proposed yet. Jyotish Kumar, who raised the issue, is investigating the problem and has clarified that it isn’t being addressed by any in-flight topic. The next steps will likely involve using Git’s existing refspec APIs (e.g., `remote_find_tracking()` or `branch_get_upstream()`) to resolve the configured fetch mapping dynamically. Key open questions include whether the bug exists in `master` (requiring a standalone fix) or is confined to an in-progress series, and what test cases are needed to cover edge cases like partial or non-standard refspecs. Harald’s work on narrowing default `git fetch` behavior may share underlying refspec resolution challenges with this issue.

This thread is exploring a bug in `git pull --rebase` where the command miscomputes the fork-point when users configure custom fetch refspecs (e.g., mapping `refs/heads/*` to `refs/remotes/origin/custom/*`). The issue stems from hard-coded assumptions in `get_tracking_branch()` about the default remote-tracking ref layout, which breaks when non-standard refspecs are used. Junio C Hamano has confirmed the problem is real, and the discussion is now focused on how to dynamically resolve the configured fetch mapping.

Harald Nordgren recently joined the thread, labeling the issue a "hardcoding bug" and raising a key question: whether this bug exists in `master` (requiring a standalone fix) or is confined to an in-flight topic (where it could be addressed as part of that work). His involvement is notable because Junio previously linked this issue to Harald’s work on narrowing default `git fetch` behavior, suggesting shared underlying challenges with refspec resolution. The thread remains conceptual, with no patch proposed yet, but the urgency may increase if the bug is confirmed to affect `master`. Open questions include which refspec API to use for the fix and whether other parts of Git make similar hard-coded assumptions.

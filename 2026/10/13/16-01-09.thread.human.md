This thread is an RFC exploring a potential issue in `git pull`'s handling of custom fetch refspecs during rebase operations. Jyotish Kumar, the author, highlights a problem in `get_tracking_branch()` (in `builtin/pull.c`), where the code assumes a default mapping between local branches and remote-tracking branches (e.g., `refs/heads/main` → `refs/remotes/origin/main`). This assumption breaks when users configure custom fetch refspecs, such as `+refs/heads/*:refs/remotes/origin/custom/*`, which would map `main` to `refs/remotes/origin/custom/main` instead. The concern is that this could cause `get_rebase_fork_point()` to use an incorrect or nonexistent remote-tracking ref, leading to flawed fork-point calculations during `git pull --rebase`.

The discussion is still in the conceptual stage, with the author seeking feedback on whether this is a legitimate issue and whether resolving the configured fetch mapping (rather than hardcoding the default layout) would be the correct approach. The thread touches on a subtle but important edge case in Git’s pull/rebase workflow, particularly for users with non-standard refspec configurations. While no patch or test case has been proposed yet, the analysis is grounded in Git’s remote and refspec APIs, suggesting the author has done some homework on the relevant subsystems.

This is the first patch in a two-part feature series that hardens Git's blame ignore-revs parser and tag-peeling logic before enabling a default ignore file. The patch addresses security concerns that arise when `git blame` and `git annotate` automatically read `.git-blame-ignore-revs` (or `HEAD:.git-blame-ignore-revs` in bare repositories) — a change introduced in the second patch.

The hardening focuses on two critical areas. First, it prevents NUL-byte injection in ignore-revs files by scanning each line for embedded NULs using `memchr()` and rejecting malformed input. This closes a parsing ambiguity where `strbuf_getline()` would read lines containing NULs, but subsequent parsing treated the buffer as NUL-terminated, potentially ignoring trailing garbage or comments. Second, it prevents promisor fetches in partial clones by using `odb_read_object_info_extended()` with `OBJECT_INFO_SKIP_FETCH_OBJECT` and `OBJECT_INFO_QUICK`, ensuring that missing tag targets do not trigger network requests. The tag-peeling logic now verifies each tag’s declared type before parsing and peels tags one layer at a time, rejecting type mismatches.

The patch is well-motivated and clearly scoped. The security rationale is explained in the commit message, and the changes are minimal and focused. Test coverage is thorough, including edge cases like chained tags, missing tag targets, and NUL-byte injection. The hardening is a prerequisite for the default ignore file lookup in the next patch, which will expose the parser to upstream-controlled content at a well-known path. No new user-facing behavior is introduced here — this is purely defensive coding.

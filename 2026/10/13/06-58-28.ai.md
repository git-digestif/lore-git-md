This is a platform compatibility bugfix targeting macOS and other environments where external tools rewrite files with CRLF line endings, causing `git status` to incorrectly report modifications. It is the fourth iteration of a patch series by Curtis Allen Smith addressing a long-standing flaw in Git's index comparison logic: `ie_modified()` in `read-cache.c` has historically treated any size change as conclusive evidence of modification, even when clean filters or CRLF conversion could legitimately alter file size without changing content.

The patch inlines the fix directly into `ie_modified()`, removing the helper function introduced in v3. The core logic remains unchanged: when a file's size changes and conversion is active (`would_convert_to_git()` returns true), Git now falls through to `ce_modified_check_fs()` to verify whether the size change reflects actual modification, rather than trusting the size difference alone. This change adds 4 lines to `read-cache.c` and 45 lines of new tests in `t/t0020-crlf.sh` covering both CRLF rewrites and lone-CR edge cases.

Benchmark data from Curtis shows the performance impact is negligible in most cases: a clean tree pays nothing, and a tree without conversion pays only one attribute lookup per size-changed file. The overhead becomes noticeable only when conversion is active *and* the file is genuinely modified or rewritten (e.g., 25ms → 137ms for 10,000 files). The patch includes a follow-up optimization that reduces this overhead further (to 57ms) by skipping conversion and hashing when the length already rules out a match.

The architectural debate remains unresolved. Johannes Sixt continues to argue the fix should target `git add` (ensuring the index records the correct post-conversion size), while Curtis maintains the fix belongs in `git status` (correcting a false positive in `ie_modified()`'s detection logic). This v4 does not address that objection but refines the implementation and commit message based on Junio's feedback. The patch is now technically clean and ready for review, though its premise may still face pushback.

Key technical details: the fix is unconditional (no configuration switch), preserves existing behavior for non-converted files, and handles edge cases like lone-CR rewrites. The commit message now clearly explains the real-world scenario (external tools rewriting CRLF endings after Git checks out files with LF endings) and the performance trade-offs.

## 2026/10/13

- [2026/10/13/21-24-41 by SZEDER Gábor <szeder.dev@gmail.com>] SZEDER Gábor reproduced the performance regression in the git repository, benchmarking `git log --follow` on `t/valgrind/valgrind.sh` at 8.825s with commit 304812ed33 versus 3.275s with its parent (2.69x slower).
- [2026/10/13/21-24-41 by SZEDER Gábor <szeder.dev@gmail.com>] Trace performance analysis showed 4.45s of the 8.8s total runtime is spent in `propagate_follow_pathspec_to_parent()` when processing second...N-th parents of merge commits.
- [2026/10/13/21-24-41 by SZEDER Gábor <szeder.dev@gmail.com>] He observed that line-level log (`-L1,40`) runs faster than `--follow` even before the regression (1.454s vs 3.260s on the pre-regression commit).
- [2026/10/13/21-24-41 by SZEDER Gábor <szeder.dev@gmail.com>] He hypothesized the cause: `--follow` diffs merge commits against all parents and always checks for renames, while line-level log skips the diff when the path is unmodified versus the first parent and only checks renames when the path is absent.

## 2026/10/15

- [2026/10/15/14-48-43 by Miklos Vajna <vmiklos@collabora.com>] Miklos Vajna submitted a patch adding two shortcuts in `propagate_follow_pathspec_to_parents()` to speed up `git log --follow` on non-linear history: only running expensive rename detection when the path is added relative to a parent, and following the parent's history directly when the path is unchanged; the change reduces the linux.git `rsc_table.h` test case from 6m43s to 29s while keeping t4219-log-follow-merge.sh passing, and he said he would send the patch to Junio later if no problems are seen.
- [2026/10/15/16-57-39 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano observed that `log_tree_commit()` calls `propagate_follow_pathspec_to_parent()` only after `log_tree_diff()` has already flushed its output, so the clue about whether the followed path existed in the parent is already lost, and suggested that `log_tree_diff_flush()` could instead inspect the diff queue while filepairs are still available to decide whether to adjust the followed paths; he also said it might be cleaner to rip out the changes from commit 304812ed33 and rethink the approach rather than pile on more code, though he was not sure ("I dunno").

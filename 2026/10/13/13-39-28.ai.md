This is a bug report for the Linux fsmonitor daemon, identifying a deterministic flaw in how it tracks edits under renamed directories.

The report comes from Erik Cervin-Edin, who demonstrates that when a directory is renamed, the fsmonitor daemon fails to report modifications to files in subdirectories of that renamed directory. The reproduction steps are clear: create a directory with a subdirectory, commit it, rename the parent directory, edit files in both the parent and the subdirectory, and observe that only the parent’s file appears in `git status`. The daemon continues to track the subdirectory under its old path, causing all subsequent edits in that subtree to be missed until the fsmonitor state is invalidated.

Erik traces the root cause to `add_watch()` in `compat/fsmonitor/fsm-listen-linux.c`. When a directory is renamed, inotify watches follow the inode, so subdirectories remain watched. The code attempts to re-register them under their new paths, but `inotify_add_watch()` fails with `EEXIST` because the watch already exists. The function then returns early without updating the descriptor-to-path map, leaving the old path intact. This matches a concern Patrick Steinhardt raised during review of v5 of the Linux listener, which was never addressed in the thread.

The report is thorough: it includes exact reproduction steps, expected vs. actual output, a minimal test case, and a precise technical explanation. The issue is not a race but a deterministic oversight in the watch-update logic. No patch is offered, but the analysis is sufficient for someone familiar with the fsmonitor internals to implement a fix.

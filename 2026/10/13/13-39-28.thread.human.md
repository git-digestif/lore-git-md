This thread is a detailed bug report from Erik Cervin-Edin about a deterministic flaw in Git’s Linux fsmonitor daemon. The issue occurs when a directory is renamed: the daemon fails to track subsequent edits to files in subdirectories of the renamed directory. Erik demonstrates that while inotify watches correctly follow the inode during a rename, the daemon’s internal descriptor-to-path mapping becomes stale because `inotify_add_watch()` fails with `EEXIST` and the code exits early without updating the path. This leaves the daemon tracking the old path, causing all edits in the subtree to be missed until the fsmonitor state is reset.

The report is thorough, including reproduction steps, expected vs. actual behavior, a minimal test case, and a precise technical explanation pinpointing the root cause in `add_watch()` in `compat/fsmonitor/fsm-listen-linux.c`. Erik also notes that this issue aligns with a concern Patrick Steinhardt raised during the review of v5 of the Linux listener, which was never addressed. No patch is provided, but the analysis is clear enough for someone familiar with the fsmonitor internals to implement a fix. The thread is currently a standalone report with no replies or proposed solutions.

This is the first patch in a two-patch feature series introducing a configurable timeout (`core.indexLockTimeout`) for Git’s index lock. The patch implements the core logic in `repository.c`, adds the configuration option to `Documentation/config/core.adoc`, and includes a new test script (`t/t0032-index-lock-timeout.sh`) to verify the behavior.

The patch addresses a real pain point for IDE users: background `git status` calls can block user-initiated commands like `git add` or `git commit` by holding the index lock. Instead of failing immediately, commands now wait up to the configured timeout (default: 1 second) for the lock to become available. The implementation includes a safeguard to skip the wait if the index was already read before locking, minimizing the risk of race conditions. This is a targeted solution that avoids the performance trade-offs of `--no-optional-locks` (which skips the lock entirely but forces re-hashing of files).

Key technical details:
- **New config key**: `core.indexLockTimeout` (integer, milliseconds; 0 = no retry, -1 = indefinite, default = 1000).
- **Behavior**: Commands wait for the lock unless the index was already read (to avoid write races).
- **Files touched**: `repository.c` (core logic), `Documentation/config/core.adoc` (docs), `t/meson.build` (test registration), `t/t0031-lockfile-pid.sh` (test setup), `t/t0032-index-lock-timeout.sh` (new tests), and `t/t7400-submodule-basic.sh` (test adjustment).
- **Test coverage**: The new test script verifies that commands fail immediately with `core.indexLockTimeout=0`, wait with a positive timeout, and skip the wait if the index was read before locking (e.g., `git commit`).

The patch is well-motivated and clearly scoped. The default timeout of 1 second is explicitly marked as open to debate, and the author acknowledges edge cases (e.g., the lock-order change in `git commit` in Patch 2). The implementation appears clean, with adequate test coverage for the core functionality. The only notable loose end is whether additional commands (e.g., `reset`) should eventually support the timeout.

This is the first patch in the v5 series that hardens the ignore-revs parser and tag-peeling logic in `git blame` before enabling the default `.git-blame-ignore-revs` file lookup. The patch addresses security concerns raised during review by preventing two specific attack vectors: embedded NUL bytes in ignore-revs files and unintended promisor fetches in partial clones.

The changes focus on two functions: `oidset_parse_file_carefully()` in `oidset.c` and `peel_to_commit_oid()` in `builtin/blame.c`. The first now scans each line for NUL bytes using `memchr()` and rejects any line containing them, closing a parsing ambiguity where trailing garbage after a valid OID could be silently ignored. The second function now uses `odb_read_object_info_extended()` with `OBJECT_INFO_SKIP_FETCH_OBJECT` and `OBJECT_INFO_QUICK` flags to prevent network requests for missing tag targets in partial clones, and verifies each tag’s declared type before parsing to prevent type confusion. The hardening also enforces a 100MB size cap (inherited from the second patch) to prevent memory exhaustion from maliciously large blobs.

The test coverage is thorough, adding two new test cases: one verifies that lines with embedded NUL bytes are rejected with a clear error message, and another confirms that chained tags are peeled correctly and missing tag targets in partial clones do not trigger promisor fetches. The tests use `test_must_fail` and `test_grep` to validate error handling, and `test_must_be_empty` to ensure no unintended side effects occur when processing malformed input.

This patch is a prerequisite for the second patch in the series, which implements the default file lookup. The hardening is motivated by the upcoming exposure of the ignore-revs parser to upstream-controlled content at a well-known path (`.git-blame-ignore-revs`), aligning with the project’s security practices for similar files like `.mailmap` and `.gitattributes`. The changes are minimal and targeted, touching only the parsing and peeling logic without altering the core blame algorithm or user-facing behavior.

The patch is well-motivated and addresses feedback from prior iterations, including Junio’s emphasis on security hardening before enabling default file lookup. The commit message clearly explains the threat model and the specific vulnerabilities being mitigated, making it easy to assess the necessity of the changes.

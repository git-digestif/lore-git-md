This is the v4 iteration of Phillip Wood’s patch series to make `git checkout -m` recreate conflict markers using the original branch names instead of generic labels. The series is now functionally complete, with all prior feedback addressed, and has been queued for integration in `next`.

The core change teaches Git’s ort merge backend to store the original conflict labels (e.g., branch names) in `.git/MERGE_LABELS` when a merge results in conflicts, so that `git checkout -m` can later reuse those labels. This matches the user’s original experience during the merge. The series also includes a preparatory refactoring of `remove_branch_state()` to use flags instead of a boolean, and a new patch (Junio’s follow-up) that caches merge config settings and conflict labels to optimize performance by eliminating redundant config reads and file I/O.

Key technical details: the series touches `branch.c`, `branch.h`, `builtin/checkout.c`, `merge-ort.c`, and related headers, introducing a new ephemeral file `.git/MERGE_LABELS` (analogous to `MERGE_MSG` or `MERGE_MODE`) and new functions `write_merge_labels()` and `read_merge_labels()`. The implementation handles edge cases (missing or malformed `.git/MERGE_LABELS`) by falling back to generic labels, and ensures cleanup via `git commit` and `git sequencer`. Test coverage in `t/t7201-co.sh` verifies label preservation and absence of `.git/MERGE_LABELS` after clean `git checkout -m <branch>`.

The v4 iteration incorporates Junio’s follow-up refactoring patch as PATCH 2/3, which introduces `struct checkout_merged_data` to cache per-invocation constants (e.g., `merge.renormalize`, conflict style, and `.git/MERGE_LABELS` file state). This patch is a pure performance optimization with no user-visible behavior change. The series also addresses all prior feedback: portability (using `strbuf_getline()` for LF/CRLF handling), API improvements (e.g., `write_merge_labels()` now takes a `const char *labels[3]` array), idiomatic buffer detachment, and style nits.

The open question about whether `git checkout -m` should also remember and restore the original conflict style (e.g., `diff3`) remains unresolved, but this series explicitly excludes that scope. The architectural discussion around using an index extension instead of `.git/MERGE_LABELS` is also unresolved, but Phillip has rejected that approach for this series, citing compatibility with existing patterns (`MERGE_MODE`, `MERGE_RR`, `MERGE_MSG`).

The series is ready for integration, with Junio’s final sign-off confirming it is "nicely done" and queued in `next`. Phillip is a well-regarded contributor with deep expertise in the merge machinery, and the implementation is thorough, with clear commit messages and test coverage. The change is user-facing but non-disruptive, affecting only the appearance of conflict markers. The only remaining uncertainty is the unresolved discussion about conflict style, which does not block this series.

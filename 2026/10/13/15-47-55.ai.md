This is the final patch (3/3) in Phillip Wood’s v4 series to make `git checkout -m` remember and reuse the original conflict labels from the initial merge. The patch is functionally complete, well-tested, and ready for integration.

The patch teaches Git’s ort merge backend to write the original conflict labels (e.g., branch names) to `.git/MERGE_LABELS` whenever a merge results in conflicts. When `git checkout -m` later recreates those conflicts, it reads the labels from that file instead of using generic "base/ours/theirs" labels. This ensures the user sees the same branch names in conflict markers that they originally saw during the merge, improving consistency and usability.

Key technical details: the patch introduces `write_merge_labels()` and `read_merge_labels()` functions that handle the new `.git/MERGE_LABELS` file (an ephemeral file analogous to `MERGE_MSG` or `MERGE_MODE`). It also extends `remove_branch_state()` with a new flag `REMOVE_BRANCH_STATE_PRESERVE_CONFLICT_LABELS` to prevent `.git/MERGE_LABELS` from being deleted when `git checkout -m <branch>` is run, ensuring the labels remain available for subsequent `git checkout -m <path>` invocations. The implementation handles edge cases (missing or malformed `.git/MERGE_LABELS`) by falling back to generic labels, and ensures cleanup via `git commit` and `git sequencer`. The patch also caches the labels in `struct checkout_merged_data` to avoid repeated file I/O, aligning with the performance optimizations introduced in the earlier patches of this series.

Test coverage in `t/t7201-co.sh` verifies that the labels are preserved and that `.git/MERGE_LABELS` is removed after a clean `git checkout -m <branch>`. The patch touches `merge-ort.c`, `branch.c`, `builtin/checkout.c`, and related headers, and is fully backward-compatible with existing workflows. All prior feedback from Junio on v2 and v3 has been addressed, including portability (using `strbuf_getline()` for LF/CRLF handling), API improvements, and style nits.

This patch is the culmination of the series and is the only one that introduces user-visible behavior changes. The implementation is thorough, with clear commit messages and robust edge-case handling. The series as a whole is queued in `next` and on track for graduation to `master`.

This is a follow-up in the ongoing discussion about extending `git branch --delete-merged` to detect squash-merged and rebase-merged branches. Junio C Hamano steps back to reconsider the fundamental goal of the feature, proposing a shift in direction that could reshape the entire series.

Junio now questions whether `--delete-merged` should handle rebased or squash-merged branches at all. He distinguishes two use cases: (1) identifying which of *your* pending branches have landed upstream (a strict subset), and (2) identifying which of your branches are *no longer relevant* because upstream has integrated similar changes from others (a broader, more subjective problem). The current series attempts to address the latter, but Junio suggests this may be the wrong approach. Instead, he proposes keeping `--delete-merged` strictly for the first use case—deleting branches whose *exact* commits have been merged—while introducing a new, separate option (e.g., `--delete-irrelevant`) for the broader problem of detecting branches whose changes are no longer needed.

This reframing has significant implications. If adopted, it would mean the current series (which adds rebase and squash detection to `--delete-merged`) is solving the wrong problem. Junio’s proposal would require a new CLI design, likely with a more granular approach (e.g., `--delete-irrelevant=rebased,squashed,cherry-picked`) to handle the various ways changes can become irrelevant. The current `--no-squashed` flag would no longer make sense in this model, and the performance optimizations in the series (batching, blob fetching) might need to be rethought for the new command.

The email does not resolve whether the series should proceed as-is or pivot to Junio’s proposed `--delete-irrelevant`. It also leaves open how the new command would handle edge cases like partial relevance (e.g., a branch where only some commits are superseded) or mixed workflows (e.g., a branch with both merged and rebased commits). Harald Nordgren’s earlier agreement to explore `git range-diff`’s commit-matching logic may still be relevant, but the broader architectural question now takes precedence. The thread is at a crossroads: the next iteration could either refine the current approach or abandon it in favor of a more ambitious redesign.

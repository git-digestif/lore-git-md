Subject: Severe performance regression in `git log --follow` (bisected to 304813ed33)
Series version: N/A (bug report, not a patch series)
Originating author: Patrick Steinhardt (forwarding a user report)
Thread type: bug report

Core problem or goal
A user-visible performance regression in `git log --stat --follow` when tracing file history in the Linux kernel repository: the command slowed from 33 seconds in Git 2.55 to nearly 8 minutes in Git 2.56. The regression is bisected to commit 304813ed33 (“log: improve --follow following renames for non-linear history”, 2026-06-22).

Current status
Under investigation; no fix posted yet. The regression is confirmed by SZEDER Gábor’s benchmarks, which show a 14× slowdown in the Linux kernel repository and a 2.7× slowdown in the Git repository itself. The bottleneck is identified as the new `propagate_follow_pathspec_to_parent()` logic in 304813ed33, which exhibits quadratic or worse behavior when processing merge commits with many parents.

Key technical details
- Command: `git log --stat --follow <file>`
- Repository: Linux kernel (primary test case) and Git repository (secondary benchmark)
- Regression commit: 304813ed33 (“log: improve --follow following renames for non-linear history”)
- Subsystem: revision-walking / rename detection
- Bottleneck function: `propagate_follow_pathspec_to_parent()`
- Performance characteristics: 4.4 seconds spent comparing a merge commit with its *non-first* parents versus 1.4 seconds for the first parent
- No new or renamed symbols; no on-disk format change; no test coverage yet
- Contrast with `git log -L`: line-level history remains significantly faster, as it skips diffing against non-first parents if the file is unchanged in the first-parent history, while `--follow` always diffs against every parent

Open questions and loose ends
- Root cause of the slowdown (whether the algorithm’s quadratic behavior is inherent to the design or an implementation detail)
- Whether the regression affects `--follow` more broadly (beyond `--stat`) or is specific to certain flags
- Whether the regression is repository-specific (e.g., exacerbated by repositories with many merge commits) or general
- What trade-offs the original commit made (correctness vs. performance) and whether a revert or partial revert is viable
- Whether the fix should adopt the `git log -L` strategy of skipping non-first parents when the file is unchanged

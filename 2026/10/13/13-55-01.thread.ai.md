Subject: Severe performance regression in `git log --follow` (bisected to 304813ed33)

Originating author: Patrick Steinhardt (forwarding a user report)
Thread type: bug report, fix proposal, and architectural review

Core problem or goal
A user-visible performance regression in `git log --stat --follow` when tracing file history in repositories with complex merge structures: the command slowed from 33 seconds in Git 2.55 to nearly 8 minutes in Git 2.56. The regression was bisected to commit 304813ed33 (“log: improve --follow following renames for non-linear history”, 2026-06-22), which aimed to fix a long-standing limitation in `--follow`’s ability to track renames across non-linear history. The goal is to restore near-original performance while preserving the corrected rename-following behavior.

Current status
A **bugfix patch** authored by Miklos Vajna proposes two optimizations to `propagate_follow_pathspec_to_parent()`. The patch reduces the runtime of `git log --stat --follow include/linux/rsc_table.h` in the Linux kernel repository from 6m43s to 29s—almost matching the pre-regression time of 28s—while maintaining all existing test cases in `t4211-log-follow-merge.sh`. The patch is under **active design review**; Junio C Hamano has proposed an alternative architectural approach that would move the optimization logic into `log_tree_diff_flush()` rather than layering it on top of the existing diff machinery. Junio’s latest review identifies a **potential correctness issue** in the patch’s optimization logic, using a concrete merge scenario to illustrate how the patch might break rename-following in cases where the file is *semantically* renamed but *syntactically* unchanged in one parent. No integration status is reported; the series remains under review.

Key technical details
- Command: `git log --stat --follow <file>`
- Repository: Linux kernel (primary test case) and Git repository (secondary benchmark)
- Regression commit: 304813ed33 (“log: improve --follow following renames for non-linear history”)
- Subsystem: revision-walking / rename detection
- Bottleneck function: `propagate_follow_pathspec_to_parent()` (optimized in the patch; Junio suggests relocating the fix to `log_tree_diff_flush()`)
- New helper: `get_follow_path_change()` classifies path differences (unchanged, added, or other)
- Optimization logic: (1) only perform rename detection when the path is *added* relative to a parent, and (2) if the path is unchanged in any parent, follow that parent’s history without further diffing
- Junio’s proposed alternative: integrate the optimization into `log_tree_diff_flush()` while the diff queue is still available, avoiding redundant diff passes entirely
- Junio’s correctness concern: the patch’s `has_same` flag may incorrectly classify a path as "unchanged" in a merge commit when the path exists in both parents but was *semantically* renamed in one parent (e.g., F→G in parent B, but F is kept in the merge). This would cause the optimization to skip rename detection for parent B, breaking `--follow`’s ability to trace the file’s history through the rename
- Files touched: `log-tree.c` only; no on-disk format changes; no new public symbols
- Performance characteristics: quadratic scaling with merge commit arity is eliminated by avoiding redundant diffs; contrast with `git log -L` remains (line-level history still faster due to skipping non-first parents when the file is unchanged)
- Test coverage: unchanged in `t4211-log-follow-merge.sh`; the scenario raised by Junio is not currently covered

Open questions and loose ends
- Whether the optimizations fully preserve the correctness fixes introduced by 304813ed33 (Miklos asserts they do, but review is pending)
- Whether the patch’s classification logic (`enum follow_path_change`) is robust across edge cases (e.g., partial renames, mode changes, symlinks, or the semantic-vs-syntactic sameness issue raised by Junio)
- Whether the regression affects `--follow` more broadly (beyond `--stat`) or is specific to certain flags
- Whether the optimizations are sufficient for repositories with even more complex merge structures than the Linux kernel
- Whether further architectural changes (e.g., adopting Junio’s proposed relocation of the optimization logic) are needed or desirable
- Whether the original fix (304813ed33) should be reconsidered at a fundamental level, as Junio’s review suggests
- How to handle the merge scenario described by Junio: whether to adjust the patch to detect semantic renames, or to argue that the scenario is outside `--follow`’s intended scope

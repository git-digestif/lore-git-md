Subject: Severe performance regression in `git log --follow` (bisected to 304813ed33)

Thread type: bug report and fix proposal

Core problem or goal
A user-visible performance regression in `git log --stat --follow` when tracing file history in repositories with complex merge structures: the command slowed from 33 seconds in Git 2.55 to nearly 8 minutes in Git 2.56. The regression was bisected to commit 304813ed33 (“log: improve --follow following renames for non-linear history”, 2026-06-22), which aimed to fix a long-standing limitation in `--follow`’s ability to track renames across non-linear history. The goal is now to restore near-original performance while preserving the corrected rename-following behavior.

Current status
A **bugfix patch** authored by Miklos Vajna has been posted, proposing two optimizations to `propagate_follow_pathspec_to_parent()`. The patch reduces the runtime of `git log --stat --follow include/linux/rsc_table.h` in the Linux kernel repository from 6m43s to 29s—almost matching the pre-regression time of 28s—while maintaining all existing test cases in `t4211-log-follow-merge.sh`. The patch is under review; no integration status is yet reported.

Key technical details
- Command: `git log --stat --follow <file>`
- Repository: Linux kernel (primary test case) and Git repository (secondary benchmark)
- Regression commit: 304813ed33 (“log: improve --follow following renames for non-linear history”)
- Subsystem: revision-walking / rename detection
- Bottleneck function: `propagate_follow_pathspec_to_parent()` (now optimized)
- New helper: `get_follow_path_change()` classifies path differences (unchanged, added, or other)
- Optimization logic: (1) only perform rename detection when the path is *added* relative to a parent, and (2) if the path is unchanged in any parent, follow that parent’s history without further diffing
- Files touched: `log-tree.c` only; no on-disk format changes; no new public symbols
- Performance characteristics: quadratic scaling with merge commit arity is eliminated by avoiding redundant diffs; contrast with `git log -L` remains (line-level history still faster due to skipping non-first parents when the file is unchanged)
- Test coverage: unchanged in `t4211-log-follow-merge.sh`

Open questions and loose ends
- Whether the optimizations fully preserve the correctness fixes introduced by 304813ed33 (Miklos asserts they do, but review is pending)
- Whether the patch’s classification logic (`enum follow_path_change`) is robust across edge cases (e.g., partial renames, mode changes, or symlinks)
- Whether the regression affects `--follow` more broadly (beyond `--stat`) or is specific to certain flags
- Whether the optimizations are sufficient for repositories with even more complex merge structures than the Linux kernel
- Whether further optimizations (e.g., adopting `git log -L`’s strategy of skipping non-first parents entirely) are needed or desirable

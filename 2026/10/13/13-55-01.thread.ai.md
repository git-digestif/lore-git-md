Subject: Severe performance regression in `git log --follow` (bisected to 304813ed33)
Series version: N/A (bug report, not a patch series)
Originating author: Patrick Steinhardt (forwarding a user report)
Thread type: bug report

Core problem or goal
A user-visible performance regression in `git log --stat --follow` when tracing file history in repositories with complex merge structures: the command slowed from 33 seconds in Git 2.55 to nearly 8 minutes in Git 2.56. The regression is bisected to commit 304813ed33 (“log: improve --follow following renames for non-linear history”, 2026-06-22), which aimed to fix a long-standing limitation in `--follow`’s ability to track renames across non-linear history.

Current status
Under investigation; no fix posted yet. The regression is confirmed by SZEDER Gábor’s benchmarks (14× slowdown in the Linux kernel repository, 2.7× in the Git repository). The bottleneck is identified as the new `propagate_follow_pathspec_to_parent()` logic in 304813ed33, which exhibits quadratic or worse behavior when processing merge commits with many parents. Miklos Vajna, the original author of 304813ed33, acknowledges the regression but frames it as a deliberate trade-off for correctness, proposing that optimizations should preserve the new rename-following behavior while mitigating the slowdown.

Key technical details
- Command: `git log --stat --follow <file>`
- Repository: Linux kernel (primary test case) and Git repository (secondary benchmark)
- Regression commit: 304813ed33 (“log: improve --follow following renames for non-linear history”)
- Subsystem: revision-walking / rename detection
- Bottleneck function: `propagate_follow_pathspec_to_parent()`
- Performance characteristics: 4.4 seconds spent comparing a merge commit with its *non-first* parents versus 1.4 seconds for the first parent; quadratic or worse scaling with merge commit arity
- Design goal of 304813ed33: store and restore the followed path during non-linear traversal to enable rename tracking across merge commits
- No new or renamed symbols; no on-disk format change; no test coverage yet
- Contrast with `git log -L`: line-level history remains significantly faster, as it skips diffing against non-first parents if the file is unchanged in the first-parent history, while `--follow` always diffs against every parent

Open questions and loose ends
- Whether the algorithm’s quadratic behavior is inherent to the design (requiring a redesign) or an implementation detail (amenable to optimization)
- Whether the regression affects `--follow` more broadly (beyond `--stat`) or is specific to certain flags
- Whether the regression is repository-specific (e.g., exacerbated by repositories with many merge commits) or general
- What trade-offs are acceptable: revert the correctness fix, accept the performance regression, or find a middle ground (e.g., adopt `git log -L`’s strategy of skipping non-first parents when the file is unchanged)
- Concrete optimization strategies for `propagate_follow_pathspec_to_parent()` that preserve the new rename-following behavior

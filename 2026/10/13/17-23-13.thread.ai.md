Thread identity
Subject: [PATCH 0/2] configurable index lock timeout for IDE workflows
Series version: v2 (4 patches)
Originating author: Jun Wu
Thread type: patch series

Core problem or goal
Add a configurable timeout (`core.indexLockTimeout`, default 1 second) for Git’s index lock to reduce contention between background IDE `git status` calls and user-initiated commands (`add`, `commit`, etc.). The series lets commands wait briefly for the lock instead of failing immediately, while avoiding race conditions by skipping the wait if the index was already read before locking. The lock-order changes in `git commit` (Patch 3) and `git reset` (Patch 4) fix **pre-existing write-race conditions** (present for 20+ years) where these commands could silently discard concurrent index updates (e.g., from `git add`) if they read the index before acquiring the lock. Jun Wu clarifies that the race-avoidance rule ("skip wait if index read before locking") applies **per-process**: within any Git command, if the in-core index (`repo->index->initialized`) was already read before attempting to lock, the command behaves as if `core.indexLockTimeout=0` (no wait), regardless of what other processes (e.g., background `git status`) have done. The lock infrastructure now **force-drops outdated in-memory indexes** once the lock is acquired, addressing Junio’s concern about stale data when the index was read but the lock is held or the index updated by another process. The read/lock order issue is confirmed to affect multiple commands (`reset`, `rebase`, `stash`, `am`, `merge`), and the series adopts a phased approach: land the timeout feature first (Patch 2 does not worsen existing races, as the timeout is disabled for commands that read the index before locking), then incrementally fix the order issues starting with the simplest or most common cases (`commit`, `reset`).

The **second patch** implements the core timeout logic, adds the `core.indexLockTimeout` configuration knob, and provides test coverage. The **fourth patch** fixes the same race in `git reset` (except `--soft`) by moving `repo_hold_locked_index()` to the start of the command, matching the approach in Patch 3. The commit message for Patch 4 explicitly frames the change as a correctness fix, addressing Peff’s feedback. Key technical details
- **Files touched**: `repository.c` (core timeout logic), `repository.h` (API documentation), `Documentation/config/core.adoc` (config docs), `t/meson.build` (test registration), `t/t0031-lockfile-pid.sh` (test setup), `t/t0032-index-lock-timeout.sh` (new test script), `t/t7400-submodule-basic.sh` (test adjustment), `builtin/commit.c` (Patch 3 lock-order fix), `builtin/reset.c` (Patch 4 lock-order fix).
- **New config key**: `core.indexLockTimeout` (integer, milliseconds; 0 = no retry, -1 = indefinite, default = 1000).
- **Behavior**: Commands wait up to the timeout for the lock unless the index was already read **by the same process** (to avoid write races). If the lock is acquired but the in-memory index is outdated (e.g., updated by another process), the infrastructure **force-drops the stale index**, ensuring the command re-reads the latest data. The lock-order changes in `git commit` (Patch 3) and `git reset` (Patch 4) fix pre-existing races where concurrent updates (e.g., `git add`) could be silently discarded. Both patches move `repo_hold_locked_index()` to the start of their respective commands, removing redundant lock acquisitions. `git reset` uses `repo_read_index()` (not `repo_read_index_preload()`), so the change does not introduce additional work (e.g., `lstat()` calls) while holding the lock.
- **Commands supporting timeout**: `add`, `rm`, `mv`, `checkout`, `restore`, `read-tree`, `apply`, `update-index`, `commit` (Patch 3), `reset` (Patch 4).
- **Commands *not* supporting timeout**: `rebase`, `merge`, `stash`, `cherry-pick`, `am` (these read the index before locking and thus skip the timeout per the race-avoidance rule).
- **New symbols**: `repo_try_hold_locked_index()` (internal API extension; no new public symbols).
- **On-disk format**: unchanged.
- **Test coverage**: new script `t/t0032-index-lock-timeout.sh` verifies timeout behavior (immediate failure with 0, wait with positive timeout, skip wait if index read before locking); updated to reflect `git commit` and `git reset` now waiting for the lock. Peff’s instrumentation (`sleep(5)`) demonstrates the pre-existing race in both commands. The refactoring in Patch 1 is exercised by existing tests with no new coverage added.

Open questions and loose ends
- **Default timeout value** (1 second) remains open to debate; Jun Wu is open to adjusting it (e.g., to 10 minutes to match Mercurial) but no consensus has emerged.
- Whether additional commands (e.g., `rebase`) should eventually support the timeout or have their lock-order issues fixed.
- **Configurability vs. simplicity**: The debate remains unresolved. Knoble prefers root-cause fixes (e.g., improving `git status` retention or IDE communication) over adding another setting, while Jun Wu defends the configurability as pragmatic, citing Mercurial/Sapling’s 10-minute timeout precedent and noting that alternatives (faster `status`, lock-free writes, fsmonitor-style notifications) each have limitations. D. Ben Knoble’s latest email signals unease about the trade-off between command success rate and responsiveness, noting that users may notice hang-ups in commands that are normally fast, but defers to the judgment of Junio and Peff.
- **Alternatives considered**: Jun Wu outlines three alternatives suggested by Knoble:
  1. Faster `git status` — does not eliminate lock contention.
  2. Lock-free writes — would require major format changes.
  3. Fsmonitor-style notifications — does not address the root issue of lock conflicts.
- **Race window amplification**: Peff notes that the timeout could make existing race windows (e.g., in `git add`) more likely, though he does not oppose the series.
- **IDE coordination**: Knoble suggests Vim’s fugitive plugin as a model for avoiding `--no-optional-locks` by limiting background refreshes to specific events and caching results. This approach is not widely adopted by other IDEs.
- **Phased approach**: Jun Wu proposes landing the timeout feature first (Patch 2 does not worsen existing races) and then incrementally fixing lock-order issues in other commands. This strategy is open to debate—whether the timeout should wait for a full audit of lock-order issues or proceed independently.

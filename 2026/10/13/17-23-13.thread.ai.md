Subject: [PATCH 0/2] configurable index lock timeout for IDE workflows
Series version: v2 (4 patches) + complementary 2-patch series from Mihai Cosma
Originating author: Jun Wu
Thread type: patch series

Core problem or goal
Add a configurable timeout (`core.indexLockTimeout`, default 1 second) for Git’s index lock to reduce contention between background IDE `git status` calls and user-initiated commands (`add`, `commit`, etc.). The series lets commands wait briefly for the lock instead of failing immediately, while avoiding race conditions by skipping the wait if the index was already read before locking. The lock-order changes in `git commit` (Patch 3) and `git reset` (Patch 4) fix **pre-existing write-race conditions** (present for 20+ years) where these commands could silently discard concurrent index updates (e.g., from `git add`) if they read the index before acquiring the lock. Jun Wu clarifies that the race-avoidance rule ("skip wait if index read before locking") applies **per-process**: within any Git command, if the in-core index (`repo->index->initialized`) was already read before attempting to lock, the command behaves as if `core.indexLockTimeout=0` (no wait), regardless of what other processes (e.g., background `git status`) have done. The lock infrastructure now **force-drops outdated in-memory indexes** once the lock is acquired, addressing Junio’s concern about stale data when the index was read but the lock is held or the index updated by another process. The read/lock order issue is confirmed to affect multiple commands (`reset`, `rebase`, `stash`, `am`, `merge`), and the series adopts a phased approach: land the timeout feature first (Patch 2 does not worsen existing races, as the timeout is disabled for commands that read the index before locking), then incrementally fix the order issues starting with the simplest or most common cases (`commit`, `reset`).

Mihai Cosma proposes an alternative (or complementary) approach: modifying `git status` to **acquire the index lock only when it needs to write** (e.g., for untracked cache updates), rather than holding it for the entire duration of the command. This **root-cause fix** reduces lock contention at the source, aligning with D. Ben Knoble’s preference for eliminating the problem rather than adding a timeout knob. Mihai reports a **6× speedup** in `git add` latency (from 1020 ms to 160 ms) in a gcc checkout with background `status` loops, demonstrating that his change significantly mitigates the same IDE workflow problem. His two-patch series also fixes a latent bug in `repo_update_index_if_able()` that affects read-then-lock callers (e.g., `rebase`, `merge`) left untouched by Jun Wu’s series. The two approaches **conflict only trivially** (a single lock-call rename in `cmd_status()`), so they could be merged in either order or combined.

Key technical details
- **Files touched by Jun Wu’s series**: `repository.c` (core timeout logic), `repository.h` (API documentation), `Documentation/config/core.adoc` (config docs), `t/meson.build` (test registration), `t/t0031-lockfile-pid.sh` (test setup), `t/t0032-index-lock-timeout.sh` (new test script), `t/t7400-submodule-basic.sh` (test adjustment), `builtin/commit.c` (Patch 3 lock-order fix), `builtin/reset.c` (Patch 4 lock-order fix).
- **New config key**: `core.indexLockTimeout` (integer, milliseconds; 0 = no retry, -1 = indefinite, default = 1000).
- **Behavior**: Commands wait up to the timeout for the lock unless the index was already read **by the same process** (to avoid write races). If the lock is acquired but the in-memory index is outdated (e.g., updated by another process), the infrastructure **force-drops the stale index**, ensuring the command re-reads the latest data. The lock-order changes in `git commit` (Patch 3) and `git reset` (Patch 4) fix pre-existing races where concurrent updates (e.g., from `git add`) could be silently discarded. Both patches move `repo_hold_locked_index()` to the start of their respective commands, removing redundant lock acquisitions. `git reset` uses `repo_read_index()` (not `repo_read_index_preload()`), so the change does not introduce additional work (e.g., `lstat()` calls) while holding the lock.
- **Commands supporting timeout**: `add`, `rm`, `mv`, `checkout`, `restore`, `read-tree`, `apply`, `update-index`, `commit` (Patch 3), `reset` (Patch 4).
- **Commands *not* supporting timeout**: `rebase`, `merge`, `stash`, `cherry-pick`, `am` (these read the index before locking and thus skip the timeout per the race-avoidance rule).
- **New symbols**: `repo_try_hold_locked_index()` (internal API extension; no new public symbols).
- **On-disk format**: unchanged.
- **Test coverage**: new script `t/t0032-index-lock-timeout.sh` verifies timeout behavior (immediate failure with 0, wait with positive timeout, skip wait if index read before locking); updated to reflect `git commit` and `git reset` now waiting for the lock. Peff’s instrumentation (`sleep(5)`) demonstrates the pre-existing race in both commands. The refactoring in Patch 1 is exercised by existing tests with no new coverage added.

- **Files touched by Mihai’s series**: `builtin/commit.c` (trivial conflict resolution), `read-cache.c` (latent bug fix in `repo_update_index_if_able()`), `wt-status.c` (defer lock acquisition until write time in `git status`).
- **Behavior change**: `git status` now acquires the index lock only when it needs to write (e.g., for untracked cache updates), avoiding the lock entirely for read-only operations. This reduces lock contention with other commands (e.g., `git add`) and eliminates the need for a timeout in many cases. The latent bug fix in `repo_update_index_if_able()` ensures that read-then-lock callers (e.g., `rebase`, `merge`) do not corrupt the index if another process updates it between the read and lock.
- **Performance impact**: Mihai reports a **6× speedup** in `git add` latency (from 1020 ms to 160 ms) in a gcc checkout with background `status` loops, demonstrating the effectiveness of his approach in mitigating the same IDE workflow problem.
- **Compatibility**: Mihai’s series is **compatible with Jun Wu’s timeout feature**; the two could be merged in either order or combined, as they conflict only trivially (a single lock-call rename in `cmd_status()`).

Open questions and loose ends
- **Default timeout value** (1 second) remains open to debate; Jun Wu is open to adjusting it (e.g., to 10 minutes to match Mercurial) but no consensus has emerged. Mihai’s data suggests that his approach may reduce the need for a long timeout, but the two approaches could coexist.
- Whether additional commands (e.g., `rebase`) should eventually support the timeout or have their lock-order issues fixed. Mihai’s latent bug fix in `repo_update_index_if_able()` affects these commands, but his series does not address their lock-order issues directly.
- **Configurability vs. simplicity**: The debate remains unresolved. D. Ben Knoble prefers root-cause fixes (e.g., Mihai’s approach) over adding another setting, while Jun Wu defends the configurability as pragmatic, citing Mercurial/Sapling’s 10-minute timeout precedent and noting that alternatives (faster `status`, lock-free writes, fsmonitor-style notifications) each have limitations. Mihai’s empirical evidence provides a new data point for this discussion, but the trade-off between command success rate and responsiveness (e.g., potential hang-ups in normally fast commands) remains a concern.
- **Alternatives considered**: Jun Wu outlines three alternatives suggested by Knoble:
  1. Faster `git status` — does not eliminate lock contention.
  2. Lock-free writes — would require major format changes.
  3. Fsmonitor-style notifications — does not address the root issue of lock conflicts.
  Mihai’s approach (deferring lock acquisition in `git status` until write time) is a fourth alternative that directly reduces lock contention without requiring new configuration or format changes.
- **Race window amplification**: Peff notes that the timeout could make existing race windows (e.g., in `git add`) more likely, though he does not oppose the series. Mihai’s approach does not introduce this risk, as it reduces the duration of lock holds rather than extending them.
- **IDE coordination**: Knoble suggests Vim’s fugitive plugin as a model for avoiding `--no-optional-locks` by limiting background refreshes to specific events and caching results. Mihai’s approach achieves a similar effect by reducing the lock hold time in `git status`, making it more compatible with other IDEs without requiring explicit coordination.
- **Phased approach**: Jun Wu proposes landing the timeout feature first (Patch 2 does not worsen existing races) and then incrementally fixing lock-order issues in other commands. This strategy is open to debate—whether the timeout should wait for a full audit of lock-order issues or proceed independently. Mihai’s series provides an alternative path: land his root-cause fix first, then decide whether the timeout is still needed.

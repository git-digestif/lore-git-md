Subject: [PATCH 0/2] configurable index lock timeout for IDE workflows
Series version: v1 (initial)
Originating author: Jun Wu
Thread type: patch series

Core problem or goal
Add a configurable timeout (`core.indexLockTimeout`, default 1 second) for Git’s index lock to reduce contention between background IDE `git status` calls and user-initiated commands (`add`, `commit`, etc.). The series lets commands wait briefly for the lock instead of failing immediately, while avoiding race conditions by skipping the wait if the index was already read before locking.

Key technical details
- **Files touched**: `repository.c` (core logic), `builtin/commit.c` (lock order change), `Documentation/config/core.adoc` (config docs), `t/meson.build` (test registration), `t/t0031-lockfile-pid.sh` (test setup), `t/t0032-index-lock-timeout.sh` (new test script), `t/t7400-submodule-basic.sh` (test adjustment).
- **New config key**: `core.indexLockTimeout` (integer, milliseconds; 0 = no retry, -1 = indefinite, default = 1000).
- **Behavior**: Commands wait up to the timeout for the lock unless the index was already read (to avoid write races). If the index was read but the lock is held or the index updated by another process, the command fails immediately.
- **Commands supporting timeout**: `add`, `rm`, `mv`, `checkout`, `restore`, `read-tree`, `apply`, `update-index`, `commit`.
- **Commands *not* supporting timeout**: `reset`, `stash`, `merge`, `rebase`, `cherry-pick`, `am`.
- **New symbols**: none (internal lockfile API extended).
- **On-disk format**: unchanged.
- **Test coverage**: new script `t/t0032-index-lock-timeout.sh` verifies timeout behavior (immediate failure with 0, wait with positive timeout, skip wait if index read before locking); existing lockfile and submodule tests updated for compatibility. Patch 2 updates the test to reflect that `git commit` now waits for the lock.
- **Performance rationale**: `--no-optional-locks` forces `git status` to re-hash file contents (not just refresh stat info) when the index lock is unavailable, causing persistent slowdowns if users don’t run index-writing commands to recover. Real-world examples from Sapling (Facebook’s Git fork) show multi-minute slowdowns due to stale stat info and 40% checkout failure rates from lock contention.

Open questions and loose ends
- **Race-avoidance logic**: Junio C Hamano requests clarification on three edge cases:
  1. What *should* happen when a command detects the index was already read but finds the lock held or the index updated by another process — is immediate failure the intended behavior, or should the command re-read the index?
  2. Are there read-only operations that take the lock purely for consistency, and how would the timeout logic interact with them?
  3. Does `repo->index->initialized` reliably indicate a prior read, or could it also be set when creating a new in-core index (e.g., during a fresh checkout), which would incorrectly disable the timeout?
- Default timeout value (1 second) remains open to debate.
- Whether the lock-order change in `git commit` (lock before read) could introduce new edge cases.
- Whether additional commands (e.g., `reset`) should eventually support the timeout.
- **Configurability vs. simplicity**: D. Ben Knoble argues the new `core.indexLockTimeout` config knob is user-hostile and opaque, preferring root-cause fixes (e.g., improving `git status` retention or IDE communication) over adding another setting. Jun Wu defends the configurability as pragmatic, citing Mercurial/Sapling’s 10-minute timeout precedent and noting that alternatives (faster `status`, lock-free writes, fsmonitor-style notifications) each have limitations. The debate over the long-term solution remains unresolved.
- **Alternatives considered**: Jun Wu outlines three alternatives suggested by Knoble:
  1. Faster `git status` — does not eliminate lock contention.
  2. Lock-free writes — would require major format changes.
  3. Fsmonitor-style notifications — does not address the root issue of lock conflicts.

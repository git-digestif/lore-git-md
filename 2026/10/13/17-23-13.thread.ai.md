Subject: [PATCH 0/2] configurable index lock timeout for IDE workflows
Series version: v1 (initial)
Originating author: Jun Wu
Thread type: patch series

Core problem or goal
Add a configurable timeout (`core.indexLockTimeout`, default 1 second) for Git’s index lock to reduce contention between background IDE `git status` calls and user-initiated commands (`add`, `commit`, etc.). The series lets commands wait briefly for the lock instead of failing immediately, while avoiding race conditions by skipping the wait if the index was already read before locking.

Current status
Under review; no prior versions. Patch 1 implements the timeout mechanism and configuration; Patch 2 adjusts `git commit` to lock the index before reading it, ensuring the timeout applies. Junio C Hamano has requested cover-letter revisions to clarify the problem statement, proposed solution, and race-avoidance logic before the series can progress. No merge status reported.

Key technical details
- **Files touched**: `repository.c` (core logic), `builtin/commit.c` (lock order change), `Documentation/config/core.adoc` (config docs), `t/meson.build` (test registration), `t/t0031-lockfile-pid.sh` (test setup), `t/t0032-index-lock-timeout.sh` (new test script), `t/t7400-submodule-basic.sh` (test adjustment).
- **New config key**: `core.indexLockTimeout` (integer, milliseconds; 0 = no retry, -1 = indefinite, default = 1000).
- **Behavior**: Commands wait up to the timeout for the lock unless the index was already read (to avoid write races).
- **Commands supporting timeout**: `add`, `rm`, `mv`, `checkout`, `restore`, `read-tree`, `apply`, `update-index`, `commit`.
- **Commands *not* supporting timeout**: `reset`, `stash`, `merge`, `rebase`, `cherry-pick`, `am`.
- **New symbols**: none (internal lockfile API extended).
- **On-disk format**: unchanged.
- **Test coverage**: new script `t/t0032-index-lock-timeout.sh` verifies timeout behavior (immediate failure with 0, wait with positive timeout, skip wait if index read before locking); existing lockfile and submodule tests updated for compatibility. Patch 2 updates the test to reflect that `git commit` now waits for the lock.

Open questions and loose ends
- Default timeout value (1 second) is explicitly marked as open to debate.
- Whether the lock-order change in `git commit` (lock before read) could introduce new edge cases.
- Whether additional commands (e.g., `reset`) should eventually support the timeout.
- **Performance rationale for `--no-optional-locks`**: D. Ben Knoble questions the claim that skipping the index lock forces `git status` to re-hash files, noting only newly refreshed stat info is lost, not the entire cached index. The underlying slowdown mechanism remains unclear.
- **Configurability vs. simplicity**: Knoble argues the new `core.indexLockTimeout` config knob is user-hostile and opaque, preferring root-cause fixes (e.g., improving `git status` retention or IDE communication) over adding another setting.
- **Cover-letter clarity**: Junio C Hamano requests explicit problem/solution statements and unambiguous description of the race-avoidance logic (which process reads/locks and when).

This is the second patch in Phillip Wood’s three-part series to make `git checkout -m` remember the original conflict labels from a merge. Specifically, this patch is Junio’s follow-up refactoring that optimizes performance by caching merge-related config settings.

The patch introduces a new `struct checkout_merged_data` that holds the conflict style and `merge.renormalize` setting. Instead of reading these values from config for every unmerged path, the code now reads them once at the start of `checkout_worktree()` and reuses the cached values. This is a pure refactoring with no user-visible behavior change, but it prepares the ground for the next patch, which will add file I/O to read the original conflict labels from `.git/MERGE_LABELS`. Without this caching, that file would be read repeatedly for every unmerged path, which would be inefficient.

The change is confined to `builtin/checkout.c` and is straightforward: the new struct is initialized once, the config lookup happens in a helper function (`checkout_merged_prepare()`), and the cached values are passed down to `checkout_merged()`. The patch is small (22 insertions, 6 deletions) and idiomatic, using the same patterns seen elsewhere in the codebase for caching per-invocation state.

Junio originally sent this as a separate “1.5/2” patch in v3; Phillip has incorporated it verbatim as PATCH 2/3 in v4. Junio’s sign-off confirms it is ready for integration, and the series as a whole is queued in `next`. The patch is well-motivated, uncontroversial, and a sensible optimization.

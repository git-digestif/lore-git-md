## 2026/10/14

- [2026/10/14/02-38-06 by Jun Wu <quark.zju@gmail.com>] Jun Wu explained to D. Ben Knoble why `--no-optional-locks status` slows over time: a file's stat info can become outdated without content change, so status loses the stat fast path and falls back to slow content checks, recovering only if a command like `add` rewrites the index; he cited two Sapling examples (a user suffering slow status from automation always passing `--no-optional-locks`, and production cases where status stayed slow for tens of seconds to minutes without a lock), presented a before/after matrix arguing the 1s default gives "no, rarely" commit conflicts without needing `--no-optional-locks`, and answered three readings of "address the underlying performance problems" (shorter lock hold, lock-free index writes, fsmonitor-style notification), noting Mercurial/Sapling default to a 10-minute lock wait.
- [2026/10/14/10-04-32 by Jeff King <peff@peff.net>] Jeff King identified a pre-existing race in `commit`: it reads the index before taking the lock without discarding the earlier read, so a concurrent `git add` during the window can be clobbered (demonstrated with an instrumented `sleep(5)` widening the window); he said the patch fixes the race but the commit message should state that as motivation and note the lock may now be held longer while stat() runs over the repo.
- [2026/10/14/10-14-02 by Jeff King <peff@peff.net>] Jeff King noted `--no-optional-locks` assumes the user eventually runs an index-updating command, which isn't guaranteed, and that an IDE could occasionally run a normal status; he judged the lock-timeout approach reasonable, said the widened race window is fine for benign commands like status but bad for `git add` (per his patch 2 reply), and observed the git-commit race has likely existed 20+ years, so closing it makes the timeout behavior a no-brainer.
- [2026/10/14/16-29-25 by D. Ben Knoble <ben.knoble@gmail.com>] D. Ben Knoble accepted Jun Wu's explanation ("Makes sense"), guessed the worsening might come from more files needing content-hashing, bowed out of the discussion since Peff considered the approach fine, and shared that his editor integration (tpope's vim-fugitive) does not use `--no-optional-locks` and instead limits background refreshes to specific events with caching.
- [2026/10/14/22-12-24 by Jun Wu <quark.zju@gmail.com>] Jun Wu clarified to Junio C Hamano that the "if the index is read before locking, the wait is skipped" rule is scoped to a single process calling `repo_hold_locked_index` (timeout=0 when `repo->index->initialized` is already set), applies to both `git status` and commands like `git add`, and leaves `git status` behavior unchanged since it always reads before locking; he also agreed to adjust the cover letter to state the proposed solution explicitly going forward.
- [2026/10/14/22-12-32 by Jun Wu <quark.zju@gmail.com>] Jun Wu answered Junio C Hamano's three questions on `core.indexLockTimeout`: (1) the lock infrastructure could force dropping an outdated in-memory index once the lock is acquired, with per-command handling (status skips the write if invalidated; `add -i` re-applies), as Mercurial's locks do; (2) read-only commands that lock without writing (e.g. `rm --dry-run`) will now wait, and he discussed whether the index lock scope covers only the index or also working-copy files, noting `clean` takes no lock and is unaffected; (3) `initialized=1` is set by `do_read_index` or `unpack_trees`, so it does not always mean the on-disk index was read (e.g. read-tree on an empty index), and he found no command that builds an index from scratch and then calls `repo_hold_locked_index`; he also acknowledged the default-timeout change alters end-user behavior and that the test timeout changes are not strictly necessary, and is open to 10 minutes, 0, or another default.

This is the first patch in the v8 series fixing a `rerere` race condition. It introduces a configurable timeout (`rerere.lockTimeout`, default 1000 ms) for acquiring the `MERGE_RR.lock` file, replacing the previous behavior of failing immediately when the lock is held. The change targets the `rerere` subsystem and affects all commands that write to the `rr-cache` (e.g., `git merge`, `git rebase`, `git rerere forget`, `git rerere clear`, and `git rerere gc`).

The patch updates `rerere.c` to use `repo_hold_lock_file_for_update_timeout()` instead of `repo_hold_lock_file_for_update()`, allowing processes to wait for the lock for up to `rerere.lockTimeout` milliseconds before failing. The default timeout (1 second) is chosen to cover typical `git rerere gc` operations, which prune stale entries quickly. Documentation for the new config key is added to `Documentation/config/rerere.adoc`, explaining valid values (0 for no wait, -1 for indefinite wait, positive integers for milliseconds). The test suite (`t/t4200-rerere.sh`) verifies the new behavior under various scenarios: waiting for the lock, failing after timeout, and ensuring explicit `rerere` commands (`forget`, `clear`, `gc`) and `git rebase --abort` fail immediately if the lock cannot be acquired.

This patch is a direct response to feedback from Junio C Hamano and Patrick Steinhardt, incorporating minor adjustments such as removing redundant lock behavior documentation, tightening test error-message matching, and moving test cleanup steps into `test_when_finished`. The changes are well-motivated by the race condition exacerbated by the geometric maintenance strategy (Git 2.54), which triggers `git rerere gc` more aggressively. The patch preserves backward compatibility: a timeout of 0 restores the old behavior, and error messages remain unchanged to avoid misleading users. The test coverage is thorough, ensuring the new timeout logic works as intended without regressing existing functionality.

The patch is technically complete and ready for integration. It addresses the core issue—concurrent `rerere` operations contending for the lock—while maintaining a conservative approach (failing outright if the lock remains held after timeout). The configurable timeout provides flexibility for users with atypical workloads, and the default value is chosen to balance responsiveness and robustness. No substantive objections remain, and the patch aligns with the project's preference for correctness over resilience in locking scenarios.

This is the v8 iteration of a two-patch bugfix series targeting the `rerere` subsystem. The patches address a long-standing race condition where concurrent `rerere` operations contend for the shared `MERGE_RR.lock`, a problem exacerbated by the geometric maintenance strategy introduced in Git 2.54. The solution introduces a configurable timeout (`rerere.lockTimeout`, default 1000 ms) for non-maintenance callers and a `--skip-locked` mode for `git rerere gc` (hidden/undocumented) that skips silently when the lock is held, matching the behavior of other auto-maintenance tasks.

The v8 updates incorporate all remaining feedback from Junio C Hamano and Patrick Steinhardt. Key changes since v7 include: removing redundant documentation about lock behavior (Junio), tightening test error-message matching to avoid false positives (Junio), moving test cleanup steps into `test_when_finished` (Junio), and reverting to a shared `RERERE_NOWAIT` flag in the existing bitmask instead of introducing a dedicated `enum rerere_gc_flags` (Patrick). The commit messages and code comments have also been refined for clarity.

Files touched span `rerere.c` (locking logic, error propagation), `rerere.h` (flag definitions), `builtin/gc.c` and `builtin/rerere.c` (caller updates), documentation (`rerere.adoc`), and tests (`t4200-rerere.sh`, `t7900-maintenance.sh`). The test suite now explicitly verifies that `--skip-locked` mode skips only when the lock is held, that manual `rerere gc` calls fail after timeout, and that the flag is rejected for non-`gc` subcommands.

The series is technically complete and ready for integration. The conservative approach (failing outright if the lock remains held after timeout) prioritizes correctness over resilience, and all prior substantive feedback has been addressed. The only remaining discussion point—a minor API design preference—does not affect functionality or block merging. The patches are well-motivated, with clear reproduction scenarios and thorough test coverage.

The `git log --follow` performance regression introduced in Git 2.56 by commit 304813ed33 is under active investigation after a user reported a dramatic slowdown—from 33 seconds to nearly 8 minutes—when tracing file history in the Linux kernel repository. Patrick Steinhardt forwarded the report and bisected the issue to the commit, which aimed to improve rename-following for non-linear history.

SZEDER Gábor has now provided a detailed technical analysis confirming the regression, though with a smaller impact in the Git repository itself (2.7× slowdown) compared to the Linux kernel (14×). The bottleneck lies in the new `propagate_follow_pathspec_to_parent()` logic, which exhibits quadratic or worse behavior when processing merge commits with many parents. Specifically, comparing a merge commit with its *non-first* parents takes 4.4 seconds, versus just 1.4 seconds for the first parent. Gábor also highlights a key architectural difference: `git log -L` (line-level history) remains much faster because it skips diffing against non-first parents if the file is unchanged in the first-parent history, while `--follow` always diffs against every parent. This suggests the fix may involve adopting a similar optimization for `--follow`.

No patch has been proposed yet, and the regression’s scope—whether it affects only `--stat` or `--follow` more broadly, and whether it’s specific to large repositories like the Linux kernel—remains unclear. The original commit’s trade-offs between correctness and performance are also still under scrutiny. So far, only Patrick Steinhardt and Gábor have weighed in, with no response yet from the original commit’s author.

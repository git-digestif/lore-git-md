This thread is about a severe performance regression in `git log --stat --follow` that emerged in Git 2.56, slowing the command from 33 seconds to nearly 8 minutes in the Linux kernel repository. The issue was bisected to commit 304813ed33, which aimed to improve `--follow`'s ability to track renames across non-linear history but introduced a bottleneck in `propagate_follow_pathspec_to_parent()`. SZEDER Gábor confirmed the regression with benchmarks showing a 14× slowdown in the Linux kernel repo and a 2.7× slowdown in Git's own repository, pinpointing the quadratic behavior of the new logic when processing merge commits.

Miklos Vajna, the author of the regressing commit, has acknowledged the issue but argues it reflects a necessary trade-off: the new behavior fixes a long-standing flaw in `--follow`'s handling of non-linear history, albeit at a performance cost. He suggests the regression was anticipated and proposes exploring optimizations to retain the correctness improvements while addressing the slowdown. The discussion now centers on whether the algorithm's design is inherently flawed or if the implementation can be refined—potentially by adopting strategies like those used in `git log -L`, which skips diffing against non-first parents when the file is unchanged. No fix has been posted yet, and the thread remains open to creative solutions that balance performance and correctness.

The `git log --follow` performance regression thread has taken a sharp turn toward architectural scrutiny. The issue began when a user reported that `git log --stat --follow` had slowed from 33 seconds in Git 2.55 to nearly 8 minutes in Git 2.56, a regression bisected to commit 304813ed33, which aimed to fix `--follow`’s long-standing inability to track renames across non-linear history. Miklos Vajna proposed a fix that restored near-original performance (29s vs. the pre-regression 28s) by optimizing `propagate_follow_pathspec_to_parent()` to avoid redundant diff passes when a file is unchanged in any parent.

Junio C Hamano has now raised a fundamental correctness concern with Miklos’s patch. Using a concrete merge scenario—where a file is modified in one branch but renamed and then modified in another—Junio demonstrates that the patch’s optimization could break rename-following by treating the file as "unchanged" in the merge’s first-parent history, even though its second-parent history contains a critical rename. This critique shifts the discussion from performance tuning to whether the optimization’s classification logic can reliably distinguish between syntactic and semantic sameness. The thread is now at a crossroads: Miklos must either adjust the patch to handle this edge case or clarify whether such scenarios fall outside `--follow`’s intended scope. SZEDER Gábor and Patrick Steinhardt, who previously provided substantive technical input, have yet to weigh in on this latest development. No integration status has been reported; the series remains under active review.

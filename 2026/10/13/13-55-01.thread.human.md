This thread began when Patrick Steinhardt forwarded a user report of a severe performance regression in `git log --stat --follow`, which slowed from 33 seconds in Git 2.55 to nearly 8 minutes in Git 2.56 after commit 304813ed33 ("log: improve --follow following renames for non-linear history"). Miklos Vajna, the author of the original commit, proposed a fix that restores near-original performance (29s vs. 28s pre-regression) by optimizing the `propagate_follow_pathspec_to_parent()` function to avoid redundant diff computations. The patch has been benchmarked against the Linux kernel repository and passes all existing tests, but its design is now under scrutiny.

Junio C Hamano has weighed in with a substantive review, questioning the patch’s architectural approach. He argues that the optimizations are applied too late—after `log_tree_diff()` has already flushed its output—making it impossible to reuse diff metadata that could have informed the rename-following logic. Instead, he suggests moving the fix *inside* `log_tree_diff_flush()`, where the diff queue is still available, or even reconsidering the entire change introduced by 304813ed33. This review shifts the discussion from performance benchmarks to design trade-offs, raising the possibility that the original fix may need a more fundamental rework. The thread is now focused on whether the patch’s incremental optimizations are sufficient or if a deeper refactor is required.

Key participants include SZEDER Gábor, who initially isolated the bottleneck and highlighted the contrast with `git log -L`’s more efficient strategy, and Miklos Vajna, who authored both the regression and the proposed fix. The outcome hinges on whether Miklos can address Junio’s architectural concerns or justify the current design. No integration status has been reported yet, and the fix remains under active review.

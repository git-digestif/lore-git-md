This is a **platform compatibility bugfix** targeting macOS (and other environments) where tools rewrite files with CRLF line endings, causing `git status` to incorrectly report modifications. Curtis Allen Smith responds to Johannes Sixt’s architectural objection in the ongoing RFC series addressing the CRLF conversion size-trusting bug in `read-cache.c`.

Curtis clarifies the core issue: the index’s recorded size is correct (it reflects the LF file as checked out or added), but tools rewriting the file with CRLF endings change the on-disk size. The problem lies in `ie_modified()`’s assumption that a size change always indicates modified content—an assumption that fails when conversion (e.g., CRLF rewriting) alters file size without changing the blob Git would record. His v4 patch (not yet posted) removes the disputed comment and rewords the commit message to reflect this reasoning.

The exchange sharpens the architectural debate. Johannes Sixt argues the fix should ensure the index records the correct size during `git add`, preserving the existing optimization (trusting size changes). Curtis counters that the index size *is* correct, and the issue is `ie_modified()`’s logic, which must account for conversion. This disagreement could determine whether the fix targets `git status` (Curtis’s approach) or `git add` (Johannes’s preference), with significant implications for performance and design.

The thread remains in RFC status, awaiting Curtis’s v4. The discussion now hinges on whether the patch’s performance trade-off (adding a conversion check in `git status`) is justified or if the root cause lies elsewhere. No resolution is in sight, but the debate is now more precise.

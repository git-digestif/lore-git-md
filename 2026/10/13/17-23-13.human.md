This is a feature patch series introducing a configurable timeout for Git’s index lock, aimed at reducing conflicts between background operations (like `git status` from an IDE) and foreground commands (like `git add` or `git commit`).

The series adds a new `core.indexLockTimeout` configuration variable (default: 1 second) that lets commands wait for the index lock instead of failing immediately. Patch 1 implements the timeout mechanism and applies it to commands that read the index *after* acquiring the lock (e.g., `add`, `rm`, `checkout`). Patch 2 reorders the lock/read sequence in `git commit` so it can also respect the timeout. Commands that read the index before locking (e.g., `reset`, `merge`) skip the wait to avoid write races.

The motivation is clear: IDEs running periodic `git status` can either slow down (with `--no-optional-locks`) or conflict with user-initiated commands. The series builds on past discussions (2017 proposals and the `--no-optional-locks` flag) but takes a different approach by making the lock acquisition more flexible rather than avoiding it entirely. The default timeout of 1 second is justified in the commit message as a balance between responsiveness and avoiding hangs.

Tests are included (`t0032-index-lock-timeout.sh`), and the changes are narrowly scoped to common commands. The author notes they’re open to extending the mechanism to other commands if there’s interest. The series looks well-crafted and addresses a real pain point for IDE users without introducing major behavioral changes.

This is the first patch in the **v6 revision of a feature series** that hardens Git's ignore-revs parser and tag-peeling logic ahead of enabling a default ignore-revs file (`.git-blame-ignore-revs`). The patch is **queued for `next`** and addresses security concerns raised during review of the broader feature.

The changes focus on two critical code paths that will soon be exposed to upstream-controlled content at a well-known path. First, `oidset_parse_file_carefully()` in `oidset.c` now rejects any line containing an embedded NUL byte using `memchr()`, preventing silent truncation of object names or comments. Second, `peel_to_commit_oid()` in `builtin/blame.c` is hardened to avoid promisor fetches in partial clones: it uses `odb_read_object_info_extended()` with `OBJECT_INFO_SKIP_FETCH_OBJECT` and `OBJECT_INFO_QUICK`, verifies each tag’s declared type before parsing, and peels tags one layer at a time while checking for local object existence. The patch also enforces a 100MB size cap (inherited from the broader series) to prevent memory exhaustion.

The test coverage is thorough, adding two new test cases to `t/t8013-blame-ignore-revs.sh`. The first verifies that lines with embedded NUL bytes are rejected with a clear error message. The second tests tag-peeling behavior with chained tags and missing tag targets, confirming that the parser skips invalid entries without triggering network requests in partial clones. The tests use `git blame --line-porcelain` to extract commit OIDs and compare them against expected values, ensuring the ignore-revs logic behaves as intended.

This patch is a **prerequisite** for the second patch in the series, which enables the default ignore-revs file. The hardening is **well-motivated** and aligns with Git’s existing security practices (e.g., `.gitattributes` size limits, NUL-byte rejection in other parsers). The implementation is **clean and minimal**, touching only the necessary code paths without introducing new symbols or dependencies. The changes are **backwards-compatible**—existing ignore-revs files remain unaffected—and the error messages are user-friendly.

The patch has **no open technical objections** and is part of a series that has already received Junio’s approval. The only remaining discussion point is whether to retain the NUL-byte check, but the author has signaled willingness to adjust it in a follow-up if needed. This is a **low-risk, high-value security improvement** that prepares the blame subsystem for broader adoption of ignore-revs files.

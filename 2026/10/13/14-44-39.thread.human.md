This thread is about a bugfix for a regression in `git fetch --all --depth=<n>` and `git fetch --all --unshallow`, where the `--depth` or `--unshallow` flags were not being forwarded to subprocesses handling multiple remotes, leaving the repository shallow when it should have been deepened. The issue was introduced in Git 2.56.0.

Rong Bao submitted an initial patch, which Junio C Hamano reviewed, raising two key concerns: (1) the same propagation issue might affect submodule fetches when `--recurse-submodules` is used, and (2) the patch only handled `--depth` but not other deepening options like `--deepen-since` or `--shallow-exclude`, risking malformed subprocess arguments. Rong has now revised the patch to address these concerns by explicitly forwarding `--depth` and `--deepen-since` while intentionally omitting `--shallow-exclude` to avoid potential issues with submodule histories. The patch remains focused on the original regression but now also touches submodule fetches, though whether submodules should inherit deepening flags at all is still an open question.

The revised patch is uncontested for the core `--all` use case but leaves the submodule behavior unresolved. Rong argues that propagating `--depth` to submodules aligns with existing behavior for `--tags` and user expectations, but Junio’s review suggests caution. The patch is expected to be resubmitted as v2, with tests verifying the fix for `--all` but no new coverage for submodule propagation. The discussion hints at broader implications for submodule handling, but the current approach is deliberately conservative to avoid regressions.

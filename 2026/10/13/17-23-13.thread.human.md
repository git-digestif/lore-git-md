This thread introduces a configurable index lock timeout (`core.indexLockTimeout`, default 1 second) to reduce contention between background IDE `git status` calls and user commands like `add` or `commit`. The series, authored by Jun Wu, lets Git commands wait briefly for the lock instead of failing immediately, while avoiding race conditions by skipping the wait if the index was already read before locking. A key side effect is fixing a long-standing race in `git commit` where concurrent index updates (e.g., from `git add`) could be silently discarded if the commit read the index before acquiring the lock.

The patches are under active review, with Junio C Hamano and Jeff King (Peff) raising substantive feedback. Junio has focused on edge cases in the lock-taking logic, particularly how the timeout interacts with commands that have already read the index or take the lock for consistency. Peff’s latest review highlights the pre-existing race in `git commit`—present for over 20 years—and endorses the series’ lock-order fix as a correctness improvement, though he stresses the commit message should frame this as a bug fix rather than just a timeout enabler. The author still needs to address Junio’s questions about race-avoidance behavior and clarify the motivation for the lock-order change.

Ben Knoble has argued against adding another config knob, favoring root-cause fixes like faster `git status` or IDE coordination, but Jun Wu defends the configurability as pragmatic, citing real-world performance issues in Sapling (Facebook’s Git fork) and Mercurial’s precedent. The series touches `repository.c`, `builtin/commit.c`, and adds a new test script (`t/t0032-index-lock-timeout.sh`), with no on-disk format changes. Commands like `add`, `commit`, and `checkout` support the timeout, while others like `reset` and `rebase` do not. The debate over the default timeout (1 second) and whether additional commands should eventually support it remains open.

This thread introduces a configurable timeout (`core.indexLockTimeout`, default 1 second) for Git’s index lock to ease contention between background IDE `git status` calls and user commands like `add` or `commit`. The series also fixes a 20-year-old race condition in `git commit` where concurrent index updates (e.g., from `git add`) could be silently discarded if the commit read the index before acquiring the lock.

Jun Wu is the author; key reviewers are Junio C Hamano (maintainer), Jeff King (Peff), and D. Ben Knoble. Junio’s feedback on edge cases in the lock-taking logic—such as what happens when the index was already read but the lock is held or the index updated—has been addressed by Jun Wu’s proposal to force-drop outdated in-memory indexes once the lock is acquired. Peff identified the pre-existing race in `git commit` and insists the commit message frame the lock-order change as a correctness fix, not just a refactor. Knoble initially opposed the configurability but stepped back after Jun Wu clarified that `--no-optional-locks` forces `git status` to re-hash file contents (not just refresh stat info) when the lock is unavailable, causing persistent slowdowns; he now defers to others on the trade-offs.

The series is under review, with v2 expected after Jun Wu revises the cover letter and commit message to incorporate these clarifications. The default timeout value and whether additional commands (e.g., `reset`) should support the timeout remain open questions. No merge status has been reported.

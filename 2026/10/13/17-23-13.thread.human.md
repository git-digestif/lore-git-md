This thread is about Jun Wu’s patch series introducing a configurable timeout (`core.indexLockTimeout`) for Git’s index lock, aimed at reducing contention between background IDE operations and user commands. The series, now at v2 with four patches, allows commands to wait briefly for the lock instead of failing immediately, while avoiding race conditions by skipping the wait if the index was already read by the same process. A key side effect is fixing long-standing write-race conditions in `git commit` and `git reset`, where concurrent updates (e.g., from `git add`) could be silently discarded due to lock-order issues.

The series is under active review, with Junio C Hamano and Jeff King (Peff) providing substantive feedback that has shaped the current version. Jun Wu has addressed concerns about edge cases in lock-taking behavior and clarified the per-process nature of the race-avoidance logic, while Peff’s insistence on framing the lock-order changes as correctness fixes has improved the commit messages. The first two patches refactor the lock API and implement the timeout logic, while the latter two fix the pre-existing races in `git commit` and `git reset`. No merge status has been reported, and the series remains in the `seen` branch pending further discussion.

Open questions include the default timeout value (1 second, though Jun Wu is open to alternatives like Mercurial’s 10-minute default), whether additional commands should eventually support the timeout, and the broader debate over configurability versus root-cause fixes. D. Ben Knoble initially raised design concerns but has stepped back, though he remains skeptical about the trade-offs, noting that users may notice hang-ups in commands that were previously fast. The series takes a pragmatic, phased approach, landing the timeout feature first while deferring lock-order fixes for other commands, a strategy that remains open to debate.

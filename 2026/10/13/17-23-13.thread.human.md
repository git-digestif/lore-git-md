This thread is about a patch series by Jun Wu that introduces a configurable timeout (`core.indexLockTimeout`) for Git’s index lock, aimed at reducing contention between background IDE operations and user commands. The series has grown from two to four patches in its second version, with the latest addition (Patch 3) fixing a long-standing write-race condition in `git commit` that could silently discard concurrent index updates.

The core idea is to let commands wait briefly for the lock instead of failing immediately, while avoiding race conditions by skipping the wait if the index was already read by the same process. The default timeout is 1 second, though this remains open to debate—Jun Wu is open to adjusting it (e.g., to 10 minutes, matching Mercurial’s precedent). The series also addresses pre-existing race conditions in `git commit` and `git reset` by reordering lock acquisition to follow a "lock → read → write" pattern, a correctness fix that has been well-received by reviewers like Jeff King (Peff).

Key participants include Jun Wu (author), Peff (who identified the pre-existing races and pushed for clearer commit messages), Junio C Hamano (maintainer, who raised concerns about edge cases now addressed), and D. Ben Knoble (who initially questioned the need for a new config knob but deferred to others on the trade-offs). The series is under review, with no merge status reported, and remains in Junio’s `seen` branch. Open questions include the default timeout value, whether additional commands (e.g., `rebase`) should eventually support the timeout, and the broader debate over configurability versus root-cause fixes (e.g., improving `git status` performance or IDE coordination).

The technical details are straightforward: the timeout is implemented in `repository.c`, with test coverage in a new script (`t/t0032-index-lock-timeout.sh`). The lock-order changes in `git commit` and `git reset` are narrowly scoped and unlikely to introduce regressions, though Peff noted the timeout could amplify existing race windows in other commands. The series adopts a phased approach, landing the timeout feature first and incrementally fixing lock-order issues in other commands.

This thread is about Jun Wu’s patch series introducing `core.indexLockTimeout`, a configurable timeout (default 1 second) to reduce lock contention between background IDE `git status` calls and user commands like `add` or `commit`. The series is still under review after two rounds of substantive feedback from Junio C Hamano, who has raised questions about edge cases in the lock-taking logic and the reliability of the race-avoidance mechanism.

Jun Wu has now responded to D. Ben Knoble’s design-level concerns, clarifying why the current `--no-optional-locks` workaround isn’t sufficient. He explains that skipping the index lock forces `git status` to re-hash file contents (not just refresh stat info), leading to persistent slowdowns if users don’t run index-writing commands to recover. Real-world data from Sapling (Facebook’s Git fork) shows multi-minute slowdowns and 40% checkout failure rates due to lock contention, motivating the 1-second default as a pragmatic balance. Jun also defends the configurability approach, arguing the default is user-friendly and aligns with Mercurial/Sapling’s precedent, though he acknowledges Knoble’s preference for root-cause fixes like lock-free writes or fsmonitor-style notifications.

The open questions remain focused on Junio’s feedback about the race-avoidance logic—specifically, whether the current behavior (immediate failure if the index was read but the lock is held) is correct, and whether `repo->index->initialized` reliably indicates a prior read. The default timeout value and the lock-order change in `git commit` are also still under debate. No new code changes have been posted yet; the discussion is still at the design level.

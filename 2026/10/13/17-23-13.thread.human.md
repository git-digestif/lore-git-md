This thread introduces a configurable index lock timeout (`core.indexLockTimeout`, defaulting to 1 second) to reduce contention between background IDE `git status` calls and user commands like `add` or `commit`. The series, now complete at four patches, also fixes long-standing write-race conditions in `git commit` and `git reset` where concurrent updates could be silently discarded.

Jun Wu is the author, and the series has drawn substantive review from Junio C Hamano, Jeff King (Peff), and D. Ben Knoble. The core change lets Git commands wait briefly for the index lock instead of failing immediately, while avoiding race conditions by skipping the wait if the index was already read by the same process. The lock-order fixes in `git commit` and `git reset` reorder operations to follow a "lock → read → write" pattern, eliminating pre-existing race windows that have existed for over 20 years.

The series is under review, with no merge status reported. Open questions include the default timeout value (1 second vs. alternatives like 10 minutes) and whether to extend the lock-order fixes to other commands like `rebase`. Knoble remains unconvinced the timeout is the best long-term solution, preferring root-cause fixes like IDE coordination, while Peff and Junio have focused on correctness and edge cases. The implementation is conservative, skipping the timeout for commands that read the index before locking to avoid amplifying race windows.

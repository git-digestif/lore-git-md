Thread identity
Subject: [PATCH 0/5] odb: refactor and optimize alternates handling in files backend
Series version: v1 (initial submission)
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring/performance)

Core problem or goal
Refactor and optimize the alternates mechanism in the Git object database’s "files" backend. The series addresses performance inefficiencies in reading and streaming objects when alternates are present, then performs internal cleanup to simplify the ODB source API and remove redundant code. No user-visible behavior changes are intended.

Current status
Under review; v1 posted. No prior versions of this specific series. Built on Patrick’s earlier `ps/odb-files-alternates` branch, which migrated alternates handling into the files backend.

Key technical details
Files touched: 12 total (series-wide); primary changes in `odb.c`, `odb/source-files.c`, `odb/source.h`, `odb/source-loose.c`, `odb/source-packed.c`, `odb/source-packed.h`. Patch 1/5 reorders loops in the "files" backend to prioritize packfile checks over loose-object `stat()` calls, achieving a 2x speedup in object lookup when alternates are present (benchmarked by Patrick). Patch 2/5 applies the same optimization to object streaming, aligning its behavior with the direct-read optimization in patch 1/5. Patch 3/5 removes the `OBJECT_INFO_SECOND_READ` flag and moves the second object read logic into the "files" backend, replacing it with `OBJECT_INFO_QUICK` in the packed source to determine when to scan packfiles covered by a MIDX (expected to have minimal performance impact). The early loop termination in `odb_source_files_read_object_info()` is structured to accommodate a planned follow-up series that will modify alternates reloading to iterate over newly added loose object directories. Patch 4/5 removes a redundant read loop in `do_oid_object_info_extended()` by replacing it with a single explicit re-read after fetching from a promisor remote. Patch 5/5 removes the now-unused `local` flag from the generic `struct odb_source` and moves it into `struct odb_source_packed`, completing the internal API cleanup. The `ODB_FOR_EACH_OBJECT_LOCAL_ONLY` flag is now considered "leaky" by Justin Tobler, as it assumes "files" backend semantics despite being part of the generic ODB API.
Behavior changes: none (plumbing-level). On-disk format: unchanged.
Test coverage: relies on existing ODB tests; no new tests introduced in this series.

Open questions and loose ends
Patch 4/5: Justin Tobler’s suggestion to tighten error handling in `do_oid_object_info_extended()` by immediately failing with `ODB_READ_ERROR` when the repository is corrupt (rather than attempting to fetch a missing object) has been acknowledged by Patrick Steinhardt, who agrees in principle but defers the change to a separate follow-up commit to keep this patch purely a refactoring. The question remains open but is now explicitly scoped as a future technical improvement rather than a blocker for this series.
Patch 5/5: The design-level concern about the `ODB_FOR_EACH_OBJECT_LOCAL_ONLY` flag’s long-term viability is now explicitly scoped as a potential follow-up effort. Patrick Steinhardt identified two current callers: `git pack-objects --local` (which he considers overly tied to the "files" backend) and `add_unseen_recent_objects_to_traversal()` in `reachable.c` (whose usage he finds dubious). He suggested the flag could potentially be removed entirely but deferred that work. Justin Tobler’s question about whether the in-memory source should ever be iterated when only "local" objects are requested was answered in the negative by Patrick, who stated he is unaware of any such scenario. The patch itself is uncontroversial and moves the codebase in the right direction, but the unresolved question about the flag’s future remains open.

Participant positions
Patrick Steinhardt (author): identified and fixed performance regressions in alternates handling (patches 1/5 and 2/5), providing benchmark data for the first patch and arguing for consistency in the second. Moved the second object read logic into the "files" backend (patch 3/5) to align with the alternates migration and simplify the ODB source API, structuring the early loop termination to accommodate a planned follow-up series. Removed the redundant read loop in `do_oid_object_info_extended()` (patch 4/5) and the `local` flag from the generic ODB source struct (patch 5/5), retaining it only in the packed source where it is still needed. All changes are mechanical and confined to the ODB plumbing. Addressed Justin Tobler’s feedback on patch 3/5, clarifying the rationale for the `OBJECT_INFO_QUICK` flag’s phrasing and the early loop termination’s structure, noting the latter is a temporary convenience for future work. Acknowledged Justin’s suggestion on patch 4/5 but deferred the error-handling change to a follow-up commit to preserve the patch’s refactoring-only scope. In the final exchange, listed the two current callers of `ODB_FOR_EACH_OBJECT_LOCAL_ONLY` (`git pack-objects --local` and `add_unseen_recent_objects_to_traversal()` in `reachable.c`), expressed skepticism about their legitimacy, and suggested the flag could be removed entirely in a future series. Confirmed that the in-memory source should never be iterated when only "local" objects are requested.
Justin Tobler (reviewer): provided **substantive, tested reviews** of patches 1/5, 2/5, 3/5, 4/5, and 5/5, confirming the technical rationale and implementation for all five. Endorsed the design decision to handle the optimizations within the "files" backend rather than introducing new ODB flags, calling the latter approach "confusing" and poorly aligned with the abstraction goals. Traced the code paths, verified the loop reordering achieves the stated performance goals, and approved the design direction for all five patches. Noted a minor style nit about early loop termination in the "files" backend in patch 3/5 and raised the error-handling question in patch 4/5. For patch 5/5, raised the abstraction concern about `ODB_FOR_EACH_OBJECT_LOCAL_ONLY`, describing it as "leaky" and "awkward" now that the `local` flag is no longer part of the generic ODB API. Explicitly stated the patch "looks reasonable" and "seems to be moving us in the right direction," with no requests for changes. Followed up to ask whether the in-memory source should ever be iterated when only "local" objects are requested, receiving a negative answer from Patrick.

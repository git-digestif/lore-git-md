This is a **maintainer feedback** email on the feature patch that proposes making `git blame` default to `.git-blame-ignore-revs` if no ignore file is explicitly configured. Junio C Hamano raises two substantive concerns about the current implementation.

First, he points out a **behavioral inconsistency** with hosting sites: the patch uses the working tree version of `.git-blame-ignore-revs`, which may differ from `HEAD:.git-blame-ignore-revs` if the file is untracked or has local changes. Hosting sites (GitHub, GitLab) operate on the committed version, so the patch as written would still produce different blame output in those cases. Junio suggests the default should instead use the `HEAD` blob if it exists, making the behavior consistent regardless of working tree state.

Second, he identifies a **new security threat vector**: the parser for ignore files now processes upstream-controlled content at a fixed path (`.git-blame-ignore-revs`), whereas previously it only read user-configured files. The current implementation uses `lstat()` to reject symlinks and non-regular files, but Junio argues this precaution is unnecessary if the default is switched to the `HEAD` blob (which avoids working tree access entirely). He calls for a security audit of the parser to ensure it cannot be exploited via malformed input.

The feedback is **substantive and tested** in spirit: Junio traces the code path, identifies the exact divergence from hosting site behavior, and highlights the security implications of the proposed change. His alternative design (using `HEAD:.git-blame-ignore-revs`) would eliminate both the inconsistency and the need for working tree access, simplifying the security story. The ball is now in the author’s court to either revise the approach or justify why the working tree version is preferable.

This is a follow-up in the ongoing documentation series introducing `gitmergeconflicts(7)`, a new man page consolidating merge conflict resolution guidance. Julia Evans responds to D. Ben Knoble’s earlier recommendation about how the guide should frame the choice between `git commit` and `git merge --continue` during conflict resolution.

Julia notes a small but important detail: `git status` currently recommends `git commit`, not `git merge --continue`, which contradicts Knoble’s suggestion to promote the latter as the default. She floats the idea of changing `git status`’s recommendation to align with the guide’s advice, but acknowledges the inertia of user habits—longtime Git users may be confused if the guide suddenly steers them toward `git merge --continue` while `git status` still points to `git commit`. Her proposed compromise is a neutral note in the guide: “`git commit` is an older alternative to `git merge --continue`. You can use either one after resolving a `git merge`.” This phrasing avoids taking sides while still informing users of both options, and it leaves the door open for future changes to `git status`’s output.

The exchange is a minor but practical refinement to the guide’s wording. It doesn’t introduce new technical content or alter the series’ direction, but it clarifies how the guide will present the two commands—neutrally, with a nod to backward compatibility. The discussion remains open on whether `git status` itself should be updated to recommend `git merge --continue`, but that would likely be a separate patch.

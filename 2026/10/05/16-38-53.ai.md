This is a design discussion about shallow clone behavior, specifically the architectural implications of preserving original commit IDs in shallow clones. Junio C Hamano responds to Matt Hunter’s tangential proposal (preserving original commit IDs in shallow clones to avoid empty-tree surprises) with a technical clarification: Git already uses a mechanism similar to grafts or replace refs to hide the true parents of shallow boundary commits, but it does *not* modify the commit objects themselves. This means the original commit IDs are preserved in the object database, and the "munging" is purely a runtime illusion for history traversal.

The key takeaway is that Hunter’s proposal is already partially implemented—shallow clones retain the original commit IDs, and the boundary commits are only *logically* rewritten as root commits during traversal. This clarification narrows the scope of the architectural question: the challenge is not preserving commit IDs (they already are), but whether the runtime illusion of root commits could be relaxed in specific contexts (e.g., fetch, revert) to avoid the empty-tree issue. Junio does not weigh in on whether this is desirable or feasible, but his response rules out object-identity changes as a solution.

This reply shifts the discussion toward the *mechanism* of shallow clones (grafts/replace-like behavior) rather than the safeguard proposal (warnings/refusals for destructive operations). It also introduces a new technical detail for follow-ups: the distinction between object storage (unchanged) and runtime history traversal (modified). Future discussion may explore whether fetch or revert logic could be adjusted to account for the original parentage of boundary commits, or whether the current behavior is an unavoidable trade-off of shallow clones.

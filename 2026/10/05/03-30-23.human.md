This is a **design discussion** continuing the RFC thread on the proposed "limbo" object-format state for new Git repositories. Jeff King (Peff) responds to Brian M. Carlson’s feedback, refining the proposal and clarifying his stance on timing and policy.

Peff agrees with Brian’s suggestion to advertise both `object-format=sha256` and `alt-object-format=sha1` (or similar) in the wire protocol, replacing the earlier `magic-limbo` capability. This approach explicitly signals support for both hash algorithms and accommodates future ones, addressing Brian’s compatibility concerns. The discussion now centers on whether this dual-advertisement is technically feasible, given Junio’s earlier skepticism about historical capability-parsing bugs.

On timing, Peff clarifies he is *not* proposing to delay Git 3.0’s SHA-256-by-default transition. He notes there’s ample time (another release cycle) to implement the limbo feature before 3.0 ships, leaving room for contributors like Scott Chacon to drive the work. This aligns with Brian’s urgency to deprecate SHA-1 but removes any suggestion of blocking progress.

Peff also addresses policy enforcement: while he sees account-level restrictions (e.g., "no SHA-1 repos") as a forge-specific concern, he agrees Git needs a config flag to mark the limbo state. This would be set by `git init` and respected by `receive-pack`, but Peff emphasizes it should *not* be enabled by default. The limbo feature would serve as a building block for forges like GitHub to reduce friction, but forges would still need to layer their own policy logic on top.

The thread is converging on a design that advertises multiple object formats and uses config to manage the limbo state, but key questions remain: whether older clients can safely parse multiple `object-format` directives, and how forges will enforce policies without Git-native support. The discussion is now more concrete but still conceptual.

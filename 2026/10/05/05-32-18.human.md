This is a **bugfix follow-up** in the ongoing thread about packfile corruption from stale delta base cache entries. Patrick Steinhardt responds to Jeff King’s suggestion to use AddressSanitizer (ASan) to detect the bug as a user-after-free, clarifying why ASan does not catch the issue in its current form.

The core problem remains a memory safety violation, but Patrick explains that the bug does not involve dereferencing freed memory. Instead, the cache key (a `packed_git *` pointer) becomes invalid when the pack is closed, but the cache entry’s *value* (the decompressed object data) is still valid. ASan fails to detect the issue because it does not reuse memory addresses, preventing the collision that triggers the corruption. This technical nuance underscores why the existing test relies on glibc’s allocator behavior—it is the only way to reproduce the bug deterministically.

The exchange does not challenge the fix itself (evicting stale cache entries when packs close), which remains uncontested. However, it highlights a limitation in ASan’s applicability to this specific bug, leaving the test design discussion unresolved. The thread’s focus now shifts back to whether the current platform-dependent test is sufficient or if an alternative approach (e.g., a custom allocator or a more targeted memory-checking tool) is needed. No new patches or action items emerge from this reply.

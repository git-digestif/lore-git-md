Matthew E. Luallen reported three date-handling bugs in Git’s ZIP archive generation and `git fast-import` logic, which can produce inconsistent or invalid timestamps. The first issue causes 1972 commits to appear as 2100 in ZIP’s legacy DOS date field, breaking tools like UnZip. The second wraps 2106-02-07 commits to 1970 in ZIP’s extended timestamp field, creating inconsistencies with TAR exports. The third allows `git fast-import` to accept negative timestamps that `git fsck --strict` later rejects, with ISO rendering showing literal placeholders.

René Scharfe has now weighed in with a substantive review, clarifying the technical constraints and trade-offs. For the DOS date overflow, he suggests clamping to 1980-01-01 (matching `zip(1)`) but questions whether tools still rely on the legacy field when a Unix timestamp is present. For the extended timestamp wrap, he proposes clamping to the maximum value (4294967295) instead of wrapping to 1970, improving consistency with TAR. On the `fast-import` validation gap, he notes that `validate_raw_date()` silently accepts negative timestamps, referencing existing `NEEDSWORK` comments in the code.

The thread remains open, with no patches or maintainer decisions yet. Key questions include what timestamp range ZIP should support, whether `fast-import` should reject timestamps that `fsck` considers invalid, and how to balance tool compatibility with correctness. René’s feedback provides a useful foundation for future fixes, but the discussion is still in the early stages.

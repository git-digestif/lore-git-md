This thread is a bug report from Matthew E. Luallen identifying three date-handling inconsistencies between Git's ZIP archive output, `git fast-import`, and downstream tools. The most advanced issue is the ZIP extended timestamp wrap, where commits dated after 2106 silently wrapped to 1970 in the UT extra field; René Scharfe has addressed this with a v2 patch that omits the UT field for out-of-range timestamps, incorporating a test prerequisite fix from Matthew that resolves CI failures on 32-bit platforms, leaving the patch ready for integration with no remaining technical blockers. The legacy DOS date field overflow remains open, with René advocating rejection of out-of-range timestamps rather than clamping, particularly after a newly discovered bug in `dos_time()` produces invalid timestamps on 32-bit platforms when values exceed 32-bit range.

For the third issue -- `fast-import` accepting negative timestamps in `--date-format=raw` that `git fsck --strict` later rejects -- the thread has gained new momentum as Aniket Gupta has volunteered to send a patch making the plain `raw` format reject values that fsck would flag as `badDate`, while leaving the `raw-permissive` format unchanged to preserve flexibility. This aligns with Matthew's earlier proposal and René's reference to `NEEDSWORK` comments in `validate_raw_date()`, though René had previously opposed stricter validation on the grounds that Git's commit objects already accommodate arbitrary decimal timestamps. Junio C Hamano has confirmed the technical soundness of the test fix for the ZIP patch and suggested a broader future audit of `timestamp_t` coercion into external formats, while Matthew continues to track a separate time-zone issue with post-2038 dates in UnZip's update mode.

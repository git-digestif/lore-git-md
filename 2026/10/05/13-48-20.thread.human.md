This thread is a bug report from Matthew E. Luallen about three date-handling inconsistencies in Git’s ZIP archive generation and `git fast-import` logic. The most progress has been made on the ZIP extended timestamp issue, where René Scharfe’s patch to omit the Extended Timestamp (UT) field for out-of-range values is now unblocked for integration after Matthew fixed the test infrastructure to use `TIME_T_IS_64BIT` instead of `TIME_IS_64BIT`. This ensures the tests pass on 64-bit platforms and are skipped on 32-bit systems where `zipinfo(1)` lacks UT field support.

The ZIP legacy DOS date overflow bug remains open, with René advocating for rejection of out-of-range timestamps rather than clamping, arguing it’s the "most honest option" to avoid tool compatibility risks. A newly identified bug in `dos_time()`—where timestamps exceeding 32-bit range produce invalid values—adds urgency, particularly for 32-bit platforms. Meanwhile, the `fast-import` negative timestamp validation gap is still contested: Matthew proposes rejecting negative timestamps to align with `NEEDSWORK` comments, while René opposes stricter validation, citing Git’s existing flexibility with decimal strings in commit objects.

Junio C Hamano’s recent review confirmed the test infrastructure fix, resolving CI failures on 32-bit platforms and clearing the way for the UT field omission patch to proceed. The unresolved issues—ZIP legacy DOS date handling and `fast-import` validation—remain separate and lack consensus, with no maintainer decisions yet. The thread highlights real-world tool compatibility risks (e.g., Python’s `ZipInfo.date_time` misreporting dates, UnZip’s update mode behaving unexpectedly) and the trade-offs between rejection, clamping, and silent overflow in legacy formats.

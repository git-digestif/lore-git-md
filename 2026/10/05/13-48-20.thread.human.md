This thread is a bug report from Matthew E. Luallen about three date-handling inconsistencies in Git’s ZIP archive generation and `git fast-import` logic. The most pressing issue—the ZIP extended timestamp wrap—has been resolved by René Scharfe’s patch, now in its second iteration. This patch omits the Extended Timestamp (UT) extra field in ZIP archives when commit times exceed the 32-bit signed integer range, preventing silent timestamp wraps that could cause tools like UnZip to misbehave. The patch includes Matthew’s test infrastructure fix, which ensures tests pass on 64-bit platforms and are skipped on 32-bit systems where `zipinfo(1)` lacks UT field support. Junio C Hamano has confirmed the fix, and the patch is now ready for integration with no remaining technical blockers.

The other two bugs remain open. The ZIP legacy DOS date overflow, where 1972 commits appear as 2100 in the legacy field, has expanded in scope after a newly identified bug in `dos_time()` was discovered. This bug produces invalid timestamps for values exceeding 32-bit range, causing fatal errors on 32-bit platforms. René advocates rejecting out-of-range timestamps entirely, arguing it’s the "most honest option" and could motivate users to adopt more robust formats like TAR. Meanwhile, the `fast-import` validation gap—where negative timestamps are accepted but later rejected by `git fsck --strict`—has no consensus yet. René opposes stricter validation, citing Git’s existing flexibility with decimal strings in commit objects, while Matthew proposes rejection to align with `NEEDSWORK` comments.

Key participants include Matthew, who provided real-world tool behavior examples and submitted the test infrastructure fix, and René, who implemented the UT field omission patch and advocates for rejection over clamping. Junio’s review has been surface-level but confirmed the test fix, unblocking integration. The thread’s broader policy debate—whether to reject or clamp out-of-range timestamps—remains unresolved for the legacy DOS date field, and the newly identified `dos_time()` bug will require separate attention. The `fast-import` issue is still contested, with no clear path forward.

This thread is a bug report from Matthew E. Luallen about three date-handling inconsistencies in Git’s ZIP archive generation and `git fast-import` logic. The most pressing issue—ZIP extended timestamp wrap—has been resolved by a patch from René Scharfe, which omits the Extended Timestamp (UT) field for out-of-range values to prevent silent misinterpretation in tools like UnZip. This fix is narrowly scoped and includes test coverage, but Junio C Hamano recently flagged a CI compatibility issue: the new tests fail on 32-bit platforms where `zipinfo(1)` either lacks UT field support or is missing entirely. The failure is purely in the test infrastructure, not the patch itself, and will likely require adjusting test prerequisites.

The other two bugs remain open. The ZIP legacy DOS date overflow (where 1972 commits appear as 2100 in the legacy field) is still under debate, with René now advocating for rejection rather than clamping to avoid misleading metadata in tools like Python’s `ZipInfo`. The `fast-import` validation gap—where negative timestamps are accepted but later rejected by `git fsck --strict`—also lacks consensus, with René opposing stricter validation on the grounds that Git’s commit objects already allow arbitrary decimal strings. Matthew has proposed incremental fixes for both issues, but no maintainer decisions have been made.

Key participants include Matthew, who provided real-world tool behavior examples demonstrating the risks of silent misinterpretation, and René, who implemented the UT field fix and shifted his stance toward rejection for the legacy DOS date issue. Junio’s recent email is a surface-level CI compatibility note and does not address the unresolved policy questions. The thread’s focus remains on balancing correctness, tool compatibility, and Git’s existing flexibility with timestamps.

This thread is a detailed bug report from Matthew E. Luallen about Git’s date-handling logic in ZIP archives and `git fast-import`. The report highlights three distinct issues: (1) a 1972 commit exported as a ZIP file produces a legacy DOS date interpreted as 2100, causing tools like UnZip to misbehave; (2) a commit at epoch 4294967296 (2106-02-07) wraps the ZIP’s extended timestamp to zero (1970), breaking consistency with TAR exports; and (3) `git fast-import` accepts negative timestamps (e.g., `-32184000 +0000`) that later trigger `fsck --strict` errors and render incorrectly in ISO format.

The report is thorough, with clear reproduction steps and real-world implications, such as macOS UnZip’s behavior in "update mode." It also raises a policy question: *What timestamp range should ZIP support, and should `fast-import` reject timestamps that `fsck` considers invalid?* The issues affect `archive-zip.c`, `fast-import.c`, and date validation logic, making them relevant to both export and import workflows. No patches or reviews have been posted yet—this is purely a bug report, not a fix.

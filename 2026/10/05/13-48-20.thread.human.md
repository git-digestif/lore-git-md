Matthew E. Luallen reported three date-handling bugs in Git’s ZIP archive generation and `git fast-import` logic, two of which affect ZIP exports and one `fast-import` validation. The most progress has been made on the ZIP extended timestamp issue, where René Scharfe’s patch now omits the Extended Timestamp (UT) field for commit times beyond 2106, preventing silent timestamp wraps that broke tools like UnZip. Matthew’s follow-up fixed the test infrastructure to handle 32-bit platforms correctly, replacing an incorrect prerequisite with `TIME_T_IS_64BIT` so the tests now pass on 64-bit systems and skip gracefully on 32-bit ones where `zipinfo` lacks UT support. This patch is ready for integration, though a newly discovered bug in the legacy DOS date conversion function (`dos_time()`) still blocks it on 32-bit platforms.

The other two bugs remain unresolved. The ZIP legacy DOS date field overflows when given pre-1980 or post-2107 timestamps, producing misleading metadata (e.g., a 1972 commit appears as 2100 in Python’s `ZipInfo`) or, in the newly identified case, invalid timestamps for values beyond 32-bit range. René now advocates rejecting out-of-range timestamps outright, arguing it’s the most honest approach and could push users toward more robust formats like TAR. Meanwhile, `git fast-import`’s `--date-format=raw` mode accepts negative timestamps that `git fsck --strict` later rejects, creating a validation gap. René opposes stricter validation here, citing Git’s existing flexibility with decimal strings in commit objects, while Matthew proposes rejecting negative values to align with existing `NEEDSWORK` comments.

The thread’s key participants are Matthew, who provided real-world tool behavior examples and the test infrastructure fix, and René, who implemented the UT field omission patch and shifted the ZIP legacy date discussion toward rejection. Junio C Hamano’s earlier CI breakage report has been addressed, but the `dos_time()` bug on 32-bit platforms now stands in the way of integrating the extended timestamp fix. The unresolved questions center on whether to reject or clamp out-of-range timestamps in the ZIP legacy field and whether to tighten `fast-import`’s validation of negative timestamps.

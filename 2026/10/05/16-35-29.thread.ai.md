Thread identity: Refactoring patch series `pw/stash-optimize-check_changes-calls/v1` by Phillip Wood, targeting redundant change-detection logic in `git stash push` and `git stash create`.

Core problem or goal: Eliminate duplicate checks for unstaged or uncommitted changes in `git stash push` and `git stash create`. The series consolidates redundant `check_changes()` calls into a single call for code hygiene, with no intended behavior change. The return-value convention of `do_create_stash()` is adjusted so that 2 now signals "no changes to stash" (previously conflated with 1, which continues to mean "nothing was stashed" due to `--patch` with no hunks selected or `--staged` when the index matches HEAD).

Current status: Under review; this is the first iteration (`v1`). The series consists of two patches touching `builtin/stash.c`, specifically `do_create_stash()` and `push_stash()`. Changes are mechanical: removal of redundant `check_changes()` calls (15 insertions, 12 deletions). Base commit is `c46c1e37724f0478939de636ab8ea5a89086d532`. A minor behavior change—attempting to create the reflog entry before discovering there is nothing to stash—is noted but deemed harmless. The first patch’s commit message has been corrected to address Junio C Hamano’s feedback, replacing three incorrect references to `stash store`/`do_store_stash` with `stash create`.

Key technical details: Files touched: `builtin/stash.c`. Functions modified: `do_create_stash()`, `push_stash()`, `create_stash()`. The single remaining `check_changes()` call is moved into `do_create_stash()`. No new functions, options, or symbols introduced. No on-disk format changes or test coverage updates. Junio C Hamano’s review identified a new inefficiency: `do_push_stash()` now calls `repo_refresh_and_write_index()` unconditionally, followed by `do_create_stash()`, which refreshes the index again, resulting in a redundant double refresh during `git stash push`. Phillip Wood acknowledges this inefficiency and confirms the double refresh is now unconditional (previously only occurred when there were changes to stash). The first refresh marks index entries as up-to-date, so the second refresh avoids unnecessary `lstat()` calls, making the regression minor. However, a deeper inefficiency is noted: files are being `lstat()`ed multiple times before `check_changes()` is even called, which is a more pressing performance concern. Both agree the proper fix is to make callers of `do_create_stash()` responsible for refreshing the index, eliminating the redundant refresh and avoiding multiple `preload_index()` calls. This refactor would also improve performance when there are actual changes to stash.

Open questions and loose ends: The redundant index refresh inefficiency is resolved in principle; the follow-up patch to implement the caller-responsibility refactor is planned and agreed upon. No other open questions or edge cases remain.

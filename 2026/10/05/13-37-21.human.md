This is a workflow demonstration for the proposed `git-bisect-rebase` script, part of an ongoing discussion about whether Git should include a helper for incremental rebase conflict resolution in `contrib/`. Alejandro Colomar provides a detailed, annotated shell session showing how the script is used to rebase a *tree of interdependent branches* in a specific order, addressing Phillip Wood’s earlier feedback about workflow design.

The session walks through rebasing three branches (A, B, and C) with complex dependencies, where conflicts must be resolved in a non-linear order. Colomar’s key argument is that a *multi-shot* approach—where the user manually invokes the script for each branch and can pause to inspect or adjust intermediate states—is essential for real-world workflows. This counters Phillip Wood’s proposal for a *single-shot* workflow (where `git rebase --continue` automatically advances to the next conflicting commit), which would break the demonstrated use case. The example also shows why Colomar prefers the multi-shot approach even for single branches, as it allows running `git range-diff` after each step to verify changes.

The demonstration reinforces the practical utility of `git-bisect-rebase` (now the consensus candidate for `contrib/` inclusion) and clarifies the requirements for any future integration into `git rebase` itself. The thread remains open on whether the project will accept the script in `contrib/` or pursue a built-in option, but this exchange narrows the design space by ruling out single-shot implementations for complex cases. The session is well-structured and persuasive, making a strong case for the flexibility of the current design.

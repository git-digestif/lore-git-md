Subject: Bug report: ZIP archive and fast-import date-handling inconsistencies
Series version: N/A (bug report, no patch series)
Originating author: Matthew E. Luallen
Thread type: bug report

Core problem or goal
Three date-handling bugs in Git’s ZIP archive generation and `git fast-import` logic:
1. ZIP legacy DOS date overflow: 1972 commit → 2100 timestamp in legacy field, breaking tools like UnZip.
2. ZIP extended timestamp wrap: 2106-02-07 commit → 1970 timestamp in extended field, causing silent data inconsistencies in UnZip’s update mode and cross-format inconsistencies with TAR.
3. `fast-import` strict validation gap: `--date-format=raw` accepts negative timestamps that `git fsck --strict` later rejects as `badDate`, with ISO rendering returning literal placeholders.

Current status
Reported; no maintainer decisions yet. Issues are confirmed via reproduction steps and real-world tool behavior observations. The discussion is converging toward **rejecting out-of-range timestamps** for ZIP export as the preferred solution, prioritizing correctness over tool compatibility. The `fast-import` negative timestamp issue remains open, with René Scharfe opposing rejection due to potential disruption of ancient record imports. No patches have been proposed, but the policy debate is narrowing.

Key technical details
- Files/subsystems: `archive-zip.c` (ZIP export), `fast-import.c` (import), date validation logic.
- Symbols: ZIP legacy DOS date field (hard limit: 1980–2107), ZIP extended timestamp field (four-byte Unix timestamp, max 2106-02-07), `validate_raw_date()` (uses `strtoul()`, silently accepts negative values), `git fsck --strict` date validation.
- Behavior:
  - ZIP legacy DOS date: Git currently overflows to 2100 for 1972 commits. René now advocates **rejection** (not clamping) to avoid tool compatibility risks, contrasting with his prior suggestion to clamp to 1980-01-01. Extraction remains correct (UnZip/bsdtar restore 1972 date), but metadata display is misleading (e.g., Python `ZipInfo.date_time` misreporting 1972 as 2100).
  - ZIP extended timestamp: Git wraps to 1970 for 2106-02-07+ commits, causing UnZip’s update mode to retain outdated content (e.g., 2025 files instead of 2106 files). René now proposes **rejection** (not clamping to 4294967295) to avoid silent misinterpretation, aligning with Matthew’s earlier lean.
  - `fast-import`: Accepts negative timestamps in `--date-format=raw` that `fsck` later rejects. René opposes stricter validation, arguing Git commit objects allow arbitrary decimal strings and `timestamp_t`’s unsigned nature is not immutable. Matthew still proposes rejection to align with `NEEDSWORK` comments.
- Test coverage: Reproduction steps provided (e.g., `git archive --format=zip` with specific commit dates); additional tool behavior examples (Python `ZipInfo`, UnZip, bsdtar) demonstrate real-world impact.
- Tool compatibility: UnZip (macOS) and bsdtar handle archives correctly for extraction, but Python’s `ZipInfo.date_time` misreports dates, and UnZip’s update mode behaves unexpectedly with post-2106 timestamps. `zip(1)` clamps to 1980, `tar` uses extended headers.

Open questions and loose ends
- Policy:
  - **ZIP export**: Should out-of-range timestamps be rejected (correctness) or clamped (tool compatibility)? Rejection is now the leading proposal, but no consensus yet.
  - **`fast-import`**: Should negative timestamps in `--date-format=raw` be rejected (Matthew’s proposal) or accepted (René’s preference, citing Git’s existing flexibility with decimal strings)?
- Implementation:
  - How to handle negative timestamps in `fast-import` if rejection is chosen (e.g., stricter `strtoul` validation or explicit checks)?
  - Should rejection behavior be configurable (e.g., `--format=zip --reject-dates`)?
  - Is an incremental fix (e.g., `fast-import` negative timestamp rejection) preferable to a broader solution, or should ZIP export and `fast-import` be addressed together?

Participant positions

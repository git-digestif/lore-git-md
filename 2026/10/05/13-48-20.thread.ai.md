Subject: Bug report: ZIP archive and fast-import date-handling inconsistencies

Core problem or goal
Three date-handling bugs in Git’s ZIP archive generation and `git fast-import` logic:
1. ZIP legacy DOS date overflow: 1972 commit → 2100 timestamp in legacy field, breaking tools like UnZip.
2. ZIP extended timestamp wrap: 2106-02-07 commit → 1970 timestamp in extended field, causing silent data inconsistencies in UnZip’s update mode and cross-format inconsistencies with TAR.
3. `fast-import` strict validation gap: `--date-format=raw` accepts negative timestamps that `git fsck --strict` later rejects as `badDate`, with ISO rendering returning literal placeholders.

Current status
- **ZIP extended timestamp wrap (bug #2)**: **Resolved by patch** from René Scharfe, now **test-infrastructure fixed** by Matthew E. Luallen. The patch omits the Extended Timestamp (UT) extra field when the commit time exceeds 32-bit signed integer range (`> 0x7fffffff`), preventing silent timestamp wrap. This aligns with the thread’s converging preference for **rejection** (omission) over clamping, prioritizing correctness. The patch is narrowly scoped to the UT field and includes test coverage in `t/t5004-archive-corner-cases.sh` with corrected prerequisites (`TIME_T_IS_64BIT` instead of `TIME_IS_64BIT`). The tests now pass on x86-64 and are correctly skipped on 32-bit platforms where `zipinfo(1)` lacks UT field support or is absent. The fix is **ready for integration**.
- **ZIP legacy DOS date overflow (bug #1)**: Still **open**. No patches proposed; policy debate continues between rejection (René’s updated position) and clamping (prior suggestion). René advocates rejection as the "most honest option," arguing it could motivate adoption of more robust formats (e.g., TAR) or a proper ZIP extension.
- **`fast-import` negative timestamp validation (bug #3)**: Still **open**. René opposes stricter validation, citing Git’s existing flexibility with decimal strings in commit objects and the non-immutable nature of `timestamp_t`. Matthew proposes rejection to align with `NEEDSWORK` comments, but no consensus yet.
No maintainer decisions on bugs #1 or #3. The ZIP extended timestamp fix is the only concrete progress.

Key technical details
- Files/subsystems: `archive-zip.c` (ZIP export), `fast-import.c` (import), date validation logic, `t/t5004-archive-corner-cases.sh` (tests).
- Symbols:
  - **ZIP export**: `zip_extra_mtime` (new `strbuf` for UT field), `TIME_T_IS_64BIT` (corrected test prerequisite for 32-bit platforms), `ZIPINFO_UT_EXTRA` (original test prerequisite, now removed).
  - **ZIP legacy DOS date**: Hard limit 1980–2107; Git currently overflows to 2100 for 1972 commits. René now advocates **rejection** (not clamping) to avoid tool compatibility risks (e.g., Python `ZipInfo.date_time` misreporting 1972 as 2100).
  - **ZIP extended timestamp**: Four-byte Unix timestamp (max 2106-02-07). Git now **omits the UT field** for out-of-range values (`> 0x7fffffff`), preventing wrap to 1970. This avoids silent misinterpretation in UnZip’s update mode (e.g., retaining 2025 files instead of 2106 files).
  - **`fast-import`**: `validate_raw_date()` uses `strtoul()`, silently accepting negative values. `git fsck --strict` later rejects these as `badDate`. René opposes stricter validation; Matthew proposes rejection to align with `NEEDSWORK` comments.
- Behavior:
  - **ZIP legacy DOS date**: Extraction remains correct (UnZip/bsdtar restore 1972 date), but metadata display is misleading (e.g., Python `ZipInfo.date_time` shows 2100 for 1972).
  - **ZIP extended timestamp**: Omission of UT field for out-of-range values avoids silent misinterpretation in UnZip’s update mode. Tools like `zipinfo(1)` and `bsdtar` handle archives correctly, but Python’s `ZipInfo` may still misreport dates if the legacy DOS field overflows.
  - **`fast-import`**: Negative timestamps in `--date-format=raw` are accepted but later rejected by `fsck`, creating a validation gap.
- Test coverage: Reproduction steps provided for all bugs; René’s patch adds tests for UT field omission in `t/t5004-archive-corner-cases.sh`. The tests now use `TIME_T_IS_64BIT` to skip checks on 32-bit platforms where `zipinfo(1)` lacks UT field support. Tool behavior examples (Python `ZipInfo`, UnZip, bsdtar) demonstrate real-world impact.
- Tool compatibility: UnZip (macOS) and bsdtar handle archives correctly for extraction, but Python’s `ZipInfo.date_time` misreports dates, and UnZip’s update mode behaves unexpectedly with post-2106 timestamps. `zip(1)` clamps to 1980, `tar` uses extended headers.

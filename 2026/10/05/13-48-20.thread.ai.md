Subject: Bug report: ZIP archive and fast-import date-handling inconsistencies
Series version: N/A (bug report, no patch series)
Originating author: Matthew E. Luallen
Thread type: bug report

Core problem or goal
Three date-handling bugs in Git's ZIP archive generation and `git fast-import` logic:
1. ZIP legacy DOS date overflow: 1972 commit -> 2100 timestamp in legacy field, breaking tools like UnZip.
2. ZIP extended timestamp wrap: 2106-02-07 commit -> 1970 timestamp in extended field, causing silent data inconsistencies in UnZip's update mode and cross-format inconsistencies with TAR.
3. `fast-import` strict validation gap: `--date-format=raw` accepts negative timestamps that `git fsck --strict` later rejects as `badDate`, with ISO rendering returning literal placeholders.

Current status
- **ZIP extended timestamp wrap (bug #2)**: **Resolved by patch and test-infrastructure fix**. René Scharfe's v2 patch omits the Extended Timestamp (UT) extra field when the commit time exceeds 32-bit signed integer range (`> 0x7fffffff`), preventing silent timestamp wrap. The patch incorporates Matthew E. Luallen's test prerequisite fix (`TIME_T_IS_64BIT` instead of `TIME_IS_64BIT`), ensuring tests pass on 64-bit platforms and are skipped on 32-bit systems where `zipinfo(1)` lacks UT field support or is missing. Junio C Hamano confirmed the test fix is technically sound, resolving CI failures on 32-bit platforms (Ubuntu 20.02 i386, Debian i386). The fix is **ready for integration**, with no remaining technical blockers. René notes that while `time_t` is a pragmatic choice for now, future refactoring could eliminate its use in archive logic. Matthew reports a **newly discovered time-zone issue** with post-2038 dates when using `unzip -u`, but this is unrelated to the UT field omission and can be tracked separately.
- **ZIP legacy DOS date overflow (bug #1)**: **Open and expanded**. No patches proposed; policy debate continues between rejection (René's updated position) and clamping (prior suggestion). René advocates rejection as the "most honest option," arguing it could motivate adoption of more robust formats (e.g., TAR) or a proper ZIP extension. A **newly identified bug in `dos_time()`** surfaces when timestamps exceed 32-bit range (`@2147483648 +0000`), producing invalid timestamps (`18446744071562067968`) instead of clamping or rejecting. This bug is **separate from the UT field omission patch** but directly impacts 32-bit platforms, reinforcing the risks of silent overflow in the legacy DOS date field. Junio's `#leftoverbits` note suggests auditing `timestamp_t` coercion into `time_t` for external formats to detect truncation risks.
- **`fast-import` negative timestamp validation (bug #3)**: Still **open**, but now has a volunteer commitment. Aniket Gupta has announced he will send a patch to make the plain `raw` date format reject timestamps that `git fsck --strict` would flag as `badDate`, while leaving the `raw-permissive` format unchanged. No patch has been sent yet; implementation details (e.g., exact rejection logic or range checks) are not yet specified.

Key technical details
- Files/subsystems: `archive-zip.c` (ZIP export), `fast-import.c` (import), `date.c` (`dos_time()` function), date validation logic, `t/t5004-archive-corner-cases.sh` (tests).
- Symbols:
  - **ZIP export**: `zip_extra_mtime` (new `strbuf` for UT field), `TIME_T_IS_64BIT` (corrected test prerequisite for 32-bit platforms), `dos_time()` (legacy DOS date conversion function, now identified as buggy for timestamps `> 0x7fffffff`).
  - **ZIP legacy DOS date**: Hard limit 1980-2107; Git currently overflows to 2100 for 1972 commits and produces invalid timestamps for values `> 0x7fffffff` (e.g., `@2147483648 +0000` -> `18446744071562067968`). René advocates **rejection** (not clamping) to avoid tool compatibility risks (e.g., Python `ZipInfo.date_time` misreporting 1972 as 2100).
  - **ZIP extended timestamp**: Four-byte Unix timestamp (max 2106-02-07). Git now **omits the UT field** for out-of-range values (`> 0x7fffffff`), preventing wrap to 1970. This avoids silent misinterpretation in UnZip's update mode (e.g., retaining 2025 files instead of 2106 files).
  - **`fast-import`**: `validate_raw_date()` uses `strtoul()`, silently accepting negative values. `git fsck --strict` later rejects these as `badDate`. René opposes stricter validation; Matthew proposes rejection to align with `NEEDSWORK` comments; Aniket Gupta has volunteered to implement stricter validation for the `raw` format while preserving `raw-permissive`.

  - Should out-of-range timestamps be rejected (René's updated position) or clamped (prior suggestion)? Rejection is now the leading proposal, but no consensus yet.
  - If rejected, should the behavior be configurable (e.g., `--format=zip --reject-dates`)?
  - How to resolve the newly identified `dos_time()` bug on 32-bit platforms? Options include fixing `dos_time()` to reject out-of-range timestamps, clamping values safely (e.g., to 1980 or 2107), or adjusting test prerequisites to skip problematic cases on 32-bit platforms.
  - Junio's `#leftoverbits` note suggests auditing `timestamp_t` coercion into `time_t` for external formats to detect truncation risks.
- **`fast-import` negative timestamps (bug #3)**:
  - Should negative timestamps in `--date-format=raw` be rejected (Matthew's proposal, now supported by Aniket Gupta's volunteer commitment) or accepted (René's preference)?
  - Aniket Gupta plans to make `raw` reject values that `fsck --strict` would flag as `badDate` while leaving `raw-permissive` unchanged; exact implementation is pending.
- **Implementation scope**:
  - Should the ZIP legacy DOS date and `fast-import` issues be addressed together, or is incremental progress acceptable?
  - Should the `dos_time()` bug be fixed as part of the UT field omission patch, or treated as a separate issue?
- **Newly discovered time-zone issue**: Matthew reports a time-zone issue with post-2038 dates when using `unzip -u`, unrelated to the UT field omission.

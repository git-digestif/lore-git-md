Subject: Bug report: ZIP archive and fast-import date-handling inconsistencies
Series version: N/A (bug report, no patch series)
Originating author: Matthew E. Luallen
Thread type: bug report

Core problem or goal
Three date-handling bugs in Git’s ZIP archive generation and `git fast-import` logic:
1. ZIP legacy DOS date overflow: 1972 commit → 2100 timestamp in legacy field, breaking tools like UnZip.
2. ZIP extended timestamp wrap: 2106-02-07 commit → 1970 timestamp in extended field, causing silent data inconsistencies in UnZip’s update mode and cross-format inconsistencies with TAR.
3. `fast-import` strict validation gap: `--date-format=raw` accepts negative timestamps that `git fsck --strict` later rejects as `badDate`, with ISO rendering returning literal placeholders.

Current status
Reported; no maintainer decisions yet. Issues are confirmed via reproduction steps and real-world tool behavior observations. René Scharfe’s review engages with technical constraints and trade-offs, and Matthew E. Luallen has provided additional tool-specific fallout details (Python `ZipInfo.date_time` misreporting, UnZip update mode retaining outdated content). The discussion is narrowing toward rejection of out-of-range timestamps as a potential solution, with the `fast-import` negative timestamp fix identified as the most actionable near-term change.

Key technical details
- Files/subsystems: `archive-zip.c` (ZIP export), `fast-import.c` (import), date validation logic.
- Symbols: ZIP legacy DOS date field (hard limit: 1980–2107), ZIP extended timestamp field (four-byte Unix timestamp, max 2106-02-07), `validate_raw_date()` (uses `strtoul()`, silently accepts negative values), `git fsck --strict` date validation.
- Behavior:
  - ZIP legacy DOS date: Git currently overflows to 2100 for 1972 commits; René suggests clamping to 1980-01-01 (matching `zip(1)`), but Matthew’s tool observations (Python `ZipInfo.date_time` misreporting 1972 as 2100) highlight compatibility risks. Extraction remains correct (UnZip/bsdtar restore 1972 date), but metadata display is misleading.
  - ZIP extended timestamp: Git wraps to 1970 for 2106-02-07+ commits, causing UnZip’s update mode to retain outdated content (e.g., 2025 files instead of 2106 files) due to the wrapped timestamp being older than the existing archive’s timestamp. René proposes clamping to 4294967295 (aligning with TAR), while Matthew leans toward rejection to avoid silent misinterpretation.
  - `fast-import`: Accepts negative timestamps in `--date-format=raw` that `fsck` later rejects; both René and Matthew agree stricter validation is needed (references `NEEDSWORK` comments in code).
- Test coverage: Reproduction steps provided (e.g., `git archive --format=zip` with specific commit dates); additional tool behavior examples (Python `ZipInfo`, UnZip, bsdtar) demonstrate real-world impact.
- Tool compatibility: UnZip (macOS) and bsdtar handle archives correctly for extraction, but Python’s `ZipInfo.date_time` misreports dates, and UnZip’s update mode behaves unexpectedly with post-2106 timestamps. `zip(1)` clamps to 1980, `tar` uses extended headers.

Open questions and loose ends
- Policy:
  - Should ZIP legacy DOS dates clamp to 1980-01-01 (tool compatibility) or reject out-of-range values (correctness)?
  - Should ZIP extended timestamps clamp to 2106-02-07 (consistency with TAR) or reject post-2106 values (avoiding silent misinterpretation, e.g., UnZip update mode retaining outdated content)?
  - Should `fast-import` reject negative timestamps in `--date-format=raw` mode, even if it breaks existing workflows?
- Implementation:
  - How to handle negative timestamps in `fast-import` (e.g., stricter `strtoul` validation or explicit checks)?
  - Should clamping/rejection behavior be configurable (e.g., via `--format=zip --clamp-dates` or `--reject-dates`)?
  - Is an incremental fix (e.g., `fast-import` negative timestamp rejection) preferable to a broader solution?

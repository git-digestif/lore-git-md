Subject: Bug report: ZIP archive and fast-import date-handling inconsistencies
Series version: N/A (bug report, no patch series)
Originating author: Matthew E. Luallen
Thread type: bug report

Core problem or goal
Three date-handling bugs in Git’s ZIP archive generation and `git fast-import` logic:
1. ZIP legacy DOS date overflow: 1972 commit → 2100 timestamp in legacy field, breaking tools like UnZip.
2. ZIP extended timestamp wrap: 2106-02-07 commit → 1970 timestamp in extended field, breaking cross-format consistency with TAR.
3. `fast-import` strict validation gap: `--date-format=raw` accepts negative timestamps that `git fsck --strict` later rejects as `badDate`, with ISO rendering returning literal placeholders.

Current status
Reported; no maintainer decisions yet. Issues are confirmed via reproduction steps in the report. René Scharfe’s review engages with technical constraints and trade-offs but does not propose a specific fix.

Key technical details
- Files/subsystems: `archive-zip.c` (ZIP export), `fast-import.c` (import), date validation logic.
- Symbols: ZIP legacy DOS date field (hard limit: 1980–2107), ZIP extended timestamp field (four-byte Unix timestamp, max 2106-02-07), `validate_raw_date()` (uses `strtoul()`, silently accepts negative values), `git fsck --strict` date validation.
- Behavior:
  - ZIP legacy DOS date: Git currently overflows to 2100 for 1972 commits; René suggests clamping to 1980-01-01 (matching `zip(1)`).
  - ZIP extended timestamp: Git wraps to 1970 for 2106-02-07+ commits; René proposes clamping to 4294967295 (aligning with TAR).
  - `fast-import`: Accepts negative timestamps in `--date-format=raw` that `fsck` later rejects; René notes `NEEDSWORK` comments in code.
- Test coverage: Reproduction steps provided (e.g., `git archive --format=zip` with specific commit dates).
- Tool compatibility: UnZip (macOS) relies on legacy DOS dates; `zip(1)` clamps to 1980, `tar` uses extended headers.

Open questions and loose ends
- Policy:
  - Should ZIP legacy DOS dates clamp to 1980-01-01 (tool compatibility) or preserve overflow (correctness)?
  - Should ZIP extended timestamps clamp to 2106-02-07 (consistency with TAR) or wrap to 1970 (compatibility with `zip(1)`)?
  - Should `fast-import` reject timestamps that `fsck` considers invalid, even in permissive mode?
- Implementation:
  - How to handle negative timestamps in `fast-import` (e.g., stricter `strtoul` validation or explicit checks)?
  - Should clamping behavior be configurable (e.g., via `--format=zip --clamp-dates`)?

Participant positions
- Matthew E. Luallen: Reported bugs with detailed reproduction steps and real-world impact (e.g., macOS UnZip behavior). No policy position yet.
- René Scharfe: **Substantive review**:
  - ZIP legacy DOS date: Clamp to 1980-01-01 (like `zip(1)`), but questions tool reliance on DOS dates.
  - ZIP extended timestamp: Clamp to 4294967295 (like TAR), not wrap to 1970.
  - `fast-import`: Stricter validation needed (references `NEEDSWORK` comments); negative timestamps should be rejected.

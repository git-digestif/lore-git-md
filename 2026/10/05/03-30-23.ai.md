This is a **design discussion** continuing the RFC thread on the "limbo" object-format state for new Git repositories. Jeff King (Peff) responds to Brian M. Carlson’s feedback, refining the proposal to use a dual-format advertisement (`object-format=sha256` and `alt-object-format=sha1`) instead of the earlier `magic-limbo` capability. This approach eliminates the need for a separate limbo signal while explicitly declaring support for both hash algorithms, addressing Brian’s concern about future compatibility with additional hash functions.

Peff clarifies that he did not intend to delay Git 3.0’s SHA-256-by-default transition, noting the feature’s feasibility within the remaining release cycle. He leaves the door open for others (e.g., Scott) to implement it but does not commit to doing so himself. On policy enforcement, Peff agrees that Git should provide a config flag to mark the limbo state—set by `git init` and respected by `receive-pack`—but emphasizes that the feature should *not* be enabled by default. He views it as a building block for forges (like GitHub) to reduce friction, with additional forge-specific work likely needed on top.

The discussion now centers on two key technical details: (1) whether the dual-format advertisement will work reliably with modern clients (2.41+), given the 2023 fix for multi-valued capability parsing, and (2) how to handle non-push repository modifications (e.g., via APIs) without a predefined hash algorithm. The thread remains in the conceptual stage, with no implementation yet, but the refined proposal narrows the scope to protocol-level changes and config-based state management.

This is the second patch in a two-part series that optimizes how Git writes the commit-graph after fetches in large repositories. The series introduces an incremental write strategy for `fetch.writeCommitGraph`, avoiding the current inefficiency of rescanning all reachable refs after every fetch. This patch implements the core logic: it tracks which refs were updated during a fetch and, when possible, writes only the newly fetched commits to the commit-graph, falling back to a full scan only when necessary (e.g., no existing graph or multi-remote fetches).

The patch is well-motivated and addresses a real performance bottleneck. The author, Kristofer Karlsson, has already addressed all substantive review feedback from Patrick Steinhardt, and the remaining changes are minor: adding benchmark numbers to the commit message, a short comment explaining the ref status filtering logic, and a test case for shallow refs. The incremental write strategy relies on split-mode commit-graphs (`COMMIT_GRAPH_WRITE_SPLIT`) to ensure additive updates, and the patch includes thorough test coverage for incremental writes, no-op fetches, and fallback cases.

This is a targeted optimization within the commit-graph subsystem, touching `builtin/fetch.c`, `commit-graph.c`, and `t/t5510-fetch.sh`. The performance improvement is substantial: in a synthetic test with 200K packed refs, incremental writes reduce the `fetch/write-commit-graph` time from ~360ms to ~9ms for a single ref update. The series is uncontested and appears ready for a reroll, after which it will likely be a strong candidate for merging. If you work with large repositories or care about fetch performance, this patch is worth tracking.

This is a design discussion about how to extend `git stash create` beyond the minimal `-u`/`-a` patch that was previously proposed. The author, Kazumasa Shigeta, acknowledges that the original patch was too narrowly scoped and now outlines three broader directions for exposing more of the stash-creation functionality while preserving backward compatibility with the existing `git stash create <message>` grammar.

The core issue is that `git stash create` currently treats all command-line arguments after the subcommand as a message, which conflicts with the need to support additional options (like `-p` for patch mode or pathspec filtering) without breaking scripts that rely on the current behavior. Shigeta proposes three approaches: (1) extend `stash create` with careful option parsing to avoid ambiguity, (2) introduce a new subcommand (e.g., `stash create-full`) with a more flexible grammar, or (3) add a `--create-only` flag to `git stash push` to reuse its existing option handling. Each option has trade-offs around compatibility, interface complexity, and long-term maintenance.

The email is a direct response to Junio C Hamano’s feedback, which questioned the original patch’s scope and commit message clarity. Shigeta’s uncertainty about which direction to pursue suggests this is now an RFC-style discussion rather than a ready-to-merge patch. The thread remains under active review, with no technical implementation yet proposed for the broader changes. If this moves forward, it will likely require a new patch series addressing the chosen design.

This is a documentation-driven design discussion about improving Git’s conflict-resolution user experience. Julia Evans responds to Junio C Hamano’s question about whether minor code changes—such as updating conflict markers or rewording `git status` output—should be considered to make the new `gitmergeconflicts(7)` guide clearer and more intuitive.

Julia agrees in principle with the idea of "documentation-driven development": if the documentation feels awkward or confusing, the code should be adjusted to match a better user experience. She already has local branches with advice-system changes in other areas, signaling she is open to small code tweaks that improve clarity. However, she does not yet have concrete proposals for `git status` and instead offers a brainstormed critique of its current output during conflicts. Her observations highlight inconsistencies and unhelpful advice (e.g., suggesting `git pull` when it is not allowed, redundant `git add` prompts, and inconsistent terminology like "unmerged" vs. "conflicted" or "fix conflicts" vs. "mark resolution"). Some of these are surface-level wording issues, while others would require conditional logic in the advice system, making them more complex.

On the "upside down" confusion during rebases, Julia acknowledges Junio’s explanation—that the issue stems from how users conceptualize `rebase` rather than the terms "ours" and "theirs"—but notes that knowing the technical rationale has never helped her remember which is which. She expresses skepticism about telling users to adopt the "right mindset," preferring to respect diverse perspectives and focus on making the interface more intuitive regardless of mental model. This exchange does not resolve the design questions but establishes that Julia is open to follow-up patches targeting code changes if they meaningfully improve the user experience. The discussion remains exploratory, with no specific changes proposed yet.

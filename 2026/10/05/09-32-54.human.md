This is a strategic counterproposal to the Git 3.0 SHA-256 transition plan, authored by Scott Chacon in response to Brian M. Carlson’s rejection of the earlier RFC patch series. The email argues that switching the default object format to SHA-256 in Git 3.0 is premature, disruptive, and unnecessary for addressing the core security concerns around SHA-1.

Chacon’s central claim is that the SHA-1 deprecation debate conflates two distinct problems: **content-addressing** (where SHA-1’s one-way hashing is sufficient) and **signature integrity** (where SHA-1’s collision resistance is inadequate). He proposes that the latter can be solved more simply by embedding SHA-256 tree digests in signed commits/tags (as in his RFC series), while leaving the default object format as SHA-1. This would avoid the ecosystem-wide disruption of a default switch while still meeting regulatory requirements for signature algorithms.

The email highlights several practical concerns about the Git 3.0 plan:
- **Lack of real-world testing**: Major forges (GitHub, Bitbucket, Gerrit) either lack SHA-256 support or offer it only in experimental form, with no time for feedback before the March 2027 deadline.
- **Incomplete interoperability work**: The proposed `compatObjectFormat` and pack index v3 features are not yet usable, and key components (e.g., submodule handling) remain unimplemented.
- **Backwards compatibility risks**: Hardcoded SHA-1 assumptions in scripts, hooks, and tools (e.g., Eclipse) will break silently, creating confusion for users who are unaware of the change.

Chacon also challenges Carlson’s framing of the problem as urgent, arguing that SHA-1’s weaknesses are overstated for Git’s primary use case (content-addressing) and that security researchers can already use SHA-256 repositories today. He suggests delaying the default switch to Git 4.0 or later, allowing time for forges to implement and test interoperability features.

The tone is direct but constructive, positioning the tree-digest RFC as a pragmatic alternative rather than a rejection of SHA-256 entirely. The email is likely to reignite debate about the Git 3.0 timeline, particularly around whether the project should prioritize regulatory compliance over ecosystem stability. Key stakeholders (Junio, Taylor Blau, and forge maintainers) may weigh in on whether the interoperability work can realistically be completed in time, or if a phased approach (e.g., opt-in SHA-256 in 3.0) is warranted.

This is a substantive design discussion in the ongoing `git stash create` feature thread. Phillip Wood responds to Kazumasa Shigeta’s proposal to extend the command’s functionality, weighing in on which options from `git stash push` would make sense for `stash create` and how to handle backward compatibility.

Phillip argues that `stash create` is primarily a scripting interface, so interactive options like `--patch` (which can fail to clear stashed changes from the worktree) are poor fits. He sees value in exposing `-u`/`--include-untracked` and `-a`/`--all` for scripts but questions whether pathspec support is necessary, suggesting `--pathspec-from-file` might suffice if it is. He endorses `PARSE_OPT_STOP_AT_NON_OPTION` as a reasonable way to preserve the existing positional message grammar, noting that messages starting with `-` are rare in practice. Adding `-m`/`--message` to match other Git commands would also improve consistency.

The review is substantive: Phillip engages with the design trade-offs, considers edge cases (like the `--patch` failure mode he documents in detail), and proposes alternatives. His feedback is constructive and directly addresses the open questions in the thread, particularly the scope of the feature and how to balance backward compatibility with new functionality. The discussion remains active, with no clear consensus yet on which of the three proposed directions (extending `create`, adding a new subcommand, or adding `--create-only` to `push`) is best.

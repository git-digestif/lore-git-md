This is a follow-up in the ongoing bug report about Git’s ZIP timestamp handling and `fast-import` date validation. Matthew E. Luallen responds to René Scharfe’s review with additional real-world observations and a proposal for how to address the issues.

Matthew clarifies that while tools like UnZip and bsdtar correctly restore file content from ZIP archives with pre-1980 or post-2106 timestamps, some downstream consumers (like Python’s `ZipInfo.date_time`) misinterpret the legacy DOS timestamp field, leading to incorrect metadata display. He also notes a practical consequence of the 2106-to-1970 wrap: in "update mode," UnZip may retain older file content when it encounters a timestamp that appears to be from 1970, though this does not create a security issue.

On the policy question René raised—whether to clamp or reject out-of-range timestamps—Matthew leans toward rejection, arguing it would be safer for downstream tools. He suggests starting with a smaller, less controversial change: rejecting negative timestamps in `fast-import`’s `--date-format=raw` mode, which would align with `git fsck --strict`’s validation. This could serve as a first step toward stricter date handling without immediately tackling the more complex ZIP timestamp issues.

The attached guidance document (not included in the email text) appears to offer recommendations for downstream developers on how to handle Git-generated ZIP timestamps safely, framing this as a complement to the eventual bug fixes rather than a security advisory. The tone remains constructive and focused on practical solutions.

The thread is still in the discussion phase, with no patches proposed yet. Matthew’s input adds real-world context to the trade-offs René outlined, but the core questions—whether to clamp or reject, and how to handle negative timestamps—remain open. If a patch emerges, it will likely start with the `fast-import` validation gap, as that seems the least controversial and most clearly aligned with existing Git behavior.

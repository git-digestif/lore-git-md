This is a **bugfix follow-up** in the ongoing thread about packfile corruption from stale delta base cache entries. Patrick Steinhardt responds to Jeff King’s (Peff) suggestion to use AddressSanitizer (ASan) to detect the bug as a user-after-free, clarifying why ASan does not catch the issue in its current form.

The core technical point: the bug does not involve dereferencing a freed `packed_git` pointer, so ASan’s memory-safety checks do not trigger. Instead, the corruption occurs because the **cache key** (a `struct packed_git *`) is reused when a new packfile occupies the same memory address as a previously freed one. The cache’s hashmap lookup then returns the wrong delta base data for the new pack, leading to incorrect object reconstruction. ASan’s behavior—allocating unique addresses for freed memory—actually *prevents* the bug from manifesting, making it unsuitable as a direct test mechanism.

This exchange refines the thread’s understanding of the bug’s nature. While Peff’s framing as a "user-after-free" is technically accurate (the cache holds a dangling pointer), the issue is more subtle: it is a **logical corruption** caused by pointer reuse, not a memory-safety violation detectable by ASan. The existing test’s reliance on glibc’s allocator behavior remains the only known way to reproduce the bug deterministically, though it is platform-dependent. No new patch versions or test proposals have been introduced here; the discussion is now focused on whether the current test’s limitations are acceptable or if an alternative approach (e.g., mocking allocator behavior) is needed. The core fix itself remains uncontested.

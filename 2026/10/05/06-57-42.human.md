This is a design discussion about Git's behavior with shallow clones and destructive operations. Patrick Steinhardt, a core contributor, responds to Sphinx's original question with a clear technical perspective.

Steinhardt confirms that Git's current behavior—allowing operations like `git revert` or `git restore` to produce an empty working tree in a shallow clone—is indeed surprising but intentional. The root cause is how shallow clones rewrite boundary commits (like commit B in the example) to appear as root commits without parents. Reverting such a commit thus removes all tracked files, which can catch users off guard.

He suggests that Git *should* improve here, proposing at minimum a warning (and possibly a default refusal) when users attempt to edit shallow boundary commits. This would align with a recent discussion about forbidding `git commit --amend` on shallow commits. Steinhardt argues that such edits are almost always unintended and could be safeguarded without breaking legitimate use cases (via an override flag).

On the broader question of Git's safety boundaries, Steinhardt clarifies that while Git avoids losing *untracked* data, it does not treat committed data as sacrosanct—users can always restore it. There are currently no warnings for empty-tree transitions, and he does not advocate adding them generally. However, the shallow boundary case is an exception where a safeguard would be justified.

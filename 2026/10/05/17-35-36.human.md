This is a follow-up in the ongoing design discussion about whether Git should warn users when destructive operations (like `git revert`) on shallow clones produce empty working trees. The author, Sphinx, acknowledges Patrick Steinhardt’s earlier explanation that the real issue isn’t the empty tree itself, but the surprising behavior caused by shallow boundary commits being treated as root commits during traversal.

Sphinx now clearly frames the core question: should Git add safeguards (warnings or refusals) for editing shallow boundary commits by default, or is the current behavior—no intervention—intentional? This email doesn’t propose a solution but reinforces the focus on Steinhardt’s earlier argument that the current behavior is likely unintended in most cases and could benefit from user-facing protections. The tone is appreciative and clarifies the thread’s direction, making it easier for readers to see what’s still unresolved: whether maintainers will view this as a justified safeguard or an overreach. No new technical details or objections are introduced.

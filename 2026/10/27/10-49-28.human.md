This is a coding-style and API design discussion, continuing the thread about officially permitting compound literals in Git's C code. The original documentation patch (updating `CodingGuidelines`) has already been accepted and is ready for merging to `next`, but this follow-up exchange between Phillip Wood and Patrick Steinhardt explores broader implications and next steps.

The conversation clarifies two long-standing compatibility blockers for C99 adoption: MinGW's lack of support for the `%z`/`%zu` format specifiers and IBM xlc's lack of support for designated initializers like `.a.b = c`. Phillip Wood notes that recent changes to MinGW's UCRT64 runtime *might* have improved support for format specifiers, but this remains unconfirmed. The discussion then shifts to whether Git should explore C11 features like `static_assert()` and `_Generic` macros, though no concrete proposals emerge yet.

The most substantive part of the exchange is Patrick Steinhardt's proposal to unify Git's dual initialization patterns (e.g., `STRBUF_INIT` macros vs. `strbuf_init()` functions) by redefining macros as compound literals. This would allow delayed initialization (e.g., `struct strbuf buf; buf = STRBUF_INIT;`) and could eventually make functions like `strbuf_init()` redundant. Phillip Wood endorses the idea in principle, noting that most callers of `strbuf_init()` pass `0` as the size parameter anyway, suggesting the current API may be over-engineered. Both agree this should be an incremental change rather than a sweeping rewrite.

The tone remains collaborative and exploratory, with no controversy or pushback.

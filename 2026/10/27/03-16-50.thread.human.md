This thread is about an RFC patch series from Pablo Sabater that removes the 10,000-OID limit in `git cat-file --remote-object-info` by batching requests internally. The goal is to improve performance for large metadata queries—400,000 OIDs now complete in 1.82 seconds instead of 5.86 seconds under the old limit—while also addressing server-side resource exhaustion risks by proposing a server-advertised OID limit via a new capability.

The series is still under review as an RFC, with no merge status reported. It consists of three patches: (1) refactoring to extract transport ownership, (2) implementing internal batching, and (3) adding the `--remote-max-batch` CLI option (default: 50,000 OIDs). Junio C Hamano has reviewed the first patch and the cover letter, requesting a clearer error message for the "smart options required" condition and explicit documentation of backwards-compatibility implications. Pablo has now addressed the error message concern by proposing a more user-friendly alternative: "object-info is not supported on bundles," which directly explains the failure without jargon. This resolves the only concrete critique Junio raised in his review of patch 1.

The technical details include unlimited OIDs accepted via internal batching (50,000-OID chunks by default, configurable via `--remote-max-batch`), connection reuse between batches, and a handshake performed once per command. The series touches `builtin/cat-file.c`, `transport-helper.c`, `transport.c`, and adds a new test script. Open questions remain about whether to implement the server-side OID limit, how to advertise it (proposed as a new capability during handshake), and whether the client should die or silently clamp if the user’s batch size exceeds the server’s limit. Junio has validated Pablo’s concern about server resource exhaustion as a legitimate design consideration, framing it as part of the collaborative review process. The thread is still in the design phase, with next steps likely involving refining the server-side limit proposal before further implementation.

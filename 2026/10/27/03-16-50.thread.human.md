This thread is an RFC patch series by Pablo Sabater that introduces batching to `git cat-file --remote-object-info`, removing the current 10k OID limit. The goal is to improve performance for large metadata queries—testing shows a 400k OID query now completes in 1.82s instead of 5.86s. The series is now complete with three patches: (1) transport ownership refactoring, (2) internal batching logic, and (3) the `--remote-max-batch` option (default: 50k OIDs).

Junio C Hamano reviewed the first patch and cover letter, endorsing the refactoring but requesting a clearer error message and explicit documentation of backwards-compatibility implications. The series is under review, with GitHub CI passing, but no merge status reported. Pablo’s latest email addresses Junio’s compatibility concern, confirming the changes are client-side only and that servers already handle variable request sizes. However, he now raises a new issue: the lack of a server-side OID limit could allow clients to send arbitrarily large requests, risking resource exhaustion. He proposes a server-side cap, advertised via a new capability during handshake, with a minimum of 10k to avoid breaking older clients. The client would either fail or clamp its batch size to the server’s limit, with the default 50k ideally matching the server’s minimum.

The thread is now focused on whether to implement this server-side cap and how to advertise it. The compatibility question is reframed as a security concern, and the next steps will likely involve design decisions rather than code changes. Key open questions include the server-side limit’s value, how to handle mismatches between client and server limits, and whether the 50k default is appropriate for all use cases. Junio’s feedback remains the most substantive so far, while Pablo has advanced the discussion by identifying a critical edge case.

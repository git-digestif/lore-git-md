This is the final patch in Patrick Steinhardt’s **v4 object storage extension series**, which teaches `git submodule` to propagate the `--object-storage-format=` option. The series as a whole introduces a pluggable object database backend mechanism (`extensions.objectStorage`), modeled after the existing ref storage extension, and this patch ensures submodules inherit the parent repository’s object storage configuration.

The patch wires up `--object-storage-format=` for `git submodule add` and `git submodule update`, mirroring the behavior already implemented for `--ref-storage-format=`. When a submodule is added or updated, the parent repository’s object storage *type* (e.g., `files`) is passed to the submodule, but the *payload* (e.g., `objs` in `files://objs`) is deliberately stripped. This matches the ref storage backend’s design and is a conscious choice for consistency, though it may attract discussion about whether payloads should be preserved for debugging or flexibility.

The implementation is straightforward: the patch extends the `module_clone_data`, `update_data`, and `add_data` structs in `builtin/submodule--helper.c` to include an `object_storage_format` field, updates the command-line parsing to accept `--object-storage-format=`, and propagates the format to submodules via `git clone`’s `--object-storage-format=` option. The shell script wrapper (`git-submodule.sh`) is updated to pass the option through, and documentation is added to `git-submodule.adoc` to describe the new flag.

Tests in the new `t/t7427-submodule-object-storage-format.sh` verify that submodules inherit the parent’s object storage *type* (e.g., `files`) but reject payloads (e.g., `files://objs`), ensuring consistency with the ref storage backend. The tests also cover error cases (invalid formats, payload rejection) and recursive clone propagation.

This patch is **mechanically complete and well-tested**, with no known issues. The only potential point of contention is the payload-stripping behavior, which is inherited from the ref storage backend and not explicitly documented in the user-facing documentation. The patch is part of a **technically approved series** (Karthik Nayak’s unconditional approval covers all patches), but integration awaits Junio’s assessment of the unresolved architectural debate about whether `extensions.objectStorage` should exist as a public API at all. For now, this patch is a clean, uncontroversial extension of the series’ core functionality.

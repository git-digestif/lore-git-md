This is a **follow-up in the RFC thread** introducing `git cat-file --remote-object-info` batching. Pablo Sabater responds to Junio C Hamano’s compatibility question, clarifying that the series only modifies the client side and that the server currently imposes no OID limit. The server already handles variable request sizes (up to 10k OIDs from old clients, larger from new ones) and multiple requests per connection, so the immediate compatibility risk is low.

However, Pablo now raises a new concern: the absence of a server-side cap could allow clients (modified or malicious) to send arbitrarily large requests, potentially straining server resources. He proposes adding a server-side limit, advertised via a new capability during the handshake, with a minimum value of 10k (to avoid breaking older clients). The client would then either die() if the user’s batch size exceeds the server’s advertised limit or silently clamp the batch size to the server’s value. The default 50k batch size would ideally match the server’s minimum cap to avoid errors for users who don’t override the default.

This reply advances the thread by identifying a previously unconsidered edge case—server resource exhaustion—and suggests a concrete mitigation. The tone is exploratory ("brainstorm"), but the proposal is technically grounded. The compatibility question Junio raised is now framed as a potential security/hardening issue rather than a protocol breakage. No code changes are attached; this is purely a design discussion. The next steps will likely involve deciding whether to implement the server-side cap and how to advertise it.

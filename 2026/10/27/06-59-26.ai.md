This is the second patch in Patrick Steinhardt’s **v4 object storage extension series**, which introduces the `extensions.objectStorage` configuration mechanism. This patch implements the core parsing and setup logic for the new extension, enabling Git to read and apply the object storage format from repository configuration.

The patch adds the `extensions.objectStorage` key to Git’s configuration system, modeled closely after the existing `extensions.refStorage`. The value can be a simple format name (e.g., `files`) or a URI (e.g., `files://objs`), where the payload (`objs`) specifies backend-specific configuration—in this case, relocating the `.git/objects` directory. The implementation splits the URI into a `type` (enum `object_storage_format`) and a `payload` (string), mirroring the ref storage backend’s design. This refactoring, introduced in v3, simplifies normalization and avoids URI re-parsing elsewhere in the codebase.

Key changes include:
- **New functions**: `object_storage_format_by_uri()` and `object_storage_format_by_name()` parse the format and payload from URIs or plain strings, returning `OBJECT_STORAGE_FORMAT_UNKNOWN` for invalid inputs.
- **Repository struct updates**: `struct repository` gains `object_storage_format` (enum) and `object_storage_payload` (string) fields, along with `repo_set_object_storage_format()` to set them.
- **Setup logic**: `handle_extension()` in `setup.c` now processes `extensions.objectStorage`, validating the format and storing the payload. The repository format version is bumped to `1` if the extension is set, ensuring older Git versions will refuse to read the repository.
- **Files backend support**: `odb_source_files_new()` accepts a payload to override the default `.git/objects` path, with relative paths resolved relative to `$GIT_COMMON_DIR`.
- **Tests**: New tests in `t/t0001-init.sh` verify initialization with valid/invalid formats, repository version enforcement, and basic functionality (e.g., committing objects with the `files` backend).

The commit message expands on the payload’s utility, addressing SZEDER Gábor’s v3 critique by justifying it as a tool for testing, alignment with ref storage, and internal use cases (e.g., repository migrations). However, the broader architectural question—whether `extensions.objectStorage` should exist as a public API—remains unresolved. The patch itself is technically sound, with clear error handling and backward compatibility (default remains `files` with no payload). Karthik Nayak’s unconditional approval of v3 signals readiness for integration, though Junio may still weigh the unresolved design debate.

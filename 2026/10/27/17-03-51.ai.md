This is a **substantive design discussion** in the `fetch: introduce +: refspec for matching-inspired fetch mode` series (v12), which is **under active review for merging to `master`**. The series is **blocked only by final review feedback** and is **expected to graduate soon**.

Phillip Wood raises a **backwards-compatibility concern** about the v12 design: if `remote.<name>.fetch` is used to specify *which* refs to fetch (e.g., `refs/heads/master`, `refs/heads/next`, `refs/heads/seen`), older Git versions will misinterpret the configuration and attempt to update local branches when fetching. This happens because older versions treat `remote.<name>.fetch` as a refspec with an implicit destination (the local branch), not as a list of source refs. Phillip proposes that the new "what to fetch" logic should use a **separate config key** (`remote.<name>.fetchRefmap` in v12) so that older Git versions fail cleanly (by not fetching anything) rather than silently corrupting local branches.

The discussion **validates the v12 design direction**: the new `remote.<name>.fetchRefmap` key (introduced in v12 to decouple "what" from "where") already addresses this concern. Junio’s example—using `remote.<name>.fetch` to list source refs—is **not the intended design** for v12; it was a hypothetical illustration of how the old system *could* work, not a proposal for the new one. The v12 implementation **explicitly avoids this pitfall** by using `remote.<name>.fetchRefmap` for the "what" and reserving `remote.<name>.fetch` for legacy compatibility. This ensures older Git versions either ignore the new key or fail safely, rather than misbehaving.

**Key technical details for follow-up**:
- **Config keys**: `remote.<name>.fetchRefmap` (new, "what to fetch") vs. `remote.<name>.refmap` (existing, "where to store").
- **Precedence**: `remote.<name>.fetch` (legacy) > `remote.<name>.fetchRefmap` (new) > dynamic branch enumeration.
- **Backwards compatibility**: Older Git versions ignore `fetchRefmap` and fail to fetch (safe) rather than misinterpreting `fetch` as a refspec (unsafe).
- **Files touched**: The v12 series updates `remote.c` (config parsing), `builtin/fetch.c` (integration), and documentation to reflect this design.
- **Open question**: Whether the documentation should explicitly warn users about the incompatibility of mixing `remote.<name>.fetch` with the new mode. This is a **documentation clarity issue**, not a design flaw.

Subject: [PATCH 0/12] Modernize git-rerere's subcommand handling
Series version: v4 (merged to 'master' as of 2025-06-25)
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring)

Core problem or goal
Replace the custom subcommand-parsing logic in `git rerere` with Git’s standard `OPT_SUBCOMMAND()` mechanism, bringing the command in line with other multi-subcommand built-ins like `git notes` and `git maintenance`. The series is purely internal restructuring: no new functionality, no behavior changes, and no on-disk format changes.

Current status
Merged to 'master' as of 2025-06-25 (Junio’s “What's cooking” report explicitly stated “Will merge to 'master'”). **Regression decisions finalized**: Junio has accepted two UI regressions as deliberate trade-offs to fix what the author and maintainer consider design flaws. No mitigation or grandfathering will be implemented; the merged code remains as-is. The regressions are confirmed on the `seen` branch and absent on `master` and `next`:
1. **Option ordering**: The `OPT_SUBCOMMAND()` machinery enforces option ordering, rejecting `git rerere --skip-locked gc` (old syntax) while accepting `git rerere gc --skip-locked` (new syntax).
2. **Error reporting**: On the `seen` branch, `git rerere unknown` yields a generic "too many arguments" message, while on `master` it correctly lists the valid subcommands in the usage string. This is a cosmetic regression that degrades the user experience by obscuring available subcommands when an invalid one is provided.

Key technical details
- Files: `builtin/rerere.c` (primary), `rerere.h`, `Documentation/git-rerere.adoc`, plus callers in `apply.c`, `builtin/am.c`, `builtin/commit.c`, `builtin/merge.c`, `builtin/stash.c`, `rerere.c`, `sequencer.c`.
- Symbols: functions renamed to follow subcommand naming (`rerere()` replaces `repo_rerere()` in patch 1; the function’s signature and behavior are unchanged, but its documentation in `rerere.h` is expanded to clarify its role as the main entry point for recording and reusing conflict resolutions; `cmd_rerere_perform()` introduced in patch 11 as the fallback subcommand; `cmd_rerere_clear()`, `cmd_rerere_status()`, `cmd_rerere_forget()`, `cmd_rerere_remaining()`, `cmd_rerere_diff()`, and `cmd_rerere_gc()` introduced as dedicated functions for their respective subcommands). Patch 10 specifically introduces `cmd_rerere_gc()` with a hidden `--skip-locked` option, preserving the existing behavior where `rerere_gc()` skips garbage collection if another process holds the lock. The global `--skip-locked` flag is removed from the top-level parser, as it is now scoped to the "gc" subcommand. Flags converted to enums (`enum rerere_flags` replaces `#define RERERE_AUTOUPDATE`, `RERERE_NOAUTOUPDATE`, `RERERE_READONLY`, `RERERE_NOWAIT` in patch 2). The enum values are defined as bit shifts (`1 << 0`, `1 << 1`, etc.) to preserve the existing bitmask semantics. The comment on `RERERE_NOWAIT` (immediate failure when `MERGE_RR.lock` is taken) is confirmed correct. The enum now documents all four flags for clarity, with `RERERE_NOAUTOUPDATE` explicitly clarified to update the working tree but leave the index untouched while still printing conflict-resolution messages to stderr.
- **Three-state flag system**: The `RERERE_AUTOUPDATE` and `RERERE_NOAUTOUPDATE` flags form a three-state system: (0) follow the configured `rerere.autoUpdate` default, (1) force `--autoupdate`, or (2) force `--no-autoupdate`. The CLI parser (`parse_opt_tertiary()`) prevents both bits from being set simultaneously, but the consuming code (`rerere_cache_setup()`) now explicitly validates the state with a `BUG()` check added in v4. In the invalid case (both bits on), the `BUG()` triggers, ensuring no silent precedence behavior. This is not a regression—it predates the series—but the refactoring made it newly visible and actionable.
- **Regressions**:
  1. **Option ordering**: The `OPT_SUBCOMMAND()` machinery enforces option ordering, rejecting `git rerere --skip-locked gc` (old syntax) while accepting `git rerere gc --skip-locked` (new syntax). The old syntax worked because the hand-rolled parser did not enforce ordering; the new parser does. The `--skip-locked` option is now scoped to the "gc" subcommand, so it must appear after the subcommand name.
  2. **Error reporting**: On the `seen` branch, `git rerere unknown` yields a generic "too many arguments" message instead of listing valid subcommands in the usage string. This is a cosmetic regression that degrades the user experience by obscuring available subcommands when an invalid one is provided. The root cause is likely a difference in how the `OPT_SUBCOMMAND()` machinery handles unrecognized subcommands compared to the hand-rolled parser it replaced.
- Subcommands: "forget", "clear", "status", "remaining", "diff", and "gc" now have dedicated functions (`cmd_rerere_forget()`, `cmd_rerere_clear()`, `cmd_rerere_status()`, `cmd_rerere_remaining()`, `cmd_rerere_diff()`, `cmd_rerere_gc()`) with standard `parse_options()` machinery. The fallback subcommand is `cmd_rerere_perform()`, introduced in patch 11. Patch 3 removes the last references to the global `the_repository` variable in `builtin/rerere.c`, replacing all 13 uses with the `repo` parameter passed to `cmd_rerere()`. The change is safe because `git rerere` cannot run outside a repository, and the `parse_options()` call happens before any repository access, so the `repo` pointer is guaranteed to be valid even when `-h` is used. Patch 4 removes the unused `--[no-]rerere-autoupdate` flag from the "status" and "diff" subcommands, hard-coding `RERERE_READONLY` in their call sites. The change is purely internal: no behavior change, no new CLI options, and no on-disk format changes. The motivation is to simplify subsequent refactorings by eliminating dead flag-passing. Patch 5 introduces `cmd_rerere_forget()` with an empty option table, preserving the existing warning about deprecated usage (`'git rerere forget' without paths`) and pathspec handling. Patch 6 introduces `cmd_rerere_clear()` with an empty option table, preserving the existing `rerere_clear()` call and behavior, including the handling of the `merge_rr` string list. Patch 7 introduces `cmd_rerere_status()` with an empty option table, preserving the existing logic, including the `RERERE_READONLY` flag, the `merge_rr` string list, and the loop that prints each conflicted path. Patch 8 introduces `cmd_rerere_remaining()` with an empty option table, preserving the existing logic (11 lines of code moved verbatim from the hand-rolled subcommand ladder in `cmd_rerere()` into a new 31-line function). The function follows the established pattern from earlier patches, using an empty `struct option` array and a `parse_options()` call to validate arguments before invoking the core `rerere_remaining()` logic. The `string_list_clear()` cleanup and the loop that prints unresolved conflicts are preserved verbatim. The only difference is the addition of a usage check (`if (argc) usage(...)`), previously handled by the top-level `cmd_rerere()` function. Patch 9 introduces `cmd_rerere_diff()` with an empty option table, preserving the existing logic: it iterates over conflicted paths in `merge_rr`, generates diffs between the stored preimage and the working tree, and dies on failure. The only difference is the addition of a usage check (`if (argc) usage(...)`), previously handled by the top-level function. **Documentation discrepancy**: The man page and usage strings for `git rerere diff` claim the subcommand accepts additional arguments and passes them to the system `diff` command, but the code has not supported this since 2006 (commit 658f365027, "Make git-rerere a builtin"). The new per-subcommand usage strings added in patch 12/12 preserve this inaccuracy by omitting any mention of arguments, while the prose description still implies they are supported. Junio’s review of patch 9 explicitly notes that the "diff" subcommand does not accept any additional arguments, serving as a reminder to verify the documentation update in patch 12. This is a purely documentary issue; no code changes are needed or proposed.
- Patch 10 introduces `cmd_rerere_gc()` with a hidden `--skip-locked` option in its option table, preserving the existing `rerere_gc()` call and behavior, and removes the now-redundant global `--skip-locked` flag from the top-level parser. The patch also removes a test (`--skip-locked is only accepted by gc`) that enforced the old behavior where the global flag was rejected for non-"gc" subcommands. **Junio’s post-merge feedback requests that the commit message for patch 10 explicitly state that the test removal was intentional and explain the rationale for accepting the regression (option ordering enforcement).** The rationale is that `--skip-locked` is a relatively new option with few users, making now the right time to enforce option ordering.
- Patch 11 replaces the hand-rolled subcommand ladder with an `OPT_SUBCOMMAND()` table, introduces `cmd_rerere_perform()` as the fallback subcommand, and removes the global `--[no-]rerere-autoupdate` flag from the top-level parser, parsing it locally in `cmd_rerere_perform()` instead. The fallback logic constructs a synthetic `"perform"` subcommand name and re-parses the arguments to ensure consistent behavior. The patch preserves all existing functionality, including the three-state autoupdate system and the `PARSE_OPT_KEEP_UNKNOWN_OPT` flag for forwards compatibility. The synthetic `"perform"` subcommand name is an internal placeholder and is not exposed to users. **Junio’s review of patch 11 identifies a latent safety issue in the fallback logic’s memory handling**: the code constructs a synthetic `"perform"` subcommand by pushing it into a `strvec` and then copying the array to avoid modification by `parse_options()`. Junio questions whether the `CALLOC_ARRAY()` and `COPY_ARRAY()` calls account for the terminating NULL pointer required by C’s `(ac, av)` convention (`av[ac]` must be NULL). If the `strvec` does not include this NULL, the copied array would be unterminated, potentially causing issues in `cmd_rerere_perform()`. This is a substantive review concern, as it could lead to memory corruption or undefined behavior.
- Patch 12 adds per-subcommand usage strings to the man page and C code, completing the series. Seven `N_()`-wrapped usage strings are defined (one per subcommand), each subcommand’s `parse_options()` call references its own usage array, and the man page’s `SYNOPSIS` section is updated to list each subcommand on its own line. The documentation for `git rerere diff` omits any mention of additional arguments, preserving the existing inaccuracy in the prose description.
- Documentation: `Documentation/git-rerere.adoc` updated in patch 12 to include per-subcommand usage strings in the `SYNOPSIS` section. The documentation for `enum rerere_flags` has been further polished in v4 to clarify the three-state system (follow default, force autoupdate, force no-autoupdate) and the purpose of each flag.
- **Workflow tooling**: `git history fixup` (from the experimental `git history` series) implements the core workflow Junio described (stage changes, commit as fixup, rebase in one step) but currently cannot replay merge commits, which would be needed to fully automate Junio’s use case (targeting a specific commit in a topic branch with merges).

Open questions and loose ends
1. **Documentation gap in `enum rerere_flags`**: While the documentation now clearly describes the three-state system and the behavior of each flag, the *rationale* for the three-state system (overriding the configured `rerere.autoUpdate` default) is still not explicitly captured in the enum’s documentation. A brief example or explanation of why this system exists (e.g., "to allow callers to override the configured default without modifying the configuration") could further improve clarity. This is a minor, non-blocking gap.
2. **`git history fixup` limitation**: The command currently cannot replay merge commits, which would be needed to fully automate Junio’s use case (targeting a specific commit in a topic branch with merges). This is not a blocker for the `rerere` series but may be relevant for future workflow tooling discussions.
3. **Error reporting regression**: The cosmetic regression in error reporting for unknown subcommands (`git rerere unknown` yielding a generic message instead of listing valid subcommands) is noted but not slated for a fix. The regression is minor and does not affect functionality, but it degrades the user experience. No further action is expected.
4. **Documentation discrepancy in `git rerere diff`**: The man page and usage strings claim the subcommand accepts additional arguments and passes them to the system `diff` command, but the code has not supported this since 2006 (commit 658f365027). The discrepancy is purely documentary—no code changes are proposed or needed—but it is a real, if minor, issue that could mislead users. Junio’s review of patch 9 explicitly notes that the "diff" subcommand does not accept any additional arguments, confirming the code’s behavior and serving as a reminder to verify the documentation update in patch 12. This is a retrospective documentation cleanup opportunity.
5. **Commit message improvement for patch 10**: Junio’s post-merge feedback requests that the commit message for patch 10 explicitly state that the test removal was intentional and explain the rationale for accepting the regression (option ordering enforcement). This is a retrospective documentation improvement for future maintainers and is not expected to require code changes.
6. **Fallback logic memory safety**: Junio’s review of patch 11 identifies a latent safety issue in the fallback logic’s memory handling. The synthetic `"perform"` subcommand array must be NULL-terminated to comply with C’s `(ac, av)` convention. If the `strvec` does not include this NULL, the copied array would be unterminated, potentially causing memory corruption or undefined behavior in `cmd_rerere_perform()`. This is a substantive review concern that may require a follow-up patch to address.

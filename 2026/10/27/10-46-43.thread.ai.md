Thread identity
Subject: [PATCH 0/12] Modernize git-rerere's subcommand handling
Series version: v1 (initial submission)
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring)

Core problem or goal
Replace the custom subcommand-parsing logic in `git rerere` with Git’s standard `OPT_SUBCOMMAND()` mechanism, bringing the command in line with other multi-subcommand built-ins like `git notes` and `git maintenance`. The series is purely internal restructuring: no new functionality, no behavior changes, and no on-disk format changes.

Current status
Under review; v1 posted 2025-06-17. Depends on the already-merged `ps/rerere-remove-global-state` topic (b948c10c8b3), which eliminated the global rerere cache state and made this refactoring possible. Junio C Hamano initially objected to the `rerere_record()` name in patch 1, arguing that “record” is too narrow because the function also resolves conflicts when a recorded resolution exists. Patrick Steinhardt has proposed `rerere_perform()` as a replacement, citing the man page’s phrasing but acknowledging the function’s broader behavior. The naming discussion remains the sole open item blocking integration. Patch 2 (“rerere: convert flags into an enum”) has received a cosmetic follow-up: Patrick proposes to extend the enum’s documentation to cover all flags (`RERERE_AUTOUPDATE`, `RERERE_NOAUTOUPDATE`, `RERERE_READONLY`, and `RERERE_NOWAIT`) for clarity, though no functional change is involved. All other patches remain uncontested and ready for integration once the naming is resolved.

Key technical details
- Files: `builtin/rerere.c` (primary), `rerere.h`, `Documentation/git-rerere.adoc`, plus callers in `apply.c`, `builtin/am.c`, `builtin/commit.c`, `builtin/merge.c`, `builtin/stash.c`, `rerere.c`, `sequencer.c`.
- Symbols: functions renamed to follow subcommand naming (`rerere_perform()` proposed to replace `repo_rerere()` in patch 1; patches 5–10 introduce `cmd_rerere_forget()`, `cmd_rerere_clear()`, `cmd_rerere_status()`, `cmd_rerere_remaining()`, `cmd_rerere_diff()`, and `cmd_rerere_gc()`); flags converted to enums (`enum rerere_flags` replaces `#define RERERE_AUTOUPDATE`, `RERERE_NOAUTOUPDATE`, `RERERE_READONLY`, `RERERE_NOWAIT`). The comment on `RERERE_NOWAIT` (immediate failure when `MERGE_RR.lock` is taken) is confirmed correct; Patrick now proposes to document all four flags in the enum for clarity. `the_repository` usage fully removed as of patch 3.
- Subcommands: "forget", "clear", "status", "remaining", "diff", and "gc" now have dedicated usage strings. Patch 4 removes the unused `--[no-]rerere-autoupdate` flag from the "status" and "diff" subcommands, hard-coding `RERERE_READONLY` in their call sites. Patches 5–10 extract the "forget", "clear", "status", "remaining", "diff", and "gc" actions into `cmd_rerere_forget()`, `cmd_rerere_clear()`, `cmd_rerere_status()`, `cmd_rerere_remaining()`, `cmd_rerere_diff()`, and `cmd_rerere_gc()` with standard `parse_options()` machinery. Patch 11 replaces the hand-rolled `if (!strcmp(...))` ladder with an `OPT_SUBCOMMAND()` table for the six subcommands, introducing a fallback `cmd_rerere_perform()` that mimics the old default behavior when no subcommand is given. The "gc" subcommand (patch 10) adds a hidden `--skip-locked` option to its option table and removes the now-redundant global `--skip-locked` flag from the top-level parser. Patch 12 adds per-subcommand usage strings to the man page and to each subcommand function, completing the series.
- Documentation: `Documentation/git-rerere.adoc` updated for new interface (SYNOPSIS now lists one line per subcommand); test suite (`t/t4200-rerere.sh`) receives minor updates (patch 10 drops one negative test for the old global-flag behavior).
- No new CLI options, config keys, or test files.

Open questions and loose ends
The naming of the fallback subcommand remains open. Junio C Hamano objected to `rerere_record()` as too narrow; Patrick Steinhardt has proposed `rerere_perform()` but awaits Junio’s acceptance or further refinement. Patch 2’s cosmetic documentation extension is uncontested and ready for integration once the naming is resolved.

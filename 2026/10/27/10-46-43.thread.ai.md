Thread identity: Subject "[PATCH 0/13] Modernize git-rerere's subcommand handling", series version v5 (superseding v4 which was reported merged to 'master' as of 2025-06-25), originating author Patrick Steinhardt, thread type patch series (refactoring).

Core problem or goal: Replace custom subcommand-parsing logic in `git rerere` with standard `OPT_SUBCOMMAND()` mechanism; purely internal restructuring with no new functionality or on-disk format changes, except for intentional option-ordering and option-acceptance restrictions now scoped to specific subcommands.

Current status: v4 was previously recorded as merged to 'master' per Junio's "What's cooking" report. v5 has now been posted as a 13-patch series that directly addresses the post-merge follow-up items. v5 is under review; no merge status for v5 is claimed.

Key technical details: Files touched include `builtin/rerere.c`, `rerere.h`, `rerere.c`, `apply.c`, `builtin/am.c`, `builtin/commit.c`, `builtin/merge.c`, `builtin/stash.c`, `sequencer.c`, `Documentation/git-rerere.adoc`, and `t/t4200-rerere.sh`. Patch 1/13 renames `repo_rerere()` to `rerere()`. Patch 2/13 converts flag `#define` macros to `enum rerere_flags` with a `BUG()` guard against contradictory autoupdate flags. Patch 3/13 removes `USE_THE_REPOSITORY_VARIABLE` from `builtin/rerere.c`. Patch 4/13 adjusts read-only subcommands to pass only `RERERE_READONLY`. Patches 5-10 extract "forget", "clear", "status", "remaining", "diff", and "gc" into dedicated `cmd_rerere_*()` handlers respectively, each with `usage(_("too many arguments"))` validation; patch 10 moves `--skip-locked` into `cmd_rerere_gc()` with `PARSE_OPT_KEEP_UNKNOWN_OPT` at top level, making `git rerere gc --skip-locked` the only accepted form. Patch 11/13 performs the core conversion: introduces an `OPT_SUBCOMMAND()` table mapping "clear", "diff", "forget", "gc", "remaining", and "status" to their handlers, adds `PARSE_OPT_SUBCOMMAND_OPTIONAL` to make the subcommand optional, and creates `cmd_rerere_perform()` as the fallback for the default no-subcommand behavior; the fallback synthesizes an argv array using `CALLOC_ARRAY(args_copy, args.nr + 1)` to guarantee NULL termination (correcting the prior `args.nr` allocation) and calls `usage_with_options()` for unknown subcommands to restore informative error messages. Patch 11 also introduces an intentional backwards-incompatible change: `--[no-]rerere-autoupdate` is now accepted only for the implicit "perform" subcommand and rejected when passed to named subcommands, fixing a previously misleading interface. Patch 12/13 replaces the single shared `rerere_usage[]` array with individual usage arrays for each subcommand handler (`cmd_rerere_clear`, `cmd_rerere_diff`, `cmd_rerere_forget`, `cmd_rerere_gc`, `cmd_rerere_perform`, `cmd_rerere_remaining`, `cmd_rerere_status`), defined via new `RERERE_*_USAGE` macros; each `parse_options()` call in these handlers now receives its subcommand-specific usage string so error messages display the correct syntax for that specific subcommand, while the top-level `cmd_rerere()` assembles a combined usage array listing all seven forms. Patch 12/13 also updates the man page synopsis to list each subcommand on its own line rather than as a bracketed alternation; this patch changes only user-facing text with no behavioral change to command execution. Patch 13/13 removes the stale claim in `Documentation/git-rerere.adoc` that `git rerere diff` passes additional arguments to the system `diff` command; the commit message traces this discrepancy to commit 658f3650273 ("Make git-rerere a builtin", 2006-12-20), which inadvertently dropped that argument-forwarding behavior when rerere was converted from a shell script to a C builtin, and notes that since nobody has complained in roughly two decades, the documentation is being aligned with actual long-standing behavior rather than restoring the old feature. Patch 13/13 is documentation-only with no code changes and carries a Suggested-by trailer from Junio C Hamano.

Open questions and loose ends: All previously identified v4 follow-ups are addressed in v5 pending review: (1) error-reporting regression fixed in patch 11 via `usage_with_options()`; (2) NULL-termination memory safety fixed in patch 11 via `CALLOC_ARRAY(args.nr + 1)`; (3) stale documentation removed in patch 13; (4) `--skip-locked` ordering restriction documented and implemented in patch 10. New intentional behavior change in patch 11: autoupdate flags rejected for named subcommands. Patch 12/13 completes the user-interface polish by giving each subcommand its own specific usage string. Watch item: whether the `usage(_("too many arguments"))` checks in patches 6-10 correctly preserve prior behavior or constitute intentional tightening. The two usability side effects of patch 11/13 that Junio C Hamano had flagged -- (a) `git rerere -h` now showing only the top-level subcommand listing and hiding the descriptive help text for `--rerere-autoupdate`, and (b) `git rerere --git-completion-helper` now emitting subcommand names rather than autoupdate flags -- have been discussed and closed: Patrick Steinhardt agrees with Junio that the help-text loss is acceptable, though he records a personal design takeaway that a default verb-less subcommand is tolerable only when the bare command accepts no flags, and that once non-default behavior is requested the interface should demand an explicit subcommand; he notes backwards compatibility prevents applying this to `git rerere` now.

Subject: [PATCH 0/12] Modernize git-rerere's subcommand handling
Series version: v3 (final; series now merged to 'master')
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring)

Core problem or goal
Replace the custom subcommand-parsing logic in `git rerere` with Git’s standard `OPT_SUBCOMMAND()` mechanism, bringing the command in line with other multi-subcommand built-ins like `git notes` and `git maintenance`. The series is purely internal restructuring: no new functionality, no behavior changes, and no on-disk format changes.

Current status
**Merged to 'master'** as of 2025-06-25 (Junio’s “What's cooking” report explicitly states “Will merge to 'master'”). The series is now complete; no further revisions are expected. All prior feedback from v1, v2, and v3 has been addressed, including the final patch (12/12) that adds per-subcommand usage strings to the man page and C code. The dependency `ps/rerere-remove-global-state` (b944c10c8b3) was already merged before this series began. A **latent safety issue** in the `enum rerere_flags` logic has been identified post-merge: the three-state system formed by `RERERE_AUTOUPDATE` and `RERERE_NOAUTOUPDATE` (follow default, force autoupdate, force no-autoupdate) lacks explicit validation for the invalid state where both bits are set. The consuming code (`rerere_cache_setup()`) silently prioritizes `RERERE_AUTOUPDATE` over `RERERE_NOAUTOUPDATE`, but no caller intentionally passes both flags. The discussion is now focused on whether to add a `BUG()` or `die()` to catch misuse, though no patch has been proposed yet.

Key technical details
- Files: `builtin/rerere.c` (primary), `rerere.h`, `Documentation/git-rerere.adoc`, plus callers in `apply.c`, `builtin/am.c`, `builtin/commit.c`, `builtin/merge.c`, `builtin/stash.c`, `rerere.c`, `sequencer.c`.
- Symbols: functions renamed to follow subcommand naming (`rerere()` replaces `repo_rerere()` in patch 1; the function’s signature and behavior are unchanged, but its documentation in `rerere.h` is expanded to clarify its role as the main entry point for recording and reusing conflict resolutions; `cmd_rerere_perform()` introduced in patch 11 as the fallback subcommand); flags converted to enums (`enum rerere_flags` replaces `#define RERERE_AUTOUPDATE`, `RERERE_NOAUTOUPDATE`, `RERERE_READONLY`, `RERERE_NOWAIT` in patch 2). The enum values are defined as bit shifts (`1 << 0`, `1 << 1`, etc.) to preserve the existing bitmask semantics. The comment on `RERERE_NOWAIT` (immediate failure when `MERGE_RR.lock` is taken) is confirmed correct. The enum now documents all four flags for clarity, with `RERERE_NOAUTOUPDATE` explicitly clarified to update the working tree but leave the index untouched while still printing conflict-resolution messages to stderr.
- **Three-state flag system**: The `RERERE_AUTOUPDATE` and `RERERE_NOAUTOUPDATE` flags form a three-state system: (0) follow the configured `rerere.autoUpdate` default, (1) force `--autoupdate`, or (2) force `--no-autoupdate`. The CLI parser (`parse_opt_tertiary()`) prevents both bits from being set simultaneously, but the consuming code (`rerere_cache_setup()`) does not explicitly validate the state. In the invalid case (both bits on), `RERERE_AUTOUPDATE` silently takes precedence. This is not a regression—it predates the series—but the refactoring makes it newly visible. Junio’s latest email notes this as a latent safety concern, though no `BUG()` or explicit validation exists in the current codebase.
- Subcommands: "forget", "clear", "status", "remaining", "diff", and "gc" now have dedicated functions (`cmd_rerere_forget()`, `cmd_rerere_clear()`, `cmd_rerere_status()`, `cmd_rerere_remaining()`, `cmd_rerere_diff()`, `cmd_rerere_gc()`) with standard `parse_options()` machinery. The fallback subcommand is `cmd_rerere_perform()`, introduced in patch 11. Patch 4 removes the unused `--[no-]rerere-autoupdate` flag from the "status" and "diff" subcommands, hard-coding `RERERE_READONLY` in their call sites. The change is purely internal: no behavior change, no new CLI options, and no on-disk format changes. Patch 5 introduces `cmd_rerere_forget()` with an empty option table, preserving the existing warning about deprecated usage (`'git rerere forget' without paths`) and pathspec handling. Patch 6 introduces `cmd_rerere_clear()` with an empty option table, preserving the existing `rerere_clear()` call and behavior. Patch 7 introduces `cmd_rerere_status()` with an empty option table, preserving the existing logic. Patch 8 introduces `cmd_rerere_remaining()` with an empty option table, preserving the existing logic. Patch 9 introduces `cmd_rerere_diff()` with an empty option table, preserving the existing logic. Patch 10 introduces a hidden `--skip-locked` option in `cmd_rerere_gc()`'s option table, preserving the existing `rerere_gc()` call and behavior, and removes the now-redundant global `--skip-locked` flag from the top-level parser. Patch 11 replaces the hand-rolled subcommand ladder with an `OPT_SUBCOMMAND()` table, introduces `cmd_rerere_perform()` as the fallback subcommand, and removes the global `--[no-]rerere-autoupdate` flag from the top-level parser, parsing it locally in `cmd_rerere_perform()` instead. Patch 12 adds per-subcommand usage strings to the man page and C code.
- Documentation: `Documentation/git-rerere.adoc` updated in patch 12 to include per-subcommand usage strings in the `SYNOPSIS` section. The C code defines seven `N_()`-wrapped usage strings (one per subcommand), and each subcommand’s `parse_options()` call references its own usage array.

Open questions and loose ends
1. **Latent safety concern in flag consumption**: The consuming code (`rerere_cache_setup()`) does not explicitly validate the invalid state where both `RERERE_AUTOUPDATE` and `RERERE_NOAUTOUPDATE` are set. While the CLI parser (`parse_opt_tertiary()`) prevents this, the lack of validation in the consuming code is a latent robustness issue. The current behavior silently prioritizes `RERERE_AUTOUPDATE` over `RERERE_NOAUTOUPDATE`, but no caller intentionally passes both flags. The discussion is now focused on whether to add a `BUG()` or `die()` to catch misuse, though no patch has been proposed yet. This is not a regression but a pre-existing issue made visible by the refactoring.
2. **Documentation gap in `enum rerere_flags`**: The discussion remains open on how best to clarify the *purpose* of the three-state system formed by `RERERE_AUTOUPDATE` and `RERERE_NOAUTOUPDATE`. The current documentation describes what the flags do (updates the working tree but not the index, prints messages to stderr) but not *why* the three-state system exists or how it differs from a binary toggle. Junio’s prior email clarifies that the flags are intended to override the configured `rerere.autoUpdate` default, but this rationale is not yet captured in the enum’s documentation. A brief example or explanation of the three states (follow default, force autoupdate, force no-autoupdate) would improve clarity.

Thread identity: RFC patch series introducing `git cat-file --remote-object-info` batching to remove the 10k OID limit, authored by Pablo Sabater.

Core problem or goal: The current `git cat-file --remote-object-info` command enforces a hard-coded 10k OID limit, forcing users to manually split large queries. The goal is to lift this limit by batching requests internally, improving performance for metadata-only queries (e.g., 400k OIDs now complete in 1.82s vs. 5.86s under the old limit).

Current status: Under review as an RFC. The series consists of 3 patches: (1) refactoring to extract transport ownership (posted), (2) implementing internal batching (now posted), and (3) adding the `--remote-max-batch` CLI option (default: 50k OIDs, upcoming). No merge status reported; GitHub CI passed for the posted patches.

Key technical details:
- **Files touched**: `builtin/cat-file.c`, `transport-helper.c`, `transport.c`, and related headers (patch 1 and 2).
- **New behavior**: Unlimited OIDs accepted via internal batching (50k-OID chunks, patch 2); patch 1 is purely preparatory.
- **New symbols**: `--remote-max-batch` option (default: 50k, introduced in patch 3); patch 1 renames `gtransport` to `transport` and moves smart-options check to caller; patch 2 converts `get_remote_info()` to die on failure (matching `git ls-remote`).
- **Behavior changes**: Connection reuse between batches; handshake performed once per command.
- **Test coverage**: New test script `t/t1017-cat-file-remote-object-info.sh` (introduced in patch 3).
- **On-disk format**: No changes; this is a transport-layer optimization.

Open questions and loose ends:
- Should the server enforce its own OID limit for object-info requests?
- Feedback requested on benchmarking methodology (simulated 47ms RTT).
- Whether the 50k default batch size is appropriate for all use cases (to be addressed by `--remote-max-batch` in patch 3).

Thread identity: RFC patch series introducing `git cat-file --remote-object-info` batching to remove the 10k OID limit, authored by Pablo Sabater.

Core problem or goal: The current `git cat-file --remote-object-info` command enforces a hard-coded 10k OID limit, forcing users to manually split large queries. The goal is to lift this limit by batching requests internally, improving performance for metadata-only queries (e.g., 400k OIDs now complete in 1.82s vs. 5.86s under the old limit).

Current status: Under review as an RFC. The series is now complete with 3 patches: (1) refactoring to extract transport ownership, (2) implementing internal batching, and (3) adding the `--remote-max-batch` CLI option (default: 50k OIDs). No merge status reported; GitHub CI passed for all posted patches. Junio C Hamano has reviewed patches 1 and the cover letter, requesting (a) a clearer error message for the "smart options required" condition in patch 1, and (b) explicit documentation and testing of backwards-compatibility implications for the batching logic.

Key technical details:
- **Files touched**: `builtin/cat-file.c`, `transport-helper.c`, `transport.c`, `Documentation/git-cat-file.adoc`, and new test script `t/t1017-cat-file-remote-object-info.sh`.
- **New behavior**: Unlimited OIDs accepted via internal batching (50k-OID chunks by default, configurable via `--remote-max-batch`); connection reuse between batches; handshake performed once per command.
- **New symbols**: `--remote-max-batch=<n>` option (default: 50k); `batch_options` field in `cat-file`; patch 1 renamed `gtransport` to `transport` and moved smart-options check to caller; patch 2 converted `get_remote_info()` to die on failure (matching `git ls-remote`).
- **Behavior changes**: No on-disk format changes; transport-layer optimization only. Compatibility with older servers/clients is now an open question.
- **Test coverage**: New test script verifies option validation (rejects zero/non-numbers), enforces `--batch-command` requirement, and tests edge cases (batch boundaries, multiples of batch size) across all transport protocols (git://, file://, http://).

Open questions and loose ends:
- Should the server enforce its own OID limit for object-info requests?
- Feedback requested on benchmarking methodology (simulated 47ms RTT).
- Whether the 50k default batch size is appropriate for all use cases (now addressable via `--remote-max-batch`; Junio suggests documenting the alignment with `git backfill`’s 50k default for clarity).
- Junio’s request for a clearer error message in patch 1 ("smart options required" is cryptic for end users).
- **New**: How the batching logic interacts with older servers and clients—will updated clients break when talking to older servers, or will older clients misbehave with newer servers? This compatibility question must be resolved before the series can progress.

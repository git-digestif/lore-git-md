Thread identity: RFC patch series introducing `git cat-file --remote-object-info` batching to remove the 10k OID limit, authored by Pablo Sabater.

Core problem or goal: The current `git cat-file --remote-object-info` command enforces a hard-coded 10k OID limit, forcing users to manually split large queries. The goal is to lift this limit by batching requests internally, improving performance for metadata-only queries (e.g., 400k OIDs now complete in 1.82s vs. 5.86s under the old limit). The series also addresses server-side resource exhaustion risks by proposing a server-advertised OID limit via a new capability.

Current status: Under review as an RFC. The series remains at 3 patches: (1) refactoring to extract transport ownership, (2) implementing internal batching, and (3) adding the `--remote-max-batch` CLI option (default: 50k OIDs). No merge status reported; GitHub CI passed for all posted patches. Junio C Hamano has reviewed patches 1 and the cover letter. His prior request for a clearer error message in patch 1 is now resolved: Pablo proposed "object-info is not supported on bundles", and Junio suggested a more generic alternative ("object-info is not supported by this remote") to avoid forward-compatibility issues if other transports lack smart options. The broader design questions (server-side OID limits, batching defaults) remain open. The thread remains in the design phase, with no code updates yet.

Key technical details:
- **Files touched**: `builtin/cat-file.c`, `transport-helper.c`, `transport.c`, `Documentation/git-cat-file.adoc`, and new test script `t/t1017-cat-file-remote-object-info.sh`.
- **New behavior**: Unlimited OIDs accepted via internal batching (50k-OID chunks by default, configurable via `--remote-max-batch`); connection reuse between batches; handshake performed once per command. Proposed addition: server-side OID limit advertised via a new capability during handshake, with a minimum value of 10k to avoid breaking older clients. Clients would either die() if the user’s batch size exceeds the server’s limit or silently clamp to the server’s value.
- **New symbols**: `--remote-max-batch=<n>` option (default: 50k); `batch_options` field in `cat-file`; patch 1 renamed `gtransport` to `transport` and moved smart-options check to caller; patch 2 converted `get_remote_info()` to die on failure (matching `git ls-remote`).
- **Behavior changes**: No on-disk format changes; transport-layer optimization only. Compatibility with older servers/clients is preserved, but the server-side limit proposal introduces a new capability negotiation mechanism. Error message for "smart options required" is now under discussion: Pablo’s "object-info is not supported on bundles" vs. Junio’s "object-info is not supported by this remote" (or a dynamic variant if the remote’s URL is available).
- **Test coverage**: New test script verifies option validation (rejects zero/non-numbers), enforces `--batch-command` requirement, and tests edge cases (batch boundaries, multiples of batch size) across all transport protocols (git://, file://, http://). Server-side limit testing would require additional test cases once implemented.

Open questions and loose ends:
- Whether to implement the server-side OID limit and how to advertise it (proposed: new capability during handshake).
- If implemented, whether the client should die() or silently clamp when the user’s batch size exceeds the server’s limit.
- Junio’s request for explicit documentation and testing of backwards-compatibility implications for the batching logic (e.g., how older clients/servers interact with the new batching behavior).
- Feedback requested on benchmarking methodology (simulated 47ms RTT).
- Whether the 50k default batch size is appropriate for all use cases (Junio suggests documenting the alignment with `git backfill`’s 50k default for clarity).
- The error message wording for "smart options required" is now resolved in principle, pending confirmation of whether the remote’s URL is available for a dynamic message.
- Junio’s latest reply validates Pablo’s concern about server resource exhaustion as a legitimate design consideration, framing it as part of the collaborative review process.

This is a documentation terminology discussion in the ongoing thread about Git's glossary definitions for object identifiers. Junio C Hamano, the maintainer, responds to Ben Knoble's suggestions with a detailed defense of the current terminology, rejecting any change that would make "object ID" the canonical term instead of "object name."

Junio clarifies that "object name" is the long-established canonical term for the 40- or 64-character hexadecimal identifier (SHA-1 or SHA-256) that uniquely identifies an object in Git's storage. He analogizes it to how a fruit might be called "orange" in one language and "laranja" in another—different names, but referring to the same thing. The various shorthand ways to refer to an object (refs, branch names, unique prefixes, HEAD) are not themselves "object names," but can often be used *in place of* the object name in commands.

Junio argues that the confusion does not stem from the term "object name" itself, but from imprecise wording in other documentation (like `gitrevisions(1)`) that fails to distinguish between the canonical object name (the hash) and the shorthand notations that can stand in for it. He insists that the solution is to fix those documents to align with the glossary's definition, not to change the glossary. He points to a 2005 commit (f1671ecbfa) that standardized the terminology after extensive discussion, and frames the current patch as undermining that effort.

The email is substantive and authoritative, leaving no room for compromise on the core issue: "object name" will remain the canonical term for the hash identifier, and any documentation using it otherwise is incorrect. Junio does not engage with Ben Knoble's proposed refinements (like using "notation" for shorthand references) beyond dismissing them as irrelevant to the real problem. The thread remains blocked unless someone is willing to audit and update the broader documentation to match the glossary's definition.

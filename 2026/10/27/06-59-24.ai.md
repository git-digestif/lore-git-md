This is the **v4 cover letter** for Patrick Steinhardt’s seven-patch series introducing the **object storage extension** (`extensions.objectStorage`), a foundational step toward pluggable object database backends in Git. The series is now **technically complete and approved** by Karthik Nayak, with only minor stylistic nits remaining. However, an **unresolved architectural debate**—raised by SZEDER Gábor in v3—continues to cloud its integration prospects.

The core goal remains unchanged: enable alternative object storage backends (e.g., cloud storage, databases) by exposing a configuration mechanism modeled after the existing ref storage extension. The v4 iteration **adds no new features** but refines the justification for the `files` backend’s payload (directory relocation) and polishes code comments and test formatting. The most notable change is the expanded commit message in patch 2/7, which now explicitly addresses the "why" behind the payload: testing infrastructure, alignment with ref storage, and internal use cases like repository migrations. This responds to SZEDER Gábor’s v3 critique, though the reviewer’s broader skepticism about exposing `extensions.objectStorage` as a public API remains unanswered.

The series touches **35 files**, including core subsystems (`odb/`, `setup.c`, `repository.c`), built-in commands (`git clone`, `git init`, `git submodule`), documentation, and tests. Key user-facing additions include:
- **Configuration**: `extensions.objectStorage` (e.g., `files://objs` to relocate `.git/objects` to `.git/objs`), `init.defaultObjectStorageFormat`.
- **CLI options**: `--object-storage-format=` for `git clone`, `git init`, and `git submodule`.
- **Environment variables**: `GIT_OBJECT_STORAGE_FORMAT` (overrides repo config), `GIT_DEFAULT_OBJECT_STORAGE_FORMAT` (sets default for new repos).
- **Inspection tools**: `git rev-parse --show-object-storage-format` and `git repo objects.storageFormat`.
- **Submodule propagation**: The `type` (e.g., `files`) is passed to submodules, but payloads are stripped for consistency with ref storage.

The implementation is **mechanically robust**, with careful attention to precedence rules (CLI > env > repo config > defaults), backward compatibility (default remains `files` with no payload), and edge cases (e.g., local clone restrictions for non-default backends). Tests cover initialization, cloning, submodule scenarios, and error handling. The v4 changes are cosmetic: a stray newline removed, comments clarified, and the commit message expanded to justify the payload’s utility.

**Status**: The series is **ready for integration** from a technical standpoint—Karthik Nayak’s unconditional approval in v3 covers all patches, and v4 addresses the remaining nits. However, the **architectural question** raised by SZEDER Gábor lingers: whether `extensions.objectStorage` should exist as a public API at all, given that the `files` backend’s payload only relocates `.git/objects`. Patrick’s v4 response justifies the payload’s utility but does not engage with the reviewer’s broader concern about API design complexity. Junio’s eventual decision may hinge on whether he views this as a necessary parallel to `extensions.refStorage` or an over-engineered abstraction.

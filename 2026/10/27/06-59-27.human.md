This is the third patch in Patrick Steinhardt’s seven-part series introducing the `extensions.objectStorage` mechanism, which lays the groundwork for pluggable object database backends in Git. This specific patch adds support for overriding the object storage format via the `GIT_OBJECT_STORAGE_FORMAT` environment variable, mirroring the existing behavior for ref storage (`GIT_REF_STORAGE_FORMAT`).

The change is straightforward and mechanical: it extends the repository discovery logic in `setup.c` to check for `GIT_OBJECT_STORAGE_FORMAT` and, if present, parse its value into the repository’s object storage format and payload. The environment variable takes precedence over the repository’s `extensions.objectStorage` configuration, following the established pattern for ref storage. Documentation is updated to describe the new variable, and a new test verifies that the override works as expected—including error handling for invalid formats.

This patch is a small but necessary piece of the larger series. It enables testing and debugging of object storage backends without modifying repository configuration, which is particularly useful for the `files` backend’s payload (e.g., relocating `.git/objects` to `.git/objs`). The implementation is clean and aligns with the project’s existing conventions. Karthik Nayak’s earlier review of this patch in v3 was positive, and the v4 iteration addresses only minor stylistic nits (e.g., comment clarifications) rather than substantive changes.

The patch itself is uncontroversial, but it’s worth noting that the broader series remains under an unresolved architectural debate. SZEDER Gábor’s review of patch 2/7 questions whether `extensions.objectStorage` should exist as a public API at all, given that the `files` backend’s payload only relocates the objects directory. While this patch doesn’t engage with that debate, it’s part of the infrastructure that would make such an API usable in practice. For now, the patch is technically sound and ready for integration, but its long-term utility depends on how Junio resolves the larger design question.

This is the author’s response to Junio C Hamano’s review in the ongoing RFC thread for `git cat-file --remote-object-info` batching. Pablo Sabater clarifies that the patch series affects only the client side, leaving the server unchanged. The server currently has no OID limit, so it will accept any request size from new clients while continuing to receive the old 10k-OID limit from older ones.

Pablo acknowledges a potential issue: the new batching logic allows multiple requests over the same connection, which the server already handles, but a user could now configure an excessively large batch (e.g., 1M OIDs). He proposes two mitigation strategies: either cap the server-side limit (advertised via a new capability) or silently clamp the client’s batch size to the server’s advertised limit. The default 50k batch size would ideally match the server’s minimum cap to avoid errors for users who don’t override the default.

The response is thoughtful and directly addresses Junio’s compatibility concern, though it leaves the server-side cap as an open design question. The tone is collaborative, and the technical details (capability advertisement, connection reuse) are clearly explained. This moves the thread toward a concrete solution but doesn’t yet resolve whether a server-side limit is necessary.

This is the fifth patch in Patrick Steinhardt’s **v4 object storage extension series** (7 patches total), which introduces user-facing configuration for the new `extensions.objectStorage` mechanism. The patch adds CLI, environment variable, and config file support for setting the object storage format during repository initialization, mirroring the existing ref storage extension’s design.

The patch wires up the `--object-storage-format=` option for `git init` (and by extension, `git clone`), allowing users to specify the backend and payload (e.g., `files://objs` to relocate `.git/objects` to `.git/objs`). It also adds `init.defaultObjectStorageFormat` (config key) and `GIT_DEFAULT_OBJECT_STORAGE_FORMAT` (environment variable) to set the default for new repositories, with the same precedence rules as the ref storage extension: CLI > `GIT_OBJECT_STORAGE_FORMAT` > repo state > `GIT_DEFAULT_OBJECT_STORAGE_FORMAT` > `init.defaultObjectStorageFormat` > `files`. The implementation is careful to maintain backward compatibility—default behavior remains unchanged—and to enforce consistency during reinitialization (e.g., rejecting mismatched formats).

Key changes:
- **CLI**: `--object-storage-format=` option for `git init` (and `git clone` via shared code in `setup.c`).
- **Config**: `init.defaultObjectStorageFormat` (e.g., `files://objs`).
- **Environment**: `GIT_DEFAULT_OBJECT_STORAGE_FORMAT` (sets default for new repos).
- **Precedence**: CLI overrides environment, which overrides repo config, which overrides defaults.
- **Validation**: Rejects unknown formats (e.g., `--object-storage-format=garbage`) and mismatched reinitialization (e.g., switching from `files` to `files://objs`).
- **Repository format version**: Bumps `core.repositoryformatversion` to `1` if the format is non-default, ensuring older Git versions can detect the extension.
- **Tests**: 14 new tests in `t0001-init.sh` covering initialization, precedence rules, error cases (invalid formats, reinitialization mismatches), and integration with `GIT_OBJECT_DIRECTORY`.

The patch is **mechanically complete** and aligns with the series’ architectural goals. It does not introduce new features beyond what was planned but fills in the user-facing plumbing for the object storage extension. The implementation is consistent with the ref storage extension’s design, including the deliberate omission of payloads in submodule propagation (e.g., `files://objs` becomes `files` for submodules).

**Context for follow-up discussion**:
- The patch touches `setup.c` (precedence logic, repository format version bump), `builtin/init-db.c` (CLI option), and `t0001-init.sh` (tests).
- The **repository format version bump** (to `1`) for non-default formats may attract scrutiny—some reviewers might argue it’s overly conservative or that alternative approaches (e.g., version bumps only for non-`files` backends) should be explored.
- The **precedence rules** and **error handling** are well-tested, but the tests do not cover edge cases like relative vs. absolute paths in payloads (e.g., `files://./objs`), which could surface in later discussion.
- The patch does not address the **architectural debate** raised by SZEDER Gábor (whether `extensions.objectStorage` should exist as a public API at all), but it assumes the feature’s viability and focuses on implementation. Junio’s eventual decision may hinge on that unresolved question.

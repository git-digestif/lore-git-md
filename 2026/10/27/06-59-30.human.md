This is the sixth patch in Patrick Steinhardt’s seven-patch **v4** series introducing the `extensions.objectStorage` mechanism, which enables pluggable object database backends in Git. This patch wires up the `--object-storage-format=` option for `git clone`, mirroring the functionality added for `git init` in the previous patch.

The patch adds a new CLI option to `git clone` that lets users specify the object storage backend (e.g., `--object-storage-format=files://objs` to relocate `.git/objects` to `.git/objs`). It enforces a key restriction: **local clones (hardlinking or copying objects) are disabled if either the source or destination repository uses a non-default object storage format**. If the user explicitly requests `--local`, the clone fails with an error; otherwise, it falls back to a non-local transport with a warning. The restriction is documented in the man page and justified as a temporary measure to avoid backend-specific complexity.

The implementation is straightforward: the option is parsed early, validated against known backends, and passed to `create_repository()`. The `is_using_default_object_storage_format()` helper checks whether a repository uses the default `files` backend with no payload, which is the only configuration currently allowed for local clones. Tests cover initialization, error cases (invalid formats, local clone restrictions), and integration with bundle URIs.

This patch is **well-crafted and uncontroversial**—it follows the established pattern for ref storage, includes thorough test coverage, and addresses edge cases like explicit `--local` requests. The local clone restriction may attract discussion about whether it’s overly conservative, but the current implementation is a pragmatic compromise. The patch is **ready for integration** alongside the rest of the series, pending Junio’s resolution of the broader architectural debate about whether `extensions.objectStorage` should exist as a public API at all.

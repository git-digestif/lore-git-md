This is a design discussion in the long-running `remote.<name>.refmap` series, now in its twelfth iteration. The series aims to fix a performance problem in shallow repositories by introducing a "matching-inspired" fetch mode that dynamically fetches only the branches tracked by local branches at the remote being fetched. The current email is a short exchange between Phillip Wood and Junio C Hamano about a backward-compatibility concern with the proposed configuration syntax.

Phillip raises a critical point: if the new design uses `remote.<name>.fetch` to specify *which* refs to fetch (e.g., `refs/heads/master`, `refs/heads/next`), older versions of Git might misinterpret those entries as full refspecs and attempt to update local branches when fetching. This would break backward compatibility. Phillip suggests using a separate config key (like the planned `remote.<name>.fetchRefmap`) to avoid this issue, ensuring older Git versions fail cleanly rather than misbehaving.

Junio’s reply confirms that the current behavior—where `remote.<name>.refmap` alone works as expected—is correct, but he does not directly address the backward-compatibility question. The exchange leaves the concern unresolved, though the thread’s broader context (the v12 redesign) already favors Phillip’s approach: the next version will use `remote.<name>.fetchRefmap` to specify which refs to fetch, keeping `remote.<name>.fetch` for namespace mapping only. This design avoids the backward-compatibility pitfall Phillip highlights.

The discussion is narrow but important: it reinforces the need for the v12 redesign and clarifies why overloading `remote.<name>.fetch` is problematic. The series is otherwise complete and under active review for merging to `master`; this is one of the last open design questions.

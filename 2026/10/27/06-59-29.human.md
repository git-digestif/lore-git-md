This is the fifth patch in Patrick Steinhardt’s seven-patch **v4 series** introducing the **object storage extension** (`extensions.objectStorage`), a foundational step toward pluggable object database backends in Git. This patch focuses on **user-facing configuration** for the object storage format, adding CLI options, environment variables, and configuration knobs to `git init` (and by extension, `git clone`).

The patch adds the `--object-storage-format=` option to `git init`, mirroring the existing `--ref-storage-format=` option. Users can now specify the object storage backend and payload (e.g., `files://objs` to relocate `.git/objects` to `.git/objs`) via the command line, environment variables (`GIT_OBJECT_STORAGE_FORMAT`, `GIT_DEFAULT_OBJECT_STORAGE_FORMAT`), or configuration (`init.defaultObjectStorageFormat`). The precedence rules are carefully designed: command-line options override environment variables, which override repository state, which overrides defaults. The patch also ensures that reinitializing a repository with a mismatched storage format fails, preserving consistency.

The implementation is **mechanically solid** and well-tested. The patch touches `setup.c` (precedence logic, repository format version bump), `builtin/init-db.c` (CLI option parsing), and documentation (`git-init.adoc`, `git.adoc`, `config/init.adoc`). Tests cover initialization, environment variable overrides, error cases (e.g., invalid formats), and integration with the repository format version bump. The patch also updates `builtin/clone.c` to pass the object storage format to `initialize_repository_version()`, ensuring consistency with `git init`.

This patch is **part of a larger architectural effort** to make Git’s object database pluggable, and it directly addresses the user-facing half of that goal. The series as a whole is **technically approved** by Karthik Nayak, and this patch introduces no new controversies—it simply extends the existing ref storage pattern to object storage. The unresolved architectural debate (raised by SZEDER Gábor in v3) about whether `extensions.objectStorage` should exist as a public API does not affect this patch’s implementation, which is narrowly focused on configuration ergonomics.

If you care about **pluggable backends** or **repository initialization**, this patch is worth skimming for its precedence logic and test coverage. Otherwise, it’s a straightforward extension of an existing pattern and unlikely to attract further discussion. The series is **ready for integration**, pending Junio’s assessment of the broader architectural question.

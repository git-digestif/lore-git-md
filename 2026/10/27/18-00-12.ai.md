This is a documentation terminology discussion in the ongoing thread about Git's glossary definitions for object identifiers. D. Ben Knoble replies to Junio C Hamano's defense of the current glossary, where "object name" is the canonical term for the hash identifier. Ben acknowledges the historical context (the 2005 standardization in `f1671ecbfa`) but questions whether preserving that decision should block improvements, especially when it conflicts with common usage ("ID" vs. "name").

Ben aligns with Julia Evans's original goal: using "object ID" for the hash and clarifying "object name" as context-dependent (e.g., refs, branch names). He argues that Git's terminology should align with user expectations where possible, even if it means deviating from historical precedent. His key point is that calling a branch name like `main` an "object ID" feels unintuitive, and the glossary's claim that an "object name" is a *unique* identifier is undermined by the existence of multiple notations (refs, unique prefixes) that resolve to the same hash.

The email does not propose a new patch or compromise but reinforces the impasse: Ben sees value in Julia's approach, while Junio insists on preserving the 2005 definition.

This is the **v12 implementation** of the long-running "matching-inspired fetch mode" series, now **finalized in design** and **actively under review for merging**. The series introduces `remote.<name>.fetchRefmap` (renamed from `remote.<name>.refmap` in v11) to decouple the "what to fetch" logic from the "where to store" mapping, resolving the maintainer and key reviewer’s objection to overloading `remote.<name>.refmap`. The **precedence rule is now settled**: `remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration (if neither is configured), with command-line refspecs overriding both config keys. Forced updates (`+`) belong on the refmap side (the "where"), not the fetchRefs side (the "what").

The **implementation is complete** and touches five patches:
1. **Patch 1/5** adds `remote.<name>.fetchRefmap`, the new config key that provides the default `--refmap` value. The patch includes thorough test coverage for edge cases: configuring both `fetch` and `fetchRefmap`, negative refspecs, and tracking branches outside `remote.<name>.fetch`. The commit message and documentation are clear and precise, explaining the interaction between `fetch`, `fetchRefmap`, and dynamic branch enumeration.
2. **Patch 2/5** extracts `collect_upstream_from_remote()` as a helper, a mechanical refactor that prepares for the next patch.
3. **Patch 3/5** implements the core logic: when `remote.<name>.fetchRefmap` is configured but `remote.<name>.fetch` is not, a refspec-less fetch infers what to fetch from local branches whose `@{upstream}` is on that remote. The patch includes a new test file (`t/t5586-fetch-refmap.sh`) with comprehensive coverage, including prefetch behavior.
4. **Patch 4/5** adds `--limited-fetch` to `git remote add`, configuring `remote.<name>.fetchRefmap` instead of `remote.<name>.fetch` so that `git fetch <name>` only fetches tracked branches. The flag is rejected with `-t/--track` or `--mirror`, as those already specify what to fetch.
5. **Patch 5/5** makes `--limited-fetch` the default in shallow repositories, addressing the original motivation: slow or hanging `git fetch`/`git pull` in shallow clones of repositories with many branches. The patch includes tests for both the default behavior and the `--no-limited-fetch` override.

The **series is well-structured**, with clear commit messages, focused patches, and strong test coverage. The **design is finalized** and **endorsed by Junio C Hamano and Phillip Wood**, resolving the fundamental objection to v11. The **implementation is clean**, with no on-disk format changes beyond new configuration entries. The **only remaining open questions** are minor edge cases (e.g., handling remotes with no default branch), but these are not blockers. This is a **high-quality, well-motivated contribution** that addresses a real pain point for users of shallow repositories. The series is **ready for review** and **likely to graduate to `master`** once any remaining nits are addressed.

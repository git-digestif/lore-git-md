This is a **design discussion reply** in the ongoing RFC thread about extending `git branch --delete` to handle branches whose upstream has been deleted. D. Ben Knoble responds to DonQuinleone’s hybrid proposal (G) with a mix of agreement, refinement, and lingering reservations about the composability model.

Knoble acknowledges the core issue Don identified—the "selection is not proof" problem when piping `--list` output to `xargs git branch -d`—but suggests workarounds rather than abandoning the composable approach. He proposes using `--format='%(refname:lstrip=2)'` to make `--list` output machine-readable, and notes that users could manually verify deletions with a dry-run before using `-D` if needed. While he concedes these are not ideal, he frames them as incremental improvements that could later be built into Git, preserving the composable syntax he advocates.

The reply also touches on edge cases: Knoble suggests explicitly excluding the current branch with `grep -v` or accepting the noise of Git’s refusal to delete it. He then circles back to the hybrid proposal, suggesting that if `-d` is to accept filters, it should reuse the same filtering logic as `--list` (and potentially add new filters like `--upstream-gone`). This would avoid duplicating code but still leaves open whether the "proof" of merge should be tied to the filter or handled separately.

Knoble’s tone is collaborative but non-committal—he doesn’t outright reject Don’s hybrid idea, but neither does he endorse it. The thread remains unresolved on whether the final design will prioritize composability (Knoble’s preference), explicit merge-checking (Don’s hybrid), or implicit behavior (Nordgren’s position). The next steps likely hinge on whether Knoble’s workarounds are deemed sufficient or if the discussion shifts toward a unified filtering implementation.

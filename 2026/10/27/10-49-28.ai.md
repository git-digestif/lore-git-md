This is a follow-up discussion in the ongoing thread about modernizing Git's C coding guidelines and API design, specifically around the use of compound literals. The original patch (updating `CodingGuidelines` to permit compound literals) has already been accepted and is marked for merging to `next`, but this email deepens the conversation about broader implications.

Phillip Wood responds to Patrick Steinhardt's earlier questions with concrete details and further exploration. First, he identifies the two C99 constructs still blocked by MinGW and IBM xlc: the `%z`/`%zu` format specifiers (MinGW) and designated initializers like `.a.b = c` (IBM xlc). He also checks whether recent changes to MinGW's UCRT64 might affect `%z` support, though no conclusion is reached. The discussion then expands to consider C11 features, with Phillip noting that `static_assert()` would be a welcome improvement over Git's current "hacky" static assertions, and that atomics *might* help reduce undefined behavior in signal handling (though their optional status in C11 could limit usefulness). He also floats the idea of `_Generic` macros, though no specific use case is proposed.

The most substantive part of the email is Phillip's engagement with Patrick's proposal to unify Git's dual initialization patterns (e.g., `STRBUF_INIT` macros vs. `strbuf_init()` functions) using compound literals. Phillip agrees this would be a good direction, noting that the test balloon for compound literals in the reftable code already demonstrates this approach. He then digs into the `strbuf_init()` usage patterns, showing that most callers pass `0` as the pre-allocation size, suggesting the hardcoded values in other cases might not be rigorously justified. This data supports the idea that a unified initialization pattern could simplify the API without sacrificing functionality. Phillip concludes by endorsing the goal of a uniform initialization method for both stack- and heap-allocated structs, aligning with Patrick's broader vision.

The tone remains collaborative and exploratory, with no controversy or pushback. The discussion is now focused on practical next steps: clarifying platform support for other C99/C11 features, and potentially prototyping API changes like redefining `STRBUF_INIT` as a compound literal.

This is the fourth patch in Patrick Steinhardt’s seven-patch **v4 series introducing the object storage extension** (`extensions.objectStorage`). It adds **user-facing inspection tools** for the object storage format, mirroring the existing functionality for the ref storage format. The patch is **mechanically straightforward** and well-scoped, touching only the plumbing needed to expose the configured object storage backend to users via `git rev-parse` and `git repo`.

The patch introduces two new inspection mechanisms:
- **`git rev-parse --show-object-storage-format`**: prints the configured object storage format (e.g., `files` or `files://objs`). This matches the existing `--show-ref-storage-format` option and follows the same output convention (omitting the payload for consistency with the ref storage backend).
- **`git repo objects.storageFormat`**: adds a new field to `git repo`’s JSON output, returning the object storage format as a string (e.g., `"files"`). The field includes a cross-reference to `object-storage-format.adoc` for documentation.

The implementation is **minimal and correct**: it adds a new helper function (`object_storage_format_to_name()`) to convert the internal `enum object_storage_format` to a string, updates `builtin/repo.c` to expose the format via `git repo`, and extends `builtin/rev-parse.c` to support the new CLI option. Tests verify that the output matches expectations for the default `files` backend and that the new field appears in `git repo`’s output.

**Key details for follow-up discussion**:
- The output **omits the payload** (e.g., `files://objs` becomes `files`), matching the ref storage backend’s behavior. This is a deliberate design choice for consistency, but it may attract discussion about whether users should see the full URI (e.g., for debugging).
- The `git repo` field name (`objects.storageFormat`) is a pragmatic compromise after a recent patch series renamed `references.format` to `references.storageFormat` to avoid a three-way naming conflict. The current naming is unlikely to change further.
- The patch **does not document the payload omission** in the user-facing documentation (`git-rev-parse.adoc` or `git-repo.adoc`). This could lead to user confusion if the payload is later deemed relevant for inspection.

**Quality assessment**: The patch is **well-crafted and uncontroversial**. It addresses a clear gap in the series’ user-facing tooling, follows established patterns, and includes thorough tests. No substantive feedback is expected beyond minor stylistic nits (e.g., the `git repo` field description could clarify that the payload is omitted). The patch is **ready for integration** and does not depend on the unresolved architectural debate about the broader `extensions.objectStorage` feature.

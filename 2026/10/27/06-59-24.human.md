This is the cover letter for the fourth iteration of Patrick Steinhardt’s seven-patch series introducing the **object storage extension**, a major architectural change that makes Git’s object database pluggable. The series defines a new `extensions.objectStorage` configuration key (modeled after the existing ref storage extension) and implements the baseline `files` backend, which now supports relocating the `.git/objects` directory via a payload (e.g., `files://objs` moves objects to `.git/objs`).

The v4 update is minor: it adds justification for the `files` backend’s payload in the commit message, removes a stray newline, and tweaks some comments. The core refactoring from v3—splitting the storage format URI into separate `(type, payload)` components—remains unchanged and is now technically approved by Karthik Nayak. The series is functionally complete and includes all planned features: environment variable support (`GIT_OBJECT_STORAGE_FORMAT`), user-facing configuration (`init.defaultObjectStorageFormat`), inspection tools (`git rev-parse --show-object-storage-format`), and submodule propagation (though submodules inherit only the `type`, not the payload, for consistency with ref storage).

The motivation is clear and compelling: this is the foundational work for pluggable object backends, enabling future support for cloud storage, databases, or other alternatives. The design mirrors the ref storage extension, suggesting deliberate consistency with existing patterns. The implementation is thorough, with careful attention to environment variable precedence, submodule handling, and backward compatibility (the default remains `files` with no payload). Tests cover initialization, cloning, and submodule scenarios, and the documentation is updated across `git-{clone,init,submodule}.adoc` and new files like `object-storage-format.adoc`.

The only unresolved issue is an architectural question raised by SZEDER Gábor in v3: whether `extensions.objectStorage` should exist as a public API at all, given that the `files` backend’s payload only relocates `.git/objects`. Patrick’s response justifies user-facing configurability on three grounds (testing, consistency with ref storage, and internal GitLab use), but the debate remains open and may influence Junio’s integration decision. The series is otherwise ready for merging, with no substantive changes expected beyond minor nits. If you care about Git’s long-term storage flexibility, this is a key series to watch.

This is the sixth patch in Patrick Steinhardt’s seven-patch **v4** series introducing the **object storage extension** (`extensions.objectStorage`), a foundational step toward pluggable object database backends in Git. This patch wires up the `--object-storage-format=` option in `git clone`, mirroring the functionality added to `git init` in the preceding patch (5/7). The implementation is **mechanically complete** and aligns with the series’ broader design goals, but it introduces a **temporary restriction** on local clones that may attract discussion.

The patch adds a new `--object-storage-format=` option to `git clone`, allowing users to specify the object storage backend (e.g., `files://objs`) for the cloned repository. The option accepts the same URI format as `git init`: `<type>[://<payload>]` (e.g., `files://objs` to relocate `.git/objects` to `.git/objs`). The patch also updates the `create_repository()` helper to pass the object storage format to the repository initialization logic, ensuring consistency with `git init`.

The most notable behavior change is the **local clone restriction**: if either the source or destination repository uses a non-default object storage format (i.e., anything other than `files` with no payload), `git clone --local` will either **fail** (if `--local` was explicitly requested) or **fall back to a non-local clone with a warning** (if `--local` was implied). This restriction is documented in the updated `git-clone(1)` man page and justified as a temporary measure to avoid hardlinking or copying objects between incompatible backends. The patch explicitly defers handling the edge case where the `files` backend is configured with an alternative object directory path (e.g., `files:///path/to/dir`), leaving it for future work.

The implementation is **thoroughly tested**, with 7 new tests in `t/t5601-clone.sh` covering:
- Basic cloning with the `files` backend (no payload).
- Cloning with a payload (e.g., `files://objs`), verifying that the payload is preserved in `extensions.objectStorage` and that the object directory is relocated.
- Integration with bundle URIs (ensuring the object storage format is preserved when cloning from a bundle).
- Error cases (invalid formats, local clone restrictions).
- Edge cases (explicit vs. implied `--local`, source repository with non-default storage).

The patch touches **3 files**:
- `Documentation/git-clone.adoc`: Adds documentation for `--object-storage-format=`, including a cross-reference to `object-storage-format.adoc` and a note about local clone restrictions.
- `builtin/clone.c`: Adds the `--object-storage-format=` option, validates the format, and enforces the local clone restriction. The `is_using_default_object_storage_format()` helper checks whether a repository uses the default `files` backend with no payload.
- `t/t5601-clone.sh`: Adds tests for the new functionality and edge cases.

**Key technical details**:
- The `object_storage_format_uri` parameter is passed to `create_repository()`, which handles the actual repository initialization and precedence rules (CLI > environment > repo config > defaults).
- The local clone restriction is enforced by checking whether both the source and destination repositories use the default `files` backend with no payload. This is a **conservative** approach that may be revisited in future patches.
- The patch reuses the `object_storage_format_by_uri()` helper (introduced in patch 2/7) to validate the format and parse the URI into `(type, payload)` components.

**Open questions**:
- The **local clone restriction** may attract discussion about whether it is too conservative or if alternative approaches (e.g., allowing same-backend clones with matching payloads) should be explored. The current implementation is documented as a temporary measure, but the restriction’s necessity and scope may be revisited.
- The **deferred edge case** (handling `files:///path/to/dir` in local clones) is explicitly left for future work, but its absence may prompt questions about the patch’s completeness.
- The **precedence rules** for `--object-storage-format=` (CLI > environment > repo config) are consistent with the rest of the series but may be scrutinized for edge cases (e.g., relative vs. absolute paths in payloads).

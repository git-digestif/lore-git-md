This is the second patch in Patrick Steinhardt’s seven-part series introducing the `extensions.objectStorage` mechanism, a foundational step toward pluggable object database backends in Git. The patch implements the core configuration logic for the new extension, modeled closely after the existing `extensions.refStorage` pattern.

The patch adds the `extensions.objectStorage` configuration key, which accepts a URI in the format `<schema>[://<payload>]` (e.g., `files://objs`). The schema identifies the backend (`files` is the only supported one for now), while the payload is backend-specific. For the `files` backend, the payload specifies an alternative location for the `.git/objects` directory, allowing users to relocate it (e.g., to `.git/objs`). The patch also introduces helper functions to parse the URI into separate `type` and `payload` components, mirroring the ref storage backend’s design, and updates the repository initialization code to handle the new extension.

While the `files` backend’s payload feature might seem niche, the commit message justifies it as a way to exercise the payload logic for future backends, align with the ref storage extension’s design, and enable internal use cases like repository migrations. The patch also bumps the repository format version to `1` when the extension is set, ensuring compatibility with older Git versions. Tests verify that the extension is rejected with repository version `0`, works with the `files` backend, and properly handles invalid formats.

This patch is well-crafted and thoroughly tested, with clear documentation and a commit message that addresses both the "how" and the "why." The only lingering question is the architectural debate raised by SZEDER Gábor in the v3 review—whether exposing `extensions.objectStorage` as a public API is justified given the limited utility of the `files` backend’s payload. Patrick’s response in the v4 cover letter clarifies the payload’s utility but doesn’t fully resolve the broader skepticism. That said, the implementation itself is uncontroversial and ready for integration. If you care about Git’s long-term extensibility or are following the ODB abstraction effort, this patch is worth your attention.

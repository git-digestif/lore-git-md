This thread is about a small but important bugfix to make Git’s `@{push}` revision suffix behave consistently with `git push` in triangular workflows when `push.default=simple`. Harald Nordgren identified that `@{push}` fails to resolve when `remote.pushDefault` points to a different remote than the branch’s upstream, even though `git push` correctly pushes to the same-named branch on the push remote. The result is that `git status` omits the push-branch comparison and shows misleading hints. Harald’s patch—a minimal four-line change in `remote.c`—aligns the two behaviors by delegating `@{push}` resolution to `tracking_for_push_dest()` in this scenario.

The patch is under review and has not yet received any formal Acked-by or Reviewed-by trailers. D. Ben Knoble provided the first substantive review, confirming the problem and endorsing the fix. His only question was whether the new conditional in `remote.c` should appear earlier in the function for stylistic reasons, but he did not insist on a change. The test updates in `t/t5516-fetch-push.sh` cover the fix and preserve error-path coverage by adjusting an existing test to use a differently named upstream branch instead of an invalid push remote. No objections or requests for changes have been raised, and the patch remains narrowly scoped with clear test coverage. If the author agrees with Knoble’s minor structural suggestion, a v2 may follow; otherwise, the patch seems ready for a maintainer’s Ack.

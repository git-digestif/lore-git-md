This is the **final patch (7/7)** in Patrick Steinhardt’s **v4 object storage extension series**, completing the feature by propagating the `--object-storage-format=` option through `git submodule`’s `add` and `update` subcommands. The patch is **mechanically straightforward** and aligns with the established pattern for ref storage format propagation, but it **enforces a deliberate design choice** that may attract discussion: submodules inherit the parent repository’s *type* (e.g., `files`) but **not the payload** (e.g., `files://objs` becomes `files`).

### What the patch does
The patch wires up `--object-storage-format=` in three `git submodule` subcommands:
1. **`add`**: Accepts the option and passes it to the underlying `git clone` call when initializing the submodule. The implementation mirrors the existing `--ref-storage-format=` logic, including error handling for unknown formats.
2. **`update`**: Propagates the option during submodule initialization (e.g., `git submodule update --init --object-storage-format=files`). This ensures newly cloned submodules respect the specified format.
3. **Recursive cloning**: The format is passed through `git clone --recurse-submodules`, but **payloads are stripped** (e.g., `files://objs` becomes `files`). This matches the ref storage backend’s behavior and is a **deliberate consistency choice**, though it may surprise users expecting payloads to propagate.

### Key technical details
- **Files touched**: `builtin/submodule--helper.c` (core logic), `git-submodule.sh` (option parsing), `builtin/clone.c` (minor adjustments to pass the format through `checkout()`), documentation, and a new test script (`t/t7427-submodule-object-storage-format.sh`).
- **New CLI options**: `--object-storage-format=` for `git submodule add` and `git submodule update`.
- **Behavior changes**:
  - Submodules **ignore payloads** (e.g., `files://objs` becomes `files`). This is **not documented in the user-facing man page**, which could lead to confusion.
  - The format is **validated** (e.g., `--object-storage-format=garbage` fails with a clear error).
  - The implementation **reuses existing helper functions** (`object_storage_format_by_name()`, `object_storage_format_to_name()`) to parse and validate formats, avoiding code duplication.
- **Tests**: The new test script (`t7427`) covers:
  - Adding a submodule with an explicit format.
  - Rejecting invalid formats (e.g., `garbage`).
  - Rejecting payloads (e.g., `files://objs`).
  - Recursive clone propagation (payloads are stripped).
  - `submodule update --init` with an explicit format.

### Context in the series
This patch **completes the user-facing interface** for the object storage extension, following the same pattern as the ref storage backend. The **payload-stripping behavior** is inherited from the ref storage design, but unlike ref storage, the object storage payload (e.g., directory relocation) is **not inherently tied to the superproject’s configuration**. This may prompt questions about whether the restriction is overly conservative.

### Likely points of future discussion
1. **Payload stripping**: Should submodules inherit payloads (e.g., `files://objs`)? The current implementation strips them for consistency with ref storage, but object storage payloads (e.g., directory relocation) are **not inherently tied to the superproject’s configuration**, unlike ref storage payloads (e.g., reftable directory).
2. **Documentation gaps**: The man page does not explain that payloads are stripped, nor does it clarify the distinction between `type` and `payload` in user-facing tools (e.g., `git rev-parse --show-object-storage-format` omits payloads).
3. **Edge cases**: The tests do not cover scenarios like:
   - Relative vs. absolute paths in payloads (e.g., `files://./objs`).
   - Submodules with pre-existing object storage formats (e.g., updating a submodule with a different format).

This is a **clean, well-tested patch** that completes the series’ user-facing interface.

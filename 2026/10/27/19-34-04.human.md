This is a **design discussion reply** in the ongoing RFC thread about extending `git branch --delete` to handle branches whose upstream has been deleted (e.g., after a GitHub PR merge). The thread explores how to let users delete local branches that are provably merged into a named ref (like `origin/master`) even when their upstream is gone.

D. Ben Knoble responds to DonQuinleone’s earlier findings about the limitations of a composable filtering approach. Don had demonstrated that piping `git branch --list --merged=origin/main` into `xargs git branch -d` fails because the pipe loses the proof of merge, causing `git branch -d` to fall back to checking against `HEAD` (which may not reflect the intended merge base). Knoble acknowledges this issue and suggests workarounds: using `--format='%(refname:lstrip=2)'` to make the output machine-readable, and manually excluding the current branch with `grep -v`. He also notes that users could dry-run the listing first and then use `-D` (force delete) if needed, though this is less ergonomic.

Knoble’s key proposal is to make `git branch -d` accept the same filters as `git branch --list`, including `--upstream-gone` and `--merged=<commit>`. This would unify the filtering logic and avoid the pipe boundary problem, allowing commands like `git branch -d --upstream-gone --merged=origin/master` to work as intended. He frames this as a natural extension of Don’s hybrid approach, where `--merged` serves as both a filter and the proof of merge. The discussion remains focused on interface design rather than implementation details, with no clear consensus yet on whether to prioritize composability, explicit opt-in, or implicit behavior.

The thread is still unresolved, but Knoble’s suggestion moves the conversation toward a more concrete technical direction. The open questions include whether this unified filtering model is the right path, how to handle edge cases (e.g., excluding the current branch), and whether the feature should eventually support squash-merged branches (a point of contention between Don and Harald Nordgren). For now, the proposal looks like a pragmatic middle ground, but it may require further refinement to address all workflow concerns.

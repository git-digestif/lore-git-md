Patrick Steinhardt has posted v5 of a thirteen-patch series modernizing `git rerere`'s subcommand handling by replacing custom parsing with the standard `OPT_SUBCOMMAND()` mechanism. The series directly addresses post-merge follow-ups from v4, fixing an error-reporting regression and a NULL-termination memory safety issue in the fallback handler, scoping `--skip-locked` strictly to `git rerere gc`, and removing stale documentation about `git rerere diff`. Patch 11 introduces an intentional backwards-incompatible change: `--[no-]rerere-autoupdate` is now accepted only by the implicit "perform" action and rejected when passed to named subcommands. The series is currently under review with no merge status claimed for v5.

The design discussion around patch 11 has now closed. Patrick Steinhardt recorded a personal takeaway that a default verb-less subcommand is tolerable only when the bare command accepts no flags, and that once non-default behavior is requested the interface should demand an explicit subcommand, though backwards compatibility prevents applying this to `git rerere` now. Junio C Hamano responded by suggesting that giving the default action an optional explicit name, such as `git rerere [run]`, would be an acceptable backward-incompatible change for the future, noting that the `PARSE_OPT_SUBCOMMAND_OPTIONAL` flag already used in the series supports this pattern. Both agreed that the loss of `--rerere-autoupdate` help text in `git rerere -h` is acceptable. With no objections raised, the series remains under review awaiting further maintainer action.

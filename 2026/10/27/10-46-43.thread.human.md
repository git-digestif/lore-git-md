The thread is now effectively closed. Patrick Steinhardt’s twelve-patch series modernizing `git rerere`’s subcommand handling was merged to `master` on June 25, 2025, after four iterations. The refactoring replaces the command’s custom parsing logic with Git’s standard `OPT_SUBCOMMAND()` mechanism, aligning it with other multi-subcommand built-ins like `git notes` and `git maintenance`. No new functionality or behavior changes were introduced, and the on-disk format remains unchanged.

Two deliberate UI regressions were accepted as trade-offs for fixing what the author and maintainer consider design flaws. First, the new parser enforces option ordering, so `git rerere --skip-locked gc` (old syntax) is now rejected in favor of `git rerere gc --skip-locked`. Second, error messages for unknown subcommands (e.g., `git rerere unknown`) no longer list valid subcommands, degrading the user experience slightly. Junio Hamano, the maintainer, has accepted both regressions as-is, with no plans for mitigation or grandfathering.

Post-merge, Junio identified a latent memory safety issue in the fallback subcommand logic (patch 11) and a long-standing documentation discrepancy in `git rerere diff`, where the man page incorrectly claims the subcommand accepts additional arguments. Neither issue is blocking, but the memory safety concern may prompt a follow-up patch. The thread also sparked light-hearted discussion about workflow tooling, including Junio’s wish for a `git fixup` command and references to the experimental `git history fixup` from the `git history` series. No further code changes are expected for the `rerere` series itself.

This thread covers Patrick Steinhardt's v5 series, "[PATCH 0/13] Modernize git-rerere's subcommand handling", a 13-patch refactoring that replaces `git rerere`'s custom subcommand parsing with the standard `OPT_SUBCOMMAND()` mechanism. The series builds on the v4 topic that was previously reported merged to `master`, and it directly addresses the post-merge follow-ups: patch 11 introduces the subcommand table with a `cmd_rerere_perform()` fallback for the default verb-less behavior, fixes a NULL-termination memory bug with `CALLOC_ARRAY(args.nr + 1)`, restores informative error messages via `usage_with_options()`, and intentionally restricts `--[no-]rerere-autoupdate` to the implicit perform subcommand. Patch 12 gives each subcommand its own usage string, and patch 13 removes a stale documentation claim about `git rerere diff` forwarding arguments to the system diff, a discrepancy dating back to the 2006 conversion of rerere from shell script to C builtin.

Junio C Hamano reviewed patch 11, endorsed the autoupdate restriction as fixing a misleading interface, confirmed the follow-up fixes, and flagged two usability side effects: `git rerere -h` no longer shows the `--rerere-autoupdate` help text, and the shell completion helper now emits subcommand names instead of autoupdate flags. Patrick Steinhardt has now replied agreeing that the help-text loss is acceptable, and he generalizes the point into a design principle: a verb-less default subcommand is tolerable only when the bare command accepts no flags, and once non-default behavior is requested the interface should demand an explicit subcommand. He notes backwards compatibility means this cannot change for `git rerere` today, but records it as a takeaway for future command design. The email contains no code changes and raises no new objections.

The series remains under review with no merge status claimed for v5. All previously identified loose ends -- the error-reporting regression, the memory-safety fix, the stale docs, the `--skip-locked` ordering restriction, and the help-text/completion side effects -- are now either addressed or explicitly accepted by both the author and the maintainer, leaving the discussion substantively closed pending integration.

Johannes Schindelin has posted version 2 of a five-patch series addressing integer overflow vulnerabilities flagged by Coverity across several core subsystems. The series hardens archive-tar, HTTP fetch, wrapper I/O, and the relative-date parser against undefined behavior that could cause crashes or silent corruption when arithmetic exceeds type limits. Patches 1 and 2 remain unchanged from the first version, while patches 3 through 5 have been substantially reworked to use portable `uintmax_t` arithmetic and overflow checks rather than compiler-specific macros, resolving earlier portability concerns raised by Phillip Wood.

The final patch targets `date.c`, where `approxidate_alpha()` now performs unit-length multiplication in `uintmax_t` using `unsigned_mult_overflows()` before verifying the result fits in `time_t`, and `approxidate_digit()` rejects parsed numbers exceeding `INT_MAX`. These changes ensure that absurd inputs like "18446744073709551615 seconds ago" are rejected with an "invalid timestamp" error instead of wrapping, while valid large quantities such as "4000 weeks ago" continue to parse correctly. Earlier patches in the series fix a latent `size_t` wrap in `archive-tar.c`'s `get_path_prefix()`, change `posn` to `size_t` in `http.c`'s `fwrite_sha1_file()`, and refactor the wrapper read/write paths to return `int` and guard against `SSIZE_MAX` overruns, migrating six call sites and adding unit tests in `t/unit-tests/u-wrapper.c` alongside new cases in `t/t0006-date.sh`.

Junio C Hamano has confirmed the `http.c` type change is sound and clarified that the `date.c` hardening applies to local user input, with the series currently sitting in his integration queue marked "Waiting for response" in the latest "What's cooking" report. No outstanding technical objections remain to the revised patches, though the commit messages do not yet address whether external callers outside the Git tree have been audited for compatibility with the new wrapper API signatures.

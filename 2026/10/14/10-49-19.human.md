This is a bugfix patch from Patrick Steinhardt targeting the pack-check subsystem.

The patch fixes an off-by-one error in how Git determines whether a blob should be verified via streaming (for large files) or in-memory (for smaller files). The issue arises when a blob's size exactly matches `core.bigFileThreshold`: the code incorrectly treats it as a large file and attempts to stream it, but the streaming backend refuses to create a stream for blobs at or below the threshold, causing `git fsck` to incorrectly report the blob as corrupt.

The fix is simple: adjust the comparison from `<=` to `<` to align with the rest of the codebase, where objects are only considered "large" if they *exceed* the threshold. The patch includes a new test case in `t/t1450-fsck.sh` that verifies `git fsck` handles blobs of exactly the threshold size correctly.

The commit message is thorough, tracing the regression back to its introduction in 2016 and explaining why the issue became acute after a 2026 change to `packfile_read_object_stream()`. Patrick notes that a more principled fix (moving the threshold logic out of the streaming backend) would be possible but might impact performance, so he opts for the minimal fix for now.

This looks like a clean, well-motivated bugfix with good test coverage. The issue is subtle but real, and the fix is uncontroversial. Worth attention if you care about fsck correctness or packfile verification.

Thread identity: standalone bugfix patch for the reftable backend, authored by Matthew Suozzo via GitGitGadget. Thread type: bug report and fix.

Core problem or goal: fix a potential buffer overflow in the reftable backend's object record decoder (`reftable/record.c`). The decoder fails to validate that the 64-bit varint offset count does not exceed the remaining record length, which could lead to writing past an allocated array on 32-bit systems or unnecessarily large allocations on 64-bit systems. The bug is latent but poses a security risk if malformed records are processed.

Current status: patch posted as a single commit; under review. No prior versions exist. The fix adds a bounds check in `reftable_obj_record_decode()` and a unit test in `t/unit-tests/u-reftable-record.c` to verify rejection of malformed records. The test suite `u-reftable-record` is also added to the Makefile (previously Meson-only). Patrick Steinhardt's review argues the fix may be misplaced, as the root cause lies in `REFTABLE_ALLOC_ARRAY()`/`reftable_alloc_size()`, which fails to detect overflow on 32-bit systems due to `size_t` truncation.

Key technical details:
- Files touched: `reftable/record.c`, `t/unit-tests/u-reftable-record.c`, `Makefile`.
- New behavior: decoder returns `REFTABLE_FORMAT_ERROR` when the offset count exceeds the remaining record length.
- On-disk format: unchanged.
- Test coverage: new unit test constructs a malformed record and verifies the error code.
- Root cause: `reftable_alloc_size()`'s overflow check is ineffective on 32-bit platforms due to `size_t` truncation of 64-bit values.

Open questions and loose ends:
- Whether the fix should target the decoder or the allocation helper (`reftable_alloc_size()`).
- The commit message requires rewriting for clarity; Patrick Steinhardt described it as overly verbose and difficult to parse.
- The Makefile addition of `u-reftable-record` should ideally have been a separate patch (minor procedural concern).

This is a bugfix patch, the third in a five-part series addressing integer overflows flagged by Coverity. It targets the `wrapper.c` subsystem, specifically the `read_in_full()` and `write_in_full()` helper functions.

The patch adds an upfront check to reject byte counts larger than `SSIZE_MAX` (the maximum value a `ssize_t` can hold), returning `EINVAL` instead of silently overflowing the accumulator. The overflow would otherwise produce a negative return value after processing `SSIZE_MAX` bytes, which callers could misinterpret as an error or even a small positive value due to further wrapping. The fix also defines `SSIZE_MAX` for platforms that lack it, ensuring portability.

The commit message explains that while Git never passes such large counts in practice (due to platform and POSIX limits), the accumulation in the `*_in_full()` wrappers could still exceed `SSIZE_MAX` if the total count does. This is a defensive hardening measure, not a fix for an observed bug. The change is small, mechanical, and uncontroversial, matching the style of prior Coverity-driven fixes from the same author. No tests are included, consistent with the series' focus on latent issues.

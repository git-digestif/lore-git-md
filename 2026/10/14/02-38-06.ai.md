This is a **design discussion reply** in the ongoing thread about `core.indexLockTimeout`. Jun Wu responds to D. Ben Knoble’s substantive review of Patch 1/2, clarifying the performance rationale for `--no-optional-locks` and defending the configurability approach.

Jun explains that `--no-optional-locks` forces `git status` to fall back to full content hashing (not just stat refresh) when the index lock is unavailable, leading to persistent slowdowns if users don’t run index-writing commands (like `add`) to recover. He provides real-world examples from Sapling (Facebook’s Git fork) where users experienced multi-minute slowdowns due to stale stat info, and where lock contention caused 40% checkout failure rates. The proposed 1-second default timeout aims to balance IDE polling needs with user command responsiveness, reducing "cannot commit" errors without requiring users to learn about the config.

On Knoble’s concern about config proliferation, Jun argues the default (1s) is user-friendly and aligns with Mercurial/Sapling’s 10-minute timeout precedent. He outlines three alternative approaches Knoble suggested (faster `status`, lock-free writes, fsmonitor-style notifications) but notes each has limitations: faster `status` doesn’t eliminate lock contention, lock-free writes would require major format changes, and fsmonitor doesn’t address the root issue of lock conflicts. The reply frames the timeout as a pragmatic middle ground, though the debate over whether this is the right long-term solution remains unresolved. No code changes are proposed here—this is purely a design-level clarification.

This is a reply in the ongoing thread about Jun Wu’s configurable index lock timeout series (v1). The email addresses Junio C Hamano’s feedback on the cover letter’s clarity, specifically the ambiguity around the race-avoidance logic.

Jun Wu clarifies the scope of the rule “if the index is read before locking, the wait will be skipped.” The rule applies **per-process**: within any Git command that calls `repo_hold_locked_index`, if the in-core index (`repo->index->initialized`) was already read before attempting to lock, the command behaves as if `core.indexLockTimeout=0` (no wait). This is independent of what other processes (e.g., background `git status`) have done. Today, `git status` always reads the index before locking, so its behavior remains unchanged.

The clarification is narrow but important: it removes the ambiguity Junio flagged about which process’s actions the rule refers to. No code changes are proposed; this is purely a documentation-of-intent fix for the cover letter. The author will revise the cover letter to incorporate this explanation before sending v2.

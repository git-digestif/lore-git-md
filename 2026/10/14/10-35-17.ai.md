This is a **CI/build system** patch in Patrick Steinhardt’s v3 series, specifically the final patch (8/8) addressing reftable test coverage. The email is Patrick’s reply to Jeff King’s **substantive technical review**, which questioned whether the proposed `linux-reftable-sha256` job is redundant because the `fedora-breaking-changes-meson` job already covers SHA-256 + reftable via the `WITH_BREAKING_CHANGES` flag.

Patrick clarifies a key technical detail: while the `WITH_BREAKING_CHANGES` flag forces SHA-256 as the default hash algorithm, it does **not** change the default ref storage backend from `files` to `reftable`. The breaking-changes job therefore tests SHA-256 with the traditional files backend, not with reftable. This distinction justifies the new job’s existence, as it ensures coverage for the combination of SHA-256 and reftable — a configuration not currently tested elsewhere in the CI pipeline.

The reply is concise and directly addresses Peff’s concern by citing the relevant code in `t/test-lib.sh` that hard-codes `files` as the default ref backend unless explicitly overridden. This explanation strengthens the patch’s rationale and may resolve the open question, though it remains to be seen whether Peff or other reviewers (e.g., contributors invested in reftable or SHA-256) will find the justification sufficient. The discussion now hinges on whether the breaking-changes job’s coverage is considered adequate without reftable, or if the new job’s explicit testing of the SHA-256 + reftable combination is necessary for thorough validation.

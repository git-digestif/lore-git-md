Subject: [PATCH 0/5] Coverity-inspired integer-overflow fixes
Series version: v1 (initial)
Originating author: Johannes Schindelin (via GitGitGadget)
Thread type: patch series

Core problem or goal
Eliminate integer overflows and unsafe arithmetic in Git’s codebase flagged by Coverity, hardening several subsystems (archive-tar, http, wrapper, date) against undefined behavior, crashes, or silent corruption when arithmetic exceeds type limits. The fixes are defensive and target latent issues rather than observed bugs.

Current status
Under review; v1 posted. Four prior Coverity-fix branches from the same author were merged to master between July and October 2026. Junio’s replies confirm the hardening is limited to local user input (e.g., `git commit --date="..."`, `git log @{...}`) and does not affect parsing of timestamps stored in commit objects, removing any risk of breaking history traversal across platforms.

Key technical details
- New overflow-checking macros in git-compat-util.h: `signed_mult_overflows` and `mult_overflows` (type-generic wrapper for signed/unsigned dispatch)
- Files touched: archive-tar.c, date.c, git-compat-util.h, http.c, wrapper.c
- Subsystems hardened: archive-tar (zero-length input), http (size_t for byte positions), wrapper (implausibly large byte counts), date (approxidate relative-time calculations)
  - http.c: `posn` variable in `fwrite_sha1_file()` changed from `int` to `size_t` to match the total size parameter, preventing heap under-read when HTTP response body exceeds INT_MAX (~2 GB). Junio’s review confirms the type change is correct after verifying `xwrite()` already clamps via `MAX_IO_SIZE`; no further adjustments needed. Patrick Steinhardt’s prior review also confirmed correctness by tracing the `xwrite` loop. Simon Richter suggested using `off_t` instead of `size_t` for `posn`, arguing that `off_t` is the conventional type for file positions and is guaranteed to be 64-bit when large file support (`O_LARGEFILE`) is enabled. Junio’s latest reply rejects this suggestion, noting that `posn` is used to offset into a contiguous in-core buffer (`ptr + posn`) whose allocation size is measured in `size_t`, so `size_t` is the correct type to avoid type mismatches when calculating the offset. The discussion is resolved in favor of `size_t` without introducing new edge cases.
  - wrapper.c: `read_in_full()` and `write_in_full()` now reject any requested byte count exceeding `SSIZE_MAX` upfront, returning `EINVAL` instead of silently overflowing the `ssize_t` accumulator
  - date.c: `approxidate_alpha()` now uses `mult_overflows` to check `tl->length * *num` for overflow before multiplication; on platforms with unsigned `time_t`, it also rejects counts exceeding `INT_MAX` or the maximum value of `time_t` to prevent truncation or negative offsets. Junio’s reply clarifies this hardening applies only to local user input, not stored commit timestamps. Phillip Wood’s review of patch 5 proposes replacing the GCC-only `mult_overflows` with `intmax_t` arithmetic to ensure portability across compilers and `time_t` representations, and suggests a simpler truncation check (`(timestamp_t)((int)number) != number`) for unsigned `time_t` platforms.
  - git-compat-util.h: added fallback definition of `SSIZE_MAX` for platforms lacking it; macros now include operand-width assertion via `BUILD_ASSERT_OR_ZERO` (per Phillip Wood’s review) and are documented as GCC-only (non-GNU compilers fall back to no-op). The macros evaluate arguments multiple times, which is explicitly documented in the macro comment.
- No on-disk format changes; no new CLI options or config keys
- No test coverage added for the hardened edge cases

Open questions and loose ends
- Absence of test coverage for the hardened edge cases may prompt review requests
- Potential for future reuse of the new macros elsewhere in the codebase
- **Platform-specific risk**: Phillip Wood challenges the commit message’s claim that byte counts exceeding `SSIZE_MAX` "never" occur in practice, citing a 2019 bugfix (`c14e5a1a50`) where `ssize_t` was narrower than `size_t` on NonStop and similar platforms. Randall S. Becker (NonStop port maintainer) cc’d to confirm whether this remains a live issue. If validated, the patch’s defensive check may be more than theoretical hardening—it could address a real, platform-dependent overflow risk.
- **Macro implementation**: Phillip Wood’s review of patch 4 raises three technical points: (1) `mult_overflows` relies on GNU `typeof`, making it unavailable on non-GCC compilers; (2) the macro evaluates arguments multiple times, which is now documented; (3) operand-width mismatch risk is mitigated by `BUILD_ASSERT_OR_ZERO`. His review of patch 5 proposes replacing the GCC-only `mult_overflows` with `intmax_t` arithmetic for portability, and suggests a simpler truncation check for unsigned `time_t`. Resolution depends on Johannes addressing these points in a v2.
- **Process suggestion**: Harald Nordgren proposes enabling Coverity as a GitHub CI check to prevent regressions once the current backlog is cleared. This is a low-weight, surface-level suggestion that does not engage with the technical content of the patches and does not imply any code changes or deeper technical discussion.

Subject: [PATCH 0/5] Coverity-inspired integer-overflow fixes

Core problem or goal
Eliminate integer overflows and unsafe arithmetic in Git’s codebase flagged by Coverity, hardening several subsystems (archive-tar, http, wrapper, date) against undefined behavior, crashes, or silent corruption when arithmetic exceeds type limits. The fixes are defensive and target latent issues rather than observed bugs.

Current status
Under review; v2 posted. Patches 1 (archive-tar.c) and 2 (http.c) remain uncontroversial and ready for integration. Patch 3 (wrapper.c) is resolved by design in v2. Patches 4 (git-compat-util.h) and the original patch 5 (date.c) are withdrawn. A simplified, portable hardening for date.c is now proposed in the thread but not yet posted as a v3 patch. Junio’s latest "What's cooking" report still marks the series as “Waiting for response” to Phillip Wood’s remaining concerns on patches 4 and 5; the series will expire from Junio’s integration branches if no further activity occurs.

Key technical details
- Files touched: archive-tar.c, date.c, git-compat-util.h, http.c, wrapper.c
- Subsystems hardened: archive-tar (zero-length input), http (size_t for byte positions), wrapper (implausibly large byte counts), date (user-supplied number truncation)
  - http.c: `posn` variable in `fwrite_sha1_file()` changed from `int` to `size_t` to match the total size parameter, preventing heap under-read when HTTP response body exceeds INT_MAX (~2 GB). Junio’s review confirms the type change is correct after verifying `xwrite()` already clamps via `MAX_IO_SIZE`; no further adjustments needed. Patrick Steinhardt’s prior review also confirmed correctness by tracing the `xwrite` loop. Simon Richter suggested using `off_t` instead of `size_t` for `posn`, arguing that `off_t` is the conventional type for file positions and is guaranteed to be 64-bit when large file support (`O_LARGEFILE`) is enabled. Junio’s latest reply rejects this suggestion, noting that `posn` is used to offset into a contiguous in-core buffer (`ptr + posn`) whose allocation size is measured in `size_t`, so `size_t` is the correct type to avoid type mismatches when calculating the offset. The discussion is resolved in favor of `size_t` without introducing new edge cases.
  - wrapper.c: `read_in_full()` and `write_in_full()` now reject any requested byte count exceeding `SSIZE_MAX` upfront, returning `EINVAL` instead of silently overflowing the `ssize_t` accumulator. In v2, `write_in_full()`’s return type is changed from `size_t` to `int` (returning `0` on success), eliminating the overflow risk entirely. A new helper, `read_in_full_or_error()`, is introduced for callers that only care about success/failure; it returns `0` or `-1`. Callers that still need the byte count remain with the original `read_in_full()`, which now errors out if the requested size is too large. The commit message’s original claim that "git never passes such large counts" is softened in v2, acknowledging that future callers might inadvertently trigger the issue.
  - date.c: hardening of `approxidate_alpha()` is now proposed in simplified form: the user-supplied number is explicitly capped at `INT_MAX` (rejecting anything larger), and the multiplication is performed only after this guard. This avoids the need for compiler-specific overflow detection and handles both signed and unsigned `time_t` uniformly. The original hardening intended to use `mult_overflows` to check `tl->length * *num` for overflow before multiplication; on platforms with unsigned `time_t`, it would also have rejected counts exceeding `INT_MAX` or the maximum value of `time_t` to prevent truncation or negative offsets. Junio’s reply clarifies this hardening was intended to apply only to local user input, not stored commit timestamps. Phillip Wood’s review of the original patch 5 proposed replacing the GCC-only `mult_overflows` with `intmax_t` arithmetic to ensure portability across compilers and `time_t` representations, and suggested a simpler truncation check (`(timestamp_t)((int)number) != number`) for unsigned `time_t` platforms. The simplified approach now proposed by Johannes adopts the truncation check and avoids the overflow-checking macros entirely.
- No on-disk format changes; no new CLI options or config keys
- No test coverage added for the hardened edge cases

This is the final patch in Harald Nordgren’s five-part series introducing a matching-inspired fetch mode for shallow repositories. Patch 5/5 makes `--limited-fetch` the default when adding a remote to a shallow repository, ensuring that `git remote add` does not set up a wildcard refspec that would force `git fetch` to negotiate history for every branch the remote has.

The change is small and surgical: it adds a single condition in `builtin/remote.c` that checks `is_repository_shallow(the_repository)` when the `limited_fetch` flag is unset (`-1`). If the repository is shallow and neither `-t/--track` nor `--mirror` was given, `--limited-fetch` is turned on automatically. The documentation in `git-remote.adoc` is updated to explain the new default, and four new tests in `t/t5505-remote.sh` verify that the shallow-repository default works as intended, that `-t` still overrides it, that full repositories keep the old wildcard behavior, and that `--no-limited-fetch` disables it explicitly.

The patch is uncontroversial and ready for review. It builds directly on the infrastructure introduced in earlier patches (the `limited_fetch` flag, the `remote.<name>.refmap` configuration, and the dynamic branch inference logic) and does not introduce new technical debt. The shallow check is implemented without hardcoding `the_repository`, and the precedence rules established in Patch 1/5 (`.fetch` takes precedence over `.refmap`) remain intact. This is a clean, well-motivated change that addresses a real performance pain point for shallow-repository users without breaking backward compatibility.

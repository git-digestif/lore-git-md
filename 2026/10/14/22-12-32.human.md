This is a follow-up in the ongoing `core.indexLockTimeout` series, responding to Junio C Hamano’s second round of maintainer feedback on Patch 1/2. The author, Jun Wu, addresses the three technical questions Junio raised about the race-avoidance logic and broader implications of the implementation.

Jun Wu clarifies that when the index was already read in-memory and the lock is held or the index updated by another process, the intended behavior is to **force a cache invalidation** once the lock is acquired. This means commands would need to handle the case where their in-memory index is dropped and potentially re-apply their changes (e.g., `git add -i` would re-apply the "add" operation). He suggests this is how Mercurial’s lock infrastructure works and implies it’s a reasonable model for Git to adopt. For read-only commands that take the lock purely for consistency (e.g., `git rm --dry-run`), the change will make them wait, but Jun Wu argues this is acceptable since a single read of the index is already consistent (the index is replaced atomically).

On the reliability of `repo->index->initialized`, Jun Wu confirms it does not always mean the index was read from disk — it can also be set by `unpack_trees` when the in-memory index is created from scratch (e.g., during `git read-tree`). However, he notes that in practice, commands like `clone` and `read-tree` take the lock *before* calling `unpack_trees`, so the initialized flag is only set after the lock is held, avoiding the race condition. This suggests the current implementation is safe, though the edge case Junio raised remains a theoretical concern.

The response also touches on the trade-off between command success rate and duration, with Jun Wu arguing that users prioritize commands working over occasional slowness. He remains open to adjusting the default timeout (1 second) and cites Mercurial’s 10-minute default as a precedent. The discussion about whether the index lock should cover the working copy files (not just the index) is left unresolved, though Jun Wu notes that most commands writing to the working copy also update the index stat, so the distinction may not matter in practice.

This reply advances the thread by clarifying the intended behavior for edge cases, but the maintainer’s concerns about cache invalidation and lock semantics are not yet fully resolved. The series is still under review, and Jun Wu will likely need to update the commit message and cover letter to reflect these clarifications before sending a v2. The patch looks well-motivated and addresses a real pain point for IDE users, but the implementation’s subtleties (e.g., cache invalidation, lock scope) may require further iteration.

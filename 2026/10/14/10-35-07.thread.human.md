This thread is about a performance regression in Git's connectivity check during deepening fetches, reported and fixed by Igor Wiedler. The issue surfaced in CI environments where shallow fetches from large alternates (millions of objects) would trigger an unnecessary full-history traversal, turning a sub-second operation into a multi-minute delay. The fix is surgical: it moves the `--alternate-refs` flag in `connected.c` so it only applies to non-deepening fetches, preserving correctness while restoring expected performance.

Igor's patch includes two new tests in `t/t5618-alternate-refs.sh` that verify the `rev-list` argument logic via `GIT_TRACE2_EVENT` without asserting behavioral changes, since the outcome remains correct for complete alternates. The commit message is detailed, explaining both the historical context (the regression was introduced by commits 39b44ba771 and cf1e7c0770) and the real-world impact. No review feedback has appeared yet, so the patch is still under initial consideration. If accepted, this should resolve a significant pain point for CI users without affecting other workflows.

This is a review comment on the third patch in Johannes Schindelin’s five-patch series hardening Git against integer overflows flagged by Coverity. The series as a whole is a defensive effort to eliminate latent undefined-behavior risks in several subsystems, and this patch specifically targets the `read_in_full()` and `write_in_full()` wrapper functions in `wrapper.c`.

Phillip Wood’s review raises a substantive question about the patch’s assumptions: it questions whether Git truly never passes byte counts exceeding `SSIZE_MAX` in practice. Phillip cites a 2019 bugfix (c14e5a1a50) where `ssize_t` was narrower than `size_t` on some platforms, and asks Randall S. Becker (the NonStop port maintainer) whether this discrepancy still exists on NonStop systems. The concern is that if `size_t` can represent values larger than `SSIZE_MAX`, Git might already be passing such counts in some code paths, and rejecting them upfront could break existing functionality rather than hardening it.

The review is narrowly focused but technically sharp: it identifies a potential blind spot in the patch’s reasoning and seeks platform-specific confirmation. This is not a surface-level nit about style or wording, but a substantive challenge to the patch’s core premise. If Randall confirms that NonStop platforms still have `ssize_t` narrower than `size_t`, the patch may need to be reworked or its scope adjusted. For now, the thread is paused awaiting that input.

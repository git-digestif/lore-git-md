Thread identity
Subject: pretty: fix indentation loss after newline in `%w()` format
Series version: standalone patch (v2)
Originating author: Andy Koppe
Thread type: bugfix patch

Core problem or goal
Fix a regression in `strbuf_add_wrapped_text()` where the first whitespace character after a hard line break (e.g., `%n`) is incorrectly skipped, causing misaligned output in `git log --format=%w(...)` and related commands. The bug manifests when a newline is followed by whitespace; the indentation is lost, making the output visually incorrect. The regression affects real-world use cases such as wrapping commit messages with `%w(72)%B` or displaying lists of files/changes with consistent indentation, where misalignment breaks readability, especially when combined with `--graph` or wide terminal windows. The patch also addresses the historical ambiguity of the 18-year-old behavior (introduced in commit `ae0b270230` in 2007), which was likely unintentional: newlines before alphanumeric characters are replaced with a space, while newlines before punctuation or whitespace are preserved—but with the first whitespace character *consumed*. The v2 patch now includes the missing documentation update for `Documentation/pretty-formats.adoc`, clarifying the corrected behavior.

Current status
Under review, with maintainer endorsement. The patch is a single commit (v2) that surgically fixes the logic in `utf8.c` to distinguish between "line too long" (where skipping a space is correct) and "hard line break" (where skipping is wrong). Junio C Hamano and René Scharfe have both endorsed the fix, provided the documentation gap is addressed—which v2 now does. The patch appears ready to proceed to `next` once final reviews are complete.

Key technical details
- Files touched: `utf8.c` (core fix), `Documentation/pretty-formats.adoc` (documentation update), `t/t4202-log.sh` (new regression test), `t/t4205-log-pretty-formats.sh` (updated test)
- Subsystem: pretty-printing (`%w()` format specifier)
- New/renamed symbols: none
- Old behavior: `%w(11) This is%n  the %s` outputs " the ..." (indentation lost); similarly, `%w(72)%B` or lists of files/changes lose one space of indentation after `%n`, breaking alignment (e.g., " Frobble." instead of "  Frobble."). The behavior was undocumented and likely unintentional.
- New behavior: `%w(11) This is%n  the %s` outputs "  the ..." (indentation preserved); alignment is maintained in real-world scenarios like commit message wrapping or file lists. The fix distinguishes between "line too long" (space-skipping correct) and "hard line break" (space-skipping incorrect). The documentation now explicitly states how newlines are handled (replaced by spaces when followed by alphanumeric characters, but preserving existing indentation).
- Test coverage: regression case (hard line break + whitespace), edge case with `%+d` (newline + decoration text), and historical behavior (newline before alphanumeric vs. punctuation/whitespace)
- On-disk format: no changes

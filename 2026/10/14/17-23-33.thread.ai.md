Subject: pretty: fix indentation loss after newline in `%w()` format
Series version: standalone patch (no series)
Originating author: Andy Koppe
Thread type: bugfix patch

Core problem or goal
Fix a regression in `strbuf_add_wrapped_text()` where the first whitespace character after a hard line break (e.g., `%n`) is incorrectly skipped, causing misaligned output in `git log --format=%w(...)` and related commands. The bug manifests when a newline is followed by whitespace; the indentation is lost, making the output visually incorrect.

Current status
Under review. The patch is a single commit that surgically fixes the logic in `utf8.c` to distinguish between "line too long" (where skipping a space is correct) and "hard line break" (where skipping is wrong). It adds a new test in `t/t4205-log.sh` and updates an existing test in `t/t4205-log-pretty-formats.sh` to verify the corrected behavior.

Key technical details
- Files touched: `utf8.c` (core fix), `t/t4205-log.sh` (new test), `t/t4205-log-pretty-formats.sh` (updated test)
- Subsystem: pretty-printing (`%w()` format specifier)
- New/renamed symbols: none
- Old behavior: `%w(11) This is%n  the %s` outputs " the ..." (indentation lost)
- New behavior: `%w(11) This is%n  the %s` outputs "  the ..." (indentation preserved)
- Test coverage: regression case (hard line break + whitespace) and edge case with `%+d` (newline + decoration text)
- On-disk format: no changes

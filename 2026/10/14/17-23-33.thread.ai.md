Subject: pretty: fix indentation loss after newline in `%w()` format
Series version: standalone patch (no series)
Originating author: Andy Koppe
Thread type: bugfix patch

Core problem or goal
Fix a regression in `strbuf_add_wrapped_text()` where the first whitespace character after a hard line break (e.g., `%n`) is incorrectly skipped, causing misaligned output in `git log --format=%w(...)` and related commands. The bug manifests when a newline is followed by whitespace; the indentation is lost, making the output visually incorrect. The regression affects real-world use cases such as wrapping commit messages with `%w(72)%B` or displaying lists of files/changes with consistent indentation, where misalignment breaks readability, especially when combined with `--graph` or wide terminal windows. The patch also addresses the historical ambiguity of the 18-year-old behavior (introduced in commit `ae0b270230` in 2007), which was likely unintentional: newlines before alphanumeric characters are replaced with a space, while newlines before punctuation or whitespace are preserved—but with the first whitespace character *consumed*.

Current status
Under review. The patch is a single commit that surgically fixes the logic in `utf8.c` to distinguish between "line too long" (where skipping a space is correct) and "hard line break" (where skipping is wrong). It adds a new test in `t/t4205-log.sh` and updates an existing test in `t/t4205-log-pretty-formats.sh` to verify the corrected behavior. René Scharfe’s review raises a backward-compatibility concern but leans toward accepting the change if the documentation gap is addressed.

Key technical details
- Files touched: `utf8.c` (core fix), `t/t4205-log.sh` (new test), `t/t4205-log-pretty-formats.sh` (updated test)
- Subsystem: pretty-printing (`%w()` format specifier)
- New/renamed symbols: none
- Old behavior: `%w(11) This is%n  the %s` outputs " the ..." (indentation lost); similarly, `%w(72)%B` or lists of files/changes lose one space of indentation after `%n`, breaking alignment (e.g., " Frobble." instead of "  Frobble."). The behavior was undocumented and likely unintentional.
- New behavior: `%w(11) This is%n  the %s` outputs "  the ..." (indentation preserved); alignment is maintained in real-world scenarios like commit message wrapping or file lists. The fix distinguishes between "line too long" (space-skipping correct) and "hard line break" (space-skipping incorrect).
- Test coverage: regression case (hard line break + whitespace), edge case with `%+d` (newline + decoration text), and historical behavior (newline before alphanumeric vs. punctuation/whitespace)
- On-disk format: no changes

Open questions and loose ends
- **Backward-compatibility**: René Scharfe notes that the existing test in `t4205` (using `%+d`) will need updating, and users who relied on the old behavior could work around it by adding an extra space. The behavior was undocumented, which weakens the case for preserving it, but the risk remains.
- **Documentation**: The `%w()` format’s behavior regarding newlines and whitespace is not documented in `pretty-formats(7)`. The patch should either document the new behavior or clarify the historical ambiguity to prevent future regressions.

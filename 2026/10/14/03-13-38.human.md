This is the third patch in Jon Simons' **v2 performance-focused feature series** (12 patches total) that speeds up `git push` refspec matching for large-scale branch deletions. This patch delivers **55–82% of the series' total speedup** by eliminating the `mkpath()` overhead in `refname_match()`.

The change replaces `mkpath()`-formatted string comparisons with direct prefix/suffix matching via a reused `match_parse_rule()` helper. This avoids `strbuf_vaddf()` and reduces the matching cost from O(n) per rule to a single `memcmp()`. Benchmark timings show dramatic improvements: pushing 100 delete refspecs to a 100k-ref server drops from **2.5s to 0.49s** (empty client) and from **6.68s to 1.18s** (mirror client).

The patch also **fixes a long-standing behavioral quirk**: `refname_match()` no longer strips leading `./` from refnames (e.g., `./refs/heads/foo` no longer silently matches `refs/heads/foo`). This aligns with prior cleanups (e.g., `6cd4a8982d`) that removed `cleanup_path()` from refname handling. New tests in `t5510-fetch.sh` and `t5516-fetch-push.sh` ensure the change doesn’t regress fetch or push workflows.

The commit message is exemplary—it documents the performance impact, explains the behavioral change with historical context, and justifies the removal of `mkpath()` as a filepath-specific function misused for refnames. The code itself is clean: the `match_parse_rule()` helper is moved earlier in `refs.c` for reuse, and the diff is minimal despite the significant optimization.

This patch is a clear win: it addresses a real scalability bottleneck, fixes a subtle bug, and maintains test coverage. The only open question is whether any obscure workflows relied on the old `./` stripping behavior, but the new tests and input validation in patch 1 (added in v2) should catch such cases early.

This is a feature patch series (v9 of 5 patches) that introduces a "matching-inspired" fetch mode for shallow repositories, addressing a long-standing performance issue where `git fetch` in a shallow clone negotiates history for all remote branches, causing slowdowns or hangs.

The series is now in excellent shape after addressing all prior review feedback. The key change in v9 is a clean split of the control-flow reorganization out of the preliminary helper-extraction patch (2/5) and into the feature patch (3/5), making the refactoring commit a simpler, uncontroversial extraction. The NULL-check for `branch` in the new `collect_upstream_from_remote()` helper is also restored, fixing a potential segfault. These changes directly respond to Junio’s latest review of v8, and the respin looks correct.

The core idea remains unchanged: when a remote is configured with `remote.<name>.refmap` but no `remote.<name>.fetch` refspec, `git fetch` dynamically infers which branches to fetch by looking at the `@{upstream}` of local branches that track that remote. This avoids fetching all remote branches while still keeping local tracking branches up to date. The `--limited-fetch` flag for `git remote add` (patch 4/5) and the shallow-repository default (patch 5/5) make this mode easily accessible, with thorough test coverage verifying edge cases like bare fetches, duplicate tracking, and cross-remote setups.

The implementation is clean, with no hardcoded `the_repository` usage, clear documentation, and a sensible precedence rule (`remote.<name>.fetch` takes precedence when both are configured). The test suite is particularly strong, with 119 lines of new coverage in `t/t5586-fetch-refmap.sh` alone. The series is a strong candidate for `next` once Junio re-reviews the respun patch 2/5.

This thread is about a bugfix for an inconsistency in how the files ref backend handles root refs (like `HEAD` and `ORIG_HEAD`) in its loose ref cache. Andy Koppe identified the issue—root refs are only included in the cache if the `REFS_FOR_EACH_INCLUDE_ROOT_REFS` flag is set during the *first* iteration that creates the cache, leading to inconsistent behavior—and proposed a fix that keeps root refs out of the shared cache entirely, instead creating a separate temporary ref cache for them when requested.

The patch is under review, with Patrick Steinhardt raising questions about whether the solution is the most efficient or conceptually clean approach. Junio C Hamano has now weighed in, suggesting an alternative design: maintaining two persistent caches (one for refs under `refs/` and another for root refs) and letting callers combine them as needed. This would avoid recreating the root ref cache for every iterator, addressing Patrick’s performance concern while keeping the logic simple. Neither approach has been rejected outright, and the discussion remains focused on trade-offs rather than finalizing a design.

The patch itself is minimal, touching only `files-backend.c` and adding a test in `t/t6302-for-each-ref-filter.sh` to verify `--include-root-refs` works correctly with `--merged`. The reftable backend is unaffected, and the fix doesn’t change the on-disk format or user-facing behavior beyond fixing the inconsistency. The main open question is whether to adopt Junio’s suggested design or stick with the current approach. No other alternatives have been proposed yet.

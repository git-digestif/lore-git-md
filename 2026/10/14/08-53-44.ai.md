This is a **refactoring and performance patch series** targeting the object database (ODB) subsystem, specifically the alternates mechanism in the "files" backend. It is the **second iteration (v2)** of Patrick Steinhardt’s follow-up cleanups to his earlier `ps/odb-files-alternates` branch, which migrated alternates handling into the files backend.

The series now consists of **six patches**, up from five in v1. The new patch (5/6) addresses Justin Tobler’s feedback from v1 by tightening error handling: it prevents Git from attempting to re-fetch objects when the repository is corrupt, failing immediately with `ODB_READ_ERROR` instead. The other five patches are unchanged from v1, retaining their focus on performance optimizations (patches 1-2) and internal API cleanup (patches 3-4, 6). The net diffstat shows a reduction of **54 lines**, reflecting the series’ emphasis on simplification.

Key technical details remain consistent with v1: the patches reorder loops in the "files" backend to prioritize packfile checks over loose-object `stat()` calls (patches 1-2), move the second object read logic into the backend (patch 3), remove a redundant read loop (patch 4), and drop the unused `local` flag from the generic ODB source API (patch 6). The new patch 5/6 modifies `do_oid_object_info_extended()` to fail early on corruption, aligning with Justin’s suggestion to treat such cases as unrecoverable errors. The series still touches **12 files**, primarily in the `odb/` directory, and is built on top of Patrick’s earlier work, with no user-visible behavior changes or on-disk format modifications.

The unresolved design question from v1—whether the `ODB_FOR_EACH_OBJECT_LOCAL_ONLY` flag should be removed—remains open, but Patrick’s skepticism about its current callers (`git pack-objects --local` and `add_unseen_recent_objects_to_traversal()`) suggests this may be addressed in a future series. The new error-handling patch (5/6) resolves Justin’s feedback while keeping the change scoped to a single, focused commit. The series looks **well-motivated and uncontroversial**, with the v2 update addressing the only substantive review concern from v1. The patches are likely to proceed to `next` once any remaining nits are addressed.

This is the first patch in a five-part **bugfix series** for `git worktree repair`, addressing Junio C Hamano’s review feedback by splitting the original refactoring into smaller, focused commits. This patch aligns `.git` file handling in `repair_worktree_at_path()` with `repair_gitfile()` by replacing `read_gitfile_gently()` with `read_gitfile_raw()`, moving path resolution and repository validation to the caller. The change eliminates reliance on the non-reentrant `read_gitfile_gently()` and prepares the codebase for subsequent patches that will further centralize `.git` file parsing.

The patch touches only `worktree.c`, introducing no new user-visible behavior but laying the groundwork for stricter `.git` file validation in later commits. Key technical details include:
- **New helper usage**: `read_gitfile_raw()` is now used to parse `.git` files, returning raw content in a `strbuf` instead of a dynamically allocated string. This avoids memory leaks and aligns with the approach already used in `repair_gitfile()`.
- **Path resolution**: The patch explicitly handles both absolute and relative paths in `.git` files, stripping the `.git` suffix and appending the relative path when necessary. This logic was previously implicit in `read_gitfile_gently()`.
- **Error handling**: Repository validation (`is_git_directory()`) is now performed after path resolution, with clearer error messages for cases where the `.git` file does not point to a valid repository. The patch preserves the existing fallback to inferred backlinks when the `.git` file is invalid but an inferred path exists.
- **Memory management**: The patch replaces `free(dotgit_contents)` with `strbuf_release(&contents)`, reflecting the shift to `strbuf`-based parsing.

The commit message is clear and concise, explaining the motivation (consistency with `repair_gitfile()`) and the mechanical changes. The diff is well-structured, with no unrelated modifications. This patch is purely preparatory—it does not yet introduce the stricter `.git` file parsing (e.g., rejecting `gitdir:` prefixes without trailing spaces) or the validation logic that prevents repairs on unrelated worktrees. Those changes appear in later patches (2–5), making this a clean, incremental step.

No test failures or edge cases are introduced here, as the patch does not alter behavior. The stricter parsing rules and validation will be tested in subsequent commits. The patch is unlikely to be controversial, as it refactors internal logic without changing user-facing functionality. Junio’s earlier review of v1 requested this kind of separation, and the v2 series delivers it effectively. The main risk is whether the new path-resolution logic handles all edge cases (e.g., symlinks, unusual path formats), but the existing test suite should catch regressions. This patch is a solid foundation for the rest of the series.

This thread is about a bugfix patch from Andy Koppe that corrects a long-standing but undocumented regression in Git’s `%w()` pretty-printing format, where the first whitespace character after a hard line break (like `%n`) is incorrectly skipped, breaking indentation in formatted output like `git log --format=%w(72)%B`. The issue affects real-world use cases such as commit message wrapping and file lists, where misalignment disrupts readability.

The patch itself is a surgical fix to `utf8.c` that distinguishes between "line too long" (where skipping a space is correct) and "hard line break" (where it’s not). It includes new and updated tests in `t/t4205-log.sh` to verify the corrected behavior. René Scharfe’s review raised a backward-compatibility concern but leaned toward accepting the change if the documentation gap is addressed—specifically, the lack of clarity in `pretty-formats(7)` about how `%w()` handles newlines and whitespace.

Junio C Hamano has now weighed in to endorse René’s position, emphasizing that the undocumented nature of the old behavior makes it fair to change, provided the documentation is updated.

This is the **final version (v3) of a bugfix patch series** that was already merged to `seen`. The series fixes a critical bug in Git’s object database (ODB) transaction layer where temporary object directory migration fails when Git is configured with a compatibility hash (e.g., SHA-1/SHA-256 interop) and batch fsync of loose objects is enabled. The core issue is that the migration logic does not correctly merge the "loose-object-idx" file—a mapping between objects and their compatibility hashes—when a preexisting index exists in the primary object directory. This can cause ODB transaction failures and potential data loss.

The v3 series is functionally identical to v2, which addressed all blocking concerns raised by Patrick Steinhardt, including atomicity (replacing append-under-lock with temp-file-then-rename) and locking (introducing a finite 1000ms timeout). The only changes in v3 are minor optimizations and documentation clarifications: the source loose-object-idx file is now read outside the lock to reduce contention, and a comment was added to `loose_object_idx_merge()` in `loose.h` to clarify its purpose. The series remains split into four patches: (1) locking timeout, (2) parsing refactor, (3) writing refactor, and (4) the core migration fix.

The regression test (`t/t1016-compatObjectFormat.sh`) verifies that all entries from both the temporary and primary indices are preserved after migration. While the series resolves the immediate bug, it defers deeper design flaws in the loose-object-idx mechanism (unsorted files, no deduplication, no stale-entry pruning) to future work. Junio C Hamano merged the series to `seen` with no functional changes but noted a minor integration artifact: the original `repo_write_loose_object_map()` function lost all its callers and will be removed in a follow-up cleanup. This is routine post-merge hygiene and does not affect correctness.

The fix is high-priority for ODB stability, particularly for users with compatibility-hash + batch-fsync enabled. The atomic-write approach and thorough test coverage make this a robust solution to the immediate issue. No further changes are expected beyond the planned cleanup.

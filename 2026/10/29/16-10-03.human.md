This is a **substantive review** in the ongoing `git worktree list` filtering discussion, focusing on a critical safety concern. Phillip Wood responds to Ben Knoble’s observation that the proposed extension of `git for-each-ref`’s `%(worktreepath)` atom—intended to let users filter worktrees by branch state—could inadvertently expose mid-rebase worktrees to deletion via `git worktree remove`. Both agree this would risk data loss and that `git worktree remove` should fail by default for worktrees in transient states (rebase, bisect) unless explicitly forced.

The exchange underscores a key limitation of the current design pivot: while extending `%(worktreepath)` to report paths for rebasing/bisecting branches aligns with Git’s existing behavior (e.g., `git worktree add` and `git branch -d`), it creates a new hazard when combined with porcelain commands. The thread has already identified other drawbacks of using `for-each-ref` as a filtering mechanism (e.g., no NUL-terminated output, no main/linked worktree distinction), and this adds another: the risk of surfacing worktrees in high-risk states. Phillip’s comment frames the issue as a bug in `git worktree remove` rather than the filtering mechanism itself, but the practical effect is the same—users or scripts could still trigger unsafe deletions.

No concrete solution is proposed here, but the discussion reinforces the need for tighter integration between filtering and safety guarantees. The thread remains open, with unresolved questions about whether `for-each-ref --merged` should exclude rebasing worktrees by default or leave that responsibility to `git worktree remove`. This is a well-motivated concern that looks likely to shape the final design.

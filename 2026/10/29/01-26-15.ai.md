This is the follow-up patch for the `fast-import` completion issue identified in the earlier thread. It addresses the edge case René Scharfe reported: when `git fast-import --git-completion-helper` is invoked (as Bash completion does), the command would block waiting for input and leave behind temporary pack files (`tmp_pack_*`). The patch moves the `--git-completion-helper` check to the very start of `cmd_fast_import()`, before any input is read or temporary files are created, so the helper can return its option list immediately without side effects.

The change is minimal and surgical: a four-line addition in `builtin/fast-import.c` that checks for the completion helper flags right after the `-h` usage check but before `fast_import_state_init()` is called. The new test in `t/t9300-fast-import.sh` verifies that no temporary pack files are created when the helper is invoked, and that the expected option list is printed. This patch depends on Christian Couder’s `cc/early-scan-options` series being stable, as noted in the thread context, but does not itself require changes to that series.

The motivation is clear and well-documented: the patch fixes a user-visible regression (completion freezing) that would occur once `NO_PARSEOPT` is removed from `fast-import` in the earlier patch. The test coverage is appropriate for the change, and the commit message explains both the problem and the solution concisely. No controversy or open questions are apparent; this looks like a straightforward, well-crafted fix.

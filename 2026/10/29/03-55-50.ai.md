This is a bugfix for the notes subsystem. The patch addresses a race condition in `git notes add` (and related commands) where concurrent note additions can silently overwrite each other, causing data loss. The author discovered the issue using Rewind, a deterministic VM that replays thread schedules to expose concurrency bugs, and confirmed it occurs in real-world scenarios (25 of 30 runs lost a note on a plain Linux machine).

The fix modifies `commit_notes()` to track the commit from which notes were originally read (`t->base_oid`) and use it as both the parent of the new notes commit and the expected old value for the ref update. If another process updates the ref concurrently, the command now fails with "cannot lock ref" instead of silently overwriting. The patch touches `notes-utils.c`, `notes.c`, `notes.h`, and adds a test case in `t/t3301-notes.sh` to verify the fix.

Key technical details: the change introduces a new `base_oid` field to `struct notes_tree` to remember the commit hash, modifies `init_notes()` to populate it during initialization, and updates `commit_notes()` to use it in the ref update transaction. The test case simulates concurrent note addition by using an editor script that adds a note to a different commit while the outer `git notes add` is waiting for editor input.

The commit message is clear and includes both a high-level explanation of the problem and specific reproduction statistics. The patch appears well-scoped and addresses the root cause without introducing unnecessary complexity. The test coverage is appropriate for the change.

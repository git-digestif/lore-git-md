This is a **design pivot** in the `git worktree list` filtering discussion. Jasper Mayone proposes abandoning the `--branch=<branch>` option entirely and instead enhancing `git for-each-ref`'s `%(worktreepath)` atom to report the worktree path even when the branch is being rebased or bisected. The change would close the gap Kristoffer Haugsbakk identified (rebasing/bisecting worktrees appearing detached) by making `%(worktreepath)` consistent with how `git worktree add` and `git branch -d` already treat those branches.

The proposal is narrower in scope than the original `--branch` patch: it touches only `ref-filter.c` (to extend `%(worktreepath)`) and avoids introducing new CLI options, so the naming and extensibility questions raised by Eric Sunshine and Junio do not arise. Jasper frames the behavior change as a bug fix, since the rest of Git already considers a rebasing/bisecting branch "checked out," but he explicitly asks whether any scripts rely on the current empty value. Phillip Wood’s earlier concern about main-worktree annotation remains unaddressed but is acknowledged as a potential follow-up.

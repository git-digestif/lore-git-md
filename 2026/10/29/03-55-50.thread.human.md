This thread is about a bugfix for a race condition in Git's notes subsystem that can cause data loss when multiple `git notes add` commands run concurrently. Farid Zakaria identified the issue using Rewind, a deterministic VM for exposing concurrency bugs, and confirmed it occurs reliably in practice—25 out of 30 test runs lost a note on a standard Linux machine.

The fix modifies `commit_notes()` to track the commit from which notes were originally read (`t->base_oid`) and use it as both the parent of the new notes commit and the expected old value for the ref update. If another process updates the ref concurrently, the command now fails with "cannot lock ref" instead of silently overwriting. The patch touches `notes-utils.c`, `notes.c`, and `notes.h`, and adds a test case in `t/t3301-notes.sh` to verify the behavior. The change is well-scoped, addresses the root cause, and includes clear reproduction statistics in the commit message.

No review feedback or objections have appeared yet, but the patch looks uncontroversial and ready for consideration. The fix is a straightforward improvement to concurrency safety in a core subsystem.

This thread tackles a race condition in Git’s notes subsystem, where concurrent `git notes add` operations can silently overwrite each other, leading to data loss. Farid Zakaria’s patch fixes this by making such operations fail outright when a concurrent update is detected, using a new `base_oid` field to track the commit from which notes were read. While the patch is widely agreed to be a correct interim fix—preventing silent data loss—it has sparked a broader debate about Git’s concurrency model for notes. Junio C Hamano and Kristoffer Haugsbakk argue the current approach is overly strict, as it blocks even non-conflicting updates (e.g., notes added to unrelated commits), and propose a retry mechanism using Git’s existing merge/rebase machinery to allow such updates to proceed. Farid has deferred implementing this more complex solution, leaving the door open for others to take the lead.

The discussion has also taken a procedural turn. Kristoffer Haugsbakk flagged Farid’s failure to disclose AI assistance in his review, citing project policy. Farid clarified an earlier ambiguous message but hasn’t yet addressed the disclosure request. Patrick Steinhardt’s recent sarcastic remark—questioning whether Farid’s clarification was human-written—highlights lingering unease about AI’s role in contributions, though it doesn’t advance the technical or procedural debate. The thread remains open, with no follow-up patch posted, and the key unresolved questions are whether the retry mechanism will be implemented, who will drive it, and how Farid will address the AI disclosure concern. Meanwhile, Farid has hinted at two other race-condition bugs (in `credential-cache` and `fsmonitor`) discovered using the same tool, suggesting this may not be the last thread on Git’s concurrency model.

This thread is about a race condition in Git’s notes subsystem where concurrent `git notes add` operations can silently overwrite each other, leading to data loss. Farid Zakaria identified the bug using Rewind, a deterministic VM for exposing concurrency issues, and proposed a fix that prevents silent overwrites by failing when concurrent updates occur. The patch touches `notes-utils.c`, `notes.c`, and related files, adding a `base_oid` field to track the commit from which notes were read and using it to enforce atomic updates.

The fix is under review and has been endorsed as correct for preventing data loss, but a broader design question has emerged: whether the current behavior—failing on *any* concurrent update—is the right long-term trade-off. Kristoffer Haugsbakk raised this, arguing that processes adding notes to unrelated commits shouldn’t interfere with each other. Junio C Hamano responded with a concrete alternative: a retry mechanism where a losing process merges or rebases its attempted note commit on top of the winning process’s commit, allowing non-conflicting updates to proceed. This approach leverages Git’s existing merge machinery and aligns with patterns like `git pull --rebase`.

The thread is now focused on implementing this retry mechanism, with the open question being whether the added complexity justifies the improved concurrency. No follow-up patch has been posted yet, but the discussion suggests a clear path forward. The fix remains a standalone bugfix for now, though the design discussion may influence future work on notes concurrency.

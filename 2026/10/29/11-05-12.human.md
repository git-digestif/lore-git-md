This is a review of Farid Zakaria’s bugfix for the notes subsystem. The patch addresses a race condition in `git notes add` where concurrent processes could silently overwrite each other’s notes, causing data loss. Kristoffer Haugsbakk’s reply is substantive but not tested—it engages with the technical design and proposes an alternative approach without having tried the code.

Kristoffer begins by praising the bug discovery and agreeing with the core fix: tracking the commit from which notes were originally read (`base_oid`) and using it as the expected old value in the ref update prevents silent overwrites and replaces them with a clear failure ("cannot lock ref"). He notes this matches his expectation for how `git update-ref` should work and calls it a "pure improvement" over the current behavior.

However, he then raises a broader design question: what if two processes are adding notes to *different* commits? In that case, he argues, the failure is overly strict—neither process is trying to clobber the other’s work, so they should be able to proceed. He sketches an alternative workflow where a losing process checks whether the winning commit touched the commit it cares about, and if not, retries. This would reduce contention while still preventing data loss.

The review is thoughtful but speculative. It does not identify any flaws in the current patch, nor does it suggest the alternative is strictly necessary—just that it might be "ideal" in some scenarios. The patch itself remains a clean, well-motivated fix for a real bug, and Kristoffer’s feedback does not undermine its correctness or urgency. The discussion is now open for whether the stricter behavior is acceptable or if a more permissive retry mechanism should be pursued.

Subject: [PATCH] notes: fix race condition in concurrent note additions
Series version: standalone patch
Originating author: Farid Zakaria
Thread type: bug report and fix

Core problem or goal
The notes subsystem in Git has a race condition in `git notes add` (and related commands) where concurrent note additions can silently overwrite each other, causing data loss. The bug was discovered using Rewind, a deterministic VM that replays thread schedules to expose concurrency bugs, and confirmed in real-world scenarios (25 of 30 runs lost a note on a plain Linux machine).

Current status
Under review. The patch is a standalone bugfix with no prior versions in this thread. The fix is endorsed as correct for preventing silent data loss, but a broader design question has been raised about whether the current behavior (failing on *any* concurrent update) is the optimal long-term trade-off for the notes subsystem.

Key technical details
- Files touched: `notes-utils.c`, `notes.c`, `notes.h`, `t/t3301-notes.sh`
- New field: `base_oid` in `struct notes_tree` to track the commit from which notes were originally read
- Modified functions: `init_notes()` (populates `base_oid`), `commit_notes()` (uses `base_oid` as parent and expected old value for ref update)
- Behavior change: concurrent note additions now fail with "cannot lock ref" instead of silently overwriting
- Test coverage: new test case in `t/t3301-notes.sh` simulates concurrent note addition using an editor script
- Design trade-off: the current implementation fails on *any* concurrent update to the notes ref, even if the updates target different commits. An alternative approach would allow non-conflicting updates to proceed by retrying after checking whether the winning process’s update affected the commit of interest.

Open questions and loose ends
1. Is the current behavior (failing on any concurrent update) the right long-term trade-off for the notes subsystem, or should a more nuanced retry mechanism be implemented to allow non-conflicting updates to proceed?
2. If a retry mechanism is pursued, what would the implementation look like, and how would it handle edge cases (e.g., repeated conflicts, performance overhead)?

Participant positions
- **Kristoffer Haugsbakk**: Substantive review. Endorses the patch’s core idea (tracking `base_oid` and using it as the expected old value for ref updates) as correct and an improvement over the status quo. Raises a forward-looking design question about whether the current behavior is overly strict, arguing that two processes adding notes to unrelated commits should not interfere with each other. Proposes an alternative approach where a losing process retries after checking for true conflicts, and only fails if the updates target the same commit. This position engages with the patch’s long-term implications for the notes subsystem’s concurrency model.

Related work
None mentioned in the thread. This remains a self-contained bugfix for the notes subsystem, though the design discussion may influence future work on notes concurrency.

Subject: [PATCH] notes: fix race condition in concurrent note additions
Series version: standalone patch (potential follow-up for retry mechanism)
Originating author: Farid Zakaria

Core problem or goal
The notes subsystem in Git has a race condition in `git notes add` (and related commands) where concurrent note additions can silently overwrite each other, causing data loss. The bug was discovered using Rewind, a deterministic VM that replays thread schedules to expose concurrency bugs, and confirmed in real-world scenarios (25 of 30 runs lost a note on a plain Linux machine). The thread explores whether the current fix (failing on any concurrent update) is the optimal long-term trade-off, or if a more nuanced retry mechanism should be implemented to allow non-conflicting updates to proceed.

Current status
Under review. The original patch (standalone bugfix) is endorsed as correct for preventing silent data loss, but the discussion has shifted to broader design and procedural questions. Junio C Hamano has proposed a concrete alternative: a retry mechanism using Git’s existing merge/rebase machinery to allow non-conflicting updates to proceed, while preserving ref integrity. Farid Zakaria has explicitly deferred implementing the retry mechanism, positioning the original patch as a "net-positive" interim fix. **Procedural concerns have surfaced**: Kristoffer Haugsbakk flagged Farid’s failure to disclose AI assistance in reviewing the patch, citing Git’s `Documentation/SubmittingPatches` guidelines under the `[ai]` trailer. No follow-up patch has been posted yet, but Farid has proposed posting two additional race-condition fixes for `credential-cache` and `fsmonitor`, both discovered using Rewind. The thread retains a clear technical direction for a v2 if another contributor takes the lead, but the procedural ambiguity may delay progress.

Key technical details
- Files touched: `notes-utils.c`, `notes.c`, `notes.h`, `t/t3301-notes.sh` (original patch); future changes may extend `commit_notes()` or notes lock/retry logic.
- New field: `base_oid` in `struct notes_tree` to track the commit from which notes were originally read (original patch).
- Modified functions: `init_notes()` (populates `base_oid`), `commit_notes()` (uses `base_oid` as parent and expected old value for ref update) (original patch).
- Behavior change: original patch fails on *any* concurrent update with "cannot lock ref"; proposed retry mechanism would merge/rebase losing updates on top of winning ones, allowing non-conflicting updates to proceed.
- **New technical constraint**: Kristoffer Haugsbakk argues that three-way merges of notes targeting the *same commit* are unsafe due to the opaque nature of note content—merging disjoint edits (e.g., prefix and suffix) could produce semantically invalid results (e.g., interleaved or duplicated content). This invalidates the naive merge/rebase approach for conflicting updates.
- Test coverage: new test case in `t/t3301-notes.sh` simulates concurrent note addition using an editor script (original patch).
- Design trade-offs:
  - Original patch: strict failure-on-concurrency (simple, safe, but overly strict for non-conflicting updates).
  - Proposed alternative: retry with merge/rebase (more complex, but allows non-conflicting updates to proceed; leverages Git’s existing machinery).
  - **Hybrid approach implied**: retry with merge/rebase *only* for non-conflicting updates (notes targeting different commits), while failing fast for conflicting updates (same commit). This requires granular conflict detection (e.g., parsing note content to determine overlap).
- Additional context: Farid has discovered two other race-condition bugs (in `credential-cache` and `fsmonitor`) using Rewind, both with tests, and has proposed posting patches for them. These would likely follow a similar pattern (strict failure on concurrency rather than retry logic), which may reignite the same design debate about whether strict failure is the right long-term trade-off.

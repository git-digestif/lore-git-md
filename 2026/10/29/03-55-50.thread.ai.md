Subject: [PATCH] notes: fix race condition in concurrent note additions
Series version: standalone patch (potential follow-up for retry mechanism)
Originating author: Farid Zakaria
Thread type: bug report and fix

Core problem or goal
The notes subsystem in Git has a race condition in `git notes add` (and related commands) where concurrent note additions can silently overwrite each other, causing data loss. The bug was discovered using Rewind, a deterministic VM that replays thread schedules to expose concurrency bugs, and confirmed in real-world scenarios (25 of 30 runs lost a note on a plain Linux machine). The thread now explores whether the current fix (failing on any concurrent update) is the optimal long-term trade-off, or if a more nuanced retry mechanism should be implemented to allow non-conflicting updates to proceed.

Current status
Under review. The original patch (standalone bugfix) is endorsed as correct for preventing silent data loss, but the discussion has shifted to a broader design question about the notes subsystem’s concurrency model. Junio C Hamano has proposed a concrete alternative: a retry mechanism using Git’s existing merge/rebase machinery to allow non-conflicting updates to proceed, while preserving ref integrity. No follow-up patch has been posted yet, but the thread now has a clear technical direction for a v2.

Key technical details
- Files touched: `notes-utils.c`, `notes.c`, `notes.h`, `t/t3301-notes.sh` (original patch); future changes may extend `commit_notes()` or notes lock/retry logic.
- New field: `base_oid` in `struct notes_tree` to track the commit from which notes were originally read (original patch).
- Modified functions: `init_notes()` (populates `base_oid`), `commit_notes()` (uses `base_oid` as parent and expected old value for ref update) (original patch).
- Behavior change: original patch fails on *any* concurrent update with "cannot lock ref"; proposed retry mechanism would merge/rebase losing updates on top of winning ones, allowing non-conflicting updates to proceed.
- Test coverage: new test case in `t/t3301-notes.sh` simulates concurrent note addition using an editor script (original patch).
- Design trade-offs:
  - Original patch: strict failure-on-concurrency (simple, safe, but overly strict for non-conflicting updates).
  - Proposed alternative: retry with merge/rebase (more complex, but allows non-conflicting updates to proceed; leverages Git’s existing machinery).

Open questions and loose ends
1. Should the retry mechanism be implemented, and if so, how should it handle edge cases (e.g., repeated conflicts, performance overhead, or cases where merge/rebase fails)?
2. Is the added complexity of a retry mechanism justified by the improved concurrency, or does the original patch’s simplicity outweigh its strictness?
3. How should the retry mechanism interact with porcelain vs. plumbing concerns (e.g., should it be opt-in, or always enabled)?

Participant positions

Raises a forward-looking design question about whether the current behavior is overly strict, arguing that two processes adding notes to unrelated commits should not interfere with each other. Proposes a concrete alternative: a retry mechanism where losing processes merge/rebase their attempted note commits on top of the winning process’s commit, allowing non-conflicting updates to proceed. Frames this as a natural extension of Git’s existing merge/rebase patterns (e.g., `git pull --rebase`), avoiding custom conflict detection logic. Implicitly sets the technical direction for a follow-up patch.

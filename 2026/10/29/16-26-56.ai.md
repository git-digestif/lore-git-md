This is a **substantive design discussion** in the `fetch: introduce +: refspec for matching-inspired fetch mode` series (v12), focusing on the unresolved edge case about how `remote.<name>.fetchRefmap` and colon-separated `remote.<name>.fetch` entries should interact. Phillip Wood’s reply challenges Junio C Hamano’s earlier suggestion that the config-based behavior should mirror the command-line precedent (dual storage), arguing that command-line refspecs should **override** the refmap rather than coexist with it.

Phillip proposes two models for the interaction:
1. **Separation of concerns**: `fetchRefmap` handles "where to store" and `fetch` handles "what to fetch", rejecting colon-separated entries in `fetch` to avoid ambiguity. This aligns with the series’ original goal of decoupling the two concerns but would break backwards compatibility for users with existing colon-separated `fetch` entries.
2. **Command-line emulation**: Treat `fetchRefmap` as a default `--refmap` argument and `fetch` as default command-line refspecs, accepting colon-separated entries in `fetch` and prioritizing them over `fetchRefmap`. This preserves backwards compatibility but reintroduces the ambiguity the series aims to resolve.

Phillip leans toward the second model but insists that command-line refspecs (or their config-based equivalents) must **override** `fetchRefmap` entirely, not store the ref in both locations. His example (`git -c remote.cabal.fetchRefmap=... fetch cabal refs/heads/master:refs/remotes/origin/master`) demonstrates the expected behavior: only `origin/master` should be updated, not `cabal/master`. This contradicts Junio’s earlier suggestion that dual storage (updating both) is acceptable.

The discussion is **high-stakes for user experience**: the outcome will determine whether users migrating from older configurations face silent behavior changes (dual storage) or explicit errors (rejection of colon-separated `fetch` entries). Phillip’s preference for command-line emulation with override semantics is likely to prevail, as it preserves existing workflows while clarifying precedence. The resolution will require updates to `remote.c` (precedence logic in `get_ref_map()`) and documentation (`remote.txt`, `git-fetch.adoc`) to explicitly state that colon-separated `fetch` entries override `fetchRefmap`.

Thread identity
Subject: redesigning signal handling in threaded Git code to fix sigchain race
Series version: not yet posted (future v2)
Originating author: ian4hu
Thread type: design discussion / RFC

Core problem or goal
Fix a race condition in Git’s `sigchain` subsystem where concurrent calls to `sigchain_pop()` for the same signal can corrupt the signal handler stack. The redesign aims to prevent worker threads from inheriting the main thread’s signal handlers by blocking common signals during thread creation, but the discovery that several signals (SIGPIPE, SIGBUS, SIGFPE, SIGILL, SIGSEGV) are thread-directed rather than process-directed complicates the original plan: blocking these signals could prevent the process from being killed if they occur in a worker thread.

Current status
Design proposal stage; prior patch series dropped. Phillip Wood has revised his earlier endorsement after Oswald Buddenhagen clarified that five signals (SIGPIPE, SIGBUS, SIGFPE, SIGILL, SIGSEGV) are thread-directed. The original plan to block all signals during thread creation is now in question because blocking thread-directed signals could mask fatal conditions. Phillip tentatively suggests using an atomic flag in the signal handler to serialize unwinding of the `sigchain` stack for SIGPIPE, but no consensus has been reached. Awaiting feedback from Jeff King (Peff) and Junio before proceeding to v2.

Key technical details
- Subsystem: `sigchain` (signal handler stack management)
- Targeted thread pools: `preload_index()`, `index-pack`, `pack-objects`, `grep`, `name-hash`, read-cache entry loader
- Excluded threads: `fsmonitor--daemon`, `simple-ipc` (distinct lifecycle)
- Mechanism under discussion: block signals during thread creation using `sigaction` with `sa_mask = sigfillset()`, but thread-directed signals (SIGPIPE, SIGBUS, SIGFPE, SIGILL, SIGSEGV) may need to remain unblocked
- Guard pattern: block once per spawn loop, not per-thread
- Signals originally proposed for blocking: SIGINT, SIGHUP, SIGTERM, SIGQUIT, SIGPIPE
- Thread-directed signals: SIGPIPE, SIGBUS, SIGFPE, SIGILL, SIGSEGV (cannot be blocked without risking process hang on fatal conditions)
- Limitation: threads created by external libraries (e.g., libcurl’s threaded resolver) cannot be protected; will be documented in cover letter
- Alternative proposal: atomic flag in signal handler to serialize `sigchain_pop()` calls for SIGPIPE

Open questions and loose ends
- Whether to block thread-directed signals during thread creation, or leave them unblocked and accept the risk of concurrent `sigchain_pop()` calls
- Whether an atomic flag in the signal handler is a viable solution for serializing unwinding
- Awaiting feedback from Jeff King (Peff) and Junio before proceeding to v2
- No design objections raised yet, but the thread-directed signal distinction has forced a rethink of the original plan

Participant positions
- ian4hu: author of the redesign; acknowledged the external-library limitation and the SIGPIPE distinction; has not yet responded to the thread-directed signal complication
- Phillip Wood: initially endorsed blocking all signals (including SIGPIPE) during thread creation and approved the guard-pattern implementation; revised position after Oswald’s clarification, now questions blocking thread-directed signals and tentatively suggests an atomic flag for SIGPIPE
- Oswald Buddenhagen: clarified that SIGPIPE, SIGBUS, SIGFPE, SIGILL, and SIGSEGV are thread-directed, requiring separate reasoning; does not object to blocking them but insists the distinction be documented
- Jeff King (Peff): feedback requested, not yet provided

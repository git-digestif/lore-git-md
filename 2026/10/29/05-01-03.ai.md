This is a **substantive review** in the ongoing `git worktree list` filtering discussion. Eric Sunshine clarifies a key usability concern about the proposed `--branch` filtering option (now abandoned in favor of extending `git for-each-ref`'s `%(worktreepath)` atom). He points out that while `git worktree list` currently guarantees the main worktree appears first in its output, filtering would break this invariant: if the main worktree is excluded by a filter, the first entry in the filtered output would no longer be the main worktree. This creates a risk for scripts or users who rely on the first entry being the main worktree, particularly when attempting to delete worktrees (e.g., `git worktree remove` should never target the main worktree).

The observation is not tied to the specific `--branch` implementation but applies to any filtering mechanism, including the now-proposed `for-each-ref` composability approach. Eric’s comment surfaces a latent design tension: filtering worktrees inherently disrupts the stable ordering that scripts may depend on, and the project has not yet decided whether to preserve the main-worktree-first guarantee, annotate the main worktree in output, or accept the breakage. Phillip Wood’s earlier proposal to add an `is-main-worktree` annotation remains relevant as a potential mitigation. The thread’s pivot to `for-each-ref` does not address this concern, leaving it as an open question for future patches.

This is the cover letter for the sixth iteration of a three-patch bugfix series targeting the fetch subsystem. The series fixes a performance regression in shallow fetches when backfilling tags, introduced by batched reference updates in commit 0e358de64a (2025-05-19). The regression caused clients to report no 'have' references during negotiation, forcing servers to send all objects.

The core approach has stabilized: instead of splitting the transaction (as in earlier versions), the fix now exposes the OIDs of just-fetched references via the transport's `negotiation_include_tips` field during tag backfilling. This restores correct 'have' reporting while preserving atomicity for `--atomic` fetches. The series is now split into three commits for clarity: a test for existing behavior (upstream tracking persistence after rejected updates), a memory leak fix in the remote-helper transport, and the core fix itself.

Key improvements in v6 are stylistic: the test for upstream tracking persistence is moved to the front of the series for narrative clarity, and commit messages have been polished. The memory leak fix (patch 2/3) is now explicitly motivated by the test coverage added in the core fix (patch 3/3). No technical changes were made to the core logic since v5, which resolved the memory management blocker raised in earlier reviews.

The series is ready for maintainer review, with all substantive feedback addressed. Junio C Hamano's input is the only remaining blocker. The scalability trade-off (O(n) complexity for fetched refs) is documented as acceptable, and benchmark results show the fix is 17× faster than pre-batched-update behavior. Test coverage includes edge cases for atomic/non-atomic fetches and rejected updates.

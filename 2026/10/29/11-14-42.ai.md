This is a **substantive review** in the ongoing `git worktree list` filtering discussion, responding to Jasper Mayone’s pivot from a `--branch` option to extending `git for-each-ref`’s `%(worktreepath)` atom. Phillip Wood engages with the new design, identifying three key limitations of using `for-each-ref` as a filtering mechanism and endorsing the behavior change as a bug fix.

The review highlights that `git for-each-ref` lacks NUL-terminated output, making it cumbersome to parse worktree paths that contain newlines. It also notes that `for-each-ref` cannot distinguish the main worktree from linked worktrees, which is critical for scripts that need to avoid deleting the main repository. Additionally, Phillip points out that `for-each-ref` does not handle branches checked out in multiple worktrees, which could be problematic for tracking or cleanup workflows. Despite these limitations, he agrees that the proposed change to `%(worktreepath)`—making it report paths for rebasing/bisecting branches—is a bug fix, aligning its behavior with the rest of Git.

Phillip also clarifies that marking the main worktree in output is only necessary if the list is filtered, since unfiltered `git worktree list` already guarantees the main worktree appears first. This observation compounds Eric Sunshine’s earlier concern about the broken ordering invariant when filtering, suggesting that the project may need to address both annotation and ordering to fully resolve the usability risks for scripts. The review does not propose a specific solution but underscores the trade-offs of the `for-each-ref` approach.

This is the cover letter for v6 of a three-patch bugfix series targeting the fetch subsystem. The series fixes a performance regression in shallow fetches when backfilling tags, introduced by commit 0e358de64a ("fetch: use batched reference updates", 2025-05-19). The regression caused clients to report no 'have' references during negotiation, forcing servers to send all objects.

The v6 re-roll is a minor update addressing surface-level feedback from Patrick Steinhardt: the commit ordering has been adjusted to place the test for upstream tracking persistence (previously patch 3/3) before the core fix (now patch 3/3), improving narrative clarity. The commit message for patch 1/3 has also been tweaked to clarify how the subsequent patch exposes the memory leak it fixes. No technical changes were made to the patches themselves.

The series is now structured as:
1. A test verifying that upstream tracking information persists after rejected updates (moved from the end of the series to the front).
2. A precursor patch introducing `transport_options_release()` to fix a pre-existing memory leak in the remote-helper transport's cleanup path.
3. The core fix, which exposes pending transaction state via the transport's `negotiation_include_tips` field, restoring correct 'have' reporting during tag backfilling while preserving atomicity for `--atomic` fetches.

The memory management blocker from v4 has been resolved, and all substantive review feedback has been addressed. The series is ready for maintainer review, with Junio C Hamano's position still unvoiced. Karthik Nayak has confirmed he will not re-roll further unless additional feedback arrives. The scalability trade-off (advertising all fetched references during negotiation) is documented as acceptable O(n) complexity. Key files touched include `builtin/fetch.c`, `transport-helper.c`, `transport.c`, `transport.h`, and `t/t5510-fetch.sh`.

This is the first patch in Tanga Joris's v3 series, implementing Junio C Hamano's proposed refactoring to centralize `--git-completion-helper` handling in `parse-options.c`. The patch moves the completion-helper logic from the earlier `fast-import`-specific fix into `show_usage_with_options_if_asked()`, a function already used by all `parse-options`-based commands to handle `-h` and `--help` flags. This change ensures that any command using `parse-options` will immediately respond to `--git-completion-helper` (and `--git-completion-helper-all`) before executing any command-specific initialization, avoiding side effects like temporary file creation or blocking on input.

The patch touches `parse-options.c` (adding a six-line block that checks for the completion-helper flags and calls `show_gitcomp()`) and adds a test in `t/t9300-fast-import.sh` to verify that `git fast-import --git-completion-helper` no longer creates temporary pack files or reads from stdin. The test is minimal but sufficient: it checks for the absence of `tmp_pack_*` files and confirms the expected option list is printed. This addresses the edge case René Scharfe identified in the v2 thread, where completion for `fast-import` would freeze and leave behind temporary files.

The commit message clearly explains the motivation and the refactoring approach, crediting Junio's suggestion. The change is well-scoped and maintains backward compatibility; it does not alter the behavior of `-h` or `--help`, only extends the same early-exit pattern to completion helpers. The patch depends on Christian Couder's `cc/early-scan-options` series (as noted in the thread context) but does not require changes to it. No test coverage is added for the other three commands (`patch-id`, `diff-pairs`, `var`) fixed in the earlier v2 patch, but the centralized approach means they will automatically benefit from the same behavior.

This is a clean, maintainable solution to a user-visible regression. The refactoring reduces boilerplate and ensures consistent completion behavior across all `parse-options`-based commands. The patch is ready for review and should be uncontroversial, assuming `cc/early-scan-options` is stable. The only loose end is whether the test suite should include completion-helper tests for the other three commands, but that is not a blocker for this patch.

This is the second patch in Justin Tobler’s four-patch **bugfix series (v2)** targeting the object database (ODB) layer. The series addresses a critical flaw in how Git migrates the "loose-object-idx" file—a mapping between objects and their compatibility hashes (e.g., SHA-1/SHA-256 interop)—when batch fsync of loose objects is enabled. This patch is a **refactoring step** that lifts the loose-object-idx parsing logic into a reusable helper, `loose_object_map_read()`, to enable atomic writes in a later patch.

The patch extracts the core parsing logic from `loose_object_map_load()` into a new helper that takes an explicit `loose_object_map` and `oidtree` cache as arguments, rather than relying on the `odb_source_loose` struct. This change is necessary because the upcoming migration logic in `tmp-objdir.c` (patch 4/4) needs to parse an index file that isn’t tied to any object source. The patch also tightens error handling: while `ENOENT` (file not found) is still treated as success, other errors (e.g., permission issues, malformed files) now propagate to the caller instead of being silently ignored. This aligns with the series’ broader goal of making the loose-object-idx mechanism more robust.

The diff is clean and focused, touching only `loose.c`. The new `loose_object_map_read()` helper is well-designed, with clear parameter documentation and consistent error handling. The patch preserves the existing behavior for `loose_object_map_load()` while making the logic more modular. One subtle behavioral change is that `repo_read_loose_object_map()` now stops loading subsequent object sources if one fails to parse, matching its existing behavior for malformed files. This is a minor improvement in consistency but could affect error reporting in edge cases.

This patch is **not user-visible**—it’s purely preparatory work for the atomic-write fix in patch 4/4. The refactoring is well-motivated and addresses Patrick Steinhardt’s earlier feedback about code organization. The series as a whole is now **technically sound** after v2 addressed all blocking concerns (atomicity, locking, and error handling), and this patch is a key enabler for those fixes. The regression test in patch 4/4 will verify that the migration logic works correctly, but this patch itself doesn’t introduce new behavior.

For a busy reader, this is a **low-risk, high-value refactoring** that sets up the real fix. It’s worth skimming the helper’s signature and error-handling changes, but the patch doesn’t require deep scrutiny unless you’re working on the ODB layer. The series is **ready for re-review** and is a high-priority fix for ODB stability.

This is a bug report for a regression in `git grep --recurse-submodules` when searching a tree object.

The issue appears in Git 2.56.0 and causes a fatal error when the command encounters a directory inside a submodule while searching a tree (e.g., `git grep --recurse-submodules <pattern> HEAD`). The error message is `fatal: unable to read tree (<id>)`, where the ID is that of the submodule directory's tree object. The working-tree form of the command (`git grep --recurse-submodules <pattern>`) is unaffected, as are submodules without directories.

The regression was introduced by commit `93cd344e34` ("builtin/grep: stop registering submodule ODB as source", 2026-09-11). The commit removed the registration of the submodule's object database as a source for the main repository's ODB, which causes the lookup for submodule directory trees to fail. The reporter provides a minimal reproduction script and confirms that reverting the change (by reading from `repo->objects` instead of `the_repository->objects`) restores the expected behavior.

The bug affects CI environments, as noted by the reporter: GitHub's ubuntu-22.04 runner image updated from Git 2.55.0 to 2.56.0, causing the issue to surface. The reporter also speculates that a similar issue might exist in `grep_cache()` when dealing with sparse-directory index entries, though this has not been verified.

This is a clear regression with a well-documented reproduction case and a known culprit commit. The fix is likely to be straightforward, but the reporter has not yet run the full test suite to confirm the impact of their proposed workaround. The issue is worth attention from anyone working on the grep or submodule subsystems.

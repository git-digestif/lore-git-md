This is a bugfix patch targeting the notes subsystem. Farid Zakaria reports a race condition in `git notes add` (and related commands) where concurrent processes can silently overwrite each other's notes, losing data. The patch modifies the notes machinery to detect concurrent updates and fail with a "cannot lock ref" error instead of clobbering existing notes.

The commit message is unusually thorough: it explains the race, describes the fix (using the commit the notes were loaded from as both the parent and the expected old value for the ref update), and provides quantitative evidence from both a deterministic testing tool (Rewind) and plain Linux runs. The author also links to a detailed write-up on their blog that walks through how they diagnosed the issue.

The patch itself touches four files. In `notes.h` it adds a `base_oid` field to the `notes_tree` struct to remember which commit the notes were read from. In `notes.c` it initializes that field during `init_notes()` and populates it when the ref is readable. In `notes-utils.c` it uses the remembered commit as the parent of the new notes commit and as the expected old value for the ref update, so a concurrent update will cause the ref update to fail. The test in `t/t3301-notes.sh` simulates a concurrent edit by having the editor add a note to a different commit while the outer `git notes add` is waiting for the editor.

The change looks well-crafted: it preserves the existing behavior when there is no race, fails cleanly when there is, and includes a test that exercises the race. The commit message and linked write-up suggest the author has thought carefully about the problem and the solution. This is a clear case of a real bug with a clean fix and should be uncontroversial.

This is a **feature pivot** in the `git worktree list` filtering discussion. Jasper Mayone proposes abandoning the `--branch` option entirely and instead enhancing `git for-each-ref`'s `%(worktreepath)` atom to report worktree paths even when the branch is being rebased or bisected. The change would close the gap Kristoffer Haugsbakk identified — the only functional difference between `%(worktreepath)` and the proposed `--branch` — without introducing new CLI options or design questions about extensibility.

The motivation is clear: the existing `for-each-ref` mechanism already supports merged/unmerged filtering via `--merged`, and the only missing piece is handling rebasing/bisecting worktrees. By extending `%(worktreepath)` to use the same logic as `branch_checked_out()` (which already covers rebase, bisect, and rebase --update-refs), the change would make the one-liner `git for-each-ref --merged origin/main --format='%(worktreepath)' refs/heads/` fully functional, eliminating the need for a dedicated `--branch` option. Jasper frames this as a bug fix rather than a new feature, since the rest of Git already treats rebasing/bisecting branches as checked out.

The proposal is narrower in scope and avoids the open design questions raised earlier (e.g., `--filter`, `--filter-command`, or a `foreach` mechanism). It also sidesteps the naming and composability debates, though it leaves Phillip Wood’s concern about identifying the main worktree in `git worktree list` output unaddressed (Jasper suggests addressing that separately). The main risk is backwards compatibility: scripts that rely on `%(worktreepath)` returning an empty string for rebasing/bisecting branches would break. Jasper acknowledges this but argues the change aligns with Git’s existing behavior elsewhere.

This looks like a pragmatic, well-motivated simplification. If the compatibility concern is manageable, it could resolve the thread with a smaller, more focused patch.

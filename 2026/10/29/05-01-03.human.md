This is a **substantive review** in the ongoing `git worktree list` filtering discussion. Eric Sunshine clarifies a key usability concern about the proposed `--branch` (and by extension, `--merged`/`--no-merged`) filtering options: while `git worktree list` currently guarantees the main worktree appears first in its output, filtering could remove it, breaking scripts or users who rely on that ordering. Phillip Wood’s earlier observation about the lack of an explicit `is-main-worktree` annotation becomes more urgent here, since filtering makes the implicit ordering unreliable.

The review does not engage with Jasper Mayone’s pivot to extending `git for-each-ref`’s `%(worktreepath)` atom (which avoids introducing new CLI options), but the concern remains relevant to any filtering mechanism, including `for-each-ref --merged`. Eric’s point underscores the need for either an explicit annotation or a design decision about whether the main worktree should be filtered out by default. No code or tests are proposed; this is purely a design-level observation.

This is the first patch in a four-part bugfix series targeting a critical flaw in Git’s object database (ODB) transaction layer. The issue affects users with compatibility hash support (e.g., SHA-1/SHA-256 interop) and batch fsync of loose objects enabled. This specific patch addresses a **locking hazard**: the loose-object-idx file, which maps objects to their compatibility hashes, previously used an indefinite lock timeout (`-1`), risking hangs if a process died while holding the lock. The fix replaces this with a **1000ms timeout**, matching the default for `core.packedRefsTimeout` and ensuring writers fail gracefully rather than hanging forever.

The change is minimal and surgical: it introduces a new constant (`LOOSE_OBJECT_IDX_LOCK_TIMEOUT_MS`) and updates two call sites in `loose.c` to use it. The patch is **well-motivated**—the commit message clearly explains the risk of indefinite timeouts and justifies the chosen value. It’s also **low-risk**: the timeout is long enough to avoid spurious failures in normal operation but short enough to prevent hangs. This aligns with Patrick Steinhardt’s blocking feedback on the v1 series, where he flagged the indefinite timeout as a correctness issue.

This patch is part of a broader effort to stabilize the ODB layer, particularly the loose-object-idx mechanism, which Patrick has described as "quite broken" in its current design. While this patch doesn’t fix the deeper systemic issues (unsorted files, no deduplication, no stale-entry pruning), it **eliminates a critical failure mode** and is a prerequisite for the atomic-write fix in patch 4. The series as a whole is **high-priority** for ODB stability, and this patch is a straightforward, uncontroversial step toward that goal. If you care about ODB correctness or compatibility-hash support, this is worth reviewing.

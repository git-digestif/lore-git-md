This is a follow-up discussion in a thread about a bugfix targeting signal handling in Git's threading code.

The author (ian4hu) is responding to review feedback from Phillip Wood on an earlier patch that attempted to fix a race condition in Git's `sigchain` mechanism, where concurrent signal handler pops could corrupt the signal stack. The original patch is now being abandoned in favor of a more comprehensive approach.

The new plan, as outlined here, involves blocking signals (SIGINT, SIGHUP, SIGTERM, SIGQUIT) during thread creation to prevent worker threads from inheriting the main thread's signal handlers, which could lead to double-pops. The blocking will be done once per thread-spawning loop rather than per-thread, using a guard pattern for cleaner code. The author also agrees to preserve the caller's `sigaction` flags and mask during signal handler manipulation.

The discussion touches on edge cases: whether SIGPIPE should be blocked (decision: no, to preserve existing behavior), and the limitation that threads spawned by external libraries (e.g., libcurl's resolver) won't benefit from this protection. The author plans to document this gap in the cover letter.

This looks like a well-scoped, technically sound fix for a subtle concurrency issue. The author is being methodical about addressing review feedback and considering real-world constraints. If no objections arise, the revised patch series (v2) should be worth watching.

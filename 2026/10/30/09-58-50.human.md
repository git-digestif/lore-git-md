This is the first patch in a four-part bugfix series targeting 64-to-32-bit truncations on Windows (LLP64 platforms). It addresses a silent data corruption issue in the object database (ODB) where files larger than 4 GiB are truncated when written as blobs. The patch converts the length parameter in `odb_write_object_ext()`, `odb_write_object()`, and related functions from `unsigned long` to `size_t`, ensuring 64-bit width on Windows. It also updates the in-memory ODB source to store object sizes as `size_t`.

The commit message clearly explains the problem: when `git add` or `git hash-object -w` processes a file over 4 GiB with any conversion (e.g., `core.autocrlf`, `eol`/`ident` attributes, or clean filters), the ODB writes only the first `size mod 2³²` bytes. The index records the correct stat data, so `git status` remains clean, and the corruption goes unnoticed until checkout. The patch includes a new test in `t1007-hash-object.sh` that verifies both the object ID and size for a 5 GiB file written with `git hash-object -w`, ensuring the fix works end-to-end.

This is a well-motivated, narrowly scoped fix with no behavior change on 64-bit Linux. The test coverage (marked `EXPENSIVE` and `SIZE_T_IS_64BIT`) directly addresses Patrick Steinhardt’s review feedback from `v1`, which flagged the lack of a test for the truncation bug. The patch is ready for integration and looks uncontroversial.

This is a **bugfix and ref-filter enhancement** patch series that addresses two related safety issues in Git's worktree subsystem. The series is a refined version of Jasper Mayone's earlier proposal, now labeled as a follow-up to a v2 patch (though Junio notes it should be called v3 to avoid breaking automation).

The first patch fixes a long-standing bug: `git worktree remove` currently allows deletion of worktrees in the middle of a rebase, bisect, cherry-pick, revert, or `git am` sequence, risking data loss. The patch makes the command refuse such deletions unless `--force` is given, aligning with Git’s general principle of protecting uncommitted or in-progress work. The second patch extends `git for-each-ref`'s `%(worktreepath)` atom to report the worktree path for branches being rebased or bisected, closing a gap where these branches were inconsistently treated as "detached" despite being actively used. This eliminates the need for a new CLI option and makes behavior consistent across Git commands.

The series is well-motivated and directly addresses concerns raised in earlier discussion. It avoids the ordering and composability pitfalls of the original `--branch` proposal by leveraging `for-each-ref`, though it leaves some limitations of that mechanism unaddressed (e.g., lack of NUL-terminated output or main-worktree distinction). The implementation is clean, with a new `worktree_is_in_progress()` helper and thorough test coverage for edge cases like unborn branches and mid-rebase scenarios. The backward-incompatible change to `%(worktreepath)` is explicitly called out in the commit message, which asks whether any scripts rely on the current behavior.

This is a **bugfix** patch (1/6 in a series) targeting the loose object reading code in `object-file.c`. It addresses a memory safety issue where Git could return uninitialized heap memory or silently truncate object data when the size of an inflated loose object does not match the size declared in its header.

The patch adds a check in `unpack_loose_rest()` to verify that the number of bytes produced by the zlib stream (`stream->total_out`) matches the expected object size from the header. If they differ, Git now reports the object as corrupt and frees the buffer. This mirrors existing checks in the packfile reader (`unpack_compressed_entry()`) and `index-pack`. The commit message demonstrates the bug with a concrete example: a loose object whose header claims 200 bytes but contains only 44 bytes would previously cause `git cat-file commit` to print 156 bytes of uninitialized memory.

The patch also extends the test helper `loose_obj()` in `lib-loose.sh` to allow writing objects with bogus header sizes, enabling new tests in `t1060-object-corruption.sh` that verify the fix for both under-sized and over-sized objects. The tests confirm that `git cat-file` and `git fsck` now correctly detect and reject such corruption.

The change is narrowly scoped to the loose object reading path and does not affect packfiles or other object storage backends. The commit message and tests are clear and thorough, making the motivation and impact easy to understand. This looks like a well-crafted fix for a real bug.

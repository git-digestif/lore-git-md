This is a refactoring patch in the `git log` subsystem, specifically targeting the `--follow` option for rename detection in non-linear (merge-heavy) histories. It is the fourth patch in a six-patch series by Miklos Vajna.

The patch removes a performance regression introduced in an earlier commit (304812ed33, June 2026) that added support for following renames through merge commits. That implementation used a separate function (`propagate_follow_pathspec_to_parent`) and an extra loop, which caused a severe slowdown—Miklos reports a real-world case where `git log --stat --follow` on a single file in the Linux kernel repository ballooned from 28 seconds to nearly seven minutes. The new approach eliminates the redundant `diff_tree_oid` call by moving the rename-tracking logic directly into the existing parent loop in `log_tree_diff`, simplifying the code without yet fixing the performance issue (that is left for the next patch in the series).

The change is confined to `log-tree.c` and touches only the diff machinery for merge commits; it does not alter the user-visible behavior of `--follow`, `--first-parent`, or any of the merge-diff options (`-c`, `--cc`, `--remerge-diff`). If the series lands, users should see the same rename-following functionality with a cleaner implementation and, in the follow-up patch, faster execution.

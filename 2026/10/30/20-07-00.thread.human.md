The `git log --follow` thread has reached a pivotal point. The series, now at v5, fixes critical correctness bugs in `--follow` when processing merges—such as lost history from non-first parents and missed edits on dropped sides of merges—while reducing a ~14× performance regression (introduced by commit 304812ed33 in June 2026) to ~1.6×. However, this remaining gap became a deployment blocker for GitLab, forcing a project-level policy decision.

After extensive debate, the thread has settled on an **opt-in toggle** as the pragmatic path forward. Junio C Hamano, the maintainer, has now endorsed this approach, calling it "sensible" and far preferable to either reverting 304812ed33 (which would reintroduce correctness bugs) or accepting the performance cost as permanent. The toggle will **disable `--follow` by default for non-linear history**, preserving the correctness fixes while mitigating the performance impact. Patrick Steinhardt has proposed a fast-tracked single-patch series to implement this, likely as `--follow=merges` (an optional parameter to `--follow`), and Junio’s blessing suggests this will proceed quickly to unblock GitLab’s deployment. The v5 series itself may land separately, but the urgency has shifted to the toggle as the critical next step.

Key participants—Patrick Steinhardt, Miklos Vajna, and Justin Tobler—have all aligned on the opt-in approach, though minor details like the toggle’s design (flag vs. config option) remain open. Miklos previously favored a config option (`log.followNonLinear`) for discoverability, but Patrick’s preference for `--follow=merges` (for user-facing clarity) appears likely to prevail. The default-disabled behavior is now confirmed, though documentation and user education (e.g., release notes) are still pending. With Junio’s endorsement, the thread is effectively resolved on policy; the focus now turns to implementation.

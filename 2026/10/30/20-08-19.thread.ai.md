Core problem or goal
Fix a regression in `git log -m --follow` where the history of later parents in a merge is lost when following renames. The regression manifests in diamond-shaped merge scenarios (test case `t4219`): when a file is renamed differently in two branches and then merged, the command fails to show the full history of the file.

Current status
Under review; patch v1 posted. No prior versions of this series are recorded.

Key technical details
- Files touched: `log-tree.c` (13 lines added)
- Subsystem: revision-walking / diff machinery
- New behavior: `git log -m --follow` now correctly restores the merge’s original path before diffing each parent, ensuring the full history of all parents is shown in diamond-shaped merge scenarios
- Old behavior: the parent loop in `log_tree_diff()` did not restore the followed path between parents, causing the second parent to be diffed against an already-renamed path rather than the merge’s original path
- Test coverage: new test case added to verify the fix in the diamond scenario; existing test `t4219` (history simplification) is the context for the regression

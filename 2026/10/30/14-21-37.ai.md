This is the second patch in a two-part series enhancing Git’s worktree and ref-filter subsystems. It extends the `%(worktreepath)` atom in `ref-filter.c` to report the worktree path for branches that are being rebased or bisected, even when the worktree’s `HEAD` is detached. This closes a gap where `git for-each-ref --format='%(worktreepath)'` previously returned an empty string for such branches, creating a mismatch with how `git worktree add` and `git branch -d` already treat them as "checked out."

The change is motivated by Kristoffer Haugsbakk’s observation that scripts currently have no way to discover which worktree is working on a rebasing or bisecting branch. The implementation reuses the logic from `branch.c`’s `prepare_checked_out_branches()` to map the branch being rebased or bisected to its worktree, and explicitly excludes branches that `rebase --update-refs` will move but are not currently checked out. The patch updates both the `git-branch` and `git-for-each-ref` documentation to reflect the new behavior, including the dual `*` and `+` markers that now appear when running `git branch` inside a worktree that is rebasing its own branch.

The code is clean and well-tested. It adds a new helper `add_worktree_entry()` to populate the worktree map, and extends `populate_worktree_map()` to check for rebase and bisect state using the existing `wt_status_check_rebase()` and `wt_status_check_bisect()` functions. Tests cover rebasing, bisecting, interactive rebase with an edit stop, `rebase --update-refs`, and detached-HEAD rebase scenarios. The backward-incompatible change (scripts relying on `%(worktreepath)` being empty for rebasing/bisecting branches) is explicitly called out in the commit message, which asks whether any such scripts exist.

This patch directly addresses the design tension identified in the RFC discussion by avoiding the need for a new CLI option and aligning behavior across Git commands. It does not attempt to solve the broader limitations of `for-each-ref` as a filtering mechanism (NUL-terminated output, main/linked worktree distinction, multiple worktrees per branch), but it does make the behavior more consistent and safer when combined with the first patch’s safety fix for `git worktree remove`. The series is ready for review and looks like a well-crafted fix for a real problem.

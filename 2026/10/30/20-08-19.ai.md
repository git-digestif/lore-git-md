This is a bugfix patch (part 3/6 of a series) targeting the `git log` command. It addresses a regression in `git log -m --follow` where the history of later parents in a merge is lost when following renames.

The issue occurs in the diamond-shaped merge scenario (test case `t4219`): when a file is renamed differently in two branches and then merged, `git log -m --follow` fails to show the full history of the file. The root cause is that the parent loop in `log_tree_diff()` doesn't restore the followed path between parents, causing the second parent to be diffed against an already-renamed path rather than the merge's original path.

The fix is straightforward: save the merge's original path before the parent loop, restore it before diffing each parent, and ensure the path is propagated correctly to parents. The patch adds this logic only for merges (single-parent commits continue working as before) and includes a new test case that verifies the full history is now shown in the diamond scenario.

The change is minimal (13 lines added to `log-tree.c`) and well-motivated, with clear test coverage. The commit message explains both the problem and the solution effectively. This looks like a clean, targeted fix for a real user-facing issue.

This is the sixth and final patch in Harald Nordgren’s v13 series introducing `remote.<name>.fetchRefmap` for matching-inspired fetch mode. The patch is a **bugfix** that ensures `@{push}` resolution works correctly when a remote is configured with `--limited-fetch` (which sets `remote.<name>.fetchRefmap` but not `remote.<name>.fetch`).

The issue is straightforward: when a branch is pushed to a remote added with `--limited-fetch`, Git has no `remote.<name>.fetch` refspec to map the pushed ref back to a local tracking branch, so `@{push}` fails with "has no local tracking branch". The fix is mechanical: `tracking_for_push_dest()` in `remote.c` now falls back to `remote->refmap` (the namespace mapping) if `remote->fetch` does not resolve the refname, mirroring the fallback logic already used in `get_ref_map()` for fetch operations. This ensures that `@{push}` works the same way for `--limited-fetch` remotes as it does for traditional remotes.

The patch touches only `remote.c` and adds a new test in `t/t1514-rev-parse-push.sh` that verifies `@{push}` resolution after pushing to a `--limited-fetch` remote. The test is minimal but sufficient: it sets up a sparse clone, adds a `--limited-fetch` remote, pushes a branch, and confirms that `@{push}` resolves to the correct ref. The change is uncontroversial and aligns with the series’ broader goal of making `fetchRefmap` behave like a drop-in replacement for traditional refspecs.

This patch is **ready for merging** and has no unresolved technical concerns. It addresses a gap in the v12 implementation (noted in the thread context) and is a prerequisite for the series’ graduation to `master`. The fix is narrow, well-tested, and does not alter the series’ core design or precedence rules. The only remaining blocker for the series is the override semantics discussion for command-line refspecs, which is unrelated to this patch.

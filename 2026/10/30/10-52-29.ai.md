This is the fifth patch in Harald Nordgren’s six-patch v13 series introducing `remote.<name>.fetchRefmap` for matching-inspired fetch mode. The patch makes `--limited-fetch` the default when adding a remote to a shallow repository, ensuring that `git remote add` does not configure a wildcard refspec that would cause `git fetch` to negotiate history for all remote branches. The change is mechanical and well-tested, with 60 new lines of test coverage in `t/t5505-remote.sh` verifying the shallow-repository default, the override behavior of `--no-limited-fetch`, and the interaction with `-t/--track` and `--mirror`.

The patch updates `builtin/remote.c` to check `is_repository_shallow(the_repository)` when `limited_fetch` is unset (`-1`), turning on `--limited-fetch` by default in shallow repositories unless `--no-limited-fetch`, `-t/--track`, or `--mirror` is given. The documentation in `git-remote.adoc` is updated to describe the new default and its interaction with the existing `--no-limited-fetch` flag. The implementation is uncontroversial and aligns with the series’ goal of improving fetch performance in shallow repositories by avoiding unnecessary history negotiation.

The test suite covers four key scenarios: (1) `-t/--track` still configures an explicit refspec in a shallow repository, (2) a full repository still gets the wildcard refspec, (3) a shallow repository defaults to `--limited-fetch` (configuring `remote.<name>.fetchRefmap` instead of `remote.<name>.fetch`), and (4) `--no-limited-fetch` overrides the shallow-repository default. The tests verify both the configuration and the runtime behavior, including that `git fetch` only fetches the branches tracked by local branches after the remote is added.

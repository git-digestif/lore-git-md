This thread is about a six-patch series from Miklos Vajna that refactors how `git log --follow` handles renames in merge-heavy histories. The goal is to fix a severe performance regression (from 28 seconds to 6 minutes 43 seconds) in `git log --stat --follow` on repositories like linux.git. This fourth patch simplifies the internal logic by removing a redundant helper function and its loop, which unnecessarily called `diff_tree_oid()` for each parent of a merge commit. The change is purely preparatory—it doesn’t improve performance yet but sets the stage for the actual fix in the next patch.

Miklos has posted three prior versions of the series, and this patch is a targeted cleanup in `log-tree.c` (removing 55 lines, adding 41). It preserves all existing `--follow` behavior, including edge cases like `--diff-merges=first-parent` and combined diffs. The commit message is clear about the trade-off: the current patch is about code clarity, not speed, but it directly addresses the root cause of the regression. The real test will be whether the follow-up patch (5/6) delivers the promised performance gain. So far, there’s no review feedback in the summary, so the series is still under initial scrutiny.

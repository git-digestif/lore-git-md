This is a performance bugfix for `git log --follow` in merge-heavy repositories. The patch is the fifth in a six-patch series (v4) from Miklos Vajna that addresses a severe slowdown introduced by commit 304812ed33 (June 2026). That earlier change improved rename following for non-linear history but inadvertently made `git log --follow` on a single file up to 14× slower in the Linux kernel repository.

The problem occurs when `log_tree_diff()` diffs each merge commit against all of its parents with rename detection enabled. Because merge commits often add a file relative to one parent, the expensive rename-detection machinery runs unnecessarily for every parent. The fix splits the diff into two passes: first, a fast pass without rename detection to find any parent where the file is unchanged; if none exists, a second pass with rename detection runs only against the parents that actually changed the file. A helper function (`follow_needs_renames()`) ensures that history is not lost when a file was renamed on one side of the merge.

The patch touches only `log-tree.c`, adding about 90 lines of new logic. Test results show the Linux kernel use case dropping from 6 minutes 43 seconds back to 36 seconds, close to the original 28-second baseline. SZEDER Gábor is credited with helping refine the approach. The commit message is clear and the code is well-commented, suggesting a thoughtful, targeted fix rather than a hasty workaround.

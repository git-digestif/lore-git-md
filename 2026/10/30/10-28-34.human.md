This is a bugfix patch targeting the loose object reading code in Git. It addresses a memory safety issue where `unpack_loose_rest()` fails to verify that the inflated size of a loose object matches the size declared in its header. When the compressed data is shorter than the header claims, Git returns a buffer with uninitialized heap memory; when it’s longer, Git silently truncates the data. The patch adds a size check and treats mismatches as corruption, aligning the loose object reader with the packfile reader’s existing behavior.

The commit message is clear and detailed, explaining both the problem (uninitialized memory exposure and silent truncation) and the fix (comparing `total_out` with the expected size). It also notes that `fsck` currently catches the first case only by accident, which underscores the urgency of the fix. The patch includes new tests in `t1060-object-corruption.sh` that create loose objects with bogus header sizes and verify that both `git cat-file` and `git fsck` now reject them.

The code change itself is small and focused: it renames a variable for clarity, adjusts the offset calculation, and adds the size check in the error condition. The test helper `loose_obj()` in `lib-loose.sh` is extended to allow writing arbitrary sizes into the object header, enabling the new test cases.

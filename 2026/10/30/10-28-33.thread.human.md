Elia Pinto has sent a five-patch v2 series fixing loose object handling and size truncation bugs, with two issues affecting all platforms and three specific to LLP64 platforms like 64-bit Windows where `long` is 32-bit but `size_t` is 64-bit. The series is rebased onto `master` and remains under review with no maintainer decision yet; the issues were previously vetted on `git-security` and deemed non-security-sensitive.

The latest email details patch 2/5, which widens size variables from `unsigned long` to `size_t` throughout the loose object reading path -- across `map_fd()`, `unpack_loose_header()`, `unpack_loose_rest()`, and `check_stream_oid()` in `object-file.c`, plus `odb_source_loose_map_object()` in `odb/source-loose.c`. This closes a gap where `parse_loose_header()` already reported sizes as `size_t` but downstream functions still truncated them, which on Windows could cause a header claiming 4 GiB + 5 bytes to allocate a 6-byte buffer while callers read far past it. The patch has no automated test because reproducing it requires a near-4 GiB allocation; the commit message documents a manual reproduction instead. It complements patch 1/5, which added post-inflation size validation that only becomes effective on LLP64 once these types are widened.

Only patches 1/5 and 3/5 have automated test coverage; the LLP64-specific fixes rely on documented manual reproduction steps. No reviewers have weighed in yet, so all technical questions and the broader `odb_write_object()` API limitation raised by patch 5/5 remain open.

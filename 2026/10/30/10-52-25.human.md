This is the first patch in Harald Nordgren’s v13 series introducing `remote.<name>.fetchRefmap`, a new configuration key that implements a "matching-inspired" fetch mode for shallow repositories. The patch adds the config variable itself, its documentation, and the core plumbing in `remote.c` and `builtin/fetch.c` to parse and apply it.

The new `remote.<name>.fetchRefmap` key provides the default value for the `--refmap` command-line option, just as `remote.<name>.fetch` provides default refspecs. Unlike `--refmap`, however, configuring `fetchRefmap` alone does not change what a refspec-less fetch does; it only maps what is already fetched by `remote.<name>.fetch`. This decouples the "what" (which refs to fetch) from the "where" (where to store them), resolving the design flaw in earlier versions that overloaded `remote.<name>.refmap`.

The patch updates `remote.c` to parse the new config key, adds a `refmap` field to the `remote` struct, and modifies `remote_find_tracking()` to fall back to the refmap when `remote.<name>.fetch` has no match. This ensures that `@{upstream}` and `git branch --track` work for branches mapped by `fetchRefmap`. The implementation is mechanical and well-tested, with 151 lines of new tests in `t/t5510-fetch.sh` covering edge cases like negative refspecs, explicit-destination `fetch` entries, and the interaction between `fetch` and `fetchRefmap`.

The documentation updates clarify that `remote.<name>.fetch` still decides what to fetch, while `fetchRefmap` only maps what is fetched. The patch also preserves backwards compatibility: older Git versions ignore `fetchRefmap` and treat `remote.<name>.fetch` entries without destinations as fetch-only refspecs (stored in `FETCH_HEAD`), avoiding silent corruption of local branches.

This patch is part of a series that is now implementation-complete and under final review for merging to `master`. The only remaining open question is the override semantics for command-line refspecs and colon-separated `remote.<name>.fetch` entries, which the thread has converged toward resolving in favor of override semantics (Phillip Wood’s preference). The v13 test case confirms the current dual-storage behavior for colon-separated `fetch` entries, but this is expected to be updated in v14 to match the chosen override model. The series is otherwise ready for graduation, with no known blockers or unresolved technical concerns.

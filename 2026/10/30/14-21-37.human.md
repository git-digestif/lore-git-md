This is the second patch in a two-patch series that enhances `git for-each-ref`'s `%(worktreepath)` atom to report the worktree path for branches being rebased or bisected. The series as a whole addresses a real usability gap: currently, `git for-each-ref --format='%(worktreepath)'` returns an empty string for branches that are being rebased or bisected, even though those branches are treated as "checked out" by other Git commands (`git worktree add`, `git branch -d`). This inconsistency makes it harder for scripts to identify which worktree is working on a given branch.

The patch modifies `ref-filter.c` to map branches being rebased or bisected to their worktrees, matching the logic already used in `branch.c`'s `prepare_checked_out_branches()`. It adds a new helper function `add_worktree_entry()` and updates `populate_worktree_map()` to check for rebase and bisect state using `wt_status_check_rebase()` and `wt_status_check_bisect()`. The implementation is careful to exclude branches that `rebase --update-refs` will move (those are not checked out, only updated), and it ignores rebases of detached HEADs. Tests cover edge cases: rebasing, bisecting, interactive rebase stopped at edit, and `rebase --update-refs`.

The change is backward-incompatible for scripts that rely on `%(worktreepath)` being empty for rebasing/bisecting branches, but the commit message explicitly asks whether any such scripts exist, suggesting the author considers this a low-risk change. The documentation is updated to reflect the new behavior, including a note about the dual `*` and `+` markers in `git branch` output for the current worktree during a rebase.

This patch is well-crafted and addresses a clear usability issue. It complements the first patch in the series, which makes `git worktree remove` refuse to delete worktrees in the middle of a rebase, bisect, or other in-progress operation unless `--force` is given. Together, the two patches make Git's worktree behavior more consistent and safer. The implementation is clean, the tests are thorough, and the commit message is clear about the motivation and backward-compatibility concerns. The patch is ready for review and looks like a solid contribution.

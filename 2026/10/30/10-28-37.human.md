This is a bugfix patch, part 4 of a 6-patch series. It addresses a silent data corruption and potential crash in `git cat-file --batch` when handling objects larger than 2 GiB.

The issue is straightforward: `batch_write()` declares its length parameter as `int`, but callers pass `size_t` values from object-reading functions. On objects between 2 GiB and 4 GiB, the length wraps to a negative `int`, which `fwrite()` and `write_or_die()` then interpret as an enormous positive `size_t`. This causes the function to write past the end of the buffer, sending arbitrary memory to stdout until it hits an unmapped page and crashes. Objects 4 GiB or larger are truncated instead, desynchronizing the `--batch` output format.

The fix is equally simple: change the parameter type from `int` to `size_t` to match what the underlying I/O functions expect. The patch touches only one line in `builtin/cat-file.c`. No tests are included because reproducing the bug requires several GiB of memory and disk space, but the commit message provides a clear reproduction recipe using `test-tool genzeros` and a 3 GiB blob.

The problem affects all platforms, not just 32-bit systems, and can be triggered on any non-blob object or on blobs when `--filters` or `--textconv` are used. The patch is a clean, minimal fix for a real and serious bug.

This is a performance bugfix patch targeting the `git log --follow` feature. It is the fifth patch in a six-patch series (v4) by Miklos Vajna, addressing a severe regression introduced in commit 304812ed33 (June 2026) where `--follow` on merge-heavy histories became unusably slow—specifically, a test case on linux.git ballooned from 28 seconds to nearly 7 minutes.

The patch restructures how `log_tree_diff()` handles merges when `--follow` is active. Previously, it diffed each merge against all parents with full rename detection, which is expensive and often unnecessary. The new approach uses a two-pass strategy: first, it diffs without rename detection to find a parent where the path is unchanged; if found, it follows that parent’s history and only performs rename detection against parents where the path might have been renamed (determined by checking merge bases). This reduces the number of rename-detection passes from O(n) to O(1) in the common case where the path is unchanged in at least one parent.

The implementation touches only `log-tree.c`, adding helper functions (`commit_has_path`, `follow_needs_renames`) and modifying the merge-diff loop to track which parents still need rename detection. The commit message reports the test case now takes 36 seconds, restoring performance close to the pre-regression baseline. SZEDER Gábor is credited with assistance. The patch is well-motivated, includes before/after measurements, and addresses a clear pain point for users of `--follow` on large repositories.

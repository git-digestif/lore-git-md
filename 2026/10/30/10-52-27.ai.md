This is the third patch in Harald Nordgren’s v13 series introducing `remote.<name>.fetchRefmap` for matching-inspired fetch mode. The series is now implementation-complete and under final review for merging to `master`, with only the override semantics edge case still open.

This patch implements the core dynamic branch enumeration logic: when a remote has `remote.<name>.fetchRefmap` configured but no `remote.<name>.fetch`, a refspec-less `git fetch` infers which branches to fetch by enumerating local branches whose `@{upstream}` points to that remote. The refmap itself only controls where those fetched refs land, not which branches are selected. The patch touches `builtin/fetch.c`, `remote.c`, and `remote.h`, adding the `branches_tracking_remote()` helper and integrating it into `get_ref_map()`. The new test file `t/t5586-fetch-refmap.sh` (133 lines) verifies the behavior, including edge cases like branches tracking different remotes, duplicate upstream tracking, and prefetch storage.

The implementation is mechanical and well-tested, with no known issues. The patch is uncontroversial and aligns with the series’ finalized design, which decouples the "what" (which refs to fetch) from the "where" (where to store them) using `remote.<name>.fetchRefmap`. The precedence rule (`remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration) is preserved, and the patch does not alter the override semantics discussion still underway for command-line refspecs and colon-separated `remote.<name>.fetch` entries. The extracted helper `branches_tracking_remote()` is a clean refactoring that enables reuse in `get_ref_map()` and aligns with the `the_repository` removal effort.

Key symbols introduced: `branches_tracking_remote()`, `add_if_tracking_remote()`, and the `branches_tracking_remote_cb_data` struct. The patch also updates documentation to clarify when dynamic branch enumeration is triggered and how it interacts with the refmap.

This is a performance-focused bugfix series targeting the `git log --follow` functionality, specifically for non-linear history (merges). The series is now at v4, with six patches that collectively address performance regressions and correctness issues introduced by earlier changes.

The core problem is that `git log --follow`—which tracks file renames across history—became significantly slower when dealing with merges after commit 304812ed33 (June 2026). The series first fixes two correctness bugs: one where `-m --follow` loses history from non-first parents, and another where `--follow` fails to track edits on the side of a merge that was dropped. It then introduces a targeted optimization that reduces the number of rename-detection passes needed when following a file through merges, cutting runtime for a real-world case (linux.git) from ~3 minutes to ~37 seconds.

Patch 3/6 is a standalone fix for the `-m --follow` bug, while patch 4/6 simplifies the rename-following logic without changing behavior. Patch 5/6 delivers the main speedup, and patch 6/6 corrects the edge case where an edit on the dropped side of a merge was being missed. The test suite (`t4219`) is expanded in patches 1/6 and 6/6 to cover these scenarios, including a new test for `--diff-merges=first-parent` interaction.

The interdiff shows the key technical change: the rename-detection logic now only checks for renames from files that the merge actually deleted, rather than scanning all files in every parent. This is implemented via two new helper functions (`follow_parent_changed_dropped_file` and `follow_has_rename_source`) that narrow the search space. The series also handles the `--first-parent` case correctly by disabling rename detection after the first parent is processed, while still walking all parents to maintain history coverage.

The patches touch `log-tree.c` and add tests to `t/t4219-log-follow-merge.sh`. The commit messages are detailed, referencing specific prior commits and real-world performance numbers. The code is well-structured, with each patch addressing a distinct issue, and the interdiff makes it easy to see how the logic evolved between v3 and v4. This looks like a mature, well-tested series that addresses a real pain point for users working with large repositories.

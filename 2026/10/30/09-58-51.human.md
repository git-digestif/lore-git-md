This is the second patch in Elia Pinto’s four-part series fixing 64-to-32 truncations on Windows (LLP64 platforms). It plugs a crash in the word-diff code when processing large files.

The bug is straightforward: since Jeff King’s 2026 commit 3c7a31204f the `mmfile_t` size is a `size_t`, but the word-diff buffers still track their allocated size in `unsigned long` (struct `diff_words_buffer`) or `long` (`diff_words_fill`). On 32-bit `long` platforms the `alloc_nr()` macro overflows when the buffer grows past ~700 MiB, producing a negative size that `REALLOC_ARRAY` turns into a huge allocation request and a fatal `die()`. Even if the buffer never overflows, the type mismatch is a latent truncation risk.

The fix is mechanical: change both counters to `size_t`. The patch touches only `diff.c` (two lines), keeps the on-disk format unchanged, and introduces no new symbols. It is part of the larger effort to align Git’s internal types with the 64-bit file sizes already exposed by the ODB layer, and it directly addresses a user-visible crash on Windows. The commit message is clear and cites the exact commit that introduced the type mismatch, making the motivation obvious. No test is added here because the series’ fourth patch (`t1007-hash-object.sh`) already covers the 4 GiB+ scenario that would trigger the overflow.

This is the fourth iteration of a bugfix/refactoring patch that defers validation of the `remote.<name>.followRemoteHEAD` configuration setting until it is actually needed—specifically, during `git fetch`. The patch eliminates spurious warnings emitted by commands like `git push` or `git remote -v` that load but never use the setting. It follows the model of an earlier change (86129fd) that did the same for `fetch.followRemoteHEAD`.

The author, Colin Hinton, has incorporated all feedback from previous versions, including Junio C Hamano’s suggestion to split the change into a two-patch series. The first patch extracts existing logic (currently commented with "See remote.c's handling of ...") into a new helper function, `determine_follow_remote_head()`, while the second extends it to defer validation. This refactoring fully resolves a mechanical conflict with Harald Nordgren’s in-flight `hn/fetch-refmap` topic, though the dependency itself must still graduate before this patch can be integrated.

The patch touches `remote.c`, `builtin/fetch.c`, `builtin/remote.c`, documentation files, and adds test coverage in `t5510-fetch.sh`. It introduces no on-disk format changes and maintains backward compatibility. The only remaining blocker is the graduation of `hn/fetch-refmap`; once that happens, this patch is ready for `next` or `master`. Matt Hunter’s explicit approval ("Looks good") from v2 remains valid, and Junio has signaled the patch is otherwise technically sound.

This is a well-crafted, narrowly scoped fix that addresses a real annoyance—spurious warnings—without introducing risk. The refactoring is clean, the test coverage is appropriate, and the dependency is the only thing holding it back. For anyone following Git’s configuration subsystem or fetch plumbing, this is worth tracking, but it’s unlikely to be controversial once the dependency clears.

This is a **substantive review comment** on the second patch of Harald Nordgren’s `git imap-send` bugfix series (now merged to `next`). Junio C Hamano identifies a latent bug in the `has_required_headers()` helper function introduced in Patch 2/4: the function assumes LF line endings (`\n\n` to detect the end of headers) but IMAP messages use CRLF (`\r\n`). This mismatch means the function could scan past the header block into the message body, potentially misclassifying messages with body text that resembles headers (e.g., a line starting with `From: ` in the body).

The issue is not hypothetical—it stems from IMAP’s RFC 2060 requirement for CRLF line endings, which the rest of `imap-send.c` already respects. The helper function’s current implementation risks false positives (e.g., treating a `Subject:` line in the body as a valid header) or false negatives (e.g., failing to detect headers if the message uses mixed line endings). Junio’s observation is precise: the function’s logic is brittle and needs to align with the existing code’s handling of CRLF.

This is a **blocking concern** for the series, despite its prior merge to `next`. The fix is likely straightforward (e.g., using `strstr(line, "\r\n\r\n")` or adapting the line-iteration logic to account for CRLF), but it requires a new iteration of the patch. The series’ other patches (case-insensitive headers, tunnel process fixes) are unaffected, but this issue undermines the core goal of RFC 5322 compliance. Expect a `v5` to address it.

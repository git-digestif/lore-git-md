This is the fifth patch in Harald Nordgren’s six-patch v13 series introducing `remote.<name>.fetchRefmap` for matching-inspired fetch mode. The patch makes `--limited-fetch` the default when adding a remote to a shallow repository, ensuring that `git remote add` does not configure a wildcard refspec that would defeat the purpose of shallow cloning.

The change is small and targeted: it modifies `builtin/remote.c` to check `is_repository_shallow(the_repository)` when `limited_fetch` is unset (its default value), turning on `--limited-fetch` automatically in shallow repositories unless the user explicitly requests `--no-limited-fetch`, `-t/--track`, or `--mirror`. The documentation in `git-remote.adoc` is updated to explain the new default, and the test suite (`t/t5505-remote.sh`) adds four new tests covering the behavior in shallow and full repositories, with and without explicit overrides.

The patch is well-motivated and uncontroversial. It addresses the real-world pain point described in the commit message—adding a remote to a shallow clone used to fetch every branch the remote has, making `git fetch` slow or hang—without breaking existing workflows. The implementation is mechanical and aligns with the series’ overall design, which has already been finalized and endorsed by Junio and Phillip Wood. The test coverage is thorough, verifying that the default is applied only in shallow repositories, that explicit overrides work, and that full repositories retain the traditional wildcard refspec. There are no known edge cases or open questions specific to this patch; it is ready for review and likely to graduate with the rest of the series once the override semantics discussion in the thread is resolved.

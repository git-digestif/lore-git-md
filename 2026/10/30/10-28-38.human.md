This is a **bugfix patch** targeting a truncation issue in Git's notes subsystem on LLP64 platforms (e.g., 64-bit Windows). It is the fifth patch in Elia Pinto's six-patch series addressing loose object handling and size truncation bugs, with this one focusing on `combine_notes_concatenate()`.

The bug occurs when concatenating two notes whose combined size exceeds 4 GiB. On platforms where `unsigned long` is 32-bit (like Windows), the function calculates the combined buffer size as an `unsigned long`, which silently truncates the value. This leads to a buffer allocation that is too small, followed by a `memcpy()` that writes past the end of the buffer, corrupting memory. The issue can be triggered by fetching notes, merging notes with the "union" strategy, or even just displaying notes that exist at multiple fanout levels in the notes tree.

The fix changes the buffer size calculation to use `size_t` (via `st_add3()`) and introduces `cast_size_t_to_ulong()` when passing the size to `odb_write_object()`, which still expects an `unsigned long`. This ensures the function fails explicitly on platforms where the size cannot be represented, rather than silently truncating and corrupting memory. The commit message notes that a full fix would require updating the write API to use `size_t`, but this patch provides a safe intermediate step.

No test is included, as reproducing the issue requires a platform with 32-bit `long` and notes larger than 4 GiB, which is impractical to automate. The patch is well-motivated and clearly explains the problem, the fix, and the limitations. It complements the broader series' goal of hardening loose object handling, particularly on Windows. The change is minimal and focused, touching only the buffer size calculation and type conversion in `notes.c`.

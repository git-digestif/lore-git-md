Core problem or goal
`git log --follow` (which tracks file renames across history) became ~14× slower when processing merges after commit 304812ed33 (June 2026). The v5 series fixes two correctness bugs—`-m --follow` losing history from non-first parents and `--follow` missing edits on dropped sides of merges—and introduces a targeted optimization that reduces the number of rename-detection passes needed when following a file through merges. The optimization now also addresses correctness regressions in handling file copies and unrelated histories (e.g., subtree merges). The remaining performance gap (~1.6× slower than pre-304812ed33) has become a **deployment blocker for GitLab**, prompting a **project-level policy decision**: whether `--follow` should be **reverted, further optimized, or made opt-in via a new toggle**. The thread has now **settled on an opt-in toggle** as the pragmatic path forward, with Patrick Steinhardt proposing a **fast-tracked single-patch series** to implement it.

Key technical details
- Files touched: `log-tree.c`, test suite (`t/t4219-log-follow-merge.sh`).
- New/updated helper functions: `follow_parent_changed_dropped_file` and `follow_has_rename_source` (narrow rename-detection to files deleted by the merge), `follow_needs_renames()` (optimization gatekeeper, now handles copies and unrelated histories).
- Behavior change: `--first-parent` disables rename detection after the first parent but still walks all parents to maintain history coverage. No on-disk format changes.
- Test coverage: new tests in `t4219` for `-m --follow` correctness, dropped-side edits, `--diff-merges=first-parent` interaction, file copy tracking, and unrelated histories.
- Optimization core: limit rename detection to files deleted by the merge, but the remaining performance gap (~1.6× slower than pre-304812ed33) is now deemed unacceptable for default behavior. The proposed toggle will **disable `--follow` by default** for non-linear history, mitigating the performance cost while preserving the correctness fixes.

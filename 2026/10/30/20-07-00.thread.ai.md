Core problem or goal
`git log --follow` (which tracks file renames across history) became ~14× slower when processing merges after commit 304812ed33 (June 2026). The series fixes two correctness bugs—`-m --follow` losing history from non-first parents and `--follow` missing edits on dropped sides of merges—and introduces a targeted optimization that reduces the number of rename-detection passes needed when following a file through merges. The optimization now also addresses correctness regressions in handling file copies and unrelated histories (e.g., subtree merges). The remaining performance gap (~1.6× slower than pre-304812ed33) has become a **deployment blocker for GitLab**, prompting a debate over whether the feature should be **reverted, further optimized, or made opt-in via a new toggle**. The thread has now shifted from technical correctness to **project-level policy**: whether `--follow` should remain enabled by default given its performance cost.

Key technical details
- Files touched: `log-tree.c`, test suite (`t/t4219-log-follow-merge.sh`).
- New/updated helper functions: `follow_parent_changed_dropped_file` and `follow_has_rename_source` (narrow rename-detection to files deleted by the merge), `follow_needs_renames()` (optimization gatekeeper, now handles copies and unrelated histories).
- Behavior change: `--first-parent` disables rename detection after the first parent but still walks all parents to maintain history coverage. No on-disk format changes.
- Test coverage: new tests in `t4219` for `-m --follow` correctness, dropped-side edits, `--diff-merges=first-parent` interaction, file copy tracking, and unrelated histories.
- Optimization core: limit rename detection to files deleted by the merge, but the remaining performance gap (~1.6× slower than pre-304812ed33) suggests further tuning may be needed or that the feature’s default behavior should be reconsidered.

Open questions and loose ends
- **Opt-in mechanism**: Config key (`log.followNonLinear`) vs. flag (`--follow=strict`). The former is more discoverable for users; the latter may be easier to implement. Consensus on the mechanism is still pending.
- **Default value**: Both Miklos and Patrick agree the feature should be **disabled by default**, but the toggle’s design (and whether it should be documented as temporary) remains open.
- **Revert vs. toggle**: A revert would reintroduce correctness bugs (e.g., `-m --follow` losing history from non-first parents). The toggle preserves the fixes while mitigating the performance cost, but may require additional documentation or user education.
- **Maintainer/PLC input**: The project-level question ("should `--follow` be opt-in?") may require input from Junio or the PLC, as it affects user-facing behavior and deployment constraints for major Git hosts. No maintainer response has been recorded yet.

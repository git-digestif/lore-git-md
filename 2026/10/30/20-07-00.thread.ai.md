Core problem or goal
`git log --follow` (which tracks file renames across history) became significantly slower when processing merges after commit 304812ed33 (June 2026). The series fixes two correctness bugs—`-m --follow` losing history from non-first parents and `--follow` missing edits on dropped sides of merges—and introduces a targeted optimization that reduces the number of rename-detection passes needed when following a file through merges. The optimization cuts runtime for a real-world linux.git case from ~3 minutes to ~37 seconds. The goal now includes addressing correctness regressions in the optimization’s handling of file copies and unrelated histories.

Current status
Under review. Series is at v4, posted by Miklos Vajna. No maintainer decision or merge status reported. Key changes from prior versions:
- Patch 3/6: standalone fix for the `-m --follow` bug (non-first-parent history loss).
- Patch 4/6: refactors rename-following logic without behavior change.

- Patch 6/6: intended to fix the edge case where edits on the dropped side of a merge were missed, but Patrick Steinhardt’s review demonstrates it introduces a new correctness gap for file copies.
- Tests expanded in patches 1/6 and 6/6 to cover new scenarios, including `--diff-merges=first-parent` interaction.

Key technical details
- Files touched: `log-tree.c`, test suite (`t/t4219-log-follow-merge.sh`).
- New helper functions: `follow_parent_changed_dropped_file` and `follow_has_rename_source` (narrow rename-detection to files deleted by the merge), `follow_needs_renames()` (optimization gatekeeper).
- Behavior change: `--first-parent` now disables rename detection after the first parent but still walks all parents to maintain history coverage.
- On-disk format: no changes.
- Test coverage: new tests in `t4219` for `-m --follow` correctness, dropped-side edits, `--diff-merges=first-parent` interaction, and (now) file copy tracking.
- The optimization in patch 5/6 introduces `follow_needs_renames()`, which Patrick Steinhardt notes may incorrectly disable rename detection for commits with unrelated histories (no merge base) and, as now revealed, fails to track edits to the source of a copy when the merge keeps the copied file but drops the original.

Open questions and loose ends
- **Correctness concern in patch 5/6**: `follow_needs_renames()` disables rename detection for commits with unrelated histories, contradicting the intent of commit 304812ed33. This requires resolution.
- **Correctness regression in patch 6/6**: the new logic fails to track edits to the *source* of a copy when the merge keeps the copied file but drops the original. Patrick Steinhardt’s test case demonstrates the regression: a copy of file `F` to `G` on `master`, an edit to `F` on a side branch, and a merge that keeps `G` but discards `F` results in `git log --follow G` no longer showing the edit to `F` on the side branch. This is a blocking concern.
- Both issues stem from the assumption in `follow_needs_renames()` that only renames (not copies) need to be considered when the merge base lacks the path. Resolution will likely require revising this logic to account for copies or documenting the behavioral change.

Core problem or goal
`git log --follow` (which tracks file renames across history) became ~14× slower when processing merges after commit 304812ed33 (June 2026). The series fixes two correctness bugs—`-m --follow` losing history from non-first parents and `--follow` missing edits on dropped sides of merges—and introduces a targeted optimization that reduces the number of rename-detection passes needed when following a file through merges. The optimization now also addresses correctness regressions in handling file copies and unrelated histories (e.g., subtree merges), though a performance gap remains: v5 reduces runtime from ~336s to ~39s, still ~1.6× slower than the pre-regression baseline (~23s).

Key technical details
- Files touched: `log-tree.c`, test suite (`t/t4219-log-follow-merge.sh`).
- New/updated helper functions: `follow_parent_changed_dropped_file` and `follow_has_rename_source` (narrow rename-detection to files deleted by the merge), `follow_needs_renames()` (optimization gatekeeper, now handles copies and unrelated histories).
- Behavior change: `--first-parent` disables rename detection after the first parent but still walks all parents to maintain history coverage. No on-disk format changes.
- Test coverage: new tests in `t4219` for `-m --follow` correctness, dropped-side edits, `--diff-merges=first-parent` interaction, file copy tracking, and unrelated histories.
- Optimization core: limit rename detection to files deleted by the merge, but performance gap suggests further tuning may be needed.

Open questions and loose ends
- **Performance trade-off**: The series reduces the regression from ~14× to ~1.6× slower than pre-304812ed33, but the gap remains significant. Justin Tobler’s proposal to make `--follow` opt-in (via a new flag) or revert 304812ed33 could spark debate about the feature’s default behavior.

- **Scope of `--follow`**: Justin’s suggestion to revert 304812ed33 risks reintroducing the original correctness bugs (e.g., lost history in `-m --follow`), while an opt-in flag could fragment user expectations.

This is a bugfix patch, the third in a six-patch series from Miklos Vajna. It targets a long-standing edge case in `git log -m --follow`: when following a file through a merge commit, Git loses the history of all but the first parent because the internal "followed path" state is not reset between parent diffs.

The problem is concrete and well-explained: in a diamond merge (two divergent renames that converge in a merge), `git log -m --follow <path>` shows only the commits from the first parent’s side. The fix is small and surgical—save the merge’s original path before the parent loop, restore it before each diff, and free it afterward. The patch adds a regression test that verifies the full history (commits A, B, C, X, Y, Z) is now visible.

The commit message is clear, the test is self-contained, and the code change is minimal. No controversy is evident; this looks like a straightforward correctness fix.

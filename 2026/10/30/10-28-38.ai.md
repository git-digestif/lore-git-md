This is the fifth patch in Elia Pinto’s six-patch **bugfix series** addressing loose object handling and size truncation issues, with a focus on LLP64 platforms (e.g., 64-bit Windows where `long` is 32-bit). This specific patch fixes a truncation bug in `combine_notes_concatenate()` where the combined size of two notes is computed as an `unsigned long`, risking silent overflow when notes exceed 4 GiB. On affected platforms, this could lead to buffer overruns during `memcpy()` or truncated note blobs being written to the object database.

The fix converts the size calculation to use `size_t` and `st_add3()` for safety, then explicitly casts to `unsigned long` when passing the size to `odb_write_object()`—a function still constrained by its legacy `unsigned long` parameter. This ensures the operation fails loudly (via `cast_size_t_to_ulong()`) rather than silently corrupting data. The patch is minimal, touching only `notes.c`, and aligns with the series’ broader goal of hardening size-related code paths against truncation.

No automated test is included, as reproducing the bug requires a 32-bit `long` platform and notes exceeding 4 GiB, but the commit message clearly documents the scenario (e.g., fetching large notes or displaying multi-note trees). The fix is well-motivated and follows the pattern established in earlier patches (e.g., patch 2/6’s propagation of `size_t` through loose object reading). While the `odb_write_object()` API remains a bottleneck, this patch mitigates the immediate risk while leaving the broader API modernization for future work. The change is uncontroversial and likely to be accepted as-is.

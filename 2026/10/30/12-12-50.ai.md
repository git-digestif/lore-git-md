This is a **documentation** patch that introduces a new man page (`gitsecurityboundary(7)`) to formally define Git's security boundary. The patch addresses a long-standing gap: the Git project receives many security reports that are ultimately deemed "not vulnerabilities" because they fall outside Git's intended security guarantees, but until now there was no authoritative document explaining those boundaries.

The new documentation codifies the principle that Git's security boundary concerns *unexpected or implicit execution of attacker-controlled code*. Inspecting repository contents (e.g., with `git log`) is considered safe, but executing hooks, filters, or other repository-supplied programs is not—unless the user explicitly enables them. The document also clarifies that Git does not protect against attackers who already have write access to the local disk, and it distinguishes between direct user intent (e.g., running a hook manually) and indirect recursion (e.g., submodule initialization without user input).

The patch includes historical context by citing specific commits and CVEs (e.g., CVE-2019-19604, `protocol.file.allow` hardening) that shaped the current understanding of Git's security model. It also explains how to create a "sanitized clone" of an untrusted repository using `git clone --no-local`, which excludes dangerous configuration and hooks. The document is linked from `git(1)` and `SECURITY.md`, ensuring it will be discoverable by both users and security reporters.

This effort was driven by Toon Claes, with substantial input from Patrick Steinhardt and Junio C Hamano, and it directly responds to the recent surge in AI-assisted security reports—many of which are well-argued but misaligned with Git's actual security guarantees. The patch is well-motivated, clearly written, and touches no code, making it uncontroversial in principle. However, the discussion in the commit message about a hypothetical `--safe` flag (which is *not* part of this patch) hints at future work that could be more contentious. For now, this patch provides a solid foundation for triaging security reports.

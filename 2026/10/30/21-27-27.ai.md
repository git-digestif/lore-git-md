This is a **substantive review** of the core API patch (3/6) in Christian Couder’s `parse-options` early-scanning series. Kaartic Sivaraam raises two technical points about the `early_scan_options()` implementation, both addressing potential correctness and usability issues.

First, Kaartic suggests adding validation checks *inside* `early_scan_options()` itself, not just in `parse_options_check()`. The current design relies on `parse_options_check()` (called by `parse_options_start()`) to catch invalid uses of `PARSE_OPT_EARLY`—such as short options or `OPTION_SUBCOMMAND`—but if a caller invokes `early_scan_options()` *before* `parse_options_start()`, these errors would go undetected. This is a real edge case: while most commands call `parse_options_start()` early, nothing enforces that order, and a misordered call could lead to silent misbehavior or crashes. The suggestion is pragmatic and low-risk, as it duplicates no logic—it merely moves the existing checks into the API entry point.

Second, Kaartic proposes clarifying the API documentation to warn callers that the `option` pointer passed to the callback is ephemeral. The pointer refers to internal `parse-options` data structures that may be freed once the scan completes, so callers must not retain it. This is a subtle but important correctness note: without it, a caller might cache the pointer and dereference it later, leading to use-after-free bugs. The clarification is a small but meaningful improvement to the API contract.

The rest of the patch is uncontroversial and well-reviewed. Kaartic’s feedback is narrowly targeted at two specific, actionable improvements—neither changes the core design, but both address real risks. The review is **tested-level**: it identifies concrete failure modes (misordered calls, pointer retention) and suggests straightforward fixes. The feedback is fully compatible with the series’ goal of replacing fragile hand-rolled scans with a robust, reusable API. Christian’s v3 already addresses the major v2 concerns (abbreviations, negated options, aliases), and this review polishes the remaining rough edges. The series remains **ready for `next`** once these points are addressed, though the unresolved usability question (caller vs. callee argument skipping) may still require maintainer input.

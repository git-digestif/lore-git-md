Core problem or goal
An Outreachy applicant proposes writing regression tests for an edge case in which a shell alias running a Git command (`git -C ../other-repo rev-parse`) from inside a **linked worktree** inherits the parent worktree’s `GIT_DIR` environment variable, causing the nested command to report the wrong repository’s directories. The goal is to determine whether this test-writing task is a suitable Outreachy microproject, given the behavior’s intentional design in `handle_alias()` and the risk that a regression test might lock in a design that could later change.

Current status
No patch series exists; the thread remains an exploratory inquiry. The author and Priestess (Cynthia) have confirmed the behavior on Git 2.56.GIT, reproduced the issue, and identified `GIT_DIR` inheritance as the root cause. The discussion has shifted from a pure test-writing task to a design question: whether the current behavior (exporting `GIT_DIR` to aliases) is correct or should be revisited. Outreachy mentors (Christian Couder, Kaartic Sivaraam, Siddharth Asthana, Usman Akinyemi) have been added to weigh in on microproject suitability.

Key technical details
- Subsystem: worktree handling, environment variable propagation
- Files likely to be touched: `t/` (test scripts, e.g., `t/tXXXX-worktree-env-inheritance.sh`), possibly `setup.c` or `environment.c` if a code change is deemed necessary

Open questions and loose ends
- **Design intent**: Is the current behavior (exporting `GIT_DIR` to aliases via `handle_alias()`) correct, or should it be changed? A regression test would implicitly endorse the current behavior, which might not age well.

- **Code vs. test**: Should the microproject include a code change (e.g., clearing `GIT_DIR` in certain contexts), or is test coverage alone sufficient?

This is the third patch in the v5 series introducing `--delete-integrated` to `git branch`. It implements the core logic for detecting branches whose changes (but not their tips) have been integrated upstream via rebase or squash merges, even when upstream modified the same files. The patch adds the new `--delete-integrated` flag, which complements `--delete-merged` by performing change-based detection rather than strict tip-reachability.

The algorithm works by collecting all file changes introduced by the branch since its fork point, then scanning upstream commits for the first one that contains all those changes (using tree-based diffing for rebase detection and a path-by-path three-way merge approximation for squash merges). When such a commit is found, the branch is deleted and the landing commit is reported in the output. The implementation avoids reading file contents, so it remains cheap in partial clones, though the three-way merge approximation may download blobs when upstream modifications are present.

The patch touches `builtin/branch.c` (adding the new flag, detection logic, and helper functions), updates the documentation to describe `--delete-integrated`, and extends the test suite with coverage for rebase merges, squash merges, reverted changes, partial landings, and mixed workflows. The new behavior is opt-in and cannot be combined with `--delete-merged`, addressing the false-positive concern raised in earlier reviews. The output format shows both the branch’s old tip and the landing commit when available.

The core algorithm remains unchanged from v4: rebase detection is tree-based (no blob fetches), squash detection uses `ll_merge` for three-way merge approximation, and the first landing commit is used regardless of later reverts. The patch does not yet implement the author-check mitigation (Jasper’s proposal to require that the landing commit’s author also authored at least one commit on the branch being deleted), which remains the sole major technical gap for safety in forge workflows and the "npm update" scenario. Performance trade-offs for large repositories or blobless clones are still unaddressed.

This is the second patch in Elia Pinto’s six-patch bugfix series addressing loose object handling and size truncation issues, particularly on LLP64 platforms like 64-bit Windows. The patch aligns the loose object reading path on the `size_t` type to prevent truncation when dealing with objects larger than 4 GiB. Previously, functions like `unpack_loose_rest()` and `map_fd()` used `unsigned long` for sizes, which is only 32 bits on Windows, leading to silent truncation and potential buffer overflows when processing large objects.

The change is straightforward: replace `unsigned long` with `size_t` in function signatures and variables across `object-file.c`, `object-file.h`, and `odb/source-loose.c`. This ensures consistency with earlier work (c6a4629e32) that switched `object_info.sizep` to `size_t`. The patch touches core loose object handling functions (`unpack_loose_header()`, `unpack_loose_rest()`, `map_fd()`, and `check_stream_oid()`), as well as the streaming reader in `odb/source-loose.c`.

While the fix is technically sound, the lack of automated test coverage is notable. The commit message explains that testing requires a 4 GiB object, making it impractical to include in the test suite. Instead, the author provides manual reproduction steps for Windows, demonstrating the issue with a crafted loose object. This is a reasonable trade-off given the platform-specific nature of the bug, but it means the fix relies on careful code inspection rather than automated validation.

The patch is well-motivated and addresses a real problem—silent truncation of large objects on Windows could lead to memory corruption or crashes in repositories with multi-gigabyte objects. The changes are confined to internal APIs and do not affect the on-disk format, so there’s no risk of breaking compatibility. This looks like a solid, uncontroversial fix that should proceed smoothly through review.

This thread introduces a new man page, `gitsecurityboundary(7)`, to formally define Git's security boundary—a long-standing gap in the project's documentation. The patch, authored by Johannes Schindelin via GitGitGadget, addresses the recurring issue of security reports being misclassified as vulnerabilities because Git's security guarantees were previously undocumented. The new documentation clarifies that Git's security model focuses on preventing *unexpected or implicit execution of attacker-controlled code*, while explicitly distinguishing between safe operations (e.g., inspecting repository contents) and unsafe ones (e.g., executing hooks or filters without explicit user consent).

The document is uncontroversial in its current form, as it codifies existing practices and historical decisions (e.g., CVE-2019-19604, `protocol.file.allow` hardening) without introducing new behavior. It also provides practical guidance, such as how to create a "sanitized clone" of an untrusted repository using `git clone --no-local`. The patch was driven by Toon Claes, with input from Patrick Steinhardt and Junio C Hamano, and is linked from `git(1)` and `SECURITY.md` for visibility. While the commit message briefly mentions a hypothetical `--safe` flag (not part of this patch), the current work is purely documentation and should face no opposition. This effort directly responds to the recent influx of AI-assisted security reports, many of which target scenarios outside Git's intended security boundary.

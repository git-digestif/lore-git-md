This is the v13 revision of Harald Nordgren’s six-patch series introducing `remote.<name>.fetchRefmap` to solve the long-standing performance problem of shallow repositories fetching every branch of a new remote. The series is now **implementation-complete and under final review for merging to `master`**.

The core goal remains unchanged: when a shallow repository (created with `git clone --depth`) runs a refspec-less `git fetch`, it should fetch only the branches tracked by local branches at that remote, not every branch on the remote. The v13 revision **resolves the last two technical edge cases** that were blocking graduation:

1. **`@{push}` resolution** – Patch 6/6 adds a mechanical fallback in `remote.c` so that `@{push}` resolves correctly when `remote.<name>.fetchRefmap` is configured. The fix mirrors the existing fallback logic for `remote.<name>.fetch` and is uncontroversial.
2. **Override semantics for colon-separated `remote.<name>.fetch` entries** – Patch 1/6 adds a regression test confirming that a colon-separated `fetch` entry (e.g., `+refs/heads/master:refs/remotes/custom/master`) is stored in **both** the explicit destination (`refs/remotes/custom/master`) and the refmap’s destination (`refs/remotes/cabal/master`). This behavior matches the **override semantics** that Junio and Phillip Wood converged on in the v12 discussion: command-line refspecs (or their config-based equivalents) override `remote.<name>.fetchRefmap` entirely, not coexist with it. The test documents the chosen behavior and ensures it does not regress.

The series is **well-tested**, with 151 new lines in `t/t5510-fetch.sh` and a new test file `t/t5586-fetch-refmap.sh` covering edge cases like forced updates, `@{push}` resolution, and backwards compatibility. The documentation in `remote.txt`, `git-fetch.adoc`, and `git-remote.adoc` is complete and now explicitly states the override semantics, precedence rules, and the minor inconvenience of forced-update placement (`+` on the refmap side).

The **design is finalized** and endorsed by Junio and Phillip Wood. The only remaining work before graduation is addressing any last-minute review nits (e.g., code style, commit message wording) and ensuring the documentation is crystal-clear about the override semantics and backwards-compatibility considerations. A v14 revision is unlikely unless a substantive issue surfaces; the series is **expected to graduate in the current cycle**.

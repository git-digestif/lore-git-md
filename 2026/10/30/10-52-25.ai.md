This is the first patch in Harald Nordgren’s v13 series introducing `remote.<name>.fetchRefmap`, a new configuration key that decouples the "what to fetch" logic from the "where to store it" mapping. The patch adds the config variable itself, updates the `remote` struct to hold it, and teaches `remote_find_tracking()` to fall back to the refmap when `remote.<name>.fetch` has no match. The implementation is mechanical and well-tested, with 144 new lines of tests in `t/t5510-fetch.sh` covering edge cases like negative refspecs, explicit-destination refspecs, and `@{upstream}` resolution.

The patch is part of a six-patch series that is now under final review for merging to `master`. The design is finalized and endorsed by Junio C Hamano and Phillip Wood, including the precedence rule (`remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration) and the placement of forced updates (`+`) on the refmap side. This patch introduces the core plumbing: the new config key, its parsing in `remote.c`, and the fallback logic in `remote_find_tracking()`. The test suite verifies that the refmap works as expected when combined with explicit refspecs, negative refspecs, and branch tracking.

The only remaining open question for the series is the override semantics for command-line refspecs and colon-separated `remote.<name>.fetch` entries, which the thread has converged toward resolving in favor of override semantics (Phillip Wood’s preference). This patch does not yet implement the override logic; that will be addressed in a later patch in the series (likely v14). The current implementation preserves the dual-storage behavior for colon-separated `fetch` entries with explicit destinations, which is expected to be updated in the next revision.

This thread is about a performance regression in `git log --follow` that made it nearly unusable on merge-heavy histories, such as the Linux kernel repository. The issue was introduced in June 2026 by commit 304812ed33, causing a test case to slow from 28 seconds to nearly 7 minutes. Miklos Vajna’s six-patch series (now at v4) proposes a fix in its fifth patch, which restructures how `log_tree_diff()` handles merges when `--follow` is active.

The solution replaces the previous approach—diffing each merge against all parents with full rename detection—with a two-pass strategy. First, it checks for a parent where the path is unchanged without rename detection; if found, it follows that parent’s history and only performs rename detection against parents where the path might have been renamed. This reduces the number of rename-detection passes from O(n) to O(1) in common cases, restoring performance to near pre-regression levels (36 seconds in the test case). The patch touches only `log-tree.c`, adding helper functions and modifying the merge-diff loop, and includes before/after measurements to validate the improvement.

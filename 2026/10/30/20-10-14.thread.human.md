This thread is about a bugfix for `git log --follow` when used with merges, specifically addressing a regression where edits from a side branch were incorrectly omitted after a merge with `-s ours`. The issue occurs when a file is renamed on one branch, edited on another, and then merged while keeping the renamed version—previously, `--follow` would show the edit, but after the regression, it stopped doing so.

Miklos Vajna identified the problem and proposed a fix in the sixth and final patch of the v4 series. The solution modifies `follow_needs_renames()` in `log-tree.c` to detect renames in cases where the merge base lacks the path but a parent modified a file that the merge no longer includes. The fix is efficient, using two new helper functions to avoid unnecessary rename detection while correctly handling the edge case. A new test in `t/t4219-log-follow-merge.sh` verifies the fix.

The patch is well-motivated, with clear reasoning in the commit message and targeted changes to avoid performance overhead. The regression is user-visible and affects a real-world scenario, making this a practical and important fix. No review feedback or maintainer decisions have been mentioned yet, so the patch is still under consideration.

This is the first patch in a **v2 bugfix series** targeting **platform compatibility (Windows/LLP64)** and **integer-overflow safety** in Git’s object database (ODB) layer. The patch mechanically converts the length parameter of ODB write functions from `unsigned long` to `size_t` to prevent silent 64-to-32 truncation when writing objects larger than 4 GiB on Windows, where `long` is 32-bit. This is a direct follow-up to Johannes Schindelin’s 2026 read-side ODB work (commit c6a4629e32), which widened the read APIs but left the write side vulnerable.

The change touches six files: the core ODB API (`odb.c`, `odb.h`), two ODB source implementations (`source-inmemory.c`, `source-loose.c`), and the test suite (`t/t1007-hash-object.sh`). The diff is minimal—only type signatures and a single struct field are modified—but the impact is significant: without this patch, `git add` or `git hash-object -w` on a 4 GiB+ file with any conversion filter (e.g., `core.autocrlf`, `eol`, `ident`, or a clean filter) silently truncates the blob to the first 4 GiB, corrupting the object while leaving the index’s stat data intact. The new test in `t1007` verifies this by writing a 5 GiB file through a null filter and checking both the object ID and its size, ensuring the fix works end-to-end.

The patch is narrowly scoped and well-motivated, addressing a clear correctness issue on a supported platform. The commit message is exemplary: it traces the truncation path from caller (`index_mem()`, `index_stream_convert_blob()`) to callee (`odb_write_object_ext()`), explains the silent corruption mechanism, and contrasts the behavior of `git hash-object` with and without `-w`. The added test is marked `EXPENSIVE` and `SIZE_T_IS_64BIT`, matching the existing large-file test and ensuring it only runs where meaningful.

No behavior change occurs on 64-bit Linux, and the on-disk format remains unchanged. The patch is part of a broader effort to eliminate Windows-specific truncations (the author’s scan found 237 such sites; this series fixes four). Patrick Steinhardt’s review of v1 focused on test coverage and forward-looking design, both of which are now addressed in v2. The series appears ready for integration, with no open technical questions or objections.

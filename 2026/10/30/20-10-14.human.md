This is a bugfix patch targeting the `git log --follow` feature, specifically addressing a regression introduced by the previous patch in the series. The issue occurs when `--follow` is used on a file that was renamed on one branch but edited on a side branch that was merged with `-s ours` (meaning the merge kept the renamed file and discarded the edited one). Previously, `git log --follow` would correctly show the edit history from the discarded side branch, but after the earlier patch, it stopped doing so.

The problem stems from how `follow_needs_renames()` determines whether to search for renames in a parent commit. The original logic only looked for renames if the merge base still contained the old path, which works when the parent branch renamed the file but fails when the other side of the merge did the rename. The fix adds a two-step check: first, it cheaply determines whether the parent branch changed any files that the merge no longer has (indicating a potential rename source), and only then performs a targeted rename detection between the parent and the merge. This avoids the expensive full rename search in most cases while still catching the edge case.

The patch includes a new test case that sets up a merge where one branch renames `F` to `G` and the other edits `F`, then merges with `-s ours` to keep `G`. The test verifies that `git log --follow G` now correctly shows the edit history from the discarded `F` on the side branch. The commit message is thorough, explaining both the problem and the solution clearly, and the code changes are well-scoped to the rename-following logic in `log-tree.c`.

This looks like a well-crafted fix for a subtle but real regression. The test coverage is good, and the performance trade-off (a cheap check to avoid an expensive one) is sensible.

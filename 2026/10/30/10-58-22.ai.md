This is the first patch in a two-part bugfix series addressing silent truncation of trees larger than 4 GiB in Git’s tree-walk subsystem. The patch converts the size fields in `struct tree_desc` and related functions from `unsigned int`/`unsigned long` to `size_t`, ensuring 64-bit capacity on all relevant platforms. The change affects `tree-walk.c` and `tree-walk.h`, specifically `init_tree_desc()`, `init_tree_desc_gently()`, `decode_tree_entry()`, and the internal `dir_state` struct used by `get_tree_entry_follow_symlinks()`.

The motivation is clear: Git currently truncates trees at 4 GiB due to 32-bit size limits, causing `git ls-tree` to silently omit entries and `fsck` to miss validation checks for malicious paths like `.gitmodules`. The patch eliminates this truncation by using `size_t`, which is consistently 64-bit. The author verified the fix by simulating a 16-bit environment (demonstrating the same truncation behavior at 64 KiB) but did not include a test for the actual 4 GiB case, as it would require an impractically large in-memory tree.

The patch is mechanically straightforward, replacing type declarations and updating variable definitions to match. No behavior changes are introduced beyond fixing the truncation, and the on-disk format remains unchanged. The use of `size_t` aligns with Git’s conventions for buffer sizes elsewhere in the codebase. While the 4 GiB boundary is rare in practice, the fix is a necessary correctness improvement for edge cases and security validation.

This patch is part of a broader effort by the same author to eliminate size truncations in Git. It applies cleanly to `master` and has no review feedback yet, but the change is well-scoped and addresses a real issue with minimal risk. The second patch in the series will apply the same fix to `struct tree` and `parse_tree_buffer()`.

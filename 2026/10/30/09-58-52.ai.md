This is the third patch in Elia Pinto’s four-patch series (`v2 3/4`) that fixes 64-to-32 truncations on Windows (LLP64 platforms). It targets the file conversion subsystem (`convert.c`, `attr.c`, `read-cache.c`) and addresses a specific class of bugs: when Git scans a file larger than 4 GiB to decide whether it is binary, contains CRLF line endings, or contains `$Id$` keywords, the scanning functions (`gather_stats`, `gather_convert_stats`, `gather_convert_stats_ascii`, `count_ident`) truncate the file size to 32 bits because they take an `unsigned long` parameter. On Windows, this means only the first 4 GiB of the file is examined, leading to incorrect decisions (e.g., converting line endings in a binary file or failing to expand keywords that appear after 4 GiB).

The patch mechanically converts these functions to use `size_t` instead of `unsigned long`, matching the type used by the callers (notably `read_blob_data_from_index`, which already returns a `size_t` size). It also removes the `cast_size_t_to_ulong` wrapper in `read_blob_data_from_index`, eliminating the truncation path entirely. The changes are confined to type signatures and local variables; no behavior changes on 64-bit Linux, but on Windows they prevent silent misclassification of large files and potential corruption during CRLF conversion or keyword expansion.

The patch touches four files (`attr.c`, `convert.c`, `read-cache-ll.h`, `read-cache.c`) and is part of a broader effort to eliminate Windows-specific truncation bugs. The author’s commit message clearly explains the truncation mechanism and the consequences, and the patch itself is narrowly scoped and well-motivated. No new symbols are introduced, and the on-disk format remains unchanged. This patch directly addresses feedback from Patrick Steinhardt’s review of `v1`, which flagged the truncation risk in the conversion helpers. The series as a whole appears ready for integration, with all review feedback addressed and test coverage added in the other patches.

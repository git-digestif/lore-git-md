This is the v13 revision of Harald Nordgren’s six-patch series introducing `remote.<name>.fetchRefmap` to implement a "matching-inspired" fetch mode for shallow repositories. The series is now **implementation-complete and under final review for merging to `master`**, with all major design questions resolved and only documentation and edge-case polish remaining.

The core goal remains unchanged: users of shallow repositories (created with `git clone --depth`) experience slow or hanging `git fetch` operations when the remote has many branches, because a refspec-less fetch negotiates history for all remote branches. The v13 series implements a dynamic fetch mode that fetches only the branches tracked by local branches at the remote being fetched, using the new `remote.<name>.fetchRefmap` config key to separate the "what" (which refs to fetch) from the "where" (where to store them). The design is finalized and endorsed by Junio C Hamano and Phillip Wood, including the placement of forced updates (`+`) on the refmap side and the precedence rule (`remote.<name>.fetch` > `remote.<name>.fetchRefmap` > dynamic branch enumeration).

The v13 revision adds two key improvements. First, it resolves `@{push}` resolution when `remote.<name>.fetchRefmap` is configured by falling back to `remote->refmap` in `remote.c`, ensuring that `@{push}` works correctly without altering the series’ core behavior. Second, it adds a regression test confirming that a colon-separated `remote.<name>.fetch` entry with an explicit destination is stored in both that destination and the refmap’s, preserving backwards compatibility while the discussion on override semantics converges. The test suite now covers all critical edge cases, including forced updates, precedence rules, and dynamic branch enumeration.

The series touches `remote.c`, `builtin/fetch.c`, `builtin/remote.c`, and documentation, introducing the new `remote.<name>.fetchRefmap` config key, the `--limited-fetch` flag for `git remote add`, and the shallow-repository default.

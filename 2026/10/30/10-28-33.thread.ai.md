Thread identity: Subject "[PATCH v2 0/5] loose object handling and size truncation fixes on LLP64 platforms", series version v2 (five-patch series; rework of v1), originating author Elia Pinto, thread type bugfix series.

Core problem or goal: Fix five distinct bugs in loose object handling and size arithmetic, two affecting all platforms (missing size checks in loose object parsing and streaming) and three specific to LLP64 platforms (e.g., 64-bit Windows) where `long` is 32-bit but `size_t` is 64-bit. The bugs include missing bounds checks that could expose uninitialized heap memory or silently truncate objects, and truncation/overflow issues in `cat-file --batch`, `notes`, and the loose object reader due to `long` vs. `size_t` mismatches. The v1 `diff.c` fix (crash in `count_trailing_blank()` for 2--4 GiB files) has been dropped from this series because it is now handled by a separate series.

Current status: Under review; no maintainer decision yet. Series is rebased onto `master` at e1ec09b23c (previously b9e5cff180 in v1). Issues were reviewed on `git-security` and deemed non-security-sensitive.

Key technical details: Files touched include `object-file.c`/`object-file.h`, `odb/source-loose.c`, `builtin/cat-file.c`, `notes.c`, plus `t/t1006-cat-file.sh`, `t/t1060-object-corruption.sh`, and `t/lib-loose.sh`. Functions modified include `unpack_loose_header()`, `stream_loose_object()`, `batch_write()`, `concat_notes()`, `map_fd()`, `unpack_loose_rest()`, `check_stream_oid()`, `odb_source_loose_map_object()`, `combine_notes_concatenate()`. Patch 1/5 specifically fixes `unpack_loose_rest()` in `object-file.c` by adding a post-inflation validation that checks `status != Z_STREAM_END` or `stream->total_out - hdrlen != size`, reporting the object as corrupt and freeing the buffer if the check fails, mirroring validation already present in `unpack_compressed_entry()` for packfiles; this prevents uninitialized heap memory exposure when compressed data ends early and prevents silent truncation when the stream contains extra data. Patch 1/5 extends `loose_obj()` in `t/lib-loose.sh` to accept an optional third argument overriding the real content size with a bogus header value, and adds three tests to `t/t1060-object-corruption.sh` verifying that reading objects with too-large or too-small header sizes fails with a "corrupt loose object" error and that `git fsck` detects both cases. Patch 2/5 widens the loose-object size variables from `unsigned long` to `size_t` throughout the loose object reading path: it changes the signatures of `map_fd()`, `unpack_loose_header()`, `unpack_loose_rest()`, and `check_stream_oid()` in `object-file.c`/`object-file.h`, plus `odb_source_loose_map_object()` and related locals in `odb/source-loose.c`, so that the entire path from file mapping through header parsing and inflation uses `size_t` consistently. The motivation is that since commit c6a4629e32, `parse_loose_header()` already reports sizes as `size_t`, but downstream functions still took `unsigned long`; on LLP64 platforms such as 64-bit Windows, a header claiming 4 GiB + 5 bytes causes the buffer allocation to truncate to 6 bytes while `*oi->sizep` retains the full 64-bit value, leading callers like `read_loose_object()` to read far past the allocated buffer. Patch 2/5 has no automated test because reproducing the bug requires allocating a buffer near 4 GiB before the short-stream check can trigger; the commit message instead documents a manual reproduction using the `loose_obj()` test helper with a bogus header size. This patch complements patch 1/5, whose post-inflation size validation becomes effective on LLP64 only once these types are widened. Patch 5/5 uses `size_t` arithmetic with `cast_size_t_to_ulong()` (new symbol introduced in that patch) only where the legacy `odb_write_object()` API requires `unsigned long`. On-disk format is unchanged. Only patches 1/5 and 3/5 have automated test coverage; LLP64-specific and multi-gigabyte scenarios (patches 2/5, 4/5, 5/5) are documented with manual reproduction steps in commit messages due to impractical test environments.

Thread identity: Subject "[PATCH v2 0/5] loose object handling and size truncation fixes on LLP64 platforms", series version v2 (five-patch series; rework of v1), originating author Elia Pinto, thread type bugfix series.

Core problem or goal: Fix five distinct bugs in loose object handling and size arithmetic, two affecting all platforms (missing size checks in loose object parsing and streaming) and three specific to LLP64 platforms (e.g., 64-bit Windows) where `long` is 32-bit but `size_t` is 64-bit. The bugs include missing bounds checks that could expose uninitialized heap memory or silently truncate objects, truncation/overflow issues in `cat-file --batch`, `notes`, and the loose object reader due to `long` vs. `size_t` mismatches, and a buffer overread in `cat-file --batch` for objects between 2 GiB and 4 GiB caused by `int` truncation of `size_t` lengths. The v1 `diff.c` fix (crash in `count_trailing_blank()` for 2--4 GiB files) has been dropped from this series because it is now handled by a separate series.

Current status: Under review; no maintainer decision yet. Series is rebased onto `master` at e1ec09b23c (previously b9e5cff180 in v1). Issues were reviewed on `git-security` and deemed non-security-sensitive.

Key technical details: Files touched include `object-file.c`/`object-file.h`, `odb/source-loose.c`, `builtin/cat-file.c`, `notes.c`, plus `t/t1006-cat-file.sh`, `t/t1060-object-corruption.sh`, and `t/lib-loose.sh`. Functions modified include `unpack_loose_header()`, `stream_loose_object()`, `batch_write()`, `combine_notes_concatenate()`, `map_fd()`, `unpack_loose_rest()`, `check_stream_oid()`, `odb_source_loose_map_object()`, and `read_istream_loose()`. Patch 1/5 fixes `unpack_loose_rest()` in `object-file.c` by adding a post-inflation validation that checks `status != Z_STREAM_END` or `stream->total_out - hdrlen != size`, reporting the object as corrupt and freeing the buffer if the check fails, mirroring validation already present in `unpack_compressed_entry()` for packfiles; this prevents uninitialized heap memory exposure when compressed data ends early and prevents silent truncation when the stream contains extra data. Patch 1/5 extends `loose_obj()` in `t/lib-loose.sh` to accept an optional third argument overriding the real content size with a bogus header value, and adds three tests to `t/t1060-object-corruption.sh` verifying that reading objects with too-large or too-small header sizes fails with a "corrupt loose object" error and that `git fsck` detects both cases. Patch 2/5 widens the loose-object size variables from `unsigned long` to `size_t` throughout the loose object reading path: it changes the signatures of `map_fd()`, `unpack_loose_header()`, `unpack_loose_rest()`, and `check_stream_oid()` in `object-file.c`/`object-file.h`, plus `odb_source_loose_map_object()` and related locals in `odb/source-loose.c`, so that the entire path from file mapping through header parsing and inflation uses `size_t` consistently. The motivation is that since commit c6a4629e32, `parse_loose_header()` already reports sizes as `size_t`, but downstream functions still took `unsigned long`; on LLP64 platforms such as 64-bit Windows, a header claiming 4 GiB + 5 bytes causes the buffer allocation to truncate to 6 bytes while `*oi->sizep` retains the full 64-bit value, leading callers like `read_loose_object()` to read far past the allocated buffer. Patch 2/5 has no automated test because reproducing the bug requires allocating a buffer near 4 GiB before the short-stream check can trigger; the commit message instead documents a manual reproduction using the `loose_obj()` test helper with a bogus header size. Patch 3/5 fixes the streaming loose object reader `read_istream_loose()` in `odb/source-loose.c` by adding a `total_read` counter and an `oid` field to `struct odb_loose_read_stream`, accumulating bytes handed to the caller, and at `Z_STREAM_END` comparing `st->total_read + total_read` against `st->base.size`; on mismatch it emits a "corrupt loose object" error, transitions the stream state to `ODB_LOOSE_READ_STREAM_ERROR`, and returns -1, mirroring the post-inflation validation of patch 1/5 so that both streaming (`git cat-file blob`) and non-streaming read paths reject objects whose inflated size disagrees with the header. Patch 3/5 includes automated test coverage in `t/t1006-cat-file.sh` using the `loose_obj()` helper to create blobs with bogus header sizes and verifying that `git cat-file blob` fails with the expected error for both too-large and too-small header claims; unlike the LLP64-specific patches (2/5, 4/5, 5/5), this fix is cross-platform and testable in normal CI. Patch 4/5 fixes a cross-platform buffer overread in `git cat-file --batch` by changing the `len` parameter of `batch_write()` in `builtin/cat-file.c` from `int` to `size_t`; callers pass object sizes from `odb_read_object()` or `filter_object()` which are already `size_t`, and when an object falls between 2 GiB and 4 GiB the old `int` parameter wraps negative, causing `fwrite()` and `write_or_die()` to interpret it as an enormous `size_t` and write past the allocated buffer until an unmapped page triggers "write error: Bad address", while objects of 4 GiB or more are silently truncated and desynchronize the `--batch` output stream. The bug triggers with `--batch` on any non-blob object or on blobs processed through `--filters` or `--textconv` since plain blobs are streamed rather than buffered. Patch 4/5 has no automated test because it would require several GiB of memory and disk; the commit message documents a manual reproduction using a 3 GiB zero-filled blob piped through `git cat-file --batch --filters`. Patch 5/5 fixes a heap overflow in `combine_notes_concatenate()` in `notes.c` where concatenating two notes totaling 4 GiB or more caused `buf_len` to be computed in a 32-bit `unsigned long`, truncating the allocation size while `memcpy()` still copied the full 64-bit lengths; the fix changes `buf_len` to `size_t` and computes it with `st_add3()` for overflow safety, then passes it through `cast_size_t_to_ulong()` only at the call to `odb_write_object()`, whose length parameter still requires `unsigned long`, so on affected platforms this now dies cleanly instead of silently writing a truncated blob. The trigger can be as simple as displaying a notes tree containing multiple notes for the same object at different fanout levels, or fetching a notes ref. No automated test is included because reproducing it requires both a 32-bit `long` platform and notes exceeding 4 GiB. On-disk format is unchanged. Only patches 1/5 and 3/5 have automated test coverage; LLP64-specific, multi-gigabyte, and batch-interface scenarios (patches 2/5, 4/5, 5/5) are documented with manual reproduction steps in commit messages due to impractical test environments.

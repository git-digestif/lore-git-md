This thread is about a bugfix for `git log -m --follow` that restores lost history when following renames across merges. Miklos Vajna identified a regression in the diamond-shaped merge scenario (test case `t4219`): when a file is renamed differently in two branches and then merged, the command fails to show the full history of the file because the parent loop in `log_tree_diff()` doesn’t restore the followed path between parents. The fix is a 13-line change to `log-tree.c` that saves and restores the merge’s original path before diffing each parent, ensuring the second parent is compared against the correct pre-rename path. The patch includes a new test case to verify the fix and targets the `git log` command specifically.

The fix is narrowly scoped, well-explained in the commit message, and addresses a real user-facing issue without disrupting existing behavior for single-parent commits. No reviews or objections have appeared yet, so the patch is still under initial consideration. If you use `git log --follow` on merge-heavy histories, this is a small but meaningful improvement to watch.

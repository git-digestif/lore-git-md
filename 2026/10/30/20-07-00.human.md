This is a performance-focused bugfix series targeting the `` `git log --follow` `` command. Miklos Vajna addresses a regression introduced in Git 2.46 (commit 304812ed33, June 2026) that slowed down rename-following in non-linear history, particularly in large repositories like linux.git.

The series is now at v4 and consists of six patches. The first patch expands test coverage for edge cases involving merges. Patches 2 and 3 are preparatory refactorings: patch 2 extracts logic for showing remerge/combined diffs of merge commits, and patch 3 fixes a bug where `` `git log -m --follow` `` loses the history of later parents. Patch 4 simplifies the rename-following logic without changing behavior, while patch 5 restores the performance by avoiding unnecessary rename detection. Patch 6 fixes a case where the speedup inadvertently dropped history when one side of a merge renamed a file and the other side edited the old name.

The interdiff shows that v4 splits the original behavioral fix into a separate patch (3/6), clarifies the commit message for the performance regression, and adds a test for `` `--diff-merges=first-parent` ``. The author reports that with these changes, following renames in linux.git still takes about 37 seconds, which is likely a significant improvement over the regressed state.

The patches touch `log-tree.c` and add tests to `t/t4219-log-follow-merge.sh`. The changes look well-motivated and the commit messages clearly explain the problem, the fix, and the trade-offs. The series appears to be converging after review from Patrick Steinhardt. If the tests pass and the performance claims hold, this is likely to be merged soon.

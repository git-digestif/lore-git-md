This is a **bugfix and ref-filter enhancement** patch series targeting the worktree subsystem. It addresses two related issues: (1) `git worktree remove` currently allows deletion of worktrees in the middle of a rebase, bisect, or other in-progress operation, risking data loss; and (2) `git for-each-ref`'s `%(worktreepath)` atom does not report the worktree path for branches being rebased or bisected, creating a mismatch with how `git worktree add` and `git branch -d` already treat those branches as "checked out."

The series consists of two patches. The first makes `git worktree remove` refuse to delete a worktree that is in the middle of a rebase, `git am`, bisect, cherry-pick, or revert sequence unless `--force` is given. This aligns with Git’s general principle of protecting uncommitted or in-progress work and fixes a pre-existing bug that becomes more likely to trigger once the second patch lands. The second patch extends `%(worktreepath)` in `ref-filter.c` to report the worktree path for branches being rebased or bisected, closing the gap Kristoffer Haugsbakk identified and eliminating the need for a new CLI option. The change is backward-incompatible for scripts that rely on `%(worktreepath)` being empty for rebasing/bisecting branches.

The implementation is clean and well-tested. The first patch adds a new helper function `worktree_is_in_progress()` that checks for rebase, bisect, cherry-pick, revert, and `git am` state, and updates `builtin/worktree.c` to refuse deletion unless `--force` is given. The second patch modifies `ref-filter.c` to include rebasing/bisecting branches in the `%(worktreepath)` atom, matching the logic already used in `branch.c`’s `prepare_checked_out_branches()`. Tests cover edge cases: rebasing/bisecting branches, unborn branches, and the interaction between `git worktree remove` and in-progress operations. The documentation is updated to reflect the new behavior, including a note about the dual `*` and `+` markers in `git branch` output for the current worktree during a rebase.

The series directly addresses the design tensions identified in the RFC discussion. It sidesteps the ordering invariant concern (main worktree appearing first) by not introducing a filtering mechanism that would break it, and it mitigates the safety risks Phillip Wood and Ben Knoble raised by making `git worktree remove` refuse deletion of in-progress worktrees. The choice to extend `%(worktreepath)` rather than add a new CLI option avoids the extensibility and naming questions Junio and Eric Sunshine raised, though it leaves open the broader limitations of `for-each-ref` as a filtering mechanism (NUL-terminated output, main/linked worktree distinction, multiple worktrees per branch). The series does not attempt to solve those limitations, but it does make the behavior more consistent and safer.

Key technical details: the series touches `builtin/worktree.c`, `ref-filter.c`, `Documentation/git-branch.adoc`, `Documentation/git-for-each-ref.adoc`, `Documentation/git-worktree.adoc`, and adds tests to `t/t2403-worktree-move.sh`, `t/t3203-branch-output.sh`, and `t/t6302-for-each-ref-filter.sh`. The new behavior is backward-incompatible for scripts relying on the current empty `%(worktreepath)` value, but the commit message explicitly asks whether any such scripts exist. The series is ready for review and looks like a well-crafted fix for a real problem.

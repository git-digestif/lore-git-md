This is the second patch in Elia Pinto’s six-patch **bugfix series** addressing loose object handling and size truncation issues, with a focus on LLP64 platforms (e.g., 64-bit Windows). The patch aligns the loose object reading path on the use of `size_t` for object sizes, fixing a truncation bug where objects larger than 4 GiB could cause buffer overflows or memory corruption due to `unsigned long` being 32-bit on Windows.

The core issue stems from a type mismatch: since `parse_loose_header()` now reports object sizes as `size_t` (per an earlier commit), but `unpack_loose_rest()` and related functions still use `unsigned long`, a 4 GiB + 5-byte object would cause `unpack_loose_rest()` to allocate a 6-byte buffer while `oi->sizep` retains the full 4 GiB + 5 value. This leads to out-of-bounds reads when callers (e.g., `read_loose_object()`) hash or process the object contents. The fix propagates `size_t` through the entire loose object reading path, including `map_fd()`, `unpack_loose_header()`, `check_stream_oid()`, and `odb_source_loose_map_object()`.

The patch touches three files (`object-file.c`, `object-file.h`, and `odb/source-loose.c`) and modifies function signatures and variable types without changing behavior on platforms where `long` and `size_t` are the same size. No new symbols are introduced, and the on-disk format remains unchanged. While the patch lacks automated test coverage (due to the impracticality of allocating 4 GiB in tests), the commit message provides a manual reproduction recipe using a helper from the previous patch. The fix is well-motivated and addresses a latent bug that could cause crashes or memory corruption in large repositories on Windows. The series as a whole remains under review, with no substantive feedback yet.

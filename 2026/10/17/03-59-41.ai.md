This is a **bugfix review** targeting the test suite in the `git repo structure` revision-filtering patch. Junio C Hamano identifies a **SHA-256 compatibility issue** in the new test added by Mark C. Chu-Carroll: the test hardcodes 40-character SHA-1 object IDs (e.g., `97d808e45116bf02103490294d3d46dad7a2ac62`) and will fail when Git defaults to SHA-256 in version 3.0. The review is **substantive**—it engages with the test’s correctness under future Git versions and references prior work on hash-agnostic testing.

The issue affects the `test_expect_success 'filter by object type'` test, which validates the command’s ability to filter objects by type (blobs, trees, commits) and size. Junio notes that the test’s hardcoded OIDs are specific to SHA-1 and will break in SHA-256 environments, a problem already present in other tests in the same file (e.g., `test_expect_success SHA1 'lines and nul format'`). He suggests two remedies: (1) **short-term**: guard the test with a `SHA1` prerequisite to hide the breakage (matching the existing pattern in the file), or (2) **long-term**: rewrite the test to be hash-agnostic, citing a recent example (`pull.2252.v4`) as inspiration.

The review does not block the patch—Junio explicitly leaves the choice of fix to the author—but it raises a **forward-compatibility concern** that will need addressing before Git 3.0. The patch is otherwise ready for merging (as confirmed by Patrick Steinhardt’s sign-off), but this test issue risks leaving the test suite in a broken state when SHA-256 becomes the default. The author’s response will determine whether the fix is a simple prerequisite addition or a more involved hash-agnostic rewrite.

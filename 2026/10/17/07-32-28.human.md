This is the first patch in Jun Wu’s **v2 series introducing a configurable index lock timeout** for Git. It is a **refactoring patch** that prepares the codebase for the timeout feature by splitting `repo_hold_locked_index()` into two functions: one for mandatory locks and one for optional locks.

The patch introduces `repo_try_hold_locked_index()`, a new function that clarifies when a command is willing to proceed without the index lock. Currently, it behaves identically to `repo_hold_locked_index()`, but the next patch will modify the latter to support waiting for the lock. The change migrates eight call sites (in `commit.c`, `describe.c`, `diff.c`, `merge.c`, `rebase.c`, `sequencer.c`, and `wt-status.c`) from `repo_hold_locked_index()` to `repo_try_hold_locked_index()`, all of which use `repo_update_index_if_able()` — a clear signal that the lock is optional.

The motivation is purely preparatory: separating the two use cases makes the timeout logic in the next patch easier to reason about and review. The patch is small (24 lines added, 8 changed), touches only internal API calls, and does not change behavior. No new tests are needed because the functionality remains unchanged.

This is a **clean, well-motivated refactoring** that directly supports the series’ goal. It is uncontroversial and unlikely to draw objections. The only open question is whether the series as a whole — and its phased approach to fixing lock-order races — will gain consensus, but that debate belongs to later patches. For now, this patch is a straightforward and necessary step.

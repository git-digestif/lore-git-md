This is a bugfix patch for the pretty-printing subsystem, specifically the `%w()` format specifier in `git log` and related commands. It is the second iteration (`v2`) of a standalone patch that addresses a regression where indentation was lost after a newline followed by whitespace in wrapped output.

The patch now includes the previously missing documentation update for the `%w()` placeholder in `Documentation/pretty-formats.adoc`. The new documentation clarifies the behavior of line wrapping and indentation, removing the outdated reference to `git shortlog -w` and explicitly stating how newlines are handled (replaced by spaces when followed by alphanumeric characters, but preserving existing indentation). The fix itself remains unchanged from `v1`: it surgically adjusts the logic in `utf8.c` to distinguish between "line too long" (where skipping a space is correct) and "hard line break" (where skipping is wrong), ensuring indentation is preserved after newlines.

Test coverage is expanded with a new regression test in `t/t4202-log.sh` and an updated test in `t/t4205-log-pretty-formats.sh` to reflect the corrected behavior. The latter change accounts for the fact that `%+d` (which emits a newline followed by decoration text) no longer loses its leading space, causing an extra line break when combined with a narrow wrap width.

The patch is under active review with maintainer endorsement. Junio C Hamano and René Scharfe have both signaled support for the fix, provided the documentation gap is addressed—which this version now does. The change is low-risk, well-motivated, and addresses a real-world formatting issue that affects commit message wrapping, file lists, and other indented output. The updated documentation should prevent future regressions by making the behavior explicit. No further technical concerns are evident, and the patch appears ready to proceed.

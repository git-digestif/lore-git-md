This is the second patch in Beat Bolli’s three-patch v3 series for `git imap-send`, replacing Git’s manual TLS hostname verification with OpenSSL’s built-in `SSL_set1_host()` API. The patch aims to achieve full RFC 6125 compliance (including support for IP-type SANs) and reduce maintenance burden by relying on OpenSSL’s native implementation. It touches only `imap-send.c` and removes roughly 70 lines of custom verification logic in favor of OpenSSL’s `SSL_set1_host()` and `SSL_set_hostflags()`.

The patch is well-motivated: OpenSSL’s built-in verification is more robust and future-proof than Git’s hand-rolled logic, which missed edge cases like IP addresses in SANs. The commit message clearly explains the rationale and cites OpenSSL’s documentation. However, the patch introduces **two critical regressions** that remain unresolved:

1. **Security regression**: The removal of the `SSL_get_peer_certificate()` check creates a trivial MITM vector by allowing certificate stripping. This is a serious flaw that undermines the patch’s security goals.
2. **Error reporting regression**: Under `SSL_VERIFY_PEER`, `SSL_connect()` fails early on any verification error (including hostname mismatches), making the `SSL_get_verify_result()` check unreachable and losing the hostname-specific error message that the old code provided.

The patch sets `X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS` to match Git’s prior behavior (rejecting partial wildcard matches like `*.example.com` for `foo.bar.example.com`), but this detail may still draw scrutiny. The diff is mechanically clean but visually noisy due to the wholesale replacement of two functions with a new `verify_peer()` helper.

This patch is part of a broader effort to modernize `git imap-send`’s OpenSSL usage, but it remains blocked on the security regression. The v3 series introduced a new patch (3/3) to address the error reporting regression via a custom verification callback, but that does not resolve the certificate stripping issue. If you care about `imap-send`’s security or OpenSSL compatibility, this patch warrants close attention—it’s a step forward in some ways but a step back in others. The unresolved security flaw is a showstopper.

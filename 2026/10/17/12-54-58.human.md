This is the first patch in a five-part bugfix series for `git worktree repair`. It refactors how `.git` files are read in `repair_worktree_at_path()` to align with the stricter parsing rules already used in `repair_gitfile()`. The key change replaces `read_gitfile_gently()` with `read_gitfile_raw()`, moving path resolution and repository validation to the caller.

The patch makes three concrete behavior changes to `.git` file handling: it now rejects `.git` files with `gitdir:` prefixes missing a trailing space (e.g., `gitdir:foo/bar`), treats trailing whitespace as part of the path (e.g., `gitdir: foo/bar/   ` resolves to `worktrees/   `), and explicitly handles both absolute and relative paths in `.git` files. These changes are motivated by consistency with `repair_gitfile()` and lay the groundwork for the validation logic introduced later in the series.

The refactoring is mechanical and well-contained, touching only `worktree.c`. It eliminates a memory leak (replacing `xstrdup_or_null` with `strbuf`) and makes the code more reentrant by avoiding `read_gitfile_gently()`. The commit message clearly explains the motivation and the specific behavior changes, though it does not address whether the stricter parsing might break manually edited `.git` files in the wild.

This patch is part of a larger effort to prevent `git worktree repair` from incorrectly modifying unrelated worktrees. The series has been through two previous iterations, with Junio C Hamano’s review concerns already addressed in the v3 update. The refactoring here is a prerequisite for the validation logic in patch 5/5, which will add the actual safety checks. The patch looks solid and uncontroversial, but its real value will become clear when the validation logic lands.

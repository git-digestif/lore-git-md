This is a **bugfix** targeting the `upload-pack` subsystem, specifically addressing a performance regression in Git protocol v2 when fetching from shallow repositories with long histories.

The patch fixes a severe slowdown (minutes instead of seconds) when fetching from a shallow repository over protocol v2. The issue stems from the server redundantly traversing the same commits multiple times to determine which shallow commits to advertise. The fix aligns protocol v2 behavior with protocol v0: when the client doesn’t request a specific depth, the server simply lists all shallow commits instead of walking the history. This also ensures `git clone --reject-shallow` works consistently across both protocols.

The change is minimal (4 lines modified across two files) and focused on the shallow commit handling logic in `shallow.c` and `upload-pack.c`. The commit message provides clear motivation with a real-world example (homebrew-core’s 900k-commit history) and explains the trade-off: while `git fetch --unshallow` still requires history traversal, the patch optimizes the common case by visiting each commit only once.

This looks like a well-scoped fix for a real pain point, with a straightforward technical rationale. The patch is marked as RFC, suggesting the author is seeking feedback on the approach, but the problem and solution are clearly articulated. Worth attention from anyone working with shallow repositories or protocol v2.

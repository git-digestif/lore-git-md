This is a **feature patch series (v2)** that introduces a configurable timeout (`core.indexLockTimeout`) for Git’s index lock, addressing lock contention between background `git status` calls (common in IDEs) and user-initiated commands like `git add` or `git commit`. The series now spans **4 patches**, up from 2 in v1, and expands the scope to fix pre-existing write-race conditions in both `git commit` and `git reset`.

### What’s new in v2
The series now **explicitly documents and enforces** the non-waiting behavior of `git status` (Patch 1) and **fixes write races** in `git reset` (Patch 4) alongside the earlier `git commit` fix (Patch 3). The lock-timeout mechanism (Patch 2) remains unchanged but is now better contextualized: commands that read the index *before* locking (e.g., `rebase`, `merge`) still skip the timeout to avoid amplifying race windows, while commands that lock *before* reading (e.g., `commit`, `reset`, `add`) now wait up to the configured timeout (default: 1 second). The commit messages for the race fixes now use "write race" as the primary motivation, addressing Jeff King’s feedback that the lock-order changes should be framed as correctness fixes.

### Key technical details
- **Files touched**: Core logic in `repository.c` (timeout implementation), `builtin/commit.c` and `builtin/reset.c` (lock-order fixes), plus documentation and tests. The series also touches `wt-status.c`, `sequencer.c`, and other built-ins to ensure consistent lock acquisition.
- **New config key**: `core.indexLockTimeout` (milliseconds; 0 = no wait, -1 = indefinite, default = 1000).
- **Behavior**: Commands wait for the lock unless the index was already read *by the same process* (to avoid write races). The lock infrastructure now **force-drops stale in-memory indexes** after acquisition, resolving Junio’s edge-case concerns about outdated data.
- **Commands supporting timeout**: `add`, `rm`, `mv`, `checkout`, `restore`, `read-tree`, `apply`, `update-index`, `commit`, `reset`.
- **Commands *not* supporting timeout**: `rebase`, `merge`, `stash`, `cherry-pick`, `am` (these read the index before locking and thus skip the timeout).
- **Test coverage**: New test script `t/t0032-index-lock-timeout.sh` verifies timeout behavior, and existing lockfile/submodule tests are updated for compatibility.

### Open questions and context
- **Default timeout (1s)**: Still open to debate; Jun Wu cites Mercurial’s 10-minute default but remains open to adjustment.
- **Phased approach**: The series lands the timeout feature first (Patch 2) and fixes lock-order issues incrementally (Patches 3–4). Whether to expand this to other commands (e.g., `rebase`) or wait for a full audit remains unresolved.
- **Alternatives**: D. Ben Knoble’s preference for root-cause fixes (e.g., faster `git status`, IDE coordination) is noted but not adopted here. The series prioritizes pragmatism, citing real-world performance issues in Sapling (Facebook’s Git fork).

### Assessment
The v2 series is **well-structured and addresses prior feedback** (clarity, race fixes, commit-message framing). The expanded scope (adding `reset`) and explicit handling of `git status` improve consistency. The default timeout may still spark discussion, but the implementation is conservative (skipping the timeout for racy commands) and includes safeguards against stale data. Test coverage is adequate, and the patches are narrowly targeted to avoid regressions. **Worth attention** for users frustrated by lock contention in IDE workflows.

This email from Luca Milanesio provides **production-scale validation of JGit's pluggable backend architecture**, directly addressing concerns raised in the Git Contributors' Summit 2026 about JGit's readiness for Git 3.0's object database (ODB) interoperability goals. Milanesio cites two concrete examples of JGit's pluggable backend in real-world use:

1. **Google's internal Git servers**, including `gerrit.googlesource.com`, which have used a proprietary JGit backend built on the same open-source pluggable interfaces for over a decade. This demonstrates the architecture's maturity, scalability, and long-term viability in high-demand environments.
2. **GerritForge's open-source global refdb backend**, donated to the Android Open Source Project (AOSP) and available on GitHub ([GerritCodeReview/modules_global-refdb](https://github.com/GerritCodeReview/modules_global-refdb)). This backend powers multi-site Gerrit deployments with globally consistent ref updates, serving as a reference implementation for distributed ref storage.

Milanesio also references **Daniele Sassoli's earlier clarification** about JGit's historical support for pluggable backends (dating back 16 years) and **a forthcoming talk at the Gerrit User Summit** ("SHA-256 in JGit: Why, What, and When") by Xing Huang (Google), signaling ongoing corporate interest in advancing JGit's SHA-256 support. The email shifts the narrative from "JGit is a gap" to **"JGit is production-ready but underutilized"**, removing technical barriers to Git 3.0's ODB goals while highlighting resource constraints—not technical limitations—as the primary obstacle for SHA-256 interoperability.

The message is **not a patch or technical proposal** but a factual correction to the summit recap, providing actionable context for future coordination between Git and JGit. It invites Git community members to attend the Gerrit User Summit (October 24–25, 2026) to engage directly with JGit maintainers, though no specific technical follow-up is proposed. The tone is collaborative and solution-oriented, emphasizing JGit's adaptability to Git 3.0's ODB abstraction efforts. Key implications for Git 3.0 planning include:
- **Pluggable ODBs**: JGit's infrastructure is validated as production-ready, though Git's implementation may still face unresolved tradeoffs (e.g., content-defined chunking).
- **SHA-256 interoperability**: Corporate interest exists (Google), but resource constraints remain the bottleneck. Milanesio's examples suggest JGit could support SHA-256 if prioritized.
- **Downstream coordination**: The email underscores the need for proactive engagement with JGit maintainers to align on ODB and SHA-256 goals, particularly given the summit's earlier characterization of JGit as a "gap."

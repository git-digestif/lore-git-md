This is the **fourth and final patch** in Jun Wu’s v2 series introducing a configurable index lock timeout (`core.indexLockTimeout`). This patch fixes a **pre-existing write-race condition** in `git reset` (except `--soft`) by reordering the lock acquisition to follow the "lock → read → write" pattern, matching the earlier fix for `git commit` in Patch 3. The change enables `git reset` to benefit from the new timeout behavior while eliminating a 20-year-old race window where concurrent index updates (e.g., from `git add`) could be silently discarded.

The patch touches only `builtin/reset.c`, moving the `repo_hold_locked_index()` call to the start of the command (before `repo_read_index()`) and removing the redundant lock acquisition later in the function. The commit message explicitly frames the change as a **correctness fix**, addressing Jeff King’s feedback that lock-order adjustments should be motivated by race elimination rather than just timeout support. Unlike `git commit`, `git reset` uses `repo_read_index()` instead of `repo_read_index_preload()`, so the change does not introduce additional work (e.g., `lstat()` calls) while holding the lock. The author omits a new test in `t0032-index-lock-timeout.sh` due to the existing coverage and the straightforward nature of the fix.

This patch completes the series’ phased approach: the timeout feature (Patch 2) is now usable by `git reset`, and the pre-existing race is resolved. The series remains under review, with no merge status reported. The default timeout value (1 second) and whether to extend the lock-order fixes to other commands (e.g., `rebase`) remain open questions. The implementation is conservative, skipping the timeout for commands that read the index before locking to avoid amplifying race windows.

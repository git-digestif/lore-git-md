Thread identity
Subject: [RFC] git branch --delete-merged: handle branches with gone upstreams
Series version: RFC (no patch version)
Originating author: DonQuinleone (first-time contributor)
Thread type: RFC / design discussion

Core problem or goal
Allow `git branch --delete-merged` to delete local branches whose upstream has been deleted by the hosting service (e.g., GitHub after merging a PR), provided the branch tip is reachable from a user-specified or implicit ref (e.g., `origin/master` or `HEAD`). The current command refuses to delete such branches because the upstream is gone, forcing users to manually identify and delete them. The discussion has expanded to consider whether squash-merged branches (common in GitHub PR workflows) should also be supported, as these also result in deleted upstreams but may not be reachable from the target branch due to the squash commit.

Current status
No implementation exists; this remains a design discussion. Seven interface shapes are under debate, with DonQuinleone now favoring (G) (a hybrid of composable filters and explicit merge-checking) as a middle ground. The thread has reopened the question of whether squash/rebased merges should be included in scope, with Harald Nordgren arguing they are integral to triangular workflows (e.g., GitHub PRs) and should be supported regardless of merge strategy. DonQuinleone’s proposal (G) explicitly excludes squash merges, while Nordgren’s position implies they should be included, potentially requiring additional logic to verify squash-merge reachability.

Key technical details
- Files touched: `builtin/branch.c` (branch deletion and filtering logic).
- New behavior: For gone-upstream branches, pass a user-specified commit (e.g., `origin/master`) to `check_branch_commit()` instead of `HEAD`. Under (G), this logic would be implemented in the `-d` code path, avoiding the pipe boundary issue in (F). If squash merges are included, additional logic may be needed to verify that the branch tip is reachable from the target branch via a squash commit (e.g., by checking commit messages or other heuristics).
- On-disk format: No changes.
- Test coverage: Not yet addressed; the included script demonstrates the issue (a provably merged branch is skipped by `--delete-merged` after fetching and pruning). Don suggests starting with tests for `--upstream-gone` as a listing filter. If squash merges are supported, tests would need to cover squash-merge scenarios.

Open questions and loose ends
- **Design direction**: (A) vs. (B) vs. (C) vs. (D) vs. (E) vs. (F) vs. (G); whether to adopt a hybrid approach (G) that combines composability with explicit merge-checking, or stick to implicit behavior (D) or unified filtering (F). The "selection is not proof" limitation of (F) remains a key technical hurdle.
- **Scope expansion**: Whether to include squash-merged branches in the feature’s scope. DonQuinleone’s proposal (G) explicitly excludes them, while Nordgren argues they are part of triangular workflows and should be supported. This could require additional logic to verify squash-merge reachability (e.g., commit message parsing or other heuristics).
- **Unified filtering model**: Whether to deprecate `--delete-merged` in favor of `--list` + `xargs`, and how to handle dry-run functionality (currently `--delete-merged --dry-run`). Knoble’s proposal (F) does not address these details, while (G) sidesteps them by keeping the logic in `-d`.
- **Safeguards**: Whether to preserve existing exclusions (worktrees, stacked branches) or relax them for gone-upstream branches; whether the feature should require explicit opt-in (e.g., `--merged`) or be enabled by default (Nordgren’s position). Don’s proposal (G) preserves safeguards by requiring explicit `--merged`.
- **Edge cases**: Handling of branches with no upstream set, or upstreams that are gone but not due to a merge (e.g., force-pushed); interaction with triangular workflows (e.g., GitHub’s push-to-topic, merge-to-main). Don’s proposal (G) narrows the selection with `--upstream-gone` to avoid false positives. If squash merges are included, additional edge cases may arise (e.g., squash commits with non-standard messages).
- **Implementation path**: Don suggests a two-patch series (first adding `--upstream-gone` as a listing filter, then extending it to support deletion), which could build consensus incrementally. If squash merges are included, the implementation may require additional patches to handle squash-merge reachability.
- **Workflow ergonomics**: How the feature interacts with settings like `push.default=current` and `branch.autosetupmerge=inherit`. Knoble notes these broader changes would require a major release (e.g., Git 4.0) due to past controversy, while Nordgren advocates for them as usability improvements for Git 3.0. The relevance to the RFC’s scope remains unresolved.

Participant positions
- DonQuinleone (author): Proposes (G) (hybrid of composable filters and explicit merge-checking) as a middle ground, addressing the "selection is not proof" limitation of (F). Explicitly excludes squash/rebased merges from scope but acknowledges Nordgren’s argument for including them. Suggests a two-patch series to build consensus incrementally. No position on workflow defaults.
- D. Ben Knoble: Initially advocated for (F) (unified filtering model) as the most composable and extensible solution, but has not yet responded to Don’s critique of the "selection is not proof" limitation. Argues that composable syntax avoids context-sensitive flags (e.g., `--into` only working with `--delete-merged`), citing Git’s `git-rebase` man page ("INCOMPATIBLE OPTIONS") as evidence. Raises broader workflow concerns (triangular workflows, `push.default=current`) but notes these are orthogonal to the RFC and would require a major release to address.
- Harald Nordgren: Advocates for (D) (implicit behavior for gone-upstream branches if their tip is reachable from `HEAD` or another implicit ref), rejecting explicit flags or composable syntax as unconventional. Argues that squash-merged branches should be included in scope, as they are part of triangular workflows (e.g., GitHub PRs). Advocates for `push.default=current` and `branch.autosetupmerge=inherit` as usability improvements for Git 3.0, framing them as better defaults for triangular workflows.

Thread identity
Subject: [RFC] git branch --delete-merged: handle branches with gone upstreams
Series version: RFC (no patch version)
Originating author: DonQuinleone (first-time contributor)
Thread type: RFC / design discussion

Core problem or goal
Allow `git branch --delete-merged` to delete local branches whose upstream has been deleted by the hosting service (e.g., GitHub after merging a PR), provided the branch tip is reachable from a user-specified or implicit ref (e.g., `origin/master` or `HEAD`). The current command refuses to delete such branches because the upstream is gone, forcing users to manually identify and delete them.

Current status
No implementation exists; this remains a design discussion. Seven interface shapes are now under debate:
- (A) A modifier like `--into origin/master` to `--delete-merged` (author’s original proposal).
- (B) Composable filters like `--upstream-gone --merged=origin/master` to `-d`, enabling standalone listing of gone-upstream branches.
- (C) A composable syntax using `--option=value,value,value` (e.g., `--delete-merged='origin/*,into:origin/master'`), suggested by D. Ben Knoble.
- (D) No new flag: relax the existing `--delete-merged` behavior to automatically treat gone-upstream branches as merged if their tip is reachable from `HEAD` (or another implicit ref like `origin/master`). Advocated by Harald Nordgren.
- (E) Repeatable options (Knoble’s refinement of C): `--into=ref1 --into=ref2`.
- (F) A unified filtering model: teach `--list` to filter branches by merge status (e.g., `--merged-upstream=<commit>`) and encourage users to pipe the output to `xargs git branch -d`. Proposed by Knoble as a broader architectural change.
- (G) Hybrid of (B) and (F): teach `git branch -d` to accept `--upstream-gone` and `--merged=<commit>` as composable filters, where `--merged` serves as both the selection criterion and the proof of merge. This is Don’s latest proposal, addressing the "selection is not proof" limitation of (F) by preserving merge-checking logic within the deletion command.

The author now prefers (G) as a middle ground between composability and explicit opt-in, while Knoble initially advocated for (F) and Nordgren continues to advocate for (D). The debate centers on **interface philosophy** (composability vs. CLI purity vs. hybrid approaches) and **technical feasibility** (whether composable filtering can preserve merge-checking logic). The thread still explicitly excludes squash/rebased merges from scope. A tangential discussion about Git’s defaults for triangular workflows (e.g., `push.default=current`, `branch.autosetupmerge=inherit`) remains unresolved but is acknowledged as orthogonal to the RFC’s core scope.

Key technical details
- Files touched: `builtin/branch.c` (branch deletion and filtering logic).
- New behavior: For gone-upstream branches, pass a user-specified commit (e.g., `origin/master`) to `check_branch_commit()` instead of `HEAD`. Under (G), this logic would be implemented in the `-d` code path, avoiding the pipe boundary issue in (F).
- On-disk format: No changes.
- Test coverage: Not yet addressed; the included script demonstrates the issue (a provably merged branch is skipped by `--delete-merged` after fetching and pruning). Don suggests starting with tests for `--upstream-gone` as a listing filter.

Open questions and loose ends
- **Design direction**: (A) vs. (B) vs. (C) vs. (D) vs. (E) vs. (F) vs. (G); whether to adopt a hybrid approach (G) that combines composability with explicit merge-checking, or stick to implicit behavior (D) or unified filtering (F). The "selection is not proof" limitation of (F) is now a key technical hurdle.
- **Unified filtering model**: Whether to deprecate `--delete-merged` in favor of `--list` + `xargs`, and how to handle dry-run functionality (currently `--delete-merged --dry-run`). Knoble’s proposal (F) does not address these details, while (G) sidesteps them by keeping the logic in `-d`.
- **Safeguards**: Whether to preserve existing exclusions (worktrees, stacked branches) or relax them for gone-upstream branches; whether the feature should require explicit opt-in (e.g., `--merged`) or be enabled by default (Nordgren’s position). Don’s proposal (G) preserves safeguards by requiring explicit `--merged`.
- **Edge cases**: Handling of branches with no upstream set, or upstreams that are gone but not due to a merge (e.g., force-pushed); interaction with triangular workflows (e.g., GitHub’s push-to-topic, merge-to-main). Don’s proposal (G) narrows the selection with `--upstream-gone` to avoid false positives.
- **Implementation path**: Don suggests a two-patch series (first adding `--upstream-gone` as a listing filter, then extending it to support deletion), which could build consensus incrementally.
- **Workflow ergonomics**: How the feature interacts with settings like `push.default=current` and `branch.autosetupmerge=inherit`. Knoble notes these broader changes would require a major release (e.g., Git 4.0) due to past controversy, while Nordgren advocates for them as usability improvements for Git 3.0. The relevance to the RFC’s scope remains unresolved.

Participant positions
- DonQuinleone (author): Now proposes (G) (hybrid of composable filters and explicit merge-checking) as a middle ground, addressing the "selection is not proof" limitation of (F). Explicitly excludes squash/rebased merges. Suggests a two-patch series to build consensus incrementally. No position on workflow defaults.
- D. Ben Knoble: Initially advocated for (F) (unified filtering model) as the most composable and extensible solution, but has not yet responded to Don’s critique of the "selection is not proof" limitation. Argues that composable syntax avoids context-sensitive flags (e.g., `--into` only working with `--delete-merged`), citing Git’s `git-rebase` man page ("INCOMPATIBLE OPTIONS") as evidence. Raises broader workflow concerns (triangular workflows, `push.default=current`) but notes these are orthogonal to the RFC and would require a major release to address.
- Harald Nordgren: Continues to advocate for (D) (implicit behavior for gone-upstream branches if their tip is reachable from `HEAD` or another implicit ref), rejecting explicit flags or composable syntax as unconventional. Advocates for `push.default=current` and `branch.autosetupmerge=inherit` as usability improvements for Git 3.0, framing them as better defaults for triangular workflows.

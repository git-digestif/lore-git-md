Thread identity
Subject: [RFC] git branch --delete-merged: handle branches with gone upstreams
Series version: RFC (no patch version)
Originating author: DonQuinleone (first-time contributor)
Thread type: RFC / design discussion

Core problem or goal
Allow `git branch --delete-merged` to delete local branches whose upstream has been deleted by the hosting service (e.g., GitHub after merging a PR), provided the branch tip is reachable from a user-specified or implicit ref (e.g., `origin/master` or `HEAD`). The current command refuses to delete such branches because the upstream is gone, forcing users to manually identify and delete them.

Current status
No implementation exists; this remains a design discussion. Six interface shapes are under active debate:
- (A) A modifier like `--into origin/master` to `--delete-merged`, which deletes branches only if their tip is reachable from the named ref (author’s original proposal).
- (B) Composable filters like `--upstream-gone --merged=origin/master` to `-d`, enabling standalone listing of gone-upstream branches.
- (C) A composable syntax using `--option=value,value,value` (e.g., `--delete-merged='origin/*,into:origin/master'`), suggested by D. Ben Knoble to avoid new flags and allow future extensions.
- (D) No new flag: relax the existing `--delete-merged` behavior to automatically treat gone-upstream branches as merged if their tip is reachable from `HEAD` (or another implicit ref like `origin/master`). Advocated by Harald Nordgren.
- (E) Repeatable options (Knoble’s refinement of C): `--into=ref1 --into=ref2` as a middle ground between explicit flags and composable syntax.
- (F) A unified filtering model: teach `--list` to filter branches by merge status (e.g., `--merged-upstream=<commit>`) and encourage users to pipe the output to `xargs git branch -d`. Proposed by Knoble in the latest email as a broader architectural change, eliminating the need for a separate `--into` flag or `--delete-merged` subcommand. This would allow the feature to be expressed as `git branch --list --merged-upstream=origin/main | xargs git branch -d`.

The author prefers (A) for simplicity and alignment with existing safeguards; Knoble now advocates for (F) as the most composable and extensible solution, refining his earlier preference for (C) or (E). Nordgren continues to advocate for (D), rejecting explicit flags or composable syntax entirely. The thread still explicitly excludes squash/rebased merges from scope, preserving the current strictness of `--delete-merged` for non-gone-upstream branches. The debate now centers on **interface philosophy**: Knoble argues for composability and a unified filtering model to avoid context-sensitive flags (e.g., `--into` only working with `--delete-merged`), citing Git’s `git-rebase` man page ("INCOMPATIBLE OPTIONS") as evidence, while Nordgren views composability as a violation of Git’s CLI conventions and prefers implicit behavior. A tangential discussion about Git’s defaults for triangular workflows (e.g., `push.default=current`, `branch.autosetupmerge=inherit`) remains unresolved, with Knoble noting these changes would require a major release (e.g., Git 4.0) due to past controversy.

Key technical details
- Files touched: `builtin/branch.c` (branch deletion and filtering logic).
- New behavior: For gone-upstream branches, pass a user-specified or implicit commit (e.g., `origin/master` or `HEAD`) to `check_branch_commit()` instead of `HEAD`. Under Knoble’s unified filtering model (F), this logic would move to the `--list` filtering code path.
- On-disk format: No changes.
- Test coverage: Not yet addressed; the included script demonstrates the issue (a provably merged branch is skipped by `--delete-merged` after fetching and pruning).

Open questions and loose ends
- Design direction: (A) vs. (B) vs. (C) vs. (D) vs. (E) vs. (F); whether to relax `--delete-merged`’s behavior by default for gone-upstream branches (Nordgren’s proposal), require explicit opt-in (author’s preference), or adopt a unified filtering model (Knoble’s proposal). The debate now hinges on **interface philosophy** (composability vs. CLI purity), with Knoble framing composability as a way to avoid context-sensitive flags and Nordgren rejecting it as unconventional.
- Unified filtering model: Whether to deprecate `--delete-merged` in favor of `--list` + `xargs`, and how to handle dry-run functionality (currently `--delete-merged --dry-run`). Knoble’s proposal does not address these details.
- Safeguards: Whether to preserve existing exclusions (worktrees, stacked branches) or relax them for gone-upstream branches; whether the feature should require explicit opt-in (e.g., `--into`) or be enabled by default (Nordgren’s position).
- User experience: Whether the interface should be composable (Knoble’s preference), monolithic (Nordgren’s preference), or a middle ground (repeatable options); how to balance discoverability with extensibility. The unresolved tension between explicit flags, implicit behavior, and composable syntax remains central.
- Edge cases: Handling of branches with no upstream set, or upstreams that are gone but not due to a merge (e.g., force-pushed); interaction with triangular workflows (e.g., GitHub’s push-to-topic, merge-to-main).
- Workflow ergonomics: How the feature interacts with settings like `push.default=current`, `branch.autosetupmerge=inherit`, and `status.comparebranches=@{upstream} @{push}`; whether these should be defaults to reduce friction in triangular workflows (raised by Knoble). Knoble has clarified that these broader changes would require a major release (e.g., Git 4.0) due to past controversy, and their relevance to the RFC’s scope remains unresolved.
- Defaults: Whether the RFC’s feature should be opt-in (requiring `--into` or a unified filtering model), opt-out (enabled by default for gone-upstream branches, with a flag to disable), or fully implicit (Nordgren’s proposal).

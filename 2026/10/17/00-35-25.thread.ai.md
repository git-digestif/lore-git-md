Thread identity
Subject: [RFC] git branch --delete-merged: handle branches with gone upstreams
Series version: RFC (no patch version)
Originating author: DonQuinleone (first-time contributor)
Thread type: RFC / design discussion

Core problem or goal
Allow `git branch --delete-merged` to delete local branches whose upstream has been deleted by the hosting service (e.g., GitHub after merging a PR), provided the branch tip is reachable from a user-specified or implicit ref (e.g., `origin/master` or `HEAD`). The discussion has expanded to consider whether squash-merged branches (common in GitHub PR workflows) should also be supported, as these also result in deleted upstreams but may not be reachable from the target branch due to the squash commit.

Current status
No implementation exists; this remains a design discussion. Seven interface shapes (A-G) have been debated, with DonQuinleone now favoring (G) (a hybrid of composable filters and explicit merge-checking) as a middle ground. The thread continues to weigh composability (Knoble’s preference) against explicit merge-checking (Don’s hybrid) and implicit behavior (Nordgren’s position). Knoble’s latest reply suggests workarounds for the "selection is not proof" limitation of the composable model (e.g., `--format='%(refname:lstrip=2)'` for machine-readable output, manual dry-run verification), but these are not yet integrated into the design. The question of whether to include squash-merged branches remains unresolved, with Nordgren advocating for their inclusion and Don’s proposal (G) explicitly excluding them.

Key technical details
- Files touched: `builtin/branch.c` (branch deletion and filtering logic).
- New behavior: For gone-upstream branches, pass a user-specified commit (e.g., `origin/master`) to `check_branch_commit()` instead of `HEAD`. Under (G), this logic would be implemented in the `-d` code path, avoiding the pipe boundary issue in (F). If squash merges are included, additional logic may be needed to verify reachability via squash commits (e.g., commit message parsing or heuristics).
- On-disk format: No changes.
- Test coverage: Not yet addressed; the included script demonstrates the issue (a provably merged branch is skipped by `--delete-merged` after fetching and pruning). Don suggests starting with tests for `--upstream-gone` as a listing filter. If squash merges are supported, tests would need to cover squash-merge scenarios, including edge cases like non-standard commit messages.

Open questions and loose ends
- **Design direction**: Whether to adopt (G) (hybrid of composable filters and explicit merge-checking), (F) (unified filtering model with workarounds for "selection is not proof"), or (D) (implicit behavior). Knoble’s latest reply frames the composable model as salvageable with workarounds, but the thread has not converged on a solution.
- **Scope expansion**: Whether to include squash-merged branches. Don’s proposal (G) excludes them, while Nordgren argues they are integral to triangular workflows (e.g., GitHub PRs) and should be supported. This could require additional logic (e.g., heuristics for squash-merge reachability) and expand test coverage.
- **Unified filtering model**: Whether to deprecate `--delete-merged` in favor of `--list` + `xargs`, and how to handle dry-run functionality (currently `--delete-merged --dry-run`). Knoble’s proposal (F) does not address these details, while (G) sidesteps them by keeping logic in `-d`.
- **Safeguards**: Whether to preserve existing exclusions (worktrees, stacked branches) or relax them for gone-upstream branches; whether the feature should require explicit opt-in (e.g., `--merged`) or be enabled by default (Nordgren’s position). Don’s proposal (G) preserves safeguards by requiring explicit `--merged`.
- **Edge cases**: Handling of branches with no upstream set, or upstreams that are gone but not due to a merge (e.g., force-pushed); interaction with triangular workflows (e.g., GitHub’s push-to-topic, merge-to-main). Don’s proposal (G) narrows selection with `--upstream-gone` to avoid false positives. If squash merges are included, additional edge cases may arise (e.g., squash commits with non-standard messages).
- **Implementation path**: Don suggests a two-patch series (first adding `--upstream-gone` as a listing filter, then extending it to support deletion), which could build consensus incrementally. If squash merges are included, the implementation may require additional patches to handle squash-merge reachability.
- **Workflow ergonomics**: How the feature interacts with settings like `push.default=current` and `branch.autosetupmerge=inherit`. Knoble notes these broader changes would require a major release (e.g., Git 4.0) due to past controversy, while Nordgren advocates for them as usability improvements for Git 3.0. The relevance to the RFC’s scope remains unresolved.

Participant positions
- DonQuinleone (author): Proposes (G) (hybrid of composable filters and explicit merge-checking) as a middle ground, addressing the "selection is not proof" limitation of (F). Explicitly excludes squash/rebased merges from scope but acknowledges Nordgren’s argument for including them. Suggests a two-patch series to build consensus incrementally. No position on workflow defaults.
- D. Ben Knoble: Advocates for composable syntax (F) as the most extensible solution, citing Git’s `git-rebase` man page ("INCOMPATIBLE OPTIONS") as precedent. Acknowledges the "selection is not proof" limitation but proposes workarounds (e.g., `--format='%(refname:lstrip=2)'`, manual dry-run verification) rather than abandoning the model. Suggests reusing `--list` filtering logic in `-d` if filters are added. Raises broader workflow concerns (triangular workflows, `push.default=current`) but notes these are orthogonal to the RFC and would require a major release to address.
- Harald Nordgren: Advocates for (D) (implicit behavior for gone-upstream branches if their tip is reachable from `HEAD` or another implicit ref), rejecting explicit flags or composable syntax as unconventional. Argues that squash-merged branches should be included in scope, as they are part of triangular workflows (e.g., GitHub PRs). Advocates for `push.default=current` and `branch.autosetupmerge=inherit` as usability improvements for Git 3.0, framing them as better defaults for triangular workflows.

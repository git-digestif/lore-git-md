Thread identity
Subject: [RFC] git branch --delete-merged: handle branches with gone upstreams
Series version: RFC (no patch version)
Originating author: DonQuinleone (first-time contributor)
Thread type: RFC / design discussion

Core problem or goal
Allow `git branch --delete-merged` to delete local branches whose upstream has been deleted by the hosting service (e.g., GitHub after merging a PR), provided the branch tip is reachable from a user-specified ref (e.g., `origin/master`). The current command refuses to delete such branches because the upstream is gone, forcing users to manually identify and delete them.

Current status
No implementation exists; this is a design discussion. Four interface shapes are now under consideration:
- (A) A modifier like `--into origin/master` to `--delete-merged`, which deletes branches only if their tip is reachable from the named ref (author’s original proposal).
- (B) Composable filters like `--upstream-gone --merged=origin/master` to `-d`, enabling standalone listing of gone-upstream branches.
- (C) A composable syntax using `--option=value,value,value` (e.g., `--delete-merged='origin/*,into:origin/master'`), suggested by D. Ben Knoble to avoid new flags and allow future extensions.
- (D) No new flag, but relax the existing `--delete-merged` behavior to automatically treat gone-upstream branches as merged if their tip is reachable from `HEAD` (implied by Nordgren’s workflow critique, though not explicitly proposed).

The author prefers (A) for simplicity and alignment with existing safeguards; Knoble prefers (C) for CLI consistency and extensibility. Nordgren’s reply does not endorse a specific interface but reinforces the need for Git to better support triangular workflows by default, suggesting that the RFC’s ergonomic goals would be partially addressed by changing defaults for `push.default`, `branch.autosetupmerge`, and `status.comparebranches`. The RFC still explicitly excludes squash/rebased merges from scope, preserving the current strictness of `--delete-merged`.

Key technical details
- Files touched: `builtin/branch.c` (branch deletion logic).
- New behavior: Pass a user-specified commit (e.g., `origin/master`) to `check_branch_commit()` instead of `HEAD` for gone-upstream branches.
- On-disk format: No changes.
- Test coverage: Not yet addressed; the included script demonstrates the issue (a provably merged branch is skipped by `--delete-merged` after fetching and pruning).

Open questions and loose ends
- Design direction: (A) vs. (B) vs. (C) vs. (D) vs. other alternatives; whether to relax `--delete-merged`’s behavior by default for gone-upstream branches.
- Safeguards: Whether to preserve existing exclusions (worktrees, stacked branches) or relax them for gone-upstream branches; whether the feature should require explicit opt-in (e.g., `--into`) or be enabled by default.
- User experience: Whether the interface should be composable or monolithic; how to balance discoverability with extensibility.
- Edge cases: Handling of branches with no upstream set, or upstreams that are gone but not due to a merge (e.g., force-pushed); interaction with triangular workflows (e.g., GitHub’s push-to-topic, merge-to-main).
- Workflow ergonomics: How the feature interacts with settings like `push.default=current`, `branch.autosetupmerge=inherit`, and `status.comparebranches=@{upstream} @{push}`; whether these should be defaults to reduce friction in triangular workflows.
- Defaults: Whether the RFC’s feature should be opt-in (requiring `--into`) or opt-out (enabled by default for gone-upstream branches, with a flag to disable).

Participant positions
- DonQuinleone (author): Proposes (A) as the simplest solution, preserving existing safeguards. Explicitly excludes squash/rebased merges. No position on workflow defaults.
- D. Ben Knoble: Critiques (A) as context-dependent and non-composable; prefers (C) (`--delete-merged='origin/*,into:origin/master'`) for CLI consistency and extensibility. Raises broader workflow concerns (triangular workflows, `push.default=current`).
- Harald Nordgren: No direct position on the RFC’s interface proposals (A/B/C), but endorses Knoble’s workflow critique. Argues that Git’s defaults (`push.default`, `branch.autosetupmerge`, `status.comparebranches`) should be changed to better support triangular workflows, which would indirectly address the pain point the RFC targets. No implementation details or edge cases discussed.

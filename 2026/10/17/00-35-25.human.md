This is an RFC proposing a new feature for `git branch --delete-merged` to handle branches whose upstream has been deleted by the hosting service (e.g., GitHub after merging a pull request). The author, DonQuinleone, is a first-time contributor to the list.

The problem: when a topic branch is merged on the server and its remote counterpart is deleted, `git branch --delete-merged` refuses to delete the local branch because the upstream is "gone" and no longer serves as a safety check. The branch is provably merged (its tip is an ancestor of `origin/master`), but Git currently treats a gone upstream as a blocker rather than a candidate for cleanup.

The proposal separates *selection* (which branches to consider) from *proof* (whether they are merged). Two possible designs are sketched: (A) a new `--into <ref>` option for `--delete-merged` that would delete branches with gone upstreams only if their tip is reachable from the named ref (e.g., `origin/master`), or (B) composable filters `--upstream-gone` and `--merged=<ref>` for `git branch -d`. The author leans toward (A) because it preserves all existing protections and is more focused.

The email references prior discussion on the `--delete-merged` series (notably Junio’s objection to inferring safety from a gone upstream) and ties into Harald Nordgren’s in-flight work on the same command. A minimal reproduction script is included to demonstrate the current behavior. The tone is collaborative and the motivation is clearly explained, making this a well-prepared RFC.

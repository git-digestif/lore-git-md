This thread is exploring how to extend `git branch --delete-merged` to handle local branches whose upstream has been deleted (e.g., by GitHub after merging a PR), while ensuring the branch tip is still reachable from a user-specified ref like `origin/master`. The author, DonQuinleone, proposed two interface designs: (A) a modifier like `--into origin/master` for `--delete-merged`, or (B) composable filters like `--upstream-gone --merged=origin/master`. The current behavior refuses to delete such branches, forcing manual cleanup.

D. Ben Knoble weighed in with a substantive critique of both proposals. He argued that (A) would clutter the CLI with a context-dependent option, while (B) risks ambiguity (e.g., `--merged` defaulting to `HEAD` if omitted). Instead, he suggested a more composable syntax like `--delete-merged='origin/*,into:origin/master'` to avoid new flags and allow future extensions. He also highlighted workflow ergonomics, noting that GitHub’s triangular workflow creates awkward upstream configurations, and suggested settings like `push.default=current` to simplify the relationship between `@{upstream}` and `@{push}`.

The discussion remains open, with no consensus on the best design. Key questions include whether to preserve existing safeguards (e.g., worktree exclusions), whether the feature should require explicit opt-in, and how to handle edge cases like force-pushed upstreams. The thread is still in the design phase, with no implementation or test coverage yet.

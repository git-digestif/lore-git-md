This thread is an RFC discussion about extending `git branch --delete-merged` to handle local branches whose upstream has been deleted (e.g., after a GitHub PR merge). The author, DonQuinleone, initially proposed a new flag like `--into origin/master` but has since shifted to a hybrid approach (G) that combines composable filters (`--upstream-gone` and `--merged=<commit>`) with explicit merge-checking logic. This aims to address a key limitation of a competing proposal (F) from D. Ben Knoble, which suggested using `--list` + `xargs` but was criticized for separating branch selection from merge verification.

The debate centers on interface design—whether to use implicit behavior (Harald Nordgren’s preference), composable filters (Knoble’s stance), or a hybrid model (Don’s latest proposal). Nordgren has now reopened a previously settled question by arguing that squash merges should also be supported, as they’re common in GitHub’s triangular workflow. This could expand the feature’s scope if the discussion converges on including them. The thread remains in the design phase, with no implementation yet, and key open questions include safeguards, edge cases (e.g., force-pushed upstreams), and whether the feature should require explicit opt-in. Don has suggested a two-patch series to build consensus incrementally.

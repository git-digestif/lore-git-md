This thread is exploring how to extend `git branch --delete-merged` to handle local branches whose upstream has been deleted (e.g., after a GitHub PR merge), a common pain point in triangular workflows. The author, DonQuinleone, proposed a simple `--into origin/master` modifier to let the command delete such branches if their tip is reachable from a specified ref. D. Ben Knoble countered with a more composable syntax (`--delete-merged='origin/*,into:origin/master'`), arguing it better fits Git’s CLI conventions.

Harald Nordgren’s recent reply dismisses Knoble’s approach as overly complex and inconsistent with Git’s design principles, siding with the author’s preference for simplicity. However, Nordgren doesn’t engage with the technical details or propose an alternative—his objection is purely about user experience. Meanwhile, the thread has also broadened to include a critique of Git’s defaults (e.g., `push.default`, `branch.autosetupmerge`) for triangular workflows, though this remains tangential to the RFC’s core proposal.

The discussion is still open, with no consensus on the interface (monolithic flag vs. composable syntax) or whether the feature should be opt-in or enabled by default. Edge cases—like branches with no upstream or force-pushed upstreams—haven’t been addressed, and no implementation exists yet. Key participants remain divided: the author and Nordgren favor simplicity, while Knoble prioritizes extensibility. Phillip Wood, a frequent reviewer, hasn’t weighed in yet. For now, the thread is stuck on design philosophy rather than technical trade-offs.

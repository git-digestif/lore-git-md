This thread is about a proposed change to `git branch --delete-merged` to handle local branches whose upstream has been deleted (e.g., after a GitHub PR merge). The current command refuses to delete such branches, forcing manual cleanup. The author, DonQuinleone, initially suggested a new `--into origin/master` flag to delete branches only if their tip is reachable from a specified ref, but the discussion has since expanded into four competing interface designs.

The debate centers on whether the feature should require explicit flags (like `--into`), use composable syntax (e.g., `--delete-merged='origin/*,into:origin/master'`), or work by default for gone-upstream branches if their tip is reachable from `HEAD`. D. Ben Knoble favors composable syntax for extensibility, while Harald Nordgren now argues for no new flags at all, reviving an earlier proposal to relax `--delete-merged`’s behavior by default. The author still prefers the explicit `--into` modifier for simplicity and safety. Key unresolved questions include whether the feature should be opt-in or opt-out, how to handle edge cases (e.g., force-pushed upstreams), and whether the interface should prioritize discoverability or composability. No implementation exists yet, and the thread remains a design discussion with no consensus.

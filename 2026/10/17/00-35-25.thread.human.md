This thread is an RFC by first-time contributor DonQuinleone proposing a change to `git branch --delete-merged` to handle local branches whose upstream has been deleted (e.g., after a GitHub PR merge). Currently, the command skips these branches, forcing users to delete them manually. Six interface designs are under debate, ranging from a simple `--into` flag (the author’s preference) to a composable filtering model using `--list` and `xargs` (now advocated by D. Ben Knoble). Harald Nordgren argues for implicit behavior, where the command would automatically delete gone-upstream branches if their tip is reachable from `HEAD` or another implicit ref, without requiring new flags.

The discussion has expanded beyond the RFC’s core question to touch on Git’s defaults for triangular workflows. Nordgren and Knoble agree that settings like `push.default=current` and `branch.autosetupmerge=inherit` would improve usability for GitHub-style workflows, but Knoble notes these changes would require a major release (e.g., Git 4.0) due to past controversy. The thread remains unresolved, with the central tension between interface philosophy—composability (Knoble) versus CLI purity (Nordgren)—and whether the feature should be opt-in, opt-out, or fully implicit. No implementation exists yet, and key details like safeguards and edge cases (e.g., force-pushed upstreams) are still open.

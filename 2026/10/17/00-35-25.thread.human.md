This thread is exploring how to improve `git branch --delete-merged` to handle local branches whose upstream has been deleted (e.g., after a GitHub PR merge), which the current command refuses to delete. The discussion has evolved into a broader debate about interface design, with three main proposals still in play.

The author, DonQuinleone, initially suggested adding a `--into origin/master` flag to `--delete-merged` to delete branches only if their tip is reachable from a specified ref. D. Ben Knoble has since pushed for a more composable approach, now proposing that Git should teach `git branch --list` to filter branches by merge status (e.g., `--merged-upstream=origin/main`), allowing users to pipe the output to `xargs git branch -d`. This would eliminate the need for a dedicated `--into` flag or even the `--delete-merged` subcommand, aligning with Git’s existing patterns. Harald Nordgren, meanwhile, argues for implicit behavior—relaxing `--delete-merged` to automatically treat gone-upstream branches as merged if their tip is reachable from `HEAD` or another implicit ref, with no new flags required.

The debate now centers on interface philosophy: Knoble’s composable, filter-based model versus Nordgren’s implicit, flag-free approach. Knoble’s latest proposal frames the issue as an opportunity to simplify Git’s branch management commands by making `--list` the primary interface for filtering, with deletion as a secondary step. The thread remains unresolved, with no consensus on whether to adopt Knoble’s unified filtering model, Nordgren’s implicit behavior, or the author’s original `--into` flag. Edge cases like safeguards for stacked branches or triangular workflows are still unaddressed, though Knoble has noted that broader workflow changes (e.g., `push.default=current`) would require a major release.

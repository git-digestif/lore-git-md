This thread is an RFC discussion about extending `git branch --delete-merged` to handle local branches whose upstream has been deleted (e.g., after a GitHub PR merge). The author, DonQuinleone, proposes adding a modifier like `--into origin/master` to allow deletion of such branches if their tip is reachable from a user-specified ref, addressing a common pain point where users must manually delete these branches today.

The discussion has centered on three interface options: (A) the author’s `--into` modifier, (B) composable filters like `--upstream-gone --merged=origin/master`, and (C) a composable syntax like `--delete-merged='origin/*,into:origin/master'` suggested by D. Ben Knoble. The author prefers (A) for simplicity, while Knoble argues for (C) to maintain CLI consistency and extensibility. Harald Nordgren, a contributor with related work, recently weighed in to support Knoble’s broader critique of Git’s defaults for triangular workflows (e.g., GitHub’s push-to-topic, merge-to-main model). Nordgren argues that settings like `push.default=current` and `branch.autosetupmerge=inherit` should be defaults to better align with how most users work, though this doesn’t directly address the RFC’s technical questions.

The thread remains in the design phase, with open questions about the interface, safeguards (e.g., whether to relax existing exclusions for gone-upstream branches), edge cases (e.g., force-pushed upstreams), and workflow ergonomics. No implementation exists yet, and the discussion has yet to converge on a preferred approach. Key participants include the author, Knoble, and Nordgren, with Phillip Wood (a reviewer of related work) also CC’d but not yet engaged.

This thread is an RFC discussion about extending `git branch --delete-merged` to handle local branches whose upstream has been deleted (e.g., after a GitHub PR merge). The author, DonQuinleone (a first-time contributor), initially proposed several interface designs and now favors a hybrid approach (G) that combines composable filters with explicit merge-checking to avoid the "selection is not proof" problem when piping `--list` output to `xargs git branch -d`.

Key participants include DonQuinleone, D. Ben Knoble, and Harald Nordgren. Don’s proposal (G) explicitly excludes squash-merged branches, while Nordgren argues they should be included as part of triangular workflows (e.g., GitHub PRs). Knoble initially advocated for a composable filtering model (F) but has now suggested workarounds to address Don’s critique, such as using `--format` to make `--list` output machine-readable and manually verifying deletions with a dry-run. He also proposes reusing `--list`’s filtering logic in `-d` if filters are added there, though this leaves open whether merge-checking should be tied to the filter or handled separately.

The discussion remains unresolved on whether the final design will prioritize composability (Knoble’s preference), explicit merge-checking (Don’s hybrid), or implicit behavior (Nordgren’s position). Open questions include whether squash merges should be in scope, how to handle edge cases (e.g., branches with no upstream or force-pushed upstreams), and whether the feature should require explicit opt-in or be enabled by default. Don has suggested a two-patch series to build consensus incrementally, starting with `--upstream-gone` as a listing filter. The thread has also touched on broader workflow concerns (e.g., `push.default=current`), though these are seen as orthogonal to the RFC’s scope.

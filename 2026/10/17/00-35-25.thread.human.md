This thread is a design discussion about extending `git branch --delete-merged` to handle local branches whose upstream has been deleted (e.g., after a GitHub PR merge). The author, DonQuinleone, proposes a new `--into` flag to allow deletion of such branches if their tip is reachable from a user-specified ref like `origin/master`. Currently, Git refuses to delete these branches, forcing manual cleanup.

The discussion has narrowed to four interface options, with the author favoring a simple `--into` modifier (A) for clarity and alignment with existing safeguards. D. Ben Knoble advocates for a composable syntax (C) like `--delete-merged='origin/*,into:origin/master'` to avoid new flags and enable future extensions, while Harald Nordgren rejects this as overly complex and inconsistent with Git’s CLI conventions. Nordgren aligns with the RFC’s ergonomic goals but hasn’t endorsed a specific alternative.

The latest reply from Knoble pushes back against Nordgren’s dismissal of composable syntax, arguing that a standalone `--into` flag is equally a "kitchen sink" and less flexible. He suggests alternatives like comma-separated values or repeatable options (e.g., `--into=ref1 --into=ref2`) to balance extensibility and simplicity. The debate remains unresolved, with no consensus on whether the feature should be opt-in (requiring `--into`) or opt-out (enabled by default for gone-upstream branches). Edge cases like triangular workflows and interaction with Git’s default settings (e.g., `push.default=current`) are still open questions, and no implementation or test coverage exists yet.

This thread is an RFC discussion about extending `git branch --delete-merged` to handle local branches whose upstream has been deleted (e.g., after a GitHub PR merge). The author, DonQuinleone, proposes adding a modifier like `--into origin/master` to delete such branches if their tip is reachable from the specified ref. The discussion has since splintered into five competing interface designs, with no clear consensus.

D. Ben Knoble favors a composable syntax (e.g., `--delete-merged='origin/*,into:origin/master'`) or repeatable options (`--into=ref1 --into=ref2`) to avoid context-sensitive flags, arguing this aligns with Git’s CLI consistency and extensibility. Harald Nordgren, however, advocates for implicit behavior—relaxing `--delete-merged` to automatically treat gone-upstream branches as merged if their tip is reachable from `HEAD` or another implicit ref—rejecting explicit flags entirely. The author prefers the original `--into` modifier for simplicity, while Knoble has also raised broader workflow concerns (e.g., triangular workflows) but notes these are orthogonal and would require a major release (e.g., Git 4.0) to address.

The debate remains stuck on interface philosophy, with no movement toward implementation. Key tensions include whether the feature should be opt-in (explicit flags) or opt-out (implicit behavior), how to balance discoverability with extensibility, and whether composability (Knoble’s preference) or CLI purity (Nordgren’s preference) should take precedence. Edge cases—like branches with no upstream or force-pushed upstreams—remain unresolved, as does the interaction with Git’s defaults for triangular workflows.

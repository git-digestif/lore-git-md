This thread is exploring how to extend `git branch --delete-merged` to handle local branches whose upstream has been deleted (e.g., after a GitHub PR merge), a common pain point that currently forces manual cleanup. The discussion, started by first-time contributor DonQuinleone, has narrowed from six competing interface proposals to a pragmatic middle ground: adding composable filters (`--upstream-gone` and `--merged=<commit>`) to `git branch -d`, allowing users to safely delete gone-upstream branches with an explicit merge base (e.g., `git branch -d --upstream-gone --merged=origin/main`).

Key participants remain divided on philosophy but are converging on implementation. D. Ben Knoble initially pushed for a unified filtering model (using `--list` piped to `xargs`), but Don’s testing revealed a critical flaw—piping loses the merge-checking logic, making the approach unsafe. Harald Nordgren continues to advocate for implicit behavior (deleting gone-upstream branches if their tip is reachable from `HEAD`), but his proposal lacks safeguards against edge cases. Don’s hybrid approach addresses both concerns: composability avoids context-sensitive flags, while explicit `--merged` preserves proof of merge and prevents accidental deletions. The proposal also sidesteps the tangential debate about Git’s defaults for triangular workflows (e.g., `push.default=current`), which Knoble notes would require a major release.

The thread is now focused on whether this filtered `-d` approach can gain consensus. Don suggests an incremental two-patch series—first adding `--upstream-gone` as a listing filter, then enabling deletion—to demonstrate the feature’s utility without risk. Open questions remain about edge cases (e.g., branches with no upstream set) and whether the "selection is not proof" model (requiring explicit `--merged`) is acceptable, but the discussion has shifted from abstract interface design to concrete implementation details. No code has been written yet, but the path forward is clearer.

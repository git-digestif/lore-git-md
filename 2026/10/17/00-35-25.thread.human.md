This thread is a request for comments (RFC) from first-time contributor DonQuinleone, proposing a new feature for `git branch --delete-merged` to handle local branches whose upstream has been deleted by the hosting service (e.g., GitHub after merging a pull request). Currently, `git branch --delete-merged` refuses to delete such branches because their upstream is gone, leaving users with no built-in way to bulk-delete local branches that are provably merged into a named ref like `origin/master`. The proposal suggests two possible designs: (A) a modifier like `--into origin/master` to `--delete-merged`, which would delete branches only if their tip is reachable from the named ref, or (B) composable filters like `--upstream-gone --merged=origin/master` to `-d`. The author prefers (A) for its simplicity and alignment with existing safeguards.

The thread is in the early design phase, with no implementation provided yet. Key participants include Harald Nordgren (author of related in-flight patches) and Phillip Wood (a reviewer of prior work in this area), who were CC’d for context. The discussion so far focuses on the problem statement and high-level design, with the author explicitly excluding squash/rebased merges from scope to maintain the current strictness of `--delete-merged`. The proposal touches the branch deletion logic in `builtin/branch.c` and would involve modifying `check_branch_commit()` to accept a user-specified commit for gone-upstream branches. No decisions or objections have been raised yet, and the thread remains open for feedback on the design direction.

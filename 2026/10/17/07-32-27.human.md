This is a feature patch series (v2) that introduces a configurable timeout for Git’s index lock, addressing a long-standing pain point for IDE users. The series now spans four patches, up from two in v1, and explicitly fixes pre-existing write-race conditions in `git commit` and `git reset` to enable the timeout behavior safely.

The core problem remains the same: background `git status` calls (common in IDEs) hold the index lock, causing user-initiated commands like `git add` or `git commit` to fail immediately. The solution adds a `core.indexLockTimeout` configuration (default: 1 second) that lets commands wait briefly for the lock instead of failing. The series is now more conservative about race conditions—commands that read the index before locking (e.g., `rebase`, `merge`) skip the timeout to avoid enlarging race windows, while commands that lock before reading (e.g., `add`, `checkout`) use it.

Key changes since v1:
- **New patch 1** makes `git status`’s non-waiting behavior explicit, clarifying the baseline.
- **New patch 4** fixes a write-race in `git reset`, mirroring the fix for `git commit` in patch 3.
- Commit messages now consistently motivate the lock-order changes as correctness fixes (addressing Jeff King’s feedback).
- The series now lists 15 files touched, including new test coverage (`t/t0032-index-lock-timeout.sh`) and adjustments to existing tests.

The implementation looks well-scoped: it targets common commands (`commit`, `reset`, `add`, `checkout`) while leaving more complex ones (e.g., `rebase`) unchanged for now. The default timeout (1 second) is still open to debate, but the author’s justification—balancing responsiveness with usability—seems reasonable. Test coverage appears thorough, with a dedicated test script and updates to lockfile/submodule tests.

This series is worth attention from anyone using Git in an IDE or tool-heavy workflow. The lock-order fixes (patches 3 and 4) are particularly notable as they address pre-existing bugs that could silently discard concurrent index updates. The trade-off (lstat() under the lock) is clearly documented and seems justified. If the default timeout sparks discussion, the author has signaled openness to adjusting it.

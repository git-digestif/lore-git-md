This is a follow-up in the ongoing discussion about deprecating the experimental `git format-rev` command. Kristoffer Haugsbakk clarifies a key technical detail about the proposed replacement, `git diff-tree`, and its limitations for scripted workflows.

The core issue is that `git diff-tree --format=medium` (the pretty-printing mode) does not support NUL termination (`-z`) for its output. While `git diff-tree` can handle NUL-terminated input and output for primitive diff formats like `--raw` or `--name-only`, it treats pretty-printed output as a stream of *separators* rather than *terminators*. This means the first commit in a stream has no delimiter, and subsequent commits are preceded by a separator (either newline or NUL). For scripts that consume output piecemeal (e.g., reading from a shell coprocess), this behavior is problematic because there’s no reliable way to detect the end of a single record without a terminator.

Kristoffer experimented with forcing terminator behavior but found it would require modifying `log-tree.c` to add a `--use-terminator` option. This would make `git diff-tree` behave like `git format-rev --stdin-mode=revs`, but the change isn’t trivial. For now, he’s working around the limitation in his own script by using `git format-rev` for pretty-printed commit messages and individual `git diff-tree` calls for interdiff generation, rather than a single coprocess.

The email doesn’t propose a patch or ask for a decision, but it underscores the functional gap between `git format-rev` and the proposed replacement. The lack of NUL termination for pretty-printed output in `git diff-tree` makes it unsuitable for scripts that need to handle multiline commit messages or revision expressions unambiguously. This weakens the case for deprecating `git format-rev` unless the gap is addressed or deemed non-critical. The discussion remains open, with no clear consensus yet.

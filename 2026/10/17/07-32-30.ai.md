This is the third patch in the v2 series introducing a configurable index lock timeout. It fixes a **pre-existing write-race condition in `git commit`** that has existed since 2007, where concurrent index updates (e.g., from `git add`) could be silently discarded if `git commit` read the index before acquiring the lock.

The patch reorders the lock acquisition in `builtin/commit.c` to follow the "lock → read → write" pattern, eliminating the race window between reading the index and locking it. This change is motivated as a **correctness fix** (addressing Jeff King’s feedback) and also enables `git commit` to benefit from the new timeout behavior introduced in the series. The commit message traces the historical context: the original C port of `git commit` (2007) locked before reading, but a later patch (2007-11-18) accidentally moved the read before the lock, introducing the race.

The implementation is straightforward: `repo_hold_locked_index()` is moved to the start of `prepare_index()`, and redundant lock acquisitions are removed. The test in `t/t0032-index-lock-timeout.sh` is updated to reflect that `git commit` now waits for the lock (instead of failing) when `core.indexLockTimeout` is set. The patch touches only `builtin/commit.c` and the test script, with no new public APIs or on-disk format changes.

This is a **well-motivated bugfix** with clear historical context and test coverage. The trade-off (holding the lock longer, potentially increasing contention) is explicitly acknowledged but justified by the correctness gain. The patch is narrowly scoped and unlikely to introduce regressions. Worth attention for users who have encountered silent index corruption in concurrent workflows.

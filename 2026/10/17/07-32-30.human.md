This is a **bugfix patch** in the v2 series introducing a configurable index lock timeout. It fixes a **long-standing write-race condition** in `git commit` (present since 2007) where concurrent index updates (e.g., from `git add`) could be silently discarded if `git commit` read the index before acquiring the lock.

The patch reorders the lock acquisition to happen *before* reading the index (`lock -> read -> write`), eliminating the race window. This change is motivated as a correctness fix, not just a prerequisite for the timeout feature, addressing Jeff King’s feedback that the commit message should frame it as such. The cost is slightly more work (e.g., `lstat()` calls) while holding the lock, but the trade-off is justified by the elimination of data loss.

The test adjustment in `t/t0032-index-lock-timeout.sh` reflects the new behavior: `git commit` now waits for the lock (like `git add` and `git checkout`) instead of failing immediately. This aligns with the series’ goal of reducing lock contention in IDE workflows.

The patch is narrowly scoped to `builtin/commit.c` and the test script, with no new public APIs or on-disk format changes. The race condition and its fix are well-documented in the commit message, including historical context (the accidental regression in 2007). While the change increases lock hold time, the impact is mitigated by the timeout mechanism introduced earlier in the series.

This is a **clear improvement** over the status quo and a necessary step toward making the timeout feature safe. The fix is conservative, well-tested, and unlikely to introduce regressions. Users who frequently run `git commit` alongside other Git commands (e.g., in IDEs) will benefit from the reduced failure rate.

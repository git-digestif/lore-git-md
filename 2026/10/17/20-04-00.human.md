This is a bugfix for the files ref backend, addressing a long-standing inconsistency in how root refs (like `HEAD` and `ORIG_HEAD`) are handled in the loose ref cache. The patch is now at v2, incorporating feedback from the initial review.

The core issue is that root refs are only included in the loose ref cache if the `REFS_FOR_EACH_INCLUDE_ROOT_REFS` flag is passed during the *first* iteration that creates the cache. Subsequent iterations include them regardless of the flag, while earlier ones omit them even if the flag is set. This patch fixes the problem by keeping root refs out of the shared loose ref cache entirely. Instead, when an iterator requests root refs, it creates a separate temporary ref cache for them, overlays its iterator on the loose ref iterator, and frees it when done.

The v2 update makes several improvements: it moves the new `create_root_ref_cache()` function for better diff readability, corrects misleading documentation and help text that incorrectly described `--include-root-refs` as listing pseudorefs (it only includes root refs like `HEAD` and `ORIG_HEAD`, not pseudorefs like `FETCH_HEAD`), and expands the commit message to discuss alternative approaches. The test coverage remains focused but sufficient, verifying that `--include-root-refs` works correctly with `--merged`.

This is a well-scoped, well-motivated fix that addresses a real bug without changing user-facing behavior beyond fixing the inconsistency. The discussion in the thread has settled on the technical approach, with no remaining objections. The patch touches only the files backend (`files-backend.c`) and adds a test case in `t/t6302-for-each-ref-filter.sh`, leaving the reftable backend unaffected. The performance impact is negligible since the flag is used in only two places, both invoking it just once per command. This looks like a solid, uncontroversial bugfix that should be ready for merging.

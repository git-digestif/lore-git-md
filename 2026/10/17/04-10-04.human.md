This is a brief follow-up in the ongoing integer-overflow hardening series from Johannes Schindelin. The thread is discussing the second patch, which changes the `posn` variable in `http.c` from `int` to `size_t` to prevent a heap under-read when HTTP response bodies exceed `INT_MAX`.

Junio replies to Simon Richter’s suggestion to use `off_t` instead of `size_t` for `posn`. He acknowledges the theoretical point that `off_t` is conventional for file positions, but argues that `posn` is not a file offset in the traditional sense—it is an offset into an in-memory buffer (`ptr`), whose size is naturally expressed in `size_t`. Since `ptr` is allocated with `size_t`-sized chunks, and `posn` never exceeds that allocation, `size_t` is the correct type for tracking progress within that buffer. Junio’s reasoning is technical and narrow: the choice hinges on whether `posn` represents a file position (favoring `off_t`) or an in-memory offset (favoring `size_t`). His conclusion reaffirms the original patch’s type choice without introducing new edge cases or questioning the patch’s overall goal.

The discussion remains substantive but settled for now. No code changes are needed, and the patch’s readiness for integration is unchanged. The thread’s broader open questions—platform-specific `SSIZE_MAX` vs. `size_t` width mismatch and macro portability—are still unresolved in other patches, but this particular point of contention appears to be closed.

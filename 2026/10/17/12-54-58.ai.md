This is the first patch in a five-part bugfix series for `git worktree repair`. It refactors `.git` file handling in `repair_worktree_at_path()` to use `read_gitfile_raw()` instead of `read_gitfile_gently()`, aligning the parsing logic with `repair_gitfile()` and centralizing path resolution and repository validation in the caller. The change eliminates reliance on the non-reentrant `read_gitfile_gently()` and prepares the codebase for stricter `.git` file validation in later patches.

The patch touches only `worktree.c`, replacing manual string handling with `strbuf` operations to avoid memory leaks and improve consistency. It explicitly handles both absolute and relative paths in `.git` files, stripping the `.git` suffix and appending relative paths when necessary. The refactoring also adjusts error handling: it now rejects `.git` files with `gitdir:` prefixes missing a trailing space (e.g., `gitdir:foo/bar`), treats trailing whitespace as part of the path (e.g., `gitdir: foo/bar/   ` resolves to `worktrees/   `), and preserves the fallback to inferred backlinks when the `.git` file is invalid but an inferred path exists. These stricter parsing rules are internal and do not affect user-visible behavior yet, but they lay the groundwork for the validation logic introduced in patch 5.

The commit message is clear and detailed, explaining the motivation (consistency with `repair_gitfile()`, reentrancy) and the mechanical changes (replacing `read_gitfile_gently()` with `read_gitfile_raw()`, using `strbuf`). The test coverage for this patch is implicit in the later patches (2–5), which verify the new parsing rules and error handling. No new test cases are added here, as the patch is purely preparatory.

The stricter `.git` file parsing could theoretically break manually edited `.git` files, but the commit message does not mention this as a concern, and the validation logic in patch 5 is designed to handle such edge cases.

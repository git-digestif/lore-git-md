This thread began with a bug report from a first-time contributor, Gingrspacecadet, about a Git crash in `git apply --check` when processing a patch that creates a new file with a specific malformed header format. The crash, an assertion failure in `apply.c`, occurs when there’s a blank line (or other non-header line) after the `diff --git` header, followed by `--- /dev/null` appearing before `new file mode`. The issue is long-standing, dating back to 2005, and affects multiple released versions of Git.

Tanga Joris has now submitted a complete two-part fix for the problem. The first patch addressed a parsing edge case where stale values in the patch struct caused the crash, while the second patch (just posted) tackles a related issue: patches where `---` or `+++` lines appear *before* the `new file mode` or `deleted file mode` lines. This second patch explicitly rejects such malformed patches with clear error messages, following the precedent set by a 2017 commit that rejected other mutually exclusive header lines. The fix is narrowly scoped, well-tested, and preserves compatibility with patches generated by Git itself. The test coverage in `t/t4133-apply-filenames.sh` is thorough, covering both the original crash scenario and the new edge cases.

The series is now ready for review by maintainers familiar with the apply subsystem. The crash is deterministic, and the reproducer is clear, so the review process should be straightforward. The only remaining open questions are whether the fix affects other `git apply` workflows (like `--index` or `--cached`) and whether there are additional edge cases (e.g., deleted files or mode changes) that might trigger similar issues. For now, the series appears to address the original bug report fully and without introducing new problems.

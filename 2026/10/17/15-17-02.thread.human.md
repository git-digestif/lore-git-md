This thread began as a bug report from first-time contributor Gingrspacecadet about a Git crash in `git apply --check` when processing patches with malformed headers. The crash, caused by an assertion failure in `apply.c`, affects multiple Git versions and stems from two related parsing edge cases in how the apply machinery handles new-file and deleted-file patches. Tanga Joris quickly submitted a two-part fix series addressing both root causes, complete with thorough test coverage.

The series has now hit a significant review hurdle. Phillip Wood, a respected reviewer with deep knowledge of Git's apply subsystem, has raised fundamental concerns about the first patch's approach. He argues that the edge cases the fix accepts—like blank lines or indented mode lines after `diff --git`—represent corrupt input rather than valid patches, and questions whether Git should accommodate them at all. His review challenges the series' core assumption that these malformations are worth supporting, suggesting instead that the fix should reject them outright to maintain strict parsing rules. This isn't a rejection but a call for deeper discussion about Git's error-handling philosophy.

The thread is now at a crossroads: the technical fix exists, but its alignment with Git's principles is contested. The next steps will likely involve Tanga either justifying why these edge cases should be treated as valid (perhaps because other tools generate them) or revising the series to adopt stricter validation. The outcome will determine whether the fix lands as-is, pivots toward stricter error handling, or requires additional iteration to address Phillip's concerns.

This thread is about a bug in `git apply --check` that causes Git to crash when processing patches with malformed headers. The issue, reported by first-time contributor Gingrspacecadet, stems from long-standing logic errors in how Git parses new-file and deleted-file patches, leading to an assertion failure (`patch->is_new <= 0`) in `apply.c`.

Tanga Joris has submitted a two-part fix (now in its second version) that addresses both root causes: stale filename values from early parsing termination and inconsistent header ordering (e.g., `---` appearing before `new file mode`). The series now strictly rejects any patch header format not generated by `git diff` or `git format-patch`, including blank lines or indented mode lines after `diff --git`, aligning with Junio C Hamano’s guidance. The fix includes thorough test coverage and resolves a memory leak in `parse_git_diff_header()` identified by Siddharth Asthana, though the leak’s fix remains pending as a minor preparatory patch.

The series is under final review, with maintainer endorsement and no remaining philosophical objections. Phillip Wood and Junio both endorsed the stricter validation approach, shifting the fix’s direction from normalization to outright rejection of corrupt input. The only open questions are minor: whether to address the memory leak in a separate patch (to retain test coverage), whether the error messages are sufficiently clear, and whether to revisit the handling of empty `diff --git` sections. Siddharth’s latest review suggests rewording error messages to avoid confusion over stripped filenames (e.g., `dev/null` instead of `/dev/null`), a surface-level but user-facing improvement. The series targets `maint` and merges cleanly with all integration branches.

This thread is about a Git crash in `git apply --check` when processing patches with malformed headers, originally reported by first-time contributor Gingrspacecadet. The issue stems from long-standing logic errors in Git's apply machinery, specifically how it parses and validates new-file and deleted-file patches. Two related edge cases were identified: stale filename values due to early parsing termination, and patches where `---` or `+++` lines appear before their corresponding mode lines, leading to inconsistent patch state and an assertion failure.

Tanga Joris submitted a two-part patch series that now fully addresses both root causes. The series has evolved significantly during review, shifting from a more permissive approach to a stricter validation model that rejects any patch header format not generated by `git diff` or `git format-patch`. This stricter approach was endorsed by maintainer Junio C Hamano and reviewer Phillip Wood, who argued that corrupt input should not be normalized. The series now rejects patches with blank lines, indented mode lines, or inconsistent header ordering, and includes thorough test coverage in a new test file, `t/t4133-apply-filenames.sh`.

The latest update is a minor refinement to error messages, based on feedback from Siddharth Asthana. The messages will now reference the problematic header lines (e.g., `"---" before "new file mode"`) rather than stripped filenames, making them more intuitive for users. A memory leak in `parse_git_diff_header()` was also identified and will be fixed in the upcoming v3 series. The series is technically complete, targets the `maint` branch, and is ready for final review. The only remaining loose end is whether to revisit the handling of empty `diff --git` sections, though this is uncontested for now.

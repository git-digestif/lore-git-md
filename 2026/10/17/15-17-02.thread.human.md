This thread began as a bug report from first-time contributor Gingrspacecadet: `git apply --check` crashes with an assertion failure (`patch->is_new <= 0`) in `apply.c`'s `check_preimage()` when fed patches with malformed headers, a bug confirmed on released versions from Git 2.43 through current `master`. The discussion has since evolved into a fix proposal from Tanga Joris, now at a v3 three-part series under review, with both Junio C Hamano and reviewers Phillip Wood and Siddharth Asthana weighing in substantively on how strict the validation should be.

The maintainer has endorsed a strict approach: any patch header that `git diff` or `git format-patch` would not generate should be rejected outright, and `find_header()` must clear stale patch state when `parse_git_diff_header()` returns early. In the latest email, Tanga confirms the historical basis for going further -- bare `diff --git` lines with no following extended headers were only ever emitted by Git in 2005 (commit 206de27efa), and commit ec1fcc16af added the `index` line months later, so modern Git cannot produce an empty `diff --git` section even for whitespace-only changes, renames, or merges. On that basis the thread has converged on a v4 design that drops the memory-leak fix in patch 1/3 in favor of having `find_header()` immediately report a corrupt patch when a `diff --git` line is followed by no extended headers. Non-patch material between complete patches will still be ignored so email commentary remains allowed, and third-party `diff` output that is not `diff --git` keeps flowing through the existing code paths unchanged.

The series remains based on `maint` and merges cleanly with `master`, `next`, and `seen`, with tests in a new `t/t4133-apply-filenames.sh` covering the blank-line, indented-mode, empty-section, and header-ordering cases. The only open item is Tanga preparing and posting the v4 iteration; no objections to the converged design remain.

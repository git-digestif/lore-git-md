This thread concerns a crash in `git apply --check` triggered by malformed patch headers, where an assertion failure in `check_preimage()` occurs when `---` or `+++` lines appear before `new file mode` or `deleted file mode` lines, or when stale state persists from `diff --git` headers followed by unexpected content. After Gingrspacecadet reported the bug and Tanga Joris submitted a three-part fix series targeting `apply.c`, the discussion has converged on a stricter validation approach endorsed by maintainer Junio C Hamano: rejecting any patch header format that `git diff` or `git format-patch` would not generate, rather than attempting to normalize corrupt input.

In the latest development, Tanga Joris has proposed simplifying the series by dropping patch 1/3 (the memory leak fix in `parse_git_diff_header()`) entirely. Instead, he suggests that `find_header()` should immediately report a corrupt patch when it encounters a `diff --git` line with no content following it, rather than continuing to search subsequent lines. This would render the memory leak fix unnecessary and significantly simplify patch 2/3, while also rejecting the "empty section" edge case that had previously been left as an exception. Tanga notes that modern Git does not generate empty `diff --git` headers and that existing apply and am tests pass under this stricter behavior.

The series is currently awaiting confirmation that this simplified approach matches Junio's intent before Tanga prepares a v4 iteration. While Phillip Wood and Siddharth Asthana have already endorsed the stricter validation philosophy and improved error messages, the specific decision to reject empty `diff --git` sections outright -- rather than ignoring them as the current code does -- represents the final open question in an otherwise technically complete fix.

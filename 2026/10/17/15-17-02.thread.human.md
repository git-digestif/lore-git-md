This thread concerns a crash in `git apply --check` triggered by malformed patch headers, specifically an assertion failure in `apply.c`'s `check_preimage` when processing new-file patches with inconsistent header ordering. First-time contributor Gingrspacecadet reported the bug, and Tanga Joris has submitted a three-part v3 fix series that rejects corrupt headers outright rather than attempting to normalize them, fully aligning with maintainer guidance that `git apply` should accept only formats generated by `git diff` or `git format-patch`. The series fixes a memory leak in `parse_git_diff_header()` (1/3), adds strict validation rejecting blank lines or indented mode lines after `diff --git` (2/3), and explicitly rejects patches where `---` precedes `new file mode` or `+++` precedes `deleted file mode` (3/3), with comprehensive tests in `t/t4133-apply-filenames.sh`.

Phillip Wood and Junio C Hamano have both endorsed the stricter validation approach, arguing that corrupt input should be diagnosed as an error rather than silently accepted, while Siddharth Asthana identified the memory leak and suggested more actionable error messages referencing header lines rather than stripped filenames. In his latest review, Junio challenged the test case in patch 1/3 as inadequate—it passes only because the bogus and legitimate `diff --git` lines happen to reference the same file—and pinpointed the root cause as `find_header()` failing to clear stale `patch->old_name` and `patch->new_name` state when `parse_git_diff_header()` returns early after encountering an unrecognized line. He insists that `find_header()` must clear the patch struct before continuing its search and that the series should reject such corrupt headers explicitly rather than tolerate them.

The series remains under review targeting `maint`, with Junio's feedback suggesting the fix may need to directly address the stale-state clearing in `find_header()` rather than relying solely on later validation patches. The only remaining uncontested edge case is whether empty `diff --git` sections followed by another `diff --git` should also be rejected, though Junio has hinted even this may warrant re-evaluation.

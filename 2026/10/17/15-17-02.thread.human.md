This thread is about a bug in Git where `git apply --check` crashes with an assertion failure when processing a patch that creates a new file. The crash occurs in `apply.c`'s `check_preimage` function due to a logic error in how the `is_new` flag is handled for new-file patches.

The bug was reported by Gingrspacecadet, a first-time contributor, and has since been confirmed by Tanga Joris, who reproduced it on both the current `master` branch and Git 2.43. This means the issue is long-standing, not a recent regression. The crash is triggered by a specific ordering in the patch header—when `--- /dev/null` appears *before* `new file mode`—rather than by the patch's content. Tanga provided a minimal reproducer that reliably triggers the assertion, narrowing the scope of the bug to an edge case in how `git apply` parses new-file patches.

No fix has been proposed yet, and the issue remains open. The next steps are to confirm the exact header ordering that triggers the bug and determine whether the fix should adjust the assertion in `check_preimage` or the parsing logic itself. If other tools (like `git format-patch`) generate patches in this order, the bug could affect more workflows than initially thought. The thread is still active, and the reproducer provided by Tanga will likely form the basis for a test case.

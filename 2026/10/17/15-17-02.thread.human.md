This thread is about a Git crash in `git apply --check` when processing patches with malformed headers, originally reported by first-time contributor Gingrspacecadet. The issue stems from long-standing logic errors in Git's apply machinery, specifically how it parses and validates new-file and deleted-file patches. Two related edge cases were identified: stale filename values due to early parsing termination, and inconsistent header ordering where `---` or `+++` lines appear before mode lines.

Tanga Joris proposed a two-part fix that has since been revised to adopt stricter validation, now rejecting malformed patches outright rather than attempting to normalize them. This aligns with Git's precedent for strict diff header validation and has been explicitly endorsed by maintainer Junio C Hamano. The series is under final review, with both patches including thorough test coverage in a new test file, `t/t4133-apply-filenames.sh`. The fix targets the `apply.c` subsystem and is narrowly scoped to the parsing logic, preserving compatibility with patches generated by Git itself.

Key participants include Phillip Wood, who provided substantive technical review and successfully argued for stricter validation, and Junio, who clarified that `git apply` should reject anything not generated by Git's own tools. The only remaining open questions are about error message clarity and whether to reject additional edge cases, such as empty `diff --git` sections. The series is technically complete, merges cleanly with all integration branches, and is expected to land soon pending final review.

This thread began as a bug report from first-time contributor Gingrspacecadet about a crash in `git apply --check` when processing malformed patches that create new files. The assertion failure in `check_preimage` stems from long-standing logic errors in `apply.c` where empty `diff --git` sections or misordered header lines leave the patch structure in an inconsistent state. Tanga Joris has developed a two-patch v4 fix series targeting `maint` that addresses both empty `diff --git` headers (rejected immediately in `find_header()`) and the ordering violations where `---` or `+++` lines precede `new file mode` or `deleted file mode` declarations.

The series has converged on a strict validation approach endorsed by Junio C Hamano, who confirmed that modern Git never generates bare `diff --git` lines and that such input should be diagnosed as corrupt. Phillip Wood and Siddharth Asthana provided substantive reviews supporting the stricter checks, with Asthana receiving a `Helped-by` credit on the second patch. Junio has now explicitly approved the first patch with a "Looking good," validating the implementation details including the error reporting at the correct line number and the clean memory handling via the `-128` return code. He noted one minor pre-existing edge case -- a trailing bare `diff --git` at end-of-file with fewer than six remaining bytes bypasses the new error message -- but considers this optional future work rather than a blocker.

The v4 series, based on commit `77904e546de3bd940621092ecec47a88d0cede5d`, merges cleanly with `master`, `next`, and `seen`, and includes comprehensive test coverage in the new `t/t4133-apply-filenames.sh` covering file creation, deletion, modification, and header-ordering violations under both `--check` and application modes. With maintainer endorsement of the core approach now in place, the series awaits final integration decisions or any remaining review feedback on the second patch.

This thread began as a bug report from first-time contributor Gingrspacecadet about a Git crash in `git apply --check` when processing patches with malformed headers. The crash, an assertion failure in `apply.c`, affects released versions of Git and stems from long-standing logic errors in how the apply machinery parses new-file and deleted-file patches. Tanga Joris quickly submitted a two-part fix series addressing the root causes, with thorough test coverage in a new test file.

The discussion has since focused on a key philosophical question: should Git accept malformed headers (like blank lines or indented mode lines after `diff --git`) as valid input, or reject them outright? Phillip Wood argued for strict validation, citing Git's precedent for rejecting inconsistent header ordering. Tanga has now revised their approach to align with this stricter philosophy, planning to reject such malformed patches with clear error messages rather than attempting to normalize them. This change addresses Phillip's concern about normalizing corrupt input but may affect backwards compatibility for patches that modify files with blank lines after `diff --git`. The next step is a v2 patch series incorporating these changes, with continued review from maintainers to assess the trade-offs of stricter parsing.

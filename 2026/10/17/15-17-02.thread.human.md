A first-time contributor, Gingrspacecadet, reported a deterministic crash in `git apply --check`: an assertion failure (`patch->is_new <= 0`) in `apply.c`'s `check_preimage()` when a malformed patch creates a new file. The crash is present in released versions including 2.43 and 2.45.0. Tanga Joris has since taken up the fix and posted a v4 two-patch series, based on commit 77904e546de3bd940621092ecec47a88d0cede5d, targeting `maint` and merging cleanly with `master`, `next`, and `seen`. The series is under review and has not been merged.

The first patch rejects empty `diff --git` sections immediately in `find_header()`, and the second -- the subject of the latest email -- adds validation at the end of `parse_git_diff_header()` so that a `---` line appearing before `new file mode` (or a `+++` line before `deleted file mode`) is rejected with a descriptive error naming the offending line, instead of leaving the patch struct in an inconsistent state that later trips the assertion. Both patches add coverage in a new test file, `t/t4133-apply-filenames.sh`. Junio C Hamano explicitly endorsed the stricter validation, drawing a distinction between malformed Git-generated diffs, inter-patch commentary, and third-party diff output; Phillip Wood also gave substantive review supporting the tighter checks, and Siddharth Asthana contributed a `Helped-by`. No open questions remain on the approach; the series now awaits a maintainer integration decision.

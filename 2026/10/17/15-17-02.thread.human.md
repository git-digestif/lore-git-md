This thread began as a bug report by first-time contributor Gingrspacecadet, who identified a Git crash in `git apply --check` when processing patches with malformed headers. The crash, caused by an assertion failure in `apply.c`, affects released versions of Git and stems from two related parsing issues in how the apply machinery handles new-file and deleted-file patches.

Tanga Joris proposed a two-part fix addressing both root causes, which has since undergone a major revision. The revised approach now strictly rejects malformed patches—such as those with blank lines or indented mode lines after `diff --git`—aligning with Git’s precedent for strict diff header validation. This shift followed substantive feedback from Phillip Wood, who argued that such malformations represent corrupt input rather than valid edge cases. The series includes thorough test coverage in a new test file, `t/t4133-apply-filenames.sh`, and is ready for final review.

Junio C Hamano, the project maintainer, has now weighed in, decisively endorsing the stricter validation. His position clarifies that Git should reject any patch header format that `git format-patch` or `git diff` would not generate, effectively closing the debate on whether to normalize or reject malformed input. This aligns with the direction Tanga Joris has already taken in the v2 patches, though Junio’s comment suggests even the "empty section" edge case (a `diff --git` line with no content) might warrant rejection if it violates Git’s own output format. The series is now poised for final review, with no further technical changes expected beyond potential refinements to error messages or test cases.

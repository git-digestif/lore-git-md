This thread is about a Git crash in `git apply --check` when processing patches with malformed headers, originally reported by Gingrspacecadet. The crash occurs due to assertion failures in `apply.c` when parsing new-file or deleted-file patches with inconsistent header ordering or blank lines after the `diff --git` line. Tanga Joris proposed a two-part fix, but after substantive review from Phillip Wood, the approach has shifted toward stricter validation—rejecting malformed patches outright rather than attempting to normalize them.

The revised fix will now die with a clear error when a `diff --git` line is followed by invalid content (e.g., blank lines, indented mode lines, or `---`/`+++` before the next `diff --git`). This stricter validation will also reject patches that modify files if they contain blank lines after `diff --git`, even though Git currently accepts these (with the side effect of ignoring mode changes). The decision to prioritize robustness over flexibility has gained consensus, with Phillip Wood endorsing the approach and calling the current behavior (silently ignoring mode changes) a bug. The only exception is empty `diff --git` sections, which will continue to be ignored.

The series is now ready for a v2 patch submission, incorporating the stricter validation and updated test coverage in `t/t4133-apply-filenames.sh`. The next step is final review by maintainers (e.g., Junio or Eric Sunshine) to assess the backwards compatibility trade-offs. No further debate is expected, as the thread has converged on the stricter approach. The fix is narrowly scoped to the parsing logic in `apply.c` and preserves compatibility with patches generated by Git itself.

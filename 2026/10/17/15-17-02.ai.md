This is a bug report about a Git crash in `git apply --check`. The reporter, a first-time contributor, encountered an assertion failure (`patch->is_new <= 0`) when running `git apply --check` on a patch that creates a new test file (`tests/constraint_type_signature_lifting.test`). The patch itself is not a Git source file—it appears to be a test case for a different language (likely a custom compiler or toolchain)—but the crash occurs regardless of the patch's content.

The crash is reproducible with Git 2.54.0 on an x86_64 Linux system (Arch Linux, glibc 2.43, GCC 15.2). The reporter provided a minimal reproducer: the patch diff, the exact command (`git apply --check`), and the assertion failure message. No prior discussion or thread context is available, so this appears to be a new issue.

The assertion (`patch->is_new <= 0`) suggests a logic error in `apply.c`'s `check_preimage` function, where the code assumes a patch cannot be both "new" and have a preimage (i.e., a file to modify). The crash is likely triggered by the patch's structure: it creates a new file (`/dev/null` -> `tests/...`), but the apply machinery may be incorrectly handling the `is_new` flag in this edge case. The reporter’s system info (Rust enabled, SHA-1/SHA-256 support) is unlikely to be relevant, as the crash is in core C code.

This is a clear regression or edge-case bug in `git apply`. The crash is deterministic and reproducible, and the reporter provided all necessary details to investigate. The patch’s content is incidental—the issue would likely occur with any patch that creates a new file and triggers the assertion. No workaround is mentioned, and the reporter’s expectation (that the check should pass) is reasonable. The bug is worth attention, especially if it affects other `git apply` workflows.

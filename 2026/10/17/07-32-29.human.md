This is the **core feature patch** in Jun Wu’s four-part series introducing a configurable index lock timeout (`core.indexLockTimeout`) to reduce lock contention in IDE workflows. It implements the actual timeout logic in `repository.c` and adds the new configuration knob.

The patch makes commands like `git add`, `git checkout`, and `git commit` wait up to the configured timeout (default: 1 second) when the index lock is held, rather than failing immediately. The wait is skipped if the index was already read *by the same process* before locking, to avoid amplifying pre-existing write races (a safeguard clarified in the thread). The implementation is conservative: it force-drops stale in-memory indexes after acquiring the lock, ensuring commands always work with the latest data.

Key files touched: `repository.c` (core logic), `Documentation/config/core.adoc` (config docs), and a new test script (`t/t0032-index-lock-timeout.sh`) that verifies the timeout behavior (immediate failure with `timeout=0`, wait with `timeout>0`, and skip-wait if the index was read before locking). The patch also updates `t/meson.build` and existing lockfile/submodule tests to set `timeout=0` for speed, ensuring no performance regressions in test suites.

The default 1-second timeout is a middle ground between Mercurial’s 10-minute default and no wait at all. The patch is narrowly scoped to avoid regressions: commands that read the index before locking (e.g., `git rebase`, `git merge`) still skip the timeout, and the timeout is disabled for commands where waiting would worsen race conditions (e.g., `git stash`). The commit message lists supported/unsupported commands explicitly, making the behavior predictable.

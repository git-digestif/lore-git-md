Thread identity: Bug report about a Git crash in `git apply --check` when processing a patch that creates a new file. Originating author: Gingrspacecadet (first-time contributor). Thread type: bug report, now with a proposed fix (3/3) under final review after incorporating stricter validation, a memory leak fix, and improved error messages.

Core problem or goal: Git crashes with an assertion failure (`patch->is_new <= 0`) in `apply.c`'s `check_preimage` function when running `git apply --check` on patches with malformed headers. The issue stems from long-standing logic errors in how the apply machinery parses and validates new-file and deleted-file patches. Two distinct but related edge cases are addressed: (1) stale `old_name`/`new_name` values due to early termination of `parse_git_diff_header()` while `find_header()` continues searching (fixed in 2/3), and (2) patches where `---` or `+++` lines appear *before* `new file mode` or `deleted file mode` lines, respectively, leading to inconsistent patch struct state (fixed in 3/3). The crash affects released versions (confirmed in Git 2.43, 2.45.0, and current `master`). The fix now **fully aligns with Junio C Hamano’s guidance** to reject any patch header format not generated by `git diff` or `git format-patch`, including `diff --git` lines in commit message bodies (which are explicitly out of scope for `git apply`).

Current status: **Fix proposed (v3 series), under final review with strict validation confirmed, maintainer endorsement, a memory leak fix, and improved error messages**. Tanga Joris has submitted a three-part patch series addressing all root causes and review feedback. The series now **rejects corrupt patch headers outright** rather than attempting to normalize them, including patches with blank lines, indented mode lines, or unrelated text after `diff --git`. Patch 1/3 fixes a memory leak in `parse_git_diff_header()` by freeing `patch->def_name` before overwriting it, enabling the reinstatement of a previously dropped test case. Patch 2/3 dies with a clear error when a `diff --git` line is followed by invalid content (e.g., blank lines or indented mode lines), while Patch 3/3 explicitly rejects patches with inconsistent header ordering (`---` before `new file mode` or `+++` before `deleted file mode`). The series is based on `maint` and merges cleanly with `master`, `next`, and `seen`. All patches include thorough test coverage in `t/t4133-apply-filenames.sh`, covering blank lines after `diff --git`, indented mode lines, empty diff sections, and the new header-ordering edge cases. Tests verify both `--check` and actual application, including reverse application (`-R`). **Error messages have been refined** to reference the problematic header lines (e.g., `"---" before "new file mode"`) instead of stripped filenames (e.g., `/dev/null`), making them more actionable for users. The only remaining exception is empty `diff --git` sections followed by another `diff --git`, which will continue to be ignored (per 206de27efa), though Junio’s comment suggests even this case may warrant re-evaluation.

Key technical details:
- **Subsystem**: `apply.c` (specifically `parse_git_diff_header`, `find_header`, and `check_preimage` functions).
- **Triggers**:
  1. A blank line or other non-header line (e.g., indented `new file mode`) after the `diff --git` header, followed by `--- /dev/null` before `new file mode` (fixed in 2/3).
  2. Patches where `---` appears before `new file mode` (for new files) or `+++` appears before `deleted file mode` (for deletions) (fixed in 3/3).
  3. `diff --git` lines appearing in commit message bodies (now explicitly out of scope for `git apply`).
- **Root cause**: Inconsistent state in the `patch` struct due to (1) stale `old_name`/`new_name` values from early parsing termination, or (2) mutually exclusive header lines (`---`/`+++` before mode lines) that violate assumptions in `check_preimage()`. The stricter validation now rejects any header format not generated by `git diff` or `git format-patch`.
- **Assertion**: `patch->is_new <= 0` in `check_preimage()` (indicates the code assumes a patch cannot be both "new" and have a preimage, but this assumption fails for the problematic header formatting).
- **Memory leak**: `parse_git_diff_header()` overwrote `patch->def_name` without freeing the old value, causing leaks when processing multiple `diff --git` headers (e.g., in tests with empty sections). The fix (a `free()` before assignment) is trivial and safe, as both callers already zero the `patch` struct.
- **Error message refinement**: The messages now reference the problematic header lines (e.g., `"---" before "new file mode"`) instead of stripped filenames (e.g., `/dev/null`), improving clarity for users.
- **Files touched**: `apply.c` (fixes), `t/t4133-apply-filenames.sh` (new test file).
- **Behavior**: The revised fix **rejects malformed patches with clear, actionable error messages**, distinguishing between file-based and line-based input sources. The stricter validation rejects patches that modify files if they contain blank lines after `diff --git`, even though Git previously accepted these (with the side effect of ignoring mode changes). Empty `diff --git` sections followed by another `diff --git` remain accepted (per 206de27efa), though this may be revisited. `git apply` is now explicitly scoped to reject anything not generated by `git diff` or `git format-patch`.
- **Test coverage**: New test file `t/t4133-apply-filenames.sh` covers:
  - Blank lines after `diff --git` (now rejected).
  - Indented `new file mode`/`deleted file mode` lines (now rejected).
  - Empty diff sections (uncontested, still accepted but leak-free after 1/3).
  - Header-ordering edge cases (`---` before `new file mode`, `+++` before `deleted file mode`) (now rejected).
  Tests verify both `--check` and actual application, including reverse application (`-R`).

Open questions and loose ends:

Should this edge case be rejected outright, or is it harmless enough to preserve? This remains the sole uncontested edge case.

Thread identity: Bug report about a Git crash in `git apply --check` when processing a patch that creates a new file. Originating author: Gingrspacecadet (first-time contributor). Thread type: bug report, now with a proposed fix under review after incorporating stricter validation, a memory leak fix, improved error messages, and full alignment with maintainer guidance. A v4 iteration is now confirmed, dropping patch 1/3 in favor of immediate rejection of empty `diff --git` sections.

Core problem or goal: Git crashes with an assertion failure (`patch->is_new <= 0`) in `apply.c`'s `check_preimage` function when running `git apply --check` on patches with malformed headers. The issue stems from long-standing logic errors in how the apply machinery parses and validates new-file and deleted-file patches. Two distinct but related edge cases are addressed: (1) stale `old_name`/`new_name` values due to early termination of `parse_git_diff_header()` while `find_header()` continues searching (addressed in 2/3), and (2) patches where `---` or `+++` lines appear before `new file mode` or `deleted file mode` lines, respectively, leading to inconsistent patch struct state (addressed in 3/3). The crash affects released versions (confirmed in Git 2.43, 2.45.0, and current `master`). The fix **fully aligns with Junio C Hamano's guidance** to reject any patch header format not generated by `git diff` or `git format-patch`, including `diff --git` lines in commit message bodies (which are explicitly out of scope for `git apply`).

Current status: **Fix proposed (v3 series), under review, with v4 now confirmed to drop patch 1/3**. Tanga Joris has submitted a three-part patch series addressing root causes and edge cases, and has proposed that `find_header()` should stop and report a corrupt patch immediately when encountering a `diff --git` line with nothing after it (an empty section), rather than continuing to search. This would render patch 1/3 (the memory leak fix in `parse_git_diff_header()`) unnecessary and simplify patch 2/3 significantly. Junio C Hamano has **endorsed this stricter approach**, confirming that a legitimate `diff --git a/f b/f` line is always followed by extended header lines (such as `rename from`, `old mode`, or similar) even for pure renames or mode-only changes, and that an empty `diff --git` section is not something modern Git generates. Junio explicitly supports diagnosing such empty sections as corrupt patches in `find_header()`, which makes patch 1/3 unnecessary. Tanga Joris has now **historically verified** that Git produced bare `diff --git` lines only in 2005 (when commit `206de27efa` was written and `diff.c` printed the header before determining whether anything changed); a few months later commit `ec1fcc16af` added the `index` line, and modern Git cannot be made to emit a bare `diff --git` line even for whitespace-only changes, renames, or merges. The series remains based on `maint` and merges cleanly with `master`, `next`, and `seen`. The thread has converged on a v4 that drops the memory-leak fix in favor of immediate rejection of empty sections in `find_header()`.

Key technical details:
- **Subsystem**: `apply.c` (specifically `parse_git_diff_header`, `find_header`, and `check_preimage` functions).
- **Triggers**:
  1. A blank line or other non-header line (e.g., indented `new file mode`) after the `diff --git` header, followed by `--- /dev/null` before `new file mode`.
  2. Patches where `---` appears before `new file mode` (for new files) or `+++` appears before `deleted file mode` (for deletions).
  3. `diff --git` lines appearing in commit message bodies (now explicitly out of scope for `git apply`).
  4. Empty `diff --git` sections (a `diff --git` line with no content followed by another `diff --git`) -- now confirmed for rejection in the v4 approach.
- **Root cause**: Inconsistent state in the `patch` struct due to (1) stale `old_name`/`new_name` values from early parsing termination, or (2) mutually exclusive header lines (`---`/`+++` before mode lines) that violate assumptions in `check_preimage()`. Junio C Hamano identified that `find_header()` fails to clear `patch->old_name`, `patch->new_name`, and related state when `parse_git_diff_header()` returns early after seeing a `diff --git` line followed by an unrecognized line.
- **Assertion**: `patch->is_new <= 0` in `check_preimage()`.
- **Input classification (per Junio)**: Three distinct input types must be handled differently: (1) malformed `diff --git` lines within Git-generated patches should be rejected strictly; (2) non-patch material appearing between complete patches (email commentary between file diffs) should continue to be ignored; (3) lines beginning with `diff` that are not `diff --git` (third-party diff output) follow different parsing code paths and should be left unchanged to avoid destabilizing existing handling of non-Git diffs.
- **Historical context**: Git emitted bare `diff --git` lines only in 2005 (commit `206de27efa`); commit `ec1fcc16af` added the `index` line months later, and modern Git never generates empty `diff --git` sections.
- **Error message refinement**: Messages reference the problematic header lines (e.g., `"---" before "new file mode" at old_before_new.diff:4`) with line numbers, improving clarity for users.
- **Files touched**: `apply.c` (fixes), `t/t4133-apply-filenames.sh` (new test file).
- **Behavior**: The revised fix rejects malformed patches with clear, actionable error messages. The v4 approach additionally rejects empty `diff --git` sections outright in `find_header()`, since modern `git diff`/`git format-patch` does not generate them. Non-patch material between complete patches continues to be ignored, and plain `diff` (non-`--git`) lines still flow through existing third-party diff code paths unchanged.
- **Test coverage**: New test file `t/t4133-apply-filenames.sh` covers blank lines after `diff --git`, indented mode lines, empty diff sections, and header-ordering edge cases. Tests verify both `--check` and actual application, including reverse application (`-R`).

Open questions and loose ends:
- **Empty section handling**: Previously the sole uncontested edge case (accepted per 206de27efa), Tanga Joris proposed rejecting empty `diff --git` sections outright, and Junio C Hamano has now confirmed this approach is correct, endorsing immediate rejection in `find_header()`. Tanga has historically verified that bare `diff --git` output existed only in 2005 before `ec1fcc16af` added the `index` line. This resolves the question for v4.
- **Implementation detail from maintainer**: Junio C Hamano has specified that `find_header()` must clear the patch struct (`patch->old_name`, `patch->new_name`, and related state) before continuing the search when `parse_git_diff_header()` returns early, rather than leaving stale state that causes the crash.
- **Test case adequacy**: Junio has rejected the proposed test case in patch 1/3 as inadequate because it only passes when both the bogus and legitimate `diff --git` lines reference the same file `g`; with a different filename the code emits an "inconsistent old filename" error. Tanga confirms this behavior and agrees corrupt input should be diagnosed as an error. With the v4 approach dropping patch 1/3, this specific test case concern becomes moot.

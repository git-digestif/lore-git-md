Thread identity: Bug report about a Git crash in `git apply --check` when processing a patch that creates a new file. Originating author: Gingrspacecadet (first-time contributor). Thread type: bug report, now with a complete proposed fix (2/2).

Core problem or goal: Git crashes with an assertion failure (`patch->is_new <= 0`) in `apply.c`'s `check_preimage` function when running `git apply --check` on patches with malformed headers. The issue stems from long-standing logic errors in how the apply machinery parses and validates new-file and deleted-file patches. Two distinct but related edge cases are now addressed: (1) stale `old_name`/`new_name` values due to early termination of `parse_git_diff_header()` while `find_header()` continues searching (fixed in 1/2), and (2) patches where `---` or `+++` lines appear *before* `new file mode` or `deleted file mode` lines, respectively, leading to inconsistent patch struct state (fixed in 2/2). The crash affects released versions (confirmed in Git 2.43, 2.45.0, and current `master`).

Current status: **Fix proposed (complete series)**. Tanga Joris has submitted a two-part patch series addressing both root causes. The series is based on `maint` and merges cleanly with `master`, `next`, and `seen`. Patch 1/2 fixes the parsing edge case by freeing stale `old_name`/`new_name` values when the `diff --git` line is unused. Patch 2/2 explicitly rejects patches with inconsistent header ordering (`---` before `new file mode` or `+++` before `deleted file mode`), following the precedent set by d70e9c5c8c (2017). Both patches include thorough test coverage in `t/t4133-apply-filenames.sh`, covering blank lines after `diff --git`, indented mode lines, empty diff sections, and the new header-ordering edge cases. Tests verify both `--check` and actual application, including reverse application (`-R`).

Key technical details:
- **Subsystem**: `apply.c` (specifically `parse_git_diff_header`, `find_header`, and `check_preimage` functions).
- **Triggers**:
  1. A blank line or other non-header line (e.g., indented `new file mode`) after the `diff --git` header, followed by `--- /dev/null` before `new file mode`.
  2. Patches where `---` appears before `new file mode` (for new files) or `+++` appears before `deleted file mode` (for deletions).
- **Root cause**: Inconsistent state in the `patch` struct due to (1) stale `old_name`/`new_name` values from early parsing termination, or (2) mutually exclusive header lines (`---`/`+++` before mode lines) that violate assumptions in `check_preimage()`.
- **Assertion**: `patch->is_new <= 0` in `check_preimage()` (indicates the code assumes a patch cannot be both "new" and have a preimage, but this assumption fails for the problematic header formatting).
- **Files touched**: `apply.c` (fixes), `t/t4133-apply-filenames.sh` (new test file).
- **Behavior**: Crash (assertion failure) instead of passing the check or gracefully rejecting the patch. The fix now rejects malformed patches with clear error messages, distinguishing between file-based and line-based input sources.
- **Test coverage**: New test file `t/t4133-apply-filenames.sh` covers:
  - Blank lines after `diff --git`.
  - Indented `new file mode`/`deleted file mode` lines.
  - Empty diff sections.
  - Header-ordering edge cases (`---` before `new file mode`, `+++` before `deleted file mode`).
  Tests verify both `--check` and actual application, including reverse application (`-R`).
- **Scope**: The crash affects `git apply --check` and potentially other workflows (e.g., `--index`, `--cached`) if they rely on the same parsing logic. The fix is narrowly scoped to the parsing logic and does not appear to introduce new edge cases. Compatibility with patches generated by Git itself is preserved.

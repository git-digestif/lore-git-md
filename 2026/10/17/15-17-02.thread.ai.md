Thread identity: Bug report about a Git crash in `git apply --check` when processing a patch that creates a new file, now with a v4 two-patch fix series under review. Originating author: Gingrspacecadet (first-time contributor). Fix author: Tanga Joris. Thread type: bug report with proposed fix. Series version: v4 (reduced from three patches to two).

Core problem or goal: Git crashes with an assertion failure (`patch->is_new <= 0`) in `apply.c`'s `check_preimage` function when running `git apply --check` on patches with malformed headers. The issue stems from long-standing logic errors in how the apply machinery parses and validates new-file and deleted-file patches. Two distinct but related edge cases are addressed: (1) empty `diff --git` sections (a `diff --git` line followed by non-header content), now rejected immediately in `find_header()` (1/2), and (2) patches where `---` or `+++` lines appear before `new file mode` or `deleted file mode` lines, respectively, leading to inconsistent patch struct state (2/2). The crash affects released versions (confirmed in Git 2.43, 2.45.0, and current `master`). The fix fully aligns with Junio C Hamano's guidance to reject any patch header format not generated by `git diff` or `git format-patch`.

Current status: **v4 posted, under review with maintainer approval of patch 1/2**. Tanga Joris has submitted a two-patch series based on commit `77904e546de3bd940621092ecec47a88d0cede5d`, targeting `maint` and merging cleanly with `master`, `next`, and `seen`. v4 drops the v3 patch 1/3 (memory leak fix in `parse_git_diff_header()`) because the stricter validation in the new 1/2 makes that leak unreachable. Junio C Hamano has reviewed and endorsed v4 1/2 with "Looking good," confirming the implementation correctly saves `linenr` before calling `parse_git_diff_header()` so error diagnostics point at the `diff --git` line, and that returning `-128` allows `apply_patch()` to clean up via `free_patch()` without leaking `def_name`, `old_name`, or `new_name`.

Key technical details:
- **Subsystem**: `apply.c` (specifically `parse_git_diff_header`, `find_header`, and `check_preimage` functions).
- **v4 patch 1/2**: `find_header()` now rejects empty `diff --git` headers immediately. When encountering a `diff --git` line followed by any line that is not a git extended header line (including a blank line, indented header, another `diff --git`, or arbitrary text), it emits `error(_("corrupt patch: empty \"diff --git\" header at %s:%d"), state->patch_input_file, linenr)` and returns `-128`. Text between complete patches continues to be ignored unless a line starts with `diff --git `. Junio validated that saving `linenr` before `parse_git_diff_header()` ensures the error references the `diff --git` line itself rather than the terminating line, and that the `-128` return enables proper cleanup via `free_patch()`.
- **Root cause mechanism**: `parse_git_diff_header()` sets `patch->old_name` and `patch->new_name` from the `diff --git` line but then returns early on the next non-header line, leaving stale state; subsequently `parse_traditional_patch()` sets `is_new` for `--- /dev/null` without clearing `old_name`, causing the assertion failure in `check_preimage()`.
- **v4 patch 2/2**: Modifies `parse_git_diff_header()` to add validation checks at the end of the function: if `patch->is_new` is set but `patch->old_name` is also present, it rejects the patch with an error indicating `"---" before "new file mode"` at the recorded line number; likewise if `patch->is_delete` is set but `patch->new_name` is present, it rejects with `"+++" before "deleted file mode"`. This catches the inconsistent state where a `--- /dev/null` line appears before `new file mode` (causing `gitdiff_verify_name()` to populate `old_name` with `dev/null` before `is_new` is set), or where `+++ /dev/null` appears before `deleted file mode`. The error messages reference the offending `---` or `+++` header line and its line number rather than printing the stripped name, and the check returns `-128` to abort parsing. The commit message notes this mirrors the approach of commit `d70e9c5c8c` (2017), which added similar early rejection for other mutually exclusive header lines. The patch carries a `Helped-by` trailer from Siddharth Asthana.
- **Assertion**: `patch->is_new <= 0` in `check_preimage()`.
- **Input classification (per Junio)**: (1) malformed `diff --git` lines within Git-generated patches are rejected strictly; (2) non-patch material appearing between complete patches continues to be ignored; (3) lines beginning with `diff` that are not `diff --git` (third-party diff output) follow different parsing code paths and are left unchanged.
- **Historical context**: Git emitted bare `diff --git` lines only in 2005 (commit `206de27efa`); commit `ec1fcc16af` added the `index` line months later, and modern Git never generates empty `diff --git` sections.
- **Files touched**: `apply.c` (fixes), `t/t4133-apply-filenames.sh` (new test file).
- **Test coverage**: New test file `t/t4133-apply-filenames.sh` covers empty headers followed by another `diff --git`, blank lines after `diff --git`, indented `new file mode` lines, deletions with blank lines, modifications with blank lines, text before and after the empty header, consecutive `diff --git` lines, and header-ordering violations (both `--- /dev/null` and `--- a/f` before `new file mode`, and `+++ /dev/null` before `deleted file mode`), verifying behavior under both `--check` and actual application including `-R`, and confirming the error message references the correct file and line number. Junio acknowledged this comprehensive coverage in his review.

Open questions and loose ends: Junio identified one minor pre-existing edge case in v4 1/2: a trailing bare `diff --git` line at EOF with fewer than six remaining bytes still hits the earlier `size < len + 6` check and exits without emitting the new error message. He noted this as optional future work rather than a blocker. The series otherwise awaits further review or integration decisions.

Thread identity: Bug report about a Git crash in `git apply --check` when processing a patch that creates a new file. Originating author: Gingrspacecadet (first-time contributor). Thread type: bug report, now with a proposed fix under review after incorporating stricter validation, a memory leak fix, improved error messages, and full alignment with maintainer guidance. A v4 iteration is now being prepared based on the latest proposal.

Core problem or goal: Git crashes with an assertion failure (`patch->is_new <= 0`) in `apply.c`'s `check_preimage` function when running `git apply --check` on patches with malformed headers. The issue stems from long-standing logic errors in how the apply machinery parses and validates new-file and deleted-file patches. Two distinct but related edge cases are addressed: (1) stale `old_name`/`new_name` values due to early termination of `parse_git_diff_header()` while `find_header()` continues searching (addressed in 2/3), and (2) patches where `---` or `+++` lines appear before `new file mode` or `deleted file mode` lines, respectively, leading to inconsistent patch struct state (addressed in 3/3). The crash affects released versions (confirmed in Git 2.43, 2.45.0, and current `master`). The fix **fully aligns with Junio C Hamano's guidance** to reject any patch header format not generated by `git diff` or `git format-patch`, including `diff --git` lines in commit message bodies (which are explicitly out of scope for `git apply`).

Current status: **Fix proposed (v3 series), under review, with a v4 iteration now proposed to further simplify by dropping patch 1/3**. Tanga Joris has submitted a three-part patch series addressing root causes and edge cases, but now proposes that `find_header()` should stop and report a corrupt patch immediately when encountering a `diff --git` line with nothing after it (an empty section), rather than continuing to search. This would render patch 1/3 (the memory leak fix in `parse_git_diff_header()`) unnecessary and simplify patch 2/3 significantly. Tanga has verified that modern Git does not generate empty `diff --git` headers (tested with whitespace-only changes, renames, and merges) and that existing apply and am tests pass with this stricter behavior. The series remains based on `maint` and merges cleanly with `master`, `next`, and `seen`. Tanga is seeking explicit confirmation from Junio that this approach matches the intent before preparing v4.

Key technical details:
- **Subsystem**: `apply.c` (specifically `parse_git_diff_header`, `find_header`, and `check_preimage` functions).
- **Triggers**:
  1. A blank line or other non-header line (e.g., indented `new file mode`) after the `diff --git` header, followed by `--- /dev/null` before `new file mode`.
  2. Patches where `---` appears before `new file mode` (for new files) or `+++` appears before `deleted file mode` (for deletions).
  3. `diff --git` lines appearing in commit message bodies (now explicitly out of scope for `git apply`).
  4. Empty `diff --git` sections (a `diff --git` line with no content followed by another `diff --git`) -- now proposed for rejection in the v4 approach.
- **Root cause**: Inconsistent state in the `patch` struct due to (1) stale `old_name`/`new_name` values from early parsing termination, or (2) mutually exclusive header lines (`---`/`+++` before mode lines) that violate assumptions in `check_preimage()`. Junio C Hamano identified that `find_header()` fails to clear `patch->old_name`, `patch->new_name`, and related state when `parse_git_diff_header()` returns early after seeing a `diff --git` line followed by an unrecognized line.
- **Assertion**: `patch->is_new <= 0` in `check_preimage()`.
- **New v4 proposal**: Instead of fixing the memory leak in `parse_git_diff_header()` (patch 1/3), `find_header()` should die immediately upon encountering a `diff --git` line with nothing after it, treating empty sections as corrupt input. This eliminates the need for the separate memory leak fix and simplifies the validation logic.
- **Error message refinement**: Messages reference the problematic header lines (e.g., `"---" before "new file mode" at old_before_new.diff:4`) with line numbers, improving clarity for users.
- **Files touched**: `apply.c` (fixes), `t/t4133-apply-filenames.sh` (new test file).
- **Behavior**: The revised fix rejects malformed patches with clear, actionable error messages. The v4 approach would additionally reject empty `diff --git` sections outright, since modern `git diff`/`git format-patch` does not generate them.
- **Test coverage**: New test file `t/t4133-apply-filenames.sh` covers blank lines after `diff --git`, indented mode lines, empty diff sections, and header-ordering edge cases. Tests verify both `--check` and actual application, including reverse application (`-R`).

Open questions and loose ends:
- **Empty section handling**: Previously the sole uncontested edge case (accepted per 206de27efa), Tanga Joris now proposes rejecting empty `diff --git` sections outright, arguing that modern Git never generates them and that existing tests pass with this stricter behavior. This requires Junio's confirmation before v4 is prepared.
- **Implementation detail from maintainer**: Junio C Hamano has specified that `find_header()` must clear the patch struct (`patch->old_name`, `patch->new_name`, and related state) before continuing the search when `parse_git_diff_header()` returns early, rather than leaving stale state that causes the crash.
- **Test case adequacy**: Junio has rejected the proposed test case in patch 1/3 as inadequate because it only passes when both the bogus and legitimate `diff --git` lines reference the same file `g`; with a different filename the code emits an "inconsistent old filename" error. Tanga confirms this behavior and agrees corrupt input should be diagnosed as an error. With the v4 approach dropping patch 1/3, this specific test case concern becomes moot.

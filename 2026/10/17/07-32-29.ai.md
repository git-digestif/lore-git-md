This is the **core feature patch** in Jun Wu’s four-part series introducing `core.indexLockTimeout`. It implements the actual timeout logic in `repository.c`, adds the configuration knob (`core.indexLockTimeout`), and provides test coverage.

The patch makes commands like `git add`, `git checkout`, and `git commit` wait up to the configured timeout (default: 1 second) when the index lock is held, rather than failing immediately. The wait is skipped if the index was already read *by the same process* before locking, to avoid amplifying pre-existing write races (e.g., in `git commit` or `git reset`). This per-process rule is enforced by checking `repo->index->initialized`; if true, the timeout is forced to 0. The infrastructure also ensures that any in-memory index is force-dropped after acquiring the lock if it might be stale, addressing Junio’s edge-case concern about outdated data.

Files touched: `repository.c` (core logic), `repository.h` (API documentation), `Documentation/config/core.adoc` (config docs), `t/meson.build` (test registration), `t/t0031-lockfile-pid.sh` (test setup), `t/t0032-index-lock-timeout.sh` (new test script), and `t/t7400-submodule-basic.sh` (test adjustment). The new test script verifies the timeout behavior: immediate failure with `core.indexLockTimeout=0`, waiting with a positive timeout, and skipping the wait if the index was read before locking (as in `git commit`).

The patch is **well-scoped and conservative**: it does not alter behavior for commands that read the index before locking (e.g., `git rebase`, `git merge`), and it includes safeguards against stale data. The default timeout (1 second) remains open to debate, but the implementation is designed to be adjustable without code changes. Test coverage is adequate, and the patch is narrowly targeted to avoid regressions. **Worth attention** for users frustrated by lock contention in IDE workflows.

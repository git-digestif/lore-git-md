This is a bugfix targeting the config subsystem, addressing a long-standing usability and security issue. Junio C Hamano proposes making Git respect file permission bits when writing configuration files, so that `chmod a-w .gitconfig` actually prevents modification as users expect. The patch adds a simple `access(2)` check before creating a lockfile, returning a new `CONFIG_NO_WRITE` error if the file is unwritable. The implementation is straightforward and includes thorough test coverage, verifying that read-only config files can still be read but reject writes and unsets.

The motivation is clear and uncontroversial: Git's current lockfile-and-rename mechanism bypasses filesystem permissions, which violates user expectations and could lead to accidental data loss. The patch addresses this by explicitly checking write permissions before proceeding with any config modification. The accompanying test uses `GIT_CONFIG_GLOBAL` to avoid modifying the user's actual config files, demonstrating careful attention to isolation.

Junio notes the lack of responses to his RFC, expressing mild surprise that others haven't been annoyed by this behavior. This suggests the change is likely to be well-received once noticed, though the silence might indicate it hasn't been a widespread pain point in practice. The patch touches core config-writing machinery in `config.c` and adds comprehensive test coverage in `t/t1300-config.sh`, making it a solid, self-contained fix.

The implementation appears technically sound, introducing a new error code and modifying the key `repo_config_set_multivar_in_file_gently()` function. The change affects all config file writes (global, local, and system-level), so it's a fundamental improvement to Git's configuration system. While the patch is marked as RFC, the approach seems mature enough for serious consideration, with the main open questions likely being edge cases like filesystem race conditions or symbolic links rather than the core idea itself.

This is a rare case where the maintainer himself is proposing what amounts to a behavioral change in Git's core functionality. The fact that Junio is driving this suggests it's a deliberate improvement rather than an oversight, and the lack of controversy in the thread so far (despite no responses) implies this is a straightforward usability win.

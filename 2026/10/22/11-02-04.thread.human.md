This thread is about a documentation patch from Wasswa Edson that clarifies how Git's partial clone feature prioritizes promisor remotes advertised via Git protocol v2 during fetches. The patch adds a small clarification to `Documentation/technical/partial-clone.adoc`, specifying that these advertised remotes are tried first before falling back to other configured ones.

The patch hit a snag when Junio C Hamano raised a critical question: whether the documented behavior is actually implemented—and more importantly, whether it’s safe. Junio’s review pointed out that if a Git server can advertise a new, untrusted promisor remote to a client during the protocol exchange, this could pose a security risk. Wasswa responded by asserting that the implementation already includes safeguards to prevent arbitrary injection, and that clients must explicitly configure acceptance policies before any server-advertised remote is used. However, he hasn’t yet provided concrete evidence (like code references or test cases) to back up this claim, leaving the core question unresolved.

The thread is now at a standstill until Wasswa either demonstrates that the behavior is both implemented and secure or revises the documentation to reflect a different reality. No updated patch has been posted yet, and the security implications of server-advertised remotes remain the key sticking point. If the current documentation is inaccurate, the patch will need to be reworked—or possibly abandoned—depending on what the actual implementation supports.

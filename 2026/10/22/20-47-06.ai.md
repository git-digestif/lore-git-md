This is a **performance bugfix** for `git log --follow` in non-linear history. The patch is the fourth and final part of a series that addresses a severe regression introduced in commit `304812ed33` (June 2026), where `--follow` became unusably slow (6m43s vs. 28s) when tracking renames across merges.

The core issue is that `log_tree_diff()` now diffs each merge against *all* parents with rename detection enabled, even when the path is unchanged in some parents. The fix splits the diff into two passes: first, a fast pass without rename detection to find parents where the path is unchanged; only if the path differs in *all* parents does it fall back to the expensive rename-detection pass. A helper function, `follow_needs_renames()`, ensures that rename detection is still performed when a parent’s fork point with an unchanged parent shows the path was renamed or removed.

The patch touches only `log-tree.c`, adding ~90 lines of logic around the existing `log_tree_diff()` function. It introduces a new `commit_has_path()` helper to check path existence in a commit, and modifies `remember_follow_pathspec()` to prefer paths that actually exist in the commit when children disagree. The commit message reports a speedup from 6m43s to 36s on the Linux kernel repository, restoring performance close to the pre-regression baseline.

This is a targeted fix for a real-world usability problem, with a clear before/after benchmark and a well-explained algorithmic improvement. The code is self-contained and does not affect behavior outside `--follow` with merges.

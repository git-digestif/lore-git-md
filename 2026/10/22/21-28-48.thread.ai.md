Subject: [PATCH 0/5] glossary & docs: align "pseudoref" vs "root ref" terminology
Series version: v2 (5 patches, addressing review feedback and incorporating Julia Evans’s `gitdatamodel.adoc` proposal)
Originating author: Andy Koppe
Thread type: patch series (documentation/terminology cleanup)

Core problem or goal
Align Git’s documentation, code comments, and tests with the 2024 terminology change (commit 993d57eded) that narrowed "pseudoref" to FETCH_HEAD and MERGE_HEAD only, while introducing "root ref" for refs outside the "refs/" hierarchy (e.g., HEAD, ORIG_HEAD). The series updates the glossary, man pages, built-in commands, refs internals, test scripts, and pedagogical documentation to replace outdated uses of "pseudoref" with "root ref" and correct related inaccuracies in reflog and per-worktree ref documentation. Julia Evans’s proposal to expand the "References" section of `gitdatamodel.adoc` is incorporated, explicitly covering pseudorefs and root refs to address a gap where the data-model guide previously only mentioned ORIG_HEAD in passing.

All five patches remain uncontroversial and appear ready for merging after addressing all review feedback from Junio C Hamano and Patrick Steinhardt, except for two unresolved documentation nits in Patch 3/5. Key technical details
- Files touched: 24 total in v2—glossary (Documentation/glossary-content.txt), man pages (git-update-ref.1, git-worktree.1, git-ls-remote.1, for-each-ref-options.7, rev-list-options.7, config/core.adoc), built-in commands (builtin/for-each-ref.c), refs internals (refs.h, revision.c), test scripts (t/t1400-update-ref.sh, t/t1415-worktree-refs.sh, t/t1460-refs-migrate.sh, t/t4013-diff-various.sh, t/t9902-completion.sh), completion script (contrib/completion/git-completion.bash), and pedagogical documentation (Documentation/gitdatamodel.adoc).
- New glossary entries: "root ref" (formal definition: refs located in the root of the ref hierarchy, e.g., HEAD, ORIG_HEAD), updated "pseudoref" (now limited to FETCH_HEAD/MERGE_HEAD, explicitly listing supported operations—direct reading via `git log`/`git diff`—and unsupported ones—no `git-update-ref` or `git-for-each-ref`). The "ref" entry no longer includes naming rules or irregular root refs, which are now covered under "root ref". The glossary explicitly states that pseudorefs are *not* refs, cannot be written by `git-update-ref` or listed by `git-for-each-ref`, and yield the first object ID when they contain multiple entries. It cross-references `gitrevisions(7)` for descriptions of commonly used root refs and pseudorefs. The latest refinement clarifies that pseudorefs *may contain multiple hashes* (with FETCH_HEAD as the example) and that commands like `git log` use the first hash when multiple entries are present. Junio’s latest reply further distinguishes the on-disk format: root refs (e.g., ORIG_HEAD) contain only a single object ID or symbolic ref and behave like normal refs except for their location outside `refs/`, while pseudorefs (FETCH_HEAD, MERGE_HEAD) can describe multiple objects and include metadata (e.g., branch names and "not-for-merge" flags). Root refs are treated as real refs by Git’s internals (e.g., reftable support), whereas pseudorefs are not. FETCH_HEAD’s multi-line format is cited as an example of pseudoref metadata. The "root" terminology is noted as a slight misnomer, as Git would technically accept any file under `.git/` as a ref if it contains a valid object ID, but only project-sanctioned ones (HEAD, ORIG_HEAD, etc.) are officially supported.
- Symbols: `__git_pseudoref_exists()` in contrib/completion/git-completion.bash left unchanged (comment updated only); `REFS_FOR_EACH_INCLUDE_ROOT_REFS` in refs.h now lists root refs explicitly in its comment. The help text for `git for-each-ref --include-root-refs` now says "root refs" instead of "HEAD ref and pseudorefs".
- Test coverage: updated test scripts to use new terminology; expected output in `t4013-diff-various.sh` updated to reflect renamed test refs (PSEUDOREF -> ROOT_REF_HEAD, REVERSE -> REVERSE_HEAD). No new test cases added.
- Per-worktree ref clarification: Patch 2/5 updates the "per-worktree ref" entry to use itemized AsciiDoc lists for root refs (HEAD, ORIG_HEAD, etc.), refs under refs/worktree/, and refs under refs/rewritten/, and clarifies that pseudorefs are also worktree-specific. The "worktree" entry now describes HEAD as a per-worktree ref and MERGE_HEAD as a pseudoref, with a cross-reference to git-worktree(1). The prose list of per-worktree refs is now formatted as an itemized AsciiDoc list for better readability and future extensibility.
- Documentation updates in Patch 3/5: Six man pages (`git-update-ref(1)`, `git-worktree(1)`, `git-ls-remote(1)`, `for-each-ref-options(7)`, `rev-list-options(7)`, `config/core.adoc`) now consistently use "root ref" for HEAD/ORIG_HEAD, clarify that `--refs` in `git-ls-remote` omits refs outside `refs/`, and correct minor inaccuracies (e.g., removing ORIG_HEAD from `git-update-ref(1)`’s reflog documentation, correcting `core.logAllRefUpdates` scope to include root refs). `git-worktree(1)` now explicitly states that both root refs and pseudorefs are per-worktree and drops the outdated claim that they live directly under `$GIT_DIR` (which doesn’t hold for reftable). `git-ls-remote(1)` fixes a typo ("symbolics" → "symbolic refs"). Julia Evans’s proposal to expand the "References" section of `gitdatamodel.adoc` is now incorporated, explicitly covering pseudorefs and root refs to address the prior gap in the data-model guide. The updated `gitdatamodel.adoc` now includes FETCH_HEAD as an example of a pseudoref containing multiple hashes and clarifies that commands like `git log` use the first hash when multiple entries are present.
- Patch 4/5 updates in-code comments and help text in `builtin/for-each-ref.c`, `contrib/completion/git-completion.bash`, `refs.h`, and `revision.c` to replace outdated uses of "pseudoref" with "root ref" where appropriate. The bash-completion script’s comments clarify that `__git_pseudoref_exists()` covers both root refs and pseudorefs (though the function name itself is left unchanged). The commit message for Patch 4/5 is now tightened per Patrick Steinhardt’s feedback, removing redundant explanations of the diff’s contents.

Open questions and loose ends

Andy acknowledges these issues but considers them out of scope for this series, deferring broader documentation updates to a future effort. Patrick Steinhardt’s suggestion to replace the detailed explanation with a cross-reference to `git-config(1)` is not implemented.
- The glossary’s "pseudoref" entry no longer includes the "different semantics" phrasing objected to by Junio and Patrick, but Julia Evans’s follow-up questions have sharpened the definition by explicitly noting that pseudorefs *may contain multiple hashes* (with FETCH_HEAD as the example) and that commands like `git log` use the first hash when multiple entries are present. Junio’s latest reply further clarifies the on-disk format distinction, reinforcing that pseudorefs can include metadata (e.g., branch names and "not-for-merge" flags) while root refs contain only a single object ID.

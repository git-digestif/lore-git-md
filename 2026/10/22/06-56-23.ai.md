This is the second patch in Harald Nordgren’s four-patch **bugfix series** for `git imap-send`, addressing a long-standing interoperability issue with tools like `b4`. The patch rewrites the header-parsing logic in `imap-send.c` to accept `From`, `Date`, and `Subject` headers in any order, fixing a failure when `Subject` precedes `Date` (a valid but non-canonical order produced by `git send-email` and other tools). The change is minimal and focused: it replaces a brittle `strstr`-based search with a new helper function, `has_required_headers()`, which scans the header block for the three required headers regardless of order. The accompanying test in `t/t9001-send-email.sh` verifies the fix by feeding a patch with `Subject` before `Date` into `git imap-send` and confirming it is accepted.

The patch is well-motivated and clearly explains the problem: `b4 mbox --single-message` (and similar workflows) produce messages that `git imap-send` previously rejected, breaking round-trip workflows. The new logic is order-agnostic and uses `starts_with()` for exact prefix matching, avoiding case-sensitivity issues (though case-insensitive matching is deferred to Patch 4/4). The test coverage is thorough, exercising both the new code path and the existing `--imap-sent-folder` workflow to ensure no regressions. The commit message explicitly ties the change to the broader goal of RFC 5322 compliance and interoperability with `b4`.

This patch is uncontroversial and ready for integration. It is part of a series where Patch 1/4 (tunnel process lifecycle fix) is already merged to `next`, and Patches 3-4/4 (removal of the `git-send-email` special case and case-insensitive header matching) are isolated for separate review. The structural improvements in `v3` make the changes easier to assess, and the series as a whole resolves all previously open technical questions. The patch touches only `imap-send.c` and the test suite, with no on-disk format changes or new symbols beyond the `has_required_headers()` helper. The test prerequisite handling is marked as `#leftoverbits` for future work, but this does not affect the correctness of the fix.

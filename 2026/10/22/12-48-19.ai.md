This is a follow-up in the ongoing `git switch`/`git checkout` tracking-configuration failure thread, focusing on control flow and atomicity.

D. Ben Knoble acknowledges 井上司’s clarification about the sequence of operations in branch-switching commands. He now understands that `merge_working_tree()` updates the worktree and index on *every* branch switch (not just when `-m` is used), because the `do_merge` flag defaults to 1. This explains why the worktree and index are updated before HEAD is moved, leaving the repository in an inconsistent state if a later step (like writing tracking configuration) fails. Knoble muses whether reordering these steps—moving worktree/index updates later in the sequence—would be feasible, but notes this would only be a partial fix, not a true atomic solution.

The email reinforces the broader control flow issue: the current sequence (update worktree/index, create ref, write tracking config, then update HEAD) means any failure after worktree/index updates but before HEAD movement leaves the repository in a broken state. This affects both the tracking-configuration case and the `-m` conflict case, where HEAD remains on the old branch, files are left conflicted, and changes stay in the stash. Knoble’s observation highlights that the problem is not just about `setup_tracking()`’s error handling, but about the fundamental order of operations in the checkout/switch control flow. The thread’s focus remains on whether an incremental fix (returning an error from `setup_tracking()`) is sufficient for now, or if a more comprehensive restructuring is needed.

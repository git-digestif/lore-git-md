## 2026/11/02

- [2026/11/02/18-19-57 by Julia Evans <julia@jvns.ca>] Julia Evans asked what distinguishes root refs like ORIG_HEAD from pseudorefs like MERGE_HEAD, noting that in .git during a merge conflict both appear as plain files (FETCH_HEAD, HEAD, MERGE_HEAD, ORIG_HEAD) and so naively look stored the same way.
- [2026/11/02/19-47-48 by Andy Koppe <andy.koppe@gmail.com>] Andy Koppe answered the distinction: root refs can be stored in reftables, hold a single hash or a single symbolic ref, and can be modified with git update-ref and listed with git for-each-ref; pseudorefs are always files in .git, may contain multiple hashes (FETCH_HEAD also annotates each hash with fetch metadata), are written only by fetch/merge/pull, and cannot be listed; both types can be passed to git log, git diff or git checkout like refs under refs/.
- [2026/11/02/21-00-48 by Julia Evans <julia@jvns.ca>] Julia Evans called the explanation helpful, suggested the documentation include "may contain multiple hashes", and asked whether a command given a multi-hash pseudoref uses the first hash and whether FETCH_HEAD and MERGE_HEAD are the only pseudorefs.
- [2026/11/02/21-49-00 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano explained that a pseudoref cannot be treated as a true ref because it can describe multiple objects (illustrating with a FETCH_HEAD listing including not-for-merge entries), whereas a root ref describes exactly one object and is special only in living outside the refs/ hierarchy; he also noted ORIG_HEAD is accepted via the same mechanism as arbitrary $GIT_DIR paths, and asked Julia Evans to trim her long quote.
- [2026/11/02/22-19-53 by Andy Koppe <andy.koppe@gmail.com>] Andy Koppe answered Julia Evans's two questions by citing the v2 pseudoref glossary entry: FETCH_HEAD and MERGE_HEAD are the pseudorefs known to Git, and when a pseudoref contains more than one object ID, using it to refer to an object yields the first one.

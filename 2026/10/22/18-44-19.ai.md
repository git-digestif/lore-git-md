This is the first patch in Mihai Cosma’s two-patch series fixing index locking behavior in `git status`. It addresses a silent data-loss bug in the `index.skipHash` code path (enabled in Scalar repositories and with `feature.manyFiles`), where `git status` could overwrite concurrent index updates without detection.

The patch restores stat-data verification in `verify_index_match()` for the `index.skipHash` case. When the index checksum is null (as it is with `index.skipHash`), the code now checks that the index file’s stat data (inode, mtime, size, etc.) hasn’t changed since it was read, instead of relying on the checksum. This prevents `git status` from silently reverting staged changes made by another process between the time `git status` reads the index and when it writes it back. The patch also copies the stat data when `unpack_trees()` builds a new index, ensuring the verification works correctly in all cases.

The change is minimal and focused: it adds a new `file_stat` field to `struct index_state`, populates it during index read/write, and introduces a helper function `index_file_unchanged()` to compare stat data. The test coverage is thorough, with a new test in `t/t7508-status.sh` that verifies the fix works for both `index.skipHash=true` and `index.skipHash=false`, including edge cases with fsmonitor hooks.

This is a clear correctness fix that could be merged independently to `maint`. The commit message includes a concise reproduction script demonstrating the bug, and the code changes are straightforward and unlikely to introduce regressions. The only platform-specific caveat is on Windows, where the stat-data check relies on mtime and size (since inode numbers aren’t available), but the trade-off is justified: a false positive (skipping an opportunistic write) is preferable to a false negative (silently discarding staged changes).

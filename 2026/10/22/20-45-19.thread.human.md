This thread is about a patch series from Miklos Vajna that aims to improve the performance of `git log --follow` when tracking file history through complex merge topologies, such as diamond merges. The series also fixes two bugs: one where `--follow` loses history on the second parent of a merge, and another where `git log -m --follow` behaves incorrectly. The current version, v3, includes a new test case and a more granular split of the refactoring steps.

The series has received substantive review from Patrick Steinhardt, who identified a regression in the final patch (4/4). This regression causes the rename-following logic to fail when a merge keeps the renamed path but the other side edits the old path. Patrick provided a test script that reproduces the bug, showing that the patch loses history for edits on the side of the merge that was not taken. This is a significant correctness issue that will need to be addressed before the series can proceed. Patrick’s review was detailed and tested, focusing on the control-flow flaw in the new `follow_needs_renames()` helper function.

So far, the series has not been conditionally approved, and there are no benchmark numbers to quantify the performance improvements. The key technical changes involve `log-tree.c` and a new test file, `t/t4219-log-follow-merge.sh`, which covers merge/rename edge cases. The author has not yet responded to Patrick’s suggestion to split patch 3/4 into smaller, issue-specific changes, nor has the potential interaction with other log-related features like `--stat` or `--patch` been addressed. The thread is currently focused on resolving the regression before moving forward.

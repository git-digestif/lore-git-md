This thread is about improving the performance of `git log --follow` when tracking file history through complex merge topologies, particularly diamond merges. Miklos Vajna authored a patch series that also fixes two bugs: history loss on the second parent of a merge and incorrect behavior with `git log -m --follow`. The series is now at version 4, expanded to six patches after addressing a regression identified by Patrick Steinhardt in the previous version.

The key change in v4 is a fix for the regression where `git log --follow` would lose history when one side of a merge renamed a file and the other side edited the old name. Miklos kept this fix separate (patch 6/6) to avoid complicating the performance improvements. He also fixed a second bug (patch 1/6) where `--diff-merges=first-parent` combined with `--follow` would lose history. The Linux kernel repository still shows a 37-second runtime with the fix applied, though no formal benchmarks have been shared. Patrick Steinhardt, the primary reviewer, has no new technical objections but requests better adherence to mailing-list norms, such as replying inline to feedback and providing a `range-diff` for future iterations.

The series is under active review, with the regression fix and first-parent bug fix addressing Patrick’s earlier concerns.

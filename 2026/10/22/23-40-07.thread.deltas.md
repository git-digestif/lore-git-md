# Thread deltas

## 2026/10/22

## 2026/10/23

- [2026/10/23/12-19-01 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt reviewed Justin Tobler's patch to merge the "loose-object-idx" file during tmp-objdir migration, calling the approach "sensible" and the tmp-objdir.c change "makes sense", while raising objections: the lock timeout of -1 could block indefinitely on a stale lockfile; appending data under the lock risks corruption on partial writes, so the usual lockfile-write-rename pattern should be used instead; the file is unsorted and readers apparently must read all mappings; and merging should verify that object IDs being added don't already exist. He also noted the "index" name is confusing (it's really a map) but can't be changed now, suggested "object directory" instead of "database", asked whether child processes writing to the quarantine directory is a real scenario, and agreed entries shouldn't be written to the main ODB index before objects exist, while noting housekeeping never prunes mappings — a problem for another day.
- [2026/10/23/21-25-12 by Justin Tobler <jltobler@gmail.com>] Justin Tobler responded to the review: he will fix "object directory" wording and may call the file a "mapping file" in the commit message; confirmed the child-process case is real (git-receive-pack(1) can spawn git-unpack-objects(1) writing loose objects and mapping entries into the quarantine); agreed no pruning logic exists and the mapping file only grows, treating it as a separate problem not tackled here; defended the defensive header check in loose_object_idx_merge() as the function being unaware of its use case, but said he is happy to remove it; explained the -1 timeout and append-under-lock were copied from write_one_object() and asked whether to make the timeout configurable or set 1000ms (possibly also changing write_one_object() to match), and said he can adapt to the lockfile-write-rename pattern; explained readers use an in-memory hash map reloaded on miss, so the unsorted file is a preexisting quirk not addressed here; and noted duplicate-entry verification is absent in write_one_object() too (only a race could duplicate entries), a preexisting issue he can address separately if reviewers feel strongly.

## 2026/10/26

- [2026/10/26/06-39-02 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt accepted the defensive header validation of the source "loose-object-idx" as at least reasonable given that the function is called with arbitrary paths, agreed that making the lock timeout configurable (e.g. 1000ms instead of blocking indefinitely with -1) would be a good idea, but called the current append-under-lock write pattern "quite broken" since a partial write could corrupt the file once the compatibility hash becomes useful, preferring to fix it rather than follow the same broken pattern as `write_one_object()`. He also agreed the unsorted file (requiring a linear scan of all mappings on lookup misses) is a preexisting quirk outside this series' scope, and enumerated four problems with the mechanism — unsorted file, no deduplication, no pruning, non-atomic writes — saying the first three are conceptual issues not required in this series, but the non-atomic writes he would like fixed in this series (though he won't insist on it).
- [2026/10/26/17-58-24 by Justin Tobler <jltobler@gmail.com>] Justin Tobler confirmed the defensive check understanding, committed to using a 1000ms lock timeout in the next version, agreed the existing problems exist, and committed to making the "loose-object-idx" writes in this patch atomic in the next version — while holding off on also making `write_one_object()` atomic, citing a possible performance regression from rewriting a potentially large mapping file for every loose object written outside a batched transaction.

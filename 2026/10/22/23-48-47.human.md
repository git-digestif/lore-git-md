This is a bugfix discussion targeting the `git switch` and `git checkout` commands. 井上司 (Tsukasa Inoue) follows up on D. Ben Knoble’s question about whether reordering the worktree update step would help, confirming that it would merely shift the cleanup burden without achieving true atomicity.

The email walks through two concrete test cases. In **Case A** (a local change conflicts with the switch), the command fails early, leaving no half-finished state. In **Case B** (a lock file blocks branch creation), the worktree and index are updated but HEAD remains on the old branch, producing the same inconsistent state the thread is trying to fix. 井上司 also notes that HEAD updates themselves can fail, compounding the problem.

The message reaffirms that the current control flow—update worktree/index, create ref, write tracking config, then update HEAD—is inherently fragile. While the linked series (https://lore.kernel.org/git/pull.2275.git.1792637495.gitgitgadget@gmail.com/) already addresses the tracking-config failure by making the command succeed without tracking, full atomicity (rolling back worktree and ref on any later failure) remains a separate, longer-term effort. Junio has already endorsed the incremental approach, so this email is essentially a technical deep-dive for anyone still weighing the trade-offs.

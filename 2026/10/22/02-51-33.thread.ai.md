Subject: [PATCH 0/2] Fix inconsistent branch switch behavior on tracking config failure

Originating author: tsukasa-ino (via GitGitGadget)

Core problem or goal
Git’s `git switch -c` and `git checkout -b` commands currently leave the repository in an inconsistent state when they fail to write the tracking configuration (e.g., due to a stale `.git/config.lock`). The worktree and index are updated, the new branch ref is created, but HEAD remains on the old branch. The goal is to make the operation non-atomic but consistent: if the tracking config cannot be written, the switch still completes and Git exits with status 0, matching the behavior of `git push -u`, `git clone`, and `git fetch`. The `git branch` command retains its stricter error handling.

Current status
Under review; no merge status reported. Patch 1/2 refactors `setup_tracking()` in `branch.c` to return an error instead of calling `exit()`, and updates its callers (`create_branch()` and `dwim_and_setup_tracking()`) to propagate the error. Patch 2/2 modifies `builtin/checkout.c` to ignore the tracking config failure and finish the switch, and updates the test suite (`t2027-checkout-track.sh`, `t2060-switch.sh`, `t3200-branch.sh`) to verify the new behavior. The series is uncontroversial and aligns with the direction previously agreed in the bug report thread.

Key technical details
- Files touched: `branch.c`, `branch.h`, `builtin/branch.c`, `builtin/checkout.c`
- Subsystems: checkout, branch
- New behavior: branch switch completes even if tracking config write fails; exit status 0 (patch 2/2)
- Old behavior: branch switch aborts, leaving HEAD on the old branch

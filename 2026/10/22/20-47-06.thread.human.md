This thread is about a performance regression in `git log --follow` that made the command unusably slow (6m43s vs. 28s) when tracking renames across merges in non-linear history. The issue was introduced in June 2026 by commit `304812ed33` and is now being fixed by Miklos Vajna with the fourth and final patch in a series.

The root cause is that `log_tree_diff()` now unnecessarily enables rename detection for *all* parents of a merge, even when the path is unchanged in some. The fix optimizes this by first running a fast pass without rename detection to identify parents where the path is unchanged; rename detection is only used if the path differs in *all* parents. This restores performance to near pre-regression levels (36s on the Linux kernel repository) while preserving correctness. The patch is self-contained to `log-tree.c` and introduces helpers like `follow_needs_renames()` and `commit_has_path()` to implement the two-pass diff strategy.

The series has addressed a real-world usability problem with a clear benchmark and a well-explained algorithmic improvement.

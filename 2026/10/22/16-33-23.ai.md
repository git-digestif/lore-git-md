This is Junio C Hamano’s follow-up in the `git branch --delete-merged` squash/rebase detection thread, responding to Harald Nordgren’s proposal for a minimal `--delete-irrelevant` flag. Junio raises two key points: naming and option granularity.

First, he objects to the negative connotation of "irrelevant" and suggests a more positive alternative like `--delete-integrated` (though he does not endorse it outright). The naming discussion is now open for input from other contributors.

Second, he argues that the detection modes should form a clear hierarchy—each broader mode should include all narrower ones—rather than being independent toggles. His proposed structure is `--delete-foo=merged` (strict tip-reachability, equivalent to `--delete-merged`), `--delete-foo=rebased` (includes rebased branches), and `--delete-foo=squashed` (includes squash-merged branches *and* all previous modes). This design ensures users don’t accidentally exclude branches that were merged normally when opting into looser detection. Junio’s example highlights the confusion that could arise if `--delete-foo=squashed,rebased` failed to delete a branch that would have been caught by `--delete-merged`.

The email does not address algorithmic trade-offs (e.g., patch IDs vs. tree-based diffing) or performance concerns, but it refines the CLI design debate by introducing a structured, user-friendly hierarchy. The next steps will likely involve revisiting the patch series to implement this granular, hierarchical approach—assuming the naming and structure gain consensus.

This thread is about a small but long-standing inconsistency in Git’s branch-switching behavior. When `git switch -c` or `git checkout -b` fails to write the tracking configuration (for example, because `.git/config.lock` is stale), the command currently leaves the repository in an inconsistent state: the worktree and index are updated, the new branch ref is created, but HEAD remains on the old branch. The series, authored by tsukasa-ino, fixes this by making the operation complete successfully even if the tracking config can’t be written, matching the behavior of `git push -u`, `git clone`, and `git fetch`.

The fix is split into two patches. The first refactors `setup_tracking()` in `branch.c` to return an error instead of calling `exit()`, and updates its callers to propagate the error. The second patch modifies `builtin/checkout.c` to ignore the tracking config failure and finish the switch, and adds tests to verify the new behavior. The tests simulate a locked config file and confirm that the switch completes, HEAD is updated, and the worktree and index remain consistent. The `git branch` command retains its stricter error handling, which is also tested.

The series is under review and uncontroversial. Junio Hamano previously reviewed the larger series and requested the split, but hasn’t explicitly approved or objected to this version. The change is well-motivated, surgically targets the edge case, and aligns with the direction agreed in the earlier bug report thread. No open questions or objections have been raised so far.

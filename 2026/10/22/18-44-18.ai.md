This is a two-patch bugfix series targeting the index locking behavior of `git status`. The patches address a long-standing usability issue where `git status` holds `index.lock` for its entire duration, blocking concurrent operations like `git add` or `git commit`. The series also fixes a silent data-loss bug in the `index.skipHash` code path (enabled in Scalar repos and with `feature.manyFiles`) where `git status` could overwrite concurrent index updates without detection.

Patch 1 ("read-cache: verify skipHash index by stat data") is a standalone bugfix that plugs a hole in the `index.skipHash` optimization. Currently, when `index.skipHash` is enabled, the check that prevents `git status` from clobbering a concurrently modified index is bypassed, allowing `git status` to silently revert staged changes. The patch restores the stat-data-based verification, ensuring the index is only updated if it hasn’t changed since being read. This is a clear correctness fix that applies cleanly to `maint` and could be merged independently.

Patch 2 ("status: lock the index only to write it") is the main performance improvement. It restructures `git status` to hold `index.lock` only when it has detected changes that require writing the index back (e.g., untracked cache updates or refresh_index() modifications). In the common case where the index is clean, `git status` now runs without holding the lock at all. The commit message includes detailed benchmarking showing the impact: in a large repository (gcc, 124k files), concurrent `git add` operations went from failing 50-60% of the time to near-zero failures, with median latency improving from ~114ms to ~128ms (the slight regression in the clean case is outweighed by the elimination of lock contention).

The series is well-motivated and technically sound. The commit messages are thorough, including reproduction steps for the bug, benchmark methodology, and discussion of interactions with Jun Wu’s concurrent "Wait for the index lock" series. The code changes are focused: Patch 1 adds a stat-data check in `verify_index_match()`, while Patch 2 moves the lock acquisition in `cmd_status()` to just before `write_locked_index()`. The new test in `t/t7508-status.sh` covers both the bugfix and the locking behavior, including edge cases with `index.skipHash` and split index.

This is a clear win for usability in large repositories and Scalar deployments, where the current behavior is actively harmful. The patches are small, self-contained, and unlikely to introduce regressions. The only potential conflict is with Jun Wu’s series, but the author has already indicated willingness to rebase. The series looks ready for `next`.

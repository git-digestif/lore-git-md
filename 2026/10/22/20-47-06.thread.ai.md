Core problem or goal
The thread addresses a severe performance regression in `git log --follow` introduced by commit `304812ed33` (June 2026). When tracking renames across merges, `--follow` became unusably slow (6m43s vs. 28s on the Linux kernel repository). The goal is to restore performance close to the pre-regression baseline without altering behavior outside `--follow` with merges.

Current status
The series is at v4, with this patch being the final part. The prior three patches in the series are not detailed in this summary, but this patch is self-contained and implements the core fix. No merge status is reported; the series is under review.

Key technical details
- **Files touched**: `log-tree.c` only (~90 lines added).
- **New symbols**: `follow_needs_renames()` (helper to determine if rename detection is needed), `commit_has_path()` (checks path existence in a commit).
- **Behavior change**: `log_tree_diff()` now splits diffing into two passes: a fast pass without rename detection to identify parents where the path is unchanged, and a fallback to the expensive rename-detection pass only if the path differs in *all* parents.
- **Modified logic**: `remember_follow_pathspec()` now prefers paths that exist in the commit when children disagree.
- **Performance impact**: Benchmarked speedup from 6m43s to 36s on the Linux kernel repository.
- **On-disk format**: No changes.
- **Test coverage**: Not explicitly mentioned in the summary, but the regression is real-world and the fix is benchmarked.

This is a review comment in an ongoing RFC thread about extending `git branch --delete-merged` to handle branches whose upstream has been deleted by the hosting service. The reviewer, D. Ben Knoble, engages with the design proposals but does not implement or test the code.

The thread’s core problem remains: `git branch --delete-merged` currently refuses to delete local branches whose upstream is gone, even when those branches are provably merged into a user-specified ref (e.g., `origin/master`). The author, DonQuinleone, proposed two shapes: (A) a modifier `--into origin/master` to `--delete-merged`, or (B) composable filters like `--upstream-gone --merged=origin/master` to `-d`.

D. Ben Knoble’s reply is substantive but focused on interface design rather than implementation. He argues that (A) makes the CLI more complex by introducing a context-dependent modifier (`--into`), and suggests instead using `--option=value,value,value` syntax (e.g., `--delete-merged='origin/*,into:origin/master'`) to keep the interface composable and avoid new flags. He also briefly critiques GitHub’s triangular workflow, noting that `push.default=current` or similar settings would make upstream configuration more intuitive in such cases.

The review does not address edge cases, test coverage, or the underlying code changes, but it does raise a clear point of contention: whether the feature should be implemented as a modifier to an existing option or as a composable filter. This is likely to be a key discussion point as the RFC evolves.

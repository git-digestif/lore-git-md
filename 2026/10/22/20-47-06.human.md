This is a performance bugfix for `git log --follow` in merge-heavy repositories. The patch is the fourth and final part of a v3 series that addresses a severe regression introduced in commit 304812ed33 (June 2026): when `--follow` is used on a file with a non-linear history, the command can become 14× slower—turning a 28-second operation into nearly seven minutes on the Linux kernel repository.

The root cause is that `log_tree_diff()` now diffs every merge against *all* of its parents with full rename detection enabled, even when the file in question is unchanged relative to one or more parents. The fix splits the diff into two passes: first, a cheap check without rename detection to find any parent where the file is unchanged; if such a parent exists, the code follows that history and only performs the expensive rename detection against the remaining parents when absolutely necessary (e.g., when the file was renamed on a side branch). A small helper, `remember_follow_pathspec()`, is also tweaked to prefer the path that actually exists in the current commit when children disagree.

The result is a 11× speed-up on the reported test case (36 s vs. 6 m 43 s), bringing performance back close to the pre-regression baseline. The patch touches only `log-tree.c` and adds about 90 lines of new logic; no new options or user-visible behavior are introduced. The commit message is clear and includes a concrete reproduction recipe, making it easy for reviewers to verify the fix.

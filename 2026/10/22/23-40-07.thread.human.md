This thread is about a bugfix patch from Justin Tobler that addresses a data-loss issue in Git's ODB transaction layer. The bug occurs when migrating loose objects from a temporary directory in repositories using compatibility hashes (e.g., SHA-1/SHA-256 interop) with batch fsync enabled. The patch introduces a new function, `loose_object_idx_merge()`, to safely append new mapping entries to the primary index instead of overwriting it.

The patch is under active review, with Patrick Steinhardt providing substantive feedback on locking, atomicity, and edge cases. Justin has responded to these concerns, agreeing to adjust the locking mechanism (including potentially making the timeout configurable) and explore Git's standard temp-file-then-rename pattern for safer atomic updates. However, issues like file corruption risks from partial writes and duplicate entry handling remain unresolved, as Justin considers them preexisting problems outside the scope of this fix. The discussion also clarified that child processes (e.g., `git-unpack-objects`) can write to quarantine directories, which the patch must account for.

The patch is likely to require a second version (v2) to address the feedback, particularly around locking and merge safety. It includes a regression test (`t/t1016-compatObjectFormat.sh`) to verify the fix, but the core logic still needs refinement. This work is part of Patrick Steinhardt's broader ODB abstraction effort and touches the in-flight compatibility-hash feature, so it’s worth tracking for future updates. No merge decisions have been made yet, and the patch is not yet ready for integration.

This thread is about a critical bugfix in Git’s object database (ODB) transaction layer, authored by Justin Tobler. The bug occurs when migrating loose-object index files (used for SHA-1/SHA-256 compatibility) under batch fsync, leading to potential data loss if a preexisting index exists. The patch, currently under review, addresses the immediate issue but has faced substantive feedback from Patrick Steinhardt, who identified blocking concerns around atomicity and locking.

A second version (v2) is confirmed and will adopt Git’s standard temp-file-then-rename pattern to prevent corruption from partial writes, replacing the current append-under-lock approach. It will also switch from an indefinite lock timeout to a finite 1000ms default. While the patch includes a strong regression test (`t/t1016-compatObjectFormat.sh`), the deeper design flaws in the loose-object-idx mechanism—unsorted files, no deduplication, and no stale entry pruning—remain deferred, though Patrick has flagged them as serious long-term risks. Justin has agreed to the v2 adjustments but notes potential performance trade-offs for operations writing many loose objects.

The fix is part of Patrick Steinhardt’s broader ODB abstraction effort and is high-priority for stabilizing the compatibility-hash feature, which is still in flight. The next step is tracking v2 closely, particularly how it balances atomicity with performance.

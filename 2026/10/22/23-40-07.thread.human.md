This thread is about a critical bugfix for Git’s object database (ODB) transaction layer, authored by Justin Tobler. The issue occurs when migrating temporary object directories under specific conditions: Git configured with a compatibility hash (e.g., SHA-1/SHA-256 interop) and batch fsync of loose objects enabled. The bug causes the "loose-object-idx" file—a mapping between objects and their compatibility hashes—to fail to merge correctly when a preexisting index exists in the primary object directory, leading to ODB transaction failures and potential data loss.

The series is now in its second version (v2), a four-patch set that addresses all blocking feedback from Patrick Steinhardt, the primary reviewer. Patches 1/4 (locking timeout) and 2/4 (parsing refactor) are effectively approved, while patch 3/4 (writing refactor) is uncontroversial. The core fix in patch 4/4 replaces the risky append-under-lock pattern with Git’s standard temp-file-then-rename approach, ensuring atomic writes and eliminating corruption risks. Other key improvements include a finite lock timeout (1000ms) to avoid hangs, stricter error handling, and a regression test (`t/t1016-compatObjectFormat.sh`) to verify the fix.

In the latest exchange, Patrick Steinhardt provided final feedback on patch 4/4, suggesting a minor optimization to reduce lock contention by reading the source loose-object-idx file outside the critical section. He also requested a clarifying comment for the new `loose_object_idx_merge()` function. These are non-blocking polish items, and Justin is expected to send a v3 incorporating them. The series remains a high-priority fix for ODB stability, targeting the current integration cycle. While deeper design flaws in the loose-object-idx mechanism (unsorted files, no stale-entry pruning) are acknowledged, they are deferred to future work. The fix is now finalized and ready for integration once the minor feedback is addressed.

This thread is about a bugfix for Git’s object database (ODB) transaction layer, specifically a failure in the temporary object directory migration logic when Git is configured with a compatibility hash (e.g., SHA-1 and SHA-256 interoperability) and batch fsync of loose objects is enabled. The issue arises because the migration code doesn’t know how to merge the "loose-object-idx" file—a mapping between objects and their compatibility hashes—when a preexisting index already exists in the primary object directory.

Justin Tobler, a frequent contributor to the ODB abstraction effort led by Patrick Steinhardt, authored the patch. It introduces a new function, `loose_object_idx_merge()`, which appends new mapping entries from the temporary index to the primary index, preserving both old and new entries. The patch is well-documented, explaining the scenario, the error, and the design choices (e.g., why not defer writing the index until commit). It includes a regression test in `t/t1016-compatObjectFormat.sh` to verify the fix by writing objects in two batches and ensuring all entries appear in the final index. The code touches `tmp-objdir.c`, `loose.c`, and `loose.h`, and is careful about locking, error handling, and file permissions.

The bug is specific to the compatibility-hash feature, so it’s unlikely to affect users who don’t enable that extension. The fix appears technically sound and addresses a real-world issue rather than a theoretical edge case. There’s no indication yet of review feedback or maintainer decisions, so the patch is still under initial consideration.

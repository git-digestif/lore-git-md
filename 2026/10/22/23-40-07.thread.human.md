This thread is about a critical bugfix in Git’s object database (ODB) transaction layer, where temporary object directory migration fails when Git is configured with a compatibility hash (e.g., SHA-1/SHA-256 interop) and batch fsync of loose objects. The issue risks ODB transaction failures and potential data loss due to a flawed migration process for the "loose-object-idx" file, which maps objects to their compatibility hashes. The series, authored by Justin Tobler, is now in its second version (v2) and consists of four patches.

The root problem occurs when loose objects are written to a temporary directory (due to batch fsync) and later migrated to the primary object directory. If a "loose-object-idx" file already exists in the primary directory, the migration fails with a "files differ in contents" error. The v2 series fixes this by atomically merging entries from both directories and writing the result using Git’s standard `tempfile.h` pattern, replacing the previous append-under-lock approach that risked corruption. The series also introduces a finite lock timeout (1000ms) to avoid hangs and refactors parsing and writing logic into reusable helpers (`loose_object_map_read()` and `loose_object_map_write()`). A regression test (`t/t1016-compatObjectFormat.sh`) verifies the fix.

Patrick Steinhardt, the primary reviewer, raised blocking concerns about atomicity, locking, and systemic flaws in the loose-object-idx design during the v1 review. All of these have been addressed in v2, though Steinhardt remains critical of the underlying design’s long-term maintainability, particularly its lack of deduplication, stale-entry pruning, and unsorted files. These issues are acknowledged but deferred to future work, as the current focus is on stabilizing the ODB layer. The series is now finalized and ready for re-review, with Steinhardt expected to approve it. The fix is high-priority for ODB stability, though it only affects users with compatibility-hash and batch-fsync enabled.

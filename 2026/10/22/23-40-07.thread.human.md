This thread is about a bugfix patch from Justin Tobler that addresses a critical flaw in Git’s ODB transaction layer, specifically in how temporary object directories migrate the "loose-object-idx" file—a mapping between objects and their compatibility hashes (e.g., SHA-1/SHA-256 interop)—when batch fsync is enabled. The bug causes data loss if a preexisting index exists in the primary object directory, and the patch aims to fix this by merging entries rather than overwriting them.

The discussion has been technical and collaborative, with Patrick Steinhardt providing substantive review. While the patch’s goal is uncontroversial, Patrick has raised serious concerns about its implementation, particularly around locking, atomicity, and long-term maintenance of the loose-object-idx mechanism. The current version is now explicitly deemed "quite broken" due to its non-atomic append-under-lock approach, which risks file corruption. Justin has agreed to adopt Git’s standard temp-file-then-rename pattern for atomicity and to replace the indefinite lock timeout with a configurable or default 1000ms timeout. These changes will require a **v2** before the patch can proceed.

Other issues—such as unsorted files, lack of deduplication, and stale entry pruning—have been deferred to future work, though Patrick’s feedback suggests they are significant long-term liabilities. The regression test (`t/t1016-compatObjectFormat.sh`) is a strong addition, but the core logic must be refined to address the atomicity and locking concerns. This patch is part of Patrick Steinhardt’s broader ODB abstraction effort and is a high-priority fix for the stability of the compatibility-hash feature, which remains in flight. Expect a v2 to address the blocking issues before this can be merged.

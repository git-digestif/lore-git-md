This is a brief but substantive review comment in the ongoing discussion about Harald Nordgren’s patch series to extend `git branch --delete-merged` with squash-merge and rebase-merge detection. D. Ben Knoble weighs in on the **false-positive issue**—the concern that the current implementation might incorrectly delete a branch whose changes were independently implemented by another author.

Knoble provides a concrete, real-world example where this edge case occurs: when two pull requests contain identical "npm update" commits and are rebased onto `main`. In such cases, the second PR’s commit may appear to have "landed" upstream even though its changes were already integrated by the first PR. This scenario is not hypothetical; Knoble has observed it in practice, though he agrees it is rare (though perhaps not "extremely" so, as Harald suggested). His example underscores that the false-positive risk is not just theoretical but can arise in common workflows involving dependency updates or other mechanical changes.

The comment is notable because it **quantifies the practical likelihood** of the edge case, pushing back slightly on Harald’s dismissal of it as "extremely rare." While Knoble does not propose a specific solution (e.g., author checks, patch IDs, or CLI redesign), his input adds weight to the argument that the current algorithm’s leniency—checking for *containment* of changes rather than *exact* integration—may lead to misleading or harmful behavior. This aligns with Junio C Hamano’s earlier test case and Jasper Mayone’s usability concerns, reinforcing the need for a clearer separation between strict tip-reachability (`--delete-merged`) and looser change-based detection (e.g., `--delete-irrelevant`).

The email does not address the broader CLI design debate (e.g., Junio’s `--delete-irrelevant` proposal or Jasper’s `--landed=<kind>` idea), but it provides **actionable context** for that discussion: any solution must account for cases where identical changes land via independent commits. This is particularly relevant for rebase detection, where Knoble’s example highlights how GitHub-style rebases can obscure the true provenance of changes.

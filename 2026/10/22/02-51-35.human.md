This is the second patch in a two-part bugfix series addressing inconsistent branch switch behavior when Git fails to write tracking configuration. The patch makes `git switch -c` and `git checkout -b` complete the branch switch even if the tracking config cannot be written (e.g., due to a stale `.git/config.lock`), aligning their behavior with `git push -u`, `git clone`, and `git fetch`. The worktree and index updates proceed, the new branch ref is created, and Git exits with status 0, though the error and hint are still printed. The `git branch` command retains its stricter error handling, as verified by the updated test suite.

The change is surgical and well-motivated, targeting a specific edge case where Git currently leaves the repository in an inconsistent state (HEAD on the old branch despite worktree and index updates). The commit message clearly explains the rationale and scope, and the test coverage in `t2027-checkout-track.sh`, `t2060-switch.sh`, and `t3200-branch.sh` is thorough. The patch was split from a larger series at Junio’s request, and the direction was previously agreed in the bug report thread, so there’s no evident controversy.

The implementation is straightforward: `create_branch()` now returns an error instead of exiting, and `builtin/checkout.c` ignores that error to finish the switch. The diff is clean, and the in-code comment explains why the error is non-fatal. This looks like a solid, uncontroversial fix that addresses a real papercut without introducing new complexity. Worth a quick review if you care about checkout or branch behavior, but unlikely to need deep discussion.

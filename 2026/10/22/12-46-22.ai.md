This is a **design discussion** in the ongoing RFC thread about extending `git branch --delete-merged` to handle branches whose upstream has been deleted by hosting services (e.g., GitHub after merging a PR). The email is a **substantive review** from D. Ben Knoble, engaging with the proposed interface and workflow implications.

D. Ben Knoble critiques the two interface proposals (A and B) put forward by the RFC author, DonQuinleone. He argues that **(A)**, a modifier like `--into origin/master` on `--delete-merged`, would complicate the CLI by introducing a context-dependent option that only makes sense in specific scenarios. Instead, he suggests a more composable syntax using `--option=value,value,value` (e.g., `--delete-merged='origin/*,into:origin/master'`), which would avoid adding new flags and allow for future extensions without cluttering the interface.

For **(B)**, the composable filters approach (`--upstream-gone --merged=origin/master`), Knoble acknowledges it would be the more natural fit in a world without `--delete-merged` but notes that it risks ambiguity (e.g., `--merged` defaulting to `HEAD` if the argument is forgotten). He suggests alternative phrasings like `--merged-upstream=<pat>` or `--merged-into=<pat>` to make the intent clearer, and hints at broader possibilities for unifying `--list` and `-d` filters.

Knoble also touches on **workflow ergonomics**, pointing out that GitHub’s triangular workflow (pushing to a topic branch but merging to another) creates awkward upstream configurations. He advocates for `push.default=current` or similar settings to simplify the relationship between `@{upstream}` (where you merge) and `@{push}` (where you push), making commands like `git pull` and `git status` more intuitive. This is not a direct critique of the RFC but highlights a related pain point that the proposed feature could help mitigate.

The email does not address implementation details (e.g., `check_branch_commit()`) or edge cases (e.g., force-pushed upstreams) but focuses squarely on **interface design and user experience**. Knoble’s feedback is constructive and technical, aiming to ensure the feature integrates cleanly with Git’s existing CLI conventions. The discussion remains open-ended, with no clear consensus yet on the best path forward.

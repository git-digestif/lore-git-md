This is a follow-up in the ongoing discussion about the inconsistent state left by `git switch` and `git checkout` when tracking configuration fails. D. Ben Knoble acknowledges 井上司’s clarification about the control flow: `merge_working_tree()` updates the worktree and index on every branch switch, not just when `-m` is used, because the `do_merge` flag defaults to 1. This means the worktree and index are updated *before* the ref is created, tracking config is written (which may fail), and HEAD is updated, leaving the repository in a halfway state if anything goes wrong.

Knoble muses whether reordering these steps—moving worktree and index updates later in the sequence—might be a quick fix, but calls it a "band-aid" rather than a proper atomic solution. The conversation remains focused on the broader design issue: the current sequence is inherently non-atomic, and even the `-m` case suffers from the same problem (conflicts leave HEAD on the old branch, files conflicted, and changes stuck in the stash). No new proposal is made here, but the exchange reinforces the need for a deeper restructuring beyond the near-term `setup_tracking()` fix that Junio has already endorsed. The thread is still in the design phase, with no patch yet posted.

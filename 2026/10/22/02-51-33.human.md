This is a two-patch bugfix series targeting the `git switch` and `git checkout` commands. The issue: when `git switch -c <new-branch>` or `git checkout -b <new-branch>` fails to write the branch’s upstream tracking configuration (for example because `.git/config.lock` already exists), the command leaves the worktree and index updated but HEAD still pointing to the old branch, leaving the user in a half-switched state. The series makes the switch complete—HEAD moves to the new branch—and exits successfully, matching the behavior of `git push -u`, `git clone`, and `git fetch`. The companion `git branch` command still fails, preserving its stricter atomicity requirement.

Patch 1/2 refactors `setup_tracking()` in `branch.c` so it returns an error code instead of calling `exit()`; no user-visible change yet. Patch 2/2 updates `git switch` and `git checkout` to ignore the tracking-configuration error and finish the switch, while leaving `git branch` unchanged. The patches include new tests in `t/t2027-checkout-track.sh`, `t/t2060-switch.sh`, and `t/t3200-branch.sh` that verify the new behavior.

The motivation is clear and the fix is narrowly scoped: the current half-switched state is surprising and inconsistent with other Git commands. The series was previously part of a larger effort that also fixed an unrelated hint message, but Junio explicitly asked for this part to be split out, and the split was agreed in the thread. The commit messages and tests are thorough, and the code changes are small and focused. This looks like a well-crafted, uncontroversial bugfix that should be easy to review.

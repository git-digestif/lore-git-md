This is a two-patch bugfix series from Mihai Cosma that targets a long-standing concurrency issue in `git status`. The problem: `git status` holds the `index.lock` for its entire run, blocking any concurrent `git add` or `git commit` that needs to update the index. The series reduces lock contention by making `status` take the lock only when it actually has something to write, and only for the duration of the write.

Patch 1 is a standalone bugfix that applies to the `maint` branch. It fixes a silent data-loss bug under `index.skipHash` (enabled with `feature.manyFiles` or in Scalar repos): the check that prevents `status` from overwriting a concurrently updated index was passing for *any* index, so `status` could revert a `git add` without warning. The patch tightens the check to use stat data instead. A reproduction case is included in the commit message.

Patch 2 is the main change: it restructures `cmd_status()` so that the lock is acquired only when `refresh_index()` reports that the index needs to be written. The lock is then released immediately after the write. Benchmark numbers on a large repository (gcc, 124 k files) show the improvement: concurrent `git add` runs go from 104 failures out of 200 on `master` to zero failures with the series applied, while the 95th-percentile latency stays roughly the same.

The series overlaps with Jun Wu’s concurrent “Wait for the index lock instead of failing” series; the two are complementary and conflict only on a single lock call. Mihai notes that rebasing onto Jun’s series further reduces latency (from 1020 ms to 160 ms in the worst case). The patches are well-motivated, include a clear reproduction script, and come with thorough performance measurements. The commit messages are detailed and the code changes are focused. This looks like a solid fix for a real pain point.

This is a **CLI design discussion** in the ongoing `git branch --delete-merged` series, where Junio C Hamano responds to Harald Nordgren’s proposal for a `--delete-irrelevant` flag. The email focuses on two key points: naming and option granularity.

Junio argues that "irrelevant" is a poor name for the feature, as it carries negative connotations and doesn’t reflect the actual purpose—identifying branches whose changes have been *integrated* (even if not via a traditional merge). He suggests `--delete-integrated` or similar as a placeholder but invites better alternatives from the list. The naming debate is important: a clear, intuitive flag will make the feature more approachable for users.

On granularity, Junio proposes a tiered option structure (`--delete-foo=merged`, `--delete-foo=rebased`, `--delete-foo=squashed`) where each level includes the previous one. This design avoids the confusion of a Venn diagram (e.g., where `--delete-foo=squashed,rebased` might exclude traditionally merged branches) and aligns with user expectations—most would assume "squashed" detection also covers rebased or cherry-picked branches. His example makes the trade-off explicit: if `--delete-foo=squashed` *didn’t* include rebased branches, users would likely find it counterintuitive.

The email doesn’t resolve the debate but sharpens the focus. Harald’s preference for a single, non-granular flag (`--delete-irrelevant`) is now contrasted with Junio’s tiered proposal, which prioritizes clarity and predictability. The next steps will likely involve the list weighing in on naming and whether the tiered approach is worth the added complexity. For now, this is a **design-in-progress** thread worth watching for anyone interested in Git’s branch maintenance workflows.

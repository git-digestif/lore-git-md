This thread is a documentation cleanup series by Andy Koppe to align Git’s terminology with a 2024 change that narrowed "pseudoref" to just `FETCH_HEAD` and `MERGE_HEAD`, while introducing "root ref" for refs like `HEAD` and `ORIG_HEAD` that live outside the `refs/` hierarchy. The v2 series, posted on June 17, updates the glossary, man pages, code comments, and tests to consistently use the new terms and clarify their behavior. Julia Evans’s proposal to expand the data-model guide (`gitdatamodel.adoc`) is now incorporated, filling a gap where pseudorefs and root refs were previously undocumented.

The series is uncontroversial and nearly ready for merging. Junio C Hamano praised the v1 cover letter as "a pleasant read" but hasn’t reviewed v2 yet. Patrick Steinhardt provided detailed feedback on v1, most of which is addressed in v2—except for two lingering documentation nits in `git-update-ref(1)` about `core.logAllRefUpdates` phrasing and reflog storage for reftable backends. Andy considers these out of scope for this series. Julia Evans’s follow-up questions about pseudoref behavior (e.g., how `git log` handles multiple hashes in `FETCH_HEAD`) are now resolved in the updated glossary and data-model guide.

Junio’s latest email clarifies the technical distinction between the two categories: pseudorefs can describe multiple objects with metadata (e.g., `FETCH_HEAD`’s branch names and "not-for-merge" flags), while root refs contain only a single object ID and behave like normal refs. This explanation reinforces the series’ goal of making the terminology precise without changing behavior. No objections or new action items were raised, so the series is likely to merge once the remaining nits are resolved or deferred.

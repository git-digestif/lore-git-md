This thread is a documentation cleanup series that aligns Git’s terminology with a 2024 change narrowing "pseudoref" to just FETCH_HEAD and MERGE_HEAD, while introducing "root ref" for refs like HEAD and ORIG_HEAD that live outside the `refs/` hierarchy. Andy Koppe’s v2 series (five patches, posted June 17) updates the glossary, man pages, built-in commands, refs internals, test scripts, and pedagogical documentation to replace outdated uses of "pseudoref" with "root ref" and correct related inaccuracies. Julia Evans’s proposal to expand the "References" section of `gitdatamodel.adoc` is now incorporated, explicitly covering both pseudorefs and root refs to address a prior gap in the data-model guide.

The series remains uncontroversial and appears ready for merging, with all review feedback from Junio C Hamano and Patrick Steinhardt addressed except for two minor documentation nits in Patch 3/5. Junio praised v1 as "a pleasant read" but hasn’t reviewed v2, while Patrick’s feedback on glossary phrasing, itemized lists, and commit message clarity is fully incorporated. The latest email clarifies a key technical distinction for readers: root refs (e.g., ORIG_HEAD) can be stored in reftables, contain only a single hash or symbolic ref, and are supported by `git update-ref` and `git for-each-ref`, whereas pseudorefs (e.g., MERGE_HEAD) are always file-backed, may contain multiple hashes with metadata, and are only modified by their respective commands. This explanation fills a gap in the documentation without requiring code changes, ensuring the terminology’s operational constraints and storage flexibility are accurately conveyed.

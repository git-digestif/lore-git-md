Subject: [PATCH v3 0/4] log --follow: performance improvements for rename following in merge-heavy histories
Series version: v3 (four patches)
Originating author: Miklos Vajna
Thread type: patch series

Core problem or goal
Improve performance of `git log --follow` when tracking file history across complex merge topologies (e.g., diamond merges). The current implementation is slow because it performs redundant diff calculations when following renames through non-linear histories; additionally, the patch series fixes two bugs: `--follow` losing history on the second parent of a merge, and incorrect behavior of `git log -m --follow`.

Current status
Under review; v3 posted. Changes since v2 include a new test case (`--follow follows renames through a fork with -m`) and a more granular split of the refactoring steps (tests, preparatory refactor, logic rework, performance optimization). The series has received substantive review from Patrick Steinhardt, who identified a **regression** in patch 4/4: the new `follow_needs_renames()` helper incorrectly handles merges where one side keeps the renamed path and the other edits the old path, causing history loss. No conditional approval or maintainer decision yet; the regression blocks further progress until addressed.

Key technical details
- Files touched: `log-tree.c` (core logic in `log_tree_commit()`), new test file `t/t4219-log-follow-merge.sh` (128 lines, covering merge/rename edge cases including diamond-merge topologies and explicit `-m` interaction).
- New behavior: simplified rename-following logic that avoids redundant diffs; fixes two bugs (history loss on second parent, incorrect `-m --follow` behavior). The regression in patch 4/4 breaks rename-following for merges where the "other" side edits the old path, causing history to be lost.
- New symbols: `follow_needs_renames()` helper function (flawed logic in current form).
- Test coverage: expanded to include diamond-merge topologies and explicit `-m` interaction; Patrick Steinhardt provided a reproducer for the regression (three-commit diamond merge with `-s ours`).
- On-disk format: unchanged.
- Subsystem: log subsystem only; no new APIs.

Open questions and loose ends

- The regression in patch 4/4 must be fixed before the series can proceed; the fix will likely require revisiting the early-return condition in `follow_needs_renames()` to account for cases where the parent has the path but the merge’s "same" side does not.
- Potential interaction with other log-related features (e.g., `--stat`, `--patch`) that share the same code paths is not addressed.
- No conditional approvals or outstanding requests for changes beyond the regression and split suggestion.

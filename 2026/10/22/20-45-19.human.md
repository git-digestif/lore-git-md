This is a performance-focused patch series targeting the `git log --follow` feature. Miklos Vajna addresses a long-standing inefficiency in how `--follow` handles renames across non-linear history (e.g., merges). The series is now in its third iteration, split into four patches: expanded test coverage, a preparatory refactor, a conceptual rewrite of the rename-following logic, and the actual speedup.

The core change abandons the previous approach of walking both parents of a merge commit in lockstep, which could miss renames when history diverged. Instead, it now treats merge commits as ordinary commits during the rename search, only falling back to the old behavior when necessary. The commit message claims this simplifies the code while making it more robust, though the 201-line diff in `log-tree.c` suggests non-trivial restructuring.

Test coverage has grown significantly, with 128 new lines in `t/t4219-log-follow-merge.sh` that exercise edge cases like renames through forks and merges. The interdiff shows one new test case added since v2, checking that `--follow -m` correctly tracks renames through a diamond-shaped merge topology.

The series appears well-motivated and technically sound, with clear attention to both correctness and performance. The split into logical patches makes review tractable, and the expanded test suite should help prevent regressions. This looks like a genuine improvement to a feature that users frequently complain about for its sluggishness in complex histories. Worth attention from anyone interested in Git's history traversal or rename detection.

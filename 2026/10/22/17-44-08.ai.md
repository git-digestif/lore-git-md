This is the next round in the `git branch --delete-merged` squash/rebase detection series, focusing on CLI naming and structure. Harald Nordgren responds to Junio C Hamano’s proposal for a hierarchical `--delete-foo=<mode>` option by suggesting an alternative naming scheme: `--delete-foo=match-hash` (strict tip-reachability), `--delete-foo=match-commits` (includes rebased branches), and `--delete-foo=match-content` (includes squash-merged branches). The proposal draws inspiration from `git push`'s `push.default` options, where modes overlap or subsume each other, and only one is active at a time.

The key difference from Junio’s suggestion is the terminology: "match-hash" (for commit hash equality), "match-commits" (for commit content equality), and "match-content" (for file content equality) aim to make the detection logic more transparent to users. Harald argues this naming better reflects what the algorithm actually checks, avoiding ambiguous terms like "merged" or "integrated." However, the proposal does not address whether the new flag should enable both squash *and* rebase detection by default or require explicit opt-in for each, nor does it resolve the ongoing debate about author checks or patch IDs for rebase detection.

The email advances the CLI design discussion but leaves open questions about naming (Junio’s `--delete-integrated` vs. Harald’s `--delete-foo=match-content`), algorithmic trade-offs (e.g., patch IDs for rebase detection), and performance implications. The next steps will likely involve further feedback on the naming scheme and whether it improves clarity over Junio’s hierarchical proposal.

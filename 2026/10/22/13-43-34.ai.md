This is a **design discussion** reply in the ongoing RFC thread about extending `git branch --delete-merged` to handle branches with deleted upstreams. Harald Nordgren, a contributor with related in-progress work, weighs in on **workflow ergonomics** rather than the RFC’s specific interface proposals.

Nordgren aligns with D. Ben Knoble’s critique of GitHub’s triangular workflows, agreeing that `push.default=current` and `branch.autosetupmerge=inherit` would make upstream tracking more intuitive for users who push to topic branches but merge into a different branch (e.g., `main`). He argues these settings should be defaults, as most GitHub/GitLab users unknowingly work in triangular setups. His broader point is that Git’s current defaults obscure the relationship between `@{upstream}` (where merges happen) and `@{push}` (where pushes go), making commands like `git pull` and `git status` harder to use correctly.

He also endorses Knoble’s suggestion to make `status.comparebranches=@{upstream} @{push}` the default, as it would help users visualize both merge and push targets without manual configuration. This isn’t a direct response to the RFC’s technical questions (e.g., `--into` vs. composable filters) but reinforces the **workflow pain** the RFC aims to address. The email doesn’t propose new solutions for the `--delete-merged` feature itself, but it underscores the need for Git to better accommodate triangular workflows by default. No implementation details or edge cases are discussed.

Subject: [PATCH] tmp-objdir: fix loose-object-idx migration with compat hash + batch fsync
Series version: standalone patch (no series)
Originating author: Justin Tobler
Thread type: bugfix patch

Core problem or goal
Fix a bug in the ODB transaction layer where the temporary object directory migration logic fails when Git is configured with a compatibility hash (e.g., SHA-1/SHA-256 interop) and batch fsync of loose objects is enabled. The migration code does not know how to merge the "loose-object-idx" file (a mapping between objects and their compatibility hashes) when a preexisting index already exists in the primary object directory, leading to data loss.

Current status
Under review; the patch is a standalone bugfix targeting the current integration cycle. Patrick Steinhardt's substantive review identified critical issues around locking, atomicity, and duplicate handling. Justin Tobler has responded with clarifications and proposed adjustments, indicating a **v2 is likely** to address:
- Locking: replacing indefinite timeout (`-1`) with a configurable or default 1000ms timeout, and exploring Git’s standard temp-file-then-rename pattern for atomicity.
- Atomicity: moving away from appending under lock to avoid partial-write corruption.
- Child processes: confirmed that `git-unpack-objects` (spawned by `git-receive-pack`) writes to quarantine directories, justifying the need for child-process support.
- Terminology: commit message will clarify "loose-object-idx" as a "mapping file" without renaming it.
Open questions about duplicate entry detection and stale entry pruning remain deferred to future work.

Key technical details
- Files touched: `tmp-objdir.c`, `loose.c`, `loose.h`
- New function: `loose_object_idx_merge()` in `loose.c`, declared in `loose.h`
- New test: `t/t1016-compatObjectFormat.sh` (regression test verifying migration preserves all entries)
- Subsystems: ODB transaction layer, loose-object storage, compatibility hash extension
- Behavior change: migration now appends new mapping entries to the primary index instead of overwriting it, preserving both old and new entries
- On-disk format: the "loose-object-idx" file is updated in-place; no format change, only a merge operation
- **New concerns**: (1) indefinite lock timeouts risking hangs, (2) file corruption from partial writes during append, (3) lack of duplicate entry detection, (4) child process writes to quarantine directories, (5) long-term maintenance of stale entries

Open questions and loose ends
- **Locking**: Should `repo_hold_lock_file_for_update_timeout()` use a finite timeout (e.g., 1000ms) instead of `-1` (indefinite)? Is the temp-file-then-rename pattern safer than appending under lock?
- **Atomicity**: Does the current append-under-lock approach risk file corruption if the write fails partially? Would a temp-file-then-rename pattern mitigate this?
- **Duplicates**: Does the merge logic need to check for existing object IDs to avoid duplicates? Do readers of the index expect sorted input or handle unsorted data?
- **Stale entries**: Git does not prune stale mapping entries when objects are pruned; this is deferred to future work but noted as a potential maintenance issue.

Subject: [PATCH v2 0/4] tmp-objdir: fix loose-object-idx migration with compat hash + batch fsync
Series version: v2 (four-patch series)
Originating author: Justin Tobler
Thread type: bugfix patch series

Core problem or goal
Fix a critical bug in the ODB transaction layer where temporary object directory migration fails when Git is configured with a compatibility hash (e.g., SHA-1/SHA-256 interop) and batch fsync of loose objects is enabled. The migration logic does not correctly merge the "loose-object-idx" file (a mapping between objects and their compatibility hashes) when a preexisting index exists in the primary object directory, leading to ODB transaction failures and potential data loss. The patch series atomically writes the merged index and uses a finite lock timeout, addressing Patrick Steinhardt’s blocking concerns about atomicity and locking. Systemic design flaws in the loose-object-idx mechanism—unsorted files, lack of deduplication, no pruning of stale entries, and non-atomic writes—are acknowledged but deferred to future work.

Current status
Under review; **v2 is finalized and ready for re-review** after addressing all blocking feedback from Patrick Steinhardt. **Patch 1/4 (locking timeout) is now effectively approved** by Patrick Steinhardt, and **patch 2/4 (parsing refactor) is uncontroversial and ready for integration** following minor documentation clarifications. The series remains a high-priority fix for ODB layer stability, targeting the current integration cycle. Key adjustments in v2:
- **Atomicity**: Replaces the append-under-lock pattern with Git’s standard temp-file-then-rename pattern (via `commit_lock_file`) to eliminate corruption risk from partial writes.
- **Locking**: Replaces the indefinite timeout (`-1`) with a default 1000ms timeout (`LOOSE_OBJECT_IDX_LOCK_TIMEOUT_MS`) to avoid hangs (introduced in 1/4). Patrick Steinhardt approves this change but suggests making the timeout configurable in future work.
- **Validation**: Retains the loose-object-idx header check (`loose_object_header`) as a defensive measure.
- **Duplicate handling**: Drops duplicate entries during the merge, though the preexisting race condition in `write_one_object()` remains unfixed.
- **Refactoring**: Patch 2/4 introduces `loose_object_map_read()` to decouple parsing logic from the `odb_source_loose` struct, and **patch 3/4 introduces `loose_object_map_write()`** to extract writing logic into a reusable helper, enabling atomic writes in the migration code. **Patch 4/4 implements the core fix** by merging entries from temporary and primary object directories and atomically writing the result using the refactored helpers.

Key technical details
- Files touched: `tmp-objdir.c`, `loose.c`, `loose.h`
- New functions: `loose_object_map_read()` (2/4), `loose_object_map_write()` (3/4), `loose_object_idx_merge()` (4/4, declared in `loose.h` and defined in `loose.c`)
- New constant: `LOOSE_OBJECT_IDX_LOCK_TIMEOUT_MS` (1000ms, introduced in 1/4)
- New test: `t/t1016-compatObjectFormat.sh` (regression test verifying migration preserves all entries from both temporary and primary indices)
- Subsystems: ODB transaction layer, loose-object storage, compatibility hash extension
- Behavior change: Migration now uses atomic temp-file-then-rename instead of append-under-lock, preserving both old and new entries without corruption risk. The loose-object-idx file’s on-disk format remains unchanged, but its systemic issues (unsorted, no deduplication, no pruning) are acknowledged as long-term liabilities. Stricter error handling in `repo_read_loose_object_map()` now fails early if any object source’s loose-object-idx file is unreadable (previously, it continued with subsequent sources).
- **New concerns resolved in v2**: (1) append-under-lock risks file corruption (replaced with temp-file-then-rename), (2) indefinite lock timeouts risking hangs (replaced with 1000ms timeout in 1/4), (3) parsing logic reuse (refactored in 2/4), (4) writing logic reuse (refactored in 3/4), (5) core migration logic (implemented in 4/4). **Remaining deferred concerns**: (1) preexisting race condition in `write_one_object()` allowing duplicates, (2) no pruning mechanism for stale mapping entries, (3) unsorted files complicating merges.

Open questions and loose ends
- **Atomicity**: v2 adopts temp-file-then-rename, resolving Patrick Steinhardt’s strongest objection. Performance concerns for high-volume loose-object writes remain but are accepted as a trade-off.
- **Locking**: v2 uses a 1000ms timeout (introduced in 1/4) instead of `-1`. Patrick Steinhardt suggests making the timeout configurable in future work but accepts the fixed value for now.
- **Duplicates**: Preexisting race condition in `write_one_object()`; fix deferred to future work. Patrick Steinhardt accepts this but remains critical of the underlying design.
- **Stale entries**: No pruning mechanism for stale mapping entries; deferred to future work. Patrick Steinhardt has flagged this as a serious long-term liability.
- **Child processes**: Confirmed that `git-unpack-objects` (spawned by `git-receive-pack`) writes to quarantine directories, justifying the need for child-process support.
- **Error handling**: Stricter propagation of file-open errors (other than `ENOENT`) may break workflows where loose-object-idx files are temporarily unreadable, but this is accepted as a correctness trade-off.
- **Documentation**: Patch 2/4’s commit message should clarify the optional `cache` parameter in `insert_loose_map()` to explain its reuse in later patches where caching is not needed. Patrick Steinhardt requests this as a minor improvement.

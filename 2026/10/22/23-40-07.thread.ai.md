Subject: [PATCH] tmp-objdir: fix loose-object-idx migration with compat hash + batch fsync
Series version: standalone patch (no series)
Originating author: Justin Tobler
Thread type: bugfix patch

Core problem or goal
Fix a bug in the ODB transaction layer where the temporary object directory migration logic fails when Git is configured with a compatibility hash (e.g., SHA-1/SHA-256 interop) and batch fsync of loose objects is enabled. The migration code does not know how to merge the "loose-object-idx" file (a mapping between objects and their compatibility hashes) when a preexisting index already exists in the primary object directory, leading to data loss.

Current status
Under review; no prior versions. The patch is a standalone bugfix targeting the current integration cycle. Patrick Steinhardt's substantive review identifies critical issues around locking, atomicity, and duplicate handling that will likely require a v2.

Key technical details
- Files touched: `tmp-objdir.c`, `loose.c`, `loose.h`
- New function: `loose_object_idx_merge()` in `loose.c`, declared in `loose.h`
- New test: `t/t1016-compatObjectFormat.sh` (regression test)
- Subsystems: ODB transaction layer, loose-object storage, compatibility hash extension
- Behavior change: migration now appends new mapping entries to the primary index instead of overwriting it, preserving both old and new entries
- On-disk format: the "loose-object-idx" file is updated in-place; no format change, only a merge operation
- Test coverage: verifies the fix by writing objects in two batches and checking that all entries appear in the final index
- **New concerns**: The review raises questions about (1) indefinite lock timeouts potentially causing hangs, (2) file corruption risk from partial writes during append, (3) lack of duplicate entry detection, and (4) whether child processes write to quarantine directories

Open questions and loose ends
- **Locking**: Should `repo_hold_lock_file_for_update_timeout()` use a finite timeout instead of `-1` (indefinite) to avoid hangs? Is the current locking pattern (append under lock) safe, or should it follow Git's standard temp-file-then-rename pattern?
- **Atomicity**: Does appending to the index under lock risk file corruption if the write fails partially? Would writing to a temp file and atomically renaming it be safer?
- **Duplicates**: Does the merge logic need to check for existing object IDs to avoid duplicates? Do readers of the index expect sorted input or handle unsorted data?
- **Child processes**: Do child processes ever write to the quarantine directory, and if so, does the patch account for this?
- **Long-term maintenance**: Git doesn't prune stale mapping entries when objects are pruned; this is deferred to future work but noted as a potential issue.

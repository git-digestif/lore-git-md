Subject: [PATCH] tmp-objdir: fix loose-object-idx migration with compat hash + batch fsync
Series version: standalone patch (no series)
Originating author: Justin Tobler
Thread type: bugfix patch

Core problem or goal
Fix a critical bug in the ODB transaction layer where the temporary object directory migration logic fails when Git is configured with a compatibility hash (e.g., SHA-1/SHA-256 interop) and batch fsync of loose objects is enabled. The migration code does not correctly merge the "loose-object-idx" file (a mapping between objects and their compatibility hashes) when a preexisting index already exists in the primary object directory, leading to data loss. The patch surfaces deeper design flaws in the loose-object-idx mechanism, including unsorted files, lack of deduplication, no pruning of stale entries, and non-atomic writes.

Current status
Under review; the patch is a standalone bugfix targeting the current integration cycle. **A v2 has been finalized** to address Patrick Steinhardt’s blocking concerns about atomicity and locking. Key adjustments in v2:
- **Atomicity**: Replace the append-under-lock pattern with Git’s standard temp-file-then-rename pattern to eliminate corruption risk from partial writes.
- **Locking**: Replace the indefinite timeout (`-1`) with a default 1000ms timeout to avoid hangs.
- **Validation**: Retain the loose-object-idx header check (`loose_object_header`) as a defensive measure.
Open questions about duplicate entry detection and stale entry pruning remain deferred to future work, though Patrick Steinhardt has explicitly labeled the current design as "quite broken" in these areas. Justin Tobler has expressed performance concerns about the atomic-write approach for operations writing many loose objects but has agreed to implement it in v2.

Key technical details
- Files touched: `tmp-objdir.c`, `loose.c`, `loose.h`
- New function: `loose_object_idx_merge()` in `loose.c`, declared in `loose.h`
- New test: `t/t1016-compatObjectFormat.sh` (regression test verifying migration preserves all entries)
- Subsystems: ODB transaction layer, loose-object storage, compatibility hash extension
- Behavior change: Migration now uses atomic temp-file-then-rename instead of append-under-lock, preserving both old and new entries without corruption risk. The loose-object-idx file’s on-disk format remains unchanged, but its systemic issues (unsorted, no deduplication, no pruning) are acknowledged as long-term liabilities.
- **New concerns**: (1) **Resolved in v2**: append-under-lock risks file corruption (replaced with temp-file-then-rename), (2) indefinite lock timeouts risking hangs (replaced with 1000ms timeout), (3) preexisting race condition in `write_one_object()` allowing duplicates (deferred), (4) child process writes to quarantine directories (confirmed as necessary), (5) long-term maintenance of stale entries (deferred).

Open questions and loose ends
- **Atomicity**: v2 adopts temp-file-then-rename, resolving Patrick Steinhardt’s strongest objection. Performance concerns for high-volume loose-object writes remain but are accepted as a trade-off.
- **Locking**: v2 uses a 1000ms timeout instead of `-1`.
- **Duplicates**: Preexisting race condition in `write_one_object()`; fix deferred to future work. Patrick Steinhardt accepts this but remains critical of the underlying design.
- **Stale entries**: No pruning mechanism for stale mapping entries; deferred to future work. Patrick Steinhardt has flagged this as a serious long-term liability.
- **Child processes**: Confirmed that `git-unpack-objects` (spawned by `git-receive-pack`) writes to quarantine directories, justifying the need for child-process support.

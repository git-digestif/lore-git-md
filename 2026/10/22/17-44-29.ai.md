This is a **CLI design and safety discussion** for Harald Nordgren’s `git branch --delete-merged` series, which extends the command to detect squash-merged and rebase-merged branches. Jasper Mayone’s reply advances the naming and granularity debate while proposing a concrete mitigation for the false-positive issue.

Jasper **endorses `--delete-integrated`** as the new flag name, aligning with Harald’s preference and Git’s existing documentation. He argues that "integrated" is neutral about the integration method (merge, rebase, or squash), making it a good fit for the hierarchical levels (`merged`, `rebased`, `squashed`) proposed earlier. To avoid breaking the existing `--delete-merged <pattern>` syntax (where `<pattern>` is required and specifies the upstream branch), Jasper suggests a **clean separation**: `--delete-merged <pattern>` for strict tip-reachability (current behavior) and `--delete-integrated <pattern>` for change-based detection (rebased *and* squashed branches). A config variable could later allow users to opt into intermediate levels (e.g., only rebased branches) without complicating the command line.

On the **false-positive issue** (branches incorrectly deleted because another author independently made the same change), Jasper **proposes an author-based mitigation**: require that the landing commit’s author also authored at least one commit on the branch being deleted. This would reject false positives in forge workflows (where squash/rebase buttons preserve the PR author) while still allowing manually applied patches (`git am`, which preserves authorship). He acknowledges this is untested but suggests it as a practical experiment. The proposal directly addresses the "npm update" scenario (identical commits from separate PRs) and Junio’s test case, both of which expose the algorithm’s current leniency.

The email does not revisit the unresolved questions about whether `--delete-integrated` should enable both squash *and* rebase detection by default or require explicit opt-in for each, nor does it address the performance trade-offs of author checks or other mitigations (e.g., patch IDs). The focus remains on **naming, syntax, and safety**, with Jasper’s proposal offering a path forward for both. The next steps will likely involve consensus on the flag name and syntax, followed by implementation of the author-check mitigation and updates to the test suite to reflect the new behavior.

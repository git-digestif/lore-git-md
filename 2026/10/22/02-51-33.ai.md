This is a two-patch bugfix series targeting the checkout and branch subsystems.

The series addresses a long-standing edge case where `git switch -c` or `git checkout -b` fails to complete the branch switch when it cannot write the tracking configuration (e.g., due to a stale `.git/config.lock`). Currently, the worktree and index are updated, the new branch ref is created, but HEAD remains on the old branch, leaving the repository in an inconsistent state. The patches make the operation non-atomic but consistent: if the tracking config cannot be written, the switch still completes, and Git exits with status 0, matching the behavior of `git push -u`, `git clone`, and `git fetch`. The `git branch` command, however, still fails in this scenario, preserving its stricter error handling.

Patch 1/2 refactors `setup_tracking()` in `branch.c` to return an error instead of calling `exit()`, preparing the ground for the behavior change. Patch 2/2 modifies `builtin/checkout.c` to ignore the tracking config failure and finish the switch, while updating the test suite (`t2027-checkout-track.sh`, `t2060-switch.sh`, and `t3200-branch.sh`) to verify the new behavior.

The series is well-motivated and surgically targets a specific inconsistency in Git’s error handling. The commit messages and test coverage are thorough, and the patches were previously part of a larger series but were split out at Junio’s request after the direction was agreed in the bug report thread. The author explicitly leaves atomicity (rolling back the switch on failure) for a future topic, keeping this series focused. No controversy is evident from the provided context.

Subject: [PATCH 0/2] Fix index locking behavior in `git status`
Series version: v1 (initial submission; coordination with Jun Wu’s "Wait for the index lock" series now contested)
Originating author: Mihai Cosma <mcosma@gmail.com>
Thread type: bugfix patch series

Core problem or goal
Fix two related issues in `git status` index handling: (1) a silent data-loss bug in the `index.skipHash` code path (enabled in Scalar repos and with `feature.manyFiles`) where concurrent index modifications are silently overwritten, and (2) a long-standing usability problem where `git status` holds `index.lock` for its entire duration, blocking concurrent operations like `git add` or `git commit`. The goal is to restore correctness and eliminate unnecessary lock contention in large repositories.

Current status
Under review; no prior versions. Coordination with Jun Wu’s concurrent "Wait for the index lock" series is now contested. Junio initially suggested merging the efforts, but Jun Wu argues the two series are complementary and should remain separate: Mihai’s series reduces lock hold time in `git status`, while Jun Wu’s makes writers wait instead of failing. Both approaches are compatible, but Jun Wu prefers to avoid consolidation to reduce complexity. Patch 1 (data-loss bugfix) remains a standalone fix suitable for `maint`; Patch 2 (lock contention improvement) may still be rebased onto Jun Wu’s work, but no firm decision has been made. No integration branch assignment yet.

Key technical details
- Files touched: `read-cache.c`, `builtin/commit.c`, `t/t7508-status.sh`
- New/renamed symbols: `struct index_state` gains a `file_stat` field; new helper functions `index_file_unchanged()`, `repo_lock_and_update_index_if_able()`, and `index_needs_write()`
- Behavior changes:
  - Patch 1: restores stat-data verification in `verify_index_match()` for the `index.skipHash` code path by comparing inode, mtime, size, and other stat fields instead of relying on a null checksum. The stat data is copied during index read/write and when `unpack_trees()` builds a new index.
  - Patch 2: moves `index.lock` acquisition in `cmd_status()` to just before `write_locked_index()`, so the lock is held only when necessary (e.g., untracked cache updates or `refresh_index()` modifications). Introduces `repo_lock_and_update_index_if_able()` to conditionally lock and write the index only if changes are pending.
- On-disk format: unchanged
- Test coverage: new tests in `t/t7508-status.sh` covering the bugfix (both `index.skipHash=true` and `index.skipHash=false`), locking behavior, and edge cases with fsmonitor hooks. Includes a reproduction script demonstrating the silent data loss and benchmarks showing a 50-60% reduction in concurrent `git add` failures in large repos (gcc, 124k files), with a minor latency trade-off (~128ms vs. ~114ms in the clean case). Combined with Jun Wu’s series, `git add` latency drops to 160ms in the clean case.

This is a **substantive review** from Junio C Hamano (the maintainer) targeting the architectural direction of Harald Nordgren’s v3 patch series, which extends `git branch --delete-merged` to detect squash-merged and rebase-merged branches. Junio’s email **rejects the current CLI design** and demonstrates a **real-world false positive** where the series incorrectly deletes a branch whose changes were independently implemented by another author.

The core issue is that the series **loosens the default behavior of `--delete-merged`** by treating branches as merged if their changes appear in any upstream commit, even if the branch tip itself is not reachable. Junio argues this violates the principle of least surprise: users expect `--delete-merged` to be a **strict, tip-reachability-only** command, and loosening it by default risks deleting work that was never actually merged. His attached test case (a 33-line addition to `t/t3200-branch.sh`) proves the series fails this expectation: it deletes a branch whose changes were independently added by another author, simply because the file contents match.

Junio’s proposed solution is to **preserve `--delete-merged` as a strict, conservative command** and introduce a new `--delete-irrelevant` option for looser detection (rebases, squash merges, and other cases where changes are upstream but the branch tip is not). This aligns with his earlier feedback but is now backed by a concrete test case and a clear demonstration of the false-positive risk. The test case is particularly damning because it shows the series deletes a branch that was **never merged or even shared** with the upstream repository, undermining the feature’s safety guarantees.

The email does not engage with the implementation details of the series (e.g., the `changed_paths` slab, tree-based diffing, or three-way merge logic) but instead focuses on **user intent and safety**. Junio’s position is that the current design conflates two distinct use cases: (1) deleting branches whose tips are safely preserved in upstream history (strict, safe), and (2) deleting branches whose changes are upstream but whose tips are not (looser, ambiguous). His test case shows that the latter can lead to data loss, and he explicitly states that the series should not change `--delete-merged`’s behavior without an explicit opt-in.

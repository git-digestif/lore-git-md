This is a documentation discussion in the ongoing `gitbreaking-changes(7)` manpage thread. The series, which moves Git’s `BreakingChanges` document into a proper manpage for better user visibility, is technically complete and ready for integration. All prior feedback has been addressed, but the maintainer has now raised a fundamental question about whether maintaining a historical record of breaking changes is worthwhile at all.

In this email, Kristoffer Haugsbakk responds to Junio C Hamano’s skepticism about the document’s long-term utility by offering pragmatic options. He suggests that old entries could either be promptly deleted after a new release or retained only for the most recent transition (e.g., keeping only Git 4.0 and 5.0 discussions when approaching Git 5.0). He also notes that users on older versions already have the relevant information in their installations, and version control can serve as a fallback for historical context. His tone is neutral, deferring to the maintainer’s judgment while providing concrete ways to address the concern.

The series itself remains unblocked from the author’s side, but its integration now hinges on Junio’s final decision about the document’s purpose. The discussion is no longer about technical implementation but about whether the project wants to commit to maintaining this kind of historical record. If the series proceeds, minor merge conflicts with `ps/ref-storage-format` and `bc/restrict-hex-to-lowercase` will need to be resolved by moving their additions to the new manpage. For now, the series is still under review.

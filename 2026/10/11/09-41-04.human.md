This is a **feature patch** (v2 of a two-patch series) that extends `git branch --delete-merged` to detect branches whose changes were integrated via squash merges, rebases, or patch-based workflows—even when the branch tip itself isn’t reachable from the upstream. The patch is now optimized for performance, includes a `--no-squashed` flag to disable the slower squash detection, and fixes correctness bugs from v1.

The core idea is simple: when you use GitHub’s "Squash and merge" button or run `git merge --squash`, the branch’s changes land in the upstream, but the branch tip isn’t merged, so `git branch --delete-merged` ignores it. This patch teaches Git to recognize such branches by checking whether some upstream commit contains all of their changes, even if the branch tip itself isn’t reachable. The output now shows where the work landed: `Deleted branch topic (was 1a2b3c4, landed as 9f8e7d6)`.

Performance was a major concern in v1. The v2 patch addresses this by batching diff calculations and reusing results across branches, so the upstream diff is computed only once. It also transparently fetches blobs in partial clones to calculate patch-ids, ensuring the feature works even in blobless repositories. The `--no-squashed` flag lets users opt out of the slower squash detection for performance-sensitive workflows, though the feature defaults to "on" for all branches.

The implementation is thorough: it handles edge cases like upstream modifying the same files as the squashed branch, reverted changes, and mixed merge/squash workflows. Tests cover local `git merge --squash`, GitHub-style squash merges, rebases, and patch-based integrations. The commit message and documentation are clear and well-motivated, explaining the real-world pain point (accumulating undeletable branches) and the technical approach.

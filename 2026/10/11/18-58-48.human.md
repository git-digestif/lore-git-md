This is the second patch in a two-part feature series that makes `git blame` automatically use `HEAD:.git-blame-ignore-revs` as the default ignore-revs file when no explicit file is configured. The series is now under review, with Junio’s feedback on this patch focusing on a minor but forward-looking refactoring opportunity.

The patch itself is feature-complete and well-tested, implementing the core behavior: when no ignore-revs file is set via command line or config, Git checks for a `.git-blame-ignore-revs` blob in the `HEAD` tree, parses it in memory using the hardened parser introduced in patch 1/2, and adds it to the ignore list before any user-configured files. The design handles edge cases like subdirectory invocations, bare repositories, committed symlinks, and CLI/config overrides, and aligns with how GitHub and GitLab already behave.

Junio’s feedback here is procedural and future-oriented. He notes that the new `parse_default_ignore_revs_blob()` function could avoid referencing the global `the_repository` variable, since the `blame_scoreboard` struct already holds a repository pointer. This is not a blocker for merging—Junio calls it “not ultra urgent”—but it’s a small, mechanical change that would help the ongoing effort to remove `the_repository` globals. The rest of the patch is clean and uncontroversial; Junio’s earlier feedback on the series was approving (“OK”, “Good”, “Very clean”).

The series is ready for broader review, though the security-sensitive parts (especially the tag-peeling logic) would benefit from scrutiny by contributors like Jeff King or brian m. carlson. The only remaining procedural decision is whether to retain or drop the NUL-byte check in the parser, which the author has already offered to adjust based on Junio’s preference. This patch is a solid, well-motivated feature that closes a usability gap without breaking backward compatibility. Worth attention if you care about blame workflows or the `the_repository` removal effort.

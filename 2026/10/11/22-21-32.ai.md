This is the first patch in a two-part **feature series** that hardens the ignore-revs parser and tag-peeling logic in `git blame` before introducing a default ignore-revs file (`HEAD:.git-blame-ignore-revs`). The hardening is a prerequisite for the upcoming default file lookup (patch 2/2) and addresses security concerns raised during review of earlier iterations.

The patch modifies `oidset_parse_file_carefully()` in `oidset.c` to reject lines containing embedded NUL bytes, preventing silent truncation of malformed input. It also updates `peel_to_commit_oid()` in `builtin/blame.c` to use `odb_read_object_info_extended()` with `OBJECT_INFO_SKIP_FETCH_OBJECT` and `OBJECT_INFO_QUICK`, ensuring that missing tag targets in partial clones do not trigger promisor fetches. The tag-peeling logic now verifies each tag’s declared type before parsing, mitigating type confusion risks.

Key changes include:
- **NUL-byte rejection**: The ignore-revs parser now scans each line for embedded NUL bytes using `memchr()` and dies if any are found. This is a defensive measure to ensure consistency with other trailing-garbage handling, though the author has offered to drop it if Junio prefers.
- **Promisor fetch prevention**: The updated `peel_to_commit_oid()` avoids network requests for missing objects by using `OBJECT_INFO_SKIP_FETCH_OBJECT` and `OBJECT_INFO_QUICK`. It also checks the type of each tag target before parsing, preventing type confusion.
- **Test coverage**: New tests in `t/t8013-blame-ignore-revs.sh` verify that lines with NUL bytes are rejected and that chained tags are peeled correctly, even when tag targets are missing in partial clones.

The patch is technically sound and aligns with Junio’s feedback from earlier iterations. The hardening is uncontroversial, though the NUL-byte check remains optional and may be removed in a future revision. The changes are well-motivated and documented, with clear test coverage for edge cases. Security-interested reviewers (e.g., Jeff King, brian m. carlson) may still weigh in on the hardening’s adequacy, but the patch is otherwise ready for integration once the NUL-byte check decision is finalized. The `the_repository` cleanup requested in v2 has been addressed in the series’ second patch.

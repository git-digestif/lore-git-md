Thread identity
Subject: Proposal to deprecate `git format-rev`
Series version: N/A (standalone RFC)
Originating author: Kristoffer Haugsbakk
Thread type: feature deprecation proposal

Core problem or goal
The thread proposes deprecating the experimental `git format-rev` command, arguing its core functionality—pretty-formatting one revision at a time from stdin—is already provided by `git diff-tree --stdin --format=medium`. However, the proposed replacement pipeline has a critical limitation: `git diff-tree` uses *separators* (not terminators) for NUL-delimited output (`-z`), meaning the first commit in a stream lacks a delimiter and subsequent commits are preceded by a NUL. This breaks incremental parsing in scripts (e.g., shell coprocs) that rely on unambiguous record termination. While `git format-rev` offers minor conveniences (direct revision expressions, object-name annotation in running text), its NUL-terminated output is uniquely suited for multiline commit messages or revision expressions, creating a functional gap the replacement cannot replicate.

Current status
Under discussion; no maintainer decision recorded. No prior version of this proposal exists. The author has experimented with adding a `--use-terminator` option to `log-tree.c` but found the code resistant to this change.

Key technical details
- Command under discussion: `git format-rev` (experimental)
- Proposed replacement pipeline: `git diff-tree --stdin --format=medium -z` (incomplete due to separator vs. terminator behavior)
- Missing feature parity:
  - NUL *termination* (vs. separation) for `--format=medium` in `git diff-tree` (critical for incremental parsing)
  - `--notes` support in `git diff-tree` (absent in `git format-rev`)
  - Direct revision expression input (absent in `git diff-tree`)
- Workaround for object-name annotation: `git cat-file --batch-command='%(objectname)'` (but does not resolve NUL termination gap)
- Subsystems touched: log-tree machinery (`log-tree.c`), pretty-printing, input/output handling for NUL-terminated streams
- Author’s use case: shell script generating `git log`/`git format-patch`-like output with interdiffs, requiring NUL-terminated commit messages for coproc parsing

Open questions and loose ends
- Whether the convenience of direct revision expressions and NUL-terminated output justifies retaining `git format-rev` despite its redundancy with `git diff-tree`.
- Whether any users or scripts rely on `git format-rev` specifically for NUL-terminated output or multiline revision handling, which the replacement pipeline cannot replicate.
- Whether the project is willing to deprecate an experimental command with a known functional gap in its proposed alternative, or if the gap should be addressed first (e.g., via `--use-terminator`).
- Whether the `log-tree.c` machinery could be extended to support NUL termination (terminators) for `--format=medium`, and if so, whether this would resolve the deprecation blocker.
- Whether the lack of `--patch` output in human-readable formats for `git diff-tree` (even with `-z`) further limits its suitability as a replacement.

Participant positions
- Kristoffer Haugsbakk (author):
  - Initially argued `git format-rev`’s raison d’être was partially superseded but acknowledged the NUL termination limitation weakened the case for deprecation.
  - Later clarified that `git diff-tree -z` uses separators, not terminators, making it unsuitable for incremental parsing in scripts. Concluded `git diff-tree` cannot fully replace `git format-rev` for their workflow due to this gap and the lack of NUL-terminated diff output (`--patch`).
  - Position remains open to deprecation if the functional gap is addressed (e.g., via `--use-terminator`) or deemed non-critical, but no longer views `git diff-tree` as a drop-in replacement.

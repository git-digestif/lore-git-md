Subject: Proposal to deprecate `git format-rev`
Series version: N/A (standalone RFC)
Originating author: Kristoffer Haugsbakk
Thread type: feature deprecation proposal

Core problem or goal
The thread proposes deprecating the experimental `git format-rev` command on the grounds that its core functionality—pretty-formatting one revision at a time from stdin—is already provided by `git diff-tree --stdin --format=medium`. However, the proposed replacement pipeline has a critical limitation: `git diff-tree` does not support NUL termination (`-z`) for the `--format=medium` pretty-printing mode, which breaks handling of multiline commit messages or revision expressions. While `git format-rev` offers minor conveniences (direct revision expressions, object-name annotation in running text), the lack of NUL termination in the replacement pipeline creates a functional gap for scripts or workflows that rely on unambiguous parsing of multiline output.

Current status
Under discussion; no maintainer decision recorded. No prior version of this proposal exists.

Key technical details
- Command under discussion: `git format-rev` (experimental)
- Proposed replacement pipeline: `git diff-tree --stdin --format=medium` (incomplete due to NUL termination limitation)
- Missing feature parity: `--notes` support in `git diff-tree` (absent in `git format-rev`) and NUL termination for `--format=medium` (absent in `git diff-tree`)
- Workaround for object-name annotation: `git cat-file --batch-command='%(objectname)'` (but does not resolve NUL termination gap)
- Subsystems touched: log-tree machinery, pretty-printing, input/output handling for NUL-terminated streams

Open questions and loose ends
- Whether the convenience of direct revision expressions and inline object-name annotation justifies keeping `git format-rev` despite the functional overlap with `git diff-tree`.
- Whether any users or scripts rely on `git format-rev` specifically for NUL-terminated output or multiline revision handling, which the replacement pipeline cannot replicate.
- Whether the project is willing to deprecate an experimental command that has never graduated to stable status, given the identified functional gap in the proposed alternative.
- Whether the `git diff-tree` machinery could be extended to support NUL termination for `--format=medium`, which would resolve the gap but require additional work.

Participant positions
- Kristoffer Haugsbakk (author): argues the command’s raison d’être has been partially superseded but acknowledges the NUL termination limitation weakens the case for deprecation. Position remains open to deprecation if the functional gap is addressed or deemed non-critical.

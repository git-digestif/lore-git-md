This is a bugfix patch targeting the cache-tree subsystem. It prevents `git rebase` from crashing when another process (such as `git status` or Magit) holds the index lock during an in-process commit attempt.

The patch removes the `LOCK_DIE_ON_ERROR` flag from `hold_lock_file_for_update()` in `write_index_as_tree()`, replacing it with a gentle lock attempt. If the lock is held by another process, the function now skips writing the updated cache-tree back to the index but still computes and returns the tree object. This matches the behavior of other callers that only refresh the index. The change affects `git rebase --continue`, `git write-tree`, and `git am`, all of which can now proceed while another process holds the lock.

The commit message traces the regression to 356ee4659b (2017-11-24), which moved commit creation in-process during cherry-picks. Before that, the `die()` happened in a child process and the sequencer state was preserved; afterward, the crash left the rebase in a half-picked state that required manual recovery. The patch includes a new test in `t/t0090-cache-tree.sh` that verifies `git write-tree` succeeds while `.git/index.lock` exists.

Code changes are minimal: the lock acquisition is made non-fatal, and the write-back step is guarded by a check on the file descriptor. The patch is well-motivated, includes reproduction steps, and adds test coverage. It looks like a clean, targeted fix for a real-world annoyance.

This is the third iteration (v3) of a **bugfix patch** targeting the fetch subsystem, specifically addressing a performance regression in shallow fetches when backfilling tags. The patch splits reference transactions into two phases—committing fetched references before backfilling tags—to restore correct negotiation behavior without sacrificing the performance benefits of batched updates.

The regression was introduced in commit `0e358de64a` ("fetch: use batched reference updates", 2025-05-19), where batched updates delayed committing references to disk until after tag backfilling. This caused shallow fetches to report no 'have' references during negotiation, forcing the server to resend all objects. The fix ensures fetched references are committed before tag backfilling begins, allowing the client to advertise them as 'haves' during negotiation. Benchmarks show the fix is **17.38±0.61× faster** than the pre-batched-update behavior and only **1.01× slower** than the single-transaction approach, making it a clear performance win.

Key changes in v3 address edge cases raised during review:
- **Empty transactions**: The patch now handles cases where the main transaction fails to initialize, ensuring post-fetch operations (e.g., `FETCH_HEAD` writes, upstream config) still execute.
- **Error handling**: A separate `commit_ref_ret` variable tracks the first transaction’s result, preventing rejections from skipping critical steps.
- **Test coverage**: Two new tests verify (1) that backfilling tags advertises fetched refs as 'haves' and (2) that upstream tracking info is set even when the main ref update is rejected but a tag is backfilled.

The patch touches `builtin/fetch.c` and adds tests to `t/t5510-fetch.sh`. It avoids the regression while preserving atomicity trade-offs (e.g., `--atomic` fetches may still trigger full clones if tag backfilling fails). The commit message clearly documents these limitations and the rationale for the two-transaction approach.

The fix is well-motivated, thoroughly tested, and maintains backward compatibility while addressing a real-world performance issue.

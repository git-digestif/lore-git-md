This is the **implementation patch (4/4)** of the incremental connectivity check series, now receiving a **substantive review** from Patrick Steinhardt. The patch introduces the core logic in `tree-verify.c` for the new `transfer.connectivityCheck=incremental` mode, which verifies incoming commits by comparing their trees against trusted parent trees rather than walking the full object closure of boundary commits.

Patrick’s review engages deeply with the algorithm and implementation details. He identifies several technical points for improvement: the use of `enum tree_state` values in a `khash` map should use the enum type directly; counters like `trees_loaded` and `blobs_checked` should be `size_t`; and a boolean flag (`need_subtree_bases`) should use `bool` instead of `int`. He also suggests renaming the `base_trees` parameter to clarify its role as parent trees, and adds that the merge-walk logic expanding parent trees to extend the trust boundary would benefit from explanatory comments.

A recurring theme in the review is the use of `die()` for error handling. Patrick notes that this is inconsistent with Git’s ongoing libification efforts, where library code should return errors rather than terminating the process. He also points out that the error message for missing objects ("missing blob object") should be more precise ("unable to read"), as the object might be corrupt rather than missing. Additionally, he flags a potential issue with `parse_commit_or_die()` in partial clones, where missing commits could trigger a fatal error even though `fetch_if_missing` is disabled.

Patrick raises two broader design questions. First, he observes that the incremental mode’s performance degrades for very long incoming histories (10,000+ commits), becoming 1.5x slower than the full check, and suggests that Git could dynamically switch between modes when crossing a threshold. The algorithm already knows the number of commits upfront, so this fallback would be feasible. Second, he questions whether the recursive tree verification could risk stack overflow for very deep trees (up to 2048 layers) and suggests using a work queue instead.

The review is constructive and precise, typical of Patrick’s thorough style. While none of the points are showstoppers, they highlight opportunities to improve code clarity, robustness, and alignment with Git’s evolving practices. The author has already accepted similar feedback in prior iterations, so these issues are likely to be addressed in the next reroll. The series remains on track for integration, with Junio C Hamano having signaled strong interest and no remaining maintainer-level concerns.

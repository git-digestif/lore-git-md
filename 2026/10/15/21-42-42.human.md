This is a bugfix patch that prevents Git from dying when the index is locked during certain operations, particularly in the sequencer (rebase/cherry-pick).

The issue arises in `write_index_as_tree()`, which currently uses `LOCK_DIE_ON_ERROR` when acquiring the index lock. This causes Git to terminate if another process (like a background `git status`) holds the lock. Since Git 356ee4659b (2017), this behavior has been problematic because the sequencer now calls `write_index_as_tree()` in-process rather than in a child process, leaving rebase operations in an unrecoverable state if the lock is held.

The patch changes the lock acquisition to be non-fatal (`0` flag instead of `LOCK_DIE_ON_ERROR`) and skips writing the index if the lock is unavailable. This matches the behavior of other callers that only refresh the index and don't strictly require writing it back. The fix allows `git write-tree`, `git am`, and rebase operations to proceed even when another process holds the index lock.

The commit includes a reproduction case and a new test in `t/t0090-cache-tree.sh` that verifies `git write-tree` succeeds while the index is locked. The author reports encountering this issue while rebasing with Magit (which runs `git status` in the background) and provides a gdb recipe to trigger it reliably.

The patch looks well-motivated and addresses a real pain point for users of interactive Git tools. The change is minimal and focused, touching only the locking behavior in `cache-tree.c`. The test coverage is appropriate for the scope of the fix.

Subject: [PATCH] cache-tree: avoid crash when index is locked
Series version: standalone patch
Originating author: Szymon Wilczek
Thread type: bugfix

Core problem or goal
Prevent `git rebase` (and related commands) from crashing when another process (e.g., `git status` or Magit) holds the index lock during an in-process commit. The crash leaves the rebase in a half-picked state requiring manual recovery.

Current status
Under review. No prior versions. Patch is minimal, well-motivated, includes reproduction steps, and adds test coverage in `t/t0090-cache-tree.sh`.

Key technical details
- Subsystem: cache-tree
- Function modified: `write_index_as_tree()` in `cache-tree.c`
- Change: remove `LOCK_DIE_ON_ERROR` flag from `hold_lock_file_for_update()`, replace with gentle lock attempt
- Behavior: if lock is held, skip writing updated cache-tree back to index but still compute and return tree object
- Commands affected: `git rebase --continue`, `git write-tree`, `git am`
- Test added: `t/t0090-cache-tree.sh` verifies `git write-tree` succeeds while `.git/index.lock` exists
- Regression introduced in 356ee4659b (2017-11-24), which moved commit creation in-process during cherry-picks

Open questions and loose ends
None identified. Patch appears complete and addresses the issue without introducing new concerns.

Subject: [PATCH v2] cache-tree: avoid crash when index is locked
Series version: standalone patch, v2
Originating author: Szymon Wilczek
Thread type: bugfix

Core problem or goal
Prevent `git rebase` (and related commands) from crashing when another process (e.g., `git status` or Magit) holds the index lock during an in-process commit. The crash leaves the rebase in a half-picked state requiring manual recovery.

Current status
**Approved and ready for Junio to pick up.** v2 addresses all feedback from v1: commit message reordered to Git conventions (problem → cause → solution), lock-check condition tweaked from `0 <= fd` to `fd >= 0` for stylistic consistency, and message now clarifies the dual roles of `write_index_as_tree()` (tree computation vs. optional index write-back). **Substantive review from Patrick Steinhardt** in v1 endorsed the technical approach, praised test coverage, and requested only the commit message reordering. **Patrick's final acknowledgment in v2 confirms the patch is complete and ready for integration.**

Key technical details
- Subsystem: cache-tree
- Function modified: `write_index_as_tree()` in `cache-tree.c`
- Change: replace `LOCK_DIE_ON_ERROR` flag in `hold_lock_file_for_update()` with a non-blocking lock attempt
- Behavior: if lock is held, skip writing updated cache-tree back to index but still compute and return tree object
- Commands affected: `git rebase --continue`, `git write-tree`, `git am`
- Test added: `t/t0090-cache-tree.sh` verifies `git write-tree` succeeds while `.git/index.lock` exists
- Regression introduced in 356ee4659b (2017-11-24), which moved commit creation in-process during cherry-picks

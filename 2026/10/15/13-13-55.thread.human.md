This thread is about a patch series from Harald Nordgren that adds two new options to `git reflog` and `git log -g`: `--operations` (collapsing multi-step operations like rebase into single entries) and `--historical-branch` (showing which branch HEAD was on when each reflog entry was recorded). The series is now at v2, addressing earlier feedback on commit message clarity and output formatting.

The discussion has centered on whether these features belong in Git's core reflog subsystem. Junio C Hamano raised an architectural concern about the preparatory refactoring in patch 1/3, suggesting it might complicate future work to make reflog messages translatable and machine-readable. Harald pushed back lightly, asserting existing tests would catch any breakage, but the core question remains unresolved. Meanwhile, Kristoffer Haugsbakk and D. Ben Knoble highlighted alternatives like `tig reflog` and `git log -g -p`, questioning whether the new options overlap with existing tooling.

The latest review from Phillip Wood introduces significant new challenges. He argues `--operations` oversells its capabilities, since not all commands update the reflog (e.g., `git cherry-pick A B C` creates indistinguishable entries) and some operations leave no trace at all. He suggests the feature might be better implemented as a branch-specific filter. For `--historical-branch`, Phillip proposes a more flexible approach using format specifiers (e.g., `%gb`) instead of a dedicated flag, and flags a critical correctness issue with how the current implementation handles `git rebase <upstream> <branch>`. His concerns go beyond implementation details to question whether these features belong in Git's core at all, given the complexity of handling all edge cases correctly. The series remains under review with no clear path forward.

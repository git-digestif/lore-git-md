This thread is about a patch series from Harald Nordgren that adds two new options to `git reflog` and `git log -g`: `--operations` (collapsing multi-step operations like rebase into single entries) and `--historical-branch` (showing which branch HEAD was on when each entry was recorded). The series is now at v2, addressing earlier feedback on commit message clarity and output formatting, but deeper architectural and correctness concerns remain unresolved.

Junio C Hamano, the maintainer, has endorsed the *direction* of the series—making reflog output easier to understand—but raised two key points. First, he questioned whether the preparatory refactoring in patch 1/3 aligns with a potential future direction for translatable, machine-readable reflog messages. Second, he proposed a broader, long-term refactoring of multi-step commands (e.g., `git am`, `git cherry-pick`) to work on detached HEAD by default, which would naturally produce cleaner reflog entries without needing a heuristic-based filter. Harald’s latest reply sidesteps these architectural concerns, instead focusing on a cosmetic UX issue (cleaning up verbose branch references in reflog output) and agreeing with Junio’s suggestion to make `git reflog` default to the current branch rather than HEAD.

Phillip Wood’s substantive review of v2 introduced two major technical concerns. The first is that `--operations` oversells its capabilities: not all commands update the reflog (e.g., `git cherry-pick A B C` creates indistinguishable entries), and some operations leave no trace at all. The second is a critical correctness gap in `--historical-branch`’s handling of `git rebase <upstream> <branch>`, where the branch name in the "(finish)" message must be compared to the pre-rebase checkout. Phillip and D. Ben Knoble both propose replacing `--historical-branch` with a format specifier (e.g., `%gb`) for flexibility and alignment with Git’s existing decoration system. These critiques have not been addressed in Harald’s latest reply, leaving the series in a state where its core functionality is still under debate.

The series touches 23 files, including `reflog-walk.c`, `revision.c`, and `builtin/rebase.c`, and introduces new CLI options, constants, and test coverage. While the tests validate edge cases like stopped rebases and branch renames, Phillip’s review implies additional tests are needed for the `git rebase <upstream> <branch>` edge case. The thread continues to weigh whether these features belong in Git’s core or would be better served by third-party tools like `tig reflog` or a future structured event log. For now, the series remains under review with no clear path forward.

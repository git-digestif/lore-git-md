This thread is about a patch series by Harald Nordgren that adds two new options to `git reflog` and `git log -g`: `--operations` (collapsing multi-step operations like rebase into single entries) and `--historical-branch` (showing which branch HEAD was on when each reflog entry was recorded). The series is now at v2, addressing earlier feedback on commit message clarity and output formatting, but deeper architectural and correctness concerns remain unresolved.

Junio C Hamano, the maintainer, raised a long-term design tension in the preparatory refactoring (patch 1/3): the changes touch the same code paths that would need to emit machine-readable markers if reflog messages were ever made translatable, potentially complicating future work. Phillip Wood’s substantive review of v2 introduced two major technical critiques. First, `--operations` oversells its capabilities—it can’t reliably track all commands (e.g., `git cherry-pick A B C` leaves indistinguishable entries, and some operations leave no reflog trace at all). Second, `--historical-branch` has a critical correctness gap in handling `git rebase <upstream> <branch>`, where the branch name in the "(finish)" message must be compared to the pre-rebase checkout, requiring backward reflog traversal. Phillip proposed replacing `--historical-branch` with a format specifier (e.g., `%gb`) to align with Git’s existing decoration system, a suggestion now endorsed by D. Ben Knoble in the latest email.

The thread has shifted from usability improvements to architectural debates: whether these features belong in Git’s core at all, and whether a structured event log might be a better long-term solution than parsing reflog messages. No maintainer decisions have been made, and the series remains under review with no revised patches addressing the open questions. Key participants include Harald (author), Junio (maintainer), Phillip (reviewer), and Knoble (reviewer), with Kristoffer Haugsbakk also contributing earlier feedback. The discussion continues to weigh the trade-offs between usability, correctness, and Git’s existing design patterns.

This thread is about a patch series by Harald Nordgren that proposes two new options for `git reflog` and `git log -g`: `--operations` (collapsing multi-step operations like rebase into single entries) and `--historical-branch` (showing which branch HEAD was on when each reflog entry was recorded). The series is now at v2, addressing earlier feedback on commit message clarity and output formatting.

The discussion has taken a significant turn. Junio C Hamano, the maintainer, initially raised concerns about the preparatory refactoring in patch 1/3 conflicting with a potential future direction for translatable, machine-readable reflog messages. More recently, he endorsed the *goal* of making reflog output easier to understand but proposed two alternative paths forward: (1) a broader refactoring of multi-step commands (e.g., `git am`, `git cherry-pick`) to work on detached HEAD by default, which would naturally produce cleaner reflog entries, and (2) changing `git reflog`’s default behavior to operate on the current branch rather than HEAD. Harald accepted the second suggestion but has not engaged with the first.

Phillip Wood’s substantive review of v2 introduced two major technical concerns. First, `--operations` oversells its capabilities, as not all commands update the reflog (e.g., `git cherry-pick A B C` creates indistinguishable entries) and some operations leave no trace. Second, `--historical-branch` has a critical correctness gap in handling `git rebase <upstream> <branch>`, where the branch name in the "(finish)" message must be compared to the pre-rebase checkout, requiring backward reflog traversal. Phillip proposed replacing `--historical-branch` with a format specifier (e.g., `%gb`) for flexibility and alignment with Git’s existing decoration system. D. Ben Knoble endorsed this approach, suggesting a structured event log might be a simpler long-term solution than parsing reflog messages.

In the latest email, Harald tentatively accepts Phillip’s format-specifier proposal, calling it a “radical change” that would also drop `--operations` from the series. He defers to Phillip’s linked patch, which demonstrates the complexity of the rebase edge case, but does not engage with the broader critiques of `--operations` or the correctness issues. The thread now hinges on whether Phillip’s approach can be implemented robustly; if so, the series would need a ground-up redesign, shifting from dedicated flags to composable formatting options. No maintainer decisions or merge status have been reported, and the series remains in review with architectural, correctness, and scope debates unresolved.

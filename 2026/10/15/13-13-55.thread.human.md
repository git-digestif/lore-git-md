This thread is about improving `git reflog` and `git log -g` to make reflog output more useful, particularly during complex operations like rebasing. Harald Nordgren initially proposed two new options: `--operations` to collapse intermediate reflog entries from multi-step operations into single entries, and `--historical-branch` to show which branch HEAD was on when each entry was recorded. The series is now at version 2, addressing earlier feedback on commit messages and output formatting.

The discussion has shifted toward replacing these dedicated flags with format specifiers (e.g., `%gb`), which would expose the same information in a more composable way, aligning with Git’s existing decoration system. Junio C Hamano, the maintainer, has endorsed the *direction* of the series but proposed two broader changes: refactoring multi-step commands (like `git am` and `git cherry-pick`) to work on detached HEAD by default, which would naturally produce cleaner reflog entries, and changing `git reflog`’s default behavior to operate on the current branch rather than HEAD. Harald has accepted the latter suggestion but hasn’t engaged with the former.

Phillip Wood’s substantive review raised major concerns about both features. He argues `--operations` oversells its capabilities, as not all commands update the reflog (e.g., `git cherry-pick A B C` creates indistinguishable entries), and `--historical-branch` has a critical correctness gap in handling `git rebase <upstream> <branch>`. He and D. Ben Knoble propose replacing `--historical-branch` with a format specifier, which Harald has tentatively accepted. This would require a ground-up redesign of the feature, and the series’ future now hinges on whether Phillip’s approach can be implemented robustly. Kristoffer Haugsbakk’s latest feedback questions whether the original motivation (obscured reset points during rebasing) still holds, given that per-branch reflogs already show rebase start/finish entries clearly, though Patrick Steinhardt’s use case (tracking branch history across renames) remains unaddressed.

The series touches 23 files, including `reflog-walk.c`, `revision.c`, and test scripts, with no on-disk format changes. Key open questions include whether the reflog subsystem is the right place for this functionality, how to handle the `git rebase <upstream> <branch>` edge case, and whether the format-specifier approach can address the UX and correctness concerns raised. The thread remains in review, with architectural, correctness, and scope debates unresolved.

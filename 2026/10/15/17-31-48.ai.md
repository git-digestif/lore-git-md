This is a maintainer's reply in a bugfix thread targeting the files ref backend. Junio C Hamano engages with Patrick Steinhardt's design questions about Andy Koppe's patch, which fixes an inconsistency in how root refs (e.g., `HEAD`, `ORIG_HEAD`) are handled in the loose ref cache.

Junio proposes a conceptual alternative: instead of creating a separate temporary ref cache for root refs on demand, the files backend could maintain two persistent caches—one for refs under the `refs/` hierarchy and another for root refs. Callers would then explicitly choose whether to include root refs by combining the two caches. This approach would avoid recreating the root ref cache for every iterator that requests root refs, addressing Patrick's performance concern while keeping the logic simple and consistent.

The reply does not endorse or reject either approach outright, but it reframes the design space. The original patch remains a well-scoped bugfix, but Junio's suggestion opens the door to a more symmetric and potentially more efficient solution. No new implementation is provided, and the discussion is still focused on evaluating trade-offs rather than finalizing a design. The files touched (`files-backend.c`) and the subsystem (refs) remain unchanged, but the architectural direction may shift depending on how the thread evolves.

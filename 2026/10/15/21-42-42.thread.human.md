This thread is about a bugfix for a long-standing crash in `git rebase` (and related commands) when another process holds the index lock. Szymon Wilczek identified that the issue stems from a 2017 change that moved commit creation in-process during cherry-picks, making the `LOCK_DIE_ON_ERROR` flag fatal where it previously wasn't. The fix is simple: replace the fatal lock attempt with a gentle one, allowing the operation to proceed without writing the cache-tree back to the index if the lock is held.

The patch has already attracted attention for its practical impact—this crash is a real annoyance for users of tools like Magit that frequently refresh the index. The change is minimal and well-tested, with a new test case in `t/t0090-cache-tree.sh` verifying that `git write-tree` now succeeds even when `.git/index.lock` exists. No objections or alternative approaches have been raised yet, so this looks like a straightforward fix that could land soon. The affected commands (`git rebase --continue`, `git write-tree`, and `git am`) will now handle concurrent index access gracefully.

This thread is about a bugfix patch from Szymon Wilczek that prevents `git rebase` (and related commands) from crashing when another process holds the index lock during an in-process commit. The crash leaves rebases in a half-picked state requiring manual recovery, and the fix replaces a fatal lock attempt with a non-blocking one, allowing the command to proceed while skipping the optional cache-tree write-back if the lock is held.

The patch has evolved from v1 to v2, addressing feedback from Patrick Steinhardt. The v2 iteration reorders the commit message to follow Git conventions (symptom first, then cause, then solution) and tweaks a lock-check condition for stylistic consistency. The technical approach remains unchanged: the fix is minimal, well-motivated, and includes test coverage in `t/t0090-cache-tree.sh` to verify that `git write-tree` succeeds while `.git/index.lock` exists. Patrick’s substantive review in v1 endorsed the direction and praised the test coverage, leaving only the commit message reordering as a requested change.

The patch is now ready for final review and likely to be merged once Junio picks it up. No open questions or loose ends remain. The regression was introduced in 2017, and this fix addresses a real-world annoyance without introducing new concerns.

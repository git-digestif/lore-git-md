Thread identity
Subject: [PATCH 0/3] reflog: add --operations and --historical-branch options
Series version: v2 (v1 previously)
Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series

Core problem or goal
Add two new options to `git reflog` and `git log -g` to improve usability: `--operations` collapses intermediate reflog entries from multi-step operations (e.g., rebase, checkout) into single entries representing the actual commands executed, and `--historical-branch` shows which branch HEAD was on when each entry was recorded, addressing a long-standing pain point where users must manually trace back through "checkout: moving from" entries to determine branch context.

Current status
Under review; v2 posted, addressing prior feedback on commit message clarity (patch 1/3) and `--historical-branch` output formatting (branch names now appear in parentheses immediately after the operation description). Junio C Hamano has raised an architectural concern about patch 1/3 (the preparatory refactoring) potentially complicating a future transition to translatable, machine-readable reflog messages. No maintainer decisions or merge status reported; series remains in review.

Key technical details
- Files touched: 23 total across the series, including `reflog-walk.c`, `revision.c`, `revision.h`, `log-tree.c`, `builtin/rebase.c`, `builtin/checkout.c`, `reflog.h`, documentation, and test script `t/t1414-reflog-walk.sh` (293 lines). Patch 1/3 (v2) touches seven files (`builtin/branch.c`, `builtin/checkout.c`, `builtin/rebase.c`, `object-name.c`, `reflog.h`, `sequencer.c`, `wt-status.c`) for preparatory refactoring (replacing hard-coded reflog message strings with `#define` constants: `REFLOG_SWITCH_PREFIX`, `REFLOG_RENAME_PREFIX`, `REFLOG_STEP_START`, `REFLOG_STEP_FINISH`, `REFLOG_STEP_ABORT`). Junio’s review notes this refactoring touches the exact places that would need to emit machine-readable markers in a future structured reflog format, creating a potential dependency that could complicate later work.
- Patch 2/3 adds a `user_operation` flag to reflog entries and a `mark_operations()` function that scans the reflog to identify and mark entries to show (e.g., rebase finish/abort) or hide (e.g., intermediate rebase steps or branch switches), with careful handling of stopped rebases, `git stash`, and `git pull --rebase`.
- Patch 3/3 adds a `branch` field to the `reflog_info` struct, a `historical_branch` flag to `struct rev_info`, extends `reflog_walk_mark()` to accept this flag, and introduces `mark_branches()` to walk the reflog backward and determine branch context for each entry (detached HEAD, branch renames, non-HEAD refs). The branch name is formatted in parentheses after the `HEAD@{n}` selector and colored like a local branch decoration, preserving column alignment.
- New CLI options: `--operations` (collapses multi-step operations), `--historical-branch` (decorates entries with branch name at recording time).
- New symbols: five `#define` constants in `reflog.h`; `user_operation` flag in reflog entries; `historical_branch` flag in `struct rev_info`; `branch` field in `reflog_info` struct.
- No on-disk format changes.
- Test coverage: 293-line test script (`t/t1414-reflog-walk.sh`) validating new behavior, including edge cases (stopped/aborted rebases, `git stash`, `git pull --rebase`, branch renames, detached HEAD, non-HEAD reflogs, interaction with `--decorate`, `--operations`, and `--historical-branch`). Junio suggested adding tests to verify the "no behavior change" claim in patch 1/3.
- Both options are additive and require `--walk-reflogs`.

Open questions and loose ends
- **Architectural alignment**: Junio’s review flags a tension between the preparatory refactoring in patch 1/3 and a potential future direction—making reflog messages translatable by splitting them into human-readable and machine-parseable parts. The refactoring touches the exact places that would need to emit machine-readable markers, while later patches parse these strings, creating a dependency that could complicate future work. This concern has not been addressed by the author or other reviewers yet.
- **Scope and subsystem fit**: The thread continues to debate whether the reflog subsystem is the most appropriate place for this functionality, or if it overlaps with existing tooling (e.g., `git log --graph`, `tig reflog`, `git log -g -p`). Kristoffer Haugsbakk demonstrated how `tig reflog` already mitigates some pain points, and D. Ben Knoble noted `git log -g -p` can track reset points during rebasing. Harald Nordgren argues the new options could improve both Git’s native interface *and* third-party tooling (since Git options are passed through), but this framing has not resolved the architectural question.
- **UX trade-offs**: The `--historical-branch` option replaces standard commit decorations with historical branch names, which may surprise users expecting traditional output. The trade-off between usability and backward compatibility remains unaddressed.
- **Real-world validation**: Harald Nordgren and Kristoffer Haugsbakk describe personal pain points (e.g., manually inspecting commits with `git show` to track reset points during rebasing), but broader community feedback is limited. The introduction of `tig` and `git log -g -p` as alternatives may shift focus toward architectural considerations.

Subject: [PATCH 0/3] reflog: add --operations and --historical-branch options
Series version: v2 (v1 previously)
Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series

Core problem or goal
Add options to `git reflog` and `git log -g` to improve usability by exposing branch context and operation boundaries in reflog output. The thread has decisively pivoted from dedicated flags (`--operations`, `--historical-branch`) to format specifiers (e.g., `%gb`) for composability, aligning with Git’s existing decoration system. The original motivation—obscured reset points during rebasing—is partially addressed by per-branch reflogs, but Patrick Steinhardt’s use case (tracking branch history across renames) remains unaddressed. Junio C Hamano has proposed two broader architectural changes: (a) refactoring multi-step commands (e.g., `git am`, `git cherry-pick`) to work on detached HEAD by default, which would naturally produce cleaner reflog entries, and (b) changing `git reflog`’s default behavior to operate on the current branch rather than HEAD. Harald Nordgren has accepted (b) but not engaged with (a).

Current status
Under review; v2 posted addressing prior feedback on commit message clarity and `--historical-branch` output formatting. The series is at a crossroads due to substantive critiques from Phillip Wood, who identified fundamental flaws in both `--operations` (overselling capabilities, incomplete reflog coverage) and `--historical-branch` (correctness gap in `git rebase <upstream> <branch>`). The community now favors replacing both flags with format specifiers (e.g., `%gb`), but no alternative patches have been posted. Junio’s latest reply endorses the *direction* of the series (improving reflog usability) but sidesteps the architectural debate, instead proposing broader refactoring of multi-step commands and a change to `git reflog`’s default behavior. Kristoffer Haugsbakk’s latest reply notes that per-branch reflogs already address some pain points, but Patrick Steinhardt’s use case remains unaddressed. The series may require a ground-up redesign if the format-specifier approach is adopted. No maintainer decisions or merge status reported; series remains in review with architectural, correctness, and scope debates unresolved.

Key technical details
- Files touched: 23 total across the series, including `reflog-walk.c`, `revision.c`, `revision.h`, `log-tree.c`, `builtin/rebase.c`, `builtin/checkout.c`, `reflog.h`, documentation, and test script `t/t1414-reflog-walk.sh` (293 lines). Patch 1/3 (v2) refactors hard-coded reflog message strings into `#define` constants (`REFLOG_SWITCH_PREFIX`, `REFLOG_RENAME_PREFIX`, `REFLOG_STEP_START`, `REFLOG_STEP_FINISH`, `REFLOG_STEP_ABORT`) across seven files, touching the same code paths that would need to emit machine-readable markers for a future structured reflog format.
- Patch 2/3 adds a `user_operation` flag to reflog entries and a `mark_operations()` function to heuristically collapse multi-step operations (e.g., rebase finish/abort) while hiding intermediate steps. Phillip Wood’s review highlights gaps: `git cherry-pick A B C` creates indistinguishable entries, and working tree modifications leave no reflog trace. Junio’s proposal to refactor multi-step commands to work on detached HEAD would obviate the need for this heuristic.
- Patch 3/3 adds a `branch` field to `reflog_info` and a `mark_branches()` function to walk the reflog backward and determine branch context for each entry. Phillip Wood’s review identifies a correctness gap in `git rebase <upstream> <branch>`: the branch name in the "(finish)" message must be compared to the pre-rebase checkout, requiring backward traversal. His linked patch demonstrates the complexity. Both Phillip and D. Ben Knoble propose replacing `--historical-branch` with a format specifier (e.g., `%gb`), which would eliminate the need for the `historical_branch` flag and `branch` field in their current form.
- New CLI options: `--operations` and `--historical-branch` are now likely to be replaced by format specifiers (e.g., `%gb`). The format-specifier approach would allow users to include branch names in custom formats, mitigating UX trade-offs.
- New symbols: five `#define` constants in `reflog.h`; `user_operation` flag in reflog entries; `historical_branch` flag in `struct rev_info`; `branch` field in `reflog_info` struct. The format-specifier approach would obviate the latter two.
- No on-disk format changes.
- Test coverage: 293-line test script (`t/t1414-reflog-walk.sh`) validates new behavior, including edge cases (stopped/aborted rebases, `git stash`, `git pull --rebase`, branch renames, detached HEAD, non-HEAD reflogs, interaction with `--decorate`). Junio initially suggested additional tests for patch 1/3’s "no behavior change" claim but accepted existing coverage as sufficient. Phillip Wood’s review implies additional tests are needed for the `git rebase <upstream> <branch>` edge case. The format-specifier approach would require new tests for composability.

Open questions and loose ends
- **Architectural alignment**: Junio’s review flags a tension between patch 1/3’s refactoring and a potential future direction—making reflog messages translatable by splitting them into human-readable and machine-parseable parts. The refactoring touches code paths that would need to emit machine-readable markers, creating a dependency that could complicate later work. Harald Nordgren has not engaged with this concern. Junio’s latest reply proposes a broader refactoring of multi-step commands to work on detached HEAD by default, which would naturally produce cleaner reflog entries without heuristics. This would require significant changes to long-standing commands and is framed as a long-term shift.
- **Feature viability and scope**: Phillip Wood’s review challenges `--operations`’s fundamental viability, arguing it oversells capabilities (incomplete reflog coverage, indistinguishable multi-step operations). Kristoffer Haugsbakk notes that per-branch reflogs already address some pain points, but Patrick Steinhardt’s use case (tracking branch history across renames) remains unaddressed. Junio’s proposal to refactor multi-step commands would address the root cause but is a long-term effort. The thread debates whether the reflog subsystem is the right place for this functionality, with alternatives like `tig reflog` and filtering branch reflogs proposed.
- **Correctness of `--historical-branch`**: Phillip Wood identifies a critical gap in handling `git rebase <upstream> <branch>`, where the branch name in the "(finish)" message must be compared to the pre-rebase checkout. His linked patch demonstrates the complexity. Both Phillip and D. Ben Knoble propose exposing the branch name via a format specifier (e.g., `%gb`), which would require a ground-up redesign. Harald Nordgren tentatively accepts this proposal.
- **UX trade-offs**: `--historical-branch` replaces standard commit decorations with historical branch names, which may surprise users. The format-specifier approach would mitigate this by allowing users to include branch names in custom formats. The trade-off between usability and backward compatibility remains unaddressed.
- **Real-world validation**: Harald Nordgren and Kristoffer Haugsbakk describe personal pain points (e.g., tracking reset points during rebasing), but broader community feedback is limited. Kristoffer’s latest reply notes that per-branch reflogs already address some pain points, but Patrick Steinhardt’s use case remains unaddressed. Junio’s latest reply focuses on workflow improvements but does not reject the feature outright.

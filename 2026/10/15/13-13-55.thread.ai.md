Thread identity
Subject: [PATCH 0/3] reflog: add --operations and --historical-branch options
Series version: v2 (v1 previously)
Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series

Core problem or goal
Add two new options to `git reflog` and `git log -g` to improve usability: `--operations` collapses intermediate reflog entries from multi-step operations (e.g., rebase, checkout) into single entries representing the actual commands executed, and `--historical-branch` shows which branch HEAD was on when each entry was recorded, addressing a long-standing pain point where users must manually trace back through "checkout: moving from" entries to determine branch context.

Current status
Under review; v2 posted, addressing prior feedback on commit message clarity (patch 1/3) and `--historical-branch` output formatting (branch names now appear in parentheses immediately after the operation description). Junio C Hamano has raised an architectural concern about patch 1/3 (the preparatory refactoring) potentially complicating a future transition to translatable, machine-readable reflog messages, but accepted Harald Nordgren’s assertion that existing tests would catch any breakage. Phillip Wood’s substantive review of v2 introduces two major technical concerns: (1) `--operations` oversells its capabilities (not all commands update the reflog, and some operations leave no trace), and (2) `--historical-branch` has a critical correctness gap in handling `git rebase <upstream> <branch>` (the branch name in the "(finish)" message must be compared to the pre-rebase checkout, requiring backward reflog traversal). Phillip proposes exposing the branch name via a format specifier (e.g., `%gb`) instead of a dedicated flag, aligning with Git’s existing decoration system. No maintainer decisions or merge status reported; series remains in review with architectural and correctness debates unresolved.

Key technical details
- Files touched: 23 total across the series, including `reflog-walk.c`, `revision.c`, `revision.h`, `log-tree.c`, `builtin/rebase.c`, `builtin/checkout.c`, `reflog.h`, documentation, and test script `t/t1414-reflog-walk.sh` (293 lines). Patch 1/3 (v2) touches seven files (`builtin/branch.c`, `builtin/checkout.c`, `builtin/rebase.c`, `object-name.c`, `reflog.h`, `sequencer.c`, `wt-status.c`) for preparatory refactoring (replacing hard-coded reflog message strings with `#define` constants: `REFLOG_SWITCH_PREFIX`, `REFLOG_RENAME_PREFIX`, `REFLOG_STEP_START`, `REFLOG_STEP_FINISH`, `REFLOG_STEP_ABORT`). Junio’s review notes this refactoring touches the exact places that would need to emit machine-readable markers in a future structured reflog format, creating a potential dependency.
- Patch 2/3 adds a `user_operation` flag to reflog entries and a `mark_operations()` function that scans the reflog to identify and mark entries to show (e.g., rebase finish/abort) or hide (e.g., intermediate rebase steps or branch switches), with handling of stopped rebases, `git stash`, and `git pull --rebase`. Phillip Wood’s review highlights that this logic is incomplete: `git cherry-pick A B C` creates multiple indistinguishable entries, and working tree modifications leave no reflog trace.
- Patch 3/3 adds a `branch` field to the `reflog_info` struct, a `historical_branch` flag to `struct rev_info`, extends `reflog_walk_mark()` to accept this flag, and introduces `mark_branches()` to walk the reflog backward and determine branch context for each entry. Phillip Wood’s review identifies a correctness gap: the current implementation does not handle `git rebase <upstream> <branch>` correctly, where the branch name in the "(finish)" message must be compared to the pre-rebase checkout (requiring backward reflog traversal). His linked patch demonstrates the complexity of this edge case.
- New CLI options: `--operations` (collapses multi-step operations), `--historical-branch` (decorates entries with branch name at recording time). Phillip Wood proposes replacing `--historical-branch` with a format specifier (e.g., `%gb`) for flexibility and alignment with Git’s existing decoration system.
- New symbols: five `#define` constants in `reflog.h`; `user_operation` flag in reflog entries; `historical_branch` flag in `struct rev_info`; `branch` field in `reflog_info` struct.
- No on-disk format changes.
- Test coverage: 293-line test script (`t/t1414-reflog-walk.sh`) validating new behavior, including edge cases (stopped/aborted rebases, `git stash`, `git pull --rebase`, branch renames, detached HEAD, non-HEAD reflogs, interaction with `--decorate`, `--operations`, and `--historical-branch`). Junio suggested adding tests to verify the "no behavior change" claim in patch 1/3; this was discussed and deemed unnecessary by Harald, with Junio accepting the existing test coverage as sufficient. Phillip Wood’s review implies additional tests are needed for the `git rebase <upstream> <branch>` edge case.

Open questions and loose ends
- **Architectural alignment**: Junio’s review flags a tension between the preparatory refactoring in patch 1/3 and a potential future direction—making reflog messages translatable by splitting them into human-readable and machine-parseable parts. The refactoring touches the exact places that would need to emit machine-readable markers, while later patches parse these strings, creating a dependency that could complicate future work. Harald Nordgren has not engaged with this concern beyond asserting existing tests would catch any breakage.
- **Feature viability and scope**: Phillip Wood’s review challenges the fundamental viability of `--operations`, arguing it oversells its capabilities (not all commands update the reflog, and some operations leave no trace) and may not belong in Git’s core given existing alternatives like `tig reflog`. He suggests the feature’s goals could be better achieved by filtering the branch reflog (noting `git reflog` should default to the current branch rather than HEAD). The thread continues to debate whether the reflog subsystem is the most appropriate place for this functionality.
- **Correctness of `--historical-branch`**: Phillip Wood identifies a critical correctness gap in `--historical-branch`’s handling of `git rebase <upstream> <branch>`, where the branch name in the "(finish)" message must be compared to the pre-rebase checkout (requiring backward reflog traversal). His linked patch demonstrates the complexity of this edge case, which the series currently does not address. He proposes exposing the branch name via a format specifier (e.g., `%gb`) instead of a dedicated flag, which would require a ground-up redesign of the feature.
- **UX trade-offs**: The `--historical-branch` option replaces standard commit decorations with historical branch names, which may surprise users expecting traditional output. Phillip Wood’s proposal to use a format specifier would mitigate this by allowing users to include the branch name in custom formats. The trade-off between usability and backward compatibility remains unaddressed.
- **Real-world validation**: Harald Nordgren and Kristoffer Haugsbakk describe personal pain points (e.g., manually inspecting commits with `git show` to track reset points during rebasing), but broader community feedback is limited. The introduction of `tig` and `git log -g -p` as alternatives may shift focus toward architectural considerations.

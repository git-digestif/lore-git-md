Subject: [PATCH 0/3] reflog: add --operations and --historical-branch options
Series version: v1
Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series

Core problem or goal
Add two new options to `git reflog` and `git log -g` to improve usability: `--operations` collapses intermediate reflog entries from multi-step operations (e.g., rebase, checkout) into single entries representing the actual commands executed, and `--historical-branch` shows which branch HEAD was on when each entry was recorded, addressing a long-standing pain point where users must manually trace back through "checkout: moving from" entries to determine branch context.

Current status
Under review; v1 posted. No maintainer decisions or merge status reported. Author has acknowledged Kristoffer Haugsbakk’s feedback on the commit message for patch 1/3 and D. Ben Knoble’s feedback on output formatting for `--historical-branch`, signaling intent to revise, but no v2 has been posted yet.

Key technical details
- Files touched: 23 total, including `reflog-walk.c`, `revision.c`, `revision.h`, `log-tree.c`, `builtin/rebase.c`, `builtin/checkout.c`, `reflog.h`, documentation, and new test script `t/t1414-reflog-walk.sh` (293 lines total: 198 from patch 2/3, 95 from patch 3/3).
- New CLI options: `--operations` (collapses rebase/checkout/rename sequences into single entries), `--historical-branch` (decorates entries with branch name at time of recording, replacing standard commit decorations).
- Internal changes: refactoring of reflog entry markers into `#define` constants (`REFLOG_SWITCH_PREFIX`, `REFLOG_RENAME_PREFIX`, `REFLOG_STEP_START`, `REFLOG_STEP_FINISH`, `REFLOG_STEP_ABORT`) to prevent drift between writing and parsing; no on-disk format changes. Patch 2/3 adds a `user_operation` flag to reflog entries and a `mark_operations()` function that scans the reflog to identify and mark entries that should be shown (e.g., rebase finish/abort) or hidden (e.g., intermediate rebase steps or branch switches). Patch 3/3 adds a `historical_branch` flag to `struct rev_info`, extends `reflog_walk_mark()` to accept this flag, and introduces a `mark_branches()` function that scans the reflog to determine the branch for each entry, handling edge cases such as detached HEAD (showing "detached at <commit>"), branch renames (showing the name at the time of the entry), and reflogs for non-HEAD refs (showing the ref name itself). Both options are additive and require `--walk-reflogs` to be set.
- New symbols: five new `#define` constants in `reflog.h`; `user_operation` flag in reflog entries; `historical_branch` flag in `struct rev_info`.
- Test coverage: 293-line test script validating new behavior, including edge cases like stopped/aborted rebases, `git stash`, `git pull --rebase`, branch renames, detached HEAD, non-HEAD reflogs, and interaction with `--decorate`. The test script does not yet cover the output formatting issue raised by D. Ben Knoble (alignment of the `HEAD@{n}` column when `--historical-branch` is used).

Open questions and loose ends
- **Commit message clarity (patch 1/3)**: Kristoffer Haugsbakk raised a substantive review objection to the commit message of the preparatory refactoring (patch 1/3), arguing that it fails to clearly communicate the motivation and rationale upfront. The message currently enumerates reflog message formats without first explaining the problem (preventing drift between writing and parsing strings), forcing reviewers to infer the purpose from a passive clause ("a later commit adds a reader for all of them"). The author has acknowledged the feedback and agreed to revise, but the revised text is not yet posted. This remains a blocker for maintainer acceptance.
- **Output formatting (--historical-branch)**: D. Ben Knoble raised a usability concern about the placement of the branch name decoration in the `--historical-branch` output. The current implementation appends the branch name at the end of each line, breaking the fixed-width alignment of the `HEAD@{n}` column that users rely on for visual parsing. Knoble suggested three alternative placements (end-of-line, immediately after `HEAD@{n}`, or immediately after the operation prefix) and noted trade-offs for each, particularly when branch names vary in length. The author has not yet responded, so this remains an open point for v2.
- **UX trade-offs**: The `--historical-branch` option replaces standard commit decorations with historical branch names, which may surprise users expecting the traditional output. The trade-off between usability and backward compatibility has not been explicitly addressed in the thread.
- **Scope and subsystem fit**: The thread has raised questions about whether the reflog subsystem is the most appropriate place for this functionality, or if it might overlap with or duplicate existing tooling (e.g., `git log --graph` or third-party tools like `tig`). Kristoffer Haugsbakk demonstrated how `tig reflog` already mitigates some of the pain points the series aims to address, and D. Ben Knoble later noted that `git log -g -p` can also help track reset points during rebasing. These observations have prompted discussion about whether Git’s core commands should replicate features already provided by external tools, or if the project should focus on improving interoperability with those tools. Harald Nordgren’s reply positions the new options as enhancements that could improve both Git’s native interface *and* third-party tooling (since Git options are passed through to tools like `tig`), but this framing has not yet resolved the broader architectural question.
- **Real-world validation**: Harald Nordgren and Kristoffer Haugsbakk have both described personal pain points with the current reflog usability (e.g., manually inspecting commits with `git show` to track reset points during rebasing), reinforcing the feature's value. However, broader community feedback remains limited, and the introduction of `tig` and `git log -g -p` as alternatives may shift the conversation toward architectural considerations rather than immediate usability improvements.

This is a bugfix patch targeting the fetch subsystem, specifically addressing a regression in shallow fetches when backfilling tags. It is the third iteration (v3) of a patch series that has been under active review.

The patch fixes a performance regression introduced by commit 0e358de64a ("fetch: use batched reference updates", 2025-05-19). The issue occurs because batched updates delay committing references to disk until after tag backfilling begins. During shallow fetches, this means the client has no references to report in the 'have' section of negotiation, causing the server to send all objects in the repository. The fix splits the transaction into two: one for the fetched references and another for backfilling tags. This ensures the client can report the correct 'have' references during negotiation, restoring performance while maintaining the benefits of batched updates.

The patch touches `builtin/fetch.c` and adds two new tests in `t/t5510-fetch.sh`. One test validates that the 'haves' are correctly advertised when backfilling tags, while the other ensures upstream tracking info is set even when the main ref update is rejected but a tag is backfilled. The commit message provides clear benchmarks showing the fix is 17.38±0.61 times faster than the pre-batched-update behavior, with only a 1% slowdown compared to the single-transaction approach.

This iteration (v3) addresses edge cases raised by Junio C Hamano in the previous review. It introduces a separate error variable (`commit_ref_ret`) to ensure errors from the main ref updates don't cause total failure and that post-fetch operations (like writing `FETCH_HEAD` and setting upstream config) still execute even if the tag backfill transaction fails. The patch also clarifies the behavior for `--atomic` fetches, documenting that atomicity is preserved at the cost of potential full clones if tag backfilling triggers the negotiation issue.

The patch looks well-crafted and addresses a real problem with thorough test coverage and clear performance benchmarks. The edge cases are thoughtfully handled, and the commit message provides a detailed rationale for the trade-offs involved. This version appears ready for further review and likely inclusion in `next` once any final feedback is addressed.

This is the second patch in Jun Wu’s two-part series introducing a configurable index lock timeout (`core.indexLockTimeout`) to reduce contention between background IDE operations and user commands. The patch itself changes `git commit` to acquire the index lock *before* reading the index, fixing a long-standing (20+ years) race condition where concurrent updates (e.g., from `git add`) could be silently discarded if `git commit` read the index before locking. Jun Wu confirms he will revise the commit message for v2 to explicitly motivate this lock-order change as a correctness fix, addressing Jeff King’s feedback that the current message understates the significance of the race.

The email also reveals a broader scope: `git commit` is not the only command with this read-before-lock issue—others like `reset`, `rebase`, `stash`, `am`, and `merge` are similarly affected, with varying degrees of complexity to fix. Jun Wu proposes a phased approach: land the timeout feature first (Patch 1/2), then incrementally address the lock-order issues in subsequent patches, starting with the simplest or most commonly used commands. This strategy is pragmatic—the timeout logic automatically disables itself for any command that still reads before locking, so Patch 1 alone cannot make existing races worse. However, it leaves open the question of whether the series should block on fixing all affected commands before merging, or whether the incremental approach is acceptable.

Jun Wu’s reply also touches on a potential alternative design: an "optimistic read" pattern where commands read the index without the lock, then verify post-lock that the index hasn’t changed. While this could reduce lock contention, it would require deeper changes and isn’t implemented here. The current patch’s simpler approach—locking earlier—may hold the lock longer, but the timeout mechanism mitigates this trade-off. The discussion suggests that while the series is technically sound, its long-term impact depends on how many other commands eventually adopt the corrected lock order. For now, the focus remains on `git commit`, with the door open for follow-up work.

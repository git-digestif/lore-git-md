This is the second patch in Christian Couder’s five-part series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration to mark repositories as trusted for lazy fetching. This patch is pure refactoring: it extracts reusable path-allowlist logic from the existing `safe.directory` code into two new helpers, `path_allowlist_apply()` and `path_allowlist_config_apply()`, so that the upcoming `uploadpack.lazyFetchTrusted` feature can reuse the same validation rules.

The patch moves roughly 50 lines of code from `safe_directory_cb()` into the new helpers, then rewires the callback to use them. The extracted logic is generalized: instead of hard-coding the `safe.directory` rules, the helpers accept a caller-provided `allow_path()` function that decides whether a path is acceptable. This lets future callers (like `uploadpack.lazyFetchTrusted`) enforce their own policies—e.g., requiring absolute paths—without duplicating the path-matching machinery. A `NEEDSWORK` comment flags a latent design issue: the helpers silently ignore non-existent paths, which could mask typos; Christian plans to address this in a follow-up.

The patch also changes the `is_safe` field in `struct safe_directory_data` from `int` to `bool` to match the helpers’ signature, and adds a small `struct path_allowlist_cb_data` to pass the config key name to the `allow_path()` callback. The refactoring is observably equivalent: the only behavioral difference is that `safe.directory` now uses the new helpers, with no change in how it validates paths.

This is a well-structured preparatory patch with no functional impact. It’s a candidate for early integration if the series stalls, and the extracted helpers will be used in patch 3/5 to implement the actual `uploadpack.lazyFetchTrusted` logic.

Thread identity
Subject: RFC: "limbo" object-format state for new repositories
Series version: RFC (no patch series yet)
Originating author: Jeff King (peff@peff.net)
Thread type: RFC / design discussion

Core problem or goal
When Git 3.0 transitions to SHA-256 as the default object format, users pushing to newly created bare repositories on forges (e.g., GitHub) will encounter fatal errors if the client and server disagree on the object format. The server must already be configured for either SHA-1 or SHA-256, and mismatches cause push failures. The goal is to eliminate this usability pain point by allowing empty repositories to advertise a "limbo" state—no object format yet—so the server can dynamically adopt the format of the first incoming push, similar to how GitHub currently sets the default branch on first push.

Current status
No implementation exists. The proposal remains in the conceptual stage, soliciting feedback on design feasibility, compatibility, and policy implications. No prior versions or related patch series.

Key technical details
- Subsystems touched: wire protocol (capability negotiation), repository initialization logic, atomic state transitions on the server.
- Proposed new capability: `magic-limbo` to signal limbo support, while continuing to advertise `object-format=sha1` for backward compatibility with older clients (2.29+). The advertised SHA-1 format is intentional, as Git 3.0’s SHA-256 transition has not yet occurred, and users with SHA-256 repos are assumed to be deliberate and can configure the server accordingly.
- Multi-format advertisement: Brian m. Carlson proposes advertising both `object-format=sha256` and `alt-object-format=sha1` (or similar) to explicitly signal SHA-256 support and accommodate future hash algorithms. This approach relies on modern Git versions (2.41+) safely handling multiple `object-format` directives, as demonstrated by a 2023 fix (aa962fef27) for a multi-valued capability parsing bug.
- Atomic adoption: server must commit to the client's object format before accepting the push.
- Edge cases raised: simultaneous mismatched pushes, mirror pushes, multiple refs with conflicting formats, compatibility with existing clients (2.29+), and server-side policy enforcement (e.g., disallowing SHA-1). Wire protocol considerations include whether older clients will ignore the `magic-limbo` capability (assumed safe) and the viability of multiple `object-format` directives (historically risky but now potentially feasible).
- Policy enforcement: Jeff views this as a forge-level concern (e.g., UI controls in GitHub’s repo creation flow), while Brian advocates for Git-native support (e.g., config or command-line options) to ensure consistent behavior across all access methods (APIs, non-push commands).

Open questions and loose ends
- **Compatibility**: Can modern clients (2.41+) safely handle multiple `object-format` directives, and is the project willing to drop support for versions with only experimental SHA-256? Junio’s earlier skepticism about historical capability-parsing bugs remains unresolved.
- **Policy enforcement**: Should Git provide native mechanisms (e.g., config) to enforce hash algorithm policies, or is this purely a forge-level concern? Brian argues for Git-native support to ensure consistency across all repository access methods.
- **Scope of applicability**: Should the limbo mechanism extend beyond pushes (e.g., to local commits), and how would the repository’s config be handled during the initial state transition?
- **Atomicity**: Can the server reliably commit to the client’s object format before accepting the push, especially in edge cases like mirror pushes?
- **Urgency vs. complexity**: Is the complexity of addressing these challenges justified by the usability gain, given the intentional design choice to prioritize backward compatibility? Brian strongly opposes delaying Git 3.0’s SHA-256 transition to accommodate the limbo feature, prioritizing SHA-1 deprecation over usability friction for new repositories.

Participant positions
- **Jeff King (Peff)**: Proposed the `magic-limbo` capability and initially dismissed multiple `object-format` directives due to corner cases. Position: the limbo feature resolves compatibility concerns while leaving policy enforcement to forges. Assumes older clients will safely ignore the new capability.
- **brian m. carlson**: **Substantive review** expressing cautious support but raising critical compatibility, policy, and urgency concerns. Initially highlighted that `object-format=limbo` would break existing clients (2.29+) and later proposed advertising both SHA-1 and SHA-256 to explicitly signal support. Position: the limbo feature is feasible but must not delay Git 3.0’s SHA-256 transition. Advocates for Git-native policy enforcement (e.g., config) to ensure consistency across all repository access methods. Cites a 2023 fix (aa962fef27) as evidence that modern clients can safely handle multiple `object-format` directives.
- **Junio C Hamano**: **Substantive review** acknowledging the conceptual appeal of multiple `object-format` directives but expressing skepticism about their practical viability due to historical capability-parsing bugs. Position: while the idea is theoretically sound, the project’s history of edge cases makes it risky to rely on. Shifts the burden of proof to testing or investigating past bugs before proceeding.

Related work
- Git 3.0’s hash-algorithm transition (SHA-1 to SHA-256) is the motivating context, with Brian emphasizing the urgency of the transition.
- GitHub’s existing behavior for setting the default branch on first push serves as a usability precedent.
- The 2023 fix for multi-valued capability parsing (aa962fef27) is relevant to the feasibility of advertising multiple `object-format` directives.

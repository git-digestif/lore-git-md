Thread identity
Subject: RFC: "limbo" object-format state for new repositories
Series version: RFC (no patch series yet)
Originating author: Jeff King (peff@peff.net)
Thread type: RFC / design discussion

Core problem or goal
When Git 3.0 transitions to SHA-256 as the default object format, users pushing to newly created bare repositories on forges (e.g., GitHub) will encounter fatal errors if the client and server disagree on the object format. The server must already be configured for either SHA-1 or SHA-256, and mismatches cause push failures. The goal is to eliminate this usability pain point by allowing empty repositories to advertise a "limbo" state—no object format yet—so the server can dynamically adopt the format of the first incoming push, similar to how GitHub currently sets the default branch on first push.

Current status
No implementation exists. The proposal remains in the conceptual stage, soliciting feedback on design feasibility, compatibility, and policy implications. The refined design now proposes a dual-format advertisement (`object-format=sha256` and `alt-object-format=sha1`) instead of the earlier `magic-limbo` capability, explicitly declaring support for both hash algorithms. Jeff King (Peff) does not plan to implement the feature himself but leaves the door open for others (e.g., Scott) to do so within the Git 3.0 release cycle. The feature is not intended to delay the SHA-256 transition.

Key technical details
- Subsystems touched: wire protocol (capability negotiation), repository initialization logic (`git init`), server-side state transitions (`receive-pack`), and config-based policy enforcement.
- Proposed capability advertisement: `object-format=sha256` and `alt-object-format=sha1` (or similar) to explicitly signal support for both hash algorithms. This replaces the earlier `magic-limbo` proposal and relies on modern Git versions (2.41+) safely handling multiple `object-format` directives, as demonstrated by a 2023 fix (aa962fef27) for a multi-valued capability parsing bug.
- Config-based state management: A new config flag (e.g., `core.objectFormatLimbo`) would mark the limbo state, set by `git init` and respected by `receive-pack`. The flag would *not* be enabled by default, requiring explicit opt-in by forges or administrators.
- Atomic adoption: The server must commit to the client's object format before accepting the push. Edge cases include simultaneous mismatched pushes, mirror pushes, and multiple refs with conflicting formats.
- Compatibility: The proposal assumes modern clients (2.41+) can safely handle the dual-format advertisement. Older clients (2.29+) are expected to ignore the `alt-object-format` capability, defaulting to SHA-1 for backward compatibility.
- Policy enforcement: Jeff now agrees that Git should provide native mechanisms (e.g., config) to enforce the limbo state, but emphasizes that the feature should not be enabled by default. Forges (e.g., GitHub) would build additional policy layers on top.
- Scope of applicability: The limbo mechanism is scoped to pushes only. Non-push repository modifications (e.g., via APIs) would require additional handling, such as falling back to a default format or rejecting the operation until the repository exits limbo.

Open questions and loose ends
- **Compatibility**: Can modern clients (2.41+) reliably handle the dual-format advertisement (`object-format=sha256` and `alt-object-format=sha1`), and is the project willing to drop support for versions with only experimental SHA-256? Junio’s earlier skepticism about historical capability-parsing bugs remains unresolved.
- **Policy enforcement**: While Jeff now agrees that Git should provide a config flag for the limbo state, the broader question of whether Git should enforce hash algorithm policies natively (e.g., disallowing SHA-1) or leave this to forges remains contested. Brian m. Carlson advocates for Git-native support to ensure consistency across all repository access methods.
- **Non-push operations**: How should the repository handle operations like local commits or API-driven modifications when in the limbo state? Should it reject them, fall back to a default format, or adopt a different mechanism?
- **Atomicity**: Can the server reliably commit to the client’s object format before accepting the push, especially in edge cases like mirror pushes or simultaneous mismatched pushes?
- **Urgency vs. complexity**: Is the complexity of addressing these challenges justified by the usability gain, given the intentional design choice to prioritize backward compatibility? Brian strongly opposes delaying Git 3.0’s SHA-256 transition to accommodate the limbo feature, while Jeff clarifies that the feature is not intended to delay the transition.

Participant positions
- **Jeff King (Peff)**: Refined the proposal to use a dual-format advertisement (`object-format=sha256` and `alt-object-format=sha1`) instead of `magic-limbo`, addressing Brian’s compatibility concerns. Position: the limbo feature is a building block for forges to reduce friction, with Git providing a config flag (not enabled by default) to mark the limbo state. Policy enforcement should remain a forge-level concern, though Git-native config support is acceptable. Does not plan to implement the feature himself but believes it is feasible within the Git 3.0 release cycle.
- **brian m. carlson**: **Substantive review** expressing cautious support for the refined proposal but maintaining critical compatibility, policy, and urgency concerns. Initially highlighted that `object-format=limbo` would break existing clients (2.29+) and later proposed the dual-format advertisement as a safer alternative. Position: the limbo feature must not delay Git 3.0’s SHA-256 transition and should include Git-native policy enforcement (e.g., config) to ensure consistency across all repository access methods. Cites a 2023 fix (aa962fef27) as evidence that modern clients can safely handle multiple `object-format` directives.
- **Junio C Hamano**: **Substantive review** acknowledging the conceptual appeal of multiple `object-format` directives but expressing skepticism about their practical viability due to historical capability-parsing bugs. Position: while the idea is theoretically sound, the project’s history of edge cases makes it risky to rely on. Shifts the burden of proof to testing or investigating past bugs before proceeding.

Thread identity
Subject: RFC: "limbo" object-format state for new repositories
Series version: RFC (no patch series yet)
Originating author: Jeff King (peff@peff.net)
Thread type: RFC / design discussion

Core problem or goal
When Git 3.0 transitions to SHA-256 as the default object format, a user pushing to a newly created bare repository on a forge (e.g., GitHub) will encounter a fatal error if the client and server disagree on the object format. The server must already be configured for either SHA-1 or SHA-256, and if the client uses the other format, the push fails. The goal is to eliminate this usability pain point by allowing empty repositories to advertise a "limbo" state—no object format yet—so the server can dynamically adopt the format of the first incoming push, similar to how GitHub currently sets the default branch on first push.

Current status
No implementation exists. The proposal remains in the conceptual stage, soliciting feedback on design feasibility, compatibility, and policy implications. No prior versions or related patch series.

Key technical details
- Subsystems touched: wire protocol (capability negotiation), repository initialization logic, atomic state transitions on the server.
- Proposed new capability: `magic-limbo` to signal limbo support, while continuing to advertise `object-format=sha1` for backward compatibility with older clients (2.29+). The advertised SHA-1 format is intentional, as Git 3.0’s SHA-256 transition has not yet occurred, and users with SHA-256 repos are assumed to be deliberate and can configure the server accordingly.
- Atomic adoption: server must commit to the client's object format before accepting the push.
- Edge cases raised: simultaneous mismatched pushes, mirror pushes, multiple refs with conflicting formats, compatibility with existing clients (2.29+), and server-side policy enforcement (e.g., disallowing SHA-1).
- Wire protocol considerations: whether older clients will ignore the `magic-limbo` capability (assumed safe), and past crasher bugs in capability parsing. Multiple `object-format` directives are dismissed due to potential corner cases, though Junio C Hamano notes the conceptual appeal of this approach while cautioning about historical compatibility risks.

Open questions and loose ends
- **Compatibility**: Does the `magic-limbo` capability resolve the breakage risk for older clients (2.29+)? Are there edge cases where clients might still misbehave (e.g., capability parsing bugs)? Junio’s reply underscores the need to investigate past crasher bugs or test whether modern clients can safely handle multiple `object-format` directives.
- **Policy enforcement**: How can forges or organizations enforce specific hash algorithms (e.g., disallow SHA-1) while supporting the limbo mechanism? Jeff suggests this is a forge-level concern (e.g., UI controls like a tri-state selector in GitHub’s repo creation flow) rather than a Git protocol one.
- **Scope of applicability**: Should the limbo mechanism extend beyond pushes (e.g., to local commits), and how would the repository’s config be handled during the initial state transition?
- **Atomicity**: Can the server reliably commit to the client’s object format before accepting the push, especially in edge cases like mirror pushes?
- **Justification**: Is the complexity of addressing these challenges justified by the usability gain, given the intentional design choice to prioritize backward compatibility?

Participant positions
- **Jeff King (Peff)**: Proposed the concept and refined it in response to feedback. Position: the `magic-limbo` capability resolves compatibility concerns while leaving policy enforcement to forges. Dismisses multiple `object-format` directives due to corner cases. Assumes older clients will safely ignore the new capability.
- **brian m. carlson**: **Substantive review** expressing cautious support but raising critical compatibility and policy concerns. Initially highlighted that `object-format=limbo` would break existing clients (2.29+) and suggested exploring multiple `object-format` directives. Position: the idea is feasible but complex; compatibility and policy challenges must be addressed. Awaiting further clarification on the `magic-limbo` proposal.
- **Junio C Hamano**: **Substantive review** acknowledging the conceptual appeal of multiple `object-format` directives but expressing skepticism about their practical viability due to historical capability-parsing bugs. Position: while the idea is theoretically sound, the project’s history of edge cases makes it risky to rely on. Shifts the burden of proof to testing or investigating past bugs before proceeding.

Related work
- Git 3.0’s hash-algorithm transition (SHA-1 to SHA-256) is the motivating context.
- GitHub’s existing behavior for setting the default branch on first push serves as a usability precedent.

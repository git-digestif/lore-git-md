This thread is an **RFC proposal** from Jeff King (Peff) to introduce a "limbo" state for Git's object format, addressing a usability issue with the upcoming Git 3.0 hash-algorithm transition. Currently, when a user pushes to a newly created bare repository (e.g., on GitHub), the repository must already be configured for either SHA-1 or SHA-256. If the client and server disagree, the push fails, forcing users to manually reconfigure or recreate the remote repository. Peff's proposal would allow empty repositories to advertise a "limbo" state—no object format yet—enabling the server to dynamically adopt the format of the first incoming push. This mirrors GitHub’s existing behavior for setting the default branch on first push but is more complex due to the object format being negotiated during the initial capability advertisement.

The proposal is still in the conceptual phase, with no implementation yet. Peff outlines the core idea: the server advertises `object-format=limbo`, the client responds with its format, and the server atomically commits to that format before accepting the push. He acknowledges potential race conditions (e.g., simultaneous mismatched pushes) but sees no fundamental blockers. The discussion is likely to focus on edge cases—such as what happens if the first push is a mirror or includes multiple refs with conflicting formats—and whether the complexity is justified by the usability gain. If implemented, this would be a **feature** targeting the object-format subsystem, touching the wire protocol, repository initialization logic, and atomic state transitions on the server.

Key participants so far include Peff as the originator, and the thread is open for feedback from the broader community, particularly those with expertise in the object-format subsystem or protocol design. No decisions or agreements have been made yet, and the proposal remains untested. The outcome will depend on whether the community sees the usability benefit as worth the added complexity.

This thread is an RFC from Jeff King (Peff) proposing a "limbo" state for newly created Git repositories to avoid a usability pitfall during Git 3.0's transition to SHA-256. Currently, if a user pushes to a fresh bare repository on a forge (like GitHub), the push fails if the client and server disagree on the object format. Peff's solution would let empty repositories advertise a "limbo" state, dynamically adopting the format of the first incoming push—mirroring how forges already handle default branch creation.

The discussion remains conceptual, with no implementation yet. Key technical details include a proposed `magic-limbo` capability to signal support while maintaining backward compatibility with older clients (2.29+), and the need for atomic state transitions on the server. Open questions revolve around compatibility (will older clients misbehave?), policy enforcement (can forges disallow SHA-1?), and whether the complexity is justified.

Brian M. Carlson raised substantive concerns about compatibility and policy, while Junio C Hamano added a pragmatic note of caution: while multiple `object-format` directives might seem elegant, past bugs in capability parsing make this approach risky. The thread now hinges on whether these compatibility issues can be resolved or worked around. No decisions have been made, but the discussion highlights the tension between usability and the project's history of protocol edge cases.

This thread is exploring a design for a "limbo" state in Git repositories to smooth the transition to SHA-256 as the default object format in Git 3.0. The idea, proposed by Jeff King (Peff), would allow empty repositories to dynamically adopt the object format of the first incoming push, avoiding fatal errors when clients and servers disagree on SHA-1 vs. SHA-256. Peff suggested a new `magic-limbo` capability to signal this support while maintaining backward compatibility with older clients.

The discussion has since focused on two key points raised by brian m. carlson. First, brian argues that servers should advertise *both* SHA-1 and SHA-256 support (via `object-format` and `alt-object-format`) to explicitly signal SHA-256 readiness, rather than relying on a single advertised format. He cites a 2023 fix for multi-valued capability parsing as evidence that modern Git versions (2.41+) can handle this safely, provided the project is willing to drop support for older versions with only experimental SHA-256. Second, brian strongly opposes delaying Git 3.0's SHA-256 transition until the limbo feature is implemented, prioritizing the move away from SHA-1 even if it means some usability friction for new repositories. He also advocates for Git-native policy enforcement (e.g., config options) to handle cases where repositories are modified via APIs or non-push commands, rather than leaving this entirely to forges.

Junio C Hamano has expressed skepticism about the practicality of multi-format advertisements due to historical capability-parsing bugs, while Peff remains cautious about edge cases. The thread is now centered on whether the project will adopt brian's multi-format approach and how it will balance the limbo feature's complexity against the urgency of the SHA-256 transition. No implementation exists yet, and the discussion remains conceptual.

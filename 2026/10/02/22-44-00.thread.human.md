This thread is an RFC discussion about introducing a "limbo" state for new Git repositories to avoid push failures when clients and servers disagree on the object format (SHA-1 vs. SHA-256) during Git 3.0’s transition. The proposal, originally by Jeff King (Peff), has evolved in response to feedback from Brian M. Carlson and Junio Hamano.

Peff now suggests advertising both `object-format=sha256` and `alt-object-format=sha1` in the wire protocol, replacing the earlier `magic-limbo` capability. This approach explicitly signals support for both hash algorithms, addressing Brian’s concerns about future compatibility while avoiding the need for a separate limbo signal. Peff clarifies that the feature is not intended to delay Git 3.0’s SHA-256 transition and could be implemented within the remaining release cycle, though he does not plan to do so himself. He also agrees that Git should provide a config flag to mark the limbo state—set by `git init` and respected by `receive-pack`—but insists it should not be enabled by default, leaving policy enforcement to forges like GitHub.

The discussion now focuses on two key technical questions: whether modern clients (Git 2.41+) can reliably handle the dual-format advertisement, given a 2023 fix for multi-valued capability parsing, and how to manage non-push repository modifications (e.g., via APIs) without a predefined hash algorithm. Junio remains skeptical about the practicality of multi-format advertisements due to historical capability-parsing bugs, while Brian continues to advocate for Git-native policy enforcement to ensure consistency across all repository access methods. No implementation exists yet, but the refined proposal narrows the scope to protocol-level changes and config-based state management.

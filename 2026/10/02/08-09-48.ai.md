This is the core API patch in Patrick Steinhardt’s v2 series introducing subcommand grouping to Git’s parse-options subsystem. It extends `OPT_SUBCOMMAND_F()` to accept an optional help string, enabling subcommands to be grouped under `OPT_GROUP()` headings in the usage output. The change is small but pivotal: it removes the need for a separate `OPT_SUBCOMMAND_H()` variant (which was present in v1) and makes the API more consistent by allowing help text to be specified directly in the subcommand definition.

The patch touches seven files. The key changes are in `parse-options.h`, where `OPT_SUBCOMMAND_F()` gains a `help` parameter (defaulting to `NULL` for backward compatibility), and in `parse-options.c`, where `usage_print_option()` now prints subcommands with help text under their group heading. The documentation (`api-parse-options.adoc`) is updated to clarify that groups apply to both options and subcommands with help strings. Two existing callers (`builtin/remote.c` and `builtin/stash.c`) are adjusted to pass `NULL` for the new parameter, preserving their current behavior. The test suite (`t/t0040-parse-options.sh`) adds coverage for the new grouping behavior, verifying that subcommands with help text appear under their group heading in the usage output.

This patch directly addresses Junio C Hamano’s feedback from v1, which requested API consistency and reduced nesting. By extending `OPT_SUBCOMMAND_F()` to handle help text directly, the patch eliminates the redundant `OPT_SUBCOMMAND_H()` macro and simplifies the interface. The preparatory refactoring in patch 2/4 (already incorporated in v2) extracted option-formatting logic into helper functions, reducing nesting in `usage_with_options_internal()` and making this patch cleaner. The changes are backward-compatible: subcommands without help text (the default) continue to be omitted from the usage output, matching the existing behavior.

The patch is well-motivated and technically sound. It introduces no new symbols outside `parse-options.c` and maintains the existing API surface for callers that do not use the new feature. The test coverage is thorough, including a new test case for the grouping behavior. The only potential point of contention is whether the API change is sufficiently intuitive—callers must now pass `NULL` explicitly for subcommands without help text—but the backward-compatible default mitigates this. The patch is part of a larger effort to improve the usability of high-level commands like `git refs` and `git objects`, and it lays the groundwork for the final patch in the series, which applies grouping to `git refs`.

No substantive reviews have been posted yet for v2, but the changes are responsive to the feedback from v1 and appear uncontroversial. The patch is under active review and is likely to proceed smoothly, given its clean design and clear alignment with the series’ goals.

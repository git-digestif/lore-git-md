Here’s the human-readable summary for a developer catching up on this thread:

This thread is about a memory usage regression in Git for Windows 2.56.0.windows.1, where `git status`-like commands—spawned by coding agents—consume roughly 1 GB of RAM per process, totaling several GB across dozens of concurrent processes. The issue is absent in Git 2.55.0, suggesting a regression in 2.56.0. The reporter, Pierre Bruno, notes the repository is large with many untracked files and fsmonitor is enabled, but key details like the exact commands run and a `git bugreport` output are still missing.

Jeff King (Peff) recently weighed in with a plausible explanation: the 1 GB figure likely reflects *virtual* memory from Git’s memory-mapped packfiles on Windows (`CreateFileMapping`/`MapViewOfFile`), not actual resident memory. Multiple processes can share these mapped pages, so total system memory usage might still be close to 1 GB regardless of process count. He suggests checking whether the 1 GB is virtual (expected) or resident (potentially problematic). If it’s virtual, the issue might be a misinterpretation of memory metrics rather than a true regression, though the reporter’s observation of steady disk I/O complicates this theory. The next steps are to clarify the memory metrics and confirm whether the regression claim holds under closer scrutiny. Brian Carlson and others have also requested the missing diagnostic details to narrow down the root cause.

This is a **memory usage / platform compatibility follow-up** in the ongoing Windows fsmonitor regression thread. Jeff King (Peff) responds to Pierre Bruno’s report of ~1 GB RAM per Git process by clarifying how Git’s memory-mapped packfiles could explain the observed behavior.

Peff suggests the high memory usage may be an artifact of how Windows reports memory for mapped files (via `CreateFileMapping`/`MapViewOfFile`), not an actual leak or regression. He notes that if the repository contains a 1 GB packfile, Git will map it into virtual memory, but the OS may only fault in the pages actually accessed, keeping resident memory lower. Multiple Git processes would share these mapped pages, so total memory use would not scale linearly with process count. He also observes that high resident memory could paradoxically indicate *low* memory pressure, since the OS retains unused pages when it has spare capacity.

The response is substantive but cautious: Peff frames his explanation as Linux-centric and defers to Windows experts on how aggressively Windows faults or releases mapped-file pages. No root cause is confirmed, and the regression claim (2.55.0 vs. 2.56.0) remains unaddressed. The key open question is whether the reported 1 GB per process reflects *virtual* memory (expected) or *resident* memory (potentially problematic). Pierre’s screenshots (not yet analyzed in the thread) and the missing `git bugreport` output will be critical to distinguish between these cases. If the issue is virtual memory inflation, it may not be actionable; if resident memory is truly ballooning, it could point to a Windows-specific bug in fsmonitor or index handling.

This is an RFC proposal for a new signing mechanism that embeds a SHA-256 digest of the entire tree contents (including submodules) in signed commits and tags, without requiring the repository to use SHA-256 as its object format. The series adds a `--hash=sha256` option to `git commit -S` and `git tag -s`, and a `gpg.treeHash=sha256` config key to make it the default. The digest is computed over a sorted list of `<sha256(content)> SP <path> NUL` records for every file in the tree, with submodules contributing their own tree digests.

The motivation is to provide a migration path away from SHA-1 that does not force a disruptive change to the default object format in Git 3.0. The author suggests this approach could offer similar security benefits while avoiding ecosystem-wide churn. The implementation is self-contained: it adds a new `tree-sha256.c` file, a test helper, and two new test scripts. Backwards compatibility is preserved: older Git versions ignore the extra header, and verification continues to work as before.

The series is explicitly experimental ("RFC") and the author is soliciting feedback on four open questions: whether the approach is viable as an alternative to switching the default hash, how verification should work, whether submodules should be excludable, and naming choices. Performance is noted as acceptable but not optimized; the author mentions that parallel hashing could significantly improve speed but is not included in this series.

This is a well-structured proposal with clear technical design, thorough test coverage, and a specific goal tied to the Git 3.0 timeline. The patch series is complete enough to evaluate the approach, but the author is not yet advocating for merging. The discussion is likely to focus on whether this mechanism addresses the perceived security needs, how it interacts with existing SHA-256 repositories, and whether the complexity is justified.

This is the second patch in the v5 series introducing a "matching-inspired" fetch mode for shallow repositories. It implements the core logic that makes `git fetch` infer which branches to fetch when a remote is configured with `remote.<name>.refmap` but no `remote.<name>.fetch` refspec.

The patch updates `builtin/fetch.c` and `remote.c` to dynamically enumerate branches tracked by local branches at the remote being fetched. When no explicit refspec is provided and the remote has a refmap but no fetch refspec, `get_ref_map()` now calls a new helper `branches_tracking_remote()` (added to `remote.c`) to iterate over local branches whose `@{upstream}` points to the remote. The inferred branch list is passed to the transport’s `ls-refs` command, ensuring only those branches are fetched. The forced inclusion of the remote’s default branch (present in v3) is removed, addressing Junio’s prior objection.

Documentation in `config/remote.adoc` and `fetch-options.adoc` is updated to describe the new behavior: when a refmap is active but there is nothing to fetch from the command line or `remote.<name>.fetch`, Git infers what to fetch from local branches tracking the remote. The test file `t/t5586-fetch-refmap.sh` (renumbered from `t/t5585` in v5) verifies the dynamic branch selection logic, including edge cases like duplicate branches, branches tracking other remotes, and compatibility with `git remote show`.

The implementation is clean and well-tested, with no on-disk format changes beyond the new configuration entry introduced in Patch 1/4. The patch preserves backward compatibility for non-shallow repositories and avoids inventing new refspec syntax, aligning with the project’s preference for incremental, non-disruptive changes. The only minor edge case noted in the thread — a bare `git fetch` against a refmap-only remote fetching no branches — is acknowledged but not considered a blocker. This patch is ready for integration and is the technical centerpiece of the series.

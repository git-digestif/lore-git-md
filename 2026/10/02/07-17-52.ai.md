This is the second patch in Harald Nordgren’s two-patch series extending `remote.pushDefault` to accept a space-separated list of remote names. It implements the core feature: when `remote.pushDefault` contains multiple remotes, Git now iterates through them in order and pushes to the first one that exists in the repository. If none exist, it falls back to the branch’s configured remote as if `remote.pushDefault` were unset. The patch updates the documentation (`Documentation/config/remote.adoc`) to describe the new behavior and adds three new tests to `t/t5516-fetch-push.sh` covering the happy path (first existing remote is used), edge cases (all remotes missing), and override behavior (repository-local `remote.pushDefault` takes precedence over a global list).

The implementation is straightforward: a new helper function `pushdefault_candidate` splits the config value on spaces and checks each remote name in sequence using the existing `find_remote` and `valid_remote` functions. The main logic in `remotes_pushremote_for_branch` now calls this helper and returns the first valid remote name, preserving the existing `explicit` flag behavior. No new dependencies or subsystems are introduced; the change is confined to `remote.c` and the test suite.

The motivation remains clear: users with multiple remotes (e.g., a fork and an upstream) can now set a global fallback chain like `fork origin` and avoid per-repository configuration. The patch handles backward compatibility gracefully—single remote names continue to work as before, and repository-local settings still override global ones. The test coverage is thorough, exercising both the new multi-remote logic and the fallback behavior when all remotes are missing.

This is a user-facing feature with a well-defined use case, but potential interactions with other push-related features (e.g., `push.default`, `push.autoSetupRemote`) are not discussed in the commit message. The implementation appears robust, but reviewers may probe whitespace handling in the config value (e.g., leading/trailing spaces, multiple consecutive spaces) and whether the fallback logic aligns with user expectations. The patch is ready for review and should integrate cleanly with the refactoring introduced in the first patch.

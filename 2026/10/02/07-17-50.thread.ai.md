Subject: [PATCH 0/2] remote: support multiple remotes in remote.pushDefault

Originating author: Harald Nordgren (via GitGitGadget)
Thread type: patch series (feature addition)

Core problem or goal
Extend `remote.pushDefault` to accept a space-separated list of remote names, allowing a single global configuration (e.g., `fork origin`) to push to the first available remote in the list across multiple repositories. This eliminates the need for per-repository configuration when working with multiple remotes (e.g., a fork and an upstream).

Current status
Under review (v1 posted). Two patches:
1. Refactoring: factor out remote lookup by name into a helper function (`remote_get_by_name` in `remote.c`).
2. Feature: iterate through the list of remotes in `remote.pushDefault` and push to the first existing remote; update documentation (`Documentation/config/remote.adoc`) and add tests (`t/t5516-fetch-push.sh`). The implementation splits the config value on spaces, checks each remote name in sequence using `find_remote` and `valid_remote`, and preserves the existing `explicit` flag behavior. Backward compatibility is maintained: single remote names continue to work, and repository-local settings override global lists.

Key technical details
- Files touched: `remote.c`, `Documentation/config/remote.adoc`, `t/t5516-fetch-push.sh`.
- New symbols: `remote_get_by_name` (helper function for remote lookup, replacing inline hashmap lookup), `pushdefault_candidate` (splits config value and returns first valid remote).
- Behavior: `remote.pushDefault = fork origin` pushes to `fork` if it exists, otherwise to `origin`; if none exist, falls back to the branch’s configured remote.
- No on-disk format changes; no new dependencies.
- Test coverage: happy path (first remote exists), edge cases (all remotes missing, repository-local override), whitespace handling not explicitly tested.

This is the second patch in Christian Couder’s five-part v5 series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration to mark repositories as trusted for lazy fetching. The patch extracts reusable path-allowlist logic from Git’s existing `safe.directory` mechanism into new helpers, `path_allowlist_apply()` and `path_allowlist_config_apply()`, so it can be reused by the new `uploadpack.lazyFetchTrusted` feature. The refactoring is observably equivalent: it removes 49 lines of duplication while adding 143 lines of new code, with no behavioral changes.

The patch now includes a `NEEDSWORK` comment flagging a latent design issue inherited from `safe.directory`: the silent ignoring of non-existent paths. This behavior, originally justified to avoid warnings when sharing `.gitconfig` files across machines, also means misspelled or misconfigured paths go unnoticed, potentially leading to unintended trust decisions. Christian’s comment proposes addressing this in a follow-up patch by warning about missing paths unless they are explicitly marked as optional (e.g., with an `:(optional)` prefix, following Git’s existing syntax for pathname-typed configuration variables). This issue does not block the current series but is now documented for future work.

Junio’s earlier review of v4 identified this same concern and suggested a similar enhancement to the configuration syntax, along with a helpful warning message to guide users. Christian has fully addressed Junio’s feedback in v5, incorporating the `NEEDSWORK` comment and leaving the door open for a follow-up patch. The rest of the series remains unchanged, with all other feedback from Junio’s v4 review already resolved in the full v5 submission.

This patch is a clean refactoring with no functional impact, making it a strong candidate for early integration if the series stalls. The `NEEDSWORK` comment is the only loose end, and it is now clearly scoped as a follow-up rather than a blocker. The patch’s role in the series is foundational: it enables the server-side trust mechanism by providing the reusable allowlist logic that later patches build on.

Subject: [PATCH 0/2] fetch: optimize commit-graph write strategy for large repos

Core problem or goal
When `fetch.writeCommitGraph` is enabled, Git currently rebuilds the commit-graph from all reachable refs after every fetch, which is inefficient for repositories with many refs. The goal is to introduce an incremental write strategy that avoids scanning all refs after every fetch by writing only the newly fetched commits when possible, falling back to full scans only when necessary (e.g., no existing graph or multi-remote fetches).

Key technical details
- Subsystem: commit-graph
- Files touched: `builtin/fetch.c`, `commit-graph.c`, `commit-graph.h`, `t/helper/test-read-graph.c`, `t/t5510-fetch.sh`
- New enum: `enum commit_graph_write_strategy { COMMIT_GRAPH_WRITE_REACHABLE, COMMIT_GRAPH_WRITE_TIPS, COMMIT_GRAPH_WRITE_SKIP }`
- New data structure: `oidset` in `builtin/fetch.c` to track updated refs during `do_fetch()`
- New APIs: `lookup_commit_in_graph()` and `commit_graph_generation()` (used by test helper); `prepare_commit_graph()` made non-static to allow fetch command to check for existing graph
- New test helper: `test-tool read-graph commit-info` (22 lines in `t/helper/test-read-graph.c`)
- Behavior: incremental writes from updated refs only when possible; fallback to `COMMIT_GRAPH_WRITE_REACHABLE` when no existing graph exists or when fetching from multiple remotes. No-op fetches (`COMMIT_GRAPH_WRITE_SKIP`) avoid unnecessary writes. The seeds passed to `write_commit_graph()` are **additive**, extending the existing graph (relying on split mode, `COMMIT_GRAPH_WRITE_SPLIT`). Non-split mode is not used by fetch, but if it were, the incremental path would require `COMMIT_GRAPH_WRITE_APPEND` or a fallback to the full reachable scan to avoid coverage loss.
- Performance: In a synthetic setup (git.git with 200K extra packed refs), incremental write reduces `fetch/write-commit-graph` time from ~360ms to ~9ms for a single ref update; no-op fetches are skipped entirely.
- Test coverage: four new tests in `t/t5510-fetch.sh` covering incremental writes, exclusion of unrelated commits, no-op fetches, and fallback cases. Planned reroll will add tests verifying no coverage loss after incremental writes.

Open questions and loose ends
- **Benchmarking**: Now addressed by Kristofer’s synthetic measurements, which will be included in the reroll’s cover letter.
- **Ref status filtering**: Kristofer explained the rationale (only `REF_STATUS_REJECT_SHALLOW` is set by `fetch-pack` during fetch) and suggested an alternative (`status != REF_STATUS_NONE`), but deferred to future-proofing considerations. No further changes planned.
- **`old_oid` vs. `new_oid`**: Resolved: `rm->old_oid` holds the remote’s advertised value (the new tip being fetched), while `rm->peer_ref->old_oid` holds the local ref’s current value. `rm->new_oid` is not set during fetch (populated later by `store_updated_refs()`).

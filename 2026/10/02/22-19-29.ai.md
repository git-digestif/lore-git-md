This is a **substantive review** in the ongoing Windows memory regression thread. Jeff King (Peff) engages directly with the reported issue, proposing a plausible technical explanation for the observed memory usage: Git’s memory-mapped packfiles on Windows (`CreateFileMapping`/`MapViewOfFile`). He clarifies that the 1 GB per process may reflect *virtual* memory rather than *resident* memory, and that multiple processes can share the same mapped pages, so total system memory usage could still be close to 1 GB regardless of how many Git processes are running. Peff also notes that high resident memory might paradoxically indicate low memory pressure, as the OS keeps mapped pages resident when it has spare capacity.

The key new detail is the distinction between virtual and resident memory. Peff suggests the reporter check whether the 1 GB figure is virtual (expected) or resident (potentially problematic). He acknowledges uncertainty about Windows-specific behavior—how aggressively Windows faults in or releases mapped-file pages—but the core mechanism (memory-mapped packfiles) is platform-agnostic and a well-known source of large virtual memory footprints in Git. This explanation, if confirmed, would demote the issue from a regression to a misinterpretation of memory metrics, though the reporter’s observation of *steady disk I/O* (not typical for purely virtual mappings) remains unexplained.

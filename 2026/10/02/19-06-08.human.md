This is a strong, principled objection to the RFC patch series proposing a SHA-256 tree-digest signing mechanism as an alternative to switching Git’s default object format to SHA-256 in Git 3.0.

brian m. carlson argues that the proposed mechanism does not address the core problem: Git’s reliance on SHA-1 for collision resistance. He points out that SHA-1 is already considered weak by major governments and industry standards (TLS, OpenPGP), and that Git’s current plan to switch the default object format to SHA-256 in Git 3.0 has been long discussed, widely communicated, and is already supported by major forges. The objection is not just technical but strategic: the project has already rejected half-measures like this one, and the timeline for Git 3.0 (targeting March 2027) leaves no room for substantial design changes.

The email also clarifies that the real need is not a new signing mechanism but interoperability tooling — specifically, the ability to automatically rewrite repositories between hash algorithms during clone or fetch. brian mentions that this work exists but has not yet been upstreamed due to corporate tooling limitations (Outlook corrupting patches), though there is an intention for another company to polish and submit it.

This is not a review of the patch’s implementation but a fundamental challenge to its premise. The tone is firm and uncompromising, reflecting a long-standing position on the SHA-1 deprecation effort. The message is clear: the proposed tree-digest signing mechanism is seen as a distraction from the necessary transition to SHA-256 as the default object format, and the project is not open to revisiting that decision at this stage.

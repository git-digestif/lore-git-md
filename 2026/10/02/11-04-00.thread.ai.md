Subject: High memory usage regression in Git 2.56.0.windows.1 with fsmonitor
Series version: N/A (bug report)
Originating author: Pierre Bruno
Thread type: bug report

Core problem or goal
A Windows user reports a memory usage regression in Git 2.56.0.windows.1, where `git status`-like commands (spawned by coding agents OpenCode and Oh My Pi) consume ~1 GB of RAM per process, totaling several GB across dozens of concurrent processes. The issue is absent in Git 2.55.0, indicating a regression in 2.56.0. The repository is large with many untracked files, and fsmonitor is enabled. The user seeks confirmation whether this memory footprint is expected and if configuration tweaks could mitigate it.

Current status
Under investigation. The report establishes a regression between 2.55.0 and 2.56.0.windows.1, with high memory usage tied to fsmonitor and concurrent process spawning. Jeff King (Peff) proposes that the observed 1 GB per process may reflect *virtual* memory (memory-mapped packfiles) rather than *resident* memory, and that multiple processes can share the same mapped pages, so total system memory usage could still be close to 1 GB regardless of process count. The distinction between virtual and resident memory is now critical: if the 1 GB is virtual, the issue may be a misinterpretation of metrics; if resident, the regression claim remains urgent. The missing `git bugreport` attachment and command-line details of the spawned processes are still gaps, but the steady disk I/O reported by the user (unexpected for purely virtual mappings) complicates Peff’s hypothesis.

- **Disk I/O anomaly**: Steady disk I/O is atypical for purely virtual memory mappings; does this indicate active page faults, or is it unrelated (e.g., fsmonitor or index scanning)?
- **Command-line arguments**: The exact commands run by the coding agents (e.g., `git status`, `git maintenance`) remain unknown but are critical for reproducing the behavior.
- **Fsmonitor dependency**: Does the issue reproduce with fsmonitor disabled? Is it specific to the Windows backend, or does it affect other platforms with memory-mapped files?
- **Configuration tweaks**: Could settings like fsmonitor idle timeout, index cache size, or maintenance scheduling mitigate resident memory usage?
- **Repository maintenance**: Are the processes inadvertently triggering concurrent `git maintenance` tasks (e.g., packing), which could explain the memory spike?
- **Root cause**: If the 1 GB is resident, what specific commit in 2.56.0 introduced the regression? Is it tied to fsmonitor, index handling, or memory-mapped file behavior?

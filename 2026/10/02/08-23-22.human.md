This is the final patch in Christian Couder’s five-part series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators explicitly mark repositories as trusted for lazy fetching. The patch activates the mechanism by modifying `builtin/upload-pack.c` to conditionally set `GIT_NO_LAZY_FETCH=1` only if the environment variable is unset and the served repository is not in the allowlist.

The core logic is straightforward: if `GIT_NO_LAZY_FETCH` is already set, the code honors it; otherwise, it checks whether the repository is trusted via `upload_pack_lazy_fetch_trusted()` and disables lazy fetching only if the repository is untrusted. This preserves operator control while shifting trust decisions to the server side, addressing the security objection that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration.

The patch also expands documentation in `Documentation/config/uploadpack.adoc`, `git-upload-pack.adoc`, and `git.adoc` to explain how the new configuration works, how repositories are identified (including edge cases like `--separate-git-dir` and linked worktrees), and how trust differs from the `GIT_NO_LAZY_FETCH=0` environment variable (notably, trust does not propagate to child processes). The documentation is thorough and clear, explicitly stating that trust does not extend to promisor remotes and that the server operator is responsible for ensuring those remotes are also trustworthy.

Tests in `t/t5710-promisor-remote-capability.sh` verify the new behavior, covering cases where the repository is trusted, untrusted, or explicitly overridden by `GIT_NO_LAZY_FETCH`. They also test edge cases: a trusted repository configured as its own promisor remote (which triggers the recursion safeguard), non-bare repositories identified by their `.git` directory, and repositories with `.git` files pointing to separate git directories. The tests are comprehensive and well-structured, providing confidence that the implementation handles real-world scenarios correctly.

The patch is clean, well-motivated, and addresses all feedback from earlier iterations. The series as a whole is now ready for integration, with no substantive concerns remaining. If this patch lands, the entire mechanism will be functional, offering a secure and flexible way for server operators to control lazy fetching.

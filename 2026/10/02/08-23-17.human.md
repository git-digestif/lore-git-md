This is the v5 cover letter for Christian Couder’s five-patch series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators explicitly mark repositories as trusted for lazy fetching. The series is now in its fifth iteration, with no functional code changes since v4—only improvements to documentation, code comments, tests, and commit messages.

The core goal remains unchanged: replacing the earlier client-side `GIT_NO_LAZY_FETCH=fromAccepted` proposal with a server-controlled trust model that addresses security concerns about untrusted repositories triggering arbitrary code execution via lazy-fetch hooks or configuration. The new `uploadpack.lazyFetchTrusted` variable works like Git’s existing `safe.directory` mechanism, allowing server operators to allowlist repositories by their git directory (e.g., `/srv/repo/.git`). The implementation is careful to avoid propagating trust to child processes, unlike the environment-based `GIT_NO_LAZY_FETCH=0`, which would allow nested `upload-pack` instances to lazily fetch as well.

Key refinements in v5 include:
- A `NEEDSWORK` comment in patch 2/5 flagging the latent design issue in `safe.directory` (silent ignoring of non-existent paths) and suggesting an `:(optional)` prefix syntax for future work.
- More precise documentation in patch 5/5 clarifying how repositories are identified (following `.git` files and symlinks, handling `--separate-git-dir` setups) and emphasizing that trust does not propagate to promisor remotes.
- New tests covering edge cases: repositories with `.git` files pointing to separate git directories, and explicit verification that trust is not inherited by child processes.
- Minor grammar and punctuation fixes in documentation (e.g., "each of which" → "each value of which", commas after "i.e." and "e.g.").

The series is cleanly structured: patches 1/5 and 2/5 are refactorings with no behavioral impact, making them candidates for early integration if the series stalls. The core functionality is introduced in patches 3/5 and 5/5, with patch 4/5 adding a recursion safeguard to prevent infinite loops when a repository is configured as its own promisor remote. All CI tests pass, and the series is rebased on Git 2.56 (a018953688).

Junio’s feedback from v4 is fully addressed, and his final review of v4 was entirely positive, suggesting only surface-level documentation tweaks. The unresolved high-weight concerns—Junio’s scalability critique about memory overhead in `lazy_fetch_objects()` and conceptual doubt about using a configuration variable, along with brian m. carlson’s security objection—remain but are mitigated by the server-side design. No new substantive reviews have been posted for v5. The series looks well-crafted, thoroughly tested, and ready for integration if no further objections arise.

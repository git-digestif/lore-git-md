This is the first review comment on Scott Chacon’s RFC series proposing a SHA-256-based signing mechanism for Git commits and tags. Junio C Hamano raises two substantive design questions about the core hashing logic introduced in patch 1/4.

First, Junio asks whether three different trees — one with an executable "hello" blob, one with a non-executable "hello" blob, and one with a symlink pointing to "hello" — should produce the same SHA-256 digest. The current implementation ignores file modes and symlink targets, treating only the blob content and path as inputs. This is a fundamental design choice: whether the digest should reflect only content (making it stable across mode changes) or also include metadata (making it sensitive to permission and type changes). The question is left open, but Junio’s phrasing suggests he expects the digest to distinguish these cases.

Second, Junio questions the decision to sort tree entries before hashing. The current code sorts the collected records by path, which means two trees with identical content but different on-disk ordering would produce the same digest. Junio argues that if a tree is corrupt (e.g., unsorted), the digest should reflect that corruption rather than silently normalizing it. This touches on whether the digest is meant to be a content hash (stable across equivalent trees) or a structural hash (sensitive to internal tree representation).

Junio also notes a performance concern: the implementation reads entire blob contents into memory before hashing, which could be inefficient for large files. He suggests using Git’s streaming interface (like `archive-tar.c` does) to hash blobs in chunks, avoiding the need to load large objects into memory.

The review is substantive, focusing on the core design and implementation trade-offs rather than surface-level issues. No objections or approvals are given; the questions are posed as open design points for discussion. The thread remains in the RFC phase, with no decisions or merge status recorded.

This is the first patch in Scott Chacon’s RFC series proposing a new SHA-256-based signing mechanism for Git commits and tags. It introduces the core hashing logic: a function that computes a SHA-256 digest over the entire tree contents (including submodules) by recursively walking the tree and producing a sorted list of `<sha256(content)> SP <path> NUL` records for every file and `<digest> SP <path>/ NUL` for every submodule. The digest is exposed through a new `tree_sha256_hex()` API and a test helper (`test-tool tree-sha256`) that lets the test suite verify the computation by hand.

The implementation is careful about submodule handling: it follows gitlinks into the submodule’s own repository, checks out the pinned commit, and recursively hashes the submodule’s tree. If a submodule is unavailable or missing the pinned commit, the function reports every problem and fails, which the later patches use to prevent signing incomplete trees. Cycles (a submodule that pins a commit already being hashed) are detected and recorded as `cycle:<commit>` to avoid infinite recursion.

The patch adds a new `tree-sha256.c` file, a corresponding header, a test helper, and a comprehensive test script (`t/t1018-tree-sha256.sh`) that validates the digest computation against a hand-rolled reference implementation using `git ls-tree`, `git cat-file`, and `sha256sum`. The test covers files, directories, symlinks, submodules, and error cases, and confirms that the digest is the same for commits, tags, and trees.

This is a well-crafted foundation for the series: the code is clean, the test coverage is thorough, and the design choices (sorted records, NUL termination, recursive submodule hashing) are clearly motivated. The patch does not yet touch signing itself; that comes in the later patches. The only open question in this patch is performance (the author notes that parallel hashing could be added later), but the current implementation is already fast enough for the RFC stage.

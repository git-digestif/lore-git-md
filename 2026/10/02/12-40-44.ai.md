This is the **reply to a substantive review** of the second patch in Kristofer Karlsson’s two-patch series optimizing `fetch.writeCommitGraph` for large repositories. The series introduces an incremental commit-graph write strategy that avoids scanning all refs after every fetch by writing only the newly fetched commits when possible.

Kristofer **clarifies the core design assumptions** Patrick Steinhardt questioned in his review. The seeds passed to `write_commit_graph()` are **additive**, extending the existing graph rather than replacing it. This relies on fetch always using split mode (`COMMIT_GRAPH_WRITE_SPLIT`), which ensures new commits are added as a new layer on top of the existing chain. Kristofer agrees to extend the test suite to verify that commits present before the fetch remain in the graph afterward, addressing Patrick’s concern about potential coverage loss.

On **non-split mode behavior**, Kristofer confirms the fetch path never uses it, but notes that if it ever did, the incremental path would need `COMMIT_GRAPH_WRITE_APPEND` or a fallback to the full reachable scan to avoid losing coverage. This clarification resolves Patrick’s question about edge-case behavior.

Kristofer **provides benchmark numbers** to quantify the performance improvement, addressing Patrick’s request for empirical evidence. In a synthetic setup (git.git with 200K extra packed refs), the incremental write reduces the `fetch/write-commit-graph` time from ~360ms to ~9ms for a single ref update, and no-op fetches are now skipped entirely. He plans to include these numbers in the cover letter of the reroll.

On **ref status filtering**, Kristofer explains why the code only filters `REF_STATUS_REJECT_SHALLOW`: during fetch, most `REF_STATUS_*` values are unused, and the only status set by `fetch-pack` is `REF_STATUS_REJECT_SHALLOW`. He suggests an alternative (`status != REF_STATUS_NONE`) but defers to future-proofing considerations.

The **`old_oid` vs. `new_oid` confusion** is resolved with a detailed explanation of the `ref_map` structure: `rm->old_oid` holds the remote’s advertised value (the new tip being fetched), while `rm->peer_ref->old_oid` holds the local ref’s current value. The code uses `rm->old_oid` because `rm->new_oid` is not set during fetch (it’s populated later by `store_updated_refs()`).

Finally, Kristofer justifies the **explicit `GRAPH_WRITE_SKIP` mode** as a safeguard: the `oidset` can be empty either because the fetch was a no-op (skip is correct) or because the multi-remote path was taken (fallback to reachable scan is required). Deriving the mode from `oidset_size()` alone would incorrectly skip writes for `fetch --all`.

The reply is **technically thorough** and directly addresses all of Patrick’s questions. Kristofer’s planned reroll will include updated commit messages, extended test coverage, and benchmark numbers, making the series more robust. The discussion confirms the patch is well-scoped but needed clarification on core assumptions (additive seeds, split-mode reliance) and edge cases. The series remains under review, with no unresolved technical objections.

Thread identity
Subject: [PATCH 0/13] Move alternates into the files ODB backend
Series version: v2 (documentation-only reroll; no code changes)
Originating author: Patrick Steinhardt
Thread type: patch series (refactoring)

Core problem or goal
Refactor the Git object database (ODB) subsystem to move alternates handling into the "files" backend, eliminating a conceptual mismatch where alternates were previously managed at the ODB source level. This mismatch caused performance regressions, complicated data structures (bitmaps, commit graphs), and blocked backend-agnostic extensions to `GIT_OBJECT_DIRECTORY` and `GIT_ALTERNATE_OBJECT_DIRECTORIES`. The series consolidates alternates into the files backend, making them a backend-specific implementation detail and enabling future ODB work such as pluggable backends.

Current status
Review complete (v2, all feedback addressed). The series is built on commit `c46c1e3772` (start of the Git 2.98 cycle) and has minor merge conflicts with the `seen` branch, as documented in the cover letter. The v2 reroll is **documentation-only**: it clarifies the motivation in the first patch’s commit message but makes no code changes. The final patch (13/13) removes the now-unused `read_alternates` callback from the ODB source interface, completing the architectural shift. The series is now **ready for integration**, pending resolution of merge conflicts with `seen`.

Patch 12/13 specifically touches 35 files, with the bulk of changes in `odb.c` (439 lines removed) and `odb/source-files.c` (482 lines added). - **Behavior changes**:
  - **Series-wide**:
    - Alternates are now managed exclusively by the files backend; the `read_alternates` callback is dropped.
    - Patch 1/13 shifts packfile path resolution responsibility from `fill_oids_from_packs()` to its caller (`builtin/commit-graph.c`), requiring fully resolved paths for `--stdin-packs`. This change is preparatory, removing assumptions in `commit-graph.c` about packfile locations relative to an ODB source to align with patch 2/13’s decoupling of the commit-graph subsystem from `struct odb_source`.
    - Patch 2/13 decouples the commit-graph subsystem from `struct odb_source`, replacing it with explicit repository and object-directory path arguments. This ensures commit graphs loaded from the same directory compare equal regardless of path spelling (relative, absolute, or symlink). The test helper `git_test_write_commit_graph_or_die()` now takes only a `struct repository *` but internally hard-codes the object directory path from `repo->objects->sources->path`, which Karthik Nayak flags as a potential inconsistency: the function should forward an explicit path argument to align with the series’ shift toward explicit repository and path arguments, avoiding assumptions about the primary ODB source’s path.
    - Patch 3/13 introduces `struct odb_files_dir` as a foundational step for later patches that will enable multiple directories per backend. The change is mechanical: every `struct odb_source_files` now contains a single `struct odb_files_dir` (accessed via `files->dirs`) instead of separate `loose` and `packed` fields. The new structure also stores the absolute path to the object directory and a `local` flag indicating whether it is the primary repository directory.
    - Patch 4/13 adapts `odb_for_each_alternate()` to iterate over `struct odb_files_dir` instead of `struct odb_source`, updating callers in `builtin/count-objects.c`, `builtin/submodule--helper.c`, and `diagnose.c` to use the `abspath` field. The `refs_from_alternate_cb()` helper is refactored to pass the repository context explicitly. This introduces a subtle behavioral difference: alternates are now identified by their canonicalized absolute path (`abspath`) rather than the raw path stored in the source, which could affect edge cases involving symlinks or relative paths.
    - Patch 5/13 removes the generic `odb_find_source()` and `odb_find_source_or_die()` functions, replacing them with `odb_source_files_find_dir()`, a files-backend-specific function that returns `struct odb_files_dir`. Callers in `builtin/commit-graph.c`, `builtin/multi-pack-index.c`, and `t/helper/test-read-midx.c` are updated to use the new function, replacing `source->path` with `dir->abspath` and using `odb_source_files_downcast()` where needed. The patch is purely preparatory, with no visible behavior changes.
    - Patch 6/13 extends `struct odb_files_dir` with a `next` pointer to form a linked list of object directories, enabling the files backend to manage multiple directories. All ODB operations in `odb/source-files.c` are updated to loop through the list: read operations check each directory in sequence until the object is found, while write operations target only the first directory. The patch is purely preparatory, with no visible behavior changes yet.
    - Patch 7/13 absorbs the temporary-primary-source logic into `tmp-objdir.c`, removing `odb_set_temporary_primary_source()` and `odb_restore_primary_source()` from the public ODB API. The functionality is reimplemented as static helpers in `tmp-objdir.c`, which now directly manipulates the ODB’s source list and `disable_ref_updates` flag.
    - Patch 8/13 adapts the quarantine logic in `tmp-objdir.c` to manage the temporary object directory as a `struct odb_files_dir` instead of a standalone `struct odb_source`. The `tmp_objdir` struct replaces its `prev_source` field with `temp_dir` (the new quarantine directory) and `orig_dir` (the original primary directory). `tmp_objdir_replace_primary_odb()` now returns a `struct odb_files_dir` and inserts the quarantine directory at the head of the files backend’s linked list. The `will_destroy` flag is propagated to both the loose and packed sources within the quarantine directory. Karthik Nayak’s review of this patch raised a conceptual question about the architectural decision to remove the ability to have multiple sources per ODB, suggesting that different sources could hypothetically use different strategies (e.g., loose vs. packed). Patrick Steinhardt’s quoted response explained that the files backend is being prepared to handle multiple object directories via a linked list of `struct odb_files_dir`, which will subsume alternates and make multiple sources per ODB impossible. Karthik retracted this question in the latest email after discovering Patrick’s explanation in patch 12/13.
    - Patch 9/13 merges `tmp_objdir_replace_primary_odb` into `tmp_objdir_create`, which now takes a `will_destroy` flag and inserts the quarantine directory at the head of the linked list immediately on creation. Callers in `log-tree.c` and `object-file.c` are updated to pass the flag at creation time.
    - Patch 10/13 moves the `will_destroy` flag from the generic `struct odb_source` to `struct odb_source_loose`, where it is actually used. The flag was previously defined in the generic ODB source structure but only checked by the loose-object backend to skip fsync when the source is ephemeral.
    - Patch 11/13 extracts the alternates-reading logic from `odb_source_files_read_alternates()` into a new helper function, `read_alternates()`, which operates on an object directory path instead of an `odb_source` struct. The change is preparatory for patch 12/13, which will add a new callsite lacking an `odb_source` for the alternate directory.
    - Patch 12/13 relocates alternates handling into the files backend, making it a backend-specific implementation detail. The `read_alternates` callback is dropped, and alternates are read only by the files backend. The alternates infrastructure (path parsing, deduplication, recursive addition) is moved from `odb.c` to `odb/source-files.c`. The `odb_source` struct loses its `next` pointer and `by_path_entry` field, as sources no longer form a linked list. Alternates are managed as a linked list of `struct odb_files_dir` within the files backend. All ODB operations are updated to loop through this list: reads check each directory in sequence; writes target only the first directory. Commands like `git fsck`, `git gc`, and `git pack-objects` are updated to iterate over directories instead of sources. Karthik Nayak’s review of this patch raised a **technical concern** about the removal of the `if (r->objects)` check in `clear_midx_file()`, which previously guarded against NULL dereferences. Patrick Steinhardt’s response clarified that the check was redundant: the sole caller (`builtin/bugreport.c`) already dereferences `r->objects`, and the function itself does so later. The removal is thus safe, eliminating a false sense of security rather than introducing a regression.

Open questions and loose ends
- **Patch 2/13**: The test helper `git_test_write_commit_graph_or_die()` now takes only a `struct repository *` but internally hard-codes the object directory path from `repo->objects->sources->path`. This could break test cases that need to write commit graphs to non-default object directories (e.g., alternates, quarantine directories, or custom test setups). The function should forward an explicit path argument to align with the series’ shift toward explicit repository and path arguments. Patrick Steinhardt dismissed this concern in his reply to Karthik Nayak, arguing the function is a test-suite hack and the current implementation is sufficient. Karthik Nayak acknowledged Patrick’s response in the latest email, accepting the dismissal without further discussion. The inconsistency persists as an unresolved loose end, though no test failures or edge cases have been reported.
- The series’ size (13 patches, 482 lines added to `odb/source-files.c`, 439 lines removed from `odb.c`) may pose integration challenges, particularly for edge cases like promisor remotes, partial clones, or non-files backends. The linked-list traversal order for alternates (e.g., whether they are appended, prepended, or managed in a specific order) remains an open question. Patches 8/13 and 9/13 clarify that the quarantine directory is inserted at the head of the list, but the broader alternates ordering is not yet addressed. Reviewers should verify that this ordering does not break assumptions in `git gc` or `git repack`.
- Merge conflicts with `seen` are documented but unresolved; a reroll may be required.
- The architectural shift is now well-justified, but the implementation’s robustness in non-default ODB configurations (e.g., partial clones, promisor remotes) remains untested. The lack of deeper edge-case review (e.g., linked-list invariants, promisor remotes, partial clones, or the behavioral implications of path canonicalization in patch 4/13) suggests potential blind spots. Patch 4/13 introduces a subtle behavioral change where alternates are identified by their canonicalized absolute path (`abspath`) rather than the raw path stored in the source, which could affect edge cases involving symlinks or relative paths. No such issues have been reported, but the change warrants scrutiny in follow-up reviews.

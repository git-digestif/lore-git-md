This is a **substantive review** of the second patch in Kristofer Karlsson’s two-patch series optimizing `fetch.writeCommitGraph` for large repositories. The series aims to replace the current full-reachability scan after every fetch with an incremental write using only the newly updated refs as seeds.

Patrick Steinhardt’s review focuses on correctness and edge cases. His key question is whether the new seeds passed to `write_commit_graph()` are **additive** (extending the existing graph) or **exclusive** (replacing it). The patch’s fallback logic—full scan when no graph exists, incremental write when one does—implies the seeds are additive, but the commit message does not state this explicitly. Patrick also asks how the optimization behaves in **non-split mode** (the patch only mentions split mode’s `close_reachable()` behavior).

Other points raised:
- **Ref status filtering**: Patrick questions whether `collect_updated_tips()` should skip more `REF_STATUS_*` values (e.g., only allow `REF_STATUS_OK`).
- **`old_oid` lookup**: He asks why the code uses `rm->old_oid` (the pre-fetch ref value) instead of `rm->new_oid` (post-fetch).
- **Benchmarking**: Patrick notes the absence of performance measurements, though the patch’s motivation is purely performance-driven.
- **Design clarity**: He observes that `GRAPH_WRITE_SKIP` is redundant (could be derived from `oidset_size()`), but accepts it as a safeguard.

The review is **tested-level in spirit**—Patrick engages deeply with the code’s behavior and edge cases—but lacks explicit confirmation of testing. His questions suggest the patch is well-scoped but needs clarification on core assumptions (additive vs. exclusive seeds, non-split mode behavior). The series remains under review; no prior discussion or open questions were raised before this exchange.

Thread identity: RFC patch series proposing a new signing mechanism that embeds SHA-256 digests of tree contents (including submodules) in signed commits/tags, authored by Scott Chacon (`scott@gitbutler.net`). Thread type: design discussion/RFC; no prior version exists.

Core problem or goal: Provide a migration path away from SHA-1 for commit/tag signing without requiring a disruptive switch to SHA-256 as the default object format in Git 3.0. The mechanism computes a SHA-256 digest over a sorted list of `<sha256(content)> SP <path> NUL` records for every file in the tree, with submodules contributing their own tree digests recursively. The digest is embedded in signed objects via a new `--hash=sha256` option for `git commit -S` and `git tag -s`, and a `gpg.treeHash=sha256` config key. The debate has expanded to question whether the Git 3.0 plan (switching the default object format to SHA-256 in March 2027) is strategically sound, given ecosystem disruption risks and the availability of alternative approaches like the tree-digest mechanism.

Current status: Under review as an RFC; no decisions or merge status recorded. The thread remains in the design-discussion phase, but the strategic viability of both the tree-digest proposal *and* the Git 3.0 plan is now actively contested. Scott Chacon has explicitly framed his RFC as a counterproposal to the Git 3.0 default switch, arguing that SHA-1’s content-addressing role does not require collision resistance and that the tree-digest mechanism could satisfy cryptographic signature requirements without ecosystem disruption. Brian M. Carlson continues to reject this framing, insisting that the Git 3.0 timeline is non-negotiable and that the tree-digest approach fails to address the core problem of SHA-1’s cryptographic weaknesses. Junio C Hamano has not yet weighed in on the strategic debate, though he previously raised substantive design questions about the digest algorithm.

Key technical details:
- Files touched: `tree-sha256.c` (new, 238 lines), `test-tree-sha256.c` (new, 31 lines), `builtin/tag.c` (29 lines added in patch 2, plus config parsing in patch 4; patch 2 refactored tag header construction to use a single newline after the `tagger` line, enabling conditional insertion of the `tree-sha256` header before the final blank line), `builtin/commit.c` (new functionality in patch 3, plus config parsing in patch 4), `Documentation/config/gpg.adoc` (new config key documented in patch 4), `git-commit.adoc` and `git-tag.adoc` (updated to mention config override behavior in patch 4), and test scripts `t/t1018-tree-sha256.sh` (123 lines), `t/t1019-tree-sha256-verify.sh`, and `t/t7032-tree-sha256-signed.sh` (extended in patch 4 with four new test cases).
- New CLI option: `--hash=sha256` for `git commit -S` (patch 3) and `git tag -s`/`git tag -u` (patch 2).
- New config key: `gpg.treeHash=sha256` (patch 4), which makes the `--hash=sha256` behavior the default for all signed objects.
- On-disk format: SHA-256 digest embedded in signed objects as an extra header (e.g., `tree-sha256: <digest>` in commits and tags) between the committer/tagger line and the `gpgsig` block (for commits) or blank line preceding the message (for tags); no change to object format itself. The digest is computed from a sorted list of `<sha256(content)> SP <path> NUL` records, with submodules contributing their own tree digests recursively.
- Subsystems: signing, commit/tag creation, submodule handling, object database, configuration.
- Test coverage: new test scripts validate the digest computation (including edge cases like file mode changes, path renames, submodule updates, and missing submodules), stability across commits/tags/trees, backwards compatibility, signature coverage, and config behavior. The test helper recomputes the digest manually using `git ls-tree`, `git cat-file`, and `sha256sum`. Tests confirm the header is present when expected, absent when not, correctly recomputed or dropped during amend operations, and properly overridden by CLI options or config values.
- Error handling: detects submodule cycles (treating them as "cycle:<commit>") and reports missing submodule commits without infinite recursion. The `--hash=sha256` option is rejected unless used with signing (`-s` or `-u`), and unknown algorithms (e.g., `--hash=md5`) are rejected with clear error messages. On amend, any existing `tree-sha256` header is deliberately dropped and recomputed only if the amended commit is signed with `--hash=sha256`. The config key rejects invalid values (e.g., `gpg.treeHash=md5`).
- Performance: Junio noted the current implementation reads entire blobs into memory before hashing, which could be problematic for large files; he suggested using Git’s streaming object interface (like `archive-tar.c` and `archive-zip.c`) to hash blobs incrementally.

Open questions and loose ends:
1. **Strategic viability of the Git 3.0 plan**: Whether the project should proceed with switching the default object format to SHA-256 in March 2027, given the ecosystem disruption risks (untested interoperability code, unaddressed edge cases like GitHub’s "limbo" state for mixed-hash repos, and widespread breakage in scripts/tools/workflows that assume SHA-1 object IDs). Chacon argues the costs outweigh the benefits, while Carlson insists the timeline is non-negotiable and that the tree-digest approach fails to address the core problem of SHA-1’s collision resistance weaknesses.
2. **Regulatory compliance**: Whether the tree-digest mechanism satisfies government mandates banning SHA-1 for signatures, or if a full SHA-256 object format switch is required. Chacon claims the former is sufficient, while Carlson’s critique implies the latter is necessary.
3. **Design of the digest algorithm**:
   - Should the digest distinguish between blobs stored as executable files, non-executable files, and symlinks pointing to the same content? (Junio’s question; current implementation ignores file modes and symlink targets.)
   - Should the digest reflect the *internal structure* of the tree object (e.g., entry order) to detect corruption, or remain a content-addressable summary (invariant under reordering)? (Junio’s question; current implementation sorts entries before hashing.)
4. Whether submodules should be excludable from the digest computation (e.g., via a `--no-submodules` flag).
5. Naming choices for the new option (`--hash=sha256`) and config key (`gpg.treeHash=sha256`).
6. Performance optimization (parallel hashing and streaming blob hashing) deferred; current implementation is unoptimized but acceptable.
7. Whether the behavior of dropping the `tree-sha256` header on amend is the right choice.
8. Whether the config key should be split into separate keys for commits and tags (e.g., `gpg.commitTreeHash` and `gpg.tagTreeHash`), or remain unified as `gpg.treeHash`.

Participant positions:
- **Scott Chacon** (author): Proposes the tree-digest mechanism as both a near-term solution for signature security *and* a strategic alternative to the Git 3.0 SHA-256 default switch. Argues that SHA-1’s content-addressing role does not require collision resistance, that the tree-digest approach satisfies regulatory mandates for signatures, and that the Git 3.0 plan’s ecosystem disruption risks outweigh its benefits. Advocates for delaying the default switch to a future release (e.g., Git 4.0) to allow opt-in adoption and iterative refinement.
- **Junio C Hamano** (maintainer): Raised substantive design questions about the digest algorithm (file mode/symlink distinctions and tree structure reflection) but has not yet engaged with the broader strategic debate. Praised the refactoring of tag header construction in patch 2 as "very nice."
- **brian m. carlson**: Firmly rejects the tree-digest proposal as strategically misaligned with the Git 3.0 plan and regulatory timelines. Argues that the mechanism fails to address the core problem of SHA-1’s collision resistance weaknesses and that the Git project is already committed to a full transition to SHA-256 as the default object format. Emphasizes that security researchers and other users need SHA-256 repositories to store colliding blobs, and that the proposal is too late given the Git 3.0 timeline (March 2027) and ecosystem adoption of SHA-256. Suggests the interoperability work (rewriting repositories between hash algorithms during clone/fetch) as the real solution.

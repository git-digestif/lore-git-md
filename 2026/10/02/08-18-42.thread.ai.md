Thread identity: RFC patch series proposing a new signing mechanism that embeds SHA-256 digests of tree contents (including submodules) in signed commits/tags, authored by Scott Chacon (`scott@gitbutler.net`). Thread type: design discussion/RFC; no prior version exists.

Core problem or goal: Provide a migration path away from SHA-1 for commit/tag signing without requiring a disruptive switch to SHA-256 as the default object format in Git 3.0. The mechanism computes a SHA-256 digest over a sorted list of `<sha256(content)> SP <path> NUL` records for every file in the tree, with submodules contributing their own tree digests recursively. The digest is embedded in signed objects via a new `--hash=sha256` option for `git commit -S` and `git tag -s`, and a `gpg.treeHash=sha256` config key. The implementation handles submodule cycles and missing commits gracefully, reporting errors without infinite recursion.

Current status: Under initial review as an RFC; no decisions or merge status recorded. The series is now complete with four patches, adding the `--hash=sha256` option to both `git commit -S` (patch 3) and `git tag -s` (patch 2). The implementation is self-contained, adding `tree-sha256.c`, a test helper (`test-tree-sha256.c`), and three test scripts (`t/t1018-tree-sha256.sh`, `t/t1019-tree-sha256-verify.sh`, and `t/t7032-tree-sha256-signed.sh`). Backwards compatibility is preserved: older Git versions ignore the extra header, and verification continues to work as before. The author explicitly labels the series as experimental and solicits feedback on five open questions.

Key technical details:
- Files touched: `tree-sha256.c` (new, 238 lines), `test-tree-sha256.c` (new, 31 lines), `builtin/tag.c` (29 lines added in patch 2), `builtin/commit.c` (new functionality in patch 3), and test scripts `t/t1018-tree-sha256.sh` (123 lines), `t/t1019-tree-sha256-verify.sh`, and `t/t7032-tree-sha256-signed.sh` (new).
- New CLI option: `--hash=sha256` for `git commit -S` (patch 3) and `git tag -s`/`git tag -u` (patch 2).
- New config key: `gpg.treeHash=sha256`.
- On-disk format: SHA-256 digest embedded in signed objects as an extra header (e.g., `tree-sha256: <digest>` in commits and tags) between the committer/tagger line and the `gpgsig` block (for commits) or blank line preceding the message (for tags); no change to object format itself. The digest is computed from a sorted list of `<sha256(content)> SP <path> NUL` records, with submodules contributing their own tree digests recursively.
- Subsystems: signing, commit/tag creation, submodule handling, object database.
- Test coverage: new test scripts validate the digest computation (including edge cases like file mode changes, path renames, submodule updates, and missing submodules), stability across commits/tags/trees, backwards compatibility, and signature coverage. The test helper recomputes the digest manually using `git ls-tree`, `git cat-file`, and `sha256sum`. Tests confirm the header is present when expected, absent when not, and correctly recomputed or dropped during amend operations.
- Error handling: detects submodule cycles (treating them as "cycle:<commit>") and reports missing submodule commits without infinite recursion. The `--hash=sha256` option is rejected unless used with signing (`-s` or `-u`), and unknown algorithms (e.g., `--hash=md5`) are rejected with clear error messages. On amend, any existing `tree-sha256` header is deliberately dropped and recomputed only if the amended commit is signed with `--hash=sha256`.

Open questions and loose ends:
1. Viability as an alternative to switching the default object format to SHA-256 in Git 3.0.
2. Design of verification: how should Git verify the embedded SHA-256 digest? (e.g., should it recompute the digest and compare, or rely on GPG signatures alone?)
3. Whether submodules should be excludable from the digest computation (e.g., via a `--no-submodules` flag).
4. Naming choices for the new option (`--hash=sha256`) and config key (`gpg.treeHash=sha256`).
5. Performance optimization (parallel hashing) deferred; current implementation is unoptimized but acceptable.
6. Whether the behavior of dropping the `tree-sha256` header on amend is the right choice.

Participant positions: Only the author (Scott Chacon) has spoken so far; no reviews or objections recorded. The author’s position is that the mechanism could offer security benefits without ecosystem-wide churn, but the series is explicitly experimental and not yet advocated for merging.

Related work: Tied to the Git 3.0 timeline and the broader SHA-1 deprecation effort. The proposal is positioned as an alternative to switching the default object format to SHA-256, which has been a long-standing discussion topic. No external dependencies or prior versions mentioned. The design is object-format-agnostic, allowing it to work with both SHA-1 and SHA-256 repositories.

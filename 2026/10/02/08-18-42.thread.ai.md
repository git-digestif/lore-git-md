Thread identity: RFC patch series proposing a new signing mechanism that embeds SHA-256 digests of tree contents (including submodules) in signed commits/tags, authored by Scott Chacon (`scott@gitbutler.net`). Thread type: design discussion/RFC; no prior version exists.

Core problem or goal: Provide a migration path away from SHA-1 for commit/tag signing without requiring a disruptive switch to SHA-256 as the default object format in Git 3.0. The mechanism computes a SHA-256 digest over a sorted list of `<sha256(content)> SP <path> NUL` records for every file in the tree, with submodules contributing their own tree digests recursively. The debate has expanded to question whether the Git 3.0 plan (switching the default object format to SHA-256 in March 2027) is strategically sound, given ecosystem disruption risks, the availability of alternative approaches like the tree-digest mechanism, and the lack of broad community buy-in for the transition. The thread now explores whether the tree-digest proposal could serve as a near-term solution for signature security, whether the Git 3.0 plan should proceed as scheduled, be delayed, or abandoned, and how to address the practical challenges of migrating real-world repositories to SHA-256. The discussion has broadened to include the feasibility of opt-in adoption models, the logistics of upstreaming the interoperability work, the readiness of Git’s tooling and documentation for the transition, and the institutional challenges of completing foundational work in an open-source project.

Current status: Under review as an RFC; no decisions or merge status recorded. The thread remains in the design-discussion phase, with the strategic viability of the tree-digest proposal, the Git 3.0 plan, and Schindelin’s compromise (SHA-256 support without default enforcement) all actively contested. Key technical details:
- Files touched: `tree-sha256.c` (new, 238 lines), `test-tree-sha256.c` (new, 31 lines), `builtin/tag.c` (29 lines added in patch 2, plus config parsing in patch 4; patch 2 refactored tag header construction to use a single newline after the `tagger` line, enabling conditional insertion of the `tree-sha256` header before the final blank line), `builtin/commit.c` (new functionality in patch 3, plus config parsing in patch 4), `Documentation/config/gpg.adoc` (new config key documented in patch 4), `git-commit.adoc` and `git-tag.adoc` (updated to mention config override behavior in patch 4), and test scripts `t/t1018-tree-sha256.sh` (123 lines), `t/t1019-tree-sha256-verify.sh`, and `t/t7032-tree-sha256-signed.sh` (extended in patch 4 with four new test cases).
- New CLI option: `--hash=sha256` for `git commit -S` (patch 3) and `git tag -s`/`git tag -u` (patch 2).
- New config key: `gpg.treeHash=sha256` (patch 4), which makes the `--hash=sha256` behavior the default for all signed objects.
- On-disk format: SHA-256 digest embedded in signed objects as an extra header (e.g., `tree-sha256: <digest>` in commits and tags) between the committer/tagger line and the `gpgsig` block (for commits) or blank line preceding the message (for tags); no change to object format itself. The digest is computed from a sorted list of `<sha256(content)> SP <path> NUL` records, with submodules contributing their own tree digests recursively.
- Subsystems: signing, commit/tag creation, submodule handling, object database, configuration.
- Test coverage: new test scripts validate the digest computation (including edge cases like file mode changes, path renames, submodule updates, and missing submodules), stability across commits/tags/trees, backwards compatibility, signature coverage, and config behavior. The test helper recomputes the digest manually using `git ls-tree`, `git cat-file`, and `sha256sum`. Tests confirm the header is present when expected, absent when not, correctly recomputed or dropped during amend operations, and properly overridden by CLI options or config values.
- Error handling: detects submodule cycles (treating them as "cycle:<commit>") and reports missing submodule commits without infinite recursion. The `--hash=sha256` option is rejected unless used with signing (`-s` or `-u`), and unknown algorithms (e.g., `--hash=md5`) are rejected with clear error messages. On amend, any existing `tree-sha256` header is deliberately dropped and recomputed only if the amended commit is signed with `--hash=sha256`. The config key rejects invalid values (e.g., `gpg.treeHash=md5`).
- Performance: Junio noted the current implementation reads entire blobs into memory before hashing, which could be problematic for large files; he suggested using Git’s streaming object interface (like `archive-tar.c` and `archive-zip.c`) to hash blobs incrementally.
- **Interoperability work status**: The interoperability work is publicly available in Carlson’s GitHub fork (`sha256-interop` branch), though it remains experimental and incomplete. Key gaps include missing in-place migration tooling (critical for submodules), unoptimized performance (e.g., recursive delta resolution, batched object map writes), and conflicts with the pluggable ODB effort. The series is large (212 patches) and would require roughly four release cycles (24 weeks) to upstream, assuming steady review. An in-place migration helper would add another two cycles. The work is not yet ready for non-experimental use, but early patches (e.g., `sha256-interop-part-2` branch) could be rebased and polished for incremental submission. Testing has been limited to a personal repository (`lawn.git`) and lacks real-world scenarios (large repos, submodules, mixed clients/servers, or interoperability with JGit/libgit2). Carlson’s earlier `convert-git` script provides a functional (if imperfect) alternative for converting repositories to SHA-256, but it is slow, produces different results than the true interoperability code, and offers a poor user experience. The interoperability work itself does not currently handle notes, but Carlson suggests in-place rewriting could address this in the future. Submodules are supported in the `convert-git` script but not yet in the upstream interoperability work. Junio’s latest reply proposes a governance experiment to accelerate upstreaming: temporarily prioritizing the interoperability work above all other changes (including scalability improvements) and granting contributors veto power over conflicting topics. Carlson’s latest reply acknowledges the potential of this approach but highlights practical barriers, including the lack of corporate-funded time for foundational work, technical debt from competing priorities (e.g., the pluggable ODB effort), and logistical constraints (e.g., Outlook corrupting patches). He welcomes community collaboration (e.g., rebasing patches, fixing tests, or upstreaming early work) and suggests that even small contributions would help, but emphasizes the need for timely reviews—a bottleneck that also plagued the original SHA-256 work.

This is the final patch (5/5) in Christian Couder’s v5 series introducing `uploadpack.lazyFetchTrusted`, a server-side protected configuration variable that lets operators explicitly mark repositories as trusted for lazy fetching. The patch activates the mechanism by conditionally *not* setting `GIT_NO_LAZY_FETCH=1` when the served repository is in the allowlist, preserving operator control over the environment variable.

The implementation is straightforward: `builtin/upload-pack.c` now checks whether the repository is trusted (using the `upload_pack_lazy_fetch_trusted()` helper introduced in patch 3/5) before setting `GIT_NO_LAZY_FETCH`. If the repository is trusted and the environment variable is unset, lazy fetching remains enabled; otherwise, it is disabled as before. The logic is cleanly separated into three cases: explicit operator override via `GIT_NO_LAZY_FETCH`, server-side trust via `uploadpack.lazyFetchTrusted`, and the default (disable lazy fetching).

The documentation updates are thorough, explaining how repositories are identified (including edge cases like `--separate-git-dir` and linked worktrees), emphasizing that trust does *not* propagate to promisor remotes, and clarifying the difference between server-side trust and client-side `GIT_NO_LAZY_FETCH=0`. The new tests cover all key behaviors: path validation (worktree vs. git-dir), recursion safeguards (a trusted repository serving itself), explicit environment variable override, and the non-propagation of trust to promisor remotes. The test for recursion safeguards is particularly important, as it verifies that the depth limit introduced in patch 4/5 works as intended.

This patch is well-motivated and addresses the security concern that untrusted repositories could trigger arbitrary code execution via lazy-fetch hooks or configuration. The server-side trust model is a clear improvement over the earlier client-side `GIT_NO_LAZY_FETCH=fromAccepted` proposal, and the implementation is careful to avoid unintended trust propagation. The documentation and tests are comprehensive, covering edge cases that could otherwise lead to subtle bugs. No substantive concerns remain from Junio’s reviews; his feedback on v4 was entirely surface-level (grammar and wording). The series as a whole is ready for integration, and this patch is the linchpin that makes the new mechanism operational.

This is the second patch in a two-part **bugfix series** targeting a subtle but serious packfile corruption issue. The problem stems from stale delta base cache entries persisting after their owning pack is closed and freed. When Git later reuses the same memory address for a new pack, the stale cache entries can collide with the new pack’s data, leading to incorrect object reconstruction—sometimes detected as corruption, but potentially silent in more contrived scenarios.

The fix itself is straightforward: when closing a pack (`close_pack()`), Git now evicts all delta base cache entries tied to that pack. This ensures no stale entries linger to cause future collisions. The patch adds a new helper function, `delta_base_cache_evict_entry()`, which iterates over the cache’s LRU list and releases any entries belonging to the closing pack. The change is minimal—just seven lines in `packfile.c`—and preserves the existing cache behavior for active packs.

The accompanying test in `t/t6437-submodule-merge.sh` is more involved, but that’s by necessity. The bug only surfaces under specific conditions: recursive submodule merges with many similarly structured packfiles, where glibc’s memory allocator happens to reuse the same address for a new pack. The test sets up 16 submodules, each with two divergent branches, then merges them in a way that reliably triggers the corruption on Patrick’s machine (NixOS with glibc 2.44-25). While the test’s success may depend on platform-specific allocation behavior, the scenario it models is realistic enough to justify inclusion.

This patch builds directly on the preparatory refactoring in patch 1, which moved `close_pack()` to avoid forward declarations. The series is well-structured: patch 1 is pure refactoring with no behavior change, while patch 2 introduces the fix and its test. The commit message is exemplary—it walks through the root cause, explains why the bug became more likely after a prior memory-leak fix (6f1e9394e2), and provides a clear reproduction case. The only caveat is the test’s reliance on glibc’s allocation quirks, but that’s noted upfront, and the core fix is portable.

For a busy reader, this is a **high-signal patch**: a narrowly scoped fix for a real, reproducible corruption bug, with thorough test coverage and a clean implementation. The risk of controversy seems low—no one is likely to argue for keeping stale cache entries around. If you care about packfile correctness or submodule merges, this is worth reviewing or at least tracking.

This is the second patch in a two-patch performance optimization series targeting the commit-graph subsystem. It implements the core logic for incremental commit-graph writes after fetches, addressing a long-standing inefficiency where `fetch.writeCommitGraph` rebuilds the entire graph from all reachable refs after every fetch—even when only a few refs were updated.

The patch introduces a three-mode strategy controlled by `prepare_commit_graph()`: skip the write entirely for no-op fetches, write incrementally from updated refs when possible, and fall back to a full reachable scan when no existing graph exists or when fetching from multiple remotes. The implementation collects updated refs in an `oidset` during `do_fetch()`, then passes them directly to `write_commit_graph()` instead of scanning all refs. This avoids the expensive ref-scanning callback (`add_ref_to_set()`) that became more costly in 2020 when it started validating refs against the object database.

The changes are well-scoped and maintain correctness: incremental writes in split mode use `close_reachable()` to walk from updated tips, stopping at commits already in the graph, which naturally covers auto-followed tags. The fallback to full scans in edge cases (no existing graph or multi-remote fetches) ensures the commit-graph remains complete, while periodic full rebuilds remain the responsibility of `git maintenance` or `git gc`. Test coverage is thorough, with four new tests in `t/t5510-fetch.sh` verifying incremental writes, unrelated commits, no-op fetches, and fallback behavior.

This looks like a clean, well-motivated optimization that should benefit large repositories without introducing regressions. The commit message clearly explains the problem, the solution, and the trade-offs, and the implementation appears careful about correctness. The series is ready for review, with no prior discussion or controversy.

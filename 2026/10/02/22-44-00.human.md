This is an RFC proposal from Jeff King (Peff) addressing a usability pain point in Git 3.0 and beyond: first-time pushes to newly created repositories on forges like GitHub.

The problem is straightforward: when a user creates a bare repository on a hosting service, it must be initialized with either SHA-1 or SHA-256. If the forge defaults to SHA-1 (as most do today), users with SHA-256 repositories will hit a fatal error on their first push, and vice versa. Savvy users can work around this by specifying the object format when creating the remote repo, but most won’t know or remember to do so.

Peff’s proposed solution is a "limbo" state for empty repositories. The server would advertise that it has no object format yet, and the client would respond with its own format during the push. The server would then atomically adopt that format, making the first push succeed regardless of the client’s hash algorithm. This mirrors how GitHub already handles the HEAD symref for new repositories.

The idea is well-motivated and addresses a real friction point for users upgrading to Git 3.0 or working across hash formats. Peff acknowledges some server-side complexity (e.g., atomic updates to avoid race conditions) but sees no fundamental blockers. He hasn’t implemented anything yet and is soliciting feedback before diving deeper.

This is early-stage brainstorming, not a patch or even a design doc, but it’s worth paying attention to if you care about Git 3.0 adoption or cross-format interoperability. The thread is likely to attract discussion from forge maintainers (GitHub, GitLab) and contributors working on hash transition plumbing.

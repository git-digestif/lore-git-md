This is the first patch in a three-part bugfix series targeting the `rerere` subsystem. It addresses a long-standing race condition where concurrent `rerere` operations (e.g., a rebase and background maintenance) contend for the shared `MERGE_RR.lock`, leading to crashes or deadlocks. The geometric maintenance strategy introduced in Git 2.54 exacerbated the issue by triggering `git rerere gc` more aggressively, but the race is a general robustness flaw in `rerere` locking.

The patch introduces a configurable timeout (`rerere.lockTimeout`, defaulting to 1000 milliseconds) for acquiring the `MERGE_RR.lock`. Instead of failing immediately when the lock is held, processes now wait up to the timeout before giving up. This change is motivated by the observation that `git rerere gc` operations typically complete within a second, so the default timeout is sufficient to avoid unnecessary failures during common scenarios like rebases. The timeout is configurable, allowing users to adjust it for their specific use cases (e.g., setting it to 0 to disable waiting or -1 to wait indefinitely).

The implementation touches `rerere.c` and adds documentation for the new `rerere.lockTimeout` configuration option in `Documentation/config/rerere.adoc`. The test suite (`t/t4200-rerere.sh`) is expanded to cover various scenarios, including waiting for the lock, failing after the timeout, and verifying that explicit `rerere` commands (e.g., `forget`, `clear`, `gc`) still fail immediately if the lock cannot be acquired. The patch also ensures that `git rebase --abort` fails gracefully if the lock is held, preserving the rebase state for later recovery.

This is a well-crafted, pragmatic fix for a real-world problem. The commit message clearly explains the motivation, the implementation is clean, and the test coverage is thorough. The patch aligns with established Git patterns (e.g., configurable timeouts) and does not introduce any controversial changes. It is ready for integration and sets the stage for the remaining patches in the series, which further refine the locking behavior for background maintenance and conflict-stopping commands.

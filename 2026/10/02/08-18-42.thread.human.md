This Git mailing list thread is a high-stakes debate about the future of Git’s cryptographic security and the planned transition to SHA-256 in Git 3.0 (March 2027). At its core, the discussion pits a new technical proposal—Scott Chacon’s tree-digest signing mechanism—against the project’s long-standing plan to switch Git’s default object format to SHA-256, with broader questions about project governance, ecosystem disruption, and the role of corporate influence now front and center.

Chacon’s RFC proposes embedding SHA-256 digests of tree contents (including submodules) in signed commits and tags, offering a migration path away from SHA-1 for signatures without requiring a disruptive switch to SHA-256 as the default object format. The mechanism is technically sound: it adds a new `--hash=sha256` option to `git commit -S` and `git tag -s`, computes digests recursively over sorted tree entries, and handles edge cases like submodule cycles and missing commits. Junio Hamano praised parts of the implementation but raised design questions about whether the digest should reflect file modes or tree structure. The proposal has since become a proxy for a larger strategic battle, with Chacon arguing that the Git 3.0 plan’s ecosystem disruption risks outweigh its benefits and that the transition lacks broad community buy-in.

The thread has now split into three camps. Brian Carlson and Patrick Steinhardt defend the Git 3.0 default switch as necessary for regulatory compliance and ecosystem momentum, framing it as a community-driven effort rather than a corporate mandate. Carlson, who has led much of the SHA-256 work, rejects the tree-digest proposal as insufficient for security researchers and institutions needing SHA-256 repositories to store colliding blobs. Steinhardt warns that abandoning the transition would halt progress entirely, making future breaking changes exponentially harder. Johannes Schindelin, however, has proposed a middle ground: Git 3.0 should ship with robust SHA-256 support but leave SHA-1 as the default, allowing opt-in adoption. He argues that the cryptographic benefits of SHA-256 are overstated (citing a $10k, one-month cost to generate a Git-specific SHA-1 collision) and that migration pain points—submodules, partial clones, and tooling compatibility—remain unresolved. Christian Couder has shifted the discussion toward pragmatism, asking pointed questions about the availability, completeness, and upstreaming timeline of the interoperability work (rewriting repositories between hash algorithms during clone/fetch) that Carlson previously identified as the "real solution" to SHA-1 deprecation.

The debate now hinges on whether Junio will view Schindelin’s compromise as a viable path forward or a dilution of the project’s commitment. Key unresolved questions include whether the tree-digest mechanism satisfies regulatory mandates, how to handle mixed-hash repositories, and whether the interoperability work can be upstreamed in time for Git 3.0. The thread has also surfaced deeper tensions about project governance, the role of corporate contributors (particularly GitHub), and how to balance technical necessity with user impact. For now, the series remains an RFC, but the strategic stakes have escalated far beyond its original scope.

This thread is an RFC patch series by Scott Chacon proposing a new signing mechanism for Git that embeds SHA-256 digests of tree contents (including submodules) in signed commits and tags. The goal is to provide a migration path away from SHA-1 for commit/tag signing without requiring a disruptive switch to SHA-256 as the default object format in Git 3.0.

The series is now complete with four patches. The latest patch adds a `gpg.treeHash=sha256` configuration key to make the `--hash=sha256` behavior the default for all signed objects, eliminating the need to specify the option manually. The implementation is self-contained, adding new files (`tree-sha256.c`, `test-tree-sha256.c`) and test scripts, while preserving backwards compatibility—older Git versions ignore the extra header, and verification continues to work as before. The digest is computed from a sorted list of file contents and paths, with submodules contributing their own tree digests recursively. The series handles edge cases like submodule cycles and missing commits gracefully.

The proposal is explicitly experimental, and the author has raised five open questions for discussion: the viability of this approach as an alternative to switching the default object format to SHA-256, how verification should work, whether submodules should be excludable, naming choices, and performance optimizations. So far, only the author has participated in the thread, and no reviews or objections have been recorded. The series is tied to the broader SHA-1 deprecation effort and the Git 3.0 timeline but remains under initial review.

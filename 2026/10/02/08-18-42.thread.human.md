This thread is an RFC from Scott Chacon proposing a new signing mechanism for Git that embeds SHA-256 digests of tree contents (including submodules) in signed commits and tags. The goal is to provide a migration path away from SHA-1 for commit/tag signing without requiring a disruptive switch to SHA-256 as the default object format in Git 3.0.

So far, the series consists of four patches. The first introduces the digest computation logic, the second adds support for `git tag -s`, and the latest patch (just summarized) teaches `git commit -S` the `--hash=sha256` option. The implementation is self-contained, adding a new `tree-sha256.c` file and test scripts, and preserves backwards compatibility—older Git versions ignore the extra header, and verification continues to work as before. The digest is embedded as an extra header in signed objects, computed from a sorted list of `<sha256(content)> SP <path> NUL` records, with submodules contributing their own tree digests recursively. The series handles submodule cycles and missing commits gracefully, reporting errors without infinite recursion.

The author has explicitly labeled the series as experimental and is soliciting feedback on several open questions, including the viability of this approach as an alternative to switching the default object format to SHA-256, how verification should work, whether submodules should be excludable from the digest, and naming choices for the new option and config key. Performance optimizations like parallel hashing are deferred for now. No reviews or objections have been recorded yet, and the series remains under initial discussion as an RFC. The proposal is tied to the broader SHA-1 deprecation effort and the Git 3.0 timeline but is designed to work with both SHA-1 and SHA-256 repositories.

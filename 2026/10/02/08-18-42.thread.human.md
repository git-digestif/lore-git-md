This thread began as an RFC by Scott Chacon proposing a new signing mechanism that embeds SHA-256 digests of tree contents in signed commits and tags, offering an alternative to the planned Git 3.0 switch to SHA-256 as the default object format. The discussion has since expanded into a broader debate about the strategic viability of the Git 3.0 transition, with Chacon arguing that the tree-digest approach could satisfy regulatory requirements for signatures without the ecosystem disruption of a full object format switch, while brian m. carlson and Patrick Steinhardt defend the transition as necessary and community-driven.

The technical proposal itself—adding a `--hash=sha256` option to `git commit -S` and `git tag -s`, along with a `gpg.treeHash=sha256` config key—has seen little substantive pushback on its mechanics. Junio C Hamano raised design questions about whether the digest should account for file modes or tree structure, but these remain unresolved. The implementation is functionally complete, with new test coverage for edge cases like submodule cycles and missing submodules, though performance optimizations (streaming blob hashing) are deferred.

The strategic debate has dominated recent discussion. Chacon frames the Git 3.0 plan as a GitHub-driven effort lacking broad community buy-in, while Carlson and Steinhardt counter that the transition is necessary for regulatory compliance and ecosystem momentum. Carlson’s critique of the tree-digest proposal centers on its incompatibility with the Git 3.0 timeline and the need for SHA-256 repositories to store colliding blobs, while Steinhardt warns that abandoning the transition would ossify the ecosystem.

Christian Couder’s latest email shifts the focus to the interoperability work—rewriting repositories between hash algorithms during clone/fetch—which Carlson previously called the "real solution." Couder’s questions about the work’s availability, completeness, effort, collaboration, and testing aim to assess whether it could be upstreamed in time to smooth the Git 3.0 transition. His constructive tone and offer to help suggest a path forward: if the interoperability work is close to ready and the involved company is willing to collaborate openly, it could reduce the urgency of the tree-digest proposal. If not, the proposal may gain traction as a stopgap. The thread is now pivoting toward actionable next steps, with the interoperability work’s status likely to shape the outcome.

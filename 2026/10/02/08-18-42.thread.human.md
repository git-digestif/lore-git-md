This thread began as an RFC proposing a new signing mechanism that embeds SHA-256 digests of tree contents in signed commits and tags, authored by Scott Chacon. The goal was to provide a migration path away from SHA-1 for signing without requiring a disruptive switch to SHA-256 as Git’s default object format in Git 3.0. The proposal introduced a `--hash=sha256` option for `git commit -S` and `git tag -s`, along with a `gpg.treeHash=sha256` config key, and included detailed handling of submodules and error cases. Junio C Hamano raised design questions about the digest algorithm, while Brian M. Carlson firmly rejected the proposal as strategically misaligned with the Git 3.0 plan, arguing it fails to address SHA-1’s collision resistance weaknesses.

The discussion has now shifted to a broader debate about the Git 3.0 timeline itself. In his latest email, Chacon directly challenges the plan to switch Git’s default object format to SHA-256 in Git 3.0 (scheduled for March 2027). He argues that the SHA-1 deprecation problem is overstated for Git’s use case—content addressing, not cryptographic protection—and that the real issue, signature integrity, can be solved by decoupling it from the object hash, as his RFC proposes. He disputes Carlson’s regulatory framing, noting that governments ban SHA-1 only for *signatures*, not general-purpose hashing, and that the tree-digest approach would satisfy compliance while preserving backwards compatibility. Chacon emphasizes the practical costs of the default switch: untested interoperability code, unaddressed edge cases (like GitHub’s "limbo" state for mixed-hash repos), and the risk of widespread breakage in tools and workflows that assume SHA-1 object IDs. He proposes delaying the default switch to a future release (e.g., Git 4.0) to allow opt-in adoption and iterative refinement, while still encouraging the tree-digest signing mechanism as a near-term solution.

The thread is now at a crossroads. The original RFC’s technical design questions (e.g., digest algorithm details, submodule handling) are overshadowed by the strategic debate over whether the Git 3.0 timeline is truly immutable. Chacon’s counterproposal frames the discussion as a trade-off between security posture and ecosystem stability, and his arguments may prompt the project to reconsider the default switch—or at least to acknowledge the practical challenges more explicitly. The outcome will likely hinge on whether other key contributors (particularly Junio and the PLC) view the Git 3.0 plan as flexible or see Chacon’s proposal as a viable alternative. For now, the series remains in the design-discussion phase, with no decisions or merge status recorded.

This thread is a high-stakes design discussion about how Git should handle cryptographic signatures in a post-SHA-1 world, with the debate now spilling into broader questions about project governance and the Git 3.0 roadmap. Scott Chacon proposed a new signing mechanism that embeds SHA-256 digests of tree contents (including submodules) in signed commits and tags, arguing this provides a migration path away from SHA-1 for signatures without the disruptive ecosystem-wide switch to SHA-256 as the default object format planned for Git 3.0 in March 2027. The proposal has become a proxy war over that plan, with Chacon framing it as a GitHub-driven effort lacking broad community buy-in and offering his tree-digest approach as a less disruptive alternative.

Key participants are deeply divided. Brian M. Carlson, who has been the public face of the SHA-256 transition, forcefully rejects Chacon’s framing in the latest email, emphasizing that his own contributions have been personal (not corporate) and that the transition addresses real institutional demand from government agencies and large corporations. He insists the Git 3.0 timeline is non-negotiable and that the tree-digest proposal fails to address the core problem of SHA-1’s cryptographic weaknesses. Patrick Steinhardt has aligned with Carlson’s timeline but focuses on ecosystem momentum, warning that abandoning the transition would ossify the ecosystem and make future breaking changes exponentially harder. Junio C Hamano has engaged only with the technical design of the digest algorithm, praising some aspects but raising questions about whether it should reflect file modes or tree structure. Scott Chacon remains the sole vocal advocate for delaying the Git 3.0 switch, arguing the costs outweigh the benefits and that the tree-digest mechanism could satisfy regulatory requirements without ecosystem disruption.

The technical proposal itself is well-developed: it adds a `--hash=sha256` option to `git commit -S` and `git tag -s`, a `gpg.treeHash=sha256` config key, and embeds the digest as an extra header in signed objects. The implementation handles submodules recursively, detects cycles, and includes comprehensive test coverage. However, the thread has largely shifted away from these details to the strategic question of whether the Git 3.0 plan should proceed as scheduled. The debate now centers on whether the transition’s benefits (forcing ecosystem adoption) justify its risks (untested interoperability, workflow breakage), and whether the effort reflects genuine community consensus or the priorities of a single corporate contributor. Junio’s eventual response will likely determine whether the project reaffirms the Git 3.0 timeline or reconsiders its approach.

This thread began as an RFC from Scott Chacon proposing a new signing mechanism that embeds SHA-256 digests of tree contents in signed commits and tags, aiming to provide a migration path away from SHA-1 for signatures without requiring a disruptive switch to SHA-256 as Git’s default object format. The discussion has since broadened into a strategic debate about the Git 3.0 plan to make SHA-256 the default in March 2027, with three main positions now in play: Carlson and Steinhardt argue the switch is non-negotiable for regulatory compliance and ecosystem momentum; Chacon advocates abandoning the plan in favor of his tree-digest proposal; and Schindelin proposes supporting SHA-256 without enforcing it as the default, allowing opt-in adoption.

The thread has pivoted toward concrete logistics, particularly the state of the interoperability work needed to rewrite repositories between hash algorithms during clone and fetch. Carlson’s latest update confirms that Christian Couder’s offer to upstream early patches from the `sha256-interop-part-2` branch would unblock critical progress, specifically pack index v3 and object map support—foundational steps for parallelizing the remaining work. This marks the first tangible progress toward addressing the upstreaming bottleneck, though the full interoperability series remains large (212 patches) and would require roughly four release cycles to upstream, with an additional two cycles for an in-place migration helper. Junio has proposed a governance experiment to temporarily prioritize this work above all other changes, but practical barriers—such as the lack of corporate-funded time for foundational work and technical debt from competing priorities—remain significant.

Key technical details of Chacon’s proposal include a new `tree-sha256` header in signed commits/tags, computed from a sorted list of `<sha256(content)> SP <path> NUL` records (including submodules recursively), and configurable via `--hash=sha256` or `gpg.treeHash=sha256`. The implementation is unoptimized but functional, with open questions about file mode distinctions, submodule handling, and performance. Meanwhile, Haugsbakk’s critique has highlighted the inadequacy of Git’s current tooling and documentation for the SHA-256 transition, describing roadblocks with `git fast-export`/`fast-import` and the lack of a supported migration path for notes and submodules. The thread now grapples with whether the Git 3.0 plan should proceed as scheduled, be delayed, or abandoned, and how to address the institutional challenges of completing foundational work in an open-source project. No decisions have been made, and Junio has not yet weighed in on the strategic debate.

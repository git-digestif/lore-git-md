This thread is a high-stakes debate about Git’s future cryptographic security and the planned transition to SHA-256 as the default object format in Git 3.0 (March 2027). Scott Chacon kicked off the discussion with an RFC proposing a new signing mechanism that embeds SHA-256 digests of tree contents—including submodules—in signed commits and tags. His goal is twofold: provide a near-term solution for secure signatures without disrupting the ecosystem, and challenge the Git 3.0 plan’s necessity. The proposal computes a SHA-256 digest over a sorted list of file and submodule records, embedding it in signed objects via a new `--hash=sha256` option or `gpg.treeHash=sha256` config key. Junio Hamano raised technical questions about the digest algorithm (e.g., whether it should distinguish file modes or reflect tree structure), but the thread has since pivoted to a broader strategic fight over whether Git 3.0’s SHA-256 transition should proceed at all.

The core dispute pits Chacon’s argument—that SHA-1’s content-addressing role doesn’t require collision resistance and the tree-digest approach satisfies regulatory mandates—against Brian M. Carlson’s insistence that the Git 3.0 timeline is non-negotiable and the tree-digest mechanism fails to address SHA-1’s cryptographic weaknesses. Patrick Steinhardt’s recent reply shifts the focus to ecosystem dynamics, warning that abandoning the Git 3.0 plan would "ossify" progress. He argues the project’s decade-long effort to force a transition has finally spurred major forges (GitHub, GitLab) to act, and reversing course now would make future breaking changes nearly impossible. While Steinhardt acknowledges the practical risks Chacon highlights (untested interoperability, workflow breakage), he treats them as unavoidable growing pains rather than reasons to delay. Junio has yet to weigh in on the strategic question, leaving the thread’s outcome uncertain. The technical implementation—including new files like `tree-sha256.c`, CLI options, and config keys—remains under review, but the real battle is over whether Git 3.0’s disruptive transition is worth the cost.

This thread is about a performance optimization for Git's commit-graph subsystem when `fetch.writeCommitGraph` is enabled. Kristofer Karlsson proposed a two-patch series (now at v3) to make `git fetch` write the commit-graph incrementally, avoiding the current full scan of all reachable refs after every fetch. The optimization targets large repositories where the full scan can be slow.

The core idea is to introduce a three-mode write strategy: incremental writes from updated refs when possible, full scans when no existing graph exists or when fetching from multiple remotes, and skipping writes entirely for no-op fetches. The implementation touches `builtin/fetch.c` and the commit-graph subsystem, adding an `oidset` to track updated refs and exposing a few internal APIs for the fetch command. Performance gains are significant—Kristofer reports a reduction from ~357ms to ~9.3ms for a single ref update in a synthetic benchmark.

Patrick Steinhardt provided a thorough technical review of the initial version, raising questions about additive seeds, split-mode behavior, ref status filtering, and shallow ref handling. Kristofer addressed all of these in v2, and v3 incorporates only surface-level improvements like commit message clarity, test script style, and a new test helper (`test-tool read-graph commit-info`) to verify commit presence in the graph. The series is now uncontested, with no open technical questions, and appears ready for final review. No merge status has been reported yet, so it remains under review.

This thread is about a two-patch series from Kristofer Karlsson that optimizes Git’s `fetch.writeCommitGraph` feature for large repositories. Currently, Git rebuilds the commit-graph from all reachable refs after every fetch, which is inefficient. The series introduces an incremental write strategy that, when possible, updates the graph using only the newly fetched commits instead of rescanning all refs. It falls back to a full scan only when necessary—for example, when no existing graph exists or when fetching from multiple remotes.

The patches touch the commit-graph subsystem, adding a new enum to control the write strategy, an `oidset` to track updated refs during fetch, and new test coverage. The series is under review, with no prior discussion or open questions. Patrick Steinhardt’s recent review of the second patch raises substantive technical points: he asks whether the new seeds passed to `write_commit_graph()` are additive or exclusive, how the optimization behaves in non-split mode, and why the code uses the pre-fetch ref value (`old_oid`) instead of the post-fetch one (`new_oid`). He also notes the absence of performance benchmarks and questions whether the ref status filtering could be stricter. The review is thorough but does not yet include explicit testing confirmation. The series remains open for further feedback.

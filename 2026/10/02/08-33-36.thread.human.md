This thread is about a patch series that optimizes Git's commit-graph writing strategy during fetches for large repositories. The series, now at version 3, introduces an incremental approach to avoid rebuilding the commit-graph from all reachable refs after every fetch, which is particularly inefficient in repos with many refs. Instead, it writes only newly fetched commits when possible, falling back to full scans only when necessary (e.g., no existing graph or multi-remote fetches).

The series has effectively been approved from a technical standpoint. All substantive feedback from Patrick Steinhardt—covering edge cases like additive seeds, split-mode behavior, ref status filtering, and shallow ref handling—was addressed in earlier versions. Version 3 incorporated only surface-level improvements, such as cleaner commit messages, simplified test scripts, and the addition of a test helper (`test-tool read-graph commit-info`) to verify commit presence and generation numbers in the commit-graph. Patrick’s final review signaled the series is ready for integration, and Kristofer Karlsson’s latest reply closes the loop on the last minor feedback about commit message verbosity, deferring further changes unless another reroll is needed.

The patches touch the commit-graph subsystem, introducing new APIs and an enum to control the write strategy, along with test coverage to ensure correctness. Performance gains are significant: in a synthetic test with 200K packed refs, incremental writes reduced fetch time from ~357ms to ~9.3ms for a single ref update, while no-op fetches are now skipped entirely. The series is uncontested and awaits Junio’s integration into the appropriate branch.

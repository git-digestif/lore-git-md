# Thread deltas

## 2026/10/02

- [2026/10/02/08-18-42 by Scott Chacon <scott@gitbutler.net>] Scott Chacon posted RFC PATCH 0/4 proposing to sign a SHA-256 digest of tree contents in commits and tags (a `tree-sha256` header) as a possibly more feasible alternative to making SHA-256 the default object format in Git 3.0.
- [2026/10/02/08-18-43 by Scott Chacon <scott@gitbutler.net>] PATCH 1/4 adds the core `tree-sha256` digest: one `<sha256 of content> SP <path> NUL` record per file sorted by path, submodules hashed recursively from their pinned commits, failing if a submodule is unavailable.
- [2026/10/02/08-18-44 by Scott Chacon <scott@gitbutler.net>] PATCH 2/4 adds `--hash=sha256` to `git tag -s`/`-u`, placing the `tree-sha256` header after `tagger` in the signed payload; `--hash=sha256` without signing is an error.
- [2026/10/02/08-18-45 by Scott Chacon <scott@gitbutler.net>] PATCH 3/4 adds `--hash=sha256` to `git commit -S`, placing the header after `committer` before `gpgsig`; amending recomputes the header or drops it when the amended commit is unsigned.
- [2026/10/02/08-18-46 by Scott Chacon <scott@gitbutler.net>] PATCH 4/4 adds the `gpg.treeHash` config so signed commits and tags include the `tree-sha256` header by default, with `--hash=none` as override and no effect on unsigned objects.
- [2026/10/02/15-45-53 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano questioned whether an executable file, a non-executable file, and a symlink with the same content should hash identically given that file mode is excluded; he was "somewhat torn but moderately against" sorting records by path, arguing a corrupt unsorted tree should hash differently from a valid one; and he suggested hashing blob contents via a streaming interface rather than reading each whole blob into memory.
- [2026/10/02/15-49-18 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano praised patch 2's reorganization that removed the hardcoded double LF after `tagger`, which had made adding an optional header a hindrance.
- [2026/10/02/15-52-48 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano stated his implementation comments are conditional and that he has not yet formed an opinion on the overall direction of the series.
- [2026/10/02/19-06-08 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson rejected the proposal, arguing Git requires collision resistance and must move to SHA-256 (citing SHA-1 deprecation by governments and other ecosystems), that the Git 3.0 SHA-256 plan is too far along to change now, and that the real need is interoperability work to rewrite repositories between hash algorithms during clone/fetch, which he said has not yet been sent upstream but is intended to be sent by another company.

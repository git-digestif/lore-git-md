# Thread deltas

## 2026/10/02

- [2026/10/02/08-18-42 by Scott Chacon <scott@gitbutler.net>] Scott Chacon posted RFC PATCH 0/4 proposing to sign a SHA-256 digest of tree contents in commits and tags (a `tree-sha256` header) as a possibly more feasible alternative to making SHA-256 the default object format in Git 3.0.
- [2026/10/02/08-18-43 by Scott Chacon <scott@gitbutler.net>] PATCH 1/4 adds the core `tree-sha256` digest: one `<sha256 of content> SP <path> NUL` record per file sorted by path, submodules hashed recursively from their pinned commits, failing if a submodule is unavailable.
- [2026/10/02/08-18-44 by Scott Chacon <scott@gitbutler.net>] PATCH 2/4 adds `--hash=sha256` to `git tag -s`/`-u`, placing the `tree-sha256` header after `tagger` in the signed payload; `--hash=sha256` without signing is an error.
- [2026/10/02/08-18-45 by Scott Chacon <scott@gitbutler.net>] PATCH 3/4 adds `--hash=sha256` to `git commit -S`, placing the header after `committer` before `gpgsig`; amending recomputes the header or drops it when the amended commit is unsigned.
- [2026/10/02/08-18-46 by Scott Chacon <scott@gitbutler.net>] PATCH 4/4 adds the `gpg.treeHash` config so signed commits and tags include the `tree-sha256` header by default, with `--hash=none` as override and no effect on unsigned objects.
- [2026/10/02/15-45-53 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano questioned whether an executable file, a non-executable file, and a symlink with the same content should hash identically given that file mode is excluded; he was "somewhat torn but moderately against" sorting records by path, arguing a corrupt unsorted tree should hash differently from a valid one; and he suggested hashing blob contents via a streaming interface rather than reading each whole blob into memory.
- [2026/10/02/15-49-18 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano praised patch 2's reorganization that removed the hardcoded double LF after `tagger`, which had made adding an optional header a hindrance.
- [2026/10/02/15-52-48 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano stated his implementation comments are conditional and that he has not yet formed an opinion on the overall direction of the series.
- [2026/10/02/19-06-08 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson rejected the proposal, arguing Git requires collision resistance and must move to SHA-256 (citing SHA-1 deprecation by governments and other ecosystems), that the Git 3.0 SHA-256 plan is too far along to change now, and that the real need is interoperability work to rewrite repositories between hash algorithms during clone/fetch, which he said has not yet been sent upstream but is intended to be sent by another company.

## 2026/10/05

- [2026/10/05/09-32-54 by Scott Chacon <schacon@gmail.com>] Scott Chacon argued that his tree-sha256 proposal was not meant to address SHA-1 collision resistance for storing colliding blobs, which he considers a niche problem, and that SHA-1 remains adequate as the one-way content-addressing hash for Git's Merkle DAG — the real issue being only its use for signature integrity, which his series addresses by signing with SHA-256 instead.
- [2026/10/05/09-32-54 by Scott Chacon <schacon@gmail.com>] Scott Chacon contended that government and business SHA-1 bans target cryptographic protection/signatures rather than "any purpose", so re-separating content-addressing hashes from signature hashes via this series could satisfy NIST-style mandates without changing the default object format.
- [2026/10/05/09-32-54 by Scott Chacon <schacon@gmail.com>] Scott Chacon argued the SHA-256 default transition is not ready: interop is currently unusable, pack index v3 and other compat pieces are not fully implemented in core or downstream tools, and major forges lack practical support (no GitHub access, no Bitbucket or Gerrit support, GitLab only "experimental"), leaving no time for real-world testing before a March 3.0 cutover.
- [2026/10/05/09-32-54 by Scott Chacon <schacon@gmail.com>] Scott Chacon warned that a hard "flag day" default switch would surprise many users and break custom scripts with hardcoded 40-hex object-ID assumptions, and urged shipping Git 3.0 without the SHA-256 default, keeping it opt-in until 4.0.
- [2026/10/05/12-41-13 by Patrick Steinhardt <ps@pks.im>] Patrick Steinhardt countered that the ecosystem only began moving on SHA-256 once the mandatory 3.0 change was announced, and that dropping the breaking change now would cause the ecosystem to stop working on it again and make future breaking changes harder, after nearly a decade of transition work.
- [2026/10/05/14-16-48 by Scott Chacon <schacon@gmail.com>] Scott Chacon asked whether the lack of prior ecosystem action might be because nobody really finds SHA-1 a concerning problem, and claimed GitHub has been essentially the only organization pushing the SHA-256 effort, with Patrick Steinhardt the only major non-GitHub/Microsoft contributor.
- [2026/10/05/22-57-29 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson replied that this is an oversimplification: people don't realize Git uses SHA-1 and will favor SHA-256 once it is default, the need to move away will become gradually urgent for large institutions, and he has had inquiries from large government agencies and corporations wanting SHA-256; he also noted open-source investment is driven by internal corporate needs, so scaling issues get attention while SHA-256 does not.
- [2026/10/05/22-57-29 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson declined to respond to the corporate-attribution claim from his personal address, clarified that his SHA-256 work was done almost exclusively in a personal capacity on nights and weekends rather than on company time, and noted he received substantial assistance, reviews, and ideas from a wide variety of contributors.

## 2026/10/06

- [2026/10/06/09-00-45 by Christian Couder <christian.couder@gmail.com>] Christian Couder asked brian m. carlson a series of questions about the SHA-256 interoperability work: whether its current state is publicly available, whether submodule support is the only missing part, how large the series is, how long full-time upstreaming would take, how others could best help, which company offered to help and whether it would work openly, and what automated/realistic testing exists.
- [2026/10/06/13-36-23 by Johannes Schindelin <Johannes.Schindelin@gmx.de>] Johannes Schindelin argued that the ecosystem's reluctance to move to SHA-256 stems less from urgency (SHAttered-style collisions cost ~$10k and a month of RTX 3090s and are hard to apply to Git objects) and more from the ginormous migration effort, listing unresolved issues: required local SHA-1↔SHA-256 mappings, submodules fetching from third parties, partial/shallow clones, inability to distinguish short SHA-1 from short SHA-256 OIDs, and tooling hard-coding 40 hex digits; he also argued the "SHA-1 is cryptographically weak" rationale rarely matters in practice, agreed only the v3.0 default-switch threat moved industry players, and proposed keeping the option open to ship excellent SHA-256 support in v3.0 without forcing it as the default, switching the default only to solve a problem users actually recognize.
- [2026/10/06/16-16-07 by Kristoffer Haugsbakk <kristofferhaugsbakk@fastmail.com>] Kristoffer Haugsbakk reported that git(1) itself does not seem ready for SHA-256 migration: his fast-export/fast-import attempt on git.git lost refs pointing to blobs/trees and Git notes (which retain SHA-1 filenames) and failed on the SHA-1 collision submodule, and there is no mapping-preserving in-place migration tooling, leaving average users nothing to do but wait for Git 3.0.
- [2026/10/06/21-55-54 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson replied that fast-export/fast-import do support rewriting submodules and provided a working script (using --rewrite-submodules-from/--rewrite-submodules-to after converting the sha1collisiondetection submodule) that successfully converted git.git to SHA-256, while noting it is slower, has poor UX, and differs from the true interoperability code but has been available since ~2.30; he also stated the interoperability work does not rewrite notes (it only runs on clone/fetch), in-place rewriting is not yet implemented, and the work has not gone upstream because the pluggable ODB work broke many things and he is burnt out.
- [2026/10/06/22-26-40 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson answered Christian Couder's questions: the work is public at https://github.com/bk2204/git.git as `sha256-interop` (~212 patches), with limitations documented in a lore link and Documentation/gitformat-hash.adoc; missing pieces include in-place migration tooling, multi-pack index support, iterative delta resolution (currently recursive, allowing stack exhaustion), and batched/transactional writing of loose objects with object maps; a partial rebase exists in `sha256-interop-part-2`; he estimated four ~6-week release cycles to upstream it plus two more for an in-place migration helper, asked volunteers to rebase and polish early patches, declined to name the interested company without permission, and described his testing (clone --object-format=sha256:sha1 of a personal repo plus t1017 tests).
- [2026/10/06/22-38-37 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano posed a hypothetical: whether corporate-funded time plus a temporary arrangement giving SHA-256 interoperability workers veto power over interfering topics for N months would have worked better, noting it would require buy-in from other stakeholders.
- [2026/10/06/23-40-52 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson agreed that arrangement might have helped, explained that his $DAYJOB forces Outlook (which corrupts patches) and he does not want to send work patches from his personal address, suggested someone else could polish and upstream patches while he works on next steps, noted that reviews are needed for timely merging, and agreed with Junio that such an arrangement requires stakeholder buy-in.

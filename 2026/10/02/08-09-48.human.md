This is the core API patch in Patrick Steinhardt’s v2 series introducing subcommand grouping to Git’s parse-options subsystem. It extends `OPT_SUBCOMMAND_F()` to accept an optional help string, allowing subcommands to be grouped under `OPT_GROUP()` headings in the usage output. The change is clean and well-motivated: it eliminates the need for a separate `OPT_SUBCOMMAND_H()` variant, simplifies the API, and enables the logical grouping of `git refs` subcommands (shown in patch 4/4).

The patch touches seven files, but the core logic is in `parse-options.c` and `parse-options.h`. The key internal change is in `usage_print_option()`, which now checks for a non-NULL `help` field to decide whether a subcommand should be displayed under a group heading. The API is backward-compatible: existing `OPT_SUBCOMMAND` calls (which pass NULL for the help string) continue to work as before, omitting the subcommand from the usage output. The test in `t/t0040-parse-options.sh` confirms that subcommands with help text appear under their group heading, while those without remain hidden.

This is a refactoring patch with no user-visible behavior change yet — the actual grouping of `git refs` is implemented in the next patch. The changes to `builtin/remote.c` and `builtin/stash.c` are mechanical updates to the new `OPT_SUBCOMMAND_F()` signature, passing NULL for the help string to preserve existing behavior. The documentation in `api-parse-options.adoc` is updated to clarify that groups apply to both options and subcommands with help text.

The patch is responsive to Junio’s feedback from v1, which requested reducing nesting in `usage_with_options_internal()` (handled in patch 2/4) and improving API consistency. By extending `OPT_SUBCOMMAND_F()` to accept help text directly, this patch achieves both goals: it removes the need for a separate `OPT_SUBCOMMAND_H()` macro and makes the interface more uniform. The implementation is straightforward and the test coverage is adequate.

This looks like a solid, uncontroversial change that addresses a real usability pain point. The series is under active review, with Junio’s feedback already incorporated, and this patch is the linchpin for the `git refs` grouping in the next patch. No substantive concerns are evident, and the patch is likely to be merged once the series receives further review.

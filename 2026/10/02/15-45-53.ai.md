This is a substantive review reply from Junio C Hamano to the first patch in Scott Chacon’s RFC series introducing SHA-256-based tree hashing for signed Git objects. The review raises two technical design questions that could significantly affect the behavior and robustness of the proposed mechanism.

Junio’s first question asks whether the digest should distinguish between a blob stored as an executable file, the same blob stored as a non-executable file, and a symbolic link pointing to the same content. The current implementation ignores file modes and symlink targets, treating all three cases identically. Junio does not state a preference but implies that the answer could affect security and correctness: if the digest is meant to capture the *content* of the tree, ignoring modes and symlinks might be acceptable; if it is meant to capture the *state* of the tree (including permissions and symlink structure), then the current approach may be insufficient.

The second question challenges the decision to sort tree entries before hashing. Junio points out that if two trees would produce the same checkout but one is internally corrupt (e.g., its entries are not sorted), the current implementation would hash them to the same value, masking the corruption. He suggests that the digest should instead reflect the *internal structure* of the tree object, not just the logical checkout, so that corruption is detectable. This is a fundamental design choice: whether the digest is a content-addressable summary (invariant under reordering) or a structural fingerprint (sensitive to internal representation).

Junio also notes a performance concern: the current implementation reads entire blobs into memory before hashing them, which could be problematic for large files. He suggests using Git’s streaming object interface (like `archive-tar.c` and `archive-zip.c` do) to hash blobs incrementally, reducing memory pressure.

The review is substantive: it engages with the core design of the digest algorithm, not just its implementation. No objections are raised to the overall goal, but the questions suggest that the current approach may need rethinking before the series can proceed. The thread is still in the RFC phase; no decisions or merge status are recorded.

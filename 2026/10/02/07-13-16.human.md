This is the second patch in Harald Nordgren’s four-patch v5 series implementing a "matching-inspired" fetch mode for shallow repositories. It teaches `git fetch` to infer which branches to fetch when the remote has a `remote.<name>.refmap` configured but no `remote.<name>.fetch` refspec: instead of failing or fetching every branch, it fetches only the branches that local branches already track on that remote.

The patch updates `builtin/fetch.c` to add a new code path in `get_ref_map()` that calls the helper `branches_tracking_remote()` (added in `remote.c`) to enumerate every local branch whose `@{upstream}` points to the remote. These branches’ upstream refspecs are collected into a temporary refspec, which is then used to drive the fetch. The same logic is mirrored in `do_fetch()` to restrict the `ls-refs` command’s ref prefixes, ensuring the transport layer only negotiates history for the branches we actually want.

Documentation in `config/remote.adoc` and `fetch-options.adoc` is updated to explain the new behavior: when a refmap is active but no explicit refspec is given, Git now infers what to fetch from local tracking branches. The new test file `t/t5586-fetch-refmap.sh` (renumbered from `t/t5585` in v5) exercises the feature with edge cases: empty fetches, duplicate branches, branches tracking other remotes, and compatibility with `git remote show`.

This is a well-crafted, thoroughly tested patch that addresses a real performance issue in shallow repositories. It preserves backward compatibility, avoids inventing new refspec syntax, and resolves the last substantive objection from Junio by removing the forced inclusion of the remote’s default branch. The only minor quibble left is that a bare `git fetch` against a refmap-only remote with no tracking branches fetches nothing, but the author acknowledges this as a non-blocker. The patch is ready for integration.

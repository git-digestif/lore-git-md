This is a feature proposal follow-up from Junio C Hamano, the Git maintainer, responding to Artem S. Tashkinov’s RFC for `git restore-mtimes`. Junio engages directly with two of the open technical questions: how to handle file concatenation (a case where no new content is introduced but the file’s identity changes) and how to define historical timestamps in a way that aligns with Git’s linearized view of history.

Junio suggests a concrete algorithm for computing historical mtimes: walk the first-parent history in reverse chronological order, checking out each commit in sequence, and assign each file the committer timestamp of the commit where it was last modified. This approach would handle renames and merges naturally by treating them as part of the linearized history, and it avoids the complexity of tracking content changes across non-linear history. He also endorses the idea of teaching `git archive` to use these synthesized timestamps, which would address one of the use cases Artem highlighted (preserving mtimes in source archives).

The response is substantive but not a full review; Junio does not comment on whether the feature belongs in core Git, nor does he address performance or interface design. His focus is on clarifying the semantics of the proposed feature, particularly around edge cases like file concatenation and merge history. This suggests the proposal is being taken seriously, but the discussion is still in the early stages of refining the technical approach. No objections or alternative proposals are raised; the tone is constructive and exploratory.

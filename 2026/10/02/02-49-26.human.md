This is a user-contributed follow-up in the ongoing discussion about a `contrib/` helper for incremental rebase conflict resolution. Simon Richter shares his own Git alias (`slowrebase`) that implements a similar workflow to Alejandro Colomar’s `git-rebase-walk`, but notes two limitations: it struggles with merge commits and is slow for large histories. He proposes a more sophisticated approach — a `rebase-bisect` (or `bisect-rebase`) command that would use a bisection-like strategy to find the *first* upstream commit that conflicts with the local branch, optionally using a test command (e.g., `make check`) to detect semantic conflicts.

The proposal is conceptual rather than a patch: Simon outlines the desired behavior (bisecting to find the first conflicting commit, with optional semantic testing) and sketches a workflow, but does not provide an implementation. His idea aligns closely with Nico Williams’ later `bisect-rebase.sh` and Colomar’s `git-bisect-rebase`, both of which use a bisection strategy to reduce the number of conflict resolutions. Simon’s suggestion predates both scripts and appears to have directly inspired them, particularly the emphasis on performance and semantic conflict detection.

The email is substantive: it identifies real pain points (merge commits, performance) and proposes an algorithmic improvement (bisection) that later became the basis for the leading candidate script. However, it does not engage with the broader question of whether Git should include *any* such helper, nor does it compare the proposed approach to existing tools like `git-imerge`. The tone is constructive and focused on workflow improvement, making it a useful data point in the thread’s evolution toward a more performant and robust solution.

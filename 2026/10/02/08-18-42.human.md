This is an RFC proposal for a new signing mechanism that embeds a SHA-256 digest of the entire tree contents in signed commits and tags. The author, Scott Chacon, frames it as a potential alternative to switching the default hash function to SHA-256 in Git 3.0, arguing it could offer similar security benefits without the ecosystem disruption of changing the default object format.

The series adds a new `--hash=sha256` option to `git tag -s` and `git commit -S`, which computes a SHA-256 hash over every file in the tree (including submodules) and inserts it as a `tree-sha256` header before signing. The digest covers file contents and paths, but not modes, and submodules are recursively hashed. A `gpg.treeHash=sha256` config setting makes this the default for all signed objects. The implementation is careful to maintain backward compatibility: older Git versions will ignore the new header and verify signatures as before.

Four patches implement the feature: the core hashing logic (with a test-tool helper), CLI options for `git tag` and `git commit`, and the config setting. The commit message notes performance trade-offs (5 seconds for the Linux tree on a default build) and suggests parallel hashing could dramatically improve this. The author explicitly seeks feedback on three open questions: whether this approach is viable, how verification should work, and how to handle large submodules that aren’t checked out.

This is a well-structured RFC with clear motivation, thorough implementation, and test coverage. The backward-compatibility story is strong, and the author acknowledges performance concerns upfront. The proposal directly engages with the Git 3.0 hash transition debate, offering a middle-ground solution that could sidestep some of the ecosystem challenges of a full SHA-256 default. Whether it gains traction will likely depend on how the community weighs the trade-offs between security guarantees and implementation complexity.

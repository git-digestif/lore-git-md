This is the fourth patch in Christian Couder’s five-part series introducing `uploadpack.lazyFetchTrusted`, a server-side mechanism to mark repositories as trusted for lazy fetching. This specific patch prevents infinite recursion when a repository and its promisor remote are configured to lazy-fetch from each other.

The problem is straightforward: if repository R is configured to lazy-fetch from promisor remote P, and P is also configured to lazy-fetch from R, a request for a missing object triggers an infinite loop. In practice, the recursion fails only when the environment variable list grows too long, producing a cryptic error. The fix introduces a new internal environment variable, `GIT_INTERNAL_LAZY_FETCH_DEPTH`, that tracks recursion depth and aborts if it exceeds a limit (currently set to 5). The limit is chosen to allow legitimate nesting (e.g., `git fetch` spawning `index-pack` to fetch REF_DELTA bases) while preventing runaway recursion.

The patch touches `promisor-remote.c` (adding depth tracking to `fetch_objects()` and `try_promisor_remotes()`), `environment.h` (defining the new environment variable), and adds a new test in `t/t0410-partial-clone.sh` that verifies the recursion safeguard works. The test sets up two partial clones that point to each other as promisor remotes, confirms lazy fetching fails with the expected warning, and checks that exactly five fetch subprocesses were spawned (matching the depth limit).

This is a well-motivated bugfix with clear test coverage. The recursion safeguard is a necessary defense-in-depth measure for the server-side trust model introduced in the series. Junio’s earlier feedback on this patch (a minor type nit about using `int` instead of `unsigned long`) is resolved, and the patch is rebased on Git 2.56. No substantive concerns remain. If the series as a whole lands, this patch is a safe and uncontroversial inclusion.

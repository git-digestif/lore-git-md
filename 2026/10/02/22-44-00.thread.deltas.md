# Thread deltas

## 2026/10/02

- [2026/10/02/22-44-00 by Jeff King <peff@peff.net>] Jeff King proposed a "limbo" object-format state for empty repositories, in which the server advertises that it has no object format yet and adopts the client's hash algorithm (sha1 or sha256) upon receiving the first push, to prevent first-push failures when a forge's default hash does not match the client's; he noted the idea is not yet implemented and may have unresolved server-side details such as atomically handling simultaneous mismatched pushes.

## 2026/10/03

- [2026/10/03/01-07-48 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson agreed the adaptive empty-repo idea would be nice, but argued that advertising `object-format=limbo` is incompatible with every existing implementation, since no client from 2.29 on would accept `limbo` as a valid hash algorithm; he noted multiple `object-format` directives would be the best advertisement if older versions support them (though he recalled a past crasher bug), and raised policy questions about letting organizations disallow one algorithm and about expressing a "versatile mode" that is safe to rewrite into the config on initial write (which need not be a push — it could be a commit or add), concluding it is not impossible but not easy.
- [2026/10/03/01-25-12 by Jeff King <peff@peff.net>] Jeff King agreed the limbo approach breaks older object-format-aware clients worse than a mismatched format does, and proposed a new capability (tentatively "magic-limbo") that older versions would ignore, combined with a valid `object-format=` value — suggesting "magic-limbo" plus "object-format=sha1" as the sensible advertisement, on the reasoning that if sha256-by-default is not switched until magic-limbo exists, anyone with a local sha256 repo chose it intentionally and can configure the server to match; he rejected emitting multiple object-format directives as introducing weird corner cases, and said the policy/forge-UI parts (a tri-state sha1/sha256/limbo selector) seem outside Git's protocol scope, with the Git-side mechanism (config or a git-init command-line option) TBD.
- [2026/10/03/01-31-48 by Junio C Hamano <gitster@pobox.com>] Junio C Hamano remarked that advertising multiple accepted hash algorithms via multiple capability lines would have been the obviously right thing conceptually, and "oh, bad" that it does not work.
- [2026/10/03/14-22-32 by brian m. carlson <sandals@crustytoothpaste.net>] brian m. carlson countered that the other object format must also be declared (e.g., `alt-object-format=sha256`, or `object-format=sha256` plus `alt-object-format=sha1`) so the server's specific SHA-256 support is known and a future third hash algorithm cannot make SHA-256 unacceptable, while insisting multiple options must be accepted; he opposed delaying SHA-256-by-default for this feature since neither he nor Jeff King intends to implement it imminently and Git 3.0's SHA-256 default (announced in 2024) should not be held up; he corrected the earlier bug recollection — it was an infinite loop, not a crasher, fixed by aa962fef27 in 2.41 before SHA-256 stabilized in 2.44, so multiple directives could work if versions with only experimental SHA-256 support are abandoned; and he disagreed that the policy mechanism is outside Git's scope, preferring config over a command-line option because non-push writes (e.g., a forge API) also need a hash algorithm specified.

This is a user-contributed review and alternative proposal in the ongoing thread about incremental rebase conflict resolution helpers for Git's `contrib/` area.

Simon Richter shares his own Git alias (`slowrebase`) that implements a similar workflow to Alejandro Colomar’s `git-rebase-walk`: it rebases HEAD onto each upstream commit in sequence, stopping at the first conflict. He notes two limitations: it struggles with merge commits, and it is slow because it processes every upstream commit regardless of whether it touches the same files as the feature branch. To address these, he proposes a new command—tentatively named `rebase-bisect` or `bisect-rebase`—that would use a bisection-like strategy to find the *first* upstream commit that conflicts with the feature branch, optionally running a test command (e.g., `make check`) to detect semantic conflicts. The envisioned interface (`git bisect rebase main -x 'make check'`) would attempt to rebase onto a midpoint commit (e.g., D in the example), then narrow the search based on whether the rebase succeeds and the test passes, with an option to prioritize trivial resolutions.

The review is substantive: it identifies concrete pain points (merge commits, performance) and proposes an alternative algorithmic approach (bisection) with a clear interface and workflow. It does not engage with the existing candidate scripts (`git-rebase-walk`, `git-bisect-rebase`, or Nico Williams’ `bisect-rebase.sh`) but instead introduces a new design direction that aligns with the bisection-based scripts already under discussion. The proposal is well-motivated and technically grounded, though it remains conceptual—no implementation is provided. The naming suggestion (`bisect-rebase`) reinforces the thread’s convergence on that name for the bisection-based candidate.

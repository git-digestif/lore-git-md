This is a substantive review from Junio C Hamano on the `git restore-mtimes` RFC. Junio engages directly with the technical design, proposing a concrete algorithm for computing historical mtimes and raising an edge case (file concatenation) that the original proposal did not address. He suggests using `--first-parent --reverse` to walk the mainline history, then applying each commit’s committer timestamp to the files it modifies, which would produce deterministic, linearized mtimes. This approach avoids the complexity of following renames across non-linear history but may not match the author’s intent for repositories with frequent merges or criss-cross renames.

Junio also endorses the idea of integrating historical mtimes into `git archive`, calling it "interesting" — a rare positive signal from him at the RFC stage. The file-concatenation scenario (e.g., `cat a b > c`) is a subtle but important edge case: under the proposed algorithm, the new file `c` would inherit the committer timestamp of the concatenation commit, even though its content is not truly "new" to the repository. This could lead to mtimes that feel counterintuitive for some use cases.

The review advances the thread by providing a clear, implementable baseline for discussion and surfacing a non-obvious correctness issue. It does not address the author’s other open questions (e.g., author vs. committer timestamps, merge semantics, or interface design), leaving those for future debate. The tone is constructive but neutral; Junio does not express a preference for whether the feature belongs in core Git or as an external tool. Likely follow-up points will include whether the `--first-parent` simplification is acceptable, how to handle file concatenation, and whether the algorithm should be exposed as a standalone command or integrated into existing workflows like `git archive`.

This is the first patch in the v5 series implementing a "matching-inspired" fetch mode for shallow repositories. It introduces the `remote.<name>.refmap` configuration variable, which provides the default value for the `--refmap` command-line option in `git fetch`.

The patch adds parsing for `remote.<name>.refmap` in `remote.c`, extends `builtin/fetch.c` to use the configured refmap as the default `--refmap` value when no explicit refmap is provided, and updates the `remote` struct to include a `refmap` field. Documentation is added to `config/remote.adoc` and `fetch-options.adoc`, and tests in `t/t5510-fetch.sh` verify that the configuration behaves identically to the `--refmap` command-line option.

The implementation is straightforward and aligns with the consensus design: `remote.<name>.refmap` defines namespace mappings (e.g., `+refs/heads/*:refs/remotes/second/*`) without specifying what to fetch, separating the concerns of ref mapping and fetch selection. The patch preserves backward compatibility by only using the configured refmap when no explicit refspecs are provided on the command line or via `remote.<name>.fetch`. The documentation wording is precise, defining `remote.<name>.refmap` as "used to map remote refs being fetched to remote-tracking refs to store," addressing Junio C Hamano’s prior review request.

No substantive objections remain for this patch. It is well-tested, with the new test covering the configuration’s behavior and edge cases (e.g., verifying that the original remote-tracking ref remains unchanged when the refmap redirects the fetched ref to a different namespace). The patch is ready for integration and is a foundational piece of the series, enabling the dynamic branch enumeration logic in Patch 2/4.

Subject: [PATCH 0/2] packfile: fix corruption from stale delta base cache entries

Thread type: bugfix patch series

Core problem or goal
Fix a packfile corruption bug caused by stale delta base cache entries that reference freed `packed_git` structs. The bug manifests as **logical corruption due to pointer reuse** when Git reuses memory addresses for new `packed_git` structs after closing packs, leading to incorrect object reconstruction if the new pack has entries at the same offsets. The issue became exposed after commit 6f1e9394e2 (2024-08-08) stopped leaking packfiles, altering memory reuse patterns. The bug is distinct from a traditional user-after-free: it does not trigger AddressSanitizer (ASan) because the corruption arises from the reuse of the pointer *value* as a cache key, not from dereferencing the freed pointer itself.

Current status
Under review. The series is a strong candidate for `next` once the thread settles. Two-patch series: (1) preparatory refactoring of `close_pack()` to avoid forward declarations (purely mechanical, no behavior change), (2) core fix evicting stale delta base cache entries when closing a pack. The core fix remains uncontested. Discussion has fully converged on **test design and bug classification**, with Peff’s latest analysis confirming the original fix’s correctness and rejecting an ASan-based alternative as semantically ambiguous and computationally expensive. The only remaining loose end—whether to document the test’s platform dependency more prominently—is unlikely to block the series.

Key technical details
- Files touched: `packfile.c` (refactoring in patch 1, core fix in patch 2), `t/t6437-submodule-merge.sh` (regression test in patch 2). No new files introduced.
- Subsystems: packfile management, delta base cache, submodule handling, test infrastructure.
- New behavior: Delta base cache entries are evicted when their owning pack is closed (patch 2).
- New functions: `delta_base_cache_evict_entry()` (patch 2) evicts cache entries for a given pack.
- Refactoring details: Patch 1 moves `close_pack()` later in `packfile.c` to ensure delta base cache declarations are in scope for patch 2; the change is purely mechanical (10 lines moved) and uncontroversial.
- On-disk format: unchanged.
- Test coverage:
  - The regression test in `t/t6437-submodule-merge.sh` verifies the fix via recursive submodule merges with 16 similarly structured submodules. It relies on the allocator to reuse memory addresses and is platform-dependent (confirmed to work on glibc and musl but not on Philippe Blain’s WSL setup). The test’s behavior varies with the test directory’s path length (fewer submodules suffice in `/tmp/` but not in deeper paths). These limitations are documented in the test script and commit message. Junio’s review confirmed that the test will not produce false positives—it either reproduces the bug or silently passes.
  - The discussion confirmed that an ASan-based test would not work for this bug because ASan prevents the pointer reuse that causes the corruption. Peff’s follow-up analysis further ruled out an ASan-based *fix*, as it would introduce semantic ambiguity (e.g., reopened packs with the same name but different contents) and trade silent corruption for undefined behavior.
- Cache key mechanism: The delta base cache uses pointer equality (`a->p == b->p`) to match entries. Peff’s proposed alternative (string comparison of pack names) was rejected for reasons noted above.

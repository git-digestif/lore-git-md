Subject: [PATCH 0/2] packfile: fix corruption from stale delta base cache entries
Series version: v1 (initial submission, discussion ongoing on test design and bug classification)
Originating author: Patrick Steinhardt
Thread type: bugfix patch series

Core problem or goal
Fix a packfile corruption bug caused by stale delta base cache entries that reference freed `packed_git` structs. The bug manifests as a **logical corruption due to pointer reuse** when Git reuses memory addresses for new `packed_git` structs after closing packs, leading to incorrect object reconstruction if the new pack has entries at the same offsets. The issue became exposed after commit 6f1e9394e2 (2024-08-08) stopped leaking packfiles, altering memory reuse patterns. While the bug involves a dangling pointer (technically a user-after-free), it does not trigger AddressSanitizer (ASan) because the corruption arises from the reuse of the pointer *value* as a cache key, not from dereferencing the freed pointer itself.

Current status
Under review. Two-patch series: (1) preparatory refactoring of `close_pack()` to avoid forward declarations, (2) core fix evicting stale delta base cache entries when closing a pack. The core fix remains uncontested. Discussion has evolved to focus on **test design and bug classification**:
- The original regression test’s platform dependency (glibc-specific memory allocation patterns) and its intentional design trade-off (simplicity over determinism) were previously acknowledged.
- Jeff King’s review reframed the bug as a **user-after-free** and proposed an ASan-based test to detect the memory violation directly. Patrick’s follow-up clarifies that ASan does not catch the issue because the bug is a **logical corruption from pointer reuse**, not a memory-safety violation detectable by ASan. ASan’s behavior (allocating unique addresses for freed memory) actually *prevents* the bug from manifesting.
- The thread is now discussing whether the current test’s limitations are acceptable or if an alternative approach (e.g., mocking allocator behavior) is needed. No new patch versions or test proposals have been posted.

Key technical details
- Files touched: `packfile.c` (refactoring in patch 1, core fix in patch 2), `t/t6437-submodule-merge.sh` (regression test in patch 2). No new files introduced.
- Subsystems: packfile management, delta base cache, submodule handling, test infrastructure.
- New behavior: Delta base cache entries are evicted when their owning pack is closed (patch 2).
- New functions: `delta_base_cache_evict_entry()` (patch 2) evicts cache entries for a given pack.
- On-disk format: unchanged.
- Test coverage:
  - The existing regression test in `t/t6437-submodule-merge.sh` (patch 2) verifies the fix via recursive submodule merges with 16 similarly structured submodules. It relies on glibc’s allocator to reuse memory addresses and is platform-dependent (did not reproduce on Philippe Blain’s WSL setup). The test’s behavior varies with the test directory’s path length (fewer submodules suffice in `/tmp/` but not in deeper paths).
  - Jeff King’s proposed ASan-based test would not work for this bug because ASan prevents the pointer reuse that causes the corruption. The discussion now centers on whether the current test’s limitations are acceptable or if a more deterministic approach (e.g., mocking allocator behavior) is needed.
- Refactoring details: Patch 1 moves `close_pack()` later in `packfile.c` to ensure delta base cache declarations are in scope for patch 2; the refactoring’s rationale (avoiding forward declarations) was explicitly confirmed by Patrick in response to Mark C. Chu-Carroll’s question.

Open questions and loose ends
1. **Test design**: The trade-off between the existing platform-dependent test and a more deterministic approach remains unresolved. The current test’s reliance on glibc’s allocator behavior is known to be non-portable, but alternatives (e.g., mocking allocator behavior) may introduce complexity. No decision has been made on whether to augment or replace the current test.
2. **Bug classification**: The thread has clarified the bug as a **logical corruption due to pointer reuse**, distinct from a traditional user-after-free detectable by ASan. This nuance has not yet been reflected in the commit messages or documentation. Updating these to explicitly note the pointer reuse mechanism could improve future maintainability.
3. **No substantive review feedback** has been posted for the core fix (patches 1 and 2), and no objections or requests for changes have been raised. The fix’s correctness remains uncontested.

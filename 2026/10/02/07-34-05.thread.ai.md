Subject: [PATCH 0/2] packfile: fix corruption from stale delta base cache entries
Series version: v1 (initial submission, now with test improvement follow-up)
Originating author: Patrick Steinhardt
Thread type: bugfix patch series

Core problem or goal
Fix a subtle packfile corruption bug caused by stale delta base cache entries. When Git reuses memory addresses for new `packed_git` structs after closing packs, the delta base cache may retain entries from the old pack, leading to incorrect object reconstruction if the new pack has entries at the same offsets. The bug is reliably reproducible via recursive submodule merges and became exposed after commit 6f1e9394e2 (2024-08-08) stopped leaking packfiles.

Current status
Under review. Two-patch series: (1) preparatory refactoring of `close_pack()` to avoid forward declarations (posted), (2) core fix evicting stale delta base cache entries when closing a pack (posted). A follow-up patch from Guillaume Chauvel proposes a deterministic, platform-independent test to replace the existing glibc-dependent regression test in `t/t6437-submodule-merge.sh`. Philippe Blain's review raised minor questions about the original test's design (why more than two submodules are merged) and noted the bug did not reproduce on his WSL setup, but did not contest the fix's correctness. Mark C. Chu-Carroll asked a surface-level clarification about the purpose of the `close_pack()` refactoring in patch 1, noting the question is procedural and does not engage with the bug or fix. No prior versions of the series; the follow-up remains a test improvement, not a new version.

Key technical details
- Files touched: `packfile.c` (refactoring in patch 1, core fix in patch 2), `t/t6437-submodule-merge.sh` (original regression test in patch 2), plus nine additional files in the follow-up (new test helper `t/helper/test-delta-base-cache.c`, enhancement to `test-pack-deltas`, new test script `t/t5336-pack-delta-base-cache.sh`, and supporting build system updates).
- Subsystems: packfile management, delta base cache, submodule handling, test infrastructure.
- New behavior: Delta base cache entries are evicted when their owning pack is closed (patch 2).
- New functions: `delta_base_cache_evict_entry()` (patch 2) evicts cache entries for a given pack; `test-delta-base-cache` helper (follow-up) forces memory reuse of `packed_git` structs for deterministic testing.
- On-disk format: unchanged.
- Test coverage: original test in `t/t6437-submodule-merge.sh` (patch 2) verifies the fix via recursive submodule merges with 16 similarly structured submodules; the follow-up replaces this with a deterministic test that creates two packs (`A-B.pack` and `B-C.pack`) where the delta base for `B` in the first pack and `C` in the second pack share the same offset, then verifies that unpacking `C` after closing the first pack does not incorrectly use `A` as the delta base. The follow-up test is portable and directly targets the bug’s root cause. Philippe Blain's review notes the original test's complexity (16 submodules) and its platform dependency (did not reproduce on WSL).
- Refactoring details: Patch 1 moves `close_pack()` later in `packfile.c` to ensure delta base cache declarations are in scope for patch 2; no functional change. The commit message explains this is preparatory for patch 2, which modifies `close_pack()` to evict stale delta base cache entries.

Open questions and loose ends
Philippe Blain's review raises two questions about the original test: (1) why merge more than two submodules when the bug was originally reproduced with two, and (2) why the test did not reproduce on WSL (suggesting platform-specific memory allocation behavior). These questions are about test design, not the fix's correctness, and are already addressed by Guillaume Chauvel's follow-up, which proposes a deterministic, platform-independent test. No substantive review has been posted yet for the follow-up, but the approach is sound and aligns with the project’s preference for deterministic tests. Mark C. Chu-Carroll's question about the purpose of the `close_pack()` refactoring in patch 1 is procedural and does not engage with the bug or fix; it is likely to be resolved with a one-line reply.

Subject: [PATCH 0/2] packfile: fix corruption from stale delta base cache entries
Series version: v1 (initial submission)
Originating author: Patrick Steinhardt
Thread type: bugfix patch series

Core problem or goal
Fix a subtle packfile corruption bug caused by stale delta base cache entries. When Git reuses memory addresses for new `packed_git` structs after closing packs, the delta base cache may retain entries from the old pack, leading to incorrect object reconstruction if the new pack has entries at the same offsets. The bug is reliably reproducible via recursive submodule merges and became exposed after commit 6f1e9394e2 (2024-08-08) stopped leaking packfiles.

Current status
Under review. Two-patch series: (1) preparatory refactoring of `close_pack()` to avoid forward declarations (posted), (2) core fix evicting stale delta base cache entries when closing a pack (now posted). No prior versions.

Key technical details
- Files touched: `packfile.c` (refactoring in patch 1, core fix in patch 2), `t/t6437-submodule-merge.sh` (new regression test in patch 2).
- Subsystems: packfile management, delta base cache, submodule handling.
- New behavior: Delta base cache entries are evicted when their owning pack is closed (patch 2).
- New function: `delta_base_cache_evict_entry()` evicts cache entries for a given pack.
- On-disk format: unchanged.
- Test coverage: new test in `t/t6437-submodule-merge.sh` (patch 2) verifies the fix via recursive submodule merges with 16 similarly structured submodules; the test is platform-dependent (relies on glibc’s allocation behavior) but the fix itself is portable.
- Refactoring details: Patch 1 moves `close_pack()` later in `packfile.c` to ensure delta base cache declarations are in scope for patch 2; no functional change.

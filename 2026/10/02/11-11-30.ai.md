This is the first patch in a three-part bugfix series targeting the `rerere` subsystem. It introduces a configurable timeout (`rerere.lockTimeout`, default 1000 ms) for acquiring the `MERGE_RR.lock` file, replacing the previous behavior of failing immediately if the lock is held. The change is motivated by a long-standing race condition where concurrent `rerere` operations (e.g., a rebase and background maintenance) contend for the lock, leading to crashes or deadlocks. The geometric maintenance strategy introduced in Git 2.54 exacerbated the issue by triggering `git rerere gc` more aggressively, but the race is a general robustness flaw in `rerere` locking.

The patch modifies `rerere.c` to use `repo_hold_lock_file_for_update_timeout()` instead of `repo_hold_lock_file_for_update()`, allowing processes to wait up to the configured timeout before failing. The default timeout (1 second) is sufficient to cover typical `git rerere gc` operations, which prune a few thousand entries in well under a second. The new `rerere.lockTimeout` config key is documented in `Documentation/config/rerere.adoc`, with clear explanations of the valid values (0 for no wait, -1 for indefinite wait, and positive integers for milliseconds).

Test coverage in `t/t4200-rerere.sh` verifies the new behavior under various scenarios: waiting for the lock, failing after timeout, and ensuring that explicit `rerere` commands (`forget`, `clear`, `gc`) and `git rebase --abort` still fail immediately if the lock cannot be acquired. The tests are thorough and cover edge cases, such as ensuring the rebase state file (`.git/rebase-merge`) is not corrupted by the lock timeout.

The patch is well-motivated and addresses a real-world problem. The implementation is clean, with clear documentation and robust test coverage. The configurable timeout aligns with established Git patterns (e.g., `core.packedRefsTimeout`), and the default value is pragmatic.

This is an **RFC proposal** for a new "limbo" object-format state in Git, aimed at solving a usability pain point for first-time pushes to newly created repositories.

Jeff King (Peff) identifies a looming problem with Git 3.0’s hash-algorithm transition: when a user pushes to a newly created bare repository on a forge (e.g., GitHub), the repository must already be configured for either SHA-1 or SHA-256. If the client and server disagree, the push fails with a fatal error, forcing users to manually reconfigure or recreate the remote repository. Peff proposes that empty repositories advertise a "limbo" state—no object format yet—allowing the server to dynamically adopt the format of the first incoming push. This mirrors GitHub’s existing behavior for setting the default branch on first push, but the mechanics are trickier because the object format is negotiated in the initial capability advertisement.

The idea is technically plausible but untested. Peff outlines the core concept: the server advertises `object-format=limbo`, the client responds with its own format, and the server atomically commits to that format before accepting the push. He acknowledges potential race conditions (e.g., simultaneous mismatched pushes) but sees no fundamental blockers. No implementation exists yet, and Peff is soliciting feedback rather than submitting a patch.

Key technical details for follow-up discussion: the proposal touches the wire protocol (capability negotiation), the repository initialization logic, and atomic state transitions on the server. The thread is likely to focus on edge cases (e.g., what happens if the first push is a mirror or includes multiple refs with conflicting formats) and whether the complexity is justified by the usability gain. If implemented, this would be a **feature** targeting the object-format subsystem.

This is the second patch in a two-patch feature series that extends `remote.pushDefault` to accept a space-separated list of remote names. The goal is to let users set a global fallback chain (e.g., `fork origin`) so they don’t have to configure each repository individually when some have a fork remote and others don’t.

The patch adds a new helper function `pushdefault_candidate()` in `remote.c` that iterates through the list of remotes in `remote.pushDefault` and returns the first one that exists in the repository. If none exist, it falls back to the branch’s configured remote as if `remote.pushDefault` wasn’t set at all. The documentation (`Documentation/config/remote.adoc`) is updated to explain the new behavior, and three new tests in `t/t5516-fetch-push.sh` verify that the feature works as intended: picking the first existing remote, handling a list of missing remotes, and respecting repository-level overrides of a global list.

The implementation is straightforward and doesn’t introduce new dependencies or on-disk format changes. It maintains backward compatibility by treating a single remote name exactly as before, and it preserves the existing override hierarchy (repository config beats global config). The test coverage looks thorough, exercising both the happy path and edge cases.

This is a well-motivated, user-facing improvement that addresses a real workflow pain point.

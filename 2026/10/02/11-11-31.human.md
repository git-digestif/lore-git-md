This is the second patch in Thomas Bachem’s three-part bugfix series addressing a race condition in Git’s `rerere` subsystem. The patch introduces a `--skip-locked` mode for `git rerere gc`, designed specifically for auto-maintenance tasks (`git maintenance run --auto` and `git gc --auto`). When the `MERGE_RR.lock` is held by another process, these background tasks now silently skip garbage collection instead of failing or waiting, avoiding disruptions to concurrent operations like rebases.

The implementation is clean and well-scoped. The new `--skip-locked` flag is hidden and undocumented, as it’s intended only for internal use by maintenance commands. The patch updates `builtin/gc.c` and `builtin/rerere.c` to pass the flag when running in auto mode, and modifies `rerere.c` to handle the new `RERERE_NOWAIT` flag, which skips lock acquisition entirely if the lock is held. Documentation in `Documentation/config/rerere.adoc` is updated to clarify that auto-maintenance runs do not wait for the lock, and the test suite (`t/t4200-rerere.sh` and `t/t7900-maintenance.sh`) now verifies the behavior under various scenarios, including lock contention and invalid flag usage.

This patch is a pragmatic solution to a real-world problem, aligning with Git’s established patterns (e.g., hidden flags for internal use, configurable timeouts). The trade-offs—silently skipping maintenance when the lock is held—are justified by the low cost of skipping a single run and the need to avoid disrupting user-facing operations. The series as a whole is ready for integration, with no unresolved technical concerns. If you care about `rerere` robustness or background maintenance, this patch is worth reviewing.

This is a bugfix patch from Junio C Hamano that addresses a surprising behavior in Git's configuration file handling. Currently, making a `.gitconfig` file read-only with `chmod a-w` does not prevent Git from overwriting it, because the config-writing machinery creates a new lockfile, copies the original content while applying changes, and then replaces the original file—effectively bypassing the read-only permission. The patch teaches Git to check the file's write permissions (using `access(2)`) before attempting to modify it, and to refuse the operation if the file is not writable.

The change is motivated by user expectations: most Unix tools respect file permissions, and users reasonably expect `chmod a-w` to protect a file from accidental modification. The patch adds a new error code (`CONFIG_NO_WRITE`) and updates the `repo_config_set_multivar_in_file_gently` function to return this error when the config file is unwritable. The accompanying test verifies that read-only config files cannot be modified, while still allowing reads.

This is a small but meaningful quality-of-life improvement that aligns Git's behavior with common Unix conventions. The implementation is straightforward and the test coverage is thorough. Given Junio's authorship and the clear rationale, this patch is likely to be uncontroversial and could land in `next` soon.

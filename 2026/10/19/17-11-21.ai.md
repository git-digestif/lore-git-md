This is the second iteration of René Scharfe’s patch addressing the ZIP extended timestamp wrap bug (bug #2 in the thread). The patch omits the Extended Timestamp (UT) extra field in ZIP archives when the commit time exceeds the 32-bit signed integer range (`> 0x7fffffff`), preventing silent timestamp wrap to 1970 and avoiding tool misbehavior (e.g., UnZip’s update mode retaining outdated content). This version incorporates Matthew E. Luallen’s test infrastructure fix, replacing `TIME_IS_64BIT` with `TIME_T_IS_64BIT` to ensure tests pass on 64-bit platforms and are skipped on 32-bit systems where `zipinfo(1)` lacks UT field support or is missing. Junio C Hamano has confirmed the test fix is sound, resolving CI failures on 32-bit platforms (Ubuntu 20.02 i386, Debian i386).

The patch touches `archive-zip.c` and adds tests to `t/t5004-archive-corner-cases.sh`. It introduces a new `strbuf zip_extra_mtime` to prepare the UT field upfront, simplifying conditional output logic. The implementation is clean and avoids repeating the out-of-range check. The interdiff shows the test prerequisite change as the only modification from v1, making this version ready for integration with no remaining technical blockers. René notes that while `time_t` is a pragmatic choice for now, future refactoring could eliminate its use in archive logic.

This fix is narrowly scoped to the ZIP extended timestamp issue and does not address the separate ZIP legacy DOS date overflow bug (bug #1) or the `fast-import` negative timestamp validation gap (bug #3). The thread’s broader policy debate—whether to reject or clamp out-of-range timestamps—remains open for the legacy DOS date field, but this patch sidesteps that question by omitting the problematic UT field entirely. The newly identified `dos_time()` bug (producing invalid timestamps for values `> 0x7fffffff`) is also unrelated to this patch and will require separate attention.

Thread identity: Subject "[PATCH] status,checkout: clarify tracking branch does-not-exist message"; standalone bugfix patch now at v3, originally authored by Elia Pinto; v3 is based on commit 47fdf2208c and remains queued in `seen` as `ep/status-missing-upstream` under review, with no evidence of graduation to `next` or `master`.

Core problem or goal: `git status` and `git checkout` previously printed "the upstream is gone" when a local branch tracks a remote branch that is absent, which is misleading when the upstream was never created, such as after cloning an empty repository. The patch changes the wording to a neutral "does not exist" form and replaces the unconditional `git branch --unset-upstream` advice with conditional guidance: suggest `git push` only when a plain push would actually create the missing upstream, otherwise suggest unsetting the upstream. The short-format `[gone]` indicator in `git status -sb`, `git branch -vv`, and `%(upstream:track)` of `git for-each-ref` is intentionally unchanged to avoid breaking scripts.

Current status and version changes: v3 has been posted and incorporates Junio C Hamano's requested structural refactor -- moving the `push_creates()` call inside `format_missing_upstream()` behind an `ADVICE_STATUS_HINTS` early return -- plus an expanded comment above `push_creates()` explaining the `@{push}`-based reasoning and roughly 150 lines of new tests in `t/t6040-tracking-info.sh`. Junio initially acknowledged the edge-case logic and accepted the v3 approach, but has since reopened review with a new objection (see Open questions); the thread is again open pending Elia Pinto's response. No merge to `next` or `master` has been announced.

Key technical details: Files touched are `remote.c` and `t/t6040-tracking-info.sh`; no on-disk format change. Implementation centers on a new `push_creates()` helper called from `format_missing_upstream()`, which is called from `format_tracking_info()`. The helper checks whether `@{push}` resolves to the tracked upstream via `branch_get_push_1()`, thereby excluding `push.default=nothing`, narrow explicit `remote.<name>.push` refspecs that do not cover the current branch, mirror remotes that would push to a different name, and `pushRemote` configurations pointing elsewhere, while retaining the existing special case for `push.default=matching` unless explicit refspecs or mirroring override it. Tests cover empty clones, deleted upstreams, all `push.default` values, explicit push refspecs including narrow and mirror-mismatch cases, `branch.<name>.pushRemote` to a different remote, and `advice.statusHints=false`. A newly identified gap: `branch_get_push_1()` returns the upstream for `PUSH_DEFAULT_UPSTREAM` without verifying that the push remote matches the upstream remote, whereas `setup_default_push_refspecs()` in `builtin/push.c` does guard against this with a `same_remote` check, so `push_creates()` wrongly returns true in the triangular-workflow scenario described below.

Open questions and loose ends: Junio C Hamano has identified a remaining edge case: when `push.default=upstream` is combined with `branch.<name>.pushRemote` (or `remote.pushDefault`) pointing to a remote different from `branch.<name>.remote`, a plain `git push` aborts with a fatal error about pushing to a remote that is not the upstream, yet the patch incorrectly advises `(use "git push" to create it)`. He proposes three possible directions without committing to one: updating `branch_get_push_1()` to check `same_remote` (matching actual `git push` behavior but risking fallout for other callers), adding a targeted guard to `push_creates()` (safer but inelegant), or consulting `branch_get_push_simple()`. He appended a test case to `t/t6040-tracking-info.sh` reproducing the misconfiguration. This edge case is unresolved and pending Elia Pinto's response. The author previously deferred any change from `[gone]` to `[missing]` in short formats to a follow-up. Final graduation remains pending.

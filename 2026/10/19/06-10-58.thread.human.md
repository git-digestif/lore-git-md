This thread is about a performance regression in `git log --follow` introduced by an earlier commit (304812ed33) that made the command unacceptably slow—ballooning from ~28 seconds to over six minutes for a test case on linux.git. Miklos Vajna’s patch restores performance to ~37 seconds while also fixing edge cases and adding test coverage.

The root cause was an expensive function (`propagate_follow_pathspec_to_parent()`) that diffed each commit against *all* its parents with rename detection enabled. The new approach eliminates this function and reuses diffs already computed in `log_tree_diff()`’s parent loop. For merge commits, it first checks if the path is unchanged against any parent (without rename detection) and only falls back to the expensive rename detection if the path differs in all parents. This two-pass strategy avoids redundant diffs while preserving correctness, including handling a previously untested edge case where a merge keeps a file from one parent but the other parent renamed and modified it.

The patch touches `log-tree.c` and adds new test cases in `t/t4219-log-follow-merge.sh`. It introduces helper functions (`commit_has_path()`, `follow_needs_renames()`, and `log_tree_merge_diff()`) and ensures `--follow` works correctly for merge commits with `-c`, `--cc`, or `--remerge-diff`.

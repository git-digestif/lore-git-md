This is a performance-focused bugfix patch targeting the `git log --follow` feature, specifically addressing a severe regression introduced by commit 304812ed33 ("log: improve --follow following renames for non-linear history"). The author, Miklos Vajna, reports that the original performance of ~28 seconds for a test case on linux.git ballooned to ~6m43s after that commit, and this patch restores it to ~37 seconds while also fixing edge cases and adding test coverage.

The core issue is that the original improvement introduced a function (`propagate_follow_pathspec_to_parent()`) that diffs each commit against *all* of its parents with rename detection enabled, which is computationally expensive. The new approach eliminates that function entirely and instead reuses the diffs already being computed in `log_tree_diff()`'s parent loop. For merge commits, it first checks if the path is unchanged against any parent (without rename detection), and only falls back to the expensive rename detection if the path differs in all parents. This two-pass strategy avoids redundant diffs while preserving correctness.

The patch also handles a previously untested edge case: when a merge keeps a file from one parent but the other parent renamed and modified it, the commits modifying the renamed path must still be followed. The solution introduces a `follow_needs_renames()` helper that computes merge bases only in this rare case, ensuring the expensive operation is avoided for back-merges where the path didn't exist on one side.

Key technical details:
- **Files touched**: `log-tree.c` (core logic) and `t/t4219-log-follow-merge.sh` (new test cases).
- **New functions**: `commit_has_path()`, `follow_needs_renames()`, and `log_tree_merge_diff()` (refactored from existing code).
- **Behavior changes**: The patch preserves `--follow` functionality for merge commits with `-c`, `--cc`, or `--remerge-diff` (previously untested), and correctly follows renames on the side of a merge that wasn't taken.
- **Performance**: The test case improves from 6m43s to 37s, nearly restoring the pre-regression performance.

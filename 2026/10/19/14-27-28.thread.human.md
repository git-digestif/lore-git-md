This thread proposes a small but important usability and security fix: making Git respect filesystem permissions when writing configuration files. Currently, Git ignores `chmod a-w .gitconfig` and overwrites the file anyway; Junio C Hamano’s patch adds a permission check before writing and returns a new `CONFIG_NO_WRITE` error if the file is read-only.

The patch itself is straightforward—it modifies `repo_config_set_multivar_in_file_gently()` in `config.c` to call `access(2)` before creating the lockfile, and adds test coverage in `t/t1300-config.sh`. The implementation is well-tested against the basic case (read-only files reject writes but still allow reads) and avoids modifying user config by using `GIT_CONFIG_GLOBAL`. Edge cases like symbolic links, NFS, and filesystem races remain unresolved, but the core change is uncontroversial in principle.

So far, the only feedback has been a brief, surface-level reply from brian m. carlson, who called the patch sensible but offered no technical critique or testing. The lack of deeper review means the patch is still in the "awaiting scrutiny" phase—no objections, but also no substantive approval. Junio’s follow-up noted the silence but didn’t withdraw the proposal, suggesting he still considers it viable. The main open questions are whether existing tools expect config writes to succeed regardless of permissions, and whether the error-handling approach (hard error vs. warning) is the most intuitive for users. For now, the patch remains under review with no merge status reported.

This thread is about a bugfix to make Git respect file permissions when writing out-of-tree configuration files like `~/.gitconfig`. Junio C Hamano initially proposed the change as an RFC, and after feedback from Patrick Steinhardt, has now sent a v2 patch. The core idea is simple: Git should return an error (`CONFIG_NO_WRITE`) when trying to write to a read-only config file, rather than silently overwriting it.

The implementation is straightforward—an `access(2)` check in the config subsystem—and the tests verify that read-only files can still be read but reject writes. The main update in v2 is the commit message, which now clearly explains why the patch is narrowly scoped to the config API rather than the lockfile layer: out-of-tree files like `~/.gitconfig` are uniquely vulnerable because they live outside the repository, and expanding the scope would require a time-consuming audit of all lockfile users. Patrick Steinhardt, who initially questioned the scope, now endorses this rationale and recommends including it in the commit message.

The patch itself is uncontroversial and well-tested, though some edge cases (race conditions, symlinks, NFS) remain unresolved. No substantive review of the implementation has emerged yet, but the narrow focus and clear motivation make it a strong candidate for merging. The unresolved architectural question about lockfile API consistency might come up again in the future, but for now, the patch is ready for closer scrutiny.

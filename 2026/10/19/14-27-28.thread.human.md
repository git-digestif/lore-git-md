This thread is about a small but important bugfix: making Git respect filesystem permissions when writing configuration files outside the repository (like `~/.gitconfig`). Junio C Hamano proposed the fix in a v2 patch after an initial RFC, keeping it narrowly focused on the config subsystem rather than refactoring the broader lockfile API—a scope Patrick Steinhardt initially questioned but now accepts. The patch adds a simple `access(2)` check before writing, returning a new `CONFIG_NO_WRITE` error if the file is read-only, and includes tests to verify the behavior.

The core design is uncontroversial and nearly ready for integration. Junio’s latest version addressed Patrick’s earlier concerns about scope justification, and the only remaining open questions are minor: whether to clarify in the commit message why in-tree files (like `.git/config`) are excluded (Junio says no, Patrick shrugs), and whether to fix an inconsistency in how filenames are quoted in error messages (Patrick prefers consistency, Junio defers it to avoid test churn). Neither is a blocker, and the patch is likely to land in `next` soon. The thread has no other active participants or objections, and the fix itself is straightforward and well-tested.

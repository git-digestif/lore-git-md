This thread is about a proposed bugfix to make Git respect filesystem permissions when writing configuration files. Currently, Git ignores write permissions on `.gitconfig` and similar files, allowing it to overwrite them even when they are read-only—a behavior that violates user expectations and could pose security or usability issues.

The patch, authored by Junio C Hamano, introduces a new error code (`CONFIG_NO_WRITE`) and modifies `repo_config_set_multivar_in_file_gently()` to check file permissions before attempting to write. Tests confirm that read-only config files can still be read but reject writes and unsets. The change touches the config subsystem and includes edge cases like symbolic links and network filesystems, though these remain unresolved.

So far, the patch has received only surface-level feedback from brian m. carlson, who acknowledged the proposal as sensible but did not engage with its technical details or broader implications. Junio’s follow-up email clarified his personal workflow—where he installs `.gitconfig` as read-only—and how he discovered the issue, but this context doesn’t address the patch’s open questions: whether existing tools expect config writes to succeed regardless of permissions, how to handle race conditions, or whether the change might break backwards compatibility. The thread is still awaiting substantive review or testing feedback.

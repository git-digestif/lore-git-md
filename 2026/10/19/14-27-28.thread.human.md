This thread is about a bugfix that makes Git respect filesystem permissions when writing out-of-tree configuration files like `~/.gitconfig`. The author, Junio C Hamano, posted a second version of the patch after an initial round of review. The change is narrowly scoped to the config subsystem, avoiding a broader refactoring of Git’s lockfile API, and is motivated by users who manage their dotfiles as read-only installed files.

The patch itself is straightforward: it adds a permission check before writing config files outside the repository, returning an error if the file is unwritable. In-tree files like `.git/config` are intentionally excluded, as users have no sensible reason to make them read-only. The implementation touches `config.c` and adds test coverage in `t/t1300-config.sh`. Junio has resisted expanding the scope, arguing that a lockfile API refactoring would require a time-consuming audit of all its users.

The only substantive feedback came from Patrick Steinhardt, who initially questioned the patch’s narrow scope but now endorses it after Junio clarified the rationale in the commit message. In the latest exchange, Patrick raised two minor points: whether the commit message should explain why in-tree files are excluded, and a coding-style inconsistency in error-message formatting. Junio pushed back on both, arguing that the exclusion of in-tree files needs no further justification and that the error-message inconsistency is better addressed in a separate cleanup effort. The exchange is more about polish than technical disagreement, and the patch appears ready to proceed.

No other contributors have weighed in on the core design or implementation. The patch is still under review, with no merge status reported, but the discussion suggests it is likely to land soon. Open questions about race conditions, symlinks, and network filesystems remain unresolved but were not reopened in this round of feedback.

This thread is about a proposed bugfix to make Git respect filesystem permissions when writing configuration files. Junio C Hamano, the maintainer, noticed that Git currently ignores `chmod a-w` on files like `.gitconfig`, allowing writes even when users expect them to be blocked. His patch introduces a `CONFIG_NO_WRITE` error and checks permissions before writing, but keeps the change narrowly focused on out-of-tree config files (like `$HOME/.gitconfig`) rather than all lockfile operations.

The patch has been under review since its initial RFC posting, with only two responses so far. Brian m. Carlson acknowledged it as sensible but offered no technical feedback, while Patrick Steinhardt raised a significant architectural question: whether permission checks should be centralized in `lockfile.c` to ensure consistency across all lockfile users (reflogs, index files, hooks). Junio’s latest response clarifies that the patch is intentionally limited to config files, arguing that in-tree files (like `.git/index`) don’t need this protection. He also notes the practical challenge of auditing all lockfile users, suggesting the current scope is a pragmatic choice.

The discussion now hinges on whether the narrow approach is sufficient or if the patch should evolve into a broader refactoring. No other reviewers have engaged with the implementation’s correctness, edge cases (like race conditions or NFS), or backwards compatibility. The patch remains in early review, with its future direction still open.

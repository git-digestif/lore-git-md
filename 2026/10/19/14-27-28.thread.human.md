This thread is about a proposed bugfix by Junio C Hamano to make Git respect filesystem permissions when writing configuration files. Currently, Git bypasses `chmod a-w` restrictions via its lockfile mechanism, which contradicts user expectations. The patch introduces a `CONFIG_NO_WRITE` error when attempting to write to a read-only config file, with tests verifying the behavior.

The proposal has received little substantive feedback so far, but Patrick Steinhardt’s recent review raises a key architectural question: why treat config files specially when Git’s lockfile mechanism is used across many subsystems (reflogs, index files, hooks)? He argues that permission checks should be centralized in `lockfile.c` to ensure consistent behavior, rather than being config-specific. This could reshape the patch into a broader refactoring of the lockfile API.

Junio’s implementation is straightforward, touching `config.c` and adding test coverage, but the lack of deeper review leaves open questions about edge cases (race conditions, symlinks, NFS) and backwards compatibility. The thread’s direction may now depend on whether others agree with Patrick’s suggestion to centralize permission checks or if config files are deemed to warrant special handling. No merge status has been reported, and the discussion remains in the design phase.

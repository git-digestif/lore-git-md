This thread is about a proposed fix to make Git respect filesystem permissions when writing configuration files like `~/.gitconfig`. Currently, Git ignores write permissions and overwrites these files even when they’re marked read-only, which breaks user expectations for managing dotfiles. Junio C Hamano authored the patch, which adds a permission check before writing out-of-tree config files (like `~/.gitconfig` or XDG config) and returns a new error (`CONFIG_NO_WRITE`) if the file is unwritable. In-tree files like `.git/config` are intentionally excluded, as users have no good reason to protect them from Git.

The patch is still under review as an RFC. While Junio’s implementation is narrowly scoped to the config subsystem—avoiding a broader refactoring of the lockfile API—Patrick Steinhardt raised an architectural concern: permission checks might be better centralized in `lockfile.c` to ensure consistency across all lockfile users (reflogs, index files, hooks). Junio defended the patch’s focus as pragmatic, but the question remains unresolved. No other reviewers have engaged with the implementation’s correctness, edge cases (like race conditions or symlinks), or broader implications. The latest exchange between Junio and Patrick merely clarifies the patch’s scope without advancing the discussion.

The series is at its first version, with no merge status reported. Key technical details include the new `CONFIG_NO_WRITE` error code, the use of `access(2)` for permission checks, and test coverage verifying that read-only config files can still be read but reject writes. The patch is well-tested but still lacks substantive review beyond Patrick’s high-level design feedback and brian m. carlson’s surface-level acknowledgment. Open questions include whether the patch’s narrow scope is sufficient or if a broader lockfile refactoring is needed, and how robust the `access(2)` check is across different filesystems.

This thread is about a proposed security and usability fix to Git's configuration system. Junio C Hamano has sent an RFC patch that makes Git respect file permission bits when writing `.gitconfig` files, preventing accidental overwrites of read-only configuration files. The change adds a permission check using `access(2)` before Git's usual lockfile-and-rename update mechanism, returning a new error code `CONFIG_NO_WRITE` if the file is unwritable.

The motivation is straightforward: users expect `chmod a-w` to protect files from modification, but Git's current implementation bypasses this protection. The patch is small and focused, modifying `config.c` and adding a comprehensive test in `t/t1300-config.sh`. The test verifies that read-only config files remain readable but reject writes, and it uses `GIT_CONFIG_GLOBAL` to avoid interfering with the user's actual configuration.

This is an early proposal (RFC/PATCH), so discussion is likely to focus on alternative approaches to error handling and potential edge cases like filesystem race conditions. However, the core idea—honoring file permissions—seems uncontroversial and aligns with user expectations. No responses or reviews have appeared yet, so the thread is still in its initial phase.

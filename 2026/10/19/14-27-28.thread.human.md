This thread is about a small but long-overdue fix to make Git respect filesystem permissions when writing configuration files like `~/.gitconfig`. The patch, now in its second version, adds a simple check before Git tries to write to a config file: if the file is read-only, Git will refuse to modify it and return an error instead of silently overwriting it. This matches what users expect when they run `chmod a-w .gitconfig`—the file should stay untouched.

Junio Hamano, the maintainer and author of the patch, kept the change narrowly focused on out-of-tree config files (like global and XDG configs) and resisted calls to expand it to Git’s internal files or the broader lockfile system. The reasoning is straightforward: users have no good reason to protect `.git/config` from Git itself, and the patch’s simplicity makes it easy to review and safe to merge. Patrick Steinhardt initially pushed back on the scope, but after Junio clarified the rationale in the commit message, Patrick endorsed the approach and shifted to minor polish: a coding-style nit about error-message formatting and a suggestion to further justify why in-tree files are excluded. Junio addressed the latter but left the former unresolved, noting that the inconsistency already exists in the codebase and fixing it now would be more trouble than it’s worth.

The patch itself is uncontroversial and well-tested, with coverage for both read-only files and edge cases like unset operations. The only loose ends were the two nits, and Junio’s latest email closes them: the error-message formatting will stay as-is, and the commit message’s justification for the scope is sufficient. The patch is now effectively ready to merge, with no remaining objections or open questions. If you’re catching up after a break, this is a safe, self-contained fix that won’t disrupt workflows—it just makes Git behave the way users already expect.

This thread is about a bugfix to make Git respect filesystem permissions when writing out-of-tree configuration files like `~/.gitconfig`. The issue is that Git currently bypasses `chmod a-w` protections, allowing it to overwrite read-only files—a behavior that violates user expectations and complicates workflows where dotfiles are managed as read-only installed files.

Junio C Hamano posted a v2 patch that adds an `access(2)` check before writing config files, returning a new `CONFIG_NO_WRITE` error if the file is unwritable. The fix is narrowly scoped to out-of-tree config files (e.g., `~/.gitconfig`, XDG config), excluding in-tree files like `.git/config`, a distinction Junio and Patrick Steinhardt have agreed is justified. The patch touches `config.c` and adds test coverage in `t/t1300-config.sh`. Junio has since revised the commit message to better document the rationale for this scope, addressing Patrick’s earlier architectural concern about whether permission checks should be centralized in the lockfile API.

The patch is under review but has yet to receive substantive technical feedback on edge cases like race conditions, symlinks, or NFS behavior. brian m. carlson acknowledged the patch as sensible but offered no detailed critique. The main open question is whether existing tools or scripts expect config writes to succeed regardless of permissions, but no objections or alternative approaches have been raised so far. The thread is still awaiting deeper review of the implementation’s correctness and robustness.

This is a bugfix and refactoring patch that aligns the behavior of `remote.<name>.followRemoteHEAD` with an earlier change for `fetch.followRemoteHEAD`. The patch defers validation of the remote-level setting until it is actually needed (during `git fetch`), eliminating spurious warnings emitted by commands like `git push` or `git remote -v` that load remote configuration but never use this setting. It also unifies the parsing logic for both settings, allowing `fetch.followRemoteHEAD` to accept the "warn-if-not-<branch>" syntax previously exclusive to the remote-level setting.

Junio C Hamano reviewed the patch and identified a key issue: the error messages in `get_follow_remote_head()` no longer specify whether the problematic value came from `fetch.followRemoteHEAD` or `remote.<name>.followRemoteHEAD`. This could confuse users, as the message now generically refers to "followRemoteHEAD" without indicating which configuration key is misconfigured. Junio suggested passing the prefix or full variable name from the calling sites to ensure clarity in error reporting. He also noted a minor style nit about an overly long line in the diff.

The patch itself is well-motivated and addresses a real annoyance, but the error message ambiguity is a legitimate concern that will need to be fixed before merging. The implementation is otherwise clean, removing a NEEDSWORK comment and consolidating duplicate logic while adding thorough test coverage. This looks like a straightforward improvement once the error message issue is resolved.

This is a **substantive review** of the OpenSSL 4.0 compatibility patch in Beat Bolli’s `imap-send` series. The patch adds macros to alias `SSL_set1_dnsname()` to `SSL_set1_host()` for OpenSSL < 4.0, but Patrick Steinhardt raises three sharp technical concerns that block its inclusion in its current form.

First, the patch is **procedurally misplaced**: the compatibility macros should have been introduced in the same commit that added the `SSL_set1_host()` call (patch 2/3), not as a separate follow-up. This violates the principle of atomic commits and makes the series harder to review. The fix is straightforward: fold the macros into patch 2/3.

Second, the patch **assumes `cfg->host` is always a DNS name**, but OpenSSL 4.0 splits hostname verification into two functions: `SSL_set1_dnsname()` for DNS names and `SSL_set1_ipaddr()` for IP addresses. If `cfg->host` could ever be an IP address (e.g., `imaps://192.168.1.1`), the current patch would silently misbehave. The commit message does not justify this assumption, and the code offers no runtime validation. This is a **latent bug** that needs either a runtime check (to call the correct function) or a clear statement in the commit message that `cfg->host` is guaranteed to be a DNS name.

Third, the patch **unnecessarily complicates error reporting** by conditionally changing the function name in the error message. The error message should simply use `SSL_set1_dnsname` unconditionally, since that is the function users will see in OpenSSL 4.0. The conditional macro for the error string adds no value and could confuse debugging.

The patch also remains **premature** in the context of the series. The v3 series is still blocked on a **security regression** in patch 2/3 (certificate stripping), and this patch does not address that issue. While the compatibility macros are uncontroversial in isolation, they should not distract from the unresolved security flaw.

If you are tracking OpenSSL compatibility or `imap-send`, this patch is a minor but necessary step for forward compatibility. However, it must be revised to address the procedural, correctness, and clarity issues Patrick raised before it can be merged. The series as a whole will likely need another iteration to resolve the security regression and these follow-up concerns.

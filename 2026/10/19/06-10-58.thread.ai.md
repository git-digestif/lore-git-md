Subject: [PATCH] log: fix --follow performance regression for merge commits
Series version: standalone patch (no series)
Originating author: Miklos Vajna
Thread type: bugfix patch

Core problem or goal
Restore the performance of `git log --follow` after a severe regression introduced by commit 304812ed33 ("log: improve --follow following renames for non-linear history"). The regression caused a test case on linux.git to balloon from ~28s to ~6m43s; the patch reduces this to ~37s while also fixing edge cases and adding test coverage.

Current status
Under review. No prior versions of this patch have been posted. The patch is a direct response to a known regression with a clear performance impact.

Key technical details
- **Files touched**: `log-tree.c` (core logic), `t/t4219-log-follow-merge.sh` (new test cases).
- **Subsystems**: revision walking, diff machinery, merge commit handling.
- **New functions**: `commit_has_path()`, `follow_needs_renames()`, `log_tree_merge_diff()` (refactored from existing code).
- **Behavior changes**: Preserves `--follow` functionality for merge commits with `-c`, `--cc`, or `--remerge-diff` (previously untested); correctly follows renames on the side of a merge that wasn’t taken.
- **Performance**: Test case improves from 6m43s to 37s.
- **Edge cases**: Handles merges where one parent kept a file while the other renamed and modified it; avoids expensive rename detection for back-merges where the path didn’t exist on one side.

This thread is about a proposed change to make `git status` compare the current branch against both `@{upstream}` and `@{push}` by default, rather than just `@{upstream}`. The patch, now in its second version, was originally motivated by the idea that users in triangular workflows (common with GitHub forks) might miss upstream changes if they don’t realize they need to explicitly monitor both branches. While the technical implementation has been refined—with updates to `remote.c`, documentation, and new tests—the discussion has evolved into a philosophical debate about Git’s defaults and user expectations.

Harald Nordgren, the patch’s author, argues that the change would benefit less experienced users who may not understand why upstream changes aren’t visible by default in triangular workflows. He dismisses concerns about reinforcing "broken" mental models (a critique Junio C Hamano raised) as idealistic, advocating instead for Git to adapt to how users actually work. Junio, however, remains unconvinced. In his latest reply, he proposes an alternative: rather than changing Git’s default, tools like GitHub’s UI or documentation should encourage users to configure `status.compareBranches` themselves when adopting triangular workflows. This would preserve Git’s internal consistency without imposing the change on all users. Junio also reiterates that the escape hatch (restoring the old behavior via config) isn’t sufficient justification for flipping the default.

The patch itself is technically sound, but its fate hinges on resolving this philosophical stalemate. Phillip Wood’s earlier feedback has been addressed, leaving Junio’s opposition as the primary obstacle. The thread is now at a crossroads: Harald could counter Junio’s proposal, seek broader consensus (e.g., from other contributors like Phillip Wood), or accept that the default change may not be justifiable. For now, the patch remains under review, with no clear path to merging.

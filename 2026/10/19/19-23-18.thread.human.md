This thread is about a proposed change to `git status` that would make it compare the current branch against both `@{upstream}` and `@{push}` by default, rather than just `@{upstream}`. The patch, now in its second version, aims to make Git more useful in triangular workflows—where users fetch from one remote but push to another—by surfacing both comparisons automatically. Harald Nordgren, the author, argues this helps less experienced users who might not realize they’re missing upstream changes when they switch to a triangular setup.

The discussion has shifted from technical details to a deeper debate about whether this change is the right fix for the problem. Junio C Hamano, the maintainer, has challenged the patch’s core assumption: he questions whether the real issue is Git’s defaults or how users are introduced to Git in the first place. His latest reply frames the problem as a cultural one, suggesting that GitHub’s fork-and-pull model may have created a "sad world" where users lack a proper understanding of Git’s branching concepts, and that accommodating this with defaults might not be the best solution. Harald counters that users often set their push branch to match upstream initially, leaving them unaware of upstream changes until they explicitly reconfigure their workflow, which can feel disruptive.

The patch itself is technically sound—it updates `remote.c`, adds tests for triangular workflows, and preserves backward compatibility via a config option—but the justification for flipping the default remains unresolved. Junio dismisses the escape hatch as insufficient reason to change the default, and the thread now hinges on whether Harald can address the maintainer’s philosophical concerns or find a way to bridge the gap between usability and Git’s design principles. No other contributors have weighed in recently, so the next move is likely Harald’s. The patch is still under review, with no clear path to merging until this debate is settled.

This thread is about a proposed change to make `git status` compare the current branch against both `@{upstream}` and `@{push}` by default, rather than just `@{upstream}`. The patch, now in its second version, aims to make Git more useful in triangular workflows (where you pull from one branch but push to another), particularly for less experienced users who may not realize they’re missing upstream information. The author, Harald Nordgren, argues this change aligns with the original intent of a 2026 commit that made the feature opt-in, while Junio C Hamano has pushed back strongly, framing the debate as a philosophical clash between adapting to users shaped by GitHub’s fork-and-pull model and preserving Git’s internal consistency.

The discussion has evolved into a broader debate about Git’s defaults and cultural assumptions. Junio critiques the patch’s premise, arguing that `@{push}` is typically under the user’s control and thus less likely to introduce "surprises" that warrant default monitoring. He also questions whether Git should accommodate users who lack a solid understanding of Git’s branching concepts, suggesting external tools (like GitHub) should promote the necessary configuration instead. Harald counters that users often set their push branch to match upstream initially, leaving them unaware of upstream changes until they explicitly reconfigure their workflow, and dismisses Junio’s concerns as idealistic. D. Ben Knoble recently weighed in with a pragmatic, user-centric argument, sharing his own workflow where he frequently checks divergence between local and push branches to answer questions like *"Have I rebased lately and need to force-push?"* His experience—including custom tooling he built before this patch—suggests the need is real and widespread.

The patch itself is technically sound, with v2 addressing all feedback from v1 and adding comprehensive test coverage for triangular workflows. The backward compatibility escape hatch (restoring the old behavior via config) remains intact, but Junio dismisses it as insufficient justification for flipping the default. The thread is still under review, with no clear path to resolution. The debate now hinges on whether the project should adapt to users’ existing mental models or resist changes that might reinforce broken assumptions about Git’s branching. Junio’s counterproposal—that external tools should promote the configuration—hasn’t gained traction yet, but it remains a possible compromise. For now, the patch’s fate depends on whether Harald can strengthen the justification or another contributor steps in to break the stalemate.

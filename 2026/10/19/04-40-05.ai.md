This is a **user report and review** from Jasper Mayone, a real-world user of the `--delete-merged` feature, responding to Junio C Hamano’s proposal to split `--delete-merged` (strict, tip-reachability only) from `--delete-irrelevant` (looser, change-based detection). Jasper built and tested Harald Nordgren’s v2 implementation (`ec88bde252`) on generated repositories, providing concrete feedback on correctness, performance, and usability.

Jasper’s testing confirms that v2 correctly identifies squash merges (including GitHub-style squashes with new messages and committers), rebase merges, renames, and even squashes that were later reverted. The "landed as" output consistently named the correct upstream commit. However, Jasper also encountered the **false-positive case** Junio warned about: v2 deleted a branch whose changes were independently implemented by another author, reporting it as "landed as" an unrelated commit. This aligns with Junio’s "irrelevant" scenario and reinforces the argument that **looser detection should not be the default** for `--delete-merged`.

Jasper **endorses Junio’s CLI redesign proposal**, suggesting a granular `--landed=<kind>` option (e.g., `--landed=squash`) instead of the current `--no-squashed` flag. This would allow users to opt into looser detection once per repository via a config variable, avoiding the need for repeated `--no-<kind>` flags. Jasper also notes that the performance impact of v2 is modest (0.078s vs. 0.030s for 80 branches) and that `--no-squashed` restores baseline speed. In blobless clones, the first run fetched 13 blobs (0.42s), while `--no-squashed` avoided fetches entirely.

On usability, Jasper highlights a **silent skip** for branches checked out in worktrees (vs. an explicit "Skipping" message for branches with `deleteMerged=false`). Jasper proposes a clearer message (`"Skipping 'topic' (checked out in <path>)"`) and suggests refactoring the "has this branch landed?" logic into a reusable helper for future commands like `git worktree list --merged`. Jasper’s `Tested-by` trailer signals hands-on validation of the v2 implementation.

The email does not engage with Harald’s latest rejection of the CLI split or the `git range-diff` performance findings, focusing instead on **user experience and safety**. Jasper’s feedback strengthens Junio’s case for decoupling strict and looser detection, while also providing actionable suggestions for CLI ergonomics and code reuse. The report is a rare example of a **tested review** from a non-contributor, offering practical insights that complement the maintainer’s architectural concerns.

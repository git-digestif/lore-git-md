This thread introduces a pluggable object database backend mechanism for Git, allowing alternative storage systems (like cloud storage) to be used in place of the default `.git/objects` directory. Patrick Steinhardt’s seven-patch series defines the `extensions.objectStorage` configuration, implements the baseline `files` backend (which supports relocating objects via a payload like `files://objs`), and adds tools to inspect the configured backend (`git rev-parse --show-object-storage-format` and `git repo objects.storageFormat`). The series also handles environment variable overrides, submodule propagation, and disables local clones when non-default storage is used—a pragmatic limitation to avoid complexity in this initial implementation.

The patches are under review, with Karthik Nayak providing the most detailed feedback so far. His reviews have been substantive but non-blocking, focusing on design consistency (e.g., path normalization in the `files` backend), test coverage gaps (particularly around environment variable handling and payload validation), and UX concerns (like the subtle naming distinction between `object.format` and `objects.storageFormat`). His latest review questions the architectural decision to hard-code the default `files` backend in the inspection tools, arguing it creates a maintenance burden if the default ever changes. No other participants have weighed in on the later patches, and the series remains uncontroversial in its core approach, following established patterns from Git’s ref storage extension.

The open questions center on design trade-offs and test thoroughness rather than correctness. The local clone restriction may spark discussion about whether it’s too conservative, but no objections have been raised yet. The series is still in its first iteration, and while Karthik’s feedback is actionable, it’s unlikely to require major changes. The next steps will likely involve addressing the test gaps and possibly revisiting the default backend encapsulation in the inspection tools.

This thread is about Patrick Steinhardt’s seven-patch series introducing the **object storage extension**, a mechanism to make Git’s object database pluggable. The goal is to allow alternative backends (like cloud storage or databases) by defining a configuration scheme (`extensions.objectStorage`) modeled after the existing ref storage extension. The series implements the baseline `files` backend, which supports relocating the `.git/objects` directory via a payload (e.g., `files://objs` moves objects to `.git/objs`), and adds user-facing tools to inspect the configured backend.

The latest update, patch 4/7 in v2, adds inspection tools: `git rev-parse --show-object-storage-format` and `git repo objects.storageFormat`. These let users query the active storage format, defaulting to `"files"` if unset. The patch is uncontroversial, following the ref storage extension’s pattern and addressing a v1 concern by ensuring the `object_storage_format` field is always initialized. The series remains under review, with no merge status reported. Key open questions include whether to normalize relative paths in payloads (deferred to avoid breaking tests) and the naming subtlety between `object.format` (hash algorithm) and `objects.storageFormat` (storage backend), which was acknowledged as a pragmatic compromise.

Karthik Nayak has provided the most substantive feedback so far, focusing on design consistency, test coverage, and naming clarity. Junio C Hamano’s input has been advisory, and Patrick has addressed most concerns, though the path normalization question remains unresolved. The series is architecturally sound, with prerequisite topics merged and no major objections raised. The next steps are likely further review of the remaining patches (5/7–7/7), particularly the submodule integration in patch 7/7.

This thread introduces the **object storage extension** (`extensions.objectStorage`), a pluggable backend mechanism for Git’s object database. The series, now at **v4**, is authored by Patrick Steinhardt and is functionally complete, with all planned features—including CLI/config/environment support, submodule propagation, and inspection tools—implemented. Karthik Nayak has unconditionally approved the series, addressing all prior feedback, while SZEDER Gábor’s architectural critique (questioning whether the feature should be a public API at all) remains unresolved but does not block integration.

The core change allows alternative object storage backends (e.g., cloud storage) by defining a configuration mechanism modeled after the existing ref storage extension. The `files` backend (default) now supports relocating the `.git/objects` directory via a payload (e.g., `files://objs` moves objects to `.git/objs`), and the series introduces user-facing tools like `git rev-parse --show-object-storage-format` and `git repo objects.storageFormat`. Key design choices include splitting the storage format URI into `(type, payload)` (e.g., `("files", "objs")`), stripping payloads in submodules for consistency with ref storage, and bumping `core.repositoryformatversion` to `1` for non-default backends. The implementation touches 35 files, including `odb/`, `setup.c`, and built-in commands like `git clone` and `git submodule`.

The series is **ready for integration**, with Junio’s decision pending only the unresolved architectural debate. Open questions include whether the payload’s utility justifies the complexity of a URI-based system and whether the local clone restriction (disabling `--local` for non-default backends) is overly conservative. Documentation gaps remain around payload-stripping behavior in submodules and inspection tools. No merge status has been reported, but the series is expected to appear in Junio’s "What’s cooking" report soon.

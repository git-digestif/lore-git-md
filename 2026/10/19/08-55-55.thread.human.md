This thread is about Patrick Steinhardt’s patch series introducing a pluggable object database backend mechanism for Git, using a new `extensions.objectStorage` configuration modeled after the existing ref storage extension. The series is now at its initial version (v1) and defines the baseline `files` backend, which supports relocating the `.git/objects` directory via a payload (e.g., `files://objs`). It also adds environment variables (`GIT_OBJECT_STORAGE_FORMAT`), user-facing configuration (`init.defaultObjectStorageFormat`), and inspection tools (`git rev-parse --show-object-storage-format`) to query the configured backend.

The series has been uncontroversial so far, with Karthik Nayak providing the most substantive feedback. His review of the third patch (adding environment variable support) highlights a test coverage gap: the current tests verify basic override behavior but don’t systematically cover combinations of configuration sources, backend validity, or path payload edge cases. While this isn’t a blocking issue, it’s a design-level suggestion to improve robustness for future backends. Earlier feedback from Karthik also raised questions about path normalization consistency with the ref storage extension and minor code hygiene issues, but none of these are objections—just actionable improvements.

The series is still under review, with no merge status reported. The local clone restriction (disabling hardlinking/copying when either source or destination uses a non-default backend) may attract further discussion, but the baseline implementation remains aligned with established patterns. No other participants have weighed in yet, and the broader design questions (e.g., backend API) are likely to dominate future iterations.

This thread introduces a new mechanism for pluggable object database backends in Git, allowing alternative storage systems (like cloud storage) to be used in place of the default `.git/objects` directory. The series, authored by Patrick Steinhardt, defines the `extensions.objectStorage` configuration key, implements a baseline `files` backend that supports relocating objects via a URI payload (e.g., `files://objs`), and adds tools to inspect the configured backend. It also ensures submodules inherit the parent repository’s storage settings and disables local clones when non-default backends are in use—a pragmatic limitation to avoid complexity in this initial implementation.

The series is now complete at version 1, with all seven patches posted and under review. The core functionality—configuration, inspection, cloning, and submodule propagation—follows established patterns from Git’s ref storage extension and has so far been uncontroversial. However, several design and implementation questions remain open. Karthik Nayak has raised concerns about path normalization consistency with the ref storage extension, the subtlety of naming between `object.format` and `objects.storageFormat` in `git repo` output, and the awkwardness of exposing the hard-coded default (`files`) in inspection tools. Test coverage for invalid path payloads and environment variable interactions is also under discussion, with Patrick deferring some changes to avoid breaking existing tests or overcomplicating the initial implementation.

The only new development in this latest exchange is a minor cleanup confirmation: Junio Hamano clarified that the `gettext.h` include in `odb/source.c` is necessary for translation macros, closing a surface-level review point. The thread’s focus remains on the unresolved technical questions, with no objections or conditional approvals recorded yet. The series is still in the early review phase, and its eventual merge will depend on resolving these design considerations.

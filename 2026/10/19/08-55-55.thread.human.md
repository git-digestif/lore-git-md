This thread is about Patrick Steinhardt’s **v3 patch series introducing `extensions.objectStorage`**, a pluggable object database backend mechanism for Git. The series defines a configuration system modeled after the existing ref storage extension, allowing users to specify alternative backends (e.g., `files://objs` to relocate `.git/objects`). The v3 refactoring splits the storage format into separate `(type, payload)` components for consistency with ref storage, adds submodule support, and includes a cleanup patch removing dead code.

The series is **functionally complete and under review**, with all planned features implemented: configuration, environment variables, command-line options (`--object-storage-format`), inspection tools (`git rev-parse --show-object-storage-format`), and submodule propagation. Prerequisite topics are merged, and the series is ready for final review. Key technical details include new config keys (`extensions.objectStorage`, `init.defaultObjectStorageFormat`), CLI options, and a repository format version bump to `1` for non-default backends.

The main open question is **architectural**: SZEDER Gábor challenged whether `extensions.objectStorage` should be a public API at all, given that the `files` backend’s payload only relocates `.git/objects`. Patrick responded by justifying user-facing configurability for testing, consistency with `extensions.refStorage`, and internal GitLab use (though the latter wasn’t elaborated). Karthik Nayak’s earlier feedback on design consistency and test readability has been addressed, and his conditional approval likely still stands. Junio’s review was surface-level and advisory.

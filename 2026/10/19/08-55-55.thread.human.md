This thread introduces a pluggable object database backend mechanism for Git, allowing alternative storage systems (like cloud storage or databases) to be used in place of the default `.git/objects` directory. The series, now at version 3, is functionally complete and under active review. Patrick Steinhardt is the driving force behind this architectural change, which defines a new `extensions.objectStorage` configuration modeled after Git’s existing ref storage extension.

The latest update (patch 7/7) teaches `git submodule` to propagate the `--object-storage-format` option to newly cloned submodules, ensuring consistency with the parent repository’s configuration. Submodules inherit the storage *type* (e.g., `files`) but not the *payload* (e.g., `files://objs` becomes `files`), mirroring the behavior of the ref storage backend. This design choice, while deliberate, may spark discussion about whether it’s overly restrictive. The patch includes thorough documentation and test coverage, addressing earlier feedback about clarity and consistency.

Key participants include Karthik Nayak, who provided substantive technical reviews of earlier versions and conditionally approved v2 pending minor cleanup, and Junio C Hamano, who offered surface-level feedback on one patch. The series has no outstanding technical objections, though open questions remain about path normalization, repository format version bumps, and the local clone restriction for non-default backends. The implementation is now ready for final review, with all planned features—configuration, environment variable support, command-line options, and inspection tools—implemented and tested.

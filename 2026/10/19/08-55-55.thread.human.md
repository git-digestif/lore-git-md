This thread introduces a new pluggable object database backend mechanism for Git, allowing alternative storage systems (like cloud storage or databases) to be used in place of the default `.git/objects` directory. The series, authored by Patrick Steinhardt, defines the `extensions.objectStorage` configuration and implements a baseline `files` backend that supports relocating objects via a URI-like payload (e.g., `files://objs` moves objects to `.git/objs`). It also adds user-facing tools like `git rev-parse --show-object-storage-format` and `git repo objects.storageFormat` to inspect the active backend, along with environment variables and configuration options for overriding defaults.

The series is now complete at v1, with all seven patches posted and under review. The implementation follows established patterns from Git’s ref storage extension and includes integration with `git clone`, `git init`, and submodules, ensuring parent repository settings propagate to submodules. A pragmatic restriction disables local clones (hardlinking or copying objects) when either the source or destination uses a non-default backend, falling back to non-local transports or failing if `--local` is explicitly requested. Tests cover initialization, cloning, submodule propagation, schema validation, and error cases.

Key participants include Patrick Steinhardt (author) and Karthik Nayak (reviewer). Karthik’s feedback has focused on design consistency—such as path normalization and naming subtleties—and test coverage, though most points have been addressed or deferred as non-blocking. The latest exchange confirms that the naming conflict between `object.format` (hash algorithm) and `objects.storageFormat` (storage backend) in `git repo`’s output is a minor wart rather than a blocker, with no further changes planned. The series remains uncontroversial, with no substantive objections or conditional approvals recorded. Open questions are largely about future-proofing (e.g., invalid path handling) rather than immediate fixes.

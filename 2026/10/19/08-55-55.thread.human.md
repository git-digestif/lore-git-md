This thread introduces Git’s new **object storage extension** (`extensions.objectStorage`), a pluggable backend mechanism for the object database. The series, now at **v4**, is the work of Patrick Steinhardt and lays the groundwork for alternative storage backends (e.g., cloud storage or databases) by defining a configuration system modeled after the existing ref storage extension. The default `files` backend supports relocating the `.git/objects` directory via a payload (e.g., `files://objs` moves objects to `.git/objs`), and the series includes environment variable support (`GIT_OBJECT_STORAGE_FORMAT`), user-facing configuration (`init.defaultObjectStorageFormat`), and inspection tools like `git rev-parse --show-object-storage-format`.

The v4 iteration is **functionally complete** and addresses only minor stylistic nits after receiving **unconditional approval** from Karthik Nayak. The series is ready for integration but awaits Junio’s assessment of an **unresolved architectural debate** raised by SZEDER Gábor: whether the object storage backend should be user-configurable at all, given that the `files` backend’s payload only relocates `.git/objects`. Patrick’s response justifies the design on grounds of testing infrastructure, consistency with ref storage, and internal use cases, but the question remains open.

Key technical details include a **repository format version bump** to `1` when `extensions.objectStorage` is set (even for the `files` backend with a payload), **submodule payload restrictions** (submodules inherit the parent’s `type` but not the payload), and **local clone restrictions** (disabled for non-default storage types). The series touches `odb/`, `setup.c`, `repository.c`, and documentation, and introduces new config keys (`extensions.objectStorage`, `init.defaultObjectStorageFormat`), CLI options (`--object-storage-format=`), and environment variables (`GIT_OBJECT_STORAGE_FORMAT`).

The latest email adds support for the `GIT_OBJECT_STORAGE_FORMAT` environment variable, a straightforward implementation that mirrors the ref storage extension’s behavior. This patch is uncontroversial and aligns with the series’ broader design. The thread’s next steps hinge on Junio’s resolution of the architectural question, though the implementation itself is technically sound and approved.

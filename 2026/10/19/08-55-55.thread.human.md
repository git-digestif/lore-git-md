This thread introduces a pluggable object database backend for Git, allowing alternative storage systems (like cloud storage) to be used in place of the default `.git/objects` directory. The series, now at its fourth and final version, is technically complete and has been unconditionally approved by Karthik Nayak. Patrick Steinhardt is the driving force behind this effort, which defines a new configuration mechanism (`extensions.objectStorage`) modeled after the existing ref storage extension.

The implementation adds user-facing tools like `git rev-parse --show-object-storage-format` and `git repo objects.storageFormat`, along with CLI options (`--object-storage-format=`) for `git init`, `git clone`, and now `git submodule add`/`update`. A key design choice—stripping payloads (e.g., `files://objs` becomes `files`) when propagating formats to submodules—mirrors the ref storage backend’s behavior but may surprise users. The series also enforces a temporary restriction: local clones are disabled if either the source or destination uses a non-default object storage type, documented as a conservative measure.

While the code is ready for integration, an unresolved architectural debate lingers. SZEDER Gábor questioned whether the object storage backend should be user-configurable at all, given that the `files` backend’s payload only relocates `.git/objects`. Patrick’s response justified the design on grounds of testing, consistency with ref storage, and internal use cases, but the broader question remains open. Junio’s eventual decision may hinge on this point, though the series itself is mechanically sound and thoroughly tested.

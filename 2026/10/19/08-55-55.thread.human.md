This thread is about Patrick Steinhardt’s seven-patch series introducing a pluggable object database backend for Git, allowing alternative storage systems (like cloud storage or databases) to replace the default `.git/objects` layout. The series defines a new `extensions.objectStorage` configuration mechanism, modeled after the existing ref storage extension, and implements the baseline `files` backend, which supports relocating the objects directory via a URI-style payload (e.g., `files://objs` moves objects to `.git/objs`).

The latest email covers patch 5/7, which adds user-facing configuration options for `git init` and `git clone`. This patch introduces `--object-storage-format=<format>` (mirroring `--ref-storage-format`), environment variable support (`GIT_DEFAULT_OBJECT_STORAGE_FORMAT`), and the `init.defaultObjectStorageFormat` config key, all following Git’s standard precedence rules. The `files` backend remains the default, and the patch includes validation to reject unknown formats. Tests verify initialization, environment variable overrides, payload handling, and error cases. While no review feedback has emerged yet, the patch is uncontroversial and aligns with the established ref storage pattern, making it a foundational piece of the series.

So far, the first five patches (refactoring, core configuration, environment variable support, inspection tools, and now this configuration UI) have been posted without substantive objections. The series is still under review, with the remaining patches likely to focus on backend integration and edge cases like submodule propagation. The inspection tools (`git rev-parse --show-object-storage-format` and `git repo objects.storageFormat`) and environment variable handling follow prior art, suggesting minimal pushback. Key technical details include new CLI options, config keys, and helper functions, but no on-disk format changes—the `files` backend remains compatible with the default layout. The thread is shaping up as a smooth architectural evolution, though broader design discussions may arise as the series progresses.

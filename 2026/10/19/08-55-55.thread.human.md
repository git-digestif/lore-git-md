This thread is about Patrick Steinhardt’s patch series introducing `extensions.objectStorage`, a mechanism to make Git’s object database pluggable. The series is now at version 3, which refactors the storage format into separate `(type, payload)` components (e.g., `("files", "objs")` instead of `"files://objs"`) and adds support for submodules, environment variables, and inspection tools. The core goal is to enable alternative object storage backends, such as cloud storage or databases, while maintaining compatibility with the default `files` backend.

The series has received unconditional approval from Karthik Nayak, who reviewed all seven patches and signaled readiness for integration. The implementation is functionally complete, with no substantive changes expected beyond minor stylistic nits. However, an architectural debate remains unresolved: SZEDER Gábor questioned whether user-configurable object storage backends are justified, given that the `files` backend’s payload only relocates `.git/objects`. Patrick defended the design as a public API, citing testing needs, consistency with the ref storage extension, and internal GitLab use, but the discussion has not swayed the reviewer’s skepticism.

The latest email addresses a surface-level review comment from Karthik on patch 3/7, which adds the `GIT_OBJECT_STORAGE_FORMAT` environment variable. The change is uncontroversial and mirrors the existing `GIT_REF_STORAGE_FORMAT` pattern. Patrick accepted Karthik’s suggestion to tweak a code comment for clarity, removing the word "Likewise" to avoid over-coupling the object storage logic to the ref storage logic. This minor adjustment has no impact on functionality or the broader architectural debate. The series awaits Junio’s assessment of the unresolved design question before integration.

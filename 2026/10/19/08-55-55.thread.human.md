This thread is about Patrick Steinhardt’s seven-patch series introducing `extensions.objectStorage`, a mechanism to make Git’s object database pluggable so that alternative backends (like cloud storage or databases) can be used. The series defines the configuration interface, implements the baseline `files` backend (which supports relocating the `.git/objects` directory), and adds tools to inspect the configured backend. It also ensures submodules inherit the parent repository’s object storage settings and disables local clones when either the source or destination uses a non-default backend—a pragmatic limitation to avoid complexity in this initial version.

The series is under review, with Karthik Nayak as the primary reviewer so far. Karthik has raised design questions about path normalization, naming consistency in inspection tools, and whether the default backend should be exposed in the code. Patrick has addressed most of these, though some—like renaming `object.format` to `objects.format` for clarity—are deferred due to their scope. The latest exchange focuses on test coverage: Karthik suggested a more exhaustive test matrix for the `GIT_OBJECT_STORAGE_FORMAT` environment variable, but Patrick argued that the combinatorial space would be excessive. They agreed to focus on one concrete gap—testing invalid path payloads for the `files` backend—but Patrick noted that the concept of an "invalid path" may change if the backend later relaxes its directory-creation rules. The series remains uncontroversial, with no objections or conditional approvals yet.

Key open questions include whether the `files` backend should normalize paths to absolute (like the ref storage extension does), how to handle the naming subtlety between `object.format` and `objects.storageFormat` in `git repo` output, and whether the default backend should be hidden from inspection tools. The local clone restriction may also attract discussion about whether it’s too conservative. The series builds on two prerequisite topics (already merged) and follows the established pattern for ref storage extensions. No merge status has been reported.

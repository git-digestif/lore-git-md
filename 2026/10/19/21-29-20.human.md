This is a **substantive review** of the second patch in Patrick Steinhardt’s seven-part series introducing Git’s new `extensions.objectStorage` mechanism, which lays the groundwork for pluggable object database backends. The patch itself implements the core configuration infrastructure, allowing users to specify an object storage backend (currently only `files`) via a URI-style format like `files://payload`.

Karthik Nayak’s review focuses on three technical points. First, he questions whether the `files` backend should use `strbuf_realpath()` to resolve relative paths, mirroring the behavior of the ref storage extension. This is a reasonable consistency concern, though the patch currently handles relative paths by prepending the repository’s commondir (e.g., `files://objs` becomes `.git/objs`). Second, he flags an unnecessary `#include "gettext.h"` in `odb/source.c`, which the patch does not appear to use. Finally, he suggests expanding the test coverage to include both valid and invalid payloads for the `files` backend, including absolute and relative paths, and questions whether the `DEFAULT_REPO_FORMAT` prereq is still needed when the tests explicitly set `core.repositoryformatversion=1`.

The review is constructive and narrowly scoped to implementation details rather than the broader design. None of the points raise fundamental objections, but the payload-handling and test-coverage suggestions could improve robustness. The thread remains uncontroversial, with no prior objections to the series’ direction. If you’re following the object storage extension effort, this patch is a key piece of the puzzle and worth monitoring for how these details are resolved.

This is a performance-focused bugfix for `git log --follow` in complex merge histories. The patch addresses a severe regression introduced in commit 304812ed33 (June 2026), where `--follow` became unusably slow—turning a 28-second operation into nearly 7 minutes—when tracking file renames through non-linear history.

The core issue was that the original fix added a new `propagate_follow_pathspec_to_parent()` function that performed expensive rename detection against *every* parent of *every* commit, even when unnecessary. Miklos Vajna’s v2 patch removes this function entirely and instead reuses the existing diff machinery in `log_tree_diff()`. The new approach first checks for parents where the path is unchanged (without rename detection), and only falls back to full rename detection if the path differs in all parents. This restores performance to near-original levels (37 seconds in the test case) while preserving correctness.

The patch also handles edge cases that were previously untested: it ensures `--follow` works with `-c`, `--cc`, and `--remerge-diff` options, and correctly follows renames on the side of a merge that wasn’t taken (e.g., when a merge keeps file F from one parent but the other parent renamed F to G). The test suite additions cover these scenarios explicitly.

The implementation is thorough—201 lines changed in `log-tree.c` and 112 new test lines—but the commit message clearly explains the trade-offs and performance wins. The patch looks well-motivated and addresses a real pain point for users working with large repositories like linux.git. Given the regression’s severity and the careful handling of edge cases, this is likely to be uncontroversial and worth merging.

This is the second patch in a two-patch bugfix series for `git imap-send`. The series addresses a real interoperability problem: `git imap-send` currently fails when processing patches where the `Subject` header appears before the `Date` header, a valid but non-canonical order produced by tools like `b4` (used to fetch patches from lore.kernel.org). This patch is the core fix, rewriting the header-parsing logic in `imap-send.c` to accept headers in any order rather than requiring a fixed sequence.

The change is minimal and targeted. The old code assumed headers would appear in a specific order (`From`, `Date`, `Subject`) and would break if they didn’t. The new implementation scans all headers first, checks for the presence of the three required headers (`From`, `Date`, `Subject`), and then processes them regardless of order. This matches the behavior of other email tools and ensures compatibility with patches fetched via `b4`. The commit message notes that this also makes a special case in `git send-email` (added in 2025) redundant, as the copy it pipes to `imap-send` will now pass the same check.

The patch includes a thorough test in `t/t9001-send-email.sh` that verifies the fix by sending a patch with `Subject` before `Date` and confirming it is accepted. The test also checks that the `--imap-sent-folder` functionality (which stores a copy of sent patches in an IMAP folder) continues to work, ensuring no regressions in existing workflows. The test coverage looks solid, exercising both the new code path and the existing one.

This is a well-crafted, uncontroversial bugfix. The problem is clearly motivated (interoperability with `b4`/`lore`), the solution is straightforward, and the test ensures it won’t regress. The patch touches only `imap-send.c` and the test script, with no on-disk format changes or broader implications. It should be an easy merge once review is complete.

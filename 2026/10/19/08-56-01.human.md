This is the sixth patch in Patrick Steinhardt’s seven-part series introducing the **object storage extension**, a major architectural change enabling pluggable object database backends in Git. This patch adds the `--object-storage-format=` option to `git clone`, mirroring the functionality already added to `git init` in the previous patch.

The implementation is straightforward: the new option lets users specify the object storage backend (e.g., `files://objs`) when cloning a repository. The patch also handles the interaction with `--local` clones, which hardlink objects from the source repository. Since hardlinking only works with the default `files` backend, the code either downgrades to a non-local clone (with a warning) or fails outright if the user explicitly requested `--local`. The patch explicitly defers handling the edge case where the `files` backend is configured with a non-default object directory path (e.g., `files:///path/to/dir`), leaving that for future work.

Tests cover the expected scenarios: cloning with the `files` backend (with and without a payload), rejecting invalid formats, and verifying that `--local` clones fail when either repository uses a non-default backend. The documentation update is minimal but clear, noting the fallback behavior for local clones.

This patch is uncontroversial in isolation and follows the established pattern set by the ref storage extension. The only potential point of discussion is the decision to bail on `--local` clones rather than attempting to handle alternative object directory paths, but the commit message justifies this as a simplification for now. The implementation looks solid, with thorough test coverage and careful attention to edge cases.

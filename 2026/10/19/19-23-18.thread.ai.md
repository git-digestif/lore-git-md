Subject: [PATCH] status: default to comparing against both @{upstream} and @{push}
Series version: v2 (addresses v1 feedback; next iteration likely required to resolve philosophical justification debate)
Originating author: Harald Nordgren
Thread type: feature patch

Core problem or goal
Make `git status` more useful in triangular workflows by defaulting to comparing the current branch against *both* `@{upstream}` and `@{push}` instead of only `@{upstream}`. The v2 commit message provides historical context: the 2026 commit (3ea95ac9c5) made the feature opt-in due to noise concerns, with the intention of revisiting the default later. Harald argues this change benefits less experienced users who may not realize they are missing upstream information when switching to a triangular workflow. The discussion has expanded into a **philosophical and cultural debate** about whether Git should adapt its defaults to accommodate users shaped by GitHub’s fork-and-pull model (Harald’s position) or resist such changes to avoid reinforcing broken mental models of Git’s branching concepts (Junio’s critique). Junio now proposes an alternative: external tools (e.g., GitHub’s UI or documentation) should promote the necessary configuration (`status.compareBranches = @{upstream},@{push}`) alongside the `-u` flag, shifting the burden of adaptation away from Git itself.

Current status
Under review; v2 addresses all technical feedback from v1 but **reopens and deepens the core justification debate** with new philosophical and pragmatic dimensions. Junio challenges the patch’s underlying assumption that comparing against both `@{upstream}` and `@{push}` by default is universally beneficial, arguing that `@{push}` is typically under the user’s control and thus less likely to introduce "surprises" that warrant default monitoring. He further critiques the cultural context, suggesting that GitHub’s influence may lead users to lack foundational understanding of Git’s branching, creating a "sad world" where defaults must accommodate broken mental models. Harald counters that users often set their push branch to match upstream initially (via `git push -u`), leaving them unaware of upstream changes until they explicitly reconfigure their workflow, at which point the sudden appearance of upstream status can feel disruptive. In his latest reply, Harald dismisses Junio’s "sad world" framing as idealistic, arguing that the project should pragmatically adapt to users’ existing mental models rather than resist them. Junio’s newest reply offers a counterproposal: external tools (e.g., GitHub) should promote the configuration alongside the `-u` flag, preserving internal consistency for triangular workflow users without disrupting existing workflows or imposing the change on all users. The escape hatch (restoring old behavior via config) is dismissed by Junio as insufficient justification for flipping the default. No merge status recorded; readiness for merging remains in doubt pending resolution of the justification debate, which now centers on **philosophical, cultural, and pragmatic trade-offs** rather than technical implementation.

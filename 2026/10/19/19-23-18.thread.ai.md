Subject: [PATCH] status: default to comparing against both @{upstream} and @{push}
Series version: v2 (addresses v1 feedback; next iteration likely required to address new substantive objections)
Originating author: Harald Nordgren
Thread type: feature patch

Core problem or goal
Make `git status` more useful in triangular workflows (where the push destination differs from the upstream) by defaulting to comparing the current branch against *both* `@{upstream}` and `@{push}` instead of only `@{upstream}`. When the two destinations resolve to the same branch, only one comparison is shown, preserving the experience for most users. The v2 commit message establishes historical context: the 2026 commit (3ea95ac9c5) made the feature opt-in due to noise concerns, with the intention of revisiting the default later.

Current status
Under review; v2 addresses all substantive feedback from v1 but **reopens the core justification debate**. Junio C Hamano's latest reply challenges the patch's underlying assumption that comparing against both `@{upstream}` and `@{push}` by default is universally beneficial. He argues that `@{push}` is typically under the user's control and thus less likely to introduce "surprises" that warrant default monitoring, undermining the patch's rationale. The escape hatch (restoring old behavior via config) is dismissed as insufficient justification for flipping the default. No technical objections remain, but the patch's readiness for merging is now in doubt pending a stronger argument for the default change. No merge status recorded.

Key technical details
- Files: `remote.c` (appends `@{push}` to the default comparison list), `Documentation/config/status.adoc`, `t/t6040-tracking-info.sh` (new tests for triangular and common-case scenarios), `t/t5505-remote.sh` (unchanged)
- New default: `status.compareBranches` now defaults to `@{upstream},@{push}`
- Backward compatibility: users can restore the old behavior by setting `status.compareBranches` to `@{upstream}`
- No on-disk format changes; no new CLI options; no new symbols
- Test coverage: v2 adds explicit tests for triangular workflows, common-case scenarios, and the escape hatch (restoring old behavior via config)

Open questions and loose ends
1. **Justification for default change**: Junio's reply reopens the debate on whether the benefit of defaulting to `@{upstream},@{push}` outweighs the cost of surprising existing users. The patch's rationale—that users in triangular workflows benefit from seeing both comparisons—is contested on the grounds that `@{push}` is less likely to introduce "surprises" than `@{upstream}`. The escape hatch is dismissed as insufficient justification. Resolution requires either a stronger argument from the author or a shift in maintainer consensus.
2. **Historical context revisited**: Junio's reply implies that the 2026 commit's intention to revisit the default was not a commitment to flip it, but rather to evaluate whether the opt-in feature gained sufficient adoption. The patch's claim that the default was "intended to be revisited" may need clarification or adjustment.

Subject: [PATCH] status: default to comparing against both @{upstream} and @{push}
Series version: v2 (addresses v1 feedback; next iteration likely required to address new substantive objections)
Originating author: Harald Nordgren
Thread type: feature patch

Core problem or goal
Make `git status` more useful in triangular workflows by defaulting to comparing the current branch against *both* `@{upstream}` and `@{push}` instead of only `@{upstream}`. The v2 commit message provides historical context: the 2026 commit (3ea95ac9c5) made the feature opt-in due to noise concerns, with the intention of revisiting the default later. Harald argues this change benefits less experienced users who may not realize they are missing upstream information when switching to a triangular workflow. The discussion has expanded to include a **philosophical critique** of the patch’s premise: Junio C Hamano questions whether the usability gap stems from GitHub’s influence, which may leave users with broken mental models of Git’s branching concepts, rather than a genuine need for default behavior changes.

Current status
Under review; v2 addresses all technical feedback from v1 but **reopens the core justification debate** with a new philosophical dimension. Junio challenges the patch’s underlying assumption that comparing against both `@{upstream}` and `@{push}` by default is universally beneficial, arguing that `@{push}` is typically under the user’s control and thus less likely to introduce "surprises" that warrant default monitoring. He further critiques the cultural context, suggesting that GitHub’s fork-and-pull model may lead users to lack foundational understanding of Git’s branching, creating a "sad world" where defaults must accommodate broken mental models. Harald counters that users often set their push branch to match upstream initially (via `git push -u`), leaving them unaware of upstream changes until they explicitly reconfigure their workflow, at which point the sudden appearance of upstream status can feel disruptive. The escape hatch (restoring old behavior via config) is dismissed by Junio as insufficient justification for flipping the default. No merge status recorded; readiness for merging remains in doubt pending resolution of the justification debate, which now includes both technical and cultural dimensions.

Key technical details
- Files: `remote.c` (appends `@{push}` to the default comparison list), `Documentation/config/status.adoc`, `t/t6040-tracking-info.sh` (new tests for triangular and common-case scenarios), `t/t5505-remote.sh` (unchanged)
- New default: `status.compareBranches` now defaults to `@{upstream},@{push}`
- Backward compatibility: users can restore the old behavior by setting `status.compareBranches` to `@{upstream}`
- No on-disk format changes; no new CLI options; no new symbols
- Test coverage: v2 adds explicit tests for triangular workflows, common-case scenarios, and the escape hatch (restoring old behavior via config)

Resolution requires either (a) a stronger argument from Harald distinguishing between GitHub-induced confusion and legitimate usability gaps, (b) a shift in maintainer consensus, or (c) intervention from another contributor with a tie-breaking perspective.

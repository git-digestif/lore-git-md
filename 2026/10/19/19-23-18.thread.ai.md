Subject: [PATCH] status: default to comparing against both @{upstream} and @{push}
Series version: v3 (addresses v2 feedback; justification refined; philosophical debate remains unresolved)
Originating author: Harald Nordgren
Thread type: feature patch

Core problem or goal
Make `git status` more useful in triangular workflows by defaulting to comparing the current branch against *both* `@{upstream}` and `@{push}` instead of only `@{upstream}`. The v3 commit message strengthens the justification by emphasizing practical benefits: (1) reminding users how their branch differs from the last push when returning to a topic, (2) indicating whether the branch was rebased or rewritten locally (signaling the need for a forced push), and (3) providing quick validation of what is about to be pushed (similar to `sendemail.annotate`). The message also notes that users in triangular workflows often create their own aliases to check divergence between local, upstream, and push branches, suggesting the patch reduces friction for those who already rely on such checks. The new default only affects users who configure `push.default` to `current` or `matching`, or set a custom push refspec; otherwise, the output remains unchanged. The discussion remains a **philosophical and cultural debate** about whether Git should adapt its defaults to accommodate users shaped by GitHub’s fork-and-pull model (Harald’s position) or resist such changes to avoid reinforcing broken mental models of Git’s branching concepts (Junio’s critique). Junio now proposes an alternative: external tools (e.g., GitHub’s UI or documentation) should promote the necessary configuration (`status.compareBranches = @{upstream},@{push}`) alongside the `-u` flag, shifting the burden of adaptation away from Git itself. D. Ben Knoble counters Junio’s skepticism with a **pragmatic, user-centric argument**, describing his own workflow where he frequently checks divergence between local and `@{push}` branches to answer questions like *"Have I rebased lately and need to force-push?"*—questions that arise naturally in triangular setups. Knoble’s personal tooling (`git sbup`, `git rdup`, `git div`) demonstrates that this need is real and widespread among users who work in such workflows, suggesting the patch would reduce friction for those who already rely on similar manual checks.

Current status
Under review; v3 refines the justification and addresses all technical feedback from v2 but **leaves the core philosophical and cultural debate unresolved**. Junio challenges the patch’s underlying assumption that comparing against both `@{upstream}` and `@{push}` by default is universally beneficial, arguing that `@{push}` divergence is less critical to monitor by default because it reflects the user’s own work, not external changes. He critiques the cultural context, suggesting that GitHub’s influence may lead users to lack foundational understanding of Git’s branching, creating a "sad world" where defaults must accommodate broken mental models. Harald counters that users often set their push branch to match upstream initially (via `git push -u`), leaving them unaware of upstream changes until they explicitly reconfigure their workflow, at which point the sudden appearance of upstream status can feel disruptive. In his latest reply, Harald dismisses Junio’s "sad world" framing as idealistic, arguing that the project should pragmatically adapt to users’ existing mental models rather than resist them. Junio’s newest reply offers a counterproposal: external tools (e.g., GitHub) should promote the configuration alongside the `-u` flag, preserving internal consistency for triangular workflow users without disrupting existing workflows or imposing the change on all users. Junio’s latest refinement argues that `@{push}` divergence is less critical to monitor by default because it reflects the user’s own work, not external changes. D. Ben Knoble’s review supports the patch, providing **anecdotal evidence** from his own workflow that the change would reduce friction for users who already rely on similar manual checks. The escape hatch (restoring old behavior via config) is dismissed by Junio as insufficient justification for flipping the default. No merge status recorded; readiness for merging remains in doubt pending resolution of the justification debate, which now centers on **philosophical, cultural, pragmatic, and user-experience trade-offs**, with Junio’s latest reply narrowing the focus to whether `@{push}` divergence is inherently less important than `@{upstream}` divergence.

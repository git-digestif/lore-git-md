This is the third patch in Beat Bolli’s v3 series addressing OpenSSL compatibility in `git imap-send`, but Patrick Steinhardt’s review raises fundamental concerns about its necessity and correctness. The patch adds macros to alias `SSL_set1_dnsname()` to `SSL_set1_host()` for OpenSSL versions below 4.0, preparing for OpenSSL 4.0’s deprecation of `SSL_set1_host()`. However, Patrick argues the patch is **premature and redundant**: the only call to `SSL_set1_host()` was introduced in the preceding commit (patch 2/3), so the compatibility macros should have been part of that patch rather than a separate one.

Patrick also questions the patch’s **technical correctness**. OpenSSL 4.0 replaces `SSL_set1_host()` with two functions: `SSL_set1_dnsname()` for DNS names and `SSL_set1_ipaddr()` for IP addresses. The patch assumes `cfg->host` is always a DNS name, but Patrick points out this may not hold true—if `cfg->host` is an IP address, the patch would silently use the wrong function, potentially breaking hostname verification. This is a **substantive regression risk** in a security-sensitive code path.

Additionally, Patrick suggests the patch’s **error message change** (using `SSL_SET_DNSNAME_FN` to print the correct function name) is unnecessary. Since the function call is already aliased via macro, the error message could simply use `SSL_set1_dnsname()` unconditionally, avoiding conditional logic that adds no value.

The patch is **blocked** by these issues and the unresolved security regression in patch 2/3 (certificate stripping). While the OpenSSL 4.0 compatibility goal is valid, this implementation is flawed and premature. If the series moves forward, the macros should be merged into patch 2/3, and the IP address case must be handled explicitly. For now, this patch is not worth deeper attention until the foundational issues in the series are resolved.

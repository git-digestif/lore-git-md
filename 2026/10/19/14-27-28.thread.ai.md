Subject: [PATCH v2] config: honor file permission bits when writing config files
Series version: v2 (supersedes RFC/PATCH)
Originating author: Junio C Hamano
Thread type: bugfix proposal

Core problem or goal
Git currently bypasses filesystem permission checks when writing configuration files via its lockfile-and-rename mechanism. Users expect `chmod a-w .gitconfig` to prevent modification, but Git ignores this and overwrites the file anyway. The goal is to make Git respect write permissions for out-of-tree config files (e.g., `$HOME/.gitconfig`, XDG config), returning an error (`CONFIG_NO_WRITE`) when attempting to write to a read-only file. The author’s workflow (managing dotfiles as read-only installed files) directly motivated this fix. In-tree files (e.g., `.git/config`, `.git/index`) are explicitly out of scope, as users have no sensible reason to "protect" them from Git, and existing read-only bits under `.git/objects/` serve a different purpose (preventing accidental overwrites by external tools). Junio’s rationale for this scope—out-of-tree files are uniquely vulnerable because they reside outside the repository—is now documented in the commit message, addressing Patrick Steinhardt’s request for clarification. Junio has further clarified that the mutability of repository contents is self-evident and that users should not use filesystem tools to manage Git’s internal files, reinforcing the exclusion of in-tree files.

Key technical details
- Files touched: `config.c`, `t/t1300-config.sh`
- New error code: `CONFIG_NO_WRITE`
- Modified function: `repo_config_set_multivar_in_file_gently()`
- New behavior: `access(2)` check before lockfile creation; returns `CONFIG_NO_WRITE` if file is unwritable. The check is limited to out-of-tree config files (e.g., `$HOME/.gitconfig`, XDG config), excluding in-tree files like `.git/config`.
- Test coverage: verifies read-only config files can still be read but reject writes and unsets; uses `GIT_CONFIG_GLOBAL` to avoid modifying user config.
- Subsystem: config subsystem (global, local, system-level config writes).
- Edge cases noted: filesystem race conditions, symbolic links, NFS/remote filesystems (still unresolved).
- Lockfile API: The patch intentionally avoids modifying `lockfile.c` to sidestep the need to audit all lockfile users (reflogs, index files, hooks). The commit message documents this rationale, addressing Patrick Steinhardt’s review.
- Error-message formatting: `error_errno()` in `config.c` inconsistently quotes its filename argument; Junio acknowledges the inconsistency but defers a broader cleanup to avoid test churn.

Open questions and loose ends
- Alternative error-handling approaches (e.g., different error codes, warnings instead of hard errors).
- Backwards compatibility: whether existing scripts/tools expect config writes to succeed regardless of permissions.
- Robustness of `access(2)` check in the face of race conditions, symlinks, and network filesystems.
- Coding-style nit: `error_errno()` in `config.c` inconsistently quotes its filename argument; Junio defers this to a future cleanup.
- Documentation nit: commit message now sufficiently explains *why* in-tree files are excluded (users have no sensible reason to make them read-only, and `.git/objects/` already uses read-only bits for a different purpose).

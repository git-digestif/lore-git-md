Subject: [RFC/PATCH] config: honor file permission bits when writing config files
Series version: RFC/PATCH (initial version)
Originating author: Junio C Hamano
Thread type: bugfix proposal

Core problem or goal
Git currently bypasses filesystem permission checks when writing configuration files via its lockfile-and-rename mechanism. Users expect `chmod a-w .gitconfig` to prevent modification, but Git ignores this and overwrites the file anyway. The goal is to make Git respect write permissions, returning an error (`CONFIG_NO_WRITE`) when attempting to write to a read-only config file. The author’s workflow (managing dotfiles as read-only installed files) directly motivated the discovery of this inconsistency.

Current status
Under review (RFC/PATCH posted). No prior versions. No merge status reported. Author has noted the lack of responses in two separate emails, but Patrick Steinhardt’s substantive review now raises a fundamental architectural question that may reshape the patch’s scope.

Key technical details
- Files touched: `config.c`, `t/t1300-config.sh`
- New error code: `CONFIG_NO_WRITE`
- Modified function: `repo_config_set_multivar_in_file_gently()`
- New behavior: `access(2)` check before lockfile creation; returns `CONFIG_NO_WRITE` if file is unwritable
- Test coverage: verifies read-only config files can still be read but reject writes and unsets; uses `GIT_CONFIG_GLOBAL` to avoid modifying user config
- Subsystem: config subsystem (global, local, system-level config writes)
- Edge cases noted: filesystem race conditions, symbolic links, NFS/remote filesystems (still unresolved)
- Lockfile API: Patrick Steinhardt’s review highlights that the lockfile mechanism is used broadly (reflogs, index files, hooks) and suggests permission checks should be centralized in `lockfile.c` rather than config-specific code

Open questions and loose ends
- Alternative error-handling approaches (e.g., different error codes, warnings instead of hard errors)
- Backwards compatibility: whether existing scripts/tools expect config writes to succeed regardless of permissions
- Whether the lack of prior reviewer feedback indicates implicit approval, lack of interest, or delayed review
- Robustness of `access(2)` check in the face of race conditions, symlinks, and network filesystems
- **New architectural question**: Should permission checks be implemented centrally in `lockfile.c` (affecting all lockfile users) or remain subsystem-specific? This could significantly expand the patch’s scope if addressed
- No substantive review has engaged with the implementation’s correctness, edge cases, or broader implications beyond Patrick’s high-level design concern

Participant positions
- Junio C Hamano (author): proposes the change as a security and usability fix; implementation is straightforward and well-tested. Two follow-up emails reinforce the motivation but do not alter the proposal or withdraw it.
- brian m. carlson: surface-level review acknowledging the patch as sensible but offering no substantive feedback on implementation, edge cases, or broader implications. The review neither endorses nor critiques the technical approach.
- Patrick Steinhardt: **substantive review** challenging the patch’s scope. Argues permission checks should be centralized in `lockfile.c` rather than config-specific code, ensuring consistent behavior across all lockfile users (reflogs, index files, hooks). Feedback is conceptual and forward-looking, focusing on design consistency rather than implementation details. No testing or reproduction of the issue, but the question is high-impact and may drive future discussion.

Related work

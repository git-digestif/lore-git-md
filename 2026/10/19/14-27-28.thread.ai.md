Subject: [RFC/PATCH] config: honor file permission bits when writing config files
Series version: RFC/PATCH (initial version)
Originating author: Junio C Hamano
Thread type: bugfix proposal

Core problem or goal
Git currently bypasses filesystem permission checks when writing configuration files via its lockfile-and-rename mechanism. Users expect `chmod a-w .gitconfig` to prevent modification, but Git ignores this and overwrites the file anyway. The goal is to make Git respect write permissions, returning an error (`CONFIG_NO_WRITE`) when attempting to write to a read-only config file.

Current status
Under review (RFC/PATCH posted). No prior versions. No merge status reported.

Key technical details
- Files touched: `config.c`, `t/t1300-config.sh`
- New error code: `CONFIG_NO_WRITE`
- Modified function: `repo_config_set_multivar_in_file_gently()`
- New behavior: `access(2)` check before lockfile creation; returns `CONFIG_NO_WRITE` if file is unwritable
- Test coverage: verifies read-only config files can still be read but reject writes and unsets
- Isolation: test uses `GIT_CONFIG_GLOBAL` to avoid modifying user config
- Subsystem: config subsystem (global, local, system-level config writes)

Open questions and loose ends
- Alternative error-handling approaches (e.g., different error codes, warnings instead of hard errors)
- Edge cases: filesystem race conditions, symbolic links, NFS/remote filesystems
- Backwards compatibility: whether existing scripts/tools expect config writes to succeed regardless of permissions

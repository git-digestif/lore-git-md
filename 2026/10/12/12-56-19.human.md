This is a follow-up to René Scharfe’s patch that fixes the ZIP extended timestamp wrap issue (bug #2 in the thread). Matthew E. Luallen confirms the patch works as intended: it omits the Extended Timestamp (UT) extra field for out-of-range commit times, preventing the silent timestamp wrap that caused tools like UnZip to misbehave in update mode. His testing shows the fix resolves the specific case where a 2106 commit would previously wrap to 1970, causing UnZip to retain outdated files instead of updating them.

The email also addresses the CI breakage Junio C Hamano reported on 32-bit platforms. Matthew identifies the root cause: the tests incorrectly use `TIME_IS_64BIT` (which checks Git’s `timestamp_t`) instead of `TIME_T_IS_64BIT` (which checks the system’s `time_t`). On some 32-bit systems, Git’s `timestamp_t` is 64-bit while `time_t` remains 32-bit, causing the tests to fail when `zipinfo(1)` lacks UT field support. His proposed two-line fix adjusts the test prerequisites, ensuring the tests pass on x86-64 Linux and skip gracefully on 32-bit platforms where `zipinfo` is insufficient.

This is a **substantive, well-tested fix** for a real bug with clear tool compatibility implications. The patch itself is narrowly scoped to the UT extra field, but Matthew’s feedback advances the broader discussion by resolving the test infrastructure issue that blocked integration. The remaining open questions—how to handle the ZIP legacy DOS date overflow (bug #1) and `fast-import` negative timestamps (bug #3)—are unaffected by this change. The patch is ready for a v2 update with the test prerequisite fix, and the thread’s focus can now shift to the unresolved policy debates.

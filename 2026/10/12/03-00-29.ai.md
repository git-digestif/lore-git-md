This is a documentation patch updating the `SubmittingPatches` guidelines to explicitly discourage the anti-pattern of splitting a test and its corresponding bugfix into separate commits. The v2 patch incorporates Junio C Hamano’s feedback from v1, replacing the original phrasing with a more direct sentence: *"A bugfix patch should include tests in `test_expect_success()` blocks that demonstrate the breakage when the code change that implements the fix is omitted."*

The patch is narrowly scoped, touching only the `Documentation/SubmittingPatches` file. It formalizes an existing reviewer preference—avoiding the "add a failing test (`test_expect_failure`) then fix it in a later commit" workflow—by making it an explicit guideline. The rationale is pragmatic: splitting the test and fix obscures the behavior being tested from the diff context, making reviews harder. The new text clarifies that while `test_expect_failure` may still be useful during local development, submitted patches should combine the test and fix into a single commit. Reviewers can verify the test reproduces the bug by temporarily reverting the code changes while keeping the test.

The patch is uncontroversial and aligns with the project’s emphasis on self-contained, reviewable commits. It does not introduce new technical concepts or change on-disk formats, but it reinforces key terms like `test_expect_success`, `test_expect_failure`, and "diff context," which may recur in future discussions about test practices. The author, Jon Simons, is not a frequent contributor, but the patch reflects a well-established norm rather than a new proposal. Junio’s feedback was substantive, focusing on clarity and removing any ambiguity about whether `test_expect_failure` is acceptable in submitted patches.

The patch is ready to proceed, pending Junio’s final review. It is unrelated to ongoing efforts like test modernization or `clar` adoption, focusing solely on improving review workflows. The mailing list recipients—Kristoffer Haugsbakk (documentation), Junio (maintainer), and Patrick Steinhardt (prolific contributor)—suggest the patch is intended for broad visibility. The tone remains collaborative, framing the change as an optimization rather than a rigid rule.

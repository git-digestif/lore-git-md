This is a **performance feature** introducing an incremental connectivity check for Git fetches and pushes, now split into a four-patch series (v3). The goal remains reducing the cost of verifying object connectivity in large repositories by shifting the workload from repository size to incoming change size. The new mode is opt-in via `transfer.connectivityCheck=incremental`.

The series now organizes the work more cleanly: patch 1/4 adds comprehensive documentation (`Documentation/technical/connectivity-check.adoc`), patch 2/4 establishes baseline performance tests, patch 3/4 introduces the config key and `rev-list` flag plumbing, and patch 4/4 implements the incremental verifier in `tree-verify.c`. This split addresses Patrick Steinhardt’s review feedback about reviewability and staleness risks in documentation.

Key technical details include the inductive trust model (parent trees trusted, new trees verified only where differing), reuse of the existing `--not --all` boundary-detection mechanism, and fallback to the full check for deepening fetches or very long histories (10,000+ commits). The implementation adds 316 lines in `tree-verify.c` and integrates with the existing `check_connected()` subprocess architecture, avoiding lazy-fetch issues in partial clones. Benchmarks show dramatic speedups (up to 190x faster, 14 MB vs. 3.4 GB memory) for small pushes to large repos, with modest regressions (1.5x slower) for very long incoming histories—an acceptable tradeoff for an opt-in feature.

The documentation now explicitly states the reverse connectivity invariant (unreachable objects are untrusted), removes code references to reduce staleness, and clarifies the trust boundary mechanism. Test coverage (`t5413-connectivity-check.sh`) verifies semantic equivalence with the full check, corruption detection, promisor object handling, and integration with fetch/push/clone. The series is rebased onto latest master (resolving a meson.build conflict) and renumbers tests to avoid collisions.

This v3 addresses all prior feedback: Junio’s NULL-dereference and lazy-fetch concerns, Patrick’s documentation and implementation questions, and the suggestion to split the patch. The incremental mode is now production-ready behind its opt-in config, with future work (MIDX-based connectivity closure, parallel ref loading) explicitly out of scope. The series is under active review and likely to land soon.

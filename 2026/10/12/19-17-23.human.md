This is the first patch in a two-part feature series that hardens Git’s ignore-revs parser and tag-peeling logic ahead of making `HEAD:.git-blame-ignore-revs` the default ignore file for `git blame` and `git annotate`. The hardening is a prerequisite for the upcoming default file lookup (patch 2/2) and addresses two security concerns that arise when parsing upstream-controlled content at a well-known path.

The patch adds two key protections. First, it rejects any line in an ignore-revs file that contains an embedded NUL byte, preventing silent truncation of object names or comments. The check uses `memchr()` to scan the entire line buffer before stripping comments or whitespace, ensuring that malformed input like `<oid>\0garbage` or `<oid>\0# comment` is caught early. Second, it prevents promisor fetches in partial clones by using `odb_read_object_info_extended()` with `OBJECT_INFO_SKIP_FETCH_OBJECT` and `OBJECT_INFO_QUICK`, and verifies each tag’s declared type before parsing. This ensures that missing tag targets or malformed tags in the ignore-revs file do not trigger network requests or pack directory rescans.

The changes are confined to `builtin/blame.c` (tag-peeling logic) and `oidset.c` (parser hardening), with new tests in `t/t8013-blame-ignore-revs.sh` covering NUL-byte rejection and chained-tag peeling. The tests use `q_to_nul` to generate NUL-containing input and verify that the parser dies with a clear error message. The tag-peeling test also confirms that missing tag targets in partial clones are skipped without error, preserving blame’s output.

This patch is well-motivated and narrowly scoped. The hardening is a direct response to the threat model introduced by the default file lookup, and the implementation is careful to avoid regressing existing behavior. The commit message clearly explains the risks and the chosen mitigations, and the tests cover both the happy path and edge cases. No objections have been raised since the v4 revision, and Junio has already approved the series for `next`. The only remaining discussion is whether to retain the NUL-byte check (the author has signaled flexibility), but this is a minor detail rather than a blocker.

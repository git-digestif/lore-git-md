This is a maintainer feedback message on René Scharfe’s patch that omits the ZIP Extended Timestamp (UT) extra field when the commit time exceeds 32-bit range. Junio reports that the new tests fail on 32-bit platforms (Ubuntu 20.02 i386 and Debian/latest i386) in GitHub CI. The failures occur in the two new test cases that verify the presence or absence of the UT extra field using `zipinfo -v`.

The issue appears to be platform-specific: the tests assume that `zipinfo` on 32-bit systems can still parse and report the UT extra field, but the CI failures suggest this is not the case. The patch itself is not broken—it correctly omits the UT field for out-of-range timestamps—but the test infrastructure on 32-bit platforms may lack support for the UT extra field, causing the `ZIPINFO_UT_EXTRA` prerequisite to fail. This is a test portability problem, not a flaw in the patch logic.

The patch is part of the ongoing effort to resolve ZIP timestamp inconsistencies reported by Matthew E. Luallen. It addresses the extended timestamp wrap issue (bug #2 in the thread) by omitting the UT field for out-of-range values, a solution that has converged on rejection (omission) over clamping. The broader thread still has two open issues: the ZIP legacy DOS date overflow (bug #1) and `fast-import` negative timestamp validation (bug #3), but this feedback is narrowly focused on the test failures for the UT field fix.

This is a **surface-level review** from the maintainer, flagging a CI failure that needs attention before the patch can proceed. The fix will likely involve adjusting the test prerequisites or skipping the UT field checks on 32-bit platforms where `zipinfo` support is unreliable. The patch remains well-motivated and technically sound, but the test suite needs to be made more portable.

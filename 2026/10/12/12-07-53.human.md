This is the **v3 patch series** for the incremental connectivity check feature, now split into four patches for better reviewability. The series introduces an opt-in `transfer.connectivityCheck=incremental` configuration that reduces the cost of verifying object connectivity during fetches and pushes by processing incoming commits incrementally rather than walking the full boundary closure.

The core idea remains unchanged: the incremental mode verifies each incoming commit’s tree against its parents’ trusted trees, skipping unchanged subtrees. This shifts the cost from being proportional to repository size to being proportional to the size of the incoming changes. The v3 series addresses all prior feedback from Junio C Hamano and Patrick Steinhardt, including documentation clarifications, NULL-dereference guards, and a more modular implementation. The implementation is now split into four patches: (1) documentation, (2) performance test baseline, (3) config plumbing and `rev-list` flag, and (4) the incremental verifier itself.

Key improvements in v3 include a rewritten documentation file (`Documentation/technical/connectivity-check.adoc`) that explicitly states the reverse of the connectivity invariant (unreachable objects are untrusted), removes code references to reduce staleness, and clarifies the trust model. The incremental verifier’s boundary detection mechanism is now confirmed to reuse the same `--not --all` logic as the full check, ensuring correctness without parsing all refs upfront. The series also adds a new performance test script (`t/perf/p5413-connectivity-check.sh`) that benchmarks both modes across repository size, incoming commit count, and files changed per commit.

The benchmarks show dramatic speedups for small pushes to large repositories (up to 190x faster for a single commit in a 3.4 GB boundary closure) with minimal memory overhead (14 MB vs. 3.4 GB). The incremental mode does regress slightly (1.5x slower) for very long incoming histories (10,000+ commits), but the author argues this is an acceptable tradeoff for an opt-in feature targeting the common case. Deepening fetches still fall back to the full check, as the incremental approach would require separate work. The implementation is well-tested, with extensive correctness tests in `t5413-connectivity-check.sh` covering corruption detection, promisor object handling, and integration with fetch/push/clone.

This series looks ready for further review. The split into smaller patches and the thorough documentation make it easier to assess, and the benchmarks demonstrate clear performance benefits for the target use case. The incremental mode is a conservative, opt-in change that maintains semantic equivalence with the full check while addressing a real scalability pain point.

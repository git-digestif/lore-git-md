This is the first patch in Christian Couder’s v3 series introducing a new `parse-options` sub-API for early argument scanning. It is a **refactoring patch** that extracts the logic for determining whether an option takes an argument into a reusable helper, `parse_options_takes_argument()`.

The patch addresses a specific need in the existing codebase: `show_gitcomp()` (the function that generates shell completions for Git commands) currently open-codes the logic for deciding whether an option consumes the next argument. This logic is complex—it depends on the option’s type (e.g., `OPTION_STRING`, `OPTION_INTEGER`) and its flags (e.g., `PARSE_OPT_NOARG`, `PARSE_OPT_OPTARG`, `PARSE_OPT_LASTARG_DEFAULT`). The new helper encapsulates this logic, making it available for reuse in the upcoming `early_scan_options()` API.

The implementation is straightforward: `parse_options_takes_argument()` returns 1 if the option takes a value (and thus consumes the next argument when not stuck with `=`), and 0 otherwise. The function handles edge cases like `PARSE_OPT_LASTARG_DEFAULT` options, which only consume the next argument if it isn’t the last one. The commit message notes that this behavior is intentional for early scanning, where callers can easily check for a next argument, but `show_gitcomp()` still treats such options as not requiring an `=` suffix in completions.

The patch is **clean and uncontroversial**, with no behavior changes—it merely moves existing logic into a shared function. The diff is minimal and focused, touching only `parse-options.c` and `parse-options.h`. This refactoring is a prerequisite for the core API patch (2/4), which will use the helper to skip option arguments during early scanning. The commit message clearly explains the motivation and edge cases, making it easy to review.

This patch is **ready for `next`** and should not hold up the series. The real discussion will center on the API design in the follow-up patches, particularly how callers handle argument skipping.

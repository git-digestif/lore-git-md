This is a **test infrastructure follow-up** to René Scharfe’s ZIP archive patch, now **fully unblocked for integration**. Junio C Hamano acknowledges Matthew E. Luallen’s fix for the 32-bit test failures: replacing `TIME_IS_64BIT` with `TIME_T_IS_64BIT` in the test prerequisites. The change is trivial but critical—it ensures the tests skip correctly on platforms where `time_t` is 32-bit (e.g., i386), even if Git’s internal `timestamp_t` is 64-bit.

Junio’s reply clarifies why the original prerequisite was problematic: `TIME_IS_64BIT` checks Git’s `timestamp_t` (always `uintmax_t`, effectively 64-bit everywhere), while `TIME_T_IS_64BIT` checks the system’s `time_t`, which determines whether tools like `zipinfo(1)` can handle extended timestamps. The distinction matters for portability, as 32-bit systems may lack UT field support entirely. He also flags a broader `#leftoverbits` question: whether Git should warn when truncating `timestamp_t` values to `time_t` for external formats like ZIP. This isn’t a blocker for the current patch but could inform future refactoring.

The patch itself—omitting the ZIP Extended Timestamp (UT) field for out-of-range commit times—is now **technically complete and ready for `next`**. The test fix resolves the last CI hurdle, and Junio’s sign-off suggests it will likely graduate soon. The thread’s two remaining open issues (ZIP legacy DOS date overflow and `fast-import` negative timestamps) are unaffected by this change.

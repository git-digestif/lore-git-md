This is the first patch in a four-part series introducing an **incremental connectivity check** for Git fetches and pushes. It adds a new technical document (`Documentation/technical/connectivity-check.adoc`) that explains the connectivity invariant and how the existing full connectivity check works.

The document is thorough and well-structured, covering the core invariant (every object reachable from references must be locally available), exceptions like submodules and promisor objects, and the mechanics of the full check. It includes a clear example graph illustrating the boundary between incoming and already-connected commits, which helps clarify how `--not --all` establishes the trust boundary. The explanation of deepening fetches and non-commit tips (tags, trees, blobs) rounds out the documentation, making it a solid foundation for the rest of the series.

This patch directly addresses prior feedback from Patrick Steinhardt, who emphasized the need for precise, maintainable documentation that avoids staleness by not referencing code internals. The author has delivered on that: the document is self-contained, focuses on concepts rather than implementation details, and explicitly states the reverse connectivity invariant (unreachable objects are untrusted). The 110-line addition is a clean, focused explanation that will help reviewers and future contributors understand the feature’s design goals.

For a busy reader, this patch signals that the series is well-motivated and thoughtfully documented. The incremental check itself isn’t introduced here—it’s covered in later patches—but this document provides the necessary context to evaluate whether the performance trade-offs (dramatic speedups for small pushes to large repos, modest regressions for very long histories) are justified. If the rest of the series holds up to the same standard, this looks like a production-ready feature behind its opt-in config.

This is the final patch (4/4) in Kristofer Karlsson’s four-part series introducing an **incremental connectivity check** for Git fetches and pushes. The series is a **performance feature** that reduces the cost of verifying object connectivity by shifting the workload from repository size to incoming change size.

This patch implements the core incremental verifier in a new file, `tree-verify.c`. The algorithm processes incoming commits in topological order, comparing each new tree against its trusted parent trees. Unchanged subtrees are skipped by OID, so only modified or new objects are verified. The implementation reuses Git’s existing `--not --all` boundary-detection mechanism and falls back to the full check for edge cases like deepening fetches, very long histories (10,000+ commits), shallow boundaries, and promisor objects. The new mode is opt-in via `transfer.connectivityCheck=incremental` and preserves partial-clone semantics by excluding promisor objects from traversal.

The patch adds 316 lines of C code in `tree-verify.c`, plus integration hooks in `builtin/rev-list.c` and `connected.c`. The verifier tracks tree OIDs in three states (untrusted, trusted, expanded) and uses a merge-walk to collect same-path parent subtrees as comparison bases. Trace2 instrumentation measures trees loaded and blobs checked, and the test suite (`t5413-connectivity-check.sh`) verifies semantic equivalence with the full check, corruption detection, promisor object handling, and integration with fetch/push/clone. Benchmarks show dramatic speedups (up to 190x faster, 14 MB vs. 3.4 GB memory) for small pushes to large repos, with modest regressions (1.5x slower) for very long incoming histories—an acceptable tradeoff for an opt-in feature.

The series has addressed all prior feedback from Junio C Hamano (NULL-dereference and lazy-fetch concerns) and Patrick Steinhardt (documentation and implementation questions). The incremental mode is production-ready behind its opt-in config, and the patch is well-structured, thoroughly tested, and clearly motivated. This is a **high-quality contribution** that directly targets a real scalability pain point in large repositories. The series is under active review and likely to land soon.

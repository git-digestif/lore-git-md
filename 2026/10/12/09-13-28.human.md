This is a **substantive review** of the `git blame` default ignore-revs file feature, specifically targeting the second patch in the v3 series. Phillip Wood raises two usability and security concerns about the current implementation:

1. **Uncommitted changes handling**: The patch ignores uncommitted modifications to `.git-blame-ignore-revs` in non-bare repositories, always reading the committed `HEAD` blob instead. This is inconsistent with how `.gitattributes` behaves (which respects uncommitted changes) and may inconvenience users testing local modifications. Phillip flags this as unintuitive and potentially frustrating for workflows where developers iterate on blame annotations before committing.

2. **Scalability and security**: The implementation loads the ignore-revs file without enforcing a size limit, which could theoretically allow memory exhaustion from maliciously large blobs. While the `oidset` implementation uses 32-bit integers for entry counts (limiting the file to ~4 billion entries), the lack of an explicit size cap remains a loose end. This is less likely to be a practical issue but still worth addressing for robustness.

The review is **medium-weight**—it doesn’t challenge the core functionality or security hardening (e.g., promisor fetch prevention, tag type verification) but highlights edge cases that could affect user experience. Phillip’s feedback aligns with his earlier comments on the thread, where he also noted the absence of subdirectory support for `.git-blame-ignore-revs` (though he acknowledges this would be expensive to implement). His concerns are framed as usability refinements rather than blockers, but they’re concrete enough to warrant attention before the series graduates to `master`.

Junio has already marked the series ready for `next`, so these points are likely to be addressed in a follow-up patch rather than a v4. The author (Ravi Mistry) has previously signaled flexibility on similar issues (e.g., the NUL-byte check), so these adjustments may be straightforward.

This is a **feature patch follow-up** in the ongoing `git blame` ignore-revs series. The author, Ravi Mistry, responds to Phillip Wood’s review of the second patch in the v3 series, which implements the default `HEAD:.git-blame-ignore-revs` lookup.

Ravi explains that the current implementation reads the *committed* `HEAD:.git-blame-ignore-revs` blob (not the working-tree file) in non-bare repositories, a design choice made in v2 based on Junio’s feedback. While this aligns with the hosting-platform convention (GitHub, GitLab, etc.), it diverges from Git’s usual behavior for special files like `.gitattributes`, which respect uncommitted changes. Ravi acknowledges Phillip’s usability concern but defers to Junio’s earlier guidance, leaving the door open for further adjustment if the maintainer prefers.

On the subtree question, Ravi agrees that scanning all directories for `.git-blame-ignore-revs` would be too expensive and reaffirms the ecosystem convention of reading the file only from the repository root. Regarding Phillip’s scalability concern, Ravi clarifies that the `oidset` parser already filters out non-existent or duplicate OIDs, so the set cannot grow larger than the number of local commits. However, he offers to add an explicit blob-size cap (like `.gitattributes`) if Junio or Phillip prefer.

The patch remains **approved for `next`**, but this exchange highlights two minor loose ends: (1) whether to respect uncommitted changes in non-bare repositories, and (2) whether to enforce a blob-size limit. Neither issue blocks integration, but both could affect user experience. The thread is now waiting on Junio’s final call.

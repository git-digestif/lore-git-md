This is the **performance test suite** for the incremental connectivity check feature, the second patch in the four-part v3 series. It adds a new `t/perf/p5413-connectivity-check.sh` script and a supporting Perl generator to benchmark the `rev-list` connectivity check across three dimensions: total repository size, incoming commit count, and files changed per commit.

The test suite creates synthetic repositories with a flat directory structure (many directories, each containing 100 files) and measures the time taken by `git rev-list --objects --stdin --not --all --exclude-promisor-objects`, which is the exact command used internally by the connectivity check. Each test case varies one parameter while holding the others constant: for example, the first group scales repository size from 5,000 to 800,000 files (50 to 8,000 directories × 100 files), the second scales incoming commit count from 1 to 10,000, and the third scales files changed per commit from 1 to 2,000. The generator script (`generate-repo-p5413-connectivity-check.perl`) produces fast-import streams that create these repositories with minimal overhead, ensuring the benchmarks measure only the connectivity check and not pack transfer or object parsing.

The test design is careful to isolate the connectivity check: it repacks the repository after setup to avoid loose-object overhead, uses `--quiet` to suppress progress output, and runs the command in a subprocess that reads commit OIDs from stdin. The test cases are named and labeled clearly (`repo-50d-100f-10c-50h-10fpc`), making it easy to correlate results with the parameters being varied. This structure directly supports the performance claims in the series: the incremental mode should show dramatic speedups when the incoming change is small relative to the repository size, and modest regressions when the incoming history is very long.

The patch is well-motivated and tightly scoped. It does not implement the incremental mode itself (that is in patch 4/4) but provides the baseline measurements that will be used to evaluate it. The test suite is ready for review and likely to land as-is; it addresses all prior feedback about test coverage and benchmarking methodology. Future work (MIDX-based connectivity closure, parallel ref loading) is explicitly out of scope, so these benchmarks will remain relevant even as the feature evolves.

This is the third patch in the v3 series extending `git branch --delete-merged` to detect squash-merged and rebase-merged branches. The author, Harald Nordgren, replies to Phillip Wood’s substantive review of the squash-merge detection algorithm used in v2.

Harald clarifies the design intent: the current implementation checks whether the upstream commit (C) already contains all the changes introduced by the branch (B), not whether C is *exactly* the squash merge of B. This means C can include additional changes beyond those from B, and the "landed as" attribution in the output may point to a commit that also contains unrelated work. He argues this is acceptable for branch deletion, since no changes are lost, but acknowledges it may be confusing for users who expect "landed as" to point to a pure squash merge.

On rename detection, Harald takes a different stance than Phillip: he considers following renames a poor basis for assuming a branch is merged, since file renames can themselves be the goal of a topic branch. This directly addresses Phillip’s concern about the current algorithm’s limitations (missing rename detection and less strict matching) but frames it as a feature rather than a bug.

The reply does not engage with Phillip’s alternative approaches (patch-ids or test merges) or Junio’s earlier suggestion to locally simulate squash merges. It also does not mention the v3 reorganization that splits rebase and squash detection into separate patches. The core algorithmic question—whether the current tree-based diffing is sufficient—remains open, but Harald’s response suggests he is satisfied with the trade-offs as they stand. This may reduce the likelihood of further algorithmic changes in the near term, though the discussion is far from settled.

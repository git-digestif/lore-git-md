This is a **substantive review** of the second patch in the v3 series that implements default `HEAD:.git-blame-ignore-revs` support for `git blame`. Phillip Wood raises three technical concerns about the current design, all focused on usability and edge-case handling rather than correctness or security.

First, he questions the decision to **ignore uncommitted working-tree changes** to `.git-blame-ignore-revs` in non-bare repositories. The patch currently reads the committed `HEAD:.git-blame-ignore-revs` blob even when a tracked `.git-blame-ignore-revs` file exists in the working tree with local modifications. Phillip argues this is inconsistent with Git’s treatment of other special files like `.gitattributes`, where uncommitted changes are respected. He suggests the default behavior should instead automatically use the working-tree file when it is tracked, making it easier for users to test local modifications without needing to explicitly pass the file path.

Second, he briefly considers whether the feature should **support `.git-blame-ignore-revs` files in subdirectories** (e.g., for subtree-specific ignore lists), but concludes this would be too expensive to implement without scanning all directories containing tracked files.

Third, he raises a **scalability concern**: the patch does not limit the size of the blob being parsed, and the underlying `khash` implementation in `oidset` uses 32-bit integers for entry counts. While he does not claim this is an immediate problem, he flags it as a potential future issue if a repository commits an extremely large ignore-revs file.

Phillip’s feedback is constructive and pragmatic, focusing on user experience and long-term robustness rather than questioning the core feature. His suggestion about respecting uncommitted changes is the most actionable and likely to influence the next revision. The review does not block integration but signals areas where the design could be refined before reaching `master`.

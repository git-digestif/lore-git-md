This is the **feature patch** that implements the second half of Ravi Mistry’s series: making `git blame` and `git annotate` automatically use `HEAD:.git-blame-ignore-revs` as the default ignore-revs file when no explicit file is configured. The patch is now in its **fourth iteration (v4)** and has been **approved by Junio for `next`**.

The core change is straightforward: if the user hasn’t set `blame.ignoreRevsFile` or passed `--ignore-revs-file`, Git now looks for a blob named `.git-blame-ignore-revs` in the `HEAD` tree. If found, it parses that blob’s contents as a list of revisions to ignore, just as it would with a user-specified file. This aligns Git’s local behavior with hosting platforms like GitHub and GitLab, which already respect this file by default.

The patch is careful about edge cases. It skips non-regular tree entries (symlinks, subdirectories), enforces a **100MB size cap** on the blob to prevent memory exhaustion, and ensures user-configured files take precedence over the default. The lookup is intentionally limited to the repository root, matching hosting platform conventions and avoiding performance overhead. The implementation also handles bare repositories and malformed input gracefully, rejecting invalid OIDs and NUL bytes.

One **user-experience trade-off** remains unresolved: the patch always reads the committed `HEAD` blob, ignoring uncommitted changes to `.git-blame-ignore-revs` in the working tree. Junio justifies this as matching hosting site behavior, but Phillip Wood and others have noted it feels unintuitive and inconsistent with how `.gitattributes` works. Ravi has left the door open to revisit this in a future series if the community prefers.

The patch is well-tested, with new tests covering the default file lookup, size cap, and edge cases. It touches `builtin/blame.c`, `oidset.c`, and documentation, and integrates cleanly with the security hardening in the first patch of the series. The **100MB size cap** (added in v4) addresses Junio’s explicit concern about memory exhaustion from maliciously large blobs, making the feature robust for untrusted repositories.

This is a **small but polished feature** that brings local Git behavior in line with hosting platforms. It’s ready for `next` and unlikely to generate further controversy, though the uncommitted-changes issue may resurface in future discussion.

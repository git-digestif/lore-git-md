This is a **bugfix follow-up** for the ZIP archive subsystem, specifically addressing a 32-bit platform regression in René Scharfe’s patch that omits the ZIP Extended Timestamp (UT) extra field for out-of-range commit times. The patch itself is sound—it resolves a silent timestamp wrap issue by omitting the UT field when the commit time exceeds 32-bit signed integer range—but the accompanying tests fail on 32-bit systems (Ubuntu 20.02 i386 and Debian i386) due to an unrelated preexisting bug in Git’s `dos_time()` function.

The failure occurs when `git archive` is called with `--mtime="@2147483648 +0000"` (the first timestamp exceeding 32-bit range). The error message, *"fatal: timestamp too large for this system: 18446744071562067968"*, reveals a bug in `dos_time()`’s time_t conversion logic, which incorrectly handles large timestamps on 32-bit platforms. This is not a flaw in René’s patch but a latent issue in the ZIP export code that surfaces only when testing the new UT field omission logic. René plans to investigate and fix the `dos_time()` bug separately.

The test failures are unrelated to the core fix (omitting the UT field for out-of-range timestamps) and do not affect the patch’s correctness on 64-bit systems, where it works as intended. The broader thread’s unresolved questions—whether to reject or clamp ZIP legacy DOS dates, and how to handle negative timestamps in `git fast-import`—remain open. For now, this email highlights a tangential but important 32-bit compatibility issue that will need addressing before the patch can land cleanly across all platforms.

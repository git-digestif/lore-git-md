This is a **substantive review** of the second patch in the v3 series implementing the default `HEAD:.git-blame-ignore-revs` feature for `git blame`. Phillip Wood raises three technical concerns about the current design, all centered on usability and edge-case handling rather than correctness or security.

First, he questions the decision to ignore uncommitted changes to `.git-blame-ignore-revs` in non-bare repositories. The current patch always reads the committed `HEAD:.git-blame-ignore-revs` blob, even when the working tree contains a tracked but uncommitted version of the file. Phillip argues this is inconsistent with how Git handles other special files like `.gitattributes`, which respect uncommitted changes, and makes it inconvenient for users to test local modifications without explicitly passing the file path. He suggests automatically using the working-tree version when the path is tracked.

Second, he briefly considers whether the feature should support `.git-blame-ignore-revs` files in subdirectories but concludes it would be too expensive to implement, as it would require scanning all directories containing tracked files.

Third, he raises a potential scalability concern: the `oidset` implementation (using `khash`) appears to use 32-bit integers for entry counts, which could theoretically limit the ignore-revs file to 2³² entries. While this is unlikely to be a practical issue, he wonders if the parser should enforce a size limit similar to `.gitattributes` to prevent memory exhaustion from maliciously large blobs.

The review is constructive and focuses on user experience and edge cases rather than the core functionality. None of the points challenge the patch’s fundamental design or security hardening, and the author has already signaled willingness to adjust the implementation if Junio prefers. The thread remains approved for integration into `next`, pending a final decision on these minor refinements.

This is a **substantive review reply** from Phillip Wood on the `git blame` default ignore-revs file series (v3). It surfaces two **usability and security concerns** that remain unresolved despite Junio’s approval and the series’ pending integration into `next`.

First, Phillip questions the decision to **ignore uncommitted changes** to `.git-blame-ignore-revs` in non-bare repositories. The current implementation always reads the committed `HEAD` blob, which is inconsistent with how `.gitattributes` behaves (respecting uncommitted changes) and may inconvenience users testing local modifications. This is a **user-experience regression** relative to the status quo, where users can edit the ignore file and immediately see the effect in `git blame`.

Second, he flags a **potential security and scalability issue**: the `oidset` parser does not enforce a size limit on the ignore-revs file, which could theoretically allow memory exhaustion from maliciously large blobs. While the 32-bit entry count in `khash` makes this unlikely in practice, the lack of an explicit cap remains a loose end. This is not a new vulnerability (the existing `blame.ignoreRevsFile` parser has the same issue), but the default file lookup makes it more likely to be triggered by untrusted repositories.

The review is **medium-weight** — it does not challenge the core functionality or security hardening, but it raises **practical usability and robustness concerns** that could affect adoption. The author (Ravi Mistry) has not yet responded, and Junio’s approval does not address these points. If the series proceeds to `next` without changes, these issues may resurface as user complaints or follow-up patches.

This is the **implementation patch (4/4)** of the incremental connectivity check series, now in its third iteration. It introduces the core logic for the new `transfer.connectivityCheck=incremental` mode, which verifies incoming commits by comparing their trees against trusted parent trees rather than walking the full object closure of boundary commits. The patch adds the new `tree-verify.c` source file (316 lines) and integrates it into `builtin/rev-list.c` and `connected.c`.

The implementation uses an inductive trust model: parent trees are trusted (either from the boundary or from earlier verified commits), and each new tree is verified only where it differs from its parents. The algorithm tracks tree OIDs in three states (untrusted, trusted, expanded) and uses a merge-walk to collect same-path parent subtrees as comparison bases. Gitlinks (submodules) are skipped entirely, and promisor objects are handled by falling back to the full check when necessary. The patch preserves the existing subprocess architecture of `check_connected()`, ensuring that `die()` calls do not disrupt server-side operations like `git-receive-pack`.

Test coverage is extensive: the new `t5413-connectivity-check.sh` (680 lines) verifies semantic equivalence with the full check, corruption detection, promisor object handling, and integration with fetch/push/clone. The performance test suite (`t/perf/p5413-connectivity-check.sh`) benchmarks the incremental mode against the full check across repository size, incoming commit count, and files changed per commit, using synthetic repositories to isolate connectivity-check overhead. Benchmarks show dramatic speedups (up to 190x faster, 14 MB vs. 3.4 GB memory) for small pushes to large repos, with modest regressions (1.5x slower) for very long incoming histories (10,000+ commits).

The patch addresses all prior feedback: Junio’s NULL-dereference and lazy-fetch concerns, Patrick Steinhardt’s documentation and implementation questions, and the suggestion to split the series for reviewability. The incremental mode is now production-ready behind its opt-in config, with future work (MIDX-based connectivity closure, parallel ref loading) explicitly out of scope.

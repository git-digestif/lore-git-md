This thread is about preserving `change-id` headers—used by tools like Gerrit, GitButler, and Jujutsu—during Git operations like rebase, cherry-pick, and amend. The discussion has evolved from technical proposals to broader governance questions, with key participants including Nico Williams (proposing a policy/hook framework), Junio C Hamano (preferring trailer-based metadata), Phillip Wood (analyzing operational scenarios), and now brian m. carlson (raising privacy and security objections).

The latest contribution from Ewout ter Hoeven shifts the focus back to practical workflow needs, countering brian’s skepticism with concrete examples. Ewout highlights how GitHub’s `gh-stack` and GitLab’s `glab stack` struggle to maintain commit identity across rewrites, leading to broken tracking, redundant replays, and cascading errors—issues that `change-id` preservation could resolve. By citing real-world incidents (e.g., a 61-commit replay failure due to branch renames), Ewout grounds the debate in observable pain points, arguing that Git should provide a native solution rather than forcing tools to rely on fragile heuristics. However, this response does not address brian’s privacy concerns (e.g., metadata leakage), leaving the core tension unresolved: can the proposal balance workflow utility with security safeguards?

The thread remains at an impasse, with Nico’s policy/hook framework technically viable but facing governance hurdles. Junio’s trailer-based alternative is still on the table, while Phillip’s operational scenarios (cherry-picks, splits, squashes) await resolution. The next steps will likely hinge on whether the community prioritizes workflow integration (as Ewout advocates) over privacy risks (as brian warns), or if a compromise—such as opt-in behavior—can bridge the gap.

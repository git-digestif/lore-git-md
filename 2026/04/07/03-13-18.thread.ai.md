Thread identity: Feature patch to preserve 'change-id' header during rebase, cherry-pick, and amend operations, with Nico Williams, Junio C Hamano, Phillip Wood, brian m. carlson, and Ewout ter Hoeven as key participants. Core problem: Git currently drops change-id headers used by external tools during commit rewriting operations, forcing workflows that rely on persistent commit identity (e.g., stacked PRs, multi-commit reviews) to use fragile heuristics. The discussion now centers on whether change-id preservation can be reconciled with security constraints, particularly the risk of malicious header manipulation and the trust boundary between client-side and server-side operations.

Current status: Nico Williams' policy/hook proposal remains the leading technical framework, but brian m. carlson's security objections have introduced a **hard constraint**: change-id headers cannot be trusted as stable identifiers unless rewritten by a server-controlled process. Ewout ter Hoeven's workflow examples (GitHub `gh-stack`, GitLab `glab stack`) demonstrate tangible pain points (e.g., 61-commit replays due to branch renames), but brian's reply reframes the problem as a security boundary issue rather than a workflow convenience one. The thread now faces a fundamental tension between utility (client-side preservation) and security (server-side control).

Key technical details:
- Nico's strawman design components (project policies, named hooks, operation context options) still provide the technical foundation for change-id preservation, but their viability is now contingent on addressing the security boundary constraint.
- brian m. carlson's objections now include:
  * **Header mutability**: Users can manually edit change-id headers, enabling malicious reuse of reviewed IDs for unvetted commits.
  * **Trust boundary**: Only server-side rewrites (e.g., GitHub/GitLab performing rebase) can guarantee header immutability; client-side preservation is inherently untrustworthy for security-sensitive decisions.
  * **Automated review risks**: Tools like `gh-stack`/`glab stack` might assume preserved change-ids imply unchanged patches, creating attack vectors.
- Ewout's examples highlight specific failure modes in stacked PR workflows:
  * Branch renames break tracking in `gh-stack`/`glab stack`.
  * Rewritten commits trigger redundant replays (e.g., 61-commit incidents).
  * Patch ID mismatches cause cascading errors.
- Trailer-based approaches (Junio's preference) and hook-based extraction remain possible, but neither addresses the security boundary issue.
